## 04-01 配置体系总览与 startup.conf 全量参数详解

### 1. 本篇定位与覆盖范围

本篇是整册的「总钥匙」。VPP 的配置并非单一入口，而是由**三条相互独立又彼此衔接的通道**共同构成：其一是进程启动时一次性读取的 `startup.conf` 静态配置文件，决定进程骨架——堆大小、线程布局、DPDK 设备与驱动、缓冲池、插件加载、日志与统计段等；其二是运行期通过 `vppctl`（或 `exec` 脚本、TCP/Unix socket CLI）下发的 CLI 命令，负责创建接口、配置地址与路由、启用网络服务等，即时生效但默认不落盘；其三是控制面程序通过 Binary API 下发的消息，与 CLI 等价但面向编程集成（`04-07` 详述）。理解这三条通道的**作用时机、优先级与持久化差异**，是正确使用后续所有命令的前提。

`startup.conf` 是 VPP 主进程 `vpp` 的启动配置，默认路径通常为 `/etc/vpp/startup.conf`，也可由命令行 `vpp -c <path>` 显式指定（对应 `src/vpp/app/vpp_main.c` 的命令行解析逻辑）。它采用「节块（block）+ 键値」的自有语法：以 `节名 {` 开始、`}` 结束，节内每行一个 `键 值` 或 `子块 { ... }`；以 `#` 起始的行为注释；标量写在节内或作为顶层键。解析由 `VLIB_CONFIG_FUNCTION` / `VLIB_EARLY_CONFIG_FUNCTION` 注册的回调完成，各节回调散落在对应模块源码中（见本篇第 3 节逐项给出的路径）。**关键认知**：`startup.conf` 只在进程启动阶段读取一次，运行期修改文件不会影响已运行的实例；凡是运行期可动态调整的参数（接口状态、路由、地址等）都属于 CLI 或 API 通道，不属于本文件。

本篇覆盖 `unix{}`、`cpu{}`、`dpdk{}`、`buffers{}`、`plugins{}`、`logging{}`、`stats{}`（及新版 `statseg{}`）、`api-trace{}`、`api-segment{}`、`socksvr{}`、`session{}`、`tuntap{}`、`vhost-user{}`、`l2learn{}` 等全部常用节，以及 `heapsize`、`main-core`、`workers`、`cli-listen`、`name`、`poll-sleep-usec`、`coredump-size`、`cli-no-banner`、`cli-no-pager` 等顶层标量，逐节逐项给出取值、默认值、作用、示例与版本差异。本篇**不**讲这些参数在数据面内部如何影响转发、也不列对应结构体的字段——那属于 `06-xx` 与 `05-xx`。本节末尾用一张配置结构图，把三条通道与持久化关系一次性交代清楚（图 04-01-01）。

从图上要读出三条结论。第一，`startup.conf` 位于最上游，决定「进程能不能起来、以什么资源规模起来」，它一次读取、不可热更。第二，CLI 与 Binary API 并列作用于运行态数据面，`04-02` 会说明 CLI 命令最终大多被翻译成同名的 Binary API 消息，二者能力基本一致，`04-08` 给出命令↔API 映射表。第三，运行期的配置默认**不持久化**——重启即丢失，必须借助 `exec` 启动脚本或外部配置管理把命令序列固化，这正是 `04-07` 要解决的「配置持久化」问题。很多初学者把 `vppctl set interface ip address ...` 当作「已保存配置」，重启后发现地址没了，根源就在这张图的虚线没有被接上。

### 3. 逐项详解

以下按节逐项展开。每个参数统一用表 `参数 | 语法 | 取值 / 类型 | 作用 | 示例 | 版本差异` 描述（本册命令篇统一用带「对应 API」列的命令表，本篇针对**配置参数**改用参数表，二者不冲突）。表中「版本差异」列不能确认的，写「需对照实际版本核验」并给出源码路径。

#### 3.1 顶层标量：进程资源与 CLI 监听

顶层标量直接写在文件根部，不包在 `{}` 里，是最早期、最基础的一批开关。`heapsize` 决定 VPP 主堆（mheap）的初始上限，堆里存放接口表、FIB 表、会话表等大量运行期对象，生产环境一般显式设为 `2G` 或更大，过小会在表项规模上来后出现「内存分配失败」。`main-core` 与 `workers` 是线程布局的老式写法，功能上与 `cpu{}` 内的同名键重叠，但**优先级低于 `cpu{}`**：当两者同时出现时以 `cpu{}` 为准，混用会造成困惑，故推荐统一用 `cpu{}`（见 3.2）。`cli-listen` 在顶层语境下开启一个基于 TCP（或 socket）的 CLI 监听，格式常为 `localhost:5002`，供 `telnet` / `vppctl` 远程接入；它与 `unix{ cli-listen <path> }` 的 Unix 域套接字不是同一件事，需区分。

| 参数 | 语法 | 取值 / 类型 | 作用 | 示例 | 版本差异 |
|---|---|---|---|---|---|
| `heapsize` | `heapsize <size>` | `1G` / `512M` / `default` | 设定主堆大小，影响可容纳的表项规模 | `heapsize 4G` | 部分版本支持 `default` 交由系统决定，需对照 `src/vlib/vlib_main.c` 核验 |
| `main-core` | `main-core <n>` | 整数核号 | 把 main 线程绑定到指定核 | `main-core 0` | 与 `cpu{ main-core }` 优先级关系需对照 `src/vlib/threads.c` 核验 |
| `workers` | `workers <n>` | 整数 | 生成 n 个 worker 线程（不指定具体核） | `workers 4` | 新版推荐 `cpu{ corelist-workers }`，需对照核验 |
| `cli-listen` | `cli-listen <host:port\|path>` | 地址或路径 | 开启 TCP / socket CLI 监听 | `cli-listen localhost:5002` | 顶层与 `unix{}` 内同名键语义不同，需对照 `src/vlib/unix/main.c` 核验 |
| `name` | `name <str>` | 字符串 | 多实例场景区分实例 | `name vpp-router-a` | 稳定 |
| `poll-sleep-usec` | `poll-sleep-usec <n>` | 微秒整数 | 主循环空闲时休眠，牺牲时延换 CPU | `poll-sleep-usec 100` | 默认 `0`（纯轮询），取值语义需对照 `src/vlib/main.c` 核验 |
| `coredump-size` | `coredump-size <size>` | 大小 / `unlimited` | 限制 core 转储大小 | `coredump-size unlimited` | 与 `full-coredump` 配合，需对照核验 |
| `cli-no-banner` | `cli-no-banner` | 无值标志 | 关闭 CLI 启动横幅，便于脚本解析 | `cli-no-banner` | 稳定 |
| `cli-no-pager` | `cli-no-pager` | 无值标志 | 关闭 CLI 分页，避免脚本被 `more` 卡住 | `cli-no-pager` | 批处理 / 自动化必备 |
| `cli-prompt` | `cli-prompt <str>` | 字符串 | 自定义提示符 | `cli-prompt "vpp-a# "` | 是否支持引号内空格需对照 `src/vlib/unix/cli.c` 核验 |

`poll-sleep-usec` 值得特别说明：VPP 数据面默认是**忙轮询**，worker 核 100% 占用是正常现象。若设置了非零 `poll-sleep-usec`，空闲时会让出 CPU，能降低功耗与 CPU 观感，但会引入额外时延、破坏低时延保证，仅在非性能敏感的测试 / 开发环境使用。这一参数不改变转发行为，只改变调度方式，属于典型的「资源层」开关。

#### 3.2 `cpu{}`：线程与绑核

`cpu{}` 是现代 VPP 推荐的线程配置入口。`main-core` 指定主线程（负责 CLI、API、定时器、控制面事件）跑在哪个核，`corelist-workers` 用逗号 / 连写区间显式列出 worker 核（如 `2-5,8,10`），`workers` 则只给数量、由系统挑核。三者关系与优先级是本节的易错点：`corelist-workers` 一旦给出，`workers` 被忽略；`skip-cores` 会从可用核列表头部预留若干核（常用于给系统 / 其他进程留核）；`use-physical-cores` 在多路超线程机器上让 VPP 只用物理核、跳过超线程兄弟核。生产部署强烈建议**显式绑核**并配合 NUMA 亲和（原理见 `06-06`），否则 worker 可能被调度到远端 NUMA 节点，吞吐明显下降。

| 参数 | 语法 | 取值 / 类型 | 作用 | 示例 | 版本差异 |
|---|---|---|---|---|---|
| `main-core` | `main-core <n>` | 核号 | main 线程绑核 | `main-core 1` | 稳定 |
| `corelist-workers` | `corelist-workers <list>` | `2-5,8` 形式 | 显式指定 worker 核集合 | `corelist-workers 2-5,8` | 稳定，优先于 `workers` |
| `workers` | `workers <n>` | 整数 | worker 数量（自动挑核） | `workers 4` | 与 `corelist-workers` 互斥，需对照 `src/vlib/threads.c` 核验 |
| `skip-cores` | `skip-cores <n>` | 整数 | 预留前 n 核不用 | `skip-cores 2` | 部分版本存在，需对照核验 |
| `thread-prefix` | `thread-prefix <str>` | 字符串 | 线程名前缀，便于 `top -H` 识别 | `thread-prefix vpp-a` | 稳定 |
| `use-physical-cores` | `use-physical-cores` | 标志 | 跳过超线程逻辑核 | `use-physical-cores` | 较新版本引入，需对照核验 |

#### 3.3 `dpdk{}`：设备接管与驱动

`dpdk{}` 是把物理网卡从内核驱动交给用户态 PMD 的配置节，也是参数最多、版本变化最频繁的一节。核心是 `dev` 指令：既可用 `dev <PCI地址>` 逐个声明（如 `dev 0000:02:00.0`），也可写 `dev default { ... }` 子块为所有设备设置默认队列数、描述符数等，还可写 `dev <PCI地址> { name <iface> num-rx-queues <n> ... }` 对单设备定制。`uio-driver` 选择 `vfio-pci`（推荐，IOMMU 更安全）或 `uio_pci_generic` / `igb_uio`；`socket-mem` 按 NUMA 节点分配大页（如双路 `1024,1024`）；`hugepage-dir` 指向 hugetlbfs 挂载点。`no-multi-seg`、`no-tx-checksum-offload`、`enable-tcp-udp-checksum` 等是卸载 / mbuf 行为开关；`no-pci` 配合 `vdev` 可只跑虚拟设备（如 `net_af_packet`、`net_memif`），用于无物理网卡的容器 / 测试环境。

| 参数 | 语法 | 取值 / 类型 | 作用 | 示例 | 版本差异 |
|---|---|---|---|---|---|
| `dev` | `dev <pci\|default> [ { 子键 } ]` | PCI 地址 / 子块 | 声明接管设备或设默认参数 | `dev 0000:02:00.0` / `dev default { num-rx-queues 2 }` | 子键集合各版本差异大，需对照 `src/plugins/dpdk/device/init.c` 核验 |
| `uio-driver` | `uio-driver <name>` | `vfio-pci` / `uio_pci_generic` / `igb_uio` / `auto` | 指定用户态驱动 | `uio-driver vfio-pci` | `auto` 为较新默认，需对照核验 |
| `socket-mem` | `socket-mem <csv>` | 每 NUMA MB，逗号分隔 | 大页配额 | `socket-mem 1024,1024` | 与 `buffers{}` 配额联动，需对照核验 |
| `hugepage-dir` | `hugepage-dir <path>` | 路径 | hugetlbfs 挂载点 | `hugepage-dir /dev/hugepages` | 稳定 |
| `no-multi-seg` | `no-multi-seg` | 标志 | 禁用多段 mbuf | `no-multi-seg` | 影响巨型帧 / 分片，需对照核验 |
| `no-tx-checksum-offload` | `no-tx-checksum-offload` | 标志 | 关发送校验和卸载 | `no-tx-checksum-offload` | 排错时常用，需对照核验 |
| `no-pci` | `no-pci` | 标志 | 不扫描 PCI 总线 | `no-pci` | 与 `vdev` 联用 |
| `vdev` | `vdev <string>` | 虚拟设备串，可多次 | 创建 DPDK 虚拟设备 | `vdev net_af_packet0,iface=eth0` | 语法随 DPDK 版本变化，需对照核验 |
| `num-mbufs` | `num-mbufs <n>` | 整数 | mbuf 池总量 | `num-mbufs 32768` | 与 `buffers{}` 关系需对照核验 |
| `kni` | `kni <n>` | 整数 | KNI 接口数（旧特性） | `kni 1` | 新版多已移除 / 弱化，需对照核验 |
| `max-simd-bitwidth` | `max-simd-bitwidth <bits>` | `256` / `512` 等 | 限制 SIMD 位宽 | `max-simd-bitwidth 256` | 较新版本引入，需对照核验 |

`dev default{}` 子块常见子键包括 `num-rx-queues`、`num-tx-queues`、`num-rx-desc`、`num-tx-desc`、`rss`、`vlan-strip-offload`、`tso`、`name`、`workers` 等，用于统一队列规模。**注意**：这些子键的名称与取值在不同 VPP / DPDK 组合下增删频繁，不能凭记忆照抄，务必对照 `src/plugins/dpdk/device/init.c` 与随版本附带的 `/etc/vpp/startup.conf` 示例核验。这也是本册反复强调「需对照实际版本核验」的原因——`dpdk{}` 是整份配置里最不该凭经验硬写的一节。

#### 3.4 `buffers{}`：缓冲池规模

`buffers{}` 决定每 NUMA 节点预分配多少 buffer 以及每个 buffer 的数据区大小。`buffers-per-numa` 直接关系突发流量下的抗丢包能力，过小在高 PPS 场景会触发 `no buffers` 类错误（现象判读见 `08-04`，命令见 `04-06` 的 `show buffers` / `show errors`）；`default data-size` 默认约 2048 字节，若要支持巨型帧 / 隧道封装后大包，需调大，但会等比放大内存占用。`page-size` 选择底层页大小，通常保持 `default-hugepage` 即可。

| 参数 | 语法 | 取值 / 类型 | 作用 | 示例 | 版本差异 |
|---|---|---|---|---|---|
| `buffers-per-numa` | `buffers-per-numa <n>` | 整数 | 每 NUMA 缓冲数量 | `buffers-per-numa 65536` | 默认值随版本调整，需对照 `src/vlib/buffer_main.c` 核验 |
| `default data-size` | `default data-size <n>` | 字节整数 | 默认数据区大小 | `default data-size 2048` | 支持巨型帧需调大，需对照核验 |
| `page-size` | `page-size <v>` | `4K` / `2M` / `1G` / `default-hugepage` | 缓冲池页大小 | `page-size default-hugepage` | 取值集合需对照核验 |
| `numa{}` | `numa <id> { ... }` | 子块 | 按 NUMA 覆盖参数 | `numa 0 { buffers-per-numa 32768 }` | 是否支持及子键需对照核验 |

#### 3.5 `plugins{}`：能力装载

VPP 的绝大多数能力（DPDK、ACL、NAT、IPsec、LB、VXLAN……）以插件形式提供，默认会加载编译产物目录下的全部 `.so`。`plugins{}` 用来精确控制：`path` 指定插件搜索目录；`plugin default { disable }` 先把所有插件默认关闭，再用一条条 `plugin <name>.so { enable }` 白名单式开启，这是生产环境收敛攻击面 / 减少启动耗时的推荐做法；也可反过来默认全开、用 `disable` 关掉个别插件。插件名必须与 `.so` 文件名一致（如 `dpdk_plugin.so`、`acl_plugin.so`），写错名字插件不会加载且往往只在日志里留一条告警。

| 参数 | 语法 | 取值 / 类型 | 作用 | 示例 | 版本差异 |
|---|---|---|---|---|---|
| `path` | `path <dir>` | 目录 | 插件 .so 搜索路径 | `path /usr/lib/x86_64-linux-gnu/vpp_plugins` | 稳定 |
| `plugin default` | `plugin default { disable }` | 子块 | 默认禁用全部插件 | `plugin default { disable }` | 稳定 |
| `plugin X` | `plugin <name> { enable\|disable }` | 插件名 + 动作 | 单独启停某插件 | `plugin dpdk_plugin.so { enable }` | 稳定 |
| 插件参数 | `plugin X { <key> <val> }` | 依插件 | 向插件传私有参数 | 见各插件文档 | 私有参数各异，需对照对应插件源码核验 |

#### 3.6 `logging{}`：日志分级

VPP 日志按「类（class）」组织，每个类有独立级别与限流。`default-log-level` 设定全局默认级别（级别序列 `emerg / alert / crit / err / warn / notice / info / debug / disabled`），`default-syslog-log-level` 控制发往 syslog 的级别，`class <name> { rate-limit <N> level <L> }` 可把某一类（如 `dpdk`、`acl`）单独调到 `debug` 并限制每秒条数，避免刷屏。运行期还可用 CLI `set logging class ... level ...`（命令见 `04-06`）动态调整，二者配合：启动配置定基调、CLI 做临时排查。

| 参数 | 语法 | 取值 / 类型 | 作用 | 示例 | 版本差异 |
|---|---|---|---|---|---|
| `default-log-level` | `default-log-level <L>` | 级别枚举 | 全局默认日志级别 | `default-log-level info` | 级别集合稳定 |
| `default-syslog-log-level` | `default-syslog-log-level <L>` | 级别枚举 | syslog 默认级别 | `default-syslog-log-level warning` | 默认值需对照 `src/vlib/log.c` 核验 |
| `class` | `class <name> { rate-limit <N> level <L> }` | 类名 / 整数 / 级别 | 按类细粒度控制 | `class dpdk { rate-limit 100 level debug }` | 类名清单需对照 `src/vlib/log.c` 核验 |

#### 3.7 `stats{}` / `statseg{}`：统计段

`stats{}`（较新版本更名 / 演化为 `statseg{}`）配置统计共享内存段（stat segment）：`interval` 是统计刷新周期，`seg-size` / `size` 是段大小，`per-node-counters on` 打开每节点计数器（会增大内存与开销，但排错时是 `show node` / `show errors` 精细数据的来源，命令见 `04-06`），`page-size` 选页大小。**注意节名与键名的版本漂移**：老配置写 `stats { interval 1 seg-size 2G }`，新配置可能写 `statseg { size 2G per-node-counters on }`，迁移时必须对照当前版本示例，不能照搬旧文件。

| 参数 | 语法 | 取值 / 类型 | 作用 | 示例 | 版本差异 |
|---|---|---|---|---|---|
| `interval` | `interval <sec>` | 浮点秒 | 统计刷新间隔 | `interval 1` | 所属节名 `stats`/`statseg` 存在版本差异，需对照 `src/vpp/app/vpp_main.c` 核验 |
| `seg-size` / `size` | `seg-size <size>` / `size <size>` | 带单位大小 | 统计段共享内存大小 | `seg-size 2G` | 键名 `seg-size` 与 `size` 随版本变化，需对照核验 |
| `per-node-counters` | `per-node-counters on\|off` | 开关 | 每节点计数器 | `per-node-counters on` | 较新版本提供，需对照核验 |
| `page-size` | `page-size <v>` | 页大小 | 统计段页大小 | `page-size 2M` | 需对照核验 |

#### 3.8 `api-trace{}` / `api-segment{}` / `socksvr{}`：控制面通道

这三节服务于控制面（编程用法见 `04-07`，消息机制原理见 `06-13`，本册只列配置）。`api-trace{}` 打开后会把收发的 Binary API 消息记录进环形缓冲（`nitems` 条），用于 `show api trace`（命令见 `04-06`）回看控制面下发了什么，是排查「配置到底有没有下发成功」的利器；`save-api-table` 可导出消息名对照表。`api-segment{}` 管理 API 共享内存区的大小与属组（`gid`、`global-size`、`api-size`、`baseva` 等），客户端与服务端必须就同一段达成一致。`socksvr{}` 指定 Binary API 的 Unix socket 路径（`socket-name`，默认 `/run/vpp/api.sock`），`default` 表示用内置默认名。

| 参数 | 语法 | 取值 / 类型 | 作用 | 示例 | 版本差异 |
|---|---|---|---|---|---|
| `on` / `off` | `on` / `off` | 标志 | 开关 API 消息追踪 | `on` | 稳定 |
| `nitems` | `nitems <n>` | 整数 | 追踪环形缓冲条数 | `nitems 5000` | 默认值需对照 `src/vlib/api/api_trace.c` 核验 |
| `save-api-table` | `save-api-table <path>` | 文件路径 | 导出消息名表 | `save-api-table /tmp/api-table` | 需对照核验 |
| `gid` | `gid <group>` | 组名 / id | API 共享内存属组 | `gid vpp` | 需对照 `src/vlibmemory/` 核验 |
| `global-size` 等 | `global-size <size>` | 带单位大小 | 全局 / 私有 / API 区大小 | `global-size 64M` | 键集合需对照核验 |
| `baseva` | `baseva <hex>` | 十六进制地址 | 共享内存基址 | `baseva 0x7fff00000000` | 高级项，需对照核验 |
| `socket-name` | `socket-name <path>` | 文件路径 | Binary API socket 路径 | `socket-name /run/vpp/api.sock` | 默认路径需对照 `src/vlibmemory/` 核验 |
| `default` | `default` | 标志 | 采用默认 socket 名 | `default` | 稳定 |

#### 3.9 其余功能节：`session{}` / `tuntap{}` / `vhost-user{}` / `l2learn{}`

这些节按启用的特性按需出现。`session{}` 打开 VPP 主机协议栈的 session / transport 层（VCL 编程依赖，见 `04-07`）；`tuntap{}` 控制 tun/tap 设备行为；`vhost-user{}` 调整 vhost 收包聚合（帧数 / 时间）与内存转储行为；`l2learn{}` 限制 MAC 学习表规模。它们的共同点是**参数少、专用性强、随特性启用才生效**，且不同版本子键增删明显，故此处只列作用与示例方向，具体键名一律以对应特性源码与版本示例为准。

| 参数 | 语法 | 取值 / 类型 | 作用 | 示例 | 版本差异 |
|---|---|---|---|---|---|
| `session{}` | `session { enable }` | 标志 | 启用主机栈 session 层 | `session { enable }` | 子键随版本变化，需对照 `src/vnet/session/` 核验 |
| `tuntap{}` | `tuntap { enable ... }` | 标志 | tun/tap 设备行为 | `tuntap { ethernet }` | 子键需对照 `src/vnet/tuntap/` 核验 |
| `vhost-user{}` | `vhost-user { coalesce-frames N }` | 整数 / 标志 | vhost 收包聚合 | `vhost-user { coalesce-frames 32 }` | 子键需对照 `src/vnet/devices/virtio/` 核验 |
| `l2learn{}` | `l2learn { limit N }` | 整数 | MAC 学习表上限 | `l2learn { limit 10000 }` | 需对照 `src/vnet/l2/` 核验 |

### 4. 典型示例

下面给出一份「生产可用」的 `startup.conf` 骨架，覆盖资源、设备、能力、观测四条链。示例中的具体取值仅示范写法，落地时必须按机器核数、NUMA、大页与网卡 PCI 地址调整，并对照随版本附带的 `/etc/vpp/startup.conf` 核验键名。

```bash
unix {
  nodaemon
  log /var/log/vpp/vpp.log
  full-coredump
  cli-listen /run/vpp/cli.sock
  gid vpp
  startup-config /etc/vpp/startup.conf
  # 启动后自动回放运行期配置（配置持久化，见 04-07）
  exec /etc/vpp/init.conf
}

cpu {
  main-core 0
  corelist-workers 2-5
  thread-prefix vpp-a
}

buffers {
  buffers-per-numa 65536
  default data-size 2048
}

dpdk {
  dev default {
    num-rx-queues 2
    num-tx-queues 2
  }
  dev 0000:02:00.0
  dev 0000:02:00.1
  uio-driver vfio-pci
  socket-mem 1024,1024
  hugepage-dir /dev/hugepages
  no-multi-seg
}

plugins {
  path /usr/lib/x86_64-linux-gnu/vpp_plugins
  plugin default { disable }
  plugin dpdk_plugin.so { enable }
  plugin acl_plugin.so { enable }
  plugin nat_plugin.so { enable }
}

logging {
  default-log-level info
  default-syslog-log-level warning
  class dpdk { rate-limit 100 level debug }
}

statseg {
  size 2G
  per-node-counters on
}

api-trace { on
  nitems 5000
}

socksvr {
  default
}

heapsize 4G
```

对这份示例要做几点说明。第一，`unix{ exec /etc/vpp/init.conf }` 是把运行期 CLI 命令固化下来的关键一行（持久化，见 `04-07`），`init.conf` 里通常是若干 `set interface ...` / `ip route ...` 命令，启动时由 VPP 自动回放，等价于人工敲一遍 `vppctl exec`。第二，`cpu{}` 显式绑核、`buffers{}` 放大缓冲、`heapsize 4G` 三者共同决定资源规模，三者需按内存预算一起算，避免大页 + 缓冲 + 堆超出物理内存。第三，`plugins{}` 采用「默认全关 + 白名单开启」，这是收敛启动项、便于排错的好习惯。第四，`statseg`/`api-trace`/`socksvr` 把可观测性与控制面通道一次性配齐，后续 `04-06` 的 `show` / `trace` 命令、`04-07` 的 API 集成才有数据可用。

针对**无物理网卡的容器 / 测试环境**，可把 `dpdk{}` 换成 `no-pci` + `vdev`，并用顶层 `cli-listen` 开一个 TCP CLI 便于远程接入：

```bash
unix { nodaemon cli-listen /run/vpp/cli.sock }
dpdk {
  no-pci
  vdev net_af_packet0,iface=eth0
}
cpu { main-core 0 workers 1 }
cli-listen 0.0.0.0:5002
cli-no-pager
```

### 5. 速查表

按「我想调什么 → 改哪里」组织的高频速查表，便于日常定位。

| 诉求 | 改动的节 / 键 | 典型取值 | 是否需重启 |
|---|---|---|---|
| 提高并发吞吐，加 worker | `cpu{ corelist-workers }` 或 `cpu{ workers }` | `2-7` | 是 |
| 绑定 main 线程核 | `cpu{ main-core }` | `0` | 是 |
| 大流量下 buffer 不够 | `buffers{ buffers-per-numa }` | `65536` | 是 |
| 支持巨型帧 / 大封装包 | `buffers{ default data-size }` | `9000` | 是 |
| 堆内存不足 | 顶层 `heapsize` | `4G` | 是 |
| 接管某张物理网卡 | `dpdk{ dev }` | `0000:02:00.0` | 是 |
| 换用户态驱动 | `dpdk{ uio-driver }` | `vfio-pci` | 是 |
| 每 NUMA 大页配额 | `dpdk{ socket-mem }` | `1024,1024` | 是 |
| 只启用指定插件 | `plugins{ default{disable} + plugin X{enable} }` | 白名单 | 是 |
| 全局调日志级别 | `logging{ default-log-level }` | `debug` | 是（也可 CLI 临时调） |
| 打开每节点计数 | `statseg/stats{ per-node-counters on }` | `on` | 是 |
| 回看控制面消息 | `api-trace{ on }` | `on` | 是 |
| 改 Binary API socket | `socksvr{ socket-name }` | 路径 | 是 |
| 开 TCP CLI 远程接入 | 顶层 `cli-listen` | `0.0.0.0:5002` | 是 |
| 启动自动加载运行期配置 | `unix{ exec }` | 文件路径 | 是 |
| 前台调试不 daemon | `unix{ nodaemon }` | 标志 | 是 |

一句话记忆：**凡属 `startup.conf` 的参数，改动一律需要重启进程才生效（日志类可再用 CLI 临时覆盖）；凡属运行期接口 / 路由 / 服务配置，走 CLI/API 即时生效但不落盘，需要 `exec` 持久化**。

### 6. 版本差异

`startup.conf` 是 VPP 版本中漂移最明显的配置面。下表列出 23.06 相对更早版本（20.x / 21.x / 22.x）需要重点核对的差异方向；由于具体版本号与行为可能随 patch 变化，落地前一律以目标版本自带的 `/etc/vpp/startup.conf` 示例与对应源码为准。

| 差异主题 | 早期写法 | 23.06 / master 方向 | 核验位置 |
|---|---|---|---|
| 线程配置 | 顶层 `main-core` / `workers` 为主 | 推荐统一到 `cpu{}`，支持 `corelist-workers`、`use-physical-cores` | `src/vlib/threads.c` |
| 统计段 | `stats { interval ... seg-size ... }` | 演化为 `statseg { size ... per-node-counters ... }`，键名与节名变化 | `src/vpp/app/vpp_main.c` |
| DPDK 设备默认参数 | `dev <pci>` 简单形式 | `dev default { ... }` 子块统设队列 / 描述符，子键增删频繁 | `src/plugins/dpdk/device/init.c` |
| DPDK SIMD 限制 | 无 | 新增 `max-simd-bitwidth` 一类开关 | `src/plugins/dpdk/device/init.c` |
| KNI | `kni N` 可用 | 多已弱化 / 移除，需改用其他机制 | `src/plugins/dpdk/device/init.c` |
| 插件默认行为 | 全部自动加载 | 仍默认全加载，但白名单式 `plugin default{disable}` 更推荐 | `src/vlib/unix/plugin.c` |
| CLI socket | `unix{ cli-listen }` 与顶层 `cli-listen` 并存 | 二者语义区分更明确，顶层偏 TCP、节内偏 Unix socket | `src/vlib/unix/main.c` |
| 日志分级 | 较粗 | `logging{}` 支持按 class + rate-limit 细粒度限流 | `src/vlib/log.c` |
| 主机栈 session | 实验性 | `session{}` 与 VCL 生态趋于稳定 | `src/vnet/session/` |

迁移建议：把旧 `startup.conf` 逐节对照新版本示例「改名、改节、改键」，尤其优先处理 `stats→statseg`、线程参数归一到 `cpu{}`、`dpdk{}` 子块三处；改完先以 `unix{ nodaemon }` 前台启动，观察启动日志里是否有「unknown config / unknown parameter」类告警，这类告警正是键名写错 / 版本不匹配最直接的信号。

### 7. 常见误用与调试

本节按「现象 → 根因 → 处理」列高频误用。所有参数级错误几乎都能在**前台启动日志**（`nodaemon` + `log` 指定文件）里看到线索，因此排错第一步永远是「前台跑、看日志」。

| 误用 / 现象 | 根因 | 处理 / 定位 |
|---|---|---|
| 改了 `startup.conf` 不生效 | 只在启动期读一次 | 重启 VPP 进程；确认用 `vpp -c <path>` 指向的是在改的那份文件 |
| 启动报 unknown parameter / unknown section | 键名或节名版本不匹配（如把 `statseg` 写成 `stats`） | 对照目标版本 `/etc/vpp/startup.conf` 示例与对应源码改名；查前台启动日志 |
| `main-core`/`workers` 与 `cpu{}` 同时写，行为不符预期 | 两套写法优先级不同、被覆盖 | 统一只用 `cpu{}`，删除顶层同名键 |
| 插件没加载，相关 CLI 命令报「unknown command」 | `plugins{}` 白名单漏开 / 插件名写错 / `path` 不对 | 查日志插件加载行，核对 `.so` 文件名与 `path` |
| worker 起来但吞吐抖动、跨 NUMA | 未绑核 / `socket-mem` 与网卡 NUMA 不匹配 | `cpu{ corelist-workers }` 绑核、`socket-mem` 按 NUMA 配；原理见 `06-06` |
| 高 PPS 下丢包、`show errors` 出现缓冲相关计数 | `buffers-per-numa` 过小 | 放大 `buffers{}`，并用 `04-06` 的 `show buffers` / `show errors` 复核 |
| 巨型帧 / 隧道大包被丢 | `default data-size` 不足 | 调大 `buffers{ default data-size }` 并同步评估内存 |
| `api-trace` 打开却看不到消息 | `nitems` 太小被冲掉 / 未真正 `on` | 增大 `nitems`，用 `04-06` 的 `show api trace` 复核 |
| 远程 `vppctl` 连不上 | 顶层 `cli-listen` 未开 / 防火墙 / 用了 Unix socket 却按 TCP 连 | 区分顶层 TCP `cli-listen` 与 `unix{ cli-listen }`，核对 `netstat` 与 `gid` 权限 |
| 脚本化 `vppctl` 被分页 / 横幅干扰 | 未关 pager / banner | 顶层 `cli-no-pager` / `cli-no-banner`，或 `vppctl` 用批处理模式 |
| 重启后地址 / 路由全丢 | 误以为 CLI 配置已持久化 | 用 `unix{ exec }` 或外部配置管理固化命令，见 `04-07` |
| 容器内无物理网卡，DPDK 启动失败 | 仍按 PCI 设备配置 | 用 `dpdk{ no-pci vdev ... }` 或改用 af_packet / memif 类接口（命令见 `04-03`） |

调试方法论可以概括为三板斧：其一，**前台 + 日志**——`unix{ nodaemon log /var/log/vpp/vpp.log }` 让所有配置解析告警可见；其二，**对照示例**——任何拿不准的键名，先查目标版本自带 `/etc/vpp/startup.conf` 与 `src/vpp/conf/startup.conf`；其三，**分层验证**——先确认进程与线程（`show threads` / `show cpu`，见 `04-06`）、再确认缓冲与设备（`show buffers` / `show hardware` / `show interface`）、最后确认控制面通道（`show api` / `show version`），逐层缩小范围。切记本册只负责「参数与命令」，一旦定位到是转发逻辑、节点错误计数语义或结构体层面的问题，应转 `06-xx`（原理）、`07-xx`（模块功能）与 `05-xx`（结构体字段），不要在本册反复徘徊。

## 04-02 CLI 基础与命令注册机制

### 1. 本篇定位与覆盖范围

上一篇讲清了「进程怎么启动」，本篇讲清「启动之后人怎么跟它对话」。VPP 的命令行接口（CLI）是运维与开发最直接的交互面：`vppctl` 是官方客户端，通过 Unix 域套接字（默认 `/run/vpp/cli.sock`，由 `04-01` 的 `unix{ cli-listen }` 指定）或 TCP 监听（顶层 `cli-listen`）连到 VPP 进程，建立一个 **CLI session**，把用户敲入的文本行送进进程内的命令解析器，再把输出回写到终端。理解 CLI 不只是会用几条命令，更要理解三件事：命令行的**语法约定**（分词、`?` 帮助、补全、引号、注释）、命令的**注册机制**（`VLIB_CLI_COMMAND` 宏、命令树、分发回调）、以及**脚本化 / 持久化**能力（`exec`、`show run`、`show startup-config`）。这三点决定了后续 `04-03` 到 `04-06` 上千条命令「为什么长这样」「敲错了会怎样」「怎么批量回放」。

本篇覆盖：`vppctl` 的交互与批处理两种模式、CLI session 与 socket 通道、`?` / `help` / Tab 补全 / 历史 / 分页、命令行的分词与引号规则、`VLIB_CLI_COMMAND` 注册宏及其注册项字段的含义（只讲**用途与用法**，不逐字段展开结构体定义——字段见 `05-xx`）、命令树按 path 分词的构建与最长匹配分发、`exec` 脚本回放、`show run` / `show startup-config` 导出当前配置、命令返回值与错误提示、以及自定义 CLI 命令的开发骨架。本篇还会给出一张 CLI 注册与分发流程图。

**去重边界**：命令注册与分发的「机制 / 调用链」若深挖到调度与内存布局，属于 `06-xx`（尤其 `06-11` 插件与 `06-13` API 机制）；`vlib_cli_command_t` 等结构体的逐字段定义属于 `05-xx`。本篇只停留在「作为命令作者 / 使用者需要知道的注册方式、语法与分发规则」这一层，讲宏怎么用、命令树怎么查、脚本怎么跑，不展开内部实现。命令本体清单从第 `04-03` 篇开始逐族穷举，本篇只覆盖 CLI 这一层「元命令」。

### 3. 逐项详解

本册命令逐项详解统一采用 `命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异` 七列表。对每个命令族，先以文字说明其使用场景与约定，再给表；表中「对应 API」对 CLI 元命令多为「CLI only」，这是客观事实而非占位。

#### 3.1 `vppctl` 与 CLI session

`vppctl` 有两种工作模式。不带参数直接运行进入**交互模式**，建立长连接 session，支持 `?` 帮助、Tab 补全、命令历史（上下键）、分页（`more`，可用 `04-01` 的 `cli-no-pager` 关闭）；把命令串作为参数传入（如 `vppctl show interface`）则进入**批处理模式**：连上、执行、打印、断开，适合脚本与自动化。多实例或用非默认 socket 时，用 `-s <socket路径>` 指定；对应的服务端监听由 `04-01` 的 `unix{ cli-listen }`（Unix socket）或顶层 `cli-listen`（TCP）提供，二者路径 / 端口要与客户端一致，权限受 `unix{ gid }` 与 socket 文件属组约束。一个常被忽略的点：`vppctl` 依赖 VPP 进程已启动并创建好 socket，若进程没起来或 socket 路径写错，典型报错是连接被拒——这时应先查进程状态与 `04-01` 的监听配置，而不是怀疑命令本身。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 交互模式 | `vppctl` | 无 | 进入交互 CLI session | CLI only | `vppctl` 后敲 `show version` | 稳定 |
| 批处理模式 | `vppctl <command...>` | 命令与参数 | 执行一次即退出，供脚本调用 | CLI only | `vppctl show interface addr` | 稳定 |
| 指定 socket | `vppctl -s <path> <cmd>` | `-s` socket 路径 | 连接非默认 socket / 多实例 | CLI only | `vppctl -s /run/vpp/cli-a.sock show version` | 选项名需对照 `src/vpp/app/vppctl.c` 核验 |
| TCP CLI | `telnet <host> <port>` | 主机、端口 | 连接顶层 `cli-listen` 开启的 TCP CLI | CLI only | `telnet 127.0.0.1 5002` | 需在 `startup.conf` 开顶层 `cli-listen` |

#### 3.2 命令行语法与帮助体系

VPP CLI 按**空格分词**把一行拆成 token，逐级与命令树匹配；带空格的字符串（如接口 tag、文件路径）需用引号包裹。`?` 是核心帮助键：在行尾敲 `?` 列出当前层级所有可选 token，在某个 token 后敲 `?` 显示该参数的取值提示；`help <command>` 给出命令完整说明。命令支持**唯一前缀缩写**（只要前缀唯一即可命中），这是老手的效率工具，但脚本里建议写完整命令以免版本升级后出现新的前缀冲突。注释以 `#` 起始，交互与 `exec` 脚本里都可用。分页默认开启，长输出（如 `show interface` 全量）会停在一屏，脚本化时务必用 `cli-no-pager` 或 `vppctl` 批处理避免卡住。历史与行编辑由 CLI session 提供，交互模式下上下键回溯。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 帮助 | `?` / `<token> ?` | 可跟命令前缀 | 列出可选命令 / 参数提示 | CLI only | `show ?`、`set interface ?` | 稳定 |
| 完整帮助 | `help <command>` | 命令名 | 显示命令完整用法 | CLI only | `help show interface` | 输出格式随版本微调，需核验 |
| 前缀缩写 | `<unique-prefix>` | 唯一前缀 | 命中命令的简写 | CLI only | `sh int` 代替 `show interface`（若唯一） | 脚本不建议依赖，需核验 |
| 注释 | `# <text>` | 文本 | 命令行注释 | CLI only | `# 配置上行口` | 稳定 |
| 引号 | `"<string with space>"` | 字符串 | 包裹含空格参数 | CLI only | `set interface tag GigabitEthernet0/8/0 "uplink-a"` | 转义规则需对照 `src/vlib/unix/cli.c` 核验 |
| 退出 | `quit` / `exit` | 无 | 关闭交互 session | CLI only | `quit` | 稳定 |

#### 3.3 命令注册：`VLIB_CLI_COMMAND` 宏

作为命令**作者**（写插件 / 模块时），注册一条 CLI 命令的标准方式是使用 `VLIB_CLI_COMMAND` 宏（定义于 `src/vlib/cli.h`）。开发者定义一个 `vlib_cli_command_t` 类型的静态变量，填入命令 path（如 `show myplugin status`）、简短帮助 `short_help`、长帮助 `long_help`（可选）、以及命令回调函数 `function`，再用宏把它登记到全局注册链；VPP 启动时遍历这些注册项按 path 分词构建命令树。回调签名形如接收 `vlib_main_t *`、`unformat_input_t *`（已解析的输入）、`vlib_cli_command_t *`，返回 `clib_error_t *`——返回非空表示出错，CLI 会把错误文本回显给用户。**这里只讲宏的用法与回调契约**：`vlib_cli_command_t` 的逐字段定义、注册链的内存组织属于 `05-xx`，命令树构建的具体调度属于 `06-11`，本篇不重复展开。参数解析用 `unformat` 系列（如 `unformat_check_input`、`unformat (%U, ...)`）从输入里取值，这是 VPP CLI 开发的通用套路。

| 命令 / 符号 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 注册宏 | `VLIB_CLI_COMMAND (cmd_var, static)` | 注册变量名 | 把命令登记进全局注册链 | CLI only（注册宏） | `VLIB_CLI_COMMAND (my_show_cmd, static);` | 稳定 |
| 注册项 | `static vlib_cli_command_t my_show_cmd = { ... }` | `.path` / `.short_help` / `.function` | 定义命令的路径、帮助、回调 | CLI only | `.path = "show myplugin status"` | 字段名需对照 `src/vlib/cli.h` 核验（字段见 `05-xx`） |
| 回调 | `static clib_error_t * fn (...)` | `vm` / `input` / `cmd` | 命令执行体，返回错误对象 | CLI only | 见 4.1 代码骨架 | 签名需对照 `src/vlib/cli.h` 核验 |
| 参数解析 | `unformat (input, "...")` | 格式串 + 出参 | 从命令行 token 解析参数 | CLI only | `unformat (input, "%U", unformat_vnet_sw_interface, ...)` | 格式符随 helper 变化，需核验 |
| 错误返回 | `clib_error_return (0, "msg")` | 错误码 / 文本 | 构造并返回错误 | CLI only | `return clib_error_return (0, "bad arg");` | 稳定 |

#### 3.4 命令树与分发

分发规则是 CLI 的「隐形骨架」，理解它能解释很多现象。所有注册命令的 `path` 按空格切成 token，插入一棵前缀树；例如 `show interface`、`show interface address`、`show interface features` 共享 `show`→`interface` 前缀，树把公共前缀合并。用户输入一行后，解析器从左到右逐 token 在树里下探，做**最长有效匹配**，命中叶节点后调用其 `function` 回调，剩余 token 作为 `unformat_input_t` 交给回调自行解析。这解释了三件事：其一，为什么 `?` 能列出「当前层所有可选项」——它就是把当前树节点的子边列出来；其二，为什么 `show interface ?` 能精确提示——它下探到 `interface` 节点再列子边；其三，为什么命令写错时报的是「unknown input / no such command」而非模糊匹配——树没有命中路径就直接回错。下面的配图把「注册 → 建树 → 输入 → 查找 → 回调 → 回译为 API」的完整链路串起来（图 04-02-01）。

:::figure id=04-02-01 | name=CLI 命令注册与分发流程 | dir=TD
node macro "VLIB_CLI_COMMAND 宏<br/>模块/插件定义命令" blue
node item "vlib_cli_command_t 注册项<br/>path / short_help / function" teal
node tree "命令树<br/>按 path 分词建前缀索引" teal
node input "vppctl / socket 输入命令行" amber
node parse "CLI 解析<br/>分词 / 引号 / ? 帮助补全" amber
node lookup "命令树查找<br/>最长有效匹配" purple
node func "调用 function 回调<br/>unformat 取参" purple
node api "回译 Binary API 消息<br/>或直接操作运行态" teal
node out "输出回写 CLI session" green
edge macro -> item "静态注册"
edge item -> tree "启动建树"
edge input -> parse
edge parse -> lookup
edge tree -> lookup dashed "提供索引"
edge lookup -> func "命中"
edge func -> api
edge api -> out
edge out -> input dashed "下一条命令"
:::

图中「回译 Binary API 消息」这一环值得强调：`04-07` 会讲到，VPP 绝大多数 CLI 命令与 Binary API 消息是一一对应的——CLI 回调往往就是把参数打包成一条 API 消息再走内部通道，因此「CLI 能做的，程序基本也能做」。这也是 `04-08` 命令↔API 映射表存在的意义。但**元命令**（`?`、`exec`、`show run` 等）是 CLI session 自身的能力，不下沉为数据面 API，故无对应消息。

#### 3.5 `exec`、`show run` 与配置持久化入口

`exec` 有两层含义：作为 CLI 元命令，`exec <file>` 会把指定文件里的每一行当作命令回放（脚本里可含注释、空行）；作为 `04-01` 的 `unix{ exec /path }` 启动项，VPP 启动时会自动回放该文件，这是**运行期配置持久化**最朴素的方案。`show run`（部分版本以 `show startup-config` / 等价导出命令呈现）尝试把当前运行态里「可导出的配置」反向生成一串等价 CLI 命令，便于备份或迁移到另一台机器。要注意：运行态里并非所有状态都能导出（动态学习到的 MAC、NAT 会话、统计计数等不属于「配置」），`show run` 输出的是**可重放的配置命令**，不是完整状态快照。把 `show run` 的输出保存到 `init.conf`、再用 `unix{ exec }` 加载，就构成了「配置保存 → 开机恢复」的闭环，这正是 `04-07` 要展开的配置持久化主线。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 回放脚本 | `exec <file>` | 文件路径 | 逐行执行文件中的命令 | CLI only | `exec /etc/vpp/init.conf` | 稳定 |
| 执行一行 | `exec "<line>"` | 命令行字符串 | 直接执行给定一行 | CLI only | `exec "set interface state loop0 up"` | 与文件形式是否同源需核验 |
| 导出配置 | `show run` | 无 | 导出当前可重放配置命令 | 视实现，需核验 | `show run > /tmp/run.conf` | 命令名 / 输出范围随版本变化，需对照 `src/vlib/unix/cli.c` 核验 |
| 启动配置 | `show startup-config` | 无 | 显示启动配置相关内容 | CLI only | `show startup-config` | 与 `show run` 是否合并随版本变化，需核验 |
| 启动项 | `unix { exec <file> }` | 文件路径 | 启动即自动回放（配置项） | CLI only | `unix { exec /etc/vpp/init.conf }` | 见 `04-01` |

#### 3.6 命令返回值与错误处理

CLI 回调通过 `clib_error_t *` 表达结果：返回空指针表示成功，返回非空表示失败，CLI 层把错误文本回显到当前 session 并通常附带命令用法提示。因此从使用者角度，命令失败时看到的「what went wrong」文本，往往就是回调里 `clib_error_return` 写的那句话。批处理模式下，命令失败还会影响 `vppctl` 的进程退出码（具体映射需对照 `src/vpp/app/vppctl.c` 核验），脚本应据此判断成败，而不是只 grep 输出文字。理解这一约定，能把「命令没生效」的排查收敛到两个方向：要么是参数解析失败（回调返回错误、看回显文本），要么是命令成功但配置未持久化（重启丢失，转 `04-07`）。

### 4. 典型示例

#### 4.1 自定义 CLI 命令的 C 骨架

下面给出一个最小的「注册一条 `show myplugin status` 命令」骨架，用于说明 `VLIB_CLI_COMMAND` 的用法契约。字段与签名请对照 `src/vlib/cli.h` 核验（结构体字段见 `05-xx`），本例只示意注册方式，不展开内部实现。

```c
#include <vlib/vlib.h>
#include <vlib/unix/unix.h>

static clib_error_t *
myplugin_status_fn (vlib_main_t * vm,
                    unformat_input_t * input,
                    vlib_cli_command_t * cmd)
{
  /* 用 unformat 解析可选参数，例如是否带 detail */
  int detail = 0;
  while (unformat_check_input (input) != UNFORMAT_END_OF_INPUT)
    {
      if (unformat (input, "detail"))
        detail = 1;
      else
        return clib_error_return (0, "unknown input `%U'",
                                  format_unformat_error, input);
    }
  vlib_cli_output (vm, "myplugin: ok, detail=%d", detail);
  return 0; /* 空 = 成功 */
}

/* 注册项：path 决定命令树位置，function 指向回调 */
VLIB_CLI_COMMAND (myplugin_status_cmd, static) = {
  .path = "show myplugin status",
  .short_help = "show myplugin status [detail]",
  .function = myplugin_status_fn,
};
```

要点：`.path` 的字符串直接决定命令在树里的层级，`show myplugin status` 会挂到 `show` 节点之下；`.short_help` 供 `?` 显示；`.function` 是执行体；回调里用 `vlib_cli_output` 把结果写回当前 session。把这段编译进模块 / 插件后（插件加载见 `06-11`），重启 VPP 即可在 `show ?` 里看到新命令。

#### 4.2 交互与脚本化对照

```bash
# 交互模式：连上后逐条敲，? 探路、Tab 补全
$ vppctl
vpp# show ?
vpp# set interface ?
vpp# show version
vpp# quit

# 批处理模式：脚本里一次性取数，配合 04-01 的 cli-no-pager
$ vppctl show interface
$ vppctl show version

# exec 回放：把常用配置写成脚本，启动时或手动加载
$ cat /etc/vpp/init.conf
# 初始化脚本
set interface state GigabitEthernet0/8/0 up
set interface ip address GigabitEthernet0/8/0 10.0.0.1/24
ip route add 0.0.0.0/0 via 10.0.0.254
$ vppctl exec /etc/vpp/init.conf
```

脚本里三点经验：其一，命令写全称、不依赖前缀缩写；其二，用 `#` 注释、用空行分段，便于人读；其三，关键命令后用 `show` 类命令做「配置 → 验证」成对出现（验证命令全集见 `04-06`），而不是一把梭到底。

CLI 机制的演进集中在「命令来源」与「注册结构」两端，下表按差异主题列出早期形态、23.06 / master 现状与核验位置：升级排查时先看「核验位置」列给出的源码文件，再决定是改脚本还是改注册代码；`vlib_cli_command_t` 的字段级差异统一见 05-xx。

### 7. 常见误用与调试

CLI 层的误用几乎都发生在「连接」与「解析」两个环节，下表第一列是现场现象、第二列归因到机制、第三列给处理动作；表里反复出现的两条主线是 socket 一致性与命令全称书写，遇到表外的新现象时先回到这两条主线排查，再考虑版本因素。

| 误用 / 现象 | 根因 | 处理 / 定位 |
|---|---|---|
| `vppctl` 连接被拒 | VPP 未启动 / socket 路径不一致 / 权限不足 | 查进程与 `unix{ cli-listen }` socket 文件、核对 `gid`；确认客户端未被沙箱隔离 |
| 脚本被 `more` 卡住 | 默认分页开启 | 用 `cli-no-pager`（`04-01`）或改批处理模式 |
| 前缀缩写在升级后失效 / 命中错命令 | 新版本新增同前缀命令破坏唯一性 | 脚本一律写命令全称 |
| 含空格参数被拆错 | 未加引号 | 用 `"..."` 包裹，转义规则对照 `src/vlib/unix/cli.c` |
| 敲命令报 `unknown input` | 参数拼写 / 顺序不符合 `unformat` 格式 | 用 `<cmd> ?` 看参数提示，逐项对照 |
| `exec` 脚本中途出错继续跑 | 未检查逐条返回 / 退出码 | 关键步骤成对加 `show` 验证，脚本判断 `vppctl` 退出码 |
| 重启后配置全丢 | 误以为 CLI 配置自动持久化 | 用 `show run` 导出 + `unix{ exec }` 加载，见 `04-07` |
| `show run` 输出「不全」 | 动态状态本就不属于可导出配置 | 理解导出的是可重放命令序列，动态表项见 `04-04` / `04-06` |
| 自定义命令在 `?` 里看不到 | 插件未加载 / `VLIB_CLI_COMMAND` 未生效 | 查 `plugins{}`（`04-01`）与启动日志的注册信息 |
| 改了 `startup.conf` 的 CLI 监听却不生效 | 只启动期读一次 | 重启进程，见 `04-01` |

调试主线：**先确认「连得上」（socket / 进程 / 权限），再确认「命令对」（`?` 探路 + 全称），最后确认「留得下」（`exec` / 持久化）**。凡涉及命令注册项字段、命令树内部实现、CLI 与 API 的消息机制细节，分别转 `05-xx`、`06-11`、`06-13`，本册只负责语法、注册方式与用法这一层。

## 04-03 接口与链路层命令全集

### 1. 本篇定位与覆盖范围

接口是 VPP 一切转发行为的起点，也是 CLI 命令最密集的族之一。本篇按「功能族穷举」的口径，系统整理**接口与链路层**的全部命令：从「无中生有」创建各类接口（loopback、vhost-user、memif、af_packet、tap/tuntap、bond、sub-interface 等），到「精雕细琢」配置接口属性（state、mtu、mac、ip 地址、tag、promisc、offload、unnumbered、rx-placement 等），再到「查证结果」的 `show interface` / `show hardware` 家族。每条命令统一按 `命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异` 七列表给出，并尽量填出真实的 Binary API 消息名，方便与 `04-07` 的编程集成、`04-08` 的映射表对照。

理解本篇需要区分两类接口对象：**硬件接口（hw interface）** 对应真实 / 虚拟设备实例，**软件接口（sw interface）** 是叠加其上的逻辑接口（如 sub-interface 挂在 hw interface 上）。绝大多数 `set interface ...` 命令作用在 sw interface 索引上，而 `show hardware` 看的是设备层信息。但本篇**只讲命令怎么列、怎么配、怎么查**，不展开 hw/sw interface 的结构体字段（字段见 `05-05`）、不讲接口收发的内部转发路径（原理见 `06-xx`、模块功能见 `07-01`）。创建隧道类接口（VXLAN / GRE / Geneve）的命令归 `04-05` 网络服务族，本篇只在索引里指向，不重复列；把接口放进桥域 / 配 L2 的命令归 `04-04`。

覆盖范围声明：本篇穷举的是**接口创建/删除、属性设置、队列绑核、状态查询**四大族；接口上的三层地址在 `04-04` 的转发语境里还会出现（如 `set interface ip table`），本篇只收录「给接口配 IP 地址」这一动作本身，涉及路由 / VRF 的命令留给 `04-04`，避免越界重复。

接口命令族可以按「对接口对象做什么动作」分成四类：创建与删除改变接口的存在性，属性与地址类修改接口的配置状态，队列类只影响收包侧的线程放置，查询类不改变任何状态。图 04-03-01 以接口对象为中心把这四类命令挂接起来——创建/删除是对象生命周期两端，属性/地址/队列三类都作用于同一对象但互不冲突，查询类则横跨全部命令的验证闭环；查本篇命令前先在这张图上确定自己处于哪个动作阶段，再回 3.x 小节取具体语法。

node del "删除类<br/>delete interface<br/>delete sub-interface" red

从图上要建立的认知：所有命令都围绕「接口对象」这一个中心，分为**生成（create）、销毁（delete）、配置（set）、读出（show）**四类动作；`set` 类里再按「通用属性 / 地址 / 队列」细分。下面逐族展开，每族先说明约定再给命令表。

### 3. 逐项详解

#### 3.1 创建与删除接口族

创建命令的形态因接口类型而异：有的只要一句 `create loopback interface`，有的需要带 socket 路径、id、模式等一堆参数（vhost-user、memif）。共同约定是：创建成功后 VPP 返回并分配一个 **sw_if_index**（软件接口索引），后续几乎所有 `set interface ...` / `show interface` 都既可用接口名（如 `GigabitEthernet0/8/0`、`loop0`）也可用该索引引用。删除命令一般用接口名或索引，删除前应先确认没有路由 / 桥域 / 地址还引用它，否则可能报错或被拒绝。命名规则：DPDK 物理口通常形如 `GigabitEthernet<bus>/<slot>/<func>` 或 `TenGigabitEthernet...`（简称 `Gig*`、` TenG*` 视版本），loopback 为 `loop0`、`loop1`……，sub-interface 为 `Gig0/8/0.100` 这类带点号的形式。**接口命名格式存在版本与驱动差异，不能凭记忆硬写，务必以 `show interface` 实际输出的名称为准**。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 创建 loopback | `create loopback interface [instance <n>] [mac <addr>]` | `instance` 实例号、可选 `mac` | 建三层逻辑口 | `create_loopback` / `create_loopback_instance` | `create loopback interface` | 是否支持 `mac` 参数需对照 `src/vnet/loopback/` 核验 |
| 删除 loopback | `delete loopback interface [sw_if_index <n>]` | 接口名 / 索引 | 删除 loopback | `delete_loopback` | `delete loopback interface intfc loop0` | 参数形式需核验 |
| 创建 vhost-user | `create vhost socket <path> [server] [id <n>] ...` / `create vhost-user socket ...` | socket 路径、`server` 角色、`id`、`features` 等 | 建 virtio 后端接口 | `create_vhost_user_if` / `create_vhost_user_if_v2` | `create vhost socket /tmp/vhost1.sock server` | 命令名与参数在 v1/v2 间变化大，需对照 `src/vnet/devices/virtio/vhost_user/` 核验 |
| 创建 memif | `create interface memif [id <n>] [socket-id <n>] [master\|slave] [ring-size <n>]` | id、socket、角色、ring 大小、mode | 建共享内存接口 | `memif_create` / `memif_socket_filename_add_del` | `create interface memif id 1 master` | `master/slave` 措辞随版本演进（含 role 化），需核验 |
| 创建 af_packet | `create host-interface name <veth>` / `create interface af_packet ...` | 宿主网卡名、`v2`/`v3` 参数 | 借内核网卡收发 | `af_packet_create` / `af_packet_create_v2` / `af_packet_create_v3` | `create host-interface name veth0` | 命令名与 v2/v3 差异需对照 `src/plugins/af_packet/` 核验 |
| 创建 tap | `create tap [id <n>] [host-ip4-addr ...]` / `tuntap ...` | id、IP、命名空间等 | 接主机栈的 tap 口 | `tap_create_v2` 等 | `create tap id 0` | 参数集合版本差异大，需对照 `src/vnet/tuntap/` 核验 |
| 创建 bond | `create bond mode <mode> [lb <lb>]` | 模式（lacp/xor/active-backup 等）、哈希 | 建聚合口 | `bond_create` | `create bond mode lacp` | 模式枚举需核验 |
| bond 增删成员 | `bond add <bond> <slave>` / `bond del <slave>` | bond 名、成员接口 | 管理聚合成员 | `bond_add_member` / `bond_detach_member` 等 | `bond add BondEthernet0 Gig0/8/0` | 命令名需对照 `src/vnet/bonding/` 核验 |
| 创建 pipe | `create pipe [instance <n>]` | 实例号 | 建本地双向管道 | 相关 `pipe_*` | `create pipe` | 需核验 |
| 通用删除 | `delete interface <name\|sw_if_index>` | 接口名 / 索引 | 删除可删除的接口 | 依类型对应 delete 消息 | `delete interface loop0` | 是否通用删除取决于类型，需核验 |

#### 3.2 子接口族

子接口（sub-interface）挂在父接口上，用于 VLAN / QinQ / dot1ad 等场景。创建时指定父接口与子接口 id，可选 VLAN tag 数量（`single-tag` / `double-tag`）、精确匹配、以及 `default`/`untagged`/`any` 等 tag 处理模式；删除按子接口名。子接口本身是一个独立 sw interface，可单独配 IP、加桥域、设状态。典型陷阱是父接口未 up 或 VLAN 模式与对端不匹配导致子接口不通——这类属于配置一致性问题，验证手段见 `04-06` 的 `show interface` / `show vlan` 类命令。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 创建子接口 | `create sub-interfaces <parent> <id> [dot1q\|dot1ad <vlan>] [exact-match]` | 父接口、子接口 id、VLAN tag、封装 | 建 VLAN 子接口 | `create_subif` / `create_vlan_subif` | `create sub-interfaces Gig0/8/0 100 dot1q 100 exact-match` | 参数形态（含 tag-rewrite 化）随版本变化，需对照 `src/vnet/interface.c` 核验 |
| 删除子接口 | `delete sub-interface <name>` | 子接口名 | 删除子接口 | `delete_subif` | `delete sub-interface Gig0/8/0.100` | 需核验 |
| 配子接口 tag-rewrite | `set interface tag-rewrite <sub> ...` | tag 重写规则（pop/push/translate） | 设 VLAN 标签改写 | `l2_interface_vlan_tag_rewrite` 等（见 `04-04`） | 见 `04-04` | 归 L2 命令族，详见 `04-04` |

#### 3.3 接口状态与通用属性族

这一族是日常用得最多的 `set interface ...`。`state up/down` 控制管理状态；`mtu` 设链路 / 三层 MTU（不同子命令区分 `mtu`、`link mtu`、`ip4 mtu` 等，需按版本核对）；`mac address` 改 MAC；`tag` 给接口打可读标签（运维检索用，可含空格需引号）；`promisc` 开混杂模式。它们的共同点是**即时生效、不落盘**（持久化见 `04-07`），且大多有对应 `sw_interface_set_flags` / `hw_interface_set_mtu` 一类 API。参数里引用接口时，既可用名字也可用 `sw_if_index <n>`，脚本里用名字更可读、用索引更稳（名字可能因驱动重命名变化）。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 接口状态 | `set interface state <if> up\|down` | 接口、`up`/`down` | 设管理状态 | `sw_interface_set_flags` | `set interface state Gig0/8/0 up` | 稳定 |
| MTU | `set interface mtu [packet\|link\|ip4\|ip6] <n> <if>` | MTU 类型、字节数、接口 | 设各类 MTU | `hw_interface_set_mtu` / `sw_interface_set_mtu` | `set interface mtu 9000 Gig0/8/0` | 子命令名随版本分化，需对照核验 |
| MAC 地址 | `set interface mac address <if> <mac>` | 接口、MAC | 改接口 MAC | `sw_interface_set_mac_address` | `set interface mac address loop0 02:fe:00:00:00:01` | 需核验 |
| 接口标签 | `set interface tag <if> <tag>` | 接口、标签（可引号） | 打可读标签 | `sw_interface_tag_add_del` | `set interface tag Gig0/8/0 "uplink"` | 需核验 |
| 删标签 | `set interface tag <if> del` / `del tag` | 接口 | 删除标签 | `sw_interface_tag_add_del` | `set interface tag Gig0/8/0 del` | 需核验 |
| 混杂模式 | `set interface promisc <if> on\|off` | 接口、开关 | 开 / 关混杂 | `sw_interface_set_promisc` | `set interface promisc Gig0/8/0 on` | 是否支持需核验 |

#### 3.4 接口地址与卸载族

给接口配 IP 用 `set interface ip address <if> <prefix>`（删除用 `del`），可多次添加多个地址；`unnumbered` 让接口借用另一接口的地址；`offload` 控制各类软硬件卸载（如 `rx`/`tx` checksum、tso 等，具体标志随版本与驱动变化）。这一族与 `04-04` 的分工要清楚：本篇只管「把地址放到接口上」这个动作，而 `set interface ip table`（把接口放进某个 VRF/路由表）、`ip route`（路由）、`ip neighbor`（邻居）属于三层转发语境，统一归 `04-04`。配完地址后应立即用 `show interface address`（见 3.6）验证，避免「配了却没生效」。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 添加 IP 地址 | `set interface ip address <if> <prefix>` | 接口、CIDR 前缀 | 给接口加 IPv4/IPv6 地址 | `sw_interface_add_del_address` | `set interface ip address Gig0/8/0 10.0.0.1/24` | 稳定 |
| 删除 IP 地址 | `set interface ip address <if> <prefix> del` / `del interface ip address ...` | 同上 + `del` | 删除接口地址 | `sw_interface_add_del_address` | `set interface ip address Gig0/8/0 10.0.0.1/24 del` | `del` 位置随版本变化，需核验 |
| unnumbered | `set interface unnumbered <if> use <src>` / `del` | 目标接口、借用源接口 | 借用地址 | `sw_interface_set_unnumbered` | `set interface unnumbered loop1 use loop0` | 需核验 |
| 卸载开关 | `set interface offload <if> <feature> on\|off` | 接口、卸载项、开关 | 配置硬件卸载 | `sw_interface_set_offload` 一类，需核验 | `set interface offload Gig0/8/0 rx-cksum off` | 卸载项清单随 DPDK/驱动变化，需核验 |
| 接口进 VRF | `set interface ip table <if> <table-id>` | 接口、表 id | 把接口放入路由表（VRF） | `sw_interface_set_table` | 见 `04-04` | 归 `04-04`，本篇不展开 |

#### 3.5 队列与绑核族

多队列网卡需要把接收队列映射到 worker 线程，命令是 `set interface rx-placement <if> queue <n> worker <m>`（或 `main` 表示主线程）；`rx-mode` 切换收包模式（polling / interrupt / adaptive），影响 CPU 占用与时延。`show interface rx-placement` 可回看映射。这一族直接决定多 worker 下的收包并行度与 NUMA 亲和，是性能调优的常客（调优方法学见 `08-02`，本册只列命令）。配置前建议先 `show threads`（`04-06`）确认 worker 编号，避免把队列绑到不存在的 worker。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 队列绑核 | `set interface rx-placement <if> queue <q> worker <w>\|main` | 接口、队列号、worker 号 | 把 RX 队列绑到 worker | `sw_interface_set_rx_placement` | `set interface rx-placement Gig0/8/0 queue 0 worker 1` | 参数名需对照核验 |
| 收包模式 | `set interface rx-mode <if> [queue <q>] polling\|interrupt\|adaptive` | 接口、队列、模式 | 切收包模式 | `sw_interface_set_rx_mode` | `set interface rx-mode Gig0/8/0 polling` | 模式枚举需核验 |
| 查看绑核 | `show interface rx-placement` | 无 | 回看队列 → worker 映射 | 相关 dump 消息 | `show interface rx-placement` | 见 3.6 |

#### 3.6 接口查询族

配置之后必须验证，这一族命令是「配 → 查」闭环的另一半。`show interface` 概览所有接口的名、索引、状态、MTU、计数；`show interface [addr|address]` 列出地址；`show hardware` / `show hardware-interfaces` 看设备层信息（驱动、队列、描述符、PCI、链路速率、offload 能力）；`show interface features` 看该接口启用的 feature arc（feature 编排原理见 `06-03`、字段见 `05-06`）；`show interface rx-placement` 回看绑核。计数类输出（rx/tx packets、drops、errors）是排错第一手数据，与 `04-06` 的 `show errors` / `show runtime` 配合判读。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 接口概览 | `show interface [ <if> ]` | 可选接口名 | 列接口状态 / MTU / 计数 | `sw_interface_dump` / `sw_interface_details` | `show interface` | 稳定 |
| 接口地址 | `show interface addr` / `show interface address` | 无 / 接口 | 列接口 IP 地址 | `ip_address_dump` 一类 | `show interface addr` | 命令名 `addr`/`address` 随版本，需核验 |
| 硬件信息 | `show hardware [ <if> ]` / `show hardware-interfaces` | 可选接口 | 设备层 / 驱动 / 队列 / PCI | `sw_interface_dump` 扩展 / 相关 dump | `show hardware` | 别名随版本，需核验 |
| 接口特性 | `show interface features [ <if> ]` | 可选接口 | 列接口启用的 feature | 相关 feature dump | `show interface features Gig0/8/0` | 输出随 feature arc 版本变化，需核验 |
| 队列绑核 | `show interface rx-placement` | 无 | 回看队列映射 | 相关 dump | `show interface rx-placement` | 需核验 |
| 接口 tag | `show interface tag` | 无 | 回看接口标签 | 相关 dump | `show interface tag` | 需核验 |

### 4. 典型示例

下面是一段「从零建一个 loopback 并配地址 + 把物理口 up 起来 + 全程验证」的完整序列，展示本篇命令的典型用法与「配→查」闭环。物理口名称请以实际 `show hardware` 输出为准。

```bash
# 1) 查看现有接口，确认命名
vppctl show interface

# 2) 创建 loopback 并配管理地址
vppctl create loopback interface
vppctl set interface state loop0 up
vppctl set interface ip address loop0 192.0.2.1/32
vppctl set interface tag loop0 "mgmt-loop"

# 3) 把物理口 up 并配地址、开混杂
vppctl set interface state GigabitEthernet0/8/0 up
vppctl set interface ip address GigabitEthernet0/8/0 10.0.0.1/24
vppctl set interface promisc GigabitEthernet0/8/0 on

# 4) 建 VLAN 子接口并配地址
vppctl create sub-interfaces GigabitEthernet0/8/0 100 dot1q 100 exact-match
vppctl set interface state GigabitEthernet0/8/0.100 up
vppctl set interface ip address GigabitEthernet0/8/0.100 10.0.100.1/24

# 5) 多队列绑核（先确认 worker 编号）
vppctl show threads
vppctl set interface rx-placement GigabitEthernet0/8/0 queue 0 worker 0
vppctl set interface rx-placement GigabitEthernet0/8/0 queue 1 worker 1

# 6) 验证闭环
vppctl show interface address
vppctl show hardware
vppctl show interface rx-placement
```

要点：第 5 步先 `show threads` 再绑核，避免绑到不存在的 worker；第 6 步用三条 show 分别验证地址、硬件、队列，形成闭环。把这些命令（去掉 `vppctl ` 前缀）保存成 `/etc/vpp/init.conf`，再在 `startup.conf` 里配 `unix { exec /etc/vpp/init.conf }`，就实现了开机自动恢复（见 `04-01`、`04-07`）。

再看一个聚焦「创建 vhost-user 接口并读出接口状态」的完整示例，含命令、典型输出与判读：

```bash
# 创建 vhost-user 后端接口（server 角色），拉起后配置 MTU / tag 并验证
vppctl create vhost-user socket /tmp/vhost1.sock server
vppctl set interface state VirtualEthernet0/0/0 up
vppctl set interface mtu 9000 VirtualEthernet0/0/0
vppctl set interface tag VirtualEthernet0/0/0 "vm1-net0"
vppctl show interface VirtualEthernet0/0/0
vppctl show interface tag
vppctl show hardware-interfaces VirtualEthernet0/0/0
# 命令名（create vhost-user socket 与旧式 create vhost socket）与接口名前缀需对照实际版本核验
```

对应典型输出（字段为示意，随版本略有差异）：

```text
vpp# show interface VirtualEthernet0/0/0
              Name               Idx    State  MTU (L3/IP4/IP6/MPLS)     Counter          Count
VirtualEthernet0/0/0              3      up          9000/0/0/0     rx packets                  1204
                                                                   rx bytes                   86520
                                                                   tx packets                  1198
                                                                   tx bytes                   86016
                                                                   drops                          0
                                                                   ip4                        1204
vpp# show interface tag
VirtualEthernet0/0/0: vm1-net0
```

判读说明：以 `show interface` 为准，`Name` / `Idx` 是接口名与 sw_if_index，后续 `set`、`show` 命令可用名字或索引引用；`State up` 表示管理状态已生效，若为 `down` 多为漏了 `set interface state ... up` 或 vhost-user 后端尚无 QEMU 连接。`MTU (L3/IP4/IP6/MPLS)` 首列 9000 说明 `set interface mtu` 已落地，仍是 1500 多为子命令名写错。`Counter/Count` 中 `rx packets` / `tx packets` 随打流持续增长且 `drops` 为 0，是通路正常的最直接证据；`rx` 不涨多因队列未绑核或对端未发包，`tx` 长期为 0 先查对端；`show interface tag` 能回显 `vm1-net0` 即标签写入成功。常见异常：`create` 报 unknown command 是 virtio / vhost 插件未在 `plugins{}` 加载（见 04-01）；接口名与预期不符必须以 `show interface` 实际输出为准，勿凭记忆硬写；计数异常再转 04-06 的 `show errors` 深挖。此外，`show hardware-interfaces` 里若队列数、链路速率或驱动能力位异常，说明多队列或 DPDK 侧未就绪，需回到 04-01 的 `startup.conf` 与 04-06 的 `show log` 复核；接口索引 `Idx` 在脚本里比名字更稳定，自动化场景建议优先用索引引用。以上命令名与生成接口名前缀随版本变化，需对照实际版本核验。

### 5. 速查表

下表按「诉求 → 命令 → 备注」组织，是第 3 节逐项详解的浓缩版：诉求列覆盖接口从创建到删除的完整生命周期，备注列标注了执行前置条件（如绑核前先 `show threads`）；每条命令执行后都应回查表末的验证命令，构成「配一个、查一个」的闭环。

| 诉求 | 命令 | 备注 |
|---|---|---|
| 看有哪些接口 / 接口名 | `show interface` | 名称以此为准 |
| 建三层逻辑口 | `create loopback interface` | 再 `state up` + `ip address` |
| 接虚机 | `create vhost socket <path> server` | virtio 后端 |
| 进程间接口 | `create interface memif ...` | 共享内存 |
| 无 DPDK 借内核网卡 | `create host-interface name <veth>` | af_packet |
| 建 VLAN 子接口 | `create sub-interfaces <if> <id> dot1q <vlan>` | 再配地址 |
| 接口 up / down | `set interface state <if> up\|down` | 即时生效 |
| 配 IP | `set interface ip address <if> <prefix>` | 可多次 |
| 删 IP | `... <prefix> del` | `del` 位置看版本 |
| 改 MAC / MTU | `set interface mac address` / `set interface mtu` | — |
| 打标签 | `set interface tag <if> "..."` | 含空格加引号 |
| 混杂 / 卸载 | `set interface promisc` / `offload` | 依驱动支持 |
| 队列绑核 | `set interface rx-placement ... worker <n>` | 先 `show threads` |
| 看地址 / 硬件 / 绑核 | `show interface address` / `show hardware` / `show interface rx-placement` | 验证闭环 |
| 删除接口 | `delete interface <name>` | 先清引用 |

一句话记忆：**「create 建、set 配、show 查、delete 删」**，接口名一律以 `show interface` 实际输出为准，配完立即查、要留存就进 `exec` 脚本。

### 6. 版本差异

接口命令是版本漂移的重灾区，下表按差异主题分列：读法是先定位你用的命令属于哪一行，对照「早期 / 变化方向」与「23.06 / master」两列判断自己处在哪个形态，最后按「核验位置」列的源码目录确认当前版本的准确语法；创建类命令几乎每代都动，升级前务必逐条核对。

| 差异主题 | 早期 / 变化方向 | 23.06 / master | 核验位置 |
|---|---|---|---|
| vhost-user 命令 | `create vhost socket` 老式 | `create vhost-user socket` / `_v2` API，参数更丰富 | `src/vnet/devices/virtio/vhost_user/` |
| memif 角色措辞 | `master`/`slave` | 逐步引入 role 化措辞，参数重写 | `src/plugins/memif/` |
| af_packet | 单一 `create` | `af_packet_create_v2/v3` 多版本 API 并存 | `src/plugins/af_packet/` |
| tap / tun | 老 `tuntap` 配置 | `tap_create_v2` 及接口化命令 | `src/vnet/tuntap/` |
| 子接口 VLAN | `dot1q`/`dot1ad` 直接参数 | 部分功能转向 tag-rewrite 命令（见 `04-04`） | `src/vnet/interface.c` |
| MTU 子命令 | 单一 `mtu` | 分化 `link`/`ip4`/`ip6`/`packet` MTU | `src/vnet/interface.c` |
| 接口命名 | `GigabitEthernetX/Y/Z` | 依 DPDK 驱动，可能含 `TenGigabitEthernet` / 自定义 `name` | `src/plugins/dpdk/` |
| 地址删除语法 | `del interface ip address` | `set ... del` 与独立 del 并存 | `src/vnet/ip/` |

迁移提示：升级后脚本里最容易出问题的是**创建类命令**（vhost/memif/af_packet/tap 的命令名与参数几乎每代都动）和**接口命名**。稳妥做法是升级后先跑一遍 `show interface` / `show hardware` 记录真实接口名与类型，再逐条用 `?` 核对创建命令的新语法。字段级差异统一见 `05-05`。

### 7. 常见误用与调试

接口命令的误用集中在三类：名字凭记忆硬写、插件没加载就敲创建命令、以及把「命令成功」当成「配置生效」，下表的现象列按这三类归组；处理列给出的定位命令均属 04-06 的查询族，遇到表内覆盖不了的现象，直接转 04-06 按「为什么丢包/不收包」继续深挖。

| 误用 / 现象 | 根因 | 处理 / 定位 |
|---|---|---|
| 创建命令报 unknown command | 对应插件未加载（vhost/memif/af_packet/tap 都是插件） | 查 `04-01` 的 `plugins{}` 白名单与 `04-02` 的 `?`，确认插件已启用 |
| 接口名对不上、命令找不到接口 | 凭记忆硬写 `GigabitEthernet...`，实际名称不同 | 一律以 `show interface` / `show hardware` 输出名为准 |
| 配了地址但 `show interface address` 看不到 | 命令语法错 / 接口未 up / 写到了别的 sw_if_index | `?` 核对语法，配完立即查，必要时用索引定位 |
| 接口 up 了但不收包 | 物理链路 / 队列绑核 / NUMA / 驱动问题 | `show hardware` 看链路、`show interface` 看计数、`04-06` 的 `show errors` 看丢弃 |
| sub-interface 不通 | 父口未 up / VLAN 模式与对端不一致 / exact-match 冲突 | 核对 dot1q/dot1ad 参数，用 `04-06` 的 `show` 类命令验证 |
| 队列绑核报无效 worker | 绑到了不存在的 worker 编号 | 先 `show threads` 确认编号再绑 |
| 改了 MAC / offload 不生效 | 驱动不支持该特性 / 命令静默失败 | 看命令回显与 `show hardware` 能力位，查 `clib_error` 文本 |
| 删除接口被拒 | 仍有地址 / 路由 / 桥域引用 | 先清引用（地址见本篇、路由见 `04-04`、桥域见 `04-04`）再删 |
| 重启后接口/地址全丢 | 误以为 CLI 配置持久化 | 用 `exec` 脚本 + `unix{ exec }`，见 `04-07` |
| 性能不及预期 | 队列未绑核 / 绑到远端 NUMA | `show interface rx-placement` + `show threads` 复核，调优方法见 `08-02` |

调试主线：**命名以 `show` 为准 → 插件先确认加载 → 配置即时 `show` 验证 → 计数 / 错误往 `04-06` 深挖 → 持久化往 `04-07` 收敛**。一旦定位到是接口内部转发路径、feature arc 编排、hw/sw interface 结构体层面的问题，分别转 `07-01`（模块功能）、`06-03`（feature 原理）、`05-05`（字段），本册只负责「命令怎么列、怎么配、怎么查」。

## 04-04 二层与三层转发命令全集

### 1. 本篇定位与覆盖范围

本篇是「转发配置」的命令权威源，按功能族穷举**二层交换**与**三层路由**两大类命令。二层侧覆盖桥域（bridge-domain / BD）、接口 L2 模式（bridge / xconnect / tag-rewrite）、L2FIB 静态表项；三层侧覆盖 VRF / 路由表（ip table）、静态路由（ip route）、邻居表（ip neighbor / ARP / ND）、MPLS 标签转发，以及 FIB / 邻接 / VRF 的查询命令。每条命令统一用 `命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异` 七列表给出，尽量填出真实 Binary API 消息名，供 `04-07` 编程集成与 `04-08` 映射表对照。

理解本篇要先建立一个「层次」概念：接口（本篇 `04-03` 创建）本身既可以被放进**二层桥域**（此时 VPP 按 MAC 转发），也可以作为**三层口**（此时按 IP/标签转发），二者由 `set interface l2 ...` / `set interface l3` 切换，互斥。放进桥域后，MAC 学习、泛洪、L2FIB 查找才生效；作为三层口后，接口要进某个路由表（VRF）、有 IP 地址、有路由与邻接，报文才能被路由。本篇只讲「用哪条命令切换、怎么配表项、怎么查表」，**不展开** MAC 学习老化机制、FIB 查找算法、DPO/邻接 rewrite、递归路由解析这些内部原理（原理见 `06-xx`、模块功能见 `07-02` / `07-03` / `07-10`），也不列 `fib_entry_t` / `l2_bridge_domain_t` / `ip_adjacency_t` 等结构体字段（字段见 `05-07` / `05-08`）。

与相邻篇的分工：接口创建 / 删除 / 配地址 / up-down 在 `04-03`；把接口放进路由表用 `set interface ip table`（本篇收录，因为它是三层转发的起点）；NAT / ACL / IPsec / 隧道等服务的命令在 `04-05`；`show` / `clear` / `trace` 等调试命令的总清单在 `04-06`，本篇只收录**专属于转发表的查询子命令**（如 `show ip fib`、`show l2fib`、`show mpls fib`），避免与 `04-06` 重复。

### 3. 逐项详解

#### 3.1 桥域（bridge-domain）族

桥域是二层交换的容器，用整数 `bd_id` 标识（范围依版本，常见 `< 2^16` 或更大，需核验）。`bridge-domain <id> add` 建域、`del` 删域；`set bridge-domain` 系列调整域行为：`learn` 开关 MAC 学习、`forward` 开关转发、`flood` 开关泛洪、`uu-flood` 开关未知单播泛洪、`arp-term` 开关 ARP 终结、`mac-age <n>` 设老化时间、`<bd> ... del` 类子命令删除域参数。`show bridge-domain [detail]` 回看每个 BD 的成员接口、BVI 接口、标志位。典型误用是建了 BD 却没把接口加进来（那是 `set interface l2 bridge`，见 3.2），于是 BD 是空的、自然不通。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 建 / 删桥域 | `bridge-domain <id> add [del]` | bd_id、`add`/`del` | 创建 / 删除二层桥域 | `bridge_domain_add_del` | `bridge-domain 10 add` | 稳定 |
| 域开关 | `set bridge-domain <id> learn\|forward\|flood\|uu-flood\|arp-term\|arp-ufwd <on\|off>` | bd_id、开关项、on/off | 调整 BD 学习与泛洪行为 | `bridge_domain_set_flags` | `set bridge-domain 10 learn on` | 开关项集合随版本变化，需对照 `src/vnet/l2/` 核验 |
| MAC 老化 | `set bridge-domain <id> mac-age <n>` | bd_id、秒数 | 设 MAC 学习老化时间 | `bridge_domain_set_mac_age` | `set bridge-domain 10 mac-age 300` | 需核验 |
| 查桥域 | `show bridge-domain [<id>] [detail\|int\|arp]` | bd_id、显示项 | 列出 BD 成员与标志 | `bridge_domain_dump` / `bridge_domain_details` | `show bridge-domain 10 detail` | 显示子项随版本变化，需核验 |

#### 3.2 接口 L2 模式族

这是「把接口放进二层」的命令集，也是与 `04-03` 衔接最紧的一族。`set interface l2 bridge <if> <bd> [bvi|uu-fwd] [shg <n>]` 把接口加入指定 BD，可选 `bvi`（桥虚拟接口，作三层网关口）、`uu-fwd`（未知单播转发口）、`shg`（水平分割组，防环路）；`set interface l2 xconnect <if> <peer>` 把两个接口做二层交叉连接（E-Line / VPWS 场景，报文从一端进必从另一端出，不查 MAC）；`set interface l3 <if>`（或 `set interface l2 ... del` 等价形式）把接口改回三层模式并清除 L2 配置；`set interface l2 tag-rewrite <if> ...` 配 VLAN 标签的 pop/push/translate（与 `04-03` 的子接口配合）。**要点**：同一接口不能既在 BD 又在三层路由表，模式切换是排错时第一个要确认的项；`show mode` 可一次性列出所有接口的 L2/L3 状态。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 加入桥域 | `set interface l2 bridge <if> <bd> [bvi\|uu-fwd] [shg <n>]` | 接口、bd_id、角色、分割组 | 把接口加入 BD | `sw_interface_set_l2_bridge` | `set interface l2 bridge Gig0/8/0 10` | 稳定 |
| 退出 L2 | `set interface l3 <if>` / `set interface l2 bridge <if> 0` | 接口 | 恢复三层模式 / 移出 BD | `sw_interface_set_l2_bridge`（enable=0） | `set interface l3 Gig0/8/0` | `set interface l3` 是否存在需核验 |
| 交叉连接 | `set interface l2 xconnect <if> <peer>` | 两端接口 | 二层点到点交叉连接 | `sw_interface_set_l2_xconnect` | `set interface l2 xconnect Gig0/8/0 Gig0/9/0` | 稳定 |
| 删交叉连接 | `set interface l2 xconnect <if> <peer> del` | 两端接口 + `del` | 删除 xconnect | `sw_interface_set_l2_xconnect` | `... del` | `del` 位置需核验 |
| VLAN 标签改写 | `set interface l2 tag-rewrite <if> [pop 1\|2] [push dot1q <vlan>] [translate ...]` | 接口、tag 规则 | 配 VLAN 标签 pop/push/translate | `l2_interface_vlan_tag_rewrite` | `set interface l2 tag-rewrite Gig0/8/0.100 pop 1` | 规则语法随版本变化明显，需核验 |
| 查模式 | `show mode [<if>]` | 可选接口 | 列接口 L2/L3 模式 | 相关 dump | `show mode` | 需核验 |
| 查接口 L2 配置 | `show interface l2 [<if>]` | 可选接口 | 显示接口的 L2 详细配置 | 相关 dump | `show interface l2` | 需核验 |
| 学习限制 | `set interface l2 learn-limit <if> <n>` | 接口、上限 | 限制接口 MAC 学习数 | 相关配置 API，需核验 | `set interface l2 learn-limit Gig0/8/0 100` | 是否提供需核验 |

#### 3.3 L2FIB 族

L2FIB 是二层的 MAC 转发表。动态学习会自动填表，静态表项用 `l2fib add <mac> <bd> <if> [static] [bvi] [filter]` 手工添加（`filter` 表示丢弃匹配 MAC 的流量，可做二层过滤），`l2fib del <mac> <bd>` 删除，`show l2fib [all|bd <id>|verbose]` 查看。注意 `static` / `bvi` / `filter` 标志的组合语义（静态不老化、bvi 指向桥虚拟接口、filter 丢弃），以及 `clear l2fib` 属于 `04-06` 的 clear 族，本篇不重复列。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 添加静态表项 | `l2fib add <mac> <bd> <if> [static] [bvi] [filter]` | MAC、bd_id、接口、标志 | 添加 L2FIB 表项 | `l2fib_add_del` | `l2fib add 52:54:00:11:22:33 10 Gig0/8/0 static` | 标志集合需核验 |
| 删除表项 | `l2fib del <mac> <bd> [filter]` | MAC、bd_id、可选标志 | 删除 L2FIB 表项 | `l2fib_add_del`（is_add=0） | `l2fib del 52:54:00:11:22:33 10` | 需核验 |
| 查 L2FIB | `show l2fib [all] [bd <id>] [verbose\|raw]` | 过滤与显示项 | 列出 MAC 转发表 | `l2_fib_table_dump` / `l2_fib_table_details` | `show l2fib all` | 显示子项随版本变化，需核验 |
| 清空（见 `04-06`） | `clear l2fib` | 无 | 清空动态学习表 | `l2fib_flush_*` | 见 `04-06` | 归 clear 族 |

#### 3.4 VRF / 路由表族

三层转发以「路由表（VRF / table id）」为隔离单位。`ip table add <id>` / `del <id>` 建删 IPv4 路由表，`ip6 table` 对应 IPv6；`set interface ip table <if> <id>` 把接口归入某表，`set interface ip6 table` 同理。默认表 id 为 `0`。一个常见困惑是「配了地址却不转发」——往往因为接口还在默认表、而路由被加进了自定义表，或反过来。查表用 `show ip table` / `show vrf`。**注意**：把接口配进 VRF 属于「接口三层属性」，本篇收录；而接口 IP 地址本身在 `04-03`，两者是不同命令。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 建 / 删 IPv4 表 | `ip table [table <id>] add\|del` | table_id、add/del | 创建 / 删除 IPv4 VRF | `ip_table_add_del` | `ip table add 100` | 语法带不带 `table` 关键字随版本，需核验 |
| 建 / 删 IPv6 表 | `ip6 table <id> add\|del` | table_id、add/del | 创建 / 删除 IPv6 VRF | `ip_table_add_del`（is_ipv6） | `ip6 table 100 add` | 需核验 |
| 接口进表 | `set interface ip table <if> <id>` | 接口、table_id | 接口归入 IPv4 路由表 | `sw_interface_set_table` | `set interface ip table Gig0/8/0 100` | 稳定 |
| 接口进 IPv6 表 | `set interface ip6 table <if> <id>` | 接口、table_id | 接口归入 IPv6 路由表 | `sw_interface_set_table`（is_ipv6） | `set interface ip6 table Gig0/8/0 100` | 需核验 |
| 查表 | `show ip table [<id>]` / `show vrf` | 可选 table_id | 列出路由表 / VRF | `ip_table_dump` 一类 | `show ip table 100` | 命令名 `show vrf` 是否存在需核验 |

#### 3.5 静态路由族

`ip route` 是三层最核心的命令族。`ip route [table <id>] add <prefix> via <next-hop> [<if>] [weight <n>] [resolve] [attached] [count <n>] ...` 添加路由：可指定 VRF、下一跳（可带出接口）、多路径权重、递归解析、attached（直连）等；`del` 删除，`replace` 替换；也支持 `drop` / `local` / `prohibit` / `unreach` / `classify` / `source-lookup` 等特殊下一跳类型。IPv6 用 `ip6 route`。查询用 `show ip route` / `show ip fib`（FIB 是路由下发后的实际转发表，含邻接与 DPO 信息，能看出路由是否真正生效）。**关键经验**：配完路由务必 `show ip fib <prefix>` 验证，而不只是 `show ip route`——前者才反映转发表里的实际状态（能否解析到邻接）。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 添加路由 | `ip route [table <id>] add <prefix> via <nh> [<if>] [weight <n>] [resolve] [attached]` | table_id、前缀、下一跳、出接口、权重、标志 | 添加静态路由 | `ip_route_add_del` / `ip_route_add_v2` | `ip route add 198.51.100.0/24 via 10.0.0.2 Gig0/8/0` | 新版支持 `ip_route_add_v2` 多路径，参数形态需核验 |
| 删除路由 | `ip route [table <id>] del <prefix> via <nh> ...` | 同添加 | 删除静态路由 | `ip_route_add_del`（is_add=0） | `ip route del 198.51.100.0/24 via 10.0.0.2` | 需与添加参数完全一致才能命中，需核验 |
| 替换路由 | `ip route [table <id>] replace <prefix> via <nh> ...` | 同添加 | 原子替换 | `ip_route_add_del`（is_replace） | `ip route replace 0.0.0.0/0 via 10.0.0.254` | 是否提供需核验 |
| 特殊下一跳 | `ip route add <prefix> via drop\|local\|prohibit\|unreach` | 前缀、动作 | 丢弃 / 本地 / 拒绝路由 | `ip_route_add_del`（特殊 DPO） | `ip route add 203.0.113.0/24 via drop` | 动作集合需核验 |
| 多路径权重 | `ip route add <prefix> via <nh1> <if1> weight 1 via <nh2> <if2> weight 2` | 多组下一跳 + 权重 | ECMP / WCMP | `ip_route_add_v2` 一类 | 见示例 | 语法随 v1/v2 API 变化，需核验 |
| IPv6 路由 | `ip6 route [table <id>] add <pfx> via <nh> ...` | 同 IPv4 | 添加 IPv6 静态路由 | `ip_route_add_del`（is_ipv6） | `ip6 route add 2001:db8::/32 via 2001:db8:1::1` | 需核验 |
| 查路由 | `show ip route [table <id>]` | 可选 table_id | 列路由表条目 | `ip_route_dump` 一类 | `show ip route table 100` | 输出格式随版本变化，需核验 |
| 查 FIB | `show ip fib [table <id>] [<prefix>] [summary]` | table_id、前缀、摘要 | 列实际转发表（含邻接） | `ip_fib_dump` / `ip_fib_details`（旧 `ip4_fib_dump`） | `show ip fib 198.51.100.0/24` | API 名在新版变化，需核验 |
| 查 IPv6 FIB | `show ip6 fib [<prefix>]` | 前缀 | 列 IPv6 转发表 | `ip6_fib_dump` | `show ip6 fib 2001:db8::/32` | 需核验 |

#### 3.6 邻居 / ARP / ND 族

三层转发最后一步需要「下一跳 IP → 二层 MAC」的映射，即邻居表。`ip neighbor add <if> <ip> <mac> [static] [no-fib-entry] [flags]` 静态添加邻居，`del` 删除，`show ip neighbors` / `show ip6 neighbors` 查看。老版本常用 `set ip arp`（IPv4）与 `set ip6 neighbor` 系列，新版统一到 `ip neighbor`。代理 ARP 用 `set proxy-arp` / `proxy-arp add-del` 类命令；IPv6 ND 相关有 `ip6 nd address autoconfig`、`set ip6 nd ...`（RA 参数）、`set ip6 nd proxy` 等。邻居不通是「路由有、但不通」最常见的根因，排查顺序是：先 `show ip fib` 看路由是否解析到邻接，再 `show ip neighbors` 看邻居是否 resolved，最后 `04-06` 的 `trace` 看 ARP/ND 报文有没有出去。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 添加邻居 | `ip neighbor add <if> <ip> <mac> [static] [no-fib-entry]` | 接口、IP、MAC、标志 | 静态添加邻居表项 | `ip_neighbor_add_del` | `ip neighbor add Gig0/8/0 10.0.0.2 52:54:00:aa:bb:cc` | 新版统一 API，旧版用 `set ip arp`，需核验 |
| 删除邻居 | `ip neighbor del <if> <ip> <mac>` | 同上 | 删除邻居 | `ip_neighbor_add_del`（is_add=0） | `ip neighbor del Gig0/8/0 10.0.0.2` | 需核验 |
| 查邻居 | `show ip neighbors [<if>]` / `show ip6 neighbors` | 可选接口 | 列邻居表与状态 | `ip_neighbor_dump` / `ip_neighbor_details` | `show ip neighbors` | 命令名 `show ip neighbor`/`neighbors` 需核验 |
| 老式 ARP | `set ip arp <if> <ip> <mac> [static] [proxy]` | 接口、IP、MAC、标志 | 旧版配静态 ARP | `proxy_arp_add_del` / `ip_neighbor_add_del` | `set ip arp Gig0/8/0 10.0.0.2 52:54:00:aa:bb:cc` | 逐步被 `ip neighbor` 取代，需核验 |
| 代理 ARP | `set proxy-arp <if> enable\|disable` / `proxy-arp add <lo>-<hi>` | 接口 / 地址范围、开关 | 开启代理 ARP | `proxy_arp_intfc_enable_disable` / `proxy_arp_add_del` | `set proxy-arp Gig0/8/0 enable` | 命令形态随版本变化，需核验 |
| ND 自动配置 | `ip6 nd address autoconfig <if> [enable\|disable] [install-default-routes]` | 接口、开关 | 接口 SLAAC 自动配地址 | `sw_interface_ip6nd_ra_config` / `ip6_nd_address_autoconfig` | `ip6 nd address autoconfig Gig0/8/0 enable` | 需核验 |
| ND 代理 | `set ip6 nd proxy <...>` | 依版本 | IPv6 ND 代理 | `ip6nd_proxy_*` | 需核验 | 是否提供需核验 |

#### 3.7 MPLS 标签转发族

MPLS 是介于二层与三层之间的标签转发，命令相对独立。`mpls table add <id>` / `del` 管理标签表；`mpls interface enable <if>` / `disable` 在接口上启用 MPLS 接收；`mpls route add <label> ...` 配标签转发（可 pop / swap / push、指定出接口与下一跳）；`show mpls fib` / `show mpls table` / `show mpls interface` 查询。MPLS 常与 `07-10` 的标签栈 / LDP 思路配合，本篇只列配置命令，不展开标签转发原理。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 建 / 删标签表 | `mpls table add <id>` / `mpls table del <id>` | table_id | 管理 MPLS 表 | `mpls_table_add_del` | `mpls table add 0` | 是否需显式建表随版本，需核验 |
| 接口启用 | `mpls interface enable <if>` / `disable <if>` | 接口、开关 | 接口启用 MPLS 接收 | `mpls_interface_enable_disable` | `mpls interface enable Gig0/8/0` | 稳定 |
| 添加标签路由 | `mpls route add <label> [via <nh> <if>] [out-label <n>] [pop] [l2-input]` | 入标签、出接口、出标签、动作 | 配标签转发（swap/pop/push） | `mpls_route_add_del` / `mpls_route_add_del_v2` | `mpls route add 100 via 10.0.0.2 Gig0/8/0 out-label 200` | 参数形态随版本变化，需核验 |
| 删除标签路由 | `mpls route del <label> ...` | 同添加 | 删除标签路由 | `mpls_route_add_del`（is_add=0） | `mpls route del 100` | 需核验 |
| 查 MPLS FIB | `show mpls fib [table <id>] [<label>]` | table_id、标签 | 列标签转发表 | `mpls_fib_dump` 一类 | `show mpls fib 100` | API 名需核验 |
| 查接口 | `show mpls interface` | 无 | 列启用 MPLS 的接口 | `mpls_interface_dump` 一类 | `show mpls interface` | 需核验 |
| 查表 | `show mpls table` | 无 | 列 MPLS 表 | `mpls_table_dump` 一类 | `show mpls table` | 需核验 |

#### 3.8 FIB / 邻接查询族

除 `show ip fib` 已在 3.5 列出，本族补齐邻接与综合能力查询。`show ip adjacency [<if>] [detail]` 列出邻接 rewrite 信息（下一跳 MAC、出接口、rewrite 字符串），是判断「路由能否真正封装成二层帧」的关键；`show ip fib summary` 看各表条目规模；`show ip6 fib`、`show adjacency` 等提供不同维度。**经验**：路由配置正确的完整证据链是「`show ip route` 有条目 → `show ip fib` 有转发项且指向有效邻接 → `show ip adjacency` 有 rewrite → `show ip neighbors` 已 resolved」，任何一环缺失都解释了「不通」。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 查邻接 | `show ip adjacency [<if>] [detail]` / `show adjacency` | 可选接口、detail | 列邻接 rewrite | `ip_adjacency_dump` / `ip_adjacency_details` | `show ip adjacency Gig0/8/0` | 命令名 / 输出随版本，需核验 |
| FIB 摘要 | `show ip fib summary` | 无 | 各表 FIB 条目规模 | `ip_fib_dump`（统计） | `show ip fib summary` | 需核验 |
| 查 IPv6 FIB | `show ip6 fib [<prefix>]` | 前缀 | 列 IPv6 转发表 | `ip6_fib_dump` | `show ip6 fib` | 详见 3.5 |
| 查 VRF | `show vrf [ip\|ip6]` | 可选协议 | 列 VRF / 表 | 相关 dump | `show vrf` | 是否提供需核验 |

### 4. 典型示例

下面给出一段「同一台 VPP 上一边做二层桥接、一边做三层路由 + VRF」的完整序列，展示本篇命令的组合与「配→查」闭环。

```bash
# ===== A. 二层桥接：把两个物理口 + 一个 BVI 放进 BD 10 =====
vppctl bridge-domain 10 add
vppctl set bridge-domain 10 learn on
vppctl set bridge-domain 10 flood on
vppctl set bridge-domain 10 uu-flood on
vppctl set bridge-domain 10 arp-term on
vppctl set bridge-domain 10 mac-age 300

vppctl create loopback interface
vppctl set interface l2 bridge loop0 10 bvi
vppctl set interface state loop0 up
vppctl set interface ip address loop0 192.168.10.1/24

vppctl set interface l2 bridge GigabitEthernet0/8/0 10
vppctl set interface l2 bridge GigabitEthernet0/9/0 10
vppctl set interface state GigabitEthernet0/8/0 up
vppctl set interface state GigabitEthernet0/9/0 up

# 静态 L2FIB 表项 + 验证
vppctl l2fib add 52:54:00:11:22:33 10 GigabitEthernet0/8/0 static
vppctl show bridge-domain 10 detail
vppctl show l2fib all
vppctl show mode

# ===== B. 三层路由：独立 VRF 100 + 静态路由 + 邻居 =====
vppctl ip table add 100
vppctl set interface ip table GigabitEthernet0/a/0 100
vppctl set interface state GigabitEthernet0/a/0 up
vppctl set interface ip address GigabitEthernet0/a/0 10.0.0.1/24

vppctl ip neighbor add GigabitEthernet0/a/0 10.0.0.2 52:54:00:aa:bb:cc static
vppctl ip route table 100 add 198.51.100.0/24 via 10.0.0.2 GigabitEthernet0/a/0
vppctl ip route table 100 add 0.0.0.0/0 via 10.0.0.2 GigabitEthernet0/a/0

# 验证链：路由 → FIB → 邻接 → 邻居
vppctl show ip route table 100
vppctl show ip fib table 100 198.51.100.0/24
vppctl show ip adjacency GigabitEthernet0/a/0
vppctl show ip neighbors

# ===== C. MPLS（可选）=====
vppctl mpls table add 0
vppctl mpls interface enable GigabitEthernet0/a/0
vppctl mpls route add 100 via 10.0.0.2 GigabitEthernet0/a/0 out-label 200
vppctl show mpls fib 100
```

要点：A 段先用 `bridge-domain add` 建域、再用 `set interface l2 bridge` 加成员，BVI 用 `bvi` 标志；B 段切记 `ip table add` 后要用 `set interface ip table` 把接口放进同一 VRF，否则路由加在表 100、接口却在表 0，路由永不生效；验证走「四连查」而不是只看 `show ip route`。把这些命令存入 `exec` 脚本即可持久化（见 `04-07`）。

再看一个聚焦「VRF 内静态路由是否真正下发到转发表」的完整示例，含命令、典型输出与判读：

```bash
# 在 VRF 100 内配静态路由 + 静态邻居，再走「四连查」验证
vppctl ip table add 100
vppctl set interface ip table GigabitEthernet0/8/0 100
vppctl set interface state GigabitEthernet0/8/0 up
vppctl set interface ip address GigabitEthernet0/8/0 10.0.0.1/24
vppctl ip neighbor add GigabitEthernet0/8/0 10.0.0.2 52:54:00:aa:bb:cc static
vppctl ip route table 100 add 198.51.100.0/24 via 10.0.0.2 GigabitEthernet0/8/0
vppctl show ip route table 100
vppctl show ip fib table 100 198.51.100.0/24
vppctl show ip adjacency GigabitEthernet0/8/0
vppctl show ip neighbors
# ip route / ip neighbor 的参数与 VRF 语法需对照实际版本核验
```

对应典型输出（字段为示意，随版本略有差异）：

```text
vpp# show ip route table 100
Table 100, fib_index 1, ipv4
198.51.100.0/24, 1 paths
  via 10.0.0.2, GigabitEthernet0/8/0
vpp# show ip fib table 100 198.51.100.0/24
198.51.100.0/24  fib_index:1  paths:1
  dpo-load-balance -> arp-ipv4: via 10.0.0.2 GigabitEthernet0/8/0
vpp# show ip adjacency GigabitEthernet0/8/0
10.0.0.2  GigabitEthernet0/8/0  rewrite: 52:54:00:aa:bb:cc
vpp# show ip neighbors
GigabitEthernet0/8/0   10.0.0.2   52:54:00:aa:bb:cc   static   resolved
```

判读说明：先看 `show ip route`，能在 `Table 100` 下看到 `198.51.100.0/24` 与下一跳 `10.0.0.2`，只说明路由条目写入控制面，并不代表能转发；必须再看 `show ip fib`，该前缀出现且带 `dpo-load-balance` / `arp-ipv4` 路径、指向 `GigabitEthernet0/8/0`，才说明已解析到有效邻接。`show ip adjacency` 有对应 rewrite、`show ip neighbors` 把 `10.0.0.2` 标为 `static` / `resolved`，「路由 → FIB → 邻接 → 邻居」四连查才完整闭合，配置算真正生效。最常见异常是 `show ip route` 有条目但 `show ip fib` 为空或路径未解析，根因多为接口未 `set interface ip table ... 100`（路由在表 100、接口仍在默认表 0）或邻居 unresolved，补 `set interface ip table` 或用 `ip neighbor ... static` 固定邻居即可。若邻居一直 incomplete，多半是对端未回 ARP 或 VLAN / IP 配错，用 04-06 的 `trace` 看 ARP 报文。另注意 `show ip fib` 输出格式与 `ip route` 参数在版本间变化，自动化解析脚本升级后要重新核对；删除路由时 `del` 参数须与添加时完全一致才能命中，`show ip fib summary` 还可快速核对各表条目规模，避免把「已配上」误判为「没生效」。以上需对照实际版本核验。

### 5. 速查表

下表把二层三件套与三层四连查压缩成十五行速查：第一列是诉求、第二列是命令、第三列提示易漏步骤——`set interface ip table` 与 `show ip fib` 两行是全表最容易跳过的动作，也是二层三层不通时最先要复查的两条。

| 诉求 | 命令 | 备注 |
|---|---|---|
| 建二层桥域 | `bridge-domain <id> add` | 再用 `set interface l2 bridge` 加成员 |
| 接口加入 BD | `set interface l2 bridge <if> <bd>` | BVI 用 `bvi` |
| 两口二层直通 | `set interface l2 xconnect <if> <peer>` | 不查 MAC |
| 接口改回三层 | `set interface l3 <if>` | 与 L2 互斥 |
| 加静态 MAC | `l2fib add <mac> <bd> <if> static` | `filter` 可做丢弃 |
| 查 MAC 表 | `show l2fib all` | — |
| 建 VRF | `ip table add <id>` | 配套 `set interface ip table` |
| 接口归 VRF | `set interface ip table <if> <id>` | 关键一步 |
| 加静态路由 | `ip route [table <id>] add <pfx> via <nh>` | — |
| 加默认路由 | `ip route add 0.0.0.0/0 via <nh>` | — |
| 加静态邻居 | `ip neighbor add <if> <ip> <mac> static` | 新版统一命令 |
| 查转发表 | `show ip fib <prefix>` | 比 `show ip route` 更反映实际 |
| 查邻接 | `show ip adjacency` | 看 rewrite |
| 启用 MPLS | `mpls interface enable <if>` | 配 `mpls route` |
| 查桥域 | `show bridge-domain <id> detail` | 看成员与标志 |

一句话记忆：**「二层三件套：建 BD、接口进 BD、看 L2FIB；三层四连查：路由 → FIB → 邻接 → 邻居」**，配置最易漏的是 `set interface ip table`（VRF 归属）与验证时漏看 `show ip fib`。

### 6. 版本差异

二层与三层的演进方向是「命令统一化 + API 多版本并存」，下表按差异主题分列：邻居命令从 `set ip arp` 统一到 `ip neighbor`、FIB dump API 走向统一，这两行影响面最大；读表方法与 04-03 相同——先定位自己用的形态，再按「核验位置」列确认当前语法，字段级差异见 `05-07` / `05-08`。

| 差异主题 | 早期 / 变化方向 | 23.06 / master | 核验位置 |
|---|---|---|---|
| 桥域命令 | 老式 `bridge-domain` 参数差异 | `bridge_domain_add_del` / `bridge_domain_set_flags` 稳定，开关子项增删 | `src/vnet/l2/` |
| 邻居命令 | `set ip arp` / `set ip6 neighbor` | 统一到 `ip neighbor add/del` + `ip_neighbor_add_del` | `src/vnet/ip-neighbor/` |
| 路由 API | `ip_route_add_del`（单路径） | `ip_route_add_v2` 等多路径 / 多标志 API 并存 | `src/vnet/ip/` |
| FIB dump | `ip4_fib_dump` / `ip6_fib_dump` | `ip_fib_dump` 统一化，字段变化 | `src/vnet/fib/` |
| VRF 建表语法 | `ip table <id> add` | `ip table add <id>` 关键字位置微调 | `src/vnet/ip/` |
| MPLS 表 | 隐式默认表 | 是否需 `mpls table add` 随版本变化 | `src/vnet/mpls/` |
| tag-rewrite | subif 参数内置 | 独立 `set interface l2 tag-rewrite` 命令更丰富 | `src/vnet/l2/` |
| xconnect | 部分子命令 | `sw_interface_set_l2_xconnect` 稳定 | `src/vnet/l2/` |

迁移提示：升级后最易失效的是**邻居与路由命令**（`set ip arp` → `ip neighbor`、路由 API v1→v2）和 **FIB dump 的 API 名**。脚本里凡用到 `show ip fib` / `show ip adjacency` 做自动化解析的，升级后要重新核对输出格式；字段级差异见 `05-07` / `05-08`。

### 7. 常见误用与调试

二层/三层命令的误用有一个共同模式：**表项写进了控制面，但转发路径没有闭合**，下表的现象列大多源于此；处理列的定位动作按「模式 → 归属 → 四连查」的顺序排列，与图 04-04-01 的分层一致，表外现象先判断是不是「配置没绑定」这类服务层问题，再转 04-05。

| 误用 / 现象 | 根因 | 处理 / 定位 |
|---|---|---|
| 建了 BD 但不通 | 没用 `set interface l2 bridge` 把接口加进来 | `show bridge-domain <id> detail` 看成员为空 |
| 接口配了地址却不路由 | 接口还在 L2 模式 / 未 `set interface l3` | `show mode` 确认层次 |
| 路由加在 VRF 100 却不生效 | 接口仍在默认表 0，未 `set interface ip table` | `show ip table` / `show interface address` 核对归属 |
| `show ip route` 有条目但不通 | 路由未解析到有效邻接 / 邻居未 resolved | 走「FIB → 邻接 → 邻居」四连查 |
| 邻居一直 incomplete | 对端未回 ARP/ND / VLAN 或 IP 配错 | `show ip neighbors`、用 `04-06` 的 `trace` 看 ARP/ND 报文 |
| 静态 ARP 加了却被老化 | 未加 `static` 标志 | 用 `static` 标志，或新版 `ip neighbor ... static` |
| xconnect 双端不通 | 只配了一端 / 接口未 up | 两端都配 `set interface l2 xconnect`，确认 up |
| L2FIB 表项不生效 | bd_id 写错 / 接口不在该 BD / 标志冲突 | `show l2fib` + `show bridge-domain` 对照 |
| MPLS 标签不转发 | 接口未 `mpls interface enable` / 出标签路由缺失 | `show mpls interface` / `show mpls fib` |
| 配置重启全丢 | 误以为 CLI 持久化 | `exec` 脚本 + `unix{ exec }`，见 `04-07` |
| 命令报 unknown | 相关插件 / 模块未加载（如 MPLS 特性） | 查 `04-01` `plugins{}` 与 `?` |

调试主线：**先定层次（L2 还是 L3，`show mode`）→ 再核归属（VRF 表 id）→ 最后走四连查（路由/FIB/邻接/邻居）**。一旦定位到 MAC 学习老化、FIB 解析算法、DPO/邻接 rewrite 结构、MPLS 标签栈这些内部机制，转 `07-02` / `07-03` / `07-10`（模块功能）、`06-xx`（原理）、`05-07` / `05-08`（字段），本册只负责命令与参数。

### 3. 逐项详解

#### 3.1 NAT 族

NAT 是命令最多、版本分化最明显的一族，务必区分「传统 NAT44」与「endpoint-dependent / ED 模式」以及 NAT66。基本流程是：先用 `nat44 add address` 声明外网地址池，再用 `nat44 add interface ... in/out`（或 `set interface nat44 in/out`，依版本）把接口标为 inside / outside，然后按需加静态映射 / 身份映射 / 负载均衡映射，`nat44 enable` 或 `set nat44 forwarding` 打开转发，最后用 `show nat44 ...` 家族查看地址、接口、静态映射、用户 / 会话。全局参数（会话超时、MSS clamping、端口范围、deterministic / ED 行为）用 `set nat44 ...` 系列。**注意**：ED 模式（endpoint-dependent）与传统模式的命令 / API 前缀不同（如 `nat44_ed_*`），混用会报 unknown，落地前先用 `?` 确认当前版本支持的子命令族。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 加地址池 | `nat44 add address <ip> [- <ip>] [tenant-vrf <id>] [twice-nat]` | 地址 / 范围、VRF、标志 | 声明 NAT 外网地址 | `nat44_add_del_address_range` | `nat44 add address 203.0.113.10 - 203.0.113.20` | 稳定 |
| 删地址池 | `nat44 del address <ip> ...` | 同上 | 删除地址池 | `nat44_add_del_address_range`（is_add=0） | `nat44 del address 203.0.113.10` | 需核验 |
| 标记内 / 外网口 | `nat44 add interface address <if> [in\|out]` / `set interface nat44 in\|out <if>` | 接口、方向 | 设 inside / outside 接口 | `nat44_interface_add_del_feature` / `nat44_interface_add_del_output_feature` | `set interface nat44 in Gig0/8/0` | 命令形态随版本差异大，需核验 |
| 静态映射 | 1:1 静态映射（见下方命令示例） | 内外地址 / 端口、协议、标志 | 1:1 静态映射 | `nat44_add_del_static_mapping` | `nat44 add static mapping local 10.0.0.10 external 203.0.113.10` | 参数较多，需核验 |
| 身份映射 | `nat44 add identity mapping <ip> [<port>] [proto ...]` | 地址、端口、协议 | 不做转换的旁路映射 | `nat44_add_del_identity_mapping` | `nat44 add identity mapping 10.0.0.10` | 需核验 |
| LB 静态映射 | `nat44 add load-balancing ...` | 后端池 | NAT 负载均衡映射 | `nat44_add_del_lb_static_mapping` | 需核验 | 是否提供需核验 |
| 开关 / 全局参数 | `nat44 enable\|disable`、`set nat44 ...`（session 超时 / mss / 端口 / forwarding） | 依子项 | 启用 NAT、配全局参数 | `nat44_plugin_enable_disable` / `nat44_set_*` / `nat44_ed_set_*` | `set nat44 forwarding enable` | ED 模式前缀不同，需核验 |

| NAT66 | NAT66 接口与静态映射语法（见下方命令示例） | 接口 / 内外地址 | IPv6 NAT | `nat66_add_del_interface` / `nat66_add_del_static_mapping` | `nat66 add interface Gig0/8/0 side inner` | 需核验 |

#### 3.2 ACL 族

ACL 用「规则列表 + 绑定到接口方向」两步：`acl add <rule...>`（或 `acl replace`）创建 / 更新 ACL 并返回 `acl-index`，`set interface acl <if> input|output <index-list> [ip4|ip6|l2]` 把 ACL 绑到接口输入 / 输出方向，`acl del <index>` 删除，`show acl [<index>]` 查看规则。规则语法用一串 `<action> <proto> src <prefix> dst <prefix> [sport <range>] [dport <range>] [tcpflags ...]` 之类的 token（具体以 `acl add ?` 为准）。macip ACL 用 `macip acl add` + `set interface macip acl`。**注意**：ACL 是「有序规则列表」，绑定时可一次挂多个 index（按序匹配）；`07-08` 讲状态化 / session 与 classify 防火墙的功能差异，本篇只列命令。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 创建 / 替换 ACL | `acl add [replace] <rules...>` | 规则串、`replace` 可带 index | 创建 ACL 返回 index | `acl_add_replace` | `acl add permit src 10.0.0.0/8 dst 0.0.0.0/0` | 规则 token 随版本变化，需用 `?` 核验 |
| 删除 ACL | `acl del <index>` | acl-index | 删除 ACL | `acl_del` | `acl del 3` | 稳定 |
| 绑定接口 | `set interface acl <if> input\|output <index-list> [ip4\|ip6\|l2]` | 接口、方向、index 列表、协议层 | 把 ACL 挂到接口 | `acl_interface_add_del` / `acl_interface_set_acl_list` | `set interface acl Gig0/8/0 input 3 5 ip4` | 绑定形式随版本变化，需核验 |
| 查 ACL | `show acl [<index>]` / `show acl-plugin ...` | 可选 index | 列出 ACL 规则与统计 | `acl_dump` / `acl_details` | `show acl 3` | 需核验 |
| macip ACL | `macip acl add <rules...>` | 规则（含 MAC/IP） | 创建 MAC+IP ACL | `macip_acl_add` | `macip acl add ...` | 需核验 |
| macip 绑定 | `set interface macip acl <if> <index> ...` | 接口、index | 绑定 macip ACL | `macip_acl_interface_add_del` | 需核验 | 需核验 |

#### 3.3 IPsec / IKEv2 族

IPsec 有「手工配 SA/SPD」与「IKEv2 自动协商」两条线。手工线：`ipsec sa add <id> spi <spi> crypto-alg <alg> ... integ-alg ... tunnel src <ip> dst <ip>` 建 SA，`ipsec spd add <id>` 建安全策略库，`ipsec spd entry add <spd> ...`（或 `ipsec policy add`）加策略（action protect/bypass/discard + 匹配 + SA），`ipsec spd interface add del spd <id> <if>` 把 SPD 绑到接口，`show ipsec sa|spd|all` 查看。IKEv2 线：`ikev2 profile add <name>` 建 profile，用 `ikev2 profile set <name> auth ...`、`... set id ...`、`... set traffic-selector ...`、`... set responder ...`、`... set ike-crypto-alg` / `... set esp-crypto-alg` / `... set sa-lifetime` 等配置，`ikev2 initiate sa-init <name>` 发起协商，`show ikev2 sa` 看 SA。**注意**：IPsec 命令与 API 在 23.06 前后有 `_v2`/`_v3` 演进（如 `ipsec_sad_entry_add_del_v2`），密钥 / 算法参数极多，务必用 `?` 与源码核对，切勿凭记忆硬写。

| 命令 | 语法 | 参数 | 作用 | 对应 API | 示例 | 版本差异 |
|---|---|---|---|---|---|---|
| 建 / 删 SA | 建 / 删 SA（见下方命令示例） | sa-id、spi、加密/认证算法与密钥、隧道端点 | 建 / 删安全关联 | `ipsec_sad_entry_add_del` / `..._v2` / `..._v3` | `ipsec sa add 10 spi 1000 crypto-alg aes-gcm-128 ...` | `_v2`/`_v3` 演进明显，需核验 |
| 建 / 删 SPD | `ipsec spd add <id>` / `ipsec spd del <id>` | spd-id | 管理安全策略库 | `ipsec_spd_add_del` | `ipsec spd add 1` | 稳定 |
| 加策略 | 配 SPD 策略（见下方命令示例） | spd-id、优先级、动作、匹配、SA | 配 SPD 策略 | `ipsec_spd_entry_add_del` / `ipsec_spd_entry_add_del_v2` | `ipsec spd entry add 1 priority 10 action protect sa 10` | 命令名 `policy` / `entry` 随版本，需核验 |
| 绑 SPD 到接口 | `ipsec spd interface add del spd <id> <if>` / `set interface ipsec spd <id> <if>` | spd-id、接口 | 接口启用 IPsec | `ipsec_spd_interface_add_del` | `set interface ipsec spd 1 Gig0/8/0` | 需核验 |
| IKEv2 profile | `ikev2 profile add <name>` / `del <name>` | 名称 | 建 / 删协商 profile | `ikev2_profile_add_del` | `ikev2 profile add peer1` | 稳定 |

#### 3.4 隧道族（VXLAN / GRE / Geneve）

隧道命令属于「创建服务类接口」，与 `04-03` 的 `create interface` 精神一致，但归本篇是因为它们由隧道插件提供、且参数围绕封装。`create vxlan tunnel src <ip> dst <ip> vni <n> [instance <n>] [encap-vrf <id>] [decap-next ...] [del]` 建 VXLAN 隧道（生成 `vxlan_tunnelN` 接口，之后可 `set interface l2 bridge` / `set interface ip address`）；`create gre tunnel src ... dst ... #### 3.5 负载均衡 LB 族

LB 插件以「VIP + AS（应用服务器后端）」建模：`lb vip <prefix> [protocol tcp|udp] [port <n>] [encap gre4|gre6|l3dsr|nat4|nat6] [dscp] [srv-cluster] [new_len <n>] [del]` 创建 / 删除 VIP，`lb as <vip> <as-address> [del]` 增删后端，`show lb vip` / `show lb as` / `show lb ...` 查看。encap 方式决定转发封装（GRE / L3DSR / NAT），与 Maglev 一致性哈希一起构成 LB 的核心（算法与 Maglev 表原理见 `07-09`，字段见 `05-12`），本篇只列命令。

### 4. 典型示例

下面给出一段「NAT44 网关 + 出方向 ACL + VXLAN 隧道」的组合序列，体现本篇命令如何与 `04-03` / `04-04` 的接口底座配合。

```bash
# 0) 前置：确认插件已加载（见 04-01 plugins{}），用 ? 探命令
vppctl show plugins
vppctl nat44 ?

# 1) 接口与地址（见 04-03）
vppctl set interface state GigabitEthernet0/8/0 up
vppctl set interface ip address GigabitEthernet0/8/0 10.0.0.1/24
vppctl set interface state GigabitEthernet0/9/0 up
vppctl set interface ip address GigabitEthernet0/9/0 203.0.113.1/24

# 2) NAT44：地址池 + 内外网口 + 静态映射 + 启用
vppctl nat44 add address 203.0.113.10 - 203.0.113.20
vppctl set interface nat44 in GigabitEthernet0/8/0
vppctl set interface nat44 out GigabitEthernet0/9/0
vppctl nat44 add static mapping local 10.0.0.10 external 203.0.113.10
vppctl set nat44 forwarding enable
vppctl show nat44 addresses
vppctl show nat44 interfaces
vppctl show nat44 static-mappings

# 3) ACL：允许内网出、其余拒绝，绑到内网口 input
vppctl acl add permit src 10.0.0.0/24 dst 0.0.0.0/0
vppctl acl add deny src 0.0.0.0/0 dst 0.0.0.0/0
vppctl set interface acl GigabitEthernet0/8/0 input 0 ip4
vppctl show acl

# 4) VXLAN 隧道：建隧道口 → up → 放进桥域（见 04-04）
vppctl create vxlan tunnel src 10.0.0.1 dst 10.0.0.2 vni 100
vppctl set interface state vxlan_tunnel0 up
vppctl bridge-domain 10 add
vppctl set interface l2 bridge vxlan_tunnel0 10
vppctl show vxlan tunnel
vppctl show bridge-domain 10 detail
```

要点：第 0 步先确认插件加载（这是 `04-05` 命令能否用的前提）；NAT 必须先 `add address` 再标接口；ACL 用有序 index 绑定；隧道创建后只是生成接口，还要 up / 进 BD 才真正参与转发。整段命令可写入 `exec` 脚本持久化（见 `04-07`）。

再看一个聚焦「LB 负载均衡 VIP + 后端 AS」的完整示例，含命令、典型输出与判读：

```bash
# 前置：确认 LB 插件已加载，并用 ? 核对当前版本支持的子命令
vppctl show plugins
vppctl lb ?

# 创建一个 LB VIP（GRE4 封装），再逐个加入后端 AS
vppctl lb vip 203.0.113.100/32 encap gre4 new_len 1024
vppctl lb as 203.0.113.100/32 10.0.0.11
vppctl lb as 203.0.113.100/32 10.0.0.12
vppctl lb as 203.0.113.100/32 10.0.0.13

# 验证：VIP 与 AS 是否都进了流表
vppctl show lb vip
vppctl show lb as
# lb vip / lb as 的参数（encap、protocol、port、new_len）需对照实际版本核验
```

对应典型输出（字段为示意，随版本略有差异）：

```text
vpp# show lb vip
VIP 203.0.113.100/32
  encap: gre4
  new_len: 1024
  as_count: 3
vpp# show lb as
VIP 203.0.113.100/32
  10.0.0.11
  10.0.0.12
  10.0.0.13
```

判读说明：`show lb vip` 应列出 `203.0.113.100/32` 及其 `encap gre4`、`new_len 1024` 与后端数量，`show lb as` 则逐行列出三个 AS 地址；两者后端数一致、且 VIP 出现在列表里，才算「VIP 已建、后端已挂」。`new_len` 是流表长度，过小会在后端较多时导致哈希冲突、命中不均；`encap` 决定封装方式（gre4 / gre6 / l3dsr / nat4 / nat6），必须与对端及隧道类型一致，否则有 VIP 却不通。判断生效的闭环是：`show plugins` 能看到 LB 插件 → `show lb vip` 有 VIP → `show lb as` 后端齐全 → 打流时 VIP 计数增长。常见异常：`lb` 报 unknown command 是 LB 插件未在 `plugins{}` 加载（见 04-01）；VIP 存在但 `show lb as` 为空是漏了 `lb as`；后端不均衡多为 `new_len` 不足或 `encap` 两端不符；`lb vip` 参数报不支持，则是 `lb_vip_add_del_v2` 等 API 演进带来的语法差异，须用 `lb ?` 核对。CLI 配置重启即失，需写入 `exec` 脚本（见 04-07）。补充一点：`show lb vip verbose` 还能看到流表桶的使用情况，配合 04-06 的 `show errors` 可区分「配置未生效」与「转发丢包」两类不同问题，避免排错方向跑偏。以上参数需对照实际版本核验。

### 5. 速查表

下表覆盖 NAT、ACL、隧道、IPsec、LB、policer/classify 六大服务的最短可用命令链：每行是「一步动作」，多行按自上而下的顺序拼起来才构成一个完整服务配置——服务类命令的特点是「本体 + 绑定」两步缺一不可，备注列专门提示了这一步的存在。

| 诉求 | 命令 | 备注 |
|---|---|---|
| 配 NAT44 地址池 | `nat44 add address <range>` | 先于标接口 |
| 标内 / 外网口 | `set interface nat44 in\|out <if>` | 或 `nat44 add interface` |
| 加静态映射 | `nat44 add static mapping local ... external ...` | 1:1 |
| 查 NAT 会话 | `show nat44 sessions` | 子命令用 `?` 看 |
| 建 ACL | `acl add <rules>` | 返回 index |
| 绑 ACL 到接口 | `set interface acl <if> input\|output <idx>` | 有序列表 |
| 查 ACL | `show acl` | — |
| 建 VXLAN 隧道 | `create vxlan tunnel src ... dst ... vni <n>` | 生成接口后要 up |
| 查隧道 | `show vxlan tunnel` / `show gre tunnel` | — |
| 建 / 绑 SPD | `ipsec spd add` + `set interface ipsec spd` | 配 SA 后 |
| IKEv2 发起 | `ikev2 initiate sa-init <profile>` | 先配 profile |
| 查 IPsec | `show ipsec all` / `show ikev2 sa` | — |
| 建 LB VIP | `lb vip <prefix> encap ...` | 再 `lb as` 加后端 |
| 定义 policer | `configure policer <name> ...` | — |
| 建分类表 | `classify table mask ...` | 再 `classify session` |
| 绑分类 / 限速 | `classify set interface <if> ...` | — |

一句话记忆：**「服务三步走：先确认插件加载 → 再配服务本体（地址/规则/隧道/VIP）→ 最后挂到接口或进 BD 并 show 验证」**；NAT 命令先 `?` 分清传统 / ED 模式，IPsec / 隧道参数一律用 `?` 核对版本。

### 6. 版本差异

服务插件是全书版本漂移最大的一族，下表按差异主题分列：NAT 模式前缀、IPsec/VXLAN 的 `_v2/_v3` 参数、ACL 绑定形式三行最常导致升级后脚本批量失效；读表时注意「变化方向」列——多数演进是「旧消息保留、新消息加字段」，控制器集成要按 04-08 的命令↔API 映射同步核对。

| 差异主题 | 早期 / 变化方向 | 23.06 / master | 核验位置 |
|---|---|---|---|
| NAT 模式 | 单一 NAT44 | 传统 / ED（endpoint-dependent）/ deterministic 并存，命令前缀不同（`nat44_ed_*`） | `src/plugins/nat/` |
| NAT 接口命令 | `set interface nat44 in/out` | `nat44 add interface ...` / `nat44_interface_add_del_feature` 形态演进 | `src/plugins/nat/` |
| IPsec SA API | `ipsec_sad_entry_add_del` | 新增 `_v2` / `_v3`，字段（如 ESN、async）变化 | `src/vnet/ipsec/` |
| VXLAN API | `vxlan_add_del_tunnel` | `_v2` / `_v3` 增加 encap-vrf、端口、GPE 等 | `src/vnet/vxlan/` |
| GRE API | `gre_tunnel_add_del` | `_v2` 支持多参数 | `src/vnet/gre/` |
| LB API | `lb_vip_add_del` | `_v2` 增加流表长度等参数 | `src/plugins/lb/` |
| ACL 绑定 | `acl_interface_add_del` | `acl_interface_set_acl_list`（多 index 列表） | `src/plugins/acl/` |
| classify | `classify_add_del_table` | `_v2`、mask/next-node 参数变化 | `src/vnet/classify/` |
| DHCP/DNS | 命令形态不一 | 逐步插件化、API 化 | `src/vnet/dhcp/` / `src/vnet/dns/` |

迁移提示：本篇是全书版本漂移最大的一族。升级后**任何**服务脚本都应先用 `?` 重新核对命令名与参数，尤其 NAT 模式前缀、IPsec/VXLAN 的 `_v2/_v3` 参数、ACL 绑定形式。控制面集成若直接调 Binary API，API 名变化会直接导致编译 / 运行失败，映射表见 `04-08`。字段级差异见 `05-11` / `05-12`。

### 7. 常见误用与调试

服务命令的误用几乎都是「三步走」缺步造成的，下表现象列按缺哪一步归组：报 unknown command 是缺第一步（插件未加载）、对象存在但不转发是缺第三步（绑定到接口）、参数报错多半撞上第二列的版本差异；每行处理列都给出了该服务专属的 `show` 命令作为定位出口。

| 误用 / 现象 | 根因 | 处理 / 定位 |
|---|---|---|
| 服务命令报 unknown command | 插件未加载（`plugins{}` 默认全关时最常见） | 查 `04-01` `plugins{}` 白名单、`show plugins`、启动日志 |
| NAT 配了不通 | 未 `add address` / 未标 in-out / 未 enable forwarding | `show nat44 addresses/interfaces` 逐项核对 |
| NAT 命令一半能一半不能 | 混用了传统 / ED 两套前缀 | 用 `?` 确认当前版本支持的子命令族，统一一套 |
| ACL 规则不生效 | index 绑错方向 / 未指定 ip4/ip6/l2 / 规则顺序错 | `show acl` + `show interface features` 核对绑定 |
| 静态映射对不上 | local/external 写反 / 端口协议不匹配 | 对照 `show nat44 static-mappings` |
| 隧道建了但不通 | 隧道口未 up / 未进 BD 或配对地址 / underlay 路由不通 | `show vxlan tunnel`、`show interface`、先验证 underlay 连通 |
| IPsec SA 建立失败 | 算法 / 密钥 / spi 两端不一致 / API 版本参数漏项 | `show ipsec all`、用 `?` 核对 `_v2/_v3` 参数 |
| IKEv2 协商不起来 | profile 少配 auth/id/ts / responder 不通 | `show ikev2 sa`、`show ipsec all`，核对 profile 全参数 |
| LB 后端不均衡 | 未加 AS / encap 方式两端不符 / 流表长度不足 | `show lb vip` / `show lb as` |
| policer 不限速 | 定义了但未绑到 classify / 接口 | `show policer` + `show classify tables` 核对绑定链 |
| 配置重启全丢 | 误以为 CLI 持久化 | `exec` 脚本 + `unix{ exec }`，见 `04-07` |

调试主线：**「插件加载 → 服务本体表项 → 接口绑定 → show 验证」四步逐层确认**，每一步都有对应的服务专属 `show`（本篇）与通用 `show`（`04-06`）。一旦定位到 NAT 会话状态机、IPsec 加密 / IKEv2 协商流程、ACL/classify 匹配算法、LB Maglev 哈希、隧道封装格式这些内部机制，转 `07-05` / `07-06` / `07-07` / `07-08` / `07-09`（模块功能）与 `06-xx`（原理），字段见 `05-11` / `05-12`，本册只负责命令与参数。

## 04-06 show / clear / trace / 调试命令全集

### 1. 本篇定位与覆盖范围

本册是 VPP **CLI 命令与配置参数的唯一权威源**，本篇则是其中"观测与诊断面"的全集：所有 `show` 子命令族、`clear` 类命令、`trace` / `pcap` 抓包、`monitor`、日志与 `api-trace`。它们不改变转发状态，只读取或复位运行时统计，因此是运维排障、性能判读、验证配置是否生效的第一入口。

边界要说清楚：本篇**只列命令、参数与用法，并说明输出里各字段怎么读**，不解释 counters 背后的实现原理（属 06 全册的调度与缓冲机制）、不展开 `vlib_buffer_t` / `vlib_node_t` 等结构体字段表（属 05 全册）、不重列模块内部转发流程（属 07 全册）。08 全册讲"在什么场景组合哪些命令、如何判读结果并定位故障"，本篇提供被组合的那些命令本身——两册分工是"命令字典"与"排障方法论"，不互相重复。

VPP 的 `show` 命令是**按插件/模块动态注册**的：加载了哪个插件，就会多出对应的 `show` 子命令。因此本节的清单以核心 + 常用插件为准，实际可用集合以 `show ?`（或 `?`）在当前实例上的输出为准；命令名、参数与输出格式在版本间有调整，凡标注「需对照实际版本核验」处，请以目标版本的 CLI help 与 `src/vlib/`、`src/vnet/`、`src/plugins/` 下注册该命令的 `VLIB_CLI_COMMAND` 宏为准。

### 3. 逐项详解

**`show interface [ <name> ] [ detail ]`**：最常用的一条。输出每个接口的 name、idx、state（up/down）、MTU、MAC、IP 地址，以及 rx/tx 的 packets / bytes、drops、error 计数。`detail` 会补充队列数、offload 标志、硬件能力等。判读要点：drops 增长而 rx 不涨通常指向收包队列或 buffer 不足；tx drops 增长要看出接口队列与驱动环大小。接口创建与地址配置命令见 04-03 / 04-04。

**`show hardware-interfaces [ <name> ] [ detail | verbose ]`**：从设备层看队列、描述符环（rx/tx desc）、中断/轮询模式、驱动名、PCI 地址、RSS 队列映射、支持的 offload。与 `show interface` 的区别是：前者是"逻辑软件接口"视角，后者是"硬件/驱动"视角。DPDK 相关参数见 04-01 的 `dpdk{}` 段。

**`show interface rx-placement` / `show interface rx-placement verbose`**：显示每个收包队列被分配给哪个 worker 线程。多 worker 调优时用它确认 RSS 队列是否均匀分布，CPU 打满但吞吐不涨的场景首先要看这里（组合用法见 08-02）。

**`show ip fib [ table <id> ] [ <prefix> ]` / `show ip6 fib`**：打印 FIB 表项：前缀、下一跳、权重、邻接索引、DPO 类型、以及以 `[@n]` 形式给出的计数器索引。加前缀可只查一条，便于确认静态路由是否装表。表项结构见 05-07，添加/删除路由的命令见 04-04。

**`show ip neighbors` / `show ip6 neighbors` / `show ip arp`**：邻居表，含 IP、MAC、接口、状态与老化计时。邻居不通时先查这里再看 `show error`（案例见 08-04）。具体命令名随版本有差异，**需对照实际版本核验**。

**`show l2fib` / `show bridge-domain [ <id> ] [ detail ]`**：二层转发表与桥域明细（成员接口、学习/泛洪/未知单播行为、MAC 老化时间）。配置命令见 04-04。

**`show runtime [ <node-name> ]`**：VPP 性能判读的核心命令。每行一个图节点，输出 Calls、Vectors（累计处理包数）、Suspends、Clocks、Vectors/Call。判读方法：Clocks/Vectors 反映单包成本；Vectors/Call 接近批处理上限说明向量规模饱满；某节点 Vectors 远小于上游说明中间有丢包或分流。进程节点平时 Calls 不增长属正常（原理见 06-15）。用法与案例见 08-02 / 08-03。

**`show node [ <name> ]` / `show vlib graph`**：节点属性（type、state、flags、下一节点索引、sibling 关系）与处理图拓扑。用于确认 feature arc 上某个特性是否挂到预期位置（原理见 06-02 / 06-03）。

**`show errors`**：按节点+原因列出错误计数。这是"为什么丢包"的第一手依据，例如 `ip4-input` 下的 `no table`、`ttl exceeded`，或 `ethernet-input` 下的 `unknown vlan`。每个计数条目都对应源码里一处 `b->error = ...` 赋值，可按名字回搜源码定位。判读流程见 08-03。

**`show buffers`**：各 buffer pool 的 size、allocated、free、以及每 NUMA 节点的分布。大页不足或 worker 数增加后 free 持续走低，是典型的丢包前兆（字段见 05-04，调优见 08-02）。

**`show memory` / `show vlib memory` / `show physmem`**：堆使用、mheap 统计、物理大页映射。怀疑内存泄漏或 heap 碎片时对比多次快照（原理见 06-10）。具体命令名**需对照实际版本核验**。

**`show threads`**：列出 main 与各 worker 的线程 ID、CPU 亲和、每线程处理包数与耗时。配合 `show interface rx-placement` 检查负载是否均衡。

**`show version [ verbose ]`**：VPP 版本、编译时间、构建信息、编译选项。报障与升级前必须记录（版本矩阵见 08-05）。

**`show plugins` / `show api clients` / `show api trace`**：已加载插件清单、当前连接的 API 客户端、API 消息轨迹。控制面连不上时先查 `show api clients`；`api-trace` 的开关在 startup.conf 的 `api-trace{}` 段（见 04-01）。消息机制原理见 06-13，编程接口见 04-07。

**`show logging`**：当前日志级别与各输出目标。日志配置在 startup.conf 的 `logging{}` 段（见 04-01），日志文件默认位于 `/var/log/vpp/`（见 08-03）。

**`trace add <input-node> <count> [ filter ]` / `show trace [ max <n> ]`**：packet trace 是 VPP 最有价值的排障手段。`trace add` 在指定 input node 上标记接下来 N 个包，`show trace` 打印这些包**完整经过的每一个图节点**及每步的决策（查表结果、错误、改写后的报文头）。常用写法如 `trace add dpdk-input 100`；加 filter 可只看特定流。用法与决策链见 08-03。

**`pcap trace [ rx | tx | drop ] ...` / `pcap trace status` / `pcap trace off`**：把指定方向/接口的报文导出为 pcap 文件，供 Wireshark 分析。与 packet trace 的区别：pcap 给报文内容，packet trace 给 VPP 内部路径。参数细节**需对照实际版本核验**。

**`monitor <...>` / `show event-logger`**：实时事件流与事件日志缓冲，用于观察接口 up/down、插件加载等异步时序（进程事件原理见 06-15）。

**`clear interfaces`、`clear errors`、`clear trace`、`clear ip neighbor`**：复位类命令。`clear errors` 之后立刻复现问题再 `show errors`，是隔离"历史累计值"与"当前增量"的标准做法；`clear trace` 清空 packet trace 缓冲。注意这些命令只清计数，不改配置。

### 4. 典型示例

一次典型的"接口不通"最小观测序列（组合方法论见 08-03，此处只演示命令本身）：

```bash
vppctl show version
vppctl show interface addr
vppctl show interface GigabitEthernet0/8/0
vppctl clear errors
# 复现流量
vppctl show errors
vppctl show ip fib 10.0.0.0/24
vppctl show ip neighbors
vppctl trace add dpdk-input 50
# 复现流量
vppctl show trace max 50
```

一次性能判读的最小序列：

```bash
vppctl show threads
vppctl show interface rx-placement
vppctl show runtime
vppctl show buffers
vppctl show errors
```

**`show runtime` 的完整输出与逐列判读**（示例输出，具体格式需对照实际版本核验）：

```text
Time 15.3, average vectors/node 18.42, last 128 main loops 0.00 usec
  Name             State     Calls   Vectors  Suspends  Clocks  Vectors/Call
  dpdk-input       polling   3.82e6  7.64e6   0         18      2.00
  ethernet-input   polling   3.82e6  7.64e6   0         24      2.00
  ip4-lookup       polling   3.80e6  7.58e6   0         46      1.99
  ip4-rewrite      polling   3.80e6  7.58e6   0         31      1.99
  GigabitEthernet0/8/0-output polling 3.80e6 7.58e6 0    22      1.99
  unix-cli-newprocess event wait 12  0        12        2.1e8   0.00
```

逐列判读：首行两个数字是全局概貌——`average vectors/node` 是平均向量规模，长期低于 10 说明流量小包化或中断路径介入，向量处理的批处理收益没有兑现；`State` 列区分 polling 与 interrupt-wait，纯 polling 是 PMD 模式的预期状态。`Calls` 是节点被调度次数、`Vectors` 是累计处理包数，两者之比即末列 `Vectors/Call`：dpdk-input 侧该值等于每轮实际收到的包数，若恒为 1 左右说明向量化失效。`Clocks` 是每包平均周期数（单位需对照实际版本核验，不同版本含义有差异），横向比较同一节点在调优前后的变化才有意义；`ip4-lookup` 明显高于 `ip4-rewrite` 属正常（查表成本高于改写），反之则说明路由表规模异常。`Suspends` 非零的行是进程节点（如 CLI 会话），平时 Calls 不增长是预期行为，不属于性能问题。全表判读的入口问题只有一个：「哪个节点的 Clocks × Calls 在总耗时里占比最高」，它就是下一个优化或排障对象。

**`show errors` 的完整输出与判读**（示例输出，具体格式需对照实际版本核验）：

```text
  Count                    Node                  Reason
  1523                     ip4-input             no such table
  9                        ip4-icmp-error        unknown
  0                        dpdk-input            rx error no buffers
```

判读：三列分别是累计计数、出错节点与原因字符串。`no such table` 集中出现在 `ip4-input` 说明报文到达了 VPP 但目的 IP 没有匹配的 FIB 表——最常见的根因是接口绑定了 VRF 而路由配在默认表（见 04-04 的 VRF 归属问题）；`rx error no buffers` 挂在 dpdk-input 下是 buffer 池耗尽的直接证据，要回查 `show buffers` 与 `buffers-per-numa` 配置；计数值为零的行只说明该原因从未发生，可放心忽略。判读动作永远是对着原因字符串回搜源码——每个 error 名都对应一处 `vlib_buffer_t` 的 error 赋值，按名字在 `src/vnet/` 下检索即可定位到产生丢包的确切代码行。此输出为示例，列名与计数器集合需对照实际版本核验。

**失败模式与边界条件**。观测命令本身也有失效场景：其一，`trace add` 的标记缓冲有限，高流量下标记名额会被新包迅速耗尽，标记数要按「复现时长 × 速率」估算，宁可多给；其二，`pcap trace` 默认有包数上限与文件大小上限，上限用尽后静默停止写入，误以为「抓到了全部」是常见误判，导出后先看文件里最后一帧的时间戳是否覆盖了复现窗口；其三，`show trace` 只保留最近若干条，`clear trace` 或进程重启后历史全部丢失，重要现场要先落盘再复现；其四，`clear` 类命令只清计数不清状态，若清零后计数仍快速增长，说明丢包根因是持续性而非历史残留，应转 `trace` 与 `show errors` 深挖（决策链见 08-03）。

| 接口 up 没有、有没有计数 | `show interface` |
| 队列绑到哪个 worker | `show interface rx-placement` |
| 驱动/队列/PCI 详情 | `show hardware-interfaces` |
| 路由装表没有 | `show ip fib <prefix>` |
| 邻居解析成功没有 | `show ip neighbors` |

### 6. 版本差异

观测类命令的版本差异集中在「命令名合并改名」与「输出列变化」两点，前者影响脚本可用性、后者影响自动化解析，下表逐项列出；凡本表覆盖不到的子命令，一律以当前实例的 `?` 输出为准再下结论。

| 差异点 | 说明 |
|---|---|
| 命令别名 | `show ip arp` 与 `show ip neighbors`、`show vlib memory` 与 `show memory` 等在不同版本有合并/改名 |
| 输出字段 | `show runtime` 的列名与 Clocks 计算方式随版本调整；`show interface` 新增 offload/queue 字段 |
| 统计段 | statseg 相关命令在新版本中改为独立工具（如 `vpp_get_stats` / `statseg` 接口），**需对照实际版本核验** |
| pcap trace 参数 | 语法在多个版本间变动较大，务必以 `pcap trace ?` 实际 help 为准 |
| `show vlib processes` | 部分版本不提供，进程节点观察改用 `show runtime` + 事件日志 |

所有版本基准为 VPP 23.06 / master；升级后命令清单的变化是 08-05 配置迁移检查项之一。

### 7. 常见误用与调试

1. **把累计值当增量看**。`show errors` / `show interface` 是开机以来累计，排查前先 `clear errors` 再复现，否则会被历史噪声误导。
2. **只 `trace add` 不 `show trace`**，或标记数太小导致没抓到目标流。先确认流量走哪个 input node（DPDK 环境通常是 `dpdk-input`），必要时加 filter。
3. **把 `show runtime` 的 Clocks 当成绝对耗时**。它是 CPU 周期数，跨机型/频率不可直接比较，应看相对占比与 Vectors/Call 的变化趋势（判读方法见 08-02）。
4. **在没加载插件时找插件专属命令**。`show nat44 sessions` 之类只在对应插件启用后出现，先 `show plugins`。
5. **误用 `clear` 以为能修问题**。`clear` 只复位计数，不重建会话或表项；清空后若计数立刻重新增长，说明根因仍在（案例见 08-04）。
6. **`pcap trace` 长期开着**。抓包会显著增加每包开销并写盘，生产环境用完立即 `pcap trace off`。
7. **忽略 `show version`**。同一命令在不同版本输出与语义可能不同，报障与对照文档时必须附版本号。
8. **命令名照抄文档**。本篇标注「需对照实际版本核验」的命令，请先用 `show ?` 确认当前实例确实存在，再套用参数。

## 04-07 控制面与 API 集成、配置持久化

### 1. 本篇定位与覆盖范围

前六篇解决"人通过 CLI 怎么配置 VPP"，本篇解决另外两件事：**程序怎么配置 VPP**，以及**配置怎么在重启后自动恢复**。前者是控制面集成——外部控制器、编排系统、自研管理平台通过 Binary API 与 VPP 通信；后者是持久化——VPP 的运行时配置默认不落盘，重启即丢，必须靠启动脚本或配置管理重建。

本篇覆盖：Binary API 的传输与消息模型、VAT 与 `vppctl` 之外的调试通道、官方语言绑定（C / Python / Go / govpp）、Honeycomb / NETCONF 等高层控制面、VCL 编程与事件订阅、`exec` 启动脚本与 `startup.conf` 的 `unix{ exec }` / `cli-listen` / `socksvr{}` / `api-trace{}` 段、以及配置保存与开机加载的几种落地方式。

边界：本篇**只列接口、参数、用法与配置片段**，不解释消息序列化与共享内存队列的实现原理（见 06-13 / 06-10）、不展开 `vlib_api_main_t` 等结构体字段表（见 05-12）、不讲模块内部转发逻辑（见 07 全册）。命令清单本身属 04-03 ~ 04-06。

### 3. 逐项详解

**Binary API 模型**。VPP 的编程接口不是 HTTP/REST，而是基于消息的二进制协议：每个操作对应一条 request/reply 消息（如创建接口、加地址、加路由），消息结构由 `.api` 文件定义，经 `vppapigen` 生成 C 头与各语言绑定。客户端与 VPP 之间通过共享内存上的消息队列（svm queue）交换序列化的消息，主循环在 API 处理节点中消费。控制面下发 → API handler 修改数据面表项 → 必要时通过 barrier 同步到所有 worker（原理见 06-13 / 06-06 / 06-07）。消息定义文件位于 `src/vnet/`、`src/vlib/`、`src/plugins/` 下的 `*.api`；字段表见 05-12。

**连接与握手**。客户端连接 VPP 的 API socket（默认路径与 `socksvr{}` 配置相关，见 04-01），随后做一次版本/消息表协商（获取消息 ID 映射）。这是绑定库自动完成的，手写客户端时必须先协商再发业务消息，否则消息 ID 对不上。可用 `show api clients` 查看当前连接（命令见 04-06）。

**VAT（VPP API Test）**。官方自带的消息级调试工具，进入交互后可直接按 API 名发消息并看原始 reply。用途是区分"CLI 封装的问题"还是"API 本身的问题"：同一操作在 `vppctl` 失败但在 VAT 成功，说明问题在 CLI 参数解析；两者都失败则要看数据面状态。VAT 的命令名与 API 名一一对应，是核对消息字段的权威参考，**需对照实际版本核验**。

**C 绑定**。由 `vppapigen` 从 `.api` 文件生成的函数与类型，适合同机、高频、要求低延迟的控制面程序。生成物通常在构建输出的 include 路径下；调用模式为"连接 → 注册 reply 回调 → 发 request → 等待/轮询 reply"。编译与链接方式见 02-04 / 02-06，构建产物路径见 02-02。

**Python 绑定（`vpp_papi`）**。适合自动化脚本、CI 验证与运维工具。典型形态是导入包、连接 socket、调用与 API 同名的方法、检查 `retval`。优点是快速验证与批量配置；性能不如 C/Go，不适合高频逐条下发。包名、安装方式与 API 生成方式**需对照实际版本核验**。

**Go 绑定（govpp）**。云原生场景（K8s CNI、控制器）最常用的绑定，提供类型化的消息结构与 channel 化的事件流。使用模式：`govpp.Connect` → 新建 `api.Channel` → `ch.SendRequest(...).ReceiveReply(...)`；事件订阅用 `SubscribeEvent` 一类接口。它是把 VPP 集成进 Go 控制面的事实标准之一，模块路径与版本**需对照实际版本核验**。

**Honeycomb / NETCONF / RESTCONF**。当上层控制器要求标准建模接口（YANG / NETCONF）时，用 hc2vpp 一类代理进程把模型操作翻译成 Binary API 消息。它属于外部进程，不在 VPP 包内，部署时需注意与 VPP 的版本匹配及 API socket 权限。生态与版本关系见 01-04。

**VCL 与 LD_PRELOAD**。VPP 的主机协议栈（session / transport 层，见 07-12）允许应用不经过内核 socket 而直接把流量交给 VPP。VCL 是显式链接的库，`ldpreload` 则通过 `LD_PRELOAD` 让既有二进制无改造接入。配置涉及 `vcl` 相关的环境变量与 VPP 侧的 session 层参数，具体参数**需对照实际版本核验**，属 04-05 插件配置范畴。

**事件订阅**。多数模块提供 `want_xxx_events` 形式的 API 消息，订阅后 VPP 在接口状态变化、会话建立/删除、统计周期到达时主动推送事件。订阅是"每连接"的，客户端断开即失效，重连必须重新订阅；事件到达速率高时要及时处理以免队列积压（事件与进程节点原理见 06-15）。

**`exec` 启动脚本与配置持久化**。VPP **不会自动保存运行时配置**——`vppctl` 里做的配置在进程重启后全部丢失。持久化只有两条路：

1. **启动脚本（推荐）**：把所有 `vppctl` 命令按顺序列成一个文本文件（约定 `.exec` 或任意路径），在 `startup.conf` 的 `unix{}` 段用 `exec /path/to/startup.exec` 指定，VPP 启动时按行执行。等价于人工把配置"重放"一遍，幂等性差，顺序有依赖，但最可靠、最透明。
2. **外部配置管理**：由控制器在 VPP 启动后通过 Binary API 重新下发全量配置（见上文的 govpp / Python），适合云环境与编排系统。

`startup.conf` 里与本篇直接相关的段（逐项字段见 04-01）：

```text
unix {
  nodaemon
  log /var/log/vpp/vpp.log
  full-coredump
  cli-listen /run/vpp/cli.sock
  exec /etc/vpp/startup.exec
  startup-config /etc/vpp/startup.conf.d/custom.exec   # 名称需对照实际版本核验
}
api-trace {
  on
  nitems 5000
}
socksvr {
  socket-name /run/vpp/api.sock                        # 名称需对照实际版本核验
}
```

`exec` 文件示例（命令本身见 04-03 / 04-04 / 04-05）：

```text
set interface state GigabitEthernet0/8/0 up
set interface ip address GigabitEthernet0/8/0 10.0.0.1/24
set interface state GigabitEthernet0/9/0 up
set interface ip address GigabitEthernet0/9/0 10.1.0.1/24
ip route add 0.0.0.0/0 via 10.0.0.254
```

**API 轨迹（api-trace）**。打开后 VPP 记录收到的 API 消息序列，可用 `show api trace`（命令见 04-06）回放，是排查"控制器下发了什么"的关键证据。生产环境建议按需开启，长期全量记录有内存开销。

**返回值与错误码处理**。每条 request 消息的 reply 都带一个 `retval` 字段：`0` 表示成功；负值表示失败，具体错误号与含义定义在 `src/vlibapi/` 与 `src/vnet/**/*.api` 关联的错误枚举里（各消息 reply 的 `retval` 语义需对照实际版本核验）。绑定库通常把 `retval != 0` 抛成异常或返回错误对象，自写客户端最常见的三类失误是：发完 request 不等 reply 就发下一条（消息 ID 与 reply 配对错乱）；只检查连接状态不检查 `retval`（命令实际失败但程序以为成功）；对 `*_dump` 类消息只收第一条 details 就停（dump 是多 reply 流，要读到空 details 或计数匹配才算结束）。排错时的标准动作是先在 reply 的 `retval` 上分层：`retval` 非 0 说明 VPP 侧拒绝（参数错、对象不存在、资源不足），要到 `show logging` 与对应模块的 `show` 命令找原因；`retval` 为 0 但功能不通，则问题在数据面，转 04-08 的排查路径。

**VAT 输出判读**。用 VAT 验证同一操作时，reply 的原始字段全部可见（示例输出，需对照实际版本核验）：

```text
vat# sw_interface_set_flags sw_if_index 1 admin-up
vat# sw_interface_dump
sw_if_index 1: GigabitEthernet0/8/0  flags: admin-up mtu 9000
sw_if_index 2: local0
vat# ip_route_add_del 10.0.0.0/24 sw_if_index 1 next-hop 10.0.0.2
ret val: 0
```

判读：`ret val: 0` 即该消息被 VPP 接受；非 0 时 VAT 会回显错误号，把它与绑定库侧的异常对照可以快速分层——VAT 也失败则问题在消息层（消息名、字段、参数），VAT 成功而 `vppctl` 失败则问题在 CLI 参数解析层，VAT 成功但功能不通则进入数据面排查。`sw_interface_dump` 这类 dump 消息在 VAT 里连发多条 details，收齐后才能下「接口清单」结论，只看第一行漏掉后续接口是 VAT 排错的常见误读。

**`exec` 的失败模式与边界**。`exec` 逐行执行脚本，行为有两处边界要写进运维手册：其一，某行失败后的继续/中止行为随版本变化（见本篇第 6 节），不能假设「报错即停」，所以脚本里关键步骤后要成对放置 `show` 类验证命令，靠人工或外部脚本核对结果而非依赖 exec 自身；其二，`exec` 在启动期执行时，此时插件加载与 DPDK 设备初始化刚完成，依赖接口存在的命令（如配地址）可能因设备枚举顺序不同而偶发失败，把「设备相关」与「纯逻辑」命令分组、组间加 `show` 检查点，能把这类偶发失败变成可定位的确定现象。手动验证脚本用 `vppctl exec <file>`（见第 4 节示例），执行完立即核对 `show interface addr` 与 `show ip fib` 是否与预期一致。

### 6. 版本差异

控制面的版本差异比 CLI 更隐蔽——消息名、socket 路径、绑定包名变了都不影响 `vppctl` 的日常使用，只有控制器集成时会暴露，下表逐项列出需要重点核验的差异点；升级控制器前逐行对照，比集成失败后再回溯省一个数量级的排错时间。

| 差异点 | 说明 |
|---|---|
| API 消息名 | 部分模块从 `*_dump`/`*_details` 迁移到新命名或改用新版本消息（带 `_v2` / `_v3` 后缀） |
| socket 路径与段名 | `socksvr{}` 与默认 API socket 路径、`unix{ startup-config }` 名称随版本变化 |
| 语言绑定 | Python 包名、govpp 模块路径、生成方式在版本间有调整 |
| Honeycomb | 与 VPP 版本强绑定，跨版本常不兼容 |
| `exec` 语义 | 多行脚本的错误处理（遇错继续/中止）行为有差异 |

统一的版本基准是 VPP 23.06 / master；升级时 API 兼容性检查是 08-05 的必检项。

### 7. 常见误用与调试

1. **以为 `vppctl` 配置会持久化**。这是最常见的坑：重启后配置全丢。要么 `unix{ exec }`，要么控制器全量重发，没有第三条路。
2. **手写客户端跳过消息表协商**。消息 ID 是协商得到的，硬编码必然错位；用官方绑定可规避。
3. **重连后不重新订阅事件**。事件订阅绑定在连接上，断开即失效，表现为"上线初期能收到通知，后来就没了"。
4. **高频逐条下发 API**。每条消息都要进主循环处理并可能触发 barrier，批量配置应合并或使用批量消息，否则控制面自身成为瓶颈（原理见 06-06 / 06-13）。
5. **`exec` 脚本顺序错**。接口没创建就配 IP、接口没 up 就加路由会失败；按"建接口 → 配地址 → 置 up → 加路由 → 加服务"顺序编排，并逐条验证。
6. **socket 权限问题**。`cli-listen` / API socket 的属主与权限不对，表现为 `vppctl` 或控制器连接被拒，检查 `/run/vpp/` 与启动用户。
7. **`api-trace` 长期全量开启**。占用共享内存且可能拖慢 API 处理，排障结束后关闭。
8. **忽略版本匹配**。绑定库、Honeycomb、控制器必须与目标 VPP 版本配套，跨版本组合的故障往往表现为"消息解析失败"而非明确报错。
9. **照抄文档里的 API 名**。本篇标注「需对照实际版本核验」处，请以目标版本 `*.api` 文件与生成头文件为准，或先用 VAT 验证。

### 3. 逐项详解

**L1 插件/服务是否加载**。VPP 的很多能力来自插件，且 `plugins{}` 段可控制加载与黑名单（见 04-01）。插件没加载时，对应 CLI 命令根本不存在，`vppctl` 会返回 parse error 而非业务错误——这类报错容易被误读成"语法写错了"。第一步永远是 `show plugins` 与 `show version`，确认能力集与版本。

**L2 配置是否写入表项**。`vppctl` 返回成功只代表命令被接受，不代表表项按预期生效。要按配置对象查对应表：`show ip fib`、`show bridge-domain`、`show l2fib`、`show nat44 ...` 等。特别注意 VRF/表 ID：路由加在默认表而接口绑在别的表，是"命令成功但不通"的典型原因（VRF 配置见 04-04）。

**L3 接口/绑定链是否完整**。很多服务需要"定义对象 + 绑定到接口"两步：ACL 要 apply、policer 要绑 classify、NAT 要设 inside/outside、feature 要按接口启用。只做了第一步时 `show` 能看到对象存在，却没有任何流量经过它。逐层核对"对象 → 绑定 → 接口方向"这条链，比反复改规则有效得多。

**L4 show 验证与 error 计数**。先用 `clear errors` 清零，复现流量，再看 `show errors` 与 `show interface` 的增量；若仍不明，用 `trace add` + `show trace` 看包具体停在哪一个图节点。packet trace 里每一跳都会写出该节点的决策与 error 名，按名字回搜源码即可定位到具体代码行（决策链详见 08-03）。

**配置持久化交叉检查**。凡"重启后消失"的问题，都回到 04-07 的两条路：`unix{ exec }` 脚本是否存在且被 startup.conf 引用、控制器是否在启动后重新下发。用 `vppctl exec <file>` 手动重放可以快速验证脚本本身是否正确。

**`api-trace` 交叉检查**。当配置由控制器下发时，`vppctl` 侧无从得知"到底发了什么"。打开 `api-trace{ on }` 后用 `show api trace` 回放消息序列，可区分"控制器没发"与"发了但 VPP 没生效"（见 04-07 / 04-06）。

### 4. 典型示例：完整 startup.conf 模板

以下模板把 04-01 的完整参数表压缩成一份可直接改用的骨架，字段逐项含义见 04-01，命令示例见 04-03 ~ 04-06。**所有路径与段名需对照实际版本核验**：

```text
unix {
  nodaemon
  log /var/log/vpp/vpp.log
  full-coredump
  cli-listen /run/vpp/cli.sock
  exec /etc/vpp/startup.exec
}

api-trace {
  on
  nitems 5000
}

cpu {
  main-core 0
  corelist-workers 2,4,6
}

dpdk {
  dev 0000:08:00.0 { name GigabitEthernet0/8/0 }
  dev 0000:09:00.0 { name GigabitEthernet0/9/0 }
  uio-driver vfio-pci
  socket-mem 1024,1024
  no-multi-seg
}

buffers {
  buffers-per-numa 16384
  default data-size 2048
}

plugins {
  plugin dpdk_plugin.so { enable }
  plugin acl_plugin.so  { enable }
}

logging {
  default-log-level info
  default-syslog-log-level warn
}

stats {
  interval 5
}

socksvr {
  socket-name /run/vpp/api.sock
}
```

配套的 `/etc/vpp/startup.exec`（顺序不可颠倒，命令见 04-03 / 04-04）：

```text
set interface state GigabitEthernet0/8/0 up
set interface ip address GigabitEthernet0/8/0 10.0.0.1/24
set interface state GigabitEthernet0/9/0 up
set interface ip address GigabitEthernet0/9/0 10.1.0.1/24
ip route add 0.0.0.0/0 via 10.0.0.254
```

验证序列：

```bash
vppctl show version
vppctl show plugins
vppctl show interface addr
vppctl show hardware-interfaces
vppctl show ip fib
vppctl show logging
```

**模板使用的边界条件与选型判据**。上面的 startup.conf 模板是单机双网卡的参考骨架，直接套用前要过四道判据：其一，`cpu{}` 的核编号必须与本机实际隔离核一致，模板里的 `2,4,6` 只是示意，抄错编号会让 worker 与内核线程抢占同一核；其二，`socket-mem 1024,1024` 的两段值分别对应两个 NUMA 节点，单路服务器应只留一段、双路大流量场景应按网卡归属加大对应段；其三，`buffers-per-numa 16384` 与报文大小、worker 数共同决定内存占用，内存富余时宁大勿小——buffer 耗尽的代价（`show errors` 出现 `rx error no buffers`）远大于多占几 GB 大页；其四，`plugins{}` 显式 enable 清单是白名单语义，漏写一个插件就少一族命令，这是模板环境命令集合与第 5 节速查索引对不上时的第一检查点。多实例部署（见 03-06）时每个实例还要独立成套：`cli-listen`、`api-segment`、stats 段、大页分区逐项错开，模板任何一段都不能被两个实例共享。模板刻意未写 `heapsize`：主堆默认值在多数场景已够用，只有把大量路由、邻接或插件私有数据放进主堆时才需要显式放大，盲目写大值反而挤占留给 buffer 的大页，调整前先用 `show memory` 确认实际峰值（字段见 05-02、05-10）。满足判据后先在测试环境按上述验证序列跑通，再进入生产；模板中所有段名与参数仍需对照实际版本核验。

**按故障现象索引的命令组合**

第 2 节的错误对照表回答「单条命令查什么」，这里换一个维度：把命令**按执行顺序**组合成排查序列，每行对应一类现象，右列给出组合输出的判读要点——命令组合的价值在于交叉印证，两条命令的输出互相矛盾时，矛盾点往往就是根因所在（命令本身的语法与全集见 04-03 ~ 04-06，此处只给组合与判读）。

| 现象类 | 命令组合（按序执行） | 判读要点 |
|---|---|---|
| 接口不存在 / 起不来 | `show plugins` → `show hardware-interfaces` → `show logging` | 插件清单缺项→L1；硬件层无此设备→绑定问题；日志取 EAL 报错原文 |
| 接口 up 但不收包 | `show interface` → `show interface rx-placement` → `show threads` | 计数全零且队列未绑 worker→绑核缺失；绑了但分散不均→RSS/NUMA |
| 配置写入但不生效 | `show <对象表>` → `show interface features` | 表里有对象但 feature 未挂→绑定链断裂（L3） |
| 不通但无丢包计数 | `clear errors` → 复现 → `show errors` → `trace add` | 计数为零说明包根本没进对应节点，trace 看止步点 |
| 丢包计数持续增长 | `show errors` → `show buffers` → `show memory` | 原因含 no buffers→池耗尽；否则按 error 名回搜源码 |
| 性能骤降 | `show runtime` → `show threads` → `show interface rx-placement` | 比对 Clocks 占比最高节点；worker 漂核/队列重排是高频根因 |
| 重启后配置丢失 | `show logging` → 核对 `unix{ exec }` → `vppctl exec <file>` 手动重放 | 日志无 exec 记录→路径未配置；重放报错→脚本顺序/语法问题 |
| 控制面异常 | `show api clients` → `api-trace{ on }` 复现 → `show api trace` | clients 空→连接问题；trace 缺消息→控制器未下发；有消息无效果→VPP 侧 |

判读时坚持「矛盾即线索」：例如 `show interface` 有 Rx 计数而 `show errors` 全零，说明包进了 VPP 且没报错，问题在后续查表或服务路径，用 trace 追路径；反过来 `show ip fib` 有表项而 trace 显示报文止步在 `ip4-input` 之前，则说明报文根本没进入三层查找，应回头查接口模式与 VLAN。八类组合覆盖了本篇第 3 节 L1–L4 四层路径的典型落点，超出这八类的现象按图 04-08-01 的分层自定组合，组合内命令顺序不可颠倒——先清零再复现、先看状态再看计数，是这个顺序存在的理由。

**组合输出示例**（示例输出，具体格式需对照实际版本核验）：以「接口 up 但不收包」组合为例：

```text
vpp# show interface GigabitEthernet0/8/0
  State: up   rx packets 0  tx packets 1024  drops 0
vpp# show interface rx-placement
  GigabitEthernet0/8/0  rx-queue 0  worker 0
vpp# show threads
  thread 0  main   cpu 0
  thread 1  worker cpu 4   (vectors 0)
```

判读：接口管理状态 up、Tx 有计数（说明发侧路径通）、Rx 恒为零；`rx-placement` 显示队列 0 已绑 worker 0，看似正常，但 `show threads` 里该 worker 的 vectors 计数也是 0——「绑定了但没轮询到任何包」，矛盾点收窄到「网卡侧没有把包交给队列」：要么 `dpdk{}` 未声明该设备、实际接口是别的驱动，要么对端/交换机侧链路或 VLAN 不通。下一步应回 `show hardware-interfaces` 确认驱动与链路状态，而不是继续在 VPP 配置里找原因。这正是命令组合的意义：任何两条命令的输出都应能互相印证，印证不上的一侧就是下一步排查方向。

### 6. 版本差异

速查手册本身的时效性集中在下表五项：段名/字段、API 消息名、插件名、show 输出列、`exec` 错误行为，任何一项变化都会让本册的表与模板「看起来对、跑起来偏」；升级后把本表作为逐项复核清单，再决定哪些脚本与模板需要修订。

| 差异点 | 影响 |
|---|---|
| `startup.conf` 段名/字段 | `cpu{}` 的 `corelist-workers` 与 `workers`、`dpdk{}` 的 `dev` 语法、`socksvr{}` 名称均随版本调整 |
| CLI → API 消息名 | 带 `_v2`/`_v3` 后缀的消息替换旧消息，控制器升级需同步 |
| 插件名 | `.so` 文件名与默认加载集合变化，`plugins{}` 显式 enable 清单需复核 |
| `show` 输出列 | 报错字段与计数列名变化，自动化解析脚本需跟着改 |
| `exec` 错误处理 | 遇错是否继续执行的行为差异，可能影响"脚本执行完但配置不全" |

版本基准 VPP 23.06 / master；升级前后的配置兼容性核对流程见 08-05。

### 7. 常见误用与调试

1. **把 parse error 当成参数写错**。命令不存在多半是插件未加载或版本不匹配，先 `show plugins` / `show version`。
2. **只看命令返回值不看表项**。返回成功不等于生效，必须 `show ip fib` / `show bridge-domain` 等复核。
3. **忘了"绑定"这一步**。ACL、policer、NAT、feature 都需要把对象绑到接口或方向，对象存在≠流量经过。
4. **VRF/表 ID 串了**。多表环境下路由与接口不在同一张表是高频根因。
5. **不清零计数就排障**。累计值会掩盖当前问题，标准动作是 `clear errors` → 复现 → `show errors`。
6. **`exec` 脚本顺序错误或中途失败**。接口未建就配地址会整行失败，后续命令可能继续执行，导致"部分配置生效"的假象。
7. **`startup.conf` 改了没重启、或重启了但改错文件**。用 `show logging` 与启动日志确认实际加载的配置文件路径。
8. **照抄模板不核验版本**。模板里的段名、插件名、API 消息名都可能与你的版本不符，凡「需对照实际版本核验」处必须核对。
9. **把 08 全册的方法论当命令字典用**。本篇是索引；遇到需要"从现象一步步推到根因"的场景，转 08-03 / 08-04。
