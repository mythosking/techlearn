# 高性能用户态 VPN 数据面方案讨论

> **文档性质**：方案讨论记录，持续迭代。DESIGN-01 完成需求澄清与候选方案列举；DESIGN-02 澄清多线程难度与 wireguard-openbsd 出处；DESIGN-03 详解四个并发点、解释 WireGuard 互通概念、补充 DPDK 相关组合方案并横向对比；DESIGN-04 列出收敛路线所需的五个关键问题；DESIGN-05 根据用户已确认的四项约束完成方案收敛，给出推荐路线与落地拆解；DESIGN-06 讨论"把 wireguard-linux 改造成不依赖内核的程序"的可行性，拆解四层依赖并给出取舍结论；DESIGN-07 讨论控制面（密钥分发、用户管理）的开源参考项目、许可证核实结果与关键设计原则；DESIGN-08 修正一处未经确认的假设——把 DESIGN-07 中"产品形态为网关"降级为待确认项，补充网关与 mesh 的拓扑差异、澄清问题，以及 wg-easy 与 Headscale 的功能对照。
> **需求**：用户态加解密、高性能、目标达到网口线速，考虑 DPDK 或其他开源框架（如 VPP）。
> **事实来源**：FD.io VPP 26.02 特性列表与 26.06 发布说明、VPP Gerrit 变更、WireGuard 官方资料。所有成熟度标注均引自官方文档，未做主观拔高。

## DESIGN-01 需求澄清与候选方案

### 1. 核心判断：线速是可达的，但瓶颈不在收包

先给结论。线速目标可达，但成败不取决于"选 DPDK 还是 VPP"，而取决于三个更底层的决策：加密怎么加速、协议兼容性要求、报文如何进出用户态。

一个容易被忽视的事实是：**加密才是瓶颈，报文 I/O 反而不是**。DPDK / VPP 的轮询模式收包做到百万 pps 是常规能力，但每个包都要过一遍 ChaCha20-Poly1305 或 AES-GCM（上下文初始化、批量提交、轮询完成、认证标签封装），CPU 很快被打满。因此方案设计的重心应放在加密流水线，而非收包框架。

### 2. 先校准"线速"这个目标

线速不是一个数字，而是速率与包长的组合，两者共同决定难度量级。

| 端口速率 | 64B 小包 | 1500B 大包 |
|---|---|---|
| 10GbE | 14.88 Mpps | 0.81 Mpps |
| 100GbE | 148.8 Mpps | 8.1 Mpps |

加密开销按包计，所以小包线速比大包线速难一到两个数量级。必须先明确目标属于哪一档：1500B 大包 10G 线速，用 AES-NI 软件加密就有机会；64B 小包 100G 线速，纯软件基本无解，必须上硬件卸载。

**决策 1：加密靠什么加速**

软件指令集路线（AES-NI / VAES）零额外成本，AES-GCM 在大包场景吞吐很高。Intel 的 IPSec-MB、ISA-L_crypto 是多缓冲实现，能把多个包的加密打包并行，吞吐显著高于逐个调用 OpenSSL；VPP 的 ipsecmb 引擎正是基于它。硬件卸载路线（Intel QAT / DPU / 智能网卡）在小包线速或 100G 以上场景几乎必需，DPDK 的 rte_cryptodev 抽象层直接支持 QAT 轮询模式驱动，代价是硬件成本与驱动适配。还有个隐藏变量：WireGuard 用的 ChaCha20-Poly1305 在无 AES 加速的 ARM 上比 AES-GCM 快，但在有 VAES 的 x86 上反而吃亏。

**决策 2：要不要兼容标准协议**

这是最大的分叉点。若要与现成 WireGuard / IPsec 客户端互通，就必须照协议实现；若两端都是自有设备，私有协议能省掉大量兼容性包袱（抗重放窗口、握手状态机、MTU 探测等），性能设计空间大得多。

**决策 3：报文怎么进出用户态**

DPDK 独占网卡是轮询模式、零拷贝、无中断，性能天花板最高，但网卡被独占，机器上其他网络栈用不了。AF_XDP 与内核共存，性能略低但运维友好。混合模式——控制面走内核 socket、数据面走 DPDK——是最常见的工程折中。

### 4. 候选方案 A：VPP + IPsec（生产级路径）

这是成熟度最高的路径。VPP 的 IPsec 标注为 production 且支持多线程，源码在 src/vnet/ipsec；三种加密引擎（Intel IPSecMB / OpenSSL / 原生实现）全部是 production，均支持 GCM 与 CBC；BFD、ACL、FIB 等配套能力齐全，FD.io 每季度 CSIT 报告提供公开性能基准，便于对照验证。

- 优点：成熟度最高、开发量最小、多线程可扩展、有公开基准数据
- 缺点：协议是 IPsec ESP 而非 WireGuard；IKEv2 插件仍为 experimental，密钥协商这一层需要额外投入或外接 strongSwan
- 适用：能接受 IPsec、要尽快上线、追求稳妥线速——这是当前的首选生产路径

### 5. 候选方案 B：VPP + WireGuard（协议正确但未成熟）

VPP 从 22.02 起就有 src/plugins/wireguard，基于 wireguard-openbsd 实现。但成熟度标注为 development，特性列表中仅列 API 与 CLI 支持，未标注 MULTITHREAD——单线程是线速的硬伤。26.06 的 Gerrit 上仍在修异步加密的上下文生命周期问题，说明正处于活跃开发但未到生产状态。此外 26.06 发布说明里 wireguard_peer_add 已被标记为 deprecated，改为 v2，意味着跟随上游要承担 API 变更成本。

- 优点：标准 WireGuard 互操作，ChaCha20-Poly1305 软件性能好，可直接复用 VPP 转发框架
- 缺点：单线程限制线速；成熟度不足；异步加密仍在完善；上游 API 仍在演进
- 适用：WireGuard 互通是硬需求且愿意投入力量推动上游成熟，或目标速率不高（如 10G 大包）时先做 POC 验证

### 6. 候选方案 C：DPDK 自研数据面（性能天花板）

用 DPDK 加 rte_cryptodev（软件 AES-NI 引擎或 QAT 硬件）与 ISA-L_crypto / IPSec-MB，从零搭建加密隧道数据面，控制面用 Go 或 Python 单独实现。

- 优点：完全掌控流水线，可针对包长与会话模型极致优化；QAT 卸载下小包线速才有可能
- 缺点：需自行实现会话表、抗重放、PMTUD、分片重组、keepalive、多核会话亲和、热升级等，工作量是 A / B 的数倍
- 适用：协议私有或有特殊性能要求、团队有足够 C 与 DPDK 积累、且有硬件预算

### 7. 补充方案 D：AF_XDP + 用户态加密

如果网卡不能被独占是硬约束，AF_XDP 是折中方案——保留内核协议栈，数据面在用户态，运维简单，适合云原生与多租户环境。VPP 有 AF_XDP 驱动（experimental，Linux 5.4 以上）。性能低于纯 DPDK，但部署代价小得多。

### 8. 核实的关键事实（官方口径）

下表摘录 VPP 26.02 特性列表的成熟度标注，是方案选型的硬依据。

| 特性 | 成熟度 | 支持 | 源码路径 |
|---|---|---|---|
| Wireguard protocol | development | API CLI | src/plugins/wireguard |
| IP Security | production | API CLI MULTITHREAD | src/vnet/ipsec |
| IPSec crypto engine · Intel IPSecMB | production | API CLI MULTITHREAD | src/crypto_engines/ipsecmb |
| IPSec crypto engine · OpenSSL | production | API CLI MULTITHREAD | src/crypto_engines/openssl |
| IPSec crypto engine · native | production | API CLI MULTITHREAD | src/crypto_engines/native |
| ikev2 plugin | experimental | API CLI MULTITHREAD | src/plugins/ikev2 |
| AF_XDP device driver | experimental | API CLI STATS MULTITHREAD | src/plugins/af_xdp |

需要特别指出：WireGuard 插件标注为 development 且未列 MULTITHREAD，这与 IPsec 的 production 加 MULTITHREAD 形成鲜明对比。所谓"用 VPP 做到线速"和"用 VPP 跑 WireGuard 做到线速"是两件难度完全不同的事。

### 9. 当前建议（待关键问题回答后收敛）

建议先确认 WireGuard 互通是否为硬需求，再按下面三条路径分流。

- 不是硬需求：选方案 A（VPP + IPsec），用 IPSecMB 引擎，先拿大包 10G / 25G 线速跑通，再评估是否上 QAT。风险最低、见效最快。
- 是硬需求且目标不超过 10G：选方案 B 做 POC，验证单线程是否够用，同时跟踪上游多线程进展。
- 是硬需求且目标 25G 以上小包：选方案 C，且必须配 QAT 或 DPU，纯软件加密做不到。

### 10. 待用户确认的问题

1. 协议：WireGuard 互通是硬需求，还是只要"用户态加密隧道"即可？对端是自有设备还是标准客户端？
2. 速率与包长：目标多少 G？典型包长是 1500B 大包还是 IMIX / 小包为主？
3. 硬件：能否接受 QAT 卡或 DPU？CPU 是什么代次（有无 VAES / AVX-512）？
4. 部署：物理机独占网卡可以吗，还是要与现有业务共用？
5. 团队与周期：几个人、多久要出可用版本？

这几点确定后，方案可收敛到一条具体技术路线，包括模块划分、加密流水线设计、性能验证方法，并可先做一份基准测试方案来量化"到底差多少才叫线速"。

## DESIGN-02 两点澄清：多线程难度与 wireguard-openbsd 出处

### 1. "单线程改多线程"难在哪

先纠正一个可能的误解：它不是不能开多线程，而是协议状态的多线程安全尚未做完。难度属于中等偏上的工程问题，不是理论难题——IPsec 在同一套 VPP 框架里就做到了 production 加 MULTITHREAD，证明框架本身支持多线程。难点在 WireGuard 协议有一批共享可变状态，多线程下会相互冲突。

下图给出从共享状态到改造点的完整逻辑。

图中节点速览（便于在不渲染框内文字的预览器中阅读）：起点「共享状态 会话密钥 握手 计数器」被「多个 worker 同时读写」，引发「竞争与顺序 重放窗口须递增」，解决办法是「加锁或无锁化改造」，具体落到四个改造点——「会话表按 worker 分片」「重放窗口原子位图」「握手单线程集中处理」「加密上下文跨 worker 生命周期」。

逐点展开。其一，会话表按 worker 分片并配合 RSS 保序：WireGuard 是 peer 粒度的会话，同一 peer 的包必须落到同一 worker 才能正确维护序号，否则要额外的会话分片与哈希规则。其二，抗重放窗口无锁化：WireGuard 用滑动位图记录收到过的包序号并要求严格递增，并发更新必须用原子操作或无锁结构，OpenBSD 实现里用了 SMR 安全内存回收，直接加锁会把性能优势吃掉。其三，握手状态机集中在主线程做，数据线程只读会话密钥快照，需要读写分离与引用计数。其四，加密上下文生命周期，这正是 26.06 Gerrit 补丁在修的问题——异步加密时一个包把 crypto context 指针排进队列跨过 worker barrier，销毁线程可能在加密完成前就释放上下文，导致 use-after-free；补丁给每个在途包加引用计数，等最后一个完成再回收。

所以准确说法是：多线程在工程上完全可做，但需要把协议状态逐处改造成并发安全，是若干个月的工作量且要处理大量边界条件。VPP 官方把插件标为 development、特性表里不列 MULTITHREAD，正是承认这项工作尚未收尾。

### 2. wireguard-openbsd 是什么，为什么官方组织里找不到

它确实存在，是 Jason Donenfeld（WireGuard 作者）维护的 OpenBSD 内核态实现，托管在 `git.zx2c4.com/wireguard-openbsd`，主仓库最后一次提交是 2021-10-26，已停更——因为 2020 年它就被合并进 OpenBSD 内核主线，独立仓库使命完成。

在 GitHub 的 WireGuard 组织里找不到它是因为托管位置不同：GitHub 组织是镜像（每个仓库都标注 Mirror only），官方源在 `git.zx2c4.com`；而 wireguard-openbsd 只在 zx2c4 的 Git 服务上，没有对应的 GitHub 镜像。

三个官方实现是同协议、不同平台的关系。

| 实现 | 平台与运行态 | 现状 |
|---|---|---|
| wireguard-linux | Linux 内核态 | 5.6 起进内核主线 |
| wireguard-openbsd | OpenBSD 内核态 | 6.6 起进内核主线，独立仓库停更于 2021 |
| wireguard-go | 跨平台用户态 | 官方持续维护，macOS/BSD/容器等平台主力 |

VPP 为什么选它做基座而不是 wireguard-linux：wireguard-openbsd 是内核态实现里结构最清晰、模块化最好、许可证最宽松的一份，没有 Linux 内核那套复杂依赖（tasklet、netlink、RCU、workqueue），更容易移植到 VPP 这种用户态数据面框架。Linux 版依赖内核设施太重，go 版是用户态进程模型，都不适合直接嵌进 VPP。这是取 kernel 实现之魂、弃 kernel 框架之壳的选择。

需要注意时效性：VPP 当作基座的代码停留在 2021 年，所以其插件加密仍用 OpenSSL（curve25519、chachapoly1305），而非更高效的实现；官方改进清单第一条就是 Use all benefits of VPP-engine，这也解释了它离线速还有距离。

## DESIGN-03 四个并发点详解，以及"互通"到底指什么

### 1. 先回答"WireGuard 互通"是什么

这是选型里最大的分叉点，必须先定义清楚，否则后面所有讨论都会错位。

所谓**WireGuard 互通**，指的是你实现的 VPN 能够与**标准 WireGuard 对端**直接建立隧道并转发流量，对端不需要安装你的专有客户端、不需要改配置、也不知道你用的是哪套代码。这里的"标准对端"包括 Linux 的 wireguard.ko 加 wg(8)、Windows 的 wireguard-nt、macOS/iOS/Android 官方 App、wireguard-go，以及 OpenBSD 内核版等任意遵守 WireGuard 协议的实现。

互通是**协议级兼容**，不是配置文件长得像。至少需要逐字节一致地实现下面这些要素：Noise_IK 四消息握手（类型 1/2/3/4 的字段布局与时序）、Curve25519 密钥协商与 BLAKE2s 密钥派生、ChaCha20-Poly1305 的数据包封装与 nonce 用法、按 peer 的传输序号与抗重放滑动窗口、cookie 质询与速率限制、persistent keepalive、AllowedIPs 的路由与访问控制语义，以及 MTU 与 DF 分片处理。任何一处字段或时序不对，表现为握手失败或静默丢包。

WireGuard 在这里有个很麻烦的特性：**它是静默协议**，收到认证失败的包不回错误响应，只是丢弃。这给互通调试带来很大困难——你只看到"不通"，却拿不到对端为什么拒收的显式反馈，只能靠抓包逐字段比对。因此"互通"不是顺带就能满足的属性，而是一笔持续的兼容性测试投入，且要跟随上游实现的行为演进。

互通程度可以分成三档，对协议设计自由度的影响截然不同。

图中节点速览（便于在不渲染框内文字的预览器中阅读）：三档互通程度分别是「完全互通 任意标准客户端直连」「有限互通 特定实现或版本」「不互通 两端都是自有设备」。前两档分别要求「逐字节实现 Noise_IK 与消息格式」和「绑定 ChaCha20-Poly1305 与抗重放窗口」，都导致「性能设计空间受限」；第三档则「可自选 AEAD 批量加密与极简握手」，因此「性能设计空间开放」。

| 互通档位 | 对端要求 | 协议自由度 | 兼容性成本 | 典型场景 |
|---|---|---|---|---|
| 完全互通 | 任意标准 WireGuard 实现 | 极低，逐字节遵循规范 | 高，需持续回归测试 | 远程办公客户端、跨组织互联 |
| 有限互通 | 指定实现或指定版本 | 低，可裁剪边角特性 | 中，需锁定版本 | 与固定合作方对接 |
| 不互通 | 两端均为自有设备 | 高，可自定义 AEAD 与握手 | 无 | 数据中心站点间加密网关 |

为什么互通会直接影响线速目标：WireGuard 把对称加密固定为 ChaCha20-Poly1305，你不能用 AES-GCM 加上 VAES 或 QAT 的成熟批量路径（绝大多数 QAT 配置也不提供 ChaCha20-Poly1305 卸载）。而如果两端都是自有设备，你可以改用 AES-GCM，直接使用 Intel IPSec-MB 或 QAT 的多缓冲能力，握手也可以简化——这部分收益往往比选 DPDK 还是 VPP 更大。

### 2. 四个并发点，逐点说清楚

先给一个总纲：这四点不是四个孤立的 bug，而是一条因果链。**点 1 决定一个包落到哪个 worker；点 2 在这个 worker 内做序号合法性检查；点 3 产生前两者要用的会话密钥；点 4 保证这些密钥在异步加密期间不会被提前回收。**任一处失守，表面现象分别是丢包、错包、密钥不一致和崩溃。

**点 1：会话表分片与 RSS 保序**

- 问题本质：WireGuard 的会话是 peer 粒度的，包含公钥、当前 endpoint、收发会话密钥、最近握手时间、cookie、AllowedIPs 等字段。多个 worker 同时读写会产生竞争；同时同一 peer 的传输序号必须按递增顺序处理，乱序到达会被抗重放窗口当成重放丢弃。
- 为什么难：网卡的 RSS 默认按五元组哈希，同一个 peer 的不同 UDP 源端口会把包散到不同 worker，天然破坏序号局部性。若改为按 peer 固定分片，少数大流量 peer 会成为热点，无法横向扩展；若做动态迁移，又要处理正在飞行中的包和旧 worker 上的未完成状态。
- 失守后果：合法包被误判为重放而丢弃；endpoint roaming 的更新丢失后流量进入黑洞；密钥轮换后部分 worker 仍用旧密钥发包。
- 常见解法：按 peer 公钥哈希固定归属 lcore，用自定义 RSS key 或软件二级分发保证同一 peer 落到同一 worker；或者每个 worker 持有只读会话快照，更新由主线程通过 RCU 发布。
- 代价：热点 peer 吞吐受单核上限约束；快照发布存在短暂不一致窗口，需要 grace period。

**点 2：抗重放窗口原子位图**

- 问题本质：WireGuard 用一个滑动位图记录已接收的传输序号（常见实现为 64 位或更大窗口），拒绝重复序号，并在收到更大序号时把窗口右移。
- 为什么难：一次接收包含"检查序号是否在窗口内 → 置位 → 必要时右移窗口"三个步骤，这三步必须对其他并发接收者表现为一个原子操作。两个 worker 同时处理同一 peer 的不同序号时，可能出现两个包都通过检查、或后到的高序号把先到包的记录右移出窗口的竞态（TOCTOU）。
- 失守后果：轻则误丢合法包造成吞吐骤降，重则放过真正的重放包，构成安全漏洞——这是四个点里唯一直接破坏安全属性的。
- 常见解法：用 CAS 循环实现原子位图；或每个 worker 维护本地窗口并周期性合并；或干脆把点 1 做彻底，保证同一 peer 只落一个 worker，从而把这个问题降维成单线程问题。
- 代价：原子竞争激烈时会退化为串行；无锁实现要配合 SMR 或 RCU 安全回收，代码复杂度高；直接加互斥锁则吃掉批量加密带来的性能收益。

**点 3：握手集中处理**

- 问题本质：Noise_IK 握手涉及临时密钥、cookie 质询、速率限制，成功一次会产生或轮换会话密钥；握手消息和数据消息共用同一个 UDP socket 与端口。
- 为什么难：如果多个 worker 都能处理同一 peer 的握手，会争抢状态机，产生重复响应或两个不同的会话密钥；握手还包含 Curve25519 椭圆曲线运算，放在数据线程会阻塞线速路径。
- 失守后果：出现"双主密钥"，对端用一个密钥加密而本端用另一个解密，隧道静默不通；握手风暴期间数据面吞吐断崖式下降。
- 常见解法：把握手固定到主 lcore 或专用控制线程，握手完成后把新会话密钥以只读快照加 RCU 的方式发布给各数据 worker；数据面只做查表加密，不做状态机推进。
- 代价：握手吞吐受单核限制（握手频率通常很低，可接受）；密钥切换瞬间要保留过渡期，处理仍在途的旧密钥数据包。

**点 4：加密上下文跨 worker 生命周期**

- 问题本质：在异步加密模式下（DPDK 的 rte_cryptodev 或 VPP 的异步 engine），一个包把 crypto context 指针排入队列，可能跨过 worker 边界，完成回调在另一个线程执行。
- 为什么难：如果密钥轮换线程或 peer 删除线程在加密完成之前释放了这个 context，回调拿到的就是悬空指针，触发 use-after-free。这正是 VPP 26.06 Gerrit 上还在修的问题——它说明这项改造是活跃开发中，尚未收敛为稳定设计。
- 失守后果：进程崩溃或内存破坏，属于 P0 级稳定性问题，比性能不达标严重得多。
- 常见解法：给每个在途包持有的 context 做引用计数，入队时加一、完成回调减一、归零才回收；或者用 RCU grace period 延迟回收，确保所有在途访问结束后再释放。
- 代价：每包原子引用计数有开销，但可以用批量 enqueue/dequeue 摊薄；RCU 延迟回收会短暂增加内存占用。

把四点的难度放在一起看：**点 1 和点 2 是性能与正确性权衡，点 3 是架构取舍，点 4 是稳定性红线**。难点不在任何一个单独点，而在于四点互相牵制——比如把点 1 做成"同一 peer 固定 worker"虽然能简化点 2，却引入了热点 peer 无法扩展的新问题；点 3 的快照发布又直接决定点 4 的回收时机。这也是为什么"改多线程"是若干人月的工程，而不是打个补丁。

### 3. 把新方案补进来，并逐项对比存在的问题

在原有 A/B/C/D 四个方案之外，补上你问到的两个组合，以及真正可落地的第三条路。

**方案 E：DPDK + wireguard-linux（内核模块）**

严格说这不是一个可以"组合"的方案，有两种理解方式，都不成立。第一种是把 DPDK 收到的包注入内核 wireguard.ko（经 KNI、virtio-user、AF_XDP 或 tap），包一旦进内核就回到 skb 与内核协议栈路径，等于绕回原点——你为了绕开内核瓶颈才用 DPDK，结果又把包送回内核。第二种是把 wireguard-linux 源码搬进用户态，但它深度依赖 net_device、netlink/RTNL、RCU、workqueue、socket 和内核 crypto API，适配层工作量约等于重写。

还有一个关键澄清：**wireguard-linux 本身已经是多核设计**（多队列 RSS 加 padata 并行加解密），"用 DPDK 让它多线程"是个伪命题。内核版那四个并发点是在内核调度模型下解决的，用户态拿不到这些现成成果。

**方案 F：DPDK + wireguard-go**

wireguard-go 官方定位是独立 Go 程序：`wireguard-go wg0` 创建 TUN 接口，再用 wg(8) 配置。它不是可嵌入 DPDK 进程的数据面库，官方主页也明确说 Linux 上应该用内核模块，因为"faster and better integrated into the OS"。若通过 TUN/IPC 对接，数据路径是 DPDK 收包 → 写 TUN → wireguard-go → 从 TUN 读回 → DPDK 发包，两次拷贝加两次内核边界加一次 Go runtime 调度，性能优势基本抵消。若试图把 Go 代码嵌进 DPDK，则要重写网络 I/O、定时器与协程调度为 lcore 模型，并背上 GC 与零拷贝模型冲突的包袱。此外 wireguard-go 内部虽然解决了那四个并发点，但那是它自己进程内的状态，DPDK 数据面拿不到，等于两套状态机并存。

**方案 G：DPDK + rte_cryptodev + 自研 WireGuard 数据面**

这是唯一能同时拿到 DPDK 高 I/O、WireGuard 互通和批量加密收益的路径：数据面用 C 或 Rust 实现 WireGuard 状态机，加密走 `rte_cryptodev` 的 chacha20-poly1305 multi-buffer PMD（或 QAT），控制面可用 Go 或 C。参考实现建议看 Cloudflare 的 Boringtun——它是 Rust 库形态，包进包出而不是绑定 TUN，比 wireguard-go 更适合作为数据面蓝本，不过其维护活跃度要自行核实。

### 4. 本轮结论

直接回答你问的两个组合：**DPDK + wireguard-linux 不能解决上述四个并发点，DPDK + wireguard-go 也不能**。前者是内核模块，其并发改造成果被困在内核态；后者是 TUN 进程模型，其并发改造成果困在另一个进程里。两者与 DPDK 对接都要引入边界，而边界开销正是线速方案要极力避免的。

能同时满足"用户态加解密、WireGuard 互通、逼近线速"的只有方案 G，但它本质上是**协议栈自研**，不是框架拼装。如果 WireGuard 互通不是硬需求，方案 A（VPP + IPsec）仍是投入产出比最高的选择。

### 3. 三条候选路线

**路线 1：方案 B 原样 POC（最快验证）**

直接用 VPP 26.x 的 src/plugins/wireguard，网卡用 VPP 的 DPDK 驱动独占。互通由现成插件保证，不写一行协议代码，一两周就能跑起来。用它测出真实流量模型下的单 worker 吞吐基线——这是后面所有决策的数据基础。

- 优点：投入最小，互通风险最低，能最快拿到"到底够不够用"的答案
- 缺点：单线程限制吞吐上限；插件标为 development，API 仍在演进（wireguard_peer_add 已 deprecated 改 v2）；异步加密上下文问题仍在 Gerrit 上修
- 判断标准：如果基线吞吐满足业务需要，到此为止就是最优解，不必自研

**路线 2：方案 H——VPP + WireGuard 插件多线程改造（推荐路线）**

在路线 1 的基础上，把 VPP WireGuard 插件的四个并发点逐项改造成多线程安全，并把加密接入 VPP 的 crypto engine。这是一条介于 B 与 G 之间的中间路线：互通由现成插件保证、网卡独占由 VPP 的 DPDK 驱动保证、转发框架用 VPP 现成能力，只针对真正卡脖子的四个点动刀。

选它而不是直接上 G 的核心理由：WireGuard 协议栈从零实现是 6 到 12 人月的高风险投入，而互通是硬需求意味着这笔投入躲不掉——但 VPP 插件已经把协议栈实现好了，你只需要补上它的多线程短板。官方改进清单第一条就是 Use all benefits of VPP-engine，说明接入 VPP 加密引擎本身就是上游既定方向，改造工作与上游演进同向。

**路线 3：方案 G——DPDK + 自研 WireGuard 数据面（性能天花板）**

数据面用 C 或 Rust 完全自研，控制面用 Go 或 C，加密走 rte_cryptodev 的 chacha20-poly1305 multi-buffer PMD。

- 优点：完全掌控流水线，性能上限最高，不受 VPP 插件成熟度与 API 变更牵制
- 缺点：协议栈自研 6 到 12 人月，互通回归测试持续投入，四个并发点全部自己解决
- 适用：路线 2 改造后仍不满足吞吐要求，或团队有充足 C/Rust 与 DPDK 积累且周期宽松

**推荐顺序**：路线 1 先跑基线 → 达标则产品化 B 并收工 → 不达标则启动路线 2 → 路线 2 仍不够再评估路线 3。这是用最小投入换取最多信息的顺序，避免一上来就背 6 到 12 人月的协议栈自研包袱。

模块划分与来源如下，尽可能复用现成能力，只自研必要部分。

| 模块 | 职责 | 来源 | 关键约束 |
|---|---|---|---|
| NIC I/O | 独占网卡，多队列收包 | VPP 的 DPDK 驱动，现成 | 需按 peer 维度控制分发，而非默认五元组哈希 |
| 转发框架 | 多 worker 运行到完成 | VPP 现成 | 不改动，复用其 MULTITHREAD 能力 |
| WireGuard 数据面 | 封装解封装、序号、抗重放 | VPP 插件改造 | 四个并发点逐项改，是主要工作量 |
| 加密引擎 | ChaCha20-Poly1305 批量加密 | VPP crypto engine | 接入 VPP engine 而非插件直调 OpenSSL |
| 控制面 | Noise_IK 握手、密钥轮换、cookie | VPP 插件改造 | 握手集中主线程，密钥快照 RCU 发布 |
| 互通回归 | 与标准实现交叉验证 | 自建测试矩阵 | 静默协议，必须抓包比对 |

四个并发点在 VPP 框架下的具体改法，与 DESIGN-03 的通用分析对应到本路线。

| 并发点 | 在 VPP 下的改造方式 | 验收判据 |
|---|---|---|
| 会话表分片与 RSS 保序 | 用自定义 RSS key 或软件二级分发，让同一 peer 固定落同一 worker；大 peer 热点用多队列加序号重组补偿 | 压测中无因乱序导致的合法包丢弃 |
| 抗重放窗口原子位图 | 位图改为 CAS 原子更新；利用上一点的单 worker 归属降维处理 | 重放包全部拒绝，正常乱序窗内包不误丢 |
| 握手集中处理 | 握手固定主线程，生成的会话密钥以只读快照经 RCU 发布给数据 worker | 密钥轮换窗口内无双主密钥，隧道不静默中断 |
| 加密上下文生命周期 | 在途包对 context 做引用计数，入队加一、完成减一、归零回收；跟踪上游 Gerrit 补丁 | 长时间压力测试无 use-after-free，无崩溃 |

需要提醒的是，第四点在 VPP 26.06 的 Gerrit 上仍在修复中，说明上游自己也没收尾。路线 2 的排期必须把"跟踪或自行合入该补丁"算进去，不能假设上游已稳定。

### 5. "不追求线速"也要有可验收的目标

"不追求完全线速"不等于没有指标，否则项目无法验收。建议用真实流量模型定义基线，而不是拿 64B 与 1500B 两个极端值自欺欺人。

| 步骤 | 做法 | 产出 |
|---|---|---|
| 定义流量模型 | 记录实际业务的包长分布、peer 数、并发流数 | 一份 IMIX 或自定义流量画像 |
| 测无加密基线 | 同样框架跑明文转发，测吞吐上限 | 框架本身的天花板 |
| 测插件现状 | 跑标准 VPP WireGuard 插件，单 worker 吞吐 | 路线 1 的基线数据 |
| 算加密成本 | 基线减插件吞吐，得到加密净开销 | 判断优化重点 |
| 设定目标 | 例如基线 10G、插件 5G，则目标定为改造后 8G | 可验收的数字 |

有了这组数据，"够不够用"才有客观答案。建议在路线 1 的 POC 阶段就把它做出来，这是整个项目性价比最高的一步——如果单线程已经够用，路线 2 和 3 都可以不做。

### 6. 风险清单

| 风险 | 表现 | 缓解措施 |
|---|---|---|
| 上游 API 变更 | wireguard_peer_add 已 deprecated 改 v2，跟随上游有改动成本 | 锁定一个 VPP 版本，在插件与业务间加适配层隔离变更 |
| 异步加密上下文缺陷 | 密钥轮换或 peer 删除时崩溃 | 跟踪 Gerrit 47382，必要时自行合入补丁并回归 |
| 互通静默失败 | 握手失败或收包丢弃但无错误反馈 | 建立标准对端回归矩阵：wg、wireguard-nt、官方 App、wireguard-go 逐项交叉测试 |
| 加密引擎落后 | 插件仍直调 OpenSSL 的 curve25519 与 chachapoly | 按官方改进清单接入 VPP engine，用批量能力摊薄每包开销 |
| 热点 peer 无法扩展 | 单 peer 流量大时固定 worker 成为瓶颈 | 评估多隧道分流，或为热点 peer 做专门的序号重组 |

### 7. 下一步建议

按下面的顺序推进，每一步都有明确的继续或停止判据。

1. 用一到两周搭路线 1 的 POC，按第 5 节方法测出单 worker 吞吐基线，同时建立互通回归矩阵。
2. 基线达标：产品化方案 B，只保留必要的稳定性补丁，项目到此收敛，不做多线程改造。
3. 基线不达标：启动路线 2，按第 4 节的模块划分和四点改造表排期，并把上游补丁跟踪列为独立任务。
4. 路线 2 改造后仍不达标：再评估路线 3 的 6 到 12 人月投入是否值得。

需要补充的输入只有一个：业务的真实流量模型（典型包长与并发规模）。没有它，第 5 节的目标无法量化，"够不够用"也就无从判断。

## DESIGN-06 把 wireguard-linux 改造成用户态程序：可行性与取舍

本节讨论一个更深的问题：既然方案 E 的问题是 wireguard-linux 依赖内核，那么能不能把它改造成不依赖内核的程序，把依赖的数据结构都换成 DPDK 的对应物，从而既拿到内核版的成熟协议实现，又拿到 DPDK 的用户态高性能？

### 1. 结论先行

技术上可行，没有理论障碍。但"把依赖的数据结构换成 DPDK 数据结构"是整件事里**最容易的那部分，不是难点**。真正的工作量在于这些数据结构背后承载的内核机制——它们没有 DPDK 对应物，只能重建。

换句话说，如果预期的工作是"skb 换成 mbuf、spinlock 换成 rte_spinlock、hlist 换成 rte_hash"，那就严重低估了。这些替换大概只占两成，剩下八成是在用 DPDK 从零造一个迷你内核网络栈。

### 2. 四层依赖，只有前两层能"替换"

wireguard-linux 的内核依赖可以拆成四层，处理方式完全不同。

:::figure id=DESIGN-06-01 | name=wireguard-linux 用户态移植的四层依赖 | dir=TD
node l1 "第1层 纯协议与算法" green
node l2 "第2层 数据结构" blue
node l3 "第3层 内核机制 真正难点" red
node l4 "第4层 运行环境" gray
node u1 "Noise_IK Curve25519 ChaCha20 消息格式" teal
node u2 "skb mbuf hlist rte_hash trie rte_lpm" teal
node u3 "net_device socket netns timer RCU netlink" amber
node u4 "procfs sysfs 模块参数 initcall" amber
edge l1 -> u1
edge l2 -> u2
edge l3 -> u3
edge l4 -> u4
:::

图中节点速览（便于在不渲染框内文字的预览器中阅读）：依赖分四层——「第1层 纯协议与算法」对应「Noise_IK Curve25519 ChaCha20 消息格式」，处理方式是直接复用；「第2层 数据结构」对应「skb mbuf hlist rte_hash trie rte_lpm」，可替换但有陷阱；「第3层 内核机制 真正难点」对应「net_device socket netns timer RCU netlink」，必须重建；「第4层 运行环境」对应「procfs sysfs 模块参数 initcall」，丢弃重做。核心判断是难点不在换数据结构，而在为第 3 层重建一套用户态网络栈环境。

| 层级 | 内容 | 处理方式 | 工作量占比（估计） |
|---|---|---|---|
| 第 1 层 · 纯协议与算法 | Noise_IK 状态机、Curve25519、ChaCha20-Poly1305、BLAKE2s、消息格式 | 直接复用 | 小 |
| 第 2 层 · 数据结构 | skb、hlist、allowedips trie、padata、各类锁 | 可替换，但非一对一 | 中 |
| 第 3 层 · 内核机制 | net_device、UDP socket、netns、timer、workqueue、RCU、netlink、GSO/GRO | 无对应物，必须重建 | 主要 |
| 第 4 层 · 运行环境 | procfs/sysfs/debugfs、模块参数、Kconfig、initcall、内核统计 | 丢弃重做 | 小 |

### 3. 第 1 层：可以直接拿的部分

`noise-protocol.c` 的 Noise_IK 状态机、`crypto/` 目录下的 Curve25519、ChaCha20-Poly1305 与 BLAKE2s 实现、`messages.h` 的消息布局，这些是纯协议逻辑，与内核运行机制无关。WireGuard 代码量本身就不大，约四千行，这一层是它的精华，也是经过安全审计的部分。

这也是整件事里唯一"拿来就能用"的部分。但要注意，协议逻辑代码虽小，它承载的边界条件却很多——漫游、cookie、密钥轮换时序、MTU 处理，这些都不写在数据结构里，而是散落在状态机的分支中。

### 4. 第 2 层：能替换，但不是一对一映射

这一层最容易低估，逐项说明替换陷阱。

| 内核数据结构 | DPDK 对应物 | 陷阱 |
|---|---|---|
| `skb` | `rte_mbuf` | 表面对应，但内核版大量使用 `pskb_may_pull`、`skb_header_pointer`、`skb_put` 这套辅助函数，DPDK 没有等价物；必须先自建一套包头操作库才能开始移植 |
| `allowedips` trie | `rte_lpm` / `rte_lpm6` | WireGuard 是 v4/v6 混合前缀树且叶子关联 peer；DPDK 两张表分开，还要额外维护"按 peer 反向删除"的索引，这是适配层而非替换 |
| `padata` 并行队列 | `rte_ring` + lcore | 反而更自然，但 padata 的顺序语义要自己补回来 |
| `spinlock_t` | `rte_spinlock` | 语法替换容易；内核单核上 spinlock 几乎免费，DPDK 多 worker 下会真实竞争，必须重新设计锁粒度 |

### 5. 第 3 层：真正的墙

这一层没有"DPDK 数据结构"可以换，只能重新设计。

`socket.c` 依赖 UDP socket 加 GSO/GRO 卸载。DPDK 下要从以太网帧开始，自己解析 IP 与 UDP、计算校验和、完成分段与重组。

`net_device` 这一层更根本：内核 IP 栈把明文包路由到 wg0 再交给 WireGuard，DPDK 里没有这一步。你要自己决定"哪些包进隧道"，也就是自己实现一张路由或策略表——这恰好是 VPP 的 FIB 已经在做的事。

RCU 是 wireguard-linux 并发设计的基石，peer 表与 allowedips 的读路径全靠它保护。DPDK 的 `rte_rcu` 语义比内核弱得多，整条读路径要重审。定时器（keepalive、握手重传、密钥过期）、netlink 配置通道、workqueue 同样全部重建。

**关键判断**：第 3 层重建完成之后，你手上就有了一个用户态网络栈。而 VPP 正是这个东西的成熟实现。从这个角度看，把 wireguard-linux 移植到 DPDK，本质上是在用 DPDK 从零造一个不如 VPP 成熟的迷你内核网络栈，只为跑一个 WireGuard。

### 6. 两个容易被忽略的事实

**内核版的很多优化搬过去就失效。** padata 并行队列、skb headroom 预分配、UDP GSO 批量发送，这些设计目标都是适配内核栈。到了 DPDK 上，正确做法是 `rte_ring` 分发加 cryptodev 批量 enqueue，架构完全不同。因此"复用代码"和"复用性能"是两回事：你复用了协议逻辑，性能路径仍要重写。

**许可证要先看。** wireguard-linux 是 GPLv2，移植出来的衍生作品通常也要以 GPLv2 提供；wireguard-go 是 MIT 许可。如果成品要闭源商用，这是需要先回答的问题，不是可以忽略的技术细节。

### 7. 真正值得拿什么，以及收益最高的组合

值得从 wireguard-linux 拿的不是数据结构，是这些年积累的**协议边界处理**：漫游时 endpoint 更新与密钥轮换的时序、cookie 质询的触发条件、抗重放的窗口推进、MTU 与分片处理。这些属于"协议知识"，与内核无关，但恰恰是 VPP 插件那份 2021 年 wireguard-openbsd 基座可能缺的东西。

| 对比维度 | 路径 A：移植 wireguard-linux 到 DPDK | 路径 B：升级 VPP 插件基座 |
|---|---|---|
| 协议栈来源 | 自己移植，承担剥离成本 | VPP 插件已有，只需更新 |
| 网络栈 | 自己用 DPDK 造 | VPP 现成且成熟 |
| 多线程框架 | 自己做 | VPP 现成 MULTITHREAD |
| 工作量 | 与方案 G 重合甚至更高 | 集中在协议逻辑更新 |
| 与上游关系 | 平行造轮子 | 同向，可回流 |
| 适合条件 | 有 VPP 满足不了的特殊约束 | 绝大多数场景 |

如果真要投入，收益最高的组合不是"把 wireguard-linux 移植到 DPDK"，而是**用 wireguard-linux 的协议逻辑去升级 VPP 插件的老基座**——复用现成的用户态网络栈和多线程框架，只把协议实现更新到当代水平。这比自己造栈划算得多，也与上游 Use all benefits of VPP-engine 的方向一致。

如果确实有 VPP 满足不了的特殊约束（例如要极致控制 NUMA 布局、要绕开 VPP 的转发开销、或产品不能引入 VPP 依赖），从零做用户态数据面才有正当理由。但那种情况下起点应该是 wireguard-go 或 Boringtun 这类**本来就为用户态设计**的实现，而不是先背上内核模块再逐个剥依赖。

### 8. 本节结论

- "把 wireguard-linux 改造成不依赖内核的程序"技术上可行，但工作量集中在重建内核机制，不在替换数据结构。
- 完成后的产物是一个自研用户态网络栈，与方案 G 趋同，且不如 VPP 成熟。
- 真正值得复用的是协议边界处理知识，最高收益的用法是拿它升级 VPP 插件基座，而不是自己造栈。

## DESIGN-07 控制面：密钥分发、用户管理与开源参考

数据面收敛之后，控制面往往是工作量更大的一半。WireGuard 协议本身故意不定义控制面，其设计哲学是"密钥即身份"——因此密钥分发、用户管理完全是上层应用的事。这也带来一个重要后果：现成项目的控制面与数据面强绑定，它们几乎都通过 wg(8) 或 netlink 配置内核 wireguard.ko 或标准客户端。自研 VPP / DPDK 数据面不能直接搬用这些控制面代码，但设计思想非常值得借鉴。

### 1. 控制面的六项职责

六项职责里，前四项是用户能直接感知的功能，后两项决定长期运维质量。需要注意的是，配置通道这一层是复用与否的关键：现成控制面全部走 netlink 与 wg(8)，而自研数据面必须自建配置接口，这一层代码无法照搬。

### 2. 密钥分发的核心原则（比选项目更重要）

这些项目在以下五点上高度一致，是真正值得抄的设计。

| 原则 | 做法 | 为什么关键 |
|---|---|---|
| 私钥永不下发 | 客户端本地生成 Curve25519 密钥对，只把公钥交给控制面 | 服务器泄露不影响客户端私钥；若做成服务器生成密钥再推送，设计上就已落后 |
| 控制面不进数据路径 | 控制面只交换公钥与策略，隧道建立后即使宕机，已有连接照常运行 | 与自研数据面天然解耦，控制面可用任意语言实现 |
| 一次性注册密钥 | 新设备凭短时效 setup key 入网，自动完成密钥交换与 IP 分配 | 避免手工分发公钥，是规模化分发的关键 |
| PSK 后量子防御 | 在 Curve25519 之上叠加每客户端预共享密钥，支持轮换 | 低成本增加一层对称密钥保护，wg-easy 已实现 |
| 身份与公钥绑定 | ACL 基于用户或设备身份而非 IP，密钥轮换时身份不变、策略不改 | 让密钥轮换不影响授权体系 |

### 3. 开源项目清单（许可证已核实）

第三方资料对这些项目的许可证说法互相矛盾，下表以官方仓库核实结果为准。许可证差异直接决定能否借鉴代码，必须逐一确认。

| 项目 | 形态 | 控制面许可证（官方核实） | 参考价值 | 适配度 |
|---|---|---|---|---|
| wg-easy | 网关 + Web UI | AGPL-3.0-only | 密钥管理功能最全：轮换密钥对、增删 PSK、客户端过期、二维码配置、OIDC 与 2FA | 仅当确认为网关形态时最贴近；形态待确认，见 DESIGN-08 |
| Headscale | mesh 控制服务器 | BSD-3-Clause | 唯一许可证干净的完整控制面，Go 实现，密钥交换与 IP 分配逻辑清晰 | 仅当确认为 mesh 形态时最贴近；形态待确认，见 DESIGN-08 |
| NetBird | mesh + ZTNA | 控制面 AGPL-3.0，其余 BSD-3-Clause | 身份策略、SSO/MFA、setup key、设备合规检查最完整 | 只能看架构，代码有传染风险 |
| Firezone | 网关 + ZTNA | 控制面 Elastic License 2.0，其余 Apache 2.0 | 基于身份的资源级 ACL 设计 | 官方声明生产自托管控制面不受支持 |
| Pritunl / Netmaker / Pangolin | 网关或 mesh | AGPLv3 / SSPL / Apache 2.0（未逐一核实） | 各有侧重 | 次级参考 |

特别提醒 NetBird 的许可证陷阱：其官方 LICENSES 目录显示，2025 年 8 月的变更把 management、signal、relay 三个目录改为 AGPL-3.0，其余保持 BSD-3-Clause。而这三个目录恰好就是密钥分发与用户管理所在——也就是说，最值得参考的那部分正是许可证最严的部分。第三方文章笼统地说它是 BSD 或 MPL 都不准确。

Firezone 同样需要注意：README 明确写着许可证允许自托管，但生产环境自托管控制面不受官方支持，自托管门户还可能需要与之匹配版本自行构建的客户端。这意味着采用它要承担自行维护控制面的全部成本。

### 4. 结合本项目场景的取舍

**重要更正**：本节此前断言"产品形态是高性能网关加标准 WireGuard 客户端，不是 mesh 组网"。经复核，这是从四项约束中推断出的假设，用户从未确认过拓扑形态，且推断过程存在循环论证（把"互通"偷换成"标准客户端接入"，再据此倒推中心网关）。因此在形态确认前，下面的参考价值排序只是**条件性结论**——成立与否取决于 DESIGN-08 列出的澄清问题。数据面路线 B/H/G 本身不受影响，但部署位置和数量会因形态不同而变化，成本模型差别很大。

- **若最终确认为网关形态**：wg-easy 是最直接的对标，它把网关模式下的密钥管理做得最完整，功能列表可以逐项抄：客户端增删启停、二维码与配置导出、密钥对轮换、PSK 增删、客户端过期时间、连接统计、Prometheus 指标、OIDC 与 2FA。注意 AGPL 的传染边界——闭源商用时只能参考设计，不能复制代码。Headscale 的 mesh 语义则需改造后才能用。
- **若最终确认为 mesh 形态**：排序反转——Headscale 才是最贴近的参考，且 BSD-3-Clause 允许直接借鉴代码，其密钥交换、IP 分配、节点注册流程用 Go 写得清晰；wg-easy 的网关客户端管理模型反而不适用。
- **VPP 插件的配置通道要自己补**。现成控制面都通过 netlink 配置 wg(8)，而本项目的数据面走 VPP API/CLI，所以配置下发这一层必须自己写。但第 2 节的五条原则与拓扑形态无关，不受影响。

### 5. 更省事的选项：兼容现成控制面协议

如果团队人手紧，还有一条比自研完整控制面更划算的路：**让本项目的数据面节点兼容现成控制面协议**。例如做成一个能被 Headscale 管理的节点，或者直接兼容标准 WireGuard 配置格式。这样用户管理、密钥分发、SSO 全部不用自己写，只需专注自研数据面。这条路在两种形态下都成立，但可对接的现成协议不同，需先按 DESIGN-08 确认拓扑再选。

代价是受制于上游协议演进——这与 DESIGN-05 风险清单里提到的 VPP API 变更属于同一类风险：省下的开发量，用长期的跟随成本来还。需要在团队规模确定后再权衡。

### 6. 本节结论

- 控制面六项职责中，配置通道是复用与否的分界：现成项目走 netlink，自研数据面必须自建。
- 真正值得抄的是五条设计原则，尤以"私钥永不下发"和"控制面不进数据路径"为根本。
- 参考价值排序取决于尚未确认的拓扑形态：网关形态下 wg-easy 功能最贴近，mesh 形态下 Headscale 最贴近且许可证最干净；两者分别作为功能参考与代码参考，结论详见 DESIGN-08。
- 人手紧张时优先评估兼容现成控制面协议，用跟随成本换开发量。

## DESIGN-08 更正：拓扑形态是待确认项，不是既定结论

### 1. 问题缘起

DESIGN-05 与 DESIGN-07 中把"高性能网关加标准 WireGuard 客户端"当作已确认的产品形态，并据此给出了控制面项目的参考价值排序。经用户指出后复核：**这一形态是推断出来的，用户从未确认，且推断过程不成立**。本节予以更正，并把需要澄清的问题明确列出。

更正不改变数据面路线 B/H/G 的技术判断——那三条路线只取决于"互通必须、网卡可独占、纯软件加密、不追线速"四项约束，与拓扑无关。但它会改变控制面的重心、数据面需要部署的份数，以及整个项目的成本模型。

### 2. 网关与 mesh 到底差在哪

两种拓扑的本质区别只有两条：**谁负责转发**，以及**连接关系是不是两两直连**。其余差异都是这两条派生出来的。

| 维度 | 网关（星型 / 站点互联） | mesh |
|---|---|---|
| 谁负责转发 | 少数专用节点承担全部或大部分流量 | 每个节点转发自己的流量 |
| 连接关系 | 客户端只连网关，彼此不连 | 节点两两直连 |
| 高性能数据面部署 | 集中在一两台机器上 | 分散到每一个节点 |
| 控制面重点 | 用户管理、准入、资源授权 | 节点注册、IP 分配、密钥轮换、路由分发 |
| 对端软件 | 常是官方 WireGuard 客户端 | 常是自家节点 |
| 典型产品 | wg-easy、Firezone、Pritunl | Tailscale、Headscale、NetBird、Nebula |
| 性能与成本模型 | 一两套高性能数据面，单机要求高 | 每节点一套，单机要求低但总数多 |

一个容易混淆的点：mesh 不等于"性能要求低"。数据中心之间的 mesh 节点同样会谈线速；只是 mesh 节点的接入链路通常只有一条，谈"打满端口"的意义不如集中式网关那么强。

### 3. 错误假设是怎么来的

推断依据有三条，都来自用户已确认的约束：

1. **"网卡可以独占"**——被理解成"有一台专用机器跑 DPDK"，这更像网关。但严格说，mesh 节点若为专用硬件，同样可以独占网卡，这条并不排除 mesh。
2. **"线速"**——线速通常是集中式网关的指标。但这条也只能说明对单机性能要求高，不能推出拓扑。
3. **"互通是必须的"**——这是关键错误：它被默认理解成了"标准 WireGuard 客户端要能接入"。这个替换一旦成立，拓扑自然就是中心网关加远程客户端。但用户说的"互通"从未限定对端类型，也可能指与其他自有节点或某个具体产品互通。

第 3 条属于**循环论证**：先把"互通"偷换成"标准客户端接入"，再用这个替换后的含义倒推网关形态。三项约束里没有任何一条真正要求网关拓扑。引入这个假设的动机，是为了在 DESIGN-07 里给 wg-easy 与 Headscale 排序——这属于为完成排序而补前提，方向反了。

### 4. 影响范围

| 结论位置 | 是否受影响 | 说明 |
|---|---|---|
| 数据面 B/H/G 三路线与四并发点分析 | 不受影响 | 只依赖四项技术约束，与拓扑无关 |
| 加密套件锁定 ChaCha20-Poly1305 | 不受影响 | 由互通硬需求决定 |
| DESIGN-07 项目表格的"适配度"列 | 受影响，已改为条件性表述 | 两款项目的贴近程度随形态反转 |
| DESIGN-07 第 4、5、6 节的取舍与结论 | 受影响，已标注待确认 | 需按澄清结果重排 |
| 控制面职责重心 | 待确认 | 网关偏用户准入，mesh 偏节点注册与路由分发 |
| 成本模型 | 待确认 | 网关一两套数据面，mesh 每节点一套 |
| 可兼容的现成控制面协议 | 待确认 | Headscale 天然面向 mesh，网关需另寻对接方式 |

### 5. 需要澄清的三个问题

判断拓扑其实只差几个事实，回答任意一个基本就能定：

| 问题 | 为什么关键 | 不同答案的后果 |
|---|---|---|
| 对端是谁？远程员工装官方 App 来连，还是自家多台服务器 / 机房互联？ | 直接决定网关还是 mesh | 前者网关，后者大概率 mesh |
| 这套软件跑几份？一两台上，还是每个参与节点都要装？ | 决定数据面部署数量与成本模型 | 一份即网关，每节点即 mesh |
| "互通"具体指什么？与标准 WireGuard 协议互通，还是与某个具体产品（如现有 Tailscale 网络）互通？ | 决定能否沿用现成控制面 | 与具体产品互通可能直接采用对方控制面，省掉自研 |

在得到答案之前，DESIGN-07 中涉及"网关"的结论一律按**条件性结论**阅读：网关形态成立时 wg-easy 最贴近，mesh 形态成立时 Headscale 最贴近，二者排序不可预先确定。

### 6. 一条与形态无关的结论

无论最终是网关还是 mesh，有两点都不变：

- **五条密钥分发原则不受影响**——私钥永不下发、控制面不进数据路径、一次性 setup key、PSK 后量子防御、身份与公钥绑定。这些是协议层与控制面的通用设计，与拓扑无关。
- **配置通道必须自建**——现成控制面走 netlink 配 wg(8)，自研数据面走 VPP API/CLI。这一层无法照搬，与拓扑无关。

### 7. wg-easy 与 Headscale 的功能差异（官方 README 核实）

既然形态待定，有必要把两者的功能差异摊开看。下表均以官方仓库 README 为准，不采信第三方转述。

| 维度 | wg-easy | Headscale |
|---|---|---|
| 本质 | WireGuard + NAT + Web UI 一体，自身就是网关 | Tailscale 控制服务器的开源实现，只有控制面 |
| 管理对象 | 客户端（client） | 节点（node） |
| 数据路径 | 客户端到网关再到目标，全量集中转发 | 节点间 WireGuard 直连，控制面不碰数据 |
| 配置下发 | 每客户端一份静态配置文件 | 全网动态状态：节点列表、Endpoint、AllowedIPs、路由、DNS、ACL |
| 密钥模型 | 服务端生成密钥对，经配置或 QR 码下发，私钥经过服务器 | 节点本地生成，只上报公钥 |
| 身份体系 | 无真正用户概念，管理界面靠密码、2FA、OIDC 保护 | 有 user、tailnet、group、tag，ACL 基于身份，支持跨用户共享节点 |
| 策略粒度 | 每客户端 iptables 防火墙，集中在网关执行 | ACL 下发到各节点执行，分布式策略 |
| 路由能力 | CIDR、增删启停、过期、流量图表 | subnet router、exit node、advertised routes、MagicDNS、DERP 中继 |
| 客户端 | 标准 WireGuard 客户端 | Tailscale 客户端，Windows / macOS / iOS GUI 闭源 |
| 设计规模 | 单机几个到几十个客户端 | README 明说单 tailnet，面向个人或小组织 |

wg-easy 官网列出的功能包括：客户端搜索筛选排序、批量启停删除、QR 码与配置导出、密钥对轮换与 PSK 增删轮换、连接状态与收发图表、One Time Links、客户端过期、Prometheus 与 JSON 指标、IPv6 与 CIDR、2FA、每客户端防火墙过滤、Google / GitHub OAuth 与通用 OIDC、实验性 AmneziaWG 支持。Headscale 的 README 则明确自我定位为 Tailscale 控制服务器的自托管实现，设计目标是单一 tailnet、面向个人与小型组织。

四个真正拉开差距的点：

- **密钥模型是最大反差**。wg-easy 的"下载或复制客户端配置"与"轮换客户端密钥对"意味着私钥由服务端生成并下发，服务器泄露会波及所有客户端；Headscale 沿袭 Tailscale 模型，控制面始终只见公钥。这正好撞上第 DESIGN-07 节那条"私钥永不下发"原则——**wg-easy 功能上值得抄，密钥模型上恰恰是反例**，借鉴时必须替换掉这一条。
- **策略性质不同**。wg-easy 的每客户端防火墙是"网关允许该客户端访问什么"，集中在网关执行；Headscale 的 ACL 是"某用户或标签的节点能访问另一节点的哪个端口"，分发到各节点执行。前者集中式，后者分布式，代码模型不可互换。
- **复杂度来源不同**。mesh 必须解决节点各自藏在 NAT 后的问题，所以 Headscale 需要 DERP 中继做穿透失败兜底，还要管 MagicDNS 与路由广播；wg-easy 的客户端连公网网关，完全不需要这层。这是 mesh 控制面重得多的主因。
- **对端绑定不同**。Headscale 实现的是 Tailscale 控制协议，客户端必须用 Tailscale，且 README 明确警告版本兼容要按 tag 选配置，属于持续跟随成本；wg-easy 用标准 WireGuard 协议，任何 wg 客户端都能接。

对本项目的含义：若为网关形态，wg-easy 功能清单几乎就是控制面需求全集，但密钥模型要改成客户端本地生成、只交公钥；若为 mesh 形态，Headscale 的架构才是对标对象——控制面只交换、数据面自治、身份化 ACL，且 BSD-3-Clause 是唯一能直接借鉴代码的一家。两者共同点是配置通道都走 netlink 配 wg(8)，都对接不了自研 VPP / DPDK 数据面，这一层无论如何要自建。
