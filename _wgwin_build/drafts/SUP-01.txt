# WireGuard 技术补充 · Linux 运行态、驱动与用户态实现

> **主题**：WireGuard 在 Linux 下究竟运行在内核态还是用户态、需要什么驱动、是否存在用户态实现
> **事实来源**：WireGuard 官方 GitHub 组织仓库列表、wireguard-go 官方仓库文档、Linux 5.6 主线合并公告与官方安装页
> **说明**：本篇为独立于正册 9 册之外的补充文档，主题聚焦 Linux 环境，用于与 wireguard-windows 正册的用户态/内核态分界内容互为参照

## SUP-01 Linux 下 WireGuard 的运行态、驱动与用户态实现

### 1. 核心结论

WireGuard 在 Linux 下**默认且官方推荐运行在内核态**。其数据面加解密与 UDP 封装由内核模块 `wireguard.ko` 完成；从 Linux 5.6（2020 年 3 月）起，WireGuard 已进入内核主线，主流发行版默认携带。用户态实现同样存在且由官方维护（wireguard-go），但官方明确不推荐在 Linux 上优先使用。

需要强调一个常见误解：WireGuard 并不是某个硬件网卡的驱动，它本身是「一个虚拟网络接口 + 一段内核协议实现」。因此绝大多数现代 Linux 上不需要额外安装任何驱动，加接口用的就是内核命令 `ip link add wg0 type wireguard`。

内核态路径中，应用流量进入内核网络栈后，直接由 `wireguard.ko` 完成加密与 UDP 封装再交给网卡，全程不离开内核。用户态路径中，内核把流量经 TUN 虚拟网卡交给 `wireguard-go` 进程，在用户态完成协议处理后再通过普通 UDP socket 发回内核，每个包都要穿越用户态与内核态的边界，因此开销更大。

### 3. 需要什么驱动

「驱动」这个问题要按内核版本分两种情况回答，见下表。

| 内核版本 | 数据面实现 | 需要额外安装的东西 |
|---|---|---|
| ≥ 5.6 | 内核内置 wireguard.ko | 仅需 wireguard-tools（wg / wg-quick 配置工具） |
| < 5.6 | 回移植内核模块 | wireguard-dkms + linux-headers，或 wireguard-linux-compat 兼容层，或改用 wireguard-lts 内核 |
| 无内核模块权限 | 用户态 wireguard-go | TUN 设备（/dev/net/tun），不需要内核模块 |

内核 ≥ 5.6 时，安装配置工具即可，命令是 `apt install wireguard`（Debian/Ubuntu）或 `dnf install wireguard-tools`（Fedora）等。

老内核（< 5.6）需要把内核模块补回来。官方安装页在 Arch 一节明确写道："Users of kernels < 5.6 may also choose wireguard-lts or wireguard-dkms + linux-headers, depending on which kernel is used." DKMS 方式会随每次内核升级重新编译模块，优点是兼容性广，缺点是升级时偶有编译失败需要手动处理。wireguard-linux-compat 则是官方维护的回移植兼容层，被 Ubuntu 20.04、Debian Buster 等发行版采用。

内核态实现复用内核自带的加密 API（早期的 Zinc，后来并入内核 crypto 子系统），这正是它代码量小、性能高的原因之一，也意味着用户不需要单独装任何加密驱动。

### 4. 有没有用户态的 WireGuard

有，而且是官方维护的，仓库就在 WireGuard 官方组织下。

| 实现 | 语言 | 许可 | 定位与状态 |
|---|---|---|---|
| wireguard-go | Go | MIT | 官方生产级用户态实现，是 macOS、FreeBSD、OpenBSD、Windows 客户端、Android 背后的协议引擎 |
| wireguard-rs | Rust | MIT | 实验性实现，仓库最后更新停在 2022 年，不建议生产使用 |
| boringtun | Rust | — | Cloudflare 的第三方用户态实现，不在 WireGuard 官方组织内，云场景常用 |

wireguard-go 官方文档对 Linux 的定位有一句关键原话："This will run on Linux; however you should instead use the kernel module, which is faster and better integrated into the OS." 意思是 Linux 上能跑，但官方明确建议优先用内核模块，因为更快、与系统集成更好。

在 Linux 上启动用户态实现的命令是 `wireguard-go wg0`（默认转入后台，加 -f 保持前台），接口起来后依然用 `wg(8)` 和 `ip(8)` 配置。删除接口用 `ip link del wg0`，或删除控制 socket `/var/run/wireguard/wg0.sock` 让其自行退出。

用户态实现的适用场景：容器或无内核模块权限的环境（无法 insmod）、需要跨多平台复用同一套实现的场景、老内核且不便装 DKMS、以及协议调试与研究。代价是每个包的用户态与内核态边界穿越带来的性能损耗。

### 5. 官方组织相关仓库的角色

用户给出的链接是 WireGuard 官方 GitHub 组织页，需要注意这里绝大多数仓库只是镜像（mirror only），官方源在 git.zx2c4.com。下表列出与运行态问题直接相关的仓库。

| 仓库 | 作用 | 运行态 |
|---|---|---|
| wireguard-linux | 内核实现（主线源码镜像） | 内核态 |
| wireguard-tools | wg / wg-quick 配置工具 | 用户态工具，仅配置 |
| wireguard-go | 官方 Go 用户态实现 | 用户态 |
| wireguard-linux-compat | 老内核回移植模块 | 内核态（兼容层） |
| wireguard-rs | Rust 实验性实现 | 用户态（实验） |
| wireguard-nt | Windows 原生内核驱动 | 内核态（Windows） |
| wireguard-windows | Windows 客户端（Go 调用 wireguard-nt） | 用户态程序 |

### 6. 小结

Linux 上默认走内核态，wireguard.ko 从 5.6 起内置、无需额外驱动；内核低于 5.6 才需要 DKMS 或兼容层回移植。用户态有官方的 wireguard-go 可用，但官方不推荐在 Linux 生产环境优先使用，主要留给无内核权限或跨平台的场景。理解这条内核态与用户态的分界，也有助于读懂 wireguard-windows 正册中「用户态组件 + wireguard-nt 内核驱动」的四层结构——两个平台只是把数据面放在不同的执行位置，协议本身是一致的。
