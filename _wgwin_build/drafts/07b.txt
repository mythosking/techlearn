# wireguard-windows 技术资料 · 07 模块与特性介绍（分片 B）

## 07-07 `tunnel/firewall` WFP 模块

### 1. 背景与动机

在 Linux 上，WireGuard 的全隧道语义常由 `wg-quick` 生成的路由与 `iptables` 规则共同完成；Windows 既没有 Netfilter，也没有 `wg-quick` 的 `%i`、`PreUp`、`PostUp` 那一套脚本上下文。Windows 官方客户端因此选择了另一条路径：路由与地址交给 IP Helper API 和 WireGuardNT 适配器，泄漏防护交给 Windows Filtering Platform（WFP）。`tunnel/firewall` 包就是这条路径的用户态实现，它不参与任何数据包加解密，也不实现握手，只负责在系统过滤引擎里安装一组“放行什么、阻断什么”的过滤器。

需要先理解它要解决的窗口期问题。全隧道配置把 `0.0.0.0/0` 与 `::/0` 写进某个 peer 的 `AllowedIPs` 后，隧道服务会把默认路由指向 WireGuard 适配器。但路由生效与隧道可用并不是同一时刻：适配器可能刚创建、WireGuardNT 可能尚未完成首次握手、DNS 查询可能比隧道更早发出、某些应用还会显式绑定物理网卡或使用自己的解析器。只要有一条路径绕开隧道，流量就会以明文离开主机。WFP 的价值在于它在 ALE（Application Layer Enforcement）层对“连接建立/接收许可”做授权判定，能在套接字真正发包之前拒绝，而不是事后补救。

选择 WFP 而不是普通 Windows 防火墙规则，有三个直接原因。第一，WFP 过滤器可以按接口 LUID 匹配，而 WireGuard 适配器是每次启动隧道时动态创建、停止时销毁的，LUID 并不稳定，用名称或别名做规则容易在适配器重建后失效。第二，WFP 能同时拿到进程身份（应用 ID）、进程安全描述符、协议、端口、远端地址与 ICMP 类型，足以表达“只允许隧道服务自身的 UDP、只允许指定 DNS 服务器的 53 端口、允许 DHCP 与 NDP”这种组合条件。第三，WFP 支持事务与动态会话，安装失败可以整体回滚，进程退出后对象自动回收，不会留下跨重启的残留规则。

触发条件被刻意设计得很窄：只有当配置里只有一个 peer，且该 peer 的 `AllowedIPs` 包含 `/0` 时，隧道服务才会进入限制模式。多 peer、部分路由、企业分流等场景不会启用这套 kill-switch，而是回退到 Windows 常规路由与 DNS 行为。这样做的好处是避免把“全隧道”的强约束误加到普通配置上；代价是用户必须理解 `/0` 的语义，否则会误以为“只要连上 VPN 就一定有泄漏防护”。`Table=off` 与触发条件的关系需要对照 `tunnel/service.go` 的实际判定核验，本仓库快照中该判定不在 `firewall` 包内。

还必须写清能力边界：本仓库是 Windows 官方客户端，不是 Linux 内核实现，也不是 wireguard-go 用户态数据面。内核数据面由外部项目 WireGuardNT 提供，`driver/` 只做 IOCTL 配置下发；`tunnel/firewall` 只操作 WFP 对象，不碰 Noise 握手、不碰 ChaCha20-Poly1305、不碰路由表。把本模块当成“Windows 版的 iptables 封装”会高估它的职责，也会误读它的规则集合。

### 2. 核心概念

**WFP 对象模型**。一个过滤器不是孤立存在的，它挂在 provider、subLayer、layer 三层坐标上。provider 用 GUID 标识“这批对象属于 WireGuard”，便于排障时按来源筛选；subLayer 是同一引擎内的排序容器，`registerBaseObjects()` 把子层权重设为 `^uint16(0)`（即 65535），使它排在系统默认子层之前；layer 决定在协议栈的哪个点评估，本模块主要使用 `FWPM_LAYER_ALE_AUTH_CONNECT_V4`、`FWPM_LAYER_ALE_AUTH_RECV_ACCEPT_V4` 及其 V6 对应层，Hyper-V 例外才使用 MAC 帧层。

**过滤器（filter）的五个要素**。一是 `layerKey`，决定出站连接还是入站接收；二是条件数组 `filterCondition`，每个条件由字段键、匹配类型和值组成；三是动作 `action`，取 `FWP_ACTION_PERMIT` 或 `FWP_ACTION_BLOCK`；四是权重 `weight`，在同一子层内数值大者先评估；五是显示数据 `displayData`，即排障时看到的名称与描述。权重在本模块里不是装饰，而是规则语义的一部分：`blockAll` 必须排在所有放行规则之后，否则“先阻断后放行”会导致全断。

**条件字段的用法**。接口条件用 `FWPM_CONDITION_IP_LOCAL_INTERFACE` 配 `FWP_UINT64`，值就是适配器 LUID；进程条件用 `FWPM_CONDITION_ALE_APP_ID` 配 `FWP_BYTE_BLOB_TYPE`，值由 `fwpmGetAppIdFromFileName0()` 从当前可执行文件取得；用户/安全上下文用 `FWPM_CONDITION_ALE_USER_ID` 配 `FWP_SECURITY_DESCRIPTOR_TYPE`，并带 `FWP_ACTION_FLAG_CLEAR_ACTION_RIGHT`，以避免“同一 exe 里托管的其他进程”命中服务放行规则。DNS 规则用 `IP_REMOTE_PORT = 53` 加两次 `IP_PROTOCOL`（UDP 与 TCP）表达“或”；DHCPv4 用本地端口 68、远端端口 67 与广播地址 `0xffffffff`；DHCPv6 用 `ff02::1:2`、`ff05::1:3`、端口 546/547 以及 `fe80::/10` 链路本地前缀；NDP 用 ICMPv6 类型 133 至 137 分别表达路由请求、路由通告、邻居请求、邻居通告与重定向。

**动作与权重分层**。服务自身放行权重 15；DNS 的“允许指定服务器”权重 15、“阻断其余 53 端口”权重 14；环回放行 13；隧道接口、DHCPv4、DHCPv6、NDP 均为 12；兜底阻断为 0。`blockDNS()` 内部会先校验 `weightDeny < weightAllow`，否则直接返回错误，因为一旦deny 权重不低于 allow，允许规则永远不会命中。这个显式校验是阅读源码时最容易被忽略、但排障时最关键的一处。

各规则组的权重与条件对照如下表所示，读表时应把“权重”理解为同一子层内的评估顺序，而不是优先级数值越大越安全。

| 规则组 | 权重 | 主要条件 | 动作 |
|---|---:|---|---|
| WireGuard 服务自身 | 15 | 应用 ID + 服务安全描述符 | 放行 |
| DNS 指定服务器 | 15 | 远端端口 53、UDP/TCP、远端地址 | 放行 |
| DNS 其余流量 | 14 | 远端端口 53、UDP/TCP | 阻断 |
| 环回 | 13 | `FWP_CONDITION_FLAG_IS_LOOPBACK` | 放行 |
| 隧道接口 | 12 | 本地接口 LUID | 放行 |
| DHCPv4 / DHCPv6 / NDP | 12 | 端口 67/68、546/547、ICMPv6 133-137 | 放行 |
| 兜底 | 0 | 无附加条件 | 阻断 |

**动态会话**。`createWfpSession()` 使用 `FWPM_SESSION_FLAG_DYNAMIC`，事务等待时间为 `INFINITE`。动态会话的含义是：引擎句柄关闭时，会话内创建的对象随之销毁。因此 `DisableFirewall()` 只需要 `fwpmEngineClose0(wfpSession)`，不需要逐条删除过滤器；即使隧道进程异常退出，系统也不会长期保留一套指向旧 LUID 的阻断规则。这与“持久化过滤器”是两种完全不同的运维模型，不能混用。

**事务语义**。`runTransaction()` 依次执行 `fwpmTransactionBegin0`、安装回调、`fwpmTransactionCommit0`；任一步失败就 `fwpmTransactionAbort0`。这意味着读者不会看到“只装了一半”的状态：要么 provider、子层、全部过滤器都生效，要么全部不生效。对于 kill-switch 这种“部分生效反而危险”的场景，事务不是可选项。

**“单 peer + `/0`”与 DNS 收紧**。`EnableFirewall()` 的第三个参数是 `restrictToDNSServers []netip.Addr`。当配置声明了 DNS 服务器时，`blockDNS()` 会为每个地址生成“允许该远端地址的 53 端口”的条件，同时保留一条“阻断所有 53 端口”的规则。其目的是压制 Windows 的多宿主 DNS 行为：系统可能同时向多个网卡的 DNS 服务器发查询，如果不收紧，查询会从物理网卡泄漏。没有配置 DNS 时，这个分支不会安装，用户需要自行确认系统解析器不会走物理链路。

### 3. 关键数据结构与源码位置

本模块的源码集中在 `tunnel/firewall/` 目录，阅读顺序建议从对象生命周期到规则细节：

- `blocker.go`：模块入口。定义 `wfpObjectInstaller` 函数类型、`baseObjects`（provider 与 filters 两个 GUID）、包级变量 `wfpSession`，以及 `createWfpSession()`、`registerBaseObjects()`、`EnableFirewall()`、`DisableFirewall()`。
- `rules.go`：规则集合。包含 `permitTunInterface()`、`permitWireGuardService()`、`permitLoopback()`、`permitDHCPIPv4()`、`permitDHCPIPv6()`、`permitNdp()`、`permitHyperV()`、`blockAll()`、`blockDNS()`。
- `helpers.go`：事务与身份辅助。`runTransaction()`、`createWtFwpmDisplayData0()`、`filterWeight()`、`wrapErr()`、`getCurrentProcessSecurityDescriptor()`、`getCurrentProcessAppID()`。
- `types_windows.go`：WFP 结构的手工镜像，包括 `wtFwpmFilter0`、`wtFwpmFilterCondition0`、`wtFwpConditionValue0`、`wtFwpValue0`、`wtFwpmSession0`、`wtFwpmSublayer0`、`wtFwpProvider0`、`wtFwpmDisplayData0`、`wtFwpByteArray16`、`wtFwpV6AddrAndMask` 等；`types_windows_32.go` 与 `types_windows_64.go` 处理指针宽度差异。
- `syscall_windows.go`、`zsyscall_windows.go`、`mksyscall.go`：系统调用声明与生成入口；`fwpmEngineOpen0`、`fwpmFilterAdd0`、`fwpmSubLayerAdd0`、`fwpmProviderAdd0`、`fwpmTransactionBegin0/Commit0/Abort0`、`fwpmEngineClose0`、`fwpmGetAppIdFromFileName0`、`fwpmFreeMemory0` 都在这里。
- `types_windows_test.go`：以 `unsafe.Sizeof` 与 `unsafe.Offsetof` 校验结构体大小和字段偏移。这类测试看似“形式主义”，实则是 WFP 调用正确性的底线：这些结构体会被直接传给内核，字段偏移错一个字节就可能得到 `FWP_E_INVALID_PARAMETER` 或更隐蔽的行为异常。

字段的逐项含义、对齐与生命周期不在本篇展开（字段见 05-08）。本篇只强调三个“读源码时必须盯住”的点：`baseObjects.filters` 同时充当子层键与过滤器归属，二者是同一个 GUID；`wtFwpmFilter0.weight` 的类型是 `wtFwpValue0`，不是一个裸整数，赋值必须经过 `filterWeight()`；`permitWireGuardService()` 的条件数组里，安全描述符 blob 必须在调用期间保持存活，源码用 `runtime.KeepAlive(sdBlob)` 与 `runtime.KeepAlive(sd)` 保证这一点。

`EnableFirewall()` 是唯一入口，调用链可以按“会话—对象—规则—事务”四段来读。第一段建立会话：`createWfpSession()` 填充 `wtFwpmSession0` 的显示名、`FWPM_SESSION_FLAG_DYNAMIC` 标志与无限事务超时，然后 `fwpmEngineOpen0()` 取得引擎句柄。若包级变量 `wfpSession` 已非零，函数立刻返回“防火墙已启用”错误，因此重复调用不是幂等的，调用方必须先判断状态或保证只调用一次。

第二段注册基础对象：`runTransaction()` 开启事务后调用 `registerBaseObjects()`，生成两个 GUID，先 `fwpmProviderAdd0()` 注册 provider，再 `fwpmSubLayerAdd0()` 注册子层，子层权重为 `^uint16(0)`。provider 的作用是归属标识，子层的作用是排序容器；两者都成功后，后续过滤器才有合法的 `providerKey` 与 `subLayerKey`。

第三段按权重安装规则，顺序写在 `EnableFirewall()` 的 `objectInstaller` 闭包里：

1. `permitWireGuardService(session, baseObjects, 15)`：以当前进程的应用 ID 与服务安全描述符为条件，在四个 ALE 层各装一条放行规则，确保 WireGuard 自己的 UDP 报文能进出。
2. 若 `doNotRestrict` 为假且 `restrictToDNSServers` 非空，调用 `blockDNS(restrictToDNSServers, session, baseObjects, 15, 14)`：先装四条阻断 53 端口的规则（V4/V6 出站与入站），再为每个 DNS 地址追加远端地址条件，装四条允许规则。IPv4 地址用 `FWP_UINT32` 承载 `binary.BigEndian.Uint32()` 的结果，IPv6 地址用 `FWP_BYTE_ARRAY16_TYPE` 承载 `wtFwpByteArray16`。
3. `permitLoopback(..., 13)`：以 `FWPM_CONDITION_FLAGS` 匹配 `FWP_CONDITION_FLAG_IS_LOOPBACK`，四个层各一条。
4. `permitTunInterface(..., 12, luid)`：以 `FWPM_CONDITION_IP_LOCAL_INTERFACE` 匹配 LUID，四个层各一条；这是“隧道内流量”被放行的关键。
5. `permitDHCPIPv4(..., 12)`：两条规则，出站 UDP 68→67 到广播地址，入站 UDP 67→68。
6. `permitDHCPIPv6(..., 12)`：两条规则，出站与入站，涉及 `ff02::1:2`、`ff05::1:3`、端口 546/547、`fe80::/10`。
7. `permitNdp(..., 12)`：按 133、134、135、136、137 五类 ICMPv6 组装七条过滤器（135 与 136 是双向，各两条）。
8. `blockAll(..., 0)`：四个层各一条无条件的阻断规则，作为兜底。

第四段提交：全部安装成功后 `fwpmTransactionCommit0()`；任一失败则 `fwpmTransactionAbort0()` 并关闭引擎。`DisableFirewall()` 只做一件事：`fwpmEngineClose0(wfpSession)` 并把包级变量清零。由于会话是动态的，过滤器随句柄关闭而消失。

需要特别指出，`permitHyperV()` 虽然完整实现，但在 `EnableFirewall()` 中被注释掉，源码注释说明它是二层规则、而其余规则是三层，作者选择“先不启用，遇到问题再打开”。这意味着在启用 Hyper-V 的主机上做全隧道时，虚拟机之间的二层流量是否受影响，需要按实际版本核验，不能仅凭函数存在就断定已生效。

### 5. 配置/命令/代码实例

触发这套规则的最小配置形态如下。这里只列与本模块直接相关的键，完整键集与语义见 04-02、04-03。

```conf
[Interface]
PrivateKey = <客户端私钥，Base64，44 字符>
Address = 10.7.0.2/32
DNS = 10.7.0.1

[Peer]
PublicKey = <服务端公钥，Base64，44 字符>
AllowedIPs = 0.0.0.0/0, ::/0
# 其他键不在本篇展开，完整配置键见 04-02 与 04-03
```

`AllowedIPs` 中的 `0.0.0.0/0` 与 `::/0` 是进入限制模式的必要条件之一；`DNS` 决定是否安装 53 端口收紧规则；`Address` 决定适配器地址，但不改变过滤规则形状；`PrivateKey` 与 `PublicKey` 只影响密钥与握手。其余接口键的行为不在本篇展开，需要时按 04-02 核验。

从代码角度，调用方的典型顺序是先拿到适配器 LUID，再启用防火墙，最后在退出路径关闭。下面的片段是示意性调用，参数来源与错误映射需对照 `tunnel/service.go` 的实际版本核验。

```go
luid, err := adapter.LUID()
if err != nil {
    return services.ErrorCreateNetworkAdapter
}

if err := firewall.EnableFirewall(uint64(luid), doNotRestrict, dnsServers); err != nil {
    return services.ErrorFirewall
}
defer firewall.DisableFirewall()
```

排障时最直接的办法是把当前 WFP 状态导出为 XML，再按显示名过滤。命令与示例输出如下，输出格式与字段名需对照实际 Windows 版本核验。

```powershell
netsh wfp show filters file=C:\Temp\wfp-filters.xml
Select-String -Path C:\Temp\wfp-filters.xml -Pattern 'WireGuard|Permit outbound DHCP|Block all outbound' |
    Select-Object -First 6 |
    ForEach-Object { $_.Line.Trim() }
```

```text
正在收集筛选器信息
已成功保存筛选器信息。

<displayData name="Permit unrestricted outbound traffic for WireGuard service (IPv4)" description=""/>
<displayData name="Permit outbound DHCP request (IPv4)" description=""/>
<displayData name="Block all outbound (IPv4)" description=""/>
<displayData name="Permit outbound IPv4 traffic on TUN" description=""/>
```

判读要点如下。第一，`netsh wfp show filters` 只负责把当前过滤器库导出为文件，控制台只会打印“正在收集/已成功保存”，真正的证据在 XML 里，因此必须用 `Select-String` 或解析器二次检索。第二，示例中的 `displayData name` 就是源码 `createWtFwpmDisplayData0()` 传入的字符串，属于稳定锚点：能看到 `Permit unrestricted outbound traffic for WireGuard service (IPv4)` 说明服务自身放行规则已安装；能看到 `Block all outbound (IPv4)` 说明兜底阻断已生效；若只有前者没有后者，通常意味着 `doNotRestrict` 为真或 `EnableFirewall()` 在中间步骤失败并被事务回滚。第三，`Permit outbound IPv4 traffic on TUN` 是否存在，直接反映 LUID 条件是否写入成功；若该条缺失而阻断存在，表现就是“隧道已连接但业务全断”，因为隧道接口本身没有被放行。第四，XML 中还会带 `weight`、`layerKey`、`action` 等字段，排查权重顺序时应优先核对 `Block all` 的权重是否为 0、各 Permit 是否大于 0；只看名称不看权重，容易得出错误结论。第五，导出文件可能包含大量系统过滤器，建议始终带 `WireGuard` 关键字过滤，避免把 Windows 自带规则误认为本模块产物。

### 6. 注意事项、陷阱与最佳实践

- **不要重复调用 `EnableFirewall()`**。包级 `wfpSession` 非零时函数直接报错，调用方若忽略错误继续启动，会得到“看起来启动了、实际没有防火墙”的假象。正确做法是把启用动作放在隧道启动的单一分支里，并在关停路径成对调用 `DisableFirewall()`。
- **权重顺序就是语义**。`blockAll` 必须是 0，所有 Permit 必须大于 0；`blockDNS` 的 allow 必须大于 deny。修改权重前先想清楚“谁先匹配”，否则会出现 DNS 全断或全放行两种极端。
- **DNS 收紧只覆盖 53 端口**。DoH（443）、DoT（853）、mDNS（5353）都不在放行/阻断条件内；如果组织依赖加密 DNS，kill-switch 不会替你把查询引到隧道内 DNS，需要额外的应用层策略。
- **DHCP 与 NDP 例外不能删**。删掉 DHCPv4/v6 规则，全隧道下物理网卡的租约续期会失败；删掉 NDP 规则，IPv6 邻居发现与路由通告会中断，表现为“IPv6 时通时不通”。
- **LUID 是动态的**。适配器每次启动都会重建，LUID 随之变化；任何缓存 LUID 的外部脚本或自定义规则都会在重启后失效。排障时应以“当前会话”的过滤器为准，而不是比对上一次的 XML。
- **`0.0.0.0/1 + 128.0.0.0/1` 是逃生门**。如果希望获得近似默认路由但不想启用 kill-switch，可以用这两条前缀替代 `0.0.0.0/0`，IPv6 对应 `::/1 + 8000::/1`；UI 编辑器提供对应复选框，本质是改写 `AllowedIPs`，不是关闭防火墙。
- **`Table=off` 要单独验证**。没有默认路由时，即使过滤器装上了，流量也未必走隧道；不要把“防火墙已启用”误当成“流量已受保护”，两者是不同层面的事实。
- **Hyper-V 规则默认未启用**。源码中 `permitHyperV()` 被注释，若在 Hyper-V 主机上观察到虚拟机互通异常，应先确认该版本是否重新启用了这段逻辑，而不是直接改权重。
- **错误信息带文件行号**。`wrapErr()` 会把 `syscall.Errno` 包装成 `Firewall error at <file>:<line>`，日志里看到这类字符串时应直接定位到对应 `fwpm*` 调用，而不是只看外层“无法启用防火墙规则”。
- **不要把 WFP 当端点安全**。它只约束本机流量的出入口路径，不检测恶意内容、不替代杀毒、不防本地管理员篡改；本地管理员可以删除过滤器或停止隧道服务。

### 7. 小结与延伸阅读

`tunnel/firewall` 是一个“小而硬”的模块：代码量不大，但每一个条件、每一个权重都直接对应一条安全语义。它用 WFP 的 provider/subLayer/filter 三层模型表达“只放行 WireGuard 自身、指定 DNS、环回、隧道接口、DHCP 与 NDP，其余全断”，用事务保证安装的原子性，用动态会话保证退出后的清理。理解它的关键不是记住函数名，而是记住三条主线：触发条件是“单 peer + `/0`”，排序依据是权重，身份绑定是“应用 ID + 服务安全描述符”。

延伸阅读建议按“配置—字段—原理—模块”四层展开：先看 04-03 弄清 `AllowedIPs` 与 `DNS` 的写法，再看 05-08 核对 WFP 结构字段，然后读 06-09 理解 kill-switch 的完整判定链，最后回到 `docs/netquirk.md` 的 “Firewall Considerations for `/0` Allowed IPs” 一节对照官方表述。若要在实验环境验证，建议先用 `0.0.0.0/1 + 128.0.0.0/1` 跑通流量，再切到 `/0` 观察过滤器差异，这样可以清晰区分“路由问题”与“防火墙问题”。

## 07-08 `manager` 服务与隧道跟踪模块

### 1. 背景与动机

Windows 官方客户端由三块用户态组件加一个内核驱动组成：Tunnel Service、Manager Service、UI，以及 WireGuardNT。Tunnel Service 每条隧道一个实例，负责把配置下发到驱动、配置地址路由、启停防火墙；UI 是普通交互进程，负责列表、编辑、日志与托盘；Manager Service 则是唯一常驻的 LocalSystem 控制面，负责“谁来创建隧道服务、谁来跟踪隧道状态、谁来把 UI 拉起来、谁来在多个会话之间同步事件”。`manager` 包实现的正是这最后一层。

为什么需要一个独立的管理服务，而不是让 UI 直接调 `sc create`？第一是权限。创建服务、写入 `%ProgramFiles%\WireGuard\Data\Configurations`、访问机器范围的 DPAPI 密文，都要求管理员甚至 SYSTEM 权限；让每个登录用户的 UI 都带高权限运行，既不符合最小权限，也会把攻击面铺到每个会话。第二是会话隔离。Windows 支持多用户同时登录、RDP 断线重连、快速用户切换；UI 必须运行在各自的交互会话里，而服务天然运行在会话 0，二者不能共享窗口句柄，只能通过 IPC 通信。第三是生命周期。隧道服务是“开机自启、按配置常驻”的对象，不能依赖某个用户的登录状态；Manager Service 以自动启动方式运行，才能在无人登录时继续跟踪隧道。

这套设计也带来一个容易被误解的边界：Manager Service 不转发数据包，也不直接操作 WireGuardNT。它做的是服务编排与状态聚合：安装/卸载 `WireGuardTunnel$<name>`、订阅服务状态变化、把变更通过管道推给 UI、在需要时以提升令牌执行更新。数据面仍然在 WireGuardNT，隧道配置仍然由 Tunnel Service 下发。把 manager 当成“VPN 网关”或“流量代理”是典型误读。

从运维视角看，manager 的价值是“单一事实来源”：UI 看到的隧道列表、托盘图标状态、日志页内容、更新进度，全部来自 manager 的 IPC 通知；`sc query` 看到的服务状态，则来自 Windows SCM，两者通过 `tunneltracker.go` 对齐。理解这一点，排障时就能快速判断问题出在“服务没起来”“跟踪没订阅上”还是“UI 没收到通知”，而不是在三个组件之间反复猜测。

### 2. 核心概念

**服务命名与配置**。管理服务名固定为 `WireGuardManager`，由 `svc.Run("WireGuardManager", &managerService{})` 注册；隧道服务名由 `conf.ServiceNameOfTunnel(name)` 生成，形如 `WireGuardTunnel$Office`。`InstallTunnel()` 创建服务时设置 `SERVICE_WIN32_OWN_PROCESS`、`StartAutomatic`、`ErrorNormal`、依赖 `Nsi` 与 `TcpIp`、显示名 `WireGuard Tunnel: <name>`，并显式要求 `SERVICE_SID_TYPE_UNRESTRICTED`。最后这一项不是可选项：没有不受限服务 SID，隧道进程在访问某些网络对象时会受限，行为与预期不符。

**会话模型**。`Execute()` 先 `WTSEnumerateSessions()` 枚举当前会话，只处理 `WTSActive` 与 `WTSDisconnected` 两种状态；对每个会话调用 `WTSQueryUserToken()` 取得用户令牌，再判断“是否管理员或可提升”“是否是受限操作员”，通过后为每个会话启动一个 UI 进程。`procs` 保存会话 ID 到 `uiProcess` 的映射，`aliveSessions` 标记会话是否仍然有效。登录触发 `WTS_SESSION_LOGON` 时新增，注销触发 `WTS_SESSION_LOGOFF` 时删除并 `Kill()` 对应 UI。

**令牌判定与受限 UI**。`elevate.TokenIsElevatedOrElevatable(userToken)` 判断当前令牌是否已提升或存在可提升的链接令牌；若不是管理员，则读取注册表 `LimitedOperatorUI`，再把令牌复制成 impersonation token，检查是否属于 `WinBuiltinNetworkConfigurationOperatorsSid`（Network Configuration Operators，S-1-5-32-556）。只有管理员或受限操作员才会被拉起 UI。受限操作员的权限被 IPC 层进一步收紧：`Delete()`、`Create()`、`Quit()`、`Update()` 在 `elevatedToken == 0` 时直接返回 `ERROR_ACCESS_DENIED`，因此他们能启停隧道，却不能删除配置或退出管理服务。

**IPC 模型**。每个 UI 与 manager 之间有三根匿名管道：UI→manager 的请求、manager→UI 的响应、manager→UI 的事件；此外还有一个可继承的日志共享内存句柄。`IPCServerListen(reader, writer, events, elevatedToken)` 为每个连接创建一个 `ManagerService`，`ServeConn()` 用 `gob` 解码方法类型与参数，执行后把结果编码回去。事件方向不是“请求-响应”，而是 `notifyAll()` 主动广播：隧道状态变化、隧道列表变化、管理服务即将停止、发现更新、更新进度，各有独立通知类型。事件写入带 1 秒写超时，避免某个卡死的 UI 拖住整个服务。

IPC 方法集合与权限边界如下表所示，表中“管理员令牌”指连接创建时传入了非零 `elevatedToken`；受限 UI 的连接该值为零。

| 方法 | 用途 | 权限要求 |
|---|---|---|
| `StoredConfig` | 读取磁盘上的配置 | 任意已连接 UI |
| `RuntimeConfig` | 读取驱动中的运行时配置 | 任意已连接 UI |
| `Start` | 安装并启动隧道服务 | 任意已连接 UI |
| `Stop` | 停止并卸载隧道服务 | 任意已连接 UI |
| `WaitForStop` | 等待服务真正删除 | 任意已连接 UI |
| `Delete` | 停止并删除配置文件 | 管理员令牌 |
| `Create` | 保存新配置 | 管理员令牌 |
| `State` | 查询单个隧道状态 | 任意已连接 UI |
| `GlobalState` | 查询全局汇总状态 | 任意已连接 UI |
| `Quit` | 退出管理服务 | 管理员令牌 |
| `Update` | 触发下载与安装更新 | 管理员令牌 |

**隧道跟踪**。`watchNewTunnelServices()` 通过 `SubscribeServiceChangeNotifications()` 订阅服务数据库变化（`SC_EVENT_DATABASE_CHANGE`），一旦有新服务创建就调用 `trackExistingTunnels()`；`trackTunnelService()` 再对单个服务订阅状态变化（`SC_EVENT_STATUS_CHANGE`）。状态被归一化为五个值：`TunnelUnknown`、`TunnelStarted`、`TunnelStopped`、`TunnelStarting`、`TunnelStopping`；`trackedTunnelsGlobalState()` 把所有隧道汇总成一个全局状态，供托盘与任务栏进度使用。这个“全局状态”不是简单取最后一个，而是按 Starting > Stopping > Started 的优先级合成。

**配置冲突处理**。`ManagerService.Start()` 在安装新隧道前，会遍历 `trackedTunnels`，用 `conf.Config.IntersectsWith()` 判断地址/路由是否与目标配置相交；相交的隧道会被异步停止，若某个相交隧道正处于 `TunnelStarting` 或 `TunnelUnknown`，则直接返回“请等待该隧道完成激活”。这套逻辑解决的是 Windows 上“同一地址段不能同时挂在两个适配器”的现实约束，也解释了为什么有时启动一个隧道会看到另一个隧道被自动停掉。

**退出码与错误**。`services.DetermineErrorCode()` 把错误分成两类：实现了 `windows.Errno` 的系统错误直接用 Win32 码，否则用服务自定义的 `services.Error` 枚举。`trackTunnelService()` 在隧道停止时读取 `ServiceSpecificExitCode`，若不是 `ErrorSuccess` 就删除服务并把错误通过 IPC 推给 UI。这样 UI 上看到的“隧道启动失败”往往对应一个具体的枚举值，而不是笼统的“服务已停止”。

### 3. 关键数据结构与源码位置

`manager/` 目录的文件分工如下：

- `service.go`：`managerService` 与 `Execute()`，管理服务的启动、会话枚举、UI 孵化、控制请求循环与停止清理；`Run()` 是 `svc.Run` 的薄封装。
- `install.go`：`InstallManager()`、`UninstallManager()`、`InstallTunnel()`、`UninstallTunnel()`、`changeTunnelServiceConfigFilePath()`，以及缓存的服务管理器 `serviceManager()`。
- `tunneltracker.go`：`trackedTunnels`、`trackTunnelService()`、`trackExistingTunnels()`、`watchNewTunnelServices()`、`trackService()` 与状态映射函数。
- `ipc_server.go`：`ManagerService` 的方法集合、`ServeConn()`、`IPCServerListen()`、`notifyAll()` 与各类 `IPCServerNotify*`。
- `ipc_client.go`：UI 侧客户端，`InitializeIPCClient()`、方法类型枚举、回调注册表与各 `IPCClient*` 函数。
- `uiprocess.go`：`uiProcess` 与 `launchUIProcess()`，负责 `CreateProcessAsUser`、句柄列表、环境块与进程等待。
- `ipc_driver.go`、`updatestate.go`：驱动侧 IPC 辅助与更新状态枚举。

需要说明的是，本仓库快照的 `manager/` 下没有独立的 `log.go`；管理服务的日志初始化直接调用 `ringlogger.InitGlobalLogger(logFile, "MGR")`，日志文件路径来自 `conf.LogFile(true)`。若读者手上的版本存在 `log.go`，应以实际文件为准，本篇不虚构其内容。

结构体层面，`managerService` 是空结构，只用于挂载 `Execute()`；`ManagerService` 持有事件管道、事件锁与提升令牌；`uiProcess` 只包一个进程句柄；`serviceSubscriptionState` 保存服务对象、回调、`sync.WaitGroup` 与一次性标志。字段的完整定义、读写时机与并发约束见 05-09，本篇不重复列表。

管理服务的生命周期可以按“启动—孵化—跟踪—停止”四段阅读，整体关系见图 07-08-01。

第一段是启动。`Run()` 调用 `svc.Run()` 后，`Execute()` 先发送 `StartPending`，随后打开日志文件并初始化全局环形日志；失败则把 `serviceError` 置为 `ErrorRingloggerOpen` 并退出。接着取当前可执行文件路径、调用 `watchNewTunnelServices()` 建立服务数据库订阅，再注册两个配置存储回调：一个在配置迁移时修改隧道服务的命令行参数，另一个在配置变化时通知所有 UI 刷新列表。之后枚举会话、为每个有效会话启动 UI 协程，最后把服务状态切到 `Running`，接受 `Stop` 与 `SessionChange`。

第二段是 UI 孵化。`startProcess(session)` 先用 `WTSQueryUserToken()` 拿用户令牌，判断管理员/可提升/受限操作员；不满足就关闭令牌返回。通过后解析用户名、域、账户类型与用户配置文件目录，管理员走提升令牌，受限操作员走普通用户令牌。随后进入循环：创建三对管道，调用 `IPCServerListen()` 注册服务端，调用 `ringlogger.Global.ExportInheritableMappingHandle()` 导出可继承的日志映射句柄，再用 `launchUIProcess()` 以 `CreateProcessAsUser()` 启动 `wireguard.exe /ui <reader> <writer> <events> <mapping>`，并把四个句柄放入 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`，确保只有这四个句柄被继承。进程启动后 `proc.Wait()` 阻塞；若退出码是 `STATUS_DLL_INIT_FAILED_LOGOFF`（0xC000026B），说明会话正在注销，协程直接结束；否则关闭本轮的管道与事件句柄，等待一秒后重新拉起 UI。

第三段是隧道跟踪。`watchNewTunnelServices()` 先订阅服务数据库变化，再调用 `trackExistingTunnels()` 扫描配置目录中的每个名字，打开对应服务并 `go trackTunnelService()`。`trackTunnelService()` 先做 20 次、每次 200 毫秒的轮询，等待服务离开 `Stopped`；若超时仍停着，就检查服务是否被标记删除或启动类型是否为 `SERVICE_DISABLED`，是则删除服务、释放驱动适配器并广播 `TunnelStopped`。随后 `trackService()` 订阅状态变化，回调里把 SCM 状态映射为 `TunnelState`，状态变化时更新 `trackedTunnels`、在停止时 `releaseDriverAdapter()`、并 `IPCServerNotifyTunnelChange()` 广播。若服务停止且退出码表示错误，还会删除服务，避免“坏配置永远卡在列表里”。

第四段是停止。收到 `svc.Stop` 或 `quitManagersChan` 后，服务发送 `StopPending`，把 `stoppingManager` 置真，调用 `IPCServerNotifyManagerStopping()` 通知 UI 退出，遍历 `procs` 逐个 `Kill()`，等待所有孵化协程结束；如果是通过 `Quit` 触发的，还会调用 `UninstallManager()` 删除服务。这里有一个容易忽略的顺序：先通知再 kill，给 UI 一个体面退出的窗口；如果先 kill，UI 可能来不及保存窗口状态。

安装与卸载路径相对独立。`InstallManager()` 打开 `WireGuardManager`，若已存在且正在运行则返回 `ErrManagerAlreadyRunning`（`StartPending` 例外，视为他人正在启动）；若已停止则先删除再重建，并轮询等待 `ERROR_SERVICE_MARKED_FOR_DELETE` 消失。`InstallTunnel()` 的逻辑类似，但多了一步“已存在且非停止则报错”，并在创建后 `go trackTunnelService(name, service)` 把句柄交给跟踪器。`UninstallTunnel()` 先 `Control(svc.Stop)` 再 `Delete()`，对“已标记删除”做容错。

### 5. 配置/命令/代码实例

本模块最典型的“配置”不是 `.conf` 键，而是服务与注册表策略。下面只列四条常用命令/策略，完整开关与服务命令见 04-04、04-06、04-07。

```powershell
wireguard.exe /installmanagerservice
wireguard.exe /installtunnelservice C:\ProgramData\WireGuard\Office.conf
sc.exe query WireGuardManager
sc.exe query "WireGuardTunnel$Office"
```

注册表侧的受限 UI 开关为 `HKLM\Software\WireGuard\LimitedOperatorUI`（DWORD 1），它决定非管理员但属于 Network Configuration Operators 的用户是否能看到并操作 UI。该键的完整语义、ACL 要求与卸载清理见 04-07。

服务状态查询的示例输出如下，字段格式需对照实际 Windows 版本核验。

```text
SERVICE_NAME: WireGuardManager
        TYPE               : 10  WIN32_OWN_PROCESS
        STATE              : 4  RUNNING
                                (STOPPABLE, NOT_PAUSABLE, ACCEPTS_SHUTDOWN)
        WIN32_EXIT_CODE    : 0  (0x0)
        SERVICE_EXIT_CODE  : 0  (0x0)
        CHECKPOINT         : 0x0
        WAIT_HINT          : 0x0

SERVICE_NAME: WireGuardTunnel$Office
        TYPE               : 10  WIN32_OWN_PROCESS
        STATE              : 4  RUNNING
                                (STOPPABLE, NOT_PAUSABLE, ACCEPTS_SHUTDOWN)
        WIN32_EXIT_CODE    : 0  (0x0)
        SERVICE_EXIT_CODE  : 0  (0x0)
```

判读要点如下。第一，`TYPE` 为 `10 WIN32_OWN_PROCESS` 表示服务在自己的进程里运行，而不是共享 `svchost`；这与 `InstallTunnel()` 设置的 `SERVICE_WIN32_OWN_PROCESS` 一致。第二，`STATE` 为 4 表示 `RUNNING`，但“服务在运行”不等于“隧道已握手”：握手状态要用 `wg show` 查，服务状态只说明进程没有退出。第三，`WIN32_EXIT_CODE` 与 `SERVICE_EXIT_CODE` 要分开看：前者是 Win32 错误码，后者是服务自定义错误码；`trackTunnelService()` 正是先看 `ERROR_SERVICE_SPECIFIC_ERROR`，再读 `ServiceSpecificExitCode` 并映射为 `services.Error`。第四，如果 `STATE` 是 1（`STOPPED`）而 `WIN32_EXIT_CODE` 非零，通常意味着启动阶段失败，例如配置解析失败、适配器创建失败或驱动加载失败，应结合 `wireguard /dumplog` 定位。第五，隧道服务名必须带 `$`，在 PowerShell 中要用引号包住，否则 `$Office` 会被当作变量展开，这是运维脚本里最常见的低级错误。

从代码角度，UI 孵化阶段最关键的两步是“注册 IPC 服务端”和“导出日志映射句柄”，顺序不能颠倒：

```go
IPCServerListen(ourReader, ourWriter, ourEvents, elevatedToken)
theirLogMapping, err := ringlogger.Global.ExportInheritableMappingHandle()
if err != nil {
    log.Printf("Unable to export inheritable mapping handle: %v", err)
    return
}
```

`IPCServerListen()` 必须在 UI 启动前完成，否则 UI 连上管道时服务端还没准备好，首帧状态可能丢失；`ExportInheritableMappingHandle()` 必须在 `CreateProcessAsUser()` 之前调用，否则子进程拿不到日志共享内存，日志页会一直为空。两者都依赖前面创建的管道与全局 `ringlogger.Global`，因此 `InitGlobalLogger()` 的失败必须被视为致命错误。

### 6. 注意事项、陷阱与最佳实践

- **不要手工 `sc create` 隧道服务**。`InstallTunnel()` 除了创建服务，还设置了依赖、服务 SID、启动类型，并在创建后把句柄交给跟踪器；手工创建容易漏掉 `SERVICE_SID_TYPE_UNRESTRICTED` 或依赖项，表现为隧道能启动但网络配置异常。
- **受限 UI 不是“只读 UI”**。受限操作员可以启动、停止隧道，也可以查看配置（敏感字段会被 `Redact()`），但不能创建、删除、退出管理服务或触发更新。给运维账号授权时，要明确这是“可启停”而不是“可改配置”。
- **配置相交会被自动停隧道**。`Start()` 用 `IntersectsWith()` 判断地址重叠，重叠的隧道会被异步停止；如果业务依赖两条隧道同时存在，应把地址段规划成不重叠，而不是反复重试启动。
- **“僵尸隧道”来自状态竞态**。`trackTunnelService()` 会在停止后重试停止仍在 `Started/Starting` 的隧道，并删除启动失败的服务；如果看到隧道列表里反复出现又消失，应查日志中的 `Trying again to stop zombie tunnel` 与退出码。
- **UI 被 kill 是设计行为**。管理服务停止或用户注销时，`procs` 中的 UI 会被 `TerminateProcess`；这不是崩溃，不要把它当成故障。真正需要关注的是 `STATUS_DLL_INIT_FAILED_LOGOFF` 之外的异常退出码。
- **会话 0 没有 UI**。`WTSEnumerateSessions()` 只处理 `WTSActive` 与 `WTSDisconnected`，服务会话不会被孵化；在无人登录的服务器上，隧道仍由服务运行，但托盘与窗口不存在，这是正常的。
- **gob 兼容性有版本边界**。IPC 的方法类型与结构体字段通过 `gob` 编码，跨版本混用（旧 UI 连新 manager）可能解码失败；升级时应整体替换 `wireguard.exe`，不要只替换其中一部分。
- **事件管道可能阻塞**。`notifyAll()` 给每次写设置 1 秒 deadline，并用 `eventLock` 串行化；如果某个 UI 长时间不读，事件会被丢弃而不是无限堆积。排障时若发现 UI 状态“卡住”，先看 UI 是否还在响应，而不是怀疑 manager 没发通知。
- **不要在隧道运行时改服务命令行**。`changeTunnelServiceConfigFilePath()` 只在配置迁移时改 `BinaryPathName`，并且会校验参数个数与可执行文件路径；手工改命令行会让跟踪器与配置名对不上，出现“服务在跑但列表里没有”的错位。

### 7. 小结与延伸阅读

`manager` 是整套客户端的中枢：它把“服务安装、会话枚举、UI 孵化、IPC、隧道跟踪、更新触发”收拢到一个 LocalSystem 进程里，用令牌判定区分管理员、受限操作员与普通用户，用服务通知而不是轮询来感知隧道状态，用 gob 管道把控制面与界面解耦。读这个模块时，建议抓住三条线：服务名与生命周期、令牌与权限、状态机与通知。只要这三条线清楚，看到任何“UI 不显示隧道”“服务在跑但连不上”“启动一个隧道另一个被停掉”的现象，都能快速定位到对应函数。

延伸阅读建议：先看 04-04 与 04-06 熟悉 `/installmanagerservice`、`/installtunnelservice`、`sc` 的用法，再看 04-07 理解 `LimitedOperatorUI` 的边界，然后读 06-10 掌握会话枚举与 `CreateProcessAsUser` 的完整机制，最后对照 05-09 的 IPC 与错误码字段。若要动手实验，可以在测试机上有意创建一个地址相交的隧道，观察 `IntersectsWith()` 触发的自动停止，再结合 `wireguard /dumplog` 验证状态通知的顺序。

## 07-09 `ui` 图形界面与配置编辑器模块

### 1. 背景与动机

`ui` 是 wireguard-windows 的门面，但它不是“必需组件”。隧道服务可以在无人登录的服务器上独立运行，`wg` 与 `wireguard.exe` 也能完成大部分运维动作；UI 的职责是把“隧道列表、状态、配置编辑、日志、更新”这些控制面操作做得可发现、可理解、可纠错。也正因为它不是数据面，UI 进程以普通用户权限运行，只有在需要写配置或管理服务时才通过 IPC 请求 manager 代劳；管理员登录时，manager 会用提升令牌启动 UI，普通用户则只能看到被 `Redact()` 过的只读视图。

界面库选择的是 `github.com/lxn/walk`，一个对 Win32 公共控件做 Go 封装的库。它决定了代码的组织方式：窗口是 `walk.FormBase` 的嵌入，控件通过 `walk.New*` 创建，布局用 `GridLayout`/`VBoxLayout`，事件用 `Attach()` 挂回调。这套 API 不像 Web 前端那样有虚拟 DOM，控件就是真实的 HWND，因此跨线程更新必须走 `Synchronize()`，否则会触发 Win32 的线程亲和性错误。阅读 `ui` 包时，看到大量 `mtw.Synchronize(func(){...})` 不是冗余，而是必须。

UI 的结构是“一个主窗口 + 三个标签页 + 一个托盘图标”。主窗口的关闭按钮默认不是退出，而是“关闭到托盘”；只有托盘菜单里的 Exit 才真正结束进程（并且在管理员场景下会顺带退出 manager）。这个行为对普通用户友好，对运维脚本却不友好：用 `Stop-Process` 强杀 UI 不会停止隧道，因为隧道活在服务里；反过来，停止 manager 会导致所有会话的 UI 被 kill。理解这个生命周期，才能正确判断“界面消失”到底意味着什么。

本模块还要处理几类“非理想输入”：用户从网上复制来的 `.conf` 可能带 BOM、CRLF、未知编码；可能一次拖入多个 `.conf` 或一个 `.zip`；可能名字与已有隧道冲突；可能在编辑框里写错一个 Base64 字符。UI 不能替用户猜，但必须在不崩溃的前提下给出可定位的错误。配置编辑器因此不是简单的多行文本框，而是带语法高亮、字段校验、私钥联动与 kill-switch 复选框的专用控件。

### 2. 核心概念

**主窗口与会话**。`ManageTunnelsWindow` 嵌入 `walk.FormBase`，持有 `TabWidget`、`TunnelsPage`、`LogPage`、可选的 `UpdatePage`，以及一个 `manager.TunnelChangeCallback`。窗口类名是 `WireGuard UI - Manage Tunnels`，注册时同时注册 `TaskbarButtonCreated` 消息，用于在任务栏按钮创建后设置进度与叠加图标。`NewManageTunnelsWindow()` 里把 `Closing()` 事件改为“取消关闭 + 隐藏/最小化”，这是“关闭到托盘”的实现点。

**隧道列表与详情**。`TunnelsPage` 由工具栏、`ListView` 与 `ConfView` 组成。`ListView` 的模型是 `ListModel`，列包括名称、状态、接收/发送流量等；`StyleCell()` 根据状态给行上色，`onTunnelChange()` 在状态变化时刷新对应行。`ConfView` 是右侧详情面板，内部把 `[Interface]` 与每个 `[Peer]` 映射成 `interfaceView`/`peerView`，每个字段是一行 `labelTextLine`，状态行是 `labelStatusLine`，底部还有一个 `toggleActiveLine` 用于启动/停止。`apply()` 负责把 `conf.Interface`/`conf.Peer` 的值填进控件，`SetTunnel()` 负责切换当前展示对象。

**配置编辑器**。`EditDialog` 由名称输入框、只读公钥框、`syntax.SyntaxEdit`、kill-switch 复选框、保存/取消按钮组成。新建隧道时 `conf.NewPrivateKey()` 生成私钥并套默认模板；编辑已有隧道时从 `tunnel.StoredConfig()` 取配置。`syntaxEdit.SetText(dlg.config.ToWgQuick())` 把结构体序列化成 wg-quick 风格文本，保存时再解析回 `conf.Config` 并交给 manager。这个“结构体 → 文本 → 结构体”的往返是编辑器的核心契约，任何序列化/解析不一致都会表现为“保存后配置变了”。

**语法高亮与校验**。`ui/syntax/highlighter.go` 是从 wireguard-tools 的 C 版 highlighter 直接翻译来的状态机。它逐字符扫描，识别段名、字段名、私钥/公钥/预共享密钥、IP、CIDR、主机名、端口、MTU、keepalive、注释、分隔符、`Table`、脚本命令与错误。每个值类型都有独立的校验函数：`isValidKey()` 检查 44 字符 Base64 与末字符集合，`isValidIPv4()`/`isValidIPv6()` 检查地址，`isValidEndpoint()` 处理 `[IPv6]:port` 与主机名，`isValidMTU()` 限定 576 至 65535，`isValidTable()` 接受 `off`/`auto`/`main`/整数。它只是“输入提示”，不是权威解析器；真正的合法性仍由 `conf` 包在保存时判定。

**kill-switch 复选框**。`blockUntunneledTrafficCB` 的提示文本明确写了触发条件：恰好一个 peer、该 peer 的 `AllowedIPs` 至少包含 `0.0.0.0/0` 或 `::/0`、且接口没有 `Table=off`。复选框不是独立配置键，它通过改写 `AllowedIPs` 实现：勾选时把 `0.0.0.0/0` 与 `::/0` 写入，取消时改写成 `0.0.0.0/1 + 128.0.0.0/1` 与 `::/1 + 8000::/1`。`onBlockUntunneledTrafficCBCheckedChanged()` 与 `onBlockUntunneledTrafficStateChanged()` 负责双向同步，`syntaxedit.go` 里的 `evaluateUntunneledBlocking()` 根据当前文本推断复选框三态。

**导入与导出**。`importFiles()` 支持 `.conf` 与 `.zip`：`.conf` 直接读文本，`.zip` 遍历条目并只取 `.conf`；随后按名称排序、检查重名、用 `conf.FromWgQuickWithUnknownEncoding()` 解析、再 `manager.IPCClientNewTunnel()` 保存。`exportTunnels()` 则把所有选中隧道的 `StoredConfig().ToWgQuick()` 写进一个 zip，每个条目名为 `<tunnel>.conf`。注意导出的是明文私钥，文件落盘位置与访问权限需要用户自己负责。

**托盘**。`Tray` 包装 `walk.NotifyIcon`，菜单包含状态行、地址行、隧道切换项、管理窗口、导入、关于与退出。`onTunnelsChange()` 重建隧道动作，`onTunnelChange()` 更新状态与图标，`updateGlobalState()` 在“有隧道启动/停止中”时切换忙状态。托盘是 UI 的常驻入口，也是“关闭窗口后还能回来”的关键。

**本地化与图标**。所有面向用户的字符串都走 `l18n.Sprintf()`，语言由 `GetUserPreferredUILanguages()` 与 `message.DefaultCatalog` 匹配；图标来自 `ui/icon/` 下的 SVG 源与编译进资源的 ico，`iconprovider.go` 提供 `iconForState()`、`iconWithOverlayForState()`、`textForState()`。状态文案与图标必须成对维护，否则会出现“图标是绿的、文字说已停止”的不一致。

`RunUI()` 的启动顺序是“先窗口、后托盘、再订阅”。它先 `runtime.LockOSThread()` 把 goroutine 绑到主线程，降低进程优先级提升，然后循环调用 `NewManageTunnelsWindow()` 直到成功（失败间隔 400 毫秒），再循环创建 `Tray`；在 Windows Server Core 上没有托盘时，`version.OsIsCore()` 为真，托盘创建失败会被接受，`noTrayAvailable` 置真。接着注册 `manager.IPCClientRegisterManagerStopping()`，在 manager 停止时让 UI `walk.App().Exit(0)`；注册更新通知回调，并主动拉一次 `IPCClientUpdateState()` 以补齐启动前的状态。最后 `mtw.Run()` 进入消息循环，退出时销毁托盘与窗口。

隧道列表的刷新由两条路径驱动。第一条是 `IPCClientRegisterTunnelChange(mtw.onTunnelChange)`：manager 每次广播 `TunnelChangeNotificationType`，客户端解码出隧道名、状态、全局状态与错误字符串，回调里 `Synchronize()` 到 UI 线程，更新任务栏进度、弹出隧道错误提示；`ListView` 与 `Tray` 也各自注册了回调，形成“一个事件、多处更新”。第二条是 `IPCClientRegisterTunnelsChange`：当配置增删导致列表结构变化时，`TunnelsPage.onTunnelsChanged()` 与 `Tray.onTunnelsChange()` 重新拉取 `IPCClientTunnels()` 并重建控件。

`runEditDialog()` 是对话框的对外入口：`newEditDialog()` 创建控件并填充初始文本，`dlg.Run()` 进入模态循环，用户点保存时 `onSaveButtonClicked()` 解析文本、校验名称与字段、把结果写回 `dlg.config`，最后返回 `DlgCmdOK`。`TunnelsPage.onAddTunnel()` 与 `onEditTunnel()` 拿到返回的 `*conf.Config` 后，分别调用 `addTunnel()`（内部 `IPCClientNewTunnel`）或 `IPCClientSetTunnel` 一类的更新接口；具体方法名随版本可能不同，需对照 `manager/ipc_client.go` 与实际版本核验。若用户取消，返回 `nil`，调用方不做任何写入。

导入流程值得单独看。`importFiles()` 在后台 goroutine 中执行，所有 UI 操作都通过 `tp.Synchronize()` 回到主线程；它先按扩展名分流，`.zip` 用 `zip.OpenReader()` 遍历，读取每个 `.conf` 的字节并保留文件名（去掉扩展名）作为候选隧道名。解析阶段用 `conf.FromWgQuickWithUnknownEncoding()`，这个函数会处理 BOM 与常见编码；保存阶段用 `manager.IPCClientNewTunnel()`，由 manager 决定最终路径与 DPAPI 加密。导入结束后根据成功数 `m` 与总数 `n` 给出四种提示：单个失败、单个成功、全部成功、部分成功，这比“导入失败”四个字有用得多。

日志页与托盘是两条旁路。`LogPage` 使用 `logModel` 定时从 manager 的共享环形日志读取增量（原理见 06-11），`isAtBottom()` 决定是否自动滚动，`onCopy()`/`onSelectAll()`/`onSave()` 提供复制、全选、另存。`Tray` 则把 `IPCClientTunnels()` 的结果映射成菜单项，点击某一项时调用启动/停止，菜单文本与图标由 `textForState()`/`iconForState()` 统一生成。

### 5. 配置/命令/代码实例

UI 直接操作的配置键不多，最典型的是 `AllowedIPs`、`DNS`、`Table` 与 `Address`。下面的片段展示了“全隧道 + kill-switch 复选框生效”的形态，完整键集见 04-02、04-03。

```conf
[Interface]
PrivateKey = <客户端私钥>
Address = 10.7.0.2/32
DNS = 10.7.0.1

[Peer]
PublicKey = <服务端公钥>
AllowedIPs = 0.0.0.0/0, ::/0
# 其他键不在本篇展开，完整配置键见 04-02 与 04-03
```

如果用户在编辑器里取消“Block untunneled traffic (kill-switch)”，UI 会把两条 `/0` 改写成四条半区前缀，路由效果接近默认路由，但不会触发 WFP 的强限制。这个改写发生在文本层，用户再次打开编辑器时能看到 `0.0.0.0/1, 128.0.0.0/1` 等值，而不是一个隐藏开关。

UI 进程本身由 manager 以四个句柄启动，命令行形如 `/ui <reader> <writer> <events> <mapping>`。这四个参数不是给用户手工调用的，但排障时可以用进程命令行确认句柄是否成组出现：

```powershell
Get-CimInstance Win32_Process -Filter "Name = 'wireguard.exe'" |
    Where-Object { $_.CommandLine -match '/ui' } |
    Select-Object ProcessId, CommandLine
```

```text
ProcessId CommandLine
--------- -----------
  6124    "C:\Program Files\WireGuard\wireguard.exe" /ui 548 552 556 560
  7180    "C:\Program Files\WireGuard\wireguard.exe" /ui 620 624 628 632
```

判读要点如下。第一，每个交互会话应当有一个 `/ui` 进程；如果同一会话出现多个，可能是 UI 崩溃后被 manager 重新拉起，旧进程尚未完全退出。第二，四个数字是继承句柄的十进制表示，顺序固定为“读管道、写管道、事件管道、日志映射”；数值本身每次启动都会变化，不能用固定值判断。第三，若命令行只有 `/ui` 而没有四个参数，说明启动参数被截断或手工伪造，UI 会在初始化 IPC 时失败并退出。第四，`ProcessId` 与 `sc query WireGuardManager` 的进程号没有直接关系：manager 是服务进程，UI 是用户进程，二者通过管道通信而不是父子关系。第五，若在服务器上看到“没有 `/ui` 进程”，先确认是否有活动会话；会话 0 不会孵化 UI，这是设计行为而非故障。

日志页的内容来自共享环形日志，典型行如下（示例输出，具体格式需对照实际版本核验）：

```text
2026-11-12 09:41:02.118: [MGR] Starting WireGuard/1.1.1 (Windows 10.0.19045; amd64)
2026-11-12 09:41:02.204: [MGR] Starting UI process for user 'alice@WORKGROUP' for session 1
2026-11-12 09:41:03.887: [TUN] [Office] Starting WireGuard/1.1.1 (Windows 10.0.19045; amd64)
```

这三行分别对应管理服务启动、UI 孵化、隧道服务启动；`[MGR]`、`[TUN]` 是 ringlogger 的 tag，方括号后是消息体。若 UI 日志页只有第一行而没有第二行，说明 manager 没有为当前会话拉起 UI；若第二行存在但界面仍空白，问题更可能在 IPC 连接或窗口初始化，而不是日志本身。

### 6. 注意事项、陷阱与最佳实践

- **关闭窗口不等于退出**。主窗口的 `Closing()` 被改写为隐藏或最小化，真正退出要走托盘 Exit；用任务管理器结束 UI 不会停止隧道，反而会让 manager 在一秒后重新拉起一个新的 UI。
- **不要在非 UI 线程直接改控件**。Walk 控件有线程亲和性，所有来自 IPC 回调的更新都必须 `Synchronize()`；自己写扩展时若省略这一步，轻则界面不刷新，重则进程崩溃。
- **高亮不是解析器**。`highlightConfig()` 会把非法值标红，但它不构建 `conf.Config`，也不做跨字段校验（例如同一 peer 是否重复、AllowedIPs 是否与接口地址冲突）。保存时的错误以 `conf` 包为准，不要因为“没红线”就认为一定能保存。
- **导入的编码与重名**。`.conf` 可能带 BOM 或 UTF-16，`FromWgQuickWithUnknownEncoding()` 会尝试处理；重名检查是大小写不敏感的，`Office` 与 `office` 会被视为冲突。批量导入时部分成功是正常结果，提示会给出成功数与总数。
- **导出包含私钥**。`exportTunnels()` 写出的是 `ToWgQuick()` 的明文，包含 `PrivateKey` 与 `PresharedKey`；导出的 zip 应放在受控目录，传输后及时删除，不要放进公共网盘。
- **受限 UI 的能力差异**。非管理员且不属于 Network Configuration Operators 的用户看不到 UI；受限操作员能看到并启停，但保存、删除、退出等按钮会因 IPC 返回 `ERROR_ACCESS_DENIED` 而失败。这是权限设计，不是界面 bug。
- **编辑运行中的隧道需要重启**。保存配置只写入存储，已运行的隧道服务不会自动重载；要让新配置生效，需要在界面上停止再启动，或由 manager 重新安装服务。
- **Core 版本没有托盘**。`version.OsIsCore()` 为真时托盘创建失败会被接受，窗口以最小化方式存在；不要在没有托盘的机器上教用户“点右下角图标”。
- **日志页不是无限历史**。它读的是固定容量的环形缓冲（容量与格式见 07-10），长时间运行后早期日志会被覆盖；需要长期留存时应在问题发生时及时“另存为”。

### 7. 小结与延伸阅读

`ui` 包把 Win32 控件、配置模型、IPC 通知与本地化粘在一起，形成一条“看得见”的控制面。它的设计重点不在视觉，而在契约：`conf.Config` 与 wg-quick 文本之间的往返必须稳定，kill-switch 复选框必须与 `AllowedIPs` 的改写严格对应，IPC 回调必须回到 UI 线程，导入导出必须对文件名、编码与重名有明确策略。掌握这四个契约，读代码时就不会被大量控件创建语句淹没。

延伸阅读建议：先看 04-02、04-03 熟悉编辑器里出现的配置键，再看 05-09 核对 `ConfView`/`EditDialog` 涉及的字段，然后读 06-10 理解 UI 进程如何被 manager 孵化，最后对照 `ui/syntax/highlighter.go` 与 wireguard-tools 的 `highlighter.c` 看状态机差异。若要做二次开发，建议从 `LogPage` 或 `Tray` 这类边界清晰的组件入手，避免一上来就改 `ConfView` 的布局与字段映射。

## 07-10 `ringlogger` 与 `services` 模块

### 1. 背景与动机

Windows 服务没有控制台。隧道服务与管理服务都以 LocalSystem 运行，既不能把日志写到某个用户的终端，也不适合为每条隧道维护一个无限增长的文本文件：全隧道长时间运行会产生大量握手、DNS、路由与错误日志，普通文件会持续膨胀，轮转又需要额外的文件锁与清理逻辑。wireguard-windows 的解法是一个固定容量的共享环形日志：所有进程把日志写进同一块内存映射区域，容量固定、写入 O(1)、旧日志自动被覆盖；需要查看时，用 `wireguard /dumplog` 把当前快照导出到标准输出，或用 `/tail` 持续跟随。

这套设计的目标不是“长期审计”，而是“故障现场”。它假设最有价值的日志是最近发生的那一段：隧道为什么没起来、握手为什么失败、服务为什么退出。因此容量被刻意限制为 2048 行、每行最多 512 字节，超出就覆盖最旧的一行；进程崩溃不会留下半截文件，也不会因为磁盘满而写失败。代价是早期日志会丢失，长期留存必须由外部采集负责。

`services` 包则是这套日志体系的“语义层”。它定义了一组稳定的错误码，把“打开日志失败、加载配置失败、创建适配器失败、启用防火墙失败、设置设备配置失败、绑定默认路由失败、监控 MTU 失败、设置网络配置失败、丢弃特权失败、执行脚本失败”等阶段映射为可枚举的 `Error`，并提供 `DetermineErrorCode()` 把 Go 错误转换成 Windows 服务的退出码。没有这一层，事件查看器里只会看到一个笼统的 `1066` 或一个 Win32 数字，排障无法定位到阶段。

两个包经常一起出现：服务启动时先 `ringlogger.InitGlobalLogger()`，失败就返回 `services.ErrorRingloggerOpen`；随后每个阶段失败都设置对应的 `serviceError`，`Execute()` 的 defer 再统一计算退出码并写日志。理解这条“日志初始化 → 阶段错误 → 退出码”的链路，才能读懂 `sc query` 里的 `SERVICE_EXIT_CODE` 与 `/dumplog` 里的最后几行。

### 2. 核心概念

**环形缓冲的物理布局**。`logMem` 是映射文件的根结构：`magic` 是魔数 `0xbadbabe`，用于判断这块内存是否已初始化；`nextIndex` 是全局递增的写入序号；`lines` 是 2048 个 `logLine` 的数组。每个 `logLine` 由 `timeNs int64` 与 `line [512]byte` 组成。写入时用 `atomic.AddUint32(&nextIndex, 1) - 1` 取得序号，再对 2048 取模定位槽位；读取时从 `nextIndex` 往前推 2048 个槽位，按序号顺序输出。因为序号只增不减，读者可以判断“哪些行是新的、哪些已经被覆盖”。

**单行的编码**。写入前会先 `bytes.TrimSpace()`，空行直接返回；然后计算 `textLen = 3 + len(p) + len(tag)`，其中 3 是 `[`、`]`、空格三个字节。若超长，就把正文截断到 `maxLogLineLength - 1 - 3 - len(tag)`，保证末尾仍有 NUL。写入顺序是“先清零、写 tag、写右括号与空格、写正文、最后写左括号与时间戳”，源码注释说明这是为了让读者在时间戳非零之前看不到半截行。这个细节决定了并发读到的要么是完整行，要么是“时间戳为 0 的空槽”，不会出现拼接错乱。

**tag 与容量**。`maxTagLength` 为 5，管理服务用 `MGR`，隧道服务用 `TUN`，dump 进程用 `DMP`；超过 5 个字符会返回 `ERROR_LABEL_TOO_LONG`。`maxLines` 为 2048，意味着所有进程共享同一个 2048 行窗口，而不是每个进程 2048 行。多条隧道同时运行时，日志会交错出现，必须靠 tag 与隧道名区分。

四个核心常量决定了这套日志的“分辨率”，如下表所示。

| 常量 | 值 | 作用 |
|---|---:|---|
| `maxLogLineLength` | 512 | 单行字节上限，含 tag 与分隔符 |
| `maxTagLength` | 5 | tag 最大长度，MGR/TUN/DMP |
| `maxLines` | 2048 | 环形槽位总数，全局共享 |
| `magic` | `0xbadbabe` | 映射初始化标记 |

为什么要同时限制行数与行长？行数决定“能回看多久”，行长决定“单条消息能说清多少”。如果只限行数不限长度，一条超长错误栈就会挤掉几十条握手日志；如果只限长度不限行数，文件会随运行时间无限增长。512 与 2048 的组合是经验值：它足够容纳一次启动序列与若干次握手失败，又不会让共享内存大到影响映射成本。代价是长消息被截断、早期日志被覆盖，这两点在排障时必须主动补偿。

**共享与继承**。`NewRinglogger()` 以 `os.O_RDWR|os.O_CREATE` 打开文件，权限 `0600`，把文件截断到 `unsafe.Sizeof(logMem{})`，再 `CreateFileMapping()` 建立映射；`NewRingloggerFromInheritedMappingHandle()` 则从十进制句柄字符串恢复一个只读视图，供 UI 进程使用。`ExportInheritableMappingHandle()` 重新以 `PAGE_READONLY` 打开同一文件映射，并设置 `HANDLE_FLAG_INHERIT`，这样 manager 可以把句柄放进 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` 传给 UI，而不需要 UI 有权限打开日志文件。

**读写 API**。`Write()` 取当前时间后调用 `WriteWithTimestamp()`；`WriteTo()` 按顺序输出全部有效行，格式为 `2006-01-02 15:04:05.000000: [TAG] message`；`FollowFromCursor()` 从游标开始增量读取，`CursorAll` 表示“从最旧的有效行开始”；`DumpTo()` 封装了“打开文件 → 映射 → 只读视图 → 全量或持续输出”的完整流程，持续模式每 100 毫秒轮询一次。

**全局 logger 与运行时挂钩**。`InitGlobalLogger(file, tag)` 创建 `Global`，调用 `log.SetOutput(Global)` 与 `log.SetFlags(0)`，并通过 `//go:linkname overrideWrite runtime.overrideWrite` 把标准库的底层写函数替换为 `globalWrite`。这样即使某处直接调用了运行时或标准库的写日志路径，也会被汇入环形缓冲；`globalWrite` 用 `//go:nosplit` 保证在不可抢占的上下文中也能工作。

**services 错误枚举**。`services.Error` 是 `uint32` 枚举，从 `ErrorSuccess` 开始，依次包括 `ErrorRingloggerOpen`、`ErrorLoadConfiguration`、`ErrorCreateNetworkAdapter`、`ErrorDNSLookup`、`ErrorFirewall`、`ErrorDeviceSetConfig`、`ErrorDeviceBringUp`、`ErrorBindSocketsToDefaultRoutes`、`ErrorMonitorMTUChanges`、`ErrorSetNetConfig`、`ErrorDetermineExecutablePath`、`ErrorTrackTunnels`、`ErrorEnumerateSessions`、`ErrorDropPrivileges`、`ErrorRunScript`、`ErrorWin32`。每个值都有对应的英文描述，`Error()` 方法把这些描述暴露给日志与 UI。

**退出码计算**。`DetermineErrorCode(err, serviceError)` 先看 `err` 是否可转换为 `windows.Errno`：是则返回 `(false, uint32(syserr))`，表示“不是服务特定错误”；否则若 `serviceError` 非 `ErrorSuccess`，返回 `(true, uint32(serviceError))`；两者都没有则返回 `(false, NO_ERROR)`。`CombineErrors()` 则把阶段错误与底层错误合并成一条链式错误，供日志使用。`svc.Run` 会根据第一个返回值决定 `SERVICE_EXIT_CODE` 还是 `WIN32_EXIT_CODE`，这就是 `sc query` 中两个退出码字段的来源。

**启动原因**。`services.StartedAtBoot()` 用 `svc.IsWindowsService()` 与 `svc.DynamicStartReason()` 判断本次启动是否由 `StartReasonAuto` 或 `StartReasonDelayedAuto` 触发，并把结果缓存；`PrintStarting()` 据此在日志里打印 “Starting at boot ...”。这不是装饰：开机自启与手动启动的失败模式不同，前者常与依赖服务未就绪有关。

### 3. 关键数据结构与源码位置

`ringlogger/` 只有三个文件，但每个都承担不同角色：

- `ringlogger.go`：常量与结构体（`maxLogLineLength`、`maxTagLength`、`maxLines`、`magic`、`logLine`、`logMem`、`Ringlogger`）、构造与映射（`NewRinglogger()`、`NewRingloggerFromInheritedMappingHandle()`、`newRingloggerFromMappingHandle()`）、读写（`WriteWithTimestamp()`、`WriteTo()`、`FollowFromCursor()`）、关闭与句柄导出（`Close()`、`ExportInheritableMappingHandle()`）。
- `dump.go`：`DumpTo(inPath, out, continuous)`，把“文件路径 + 输出流 + 是否持续”封装成一条命令可调用的路径。
- `global.go`：`Global`、`InitGlobalLogger()`、`globalWrite()` 与 `runtime.overrideWrite` 挂钩。

`services/` 只有两个文件：

- `errors.go`：`Error` 枚举、`Error()` 文案、`DetermineErrorCode()`、`CombineErrors()`。
- `boot.go`：`StartedAtBoot()`、`PrintStarting()`。

需要澄清一个文件名问题：本仓库快照的 `ringlogger/` 下没有 `ringlogger_windows.go`，Windows 相关逻辑直接写在 `ringlogger.go` 里，通过 `golang.org/x/sys/windows` 调用；如果读者手上的版本存在该文件，应以实际版本为准。字段的完整定义、内存布局与读写时机见 05-09，本篇不重复字段表。

### 4. 关键流程与调用链

日志的写入与读取是两条独立路径，整体关系见图 07-10-01。

:::figure id=07-10-01 | name=环形日志的写入与导出路径 | dir=TD
node n1 "log.Printf" blue
node n2 "globalWrite 缓冲" teal
node n3 "WriteWithTimestamp" amber
node n4 "logMem 2048 行" purple
node n5 "WriteTo 全量" gray
node n6 "FollowFromCursor" green
node n7 "DumpTo 与 /dumplog" red
edge n1 -> n2 "标准库输出"
edge n2 -> n3 "按行提交"
edge n3 -> n4 "原子序号定位"
edge n4 -> n5 "顺序遍历"
edge n4 -> n6 "游标增量"
edge n5 -> n7 "一次性快照"
edge n6 -> n7 "持续跟随"
edge n7 -> n4 dashed "只读映射"
:::

写入路径从 `log.Printf()` 开始。标准库把格式化后的字节写到 `Global`，`Ringlogger.Write()` 取 `time.Now().UnixNano()` 作为时间戳，转交 `WriteWithTimestamp()`。后者先拒绝只读视图（返回 `io.ErrShortWrite`），再 `TrimSpace`、判空，然后用原子自增拿到序号，定位到 `lines[index%2048]`。接着把 `timeNs` 置零、清空整行，计算并截断正文，按 `[`、tag、`]`、空格、正文的顺序写入，最后用 `atomic.StoreInt64` 写入时间戳。读者看到时间戳非零，才认为这一行有效。

读取路径分两种。`WriteTo()` 先读取 `nextIndex`，然后从 `(i+l)%maxLines` 遍历 2048 个槽位，跳过 `timeNs == 0` 的空槽，用 `bytes.IndexByte(line, 0)` 找到正文长度，按固定时间格式输出。`FollowFromCursor(cursor)` 则从调用方给的游标开始，最多遍历 2048 行；`CursorAll` 表示从最旧有效行开始，否则在遇到 `i%maxLines == nextIndex%maxLines` 时停止，避免把未写入的区域当成新日志。每读一行就更新 `nextCursor = i % maxLines`，调用方下次用它继续。

`DumpTo()` 把读取路径封装成 CLI 行为：以只读方式打开日志文件，`CreateFileMapping(PAGE_READONLY)`，构造 `DMP` tag 的 `Ringlogger`；非持续模式调用 `WriteTo(out)`，持续模式从 `CursorAll` 开始循环调用 `FollowFromCursor()`，每 100 毫秒睡眠一次，遇到 `io.EOF` 正常返回。`wireguard.exe /dumplog` 与 `/dumplog /tail` 最终都落到这里，区别只是 `continuous` 参数。

服务退出码路径与日志路径在 `Execute()` 的 defer 里汇合：`err` 是具体错误，`serviceError` 是阶段枚举，`DetermineErrorCode()` 决定 `svcSpecificEC` 与 `exitCode`，`CombineErrors()` 生成可读消息并 `log.Print`。如果 `err` 是 `windows.Errno`，退出码就是 Win32 码，`SERVICE_EXIT_CODE` 为 0；如果 `err` 不是系统错误而 `serviceError` 非零，则 `SERVICE_EXIT_CODE` 等于枚举值；两者都没有才是正常退出。这一区分对排障极其重要：看到 `SERVICE_EXIT_CODE: 5` 应查 `ErrorFirewall`，看到 `WIN32_EXIT_CODE: 5` 则应查 `ERROR_ACCESS_DENIED`。

### 5. 配置/命令/代码实例

`ringlogger` 没有用户可配的 `.conf` 键，日志路径由 `conf.LogFile()` 决定，通常位于 `%ProgramData%\WireGuard\Data\Logs\wireguard.log` 一类位置（具体路径需对照 `conf/path_windows.go` 与实际版本核验）。最典型的操作是三个命令，完整开关见 04-04、04-06。

```powershell
wireguard.exe /dumplog
wireguard.exe /dumplog /tail
sc.exe qc WireGuardManager
```

一次性导出的示例输出如下，时间格式与行内容需对照实际版本核验。

```text
2026-11-12 09:41:02.118: [MGR] Starting WireGuard/1.1.1 (Windows 10.0.19045; amd64)
2026-11-12 09:41:02.204: [MGR] Starting UI process for user 'alice@WORKGROUP' for session 1
2026-11-12 09:41:03.887: [TUN] [Office] Starting WireGuard/1.1.1 (Windows 10.0.19045; amd64)
2026-11-12 09:41:04.012: [TUN] [Office] Creating network adapter
2026-11-12 09:41:04.660: [TUN] [Office] Monitoring default routes
```

判读要点如下。第一，时间戳精确到微秒，格式固定为 `2006-01-02 15:04:05.000000`，便于按时间排序与对齐事件查看器。第二，`[MGR]` 与 `[TUN]` 是 tag，`[Office]` 是隧道名；同一秒内可能交错出现多条隧道，必须结合 tag 与隧道名阅读，不能只看行尾。第三，`Creating network adapter` 之后若没有 `Monitoring default routes`，说明适配器创建成功但后续网络配置失败，应结合 `SERVICE_EXIT_CODE` 判断是 `ErrorSetNetConfig` 还是 `ErrorMonitorMTUChanges`。第四，日志只有最近 2048 行，若隧道已运行很久，启动阶段的日志可能已被覆盖；要复现启动失败，应先停止再启动，然后立刻 dump。第五，`/tail` 是持续输出，适合在另一个窗口观察握手与路由变化，但它不会把历史行重新打印一遍（取决于游标策略），需要历史时先做一次全量 dump。

从代码角度，服务的日志初始化通常只有三行，但顺序不能错：

```go
logFile, err := conf.LogFile(true)
if err != nil {
    serviceError = services.ErrorRingloggerOpen
    return
}
if err := ringlogger.InitGlobalLogger(logFile, "TUN"); err != nil {
    serviceError = services.ErrorRingloggerOpen
    return
}
```

`conf.LogFile(true)` 的布尔参数表示“是否需要写权限/是否创建目录”，具体语义需对照 `conf/path_windows.go`；`InitGlobalLogger()` 在 `Global` 已存在时直接返回 nil，因此同一进程内重复调用是安全的，但不同 tag 不会生效——第一个初始化的 tag 会一直沿用。这也是为什么管理服务与隧道服务必须各自在自己的进程里初始化，而不能共享一个进程。

### 6. 注意事项、陷阱与最佳实践

- **环形日志会覆盖**。2048 行是全局共享容量，不是每进程、每隧道独立；多条隧道 + 长时间运行会快速冲掉早期日志。排障前先停掉无关隧道，或尽快 dump。
- **单行会被截断**。正文上限是 `512 - 1 - 3 - len(tag)`，超长消息会被截断而不是换行；打印大段配置或错误栈时，应分段输出，避免关键信息落在截断点之后。
- **tag 最长 5 字符**。自定义 tag 超过 5 会直接失败；这不是可调参数，源码里是常量。
- **时间戳是写入时间，不是事件发生时间**。高并发下 `time.Now()` 在取序号之前，可能出现“序号大但时间戳略小”的轻微乱序，源码注释已明确说明。对严格顺序有要求的场景，不要依赖时间戳排序。
- **只读视图不能写**。UI 持有的是 `FILE_MAP_READ` 映射，`WriteWithTimestamp()` 会返回 `io.ErrShortWrite`；如果 UI 侧出现写日志失败，先确认句柄来源，而不是怀疑磁盘权限。
- **日志文件权限是 0600**。`NewRinglogger()` 用 `os.OpenFile(..., 0o600)`，只有创建者可读写；共享靠继承句柄而不是放宽 ACL，不要为了“方便查看”把文件权限改成 Everyone。
- **`/tail` 可能看起来“没输出”**。持续模式每 100 毫秒轮询，若期间没有新行就不会打印；另外它从当前游标开始，历史行需要先全量 dump。
- **退出码要看两个字段**。`SERVICE_EXIT_CODE` 对应 `services.Error` 枚举，`WIN32_EXIT_CODE` 对应系统错误；把两者混为一谈会得到完全错误的排障方向。
- **同 tag 的多实例会混在一起**。同一台机器上如果跑了两条隧道，二者都用 `TUN`，只能靠消息里的 `[隧道名]` 区分；自定义嵌入服务若也写同一文件，建议使用独立 tag 或独立日志路径，否则现场会被无关日志淹没。
- **不要用日志判断服务是否“健康”**。日志只记录已发生的写操作，进程卡死、死锁或驱动阻塞时可能一条新日志都没有；健康检查应看 `sc query`、`wg show` 与实际的握手时间，而不是“最后一行日志离现在多久”。
- **日志不是审计**。它没有防篡改、没有持久化保证、没有序列号完整性校验；安全事件应依赖 Windows 事件日志与外部 SIEM，而不是环形缓冲。

### 7. 小结与延伸阅读

`ringlogger` 用一块固定大小的共享内存解决了“服务无控制台、日志不能无限增长、多进程要看到同一份现场”三个问题；`services` 用一组稳定枚举把“失败在哪个阶段”编码进退出码。两者合起来，构成了 Windows 客户端可运维性的底座：日志告诉你发生了什么，退出码告诉你发生在哪一步。读源码时抓住三个数字即可：2048 行、512 字节、5 字符 tag；再抓住两个函数：`WriteWithTimestamp()` 的原子写入与 `DetermineErrorCode()` 的退出码映射。

延伸阅读建议：先看 04-04 与 04-06 熟悉 `/dumplog`、`sc qc` 的用法，再看 05-09 核对 `logMem` 与 `Error` 枚举字段，然后读 06-11 理解共享内存与 IPC 的完整机制，最后结合 08-01 的日志采集实战，把 `/dumplog`、事件查看器与 `wg show` 组合成一套现场取证流程。

## 07-11 `updater` 与 `version` 模块

### 1. 背景与动机

桌面客户端的更新链是最容易被低估的攻击面：它要在无人值守的情况下下载一个可执行安装包，并以高权限运行。wireguard-windows 的选择是“只信任签名清单，不信任传输通道”：服务端用 signify 对文件清单做 Ed25519 签名，客户端用内置公钥验证签名，再从清单里取出对应架构 MSI 的 BLAKE2b-256，下载后做一次常量时间比较，最后交给 `msiexec` 静默安装。整个链路不依赖证书链、不依赖 HTTPS 作为唯一信任根，也不接受“服务器说是什么就是什么”。

`version` 包是这条链的“身份层”。它提供版本号 `Number`、架构名 `Arch()`、操作系统名 `OsName()`、User-Agent `UserAgent()`，以及两个“官方构建判定”：`IsRunningOfficialVersion()` 检查可执行文件的签名证书里是否包含 `WireGuard LLC`，`IsRunningEVSigned()` 检查证书策略里是否包含 EV 代码签名 OID。源码在 `official.go` 顶部用醒目注释说明：这些检查很容易被绕过，不承担安全职责，安全敏感逻辑不要放在这个文件里。理解这一点，才不会把“官方构建”误当成“可信执行环境”。

更新器还承担一个现实约束：它必须以足够高的权限运行，才能让 `msiexec` 完成 per-machine 安装。UI 进程通常是普通权限或提升权限，但不一定是 SYSTEM；manager 服务是 LocalSystem，可以 impersonate 到 SYSTEM 后执行安装。`DownloadVerifyAndExecute(userToken)` 因此有两种模式：`userToken == 0` 时用 `elevate.DoAsSystem()` 包住整个流程，非零时直接在调用者令牌下执行。这个参数决定了“谁在装”，也决定了失败时的权限错误形态。

对企业环境，更新器还提供了一个可编排的入口：`wireguard.exe /update` 可以由计划任务每日触发，配合 MSI 的 `DO_NOT_LAUNCH` 属性可以做到“只更新、不弹 UI”。这意味着更新链不仅要正确，还要能在没有交互、没有托盘、甚至没有登录会话的机器上跑通。`updater` 的很多设计（临时文件、静默参数、进度通道）都是为这个场景服务的。

### 2. 核心概念

**签名清单**。更新服务器上的 `latest.sig` 是一个 signify 格式的签名文件：第一行是 `untrusted comment: ...`，第二行是 Base64 签名，第三行是被签名的文件清单。`readFileList()` 先 Base64 解码内置公钥，检查长度等于 `ed25519.PublicKeySize + 10` 且前两字节是 `Ed`（signify 的公钥类型标识），再检查签名长度与 keyid 前缀，最后 `ed25519.Verify()`。清单每行形如 `<hex BLAKE2b-256>  <filename>`，用两个空格分隔；解析后得到 `fileList`，即文件名到 32 字节哈希的映射。

**候选选择**。`findCandidate()` 用 `msiArchPrefix`（`wireguard-%s-`）与 `msiSuffix`（`.msi`）过滤，`%s` 来自 `version.Arch()`：`amd64`、`x86`、`arm64`（`386` 映射为 `x86`，`arm`/`arm64` 原样）。文件名去掉前后缀后就是版本字符串，长度超过 128 直接报错。`versionNewerThanUs()` 按点分段，每段用 `ParseUint(..., 10, 16)` 限制在 16 位内，逐段比较；候选段多于本地时，多出的段视为本地 0，反之亦然。这个比较是纯数字的，不处理 `-beta` 之类的后缀，遇到非数字段会返回“Invalid version integer part”。

**下载与校验**。`checkForUpdate(true)` 建立 WinHTTP 会话，`Connect(download.wireguard.com, 443, true)`，`GET /windows-client/latest.sig`，用 `io.LimitReader` 限制清单最大 512 KiB。`DownloadVerifyAndExecute()` 再 `GET /windows-client/<name>` 下载 MSI，限制 100 MiB，用 `io.TeeReader` 同时写文件和算 BLAKE2b-256；下载完成后 `subtle.ConstantTimeCompare()` 与清单哈希比较，失败即报“wrong hash”。

为什么用 `updater/winhttp` 而不是 Go 标准库的 `net/http`？源码给出的实现是一个围绕 WinHTTP 的薄封装：`NewSession(version.UserAgent())`、`Connect(host, port, useHttps)`、`Get(path, redirect)`、`Response.Length()`。从可观察行为看，它复用了系统的代理配置、证书存储与 HTTP 栈，这对企业环境很重要——很多公司的出站流量必须经过代理，而代理设置往往只配置在 WinHTTP/WinINet 层。代价是行为受系统策略影响，排障时不能只用 `curl` 验证，必须同时检查 WinHTTP 代理与 TLS 信任链。这一设计取舍的具体历史原因需对照上游提交与文档核验，本篇只描述可验证的调用面。

**临时文件的安全属性**。`msiTempFile()` 生成 32 字节随机数，文件名是 `%WINDIR%\Temp\<hex>`，用 `windows.CreateFile()` 以 `CREATE_NEW` 创建，安全描述符为 `O:SYD:PAI(A;;FA;;;SY)(A;;FR;;;BA)`：SYSTEM 完全控制，Administrators 只读。创建后调用 `MoveFileEx(..., MOVEFILE_DELAY_UNTIL_REBOOT)` 注册重启删除，作为异常退出时的兜底。`tempFile.ExclusivePath()` 会在交给 `msiexec` 前关闭句柄，因为 MSI 需要一个不共享的文件；`Delete()` 则根据句柄是否已关闭选择 `DeleteFile` 或 `SetFileInformationByHandle(FileDispositionInfo)`。

**执行**。`runMsi()` 取 `%SystemRoot%\System32\msiexec.exe`，参数固定为 `/qb!- /i <basename>`，工作目录设为临时文件所在目录，标准输入输出全部重定向到 `os.DevNull`，并通过 `syscall.SysProcAttr{Token: userToken}` 指定令牌。`/qb!-` 的含义是“基本 UI、无取消按钮”，既不是完全静默，也不给用户中途取消的机会；具体参数语义以 `msiexec` 文档与实际版本为准。

**进度通道**。`DownloadVerifyAndExecute()` 返回 `chan DownloadProgress`，容量 128。每个阶段都会发一条 `Activity`：`Initializing`、`Checking for update`、`Creating temporary file`、`Msi destination is ...`、`Downloading update`、`Installing update`，完成时发 `Complete: true`，出错发 `Error`。`progressHashWatcher` 实现 `io.Writer`，每写一块就累加 `BytesDownloaded` 并投递进度，同时把字节喂给哈希。`updateInProgress` 是 `uint32` 的 CAS 锁，保证同一时刻只有一个更新在跑。

**version 的身份信息**。`version.Number` 在快照中是 `1.1.1`；`Arch()` 把 Go 的 `GOARCH` 映射为 MSI 架构名；`OsName()` 通过 `RtlGetVersion()` 与 `ProductType` 拼出 `Windows Server 10.0.17763` 这类字符串，`OsIsCore()` 还会读 `ServerLevels` 判断 Server Core；`UserAgent()` 形如 `WireGuard/1.1.1 (Windows 10.0.19045; amd64)`，用于 WinHTTP 请求头与日志。`IsRunningOfficialVersion()` 与 `IsRunningEVSigned()` 只做证书枚举与策略 OID 匹配，属于“提示/分流”而非“准入控制”。

### 4. 关键流程与调用链

更新链的整体关系见图 07-11-01。

:::figure id=07-11-01 | name=更新清单验证与 MSI 执行链路 | dir=TD
node n1 "checkForUpdate" blue
node n2 "latest.sig" teal
node n3 "readFileList 验签" amber
node n4 "findCandidate" purple
node n5 "msiTempFile 临时文件" gray
node n6 "BLAKE2b 常量比较" green
node n7 "runMsi 静默安装" red
edge n1 -> n2 "WinHTTP 获取"
edge n2 -> n3 "Ed25519 验证"
edge n3 -> n4 "按架构筛选"
edge n4 -> n5 "下载到 Temp"
edge n5 -> n6 "边下边算"
edge n6 -> n7 "哈希一致"
edge n7 -> n1 dashed "下次启动复查"
:::

第一步是资格检查。`checkForUpdate()` 首先调用 `version.IsRunningOfficialVersion()`，不是官方签名构建就直接返回“updates are disabled”。这不是安全边界，而是产品策略：非官方构建可能被重新打包，更新到官方 MSI 会覆盖用户改动，也可能破坏发行版约定。

第二步是获取并验证清单。`winhttp.NewSession(version.UserAgent())` 建立会话，`Connect()` 连接 `download.wireguard.com:443`，`Get(latestVersionPath, true)` 取 `latest.sig`，`io.ReadAll(io.LimitReader(response, 512*1024))` 限制大小。`readFileList()` 验证通过后返回 `fileList`；任何一步失败都会关闭会话与连接，不会留下半开状态。

第三步是选候选。`findCandidate()` 遍历 `fileList`，用 `strings.HasPrefix(name, prefix)` 与 `HasSuffix(name, suffix)` 过滤，取出中间版本串，做长度检查与 `versionNewerThanUs()` 比较，返回第一个更新的条目。若没有更新，`CheckForUpdate()` 返回 `(nil, nil)`，`DownloadVerifyAndExecute()` 会把它当成错误“No update was found”，但这不是异常，而是“已是最新”。

第四步是准备临时文件。`DownloadVerifyAndExecute()` 先投递 `Initializing`，用 CAS 抢 `updateInProgress`；抢不到就投递“An update is already in progress”。然后 `msiTempFile()` 创建随机名文件，投递 `Msi destination is ...`，并注册 `defer file.Delete()`。这个 defer 只在进程正常返回时执行；异常退出由 `MOVEFILE_DELAY_UNTIL_REBOOT` 兜底。

第五步是下载与校验。`connection.Get(fmt.Sprintf(msiPath, update.name), false)` 打开响应，`response.Length()` 取总长度（可能失败，失败就不显示总量），`blake2b.New256(nil)` 建哈希，`io.Copy(file, io.TeeReader(io.LimitReader(response, 100*1024*1024), pm))` 边下边写边算。完成后 `subtle.ConstantTimeCompare(hasher.Sum(nil), update.hash[:])`，不一致就报“The downloaded update has the wrong hash”并删除临时文件。

第六步是执行。`runMsi(file, userToken)` 先 `ExclusivePath()` 关闭句柄，取 `System32` 与 `DevNull`，构造 `os.ProcAttr`，`os.StartProcess(msiexec, []string{msiexec, "/qb!-", "/i", filepath.Base(msiPath)}, attr)`，`proc.Wait()` 后检查 `state.Success()`。安装成功后投递 `Complete: true`；失败则把 `exec.ExitError` 投递出去。

第七步是权限包装。若 `userToken == 0`，整个 `doIt()` 被放进 `elevate.DoAsSystem()`，通过 `SeDebugPrivilege` + `winlogon.exe` 令牌 impersonate 到 SYSTEM；否则直接在调用者令牌下运行。manager 的 `Update()` 传入的是 `s.elevatedToken`，所以 UI 触发的更新通常走“已提升令牌”路径；`wireguard.exe /update` 在无 UI 场景下可能走 SYSTEM 路径。两条路径的差异会影响临时文件 ACL 与 `msiexec` 的可见性，排障时要先确认是哪一条。

### 5. 配置/命令/代码实例

更新器没有 `.conf` 键，入口是命令行开关与计划任务。最典型的三条命令如下，完整开关见 04-04，服务与计划任务命令见 04-06。

```powershell
wireguard.exe /update
schtasks /create /tn "WireGuard Update" /tr "\"C:\Program Files\WireGuard\wireguard.exe\" /update" /sc daily /st 03:00 /ru SYSTEM
Get-Item "C:\Program Files\WireGuard\wireguard.exe" | Select-Object VersionInfo
```

一次成功更新的日志片段如下，活动名称与顺序需对照实际版本核验。

```text
2026-11-12 03:00:01.004: [MGR] Checking for update
2026-11-12 03:00:01.512: [MGR] Creating temporary file
2026-11-12 03:00:01.517: [MGR] Msi destination is "C:\\Windows\\Temp\\9f3c1a5d7b2e4c8a10f6d3b9e7a1c5d2"
2026-11-12 03:00:01.520: [MGR] Downloading update
2026-11-12 03:00:09.884: [MGR] Installing update
2026-11-12 03:00:31.220: [MGR] Update completed
```

判读要点如下。第一，`Checking for update` 之后若立刻出现 “Build is not official, so updates are disabled”，说明当前 exe 的签名证书不含 `WireGuard LLC`，常见于自编译或第三方重打包；这不是网络问题。第二，`Msi destination is ...` 中的路径应位于 `%WINDIR%\Temp` 且文件名是 64 位十六进制随机串；如果出现可预测文件名或用户目录路径，说明不是本模块的标准行为。第三，`Downloading update` 与 `Installing update` 之间通常有几秒到几十秒的间隔，取决于 MSI 大小与网络；若长期停在 Downloading，应检查 WinHTTP 代理与 100 MiB 限制。第四，`Installing update` 之后若出现 `msiexec` 的退出码错误，常见原因是另一个安装正在进行、MSI 文件被占用或权限不足；`/qb!-` 不会弹交互窗口，错误只能从日志与事件查看器看。第五，`Update completed` 只代表 `msiexec` 返回成功，不代表新版本已生效；服务重启与 UI 重启由安装器/后续启动完成，必要时应复查 `version.Number` 或文件版本。

从代码角度，更新器最关键的三个“不变量”是：清单必须先验签再解析、下载必须先哈希再执行、临时文件必须独占且随机命名。对应的代码片段如下：

```go
files, err := readFileList(fileList)
if err != nil {
    return nil, nil, nil, err
}
updateFound, err := findCandidate(files)
if err != nil {
    return nil, nil, nil, err
}

hasher, err := blake2b.New256(nil)
if err != nil {
    progress <- DownloadProgress{Error: err}
    return
}
pm := &progressHashWatcher{&dp, progress, hasher}
_, err = io.Copy(file, io.TeeReader(io.LimitReader(response, 1024*1024*100), pm))
if err != nil {
    progress <- DownloadProgress{Error: err}
    return
}
if subtle.ConstantTimeCompare(hasher.Sum(nil), update.hash[:]) != 1 {
    progress <- DownloadProgress{Error: errors.New("The downloaded update has the wrong hash")}
    return
}
```

这段代码没有“先落盘再校验”的中间态：哈希与写入是同一遍 `io.Copy`，校验失败时文件已被 `defer Delete()` 清理。`subtle.ConstantTimeCompare` 而非 `bytes.Equal`，是为了避免比较过程泄露哈希前缀信息；虽然这里的威胁模型主要是“服务器被攻破后投毒”，常量时间比较仍是良好习惯。

### 6. 注意事项、陷阱与最佳实践

- **官方构建判定不是安全边界**。`IsRunningOfficialVersion()` 只枚举证书简单名，注释明确说可绕过；不要用它做权限决策，也不要把“非官方构建不支持更新”理解为“官方构建绝对可信”。
- **签名清单有大小上限**。512 KiB 的 `LimitReader` 是防御性限制，正常清单远小于此；若服务端返回异常大文件，读取会被截断并导致解析失败，这是预期行为。
- **MSI 有 100 MiB 上限**。超过会被 `LimitReader` 截断，随后哈希不匹配；如果官方包体积增长，客户端必须同步调整上限，否则会出现“下载完成但哈希错误”的误判。
- **临时文件必须先关闭再交给 MSI**。`ExclusivePath()` 的注释直言这是一个 TOCTOU 权衡，但 MSI 要求不共享文件；不要在调用 `runMsi()` 前重新打开该路径，否则安装会失败。
- **`/qb!-` 不是完全静默**。它会显示基本进度但禁用取消；在无人值守场景仍可能因 UAC、重启提示或安装器对话框卡住。企业部署建议结合 `DO_NOT_LAUNCH` 与维护窗口。
- **更新期间不要重复触发**。`updateInProgress` 的 CAS 会拒绝并发更新，但 UI 上仍可能看到“正在检查”与“已在更新”交错；应以日志中的 `An update is already in progress` 为准。
- **版本比较只支持数字段**。`1.1.1-beta` 这类版本会在 `ParseUint` 处失败；官方发布使用纯数字版本，第三方构建不要指望更新器能正确比较预发布号。
- **架构必须匹配**。`findCandidate()` 只找同架构的 MSI；在 x86 系统上不会下载 amd64 包，反之亦然。跨架构迁移需要手工卸载重装，不能靠 `/update`。
- **降级被禁止**。MSI 的 `MajorUpgrade` 设置了 `AllowDowngrades="no"`，即使手工指定旧包也会被拒绝；需要回滚时应走卸载 + 安装旧版的受控流程。
- **清单缺失与“已是最新”要区分**。服务器返回 404、返回空清单、清单里没有同架构条目，最终都可能表现为“没有可用更新”，但日志与错误文本不同：404 是传输层错误，空清单是“No file hashes found”，无候选是“No update was found”。排障时先看是哪一种，再决定查网络、查发布流程还是查架构匹配。
- **代理与 TLS 检查**。WinHTTP 使用系统代理与系统证书存储；企业 TLS 拦截若未被系统信任，`Connect` 会失败，日志里表现为网络错误而不是签名错误。
- **更新成功不等于新版本已运行**。`msiexec` 返回 0 只代表安装事务完成；正在运行的 manager、隧道服务与 UI 是否重启，取决于 MSI 的服务控制与后续启动逻辑。验证时应比较 `wireguard.exe` 的文件版本与 `version.Number`，并确认服务进程的启动时间晚于安装时间。
- **文件版本与产品版本可能不同**。`version.Number` 是编译进二进制的字符串，MSI 的 `Version` 来自构建变量 `$(var.WIREGUARD_VERSION)`；两者在正常发布中一致，但自编译或改造构建中可能不一致。更新器只用 `version.Number` 做比较，MSI 升级规则只看产品版本，排查“为什么总提示有更新”时要同时核对这两处。

### 7. 小结与延伸阅读

`updater` 的核心不是“下载一个文件”，而是“用一条可验证的信任链把文件变成可执行的安装”。这条链由四段组成：Ed25519 验签保证清单来源，BLAKE2b-256 保证 MSI 完整，随机独占临时文件保证落盘安全，`msiexec /qb!-` 保证安装可控。`version` 则提供版本、架构、系统名与官方构建判定，是这条链的输入与旁路提示。把这两者分开看，就不会把“产品策略”误当成“安全机制”。

延伸阅读建议：先看 04-04 的 `/update` 与 04-06 的计划任务命令，再看 05-09 的 `DownloadProgress`/`UpdateFound` 字段，然后读 06-12 理解完整更新链与 signify 的密钥管理，最后结合 `docs/attacksurface.md` 的更新章节与 `docs/enterprise.md` 的企业部署建议，设计自己的更新窗口与回滚预案。

## 07-12 `elevate` / `l18n` / `installer` / `embeddable-dll-service` 扩展模块

### 1. 背景与动机

前面几篇讲的是“主链路”：配置、驱动、隧道、管理、界面、日志、更新。这一篇讲四个外围但不可缺的扩展模块，它们分别回答四个问题：进程如何获得、使用并放弃高权限；界面如何跟随用户语言；安装包如何把文件、服务、自定义动作编排成一个可回滚的 MSI；以及如何把 WireGuard 隧道能力嵌入到第三方程序里。四者看似无关，但共同构成了“可部署、可本地化、可集成”的外壳。

`elevate` 的动机是权限最小化。Windows 客户端里至少有三类权限主体：LocalSystem 的管理服务与隧道服务、提升令牌下的 UI、普通用户令牌下的 UI。隧道服务启动后只需要保留加载驱动所需的一项特权，其余全部丢弃；UI 需要提升时不能在进程内“假装”提权，而要通过链接令牌或 COM 自动提升对象；更新器需要在 SYSTEM 上下文里运行 `msiexec`，但不能要求用户先开一个 SYSTEM 终端。`elevate` 把这些令牌操作封装成可复用函数，并明确哪些是“能力”、哪些是“边界”。

`l18n` 的动机是可翻译性。WireGuard 的界面文字、错误消息、单位与枚举分隔符都面向最终用户；如果字符串散落在代码里、用 `fmt.Sprintf` 拼接，翻译工具无法提取，中文与日文的列举分隔符也无法正确处理。`l18n` 用 `golang.org/x/text/message` 的 printer 与 catalog，把“取用户首选 UI 语言、选择最可信翻译、按语言格式化”收敛到一处，再用 `gotext` 流水线生成 `zgotext.go`。

`installer` 的动机是可运维性。MSI 不只是“复制文件”：它要在升级前停止并删除旧服务、在卸载时清理配置目录与适配器、在安装后按需启动 UI、在旧系统上提前失败、在多架构之间使用不同 `UpgradeCode`。这些动作有的适合用 WiX 声明式表达，有的必须写 C 自定义动作。`installer/` 里的 `wireguard.wxs`、`customactions.c` 与 `fetcher/` 就是这两类手段的分工。

`embeddable-dll-service` 的动机是可集成。有些产品不希望用户安装完整的 WireGuard 客户端，而是希望在自己的进程里“顺带”提供一条隧道。上游提供的方案是编译一个 `tunnel.dll`，导出 `WireGuardTunnelService` 与 `WireGuardGenerateKeypair`，由宿主程序注册一个符合命名与 SID 要求的服务，再把配置路径传进来。它复用同一套隧道实现，但把“服务外壳”交给了集成方。

### 2. 核心概念

**特权丢弃**。`elevate.DropAllPrivileges(retainDriverLoading bool)` 打开当前进程令牌，取 `TokenPrivileges`，遍历每个 `LUIDAndAttributes`，把 `Attributes` 设为 `SE_PRIVILEGE_REMOVED`；若 `retainDriverLoading` 为真，则跳过 `SeLoadDriverPrivilege`。注意它用的是 `AdjustTokenPrivileges` 的“移除”语义，不是简单地禁用，移除后无法在同一令牌上重新启用。隧道服务在完成适配器创建后调用它，只留下加载驱动所需的能力，这对缩小攻击面有实际意义。

**以 SYSTEM 执行**。`DoAsSystem(f func() error)` 先 `runtime.LockOSThread()`，启用 `SeDebugPrivilege`，`ImpersonateSelf()` 后打开线程令牌；如果当前已是 LocalSystem，直接执行回调。否则枚举 `winlogon.exe`，打开其令牌，确认用户 SID 是 `WinLocalSystemSid`，复制为 impersonation token，`SetThreadToken()`，切换环境变量，执行回调，最后恢复环境并 `RevertToSelf()`。这条路径依赖 `SeDebugPrivilege`，因此调用者必须先是管理员或 SYSTEM；它不是“任意用户提权”的工具。

**以服务身份执行**。`DoAsService(serviceName, f)` 先通过 `mgr.Connect()` 打开服务，查 `ProcessId`，再在 `DoAsSystem()` 里打开该进程令牌、复制、`SetThreadToken()`、切换环境、执行回调。它适合“以某个已运行服务的身份做一件事”，例如让更新器借用管理服务的令牌。与 `DoAsSystem()` 的区别是：前者最终 impersonate 到目标服务进程的用户（通常是 SYSTEM），后者固定找 `winlogon.exe`。

**UI 提权的两条路**。`ShellExecute(program, arguments, directory, show)` 先检查 `version.IsRunningEVSigned()`；不是 EV 签名就返回 `ERROR_INSUFFICIENT_LOGON_INFO`。然后看当前令牌是否已提升，未提升则检查是否可提升；再读 `ConsentPromptBehaviorAdmin`：为 0（无提示直接提升）则直接返回成功，为 5（提示同意）才继续，其他值返回 `ERROR_ACCESS_DENIED`。接着读 `COMAutoApprovalList` 中 `{3E5FC7F9-9A51-4367-9063-A120244FBEC7}` 的值，最后通过修改当前模块的 `LDR_DATA_TABLE_ENTRY.FullDllName` 指向 `explorer.exe`，用 `CoGetObject("Elevation:Administrator!new:{3E5FC7F9-9A51-4367-9063-A120244FBEC7}")` 拿到自动提升对象的接口指针，再按 vtable 偏移调用 `Release` 与 `ShellExecute`。这是一条“利用 COM 自动提升”的路径，失败时 defer 会回退到 `ShellExecute(0, "runas", ...)`，也就是普通 UAC 弹窗。

**管理员判定**。`TokenIsElevatedOrElevatable(token)` 先看 `token.IsElevated() && isAdmin(token)`，否则取链接令牌再判断；`IsAdminDesktop()` 则通过 `GetShellWindow()` 找到桌面窗口、取进程、开令牌，判断“当前桌面是否由管理员拥有”。前者用于“这个用户能不能提权”，后者用于“当前桌面是不是管理员桌面”，两者不能混用。

**本地化流水线**。`l18n.prn()` 惰性创建 `message.Printer`，语言由 `lang()` 决定：从 `GetUserPreferredUILanguages(MUI_LANGUAGE_NAME)` 取列表，逐个用 `message.DefaultCatalog.Matcher().Match()` 匹配，选置信度最高的；没有匹配就回退英语。`Sprintf()` 只是 `prn().Sprintf()` 的薄封装。`EnumerationSeparator()` 与 `UnitSeparator()` 通过翻译特殊的占位键来获得语言相关的分隔符（中文为 `、`，多数西方语言为 `, `），因为 `gotext` 会跳过没有字母的字符串，所以源码用带方括号的占位键绕过这一限制。

**gotext 生成**。`gotext.go` 是 `//go:build generate` 的生成程序：读取 `locales/<lang>/messages.gotext.json`，把目录名规范化为语言标签，构建 `gotext` 命令，执行 `gotext -srclang=en update -out=zgotext.go -lang=<列表>`，再把 `out.gotext.json` 重命名为 `messages.gotext.json`。生成结果 `zgotext.go` 被编译进程序，`l18n` 在运行时通过 `message.DefaultCatalog` 使用它。换句话说，翻译不是运行时读文件，而是编译期固化。

**WiX 安装包**。`wireguard.wxs` 的 `Product` 使用 `Version="$(var.WIREGUARD_VERSION)"`、`Manufacturer="WireGuard LLC"`、按架构选择 `UpgradeCode`（amd64、x86、arm、arm64 各一个），`Package` 设置 `InstallScope="perMachine"`、`InstallerVersion="500"`、`Compressed="yes"`。`MajorUpgrade` 设置 `AllowDowngrades="no"`、`AllowSameVersionUpgrades="yes"`、`Schedule="afterInstallExecute"`。组件里包含 `wireguard.exe`（带开始菜单快捷方式）、`wg.exe`（写系统 PATH），并用一个 `DummyService` 的 `ServiceControl` 强制 WiX 生成 ServiceControl 表，供自定义动作使用。

**自定义动作**。`customactions.c` 导出多个 `__stdcall` 函数：`CheckWinVer` 提前拒绝旧系统，`CheckWow64` 检查架构匹配，`EvaluateWireGuardServices` 判断现有服务状态，`LaunchApplicationAndAbort` 在“首次安装且未设置 `DO_NOT_LAUNCH`”时启动 UI 并中止安装流程，`KillWireGuardProcesses` 结束占用文件的进程，`RemoveConfigFolder` 删除配置目录，`RemoveAdapters` 清理适配器。`wireguard.wxs` 用 `CustomAction` + `InstallExecuteSequence` 把它们插到 `CostFinalize`、`InstallValidate`、`InstallFinalize` 等时点；延迟动作标 `Execute="deferred" Impersonate="no"`，确保以 SYSTEM 运行。

**可嵌入 DLL**。`embeddable-dll-service/main.go` 用 cgo 导出两个函数：`WireGuardTunnelService(confFile16 *uint16) bool` 设置配置根目录、强制 `tunnel.UseFixedGUIDInsteadOfDeterministic = true`，再调用 `tunnel.Run(confFile)`；`WireGuardGenerateKeypair(publicKey, privateKey *byte)` 用 `ecdh.X25519()` 生成密钥并做 clamp。README 要求宿主注册服务时使用 `WireGuardTunnel$SomeTunnelName`、`SERVICE_WIN32_OWN_PROCESS`、`StartAutomatic`、`ErrorNormal`、依赖 `Nsi` 与 `TcpIp`、`SERVICE_SID_TYPE_UNRESTRICTED`，可执行文件带 `/service configfile.conf` 参数，并在主函数里 `LoadLibrary("tunnel.dll")` + `GetProcAddress("WireGuardTunnelService")`。

先看隧道服务的权限链。进程以 LocalSystem 启动，创建适配器、加载驱动、设置配置；在合适的时点调用 `elevate.DropAllPrivileges(true)`，只保留 `SeLoadDriverPrivilege`。此后即使进程被攻破，攻击者也无法直接获得调试、备份、改系统时间等特权。这个调用点不在 `elevate` 包内，而在 `tunnel/service.go` 的启动序列里；具体顺序与错误处理需对照实际版本核验。若降权失败，服务应把 `serviceError` 置为 `ErrorDropPrivileges` 并退出，而不是“带着全特权继续跑”。

再看 UI 的提升链。普通用户启动 `wireguard.exe` 时，若当前不是管理员，程序可以调用 `elevate.ShellExecute()` 尝试自动提升；若 EV 签名、UAC 策略或 COM 自动批准任一条件不满足，就回退到 `runas`，由系统弹 UAC。提升成功后，UI 以高完整性运行，但仍然通过 IPC 让 manager 执行真正的服务操作；UI 自身不做 `CreateService`。这条“UI 提升但服务仍是唯一执行者”的分工，是权限模型的关键。

安装链从 MSI 开始。`InstallExecuteSequence` 先跑 `CheckWinVer`（旧系统直接失败），再跑 `CheckWow64`（架构不匹配失败），然后 `EvaluateWireGuardServices` 判断现有服务，`LaunchApplicationAndAbort` 在首次安装且未设置 `DO_NOT_LAUNCH` 时启动 UI 并中止，`KillWireGuardProcesses` 结束占用文件的进程，文件复制完成后 `RemoveConfigFolder`/`RemoveAdapters` 在卸载路径清理，最后 `LaunchApplication` 按需启动。`DO_NOT_LAUNCH` 是一个 MSI 属性，企业分发时通过 `msiexec DO_NOT_LAUNCH=1` 设置，`wireguard.wxs` 里的条件写作 `NOT DO_NOT_LAUNCH`，因此“属性存在且非空”就会抑制启动。

本地化链从源码到产物。开发者运行 `go generate`，`gotext.go` 扫描 `locales/` 下的 `messages.gotext.json`，调用 `gotext update` 生成 `zgotext.go`；编译时该文件进入二进制，运行时 `l18n.prn()` 按用户首选 UI 语言选择 catalog。翻译更新不需要改 Go 代码，但需要重新生成并重新编译；如果只替换 `locales/` 下的 JSON 而不重新生成，程序不会看到新翻译。

嵌入链从构建到注册。`embeddable-dll-service/build.bat` 首次运行会调用上层 `build.bat` 下载依赖，随后产出 `amd64/tunnel.dll`、`x86/tunnel.dll`、`arm64/tunnel.dll`；`tunnel.dll` 依赖 `wireguard.dll`（WireGuardNT 的用户态 DLL）。宿主程序注册服务时必须使用 `WireGuardTunnel$` 前缀、正确的依赖与 `SERVICE_SID_TYPE_UNRESTRICTED`，并在 `/service` 分支里加载 DLL、取 `WireGuardTunnelService` 地址、把配置路径传进去。`WireGuardTunnelService` 内部强制固定 GUID，避免嵌入场景下确定性 GUID 与宿主网络策略冲突。

### 5. 配置/命令/代码实例

这一篇的“配置”主要是安装属性、注册表策略与构建命令。最典型的三条如下，完整命令与策略见 04-04、04-06、04-07。

```powershell
msiexec.exe /i wireguard-amd64-1.1.1.msi /qn DO_NOT_LAUNCH=1
reg add "HKLM\Software\WireGuard" /v DangerousScriptExecution /t REG_DWORD /d 1 /f
cd C:\src\wireguard-windows\embeddable-dll-service && build.bat
```

第一条用于企业静默安装并抑制安装后启动；第二条开启危险脚本执行（默认关闭，开启后 `PreUp`/`PostUp`/`PreDown`/`PostDown` 会以 LocalSystem 执行，环境变量是 `WIREGUARD_TUNNEL_NAME`）；第三条构建可嵌入 DLL。三条命令的风险等级完全不同，生产环境应把第二条视为高风险变更。

安装后的验证输出如下，属性名与提示文本需对照实际 MSI 版本核验。

```text
PS> Get-WinEvent -LogName Application -MaxEvents 5 |
>> Where-Object { $_.ProviderName -eq 'MsiInstaller' } |
>> Select-Object TimeCreated, Id, Message

TimeCreated            Id Message
-----------            -- -------
2026-11-12 10:02:11  11707 Product: WireGuard -- Installation completed successfully.
2026-11-12 10:02:11  1033 Windows Installer installed the product.
```

判读要点如下。第一，`11707` 表示安装成功完成，`1033` 是更详细的“已安装产品”事件；两者同时出现通常说明主流程与自定义动作都走完了。第二，如果只看到 `1033` 而没有 `11707`，可能是安装被 `LaunchApplicationAndAbort` 中止，或某个延迟动作返回失败；应结合 `DO_NOT_LAUNCH` 是否设置来判断。第三，事件里不会直接告诉你“哪个自定义动作失败”，需要看 MSI 日志（`/l*v`）中的 `ActionStart`/`ActionEnd` 与返回值。第四，安装成功后仍要检查 `sc query WireGuardManager` 与 `Get-Service WireGuardTunnel$*`，因为 MSI 成功只代表文件与服务注册完成，不代表服务已启动。第五，卸载时若 `RemoveConfigFolder` 被跳过，配置目录可能残留；这是有意为之的保护，重装前应确认是否需要保留。

从代码角度，嵌入服务的核心只有两个导出函数，宿主侧的关键是“服务参数必须完全匹配”：

```go
//export WireGuardTunnelService
func WireGuardTunnelService(confFile16 *uint16) bool {
    confFile := windows.UTF16PtrToString(confFile16)
    conf.PresetRootDirectory(filepath.Dir(confFile))
    tunnel.UseFixedGUIDInsteadOfDeterministic = true
    err := tunnel.Run(confFile)
    if err != nil {
        log.Printf("Service run error: %v", err)
    }
    return err == nil
}
```

这段代码做了三件事：把配置根目录设为配置文件所在目录，避免嵌入方与官方客户端的路径假设冲突；强制使用固定 GUID，避免确定性 GUID 在宿主环境中触发网络分类变化；直接调用 `tunnel.Run()`，复用完整的隧道启动、驱动下发、路由与防火墙逻辑。返回值是 `bool`，宿主应把它映射为服务退出码，否则 SCM 只能看到“进程退出”而不知道原因。

### 6. 注意事项、陷阱与最佳实践

- **降权是移除，不是禁用**。`DropAllPrivileges()` 把权限标记为 `SE_PRIVILEGE_REMOVED`，之后不能在同一令牌上重新启用；如果代码后续还需要某项权限，必须在调用前完成，或重新打开进程令牌。
- **`DoAsSystem()` 不是通用提权**。它需要 `SeDebugPrivilege` 才能打开 `winlogon.exe`，普通用户调用会失败；把它包装成“任意用户可调用”的 API 是危险的，也会破坏权限模型。
- **EV 签名检查只影响自动提升路径**。`ShellExecute()` 在非 EV 签名时直接返回错误，但 defer 会回退到 `runas`；这意味着“没有 EV 签名”不等于“不能提权”，只是不能走无弹窗的 COM 路径。
- **修改 `FullDllName` 是敏感操作**。`shellexecute.go` 临时把当前模块的 `LDR_DATA_TABLE_ENTRY.FullDllName` 指向 `explorer.exe`，调用后必须恢复；任何 panic 或提前返回都可能留下不一致状态，扩展这段代码时要格外小心。
- **`DO_NOT_LAUNCH` 只抑制启动**。它不会跳过服务注册、文件复制或自定义动作；企业静默安装仍需确保 `WireGuardManager` 被正确安装，否则 UI 启动后连不上服务。
- **危险脚本默认关闭**。`DangerousScriptExecution` 未开启时四个脚本键不执行；开启后脚本以 LocalSystem 运行，等于把配置文件的写入权限提升为系统命令执行权限。不要把“能写配置”与“能执行脚本”混为一谈。
- **翻译要重新生成**。`zgotext.go` 是生成文件，手工修改会在下次 `go generate` 时被覆盖；新增语言应同时更新 `locales/` 与生成结果，并确认 `l18n.lang()` 能匹配到该标签。
- **MSI 的 `UpgradeCode` 按架构区分**。amd64、x86、arm、arm64 各有独立 GUID，跨架构升级不会被识别为同一产品；迁移架构时必须先卸载再安装，不能指望 `MajorUpgrade` 自动处理。
- **嵌入服务的 SID 要求不可省**。README 明确说 `SERVICE_SID_TYPE_UNRESTRICTED` “absolutely essential”；漏掉它，隧道进程在访问某些网络对象时会受限，表现为路由或 DNS 行为异常。
- **`tunnel.dll` 依赖 `wireguard.dll`**。只复制 `tunnel.dll` 而不部署 WireGuardNT 用户态 DLL，`LoadLibrary` 可能成功但运行期失败；分发时应把两个 DLL 与架构一起校验。

### 7. 小结与延伸阅读

这四个扩展模块分别守护四个边界：`elevate` 守护权限边界，`l18n` 守护语言边界，`installer` 守护部署边界，`embeddable-dll-service` 守护集成边界。它们的共同点是“不改变隧道数据面，但决定了客户端能否安全、正确地被安装、被理解、被复用”。读这些代码时，不要只看函数做了什么，更要看它拒绝做什么：拒绝保留多余特权、拒绝在非 EV 签名时静默提升、拒绝跨架构升级、拒绝在缺少服务 SID 时正常工作。

延伸阅读建议：先看 04-07 理解 `DangerousScriptExecution` 与受限 UI 的策略，再看 06-05 理解适配器创建与驱动加载的权限前提，然后读 `installer/wireguard.wxs` 与 `customactions.c` 对照安装序列，最后按 `embeddable-dll-service/README.md` 的步骤在测试程序里注册一个 `WireGuardTunnel$` 服务，验证 `/service` 分支与 `WireGuardTunnelService` 的返回值映射。这样可以把“模块介绍”落到可复现的实验上，而不是停留在函数名层面。
