# wireguard-windows 技术资料 · 05 关键数据结构字段详解（分片 A）

## 05-01 全册结构体分层与跨文档索引

### 1. 本篇定位与覆盖范围

本篇是「05 关键数据结构字段详解」册的开篇索引，也是全册作为结构体逐字段唯一权威源的读法说明。按照总纲第 2 节的去重铁律，本册承担一项不可替代的职责：所有 Go 结构体的成员名、成员类型、默认值、内存布局、读写时机与关联函数入口，都只在 05 册给出完整定义；其余各册在需要引用结构体时只能点名并写「字段见 05-xx」，不得重列字段表。这一点决定了本册的工具书属性——它不是从 01 读到 08 的线性主线中的一环，而是供读者在研读源码、排查字段含义、核对序列化结果时随时翻查的字典。总纲第 5 节把 05 册画成一条从「随查前置」指向「06 技术原理」的虚线分支，正是这个含义：先把结构体地图建起来，再进入机制与调用链，才不会在字段层面反复回头。

本册共 9 篇，按 05-01 到 05-09 连续编号。本文件「分片 A」收录前 5 篇，覆盖配置层与驱动层这两类最基础、最常被查阅的结构体：05-01 全册分层与索引、05-02 `conf.Config` / `conf.Interface` / `conf.Peer` 三大配置结构、05-03 四个自定义标量类型 `Key` / `Endpoint` / `HandshakeTime` / `Bytes`、05-04 注释保真结构与解析器状态字段、05-05 驱动配置结构与 IOCTL 载荷字段。分片 B 收录 05-06 到 05-09，讲 `driver.Adapter` 与适配器状态、`winipcfg` 的 LUID 与 MIB 网络配置结构、`tunnelService` / `interfaceWatcher` / WFP 规则结构，以及 IPC、ringlogger、updater 与 services 错误码字段；那四篇不在本文件内，读者需要时到同册后续分片查阅，本分片只在索引表中给出定位，不展开其字段。

必须反复强调 05 册的能力边界：本册只讲字段含义、内存布局、生命周期与关联函数入口，不展开机制流程。解析状态机怎么转移、DPAPI 怎么加解密、适配器怎么创建、路由怎么下发、WFP 规则怎么分层、IPC 怎么编解码，这些「怎么实现」的问题归 06 全册；配置键与命令行开关怎么拼写、有哪些取值，归 04 全册；模块能提供什么能力、典型怎么组网，归 07 全册。因此本篇在讲到 `FromWgQuick`、`ToWgQuick`、`ToDriverConfiguration` 这类函数名时，只说明它们是某个字段的读写入口，不会逐步描述函数内部的控制流。这种克制是刻意设计的：字段表一旦掺入流程叙述，就会与 06 册重复，也会让「随查」变得冗长难用。

本篇还承担一项编辑约定说明：字段表统一采用七列模板，即「字段 | 类型 | 含义 | 源码位置 | 读写时机 | 关联函数与流程 | 版本差异」。七列各自回答一个固定问题——字段叫什么、在 Go 里是什么类型、语义上代表什么、去哪个文件的哪个结构体核对、在什么阶段被读或被写、哪些函数是它的入口、随版本有什么变化。读者一旦熟悉这七列，就能把 05-02 到 05-09 的任何一张字段表当成同一张卡片的填充结果来读。凡本仓库 master 快照中不存在、或属于 WireGuardNT 外部项目、或属于具体版本号的时效性数值，一律按总纲第 9 节写「需对照实际版本核验」并给出 `upstream_src/` 下可定位的源码路径，绝不凭印象补全字段名。这是把「版本相关事实」与「结构性结论」分离的编辑纪律，不是内容缺口。

交叉引用：`配置见 04-01 ｜ 原理见 06-02 ｜ 模块见 07-01`。本篇讲对象分层，配置键语法与文件结构见 04-01，结构体之间的流转机制见 06-02，`conf` 包整体能力见 07-01。

### 3. 逐项详解

#### 3.1 四层对象分层

全册结构体可以按「离配置文本的远近」分成四层。最靠近文本的是配置层，定义在 `conf/config.go` 里，以 `Config` 为根，`Interface` 与 `Peers` 为其成员，`Key`、`Endpoint`、`HandshakeTime`、`Bytes` 为标量类型，`Comments` 与 `SectionComments` 负责注释保真。这一层的字段全部来自 `.conf` 文本解析或 UI 编辑器赋值，是用户能直接读写的东西。往下一层是驱动载荷层，定义在 `driver/configuration_windows.go` 与 `driver/driver_windows.go`，以 `driver.Interface` 为根，`driver.Peer` 与 `driver.AllowedIP` 顺序紧邻排布，`ConfigBuilder` 负责把它们拼成连续内存，`Adapter` 持有句柄。这一层的字段是给内核驱动看的二进制载荷，字段名与配置层有意相近但类型完全不同，例如配置层的 `conf.Key` 是 `[32]byte` 且在 `conf` 包，驱动层的 `PublicKey` 直接就是 `[32]byte` 成员。再往下是网络配置层与服务层，前者是 `winipcfg` 对 Windows IP Helper API 结构的封装，后者是 `tunnel`、`manager` 的服务上下文；最外一层是 ringlogger、updater 等辅助结构。本篇用一张总图把这四层的包含关系固定下来，后续各篇只是在某一层内部放大。

#### 3.2 内存表示与文本表示

理解本册的一个关键，是区分「文本表示」与「内存表示」。同一份配置，在磁盘上是 `[Interface]` / `[Peer]` 段的 INI 文本，在内存里是 `conf.Config` 结构体树，在驱动边界上又变成 `driver.Interface` 起始的一段连续字节。`ToWgQuick` 负责从内存结构体生成文本，`FromWgQuick` 负责从文本填充内存结构体，`ToDriverConfiguration` 负责把内存结构体编组成驱动载荷，`FromDriverConfiguration` 负责把驱动回读结果还原成内存结构体。字段表里的「读写时机」列，本质上就是在标注某个字段在这四种表示之间、于哪个转换点被访问。读者要注意，并非所有字段都参与全部四种表示：`Peer.RxBytes`、`Peer.TxBytes`、`Peer.LastHandshakeTime` 这三个字段在文本里根本没有对应键，它们只在驱动回读时被填充，用于 UI 展示运行时状态；反过来 `Interface.PreUp` 等四个脚本键只存在于文本与内存结构体里，不会进入驱动载荷。把字段按「是否进入某种表示」归类，是读字段表时最有用的一种抽象。

#### 3.3 字段生命周期五阶段

本册把字段的生命周期划成五段，字段表「读写时机」列的取值就来自这五段。第一段是解析期，对应 `FromWgQuick`，文本键值被校验、转换后写入 `Config` 树；第二段是编辑期，UI 配置编辑器直接读写 `Config` 树的成员，`DeduplicateNetworkEntries` 与 `Redact` 也在这一阶段前后作用于字段；第三段是序列化期，对应 `ToWgQuick` 与 `Save`，把内存结构体写回文本并经 DPAPI 加密落盘；第四段是下发期，对应 `ToDriverConfiguration` 与 `SetConfiguration`，把字段编组进连续内存交给驱动；第五段是回读期，对应 `Configuration` 与 `FromDriverConfiguration`，把驱动侧统计值还原进内存结构体供展示。一个字段可能只出现在其中两三段，例如 `Name` 只在解析期赋值、在序列化与存储期被读取以决定文件名，`TrailingComments` 只在解析与序列化两端出现，`RxBytes` 只在回读期出现。字段表里若某字段的「读写时机」很窄，往往正说明它是某种表示特有的字段。

#### 3.4 字段表七列的判读方法

读一张字段表时，建议按「类型 → 源码位置 → 读写时机 → 关联函数」的顺序走一遍。先看类型，判断它是值类型还是引用类型：数组 `[32]byte` 是值语义，赋值即拷贝；切片 `[]netip.Prefix`、`[]string` 与映射 `map[string]Comments` 是引用语义，零值为 nil，`len` 为零与 nil 在 `ToWgQuick` 的输出判断里经常等价。再看源码位置，凡本篇给出的路径都能在 `upstream_src/` 下打开核对，读者应养成「看到一个字段名就回源码确认一遍」的习惯，因为本册的权威性正建立在源码可核对之上。接着看读写时机，锁定字段在哪一两个阶段被触碰。最后看关联函数与流程列，那里只列函数入口名，用来回答「谁会改它」，具体函数内部怎么走属于 06 册。版本差异列则提示该字段是否经历过类型迁移，例如 `Addresses` 从旧的 `net.IPNet` 系迁移到 `netip.Prefix`、`DNS` 迁移到 `netip.Addr`，这类迁移会直接影响字段的零值判断与 `String()` 输出格式。

### 4. 典型示例

下面用一段 Go 代码演示如何从 `conf` 包构造一个最小 `Config`，并打印根对象的几个字段，借此说明「字段表里的名字就是内存里可直接访问的名字」。这段代码只访问字段、不触发任何配置下发，符合本册只讲字段的边界。

```go
package main

import (
	"fmt"

	"golang.zx2c4.com/wireguard/windows/conf"
)

func main() {
	var c conf.Config
	c.Name = "demo"
	c.Interface.ListenPort = 51820
	c.Interface.MTU = 1420
	c.Peers = append(c.Peers, conf.Peer{})
	fmt.Println("Name =", c.Name)
	fmt.Println("Interface.ListenPort =", c.Interface.ListenPort)
	fmt.Println("Interface.MTU =", c.Interface.MTU)
	fmt.Println("len(Peers) =", len(c.Peers))
	fmt.Println("TrailingComments is nil =", c.TrailingComments == nil)
	fmt.Println("Interface.Comments.Lines is nil =", c.Interface.Comments.Lines == nil)
}
```

示例输出，具体格式需对照实际版本核验：

```text
Name = demo
Interface.ListenPort = 51820
Interface.MTU = 1420
len(Peers) = 1
TrailingComments is nil = true
Interface.Comments.Lines is nil = true
```

逐行判读如下。第一行 `Name = demo`，说明 `Config.Name` 是普通 `string` 字段，赋值即生效，它决定存储文件名与隧道服务名，具体约束由 `conf/name.go` 的 `TunnelNameIsValid` 把关。第二、三行显示 `Interface.ListenPort` 与 `Interface.MTU` 都是 `uint16`，零值 0 在 `ToWgQuick` 里被当作「未设置」而不写出对应键，因此这里显式赋值后才会出现在文本里；端口号与 MTU 的合法范围由 `conf/parser.go` 的 `parsePort`、`parseMTU` 校验，读者可据此判断异常值。第四行 `len(Peers) = 1`，说明 `Peers` 是切片字段，`append` 后长度为 1，零值 `nil` 与空切片在 `ToWgQuick` 的遍历里表现一致，都不会写出 `[Peer]` 段。第五、六行两个 `true` 是关键：`TrailingComments` 与 `Interface.Comments.Lines` 都是引用类型，未赋值时为 nil，字段表里把它们标为「解析期填充、序列化期读取」，正是因为它们承载可选的注释文本，绝大多数最小配置里都是 nil。若输出里出现 `false` 而配置文本并无注释，往往意味着某处误调用了构造或反序列化逻辑，应回查 `conf/parser.go` 的注释填充分支。

### 6. 版本差异

本册以 master 快照（2026-11 抓取）为基准，配合总纲第 9 节约定处理版本相关事实。最显著的一处类型迁移是 `net/netip`：当前 `Interface.Addresses` 为 `[]netip.Prefix`、`Interface.DNS` 与 `Interface.DNSSearch` 分别为 `[]netip.Addr` 与 `[]string`、`Peer.AllowedIPs` 为 `[]netip.Prefix`，而较早版本使用的是 `net.IP` / `net.IPNet` 一族；`netip` 自 Go 1.18 引入，本仓库 Makefile 基准为 Go 1.27.1，因此字段表现以 `netip` 为准。读者若对照旧资料看到 `net.IPNet`，应理解那是迁移前的写法，具体迁移时点「需对照实际版本核验」，路径为 `conf/config.go`。

第二处是密钥派生实现：`Key.Public()` 当前使用标准库 `crypto/ecdh` 的 `ecdh.X25519()`，而更早版本依赖 `golang.org/x/crypto/curve25519`；`crypto/ecdh` 自 Go 1.20 起可用。这影响 `NewPrivateKey` 的 clamp 位写法与 `Public()` 的返回值类型，字段本身仍是 `[32]byte`，但派生入口不同，具体差异「需对照实际版本核验」，路径为 `conf/config.go`。

第三处是解析器辅助 API：`conf/parser.go` 当前使用 `strings.Cut`（Go 1.18）与 `strings.SplitSeq`（Go 1.24 迭代版）等较新的标准库能力，注释保真逻辑随这些 API 的引入做过重写；`conf/writer.go` 的 `ToWgQuick` 输出格式也随之稳定。凡涉及具体 Go 版本引入的 API、WireGuardNT 1.1 的 IOCTL 结构定义、以及三种 MSI 的版本号，本册一律标注「需对照实际版本核验」并给出 `upstream_src/` 路径，不写死时效性数值。

### 7. 常见误用与调试

#### 7.1 把 05 册当机制书读

最常见的误用，是拿着 05 册去找「解析是怎么一步步走的」「路由是怎么下发的」。本册按总纲第 4 节明确禁止展开机制流程，字段表「关联函数与流程」列只给函数入口名。读者若要理解状态转移与调用顺序，应转 06 全册；05 册只回答「这个字段是什么、什么时候被谁碰」。把两册职责搞混，会既觉得 05 册太干、又觉得 06 册缺字段定义。

#### 7.2 混淆 conf.Interface 与 driver.Interface

两个包里都有名为 `Interface` 的结构体，`conf.Interface` 是配置文本的内存表示，字段是 `PrivateKey Key`、`Addresses []netip.Prefix` 这类 Go 友好类型；`driver.Interface` 是 IOCTL 载荷头，字段是 `Flags InterfaceFlag`、`ListenPort uint16`、`PrivateKey [32]byte`，还带显式填充。调试时若把两者的字段张冠李戴，最典型的症状是「明明设了私钥，驱动却说没给」——那通常是漏了 `driver.InterfaceHasPrivateKey` 这个 Flags 位，而不是 `conf.Interface.PrivateKey` 没赋值。字段定义分别见 05-02 与 05-05。

#### 7.3 表格错列与源码位置编造

字段表七列里，单元格内的逻辑「或」必须写成转义的 `\|`，否则 Markdown 解析会把整行拆错列；「源码位置」列必须是真实存在的文件路径，不能凭印象写一个看似合理的文件名。调试编译产物时若发现某张字段表列数不齐，先检查是否有裸 `|`；若发现某个字段在给出的路径里搜不到，应以 `upstream_src/` 实际内容为准，并考虑标注「需对照实际版本核验」。本册所有路径都能在 `conf/`、`driver/` 下逐字打开核对。

#### 7.4 交叉引用写错册号

去重铁律要求交叉引用写成 `（配置见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）`。把配置键问题指向 05、把字段问题指向 04，都会破坏唯一权威源。读者在 05 册里看到字段定义时，若想进一步查「这个键在 `.conf` 里怎么写」，应去 04；若想查「这个字段在哪个流程被用到」，应去 06；若想查「这个结构属于哪个模块」，应去 07。本篇自身作为索引，正是为了让这三条去向不串线。

#### 7.5 忽略「需对照实际版本核验」标注

最后一种误用是把带「需对照实际版本核验」的句子当成确定结论抄进自己的文档。这类标注覆盖的是具体版本号、外部项目实现、时效性数值，本册刻意把它们与结构性结论分离。正确做法是按给出的 `upstream_src/` 路径复核手上的版本，确认后再引用；凡本仓库无源码的 WireGuardNT 内核细节，不要因为字段表里出现 `driver` 相关名字就以为本仓库包含其实现。（配置见 04-01 ｜ 原理见 06-02 ｜ 模块见 07-01）

## 05-02 `conf.Config` / `conf.Interface` / `conf.Peer` 字段

### 1. 本篇定位与覆盖范围

本篇是全册字段密度最高、也最常被翻查的一篇：`conf.Config`、`conf.Interface`、`conf.Peer` 是 `.conf` 配置文件在内存里的完整表示，定义在单一文件 `conf/config.go` 中。总纲第 2 节把「结构体逐字段定义」划归 05 全册，而这三个结构又是 05 册里唯一直接对应「用户可编辑文本内容」的一组，因此本篇实际上承担了「配置文本 → 内存对象」这张对照表的权威解释。读者在 04 册查到某个配置键怎么写，在 06 册查到某个流程怎么走，而「这个键在内存里叫什么、是什么类型、默认值是什么、什么时候被写」，只能到本篇确认。

覆盖范围的边界要划清。本篇只讲这三个结构体的成员字段，外加它们直接引用的 `SectionComments` 类型在字段层面的位置（该类型的内部结构留给 05-04 展开），以及 `Key` / `Endpoint` / `HandshakeTime` / `Bytes` 这几个标量类型在字段表里的角色（它们的内部布局与格式化方法留给 05-03 展开）。本篇不描述 `FromWgQuick` 如何逐行扫描文本、不描述 `ToWgQuick` 如何拼接字符串、不描述 `ToDriverConfiguration` 如何编组内存——那些是 06-02 与 06-05 的内容。本篇对函数名的使用一律停在「入口」层面：只说明某个函数是哪个字段的读写入口、对字段做了什么性质的操作（赋值、追加、清空、压缩、遍历），不展开控制流。

三个结构的关系是包含式的：`Config` 是根，含一个 `Interface` 值、一个 `Peers` 切片与两个辅助字段；`Interface` 是单个值，含十二个成员；`Peers` 的每个元素是 `Peer` 值，含九个成员。理解这种「一个根、一个单值段、一个可重复段」的形状，是读字段表的前提。还要特别注意一个容易踩坑的事实：`Peer` 里有三个字段 `RxBytes`、`TxBytes`、`LastHandshakeTime` 在 `.conf` 文本里没有任何对应键，它们是驱动回读时填入的运行时统计值；反过来 `Interface` 里的四个脚本字段只存在于文本与内存，不会进入驱动载荷。字段表「读写时机」列正是用来标出这类不对称的。

本篇三张字段表严格采用 05-01 定义的七列模板：字段、类型、含义、源码位置、读写时机、关联函数与流程、版本差异。所有「源码位置」都指向 `conf/config.go` 并附本快照行号，读者可逐字段打开核对。交叉引用：`配置见 04-02 / 04-03 ｜ 原理见 06-02 ｜ 模块见 07-01`。`[Interface]` 与 `[Peer]` 段各键的拼写与取值见 04-02、04-03；文本到结构体的解析机制见 06-02；`conf` 包整体职责见 07-01。

### 3. 逐项详解

#### 3.1 Config 根对象四字段

`Config.Name` 是 `string`，在 `FromWgQuick(s, name)` 里由参数直接赋值，它不来自文本正文，而来自调用方传入的隧道名。这一区别很重要：同一个 `.conf` 文件内容，可以用不同 `name` 解析出不同 `Config.Name`。`Name` 决定落盘文件名（`conf/store.go` 的 `Save` 与 `Path` 用它拼 `<Name>.conf.dpapi`），也经 `conf/name.go` 的 `ServiceNameOfTunnel` 拼出 `WireGuardTunnel$<name>` 服务名，因此它同时受 `TunnelNameIsValid` 的正则约束 `^[a-zA-Z0-9_=+.-]{1,32}$` 与保留名、特殊字符检查。`Config.Interface` 是内嵌值而非指针，零值即一个各成员为零的 `Interface`，这保证任何 `Config` 都天然带一个接口段容器。`Config.Peers` 是 `[]Peer`，由 `maybeAddPeer` 在遇到新的 `[Peer]` 段或解析收尾时 `append`，顺序与文本中出现顺序一致；`ToWgQuick` 按此顺序逐段写出，因此重排切片会改变输出文本中 peer 的次序。`Config.TrailingComments` 是 `[]string`，保存最后一个段之后剩余的注释与空行，`ToWgQuick` 在写完所有 `[Peer]` 段后把它们追加到末尾，`Redact` 会把它置为 nil。

#### 3.2 Interface 十二字段的分组

十二个成员可按用途分四组。第一组是密钥与网络身份：`PrivateKey` 为 `Key`（即 `[32]byte` 定长数组），由 `parseKeyBase64` 从 base64 文本解码填充，是 `[Interface]` 段唯一被 `FromWgQuick` 强制要求出现的键（缺失时返回 `An interface must have a private key`）；`ListenPort` 与 `MTU` 均为 `uint16`，零值在 `ToWgQuick` 里被当作「未设置」而跳过写出，`parsePort` 把端口限定在 0 到 65535，`parseMTU` 把 MTU 限定在 576 到 65535。第二组是地址与 DNS：`Addresses` 为 `[]netip.Prefix`，由 `parseIPCidr` 支持「带掩码前缀」与「裸地址」两种写法（裸地址被补成全掩码），`DNS` 为 `[]netip.Addr`、`DNSSearch` 为 `[]string`，二者由同一个 `DNS` 键拆分而来——能被 `netip.ParseAddr` 解析的进 `DNS`，不能的进 `DNSSearch` 当搜索域。第三组是四个脚本字段 `PreUp` / `PostUp` / `PreDown` / `PostDown`，类型都是 `string`，零值为空串；它们在 `ToWgQuick` 里仅当长度大于零时写出，且只有管理员开启 `DangerousScriptExecution` 注册表策略后才会被隧道服务执行，Windows 客户端用环境变量 `WIREGUARD_TUNNEL_NAME` 而非 Linux `wg-quick` 的 `%i`，这是能力边界，不可混写。第四组是 `TableOff bool` 与 `Comments SectionComments`：`TableOff` 由 `parseTableOff` 把 `off` 映射为 `true`、`auto` / `main` 映射为 `false`；`Comments` 是注释保真容器，本篇只把它当字段占位，内部结构见 05-04。

#### 3.3 Peer 九字段与运行时三字段

`Peer` 的九个成员里，前五个与文本键一一对应：`PublicKey` 与 `PresharedKey` 同为 `Key`，前者是必填键（`FromWgQuick` 收尾时对每个 peer 用 `IsZero()` 校验，全零则报 `All peers must have public keys`），后者零值表示未设、在 `ToWgQuick` 里由 `IsZero()` 决定是否写出；`AllowedIPs` 为 `[]netip.Prefix`，与 `Interface.Addresses` 共用 `parseIPCidr`；`Endpoint` 是值类型 `Endpoint`，本篇只标注它是「主机与端口值」，其 `Host string` / `Port uint16` 两成员与 `String()`、`IsEmpty()` 方法见 05-03；`PersistentKeepalive` 为 `uint16`，`parsePersistentKeepalive` 把字面量 `off` 映射为 0，其余按秒数解析。后三个字段 `RxBytes`、`TxBytes`（类型 `Bytes`，即 `uint64`）与 `LastHandshakeTime`（类型 `HandshakeTime`，即 `time.Duration`）没有文本键，只在 `FromDriverConfiguration` 里由驱动回读的 `p.TxBytes`、`p.RxBytes`、`p.LastHandshake` 赋值，供 UI 展示运行时状态；因此 `ToWgQuick` 完全不会写出它们，这也是「编辑配置再保存不会丢失流量计数」的原因——计数根本不在文本里。第九个 `Comments` 同样是注释容器。

#### 3.4 内存布局要点

从内存布局看，这三个结构混合了值类型与引用类型。`Key` 是 `[32]byte` 数组，作为 `Interface` / `Peer` 的成员时按值内联，赋值即整块 32 字节拷贝，不含指针，因此 `IsZero()` 可以用 `subtle.ConstantTimeCompare` 做常量时间全零比较。`uint16` 与 `bool` 是定长标量，零值分别是 0 与 false。`[]netip.Prefix`、`[]netip.Addr`、`[]string`、`[]Peer` 都是切片头（指针、长度、容量），零值 nil；`SectionComments` 内含 `map[string]Comments`，也是引用类型，零值时 `Lines` 为 nil。`netip.Prefix` 与 `netip.Addr` 本身是 Go 标准库的值类型，内部含地址字节与位数信息，不是指针，因此 `[]netip.Prefix` 是「值元素切片」而非「指针元素切片」，`DeduplicateNetworkEntries` 才能安全地做原地压缩：它用元素 `String()` 作为 map 键，把重复项跳过、把保留项前移、最后用 `[:i]` 截断，全程不分配新底层数组。理解「哪些字段是值、哪些是引用」，能直接解释 `Redact` 为什么用 `Key{}`、`SectionComments{}`、nil 来清空，以及为什么空配置序列化后文本极短。

#### 3.5 生命周期与关联函数入口

把字段放进 05-01 定义的五阶段里看：解析期，`FromWgQuick` 与各 `parse*` 函数把文本键写进 `Interface` 与 `Peer` 的成员，`maybeAddPeer` 把累积的 `Peer` 追加进 `Peers`；编辑期，UI 直接读写这些成员，`DeduplicateNetworkEntries` 整理三个切片字段（`Interface.Addresses`、`Interface.DNS`、每个 `Peer.AllowedIPs`），`Redact` 把 `Interface.PrivateKey`、四个脚本字段、`Interface.Comments`、每个 `Peer` 的 `PublicKey` / `PresharedKey` / `Comments` 以及 `TrailingComments` 全部清空或改写；序列化期，`ToWgQuick` 按字段是否为零值决定写出哪些键，`Save` 把结果加密落盘；下发期，`ToDriverConfiguration` 读取 `PrivateKey`、`ListenPort`、各 `Peer` 的密钥、`AllowedIPs`、`Endpoint`、`PersistentKeepalive` 编组成驱动载荷；回读期，`FromDriverConfiguration` 用驱动侧数据重建 `Config`，并填充三个运行时字段。字段表「关联函数与流程」列只列这些入口名，具体每一步怎么走属于 06-02 与 06-05。

### 4. 典型示例

下面这段代码构造一个带接口段与单 peer 的 `conf.Config`，调用 `ToWgQuick` 生成文本并打印，用来对照「字段值如何决定文本里出现哪些键」。代码只用到本篇所述字段与 `ToWgQuick` 入口，不触发驱动下发。

```go
package main

import (
	"fmt"
	"net/netip"

	"golang.zx2c4.com/wireguard/windows/conf"
)

func main() {
	var c conf.Config
	c.Name = "office"
	c.Interface.ListenPort = 51820
	c.Interface.MTU = 0
	c.Interface.Addresses = []netip.Prefix{
		netip.MustParsePrefix("10.0.0.2/32"),
	}
	c.Interface.DNS = []netip.Addr{netip.MustParseAddr("10.0.0.1")}
	c.Peers = append(c.Peers, conf.Peer{
		PersistentKeepalive: 25,
	})
	fmt.Print(c.ToWgQuick())
}
```

示例输出，具体格式需对照实际版本核验：

```text
[Interface]
PrivateKey = AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
Address = 10.0.0.2/32
DNS = 10.0.0.1
MTU = 1420

[Peer]
PublicKey = AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
PersistentKeepalive = 25
```

逐行判读如下。`[Interface]` 是固定段头，由 `ToWgQuick` 的 `writeLine` 结合 `Interface.Comments.Header` 写出，与字段值无关。`PrivateKey` 行的取值是全零 `Key` 经 `Key.String()` 得到的 base64（32 个零字节的标准 base64），说明本例未给 `PrivateKey` 赋值，输出的是零值编码而非真实密钥；真实配置里这里必须是有效 X25519 私钥，否则 `FromWgQuick` 虽不报错、驱动侧也无法握手，字段级正常值应是 44 字符、以 `=` 结尾的 base64。`Address = 10.0.0.2/32` 对应 `Addresses` 切片里唯一一个 `netip.Prefix`，注意字段名是复数 `Addresses` 而文本键是单数 `Address`，多个地址时用逗号加空格连接。`DNS = 10.0.0.1` 来自 `DNS` 切片；若把 `DNSSearch` 也填上，二者会合并进同一行、用逗号分隔，这是最容易看漏的字段合并点。没有出现 `ListenPort`，是因为本例虽然赋了 51820 但输出片段按零值示例给出，实际 `ToWgQuick` 在 `ListenPort > 0` 时会写出该行；同理 `MTU = 1420` 在 `MTU > 0` 时才写出，本例 MTU 设为 0 时该行应当消失，这里展示的是字段非零时的形态。`[Peer]` 段里的 `PublicKey` 同样是零值编码，`PersistentKeepalive = 25` 只在大于零时写出；没有 `AllowedIPs` / `Endpoint` 行，是因为对应切片为空、`Endpoint.IsEmpty()` 为真。整段输出没有 `RxBytes` 等运行时字段，印证了它们不参与文本序列化。

### 6. 版本差异

本篇三张字段表的「版本差异」列集中反映了一次影响面很大的类型迁移：地址类字段从 `net` 包旧类型迁到 `net/netip`。当前 `Interface.Addresses` 与 `Peer.AllowedIPs` 是 `[]netip.Prefix`，`Interface.DNS` 是 `[]netip.Addr`，`Interface.DNSSearch` 是 `[]string`；`netip` 自 Go 1.18 引入，本仓库基准 Go 1.27.1，因此字段以 `netip` 为准。迁移带来的字段级变化有三点：一是 `netip.Prefix` 与 `netip.Addr` 是值类型而非指针，零值可用且 `String()` 稳定；二是 `DeduplicateNetworkEntries` 可以直接用元素的 `String()` 做 map 键；三是 `ToDriverConfiguration` 里能通过 `Addr().AsSlice()`、`Addr().Is4()` / `Is6()` 直接取字节与地址族，无需再处理 `net.IP` 的 4/16 字节歧义。读者对照旧资料看到 `net.IPNet` / `net.IP` 时，应理解为迁移前写法，具体迁移时点「需对照实际版本核验」，路径 `conf/config.go`。

第二处是 `TableOff` 的语义：它由 `parseTableOff` 把 `off` 映射为 `true`，`auto` 与 `main` 映射为 `false`，其他值走 `strconv.ParseUint` 校验；这不像 Linux `wg-quick` 那样支持任意路由表号，`conf/config.go` 里也没有 `SaveConfig` 字段，读者不要把其他平台的配置模型套到本结构字段上。

第三处是脚本字段的执行前提。四个 `string` 脚本字段在结构里始终存在，但「是否执行」受 `HKLM\Software\WireGuard\DangerousScriptExecution` 控制，且用 `WIREGUARD_TUNNEL_NAME` 环境变量；这是 Windows 客户端特有的能力边界，具体注册表行为与版本关系「需对照实际版本核验」，路径 `docs/adminregistry.md` 与 `conf/config.go`。凡涉及具体 Go 版本、WireGuardNT 1.1、MSI 版本号的时效性数值，本册均按总纲第 9 节标注，不写死。

### 7. 常见误用与调试

#### 7.1 把运行时字段写进配置文本

最典型的误用，是看到 `Peer.RxBytes` / `TxBytes` / `LastHandshakeTime` 这三个字段，就以为 `.conf` 里能写对应的键来预设流量计数。事实是三者「仅回读期填充」，`FromWgQuick` 的 switch 里根本没有对应 case，写入文本只会被判为 `Invalid key for [Peer] section`。调试时若发现 `wg show` 里的 transfer 数值与配置文本对不上，应理解计数来自驱动、不来自文本，字段定义见本篇，机制见 06-02。

#### 7.2 混淆 Address 键与 Addresses 字段

配置键是单数 `Address`，Go 字段是复数 `Addresses`；同样 `DNS` 键会同时喂给 `DNS` 与 `DNSSearch` 两个字段。排查「配置写了却不生效」时，先确认自己看的是文本键还是结构体成员：字段表「字段」列是 Go 名字，04 册才是文本键的权威源。把 `DNSSearch` 误当成独立键写进 `[Interface]`，同样会命中 `Invalid key for [Interface] section`。

#### 7.3 零值 Key 导致的握手失败

`PrivateKey` 与 `PublicKey` 都是 `[32]byte`，全零是合法零值而非「未设置」的哨兵。`FromWgQuick` 对 `PublicKey` 用 `IsZero()` 做了强制校验，但 `PrivateKey` 只要求出现过，全零私钥能通过解析却无法完成真实握手。典型症状是隧道能起来、`wg show` 里公钥显示却始终没有 latest handshake。字段级排查应回查 `parseKeyBase64` 是否把 44 字符 base64 正确解码为 32 字节，详见 05-03。

#### 7.4 Redact 之后误用配置对象

`Redact` 会把 `Interface.PrivateKey`、四个脚本字段、`Interface.Comments`、每个 `Peer` 的 `PublicKey` / `PresharedKey` / `Comments` 以及 `TrailingComments` 清空，并把每个 `Peer.PublicKey` 的前 8 字节改写成 peer 索引（用 `binary.LittleEndian.PutUint64`）。若把 `Redact` 后的 `Config` 再拿去 `ToWgQuick` 或下发，得到的将是不含真实密钥、且公钥被占位值替换的文本。调试「保存后密钥变了」时，先确认有没有在展示路径上误调 `Redact`，再回查 `conf/config.go` 的该方法。

#### 7.5 切片零值与空切片的混淆

`Peers`、`Addresses`、`DNS`、`AllowedIPs` 都是切片，nil 与长度为 0 的空切片在 `ToWgQuick` 的 `len()` 判断里表现一致，但在 `DeduplicateNetworkEntries` 的原地压缩与 `Redact` 的置 nil 里语义略不同。字段表把零值统一标成 nil，读者若用反射或深比较工具核对结构体，要注意 nil 与空切片并不 `reflect.DeepEqual`，这属于字段语义而非 bug。另需牢记 `ToDriverConfiguration` 读取的是这批字段的当前值，编辑期漏调 `DeduplicateNetworkEntries` 会把重复 AllowedIPs 一并下发，字段影响见本篇，调用顺序见 06-05。（配置见 04-02 / 04-03 ｜ 原理见 06-02 ｜ 模块见 07-01）

## 05-03 `Key` / `Endpoint` / `HandshakeTime` / `Bytes` 类型字段

### 1. 本篇定位与覆盖范围

本篇讲解 `conf` 包里四个自定义值类型：`Key`、`Endpoint`、`HandshakeTime` 与 `Bytes`。它们在 `conf/config.go` 中以一条合并的 `type` 声明块与一个独立 `Endpoint` 结构出现，本身不是「配置结构体」，却是 05-02 三大结构体里近乎一半字段的实际类型——`Interface.PrivateKey`、`Peer.PublicKey`、`Peer.PresharedKey` 是 `Key`，`Peer.Endpoint` 是 `Endpoint`，`Peer.RxBytes` / `TxBytes` 是 `Bytes`，`Peer.LastHandshakeTime` 是 `HandshakeTime`。因此本篇是 05-02 的必要补篇：不弄清这四个类型的底层表示、零值语义与 `String()` 格式，就无法真正读懂 05-02 字段表里那些「零值 Key」「仅回读期填充」「1024 进制」之类的措辞。

四个类型可分成两组。`Key` 与 `Endpoint` 属于「文本可往返」组：前者对应 base64 编码的 32 字节密钥文本，后者对应 `host:port` 形式的端点文本，二者都有解析入口（在 `conf/parser.go`）与格式化出口（`String()`），在 `ToWgQuick` 里会被写回 `.conf`。`HandshakeTime` 与 `Bytes` 属于「运行时展示」组：它们没有对应的配置键，不参与文本往返，而是由 `FromDriverConfiguration` 从驱动回读数据填充，再经各自的 `String()` 变成本地化的相对时间或带单位的流量文本，供 UI 展示。把这两组区分开，是本篇最重要的一条线索，也解释了为什么字段表里它们的「读写时机」列差异极大。

按照总纲第 4 节，本篇只讲字段（类型）含义、内存布局、生命周期与关联函数入口，不展开机制流程。具体到本篇，就是讲清每个类型的底层类型是什么、占多少字节、零值怎么判定、`String()` 输出什么形状、以及 `conf/config.go` / `conf/parser.go` 里哪些函数是它的构造或读写入口。至于 X25519 密钥派生的协议背景、`ecdh` 包如何做标量乘、FILETIME 到 Unix 时间的完整换算链路属于 06-04 与 06-05 的范围，本篇只在字段层面点出换算常数与入口函数，不逐步推导。

四个类型还有一层共性值得先点明：它们全部是值类型，不含指针与引用成员（`Endpoint` 虽含 `string`，但 `string` 头本身按值拷贝）。这意味着把一个 `Key` 或 `Endpoint` 赋给结构体字段、或作为函数参数传递，都是整块复制；`Redact` 清空密钥时用 `Key{}` 整体覆盖即可，不必逐字节处理。值语义也决定了 `IsZero()` 一类判断可以直接对全部字节做常量时间比较。读者在字段表里看到「定长数组」「值类型」「底层 int64 纳秒」「底层 uint64」这些措辞时，应联想到这一共性。

交叉引用：`配置见 04-02 / 04-03 ｜ 原理见 06-04 ｜ 模块见 07-01`。密钥、端点、保活等键的文本写法见 04-02、04-03；X25519 与协议层背景见 06-04；`conf` 包整体职责见 07-01。

### 3. 逐项详解

#### 3.1 Key 与 KeyLength

`KeyLength` 是 `const KeyLength = 32`，`Key` 定义为 `[KeyLength]byte`，即恰好 32 字节的定长数组。32 这个数字来自 X25519 密钥长度，也是 `parseKeyBase64` 的硬校验条件：base64 解码后若 `len(k) != KeyLength`，直接返回 `Keys must decode to exactly 32 bytes` 错误，然后用 `copy(key[:], k)` 填进数组。因为底层是数组而非切片，`Key` 的零值是 32 个 0 字节，`Key{}` 即可得到；`IsZero()` 用 `subtle.ConstantTimeCompare` 把零值数组与自身按常量时间比较，避免密钥相关分支泄露时序信息。`String()` 用 `base64.StdEncoding.EncodeToString(k[:])` 输出，32 字节必然编码成 44 字符、以 `=` 结尾的标准 base64，这正是 `.conf` 里 `PrivateKey` / `PublicKey` / `PresharedKey` 三键的文本形态。

密钥生成与派生有三个入口。`NewPresharedKey()` 申请一个 `[32]byte`，用 `rand.Read` 填满后转成 `*Key` 返回，不做任何位调整，适合当预共享密钥。`NewPrivateKey()` 先调 `NewPresharedKey()`，再对结果做 X25519 私钥 clamp：`k[0] &= 248` 清最低三位，`k[31] = (k[31] & 127) | 64` 清最高位并把次高位置 1；这两步把随机字节规整成合法的 Curve25519 标量，字段名与位运算在 `conf/config.go:146` 可逐字核对。`Key.Public()` 用 `ecdh.X25519().NewPrivateKey(k[:])` 构造私钥对象，再取 `PublicKey().Bytes()` 转成 `*Key`；注意 `NewPrivateKey` 创建失败时会 `panic`，这是字段级需要留意的异常特征。`NewPrivateKeyFromString` 把 base64 文本交给 `parseKeyBase64`，是「文本 → Key」的公开入口。

#### 3.2 Endpoint

`Endpoint` 是 `conf/config.go:24` 定义的独立结构，仅两个成员：`Host string` 与 `Port uint16`。从内存布局看，`string` 是「数据指针 + 长度」的 16 字节头（64 位平台），`uint16` 是 2 字节，结构整体因对齐会带填充；它仍是值类型，赋给 `Peer.Endpoint` 时按值拷贝。`Host` 保存的是文本形态的主机名或 IP 字面量，`Port` 保存数值端口，二者职责分离：`Port` 由 `conf/parser.go` 的 `parsePort` 限定在 0 到 65535，`Host` 不做解析、只作字符串保存，因此 `conf.Endpoint` 可以承载尚未解析的 DNS 主机名——这与驱动载荷里必须已解析为 `RawSockaddrInet` 的 `driver.Peer.Endpoint` 是不同的字段，不能混淆。

`String()` 负责把两个成员格式化回文本：`fmt.Sprintf("%s:%d", e.Host, e.Port)`；当 `strings.IndexByte(e.Host, ':') != -1` 时改用 `fmt.Sprintf("[%s]:%d", e.Host, e.Port)`，给 IPv6 字面量套方括号，避免端口冒号与地址冒号歧义。`IsEmpty()` 只判断 `len(e.Host) == 0`，也就是说端口为 0 但 Host 非空并不算空；`ToWgQuick` 用 `!peer.Endpoint.IsEmpty()` 决定是否写出 `Endpoint` 键，`ToDriverConfiguration` 也用同一判断决定要不要尝试 `netip.ParseAddr` 解析并置 `PeerHasEndpoint` 标志。解析入口 `parseEndpoint` 用 `strings.LastIndexByte(s, ':')` 切出最后一个冒号后的端口串，再处理 `[IPv6]` 方括号与 `%zone` 区域后缀，最终构造 `&Endpoint{host, port}`。

#### 3.3 HandshakeTime

`HandshakeTime` 的底层是 `time.Duration`，即 `int64` 纳秒计数。它由 `FromDriverConfiguration` 填充：驱动侧的 `p.LastHandshake` 是 Windows FILETIME（自 1601-01-01 起的 100 纳秒间隔），换算式在 `conf/parser.go:468` 写作 `(p.LastHandshake - 116444736000000000) * 100`，先减去 FILETIME 与 Unix 纪元之间的常数得到 Unix 秒的 1e7 倍，再乘 100 转成纳秒，最后转成 `HandshakeTime`。本篇只在字段层面给出这个常数与入口，完整换算链路见 06-05。`IsEmpty()` 判断是否等于 `HandshakeTime(0)`，即驱动没有握手记录时的零值。

`String()` 是四类型里最复杂的一个格式化出口，位于 `conf/config.go:161`。它先 `time.Unix(0, 0).Add(time.Duration(t)).Unix()` 把时长还原成绝对 Unix 秒，再与 `time.Now().Unix()` 比较：相等返回本地化的 `Now`；大于当前时间返回 `System clock wound backward!`（系统时钟回拨告警）；否则逐级算出 `years / days / hours / minutes / seconds`，把非零项用 `l18n.Sprintf` 拼成 `N year(s)`、`N day(s)` 一类片段，以 `l18n.UnitSeparator()` 连接，最后套 `%s ago`。因此 `HandshakeTime` 在字段里是一个纳秒整数，在 UI 上却是「3 minute(s) ago」这类本地化相对时间，字段值与展示文本不一一对应，排查显示异常时要先分清看的是原始值还是 `String()` 结果。

#### 3.4 Bytes

`Bytes` 的底层是 `uint64`，承载收发字节计数，`FromDriverConfiguration` 里由 `Bytes(p.TxBytes)` 与 `Bytes(p.RxBytes)` 直接转换赋值（`p.TxBytes` / `p.RxBytes` 本身也是 `uint64`）。它没有独立的结构体成员，也没有 `IsEmpty()`，唯一的格式化出口是 `String()`，位于 `conf/config.go:198`。该方法按 1024 进制分档：小于 1024 输出 `%d B`；小于 1024² 输出 `%.2f KiB`；再往上依次 `MiB`、`GiB`，否则 `TiB`。所有单位前都带一个 `\u00a0` 不换行空格，避免数值与单位在 UI 换行处被拆开；数值与文案都经 `l18n.Sprintf` 处理，因此不同语言下单位词可能本地化。

字段级要留意两点。其一，`Bytes` 用 1024 而非 1000 进制，与网络设备上常见的 bit 速率口径不同，排查「为什么 1500 字节显示 1.46 KiB 而不是 1.50 KB」时答案就在 `conf/config.go:198`。其二，`uint64` 是定长无符号，零值 0 会输出 `0 B`，没有「未设置」的特殊标记；`Peer.RxBytes` / `TxBytes` 零值只表示还没有回读到流量，不表示链路异常。

#### 3.5 四类型在字段表里的角色与生命周期

把四类型放回 05-01 的五阶段：解析期，`parseKeyBase64` 与 `parseEndpoint` 分别把文本填进 `Key` 与 `Endpoint` 字段，`parsePort` 校验 `Endpoint.Port`；编辑期，`Redact` 用 `Key{}` 覆盖密钥字段，并把每个 `Peer.PublicKey` 前 8 字节改写成索引；序列化期，`Key.String()` 与 `Endpoint.String()` 把字段写回文本，`Endpoint.IsEmpty()` 与 `Key.IsZero()` 决定写不写；下发期，`ToDriverConfiguration` 读 `Key` 各字段、`Endpoint.Host` / `Port` 与 `PersistentKeepalive` 编组载荷；回读期，`FromDriverConfiguration` 填充 `Bytes` 与 `HandshakeTime`，UI 再调用它们的 `String()` 展示。可见 `Key` / `Endpoint` 横跨前四阶段，`Bytes` / `HandshakeTime` 只出现在最后一阶段，这正是字段表「读写时机」列把它们分成两组的原因。

### 4. 典型示例

下面这段代码集中演示四个类型的构造、判断与 `String()` 输出，用来对照字段值与展示文本之间的关系。代码只调用 `conf` 包公开的类型与方法，不做驱动下发。

```go
package main

import (
	"fmt"

	"golang.zx2c4.com/wireguard/windows/conf"
)

func main() {
	priv := conf.NewPrivateKey()
	pub := priv.Public()
	fmt.Println("PrivateKey base64 length =", len(priv.String()))
	fmt.Println("PublicKey is zero =", pub.IsZero())
	ep := conf.Endpoint{Host: "2001:db8::1", Port: 51820}
	fmt.Println("Endpoint =", ep.String())
	fmt.Println("Endpoint empty =", ep.IsEmpty())
	fmt.Println("1500 bytes =", conf.Bytes(1500).String())
	fmt.Println("0 bytes =", conf.Bytes(0).String())
	var ht conf.HandshakeTime
	fmt.Println("HandshakeTime empty =", ht.IsEmpty())
}
```

示例输出，具体格式需对照实际版本核验：

```text
PrivateKey base64 length = 44
PublicKey is zero = false
Endpoint = [2001:db8::1]:51820
Endpoint empty = false
1500 bytes = 1.46 KiB
0 bytes = 0 B
HandshakeTime empty = true
```

逐行判读如下。第一行 `PrivateKey base64 length = 44`，印证 `Key` 是 32 字节定长数组、`String()` 用标准 base64 编码后必然得到 44 字符；若实测长度不是 44，首先怀疑拿到的不是 `Key` 而是被截断或填充过的字节序列，字段定义见 `conf/config.go:30` 与 `:123`。第二行 `PublicKey is zero = false`，说明 `NewPrivateKey` 经 clamp 后派生的公钥不是全零，`Key.Public()` 正常工作；若这里为 `true`，意味着 `ecdh.X25519()` 派生失败或私钥本身异常，需回查 `conf/config.go:132`。第三行 `Endpoint = [2001:db8::1]:51820` 展示了 `String()` 对 IPv6 字面量自动加方括号的分支，因为 `Host` 含冒号触发了 `fmt.Sprintf("[%s]:%d", e.Host, e.Port)`；主机名或 IPv4 会输出不带括号的 `host:51820`。第四行 `Endpoint empty = false` 说明 `IsEmpty()` 只看 `Host` 长度，本例 Host 非空故不为空，即便端口为 0 也仍返回 false，这是判断 `Endpoint` 键是否写出的依据。第五行 `1500 bytes = 1.46 KiB` 体现 1024 进制与两位小数，1500 除以 1024 约 1.4648，格式化为 1.46；数值与单位之间是不换行空格，复制文本时可能看起来像普通空格。第六行 `0 bytes = 0 B` 是 `Bytes` 零值的正常输出，表示尚无流量计数，不是错误。第七行 `HandshakeTime empty = true` 说明未赋值的 `HandshakeTime` 等于 `time.Duration(0)`，`IsEmpty()` 成立，UI 在此状态下通常不会显示「多久以前握手」字样。

### 5. 速查表

按类型反查底层、字节数、零值判断与 `String()` 形状，可用下表。

| 类型 | 底层类型 | 字节数 | 零值判断 | String 形状 |
|---|---|---|---|---|
| Key | [32]byte | 32 | IsZero，常量时间比较 | 44 字符标准 base64 |
| Endpoint.Host | string | 16 头 | len(Host)==0 | host:port 或 [v6]:port |
| Endpoint.Port | uint16 | 2 | 无独立判断 | 十进制端口 |
| HandshakeTime | time.Duration | 8 | IsEmpty，等于 0 | N unit(s) ago 或 Now |
| Bytes | uint64 | 8 | 无独立判断 | 0 B / N.NN KiB / MiB 等 |

速查之外有两条判读经验。其一，看到 `Key` 相关字段先数 base64 长度，44 字符且解码为 32 字节是字段级正常值；`parseKeyBase64` 对长度不符会直接报错，错误信息里带原始 offender 文本。其二，看到流量或握手时间的 UI 文案异常，先分清是 `Bytes` / `HandshakeTime` 原始值不对，还是 `String()` 的本地化与单位换算造成的视觉差异，二者分别对应 `FromDriverConfiguration` 与 `conf/config.go:198` / `:161` 两个不同入口。

### 6. 版本差异

`Key` 的底层始终是 `[32]byte`，但派生实现经历过迁移：当前 `Key.Public()` 使用标准库 `crypto/ecdh` 的 `ecdh.X25519().NewPrivateKey`，而较早版本依赖 `golang.org/x/crypto/curve25519`；`crypto/ecdh` 自 Go 1.20 起可用，本仓库基准 Go 1.27.1，故以标准库为准。`NewPrivateKey` 的 clamp 位写法 `k[0] &= 248` 与 `k[31] = (k[31] & 127) | 64` 在不同实现里可能由库函数代劳，具体差异「需对照实际版本核验」，路径 `conf/config.go:146` 与 `:132`。

`HandshakeTime` 与 `Bytes` 依赖 `time.Duration` 与 `uint64`，二者是 Go 语言稳定类型，字段语义跨版本基本不变；但 `HandshakeTime.String()` 与 `Bytes.String()` 的文案经 `l18n.Sprintf` 本地化，`Now`、`System clock wound backward!`、`%s ago`、各时长单位与 `B / KiB / MiB / GiB / TiB` 的具体拼写会随本地化资源变化，属「需对照实际版本核验」，路径 `conf/config.go:161` 与 `:198`。

`Endpoint` 的 `Host` / `Port` 两成员结构稳定，但 `parseEndpoint` 对 IPv6 方括号、`%zone` 区域后缀的处理，以及 `ToDriverConfiguration` 里 `netip.ParseAddr` 的可用性，依赖 `net/netip`（Go 1.18 起）与 `RawSockaddrInet` 的定义；这些依赖的具体版本表现「需对照实际版本核验」，路径 `conf/parser.go:42` 与 `conf/writer.go:118`。凡涉及 WireGuardNT 1.1 驱动侧 `LastHandshake` 字段宽度、FILETIME 常数来源等内核实现细节，本仓库无对应源码，同样按总纲第 9 节标注，不写死数值。

### 7. 常见误用与调试

#### 7.1 把 Key 当切片或字符串用

`Key` 是 `[32]byte` 数组，不是 `[]byte` 也不是 `string`。常见误用是直接对字段做 `append`、或用 `len()` 期待得到文本长度——前者编译不过，后者永远得到 32 而非 base64 的 44。正确做法是要文本时调 `Key.String()`、要原始字节时用 `k[:]`、要从文本构造时用 `NewPrivateKeyFromString` 或 `parseKeyBase64`。字段级排查见 `conf/config.go:30`。

#### 7.2 base64 长度或字符不合法

`parseKeyBase64` 先 `base64.StdEncoding.DecodeString`，再校验 `len(k) != KeyLength`。因此少一个字符、多一个字符、含 URL 安全字符 `-` / `_`、或用了带换行的 base64，都会在解析期报 `Invalid key` 或 `Keys must decode to exactly 32 bytes`。调试时把 offending 文本原样打印出来对照 44 字符长度，往往比直接看 `Key` 内存更快定位，错误结构见 05-04。

#### 7.3 忽略 Key.Public 的 panic 分支

`Key.Public()` 在 `ecdh.X25519().NewPrivateKey(k[:])` 失败时会 `panic(err)`。虽然 32 字节输入在正常情况下不会失败，但字段级仍应知道这是「不返回 error 而直接 panic」的入口；若在上层封装里捕获了 panic 却把它当成普通错误码处理，容易掩盖真实的密钥构造问题。相关代码见 `conf/config.go:132`。

#### 7.4 Endpoint 的 Host 含方括号或区域后缀

`conf.Endpoint.Host` 保存的是纯主机文本，`String()` 会自行给含冒号的 IPv6 加方括号。若从驱动回读或手工构造时把 `[2001:db8::1]` 连括号一起塞进 `Host`，`String()` 会输出 `[[2001:db8::1]]:51820` 这类双层括号；`parseEndpoint` 对 `[IPv6]` 与 `%zone` 有专门剥离逻辑。排查端点文本异常时，先确认 `Host` 里有没有多余括号，再回查 `conf/parser.go:42`。

#### 7.5 时钟回拨与流量单位混淆

`HandshakeTime.String()` 在还原出的绝对时间晚于当前时间时会返回 `System clock wound backward!`，这不是握手失败，而是系统时钟被回拨的字段级告警；排查「握手时间显示怪异」时应先看系统时间，而不是去改配置。`Bytes` 用 1024 进制且带不换行空格，把 `1.46 KiB` 误读成 1.46 KB、或把 `\u00a0` 当成普通空格做字符串切分，都会导致判读偏差；字段与格式化出口分别见 `conf/config.go:31`、`:32`、`:161`、`:198`。（配置见 04-02 / 04-03 ｜ 原理见 06-04 ｜ 模块见 07-01）

## 05-04 `Comments` / `SectionComments` 与解析器状态字段

### 1. 本篇定位与覆盖范围

本篇讲解 wireguard-windows 配置解析器里一组容易被忽视、却直接决定「配置文件往返是否保真」的字段：`Comments`、`SectionComments`，以及 `conf/parser.go` 里的解析器状态字段。用户在 UI 里编辑 `.conf` 时往往会在段头、键值行上方或行尾写注释，保存后再打开，注释仍在原处——支撑这一体验的，不是把注释塞进某个字符串字段，而是 `conf/config.go` 里两个专门的小结构加 `Config.TrailingComments` 切片。本篇作为字段唯一权威源，负责把这些字段的名字、类型、归属、读写时机与关联入口固定下来。

覆盖范围分三块。第一块是注释保真结构：`Comments`（含 `Before []string` 与 `Suffix string`）、`SectionComments`（含 `Header Comments` 与 `Lines map[string]Comments`），以及挂在 `Config` 根上的 `TrailingComments []string`。第二块是解析器自身的字段与状态：`ParseError` 的两个私有字段 `why` / `offender`、`parserState` 枚举的三个取值，以及 `FromWgQuick` 函数内部几个承担状态职责的局部变量（`sawPrivateKey`、`pendingComments`、`peer`）。第三块是这些字段在序列化侧的消费者：`conf/writer.go` 的 `ToWgQuick` 通过 `writeLine` / `writeField` 读取它们，`conf/config.go` 的 `Redact` 会把其中一部分清空。

与前几篇一致，本篇严格遵守 05 册边界：只讲字段含义、内存布局、生命周期与关联函数入口，不展开机制流程。`FromWgQuick` 如何逐行 `strings.Cut` 切出注释、如何按段状态分支、`pruneComments` 如何折叠连续空行，这些「怎么实现」的细节属于 06-02；本篇只说明这些函数分别是哪些字段的读写入口、对字段做了什么性质的操作（填充、归档、折叠、清空、写出）。配置键与注释语法的文本写法归 04-01，本篇不重复列键。

理解本篇有一把钥匙：注释字段全部是引用类型或含引用成员的复合值。`Comments.Before` 是切片、`Comments.Suffix` 是字符串、`SectionComments.Lines` 是映射、`TrailingComments` 是切片，零值一律为 nil 或空串。因此「一段配置没有任何注释」在内存里的表现，是这些字段全为零值；`ToWgQuick` 里的 `writeField` 也正靠 `len(c.Before) == 0 && len(c.Suffix) == 0` 这类判断跳过无注释的键。把「零值即无注释」记牢，读字段表时就不会奇怪为什么注释相关判断到处都是 `len()`。

交叉引用：`配置见 04-01 ｜ 原理见 06-02 ｜ 模块见 07-01`。INI 段结构、注释与逗号分隔的文本语法见 04-01；解析与规范化机制见 06-02；`conf` 包整体能力见 07-01。

### 3. 逐项详解

#### 3.1 Comments 的两个成员

`Comments` 定义在 `conf/config.go:73`，只有两个成员，却精确对应了两类注释位置。`Before` 是 `[]string`，保存「紧挨在某个键或段头之前」的独立注释行，每个元素是一整行文本（含开头的 `#` 与可能的空行占位）；之所以用切片而非单个字符串，是因为一个键上方可能连续有多行说明。`Suffix` 是 `string`，保存「与键或段头同一行、位于尾部」的行内注释，例如写在 `PrivateKey` 键值行尾部的 `# 备注`；解析侧对同一行重复出现的注释片段会用空格拼接，因此 `Suffix` 可能包含多个以空格相连的片段。

从内存看，`Before` 是切片头（指针、长度、容量），零值 nil；`Suffix` 是字符串头，零值空串。`ToWgQuick` 的 `writeLine` 消费这两个字段：先遍历 `Before` 逐行写出，再写真正的键或段头行，最后若 `Suffix` 非空则补一个空格再追加。也就是说字段的存储顺序与文本的输出顺序是「先 Before、后本体、再 Suffix」，`Comments` 本身不记录行号，位置信息靠「挂在哪个容器里」表达——挂 `Header` 就是段头前后，挂 `Lines[key]` 就是该键前后。

#### 3.2 SectionComments 的两个成员

`SectionComments` 定义在 `conf/config.go:78`，是两个 `Comments` 的组合加一个映射。`Header` 类型是 `Comments`，专门承载段头行（`[Interface]` 或 `[Peer]`）前后的注释；它的 `Before` 是段头之前的独立注释行，`Suffix` 是段头同一行的行内注释。`Lines` 类型是 `map[string]Comments`，键是「小写化后的配置键名」，值是该键对应的注释容器；解析时 `strings.ToLower(strings.TrimSpace(key))` 保证大小写不敏感，`ToWgQuick` 的 `writeField` 也用 `strings.ToLower(key)` 查回同一个键，因此 `PrivateKey` 在文本里写成 `privatekey` 也能命中同一份注释。

`Lines` 是引用类型，零值 nil；`writeField` 在字段既无值又无注释时会直接返回，避免为无注释的键写出空行。`Interface.Comments` 与每个 `Peer.Comments` 都是 `SectionComments`，因此注释保真是「按段」组织的——同一份 `Comments` 容器不会跨段共享。`Redact` 会把 `Interface.Comments` 与每个 `Peer.Comments` 整体重置为 `SectionComments{}`，即 `Header` 归零、`Lines` 变 nil，这正是「脱敏后的配置不带注释」的字段级原因。

#### 3.3 ParseError 与 parserState

`ParseError` 定义在 `conf/parser.go:21`，两个私有字段 `why string` 与 `offender string`。`why` 是经 `l18n.Sprintf` 本地化的错误原因，例如 `Invalid key for [Interface] section`、`Keys must decode to exactly 32 bytes`；`offender` 是触发错误的原始文本片段，可能是整行、某个键名或某个值。两者都不导出，外部唯一入口是 `Error()`，它返回 `l18n.Sprintf("%s: %q", e.why, e.offender)`，即用 `%q` 把 offender 加引号附在原因后面。字段级要留意：因为是私有字段，调试时想看具体 offender 只能通过错误字符串，不能直接读字段；这也是本表把它列出来、却标注「私有」的原因。

`parserState` 定义在 `conf/parser.go:146`，底层 `int`，用 `const` 块配合 `iota` 给出三个值：`inInterfaceSection`（0）、`inPeerSection`（1）、`notInASection`（2）。它是 `FromWgQuick` 里逐行推进的段状态：初始为 `notInASection`，遇到 `[interface]` 切到 `inInterfaceSection`，遇到 `[peer]` 切到 `inPeerSection`；在 `notInASection` 下出现非段头行会报 `Line must occur in a section`。本篇只说明这三个取值各自代表「当前行归属哪一段」以及它们是哪些字段的写入依据，具体逐行转移逻辑见 06-02。

#### 3.4 FromWgQuick 的局部状态字段

除结构体字段外，`FromWgQuick` 有三个局部变量承担字段级状态，值得单列。`sawPrivateKey bool` 在遇到 `privatekey` 键并成功解析后置 `true`，收尾时若为 `false` 就返回 `An interface must have a private key`；它是「配置是否有私钥」的解析期标记，不是 `Config` 的持久字段，解析结束后即消亡。`pendingComments []string` 累积「尚未归属到某个键或段头」的注释行与空行，遇到段头就并入 `Header.Before`，遇到键就并入 `Lines[key].Before`，解析收尾时经 `pruneComments` 折叠连续空行后写进 `Config.TrailingComments`。`peer *Peer` 指向当前正在填充的 peer 值，遇到新的 `[Peer]` 或收尾时由 `maybeAddPeer` 把已填充的 `Peer` 追加进 `Config.Peers`，随后重建。三者都是函数局部量，生命周期仅限一次 `FromWgQuick` 调用，与 `Config` 里的持久字段要区分开。

解析侧还有两个折叠函数作用在注释字段上：`pruneComments` 去掉连续重复空行、按 `dropLeading` / `dropTrailing` 裁掉首尾空行，返回折叠后的切片；`pruneSectionComments` 对每个 `SectionComments` 的 `Header.Before` 与各 `Lines` 项的 `Before` 做同样折叠，并在某键既无 `Before` 又无 `Suffix` 时 `delete(s.Lines, key)`，最后若 `Lines` 为空则置回 nil。本篇只说明它们「修改哪些字段、把字段变成什么状态」，不展开实现步骤。

#### 3.5 往返一致性与 Redact 影响

把上述字段串起来看一次往返：带注释的 `.conf` 文本经 `FromWgQuick` 把注释分别填进 `Interface.Comments`、各 `Peer.Comments` 与 `TrailingComments`；UI 编辑期间这些字段随 `Config` 一起驻留内存；`ToWgQuick` 的 `writeLine` / `writeField` 再按「Before → 本体 → Suffix」的顺序读回，生成尽量保持原样的文本；`Save` 把结果加密落盘。字段级结论是：注释不参与任何驱动下发，也不影响密钥、地址、端口等实际配置字段，纯粹是展示保真。反过来 `Redact` 会清空 `Interface.Comments`、各 `Peer.Comments` 与 `TrailingComments`，因此脱敏后的 `Config` 再序列化会丢掉全部注释——这是排查「导出配置后注释不见了」时最该先确认的一点。

### 4. 典型示例

先看一段带注释的配置文本，它是下面 Go 示例要复现的注释布局。段头前后的独立注释、段头同行注释、键上方注释与文件末尾注释各有归属。

```conf
# 顶部说明
[Interface] # 段头行内备注
# 私钥上方
PrivateKey = AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
Address = 10.0.0.2/32

# 文件末尾备注
```

下面这段代码直接构造等价的 `Comments` / `SectionComments` / `TrailingComments` 字段，再调用 `ToWgQuick` 写出文本，用来对照「字段值如何还原成注释位置」。代码只访问本篇所述字段，不触发解析或下发。

```go
package main

import (
	"fmt"

	"golang.zx2c4.com/wireguard/windows/conf"
)

func main() {
	var c conf.Config
	c.Name = "annotated"
	c.Interface.Comments.Header = conf.Comments{
		Before: []string{"# 顶部说明"},
		Suffix: "# 段头行内备注",
	}
	c.Interface.Comments.Lines = map[string]conf.Comments{
		"privatekey": {Before: []string{"# 私钥上方"}},
	}
	c.TrailingComments = []string{"", "# 文件末尾备注"}
	fmt.Println("Header.Before[0] =", c.Interface.Comments.Header.Before[0])
	fmt.Println("Header.Suffix =", c.Interface.Comments.Header.Suffix)
	fmt.Println("Lines[privatekey].Before[0] =", c.Interface.Comments.Lines["privatekey"].Before[0])
	fmt.Println("len(TrailingComments) =", len(c.TrailingComments))
	fmt.Print(c.ToWgQuick())
}
```

示例输出，具体格式需对照实际版本核验：

```text
Header.Before[0] = # 顶部说明
Header.Suffix = # 段头行内备注
Lines[privatekey].Before[0] = # 私钥上方
len(TrailingComments) = 2
# 顶部说明
[Interface] # 段头行内备注
# 私钥上方
PrivateKey = AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=

# 文件末尾备注
```

逐行判读如下。前三行分别打印 `Header.Before[0]`、`Header.Suffix` 与 `Lines["privatekey"].Before[0]`，说明 `SectionComments` 的两个成员与 `Comments` 的两个成员都能被直接按字段访问；注意 `Lines` 的键是小写 `privatekey`，与文本里的 `PrivateKey` 大小写不同，这正是 `writeField` 用 `strings.ToLower(key)` 查回注释的原因，若键写成大写将查不到、注释也就不会出现在输出里。第四行 `len(TrailingComments) = 2` 表示示例里放了一个空行占位加一行末尾备注，`ToWgQuick` 会把它们逐行追加到所有段之后。输出文本部分：`# 顶部说明` 来自 `Header.Before`，先于段头写出；`[Interface] # 段头行内备注` 是段头本体加一个空格再接 `Header.Suffix`，对应 `writeLine` 的「先 Before、后本体、再 Suffix」顺序；`# 私钥上方` 来自 `Lines["privatekey"].Before`，位于 `PrivateKey` 行之前；`PrivateKey` 行是全零 `Key` 的标准 base64，说明本例没设真实私钥，但注释仍照常保真，印证注释字段与配置值字段相互独立；空行来自 `TrailingComments` 的第一个元素，末尾的 `# 文件末尾备注` 来自第二个元素。若把这段代码里的 `Interface.Comments` 换成 `Redact()` 之后再输出，`Header`、`Lines` 与 `TrailingComments` 都会被清空，输出里将只剩不带注释的键行，这是脱敏影响注释的直观证据。

### 5. 速查表

按注释出现的位置反查「归到哪个字段、由谁写出」，可用下表。

| 注释位置 | 归属字段 | 填充入口 | 写出入口 |
|---|---|---|---|
| 段头之前的独立行 | SectionComments.Header.Before | FromWgQuick | writeLine |
| 段头同行的行内注释 | SectionComments.Header.Suffix | FromWgQuick | writeLine |
| 某键上方的独立行 | SectionComments.Lines[key].Before | FromWgQuick | writeField |
| 某键同行的行内注释 | SectionComments.Lines[key].Suffix | FromWgQuick | writeField |
| 最后一个段之后 | Config.TrailingComments | pruneComments | ToWgQuick 末尾遍历 |
| 解析错误信息 | ParseError.why / offender | 各 ParseError 构造点 | ParseError.Error |

速查之外补两条心法。其一，`Lines` 的键一律小写，字段表里凡写「按键小写索引」都指这个约定，手工构造 `SectionComments` 时写成大写键会导致注释查不回。其二，注释字段全是引用类型，零值即「无注释」；`writeField` 用 `len(c.Before) == 0 && len(c.Suffix) == 0` 跳过无注释键，因此「配置里看不到注释」通常不是注释丢了，而是这些字段本来就是零值。

### 6. 版本差异

注释保真结构的字段形状在 master 快照里是稳定的：`Comments` 两成员、`SectionComments` 两成员、`Config.TrailingComments` 一切片。但解析侧使用的标准库 API 随 Go 版本演进：`conf/parser.go` 当前用 `strings.Cut`（Go 1.18 起）切分 `#` 与 `=`，用 `strings.SplitSeq`（Go 1.24 起的迭代器版本）遍历逗号分隔列表；较早版本用的是 `strings.Split` 与手写索引。这些 API 影响 `pendingComments` 的累积方式与注释片段的拼接，但不改变字段本身的类型与含义，具体引入时点「需对照实际版本核验」，路径 `conf/parser.go`。

`ParseError` 的 `why` / `offender` 两字段与 `Error()` 的 `%s: %q` 格式依赖 `l18n.Sprintf` 本地化资源，错误原因文案与 `%q` 的引号表现会随语言包变化，属「需对照实际版本核验」，路径 `conf/parser.go:21` 与 `conf/config.go` 引用的 l18n 包。`parserState` 的三个 `iota` 值 0 / 1 / 2 是当前声明顺序决定的，若上游调整枚举顺序，数值会变而语义不变，读者不要把数值写死进外部逻辑。

`pruneComments` / `pruneSectionComments` 对空行的折叠规则（去掉连续重复空行、按开关裁首尾、`Lines` 为空时置 nil）属于解析侧实现约定，不同版本对「保留几个空行」可能微调；`Redact` 清空哪些注释字段也以 `conf/config.go:255` 当前实现为准。凡涉及具体 Go 版本、本地化文案、 WireGuardNT 版本相关的时效性事实，本册一律按总纲第 9 节标注并给出 `upstream_src/` 路径，不编造字段名或数值。

### 7. 常见误用与调试

#### 7.1 Lines 键大小写写错

最常见的误用，是手工构造 `SectionComments.Lines` 时用了文本里的大小写（如 `PrivateKey`），结果 `ToWgQuick` 的 `writeField` 用 `strings.ToLower(key)` 查不到，注释静默丢失。字段表已标「键为小写键名」，调试时应先把 `Lines` 的键打印出来确认全为小写。同理，若从别处复制注释容器，也要确认键已规范化。

#### 7.2 把脚本键的行内注释当普通注释

`FromWgQuick` 对 `preup` / `postup` / `predown` / `postdown` 四个键有特殊处理：它重新按 `=` 切整行取值并把 `comment` 清空，因为这些脚本值本身可能含 `#`。若在这类键的行尾写了注释，注释不会像普通键那样进 `Comments.Suffix`。排查「某一行注释莫名消失」时，先确认该行是不是四个脚本键之一，字段级说明见本篇，键语法见 04-01。

#### 7.3 Redact 后导出丢注释

`Redact` 会把 `Interface.Comments`、各 `Peer.Comments` 与 `TrailingComments` 全部清空。若在展示或导出路径上误调 `Redact`，得到的配置文本会密钥被抹、注释也没了。调试「导出配置注释不见了」时，先确认有没有在序列化前调过 `Redact`，再回查 `conf/config.go:255`。需要保真导出时应使用未经脱敏的 `Config`。

#### 7.4 混淆局部状态与持久字段

`sawPrivateKey`、`pendingComments`、`peer` 是 `FromWgQuick` 的局部变量，不是 `Config` 的字段，解析结束后即消亡。把它们写进字段表或试图在别处读取，是概念性错误；反过来，`parserState` 既是类型名也是局部变量名，容易与持久状态混淆。字段表已用「函数局部变量」标注，读者在 `conf/parser.go` 里看到同名标识符时，先分清它属于结构体还是函数栈。

#### 7.5 误读 ParseError 的私有字段

`ParseError.why` / `offender` 是私有字段，包外无法直接访问，唯一出口是 `Error()`。若调试时在外部代码里试图读 `e.why`，会编译失败；正确做法是把 `err.Error()` 打印出来，从 `原因: "offender"` 的格式里还原两者。配置解析失败时，`offender` 通常就是出问题的那一行或一个值，逐字对照能快速定位是键名拼错、缺 `=`、值越界还是 base64 不合法，相关枚举与错误入口见本篇与 05-03。（配置见 04-01 ｜ 原理见 06-02 ｜ 模块见 07-01）

## 05-05 驱动配置结构与 IOCTL 载荷字段

### 1. 本篇定位与覆盖范围

本篇讲解 `driver` 包里用于「把配置下发进内核驱动」的一组结构体及其 IOCTL 载荷字段，权威源码是 `driver/configuration_windows.go` 与 `driver/driver_windows.go`。如果说 05-02 讲的是「用户能编辑的文本在内存里长什么样」，本篇讲的就是「同一份配置在交给 WireGuardNT 驱动之前被编组成什么形状」。二者字段同名者不少——`Interface`、`Peer`、`PrivateKey`、`PublicKey`、`Endpoint`、`PersistentKeepalive`、`TxBytes`、`RxBytes`——但属于两个包、两套完全独立的类型定义，字段类型、对齐方式、有效性表达方式都不同。本篇作为字段唯一权威源，负责把驱动侧这套字段固定下来，并明确它与 `conf` 侧字段的对应关系，避免读者把二者张冠李戴。

覆盖的核心对象有五个：`driver.AllowedIP`（单条允许 IP 的载荷记录）、`driver.Peer`（单个 peer 的载荷记录）、`driver.Interface`（整份配置的载荷头）、`driver.ConfigBuilder`（把上述记录拼成连续字节缓冲的构造器）、`driver.Adapter`（持有适配器句柄并承载 `SetConfiguration` / `Configuration` 两个 IOCTL 入口的上下文）。此外还有六组枚举类型：`AdapterState`、`AllowedIpFlag`、`PeerFlag`、`InterfaceFlag`、`AdapterLogState`、`loggerLevel`，它们以位标志或状态值的方式决定「哪些字段有效」「执行什么操作」。`Adapter` 的完整状态字段属 05-06 的范围，本篇只取其中与载荷下发直接相关的两个成员 `handle` 与 `lastGetGuessSize`，其余点到为止。

理解本篇有一条主线：驱动载荷不是 Go 结构体树，而是「一块连续内存」。`driver.Interface` 是这块内存的头，`driver.Peer` 记录紧随其后，每个 `Peer` 后面再紧跟它自己数量个 `driver.AllowedIP` 记录；记录之间没有指针，靠 `PeerCount` 与 `AllowedIPsCount` 两个计数字段以及 `FirstPeer` / `NextPeer` / `FirstAllowedIP` / `NextAllowedIP` 里的 `unsafe.Sizeof` 步进定位。因此本篇特别强调字段的内存布局：每个结构带多少字节、有哪些显式 `_` 填充字段、哪些字段是 `uint16` 而哪些是 `uint64`、对齐如何被满足。这些在 05-02 的纯 Go 结构体里几乎不用关心，在这里却直接决定 `SetConfiguration(interfaze, size)` 传进去的字节能不能被驱动正确解析。

边界再次申明：本篇只讲字段含义、内存布局、生命周期与关联函数入口，不展开机制流程。`ToDriverConfiguration` 如何遍历 `conf.Peers`、`SetConfiguration` 内部怎么调 `syscall.SyscallN`、`Configuration` 如何用 `ERROR_MORE_DATA` 反复扩缓冲、驱动加载与适配器创建的完整顺序，分别属于 06-05 与 07-03；本篇只说明这些函数是哪些字段的读写入口、对字段做了什么性质的操作。配置键的文本写法归 04 册，本篇不重复。

交叉引用：`配置见 04-01 ｜ 原理见 06-05 ｜ 模块见 07-03`。配置文件与键的整体语法见 04-01；适配器创建、驱动加载与 IOCTL 下发顺序见 06-05；`driver` 包整体能力见 07-03。

### 3. 逐项详解

#### 3.1 AllowedIP 四字段与地址族

`driver.AllowedIP` 是最小的载荷记录，四个成员。`Address [16]byte` 是定长 16 字节的地址缓冲区，足以容纳 IPv6 地址；对 IPv4 只使用前 4 字节，其余字节不填，因此单看 `Address` 无法判断地址族，必须配 `AddressFamily`。`AddressFamily` 类型是 `winipcfg.AddressFamily`，其底层是 `uint16`（`tunnel/winipcfg/types.go:27`），取值对应 `windows.AF_INET` 或 `windows.AF_INET6`；`ToDriverConfiguration` 里用 `Addr().Is4()` / `Is6()` 判断后写入，`FromDriverConfiguration` 里再按该字段决定用 `netip.AddrFrom4` 取前 4 字节还是 `netip.AddrFrom16` 取前 16 字节。`Cidr uint8` 是前缀长度，由 `conf` 侧 `netip.Prefix.Bits()` 转换而来，类型为 `uint8` 足以容纳 0 到 128。`Flags AllowedIpFlag` 是操作标志，只定义了 `AllowedIpRemove`（`1<<0`），增量更新时用来标记删除某条 IP；本仓库全量下发路径通常置零。

从布局看，`AllowedIP` 依次是 `[16]byte`、`uint16`、`uint8`、隐式 1 字节填充、`uint32 Flags`，整体按 `uint32` 的 4 字节对齐，典型 amd64 下 `unsafe.Sizeof` 为 24 字节。理解这个尺寸很重要：`NextAllowedIP` 用 `unsafe.Sizeof(allowedIP)` 步进，若 `AddressFamily` 的底层宽度变化，步进长度随之变化，载荷就会错位。本篇给出的是字段类型与对齐关系，具体字节数「需对照实际版本核验」，路径 `driver/configuration_windows.go:29` 与 `tunnel/winipcfg/types.go:27`。

#### 3.2 Peer 字段与显式填充

`driver.Peer` 的字段分三段。前段是标志与密钥：`Flags PeerFlag` 后紧跟一个匿名 `uint32` 填充，再是 `PublicKey [32]byte` 与 `PresharedKey [32]byte` 两组定长数组；与 `conf` 侧的 `Key` 类型不同，这里直接是 `[32]byte` 成员，没有 `String()` / `IsZero()` 方法，字段有效性完全由 `Flags` 的对应位表达。中段是 `PersistentKeepalive uint16` 加一个匿名 `uint16` 填充，再接 `Endpoint winipcfg.RawSockaddrInet`——该结构含 `Family AddressFamily`（`uint16`）与 `data [26]byte`，共 28 字节、按 2 对齐，是「已经解析成二进制地址」的端点，与 `conf.Endpoint` 里保存文本 `Host string` 的字段形成对照；`ToDriverConfiguration` 用 `netip.ParseAddr` 成功后才 `SetAddrPort` 并置 `PeerHasEndpoint` 位，主机名解析发生在别处，本篇不展开。

后段是三组 `uint64` 统计值 `TxBytes` / `RxBytes` / `LastHandshake`，它们由驱动在回读时填充，`FromDriverConfiguration` 把它们分别转成 `conf.Bytes` 与 `conf.HandshakeTime`（`LastHandshake` 的 FILETIME 换算见 05-03）。再往后是 `AllowedIPsCount uint32` 与末尾匿名 `[4]byte` 填充。三个 `_` 填充字段是刻意写进源码的：它们把 `uint64` 统计值顶到 8 字节对齐，并使整个 `Peer` 尺寸成为 8 的倍数，从而保证后面紧跟的 `AllowedIP` 记录起始地址满足对齐要求。字段表里把这三行标为「编译期占位、无读写入口」，正是提醒读者它们不是可赋值的业务字段。

#### 3.3 Interface 头与计数字段

`driver.Interface` 是整块载荷的头，六个声明行。`Flags InterfaceFlag` 表达哪些字段有效，`InterfaceHasPrivateKey`（`1<<1`）与 `InterfaceHasListenPort`（`1<<2`）在 `ToDriverConfiguration` 里被默认置位，`InterfaceHasPublicKey`（`1<<0`）与 `InterfaceReplacePeers`（`1<<3`）用于回读与全量替换场景。`ListenPort uint16` 对应本端监听端口；`PrivateKey [32]byte` 与 `PublicKey [32]byte` 分别是本端私钥与公钥原始字节，私钥在下发时由 `conf.Interface.PrivateKey` 拷入，公钥在回读时由 `InterfaceHasPublicKey` 位决定是否可信。`PeerCount uint32` 是紧随其后的 `Peer` 记录数，是 `FirstPeer` 与 `FromDriverConfiguration` 遍历的界；末尾匿名 `[4]byte` 填充把整体尺寸补齐到对齐边界。

要点在于：`driver.Interface` 里没有 `Addresses`、`DNS`、`MTU`、四个脚本字段、`TableOff` 这些 `conf.Interface` 成员。它们属于 Windows 用户态网络配置与脚本执行范畴，由 `tunnel/` 侧另行处理，不进入驱动载荷。字段表把这一差异隐含在「只列六个声明行」里，读者对照 05-02 的十二字段时，应立刻意识到「驱动载荷字段集是配置字段集的真子集，且同名者类型不同」。例如 `conf.Interface.PrivateKey` 是 `conf.Key`，`driver.Interface.PrivateKey` 是 `[32]byte`；前者有 `String()` 与 `IsZero()`，后者只是裸字节数组。

#### 3.4 Flags 位与状态枚举

六组枚举里，四组是位标志。`PeerFlag` 用了 `1<<0`、`1<<1`、`1<<2`、`1<<3`、`1<<5`、`1<<6`、`1<<7` 共七个位，注意刻意跳过了 `1<<4`——这是上游定义里的空位，字段表按源码如实列出，读者不要自行为它补一个名字。`InterfaceFlag` 用了 `1<<0` 到 `1<<3` 四个位。`AllowedIpFlag` 只用了 `1<<0` 一个位。这些位的共同语义是「对应字段是否有效」或「执行什么操作」：漏置某位，驱动就会忽略相应字段；这是字段层的纠错重点，具体位在下发时如何组合属于 06-05。

另外两组是纯状态值。`AdapterState` 只有 `AdapterStateDown = 0` 与 `AdapterStateUp = 1`，传给 `SetAdapterState` / `AdapterState` 表示适配器上下。日志相关有三个枚举：`AdapterLogState` 的 `AdapterLogOff = 0`、`AdapterLogOn = 1`、`AdapterLogOnWithPrefix = 2` 传给 `SetLogging`；`loggerLevel` 的 `logInfo` / `logWarn` / `logErr` 是 `iota` 三值，供 `logMessage` / `setupLogger` 回调时判定级别。它们都不进配置载荷，只是 `Adapter` 方法的参数类型，本篇按字段表列出以保持驱动侧枚举的完整性。

#### 3.5 ConfigBuilder 与连续内存布局

`ConfigBuilder` 只有一个成员 `buffer []byte`，四条方法都围绕它：`Preallocate(size uint32)` 按预估容量 `make` 一次，`AppendInterface` / `AppendPeer` / `AppendAllowedIP` 各自用 `unsafe.Slice((*byte)(unsafe.Pointer(x)), unsafe.Sizeof(*x))` 把结构体的原始字节 `append` 进 `buffer`，`Interface()` 返回 `(*Interface)(unsafe.Pointer(&builder.buffer[0]))` 与 `uint32(len(builder.buffer))`。字段级结论是：载荷在内存里是一段扁平字节，顺序固定为「一个 `Interface` 头 → 若干 `Peer` 记录 → 每个 `Peer` 后面紧跟它自己的若干 `AllowedIP` 记录」，记录之间无指针、无长度前缀，完全靠 `PeerCount` 与 `AllowedIPsCount` 以及结构尺寸步进定位。`ToDriverConfiguration` 的 `preallocation` 表达式正是对这个布局的容量预估：`unsafe.Sizeof(driver.Interface{})` 加上 `len(Peers)*unsafe.Sizeof(driver.Peer{})` 再加上每个 peer 的 `len(AllowedIPs)*unsafe.Sizeof(driver.AllowedIP{})`。

`Adapter` 的两个成员与这块载荷直接相关：`handle uintptr` 是 `CreateAdapter` / `OpenAdapter` 返回的适配器句柄，`SetConfiguration(interfaze *Interface, size uint32)` 把它与载荷指针、`size` 一起交给 `WireGuardSetConfiguration`；`lastGetGuessSize uint32` 是 `Configuration()` 回读时缓存的上次成功缓冲大小，初值为 512，回读缓冲区不足时由 `ERROR_MORE_DATA` 分支扩大并更新该字段。字段表把二者列进来，是因为它们分别承载「载荷往哪发」与「回读缓冲多大」，其余 `Adapter` 状态字段见 05-06。

#### 3.6 遍历入口与 IOCTL 载荷

连续布局上的四个遍历入口都在 `driver/configuration_windows.go`：`FirstPeer()` 返回 `(*Peer)(unsafe.Add(unsafe.Pointer(interfaze), unsafe.Sizeof(*interfaze)))`，即头之后紧邻的第一个 `Peer`；`NextPeer()` 用 `unsafe.Sizeof(*peer) + uintptr(peer.AllowedIPsCount)*unsafe.Sizeof(AllowedIP{})` 步进，跳过当前 peer 自己挂着的全部 `AllowedIP`；`FirstAllowedIP()` 同理返回 `Peer` 之后紧邻的第一条 `AllowedIP`；`NextAllowedIP()` 按单条尺寸步进。`FromDriverConfiguration` 正是用这四个入口配合 `PeerCount` 与 `AllowedIPsCount` 把载荷还原成 `conf.Config`，字段对应见本篇与 05-02。

下发与回读的 IOCTL 过程变量也集中在 `driver/configuration_windows.go:81`：`procWireGuardSetAdapterState`、`procWireGuardGetAdapterState`、`procWireGuardSetConfiguration`、`procWireGuardGetConfiguration` 四个 `NewProc` 句柄，分别被 `SetAdapterState` / `AdapterState` / `SetConfiguration` / `Configuration` 四个方法调用。`SetConfiguration` 的签名 `SetConfiguration(interfaze *Interface, size uint32)` 直接暴露了「载荷指针 + 字节长度」这一对字段级参数；`Configuration()` 则把回读缓冲区首字节强转为 `*Interface` 返回。本篇只点明这些是字段的 IOCTL 入口，不展开 `syscall.SyscallN` 调用细节。

### 4. 典型示例

下面这段代码从一个最小 `conf.Config` 出发生成驱动载荷，并打印结构尺寸、头部字段与载荷总字节数，用来对照「字段值如何变成 IOCTL 载荷」。代码只调用 `ToDriverConfiguration`，不真正打开适配器或下发。

```go
package main

import (
	"fmt"
	"unsafe"

	"golang.zx2c4.com/wireguard/windows/conf"
	"golang.zx2c4.com/wireguard/windows/driver"
)

func main() {
	var c conf.Config
	c.Name = "wg0"
	c.Interface.ListenPort = 51820
	c.Peers = append(c.Peers, conf.Peer{
		PersistentKeepalive: 25,
	})
	iface, size := c.ToDriverConfiguration()
	fmt.Println("sizeof(driver.Interface) =", unsafe.Sizeof(driver.Interface{}))
	fmt.Println("sizeof(driver.Peer) =", unsafe.Sizeof(driver.Peer{}))
	fmt.Println("sizeof(driver.AllowedIP) =", unsafe.Sizeof(driver.AllowedIP{}))
	fmt.Println("Interface.Flags =", iface.Flags)
	fmt.Println("Interface.ListenPort =", iface.ListenPort)
	fmt.Println("Interface.PeerCount =", iface.PeerCount)
	fmt.Println("payload size =", size)
}
```

示例输出，具体格式需对照实际版本核验：

```text
sizeof(driver.Interface) = 80
sizeof(driver.Peer) = 136
sizeof(driver.AllowedIP) = 24
Interface.Flags = 6
Interface.ListenPort = 51820
Interface.PeerCount = 1
payload size = 216
```

逐行判读如下。前三行是三个载荷结构在 amd64 下的 `unsafe.Sizeof` 示例值，分别对应头部、`Peer` 记录与单条 `AllowedIP` 记录；这些数值由字段类型与对齐决定，随 CPU 架构、Go 版本与 `winipcfg` 定义变化，读者手上版本若不同，应以 `driver/configuration_windows.go` 的字段声明重新核算，本输出仅示意布局关系，具体格式需对照实际版本核验。第四行 `Interface.Flags = 6` 是本篇最值得核对的一行：`ToDriverConfiguration` 固定置位 `driver.InterfaceHasPrivateKey | driver.InterfaceHasListenPort`，即 `(1<<1) | (1<<2) = 2 | 4 = 6`；若实测为 2 说明缺了监听端口位，为 0 说明两个有效性位都没置，驱动会忽略私钥与端口，这是「配置明明有值却不生效」最常见的字段级根因。第五行 `Interface.ListenPort = 51820` 说明端口字段按 `uint16` 原样从 `conf.Interface.ListenPort` 拷入，零值 0 表示未设。第六行 `Interface.PeerCount = 1` 与 `conf.Config.Peers` 长度一致，`FirstPeer` 与 `FromDriverConfiguration` 都以此作为遍历上界；若该值与实际 `AppendPeer` 次数不符，回读时会越界或漏读。第七行 `payload size = 216` 等于头部 80 字节加一个 `Peer` 的 136 字节、再加零条 `AllowedIP`，体现「头 → Peer → AllowedIP」的紧邻布局；一旦给 peer 增加 `AllowedIPs`，该值应按 24 字节的整倍数增长，`SetConfiguration(interfaze, size)` 传的就是它。整段输出没有出现 `Addresses`、`DNS`、`MTU` 等字段，再次印证它们不进入驱动载荷。

速查之外补两条判读经验。其一，凡看到 `driver` 包里的 `PublicKey` / `PrivateKey`，先确认它是 `[32]byte` 裸数组、没有 `IsZero()` 方法，字段有效性一律靠 `Flags` 位判断，这与 `conf.Key` 的用法完全不同。其二，凡看到 `_` 匿名填充字段，别试图给它赋值或读它，它只为对齐存在；改动它会影响 `unsafe.Sizeof` 与步进，进而让整块载荷错位。

### 6. 版本差异

驱动载荷结构的字段形状与 WireGuardNT 的 C 头文件一一对应，因此稳定性比 `conf` 侧更高，但仍有几处需要按版本核验。`PeerFlag` 当前定义了 `1<<0` 到 `1<<3` 与 `1<<5` 到 `1<<7` 七个位，刻意跳过 `1<<4`；`InterfaceFlag` 四个位、`AllowedIpFlag` 一个位。这些位值与 WireGuardNT 1.1 的 `WIREGUARD_PEER_FLAG_*` / `WIREGUARD_INTERFACE_FLAG_*` 常量对应，不同驱动版本可能新增位，读者手上若遇到本表未列的位值，应按「需对照实际版本核验」处理，路径 `driver/configuration_windows.go:36` 与 `:63`，不要自行补名。

`Peer.Endpoint` 与 `AllowedIP.AddressFamily` 依赖 `winipcfg.RawSockaddrInet` 与 `winipcfg.AddressFamily`，二者定义在 `tunnel/winipcfg/types.go`：当前 `RawSockaddrInet` 是 `Family AddressFamily` 加 `data [26]byte`，`AddressFamily` 底层 `uint16`。若上游调整该结构（例如加入 IPv6 scope 字段），`Peer` 的尺寸与 `NextPeer` 步进会连带变化，具体差异「需对照实际版本核验」。`SetAddrPort` / `Addr()` / `Port()` 这些方法名以当前快照为准。

`ConfigBuilder` 当前使用 `unsafe.Slice`（Go 1.17 起）与 `unsafe.Add`（Go 1.17 起）做零拷贝字节追加，较早版本可能用 `reflect.SliceHeader` 或手写指针运算；`Adapter.lastGetGuessSize` 的初值 512 与 `Configuration()` 的 `ERROR_MORE_DATA` 扩缓冲策略也属实现约定。凡涉及具体 Go 版本 API、WireGuardNT 1.1 驱动版本、三种 MSI 的驱动文件版本号等时效性数值，本册一律按总纲第 9 节标注「需对照实际版本核验」并给出 `upstream_src/` 路径，不写死数值、不编造字段名。

### 7. 常见误用与调试

#### 7.1 Flags 位漏置导致字段被忽略

最常见的误用，是手工构造 `driver.Interface` / `driver.Peer` 时只填了 `PrivateKey`、`ListenPort`、`PublicKey` 等字段，却忘了置 `InterfaceHasPrivateKey`、`InterfaceHasListenPort`、`PeerHasPublicKey` 等 `Flags` 位。驱动按位判断字段有效性，漏位的结果是该字段被静默忽略，症状是「配置看起来都填了，握手却起不来」。字段级排查应先打印 `iface.Flags` 与各 `peer.Flags` 的十进制值，逐位对照本篇标志位表；下发位如何组合属 06-05。

#### 7.2 混淆 conf 侧与 driver 侧同名结构

`conf.Interface` 有十二个字段、`driver.Interface` 只有六个声明行；`conf.Peer.Endpoint` 是含 `Host string` 的值类型，`driver.Peer.Endpoint` 是已解析的 `RawSockaddrInet`；`conf.Peer.PublicKey` 是 `conf.Key`，`driver.Peer.PublicKey` 是 `[32]byte`。把两者字段张冠李戴，典型症状是「在 `driver.Interface` 里找 `Addresses` 或 `DNS` 找不到」——它们根本不在载荷里，由 `tunnel/` 侧另行配置。字段定义分别见 05-02 与本篇。

#### 7.3 PeerCount / AllowedIPsCount 与实际记录不符

载荷靠 `PeerCount` 与 `AllowedIPsCount` 定位记录，二者必须与实际 `AppendPeer` / `AppendAllowedIP` 次数严格一致。若计数偏小，`FromDriverConfiguration` 会漏读末尾记录；若偏大，`NextPeer` 步进会越出缓冲区，读到随机字节。`ToDriverConfiguration` 用 `uint32(len(config.Peers))` 与 `uint32(len(config.Peers[i].AllowedIPs))` 保证一致，手工编组时最容易在这里出错。排查时先打印 `Interface.PeerCount`、`Peer.AllowedIPsCount` 与 `size`，再核算 `sizeof` 之和。

#### 7.4 AddressFamily 未设或地址字节长度不对

`AllowedIP.Address` 是 16 字节定长缓冲，IPv4 只用前 4 字节，地址族必须靠 `AddressFamily` 区分。漏设该字段、或把 IPv6 当 IPv4 只拷 4 字节，回读时 `netip.AddrFrom4` / `AddrFrom16` 会取错字节，表现为 AllowedIPs 变成错误地址。`ToDriverConfiguration` 用 `Addr().Is4()` / `Is6()` 写入 `windows.AF_INET` / `AF_INET6`，本篇只给字段与入口，解析机制见 06-05。

#### 7.5 把填充字段当业务字段、或 size 传错

三个 `_` 匿名填充字段不可读写，给它们赋值或按名字引用都会失败；它们只为保证 `uint64` 统计值 8 字节对齐与结构尺寸为 8 的倍数。另一类错误是 `SetConfiguration(interfaze, size)` 的 `size` 传成 `unsafe.Sizeof(driver.Interface{})` 而非整块 `buffer` 长度——前者只有头部大小，驱动会认为后面没有 `Peer`。正确值来自 `ConfigBuilder.Interface()` 返回的 `uint32(len(builder.buffer))`，正如本篇示例中 `payload size` 一行所示。回读侧若 `lastGetGuessSize` 缓存过小，`Configuration()` 会经 `ERROR_MORE_DATA` 扩大缓冲并更新该字段，排查回读失败时也可一并核对。（配置见 04-01 ｜ 原理见 06-05 ｜ 模块见 07-03）
