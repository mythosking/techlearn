## 04-01 配置文件语法与 `[Interface]` / `[Peer]` 全集速查

### 1. 本篇定位与覆盖范围

本篇是整册的入口与总索引。wireguard-windows 的「配置」不是一个孤立文件，而是一组以 wg-quick 风格 INI 文本为载体的键，叠加在 Windows 客户端的隧道服务之上。读者拿到一份 `.conf` 时，最先需要回答三个问题：文件由哪些段构成、每段允许哪些键、键与值遵循什么书写与校验规则。本篇把这三个问题一次性讲清，并给出「全集索引表」作为后续 04-02、04-03 逐项详解的目录。需要强调的是，本仓库是 Windows 官方客户端，配置文件格式虽然借鉴了 Linux `wg-quick(8)` 的 INI 外观，但其解析、校验与序列化完全由本仓库的 `conf` 包完成，源码位置为 `conf/parser.go` 的 `FromWgQuick` 与 `conf/writer.go` 的 `ToWgQuick`。因此不能把 Linux `wg-quick` 的 `iptables`、`%i`、`resolvconf`、`SaveConfig` 等语义当成 Windows 客户端能力；这些差异在本篇、04-02、04-07 会反复标注。本篇覆盖范围包括：INI 段结构与键值语法、注释规则、逗号分隔列表与多行键、隧道名与文件名约束、`[Interface]` 与 `[Peer]` 全部键的索引、以及配置键到源码校验函数的归属关系。结构体逐字段定义属于 05 册（字段见 05-02），解析状态机与调用链属于 06 册（原理见 06-02），`conf` 模块的整体能力属于 07 册（模块见 07-01），本篇均不展开。

### 2. 索引与全参数表

配置文件的顶层结构只有两类段：`[Interface]` 段描述本端，一个文件有且仅应有一段；`[Peer]` 段描述对端，一个文件可出现零到多段。每个段内是若干 `键 = 值` 行，值可以是通过逗号分隔的列表。下表给出本册管辖的全部配置键索引，「段」列标明归属，「是否必需」列以 `conf/parser.go` 末尾的强制校验为准：接口必须有私钥、每个 peer 必须有公钥。

下表为 `[Interface]` 与 `[Peer]` 全部键的索引，键名大小写不敏感（解析器统一 `strings.ToLower`），表中保留官方惯用拼写；完整取值示例见下方配置示例。

| 段 | 键 | 取值形态 | 是否必需 | 简要说明 |
|---|---|---|---|---|
| `[Interface]` | PrivateKey | 单个 Base64 串 | 必需 | 本端 32 字节私钥，见 04-02 |
| `[Interface]` | Address | 逗号分隔 CIDR 列表 | 通常必需 | 本端接口地址，可多次出现，见 04-02 |
| `[Interface]` | ListenPort | 0–65535 整数 | 可选 | 本端 UDP 监听端口，见 04-02 |
| `[Interface]` | MTU | 576–65535 整数 | 可选 | 接口 MTU，见 04-02 |
| `[Interface]` | DNS | 逗号分隔 IP 或域名列表 | 可选 | DNS 服务器与搜索域，见 04-02 |
| `[Interface]` | Table | `off` \| `auto` \| `main` \| 数字 | 可选 | 是否禁用路由下发，见 04-02 |
| `[Interface]` | PreUp | 命令字符串 | 可选 | 启动前脚本，默认不执行，见 04-02 |
| `[Interface]` | PostUp | 命令字符串 | 可选 | 启动后脚本，默认不执行，见 04-02 |
| `[Interface]` | PreDown | 命令字符串 | 可选 | 停止前脚本，默认不执行，见 04-02 |
| `[Interface]` | PostDown | 命令字符串 | 可选 | 停止后脚本，默认不执行，见 04-02 |
| `[Peer]` | PublicKey | 单个 Base64 串 | 必需 | 对端 32 字节公钥，见 04-03 |

### 3. 逐项详解

**段头 `[Interface]` 与 `[Peer]`**。解析器 `FromWgQuick` 逐行扫描，遇到 `[interface]`（比较前已转小写）且该行不含等号时，切换到 `inInterfaceSection` 状态；遇到 `[peer]` 且不含等号时，切换到 `inPeerSection` 状态并新建一个 peer。段头本身不区分大小写，但必须是整行、且不能写成 `[Interface] = something` 之类带等号的形式。任何出现在段外的 `键 = 值` 行都会触发 `Line must occur in a section` 解析错误；任何落在 `[Interface]` 段却属于 `[Peer]` 段专属的键（或反之）会触发 `Invalid key for [Interface] section` 或 `Invalid key for [Peer] section`。段可以重复出现，但语义上 `[Interface]` 只会累积到同一个接口对象，重复写 `PrivateKey` 会互相覆盖；`[Peer]` 每出现一次就新增一个对端。

**键值行 `键 = 值`**。每行用第一个等号 `strings.Cut(stripped, "=")` 分割，键名去空白并转小写，值去首尾空白。值不能为空，否则报 `Key must have a value`。注意脚本键是例外：`conf/parser.go` 对 `preup`、`postup`、`predown`、`postdown` 做了特殊处理，改用整行第一个等号后的原文 `strings.Cut(line, "=")`，并清空行尾注释，从而保留脚本里的 `#`、管道、引号等字符不被当作注释切断。这是四个脚本键与普通键在语法层的关键差异。

**注释规则**。井号 `#` 之后的内容被视为注释：`strings.Cut(line, "#")` 把行切成代码与注释两部分，注释被裁剪尾部空白后保存。因此既能写整行注释，也能写 `Address = 10.0.0.1/24 # 本端地址` 这样的行尾注释。注释不是被丢弃的——`conf/writer.go` 的 `ToWgQuick` 通过 `SectionComments`、`Comments` 把段头注释、行前注释、行尾后缀注释一并回写，做到解析再序列化后的「注释保真」。注释结构与状态字段见 05-04，往返序列化机制见 06-02。

**逗号分隔列表**。Address、DNS、AllowedIPs 三个键的值可由逗号分隔多项。`conf/parser.go` 的 `splitList` 用 `strings.SplitSeq(s, ",")` 切分、逐项 `TrimSpace`，但拒绝空项：出现连续两个逗号（例如 `10.0.0.1/24,,10.0.0.2/24`）会报 `Two commas in a row`。这一点常被误写成「尾部多一个逗号也无妨」，实际上 `Address = 10.0.0.1/24,` 会因为末项为空而报错，务必避免。

**可多次出现的键**。Address、DNS、AllowedIPs 在解析时是「追加」而非「覆盖」：`case "address"`、`case "dns"`、`case "allowedips"` 都把解析结果 `append` 到对应切片。因此既可以一行写多项（`Address = 10.0.0.1/24, fd00::1/64`），也可以拆成多行 `Address = ...` 重复书写，效果等价，解析后由 `DeduplicateNetworkEntries` 去除完全重复的条目（去重机制见 06-02）。而 PrivateKey、ListenPort、MTU、Table、四个脚本键、PublicKey、PresharedKey、Endpoint、PersistentKeepalive 都是「后写覆盖前写」。

**隧道名与文件名约束**。配置不是孤立文本，它要落盘为文件并派生出 Windows 服务名。`conf/name.go` 的 `TunnelNameIsValid` 用正则 `^[a-zA-Z0-9_=+.-]{1,32}$` 限定名字：长度 1–32，字符仅限字母、数字、下划线、等号、加号、点、连字符；同时通过 `isReserved` 拒绝 Windows 保留设备名（CON、PRN、AUX、NUL、COM1–COM9、LPT1–LPT9，比较时忽略大小写并去掉首个点之前的部分），通过 `hasSpecialChars` 拒绝 `$`（服务名禁用）、`\/:*?"<>|` 与制表符、控制字符，以及以点开头或结尾的名字。`ServiceNameOfTunnel` 把合法隧道名拼成 `WireGuardTunnel$<name>`。配置文件的扩展名在 `docs/enterprise.md` 中有明确语义：以 `.conf` 结尾按普通 wg-quick 文本解析，以 `.conf.dpapi` 结尾按 `CryptProtectData(bytes, "myconfname")` 加密后的同一格式解析；完整存储与 DPAPI 流程见 03-04 与 06-03。

**键到校验函数的归属**。每个键都有专用解析函数：`PrivateKey` / `PublicKey` / `PresharedKey` 走 `parseKeyBase64`（`base64.StdEncoding` 解码且必须恰好 32 字节，否则 `Keys must decode to exactly 32 bytes`）；`ListenPort` 走 `parsePort`（0–65535）；`MTU` 走 `parseMTU`（576–65535，越界报 `Invalid MTU`）；`Address` / `AllowedIPs` 走 `parseIPCidr`（先 `netip.ParsePrefix`，失败再 `netip.ParseAddr` 并补成 `/32` 或 `/128` 主机前缀）；`DNS` 走 `netip.ParseAddr`，解析失败的项被当作搜索域存入 `DNSSearch`；`Endpoint` 走 `parseEndpoint`（必须含端口，IPv6 用方括号且方括号内必须是合法 IPv6，否则 `Brackets must contain an IPv6 address`）；`PersistentKeepalive` 走 `parsePersistentKeepalive`（`off` 转为 0，否则 0–65535）；`Table` 走 `parseTableOff`（`off` 为真，`auto` / `main` 为假，纯数字字符串用 `ParseUint` 校验通过但同样记为假）。这些函数的逐字段细节见 05-02、05-03，解析主流程见 06-02。

**必需性校验**。解析收尾有两道硬校验：`if !sawPrivateKey` 报 `An interface must have a private key`，随后遍历每个 peer，若 `p.PublicKey.IsZero()` 则报 `All peers must have public keys`。也就是说接口私钥与每个 peer 的公钥是唯一被强制要求的键；其余键都可省略，省略时 `conf/writer.go` 的 `ToWgQuick` 也会按「仅当值非零 / 非空才写」的条件跳过对应行。字段是否为零值、默认值如何参与序列化，见 05-02。

**编码兼容**。`FromWgQuickWithUnknownEncoding` 会先按 UTF-8 试解析，失败后遍历 `unicode.All` 里各种编码的解码器重试，以便兼容从别处拷来的非 UTF-8 配置文件。这属于读取层的容错，机制见 06-02。

### 4. 典型示例

下面给出一份合法的完整配置示例，涵盖两段的常用键、逗号列表、行尾注释与搜索域。随后给出用 `wg(8)` 查询该隧道时的典型输出，并逐行判读。完整 `wg(8)` 子命令见 04-05。

```conf
[Interface]
PrivateKey = yAnz5TF+lXyfBAtZqP8kESiuAxMtN2FHGvVYdFhQ9gO0E=
Address = 10.0.0.2/24, fd00::2/64
DNS = 10.0.0.1, corp.example.com
MTU = 1420

[Peer]
PublicKey = JRI8Xc0zKP9kXk8qP84NdUQA04h6DLfFbwJn4g+/PFs=
AllowedIPs = 0.0.0.0/0, ::/0
Endpoint = 163.172.161.0:12912
PersistentKeepalive = 25
```

与之对应的运行时查询（命令与子命令语义见 04-05）输出如下。示例输出，具体格式需对照实际版本核验。

```text
> wg show myconfname
interface: myconfname
  public key: lfTRXEWxt8mZc8cjSvOWN3tqnTpWw4v2Eg3qF6WTklw=
  private key: (hidden)
  listening port: 53488

peer: JRI8Xc0zKP9kXk8qP84NdUQA04h6DLfFbwJn4g+/PFs=
  endpoint: 163.172.161.0:12912
  allowed ips: 0.0.0.0/0
  latest handshake: 3 seconds ago
  transfer: 6.55 KiB received, 4.13 KiB sent
```

逐行判读如下。第一行 `interface: myconfname` 中 `myconfname` 即隧道名，也是服务名 `WireGuardTunnel$myconfname` 的后缀，必须符合 `conf/name.go` 的 1–32 字符约束。`public key` 一行是由 `PrivateKey` 经 X25519 派生出的公钥，用于对面配置里的 `PublicKey`；它显示为 Base64，长度对应 32 字节。`private key: (hidden)` 表示私钥被刻意隐藏，这是 `wg show` 的默认安全行为，不代表配置里没有私钥；若需连同私钥一起查看须用 `wg showconf`（见 04-05）。`listening port: 53488` 是本端实际监听的 UDP 端口：示例配置未写 `ListenPort`，故由系统随机选择，若配置里显式写了 `ListenPort` 则这里应显示该固定值。`peer:` 行的 Base64 串应与配置里 `PublicKey` 完全一致，不一致说明当前运行时配置与磁盘配置已漂移。`endpoint: 163.172.161.0:12912` 与配置 `Endpoint` 一致，是握手目标；若显示 `(none)` 说明尚未学到对端地址。`allowed ips: 0.0.0.0/0` 表示全流量走隧道，这一取值会触发 kill-switch 防火墙语义（原理见 06-09）。`latest handshake: 3 seconds ago` 是最近握手距今时间，数值很小说明握手活跃；长时间不刷新通常意味着密钥、Endpoint 或网络不通。`transfer: 6.55 KiB received, 4.13 KiB sent` 是收发字节计数，其格式化规则见 05-03；两者长期为零而握手时间又是「很久以前」，是典型的单向不通或路由错误特征。以上输出样例取自 `docs/enterprise.md`，字段含义与运行时统计字段见 05-02，机制见 06-xx。

### 5. 速查表

下表按「我想做的事」反查应改哪个键，便于排错时快速定位；命令类速查见 04-04 与 04-08。

| 目标 | 应改的键 | 所在段 | 关键约束 |
|---|---|---|---|
| 改本端身份 | PrivateKey | Interface | 32 字节 Base64，必填 |
| 改本端地址 | Address | Interface | CIDR 列表，可多行 |
| 固定监听端口 | ListenPort | Interface | 0–65535，0 表示随机 |
| 手动指定 MTU | MTU | Interface | 576–65535，省略则自动 |
| 指定 DNS 与搜索域 | DNS | Interface | IP 进 DNS，域名进搜索域 |
| 禁止自动下发路由 | Table | Interface | 仅 `off` 生效 |
| 起停时执行命令 | 四个脚本键 | Interface | 需 04-07 注册表开关 |
| 指定对端身份 | PublicKey | Peer | 32 字节 Base64，必填 |
| 追加预共享密钥 | PresharedKey | Peer | 32 字节 Base64，可选 |
| 控制哪些网段走隧道 | AllowedIPs | Peer | CIDR 列表，可多行 |
| 指定对端地址 | Endpoint | Peer | 必须带端口 |
| 维持 NAT 映射 | PersistentKeepalive | Peer | `off` 或秒数 |

使用速查表时要注意，`Table = off` 只是关闭「由隧道服务把 AllowedIPs 下发成系统路由」这一动作，并不等于禁用加密或禁用接口；`AllowedIPs` 同时承担「加密目的地址选择」与「路由来源」双重语义，删空它会导致隧道无流量可发。这些语义差异见 04-02、04-03 与 04-08，路由下发的机制见 06-06。

### 6. 版本差异

本册版本基准为上游仓库 master 快照（2026-11 抓取）、WireGuardNT 1.1、Go 1.27.1、Windows 10 / Server 2019 及以上，amd64 / x86 / arm64 三种 MSI；版本来源 `version/version.go`、`Makefile` 与 `build.bat`。就配置语法而言，需要区分「格式稳定部分」与「可能随版本变化部分」。稳定部分包括：INI 两段结构、`键 = 值` 语法、`#` 注释、逗号列表、键名大小写不敏感、`[Interface]` 必需私钥、`[Peer]` 必需公钥——这些由 `conf/parser.go` 的 `FromWgQuick` 与 `conf/writer.go` 的 `ToWgQuick` 直接定义，形式简明，跨版本一致性高。可能变化的部分包括：具体错误文案会被 `l18n` 本地化替换、新增或废弃的键、`Table` 对数字取值的处理方式（当前 `parseTableOff` 只把数字当作「非 off」通过校验，并不建立编号路由表，需对照实际版本核验）、以及四个脚本键的执行策略。凡是本仓库 `conf/config.go` 不存在、但别的平台 `wg-quick` 有的键（例如 `SaveConfig`、`FwMark`、`PostUp` 里引用的 `iptables` / `resolvconf`），一律不属于 Windows 客户端能力，具体差异需对照实际版本核验并给出源码路径。另需注意 `wg(8)` 可执行文件由外部 `wireguard-tools` 项目提供，`docs/buildrun.md` 说明它在 Windows 上「works well」并由 `build.bat` 一并构建，但其子命令细节以该外部项目版本为准，需对照实际版本核验。

### 7. 常见误用与调试

第一类是段归属错误：把 `AllowedIPs` 写进 `[Interface]`、把 `Address` 写进 `[Peer]`，解析器直接报 `Invalid key for [Interface] section` 一类错误。排查时先用「键在哪一段」对照第 2 节索引表。第二类是列表逗号错误：连续逗号或尾部逗号触发 `Two commas in a row`，这是 `splitList` 的硬性约束，不能靠「多写个空格」绕过。第三类是把 Linux `wg-quick` 的写法直接搬来：写成 `PostUp = iptables -A FORWARD -i %i ...`、`DNS = ...` 配合 `resolvconf`、或加一行 `SaveConfig = true`。在 Windows 上，`iptables` 与 `resolvconf` 不是客户端命令，`%i` 占位符不存在（Windows 用环境变量 `WIREGUARD_TUNNEL_NAME`，见 04-07），`SaveConfig` 会触发 `Invalid key for [Interface] section`；四个脚本键即便写对，默认也不会执行。第四类是隧道名非法：名字里带空格、中文、斜杠、美元符号，或以点结尾、用保留名 `CON`，都会在 `FromWgQuick` 开头 `TunnelNameIsValid` 处失败并报 `Tunnel name is not valid`，进而导致服务名 `WireGuardTunnel$<name>` 无法建立。第五类是「看似生效实则漂移」：改了磁盘 `.conf` 但运行时配置未重载，`wg show` 显示的公钥或 endpoint 与文件不一致；这类现象要用 04-05 的 `wg showconf` 与 04-06 的服务重启命令核对。第六类是注释丢真：手工拼接脚本或含 `#` 的值时，普通键的 `#` 会被当注释切掉，只有四个脚本键保留整行原文，若确需在普通值里放井号，需对照 `conf/parser.go` 的 `strings.Cut(line, "#")` 行为核验。调试入口建议依次使用：`wireguard /dumplog`（见 04-04、04-06）看解析错误文案、`wg show`（见 04-05）看运行时状态、`conf/parser.go` 对照具体键的校验分支定位。错误现象到配置域的完整映射见 04-08，解析机制见 06-02，`conf` 模块能力见 07-01。

## 04-02 `[Interface]` 段配置键逐项详解

### 1. 本篇定位与覆盖范围

本篇逐项拆解 `[Interface]` 段的全部配置键，是 04-01 索引表在「本端」分支上的展开。Windows 客户端把本端参数分为四类：身份与监听（PrivateKey、ListenPort）、网络参数（Address、DNS、MTU、Table）、生命周期脚本（PreUp、PostUp、PreDown、PostDown），以及一个只在 Linux 侧存在、Windows 必须明确否定的 `SaveConfig`。每个键都按「语法—取值范围—默认行为—解析与校验—Windows 语义—常见误用」的顺序讲透，并标注对应源码位置：`conf/config.go` 定义键的内存归属、`conf/parser.go` 负责解析校验、`conf/writer.go` 负责序列化回写。本篇反复强调能力边界：本仓库是 Windows 客户端，`wg-quick` 的 `iptables` / `%i` / `resolvconf` / `SaveConfig` 语义不是它的能力；四个脚本键默认不执行，且执行时用的是环境变量 `WIREGUARD_TUNNEL_NAME` 而非 `%i`。结构体逐字段定义见 05-02（`conf.Interface` 成员类型与默认值），DNS / 路由 / MTU 的下发机制见 06-07、06-08、06-06，`conf` 模块整体见 07-01。本篇不列结构体字段全集，只讲键与用法。

### 2. 索引与全参数表

### 3. 逐项详解

**PrivateKey**。语法为单个 Base64 字符串，例如 `PrivateKey = yAnz...O0E=`。`conf/parser.go` 的 `parseKeyBase64` 用 `base64.StdEncoding.DecodeString` 解码，并要求 `len(k) == KeyLength`，即恰好 32 字节，否则报 `Keys must decode to exactly 32 bytes`；解码本身失败报 `Invalid key`。它是 `FromWgQuick` 收尾 `sawPrivateKey` 校验盯住的唯一强制键，缺失时报 `An interface must have a private key`。Windows 语义上它是 Curve25519（X25519）私钥，公钥由 `conf/config.go` 的 `Key.Public()` 经 `ecdh.X25519().NewPrivateKey` 派生，用于对面 `[Peer]` 的 `PublicKey`；私钥本身经 `ToDriverConfiguration` 编组下发驱动（机制见 06-05）。`wg show` 默认把私钥显示为 `(hidden)`，`wg showconf` 才显示明文（见 04-05）。常见误用：把公钥填进 PrivateKey、复制时漏字符导致 32 字节校验失败、或用 URL-safe Base64（`-` / `_`）而非标准 Base64，均会在解析阶段报错。密钥生成可用 `wg genkey`（见 04-05），字段类型见 05-03。

**Address**。语法为逗号分隔的 CIDR 列表，也接受不带前缀长度的裸 IP：`parseIPCidr` 先试 `netip.ParsePrefix`，失败后 `netip.ParseAddr` 成功则补成「该地址位宽」的主机前缀（IPv4 为 /32，IPv6 为 /128）。可写一行多项，也可多行重复书写，解析时一律 `append` 到接口地址切片，随后由 `DeduplicateNetworkEntries` 去完全重复项（机制见 06-02）。`conf/writer.go` 在 `ToWgQuick` 时用 `strings.Join(addrStrings, ", ")` 把多个地址写回单行。Windows 语义上，这些地址由隧道服务配置为 WireGuard 适配器的单播地址（原理见 06-06）；适配器在隧道启动时动态创建、停止时销毁（`docs/netquirk.md`）。常见误用：写成 `10.0.0.2` 却期望获得 /24 网段路由——裸 IP 只会得到 /32 主机地址，网段路由来自 `[Peer]` 的 `AllowedIPs`（见 04-03）；以及地址与已有隧道重叠，路由冲突检测见 04-08。字段类型 `[]netip.Prefix` 见 05-02。

**ListenPort**。语法为 0–65535 的十进制整数，由 `parsePort` 校验，出界报 `Invalid port`。值为 0 或未写该键时，`conf/writer.go` 不回写该行，运行时由系统随机选择监听端口，这正是 04-01 示例里 `wg show` 显示 `listening port: 53488` 而非固定值的原因。需要让对端能主动连入（例如本端在防火墙后需固定端口映射）时应显式指定，如 `ListenPort = 51820`。它经 `ToDriverConfiguration` 以 `InterfaceHasListenPort` 标志下发（机制见 06-05）。常见误用：把端口写成字符串加引号、写成 65536 出界、或与本机另一进程已占用的 UDP 端口冲突；后者在解析阶段不报错，要到隧道启动才表现为绑定失败，可用 04-06 的 `netsh` / `Get-NetUDPEndpoint` 类命令排查。字段类型见 05-02。

**MTU**。语法为 576–65535 整数，由 `parseMTU` 校验，低于 576 或高于 65535 报 `Invalid MTU`。未显式书写时，`conf/writer.go` 不回写，隧道服务按 `docs/netquirk.md` 的规则推导：监视「非本隧道的默认路由接口」的 MTU，取该值减 80 作为 WireGuard 接口 MTU；完整监控链见 06-07。因此手写 `MTU = 1420` 会覆盖自动推导，适合在 PPPoE、某些云环境或已知链路 MTU 偏小的场景显式固定。常见误用：把 MTU 设得过大导致分片与吞吐下降、过小导致效率损失；以及误以为不写 MTU 就是 1500，实际上默认值取决于默认路由接口且会随网络切换动态更新。字段类型 `uint16` 见 05-02。

**DNS**。语法为逗号分隔列表，且每一项既可以是 IP 地址，也可以是搜索域名。`conf/parser.go` 的 `case "dns"` 对每项先试 `netip.ParseAddr`：成功则作为 DNS 服务器地址存入 `DNS` 切片；失败（例如 `corp.example.com`）则作为搜索域存入 `DNSSearch` 切片。这一「一鍵两义」是 Windows 客户端解析器的独特设计，`conf/writer.go` 回写时把 `DNS` 与 `DNSSearch` 合并成一行 `DNS = 10.0.0.1, corp.example.com`。Windows 语义上，DNS 服务器与搜索域由隧道服务下发给系统解析器（原理见 06-08）；当配置含 `0.0.0.0/0` 这类 `/0` 路由时，kill-switch 会进一步收紧 53 端口，只允许查询配置里指定的 DNS 服务器（`docs/netquirk.md`，原理见 06-09）。常见误用：把域名误当 IP 写反、期望 Windows 自动调用 Linux 的 `resolvconf`（不是客户端能力）、或漏配 DNS 导致隧道内域名无法解析。字段类型 `[]netip.Addr` 与 `[]string` 见 05-02。

**Table**。语法取值为 `off`、`auto`、`main` 或一个十进制数字字符串，`conf/parser.go` 的 `parseTableOff` 处理如下：`off` → `TableOff = true`；`auto` / `main` → `TableOff = false`；其他字符串用 `strconv.ParseUint(s, 10, 32)` 校验是否为合法 32 位无符号整数，合法则同样返回 `false`（即「非 off」），非法则报错。`conf/writer.go` 仅在 `TableOff` 为真时回写 `Table = off`。Windows 语义上，这个键只表达一个布尔意图：是否让隧道服务把 `[Peer]` 的 `AllowedIPs` 汇总去重后下发成系统路由（原理见 06-06）。`Table = off` 即关闭该下发动作，用户需自行管理路由；`auto` / `main` 与数字值当前都不改变「由服务下发路由」这一行为，数字值并不建立 Linux 那样的编号策略路由表，这一点需对照实际版本核验。常见误用：以为 `Table = 1234` 会把路由写进编号表、以为 `off` 能关掉加密。字段类型 `bool` 见 05-02。

**PreUp / PostUp / PreDown / PostDown（四个脚本键）**。语法是任意命令字符串，且如 04-01 所述，解析器对这四个键使用整行第一个等号后的原文，保留 `#`、管道与引号不被注释切断。`conf/config.go` 把它们保存为四个字符串，`conf/writer.go` 在非空时回写。关键边界：`conf/parser.go` 只是「保存」这些值，**默认不执行**；只有 `HKLM\Software\WireGuard\DangerousScriptExecution` 为 DWORD 1 时，隧道服务才在对应生命周期点以 LocalSystem 运行它们（`docs/adminregistry.md`，详见 04-07）。执行时 Windows 通过环境变量 `WIREGUARD_TUNNEL_NAME` 传入隧道名，而不是 Linux `wg-quick` 的 `%i`；因此把 `PostUp = iptables -A FORWARD -i %i -j ACCEPT` 抄到 Windows 既无 `iptables` 可用，`%i` 也不会被替换。四个键的触发时机（启动前 / 启动后 / 停止前 / 停止后）属于服务生命周期，机制见 07-05 与 06-05；开启开关的安全代价见 04-07、08-05。字段类型 `string` 见 05-02。

**SaveConfig（非 Windows 键）**。这是 Linux `wg-quick` 的键，含义是「把运行时的改动回存到配置文件」。本仓库 `conf/parser.go` 的 `[Interface]` 分支 `switch key` 只收录 `privatekey`、`listenport`、`mtu`、`address`、`dns`、`preup`、`postup`、`predown`、`postdown`、`table`，**没有 `saveconfig`**；写入会落入 `default` 分支报 `Invalid key for [Interface] section`。因此 Windows 客户端没有「运行时自动回写磁盘配置」这一能力，配置变更应通过 UI 编辑器或替换 `.conf` 文件并重启隧道服务完成（见 03-04、04-06）。同理，`wg-quick` 里常见的 `FwMark`、`iptables`、`resolvconf` 组合也不属于本仓库能力。凡遇到此类键，处理方式统一为「删除该行，按 04-01 索引表与 04-02 逐项详解重写」，并标注「需对照实际版本核验」加源码路径 `conf/parser.go`。

### 4. 典型示例

下面给出一份刻意覆盖多个 `[Interface]` 键、并附带注释的配置示例；随后给出带脚本键与危险开关时的诊断输出判读。四个脚本键的完整开关条件见 04-07。

```conf
[Interface]
# 本端固定监听 51820，便于对端主动连入
PrivateKey = yAnz5TF+lXyfBAtZqP8kESiuAxMtN2FHGvVYdFhQ9gO0E=
ListenPort = 51820
Address = 10.0.0.2/24
Address = fd00::2/64
DNS = 10.0.0.1, corp.example.com
MTU = 1420
Table = off

[Peer]
PublicKey = JRI8Xc0zKP9kXk8qP84NdUQA04h6DLfFbwJn4g+/PFs=
AllowedIPs = 10.0.0.0/24
```

用注册表命令查询危险脚本开关、并查看接口段回写结果的典型输出如下。示例输出，具体格式需对照实际版本核验。

```text
> reg query HKLM\Software\WireGuard /v DangerousScriptExecution

HKEY_LOCAL_MACHINE\Software\WireGuard
    DangerousScriptExecution    REG_DWORD    0x1

> wg show myconfname listen-port
51820
```

逐行判读如下。`reg query ... /v DangerousScriptExecution` 用于确认 04-07 的开关是否打开；输出中 `REG_DWORD 0x1` 表示 DWORD 值为 1，即四个脚本键会被隧道服务以 LocalSystem 执行，若显示 `0x0` 或提示「系统找不到指定的注册表项或值」则说明默认不执行、脚本被静默忽略。`HKEY_LOCAL_MACHINE\Software\WireGuard` 一行是键路径，说明这是机器级策略，普通用户无权改动，修改需管理员权限（命令见 04-06、04-07）。第二段 `wg show myconfname listen-port` 查询运行时监听端口，回显 `51820` 与示例配置里的 `ListenPort = 51820` 完全一致，证明固定端口已生效；若回显一个随机高位端口，则说明配置未重载或该键被省略。注意示例里 `Table = off` 已关闭自动路由下发，因此即便 `[Peer]` 写了 `AllowedIPs = 10.0.0.0/24`，系统路由表也不会被自动加入该网段，必须自行补路由；这正呼应 `parseTableOff` 只把 `off` 记为真的语义。示例里的两行 `Address` 演示「键可多次出现、解析时追加」，等价于一行写 `Address = 10.0.0.2/24, fd00::2/64`。字段回写条件见 05-02，`wg(8)` 子命令语义见 04-05。

### 5. 速查表

下表按「症状」反查 `[Interface]` 应调哪个键，是 04-08 排错映射在本段的细化。

| 症状 | 优先检查键 | 典型取值 | 关联篇 |
|---|---|---|---|
| 解析报缺私钥 | PrivateKey | 32 字节 Base64 | 04-02 |
| 握手不通且对端连不进 | ListenPort | 固定端口 | 04-02 |
| 域名解析失败 | DNS | 服务器 IP 加搜索域 | 04-02 |
| 大包卡顿或分片 | MTU | 1420 或自动 | 04-02 |
| 路由未被自动加入 | Table | 删掉或写 `auto` | 04-02 |
| 脚本不执行 | 四个脚本键 | 配合 04-07 开关 | 04-07 |
| 写入被报非法键 | SaveConfig | 删除该行 | 04-02 |
| 适配器地址不对 | Address | 带正确前缀长度 | 04-02 |

速查表的用法是「先定位段、再定位键」：所有症状都先确认发生在 `[Interface]` 而非 `[Peer]`（后者见 04-03），再用 04-04 的 `/dumplog` 读解析错误文案，最后按本表回到具体键修正。字段默认值见 05-02，机制见 06-06、06-07、06-08。

### 6. 版本差异

版本基准与 04-01 相同。就 `[Interface]` 而言，稳定的是键集合本身与校验边界：PrivateKey 的 32 字节要求、ListenPort 的 0–65535、MTU 的 576–65535、Table 的 `off` / `auto` / `main` / 数字、DNS 的「IP 或搜索域」二分、四个脚本键「只保存不执行」——这些由 `conf/parser.go`、`conf/writer.go` 直接固定。可能随版本变化、需对照实际版本核验的有：错误文案的本地化（`l18n.Sprintf`）、`Table` 对数字取值是否引入编号路由表语义（当前 `parseTableOff` 把数字当作「非 off」通过）、四个脚本键执行时注入的环境变量集合（当前 `docs/adminregistry.md` 明确只有 `WIREGUARD_TUNNEL_NAME`）、以及 MTU 自动推导的「减 80」常量（`docs/netquirk.md`，机制见 06-07）。能力边界类结论不随版本改变：`SaveConfig`、`iptables`、`%i`、`resolvconf`、`FwMark` 不是 Windows 客户端能力，凡 upstream `conf/config.go` 无对应成员、或属于外部 `wg-quick` 的键，一律写「需对照实际版本核验」并给出 `conf/parser.go` 路径。`wg(8)` 由外部 `wireguard-tools` 提供，`docs/buildrun.md` 仅说明其 Windows 可用性与构建方式，子命令细节需对照实际版本核验。

### 7. 常见误用与调试

本段最常见的误用是把 Linux `wg-quick` 配置原样导入：出现 `SaveConfig = true`、`PostUp = iptables ... -i %i`、`PostUp = resolvconf -a %i ...`。三者在 Windows 上的结果分别是「解析报非法键」「脚本默认不执行，即便执行也无 iptables 且 `%i` 不被替换」「同上」。正确做法见 04-07：删掉 `SaveConfig`、把脚本改写成 Windows 命令并按需用 `WIREGUARD_TUNNEL_NAME`，仅在确实必要时才开 `DangerousScriptExecution`。第二类误用是 `Table` 取值误解：写 `Table = 1234` 期望编号路由表，或写 `Table = off` 后又奇怪「为什么没有加密流量」——`off` 只关路由下发，不关加密。第三类是 DNS 混写：把搜索域当 IP、或把 IP 写成域名，解析器会按 `netip.ParseAddr` 成败把值悄悄分到 `DNS` 或 `DNSSearch` 两个不同去向，排查时要看 `wg show` 与系统解析器实际拿到的服务器。第四类是 MTU 越界：写 500 或 70000 会在解析阶段报 `Invalid MTU`，写 1500 虽合法却可能在隧道封装后分片，需结合 06-07 的自动推导权衡。第五类是 Address 只写裸 IP 却期望网段路由，或漏写前缀导致对端 `AllowedIPs` 与本端地址不在同一网段。调试顺序建议：先用 `wireguard /dumplog`（04-04、04-06）抓 `conf/parser.go` 抛出的具体错误文案；再用 `wg show` / `wg showconf`（04-05）核对运行时是否等于磁盘配置；最后按本节与 04-08 的映射回到键。涉及字段类型与默认值查 05-02，涉及路由、DNS、MTU、脚本生命周期的机制查 06-06、06-08、06-07、07-05。

## 04-03 [Peer] 段配置键逐项详解

### 1. 本篇定位与覆盖范围

本册（04 配置与命令行）是整套资料里「全部配置键、`wireguard.exe` 开关、`wg(8)` 子命令、`sc` / PowerShell 服务命令、注册表策略」的唯一权威源，其余各册凡涉及配置与命令只给本场景最小必要片段并写「完整配置见 04-xx」，不再重列全集。本篇在其中承担 `[Peer]` 段的逐键字典职能：把每一个对端配置键的合法取值、解析入口、省略时的默认行为、序列化的写出条件、以及多 peer 组合时的规则讲清楚，使读者在编写或审查 `.conf` 文件时能逐条对照，而不必回头翻源码。手册型册子的价值在于「查得到、查得全、查得准」，因此本篇给出的参数表与逐项详解都不做删减，也不以「举例若干」代替全集。

覆盖的键严格以 `conf/config.go` 中 `conf.Peer` 的成员为准，共五个：`PublicKey`、`PresharedKey`、`AllowedIPs`、`Endpoint`、`PersistentKeepalive`。这五个键在 `conf/parser.go` 的 `FromWgQuick` 函数中对应 `parserState == inPeerSection` 分支下的五个 `case`，在 `conf/writer.go` 的 `ToWgQuick` 函数中对应五条 `writeField` 调用，在 `conf/writer.go` 的 `ToDriverConfiguration` 中对应下发给驱动的对端标志与载荷。除此之外，`conf.Peer` 还有 `RxBytes`、`TxBytes`、`LastHandshakeTime` 三个成员，它们是运行时统计值而非配置键：解析配置文件时不会被写入，序列化回 `.conf` 时也不会被输出，只在通过 `conf/parser.go` 的 `FromDriverConfiguration` 从驱动读回运行状态时填充，供 UI 状态页与 `wg show` 之类的运行时查询呈现。本篇会把这组「只读状态」与「可写配置键」明确区分开，避免读者把 `transfer`、`latest handshake` 之类的输出行误当成可以写回配置文件的键。

能力边界必须前置说明。本仓库是 WireGuard 官方 Windows 客户端，不是 Linux 内核实现，也不是 `wg-quick(8)` 脚本。Linux `wg-quick` 里 `AllowedIPs` 会同时驱动路由与 `iptables` 规则、脚本里的 `%i` 会被替换成接口名、DNS 通过 `resolvconf` 设置、`SaveConfig` 会把运行时状态回写到配置文件——这四组语义都不是 Windows 客户端的能力。Windows 侧把 `AllowedIPs` 汇总去重后下发为 WireGuard 接口的路由，全流量场景的封锁由 WFP 规则实现而非 `iptables`；自定义脚本键用的是环境变量 `WIREGUARD_TUNNEL_NAME` 而不是 `%i`，且默认不执行，需 `DangerousScriptExecution` 注册表键（见 04-07）；DNS 是作为接口配置下发而不是调用 `resolvconf`；`conf/config.go` 的 `Interface` 与 `Peer` 都没有 `SaveConfig` 成员，`conf/parser.go` 的 `switch` 也没有对应的 `case`，把它写进配置只会得到「段内无效键」的解析错误。逐条边界会在第 7 节结合误用再展开。

本篇不展开结构体字段的内存布局与类型定义，不展开配置解析状态机、路由下发与 WFP 规则的实现，也不罗列 `conf` 包与 `tunnel` 包的模块能力清单，统一收敛到交叉引用：`字段见 05-02 ｜ 原理见 06-02 ｜ 模块见 07-01`。更细的类型（32 字节密钥、主机端口结构、时间与流量格式化）见 05-03，路由与 kill-switch 机制见 06-06 与 06-09，隧道服务模块见 07-05。本册内部分工：`[Interface]` 段逐键见 04-02，INI 语法与全集索引见 04-01，运行时查询与修改见 04-05，配置排错见 04-08。后文所有「解析报错」文本取自 `conf/parser.go` 中 `l18n.Sprintf` 的英文原串，运行时会按本地化资源显示为对应语言，具体显示文案需对照实际版本核验。

### 2. 索引与全参数表

下表把 `[Peer]` 段五个键一次列全，列依次为键名、必填性、合法取值、解析入口、省略行为与序列化写出条件。解析入口列均为 `conf/parser.go` 内的函数，写出条件列均为 `conf/writer.go` 内 `ToWgQuick` 的判定表达式。

| 键名 | 必填性 | 合法取值 | 解析入口（conf/parser.go） | 省略时的行为 | 写出条件（conf/writer.go） |
|---|---|---|---|---|---|
| `PublicKey` | 必填，缺失即整份配置解析失败 | Base64 编码且解码后恰为 32 字节 | `parseKeyBase64` | 返回 `All peers must have public keys` | 恒为真，每个 peer 都输出 |
| `PresharedKey` | 可选 | Base64 编码且解码后恰为 32 字节 | `parseKeyBase64` | 保持全零，视为未设置 | `!peer.PresharedKey.IsZero()` |
| `AllowedIPs` | 可选 | 逗号分隔的 CIDR 或裸 IP 列表 | `splitList` 加 `parseIPCidr` | 空列表，该 peer 不贡献路由 | 列表长度大于 0 时输出 |
| `Endpoint` | 可选 | `主机:端口` 或 `[IPv6]:端口` | `parseEndpoint` 加 `parsePort` | 空主机，视为未设置 | `!peer.Endpoint.IsEmpty()` |
| `PersistentKeepalive` | 可选 | `off` 或 0 到 65535 的整数 | `parsePersistentKeepalive` | 0，等同关闭保活 | `peer.PersistentKeepalive > 0` |

表中「必填性」一列只有 `PublicKey` 为真，依据是 `conf/parser.go` 在 `FromWgQuick` 收尾处的循环：只要某个 peer 的 `PublicKey.IsZero()` 成立就返回错误并中止整份配置的解析；而 `PrivateKey` 的必填校验针对的是 `[Interface]` 段，与本段无关。其余四键在源码里都没有「必须出现」的检查，省略后保留各自的零值，由 `ToWgQuick` 按写出条件决定是否回写该行。另需注意，写出条件与「是否曾出现在原文件里」无关：即使原配置显式写了 `PersistentKeepalive = off`，解析后值为 0，`ToWgQuick` 也不会再输出这一行；`PresharedKey` 若写了一个恰好全零的 32 字节值，同样会被 `IsZero()` 判为未设置而丢弃。这是配置往返（导入再导出）后文本可能发生变化的直接原因。

下表汇总五个键在解析阶段可能触发的错误，便于把编辑器的报错信息反查到具体键与具体函数。错误文本为 `l18n.Sprintf` 的英文原串，实际界面文案需对照实际版本核验。

| 错误文本（英文原串） | 触发条件 | 关联解析函数 |
|---|---|---|
| `Invalid key for [Peer] section` | 段内出现五个白名单之外的键 | `FromWgQuick` 的 `default` 分支 |
| `All peers must have public keys` | 任一 peer 未写 `PublicKey` | `FromWgQuick` 收尾校验 |
| `Invalid key: %v` | Base64 字符串无法解码 | `parseKeyBase64` |
| `Keys must decode to exactly 32 bytes` | 解码后字节数不是 32 | `parseKeyBase64` |
| `Two commas in a row` | 列表里出现连续逗号或首尾逗号 | `splitList` |
| `Invalid IP address: ` | CIDR 与裸 IP 都解析失败 | `parseIPCidr` |
| `Missing port from endpoint` | 端点字符串不含冒号 | `parseEndpoint` |
| `Invalid endpoint host` | 冒号前的主机部分为空 | `parseEndpoint` |
| `Brackets must contain an IPv6 address` | 方括号内不是合法 IPv6 | `parseEndpoint` |
| `Invalid port` | 端口不在 0 到 65535 | `parsePort` |
| `Invalid persistent keepalive` | 保活值越界且不是 `off` | `parsePersistentKeepalive` |
| `Key must have a value` | 等号后为空 | `FromWgQuick` 通用校验 |
| `Config key is missing an equals separator` | 行内没有等号 | `FromWgQuick` 通用校验 |

最后一类容易混淆的是「配置键」与「只读运行时统计」的界线，如下表所示。`conf/config.go` 的 `Peer` 同时容纳两类成员，但只有前五个能出现在 `.conf` 文本里。

| 名称 | 归属 | 数据来源 | 能否写入 .conf |
|---|---|---|---|
| `PublicKey` 等五键 | 可写配置键 | `FromWgQuick` 解析文本 | 能，见本节第一张表 |
| `RxBytes` / `TxBytes` | 只读运行时统计 | `FromDriverConfiguration` 读回驱动 | 不能，写出时被忽略 |
| `LastHandshakeTime` | 只读运行时统计 | `FromDriverConfiguration` 读回驱动 | 不能，写出时被忽略 |
| `Comments` | 段内注释保真 | `FromWgQuick` 收集注释行 | 由注释语法体现，非键值 |

补充三条通用语法规则，它们对五个键一视同仁。其一，键名在 `FromWgQuick` 里先经 `strings.ToLower` 归一，因此 `PublicKey`、`publickey`、`PUBLICKEY` 等价，导出时统一回写为标准驼峰写法。其二，行内以 `#` 起始的部分被 `strings.Cut` 切为注释，不参与取值，但注释会被保留在 `Comments` 结构里以便往返还原（字段见 05-04）。其三，同一 peer 段内重复写同一个键并不报错：标量键如 `PublicKey`、`PresharedKey`、`Endpoint`、`PersistentKeepalive` 采用直接赋值，后写覆盖前写；列表键 `AllowedIPs` 采用 `append` 累加，重复写会累积条目，之后再经 `DeduplicateNetworkEntries` 在同一 peer 内按字符串精确去重。因此「重复键」不会让解析失败，却可能产生与直觉不同的最终值，编写配置时应避免。

### 3. 逐项详解

#### 3.1 `PublicKey`

`PublicKey` 是对端（远程节点）的 Curve25519 公钥，Base64 编码，解码后必须恰为 32 字节，对应 `conf/config.go` 中 `Key` 类型（底层为 `[32]byte`）。它是 `[Peer]` 段唯一强制键：`FromWgQuick` 收尾会遍历所有 peer，调用 `Key.IsZero()` 判定，任何全零公钥都会让整份配置解析失败。这与 `[Interface]` 段的 `PrivateKey` 形成配对——本地私钥用来派生本地公钥，对端公钥用来标识并认证该 peer，二者经 X25519 参与 Noise_IKpsk2 握手；本仓库只负责把密钥下发到驱动，握手与加密的数据面由外部项目 WireGuardNT 实现（原理见 06-04）。写配置时最常见的来源是 `wg genkey` 与 `wg pubkey` 的组合（见 04-05），或由对端管理员提供。

解析入口 `parseKeyBase64` 用 `base64.StdEncoding.DecodeString`，随后检查 `len(k) != KeyLength`，`KeyLength` 在 `conf/config.go` 中定义为 32。这意味着粘贴时多余空格、换行、被邮件客户端改写过的字符、少一位或 trailing padding 错误都会让解码失败；`FromWgQuick` 已对值做过 `TrimSpace`，所以行首行尾空白无害，但字符串中间的空白不行。写出侧 `ToWgQuick` 对 `PublicKey` 的 `present` 参数恒传 `true`，即每个 `[Peer]` 段都会输出一行公钥，值由 `Key.String()` 以标准 Base64 重新编码。

还须区分 `conf/config.go` 里两个与密钥相关但不属于配置键的方法：`Key.Public()` 用 `ecdh.X25519().NewPrivateKey` 从私钥派生公钥，`Config.Redact()` 则把私钥、四个脚本键以及每个 peer 的公钥与预共享密钥清零后用于日志脱敏，其中公钥被替换成小端序号以便日志里区分 peer。前者是工具方法，后者是日志输出前的处理，都不改变 `.conf` 里的值，也不该被误读为「配置里可以写派生结果」。字段与类型细节统一见 05-02 与 05-03。

#### 3.2 `PresharedKey`

`PresharedKey` 是可选的第二层对称密钥，同样要求 Base64 解码为 32 字节，解析入口仍是 `parseKeyBase64`。它在协议里与 Noise_IKpsk2 的 psk2 环节相关，作用是在 Curve25519 之外再叠加一层双方共享的对称秘密；是否启用完全取决于对端是否配置了相同的值，两端不一致会导致握手失败，而不是「降级为不加密」。本仓库只把它作为普通 `Key` 成员保存并下发，不做密钥协商，密钥的生成可用 `wg genpsk`（见 04-05）。

零值语义是该键最需要留意的点。`conf/config.go` 的 `Peer` 里 `PresharedKey` 是值类型 `Key` 而非指针，未配置时是 32 个零字节；`conf/writer.go` 用 `!peer.PresharedKey.IsZero()` 决定是否写出该行，`ToDriverConfiguration` 也用同一判断决定是否为该 peer 追加 `driver.PeerHasPresharedKey` 标志。也就是说，「没写这一行」与「写了一个全零值」在语义上等价：前者不设置标志，后者同样被判为未设置。反过来，只要写出条件成立，导出文本里就会出现 `PresharedKey` 这一行，因此导入一份带 PSK 的配置再导出，PSK 会原样保留，这点是配置往返无损的关键。

由于 `PresharedKey` 是明文敏感材料，它与 `[Interface]` 的 `PrivateKey` 一样受 Windows 侧的存储保护约束：manager 服务把新增 `.conf` 用 DPAPI 加密为 `.conf.dpapi` 后删除明文（见 03-04、原理见 06-03），因此不应把带 PSK 的明文配置长期留在共享目录或版本库里。本篇只讲键的用法，存储与加解密机制不在此展开。

#### 3.3 `AllowedIPs`

`AllowedIPs` 是本段语义最重的键：它既定义「哪些目标地址的数据包应该发往这个 peer」（出站路由选择），也定义「来自这个 peer 的数据包允许携带哪些源地址」（入站校验），在 Windows 客户端里由 tunnel 服务汇总所有 peer 的该值、去重后写入 WireGuard 接口的路由表（原理见 06-06）。取值是逗号分隔的列表，每一项经 `conf/parser.go` 的 `splitList` 切分、再由 `parseIPCidr` 解析：先尝试 `netip.ParsePrefix` 接受 `10.0.0.0/8` 这类 CIDR；失败后尝试 `netip.ParseAddr` 接受裸地址，并按 `netip.PrefixFrom(addr, addr.BitLen())` 补成主机路由，即 IPv4 裸地址等价于 `/32`、IPv6 裸地址等价于 `/128`。因此 `AllowedIPs = 192.168.5.7` 是合法写法，等价于 `192.168.5.7/32`；两者都失败才返回 `Invalid IP address`。`splitList` 会对每段 `TrimSpace`，但遇到空段（连续逗号、行尾多余逗号）直接返回 `Two commas in a row`，所以结尾多打一个逗号会让整份配置解析失败。

多 peer 场景下该键的规则尤其重要。配置文件里每出现一次 `[Peer]`，`FromWgQuick` 就调用 `maybeAddPeer` 收起上一个 peer 并新建一个 `Peer`，因此 `AllowedIPs` 的作用域严格限于所在段，不会自动继承到下一个 peer。多个 peer 之间若写了重叠网段，源码层面的 `DeduplicateNetworkEntries` 只在**单个 peer 内部**按 `addr.String()` 精确去重，并不跨 peer 合并；跨隧道的路由冲突则由 `Config.IntersectsWith` 判定（原理见 06-06，排障见 04-08）。全流量场景通常写 `0.0.0.0/0` 与 `::/0`；按 `docs/netquirk.md` 的约定，单 peer 且该 peer 含 `/0` 的 AllowedIP 会触发 WFP kill-switch 规则，而用 `0.0.0.0/1 + 128.0.0.0/1`、`::/1 + 8000::/1` 的拆分写法可规避该触发条件（原理见 06-09）。这些是 Windows 侧的路由与防火墙语义，不是 Linux `iptables` 规则；Windows 客户端不提供也不执行 `iptables`。

写出侧 `ToWgQuick` 在列表非空时以 `", "` 连接各 `netip.Prefix.String()` 输出，顺序保持解析时的先后顺序。`ToDriverConfiguration` 则把每一项编组为 `driver.AllowedIP`：用 `prefix.Bits()` 填 `Cidr`，按地址族写 `AF_INET` 或 `AF_INET6`，并把地址字节拷入固定数组。这里只需知道「配置里的每个网段最终成为驱动侧的一条允许 IP 记录」即可，结构与标志定义见 05-05。

#### 3.4 `Endpoint`

`Endpoint` 指定对端的网络可达地址与 UDP 端口，格式为 `主机:端口`；当主机是 IPv6 字面地址时必须用方括号包裹，如 `[2001:db8::1]:51820`。解析入口 `parseEndpoint` 用 `strings.LastIndexByte(s, ':')` 找最后一个冒号来切分主机与端口，因此带方括号的 IPv6 也能正确切出末尾端口；找不到冒号返回 `Missing port from endpoint`，冒号前为空返回 `Invalid endpoint host`。端口交给 `parsePort`，合法范围 0 到 65535，越界返回 `Invalid port`。方括号的校验比较严格：源码要求括号内必须是能被 `netip.ParseAddr` 解析且 `Is6()` 为真的地址，否则返回 `Brackets must contain an IPv6 address`；同时也处理了形如 `[fe80::1%eth0]:51820` 的区域标识，会在最后一个 `%` 处截断后再校验地址。写出侧 `Endpoint.String()` 会在主机含冒号时自动补回方括号，因此导入导出的文本格式一致。

该键是可选的：省略后 `Endpoint.IsEmpty()`（判据是 `len(e.Host) == 0`）为真，`ToWgQuick` 不输出该行，`ToDriverConfiguration` 也不追加 `driver.PeerHasEndpoint` 标志，此时该 peer 只能被动等待对端先发起连接，常见于服务端为对端预置公钥、由客户端主动连入的拓扑。还有一层容易忽略的事实：`ToDriverConfiguration` 只在 `netip.ParseAddr(config.Peers[i].Endpoint.Host)` 成功时才设置 `PeerHasEndpoint` 并写入 `RawSockaddrInet`，也就是下发到驱动时端点主机必须是**字面 IP 地址**；配置里写域名是可接受的写法，域名在真正下发前会被解析为地址，这一解析属于运行时机制，原理见 06-02，本篇不展开。

`Endpoint` 与 `[Interface]` 段的 `ListenPort` 分工不同：前者是「我要连到哪里」，后者是「我在本地哪个 UDP 端口监听」。二者都可为 0（未设置时由系统选择），但语义不可互换。另须强调，配置端点不涉及 Linux `resolvconf` 或任何 DNS 解析器配置文件，DNS 服务器由 `[Interface]` 的 `DNS` 键作为接口配置下发（见 04-02，原理见 06-08）。

#### 3.5 `PersistentKeepalive`

`PersistentKeepalive` 控制是否周期性发送保活报文以维持 NAT / 防火墙上的 UDP 映射，取值是 `off` 或 0 到 65535 的整数（秒）。解析入口 `parsePersistentKeepalive` 先特判字符串 `off` 返回 0，再用 `strconv.Atoi` 转换，越界返回 `Invalid persistent keepalive`。零值即等同于关闭保活，因此 `off`、不写、`0` 三者在 `conf.Peer.PersistentKeepalive`（`uint16`）里最终都是 0。写出侧 `ToWgQuick` 仅在 `peer.PersistentKeepalive > 0` 时输出该行；`ToDriverConfiguration` 却把 `driver.PeerHasPersistentKeepalive` 作为基础标志恒定追加给每个 peer，再把该值填入 `driver.Peer.PersistentKeepalive` 字段，这一点与「不写就不设置」的直觉不同，值得留意。

典型用法是位于 NAT 之后、且需要被对端随时访问的一端设置 15 到 25 秒量级的保活，例如 `PersistentKeepalive = 25`；对端有固定公网地址、或只在有流量时才需要连通的场景则无需设置。取值过大不会带来额外收益，只会产生周期性空流量；取值过小则增加握手与设备唤醒频率。它不影响 `AllowedIPs` 的路由选择，也不参与密钥派生，纯粹是链路保活参数。该键按 peer 生效，多 peer 配置里可以只对需要穿透 NAT 的那个 peer 设置。

#### 3.6 多 Peer 组合规则

一份配置可以包含任意多个 `[Peer]` 段，`FromWgQuick` 用 `parserState` 在 `inInterfaceSection`、`inPeerSection`、`notInASection` 三态间切换：遇到 `[interface]` 或 `[peer]` 时先 `maybeAddPeer` 收起当前 peer（若非空），再重置状态与注释收集器；段外的非注释行统一返回 `Line must occur in a section`。因此 `[Peer]` 段之间可以穿插注释，但不能把键值行写在任何段之外。每个 peer 各自持有完整的五个键，互不共享；`PublicKey` 的必填校验是「每个 peer 都要有」，而不是「整份配置有一个即可」。

组合时要注意三点。第一，五个键都属于 peer 作用域，把 `PreUp`、`PostUp`、`PreDown`、`PostDown` 或 `Table` 之类 `[Interface]` 专用键误写进 `[Peer]` 段，会命中 `default` 分支并返回 `Invalid key for [Peer] section`；反之把 `PublicKey` 写进 `[Interface]` 段同样会报 `Invalid key for [Interface] section`。第二，多个 peer 的 `AllowedIPs` 会在运行时被汇总，重叠网段可能引发路由归属不明，配置阶段应主动规划网段划分。第三，`PersistentKeepalive` 与 `PresharedKey` 都是按 peer 独立判断的，导出时 `ToWgQuick` 逐 peer 输出，段间以空行分隔。多 peer 与 AllowedIPs 的汇总、去重及 kill-switch 判定关系见图 04-03-02，五个键从文本到驱动的总体去向则见图 04-03-01。

#### 3.7 运行时统计字段（只读）

`conf/config.go` 的 `Peer` 末尾三个成员 `RxBytes`、`TxBytes`、`LastHandshakeTime` 不属于本章参数表，因为它们不是配置键，没有任何一个 `case` 会从 `.conf` 文本里读取它们，`ToWgQuick` 也不会写出。它们的填充路径是 `conf/parser.go` 的 `FromDriverConfiguration`：该函数从 `driver.Interface` 逐个取出 `driver.Peer`，把 `p.TxBytes`、`p.RxBytes` 转成本仓库的 `Bytes` 类型，把 `p.LastHandshake` 由 Windows FILETIME 基准换算成 `HandshakeTime`，并同时读回公钥、预共享密钥、端点、保活与允许 IP 列表，用于 UI 展示与运行时查询（字段见 05-03，原理见 06-05）。展示格式由 `conf/config.go` 的 `Bytes.String()` 与 `HandshakeTime.String()` 决定：前者按 1024 进制输出 B / KiB / MiB / GiB / TiB 并保留两位小数，后者输出「Now」、类似 `3 seconds ago` 的相对时间字串，或在系统时钟回拨时输出告警串。这正是 `wg show` 里 `transfer` 与 `latest handshake` 两行的数据来源，判读见第 4 节。

### 4. 典型示例

下面是一份包含两个 peer 的完整配置，用于把五个键的取值与组合规则落到实例上。第一台对端使用 IPv4 端点、预共享密钥与保活，承载内网网段与全流量 IPv4 默认路由；第二台对端使用 IPv6 字面端点、站点网段，且不设置保活。

```conf
[Interface]
PrivateKey = yAnz5TF+lXXJte14tfi3MtAFlb1qppTVR0kH4bqvkUwqU=
Address = 10.2.0.2/32
DNS = 10.2.0.1

[Peer]
# 主网关：全流量 + 内网
PublicKey = JRI8Xc0zKP9kXk8qP84NdUQA04h6DLfFbwJn4g+/PFs=
PresharedKey = FpKy5hBZDeXKnjBRbwQZ8Fp9pUcVZ3mHtLxNrS1vQaE7c=
AllowedIPs = 0.0.0.0/0, 10.2.0.0/24
Endpoint = 163.172.161.0:12912
PersistentKeepalive = 25

[Peer]
# 站点到站点分支
PublicKey = lfTRXEWxt8mZc8cjSvOWN3tqnTpWw4v2Eg3qF6WTklw=
AllowedIPs = 10.42.0.0/16, 2001:db8:42::/48
Endpoint = [2001:db8:1::1]:51820
```

把这类配置安装为隧道服务并用 `wg show` 查询，可以得到类似下面这份输出。输出样例取自 `docs/enterprise.md`，此处为原样引用；示例输出，具体格式需对照实际版本核验。

```text
> wg show myconfname
interface: myconfname
  public key: lfTRXEWxt8mZc8cjSvOWN3tqnTpWw4v2Eg3qF6WTklw=
  private key: (hidden)
  listening port: 53488

peer: JRI8Xc0zKP9kXk8qP84NdUQA04h6DLfFbwJn4g+/PFs=
  endpoint: 163.172.161.0:12912
  allowed ips: 0.0.0.0/0
  latest handshake: 3 seconds ago
  transfer: 6.55 KiB received, 4.13 KiB sent
```

逐行判读如下。第一行 `interface: myconfname` 给出实例名，Windows 侧对应隧道服务名 `WireGuardTunnel$myconfname`，因此 `wg show` 的参数用的是隧道名而非 Linux 意义上的内核接口名，写错名字会查不到实例。第二行 `public key` 是本地公钥，由 `[Interface]` 的 `PrivateKey` 经 X25519 派生，与 `[Peer]` 里的 `PublicKey` 不是一回事，切勿混淆。第三行 `private key: (hidden)` 表明私钥被隐藏，属正常保护行为；若查询工具把它打印为具体 Base64 值，应视为异常并核查工具版本与权限。第四行 `listening port: 53488` 是本地 UDP 监听端口，未配置 `ListenPort` 时由系统随机选取，每次启动可能变化。第五行 `peer:` 之后是第一个对端的公钥，应与配置中该 `[Peer]` 段的 `PublicKey` 完全一致，不一致说明查到了别的 peer 或配置被改动。第六行 `endpoint` 是实际协商出的对端地址端口，与配置里的 `Endpoint` 对得上说明解析与 DNS 解析链正常；显示 `(none)` 则说明对端尚未连入。第七行 `allowed ips: 0.0.0.0/0` 表明该 peer 承载 IPv4 全流量，此时按 06-09 的判定会启用 WFP kill-switch，需要额外确认 DNS 与本地网段放行。第八行 `latest handshake: 3 seconds ago` 对应 `LastHandshakeTime`，数值很小说明握手刚完成、链路活跃；长时间不更新（例如几分钟甚至几小时）通常指向端点不可达、公钥不匹配或 `PresharedKey` 两端不一致。第九行 `transfer: 6.55 KiB received, 4.13 KiB sent` 对应 `RxBytes` 与 `TxBytes`，是判断「握手成功但业务不通」的关键证据：若 received 持续增长而 sent 几乎为零，多为本地路由或 AllowedIPs 方向问题；若两个方向都不动，则更可能是握手尚未建立。以上六个运行时字段都不写回 `.conf`，运行时修改方式见 04-05。

### 5. 速查表

下表按常见组网意图给出五个键的建议组合，读者可据此快速起稿，再回到第 3 节核对每项取值约束。

| 场景 | 建议键组合 | 关键约束 |
|---|---|---|
| 客户端连固定公网网关 | `PublicKey` + `AllowedIPs` + `Endpoint` | 端点须写端口，IPv6 用方括号 |
| NAT 后需被随时访问 | 在上述基础上加 `PersistentKeepalive = 25` | 仅对需要保活的 peer 设置 |
| 启用第二层对称密钥 | 在上述基础上加 `PresharedKey` | 两端取值必须完全一致 |
| IPv4 全流量并启用 kill-switch | 单 peer 且 `AllowedIPs = 0.0.0.0/0` | 触发条件见 06-09 |
| 规避 kill-switch 触发 | 拆分 `0.0.0.0/1, 128.0.0.0/1` | 原理见 06-09 |
| 站点到站点分支 | `PublicKey` + `AllowedIPs` 写对端网段 | 避免与其他 peer 网段重叠 |
| 服务端预置对端公钥 | 仅 `PublicKey` 加 `AllowedIPs`，省略 `Endpoint` | 等待对端主动连入 |

下表把「零值 / 省略」与「导出时是否输出该行」对应起来，用于预判配置导入再导出后的文本差异。

| 键 | 省略或零值时的内存态 | `ToWgQuick` 是否输出该行 |
|---|---|---|
| `PublicKey` | 全零，但解析阶段即被判为非法 | 恒输出 |
| `PresharedKey` | 全零，`IsZero()` 为真 | 不输出 |
| `AllowedIPs` | 空列表 | 不输出 |
| `Endpoint` | 空主机，`IsEmpty()` 为真 | 不输出 |
| `PersistentKeepalive` | 0，等价 `off` | 不输出 |

两张表合起来给出一条实用结论：只有 `PublicKey` 是任何合法 peer 都必然存在的行，其余四行是否出现在导出文本里取决于取值是否非零、非空。若用脚本比对导入前后的 `.conf` 文本，应先把显式写的 `off`、全零 PSK、空列表等归一化为「该行不存在」，否则会把无害的序列化差异误判为配置篡改。

### 6. 版本差异

本篇事实以上游仓库 master 快照（2026-11 抓取）、WireGuardNT 1.1、Go 1.27.1 与 Windows 10 / Server 2019 及以上为版本基准。就 `conf/config.go`、`conf/parser.go`、`conf/writer.go` 三份文件而言，`[Peer]` 段的五个键与 `Peer` 的八个成员（五个配置字段加三个运行时统计字段）是稳定的核心契约：`FromWgQuick` 的 peer 分支只认这五个键，`ToWgQuick` 只回写这五个键，`ToDriverConfiguration` 只把这五个键编组进驱动载荷。凡在其他平台的 `wg-quick` 里见过、但 `conf/config.go` 里不存在的键，本仓库一律在 `default` 分支报「段内无效键」，不会静默忽略，也不会被当作扩展点。

以下项目属于版本相关事实，使用时应写「需对照实际版本核验」并回到给出的源码路径复核，不要凭印象补全。其一，`PresharedKey` 与 `AllowedIPs` 是否在某些发行版被改为必填：本快照的 `FromWgQuick` 收尾只校验 `PublicKey` 与 `[Interface]` 的 `PrivateKey`，没有对这两项做非空检查，核验路径为 `conf/parser.go` 的收尾校验段。其二，端点主机对域名与 IPv6 区域标识的支持范围：`parseEndpoint` 目前接受方括号内带 `%` 的区域标识，但 `ToDriverConfiguration` 只把能 `netip.ParseAddr` 的字面 IP 设为 `PeerHasEndpoint`，域名解析发生在本仓库之外，核验路径为 `conf/parser.go` 与 `conf/writer.go`。其三，`PersistentKeepalive` 与端口的上限 65535 来自 `uint16` 与 `parsePort` / `parsePersistentKeepalive` 的显式范围检查，具体错误文案与边界是否随本地化或版本调整，核验路径同为 `conf/parser.go`。其四，驱动侧 `driver.PeerHasPresharedKey`、`driver.PeerHasEndpoint`、`driver.PeerHasPersistentKeepalive` 等标志位的命名与取值，核验路径为 `driver/configuration_windows.go`（字段见 05-05）。其五，`wg show` 输出行的具体措辞、单位与本地化，核验路径为 `docs/enterprise.md` 与 `wireguard-tools` 的 `wg(8)` 实现（见 04-05）。凡涉及具体版本号、驱动版本、MSI 文件名与下载 URL 的时效性数值，一律按总纲第 9 节约定处理，不在本篇写死。

### 7. 常见误用与调试

误用一：把 Linux `wg-quick` 语义搬进来。最常见的是在 `[Peer]` 段附近写 含 `iptables` 规则的 `PostUp` 行，或引用 `%i` 占位符，或期望 `SaveConfig = true` 把运行时状态回写。本仓库 `conf/config.go` 无 `SaveConfig` 成员、`conf/parser.go` 无对应 `case`，`PostUp` 等脚本键只在 `[Interface]` 段被识别；Windows 用 WFP 规则实现封锁、用 `WIREGUARD_TUNNEL_NAME` 环境变量替代 `%i`、用接口 DNS 配置替代 `resolvconf`，且四个脚本键默认不执行（见 04-02 与 04-07）。把这些写法当 Windows 能力会导致解析直接失败或配置「看起来生效、实际什么都没发生」。

误用二：`AllowedIPs` 语法细节。行尾多一个逗号触发 `Two commas in a row`；写了既非 CIDR 也非裸地址的字符串触发 `Invalid IP address`；把 IPv6 端点写成 `2001:db8::1:51820` 而不加方括号会命中 `Missing port from endpoint` 或方括号校验错误。另需注意 `0.0.0.0/0` 与 `::/0` 是两条独立记录，只写前者不会覆盖 IPv6 流量。

误用三：端点与公钥错配。`Endpoint` 省略后该 peer 只能被动等待连入，却仍期待它主动出站；`PublicKey` 与对端实际公钥不一致、`PresharedKey` 两端取值不同，都会表现为「配置能解析、服务能启动，但 `latest handshake` 一直不更新」。此时应先用第 4 节的判读方法看 `wg show` 输出，再逐项比对两端密钥文本。

误用四：把运行时统计当配置键。有人看到 `transfer: 6.55 KiB received` 就往 `.conf` 里加 `RxBytes` 这样的赋值行，或在 `latest handshake` 长时间不更新时试图改配置文件里的 `LastHandshakeTime`。这三者由 `FromDriverConfiguration` 从驱动读回，写入文本只会得到「段内无效键」错误；正确做法是排查端点可达性、密钥一致性、防火墙与路由归属。

误用五：多 peer 网段重叠。两个 peer 写了重叠或包含的 `AllowedIPs`，`DeduplicateNetworkEntries` 只在单个 peer 内去重，不会替你裁决归属；重叠会让数据包被发往非预期的 peer。排查时把每个 peer 的网段列成清单逐个比对，跨隧道冲突可借助 `Config.IntersectsWith` 的判定（原理见 06-06，工具化排错见 04-08）。

调试顺序建议固定为四步：第一步，用 UI 的配置编辑器或 `FromWgQuick` 等价的解析动作确认配置能被接受，先排除语法与必填错误；第二步，确认隧道服务已启动、适配器已创建，再执行 `wg show <隧道名>` 取回运行时状态；第三步，按第 4 节逐行判读 `endpoint`、`latest handshake`、`transfer` 三行，定位是「握手未建立」还是「握手已建立但业务不通」；第四步，用 `wireguard /dumplog` 与 `wireguard /dumplog /tail` 读取共享环形日志（见 04-04、08-01），结合 `docs/enterprise.md` 给出的权限要求确认查询进程是否具备 LocalSystem 或 Administrator 权限。整条链路里，配置键只负责第一步之前的静态正确性，运行期的一切状态都要回到 `wg show` 与日志判读，而不是反复改 `.conf` 猜结果。

## 04-04 `wireguard.exe` 命令行开关全集

### 1. 本篇定位与覆盖范围

本篇是 04 册「配置与命令行」中专门穷举 `wireguard.exe` 进程入口开关的一篇，事实依据只有两处：`main.go` 里 `usage()` 函数的 `flags` 数组，以及 `main()` 函数里按 `os.Args[1]` 分派的 `switch`。前者决定「官方承认哪些开关」，后者决定「每个开关接受几个参数、调用哪个入口、参数个数不对时怎么处理」。两者合起来才是完整契约，只读其一都会漏掉细节：例如 `usage()` 里写的是 `/ui CMD_READ_HANDLE CMD_WRITE_HANDLE CMD_EVENT_HANDLE LOG_MAPPING_HANDLE`，而 `main()` 用 `len(os.Args) != 6` 精确校验「程序名加开关再加四个句柄」共六个参数；又如 `/dumplog [/tail]` 里的方括号表示可选参数，对应的校验是 `len(os.Args) != 2 && len(os.Args) != 3`。

覆盖范围包含三类行为。第一类是「无参数」默认行为：`wireguard.exe` 不带任何开关时先尝试唤起已运行的 UI（`ui.RaiseUI()`），若失败则检查管理员组、提权并触发 manager 服务安装，因此它是交互式启动入口，而 `/installmanagerservice` 才是静默安装入口。第二类是十个斜杠开关，逐个覆盖安装 / 卸载 manager 服务、安装 / 卸载 / 运行 tunnel 服务、以四个继承句柄启动 UI、导出日志、触发更新、移除驱动。第三类是这些开关共有的前置检查与输出行为：`SetDllDirectory` 与 `SetDefaultDllDirectories` 的 DLL 搜索路径收敛、`checkForWow64` 的原生架构检查、`checkForAdminGroup` 的管理员组检查、`setLogFile` 的标准错误 / 标准输出分流，以及 `fatal` 在无标准错误时改用 MessageBox 的兜底。

必须先把三类命令区分清楚，这是本篇最容易被误用的边界。这里列的是 `wireguard.exe` 的 Windows 风格 `/` 开关，由本仓库 `main.go` 直接分派；`wg(8)` 的 `show`、`set`、`genkey` 等子命令属于外部项目 wireguard-tools 的 `wg.exe`，与本进程不是同一个可执行文件（见 04-05）；`sc`、`Get-Service`、`reg`、`schtasks` 等属于 Windows 自带运维命令，由 04-06 收录。三者都可在命令行里出现，但不要互相拼接或混淆参数风格。另须强调，这些开关只负责进程分派、服务安装与诊断，**不是** Linux `wg-quick` 的接口配置工具：`wireguard.exe` 没有 `up` / `down` 之类的 `wg-quick` 子命令，不解析 `iptables` 规则，不识别 `%i` 占位符，不调用 `resolvconf`，也不提供 `SaveConfig` 式的运行时回写。配置的持久化靠 `.conf` 文件与 manager 服务的 DPAPI 存储（见 03-04、原理见 06-03），运行时查询与修改靠 `wg(8)`（见 04-05）。

本篇不展开进程入口之后的服务实现、IPC 协议、环形日志格式与更新校验链，统一收敛到交叉引用：`字段见 05-09 ｜ 原理见 06-01 ｜ 模块见 07-08`。更具体的错误码与退出码映射见 05-09，入口分派与前置检查见 06-01，manager 服务与隧道跟踪见 07-08，环形日志见 07-10，更新器见 07-11，驱动卸载见 07-03。本篇只回答「有哪些开关、怎么传参、会调用什么、输出去哪里」，实现细节一律不重列。

### 2. 索引与全参数表

下表按 `usage()` 中 `flags` 数组的顺序列出全部开关，含无参数默认行为，共十一行。参数个数一列是 `main()` 里 `len(os.Args)` 的实际校验值，入口调用一列是 `main()` 的 `switch` 分支所调用的函数。

| 开关 | 参数个数 | 参数占位 | `len(os.Args)` 校验 | 入口调用（main.go） | 作用 |
|---|---|---|---|---|---|
| 无参数 | 1 | 无 | `<= 1` 进入默认分支 | `ui.RaiseUI` 或提权安装 | 唤起已有 UI，否则提权装 manager 服务 |
| `/installmanagerservice` | 2 | 无 | `!= 2` 则 `usage()` | `manager.InstallManager` | 安装 `WireGuardManager` 服务并等托盘 |
| `/uninstallmanagerservice` | 2 | 无 | `!= 2` 则 `usage()` | `manager.UninstallManager` | 卸载 manager 服务 |
| `/managerservice` | 2 | 无 | `!= 2` 则 `usage()` | `manager.Run` | 以服务方式运行 manager 主循环 |
| `/installtunnelservice` | 3 | `CONFIG_PATH` | `!= 3` 则 `usage()` | `manager.InstallTunnel` | 安装 `WireGuardTunnel$<name>` |
| `/uninstalltunnelservice` | 3 | `TUNNEL_NAME` | `!= 3` 则 `usage()` | `manager.UninstallTunnel` | 按隧道名卸载隧道服务 |
| `/tunnelservice` | 3 | `CONFIG_PATH` | `!= 3` 则 `usage()` | `tunnel.Run` | 以服务方式运行隧道主循环 |
| `/ui` | 6 | 四个句柄，见下方参数说明 | `!= 6` 则 `usage()` | `ui.RunUI` | 由 manager 孵化并接管 UI |
| `/dumplog` | 2 或 3 | 可选 `/tail` | `!= 2` 且 `!= 3` 则 `usage()` | `ringlogger.DumpTo` | 导出共享环形日志到标准输出 |
| `/update` | 2 | 无 | `!= 2` 则 `usage()` | `updater.DownloadVerifyAndExecute` | 检查并执行 MSI 更新 |
| `/removedriver` | 2 | 无 | `!= 2` 则 `usage()` | `driver.Uninstall` | 无适配器时移除 WireGuardNT 驱动 |

表中「参数个数」含 `os.Args[0]` 程序名本身，因此 `/installtunnelservice CONFIG_PATH` 对应 3、`/ui` 加四个句柄对应 6。凡是参数个数不符、或传入了 `switch` 未匹配的开关，`main()` 末尾统一落到 `usage()`：先用 `info` 打印命令行选项清单，再 `os.Exit(1)`。也就是说，本进程没有「未知开关静默忽略」的行为，也没有多级子命令与帮助开关，`--help`、`-h` 这类写法都会走 `usage()` 并以退出码 1 结束。

`usage()` 打印的选项清单本身就是一份权威索引，其格式可由 `main.go` 精确还原：`info` 把标题 `Command Line Options` 与格式串 `Usage: %s [\n%s]` 拼起来，`builder` 则把 `flags` 数组逐行以四个空格缩进。下表把这份清单与 `main()` 分支的对应关系再压缩一次，便于速查。

| `usage()` 中的行 | `main()` 分支 | 是否需管理员组检查 |
|---|---|---|
| `(no argument): elevate and install manager service` | `len(os.Args) <= 1` | 是，仅 UI 唤起失败后 |
| `/installmanagerservice` | 同名 `case` | 间接，由服务安装路径负责 |
| `/installtunnelservice CONFIG_PATH` | 同名 `case` | 由 `manager.InstallTunnel` 路径负责 |
| `/uninstallmanagerservice` | 同名 `case` | 由 `manager.UninstallManager` 路径负责 |
| `/uninstalltunnelservice TUNNEL_NAME` | 同名 `case` | 由 `manager.UninstallTunnel` 路径负责 |
| `/managerservice` | 同名 `case` | 由服务控制管理器约束 |
| `/tunnelservice CONFIG_PATH` | 同名 `case` | 由服务控制管理器约束 |
| `/ui 4 个句柄` | 同名 `case` | 内部判定令牌并降权 |
| `/dumplog [/tail]` | 同名 `case` | 由日志文件 ACL 约束 |
| `/update` | 同名 `case` | 由更新器与 MSI 权限约束 |
| `/removedriver` | 同名 `case` | 由驱动卸载权限约束 |

`/ui` 的四个句柄在 `usage()` 中的完整占位为 `CMD_READ_HANDLE CMD_WRITE_HANDLE CMD_EVENT_HANDLE LOG_MAPPING_HANDLE`，详见下方参数说明；为避免表格单元格过长，第二张表以「4 个句柄」概括。所有开关的输出与退出行为见下表，依据是 `setLogFile`、`info`、`fatal` 三个辅助函数。

| 行为 | 触发条件 | 具体表现（main.go） |
|---|---|---|
| 标准错误优先 | `GetStdHandle(STD_ERROR_HANDLE)` 成功 | 日志写到 stderr |
| 退而求其次 | 前者失败但 `STD_OUTPUT_HANDLE` 成功 | 日志写到 stdout |
| 无控制台兜底 | 两个句柄都取不到 | `log.SetOutput(io.Discard)`，改用 MessageBox |
| 打印选项清单 | 参数不匹配或未知开关 | `info` 输出后 `os.Exit(1)` |
| 致命错误 | 各分支返回 `err` | `fatal` 输出后以 1 退出 |
| 正常完成 | 分支成功返回 | `main` 直接返回，退出码 0 |

`docs/enterprise.md` 对输出分流有一句概括性说明：这些命令把错误和状态写到标准错误，若标准错误不存在则写到标准输出。这正是上表前三行的行为，也是 `/update 2> C:\path\to\update\log.txt`、`/dumplog > C:\path\to\diagnostic\log.txt` 之类重定向写法能生效的原因。

### 3. 逐项详解

#### 3.1 无参数：交互式启动

当 `len(os.Args) <= 1` 时，`main()` 不进入 `switch`，而是先调用 `ui.RaiseUI()` 尝试把已经运行的 UI 窗口提到前台；若返回 true 就直接返回，进程结束。若 UI 尚不存在，则调用 `checkForAdminGroup()`（用 `elevate.TokenIsElevatedOrElevatable` 判断当前令牌是否属于内建管理员组，否则 `fatalf` 报「WireGuard may only be used by users who are a member of the Builtin Administrators group」），随后调用 `execElevatedManagerServiceInstaller()`：取自身可执行路径，用 `elevate.ShellExecute` 以 `/installmanagerservice` 参数、窗口模式 `SW_SHOW` 提权重启自己，随后 `os.Exit(0)`。因此「双击 wireguard.exe」与「运行 `wireguard /installmanagerservice`」最终都会走到同一安装入口，区别是前者先尝试唤起 UI、且按需弹出 UAC 提权。`docs/enterprise.md` 把这句话总结为：无参数适合交互式启动，`/installmanagerservice` 适合静默安装。

#### 3.2 `/installmanagerservice`

参数个数必须为 2。分支先起一个 goroutine 执行 `ui.WaitForRaiseUIThenQuit()`，再调用 `manager.InstallManager()`。若返回 `manager.ErrManagerAlreadyRunning`，说明服务已在运行，此时调用 `checkForAdminDesktop()` 检查当前桌面，随后仍以 `fatal(err)` 结束；若安装成功，同样调用 `checkForAdminDesktop()`，然后 `time.Sleep(30 * time.Second)` 等待托盘图标出现，超时则 `fatalf` 报「WireGuard system tray icon did not appear after 30 seconds.」。这条 30 秒等待解释了为什么静默安装命令在脚本里看起来「卡住」——它在等服务孵化出 UI。服务名固定为 `WireGuardManager`（见 `docs/enterprise.md` 与 `manager/install.go`）。安装后可用 `services.msc` 或 `sc` 查询（见 04-06）。

#### 3.3 `/uninstallmanagerservice` 与 `/managerservice`

两者参数个数都必须为 2。前者调用 `manager.UninstallManager()` 卸载 `WireGuardManager` 服务；后者调用 `manager.Run()` 进入 manager 服务主循环，是服务控制管理器实际启动服务时执行的入口，不应由管理员手动在普通命令行里长期运行。二者都是「无额外参数」的开关，多传一个参数就会命中 `usage()` 并退出码 1。卸载顺序、服务清理与注册表清理的运维流程见 03-06，服务内部实现见 07-08，机制见 06-10。

#### 3.4 `/installtunnelservice CONFIG_PATH`

参数个数必须为 3，`os.Args[2]` 是配置文件路径，交给 `manager.InstallTunnel(os.Args[2])`。`docs/enterprise.md` 给出了两条最典型的用法：

```text
> wireguard /installtunnelservice C:\path\to\some\myconfname.conf
> wireguard /uninstalltunnelservice myconfname
```

安装后生成的服务名为 `WireGuardTunnel$myconfname`，隧道名取自配置文件名。文件扩展名决定解读方式：以 `.conf` 结尾按普通 `wg-quick(8)` 配置文件解析；以 `.conf.dpapi` 结尾则视为同一份配置经 `CryptProtectData(bytes, "myconfname")` 加密后的版本。这一区分很重要：manager 服务会把放进 `%ProgramFiles%\WireGuard\Data\Configurations\` 的明文 `.conf` 加密为 `.conf.dpapi` 并删除明文（见 03-04），因此脚本化部署时可以直接投放 `.conf`，也可以投放预先生成的 `.conf.dpapi`。注意这里说的「按 `wg-quick(8)` 配置文件解析」仅指 INI 配置键语法（见 04-01 至 04-03），**不表示**本命令会执行 `wg-quick` 的 `iptables`、`%i`、`resolvconf` 或 `SaveConfig` 逻辑。

#### 3.5 `/uninstalltunnelservice TUNNEL_NAME` 与 `/tunnelservice CONFIG_PATH`

两者参数个数都必须为 3。`os.Args[2]` 的含义不同：前者是隧道名（`TUNNEL_NAME`），交给 `manager.UninstallTunnel` 按名卸载，对应服务名 `WireGuardTunnel$<name>`；后者是配置文件路径（`CONFIG_PATH`），交给 `tunnel.Run` 进入隧道服务主循环，是服务控制管理器启动隧道服务时的实际入口。把隧道名误传给 `/tunnelservice` 或把路径误传给 `/uninstalltunnelservice`，参数个数虽然对了，但入口函数拿到的是错误类型的实参，会在各自内部报错，这是脚本里最常见的参数错配。`docs/enterprise.md` 明确隧道服务可以独立于 manager 服务与 UI 使用，二者也可组合使用，这类部署形态见 03-03。

#### 3.6 `/ui` 与四个继承句柄

`/ui` 是本进程唯一需要四个额外参数的开关，`main()` 要求 `len(os.Args) == 6`，即 `wireguard.exe`、`/ui` 加四个句柄值。四个占位依次为 `CMD_READ_HANDLE`、`CMD_WRITE_HANDLE`、`CMD_EVENT_HANDLE`、`LOG_MAPPING_HANDLE`，在 `usage()` 里已按此顺序列出。分支先用 `windows.OpenProcessToken` 取当前进程令牌，用 `elevate.TokenIsElevatedOrElevatable` 判定 `isAdmin`；若为真则 `elevate.DropAllPrivileges(false)` 主动丢弃特权，再把结果写入 `ui.IsAdmin`。随后 `pipeFromHandleArgument` 依次把 `os.Args[2]`、`os.Args[3]`、`os.Args[4]` 三个十进制整数字符串转成 `*os.File`，分别作为读管道、写管道、事件管道，交给 `manager.InitializeIPCClient(readPipe, writePipe, eventPipe)` 初始化 IPC 客户端；`os.Args[5]` 则交给 `ringlogger.NewRingloggerFromInheritedMappingHandle(os.Args[5], "GUI")` 复用 manager 传入的共享日志映射。最后调用 `ui.RunUI()`。

四个句柄的含义与去向见下表，这一组参数是 manager 服务孵化 UI 进程时通过句柄继承传入的，**不是**供管理员手工拼装的公开接口：手工运行 `/ui` 几乎必然因为句柄值无效而在 `pipeFromHandleArgument` 或日志映射初始化处 `fatal`。

| 顺序 | `usage()` 占位 | `os.Args` 下标 | 用途（main.go） |
|---|---|---|---|
| 1 | `CMD_READ_HANDLE` | `os.Args[2]` | IPC 命令读管道 |
| 2 | `CMD_WRITE_HANDLE` | `os.Args[3]` | IPC 命令写管道 |
| 3 | `CMD_EVENT_HANDLE` | `os.Args[4]` | IPC 事件通知管道 |
| 4 | `LOG_MAPPING_HANDLE` | `os.Args[5]` | 环形日志共享映射，名称 `GUI` |

句柄继承、会话枚举与 `CreateProcessAsUser` 的机制见 06-10，IPC 三根无名管道与 gob 编解码见 06-11，字段与结构见 05-09。四个句柄从 manager 服务到 UI 进程的传递关系如图 04-04-02 所示。

#### 3.7 `/dumplog [/tail]`

参数个数允许 2 或 3；当为 3 时，只有 `os.Args[2] == "/tail"` 才会把 `tail` 参数置为 true，其他任意第三个参数虽能通过个数校验，但不会进入跟随模式，等效于普通导出。分支先 `windows.GetStdHandle(STD_OUTPUT_HANDLE)`，取不到则 `fatal("Stdout must be set")`；随后 `conf.LogFile(false)` 定位共享环形日志，再调用 `ringlogger.DumpTo(logPath, file, tail)` 把日志写到标准输出。`docs/enterprise.md` 给出三种典型用法：重定向到文件（`wireguard /dumplog > log.txt`）、持续跟随并交给日志采集（`wireguard /dumplog /tail | log-ingest`）、在 PowerShell 里用 `select` 监视（`wireguard /dumplog /tail | select`）。日志实现见 07-10，读取链见 06-11，运维采集见 08-01。

#### 3.8 `/update`

参数个数必须为 2。分支遍历 `updater.DownloadVerifyAndExecute(0)` 返回的进度通道：若 `progress.Activity` 非空，且 `BytesTotal` 或 `BytesDownloaded` 大于 0，就按 `log.Printf` 的 `"%s: %d/%d (%.2f%%)\n"` 格式串打印活动名、已下载 / 总字节数与百分比，否则用 `log.Println` 只打印活动名；若 `progress.Error` 非空则打印错误；当 `progress.Complete` 为真或出现错误时 `return` 结束。`docs/enterprise.md` 给出重定向状态日志的写法，以及用计划任务每日触发的命令（计划任务命令的完整写法见下方示例，属 04-06 的 `schtasks` 范畴，此处仅作引用）。更新链的签名校验与 MSI 执行见 06-12，更新器模块见 07-11。

#### 3.9 `/removedriver`

参数个数必须为 2，调用 `driver.Uninstall()`。`docs/enterprise.md` 说明隧道服务在启动时创建网络适配器、关停时销毁适配器，因此该开关的适用前提是「已经没有任何 WireGuard 适配器」；在适配器仍存在时执行会失败。典型用法是 `wireguard /removedriver` 或带状态重定向的 `wireguard /removedriver 2> log.txt`。驱动卸载的权限与顺序见 03-06，驱动模块见 07-03。

#### 3.10 共有的前置检查

无论走哪条分支，`main()` 开头先执行 `windows.SetDllDirectory("")` 与 `windows.SetDefaultDllDirectories(windows.LOAD_LIBRARY_SEARCH_SYSTEM32)` 收敛 DLL 搜索路径，失败直接 `panic("failed to restrict dll search path")`；随后 `setLogFile()` 建立日志输出，再 `checkForWow64()` 判定架构——它通过 `IsWow64Process2`（旧系统上回退 `IsWow64Process`）比较进程机器类型与 `runtime.GOARCH` 对应的原生类型，若发现运行在 WOW64 下则 `fatalf("You must use the native version of WireGuard on this computer.")`，即 32 位程序跑在 64 位系统上会被拒绝。这两项发生在 `switch` 之前，因此「用错架构 MSI」和「日志句柄异常」会在任何开关上先暴露。入口分派全貌如图 04-04-01 所示。

### 4. 典型示例

第一组示例展示最容易在脚本里踩到的行为：传入 `switch` 未匹配的开关会落到 `usage()` 并打印完整选项清单。下面的输出依据 `main.go` 的 `usage()` 与 `info()` 格式串还原；示例输出，具体格式需对照实际版本核验（程序名路径与本地化文案随环境与版本变化）。

```text
> wireguard.exe /bogus
Command Line Options:
Usage: C:\Program Files\WireGuard\wireguard.exe [
    (no argument): elevate and install manager service
    /installmanagerservice
    /installtunnelservice CONFIG_PATH
    /uninstallmanagerservice
    /uninstalltunnelservice TUNNEL_NAME
    /managerservice
    /tunnelservice CONFIG_PATH
    /ui CMD_READ_HANDLE CMD_WRITE_HANDLE CMD_EVENT_HANDLE LOG_MAPPING_HANDLE
    /dumplog [/tail]
    /update
    /removedriver
]
```

逐行判读如下。第一行是标题，`info` 把 `l18n.Sprintf("Command Line Options")` 作为标题拼进日志前缀，实际界面可能显示为本地化后的「命令行选项」。第二行的 `Usage:` 后是 `os.Args[0]`，也就是本机实际可执行文件路径，据此可确认脚本调用的是amd64、x86 还是 arm64 版本，若路径指向意料之外的安装目录，应立即核查是否装错了架构或多版本并存。第三行 `(no argument): elevate and install manager service` 说明「不带参数」并非无事可做，而是提权并安装 manager 服务，这正是无参数双击与静默安装的关系。第四到第九行是三对成对开关：manager 服务的安装 / 卸载 / 运行与 tunnel 服务的安装 / 卸载 / 运行，注意带 `CONFIG_PATH` 的两个安装 / 运行开关与带 `TUNNEL_NAME` 的卸载开关参数类型不同。第十行 `/ui` 后面跟着四个大写占位，说明该开关必须由 manager 服务附带四个继承句柄调用，管理员不应手工拼接。第十一行 `/dumplog [/tail]` 的方括号表示可选参数，对应「导出一次」与「持续跟随」两种模式。第十二、十三行分别是更新与驱动移除。最后的 `]` 来自格式串 `Usage: %s [\n%s]` 的收尾，并非配置语法。整份清单出现意味着本次调用以退出码 1 结束，脚本应把「打印 Usage」视为失败而不是帮助信息。

第二组示例给出 `docs/enterprise.md` 里的典型运维命令序列，覆盖服务安装、隧道查询、日志导出、更新与驱动移除，具体命令见下方配置示例。

```text
> wireguard /installtunnelservice C:\path\to\some\myconfname.conf
> wg show myconfname
> wireguard /dumplog > C:\path\to\diagnostic\log.txt
> wireguard /dumplog /tail | log-ingest
> wireguard /update 2> C:\path\to\update\log.txt
> schtasks /create /f /ru SYSTEM /sc daily /tn "WireGuard Update" /tr "%PROGRAMFILES%\WireGuard\wireguard.exe /update" /st 03:00
> wireguard /removedriver 2> C:\path\to\removal\log.txt
```

判读这组命令时要抓住「输出去哪里」。前两条里 `/installtunnelservice` 本身成功时通常不打印内容，错误与状态走标准错误或标准输出，因此静默脚本应显式重定向；`wg show` 属于 `wg.exe` 而非 `wireguard.exe`（见 04-05）。第三、四条用 `>` 与管道消费 `/dumplog` 的标准输出，若当前会话没有标准错误，`setLogFile` 会把日志改写到标准输出，重定向依然有效；`/tail` 表示持续跟随而非一次性导出，适合交给日志采集进程。第五条把 `/update` 的状态写到文件，依据是 `main.go` 的分支用 `log.Printf` 打印活动名与百分比。第六条是 `docs/enterprise.md` 给出的计划任务示例，用 SYSTEM 账户每日 03:00 触发 `/update`，其中 `schtasks` 属 04-06 收录的运维命令。第七条在确认没有适配器后移除驱动并留状态日志。整组命令体现了 04 册的分工：`wireguard.exe` 的 `/` 开关管进程与服务生命周期，`wg(8)` 管运行时状态，`sc` / `schtasks` 管 Windows 服务与任务，三者不可混为一谈。

### 5. 速查表

下表按运维意图把开关收敛成「一行动作」，参数细节回到第 3 节核对。

| 意图 | 使用的开关 | 参数要点 |
|---|---|---|
| 交互式启动或唤起 UI | 无参数 | 会按需弹 UAC 提权 |
| 静默安装管理服务 | `/installmanagerservice` | 会等待托盘最多 30 秒 |
| 卸载管理服务 | `/uninstallmanagerservice` | 无额外参数 |
| 部署一条隧道为服务 | `/installtunnelservice` | 传 `.conf` 或 `.conf.dpapi` 路径 |

| 导出一次诊断日志 | `/dumplog` | 标准输出需可写 |
| 持续跟随日志 | `/dumplog /tail` | 第三个参数必须是 `/tail` |

| 参数个数错误示例 | `main()` 的判定 | 表现 |
|---|---|---|
| `/installtunnelservice` 少传路径 | `len(os.Args) != 3` | 打印 Usage，退出码 1 |
| `/dumplog /tail extra` 多传一项 | `len` 既不是 2 也不是 3 | 打印 Usage，退出码 1 |

### 6. 版本差异

本篇以上游仓库 master 快照（2026-11 抓取）、WireGuardNT 1.1、Go 1.27.1、Windows 10 / Server 2019 及以上、amd64 / x86 / arm64 三种 MSI 为基准。`main.go` 的 `usage()` 数组与 `main()` 的 `switch` 是本仓库最稳定的对外契约之一，但「稳定」指的是结构，不是逐字文案：所有提示串都经 `l18n.Sprintf` 走本地化，中文环境下的「Command Line Options」与「Usage」显示会随语言资源变化，因此脚本不应靠匹配提示文本判断结果，而应看退出码与服务状态。

以下项目属于版本相关事实，应写「需对照实际版本核验」并回到给出的源码路径复核。其一，开关全集是否随版本增删：本快照 `usage()` 的 `flags` 数组共十一行（无参数一行加十个斜杠开关），`main()` 的 `switch` 有十个 `case` 加末尾默认分支，任何未列出的开关都会落到 `usage()`，核验路径为 `main.go` 的 `usage()` 与 `main()`。其二，`/ui` 四个句柄的个数与顺序：本快照要求 `len(os.Args) == 6`，顺序为读管道、写管道、事件管道、日志映射，核验路径同为 `main.go` 的 `/ui` 分支。其三，`/installmanagerservice` 等待托盘的 30 秒与 `ErrManagerAlreadyRunning` 的处理逻辑，核验路径为 `main.go` 对应分支与 `services/errors.go`。其四，`os.Exit(1)` 之外的退出码细节：`fatal` 在无标准错误时用 MessageBox 后 `os.Exit(1)`，有标准错误时走 `log.Fatal`，更细的错误码映射见 05-09 与 `services/errors.go`，需对照实际版本核验。其五，`conf.LogFile(false)` 解析出的日志路径、`driver.Uninstall()` 的成功条件、`updater.DownloadVerifyAndExecute(0)` 的进度字段，核验路径分别为 `conf/path_windows.go`、`driver/driver_windows.go`、`updater/downloader.go`。其六，`docs/enterprise.md` 里示例命令的路径、服务名 `WireGuardManager` 与 `WireGuardTunnel$<name>` 的前缀，以及 `DO_NOT_LAUNCH` 等 MSI 属性，核验路径为 `docs/enterprise.md` 与 `manager/install.go`。凡涉及具体版本号、驱动版本、MSI 文件名与下载 URL 的时效性数值，按总纲第 9 节约定处理，不在本篇写死。

### 7. 常见误用与调试

误用一：把三类命令混用。把 `wg show` 写成 `wireguard.exe show`、把 `/installtunnelservice` 写成 `/installtunnelservice up`、或以为 `wireguard.exe` 有 `--help`，都会命中 `switch` 末尾的 `usage()` 并以退出码 1 结束。前者属于 `wg.exe` 的子命令（见 04-05），后者属于 Windows 服务运维命令（见 04-06）。同理，`wireguard.exe` 没有 `wg-quick` 的 `up` / `down`，也没有 `SaveConfig`、`iptables`、`%i`、`resolvconf` 语义，把它当 Linux 配置工具会一无所获。

误用二：参数个数与类型错配。最常见的是 `/installtunnelservice` 漏传路径、`/uninstalltunnelservice` 传了文件路径而非隧道名、`/tunnelservice` 传了隧道名而非路径、`/ui` 少传句柄、`/dumplog` 传了 `/tail` 之外的第三个参数。前四者会打印 Usage 退出，最后一种不会报错但也不会进入跟随模式，属于「静默失效」，排查时应回到 `main.go` 的 `len(os.Args)` 判定逐条核对。

误用三：手工调用 `/ui`。四个句柄是 manager 服务孵化 UI 进程时通过句柄继承传入的内部值，不是可公开拼装的命令行参数。手工运行 `/ui 1 2 3 4` 之类会在 `pipeFromHandleArgument` 或 `NewRingloggerFromInheritedMappingHandle` 处 `fatal`，报句柄或映射无效。正确做法是用无参数启动或 `/installmanagerservice` 让 manager 服务自行孵化 UI。

误用四：忽略架构与权限前置检查。`checkForWow64` 在 `switch` 之前执行，用错架构（例如在 64 位系统上运行 x86 版）会直接报「必须使用原生版本」；`checkForAdminGroup` 要求调用者属于内建管理员组。企业分发时应确认 GPO 下发的 MSI 与目标架构一致（见 03-05、02-05），并留意 `LimitedOperatorUI` 只放宽受限 UI、不改变这些开关的权限要求（见 04-07）。

误用五：把 usage 输出当成功。任何参数不匹配都会 `info` 打印清单后 `os.Exit(1)`，但清单本身不含「错误」字样，日志采集脚本若只匹配 stdout 文本容易漏判。应检查退出码，或配合 `sc query WireGuardManager`、`Get-Service` 之类确认服务是否真的存在（见 04-06）。

调试顺序建议固定为四步。第一步，确认二进制路径与架构：无参数或 `/bogus` 触发的 Usage 里 `os.Args[0]` 会打印实际路径，据此排除多版本并存与 WOW64 问题。第二步，确认日志去向：`setLogFile` 优先 stderr、其次 stdout、都没有则 MessageBox，因此脚本里一定要显式做 `2>` 或 `>` 重定向，否则在计划任务等无控制台环境下错误只会以弹窗形式出现并被忽略。第三步，用 `/dumplog` 导出共享环形日志、必要时用 `/dumplog /tail` 持续跟随，观察服务安装、适配器创建与 IPC 相关记录（日志判读见 08-01）。第四步，对照 `docs/enterprise.md` 的权限说明确认调用账户，隧道服务与 manager 服务均以 LocalSystem 运行，普通用户执行这些开关通常失败。整个链路里，`wireguard.exe` 的开关只负责把进程分派到正确入口，真正的隧道状态要用 `wg show` 查询（见 04-05），服务状态要用 `sc` / PowerShell 查询（见 04-06）。

## 04-05 `wg(8)` 在 Windows 的运行时查询与修改

### 1. 本篇定位与覆盖范围

本篇是 04 册「配置与命令行」中专门讲运行时查询与修改的一篇，覆盖大纲列出的九个子命令：`show`、`showconf`、`set`、`setconf`、`addconf`、`syncconf`、`genkey`、`pubkey`、`genpsk`。它与前两篇的分工是清晰的：04-01 至 04-03 讲的是静态 `.conf` 配置文件里的键，04-04 讲的是 `wireguard.exe` 的进程与服务的 `/` 开关，本篇讲的是隧道服务**跑起来之后**如何查状态、如何临时改状态、以及如何离线生成密钥材料。三者的权威源都在 04 册，但操作对象完全不同，混用是排障中最常见的错误来源。

有一条边界必须先讲透，否则后面所有结论都会被误置：`wg(8)` 的 `wg.exe` **不是本仓库的产物**。`docs/buildrun.md` 专设「`wg(8)` Support for Windows」一节，明确它是 以 Unix 为中心的 wireguard-tools 项目，用 `PLATFORM=windows make -C wireguard-tools/src` 交叉编译，产物为 `wireguard-tools/src/wg.exe`；Windows 上的 `build.bat` 会顺带构建它；它「与主 WireGuard for Windows 程序所运行的 WireGuard 实例交互」。`upstream_src/` 这份快照里没有 wireguard-tools 的源码，`main.go` 的 `usage()` 里也没有任何 `wg` 子命令。因此本篇关于子命令全集、参数形式与输出格式的描述，属于对 wg(8) 通用手册的引用与对 `docs/enterprise.md` 输出样例的判读，**具体行为需对照实际版本核验**，可定位的资料路径是 `docs/buildrun.md`、`docs/enterprise.md` 以及它们指向的 wireguard-tools 仓库与 `wg.8` 手册。凡本仓库源码里查不到的字段与措辞，本篇一律不写死。

在本仓库能确证的事实有四项。其一，`docs/enterprise.md` 给出了 `wg show myconfname` 的完整输出样例，含 interface、public key、private key、listening port、peer、endpoint、allowed ips、latest handshake、transfer 等行，本篇第 4 节据此逐行判读。其二，同一文档明确「隧道服务可在运行时用标准 `wg(8)` 命令行工具查询与修改」，并说明调用遵循其他平台上的惯用模式。其三，交互对象是正在运行的隧道服务实例，Windows 侧服务名为 `WireGuardTunnel$<name>`（见 `docs/enterprise.md`、`manager/install.go`），`wg show` 的参数用的是隧道名（样例里是 `myconfname`），而不是 Linux 意义上的内核网络接口名。其四，权限有硬要求：`docs/enterprise.md` 规定，若配置文件是 `.conf.dpapi`，则需要 Local System 或 Administrator 权限才能用 `wg(8)` 交互；若是普通 `.conf`，则需要 Local System、Administrator，或与 `.conf` 文件所有者相同的权限。这四点构成 Windows 上使用 `wg(8)` 的基本盘。

同样必须写清能力边界。`wg(8)` 不是 `wg-quick(8)`：它不负责把配置文件「起」成接口，也不执行 `iptables` 规则、不展开 `%i` 占位符、不调用 `resolvconf`、不提供 `SaveConfig` 式的运行时回写。Windows 客户端把 `[Interface]` 的 `DNS` 作为接口配置下发（见 04-02、原理见 06-08），把 `[Peer]` 的 `AllowedIPs` 汇总为接口路由（见 04-03、原理见 06-06），全流量封锁用 WFP 规则（原理见 06-09）。运行时用 `wg set` 改的是内存中的驱动状态，本仓库 `conf/config.go` 的 `Interface` 与 `Peer` 都没有 `SaveConfig` 成员，`conf/parser.go` 也没有对应 `case`，配置文件与 DPAPI 密文不会因为 `wg set` 而改变（存储链路见 03-04、原理见 06-03）。换言之，运行时修改是临时的，重启隧道服务后以配置文件为准。

本篇不展开驱动 IOCTL 载荷、UAPI 交互通道与状态回查的实现，统一收敛到交叉引用：`字段见 05-02 ｜ 原理见 06-05 ｜ 模块见 07-03`。更细的密钥、端点、时间与流量类型见 05-03，驱动配置结构见 05-05，运行时状态回查见 06-05，路由下发联动见 06-06，隧道服务模块见 07-05，驱动适配模块见 07-03。本篇只回答「有哪些子命令、各自做什么、需要什么权限、输出怎么读、改了会不会持久」。

| `pubkey` | 密钥生成 | 从标准输入读私钥并派生公钥 | 否 | 无，纯本地 | 否 |
| `genpsk` | 密钥生成 | 生成一段 Base64 预共享密钥 | 否 | 无，纯本地 | 否 |

表中「写回 .conf」一列全部为否，这不是逐个子命令的偶然结果，而是 Windows 客户端架构决定的：配置的权威副本在 `%ProgramFiles%\WireGuard\Data\Configurations\` 下的 `.conf` 或 `.conf.dpapi` 文件里，由 manager 服务与 tunnel 服务读取；`wg(8)` 作用于已经跑起来的实例，不参与该目录的写入。所以「用 `wg set` 改了端点，重启后又变回去」是预期行为，不是 bug；要让改动持久，应修改配置文件并重启隧道服务（或用 UI 编辑配置，见 03-01、04-08）。九个命令的具体参数形式、字段选择器名称与输出措辞，均需对照 wireguard-tools 实际版本核验，路径见 `docs/buildrun.md` 指向的外部仓库与 `wg.8` 手册。

`wg show` 的输出字段与本仓库结构体的对应关系见下表，左侧取自 `docs/enterprise.md` 的输出样例，右侧取自 `conf/config.go` 与 `conf/parser.go`。这张表是「只读运行时状态」与「可写配置键」之间的桥梁。

| 输出行（docs/enterprise.md） | 数据来源 | 能否写进 .conf |
|---|---|---|
| `interface: myconfname` | 隧道名，对应服务名后缀 | 由文件名决定，非配置键 |
| `public key`（接口段） | `PrivateKey` 经 X25519 派生 | 否，派生结果 |
| `private key: (hidden)` | `[Interface]` 的 `PrivateKey` | 能，但查询时被隐藏 |
| `listening port` | `[Interface]` 的 `ListenPort` | 能 |
| `peer: 公钥值` | `[Peer]` 的 `PublicKey` | 能 |
| `endpoint` | `[Peer]` 的 `Endpoint` | 能 |
| `allowed ips` | `[Peer]` 的 `AllowedIPs` | 能 |
| `latest handshake` | `Peer.LastHandshakeTime` | 否，只读统计 |
| `transfer` | `Peer.RxBytes` 与 `Peer.TxBytes` | 否，只读统计 |

`latest handshake` 与 `transfer` 两行对应 `conf/config.go` 中 `Peer` 的三个运行时统计成员，它们由 `conf/parser.go` 的 `FromDriverConfiguration` 从驱动读回后填充，`conf/writer.go` 的 `ToWgQuick` 不会写出（见 04-03 第 3.7 节、字段见 05-03）。展示格式由 `conf/config.go` 的 `HandshakeTime.String()` 与 `Bytes.String()` 决定：前者输出类似 `3 seconds ago` 的相对时间字串或「Now」，时钟回拨时输出告警串；后者按 1024 进制输出 B / KiB / MiB / GiB / TiB 并保留两位小数。样例里的 `3 seconds ago`、`6.55 KiB received, 4.13 KiB sent` 正是这两种格式化的结果。

权限矩阵见下表，完全依据 `docs/enterprise.md` 的表述整理。

| 配置存储形态 | 允许使用 `wg(8)` 的身份 | 依据 |
|---|---|---|
| `.conf.dpapi` 加密配置 | Local System 或 Administrator | `docs/enterprise.md` |
| 普通 `.conf` 明文配置 | Local System、Administrator，或与文件所有者相同权限 | `docs/enterprise.md` |
| `genkey` / `pubkey` / `genpsk` | 任意用户，纯本地计算，不接触实例 | 子命令性质，需对照实际版本核验 |
| 未启动的隧道 | 查询与修改均无法定位实例 | 实例由 tunnel 服务创建 |

三点补充。第一，`.conf.dpapi` 是 manager 服务用 `CryptProtectData(bytes, "myconfname")` 加密后的文件，只有 Local System 能解，因此权限要求更严（见 03-04、原理见 06-03）。第二，「与文件所有者相同权限」是普通 `.conf` 场景下的放宽路径，企业批量投放明文配置时尤为相关（见 03-05）。第三，权限不足时不会得到半份输出，通常表现为打不开实例或直接报错；具体报错文本需对照实际版本核验，排查顺序见第 7 节。

### 3. 逐项详解

#### 3.1 `show`

`show` 是最常用的运行时查询子命令，用于查看接口与每个 peer 的当前状态。`docs/enterprise.md` 的样例写法是 `wg show myconfname`，其中 `myconfname` 是隧道名，对应服务名 `WireGuardTunnel$myconfname`。按 wg(8) 通用手册，`show` 还可只取某一类字段（如公钥、监听端口、端点、允许 IP、最近握手、流量、保活间隔等），字段名与是否支持 `dump` 之类的机器可读输出需对照 wireguard-tools 实际版本核验，路径见 `docs/buildrun.md` 指向的 `wg.8` 手册。在 Windows 上，能查到实例的先决条件是该隧道服务已启动、适配器已由驱动创建（原理见 06-05）。

判读时要把「配置里写了什么」与「运行时实际是什么」分开：`endpoint` 行显示的是协商出的实际对端地址，可能与静态配置里的域名不同；`allowed ips` 行是驱动侧当前生效的允许 IP 列表；`listening port` 行在未配置 `ListenPort` 时是系统随机选取的端口，每次启动都可能变化。这些行都来自运行实例，不是对 `.conf` 文本的直接回显。完整逐行判读见第 4 节。

#### 3.2 `showconf`

`showconf` 以配置文件的格式输出当前运行配置，相当于把实例状态反序列成一份可阅读的 `[Interface]` / `[Peer]` 文本。它与 `show` 的区别是：`show` 给的是「状态视图」，含握手时间、流量等运行时统计；`showconf` 给的是「配置视图」，主体是可写配置键。就本仓库而言，`conf/writer.go` 的 `ToWgQuick` 正是这类文本的格式基准：每个 `[Peer]` 段恒定输出 `PublicKey`，仅在非零 / 非空时输出 `PresharedKey`、`AllowedIPs`、`Endpoint`、`PersistentKeepalive`，运行时统计字段一律不输出。因此 `showconf` 的输出里不会出现 `latest handshake`、`transfer` 之类的行。字段选择范围与具体序列化措辞需对照实际版本核验，可定位源码路径为 `conf/writer.go` 的 `ToWgQuick`。

实践中常把 `wg showconf <name>` 的输出重定向成文件作为备份，但要注意：它反映的是「当前运行态」，若此前用 `wg set` 做过临时修改，这份输出会包含那些临时值，却不会写回管理器的配置存储。把它当作配置备份时，应先确认没有未落盘的运行时改动。

#### 3.3 `set`

`set` 按参数增量修改运行中的接口或某个 peer，是「运行时修改」这一类的代表。按 wg(8) 通用手册，常见参数包括改监听端口、改私钥、按公钥定位 peer 后改端点 / 保活间隔 / 允许 IP / 预共享密钥，以及移除某个 peer 等；具体参数名与文件传参方式需对照 wireguard-tools 实际版本核验，路径见 `docs/buildrun.md` 指向的 `wg.8` 手册。在 Windows 语境下有三点必须记住。

第一，`set` 的第一个参数是隧道名，不是接口索引，也不是服务全名 `WireGuardTunnel$myconfname`。第二，它改的是运行实例的状态，权限受第 2 节矩阵约束；若目标配置是 `.conf.dpapi`，普通用户执行会失败。第三，也是最容易踩坑的一点：改动不落盘。本仓库没有 `SaveConfig` 键，`conf/config.go` 无对应成员，`conf/parser.go` 无对应 `case`，`wg set` 不会改写 `%ProgramFiles%\WireGuard\Data\Configurations\` 里的文件；隧道服务重启后，配置重新从文件载入，临时改动随之消失。这与 Linux `wg-quick` 的 `SaveConfig = true` 语义完全不同，把后者当成 Windows 能力会导致「改了没生效」的误判。若 `set` 涉及 `AllowedIPs` 等会影响路由的字段，Windows 侧的路由联动属于运行时机制，原理见 06-06，具体联动行为需对照实际版本核验。

#### 3.4 `setconf`、`addconf` 与 `syncconf`

这三个子命令都以配置文件为输入，作用于运行实例，常被放在一起比较。按 wg(8) 通用手册的语义：`setconf` 从文件整体替换运行时配置（原有 peer 若不在新文件里会被清掉）；`addconf` 在现有配置基础上追加文件中的内容；`syncconf` 按文件同步配置，但尽量保留现有 peer 的握手与流量等运行时状态，因此在「只改一两项又不想打断已建立会话」的场景更常用。三者的精确差异、对已有 peer 的处理顺序、以及是否接受标准输入，需对照 wireguard-tools 实际版本核验，路径同为 `docs/buildrun.md` 指向的 `wg.8` 手册。

把它们放到 Windows 客户端里看，还有两层约束。其一，文件格式是 wg-quick 风格的 INI 文本，但本仓库 `conf/parser.go` 的 `FromWgQuick` 只认白名单内的键（见 04-01 至 04-03），把含 `iptables` 规则的 `PostUp` 行、`SaveConfig`、`%i` 之类写进去不会被当作扩展能力执行，反而可能报错（脚本键的执行条件见 04-07）。其二，这三个命令同样不写回管理器配置存储，`docs/enterprise.md` 所说的「可在运行时查询与修改」指的是实例状态，不是配置文件持久化。要让改动在重启后仍在，必须回到 `.conf` / `.conf.dpapi` 文件本身（见 03-04、03-06）。这一点与 04-04 里 `/installtunnelservice CONFIG_PATH` 的「以文件为准」正好互相印证：文件是权威副本，`wg(8)` 只是运行态入口。

#### 3.5 `genkey`、`pubkey` 与 `genpsk`

这三个是纯本地的密钥工具，不需要运行实例、不需要管理员权限，也不接触隧道服务。`genkey` 生成一段 Base64 私钥；`pubkey` 从标准输入读私钥、派生并输出对应公钥；`genpsk` 生成一段 Base64 预共享密钥。三者输出都是解码后恰为 32 字节的密钥，正好对应 `conf/config.go` 里的 `Key` 类型与 `KeyLength = 32`，也对应 `conf/parser.go` 的 `parseKeyBase64` 校验（见 04-03）。因此它们是编写 `.conf` 时生成 `PrivateKey`、`PublicKey`、`PresharedKey` 取值的标准来源。

本仓库 `conf/config.go` 里能看到同类的本地方法作为佐证：`NewPrivateKey` 先取随机 32 字节再做 X25519 的钳位（`k[0] &= 248`、`k[31] = (k[31] & 127) | 64`），`Key.Public()` 用 `ecdh.X25519().NewPrivateKey` 派生公钥，`NewPresharedKey` 直接取 32 字节随机数。也就是说，`wg genkey` / `wg pubkey` 产出的值与 UI「生成密钥对」按钮背后的运算是同一类，只是入口不同（字段见 05-03）。命令行里常用管道把两者串起来生成密钥对，示例见第 4 节；注意管道符属于 shell 语法，写在表格单元格里必须转义为 `\|`，代码块里则按原样书写。

#### 3.6 隧道名与实例定位

Windows 上 `wg(8)` 的第一个关键参数是「要连到哪个实例」。`docs/enterprise.md` 用 `wg show myconfname` 演示，其中名字来自配置文件名：`/installtunnelservice C:\path\to\some\myconfname.conf` 安装出的服务是 `WireGuardTunnel$myconfname`。因此排查「`wg show` 查不到东西」时，第一步是确认隧道名拼写与已安装服务列表一致（服务查询命令见 04-06），第二步是确认该隧道服务确实处于运行状态。Linux 上常见的 `wg show wg0` 用的是内核接口名，Windows 客户端在启动隧道时动态创建适配器、停止时销毁（见 `docs/netquirk.md`、`docs/enterprise.md` 的 Driver Removal 一节），并不存在一个长期叫 `wg0` 的固定接口，把 Linux 习惯照搬会找不到实例。示例输出里 `interface: myconfname` 这一行正是这个隧道名的回显。

#### 3.7 权限模型

第 2 节的权限矩阵需要在调用链上再落实一遍。`docs/enterprise.md` 的原话是：隧道服务可在运行时用标准 `wg(8)` 工具查询和修改；若配置文件是 `.conf.dpapi`，则用 `wg(8)` 交互需要 Local System 或 Administrator 权限；否则用户需要 Local System、Administrator，或与 `.conf` 文件所有者相同的权限。这解释了两个常见现象：其一，在普通用户会话里对 UI 导入的配置执行 `wg show` 常常报权限错误，因为那份配置已被 manager 服务转成 `.conf.dpapi`（见 03-04）；其二，企业场景里直接把明文 `.conf` 投放到配置目录、且投放账户与查询账户相同，权限路径会宽松一些（见 03-05）。

`genkey` / `pubkey` / `genpsk` 是例外：它们不接触实例，因此不受上述矩阵约束。另需注意，权限检查与 04-04 里 `wireguard.exe` 的 `checkForAdminGroup` 是两回事：后者约束的是主程序的 `/` 开关，前者约束的是 `wg.exe` 与隧道服务实例的交互，二者由不同进程、不同文档分别规定（受限 UI 策略见 04-07）。

### 4. 典型示例

第一组是 `docs/enterprise.md` 给出的 `wg show` 输出样例，原样引用。示例输出，具体格式需对照实际版本核验。

```text
> wg show myconfname
interface: myconfname
  public key: lfTRXEWxt8mZc8cjSvOWN3tqnTpWw4v2Eg3qF6WTklw=
  private key: (hidden)
  listening port: 53488

peer: JRI8Xc0zKP9kXk8qP84NdUQA04h6DLfFbwJn4g+/PFs=
  endpoint: 163.172.161.0:12912
  allowed ips: 0.0.0.0/0
  latest handshake: 3 seconds ago
  transfer: 6.55 KiB received, 4.13 KiB sent
```

逐行判读（本篇侧重运行时语义，与 04-03 第 4 节侧重配置键的角度互补）。第一行 `interface: myconfname` 回显隧道名，它同时是服务名 `WireGuardTunnel$myconfname` 的后缀，据此可确认查到的是哪一条隧道，写错名字会在这一步就查不到实例。第二行 `public key` 是本地公钥，由 `[Interface]` 的私钥派生，属于只读派生结果，不能写进配置；第三行 `private key: (hidden)` 说明查询工具主动隐藏私钥，属正常保护，若某版本把它打印成 Base64 明文，应核查工具版本与调用权限。第四行 `listening port: 53488` 是本次启动实际占用的 UDP 端口，未配置 `ListenPort` 时由系统选择，重启后可能变化，因此脚本不应硬编码该值。空行之后是 peer 段：第五行的公钥应与该 `[Peer]` 段的 `PublicKey` 一致，是定位与比对配置的锚点；第六行 `endpoint` 显示协商出的实际对端地址端口，配置里若写的是域名，这里通常已是解析后的地址，显示为空则说明对端尚未连入；第七行 `allowed ips: 0.0.0.0/0` 表示驱动侧当前生效的允许 IP 为 IPv4 全流量，按 06-09 的判定会触发 WFP kill-switch，需额外确认 DNS 与本地网段放行。第八行 `latest handshake: 3 seconds ago` 与第九行 `transfer: 6.55 KiB received, 4.13 KiB sent` 是纯运行时统计，对应 `Peer.LastHandshakeTime`、`RxBytes`、`TxBytes`，由 `FromDriverConfiguration` 从驱动读回，任何 `wg(8)` 修改命令都不会把它们写回 `.conf`。判读链路活性的要点是：握手时间长期不更新指向端点不可达、公钥或预共享密钥两端不一致；received 增长而 sent 不动多与本地路由或 AllowedIPs 方向有关；两个方向都不动则优先怀疑握手未建立。这九行里只有 `private key`、`listening port`、`peer`、`endpoint`、`allowed ips` 对应的值能在配置文件里找到源头，其余都是运行态信息。

第二组给出密钥生成与运行时修改的常用命令序列，命令形式见下方示例。

```text
> wg genkey > private.key
> wg pubkey < private.key
> wg genpsk > preshared.key
> wg set myconfname peer JRI8Xc0zKP9kXk8qP84NdUQA04h6DLfFbwJn4g+/PFs= endpoint 163.172.161.0:12912
> wg show myconfname endpoints
> wg showconf myconfname > running.conf
```

这组命令覆盖三类动作。前三行是离线密钥生成：`wg genkey` 把私钥写入 `private.key`，`wg pubkey` 从标准输入读回并输出公钥用于填 `[Peer]` 的 `PublicKey`，`wg genpsk` 产出预共享密钥用于填 `PresharedKey`；三者都不需要隧道在跑，也不需要管理员权限。第四行是运行时修改：按公钥定位 peer 并改端点，`set` 的具体参数名与是否支持文件传参需对照 wireguard-tools 实际版本核验（`docs/buildrun.md` 指向 `wg.8` 手册）；改动只作用于内存中的运行态，重启隧道服务即失效，因为没有 `SaveConfig` 能力。第五行按字段选择器只看端点，字段名需对照实际版本核验。第六行把当前运行配置导出到 `running.conf`，输出格式以 `conf/writer.go` 的 `ToWgQuick` 为参照，不会包含握手时间与流量等运行时统计行。

第三组给出 `showconf` 输出的示意，格式依据 `conf/writer.go` 的 `ToWgQuick` 写出条件推演；示例输出，具体格式需对照实际版本核验。

```text
> wg showconf myconfname
[Interface]
PrivateKey = yAnz5TF+lXXJte14tfi3MtAFlb1qppTVR0kH4bqvkUwqU=
ListenPort = 53488
Address = 10.2.0.2/32

[Peer]
PublicKey = JRI8Xc0zKP9kXk8qP84NdUQA04h6DLfFbwJn4g+/PFs=
AllowedIPs = 0.0.0.0/0
Endpoint = 163.172.161.0:12912
PersistentKeepalive = 25
```

判读要点如下。`[Interface]` 与 `[Peer]` 两段结构对应 `conf/config.go` 的 `Config`，`PrivateKey`、`ListenPort`、`Address` 与 `PublicKey`、`AllowedIPs`、`Endpoint`、`PersistentKeepalive` 都是可写配置键（见 04-02、04-03）。输出中没有 `PresharedKey` 行说明该值全零或该版本未导出，没有 `Table` 行说明 `TableOff` 为假，没有任何握手与流量行则印证了「运行时统计不属于配置文本」。若此前用 `wg set` 临时改过端点，这份输出里的 `Endpoint` 会是改后的值，但磁盘上的 `.conf` 或 `.conf.dpapi` 仍是旧值——这正是 `showconf` 与「配置文件」之间最容易混淆的地方。把它当备份使用前，应先用 UI 或文件比对确认没有未落盘的改动。

### 5. 速查表

下表按意图把九个子命令收敛成速查项，参数细节回到第 3 节。

| 意图 | 子命令 | 关键前提 |
|---|---|---|
| 查看隧道整体状态 | `show <隧道名>` | 隧道服务已启动 |
| 只看某类字段 | `show <隧道名> <字段>` | 字段名需对照实际版本核验 |
| 导出当前运行配置 | `showconf <隧道名>` | 注意可能含临时改动 |
| 临时改端点或保活 | `set` 指定 peer 与新端点 | 不落盘，重启失效 |
| 按文件整体替换 | `setconf <隧道名> <文件>` | 文件用白名单内的键 |
| 按文件追加 | `addconf <隧道名> <文件>` | 不覆盖既有 peer |
| 按文件同步 | `syncconf <隧道名> <文件>` | 尽量保留运行时状态 |
| 生成私钥 | `genkey` | 纯本地，无权限要求 |
| 派生公钥 | `pubkey` | 从标准输入读私钥 |
| 生成预共享密钥 | `genpsk` | 纯本地，无权限要求 |
| 一行生成密钥对 | `wg genkey \| wg pubkey` | 单元格内管道已转义 |

下表把 `show` 输出行与判读结论对应起来，供排障时快速定位。

| 输出现象 | 优先怀疑 | 关联章节 |
|---|---|---|
| 查不到实例 | 隧道名写错或服务未启动 | 04-04、04-06 |
| 提示权限不足 | `.conf.dpapi` 需 LocalSystem 或 Administrator | 本篇第 3.7 节 |
| `endpoint` 为空 | 对端尚未连入或端点未解析 | 04-03、06-02 |
| `latest handshake` 长期不动 | 端点不可达或密钥两端不一致 | 04-03、08-04 |
| `transfer` 只有单向增长 | 本地路由或 AllowedIPs 方向 | 04-03、06-06 |
| `listening port` 每次变化 | 未配置 `ListenPort`，系统随机选取 | 04-02 |
| `wg set` 后重启失效 | 运行时修改不落盘，无 `SaveConfig` | 本篇第 3.3 节 |

两张表合起来给出一条主线：`show` 与 `showconf` 负责「看见」，`set` 及三个文件型命令负责「临时改变」，`genkey` 家族负责「备料」。任何需要「永久生效」的改动都要回到配置文件与隧道服务生命周期，而不是反复执行 `wg set`。

### 6. 版本差异

本篇的版本基准是上游仓库 master 快照（2026-11 抓取）、WireGuardNT 1.1、Go 1.27.1、Windows 10 / Server 2019 及以上。但必须强调：`wg.exe` 的版本由 wireguard-tools 决定，不由 wireguard-windows 的 `version/version.go` 决定。`docs/buildrun.md` 说明 Windows 侧 `build.bat` 会构建 `wg.exe`，Linux 侧用 `PLATFORM=windows make -C wireguard-tools/src` 交叉编译，产物路径为 `wireguard-tools/src/wg.exe`；这两条命令的具体 flags、依赖版本与产物名需对照实际版本核验，路径为 `docs/buildrun.md` 与 `Makefile`。

以下项目一律写「需对照实际版本核验」并给出可定位路径。其一，九个子命令的全集与各自参数：本仓库 `upstream_src/` 内没有 wg 源码，可定位资料是 `docs/buildrun.md` 指向的 wireguard-tools 仓库与 `wg.8` 手册；`docs/enterprise.md` 只明确「遵循其他平台上的惯用模式」并给出 `wg show` 一例。其二，`show` 的字段选择器名称、`dump` 之类的输出形式、`setconf` / `addconf` / `syncconf` 对已有 peer 的精确处理顺序，同样以 `wg.8` 手册为准，需对照实际版本核验。其三，`wg show` 输出行的措辞、单位与本地化：`docs/enterprise.md` 给出的是英文样例，`conf/config.go` 的 `Bytes.String()` 与 `HandshakeTime.String()` 决定了 UI 侧同类数值的格式化，两者是否完全一致需对照实际版本核验。其四，权限矩阵：`docs/enterprise.md` 对 `.conf.dpapi` 与普通 `.conf` 的规定是本快照的表述，具体 ACL 与身份判定见 `docs/attacksurface.md` 与 `conf/dpapi/`，需对照实际版本核验。其五，`wg(8)` 与运行实例之间的具体交互通道、以及修改 `AllowedIPs` 后 Windows 路由的联动时机，本仓库可见的相邻机制在 `conf/writer.go` 的 `ToDriverConfiguration` 与 `conf/parser.go` 的 `FromDriverConfiguration`（原理见 06-05、06-06），但交互细节属外部项目，需对照实际版本核验。其六，具体版本号、驱动版本、MSI 文件名与下载 URL 等时效性数值，按总纲第 9 节约定处理，不在本篇写死。

### 7. 常见误用与调试

误用一：把 `wg(8)` 当 `wg-quick(8)`，或把 Linux 语义带进来。有人期望 `wg` 能「起」一条隧道，或在配置里写含 `iptables` 规则的 `PostUp` 行、`%i`、`resolvconf`、`SaveConfig = true`。本仓库是 Windows 客户端：接口由 tunnel 服务启动时动态创建（见 `docs/enterprise.md` 的 Driver Removal 一节），封锁用 WFP 而非 `iptables`，脚本键用 `WIREGUARD_TUNNEL_NAME` 环境变量且默认不执行（见 04-07），DNS 作为接口配置下发（原理见 06-08），`conf/config.go` 无 `SaveConfig` 成员。把 `wg(8)` 当 `wg-quick` 会既起不了隧道，也得不到期望的持久化效果。

误用二：混淆三类命令。把 `wg show` 写成 `wireguard.exe show`、把 `wireguard /installtunnelservice` 写成 `wg setconf`、或把服务查询写成 `wg show WireGuardTunnel$name`，都是把 04-04、04-05、04-06 三块内容串了线。`wireguard.exe` 的 `/` 开关管进程与服务生命周期，`wg.exe` 的子命令管运行态，`sc` / PowerShell 管 Windows 服务与任务，各管一段。

误用三：用错实例名。`wg show wg0` 是 Linux 习惯，Windows 侧应传隧道名（样例为 `myconfname`），该名字来自配置文件名并构成服务名 `WireGuardTunnel$myconfname`。查不到实例时先列服务、再核拼写，而不是反复改配置。

误用四：忽略权限。对 UI 导入后已被转成 `.conf.dpapi` 的配置，普通用户执行 `wg show` 会因权限不足失败；按 `docs/enterprise.md`，这需要 Local System 或 Administrator。排查时应确认配置文件形态（明文 `.conf` 还是加密 `.conf.dpapi`）、调用账户，以及是否为提权会话。受限 UI 策略（见 04-07）只影响 UI，不会放宽 `wg(8)` 的这些要求。

误用五：把运行时修改当持久化。`wg set` 改端点、`syncconf` 同步配置，改的都是内存中的运行态；重启隧道服务后以配置文件为准。若发现「改了又变回去」，不要反复执行 `wg set`，而应修改 `.conf` / `.conf.dpapi` 并重启服务，或用 UI 编辑配置（见 03-01、04-08）。用 `showconf` 导出的文本也可能包含这些临时值，作为备份前要核对磁盘上的权威副本。

误用六：把运行时统计当可写字段。看到 `latest handshake` 长时间不更新就试图在配置里改 `LastHandshakeTime`，或往 `.conf` 里加 `transfer` 行，只会得到「段内无效键」错误。这三者由 `FromDriverConfiguration` 从驱动读回，只能通过排查链路来间接改变。

调试顺序建议固定为五步。第一步，确认隧道服务已启动、适配器已创建，服务名与隧道名对应（命令见 04-06）。第二步，确认调用账户满足 `docs/enterprise.md` 的权限矩阵，必要时用提权会话重跑。第三步，执行 `wg show <隧道名>`，按第 4 节逐行判读 `endpoint`、`latest handshake`、`transfer` 三行，区分「握手未建立」与「握手已建立但业务不通」。第四步，若怀疑有临时改动，用 `wg showconf <隧道名>` 导出运行配置，与磁盘上的 `.conf` / `.conf.dpapi` 比对。第五步，用 `wireguard /dumplog` 与 `wireguard /dumplog /tail` 读取共享环形日志（见 04-04、08-01），结合 UI 的配置编辑器确认静态配置本身合法。整条链路里，`wg(8)` 负责「看见运行态」，静态正确性仍要回到 04-01 至 04-03 的配置键与 `conf/parser.go` 的解析规则。

## 04-06 服务管理、PowerShell 与诊断命令全集

### 1. 本篇定位与覆盖范围

本篇是 04「配置与命令行」册的第六篇，采用 B 手册字典型骨架，主题是服务管理、PowerShell 与诊断命令全集。大纲为它列出九类命令：`sc`、`Get-Service`、`netsh`、`Get-NetAdapter`、`Get-NetRoute`、`pnputil`、`wevtutil`、`reg`、`schtasks`。把这九类放在一起，是因为它们共同回答同一个运维问题：当 wireguard-windows 已经被安装到一台 Windows 主机上之后，管理员如何不依赖图形界面，纯靠命令行与脚本去观测、控制、核验和采集这套软件留下的服务对象、网络对象、驱动对象与日志对象。它们不是配置键，也不是 `wireguard.exe` 的进程开关，而是「站在操作系统一侧、面向本仓库产物」的管理工具，因此本篇的定位是运维侧的命令字典，而不是配置语法或程序入口的复述。

必须先划清本篇与同册前几篇的分工，否则命令清单会被重复抄写。`wireguard.exe` 自身那组以斜杠开头的进程开关——无参数、`/installmanagerservice`、`/installtunnelservice CONFIG_PATH`、`/uninstallmanagerservice`、`/uninstalltunnelservice TUNNEL_NAME`、`/managerservice`、`/tunnelservice CONFIG_PATH`、`/ui` 四个句柄、`/dumplog [/tail]`、`/update`、`/removedriver`——是 04-04 的唯一权威源，本篇不重列；`wg(8)` 的 `show`、`showconf`、`set`、`setconf`、`addconf`、`syncconf`、`genkey`、`pubkey`、`genpsk` 九个子命令是 04-05 的唯一权威源，本篇同样不重列；两个 `HKLM\Software\WireGuard` 注册表键的取值、语义与安全代价是 04-07 的唯一权威源，本篇只把 `reg` 当作「读写键的通道」点到为止。本篇的独立价值在于：把 Windows 平台自带的系统管理工具，与上述几组本仓库能力所产出的具体对象一一对应起来，给出「查哪个服务、看哪块适配器、读哪份日志、用哪个计划任务账户」的完整操作面。凡涉及某个开关或子命令本身的完整语义，一律回指 04-04 或 04-05。

第二条边界是「这些命令是谁写的」。`sc`、`netsh`、`pnputil`、`wevtutil`、`reg`、`schtasks` 以及 `Get-Service`、`Get-NetAdapter`、`Get-NetRoute` 等 PowerShell cmdlet，全部是 Windows 操作系统自带的管理工具，不是本仓库的产物；`upstream_src/` 这份快照里既没有它们的实现，也没有为它们封装的 Go 包。因此本篇给出的参数与输出属于「面向 WireGuard 对象的调用惯例」，命令自身的完整开关、字段名称与输出措辞属于微软 Windows 文档范畴，具体格式需对照实际版本核验，可定位的本仓库依据是 `docs/enterprise.md` 与 `docs/adminregistry.md` 两份官方说明，以及 `main.go`、`conf/name.go`、`services/errors.go` 三处源码。凡是本仓库源码与官方文档里查不到的措辞，本篇一律不写死，也不把 Linux 平台上 `systemctl`、`ip route` 之类的习惯硬套到 Windows 上。

第三条边界是「本仓库确凿产出了什么对象」，这是所有命令的作用目标。`docs/enterprise.md` 与 `manager/install.go` 明确：管理服务只有一个，名为 `WireGuardManager`；每安装一条隧道就多一个独立服务，名为 `WireGuardTunnel$<name>`；`conf/name.go` 的 `ServiceNameOfTunnel` 函数把合法隧道名拼成 `"WireGuardTunnel$" + tunnelName`，正好与文档互证。`docs/enterprise.md` 又明确这两类服务可用标准 Windows 服务管理工具控制，例如 `services.msc` 或 `sc`，这是本篇把 `sc` 与 `Get-Service` 列为首选命令的直接依据。此外，`docs/enterprise.md` 的 Diagnostic Logs 一节给出 `wireguard /dumplog` 重定向与 `/tail` 管道到日志采集服务、以及 PowerShell 里 `wireguard /dumplog /tail | select` 的写法；Updates 一节给出用 `schtasks` 每日凌晨三点触发 `/update` 的示例；Driver Removal 一节给出 `wireguard /removedriver`。这几处是官方文档直接点名 Windows 运维命令的地方，本篇据实引用，不额外发明本仓库不存在的管理面。

能力边界同样要写清：本仓库是 Windows 官方客户端，内核数据面由外部项目 WireGuardNT 提供，本仓库只负责 IOCTL 配置下发、适配器与网络配置；不要把 Linux `wg-quick` 的 `iptables`、`%i`、`SaveConfig`、`resolvconf` 语义写成 Windows 客户端能力，也不要把 `wireguard-go` 的用户态数据面写进本篇（配置键全集见 04-01 至 04-03，脚本键执行条件见 04-07）。本篇不展开 Manager 服务的 WTS 会话枚举、令牌降权、IPC 句柄继承等内部机制，统一收敛到交叉引用：`字段见 05-09 ｜ 原理见 06-10 ｜ 模块见 07-08`。服务错误码枚举见 05-09，进程入口与日志句柄初始化见 06-01 与 06-11，隧道服务启动顺序见 06-05，服务与错误码模块见 07-10。本篇只回答「有哪些系统命令、各自查什么、怎么读输出、哪些坑会导致查错对象」。

### 3. 逐项详解

#### 3.1 `sc`：服务状态与配置的第一入口

`docs/enterprise.md` 明确点名 `sc` 可控制 `WireGuardManager` 与每条隧道服务。`sc query <服务名>` 返回服务名、类型、当前状态、Win32 退出码、服务退出码、检查点与等待提示；`sc qc <服务名>` 返回启动类型、二进制路径、依赖与运行账户，是核验「这条隧道服务到底指向哪个配置文件」的关键，其 `BINARY_PATH_NAME` 应呈现 04-04 里 `/tunnelservice CONFIG_PATH` 的形态；`sc start`、`sc stop` 触发启停，`sc config` 改启动类型，`sc delete` 删除服务。要点有三：服务名必须是 `WireGuardManager` 或完整的 `WireGuardTunnel$<隧道名>`，其中 `$` 在部分 shell 里需要转义或用引号包裹；把裸隧道名当服务名是本篇第 7 节要讲的头号误用；`WIN32_EXIT_CODE` 是服务控制管理器记录的退出码，与 `services/errors.go` 里 `DetermineErrorCode` 由服务进程自己报告的码属于两条不同来源，判读时不要混为一谈（错误码枚举见 05-09）。

#### 3.2 `Get-Service` 与 PowerShell 服务族

`Get-Service -Name WireGuardManager` 以对象形式返回 `Status`、`StartType`、`Name` 等属性，`Start-Service`、`Stop-Service`、`Set-Service -StartupType Automatic` 完成对应动作，配合 `Where-Object` 可批量筛选正在运行的服务。相比 `sc`，cmdlet 的输出可直接进管道、可序列化为 JSON、可被脚本消费，适合企业批量运维与巡检报表。一个 Windows 特有的坑是：`$` 在 PowerShell 里是变量引导符，`WireGuardTunnel$mytunnel` 若不加单引号会被展开成只剩前缀，导致查不到服务；稳妥写法是 `Get-Service -Name 'WireGuardTunnel$mytunnel'`。各 cmdlet 的具体参数名与 `Start-Service` 的等待行为需对照实际 PowerShell 版本核验，本仓库不定义这些行为。

#### 3.3 `netsh` 与 `Get-NetAdapter`、`Get-NetRoute`、`Get-NetIPConfiguration`

`netsh` 是传统网络配置入口，`netsh interface ipv4 show interfaces`、`show route`、`show addresses` 可看接口、路由与地址，但输出是文本表格、不易脚本化，微软后续用 `Get-Net*` cmdlet 取代其大部分观测用途。`Get-NetAdapter` 列出适配器名、接口索引、状态与链路速度；隧道适配器由 tunnel 服务在启动时动态创建、停止时销毁（见 `docs/netquirk.md` 与 `docs/enterprise.md` 的 Driver Removal 一节），因此只有隧道处于运行状态时才能查到它，停止后查不到是预期行为而非故障。`Get-NetRoute -DestinationPrefix <网段>` 用来核验 `[Peer]` 的 `AllowedIPs` 是否真的落成路由并指向隧道接口索引（配置语义见 04-03、原理见 06-06）；`Get-NetIPConfiguration -InterfaceIndex <索引>` 汇总地址、默认网关与 DNS 服务器，配合 04-02 的 `DNS` 键与 06-08 的下发行为判读是否有 DNS 泄漏或搜索域错配。

#### 3.4 `pnputil`：驱动包核验

WireGuardNT 是内核驱动，`pnputil /enum-drivers` 可列出系统里的第三方驱动包，`/delete-driver` 可清理。但本仓库提供了更安全的正规入口 `wireguard /removedriver`（见 04-04、03-06）：`docs/enterprise.md` 说明「当没有更多网络适配器时，驱动可被移除」，`main.go` 的 `/removedriver` 分支调用 `driver.Uninstall()`，由本仓库自行判断时序与清理范围。直接用 `pnputil` 删驱动包绕过了这套判定，可能留下残留适配器、服务或注册表状态，仅在 `/removedriver` 明确失败后的善后场景才考虑，且应先确认所有隧道服务已停止、适配器已销毁。`pnputil` 的具体子命令拼写与 OEM INF 名称形式需对照实际 Windows 版本核验。

#### 3.5 `wevtutil` 与 `wireguard /dumplog` 的日志双通道

必须区分两套日志。本仓库主用共享环形日志：`docs/enterprise.md` 说 manager 与所有 tunnel 服务把诊断日志写进同一份 ringbuffer 日志，UI 里可见，也能用 `wireguard /dumplog` 导到标准输出，或用 `/dumplog /tail` 持续输出接给日志采集服务，PowerShell 里可写 `wireguard /dumplog /tail | select`。源码侧 `main.go` 的 `/dumplog` 分支先取 `STD_OUTPUT_HANDLE`，取不到就报 `Stdout must be set`，再经 `conf.LogFile(false)` 拿到路径交给 `ringlogger.DumpTo`，第三个参数由 `len(os.Args) == 3 && os.Args[2] == "/tail"` 决定是否持续跟随。`wevtutil qe` 查的是 Windows 事件日志（服务控制管理器记录的服务启停事件等），是辅助证据而非本仓库主日志，二者不要互相替代；ringlogger 的格式见 05-09、共享内存与读取链见 06-11、模块归属见 07-10。日志判读与故障归类见 08-01、08-03。

#### 3.6 `reg`：注册表策略的读写通道

`reg` 在本篇只作为通道出现，键值语义的权威源是 04-07。`docs/adminregistry.md` 给出的官方写法是 `reg add HKLM\Software\WireGuard /v LimitedOperatorUI /t REG_DWORD /d 1 /f`，以及把 `/v` 换成 `DangerousScriptExecution` 的同形命令，核验用 `reg query HKLM\Software\WireGuard`。要点有四：路径在 `HKLM` 下、写入需要管理员权限；类型是 `REG_DWORD` 且值必须为 `1` 才生效；文档明确「没有 UI 来开启这些、将来可能移除、卸载器会清理整个 `HKLM\Software\WireGuard`」；因此 `reg` 是本篇唯一直接改动本仓库行为的命令，操作前应备份键值、操作后应复核生效范围。具体开关拼写需对照 `docs/adminregistry.md` 实际版本核验，两个键的完整影响矩阵见 04-07。

#### 3.7 `schtasks`：定时更新任务

`docs/enterprise.md` 给出可直接引用的示例：`schtasks /create /f /ru SYSTEM /sc daily /tn "WireGuard Update" /tr "%PROGRAMFILES%\WireGuard\wireguard.exe /update" /st 03:00`。逐项拆解：`/f` 覆盖同名任务，`/ru SYSTEM` 让任务以 LocalSystem 运行（与 manager、tunnel 服务同账户，见 `docs/attacksurface.md`），`/sc daily` 与 `/st 03:00` 定每日三点，`/tr` 里因为路径含空格必须整体加引号，末尾 `/update` 是 04-04 的命令行开关，把进度输出到标准错误。配套 `schtasks /query /tn "WireGuard Update" /fo LIST` 与 `schtasks /delete` 做核验与清理；文档还给出 `wireguard /update 2> C:\path\to\update\log.txt` 的日志落盘写法。任务失败的常见原因是 `/tr` 引号缺失、账户权限不足，或 `wireguard.exe` 路径与实际安装架构不符（amd64 / x86 / arm64 三种 MSI，见 02-05）。具体参数需对照实际 Windows 版本核验。

#### 3.8 `services.msc` 与图形入口

`docs/enterprise.md` 把 `services.msc` 与 `sc` 并列为标准服务管理工具。它是图形化的服务控制管理器前端，适合一次性人工核验服务状态、启动类型与登录账户，也适合在排障现场快速看一眼「服务是不是停了」。但它不可脚本化、不产生可采集的结构化文本，因此企业批量运维与自动化巡检仍以 `sc` 与 PowerShell 族为主。本篇把它列全，是为了与官方文档的措辞保持一致，避免读者以为遗漏了图形入口；服务恢复策略的配置与开机自启讨论见 03-03。

#### 3.9 服务名、隧道名与合法字符

`conf/name.go` 是服务名后缀合法性的权威来源，也解释了 `$` 为什么是分隔符。`TunnelNameIsValid` 要求名字匹配正则 `^[a-zA-Z0-9_=+.-]{1,32}$`，即长度 1 到 32、只允许字母、数字与 `_=+.-`；`isReserved` 拒绝 `CON`、`PRN`、`AUX`、`NUL`、`COM1` 至 `COM9`、`LPT1` 至 `LPT9` 这些 Windows 保留设备名；`hasSpecialChars` 拒绝 `$`（源码常量 `serviceNameForbidden`）、`\/:*?"<>|` 与制表符及控制字符，并拒绝以 `.` 开头或结尾的名字。`ServiceNameOfTunnel` 在名字非法时直接返回 `Tunnel name is not valid` 错误，合法时返回 `"WireGuardTunnel$" + tunnelName`。这解释了为什么含空格、中文或 `$` 的配置文件名会被拒，也解释了服务名里 `$` 之后的部分必然不含 `$`。命名规则的完整讨论见 04-01，相关字段见 05-02。

### 4. 典型示例

第一组给出一次完整的服务与网络状态采集。命令形式见下方示例，其中 PowerShell 里带 `$` 的服务名用单引号包裹，避免被当成变量展开。

```powershell
sc query WireGuardManager
sc qc 'WireGuardTunnel$mytunnel'
Get-Service -Name WireGuardManager | Format-List Name, Status, StartType
Get-NetAdapter | Where-Object Status -eq Up | Format-Table Name, InterfaceIndex, Status
Get-NetRoute -DestinationPrefix 10.0.0.0/24 | Format-Table InterfaceIndex, DestinationPrefix, NextHop
```

上面第一行 `sc query` 的典型输出如下。示例输出，具体格式需对照实际版本核验。

```text
> sc query WireGuardManager

SERVICE_NAME: WireGuardManager
        TYPE               : 10  WIN32_OWN_PROCESS
        STATE              : 4  RUNNING
                                (STOPPABLE, NOT_PAUSABLE, ACCEPTS_SHUTDOWN)
        WIN32_EXIT_CODE    : 0  (0x0)
        SERVICE_EXIT_CODE  : 0  (0x0)
        CHECKPOINT         : 0x0
        WAIT_HINT          : 0x0
```

逐行判读如下，读法可直接套用到任意一条隧道服务。首行 `SERVICE_NAME: WireGuardManager` 回显被查询的服务名，用它确认没有把管理服务与隧道服务搞混；若这里出现 `WireGuardTunnel$...` 说明查的是某条隧道。`TYPE : 10 WIN32_OWN_PROCESS` 表示该服务运行在独立进程里，与 docs 所说「manager 服务与 tunnel 服务是分开的 Windows 服务」一致。`STATE : 4 RUNNING` 是核心状态行，数字 4 对应运行中，常见对照是 1 为已停止、2 为正在启动、3 为正在停止、4 为运行中、7 为暂停；当它长期停在 2 或 3，要结合 `CHECKPOINT` 与 `WAIT_HINT` 判断是否卡在启停过渡态。括号内 `STOPPABLE, NOT_PAUSABLE, ACCEPTS_SHUTDOWN` 说明该服务可停止、不可暂停、接受关机通知，这决定 `sc stop` 是否可能成功。`WIN32_EXIT_CODE : 0` 与 `SERVICE_EXIT_CODE : 0` 都为 0 表示上一次退出是干净的；若前者非 0，它是服务控制管理器记录的 Win32 错误码，需与 `services/errors.go` 的 `DetermineErrorCode` 所报告的服务自定义错误码分开看，后者可能是 `Error` 枚举值，也可能是直接透传的 `windows.Errno`（字段见 05-09、原理见 06-01）。`CHECKPOINT : 0x0` 与 `WAIT_HINT : 0x0` 在稳定运行态都应为 0，只有启停进行中才会递增，排障时若发现服务长时间处于非 4 状态且检查点不推进，应转去读环形日志。把同一命令换成 `sc query 'WireGuardTunnel$mytunnel'` 时，状态若为 1（已停止），则 `Get-NetAdapter` 里查不到对应适配器属于预期，因为适配器随隧道启动而创建、随停止而销毁，不应据此误判驱动丢失。

把采集到的四类数据汇合成故障域判读的链路如图 04-06-02 所示，日志层以虚线为另外三层提供佐证。

### 6. 版本差异

第一层差异来自操作系统本身。本篇九类命令绝大多数是 Windows 自带工具，其行为随 Windows 版本与 PowerShell 版本演进：`netsh` 是长期存在的传统入口，`Get-NetAdapter`、`Get-NetRoute`、`Get-NetIPConfiguration` 属于较新的 NetTCPIP PowerShell 模块，在旧版系统或 Server Core 上可能不可用或参数名不同；`sc` 的文本输出格式相对稳定，`Get-Service` 的属性集合则随 PowerShell 版本略有增减；`wevtutil` 的事件通道名称与查询语法、`pnputil` 的子命令拼写、`schtasks` 的参数细节都需对照实际版本核验。本仓库不锁定这些命令的版本，只锁定「要用它们去查哪些对象」。

第二层差异来自本仓库自身的稳定面与易变面。`docs/enterprise.md` 给出的服务名 `WireGuardManager` 与 `WireGuardTunnel$<name>` 是稳定约定，`conf/name.go` 的 `ServiceNameOfTunnel` 用字符串常量拼接予以固化；`wireguard /dumplog`、`/dumplog /tail`、`/update`、`/removedriver` 是 `main.go` 的 `usage()` 里列出的稳定开关（见 04-04），其中 `/dumplog` 依赖 stdout 这一约束来自源码而非文档约定，跨版本保持一致。相对易变的是 `docs/adminregistry.md` 明确声明的两个注册表键「没有 UI、将来可能移除、卸载器会清理整个 `HKLM\Software\WireGuard`」——这意味着依赖 `reg` 写入的策略不具备长期兼容性，升级后必须复核。同理，`docs/enterprise.md` 示例里的 `%PROGRAMFILES%\WireGuard\wireguard.exe` 路径需对照实际安装路径与架构核验，三种 MSI 的安装布局见 02-05。

第三层是随源码快照可能调整的事实：`conf/name.go` 里 `allowedNameFormat` 正则、保留设备名列表、`specialChars` 常量内容属于源码细节，跨版本有微调可能；`services/errors.go` 的 `Error` 枚举项与 `DetermineErrorCode` 的返回值需对照 `upstream_src/services/errors.go` 当前版本核验（字段见 05-09）；`docs/netquirk.md` 关于适配器动态创建、确定性 GUID 的描述是机制性结论，稳定性高于任何具体数值。凡涉及具体版本号、cmdlet 参数名、事件通道名、驱动 INF 名称与下载 URL，本篇统一标注「需对照实际版本核验」，可定位路径为 `docs/enterprise.md`、`docs/adminregistry.md`、`docs/netquirk.md`、`main.go`、`conf/name.go`、`services/errors.go`。

### 7. 常见误用与调试

1. **把裸隧道名当服务名**。`sc query mytunnel` 查不到任何东西，因为服务名是 `WireGuardTunnel$mytunnel`；`WireGuardManager` 则是另一个独立服务。命名与拼接规则见 `conf/name.go` 的 `ServiceNameOfTunnel`（见 3.9 与 04-01）。排障第一步永远是拿 `sc query` 逐个确认服务全名。

2. **把 `wg show` 与 `sc query` 混用**。`wg show <name>` 查的是运行实例里的接口、peer、握手与流量（见 04-05），`sc query` 查的是服务控制管理器里的服务状态。服务显示 RUNNING 但 `wg show` 无握手，说明服务起来了而数据面未通，应转去查端点、AllowedIPs 与路由，不要反复重启服务。

3. **在普通用户会话里执行服务控制**。`docs/attacksurface.md` 明确 manager 与 tunnel 服务均以 LocalSystem 运行，UI 以高完整性提升令牌运行；`sc stop`、`sc config`、`Set-Service` 这类操作通常需要管理员权限，权限不足时表现为「拒绝访问」而非半份输出。企业脚本应显式以管理员或 SYSTEM 账户运行，`schtasks` 示例用 `/ru SYSTEM` 正是这个道理。

4. **把环形日志与 Windows 事件日志互相替代**。`wireguard /dumplog` 读的是本仓库 `ringlogger/` 的共享环形日志，`wevtutil qe` 读的是系统事件日志。服务为何启动失败、脚本键为何被跳过这类信息写在前者里；后者只有 SCM 层面的启停记录。只盯事件日志会漏掉关键诊断行（见 3.5、06-11）。

5. **`wireguard /dumplog` 在没有 stdout 的上下文里报错**。`main.go` 的 `/dumplog` 分支要求 `STD_OUTPUT_HANDLE` 有效，否则直接报 `Stdout must be set`。在计划任务、服务包装或某些远程执行环境里标准输出可能为空，此时应显式重定向到文件或改为读日志文件，不要以为是日志功能坏了。

6. **计划任务路径空格与账户配错**。`docs/enterprise.md` 的示例把 `/tr` 整串用双引号包住，是因为 `%PROGRAMFILES%\WireGuard\wireguard.exe` 含空格；漏引号会让任务只执行到目录名为止。同时 `/ru SYSTEM` 决定更新以 LocalSystem 身份运行，换成普通账户可能因权限不足而失败。

7. **隧道停止后查不到适配器就判驱动丢失**。`docs/enterprise.md` 的 Driver Removal 一节与 `docs/netquirk.md` 都说明适配器在启动时动态创建、停止时销毁。`Get-NetAdapter` 在隧道停止时为空是预期；只有在隧道运行状态下仍查不到，才需要结合 `pnputil /enum-drivers` 与 `wireguard /removedriver` 排查（见 3.4）。

8. **绕过本仓库直接用 `pnputil` 删驱动**。`wireguard /removedriver` 会自行判断「没有更多适配器」的前提并调用 `driver.Uninstall()`；直接删驱动包可能留下服务、注册表或适配器残留。正确顺序是先停全部隧道服务、确认无适配器，再走 `/removedriver`，失败后才把 `pnputil` 当善后手段（见 03-06、04-04）。

推荐的调试顺序是：先用 `sc query` 与 `Get-Service` 锁定服务状态，再用 `Get-NetAdapter`、`Get-NetRoute`、`Get-NetIPConfiguration` 核验网络对象是否齐备，接着用 `wireguard /dumplog` 读主日志、必要时用 `wevtutil` 补事件旁证，最后用 `wg show` 看握手与流量是否推进；涉及策略与更新的分支分别用 `reg query` 与 `schtasks /query` 收口。这条顺序把「服务—网络—日志—实例」四层证据串起来，与图 04-06-02 的分层判读一致，具体故障到命令的映射速查见 04-08。

## 04-07 管理员注册表策略与危险脚本执行

### 1. 本篇定位与覆盖范围

本篇是 04「配置与命令行」册的第七篇，采用 B 手册字典型骨架，也是全册关于「管理员注册表策略」的唯一权威源。它覆盖的内容集中而敏感：`HKLM\Software\WireGuard` 下的两个 DWORD 键——`LimitedOperatorUI` 与 `DangerousScriptExecution`——以及由后者解锁的四个脚本配置键 `PreUp`、`PostUp`、`PreDown`、`PostDown`，外加 Windows 客户端专用的环境变量 `WIREGUARD_TUNNEL_NAME`。大纲把「受限 UI 能力矩阵」「脚本开关的安全代价」「卸载清理行为」一并交给本篇，因此本篇既要给全参数表，又要把每个键背后「谁能用、能做什么、代价是什么」讲透。

一手依据是 `docs/adminregistry.md`，它开篇就把这批键定性为「供管理员完成非常规操作的高级旋钮，不推荐启用，没有 UI 可以打开，将来也可能移除，卸载器会清理整个 `HKLM\Software\WireGuard`，请自行承担风险并确认你知道自己在做什么」。这段定性不是套话，而是本篇所有结论的前提：这两个键没有图形开关、不受常规配置校验保护、不保证跨版本存在，写入即生效于整机。第二手依据是 `docs/enterprise.md`，它在 Tunnel Service 一节补了一句关键约束：`PreUp`、`PostUp`、`PreDown`、`PostDown` 可以在隧道服务生命周期的若干时点运行自定义命令，但「只有设置了正确的注册表键」才行；在 Manager Service 一节又说明受限 UI 会在 Network Configuration Operators 组的桌面上出现，前提同样是「正确的注册表键」。两份文档互相咬合，构成本篇事实骨架。

必须写清三条边界。第一，本篇不重列 `wireguard.exe` 的 `/` 开关（04-04 是权威源）、不重列 `wg(8)` 子命令（04-05 是权威源）、不重列 `[Interface]` 与 `[Peer]` 的全部配置键（04-01 至 04-03 是权威源）；四个脚本键只在「受注册表开关约束的执行条件」这一维度展开，其作为普通配置键的语法与注释行为见 04-02、字段见 05-02。第二，本仓库是 Windows 官方客户端，不是 Linux `wg-quick(8)`：Linux 用 `%i` 指代接口名、用 `SaveConfig` 回写、用 `resolvconf` 管 DNS、用 `iptables` 写规则，这些语义 Windows 客户端一概不提供；`docs/adminregistry.md` 特别点明「不要使用 `%i`，WireGuard for Windows 改为设置环境变量 `WIREGUARD_TUNNEL_NAME`」，这是本篇反复强调的能力红线。第三，内核数据面由外部项目 WireGuardNT 实现，本仓库只负责 IOCTL 配置下发与网络配置，脚本执行发生在用户态的 tunnel 服务里，与内核数据面无关。

交叉引用统一收敛如下：`字段见 05-02 ｜ 原理见 06-05 ｜ 模块见 07-05`，服务错误码枚举另见 05-09，进程入口分派见 06-01，配置解析见 06-02；`tunnel` 服务模块能力见 07-05，脚本执行失败对应的错误码模块见 07-10，安全加固与攻击面总览见 08-05。本篇只回答「有哪些策略键、各自取值与作用域、解锁了什么、注入了什么变量、卸载后还在不在、踩了坑怎么查」，不展开 Manager 服务的令牌判定、IPC 结构与 WFP 规则实现。

### 3. 逐项详解

#### 3.1 键路径、类型与作用域

两个键的完整路径分别是 `HKLM\Software\WireGuard\LimitedOperatorUI` 与 `HKLM\Software\WireGuard\DangerousScriptExecution`，官方写入模板为 `reg add HKLM\Software\WireGuard /v <值名> /t REG_DWORD /d 1 /f`，其中 `/f` 表示强制覆盖、`/t REG_DWORD` 指定 32 位整型、`/d 1` 给值。路径位于 `HKLM`（HKEY_LOCAL_MACHINE），意味着作用域是整机而非当前用户，任何登录到这台机器的相关账户都会受影响；写入需要管理员权限，这也和 `docs/attacksurface.md` 所述「manager 与 tunnel 服务以 LocalSystem 运行、UI 以高完整性令牌运行」的权限模型一致。核验用 `reg query HKLM\Software\WireGuard` 一次列出项下所有值。注意 `docs/adminregistry.md` 声明卸载器会清理整个 `HKLM\Software\WireGuard` 项，因此把别的自定义值塞进同一项并不会比这两个键更持久。

#### 3.2 `LimitedOperatorUI` 与内置组 S-1-5-32-556

`docs/adminregistry.md` 原文是：当该键设为 `DWORD(1)`，UI 会在属于 Network Configuration Operators 内置组（`S-1-5-32-556`）的用户桌面上启动，并对该组成员施加一组限制。`S-1-5-32-556` 是 Windows 内置的「网络配置操作员」组的固定 SID，成员默认能管理网络设置但不是完整管理员；`docs/enterprise.md` 相应说明「若设置了正确的注册表键，受限 UI 也可在该组所有成员的托盘启动」。要分清两个层次：键值为 1 决定「受不限限」，组归属决定「谁的桌面上出现」；两者都满足才得到受限 UI。内置 Administrators 组不受这组限制约束，他们看到的仍是完整 UI，UI 本来就会在他们的托盘出现（见 `docs/enterprise.md` 的 Manager Service 一节）。把这个键理解成「让普通用户变成管理员」是错的，它只是把一个只读、只能启停的界面投放到非管理员桌面。

#### 3.3 受限 UI 的四类限制逐条判读

`docs/adminregistry.md` 列了四条限制加一句保留语，可归为四类。第一类是密钥剥离：配置里的所有公钥、私钥、预共享密钥都被去掉，界面不展示，因而受限用户无法读取密钥材料，也无法通过导出得到完整可用配置。第二类是配置管理封禁：添加、删除、编辑、导入、导出配置一律禁止，这直接对应 03-04 的配置存储与 04-01 至 04-03 的配置键编辑能力被整体关掉。第三类是更新收敛：不显示版本更新弹窗通知、不允许执行更新，但仍保留一个标签页指示更新可用；更新入口因此只剩管理员侧的 `wireguard /update`（见 04-04）与 04-06 的 `schtasks` 定时任务。第四类是退出封禁：不允许退出 manager，避免受限用户把托盘服务关掉影响其他会话。保留语是「启动与停止隧道等基本功能保持不变」——这正是企业里把「链路开关」下放给一线、同时把「配置与密钥」收归管理员的典型用法（场景见 03-05、安全讨论见 08-05）。

#### 3.4 `DangerousScriptExecution` 与四个脚本键

`docs/adminregistry.md` 原文是：当该键设为 `DWORD(1)`，tunnel 服务会执行隧道配置中 `PreUp`、`PostUp`、`PreDown`、`PostDown` 四个选项所指定的命令。`docs/enterprise.md` 用「但只有设置了正确的注册表键」再次确认这是硬开关：未开启时，这四个键即便写进 `.conf` 也不会被执行。这一点与 04-02 讲配置键语法时的结论互相印证——解析器会接受并保存这四个键，但「接受」不等于「执行」，执行权在注册表开关手里。四个键按命名分别对应隧道启动前、启动后、停止前、停止后四个时点，`docs/enterprise.md` 只笼统说「隧道服务生命周期的若干时点」，精确顺序与失败时是否继续启停需对照实际版本核验，可定位 `docs/enterprise.md` 与 `tunnel/service.go`。开关判定与触发时序如图 04-07-02 所示，虚线表示「配置被解析」是始终发生的、与开关无关。

#### 3.5 `WIREGUARD_TUNNEL_NAME` 与 `%i` 的边界

`docs/adminregistry.md` 用一句很具体的话划清了与 Linux 的差异：「Rather than use `%i`，WireGuard for Windows instead sets the environment variable `WIREGUARD_TUNNEL_NAME` to the name of the tunnel when executing these scripts」。也就是说，Windows 客户端在执行这四个脚本时，把当前隧道名放进名为 `WIREGUARD_TUNNEL_NAME` 的环境变量里，脚本通过读该变量拿到隧道名；Linux `wg-quick` 的 `%i` 占位符在这里不存在，照抄含 `%i` 的 `PostUp` 行不会得到接口名，只会得到一个字面量或解析异常。变量的值是隧道名而非服务名，也不是适配器名：隧道名来自配置文件名，受 `conf/name.go` 的 `TunnelNameIsValid` 约束（长度 1 至 32、字母数字与 `_=+.-`、拒绝保留设备名与特殊字符），服务名则是 `ServiceNameOfTunnel` 拼出的 `WireGuardTunnel$<name>`（见 04-01、04-06）。脚本里若需要拼服务名，应自行加上前缀，不要指望环境变量已经带好。

#### 3.6 脚本键在 `conf/parser.go` 的解析特判

四个脚本键在解析器里有一处专门处理，值得单独点出，因为它影响写脚本时的注释习惯。`conf/parser.go` 的 `FromWgQuick` 在按键名分派之前有一段 `case "preup", "postup", "predown", "postdown"`：对这四个键，它不按 `#` 切断行内注释，而是取等号之后的整段内容作为值，并把 `comment` 清空。原因在于脚本命令本身常含 `#`（例如颜色值、正则、shell 片段），若按普通键那样把 `#` 当注释起始，命令会被截断。其余 `[Interface]` 与 `[Peer]` 键仍按通用逻辑处理行内注释与注释保真。因此写 `PostUp` 时不必担心 `#` 被吃掉，但也要意识到：这一整行在解析后就是脚本字符串本身，不要指望在行尾追加一句以 `#` 开头的说明还能被当成配置注释保留。解析状态机与注释保真的完整讨论见 06-02，字段见 05-04。

#### 3.7 LocalSystem 执行的安全代价

`docs/adminregistry.md` 对 `DangerousScriptExecution` 的警告措辞是全文最重的：执行以 Local System 用户身份进行，而该账户在操作系统里拥有最高权限，因此是恶意软件的真实目标，开启时须「极度审慎」，仅在确知后果时启用。这与 `docs/attacksurface.md` 的权限描述一致——tunnel 服务本就以 LocalSystem 运行，只是通过 `AdjustTokenPrivileges` 丢弃了除 `SeLoadDriverPrivilege` 外的大部分特权；一旦允许执行配置里的任意命令，等于把「能写配置文件」间接升级为「能以最高权限执行命令」。风险链条是：配置文件可被导入或投放（见 03-04、03-05），脚本键内容随配置走，开关又只需一个整机级 DWORD 值，三者叠加会显著扩大攻击面。因此 08-05 把「默认不执行、开启条件、最小权限」列为加固项；本篇的立场与文档一致，只解释机制，不推荐在生产环境默认开启。

#### 3.8 `ErrorRunScript` 与脚本失败的错误码

脚本执行失败会落到本仓库统一的错误码体系里。`services/errors.go` 的 `Error` 枚举中有一项 `ErrorRunScript`，其 `Error()` 字符串为 `An error occurred while running a configuration script command`，正好对应脚本命令执行出错；同文件还定义了 `ErrorCreateNetworkAdapter`、`ErrorSetNetConfig`、`ErrorFirewall` 等相邻阶段错误码。`DetermineErrorCode(err, serviceError)` 的返回逻辑是：若错误可 `errors.As` 成 `windows.Errno`，直接返回该 Win32 错误码；否则若传入了非零的 `serviceError`，返回它的数值；再否则返回 `NO_ERROR`。`CombineErrors` 则把服务错误码与底层错误包装成一条可读文本。排障时看到脚本相关失败，应先读环形日志（见 04-06 的 `wireguard /dumplog`），再对照 `services/errors.go` 判断是脚本本身返回非零、还是被相邻阶段错误掩盖。错误码枚举逐项见 05-09，服务退出与日志行为见 06-01、07-10。

#### 3.9 卸载清理与键的易失性

`docs/adminregistry.md` 开头明确「卸载器会清理整个 `HKLM\Software\WireGuard`」，并在结尾再次提示这些键「没有 UI、也不计划提供 UI，将来某个版本可能被移除」。这两句合起来给出运维结论：这两个键不是稳定的配置面，而是临时的高级旋钮。任何依赖 `LimitedOperatorUI` 的受限 UI 部署或依赖 `DangerousScriptExecution` 的脚本钩子，都应把「键的建立」写进部署脚本（见 03-05、04-06 的 `reg` 用法），并在每次升级、覆盖安装或卸载后复核键值是否还在；卸载后残留的配置目录与服务清理顺序见 03-06。把这两个键当成写入即永久生效的常规设置，是本篇第 7 节要专门纠正的误用。

### 4. 典型示例

第一组给出两个键的写入与核验命令，来自 `docs/adminregistry.md` 的官方模板，在提升的命令提示符或 PowerShell 中执行。命令形式见下方示例。

```powershell
reg add HKLM\Software\WireGuard /v LimitedOperatorUI /t REG_DWORD /d 1 /f
reg add HKLM\Software\WireGuard /v DangerousScriptExecution /t REG_DWORD /d 1 /f
reg query HKLM\Software\WireGuard
```

核验命令的典型输出如下。示例输出，具体格式需对照实际版本核验。

```text
> reg query HKLM\Software\WireGuard

HKEY_LOCAL_MACHINE\Software\WireGuard
    LimitedOperatorUI    REG_DWORD    0x1
    DangerousScriptExecution    REG_DWORD    0x1
```

逐行判读如下。首行 `HKEY_LOCAL_MACHINE\Software\WireGuard` 是所查询的注册表项，确认写在了 `HKLM` 而不是当前用户配置单元；若这里报「错误: 系统找不到指定的注册表项」，说明两个键都还没建立，此时 `LimitedOperatorUI` 与 `DangerousScriptExecution` 均按未开启处理，受限 UI 不会出现、四个脚本键也不会执行。第二行 `LimitedOperatorUI REG_DWORD 0x1` 有三段信息：值名必须与文档一字不差，类型必须是 `REG_DWORD` 而不是 `REG_SZ` 或 `REG_QWORD`，`0x1` 是十六进制的 1，只有这个值才触发文档描述的受限界面；若看到 `0x0`，界面仍按完整管理员 UI 呈现。第三行 `DangerousScriptExecution REG_DWORD 0x1` 同理，它一旦为 1，tunnel 服务就会以 LocalSystem 执行配置里的四个脚本键，这是整机级的行为变更，判读时不能只看「值存在」就认为安全。特别要注意输出里没有第四行其它值时属于正常——`docs/adminregistry.md` 只定义了这两个值，卸载器清理的是整个项而不是逐个值；反之，若这里出现拼写近似的值名（例如少一个字母或大小写混用），那不是官方键，不产生任何文档描述的效果，需对照 `docs/adminregistry.md` 实际版本核验。最后，`reg query` 只能证明键值已写入，不能证明受限 UI 已弹出或脚本已成功执行，后者仍要回到服务日志与运行时状态确认。

第二组给出一段带脚本键的配置示例，以及配套的说明。脚本键的语法归属见 04-02，此处只演示开关与环境变量的关系。

```conf
[Interface]
PrivateKey = yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=
Address = 10.0.0.2/32
DNS = 10.0.0.1
PostUp = echo %WIREGUARD_TUNNEL_NAME% up >> C:\wg-diag\hooks.log
PostDown = echo %WIREGUARD_TUNNEL_NAME% down >> C:\wg-diag\hooks.log

[Peer]
PublicKey = xTIBA5rboUvnH4htodjb6e697QjLERt1NAB4mZqp8Dg=
AllowedIPs = 0.0.0.0/0
Endpoint = 203.0.113.1:51820
```

这段配置里 `PostUp` 与 `PostDown` 用 `%WIREGUARD_TUNNEL_NAME%` 读取隧道名，是 Windows 客户端的写法；若照抄 Linux `wg-quick` 的 `%i`，脚本拿不到接口名。按 `docs/adminregistry.md`，只要 `DangerousScriptExecution` 不是 DWORD 1，这两行就只被解析保存、不会执行，日志里也不会出现 `up` 与 `down`；开启后它们才以 LocalSystem 身份运行，写文件位置、路径权限都要按最高权限账户重新评估。另需提醒：`conf/parser.go` 对四个脚本键不切行内 `#`（见 3.6），所以脚本命令里出现 `#` 不会被当注释截断，但也别在行尾追加 `# 说明` 指望它被当成配置注释保留。配置键全集见 04-01 至 04-03，脚本执行条件以本篇为准。

### 5. 速查表

下表把「想做什么 → 需要哪个键 → 怎么核验 → 代价」压缩成一行行查表项，具体命令回指 04-06 与本篇第 4 节。

| 目标 | 需要的键值 | 核验命令 | 主要代价 |
|---|---|---|---|
| 让非管理员看到只读托盘 UI | `LimitedOperatorUI` = `1` | `reg query HKLM\Software\WireGuard` | 密钥被剥离、配置管理封禁 |
| 允许下放启停隧道 | `LimitedOperatorUI` = `1`，无需额外键 | 让该组成员登录查看托盘 | 只能启停，不能改配置 |
| 执行 `PreUp` 等四个脚本键 | `DangerousScriptExecution` = `1` | `reg query HKLM\Software\WireGuard`，再看服务日志 | 以 LocalSystem 运行，攻击面扩大 |
| 在脚本里拿到隧道名 | 读 `WIREGUARD_TUNNEL_NAME` | 脚本内 echo 到日志 | 不是服务名、不是 `%i` |
| 关闭受限 UI 或脚本执行 | 删除对应值或改为 `0` | `reg query` 复核 | 需管理员权限，立即生效于整机 |
| 卸载后的状态复核 | 整项被清理 | `reg query` 应报找不到项 | 定制不持久，需重新写入 |
| 脚本失败定位 | 看 `ErrorRunScript` | `wireguard /dumplog` 见 04-06 | 错误码见 `services/errors.go` |

使用这张表时有两条约定。其一，所有 `reg` 操作都作用于 `HKLM\Software\WireGuard`，必须在提升的会话里执行；表格里的 `1` 指 `REG_DWORD` 类型的数值 1，`0` 或类型不符都不生效，具体判定需对照 `docs/adminregistry.md` 实际版本核验。其二，「主要代价」列不是建议清单而是风险提示，尤其第二行与第三行：受限 UI 的代价是能力被削，脚本开关的代价是权限被放大，二者方向相反，不要因为都写在同一个注册表项下就一并开启。

### 6. 版本差异

第一层是官方文档自己声明的易变性。`docs/adminregistry.md` 开头就说这些是「非常规、不推荐、没有 UI、也不计划提供 UI」的高级旋钮，且「将来某个版本可能被移除」，卸载器还会清理整个 `HKLM\Software\WireGuard`。因此本篇描述的两个键属于版本敏感事实：它们的存在性、值名、作用域在不同 master 快照之间可能变化，也可能被整体删掉。凡要把它们写进自动化部署脚本，都应把「键是否存在、值是否仍生效」列为升级后的复核项，并保留一份可重新写入的模板（见 3.9、04-06 的 `reg` 用法）。相比之下，`docs/enterprise.md` 描述的服务名、配置目录、日志入口属于稳定面，两者不可相提并论。

第二层是 `WIREGUARD_TUNNEL_NAME` 与 `%i` 的跨版本稳定性。`docs/adminregistry.md` 明确「不要使用 `%i`，改用环境变量 `WIREGUARD_TUNNEL_NAME`」，这是 Windows 客户端的长期设计取向，与 Linux `wg-quick` 的 `%i`、`SaveConfig`、`resolvconf` 语义永久分离。变量值取自隧道名，而隧道名合法性由 `conf/name.go` 的 `TunnelNameIsValid`、`allowedNameFormat` 正则、保留设备名列表与 `specialChars` 常量决定；这些是源码细节，跨版本有微调可能，字段名与取值需对照 `upstream_src/conf/name.go` 当前版本核验。服务名前缀 `WireGuardTunnel$` 来自 `ServiceNameOfTunnel`，属稳定约定（见 04-06）。

第三层是错误码与解析行为的版本相关面。`services/errors.go` 的 `Error` 枚举项、`ErrorRunScript` 的返回字符串、以及 `DetermineErrorCode` 对 `windows.Errno` 与服务自定义码的取舍，都需对照 `upstream_src/services/errors.go` 核验（字段见 05-09）；`conf/parser.go` 对四个脚本键「不切 `#` 注释」的特判属解析实现，跨版本可能调整，相关机制见 06-02、注释保真字段见 05-04。四个脚本键的精确触发时点，`docs/enterprise.md` 只给「隧道服务生命周期的若干时点」这一笼统表述，具体顺序需对照 `tunnel/service.go` 实际版本核验，本篇不写死。凡涉及具体版本号、注册表子项新增、脚本执行时序与错误码数值，统一标注「需对照实际版本核验」，可定位路径为 `docs/adminregistry.md`、`docs/enterprise.md`、`conf/name.go`、`conf/parser.go`、`services/errors.go`、`tunnel/service.go`。

### 7. 常见误用与调试

1. **以为写了脚本键就会执行**。`PreUp`、`PostUp`、`PreDown`、`PostDown` 被 `conf/parser.go` 正常解析保存，但 `docs/enterprise.md` 明确「只有设置了正确的注册表键」才运行。未把 `DangerousScriptExecution` 设为 DWORD 1 时，脚本静默不执行是最常见的「配了没生效」根因，先 `reg query` 再谈脚本逻辑。

2. **照抄 Linux 的 `%i`**。`docs/adminregistry.md` 专门写「Rather than use `%i`」，Windows 只注入 `WIREGUARD_TUNNEL_NAME`。把含 `%i` 的 `PostUp` 行搬过来，轻则拿到字面量、重则命令语义错乱；同理，`SaveConfig`、`resolvconf`、`iptables` 都不是 Windows 客户端能力（见 04-02、04-05）。

3. **把 `WIREGUARD_TUNNEL_NAME` 当服务名或接口名用**。它的值是隧道名（来自文件名、受 `conf/name.go` 约束），不是 `WireGuardTunnel$<name>`，也不是动态创建的适配器名。脚本里要拼服务名得自己加前缀，要找适配器得走 `Get-NetAdapter`（见 04-06）。

4. **用 `REG_SZ` 写值或写成 `0`**。官方模板是 `/t REG_DWORD /d 1`，类型不符或值不为 1 都不会触发文档描述的行为。`reg query` 里看到 `REG_SZ`、`0x0` 或拼写近似的值名，都要按「未开启」处理，具体判定需对照 `docs/adminregistry.md` 实际版本核验。

5. **在 `HKCU` 下找键**。两个键都在 `HKLM\Software\WireGuard`，是整机级设置。在 `HKCU` 里增删同名值完全不影响 manager 与 tunnel 服务，排障时第一步应确认查询的是 `HKEY_LOCAL_MACHINE`。

6. **低估 LocalSystem 执行的代价**。`docs/adminregistry.md` 用「恶意软件的真实目标」「极度审慎」形容这个开关，因为配置文件可被导入或批量投放，脚本内容随配置走，开启后等于把写配置的能力间接升级为最高权限命令执行。默认应关闭，确需开启时配合配置目录 ACL 与最小权限一并评估（见 03-04、08-05）。

7. **以为受限 UI 能改配置或能看到密钥**。`docs/adminregistry.md` 的四条限制是硬约束：密钥被剥离、增删改导入导出全禁、更新被禁、退出 manager 被禁，只保留启停隧道。想把「改配置」下放给该组用户是做不到的，那属于内置 Administrators 的能力。

8. **把两个键当成永久设置**。`docs/adminregistry.md` 明说卸载器清理整个 `HKLM\Software\WireGuard`、且这些键将来可能移除。升级或覆盖安装后受限 UI 消失、脚本突然不跑，第一反应应是用 `reg query` 复核键值，而不是怀疑脚本本身或 UI 进程。

9. **脚本行尾追加 `#` 注释**。`conf/parser.go` 对四个脚本键不切行内 `#`，命令里的 `#` 不会被截断，但你在行尾写的 `# 说明` 也会一并成为命令字符串的一部分，可能让命令执行失败。注释要写在脚本键之外的独立行（解析特判见 3.6、机制见 06-02）。

推荐的调试顺序是：先 `reg query HKLM\Software\WireGuard` 确认键值与类型，再用 `wireguard /dumplog` 读共享环形日志（见 04-06）找 `ErrorRunScript` 或相邻阶段错误码，接着对照 `services/errors.go` 判断失败来源，最后才检查脚本命令本身与 `%WIREGUARD_TUNNEL_NAME%` 的展开结果。受限 UI 不复现时，先确认 `LimitedOperatorUI` 为 1，再确认目标账户确实属于 `S-1-5-32-556` 组，二者缺一不可。整条链路与图 04-07-01、图 04-07-02 的作用域划分一致，错误码逐项见 05-09，服务与安全加固讨论见 07-10、08-05。

### 3. 逐项详解

#### 3.1 解析期错误：`conf/parser.go` 的三层校验

配置导入失败几乎都能在 `FromWgQuick` 里找到对应分支，按「结构 → 值域 → 语义」三层排查最省事。结构层：每一行先按 `#` 切出注释，再按 `=` 切键值；不在任何段内的行报 `Line must occur in a section`，缺 `=` 报 `Config key is missing an equals separator`，`=` 后为空报 `Key must have a value`，`[Interface]` 与 `[Peer]` 段里出现白名单之外的键分别报两个 `Invalid key for ... section`。值域层：`parseIPCidr` 用 `netip.ParsePrefix` 与 `netip.ParseAddr` 解析地址，失败报 `Invalid IP address`；`splitList` 遇连续逗号报 `Two commas in a row`；`parseKeyBase64` 要求 Base64 解码后恰为 32 字节，否则报 `Invalid key` 或 `Keys must decode to exactly 32 bytes`；`parseMTU` 限定 576 至 65535，`parsePort` 与 `parsePersistentKeepalive` 限定 0 至 65535 且后者接受 `off`；`parseEndpoint` 要求有冒号端口、IPv6 方括号里必须是合法 v6 地址。语义层：函数末尾强制 `sawPrivateKey` 为真，否则报 `An interface must have a private key`；逐个 peer 检查 `PublicKey.IsZero()`，任一为零报 `All peers must have public keys`。这三层之外的 `FromWgQuickWithUnknownEncoding` 会在首次解析失败后尝试多种 Unicode 编码重解，因此「文件编码不对」也可能表现为上述某条错误，而不是独立的编码报错（机制见 06-02）。

#### 3.2 隧道名与路由冲突检测

隧道名冲突有两条独立线索。其一是命名合法性：`conf/name.go` 的 `TunnelNameIsValid` 先排除 Windows 保留设备名与特殊字符，再要求匹配 `^[a-zA-Z0-9_=+.-]{1,32}$`，且不允许以 `.` 开头或结尾；`ServiceNameOfTunnel` 在非法时返回 `Tunnel name is not valid`，合法时拼出 `WireGuardTunnel$<name>`。含空格、中文、`$` 或超过 32 字符的文件名会在这一步被拒，`docs/enterprise.md` 里 `/installtunnelservice C:\path\to\some\myconfname.conf` 生成 `WireGuardTunnel$myconfname` 正是合法样例。其二是路由层面的「弱主机发送」检测：`tunnel/pitfalls.go` 的 `pitfallWeakHostSend` 遍历 `winipcfg.GetIPForwardTable2` 得到的路由表，对每个 peer 的 `Endpoint.Host` 找到最长前缀匹配、取最低度量，若最终出接口不是本隧道接口、且该接口开启了 `ForwardingEnabled` 或 `WeakHostSend`，就记录「会致路由环路」的告警。排查「能连上但流量绕路或环回」时，先按 04-06 的 `Get-NetRoute` 看端点网段路由是否落在隧道接口，再看日志里有没有这条告警（原理见 06-06）。

#### 3.3 服务错误码与 `DetermineErrorCode`

`services/errors.go` 把服务启动各阶段映射成一个 `Error` 枚举，从 `ErrorRingloggerOpen`、`ErrorLoadConfiguration`、`ErrorCreateNetworkAdapter` 一路到 `ErrorDeviceSetConfig`、`ErrorSetNetConfig`、`ErrorRunScript`、`ErrorWin32`，共 17 项，逐项文本见第 2 节第二张表。判读的关键在两个函数：`DetermineErrorCode(err, serviceError)` 先看错误能否 `errors.As` 成 `windows.Errno`，能则直接返回该 Win32 错误码；否则若传入了非零的 `serviceError` 就返回它的数值；再否则返回 `NO_ERROR`。`CombineErrors(err, serviceError)` 则把服务错误码字符串与底层 `err` 用 `fmt.Errorf("%v: %w", ...)` 包装成一条可读文本。因此同一个故障，日志里可能同时出现「`Unable to ...`」这样的语义串和一个 Win32 数值码，二者不矛盾：前者是阶段定位，后者是底层原因。第 2 节表格的「首选取证命令」一列就是按阶段给出的，逐项错误码枚举见 05-09，服务启动顺序见 06-05，错误码模块见 07-10。

#### 3.4 三类主动告警：`tunnel/pitfalls.go`

`evaluateStaticPitfalls` 起两个 goroutine 分别跑 `pitfallDnsCacheDisabled` 与 `pitfallVirtioNetworkDriver`，`evaluateDynamicPitfalls` 针对地址族起 `pitfallWeakHostSend`。第一条查 `dnscache` 服务的 `StartType`，若为 `mgr.StartDisabled` 就警告「请重新启用」，因为 DNS 客户端缓存被禁用会影响解析。第二条用 `NtQuerySystemInformation` 枚举内核模块找 `netkvm.sys`，读到文件版本后与源码里的 `minimumGoodVersion`（注释写成 v100.85.104.20800）比较，落在旧版本区间就警告升级 VirtIO 驱动。第三条即 3.2 讲的弱主机发送与路由环路检测。三条都以 `Warning:` 前缀写进共享环形日志，不是致命错误：隧道可能照常起来，但存在解析或路由隐患。因此「日志有 Warning 但界面没报错」不应被忽略，具体版本阈值与检测条件需对照 `upstream_src/tunnel/pitfalls.go` 实际版本核验。

#### 3.5 日志行格式与来源

排障取证几乎都要落到 `wireguard /dumplog`（开关见 04-04、采集命令见 04-06），而读懂它需要先知道格式。`ringlogger/ringlogger.go` 里每行写入时构造成 `[TAG] <内容>`，`WriteTo` 再用 `fmt.Fprintf(out, "%s: %s\n", time.Unix(0, timeNs).Format("2006-01-02 15:04:05.000000"), line...)` 输出，所以一行日志形如 `年-月-日 时:分:秒.六位微秒: [tag] 内容`。tag 来自各进程初始化：`manager/service.go` 用 `InitGlobalLogger(logFile, "MGR")`，`tunnel/service.go` 用 `"TUN"`，`main.go` 的 `/ui` 分支用 `"GUI"`，`ringlogger/dump.go` 只读映射用 `"DMP"`。于是看到 `[MGR]` 就知道是 manager 服务写的、`[TUN]` 是某条隧道服务写的，定位多隧道问题时很有用。`ringlogger` 常量 `maxLines = 2048`、`maxLogLineLength = 512` 决定它是有界环形缓冲，旧行会被覆盖，因此故障发生后应尽快 dump 到文件（格式见 05-09、共享内存与读取链见 06-11、模块见 07-10）。

#### 3.6 最小可复现配置集

「最小可复现配置集」是把问题从复杂生产配置里剥离出来的标准手法，本篇给的是组合原则，不重列配置键全集（见 04-01 至 04-03）。原则是：一条隧道、一个 `[Interface]`、一个 `[Peer]`，只保留必需键——`[Interface]` 的 `PrivateKey` 与 `Address`，`[Peer]` 的 `PublicKey` 与 `AllowedIPs`，以及需要对端主动连入或本端主动连出时的 `Endpoint`；先不写 `DNS`、`MTU`、`ListenPort`、`PresharedKey`、`PersistentKeepalive`、`Table`、四个脚本键，也不启用 04-07 的注册表策略。用这份最小集若能握手成功，再逐一把生产配置里的键加回去，第一个让故障复现的键就是嫌疑域；若最小集仍失败，则问题多半在密钥配对、端点可达性、系统服务或路由，而不在某个可选配置键。配合 04-06 的 `Get-NetRoute` 与 04-05 的 `wg show`，可把「配置问题」与「网络问题」分开。最小集仍然受 3.1 的语义校验约束：没有 `PrivateKey`、或 `[Peer]` 缺 `PublicKey`，解析器根本不会让它进入运行阶段。

投放最小集时还要留意命名与存储链路两处附带条件。文件名即隧道名，必须过 `conf/name.go` 的 `TunnelNameIsValid`，否则 `FromWgQuick` 开头就会以 `Tunnel name is not valid` 拒绝，服务名也无从拼出；因此做对照实验时建议固定一个短名如 `mintest`，只改配置内容而不改文件名，避免把命名问题误算成配置问题。若按 03-04 的路径把 `.conf` 放进 `%ProgramFiles%\WireGuard\Data\Configurations\`，manager 服务会把它加密成 `.conf.dpapi` 并删除明文，之后 `wg(8)` 交互就需要 Local System 或 Administrator 权限（见 04-05）；排障期间若希望用普通权限反复 `wg show`，可改用 `/installtunnelservice` 直接指向一份不在该目录里的明文 `.conf`（见 04-04、03-03），但实验结束后应把临时配置清理掉，避免遗留可被低权限读取的私钥。这两点不改配置键本身，却常常决定最小集能不能顺利跑起来，属于「环境而非配置」的排障分支。

#### 3.7 诊断命令的组合顺序

排障不是把所有命令跑一遍，而是按层取证。第一层配置与命名：先看导入时的 `ParseError` 文本，对照第 2 节第一张表与 `conf/name.go` 规则；第二层服务与错误码：`sc query`、`wireguard /dumplog`，对照 `services/errors.go`；第三层适配器与路由：`Get-NetAdapter`、`Get-NetRoute`、`Get-NetIPConfiguration`，看 AllowedIPs 是否落成路由、DNS 是否按 04-02 生效；第四层握手与端点：`wg show` 看 `latest handshake` 与 `transfer`（输出判读见 04-05、原理见 06-06）。四层顺序如图 04-08-02 所示，前一层通过后才进入下一层，日志为各层提供旁证。所有命令的开关与参数分别回指 04-04、04-05、04-06，本篇只固定「先后顺序」而不重列命令清单。

### 4. 典型示例

第一组给出一次排障取证的完整命令序列，命令本身见 04-04 至 04-06，此处只固定组合顺序。命令形式见下方示例。

```powershell
sc query 'WireGuardTunnel$mytunnel'
wireguard /dumplog > C:\wg-diag\dump.log
wg show mytunnel
Get-NetRoute -DestinationPrefix 10.0.0.0/24 | Format-Table InterfaceIndex, DestinationPrefix, NextHop
reg query HKLM\Software\WireGuard
```

`wireguard /dumplog` 的典型输出如下，其中三条 `Warning` 文本取自 `tunnel/pitfalls.go`，时间戳与 tag 前缀取自 `ringlogger/ringlogger.go` 与 `ringlogger/dump.go`。示例输出，具体格式需对照实际版本核验。

```text
> wireguard /dumplog

2026-11-11 09:12:04.002915: [TUN] Warning: the "DNS Client" (dnscache) service is disabled; please re-enable it
2026-11-11 09:12:04.117340: [TUN] Warning: the VirtIO network driver (NetKVM) is out of date and may cause known problems; please update to v100.85.104.20800 or later
2026-11-11 09:12:05.663018: [TUN] Warning: the "Ethernet" interface has Forwarding/WeakHostSend enabled, which will cause routing loops
```

逐行判读如下。三行的公共前缀都遵循 `年-月-日 时:分:秒.六位微秒: [TUN] 内容` 这一格式：`2026-11-11 09:12:04.002915` 是 `ringlogger` 用 `2006-01-02 15:04:05.000000` 布局输出的微秒级时间戳，用于把三条告警与同一时刻的服务动作对齐；`[TUN]` 是 `tunnel/service.go` 以 `InitGlobalLogger(logFile, "TUN")` 写入的进程标签，若某行是 `[MGR]` 则来自 `manager/service.go`，是区分「哪条隧道服务」与「管理服务」的第一线索。第一条 `dnscache service is disabled` 出自 `pitfallDnsCacheDisabled`，它查到 DNS Client 服务的启动类型为禁用后发出，修复方向是恢复该服务，否则依赖域名解析的 `Endpoint` 可能失败，对应 `services/errors.go` 的 `ErrorDNSLookup`。第二条 `VirtIO network driver (NetKVM) is out of date` 出自 `pitfallVirtioNetworkDriver`，它枚举内核模块找到 `netkvm.sys` 并比对文件版本，落在旧区间就提示升级到 v100.85.104.20800 或更高，这是虚拟化环境特有的已知问题，与 WireGuard 配置本身无关。第三条 `Forwarding/WeakHostSend ... routing loops` 出自 `pitfallWeakHostSend`，说明到某个 peer 端点的路由最终落在了非隧道接口、且该接口开启了转发或弱主机发送，可能形成路由环路，应结合 `Get-NetRoute` 检查端点网段与接口索引（原理见 06-06）。三条都是 `Warning` 而非致命错误，服务通常仍能启动，但它们分别指向 DNS、驱动与路由三个不同隐患域，正好演示「同一份日志按前缀分类、按文本定位域」的判读方法。若日志里出现的是 `Unable to ...` 这类 `Error()` 字符串而非 `Warning`，则改用第 2 节第二张表按阶段反查，并注意 `DetermineErrorCode` 可能同时透传一个 Win32 数值码。

第二组给出 3.6 所述的最小可复现配置集，只保留必需键，用于把生产配置里的可疑项逐一切回。配置形式见下方示例。

```conf
[Interface]
PrivateKey = yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=
Address = 10.0.0.2/32

[Peer]
PublicKey = xTIBA5rboUvnH4htodjb6e697QjLERt1NAB4mZqp8Dg=
AllowedIPs = 10.0.0.0/24
Endpoint = 203.0.113.1:51820
```

这份配置满足 `FromWgQuick` 的语义校验：有 `PrivateKey`、`[Peer]` 有 `PublicKey`，两个密钥都是 32 字节 Base64，`Address` 与 `AllowedIPs` 是合法 CIDR，`Endpoint` 带端口。它刻意不写 `DNS`、`MTU`、`ListenPort`、`PresharedKey`、`PersistentKeepalive`、`Table` 与四个脚本键，也不依赖 04-07 的注册表开关，因此一旦它能握手，就可以把生产配置里的可选键逐个加回，第一个导致故障复现的键即为嫌疑域。若这份最小集也失败，优先怀疑两端密钥是否配对、`Endpoint` 是否可达、服务是否启动、`AllowedIPs` 路由是否落到隧道接口，而不是某个可选配置键。配置键完整语义见 04-01 至 04-03，字段见 05-02。

### 5. 速查表

下表把最常见的现象压成「首查 → 次查 → 修复方向」三列，命令与开关的完整语义分别回指 04-04 至 04-07。

| 现象 | 首查 | 次查 | 修复方向 |
|---|---|---|---|
| 导入配置报 `Invalid key` | 错误文本对照第 2 节第一表 | `conf/parser.go` 键白名单 | 删未知键，见 04-01 至 04-03 |
| 导入报缺私钥或缺公钥 | `[Interface]` / `[Peer]` 必填项 | `sawPrivateKey`、`PublicKey.IsZero` | 补密钥，见 04-02、04-03 |
| 隧道名被拒 | `TunnelNameIsValid` 规则 | `conf/name.go` 保留名与正则 | 改名，见 04-01 |
| 服务起不来 | `sc query` 状态 | `wireguard /dumplog` 与错误码表 | 按阶段修，见 04-06、05-09 |
| 提示 `Unable to load configuration` | 配置文件路径与权限 | `.conf.dpapi` 形态，见 03-04 | 修路径或权限 |
| 提示 `Unable to resolve ... endpoints` | `Endpoint` 域名 | `dnscache` 告警、DNS 配置 | 修解析，见 04-03、04-02 |
| 服务运行但无握手 | `wg show` 的握手与流量 | `Get-NetRoute` 与端点可达性 | 查密钥与端点，见 04-05 |
| 日志有 `routing loops` 告警 | `pitfallWeakHostSend` 文本 | `Get-NetRoute` 与接口标志 | 关转发或弱主机发送 |
| 日志有 `dnscache` 告警 | `pitfallDnsCacheDisabled` 文本 | DNS Client 服务启动类型 | 恢复服务 |
| 脚本键不执行 | `reg query` 的 DWORD 值 | 04-07 开关与 `ErrorRunScript` | 设 `DangerousScriptExecution=1` |
| 升级后策略失效 | `reg query` 是否有项 | 卸载清理整个键，见 04-07 | 重新写入键值 |

使用这张表时记住两条：其一，「首查」给的是成本最低、信息量最大的一步，不要一上来就重装或改一堆配置；其二，表格里的 `\|` 是转义后的竖线，实际命令与路径按半角书写，含 `$` 的服务名在 PowerShell 里用单引号包裹。本篇所有表格都是索引，不替代 08-04 的完整故障案例与 08-03 的诊断决策树；遇到表里没有的现象，按图 04-08-02 的四层顺序逐层取证，再带着证据回查对应权威源。

### 6. 版本差异

第一层是「事实锚点」与「版本相关数值」的分离。本篇引用的机制性结论——解析分结构、值域、语义三层校验，隧道名受 `conf/name.go` 正则与保留名约束，服务错误码分阶段，`pitfalls.go` 产三类 `Warning`，日志为有界环形缓冲且带 `MGR` / `TUN` / `GUI` 标签——都属于源码结构层面的稳定结论，可直接用于判读。而具体的错误串措辞、`Error()` 返回文本、`services/errors.go` 的枚举项数量与顺序、`pitfallVirtioNetworkDriver` 里的 `minimumGoodVersion` 版本阈值、`maxLines` 与 `maxLogLineLength` 数值，都是版本相关事实，需对照 `upstream_src/conf/parser.go`、`upstream_src/conf/name.go`、`upstream_src/services/errors.go`、`upstream_src/tunnel/pitfalls.go`、`upstream_src/ringlogger/ringlogger.go` 当前版本核验。本篇第 2 节表格已把「措辞需对照实际版本核验」写明，正是这个约定的落地。

第二层是本地化与输出格式。`conf/parser.go` 的错误原因串经 `l18n.Sprintf` 生成本地化文本，不同语言环境下界面显示与源码里的英文原因串不完全一致；`ringlogger` 的时间戳用固定布局 `2006-01-02 15:04:05.000000`，但具体时区、tag 拼写与各进程写入顺序随运行场景变化。因此本篇给的「典型输出」是按源码格式构造的示例，已标注「示例输出，具体格式需对照实际版本核验」，排障时应以现场实际行为准，不要拿示例文本做字符串精确匹配。同理，`sc query`、`wg show`、`reg query` 的输出格式分别属于 Windows 与 wireguard-tools 的版本面，回指 04-06 与 04-05。

第三层是跨册与跨平台的边界。04 册本身是配置与命令的唯一权威源，本篇作为其收官篇只做索引与判读；05 册给字段定义、06 册给机制与调用链、07 册给模块能力、08 册给案例与决策树，四者都不重列配置或命令清单。版本基准是上游仓库 master 快照（2026-11 抓取）、WireGuardNT 1.1、Go 1.27.1、Windows 10 / Server 2019 及以上与 amd64 / x86 / arm64 三种 MSI；凡涉及具体版本号、驱动版本、MSI 文件名与下载 URL 的时效性数值，一律按总纲第 9 节写「需对照实际版本核验」。特别提醒：Linux `wg-quick` 的 `%i`、`SaveConfig`、`resolvconf`、`iptables` 与 `wireguard-go` 用户态数据面都不属于 Windows 客户端能力，任何把它们写进排错结论的做法都是错误迁移（见 04-02、04-05、04-07）。

### 7. 常见误用与调试

1. **把解析错误当服务错误处理**。「`Invalid key for [Interface] section`」来自 `conf/parser.go`，是配置文件本身不合法，重启服务或重装驱动都不会解决；「`Unable to load configuration from path`」来自 `services/errors.go`，是服务读不到文件。前者改配置（见 04-01 至 04-03），后者查路径与权限（见 03-04），两者分属第 2 节不同表格。

2. **照搬 Linux 排障习惯**。用 `wg show wg0` 查固定接口名、用 `iptables` 找规则、用 `%i` 写脚本、指望 `SaveConfig` 回写，都是把 `wg-quick` 或 wireguard-go 的语义套到 Windows 客户端上。Windows 侧用隧道名定位实例（见 04-05）、用 `Get-NetRoute` 看路由（见 04-06）、脚本用 `WIREGUARD_TUNNEL_NAME`（见 04-07），三者与 Linux 不通用。

3. **忽略 `Warning` 级告警**。三条 `pitfalls.go` 告警不阻断启动，但分别指向 DNS 缓存禁用、VirtIO 驱动过旧、弱主机发送致路由环路。「界面没报错」不等于没问题，日志里的 `Warning` 应按 3.4 逐条判读，具体阈值需对照实际版本核验。

4. **把 `wg show` 的服务状态与 `sc query` 混为一谈**。`sc query` 显示服务 RUNNING 只说明 tunnel 服务在跑；握手是否推进要看 `wg show` 的 `latest handshake` 与 `transfer`（输出判读见 04-05）。服务起来了却无流量，应查端点、密钥与 AllowedIPs，而不是反复重启服务。

5. **在生产配置上直接试错**。一上来就改 `MTU`、`DNS`、`Table`、脚本键，会让变量失控。正确做法是先上 3.6 的最小可复现配置集，确认基线可握手，再逐一把生产键加回，第一个复现故障的键即嫌疑域。

6. **隧道名含空格、中文或 `$`**。`conf/name.go` 只允许长度 1 至 32 的字母数字与 `_=+.-`，并拒绝保留设备名与特殊字符。文件名不合规时，`FromWgQuick` 开头的 `TunnelNameIsValid` 检查就会失败，表现为导入被拒；同时记住服务名是 `WireGuardTunnel$<name>`，`$` 是分隔符而非名字的一部分（见 04-01、04-06）。

7. **把 `Error()` 文本与 Win32 数值码对立起来**。`DetermineErrorCode` 可能直接透传 `windows.Errno`，`CombineErrors` 又会把服务错误码字符串与底层 `err` 包装在一起。日志里同时出现「`Unable to ...`」和一个数字码是正常的，前者定位阶段、后者给底层原因，不要只取其一。

8. **脚本不执行就改脚本内容**。`PreUp` 等四个键只有在 `DangerousScriptExecution` 为 `REG_DWORD` 1 时才运行（见 04-07）。先 `reg query HKLM\Software\WireGuard` 确认开关，再谈脚本逻辑；若日志出现 `ErrorRunScript`，才轮到检查命令本身与 `%WIREGUARD_TUNNEL_NAME%` 的展开。

9. **故障后迟迟不导日志**。`ringlogger` 是有界环形缓冲（`maxLines` 与 `maxLogLineLength` 常量），旧行会被覆盖。故障发生后应尽快 `wireguard /dumplog > 文件`（见 04-06），否则关键的错误行可能已被冲掉；`/dumplog /tail` 适合持续采集，不适合事后回捞。

10. **升级后不复核策略键**。`docs/adminregistry.md` 明说卸载器清理整个 `HKLM\Software\WireGuard`、且这些键将来可能移除。升级后受限 UI 消失或脚本不跑，先用 `reg query` 复核键值，再怀疑别的（见 04-07）。

推荐的调试顺序与图 04-08-02 一致：先按第 2 节第一张表与 `conf/name.go` 排除配置与命名问题，再用 `sc query` 与 `wireguard /dumplog` 对照 `services/errors.go` 定位服务阶段，接着用 `Get-NetAdapter`、`Get-NetRoute`、`Get-NetIPConfiguration` 核验适配器与路由，最后用 `wg show` 看握手与流量；涉及策略与脚本的分支用 `reg query` 收口。四层都过仍不通时，带着日志与 `wg show` 输出转 08-04 的案例库按现象反查。错误码逐项见 05-09，解析与下发机制见 06-02、06-05、06-06，模块归属见 07-01、07-05、07-10。
