# wireguard-windows 技术资料 · 05 关键数据结构字段详解（分片 B）

## 05-06 `driver.Adapter` 与适配器状态字段

### 1. 本篇定位与覆盖范围

本篇是 05 册「工具书·随查」分片 B 的开篇，聚焦 `driver` 包里描述「一个已经创建出来的 WireGuard 适配器」的那组字段，以及围绕适配器的状态枚举、日志开关、运行版本查询与 DLL 延迟加载结构。需要首先划清能力边界：本仓库是 WireGuard 官方 Windows 客户端，内核数据面由外部项目 WireGuardNT 提供，`driver.Adapter` 并不是内核对象本身，而是用户态持有的、指向 WireGuardNT 适配器的一层极薄封装。它内部只有两个字段，所有真正的私钥、公钥、peer、AllowedIP 配置都经 `SetConfiguration` 以 IOCTL 载荷下发，相关结构定义归 05-05，本篇不重复列出 `driver.Interface` / `driver.Peer` / `driver.AllowedIP` 的字段（字段见 05-05）。本篇只回答五个问题：适配器句柄究竟是什么、状态用什么枚举表示、日志开关有哪几档、驱动运行版本怎么读出来、`wireguard.dll` 又是怎样被延迟加载进进程的。

覆盖范围按真实源码文件列出：`driver/driver_windows.go` 给出 `Adapter`、`AdapterLogState`、`loggerLevel`、`AdapterNameMax` 常量、`TimestampedWriter` 接口、各 `procWireGuard*` 导出函数句柄变量，以及 `CreateAdapter` / `OpenAdapter` / `Close` / `Uninstall` / `SetLogging` / `RunningVersion` / `LUID` 等入口；`driver/configuration_windows.go` 给出 `AdapterState` 枚举以及 `SetAdapterState` / `AdapterState` / `SetConfiguration` / `Configuration` 入口；`driver/dll_windows.go` 给出 `lazyProc` 与 `Version()`；`driver/dll_fromrsrc_windows.go` 与 `driver/dll_fromfile_windows.go` 给出两份按构建标签二选一的 `lazyDLL`。凡涉及具体驱动版本号、结构体字节对齐数值、导出函数原型，一律以本快照源码为准，不确定处写「需对照实际版本核验」并给出可定位路径。

按去重铁律，本篇只讲字段含义、内存布局、生命周期与关联函数入口，刻意不展开适配器创建时序、权限降级顺序、路由下发等机制流程（原理见 06-05、原理见 06-06），也不列配置键（配置见 04-02）与模块能力清单（模块见 07-03、模块见 07-04）。全册交叉引用统一写作：（字段见 05-05 ｜ 配置见 04-02 ｜ 原理见 06-05 ｜ 模块见 07-03）。读者把本篇当作一页「字段字典」随查即可，不必线性通读。

### 3. 逐项详解

**① `Adapter.handle`（`uintptr`）。** 这是整个 `Adapter` 结构最核心的字段，保存 `WireGuardCreateAdapter` 或 `WireGuardOpenAdapter` 返回的适配器句柄。它是不透明值，Go 侧不解释其内部结构，只在每次 `syscall.SyscallN` 调用时作为第一个参数原样传回驱动。创建成功后 `CreateAdapter` 用 `&Adapter{handle: r0}` 构造对象，并立刻 `runtime.SetFinalizer(wireguard, closeAdapter)` 挂上终结器，使得对象被 GC 时也能兜底关闭句柄。`Close` 方法先 `runtime.SetFinalizer(wireguard, nil)` 撤销终结器，再调用 `WireGuardCloseAdapter`，因此显式 `Close` 与 GC 兜底不会重复释放。读写时机非常干净：仅在创建/打开时写入一次，之后所有方法只读，不存在并发写，这也是它无需加锁的原因。需对照实际版本核验的是句柄在 32 位与 64 位进程里的位宽语义，但字段类型固定为 `uintptr`，随架构自适应。

**② `Adapter.lastGetGuessSize`（`uint32`）。** 这是为 `Configuration()` 准备的缓冲区大小缓存。WireGuardNT 的 `WireGuardGetConfiguration` 采用「传入缓冲区与实际所需尺寸」的协议：缓冲区不足时返回 `windows.ERROR_MORE_DATA` 并回填所需大小。`Configuration` 先取 `wireguard.lastGetGuessSize`，若为零则默认 512，循环分配 `make([]byte, size)` 再试；一旦成功就把回填的 `size` 写回 `lastGetGuessSize`。这样对同一适配器连续读取配置时，几乎总是一次命中，避免反复扩容。它属于性能性缓存字段，语义上是「上次成功值」而非「当前配置大小」，把它当作配置长度来用是典型误读；相关逻辑集中在 `driver/configuration_windows.go` 的 `Configuration`，本篇只点入口，不展开调用链（原理见 06-05）。

**③ `AdapterNameMax`（常量 = 128）。** 定义在 `driver/driver_windows.go`，表示适配器名称的最大长度约束。它是编译期常量，运行期全程只读，主要作为 `CreateAdapter` 的 `name` 入参语义参考。源码中 `CreateAdapter(name, tunnelType string, requestedGUID *windows.GUID)` 把 `name` 经 `windows.UTF16PtrFromString` 转为 UTF-16 指针后传入驱动，`name` 是适配器的「外观名称」，与 `tunnelType` 固定填 `"WireGuard"` 不同。该常量的具体数值可能随版本调整，写「需对照实际版本核验」并定位到 `driver/driver_windows.go` 顶部常量区。

**④ `loggerLevel`（`int`）与三个级别常量。** `logInfo` / `logWarn` / `logErr` 用 `iota` 依次取 0、1、2，是驱动通过 `WireGuardSetLogger` 回调回传日志时携带的级别标签。它只用于 `logMessage(level loggerLevel, timestamp uint64, msg *uint16) int` 的入参与 `setupLogger` 里按 `runtime.GOARCH` 分支构造的回调签名。注意 `logMessage` 并未用 `level` 做分级过滤，而是把级别编码进回调参数后统一写日志，因此级别更多是「驱动侧标记」而非「Go 侧分流开关」。三个常量在 `driver/driver_windows.go` 的同一 `const` 块里，属于稳定枚举。

**⑤ `AdapterLogState`（`uint32`）与三档日志开关。** 这是本篇标题里「适配器状态字段」中与日志相关的那一支，定义在 `driver/driver_windows.go`。`AdapterLogOff = 0` 关闭、`AdapterLogOn = 1` 开启、`AdapterLogOnWithPrefix = 2` 开启并附加前缀，均为显式赋值而非 `iota`，说明取值是与 WireGuardNT 约定好的 ABI 数值，不能随意重排。`SetLogging(logState AdapterLogState)` 把该值经 `uintptr(logState)` 传给 `WireGuardSetAdapterLogging`。在 `tunnel/service.go` 里创建适配器后调用的是 `driver.AdapterLogOn`，即不带前缀那一档。把 `AdapterLogState` 与 `loggerLevel` 混为一谈是常见误用：前者是「下发给驱动的开关」，后者是「驱动回传日志的级别」，方向恰好相反。

**⑥ `AdapterState`（`uint32`）与 Up/Down 两态。** 定义在 `driver/configuration_windows.go`，`AdapterStateDown = 0`、`AdapterStateUp = 1`。它是唯一描述适配器承载状态的枚举：`SetAdapterState(adapterState AdapterState)` 写入，`AdapterState()` 读出并比较。`tunnel/service.go` 在 `SetConfiguration` 之后调用 `SetAdapterState(driver.AdapterStateUp)` 把适配器拉起；`tunnel/interfacewatcher.go` 在接口变更回调里读到 `driver.AdapterStateDown` 时会重新下发配置并再次置 Up。需要强调：这是驱动适配器状态，与 Windows 服务状态 `svc.State` 或 manager 侧的 `TunnelState` 完全不是同一套枚举（后者字段见 05-09）。三者同名近义，务必按包区分。

**⑦ `TimestampedWriter` 接口。** 定义在 `driver/driver_windows.go`，唯一方法为 `WriteWithTimestamp(p []byte, ts int64) (n int, err error)`。`logMessage` 先取 `log.Default().Writer()`，若它实现了该接口，就用 `tw.WriteWithTimestamp` 把驱动时间戳换算后写入；换算公式 `int64(timestamp)-116444736000000000` 再乘 100，是把 Windows FILETIME 偏移到 Unix 纳秒。否则退化为 `log.Println`。该接口是「日志写入器能力契约」，与 `ringlogger` 的落盘结构配合（字段见 05-09），本篇只描述接口形状，不展开共享内存日志机制（原理见 06-11）。

**⑧ `lazyProc` 的四个字段。** 定义在 `driver/dll_windows.go`。`Name` 是导出函数名字符串，`dll` 指回所属 `lazyDLL`，`addr` 是解析后的入口地址，`mu` 保护解析临界区。`Find()` 先用 `atomic.LoadPointer` 快速判断 `addr` 是否已解析，未解析才加锁、调用 `p.dll.Load()`、再 `p.nameToAddr()`，最后用 `atomic.StorePointer` 发布地址；`Addr()` 直接调 `Find()`，失败则 `panic(err)`。这里 `addr` 的读写被刻意做成「一次发布、多次无锁读」，是典型的延迟解析模式。所有 `procWireGuard*` 变量都是它的实例，故 `Adapter` 各方法里 `.Addr()` 的调用即触发首次 DLL 加载与符号解析。

**⑨ 两份 `lazyDLL` 与五个字段。** 这是最容易被忽略、却决定「驱动 DLL 从哪来」的一组字段。`driver/dll_fromrsrc_windows.go`（构建标签 `load_wgnt_from_rsrc`）里 `lazyDLL` 的 `module` 类型为 `*memmod.Module`，`Load()` 用 `windows.FindResource` / `LoadResourceData` 从当前模块 RCDATA 资源取出 DLL 字节流，再 `memmod.LoadLibrary(data)` 做内存 PE 映射，把 `module.BaseAddr()` 写入 `Base`。`driver/dll_fromfile_windows.go`（标签 `!load_wgnt_from_rsrc`）里同名结构的 `module` 改为 `windows.Handle`，`Load()` 走 `windows.LoadLibraryEx`，并带 `LOAD_LIBRARY_SEARCH_APPLICATION_DIR|LOAD_LIBRARY_SEARCH_SYSTEM32` 两个搜索标志。两版共有 `Name`、`Base`、`mu`、`onLoad` 四字段且语义一致：`Name` 固定 `wireguard.dll`，`Base` 供 `Version()` 查版本资源，`mu` 串行化加载，`onLoad` 在加载成功后触发 `setupLogger` 注册日志回调。`module` 的类型差异正是版本差异一节要重点交代的地方（模块见 07-04）。

**⑩ `modwireguard` 全局实例与 `Version()`。** `modwireguard = newLazyDLL("wireguard.dll", setupLogger)` 在 `driver/driver_windows.go` 包初始化时构造，是全部 `procWireGuard*` 的宿主。`Version()` 定义在 `driver/dll_windows.go`：先 `modwireguard.Load()`，失败返回字符串 `"unknown"`；随后 `windows.FindResource(modwireguard.Base, windows.ResourceID(1), windows.RT_VERSION)` 取版本资源，`VerQueryValue` 得 `VS_FIXEDFILEINFO`，把 `FileVersionMS` / `FileVersionLS` 按高低 16 位拼成点分版本字符串。注意 `RunningVersion()` 返回的是 `uint32` 运行驱动版本，与 `Version()` 返回的 DLL 文件版本字符串是两回事：前者来自 `WireGuardGetRunningDriverVersion`，后者来自 PE 资源，`tunnel/service.go` 打印的是前者并按 `(driverVersion>>16)&0xffff` 与 `driverVersion&0xffff` 拆成两段。二者不可互换使用。

### 4. 典型示例

下面这段 Go 代码集中演示本篇字段的典型读写：创建适配器拿到 `handle`，下发配置，开启日志，置为 Up，再查询 `LUID` 与运行驱动版本。所有调用名、枚举名与返回类型均取自 `driver/driver_windows.go` 与 `driver/configuration_windows.go`。

```go
func bringUp(name string, cfg *conf.Config) error {
	adapter, err := driver.CreateAdapter(name, "WireGuard", nil)
	if err != nil {
		return err
	}
	defer adapter.Close()

	interfaze, size := cfg.ToDriverConfiguration()
	if err := adapter.SetConfiguration(interfaze, size); err != nil {
		return err
	}
	if err := adapter.SetLogging(driver.AdapterLogOn); err != nil {
		return err
	}
	if err := adapter.SetAdapterState(driver.AdapterStateUp); err != nil {
		return err
	}

	luid := adapter.LUID()
	version, verErr := driver.RunningVersion()
	if verErr != nil {
		log.Printf("driver version unavailable: %v", verErr)
		return nil
	}
	log.Printf("luid=%d wireguardnt=%d.%d", luid,
		(version>>16)&0xffff, version&0xffff)
	return nil
}
```

```text
[TUN] Using WireGuardNT/0.10
[TUN] luid=1689399647805450 wireguardnt=0.10
[TUN] Startup complete
```

逐行判读如下。第一行 `[TUN] Using WireGuardNT/0.10` 对应 `tunnel/service.go` 中 `driver.RunningVersion()` 成功后的 `log.Printf("Using WireGuardNT/%d.%d", (driverVersion>>16)&0xffff, driverVersion&0xffff)`，前缀 `[TUN]` 来自 `ringlogger.InitGlobalLogger(logFile, "TUN")` 设置的标签，主次两段是把 `uint32` 版本值按高 16 位、低 16 位拆开显示；这里出现说明 `RunningVersion` 返回非零且未报错，若返回 0 则会走「Warning: unable to determine driver version」分支，不会出现该行。第二行 `luid=... wireguardnt=0.10` 来自示例代码自身的 `log.Printf`，`luid` 是 `Adapter.LUID()` 经 `WireGuardGetAdapterLUID` 回填的 `winipcfg.LUID`（本质是 `uint64`），正常应为非零的十进制大整数，若为 0 说明适配器尚未被系统分配有效 LUID，后续所有地址与路由下发都会失败；`wireguardnt=0.10` 与第一行同源，是版本值的再次打印，二者一致才说明版本查询链路稳定。第三行 `[TUN] Startup complete` 是 `tunnel/service.go` 在收到 `watcher.started` 后把服务状态置为 `svc.Running` 时打印，标志适配器已 Up、接口配置完成。异常特征方面：若看到 `Error enabling adapter logging` 或 `Error creating adapter`，分别对应 `SetLogging` 与 `CreateAdapter` 失败，应以 `services.ErrorCreateNetworkAdapter` 归类；若日志里完全缺 `Using WireGuardNT` 行，多半是 `RunningVersion` 取到 0 或 `SetLogging` 未成功开启，需回查 `procWireGuardGetRunningDriverVersion.Addr()` 是否解析成功。以上输出的具体文案、数值位数与版本段数需对照实际版本核验，路径见 `tunnel/service.go`、`driver/driver_windows.go`。

### 6. 版本差异

版本基准按总纲执行：上游 master 快照、WireGuardNT 1.1、Go 1.27.1、Windows 10 / Server 2019 及以上、amd64 / x86 / arm64 三种 MSI。就本篇字段而言，差异集中在三处。第一处是 `lazyDLL.module` 的类型分叉：`driver/dll_fromrsrc_windows.go` 带 `//go:build load_wgnt_from_rsrc`，用 `*memmod.Module` 做内存加载；`driver/dll_fromfile_windows.go` 带 `//go:build !load_wgnt_from_rsrc`，用 `windows.Handle` 从磁盘加载。`Makefile` 的 `GOFLAGS` 里含 `-tags load_wgnt_from_rsrc`，正式构建走资源版，调试或特定交叉构建可能落到文件版，读者核对字段类型前要先确认构建标签。第二处是 `setupLogger` 的回调签名按 `runtime.GOARCH` 分支：`386` 与 `arm` 把 64 位时间戳拆成 `timestampLow`、`timestampHigh` 两个 `uint32`，`amd64` / `arm64` 则直接复用 `logMessage` 签名，这与 32/64 位调用约定有关，字段本身不变但回调参数布局不同，属「需对照实际版本核验」的 ABI 细节，路径 `driver/driver_windows.go`。第三处是版本数值：`RunningVersion()` 的 `uint32` 编码、``Version()` 的点分字符串长度、`AdapterNameMax` 的 128 都可能随 WireGuardNT 版本演进，本快照只保证字段类型与枚举名，具体数值请对照 `driver/driver_windows.go`、`driver/configuration_windows.go` 与 `version/version.go` 复核。此外 `Adapter` 两个字段自 2019 年以来结构稳定，未见新增成员；若手头版本出现第三个字段，应以源码为准并标注核验，不要沿用本篇结论。

### 7. 常见误用与调试

其一，把 `Adapter` 当成配置容器。它只有 `handle` 与 `lastGetGuessSize`，任何 `PrivateKey`、`Peer`、`AllowedIP` 都不在其中，误以为 `adapter.Xxx` 能取到配置会直接编译失败；正确做法是 `Configuration()` 读回 `*driver.Interface`（字段见 05-05），或经 manager 侧 `RuntimeConfig` 转换为 `conf.Config`。其二，混淆 `AdapterState` 与服务状态。`svc.Stopped` / `svc.Running` 来自 `golang.org/x/sys/windows/svc`，`TunnelState` 来自 `manager/ipc_client.go`，三者都表达「起没起」但生命周期与写入方完全不同，排障时若把 `AdapterStateDown` 当成服务停止，会得出错误结论。其三，`SetLogging` 与 `loggerLevel` 方向搞反：前者是下发开关，后者是回传级别，关掉 `AdapterLogOff` 后再去 `logMessage` 里找分级逻辑是徒劳的。其四，忽略 `lazyProc.Addr()` 的 `panic` 语义。`Addr()` 在 `Find()` 失败时直接 `panic`，因此 DLL 缺失、导出名不匹配、资源未嵌入等问题表现为进程崩溃而非 `error` 返回，调试时应先查 `modwireguard.Load()` 与 `Name` 是否对得上，再看 `Base` 是否有效。其五，`Close` 与终结器重复释放。显式 `Close` 已撤销终结器，若又手动调 `closeAdapter` 或长期持有 `Adapter` 不释放，会出现句柄晚释放或二次释放；应坚持 `defer adapter.Close()` 单一路径。其六，`RunningVersion` 返回 0 未处理。源码里 `version == 0` 时 `err = e1` 且 `err` 可能为 nil，调用方若不判断「零值即不可用」会把 `Using WireGuardNT/0.0` 当成真实版本打印，`tunnel/service.go` 的写法是先判 `err` 再打印，值得照搬。以上排查均只针对字段读写，完整启动时序与错误码映射（原理见 06-05、原理见 06-10，字段见 05-09），配置侧开关（配置见 04-04），模块边界（模块见 07-03）。

## 05-07 `winipcfg.LUID` 与 MIB 网络配置结构字段

### 1. 本篇定位与覆盖范围

本篇是 05 册分片 B 里最贴近 Windows 网络栈的一页字典，覆盖 `tunnel/winipcfg` 包中「用什么标识一块网卡」以及「地址、路由、IP 接口参数如何以 MIB 行的形式被读写」的两组字段。理解本包的第一个前提是：Windows 的 IP Helper API 不用 `conf` 里的隧道名，也不用 `driver.Adapter` 的句柄来定位网卡，而是统一用 `LUID`（Locally Unique Identifier，本地唯一标识符）这一 64 位整数。适配器创建后，`driver.Adapter.LUID()` 取回这个值（字段见 05-06），随后所有单播地址下发、路由写入、MTU 设置、DNS 设置都以它为第一入口。本篇正是把这个「入口值」以及挂在它上面的各类 MIB 结构逐字段拆开。

覆盖范围按真实源码文件列出：`tunnel/winipcfg/luid.go` 定义 `LUID` 类型及其 `IPInterface` / `Interface` / `GUID` / `LUIDFromGUID` / `LUIDFromIndex` / `IPAddress` / `AddIPAddress` / `SetIPAddresses` / `Route` / `AddRoute` / `SetRoutes` / `DNS` / `SetDNS` / `FlushRoutes` / `FlushIPAddresses` / `FlushDNS` 等方法入口；`tunnel/winipcfg/types.go` 定义 `AddressFamily`、`IfOperStatus`、`DadState`、`PrefixOrigin`、`SuffixOrigin`、`RouteOrigin`、`RouteProtocol`、`MibNotificationType`、`ChangeCallback` 等枚举与接口，以及 `RouteData`、`RawSockaddrInet`、`IPAddressPrefix`、`MibIPforwardRow2`、`DnsInterfaceSettings` 等结构；`tunnel/winipcfg/types_64.go`（构建标签 `amd64 || arm64`）定义 `MibIPInterfaceRow`、`MibUnicastIPAddressRow`、`MibIfRow2`、`IPAdapterAddresses` 及三类 `mib*Table` 表头；`tunnel/winipcfg/types_32.go` 为 32 位对应版本；`tunnel/winipcfg/interface_change_handler.go`、`route_change_handler.go`、`unicast_address_change_handler.go` 定义三个变更回调结构。字段位置一律写这些 `.go` 路径，不确定处写「需对照实际版本核验」。

按去重铁律，本篇只讲字段含义、内存布局、生命周期与关联函数入口，不展开「AllowedIPs 如何汇总去重后写路由」「MTU 如何按默认路由推导」「DNS 如何防泄漏」等机制与调用链（原理见 06-06、原理见 06-07、原理见 06-08），也不列配置键（配置见 04-02、配置见 04-03）与模块能力（模块见 07-06）。全册交叉引用统一写作：（字段见 05-06 ｜ 配置见 04-02 ｜ 原理见 06-06 ｜ 模块见 07-06）。

### 3. 逐项详解

**① `LUID`（`uint64`）。** 定义在 `tunnel/winipcfg/luid.go`，是全包唯一的网卡主键。它不是结构体，而是 `type LUID uint64` 的命名类型，因此可以直接比较、可作 map 键、可判零；`interfacewatcher.go` 里 `iw.luid == 0` 正是用零值表示「尚未绑定到具体适配器」。方法集全部以值接收者 `func (luid LUID) ...` 定义，说明 `LUID` 被设计为可随意拷贝的标量，而非持有资源的对象。它与 `windows.GUID`、`uint32` 接口索引之间可互转：`GUID()` 走 `ConvertInterfaceLuidToGuid`，`LUIDFromGUID`、`LUIDFromIndex` 走反向转换，`SetDNS` 里就先 `luid.GUID()` 再拼注册表路径。理解 `LUID` 是「值」而非「句柄」，是读懂其余方法的前提；它由 `driver.Adapter.LUID()` 经 `WireGuardGetAdapterLUID` 回填（字段见 05-06）。

**② `RawSockaddrInet` 与 `IPAddressPrefix`。** 定义在 `tunnel/winipcfg/types.go`。`RawSockaddrInet` 只有 `Family AddressFamily` 与未导出的 `data [26]byte` 两字段，是对 Windows `SOCKADDR_INET` 联合体的定长映射：`SetAddrPort` 按 IPv4/IPv6 分别把内存重解释为 `windows.RawSockaddrInet4` / `RawSockaddrInet6` 并写 `Family`、`Addr`、`Port`、`Scope_id`，`Addr()` / `Port()` 再按 `Family` 反解。`IPAddressPrefix` 在此基础上加 `PrefixLength uint8` 与 `[2]byte` 对齐填充，构成「地址 + 掩码位数」，`SetPrefix(netip.Prefix)` 把 `netip.Prefix` 拆成地址与 `Bits()` 分别写入，`Prefix()` 反向还原。二者是 MIB 行里所有地址字段的公共底座：`MibUnicastIPAddressRow.Address`、`MibIPforwardRow2.DestinationPrefix` / `NextHop` 都依赖它们。注意 `Family` 取值是 `windows.AF_INET`(2) / `AF_INET6`(23) / `AF_UNSPEC`(0) 等 `uint16` 常量，判族时不要与 Go 的 `netip` 的 `Is4()` / `Is6()` 混用。

**③ `MibIPInterfaceRow` 的字段分组。** 这是 `MIB_IPINTERFACE_ROW` 的完整 Go 映射，定义在 `types_64.go`。可把 36 个字段按用途分四组：定位组（`Family`、`InterfaceLUID`、`InterfaceIndex`）决定「这一行描述哪块网卡的哪个地址族」；通告与路由发现组（`MinRouterAdvertisementInterval`、`MaxRouterAdvertisementInterval`、`AdvertisingEnabled`、`ForwardingEnabled`、`AdvertiseDefaultRoute`、`RouterDiscoveryBehavior`、`DadTransmits`、`BaseReachableTime`、`RetransmitTime`、`PathMTUDiscoveryTimeout`、`LinkLocalAddressBehavior`、`LinkLocalAddressTimeout`、`ReachableTime`）多为系统回读值；能力标志组（`WeakHostSend` / `WeakHostReceive`、`UseAutomaticMetric`、`UseNeighborUnreachabilityDetection`、`ManagedAddressConfigurationSupported`、`OtherStatefulConfigurationSupported`、`SupportsWakeUpPatterns`、`SupportsNeighborDiscovery`、`SupportsRouterDiscovery`、`Connected`、`TransmitOffload` / `ReceiveOffload`、`DisableDefaultRoutes`）是布尔或位域；配置组里最要紧的是 `Metric` 与 `NLMTU`——前者是接口跃点数，后者是网络层 MTU。

其中 `NLMTU` 值得单独点名：`tunnel/mtumonitor.go` 的 `monitorMTU` 在未显式配置 MTU 时，取默认路由接口 MTU 减 80，赋给 `iface.NLMTU` 后调用 `iface.Set()` 生效；`Set()` 只是 `setIPInterfaceEntry(row)` 的包装，字段写入和 API 调用是分开的两步，因此「改了 `NLMTU` 却没 `Set()`」不会有任何效果。`SitePrefixLength` 也有特殊处理：`types.go` 的 `get()` 里针对 `AF_INET` 超过 32、针对 `AF_INET6` 超过 128 做了修正，这是绕开 Windows 已知问题的补丁，属于字段级语义而非流程（原理见 06-07）。`Init()` 调用 `initializeIPInterfaceEntry` 填默认值，`IPInterface(family)` 则先 `Init()` 再写 `InterfaceLUID` 与 `Family` 后 `get()`，是取一行的标准入口。

**④ `MibUnicastIPAddressRow` 的 11 个字段。** 定义在 `types_64.go`，对应 `MIB_UNICASTIPADDRESS_ROW`。`Address`（`RawSockaddrInet`）与 `InterfaceLUID` 是定位键；`PrefixOrigin` / `SuffixOrigin` / `DadState` / `ScopeID` / `CreationTimeStamp` 为系统回读的状态元数据；`ValidLifetime` / `PreferredLifetime` / `OnLinkPrefixLength` / `SkipAsSource` 为可配置项。`luid.go` 的 `AddIPAddress` 展示了典型写入：`row.Init()` 后写 `InterfaceLUID`，把 `DadState` 置 `DadStatePreferred`、两个 Lifetime 置 `0xffffffff`（永久）、`Address.SetAddr(address.Addr())`、`OnLinkPrefixLength = uint8(address.Bits())`，最后 `row.Create()`。`DadState` 取 `DadStatePreferred`(4) 表示地址已通过重复地址检测可用；`SetIPAddresses` 系列方法先 `FlushIPAddresses` 再 `AddIPAddresses`，因此这些字段的生命周期是「被整体替换」而非「就地改」。判读日志或转储时，若 `DadState` 停在 `DadStateTentative`(1) 或 `DadStateDuplicate`(2)，说明地址未就绪。

**⑤ `MibIPforwardRow2` 的 15 个字段。** 定义在 `types.go`，对应 `MIB_IPFORWARD_ROW2`。定位与寻址字段为 `InterfaceLUID`、`InterfaceIndex`、`DestinationPrefix`（`IPAddressPrefix`）、`NextHop`（`RawSockaddrInet`）、`SitePrefixLength`；可写项为 `ValidLifetime`、`PreferredLifetime`、`Metric`；只读元数据为 `Protocol`（`RouteProtocol`）、`Loopback`、`AutoconfigureAddress`、`Publish`、`Immortal`、`Age`、`Origin`（`RouteOrigin`）。`AddRoute(destination, nextHop, metric)` 把 `RouteData` 的三个字段分别灌入 `DestinationPrefix.SetPrefix`、`NextHop.SetAddr`、`Metric` 再 `Create()`；`Route()` 读一行时会把两个 Lifetime 置 `0xffffffff`。`DestinationPrefix.PrefixLength == 0` 表示默认路由，`mtumonitor.go` 的 `findDefaultLUID` 与 `monitorMTU` 的路由变更回调正是用这个字段筛默认路由，属字段判据，机制不在此展开（原理见 06-06、原理见 06-07）。

**⑥ `RouteData` 与 `DnsInterfaceSettings`。** `RouteData` 是 `tunnel/winipcfg/types.go` 里极简的 Go 侧结构：`Destination netip.Prefix`、`NextHop netip.Addr`、`Metric uint32`，它的 `String()` 用 `%+v` 打印，便于日志。`DnsInterfaceSettings` 则是给 `SetInterfaceDnsSettings` 用的结构体，`Version` 由 `SetDNS` 置 `DnsInterfaceSettingsVersion1`，`Flags` 拼 `DnsInterfaceSettingsFlagNameserver | DnsInterfaceSettingsFlagSearchList`，IPv6 时再或上 `DnsInterfaceSettingsFlagIPv6`，`NameServer` / `SearchList` 为 UTF-16 逗号分隔串。二者都是「输入型」字段集合，不是从系统回读的 MIB 行，方向不要弄反。

**⑦ 三类变更回调结构与 `ChangeCallback` 接口。** `ChangeCallback` 定义在 `types.go`，只有 `Unregister() error` 一个方法，是三个具体回调结构的公共契约。`InterfaceChangeCallback`（`interface_change_handler.go`）、`RouteChangeCallback`（`route_change_handler.go`）、`UnicastAddressChangeCallback`（`unicast_address_change_handler.go`）形状完全一致：一个 `cb` 函数字段保存用户回调，一个 `wait sync.WaitGroup` 跟踪在飞回调。三者各自配一套包级全局 `map[*XxxCallback]bool`、两把 `sync.Mutex`、一个 `windows.Handle` 通知句柄。`cb` 的签名随行类型不同：接口回调收 `*MibIPInterfaceRow`、路由回调收 `*MibIPforwardRow2`、单播回调收 `*MibUnicastIPAddressRow`，且第一个参数都是 `MibNotificationType`。`Unregister` 先 `wait.Wait()` 再在最后一个回调注销时 `cancelMibChangeNotify2`，`wait` 字段正是为避免「回调还在跑就被释放」而存在。`interfacewatcher.go` 的 `interfaceWatcher` 把这些回调存进 `changeCallbacks4` / `changeCallbacks6` 切片（字段见 05-08），本篇不再展开。

**⑧ 三类表头结构的 `numEntries`。** `mibIPInterfaceTable`、`mibUnicastIPAddressTable`、`mibIPforwardTable2` 都定义在 `types_64.go`，形状统一为 `numEntries uint32` + `table [anySize]T`（`anySize = 1`）。`get()` 用 `unsafe.Slice(&tab.table[0], tab.numEntries)` 把系统返回的连续内存切成 Go 切片，`flush` 类方法据此遍历并逐行 `Delete()`。`numEntries` 是「系统回填、Go 侧只读」的字段，把它当容量自行改写会直接越界，属典型误用。

**⑨ 作为字段类型的枚举与接口补遗。** `winipcfg` 里大量字段的类型不是 Go 基础类型，而是 `tunnel/winipcfg/types.go` 顶部定义的命名枚举，随查时容易只盯着结构名而忽略这些类型本身的取值范围，故在此集中补列。`AddressFamily uint16` 是 `windows.AF_*` 常量族，出现在 `MibIPInterfaceRow.Family`、`MibUnicastIPAddressRow.Address.Family`、`MibIPforwardRow2.DestinationPrefix.RawPrefix.Family` 以及所有 `LUID` 方法的 `family` 入参，本包内被显式分支处理的只有 `AF_UNSPEC`、`AF_INET`、`AF_INET6` 三者。`IfOperStatus uint32` 是 `IfOperStatusUp` 到 `IfOperStatusLowerLayerDown` 的七态枚举，`MibIfRow2.OperStatus` 与 `findDefaultLUID` 里的 `ifrow.OperStatus != winipcfg.IfOperStatusUp` 判据都用它，只有 Up 态的默认路由接口才参与 MTU 推导。`DadState uint32` 五态、`PrefixOrigin uint32` 与 `SuffixOrigin uint32` 各带 `Unchanged = 1 << 4` 标志、`RouteOrigin uint32` 六态、`RouteProtocol uint32` 含 `RouteProtocolNTAutostatic` 等 Windows 专用值，分别是 `MibUnicastIPAddressRow` 与 `MibIPforwardRow2` 里那些元数据字段的类型，判读转储时应回查 `types.go` 的常量表而不是猜数值。

`MibNotificationType uint32` 四值（`MibParameterNotification`、`MibAddInstance`、`MibDeleteInstance`、`MibInitialNotification`）是三类回调 `cb` 的第一个参数，`interfacewatcher.go` 只处理 `MibAddInstance`、`mtumonitor.go` 只处理 `MibParameterNotification`，可见同一枚举在不同调用方只用到子集。`ChangeCallback` 接口只有 `Unregister() error`，是 `interfaceWatcher` 里 `interfaceChangeCallback`、`changeCallbacks4`、`changeCallbacks6` 三处字段的声明类型，多态地承载三种具体结构。`GAAFlags uint32` 与 `ScopeLevel uint32` 则分别服务于 `GetAdaptersAddresses` 调用参数与 `MibIPInterfaceRow.ZoneIndices` 的数组长度（`ScopeLevelCount = 16`）。`OffloadRod uint8`、`InterfaceAndOperStatusFlags uint8`、`TunnelType uint32`、`NdisMedium` / `NdisPhysicalMedium` / `NetIfAccessType` / `NetIfAdminStatus` / `NetIfConnectionType` / `NetIfDirectionType` / `NetIfMediaConnectState` 等类型共同构成 `MibIfRow2` 的字段类型面板，它们是 Windows SDK 枚举的 Go 镜像，字段名固定、数值由 SDK 定义，属「需对照实际版本核验」的一类，路径 `tunnel/winipcfg/types.go`、`types_64.go`。把这些类型与第 2 节字段表对照阅读，才能在看到 `Protocol=...`、`OperStatus=...` 之类转储值时立刻定位到对应字段与含义，而不必反复翻源码。

**⑩ `MibIfRow2` 与 `IPAdapterAddresses` 的字段补遗。** 这两类结构同样定义在 `tunnel/winipcfg/types_64.go`，虽不是本篇三张 MIB 行表的主体，却是 `LUID.Interface()` 与 `LUID.DNS()` 的实际返回类型，随查时会一并遇到。`MibIfRow2` 以 `InterfaceLUID`、`InterfaceIndex`、`InterfaceGUID`、`alias [ifMaxStringSize+1]uint16`、`description`、`physicalAddress` / `permanentPhysicalAddress`、`MTU`、`Type`、`TunnelType`、`MediaType`、`PhysicalMediumType`、`AccessType`、`DirectionType`、`InterfaceAndOperStatusFlags`、`OperStatus`、`AdminStatus`、`MediaConnectState`、`NetworkGUID`、`ConnectionType` 开头，后接 `TransmitLinkSpeed`、`ReceiveLinkSpeed` 与成组的 `InOctets` / `InUcastPkts` / `OutOctets` / `OutErrors` / `OutQLen` 等统计计数器；它们全部是系统回读值，`Alias()` / `Description()` / `PhysicalAddress()` / `PermanentPhysicalAddress()` 四个方法只是把定长数组转成 Go 字符串或切片。`IPAdapterAddresses` 则更宽，含 `Length`、`IfIndex`、`Next`、各 `First*` 链表指针、`Flags`、`MTU`、`IfType`、`OperStatus`、`ZoneIndices [16]uint32`、`LUID`、`NetworkGUID`、`ConnectionType`、`TunnelType`、`FirstDNSSuffix` 等，`LUID.DNS()` 正是靠它的 `LUID` 与 `FirstDNSServerAddress` 字段筛出本机 DNS 服务器。二者字段多但方向单一：只读快照，不含任何写入口，改它们不会影响系统，要生效必须回到 `MibIPInterfaceRow.Set()` 或 `LUID.AddIPAddress` 一类入口。

**⑪ `LUID` 方法族对应的字段读写方向。** `tunnel/winipcfg/luid.go` 的方法虽多，落到字段层面只有三类，随查时按方向归类比逐个记更快。第一类是「构造行并回读」：`IPInterface(family)` 造 `MibIPInterfaceRow`、`Interface()` 造 `MibIfRow2`、`IPAddress(addr)` 造 `MibUnicastIPAddressRow`、`Route(destination, nextHop)` 造 `MibIPforwardRow2`，四者都先给 `InterfaceLUID` 赋值再 `get()`，返回的指针里除定位字段外全是系统回填值。第二类是「构造行并写入」：`AddIPAddress` 写 `DadState`、`ValidLifetime`、`PreferredLifetime`、`OnLinkPrefixLength` 后 `Create()`，`AddRoute` 写 `DestinationPrefix`、`NextHop`、`Metric` 后 `Create()`，`SetDNS` 拼 `DnsInterfaceSettings.Version` / `Flags` / `NameServer` / `SearchList`，这几组字段是 Go 侧唯一主动填值的地方。第三类是「按表删行」：`FlushIPAddresses` / `FlushRoutes` / `FlushDNS` 借 `mib*Table.numEntries` 与 `get()` 切片遍历，逐行 `Delete()`，不改写任何行字段。`SetIPAddresses`、`SetRoutes` 则是「先 Flush 再 Add」的组合，本身不引入新字段。把这三类与第 2 节表对照，就能回答「某个字段到底由谁写、什么时候读」，而不必把每个方法都跟一遍调用链（原理见 06-06）。

### 4. 典型示例

下面这段 Go 代码演示 `LUID` 方法如何把 `netip.Prefix`、`RouteData` 落到 MIB 行字段，并回读 `MibIPInterfaceRow` 改写 `NLMTU`。所有调用名、字段名与类型均取自 `luid.go`、`types.go`、`types_64.go`。

```go
func configure(luid winipcfg.LUID, family winipcfg.AddressFamily, addr netip.Prefix) error {
	if err := luid.SetIPAddressesForFamily(family, []netip.Prefix{addr}); err != nil {
		return err
	}
	routes := []*winipcfg.RouteData{
		{
			Destination: netip.MustParsePrefix("10.0.0.0/8"),
			NextHop:     netip.IPv4Unspecified(),
			Metric:      0,
		},
	}
	if err := luid.SetRoutesForFamily(family, routes); err != nil {
		return err
	}
	iface, err := luid.IPInterface(family)
	if err != nil {
		return err
	}
	iface.NLMTU = 1420
	return iface.Set()
}
```

示例输出，具体格式需对照实际版本核验：

```text

NLMTU=1420 Metric=0 SitePrefixLength=0
DadState=4 OnLinkPrefixLength=24 SkipAsSource=false
DestinationPrefix=10.0.0.0/8 NextHop=0.0.0.0 Metric=0
```

逐行判读如下。第一行 `Family=2` 对应 `AddressFamily` 取值 `windows.AF_INET`，若是 IPv6 应为 `AF_INET6`；`InterfaceLUID` 是与 `driver.Adapter.LUID()` 同源的 64 位十进制值，正常应为非零大整数，为 0 表示尚未绑定适配器；`InterfaceIndex` 是系统分配的接口索引，随每次适配器创建变化，不能写死。第二行 `NLMTU=1420` 是示例代码中 `iface.NLMTU = 1420` 经 `Set()` 生效后的回读值，未显式配 MTU 时它应等于「默认路由接口 MTU − 80」且不小于下限；`Metric=0` 表示该接口未叠加额外跃点；`SitePrefixLength=0` 符合 IPv4 常见值，若 IPv4 下出现大于 32 或 IPv6 下大于 128，说明 `get()` 里的修正补丁未生效。第三行 `DadState=4` 即 `DadStatePreferred`，证明 `AddIPAddress` 已把单播地址置为可用态，若停在 1（Tentative）或 2（Duplicate）则地址尚未就绪；`OnLinkPrefixLength=24` 与传入的 `/24` 前缀一致；`SkipAsSource=false` 为默认。第四行 `DestinationPrefix=10.0.0.0/8` 与 `NextHop=0.0.0.0` 来自 `RouteData` 经 `SetPrefix` / `SetAddr` 写入的 `MibIPforwardRow2` 字段，`PrefixLength` 为 8，非 0 说明这是普通网段路由而非默认路由；`Metric=0` 与 `RouteData.Metric` 一致。异常特征：若 `NextHop` 族与 `Family` 不匹配、或 `PrefixLength` 异常为 0，应回查 `SetPrefix` / `SetAddr` 是否被误用。以上字段名与数值口径以本快照为准，实际打印格式、具体位数需对照实际版本核验，路径见 `tunnel/winipcfg/types.go`、`types_64.go`、`luid.go`。

### 6. 版本差异

版本基准同总纲：上游 master 快照、WireGuardNT 1.1、Go 1.27.1、Windows 10 / Server 2019 及以上、amd64 / x86 / arm64 三种 MSI。本篇字段差异主要有三处。第一处是 `types_64.go` 与 `types_32.go` 的构建标签分叉：前者 `//go:build amd64 || arm64`，后者服务 32 位构建；两者结构体字段集合大体一致，但含指针的布局、对齐填充（如 `IPAdapterWINSServerAddress` 的 `_ uint32`）不同，`MibIPInterfaceRow`、`MibUnicastIPAddressRow` 的字段顺序与 `bool` 内存宽度需按架构核对，跨架构比对转储时尤其要注意，路径 `tunnel/winipcfg/types_32.go`。第二处是 `SetDNS` 的双路径：`DnsInterfaceSettings` 与 `DnsInterfaceSettingsVersion1` 仅用于 Windows 10 1809 及以上的 `SetInterfaceDnsSettings`，更老系统退回注册表 `NameServer` / `SearchList` 与 `dnscache` 服务 `ParamChange`，因此 `Version`、`Flags` 等字段在不同系统上「是否真正被使用」不同，属需对照实际版本核验的行为差异，路径 `tunnel/winipcfg/luid.go`。第三处是 `netip` 的引入：`RouteData` 用 `netip.Prefix` / `netip.Addr` 而非老的 `net.IP`，`SetAddrPort`、`Prefix()` 等辅助方法随 Go 版本演进，具体行为以所抓快照的 Go 1.27.1 为准。此外 `anySize = 1`、`maxDNSSuffixStringLength = 256`、`ifMaxStringSize = 256`、`ifMaxPhysAddressLength = 32` 等常量定义在 `types.go` 顶部，若手头版本数值不同请以源码为准并标注核验，不要照抄本篇口径。

### 7. 常见误用与调试

其一，把 `LUID` 当句柄释放。`LUID` 是 `uint64` 值类型，没有 `Close`，也不由 GC 管理；真正需要 `Close` 的是 `driver.Adapter`（字段见 05-06），二者生命周期不同，混用会导致「适配器关了但 LUID 还在被写」或反之。其二，认为 `MibIPInterfaceRow` 改字段即生效。所有 `Set()` 都是显式调用，改 `NLMTU`、`Metric`、`DisableDefaultRoutes` 后不 `Set()` 等于没改，这是 MTU 排障里最常见的疏漏。其三，把 `Family` 与 `netip` 的 `Is4()` / `Is6()` 混为一谈：`AddressFamily` 是 `uint16` 的 `windows.AF_*` 常量，判族要用常量或 `SetIPAddressesForFamily` 里的显式比较，族错会让 `SetAddr` 把 IPv4 地址按 IPv6 布局写入 `data [26]byte`。其四，误改 `numEntries`。表头 `numEntries` 由系统回填，`get()` 直接据此 `unsafe.Slice`，任何 Go 侧写入都可能造成越界读，遍历时应只读。其五，忽略 `wait` 字段导致回调竞态：三个 `XxxCallback` 的 `Unregister` 依赖 `wait.Wait()` 等待在飞 `cb`，若自定义回调里长时间阻塞或忘记让 goroutine 退出，注销会卡死；`interfacewatcher.go` 的 `Destroy` 正是在持锁与解锁之间批量 `Unregister`（字段见 05-08）。其六，把 `DestinationPrefix.PrefixLength == 0` 当成「无效路由」。它恰是默认路由标志，`monitorMTU` 的回调据此筛选，`findDefaultLUID` 也靠它跳过非默认路由，误判会让 MTU 监控失效。其七，混淆「输入结构」与「回读行」：`RouteData` / `DnsInterfaceSettings` 是 Go 侧拼装的输入，`MibIPforwardRow2` / `MibUnicastIPAddressRow` 是与系统交互的行，方向搞反会写出永远不生效的代码。以上只针对字段读写，完整地址与路由下发顺序（原理见 06-06）、MTU 推导链（原理见 06-07）、DNS 处理（原理见 06-08）、配置键（配置见 04-02、配置见 04-03）、模块边界（模块见 07-06）。

### 3. 逐项详解

**① `tunnelService.Path`（`string`）。** 这是全篇最简单的结构：`tunnel/service.go` 里 `type tunnelService struct { Path string }` 只有一个字段。`Run(confPath string)` 先由 `conf.NameFromPath` / `conf.ServiceNameOfTunnel` 推出服务名，再 `svc.Run(serviceName, &tunnelService{confPath})` 把配置路径塞进 `Path`；`Execute` 里用 `conf.LoadFromPath(service.Path)` 读回 `conf.Config`（字段见 05-02）。它的语义是「配置在哪」，不是「配置是什么」，也不是服务名——服务名由 `conf.ServiceNameOfTunnel` 另行推导。生命周期与 `svc.Run` 一致，进程存活期只读。把 `Path` 当成可写配置或当成隧道名，是读这段代码时最常见的偏差。

**② `interfaceWatcherError` 与 `interfaceWatcherEvent`。** 两个小结构定义在 `interfacewatcher.go`。`interfaceWatcherError` 把 `services.Error`（枚举，字段见 05-09）与原始 `error` 成对打包，使 `Execute` 的 `defer` 既能 `services.DetermineErrorCode` 定退出码，又能 `services.CombineErrors` 拼日志。`interfaceWatcherEvent` 把 `winipcfg.LUID` 与 `winipcfg.AddressFamily` 打包，用于「适配器 LUID 还没确定时先把接口新增事件存起来」。两者都是纯值载体，无方法、无锁，字段在构造时一次写入。

**③ `interfaceWatcher` 的通道字段。** `errors` 为 `chan interfaceWatcherError`、`started` 为 `chan winipcfg.AddressFamily`，二者在 `watchInterface()` 里用 `make(chan interfaceWatcherError, 2)` 与 `make(chan winipcfg.AddressFamily, 4)` 建立，缓冲大小是硬编码常量。`errors` 承载 `setup` 阶段失败与 `watchdog` 超时，`tunnelService.Execute` 的 `select` 里 `case e := <-watcher.errors:` 取出后直接 `serviceError, err = e.serviceError, e.err` 并退出；`started` 由 `setup` 在成功配置完某地址族后写入，`Execute` 收到第一次就把服务状态置 `svc.Running` 并打印 `Startup complete`。缓冲 2 与 4 保证在 `Execute` 尚未进入 `select` 时回调不阻塞，属字段级容错设计（原理见 06-05，本篇不展开时序）。

**④ `interfaceWatcher` 的绑定字段：`conf`、`adapter`、`luid`。** 三个字段在 `watchInterface()` 里都是零值，直到 `Configure(adapter *driver.Adapter, conf *conf.Config, luid winipcfg.LUID)` 才一次性赋值 `iw.adapter, iw.conf, iw.luid = adapter, conf, luid`。其中 `luid == 0` 是重要哨兵：`watchInterface` 注册的接口变更回调里，若 `iw.luid == 0`，只把事件追加进 `storedEvents` 而不立即 `setup`；待 `Configure` 绑定真实 LUID 后，才遍历 `storedEvents` 挑出 `event.luid == luid` 的补做 `setup`，随后 `iw.storedEvents = nil`。`conf` 与 `adapter` 供回调里 `AdapterState()` 判断为 Down 时重新 `SetConfiguration` / `SetAdapterState`（字段见 05-06）。三者均为指针或值，绑定后只读。

**⑤ `interfaceWatcher` 的锁与回调集合。** `setupMutex sync.Mutex` 保护 `setup`、`Configure`、`Destroy` 与接口变更回调之间的并发，几乎所有字段读写都在持锁区间。`interfaceChangeCallback winipcfg.ChangeCallback` 是主回调，注册于 `watchInterface`，在 `Destroy` 里 `Unregister`。`changeCallbacks4` / `changeCallbacks6` 是 `[]winipcfg.ChangeCallback` 切片，`setup(family)` 按 `family == windows.AF_INET` / `AF_INET6` 选中其中一个，先逐个 `Unregister` 旧回调再重建：当 `conf.Interface.MTU == 0` 时调 `monitorMTU(family, iw.luid)` 得到两个回调（路由变更与接口变更），否则不监控。`Destroy` 会把三组回调在解锁后统一注销，并逐一切掉切片头部，避免并发下重复 `Unregister`。这里 `winipcfg.ChangeCallback` 是接口（字段见 05-07），切片里实际装的是 `*RouteChangeCallback` / `*InterfaceChangeCallback` 等具体结构。

**⑥ `interfaceWatcher.watchdog`（`*time.Timer`）。** 在 `watchInterface()` 里用 `time.AfterFunc(time.Duration(1<<63-1), ...)` 建立并立刻 `Stop()`，回调内容是向 `errors` 写入 `services.ErrorCreateNetworkAdapter` 与「TCP/IP interface for adapter did not appear after one minute」错误；`Configure` 里 `iw.watchdog.Reset(time.Minute)` 才真正启动一分钟计时，`Destroy` 里再 `Stop()`。它是「接口长时间不出现」的兜底，字段类型是 `*time.Timer` 而非 `time.Time`，读写都要走 `Reset` / `Stop`，不要当普通时间戳用。

**⑦ `mtumonitor.go` 的局部状态字段。** `monitorMTU` 内部声明 `minMTU int`（IPv4 取 576、IPv6 取 1280）、`lastLUID winipcfg.LUID`、`lastIndex ^uint32(0)`、`lastMTU uint32(0)`、`mu sync.Mutex` 与闭包 `doIt`。`findDefaultLUID(family, ourLUID, lastLUID, lastIndex)` 用 `GetIPForwardTable2` 遍历 `MibIPforwardRow2`，以 `DestinationPrefix.PrefixLength != 0` 跳过非默认路由、以 `InterfaceLUID == ourLUID` 跳过本隧道，`combinedMetric = uint64(r[i].Metric) + uint64(iface.Metric)` 选最小者回写 `lastLUID` / `lastIndex`。`doIt` 在 `mtu > 0 && lastMTU != mtu` 时取 `ourLUID.IPInterface(family)`，置 `iface.NLMTU = uint32(max(int(mtu)-80, minMTU))` 后 `iface.Set()` 并回写 `lastMTU`。这些是闭包捕获的局部字段，不是结构体成员，但字段语义与 05-07 的 `MibIPInterfaceRow.NLMTU`、`MibIPforwardRow2.Metric` 直接对应（原理见 06-07，本篇不展开链路）。

**⑧ WFP 基础对象与会话字段。** `baseObjects` 只有 `provider windows.GUID` 与 `filters windows.GUID` 两个字段，在 `registerBaseObjects` 里各由 `windows.GenerateGUID()` 随机生成，前者作 `wtFwpmProvider0.providerKey`，后者作 `wtFwpmSublayer0.subLayerKey` 并被所有规则的 `subLayerKey` 指向。`wfpSession uintptr` 是包级全局，保存 `fwpmEngineOpen0` 返回的会话句柄，`EnableFirewall` 成功事务后写入，`DisableFirewall` 里 `fwpmEngineClose0(wfpSession)` 并清零；`EnableFirewall` 开头 `if wfpSession != 0` 即报「already been enabled」，说明它是单例哨兵。`wtFwpmSession0` 的 `flags` 置 `cFWPM_SESSION_FLAG_DYNAMIC`，使规则在会话关闭时自动清除，这正是「无需持久化、随服务退出即失效」的字段依据。`wtFwpmSublayer0.weight` 置 `^uint16(0)`（最大），保证本子层优先于系统默认子层被评估。

**⑨ `wtFwpmFilter0` 的规则字段。** 定义在 `types_windows_64.go`，是 WFP 规则主体。装配模式高度一致：每个 `permit*` / `block*` 函数先构造一个 `filter` 变量，填 `providerKey`、`subLayerKey`、`weight`、`numFilterConditions`、`filterCondition`、`action`，再循环改写 `displayData` 与 `layerKey` 对四个 ALE 层各 `fwpmFilterAdd0` 一次。`layerKey` 取 `cFWPM_LAYER_ALE_AUTH_CONNECT_V4` / `ALE_AUTH_RECV_ACCEPT_V4` / `..._V6` 等 GUID；`action._type` 取 `cFWP_ACTION_PERMIT` 或 `cFWP_ACTION_BLOCK`。`weight` 是 `wtFwpValue0` 而非裸整数，由 `filterWeight(weight uint8)` 转换；`blocker.go` 里实参依次为 15（service）、15/14（DNS allow/deny）、13（loopback）、12（tun/DHCP/NDP）、0（blockAll），数值越大越先命中，故「放行规则权重高于阻断」是 kill-switch 成立的字段前提。`.offset1 [4]byte` 是 64 位特有的布局校正字段，恒为零，不参与语义；`.filterID` 与 `.effectiveWeight` 由系统回填。

**⑩ `wtFwpmFilterCondition0` 与 `wtFwpValue0`。** 条件结构定义在 `types_windows.go`，三个字段：`fieldKey windows.GUID`（如 `cFWPM_CONDITION_IP_LOCAL_INTERFACE`、`cFWPM_CONDITION_IP_REMOTE_PORT`）、`matchType wtFwpMatchType`（`cFWP_MATCH_EQUAL`、`cFWP_MATCH_FLAGS_ALL_SET` 等）、`conditionValue wtFwpConditionValue0`（即 `wtFwpValue0` 的别名）。`wtFwpValue0` 的 `_type wtFwpDataType` 决定 `value uintptr` 怎么解释：标量类型（`cFWP_UINT8` / `UINT16` / `UINT32` / `UINT64`）时 `value` 直接存数值，如端口 53、协议 17；复合类型（`cFWP_BYTE_ARRAY16_TYPE` / `cFWP_V6_ADDR_MASK` / `cFWP_BYTE_BLOB_TYPE` / `cFWP_SECURITY_DESCRIPTOR_TYPE`）时 `value` 存的是指向数据的指针，并用 `runtime.KeepAlive` 保活。把 `value` 一律当整数读，是判读规则时最易犯的错。`wtFwpByteBlob` 的 `size uint32` + `data *uint8` 正是复合值的典型载体，如 `permitWireGuardService` 把进程安全描述符长度与指针填进去。`rules.go` 的 `filterDefinition` 把 `displayData`、`conditions`、`layer` 三字段打包成 `defs` 切片，供 `permitNdp` 批量下规则。

**⑪ WFP 侧其余枚举、GUID 与尺寸常量补遗。** 除第 2 节已列的结构外，`tunnel/firewall/types_windows.go` 还定义了一批作为字段类型或字段取值来源的常量，随查规则时同样需要对照。`wtFwpmFilterFlags uint32` 是 `wtFwpmFilter0.flags` 的类型，取值含 `cFWPM_FILTER_FLAG_NONE`、`cFWPM_FILTER_FLAG_PERSISTENT`、`cFWPM_FILTER_FLAG_BOOTTIME`、`cFWPM_FILTER_FLAG_CLEAR_ACTION_RIGHT`、`cFWPM_FILTER_FLAG_DISABLED` 等，本仓库里 `permitWireGuardService` 显式置 `cFWPM_FILTER_FLAG_CLEAR_ACTION_RIGHT` 以清除硬允许权，其余规则多留零值。`wtFwpActionFlag uint32` 的 `cFWP_ACTION_FLAG_TERMINATING`、`cFWP_ACTION_FLAG_NON_TERMINATING`、`cFWP_ACTION_FLAG_CALLOUT` 三个位与 `cFWP_ACTION_BLOCK` / `cFWP_ACTION_PERMIT` 组合成 `wtFwpActionType`，所以 `wtFwpmAction0._type` 的数值并非简单的 1 或 2，而是带终止位的复合值，判读时不要按裸整数理解。`wtFwpMatchType uint32` 从 `cFWP_MATCH_EQUAL` 到 `cFWP_MATCH_TYPE_MAX` 共十余档，`wtFwpDataType uint` 从 `cFWP_EMPTY` 到 `cFWP_DATA_TYPE_MAX` 定义了 `value` 的解释方式，二者共同构成 `wtFwpmFilterCondition0` 的字段语义。`wtIPProto uint32` 给出 `cIPPROTO_ICMP`(1)、`cIPPROTO_TCP`(6)、`cIPPROTO_UDP`(17)、`cIPPROTO_ICMPV6`(58)，是各 permit 规则里 `conditionValue.value` 的常用标量值。`wtFwpmFlags uint32` 的 `cFWP_CONDITION_FLAG_IS_LOOPBACK`、`wtFwpmL2Flags uint32` 的 `cFWP_CONDITION_L2_IS_VM2VM`、`wtRpcCAuthN uint32` 的 `cRPC_C_AUTHN_WINNT`(10) 分别服务于 loopback 放行、Hyper-V 放行与 `fwpmEngineOpen0` 的认证方式。

另一类常量是 `tunnel/firewall/types_windows_64.go` 里的 `*_Size` 与 `*_Offset` 族：如 `wtFwpmFilter0_Size = 200`、`wtFwpmFilterCondition0_Size = 40`、`wtFwpConditionValue0_Size = 16`、`wtFwpmSession0_Size = 72`、`wtFwpmSublayer0_Size = 72`、`wtFwpProvider0_Size = 64`，以及 `wtFwpmFilter0_layerKey_Offset = 64`、`wtFwpmFilter0_action_Offset = 128` 等偏移。它们不是结构体字段，而是「按偏移量手工定位成员」的辅助常量，供 `helpers.go` 里基于 `unsafe` 的封装校验布局使用；`anysizeArray = 1`、`wtFwpBitmapArray64_Size = 8`、`wtFwpByteArray16_Size = 16`、`wtFwpByteArray6_Size = 6`、`wtFwpV4AddrAndMask_Size = 8`、`wtFwpV6AddrAndMask_Size = 17` 同属一组。这些数值与 32 位版本一一对应但不同，属「需对照实际版本核验」的布局事实，路径 `tunnel/firewall/types_windows_64.go`、`types_windows_32.go`。最后，所有 `cFWPM_LAYER_*`、`cFWPM_CONDITION_*` 都是 `windows.GUID` 类型的包级变量而非结构体字段，它们作为 `wtFwpmFilter0.layerKey` 与 `wtFwpmFilterCondition0.fieldKey` 的取值来源，GUID 的 `Data1` 到 `Data4` 在源码里逐字节写死，跨版本基本稳定，引用时应直接点名常量而非复制十六进制字面量。

**⑫ 显示数据、字节数组与布局填充字段补遗。** `wtFwpmDisplayData0` 的 `name *uint16` 与 `description *uint16` 由 `createWtFwpmDisplayData0` 从 Go 字符串转 UTF-16 后填入，出现在 `wtFwpmFilter0.displayData`、`wtFwpmSession0.displayData`、`wtFwpmSublayer0.displayData`、`wtFwpmProvider0.displayData` 四处，是结构里唯一带可读文字的字段，排障时按 `name` 反查规则来源最有效。`tunnel/firewall/types_windows.go` 里还并列定义了 `wtFwpProvider0` 与 `wtFwpmProvider0` 两个字段集合完全相同的结构（`providerKey`、`displayData`、`flags`、`providerData`、`serviceName`），`registerBaseObjects` 实际装配的是 `wtFwpmProvider0`，读源码时若只搜到前者容易误判字段归属，这是命名层面的坑而非语义差异。`wtFwpByteArray6`、`wtFwpByteArray16`、`wtFwpBitmapArray64` 分别是 `[6]uint8`、`[16]uint8`、`[8]uint8` 的单字段包装，用来承载 MAC、IPv6 地址与 64 位位图；`rules.go` 顶部的 `linkLocal`、`linkLocalDHCPMulticast` 等包级变量就是它们的实例，作为 `conditionValue.value` 指向的数据。`wtFwpmFilter0.offset1 [4]byte` 在 `types_windows_64.go` 里被注释为布局校正字段，纯为对齐 64 位 `action` 与后续 GUID 而存在，恒为零、不参与任何规则语义，手工构造结构时保留即可，切勿往里写值。这些字段与第 2 节表合看，才能把「WFP 结构里哪些字段有语义、哪些只是对齐或显示」分清楚。

### 4. 典型示例

下面这段 Go 代码演示 `interfaceWatcher` 通道与绑定字段的读写，节选自 `tunnel/service.go` 与 `tunnel/interfacewatcher.go` 的同包调用形态。

```go
func wireUpWatcher(adapter *driver.Adapter, cfg *conf.Config, luid winipcfg.LUID) error {
	watcher, err := watchInterface()
	if err != nil {
		return err
	}
	watcher.Configure(adapter, cfg, luid)
	select {
	case family := <-watcher.started:
		log.Printf("interface up for family=%d", family)
	case e := <-watcher.errors:
		return fmt.Errorf("%v: %w", e.serviceError, e.err)
	}
	return nil
}
```

```text
[TUN] Watching network interfaces
[TUN] Setting device v4 addresses
[TUN] interface up for family=2

```

逐行判读如下。第一行 `[TUN] Watching network interfaces` 出现在 `tunnel/service.go` 调 `watchInterface()` 之前，说明 `interfaceWatcher` 的 `errors`、`started` 通道与 `interfaceChangeCallback` 即将建立，若此行之后长期无后续输出，应怀疑 `watchdog` 是否在一分钟后触发 `services.ErrorCreateNetworkAdapter`。第二行 `[TUN] Setting device v4 addresses` 来自 `interfacewatcher.go` 的 `setup`，`ipversion` 为 `v4` 表示本次处理 `family == windows.AF_INET`，即 `changeCallbacks4` 分支被选中；若只有 v4 没有 v6，通常是配置里没有 IPv6 地址而非故障。第三行 `[TUN] interface up for family=2` 是示例代码从 `watcher.started` 通道读到的 `winipcfg.AddressFamily`，数值 2 对应 `windows.AF_INET`，若读到 23 则对应 `AF_INET6`；能读到值说明 `setup` 已成功完成 `configureInterface` 并向 `started` 写入，反之若走 `watcher.errors` 分支，会得到 `interfaceWatcherError.serviceError` 与 `err` 拼出的错误。第四行 `[TUN] Startup complete` 来自 `Execute` 收到 `started` 后把服务置 `svc.Running`，标志三条字段线（绑定、地址、回调）都已就绪。异常特征：若 `family` 打印为 0（`AF_UNSPEC`），说明 `setup` 被未知族调用，应回查 `interfaceWatcherEvent.family` 的来源；若日志里出现 `Reinitializing adapter configuration`，说明接口变更回调里检测到 `driver.AdapterStateDown` 并重下发配置（字段见 05-06）。以上文案与数值口径以本快照为准，具体打印格式需对照实际版本核验，路径见 `tunnel/service.go`、`tunnel/interfacewatcher.go`、`tunnel/firewall/rules.go`。

### 6. 版本差异

版本基准同总纲：上游 master 快照、WireGuardNT 1.1、Go 1.27.1、Windows 10 / Server 2019 及以上、amd64 / x86 / arm64 三种 MSI。本篇差异集中在四处。第一处是 `wtFwpmFilter0` 的 32/64 位布局：`types_windows_64.go` 带 `//go:build amd64 || arm64`，其 `wtFwpmFilter0_Size = 200`、各 `*_Offset` 常量（如 `filterCondition_Offset = 120`、`action_Offset = 128`）与独有的 `offset1 [4]byte` 是 64 位专属；`types_windows_32.go` 有另一套尺寸与偏移，`wtFwpDataType` 底层为 `uint`，在 32 位下宽度不同，跨架构比对转储必须按对应文件核对，路径 `tunnel/firewall/types_windows_32.go`。第二处是 `types_windows.go` 里同时存在 `wtFwpProvider0`（约 338 行）与 `wtFwpmProvider0`（约 393 行）两个近似同名、字段相同的结构，`blocker.go` 的 `registerBaseObjects` 实际用的是 `wtFwpmProvider0`，读源码时不要张冠李戴，属「需对照实际版本核验」的命名细节。第三处是 WFP 层与条件 GUID：`cFWPM_LAYER_*`、`cFWPM_CONDITION_*` 均为 Windows SDK 固定 GUID，随系统版本基本稳定，但个别层（如 `OUTBOUND_MAC_FRAME_NATIVE`）仅在较新系统可用，`blocker.go` 里 `permitHyperV` 被注释掉正是出于兼容性考虑，具体可用层需对照实际版本核验。第四处是权重数值 15/14/13/12/0、`minMTU` 的 576/1280、`watchdog` 的一分钟超时，都是硬编码策略值，可能随版本调整，请以源码为准。此外 `wfpSession` 为 `uintptr`、随进程位宽变化，属架构相关字段类型，不过程序逻辑不依赖其具体数值。

### 7. 常见误用与调试

其一，把 `tunnelService.Path` 当配置对象。`Path` 只是路径字符串，配置字段在 `conf.Config`（字段见 05-02），服务名由 `conf.ServiceNameOfTunnel` 推导，三者不可混用。其二，忽略 `interfaceWatcher` 通道的缓冲语义：`errors` 缓冲 2、`started` 缓冲 4 是刻意留的，若擅自改成无缓冲，接口回调可能在 `Execute` 进入 `select` 前阻塞，进而拖住 `setupMutex`。其三，在 `luid == 0` 时就期待 `setup` 生效：`storedEvents` 的存在正是为绑定前暂存事件，若绕过 `Configure` 直接读 `started`，会永远等不到值。其四，回调集合重复注册或漏注销：`changeCallbacks4/6` 每次 `setup` 都先 `Unregister` 再重建，`Destroy` 又统一注销，手动改这套逻辑极易留下孤立回调，表现为服务退出后仍有 goroutine 在跑。其五，把 `wtFwpValue0.value` 一律当整数：`_type` 为 `cFWP_BYTE_ARRAY16_TYPE` / `cFWP_BYTE_BLOB_TYPE` / `cFWP_SECURITY_DESCRIPTOR_TYPE` 时它是指针，且必须 `runtime.KeepAlive` 保活，否则规则装配时可能读到已回收内存。其六，`numFilterConditions` 与 `filterCondition` 切片长度不一致：`filterCondition` 取的是首元素地址，长度由 `numFilterConditions` 单独给出，二者不匹配会让 WFP 越界读，`blockDNS` 里 `weightDeny >= weightAllow` 的校验也是同类防御。其七，误以为 `baseObjects` 两个 GUID 是固定常量：它们由 `GenerateGUID()` 每次运行随机生成，日志里看到的值每次都不同，拿它去跨进程比对没有意义。其八，混淆 `services.Error`（字段见 05-09）与 `winipcfg` 的 `AddressFamily`：二者都常以整数出现，`interfaceWatcherError.serviceError` 与 `interfaceWatcherEvent.family` 的含义完全不同。以上只针对字段读写，完整启动与关停顺序（原理见 06-05）、MTU 推导（原理见 06-07）、kill-switch 规则分层（原理见 06-09）、配置键（配置见 04-02、配置见 04-03）、模块边界（模块见 07-05、模块见 07-07）。

### 3. 逐项详解

**① `ManagerService` 的三个字段。** 定义在 `manager/ipc_server.go`。`events *os.File` 是事件通知管道的服务端文件对象，`IPCServerListen(reader, writer, events *os.File, elevatedToken windows.Token)` 构造 `&ManagerService{events: events, elevatedToken: elevatedToken}` 后交给 `ServeConn`；`notifyAll` 里对每个实例 `m.events.SetWriteDeadline(time.Now().Add(time.Second))` 再 `m.events.Write(buf.Bytes())`，因此 `events` 可能被并发写，需要 `eventLock sync.Mutex` 串行化，且 `Quit` 会在持锁下把它置为 nil 以摘除通知。`elevatedToken windows.Token` 是权限判据：`StoredConfig` / `RuntimeConfig` 在 `s.elevatedToken == 0` 时调用 `conf.Redact()` 脱敏，`Delete` / `Create` / `Quit` / `Update` 在 token 为 0 时直接返回 `windows.ERROR_ACCESS_DENIED` 或静默跳过。三个字段分工极清晰：连接、并发、权限。注意 `events` 置 nil 与 `managerServices` 表删除必须成对，否则会向已关闭连接写事件。

**② `Tunnel` 与 `TunnelState`。** `Tunnel` 只有 `Name string` 一个字段，是 UI 侧对隧道的极简句柄，所有方法（`State`、`Start`、`Stop`、`Toggle`、`WaitForStop`、`Delete`、`StoredConfig`、`RuntimeConfig`）都以 `t.Name` 作为 gob 请求参数。`TunnelState int` 是 `iota` 枚举：`TunnelUnknown`/`TunnelStarted`/`TunnelStopped`/`TunnelStarting`/`TunnelStopping`。它来自 `svc.Query()` 的 `status.State` 映射：`svc.Stopped`→`TunnelStopped`、`StopPending`→`TunnelStopping`、`Running`→`TunnelStarted`、`StartPending`→`TunnelStarting`、其余→`TunnelUnknown`。务必与 `driver.AdapterState`（字段见 05-06）和 `svc.State` 区分：一个是 Windows 服务状态在 manager 侧的投影，另外两个分别是驱动适配器状态与服务框架枚举，数值不可互换。

**③ `NotificationType` 与 `MethodType`。** 两者都定义在 `manager/ipc_client.go`，均为 `int` 的 `iota` 枚举，是 gob 流的「消息标签」。`MethodType` 共 13 项，覆盖 `StoredConfigMethodType` 到 `UpdateMethodType`，`ManagerService.ServeConn` 的 `switch methodType` 与 `ipc_client.go` 里各 `IPCClient*` 方法一一对应：客户端先 `Encode(MethodType)` 再 `Encode` 参数，服务端解码后分发，再 `Encode` 结果与 `errToString(retErr)`。`NotificationType` 共 5 项，`InitializeIPCClient` 起的事件 goroutine 用它 `switch` 决定解出哪些后续字段，例如 `UpdateProgressNotificationType` 会依次解 `dp.Activity`、`dp.BytesDownloaded`、`dp.BytesTotal`、`errStr`、`dp.Complete` 并重组 `DownloadProgress`。两个枚举的顺序就是 gob 线协议的一部分，客户端与服务端必须同版本，插入新值只能追加到末尾。

**④ 五类 `*Callback` 结构。** `TunnelChangeCallback`、`TunnelsChangeCallback`、`ManagerStoppingCallback`、`UpdateFoundCallback`、`UpdateProgressCallback` 形状一致，各含一个 `cb func(...)` 字段，签名随事件不同：`TunnelChangeCallback.cb` 为 `func(tunnel *Tunnel, state, globalState TunnelState, err error)`，`UpdateProgressCallback.cb` 为 `func(dp updater.DownloadProgress)`，其余为无参或单 `UpdateState` 参数。每类配一个包级 `map[*XxxCallback]bool` 与一把 `sync.RWMutex`（如 `tunnelChangeCallbacks` / `tunnelChangeCallbacksLock`），`IPCClientRegister*` 负责注册、`Unregister` 负责删除。与 `winipcfg` 的三类回调不同（字段见 05-07），这里没有 `wait sync.WaitGroup`，因为事件分发是同 goroutine 内 `RLock` 下直接调用 `cb.cb(...)`，不存在跨进程在飞回调的注销竞态，字段更少。

**⑤ `serviceSubscriptionState` 与 `trackedTunnels`。** 定义在 `manager/tunneltracker.go`。`serviceSubscriptionState` 四个字段：`service *mgr.Service` 是被订阅服务、`cb func(status uint32) bool` 返回 true 表示订阅可结束、`done sync.WaitGroup` 用 `Add(1)`/`Done()`/`Wait()` 等待、`once uint32` 用 `atomic.CompareAndSwapUint32(&state.once, 0, 1)` 保证只结束一次。全局 `serviceSubscriptionCallbackPtr` 把 `notification` 与 `context`（即该结构指针）关联，回调里先查 `once`、再 `state.service.Query()` 补状态、最后 `state.cb(notification)`。`trackedTunnels map[string]TunnelState` 与 `trackedTunnelsLock sync.Mutex` 是隧道状态表：`trackTunnelService` 开头写入 `TunnelUnknown`、状态变化时改写、结束时 `delete`；`trackedTunnelsGlobalState()` 遍历它汇总全局态。这里是 `services.Error` 与 IPC 的交汇点：服务停止且 `Win32ExitCode == ERROR_SERVICE_SPECIFIC_ERROR` 时，用 `services.Error(serviceStatus.ServiceSpecificExitCode)` 把整数强转回错误码枚举，再作为 `IPCServerNotifyTunnelChange` 的 `err` 传出。

**⑥ `UpdateState` 与 `updateState`。** 定义在 `manager/updatestate.go`，`type UpdateState uint32`，三个值 `UpdateStateUnknown` / `UpdateStateFoundUpdate` / `UpdateStateUpdatesDisabledUnofficialBuild`。`updateState` 是包级全局，`checkForUpdates()` 在非官方构建时置 `UpdateStateUpdatesDisabledUnofficialBuild`、发现更新时置 `UpdateStateFoundUpdate`，并各调一次 `IPCServerNotifyUpdateFound(updateState)`；`ManagerService.UpdateState()` 直接返回它。它是「更新可用性」的全局快照字段，而非进度字段，进度在 `DownloadProgress`（见下）。

**⑦ `Ringlogger` 的五个字段。** 定义在 `ringlogger/ringlogger.go`。`tag string` 是写入每行前缀的标签，`NewRinglogger(filename, tag)` 与 `NewRingloggerFromInheritedMappingHandle(handleStr, tag)` 都会校验 `len(tag) > maxTagLength` 则返回 `windows.ERROR_LABEL_TOO_LONG`；`file *os.File` 是 `os.OpenFile(filename, os.O_RDWR|os.O_CREATE, 0o600)` 并 `Truncate(int64(unsafe.Sizeof(logMem{})))` 得到的底层文件；`mapping windows.Handle` 是 `CreateFileMapping` 句柄；`log *logMem` 是 `MapViewOfFile` 后把视图首地址强转成的共享内存头指针；`readOnly bool` 由 `access&windows.FILE_MAP_WRITE == 0` 推导，`WriteWithTimestamp` 见到只读直接返回 `io.ErrShortWrite`。`Close()` 依次关 `file`、解映射 `log`、关 `mapping` 并把三者清零，是典型资源三件套；`ExportInheritableMappingHandle` 则另建只读映射并置 `HANDLE_FLAG_INHERIT`，供子进程继承句柄。

**⑧ `logMem`、`logLine` 与四个常量。** `logMem` 三字段：`magic uint32` 在 `newRingloggerFromMappingHandle` 里若不等于 `magic` 常量就把整块清零并写入魔数，用来判定共享内存是否已被初始化；`nextIndex uint32` 是原子递增的写游标；`lines [maxLines]logLine` 是 2048 行的定长环形数组。`logLine` 两字段：`timeNs int64` 存 Unix 纳秒时间戳，`line [maxLogLineLength]byte` 存 `[tag] 正文` 格式的字节。写入算法很讲究：`WriteWithTimestamp` 先 `atomic.AddUint32(&rl.log.nextIndex, 1) - 1` 取槽位 `index%maxLines`，把 `timeNs` 原子清 0、整行清零，再拼正文，最后 `atomic.StoreInt64(&line.timeNs, ts)` 作为「本行写完」的发布标志——读侧 `WriteTo` 见到 `timeNs == 0` 就 `continue`，从而避免读到半写行。`maxLogLineLength = 512`、`maxTagLength = 5`、`maxLines = 2048`、`magic = 0xbadbabe` 四个常量决定了内存占用与截断行为：超长正文按 `maxLogLineLength-1-3-len(rl.tag)` 截断。`CursorAll = ^uint32(0)` 是 `FollowFromCursor` 的哨兵，表示「从全部历史开始跟随」，`DumpTo(inPath, out, continuous)` 在 `continuous == true` 时以 `cursor := CursorAll` 循环 `FollowFromCursor` 并每 100 毫秒轮询，非连续模式直接 `rl.WriteTo(out)`。

**⑨ `FollowLine`。** 定义在 `ringlogger/ringlogger.go`，只有 `Line string` 与 `Stamp time.Time` 两字段，是读侧对外结构：`FollowFromCursor` 把 `logLine.line[:index]` 转字符串、`time.Unix(0, timeNs)` 转时间后构造 `FollowLine`。`WriteTo` 则直接用 `fmt.Fprintf(out, "%s: %s\n", time.Unix(0, timeNs).Format("2006-01-02 15:04:05.000000"), line.line[:index])` 打印，二者格式一致（时间戳精度到微秒）。`FollowLine` 不进共享内存，只是 Go 侧值对象，可安全跨 goroutine 传递。

**⑩ `DownloadProgress` 与 `progressHashWatcher`。** 定义在 `updater/downloader.go`。`DownloadProgress` 五字段：`Activity string` 描述阶段（如 `"Initializing"`、`"Checking for update"`、`"Downloading update"`、`"Installing update"`）、`BytesDownloaded` / `BytesTotal uint64` 是进度计数、`Error error` 承载失败、`Complete bool` 标志结束。`DownloadVerifyAndExecute(userToken uintptr)` 返回 `chan DownloadProgress`（缓冲 128），各阶段向该通道发送值；`ManagerService.Update()` 起 goroutine 循环读取，遇 `dp.Complete || dp.Error != nil` 即退出，并每轮 `IPCServerNotifyUpdateProgress(dp)` 把五个字段拆开 gob 编码转发。`progressHashWatcher` 三字段 `dp *DownloadProgress`、`c chan DownloadProgress`、`hashState hash.Hash`，其 `Write(p []byte)` 每收到一块就累加 `BytesDownloaded`、`pm.c <- *pm.dp` 发进度、并 `pm.hashState.Write(p)` 喂 BLAKE2b 哈希；它是 `io.TeeReader` 的写入端，把「下载」「计数」「哈希」三件事绑在一次拷贝里完成。`updateInProgress uint32` 用 CAS 保证同时只有一个更新在跑。

**⑪ `UpdateFound` 与 `services.Error`。** `UpdateFound` 两字段：`name string`（候选 MSI 文件名）与 `hash [blake2b.Size256]byte`（32 字节摘要），由 `readFileList` / `findCandidate` 从服务端清单解析；下载完成后用 `subtle.ConstantTimeCompare(hasher.Sum(nil), update.hash[:])` 比对。`services.Error` 是 `uint32` 枚举，17 个常量按 `iota` 从 0 排到 16，`Error()` 方法把每个值映射为英文文案（见第 2 节表）。两个关键函数：`DetermineErrorCode(err error, serviceError Error) (bool, uint32)` 在 `errors.As(err, &syserr)` 命中 `windows.Errno` 时返回 `(false, uint32(syserr))`，否则若 `serviceError != ErrorSuccess` 返回 `(true, uint32(serviceError))`，再否则 `(false, windows.NO_ERROR)`；`CombineErrors(err, serviceError)` 把二者拼成带 `%w` 的错误链供日志打印。返回值第一个 `bool` 即 `svcSpecificEC`，对应 Windows 服务的 `ERROR_SERVICE_SPECIFIC_ERROR` 语义，这正是 `tunneltracker.go` 反向强转的依据。

**⑫ IPC 侧包级全局与通知辅助字段补遗。** `manager/ipc_server.go` 除 `ManagerService` 外还有四个包级全局：`managerServices map[*ManagerService]bool` 与 `managerServicesLock sync.RWMutex` 管理所有活跃连接，`notifyAll` 在 `RLock` 下遍历它并跳过 `elevatedToken == 0 && adminOnly` 的实例；`haveQuit uint32` 与 `quitManagersChan chan struct{}`（缓冲 1）配合 `Quit` 的 CAS 与 `quitManagersChan <- struct{}{}` 实现一次性退出信号。这些不是结构体字段，却是 `events` / `eventLock` / `elevatedToken` 三字段能否被正确读写的上下文，随查时不应略过。`errToString(err error) string` 把错误转成空串或 `err.Error()`，是 `ServeConn` 每个 case 里 `encoder.Encode(errToString(retErr))` 与客户端 `rpcDecodeError()` 之间的字段约定：空串表示无错误，非空串在客户端 `errors.New(str)` 还原。`IPCServerNotifyTunnelChange`、`IPCServerNotifyTunnelsChange`、`IPCServerNotifyUpdateFound`、`IPCServerNotifyUpdateProgress`、`IPCServerNotifyManagerStopping` 五个函数则把 `NotificationType` 与后续字段（隧道名、`TunnelState`、`UpdateState`、`DownloadProgress` 的五字段、`alreadyQuit` 等）打包进 `bytes.Buffer` 后写 `events`，与 `InitializeIPCClient` 事件 goroutine 的解码顺序严格对应。`ringlogger/dump.go` 的 `DumpTo(inPath string, out io.Writer, continuous bool)` 没有新结构，但 `continuous` 决定走 `WriteTo` 一次输出还是 `FollowFromCursor` 循环，它消费的正是 `FollowLine.Line` 与 `FollowLine.Stamp` 两字段。把这些全局与辅助入口与第 2 节表并读，IPC 与日志两侧字段的「谁写、谁读」才算完整。

### 4. 典型示例

下面两段 Go 代码分别演示 IPC 客户端读取状态，以及 `services.Error` 与 `DownloadProgress` 的字段读取。所有类型、字段与方法名均取自 `manager/ipc_client.go`、`services/errors.go`、`updater/downloader.go`。

```go
func queryState(name string) error {
	tunnel := &manager.Tunnel{Name: name}
	state, err := tunnel.State()
	if err != nil {
		return err
	}
	switch state {
	case manager.TunnelStarted:
		log.Println("tunnel started")
	case manager.TunnelStopped:
		log.Println("tunnel stopped")
	default:
		log.Printf("tunnel state=%d", state)
	}
	return nil
}

func report(serviceError services.Error, dp updater.DownloadProgress) {
	svcSpecificEC, exitCode := services.DetermineErrorCode(nil, serviceError)
	log.Printf("svcSpecificEC=%v exitCode=%d", svcSpecificEC, exitCode)
	if dp.Error != nil {
		log.Printf("update failed: %s: %v", dp.Activity, dp.Error)
		return
	}
	log.Printf("progress: %s %d/%d complete=%v", dp.Activity,
		dp.BytesDownloaded, dp.BytesTotal, dp.Complete)
}
```

示例输出，具体格式需对照实际版本核验：

```text
svcSpecificEC=true exitCode=3
progress: Downloading update 5242880/10485760 complete=false
progress: Installing update 10485760/10485760 complete=false
progress: Installing update 10485760/10485760 complete=true
```

逐行判读如下。第一行 `svcSpecificEC=true exitCode=3` 来自 `services.DetermineErrorCode(nil, services.ErrorCreateNetworkAdapter)`：`err` 为 nil 且不命中 `windows.Errno`，`serviceError` 非 `ErrorSuccess`，故返回 `(true, uint32(serviceError))`；数值 3 对应 `services.Error` 枚举里 `ErrorCreateNetworkAdapter`（`ErrorSuccess` 为 0、`ErrorRingloggerOpen` 为 1、`ErrorLoadConfiguration` 为 2），`svcSpecificEC=true` 表示这是服务专用退出码而非 Win32 错误码。若传入的 `err` 是 `windows.Errno`，则会返回 `(false, uint32(syserr))`，`svcSpecificEC` 为 false 且数值直接是系统错误号，二者不可混淆。第二行 `progress: Downloading update 5242880/10485760 complete=false` 中 `Activity` 为 `"Downloading update"`，`BytesDownloaded` 约 5 MiB、`BytesTotal` 约 10 MiB，二者由 `progressHashWatcher.Write` 与 `response.Length()` 分别填充，正常应满足 `0 <= BytesDownloaded <= BytesTotal`；`complete=false` 说明仍在进行。第三行 `Installing update` 且计数已达总量，说明下载完成、BLAKE2b 校验通过、进入 `runMsi` 阶段，但 `Complete` 仍为 false，因为 `DownloadVerifyAndExecute` 只在 `runMsi` 成功后才发 `DownloadProgress{Complete: true}`。第四行 `complete=true` 是终止标志，`ManagerService.Update()` 的 goroutine 见到它即退出循环；若某行出现 `update failed: ...` 前缀，则 `dp.Error != nil`，应结合 `Activity` 判断失败阶段（如 `"Checking for update"` 对应清单或签名校验失败）。异常特征：`BytesTotal` 为 0 表示 `response.Length()` 未取到长度，`BytesDownloaded` 长时间不动可能是下载停滞。以上文案与数值口径以本快照为准，实际枚举取值、进度文案需对照实际版本核验，路径见 `services/errors.go`、`updater/downloader.go`、`manager/ipc_server.go`。

### 5. 速查表

下表按「看到什么、查哪个字段」整理，便于排障反查，不重复字段含义。

| 现象或需求 | 优先核对的字段 | 取值线索 | 源码位置 |
|---|---|---|---|
| UI 读不到隧道状态 | `Tunnel.Name` / `TunnelState` | 名称与枚举映射 | `manager/ipc_client.go` |
| 配置被脱敏 | `ManagerService.elevatedToken` | 是否为 0 | `manager/ipc_server.go` |
| 事件写失败 | `.events` / `.eventLock` | 是否已被 Quit 置 nil | `manager/ipc_server.go` |
| 服务退出码异常 | `services.Error` 枚举值 | iota 顺序是否被改动 | `services/errors.go` |
| 日志为空或半行 | `logLine.timeNs` | 是否为 0 表示未发布 | `ringlogger/ringlogger.go` |
| 日志顺序错乱 | `logMem.nextIndex` | 原子计数与槽位取模 | `ringlogger/ringlogger.go` |
| 更新进度卡住 | `DownloadProgress.BytesDownloaded` | 是否长期不增长 | `updater/downloader.go` |
| 更新重复触发 | `updateInProgress` | CAS 是否被正确清零 | `updater/downloader.go` |

### 6. 版本差异

版本基准同总纲：上游 master 快照、WireGuardNT 1.1、Go 1.27.1、Windows 10 / Server 2019 及以上、amd64 / x86 / arm64 三种 MSI。本篇差异集中在五处。第一处也是最重要的一处：`services.Error` 用 `iota` 连续赋值，数值 0..16 会被写进 Windows 服务的 `ServiceSpecificExitCode`，并由 `manager/tunneltracker.go` 反向强转回 `services.Error`。因此这个枚举是跨进程 ABI 契约，任何版本升级都只能在末尾追加新值、绝不能中间插入或重排，否则老 manager 会把新 tunnel 的退出码解释成完全不同的错误；具体取值需对照 `services/errors.go` 核验。第二处是 `MethodType` / `NotificationType` 的 `iota` 顺序同样是 gob 线协议，`ipc_server.go` 的 `switch` 与 `ipc_client.go` 的编码必须同版本，UI 与 Manager 服务版本不一致时解码会错位，路径 `manager/ipc_client.go`。第三处是 ringlogger 的共享内存布局：`maxLogLineLength = 512`、`maxLines = 2048`、`magic = 0xbadbabe` 与 `logLine` 的字段顺序共同决定 `unsafe.Sizeof(logMem{})`，不同版本若改了这些常量，新旧进程映射同一文件会读到错乱数据，升级时需留意旧日志文件是否被复用，路径 `ringlogger/ringlogger.go`。第四处是 `DnsInterfaceSettings` 之类系统 API 之外，`DownloadProgress` / `UpdateFound` 字段随 Go 版本与 `golang.org/x/crypto/blake2b` 的 `Size256` 常量稳定，但 `UpdateFound.hash` 的数组长度绑定该常量，属「需对照实际版本核验」的依赖。第五处是 `UpdateState` 与 `TunnelState` 的枚举值可能随功能增加而追加，同样只能尾部追加。此外 `manager/updatestate.go` 用 `//go:linkname fastrandn runtime.fastrandn` 直接链接运行时内部函数做抖动休眠，与 Go 版本强相关，是另一处版本敏感点，但该技巧不影响字段定义。

### 7. 常见误用与调试

其一，混淆三套「状态/错误」整数：`driver.AdapterState`（字段见 05-06）、`manager.TunnelState`、`services.Error` 都以小整数出现，但分别代表驱动适配器、Windows 服务状态投影、服务退出码，排障时若把 `exitCode=3` 当成 `TunnelStarting` 会南辕北辙。其二，在 `services.Error` 枚举中间插值：如上所述它经 `ServiceSpecificExitCode` 跨进程传递，插入会静默破坏错误归类，新增错误码必须追加到 `ErrorWin32` 之后并同步 `Error()` 的 `switch`。其三，`ManagerService.events` 置 nil 与 `managerServices` 删除不同步：`Quit` 与 `IPCServerListen` 的清理段都成对操作，若自定义路径只置 nil 不删表项，`notifyAll` 仍会遍历到该实例并跳过写入，造成事件静默丢失。其四，误改 `Ringlogger.log` 指向或忽略 `readOnly`：只读视图（`NewRingloggerFromInheritedMappingHandle` 用 `FILE_MAP_READ`）下 `WriteWithTimestamp` 直接返回 `io.ErrShortWrite`，把只读实例当写入器用会得到「写不进但也不报错到底」的假象。其五，把 `logLine.timeNs == 0` 当成「空行所以跳过没关系的正常态」：在写入过程中它确实是瞬态，但若某行长期为 0，说明写协程在发布前崩溃，`WriteTo` 会永久漏掉该行，应结合 `nextIndex` 判断是否发生半写。其六，`FollowFromCursor` 的 `CursorAll` 用错：`CursorAll = ^uint32(0)` 是哨兵而非合法游标，把它当普通 `nextCursor` 传回下一轮会导致取模错乱，`DumpTo` 的连续模式正是靠首轮传 `CursorAll`、后续传返回值来区分。其七，`DownloadProgress` 的 `Error` 与 `Complete` 未联合判断：`ManagerService.Update()` 的退出条件是 `dp.Complete || dp.Error != nil`，只看 `Complete` 会在失败时永远等不到 true。其八，`progressHashWatcher.Write` 里把 `BytesDownloaded` 当成「已校验字节」：它只是已下载计数，哈希正确性由末尾 `subtle.ConstantTimeCompare` 保证，二者不是一回事。其九，忽略 `elevatedToken == 0` 的脱敏语义：低权限 UI 拿到的 `conf.Config` 已被 `Redact()`，若据此断言「私钥为空」是误判。以上只针对字段读写，完整 IPC 与环形日志机制（原理见 06-10、原理见 06-11）、更新验签链（原理见 06-12）、命令行开关（配置见 04-04、配置见 04-06）、模块边界（模块见 07-08、模块见 07-10、模块见 07-11）。
