# wireguard-windows 技术资料 · 04 配置与命令行（分片 C）

## 04-06 服务管理、PowerShell 与诊断命令全集

### 1. 本篇定位与覆盖范围

本篇是 04「配置与命令行」册的第六篇，采用 B 手册字典型骨架，主题是服务管理、PowerShell 与诊断命令全集。大纲为它列出九类命令：`sc`、`Get-Service`、`netsh`、`Get-NetAdapter`、`Get-NetRoute`、`pnputil`、`wevtutil`、`reg`、`schtasks`。把这九类放在一起，是因为它们共同回答同一个运维问题：当 wireguard-windows 已经被安装到一台 Windows 主机上之后，管理员如何不依赖图形界面，纯靠命令行与脚本去观测、控制、核验和采集这套软件留下的服务对象、网络对象、驱动对象与日志对象。它们不是配置键，也不是 `wireguard.exe` 的进程开关，而是「站在操作系统一侧、面向本仓库产物」的管理工具，因此本篇的定位是运维侧的命令字典，而不是配置语法或程序入口的复述。

必须先划清本篇与同册前几篇的分工，否则命令清单会被重复抄写。`wireguard.exe` 自身那组以斜杠开头的进程开关——无参数、`/installmanagerservice`、`/installtunnelservice CONFIG_PATH`、`/uninstallmanagerservice`、`/uninstalltunnelservice TUNNEL_NAME`、`/managerservice`、`/tunnelservice CONFIG_PATH`、`/ui` 四个句柄、`/dumplog [/tail]`、`/update`、`/removedriver`——是 04-04 的唯一权威源，本篇不重列；`wg(8)` 的 `show`、`showconf`、`set`、`setconf`、`addconf`、`syncconf`、`genkey`、`pubkey`、`genpsk` 九个子命令是 04-05 的唯一权威源，本篇同样不重列；两个 `HKLM\Software\WireGuard` 注册表键的取值、语义与安全代价是 04-07 的唯一权威源，本篇只把 `reg` 当作「读写键的通道」点到为止。本篇的独立价值在于：把 Windows 平台自带的系统管理工具，与上述几组本仓库能力所产出的具体对象一一对应起来，给出「查哪个服务、看哪块适配器、读哪份日志、用哪个计划任务账户」的完整操作面。凡涉及某个开关或子命令本身的完整语义，一律回指 04-04 或 04-05。

第二条边界是「这些命令是谁写的」。`sc`、`netsh`、`pnputil`、`wevtutil`、`reg`、`schtasks` 以及 `Get-Service`、`Get-NetAdapter`、`Get-NetRoute` 等 PowerShell cmdlet，全部是 Windows 操作系统自带的管理工具，不是本仓库的产物；`upstream_src/` 这份快照里既没有它们的实现，也没有为它们封装的 Go 包。因此本篇给出的参数与输出属于「面向 WireGuard 对象的调用惯例」，命令自身的完整开关、字段名称与输出措辞属于微软 Windows 文档范畴，具体格式需对照实际版本核验，可定位的本仓库依据是 `docs/enterprise.md` 与 `docs/adminregistry.md` 两份官方说明，以及 `main.go`、`conf/name.go`、`services/errors.go` 三处源码。凡是本仓库源码与官方文档里查不到的措辞，本篇一律不写死，也不把 Linux 平台上 `systemctl`、`ip route` 之类的习惯硬套到 Windows 上。

第三条边界是「本仓库确凿产出了什么对象」，这是所有命令的作用目标。`docs/enterprise.md` 与 `manager/install.go` 明确：管理服务只有一个，名为 `WireGuardManager`；每安装一条隧道就多一个独立服务，名为 `WireGuardTunnel$<name>`；`conf/name.go` 的 `ServiceNameOfTunnel` 函数把合法隧道名拼成 `"WireGuardTunnel$" + tunnelName`，正好与文档互证。`docs/enterprise.md` 又明确这两类服务可用标准 Windows 服务管理工具控制，例如 `services.msc` 或 `sc`，这是本篇把 `sc` 与 `Get-Service` 列为首选命令的直接依据。此外，`docs/enterprise.md` 的 Diagnostic Logs 一节给出 `wireguard /dumplog` 重定向与 `/tail` 管道到日志采集服务、以及 PowerShell 里 `wireguard /dumplog /tail | select` 的写法；Updates 一节给出用 `schtasks` 每日凌晨三点触发 `/update` 的示例；Driver Removal 一节给出 `wireguard /removedriver`。这几处是官方文档直接点名 Windows 运维命令的地方，本篇据实引用，不额外发明本仓库不存在的管理面。

能力边界同样要写清：本仓库是 Windows 官方客户端，内核数据面由外部项目 WireGuardNT 提供，本仓库只负责 IOCTL 配置下发、适配器与网络配置；不要把 Linux `wg-quick` 的 `iptables`、`%i`、`SaveConfig`、`resolvconf` 语义写成 Windows 客户端能力，也不要把 `wireguard-go` 的用户态数据面写进本篇（配置键全集见 04-01 至 04-03，脚本键执行条件见 04-07）。本篇不展开 Manager 服务的 WTS 会话枚举、令牌降权、IPC 句柄继承等内部机制，统一收敛到交叉引用：`字段见 05-09 ｜ 原理见 06-10 ｜ 模块见 07-08`。服务错误码枚举见 05-09，进程入口与日志句柄初始化见 06-01 与 06-11，隧道服务启动顺序见 06-05，服务与错误码模块见 07-10。本篇只回答「有哪些系统命令、各自查什么、怎么读输出、哪些坑会导致查错对象」。

表中 `sc` 与 `Get-Service` 是同一批服务对象的两种入口：前者是随 Windows 长期存在的命令行工具，输出为固定文本；后者是 PowerShell 对象化入口，便于进管道与脚本。`netsh` 与三个 `Get-Net*` cmdlet 是新旧两代网络观测入口，语义有重叠，实际运维建议以 PowerShell 族为主、`netsh` 为兼容兜底。`reg` 与 `schtasks` 各自只服务一个专门场景：前者是 04-07 两个策略键的落地通道，后者是 `docs/enterprise.md` 里定时更新的载体。需要再次强调，表中「关键参数与用法」是面向 WireGuard 的最小集合，不是这些系统命令的完整手册；`sc` 的 `failure` 恢复策略子命令、`netsh` 的众多上下文、`wevtutil` 的 XPath 过滤写法等，均需对照实际版本核验，本仓库源码不承担这些命令的语义定义。

### 3. 逐项详解

#### 3.1 `sc`：服务状态与配置的第一入口

`docs/enterprise.md` 明确点名 `sc` 可控制 `WireGuardManager` 与每条隧道服务。`sc query <服务名>` 返回服务名、类型、当前状态、Win32 退出码、服务退出码、检查点与等待提示；`sc qc <服务名>` 返回启动类型、二进制路径、依赖与运行账户，是核验「这条隧道服务到底指向哪个配置文件」的关键，其 `BINARY_PATH_NAME` 应呈现 04-04 里 `/tunnelservice CONFIG_PATH` 的形态；`sc start`、`sc stop` 触发启停，`sc config` 改启动类型，`sc delete` 删除服务。要点有三：服务名必须是 `WireGuardManager` 或完整的 `WireGuardTunnel$<隧道名>`，其中 `$` 在部分 shell 里需要转义或用引号包裹；把裸隧道名当服务名是本篇第 7 节要讲的头号误用；`WIN32_EXIT_CODE` 是服务控制管理器记录的退出码，与 `services/errors.go` 里 `DetermineErrorCode` 由服务进程自己报告的码属于两条不同来源，判读时不要混为一谈（错误码枚举见 05-09）。

#### 3.2 `Get-Service` 与 PowerShell 服务族

`Get-Service -Name WireGuardManager` 以对象形式返回 `Status`、`StartType`、`Name` 等属性，`Start-Service`、`Stop-Service`、`Set-Service -StartupType Automatic` 完成对应动作，配合 `Where-Object` 可批量筛选正在运行的服务。相比 `sc`，cmdlet 的输出可直接进管道、可序列化为 JSON、可被脚本消费，适合企业批量运维与巡检报表。一个 Windows 特有的坑是：`$` 在 PowerShell 里是变量引导符，`WireGuardTunnel$mytunnel` 若不加单引号会被展开成只剩前缀，导致查不到服务；稳妥写法是 `Get-Service -Name 'WireGuardTunnel$mytunnel'`。各 cmdlet 的具体参数名与 `Start-Service` 的等待行为需对照实际 PowerShell 版本核验，本仓库不定义这些行为。

#### 3.3 `netsh` 与 `Get-NetAdapter`、`Get-NetRoute`、`Get-NetIPConfiguration`

`netsh` 是传统网络配置入口，`netsh interface ipv4 show interfaces`、`show route`、`show addresses` 可看接口、路由与地址，但输出是文本表格、不易脚本化，微软后续用 `Get-Net*` cmdlet 取代其大部分观测用途。`Get-NetAdapter` 列出适配器名、接口索引、状态与链路速度；隧道适配器由 tunnel 服务在启动时动态创建、停止时销毁（见 `docs/netquirk.md` 与 `docs/enterprise.md` 的 Driver Removal 一节），因此只有隧道处于运行状态时才能查到它，停止后查不到是预期行为而非故障。`Get-NetRoute -DestinationPrefix <网段>` 用来核验 `[Peer]` 的 `AllowedIPs` 是否真的落成路由并指向隧道接口索引（配置语义见 04-03、原理见 06-06）；`Get-NetIPConfiguration -InterfaceIndex <索引>` 汇总地址、默认网关与 DNS 服务器，配合 04-02 的 `DNS` 键与 06-08 的下发行为判读是否有 DNS 泄漏或搜索域错配。

#### 3.4 `pnputil`：驱动包核验

WireGuardNT 是内核驱动，`pnputil /enum-drivers` 可列出系统里的第三方驱动包，`/delete-driver` 可清理。但本仓库提供了更安全的正规入口 `wireguard /removedriver`（见 04-04、03-06）：`docs/enterprise.md` 说明「当没有更多网络适配器时，驱动可被移除」，`main.go` 的 `/removedriver` 分支调用 `driver.Uninstall()`，由本仓库自行判断时序与清理范围。直接用 `pnputil` 删驱动包绕过了这套判定，可能留下残留适配器、服务或注册表状态，仅在 `/removedriver` 明确失败后的善后场景才考虑，且应先确认所有隧道服务已停止、适配器已销毁。`pnputil` 的具体子命令拼写与 OEM INF 名称形式需对照实际 Windows 版本核验。

#### 3.5 `wevtutil` 与 `wireguard /dumplog` 的日志双通道

必须区分两套日志。本仓库主用共享环形日志：`docs/enterprise.md` 说 manager 与所有 tunnel 服务把诊断日志写进同一份 ringbuffer 日志，UI 里可见，也能用 `wireguard /dumplog` 导到标准输出，或用 `/dumplog /tail` 持续输出接给日志采集服务，PowerShell 里可写 `wireguard /dumplog /tail | select`。源码侧 `main.go` 的 `/dumplog` 分支先取 `STD_OUTPUT_HANDLE`，取不到就报 `Stdout must be set`，再经 `conf.LogFile(false)` 拿到路径交给 `ringlogger.DumpTo`，第三个参数由 `len(os.Args) == 3 && os.Args[2] == "/tail"` 决定是否持续跟随。`wevtutil qe` 查的是 Windows 事件日志（服务控制管理器记录的服务启停事件等），是辅助证据而非本仓库主日志，二者不要互相替代；ringlogger 的格式见 05-09、共享内存与读取链见 06-11、模块归属见 07-10。日志判读与故障归类见 08-01、08-03。

#### 3.6 `reg`：注册表策略的读写通道

`reg` 在本篇只作为通道出现，键值语义的权威源是 04-07。`docs/adminregistry.md` 给出的官方写法是 `reg add HKLM\Software\WireGuard /v LimitedOperatorUI /t REG_DWORD /d 1 /f`，以及把 `/v` 换成 `DangerousScriptExecution` 的同形命令，核验用 `reg query HKLM\Software\WireGuard`。要点有四：路径在 `HKLM` 下、写入需要管理员权限；类型是 `REG_DWORD` 且值必须为 `1` 才生效；文档明确「没有 UI 来开启这些、将来可能移除、卸载器会清理整个 `HKLM\Software\WireGuard`」；因此 `reg` 是本篇唯一直接改动本仓库行为的命令，操作前应备份键值、操作后应复核生效范围。具体开关拼写需对照 `docs/adminregistry.md` 实际版本核验，两个键的完整影响矩阵见 04-07。

#### 3.7 `schtasks`：定时更新任务

`docs/enterprise.md` 给出可直接引用的示例：`schtasks /create /f /ru SYSTEM /sc daily /tn "WireGuard Update" /tr "%PROGRAMFILES%\WireGuard\wireguard.exe /update" /st 03:00`。逐项拆解：`/f` 覆盖同名任务，`/ru SYSTEM` 让任务以 LocalSystem 运行（与 manager、tunnel 服务同账户，见 `docs/attacksurface.md`），`/sc daily` 与 `/st 03:00` 定每日三点，`/tr` 里因为路径含空格必须整体加引号，末尾 `/update` 是 04-04 的命令行开关，把进度输出到标准错误。配套 `schtasks /query /tn "WireGuard Update" /fo LIST` 与 `schtasks /delete` 做核验与清理；文档还给出 `wireguard /update 2> C:\path\to\update\log.txt` 的日志落盘写法。任务失败的常见原因是 `/tr` 引号缺失、账户权限不足，或 `wireguard.exe` 路径与实际安装架构不符（amd64 / x86 / arm64 三种 MSI，见 02-05）。具体参数需对照实际 Windows 版本核验。

#### 3.8 `services.msc` 与图形入口

`docs/enterprise.md` 把 `services.msc` 与 `sc` 并列为标准服务管理工具。它是图形化的服务控制管理器前端，适合一次性人工核验服务状态、启动类型与登录账户，也适合在排障现场快速看一眼「服务是不是停了」。但它不可脚本化、不产生可采集的结构化文本，因此企业批量运维与自动化巡检仍以 `sc` 与 PowerShell 族为主。本篇把它列全，是为了与官方文档的措辞保持一致，避免读者以为遗漏了图形入口；服务恢复策略的配置与开机自启讨论见 03-03。

#### 3.9 服务名、隧道名与合法字符

`conf/name.go` 是服务名后缀合法性的权威来源，也解释了 `$` 为什么是分隔符。`TunnelNameIsValid` 要求名字匹配正则 `^[a-zA-Z0-9_=+.-]{1,32}$`，即长度 1 到 32、只允许字母、数字与 `_=+.-`；`isReserved` 拒绝 `CON`、`PRN`、`AUX`、`NUL`、`COM1` 至 `COM9`、`LPT1` 至 `LPT9` 这些 Windows 保留设备名；`hasSpecialChars` 拒绝 `$`（源码常量 `serviceNameForbidden`）、`\/:*?"<>|` 与制表符及控制字符，并拒绝以 `.` 开头或结尾的名字。`ServiceNameOfTunnel` 在名字非法时直接返回 `Tunnel name is not valid` 错误，合法时返回 `"WireGuardTunnel$" + tunnelName`。这解释了为什么含空格、中文或 `$` 的配置文件名会被拒，也解释了服务名里 `$` 之后的部分必然不含 `$`。命名规则的完整讨论见 04-01，相关字段见 05-02。

### 4. 典型示例

第一组给出一次完整的服务与网络状态采集。命令形式见下方示例，其中 PowerShell 里带 `$` 的服务名用单引号包裹，避免被当成变量展开。

```powershell
sc query WireGuardManager
sc qc 'WireGuardTunnel$mytunnel'
Get-Service -Name WireGuardManager | Format-List Name, Status, StartType
Get-NetAdapter | Where-Object Status -eq Up | Format-Table Name, InterfaceIndex, Status
Get-NetRoute -DestinationPrefix 10.0.0.0/24 | Format-Table InterfaceIndex, DestinationPrefix, NextHop
```

上面第一行 `sc query` 的典型输出如下。示例输出，具体格式需对照实际版本核验。

```text
> sc query WireGuardManager

SERVICE_NAME: WireGuardManager
        TYPE               : 10  WIN32_OWN_PROCESS
        STATE              : 4  RUNNING
                                (STOPPABLE, NOT_PAUSABLE, ACCEPTS_SHUTDOWN)
        WIN32_EXIT_CODE    : 0  (0x0)
        SERVICE_EXIT_CODE  : 0  (0x0)
        CHECKPOINT         : 0x0
        WAIT_HINT          : 0x0
```

逐行判读如下，读法可直接套用到任意一条隧道服务。首行 `SERVICE_NAME: WireGuardManager` 回显被查询的服务名，用它确认没有把管理服务与隧道服务搞混；若这里出现 `WireGuardTunnel$...` 说明查的是某条隧道。`TYPE : 10 WIN32_OWN_PROCESS` 表示该服务运行在独立进程里，与 docs 所说「manager 服务与 tunnel 服务是分开的 Windows 服务」一致。`STATE : 4 RUNNING` 是核心状态行，数字 4 对应运行中，常见对照是 1 为已停止、2 为正在启动、3 为正在停止、4 为运行中、7 为暂停；当它长期停在 2 或 3，要结合 `CHECKPOINT` 与 `WAIT_HINT` 判断是否卡在启停过渡态。括号内 `STOPPABLE, NOT_PAUSABLE, ACCEPTS_SHUTDOWN` 说明该服务可停止、不可暂停、接受关机通知，这决定 `sc stop` 是否可能成功。`WIN32_EXIT_CODE : 0` 与 `SERVICE_EXIT_CODE : 0` 都为 0 表示上一次退出是干净的；若前者非 0，它是服务控制管理器记录的 Win32 错误码，需与 `services/errors.go` 的 `DetermineErrorCode` 所报告的服务自定义错误码分开看，后者可能是 `Error` 枚举值，也可能是直接透传的 `windows.Errno`（字段见 05-09、原理见 06-01）。`CHECKPOINT : 0x0` 与 `WAIT_HINT : 0x0` 在稳定运行态都应为 0，只有启停进行中才会递增，排障时若发现服务长时间处于非 4 状态且检查点不推进，应转去读环形日志。把同一命令换成 `sc query 'WireGuardTunnel$mytunnel'` 时，状态若为 1（已停止），则 `Get-NetAdapter` 里查不到对应适配器属于预期，因为适配器随隧道启动而创建、随停止而销毁，不应据此误判驱动丢失。

### 6. 版本差异

第一层差异来自操作系统本身。本篇九类命令绝大多数是 Windows 自带工具，其行为随 Windows 版本与 PowerShell 版本演进：`netsh` 是长期存在的传统入口，`Get-NetAdapter`、`Get-NetRoute`、`Get-NetIPConfiguration` 属于较新的 NetTCPIP PowerShell 模块，在旧版系统或 Server Core 上可能不可用或参数名不同；`sc` 的文本输出格式相对稳定，`Get-Service` 的属性集合则随 PowerShell 版本略有增减；`wevtutil` 的事件通道名称与查询语法、`pnputil` 的子命令拼写、`schtasks` 的参数细节都需对照实际版本核验。本仓库不锁定这些命令的版本，只锁定「要用它们去查哪些对象」。

第二层差异来自本仓库自身的稳定面与易变面。`docs/enterprise.md` 给出的服务名 `WireGuardManager` 与 `WireGuardTunnel$<name>` 是稳定约定，`conf/name.go` 的 `ServiceNameOfTunnel` 用字符串常量拼接予以固化；`wireguard /dumplog`、`/dumplog /tail`、`/update`、`/removedriver` 是 `main.go` 的 `usage()` 里列出的稳定开关（见 04-04），其中 `/dumplog` 依赖 stdout 这一约束来自源码而非文档约定，跨版本保持一致。相对易变的是 `docs/adminregistry.md` 明确声明的两个注册表键「没有 UI、将来可能移除、卸载器会清理整个 `HKLM\Software\WireGuard`」——这意味着依赖 `reg` 写入的策略不具备长期兼容性，升级后必须复核。同理，`docs/enterprise.md` 示例里的 `%PROGRAMFILES%\WireGuard\wireguard.exe` 路径需对照实际安装路径与架构核验，三种 MSI 的安装布局见 02-05。

第三层是随源码快照可能调整的事实：`conf/name.go` 里 `allowedNameFormat` 正则、保留设备名列表、`specialChars` 常量内容属于源码细节，跨版本有微调可能；`services/errors.go` 的 `Error` 枚举项与 `DetermineErrorCode` 的返回值需对照 `upstream_src/services/errors.go` 当前版本核验（字段见 05-09）；`docs/netquirk.md` 关于适配器动态创建、确定性 GUID 的描述是机制性结论，稳定性高于任何具体数值。凡涉及具体版本号、cmdlet 参数名、事件通道名、驱动 INF 名称与下载 URL，本篇统一标注「需对照实际版本核验」，可定位路径为 `docs/enterprise.md`、`docs/adminregistry.md`、`docs/netquirk.md`、`main.go`、`conf/name.go`、`services/errors.go`。

### 7. 常见误用与调试

1. **把裸隧道名当服务名**。`sc query mytunnel` 查不到任何东西，因为服务名是 `WireGuardTunnel$mytunnel`；`WireGuardManager` 则是另一个独立服务。命名与拼接规则见 `conf/name.go` 的 `ServiceNameOfTunnel`（见 3.9 与 04-01）。排障第一步永远是拿 `sc query` 逐个确认服务全名。

2. **把 `wg show` 与 `sc query` 混用**。`wg show <name>` 查的是运行实例里的接口、peer、握手与流量（见 04-05），`sc query` 查的是服务控制管理器里的服务状态。服务显示 RUNNING 但 `wg show` 无握手，说明服务起来了而数据面未通，应转去查端点、AllowedIPs 与路由，不要反复重启服务。

3. **在普通用户会话里执行服务控制**。`docs/attacksurface.md` 明确 manager 与 tunnel 服务均以 LocalSystem 运行，UI 以高完整性提升令牌运行；`sc stop`、`sc config`、`Set-Service` 这类操作通常需要管理员权限，权限不足时表现为「拒绝访问」而非半份输出。企业脚本应显式以管理员或 SYSTEM 账户运行，`schtasks` 示例用 `/ru SYSTEM` 正是这个道理。

4. **把环形日志与 Windows 事件日志互相替代**。`wireguard /dumplog` 读的是本仓库 `ringlogger/` 的共享环形日志，`wevtutil qe` 读的是系统事件日志。服务为何启动失败、脚本键为何被跳过这类信息写在前者里；后者只有 SCM 层面的启停记录。只盯事件日志会漏掉关键诊断行（见 3.5、06-11）。

5. **`wireguard /dumplog` 在没有 stdout 的上下文里报错**。`main.go` 的 `/dumplog` 分支要求 `STD_OUTPUT_HANDLE` 有效，否则直接报 `Stdout must be set`。在计划任务、服务包装或某些远程执行环境里标准输出可能为空，此时应显式重定向到文件或改为读日志文件，不要以为是日志功能坏了。

6. **计划任务路径空格与账户配错**。`docs/enterprise.md` 的示例把 `/tr` 整串用双引号包住，是因为 `%PROGRAMFILES%\WireGuard\wireguard.exe` 含空格；漏引号会让任务只执行到目录名为止。同时 `/ru SYSTEM` 决定更新以 LocalSystem 身份运行，换成普通账户可能因权限不足而失败。

7. **隧道停止后查不到适配器就判驱动丢失**。`docs/enterprise.md` 的 Driver Removal 一节与 `docs/netquirk.md` 都说明适配器在启动时动态创建、停止时销毁。`Get-NetAdapter` 在隧道停止时为空是预期；只有在隧道运行状态下仍查不到，才需要结合 `pnputil /enum-drivers` 与 `wireguard /removedriver` 排查（见 3.4）。

8. **绕过本仓库直接用 `pnputil` 删驱动**。`wireguard /removedriver` 会自行判断「没有更多适配器」的前提并调用 `driver.Uninstall()`；直接删驱动包可能留下服务、注册表或适配器残留。正确顺序是先停全部隧道服务、确认无适配器，再走 `/removedriver`，失败后才把 `pnputil` 当善后手段（见 03-06、04-04）。

推荐的调试顺序是：先用 `sc query` 与 `Get-Service` 锁定服务状态，再用 `Get-NetAdapter`、`Get-NetRoute`、`Get-NetIPConfiguration` 核验网络对象是否齐备，接着用 `wireguard /dumplog` 读主日志、必要时用 `wevtutil` 补事件旁证，最后用 `wg show` 看握手与流量是否推进；涉及策略与更新的分支分别用 `reg query` 与 `schtasks /query` 收口。这条顺序把「服务—网络—日志—实例」四层证据串起来，与图 04-06-02 的分层判读一致，具体故障到命令的映射速查见 04-08。

## 04-07 管理员注册表策略与危险脚本执行

### 1. 本篇定位与覆盖范围

本篇是 04「配置与命令行」册的第七篇，采用 B 手册字典型骨架，也是全册关于「管理员注册表策略」的唯一权威源。它覆盖的内容集中而敏感：`HKLM\Software\WireGuard` 下的两个 DWORD 键——`LimitedOperatorUI` 与 `DangerousScriptExecution`——以及由后者解锁的四个脚本配置键 `PreUp`、`PostUp`、`PreDown`、`PostDown`，外加 Windows 客户端专用的环境变量 `WIREGUARD_TUNNEL_NAME`。大纲把「受限 UI 能力矩阵」「脚本开关的安全代价」「卸载清理行为」一并交给本篇，因此本篇既要给全参数表，又要把每个键背后「谁能用、能做什么、代价是什么」讲透。

一手依据是 `docs/adminregistry.md`，它开篇就把这批键定性为「供管理员完成非常规操作的高级旋钮，不推荐启用，没有 UI 可以打开，将来也可能移除，卸载器会清理整个 `HKLM\Software\WireGuard`，请自行承担风险并确认你知道自己在做什么」。这段定性不是套话，而是本篇所有结论的前提：这两个键没有图形开关、不受常规配置校验保护、不保证跨版本存在，写入即生效于整机。第二手依据是 `docs/enterprise.md`，它在 Tunnel Service 一节补了一句关键约束：`PreUp`、`PostUp`、`PreDown`、`PostDown` 可以在隧道服务生命周期的若干时点运行自定义命令，但「只有设置了正确的注册表键」才行；在 Manager Service 一节又说明受限 UI 会在 Network Configuration Operators 组的桌面上出现，前提同样是「正确的注册表键」。两份文档互相咬合，构成本篇事实骨架。

必须写清三条边界。第一，本篇不重列 `wireguard.exe` 的 `/` 开关（04-04 是权威源）、不重列 `wg(8)` 子命令（04-05 是权威源）、不重列 `[Interface]` 与 `[Peer]` 的全部配置键（04-01 至 04-03 是权威源）；四个脚本键只在「受注册表开关约束的执行条件」这一维度展开，其作为普通配置键的语法与注释行为见 04-02、字段见 05-02。第二，本仓库是 Windows 官方客户端，不是 Linux `wg-quick(8)`：Linux 用 `%i` 指代接口名、用 `SaveConfig` 回写、用 `resolvconf` 管 DNS、用 `iptables` 写规则，这些语义 Windows 客户端一概不提供；`docs/adminregistry.md` 特别点明「不要使用 `%i`，WireGuard for Windows 改为设置环境变量 `WIREGUARD_TUNNEL_NAME`」，这是本篇反复强调的能力红线。第三，内核数据面由外部项目 WireGuardNT 实现，本仓库只负责 IOCTL 配置下发与网络配置，脚本执行发生在用户态的 tunnel 服务里，与内核数据面无关。

交叉引用统一收敛如下：`字段见 05-02 ｜ 原理见 06-05 ｜ 模块见 07-05`，服务错误码枚举另见 05-09，进程入口分派见 06-01，配置解析见 06-02；`tunnel` 服务模块能力见 07-05，脚本执行失败对应的错误码模块见 07-10，安全加固与攻击面总览见 08-05。本篇只回答「有哪些策略键、各自取值与作用域、解锁了什么、注入了什么变量、卸载后还在不在、踩了坑怎么查」，不展开 Manager 服务的令牌判定、IPC 结构与 WFP 规则实现。

| `LimitedOperatorUI` | `HKLM\Software\WireGuard\LimitedOperatorUI` | `REG_DWORD` | `1` | Network Configuration Operators 组 | 在该组桌面启动受限 UI，剥离密钥并禁用配置管理 | `docs/adminregistry.md` |
| `DangerousScriptExecution` | `HKLM\Software\WireGuard\DangerousScriptExecution` | `REG_DWORD` | `1` | tunnel 服务与四个脚本键 | 允许以 LocalSystem 执行 `PreUp` \| `PostUp` \| `PreDown` \| `PostDown` | `docs/adminregistry.md` |
| 键容器 | `HKLM\Software\WireGuard` | 注册表项 | 无 | 整机 | 卸载器清理整个该项 | `docs/adminregistry.md` |

两点需要立刻点明。其一，两个键都挂在同一个 `HKLM\Software\WireGuard` 项下，写入位置是 `HKLM` 而非 `HKCU`，因此影响整机、需要管理员权限，且 `docs/adminregistry.md` 明说卸载器会清理整个项——这意味着任何依赖它们做的定制在卸载或覆盖安装后都会消失。其二，官方给出的写入命令形如 `reg add HKLM\Software\WireGuard /v LimitedOperatorUI /t REG_DWORD /d 1 /f`，两个键共用同一模板，只换 `/v` 后面的值名；`REG_DWORD` 且值为 `1` 才生效，写成字符串 `REG_SZ` 或值 `0` 都不会触发文档描述的受限/脚本行为，具体判定需对照实际版本核验。

受限 UI 的能力矩阵是本篇第一张重点表，完全依据 `docs/adminregistry.md` 的四条限制与一句保留语整理。

| 功能项 | 内置 Administrators | Network Configuration Operators | 依据 |
|---|---|---|---|
| 启动与停止隧道 | 允许 | 允许，基本功能保留 | `docs/adminregistry.md` |
| 查看配置里的公钥、私钥、预共享密钥 | 允许 | 全部被剥离，界面不显示 | `docs/adminregistry.md` |
| 添加、删除、编辑、导入、导出配置 | 允许 | 全部禁止 | `docs/adminregistry.md` |
| 版本更新弹窗通知 | 允许 | 不显示弹窗 | `docs/adminregistry.md` |
| 执行版本更新 | 允许 | 不允许，但仍有 tab 指示可用 | `docs/adminregistry.md` |
| 退出 manager | 允许 | 禁止 | `docs/adminregistry.md` |
| UI 出现位置 | 内置管理员桌面 | 仅当 DWORD 1 才在该组桌面出现 | `docs/adminregistry.md`、`docs/enterprise.md` |

这里最容易读错的是「仍有 tab 指示可用」：`docs/adminregistry.md` 的原文是不显示版本更新弹窗通知、也不允许更新，但界面上仍有一个标签页指示更新可用。也就是说受限用户能「看见」有更新，却既不会被弹窗打扰、也无法触发升级，更新动作仍由管理员通过 04-04 的 `/update` 或 UI 完成（计划任务见 04-06）。另一处是「配置被剥离所有密钥」：受限 UI 里看到的配置不是原文件的副本，公钥、私钥、预共享密钥三种材料都被去掉，因此它不能用来抄密钥、也不能导出成可复用的完整配置，这与 03-04 的 DPAPI 安全存储是两条独立的保护线。

### 3. 逐项详解

#### 3.1 键路径、类型与作用域

两个键的完整路径分别是 `HKLM\Software\WireGuard\LimitedOperatorUI` 与 `HKLM\Software\WireGuard\DangerousScriptExecution`，官方写入模板为 `reg add HKLM\Software\WireGuard /v <值名> /t REG_DWORD /d 1 /f`，其中 `/f` 表示强制覆盖、`/t REG_DWORD` 指定 32 位整型、`/d 1` 给值。路径位于 `HKLM`（HKEY_LOCAL_MACHINE），意味着作用域是整机而非当前用户，任何登录到这台机器的相关账户都会受影响；写入需要管理员权限，这也和 `docs/attacksurface.md` 所述「manager 与 tunnel 服务以 LocalSystem 运行、UI 以高完整性令牌运行」的权限模型一致。核验用 `reg query HKLM\Software\WireGuard` 一次列出项下所有值。注意 `docs/adminregistry.md` 声明卸载器会清理整个 `HKLM\Software\WireGuard` 项，因此把别的自定义值塞进同一项并不会比这两个键更持久。

#### 3.2 `LimitedOperatorUI` 与内置组 S-1-5-32-556

`docs/adminregistry.md` 原文是：当该键设为 `DWORD(1)`，UI 会在属于 Network Configuration Operators 内置组（`S-1-5-32-556`）的用户桌面上启动，并对该组成员施加一组限制。`S-1-5-32-556` 是 Windows 内置的「网络配置操作员」组的固定 SID，成员默认能管理网络设置但不是完整管理员；`docs/enterprise.md` 相应说明「若设置了正确的注册表键，受限 UI 也可在该组所有成员的托盘启动」。要分清两个层次：键值为 1 决定「受不限限」，组归属决定「谁的桌面上出现」；两者都满足才得到受限 UI。内置 Administrators 组不受这组限制约束，他们看到的仍是完整 UI，UI 本来就会在他们的托盘出现（见 `docs/enterprise.md` 的 Manager Service 一节）。把这个键理解成「让普通用户变成管理员」是错的，它只是把一个只读、只能启停的界面投放到非管理员桌面。

#### 3.3 受限 UI 的四类限制逐条判读

`docs/adminregistry.md` 列了四条限制加一句保留语，可归为四类。第一类是密钥剥离：配置里的所有公钥、私钥、预共享密钥都被去掉，界面不展示，因而受限用户无法读取密钥材料，也无法通过导出得到完整可用配置。第二类是配置管理封禁：添加、删除、编辑、导入、导出配置一律禁止，这直接对应 03-04 的配置存储与 04-01 至 04-03 的配置键编辑能力被整体关掉。第三类是更新收敛：不显示版本更新弹窗通知、不允许执行更新，但仍保留一个标签页指示更新可用；更新入口因此只剩管理员侧的 `wireguard /update`（见 04-04）与 04-06 的 `schtasks` 定时任务。第四类是退出封禁：不允许退出 manager，避免受限用户把托盘服务关掉影响其他会话。保留语是「启动与停止隧道等基本功能保持不变」——这正是企业里把「链路开关」下放给一线、同时把「配置与密钥」收归管理员的典型用法（场景见 03-05、安全讨论见 08-05）。

#### 3.4 `DangerousScriptExecution` 与四个脚本键

`docs/adminregistry.md` 原文是：当该键设为 `DWORD(1)`，tunnel 服务会执行隧道配置中 `PreUp`、`PostUp`、`PreDown`、`PostDown` 四个选项所指定的命令。`docs/enterprise.md` 用「但只有设置了正确的注册表键」再次确认这是硬开关：未开启时，这四个键即便写进 `.conf` 也不会被执行。这一点与 04-02 讲配置键语法时的结论互相印证——解析器会接受并保存这四个键，但「接受」不等于「执行」，执行权在注册表开关手里。四个键按命名分别对应隧道启动前、启动后、停止前、停止后四个时点，`docs/enterprise.md` 只笼统说「隧道服务生命周期的若干时点」，精确顺序与失败时是否继续启停需对照实际版本核验，可定位 `docs/enterprise.md` 与 `tunnel/service.go`。开关判定与触发时序如图 04-07-02 所示，虚线表示「配置被解析」是始终发生的、与开关无关。

#### 3.5 `WIREGUARD_TUNNEL_NAME` 与 `%i` 的边界

`docs/adminregistry.md` 用一句很具体的话划清了与 Linux 的差异：「Rather than use `%i`，WireGuard for Windows instead sets the environment variable `WIREGUARD_TUNNEL_NAME` to the name of the tunnel when executing these scripts」。也就是说，Windows 客户端在执行这四个脚本时，把当前隧道名放进名为 `WIREGUARD_TUNNEL_NAME` 的环境变量里，脚本通过读该变量拿到隧道名；Linux `wg-quick` 的 `%i` 占位符在这里不存在，照抄含 `%i` 的 `PostUp` 行不会得到接口名，只会得到一个字面量或解析异常。变量的值是隧道名而非服务名，也不是适配器名：隧道名来自配置文件名，受 `conf/name.go` 的 `TunnelNameIsValid` 约束（长度 1 至 32、字母数字与 `_=+.-`、拒绝保留设备名与特殊字符），服务名则是 `ServiceNameOfTunnel` 拼出的 `WireGuardTunnel$<name>`（见 04-01、04-06）。脚本里若需要拼服务名，应自行加上前缀，不要指望环境变量已经带好。

#### 3.6 脚本键在 `conf/parser.go` 的解析特判

四个脚本键在解析器里有一处专门处理，值得单独点出，因为它影响写脚本时的注释习惯。`conf/parser.go` 的 `FromWgQuick` 在按键名分派之前有一段 `case "preup", "postup", "predown", "postdown"`：对这四个键，它不按 `#` 切断行内注释，而是取等号之后的整段内容作为值，并把 `comment` 清空。原因在于脚本命令本身常含 `#`（例如颜色值、正则、shell 片段），若按普通键那样把 `#` 当注释起始，命令会被截断。其余 `[Interface]` 与 `[Peer]` 键仍按通用逻辑处理行内注释与注释保真。因此写 `PostUp` 时不必担心 `#` 被吃掉，但也要意识到：这一整行在解析后就是脚本字符串本身，不要指望在行尾追加一句以 `#` 开头的说明还能被当成配置注释保留。解析状态机与注释保真的完整讨论见 06-02，字段见 05-04。

#### 3.7 LocalSystem 执行的安全代价

`docs/adminregistry.md` 对 `DangerousScriptExecution` 的警告措辞是全文最重的：执行以 Local System 用户身份进行，而该账户在操作系统里拥有最高权限，因此是恶意软件的真实目标，开启时须「极度审慎」，仅在确知后果时启用。这与 `docs/attacksurface.md` 的权限描述一致——tunnel 服务本就以 LocalSystem 运行，只是通过 `AdjustTokenPrivileges` 丢弃了除 `SeLoadDriverPrivilege` 外的大部分特权；一旦允许执行配置里的任意命令，等于把「能写配置文件」间接升级为「能以最高权限执行命令」。风险链条是：配置文件可被导入或投放（见 03-04、03-05），脚本键内容随配置走，开关又只需一个整机级 DWORD 值，三者叠加会显著扩大攻击面。因此 08-05 把「默认不执行、开启条件、最小权限」列为加固项；本篇的立场与文档一致，只解释机制，不推荐在生产环境默认开启。

#### 3.8 `ErrorRunScript` 与脚本失败的错误码

脚本执行失败会落到本仓库统一的错误码体系里。`services/errors.go` 的 `Error` 枚举中有一项 `ErrorRunScript`，其 `Error()` 字符串为 `An error occurred while running a configuration script command`，正好对应脚本命令执行出错；同文件还定义了 `ErrorCreateNetworkAdapter`、`ErrorSetNetConfig`、`ErrorFirewall` 等相邻阶段错误码。`DetermineErrorCode(err, serviceError)` 的返回逻辑是：若错误可 `errors.As` 成 `windows.Errno`，直接返回该 Win32 错误码；否则若传入了非零的 `serviceError`，返回它的数值；再否则返回 `NO_ERROR`。`CombineErrors` 则把服务错误码与底层错误包装成一条可读文本。排障时看到脚本相关失败，应先读环形日志（见 04-06 的 `wireguard /dumplog`），再对照 `services/errors.go` 判断是脚本本身返回非零、还是被相邻阶段错误掩盖。错误码枚举逐项见 05-09，服务退出与日志行为见 06-01、07-10。

#### 3.9 卸载清理与键的易失性

`docs/adminregistry.md` 开头明确「卸载器会清理整个 `HKLM\Software\WireGuard`」，并在结尾再次提示这些键「没有 UI、也不计划提供 UI，将来某个版本可能被移除」。这两句合起来给出运维结论：这两个键不是稳定的配置面，而是临时的高级旋钮。任何依赖 `LimitedOperatorUI` 的受限 UI 部署或依赖 `DangerousScriptExecution` 的脚本钩子，都应把「键的建立」写进部署脚本（见 03-05、04-06 的 `reg` 用法），并在每次升级、覆盖安装或卸载后复核键值是否还在；卸载后残留的配置目录与服务清理顺序见 03-06。把这两个键当成写入即永久生效的常规设置，是本篇第 7 节要专门纠正的误用。

### 4. 典型示例

第一组给出两个键的写入与核验命令，来自 `docs/adminregistry.md` 的官方模板，在提升的命令提示符或 PowerShell 中执行。命令形式见下方示例。

```powershell
reg add HKLM\Software\WireGuard /v LimitedOperatorUI /t REG_DWORD /d 1 /f
reg add HKLM\Software\WireGuard /v DangerousScriptExecution /t REG_DWORD /d 1 /f
reg query HKLM\Software\WireGuard
```

核验命令的典型输出如下。示例输出，具体格式需对照实际版本核验。

```text
> reg query HKLM\Software\WireGuard

HKEY_LOCAL_MACHINE\Software\WireGuard
    LimitedOperatorUI    REG_DWORD    0x1
    DangerousScriptExecution    REG_DWORD    0x1
```

逐行判读如下。首行 `HKEY_LOCAL_MACHINE\Software\WireGuard` 是所查询的注册表项，确认写在了 `HKLM` 而不是当前用户配置单元；若这里报「错误: 系统找不到指定的注册表项」，说明两个键都还没建立，此时 `LimitedOperatorUI` 与 `DangerousScriptExecution` 均按未开启处理，受限 UI 不会出现、四个脚本键也不会执行。第二行 `LimitedOperatorUI REG_DWORD 0x1` 有三段信息：值名必须与文档一字不差，类型必须是 `REG_DWORD` 而不是 `REG_SZ` 或 `REG_QWORD`，`0x1` 是十六进制的 1，只有这个值才触发文档描述的受限界面；若看到 `0x0`，界面仍按完整管理员 UI 呈现。第三行 `DangerousScriptExecution REG_DWORD 0x1` 同理，它一旦为 1，tunnel 服务就会以 LocalSystem 执行配置里的四个脚本键，这是整机级的行为变更，判读时不能只看「值存在」就认为安全。特别要注意输出里没有第四行其它值时属于正常——`docs/adminregistry.md` 只定义了这两个值，卸载器清理的是整个项而不是逐个值；反之，若这里出现拼写近似的值名（例如少一个字母或大小写混用），那不是官方键，不产生任何文档描述的效果，需对照 `docs/adminregistry.md` 实际版本核验。最后，`reg query` 只能证明键值已写入，不能证明受限 UI 已弹出或脚本已成功执行，后者仍要回到服务日志与运行时状态确认。

第二组给出一段带脚本键的配置示例，以及配套的说明。脚本键的语法归属见 04-02，此处只演示开关与环境变量的关系。

```conf
[Interface]
PrivateKey = yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=
Address = 10.0.0.2/32
DNS = 10.0.0.1
PostUp = echo %WIREGUARD_TUNNEL_NAME% up >> C:\wg-diag\hooks.log
PostDown = echo %WIREGUARD_TUNNEL_NAME% down >> C:\wg-diag\hooks.log

[Peer]
PublicKey = xTIBA5rboUvnH4htodjb6e697QjLERt1NAB4mZqp8Dg=
AllowedIPs = 0.0.0.0/0
Endpoint = 203.0.113.1:51820
```

这段配置里 `PostUp` 与 `PostDown` 用 `%WIREGUARD_TUNNEL_NAME%` 读取隧道名，是 Windows 客户端的写法；若照抄 Linux `wg-quick` 的 `%i`，脚本拿不到接口名。按 `docs/adminregistry.md`，只要 `DangerousScriptExecution` 不是 DWORD 1，这两行就只被解析保存、不会执行，日志里也不会出现 `up` 与 `down`；开启后它们才以 LocalSystem 身份运行，写文件位置、路径权限都要按最高权限账户重新评估。另需提醒：`conf/parser.go` 对四个脚本键不切行内 `#`（见 3.6），所以脚本命令里出现 `#` 不会被当注释截断，但也别在行尾追加 `# 说明` 指望它被当成配置注释保留。配置键全集见 04-01 至 04-03，脚本执行条件以本篇为准。

### 5. 速查表

下表把「想做什么 → 需要哪个键 → 怎么核验 → 代价」压缩成一行行查表项，具体命令回指 04-06 与本篇第 4 节。

| 目标 | 需要的键值 | 核验命令 | 主要代价 |
|---|---|---|---|
| 让非管理员看到只读托盘 UI | `LimitedOperatorUI` = `1` | `reg query HKLM\Software\WireGuard` | 密钥被剥离、配置管理封禁 |
| 允许下放启停隧道 | `LimitedOperatorUI` = `1`，无需额外键 | 让该组成员登录查看托盘 | 只能启停，不能改配置 |
| 执行 `PreUp` 等四个脚本键 | `DangerousScriptExecution` = `1` | `reg query HKLM\Software\WireGuard`，再看服务日志 | 以 LocalSystem 运行，攻击面扩大 |
| 在脚本里拿到隧道名 | 读 `WIREGUARD_TUNNEL_NAME` | 脚本内 echo 到日志 | 不是服务名、不是 `%i` |
| 关闭受限 UI 或脚本执行 | 删除对应值或改为 `0` | `reg query` 复核 | 需管理员权限，立即生效于整机 |
| 卸载后的状态复核 | 整项被清理 | `reg query` 应报找不到项 | 定制不持久，需重新写入 |
| 脚本失败定位 | 看 `ErrorRunScript` | `wireguard /dumplog` 见 04-06 | 错误码见 `services/errors.go` |

使用这张表时有两条约定。其一，所有 `reg` 操作都作用于 `HKLM\Software\WireGuard`，必须在提升的会话里执行；表格里的 `1` 指 `REG_DWORD` 类型的数值 1，`0` 或类型不符都不生效，具体判定需对照 `docs/adminregistry.md` 实际版本核验。其二，「主要代价」列不是建议清单而是风险提示，尤其第二行与第三行：受限 UI 的代价是能力被削，脚本开关的代价是权限被放大，二者方向相反，不要因为都写在同一个注册表项下就一并开启。

### 6. 版本差异

第一层是官方文档自己声明的易变性。`docs/adminregistry.md` 开头就说这些是「非常规、不推荐、没有 UI、也不计划提供 UI」的高级旋钮，且「将来某个版本可能被移除」，卸载器还会清理整个 `HKLM\Software\WireGuard`。因此本篇描述的两个键属于版本敏感事实：它们的存在性、值名、作用域在不同 master 快照之间可能变化，也可能被整体删掉。凡要把它们写进自动化部署脚本，都应把「键是否存在、值是否仍生效」列为升级后的复核项，并保留一份可重新写入的模板（见 3.9、04-06 的 `reg` 用法）。相比之下，`docs/enterprise.md` 描述的服务名、配置目录、日志入口属于稳定面，两者不可相提并论。

第二层是 `WIREGUARD_TUNNEL_NAME` 与 `%i` 的跨版本稳定性。`docs/adminregistry.md` 明确「不要使用 `%i`，改用环境变量 `WIREGUARD_TUNNEL_NAME`」，这是 Windows 客户端的长期设计取向，与 Linux `wg-quick` 的 `%i`、`SaveConfig`、`resolvconf` 语义永久分离。变量值取自隧道名，而隧道名合法性由 `conf/name.go` 的 `TunnelNameIsValid`、`allowedNameFormat` 正则、保留设备名列表与 `specialChars` 常量决定；这些是源码细节，跨版本有微调可能，字段名与取值需对照 `upstream_src/conf/name.go` 当前版本核验。服务名前缀 `WireGuardTunnel$` 来自 `ServiceNameOfTunnel`，属稳定约定（见 04-06）。

第三层是错误码与解析行为的版本相关面。`services/errors.go` 的 `Error` 枚举项、`ErrorRunScript` 的返回字符串、以及 `DetermineErrorCode` 对 `windows.Errno` 与服务自定义码的取舍，都需对照 `upstream_src/services/errors.go` 核验（字段见 05-09）；`conf/parser.go` 对四个脚本键「不切 `#` 注释」的特判属解析实现，跨版本可能调整，相关机制见 06-02、注释保真字段见 05-04。四个脚本键的精确触发时点，`docs/enterprise.md` 只给「隧道服务生命周期的若干时点」这一笼统表述，具体顺序需对照 `tunnel/service.go` 实际版本核验，本篇不写死。凡涉及具体版本号、注册表子项新增、脚本执行时序与错误码数值，统一标注「需对照实际版本核验」，可定位路径为 `docs/adminregistry.md`、`docs/enterprise.md`、`conf/name.go`、`conf/parser.go`、`services/errors.go`、`tunnel/service.go`。

### 7. 常见误用与调试

1. **以为写了脚本键就会执行**。`PreUp`、`PostUp`、`PreDown`、`PostDown` 被 `conf/parser.go` 正常解析保存，但 `docs/enterprise.md` 明确「只有设置了正确的注册表键」才运行。未把 `DangerousScriptExecution` 设为 DWORD 1 时，脚本静默不执行是最常见的「配了没生效」根因，先 `reg query` 再谈脚本逻辑。

2. **照抄 Linux 的 `%i`**。`docs/adminregistry.md` 专门写「Rather than use `%i`」，Windows 只注入 `WIREGUARD_TUNNEL_NAME`。把含 `%i` 的 `PostUp` 行搬过来，轻则拿到字面量、重则命令语义错乱；同理，`SaveConfig`、`resolvconf`、`iptables` 都不是 Windows 客户端能力（见 04-02、04-05）。

3. **把 `WIREGUARD_TUNNEL_NAME` 当服务名或接口名用**。它的值是隧道名（来自文件名、受 `conf/name.go` 约束），不是 `WireGuardTunnel$<name>`，也不是动态创建的适配器名。脚本里要拼服务名得自己加前缀，要找适配器得走 `Get-NetAdapter`（见 04-06）。

4. **用 `REG_SZ` 写值或写成 `0`**。官方模板是 `/t REG_DWORD /d 1`，类型不符或值不为 1 都不会触发文档描述的行为。`reg query` 里看到 `REG_SZ`、`0x0` 或拼写近似的值名，都要按「未开启」处理，具体判定需对照 `docs/adminregistry.md` 实际版本核验。

5. **在 `HKCU` 下找键**。两个键都在 `HKLM\Software\WireGuard`，是整机级设置。在 `HKCU` 里增删同名值完全不影响 manager 与 tunnel 服务，排障时第一步应确认查询的是 `HKEY_LOCAL_MACHINE`。

6. **低估 LocalSystem 执行的代价**。`docs/adminregistry.md` 用「恶意软件的真实目标」「极度审慎」形容这个开关，因为配置文件可被导入或批量投放，脚本内容随配置走，开启后等于把写配置的能力间接升级为最高权限命令执行。默认应关闭，确需开启时配合配置目录 ACL 与最小权限一并评估（见 03-04、08-05）。

7. **以为受限 UI 能改配置或能看到密钥**。`docs/adminregistry.md` 的四条限制是硬约束：密钥被剥离、增删改导入导出全禁、更新被禁、退出 manager 被禁，只保留启停隧道。想把「改配置」下放给该组用户是做不到的，那属于内置 Administrators 的能力。

8. **把两个键当成永久设置**。`docs/adminregistry.md` 明说卸载器清理整个 `HKLM\Software\WireGuard`、且这些键将来可能移除。升级或覆盖安装后受限 UI 消失、脚本突然不跑，第一反应应是用 `reg query` 复核键值，而不是怀疑脚本本身或 UI 进程。

9. **脚本行尾追加 `#` 注释**。`conf/parser.go` 对四个脚本键不切行内 `#`，命令里的 `#` 不会被截断，但你在行尾写的 `# 说明` 也会一并成为命令字符串的一部分，可能让命令执行失败。注释要写在脚本键之外的独立行（解析特判见 3.6、机制见 06-02）。

推荐的调试顺序是：先 `reg query HKLM\Software\WireGuard` 确认键值与类型，再用 `wireguard /dumplog` 读共享环形日志（见 04-06）找 `ErrorRunScript` 或相邻阶段错误码，接着对照 `services/errors.go` 判断失败来源，最后才检查脚本命令本身与 `%WIREGUARD_TUNNEL_NAME%` 的展开结果。受限 UI 不复现时，先确认 `LimitedOperatorUI` 为 1，再确认目标账户确实属于 `S-1-5-32-556` 组，二者缺一不可。整条链路与图 04-07-01、图 04-07-02 的作用域划分一致，错误码逐项见 05-09，服务与安全加固讨论见 07-10、08-05。

## 04-08 配置排错与命令速查手册

### 1. 本篇定位与覆盖范围

本篇是 04「配置与命令行」册的收官篇，采用 B 手册字典型骨架，定位是把前七篇攒下的配置键、命令行开关、运行时查询、系统管理命令与注册表策略，压成一套「按现象反查」的排错手册。大纲交给它四项内容：错误现象到配置域的映射、隧道名与路由冲突检测、最小可复现配置集、版本差异速查。它不新增任何配置语法，也不新增任何命令，而是回答运维现场最实际的问题：界面报了一句错、日志打了一行警告、隧道起不来或起来却不通，第一步该看哪个键、第二步该跑哪条命令、输出怎么读、读完往哪儿修。

去重边界在本篇尤其要紧，因为速查手册最容易变成清单的二次抄写。04-01 至 04-03 是全部配置键的唯一权威源，04-04 是 `wireguard.exe` 斜杠开关的唯一权威源，04-05 是 `wg(8)` 子命令与 `wg show` 输出样例的唯一权威源，04-06 是 `sc` / PowerShell / 诊断系统命令的唯一权威源，04-07 是两个管理员注册表键与四个脚本键的唯一权威源。本篇一律不重列这些清单：表格里出现的是「错误码、告警文本、现象到诊断命令的映射、隧道名规则、最小可复现集」，属于排错索引而非配置或命令全集；凡需要某个键或开关的完整语义，正文只写「配置见 04-xx」「开关见 04-04」「命令见 04-06」。这与总纲第 2 节的强制约束一致：04 全册不展开模块内部实现与结构体字段，本篇同样只讲「查什么、怎么判、怎么修」。

本篇的一手依据比同册其他篇更偏向错误与告警路径，全部落在本地快照里。`conf/parser.go` 的 `FromWgQuick` 给出配置解析期的全部校验点与 `ParseError` 文本，是「配置导入失败」这一类现象的根；`conf/name.go` 的 `TunnelNameIsValid`、`ServiceNameOfTunnel` 给出隧道名合法性与服务名拼接，是「隧道名被拒」「服务名对不上」的根；`services/errors.go` 的 `Error` 枚举、`Error()` 字符串、`DetermineErrorCode` 与 `CombineErrors` 给出服务启动各阶段的错误码，是「服务起不来」的根；`tunnel/pitfalls.go` 的 `evaluateStaticPitfalls`、`evaluateDynamicPitfalls` 与三个 `pitfall*` 函数给出三类主动告警，是「日志里出现 Warning」的根；`ringlogger/ringlogger.go` 与 `ringlogger/dump.go` 给出日志行的时间戳格式与 tag 前缀，让「典型输出」有据可依；`main.go` 的 `setLogFile`、`fatal`、`usage()` 与各开关分支说明命令行错误如何落到标准错误；`docs/enterprise.md` 给出 `wg show` 的真实输出样例与 `wireguard /dumplog` 的用法。内核数据面由外部项目 WireGuardNT 提供，本仓库只负责 IOCTL 配置下发与网络配置，因此本篇所有结论都停在用户态与配置层，不把 Linux `wg-quick` 的 `iptables`、`%i`、`SaveConfig`、`resolvconf` 或 `wireguard-go` 用户态数据面写成 Windows 客户端能力。

交叉引用统一收敛如下：`字段见 05-02 ｜ 原理见 06-02 ｜ 模块见 07-01`，密钥与端点类型见 05-03，错误码与 ringlogger 结构见 05-09；配置解析机制见 06-02，进程入口分派见 06-01，适配器与路由下发见 06-05 与 06-06，kill-switch 与 WFP 见 06-09，IPC 与环形日志见 06-11；`conf` 配置管理模块见 07-01，`tunnel` 服务模块见 07-05，`ringlogger` 与 `services` 模块见 07-10。更完整的故障案例库按现象组织在 08-04，日志采集实战在 08-01，诊断决策树在 08-03——本篇是它们随手可翻的索引页，不替代案例与决策树。本篇只回答「有哪些错误现象与错误码、各自指向哪个配置域、用哪条命令取证、输出怎么读、最小可复现配置长什么样」。

### 3. 逐项详解

#### 3.1 解析期错误：`conf/parser.go` 的三层校验

配置导入失败几乎都能在 `FromWgQuick` 里找到对应分支，按「结构 → 值域 → 语义」三层排查最省事。结构层：每一行先按 `#` 切出注释，再按 `=` 切键值；不在任何段内的行报 `Line must occur in a section`，缺 `=` 报 `Config key is missing an equals separator`，`=` 后为空报 `Key must have a value`，`[Interface]` 与 `[Peer]` 段里出现白名单之外的键分别报两个 `Invalid key for ... section`。值域层：`parseIPCidr` 用 `netip.ParsePrefix` 与 `netip.ParseAddr` 解析地址，失败报 `Invalid IP address`；`splitList` 遇连续逗号报 `Two commas in a row`；`parseKeyBase64` 要求 Base64 解码后恰为 32 字节，否则报 `Invalid key` 或 `Keys must decode to exactly 32 bytes`；`parseMTU` 限定 576 至 65535，`parsePort` 与 `parsePersistentKeepalive` 限定 0 至 65535 且后者接受 `off`；`parseEndpoint` 要求有冒号端口、IPv6 方括号里必须是合法 v6 地址。语义层：函数末尾强制 `sawPrivateKey` 为真，否则报 `An interface must have a private key`；逐个 peer 检查 `PublicKey.IsZero()`，任一为零报 `All peers must have public keys`。这三层之外的 `FromWgQuickWithUnknownEncoding` 会在首次解析失败后尝试多种 Unicode 编码重解，因此「文件编码不对」也可能表现为上述某条错误，而不是独立的编码报错（机制见 06-02）。

#### 3.2 隧道名与路由冲突检测

隧道名冲突有两条独立线索。其一是命名合法性：`conf/name.go` 的 `TunnelNameIsValid` 先排除 Windows 保留设备名与特殊字符，再要求匹配 `^[a-zA-Z0-9_=+.-]{1,32}$`，且不允许以 `.` 开头或结尾；`ServiceNameOfTunnel` 在非法时返回 `Tunnel name is not valid`，合法时拼出 `WireGuardTunnel$<name>`。含空格、中文、`$` 或超过 32 字符的文件名会在这一步被拒，`docs/enterprise.md` 里 `/installtunnelservice C:\path\to\some\myconfname.conf` 生成 `WireGuardTunnel$myconfname` 正是合法样例。其二是路由层面的「弱主机发送」检测：`tunnel/pitfalls.go` 的 `pitfallWeakHostSend` 遍历 `winipcfg.GetIPForwardTable2` 得到的路由表，对每个 peer 的 `Endpoint.Host` 找到最长前缀匹配、取最低度量，若最终出接口不是本隧道接口、且该接口开启了 `ForwardingEnabled` 或 `WeakHostSend`，就记录「会致路由环路」的告警。排查「能连上但流量绕路或环回」时，先按 04-06 的 `Get-NetRoute` 看端点网段路由是否落在隧道接口，再看日志里有没有这条告警（原理见 06-06）。

#### 3.3 服务错误码与 `DetermineErrorCode`

`services/errors.go` 把服务启动各阶段映射成一个 `Error` 枚举，从 `ErrorRingloggerOpen`、`ErrorLoadConfiguration`、`ErrorCreateNetworkAdapter` 一路到 `ErrorDeviceSetConfig`、`ErrorSetNetConfig`、`ErrorRunScript`、`ErrorWin32`，共 17 项，逐项文本见第 2 节第二张表。判读的关键在两个函数：`DetermineErrorCode(err, serviceError)` 先看错误能否 `errors.As` 成 `windows.Errno`，能则直接返回该 Win32 错误码；否则若传入了非零的 `serviceError` 就返回它的数值；再否则返回 `NO_ERROR`。`CombineErrors(err, serviceError)` 则把服务错误码字符串与底层 `err` 用 `fmt.Errorf("%v: %w", ...)` 包装成一条可读文本。因此同一个故障，日志里可能同时出现「`Unable to ...`」这样的语义串和一个 Win32 数值码，二者不矛盾：前者是阶段定位，后者是底层原因。第 2 节表格的「首选取证命令」一列就是按阶段给出的，逐项错误码枚举见 05-09，服务启动顺序见 06-05，错误码模块见 07-10。

#### 3.4 三类主动告警：`tunnel/pitfalls.go`

`evaluateStaticPitfalls` 起两个 goroutine 分别跑 `pitfallDnsCacheDisabled` 与 `pitfallVirtioNetworkDriver`，`evaluateDynamicPitfalls` 针对地址族起 `pitfallWeakHostSend`。第一条查 `dnscache` 服务的 `StartType`，若为 `mgr.StartDisabled` 就警告「请重新启用」，因为 DNS 客户端缓存被禁用会影响解析。第二条用 `NtQuerySystemInformation` 枚举内核模块找 `netkvm.sys`，读到文件版本后与源码里的 `minimumGoodVersion`（注释写成 v100.85.104.20800）比较，落在旧版本区间就警告升级 VirtIO 驱动。第三条即 3.2 讲的弱主机发送与路由环路检测。三条都以 `Warning:` 前缀写进共享环形日志，不是致命错误：隧道可能照常起来，但存在解析或路由隐患。因此「日志有 Warning 但界面没报错」不应被忽略，具体版本阈值与检测条件需对照 `upstream_src/tunnel/pitfalls.go` 实际版本核验。

#### 3.5 日志行格式与来源

排障取证几乎都要落到 `wireguard /dumplog`（开关见 04-04、采集命令见 04-06），而读懂它需要先知道格式。`ringlogger/ringlogger.go` 里每行写入时构造成 `[TAG] <内容>`，`WriteTo` 再用 `fmt.Fprintf(out, "%s: %s\n", time.Unix(0, timeNs).Format("2006-01-02 15:04:05.000000"), line...)` 输出，所以一行日志形如 `年-月-日 时:分:秒.六位微秒: [tag] 内容`。tag 来自各进程初始化：`manager/service.go` 用 `InitGlobalLogger(logFile, "MGR")`，`tunnel/service.go` 用 `"TUN"`，`main.go` 的 `/ui` 分支用 `"GUI"`，`ringlogger/dump.go` 只读映射用 `"DMP"`。于是看到 `[MGR]` 就知道是 manager 服务写的、`[TUN]` 是某条隧道服务写的，定位多隧道问题时很有用。`ringlogger` 常量 `maxLines = 2048`、`maxLogLineLength = 512` 决定它是有界环形缓冲，旧行会被覆盖，因此故障发生后应尽快 dump 到文件（格式见 05-09、共享内存与读取链见 06-11、模块见 07-10）。

#### 3.6 最小可复现配置集

「最小可复现配置集」是把问题从复杂生产配置里剥离出来的标准手法，本篇给的是组合原则，不重列配置键全集（见 04-01 至 04-03）。原则是：一条隧道、一个 `[Interface]`、一个 `[Peer]`，只保留必需键——`[Interface]` 的 `PrivateKey` 与 `Address`，`[Peer]` 的 `PublicKey` 与 `AllowedIPs`，以及需要对端主动连入或本端主动连出时的 `Endpoint`；先不写 `DNS`、`MTU`、`ListenPort`、`PresharedKey`、`PersistentKeepalive`、`Table`、四个脚本键，也不启用 04-07 的注册表策略。用这份最小集若能握手成功，再逐一把生产配置里的键加回去，第一个让故障复现的键就是嫌疑域；若最小集仍失败，则问题多半在密钥配对、端点可达性、系统服务或路由，而不在某个可选配置键。配合 04-06 的 `Get-NetRoute` 与 04-05 的 `wg show`，可把「配置问题」与「网络问题」分开。最小集仍然受 3.1 的语义校验约束：没有 `PrivateKey`、或 `[Peer]` 缺 `PublicKey`，解析器根本不会让它进入运行阶段。

投放最小集时还要留意命名与存储链路两处附带条件。文件名即隧道名，必须过 `conf/name.go` 的 `TunnelNameIsValid`，否则 `FromWgQuick` 开头就会以 `Tunnel name is not valid` 拒绝，服务名也无从拼出；因此做对照实验时建议固定一个短名如 `mintest`，只改配置内容而不改文件名，避免把命名问题误算成配置问题。若按 03-04 的路径把 `.conf` 放进 `%ProgramFiles%\WireGuard\Data\Configurations\`，manager 服务会把它加密成 `.conf.dpapi` 并删除明文，之后 `wg(8)` 交互就需要 Local System 或 Administrator 权限（见 04-05）；排障期间若希望用普通权限反复 `wg show`，可改用 `/installtunnelservice` 直接指向一份不在该目录里的明文 `.conf`（见 04-04、03-03），但实验结束后应把临时配置清理掉，避免遗留可被低权限读取的私钥。这两点不改配置键本身，却常常决定最小集能不能顺利跑起来，属于「环境而非配置」的排障分支。

#### 3.7 诊断命令的组合顺序

排障不是把所有命令跑一遍，而是按层取证。第一层配置与命名：先看导入时的 `ParseError` 文本，对照第 2 节第一张表与 `conf/name.go` 规则；第二层服务与错误码：`sc query`、`wireguard /dumplog`，对照 `services/errors.go`；第三层适配器与路由：`Get-NetAdapter`、`Get-NetRoute`、`Get-NetIPConfiguration`，看 AllowedIPs 是否落成路由、DNS 是否按 04-02 生效；第四层握手与端点：`wg show` 看 `latest handshake` 与 `transfer`（输出判读见 04-05、原理见 06-06）。四层顺序如图 04-08-02 所示，前一层通过后才进入下一层，日志为各层提供旁证。所有命令的开关与参数分别回指 04-04、04-05、04-06，本篇只固定「先后顺序」而不重列命令清单。

### 4. 典型示例

第一组给出一次排障取证的完整命令序列，命令本身见 04-04 至 04-06，此处只固定组合顺序。命令形式见下方示例。

```powershell
sc query 'WireGuardTunnel$mytunnel'
wireguard /dumplog > C:\wg-diag\dump.log
wg show mytunnel
Get-NetRoute -DestinationPrefix 10.0.0.0/24 | Format-Table InterfaceIndex, DestinationPrefix, NextHop
reg query HKLM\Software\WireGuard
```

`wireguard /dumplog` 的典型输出如下，其中三条 `Warning` 文本取自 `tunnel/pitfalls.go`，时间戳与 tag 前缀取自 `ringlogger/ringlogger.go` 与 `ringlogger/dump.go`。示例输出，具体格式需对照实际版本核验。

```text
> wireguard /dumplog

2026-11-11 09:12:04.002915: [TUN] Warning: the "DNS Client" (dnscache) service is disabled; please re-enable it
2026-11-11 09:12:04.117340: [TUN] Warning: the VirtIO network driver (NetKVM) is out of date and may cause known problems; please update to v100.85.104.20800 or later
2026-11-11 09:12:05.663018: [TUN] Warning: the "Ethernet" interface has Forwarding/WeakHostSend enabled, which will cause routing loops
```

逐行判读如下。三行的公共前缀都遵循 `年-月-日 时:分:秒.六位微秒: [TUN] 内容` 这一格式：`2026-11-11 09:12:04.002915` 是 `ringlogger` 用 `2006-01-02 15:04:05.000000` 布局输出的微秒级时间戳，用于把三条告警与同一时刻的服务动作对齐；`[TUN]` 是 `tunnel/service.go` 以 `InitGlobalLogger(logFile, "TUN")` 写入的进程标签，若某行是 `[MGR]` 则来自 `manager/service.go`，是区分「哪条隧道服务」与「管理服务」的第一线索。第一条 `dnscache service is disabled` 出自 `pitfallDnsCacheDisabled`，它查到 DNS Client 服务的启动类型为禁用后发出，修复方向是恢复该服务，否则依赖域名解析的 `Endpoint` 可能失败，对应 `services/errors.go` 的 `ErrorDNSLookup`。第二条 `VirtIO network driver (NetKVM) is out of date` 出自 `pitfallVirtioNetworkDriver`，它枚举内核模块找到 `netkvm.sys` 并比对文件版本，落在旧区间就提示升级到 v100.85.104.20800 或更高，这是虚拟化环境特有的已知问题，与 WireGuard 配置本身无关。第三条 `Forwarding/WeakHostSend ... routing loops` 出自 `pitfallWeakHostSend`，说明到某个 peer 端点的路由最终落在了非隧道接口、且该接口开启了转发或弱主机发送，可能形成路由环路，应结合 `Get-NetRoute` 检查端点网段与接口索引（原理见 06-06）。三条都是 `Warning` 而非致命错误，服务通常仍能启动，但它们分别指向 DNS、驱动与路由三个不同隐患域，正好演示「同一份日志按前缀分类、按文本定位域」的判读方法。若日志里出现的是 `Unable to ...` 这类 `Error()` 字符串而非 `Warning`，则改用第 2 节第二张表按阶段反查，并注意 `DetermineErrorCode` 可能同时透传一个 Win32 数值码。

第二组给出 3.6 所述的最小可复现配置集，只保留必需键，用于把生产配置里的可疑项逐一切回。配置形式见下方示例。

```conf
[Interface]
PrivateKey = yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=
Address = 10.0.0.2/32

[Peer]
PublicKey = xTIBA5rboUvnH4htodjb6e697QjLERt1NAB4mZqp8Dg=
AllowedIPs = 10.0.0.0/24
Endpoint = 203.0.113.1:51820
```

这份配置满足 `FromWgQuick` 的语义校验：有 `PrivateKey`、`[Peer]` 有 `PublicKey`，两个密钥都是 32 字节 Base64，`Address` 与 `AllowedIPs` 是合法 CIDR，`Endpoint` 带端口。它刻意不写 `DNS`、`MTU`、`ListenPort`、`PresharedKey`、`PersistentKeepalive`、`Table` 与四个脚本键，也不依赖 04-07 的注册表开关，因此一旦它能握手，就可以把生产配置里的可选键逐个加回，第一个导致故障复现的键即为嫌疑域。若这份最小集也失败，优先怀疑两端密钥是否配对、`Endpoint` 是否可达、服务是否启动、`AllowedIPs` 路由是否落到隧道接口，而不是某个可选配置键。配置键完整语义见 04-01 至 04-03，字段见 05-02。

### 5. 速查表

下表把最常见的现象压成「首查 → 次查 → 修复方向」三列，命令与开关的完整语义分别回指 04-04 至 04-07。

| 现象 | 首查 | 次查 | 修复方向 |
|---|---|---|---|
| 导入配置报 `Invalid key` | 错误文本对照第 2 节第一表 | `conf/parser.go` 键白名单 | 删未知键，见 04-01 至 04-03 |
| 导入报缺私钥或缺公钥 | `[Interface]` / `[Peer]` 必填项 | `sawPrivateKey`、`PublicKey.IsZero` | 补密钥，见 04-02、04-03 |
| 隧道名被拒 | `TunnelNameIsValid` 规则 | `conf/name.go` 保留名与正则 | 改名，见 04-01 |
| 服务起不来 | `sc query` 状态 | `wireguard /dumplog` 与错误码表 | 按阶段修，见 04-06、05-09 |
| 提示 `Unable to load configuration` | 配置文件路径与权限 | `.conf.dpapi` 形态，见 03-04 | 修路径或权限 |
| 提示 `Unable to resolve ... endpoints` | `Endpoint` 域名 | `dnscache` 告警、DNS 配置 | 修解析，见 04-03、04-02 |
| 服务运行但无握手 | `wg show` 的握手与流量 | `Get-NetRoute` 与端点可达性 | 查密钥与端点，见 04-05 |
| 日志有 `routing loops` 告警 | `pitfallWeakHostSend` 文本 | `Get-NetRoute` 与接口标志 | 关转发或弱主机发送 |
| 日志有 `dnscache` 告警 | `pitfallDnsCacheDisabled` 文本 | DNS Client 服务启动类型 | 恢复服务 |
| 脚本键不执行 | `reg query` 的 DWORD 值 | 04-07 开关与 `ErrorRunScript` | 设 `DangerousScriptExecution=1` |
| 升级后策略失效 | `reg query` 是否有项 | 卸载清理整个键，见 04-07 | 重新写入键值 |

使用这张表时记住两条：其一，「首查」给的是成本最低、信息量最大的一步，不要一上来就重装或改一堆配置；其二，表格里的 `\|` 是转义后的竖线，实际命令与路径按半角书写，含 `$` 的服务名在 PowerShell 里用单引号包裹。本篇所有表格都是索引，不替代 08-04 的完整故障案例与 08-03 的诊断决策树；遇到表里没有的现象，按图 04-08-02 的四层顺序逐层取证，再带着证据回查对应权威源。

### 6. 版本差异

第一层是「事实锚点」与「版本相关数值」的分离。本篇引用的机制性结论——解析分结构、值域、语义三层校验，隧道名受 `conf/name.go` 正则与保留名约束，服务错误码分阶段，`pitfalls.go` 产三类 `Warning`，日志为有界环形缓冲且带 `MGR` / `TUN` / `GUI` 标签——都属于源码结构层面的稳定结论，可直接用于判读。而具体的错误串措辞、`Error()` 返回文本、`services/errors.go` 的枚举项数量与顺序、`pitfallVirtioNetworkDriver` 里的 `minimumGoodVersion` 版本阈值、`maxLines` 与 `maxLogLineLength` 数值，都是版本相关事实，需对照 `upstream_src/conf/parser.go`、`upstream_src/conf/name.go`、`upstream_src/services/errors.go`、`upstream_src/tunnel/pitfalls.go`、`upstream_src/ringlogger/ringlogger.go` 当前版本核验。本篇第 2 节表格已把「措辞需对照实际版本核验」写明，正是这个约定的落地。

第二层是本地化与输出格式。`conf/parser.go` 的错误原因串经 `l18n.Sprintf` 生成本地化文本，不同语言环境下界面显示与源码里的英文原因串不完全一致；`ringlogger` 的时间戳用固定布局 `2006-01-02 15:04:05.000000`，但具体时区、tag 拼写与各进程写入顺序随运行场景变化。因此本篇给的「典型输出」是按源码格式构造的示例，已标注「示例输出，具体格式需对照实际版本核验」，排障时应以现场实际行为准，不要拿示例文本做字符串精确匹配。同理，`sc query`、`wg show`、`reg query` 的输出格式分别属于 Windows 与 wireguard-tools 的版本面，回指 04-06 与 04-05。

第三层是跨册与跨平台的边界。04 册本身是配置与命令的唯一权威源，本篇作为其收官篇只做索引与判读；05 册给字段定义、06 册给机制与调用链、07 册给模块能力、08 册给案例与决策树，四者都不重列配置或命令清单。版本基准是上游仓库 master 快照（2026-11 抓取）、WireGuardNT 1.1、Go 1.27.1、Windows 10 / Server 2019 及以上与 amd64 / x86 / arm64 三种 MSI；凡涉及具体版本号、驱动版本、MSI 文件名与下载 URL 的时效性数值，一律按总纲第 9 节写「需对照实际版本核验」。特别提醒：Linux `wg-quick` 的 `%i`、`SaveConfig`、`resolvconf`、`iptables` 与 `wireguard-go` 用户态数据面都不属于 Windows 客户端能力，任何把它们写进排错结论的做法都是错误迁移（见 04-02、04-05、04-07）。

### 7. 常见误用与调试

1. **把解析错误当服务错误处理**。「`Invalid key for [Interface] section`」来自 `conf/parser.go`，是配置文件本身不合法，重启服务或重装驱动都不会解决；「`Unable to load configuration from path`」来自 `services/errors.go`，是服务读不到文件。前者改配置（见 04-01 至 04-03），后者查路径与权限（见 03-04），两者分属第 2 节不同表格。

2. **照搬 Linux 排障习惯**。用 `wg show wg0` 查固定接口名、用 `iptables` 找规则、用 `%i` 写脚本、指望 `SaveConfig` 回写，都是把 `wg-quick` 或 wireguard-go 的语义套到 Windows 客户端上。Windows 侧用隧道名定位实例（见 04-05）、用 `Get-NetRoute` 看路由（见 04-06）、脚本用 `WIREGUARD_TUNNEL_NAME`（见 04-07），三者与 Linux 不通用。

3. **忽略 `Warning` 级告警**。三条 `pitfalls.go` 告警不阻断启动，但分别指向 DNS 缓存禁用、VirtIO 驱动过旧、弱主机发送致路由环路。「界面没报错」不等于没问题，日志里的 `Warning` 应按 3.4 逐条判读，具体阈值需对照实际版本核验。

4. **把 `wg show` 的服务状态与 `sc query` 混为一谈**。`sc query` 显示服务 RUNNING 只说明 tunnel 服务在跑；握手是否推进要看 `wg show` 的 `latest handshake` 与 `transfer`（输出判读见 04-05）。服务起来了却无流量，应查端点、密钥与 AllowedIPs，而不是反复重启服务。

5. **在生产配置上直接试错**。一上来就改 `MTU`、`DNS`、`Table`、脚本键，会让变量失控。正确做法是先上 3.6 的最小可复现配置集，确认基线可握手，再逐一把生产键加回，第一个复现故障的键即嫌疑域。

6. **隧道名含空格、中文或 `$`**。`conf/name.go` 只允许长度 1 至 32 的字母数字与 `_=+.-`，并拒绝保留设备名与特殊字符。文件名不合规时，`FromWgQuick` 开头的 `TunnelNameIsValid` 检查就会失败，表现为导入被拒；同时记住服务名是 `WireGuardTunnel$<name>`，`$` 是分隔符而非名字的一部分（见 04-01、04-06）。

7. **把 `Error()` 文本与 Win32 数值码对立起来**。`DetermineErrorCode` 可能直接透传 `windows.Errno`，`CombineErrors` 又会把服务错误码字符串与底层 `err` 包装在一起。日志里同时出现「`Unable to ...`」和一个数字码是正常的，前者定位阶段、后者给底层原因，不要只取其一。

8. **脚本不执行就改脚本内容**。`PreUp` 等四个键只有在 `DangerousScriptExecution` 为 `REG_DWORD` 1 时才运行（见 04-07）。先 `reg query HKLM\Software\WireGuard` 确认开关，再谈脚本逻辑；若日志出现 `ErrorRunScript`，才轮到检查命令本身与 `%WIREGUARD_TUNNEL_NAME%` 的展开。

9. **故障后迟迟不导日志**。`ringlogger` 是有界环形缓冲（`maxLines` 与 `maxLogLineLength` 常量），旧行会被覆盖。故障发生后应尽快 `wireguard /dumplog > 文件`（见 04-06），否则关键的错误行可能已被冲掉；`/dumplog /tail` 适合持续采集，不适合事后回捞。

10. **升级后不复核策略键**。`docs/adminregistry.md` 明说卸载器清理整个 `HKLM\Software\WireGuard`、且这些键将来可能移除。升级后受限 UI 消失或脚本不跑，先用 `reg query` 复核键值，再怀疑别的（见 04-07）。

推荐的调试顺序与图 04-08-02 一致：先按第 2 节第一张表与 `conf/name.go` 排除配置与命名问题，再用 `sc query` 与 `wireguard /dumplog` 对照 `services/errors.go` 定位服务阶段，接着用 `Get-NetAdapter`、`Get-NetRoute`、`Get-NetIPConfiguration` 核验适配器与路由，最后用 `wg show` 看握手与流量；涉及策略与脚本的分支用 `reg query` 收口。四层都过仍不通时，带着日志与 `wg show` 输出转 08-04 的案例库按现象反查。错误码逐项见 05-09，解析与下发机制见 06-02、06-05、06-06，模块归属见 07-01、07-05、07-10。
