# WhatsApp 技术资料 · SUP-03 DNS 辅助识别与 ECH 机制评估

## SUP-03-01 方案提出与前提辨析

### 1. 方案背景

SUP-01 论证了端到端加密使 OTP 语义对网络不可见，SUP-02 论证了事件关联方案的三处技术断点与因果链断裂。在此基础上，又产生了一条看似更朴素的补救思路：既然读不到消息内容，能否退一步，通过**分析 DNS 流量，按不同域名判断用户当前正在进行的操作**？其设想是——如果用户先查询了某登录相关域名、随后又出现即时通讯流量，就把两者关联起来；如果域名本身能细粒度到业务（例如 `login`、`pay`、`otp` 各有独立域名），那么"判断当前操作"这件事就有了一个可观测的抓手。

这条思路比直接识别 OTP 内容更弱，因为它只求"判断操作类型"，不求"读取消息语义"。但正因如此，它更容易被误认为可行。本文要证明的是：即使把目标降到"只判断操作"，这条路径的主导前提——**域名能够映射到操作**——在现代移动应用的架构下也已经不成立。叠加 DNS 分析既补不上 SUP-02 的条件 A，也无法触及 SUP-01 的加密边界和 SUP-02 的因果链断裂。

### 2. 关键前提：域名到操作的映射是否稳定

"按域名判断操作"隐含一个前提：**不同的业务操作落在不同域名上，且这个映射稳定、可观测**。这个前提并非凭空而来，它来自早期 Web 应用的真实实践，因此不能简单否定；但它的适用范围有明确边界。下图把前提成立与失效的两条路径并列画出。

### 3. 老式 Web 应用：前提部分成立

必须明确一点：**对一部分老式 Web 应用，这个前提确实成立**。早期 Web 系统常把不同业务拆到不同路径或子域上，例如 `/login`、`/pay`、`/otp` 各自对应独立的处理入口，甚至 `login.example.com`、`pay.example.com`、`sms.example.com` 各自是独立站点。在这种架构下：

1. **DNS 查询本身携带业务信息**：用户解析 `login.example.com` 与解析 `pay.example.com`，在明文 DNS 时代是两个不同的查询报文，网络侧可直接区分；
2. **主机名在多个协议层重复出现**：除 DNS 外，TLS 的 SNI、HTTP 的 Host 头、证书主题都携带同一域名，多个观测面互相印证；
3. **路径在明文 HTTP 时代也曾可见**：早期 HTTP 不加密，`/login` 与 `/otp` 这类路径可直接从请求行读出，粒度甚至细到具体操作。

因此，如果把目标限定为"判断用户正在使用登录业务还是支付业务"，老式 Web 架构下确实可以做到粗粒度分类。这正是"按域名判断操作"这一直觉的经验来源，不能一概斥为错误。但要强调两条限制：其一，它区分的是**业务类别**，不是**消息内容**——即便知道用户访问了 `/otp` 页面，也读不到页面里收到的那串数字；其二，它依赖的是**明文 DNS 与明文 HTTP** 的历史条件，而后文会说明，这两个条件在当代都被系统性削弱。

### 4. 现代移动 App：前提基本失效

现代移动应用普遍采用 API 收敛架构：一个应用只对接少数几个 API 网关域名，所有业务操作复用同一入口。用户观察到的 Facebook 现象正是这一架构的典型代表——绝大部分请求都指向 `graph.facebook.com`，而不是"每个业务一个域名"。在这种架构下，DNS 查询只能回答"用户连了 Meta 的 API"，无法回答"用户在做登录、点赞还是发帖"。

驾驭这种架构的关键技术有两项：**GraphQL 统一端点**（把操作类型从 URL 挪进 POST 请求体）与**服务端驱动 UI**（把界面结构也交给服务器下发）。下一章展开第一项，第三章详解进一步加固隐私边界的 ECH。两类应用的能力对照见下表。

| 对比维度 | 老式 Web 应用 | 现代移动 App |
|---|---|---|
| 业务划分方式 | 不同路径或不同子域 | 统一 API 端点 |
| 典型形态 | login 与 pay 各自独立入口 | graph.facebook.com 单一 host |
| DNS 可见性 | 子域不同，可粗分业务 | 单一域名，零区分度 |
| 操作语义位置 | 路径中，明文 HTTP 时代可见 | HTTPS 请求体内，长期加密 |
| 按域名判断操作 | 部分成立 | 基本失效 |

表中最后一列是本文的结论落点。需要提醒的是，"老式 Web 成立"与"现代 App 失效"不是绝对的时间二分，而是架构二分：仍有现代网站保留多子域设计，也有老应用已被改造为统一网关。判断标准不是应用的新旧，而是**它的业务操作是否真的落在不同域名上**。工程上应先做域名枚举与流量测绘，再决定是否适用该方法。

### 5. 小结

"按域名判断操作"是一个有明确适用边界的方法：它对老式 Web 应用的部分业务粗分类成立，对现代移动 App 基本失效。把它套到 WhatsApp OTP 封堵这一具体需求上，还叠加了一层更严苛的要求——目标操作"接收验证码"发生在**端到端加密的消息内部**，即便域名映射成立也读不到。因此，叠加 DNS 分析最多只能改善"条件 A 有哪些流量属于 inDrive"这类应用级识别，无法回答"这是不是一次 OTP 登录"。

## SUP-03-02 现代 App 的域名收敛机制：以 Facebook 为例

### 1. 观察到的现象

一个常见观察是：使用 Facebook 应用时，请求的目标域名大部分是 `graph.facebook.com`，而不是"不同业务使用不同域名"。这不是配置错误，也不是抓包工具遗漏，而是 Meta 刻意设计的 API 架构。理解它，就能理解为什么 DNS 侧看不出用户在做什么。下图展示多业务如何汇聚到单一端点。

:::figure id=SUP-03-02-01 | name=GraphQL 统一端点与请求体语义 | dir=LR

node n2 "点赞请求" blue
node n3 "发帖请求" blue
node n4 "graph.facebook.com<br/>graphql 统一端点" amber
node n5 "HTTPS 加密请求体" red
node n6 "fb_api_req_friendly_name" red
node n7 "variables 参数" red
node n8 "DNS 只见单一域名" gray
edge n1 -> n4 "同一 host"
edge n2 -> n4 "同一 host"
edge n3 -> n4 "同一 host"
edge n4 -> n5 "载荷加密"
edge n5 -> n6 "操作名字段"
edge n5 -> n7 "业务参数"
edge n4 -> n8 "解析目标"
:::

图中节点速览：n1、n2、n3 分别是登录、点赞、发帖三种业务请求；n4 是它们共同汇聚的 `graph.facebook.com/graphql` 统一端点；n5 是 HTTPS 加密的请求体，n6 与 n7 是其中区分操作的关键字段 `fb_api_req_friendly_name` 和 `variables`；n8 指出 DNS 侧只能看到单一域名。整张图表达的是：业务差异被从"域名维度"搬进了"加密请求体维度"，DNS 观察者恰好失去分辨能力。

### 2. Graph API 的单一 host 设计

Meta 官方 Graph API 文档在"Host URL"一节明确写道：**所有请求都发往 `graph.facebook.com` 这一个主机**（原文为 All requests are passed to the graph.facebook.com host URL）。Graph API 把平台上的一切建模为节点（用户、页面、帖子、照片）、边（节点的连接关系）与字段（请求返回的属性）。业务差异通过路径参数、`fields` 查询参数、HTTP 方法与访问令牌类型表达，而不是通过不同域名表达。该框架还启用了 `includeSubdomains` 的 HSTS 指令，进一步把整个域名家族绑成一个安全整体。

这意味着：即使一个应用同时完成"读取用户资料""发布帖子""管理广告"三类完全不同的操作，DNS 侧看到的解析目标仍是同一个名字。对 DPI 而言，域名这一维度提供的信息量接近于零。

### 3. GraphQL 统一端点：把操作语义搬进请求体

移动端进一步收敛。大量 FB4A（Facebook for Android）类客户端的请求指向 `graph.facebook.com/graphql` 这一统一端点。在这个端点上，**不同的操作靠请求体字段区分**，典型字段包括：`fb_api_req_friendly_name`（人类可读的操作名，如各种查询与变更的名称）、`client_doc_id`（查询文档标识）、`variables`（业务参数，通常为嵌套 JSON）、`fb_api_analytics_tags`（分析分类标签）、`client_trace_id`（请求追踪标识）。这些字段全部位于 POST 请求体内，由 HTTPS 加密保护。

下面给出这类请求的结构示意。字段名与取值来自公开的项目逆向分析，实际客户端版本会持续变化，具体字段与取值需对照抓取到的实际版本核验。

```text
POST /graphql HTTP/3
Host: graph.facebook.com
content-type: application/x-www-form-urlencoded

method=post&pretty=false&format=json&
fb_api_req_friendly_name=<OperationNameMutation>&
client_doc_id=<QueryDocumentId>&
variables={"input":{"code":"123456","login_id":"<masked>"}}&
fb_api_analytics_tags=["<tag>"]
```

对应的抓包侧观测结果通常如下（示例输出，具体字段与取值需对照实际版本核验）。

```text
DNS  q: A/AAAA graph.facebook.com      -> <Meta CDN IP>
TLS  SNI: graph.facebook.com (或 ECH 下的 public_name)
HTTP :method=POST  :path=/graphql  :authority=graph.facebook.com
body application/x-www-form-urlencoded  (HTTPS 内，抓包不可见)
```

对这两段输出做逐字段判读：DNS 行说明网络侧能拿到的只有域名到 IP 的映射，`A/AAAA` 记录本身不携带任何业务标识；TLS 行的 SNI 在无 ECH 时是明文域名，第三章会说明 ECH 部署后这一行会变成中性的 public_name；HTTP 行的 `:path=/graphql` 是关键——所有业务共用同一路径，这与老式 Web 的 `/login`、`/pay` 形成鲜明对比，说明路径粒度也已消失；最后一行 `body` 明确标注"HTTPS 内，抓包不可见"，这正是操作语义所在的位置，`fb_api_req_friendly_name` 与 `variables` 都在这里。判读结论是：从 DNS 到 TLS 到 HTTP 头部，三个观测面给出的都是同一个无区分度的域名，唯一有区分度的信息被加密载荷保护，因此"按域名判断用户操作"在架构层就被堵死。

### 4. 服务端驱动 UI：进一步减少域名分裂

除 GraphQL 外，还有一个容易被忽视的因素：服务端驱动 UI 框架（Meta 内部称 Bloks）。其思路是服务器下发界面布局指令，客户端负责渲染，界面结构随服务端版本更新而无需发版。这类框架配合 Native Template 上下文参数（如 bloks 版本标识、样式标识、像素比等）工作，这些参数同样位于请求体内。结果是：本可以拆成多个页面的界面层级，被压缩为对同一端点的多次请求，进一步减少了对外域名的分裂。

### 5. 这不是域名前置

需要澄清一个常见混淆：Facebook 的这种做法**不是域名前置**（domain fronting）。域名前置的特征是 TLS SNI 与 HTTP Host 故意不一致，借 CDN 的共享证书隐藏真实目标；而这里的情况是应用**本来就只使用一个真实域名**，所有业务在该域名下正常注册、正常解析，不存在"挂羊头卖狗肉"。前者是规避审查的伪装技术，后者是 API 架构的收敛设计。两者在网络上呈现的现象有相似之处（都是"看到的域名比实际业务少"），但成因、合规性质与对抗意图完全不同，不应混为一谈。

### 6. 小结

现代 App 通过 Graph API 单一 host、GraphQL 统一端点与服务端驱动 UI 三层设计，把业务差异从域名和路径搬进了加密请求体。DNS 分析在这一架构下只能看到"用户连了某个大厂 API"，无法下沉到操作粒度。这一结论与 SUP-02-02 中"条件 A 的召回率有限"相互印证：DNS 不是条件 A 的救星，它本身就是条件 A 失效的原因之一。

## SUP-03-03 ECH 机制详解：为什么连 SNI 都看不到

### 1. 从明文 SNI 说起

要理解"外部连 SNI 都看不到"，先要看清 SNI 原本暴露了什么。TLS 1.3 加密了服务器证书和大部分握手内容，但客户端在握手之初必须告诉服务器自己要访问哪个主机名——因为同一台服务器可能托管数百个站点，需要据此选择证书。这个字段就是 SNI（Server Name Indication），它以明文出现在 ClientHello 中。RFC 9849 把它称为"TLS 1.3 中遗留的最敏感信息"。凭借明文 SNI，运营商的 DPI 设备无需解密即可按域名识别与阻断，这正是 SUP-01-03 讨论的 SNI 检查之所以有效的原因。

### 2. ECH 的标准机制：两个 ClientHello

ECH（Encrypted Client Hello）是 IETF 的标准化方案，规范为 **RFC 9849（2026 年 3 月发布为 Proposed Standard）**，前身是长期演进的 `draft-ietf-tls-esni`。它的核心做法是构造两个 ClientHello：

1. **ClientHelloInner（内层）**：真正的握手消息，包含真实 SNI、真实 ALPN 列表（声明 HTTP/2 或 HTTP/3 等协议）及其他扩展；
2. **ClientHelloOuter（外层）**：一个看起来普通的 ClientHello，其 `server_name` 被设置为 ECH 配置中的 `public_name`（客户端面向服务器的名字，通常是提供服务的 CDN 共享主机名），并携带一个 `encrypted_client_hello` 扩展，里面装着经 HPKE 加密并填充后的内层 ClientHello。

客户端只把外层发到网络上。面向客户端的服务器尝试解密：成功则按内层继续握手（接受 ECH），失败则按外层完成握手（拒绝 ECH），并用 `retry_config` 机制让客户端重试新配置。规范定义了两种拓扑：共享模式下同一实体既是前端又是后端；分离模式下前端把解密后的内层转发给独立后端，前端除握手明文部分外看不到连接内容。ECH 的首要目标是让**同一匿名集合内的连接在观察者眼中不可区分**——它暴露"客户端连到了某个服务提供商"，但不暴露"匿名集合里哪一个服务器终止了连接"。

### 3. 配置从哪来：标准路径是 DNS

客户端加密内层之前，必须先拿到服务器的 ECH 公钥。标准路径是通过 DNS 的 HTTPS/SVCB 记录（RFC 9460）中的 `ech` SvcParamKey（RFC 9848）发布 `ECHConfigList`。配置结构中的关键字段包括：`config_id`（一字节配置标识）、`kem_id` 与 `public_key`（HPKE 公钥）、`cipher_suites`（对称算法组合）、`maximum_name_length`（用于填充计算）、`public_name`（外层使用的中性名字）。HPKE 本身定义在 RFC 9180。

这里存在一条著名的依赖链：**如果查询 HTTPS 记录的 DNS 请求本身是明文的，解析器与路径上的观察者会在 ECH 隐藏任何东西之前就先学到主机名**。RFC 9849 明确指出，没有传输中的 DNS 加密，SNI 加密的作用大打折扣。这也是 ECH 通常与 DoH/DoT 配套部署的原因。下图把双层 ClientHello 与可见性边界画在一起。

:::figure id=SUP-03-03-01 | name=ECH 双层 ClientHello 与可见性 | dir=TB

node n2 "ClientHelloOuter<br/>SNI 为 public_name" teal
node n3 "ClientHelloInner<br/>真实 SNI 与 ALPN" red
node n4 "HPKE 公钥加密" amber

:::

图中节点速览：n1 是构造两个 ClientHello 的起点；n2 是外层，SNI 被替换为 public_name；n3 是内层，携带真实 SNI 与 ALPN；n4 与 n5 是 HPKE 加密与封装步骤，内层被塞进 `encrypted_client_hello` 扩展；n6 是网络侧可见的极限，只有中性名与 IP；n7 是面向客户端的服务器，解密后获得真实域名；n8 是 Meta 的特殊之处——配置由 App 内置，不经 DNS 广播，直接向 n4 提供公钥。整张图说明：真正被保护的是内层，而外层依然是可见的普通握手。

### 4. Meta 的特殊做法：内置配置，不经 DNS 广播

标准路径是 DNS，但 Meta 没有走这条路。2026 年德累斯顿工业大学网络技术组发表的 ECH 主动探测研究（`Discovering Encrypted Client Hello Deployments by Active ECH Probing`）给出了实测证据，要点如下：

- 研究者发现 **Meta 对 `graph.facebook.com` 部署了 ECH，但不在 DNS 中广播其配置**（原文：Meta deploys ECH but does not advertise in DNS）；这些域名的 DNS 记录不暴露 ECH 配置。
- 论文指出，**专用客户端应用（如 Facebook、Instagram 移动应用）可能使用预配置的 ECH 配置，或自定义的配置获取机制**。换言之，密钥随 App 分发或由 App 自己的通道取得，而不是靠公开的 DNS HTTPS 记录。
- 研究者录制了一台 iOS 设备使用 WhatsApp、Facebook、Instagram 及 Android 版 Facebook、Instagram 共 30 分钟的流量进行验证：在 iOS 上观测到一个带 ECH 扩展、发往 `graph.facebook.com` 的包（走 HTTP/2），以及 47 个发往 `scontent.xx.fbcdn.net` 的包（走 HTTP/3）。两条链路的 ECH 配置标识与 Meta 在 RetryConfigurations 中提供的一致。
- 并非所有请求都带 ECH 扩展，即 Meta 并未对所有 TLS 连接做 GREASE 处理；Meta 官方也确认"ECH 目前部署于我们移动应用流量的一部分"。
- 该研究在 2026 年 8 月 15 日的探测中，通过 TCP 与 QUIC 覆盖约 4.7k 个域名，其中 59% 是 `apps.fbsbx.com` 的子域。

三种配置分发方式的差异见下表。

| 分发方式 | 获取途径 | DNS 侧是否可见配置 | 主要特征 | 代表主体 |
|---|---|---|---|---|
| 标准 DNS 广播 | HTTPS/SVCB 记录的 ech 参数 | 可见，需 DoH 保护 | 依赖解析链路隐私 | 浏览器与多数 CDN 站点 |
| App 内置预配置 | 随应用分发或自定义通道 | 不可见，DNS 无 ech 记录 | 不依赖公开解析 | Meta 移动应用 |
| 握手重试下发 | RetryConfig 机制 | 不适用，位于 TLS 内 | 配置轮换与纠错 | RFC 9849 通用 |

表中第二行是本案关键：当配置由 App 内置时，运营商即使完整镜像了 DNS 流量，也看不到任何 ECH 配置痕迹；而由于内层 ClientHello 被 HPKE 加密、外层又只显示中性名，明文 SNI 这一传统抓手同时失效。

### 5. 逐句解读那句结论

现在可以逐段拆解"部署了 ECH，而且配置由 App 内置、不通过 DNS 广播。所以外部连 SNI 都看不到，运营商侧能观测到的只剩'连了 Meta 的 IP'"这句话。

**第一层——"部署了 ECH"**：指 Meta 在移动 App 的部分流量中启用了 RFC 9849 机制，真实 SNI 被封进内层 ClientHello，经 HPKE 加密后作为扩展塞进外层。网络观察者读外层握手，只能读到 public_name 这一中性名字，而不是 `graph.facebook.com` 这个真实业务域名。

**第二层——"配置由 App 内置、不通过 DNS 广播"**：这是 Meta 与标准浏览器路径的关键差异。常规 ECH 依赖 DNS HTTPS 记录发布公钥，因此 DNS 查询会泄露主机名（除非 DoH/DoT）；Meta 改为随 App 预置配置或走自有获取通道，DNS 里查不到 ech 参数。这一做法同时切断了两条观测线索：既没有 DNS 层的 ECH 配置可供识别，也不需要暴露真实域名的解析查询。

**第三层——"外部连 SNI 都看不到"**：严格地说，外部看到的是**外层的 public_name**，它是中性、共享的名字，不承担业务区分功能；真正的 SNI 在内层且已加密。所以这句话的准确表述是"看不到**真实** SNI"。这并不等于所有握手特征都消失——外层仍是可读的 ClientHello，密码套件、长度、ALPN 等仍可被复制进外层形成指纹。RFC 9849 也提醒，ECH 隐藏的是名字而非长度，流量分析对加密字段尺寸的推断仍是开放问题。

**第四层——"运营商只剩连了 Meta 的 IP"**：由于 IP 层路由必须可见，运营商仍能知道流量去往 Meta 的某个地址；再结合包长、时序、连接频率等侧信道，可以做出"这是 Meta 系应用流量"的应用级画像。但如果该 IP 后面对应一个庞大的匿名集合（许多服务共享前端），ECH 的设计目标正是让这些连接不可区分。需要注意反面情形：若某个 IP 只服务单一站点，那么目标 IP 本身就会泄露身份，ECH 的保护效果与其匿名集合规模成正比。

四层合起来的结论是：DNS 分析能拿到的信息被从两端同时压缩——域名侧因统一网关而无区分度，SNI 侧因 ECH 而看不到真实名字。这不是某一项配置的临时状态，而是应用架构与加密协议共同作用的结构性结果。

### 6. 小结

ECH 把明文 SNI 变成加密内层，Meta 又用 App 内置配置绕开了 DNS 广播这条标准路径，使 DNS 与 TLS 两个观测面同时失去业务区分能力。这解释了为什么"叠加 DNS 分析判断操作"在现代移动 App 上先天不足。需要提示的是，ECH 部署仍在推进中，Meta 官方表述是"部分移动应用流量"，具体覆盖比例、字段取值与版本行为需对照实际抓包与最新文档核验，本文不构成对某一时刻部署率的精确断言。

## SUP-03-04 叠加 DNS 分析能否达成目的

### 1. 三堵墙

把 DNS 分析放回 SUP-01 与 SUP-02 的论证框架，可以看到它面对三堵墙，且没有一堵是它能推倒的。

第一堵是**分辨率不足**。DNS 只回答"查了哪个域名"，而现代 App 把所有操作收敛到同一域名；即使退到老式 Web 场景，域名也只能粗分业务类别，无法定位到"这一条消息是不是 OTP"。信息根本不在这一层。

第二堵是**观测面收缩**。DoH 与 DoT 让 DNS 查询本身离开运营商视野；ECH 让真实 SNI 变成加密内层；Meta 的 App 内置配置让 DNS 里连 ECH 配置都查不到。运营商能稳定观测到的，只剩目标 IP、包长与时序。

第三堵是**因果链断裂**。这是 SUP-02-03 已经论证的、与技术无关的根本问题：OTP 通道由 inDrive 这样的应用方决定，用户侧无论多精确地识别到"正在登录"，都传导不到应用方的通道决策。DNS 分析完全不触及这一环。

### 2. DNS 分析的正确用途

否定其在 OTP 封堵中的作用，不等于否定 DNS 分析本身。它在下列场景仍然有价值：

1. **流量画像与容量规划**：识别 Meta 系、OTT 类应用的总体占比，为骨干网扩容提供依据；
2. **A2P 服务质量保障**：把运营商自身短信通道的流量与其他流量分开，做可达率与时延监控；
3. **异常检测**：发现异常域名查询模式，用于安全运营而非歧视性阻断；
4. **关联分析的输入增强**：作为 SUP-02-01 承认的成熟方法之一，在具备稳定协议绑定的场景（如 DNS 查询与后续连接的地址对应）提升识别召回率。

这些用途的共同点是：产出运营指标或风险提示，而不是对用户执行有副作用的阻断。用途不同，合规基础完全不同。

### 3. 结论

1. **老式 Web 成立、现代 App 失效**：按域名判断操作的方法对早期多子域 Web 应用的业务粗分类部分成立，对采用 GraphQL 统一端点与服务端驱动 UI 的现代移动 App 基本失效；判断标准是业务是否真的落在不同域名，而非应用新旧。
2. **DNS 分析补不上条件 A**：在统一网关架构下 DNS 零区分度，ECH 又压缩了 SNI 观测面，DNS 不是关联方案的补救，反而是其失效原因之一。
3. **语义与因果两道鸿沟仍在**：DNS 分析无法触及端到端加密的消息语义（SUP-01-02），也无法触及"施压对象错位"的因果链断裂（SUP-02-03）。
4. **建议**：放弃以 DNS 分析支撑 OTP 封堵的思路，把 DNS 能力投向流量画像与运营优化；营收问题回到 A2P 产品化、RCS 商业消息与运营商自有认证（替代路径见 SUP-01-06）。

### 4. 延伸阅读与交叉引用

- 加密边界与语义不可见：SUP-01-02（Signal 协议与可见性模型）；SNI 检查与传统 DPI 抓手见 SUP-01-03。
- 关联方案的三处断点与因果链断裂：SUP-02-02、SUP-02-03。
- ECH 标准文本：RFC 9849（TLS Encrypted Client Hello）、RFC 9848（DNS 引导）、RFC 9460（SVCB/HTTPS 记录）、RFC 9180（HPKE）；Meta 部署实测见德累斯顿工业大学 2026 年 ECH 主动探测论文。
