# WhatsApp 技术资料 · SUP-02 关联识别方案可行性与因果链评估

## SUP-02-01 关联方案的提出与逻辑拆解

### 1. 方案背景

SUP-01 已经论证：由于端到端加密，链路上不存在可匹配的"OTP 报文特征"，直接识别方案不成立。在此基础上产生了一种改进思路——不做单一报文识别，改做**事件关联**：如果能同时检测到（A）inDrive 等应用发起登录操作，与（B）该用户设备上出现 WhatsApp 下行短消息，且二者在时间窗内共现，就判定为一次 OTP 登录并触发封堵。

这个思路的价值在于它承认了语义不可见，转而用**行为关联**替代**内容识别**。从方法论上看，这是正确的方向：既然读不到内容，就读行为。但方向正确不等于方案成立，仍需逐环节验证。

### 2. 三层逻辑拆解

关联方案的实际逻辑是一个合取式判定 `A ∧ B → 封堵`。要让它成立，必须同时满足三个前提：

1. **条件 A 可观测**：inDrive 的登录操作能被网络侧稳定识别；
2. **条件 B 可观测且语义正确**：WhatsApp 侧的下行消息能被检测，并且这个检测确实指向 OTP；
3. **判定可落地**：封堵动作有明确、合规、有效的落点。

任一前提不成立，合取式就不成立。下面两章逐一验证，第四章再讨论一个更根本的、与技术实现无关的问题。本方案的能力边界与逻辑链见图 SUP-02-02-01。

### 3. 为什么这个方案值得单独评估

关联方案在工程上很有迷惑性，因为它把"读不到内容"这个硬约束，转化成了"多观测几个相关事件"这种看起来可实施的工程任务。在不少网络分析场景里，这种转化确实有效：例如把 DNS 查询、TLS 握手与后续流量关联，可以显著提升应用识别的召回率；把 RADIUS 计费时间与 DPI 流时间对齐，可以稳定完成订户归属。这些都已被现网实践验证。

但这些成功案例有一个共同前提：被用来关联的事件，与要推断的目标之间具备**稳定的因果或协议绑定关系**。DNS 查询的目标域名与后续连接的目标地址由同一套解析逻辑产生；RADIUS 会话时间与用户实际在线时间由认证系统保证一致。关联方案借用同样的方法论，却把它用在了不具备这种绑定关系的两个事件上——"inDrive 发起登录"与"用户收到一条 WhatsApp 消息"之间，既没有协议层的绑定，也没有必然的因果关系，只有业务上的偶然共现。

这正是本文要单独评估它的原因：方法本身是成熟的，但被套用到了一个方法不适用的对象上。识别这类"方法论正确、适用对象错误"的方案，比单纯指出加密边界更有价值，因为它揭示了一种容易反复出现的思维陷阱——只要多找几个相关信号，就能绕过内容不可见。第三章的工程判读会进一步说明，即便把窗口、包长这些信号都调到位，输出的命中列表依然无法达到可执行的确定度。

## SUP-02-02 三个技术断点

### 1. 断点一：条件 A 的可识别性有限

inDrive 客户端到其自身服务器的通信是普通 HTTPS，网络侧可以通过证书、SNI、IP 段把它归类为 inDrive 应用流量。但要进一步区分"登录操作"与"查询订单""刷新位置""拉取消息"等其他操作，需要看到 URI 路径或请求体特征——而这些在 HTTPS 里是加密的。

即使退一步，只按"认证相关端点"做粗粒度匹配，也有三个削弱因素：

- **DNS 加密**：DoH 与 DoT 使域名查询不可见；
- **SNI 加密**：ECH 把 ClientHello 中的目标域名替换成中性域名；
- **地址轮换与连接池**：应用使用 CDN 与长连接时，单次操作不必然产生新的可指纹连接。

因此条件 A 的召回率本身就有限，不能假设"登录操作总能被稳定识别"。这一点与 SUP-01-03 讨论的 DPI 应用识别边界一致（应用识别见 SUP-01-03）。

### 2. 断点二：条件 B 偷换了概念

方案把"OTP 特征"替换成了"登录后的 WhatsApp 下行短消息"。这两者不是一回事。OTP 之所以是 OTP，靠的是**内容**（一串一次性验证码）和**用途**（完成本次登录），而不是**到达时机**。用时序相关替代语义，会带来双向误差：

| 误差类型 | 触发场景 | 后果 |
|---|---|---|
| 误判 | 用户此刻收到任何 WhatsApp 消息：家人问候、群聊、通知、广告 | 把普通消息当成 OTP，触发错误封堵 |
| 漏判 | OTP 因网络延迟提前或延后到达；或 inDrive 改用短信/邮箱通道 | 真正的 OTP 登录未被覆盖 |
| 错配 | 用户发起两次登录，或先收到 OTP 再发起登录 | 时间窗关联指向错误的会话 |
| 无法区分 | inDrive 同时支持多种验证码通道 | 无法判定这次到底用了 WhatsApp |

表中四类误差的共同根源是：时间窗只提供相关性，不提供因果性。相关性可以在统计意义上提升置信度，但无法把"一条消息"确定性地标记为"OTP"。而封堵是一个有副作用的动作，对确定性的要求远高于对置信度的要求。

### 3. 断点三：封堵落点两难

即便 A∧B 判定成立，封堵动作仍然没有合适的落点：

- **封 WhatsApp 流**：牵连用户全部通信，包括与登录完全无关的个人与工作消息，用户体验代价极大；
- **封 inDrive 流**：这是直接阻断第三方应用的正常业务，比 SUP-01-05 讨论的应用级阻断更进一步，合规风险更高（合规依据见 SUP-01-05）；
- **只丢弃判定为 OTP 的那条消息**：技术上做不到，因为条件 B 本身就没有语义识别能力。

### 5. 关联判定的工程实现与判读

为让断点二更具体，下面给出这套关联引擎的典型实现逻辑。伪 SQL 把"应用登录事件表"与"WhatsApp 下行消息表"在订户维度上做时间窗连接，窗口设为登录时刻之后 120 秒——这个数值是示意，实际需按 OTP 平均到达时延标定，并需对照现网日志核验字段名。

```sql
-- 伪 SQL：订户维度上关联登录事件与随后的 WhatsApp 下行消息
SELECT a.imsi, a.login_time, m.msg_time,
       (m.msg_time - a.login_time) AS delta_sec,
       m.pkt_len, m.direction
FROM app_login_event a
JOIN whatsapp_flow m
  ON a.imsi = m.imsi
 AND m.direction = 'downlink'
 AND m.msg_time BETWEEN a.login_time
                    AND a.login_time + INTERVAL '120' second
WHERE a.app = 'inDrive'
  AND m.pkt_len < 400;
```

下面是这段查询的示例输出（示例数据，格式需对照实际系统核验）。

```text
imsi              login_time           msg_time             delta_sec  pkt_len  direction
46000********123  2026-11-20 14:03:11  2026-11-20 14:03:19  8          218      downlink
46000********123  2026-11-20 14:05:40  2026-11-20 14:06:58  78         396      downlink
46000********456  2026-11-20 14:07:02  2026-11-20 14:07:44  42         175      downlink
```

对输出逐行判读：第一行 `delta_sec=8`、`pkt_len=218`，看起来最像"登录后立即收到短验证码"，会被关联引擎判为高危并触发封堵——但请注意，`pkt_len` 只是加密后的帧长度，一条 218 字节的消息既可能是六位验证码，也可能是"好的，稍后回你"，引擎对此没有任何区分能力。第二行 `delta_sec=78`、`pkt_len=396`，时间窗内但明显偏长，很可能是用户在登录过程中顺便聊天；若把窗口放宽到 120 秒，这类噪声会被大量纳入。第三行同样落在窗口内，但无法排除是无关消息。三行的共同点是：所有字段都是元数据，没有任何一列承载消息语义。这正是断点二的工程体现——引擎输出的"疑似 OTP"命中列表里混杂着大量正常通信，误判率无法压到可封堵的水平。若据此执行丢弃，代价是真实用户收不到消息；若不执行，则整套系统不产生任何效果。这便是关联方案在"判定—执行"之间的死结。

## SUP-02-03 商业逻辑断点：施压对象错位

### 1. 被忽略的因果链

前两章讨论的都是技术能否成立。但即使三个技术断点被侥幸绕过，还有一个更根本的问题：**这个方案能达成"提振短信营收"的业务目标吗？** 沿着产业链追一遍因果链就会发现，答案是否定的。

关键在于谁决定 OTP 通道。决定"用 WhatsApp OTP 还是短信 OTP"的是 inDrive 这样的**应用方**，不是用户。用户在登录界面上看到的是应用提供的选项，他无法自行把 WhatsApp 验证码换成短信验证码。运营商在用户侧封堵登录，用户看到的结果是"inDrive 登不进去"，而不是"我改用短信验证码吧"。

### 2. 各方激励分析

下表列出关联方案涉及各方的激励，可以清楚看到施压对象错位。

| 参与方 | 诉求 | 对封堵的反应 | 是否因此改用短信 OTP |
|---|---|---|---|
| 运营商 | 提振 A2P 短信营收 | 主动发起封堵 | 不适用 |
| inDrive 应用方 | 保障用户登录成功率 | 认为运营商妨碍业务，可能投诉 | 没有动力，反而受损 |
| 最终用户 | 顺利登录目标应用 | 换网络、换设备重试或放弃应用 | 无法自行切换通道 |
| 监管机构 | 维护竞争中立与用户权益 | 关注歧视性阻断投诉 | 不适用 |

表中 inDrive 一行的激励最关键：封堵直接损害它的登录成功率，它没有任何动机改成短信 OTP，反而有动机投诉运营商。这意味着封堵动作不但不能把用户"引导回短信"，反而可能把网络中立风险从"疑似"变成"实锤"。

### 3. 用户反应的三种走向

从用户侧看，封堵后的反应有三种，没有一种会把营收带回运营商：

1. **换网络或换设备重试**：绕过封堵，OTP 仍走 WhatsApp，营收不变；
2. **放弃使用 inDrive**：用户流失，OTT 与短信两方都失去流量，运营商并未获益；
3. **转向其他支持短信 OTP 的竞品**：运营商获得短信收入，但收入来自另一个应用，与封堵 inDrive 没有因果关系——同样数量的短信流量本来就可能自然发生。

## SUP-02-04 关联思路的正确用途与结论

### 1. 技术本身并非无用

需要澄清的是，本文否定的是"用关联分析做营收封堵"，不是否定关联分析本身。把"应用登录事件"与"消息到达事件"做时间窗关联，在**风控反欺诈**场景是成立且有用的，例如：

- 检测账号盗用：异地登录后立即索取 OTP，属于高风险序列；
- 识别自动化攻击：短时间内大量登录伴随批量消息到达；
- 保护用户：对异常序列要求二次验证，而不是切断通信。

在这些场景里，关联的产出是"风险提示"而非"封堵执行"，误判的代价是让用户多做一次验证，而不是切断正常通信。同一个技术，目的不同，结论相反。

### 2. 与 SUP-01 的关系

本文承接 SUP-01 的加密边界论证（加密边界见 SUP-01-02），进一步验证"用关联绕过语义不可见"这一补救思路（数据源边界见 SUP-01-03）。两篇合起来，覆盖了两条被否定的路径：直接报文识别，与事件关联识别。合规替代路径不因关联方案的提出而改变（替代路径见 SUP-01-06）。

### 3. 结论

1. **关联方案不成立**：条件 A 的召回率受 DoH/ECH 限制，条件 B 用时序偷换语义，封堵落点两难，三个技术断点各自独立致命。
2. **更根本的是因果链断裂**：OTP 通道由应用方决定，用户侧封堵无法传导到应用方决策，因此无法达成提振短信营收的目标。
3. **激励结构站在方案对立面**：inDrive 因封堵受损，有动机投诉；监管视角下这会坐实歧视性阻断的指控。
4. **建议**：放弃关联封堵思路，把关联分析能力投向风控反欺诈，把营收问题交回 A2P 产品化、RCS 商业消息与运营商自有认证（替代路径见 SUP-01-06）。

### 4. 延伸阅读与交叉引用

- 加密边界与语义不可见：SUP-01-02（信号协议与哑管道）。
- DPI 应用识别与数据源能力：SUP-01-03（SNI、指纹、RADIUS 与 NAT）。
- 合规风险与监管案例：SUP-01-05（网络中立与竞争法）。
- 合规替代路径：SUP-01-06（A2P、RCS、运营商认证）。

## SUP-02-05 放弃语义的简化方案：登录识别加粗特征封堵

### 1. 方案的提出：从识别 OTP 退到识别登录

第二章的断点二指出，关联方案把"OTP 特征"偷换成了"登录后的 WhatsApp 下行短消息"，因为后者只是时序相关、不是语义特征。对此有一种直接的回应：**既然语义不可见，那就不要语义**。新方案不再声称自己识别出了验证码，也不区分这次登录究竟用的是短信、邮件、第三方账号还是 WhatsApp 验证码，而是一律假设为 WhatsApp 验证码；只要检测到某应用正在登录，且随后短时间内出现一条 WhatsApp 下行短消息，就判定命中并实施封堵。

这个简化有值得肯定的一面：它正视了断点二，不再做"这条消息是 OTP"的不可证断言，改以概率判定驱动动作，工程实现难度明显下降。但必须说清楚，它不是一条新路径——它正是第一章定义的关联方案 `A ∧ B → 封堵`，区别仅在于明确接受误报作为代价。第二章的三处断点逐条适用，并未因放弃语义而消失。

本章补充两项此前未展开的评估：其一，条件 A 所依赖的"登录前后是否真的有可观测特征"；其二，"全部假设为 WhatsApp 验证码"这一策略对误伤面的实际影响。这两项决定了简化方案是否真的比原方案更可用。

### 2. 登录前后是否真的有可观测特征

先回答事实层面。加密流量分析领域确实有研究支持"登录阶段可识别"：特温特大学的硕士论文专门做了从移动加密流量中识别应用阶段，把认证阶段列为可分类的一类，结论是使用包长、时序等特征训练的分类器可以区分认证阶段与其他阶段。但同一篇论文也暴露了一个关键限制：安卓系统没有任何默认事件能标记"用户正在登录"，研究者最终只能自己往应用里插入认证开始与认证结束的日志，用来生成标注数据。

这个细节对本评估至关重要。它说明网络侧看到的只是流量形状，没有天然的真值标签；标注真值必须进入设备。对运营商而言，这意味着登录阶段是一个**概率分类目标**，不是确定性判定目标。下图把登录三个阶段的可观测特征画在一起。

三阶段的可观测差异与混淆因素见下表。

| 阶段 | 可观测特征 | 网络侧可得性 | 主要混淆因素 |
|---|---|---|---|
| 登录前 | 请求零散、上行数据小、拉取配置与探测 | 弱信号 | 应用冷启动即有相同行为 |
| 登录中 | 一次上行认证请求加一次下行短响应 | 中等 | 长连接复用使边界模糊 |
| 登录后 | 密集初始化请求簇随后稳定心跳 | 较强 | 后台重连、令牌刷新、切换账号高度相似 |
| 全程 | 包长序列、时序、连接指纹 | 需基线标定 | 填充与流量整形可抹平差异 |

表中第三行是看起来最有区分力的特征，但也是被混淆最严重的：后台重连、令牌刷新、切换账号都会产生与登录几乎一致的初始化请求簇；应用在超文本传输协议二、快速用户数据报协议与长连接下，登录前后常复用同一连接，阶段边界进一步模糊；预取与后台任务还会持续制造噪声。防御方只要加入填充、批量化或流量整形，这些形状特征就会被主动抹平。因此条件 A 的准确率和召回率都有限，不能假设登录总能被稳定识别。这一点与 SUP-01-03 讨论的应用识别边界一致。

### 3. 误判率：粗特征命中是常态而非异常

现在评估简化方案的核心。粗特征是"登录后短窗口内出现一条 WhatsApp 下行短消息"。关键在于，**这个特征的命中率取决于 WhatsApp 消息的背景到达率，而不是验证码的发生率**。WhatsApp 是日常即时通讯工具，活跃用户每天收到数十到数百条消息；登录动作又发生在用户正在使用手机的时段，此时消息到达是高频背景事件。于是"登录后短时间内有下行消息"是一个高基线概率事件，它几乎不携带区分力。

用一个示意计算说明量级（参数为假设值，需按本网实际消息到达率与登录分布核验）：若用户平均每五分钟收到一条消息，一百二十秒窗口内至少命中一条的概率约为三分之一；对重度用户若平均每三十秒一条，则接近百分之九十八。也就是说，即便完全没有验证码产生，判定也会大面积命中。命中只意味着两个独立的高频事件在时间上偶然重叠，不意味着 OTP 发生。这正是断点二"时间窗只提供相关性、不提供因果性"的量化版本：相关性在统计上提升了命中数，但同时把大量正常通信塞进了命中列表。

下面的伪 SQL 展示这套判定如何计算窗口命中，字段与表名需按现网系统核验。

```sql
-- 伪 SQL：登录事件与随后 WhatsApp 下行消息的时间窗连接
SELECT a.imsi, a.login_time, m.msg_time,
       (m.msg_time - a.login_time) AS delta_sec,
       m.pkt_len
FROM app_login_event a
JOIN whatsapp_flow m
  ON a.imsi = m.imsi
 AND m.direction = 'downlink'
 AND m.msg_time BETWEEN a.login_time
                    AND a.login_time + INTERVAL '120' second
WHERE a.app = 'inDrive'
  AND m.pkt_len < 400;
```

这段查询的示例输出与逐字段判读见下文（示例数据，格式需对照实际系统核验）。

```text
imsi              login_time           msg_time             delta_sec  pkt_len
46000********123  2026-11-20 14:03:11  2026-11-20 14:03:19  8          218
46000********456  2026-11-20 14:05:40  2026-11-20 14:05:52  12         164
46000********123  2026-11-20 14:07:02  2026-11-20 14:07:58  56         396
```

判读：`delta_sec` 是消息相对登录的时延，三行分别落在八秒、十二秒与五十六秒，都落在窗口内且看起来像"登录后立即收到短消息"，会被判为高危；`pkt_len` 是加密后的帧长度，二百一十八字节与一百六十四字节既可能是验证码，也可能是"好的""收到"这类日常短消息，引擎没有任何区分能力；第三行三百九十六字节偏长，很可能是登录过程中的普通聊天。三行的共同点是所有列都是元数据，没有一列承载消息语义。若据此执行丢弃，代价是真实用户收不到正常消息：命中列表里验证码是少数，日常通信是多数，封堵动作会把多数一并伤害。

### 4. 全部假设为 WhatsApp 验证码：假设改变解释，不改变命中

用户提出的关键简化是"不考虑这次登录用的是什么通道，全部假设为 WhatsApp 验证码"。需要分清假设作用于哪一层：它改变的是对命中结果的**解释**，不改变判定的**输入**。判定输入仍然是"登录事件加 WhatsApp 消息共现"，而这个输入对使用短信、邮箱或第三方账号登录的用户同样会命中——因为这些用户在登录时同样会收到 WhatsApp 消息。于是"全部假设"不是收窄了范围，而是把原本可以靠通道信息排除掉的用户也纳入了误伤集合，使误伤面扩大。

更关键的是，通道选择由应用方决定，运营商的假设不参与应用方的决策。即使假设 WhatsApp 验证码占比为百分之百，也不会让应用方改成短信验证码；假设与实际不符时，误伤已经发生且不可撤销。这是 SUP-02-03 论证的因果链断裂在"假设策略"下的新表现：无论判定端如何简化，施压对象仍在应用方，用户侧封堵传导不到应用方的通道决策。下图把这条判定链和各处断点画在一起。

简化方案相对原方案的取舍见下表。

| 维度 | 原关联方案 | 放弃语义的简化方案 | 变化 |
|---|---|---|---|
| 语义识别 | 声称识别 OTP 语义 | 明确放弃，改概率判定 | 规避断点二的表述问题 |
| 条件 A 要求 | 稳定识别登录 | 同样需要，且只能概率分类 | 未改善 |
| 误判来源 | 时序偷换语义 | 高基线消息到达叠加共现 | 误伤面扩大 |
| 通道差异 | 无法区分，列在误差表 | 全假设为 WhatsApp | 不减少误伤，只改变解释 |
| 封堵落点 | 两难 | 两难 | 未改善 |
| 营收回流 | 因果链断裂 | 因果链断裂 | 未改善 |

表中前两行是简化方案真正拿到的收益：它让表述更诚实、实现更容易。后四行说明它没有触碰任何一条结构性断点，其中"误伤面扩大"一项甚至是净损失。综合看，这是一个把不可证的语义断言换成了可实施的高误报判定的方案，实施门槛下降与误伤代价上升同时发生。

### 5. 结论与交叉引用

1. **登录阶段特征确实存在**，但属流量形状层，是概率分类而非确定性判定；学术研究的真值标签依赖设备侧插桩，四个混淆因素会持续污染特征。
2. **简化方案规避了断点二的表述问题，没有规避误判**：粗特征命中是高基线事件，不具区分力，命中列表里验证码是少数、日常通信是多数。
3. **全部假设为 WhatsApp 验证码不降低误伤，反而扩大误伤面**：假设只改变解释、不改变命中输入，且不参与应用方通道决策。
4. **两条结构性断点与识别精度无关**：封堵落点两难与施压对象错位，即使判定做到满分也不会自动打通；因此本方案仍无法达成提振短信营收的目标。
5. **正确方向不变**：把登录与消息到达的关联能力投向风控反欺诈，把营收问题交回产品化路径。

- 登录阶段特征所依赖的网络侧可见性边界：SUP-01-03；设备侧行为信号的可得性与合规墙：SUP-01-04。
- 关联方案的三处断点与误报工程判读：SUP-02-02；施压对象错位与因果链断裂：SUP-02-03。
- 关联分析的正当用途，即风控反欺诈：SUP-02-04；营收问题的产品化路径：SUP-04-02 至 SUP-04-04。
- 合规替代路径总览：SUP-01-06。

## SUP-02-06 概率框架下的优化建议：如果一定要做，怎样伤害最小

### 1. 前提重置：从"能不能做"到"怎样伤害最小"

上一章的结论，是在"判定必须指向真正的验证码"这一口径下得出的。现在换一个前提：不求精准识别，只求大概率识别；不区分这次登录用的是短信、邮件、第三方账号还是 WhatsApp 验证码，一律按 WhatsApp 验证码处理；把"登录识别"与"WhatsApp 下行短消息粗特征"碰撞，二者同时满足即实施封堵。这个前提值得认真接住——它没有推翻前几章的事实判断，但改变了要回答的问题：不再问"这个系统在语义上是否成立"，而是问"在概率框架下，怎样做才能既有效、又把伤害控制到最小"。

先把一条边界说在前面。接下来的四条建议改善的都是**技术有效性**：提高命中质量、压低误报代价、让处置动作可逆。它们不改变第二章断点三（封堵落点两难）与第三章（施压对象错位）这两条结构性断点。概率化让系统更容易建成、误伤更可控，但仍然封不到 inDrive 的通道决策，营收因果链依旧不通。因此本章的定位是"如果一定要做，这样做伤害最小"，而不是对方案可行性的翻案。

概率框架还带来一个新的工程义务：一旦承认误报必然存在，就必须给误报定价，并把定价反映到判定阈值和处置动作上。这是下面四条建议的共同主线——一个只输出"命中/不命中"的二值系统，无法承载这种定价；一个输出连续风险分、并按分数分级处置的系统才可以。

### 2. 建议一：判定对象从两事件共现升级为三段闭环

原方案的判定对象是二段共现：登录事件出现，随后短时间内有 WhatsApp 下行短消息。二段的弱点是，任何一条日常消息都能填满第二段。改进方向是把它改成**三段严格有序闭环**：登录 → 认证模板消息 → 回填二次请求。

依据有三点。第一，Meta 要求验证码类消息必须通过 authentication template 下发，这类消息有固定模板结构，帧长分布与普通聊天不同，比"一条短消息"更可区分。第二，也是更关键的一点，验证码的本质是"发出后会被回填校验"；用户把收到的数字填回应用，应用侧必然产生一次新的超文本传输协议请求去校验凭证。普通聊天消息不会触发这次回填。第三，这次回填请求本身就提供了天然的真值标签——"用户是否回填成功"可以直接观测，用来离线标定模型、持续优化，不必像特温特大学论文那样往应用里插桩造标签。这同时解决了误判和标注两个问题。

检索到的多阶段应用指纹研究（MPAF 类工作）报告了百分之九十六点三三到百分之九十九点四二的识别准确率，其方法正是把握手、早期数据、稳定态分阶段建模，而不是在单一时点取特征。这与三段闭环的思路一致：分阶段、按序验证，比单点碰撞强得多。三段闭环与自监督标签见图 SUP-02-06-01。

| 判定段 | 可观测信号 | 区分力 | 标注来源 |
|---|---|---|---|
| 登录 | 请求响应对、令牌下发 | 中，受四个混淆因素污染 | 回填成功与否 |
| 认证模板消息 | 固定模板结构、帧长分布 | 中高，模板相对固定 | 模板下发记录 |
| 回填二次请求 | 应用侧新的校验请求 | 高，无回填即可排除 | 回填请求本身 |

表中第三行是这套改造的核心收益：它把一个"看消息像不像验证码"的语义问题，换成了一个"有没有随后那次校验请求"的行为问题，后者在网络侧可见。需要如实说明的是，三段闭环依然不是确定性判定——回填请求也可能来自邮箱或短信验证码，且模板消息可能因推送延迟而错位；它提高的是命中质量，不是把误报率归零。字段与判定阈值需按本网实际日志核验。

### 3. 建议二：用基础概率反推阈值，而不是拍脑袋定大概率

这是概率框架下最容易被忽略的数学约束。目标事件在全部流量里是极少数：一个用户一天可能只有一两次登录，却有上百条消息。即使分类器准确率达到百分之九十九，在海量普通消息的基数上，误报的绝对数量仍可能超过真报数量。这就是类别不平衡放大误报效应——准确率这个指标在这里具有误导性。

正确做法分三步：先用本网数据测出验证码事件在候选事件中的基础概率；再用真阳性率与假阳性率算出似然比，由似然比反推达到可接受精确率所需的判定阈值；最后明确报告精确率、召回率与混淆矩阵，而不是只说"大概率"。检索到的流量分析研究中，百分之九十六点四真阳性率配百分之零点二假阳性率才敢称可用，这个量级可作为参照，但绝不能照搬到本网。

下面的伪代码演示基础概率如何改变一次阳性命中的含义（数值为示意，需按本网核验）。

```python
# 伪代码：由基础概率与分类器表现反推命中后的后验概率
base_rate = otp_events / all_login_sessions   # 目标事件基础概率
tp_rate = 0.964                               # 参照研究真阳性率
fp_rate = 0.002                               # 参照研究假阳性率
lr_pos = tp_rate / fp_rate                    # 阳性似然比
posterior = (base_rate * lr_pos) / (
    base_rate * lr_pos + (1 - base_rate)      # 贝叶斯反推
)
```

这段计算的示意输出与判读如下（示例数据，格式需对照实际系统核验）。

```text
base_rate=0.001  lr_pos=482  posterior=0.325
base_rate=0.010  lr_pos=482  posterior=0.830
base_rate=0.100  lr_pos=482  posterior=0.982
```

逐行判读：真阳性率百分之九十六点四、假阳性率百分之零点二看起来非常好，但当基础概率只有千分之一时，一次阳性命中的后验概率仅约百分之三十二点五——每三次命中大约两次是误报，这样的命中列表根本不能直接驱动封堵。基础概率升到百分之一，后验才到百分之八十三；升到百分之十，才接近百分之九十八。这说明"分类器很准"与"命中即可封堵"是两回事，目标越稀有，同样的分类器产出越不可直接执行。因此阈值不能拍脑袋定为"大概率"，必须用本网基础概率和似然比反推，并把精确率、召回率、混淆矩阵作为系统的验收指标固定下来。若本网基础概率确实在千分之一量级，那么任何声称"大概率命中即可封堵"的设计都应当被这条计算直接否决。

### 4. 建议三：封堵动作要可逆、分级、可申诉

既然接受误报，就必须控制误报的代价。一刀切丢弃把每一次误判都变成一次真实的通信中断，代价最高且不可撤销。分级处置的核心是把误报代价和漏报代价分开定价：低置信度只做标记和限速，几乎不影响用户；中置信度采用延迟放行，利用验证码通常五到十分钟的有效期，把消息拖过有效期在效果上等于封堵，但用户感知是"验证码过期"而不是"网络被掐"；只有高置信度才进入阻断，并且必须配人工复核与快速恢复通道。图 SUP-02-06-02 把这条分级路径画出来。

:::figure id=SUP-02-06-02 | name=分级可逆处置与情报输出 | dir=LR
node n1 "判定输出<br/>风险分与置信度" blue
node n2 "低置信度<br/>标记与限速" teal
node n3 "中置信度<br/>延迟放行" amber
node n4 "高置信度<br/>才考虑阻断" red
node n5 "验证码有效期<br/>五至十分钟" amber
node n6 "用户感知<br/>验证码过期非断网" teal
node n7 "人工复核与快速恢复<br/>可逆可申诉" blue
node n8 "情报输出<br/>喂给风控与客服" teal
edge n1 -> n2 "低分"
edge n1 -> n3 "中分"
edge n1 -> n4 "高分"
edge n3 -> n5 "利用时效"
edge n5 -> n6 "降低伤害"
edge n4 -> n7 "兜底"

:::

图中节点速览：n1 是判定输出的风险分与置信度，是后续分级的依据；n2 是低置信度的标记与限速；n3 是中置信度的延迟放行；n4 是高置信度才考虑阻断；n5 是验证码五至十分钟的有效期，是延迟放行能生效的前提；n6 是用户侧感知，即验证码过期而非网络被掐；n7 是人工复核与快速恢复通道，保证处置可逆可申诉；n8 是情报输出，把风险分喂给风控与客服，是推荐的主用途。整张图表达的是：同样的判定分数，走处置分支的伤害依次递增，走情报分支的伤害最小。

分级处置矩阵见下表（区间为示意，需按业务容忍度标定）。

| 置信度区间 | 处置动作 | 用户感知 | 可逆性 | 适用范围 |
|---|---|---|---|---|
| 低于百分之三十 | 标记与限速 | 无明显感知 | 完全可逆 | 大批量低质命中 |
| 百分之三十至八十 | 延迟放行六至十分钟 | 验证码过期 | 可逆 | 主要处置区间 |
| 高于百分之八十 | 阻断并人工复核 | 登录失败 | 需人工恢复 | 少量高危命中 |

表中第二行是这套分级的关键：延迟放行把"通信权"的剥夺换成"时效"的消耗，既不真正丢包，又达到让验证码失效的效果，同时保留了撤销可能。需要说明两个限制：延迟放行依赖对消息时效的精确控制，对实时性要求高的消息场景不适用；人工复核意味着需要运营资源和可追溯日志，不能只建算法不建流程。若这两项配套缺位，分级处置就退回到一刀切。

### 5. 建议四：把系统产出定位成情报而非开关

概率判定的正确用法，是输出风险分喂给风控和客服流程，而不是自动执行丢弃。这与 SUP-04 的"风险即服务"是同一条路：同一套三段闭环能力，用来做异常登录保护是资产——帮应用方拦住盗号，产出的是风险提示，误判的代价只是让用户多做一次验证；用来做定向营收封堵则是负债——产出的是阻断指令，误判的代价是切断正常通信。同一份信号，用途不同，结论相反。

因此更现实的产品形态是：把系统接入运营商已有的号码认证与风控接口，对检出的异常登录序列输出风险分，供应用方决定是否追加验证；把营收问题交回 A2P 产品化、富媒体商业消息与运营商自有认证。这样既用上了前面所有识别能力，又不承担歧视性阻断的合规风险。

### 6. 边界提示、结论与交叉引用

必须再次明确：以上四条只改善技术有效性，不改变结构性断点。落点两难与施压对象错位不因概率化而改变——概率系统依然封不到 inDrive 的通道决策，营收因果链仍不通。更准确地说，风险分级让封堵的伤害变小，但也让"封堵"这件事本身更难被证明为必要：当一个系统需要靠分级和申诉来兜底时，它实际产出的已经更接近情报，而不是开关。

1. **三段闭环优于二段共现**：回填二次请求既提供强区分信号，又自带真值标签，可离线标定、无需设备插桩。
2. **阈值必须由基础概率反推**：目标事件越稀有，同样的准确率产出的误报越多；千分之一基础概率下，百分之九十六点四真阳性率仍对应约三分之二的误报命中。
3. **处置要分级可逆**：低置信度标记限速、中置信度延迟放行、高置信度才阻断，并配人工复核与快速恢复。
4. **产出定位为情报**：把风险分喂给风控与客服，是这套能力伤害最小、合规风险最低的用法；它与 SUP-04 的风险即服务同源。
5. **不改结构性结论**：四条建议均不触及封堵落点与施压对象，因此仍无法达成提振短信营收的目标；它们只是在"如果一定要做"的前提下，给出了伤害最小的做法。
