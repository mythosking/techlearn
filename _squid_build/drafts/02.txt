# Squid 技术资料 · 02 编译与构建

## 02-01 编译环境准备：依赖与工具链

### 1. 背景与动机

多数发行版提供打包好的 Squid，安装简单但版本滞后、特性开关固定。自研或需要特定模块（SSL-Bump、ICAP、认证辅助程序）时，从源码编译是必经之路。编译失败绝大多数不是代码问题，而是依赖缺失或工具链版本不匹配。本篇把环境准备讲清楚。

### 2. 核心概念

Squid 使用 GNU AutoTools（autoconf/automake/libtool）作为构建系统，主体是 C++，因此需要 C++ 编译器与标准库。可选的依赖按功能分组：

| 依赖组 | 代表库 | 启用能力 | 缺失后果 |
|---|---|---|---|
| 编译工具链 | g++/clang、make、autoconf、automake、libtool | 基础构建 | 无法 bootstrap |
| TLS | OpenSSL / GnuTLS | https_port、SSL-Bump | 无法处理 HTTPS |
| 文本处理 | PCRE | 正则 ACL（url_regex 等） | 正则匹配不可用 |
| 压缩 | zlib、liblzma、libzstd | 内容编码与日志压缩 | 相关特性关闭 |
| 认证 | OpenLDAP、MIT/Heimdal Kerberos | LDAP/Kerberos 辅助程序 | 对应认证不可用 |
| 数据库 | libdb | 旧式缓存认证后端 | 特定后端不可用 |
| 系统 | libcap、libpthread、IPv6 头文件 | 能力裁剪、线程、IPv6 | 特性降级 |

### 3. 关键流程

编译前的准备顺序是：安装编译工具链 → 安装可选依赖开发包 → 获取源码 → 运行 bootstrap 生成 configure 脚本。值得注意的是，从 Git 仓库克隆的源码不含生成的 configure，必须先 bootstrap；而官方发布的 tarball 通常已包含 configure，可直接配置。这个差别是新手最常见的困惑来源。

### 4. 命令示例

命令示例 · Shell（Debian/Ubuntu 系列）：

```bash
sudo apt-get update
sudo apt-get install -y build-essential autoconf automake libtool \
  libssl-dev libpcre3-dev zlib1g-dev libcap-dev
git clone https://github.com/squid-cache/squid.git
cd squid && ./bootstrap.sh
```

命令示例 · Shell（RHEL 系列）：

```bash
sudo dnf install -y gcc-c++ autoconf automake libtool \
  openssl-devel pcre-devel zlib-devel libcap-devel
```

判读要点：`bootstrap.sh` 成功后当前目录出现 configure；若报 automake 版本过低，按提示升级或改用发布 tarball。具体包名在不同发行版有差异，需对照实际仓库。

### 5. 陷阱与最佳实践

- **装了运行库没装开发包**：例如只有 libssl 没有 libssl-dev，configure 探测失败。开发包通常带 -dev 或 -devel 后缀。
- **混用 OpenSSL 与 GnuTLS**：TLS 后端要提前选定，中途切换需清理构建目录。
- **忘记 libcap**：未启用能力支持时，以 root 启动会被 Squid 拒绝，需要额外配置。

### 6. 小结

环境准备的核心是「工具链 + 分层依赖 + bootstrap」。下一步 `02-02` 给出完整编译实战。

## 02-02 从源码完整编译 Squid 实战

### 1. 目标

在干净环境中走通从源码到可运行二进制的完整流程，理解每一步的产物与失败点。

### 2. 前置条件

按 `02-01` 装齐依赖，源码已 bootstrap 生成 configure。建议非 root 用户编译，安装阶段再用 sudo。

### 3. 分步操作

命令示例 · Shell：完整编译流程。

```bash
./configure --prefix=/usr/local/squid \
  --enable-ssl --with-openssl \
  --enable-linux-netfilter \
  --enable-delay-pools
make -j$(nproc)
sudo make install
```

每一步的含义：

- configure：探测系统、生成 Makefile 与配置头。选项决定了哪些模块被编译进来。
- make：编译全部目标。-j 并行数取 CPU 核数可显著加速。
- make install：安装二进制、配置模板、辅助程序到 prefix 指定目录。

验证命令：

```bash
/usr/local/squid/sbin/squid -v          # 查看版本与编译选项
/usr/local/squid/sbin/squid -k parse    # 校验默认配置
```

判读要点：`squid -v` 输出的 configure 选项应与编译时一致，这是确认特性是否真正启用的最快方法。若发现某个 --enable 选项没生效，多半是依赖探测失败被静默关闭，回头看 configure 输出。

### 4. 常见失败与排错

- configure 报「cannot find SSL library」：TLS 开发包未装或路径非标准，用 --with-openssl=路径指定。
- make 中途编译错误：先看第一个错误，多数是依赖头文件版本不兼容。
- 安装后启动失败：检查 prefix 下的 sbin/squid 是否存在、配置模板是否生成。

### 5. 小结

编译流程本身不复杂，难点在依赖与选项。`02-03` 系统梳理 configure 选项。

## 02-03 configure 选项详解

### 1. 本篇定位

configure 选项数量众多，本篇按功能族归类，给出高频选项、作用与取舍，作为查表使用。完整列表以 `./configure --help` 为准。

### 2. 选项分类速查

| 选项族 | 代表选项 | 作用 | 建议 |
|---|---|---|---|
| 路径 | --prefix、--sbindir、--sysconfdir | 安装布局 | 发行版打包时按需拆分 |
| TLS | --enable-ssl、--with-openssl、--with-gnutls | HTTPS 与 SSL-Bump | 二选一，不要混用 |
| 认证 | --enable-auth、--enable-basic-auth、--enable-negotiate-auth | 认证框架与方案 | 按实际认证源启停 |
| 内容适配 | --enable-icap-client、--enable-ecap | ICAP/eCAP 支持 | 需要内容改写时启用 |
| 网络 | --enable-linux-netfilter | 透明代理拦截 | Linux 透明代理必开 |
| 缓存 | --enable-delay-pools、--enable-cache-digests | 带宽管理与缓存摘要 | 视场景启用 |
| 存储 | --with-maxfd、--enable-rock-store | 描述符上限与 rock 后端 | 高并发调大 maxfd |
| 调试 | --enable-debug、--enable-asan | 调试符号与内存检测 | 仅开发测试启用 |

### 3. 典型示例

命令示例 · Shell：一个功能较全的编译配置。

```bash
./configure --prefix=/usr/local/squid \
  --enable-ssl --with-openssl \
  --enable-icap-client \
  --enable-linux-netfilter \
  --enable-delay-pools \
  --enable-cache-digests \
  --with-maxfd=16384
```

判读要点：`--with-maxfd` 提升可打开文件描述符上限，高并发部署必调；启用选项越多，二进制越大、攻击面越广，生产环境应按需最小化。

### 4. 版本差异与常见误用

- 部分选项在新版本被移除或改名（如某些认证辅助程序独立出去），升级时对照 `configure --help`。
- 误把仓库自带测试选项当生产选项启用，导致性能下降或行为异常。
- 依赖探测失败时 configure 可能「静默关闭」特性，务必看输出末尾的汇总表确认。

### 5. 小结

configure 选项决定了 Squid 的能力边界。定好选项后，`02-04` 解释构建系统与源码目录如何组织这些能力。

## 02-04 构建系统与源码目录结构

### 1. 本篇定位

理解源码目录分布，才能在遇到问题时快速定位文件。本篇是目录导览，不展开模块原理（原理见 `06`，模块见 `07`）。

### 2. 源码目录总览

| 目录 | 内容 | 何时翻阅 |
|---|---|---|
| src/ | 主程序、核心类、协议处理 | 追调用链、查核心逻辑 |
| src/acl/ | 访问控制链表实现 | 查 ACL 匹配逻辑 |
| src/ssl/ | SSL-Bump 与证书处理 | 查 HTTPS 拦截 |
| src/fs/ | 存储后端实现 | 查落盘机制 |
| src/log/ | 日志模块 | 查日志格式与输出 |
| src/clients/、src/server/ | 客户端与源站侧处理 | 查请求/响应流程 |
| helpers/ | 认证、重写、内容适配辅助程序 | 查 helper 协议实现 |
| lib/ | 通用工具库 | 查基础数据结构 |
| scripts/、test-suite/ | 构建脚本与测试 | 查测试与回归 |

### 3. 关键文件定位法

面对一个符号，最快定位方式是文本搜索。例如查 `http_port` 指令定义，在 src/ 下搜索该字符串，通常命中 cf.data.pre（定义）与解析代码；查某个类名，搜索类名找到头文件与实现文件。

### 4. 常见误用

- 在错误的目录搜索符号，浪费时间。先按上表判断归属再搜。
- 直接改生成文件（如 squid.conf.documented）而非源文件 cf.data.pre，下次构建被覆盖。

### 5. 小结

目录结构是查源码的地图。掌握它，后面各册给出的源码路径才能落到实处。

## 02-05 发行版打包与容器镜像

### 1. 背景与动机

生产环境很少直接「make install」到裸机，通常用系统包或容器交付。两种方式各有坑：发行版包版本滞后但集成好；容器隔离好但网络与缓存持久化要额外设计。

### 2. 发行版包

命令示例 · Shell：

```bash
sudo apt-get install squid           # Debian/Ubuntu
sudo dnf install squid               # RHEL 系列
squid -v | head -5                   # 确认版本与编译选项
```

判读要点：系统包常拆分出 squid-common、squidclient 等子包；SSL-Bump 等特性是否在包内启用，用 `squid -v` 确认，不要假设。

### 3. 容器镜像

容器化要点是三件事：配置外挂、缓存目录持久化、网络模式选择。

配置片段 · Dockerfile（要点示例）：

```dockerfile
FROM debian:stable-slim
RUN apt-get update && apt-get install -y squid && rm -rf /var/lib/apt/lists/*
COPY squid.conf /etc/squid/squid.conf
RUN mkdir -p /var/spool/squid && chown -R proxy:proxy /var/spool/squid
EXPOSE 3128
ENTRYPOINT ["squid", "-N", "-f", "/etc/squid/squid.conf"]
```

配套运行要点：用卷挂载 cache_dir 以持久化缓存；`-N` 让 Squid 前台运行，符合容器主进程约定；透明代理场景需 host 网络或显式端口映射配合。

### 4. 陷阱与最佳实践

- 容器内以 root 运行被 Squid 拒绝，需用 proxy 用户或调整能力配置。
- 缓存目录不挂载卷，容器重建后缓存全丢。
- 系统包与自编译混装，导致二进制与配置路径不一致。

### 5. 小结

编译与构建篇到此结束。从此有了可运行的 Squid，下一步 `03` 部署把它落到具体拓扑里。
