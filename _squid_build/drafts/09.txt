# Squid 技术资料 · 09 统一代理平台架构设计

> 本册是一份**架构设计蓝图**，讨论如何在一套数据面上同时承载正向代理、反向代理与中间人审计三种角色。它不是某个现有开源软件的能力声明，而是对 06-18～06-22 选型讨论的收束与推演。文中涉及的 Squid 指令、字段与源码落点沿用 04、05、06 册的唯一权威源口径，配置骨架只表达结构，指令名与默认行为需对照目标版本核验。

## 09-01 目标、角色模型与单实例多角色

### 1. 背景与动机

前面各册把 Squid 作为一个具体软件拆解：它怎么编译、怎么部署、怎么配置、内部怎么跑、怎么运维。但工程选型时经常跳出一个更高层的问题：**如果我要一套系统，既能挡在业务前面做反向代理，又能放在出口做正向代理，还能对指定流量做中间人审计，它应该长什么样？**

这个问题不再是"Squid 会不会",而是"一套代理平台该怎样组织"。答案的第一块基石是一个容易被误解的判断：**角色不是进程的属性，而是每条连接的属性**。正向、反向、中间人不是三个软件，也不必是三个进程——它们是同一条数据面上，几个决策点取不同值的结果。

### 2. 核心概念

先固定四个术语，后面全程按此口径：

| 术语 | 回答的问题 | 关键特征 |
|---|---|---|
| 正向代理 | 客户端怎么访问外网 | 客户端主动配置，代理替客户端上网，对服务端隐藏客户端 |
| 反向代理 | 客户端访问哪个后端 | 服务端在入口部署，客户端无感，对客户端隐藏后端 |
| 中间人审计 | HTTPS 能否被看见 | 伪造目标证书，依赖客户端信任代理 CA，受合规约束 |
| 统一代理平台 | 三者能否共存于一套系统 | 入口可多选、TLS 策略按域名切换、上游由上下文决定 |

角色由入口决定，而不是由进程决定。同一个进程开两类监听端口，就能同时对外提供两类服务；对一条具体连接而言，入口在建立时就确定了它的角色，中途不会切换。因此"一个软件同时做正向和反向"完全成立，且是商业 SWG/SASE 产品的常态形态。

### 3. 关键结构

图 09-01-01 把单实例多角色画成一张链路图：同一个进程内，正向监听服务内网客户端访问任意 Internet，反向 accel 监听服务外部用户访问固定后端池，两类流量在进程内共享数据面，但角色从入口起就分开。

### 4. 多角色共存的判据

判断一个平台是否真的支持多角色，看三件事：

1. **入口能否多选**：普通正向端口、反向 accel 端口、透明 TPROXY、SOCKS5 能否在同一实例里并存。
2. **TLS 策略能否按域名切换**：同一批流量里，有的域名 splice 透传，有的域名 bump 解密，反向入口则用自己的证书终止。
3. **上游能否由上下文决定**：正向的上游是任意 Internet，反向的上游是固定后端池，两者靠会话上下文而非全局配置区分。

以 Squid 为例，同一实例同时开正向与反向入口的配置骨架如下（指令细节见 04-02，需对照版本核验）：

```text
# 正向出口：内网客户端把浏览器代理指向这里
http_port 3128

# 反向入口：对外提供业务加速，客户端无需任何代理设置
http_port 10.0.0.1:80 accel vhost
https_port 10.0.0.1:443 accel vhost cert=/etc/squid/cert.pem key=/etc/squid/key.pem

# 后端声明与分流：只有 accel 流量走 cache_peer
cache_peer 10.0.0.11 parent 80 0 originserver name=app1
cache_peer 10.0.0.12 parent 80 0 originserver name=app2
cache_peer_access app1 allow dstdomain app.example.com
```

这段骨架的意义在于说明：**正向与反向共用同一个配置体系与事件循环，只在入口处分流**。同一份 ACL 引擎、同一套证书框架、同一个缓存层被两种角色复用，这正是统一平台的价值所在。

### 5. 陷阱与最佳实践

- 不要把"单实例"理解成"单端口"。角色绑定在入口上，一个实例通常需要多个监听端口承载不同角色。
- 不要试图让一条连接中途切换角色。连接建立时角色已确定，强行改向会造成状态机混乱与日志错乱。
- 不要把"同时承载"当作"共用策略"。角色隔离是后面的硬约束（见 09-04），共用配置体系不等于共用策略语义。
- 配置骨架只表达结构，指令名、参数与默认行为按目标版本核验后再上线。

### 6. 小结

统一代理平台的起点是一个观念转变：角色属于连接，不属于进程。由此，正向、反向、中间人不再是三套软件，而是同一条链上几个决策点的不同取值。下面 09-02 拆解这条链的分层结构。

## 09-02 六层数据面架构

### 1. 背景与动机

确定"单实例多角色"之后，需要回答平台内部怎么分层。分层的目的不是好看，而是把不同时间尺度的处理隔离开：包处理是微秒级，TLS 握手是毫秒级，ICAP/AV/DLP 是毫秒到秒级，日志落盘更慢。混在一层里，最慢的环节会拖垮最快的路径。

### 2. 六层职责

图 09-02-01 给出统一平台的六层数据面。它是一个单向流水线，请求自上而下、响应自下而上，每一层只做自己那一类决策。

:::figure id=09-02-01 | name=统一代理六层数据面 | dir=TD
node n1 "接入层" blue
node n2 "TLS 引擎层" teal
node n3 "HTTP 语义层" teal
node n4 "策略与路由引擎" purple
node n5 "缓存与内容适配" purple
node n6 "上游与出口" green
edge n1 -> n2
edge n2 -> n3
edge n3 -> n4
edge n4 -> n5
edge n5 -> n6
:::

图中节点速览：接入层接连接，TLS 引擎层解密或终止，HTTP 语义层解析明文，策略与路由引擎做决策，缓存与内容适配做存储和改包，上游与出口负责转发。请求向下、响应向上，共用同一组分层。

### 3. 每层的关键功能

| 层 | 必须具备的能力 | 为什么这一层做 |
|---|---|---|
| 接入层 | 多模式监听、协议嗅探、连接与 fd 管理、上游长连接复用 | 角色在入口确定，接入层是唯一能看到原始连接属性的地方 |
| TLS 引擎层 | 终止 / 伪造 Bump / 透传三态共存，决策状态机，CA 与叶证书签发缓存，会话恢复，硬件加速 | 加解密开销最大，必须集中管理并支持异步卸载 |
| HTTP 语义层 | HTTP/1.1、HTTP/2、HTTP/3 解析，流式转发与零拷贝，Header/Body 改写，WebSocket 与 gRPC | 只有在明文层才能做内容级改写与协议适配 |
| 策略与路由引擎 | 统一 ACL 匹配来源、域名、SNI、用户、内容；规则可同时选出网与选后端；热加载 | 三种角色共用一套规则，决策点必须统一 |
| 缓存与内容适配 | 正向与反向缓存共用存储与置换，ICAP/eCAP 钩子，AV/DLP/WAF 独立接入 | 缓存命中能跳过后面所有慢路径 |
| 上游与出口 | 连接池、健康检查、负载均衡、代理链、出站 IP 与路由策略 | 正向与反向的上游语义不同，要按上下文分流 |

### 4. 横向能力

六层之外还有一组贯穿全链路的能力，缺一不可：

- **统一日志与指标**：连接数、握手速率、bump 比例、缓存命中率、P99 延迟，按角色分别聚合。
- **Runtime API**：不重载就改后端、改权重、改策略，避免改一条规则就重启。
- **全链路追踪**：按请求串起接入、TLS、策略、缓存、上游各阶段的耗时。
- **配置热更新**：规则与证书都能在线生效，且变更可追溯。

### 5. 与 Squid 现有模块的对应

统一平台不是凭空设计，它的每一层在 Squid 里都能找到对应物：接入层对应 `http_port` / `https_port` 与 comm 层（06-09），TLS 引擎层对应 SSL-Bump 状态机（06-06、06-11），HTTP 语义层对应请求解析与转发，策略层对应 ACL 框架（06-07、06-10），缓存层对应 StoreEntry 与存储引擎（06-03、06-12），上游层对应 peer 与 FwdState（05-04）。差别在于 Squid 的这些模块是为正向缓存设计的，统一平台要求它们同时服务反向与审计场景，因此每层都要补上角色维度。

### 6. 陷阱与最佳实践

- 不要按软件模块分层，要按处理时态分层。同一时间尺度的处理放一起，隔离才有效。
- TLS 引擎层是最难自研的一层，涉及证书信任链与双会话关联，不宜用简单封装替代（见 06-14、06-15）。
- 策略引擎必须能表达"这条规则适用于哪个角色"，否则三种角色的规则会互相污染（见 09-04）。
- 横向能力不是附属品。没有按角色聚合的指标，多角色平台上线后无法排障。

### 7. 小结

六层数据面是功能骨架，横向能力是神经系统。真正决定性能上限的，是下一节要讲的三个决策点如何取值，以及快慢路径是否物理隔离。

## 09-03 三个决策点与角色取值

### 1. 背景与动机

同一个 pipeline，靠几个开关就能区分角色？答案是三个决策点：**入口如何接收、TLS 如何处理、上游去哪里**。把这三个点讲清楚，"既能正向又能反向还能中间人"就不再是一句口号，而是一组可配置的取值。

### 2. 三个决策点

图 09-03-01 把三个决策点与角色取值的关系画成一张汇聚图：三种角色是三个决策点各自取值的组合结果。

:::figure id=09-03-01 | name=三个决策点决定角色 | dir=LR
node n1 "三个决策点" blue
node n2 "入口如何接收" teal
node n3 "TLS 如何处理" teal
node n4 "上游去哪里" teal
node n5 "角色 = 取值组合" purple
edge n1 -> n2
edge n1 -> n3
edge n1 -> n4
edge n2 -> n5
edge n3 -> n5
edge n4 -> n5
:::

图中节点速览：入口、TLS、上游三个决策点共同决定一条连接的角色。改变任意一个取值，角色随之改变。

### 3. 取值矩阵

| 决策点 | 正向代理 | 反向代理 | 中间人（Bump） |
|---|---|---|---|
| 入口如何接收 | 客户端配置代理 / 透明拦截 | accel 端口对外服务 | 通常附着在正向入口 |
| TLS 如何处理 | 透传或 Bump | 自有证书终止 | 伪造目标证书 |
| 上游去哪里 | 任意 Internet | 固定后端池 | 原目标站点 |

三种角色中，中间人不是一个独立的入口形态，而是"正向入口 + Bump 这个 TLS 取值"的组合。这解释了为什么 06-22 强调出口与 SSL-Bump 是"位置 + 可选功能"的关系，而不是并列关系。

### 4. 策略表达示例

一套统一 ACL 要能同时表达三种角色的意图。下面的骨架展示作用域如何写进规则（仅表意，语法需对照版本核验）：

```text
# 正向出口：按域名决定是否解密
acl step1 at_step SslBump1
acl no_bump ssl::server_name .bank.com .gov.cn .pay.com
acl audit_sites ssl::server_name .example.com .saas.example.net
ssl_bump peek step1
ssl_bump splice no_bump
ssl_bump stare step2 audit_sites
ssl_bump bump step3 audit_sites
ssl_bump splice all

# 反向入口：按目标域名选后端，不参与 bump 决策
acl app1 dstdomain app.example.com
cache_peer_access app1 allow app1
```

注意两段规则虽然写在同一份配置里，但作用域不同：第一段作用于正向入口的 TLS 决策，第二段作用于反向入口的后端选择。把它们分开的关键是入口 role 标记（见 09-04）。

### 5. 为什么说这是商业产品的真实形态

商业 SWG/SASE 产品的控制台里，管理员同时配置"内网用户上网策略"（正向）、"对外发布的应用"（反向）和"HTTPS 检查规则"（中间人），三者共存于一套策略引擎、一套日志系统、一套证书体系。这正是三个决策点取不同值的工程实现，也验证了这条路线的可行性。

### 6. 陷阱与最佳实践

- 不要把中间人当成第四个独立角色。它是正向入口上一个 TLS 取值，认清这点能省掉大量架构歧义。
- 反向入口不该做 Bump。证书本来就是自己的，直接终止即可，伪造反而破坏信任链（见 06-22）。
- 决策点要集中表达。分散在多个模块的开关会让"这条连接为什么被解密"难以回答。
- 策略冲突要可预测。三种角色共用规则时，优先级必须显式定义（见 09-06）。

### 7. 小结

三个决策点把角色从"软件种类"降维成"配置取值"。下一步 09-04 讨论：当三种取值在同一进程里并存时，哪些东西必须严格隔离。

## 09-04 多角色共存的五个硬约束

### 1. 背景与动机

单实例多角色的收益是共享——共享事件循环、共享 ACL 引擎、共享缓存、共享日志系统。但共享带来一个危险：**同一句"允许所有"，在出口是放行内网用户上网，在入口就变成放行外网用户访问后端**。语义完全相反。因此"共用一套代码"必须配"严格隔离的上下文"，这就是五个硬约束的由来。

### 2. 约束全景

图 09-04-01 把五个约束画成从"单实例多角色"出发、汇聚到"稳定运行"的隔离图：每一项都是必须完成的隔离维度。

图中节点速览：五个隔离维度都从多角色共存这个前提出发，共同支撑策略语义稳定。缺任何一项，都会出现跨角色污染。

### 3. 五项约束详解

| 约束 | 风险表现 | 实现要点 |
|---|---|---|
| 角色标记贯穿全链路 | 入口之后模块不知道这条连接是谁的，策略误用 | 每个 listener 打 role 标签，写进会话元数据，策略、缓存、日志一律带这个维度 |
| 证书体系双轨 | 正向伪造证书与反向自有证书混用，信任链错乱 | 两套 CA、两套缓存、两套信任链严格隔离，禁止互签 |
| ACL 命名空间隔离 | 同一规则在出口与入口含义相反，配置一改两边都变 | 规则显式声明作用域；角色缺省时不匹配，而不是默认匹配 |
| 缓存与连接池分离 | 正向缓存互联网内容、反向缓存业务内容，互相污染 | 按 role 分 store 分区与连接池，避免串味和错误复用 |
| 日志与指标打角色标签 | 混在一起无法排障，算不出 bump 比例与命中率 | 连接数、握手速率、bump 比例、命中率按角色分别聚合 |

### 4. 角色标记的落点

角色标记必须在入口产生，并跟随会话贯穿全链路。下面的伪代码表达这个约束（结构示意，非任何现有软件的真实接口）：

```text
on_accept(listener, fd):
    session = new Session(fd)
    session.role = listener.role        # FORWARD / REVERSE
    session.tls_mode = decide_tls(session)  # TERMINATE / BUMP / SPLICE
    attach(session, metadata_bus)

policy_match(session, rule):
    if rule.scope not in (session.role, "ANY"):
        return NO_MATCH                  # 缺省不匹配，杜绝跨角色误命中
    return evaluate(rule, session)
```

关键点在 `scope` 的缺省行为：无作用域声明的规则默认不匹配，而不是默认匹配。这个选择牺牲了一点配置便利性，换来的是"改一条规则不会意外影响另一个角色"的可预测性。

### 5. 与"Squid 能否同时正反"的关系

回到 09-01 的问题：Squid 用 `http_port ... accel` 与 `http_port 3128` 共存在同一实例，说明角色标记在 Squid 里是有雏形的——accel 端口与普通端口走不同的请求处理路径。但 Squid 并没有把 role 做成贯穿全链路的一等元数据，因此缓存、日志、策略的隔离仍需管理员靠配置纪律保证。统一平台要把这条纪律固化成结构。

### 6. 陷阱与最佳实践

- 不要把 role 存在全局变量或按连接临时推断。它必须是会话的一等字段，随会话传递。
- 证书双轨不只是两把钥匙，而是两条完整的签发与缓存链，包括 OCSP/CRL 与会话恢复状态。
- ACL 缺省行为要选"不匹配"。选"匹配"会让漏写作用域的规则变成安全漏洞。
- 日志字段要包含 role，且指标按 role 分组。否则多角色平台的监控是一笔糊涂账。

### 7. 小结

五个硬约束的本质是"共享代码、隔离语义"。它们不增加新功能，却决定了多角色平台能不能安全上线。下一节转向性能：把快路径与慢路径物理隔离。

## 09-05 快路径与慢路径的物理隔离

### 1. 背景与动机

六层架构列全了功能，但功能齐全不等于高性能。决定吞吐的关键设计只有一条：**快路径与慢路径必须物理隔离**。任何在 worker 线程里发生的同步签发、同步落盘、同步 ICAP 调用，都会把吞吐打回原型机水平。

### 2. 隔离模型

图 09-05-01 画出了快慢路径的边界：请求进入后，能立即处理的部分留在快路径，慢操作通过异步边界队列交给独立执行单元，结果回流后再从出口返回。

:::figure id=09-05-01 | name=快路径与慢路径隔离 | dir=LR
node n1 "请求入口" blue
node n2 "快路径<br/>转发与命中" teal
node n3 "慢路径<br/>签发/落盘/策略" amber
node n4 "异步边界队列" purple
node n5 "响应出口" green
edge n1 -> n2
edge n1 -> n4
edge n4 -> n3
edge n2 -> n5
edge n3 -> n5
:::

图中节点速览：请求在入口分为两路，快路径直接转发或命中缓存，慢路径经异步队列处理签发、落盘与外部策略，两路结果都在出口汇合。

### 3. 职责划分

| 路径 | 典型操作 | 时间尺度 | 隔离要求 |
|---|---|---|---|
| 快路径 | 转发、缓存命中、splice 决策、简单 ACL、连接复用 | 微秒到毫秒 | 留在 worker 线程，禁止任何阻塞调用 |
| 慢路径 | 证书签发、缓存落盘、ICAP/AV/DLP、认证查询、日志写入 | 毫秒到秒 | 独立线程池或进程，通过队列与主链路解耦 |
| 异步边界 | 任务入队、结果回调、超时与降级 | 取决于队列 | 必须有背压与超时，避免慢路径拖垮快路径 |

### 4. 背压与降级

异步隔离不是把任务丢进队列就完事。队列必须有明确的背压与降级策略：

- **有界队列**：队列长度设上限，超限直接降级，避免内存被慢操作撑爆。
- **超时即放行**：ICAP/AV 超时时按配置选择 fail-open 或 fail-close，不能无限等待。
- **证书预生成**：热门域名的叶证书提前签好并缓存，避免每次握手都进慢路径。
- **日志批量异步**：日志写 Kafka 或批量落盘，不阻塞主线程。

### 5. 性能杠杆：bump 比例

在中间人场景里，性能的主变量不是转发带宽，而是解密比例。设 bump 比例为 r，每个 bump 连接带来两次 TLS 握手、双向加解密、一次证书签发与一次内容检查；splice 连接只有转发开销。因此：

```text
总开销 ≈ 转发开销 + r × (握手 + 加解密 + 签发 + 内容检查)

r → 0   退化为普通转发代理，吞吐接近线速
r → 1   全量解密，吞吐由最慢的慢路径环节决定
```

结论很直接：**把 splice 做扎实，让绝大多数流量不进解密链**，是提升容量最有效的手段，比换更快的 CPU 或加硬件加速卡都有效。这也是 06-17、06-18 反复强调选择性解密的原因。

### 6. 陷阱与最佳实践

- 不要把"异步"做成"无限队列"。没有背压的异步只是把阻塞延迟到内存耗尽。
- 不要全量 stare。全量观察 SNI 等于把所有连接推进慢路径。
- 硬件加速只解决加法里的"加解密"项，不解决"签发"和"内容检查"项（见 06-18）。
- 压测时分别测 r=0 与 r=1 两个极端，中间值按线性插值估算，比单一数字更有参考价值。

### 7. 小结

快慢路径隔离是性能的必要条件，bump 比例是容量的主变量。两者结合，才能在不牺牲功能完整性的前提下得到可用吞吐。下一节讨论真正的难点排序。

## 09-06 难点排序与风险

### 1. 背景与动机

功能清单列完，最后要回答："按什么顺序做，风险最小？"三件事的优先级并不相同，顺序错了会浪费大量返工。

### 2. 难点排序

| 排序 | 难点 | 为什么难 | 应对 |
|---|---|---|---|
| 1 | TLS 三态状态机 | 伪造证书、双会话关联、CA 信任链，是几十年积累的核心，轻量封装做不深 | 复用成熟实现或独立成进程，勿塞进数据面 worker |
| 2 | 快慢路径隔离 | 任何同步签发、落盘、ICAP 调用都会毁掉吞吐 | 从设计第一天就划分边界，不要事后补救 |
| 3 | 策略一致性 | 三种角色共用规则，冲突与优先级必须可预测 | 作用域显式声明，缺省不匹配，变更可追溯 |
| 4 | 协议持续成本 | QUIC、ECH、TLS 1.3、证书固定在不断变化 | 明确降级与覆盖策略，按版本持续跟进 |

### 3. TLS 状态机为什么排第一

终止、伪造 Bump、透传三态共存，看似只是三个分支，实则牵动：ClientHello 阶段取 SNI 与 ALPN 的时机、peek/stare/splice/bump 的推进顺序、客户端 TLS 与上游 TLS 的会话关联、动态叶证书签发与缓存、会话恢复与 TLS 1.3 的兼容。这些逻辑相互耦合，任何一处时序错误都表现为"某些网站打不开"或"证书告警"，排查成本极高。凡是要做中间人的平台，这一层都要当作核心资产对待。

### 4. 协议演进是持续成本

QUIC/HTTP3 走 UDP 443，中间人要么阻断后降级到 TCP，要么单独设计 QUIC 代理链路；ECH 加密了 SNI，基于域名的 peek 决策受限；证书固定让伪造证书直接失败。这些都不是一次性功能，而是需要长期跟进的兼容成本。架构上要为"新增一种协议处理方式"预留扩展点，而不是把决策逻辑写死在解析代码里。

### 5. 合规边界不是技术项

中间人能力的前提是客户端信任代理 CA，这要求组织拥有终端管理能力与明确的用户告知。没有这个前提，技术上能解密也用不了。把合规与信任链分发当成架构的一部分，而不是上线前补的文档，是这类平台能否落地的关键（见 06-15）。

### 6. 陷阱与最佳实践

- 不要从零写 TLS 状态机后再考虑性能。两者耦合紧密，需同步设计。
- 不要低估协议演进成本。选型时问一句"QUIC/ECH 来了怎么办"，答案要具体。
- 不要把合规当事后事项。CA 信任链分发决定中间人能力的覆盖率。
- 不要追求一次做全。先做透传 + 选择性 Bump，再逐步扩展协议覆盖。

### 7. 小结

难点排序给出一条务实的路线：先解决 TLS 与隔离这两个地基，再谈策略与协议覆盖。下一节把路线落成可执行的选项。

## 09-07 落地路线与自建判断

### 1. 背景与动机

最后回到工程决策：真要做这套平台，是组合现有软件，还是全自研？答案取决于规模与目标，但有一条通用原则——**不要从零写数据面**。

### 2. 三条路线

图 09-07-01 把三条路线画成分叉图：组合式部署、轻量插件、全自研，各自对应不同的适用场景。

:::

图中节点速览：从统一平台需求出发有三条路线，组合式部署是推荐起点，轻量插件是中期优化，全自研只适合专项场景。

### 3. 路线对照

| 路线 | 做法 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| 组合式部署 | Envoy/HAProxy 做反向与 TLS 终止，Squid 或自研应用做正向与 Bump，VPP 前置转发 | 各层用成熟组件，风险最低 | 多组件运维与状态同步 | 绝大多数企业场景 |
| 轻量 peek/splice 插件 | 在入口按 SNI 决策，多数流量直接 splice，少数 redirect 到 Bump 节点 | 投入产出比最高，90% 流量不进解密链 | 需要开发入口分流逻辑 | 已有 Squid 出口的性能优化 |
| 全自研应用 | VPP 数据面 + QAT/SmartNIC + 自研 MITM 应用进程 | 性能上限最高，可深度定制 | 接近自研一套 SWG，长期跟进协议 | 100G 级专项网关且已有团队 |

### 4. 推荐的演进顺序

1. **第一步：分层组合**。用反向代理与 TLS 终止骨架承接业务入口，用 Squid 承担正向与 Bump，验证策略与合规边界。
2. **第二步：入口分流**。加一层轻量分流，让银行、政务、支付等域名直接 splice，只把需要审计的域名送进 Bump 节点。
3. **第三步：按实证瓶颈自研**。只有在压测证明某环节确实是瓶颈、且现有组件无法调优解决时，才考虑替换该环节。

这个顺序的核心是：**先用成熟组件把功能跑通，再按数据决定优化哪里**，避免一开始就把全部工程量压在自研上。

### 5. 与 VPP 的分工

VPP 在这套平台里的位置是数据面加速，而不是替代 MITM 语义。它可以承担高速转发、分流、ACL 前置与 TLS 加解密卸载；Squid、Envoy 或自研应用承担证书策略、HTTP 语义、审计日志与内容检查。这一分工延续 06-19、06-20 的结论：VPP 与代理软件是互补关系，把正确的职责放在正确的层，比追求单一插件包办一切更能同时得到性能与功能完整性。

### 6. 陷阱与最佳实践

- 不要为"架构统一"而强行合并进程。分层组合的运维复杂度，通常低于全自研的维护成本。
- 不要在没有压测数据时自研。先测出 r 与瓶颈，再决定优化点（见 09-05）。
- 不要忽略证书信任链分发这个非技术问题，它决定中间人能力的实际覆盖率。
- 不要把"支持三种角色"当成上线标准。先支持一种角色跑稳，再扩展另外两种。

### 7. 小结

统一代理平台的合理路线是：组合式起步、入口分流优化、按实证瓶颈自研。三种角色可以共存于一套系统，但共存的价值来自共享与隔离的平衡，而不是把所有功能塞进一个模块。到这里，本册从角色模型、六层架构、决策点、隔离约束、性能设计、难点排序，收束到可执行的落地路线，与 06-18～06-22 的选型讨论形成闭环。

## 09-08 与加密隧道类工具的边界：可观测与抗观测

### 1. 背景与动机

讨论统一平台时经常被问到一个看似同类、实则异类的问题：Shadowsocks、V2Ray（及其后继 Xray）这些工具，和前面讲的 Squid、Envoy、HAProxy、mitmproxy 都是"代理"，差别在哪？答案不在性能，而在设计目标的象限：**网关代理要把流量管起来，加密隧道要把流量藏起来**。前者服务于网络管理员，后者服务于终端用户绕过路径管控。认清这条分界线，才不会拿错工具、也不会误判安全性。

> 术语说明：Shadowsocks 是一种加密 SOCKS5 代理协议；V2Ray 是一套支持多协议入站出站与路由规则的网络代理软件，其社区后继项目常称 Xray-core。二者的具体版本、协议名与功能开关需对照各自官方文档核验，本节只讨论架构定位。

### 2. 两类工具的正反目标

图 09-08-01 把两类工具放在对立象限：左侧隧道类让流量对链路不可见，右侧网关类让流量对管理员可见。它们对明文的态度正好相反。

:::figure id=09-08-01 | name=可观测与抗观测两类定位 | dir=LR
node n1 "加密隧道类" blue
node n2 "Shadowsocks / V2Ray" blue
node n3 "网关代理类" teal
node n4 "Squid / Envoy / HAProxy" teal
node n5 "藏起来：抗检测<br/>最小化日志" purple
node n6 "管起来：可审计<br/>内容级策略" green

:::

图中节点速览：左侧是 Shadowsocks/V2Ray 代表的隧道类，目标是抗检测、少留痕；右侧是 Squid/Envoy/HAProxy 代表的网关类，目标是可审计、可策略化。两类工具对"明文该不该被看见"的回答相反。

### 3. 逐项对比

| 维度 | 加密隧道类（Shadowsocks / V2Ray） | 网关代理类（Squid / Envoy / HAProxy / mitmproxy） |
|---|---|---|
| 设计目标 | 穿越不可信链路、规避检测与封锁 | 在可控网络内做转发、缓存与审计 |
| 工作层次 | 会话层加密隧道，字节流中继 | 应用层/传输层代理，理解 HTTP 语义 |
| 加密模型 | 自建加密信道，隐藏流量特征 | 处理标准 HTTPS，不改变链路加密特性 |
| 对明文的态度 | 保护流量不被中间人看见 | Bump 与 mitmproxy 主动解密来看 |
| 证书体系 | 不涉及伪造证书 | 核心能力就是证书伪造与信任链 |
| 日志策略 | 刻意最小化，抗追溯 | 详尽日志，用于审计、计费与排障 |
| 协议适配 | 传输任意 TCP/UDP 字节流，不解析内容 | HTTP/1/2/3、gRPC、WebSocket 内容级处理 |
| 性能取向 | 单连接延迟、链路稳定性 | 并发连接、缓存命中、七层路由吞吐 |
| 缓存 / ACL / DLP | 不具备 | 核心能力 |
| 主要使用者 | 个人用户为主 | 企业、ISP、云服务与研发调试 |

### 4. 三个关键区别

**第一，它们不解析 HTTP。** Shadowsocks 本质是加密 SOCKS5 中继：客户端把 SOCKS5 请求交给本地端，本地端加密后发给服务端，服务端解密再转发。它传输的是字节流，不知道里面是 HTTP 还是 SSH，因此没有 ACL、没有缓存、没有内容改写。V2Ray 功能更多（多协议入站出站、路由规则、多路复用），但核心仍是加密隧道与流量塑形，不是内容级代理。

**第二，它们与中间人是反向关系。** 前面讲的 SSL-Bump、证书伪造、CA 信任链，目的是让代理看见明文；加密隧道的目的是让链路上任何人都看不见明文。所以这类工具天然不做 MITM——做了就违背设计初衷。反过来，企业出口审计最担心的正是员工用加密隧道绕过审计网关，因为网关看不到内容。

**第三，部署位置与配置者不同。** 网关类部署在网络的必经之路上（出口或入口），由网络管理员配置；隧道类由终端用户自己启用，用来绕过路径管控。这是 09-01「角色由入口决定、谁来配置决定谁有感知」的延伸：一个由管理员配、一个由用户配，天然对立。

### 5. 性能不可比

拿 Shadowsocks 与 HAProxy 比每秒请求数没有意义。前者衡量的是单用户跨境链路的延迟与稳定性，瓶颈在链路质量与加密开销；后者衡量的是单机每秒能转发多少请求，瓶颈在握手速率、策略链与缓存命中率。两者场景不同、指标不同、瓶颈不同，属于不可比集合。强行比较只会得出误导性结论。

### 6. 合规边界

加密隧道类工具本身是开源技术，但使用受法律与单位规章约束。在中国境内，**未经批准使用此类工具跨境联网属于违规行为**；这与 06-15 讲"中间人需要合规授权"是同一类问题——技术能力不等于可以随意使用。企业若确有跨境访问需求，应走合规审批的专线或企业级网关，而不是个人部署隧道工具。做技术辨析时把这条边界写清楚，是资料完整性的要求。

### 7. 在工具光谱中的位置

把前面聊过的四类工具排成一条光谱：**隧道隐藏（Shadowsocks/V2Ray）→ TLS 终止（HAProxy/Envoy）→ 明文调试（mitmproxy）→ 出口审计（Squid SSL-Bump）**。本册讨论的统一代理平台覆盖的是后三类，加密隧道类是它的"对立面"——正因为存在绕过审计的加密流量，统一平台才需要 QUIC/ECH 降级策略与加密流量识别能力（见 09-06）。理解这条光谱，就能回答"某工具属于哪一类、能否替代另一类"：同一象限内可比较，跨象限只谈边界不谈替代。

## 09-09 三类工具的分层边界：VPN、应用代理与网关代理

### 1. 背景与动机

09-08 把网关代理与加密隧道分成两个象限，但没有回答一个更细的问题：同属"抗观测"一侧的 WireGuard 与 V2Ray/Shadowsocks，是不是一类东西？答案是**不是**。WireGuard 是正规的网络层 VPN，V2Ray/Shadowsocks 是应用层代理；它们虽然都在加密，但接管流量的层次、拓扑模型、身份体系完全不同。把它们混为一谈，会导致配置方式、排障思路和合规判断全部出错。

> 术语说明：WireGuard 是 L3 网络层 VPN，在内核（或用户态实现）创建虚拟网卡；V2Ray 是支持多协议入站出站与路由规则的应用代理软件，Shadowsocks 是加密 SOCKS5 代理协议。具体实现版本、协议名与功能开关需对照各自官方文档核验，本节只讨论架构分层。

### 2. 分层判据：接管哪一层

图 09-09-01 把三类工具按"接管哪一层"和"谁来配置"拆开：WireGuard 在网络层接管整机流量，应用无感；V2Ray/Shadowsocks 在应用层按应用配置接管，只有指向端口的流量才走；网关代理部署在网络必经之路，由管理员配置。

### 3. 逐项对比

| 维度 | WireGuard | V2Ray / Xray | Shadowsocks |
|---|---|---|---|
| OSI 层次 | L3 网络层 | L5/L7 会话与应用层 | L5，SOCKS5 之上 |
| 拓扑模型 | Peer 对等体，可 mesh、站点互联 | 客户端—服务端代理链 | 客户端—服务端单跳 |
| 身份体系 | 公钥即身份，`AllowedIPs` 同时做路由与准入 | UUID / 用户 ID，支持多用户 | 共享密码，通常单凭证 |
| 加密机制 | 固定套件 Noise_IK + Curve25519 + ChaCha20-Poly1305 + BLAKE2s | VMess / VLESS / Trojan 等 | AEAD（ChaCha20 / AES-GCM） |
| 代码规模 | 约 4000 行，可单人审计 | 大型 Go 程序，功能多 | 小而精简 |
| 流量特征 | 握手包结构固定，DPI 易识别 | 可套 WebSocket + TLS 伪装 | AEAD 随机噪声，抗指纹 |
| 多用户 | 靠多个 peer 公钥 | 原生多用户与路由规则 | 通常单凭证 |
| 性能位置 | 内核态，高吞吐、低延迟 | 用户态，功能换开销 | 用户态，开销小 |
| 主要用途 | 企业远程接入、站点互联、内网穿透 | 抗封锁、流量分流 | 轻量抗封锁 |

### 4. 三个关键差异

**第一，拓扑能力不同。** WireGuard 的 peer 模型天然支持 mesh 与 site-to-site：把两个机房的网段互相写进 `AllowedIPs` 就通了，这是它作为 VPN 的主场。V2Ray/Shadowsocks 是"客户端找服务端拿出口"的代理链，不做站点互联，但胜在能按域名、GeoIP、进程做分流——这是 WireGuard 按 IP 段的 `AllowedIPs` 做不到的。

**第二，密码学哲学相反。** WireGuard 固化一套最强算法、拒绝协商、握手包规整可识别，追求"可审计的安全"；V2Ray/Shadowsocks 追求"看起来像随机噪声或普通 HTTPS"，追求"不被 DPI 认出来"。前者是工程简洁性，后者是抗审查性，目标不同，不能互相打分。

**第三，密钥路由是 WireGuard 独有机制。** `AllowedIPs` 一个参数承担两件事：出站时按目标 IP 选 peer 加密，入站时校验源 IP 是否属于该 peer，不属于就静默丢弃。这叫 Cryptokey Routing，把"路由表"与"防火墙"合成一张表。代理没有这套机制，靠 SOCKS5 握手与上层认证完成准入。

### 5. 与工具光谱的连接

这正是 09-08 光谱的细化：WireGuard 属于加密隧道的**正统 VPN 分支**（整机接管、可审计、企业可用），V2Ray/Shadowsocks 属于同一分支里的**抗观测变体**（单应用接管、可伪装）。它们与 Squid/Envoy 那类网关代理的对立关系不变——都是让中间人看不见明文，只是 WireGuard 用"规整但加密"，V2Ray/Shadowsocks 用"伪装成普通流量"。理解这条细分，才能判断某工具是"企业远程接入的合规选项"还是"绕过管控的终端工具"。

### 6. 配置与排障的实务差异

WireGuard 的排障对象是路由与握手：`AllowedIPs` 写错会导致流量不进隧道或入站被静默丢弃，`Endpoint`、`PersistentKeepalive` 与 MTU 决定 NAT 后的连通性，排查靠 `wg show` 看握手时间与流量计数。V2Ray/Shadowsocks 的排障对象是本地端口与规则：应用是否真的指向了 SOCKS5 端口、分流规则是否命中、本地端是否监听成功，排查靠本地连接与代理日志。网关代理的排障则回到 08-03 的链路：现象 → 日志 → 配置 → 内核决策链。三者的故障域不同，拿一套排障模板套三类工具必然走偏。

### 7. 合规边界与小结

合规口径与 09-08 一致：WireGuard 在企业跨机房互联、远程办公中是正规用途；V2Ray/Shadowsocks 在境内未经批准用于跨境访问属违规。技术辨析不等于可以随意使用。把本节与 09-08 合起来看，工具边界的完整判据是三问：**接管哪一层、谁来配置、对明文持什么态度**。三问的回答确定后，工具归属、能力边界与合规判断就都清楚了。
