# Squid 技术资料 · 03 部署

## 03-01 单机部署：目录初始化与最小可用配置

### 1. 目标与拓扑

一台 Linux 主机，安装好 Squid（源码编译或系统包均可），完成缓存目录初始化，启动一个只监听本地网段的正向代理并验证可用。这是后续所有部署形态的基础。

拓扑：客户端（同网段）→ Squid（3128）→ 互联网源站。

### 2. 前置条件与环境

- 已安装 Squid（见 `02`），`squid -v` 正常输出。
- 有一个专门存放缓存的分区或目录，磁盘空间按业务预估。
- 防火墙放行 3128（若跨主机访问）。

### 3. 分步操作

步骤一：准备最小配置。

```text
# 配置片段 · squid.conf（单机最小配置）
http_port 3128
acl localnet src 192.168.1.0/24
http_access allow localnet
http_access deny all
cache_dir ufs /var/spool/squid 10000 16 256
access_log /var/log/squid/access.log
cache_log /var/log/squid/cache.log
```

步骤二：校验语法并初始化目录。

```bash
squid -k parse
squid -z
```

步骤三：启动并观察。

```bash
sudo squid                       # 守护方式启动
tail -f /var/log/squid/cache.log # 观察启动日志
```

:::figure id=03-01-01 | name=单机部署步骤链 | dir=LR

node n2 "k parse<br/>校验语法" teal

edge n3 -> n4

:::

图中节点速览：顺序不可颠倒，语法校验与目录初始化都在启动之前。

### 4. 验证方法与预期结果

```bash
curl -x http://127.0.0.1:3128 -I http://example.com
tail -n 5 /var/log/squid/access.log
```

预期：curl 返回源站响应头；access.log 出现一条记录，结果码首次多为 TCP_MISS，重复请求出现 TCP_HIT。

### 5. 常见失败与排错

- 启动报「cache_dir 目录不存在」：漏做 `squid -z` 或权限不足，检查属主与权限。
- 客户端连接被拒：`http_access` 顺序错误或网段不匹配，检查 localnet 定义。
- 以 root 启动被拒：用系统服务方式（自动降权）或配置能力。

### 6. 小结

单机部署的关键是「校验—初始化—启动—验证」四步。后续形态都在这套流程上叠加配置。

## 03-02 正向代理部署

### 1. 目标与拓扑

把 Squid 部署为企业出口缓存，内网客户端显式配置代理，Squid 代表客户端访问互联网并缓存结果。拓扑：内网客户端 → Squid 出口（双网卡）→ 防火墙 → 互联网。

### 2. 前置条件

- Squid 主机有内网与外网连通性。
- 明确允许访问的网段与时间策略。
- 按 `03-01` 完成基础部署。

### 3. 分步操作

配置片段 · squid.conf（出口缓存要点）：

```text
http_port 3128
acl localnet src 10.0.0.0/8
acl workhours time MTWHF 09:00-18:00
http_access allow localnet workhours
http_access deny localnet
http_access deny all
cache_dir ufs /var/spool/squid 20000 16 256
cache_mem 512 MB
maximum_object_size 64 MB
```

客户端配置：浏览器或系统代理设为 Squid 的内网地址与 3128 端口。

:::figure id=03-02-01 | name=正向代理出口缓存拓扑 | dir=LR

node n2 "Squid 出口<br/>缓存+ACL" teal
node n3 "防火墙" amber
node n4 "互联网源站" gray
edge n1 -> n2
edge n2 -> n3
edge n3 -> n4
:::

图中节点速览：客户端显式指向 Squid，Squid 承担缓存与访问控制双重职责。

### 4. 验证方法

- 客户端访问同一外网页面两次，access.log 第二次应出现 TCP_HIT 或 TCP_REFRESH_HIT。
- 用被拒绝的网段或时间访问，应返回访问拒绝页面。
- `squidclient mgr:info` 查看命中率与内存使用（命令见 `04-05`）。

### 5. 常见失败与排错

- 命中率为零：检查 URL 是否可缓存（动态页面、含个人标识的响应通常不缓存），详见 `06-02`。
- 部分网站打不开：可能是 TLS 或高版本协议特性问题，用 `curl -v` 对比直连与走代理。
- 代理被外网滥用：`http_access deny all` 必须存在且 localnet 要精确。

### 6. 小结

正向代理部署的重点是访问控制精确与缓存策略合理。指令细节见 `04-03`、`04-04`。

## 03-03 反向代理加速部署

### 1. 目标与拓扑

把 Squid 放在自有 Web 服务器前面，客户端访问 Squid，Squid 回源取内容并缓存，加速响应并隐藏后端。拓扑：互联网客户端 → Squid（accel）→ 后端 Web 集群。

### 2. 前置条件

- 后端 Web 服务地址与端口确定。
- 对外域名解析指向 Squid。
- 需要 https_port 时按 `02-01` 确认 TLS 依赖已编译进来。

### 3. 分步操作

配置片段 · squid.conf（反向代理）：

```text
http_port 80 accel defaultsite=www.example.com
cache_peer 10.0.0.10 parent 80 0 no-query originserver name=web1
cache_peer 10.0.0.11 parent 80 0 no-query originserver name=web2
acl site dstdomain www.example.com
http_access allow site
http_access deny all
cache_peer_access web1 allow site
cache_peer_access web2 allow site
```

要点：`no-query originserver` 表明后端是源站而非邻居缓存，不向其发 ICP 查询；多个 cache_peer 配合缓存规则实现负载分担。

:::figure id=03-03-01 | name=反向代理加速拓扑 | dir=TD
node n1 "互联网客户端" blue
node n2 "Squid accel<br/>缓存与回源" teal
node n3 "后端 Web1" amber
node n4 "后端 Web2" amber
edge n1 -> n2
edge n2 -> n3
edge n2 -> n4
:::

图中节点速览：Squid 承接所有客户端请求，按 access 规则回源到两个后端之一。

### 4. 验证方法

```bash
curl -I -H 'Host: www.example.com' http://<Squid地址>/
tail -f /var/log/squid/access.log
grep -i "error" /var/log/squid/cache.log
```

预期：返回后端页面；日志中结果码指示回源（TCP_MISS/FIRSTUP_PARENT）与命中（TCP_HIT）交替。

### 5. 常见失败与排错

- 返回 403/404：Host 未正确匹配 acl site，或 cache_peer_access 未放行。
- 全部回源无命中：响应缺少可缓存头（Cache-Control/Expires），详见 `06-02`。
- 后端取到错误站点：Host 头未转发或被改写。

### 6. 小结

反向代理的核心是「目标由后端确定 + 正确转发 Host」。层级与缓存协议详见 `03-05`、`06-05`。

## 03-04 透明代理部署

### 1. 目标与拓扑

客户端无需任何代理设置，网关把上网流量透明重定向到 Squid，由 Squid 缓存与审计。拓扑：内网客户端 → 网关（重定向）→ Squid → 互联网。

### 2. 前置条件

- Squid 编译时启用了 Linux netfilter 支持（`--enable-linux-netfilter`，见 `02-03`）。
- 网关与 Squid 可同机或分离，需能接收被重定向的流量。
- 明确透明代理不涉及 HTTPS 内容解密的边界（见 `07-02`）。

### 3. 分步操作

配置片段 · squid.conf（透明代理要点）：

```text
http_port 3129 intercept
acl localnet src 10.0.0.0/8
http_access allow localnet
http_access deny all
```

命令示例 · Shell（iptables 重定向，具体规则依环境核验）：

```bash
iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 80 \
  -s 10.0.0.0/8 ! -d 10.0.0.0/8 \
  -j REDIRECT --to-port 3129
```

要点：`intercept` 参数告诉 Squid 该端口接收的是被重定向的透明流量，需从原始目的地址推断目标；`tpproxy` 等参数用于代理协议衔接，按实际拓扑选用。

:::figure id=03-04-01 | name=透明代理流量重定向 | dir=LR
node n1 "客户端<br/>无感知" blue
node n2 "网关<br/>nat REDIRECT" teal
node n3 "Squid<br/>intercept 端口" purple
node n4 "互联网源站" amber
edge n1 -> n2
edge n2 -> n3
edge n3 -> n4
:::

图中节点速览：网关把 80 端口流量重定向到 Squid 的 intercept 端口，客户端全程无感。

### 4. 验证方法

- 客户端不配代理直接访问网页，access.log 应出现记录。
- 日志中目的地址应为真实源站而非 Squid 本身，说明拦截参数生效。
- 重复访问验证缓存命中。

### 5. 常见失败与排错

- 请求循环或打不开：重定向规则未排除 Squid 自身或缓存主机，形成回环。
- 日志目的地址错误：http_port 未用 intercept 参数，Squid 不知如何取原始目标。
- HTTPS 流量无法缓存：未启用 SSL-Bump 时加密内容不可见，属预期行为。

### 6. 小结

透明代理部署的重点是重定向规则与 intercept 参数配合。iptables/nftables 规则语法随内核与发行版变化，需对照实际环境核验。

## 03-05 缓存层级部署

### 1. 目标与拓扑

部署多级缓存：子级 Squid 未命中时向父级或同级查询，减少重复回源与出口带宽。拓扑：客户端 → 子级 Squid → 父级 Squid → 互联网；同级之间可互为补充。

### 2. 前置条件

- 至少两台 Squid，网络互通。
- 明确父子关系与是否使用 ICP/HTCP 查询协议。
- 了解缓存摘要（cache digest）作为 ICP 的轻量替代。协议原理见 `06-05`。

### 3. 分步操作

配置片段 · squid.conf（子级）：

```text
cache_peer parent.example.com parent 3128 3130 default no-query
acl localnet src 10.0.0.0/8
http_access allow localnet
http_access deny all
```

要点：`parent` 指定为父级；端口 3128 是代理端口，3130 是 ICP 端口；`no-query` 表示不发 ICP 查询，直接转发（简化部署）；若要用 ICP 则去掉 no-query 并配置ICP相关指令。

:::figure id=03-05-01 | name=父子缓存层级 | dir=TD
node n1 "客户端" blue
node n2 "子级 Squid" teal
node n3 "父级 Squid" purple
node n4 "同级 Squid" gray
node n5 "互联网源站" amber
edge n1 -> n2
edge n2 -> n3
edge n2 -> n4 dashed "ICP 查询"
edge n3 -> n5
:::

图中节点速览：子级未命中向父级取，同级之间用 ICP 互通缓存摘要以减少回源。

### 4. 验证方法

- 在子级制造一次未命中，父级日志应出现对应请求。
- `squidclient mgr:cache_peer` 查看邻居状态（命令见 `04-05`）。
- 观察命中率是否因层级而提升。

### 5. 常见失败与排错

- 邻居状态不可达：ICP 端口未放行或主机不可达。
- 全部绕开父级：cache_peer 未设为 default 或缺少转发规则。
- 命中率不升反降：层级配置导致严格层级约束过强，详见 `06-05`。

### 6. 小结

缓存层级用协议与摘要协同减少回源。协议细节见 `06-05`，相关指令见 `04`。

## 03-06 高可用与 SMP 多实例

### 1. 目标与拓扑

用两个层面提升可用性：SMP 多 worker 利用多核；多实例加负载均衡消除单点。拓扑：负载均衡器 → 多个 Squid 实例 → 互联网。

### 2. 前置条件

- CPU 多核，编译版本支持 SMP（多数现代版本）。
- 明确 workers 数量与缓存共享方式。
- 前端负载均衡器（HAProxy/LVS 等）。

### 3. 分步操作

配置片段 · squid.conf（SMP 要点）：

```text
workers 4
cache_dir ufs /var/spool/squid 20000 16 256
```

要点：workers 指定工作进程数。官方明确：修改 workers 需要重启 Squid 而非 reload，因为涉及共享内存与进程的重新布局。这一点在升级与变更时要特别注意。

:::figure id=03-06-01 | name=高可用双实例架构 | dir=TD
node lb "负载均衡器" blue
node s1 "Squid 实例 A<br/>多 worker" teal
node s2 "Squid 实例 B<br/>多 worker" teal
node net "互联网源站" amber
edge lb -> s1
edge lb -> s2
edge s1 -> net
edge s2 -> net
:::

图中节点速览：前端负载均衡把请求分发到两个独立 Squid 实例，每个实例内部再由多 worker 并行。

### 4. 验证方法

- 查看进程数是否等于 workers 设定加协调进程。
- 停掉一个实例，负载均衡应把流量切到另一个，业务不中断。
- 检查各实例缓存命中率是否均衡。

### 5. 常见失败与排错

- 改 workers 后 reload 不生效：必须重启，属预期行为。
- 多实例缓存不共享：实例各自维护缓存，命中率下降属正常，可用一致性哈希分担。
- 内存翻倍：每 worker 独立内存开销，规划容量时要计入。

### 6. 小结

高可用靠多实例，多核利用靠 SMP。两者叠加时要注意重启约束与内存规划。部署篇结束，下一步 `04` 系统梳理配置与命令。
