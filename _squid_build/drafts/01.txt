# Squid 技术资料 · 01 基础与概述

## 01-01 Squid 是什么：缓存转发代理概览

### 1. 背景与动机

互联网早期，带宽昂贵且时延高。1990 年代科罗拉多大学的 Harvest 项目试图解决一个问题：同一批用户反复访问同样的网页，能否把第一次取回的副本留在本地，后续请求直接命中本地副本？Harvest 的缓存组件后来被 Duane Wessels 分叉出来，为避免与商业分支 NetCache 混淆，改名为 Squid，1996 年发布 1.0。

三十年后，Squid 已经从一个网页缓存成长为成熟的**缓存转发代理**：它站在客户端与服务器之间，替客户端转发请求，同时把可缓存的响应留在本地。理解 Squid，先要抓住两个词——**转发**与**缓存**。转发指它接受客户端请求、代替客户端向源站发起请求并把结果回送；缓存指它把结果按规则保存，供后续相同请求复用。这两个能力组合，衍生出加速、节省带宽、访问控制、内容过滤、匿名化等一系列用途。

### 2. 核心概念

从功能视角看，Squid 同时扮演三种角色：

- **正向代理**：客户端明确知道并配置代理，Squid 代表客户端访问任意源站。企业出口缓存、上网行为管理是典型场景。
- **反向代理**：源站明确，Squid 站在源站前面承接大量客户端请求，加速并保护后端。此时它也叫 Web 加速器。
- **透明代理**：客户端无感知，网络层把请求重定向到 Squid。关键在于是否改写请求、源站能否感知代理存在。

从数据视角看，Squid 处理的对象叫**缓存条目**（StoreEntry）。每个条目有唯一的键（通常是请求的 URL 归一化结果）、一组元数据和一段主体数据。条目的生命周期覆盖「接收请求 → 判定能否缓存 → 向源站取回 → 写入存储 → 命中复用 → 失效淘汰」全过程。

从版本视角看，Squid 主线已推进到 7.x。历史上 2.x、3.x、4.x、5.x 都有大规模部署，指令名称和默认行为差异明显。阅读任何资料都应先确认版本，本套以 7.x 为基准，涉及旧版本差异处会专门标注。

### 3. 关键结构与源码位置

Squid 主体用 C++ 编写，源码在 GitHub 的 squid-cache/squid 仓库。入门阶段只需认识几个关键位置：

| 位置 | 作用 | 何时用到 |
|---|---|---|
| src/main.cc | 程序入口，初始化与事件主循环启动 | 想理解启动过程 |
| src/cf.data.pre | 所有配置指令的定义源文件 | 查指令的确切语法与默认值 |
| src/squid.conf.documented | 由 cf.data.pre 生成的完整配置说明 | 查某指令的全部选项 |
| src/HttpRequest.h / request_t | 请求对象与请求行、头部表示 | 理解请求如何被解析 |
| src/store/ | 缓存存储子系统 | 理解条目如何存取 |
| src/acl/ | 访问控制链表实现 | 理解规则如何匹配 |
| src/fs/ | 存储后端（UFS、rock 等） | 理解落盘方式 |
| src/ssl/ | SSL-Bump 相关实现 | 理解 HTTPS 处理 |
| helpers/ | 各类外部辅助程序 | 认证、重写、内容适配 |

需要说明的是，具体文件名与类层次在不同版本间调整频繁，上表用于建立路径直觉，精确位置请以 `需对照实际版本核验` 为准，方法是在源码根目录用文本搜索定位符号。

### 4. 关键流程与调用链

一次最典型的缓存命中请求，调用链大意如下：客户端连接被接受后，通信层把字节流解析成 HttpRequest 对象；访问控制链检查该请求是否被允许；随后缓存层用请求生成的键查询 StoreEntry；若命中且条目仍然新鲜，直接从存储读出主体并回送客户端；若不命中或已陈旧，则创建转发状态（FwdState），选中目标源站，发起上游请求，取回响应后经缓存规则判定是否写入存储，最后回送客户端。

这条链路串起了后面所有册的内容：请求解析属于基础，访问控制属于模块，缓存判定与存储属于原理，落盘属于存储引擎，日志属于运维判读。

### 5. 配置与命令示例

最小可用的正向代理配置只需要监听端口与访问控制两件事：

```text
# 配置片段 · squid.conf（最小正向代理）
http_port 3128
acl localnet src 10.0.0.0/8
http_access allow localnet
http_access deny all
cache_dir ufs /var/spool/squid 10000 16 256
```

配置示例 · Shell：启动前先校验语法、初始化缓存目录，再前台观察日志。

```bash
squid -k parse          # 校验配置文件语法
squid -z                # 初始化 cache_dir 目录结构
squid -NCd1             # 不守护、不缓存、调试级别 1 前台运行
```

判读要点：`squid -k parse` 会逐行指出指令错误，升级后必须执行；`-z` 只在首次或新增缓存目录时运行；`-NCd1` 的 d1 是调试级别，数值越大日志越细，排障时逐步调高。

### 6. 陷阱与最佳实践

- **把 Squid 当成匿名工具**：普通正向代理并不匿名，请求头里仍可能携带客户端信息。是否隐匿由配置决定，不要默认它保护隐私。
- **版本混用配置**：把 3.x 的指令直接搬到 7.x，轻则被忽略，重则启动失败。升级路径必须配合 `squid -k parse`。
- **缓存目录未初始化**：新建 cache_dir 后忘记 `-z`，目录结构缺失会导致启动报错或缓存不可用。

### 7. 小结与延伸阅读

Squid 的本质是「带缓存的转发代理」。抓住转发与缓存两条主线，三种代理形态、后续所有模块与机制都能挂上去。建议接着读 01-02 三种代理形态的拓扑差异，再读 01-04 整体架构。

## 01-02 正向、反向与透明代理三种形态

### 1. 背景与动机

同样是 Squid，部署位置不同，行为差异巨大。选错形态会导致两种典型事故：本想加速网站却配成开放代理，成为被滥用的跳板；本想无感拦截却配成显式代理，客户端根本没走代理。因此必须先明确形态，再写配置。

### 2. 核心概念

**正向代理（forward proxy）**面向客户端。客户端在浏览器或系统中设置代理地址，所有请求发往 Squid，由 Squid 代替访问互联网。它解决的是「客户端如何上网」的问题， Cache 命中节省出口带宽。

**反向代理（reverse proxy / accelerator）**面向源站。客户端以为自己访问的是真实站点，实际请求先到 Squid，Squid 再回源。它解决的是「源站如何扛住流量」的问题，同时隐藏后端拓扑。

**透明代理（transparent / intercept proxy）**面向网络。客户端不知道代理存在，网关用重定向规则把 80/443 流量引到 Squid。它解决的是「无需配置客户端即可强制经过代理」的问题，常见于企业网关与校园网。

### 3. 三种形态对照

| 维度 | 正向代理 | 反向代理 | 透明代理 |
|---|---|---|---|
| 谁感知代理 | 客户端明确配置 | 客户端以为直连源站 | 客户端完全无感 |
| 配置入口 | 浏览器/系统代理设置 | DNS 或负载均衡指向 | 网关重定向规则 |
| 主要目标 | 出口缓存、访问控制 | 加速与保护后端 | 强制审计与缓存 |
| 典型端口 | 3128 | 80/443 | 80/443 拦截 |
| 关键指令族 | http_port、http_access | http_port accel、cache_peer | 拦截端口参数 |
| 主要风险 | 开放代理被滥用 | 回源配置错误 | HTTPS 无法直接拦截 |

### 4. 关键流程与调用链

反向代理与正向代理在 Squid 内部走的是同一套缓存与转发引擎，差别集中在**请求的目标如何确定**。正向代理的请求行通常是完整 URL，Squid 直接解析出目标主机；反向代理的请求行往往只是路径，目标由 `cache_peer` 或 `http_port` 的 accel 参数决定；透明代理则请求行是路径且目标来自网络层原始目的地址，需要拦截参数告诉 Squid 从何处取真实目标。

因此，排障时判断形态的最快方法是看访问日志里的请求 URL 形态与目的地址来源：完整 URL 多半是正向，纯路径加后端地址多半是反向或透明。字段含义详见 `05-05`，转发决策详见 `06-04`。

### 5. 配置与命令示例

反向代理的最小骨架：

```text
# 配置片段 · squid.conf（反向代理加速）
http_port 80 accel defaultsite=www.example.com
cache_peer 10.0.0.10 parent 80 0 no-query originserver name=backend1
acl site dstdomain www.example.com
http_access allow site
cache_peer_access backend1 allow site
```

命令示例 · Shell：验证路由与回源是否通。

```bash
curl -I -x http://127.0.0.1:3128 http://example.com   # 测正向代理
curl -I -H 'Host: www.example.com' http://127.0.0.1/   # 测反向代理
tail -f /var/log/squid/access.log                      # 观察请求是否命中
```

判读要点：第一条用 `-x` 指定代理测正向；第二条靠 Host 头让反向代理匹配站点；第三条若出现 TCP_MISS 后接 TCP_HIT，说明缓存生效。

### 6. 陷阱与最佳实践

- **反向代理忘记配置 Host 转发**：后端依赖 Host 选站点时，未转发正确 Host 会返回错误站点。
- **透明代理的 HTTPS 盲区**：不启用 SSL-Bump 的透明代理无法解析加密请求内容，只能按连接转发。是否解密涉及合规边界，详见 `07-02`。
- **正向代理变开放代理**：`http_access` 若写成 allow all 且监听对外网卡，会被当成公开跳板。务必先 allow 内网段再 deny all。

### 7. 小结与延伸阅读

三种形态共享内核、区别在入口与目标确定方式。确定形态后再进入 `03` 部署章节照步骤落地，配置细节统一查 `04`。

## 01-03 与其他代理及缓存软件的架构对比

### 1. 背景与动机

选型时最常被问的是「为什么不用 Nginx」「Varnish 是不是更快」。这些软件都能放在客户端与服务器之间，但设计目标不同：有的主打缓存命中率与细粒度缓存策略，有的主打反向代理与负载均衡，有的主打纯内存极速缓存。理解差异，才能把 Squid 用在它最擅长的地方。

### 2. 核心概念与对比

- **Squid**：成熟的缓存转发代理，正向/反向/透明通吃，缓存策略与访问控制极其丰富，支持磁盘持久化缓存与缓存层级。适合出口缓存、需要复杂访问控制和审计的场景。
- **Nginx**：高性能反向代理与 Web 服务器，缓存是其功能之一，强在负载均衡、静态服务与生态。适合反向代理与网关。
- **Varnish**：纯内存 HTTP 加速器，缓存命中极快，配置语言灵活，但重启丢缓存，主要做反向缓存。适合高吞吐反向缓存。
- **HAProxy**：专注四层/七层负载均衡与高可用，缓存能力弱。适合流量调度。
- **Apache Traffic Server（ATS）**：与 Squid 类似的缓存代理，扩展性设计强，生态较小。

| 维度 | Squid | Nginx | Varnish | HAProxy |
|---|---|---|---|---|
| 正向代理 | 强项 | 有限 | 不支持 | 有限 |
| 反向代理 | 支持 | 强项 | 强项 | 强项 |
| 磁盘缓存 | 支持多后端 | 支持 | 主要内存 | 弱 |
| 缓存层级 | ICP/HTCP/CARP | 弱 | 有限 | 无 |
| 访问控制 | 极丰富 | 中等 | 中等 | 中等 |
| 典型定位 | 出口缓存/网关 | 通用网关 | 反向加速 | 负载均衡 |

### 3. 选型判断

一句话判断：**要缓存策略与正向代理，选 Squid；要通用反向网关，选 Nginx；要极致反向缓存命中，选 Varnish；要流量调度，选 HAProxy。** 它们并非互斥，生产架构里常见 Squid 做出口缓存、Nginx 做反向网关、HAProxy 做四层调度的组合。

### 4. 小结

了解对比是为了不误用。Squid 的护城河是「缓存 + 访问控制 + 缓存层级」的组合，这三点在 `04`、`06`、`07` 详细展开。

## 01-04 整体架构：事件驱动、SMP 与协议栈分层

### 1. 背景与动机

Squid 能在单机上处理数万并发连接，靠的不是多线程抢占，而是单进程事件驱动加异步 I/O，再叠加 SMP 多进程协作。理解这套架构，是理解后面「为什么配置 workers 要重启」「为什么磁盘 I/O 有专用线程」的前提。

### 2. 核心概念

**事件驱动主循环**：Squid 用一个主循环监听大量文件描述符，哪个描述符就绪就处理哪个，避免为每个连接创建线程。网络读写、磁盘 I/O、定时器都抽象成事件，统一调度。详见 `06-01`。

**异步 I/O**：磁盘操作不能阻塞主循环，因此 Squid 提供多种存储后端，把落盘交给独立机制（线程、辅助进程或内核异步接口）。详见 `06-03`。

**SMP 多进程**：现代 Squid 支持多个 worker 进程并行处理，通过进程间协调共享缓存索引与状态。启用 workers 需要重启而非热加载，这是官方明确说明的约束。详见 `03-06`。

**协议栈分层**：从下到上大致是——通信层（连接与描述符）→ 协议解析层（HTTP/FTP/HTTPS）→ 请求处理层（访问控制、缓存查找、转发决策）→ 存储层（内存与磁盘）→ 辅助层（认证、重写、日志）。

### 3. 版本差异提示

3.x 之前以单进程为主，SMP 支持是后续版本逐步引入并完善的。查阅老资料时若只谈单进程模型，多半针对旧版本。本套以 7.x 的多进程能力为基准。

### 4. 小结

事件驱动解决并发，异步 I/O 解决磁盘阻塞，SMP 解决多核利用，分层让各模块职责清晰。后续 05、06、07 三册分别对应这里的「结构、机制、模块」，形成完整闭环。基础篇到此结束，下一步进入 `02` 编译与构建。
