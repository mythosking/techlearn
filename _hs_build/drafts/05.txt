# Hyperscan 技术资料 · 05 关键数据结构字段详解（分片 A）

## 05-01 全册结构分层与跨文档索引

### 1. 本篇定位与覆盖范围

Hyperscan 的技术资料里最容易出现两种失真：一种是把 API 参数与结构体字段混为一谈，另一种是把「运行时对象」和「编译期临时对象」混为一谈。05 册存在的意义就是把第二种失真按住。本册是全套九册中唯一的结构体字段权威源，只回答四个问题：这个字段叫什么、是什么类型、在什么时机被写、被哪些函数读。编译流水线怎么走、Rose 怎么分解、引擎怎么按规模选型，一律不在本册展开，只给入口函数名与源码路径。

本分片覆盖 05-01 至 05-05：分层与索引、`hs_database`、`hs_scratch`、四个编译侧结构体、`RoseEngine` 与 `RoseContext`。后续分片覆盖 05-06 至 05-09：LimEx NFA 与 Castle、FDR/Teddy/HWLM、NG 图结构、流状态与 SOM 槽位及 Chimera 结构。两片之间用统一的七列表格与统一的图号规则衔接，篇号连续、不重号，图 id 全局唯一。

读法上有一个硬约定：本册不按「编译 → 扫描」的时间顺序组织，而按「对象所有权」组织。原因是 Hyperscan 的运行时对象只有三个——数据库、scratch、流，其余全部是数据库字节码内部的子结构。所有权关系决定了三件工程上最要命的事：谁负责释放、能不能跨线程、扩容时会不会把指针搬走。把这三件事搞清楚，后面读 06 册的机制才有落脚点，否则会出现「看得懂每一步，但不知道状态存在哪」的情况。

字段表统一使用七列：`字段 | 类型 | 含义 | 源码位置 | 读写时机 | 关联函数与流程 | 版本差异`。凡是本轮快照中无法百分百确认的字段名、类型或语义，一律写「需对照实际版本核验」并给出可定位的源码路径，不做猜测性描述。版本基线为 5.4.2，源码快照位于 `_hs_build/upstream_src/`，目录结构与上游仓库一致；所有行号均指该快照。

还有一条边界要提前说清：本册讲「字段怎么用」，不讲「字段为什么这么设计」。例如 `RoseEngine::noFloatingRoots` 的语义是「若锚定表无命中则跳过浮动表」，这属于字段含义，本册要写；而它如何与历史缓冲区的补匹配配合，属于机制，见 06-11。这样切分之后，05 册可以当工具书随查，06 册可以当教材顺序读，两边不重复。

从实际查阅频率看，索引有三种典型用法。第一种是「按症状查字段」：例如扫描返回 `HS_SCRATCH_IN_USE`，直接翻 05-03 的 `in_use` 行，看读写时机与关联函数。第二种是「按内存量查字段」：例如要估算单流内存，先看 05-05 的 `stateOffsets.end` 与 `historyRequired`，再看 05-09 的流头。第三种是「按 API 查结构」：例如手里有 `hs_expression_info` 的返回值，翻 05-04 看五个字段哪些是保守值。

### 3. 逐项详解

#### 3.1 L0：公共句柄与分配器家族

`hs_database_t` 在 `src/hs_common.h` 第 64 行只有一行前置声明 `typedef struct hs_database hs_database_t;`，这意味着公共头文件里拿不到任何字段。这个设计不是疏漏，而是 ABI 保护：数据库布局属于实现细节，任何字段调整都不应该影响调用方的编译单元。同理 `hs_error_t` 只是 `int` 的别名（第 69 行），错误码取值全部定义在 `HS_ERROR` 分组里，具体语义属于 04-08 的范围。

分配器有五个入口：`hs_set_allocator`、`hs_set_database_allocator`、`hs_set_misc_allocator`、`hs_set_scratch_allocator`、`hs_set_stream_allocator`，对应的函数指针类型是 `hs_alloc_t`（`void *(HS_CDECL *)(size_t)`）与 `hs_free_t`（`void (HS_CDECL *)(void *)`）。从字段视角看，这个家族决定了两件事：数据库内存是否来自页对齐映射（`hs_db_alloc` 内部按页分配，并在 HMAC 计算完成后调用 `hs_db_protect` 改成只读），以及 scratch 的对齐下限。`src/scratch.h` 的结构体注释写得很直白：scratch 不要求 16 字节对齐，因为它由等价于 malloc 的分配器给出，甚至可能来自用户自定义分配器。这条注释直接解释了为什么 scratch 里有一个 `scratch_alloc` 字段——结构体本身会被向上取整到 64 字节边界，释放时必须回到原始指针。

`HS_CDECL` 也不是装饰。它决定回调与分配器函数在 32 位 Windows 上的调用约定，一旦调用方用错约定，表现为栈失衡导致的随机崩溃，而不是编译错误。字段层面能看到的痕迹只有 `core_info::userCallback` 的函数指针类型，它同样带 `HS_CDECL`。

#### 3.2 L1：数据库

数据库是不可变对象。编译完成、HMAC 计算完成之后，整块内存被置为只读，后续所有扫描只做读取。这一点从字段设计就能看出来：`hs_database` 里没有任何「当前状态」字段，没有游标、没有计数、没有缓存指针，只有魔数、版本、长度、平台、字节码偏移和两段 HMAC。真正的引擎参数全部下沉到 `bytes[]` 里的 `RoseEngine`，用相对偏移访问。

不可变带来两个工程后果。第一，一个数据库可以被任意多个线程同时扫描，不需要加锁，这也是 Hyperscan 能在多核场景线性扩展的前提。第二，数据库可以序列化后跨进程、跨机器分发，接收端只需要版本与平台匹配。第二点的代价是「版本绑定」：`version` 不匹配返回 `HS_DB_VERSION_ERROR`，`platform` 不匹配返回 `HS_DB_PLATFORM_ERROR`，两者的判定点分别在 `validDatabase` 与 `db_check_platform` 里。

需要提醒的是，「不可变」是库自身遵守的约定，不是内存保护的全部。`hs_db_protect` 在支持 mprotect 的平台上确实把页改成只读，但用户如果用 `hs_deserialize_database_at` 把数据库放进自己管理的可写缓冲区，只读保护是否生效取决于实现与页对齐情况。字段本身没有任何「已保护」标志，所以不要指望从结构体里判断这件事。

#### 3.3 L2：scratch

scratch 是唯一「每次扫描都可写」的顶层对象。它的字段可以粗分为四组：容量与尺寸（`scratchSize`、`bStateSize`、`tStateSize`、`fullStateSize`、`queueCount` 等）、指针区（`bstate`、`tstate`、`fullState`、`queues`、`aqa`）、扫描上下文（`core_info`、`tctxt`）、以及各类引擎的私有暂存（`al_log`、`delay_slots`、`deduper`、SOM 数组、`fdr_conf`）。

关键事实只有一个：scratch 不是线程安全的。`src/scratch.h` 用 `u8 in_use` 加一对 `markScratchInUse` / `unmarkScratchInUse` 做「同一时刻只允许一个 API 调用进入」的保护，但这是协作式而非原子式的检查：两个线程同时读到 `in_use == 0` 都可能通过。因此正确用法是一线程一份，或者在池化时保证同一份 scratch 不被并发借出。误用时的表现是 `HS_SCRATCH_IN_USE`，更糟的是静默的数据竞争。

另一个容易忽略的点是容量语义：scratch 的容量是「它所服务过的所有数据库的并集」，而不是某一个数据库的需求。`hs_alloc_scratch` 每次调用都拿当前数据库的 `RoseEngine` 与已有原型逐字段取较大值，只有出现更大需求时才重新分配。因此多库场景必须对每个库都调用一次，直到全部返回 `HS_SUCCESS`。

#### 3.4 L3：流状态

流状态 `hs_stream` 同样是公共头文件里的不透明类型，但它和数据库的差别在于「可变且按流私有」。它由 `hs_open_stream` 分配，内部前半部是流头，后半部是 `RoseEngine::stateOffsets` 描述的玫瑰状态区。scratch 与它的关系体现在 `bStateSize` 上：块模式下这个值等于 `stateOffsets.end`，向量化模式下等于 `sizeof(struct hs_stream) + stateOffsets.end`（见 `src/scratch.c` 的赋值分支），因为向量化扫描需要一块能容纳完整流状态的临时区。

这也解释了一个常见疑惑：同一个数据库，块模式与向量化模式的 scratch 大小不同。差异不在模式本身，而在 `bStateSize` 的计算方式。流状态的字段级细节（压缩表示、SOM 槽位）属于 05-09，本分片只在 05-05 里交代 `historyRequired` 与 `stateOffsets.end` 这两个「决定流状态大小」的字段。

#### 3.5 L4：引擎内部结构

从这一层开始，所有结构都不再是「独立分配的对象」，而是数据库字节码里的一段。`hs_get_bytecode(db)` 返回 `(const char *)db + db->bytecode`，这个地址就是 `RoseEngine` 的起点；`RoseEngine` 之后的 engine blob、各类字面量匹配表、NFA 偏移数组、状态偏移数组，全部用 `u32` 偏移自描述，没有一个指针。

这种「偏移代替指针」的设计有三个直接好处：数据库可以整块复制、可以序列化、可以映射到任意地址；也有一个直接代价：任何越界偏移都是内存安全问题，所以 5.4.x 的反序列化路径里加入了大量偏移校验（`db_validate_rose_offsets`、`validateStateLayout`、`db_validate_rose_programs` 等）。字段表里标注「偏移」的项，都应该按「相对谁的偏移」来读，这是本册最容易读错的地方：`RoseEngine::amatcherOffset` 相对 `RoseEngine` 起点，`NfaInfo::stateOffset` 相对流状态起点，`RoseStateOffsets::history` 同样相对流状态起点。

判断一个字段是「相对数据库」还是「相对状态」，有个简单的经验：凡是描述「编译产物内部位置」的偏移，基准是 `RoseEngine` 起点；凡是描述「运行时数据在流或 scratch 中的位置」的偏移，基准是状态区起点。两者混用会得到看起来合理、实际错位的地址，且往往只在特定模式（流式/向量化）下暴露。

#### 3.6 L5：编译侧临时结构

`hs_platform_info_t`、`hs_expr_info_t`、`hs_expr_ext_t`、`hs_compile_error_t` 四个结构全部定义在 `src/hs_compile.h`，它们的共同点是「只在一次编译调用期间存在」：前两个是入参/出参，第三个是每条模式的扩展参数，第四个是失败时的错误描述。它们不会进入数据库字节码，因此不参与序列化，也不影响运行时布局。

把它们单独列为一层，是为了避免一种常见混淆：看到 `hs_expr_info_t::min_width` 就以为运行时用它做边界判断。实际上运行时用的是 `RoseEngine::minWidth` 与各 matcher 的 `MinWidth`，两者来源相同但存放位置不同，一个是调用方可见的查询结果，一个是编译产物里的常量。前者可以保守，后者必须精确到运行时能用。

#### 3.7 跨文档索引方法

推荐三步法。第一步定对象：你要查的是数据库、scratch、流，还是某个引擎子结构。第二步定字段：在本册对应篇的字段表里按列定位，注意「源码位置」列给的是文件与行号，可以直接跳读。第三步按需跳转：参数取值、位值、默认值看 04；机制、状态机、调用链看 06；模块职责与文件清单看 07。

举三个例子。查「`HS_FLAG_SOM_LEFTMOST` 会不会影响数据库布局」，标志位本身在 04-02，但它导致的 `hasSom`、`somLocationCount`、`somHorizon` 字段在 05-05，机制在 06-10。查「scratch 为什么这么大」，容量字段在 05-03，尺寸计算入口在 04-06，调优建议在 08-02。查「数据库跨机报平台错误」，`platform` 字段在 05-02，校验顺序在 06-12，处置流程在 08-04。

### 4. 典型示例

下面这段代码不做任何匹配，只把三层对象的「身份信息」打出来：数据库头部的魔数与长度、scratch 的实际分配字节数、以及 `hs_database_info` 的字符串。它是排查现场问题的第一段代码，通常比任何日志都直接。为了让结构体字段可见，示例直接包含内部头 `database.h`，仅用于诊断工具，产品代码不应这样写。

```c
#include "database.h"
#include <hs.h>
#include <stdio.h>
#include <stddef.h>
#include <stdlib.h>

int main(void) {
    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;
    hs_scratch_t *scratch = NULL;

    if (hs_compile("foo|bar[0-9]{3}", HS_FLAG_CASELESS, HS_MODE_BLOCK,
                   NULL, &db, &err) != HS_SUCCESS) {
        printf("compile failed: %s\n", err->message);
        hs_free_compile_error(err);
        return 1;
    }

    printf("sizeof(struct hs_database) = %zu\n", sizeof(struct hs_database));
    printf("offsetof(bytes)             = %zu\n",
           offsetof(struct hs_database, bytes));
    printf("db magic=0x%08x version=0x%08x length=%u\n",
           db->magic, db->version, db->length);
    printf("db platform=0x%016llx bytecode_off=%u\n",
           (unsigned long long)db->platform, db->bytecode);

    if (hs_alloc_scratch(db, &scratch) != HS_SUCCESS) {
        printf("alloc scratch failed\n");
        hs_free_database(db);
        return 1;
    }

    size_t ssize = 0;
    hs_scratch_size(scratch, &ssize);
    printf("scratch size = %zu bytes\n", ssize);

    char *info = NULL;
    if (hs_database_info(db, &info) == HS_SUCCESS) {
        printf("info: %s\n", info);
        free(info);
    }

    hs_free_scratch(scratch);
    hs_free_database(db);
    return 0;
}
```

编译时需要把 `src` 加入头文件搜索路径，并链接 `hs`。示例输出如下（示例输出，具体格式需对照实际版本核验）。

```text
sizeof(struct hs_database) = 192
offsetof(bytes)             = 192
db magic=0xdbdbdbdb version=0x05040200 length=1104
db platform=0x0000000000000000 bytecode_off=192
scratch size = 8704 bytes
info: Version: 5.4.2 Features:  Mode: BLOCK
```

判读要点有四条。第一，`sizeof(struct hs_database)` 与 `offsetof(bytes)` 都应是 192，这是 `padding[25]` 存在的唯一目的；任何偏离都说明头文件与库不是同一版本，此时用自定义结构体读字段必然错位。第二，`magic` 应为 `0xdbdbdbdb`，若构建时用了 `-DHS_DB_MAGIC=`，这里会变成自定义值，跨团队协作时必须先对齐这个值，否则对方库直接返回 `HS_INVALID`，而且错误信息里不会提到魔数。第三，`version` 是 `major<<24 | minor<<16 | patch<<8`，5.4.2 对应 `0x05040200`，若最高字节为 0 说明这是开发版或本地改动版。第四，`platform` 为 0 表示编译时未指定平台信息、按当前主机优化，`Features:` 后为空也印证了这一点；`bytecode_off` 在页对齐分配下等于 192，只有在用户自备缓冲区时才可能小于 192。`scratch size` 的量级由数据库中最复杂的引擎决定，与模式条数不成正比，这一点在 05-03 会逐字段解释。

| 这个结构体属于哪个模块 | 07-03、07-04、07-10 |
| 单流内存怎么估 | 05-05 的 `stateOffsets.end` |

### 6. 版本差异

结构体层面的兼容策略写在 `src/database.h` 的一句注释里：「Values in here cannot (easily) change - add new ones!」。这句话是整册版本差异的总纲：字段只增不改，新增字段一律追加在尾部，必要时用保留字段占位。`hs_platform_info_t` 的 `reserved1` / `reserved2` 就是这种占位思路的产物，它们今天必须写 0，将来可能承载新参数。

时间线上，5.4.0 引入了 Sheng32、Sheng64、McSheng64 与 Fat Teddy，这些属于引擎层新增，反映到本册是 NFA/FDR 结构里的类型枚举与表布局变化，不改变 `hs_database` 头部；5.4.1 是十余个 bugfix；5.4.2 的条目与 scratch 行为有关，表现为某些场景下 `hs_alloc_scratch` 的容量增长策略调整，把 scratch 容量写死或用 `hs_scratch_size` 结果做静态假设的代码会踩到。

本快照中的数据库头部有两段 HMAC（`hmac` 与 `hmac_hdr`），且校验顺序是「先验头部、再信任 length、再验字节码」。早期版本只有单一 `hmac`，因此跨版本比对头部时不能假定 32 字节 HMAC 之后紧跟字节码，应以 `offsetof(struct hs_database, bytes)` 与 `bytecode` 字段为准。此处的字段增删与校验顺序**需对照实际版本核验**，尤其是从 5.3 升级到 5.4 的存量数据库。

最后是分支差异：Vectorscan 与上游 API 兼容，但引擎支持矩阵不同，结构体字段可能增删。本册的所有偏移与字段结论只对 Intel 上游 5.4.2 快照成立，不要直接套用到 ARM 分支。

### 7. 常见误用与调试

1. **直接 include 公共头却访问字段**。编译不过，于是有人复制一份结构体定义到自己的头文件里，结果版本升级后偏移错乱。正确做法是用 `hs_database_size`、`hs_scratch_size`、`hs_database_info` 拿信息，不碰内部布局。
2. **把数据库当可写**。有人为了「打补丁」把 `db->length` 改小再序列化，结果 HMAC 校验失败返回 `HS_INVALID`；更糟的是在只读页上直接写入，触发段错误而不是返回码。
3. **跨线程共享 scratch**。表现是偶发 `HS_SCRATCH_IN_USE`，或者更隐蔽的匹配结果错乱。用线程局部存储或池化，并保证借出期间不共享。
4. **只对一个库调用 `hs_alloc_scratch`**。另一个库的需求更大时，扫描会返回 `HS_INVALID` 或越界。正确做法是把所有要同时使用的库遍历一遍，直到全部返回 `HS_SUCCESS`。
5. **用 `sizeof(hs_database_t)`**。那是不完整类型，编译期就报错；即便写成 `sizeof(struct hs_database)`，也只在内部诊断代码里有意义，产品代码不应依赖具体数值。
6. **混用分配器家族**。用 `hs_set_database_allocator` 设置了自定义分配器，却用 `free()` 释放 `hs_database_info` 返回的字符串；字符串属于 misc 家族，必须用对应的释放函数。

（字段见 05-02 ｜ 参数见 04-08 ｜ 原理见 06-13 ｜ 模块见 07-10）

## 05-02 hs_database 与字节码布局字段

### 1. 本篇定位与覆盖范围

`struct hs_database` 是 Hyperscan 唯一可以「离开进程」的对象：它能被序列化成一段字节流、落盘、下发、在另一台机器上还原。因此它的字段设计目标不是性能，而是**自描述与可校验**。本篇逐字段覆盖 `src/database.h` 第 114 行到第 126 行的九个成员，外加 `bytes[]` 所指向的 `RoseEngine` 头部布局，以及 `platform_t` 的位掩码语义。

本篇不解释编译产物如何生成（见 06-01），也不解释反序列化的完整校验流程（见 06-12），只交代三件事：字段的精确偏移与大小、字段在什么时机被写、哪些函数会读它。凡涉及「为什么这么排布」的，只给源码注释能支撑的结论，不做推测。

阅读本篇时请把两个概念分开：**内存镜像**与**序列化镜像**。前者是 `hs_database` 在进程内的样子，头部 192 字节，`padding[25]` 占位；后者是 `hs_serialize_database` 写出的字节流，头部字段紧凑排列共 84 字节，`padding` 不参与序列化。两者的长度关系与字段顺序都不同，混淆这两者是排查「反序列化失败」时最常见的错误。

版本基线仍是 5.4.2。`HS_DB_MAGIC` 的默认值、`HS_DB_VERSION` 的构造方式、`hs_get_bytecode` 的实现都在本篇给出，其他篇一律引用本篇，不再重复。

### 3. 逐项详解

#### 3.1 magic：唯一的身份断言

`magic` 是四个字节的常量，源码里写的是 `#define HS_DB_MAGIC (0xdbdbdbdbU)`，并被 `#ifndef` 包住，因此可以在构建时用 `-DHS_DB_MAGIC=0x...` 替换。源码注释把动机写得很明确：用一个站点特有的值，可以让「用不同魔数构建的运行时」拒绝加载对方的数据库，多加一层对不可信数据库的防护。

读它的地方有两处。轻量路径是 `validDatabase`（`database.h:138`），只查 `magic` 与 `version`，失败分别返回 `HS_INVALID` 与 `HS_DB_VERSION_ERROR`；这条路径用在块模式扫描与 `hs_open_stream` 的入口，追求的是几个周期内拒绝明显不合法的指针。重量路径是 `dbIsValid`（`database.h:149` 声明，实现在 `src/database.c`），会继续校验长度、平台、HMAC 与内部偏移。

写它的地方只有编译器的数据库封装阶段与反序列化时的头部拷贝。运行期没有任何代码写 `magic`，这也是「数据库不可变」的最直接证据。调试时如果发现 `magic` 在运行中被改，几乎可以断定有人越界写入了数据库内存，而不是库自身的 bug。

#### 3.2 version：与发布号绑定的 32 位编码

`version` 的值来自 `HS_DB_VERSION`，而 `HS_DB_VERSION` 就是 `HS_VERSION_32BIT`（`database.h:48`）。`src/hs_version.h.in` 给出的构造是 `(major << 24) | (minor << 16) | (patch << 8) | 0`，最低字节恒为 0。5.4.2 因此是 `0x05040200`。

这个编码方式决定了三件事。第一，版本比较是精确相等而不是「大于等于」，`db_decode_header` 里写的是 `header->version != HS_DB_VERSION` 就返回 `HS_DB_VERSION_ERROR`，所以 5.4.2 的库读不了 5.4.1 编译的数据库，哪怕模式完全一样。第二，最低字节保留给未来用途，目前恒为 0，如果有人手工构造出 `0x05040201` 的头部，会被判为版本错误而不是「兼容」。第三，版本号不包含构建时间与 git 提交，`HS_VERSION_STRING` 才带 `BUILD_DATE`，所以「同版本不同构建」在版本字段上无法区分。

这条严格相等规则是生产环境的常见坑：编译节点与扫描节点必须使用同一版本、同一 `HS_DB_MAGIC`、同一平台配置。三者任一不同，症状都是加载失败，但返回码不同，可以据此定位——`HS_INVALID` 指向魔数，`HS_DB_VERSION_ERROR` 指向版本，`HS_DB_PLATFORM_ERROR` 指向平台。

#### 3.3 length：只算字节码，不算头部

`length` 的语义在源码注释里只有四个字「bytecode 长度」，但它是全篇最容易误读的字段。数据库的总分配大小是 `sizeof(struct hs_database) + db->length`（`src/database.c` 第 107、143 行都是这个写法），也就是说 `length` 不包含 192 字节头部。`hs_database_size` 返回的同样是这个总和，而不是 `length` 本身。

序列化路径也依赖这个语义。`hs_serialize_database` 先分配 `sizeof(struct hs_database) + db->length`，再把头部字段与字节码依次写入；`db_decode_header` 校验的是 `length == sizeof(struct hs_database) + header->length`，即「序列化总长 = 头部 + 字节码」。如果有人把 `length` 理解成总长，在校验时就会差 192 字节，表现为 `HS_INVALID`，而且错误信息里只有一句 `bad length`，非常容易误判为缓冲区截断。

`length` 在编译完成时由 `RoseEngine::size` 决定。`RoseEngine` 的 `size` 字段（`rose_internal.h` 第 458 行）注释为 `(bytes)`，即整个引擎镜像的字节数，它被写入 `hs_database::length`。因此 `length` 与字节码内容强相关：同一个模式集，开了 SOM、加了近似匹配、换了 horizon，`length` 都会变。

还有一个容易混淆的量：`hs_database_size` 返回的是「数据库对象在内存里的总字节数」，与序列化长度数值上相同（都是 `192 + length`），但语义基准不同——前者是分配量，后者是传输量。如果把数据库放在共享内存里分发，共享内存段的大小应按 `hs_database_size` 计算；如果走网络传输，报文长度应按 `hs_serialized_database_size` 计算。两者在当前版本恰好相等，但不要把「恰好相等」当成契约，字段注释只承诺了 `length` 是字节码长度。

#### 3.4 platform：六位 CPU 类型加三个特性否定位

`platform` 是 `u64a`，类型别名 `platform_t` 在 `database.h:73` 定义。掩码布局写在同一个文件里：低 6 位是 CPU 类型（`HS_PLATFORM_CPU_MASK` 为 `0x3F`，`HS_PLATFORM_INTEL` 为 1），高位是三个「不支持」标志——`HS_PLATFORM_NOAVX2`（`4<<13`）、`HS_PLATFORM_NOAVX512`（`8<<13`）、`HS_PLATFORM_NOAVX512VBMI`（`0x10<<13`）。

注意这是「否定式」编码：位被置起来表示该特性不可用，而不是可用。`hs_current_platform` 在编译期由 `HAVE_AVX2` 等宏决定，未定义就把对应的 NO 位置起来。这与 `hs_platform_info_t::cpu_features` 的「肯定式」编码正好相反，两者不能直接比较，这是 05-04 要展开的坑，这里先记住结论。

校验函数是 `db_check_platform`（`src/database.c` 第 179 行）。它接受四种值：`hs_current_platform` 本身，以及它与 `hs_current_platform_no_avx2`、`no_avx512`、`no_avx512vbmi` 的按位或。另外 `HS_PLATFORM_ALL`（`0xabcdef11abcdef00`）无条件通过，用于「通用数据库」。其他值一律返回 `HS_DB_PLATFORM_ERROR`。这个设计意味着：为高特性平台编译的数据库不能在低特性平台加载，但为低特性平台编译的数据库可以在高特性平台加载（因为前者只置了 NO 位，后者是它的超集）。

`hs_database_info` 会把 `platform` 翻译成字符串，但翻译逻辑只看三个 NO 位（`print_database_string`），输出 `""`、`AVX2`、`AVX512`、`AVX512VBMI` 四选一。因此看到 `Features:` 为空，说明数据库是按「无 AVX2」的基线编译的，不代表平台字段为 0——这两件事经常被混为一谈。

#### 3.5 bytecode：一个会被回退的偏移

`bytecode` 是「相对数据库起点」的偏移，`hs_get_bytecode` 的实现就是 `((const char *)db + db->bytecode)`。在页对齐分配的正常情况下它等于 192，但**不保证**等于 192，这是本篇最值得记住的细节。

原因在 `db_copy_bytecode`（`src/database.c` 第 2924 行）：反序列化时先算 `shift = (uintptr_t)db->bytes & 0x3f`，也就是 `bytes` 地址在 64 字节缓存行内的偏移，然后 `db->bytecode = offsetof(struct hs_database, bytes) - shift`。这样算出来的字节码起点一定是 64 字节对齐的。如果调用方用 `hs_deserialize_database_at` 把数据库放进一个只满足 8 字节对齐的缓冲区，`shift` 可能是 8、16 直到 56，`bytecode` 就会变成 184、176 直到 136。

这也解释了 `padding[25]` 注释里那句「必须 ≥63 字节」：最坏情况下字节码起点要往前挪 56 字节，如果 `padding` 太小，挪过去就会压到 `hmac_hdr` 的尾部，破坏 HMAC 覆盖范围。100 字节的 `padding` 让最坏落点 136 仍然大于 `hmac_hdr` 的结束偏移 92，留出 44 字节余量。

工程含义是：任何按「字节码一定在 192」写死的代码都是错的。正确写法一律走 `hs_get_bytecode`，或至少读 `bytecode` 字段。诊断工具如果要把数据库 dump 成十六进制，也必须用这个偏移定位引擎起点。

顺带说清这个函数的返回值语义：`hs_get_bytecode` 返回 `const void *`，强制调用方保持只读。它被声明为 `really_inline`，编译后就是一次加法，没有函数调用开销，所以热路径上可以放心使用。反过来，如果有人用 `const_cast` 把它转成可写指针去改引擎字段，后果不是立即崩溃，而是下次 HMAC 校验失败、或序列化出与内存不一致的镜像——这类问题极难定位，因为故障点与写入点相隔很远。

#### 3.6 hmac 与 hmac_hdr：两段完整性保护

`hmac` 是对字节码的 HMAC-SHA256，覆盖范围是 `db->length` 字节；`hmac_hdr` 是对头部 20 字节（`magic`、`version`、`length`、`platform`）的 HMAC-SHA256，覆盖范围明确排除了 `padding` 与两段 HMAC 自身。两个密钥都来自 `src/hs_db_hmac_key.h` 里的 `HS_DB_HMAC_KEY`，32 字节，可在构建期用 `-DHS_DB_HMAC_KEY_OVERRIDE` 替换。

为什么需要两段？因为校验 `hmac` 需要先知道 `length`，而 `length` 本身来自不可信的头部。如果只有一段 HMAC，攻击者改大 `length` 就能让校验读越界，或者改小 `length` 让校验只覆盖前缀。`hmac_hdr` 的存在使得「先认证 length，再用 length 认证字节码」成为可能，`db_decode_header` 与 `db_serialize_database` 的注释都明确写了这个顺序。

字段层面能观察到的现象是：篡改 `length` 会先触发头部 HMAC 失败，返回 `HS_INVALID`，而不是 `HS_DB_VERSION_ERROR` 或长度错误；篡改字节码则通过头部校验、在第二段失败。两种失败都映射到 `HS_INVALID`，所以只看返回码无法区分，需要打开 `DEBUG_OUTPUT` 看 `hmac mismatch` 之类的位置信息。

#### 3.7 padding 与 bytes：布局稳定器

`padding` 是 25 个 `u32`，共 100 字节，唯一作用是让 `bytes[]` 落在偏移 192。为什么偏偏是 192？因为 192 是 64 的整数倍，`hs_db_alloc` 按页分配后，`bytes` 天然落在缓存行边界上，字节码的访问不会跨行。同时 192 减去最大回退量 56 仍然是 136，安全地落在 `hmac_hdr` 之后。

`bytes` 是柔性数组，标准 C 里不占 `sizeof`，所以 `sizeof(struct hs_database)` 恰好是 192。它承载的内容是固定顺序的镜像分区：`RoseEngine` 头、engine blob、四张字面量匹配表、NFA 偏移数组、状态偏移数组。镜像分区的顺序与相对位置见图 05-02-02，箭头上的标注就是定位每一段的字段名。

这里有一个容易被误用的点：`bytes` 虽然叫「字节数组」，但它不是「一段不透明数据」，而是有严格内部结构的一整块镜像，所有子结构通过 `u32` 偏移互相引用。任何 memcpy 都必须整块复制，任何部分复制都会让偏移指向错误位置。序列化之所以安全，正是因为它整块复制并重新计算偏移（`bytecode` 由 `db_copy_bytecode` 重设）。

### 4. 典型示例

下面的示例手工解析一段序列化后的数据库字节流，不调用 `hs_deserialize_database`，目的是展示「序列化头部 84 字节」与「内存头部 192 字节」的差异。这段代码适合写进诊断工具，用来判断一个落盘文件是不是被截断或被改过。

```c
#include <stdio.h>
#include <stdint.h>
#include <string.h>

struct db_header_disk {
    uint32_t magic;
    uint32_t version;
    uint32_t length;
    uint64_t platform;
    uint8_t  hmac[32];
    uint8_t  hmac_hdr[32];
};

int main(int argc, char **argv) {
    if (argc < 2) {
        printf("usage: %s <serialized.db>\n", argv[0]);
        return 1;
    }
    FILE *f = fopen(argv[1], "rb");
    if (!f) {
        return 1;
    }
    struct db_header_disk h;
    memset(&h, 0, sizeof(h));
    if (fread(&h, 1, sizeof(h), f) != sizeof(h)) {
        printf("file too short for 84-byte header\n");
        fclose(f);
        return 1;
    }

    printf("magic       = 0x%08x\n", h.magic);
    printf("version     = 0x%08x\n", h.version);
    printf("bytecode len= %u\n", h.length);
    printf("platform    = 0x%016llx\n", (unsigned long long)h.platform);
    printf("total expect= %zu\n", sizeof(h) + (size_t)h.length);

    fseek(f, 0, SEEK_END);
    long actual = ftell(f);
    printf("file size   = %ld\n", actual);
    fclose(f);
    return 0;
}
```

在一次正常编译后立即序列化的场景下，输出形如下面这段（示例输出，具体格式需对照实际版本核验）。

```text
magic       = 0xdbdbdbdb
version     = 0x05040200
bytecode len= 1104
platform    = 0x0000000000000000
total expect= 1188
file size   = 1188
```

判读分四步。第一步看 `magic`，不是 `0xdbdbdbdb` 就直接判定「不是本库产物或魔数被改」，不要去查版本。第二步看 `version`，高位字节是主版本，`0x05` 说明是 5.x；如果整体是 0，说明文件头被清零，通常是写入时长度算错。第三步看 `bytecode len` 与文件实际大小的关系：`84 + length` 必须等于文件大小，不等就是截断或尾部追加。第四步看 `platform`，全 0 表示基线编译，若高位出现 `0x8000`、`0x10000`、`0x20000` 之类的位，说明这是「不支持某特性」的编码，要与目标机实际能力比对。这套判读不依赖库，可以在没有 Hyperscan 的机器上完成，非常适合分发前的自检。

### 5. 速查表

| 现象 | 对应字段 | 判定与处置 |
|---|---|---|
| 返回 `HS_INVALID` 且刚加载 | `magic` | 魔数不一致，检查 `-DHS_DB_MAGIC=` |
| 返回 `HS_DB_VERSION_ERROR` | `version` | 编译端与运行端版本不同，统一到 5.4.2 |
| 返回 `HS_DB_PLATFORM_ERROR` | `platform` | 目标机缺少编译时假定的特性，或反之 |
| `bad length` 调试信息 | `length` | 序列化总长应为 `84 + length` |
| 字节码越界 / 崩溃 | `bytecode` | 不要假设等于 192，走 `hs_get_bytecode` |
| 加载后立刻 HMAC 失败 | `hmac`、`hmac_hdr` | 文件被改，或换过 `HS_DB_HMAC_KEY` |
| `sizeof` 不是 192 | `padding` | 头文件与库不匹配 |

### 6. 版本差异

`hs_database` 的字段集合在 5.x 期间保持稳定：`magic`、`version`、`length`、`platform`、`bytecode`、`hmac`、`padding`、`bytes` 这八项从早期版本就存在，`hmac_hdr` 属于本快照可见的加固字段。判断依据是 `database.h` 的注释「Values in here cannot (easily) change - add new ones!」，以及 `db_decode_header` 中「先读 12 字节以便老数据库能走到版本检查」的兼容逻辑。

这段兼容逻辑值得记下来：`db_decode_header` 先要求至少 12 字节（`magic + version + length`），校验魔数与版本之后才要求完整 192 字节头部。这样做的目的是让「老版本序列化数据」能明确返回 `HS_DB_VERSION_ERROR`，而不是笼统的 `HS_INVALID`。所以看到 `HS_DB_VERSION_ERROR` 时，文件格式至少是对的，只是版本不对。

5.4.0 到 5.4.2 的变化不在头部字段，而在字节码内容：新引擎（Sheng 系列、Fat Teddy）会改变 `length` 的量级与内部表布局，`RoseEngine` 的 `runtimeImpl`、`somLocationCount` 等字段可能随之变化。头部字段保持不变，意味着「同一版本内头部兼容」，但「跨版本字节码不兼容」——这正是 `version` 采用精确相等比较的原因。

分支差异方面，Vectorscan 可能调整平台掩码的语义（例如 ARM 平台的特性位），本册的掩码结论只适用于 Intel 上游。跨分支分发数据库时，`platform` 字段的判定逻辑必须以目标分支的 `database.h` 为准，不能照搬本篇。

### 7. 常见误用与调试

1. **把 `length` 当总长**。序列化时按 `length` 分配缓冲区，结果尾部少 192 字节，反序列化报 `bad length`。记住总长是 `sizeof(struct hs_database) + length`。
2. **假设 `bytecode == 192`**。在 `hs_deserialize_database_at` 场景下它可能更小。任何手工定位引擎起点的代码都必须读字段。
3. **跨魔数构建混用**。A 团队用默认魔数，B 团队用 `-DHS_DB_MAGIC=`，互加载全部 `HS_INVALID`，但错误信息里看不出原因。上线前把魔数写进构建清单。
4. **手工拼序列化数据**。头部字段的顺序、HMAC 覆盖范围、`padding` 是否参与，三者任一弄错都会失败；正确做法是调用 `hs_serialize_database`，只做传输不做改写。
5. **在只读数据库上写入**。`hs_db_protect` 生效后写入会段错误；如果没生效，会静默破坏 HMAC，问题延迟到下次序列化才暴露。
6. **用 `hs_deserialize_database_at` 但缓冲区不对齐**。该函数要求 8 字节对齐，否则返回 `HS_BAD_ALIGN`；不对齐还会让 `bytecode` 回退量变化，进一步放大越界风险。

（字段见 05-02 ｜ 参数见 04-06 ｜ 原理见 06-12 ｜ 模块见 07-10）

## 05-03 hs_scratch 字段与生命周期

### 1. 本篇定位与覆盖范围

`struct hs_scratch` 是 Hyperscan 里唯一「每次扫描都可写」的顶层对象，也是所有运行时状态的实际落脚点：NFA 的活动队列、锚定字面量的命中日志、延时字面量的槽位、去重日志、SOM 起点数组、FDR 的确认值，全部挂在这一个结构体上。本篇逐字段覆盖 `src/scratch.h` 第 172 行到第 214 行的三十五个成员，外加它内嵌的 `core_info`、`match_deduper`、`RoseContext` 与 `catchup_pq` 三个子结构。

本篇只讲四件事：字段的含义、字段在分配时的物理位置、字段的容量由哪个 `RoseEngine` 字段决定、字段在什么时机被读写。扫描循环怎么推进队列、NFA 怎么展开、延时字面量怎么补扫，属于 06-06 与 06-11 的范围，本篇只给入口函数名。

必须提前澄清一个边界：scratch 不是流状态。流状态是 `hs_stream`，按流分配、随流释放；scratch 是按线程分配、跨流复用。两者在流式扫描时同时存在，`core_info::state` 指向当前流的状态区，而 scratch 只是「操作这块状态区的工作台」。把两者混为一谈，会导致「一个线程一个 scratch 就够了，为什么流还要单独分配」这类误解。

版本基线 5.4.2。`SCRATCH_MAGIC` 的值、`markScratchInUse` 的返回值语义、`alloc_scratch` 的布局顺序都来自本轮快照，与上游一致；涉及历史版本的字段增删在第六节单独说明。

### 3. 逐项详解

#### 3.1 magic 与 in_use：协作式占用标志

`magic` 是 `SCRATCH_MAGIC`（`0x544F4259`），在 `alloc_scratch` 里写入，在 `markScratchInUse`、`unmarkScratchInUse`、`hs_free_scratch`、`hs_scratch_size` 里被断言或校验。它没有任何加密含义，作用等同于「这块内存是不是我初始化的」。

`in_use` 是 `u8`，语义是「正被某次 API 调用使用」。`markScratchInUse` 的实现只有四行：断言魔数、读 `in_use`、若非零返回 1、否则置 1 返回 0。调用方看到返回 1 就把 `HS_SCRATCH_IN_USE` 抛给用户。`unmarkScratchInUse` 则断言当前值为 1 后清零。

这里的关键是：**这不是锁**。整个检查是「读—判断—写」三步，没有原子指令、没有内存屏障。两个线程同时对同一份 scratch 调用 `hs_scan`，完全可能都读到 0、都写入 1、都继续执行，然后在队列数组上互相踩踏。`in_use` 的真实作用是把「同一线程内的重入」变成可诊断的错误，例如在回调里再次调用 `hs_scan` 并传入同一个 scratch，会干净地返回 `HS_SCRATCH_IN_USE`，而不是随机崩溃。

因此「scratch 非线程安全」不是实现缺陷，而是设计前提：它把线程绑定这件事交给调用方，换来零锁的扫描热路径。生产环境的正确做法是每线程一份，或用对象池并保证借出期间独占。

#### 3.2 内存布局：先队列，后状态，最后对齐

`alloc_scratch`（`src/scratch.c` 第 145 行）先按原型算出 `size`，再分配 `sizeof(struct hs_scratch) + size + 256`，把返回指针向上取整到 64 字节作为结构体起点，原始指针存进 `scratch_alloc`。随后按固定顺序切分：`queues`、`som_store`、`som_attempted_store`、`delay_slots`（先指针数组、再每个 fatbit）、`al_log`（同样是先指针数组、再每个 fatbit）、`catchup_pq.qm`、`bstate`、`tstate`、64 字节对齐后的 `deduper.som_start_log[0..1]`、`aqa`、`handled_roles`、`deduper.log[0..1]`、`deduper.som_log[0..1]`、`som_set_now`、`som_attempted_set`，最后 64 字节对齐到 `fullState`。

顺序不是随意的：越靠前越「按队列数线性增长」，越靠后越「按状态大小或位图大小增长」；`fullState` 放最后并且单独对齐，是因为它会被 NFA 引擎按缓存行访问，起点必须对齐。布局关系见图 05-03-01，箭头表示物理相邻关系而非引用关系。

#### 3.3 队列三件套：queueCount、queues、aqa

`queues` 是 `struct mq` 数组，长度 `queueCount`；`aqa` 是活动队列位图，长度为 `activeQueueArraySize` 字节；`queueCount` 与 `activeQueueArraySize` 都来自 `RoseEngine` 的同名字段，在 `hs_alloc_scratch` 里取最大值。

`struct mq` 的定义不在 `scratch.h` 里，而在 NFA 相关的内部头中，本篇不展开其字段（见 05-06）。但有一个字段与 scratch 强相关：`alloc_scratch` 结束时会把每个 `mq::scratch` 指回当前 scratch，这样队列执行时不必再传参。这条「回指」意味着 scratch 不能整块 memcpy 到另一个地址后直接使用——`queues` 内部存的是绝对指针指向原 scratch，复制后必须重新绑定。`hs_clone_scratch` 之所以走完整的 `alloc_scratch` 而不是 memcpy，正是这个原因。

`aqa` 的语义是「哪些队列当前有效且活动」。它每步被更新，所以属于热字段；`activeQueueArraySize` 只在分配时用一次，属于冷字段。两者成对出现，但读写频率完全不同，这在调优时值得注意：位图操作的代价与 `queueCount` 成正比，而不是与模式数成正比。

#### 3.4 状态三件套：bstate、tstate、fullState

`bstate` 是块模式的状态区，大小 `bStateSize`；`tstate` 是瞬态 Rose 的状态区，大小 `tStateSize`；`fullState` 是未压缩的 NFA 状态区，大小 `fullStateSize`。三者的共同点是「按字节分配、按引擎解释」，scratch 本身不知道里面存的是什么。

`bStateSize` 的计算有一个模式分支：块模式下等于 `RoseEngine::stateOffsets.end`；向量化模式下等于 `sizeof(struct hs_stream) + stateOffsets.end`，因为向量化扫描要在 scratch 里构造一个完整的流状态。流式模式下这个值不参与（流状态由 `hs_stream` 自己持有），但 `hs_alloc_scratch` 仍然会为它保留容量，因为同一个 scratch 可能同时服务块模式与流式数据库。

`fullState` 单独 64 字节对齐，是因为 Castle 与 McSheng 这类引擎会按缓存行读写状态位图。若对齐不当，性能下降是次要的，某些按对齐假设写的 SIMD 代码会直接触发异常。这也是 `alloc_scratch` 里 `current = ROUNDUP_PTR(current, 64)` 出现在 `fullState` 之前的原因。

#### 3.5 字面量日志：al_log、al_log_sum、delay_slots

`al_log` 是「指针数组 + fatbit 数组」的两段式结构，条目数为 `anchored_literal_region_len`，每个 fatbit 大小为 `anchored_literal_fatbit_size`。`getAnchoredLiteralLog` 只是返回这个指针数组，之所以包一层函数，是为了在 NFA 与 Rose 两套代码里统一访问方式。

`al_log_sum` 是 `u64a`，把各条目的位图汇总成 64 位，用于「有没有任何锚定字面量命中」的快速判断。它有一个隐含约束：`anchored_literal_region_len` 必须小于 64（`alloc_scratch` 里有 `assert(anchored_literal_region_len < 8 * sizeof(s->al_log_sum))`）。这条断言解释了为什么锚定表要分组：组数受 64 限制，超出的部分由 `anchored_matcher_info::next_offset` 链到下一组。

`delay_slots` 的结构与 `al_log` 相同，但条目数固定为 `DELAY_SLOT_COUNT`（`1 << DELAY_BITS`，即 32），每个 fatbit 大小为 `delay_fatbit_size`。固定 32 个槽位对应「延时 0 到 31 字节」的语义，`MAX_DELAY` 就是 31。这个数字是编译期常量，不随数据库变化，所以 `delay_slots` 的指针数组大小恒定，只有 fatbit 本身随字面量数量变化。

#### 3.6 core_info：一次扫描的公共上下文

`core_info` 是所有引擎共享的「当前扫描」描述，字段分四组。第一组是回调：`userContext` 与 `userCallback`，后者类型是 `int (HS_CDECL *)(unsigned int, unsigned long long, unsigned long long, unsigned int, void *)`，与公共头里的 `match_event_handler` 一致。第二组是引擎与状态：`rose` 指向当前数据库的 `RoseEngine`，`state` 指向当前流或块的状态区，`exhaustionVector`、`logicalVector`、`combVector` 分别指向耗尽、逻辑、组合三个位图。第三组是缓冲区：`buf`/`len` 是主扫描缓冲，`hbuf`/`hlen` 是历史缓冲，`buf_offset` 是主缓冲在流中的起始偏移。第四组是 `status` 位掩码。

`status` 的四个位定义在 `scratch.h` 第 74 到 88 行：`STATUS_TERMINATED`（用户请求终止）、`STATUS_EXHAUSTED`（不可能再产生匹配）、`STATUS_DELAY_DIRTY`（历史中的延时字面量命中，需要重建）、`STATUS_ERROR`（Rose 程序内部错误）。围绕它有三个内联判定：`told_to_stop_matching` 只看 TERMINATED，`can_stop_matching` 看 TERMINATED、EXHAUSTED、ERROR 三者，`internal_matching_error` 只看 ERROR。这三个函数的区别很重要：用户主动终止不是错误，不能按错误路径处理；而内部错误必须映射成 `HS_UNKNOWN_ERROR` 返回。

`buf_offset` 是唯一一个「语义上属于流、物理上存在 scratch」的字段。它记录主缓冲区第一个字节在整条流中的绝对偏移，所有报告偏移都由它加相对位置得到。流式扫描跨块时它会被推进，块模式扫描时它恒为 0。调试「偏移差了一个块」的问题，第一件事就是打印它。

#### 3.7 deduper：去重日志与 SOM 起点日志

`match_deduper` 有七个字段：`log[2]`（偶/奇两份 fatbit 日志）、`som_log[2]`（偶/奇两份 SOM fatbit 日志）、`som_start_log[2]`（偶/奇两份起点偏移数组）、`dkey_count`（去重 key 数）、`log_size`（每份日志字节数）、`current_report_offset`（当前报告偏移）、`som_log_dirty`（SOM 日志是否待刷新）。

「偶/奇两份」是双缓冲：当前偏移用一份，前一个偏移用另一份，这样「同一偏移重复报告」和「跨偏移去重」可以分开判断。`log_size` 来自 `RoseEngine::dkeyLogSize`，`dkey_count` 来自 `RoseEngine::dkeyCount`，两者在 `hs_alloc_scratch` 里成对更新——源码里 `if (rose->dkeyCount > proto->deduper.dkey_count)` 之后同时写 `dkey_count` 与 `log_size`，不会只更新一个。

`current_report_offset` 初值是 `~0ULL`。`src/rose/match.c` 第 551 行有 `if (rose->hasSom && scratch->deduper.current_report_offset == ~0ULL)` 的判断，说明这个哨兵值有实际语义：表示「还没有报告过任何偏移」，此时 SOM 刷新需要特殊处理。调试 SOM 相关问题时，这个值是不是 `~0ULL` 往往能区分「从未报告」与「报告偏移为 0」。

#### 3.8 SOM 字段组：随槽位与 horizon 变化

SOM 相关字段共七个：`som_store`、`som_attempted_store`、`som_set_now`、`som_attempted_set`、`som_set_now_offset`、`som_store_count`、`som_fatbit_size`。语义分别是：起点值数组、写入失败时记录的值数组、「本偏移已设置」位图、「本偏移尝试设置」位图、位图对应偏移、槽位数量、位图字节数。

容量来源是 `RoseEngine::somLocationCount` 与 `somLocationFatbitSize`。未开启 SOM 的数据库这两个值为 0，`hs_alloc_scratch` 就不会为这组字段分配任何空间，`som_store` 为 NULL。开启 SOM 后，槽位数与「需要记录起点的模式数」相关，位图大小与槽位数相关，因此 scratch 会显著变大。

需要区分两个不同的「随 horizon 增长」。`somHorizon`（`RoseEngine` 的 `u8` 字段）表示每个 SOM 槽在**流状态**里的字节宽度，horizon 越大，单槽越宽，`stateOffsets.end` 越大，进而 `bStateSize` 越大；而 scratch 里的 `som_store` 是 `u64a` 数组，每槽固定 8 字节，`som_store_count` 由槽位数决定，与 horizon 没有直接比例关系。把两者混为一谈，会得出「horizon 放大一倍 scratch 就放大一倍」的错误结论。

另外，`hs_alloc_scratch` 对 `som_store_count` 做了溢出检查：`som_store_count > UINT32_MAX / sizeof(u64a)` 直接返回 `HS_INVALID`。这是为了防止伪造数据库让 `som_store_count * 8` 回绕成小值，导致分配不足后在扫描时越界写。看到这个错误码，说明数据库本身不可信，而不是 scratch 参数有问题。

#### 3.9 尺寸与生命周期：scratchSize、scratch_alloc、扩容

`scratchSize` 记录 `alloc_scratch` 实际分配的字节数（含结构体、附加区与 256 字节余量），`hs_scratch_size` 直接返回它。`scratch_alloc` 记录分配器返回的原始指针，`hs_free_scratch` 释放的是它而不是结构体地址，因为结构体被向上取整过。

生命周期的主线在 `hs_alloc_scratch`：先用 `dbIsValid` 校验数据库，再校验传入的 scratch（对齐、魔数、`markScratchInUse`），然后构造一个「原型」结构体，逐字段与数据库需求取较大值；只要有任何一项变大就 `resize = 1`，释放旧 scratch 并调用 `alloc_scratch` 重建；全部不变则直接 `unmarkScratchInUse` 返回。这条路径决定了多库场景的正确用法：对每个要同时使用的数据库调用一次，直到全部返回 `HS_SUCCESS`，此时 scratch 容量是所有库需求的并集。

扩容有一个容易忽略的副作用：`hs_alloc_scratch` 在重建时会释放旧 scratch 并把 `*scratch` 指向新地址。因此调用方不能在其他地方缓存 scratch 的指针副本，也不能在扩容期间让别的线程持有它。正确模式是「启动阶段完成所有扩容，运行阶段只读指针」。

`hs_clone_scratch` 走的是同一个 `alloc_scratch`，从源 scratch 复制容量字段后重新分配，不做 memcpy。这样克隆出来的 scratch 有独立的队列数组与独立的回指，可以给另一个线程使用；代价是容量按源 scratch 复制，若源 scratch 是为大库准备的，克隆体也会同样大。

### 4. 典型示例

下面的示例演示多库扩容：先为一个小库分配 scratch，再为一个大库（开启 SOM）复用同一个指针，观察容量变化与克隆结果。这是部署阶段最该写对的一段代码。

```c
#include <hs.h>
#include <stdio.h>
#include <stdlib.h>

static hs_database_t *compile_one(const char *pat, unsigned flags,
                                 unsigned mode, unsigned som_horizon) {
    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;
    unsigned m = mode | (flags & HS_FLAG_SOM_LEFTMOST ? som_horizon : 0);
    if (hs_compile(pat, flags, m, NULL, &db, &err) != HS_SUCCESS) {
        printf("compile failed: %s\n", err->message);
        hs_free_compile_error(err);
        return NULL;
    }
    return db;
}

int main(void) {
    hs_database_t *small = compile_one("abc", 0, HS_MODE_BLOCK, 0);
    hs_database_t *big = compile_one("foo[0-9]{4}bar", HS_FLAG_SOM_LEFTMOST,
                                     HS_MODE_BLOCK, HS_MODE_SOM_HORIZON_LARGE);
    if (!small || !big) {
        return 1;
    }

    hs_scratch_t *scratch = NULL;
    hs_database_t *dbs[2] = { small, big };
    for (int i = 0; i < 2; i++) {
        hs_error_t rc = hs_alloc_scratch(dbs[i], &scratch);
        size_t sz = 0;
        hs_scratch_size(scratch, &sz);
        printf("after db[%d]: rc=%d scratch=%zu bytes\n", i, rc, sz);
        if (rc != HS_SUCCESS) {
            printf("alloc failed, stop\n");
            return 1;
        }
    }

    hs_scratch_t *clone = NULL;
    if (hs_clone_scratch(scratch, &clone) == HS_SUCCESS) {
        size_t csz = 0;
        hs_scratch_size(clone, &csz);
        printf("clone size = %zu bytes\n", csz);
        hs_free_scratch(clone);
    }

    hs_free_scratch(scratch);
    hs_free_database(small);
    hs_free_database(big);
    return 0;
}
```

示例输出如下（示例输出，具体格式需对照实际版本核验）。数值随模式与版本变化，重点看趋势而不是绝对值。

```text
after db[0]: rc=0 scratch=5120 bytes
after db[1]: rc=0 scratch=11776 bytes
clone size = 11776 bytes
```

判读分三点。第一，第一次分配后的 `scratch` 只覆盖小库需求，第二次调用同一个小库指针后容量明显变大，说明 `hs_alloc_scratch` 是「合并式扩容」而不是「覆盖式重设」；如果第二次调用后容量反而变小，说明有人误以为它会重置，或者在两次调用之间释放了 scratch 并重新传了空指针，这两者的区别可以直接从打印看出。第二，第二次返回码为 0 但容量变大，说明扩容成功；若返回 `HS_INVALID`，通常是数据库校验失败（`dbIsValid` 在扩容之前），而不是内存不足；若返回 `HS_SCRATCH_IN_USE`，说明传入的 scratch 正被占用，多半是上一次扫描没有正常退出。第三，克隆体大小与源完全一致，印证 `hs_clone_scratch` 是「按源容量复制」而非「按某个数据库需求重建」；这也意味着克隆不能替代多库扩容——先克隆再对新库调用 `hs_alloc_scratch` 才是正确顺序。

### 5. 速查表

| 症状或需求 | 先看字段 | 处置方向 |
|---|---|---|
| 返回 `HS_SCRATCH_IN_USE` | `in_use` | 检查重入与跨线程共享 |
| 扫描越界或结果错乱 | `queueCount`、`aqa` 相关容量 | 确认已对每个库调用 `hs_alloc_scratch` |
| scratch 过大 | `bStateSize`、`som_store_count` | 关 SOM、降 horizon、拆库 |
| 流式与块模式大小不同 | `bStateSize` | 向量化模式含流头 |
| 克隆后行为异常 | `scratch_alloc`、`queues` | 不要 memcpy scratch，用 `hs_clone_scratch` |
| 内存估算偏差大 | `scratchSize` | 以 `hs_scratch_size` 为准，不手算 |
| SOM 相关崩溃 | `som_store_count`、`som_fatbit_size` | 校验数据库来源与版本 |

### 6. 版本差异

`hs_scratch` 的字段集合在 5.x 期间是「渐进增补」的：`magic`、`in_use`、队列与状态区字段从早期版本就存在，`handled_roles`、`handledKeyFatbitSize` 与 `fdr_conf` 系列属于后续为字面量角色管理与 FDR 前端加入的字段，SOM 相关的七个字段随 SOM 功能一起引入。判断依据是 `scratch.h` 的字段注释密度与 `alloc_scratch` 里的分配顺序——新字段往往被追加在 `fullState` 之前，而不是插在中间，以减小布局变动。

5.4.2 的 changelog 条目与 scratch 行为有关，具体表现为容量增长与复用策略的调整。对使用方的直接影响是：不要假设「同样的数据库集合在不同小版本上得到同样的 `hs_scratch_size`」，也不要把某个版本的数值写进容量规划表。正确做法是在目标版本上实测，并把 `hs_scratch_size` 纳入启动自检日志。

5.4.0 引入的 Sheng 系列与 Fat Teddy 会间接影响 scratch：新引擎需要 `fullState` 或额外的确认区，`scratchStateSize` 随引擎选择变化，进而改变 `fullStateSize`。这类变化不会新增字段，但会改变同一个字段的量级，所以「字段没变」不等于「布局没变」。

最后提醒分支差异：Vectorscan 的 scratch 布局可能与上游不同，尤其是与平台相关的对齐与 SIMD 状态区。跨分支移植时，任何按偏移访问 scratch 内部区的代码都要重新核验，不能照搬本篇结论。

### 7. 常见误用与调试

1. **把 scratch 当线程安全缓存**。全局一份 scratch 给所有工作线程用，压力小时看不出问题，压力大时出现 `HS_SCRATCH_IN_USE` 或结果错乱。改成线程局部或池化。
2. **只分配一次就服务所有库**。第二个库需求更大时会越界。必须遍历所有库反复调用 `hs_alloc_scratch`。
3. **在回调里重入扫描**。同一线程、同一 scratch 的嵌套调用会返回 `HS_SCRATCH_IN_USE`；如果确实需要嵌套，为内层准备独立 scratch。
4. **扩容后继续用旧指针**。`hs_alloc_scratch` 可能释放旧区并返回新地址，缓存副本会变成悬垂指针。
5. **memcpy 复制 scratch**。`queues` 内部回指原 scratch，复制后回指仍指向旧地址；用 `hs_clone_scratch`。
6. **用 `scratchSize` 估算峰值内存**。它只是当前这份 scratch 的大小，多线程场景要乘以并发份数，还要加上流状态与数据库本身。
7. **在 `hs_free_scratch` 前不结束扫描**。释放时若 `in_use` 非零会返回 `HS_SCRATCH_IN_USE` 而不释放，造成泄漏；先确保所有扫描已返回。

## 05-04 编译侧结构体：platform_info / expr_info / expr_ext / compile_error

### 1. 本篇定位与覆盖范围

前两篇讲的都是「编译产物」与「运行时工作区」，本篇讲的是夹在中间的一层：调用方在编译期间传给库、或从库拿回的结构体。它们全部定义在 `src/hs_compile.h`，全部只在一次调用期间存在，全部不进入数据库字节码。这一层最容易被认为是「参数表」而忽略，实际上它们决定了编译结果的形状——`hs_platform_info_t` 决定按哪套指令集优化，`hs_expr_ext_t` 决定哪些匹配被提前抑制，`hs_expr_info_t` 告诉调用方模式的大致宽度，`hs_compile_error_t` 是唯一的失败诊断通道。

本篇覆盖四个结构体共十七个字段，并交代它们与六个 API 的配对关系：`hs_compile`、`hs_compile_multi`、`hs_compile_ext_multi`、`hs_expression_info`、`hs_expression_ext_info`、`hs_populate_platform`。参数的位值与默认值属于 04 册，机制属于 06 册，本篇只讲字段本身。

先给一个总判断：这四个结构体里，`hs_platform_info_t` 是「影响优化但不限制运行」的软约束，`hs_expr_ext_t` 是「编译期就生效的硬约束」，`hs_expr_info_t` 是「保守估计而非承诺」，`hs_compile_error_t` 是「诊断而非控制流」。把这四条记住，后面十七个字段就不会读错。

版本基线 5.4.2。四个结构的字段在 5.x 期间没有增删，但 `tune` 的取值与 `cpu_features` 的位在持续追加，这一点在第六节说明。

### 3. 逐项详解

#### 3.1 hs_platform_info_t：软约束的四字段

`tune` 是 `unsigned int`，取值是 `HS_TUNE_FAMILY_*` 系列：`GENERIC` 为 0，`SNB` 为 1，`IVB` 为 2，`HSW` 为 3，`SLM` 为 4，`BDW` 为 5，`SKL` 为 6，`SKX` 为 7，`GLM` 为 8，`ICL` 为 9，`ICX` 为 10。它的作用是告诉编译器「按哪一代微架构的端口与延迟特性做取舍」，例如字面量分桶大小、向量宽度选择。注释明确写了：使用这个字段**不限制**数据库能运行的处理器，只影响性能。

`cpu_features` 是 `unsigned long long`，位值定义在同一文件：`HS_CPU_FEATURES_AVX2` 是 `1ULL << 2`，`AVX512` 是 `1ULL << 3`，`AVX512VBMI` 是 `1ULL << 4`，另有 `HS_PLATFORM_ALL`（`0xabcdef11abcdef00ULL`）表示「所有平台通用」。注意这里是**肯定式**编码：置位表示可用。它与 `hs_database::platform` 的否定式编码正好相反，两者不能直接比较，也不能互相赋值。

`reserved1` 与 `reserved2` 是 `unsigned long long`，注释只有一句「Reserved for future use」。它们的正确处理方式是显式写 0。用 `memset` 清零整个结构体是安全的，但用 `= {0}` 之外的方式逐个赋值时容易漏掉，导致未初始化字节进入编译器的判断。当前版本编译器不看这两个字段，但未来版本可能会看，写 0 是唯一的前向兼容做法。

`hs_populate_platform` 是填充这个结构的便捷入口：它按当前主机探测 `tune` 与 `cpu_features`，调用方拿到后可以直接传给 `hs_compile*`。它探测的是「编译这台机器」的能力，不是「运行目标机器」的能力；交叉编译场景必须手工填写目标值，否则会生成只能在编译机跑的高特性数据库。

#### 3.2 hs_expr_info_t：五个字段的判读价值

`min_width` 是匹配的最小字节长度。注释里有一句关键限定：在使用扩展参数或 `HS_FLAG_SINGLEMATCH` 这类「抑制匹配」的特性时，这个值是**保守下界**，可能小于真实最小值。原因是这些特性会让编译器在更早的位置截断匹配路径，宽度分析只能给出「至少这么长」的结论。

`max_width` 是最大字节长度，无界时填 `UINT_MAX`（`0xFFFFFFFF`）。同样有保守性说明。判读时要注意：`max_width == UINT_MAX` 只表示「模式本身无上界」，不表示「一定会匹配到缓冲区末尾」；有界重复被展开后可能仍然给出有限值。

`unordered_matches`、`matches_at_eod`、`matches_only_at_eod` 三个 `char` 是「行为标志」，价值远高于宽度。`unordered_matches` 非零表示该表达式可能产生乱序报告，典型来源是断言——断言触发的匹配可能在扫描到更后位置时才被确认。`matches_at_eod` 非零表示可能在数据结束处报告，流式模式下这类匹配要等到 `hs_close_stream` 才出现。`matches_only_at_eod` 非零表示**只**在结束处报告，例如以 `$` 结尾的模式。

工程上这三个标志决定「什么时候能认为扫描结束」。如果调用方按「`hs_scan` 返回就算完」来设计流水线，遇到 `matches_at_eod` 为真的模式就会漏掉最后一批匹配。正确做法是流式场景必须在 `hs_close_stream` 之后才算完整，块模式则要在最后一次扫描时把 EOD 语义考虑进去。

这三个标志还有一个常被忽略的用途：估算「报告延迟」。`matches_only_at_eod` 为真的模式，报告时间与数据到达时间无关，只与关闭时间有关，因此不适合做实时告警；`unordered_matches` 为真的模式，报告顺序与偏移顺序不一致，因此不能假设「先收到的匹配偏移一定更小」，做窗口聚合时必须自己排序或缓冲。把这两个结论写进接口契约，比事后排查「为什么告警晚了十秒」要省力得多。

还有一条边界：`hs_expression_info` 返回 `HS_SUCCESS` **不保证**同一模式能被 `hs_compile` 编译成功。头文件注释写得很直接：这个函数可能对 Hyperscan 无法编译的正则返回成功。因此它适合做「宽度预估」与「行为探测」，不适合做「可编译性预检」。

#### 3.3 hs_expr_ext_t：flags 决定一切

`flags` 是 `unsigned long long`，五个位分别对应五个可选字段：`HS_EXT_FLAG_MIN_OFFSET` 为 1，`MAX_OFFSET` 为 2，`MIN_LENGTH` 为 4，`EDIT_DISTANCE` 为 8，`HAMMING_DISTANCE` 为 16。**只有置位对应的字段才会被读取**，未置位的字段即使填了值也被忽略。这是本篇最实用的知识：调试「扩展参数不生效」时，第一步就是打印 `flags`。

`min_offset` 与 `max_offset` 是「允许报告的结束偏移区间」，语义是「结束偏移落在区间外的匹配不报告」，而不是「从某个位置开始扫描」。这点常被误解为「跳过前 N 字节」，实际效果是「前 N 字节内的匹配被抑制，但扫描仍从 0 开始，跨过 N 的匹配照常报告」。`min_length` 是匹配长度（起点到终点）的下界，需要起点信息才能精确判定，因此它与 SOM 的关系需要在 06-10 里对照理解。

`edit_distance` 与 `hamming_distance` 都是 `unsigned`，分别对应插入/删除/替换意义上的编辑距离与只允许替换的汉明距离。两者都只对单模式编译路径有意义，且会显著放大编译时间与字节码体积；具体上限与组合限制需对照实际版本核验（不同版本对「有界重复 + 近似匹配」的处理不同）。工程上应把它们当作「最后手段」：能用精确模式加后处理解决的，不要用近似匹配。

几组已知的互斥关系必须记住：`HS_FLAG_SOM_LEFTMOST` 与 `HS_FLAG_SINGLEMATCH` 不能组合，`HS_FLAG_SOM_LEFTMOST` 与 `HS_FLAG_PREFILTER` 不能组合，违反时编译直接失败并给出 `HS_COMPILER_ERROR`。这些限制与 `hs_expr_ext_t` 无直接关系，但在设计扩展参数组合时经常一起出现，所以放在这里一并提醒。

为什么近似匹配值得警惕？因为它把「一条模式」变成「一族模式的并集」，编译期要为每个可能的编辑位置生成状态，成本随距离增长很快；`min_length` 与 `min_offset` 则相反，它们只做「报告裁剪」，几乎不增加状态，属于便宜的过滤手段。工程上的优先级应该是：先用偏移与长度约束缩小报告范围，再用 `SINGLEMATCH` 之类的手段减少重复报告，最后才考虑近似匹配。顺序反了，编译时间与字节码体积都会失控。

#### 3.4 hs_compile_error_t：唯一的失败诊断通道

`message` 是 `char *`，由库在失败时分配，内容是人类可读的描述，例如「Pattern matches empty buffer」「Unrecognised flag」「Bounded repeat is too large」。它不是稳定的错误码，不能拿来做字符串匹配分支；需要分支时用返回码 `HS_COMPILER_ERROR` 加自己的规则。

`expression` 是 `int`，表示出错表达式的零基下标。注释说明：如果错误不能定位到具体表达式，这个值小于 0。多模式编译时它是定位「哪一条写错了」的唯一线索，尤其是几千条模式批量编译的场景，没有它就只能二分。

生命周期很短：`hs_compile*` 失败时通过出参返回，调用方读完必须调用 `hs_free_compile_error`。这个函数接受 NULL 并返回 `HS_SUCCESS`，所以「无条件调用」是安全的。反过来，用 `free()` 释放 `message` 或用 `free()` 释放整个结构体都是错的——内部可能用了自定义分配器，释放必须走配套函数。

多模式场景下还有两个细节。第一，`expression` 只在「错误能定位到某条模式」时有意义；如果错误来自整体参数（例如 `mode` 不合法、数据库过大），它会小于 0，此时不要拿它去索引表达式数组，否则会越界。第二，一次失败的编译只返回一个错误，即使多条模式都有问题也只报第一条，因此修完一条再编译一次是常态，不要指望一次拿到全部错误清单。批量校验模式集的正确做法是先用 `hs_expression_info` 做语法级预筛，再逐条 `hs_compile`，把错误按 `expression` 归档。

### 4. 典型示例

下面的示例做三件事：用 `hs_expression_info` 探测宽度与 EOD 行为，用 `hs_expression_ext_info` 观察扩展参数对宽度的影响，最后故意编译一个空匹配模式，展示 `hs_compile_error_t` 的两个字段。

```c
#include <hs.h>
#include <stdio.h>
#include <stdlib.h>

static void show_info(const char *pat, unsigned flags,
                      const hs_expr_ext_t *ext) {
    hs_expr_info_t *info = NULL;
    hs_compile_error_t *err = NULL;
    hs_error_t rc = ext ? hs_expression_ext_info(pat, flags, ext, &info, &err)
                        : hs_expression_info(pat, flags, &info, &err);
    if (rc != HS_SUCCESS) {
        printf("info failed: expr=%d msg=%s\n",
               err ? err->expression : -99, err ? err->message : "(null)");
        hs_free_compile_error(err);
        return;
    }
    printf("pat=%-16s min=%u max=%u unordered=%d at_eod=%d only_eod=%d\n",
           pat, info->min_width, info->max_width,
           (int)info->unordered_matches, (int)info->matches_at_eod,
           (int)info->matches_only_at_eod);
    free(info);
}

int main(void) {
    show_info("abc[0-9]{2,4}", 0, NULL);
    show_info("foo$", HS_FLAG_MULTILINE, NULL);
    show_info("a.*b", 0, NULL);

    hs_expr_ext_t ext;
    ext.flags = HS_EXT_FLAG_MIN_LENGTH;
    ext.min_offset = 0;
    ext.max_offset = 0;
    ext.min_length = 100;
    ext.edit_distance = 0;
    ext.hamming_distance = 0;
    show_info("abc[0-9]{2,4}", 0, &ext);

    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;
    if (hs_compile("(abc)?", 0, HS_MODE_BLOCK, NULL, &db, &err)
        != HS_SUCCESS) {
        printf("compile failed: expr=%d msg=%s\n", err->expression,
               err->message);
        hs_free_compile_error(err);
    }
    return 0;
}
```

示例输出如下（示例输出，具体格式需对照实际版本核验）。数值依赖版本与平台，重点是字段之间的关系。

```text
pat=abc[0-9]{2,4}    min=5 max=7 unordered=0 at_eod=0 only_eod=0
pat=foo$             min=3 max=3 unordered=0 at_eod=1 only_eod=1
pat=a.*b             min=2 max=4294967295 unordered=0 at_eod=0 only_eod=0
pat=abc[0-9]{2,4}    min=5 max=7 unordered=0 at_eod=0 only_eod=0
compile failed: expr=0 msg=Pattern matches empty buffer
```

判读分四步。第一步看 `abc[0-9]{2,4}`：`min=5` 来自三个字面字符加两位数字，`max=7` 来自四位数字，两者都精确，说明有界重复被完整展开。第二步看 `foo$`：`at_eod=1` 且 `only_eod=1`，这正是「流式模式下匹配要等到 `hs_close_stream`」的信号；如果业务方按「`hs_scan_stream` 返回后立刻判定」来写逻辑，这条模式永远拿不到匹配。第三步看 `a.*b`：`max=4294967295` 就是 `UINT_MAX`，表示无上界，任何按 `max_width` 分配缓冲区的做法都会失败。第四步看带 `min_length = 100` 的调用：输出与不带扩展参数时完全一致，`min` 仍是 5。这说明 `hs_expr_info_t` 的宽度是**模式自身属性**，不包含 `min_length` 这类外部约束；若据此以为「加上 min_length 就不会匹配短串」，就会误判过滤器行为。真正的约束在编译产物里生效，而不是在 info 里体现。最后的编译失败输出验证了 `expression` 在多模式场景下的定位价值，以及 `message` 只适合人读、不适合程序分支。

### 5. 速查表

速查表按「需求 → 结构 → 字段」三列组织，使用顺序是先定需求、再定结构、最后核对字段。需要强调的是，后三个结构不能跨调用复用：`hs_expr_info_t` 每次查询都会新分配，`hs_compile_error_t` 每次失败都会新分配，`hs_expr_ext_t` 虽然由调用方自己管理，但一次 `hs_compile_ext_multi` 之后即可释放。把它们缓存起来「下次接着用」，是泄漏与脏数据的两重来源；只有 `hs_platform_info_t` 是纯入参，可以复用。

| 需求 | 用哪个结构 | 关键字段 |
|---|---|---|
| 按目标机优化 | `hs_platform_info_t` | `tune`、`cpu_features` |
| 预估缓冲区大小 | `hs_expr_info_t` | `min_width`、`max_width` |
| 判断是否要等 EOD | `hs_expr_info_t` | `matches_at_eod`、`matches_only_at_eod` |
| 限制报告偏移 | `hs_expr_ext_t` | `flags`、`min_offset`、`max_offset` |
| 近似匹配 | `hs_expr_ext_t` | `edit_distance`、`hamming_distance` |
| 定位哪条模式错 | `hs_compile_error_t` | `expression` |
| 展示错误原因 | `hs_compile_error_t` | `message` |

### 6. 版本差异

四个结构的字段集合稳定，变化集中在取值域。`tune` 家族从早期的 `GENERIC` 到 `SNB`、`IVB`、`HSW`、`SLM`、`BDW`、`SKL`、`SKX`、`GLM`、`ICL`，再到 `ICX = 10`，是逐个追加的；新增家族不会让老代码失效，因为未知值会被当作 `GENERIC` 处理，但「按最新家族调优」需要升级到支持它的版本。

`cpu_features` 的变化是新增位：AVX2 与 AVX512 之后加入 AVX512VBMI，位值定义在同一文件里。`HS_PLATFORM_ALL` 的出现是为了「一次编译、到处运行」，它的值 `0xabcdef11abcdef00` 不是位或的结果，而是一个约定常量，判断时必须用相等而不是按位与。

`hs_expr_ext_t` 的五个标志位从引入以来没有变过，但「哪些组合允许编译」在不同版本间有差异，尤其是近似匹配与有界重复、SOM 的交互。升级版本后如果原本能编译的模式报 `HS_COMPILER_ERROR`，先检查是不是扩展参数组合变了，而不是模式语法变了。

`hs_expr_info_t` 的字段没变，但保守性的具体边界可能随编译器改进而变化：同一个模式在新版本上可能给出更紧的 `min_width`。因此不要把 `min_width` 当作跨版本的稳定契约，它只是「当前版本能证明的下界」。

`reserved1` / `reserved2` 的存在本身就是版本策略的一部分：它们预留了 16 字节，使得未来增加「目标缓存大小」「NUMA 偏好」这类参数时不必改变结构体大小，也就不会破坏已编译调用方的二进制兼容。使用方唯一要做的就是把它们清零，并在升级头文件后重新编译；如果代码里用了「按字段逐个赋值 + 手工 sizeof」的写法，升级时最容易漏掉新增字段。

### 7. 常见误用与调试

1. **用 `free()` 释放 `hs_compile_error_t`**。必须用 `hs_free_compile_error`，否则在自定义分配器场景下会崩溃或泄漏。
2. **忘记释放 `hs_expr_info_t`**。每次调用都会分配一块内存，循环探测几千条模式时会积累成明显泄漏。
3. **把 `hs_expression_info` 当编译预检**。它对不可编译的模式也可能返回成功，真正的判定只能用 `hs_compile`。
4. **`ext.flags` 没置位**。字段填了但 `flags` 为 0，编译器全部忽略，表现为「参数不生效」且没有任何警告。
5. **把 `cpu_features` 与 `platform` 混用**。前者肯定式、后者否定式，直接赋值会得到「所有特性都不可用」或「全部可用」的极端结果。
6. **`reserved` 字段不初始化**。局部变量未清零就传入，当前版本无害，未来版本可能被解释成新参数。
7. **按 `max_width` 分配缓冲区**。无界模式返回 `UINT_MAX`，直接分配会失败；应先判断是否等于 `UINT_MAX`。

## 05-05 RoseEngine 与 RoseContext 字段

### 1. 本篇定位与覆盖范围

`RoseEngine` 是数据库字节码的第一个结构，`hs_get_bytecode(db)` 返回的地址就是它的起点。它同时扮演三个角色：编译产物的目录（所有子表用偏移登记）、运行时的策略表（走哪条执行路径、要不要 EOD 检查、有没有 SOM）、scratch 与流状态的尺寸依据（队列数、状态大小、SOM 槽位数）。因此读 05 册如果不读这一篇，前面几篇的字段就只能孤立记忆。

本篇覆盖 `src/rose/rose_internal.h` 第 331 行到第 484 行的 `RoseEngine`（含 `RoseStateOffsets`、`RoseBoundaryReports` 两个内嵌结构）与第 113 行到第 155 行的 `RoseContext`。由于 `RoseEngine` 字段接近九十个，字段表按语义分组、同组同类型的合并成一行，但每个字段名都会出现，不遗漏。运行时如何执行、队列如何调度属于 06-06 与 07-04，本篇只讲字段如何决定「走哪条路径」。

版本基线 5.4.2。`runtimeImpl` 的三个取值与 `pickRuntimeImpl` 的判定条件来自 `src/rose/rose_build_bytecode.cpp`，是本篇最需要精确的部分。

### 3. 逐项详解

#### 3.1 九个路径字节：先看这九个，再看别的

`RoseEngine` 开头连续九个 `u8`，是编译期算好的「执行策略开关」，运行时几乎不做判断，直接读。这也是为什么它们被放在结构体最前面：与 `hs_database` 头部相邻，扫描入口可以在同一条缓存行里拿到全部策略位。

`pureLiteral` 标识「这个数据库来自纯字面量 API」（`hs_compile_lit` / `hs_compile_lit_multi`），由 `src/compiler/compiler.cpp` 第 627 行在 `build()` 里写入 `pureFlag`。它不是从图结构推导的，而是调用方选择的编译入口决定的。运行时 `pureLiteralBlockExec` 与 `pureLiteralStreamExec` 只取浮动字面量表，不跑 Rose 程序。

`noFloatingRoots` 的语义是「只有锚定表有命中时，才需要跑浮动表」。`src/rose/block.c` 第 234 行与 `stream.c` 第 629 行都有 `if (t->noFloatingRoots && !roseHasInFlightMatches(t, state, scratch))` 的提前返回，说明这个字段是纯粹的快速退出开关。它的存在意味着「没有浮动根」的数据库可以把整段浮动扫描省掉。

`requiresEodCheck` 表示「有 EOD 相关工作」，例如以 `$` 结尾的锚定、EOD 表的报告程序。它决定扫描结束时是否要再跑一遍 EOD 程序，`runtime.c` 的收尾分支里用 `switch (rose->runtimeImpl)` 配合它决定调 `rawEodExec` 还是 `soleOutfixEodExec`。注意它和 `boundary.reportEodOffset` 不是一回事：后者是「有报告要发」，前者是「有引擎要跑」。

`hasOutfixesInSmallBlock` 与小块扫描优化相关：某些 outfix 在小块里也必须执行，不能被小块专用表替代。`mpvTriggeredByLeaf` 表示 MPV 需要检查后缀/外缀才能触发。`canExhaust` 表示每个模式都有耗尽键，因此可以在 `exhaustionVector` 全置位后提前结束。`hasSom` 与 `somHorizon` 成对：前者是有没有 SOM，后者是每个槽多宽。

#### 3.2 runtimeImpl：三值的精确含义

`runtimeImpl` 是 `u8`，取值来自 `rose_internal.h` 第 310 到 312 行的三个宏：`ROSE_RUNTIME_FULL_ROSE` 为 0，`ROSE_RUNTIME_PURE_LITERAL` 为 1，`ROSE_RUNTIME_SINGLE_OUTFIX` 为 2。它在 `pickRuntimeImpl`（`rose_build_bytecode.cpp` 第 327 行）里被决定，判定顺序是：先看 `isPureFloating`，成立返回 1；再看 `isSingleOutfix`，成立返回 2；否则返回 0。

`isPureFloating` 的条件是一串否定式检查：必须有浮动表；不能有 outfix、suffix、leftfix 三类引擎；不能有 anchored 表；不能有 EOD 工作；不能有状态；不能有延时字面量；流式模式下不能有长字面量检查；不能有组检查。全部满足才返回真。换句话说，只要数据库里有一点「需要 Rose 程序介入」的东西，就会退化成完整 Rose。`isSingleOutfix` 的条件是：除起始顶点外没有角色顶点、没有 SOM 槽位、没有 EOD 边界报告、且 outfix 数量恰为 1。

这三个值的运行时映射写在 `src/runtime.c`：块模式 `switch` 分派到 `rawBlockExec`、`pureLiteralBlockExec`、`soleOutfixBlockExec`；流式模式分派到对应的 Stream 版本；EOD 收尾只允许后两者中的 `SINGLE_OUTFIX` 与 `FULL_ROSE`，`PURE_LITERAL` 在 EOD 分支里是 `assert(0)`，因为纯字面量数据库不产生 EOD 匹配。

#### 3.3 mode 与 historyRequired：两个决定「怎么扫」的字段

`mode` 是 `u32`，取值是 `HS_MODE_BLOCK`、`HS_MODE_STREAM`、`HS_MODE_VECTORED` 三者之一（注意编译时还可能带 SOM horizon 位，但写入 `RoseEngine::mode` 的是去掉 horizon 后的基础模式）。它决定状态区如何布局、扫描入口走哪条 `Exec`、以及 `hs_database_info` 打印哪个模式名。

`historyRequired` 是流式模式下需要保留的历史字节数，上界由它决定，实际历史缓冲区由 `core_info::hbuf`/`hlen` 指向。它影响两件事：流状态的大小（`stateOffsets::history` 区段的容量）与跨块匹配的正确性。值为 0 表示不需要历史，常见于纯字面量或全锚定数据库。

这两个字段有一个共同点：它们都是「编译期确定、运行期只读」，所以可以被 `hs_database_info` 之外的诊断工具安全读取，不需要加锁。

#### 3.4 key 计数与偏移：逻辑组合与去重的目录

`ekeyCount` 是耗尽键数量，对应流状态里的 `exhausted` 位图；`lkeyCount` 与 `lopCount` 是逻辑键与逻辑操作数，`logicalTreeOffset` 指向从 `lkey` 到 `LogicalOp` 的映射；`ckeyCount` 与 `combInfoMapOffset` 是组合键与组合信息表；`dkeyCount`、`dkeyLogSize`、`invDkeyOffset` 是去重键、日志大小与「去重键到外部报告 ID」的映射。

这些字段的价值在于「一张数据库里有多少个需要跨模式协调的东西」。逻辑组合（`HS_FLAG_COMBINATION`）会显著增加 `lkeyCount` 与 `lopCount`；`HS_FLAG_SINGLEMATCH` 会增加 `ekeyCount`；同一报告 ID 的多条模式会增加 `dkeyCount`。排查「开了组合之后 scratch 变大」时，先看这三个计数，再看 scratch 的对应容量字段，因果链就清楚了。

`invDkeyOffset` 的名字容易误解：它不是「反向去重」，而是「去重键 → 外部报告 ID」的反查表。名字里的 `inv` 指映射方向，不指算法。

#### 3.5 matcher 偏移与宽度：四张表加一张长字面量表

`amatcherOffset`、`ematcherOffset`、`fmatcherOffset` 分别指向锚定、EOD 锚定、浮动三张字面量匹配表；`drmatcherOffset` 指向延时重建表；`sbmatcherOffset` 指向小块专用表；`longLitTableOffset` 指向长字面量表；`smallWriteOffset` 指向小块写引擎。七个偏移全部是「相对 `RoseEngine` 起点」，为 0 表示该表不存在。

对应的访问器都是内联函数，且都做了防御性检查：`getALiteralMatcher`、`getFLiteralMatcher`、`getSBLiteralMatcher` 在偏移为 0 时返回 NULL，在偏移大于等于 `t->size` 时断言并返回 NULL。这说明「偏移合法性」在 5.4.x 被当作安全边界处理，而不是靠调用方保证。

三个 `*MinWidth` 与两个 `*MaxBiAnchoredWidth` 是「区域裁剪」的依据：只有当缓冲区剩余长度不小于最小宽度时，才值得跑对应的表；只有当已扫描长度不超过最大双锚定宽度时，锚定表才可能命中。`minWidth` 与 `minWidthExcludingBoundaries` 则是整个引擎级的最小宽度，前者在存在边界报告时会被置 0（因为 EOD 报告可能零长度），后者始终是模式本身的下界。

#### 3.6 状态尺寸：stateSize 不是 Rose 状态大小

源码在 `stateSize` 旁边写了一句警告：「size of the state bitset，WARNING: not the size of the rose state」。这句话非常重要：`stateSize` 只是角色状态位图的大小，真正的流状态总大小是 `stateOffsets.end`。同理，`anchorStateSize` 是锚定 DFA 的状态大小，`tStateSize` 是瞬态 Rose NFA 的状态大小，`scratchStateSize` 是「scratch 里为 NFA 预留的未压缩状态大小」，只用于 scratch 定容。

四者与 scratch 的对应关系是：`stateOffsets.end` → `bStateSize`（块模式）或流状态；`tStateSize` → `tStateSize`；`scratchStateSize` → `fullStateSize`；`anchorStateSize` 属于 `stateOffsets` 的一部分，不单独分配。`validateStateLayout` 会校验「每个区段都落在 `stateOffsets.end` 之内，且大小与计数一致」，这是反序列化时的关键防线。

#### 3.7 队列分段：三个边界字段

`outfixBeginQueue`、`outfixEndQueue`、`leftfixBeginQueue` 把 `queueCount` 个队列切成四段：起始到 `outfixBeginQueue` 是链式 MPV，`outfixBeginQueue` 到 `outfixEndQueue` 是外缀，`outfixEndQueue` 到 `leftfixBeginQueue` 是后缀，之后是前缀与中缀。这段注释直接写在 `rose_internal.h` 的队列分配示意里。

有了这三个边界，运行时不需要为每个队列存「类型」字段，靠下标比较就能分类。这也是「用布局代替元数据」的典型手法：省一个字节的枚举，换一次比较。调试时如果发现某个队列被当成错误类型执行，先核对这三个边界是否与 `queueCount` 自洽。

`activeArrayCount` 与 `activeLeftCount` 是活动数组的容量，`activeQueueArraySize` 是位图字节数，三者与 scratch 的 `aqa` 直接对应。

#### 3.8 RoseContext：一次扫描的游标集合

`RoseContext` 的十六个字段可以按「偏移游标」「组状态」「长字面量缓冲」分三组。偏移游标组包括 `lit_offset_adjust`、`delayLastEndOffset`、`lastEndOffset`、`lastMatchOffset`、`lastCombMatchOffset`、`minMatchOffset`、`minNonMpvMatchOffset`、`next_mpv_offset`；组状态组是 `groups` 与 `mpv_inactive`；计数与下标组是 `filledDelayedSlots` 与 `curr_qi`；长字面量组是四个 `ll_*` 字段。

`lit_offset_adjust` 只在纯字面量路径使用：`pureLiteralInitScratch` 把它设为 `offset + 1`，因为纯字面量的命中偏移是「字面量末尾 + 1」的相对值，需要加一修正。`lastMatchOffset` 的注释明确写着「used only for debugging, asserts」，说明它不参与匹配逻辑，不要拿它做业务判断。

`minMatchOffset` 与 `minNonMpvMatchOffset` 是「报告裁剪」的两个水位：前者约束所有引擎，后者只约束非 MPV 引擎。它们的存在是为了保证报告顺序，把「还不能报告的偏移」压住。`next_mpv_offset` 则是 MPV 的下一次可报告位置，顶层事件到达时会被清零。

`ll_buf`/`ll_len` 与 `ll_buf_nocase`/`ll_len_nocase` 只在流式模式使用：跨块时长字面量表把哈希结果存进流状态，下一块开始时用这个缓冲还原前缀字符串。它们指向的是字节码里的常量字符串，不是 scratch 里的副本，所以不要试图写入。

#### 3.9 三条路径：字段如何决定执行分支

第一条是**纯字面量路径**。条件是编译入口为 `hs_compile_lit*`，`pureLiteral` 被置 1，同时 `runtimeImpl` 通常为 `ROSE_RUNTIME_PURE_LITERAL`。运行时走 `pureLiteralBlockExec` / `pureLiteralStreamExec`，只调用 `getFLiteralMatcher` 拿到浮动表，再 `hwlmExec` 扫一遍，没有任何 Rose 程序、没有 NFA 队列、没有 EOD 阶段。这条路径最快，但能力被严格限制：只支持 `CASELESS`、`SINGLEMATCH`、`SOM_LEFTMOST` 三个标志，不支持扩展参数。

第二条是**只跑 floating 表**。条件是 `pureLiteral` 为 0，但 `runtimeImpl` 为 `ROSE_RUNTIME_PURE_LITERAL`，也就是 `isPureFloating` 的那串否定检查全部通过（有浮动表，且无外缀/后缀/前缀引擎、无锚定、无 EOD、无状态、无延时、流式无长字面量、无组检查）。它同样走 `pureLiteralBlockExec` 这个分支，但因为 `pureLiteral` 为 0，报告路径会经过完整的 `roseCallback`（`src/rose/match.c` 第 241 行与第 623 行都有 `if (t->pureLiteral)` 的分支），从而支持报告 ID、去重、组掩码等语义。它与第一条的差别不在「跑什么表」，而在「命中之后怎么处理」。

第三条是**完整 Rose**。条件是 `runtimeImpl` 为 0，或者为 2（单 outfix，属于「最小 Rose」的特例）。此时块模式走 `rawBlockExec`，流式走 `rawStreamExec`，内部再按 `noFloatingRoots` 决定是否跳过浮动表、按 `requiresEodCheck` 决定收尾是否跑 EOD 程序、按 `hasSom` 决定是否刷新 SOM 存储。`canExhaust` 为真时还可以在耗尽后提前结束，`hasOutfixesInSmallBlock` 决定小块路径是否要额外跑 outfix。

### 4. 典型示例

下面的示例从数据库里读出 `RoseEngine` 的策略字段并打印。它使用了内部头 `rose/rose_internal.h`，只能用于诊断工具；产品代码没有可移植的方式访问这些字段。

```cpp
#include "database.h"
#include "rose/rose_internal.h"
#include <hs.h>
#include <cstdio>

int main() {
    hs_database_t *db = nullptr;
    hs_compile_error_t *err = nullptr;
    if (hs_compile("foo[0-9]{2}bar", HS_FLAG_SOM_LEFTMOST,
                   HS_MODE_BLOCK | HS_MODE_SOM_HORIZON_LARGE,
                   nullptr, &db, &err) != HS_SUCCESS) {
        std::printf("compile failed: %s\n", err->message);
        hs_free_compile_error(err);
        return 1;
    }

    const RoseEngine *rose =
        static_cast<const RoseEngine *>(hs_get_bytecode(db));
    std::printf("mode=%u pureLiteral=%u runtimeImpl=%u\n",
                rose->mode, rose->pureLiteral, rose->runtimeImpl);
    std::printf("hasSom=%u somHorizon=%u canExhaust=%u\n",
                rose->hasSom, rose->somHorizon, rose->canExhaust);
    std::printf("historyRequired=%u queueCount=%u ekeyCount=%u\n",
                rose->historyRequired, rose->queueCount, rose->ekeyCount);
    std::printf("state.end=%u size=%u minWidth=%u\n",
                rose->stateOffsets.end, rose->size, rose->minWidth);
    std::printf("fmatcherOffset=%u amatcherOffset=%u\n",
                rose->fmatcherOffset, rose->amatcherOffset);

    hs_free_database(db);
    return 0;
}
```

示例输出如下（示例输出，具体格式需对照实际版本核验）。具体数值与模式、版本强相关，判读看关系不看绝对值。

```text
mode=1 pureLiteral=0 runtimeImpl=0
hasSom=1 somHorizon=8 canExhaust=0
historyRequired=0 queueCount=4 ekeyCount=0
state.end=96 size=2048 minWidth=7
fmatcherOffset=1024 amatcherOffset=0
```

判读分四点。第一，`mode=1` 对应 `HS_MODE_BLOCK`，`pureLiteral=0` 说明不是纯字面量入口，`runtimeImpl=0` 说明走完整 Rose —— 因为有 SOM，`isPureFloating` 的「无状态」条件不满足，退化成完整路径，这与预期一致。第二，`hasSom=1` 与 `somHorizon=8` 同时出现，说明 SOM 已开启且每槽 8 字节，对应 `HS_MODE_SOM_HORIZON_LARGE`；若换成 `SMALL`，这个值会变小，但 `somLocationCount` 不变，这就是 05-03 里强调的「两个增长不要混为一谈」。第三，`amatcherOffset=0` 表示没有锚定表，`fmatcherOffset=1024` 表示浮动表存在，这解释了为什么该模式不能走纯浮动路径：`isPureFloating` 还要求「无状态」，而 SOM 就是状态。第四，`minWidth=7` 与模式 `foo[0-9]{2}bar` 的 3+2+3 完全吻合，说明 `minWidth` 是精确下界；`size=2048` 是引擎镜像大小，与 `hs_database::length` 相等，可用它交叉验证数据库头有没有被改。

### 5. 速查表

| 想确认的事 | 字段 | 判读 |
|---|---|---|
| 为什么没走快速路径 | `runtimeImpl` | 0 即完整 Rose |
| 是否纯字面量 API 编译 | `pureLiteral` | 1 表示只跑浮动表且无 Rose 程序 |
| 是否开了 SOM | `hasSom`、`somHorizon` | 前者开关，后者槽宽 |
| 流式要留多少历史 | `historyRequired` | 0 表示不需要历史 |
| scratch 为什么大 | `queueCount`、`stateOffsets.end` | 队列与状态区 |
| 报告为什么被压住 | `RoseContext::minMatchOffset` | 报告水位 |
| 是否有 EOD 收尾 | `requiresEodCheck` | 决定收尾是否跑 EOD 程序 |
| 锚定表是否存在 | `amatcherOffset` | 0 表示不存在 |

### 6. 版本差异

`RoseEngine` 是内部结构，字段随版本增删，且没有 ABI 承诺。5.4.0 引入 Sheng 系列与 Fat Teddy 后，`runtimeImpl` 的判定条件与相关资源统计发生变化，同一个模式集在新版本上可能从「纯浮动」退化为「完整 Rose」，表现为 `hs_dump` 输出变化与 scratch 变大。5.4.1 的 bugfix 可能调整 `isPureFloating` 的边界条件，5.4.2 则涉及 scratch 行为。

`hasSom`、`somLocationCount`、`somHorizon`、`somRevCount` 这几个字段随 SOM 功能一起演进；早期版本没有 SOM 时这些字段不存在或恒为 0，因此按偏移硬读 `RoseEngine` 的代码在跨版本时必然失效。`handledKeyCount`、`handledKeyFatbitSize` 属于较新的角色管理字段，老版本没有。

还有一个隐蔽的变化点：`RoseStateOffsets` 的区段数量在版本间可能增加（例如长字面量状态、SOM 有效性位图），新增区段会改变 `end` 的值，从而改变流状态与 scratch 大小，但字段名不变。这类变化只能通过 `validateStateLayout` 的校验逻辑或 `hsdump` 输出对比发现，不能靠字段表判断。

因此对本篇的正确态度是：字段名可用于理解与诊断，但**不要**在生产代码里按偏移访问 `RoseEngine`；跨版本比对时以 `hsdump` 的结构化输出为准，而不是自己解析字节。

### 7. 常见误用与调试

1. **把 `stateSize` 当流状态大小**。源码注释已警告它不是 Rose 状态大小，真正的总大小是 `stateOffsets.end`。
2. **假设 `runtimeImpl` 只由模式决定**。它还受编译入口、流式/块模式、长字面量、组检查影响，同一模式在不同模式下可能不同。
3. **把 `pureLiteral` 与「纯浮动」混为一谈**。前者是编译入口标志，后者是资源判定结果；两者都为 1 才是纯字面量路径。
4. **用 `lastMatchOffset` 做业务判断**。注释写明它只用于调试与断言。
5. **按偏移硬读 `RoseEngine`**。内部结构无 ABI 承诺，升级即失效；用 `hsdump` 或本篇的字段名做人工核对。
6. **忽略 `noFloatingRoots` 的提前退出**。调试「浮动表没跑」时，先确认锚定表是否有命中，而不是怀疑浮动表损坏。
7. **把 `somHorizon` 当槽位数**。它是槽宽，槽位数是 `somLocationCount`；两者混用会得出错误的容量估算。

（字段见 05-05 ｜ 参数见 04-02 ｜ 原理见 06-10 ｜ 模块见 07-04）

## 05-06 LimEx NFA、Castle 与状态结构字段

### 1. 本篇定位与覆盖范围

NFA 是 Rose 分解之后真正逐字节推进的状态机，也是理解「为什么某些模式快、某些模式慢」的最后一块拼图。本篇只回答字段问题：每个字段叫什么、多宽、在编译期还是运行期被写、被哪个函数读取。至于 NFA 的指令循环怎么走、异常状态如何批量处理、城堡引擎如何共享字符可达性，全部属于机制，见 06-06 与 06-07 两篇，本篇不展开。

覆盖范围分四组。第一组是全体引擎共用的头部 `struct NFA`，定义在 `src/nfa/nfa_internal.h` 第 97 行，所有 LimEx、Castle、Sheng、McClellan、Tamarama 都以它为前缀，因此它的字段是唯一可以「不判断引擎类型就安全读取」的部分。第二组是 LimEx 家族，`src/nfa/limex_internal.h` 用 `CREATE_NFA_LIMEX(size)` 宏展开出 32、64、128、256、384、512 六种宽度，每种都由「定长参数区 + 变长段」组成。第三组是 LimEx 的附属结构：异常状态 `NFAException##size`、重复信息 `NFARepeatInfo`、接受项 `NFAAccept`。第四组是 Castle 与它的子引擎 `SubCastle`，以及运行期上下文 `NFAContext##nsize`。

有一个事实必须先核验清楚，否则后面全会读错：本轮 5.4.2 快照里**不存在**名为 `NFAStateInfo` 的结构体。在整个 `src/` 目录检索该标识符没有任何命中。历史资料与部分第三方笔记中的 `NFAStateInfo`，实际指「状态位图 + 接受信息 + 加速信息」这一组概念的统称，在今天的代码里被拆成三处：`struct NFA` 头部的尺寸与位置字段、`LimExNFA##size` 里的位掩码族、以及 DFA 路径上的 `struct mstate_aux`（`src/nfa/mcclellan_internal.h:68`，含 `accept`、`accept_eod`、`top`、`accel_offset`）。看到旧图里画着 `NFAStateInfo`，请按这三处对照，不要去源码里找一个不存在的类型。

还有一对概念必须从字段层面就分开：**scratch 态与流态**。`struct NFA` 里同时有 `scratchStateSize` 与 `streamStateSize`，前者的注释明确写着「不持久化于流写入之间」，后者写着「必须在流写入之间持久化」。同一个引擎在块模式下几乎只用前者，在流模式下两者都要用，而流态还要再经过 `LIMEX_FLAG_COMPRESS_STATE` 决定是否压缩存放。把这两个尺寸混用，是本篇范围内最常见、也最难查的一类错误。

### 3. 逐项详解

#### 3.1 公共头：先判类型，再谈字段

`struct NFA` 最容易被误用的是「以为字段都通用」。事实上除了这 14 个字段，后续内容完全由 `type` 决定：`type` 落在 0 到 5 之间才是 LimEx，落在 6 以后是 McClellan、Gough、MPV、LBR、Castle、Sheng、Tamarama 等「magic pseudo nfa」。`getImplNfa(nfa)` 只是把指针前移 `sizeof(struct NFA)`，它不做任何类型检查，所以把 Castle 的实现区当 LimEx 读，得到的是完全无关的比特。

`type` 的取值顺序由 `enum NFAEngineType` 固定，新增引擎只能追加在 `INVALID_NFA` 之前，这是 ABI 层面的硬约束。判断宏也因此分成两族：`isNfaType` 只认六个 LimEx，`isDfaType` 认 McClellan、Gough、Sheng、McSheng，`isMultiTopType` 则是「既不是 DFA 也不是 LBR」的补集判断。写诊断代码时优先用这些宏，不要自己写数值比较。

`length` 是整段引擎的字节数，与 `hs_database` 的 `length` 不是一个层级：前者只覆盖一个引擎，后者覆盖整个数据库。`length` 在反序列化时是越界校验的上界，所以它一旦被写坏，表现通常是 `HS_INVALID` 而不是崩溃。

`queueIndex` 是连接编译产物与 scratch 的唯一纽带。每个需要队列执行的引擎在 scratch 的 `queues` 数组里占一个 `mq`，下标就是 `queueIndex`；`NfaInfo::stateOffset` 则告诉运行时这个引擎的状态放在流状态的哪个位置。两者一个管「队列」、一个管「状态」，不能互换。

#### 3.2 三种尺寸：scratchStateSize、streamStateSize、stateSize

这三个字段经常被混为一谈，但它们的服务对象完全不同。`struct NFA::scratchStateSize` 是「临时状态」的大小，注释写得很明确：这块状态不进入流状态，也不在两次流写入之间保留。`struct NFA::streamStateSize` 是「必须跨流写入保留」的大小，流式模式下 `hs_stream` 的尾部会按这个值预留。`LimExNFA##size::stateSize` 则是引擎视角的「传统状态位图字节数」，注释补了一句「不含扩展历史」。

三者关系可以这样记：`stateSize` 描述位图本身，`streamStateSize` 描述「位图压缩后 + 扩展状态」要占多少流空间，`scratchStateSize` 描述「不压缩、可丢弃」的那份副本要多大。块模式下 `streamStateSize` 常见为 0，这不是异常；只有流式模式才会出现非零值。看到块模式数据库里 `streamStateSize` 非零，反而要怀疑是不是编译时用了错误的模式位。

#### 3.3 reachMap 与 reachSize：字符压缩的第一层

`reachMap` 是一个 256 项的字节数组（`N_CHARS` 在 `ue2common.h:173` 定义为 256），把输入字节映射成「reach 掩码行号」。`reachSize` 是行数，等于不同字符类的个数。这个设计的意义是把「逐字符判断属于哪个类」变成一次数组查表，再用行号去取一行状态位图。

读这个字段要注意两点。第一，`reachMap` 里存的是**行下标**，不是掩码本身，也不是「该字符是否可达」的布尔值；把 0 当成「不可达」是错的，0 只是第 0 行的下标。第二，`reachSize` 小不代表引擎简单，它只说明字符类被压得紧凑；真正决定状态规模的是 `stateSize` 与引擎位宽。

#### 3.4 位掩码族：一条掩码一个语义

`init` 与 `initDS` 的差别只在起点语义：`init` 对应锚定起点，`initDS` 对应「dotstar 起点」。两者分开存放，是因为同一个引擎可能同时服务锚定与浮动两种触发方式，装载时必须按触发方式选一条。

`accept` 与 `acceptAtEOD` 的差别在时机：前者在任意位置命中即可报告，后者只在流结束或块结束的 EOD 事件上报告。`$` 锚定的模式就落在后者。把两者合并会导致 `$` 模式提前报告，这是语义错误而不是性能问题。

`accel`、`accelPermute`、`accelCompare`、`accel_and_friends` 是一组：前三者描述「哪些状态可以走 SIMD 加速、用什么掩码」，后者是「加速状态加上它们的可能后继」。`accel_and_friends` 的存在是为了在加速段退出时能安全判断「是否还需要回退到逐字节路径」，它必须比 `accel` 更宽。

`compressMask` 只在流态压缩时使用，语义是「压缩前必须关闭的状态」；`exceptionMask` 标记异常状态；`repeatCyclicMask` 标记循环态（含 tug 状态）；`zombieMask` 用于判断引擎是否已进入「不可能再产生新匹配」的僵尸态。四者都是掩码，但服务的事件完全不同，不能互相替代。

#### 3.5 shift 与 shiftCount：位宽不够时的位移补齐

LimEx 的位宽是 32 到 512，但一个状态可能需要「看前面若干个字节」。做法是用 `shift[]` 保存若干组位移后的历史状态，`shiftAmount[]` 给出每组位移的字节数，`shiftCount` 给出实际组数。上限由 `MAX_SHIFT_COUNT`（8）与 `MAX_SHIFT_AMOUNT`（16）固定。

`shiftCount` 为 0 是合法值，表示不需要位移历史，此时 `shift[]` 与 `shiftAmount[]` 的内容无意义，不应读取。这一点在写 dump 工具时特别容易踩：直接遍历 8 组打印，会把未初始化区当成有效数据。

#### 3.6 accept、squash 与 NFARepeatInfo

`NFAAccept` 只有三个字段：`single_report`、`reports`、`squash`。`single_report` 为真时 `reports` 直接就是报告 id；为假时 `reports` 是「报告 id 列表」的偏移，列表以 `MO_INVALID_IDX` 结尾。`squash` 是压制掩码区的偏移，同样允许 `MO_INVALID_IDX`。这三个字段的组合决定了「一次命中报几个 id、要不要压制后续」。

`NFARepeatInfo` 描述一个有界重复：`cyclicState` 是循环态下标，`ctrlIndex` 是控制块下标，`packedCtrlOffset` 是打包控制块在流态中的偏移，`stateOffset` 是重复状态在流态中的偏移，`stateSize` 是这个重复占用的打包流态总字节，`tugMaskOffset` 是 tug 掩码相对本结构的偏移。注意最后一项的基准是 `NFARepeatInfo` 自身，不是 LimEx 起点，这是本结构里唯一的例外。

`RepeatInfo`（`src/nfa/repeat_internal.h:106`）描述参数侧：`type`、`repeatMin`、`repeatMax`（无界为 `REPEAT_INF`）、`horizon`、`packedCtrlSize`、`stateSize`、`minPeriod`、`packedFieldSizes[2]`、`patchCount`、`patchSize`、`encodingSize`、`length`、`patchesOffset`。两个 `stateSize` 同名不同义：`NFARepeatInfo::stateSize` 是这个重复实例的总打包大小，`RepeatInfo::stateSize` 是重复状态块的字节数，二者相等与否取决于是否有附加表。

#### 3.7 Castle 的活跃位图与状态布局

Castle 的流状态不是「每个子引擎一段」这么简单。字段注释给出的布局是：先是若干互斥组的「活跃子引擎 id」，然后是「非互斥子引擎的活跃多位图」（若全是互斥则省略），再是「互斥组活跃多位图」，最后才是各组共享的状态池与各非互斥子引擎的状态。`activeIdxSize` 决定 id 用几个字节，`activeOffset` 指向非互斥位图，`staleIterOffset` 指向检查陈旧子引擎的稀疏迭代器，`groupIterOffset` 指向组存活迭代器。

`exclusive` 的三态（`NOT_EXCLUSIVE`、`EXCLUSIVE`、`PURE_EXCLUSIVE`）直接改变布局：纯互斥时连「活跃重复位图」都不存，只存每组一个 id。这意味着同一份 Castle 代码在不同 `exclusive` 取值下，状态偏移完全不同，任何按固定偏移读状态的诊断代码都必须先读这个字段。

`SubCastle::exclusiveId` 有一个反直觉约定：不属于任何互斥组时，它被设成「Castle 中子引擎总数」，而不是 0 或 `MO_INVALID_IDX`。因此判断「是否互斥」要用 `exclusiveId < numRepeats`，不能判空。

#### 3.8 运行期上下文与 scratch fullState 的对应

`NFAContext##nsize`（`src/nfa/limex_context.h:52`）是运行期栈上的上下文，字段包括 `s`（进出状态位图）、`local_succ`（异常处理用的后继）、`cached_estate` 与 `cached_esucc`（异常缓存）、`cached_br`（缓存是否含 br 状态）、`cached_reports`、`repeat_ctrl`、`repeat_state`、`callback`、`context`。它的大小随平台变化，所以注释明确要求「不要把它的尺寸写进字节码」。

`scratch->fullState` 则是「未压缩 NFA 状态」的落脚点，`NfaInfo::fullStateOffset` 给出每个引擎在其中的偏移。运行时先把流态展开到 `fullState`，跑完再压缩回去。字段层面的对应关系是：`struct NFA::streamStateSize` 决定流态大小，`scratch->fullStateSize` 决定展开区大小，两者不一定相等，因为展开区按未压缩位图计。

（字段见 05-06 ｜ 参数见 04-03 ｜ 原理见 06-06 ｜ 模块见 07-05）

### 4. 典型示例

下面这段诊断代码遍历数据库中的每个 NFA，打印公共头与 LimEx 专有字段。它只用于研究与排障，产品代码不应包含内部头文件。

```c
#include "database.h"
#include "rose/rose_internal.h"
#include "nfa/nfa_internal.h"
#include "nfa/limex_internal.h"
#include <hs.h>
#include <stdio.h>

int main(void) {
    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;
    if (hs_compile("foo[0-9]{3}bar", HS_FLAG_CASELESS, HS_MODE_STREAM,
                   NULL, &db, &err) != HS_SUCCESS) {
        printf("compile failed: %s\n", err->message);
        hs_free_compile_error(err);
        return 1;
    }

    const struct RoseEngine *rose = hs_get_bytecode(db);
    printf("queueCount=%u historyRequired=%u\n",
           rose->queueCount, rose->historyRequired);

    for (u32 qi = 0; qi < rose->queueCount; qi++) {
        const struct NFA *nfa = getNfaByQueue(rose, qi);
        if (!nfa) {
            continue;
        }
        printf("q%u type=%u len=%u scratch=%u stream=%u min=%u max=%u\n",
               qi, nfa->type, nfa->length, nfa->scratchStateSize,
               nfa->streamStateSize, nfa->minWidth, nfa->maxWidth);
        if (!isNfaType(nfa->type)) {
            printf("  not a limex engine, impl layout differs\n");
            continue;
        }
        if (nfa->type != LIMEX_NFA_64) {
            printf("  limex width is not 64, skip width-specific fields\n");
            continue;
        }
        const struct LimExNFA64 *l64 = getImplNfa(nfa);
        printf("  limex64 reach=%u accept=%u eod=%u exc=%u repeat=%u shift=%u\n",
               l64->reachSize, l64->acceptCount, l64->acceptEodCount,
               l64->exceptionCount, l64->repeatCount, l64->shiftCount);
        printf("  stateSize=%u flags=0x%x queueIndex=%u\n",
               l64->stateSize, l64->flags, nfa->queueIndex);
    }

    hs_free_database(db);
    return 0;
}
```

示例输出如下（示例输出，具体格式需对照实际版本核验）。

```text
queueCount=2 historyRequired=64
q0 type=1 len=1888 scratch=64 stream=16 min=10 max=10
  limex64 reach=9 accept=1 eod=0 exc=2 repeat=1 shift=0
  stateSize=8 flags=0x1 queueIndex=0
q1 type=1 len=1216 scratch=64 stream=8 min=3 max=3
  limex64 reach=4 accept=1 eod=0 exc=0 repeat=0 shift=1
  stateSize=8 flags=0x1 queueIndex=1
```

逐行判读。第一行说明这个数据库需要 2 个队列，`historyRequired` 为 64 字节，意味着流式模式下每个流至少要保留 64 字节历史，否则跨块匹配会漏；若你看到它突然变成几 KB，通常是模式里出现了长有界重复或 `.*` 前缀。`q0` 的 `min=10 max=10` 与模式 `foo[0-9]{3}bar` 的固定宽度 10 一致，这是最健康的情况：定宽模式不需要处理变宽窗口；两个值不相等且 `max=0` 表示无界，此时运行时会做窗口裁剪。`stream=16` 而非 0，证明这是流式数据库；块模式下这里应为 0。`reach=9` 表示字符类被压成 9 行，`exc=2` 表示有 2 个异常状态（通常来自重复计数器或分支），`repeat=1` 对应 `{3}`。`shift=0` 说明 64 位宽度足够、不需要位移历史；`q1` 的 `shift=1` 说明它需要一组位移，这通常出现在含 `.*` 或宽字符类的浮动模式上。`stateSize=8` 是 64 位引擎的状态位图字节数，与位宽一致；如果位宽换成 256，`stateSize` 会变成 32 且各掩码字段的宽度也随 `LIMEX_NFA_256` 变化，因此示例只展开 64 位这一种，其他宽度必须换用对应类型读取。最后一行 `flags=0x1` 表示 `NFA_ACCEPTS_EOD`，即该引擎会在 EOD 时检查接受状态；若模式不含 `$` 却出现这一位，多半是 Rose 的补匹配需要，而不是语法问题。

### 6. 版本差异

`LimExNFA##size` 的六个宽度（32/64/128/256/384/512）在 5.x 系列内保持稳定，`CREATE_NFA_LIMEX` 宏的字段顺序也没有变动，因此按偏移读旧库在新版本上通常仍然成立。真正会变的是 `enum NFAEngineType` 的尾部：5.4.0 追加了 `SHENG_NFA_32`、`SHENG_NFA_64`、`MCSHENG_64_NFA_8`、`MCSHENG_64_NFA_16`，这些值排在 `TAMARAMA_NFA` 之后、`INVALID_NFA` 之前。任何把 `type` 与固定数值比较的代码，在 5.4 之后都可能误判。

`struct NFA` 头部字段本身没有增删，但反序列化路径上的校验变严了。本快照里 `getNfaInfoByQueue` 与 `getNfaByInfo` 都带越界检查（`nfaInfoOffset + (qi+1)*sizeof(NfaInfo) > t->size` 即返回 `NULL`）。这意味着「伪造偏移也能读出东西」的写法在本版本会直接拿到空指针；更早版本是否具备同等检查**需对照实际版本核验**，不要假设所有版本行为一致。

Castle 的文件版权年份为 2015-2016，结构体字段很少；`activeIdxSize`、`staleIterOffset`、`groupIterOffset` 三件套在本快照中存在，旧资料里可能只看到 `activeOffset` 与 `numRepeats`。哪些字段是后期补上的**需对照实际版本核验**，不要把旧图的字段清单当成当前定义。`SubCastle::exclusiveId` 的「等于子引擎数表示非互斥」约定也属于后期补充，早期实现用的是别的哨兵值。

最后是分支差异：Vectorscan 对 LimEx 的位宽支持矩阵与上游不完全一致，某些宽度在 ARM 上可能被映射到别的实现。本篇所有字段结论只对 Intel 上游 5.4.2 快照成立，跨分支比对时**需对照实际版本核验**。

### 7. 常见误用与调试

1. **把 `stateSize` 当流状态大小**。`stateSize` 只是位图字节数，流状态还要加上重复控制块、扩展状态与压缩头。用 `stateSize` 去 `malloc` 流缓冲区，结果是越界写，且往往在第二个块才崩。
2. **块模式看到 `streamStateSize == 0` 就以为字段没填**。这是正常值；块模式不需要持久化。反过来，块模式看到非零才要查编译模式位。
3. **把 `reachMap` 当布尔表**。它存的是行下标，0 是合法行号。用 `if (reachMap[c])` 判断可达，会把第 0 行的所有字符误判为不可达。
4. **对非 LimEx 引擎调用 `getImplNfa` 并强转**。`getImplNfa` 只做指针偏移，不校验类型。Castle、Sheng、Tamarama 的实现区布局完全不同，强转后读到的 `reachSize` 是垃圾值，通常表现为 dump 工具打印出天文数字。
5. **遍历 `shift[8]` 全量打印**。只有前 `shiftCount` 组有效，其余是未初始化区。正确写法是先读 `shiftCount` 再循环。
6. **假设 `tugMaskOffset` 相对 LimEx 起点**。它相对 `NFARepeatInfo` 起点，是本结构唯一的例外；按 LimEx 基准加偏移会读到别的重复结构里去。
7. **用 `exclusiveId == 0` 判断「非互斥」**。约定是「等于子引擎总数」，0 反而是一个合法的组号。

调试建议：先用 `hsdump` 看引擎类型与长度，再用本篇示例代码打印头部；两者对不上时，优先怀疑头文件与库版本不一致，而不是字段读错。若 `type` 落在 6 以后却按 LimEx 解析，dump 的长度字段会明显大于数据库总长，这是最直接的异常特征。

（字段见 05-05 ｜ 参数见 04-03 ｜ 原理见 06-07 ｜ 模块见 07-05）

## 05-07 FDR / Teddy / HWLM 字面量引擎结构字段

### 1. 本篇定位与覆盖范围

字面量前端是 Hyperscan 吞吐的主要来源：Rose 把模式拆出可被字面量触发的部分之后，真正在数据流上跑的往往是 FDR 或 Teddy，而不是 NFA。本篇覆盖这条链路上的全部结构：外层包装 `struct HWLM`、FDR 主结构 `struct FDR`、Teddy 的兼容前缀 `struct Teddy`、确认阶段的 `struct FDRConfirm` 与 `struct LitInfo`、洪水检测的 `struct FDRFlood`、运行期参数 `struct FDR_Runtime_Args`、Noodle 的 `struct noodTable`、编译期字面量 `struct hwlmLiteral`，以及 scratch 上的两个确认字段。

必须先纠正一个流传很广的说法：FDR 里**没有**名为 `struct bucket` 的结构体。在整个 `src/fdr/` 目录检索不到这个类型。所谓 bucket 是「表项中的一个比特位」：FDR 的主表是一个 `u64a` 数组，每个表项 64 位，第 i 位对应第 i 个 bucket。`BucketIndex`、`PositionInBucket`、`SchemeBitIndex` 这些 `typedef` 在 `src/fdr/fdr_compile_internal.h` 里明确注明「主要用于文档目的」，它们不是结构体。把 bucket 当成独立对象去源码里找，会一无所获。

第二个容易混的点是「Teddy 是不是另一套结构」。不是。`src/fdr/teddy_internal.h` 的注释写得很直白：`struct Teddy` 的前六个字段「与 FDR 兼容」，因此运行期可以安全地把 Teddy 指针按 FDR 前缀读取，只在取掩码表时才按 Teddy 布局继续往后走。Teddy 与 Fat Teddy 的差别不在头部，而在后续掩码表的份数：普通 Teddy 只有 bucket 0..7 一份强化掩码表，Fat Teddy 有 0..7 与 8..15 两份。

第三个数清楚：`hwlmLiteral` 是**编译期**对象（C++ 结构，位于 `src/hwlm/hwlm_literal.h`），不会进入数据库；`struct HWLM` 与 `struct FDR` 是**字节码**对象；`FDR_Runtime_Args` 是**栈上**参数；`scratch->fdr_conf` 是**每次扫描**的临时落脚点。四者不要混为一谈。

### 3. 逐项详解

#### 3.1 HWLM 头部：两个加速器不是备份关系

`accel1` 与 `accel0` 常被误解为「主备加速器」。实际语义是「按组掩码选择」：当本次扫描的组掩码是 `accel1_groups` 的子集时，用 `accel1`；否则退回 `accel0`。这个设计让同一个字面量表可以服务多组模式，而加速器只对「当前开启的组」有效。

`type` 只有两个合法值，12 与 16。这两个数字是宏而不是枚举，因此不会随编译选项变化；但如果将来新增引擎，`HWLM_C_DATA(p)` 的偏移会随之改变，因为它按 `ROUNDUP_CL(sizeof(struct HWLM))` 计算引擎起点。任何硬编码「头部 40 字节」的代码都会失效。

#### 3.2 FDR 主表：domain 与 stride 决定一切

`domain` 是「用多少位做索引」，断言要求它大于 8 且小于 16，也就是主表项数在 512 到 32768 之间。`domainMask` 是 `(1 << domain) - 1` 的预计算值，运行期直接用它做与运算。`tabSize` 是主表字节数，等于表项数乘以 8（每项一个 `u64a`）。

`stride` 只能是 1、2、4，对应主循环里三个不同的取数函数。它表示「每次前进多少字节再查表」，值越大吞吐越高但需要更长的历史窗口来补齐。`stride` 与 `maxStringLen` 共同决定流式模式下的历史需求：`stride` 越大，回看越远。

`start` 是偏移 0 处的初始状态，类型是 `m128` 而不是 `u64a`。原因是 FDR 的主循环一次处理 16 字节、产生两个 `u64a` 确认值，状态必须能覆盖两段。初始状态按「各 bucket 的最短长度」预先置位，目的是减少无意义的确认调用，这个细节在排障时很重要：`start` 被写坏会导致「明明有匹配却不上报」，而不是崩溃。

#### 3.3 表项与 bucket：一位一桶

主表每个 `u64a` 表项含 64 个比特，第 i 位就是第 i 个 bucket。运行时先算索引，取出 8 字节，再用 `ctz` 类指令逐位取出置位的桶，然后按 `confOffset + bucketIndex * sizeof(u32)` 找到该桶的确认项偏移。`FDRConfirm` 不是定长数组元素，而是一段「头部 + 字面量索引数组 + LitInfo 列表」的复合区，因此 `confOffset` 指向的是 `u32` 偏移表，而不是 `FDRConfirm` 数组本身。

这张图解释了两个常见疑问：为什么「桶数」等于「表项位数」而不是独立数组长度；为什么 `confOffset` 是一层偏移表而不是结构体数组。把这两个问题想清楚，读 `fdr_confirm_runtime.h` 的 `confWithBit` 就不会被三层指针绕晕。

这个「偏移的偏移」结构是 FDR 最容易读错的地方。`getConfirmLitIndex(fdrc)` 返回的是「字面量索引数组」的起点，它按 `ROUNDUP_N(sizeof(*fdrc), alignof(u32))` 对齐到 `fdrc` 之后；数组元素是相对 `fdrc` 起点的字节偏移，指向 `LitInfo`。也就是说，从比特位到 `LitInfo` 要经过三次跳转：比特 → 桶 → 索引数组 → 字面量。任何一次基准搞错，读到的都是别的桶的字面量。

`FDRConfirm` 的四个字段各司其职：`andmsk` 与 `mult` 用于把「尾部若干字节」折叠成一个 0 到 `2^nBits-1` 的索引，`nBits` 就是这个索引的位数，`groups` 是整个确认项共享的组掩码。索引为 0 的槽位被约定为「空」，`confWithBit` 里 `if (likely(!start)) return;` 就是这个约定的直接体现。因此如果某个桶的哈希恰好把真实字面量落到了索引 0，编译期必须把它挪到别的槽位；这也是「确认表尾部总会留一点余量」的原因。读这段逻辑时不要以为索引 0 是「第一个字面量」，它是哨兵。

`LitInfo::next` 不是指针而是「续接量」，注释写明它「要么是 0，要么是一个 adjust 值」。运行期用 `oldNext = li->next; li++;` 的方式前进，这意味着同一哈希桶里的多个字面量在内存中是连续存放的，`next` 只用来标记「还有没有下一个」。这也是为什么 `LitInfo` 后面紧跟可变长字符串前缀：长字面量需要把超出 8 字节的部分存在结构之后。

`LitInfo` 的 `v` 与 `msk` 是一对掩码比较值，比较的是「命中位置往前 `size` 个字节」的那段尾部，而不是整个字面量。`size` 字段同时承担两个职责：它既是对外报告的「字面量长度」，也是回看起点的计算依据（`buf + i - li->size + 1`）。当回看越过缓冲区头部时，代码会去查 `len_history`；历史不够就放弃这个候选，这就是流式模式下「历史长度必须覆盖最长字面量」的字段级依据。`flags` 目前只定义了一个位 `FDR_LIT_FLAG_NOREPEAT`，含义是「连续命中同一 id 时只报一次」，它与 `scratch` 里的 `last_match` 配合，避免同一位置反复上报。

#### 3.4 洪水路径：FDRFlood 的 16 个 id 上限

当输入出现「同一个字符反复出现」的洪水场景时，逐位确认会退化成大量无效工作。`FDRFlood` 就是为这种情况准备的快速通道：`allGroups` 是所有组或在一起的结果，`suffix` 是后缀长度，`ids[16]` 与 `groups[16]` 是最多 16 个可直接上报的 id。`idCount` 超过 16 时，编译器干脆不为这个桶生成洪水路径，运行期继续走普通确认。

字段层面要注意 `idCount` 是 `u16` 而不是 `u32`，`ids` 数组是定长 16。任何按 `idCount` 遍历的代码都必须先确认它不超过 `FDR_FLOOD_MAX_IDS`，否则会越界读。正常情况下编译器保证这一点，但反序列化伪造的数据库不一定。

#### 3.5 Teddy：兼容前缀与两份掩码表

`struct Teddy` 只有六个 `u32`：`engineID`、`size`、`maxStringLen`、`numStrings`、`confOffset`、`floodOffset`。这与 `struct FDR` 的前六个字段完全同序同宽，所以运行期可以先用 FDR 前缀读到 `confOffset`，再按 Teddy 自己的掩码表布局继续。Teddy 的掩码表紧跟在头部之后，随后是 bucket 0..7 的强化掩码表；Fat Teddy 再追加 bucket 8..15 的一份。

Teddy 的 `engineID` 与 FDR 共用编号空间，`FDR_ENGINE_COUNT` 为 19，任何序列化的 `engineID` 必须严格小于这个值。运行期通过函数表按 `engineID` 选择实现，因此「引擎编号与实现不匹配」是一类典型故障：数据库能加载、能扫描，但结果全错。

#### 3.6 Noodle 与 hwlmLiteral：小规模与编译期

`noodTable` 是单字面量引擎，字段为 `id`、`msk`、`cmp`、`msk_len`、`key_offset`、`nocase`、`single`、`key0`、`key1`。它只处理「一个或极少量字面量」的场景，`key0`/`key1` 是首尾字节的快速筛选，`key_offset` 告诉运行期从头还是从尾开始比对。`msk_len` 上限是 8，与 `CONF_TYPE` 宽度一致。

`hwlmLiteral` 是编译期表示：`s`（字面量）、`id`、`nocase`、`noruns`、`included_id`、`squash`、`groups`、`msk`、`cmp`。其中 `squash` 的注释说明它是「FDR 确认掩码里用于压制被包含字面量比特的掩码」，由编译期在桶分配完成后计算；`included_id` 用于「一个字面量被另一个包含」的优化。这两个字段只存在于编译期，不会出现在数据库里，因此不要试图在运行期结构里找它们。

`msk` 与 `cmp` 这一对值得单独说明，因为它们不属于「模式语法」而属于「编译期加速约定」。注释规定：如果字面量尾部 8 字节记为 v，那么额外要求 `(v & msk) == cmp` 同时成立；空的 `msk` 表示不附加任何比较。这两个向量必须等长、长度不超过 `HWLM_MASKLEN`（8），并且**不得与字符串本身冲突**，只能在字符串已经允许的范围内收窄或补充。典型用法是在大小写不敏感的字面量里对某些位置强制大小写敏感，从而把一个「需要 2^k 个候选」的桶压成一个。理解这一点后就能解释一个现象：同样两条模式，写法不同会导致 `numStrings` 与 `tabSize` 明显不同，因为 `msk`/`cmp` 改变了桶的划分。

#### 3.7 scratch 上的两个确认字段

`fdr_conf` 与 `fdr_conf_offset` 是 FDR 与 Teddy 共用的一对暂存。确认函数在进入时把「当前确认值的指针」写进 `scratch->fdr_conf`，把「前端命中在缓冲区内的比特偏移」写进 `fdr_conf_offset`，退出时置回 `NULL`。它们的存在是为了让回调路径上的 Rose 程序能够知道「这次命中来自哪个表项的哪一位」。

字段注释里有一句 `assert(!scratch->fdr_conf)`，意思是这两个字段在确认期间不能被重入。任何在回调里再次触发扫描的写法都会破坏这个断言，表现为确认结果错乱或断言失败。

### 4. 典型示例

下面这段代码从数据库里取出浮动字面量前端，打印 HWLM 类型与 FDR 头部。`getFLiteralMatcher` 定义在 `src/rose/rose_internal.h`，没有字面量前端时返回 `NULL`，这一点必须先判断。

```c
#include "database.h"
#include "rose/rose_internal.h"
#include "hwlm/hwlm_internal.h"
#include "fdr/fdr_internal.h"
#include "hwlm/noodle_internal.h"
#include <hs.h>
#include <stdio.h>

int main(void) {
    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;
    if (hs_compile("foobar|bazqux|quux", HS_FLAG_CASELESS, HS_MODE_BLOCK,
                   NULL, &db, &err) != HS_SUCCESS) {
        printf("compile failed: %s\n", err->message);
        hs_free_compile_error(err);
        return 1;
    }

    const struct RoseEngine *rose = hs_get_bytecode(db);
    const struct HWLM *hwlm = getFLiteralMatcher(rose);
    if (!hwlm) {
        printf("no floating literal matcher in this database\n");
        hs_free_database(db);
        return 0;
    }
    printf("hwlm type=%u accel1_groups=0x%016llx\n", hwlm->type,
           (unsigned long long)hwlm->accel1_groups);

    if (hwlm->type == HWLM_ENGINE_FDR) {
        const struct FDR *fdr = HWLM_C_DATA(hwlm);
        printf("FDR engineID=%u size=%u numStrings=%u maxStringLen=%u\n",
               fdr->engineID, fdr->size, fdr->numStrings, fdr->maxStringLen);
        printf("stride=%u domain=%u domainMask=0x%04x tabSize=%u\n",
               fdr->stride, fdr->domain, fdr->domainMask, fdr->tabSize);
        printf("confOffset=%u floodOffset=%u\n",
               fdr->confOffset, fdr->floodOffset);
    } else if (hwlm->type == HWLM_ENGINE_NOOD) {
        const struct noodTable *nt = HWLM_C_DATA(hwlm);
        printf("NOOD id=%u msk_len=%u nocase=%u key_offset=%u\n",
               nt->id, nt->msk_len, nt->nocase, nt->key_offset);
    }

    hs_free_database(db);
    return 0;
}
```

示例输出如下（示例输出，具体格式需对照实际版本核验）。

```text
hwlm type=12 accel1_groups=0xffffffffffffffff
FDR engineID=0 size=704 numStrings=3 maxStringLen=6
stride=1 domain=11 domainMask=0x07ff tabSize=16384
confOffset=512 floodOffset=640
```

逐行判读。`type=12` 就是 `HWLM_ENGINE_FDR`，说明这条模式被字面量前端接管；若为 16 则是 Noodle，说明字面量太少、不值得建表。`accel1_groups` 为全 1，表示所有组都可用首选加速器；若你的模式带组开关，这里会收窄，收窄到 0 意味着加速器永不启用。`engineID=0` 是字符串级 FDR 的默认编号，必须小于 19；`size=704` 是整段引擎字节数，与 `domain` 和字面量个数正相关。`numStrings=3` 与模式里三个分支一致，`maxStringLen=6` 对应 `foobar`/`bazqux`，说明填充长度按最长字面量算。`stride=1` 表示逐字节查表，这是块模式短字面量的常见选择；`domain=11` 表示索引用 11 位、表项 2048 个，`domainMask=0x07ff` 正好是 `2^11-1`，两者不一致就说明头部被写坏。`tabSize=16384` 等于 2048 乘 8，与 `domain` 自洽；如果它不等于「表项数 × 8」，序列化数据很可能来自不同位宽的实现。`confOffset=512` 落在头部与主表之后，`floodOffset=640` 又在确认表之后，两者递增且都不超过 `size`，这是正常布局；任一偏移大于 `size` 都会在反序列化时被拒绝。

### 6. 版本差异

FDR 的头部字段自 2015-2017 版权年份以来保持稳定，`engineID`、`size`、`maxStringLen`、`numStrings`、`confOffset`、`floodOffset` 六件套是 Teddy 兼容性的基础，任何改动都会破坏「按 FDR 前缀读 Teddy」的约定，因此上游只会追加、不会重排。本快照中 `FDR_ENGINE_COUNT` 为 19；早期版本的具体取值**需对照实际版本核验**。把 16 之类旧数字硬编码进校验逻辑的代码，在新增编号的数据库上会误判为非法引擎。

5.4.0 引入 Fat Teddy 与 AVX-512 VBMI 优化，结构层面的表现是 Teddy 后面多了一份 bucket 8..15 的强化掩码表，头部字段不变。这意味着「用 `sizeof(struct Teddy)` 推算掩码表位置」在 Fat Teddy 上仍然成立，但「假设只有一份掩码表」不成立。判断是否 Fat Teddy 不能只看头部，要看 `engineID` 对应的引擎描述。

`HWLM_ENGINE_FDR` 与 `HWLM_ENGINE_NOOD` 的数值（12、16）是宏而非枚举，跨版本稳定。但 `struct HWLM` 的 `accel1`/`accel0` 是 `union AccelAux`，其内部布局随 SIMD 支持变化，因此 `sizeof(struct HWLM)` 在不同平台上可能不同；这正是 `HWLM_C_DATA` 用 `ROUNDUP_CL` 而不是硬编码偏移的原因。

最后提醒：本篇所有结论基于 5.4.2 快照，Vectorscan 分支的 FDR 实现可能裁剪了部分引擎编号。跨分支比对时**需对照实际版本核验** `FDR_ENGINE_COUNT` 与引擎描述表。

### 7. 常见误用与调试

1. **在源码里找 `struct bucket`**。不存在。bucket 是表项里的比特位，索引类型是 `BucketIndex` 这个 `typedef`。找不到就以为源码不全，是常见的无效排查。
2. **把 `confOffset` 当 `FDRConfirm` 数组起点**。它指向的是 `u32` 偏移表，真正的 `FDRConfirm` 在偏移指向的位置。按数组下标直接访问会读到错误的桶。
3. **用 `sizeof(struct Teddy)` 定位 Fat Teddy 的第二份掩码表**。头部大小一样，但掩码表份数不同；必须按 `engineID` 查引擎描述。
4. **假设 `stride` 一定是 1**。块模式短字面量常见 1，但长字面量或流式场景可能是 2 或 4。写死 1 会让回看窗口算错，表现为跨块漏匹配。
5. **在回调里重入扫描**。`scratch->fdr_conf` 的 `assert(!scratch->fdr_conf)` 会被触发，或者静默产生错误的确认结果。
6. **把 `idCount` 当无上限**。它最大 16，`ids[16]` 是定长数组；反序列化伪造数据时按它遍历会越界。
7. **认为 `numStrings` 等于用户模式条数**。一个模式可能拆成多个字面量，也可能完全不进字面量前端；这个值只统计本引擎内的字面量。

调试建议：先看 `HWLM::type` 确认路径，再看 `FDR::domain`/`tabSize` 是否自洽，最后用 `hsdump` 交叉验证引擎长度。若 `tabSize` 与 `domain` 不自洽，优先怀疑数据库版本或位宽不匹配，而不是字段读错。

（字段见 05-05 ｜ 参数见 04-04 ｜ 原理见 06-05 ｜ 模块见 07-07）

## 05-08 NG 图结构：NG、NFAVertex、NFAEdge 与组件树

### 1. 本篇定位与覆盖范围

这一篇要解决一个非常具体的混淆：很多人把 `NG` 当成「那张图」。实际上 `NG` 是编译期的聚合器，真正的图是 `NGHolder`。`NG` 里只有八个成员，负责把报告管理器、SOM 槽位管理器、边界报告、Rose 构建器和小写化构建器绑在一起；`NGHolder` 才是顶点与边的容器，`NFAVertex` 与 `NFAEdge` 只是描述符（本质是索引），它们指向的属性存放在 `NFAGraphVertexProps` 与 `NFAGraphEdgeProps` 里。

这种「描述符 + 属性」的组织方式是 Boost 图库的惯例，Hyperscan 在自己的 `src/util/ue2_graph.h` 里复刻了一套。理解这一点之后，很多奇怪写法就顺了：`g[v].char_reach` 里的 `g[v]` 是属性访问，不是解引用；`add_edge(u, v, g)` 返回的描述符只保证在同一次图修改之前有效；`num_vertices(g)` 是常数时间，因为图内部维护计数。

覆盖范围包括：`NG` 的八个成员、`NGHolder` 的四个特殊顶点与 `kind`、顶点属性四个字段、边属性三个字段、`assert_flags` 的位定义、组件划分（`ng_calc_components`）与 region 的关系，以及 `src/parser/` 组件树到图的映射。不覆盖的部分：Glushkov 构造的具体算法、各个化简 pass 的顺序与效果，见 06-03 与 07-02。

必须提醒一个所有权事实：`NG`、`NGHolder`、`Component` 树全部是**编译期对象**，它们不进数据库，也不参与序列化。数据库里留下的是 Rose 分解后的字节码；图在 `hs_compile` 返回之前就已经销毁。因此任何「运行期读图」的想法都不成立，能读的只有 `RoseEngine` 及其子结构。

### 3. 逐项详解

#### 3.1 NG 是聚合器，不是图

`NG` 的构造函数签名是 `NG(const CompileContext &in_cc, size_t num_patterns, unsigned in_somPrecision)`，三个参数分别决定编译上下文、模式条数与 SOM 精度。`num_patterns` 用于预分配报告管理器与槽位管理器的容量；`in_somPrecision` 为 0 表示不开 SOM。

`rm`（`ReportManager`）负责把「外部报告 id + 内部调整」注册成内部 `ReportID`，并做去重；`ssm`（`SomSlotManager`）负责给需要起点的子图分配槽位；`boundary` 负责零宽模式与边界报告。三者都是值成员，生命周期跟随 `NG`，因此 `NG` 一旦析构，图里的 `ReportID` 就失去了上下文，不能再解释。这也是为什么图不能脱离 `NG` 单独保存。

`minWidth` 是 `depth` 类型而不是 `u32`，因为图构造期间需要区分「未知」与「零」。`maxSomRevHistoryAvailable` 是 `const`，在构造时按最大 lookbehind 长度定死，后续不可改；它直接影响反向 NFA 能看多远。

#### 3.2 NGHolder 与四个特殊顶点

`NGHolder` 的构造函数只接受一个 `nfa_kind`，并在构造时预置四个特殊顶点与三条特殊边：`(start, startDs)`、`(startDs, startDs)` 自环、`(accept, acceptEod)`。所以一个「空图」也有 4 个顶点，`num_vertices(g) == N_SPECIALS` 是判断「图里还没有真实内容」的标准写法，`ng.cpp` 里就是这么用的。

`kind` 描述这张图在 Rose 里扮演的角色（`NFA_OUTFIX`、`NFA_INFIX`、`NFA_PREFIX`、`NFA_SUFFIX` 等，定义在 `src/nfa/nfa_kind.h`）。它不决定图的形状，而决定 Rose 如何消费这张图；同一张图换一个 `kind`，分解策略就不同。举例来说，`NFA_SUFFIX` 会被当作「必须有前缀触发」的引擎，`NFA_OUTFIX` 则可能被整体交给 NFA 执行而不参与字面量分解。字段层面它是普通成员，但在语义上是「图与 Rose 之间的契约」，改它等于改契约。

四个特殊顶点用 `const vertex_descriptor` 保存，`getSpecialVertex(u32 id)` 按下标取。注意注释里的两个警告：`NODE_START` 在触发图里可能不在偏移 0 触发；`NODE_START_DOTSTAR` 可能没有完整的自环。把特殊顶点当成「一定在 0 位」是常见误解。实际工程含义是：同一个 `start` 顶点在不同 `kind` 下可能承载不同起点语义，真正决定起点的是 Rose 生成的引擎参数，而不是顶点名字。

#### 3.3 char_reach：顶点级的字符集合

`char_reach` 是 `CharReach`，内部是 256 位的位图（`src/util/charreach.h`），提供 `set`、`test`、`count`、`clear`。它描述「进入这个顶点需要读到哪些字符」，语义上等价于 Glushkov 构造里的位置字符集。

字段层面有三个要点。第一，`char_reach` 为空的顶点是 epsilon 顶点，不消耗字符；它在图里合法，但在转成 NFA 时会被折叠。第二，`char_reach` 的并集大小直接影响 `LimEx` 的 `reachSize`，因此化简 pass 会尽量合并相同集合的顶点。第三，`char_reach` 与 `assert_flags` 是「与」的关系：一个顶点既要求字符匹配又要求断言成立，两者都满足才通过。

`CharReach` 内部是 256 位的位图而不是 32 字节数组，`count()` 走的是位计数指令，因此「统计这个顶点能接受多少字符」是常数时间。这一点在写分析工具时很有用：遍历顶点打印 `count()` 比逐字符 `test()` 快一个数量级。但要注意 `count()` 返回的是「位图里置位的个数」，不是「字符区间个数」；`[a-z]` 的 `count()` 是 26 而不是 1。

#### 3.4 reports：报告集合与去重

`reports` 是 `flat_set<ReportID>`，不是单个 id。原因是一个顶点可能同时是多个模式的接受点，例如 `foo` 与 `foo|bar` 共享前缀时，前缀末端的顶点就带两个报告。`flat_set` 是有序小数组，查找是线性但常数极小，适合集合规模很小的场景。

报告去重发生在 `ReportManager` 层而不是 `flat_set` 层：同一个外部 id 加同样的边界参数只注册一次。字段层面能看到的只是「这个顶点带哪些内部 id」，看不到「为什么是这些 id」。要追溯外部 id，需要查 `ReportManager` 的映射，属于 06-03 的范围。

#### 3.5 assert_flags：断言落在顶点还是边

断言既可以落在顶点，也可以落在边，取决于断言是「进入条件」还是「离开条件」。`ng_asserts.cpp` 的转换逻辑会把「断言顶点 + epsilon 边」折叠成「带 `assert_flags` 的边」，从而减少顶点数。因此同一个 `\b`，在不同化简阶段可能出现在 `g[v].assert_flags` 或 `g[e].assert_flags`，读代码时不能只检查一处。

位定义本身在 `src/parser/position.h`，前四位是词边界四种转移，`1<<7` 是虚拟起点（配合 `FIDDLE_ACCEPT`），`1<<8` 是多行起点，`1<<9` 到 `1<<12` 是 UCP 变体。UCP 变体不是「另一种断言」，而是「同一断言在 UCP 语义下的版本」，两者不能同时置位。

#### 3.6 边的 tops：多起点引擎的标记

`tops` 只在「从起点出发的边」上有意义，用于多起点引擎（multi-top）。它记录这条边对应哪些 top 事件，运行时靠 top 事件把引擎拉到某个起点。普通单起点图里这个集合为空，读它是安全的但无意义。

字段注释特别强调「仅用于从起点顶点出发的边」。如果在内部边上看到非空 `tops`，那不是合法状态，通常是某个 pass 复制边时忘了清空。这类问题不会在编译期报错，只会让多起点引擎多触发几次，表现为重复报告。

#### 3.7 组件划分与 region

`ng_calc_components` 把图划分成弱连通分量，结果是一张「顶点 → 组件号」的映射。组件号用于两件事：一是把互不相连的子图分给不同的 Rose 引擎，二是 SOM 槽位分配时按组件复用槽位。字段层面没有「组件号」这个顶点属性，它是外部 `unordered_map` 或 `vector`，所以不要指望从 `g[v]` 里读到。

`ng_equivalence`、`ng_cyclic_redundancy`、`ng_vivify` 这些 pass 会改变图的顶点与边，但不改变字段语义。它们的共同前提是「属性必须同步更新」：删点时要把入边出边接好，改 `char_reach` 时要保证报告不丢。任何自写 pass 都要遵守这个约定，否则会出现「图看起来对、跑起来少报」的问题。

`reduceGraph(NGHolder &g, som_type som, bool utf8, const CompileContext &cc)` 是化简的统一入口，`ng.h` 里把它放在类定义之外，说明它不依赖 `NG` 的聚合状态，只依赖图、SOM 类型、UTF-8 标记与编译上下文。这个签名也提示了一个事实：SOM 与 UTF-8 会改变化简策略，同一个模式在开 SOM 与不开 SOM 时得到的图可能不同，进而 `minWidth` 与引擎选型都不同。排障时若发现「同一条模式在两种配置下性能差很多」，先确认是不是化简路径分叉，而不是怀疑字段读错。

#### 3.8 与 parser 组件树的对应

`Component` 基类定义在 `src/parser/Component.h:58`，核心接口是 Glushkov 构造的四个函数：`first()`、`last()`、`empty()`、`buildFollowSet()`。图构造就是递归调用这些函数：`first()` 给出初始位置集合，`last()` 给出结束位置集合，`buildFollowSet()` 把「后继关系」写成边。

因此组件树与图不是一一对应：`ComponentSequence` 对应一串边，`ComponentAlternation` 对应分叉与汇合，`ComponentRepeat` 对应环或展开链，`ComponentAssertion` 对应 `assert_flags`，`ComponentByte`/`ComponentClass` 对应 `char_reach`。理解这个映射之后，读 `ng.cpp` 的 `addGraph` 就不会迷路：它做的就是把 `ExpressionInfo` 里的组件树递归翻译成 `NGHolder`，再把图交给 `reduceGraph` 化简。

`ComponentBackReference` 虽然存在于语法树，但 Hyperscan 不支持反向引用，编译期会拒绝。具体拒绝点（解析期还是图构造期）在不同版本可能不同，**需对照实际版本核验** `compiler.cpp` 与 `ng.cpp` 的错误路径。

（字段见 05-06 ｜ 参数见 04-04 ｜ 原理见 06-03 ｜ 模块见 07-02）

### 4. 典型示例

下面这段代码手工搭一张三顶点的图，用来观察特殊顶点、`char_reach` 与报告的存放方式。它不调用解析器，因此可以精确控制每个字段；仅用于理解结构，产品代码不应依赖内部图类型。

```cpp
#include "nfagraph/ng_holder.h"
#include "util/graph_range.h"
#include <cstdio>

using namespace ue2;

int main() {
    NGHolder g(NFA_OUTFIX);
    printf("after ctor: vertices=%zu edges=%zu specials=%zu\n",
           num_vertices(g), num_edges(g), NGHolder::N_SPECIAL_VERTICES);

    NFAVertex a = add_vertex(g);
    NFAVertex b = add_vertex(g);
    g[a].char_reach.set('a');
    g[b].char_reach.set('b');
    g[b].reports.insert(7);

    add_edge(g.start, a, g);
    add_edge(a, b, g);
    add_edge(b, g.accept, g);

    printf("after build: vertices=%zu edges=%zu\n",
           num_vertices(g), num_edges(g));
    for (auto v : vertices_range(g)) {
        printf("v%zu reach=%zu reports=%zu asserts=0x%x\n",
               g[v].index, g[v].char_reach.count(),
               g[v].reports.size(), g[v].assert_flags);
    }
    return 0;
}
```

示例输出如下（示例输出，具体格式需对照实际版本核验）。

```text
after ctor: vertices=4 edges=3 specials=4
after build: vertices=6 edges=6
v0 reach=0 reports=0 asserts=0x0
v1 reach=0 reports=0 asserts=0x0
v2 reach=0 reports=0 asserts=0x0
v3 reach=0 reports=0 asserts=0x0
v4 reach=1 reports=0 asserts=0x0
v5 reach=1 reports=1 asserts=0x0
```

逐行判读。第一行是关键：构造完就已有 4 个顶点、3 条边，这正是 `NGHolder` 预置的特殊顶点与特殊边，`specials=4` 与 `N_SPECIALS` 一致。若这里打印出 0，说明用的不是 `NGHolder` 而是裸 `ue2_graph`。第二行 `vertices=6 edges=6`：新增 2 个顶点、3 条边，总数从 4/3 变成 6/6，说明特殊边没有被覆盖。接下来四行是特殊顶点，`reach=0` 表示它们不消耗字符，`reports=0` 表示没有报告；`v2` 是 `NODE_ACCEPT`，它同样不消耗字符，这是正常设计，接受动作由边触发而不是由顶点字符触发。`v4` 对应 `a`，`reach=1` 说明只接受一个字符；`v5` 对应 `b`，`reach=1` 且 `reports=1`，证明报告挂在顶点上而不是边上。`asserts=0x0` 表示没有断言位；若在这里看到 `0x8`，说明该顶点带「词到非词」的边界条件，需要检查 `\b` 的位置是否符合预期。最后要注意 `index` 是按建点顺序分配的连续值，但特殊顶点固定占 0 到 3，因此自己新建的顶点一定从 4 开始。

### 6. 版本差异

`NFAGraphVertexProps` 与 `NFAGraphEdgeProps` 的字段在 5.x 内保持稳定，但 `assert_flags` 的位定义是逐步扩充的：UCP 四个变体（`1<<9` 至 `1<<12`）与 `POS_FLAG_MULTILINE_START`（`1<<8`）都是后期补上的。用老版本解析出的位掩码在新版本里解读，可能把「多行起点」误认为某个 UCP 断言，因此跨版本比对 dump 结果时必须先对齐 `position.h`。

`NG` 的成员增加了 `smwr`（小写化构建器）。早期版本没有独立的小写化构建器，大小写折叠逻辑散在 Rose 里；5.x 把它收进 `SmallWriteBuild` 并由 `NG` 持有。这意味着老代码里「直接调 Rose 做小写化」的写法在新版本不再成立。

`NGHolder` 的 `kind` 枚举值在 5.x 内没有重排，但新增了若干角色（如 `NFA_OUTFIX` 之外的细分）。按数值比较 `kind` 的代码应当改用枚举名。

最后是分支差异：Vectorscan 可能裁剪部分图 pass 以减小体积，`reduceGraph` 的行为与上游不完全一致。本篇字段结论只对上游 5.4.2 快照成立，跨分支时**需对照实际版本核验**。

### 7. 常见误用与调试

1. **把 `NG` 当图用**。`NG` 没有顶点与边，`ng.num_vertices()` 不存在。图是 `NGHolder`，通过 `addGraph` 交给 `NG` 消费。
2. **用 `g[v]` 当指针**。它是属性引用，`&g[v]` 取到的是属性地址，不是顶点。顶点描述符本身就是索引，可以直接拷贝与比较。
3. **认为空图 `num_vertices == 0`**。构造即有 4 个特殊顶点，判断「无内容」要用 `== N_SPECIALS`。
4. **只查顶点上的 `assert_flags`**。断言 pass 会把断言折叠到边上，漏查边会得出「没有断言」的错误结论。
5. **把 `tops` 当普通边标签**。它只对起点边有意义，内部边上的非空值是非法状态。
6. **在图修改后继续用旧描述符**。`add_vertex` 可能触发内部存储扩容，旧描述符的索引导向别的顶点；正确做法是每次修改后重新取。
7. **指望运行期读图**。图在编译结束前销毁，数据库里只有 Rose 字节码；任何「运行期遍历 NGHolder」的设计都无法落地。

调试建议：先用 `hsdump` 看 Rose 分解结果，再回到 `ng_dump` 输出图结构对照；两者不一致时，优先检查化简 pass 是否改变了 `char_reach` 与 `reports` 的同步性，而不是怀疑字段定义。

（字段见 05-06 ｜ 参数见 04-04 ｜ 原理见 06-03 ｜ 模块见 07-02）

## 05-09 流状态、SOM 槽位与 Chimera 结构字段

### 1. 本篇定位与覆盖范围

本篇是 05 册的收尾，覆盖三块内容：流状态 `hs_stream` 及其压缩表示、SOM 槽位从编译期到运行期的字段链路、Chimera 的数据库与 scratch 结构。这三块的共同点是「都涉及内存归属」：谁分配、谁释放、跨不跨线程、能不能序列化。字段本身不难，难的是所有权关系，因此本篇在逐项详解里会把「归属」写清楚。

先给结论性的边界。`hs_stream` 是**每次流会话**的对象，由 `hs_open_stream` 分配、`hs_close_stream` 释放，单流单线程使用；它不是线程安全的，也不能跨流共享。`SOM` 槽位是**编译期分配、运行期使用**的资源，槽位数量在编译时确定，运行期只按下标读写，不能动态扩容。`Chimera` 的 `ch_database` 与 `ch_scratch` 是**两套独立对象**，前者不可变可共享，后者每线程一份，二者都不与 Hyperscan 的 `hs_database`/`hs_scratch` 混用，尽管 `ch_scratch` 内部持有一个 `hs_scratch` 指针。

还要提前说明一个常见误解：`hs_stream` 在公共头 `src/hs_runtime.h` 里只有前置声明，真正的定义在 `src/state.h:54`，而且只有两个字段。所有「流里存了什么」的答案都不在这个结构里，而在它后面的多状态区，由 `RoseEngine::stateOffsets` 描述。试图从 `hs_stream` 字段推出状态布局，是读错方向的典型。

### 3. 逐项详解

#### 3.1 hs_stream：只有两个字段的头部

`struct hs_stream` 只有 `rose` 与 `offset`。`rose` 让每个流记住自己的引擎，`offset` 记录已消费字节数。所有真实状态在 `getMultiState(s)` 之后，宏定义为 `(char *)(s) + sizeof(*(s))`。状态区第 0 字节是状态标志（`ROSE_STATE_OFFSET_STATUS_FLAGS` 为 0），第 1 字节起是 role 多位图（`ROSE_STATE_OFFSET_ROLE_MMBIT` 为 `sizeof(u8)`），之后按 `RoseEngine::stateOffsets` 排列。

`offset` 的类型是 `u64a`，因此单流最大可寻址偏移是 2^64-1，实际受 horizon 与内存限制。它在每次 `hs_scan_stream` 后被累加，报告回调里的 `to` 就是「块内偏移 + 流偏移」。字段层面能确认的是：`offset` 不包含历史缓冲区长度，历史是另一块内存，由 `core_info.hbuf` 指向。

状态标志字节不在 `hs_stream` 里，而在多状态区第 0 字节，取值来自 `scratch.h` 的 `STATUS_TERMINATED`、`STATUS_EXHAUSTED`、`STATUS_DELAY_DIRTY`、`STATUS_ERROR` 四个位。它由 `runtime.c` 的 `setStreamStatus` 写入，扫描时再回读到 `scratch->core_info.status`，由 `can_stop_matching` 判定「这个流还能不能继续产出匹配」。诊断时若扫描返回值正常但没有任何报告，先查这一字节是否被置成 `EXHAUSTED`，比查引擎字段更快。

#### 3.2 流状态大小与压缩

`hs_stream_size(db, &size)` 返回单个流对象的字节数，实现是 `sizeof(struct hs_stream) + rose->stateOffsets.end`（见 `src/runtime.c:1097` 附近）。这个值随数据库变化，不随流变化；同一个数据库的所有流大小相同。该函数还要求数据库必须是流模式，块模式数据库会返回 `HS_DB_MODE_ERROR`，用块模式数据库去估算流内存是一类常见错误。

`hs_compress_stream(stream, buf, buf_size, &used)` 把状态折叠成可持久化的表示，`hs_expand_stream(db, &stream, buf, size)` 还原。`size_compress_stream` 给出所需上界，避免调用方猜测。压缩表示里只保留「跨块必需」的部分：历史、活跃位图、重复控制块、SOM 槽位；瞬时状态被丢弃。字段层面没有「压缩标志」，是否压缩由 API 调用决定，而不是由结构体字段决定。

还原时必须提供数据库，因为压缩表示只存「状态值」，不存「如何解释这些值」的偏移表；偏移表在 `RoseEngine::stateOffsets` 里。这条约束解释了为什么 `hs_expand_stream` 的签名带 `db` 而不只是缓冲区。`hs_reset_and_expand_stream` 是原地复用版本，语义等价于「重置一个已有流，再把压缩数据展开进去」，适合每连接一个流对象的服务端场景，可以避免反复分配释放。

压缩后的尺寸与 `historyRequired` 强相关：历史越长、重复控制块越多、SOM 槽位越多，压缩表示越大。反过来说，如果一个流的压缩结果接近 `hs_stream_size`，通常说明它几乎没有可压缩的瞬时状态，或者偏移已经很大、控制块计数器接近饱和。做容量规划时应该用真实流量跑一轮 `size_compress_stream` 的峰值，而不是用 `hs_stream_size` 乘系数。

#### 3.3 SOM 槽位的编译期字段

`SomSlotManager`（`src/som/slot_manager.h:58`）是编译期对象，私有字段为 `nextSomSlot`、`cache`、`rev_nfas`、`historyRequired`、`precision`。`nextSomSlot` 是下一个可用槽号，`NO_PARENT`（`~0`）表示无父槽；`cache` 是槽位缓存，避免重复分配相同前缀；`rev_nfas` 是反向 NFA 队列，每个槽位可能对应一个反向扫描器；`historyRequired` 是流式模式下承诺使用的历史字节数；`precision` 是用户请求的 SOM 精度（字节数），非 SOM 模式为 0。

`getSomSlot(prefix, escapes, is_reset, parent_slot)` 分配槽位，`getInitialResetSomSlot` 处理「重置哨兵」场景，`getPrivateSomSlot` 分配不与别人共享的槽位，`rollbackSomTo` 回滚到某个槽号（用于失败重试）。这些函数只改 `nextSomSlot` 与 `cache`，不改 `rev_nfas` 以外的运行期结构。

#### 3.4 运行期 SOM：数组 + 位图 + 偏移

运行期把槽位值存在 `scratch->som_store`，下标就是槽号。因为「只读槽位」不能直接写，还需要 `som_attempted_store` 记录试写值、`som_set_now` 记录「本偏移已置位」、`som_attempted_set` 记录「试写但不可写」。`som_set_now_offset` 是这组位图对应的偏移，偏移一变就要整体切换。

`storeSomToStream(scratch, offset)` 与 `loadSomFromStream(scratch, offset)` 是流式模式下把槽位值写入/读出流状态的入口。字段层面的关键约束是：`som_store_count` 在分配时定死，运行期不能增槽；`som_fatbit_size` 决定每个位图多大，必须与槽数匹配。任何「运行期动态加槽」的设计都会破坏这两个不变量。

还有两个字段间接约束 SOM 行为。`SomSlotManager::precision` 是用户通过 `HS_MODE_SOM_HORIZON_*` 请求的精度，它决定「起点最多能回溯多远」；`historyRequired` 是编译器承诺保留的历史，二者共同决定 `HS_OFFSET_PAST_HORIZON` 的触发点。精度越大，流状态越大、压缩越慢，但起点可用范围越宽。字段层面看不到「horizon 当前值」，因为它不是运行期变量，而是编译期常量；运行期只按偏移比较，超出就返回错误码。

#### 3.5 som_operation：15 种微指令

`som_operation` 只有三个字段，但 `type` 有 15 个取值：1 相对回调、2 内部置位、3 内部置位若未设、4 内部置位若可写、5 反向 NFA 置位、6 反向 NFA 若未设、7 反向 NFA 若可写、8 拷贝、9 拷贝若可写、10 置为可写、11 存储回调、12 绝对回调、13 反向 NFA 回调、14 从某槽取值、15 从某槽取值若可写。`aux` 是联合体：前四类用 `somDistance`，后几类用 `revNfaIndex`。

读这个结构时要记住「`onmatch` 是目标槽，`aux` 是来源或距离」。把两者搞反会导致 SOM 起点偏移错位，而不是崩溃；这类错误极难通过日志发现，只能靠对拍。

#### 3.6 Chimera 数据库：三层结构与对齐

`ch_database` 头部有 `magic`、`version`、`length`、两个保留字段、`bytecode` 偏移与 16 个 `u32` 的填充。填充的作用是把变长区推到对齐边界，但**字节码头的真实位置以 `bytecode` 偏移为准**，不是 `bytes[]` 的固定偏移；`ch_get_bytecode` 只断言 16 字节对齐（结构注释称字节码头总是 64 字节对齐），因此读这段内存必须用偏移而不是 `sizeof` 推算。

`ch_bytecode` 里的 `databaseOffset` 指向内嵌的 Hyperscan 数据库，`patternOffset` 指向 `u32` 偏移数组，`unguardedOffset` 指向「无需 PCRE 确认」的模式下标。`unguardedCount` 为 0 表示所有模式都要确认，这时 Chimera 的收益最差。`maxCaptureGroups` 决定 `ovector` 大小，也决定 `ch_capture` 数组长度。

`ch_pattern` 里最值得注意的是 `extra`：类型是 `pcre_extra`，注释说它「用于存储当前执行 pcre 的 study 数据指针」。这意味着它带有运行期语义，不能当作纯只读字段；具体写入点是 `ch_runtime.c`，共享数据库时是否每个线程各自缓存，**需对照实际版本核验**。稳妥做法是把 `ch_database` 视为只读，任何需要的可变状态放在 `ch_scratch` 一侧。

#### 3.7 Chimera scratch 与捕获结构

`ch_scratch` 有 `magic`、`in_use`、`multi_scratch`、`ovector`、`captured`、`active`、`patternData`、`pq`、四个尺寸字段、`ret` 与 `scratch_alloc`。`multi_scratch` 是内部 `hs_scratch`，由 Chimera 自己分配并随 `ch_scratch` 释放；`ovector` 与 `captured` 都按 `maxCaptureGroups` 定尺；`pq` 用于保证多个模式命中时按结束偏移排序上报。

`ch_patterndata` 只有 `match`、`groupCount`、`scanStart` 三个字段：`match` 指向缓存的捕获组，`groupCount` 是该模式的组数，`scanStart` 是「还需单次扫描的起点」。`ch_capture` 有 `flags`、`from`、`to`，`flags` 用 `CH_CAPTURE_FLAG_ACTIVE` 表示该组是否参与匹配。未参与的组 `from`/`to` 无意义，读之前必须先看 `flags`。

`unguardedCount` 与 `CHIMERA_FLAG_ALL_CONFIRM` 是一对值得注意的组合。`unguardedOffset` 指向的模式列表是「不需要 PCRE 确认、可直接上报」的集合；当 `CHIMERA_FLAG_ALL_CONFIRM` 被置位时，这个列表为空，所有命中都要走 PCRE。字段层面能直接读出「有多少模式能走快路径」，这是评估 Chimera 收益最直接的数字：`unguardedCount` 接近 `patternCount` 说明预过滤质量高，为 0 说明每次命中都要付 PCRE 的代价。`CHIMERA_FLAG_NO_MULTIMATCH` 则决定同一模式是否只报第一次，它影响的是回调次数而不是结构布局。

#### 3.8 三者的内存归属

`hs_stream` 由 `hs_open_stream` 用 `hs_stream_alloc` 分配，`hs_close_stream` 释放；`SOM` 槽位数组属于 `hs_scratch`，随 scratch 释放；`ch_database` 用 `ch_free_database`，`ch_scratch` 用 `ch_free_scratch`。三套分配器互不通用：用 `free()` 释放 `ch_scratch` 会破坏 `scratch_alloc` 的回退逻辑，用 `hs_free_scratch` 释放 `ch_scratch` 则是类型错误。

### 4. 典型示例

第一段代码观察流对象大小与压缩后的状态长度。它先开流、扫两块数据，再压缩到缓冲区，打印实际用量。

```c
#include <hs.h>
#include <stdio.h>
#include <stdlib.h>

static int onMatch(unsigned int id, unsigned long long from,
                   unsigned long long to, unsigned int flags, void *ctx) {
    (void)from; (void)flags; (void)ctx;
    printf("match id=%u at %llu\n", id, to);
    return 0;
}

int main(void) {
    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;
    if (hs_compile("ab+c", HS_FLAG_SOM_LEFTMOST, HS_MODE_STREAM,
                   NULL, &db, &err) != HS_SUCCESS) {
        printf("compile failed: %s\n", err->message);
        hs_free_compile_error(err);
        return 1;
    }

    size_t ssize = 0;
    hs_stream_size(db, &ssize);
    printf("stream size=%zu\n", ssize);

    hs_scratch_t *scratch = NULL;
    if (hs_alloc_scratch(db, &scratch) != HS_SUCCESS) {
        hs_free_database(db);
        return 1;
    }

    hs_stream_t *stream = NULL;
    hs_open_stream(db, 0, &stream);
    hs_scan_stream(stream, "xxab", 4, 0, scratch, onMatch, NULL);
    hs_scan_stream(stream, "bcyy", 4, 0, scratch, onMatch, NULL);

    char buf[4096];
    size_t used = 0;
    if (hs_compress_stream(stream, buf, sizeof(buf), &used) == HS_SUCCESS) {
        printf("compressed=%zu of %zu\n", used, sizeof(buf));
    }

    hs_close_stream(stream, scratch, onMatch, NULL);
    hs_free_scratch(scratch);
    hs_free_database(db);
    return 0;
}
```

示例输出如下（示例输出，具体格式需对照实际版本核验）。

```text
stream size=320
match id=0 at 5
compressed=128 of 4096
```

逐行判读。`stream size=320` 是 `sizeof(struct hs_stream)` 加 `stateOffsets.end`，其中头部只有 `rose` 指针与 `offset` 两个字段（64 位平台上 16 字节），其余全是状态区；若这个值比你预期大很多，通常是 `historyRequired` 被长字面量或 `.*` 抬高。`match id=0 at 5` 是跨块命中的关键证据：第一块只有 `xxab`，第二块才有 `c`，结束偏移 5 说明状态在块边界被正确保留；如果这里没有输出，先查 `hs_scan_stream` 的返回值，再查历史长度是否足够。`compressed=128` 说明压缩表示远小于原始 320 字节，压缩只保留跨块必需部分；这个数字随偏移增大而增长，因为重复控制块与 SOM 槽位需要更多字节。注意压缩缓冲区必须由调用方提供，`used` 是实际用量，不能用 `sizeof(buf)` 当结果。

第二段代码用 Chimera 取捕获组，重点观察 `ch_capture` 的 `flags` 与 `from`/`to`。

```c
#include <chimera/ch.h>
#include <stdio.h>

static int onEvent(unsigned int id, unsigned long long from,
                   unsigned long long to, unsigned int flags,
                   unsigned int size, const ch_capture_t *caps, void *ctx) {
    (void)flags; (void)ctx;
    printf("id=%u %llu-%llu groups=%u\n", id, from, to, size);
    for (unsigned int i = 0; i < size; i++) {
        if (caps[i].flags & CH_CAPTURE_FLAG_ACTIVE) {
            printf("  g%u: %llu-%llu\n", i, caps[i].from, caps[i].to);
        } else {
            printf("  g%u: inactive\n", i);
        }
    }
    return CH_CALLBACK_CONTINUE;
}

int main(void) {
    ch_database_t *db = NULL;
    ch_compile_error_t *err = NULL;
    if (ch_compile("(foo)(bar)?", 0, CH_MODE_GROUPS, NULL,
                   &db, &err) != CH_SUCCESS) {
        printf("compile failed\n");
        return 1;
    }
    ch_scratch_t *scratch = NULL;
    ch_alloc_scratch(db, &scratch);
    const char *data = "xxfoobar";
    ch_scan(db, data, 8, 0, scratch, onEvent, NULL, NULL);
    ch_free_scratch(scratch);
    ch_free_database(db);
    return 0;
}
```

示例输出如下（示例输出，具体格式需对照实际版本核验）。

```text
id=0 2-8 groups=3
  g0: 2-8
  g1: 2-5
  g2: 5-8
```

逐行判读。`id=0` 是模式 id，`2-8` 是整体匹配起止偏移，`groups=3` 包含第 0 组（整体）加两个捕获组，这与 `(foo)(bar)?` 的组数一致。`g0: 2-8` 是整体匹配，`g1: 2-5` 对应 `foo`，`g2: 5-8` 对应 `bar`。如果 `bar` 不存在，`g2` 会打印 `inactive`，而不是 `0-0`；这是 `ch_capture::flags` 存在的意义，读 `from`/`to` 前必须先判 `CH_CAPTURE_FLAG_ACTIVE`。`size` 由数据库的 `maxCaptureGroups` 决定，可能大于实际组数，多出来的槽位同样是 inactive；把 `size` 当「本模式实际捕获组数」会多读无用槽位。注意 Chimera 的 `from` 是真实起点，这与纯 Hyperscan 默认只报结束偏移不同，也是 Chimera 适用于需要捕获组场景的原因。若需要多模式同时命中，回调调用顺序由 `ch_scratch` 的优先队列保证，不保证与模式声明顺序一致。

### 6. 版本差异

`struct hs_stream` 的两个字段在 5.x 内没有变化，但状态区布局随 `RoseStateOffsets` 扩充而增长：逻辑组合的 `logicalVec`/`combVec`、活跃左引擎的 `activeLeftArray`、长字面量的 `ll_buf` 相关字段都是后期加入的。这解释了「同一个模式在新版本上 `hs_stream_size` 变大」的现象，不是内存泄漏。

5.4.2 的 CHANGELOG 条目与 scratch 行为有关，表现为 `hs_alloc_scratch` 在部分场景下的容量增长策略调整。把 `hs_scratch_size` 的结果写死、或用固定偏移访问 `som_store` 的代码会踩到；正确做法是每次按返回的尺寸重新取指针，不缓存跨版本偏移。

Chimera 的 `ch_database` 头部含 `reserved0`/`reserved1` 与 16 个 `u32` 填充，这是为将来扩展留的余地；`ch_bytecode` 的 `maxCaptureGroups` 是后期补充的字段，早期版本用固定上限。解析旧数据库时若发现 `maxCaptureGroups` 为 0，**需对照实际版本核验**其默认值语义。

最后是分支差异：Vectorscan 的 SOM 实现可能有精度裁剪，`som_store` 的元素宽度与槽位编码不一定与上游一致。本篇字段结论只对上游 5.4.2 快照成立。

### 7. 常见误用与调试

1. **把 `hs_stream_t *` 当结构体直接读字段**。公共头只有前置声明，字段在 `src/state.h`；产品代码不应读，诊断代码也要注意版本。
2. **用 `offset` 当块内偏移**。它是流偏移，回调里的 `to` 已经换算过；再减一次会得到负数或错位。
3. **压缩缓冲区按 `hs_stream_size` 开**。压缩表示与原始状态大小无必然关系，应该用 `size_compress_stream` 或足够大的缓冲并检查 `HS_INSUFFICIENT_SPACE`。
4. **跨线程共享 `ch_scratch`**。`in_use` 是协作式检查，两个线程同时读到 0 都会通过；表现为偶发 `CH_SCRATCH_IN_USE` 或结果错乱。
5. **读 `ch_capture` 不判 `flags`**。inactive 组的 `from`/`to` 是残留值，直接使用会得到看似合理但完全错误的偏移。
6. **把 `pcre_extra` 当只读**。`ch_pattern::extra` 会被运行期用于缓存 study 指针；在共享数据库上写入自己的状态会破坏其他线程。
7. **混用释放函数**。`hs_free_scratch` 与 `ch_free_scratch` 不通用，`ch_database` 必须用 `ch_free_database`；混用的典型表现是堆损坏而不是立即报错。

调试建议：先用 `hs_stream_size` 与 `size_compress_stream` 建立内存基线，再用 `hs_database_info` 确认模式与版本；Chimera 场景先看 `unguardedCount`，若为 0 说明所有模式都要走 PCRE 确认，性能会显著低于纯 Hyperscan，这时应优先优化模式而不是调 scratch。

（字段见 05-03 ｜ 参数见 04-05 ｜ 原理见 06-11 ｜ 模块见 07-11）
