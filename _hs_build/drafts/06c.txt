# Hyperscan 技术资料 · 06 技术原理（分片 C）

## 06-11 流式匹配与流状态压缩

### 1. 背景与动机

块模式与流模式的区别，表面上是「一次给一整块」还是「分多次给」，实质上是「有没有一个跨调用存活的对象」。块模式每次 `hs_scan` 都从零开始，函数返回后所有中间结果都作废；流模式必须把「已经看过但还没有结论」的那部分信息留在内存里，因为一个匹配可能从三个月前的第一个字节开始，到今天这一块才闭合。这个跨调用存活的内存，就是流状态。

流状态一旦存在，就带来三个工程问题。第一是容量。`hs_stream_size()` 返回的是状态体的固定上界，等于 `sizeof(struct hs_stream)` 加 `RoseEngine::stateOffsets.end`；对上千条模式、开启 SOM 的数据库，这个值可能是几 KB 到几十 KB。一个网关同时维持十万条 TCP 会话，乘起来就是 GB 级常驻内存。而真实状态里绝大部分区域是空的：表示「哪些队列活跃」的位图大多数位为 0，SOM 槽位大多数无效，anchored 表在流推进足够远之后再也用不到。把这些空区域也原样保存，是纯粹的浪费。

第二是持久化与迁移。会话要能被换出到磁盘、搬迁到另一台机器、在进程崩溃后由接管者恢复。这就要求状态能被写成一个字节串，并且能在新进程里、对着同一份数据库重新变成一个可继续喂数据的流。这也解释了为什么 Hyperscan 提供的是 `hs_compress_stream` 而不是「你自己 memcpy 那几十 KB」：只有库自己知道哪些字段是「活的」。

第三是解释「压缩后大小为什么会变」。很多人第一次用 `hs_compress_stream` 时会假设输出是定长的，于是按 `hs_stream_size` 的返回值一次性备好缓冲，结果发现 `used_space` 远小于上界，或者在不同时刻压缩同一流得到不同长度。这个波动不是实现瑕疵，而是「按活跃性搬运」的必然结果：活跃队列越多、SOM 槽越满、历史窗口越靠前，压缩表示就越长。

还有一个容易被忽略的动机：压缩表示是**不带自描述信息**的。它没有魔数、没有版本号、没有数据库指纹，格式完全由 `RoseEngine` 的布局决定。这不是疏忽，而是把「绑定关系」交给调用方：只有你能决定这个字节串属于哪份数据库、哪个版本、哪条会话。理解这一点，才能理解本篇后半部分几乎所有陷阱的来源。

### 2. 核心概念

`struct hs_stream` 本身极小，只有两个字段：指向 `RoseEngine` 的 `rose` 指针，以及当前流的累计偏移 `offset`。真正的状态体紧跟在结构体之后，基址由 `getMultiState()` 计算，即「流指针加结构体大小」。状态体内部的每一块区域都通过 `RoseEngine::stateOffsets` 里的偏移定位，因此同一个数据库编译出来的所有流，布局完全一致。

需要强调 `offset` 的语义：它是**整个流**已经喂入的字节数，不是当前块的偏移。回调里拿到的 `from`、`to` 也相对于整个流的起点。这一点与块模式一致（块模式整个流就是那一块），但流模式下跨块时如果按块内偏移理解，就会得出「匹配位置越跑越靠前」的错觉。

状态体可以按「用途」分成四组。第一组是调度位图：状态标志字节、表示哪些角色有状态的 multibit、活跃叶子队列位图、活跃左扩展队列位图。第二组是引擎私有状态：每个 NFA 的 `streamState`（按 `NfaInfo::stateOffset` 定位）、左扩展的 lag 字节表、long literal 状态、anchored 表状态。第三组是逻辑与组合：耗尽向量、逻辑向量、组合向量。第四组是数据与偏移：历史缓冲区 `history`、组标志、SOM 的 valid/writable 位图与槽位数组。

`history` 是流式语义的核心。它的长度由编译期算出的 `historyRequired` 决定，含义是「为了判断跨块的 anchored / floating 匹配，最多需要回看多少字节」。`maintainHistoryBuffer()` 在每次扫描成功后把新数据尾部拷进历史窗口；如果本次块长小于窗口，就先把旧历史左移再拷。历史只保留最近的一段，因此**早于窗口的数据不可重放**——这正是「流式模式要求数据按序、不能回头补历史」的技术根据。

multibit（简称 mmbit）是 Hyperscan 自己实现的分层位图，用来表示「哪些队列/角色/键是活跃的」。位数多时它不是一块平坦的位数组，而是金字塔：上层每个字描述下层若干字是否有非零位。压缩算法就建立在这个结构上：深度优先遍历，若某块的「有效位子集」与整块等价（`mmbit_popcount` 相等），就说明下层没有额外信息，整块省略；全零时只写一个字的头。于是「活跃队列很少」的流能压得非常小，「几乎所有队列都活跃」的流压缩收益趋近于零。

SOM 的搬运是另一个典型：压缩时只遍历 `somValid` 位图中为 1 的槽，把该槽 `somHorizon` 字节的偏移值拷出去；无效槽完全不占空间。这是「按需搬运」而不是「压缩算法」的最佳例子，也说明为什么开 SOM 的流压缩后大小与「有多少模式已经见过起点」强相关。

最后要区分三种「大小」：`hs_stream_size()` 是状态体上界；`hs_compress_stream()` 的输出是当前活跃状态的编码；两者之间没有固定比例。把上界当预算、把压缩输出当实际占用，是容量规划的正确做法。

### 3. 关键数据结构与源码位置

流对象的定义在 `src/state.h`，`struct hs_stream` 与 `getMultiState()` 都在这个文件里，注释明确写了「状态体紧跟结构体、偏移以结构体末尾为基准」。`RoseEngine` 中与本篇相关的字段是 `historyRequired`、`stateOffsets`、`anchoredDistance`、`activeArrayCount`、`activeLeftCount`、`leftfixBeginQueue`、`somLocationCount`、`somHorizon`、`rolesWithStateCount`、`ekeyCount`、`lkeyCount`、`lopCount`、`ckeyCount`，定义在 `src/rose/rose_internal.h`（字段见 05-05）。

压缩与还原的实现极有特色：真正的搬运逻辑只写了一遍，放在 `src/stream_compress_impl.h`，靠六个宏在 `src/stream_compress.c` 里被定义三次，展开成三个函数。`COPY` 在压缩侧是 `COPY_IN`（断言后 `memcpy` 到缓冲），在还原侧是 `COPY_OUT`（先检查剩余空间，不够就返回 0），在计长侧是 `SIZE_COPY_IN`（只累加偏移、不碰内存）。`COPY_MULTIBIT` 对应 `mmbit_compress` / `mmbit_decompress` / `mmbit_compsize` 三个位图接口，`FN_SUFFIX` 决定函数名后缀 `sc_compress` / `sc_expand` / `sc_size`。这种「一份模板三种语义」的写法，既保证了压缩与还原的字段顺序绝对一致，也解释了为什么计长路径不做边界检查——它根本不写缓冲区。

对外的三个入口在 `src/stream_compress.h`：`compress_stream()`、`expand_stream()`、`size_compress_stream()`。公共 API 在 `src/runtime.c`：`hs_open_stream`（`runtime.c:556`）、`hs_scan_stream`（`runtime.c:1019`）、`hs_close_stream`（`runtime.c:1038`）、`hs_reset_stream`（`runtime.c:1067`）、`hs_copy_stream`（`runtime.c:747`）、`hs_reset_and_copy_stream`（`runtime.c:775`）、`hs_stream_size`（`runtime.c:1097`）、`hs_compress_stream`（`runtime.c:1225`）、`hs_expand_stream`（`runtime.c:1258`）、`hs_reset_and_expand_stream`（`runtime.c:1298`）。位图接口见 `src/util/multibit.h` 与 `src/util/multibit_compress.h`。

下表把状态区域与对应的处理手段放在一起，便于对照源码阅读；参数与返回码语义见 04-05。

| 状态区域 | 压缩手段 | 触发条件与说明 |
|---|---|---|
| 状态标志、`offset` | 定长 `memcpy` | 总是搬运，标志位决定流是否已终止 |
| 角色 / 活跃队列位图 | mmbit 金字塔裁剪 | 按活跃位数收益，全零时只留一个字 |
| 各 NFA 的 `streamState` | 按活跃位迭代搬运 | 只搬 `activeLeafArray` 中置位的队列 |
| 左扩展 lag 字节 | 按活跃位搬 1 字节 | 仅非瞬态左扩展，且 lag 索引有效 |
| SOM 槽位 | 只搬 `somValid` 为 1 的槽 | 每槽宽度等于 `somHorizon` |
| anchored 表状态 | 条件搬运 | 仅当 `offset <= anchoredDistance` 时搬 |
| 历史缓冲区 | 只搬有效尾部 | 长度取 `min(offset, historyRequired)` |

从这张表能看出一个规律：搬运量由「活跃度」决定，而不是由「数据库规模」决定。这也解释了为什么同一个数据库上，刚打开的流压缩后很小，跑了很久且大量模式见过起点的流压缩后接近上界。

### 4. 关键流程与调用链

打开流的第一步是校验。`hs_open_stream()` 先查 `stream` 指针非空，把它置空，然后 `validDatabase()`（只查魔数与版本），再检查 `db->bytecode` 落在头部区间内、`hs_get_bytecode()` 结果 16 字节对齐，接着比较 `rose->mode` 是否等于 `HS_MODE_STREAM`——不等就是 `HS_DB_MODE_ERROR`。之后调用 `validateStateLayout()` 做一次完整的偏移合法性检查，因为后面的 `init_stream()` 会按这些偏移直接写内存。全部通过才按 `sizeof(struct hs_stream) + stateOffsets.end` 分配。

`init_stream()` 有三个细节值得记住。第一，当 `init_history` 为真时，它把历史窗口末尾 16 字节填成 `0x5a`，理由是 FDR 引擎会无条件读取这 16 字节做前缀比较，初值必须确定（源码注释写得很直白）。第二，`s->offset` 置 0，`setStreamStatus(state, 0)`，再 `roseInitState()` 按数据库里的初始化表铺开各区域。第三，清空耗尽向量、清空逻辑与组合向量、初始化 SOM 状态。`hs_reset_stream()` 复用同一个流对象时 `init_history` 传 0，历史保留，只重置其余状态——这是复用时唯一「不清」的区域。

扫描的调用链是 `hs_scan_stream()` → `markScratchInUse()` → `hs_scan_stream_internal()`。后者按顺序做：读状态标志，若已 `TERMINATED` / `EXHAUSTED` / `ERROR` 则直接返回对应码（终止返回 `HS_SCAN_TERMINATED`，耗尽返回 `HS_SUCCESS`）；长度为 0 直接返回成功且不推进偏移；用 `getHistoryAmount()` 算出可回看的历史量；`populateCoreInfo()` 把数据指针、长度、历史指针、流偏移塞进 scratch；有 SOM 时 `loadSomFromStream()` 把槽位读进 scratch；偏移为 0 时跑一次零偏移 boundary 程序；然后按 `rose->runtimeImpl` 三分支执行（完整 Rose、纯字面量、单外缀）。

扫描收尾的顺序同样重要：先 `setStreamStatus()` 把可能被置位的终止/耗尽标志写回流；若有内部错误返回 `HS_UNKNOWN_ERROR`；否则在「未要求停止」的前提下调用 `maintainHistoryBuffer()`、把 `id->offset` 增加本次长度、并在有 SOM 时 `storeSomToStream()` 把 scratch 里的槽位写回。注意历史推进与偏移推进是**同一个条件分支**里的，任何导致停止匹配的情况都不会推进历史——这也意味着流的「已消费偏移」与「历史内容」始终一致。

压缩链路的入口是 `hs_compress_stream()`。它先调 `size_compress_stream()` 算出精确需求（返回 0 视为布局非法），把需求写进 `used_space`，空间不足就返回 `HS_INSUFFICIENT_SPACE`；空间足够才真正 `compress_stream()`。还原链路的入口是 `hs_expand_stream()`：校验数据库、对齐、模式，按上界分配，再 `expand_stream()`；展开失败会先释放内存再返回 `HS_INVALID`，不会泄漏半个流。

`hs_reset_and_expand_stream()` 是「原地还原」，语义上等价于「先把旧流的 EOD 报告补完，再把压缩表示覆盖上去」。因此传入回调时它会先跑一遍 `report_eod_matches()`，让旧流尾部的待报告匹配有机会吐出来，然后才覆盖。很多「还原后丢了最后一条匹配」的现场，根因就是用了 `hs_expand_stream()` 而不是这个接口，或者用了这个接口却没传回调。

### 5. 配置/命令/代码实例

下面的程序把「打开 → 分块扫描 → 查询压缩所需空间 → 压缩 → 关闭 → 还原 → 继续扫描」串成一条完整链路。模式 `ab+c` 跨两块才闭合，正好用来验证历史回看；SOM 打开是为了让输出能看出跨块匹配的起点仍被正确保留。完整 API 参数见 04-05，编译标志见 04-02。

```c
#include <hs.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static int on_match(unsigned int id, unsigned long long from,
                    unsigned long long to, unsigned int flags, void *ctx) {
    (void)flags;
    (void)ctx;
    printf("match id=%u [%llu, %llu)\n", id, from, to);
    return 0; /* 0 表示继续扫描 */
}

int main(void) {
    hs_database_t *db = NULL;
    hs_scratch_t *scratch = NULL;
    hs_compile_error_t *cerr = NULL;
    hs_stream_t *stream = NULL;
    hs_stream_t *restored = NULL;

    if (hs_compile("ab+c", HS_FLAG_SOM_LEFTMOST, HS_MODE_STREAM, NULL,
                   &db, &cerr) != HS_SUCCESS) {
        fprintf(stderr, "compile failed: %s\n", cerr->message);
        hs_free_compile_error(cerr);
        return 1;
    }
    if (hs_alloc_scratch(db, &scratch) != HS_SUCCESS) {
        hs_free_database(db);
        return 1;
    }

    size_t ceiling = 0;
    hs_stream_size(db, &ceiling);
    printf("stream_size ceiling = %zu\n", ceiling);

    hs_open_stream(db, 0, &stream);
    hs_scan_stream(stream, "xabb", 4, 0, scratch, on_match, NULL);

    size_t need = 0, used = 0;
    hs_compress_stream(stream, NULL, 0, &need); /* 只查询所需空间 */
    char *frozen = malloc(need);
    if (hs_compress_stream(stream, frozen, need, &used) == HS_SUCCESS) {
        printf("compressed = %zu bytes\n", used);
    }

    hs_scan_stream(stream, "bc", 2, 0, scratch, on_match, NULL);
    hs_close_stream(stream, scratch, on_match, NULL);

    if (hs_expand_stream(db, &restored, frozen, used) == HS_SUCCESS) {
        hs_scan_stream(restored, "bc", 2, 0, scratch, on_match, NULL);
        hs_close_stream(restored, scratch, on_match, NULL);
    }

    free(frozen);
    hs_free_scratch(scratch);
    hs_free_database(db);
    return 0;
}
```

示例输出，具体格式需对照实际版本核验。

```text
stream_size ceiling = 1184
compressed = 47 bytes
match id=0 [1, 6)
match id=0 [1, 6)
```

逐行判读。第一行的 1184 是 `hs_stream_size()` 给出的状态上界，等于 `sizeof(struct hs_stream)` 加 `stateOffsets.end`；它随模式数量、是否开 SOM、SOM horizon 大小、各引擎状态宽度共同变化，换一条模式就会变，不能当常量。第二行的 47 是压缩后的实际字节数，远小于上界，原因正是此时活跃队列只有一条、SOM 只有一个槽有效、`historyRequired` 只有几个字节；这个数会随流推进而增长，绝不能当容量预算用。第三行来自原始流的第二块：`xabb` 加 `bc` 组成 `xabbc`，`ab+c` 从头匹配到偏移 6，开区间写法表示最后一个字节下标为 5；起偏移 1 由 `HS_FLAG_SOM_LEFTMOST` 提供，没有这个标志时 `from` 无意义。第四行与第三行完全相同，但它来自**还原出来的流**——因为压缩点在此之前，还原后重新喂相同的 `bc` 必然得到相同的匹配，这一对重复行正是「压缩是无损的」最直观的证据。如果第四行消失或偏移不对，先怀疑还原时用了不同的数据库，而不是怀疑压缩算法。

第二种常见写法是「先探测、再分配、失败重试」。因为 `hs_compress_stream()` 在空间不足时会返回 `HS_INSUFFICIENT_SPACE` 并把需求写回 `used_space`，所以可以按下面的方式做定长缓冲池。

```c
size_t need = 0;
hs_error_t rv = hs_compress_stream(stream, buf, cap, &need);
if (rv == HS_INSUFFICIENT_SPACE) {
    char *bigger = realloc(buf, need);
    if (bigger) {
        buf = bigger;
        cap = need;
        rv = hs_compress_stream(stream, buf, cap, &need);
    }
}
if (rv == HS_SUCCESS) {
    /* need 现在是实际使用量，可写入会话表 */
}
```

注意 `need` 在成功时是「已用」，在失败时是「所需」，语义随返回值变化，这是接口里最容易写错的一处。稳妥的做法是每次调用后立刻按返回值分支处理，不要先读 `need` 再判断。

### 6. 注意事项、陷阱与最佳实践

第一，压缩表示没有自描述头，跨版本、跨平台、跨数据库展开都是未定义行为。它只包含「字段的裸字节」，解码完全依赖 `RoseEngine` 的布局；一旦数据库换了版本，偏移含义就变了，`expand_stream()` 会按错误的位置解释内存。生产上应把「数据库指纹 + 版本 + 会话编号」写在自己的封装头里，还原前先比对，而不是把裸压缩串直接扔进共享缓存。

第二，压缩表示里包含状态标志，因此「已终止的流」压缩后展开仍然是已终止的。如果业务在回调里返回非零终止了扫描，然后想把流冻结、稍后恢复，恢复后第一次 `hs_scan_stream()` 会直接返回 `HS_SCAN_TERMINATED`，不会处理新数据。这不是 bug，而是「终止」被当作流的终态记录下来了。需要「可恢复的暂停」时，不要在回调里终止，改用 `hs_copy_stream()` 分叉。

第三，`hs_compress_stream()` 不关闭流。压缩之后原流依然可用、依然需要 `hs_close_stream()` 释放；忘记关闭就是稳定的内存泄漏，而且泄漏量与流数量成正比，在小流量测试里根本看不出来。

第四，`offset` 是流级累计值，跨块不会归零。把回调里的 `from`、`to` 减去「本块起始偏移」是错的；正确做法是直接用流级偏移，或者在业务层维护「本会话已喂入字节数」做展示换算。

第五，历史窗口之外不可回放。`historyRequired` 是编译期按模式算出的上界，喂数据的顺序一旦打乱（比如 TCP 乱序段直接送进来、或者重传时重复喂了旧数据），匹配结果就没有意义。流式接口不做重组、不做去重，这是库的能力边界。

第六，`hs_stream_size()` 是上界不是实际占用。把它乘以会话数做容量规划会严重高估；把压缩输出当上界又会低估并频繁触发 `HS_INSUFFICIENT_SPACE`。可行做法是「按上界分配对象池、按压缩输出计入持久化容量」两套数字分开管理。

第七，`hs_reset_stream()` 保留历史、重置其余状态，`init_stream` 的 `init_history` 参数为 0 就是这个意思；如果业务希望「完全等价于新流」，需要在重置后先喂一段与旧数据无关的填充，或者直接关闭重开。误以为重置会清历史，会导致新会话的第一个匹配莫名带上旧会话的尾巴。

第八，scratch 依然不是线程安全的。流可以多线程各自持有，但**同一个 scratch 不能并发进入**；`hs_scan_stream()` 里 `markScratchInUse()` 失败会直接返回 `HS_SCRATCH_IN_USE`，这是保护而不是排队。正确模型是「一线程一 scratch，流可跨线程迁移但迁移时必须保证没有并发扫描」。

### 7. 小结与延伸阅读

流式匹配的本质是「把未决状态外化成一块可搬运的内存」。Hyperscan 把这块内存切成若干语义明确的区域，用 `stateOffsets` 索引，用 multibit 描述活跃性，再用一份三展开的模板实现「压缩 / 还原 / 计长」三条路径。压缩之所以有效，不是因为用了通用压缩算法，而是因为真实流里大量区域是空的，而库知道怎么只搬活的那些。

记住三件事：压缩表示与数据库强绑定，必须自带版本与指纹；压缩是逐字段按活跃度搬运，长度随状态波动；压缩不等于关闭，还原不等于续传，`hs_reset_and_expand_stream` 才是「原地接续」的语义。

延伸阅读建议：想弄清状态区域逐字段含义查 05-09 与 05-05；想弄清 `hs_open_stream` 系列 API 的返回码与参数查 04-05；想弄清 `historyRequired` 与 SOM horizon 是如何在编译期算出来的，回看 06-10 与 06-04；工程侧的流式接入与数据库分发分别见 03-05、03-03；模块边界见 07-10。本篇的检索口径统一为（字段见 05-09 ｜ 参数见 04-05 ｜ 模块见 07-10）。

## 06-12 数据库序列化、版本校验与 HMAC 完整性

### 1. 背景与动机

Hyperscan 的数据库是编译产物，编译一次可能要几秒到几分钟，扫描一块数据却只要微秒级。这个不对称决定了生产部署的正确形态：在构建机上编译、序列化成字节流、分发到成百上千个节点、在节点上反序列化加载。序列化因此不是「可选优化」，而是部署模型的基础设施。

一旦数据库变成「在网络上传输、在磁盘上存放的字节流」，它就从「可信的内部对象」变成了「不可信的输入」。这个转变很关键，因为数据库不是纯数据：它是一段被运行的字节码，里面有大量偏移量、表长度、状态宽度。一个被篡改的偏移可以让扫描器越界读，一个被篡改的长度可以让反序列化拷贝溢出。所以 Hyperscan 在头部放了两级完整性校验：`hmac_hdr` 保护头部字段（尤其是 `length`），`hmac` 保护字节码本体。顺序不能反——不先确认 `length` 可信，就不能按 `length` 去读字节码算 HMAC。

第三个动机是「版本与平台绑定」。数据库里嵌着编译时的假设：字节码的布局随版本变化，指令集随目标平台变化，扫描模式（block / stream / vectored）也写进了引擎头。加载时必须逐项核对，否则轻则行为错乱，重则崩溃。这三个核对分别对应 `HS_DB_VERSION_ERROR`、`HS_DB_PLATFORM_ERROR`、`HS_DB_MODE_ERROR`，它们是排障时最有信息量的三个返回码。

最后要澄清一个常见误解：HMAC 在这里证明的是「这段字节由持有 `HS_DB_HMAC_KEY` 的构建产出，且未被改动」，而不是「这段字节是可信的」。密钥是编译进库里的常量，任何拿到库文件的人都能提取。它的真实作用是防传输损坏、防误配（把 A 版本的库配给 B 版本的数据库）、防「随手改一个字节试试」的低成本篡改，而不是防御有能力读二进制并重新签名的攻击者。把它当签名体系用，是安全设计上的误判。

### 2. 核心概念

数据库头部是固定 192 字节的结构：`magic`、`version`、`length`、`platform`、`bytecode`、`hmac[32]`、`hmac_hdr[32]`、`padding[25]`，随后是可变的 `bytes[]`。`bytes[]` 起始偏移固定为 192，`padding` 的作用就是把头部撑到这个位置，同时保证按 64 字节缓存行对齐调整 `bytecode` 时，字节码起点不会落进两个 HMAC 字段里。`bytecode` 是「相对数据库起点的字节码偏移」，由于对齐需要，它可能小于 192，所以合法范围是 `[offsetof(padding), offsetof(bytes)]` 这个区间，运行时会显式检查。

`HS_DB_MAGIC` 默认是 `0xdbdbdbdb`，可以在构建期用 `-DHS_DB_MAGIC=` 替换成站点私有值；`HS_DB_VERSION` 直接取 `HS_VERSION_32BIT`，即把主次修订版本压进一个 32 位整数。这两个值构成「廉价校验」：`validDatabase()` 只查这两项，因为它在每次扫描入口都会被调用，不能做重活。真正完整的检查是 `dbIsValid()`，它还会查平台、对齐、两级 HMAC、字节码偏移、状态布局、NFA 表边界。

序列化格式有一个很容易被忽略的细节：**序列化流里没有 `bytecode` 字段**。`hs_serialize_database()` 按 `magic`、`version`、`length`、`platform`（两个 32 位）、`hmac`、`hmac_hdr` 的顺序写出，然后直接跟字节码本体；反序列化时由 `db_copy_bytecode()` 根据目标缓冲区地址重新计算对齐后的偏移并写回头部。这样同一份序列化数据可以在不同对齐的缓冲区里加载，代价是「序列化长度 = 192 + length」而不是「头部原样拷贝」。

平台描述 `platform` 是一个 64 位掩码，除了 CPU 特性位，还有几个「否定位」：`HS_PLATFORM_NOAVX2`、`HS_PLATFORM_NOAVX512`、`HS_PLATFORM_NOAVX512VBMI`，它们表示「编译时明确知道目标不支持该特性」。`HS_PLATFORM_ALL`（`0xabcdef11abcdef00`）表示通用数据库，任何平台都接受。这一套设计的目的是让「用 AVX2 编译的数据库」不会被「只有 SSSE3 的机器」加载，也让「通用数据库」能到处跑。

两级 HMAC 的分工值得单独说。`hmac_hdr` 覆盖头部字段（含 `length`），`hmac` 覆盖 `length` 字节的字节码。校验顺序是「先头后体」，原因很实在：不知道 `length` 是否可信，就不能按它去读内存。`db_check_header_integrity()` 与 `db_check_integrity()` 分别对应这两级，比较时用 `CRYPTO_memcmp()` 做常量时间比较，避免时序侧信道。

最后是「只读保护」。反序列化成功后会对整块内存调用 `hs_db_protect()`，把它标记为只读。这既是安全加固（防止运行期被改写），也意味着调用方不能把 `hs_deserialize_database_at()` 的目标缓冲区当成普通内存随意写。

### 3. 关键数据结构与源码位置

头部结构 `struct hs_database` 定义在 `src/database.h`，`hs_get_bytecode()` 与 `validDatabase()` 是同文件的 inline 函数；`HS_DB_VERSION` 与 `HS_DB_MAGIC` 也在该文件。HMAC 密钥在 `src/hs_db_hmac_key.h`：默认是一段 32 字节的静态数组 `HS_DB_HMAC_KEY`，若定义了 `HS_DB_HMAC_KEY_OVERRIDE` 则改用外部传入的数组，这是一个纯编译期开关，没有运行期换钥接口。字段逐项含义见 05-02。

实现全部在 `src/database.c`：`hs_serialize_database`（`database.c:116`）、`db_check_platform`（`database.c:179`）、`db_decode_header`（`database.c:198`）、`db_check_integrity`（`database.c:254`）、`hs_deserialize_database_at`（`database.c:2935`）、`hs_deserialize_database`（`database.c:3008`）、`hs_database_size`（`database.c:3085`）、`hs_serialized_database_size`（`database.c:3106`）、`dbIsValid`（`database.c:3124`）、`hs_database_info`（`database.c:3397`）。另有 `db_validate_rose_offsets()` 与 `db_validate_mcsheng_succ_table()` 等一批结构校验函数，负责在加载期把「伪造偏移」挡在运行之前。

需要特别指出：`dbIsValid()` 的校验链里**没有**扫描模式检查。模式检查发生在运行接口入口，`hs_scan()` 比较 `rose->mode != HS_MODE_BLOCK`、`hs_open_stream()` 与 `hs_stream_size()` 比较 `HS_MODE_STREAM`、`hs_scan_vector()` 比较 `HS_MODE_VECTORED`，不符即返回 `HS_DB_MODE_ERROR`。这意味着同一个数据库可以被成功反序列化，却在第一次扫描时告诉您模式不对——排障时不要把这两个阶段混为一谈。

下表把常见返回码与其真正触发点对应起来，避免把「加载失败」笼统归因于 HMAC。

| 返回码 | 触发点 | 典型原因 |
|---|---|---|
| `HS_INVALID` | 魔数、长度、对齐、HMAC、偏移校验 | 字节流被截断或改写，缓冲区未对齐 |
| `HS_DB_VERSION_ERROR` | `db_decode_header` 的版本比较 | 数据库与库版本不一致 |
| `HS_DB_PLATFORM_ERROR` | `db_check_platform` | 目标机缺少编译时假定的指令集 |
| `HS_DB_MODE_ERROR` | `hs_scan` / `hs_open_stream` 入口 | 用块库走流式接口，或反之 |
| `HS_NOMEM` | 反序列化分配或分配器回调 | 内存不足，或自定义分配器返回空 |
| `HS_BAD_ALIGN` | 序列化 / `_at` 反序列化 | 数据库或目标缓冲区未按要求对齐 |

一个实用推论：如果 `hs_serialized_database_size()` 就已经失败，说明头部结构本身有问题（长度不足、魔数错、版本错），根本还没走到 HMAC；如果它成功而 `hs_deserialize_database()` 失败，问题多半在 HMAC 或后续结构校验。

### 4. 关键流程与调用链

序列化链路较短但有几处校验不能省。`hs_serialize_database()` 先查三个指针非空，再 `db_correctly_aligned()` 检查对齐（不对齐返回 `HS_BAD_ALIGN`），然后 `validDatabase()` 查魔数与版本，接着**先**校验头部 HMAC、**再**校验字节码 HMAC——注释写得很清楚：只有确认 `length` 真实，才能按它去读字节码。全部通过后按 `192 + length` 分配内存，逐字段写出，最后把字节码整段拷到头部之后。

反序列化链路分为「解码头部」与「装载」两段。`db_decode_header()` 是两段共用的：先要求至少 12 字节（保证老数据库能走到版本检查而不是直接报无效），用非对齐读取出 `magic`；魔数不符返回 `HS_INVALID`；版本不符返回 `HS_DB_VERSION_ERROR`；确认前两项后才要求完整 192 字节头部；读 `length` 并核对「传入长度 == 192 + length」；最后读出 `platform` 与两个 HMAC，把指针推进到字节码起点。

装载段的关键差别在内存归属。`hs_deserialize_database()` 自己用 `hs_db_alloc()` 分配（页对齐），把头部与字节码拷进去，再做两级 HMAC 与结构校验，成功后 `hs_db_protect()` 置只读；`hs_deserialize_database_at()` 则要求调用方提供 8 字节对齐、容量足够的缓冲区，它只做 `memset`、拷头、`db_copy_bytecode()`、校验，最后同样置只读。前者的注释明确提醒：函数**无法**验证你给的缓冲区到底有多大，必须自己先调 `hs_serialized_database_size()` 拿到所需尺寸。

`db_copy_bytecode()` 是「零拷贝」假象的来源：它并不真的零拷贝，而是把字节码搬到目标缓冲区里紧邻头部的对齐位置，并回填 `db->bytecode`。所谓「at」版本省掉的是一次额外分配和一次整体搬运（数据本来就在你的缓冲区里），代价是你要自己管对齐、容量与生命周期。真正的零拷贝只有一种情况：数据库本来就已经在内存里且对齐正确，那就根本不需要反序列化。

加载完成后的校验链与 `dbIsValid()` 一致：魔数 → 版本 → 平台 → 对齐 → 头部 HMAC → 字节码 HMAC → 字节码偏移范围 → 状态布局 → NFA 表边界。任意一步失败都会释放已分配内存并返回，不会留下半加载对象。整条顺序见图 06-12-01。

### 5. 配置/命令/代码实例

下面的程序演示完整往返，并在最后故意翻转字节码首字节，观察篡改后的返回码。序列化后第 192 字节正是字节码起点（头部固定 192 字节），所以翻转它等价于破坏内容而不动头部。

```c
#include <hs.h>
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    hs_database_t *db = NULL;
    hs_database_t *loaded = NULL;
    hs_compile_error_t *cerr = NULL;

    if (hs_compile("foo[0-9]{3}", 0, HS_MODE_BLOCK, NULL, &db, &cerr)
        != HS_SUCCESS) {
        fprintf(stderr, "compile: %s\n", cerr->message);
        hs_free_compile_error(cerr);
        return 1;
    }

    char *bytes = NULL;
    size_t len = 0;
    if (hs_serialize_database(db, &bytes, &len) != HS_SUCCESS) {
        fprintf(stderr, "serialize failed\n");
        return 1;
    }
    printf("serialized length = %zu\n", len);

    size_t want = 0;
    if (hs_serialized_database_size(bytes, len, &want) == HS_SUCCESS) {
        printf("deserialized size = %zu\n", want);
    }

    if (hs_deserialize_database(bytes, len, &loaded) == HS_SUCCESS) {
        char *info = NULL;
        if (hs_database_info(loaded, &info) == HS_SUCCESS) {
            printf("%s\n", info);
            free(info);
        }
        hs_free_database(loaded);
        loaded = NULL;
    }

    bytes[192] ^= 0x01; /* 篡改字节码第一个字节，头部不动 */
    hs_error_t rv = hs_deserialize_database(bytes, len, &loaded);
    printf("tampered deserialize rv = %d\n", rv);

    free(bytes);
    hs_free_database(db);
    return 0;
}
```

示例输出，具体格式需对照实际版本核验。

```text
serialized length = 1933
deserialized size = 1933
Version: 5.4.2 Features: AVX2 Mode: BLOCK
tampered deserialize rv = -1
```

逐行判读。第一行的 1933 等于 192 加字节码长度，说明序列化长度与头部长度是固定换算关系，看到这个数就能反推字节码本体大小；不同模式、不同模式集会显著改变它，此处的具体数值仅作示例。第二行来自 `hs_serialized_database_size()`，它只解码头部、不碰字节码，因此速度极快，适合在「先问多大再分配」的两段式加载里做前置探测；它与第一行相等是正常的，因为反序列化后占用恰好是「头部 + 字节码」。第三行是 `hs_database_info()` 的输出，格式固定为版本、特性、模式三段；`AVX2` 表示该数据库的目标平台允许 AVX2，`BLOCK` 表示只能用 `hs_scan()`，若拿它去 `hs_open_stream()` 会得到 `HS_DB_MODE_ERROR`。第四行的 `-1` 是 `HS_INVALID`，不是专门的「HMAC 错误码」——这一点很容易误判：HMAC 不匹配、魔数错、对齐错、结构校验失败都归到同一个返回值，只能靠上下文（哪一步失败）区分，所以生产代码应在每步之后立即记录阶段，而不是只记最终码。

如果希望把「篡改」与「版本不符」区分开，可以再做一个实验：把 `bytes` 的第 4 到第 7 字节（`version` 字段）改成别的值，重新反序列化，会得到 `-5`，即 `HS_DB_VERSION_ERROR`。这个差别来自 `db_decode_header()` 的判断顺序：版本检查发生在长度检查与 HMAC 之前，所以改版本一定会先被抓住。

```c
/* 把 version 字段（偏移 4，长度 4）改成 0x00000000 */
bytes[4] = 0;
bytes[5] = 0;
bytes[6] = 0;
bytes[7] = 0;
hs_error_t vrv = hs_deserialize_database(bytes, len, &loaded);
printf("bad version rv = %d\n", vrv); /* 期望 -5 */
```

### 6. 注意事项、陷阱与最佳实践

第一，不要依赖 HMAC 做「来源认证」。密钥编译在库里，攻击者拿得到；它的定位是完整性校验与误配拦截。需要真正的信任链，应在数据库外层加自己的签名，并在加载前验证签名再交给 Hyperscan。

第二，`-DHS_DB_HMAC_KEY_OVERRIDE` 是构建期开关，一旦启用，用默认密钥构建的旧数据库会全部加载失败，且错误码是 `HS_INVALID`，没有任何「密钥不匹配」的提示。切换密钥必须与数据库重新分发同步进行，不能灰度一半。

第三，`HS_DB_VERSION` 只比较主次修订压成的整数，不比较构建配置。相同版本号、不同 `HS_DB_MAGIC`、不同 `BUILD_AVX512`、不同 `HS_DB_HMAC_KEY_OVERRIDE` 构建出来的库互不接受。跨团队分发数据库时，应把「构建配置指纹」也写进你自己的分发元数据。

第四，`hs_deserialize_database_at()` 不会替你检查缓冲区大小，注释里明确把责任交给调用方。正确顺序永远是：`hs_serialized_database_size()` 拿尺寸 → 分配（8 字节对齐）→ `_at` 加载。省掉第一步就是堆溢出。

第五，加载成功后内存被置为只读。任何「加载后原地改一个字段做实验」的想法都会导致段错误，而不是静默生效。需要可变副本就先复制到自己的缓冲区，再对副本加载。

第六，不要每次进程启动重新编译。编译成本高、峰值内存大，而且会让「同一份配置在不同节点产生不同字节码」成为可能（编译期启发式、硬件特性都会影响产物）。正确姿势是构建期编译、分发、加载；只有开发期才反复编译。

第七，`hs_database_info()` 返回的字符串由默认分配器分配，必须由调用方 `free()`；它只报告版本、特性、模式，不包含模式文本——因为字节码里根本没有原始正则。想核对「这份数据库是不是我编的那份」，只能比对 HMAC 或自己记录的指纹。

第八，序列化数据的长度必须精确。少一个字节会在 `db_decode_header()` 的「长度 == 192 + length」检查处失败；多一个字节同样失败，因为它要求严格相等。文件传输时不要用「读到 EOF 为止」的宽松解析。

### 7. 小结与延伸阅读

序列化把「内存里的编译产物」变成「可分发、可校验的字节流」，代价是把可信对象变成了不可信输入，于是有了头部、魔数、版本、平台、两级 HMAC 与一整套结构校验。校验顺序是设计的核心：先能安全读取（长度、魔数、版本），再验证完整（头 HMAC、体 HMAC），最后验证自洽（偏移、状态布局、NFA 表边界）；模式检查不在这一层，而在扫描入口。

三句话记住本篇：数据库是字节码不是数据，加载等于执行，所以要按不可信输入对待；两级 HMAC 的先后不能反，因为 `length` 本身需要先被认证；版本、平台、模式是三个不同阶段的检查，返回码不同、处置方式也不同。

延伸阅读：字段与偏移细节见 05-02；API 签名与返回码全集见 04-06；工程侧的分发与加载流程见 03-03；安全模型与密钥管理见 08-05；模块边界见 07-10。想理解字节码里到底有什么、为什么偏移校验如此繁琐，回看 06-01 与 06-04。本篇的检索口径统一为（字段见 05-02 ｜ 参数见 04-06 ｜ 模块见 07-10）。

## 06-13 fat runtime 与 CPU 特性分派

### 1. 背景与动机

Hyperscan 的性能高度依赖指令集。字面量前端的 Teddy 用 nibble 查表做位并行，FDR 用分桶加确认表，Sheng 系列用向量 shuffle 做状态压缩，这些引擎在不同微架构上的最佳实现完全不同：SSSE3 只有 16 字节向量，AVX2 有 32 字节，AVX-512BW 有 64 字节且多了掩码寄存器，AVX512VBMI 还多了字节级置换。同一份源码，用不同 `-march` 编译出来的扫描循环，吞吐可以差出数倍。

于是产生一个分发难题：库要交付给成千上万台机器，这些机器的 CPU 代际跨越十年。三条路各有代价。第一条是 `-march=native`，在构建机上达到最优，但产物一到老机器上就执行非法指令，且「构建机是哪台」成了不可复现的隐变量。第二条是每个微架构编一份库，让运维按机器选，代价是发行包膨胀、部署脚本复杂、容器镜像要按节点打标签。第三条是把多份实现塞进同一个动态库，在装载时按当前 CPU 选一份——这就是 fat runtime。

「fat」这个词说的就是体积：同一批源文件被编译五遍，分别针对 core2、corei7、avx2、avx512、avx512vbmi，每份都带自己的符号，最后链接进同一个 `libhs.so`，所以库比单架构版本大数倍。换来的是「编译一次、到处运行」，并且在这台机器上跑的就是这台机器能跑的最快实现。

理解这套机制有三个现实收益。第一，能解释 `HS_ARCH_ERROR` 从哪来：它不是「模式有问题」，而是「这台机器连 SSSE3 都没有」，或者更常见——库在装载时找不到可用实现。第二，能解释「库能跑但数据库加载失败」这种看似矛盾的现象：库的分派是运行期 CPU 探测，数据库的平台位却是编译期的承诺，两者是两套机制。第三，能判断构建选项该怎么选：`FAT_RUNTIME` 决定「一份库多实现」，`BUILD_AVX512` 决定「多实现里是否包含 AVX-512 那两份」，两者的默认值与适用条件完全不同。

需要强调一点边界：fat runtime 是 Linux 上的特性，依赖 GNU 的 `ifunc` 扩展。Windows 的 MSVC 没有对应机制，只能编单架构库；ARM 平台的 Vectorscan 分支有自己的分派方案，不能把这里的结论直接搬过去。这也是本套资料反复标注「上游开源版」的原因。

### 2. 核心概念

微架构分组是这套机制的骨架。构建时按 `-march` 把同一批运行期源文件编成五组：`core2`（SSSE3 基线）、`corei7`（SSE4.2 加 POPCNT）、`avx2`（`-march=core-avx2`）、`avx512`（Skylake 级别的 AVX-512BW）、`avx512vbmi`（Ice Lake 级别）。每组产出一个 OBJECT 库，符号名统一加上后缀：`core2_`、`corei7_`、`avx2_`、`avx512_`、`avx512vbmi_`。公共符号 `hs_scan` 本身不实现任何逻辑，它只是一层跳板。

跳板的实现是 `ifunc`（indirect function）。写法是「声明一个同名函数，挂上 `__attribute__((ifunc("resolver名")))`」，动态链接器在装载时调用 resolver，把返回值（某个实现的地址）填进这个符号。关键在于**解析只发生一次**：之后每次调用 `hs_scan` 都是一次普通的间接跳转，没有 `cpuid`、没有分支预测惩罚、没有每次调用的探测开销。这是 fat runtime 相对「每次调用查表」方案的核心优势。

resolver 的顺序就是优先级：先 `check_avx512vbmi()`，再 `check_avx512()`，再 `check_avx2()`，再「`check_sse42()` 且 `check_popcnt()`」，再 `check_ssse3()`，全不满足则返回 `error_` 版本。`error_` 版本不做任何事，直接返回 `HS_ARCH_ERROR`。这个顺序体现了两条原则：能力越强越优先；能力必须「配套」——corei7 那档要求 SSE4.2 与 POPCNT 同时具备，因为那份实现里两者都用。

`check_*` 系列在 `src/util/cpuid_inline.h`，每个函数做一次 `cpuid` 并按位判断，内部还处理了操作系统是否开启相应寄存器状态（XGETBV）的情况。这些函数是 `static inline`，编译进各自的实现里；resolver 只在装载时跑一遍，所以这点开销无所谓。

`hs_valid_platform()` 是一个容易误解的接口：它只检查 SSSE3，因为那是 Hyperscan 的硬性下限。它返回 `HS_SUCCESS` 不代表 AVX2 可用，更不代表数据库能加载。真正想知道「这台机器支持什么」要用 `hs_populate_platform()`：它把 `cpuid_flags()` 的结果写进 `hs_platform_info_t::cpu_features`（只含 AVX2、AVX512、AVX512VBMI 三位），把 `cpuid_tune()` 的微架构家族写进 `tune`。这两个值可以直接传给 `hs_compile` 的 `platform` 参数，让编译产物针对本机优化。

平台位是另一套东西。`database.h` 里定义了 `HS_PLATFORM_NOAVX2`、`HS_PLATFORM_NOAVX512`、`HS_PLATFORM_NOAVX512VBMI` 三个「否定位」，以及 `HS_PLATFORM_ALL` 这个通用值。否定式编码的好处是「缺省即可用」：没写否定位，就表示编译时假定这些特性可用。`hs_current_platform` 是一个 `static const` 常量，由 `HAVE_AVX2` 等编译期宏拼出来——注意它是**编译期**决定的，不是运行期探测的。在 fat 构建下，每个微架构分组的 `database.c` 各编一份，于是各分组看到的 `hs_current_platform` 也不同，平台校验自然跟着「选中的实现」走：选了 AVX2 实现，就只接受允许 AVX2 的数据库。

构建条件值得单独记。`FAT_RUNTIME` 只在 `CMAKE_SYSTEM_NAME MATCHES Linux` 时才被定义，且要满足三个前提：编译器支持 `ifunc` 属性（`HAS_C_ATTR_IFUNC`）、生成器是 Unix Makefiles 或 CMake 3.0 以上的 Ninja、Clang 版本不低于 3.9。任一条不满足，`FAT_RUNTIME_REQUISITES` 为假，这个选项根本不会出现。默认值取 `${RELEASE_BUILD}`，也就是 release 构建默认开启、debug 构建默认关闭。`BUILD_AVX512` 与 `BUILD_AVX512VBMI` 则是普通的 `option`，默认都是 `OFF`；后者为真时会强制把前者也打开，因为 VBMI 隐含 AVX-512。

不打开这两个选项时，CMake 会往 `dispatcher.c` 的编译命令里加 `-DDISABLE_AVX512_DISPATCH` 与 `-DDISABLE_AVX512VBMI_DISPATCH`。`dispatcher.c` 顶部据此把 `avx512_` 前缀重定义成 `disabled_`、把 `check_avx512()` 重定义成恒假。于是「库里没有这份实现」和「有实现但探测不到」在代码上统一成了同一种形态：resolver 跳过这一档。这样 dispatcher 的源码只有一份，不需要为每种开关组合写条件编译分支。

### 3. 关键数据结构与源码位置

分派层只有一个文件：`src/dispatcher.c`。核心是 `CREATE_DISPATCH` 宏（`dispatcher.c:46`），它为每个公共函数生成五条前置声明、一个 `error_` 实现、一个 `resolve_` 解析器（`dispatcher.c:60`），以及挂了 `ifunc` 属性的公共符号（`dispatcher.c:82`）。宏之后是一长串展开：`hs_scan`、`hs_stream_size`、`hs_database_size`、`dbIsValid`、`hs_open_stream`、`hs_scan_stream`、`hs_close_stream`、`hs_scan_vector`、`hs_database_info`、`hs_copy_stream`、`hs_reset_stream`、`hs_reset_and_copy_stream`、`hs_serialize_database`、`hs_deserialize_database`、`hs_deserialize_database_at`、`hs_serialized_database_info`、`hs_serialized_database_size`、`hs_compress_stream`、`hs_expand_stream`、`hs_reset_and_expand_stream`（`dispatcher.c:84` 起）。逐个看这张清单能发现一个事实：**分派粒度是公共 API**，不是内部函数；库内部调用走的是同一份实现里的直接调用，没有二次间接。

CPU 探测在 `src/util/cpuid_inline.h`：`check_avx2`（`cpuid_inline.h:112`）、`check_avx512`（`cpuid_inline.h:148`）、`check_avx512vbmi`（`cpuid_inline.h:191`）、`check_ssse3`（`cpuid_inline.h:236`）、`check_sse42`（`cpuid_inline.h:243`）、`check_popcnt`（`cpuid_inline.h:250`）。平台信息组装在 `src/util/cpuid_flags.c`：`cpuid_flags`（`cpuid_flags.c:40`）只置三个特性位，`cpuid_tune`（`cpuid_flags.c:146`）按 family/model 查表映射到 `HS_TUNE_FAMILY_*`。公共入口 `hs_valid_platform()` 在 `src/hs_valid_platform.c`，`hs_populate_platform()` 在 `src/hs.cpp` 末尾附近，两者都很短。

编译期特性宏在 `src/util/arch.h`：`HAVE_SSE2`、`HAVE_SSE41`、`HAVE_SSE42`、`HAVE_AVX`、`HAVE_AVX2`、`HAVE_AVX512`（对应 `__AVX512BW__`）、`HAVE_AVX512VBMI`、`HAVE_POPCOUNT_INSTR`、`HAVE_BMI`、`HAVE_BMI2`。这些宏不只用于分派，也用于各引擎在编译期裁掉本平台用不上的代码路径——所以「同一份源码在不同分组里编出来的引擎集合都可能不同」。

构建侧全部在 `CMakeLists.txt`：`BUILD_AVX512` 与 `BUILD_AVX512VBMI` 的 `option` 与蕴含关系（`CMakeLists.txt:142` 起）、`FAT_RUNTIME_REQUISITES` 的四项判定与 `CMAKE_DEPENDENT_OPTION`（`CMakeLists.txt:332` 起）、非 fat 分支的单一 `-march` 编译（`CMakeLists.txt:1194` 起）、fat 分支的五组 OBJECT 库与 `-DDISABLE_*_DISPATCH`（`CMakeLists.txt:1224` 起）。分组编译时用 `cmake/build_wrapper.sh` 配合 `cmake/keep.syms.in` 做符号重命名与保留，这条链路决定了 `libhs.so` 里最终存在哪些带后缀的符号。

下表把分组、编译标志与符号后缀对应起来，便于在 `nm` 输出里对号入座；构建变量全集见 04-01，平台与特性常量见 04-03。

| 微架构分组 | 编译标志 | 符号后缀 | 最低硬件要求 |
|---|---|---|---|
| core2 | `-march=core2` | `core2_` | SSSE3 |
| corei7 | `-march=corei7` | `corei7_` | SSE4.2 且 POPCNT |
| avx2 | `-march=core-avx2` | `avx2_` | AVX2 |
| avx512 | `${SKYLAKE_FLAG}` | `avx512_` | AVX-512BW |
| avx512vbmi | `${ICELAKE_FLAG}` | `avx512vbmi_` | AVX512VBMI |
| 兜底 | 无 | `error_` | 无，直接返回错误码 |

`SKYLAKE_FLAG` 与 `ICELAKE_FLAG` 的具体取值由 `cmake/arch.cmake` 按编译器能力探测，不同 GCC 版本上可能回退到近似标志，因此「打开 `BUILD_AVX512` 就一定有 AVX-512BW 实现」这句话要打个折扣，需对照实际工具链核验。

### 4. 关键流程与调用链

构建期的分流从 `CMakeLists.txt:332` 开始。先判断系统是不是 Linux；不是就整段跳过，`FAT_RUNTIME` 选项不存在，缓存里查不到这个键。是 Linux 则依次判断 Clang 版本、生成器类型、`ifunc` 支持，三项全过才把 `FAT_RUNTIME_REQUISITES` 置真，再用 `CMAKE_DEPENDENT_OPTION` 定义 `FAT_RUNTIME`，默认值等于 `RELEASE_BUILD`。

进入 fat 分支后，CMake 为每个分组建一个 OBJECT 库：`hs_exec_core2`、`hs_exec_corei7`、`hs_exec_avx2`，条件满足时再加 `hs_exec_avx512` 与 `hs_exec_avx512vbmi`。每个库都编译同一批 `hs_exec_SRCS`（运行期引擎与 `database.c`、`runtime.c` 等），AVX-512 那两组还会额外并入 `hs_exec_avx2_SRCS`。编译时通过 `RULE_LAUNCH_COMPILE` 调用 `build_wrapper.sh`，用 `objcopy` 把全局符号按分组重命名——这是「同一份源码编出五套互不冲突的符号」的实现手段。最后 `hs_exec_common`（含 `dispatcher.c`）与所有分组一起链进 `hs` 与 `hs_runtime`。

运行期的分流发生在装载时。动态链接器遇到带 `ifunc` 的符号，调用 `resolve_hs_scan()`；resolver 依次问 `check_avx512vbmi()`、`check_avx512()`、`check_avx2()`、`check_sse42() && check_popcnt()`、`check_ssse3()`，返回第一个为真的实现地址；全假返回 `error_hs_scan`。这个返回值被写入符号的解析结果，后续调用直接跳过去。整个过程没有加锁、没有缓存失效问题，因为 `ifunc` 的解析由装载器保证只做一次。

需要注意的是 resolver 的失败路径不是「装载失败」，而是「装载成功但调用返回 `HS_ARCH_ERROR`」。这个设计让「库能被加载」与「库能用」解耦：即使跑在不支持 SSSE3 的机器上，程序也能启动，只有在真正调用扫描接口时才拿到错误码。这对「先启动、后探测能力」的服务模型是有利的，但也意味着监控必须覆盖首次调用的返回码，否则会看到「进程活着但一条流量都没处理」的诡异现象。

编译侧还有一处 `FAT_RUNTIME` 条件编译：`hs_compile_multi_int()` 在入口处检查 `check_ssse3()`，不满足直接返回 `HS_ARCH_ERROR` 并给出「Unsupported architecture」；`hs_expression_info`、`hs_free_compile_error` 等入口也有同样的守卫（`src/hs.cpp` 中三处 `#if defined(FAT_RUNTIME)`）。为什么编译也要查？因为 fat 库为了能在老机器上装载，装载路径本身不能含 SSSE3 指令，但编译与扫描路径是按分组编的，真的跑起来必须有 SSSE3 打底。

最后要理解平台位的闭环：编译时 `hs_compile` 把 `platform` 参数（或 `get_current_target()` 的结果）写进数据库头部；加载时 `db_check_platform()` 把它与当前实现里的 `hs_current_platform` 比对，不等就返回 `HS_DB_PLATFORM_ERROR`。这条链解释了那个常见困惑——「同一个 `.so` 在这台机器上能跑，为什么加载那份数据库失败」：库能跑只说明有可用实现，数据库能否加载还取决于它的平台位是否被这份实现接受。如果希望数据库到处都能加载，编译时传 `HS_PLATFORM_ALL`。

edge n5 -> n9 "avx2_"
edge n5 -> n6 "不支持"
edge n6 -> n9 "corei7_"
edge n6 -> n7 "不支持"
edge n7 -> n9 "core2_"

:::

图里没有画「解析结果被缓存」这一步，因为它不是代码，而是装载器的语义：resolver 的返回值被写进符号表项后就不再重算。理解这一点，才能解释为什么「在容器里改了 CPU 亲和性」不会让分派结果变化——分派在进程装载时就定了。

### 5. 配置/命令/代码实例

先看构建侧。下面的命令在 Linux 上以 release 配置一次，然后从缓存里读出三个关键变量。默认情况下 `FAT_RUNTIME` 应为 `ON`，两个 AVX-512 选项应为 `OFF`。

```bash
mkdir -p build && cd build
cmake -DCMAKE_BUILD_TYPE=Release -DBUILD_AVX512=OFF -DBUILD_AVX512VBMI=OFF ../
grep -E "^(FAT_RUNTIME|BUILD_AVX512|BUILD_AVX512VBMI):" CMakeCache.txt
```

示例输出，具体格式需对照实际版本核验。

```text
FAT_RUNTIME:BOOL=ON
BUILD_AVX512:BOOL=OFF
BUILD_AVX512VBMI:BOOL=OFF
```

逐行判读。第一行说明这次构建走的是「一份库多套实现」的路径，产物里应当能找到 `avx2_hs_scan`、`corei7_hs_scan` 这类带后缀的符号；如果这里是 `OFF`，说明 `FAT_RUNTIME_REQUISITES` 有一项没满足——最常见的是生成器不是 Unix Makefiles 或 Ninja，其次是编译器不支持 `ifunc`，CMake 在配置阶段会打印具体原因，往上翻几十行就能看到。第二、三行为 `OFF` 表示库里不含 AVX-512 与 VBMI 两组实现，resolver 里对应的两个 `check_*` 被编译成恒假；这不影响功能，只影响在 Skylake 及以上机器上的峰值吞吐。如果第三行是 `ON` 而第二行是 `OFF`，说明缓存被人手工改过——正常情况下 `BUILD_AVX512VBMI` 会把 `BUILD_AVX512` 强制拉成 `ON`。如果三行全部查不到，先确认是不是在非 Linux 平台构建：那里根本没有这几个选项。

再看运行侧。下面的程序回答两个问题：「这台机器能不能跑 Hyperscan」以及「它能跑哪一档」。

```c
#include <hs.h>
#include <stdio.h>

int main(void) {
    hs_error_t v = hs_valid_platform();
    printf("hs_valid_platform = %d\n", v);

    hs_platform_info_t p;
    if (hs_populate_platform(&p) == HS_SUCCESS) {
        printf("cpu_features = 0x%llx tune = %u\n",
               (unsigned long long)p.cpu_features, p.tune);
    } else {
        printf("hs_populate_platform failed\n");
    }
    return 0;
}
```

示例输出，具体格式需对照实际版本核验。

```text
hs_valid_platform = 0
cpu_features = 0x4 tune = 6
```

逐行判读。第一行 `0` 是 `HS_SUCCESS`，含义仅为「这台机器至少有 SSSE3」，这是 Hyperscan 的硬性下限，不代表能跑 AVX2；如果这里是 `-11`（`HS_ARCH_ERROR`），后面的扫描一定失败，应当直接拒绝启动而不是重试。第二行的 `cpu_features` 是 `HS_CPU_FEATURES_*` 的按位或，`0x4` 等于 `1ULL << 2`，即只置了 `HS_CPU_FEATURES_AVX2` 这一位，说明这台机器支持 AVX2 但不支持 AVX-512（否则会多出 `0x8` 甚至 `0x10`）；这个值可以直接作为 `hs_compile` 的 `platform->cpu_features` 传入，让编译产物针对本机生成。`tune = 6` 是 `cpuid_tune()` 按 family/model 映射出的微架构家族编号，对照 `hs_compile.h` 的 `HS_TUNE_FAMILY_*` 序列，6 对应 Skylake 家族；换一台机器这个数会变，具体映射需对照实际版本核验。要注意这两个值描述的是「当前机器」，不是「当前库」——库的分派结果无法通过公共 API 查询，只能靠 `nm` 看符号、靠基准测试间接判断。

如果想知道某个 `.so` 到底带了哪几套实现，可以用符号表反查。带后缀的符号存在，说明该分组被编进了库；只有 `error_` 而没有某档，说明该档被 `DISABLE_*_DISPATCH` 关掉了。

```bash
nm -D --defined-only build/lib/libhs.so | grep -E "_(hs_scan|hs_open_stream)$"
```

`nm` 的输出里，`hs_scan` 本身通常显示为 `i`（间接函数）类型，带后缀的才是真正的代码符号。这条命令的价值在于验证「构建选项是否真的生效」——比读 CMake 缓存更直接。

### 6. 注意事项、陷阱与最佳实践

第一，不要把 `hs_valid_platform()` 当成能力探测。它只查 SSSE3，在只支持 SSSE3 的机器上也会返回成功，随后 AVX2 相关路径根本不会被执行（分派会退到 core2），性能可能只有预期的三分之一。要判断实际档位，用 `hs_populate_platform()` 读特性位，或者直接用基准测试对比。

第二，`FAT_RUNTIME` 在非 Linux 平台上不存在，不是「默认关闭」。跨平台项目里写 `-DFAT_RUNTIME=ON` 在 Windows 上不会报错，但也不会生效，产物仍是单架构。构建脚本应当显式检查平台，而不是假设选项一定被识别。

第三，关闭 fat runtime 后，库只含一套 `-march` 实现，通常就是构建机默认的架构。这种库拿到老机器上不是返回 `HS_ARCH_ERROR`，而是直接执行非法指令导致进程崩溃——错误形态完全不同。要发布到异构机群，必须用 fat runtime 或明确的最低架构标志（如 `-march=core2`）构建。

第四，`BUILD_AVX512` 不是「打开就更快」。AVX-512 在部分负载下会触发降频，且 512 位向量对短模式、小块的收益有限；Hyperscan 把它标为实验性选项、默认关闭，是有工程依据的。上线前应在目标机群上做 A/B，而不是看单机峰值。

第五，数据库的平台位是编译期承诺，不是运行期探测。用 `hs_populate_platform()` 的结果去编译，得到的数据库就只能在那台机器（或同档机器）上加载；要跨机群分发，编译时传 `HS_PLATFORM_ALL`，接受「不针对具体微架构优化」的代价。把这两件事混为一谈，就会出现「同一份数据库在一半节点上 `HS_DB_PLATFORM_ERROR`」的现场。

第六，静态链接 fat runtime 时，`ifunc` 依赖链接器与 C 库的支持。老版本 binutils 或不支持 `STT_GNU_IFUNC` 的工具链可能在链接期就报错，或者运行期解析失败。这类问题不会在编译日志里显眼地出现，需对照工具链版本核验。

第七，`libhs` 与 `libhs_runtime` 是两种产物：后者只含扫描侧，不含编译 API。用 `libhs_runtime` 的节点无法 `hs_compile`，只能加载序列化数据库。分派逻辑两者都有，但「能编译」这件事取决于链接了哪个库——这是部署时最容易配错的一处（模块见 07-10）。

第八，不要在运行期期待「换 CPU 就换实现」。解析在装载时完成，容器热迁移、cpuset 调整、甚至在同一进程里 `dlopen` 两次（同一路径）都不会重新解析。需要按机器定制时，应在编排层决定用哪份库或哪份数据库，而不是指望库自己适配。

### 7. 小结与延伸阅读

fat runtime 用「多份编译 + 装载时分派」换取了「一份库到处跑」。它的三个关键点分别是：构建期按 `-march` 分组并用符号后缀隔离；运行期用 `ifunc` 在装载时解析一次并缓存；失败路径收敛到 `error_` 实现，把「不支持」变成 `HS_ARCH_ERROR` 而不是装载失败。与之配套的平台位机制则把「编译时的硬件承诺」写进数据库，加载时与当前实现比对，形成另一条独立的兼容性检查。

记住三件事：分派是装载时的一次性决策，不是每次调用的探测；`hs_valid_platform` 只保证 SSSE3，能力探测要用 `hs_populate_platform`；数据库的平台位与库的分派是两套机制，前者决定「能不能加载」，后者决定「跑得多快」。

延伸阅读：构建变量全集与默认值见 04-01，平台与调优常量见 04-03，工程侧的库形态选择见 02-05，模块职责见 07-10；想理解各档实现在引擎层面差在哪里，回看 06-05、06-08 与 06-09。本篇的检索口径统一为（字段见 05-05 ｜ 参数见 04-01 ｜ 模块见 07-10）。

## 06-14 Chimera 混合引擎：Hyperscan 预过滤 + PCRE 确认

### 1. 背景与动机

Hyperscan 的能力边界很清楚：不支持反向引用、不支持捕获子表达式、不支持任意零宽断言、不支持递归与条件模式。这些构造在真实规则集里并不罕见——「密码出现在 URL 参数里」「同一个单词重复出现」「邮箱的本地部分与域名部分满足某种关系」，都需要回溯语义或捕获结果。纯 Hyperscan 在这些规则上只能拒绝编译。

另一条路是纯 PCRE。功能完整，但代价是「一条模式扫一遍数据」：一万条规则就是一万次全缓冲区扫描，再叠加回溯的最坏情况复杂度，吞吐会掉到不可接受。而且 PCRE 是单模式引擎，没有「一次扫描同时匹配上万条」的概念。

Chimera 的思路是把两者叠起来：用 Hyperscan 的多模式能力做一次快速扫描，把「可能命中」的位置找出来，再让 PCRE 只在这些位置上做精确确认与捕获。Hyperscan 在这里扮演的是**触发器**（trigger）而不是判定器：它只需要保证「真匹配不会被漏掉」，多报一些无所谓，因为后面有 PCRE 兜底。这与 Hyperscan 的预过滤语义正好吻合——`HS_FLAG_PREFILTER` 会把不支持的构造放宽成超集，允许多报，但不允许漏报。

这个设计的收益完全由「命中率」决定。如果规则集在流量上几乎不命中，Hyperscan 一次扫描就排除了 99.9% 的数据，PCRE 只在极少数位置跑，总体吞吐接近纯 Hyperscan。如果规则本身很宽（比如 `\w+` 这种），Hyperscan 会在几乎每个位置触发，PCRE 就要跑几乎每个位置，此时 Chimera 比纯 PCRE 还慢——多了一次 Hyperscan 扫描的开销。所以「Chimera 一定比 PCRE 快」是错的，「Chimera 在稀疏命中场景下接近 Hyperscan」才是准确的表述。

还有一层动机是工程上的：Chimera 把「哪些模式能被 Hyperscan 覆盖」这件事编译期就判定完了，运行期不需要业务代码做分流。规则作者写 PCRE 语法，编译器自动决定每条模式走「Hyperscan 触发 + PCRE 确认」还是「直接 PCRE 扫描」，业务代码只看到一个 `ch_scan`。

需要提前说清边界：Chimera 只有块模式，`ch_compile` 内部固定用 `HS_MODE_BLOCK` 编译底层 Hyperscan 库，公开 API 里没有 `ch_open_stream` / `ch_scan_stream`。需要流式 + 捕获组的场景，只能自己做分块与状态拼接，而那已经超出库的能力范围。

### 2. 核心概念

Chimera 把每条模式分成两类。**guarded** 模式：能用 Hyperscan 的预过滤形式编译出来，于是进入底层多模式库，由 Hyperscan 负责触发。**unguarded** 模式：连预过滤都编不出来（比如某些极端构造），只能自己用 PCRE 全量扫描。分类发生在编译期，判据是 `isHyperscanSupported(pattern, flags | HS_FLAG_PREFILTER, platform)` 是否成功。

在 guarded 里还有一条快速路径：**定宽模式**。如果 `hs_expression_info` 报出的 `min_width` 等于 `max_width`、宽度有限且非零，同时该模式没有捕获组、匹配有序、且不带预过滤也能编译成功，那么 Chimera 认为「Hyperscan 报出的位置就是精确结果」，运行时直接采信，不再调用 PCRE。这条路径把「定宽字面量类规则」的成本压到接近纯 Hyperscan，是 Chimera 性能模型里最重要的优化。

「确认」的具体含义是：Hyperscan 报了一个结束偏移 `to`，Chimera 从该模式上次扫描的起点 `scanStart` 开始，用 `pcre_exec` 在 `[scanStart, length)` 上找第一个匹配；若找到的匹配结束位置不晚于 `to`，就认为确认通过并报告，否则继续找。这个「以 Hyperscan 的结束位置为界」的机制保证了报告顺序与纯 PCRE 一致，不会因为触发器多报而输出多余的匹配。

报告顺序由优先队列保证。每条模式确认出的匹配按 `(from, to)` 入队，出队时按 `to` 升序、同 `to` 按插入顺序，于是用户看到的回调序列与「把所有模式交给 PCRE 逐条扫、再按结束位置归并」的结果一致。这个顺序性对规则引擎很重要——很多业务逻辑依赖「先短后长」「同位置按规则号」的稳定输出。

捕获组通过 `ch_capture_t` 数组传递。回调签名里除了 `from`、`to`，还有 `size`（捕获组个数）与 `captured` 指针；数组第 0 项是整个匹配，第 i 项是第 i 个捕获组，未参与匹配的组用 `CH_CAPTURE_FLAG_ACTIVE` 区分。只有在 `CH_MODE_GROUPS` 模式下才填充捕获组，`CH_MODE_NOGROUPS` 下 `size` 为 0——这是纯性能取舍，不开捕获可以省掉 ovector 的填充与拷贝。

错误处理是另一条独立通道。`ch_scan` 接受两个回调：匹配回调与错误回调。当 PCRE 撞到 `match_limit` 或 `match_limit_recursion` 时，会调用错误回调并传 `CH_ERROR_MATCHLIMIT` 或 `CH_ERROR_RECURSIONLIMIT`；如果没提供错误回调，这类错误被静默忽略、当作「没匹配」。这个默认行为很危险：规则写得不好导致回溯爆炸时，你会看到「某些匹配时有时无」，而不是一个明确的错误。

最后是数据库结构。Chimera 数据库 = `ch_database` 头 + `ch_bytecode` 头 + 底层 Hyperscan 数据库 + 模式偏移数组 + unguarded 索引数组 + 每条模式的 `ch_pattern` 与 PCRE 字节码/study 数据。`CH_DB_MAGIC` 是 `0xdededede`，与 Hyperscan 的 `0xdbdbdbdb` 刻意不同，避免两类数据库被互相误加载。

### 3. 关键数据结构与源码位置

`src/` 之外，Chimera 全部在 `chimera/` 目录。头文件三个：`chimera/ch_compile.h`（编译 API、`CH_MODE_NOGROUPS` 为 0、`CH_MODE_GROUPS` 为 1048576、`ch_compile_error_t`）、`chimera/ch_runtime.h`（`ch_scan`、`ch_match_event_handler`、`ch_capture_t`、三个回调返回值）、`chimera/ch_common.h`（`CH_SUCCESS` 为 0、`CH_INVALID` 为 -1、`CH_SCAN_TERMINATED` 为 -3、`CH_DB_VERSION_ERROR` 为 -5、`CH_SCRATCH_IN_USE` 为 -10、`CH_FAIL_INTERNAL` 为 -32）。`chimera/ch.h` 只是把编译与运行期两个头包含进来。

数据库布局在 `chimera/ch_database.h`：`struct ch_database`（魔数、版本、长度、保留位、`bytecode` 偏移、`padding[16]`、`bytes[]`）、`struct ch_bytecode`（长度、整库标志、模式数、活跃位图大小、底层数据库偏移、模式偏移表偏移、unguarded 列表偏移与数量、最大捕获组数）、`struct ch_pattern`（用户 id、每模式标志、最小/最大/固定宽度、study 偏移、长度、内嵌 `pcre_extra`）。字段逐项含义见 05-09，本篇不重复。

编译实现在 `chimera/ch_compile.cpp`：`PatternData` 构造函数（`ch_compile.cpp:271`）负责 `pcre_compile` 与信息提取，`buildPcre`（`ch_compile.cpp:335`）调 `pcre_compile` 与 `pcre_study(PCRE_STUDY_JIT_COMPILE)`，`ch_compile_multi_int`（`ch_compile.cpp:474`）负责分类、建底层库与布局，`ch_compile`（`ch_compile.cpp:672`）、`ch_compile_multi`（`ch_compile.cpp:734`）、`ch_compile_ext_multi` 是三个公开入口（后者多两个参数：`match_limit` 与 `match_limit_recursion`）。

运行期在 `chimera/ch_runtime.c`：`ch_scan_i`（`ch_runtime.c:527`）是总控，`initQueue`（`ch_runtime.c:491`）给 unguarded 模式预置首次扫描，`scanHyperscan`（`ch_runtime.c:472`）调 `hs_scan`，`multiCallback`（`ch_runtime.c:369`）是 Hyperscan 的回调、决定「直接入队」还是「跑 PCRE 确认」，`scanPcre`（`ch_runtime.c:211`）执行一次 `pcre_exec` 并入队，`catchupPcre`（`ch_runtime.c:296`）按顺序出队并回调用户，`handlePcreNonMatch`（`ch_runtime.c:182`）把 PCRE 返回码翻译成 Chimera 错误。scratch 管理在 `chimera/ch_scratch.c`：`ch_alloc_scratch`（`ch_scratch.c:141`）、`ch_clone_scratch`（`ch_scratch.c:256`）、`ch_scratch_size`（`ch_scratch.c:316`）、`ch_free_scratch`（`ch_scratch.c:285`）。链接关系在 `chimera/CMakeLists.txt`：`target_link_libraries(chimera hs pcre)`，且 `add_dependencies(chimera hs pcre)`。

scratch 结构值得单独提一句：Chimera 的 scratch 里嵌着一个 `hs_scratch_t *multi_scratch`，由 `hs_alloc_scratch` 分配并随 `ch_clone_scratch` 一起克隆。所以「Chimera scratch 非线程安全」与「Hyperscan scratch 非线程安全」是同一件事的两层——共享一个 `ch_scratch_t` 并发 `ch_scan`，会在 `markScratchInUse` 处拿到 `CH_SCRATCH_IN_USE`。

下表按模式特征归纳编译期的分类结果与运行期代价；API 参数与返回码全集见 04-04 与 04-05，模块边界见 07-11。

| 模式特征 | 是否进底层 Hyperscan | 是否需 PCRE 确认 | 运行期代价 |
|---|---|---|---|
| 定宽、无捕获、可精确编译 | 是，关闭预过滤并开 SOM | 否 | 接近纯 Hyperscan |
| 变宽、可预过滤编译 | 是，`HS_FLAG_PREFILTER` | 是 | 触发次数决定 PCRE 开销 |
| 含捕获组、可预过滤编译 | 是 | 是 | 多一次 ovector 填充 |
| 连预过滤都无法编译 | 否，进 unguarded 列表 | 是，全量扫描 | 接近纯 PCRE |
| 全部模式都 unguarded | 否 | 是 | 与纯 PCRE 基本相同 |

最后一行是个有用的判据：如果 `ch_database_info()` 的输出只有 `Chimera ` 而后面没有 Hyperscan 的版本信息，说明整库没有底层 Hyperscan 数据库（`CHIMERA_FLAG_NO_MULTIMATCH`），此时 Chimera 退化成了「PCRE 的批量封装」，性能不会有任何惊喜。

### 4. 关键流程与调用链

编译期先从 PCRE 开始。`PatternData` 构造函数先 `flags |= HS_FLAG_ALLOWEMPTY`，理由写在注释里：避免为了「空匹配」把模式交给 PCRE 反复确认。然后 `buildPcre()`：`pcre_compile` 拿字节码，失败就抛 `CompileError`；`pcre_study` 带 `PCRE_STUDY_JIT_COMPILE` 生成 JIT 数据（返回 NULL 且无错误是合法的，表示没什么可优化的）；再用 `pcre_fullinfo` 取 `PCRE_INFO_SIZE`、`PCRE_INFO_STUDYSIZE`、`PCRE_INFO_CAPTURECOUNT`、`PCRE_INFO_OPTIONS`（用于判断是否 UTF-8）。

接着取宽度信息。`hs_expression_info` 用「预过滤 + 去 SINGLEMATCH」的标志问 Hyperscan 要 `min_width` 与 `max_width`，同时看 `unordered_matches` 判断报告是否有序。若这一步就失败，说明连预过滤都编不出来，该模式进 unguarded 列表，后续完全靠 PCRE。

宽度拿到后做定宽判定：`min_width == max_width`、非零、有限、无捕获组、有序、且用「原始标志 + SOM」能编译成功，五条全满足才把 `fixedWidth` 置成该宽度。注意这里用的是 `rawflags`（含 `HS_FLAG_SOM_LEFTMOST`、去掉 `SINGLEMATCH`），因为定宽路径要靠 SOM 拿起点；而 `SINGLEMATCH` 与 SOM 互斥。

然后分类。`guard = isHyperscanSupported(pattern, flags | HS_FLAG_PREFILTER, platform)`。为真的模式进 `multiExpr` / `multiFlags` / `multiIds` 三个数组，索引用模式在数组中的位置（不是用户 id），这样 Hyperscan 回调里的 `id` 就是数组下标，可以直接索引 `patternData`。为假的进 `unguarded` 列表。若某个模式是定宽的，编译标志会额外加上 `HS_FLAG_SOM_LEFTMOST`、去掉 `HS_FLAG_PREFILTER` 与 `HS_FLAG_SINGLEMATCH`。

全部模式处理完后，若 `multiExpr` 非空，调一次 `hs_compile_multi` 建底层库（固定 `HS_MODE_BLOCK`），再用 `hs_database_size` 量尺寸。接着算总布局：`ch_bytecode` 头 + 底层库 + 对齐 + unguarded 索引数组 + 模式偏移数组 + 各模式块 + 128 字节对齐余量。分配、清零、填头、填 `ch_bytecode` 的各个偏移、按 `CHIMERA_FLAG_NO_MULTIMATCH` / `GROUPS` / `ALL_CONFIRM` / `ALL_SINGLE` 置整库标志，最后逐模式写 `ch_pattern` 与 PCRE 字节码。

运行期从 `ch_scan` 进 `ch_scan_i`。先校验数据库（`hydbIsValid` 查魔数与版本）、scratch 对齐与魔数，`markScratchInUse`；再检查 `length <= INT_MAX`，因为 `pcre_exec` 的长度参数是 `int`。然后清空队列、构造 `HybridContext`（数据、长度、数据库、scratch、队列、两个回调、上下文）。

第一步是 `initQueue`：对每个 unguarded 模式，在 `active` 位图里置位，然后 `scanPcre(length, 0, patternId)` 做一次全缓冲区扫描，找到的匹配入队。这一步的语义是「这些模式没有触发器，只能自己找第一个匹配」。

第二步是 `scanHyperscan`（只要不是 `NO_MULTIMATCH`）：`hs_scan` 底层库，回调是 `multiCallback`。回调里对每个触发做判定：若该模式需要确认且已经在 `active` 里（说明之前已经确认过一次、有一条待续的扫描链），直接返回 0（继续扫描，不重复确认）；否则置位 `active`，检查「本次 `to` 是否早于 `scanStart + minWidth`」（太早则忽略），检查 `SINGLEMATCH`，然后分两路：定宽模式直接算出 `[from, to)` 入队；变宽模式调 `scanPcre` 从 `scanStart` 开始确认，确认到的匹配入队，并把 `scanStart` 推进到匹配之后。

第三步是 `catchupPcre` 收尾：把队列里剩余项按 `to` 升序弹出，逐个调用户回调；若回调返回 `CH_CALLBACK_SKIP_PATTERN`，把该模式的 `scanStart` 推到缓冲区末尾（等于放弃这条模式后续的匹配）；若返回 `CH_CALLBACK_TERMINATE`，整体返回 `CH_SCAN_TERMINATED`。每弹出一项，如果这条模式还没到 `SINGLEMATCH` 上限，会再跑一次 `scanPcre` 把下一个匹配补进队列，形成「边报告边补货」的流水。

### 5. 配置/命令/代码实例

下面的程序编译一条带两个捕获组的模式，扫描一段文本，打印整段匹配与各组偏移。链接时需要同时给 `chimera`、`hs`、`pcre` 三个库，顺序不能颠倒（依赖在前）。

```c
#include <hs/ch.h>
#include <stdio.h>
#include <string.h>

static ch_callback_t on_match(unsigned int id, unsigned long long from,
                              unsigned long long to, unsigned int flags,
                              unsigned int size,
                              const ch_capture_t *caps, void *ctx) {
    (void)flags;
    (void)ctx;
    printf("id=%u [%llu,%llu) groups=%u\n", id, from, to, size);
    for (unsigned int i = 0; i < size; i++) {
        if (caps[i].flags & CH_CAPTURE_FLAG_ACTIVE) {
            printf("  g%u [%llu,%llu)\n", i, caps[i].from, caps[i].to);
        }
    }
    return CH_CALLBACK_CONTINUE;
}

int main(void) {
    ch_database_t *db = NULL;
    ch_scratch_t *scratch = NULL;
    ch_compile_error_t *cerr = NULL;
    const char *pat = "(\\w+)@(\\w+)\\.com";
    const char *data = "x bob@example.com";

    if (ch_compile(pat, 0, CH_MODE_GROUPS, NULL, &db, &cerr) != CH_SUCCESS) {
        fprintf(stderr, "ch_compile: %s\n", cerr->message);
        ch_free_compile_error(cerr);
        return 1;
    }
    if (ch_alloc_scratch(db, &scratch) != CH_SUCCESS) {
        ch_free_database(db);
        return 1;
    }
    ch_error_t rv = ch_scan(db, data, (unsigned int)strlen(data), 0,
                            scratch, on_match, NULL, NULL);
    printf("ch_scan rv = %d\n", rv);

    ch_free_scratch(scratch);
    ch_free_database(db);
    return 0;
}
```

编译命令与运行结果如下。Chimera 是静态库，链接顺序必须是 `-lchimera -lhs -lpcre`，并且 C++ 运行库也要带上（Chimera 的编译侧是 C++ 写的）。示例输出，具体格式需对照实际版本核验。

```bash
gcc demo.c -o demo -lchimera -lhs -lpcre -lstdc++ -lm
./demo
```

```text
id=0 [2,17) groups=3
  g0 [2,17)
  g1 [2,5)
  g2 [6,13)
ch_scan rv = 0
```

逐行判读。第一行的 `id=0` 是编译时传入的 id（`ch_compile` 单模式固定为 0），`[2,17)` 是整段匹配的开区间偏移：数据是 `x bob@example.com`，`x ` 占两个字节，所以 `bob` 从 2 开始，`com` 到 16 结束、开区间写 17。`groups=3` 表示本次传送了 3 个 `ch_capture_t`：第 0 项是整段匹配，第 1、2 项是两个捕获组；这个数来自编译期的 `maxCaptureGroups`（本例为 2）加 1，而不是「本模式实际参与匹配的组数」。第二行 `g0 [2,17)` 与第一行完全一致，是约定俗成的「第 0 组等于整段匹配」。第三行 `g1 [2,5)` 对应 `(\w+)` 捕获到的 `bob`，长度 3。第四行 `g2 [6,13)` 对应第二个 `(\w+)` 捕获到的 `example`，起点 6 是因为 `@` 在 5。注意偏移都是字节偏移而不是字符偏移；在 UTF-8 数据上开 `HS_FLAG_UTF8` 后仍按字节计，业务侧若要按字符展示需要自行换算。最后一行的 `0` 是 `CH_SUCCESS`；若这里是 `-3` 说明回调返回了终止，`-1` 说明参数或数据库有问题，`-10` 说明 scratch 正在被另一线程使用。

`ch_database_info()` 的输出在这种模式上应当是 `Chimera ` 加上底层 Hyperscan 的信息串（类似 `Chimera Version: 5.4.2 Features: AVX2 Mode: BLOCK`），因为这条模式可以被预过滤编译、进了 guard 集合。如果输出只有 `Chimera ` 而没有后半段，说明整库退化为纯 PCRE 封装，性能会明显低于预期，应检查模式里是否有连预过滤都无法处理的构造。

想观察「确认」这一步真的发生了，可以把模式改成变宽的（例如 `(\w+)@(\w+)\.(com|org)`），再用一个不命中的文本跑一遍；此时 Hyperscan 不触发，`scanPcre` 也不会被调用，输出为空。反过来用一个宽模式（例如 `\w+`）跑长文本，会看到大量触发与大量确认，这正是「命中率决定收益」的直观体现。

### 6. 注意事项、陷阱与最佳实践

第一，Chimera 只有块模式。`ch_compile` 内部固定 `HS_MODE_BLOCK`，公开 API 没有流式接口。想在 TCP 流上用它，必须自己保证「匹配不跨块」，或者接受跨块漏报；这与 Hyperscan 的流式能力是两回事，不要混淆。

第二，性能完全取决于命中率。宽模式（`\w+`、`.*`、单字符类）会让 Hyperscan 在几乎每个位置触发，PCRE 被调用几乎每个位置，总耗时可能超过纯 PCRE。选型前应先估算「每 MB 触发次数」，而不是只看规则条数。

第三，必须提供错误回调。不传 `onError` 时，`PCRE_ERROR_MATCHLIMIT` 与 `PCRE_ERROR_RECURSIONLIMIT` 会被当作「没匹配」静默吞掉，表现为「匹配时有时无」。生产代码应当始终传错误回调，把 `CH_ERROR_MATCHLIMIT` 计入监控，并配合 `ch_compile_ext_multi` 显式设置 `match_limit` 与 `match_limit_recursion`。

第四，`CH_MODE_GROUPS` 有实打实的成本。它让每条模式都保留 ovector 并填充捕获组，同时抬高 scratch 的 `maxCaptureGroups`。不需要捕获结果时用 `CH_MODE_NOGROUPS`，能省下这部分开销。

第五，`CH_CALLBACK_SKIP_PATTERN` 的语义是「放弃这条模式后续的所有匹配」，不是「跳过这一次」。它会把 `scanStart` 推到缓冲区末尾，等于本块内该模式不再报告。用它做「首命中即停」时要清楚这是块级而非流级。

第六，`ch_scratch_t` 不能跨线程共享。它内部持有 `hs_scratch_t`，两层都有 `markScratchInUse` 保护，并发会返回 `CH_SCRATCH_IN_USE`。正确模型与 Hyperscan 一致：一线程一 scratch，或用 `ch_clone_scratch` 复制。

第七，`pcre_study` 带 JIT 会申请可执行内存。在某些加固环境（禁用 `PROT_EXEC` 的堆、SELinux 严格策略）里可能失败，表现为 `ch_compile` 抛「PCRE compilation failed」。这类环境需要去掉 JIT 或调整策略，具体行为需对照 PCRE 版本核验。

第八，Chimera 数据库与 Hyperscan 数据库不能互换。`CH_DB_MAGIC` 是 `0xdededede`，Hyperscan 是 `0xdbdbdbdb`，误加载会得到 `CH_INVALID` 或 `HS_INVALID`。分发时不要把两类文件放进同一个目录靠文件名区分。

### 7. 小结与延伸阅读

Chimera 用「Hyperscan 触发 + PCRE 确认」把两种引擎的能力拼在一起：Hyperscan 负责在整块数据上快速排除，PCRE 负责在少量候选位置上做精确判定与捕获。编译期把模式分成 guarded 与 unguarded，并识别出「定宽可免确认」的快速路径；运行期用优先队列保证报告顺序与纯 PCRE 一致。它的收益与命中率强相关，边界是只有块模式、且不改变 PCRE 的最坏情况复杂度。

记住三件事：Hyperscan 在这里只保证「不漏」，多报由 PCRE 收敛；定宽模式是性能关键路径，写规则时应尽量让常用规则落在这一档；没有错误回调时 PCRE 的 match limit 会被静默吞掉，这是最难查的一类「偶发漏报」。
