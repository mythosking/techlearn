# Hyperscan 技术资料 · 04 参数与 API 手册（分片 A）

## 04-01 CMake 构建变量全集

### 1. 本篇定位与覆盖范围

04 册是整套资料中**参数与 API 的唯一权威源**：任何构建变量、编译标志、模式常量、扩展参数、函数签名、错误码与工具命令行，都以本册为准；其余各册只给本场景的最小必要调用，并写「完整变量见 04-01」之类的交叉引用。本分片（04-01 至 04-04）负责其中的「构建期」部分：构建变量、编译标志、模式与扩展参数、编译 API。运行时 API、scratch 与序列化 API、工具命令行、错误码总表分别落在 04-05 至 04-08。

本篇只覆盖 `CMakeLists.txt` 与 `cmake/` 目录下模块真正读取的构建变量，不讨论编译器开关的取舍（那属于 02-02 的组合语义与 02-05 的库形态论证），也不讨论构建完成之后的任何运行期行为。所有条目的名称、默认值与判定条件均逐项对照 `upstream_src/CMakeLists.txt`，行号即该文件中的物理行号，可直接定位。凡上游快照与读者手上的分支不一致的地方，以源码为准，本篇给出的行号只保证对应本快照。

读这张表之前必须先建立三个概念，否则很容易把「可配置项」与「派生量」混为一谈。

第一类是**用户可设的 `option`**：`option(<name> "<doc>" <default>)` 的第三个参数就是默认值，`-D<name>=ON/OFF` 可以覆盖。例如 `BUILD_SHARED_LIBS` 默认 `OFF`（`CMakeLists.txt:118`），`BUILD_EXAMPLES` 默认 `TRUE`（`CMakeLists.txt:1441`）。

第二类是**条件依赖项 `CMAKE_DEPENDENT_OPTION`**：它的签名是 `(name doc default depends value_if_false)`，语义是「当 `depends` 为真时取 `default`，否则取 `value_if_false`」，而且这个求值发生在配置阶段，用户仍然可以显式覆盖，但覆盖后不会自动跟随条件变化。本仓库共有三个这样的变量：`DUMP_SUPPORT`、`DISABLE_ASSERTS`、`FAT_RUNTIME`。

第三类是**派生量**：由 `set()` 在配置过程中算出，例如 `RELEASE_BUILD`（由 `CMAKE_BUILD_TYPE` 正则匹配得出）、`BUILD_STATIC_LIBS`（由 `BUILD_SHARED_LIBS` 反推）、`BUILD_CHIMERA`（由 PCRE 三个条件合取）。派生量原则上不应由用户在命令行指定，指定后往往只改变一半逻辑，产生「看起来配了、实际没生效」的假象。

需要强调的是：**构建变量只影响「编出什么样的库」，不影响「库如何匹配」**。同一个 `libhs` 无论是静态还是动态、是否 fat runtime，其 API 语义与匹配结果都一致；差异体现在可执行文件大小、部署约束、可用 CPU 指令集与吞吐上限。把构建变量当成功能开关，是本篇要纠正的最常见误解。

### 3. 逐项详解

**版本三元组与 `HS_VERSION`。** 三者不是 `option`，而是 `set()` 直接写死的常量（`CMakeLists.txt:4-6`），合成 `HS_VERSION=5.4.2`，再派生出 `LIB_VERSION` 与 `LIB_SOVERSION`（后者取主版本号 5），最终决定 `libhs.so.5.4.2` 的名字与 SONAME。因为 `set()` 不带 `CACHE`，命令行传 `-DHS_VERSION=9.9.9` 会在配置阶段被源码里的 `set()` 覆盖，属于无效操作；要判断一个已装库的真实版本，应调用 `hs_version()`（`src/hs_common.h:450`），它返回一个静态分配的版本字符串。

**`CMAKE_BUILD_TYPE`。** 未指定时，脚本先打印 `Default build type 'Release with debug info'`，再以 `FORCE` 写入 cache；已指定时统一用 `string(TOUPPER ...)` 转成大写。紧接着用正则 `RELEASE|RELWITHDEBINFO|MINSIZEREL` 判定 `RELEASE_BUILD`。这里有三个坑：其一，大小写不敏感但拼写必须匹配，写 `RelDebug` 不会报错，只会被判成非 release；其二，多配置生成器（Visual Studio、Xcode）下该变量为空，`RELEASE_BUILD` 落到 FALSE，真正的优化级别由构建时的 `--config` 决定；其三，`Debug` 与 `RelWithDebInfo` 分属两侧，后者仍算 release，因此默认关闭断言、关闭 dump。

**`RELEASE_BUILD`。** 纯派生量，不建议手工干预。它除了决定三个条件默认值，还控制两处编译选项：非 release 才追加 `-Werror`（`CMakeLists.txt:251-256`），release 才追加 `-fvisibility=hidden`（`CMakeLists.txt:316-323`）。把 `RELEASE_BUILD` 手工设成 TRUE 而不改 `CMAKE_BUILD_TYPE`，会得到「release 的可见性与警告策略 + debug 的优化级别」这种四不像组合。

**`OPTIMISE`。** 默认 TRUE。语义是正向的「是否优化」，尽管帮助字符串写成了容易误读的 `Turns off compiler optimizations`。TRUE 时 C 用 `-O3`、C++ 用 `-O2`，`MINSIZEREL` 下两者都退化为 `-Os`；FALSE 时一律 `-O0`（`CMakeLists.txt:234-245`）。`DEBUG_OUTPUT=ON` 会把它强制置 FALSE，且这个覆盖发生在读入用户值之后，所以同时写 `-DOPTIMISE=ON -DDEBUG_OUTPUT=ON` 仍然是 `-O0`。

**`DEBUG_OUTPUT`。** 默认 FALSE。打开后追加 `-DDEBUG`，于是 `DEBUG_PRINTF` 宏与组件树 dump 生效，编译期会向 stderr 输出大量解析与建图信息。它和 `DUMP_SUPPORT` 常被混淆：前者是**运行期/编译期的即时打印**，后者是**把中间产物落盘**给 `hsdump` 读。调试「为什么这条模式编不过」用 `DEBUG_OUTPUT`，分析「编出来的字节码长什么样」用 `DUMP_SUPPORT`，两者可以同时开，但都会显著拖慢构建。

**`VALIDATE_PATTERN_INPUT`。** 默认 FALSE。打开后追加 `-DVALIDATE_PATTERN_INPUT`，在纯字面量解析与 `addLitExpression` 路径上启用 `validatePatternInput()`（`src/compiler/compiler.cpp:121`）：拒绝长度为 0、超过 `MAX_PATTERN_LENGTH`（`src/util/compile_error.h:37`，8192 字节）、声明长度与实际内容不符、以及长度大于 10 且九成以上字节为 NUL 的畸形输入。它只做入参健壮性检查，不改变任何匹配语义；面向不可信模式源的服务应打开，配合 08-05 的配额策略一起用。

**`BUILD_SHARED_LIBS`。** 默认 OFF。OFF 时把 `BUILD_STATIC_LIBS` 置 ON 并 `mark_as_advanced`，产出 `libhs.a` 与 `libhs_runtime.a`；ON 时只产出动态库 `libhs.so`、`libhs_runtime.so`，且**不会**同时保留静态库。这个变量的名字沿用 CMake 惯例，但本仓库对它的处理是「非此即彼」，不是「优先动态」。

**`BUILD_STATIC_AND_SHARED`。** 默认 OFF。与 `BUILD_SHARED_LIBS` 是「或」的关系：任一为真都进入 shared 分支，区别只在于静态目标是否也生成。需要既给内部工具静态链接、又对外发 `.so` 时才用它。注意它会同时编译 `hs_exec` 与 `hs_exec_shared` 两套目标，构建时间与磁盘占用接近翻倍。

**`BUILD_STATIC_LIBS`。** 派生量：`NOT BUILD_SHARED_LIBS` 时置 ON，并被标记为 advanced 从普通 `cmake-gui` 列表隐藏。它不是给用户用的开关，但在 `BUILD_CHIMERA` 的判定里出现（`CMakeLists.txt:504`），因此手工置 OFF 会连带让 Chimera 不构建，表现为「PCRE 明明装了却没有 libchimera」。

**`DUMP_SUPPORT`。** `CMAKE_DEPENDENT_OPTION(DUMP_SUPPORT "..." ON "NOT RELEASE_BUILD" OFF)`：非 release 默认 ON，release 默认 OFF。ON 时把 `hs_dump_SRCS` 整组源码追加进 `hs_compile_SRCS`（`CMakeLists.txt:1184-1186`），`hsdump` 才有字节码可转储。生产 release 构建默认关闭它，因此「hsdump 输出为空」的第一嫌疑永远是这个变量，而不是数据库损坏。

**`DISABLE_ASSERTS`。** `CMAKE_DEPENDENT_OPTION(..., OFF, "NOT RELEASE_BUILD", ON)`：非 release 默认 OFF（断言开启），release 默认 ON（追加 `-DNDEBUG`）。它与 `OPTIMISE` 完全正交，可以出现「断言开启 + `-O3`」的性能剖析构建，这是排查「release 才崩、debug 不崩」类问题的常用组合。

**`FAT_RUNTIME`。** 只在 `CMAKE_SYSTEM_NAME MATCHES "Linux"` 的分支里定义，默认值就是 `${RELEASE_BUILD}`，即 release 默认 ON。可用性由 `FAT_RUNTIME_REQUISITES` 把关，三个条件缺一不可：Clang 版本不低于 3.9（GCC 无此限制）；生成器是 Unix Makefiles，或是 CMake 版本大于 3.0 的 Ninja；编译器支持 `ifunc` 属性（`cmake/attrib.cmake` 的 `HAS_C_ATTR_IFUNC`）。任一不满足就退化为 OFF 并打印具体原因。ON 时以 `-march=core2`、`-march=corei7`、`-march=core-avx2` 各编一份运行时（可选再加 avx512、avx512vbmi），由 `src/dispatcher.c` 在首次调用时按 CPUID 绑定函数指针；OFF 时只编一份，使用 `-march=native -mtune=<探测值>`。

**`BUILD_AVX512`。** 默认 OFF，帮助字符串明确标注 Experimental。它只在 `FAT_RUNTIME` 为真的分支里被读取：增加一份用 `${SKYLAKE_FLAG}`（GCC 为 `-march=skylake-avx512`，ICC 为 `-xCORE-AVX512`）编译的目标，并决定是否向 dispatcher 传 `-DDISABLE_AVX512_DISPATCH`。`FAT_RUNTIME=OFF` 时设它不产生任何效果，这是最典型的「配了等于没配」。

**`BUILD_AVX512VBMI`。** 默认 OFF。置 ON 会先执行 `set(BUILD_AVX512 ON)`（`CMakeLists.txt:148-150`），再额外编一份 `${ICELAKE_FLAG}`（`-march=icelake-server`）目标。由于 AVX-512 VBMI 只在 Ice Lake 及更新的服务器核上可用，开启后产物体积与构建时间都会上升，而收益只在特定 CPU 上兑现；生产分发前应确认目标机群确实包含这些型号。

**`WINDOWS_ICC`。** 默认 OFF，只在 MSVC/ICC 分支被读取。ON 时改用 `/QxHost /O3 /Qstd=c99 /Qrestrict` 等 ICC 专用开关，并要求工程已把编译器切成 ICC；用 MSVC 配这个变量只会得到一堆无法识别的选项。

**`BUILD_EXAMPLES`。** 默认 TRUE，5.4.0 引入。仅在 `NOT WIN32` 时 `add_subdirectory(examples)`，产出 `simplegrep`、`pcapscan`、`patbench` 等示例。它不影响库，只是很多团队在 CI 里关掉它以缩短构建时间。

**依赖与安装相关变量。** `BOOST_ROOT` 不是本仓库定义的 option，而是 `find_package(Boost)` 的标准提示变量：`cmake/boost.cmake` 先以仓库内 `include/` 为 `BOOST_INCLUDEDIR` 查找，失败后清空提示再查系统路径，两次都失败才 `FATAL_ERROR`，并在消息里点名「set the CMake BOOST_ROOT variable」。Boost 最低版本 1.57.0，使用 libc++ 时提高到 1.61.0。PCRE 侧由 `PCRE_REQUIRED_VERSION=8.41`、`PCRE_SOURCE`、`PCRE_BUILD_SOURCE` 驱动，只有「版本正确 + 从源码构建 + `BUILD_STATIC_LIBS` 为真」三者同时成立才置 `BUILD_CHIMERA`，因此系统装了 libpcre 动态库并不足以编出 Chimera。OpenSSL 由 `find_package(OpenSSL REQUIRED)` 强制要求，没有关闭开关，用于数据库 HMAC-SHA256 完整性校验。安装路径取自 GNUInstallDirs：四个公共头文件装到 `${CMAKE_INSTALL_INCLUDEDIR}/hs`，库装到 `CMAKE_INSTALL_LIBDIR`，`libhs.pc` 装到 `lib/pkgconfig`；交叉编译时必须显式指定这两个目录，否则会装进 sysroot 的默认前缀。

### 4. 典型示例

下面这次配置打开共享库、保留 fat runtime、并把 AVX-512 变体一起编进去，同时关闭示例以缩短时间。命令在源码树外的 `build/` 目录执行。

```bash
mkdir -p build && cd build
cmake .. \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DBUILD_SHARED_LIBS=ON \
  -DFAT_RUNTIME=ON \
  -DBUILD_AVX512=ON \
  -DBUILD_EXAMPLES=OFF \
  -DCMAKE_INSTALL_PREFIX=/opt/hyperscan
```

配置阶段的输出如下（示例输出，具体格式需对照实际版本核验）。

```text
-- Default build type 'Release with debug info'
-- The C compiler identification is GNU 11.2.0
-- The CXX compiler identification is GNU 11.2.0
-- Build type RELWITHDEBINFO
-- using release build
-- Found OpenSSL: /usr/lib/x86_64-linux-gnu/libcrypto.so (found version "3.0.11")
-- Boost version: 1.74.0
-- Found PythonInterp: /usr/bin/python2.7 (found version "2.7.18")
-- Build date: 2026-11-12
-- Building shared libraries
-- gcc version 11.2.0
-- g++ version 11.2.0
-- Building runtime for multiple microarchitectures
-- Configuring done
-- Generating done
-- Build files have been written to: /home/dev/hyperscan/build
```

逐行判读这段输出，重点不在「成功」，而在四行状态。第一行 `Default build type` 只会在完全没给 `CMAKE_BUILD_TYPE` 时出现；本例显式给了值，所以这一行实际上不应该出现，若出现说明 `-D` 没传进去（常见于把参数写在 `--` 之后，或被外层脚本吞掉）。`Build type RELWITHDEBINFO` 与 `using release build` 必须成对出现，前者证明大小写归一化生效，后者证明 `RELEASE_BUILD` 为真；只有前者没有后者，说明拼写落在了三个关键字之外。`Building shared libraries` 对应 `BUILD_SHARED_LIBS=ON`，如果期望静态库却看到这一行，说明上一次配置的 cache 还在，需要删掉 `CMakeCache.txt` 重来。`Building runtime for multiple microarchitectures` 是 `FAT_RUNTIME` 真正生效的标志；若这里打印的是 `Building for current host CPU: -march=native ...`，则后面所有 `BUILD_AVX512` 的设置都是空转。`Boost version` 与 `Found OpenSSL` 两行给出依赖实参与了什么，跨机器复现构建问题时，这两行是最先要比对的证据。

配置完成后，验证「默认值到底落成了什么」不要靠猜，直接读 cache。下面这条命令只列出非 advanced 的缓存项并过滤出关键变量。

```bash
cmake -LA -N . | grep -E "^(BUILD_|FAT_RUNTIME|OPTIMISE|DUMP_SUPPORT|DISABLE_ASSERTS|VALIDATE_PATTERN_INPUT)"
```

```text
BUILD_AVX512:BOOL=ON
BUILD_AVX512VBMI:BOOL=OFF
BUILD_EXAMPLES:BOOL=OFF
BUILD_SHARED_LIBS:BOOL=ON
BUILD_STATIC_AND_SHARED:BOOL=OFF
DISABLE_ASSERTS:BOOL=ON
DUMP_SUPPORT:BOOL=OFF
FAT_RUNTIME:BOOL=ON
OPTIMISE:BOOL=ON
VALIDATE_PATTERN_INPUT:BOOL=OFF
```

这段输出把「条件默认值」的实际落点暴露得很清楚：`DISABLE_ASSERTS=ON` 与 `DUMP_SUPPORT=OFF` 都是 `RELEASE_BUILD` 为真的推论，而不是有人手工设过；`BUILD_STATIC_LIBS` 没有出现，因为它被 `mark_as_advanced` 隐藏，需要 `cmake -LA` 才能看到全部。若发现 `FAT_RUNTIME:BOOL=OFF` 而命令行确实写了 ON，就回到 1 号证据看 `FAT_RUNTIME_REQUISITES` 的失败原因——通常是生成器不是 Makefiles/Ninja，或 Clang 低于 3.9。判读这张表时还要注意一个反直觉点：`BUILD_AVX512=ON` 本身不保证产物里真有 AVX-512 代码，它只保证「如果 fat runtime 成立，就多编一份」；两者必须同时为 ON 才兑现。

### 5. 速查表

按使用场景挑选组合，比逐项记忆更可靠。速查表如下。

| 场景 | 推荐配置 | 说明 |
|---|---|---|
| 生产静态链接、单机型 | `BUILD_SHARED_LIBS=OFF`，`FAT_RUNTIME=OFF` | 体积最小，绑定 `-march=native` |
| 生产动态库、机群异构 | `BUILD_SHARED_LIBS=ON`，`FAT_RUNTIME=ON` | 一份 `.so` 运行时分派 |
| 需要 AVX-512 收益 | 上面基础上加 `BUILD_AVX512=ON` | 必须先让 `FAT_RUNTIME=ON` |
| Ice Lake 专属优化 | 再加 `BUILD_AVX512VBMI=ON` | 隐含打开 `BUILD_AVX512` |
| 排查编译失败原因 | `CMAKE_BUILD_TYPE=Debug`，`DEBUG_OUTPUT=ON` | 得到解析与建图打印 |
| 分析字节码 | 非 release 构建，或 `DUMP_SUPPORT=ON` | 配合 04-07 的 hsdump |
| 对外发静态与动态 | `BUILD_STATIC_AND_SHARED=ON` | 构建时间约翻倍 |
| 构建期加固 | `VALIDATE_PATTERN_INPUT=ON` | 校验不可信模式入参 |
| 需要 Chimera | 源码树放 `pcre/`，保持静态库 | 三条件同时满足才构建 |

速查表只能覆盖常见组合，真正的判定顺序应当反过来：先确定交付形态（静态还是动态），再确定目标机群是否同构（fat 与否），最后才叠加 AVX-512 与示例开关。顺序颠倒就会出现「先开了 AVX-512，后来才发现 fat runtime 没生效」的返工。

### 6. 版本差异

5.4.2 相对 5.4.1 在构建变量层面没有改动，`CMakeLists.txt` 的变量集合与默认值可以视为一致；5.4.2 的变更集中在 scratch 行为回退与 hsdump 的 NFA 类型修复，属于运行期与工具侧，详见 04-06 与 04-07。

把时间轴拉长看，与本篇直接相关的节点有四个。5.2.0 引入 Windows 动态库（DLL）支持，`BUILD_SHARED_LIBS` 从此在 Windows 上也有意义；同版本还新增了纯字面量 API，但不涉及 CMake 变量。5.2.1 修复了「release 模式下 `BUILD_SHARED_LIBS=ON` 编译失败」的问题，如果你的分支早于该版本，共享库 + release 的组合需要打补丁。5.4.0 新增 `BUILD_EXAMPLES`（变更日志明确写为 `Add BUILD_EXAMPLES cmake option`），并修复了 Ice Lake 在 release 模式下的 CMake 报错；同版本把 Sheng32/Sheng64/McSheng64 与 Fat Teddy 的 VBMI 优化带入，这也是 `BUILD_AVX512VBMI` 开始有实际收益的版本。更早的版本里 `BUILD_AVX512` 与 `BUILD_AVX512VBMI` 的组合语义可能不同，需对照实际版本核验 `CMakeLists.txt` 中 `if (BUILD_AVX512VBMI)` 段落。

另有两个容易忽略的版本约束。其一，`cmake_minimum_required` 写的是 2.8.11，但 fat runtime 对 Ninja 生成器要求 CMake 大于 3.0（`CMakeLists.txt:333-335`），因此在 2.8.x 上只能用 Unix Makefiles 构建 fat runtime。其二，Boost 的最低版本随标准库变化：默认 1.57.0，检测到 libc++ 时提高到 1.61.0，这个分支在 `cmake/boost.cmake` 开头，属于「同一份源码在不同发行版上要求不同依赖」的典型例子。

### 7. 常见误用与调试

构建变量的问题几乎都能归到三类：配了没生效、生效了但不是预期、预期对了但产物不对。下表按现象给出定位顺序，随后是三条补充说明。

| 现象 | 可能原因 | 处置 |
|---|---|---|
| 设了 `BUILD_AVX512=ON` 但无反汇编证据 | `FAT_RUNTIME` 为 OFF | 查配置输出是否打印多微架构 |
| 期望 `libhs.a` 却只有 `.so` | `BUILD_SHARED_LIBS=ON` | 改 OFF 或加 `BUILD_STATIC_AND_SHARED` |
| `hsdump` 无输出 | release 下 `DUMP_SUPPORT=OFF` | 用非 release 或显式打开 |
| 没有 `libchimera` | `BUILD_CHIMERA` 三条件未全满足 | 看 PCRE 提示与静态库开关 |
| `OPTIMISE=OFF` 后仍很慢 | 值被 `DEBUG_OUTPUT` 覆盖 | 同时关掉 `DEBUG_OUTPUT` |
| Boost 找不到 | 未设 `BOOST_ROOT` 且无 `include/` | 指定根目录或解压到 `include/` |
| 断言在 release 里消失 | `DISABLE_ASSERTS` 条件默认 ON | 显式 `-DDISABLE_ASSERTS=OFF` |

第一条补充：**不要手工设置派生量**。`RELEASE_BUILD`、`BUILD_STATIC_LIBS`、`BUILD_CHIMERA` 都应在配置阶段算出，手工覆盖只会让一半逻辑跟随、一半逻辑不跟随。判断一个变量是不是派生量，看它是否由 `set(... )` 而非 `option(...)` 定义，本篇表格的「默认值」列已经用「派生」二字标出。

第二条补充：**改完变量要清 cache**。`CMAKE_BUILD_TYPE` 在未指定时以 `FORCE` 写入 cache，这类强制写入的值在后续配置中不会自动跟随命令行变化；如果先在空目录配置了一次、再加 `-DCMAKE_BUILD_TYPE=Debug`，很可能仍走 `RELWITHDEBINFO`。稳妥做法是删掉 `CMakeCache.txt` 与 `CMakeFiles/` 后重新配置。

第三条补充：**构建变量不改变匹配语义**。若扫描结果与预期不符，不要怀疑 `FAT_RUNTIME` 或 `AVX-512`，它们只影响走哪份实现；语义问题应回到 04-02 的标志位与 04-03 的模式/扩展参数，行为差异再对照 06-13 的分派原理。字段级的产物结构（`hs_database` 头部、字节码布局）见 05-02，编译流水线的阶段划分见 06-01，模块归属见 07-10。

## 04-02 编译标志 HS_FLAG_* 全集

### 1. 本篇定位与覆盖范围

`HS_FLAG_*` 是**逐表达式**（per-expression）的编译标志，作用于「这条正则怎么被解释、匹配结果怎么被上报」，与**逐数据库**（per-database）的 `HS_MODE_*` 严格分层。同一个数据库里，不同表达式可以带完全不同的 flags；而 mode 一旦确定，整个数据库只能有一种扫描形态。这个分层是理解本篇与 04-03 分工的前提。

本篇覆盖 `src/hs_compile.h:856-1007` 定义的全部 11 个标志：`CASELESS`、`DOTALL`、`MULTILINE`、`SINGLEMATCH`、`ALLOWEMPTY`、`UTF8`、`UCP`、`PREFILTER`、`SOM_LEFTMOST`、`COMBINATION`、`QUIET`。每一个都给出位值、语义、与 PCRE 的对应关系、互斥约束、对性能与内存的影响、典型组合。位值的十进制与十六进制同时给出，因为在日志里看到的往往是十进制，在 `hsdump` 或调试器里看到的往往是十六进制。

本篇**不**覆盖：`HS_MODE_*`（含三个 SOM horizon，见 04-03）、`HS_EXT_FLAG_*` 与 `hs_expr_ext_t`（见 04-03）、`HS_CPU_FEATURES_*` 与 `HS_TUNE_FAMILY_*`（见 04-04）、运行时回调里的 `HS_MATCH_FLAG_ADJUSTED`（内部使用，见 04-05）。另外，标志的**实现后果**——为什么开 SOM 会膨胀字节码、为什么 `PREFILTER` 会改写语法树——属于 06-10 与 06-04 的范围，本篇只讲「开了会怎样」，不讲「内部怎么做到」。

有两个总纲级的约束必须先记住，它们决定了很多组合能不能成立。第一，**只有开了 `HS_FLAG_SOM_LEFTMOST` 才会返回起始偏移**，默认只报结束偏移，`from` 参数恒为 0；第二，**SOM 与「只报一次」「预过滤」「静默」三类语义互斥**，`SOM_LEFTMOST` 与 `SINGLEMATCH`、`PREFILTER`、`QUIET` 任意一个同时出现都会在编译期抛错，而不是运行期降级。这两条贯穿全篇。

### 3. 逐项详解

**`HS_FLAG_CASELESS`（1，`0x0001`）。** 让整条表达式默认大小写不敏感，等价于 PCRE 的 `i` 修饰符。它不冻结大小写语义：模式里仍可用 `(?i)` 与 `(?-i)` 局部开关，这一点在 `src/hs_compile.h:862-868` 的注释里写明。实现上会走 `smallwrite` 的小写化路径（模块见 07-08），把字符类与字面量折叠到同一等价类，因此对吞吐几乎没有负面影响，代价是字符类集合变大、字节码略增。与 `UTF8` 同用时，折叠依赖 Unicode 表，字符类会进一步膨胀，具体折叠范围以实测为准。

**`HS_FLAG_DOTALL`（2，`0x0002`）。** 让 `.` 匹配包括换行在内的任意字符，等价于 PCRE 的 `s`。默认（不带此标志）`.` 不跨行，这是 PCRE 的语义。注意它与 `MULTILINE` 是两件不同的事：`DOTALL` 改的是 `.`，`MULTILINE` 改的是 `^`/`$`；很多「跨行匹配不生效」的报障其实是只开了其中一个。性能上，`DOTALL` 会让 `.` 的字符类从「除换行外全部」变成「全部」，通常可忽略。

**`HS_FLAG_MULTILINE`（4，`0x0004`）。** 让 `^` 与 `$` 在任意换行处匹配，等价于 PCRE 的 `m`。不开启时，`^` 只在流/块起点匹配，`$` 只在终点匹配。它是三者中最容易影响性能的一个：多行锚点意味着引擎必须在每个换行处检查锚定条件，原本可以一次性锚定的模式可能退化为需要 NFA 参与的形式；在流式模式下还会增加对「上一块末尾是不是换行」的状态依赖，进而影响流状态大小。

**`HS_FLAG_SINGLEMATCH`（8，`0x0008`）。** 让该匹配 ID 在每个流（stream 模式）或每次扫描调用（block/vectored 模式）中最多上报一次。它的粒度是**匹配 ID 而不是表达式**：如果多条表达式共享同一个 ID，那么它们必须全部带此标志或全部不带，混合会出现「部分表达式只报一次、部分报多次」的不一致；`src/hs_compile.h:902-906` 明确要求同 ID 组内保持一致。性能收益来自「命中一次后可以把该 ID 标记为已耗尽」，从而剪掉后续候选；代价是「只报第一次」的语义可能与「最左最长」直觉不符，需要应用自己判断是否接受。与 `SOM_LEFTMOST` 组合直接编译失败。

**`HS_FLAG_ALLOWEMPTY`（16，`0x0010`）。** 允许编译「可能匹配空串」的表达式，例如 `.*`、`.?`、`(a|)`。默认情况下 Hyperscan 只接受「至少消费一个字节」的模式，否则报 `Pattern matches empty buffer`；这个默认是有意为之：可空模式在每一字节位置都可能产生匹配，扫描成本极高。打开后语义仍然正确，但会出现「每个字节都命中一次」的现象，调用方常常误判为引擎故障。凡是准备开这个标志的场景，都应先问一句「是否可以用 `.+` 或加锚点替代」。

**`HS_FLAG_UTF8`（32，`0x0020`）。** 把模式当作 UTF-8 字符序列解释，而不是字节序列。它影响字符类、量词与 `.` 的计数单位：`.{3}` 表示三个 UTF-8 字符而非三字节。头文件明确警告：用带此标志编译的库去扫描**非法 UTF-8 序列**，结果是未定义的（`src/hs_compile.h:925-932`）。生产环境若数据源不可信，必须在入库前做 UTF-8 校验，否则可能得到越界读或错误匹配。它本身不改变 `\w`、`\s` 的语义，那需要 `UCP`。

**`HS_FLAG_UCP`（64，`0x0040`）。** 让 `\w`、`\s`、`\d` 等字符助记符与 POSIX 字符类使用 Unicode 属性，而不是默认的 ASCII 解释。头文件写明它「only meaningful in conjunction with `HS_FLAG_UTF8`」（`src/hs_compile.h:935-942`）——单独设置 `UCP` 而不设 `UTF8` 不会报错，但也不会有预期的 Unicode 行为，这是最常见的「静默无效」标志。开启后字符类集合显著膨胀，字节码与编译时间都会上升，个别大字符类（如 `\p{L}`）可能触发编译期规模限制。

**`HS_FLAG_PREFILTER`（128，`0x0080`）。** 以「预过滤」模式编译：即使模式包含 Hyperscan 正常不支持的结构（零宽断言、反向引用、条件引用），也会用更宽泛的结构替换后编出来。它给出一条硬保证：**返回的匹配集合是精确匹配集合的超集**，因此**允许假阳性**，但绝不允许漏报。这正是「预过滤」三个字的含义：应用必须用另一个精确引擎（PCRE、Chimera 或业务逻辑）对命中做二次确认。它还会把可能报 `Pattern too large` 的模式简化到可编译，代价是假阳性率上升。与 `SOM_LEFTMOST` 组合直接编译失败；由于 SOM 不可用，`min_length` 约束在预过滤模式下会被静默清零（`src/compiler/compiler.cpp:286-291`），这一点极易被忽略。

**`HS_FLAG_SOM_LEFTMOST`（256，`0x0100`）。** 开启最左起始偏移上报：回调的 `from` 参数给出该次匹配**最左可能的起点**，`to` 给出结束偏移（不含）。不开时 `from` 恒为 0。这是全套标志里代价最大的一个：三种模式下都会降低吞吐，流式模式下还会显著增加流状态（要记住候选起点）；流式模式还必须同时指定一个 `HS_MODE_SOM_HORIZON_*`，否则编译直接报错「To use a SOM expression flag in streaming mode, an SOM precision mode ... must be specified」（`src/compiler/compiler.cpp:427-433`）。超出 horizon 的起点在运行期以 `HS_OFFSET_PAST_HORIZON`（`~0ULL`，`src/hs_runtime.h:615`）返回。它与 `SINGLEMATCH`、`PREFILTER`、`QUIET` 三者互斥，原因见 06-10。

**`HS_FLAG_COMBINATION`（512，`0x0200`）。** 表示这条「表达式」是逻辑组合公式，操作数是**表达式的下标**（不是匹配 ID），运算符只有 `!`（非）、`&`（与）、`|`（或）与括号。头文件给的例子是 `(101&102&103)|(104&!105)`；下标从 0 开始，指向同一次 `hs_compile_multi`/`hs_compile_ext_multi` 调用里的第几条。组合表达式自身也占一个下标，并可被后续组合引用。它只允许与 `QUIET`、`SINGLEMATCH` 共存，其它标志一律报错「only HS_FLAG_QUIET and HS_FLAG_SINGLEMATCH are supported in combination with HS_FLAG_COMBINATION」（`src/compiler/compiler.cpp:343-349`）；扩展参数也只允许 `MIN_OFFSET` 与 `MAX_OFFSET`。逻辑组合的匹配时机（子表达式全部落定后才报）与 EOD 语义见 06-04。

**`HS_FLAG_QUIET`（1024，`0x0400`）。** 对该表达式**不做匹配上报**，但**匹配照常发生**——它只是把「报告」这一步关掉，不会把模式从引擎里删掉，也不会阻止它作为组合操作数参与布尔运算。这正是逻辑组合需要的语义：子表达式静默命中，由组合表达式统一上报。误用最典型的是「想临时禁用一条规则就加 QUIET」：规则仍然参与扫描、仍然消耗性能，只是你看不到结果。它与 `SOM_LEFTMOST` 互斥（`src/compiler/compiler.cpp:215-218`），因为「不报结果却要算起点」没有意义。

### 4. 典型示例

下面的程序把六种标志组合逐一送进编译器，只观察返回码与错误消息，不进行扫描。这样可以在几分钟内把互斥关系全部验证一遍。

```c
#include <hs.h>
#include <stdio.h>

static void try_compile(const char *label, const char *expr, unsigned flags) {
    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;
    hs_error_t rc = hs_compile(expr, flags, HS_MODE_BLOCK, NULL, &db, &err);
    if (rc != HS_SUCCESS) {
        printf("[%-14s] rc=%d expr=%d msg=%s\n", label, rc,
               err ? err->expression : -1, err ? err->message : "(null)");
        hs_free_compile_error(err);
        return;
    }
    printf("[%-14s] compiled ok\n", label);
    hs_free_database(db);
}

int main(void) {
    try_compile("caseless", "abc", HS_FLAG_CASELESS);
    try_compile("som+single", "abc",
                HS_FLAG_SOM_LEFTMOST | HS_FLAG_SINGLEMATCH);
    try_compile("som+prefilter", "abc",
                HS_FLAG_SOM_LEFTMOST | HS_FLAG_PREFILTER);
    try_compile("quiet+som", "abc", HS_FLAG_QUIET | HS_FLAG_SOM_LEFTMOST);
    try_compile("combo+utf8", "0&1", HS_FLAG_COMBINATION | HS_FLAG_UTF8);
    try_compile("empty", ".*", 0);
    try_compile("empty-ok", ".*", HS_FLAG_ALLOWEMPTY);
    return 0;
}
```

编译并运行后，输出形如下面这样（示例输出，具体格式需对照实际版本核验）。

```text
[caseless      ] compiled ok
[som+single    ] rc=-4 expr=0 msg=HS_FLAG_SINGLEMATCH is not supported in combination with HS_FLAG_SOM_LEFTMOST.
[som+prefilter ] rc=-4 expr=0 msg=HS_FLAG_PREFILTER is not supported in combination with HS_FLAG_SOM_LEFTMOST.
[quiet+som     ] rc=-4 expr=0 msg=HS_FLAG_QUIET is not supported in combination with HS_FLAG_SOM_LEFTMOST.
[combo+utf8    ] rc=-4 expr=0 msg=only HS_FLAG_QUIET and HS_FLAG_SINGLEMATCH are supported in combination with HS_FLAG_COMBINATION.
[empty         ] rc=-4 expr=0 msg=Pattern matches empty buffer; use HS_FLAG_ALLOWEMPTY to enable support.
[empty-ok      ] compiled ok
```

逐行判读这份输出，可以一次性确认四条规则。第一行证明单标志路径正常，`rc=0` 且 `db` 非空，程序随后释放数据库，没有泄漏。第二、三、四行的共同特征是 `rc=-4`，即 `HS_COMPILER_ERROR`，而**不是** `HS_INVALID`——这说明参数本身合法，是「标志组合不被支持」，编译器在语义检查阶段拒绝，而非在参数校验阶段拒绝；`expr=0` 表示错误定位到第 0 条表达式，因为 `hs_compile` 只有一条。这三行也说明互斥检查发生在**解析表达式之前**：`abc` 这种必然合法的模式，仅因为标志组合就被拒，若你的代码先构造复杂模式再逐步加标志，很容易误以为是模式写错。第五行值得单独注意：`0&1` 在下标语法上是合法的组合公式，但 `COMBINATION` 与 `UTF8` 不能共存，错误消息明确点出「只允许 QUIET 与 SINGLEMATCH」，这条消息比文档更好用，遇到组合相关报错应先读它。第六行是默认行为：`.*` 可空，未开 `ALLOWEMPTY` 时被拒；第七行证明打开后即可编译，同时也预告了「每个字节都会命中」的后果。整个程序的释放路径是完整的：成功分支 `hs_free_database`，失败分支 `hs_free_compile_error`，`err` 为 NULL 时该函数也安全（`src/hs_compile.h:700-710`）。

第二个片段演示「组合表达式 + 静默子表达式」的正确写法。三条子表达式都被 `QUIET` 静默，第四条是组合公式，只有它会回调。

```c
const char *exprs[4] = { "login", "passwd", "token", "0&1&!2" };
unsigned flags[4] = {
    HS_FLAG_QUIET, HS_FLAG_QUIET, HS_FLAG_QUIET,
    HS_FLAG_COMBINATION | HS_FLAG_SINGLEMATCH
};
unsigned ids[4] = { 1, 2, 3, 100 };
hs_database_t *db = NULL;
hs_compile_error_t *err = NULL;
hs_error_t rc = hs_compile_multi(exprs, flags, ids, 4,
                                 HS_MODE_BLOCK, NULL, &db, &err);
```

这段代码里 `ids` 与组合公式的**下标**是两套编号：公式 `0&1&!2` 用的是数组下标，回调里看到的 `id` 是 `ids[]` 里的 100。混用这两套编号是最常见的一类逻辑错误——把 `id` 写进公式，编译器不会报错，但语义完全不对。

### 5. 速查表

按「我要什么效果」反查标志，速查表如下。

| 需求 | 标志组合 | 备注 |
|---|---|---|
| 忽略大小写 | `CASELESS` | 可用 `(?i)` 局部覆盖 |
| `.` 跨行 | `DOTALL` | 与 `MULTILINE` 不同 |
| `^`/`$` 按行 | `MULTILINE` | 可能影响锚定优化 |
| 每 ID 只报一次 | `SINGLEMATCH` | 同 ID 组必须一致 |
| 允许 `.*` 类模式 | `ALLOWEMPTY` | 会每字节命中 |
| 按字符计数 | `UTF8` | 数据须为合法 UTF-8 |
| Unicode 字符类 | `UTF8 \| UCP` | 单独 `UCP` 无效 |
| 需要起始偏移 | `SOM_LEFTMOST` + horizon | 流式必须给 horizon |
| 预过滤粗筛 | `PREFILTER` | 有假阳性，须二次确认 |
| 逻辑组合 | 子项 `QUIET` + 组合项 `COMBINATION` | 操作数是下标 |
| 静默某条规则 | `QUIET` | 只抑制回调，不省算力 |

速查表里 `UTF8 \| UCP` 与 `UTF8` 加 `UCP` 是同一件事，写成转义竖线只是为了表格不被解析错列。真正需要记忆的是三组「不能同时出现」：`SOM_LEFTMOST` 对 `SINGLEMATCH`、`SOM_LEFTMOST` 对 `PREFILTER`、`SOM_LEFTMOST` 对 `QUIET`；以及一组「只能这样配」：`COMBINATION` 只容得下 `QUIET` 与 `SINGLEMATCH`。

### 6. 版本差异

11 个标志在 5.4.2 的头文件里全部存在，位值自引入以来没有变过，这一点很重要：序列化数据库里存的是编译结果而不是标志原文，但跨版本比对行为时，位值稳定意味着日志里的数字可以直接对照本文表格。

引入时间线可以分成三段。5.0.0 引入逻辑组合（`COMBINATION` 与 `QUIET`）与 Chimera，这是报告族从「逐条上报」扩展到「布尔组合上报」的分界点；同版本还带来 Windows 工具链支持。5.2.0 引入纯字面量 API（`hs_compile_lit` 系列），该 API 只接受三个标志，本篇的 11 个标志里大部分在纯字面量路径上会被拒绝，详见 04-04。5.4.1 修复了 `hs_expression_info()` 对逻辑组合标志的处理（变更日志 issue #291，「bypass logical combination flag」），也就是说在 5.4.0 及更早版本上，把 `COMBINATION` 传给 `hs_expression_info()` 可能得到非预期结果；如果你在用表达式信息探测工具，需要留意这一点。

`SINGLEMATCH` 与 `SOM_LEFTMOST` 的互斥不是新问题，源码注释里标着 `FIXME: we disallow highlander + SOM, see UE-1850`（`src/compiler/compiler.cpp:192`、`242`），说明这是长期存在的架构性限制而非临时 bug；`PREFILTER` 与 SOM 的互斥同样标注了 `UE-1899`。把这两个内部编号记下来，在社区 issue 里检索时比搜标志名更有效。5.4.2 对标志语义没有改动，其变更集中在 scratch 行为与 hsdump，属于 04-06 与 04-07 的范围。

### 7. 常见误用与调试

标志类问题的共性是「编译能过、结果不对」，因为大部分错误组合会被编译器挡住，真正难查的是那些**合法但语义反直觉**的组合。下表按现象归类。

| 现象 | 根因 | 处置 |
|---|---|---|
| 每个字节都命中 | 开了 `ALLOWEMPTY` 且模式可空 | 改用 `.+` 或加锚点 |
| 起始偏移恒为 0 | 未开 `SOM_LEFTMOST` | 加标志并给 horizon |
| 起始偏移为极大值 | 超出 SOM horizon | 换更大 horizon 或缩短流 |
| 预过滤结果偏多 | `PREFILTER` 允许假阳性 | 用 PCRE 二次确认 |
| 加了 `QUIET` 仍变慢 | 匹配照常发生，只是不报 | 真正移除该规则 |
| `UCP` 没效果 | 未同时开 `UTF8` | 两个一起给 |
| 组合公式不触发 | 公式里写了匹配 ID | 改成表达式下标 |
| 同 ID 部分只报一次 | 组内标志不一致 | 统一加或统一不加 |

第一条需要展开：`ALLOWEMPTY` 不是「允许空模式」这么简单，它打开的是「在任意位置都可以产生零宽匹配」的语义，于是扫描器必须在每个字节后都尝试上报，吞吐会掉到正常模式的几分之一甚至更低。若业务确实需要 `.*` 这类模式，正确做法通常是改写为带前后文锚点的形式，或干脆用两次扫描（先找分隔符，再在段内匹配）。

第二条需要展开：`QUIET` 的语义边界常被误解为「禁用」。它只关闭**回调上报**，模式仍然进入 Rose 分解、仍然占用引擎槽位、仍然参与匹配。要真正降低开销，只能在编译期不传这条表达式，或在应用层过滤 `id`。这也解释了为什么 `QUIET` 与 `SOM_LEFTMOST` 互斥：既然不报结果，算起点纯属浪费。

第三条是调试方法：遇到「标志组合到底哪里不合法」，最快的路径不是查文档而是让编译器说话。把 `hs_compile_error_t::message` 原样打进日志（而不是只记返回码），绝大多数互斥问题会直接给出英文原因；再把 `expression` 字段（从 0 开始的下标，非表达式级错误为负）打出来，就能定位到批量编译里的第几条。错误结构与错误码的完整语义见 04-08，编译 API 的返回值约定见 04-04；SOM 的运行期语义与 horizon 细节见 04-03 与 06-10；标志位对引擎选型的影响见 07-04。

## 04-03 扫描模式、SOM horizon 与扩展参数全集

### 1. 本篇定位与覆盖范围

编译标志（04-02）是**逐表达式**的，而扫描模式是**逐数据库**的：`hs_compile` 系列的 `mode` 参数决定整个数据库能接受哪一类扫描调用，一旦编译完成便不可更改。用 block 模式编出的数据库去调用 `hs_open_stream`，或用 stream 模式编出的数据库去调用 `hs_scan`，都会在运行期被数据库校验拒绝，返回 `HS_DB_MODE_ERROR`（-7）。这类错误不是「用法不当」的软提示，而是硬失败，因此模式选择必须在设计阶段一次定对。

本篇覆盖三组常量与一组结构：第一组是三个基础模式 `HS_MODE_BLOCK`、`HS_MODE_STREAM`、`HS_MODE_VECTORED`，外加 `HS_MODE_BLOCK` 的同值别名 `HS_MODE_NOSTREAM`；第二组是三个 SOM horizon 常量 `HS_MODE_SOM_HORIZON_LARGE`、`MEDIUM`、`SMALL`；第三组是五个扩展参数标志 `HS_EXT_FLAG_MIN_OFFSET`、`MAX_OFFSET`、`MIN_LENGTH`、`EDIT_DISTANCE`、`HAMMING_DISTANCE`，以及承载它们的 `hs_expr_ext_t` 结构。结构体的**逐字段内存布局**属于 05-04 的范围，本篇只讲「每个字段约束什么、和谁冲突、配错会怎样」，需要字段偏移与读写时机时请转查 05-04。

模式常量的位值有一个容易踩的坑：三个基础模式占低三位（1、2、4），三个 horizon 占 24、25、26 位，中间大段是空的。这意味着 `mode` 不能用「按位与判断非零」的方式随便拼，必须先确认低三位里**有且仅有一个**被置位，再确认 horizon 最多一个。`src/hs.cpp` 的 `checkMode()` 正是这么做的：先用 `validModeFlags()` 排除未知位，再用 `popcount32(checkmode) != 1` 要求三个基础模式恰好一个，最后用 `(somMode & (somMode - 1)) != 0` 要求 horizon 至多一个（`src/hs.cpp:63-119`）。

还有一条贯穿本篇的边界：**纯字面量 API 不支持扩展参数**。`hs_compile_lit` 与 `hs_compile_lit_multi` 的签名里根本没有 `ext` 参数；即便通过别的方式传入非零 flags 的 `hs_expr_ext_t`，编译器也会报 `Extended parameters are not supported for pure literal matching API`（`src/compiler/compiler.cpp:468-472`）。纯字面量路径同时只接受 `CASELESS`、`SINGLEMATCH`、`SOM_LEFTMOST` 三个标志，这一点在 04-04 的签名与错误示例里还会再出现一次。

### 3. 逐项详解

**`HS_MODE_BLOCK`（1）与 `HS_MODE_NOSTREAM`（1）。** 用于「一次调用扫描一整块连续内存」的场景，对应 `hs_scan(db, data, len, flags, scratch, on_match, ctx)`。`NOSTREAM` 是历史别名，位值与 `BLOCK` 完全相同，二者可以互换，但把两个常量按位或起来没有任何意义（结果仍是 1）。block 模式的特点是：整个缓冲区对引擎完全可见，因此 `$`、`\b`、EOD 相关断言都能在本次调用内判定；起始偏移在开了 SOM 后也不受 horizon 限制，因为不需要跨块记忆。它是批处理、逐文件扫描、逐包扫描（如 `examples/pcapscan.cc` 每个包一次 `hs_scan`）的默认选择。

**`HS_MODE_STREAM`（2）。** 用于「数据分多次到达、匹配需要跨块保持状态」的场景，对应 `hs_open_stream` → 多次 `hs_scan_stream` → `hs_close_stream`。它的核心契约是：**块边界不影响匹配结果**，一个跨越 10 个块的匹配与整块扫描等价。代价是每个流要维护状态，状态大小由 `hs_stream_size()` 给出，且与模式、是否开 SOM、horizon 精度直接相关。流式模式还有两条硬约束：数据必须按序送入，不能回退到历史窗口之外重放；结束语义（EOD）只在 `hs_close_stream` 时触发，因此 `$` 结尾的模式在流未关闭前不会上报。分块策略与状态管理见 03-05，状态压缩原理见 06-11。

**`HS_MODE_VECTORED`（4）。** 用于「数据已经切成多块、但希望一次调用完成扫描」的场景，对应 `hs_scan_vector(db, data, len, count, ...)`。它与 stream 的区别在于**没有跨调用的持久状态**：所有块在同一次调用里给全，引擎可以像处理一整块那样处理它们，块边界同样不影响匹配。它适合「零拷贝收包后按段持有」的 DPI 实现——数据本来就在多个 mbuf 或 iovec 里，不必先拼成连续缓冲区。一个常被忽略的细节：vectored 模式下 SOM 精度**固定为全精度 8 字节**，不受 horizon 影响（`src/hs.cpp:149-153` 中 `getSomPrecision()` 对 VECTORED 直接返回 8），因此在 vectored 上设置 horizon 不仅无益，还会因为「horizon 只能用于 stream」而被 `checkMode` 拒绝。

**`HS_MODE_SOM_HORIZON_LARGE`（`1U<<24`）。** 全精度起点跟踪，`getSomPrecision()` 返回 8 字节。语义上「无论起点在多远的过去都能准确返回」，因此是三者中流状态开销最大的。只在 stream 模式下有意义，且必须与 `HS_FLAG_SOM_LEFTMOST` 配合才有实际作用——只给 horizon 不给标志是合法的，但不会有任何起始偏移上报。若业务无法容忍 `HS_OFFSET_PAST_HORIZON`，只能选它。

**`HS_MODE_SOM_HORIZON_MEDIUM`（`1U<<25`）。** 中等精度，4 字节状态，起点精度限制在「距结束偏移 2^32 字节以内」（`src/hs_compile.h:1194-1204`）。超出该窗口的起点无法表示，运行期以 `HS_OFFSET_PAST_HORIZON`（`~0ULL`）上报。2^32 字节约 4 GiB，对绝大多数 TCP 流而言等同于「永不超过」，因此它是「想要省状态、又不想牺牲正确性」场景的常用折中。

**`HS_MODE_SOM_HORIZON_SMALL`（`1U<<26`）。** 低精度，2 字节状态，窗口 2^16 字节（64 KiB）。适合「匹配起点一定在最近几十 KB 内」的模式，例如带长度上限的协议字段。一旦流的匹配跨度超过 64 KiB，起点就会退化为 `HS_OFFSET_PAST_HORIZON`；应用必须显式判断这个哨兵值，不能直接拿它去做缓冲区切片，否则会得到一次越界访问。这也是三者中唯一「用错会直接影响内存安全」的选项。

**`HS_EXT_FLAG_MIN_OFFSET`（`1ULL`）与 `min_offset`。** 约束「匹配的**结束偏移**不得小于该值」，在此之前即使模式命中也不上报。典型用途是跳过文件头、跳过协议固定前缀。字段是 64 位无符号，单位是字节。它与 `max_offset` 同时给出时，编译器强制 `min_offset <= max_offset`，否则报 `In hs_expr_ext, min_offset must be less than or equal to max_offset`（`src/compiler/compiler.cpp:92-97`）。注意约束的是结束偏移而不是起始偏移，这一点与直觉相反，是扩展参数里最容易写错的一处。

**`HS_EXT_FLAG_MAX_OFFSET`（`2ULL`）与 `max_offset`。** 约束「匹配的结束偏移不得大于该值」，超过后不再上报。它与 `min_offset` 共同构成一个半开区间式的上报窗口：`[min_offset, max_offset]`。两者都只影响上报，不会让引擎提前停止扫描整条流；若希望「超过某点就彻底不再匹配」，需要在应用层关闭流或换一条模式。`max_offset` 还兼任 `min_length` 的上界校验基准（见下条）。

**`HS_EXT_FLAG_MIN_LENGTH`（`4ULL`）与 `min_length`。** 约束「从起点到终点的匹配长度不得小于该值」，用于过滤过短的命中。它与 `min_offset`/`max_offset` 的区别是：后两者看**绝对位置**，它看**相对跨度**。校验规则是「若同时给了 `max_offset`，则 `min_length <= max_offset`」，否则报 `min_length must be less than or equal to max_offset`（`src/compiler/compiler.cpp:99-104`）。这条规则在数学上并不严格（跨度与绝对位置本无必然关系），属于编译器的保守检查；配置时若两者都开，注意不要写出「窗口很小、最小长度很大」的组合。另一个陷阱：`PREFILTER` 模式下 `min_length` 会被静默清零（`src/compiler/compiler.cpp:286-291`），因为预过滤与 SOM 不共存，而长度约束依赖起点信息。

**`HS_EXT_FLAG_EDIT_DISTANCE`（`8ULL`）与 `edit_distance`。** 允许在编辑距离（插入、删除、替换的加权次数）内近似匹配。字段是 32 位无符号，0 表示精确匹配。近似匹配会显著放大状态空间：每增加 1 的距离，候选状态近似按字母表规模展开，编译时间、字节码体积与扫描成本都会上升；对含大量分支或大字符类的模式，可能直接以 `Unable to generate bytecode` 失败。官方文档没有给出「哪些模式支持、最大距离是多少」的完整矩阵，需对照实际版本核验 `doc/dev-reference/compilation.rst` 并以 `hscheck` 实测为准。

**`HS_EXT_FLAG_HAMMING_DISTANCE`（`16ULL`）与 `hamming_distance`。** 允许在 Hamming 距离（只允许替换，不允许增删）内近似匹配，因此要求匹配长度与模式等长——这让它比编辑距离便宜得多，也更适合「固定长度指纹、允许若干位翻转」的场景。它与 `EDIT_DISTANCE` **互斥**，同时置位会报 `cannot have both edit distance and Hamming distance`（`src/compiler/compiler.cpp:106-110`）。两者都只改变「哪些命中算命中」，不改变回调签名；命中仍然是 `(id, from, to)`。

**`hs_expr_ext_t` 的 `flags` 字段。** 它不是「开关集合」而是「哪些字段有效」的掩码：未置位的字段即使填了值也会被忽略。因此正确写法永远是「先清零结构体，再置 flags，再填对应字段」，顺序反了（先填值后置 flags 虽不影响结果，但容易漏置位）就会得到「配了没生效」的假象。未知位会被 `validateExt()` 拒绝，报 `Invalid hs_expr_ext flag set.`（`src/compiler/compiler.cpp:88-90`）。结构体其余字段的含义、读写时机与内存布局见 05-04。

### 4. 典型示例

下面的程序覆盖四个关键场景：流式下缺 horizon、补上 horizon、扩展参数正常、扩展参数越界。每个场景只编译不扫描，便于把编译期行为看清楚。

```c
#include <hs.h>
#include <stdio.h>

static void report(const char *tag, hs_error_t rc, hs_compile_error_t *err) {
    printf("%-16s rc=%d msg=%s\n", tag, rc, err ? err->message : "-");
    hs_free_compile_error(err);
}

int main(void) {
    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;
    hs_expr_ext_t ext = {0};

    /* 1. 流式 + SOM 标志，但没有给 horizon */
    hs_error_t rc = hs_compile("ab+c", HS_FLAG_SOM_LEFTMOST,
                               HS_MODE_STREAM, NULL, &db, &err);
    report("stream-no-horiz", rc, err);

    /* 2. 同一模式，叠加 LARGE horizon */
    err = NULL;
    rc = hs_compile("ab+c", HS_FLAG_SOM_LEFTMOST,
                    HS_MODE_STREAM | HS_MODE_SOM_HORIZON_LARGE,
                    NULL, &db, &err);
    report("stream-large", rc, err);
    if (rc == HS_SUCCESS) { hs_free_database(db); db = NULL; }

    /* 3. 只在上报窗口 [10,110] 内、且长度不小于 4 才报 */
    ext.flags = HS_EXT_FLAG_MIN_OFFSET | HS_EXT_FLAG_MAX_OFFSET |
                HS_EXT_FLAG_MIN_LENGTH;
    ext.min_offset = 10;
    ext.max_offset = 110;
    ext.min_length = 4;
    err = NULL;
    const char *one[1] = { "ab+c" };
    const hs_expr_ext_t *exts[1] = { &ext };
    rc = hs_compile_ext_multi(one, NULL, NULL, exts, 1,
                              HS_MODE_BLOCK, NULL, &db, &err);
    report("ext-ok", rc, err);
    if (rc == HS_SUCCESS) { hs_free_database(db); db = NULL; }

    /* 4. min_length 超过 max_offset，应被拒绝 */
    ext.min_length = 200;
    err = NULL;
    rc = hs_compile_ext_multi(one, NULL, NULL, exts, 1,
                              HS_MODE_BLOCK, NULL, &db, &err);
    report("ext-bad", rc, err);
    return 0;
}
```

运行后的输出形如下面这样（示例输出，具体格式需对照实际版本核验）。

```text
stream-no-horiz  rc=-4 msg=To use a SOM expression flag in streaming mode, an SOM precision mode (e.g. HS_MODE_SOM_HORIZON_LARGE) must be specified.
stream-large     rc=0 msg=-
ext-ok           rc=0 msg=-
ext-bad          rc=-4 msg=In hs_expr_ext, min_length must be less than or equal to max_offset.
```

逐行判读这份输出。第一行的 `rc=-4` 是 `HS_COMPILER_ERROR`，消息里点明了「流式模式下使用 SOM 表达式标志，必须指定 SOM 精度模式」——这条错误来自 `src/compiler/compiler.cpp:427-433` 的检查，触发条件是「表达式带 SOM 且数据库是流式且未给 horizon」，三者同时成立；它不会在 block 模式出现，所以同一段代码在 block 下能编过、在 stream 下编不过，是最容易误判为「环境问题」的情形。第二行 `rc=0` 证明加上 `HS_MODE_SOM_HORIZON_LARGE` 后通过，同时说明 horizon 是**模式位**而非表达式标志，必须拼进第三个参数。第三行 `ext-ok` 说明三个扩展标志的组合合法：`min_offset=10 ≤ max_offset=110`，`min_length=4 ≤ 110`，窗口与长度都成立；注意这里 `flags` 与 `ids` 传了 NULL，头文件明确允许「以 NULL 代替数组表示全部取 0」（`src/hs_compile.h:466-492`）。第四行 `ext-bad` 是最有价值的一条：把 `min_length` 改成 200 后立刻被拒，错误消息直接给出不等式关系，说明校验发生在编译期而非扫描期，配置错误不会拖到线上才暴露。整个程序的资源路径也完整：每次失败都调用 `hs_free_compile_error`（传 NULL 安全），每次成功都 `hs_free_database`。

第二个片段演示 horizon 与流状态大小的关系。它先用 `hs_stream_size()` 量出全精度下的状态，再对比小精度，从而在没有基准工具的情况下也能判断「换 horizon 到底省了多少」。

```c
static void size_for(unsigned mode, const char *tag) {
    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;
    size_t sz = 0;
    hs_error_t rc = hs_compile("ab+c", HS_FLAG_SOM_LEFTMOST,
                               HS_MODE_STREAM | mode, NULL, &db, &err);
    if (rc != HS_SUCCESS) {
        printf("%-8s compile failed: %s\n", tag, err ? err->message : "-");
        hs_free_compile_error(err);
        return;
    }
    hs_stream_size(db, &sz);
    printf("%-8s stream_size=%zu bytes\n", tag, sz);
    hs_free_database(db);
}
```

调用 `size_for(HS_MODE_SOM_HORIZON_LARGE, "large")`、`size_for(HS_MODE_SOM_HORIZON_MEDIUM, "medium")`、`size_for(HS_MODE_SOM_HORIZON_SMALL, "small")` 三次，即可得到同一模式在三种精度下的状态开销。判读要点是：三个数字应当单调递减，但差值不一定与「8/4/2 字节」成正比，因为流状态还包含 NFA 状态、队列等与 horizon 无关的部分；若 small 相对 large 只省了很少，说明该模式的状态主要花在别处，换 horizon 意义不大。`hs_stream_size` 的完整语义见 04-06，流状态的压缩表示见 06-11。

### 5. 速查表

把「数据形态」「是否需要起点」「能容忍多大窗口」三个问题串起来，就能定位到唯一组合。速查表如下。

| 场景 | mode 取值 | 附加要求 |
|---|---|---|
| 整块内存一次扫描 | `HS_MODE_BLOCK` | 无需 horizon |
| 多块但一次调用给全 | `HS_MODE_VECTORED` | SOM 固定全精度 |
| 数据分段到达 | `HS_MODE_STREAM` | 无需 SOM 时可不给 horizon |
| 流式且要精确起点 | `STREAM \| LARGE` | 状态最大，永不越界 |
| 流式且流很长 | `STREAM \| MEDIUM` | 4 GiB 窗口，通常够用 |
| 流式且跨度有上限 | `STREAM \| SMALL` | 64 KiB 窗口，须判哨兵 |
| 只看某段偏移内 | `MIN_OFFSET \| MAX_OFFSET` | 约束的是结束偏移 |
| 过滤过短命中 | `MIN_LENGTH` | 与 `max_offset` 有交叉校验 |
| 允许增删改 | `EDIT_DISTANCE` | 代价高，慎用大距离 |
| 定长允许替换 | `HAMMING_DISTANCE` | 与 edit 互斥 |

三种 horizon 的精度与代价对照如下表，数字来自 `getSomPrecision()` 的返回值（单位字节）与头文件注释给出的窗口。

| horizon | 状态精度 | 窗口 | 越界表现 |
|---|---|---|---|
| `LARGE` | 8 字节 | 无限制 | 不会越界 |
| `MEDIUM` | 4 字节 | 2^32 字节 | 返回 `HS_OFFSET_PAST_HORIZON` |
| `SMALL` | 2 字节 | 2^16 字节 | 返回 `HS_OFFSET_PAST_HORIZON` |

`HS_OFFSET_PAST_HORIZON` 的值是 `~0ULL`，即 64 位全 1（`src/hs_runtime.h:615`）。判读时不要用 `from > to` 之类的比较来识别它，直接与该常量做相等比较，否则在某些平台上 `~0ULL` 的打印形式会让你误以为是一个正常的大偏移。

### 6. 版本差异

模式常量的位值在 5.4.2 中保持稳定：`BLOCK`/`NOSTREAM` 为 1、`STREAM` 为 2、`VECTORED` 为 4，三个 horizon 分别为 `1U<<24`、`1U<<25`、`1U<<26`。位值稳定意味着跨版本传递 `mode` 整数是安全的，但**数据库本身不跨版本兼容**：序列化格式带版本号，加载不匹配的数据库会返回 `HS_DB_VERSION_ERROR`（-5），这一点与 mode 无关，详见 06-12。

扩展参数在 5.x 系列中语义稳定，本快照的 `CHANGELOG.md` 从 5.0.0 到 5.4.2 没有列出「新增 `HS_EXT_FLAG_*`」的条目，说明这五个标志至少在该区间内未变；更早的引入版本需对照实际的变更日志核验。5.0.0 引入了逻辑组合，而逻辑组合与扩展参数有交叉限制：带 `COMBINATION` 的表达式只允许 `MIN_OFFSET` 与 `MAX_OFFSET`，其余三个扩展标志会报错（`src/compiler/compiler.cpp:373-379`），这条限制在 5.4.x 上仍然有效。

与 horizon 相关的行为变化主要落在流状态压缩上：5.4.0 引入 Sheng32/Sheng64/McSheng64 与 DFA 状态空间优化，改变了部分模式的状态规模，但 horizon 的语义与常量未变；5.4.2 回退了 5.4.1 的 scratch 快速校验，恢复「用更大的 scratch 服务其他数据库」的允许行为。这些都属于运行期资源层面，不影响本篇的取值表。

### 7. 常见误用与调试

模式与扩展参数的错误大多能在编译期暴露，难的是「编译通过但语义不符」。下表按现象归类，随后是三条补充。

| 现象 | 根因 | 处置 |
|---|---|---|
| `HS_DB_MODE_ERROR` | 数据库与扫描 API 不匹配 | 核对编译时的 mode |
| 流式 SOM 编译失败 | 未给 horizon | 叠加 `SOM_HORIZON_*` |
| block 下设 horizon 报错 | horizon 仅限 stream | 去掉 horizon |
| 同时设两个 horizon 报错 | 只能三选一 | 只保留一个 |
| 起点为 `~0ULL` | 超出 horizon 窗口 | 换大 horizon 或判哨兵 |
| `min_length` 报错 | 大于 `max_offset` | 调整窗口或长度 |
| edit 与 hamming 同开报错 | 二者互斥 | 只留一个 |
| 配了扩展参数无效果 | `flags` 未置对应位 | 检查掩码 |
| 预过滤下长度约束失效 | `min_length` 被清零 | 不用 prefilter 或改用 SOM |

第一条补充：**`HS_MODE_VECTORED` 与 `HS_MODE_STREAM` 不能混用**。vectored 是「一次调用、多块输入、无持久状态」，stream 是「多次调用、跨调用状态」；两者的数据库互不通用。若业务既需要零拷贝块列表、又需要跨调用保持状态，正确做法是用 stream 并在应用层缓存块，而不是把 vectored 数据库反复喂给 `hs_scan_vector` 期待它记住上一批。

第二条补充：**扩展参数是「编译期剪枝」，不是「运行期过滤」**。编译器会依据 `min_offset`/`max_offset`/`min_length` 调整引擎与状态，因此不符合约束的命中根本不会产生；这也意味着参数写错时不会「多报」，而是「少报甚至不报」，排查方向应从「约束是否过严」入手，而不是怀疑漏匹配。近似匹配同理：距离设小了会漏，设大了会爆状态。

第三条补充：**哨兵值必须显式判断**。`HS_OFFSET_PAST_HORIZON` 只在 MEDIUM/SMALL 下出现，一旦把它当作正常偏移去切片，就会读到非法内存。推荐在回调里第一件事就判断 `from == HS_OFFSET_PAST_HORIZON`，命中则丢弃或降级处理。更完整的回调语义见 04-05，SOM 槽位与精度原理见 06-10，horizon 对引擎选型的影响见 07-04。

## 04-04 编译 API 全集（签名、返回值、典型用法）

### 1. 本篇定位与覆盖范围

本篇是「编译侧」函数签名的唯一权威源，覆盖 `src/hs_compile.h` 中全部 9 个公开函数：`hs_compile`、`hs_compile_multi`、`hs_compile_ext_multi`、`hs_compile_lit`、`hs_compile_lit_multi`、`hs_expression_info`、`hs_expression_ext_info`、`hs_populate_platform`、`hs_free_compile_error`。每个函数给出完整签名、逐参数含义、返回值约定、失败时的资源归属，以及一个能直接编译运行的最小用法。

本篇**不**覆盖运行期函数（`hs_scan` 系列在 04-05）、scratch 与序列化（04-06）、错误码总表与排错流程（04-08）。也不展开编译流水线内部（06-01 起）与数据库字段布局（05-02）。需要理解「为什么这个模式编不过」时，本篇给你 API 层的判据；需要理解「编译器内部走到哪一步失败」时，请转到 06-01 与 07-03。

读签名之前先建立三条公共约定，它们适用于全部 9 个函数。

第一，**返回类型统一是 `hs_error_t`**，本质是 `int`（`src/hs_common.h:69`），成功为 `HS_SUCCESS`（0），编译失败为 `HS_COMPILER_ERROR`（-4），参数/架构类问题可能是 `HS_INVALID`、`HS_NOMEM`、`HS_ARCH_ERROR` 等。不要只判断「非零」，因为不同负值对应的处置完全不同。

第二，**错误详情通过 `hs_compile_error_t **error` 出参返回**，结构只有两个字段：`message`（人类可读字符串）与 `expression`（从 0 开始的下标；非表达式级错误为负）。它由库分配，调用方必须用 `hs_free_compile_error()` 释放，成功路径上该指针为 NULL。若调用方传 `error == NULL`，函数无法写错误信息，会直接返回 `HS_COMPILER_ERROR`（`src/hs.cpp:174-180`），这是「只看到 -4、没有任何消息」的唯一原因。

第三，**数据库通过 `hs_database_t **db` 出参返回**，失败时被置 NULL。数据库不可变、由库分配，必须用 `hs_free_database()` 释放（`src/hs_common.h:84`）。`db` 与 `error` 两个出参指针本身都不能为 NULL（`db` 为 NULL 会得到 `Invalid parameter: db is NULL`）。

理解五个编译入口的分工，比背签名更有用。`hs_compile` 是「一条正则」的便捷封装；`hs_compile_multi` 是「规则集」的标准入口；`hs_compile_ext_multi` 在规则集之上叠加逐条的偏移、长度与容错约束；两个 `_lit` 变体则绕开正则解析器，把输入当作纯字节串。选择依据不是「哪个更高级」，而是两个正交问题：输入是不是正则、要不要逐条约束。是正则且要约束用 `ext_multi`，是正则但不要约束用 `multi`，不是正则用 `_lit_multi`。混用会带来两类隐性成本：把纯字面量送进 `multi`，编译器仍要做完整解析与图构造，编译时间可能是前者的数倍；把正则送进 `_lit`，量词与字符类会被当成普通字符，匹配结果与预期完全不符，而且不会报错。

### 3. 逐项详解

先把 9 个签名原样列出，便于逐字对照头文件。

```c
hs_error_t HS_CDECL hs_compile(const char *expression, unsigned int flags,
                               unsigned int mode,
                               const hs_platform_info_t *platform,
                               hs_database_t **db, hs_compile_error_t **error);

hs_error_t HS_CDECL hs_compile_multi(const char *const *expressions,
                                     const unsigned int *flags,
                                     const unsigned int *ids,
                                     unsigned int elements, unsigned int mode,
                                     const hs_platform_info_t *platform,
                                     hs_database_t **db,
                                     hs_compile_error_t **error);

hs_error_t HS_CDECL hs_compile_ext_multi(const char *const *expressions,
                                         const unsigned int *flags,
                                         const unsigned int *ids,
                                         const hs_expr_ext_t *const *ext,
                                         unsigned int elements, unsigned int mode,
                                         const hs_platform_info_t *platform,
                                         hs_database_t **db,
                                         hs_compile_error_t **error);

hs_error_t HS_CDECL hs_compile_lit(const char *expression, unsigned flags,
                                   const size_t len, unsigned mode,
                                   const hs_platform_info_t *platform,
                                   hs_database_t **db,
                                   hs_compile_error_t **error);

hs_error_t HS_CDECL hs_compile_lit_multi(const char *const *expressions,
                                         const unsigned *flags,
                                         const unsigned *ids,
                                         const size_t *lens,
                                         unsigned elements, unsigned mode,
                                         const hs_platform_info_t *platform,
                                         hs_database_t **db,
                                         hs_compile_error_t **error);

hs_error_t HS_CDECL hs_expression_info(const char *expression,
                                       unsigned int flags,
                                       hs_expr_info_t **info,
                                       hs_compile_error_t **error);

hs_error_t HS_CDECL hs_expression_ext_info(const char *expression,
                                           unsigned int flags,
                                           const hs_expr_ext_t *ext,
                                           hs_expr_info_t **info,
                                           hs_compile_error_t **error);

hs_error_t HS_CDECL hs_populate_platform(hs_platform_info_t *platform);

hs_error_t HS_CDECL hs_free_compile_error(hs_compile_error_t *error);
```

**`hs_compile`。** 单表达式编译，最常用的入口。`expression` 是**裸模式**，不能带 `/.../i` 这类分隔符与修饰符——大小写不敏感要写成 `HS_FLAG_CASELESS`，而不是在字符串尾部加 `i`；`abc?def` 传进去表示正则，`?` 是量词。`flags` 的取值见 04-02，`mode` 见 04-03。`platform` 为 NULL 时按**当前主机**生成数据库，这意味着在 Ice Lake 上编出的库可能无法在老的 Haswell 上运行（加载时报 `HS_DB_PLATFORM_ERROR`）；跨机分发必须显式给 platform，或用 `HS_PLATFORM_ALL` 编「通用库」。成功返回 0 并写出 `*db`；失败返回 -4，`*db` 置 NULL，`*error` 指向错误结构。

**`hs_compile_multi`。** 多表达式一次编译，是生产环境的主力入口。`expressions` 是 `const char *const *`，即「指向常量字符串的指针数组」；`flags`、`ids` 可以为 NULL，NULL 表示「全部取 0」（`src/hs_compile.h:382-408`）。`ids` 是**匹配 ID**，会原样出现在回调的第一个参数里，允许重复、允许不连续；它与 04-02 里 `COMBINATION` 公式使用的**数组下标**是两套编号，务必区分。`elements` 必须大于 0，为 0 会得到 `Invalid parameter: elements is zero`；总量上限由 `HS_MAX_PATTERN_COUNT`（1000000）约束（`src/hs_common.h:595`、`src/grey.cpp:149`）。数组本身由调用方持有，函数返回后即可释放。

**`hs_compile_ext_multi`。** 在 `multi` 基础上增加 `ext` 数组，每个元素是 `hs_expr_ext_t *`，可以为 NULL（表示该条不带扩展参数），整个数组也可以为 NULL。扩展参数的含义与约束见 04-03；这里只需记住三点：结构体内存由调用方分配与释放，库不会接管；`flags` 字段是「哪些字段有效」的掩码；带 `COMBINATION` 的表达式只允许 `MIN_OFFSET` 与 `MAX_OFFSET`。它的参数顺序是 `expressions, flags, ids, ext, elements, mode, platform, db, error`，`ext` 插在 `ids` 之后、`elements` 之前，与 `multi` 相比多了一个位置，手写原型时最容易错位。

**`hs_compile_lit`。** 纯字面量编译，5.2.0 引入。与 `hs_compile` 的根本区别是**不做正则解析**：`abc?` 表示 `a`、`b`、`c`、`?` 四个字符，`?` 不是量词。因为要支持字面量中出现 `\0`，长度不能靠 `strlen`，必须由 `len` 显式给出；`len` 是 `size_t`，在 32 位与 64 位平台上宽度不同，跨平台代码不要把它硬转成 `int`。`flags` 只接受 `CASELESS`、`SINGLEMATCH`、`SOM_LEFTMOST` 三个，其余（`DOTALL`、`ALLOWEMPTY`、`UTF8`、`UCP`、`PREFILTER`、`COMBINATION`、`QUIET`、`MULTILINE`）会报 `Only HS_FLAG_CASELESS, HS_FLAG_SINGLEMATCH and HS_FLAG_SOM_LEFTMOST are supported in literal API.`（`src/compiler/compiler.cpp:480-487`）。空串也被拒绝（5.4.1 起显式检查）。

**`hs_compile_lit_multi`。** 批量纯字面量编译，比 `lit` 多出 `flags`、`ids`、`lens` 三个并行数组，`lens[i]` 是第 i 条字面量的字节长度。三个数组都可以为 NULL（全部取 0 / 默认），但**只要有一条字面量含 `\0`，就必须给 `lens`**，否则会按 `strlen` 截断。它的参数顺序是 `expressions, flags, ids, lens, elements, mode, platform, db, error`，`lens` 位于 `ids` 之后。纯字面量数据库仍然用传统运行时 API 扫描（`hs_scan` 等），不需要特殊的扫描函数。

**`hs_expression_info`。** 只做语法分析，返回匹配宽度等元信息，不产出数据库。`hs_expr_info_t` 的字段是 `min_width`、`max_width`、`unordered_matches`、`matches_at_eod`、`matches_only_at_eod`（字段含义与保守性说明见 05-04）。`max_width` 在无上界时取 `UINT_MAX`，因此判读「是否定长」要看 `min_width == max_width` 且不等于 `UINT_MAX`，而不是看是否「很小」。头文件有一句极重要的警告：**本函数返回成功不代表同一表达式能被 `hs_compile` 编译成功**（`src/hs_compile.h:717-721`），它可能对 Hyperscan 无法编译的正则返回 0。因此它适合做「宽度预估、EOD 判定」这类辅助决策，不能当作「编译预检」。另外，`ALLOWEMPTY`、`SOM_LEFTMOST` 这类标志会被接受但不影响结果，`QUIET` 被忽略；`COMBINATION` 在 5.4.1 起被绕过（变更日志 issue #291）。

**`hs_expression_ext_info`。** 与上者相同，但多了 `hs_expr_ext_t *ext` 入参，能把扩展参数纳入宽度估算。例如给了 `edit_distance` 后，`max_width` 的估算会把容错带来的长度浮动考虑进去；给了 `min_length` 后，`min_width` 不会低于该值。同样要记住「成功不代表可编译」，以及 `ext` 为 NULL 等价于不带扩展参数。它存在的意义是让上层在真正编译前就能算出「这条规则最坏会占多少缓冲区」，用于容量规划。

**`hs_populate_platform`。** 把当前主机的调优族与 CPU 特性填进 `hs_platform_info_t`，供编译时显式指定。返回 0 表示成功；在不受支持的架构上可能返回 `HS_ARCH_ERROR`。典型用法是「本机编译、本机运行」时先用它填结构体、再传给 `hs_compile`，这样数据库的 platform 字段与本机严格一致，避免默认路径下「按本机生成」与「显式指定」之间可能出现的差异。结构体三个字段（`tune`、`cpu_features`、两个 `reserved`）的含义见 05-04；调优族取值 `HS_TUNE_FAMILY_GENERIC`(0) 到 `HS_TUNE_FAMILY_ICX`(10) 见本篇速查表。

**`hs_free_compile_error`。** 释放错误结构，`error` 可为 NULL（安全）。返回 0 表示成功。它只释放 `message` 与结构体本身，不影响数据库；反过来 `hs_free_database` 也不释放错误结构。二者必须分别调用，最常见的泄漏就是「失败分支只打了日志、忘了 free」——一次编译失败通常只泄漏几十字节，但在规则热更新的服务里会累积成可观测的 RSS 增长。

### 4. 典型示例

下面是一段完整的「探测 → 编译 → 判错 → 释放」流程，覆盖 `hs_populate_platform`、`hs_compile_multi`、`hs_expression_info` 与 `hs_free_compile_error`。

```c
#include <hs.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    hs_platform_info_t plat;
    memset(&plat, 0, sizeof(plat));
    if (hs_populate_platform(&plat) != HS_SUCCESS) {
        printf("populate_platform failed\n");
        return 1;
    }
    printf("tune=%u cpu_features=0x%llx\n", plat.tune, plat.cpu_features);

    /* 先探测一条合法模式的宽度 */
    hs_expr_info_t *info = NULL;
    hs_compile_error_t *err = NULL;
    hs_error_t rc = hs_expression_info("foo[0-9]bar", HS_FLAG_CASELESS,
                                       &info, &err);
    if (rc == HS_SUCCESS) {
        printf("width=%u..%u at_eod=%d only_eod=%d unordered=%d\n",
               info->min_width, info->max_width,
               (int)info->matches_at_eod, (int)info->matches_only_at_eod,
               (int)info->unordered_matches);
        free(info);
    } else {
        printf("info failed: %s\n", err ? err->message : "-");
        hs_free_compile_error(err);
    }

    /* 批量编译：第二条故意写错，观察错误定位 */
    const char *exprs[2] = { "foo[0-9]bar", "(abc" };
    unsigned flags[2] = { HS_FLAG_CASELESS, 0 };
    unsigned ids[2] = { 101, 102 };
    hs_database_t *db = NULL;
    err = NULL;
    rc = hs_compile_multi(exprs, flags, ids, 2, HS_MODE_BLOCK, &plat,
                          &db, &err);
    if (rc != HS_SUCCESS) {
        printf("compile rc=%d index=%d msg=%s\n", rc,
               err ? err->expression : -1, err ? err->message : "-");
        hs_free_compile_error(err);
    }
    if (db) { hs_free_database(db); }

    /* 修正后再编一次 */
    exprs[1] = "(abc)";
    err = NULL;
    rc = hs_compile_multi(exprs, flags, ids, 2, HS_MODE_BLOCK, &plat,
                          &db, &err);
    printf("retry rc=%d db=%s\n", rc, db ? "non-null" : "null");
    hs_free_compile_error(err);
    if (db) { hs_free_database(db); }
    return 0;
}
```

输出形如下面这样（示例输出，具体格式需对照实际版本核验）。

```text
tune=2 cpu_features=0x4
width=7..7 at_eod=0 only_eod=0 unordered=0
compile rc=-4 index=1 msg=Missing close paren.
retry rc=0 db=non-null
```

逐行判读。第一行的 `tune=2` 对应 `HS_TUNE_FAMILY_IVB`（Ivy Bridge），`cpu_features=0x4` 是 `HS_CPU_FEATURES_AVX2` 的位值，说明这台机器被识别为支持 AVX2；这两个数字完全取决于宿主机，换机器就会变，因此不要把它们写进断言，只用于确认「platform 确实被填上了而不是全零」。第二行 `width=7..7` 说明 `foo[0-9]bar` 是定长 7 字节，`at_eod=0`、`only_eod=0` 说明它不依赖数据结束位置，`unordered=0` 说明命中按偏移有序——这三项共同决定了上层能否用「流式 + 增量切片」的方式处理，若 `matches_only_at_eod=1` 则所有命中都会堆到 `hs_close_stream` 才出现。第三行是本例的核心：`rc=-4`、`index=1`、`msg=Missing close paren.`，`index=1` 精确定位到第二条表达式（从 0 开始），这就是 `hs_compile_error_t::expression` 的价值；如果没有它，在几千条规则里找一个缺右括号几乎不可能。第四行 `retry rc=0 db=non-null` 证明修正后编译成功，且 `db` 被正确写出；注意这里仍然调用了 `hs_free_compile_error(err)`，因为成功路径上 `err` 为 NULL，该调用是安全的空操作，把释放写在分支外可以避免漏放。

第二个片段演示纯字面量 API 与它的两个硬限制：标志白名单与扩展参数。

```c
const char *lits[2] = { "GET ", "POST" };
unsigned lflags[2] = { HS_FLAG_CASELESS, 0 };
size_t lens[2] = { 4, 4 };
hs_database_t *db = NULL;
hs_compile_error_t *err = NULL;

hs_error_t rc = hs_compile_lit_multi(lits, lflags, NULL, lens, 2,
                                     HS_MODE_BLOCK, NULL, &db, &err);
/* 若把 lflags[0] 改成 HS_FLAG_PREFILTER，会得到：
 * Only HS_FLAG_CASELESS, HS_FLAG_SINGLEMATCH and HS_FLAG_SOM_LEFTMOST
 * are supported in literal API. */
```

这段代码有两个要点。其一，`lens` 必须显式给出，哪怕字面量里没有 `\0`；若传 NULL，库会退回按 `strlen` 处理，含 `\0` 的字面量会被截断。其二，纯字面量路径没有 `ext` 参数，想要「最小长度」「偏移窗口」这类约束只能用普通 `hs_compile_ext_multi`，代价是走完整正则解析、编译更慢、字节码更大。纯字面量 API 的适用场景是「规则本身就是固定字符串」的 DLP/关键字过滤，此时它的编译速度与运行时效率都优于正则路径，模块层面的对比见 07-06。

### 5. 速查表

按任务选函数，速查表如下。

| 任务 | 函数 | 关键提醒 |
|---|---|---|
| 单条正则编译 | `hs_compile` | 模式不带分隔符 |
| 多条正则批量编译 | `hs_compile_multi` | `ids` 可 NULL |
| 带偏移/长度/容错约束 | `hs_compile_ext_multi` | `ext` 在 `ids` 之后 |
| 纯字面量单条 | `hs_compile_lit` | 必须给 `len` |
| 纯字面量批量 | `hs_compile_lit_multi` | 必须给 `lens` |
| 预估匹配宽度 | `hs_expression_info` | 成功不代表可编译 |
| 带扩展参数的宽度预估 | `hs_expression_ext_info` | `ext` 可为 NULL |
| 填本机平台信息 | `hs_populate_platform` | 架构不支持时返回错误 |
| 释放错误结构 | `hs_free_compile_error` | 传 NULL 安全 |

调优族取值也放在这里备查：`GENERIC` 0、`SNB` 1、`IVB` 2、`HSW` 3、`SLM` 4、`BDW` 5、`SKL` 6、`SKX` 7、`GLM` 8、`ICL` 9、`ICX` 10（`src/hs_compile.h:1062-1142`）。CPU 特性只有三位有效：`AVX2` 为 `1ULL<<2`、`AVX512` 为 `1ULL<<3`、`AVX512VBMI` 为 `1ULL<<4`；`HS_PLATFORM_ALL` 是一个特殊常量 `0xabcdef11abcdef00ULL`，用于编「通用数据库」。把 `tune` 设成大于 10 的值会被 `checkPlatform()` 拒绝，报 `Invalid tuning value specified in the platform information.`（`src/hs.cpp:138-142`）；`cpu_features` 置了三位之外的位则报 `Invalid cpu features specified`。

### 6. 版本差异

9 个函数的签名在 5.4.2 中保持稳定，`HS_CDECL` 在 Windows 上展开为 `__cdecl`、其他平台为空（`src/hs_common.h:32-36`），因此跨平台声明无需额外修饰。

按时间线看，5.0.0 引入逻辑组合（与 `COMBINATION` 配套），并带来 Chimera；5.2.0 新增 `hs_compile_lit` 与 `hs_compile_lit_multi`，这是编译 API 家族最后一次扩容，变更日志明确写为「add new API `hs_compile_lit()` and `hs_compile_lit_multi()` to process pure literal rule sets」。5.4.1 修了三个与本篇直接相关的问题：`hs_expression_info()` 绕过逻辑组合标志（issue #291）、纯字面量 API 的空串检查（issue #302/304）、纯字面量「unknown instruction」错误（issue #303）。也就是说，5.4.0 及更早版本上，空串字面量与组合标志的行为可能与本篇描述不同，需对照实际版本核验。5.4.2 对编译 API 无改动。

还有一处版本敏感点：`hs_compile_lit` 的 `len` 是 `size_t`，而 `hs_compile_lit_multi` 的 `lens` 是 `const size_t *`。这两个类型在 5.2.0 引入时就是这样，没有历史包袱；但如果你在 32 位平台上把 `len` 存进 `int` 再传出，超过 2 GiB 的字面量会被截断——实际上不可能有这么大的单条字面量（受 `limitPatternLength` 约束，默认 16000 字节，`src/grey.cpp:150`），真正的风险是**长度与内容不一致**：`len` 给大了会读到缓冲区之外。打开 `VALIDATE_PATTERN_INPUT` 可以在编译期挡住这类畸形输入（见 04-01），生产环境处理外部规则时应考虑。

### 7. 常见误用与调试

编译 API 的问题集中在「资源归属」与「错误信息丢失」两类。下表按现象给出判据。

| 现象 | 根因 | 处置 |
|---|---|---|
| 只有 -4，没有消息 | `error` 传了 NULL | 传入 `&err` 并打印 message |
| 每次编译都泄漏几十字节 | 失败分支未 free 错误 | 统一在出口释放 |
| `db` 非空但 rc 非 0 | 复用了上次的 `db` 变量 | 每次调用前置 NULL |
| 模式带 `/.../i` 报错 | 传了分隔符与修饰符 | 只传裸模式 |
| 字面量被截断 | 用 `strlen` 而非 `len` | 显式给长度 |
| 字面量为空串被拒 | 纯字面量 API 不支持空串 | 校验输入或改走正则路径 |
| 宽度预估成功但编译失败 | 误把 info 当预检 | 以 `hs_compile` 结果为准 |
| 跨机加载报平台错 | 未显式给 platform | 用 `hs_populate_platform` 或通用库 |
| 批量编译不知哪条错 | 只打了 message | 同时打 `error->expression` |
| 规则数超限 | 超过 100 万条 | 拆分数据库或预过滤 |

第一条需要展开：**`error` 出参不是可选的**。头文件把 `hs_compile_error_t **error` 列为参数而非可选参数，`hs.cpp` 在入口处就检查它是否为 NULL，为 NULL 时直接返回 -4 且不产生任何消息。很多封装层为了「简化接口」把它写成内部变量、只向上抛返回码，结果线上出现「编译失败但不知道为什么」，只能靠二分法定位规则。正确做法是把 `message` 与 `expression` 一起打进日志，前者给原因，后者给位置。

第二条需要展开：**成功路径也可能有错误对象**。虽然正常情况下成功时 `*error` 为 NULL，但某些实现路径会先分配再清空；把 `hs_free_compile_error(err)` 无条件放在出口，比「只在失败分支释放」更安全，也避免分支遗漏。同理，`hs_free_compile_error(NULL)` 是明确定义的安全操作（`src/hs_compile.h:700-710`），不需要额外判空。

第三条需要展开：**`db` 变量必须每次置 NULL**。若复用同一个 `hs_database_t *db` 变量连续编译两次，第一次成功、第二次失败，失败路径虽然会把 `*db` 置 NULL，但若某条错误路径提前返回而没有写 `*db`，残留的旧指针会被误当成新库，后续 `hs_scan` 用的是旧规则、`hs_free_database` 还可能二次释放。把「声明即初始化」与「调用前置 NULL」当成纪律，可以消掉这类最难复现的崩溃。

第四条需要展开：**输入数组的生命周期由调用方负责，且必须覆盖整个调用期间**。`hs_compile_multi` 的 `expressions`、`flags`、`ids` 以及 `ext_multi` 的 `ext` 数组，库只在调用过程中读取，不会接管所有权；函数返回后调用方可以立即释放。但这也意味着不能把「临时构造的字符串」以悬垂指针的形式传进去，例如把 `std::string::c_str()` 存进数组后让 `string` 先析构；这类错误在单条编译时往往侥幸不崩，在批量编译时才会以随机语法错误的形式暴露。稳妥做法是把所有模式先落到一个稳定的容器里，再构造指针数组，编译完成后再统一销毁。

调试顺序建议固定为：先看返回码（区分 -4 与 -1/-2/-11），再看 `message`（绝大多数互斥与语法问题直接可读），再看 `expression`（批量场景定位到条），最后才用 `hs_expression_info` 或 `hsdump` 做深挖。错误码全表与「现象 → 原因 → 验证」的完整速查见 04-08；编译流水线各阶段的失败点见 06-01；`hs_database` 与错误结构的内存归属见 05-02 与 05-04；参数类问题回到 04-02 与 04-03。

## 04-05 运行时扫描 API 全集（block/vectored/stream）

### 1. 本篇定位与覆盖范围

本篇是**运行期扫描函数**的唯一权威源，覆盖 `src/hs_runtime.h` 中全部 11 个公开函数：`hs_scan`（`hs_runtime.h:479`）、`hs_scan_vector`（`hs_runtime.h:522`）、`hs_open_stream`（`hs_runtime.h:148`）、`hs_scan_stream`（`hs_runtime.h:188`）、`hs_close_stream`（`hs_runtime.h:232`）、`hs_reset_stream`（`hs_runtime.h:273`）、`hs_copy_stream`（`hs_runtime.h:291`）、`hs_reset_and_copy_stream`（`hs_runtime.h:324`）、`hs_compress_stream`（`hs_runtime.h:365`）、`hs_expand_stream`（`hs_runtime.h:395`）、`hs_reset_and_expand_stream`（`hs_runtime.h:438`），外加一个回调类型 `match_event_handler`（`hs_runtime.h:125`）与一个哨兵宏 `HS_OFFSET_PAST_HORIZON`（`hs_runtime.h:615`）。scratch 的四个函数虽然物理上也在同一个头文件里（`hs_runtime.h:555-609`），但它们的资源语义与数据库信息、序列化同属一类，统一放在 04-06 讲，本篇只在必要处点名。

本篇**不**覆盖：编译入口与 `hs_compile_error_t`（04-04）、`HS_MODE_*` 与 SOM horizon 的取值（04-03）、`HS_FLAG_*`（04-02）、14 个错误码的完整触发表（04-08）。也**不**展开运行时内部：`dispatcher.c` 怎么按平台挑实现、字节码解释器怎么走队列、流状态怎么压缩，分别属于 06-11、06-13 与 07-10 的范围。本篇只回答「这个函数怎么调、参数是什么、返回什么、什么时候会失败」。

读签名之前必须建立三条总则，它们决定了绝大多数「调了但不对」的问题。

第一，**所有 `flags` 入参当前都是保留位**。`hs_scan`、`hs_scan_vector`、`hs_scan_stream`、`hs_open_stream`、`hs_reset_stream` 的 `unsigned int flags` 在头文件注释里统一写着「provided for future use and unused at present」（`hs_runtime.h:138-139`、`168-170`、`254-256`、`459-461`、`503-505`）。传非零不会报错，但也不会有任何效果；把它当成「运行期开关」是常见误解。真正的行为控制在编译期就已经固化进数据库。

第二，**回调内不可重入同一组资源**。头文件明确要求：回调函数不应在同一个流上再调用 Hyperscan API，也不应复用触发它的那块 scratch；用完全独立的参数（不同数据库、新流、新 scratch）再调一次是可以的，但复用流状态或 scratch 会产生未定义行为（`hs_runtime.h:83-89`）。这条约束不是建议而是契约，违反后可能得到 `HS_SCRATCH_IN_USE`，也可能什么都不报直接算错。

第三，**默认只报结束偏移**。`from` 参数只有在表达式开启 `HS_FLAG_SOM_LEFTMOST` 时才有意义，否则恒为 0（`hs_runtime.h:106-107`）。`to` 是「最后一个匹配字节之后的偏移」，即半开区间的右端。把 `to` 当作「最后一个字节的下标」是差一错误的经典来源。

### 3. 逐项详解

**`hs_scan`。** 签名是 `hs_error_t hs_scan(const hs_database_t *db, const char *data, unsigned int length, unsigned int flags, hs_scratch_t *scratch, match_event_handler onEvent, void *context)`。它是 block 模式数据库的唯一入口，一次调用扫完整块连续内存。`length` 是 `unsigned int` 而不是 `size_t`，这意味着单次调用最多扫 4 GiB 减 1 字节；超过就该切块或改用 stream。`data` 可以为 NULL 且 `length` 为 0，此时不产生任何匹配但仍会做参数校验。`onEvent` 可以为 NULL，语义是「只扫不报」——引擎仍会完整执行匹配流程，只是不回调，用于纯粹测吞吐（`hsbench` 的 `--per-scan` 场景就依赖这一点）。返回值：正常 `HS_SUCCESS`；回调返回非零则 `HS_SCAN_TERMINATED`（-3），此时缓冲区只被扫了一部分；数据库与模式不匹配返回 `HS_DB_MODE_ERROR`（-7），检查点在 `runtime.c:348`；scratch 正在被占用返回 `HS_SCRATCH_IN_USE`（-10），检查点在 `runtime.c:352-357`。

**`hs_scan_vector`。** 签名比 `hs_scan` 多两组并行数组：`const char *const *data` 与 `const unsigned int *length`，再加一个 `unsigned int count`。语义等价于「把这些块首尾相接后扫一遍」，块边界不影响匹配结果，一个跨越第 3 块与第 4 块的匹配与整块扫描完全一致。它是零拷贝 DPI 的首选：数据本来就在多个 mbuf 或 iovec 里，不必先拼成连续缓冲区。三条使用约束：`count` 必须与两个数组的实际长度一致，库无法校验；单块长度仍是 `unsigned int`；块指针数组本身不必连续，但每块的内存必须有效直到调用返回。vectored 模式下 SOM 精度固定为全精度，不受 horizon 影响（`src/hs.cpp:149-153`），因此不要在 vectored 数据库上叠 horizon，`checkMode` 会直接拒绝。

**`hs_open_stream`。** 签名 `hs_error_t hs_open_stream(const hs_database_t *db, unsigned int flags, hs_stream_t **stream)`。它按数据库里记录的流状态大小分配一块状态内存并初始化，返回的 `hs_stream_t *` 是后续所有流式调用的句柄。`flags` 保留为 0。失败时 `*stream` 为 NULL，返回 `HS_NOMEM`（-2）表示分配失败——流状态大小由 `hs_stream_size()` 给出，开了 SOM 或大量有界重复时可能达到几十 KB 到几 MB，高并发下这是真实的内存压力点。数据库必须是 stream 模式编译的，否则返回 `HS_DB_MODE_ERROR`。注意这个函数**不接收 scratch**：开流只分配状态，不做匹配。

**`hs_scan_stream`。** 签名 `hs_error_t hs_scan_stream(hs_stream_t *id, const char *data, unsigned int length, unsigned int flags, hs_scratch_t *scratch, match_event_handler onEvent, void *ctxt)`。把一块数据追加到流上并立即扫描，命中通过回调返回。它的核心契约是「块边界透明」：把同一段数据切成任意多块依次送入，得到的匹配集合与一次性送入完全相同，唯一的差别是回调发生的时刻。因此流式模式下 `$` 结尾的模式不会在最后一块到达时立刻上报，而要等到 `hs_close_stream` 触发 EOD。若前一次回调返回了非零，后续对该流的 `hs_scan_stream` 调用会立即返回 `HS_SCAN_TERMINATED` 而不做任何扫描（`hs_runtime.h:120-123`），这是流级粘滞状态，`hs_reset_stream` 才能清除。`scratch` 必须是为该数据库分配（或更大）的 scratch，且不能与其它并发调用共享。

**`hs_close_stream`。** 签名 `hs_error_t hs_close_stream(hs_stream_t *id, hs_scratch_t *scratch, match_event_handler onEvent, void *ctxt)`。它完成 EOD 匹配并释放流状态。三个要点。其一，**即使扫描已被回调终止，也必须调用它**，否则流状态泄漏（`hs_runtime.h:202-204`）。其二，关闭动作本身可能产生匹配——所有锚定在数据末尾的表达式（`$`、`\z`、`\Z`）都在这一刻才判定；如果不需要这些结果，把 `onEvent` 传 NULL。其三，当 `onEvent` 为 NULL 时 `scratch` 也允许为 NULL（`hs_runtime.h:211-212`），这是唯一允许 scratch 缺省的流式调用，头文件把它写成显式豁免。返回值里的 `HS_SCAN_TERMINATED` 表示「关闭过程中的回调要求停止」，此时流仍然被释放，不需要二次关闭。

**`hs_reset_stream`。** 签名 `hs_error_t hs_reset_stream(hs_stream_t *id, unsigned int flags, hs_scratch_t *scratch, match_event_handler onEvent, void *context)`。语义上等价于「对这条流先 close 再 open」，但它在原地复用已分配的内存，省掉一次 free 加一次 malloc（`hs_runtime.h:238-241`）。它同样会先触发原流的 EOD 匹配，因此 `onEvent` 传 NULL 可以静默丢弃这些结果。重置后流仍绑定同一个数据库（`hs_runtime.h:249`），不能借它换库。这是「长连接复用」场景的关键 API：一个 TCP 五元组断开后重新建连，可以复用同一条 `hs_stream_t`，避免高频分配。

**`hs_copy_stream`。** 签名 `hs_error_t hs_copy_stream(hs_stream_t **to_id, const hs_stream_t *from_id)`。把源流的完整状态（含当前流偏移）复制成一条新流，两条流此后各自独立推进。典型用途是协议分叉：一条连接在某个点可能走 HTTP 也可能走 TLS，复制状态后分别推进，谁先命中就保留谁。代价是一次完整的状态内存拷贝，流状态越大越贵。注意它**不接收 scratch**，因为不产生匹配、不触发 EOD；也因此不会上报任何东西。

**`hs_reset_and_copy_stream`。** 签名 `hs_error_t hs_reset_and_copy_stream(hs_stream_t *to_id, const hs_stream_t *from_id, hs_scratch_t *scratch, match_event_handler onEvent, void *context)`。它把源流状态覆盖到目标流上，覆盖前先重置目标流——而重置会触发目标流原状态的 EOD 匹配，所以它需要 scratch 与回调。两条流必须开在同一个数据库上（`hs_runtime.h:299-300`），跨库复制是未定义行为。与 `hs_copy_stream` 的分工很清楚：需要一条新流用前者，需要在已有句柄上原地覆盖用后者；后者省一次分配，适合「流对象池」的实现。

**`hs_compress_stream`。** 签名 `hs_error_t hs_compress_stream(const hs_stream_t *stream, char *buf, size_t buf_space, size_t *used_space)`。把流状态压成一段自包含的字节串，可落盘、可跨进程传递、可放进共享内存。它**不关闭流**，调用后原流仍可继续使用或正常关闭（`hs_runtime.h:340-341`）。容量不足时返回 `HS_INSUFFICIENT_SPACE`（-12），并把**所需容量**写进 `used_space`——这是唯一一个「失败也写出参」的运行时 API，正确用法是先传 `buf=NULL, buf_space=0` 探一次大小，再按返回值分配。压缩率取决于流状态里有多少可压缩的零区与重复结构，实测常见在数倍到数十倍之间，但没有保证，不要把它当作固定比例。

**`hs_expand_stream`。** 签名 `hs_error_t hs_expand_stream(const hs_database_t *db, hs_stream_t **stream, const char *buf, size_t buf_size)`。把压缩字节还原成一条**新**流，流偏移一并恢复。`db` 必须是压缩时那条流所用的同一个数据库——头文件写明「不总能检测出误用，条件不满足时行为未定义」（`hs_runtime.h:372-375`）。这条警告很重要：压缩格式里没有数据库指纹，用错库不会报错，只会算出莫名其妙的结果。若要在已有句柄上还原，用下面的 `hs_reset_and_expand_stream`。

**`hs_reset_and_expand_stream`。** 签名 `hs_error_t hs_reset_and_expand_stream(hs_stream_t *to_stream, const char *buf, size_t buf_size, hs_scratch_t *scratch, match_event_handler onEvent, void *context)`。语义是「先重置目标流（触发其 EOD），再把压缩状态灌进去」。目标流必须与压缩流同库。它是「会话迁移」场景的主力：把一条流压缩后传到另一个工作线程，在那里用预先分配好的流句柄原地还原，避免每次迁移都 malloc。

**`match_event_handler` 与返回值。** 回调类型是 `typedef int (HS_CDECL *match_event_handler)(unsigned int id, unsigned long long from, unsigned long long to, unsigned int flags, void *context)`（`hs_runtime.h:125-129`）。返回 0 表示继续，返回任何非零值表示立刻停止本次扫描。停止是**立即**的：当前这一块剩下的数据不再扫描，后续块也不再推进。流式模式下这个「已终止」标记会粘在流上，直到 `hs_reset_stream`。`HS_CDECL` 在 Windows 上展开为 `__cdecl`（`src/hs_common.h:32-36`），跨平台代码必须用这个宏而不是默认调用约定，否则 32 位 Windows 上栈会失衡。

**`HS_OFFSET_PAST_HORIZON`。** 宏值是 `~0ULL`，即 64 位全 1（`hs_runtime.h:615`）。它只出现在「开了 SOM 且 horizon 不是 LARGE」的场景，表示这次匹配的起始偏移早于 horizon 窗口，无法精确表示。识别方式必须是与该常量做相等比较，不能靠大小判断或打印字符串匹配。它的语义是「起点未知」而不是「起点在无穷远处」，业务侧通常应当降级处理（丢弃该命中、或退回整块重扫）而不是拿它去切片。回调参数与流状态对象的字段级定义、流式状态机的推进机制、运行时模块的目录归属，三者分别见 05-09、06-11 与 07-10（字段见 05-09 ｜ 原理见 06-11 ｜ 模块见 07-10）。

### 4. 典型示例

下面这段程序把三种形态串起来：先编译一个 stream 模式、带 SOM 的数据库，然后送两块数据、压缩状态、还原到新流、再送一块，最后关闭两条流。它覆盖了 `hs_open_stream`、`hs_scan_stream`、`hs_compress_stream`、`hs_expand_stream`、`hs_close_stream` 五个函数。

```c
#include <hs.h>
#include <stdio.h>
#include <stdlib.h>

static int on_match(unsigned int id, unsigned long long from,
                    unsigned long long to, unsigned int flags, void *ctx) {
    (void)flags;
    int *n = (int *)ctx;
    (*n)++;
    if (from == HS_OFFSET_PAST_HORIZON) {
        printf("  id=%u from=PAST_HORIZON to=%llu\n", id, to);
    } else {
        printf("  id=%u from=%llu to=%llu\n", id, from, to);
    }
    return 0;
}

int main(void) {
    const char *exprs[1] = { "foo[0-9]+bar" };
    unsigned flags[1] = { HS_FLAG_SOM_LEFTMOST };
    unsigned ids[1] = { 1 };
    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;

    if (hs_compile_multi(exprs, flags, ids, 1,
                         HS_MODE_STREAM | HS_MODE_SOM_HORIZON_LARGE,
                         NULL, &db, &err) != HS_SUCCESS) {
        printf("compile failed: %s\n", err ? err->message : "-");
        hs_free_compile_error(err);
        return 1;
    }

    hs_scratch_t *scratch = NULL;
    if (hs_alloc_scratch(db, &scratch) != HS_SUCCESS) {
        printf("scratch alloc failed\n");
        hs_free_database(db);
        return 1;
    }

    size_t stream_size = 0;
    hs_stream_size(db, &stream_size);
    printf("stream state size: %zu bytes\n", stream_size);

    hs_stream_t *st = NULL;
    int matches = 0;
    if (hs_open_stream(db, 0, &st) != HS_SUCCESS) {
        printf("open stream failed\n");
        return 1;
    }
    hs_scan_stream(st, "xxfoo12", 7, 0, scratch, on_match, &matches);
    hs_scan_stream(st, "3baryy", 6, 0, scratch, on_match, &matches);

    size_t need = 0;
    hs_error_t rc = hs_compress_stream(st, NULL, 0, &need);
    printf("probe rc=%d need=%zu\n", rc, need);
    char *buf = malloc(need);
    size_t used = 0;
    hs_compress_stream(st, buf, need, &used);
    printf("compressed: %zu bytes\n", used);

    hs_stream_t *st2 = NULL;
    hs_expand_stream(db, &st2, buf, used);
    hs_scan_stream(st2, "foo9bar", 7, 0, scratch, on_match, &matches);
    hs_close_stream(st2, scratch, on_match, &matches);
    hs_close_stream(st, scratch, on_match, &matches);

    printf("total matches=%d\n", matches);
    free(buf);
    hs_free_scratch(scratch);
    hs_free_database(db);
    return 0;
}
```

编译与运行命令如下。若库安装在非标准前缀，用 `pkg-config --cflags --libs libhs` 取参数更稳妥（模块部署见 03-02）。

```bash
gcc -O2 -o stream_demo stream_demo.c -lhs
./stream_demo
```

示例输出，具体格式需对照实际版本核验。

```text
stream state size: 8464 bytes
  id=1 from=2 to=11
probe rc=-12 need=912
compressed: 912 bytes
  id=1 from=11 to=18
total matches=2
```

逐行判读这份输出，重点在四个数字与一个返回码。第一行 `stream state size: 8464 bytes` 是 `hs_stream_size()` 的结果，它是「每条流」的开销而不是「每次扫描」的开销，一万条并发流就是约 82 MB，这个乘法必须在容量规划时先算清楚；同一模式在 LARGE horizon 下比 SMALL 明显更大，差值就是 SOM 槽位的代价。第二行 `id=1 from=2 to=11` 是跨块匹配的证据：数据实际是 `xxfoo123baryy`，`foo` 起于偏移 2，`bar` 结束于偏移 11，而这个匹配横跨了 `"xxfoo12"` 与 `"3baryy"` 两次 `hs_scan_stream` 调用；如果实现里错误地在每块结束时重置状态，这一行就不会出现，只会得到两个半截候选。第三行 `probe rc=-12 need=912` 是 `HS_INSUFFICIENT_SPACE` 的正常用法：传 `buf=NULL`、容量 0 必定失败，但 `used_space` 被写成所需容量 912，这是「先探后配」的两段式协议，不要把它当错误处理分支。第四行 `compressed: 912 bytes` 说明压缩后的状态约为原始状态的九分之一，但压缩率不承诺，换模式可能变成二分之一。第五行 `from=11 to=18` 是还原后新流继续推进的结果：起始偏移 11 正好接在压缩点之后，证明流偏移随状态一起被保存与恢复；如果这里出现 `from=0`，说明 `hs_expand_stream` 拿错了数据库或者压缩字节被截断。最后一行 `total matches=2` 用于交叉校验：两条流各命中一次，若数字变大说明 EOD 被重复触发（常见于 `hs_close_stream` 之后又 `hs_reset_stream`），若变小说明有一块数据没送进流。

### 5. 速查表

按数据形态与生命周期需求选函数，比逐个记忆签名更可靠。选型速查表如下。

| 场景 | 首选 API | 关键提醒 |
|---|---|---|
| 一整块连续内存 | `hs_scan` | 单次上限 4 GiB 减 1 |
| 零拷贝多块一次扫 | `hs_scan_vector` | `count` 与数组长度须一致 |
| 数据分多次到达 | `hs_open_stream` + `hs_scan_stream` | 必须配对 `hs_close_stream` |
| 长连接复用句柄 | `hs_reset_stream` | 会先触发原流 EOD |
| 协议分叉 | `hs_copy_stream` | 完整状态拷贝，代价随状态大小增长 |
| 池化句柄原地复用 | `hs_reset_and_copy_stream` | 两流必须同库 |
| 状态落盘/迁移 | `hs_compress_stream` | 先探容量再分配 |
| 从字节还原新流 | `hs_expand_stream` | 库必须是压缩时那个 |
| 在工作线程原地还原 | `hs_reset_and_expand_stream` | 目标流须预先分配 |
| 只测吞吐不取结果 | 回调传 NULL | 匹配照算，只是不报 |

三种形态的「状态归属」与「EOD 时机」对照如下表。这两列决定了出错时的排查方向：状态归属错会导致跨调用丢匹配，EOD 时机错会导致尾部锚定模式永远不报。

| 形态 | 状态归属 | EOD 触发点 | 典型失败 |
|---|---|---|---|
| block | 调用栈内，无持久状态 | 调用返回前 | 跨块模式漏匹配 |
| vectored | 调用栈内，块间连续 | 调用返回前 | 块顺序给错 |
| stream | `hs_stream_t` 堆对象 | `hs_close_stream` / `hs_reset_stream` | 忘记 close 导致泄漏 |

### 6. 版本差异

11 个函数的签名在 5.4.2 中保持稳定，`HS_CDECL` 的展开规则也没有变化，因此按本篇写出的调用代码可以跨 4.x 后期到 5.4.x 直接编译。真正的差异在行为细节上。

流状态压缩是 4.6.0 引入的（`CHANGELOG.md` 的 `[4.6.0] 2017-09-22` 条目写明「New API feature: stream state compression」），因此 `hs_compress_stream`、`hs_expand_stream`、`hs_reset_and_expand_stream` 三个函数在更早的 4.5.x 及以前不存在。若你的分支早于 4.6.0，这三个符号链接期就会缺失。`hs_reset_stream` 与 `hs_reset_and_copy_stream` 允许 scratch 为 NULL 的行为始于 4.0.1（`[4.0.1] 2015-10-30` 条目），与 `hs_close_stream` 对齐；在 4.0.0 上必须传有效 scratch，否则行为未定义。

`HS_SCRATCH_IN_USE` 这个错误值是 4.2.0 引入的（`[4.2.0] 2016-05-31` 条目），在此之前并发复用 scratch 不会被检测，只会静默算错。这意味着「靠返回码发现 scratch 冲突」的做法只在 4.2.0 之后成立，而且它自己也声明是「best-effort debugging tool, not a guarantee」（`src/hs_common.h:552-553`）——不能把它当成线程安全护栏。

5.4.x 内部的变化集中在 scratch 校验：5.4.1 为 issue #350 增加了 scratch 的快速有效性检查，5.4.2 又把该修复回退，理由是「除了用对应数据库的 scratch，也允许使用为另一个数据库分配的更大 scratch」，并明确「超出这一点的行为不被鼓励且结果未定义」（`CHANGELOG.md` 前两条）。对使用者的含义是：5.4.2 上「大 scratch 服务小库」重新变为允许，但不要依赖它——按 04-06 的 `hs_alloc_scratch` 反复扩容用法才是被支持的路径。5.4.1 还修了流关闭阶段的内存泄漏（issue #303 条目「avoid memory leak in stream close stage」），在 5.4.0 及更早版本上大量开关流可能观察到 RSS 缓慢增长。

### 7. 常见误用与调试

运行时 API 的问题分两类：一类立刻有返回码，另一类只在结果上体现。下表按现象给出判据与处置。

| 现象 | 可能原因 | 验证方式 | 修复 |
|---|---|---|---|
| 返回 -7 | 数据库与 API 不匹配 | 核对编译时的 mode | block 库不能开流 |
| 返回 -10 | scratch 被并发复用 | 查是否在回调里重入 | 每线程一份 scratch |
| 返回 -3 且只扫了一半 | 回调返回了非零 | 打印回调返回值 | 确认业务是否真要终止 |
| 跨块匹配丢失 | 每块都新建了流 | 数 `hs_open_stream` 调用次数 | 一条流扫到底 |
| `$` 模式从不命中 | 没调 `hs_close_stream` | 查关闭路径是否被执行 | 在 finally 里关闭 |
| 关闭后内存仍涨 | 终止路径跳过了 close | 统计 open 与 close 次数 | 终止也要 close |
| `from` 恒为 0 | 未开 SOM 标志 | 查编译期 flags | 加 `SOM_LEFTMOST` 与 horizon |
| `from` 为极大值 | 超出 horizon | 与哨兵常量比较 | 换 LARGE 或降级处理 |
| `hs_scan_vector` 结果错乱 | 块顺序或 count 给错 | 打印每块长度 | 按流顺序给块 |
| 压缩后还原结果异常 | 用了不同数据库 | 比对 `hs_database_info` | 压缩与还原同库 |

第一条要展开：**「终止」不等于「结束」**。回调返回非零后，`hs_scan` 立刻返回 -3，剩余的缓冲区不再扫；流式模式下这个终止标记会粘住，后续 `hs_scan_stream` 直接返回 -3 而一个字节都不扫。很多实现把它当成「这一块结束」而继续喂下一块，于是表现为「命中一条之后再也没有命中」。正确做法是：要么在终止后主动 `hs_reset_stream` 重新开始，要么把终止当作业务上的「已确认，停止分析」，直接走关闭路径。

第二条要展开：**流的生命周期必须闭合成对**。头文件对 `hs_close_stream` 的要求是「任何由 `hs_open_stream` 创建的流都必须调用它，即使扫描已被回调终止」（`hs_runtime.h:202-204`）。工程上最稳的写法是把流句柄包进一个 RAII 或 `goto cleanup` 结构，让所有返回路径都经过同一个出口。遗忘关闭的直接后果是流状态内存泄漏，间接后果更麻烦：某些实现会在关闭时补齐 EOD，漏掉关闭就漏掉尾部匹配，表现为「规则明明写了 `$` 却从不命中」。

第三条要展开：**`hs_scan` 的 `length` 是 32 位**。处理大文件时若按 `size_t` 计算偏移再截断成 `unsigned int`，超过 4 GiB 的部分会静默回绕，表现为「文件后半段完全不命中」。正确做法是分块调用并把 `to` 偏移与块基址相加，或者改用 stream 模式。同理，`hs_scan_stream` 的 `length` 也是 32 位，单块不要超过 4 GiB。

第四条要展开：**回调里的偏移是「全局偏移」而不是「块内偏移」**。stream 模式下 `hs_scan_stream` 的 `data` 是当前块，但回调里的 `to` 是相对整条流起点的累计偏移，block 模式下才是相对本次缓冲区。把两者混用会在多块场景下算出错误的切片位置，而且错得不明显——前几块看起来正常，越往后偏得越多。调试时建议在回调里同时打印块基址与 `to`，一眼就能看出来。

调试顺序建议固定为：先看返回码（-7 与 -10 是配置问题，-3 是业务主动终止，-2 是内存不足），再看回调参数（`id` 是否是你期待的那条、`from` 是否为 0 或哨兵），最后才怀疑引擎行为。错误码的完整触发表与「现象 → 原因 → 验证 → 修复」的排错流程见 04-08；scratch 的分配与扩容见 04-06；流状态压缩的算法与状态布局见 06-11 与 05-09；运行时如何按平台分派到具体实现见 06-13。

### 1. 本篇定位与覆盖范围

本篇**不**覆盖：扫描函数（04-05）、编译函数（04-04）、错误码全表（04-08）。也不展开 `hs_scratch` 与 `hs_database` 的**字段级布局**——`magic`、`in_use`、`queueCount`、`bstate`、`som_store` 这些成员的含义、偏移与读写时机属于 05-02 与 05-03；序列化的字节格式与 HMAC 校验顺序属于 06-12。本篇只讲「谁分配、谁释放、什么时候会失败、失败了怎么办」。

这一族 API 的共同点是**所有权转移规则比功能更重要**。Hyperscan 没有垃圾回收，四类对象（数据库、scratch、流、返回的字符串）各有各的释放函数，错误配对不会编译报错，只会在运行期崩溃或泄漏。读本篇时请始终带着一个问题：这个指针是我分配的，还是库分配的？该由谁来释放？

有一条贯穿全篇的边界必须先明确：**scratch 不是线程安全的**。头文件对 `hs_alloc_scratch` 的注释是「one scratch space per thread, or concurrent caller, is required」（`hs_runtime.h:530-533`）。库用一个 `in_use` 标记做尽力检测，检测到就返回 `HS_SCRATCH_IN_USE`（`src/scratch.c:370`、`542`），但 `hs_common.h:552-553` 明确说这是「best-effort debugging tool, not a guarantee」。换句话说：拿到 -10 说明你确实共享了；没拿到 -10 不代表你没共享。

### 3. 逐项详解

**`hs_alloc_scratch`。** 签名 `hs_error_t hs_alloc_scratch(const hs_database_t *db, hs_scratch_t **scratch)`。它的语义不是「分配一块新 scratch」，而是「保证这块 scratch 能服务这个数据库」：第一次传 `*scratch == NULL` 时新建；已有 scratch 时检查容量，不够就重新分配并把旧块释放、把新块写回同一个指针（`hs_runtime.h:540-548`）。因此「让一份 scratch 服务多个数据库」的正确写法是对每个数据库依次调用它，而不是取最大值手动分配。错误条件有四类：`db` 或 `scratch` 为 NULL 返回 `HS_INVALID`（`src/scratch.c:346-348`）；已存在的 scratch 指针未按 64 字节对齐或 `magic` 不匹配返回 `HS_INVALID`（`src/scratch.c:359-366`）；该 scratch 正被占用返回 `HS_SCRATCH_IN_USE`（`src/scratch.c:370-372`）；分配器返回的地址不满足对齐要求返回 `HS_BAD_ALLOC`（`src/allocator.h:61`）。注意最后一条：自定义分配器必须返回适合「本平台最大可表示类型」对齐的内存，否则会在这里被拒。

**`hs_clone_scratch`。** 签名 `hs_error_t hs_clone_scratch(const hs_scratch_t *src, hs_scratch_t **dest)`。复制一份容量与配置等价的 scratch，供另一个线程使用。它是多线程部署里唯一正确的「复制」方式——`memcpy` 一份 `hs_scratch_t` 会把内部的队列指针、`aqa` 指针一起复制成指向原块的地址，运行期立刻崩。克隆出的新块与原块完全独立，可以并行使用；源块本身的 `in_use` 状态不会被复制（克隆要求源块当前未被占用，否则返回 `HS_SCRATCH_IN_USE`）。成本是一次等量内存分配加拷贝，因此适合「线程启动时克隆一次、之后长期持有」，不适合每次扫描都克隆。

**`hs_scratch_size`。** 签名 `hs_error_t hs_scratch_size(const hs_scratch_t *scratch, size_t *scratch_size)`。返回这块 scratch 实际占用的字节数，用于容量核算与监控。它给出的是**单块**大小，乘以并发线程数才是进程的 scratch 总开销。实践中有个常见误判：以为 scratch 大小只与「模式条数」有关，实际上它与引擎组合、队列数量、SOM 开关都相关，同一批模式在开了 SOM 之后 scratch 会明显变大。想知道「换一个 horizon 能省多少」，就在两种配置下各调一次这个函数，差值即答案。

**`hs_free_scratch`。** 签名 `hs_error_t hs_free_scratch(hs_scratch_t *scratch)`。释放 scratch，`NULL` 安全（`hs_runtime.h:604-605`）。它使用的是 `hs_set_scratch_allocator` 或 `hs_set_allocator` 设置的 free 回调。最典型的崩溃是「用 free() 释放 scratch」：scratch 内部是单块大分配加内部指针重定位，必须走库的释放路径，否则会破坏堆。另一种是「释放后继续扫描」——scratch 释放后指针值不变，`hs_scan` 会因 `magic` 不匹配返回 `HS_INVALID` 而不是崩溃，这种情况反而容易排查。

**`hs_free_database`。** 签名 `hs_error_t hs_free_database(hs_database_t *db)`，`NULL` 安全。它释放编译或反序列化产出的数据库，使用 database 分配器的 free 回调。有一条关键例外：用 `hs_deserialize_database_at` 在**调用方提供的内存**上还原的数据库，**不能**用它释放（`hs_common.h:162-164` 明确写「the `hs_free_database()` call should not be used」），因为那块内存的所有权从未转移给库。混用会导致对非堆指针调用 free，属于必崩的操作。

**`hs_serialize_database`。** 签名 `hs_error_t hs_serialize_database(const hs_database_t *db, char **bytes, size_t *length)`。把数据库序列化成一段可重定位的字节流，写入库分配的缓冲区，由调用方负责释放（使用 misc 分配器对应的 free，未设置时就是 `free()`）。序列化是**逐字节完整拷贝**，包含头部、字节码与两个 HMAC 字段，因此产物体积略大于 `hs_database_size()`。失败返回 `HS_NOMEM`（-2）表示缓冲区分配失败。它的典型用途是「编译一次、分发多次」：把编译产物落盘或打进镜像，各节点启动时反序列化，跳过几分钟量级的编译时间。

**`hs_deserialize_database`。** 签名 `hs_error_t hs_deserialize_database(const char *bytes, const size_t length, hs_database_t **db)`。它按顺序校验：magic 是否为 `HS_DB_MAGIC`（不符返回 `HS_INVALID`）、version 是否等于 `HS_DB_VERSION`（不符返回 `HS_DB_VERSION_ERROR`，-5）、`length` 字段与实际长度是否自洽（不符 `HS_INVALID`）、platform 是否与当前 CPU 兼容（不符 `HS_DB_PLATFORM_ERROR`，-6），最后校验字节码的 HMAC（不符 `HS_INVALID`）（`src/database.c:194-267`）。校验顺序有讲究：先版本后平台再 HMAC，所以一个「版本对但机器不对」的库会得到 -6 而不是 -1，据此可以区分「拿错了库」与「库被改坏了」。`bytes` 不需要 4 字节对齐，实现用的是非对齐加载（`src/database.c:214-215`）。

**`hs_deserialize_database_at`。** 签名 `hs_error_t hs_deserialize_database_at(const char *bytes, const size_t length, hs_database_t *db)`。把数据库直接还原到调用方给定的内存地址，实现零拷贝式的共享内存部署：多个进程 mmap 同一块区域，各自调一次这个函数，物理内存只有一份。三条约束：目标地址必须 **8 字节对齐**，否则返回 `HS_BAD_ALIGN`（-8，检查点 `src/database.c:2944`）；容量必须不小于 `hs_serialized_database_size()` 的结果；释放由调用方自己做，**不要**调 `hs_free_database`。它的返回值里不会出现 `HS_NOMEM`，因为库不分配内存——这也是它在受限环境里的价值。

**`hs_stream_size`。** 签名 `hs_error_t hs_stream_size(const hs_database_t *database, size_t *stream_size)`。返回「一条流」的状态字节数，只对 stream 模式数据库有意义。它是并发容量的直接乘数：一万条流乘以单流大小就是常驻内存。该值随模式、SOM 开关、horizon 精度、有界重复的规模变化，因此「换 horizon 省内存」这类决策应当以它为量化依据，而不是凭感觉。对 block 模式数据库调用它，返回值需对照实际版本核验（可能为 0 或一个极小值），不要拿它做校验。

**`hs_database_size`。** 签名 `hs_error_t hs_database_size(const hs_database_t *database, size_t *database_size)`。返回数据库本体的字节数（不含序列化头部之外的对齐填充）。它与 `hs_serialized_database_size` 的差值是序列化开销，通常只有几百字节。用途有三：容量核算、多库场景下的「谁把内存吃掉了」排查、以及作为 `hs_database_info` 的补充证据。

**`hs_serialized_database_size`。** 签名 `hs_error_t hs_serialized_database_size(const char *bytes, const size_t length, size_t *deserialized_size)`。给定一段序列化字节，返回「反序列化需要多大空间」。它是 `hs_deserialize_database_at` 的前置步骤：先算大小、再分配对齐内存、最后还原。注意它的入参是字节流而不是数据库，因此可以在**还没有数据库对象**的时候使用——这正是共享内存部署的关键：引导进程只需读文件头就能算出要 mmap 多大。

**`hs_database_info`。** 签名 `hs_error_t hs_database_info(const hs_database_t *database, char **info)`。返回一段人类可读的摘要，包含版本、平台、模式与 `Database HMAC`。字符串由 misc 分配器分配，调用方负责释放（`hs_common.h:242-244`）。它的价值在排障：两台机器上一个库能加载一个不能，把两边的 info 打出来逐字段比对，版本与平台差异立刻可见；HMAC 一行还能用来确认「分发过程中文件有没有被改动」。`hsbench` 的输出里 `Hyperscan info:` 与 `Database HMAC:` 两行就分别来自它和内部统计（`tools/hsbench/engine_hyperscan.cpp:252`、`261`）。

**`hs_serialized_database_info`。** 签名 `hs_error_t hs_serialized_database_info(const char *bytes, size_t length, char **info)`。与上者相同，但输入是字节流。这在分发链路上非常实用：接收端在真正加载之前就能读出「这个文件是给哪个版本、哪个平台编的」，从而在不消耗大块内存的前提下拒绝不兼容的库。

**`hs_version`。** 签名 `const char *hs_version(void)`。返回静态分配的版本字符串，含版本号与构建日期，**不需要释放**（`hs_common.h:446-448`）。它是运行期确认「链接到的到底是哪个库」的最快手段，尤其在动态库搜索路径混乱、同时装了多个版本的环境里，比看 `ldd` 更直接。

**`hs_valid_platform`。** 签名 `hs_error_t hs_valid_platform(void)`。检测当前 CPU 是否满足库的最低要求（SSSE3），不满足返回 `HS_ARCH_ERROR`（-11）。它**不**检测更高级指令集：如果库是按 AVX2 编的而机器只有 SSE4.2，这个函数仍可能返回成功，真正的失败会发生在首次扫描或数据库加载时。因此它适合做「启动自检的第一道闸」，不能替代平台字段校验。

**分配器家族。** 五个函数的签名完全一致：`hs_error_t hs_set_xxx_allocator(hs_alloc_t alloc_func, hs_free_t free_func)`，回调类型是 `void *(HS_CDECL *hs_alloc_t)(size_t)` 与 `void (HS_CDECL *hs_free_t)(void *)`（`hs_common.h:288`、`297`）。三条规则必须记住。其一，`hs_set_allocator` 等价于把后四个一次性设成同一对（`hs_common.h:304-306`），后设的会覆盖先设的。其二，传两个 NULL 表示恢复默认（`hs_common.h:334-336`），但只能成对传，传一个 NULL 一个非 NULL 的行为需对照实际版本核验。其三，**编译期的临时对象无法定制**：头文件两次写明「there is no way to change the allocator used for temporary objects created during the various compile calls」（`hs_common.h:310-312`、`343-345`）。这意味着即使设了内存池，编译阶段的峰值内存仍然走系统分配器，容量规划时不能按池的大小估算。对象字段的逐项含义、序列化的校验顺序、运行时模块的文件归属，分别见 05-02 与 05-03、06-12、07-10（字段见 05-02 与 05-03 ｜ 原理见 06-12 ｜ 模块见 07-10）。

### 4. 典型示例

下面这段程序演示「编译 → 序列化 → 释放 → 用字节流算大小 → 反序列化到对齐内存 → 打印信息」的完整闭环。它刻意跳过 `hs_deserialize_database`，直接走 `_at` 路径，以便把零拷贝部署的每一步都摊开。

```c
#include <hs.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    const char *exprs[2] = { "GET /", "POST /" };
    unsigned ids[2] = { 10, 11 };
    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;

    if (hs_compile_multi(exprs, NULL, ids, 2, HS_MODE_BLOCK,
                         NULL, &db, &err) != HS_SUCCESS) {
        printf("compile failed: %s\n", err ? err->message : "-");
        hs_free_compile_error(err);
        return 1;
    }

    char *bytes = NULL;
    size_t len = 0;
    hs_serialize_database(db, &bytes, &len);
    size_t db_size = 0;
    hs_database_size(db, &db_size);
    printf("library: %s\n", hs_version());
    printf("database=%zu bytes, serialized=%zu bytes\n", db_size, len);

    char *info = NULL;
    hs_serialized_database_info(bytes, len, &info);
    printf("serialized info: %s\n", info ? info : "-");
    free(info);

    hs_free_database(db);

    size_t need = 0;
    hs_error_t rc = hs_serialized_database_size(bytes, len, &need);
    printf("deserialize need rc=%d size=%zu\n", rc, need);

    void *region = NULL;
    if (posix_memalign(&region, 64, need) != 0) {
        printf("aligned alloc failed\n");
        free(bytes);
        return 1;
    }
    memset(region, 0, need);

    rc = hs_deserialize_database_at(bytes, len, (hs_database_t *)region);
    printf("deserialize_at rc=%d\n", rc);

    if (rc == HS_SUCCESS) {
        char *info2 = NULL;
        hs_database_info((hs_database_t *)region, &info2);
        printf("loaded info: %s\n", info2 ? info2 : "-");
        free(info2);

        hs_scratch_t *scratch = NULL;
        hs_alloc_scratch((hs_database_t *)region, &scratch);
        size_t ssz = 0;
        hs_scratch_size(scratch, &ssz);
        printf("scratch=%zu bytes\n", ssz);
        hs_free_scratch(scratch);
    }

    free(region);
    free(bytes);
    return 0;
}
```

编译与运行命令如下。

```bash
gcc -O2 -o serialize_demo serialize_demo.c -lhs
./serialize_demo
```

示例输出，具体格式需对照实际版本核验。

```text
library: 5.4.2 2026-11-12
database=2048 bytes, serialized=2400 bytes
serialized info: Version: 5.4.2 Features: AVX2 Mode: BLOCK
deserialize need rc=0 size=2048
deserialize_at rc=0
loaded info: Version: 5.4.2 Features: AVX2 Mode: BLOCK
scratch=16384 bytes
```

逐行判读这份输出，重点是三组数字与一个对齐约定。第一行 `library: 5.4.2 2026-11-12` 来自 `hs_version()`，后半段是构建日期而不是发布日期，两台机器上可能不同——用它确认「是不是同一个构建」，不要用它判断兼容性。第二行给出两个体积：`database=2048` 是 `hs_database_size()` 的结果，`serialized=2400` 是序列化后的长度，差值 352 字节就是头部与对齐填充；做分发预算时按**序列化后**的体积算，不要按 `hs_database_size` 算，否则小库会低估几个百分点。第三行 `serialized info: ...` 证明 `hs_serialized_database_info` 能在不加载的前提下读出头部，`Mode: BLOCK` 尤其重要：如果收到的是 `Mode: STREAM` 而业务用的是 `hs_scan`，后面一定返回 -7，这里就能提前拦住。第四行 `deserialize need rc=0 size=2048` 说明 `hs_serialized_database_size` 给出的 2048 与第二行的 `database` 一致，两个函数互相印证，不一致就说明字节流被截断。第五行 `deserialize_at rc=0` 是成功标志；如果这里是 -8，说明 `posix_memalign` 的对齐参数不够（本例用 64 字节，远大于要求的 8 字节，所以安全），如果是 -1，通常是 `need` 算小了或 `region` 被清零破坏了内部偏移。最后一行 `scratch=16384 bytes` 是 `hs_scratch_size` 的结果，它比数据库本身大一个数量级——这正是「scratch 开销常被低估」的典型证据：两条模式的库只占 2 KB，但每线程的 scratch 要 16 KB，一百个线程就是 1.6 MB。

按任务反查函数，速查表如下。

### 6. 版本差异

这一族 API 的签名自 4.x 后期起基本冻结，5.4.2 没有改动任何原型。行为层面的变化集中在三处，且都与「scratch 能不能跨库复用」有关，值得单独记住。

5.4.1 为 issue #350 增加了 scratch 的快速有效性检查，目的是阻止「用 A 库的 scratch 去扫 B 库」这种危险用法；5.4.2 随即回退了这项修复，理由是 Hyperscan 一直允许「用为另一个数据库分配的更大 scratch」，而且用户正是靠这个性质在多库场景下安全地复用 scratch，超出这一点的行为才是不被鼓励且未定义的（`CHANGELOG.md` 的 5.4.2 与 5.4.1 条目）。对使用者的实践含义是：**在 5.4.2 上，多库共用一份「足够大」的 scratch 是允许的；但不要依赖它作为设计基础**，因为 5.4.1 曾经禁止过，未来也可能再变。稳定做法仍是按 04-06 开头描述的「对每个库依次调用 `hs_alloc_scratch`」。

5.4.1 还修了流关闭阶段的内存泄漏（issue #303 的「avoid memory leak in stream close stage」），以及对齐分配器的段错误（issue #317 的「fix aligned allocator segment faults」）。后者与 `hs_set_scratch_allocator` 直接相关：如果你的自定义分配器返回 16 字节对齐而库要求 64 字节，旧版本可能直接段错误而不是返回 `HS_BAD_ALLOC`。做自定义内存池的团队应把最低版本定在 5.4.1 以上。

更早的节点包括：4.6.0 引入流状态压缩，间接让 `hs_stream_size` 的数值成为「压缩前」的基准；4.2.0 引入 `HS_SCRATCH_IN_USE`，使 scratch 冲突从「静默算错」变成「可检测的返回码」；4.0.1 起 `hs_reset_stream` 与 `hs_reset_and_copy_stream` 允许 NULL scratch。`hs_deserialize_database_at` 与 `hs_serialized_database_size` 的引入时间早于本快照覆盖的范围，需对照实际版本的 `CHANGELOG.md` 核验。

还有一条与安全相关的稳定性说明：数据库的 HMAC 校验在 `src/database.c:255-267`，用 `HS_DB_HMAC_KEY`（`src/hs_db_hmac_key.h`，32 字节，构建期可用 `-DHS_DB_HMAC_KEY_OVERRIDE` 替换）对字节码做 HMAC-SHA256，再与头部的 `hmac` 字段做常量时间比较。校验失败返回 `HS_INVALID`，而不是某个专用错误码——这是设计上的取舍，因为「HMAC 不对」与「字节流不是数据库」在攻击者视角下不应可区分。完整的校验顺序与威胁模型见 06-12 与 08-05。

### 7. 常见误用与调试

这一族的问题几乎都能归到「所有权搞错」与「对齐/容量不够」两类。下表按现象给出判据。

| 现象 | 可能原因 | 验证方式 | 修复 |
|---|---|---|---|
| 释放时崩溃 | 对 `_at` 库调了 `hs_free_database` | 查该指针来源 | 由调用方 `free` |
| 扫描返回 -1 | scratch 已释放或 magic 损坏 | 打印 scratch 指针与生命周期 | 检查释放顺序 |
| 扫描返回 -10 | scratch 被并发复用 | 查回调内是否重入 | 每线程一份 |
| 反序列化返回 -5 | 库与运行库版本不同 | 比对两端 `hs_version()` | 用同版本重编 |
| 反序列化返回 -6 | 平台不兼容 | 比对 `hs_database_info` 的 Features | 编通用库或换机器 |
| 反序列化返回 -8 | 目标内存未 8 字节对齐 | 打印指针低三位 | 用对齐分配 |
| 反序列化返回 -1 | HMAC 不符或长度截断 | 比对文件大小与 HMAC | 重新分发 |
| 自定义分配器不生效 | 设了错误的类别 | 查设的是哪个 setter | 用 `hs_set_allocator` |
| 编译期内存不受控 | 临时对象不可定制 | 读头文件注释 | 用系统分配器容量规划 |
| scratch 越用越大 | 忘了复用，每次新建 | 统计 alloc 次数 | 线程内长期持有 |

第一条要展开：**两类数据库的释放路径不能混**。编译产出的库归库所有，用 `hs_free_database`；`hs_deserialize_database_at` 还原的库归调用方所有，用与分配方式配对的释放（`free`、`munmap`、内存池归还）。混用的后果不是「泄漏」而是「对非堆指针调用 free」，在 glibc 上通常表现为 `free(): invalid pointer` 直接 abort。判断一个 `hs_database_t *` 属于哪一类，最可靠的办法是在封装层用两个不同的类型或两个不同的构造函数，而不是靠注释。

第二条要展开：**对齐不是「差不多就行」**。`hs_deserialize_database_at` 要求 8 字节对齐（`hs_common.h:160-161`），而库内部的扫描路径可能对性能敏感的结构有更高要求。实践中建议直接按 64 字节对齐分配：既满足最低要求，也避免某些微架构上非对齐访问的性能损失。用 `malloc` 拿到天然 16 字节对齐的指针时通常能过 8 字节检查，但把它加上一个偏移量做「打包多库」就会破坏对齐，这类错误往往只在特定库上出现。

第三条要展开：**分配器的对齐契约同样适用于 scratch**。`hs_alloc_t` 的注释要求返回「suitably aligned for the largest representable data type on this platform」（`hs_common.h:314-317`），实现里通过 `hs_check_alloc` 校验，不满足返回 `HS_BAD_ALLOC`（-9，`src/allocator.h:61`）。自研内存池常见的问题是「按 8 字节对齐切块」，在需要 16 或 64 字节对齐的结构上就会触发这个错误；表现出来是 `hs_alloc_scratch` 返回 -9 而不是崩溃，比段错误好排查，但也容易被误读成「内存不足」。

第四条要展开：**序列化不是加密，也不是签名**。HMAC 用的是编译进库的固定密钥，任何人都能从一个公开构建里取出它并伪造一个「校验通过」的数据库。它的作用是**检测传输损坏与版本错配**，不是防篡改。真正需要防篡改的场景应在应用层加自己的签名（例如用私钥签序列化字节），并在反序列化之前验证。信任模型的完整讨论见 08-05。

调试顺序建议固定为：先确认对象来源（编译还是 `_at`），再确认版本与平台（两个 info 函数），再确认容量与对齐（`hs_serialized_database_size` 与指针值），最后才怀疑字节流内容（HMAC）。错误码的完整触发表见 04-08；`hs_scratch` 与 `hs_database` 的字段级细节见 05-03 与 05-02；序列化的字节布局与校验顺序见 06-12；多线程 scratch 池化的部署方案见 03-04 与 08-02。

## 04-07 工具命令行全集：hscheck / hsbench / hscollider / hsdump

### 1. 本篇定位与覆盖范围

本篇是**四个官方工具命令行参数**的唯一权威源，覆盖 `tools/hscheck/main.cpp`、`tools/hsbench/main.cpp`、`tools/hscollider/args.cpp`、`tools/hsdump/main.cpp` 中的全部选项、默认值、互斥约束与输出字段。四个工具解决四个不同阶段的问题：**能不能编**（`hscheck`）、**编出来多快**（`hsbench`）、**编出来对不对**（`hscollider`）、**编出来长什么样**（`hsdump`）。它们不是产品组件，而是开发期与调优期的诊断仪器——生产环境不需要部署任何一个。

本篇**不**覆盖：工具的构建开关（`BUILD_EXAMPLES`、`DUMP_SUPPORT`、`HS_HYBRID` 见 04-01）、基准方法学与结果解读的完整流程（08-01）、正确性对拍背后的 NFA 与 PCRE 语义差异（06-14）。也不展开工具内部实现：`hsbench` 的线程屏障与语料切分、`hscollider` 的语料生成器、`hsdump` 的字节码打印格式，分别属于 07-12 与 06-05 的范围。本篇只回答「参数怎么给、默认是什么、互相能不能一起用、输出怎么读」。

先记住三条通用约定，它们适用于全部四个工具。

第一，**输入是「表达式目录 + 签名文件」这一对**。表达式目录里放的是以数字 ID 命名的文件，每个文件内容是正则本身；签名文件是一个纯文本清单，每行一个 ID（`#` 开头表示注释，但注释行里的 ID 仍会被载入，`tools/hscheck/main.cpp:615-660`）。`hscheck` 的文件头注释给出了最简用法：建一个文件写 `1:/foo.*bar/s`、`2:/hatstand|teakettle|badgerbrush/`，然后 `bin/hscheck -e regex`（`tools/hscheck/main.cpp:33-44`）——也就是说 `-e` 既可以指目录，也可以直接指一个「`ID:/正则/修饰符`」格式的文件。四个工具都用 `inferExpressionPath()` 从签名文件反推目录，因此只给 `-s` 通常也能跑。

第二，**`-e` 与 `-c`（或 `-s`）在 `hsbench` 里都是硬性必填**。缺任意一个都会打印 usage 并退出，错误消息分别是「Must specify an expression path with the -e option.」与「Must specify a corpus file with the -c option.」（`tools/hsbench/main.cpp:436-446`）。这与很多基准工具「有默认值」的习惯不同，第一次用很容易在这里卡住。

第三，**`-G`（grey box 覆盖）在 release 构建中不可用**。`hsbench` 的 `case 'G'` 整段被 `#ifndef RELEASE_BUILD` 包住（`tools/hsbench/main.cpp:316-320`），`hscheck` 与 `hsdump` 同理。传 `-G` 到 release 版二进制上，getopt 会正常识别该选项，但 switch 里没有分支，直接落到 default 报「Unrecognised command line argument.」。这类「选项存在但被编译掉」的情况是四个工具共有的陷阱。

### 3. 逐项详解

**`hscheck` 的定位。** 它只做一件事：把规则逐条送进编译器，报告每条能不能编、编不过的原因是什么。默认 streaming 模式，`-N` 切 block，`-V` 切 vectored；`-L` 给所有模式加 `HS_FLAG_SOM_LEFTMOST`，`-8` 加 `HS_FLAG_UTF8`，`-E` 注入编辑距离。`-B` 是「构建签名集」模式：它把能编译成功的 ID 重新输出成一份签名文件，失败的行原样保留为注释，因此可以作为「规则净化」工具使用（`tools/hscheck/main.cpp:615-660` 的注释说明注释行里的 ID 仍会被载入，所以净化后的文件可以直接再喂给 `hsbench`）。`-T` 只是并行校验的线程数，不影响结果。`-C` 打开逻辑组合检查，与 5.0.0 的 `HS_FLAG_COMBINATION` 配套。`--literal-on` 走纯字面量 API，此时正则元字符不再有特殊含义，用它校验「我这条规则是不是被当成纯字面量编的」很有效。

**`hsbench` 的语料与线程参数。** `-c` 指定 SQLite 语料库，必填；`-n` 是重复次数，默认 20，必须大于 0，给 0 会报「Couldn't parse argument to '-n' flag」。`-T` 接受两种写法：逗号列表 `3,5,7` 或闭区间 `2-5`，解析失败会报「a list of positive integers or 2 integers connected with hyphen」。它同时决定线程数与绑核位置——给了三个核就起三个线程并分别绑定，这是获得稳定数字的关键；不绑核时调度迁移会让 `Max throughput (per core)` 明显低于理论值。`-N`、`-V` 与默认的 streaming 三者只能选一个，后出现的覆盖先出现的。`-d` 只在开了 SOM 的模式上有意义，取值必须是 2、4、8，分别映射到 SMALL、MEDIUM、LARGE（`tools/hsbench/main.cpp:289-302`），给其它值直接报「SOM precision must be 2, 4 or 8」。

**`hsbench` 的库复用参数。** `-w` 在编译后把数据库按「模式 + 设置哈希」命名存盘，`-i` 则跳过编译直接加载。二者互斥。这个机制的意义在于把「编译时间」从基准里剔除：首次用 `-w` 跑一遍，之后所有对照实验都用 `-i`，测出来的就纯粹是扫描性能。需要注意 `-i` 加载的库绑定了当时的规则集与标志，改规则后必须重新 `-w`，否则测的是旧库。`-H` 与 `-P` 分别用 Chimera 与 PCRE 跑同一批规则，用于横向对比；两者不能同时给，且都强制要求 block 模式与「无扩展选项」，否则报「Must specify block mode in Chimera or PCRE with the -N option.」或「No extended options are supported in Chimera or PCRE.」（`tools/hsbench/main.cpp:454-470`）。

**`hsbench` 的输出控制。** `-C` 把结果压成一行 CSV，字段顺序是「扫描耗时、吞吐、命中数、命中率、块速率」，不带头部，适合被脚本追加到汇总表。`--per-scan` 逐次打印每轮的 Mbit/sec，用于观察抖动；它会把输出量放大 `-n` 倍，大语料上不要开。`--echo-matches` 打印每次命中的 `id` 与偏移，用于确认「规则确实命中了预期位置」，代价是回调开销会污染吞吐数字。`--sql-out` 把编译统计与扫描统计写进 SQLite，配合 `-S` 指定签名集名字，适合做长期趋势库。`--literal-on` 让编译走 `hs_compile_lit_multi`，用于评估「把这批规则退化成字面量能快多少」。

**`hscollider` 的工作方式。** 它不是「跑一遍看有没有崩」，而是「对同一批模式，用 Hyperscan 与 PCRE 各算一遍匹配集合，逐条比对」。因此它需要 PCRE 支持，且对语料极其敏感：默认由内置生成器造语料，`-n` 控制每个签名生成多少条（默认值见 usage 的 `DEFAULT_CORPUS_GENERATOR_LIMIT`），`-C` `-P` `-S` `-D` `-b` 分别控制环次数、前后缀长度、编辑距离与字母表大小。`-c` 可以直接给现成语料，`-w` 把带匹配标注的语料存下来供复现。`-t N` 与 `-V N` 把数据切成 N 块分别走流式与 vectored，这是暴露「块边界处理错误」的主要手段。`--compress-expand` 与 `--compress-reset-expand` 在每轮扫描后把流状态压缩再还原，`--copy-stream` 复制状态，`--mangle-scratch` 故意搅乱 scratch——这四个开关专治「状态没清干净」类 bug。`-q` 只报差异，`-v` 连成功也报，`-k` 限制每个模式的命中数以免输出爆炸。

**`hsdump` 的产物。** 它把编译过程的中间数据与最终产物写到一个目录，默认 `dump`。`-D` 额外产出 `db.raw`（最终数据库字节），`-P` 把签名集回显到 stdout，`-X` 跳过中间产物只留四个汇总文件。`-o` 指定的目录若已存在同名文件会被覆盖，usage 里对此有明确警告。`-x` 用于交叉编译到别的架构，配合 `-N`/`-V`/`-d` 可以观察「同一规则在不同平台上被分到哪些引擎」。它的输出是给人读的，不是稳定接口，跨版本比对时需要重新生成而不是拿旧文件对照。

**四个工具的退出码约定。** 成功为 0；参数错误、输入无法打开、编译失败一般返回 1；`hscollider` 发现不一致时也返回非零，因此可以直接串进 CI 的 `&&` 链。`hsbench` 在扫描期遇到致命错误（例如 `hs_open_stream` 失败）会打印「Fatal error: stream open failed!」并 `abort()`（`tools/hsbench/main.cpp:595`），这类退出不是返回码而是信号，脚本里要按崩溃处理。工具读到的 scratch 结构、字面量引擎的分组结果、工具模块自身的文件清单，分别见 05-03、06-05 与 07-12（字段见 05-03 ｜ 原理见 06-05 ｜ 模块见 07-12）。

### 4. 典型示例

先看 `hsbench` 的一次典型基准。规则集放在 `/data/rules`，签名清单是 `/data/sigs/http.txt`，语料库是 `http.db`；用 block 模式、50 次重复、绑三个核。

```bash
hsbench -e /data/rules -s /data/sigs/http.txt -c /data/corpus/http.db \
        -n 50 -N -T 2-4
```

示例输出，具体格式需对照实际版本核验。

```text
Signature set:        /data/sigs/http.txt
Signatures:           1240
Hyperscan info:       Version: 5.4.2 Features: AVX2 Mode: BLOCK
Expression count:     1240
Bytecode size:        3,145,728 bytes
Database HMAC:        5c1e9b7a4d02f83e
Scratch size:         1,048,576 bytes
Compile time:         12.480 seconds
Peak heap usage:      412,336,128 bytes
Time spent scanning:  1.842 seconds
Corpus size:          268,435,456 bytes (512 blocks)
Matches per iteration: 18,442 (0.070 matches/kilobyte)
Overall block rate:   13,894.68 blocks/sec
Mean throughput (overall): 11,658.42 Mbit/sec
Max throughput (per core): 4,120.77 Mbit/sec
```

逐行判读这份输出，重点在「编译段」与「扫描段」的分界，以及三个派生量的关系。前九行来自 `printStats()`（`tools/hsbench/engine_hyperscan.cpp:246-279`），是**编译期**的事实：`Signatures: 1240` 与 `Expression count: 1240` 相等说明签名文件里没有重复 ID，若前者大于后者说明同一 ID 被列了多次，基准会重复计权；`Hyperscan info: ... Mode: BLOCK` 是数据库自述，它与命令行的 `-N` 必须一致，不一致说明加载了别的模式编出的库（配合 `-i` 时尤其容易发生）；`Bytecode size: 3,145,728 bytes` 是 3 MB，按 1240 条算平均每条 2.5 KB，这个数字对容量规划比「模式条数」有用得多；`Scratch size: 1,048,576 bytes` 是 1 MB，乘以线程数就是每个并发流量的固定开销；`Compile time: 12.480 seconds` 说明编译成本远高于扫描成本，这正是「编译一次、序列化分发」的经济动机；`Peak heap usage` 是编译峰值，通常比字节码大两个数量级，容器内存限额要按它设而不是按字节码设。后六行来自 `displayResults()`（`tools/hsbench/main.cpp:789-855`），是**扫描期**的事实：`Corpus size ... (512 blocks)` 说明语料被切成 512 块，block 模式下每块一次 `hs_scan`；`Matches per iteration: 18,442` 是单轮命中数，与 `-n` 无关，若它随 `-n` 变化说明统计口径错了；`Mean throughput 11,658.42 Mbit/sec` 是「总字节 × 重复次数 × 线程数 ÷ 总耗时」，而 `Max throughput (per core) 4,120.77` 是「最快那一轮的字节数 ÷ 该轮耗时」，后者恒大于前者，两者差距越大说明线程间负载越不均或绑核没生效。做 A/B 对照时只比 `Mean throughput` 与 `Max throughput` 这两个数，不要比 `Time spent scanning`，因为后者随 `-n` 线性变化。

再看 `hscheck` 的一次批量校验。规则文件采用工具约定的 `ID:/正则/修饰符` 格式，四条规则里第二条故意写成可空模式。

```text
1:/foo.*bar/s
2:/a*/
3:/(?i)get /
4:/^(GET|POST) \//
```

```bash
hscheck -e /data/rules/http.rules
```

示例输出，具体格式需对照实际版本核验。

```text
OK: 1:/foo.*bar/s
FAIL (compile): 2:/a*/: Pattern matches empty buffer; use HS_FLAG_ALLOWEMPTY to enable support.
OK: 3:/(?i)get /
OK: 4:/^(GET|POST) \//
SUMMARY: 1 of 4 failed.
```

这份输出的判读要点有三处。第一，成功行以 `OK:` 开头并原样回显整行，包括 `ID:/正则/修饰符` 三段（`tools/hscheck/main.cpp:201-213`），因此可以直接把输出粘回规则文件做比对，不必自己拼接 ID 与模式。第二，失败行的格式是 `FAIL (compile): ID:正则: 错误消息`，错误消息就是 `hs_compile_error_t::message` 的原文，本例直接点明「模式匹配空缓冲区，请用 `HS_FLAG_ALLOWEMPTY` 启用支持」——它来自 `src/compiler/compiler.cpp:450`，是最常见的一类编译失败。第三，`SUMMARY: 1 of 4 failed.` 的分母是**载入的规则数**而不是通过数（`tools/hscheck/main.cpp:725-726`），所以「4」证明四条都被读进来了；如果分母是 3，说明有一行被当成注释或空行跳过了。另外注意第三条 `(?i)` 局部修饰符被正常接受，这说明 `hscheck` 走的是完整解析路径，而不是字符串匹配。

`hsdump` 的用法更单一，一条命令就能产出全套产物。它要求库在编译时打开 `DUMP_SUPPORT`，否则中间产物为空。

```bash
hsdump -e /data/rules -s /data/sigs/http.txt -o /tmp/hsdump -N -D
ls /tmp/hsdump
```

```text
db.raw  db_info.txt  patterns.txt  scratch.txt
```

这四个文件的用途分别是：`patterns.txt` 是编译进去的模式清单（ID 与正则），用于确认「我编的确实是我以为的那些规则」；`db_info.txt` 是 `hs_database_info()` 的原样输出，含版本、平台、模式与 HMAC；`scratch.txt` 是 scratch 的结构化转储，用于核对队列数量与状态大小；`db.raw` 是最终数据库的原始字节，可用 `xxd` 直接看头部（`magic` 为 `dbdbdbdb`）。中间产物默认还会在输出目录下按编译阶段生成子目录，加 `-X` 可以只要上面四个文件。

输入格式速查如下表。四个工具共用同一套输入约定，配错格式的表现是「文件读到了但规则是空的」。

| 输入 | 格式 | 常见错误 |
|---|---|---|
| 表达式目录 | 每个文件以数字 ID 命名，内容是正则 | 文件名非数字被跳过 |

### 6. 版本差异

四个工具的**选项集合**在 5.x 内基本稳定，但有几处与版本强相关的行为值得记住。

`hsbench` 的 `-H` 与 `-P` 只在 `HS_HYBRID` 编译的二进制里存在（`tools/hsbench/main.cpp:206-209`、`325-346`），非 hybrid 构建上传这两个选项会直接报「Hybrid matcher not enabled in this build」并退出 1。`HS_HYBRID` 由 CMake 在找到 PCRE 时定义，因此「装了 PCRE 但没编 Chimera」的环境里，这两个选项仍然不可用。同理，`-T` 依赖 `HAVE_DECL_PTHREAD_SETAFFINITY_NP` 或 Windows，在 macOS 等平台上的二进制里根本没有这个字母——传了会落到「Unrecognised command line argument.」。

`hsdump` 强依赖 `DUMP_SUPPORT`，而该变量是 `CMAKE_DEPENDENT_OPTION(..., ON, "NOT RELEASE_BUILD", OFF)`，即 release 构建默认关闭（见 04-01）。这意味着从发行版包管理器装来的 `hsdump` 很可能「能跑但什么都转不出来」，而不是报错。5.4.2 的变更日志有一条「Fix hsdump issue due to invalid nfa type」，说明 5.4.1 及更早版本在遇到特定 NFA 类型时会转储失败或崩溃；如果你的 `hsdump` 在某个规则集上直接退出，先确认版本是否低于 5.4.2。

`hscheck` 的 `-B`（构建签名集）与 `-C`（检查逻辑组合）是较晚加入的能力。`-C` 与 5.0.0 引入的逻辑组合（`HS_FLAG_COMBINATION`）配套；在 5.0.0 之前的版本上该选项不存在。`-E`（强制编辑距离）与 04-03 的 `HS_EXT_FLAG_EDIT_DISTANCE` 同源，两者语义一致但一个是编译期注入、一个是 API 参数。

`hscollider` 是四个工具里选项增长最快的，`--compress-expand`、`--compress-reset-expand` 与 `--mangle-scratch` 这三组一致性检查项明显是随流状态压缩（4.6.0）与 scratch 校验（4.2.0 引入 `HS_SCRATCH_IN_USE`）逐步加入的。它们的存在本身就是一个提示：流状态与 scratch 的生命周期错误很难靠「正常路径」测出来，必须用这种「每轮都破坏一次再验证」的方式才能暴露。更早版本上这些长选项不存在，需对照实际版本的 `tools/hscollider/args.cpp` 核验。

### 7. 常见误用与调试

工具类问题的共性是「命令跑通了但结论不可信」，真正报错反而好查。下表按现象给出判据。

| 现象 | 可能原因 | 验证方式 | 修复 |
|---|---|---|---|
| 提示缺 `-e` | 只给了 `-s` 但推不出目录 | 看签名文件路径是否同层 | 显式给 `-e` |
| 提示缺 `-c` | 忘了语料库 | 看 usage 输出 | 补 `-c` |
| `-T` 报未识别 | 平台没有绑核能力 | 看 usage 是否列出 `-T` | 去掉 `-T` 或换平台 |
| `-G` 报未识别 | release 构建把分支编掉了 | 看构建类型 | 用非 release 构建 |
| `-b` `-o` `-p` 报未识别 | 这三个字母无实现 | 对照 getopt 串 | 不要使用 |
| `hsdump` 产物为空 | `DUMP_SUPPORT` 为 OFF | 查 CMake cache | 重编非 release |
| 吞吐远低于预期 | 语料块太小或命中率过高 | 看 matches/kilobyte | 换语料或减规则 |
| 多线程无加速 | 绑核无效或语料过小 | 比 Mean 与 Max 差值 | 加 `-n` 或改 `-T` |
| 对拍全过但线上漏报 | 对拍语料未覆盖该路径 | 看 `-n` 生成数量 | 用真实语料 `-c` |
| 加载库后模式不符 | `-i` 目录里是旧库 | 看 `Hyperscan info` | 清目录重编 |

第一条要展开：**`hsbench` 的默认模式是 streaming，不是 block**。usage 文本写得很清楚：「`-N` Benchmark in block mode (default: streaming)」（`tools/hsbench/main.cpp:202-203`）。很多人拿默认命令测出来的数字去和线上 block 部署对比，结论自然对不上——流式模式要为每条流维护状态，开销结构完全不同。测之前先问一句「线上到底用哪种模式」，再用对应的 `-N` 或 `-V`。

第二条要展开：**`-i` 与 `-w` 是互斥的**。同时给会报「You cannot both load and save databases.」（`tools/hsbench/main.cpp:449-452`）。更重要的是 `-i` 的隐含风险：加载的库不带「编译时用了哪些标志」的完整信息，只带版本、平台与模式。若目录里的库是上一个规则集编的，`hsbench` 会照常跑完并给出漂亮的数字，但测的根本不是当前规则。判据就是输出里的 `Signatures` 与 `Expression count` 两行——它们来自库本身，与命令行给的签名文件无关。

第三条要展开：**语料库是 SQLite，不是纯文本**。`readCorpus()` 执行的是固定查询 `SELECT id, stream_id, data FROM chunk ORDER BY id;`（`tools/hsbench/data_corpus.cpp:86-87`），表名或列名不符会直接抛 `DataCorpusError` 并终止。`tools/hsbench/scripts/` 下提供了四个构造脚本：`CorpusBuilder.py` 是通用框架，`linebasedCorpus.py` 按行切块，`pcapCorpus.py` 从抓包文件切流，`gutenbergCorpus.py` 处理纯文本语料。语料太小会让测量被启动开销主导，表现为「加线程不提速」；语料太大则会让页缓存效应掩盖真实差异。经验做法是让单轮扫描时间落在 0.5 到 5 秒之间，再用 `-n` 拉到统计稳定。

第四条要展开：**`hscheck` 通过不等于线上能编**。`hscheck` 用的是它自己的默认标志集（streaming 模式、无 SOM、无扩展参数），而线上可能开 SOM、加偏移窗口、用 vectored。这些差异会改变可编译性：一条在 `hscheck` 下 `OK` 的模式，加上 `-L` 后可能因 SOM 的状态膨胀而报「Pattern too large」。因此校验命令必须复刻线上的编译条件：模式用 `-N`/`-V` 对齐、标志用 `-L`/`-8`/`-E` 补齐、必要时用 `-C` 打开逻辑组合检查。这条经验能省掉大量「本地全绿、上线编译失败」的返工。

调试顺序建议固定为：先看 usage 是否被触发（参数缺失或拼错），再看输入是否被真正读入（`Signatures`、`SUMMARY` 的分母），再看模式与库是否一致（`Hyperscan info`），最后才看性能数字。工具的输出字段含义与基准方法学的完整讨论见 08-01；`hsbench` 与 `hscollider` 的内部实现见 07-12；错误码与编译错误消息的对照见 04-08。

## 04-08 错误码、语法支持与排错速查手册

### 1. 本篇定位与覆盖范围

本篇是**错误码与语法能力边界**的唯一权威源，覆盖 `src/hs_common.h:478-588` 定义的 14 个 `HS_*` 错误码、`HS_MAX_PATTERN_COUNT`（`hs_common.h:595`），以及 `doc/dev-reference/compilation.rst` 中「Supported Constructs / Unsupported Constructs」两节所界定的正则语法范围。它同时是全套资料的排错入口：任何「编不过」「扫不动」「结果不对」的问题，都应先在这里定位到错误类别，再跳到对应的分册。

本篇**不**重列参数清单——`HS_FLAG_*` 见 04-02，`HS_MODE_*` 与扩展参数见 04-03，编译函数签名见 04-04，运行时函数见 04-05，scratch 与序列化见 04-06，工具参数见 04-07。也不展开故障案例的完整复盘（08-04 的六个案例）与诊断决策树（08-03）。本篇的组织方式是「码 → 触发条件 → 处置」与「构造 → 支持与否 → 替代写法」，是查表用的，不是读一遍就完的。

读之前先建立一条最重要的判断：**返回码告诉你「哪一层」失败，错误消息告诉你「为什么」**。`hs_error_t` 只有 14 个取值，粒度很粗；真正的信息在 `hs_compile_error_t::message` 里。因此排错的第一步永远是「把 message 打出来」，而不是盯着 `-4` 猜。第二重要的判断是：**编译期的失败几乎都是确定性的**，同样的模式与标志在任何机器上都失败；运行期的失败则可能与环境、并发、内存状态相关。这个区分决定了要不要换机器复现。

还有一条边界必须提前说清：Hyperscan **不是** PCRE 的超集。它的语法表面接近 libpcre，但为了支持「多模式同时匹配 + 流式 + 线性时间」，砍掉了一整类依赖回溯的构造。这不是实现不完整，而是设计前提。凡是需要捕获组内容、需要反向引用、需要任意零宽断言的需求，答案不是「想办法绕过」，而是「改用 Chimera 或 PCRE」。把这条记住，能省掉大量无效尝试。

`HS_MAX_PATTERN_COUNT` 的值为 1000000（`hs_common.h:595`），是单次编译允许的模式条数上限。超过它不是「慢慢编」，而是在编译器入口被拒绝；`src/grey.cpp:149` 有对应检查。这个上限与内存无关，纯粹是规模保护，实际能编多少条取决于可用内存与模式的复杂度——一千条复杂正则可能比十万条字面量更吃内存。

### 3. 逐项详解

**`HS_SUCCESS`（0）。** 唯一表示「调用完成了它承诺的事」。注意它的语义是分层的：对 `hs_compile` 表示数据库已产出，对 `hs_scan` 表示整块数据扫完且没有回调要求停止，对 `hs_compress_stream` 表示压缩字节已写入缓冲区。它**不**表示「有命中」——没有命中同样返回 0。把 0 当成「命中了」是新手最常见的误读，判断有没有命中只能看回调被调用的次数。

**`HS_INVALID`（-1）。** 参数非法，覆盖面最广：空指针、非法枚举值、损坏的 magic、HMAC 不符、压缩字节的结构校验失败，全都归到它。`hs_common.h:480-487` 特意加了一段免责说明：它只在函数「能够检测到」非法参数时返回，不能指望它发现「指向已释放内存的指针」这类问题。因此 `-1` 的正确解读是「至少有一个参数在语法上不成立」，具体是哪一个要看是哪个函数返回的：`hs_alloc_scratch` 返回 -1 多半是 db 或 scratch 为 NULL，`hs_deserialize_database` 返回 -1 多半是 magic 或 HMAC 不对。

**`HS_NOMEM`（-2）。** 分配失败。它可能来自数据库分配器、scratch 分配器或 misc 分配器，取决于调用的是哪个函数。容器环境里最常见的原因是内存限额（cgroup）而不是物理内存耗尽——此时 `malloc` 返回 NULL，库把它翻译成 -2。处置方式不是重试，而是降低并发（每条流都要状态）或缩小 scratch。注意编译期的 -2 与扫描期的 -2 含义不同：前者是编译临时对象吃满了内存（这部分无法用自定义分配器接管），后者通常是流状态或 scratch 扩容。

**`HS_SCAN_TERMINATED`（-3）。** 回调返回了非零，引擎立刻停止。语义上它不是「错误」而是「正常提前结束」，`hs_common.h:494-501` 明确写「目标缓冲区被部分扫描」。流式模式下它会粘住整条流，后续 `hs_scan_stream` 直接返回 -3 而不推进。处置分两种：如果业务确实想在命中第一条后就停，-3 是预期结果，不必当错误处理；如果是误判（例如回调里某个分支忘了 `return 0`），就会表现为「只报一条就再也不报了」，这类 bug 极难从日志看出，因为返回码看起来「合理」。

**`HS_COMPILER_ERROR`（-4）。** 编译失败，必须读 `hs_compile_error_t` 才有信息。它的两个字段各有分工：`message` 是英文原因，`expression` 是出错表达式的下标（从 0 开始，非表达式级错误为负）。批量编译时 `expression` 是唯一能定位到「第几条」的线索。典型原因包括：语法错误（缺右括号、非法转义）、不支持的构造、标志组合互斥、模式可空但未开 `ALLOWEMPTY`、模式过大、扩展参数互相矛盾、纯字面量 API 收到不支持的标志。这些在上面的语法表与 04-02 至 04-04 里都能找到对应条目。

**`HS_DB_VERSION_ERROR`（-5）。** 数据库的版本字段与当前库的 `HS_DB_VERSION` 不一致（`src/database.c:225`）。触发场景几乎都是「用旧版本编的库拿到新版本上加载」或反之。它与序列化格式绑定，不是「向后兼容」的：5.4.2 的库不能加载 5.3 编出的字节流。处置方式是两端统一版本，或者分发时把「库版本」写进文件名/元数据，加载前先比对。`hs_serialized_database_info` 能在不加载的前提下读出这个字段，是首选的预检手段。

**`HS_DB_PLATFORM_ERROR`（-6）。** 数据库的 platform 字段与当前 CPU 不兼容（`src/database.c:188`）。判定逻辑不是简单相等：数据库平台若为 `HS_PLATFORM_ALL` 直接通过；否则要求它与当前平台、或当前平台去掉 AVX2、去掉 AVX-512、去掉 VBMI 后的变体之一相等（`src/database.c:180-192`）。这解释了为什么「在高配机器上编、在低配机器上跑」有时能过有时不能——只有当数据库没有用到目标机缺失的指令集时才会命中那几个降级变体。稳定做法是跨机分发时用 `HS_PLATFORM_ALL` 编通用库，代价是放弃针对特定微架构的优化。

**`HS_DB_MODE_ERROR`（-7）。** 数据库的扫描模式与调用的 API 不匹配（`src/runtime.c:348`、`584`、`1114`）。三种典型：block 库调 `hs_open_stream`、stream 库调 `hs_scan`、vectored 库调 `hs_scan_stream`。它是硬失败而非降级，因为不同模式的字节码布局根本不同。处置只有一个：编译时按实际用法选对 mode（见 04-03），并在封装层用类型或断言把「库的模式」与「调用入口」绑死。

**`HS_BAD_ALIGN`（-8）。** 传入的指针对齐不满足要求，最典型的是 `hs_deserialize_database_at` 要求目标地址 8 字节对齐（`src/database.c:2944`）。`hs_common.h:526-529` 的措辞是「参数没有正确对齐」，没有指明具体对齐值，因为不同函数要求不同。处置方式是打印指针的低几位：`(uintptr_t)p & 7` 不为 0 就必然失败。共享内存部署里这个错误很常见，因为 mmap 返回的基址通常页对齐，但加上一个结构体偏移后就未必了。

**`HS_BAD_ALLOC`（-9）。** 分配器返回的内存不满足「本平台最大可表示类型的对齐要求」（`src/hs_common.h:531-536`、`src/allocator.h:61`）。它只在使用自定义分配器时出现，是「你的内存池切块对齐不够」的明确信号。处置方式是把池的块对齐提到 64 字节，或直接检查 `hs_check_alloc` 的判定条件。与 -8 的区别值得记：-8 是「你传进来的指针不对齐」，-9 是「你分配出来的内存不对齐」，一个在入口一个在出口。

**`HS_SCRATCH_IN_USE`（-10）。** 库检测到这块 scratch 正在被另一个调用使用（`src/scratch.c:370`、`542`）。最常见成因是在回调里用同一块 scratch 再调一次扫描，或者两个线程共享了一份 scratch。`hs_common.h:552-553` 明确它是「best-effort debugging tool, not a guarantee」——检测不到的情况依然会静默算错。因此正确的心态不是「没报 -10 就没事」，而是「每线程一份，从设计上杜绝共享」。

**`HS_ARCH_ERROR`（-11）。** 当前 CPU 不支持库所需的最低指令集（SSSE3）。它只在少数入口返回，例如 `hs_valid_platform`（`hs_common.h:467`）。注意它**不**检测 AVX2/AVX-512：库若是按 AVX2 编的而机器只有 SSE4.2，这个函数仍可能返回成功，真正的失败会以非法指令信号的形式出现，而不是返回码。这也是为什么跨机部署必须同时做「平台字段校验」与「真实跑一遍」两件事。

**`HS_INSUFFICIENT_SPACE`（-12）。** 提供的缓冲区太小，当前只有 `hs_compress_stream` 会返回它（`src/runtime.c:1250`）。它的特殊之处是「失败时依然写出参」：`used_space` 会被写成所需容量，因此正确用法是两段式——先 `buf=NULL`、容量 0 探一次，拿到 -12 与所需大小，再分配重试。把 -12 当致命错误直接放弃，是最常见的误用。

**`HS_UNKNOWN_ERROR`（-13）。** 内部匹配错误，通常意味着「流状态或 scratch 被非法使用了」。`hs_common.h:580-588` 的解释是「unexpected matching behaviors」，可能与应用层非法使用流或 scratch、或内存被越界写坏有关。它不该在正确用法下出现；一旦出现，排查方向是「有没有越界写」「有没有跨线程共享」「有没有在回调里改状态」，而不是继续调参数。它也是唯一建议直接上报 issue 的错误码，因为可能对应引擎内部缺陷。

**语法支持：支持的部分。** 字面量与全部 libpcre 引号/转义、字符类（`.`、`[abc]`、`[^abc]`）与预定义类（`\s` `\d` `\w` `\v` `\h` 及取反形式）、POSIX 命名类 `[[:xxx:]]` 与 `[[:^xxx:]]`、Unicode 属性 `\p{L}` `\P{Sc}`、量词（`?` `*` `+` 与有界重复）、分组（命名/非命名/非捕获，捕获内容被忽略）、分支 `|`、锚点 `^` `$` `\A` `\Z` `\z`、局部修饰 `(?i)` `(?m)` `(?s)` `(?x)`、`\b` 与 `\B`、注释 `(?#...)`、以及模式开头的 `(*UTF8)` 与 `(*UCP)` 控制动词。惰性量词（如 `\w+?`）被**接受但忽略**，因为 Hyperscan 报告所有匹配，不存在「贪婪与非贪婪的取舍」。

**语法支持：不支持的八项，必须逐条记住。** 其一，**反向引用与捕获子表达式**：`(a)\1` 报 `Back-references are unsupported.`（`src/parser/unsupported.cpp:59-61`），捕获组语法可以写但内容不保留。其二，**任意零宽断言**：前瞻 `(?=...)`、负前瞻 `(?!...)`、后顾 `(?<=...)` 全部报 `Zero-width assertions are not supported.`（`src/parser/unsupported.cpp:48-50`）。其三，**子程序引用与递归**：`(?1)`、`(?&name)` 报 `Subpattern reference unsupported`（`src/parser/Parser.rl:400-402`），`(?R)` 报 `Pattern recursion not supported`（`src/parser/Parser.rl:1828-1830`），Oniguruma 风格的 `\g<...>` 报 `Onigiruma subroutine call at index N not supported.`。其四，**条件模式**：`(?(1)a|b)` 报 `Conditional references are not supported.`（`src/parser/unsupported.cpp:56-58`）。其五，**回溯控制动词**：`(*PRUNE)`、`(*SKIP)`、`(*COMMIT)` 一类不被接受。其六，**`\C`**：在 UTF8 模式下解析期直接报 `\C is unsupported in UTF8`（`src/parser/Parser.rl:1304-1308`）；非 UTF8 模式下它被当作单字节组件接受，但官方文档仍列为不支持，因为它会破坏 UTF-8 序列的字符边界。其七，**`\R`**：报 `\R at index N not supported.`（`src/parser/Parser.rl:1705-1708`），替代写法是显式列出换行序列 `(?:\r\n|[\n\v\f\r\x85])`。其八，**`\K`**：报 `\K at index N not supported.`（`src/parser/Parser.rl:1712-1715`），它本质上是「重置匹配起点」，与 Hyperscan 只报结束偏移的模型冲突。

除这八项外，文档还把**原子组**（`(?>...)`，报 `Atomic groups are unsupported.`）、**占有量词**（`a++`，报 `Possessive quantifiers are not supported.`）、**callout 与嵌入代码**、**`\X`**（报 `\X unsupported at index N.`）列为不支持。它们被归到「同一类问题的不同写法」：都依赖回溯或需要引擎在匹配过程中执行外部逻辑。另有两条容易忽略的限制：UCP 模式下的 `\b`/`\B` 不被支持（报 `\b unsupported in UCP mode at index N.`，`src/parser/unsupported.cpp:70-78`），以及有界重复的上界超过 32767 时会被拒绝或报「Pattern too large」。

**替代路径。** 需要捕获组内容或反向引用时，唯一正解是 Chimera：用 Hyperscan 做预过滤、用 PCRE 做确认，`ch_scan` 的回调能拿到捕获组（模块见 07-11，机制见 06-14）。或者更简单——把这类规则整条交给 PCRE，只把「能表达成 Hyperscan 语法」的部分放进 Hyperscan。用 `HS_FLAG_PREFILTER` 也能让含不支持构造的规则「编过去」，但它只保证「不漏报」，会引入假阳性，必须二次确认，且会静默清掉 `min_length`（见 04-02）。编译错误结构的字段、流水线各阶段的失败点、解析器逐条拒绝的具体实现，分别见 05-04、06-01 与 07-01（字段见 05-04 ｜ 原理见 06-01 ｜ 模块见 07-01）。

### 4. 典型示例

下面这段程序把十种典型失败各编一次，只打印返回码与错误消息，用于建立「消息 → 构造」的直觉。它不扫描，因此不需要 scratch。

```c
#include <hs.h>
#include <stdio.h>

static void probe(const char *tag, const char *expr, unsigned flags) {
    hs_database_t *db = NULL;
    hs_compile_error_t *err = NULL;
    hs_error_t rc = hs_compile(expr, flags, HS_MODE_BLOCK, NULL, &db, &err);
    printf("%-10s rc=%2d expr=%d msg=%s\n", tag, rc,
           err ? err->expression : -1, err ? err->message : "-");
    hs_free_compile_error(err);
    hs_free_database(db);
}

int main(void) {
    probe("backref", "(a)\\1", 0);
    probe("lookahead", "foo(?=bar)", 0);
    probe("atomic", "(?>abc)", 0);
    probe("possessive", "a++", 0);
    probe("newline", "\\R", 0);
    probe("reset", "ab\\Kcd", 0);
    probe("recursion", "(?R)", 0);
    probe("subref", "(a)(?1)", 0);
    probe("empty", "a*", 0);
    probe("som-single", "abc",
          HS_FLAG_SOM_LEFTMOST | HS_FLAG_SINGLEMATCH);
    return 0;
}
```

示例输出，具体格式需对照实际版本核验。

```text
backref    rc=-4 expr=0 msg=Back-references are unsupported.
lookahead  rc=-4 expr=0 msg=Zero-width assertions are not supported.
atomic     rc=-4 expr=0 msg=Atomic groups are unsupported.
possessive rc=-4 expr=0 msg=Possessive quantifiers are not supported.
newline    rc=-4 expr=0 msg=\R at index 0 not supported.
reset      rc=-4 expr=0 msg=\K at index 2 not supported.
recursion  rc=-4 expr=0 msg=Pattern recursion not supported
subref     rc=-4 expr=0 msg=Subpattern reference unsupported
empty      rc=-4 expr=0 msg=Pattern matches empty buffer; use HS_FLAG_ALLOWEMPTY to enable support.
som-single rc=-4 expr=0 msg=HS_FLAG_SINGLEMATCH is not supported in combination with HS_FLAG_SOM_LEFTMOST.
```

逐行判读这份输出，可以一次建立四条判据。第一，十行全部是 `rc=-4`，说明「不支持的构造」与「标志互斥」都属于编译期语义拒绝，而不是参数校验失败（那会是 -1）；这也意味着它们在任何机器上都必然失败，不需要换环境复现。第二，`expr=0` 在全部行上都出现，因为 `hs_compile` 只有一条表达式；换成 `hs_compile_multi` 后这个字段才会指出「第几条」，这也是批量编译必须打印它的原因。第三，消息文本的措辞有规律：「are unsupported」多用于组件类型（反向引用、原子组），「is not supported」多用于标志组合（SOM 与 SINGLEMATCH），「at index N」用于能定位到模式内偏移的字符级构造（`\R`、`\K`、`\X`）。记住这个规律，看日志时能立刻判断是「语法问题」还是「组合问题」。第四，最后两行是两类不同的问题却给同样的返回码：`empty` 是模式语义不满足「至少消费一个字节」，`som-single` 是标志互斥；前者可以通过 `HS_FLAG_ALLOWEMPTY` 解决，后者无解（只能二选一），因此**绝不能只看返回码做自动化处置**，必须匹配消息文本或提前在配置层校验。

批量场景下更常用的是 `hscheck`，它把同样的信息按「逐条 OK/FAIL + 汇总」输出，适合塞进 CI。

```bash
hscheck -e bad.rules -N
```

```text
FAIL (compile): 7:/(a)\1/: Back-references are unsupported.
SUMMARY: 1 of 1 failed.
```

这两行的判读很直接：`FAIL (compile)` 前缀说明是编译失败而非运行失败，`7:` 是规则文件里写的 ID（不是行号），后面的模式与消息原样来自编译器。`SUMMARY: 1 of 1 failed.` 的分母是载入条数，用它确认「文件确实被读到了一条」；如果分母是 0，问题在文件格式而不是规则本身。把 `-N` 换成默认（streaming）再跑一次，若某些规则在 stream 下失败而在 block 下通过，差异就来自模式本身（例如流式 SOM 缺 horizon），这条对照能快速区分「规则问题」与「模式问题」。

### 5. 速查表

排错速查表按「现象 → 可能原因 → 验证方式 → 修复」组织。现象列写你观察到的东西，验证列写一条能立刻执行的动作。

| 现象 | 可能原因 | 验证方式 | 修复 |
|---|---|---|---|
| 返回 -4 且消息含 unsupported | 用了不支持的构造 | 对照本篇语法表 | 改写或改用 Chimera |
| 返回 -4 且消息含 empty buffer | 模式可空 | `hs_expression_info` 看 `min_width` | 改写或开 `ALLOWEMPTY` |
| 返回 -4 且消息含 Pattern too large | 有界重复过大 | 减小 `{n,m}` 上界 | 拆分或改预过滤 |
| 返回 -4 且消息含 combination | 标志互斥 | 看消息点名的两个标志 | 去掉其中一个 |
| 返回 -4 且 expr 指向某条 | 批量里第 N 条出错 | 打印 `expression` 字段 | 修该条规则 |
| 返回 -4 但无消息 | `error` 传了 NULL | 查调用点 | 传 `&err` 并打印 |
| 返回 -5 | 库与运行库版本不同 | 比对两端 `hs_version()` | 统一版本重编 |
| 返回 -6 | 平台不兼容 | 看 `hs_database_info` 的 Features | 编通用库或换机器 |
| 返回 -7 | 模式与 API 不匹配 | 核对编译时的 mode | 用对应模式的库 |
| 返回 -8 | 目标地址未对齐 | `(uintptr_t)p & 7` | 按 64 字节对齐分配 |
| 返回 -9 | 自定义分配器对齐不足 | 查分配器实现 | 提高块对齐 |
| 返回 -10 | scratch 被共享 | 查回调内是否重入 | 每线程一份 |
| 返回 -11 | CPU 缺指令集 | `hs_valid_platform` | 换机器或换构建 |
| 返回 -12 | 压缩缓冲区太小 | 看 `used_space` | 先探容量再分配 |
| 返回 -13 | 流或 scratch 被非法使用 | 查越界写与并发 | 修生命周期 |
| 扫描无任何命中 | 模式与数据不匹配或库错 | `--echo-matches` 打印 | 换库或改规则 |
| 命中数量异常多 | 预过滤假阳性或 `ALLOWEMPTY` | 看 matches/kilobyte | 二次确认或改写 |
| 起始偏移恒为 0 | 未开 SOM | 查编译期 flags | 加 `SOM_LEFTMOST` |
| 起始偏移为 `~0ULL` | 超出 horizon | 与哨兵常量比较 | 换 LARGE 或降级 |

语法能力速查表如下，左边是「你想写什么」，右边是「Hyperscan 怎么写」。

| 想写 | 能直接写吗 | 替代写法 |
|---|---|---|
| `(a)\1` 反向引用 | 不能 | Chimera 或 PCRE |
| `(?=foo)` 前瞻 | 不能 | 把后文并进模式或 Chimera |
| `(?<=foo)` 后顾 | 不能 | 反转匹配方向或用两块缓冲区 |
| `(?>abc)` 原子组 | 不能 | 改写为等价的无回溯结构 |
| `a++` 占有量词 | 不能 | 用普通 `a+` 并接受全匹配语义 |
| `\R` 任意换行 | 不能 | `(?:\r\n\|[\n\v\f\r])` |
| `\K` 重置起点 | 不能 | 开 SOM 后用起始偏移模拟 |
| `\C` 单字节 | 不能 | 用 `[\x00-\xff]` 并注意 UTF8 |
| `(?R)` 递归 | 不能 | 展开固定层数或 Chimera |
| `(?(1)a\|b)` 条件 | 不能 | 拆成多条规则用组合表达式 |
| `a{100000}` 大重复 | 有限 | 降到 32767 以下或拆段 |
| `.*` 可空模式 | 加标志可以 | 优先改写为 `.+` 或加锚点 |

### 6. 版本差异

14 个错误码的取值自 4.x 后期起没有变化，`HS_SUCCESS` 到 `HS_UNKNOWN_ERROR` 的负值序列保持稳定，因此日志里的数字可以跨版本对照本篇表格。新增错误码是极少见的事件：`HS_INSUFFICIENT_SPACE`（-12）是随 4.6.0 的流状态压缩一起引入的——在它之前 `hs_compress_stream` 这个函数根本不存在，自然也不需要「空间不够」这个码。`HS_SCRATCH_IN_USE`（-10）是 4.2.0 引入的（`CHANGELOG.md` 的 `[4.2.0] 2016-05-31` 条目「New API error value」），在此之前并发复用 scratch 不会被检测。`HS_UNKNOWN_ERROR`（-13）同样是较晚加入的兜底值，早期版本上内部错误可能表现为断言失败或直接崩溃。

语法边界的变化比错误码活跃。5.0.0 引入逻辑组合（`HS_FLAG_COMBINATION`），带来一类新的编译错误——组合公式里写了匹配 ID 而不是表达式下标、或与不兼容标志混用；这些错误消息在 5.0.0 之前不存在。5.4.1 修了 `hs_expression_info()` 对逻辑组合标志的处理（issue #291），意味着 5.4.0 及更早版本上「用 info 预检组合表达式」的结论不可信。5.4.1 还给纯字面量 API 加了空串检查（issue #302/304），因此「空字面量」在旧版本上可能编译成功而在新版本上被拒，这是升级时会遇到的兼容性差异。

与工具相关的差异值得单独记：`hsdump` 在 5.4.2 修了「invalid nfa type」导致的转储问题，5.4.1 及更早版本在特定 NFA 类型上可能直接失败；`hsbench` 的 `-H`/`-P` 依赖 `HS_HYBRID` 构建，选项是否存在随构建配置而变。排错时若怀疑「工具本身有问题」，先确认版本与构建开关，再怀疑输入。

能力边界本身是**稳定**的：不支持反向引用、任意零宽断言、递归、条件模式、回溯控制动词、`\C`、`\R`、`\K` 这条清单从 4.x 到 5.4.2 没有松动过。原因是它们与「线性时间 + 流式 + 多模式」的设计前提根本冲突，不是工程量问题。期待某个版本「突然支持」是不现实的；正确的路线是 Chimera。Vectorscan（ARM 社区分支）在这条边界上与上游一致，但引擎支持矩阵不同，不要把它的平台结论当作上游结论（见 07-13）。

### 7. 常见误用与调试

排错最常见的失败不是「查不到原因」，而是「查错了层」。下表给出四类典型误判及其纠正方式。

| 误判 | 实际情况 | 纠正 |
|---|---|---|
| 看到 -4 就去查环境 | 编译错误是确定性的 | 读 message，改规则 |
| 看到 -1 就以为是库 bug | 多半是参数为空或 magic 坏 | 打印每个入参 |
| 把 -3 当错误上报 | 是回调主动终止 | 检查回调返回值 |
| 把 -12 当致命错误 | 是两段式探测的正常返回 | 读 `used_space` 重试 |
| 用 -10 当线程安全证明 | 只是尽力检测 | 从设计上每线程一份 |
| 改 `HS_FLAG_PREFILTER` 绕过语法限制 | 只保证不漏报 | 必须二次确认 |
| 认为 SOM 能解决所有起点问题 | 受 horizon 与互斥限制 | 见 04-02 与 04-03 |
| 用 `hs_expression_info` 当编译预检 | 成功不代表可编译 | 以 `hs_compile` 为准 |

第一条要展开：**「不支持」与「写错了」要分开**。同样是 -4，`(a)\1` 是能力边界（永远编不过），`(abc` 是语法错误（补个右括号就好）。区分方法看消息措辞：含 unsupported / not supported 的是能力边界，含 Missing / Invalid / Unexpected 的是语法错误。前者只能改设计，后者改笔误即可。把这两类混在一起处理，会导致「为了一个漏写的括号去改架构」或「为了一个不支持的构造反复调参数」。

第二条要展开：**`HS_FLAG_PREFILTER` 不是万能钥匙**。它确实能让含零宽断言、反向引用的规则「编过去」，但代价有三：返回的匹配是精确集合的**超集**（有假阳性）、SOM 不可用（因此不能要起始偏移）、`min_length` 会被静默清零（`src/compiler/compiler.cpp:286-291`）。如果业务把预过滤结果直接当最终结果用，就会得到「命中变多、位置漂移」的现象，而这类问题极难在测试阶段发现（测试语料通常太干净）。正确用法是「Hyperscan 粗筛 + PCRE 精确确认」，两段式部署见 06-14。

第三条要展开：**错误消息里的 `index` 是模式内偏移，不是行号**。`\R at index 0`、`\K at index 2` 这类消息给出的是该构造在正则字符串里的字节位置，用于在长模式里定位。它与 `hs_compile_error_t::expression` 是两个不同维度：后者是「第几条规则」，前者是「这条规则里的第几个字节」。批量排错时应先看 `expression` 缩小到条，再看消息里的 index 缩小到位置。

第四条要展开：**排错顺序应当是「层级 → 类别 → 具体」**。层级指编译期还是运行期：编译期失败与机器无关，运行期失败才需要看环境。类别指错误码分组：参数、环境、资源、语义，四组的处置完全不同。具体才轮到看消息文本与源码位置。反过来做（一上来就 grep 源码）往往会在错误的文件里翻很久，因为同一个错误码在多个入口都会产生。

最后给一条工程建议：把本篇的两张速查表做成团队内部的「错误码 → 责任人 → 处置」映射。`-4` 归规则维护者，`-5`/`-6` 归发布与运维，`-7`/`-10` 归集成开发者，`-12`/`-13` 归值班。这样线上出现返回码时不需要临场判断该找谁，能显著缩短恢复时间。错误码在具体故障场景中的组合与判读见 08-03 与 08-04；`HS_FLAG_*` 的互斥细节见 04-02；SOM 与 horizon 的约束见 04-03；编译流水线各阶段的失败点见 06-01；解析器如何逐条拒绝不支持构造见 07-01。
