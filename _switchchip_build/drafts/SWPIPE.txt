# 交换芯片数据面流水线深度解析：从端口到端口的逐阶段之旅

## SWPIPE-01 为什么必须端到端看流水线

关于交换芯片流水线，多数资料是拆开讲的：讲二层就说查 MAC 表，讲三层就说最长前缀匹配，讲 QoS 就说分类排队调度，讲隧道就说封装解封装。这种讲法能让你知道每一块"做什么"，却留下一个关键空白——这些功能在一个真实报文上到底按什么顺序发生、哪些步骤挤在同一个硬件阶段、哪一步的结果被后面的步骤拿去用。空白不补上，就回答不了工程里最实际的问题：报文丢了，是哪一段丢的？时延高了，是哪个阶段拖的？表项加不进去，是哪一级资源满了？

流水线这个词有两层含义，必须分清。第一层是功能流水线：转发要依次完成解析、查表、决策、缓冲、调度、改写、发送，这是一个逻辑顺序。第二层是物理流水线：芯片把功能拆到若干硬件阶段上，每个阶段由专门的电路执行，报文像在工厂装配线上一样一站站往下走，不同报文可以同时处在不同阶段。前者是"要做什么"，后者是"在什么上面做、能并行多少"。只懂第一层，你看得懂网络图；懂了第二层，你才看得懂芯片数据手册里的"每管道阶段数""查表级数""单遍处理能力"这些参数到底在说什么。

这一篇和基础知识分册的关系要讲清楚：基础知识里按功能把 L2、L3、QoS、隧道各讲了一遍，本篇不重复那些功能细节，而是换一个视角——跟着一个报文走完全程，在每一站停下来看清楚这里发生了什么、依赖上一站的什么结果、又把什么交给下一站。看完之后，你应该能把任意一个转发功能挂到流水线的具体位置上，也能反过来从现象定位到阶段。

图中节点速览：n1 是入口端口，完成物理层和媒体接入层的处理；n2 是入口处理段，负责解析报文头、查表做出转发决策、完成分类与监管；n3 是交换与缓冲段，把报文送到目标端口并在队列中等待发送；n4 是出口处理段，执行出口策略、改写报文头、准备串行发送；n5 是出口端口，把报发送到线路上。整张图确立三大段骨架：入口处理、交换缓冲、出口处理。后续章节都围绕这三段展开，任何时候迷路了都回到这张图定位。

下表把流水线两层含义的区别列清楚，这是全篇的概念基础。

| 视角 | 关心的问题 | 对应参数 | 排障时的用途 |
|---|---|---|---|
| 功能流水线 | 转发要完成哪些处理 | 支持哪些协议与功能 | 判断功能有没有被支持 |
| 物理流水线 | 处理落在哪些硬件阶段 | 阶段数、查表级数、单遍多遍 | 判断性能瓶颈与资源上限 |
| 两者关系 | 多个功能如何映射到有限阶段 | 阶段资源共享、依赖链长度 | 判断功能叠加后能否线速 |

一个贯穿全篇的判断标准：凡是涉及"能不能同时做""做了会不会变慢""加了这条规则会不会挤掉别的"，都要落到物理流水线层面去想，光看功能清单是看不出来的。这也是为什么岗位要求里强调"熟悉交换机硬件结构"——不理解阶段，就没法做资源规划和性能诊断。

## SWPIPE-02 三段式骨架：入口、交换缓冲、出口

几乎所有交换芯片的数据通路都能归纳成三大段：入口处理段、交换与缓冲段、出口处理段。这个三段式不是某家厂商的专有设计，而是由转发这件事本身的逻辑决定的——进来要先判断往哪走，中间要把它送到目标并管理拥塞，出去前要按出口要求把报文改好发出去。

入口处理段的核心任务是"做决策"。报文进来后，先解析出关键字段，再用这些字段查表，得到转发决策：去哪个端口、走哪条路径、属于哪个队列、要不要上送控制面、要不要复制。这个阶段的关键是快——决策必须在报文进入时尽快完成，否则会成为整条流水线的瓶颈。入口段的决策结果会以内部元数据的形式跟着报文走完整条流水线，后面的阶段都读它，不再重复查表。

交换与缓冲段的核心任务是"搬运与排队"。决策做好后，报文要通过芯片内部的交换网送到目标端口。如果目标端口正忙，报文就要在缓冲区里等待。这一段同时承担拥塞管理：队列满了要不要丢包、要不要标记、要不要发暂停帧，都在这里决定。它是芯片里面积最大、功耗最高的部分之一，也是吸收微突发的主战场。

出口处理段的核心任务是"按出口要求整形"。同一个报文从不同端口出去，可能需要不同的处理：这个端口要加 VLAN 标签，那个端口要做隧道封装；这个端口开了出口 ACL，那个端口要重新计算校验和。出口段把入口决策的结果落地成对报文的实际改写，最后交给端口串行发出。

下表把三段的目标、典型动作和关注参数并列，方便你对照数据手册阅读。

|---|---|---|---|

| 出口处理段 | 按出口要求整形报文 | 出口策略、改写、封装、串行化 | 出口带宽、改写能力、端口速率 |

把三段式骨架再抽象一层，会得到一个贯穿全篇的模型：整条流水线就是在给同一张"决策单"逐层填字段。入口段写下目标端口、下一跳和内部优先级；交换缓冲段追加队列位置、调度时隙和拥塞标记；出口段补上改写指令与封装动作；串行化时决策单随报文丢弃，只留下改写后的比特流。下游各段只读上游写好的字段，不回头重查——这是流水线能线速运行的前提。下图把这张决策单的填写过程画出来。

图中节点速览：n1 是入口段写下的目标端口、下一跳与内部优先级；n2 是交换缓冲段追加的队列、调度时隙和拥塞标记；n3 是出口段追加的改写指令与封装动作；n4 是串行化发出，元数据随报文丢弃。整张图的关键是方向性——字段只往下游写、不回头读，上游写错的值下游照单全收。这解释了为什么很多问题"现象在出口、根因在入口"：出口只是把入口写好的结论兑现出来。后面每一段展开时，都可以拿这张图对照，看这一段到底往决策单里写了什么、又读了谁的。

用一个形象的类比收束：入口段像快递分拣中心，看地址决定去向；交换缓冲段像分拣后的传送与暂存区，包裹多了要排队；出口段像发货口，按目的地贴单、装箱、送上货车。三段各司其职，任何一段的处理能力不匹配，整条线的吞吐就上不去。理解了这个骨架，后面逐段深入时就不会迷失方向。

## SWPIPE-03 入口段之一：物理层与端口接入

报文进入芯片的第一站是端口。这一站看起来与"转发逻辑"无关，实际上决定了后面所有阶段能看到什么样的报文，也决定了链路质量问题的表现形态。

高速端口这一层包括物理层收发、物理编码子层和媒体接入控制三个部分。物理层收发负责把线路上的电信号或光信号转成数字比特，物理编码子层负责编码解码和前向纠错，媒体接入控制负责成帧、地址识别和差错校验。在 112G 这类高速SerDes 上，前向纠错是标配——线路误码率很高，不纠正的话链路根本没法用。纠错会带来时延，这个时延是固定的，属于芯片时延预算的一部分。

端口这一层还有几个概念容易混。物理端口是芯片对外的一个实际接口；逻辑端口是芯片内部识别的通道编号；桥端口是二层转发视角下的端口实例，承载生成树状态、VLAN 成员关系。一个物理端口可能对应多个逻辑端口，比如把一个物理口拆成若干虚拟口，或者做链路聚合时把多个物理口聚成一个逻辑口。查表和转发决策用的是逻辑端口或桥端口，不是物理引脚号。排障时要特别注意这个映射关系——配置里写的端口号和数据手册里的物理引脚号往往不是一回事。

下表列出端口接入阶段常见问题与对应的现象，便于现场快速定位。

| 问题 | 现象 | 定位层次 |
|---|---|---|
| 链路起不来 | 端口始终 down | 物理层收发、编码、光模块 |
| 误码高 |  crc 错误计数增长 | 前向纠错、信号质量 |
| 帧校验错 | 丢弃计数增长 | 媒体接入控制层 |
| 端口映射错 | 配置的口和实际不通 | 逻辑端口映射表 |
| 聚合不等于预期 | 流量只走一个成员口 | 逻辑端口与聚合组关系 |

工程上有一条经验：如果计数器显示物理层就有错误，不要往转发逻辑方向查。物理层问题表现为链路不稳定、误码和 crc 错误，与查表或策略无关；查表问题表现为报文进了芯片却没从预期的口出来，物理层计数器是干净的。分清这两类现象，能省掉大量无效排查。

## SWPIPE-04 入口段之二：解析器与字段提取

端口把报文变成内部形式后，第一件转发相关的事是解析。解析器负责识别报文头的结构，把关键字段抽出来，供后面的查表使用。这一步决定了后面能看到什么——解析器没识别的字段，后面的表就用不了。

解析器的工作方式可以理解成一个状态机：从最外层头开始，按协议类型一层层往里剥。看到以太网头，根据类型字段判断里面是 IPv4、IPv6 还是其他协议；看到 IPv4 头，根据协议字段判断是传输层还是隧道；遇到 VLAN 标签就记录标签信息再继续。每剥一层头，就消耗一个解析阶段，并把抽出来的字段放进一组内部寄存器，通常叫头向量或字段缓存。后面的查表逻辑不直接读报文原始字节，而是读这组字段。

解析深度是硬约束。芯片的解析阶段数固定，常见十几级，具体数字要查数据手册。一个套了 VLAN、VXLAN、IPv6、TCP 的报文已经吃掉大半预算，再叠几层隧道就超出上限——解析器停止工作，后面的字段"看不见"，依赖这些字段的功能（比如基于内层端口的负载均衡）随之失效。这正是基础知识分册里反复强调的"IPv6 扩展头与解析深度矛盾"的根源，也是选型时必须核对"隧道嵌套层数"这个参数的原因。

下面用伪代码表达解析的迭代过程，重点是"每剥一层消耗一个阶段"这条约束如何体现。这不是任何真实芯片的接口，只用于建立概念。

```c
/* 工程理解伪代码：解析阶段预算如何约束深层字段可见性 */
int parse_packet(struct packet *p, struct fields *f)
{
    int stages_used = 0;

    parse_l2(p, f); stages_used++;          /* 以太网头 */

    while (has_vlan_tag(p)) {
        if (stages_used >= MAX_PARSE_STAGES)
            return PARSE_TRUNCATED;         /* 预算耗尽，后面的头看不见 */
        parse_vlan(p, f); stages_used++;
    }

    if (is_ipv4(p) || is_ipv6(p)) {
        parse_l3(p, f); stages_used++;
        while (has_extension_header(p)) {   /* IPv6 扩展头链 */
            if (stages_used >= MAX_PARSE_STAGES)
                return PARSE_TRUNCATED;
            skip_extension(p, f); stages_used++;
        }
    }

    if (is_tunnel(p)) {
        parse_tunnel(p, f); stages_used++;  /* 隧道头，再嵌套就危险 */
        parse_inner_l3(p, f); stages_used++;
    }

    return PARSE_OK;
}
```

对这段伪代码的判读：`stages_used` 每次解析一层就加一，与 `MAX_PARSE_STAGES` 比较，超过就返回截断——这直接对应芯片里解析流水线深度固定的事实。`while (has_vlan_tag)` 和 `while (has_extension_header)` 两个循环是消耗阶段的大户，因为这两类头的层数不固定。隧道部分连续调用两次解析，说明嵌套隧道对预算的压力最大。一旦返回 `PARSE_TRUNCATED`，后续依赖深层字段的功能会静默失效——报文可能仍然被转发，但基于内层端口的负载均衡、基于内层地址的 ACL 都不工作，这种"看起来通但策略不生效"的现象很难排查。真实芯片的解析器比这段伪代码复杂得多，会并行处理多路、支持条件分支，但"阶段预算有限"这条底层约束是一致的。

## SWPIPE-05 入口段之三：查表决策与并行查找

解析出的字段被放进头向量后，入口段开始查表。这是转发决策的核心，也是芯片里最讲究并行设计的地方。查表的目标是把字段组合成键，在硬件表里找到对应的动作，得到转发决策。

入口段要查的表通常有好几类：二层转发表按目的媒体地址查，三层路由表按目的 IP 做最长前缀匹配，邻接表把下一跳解析成媒体地址，等价多路径表决定走哪条成员链路，访问控制列表按多维条件匹配，服务质量分类表决定队列和标记。这些表不能串行一个查完再查下一个——那样时延会累加到无法接受。芯片的做法是把它们分成若干查表阶段，能并行的尽量并行，必须串行的才排成先后。

两张表能不能并行，取决于后一张的键是否依赖前一张的结果。二层转发表的键是目的媒体地址，邻接表的键是三层查表得到的下一跳，后者依赖前者，必须串行。而基于源地址的访问控制和基于目的地址的三层查表互不依赖，可以放在同一阶段并行查。编译器或硬件设计时的一项工作，就是把这些依赖关系排成一条尽可能短的链——链越长，转发时延越大，占用的阶段越多。

下表把常见查表按"键来自哪里"分类，这决定了它们能否并行。

| 表类型 | 查找键 | 键的来源 | 与其他表的关系 |
|---|---|---|---|
| 二层转发表 | 目的媒体地址加虚拟局域网 | 解析结果 | 独立，可并行 |
| 三层路由表 | 目的网际协议地址 | 解析结果 | 独立，可并行 |
| 访问控制列表 | 地址、端口、协议组合 | 解析结果 | 独立，可并行 |
| 邻接表 | 下一跳地址 | 路由表结果 | 依赖三层查表，须串行 |
| 等价多路径表 | 路由表结果或流哈希 | 路由表结果 | 依赖三层查表，须串行 |
| 隧道终止表 | 隧道标识与内层地址 | 解析结果 | 依赖隧道解析 |

下图把并行与串行查表的关系画出来，说明依赖链如何形成。

图中节点速览：n1 是解析结果形成的字段缓存；n2、n3、n4 是三张互不依赖的表，可以放在同一查表阶段并行查；n5 和 n6 的键来自三层查表结果，必须等 n3 完成后才能查，形成串行依赖；n7 汇总所有查表结果形成最终转发决策。两条信息值得单独记住：一是 n2、n3、n4 并行而 n5、n6 必须等待，这张图的键来源决定了哪些表能挤进同一阶段；二是 n4 访问控制列表虽然并行查，其动作却能在汇总时覆盖 n7 已定下的目标端口——查表动作的并行性与动作的生效时机是两回事。整张图说明查表调度的核心是依赖关系：无依赖的表并行压缩时延，有依赖的那些表排成链，链的长度直接决定入口段时延。

下面这段伪代码展示查表依赖如何体现为阶段顺序，以及为什么邻接查表不能提前。

```c
/* 工程理解伪代码：查表依赖决定的阶段顺序 */
struct decision lookup_pipeline(struct fields *f)
{
    struct decision d = {0};

    /* 第一查表阶段：三张表并行，键都来自解析结果 */
    d.l2_entry   = fdb_lookup(f->vlan, f->dst_mac);
    d.route      = lpm_lookup(f->dst_ip);
    d.acl_action = acl_lookup(f->src_ip, f->dst_ip, f->l4_port);

    /* 第二查表阶段：键依赖第一阶段结果，无法提前 */
    if (d.route.hit) {
        d.adj = adjacency_lookup(d.route.nexthop);    /* 依赖路由结果 */
        d.ecmp = ecmp_select(d.route.ecmp_group, f->flow_hash);
        d.egress_port = d.adj.port;
    } else {
        d.egress_port = d.l2_entry.port;
    }

    /* 决策汇总：访问控制的动作可能覆盖前面的结果 */
    if (d.acl_action.redirect)
        d.egress_port = d.acl_action.target_port;

    return d;
}
```

对这段伪代码的判读：第一个阶段的三张表都以解析结果为键，没有相互依赖，硬件里可以同时发起查找；第二个阶段的邻接表和等价多路径表都以路由结果为键，必须等 `lpm_lookup` 返回，这就是依赖链上不可压缩的一段；最后的访问控制动作可以覆盖前面得到的目标端口，说明查表结果并非简单叠加，后阶段有权改写前阶段的决策。这段伪代码还揭示了一个常被忽略的事实：访问控制列表虽然是"独立可并行"的，但它的动作可能在决策汇总时生效，因此逻辑上它出现在流程末端——并行的是查表动作，生效时机是另一回事。真实芯片里这些阶段由硬件调度，开发者能做的是控制表的数量和依赖链长度，让它们放得下、跑得快。

## SWPIPE-06 入口段之四：分类、监管与镜像

查表做出决策后，入口段还要完成几项配套处理：服务质量分类、流量监管和镜像。这些动作看似附属，实际上决定了报文进入缓冲段后享受什么待遇。

服务质量分类决定报文属于哪个队列、带什么内部优先级。分类的依据可以是报文自带的标记，比如网际协议服务类型字段或二层优先级字段，也可以根据入口端口、虚拟局域网或访问控列表结果重新标记。这里有一个重要概念叫信任边界：交换机是相信报文自带的标记，还是按自己的策略重新标记。信任边界设在入口，一旦分类完成，报文在芯片内部就带上了内部优先级，后面的队列调度只看这个内部值。

流量监管用令牌桶机制限制流量速率。超过契约的报文可以被丢弃，也可以被重新标记为低优先级——后者叫重标记，比直接丢弃温和，在网络里更常用。监管发生在入口，因为它要控制的是"进入网络的流量"，而不是已经挤压在出口队列里的流量。

镜像是把报文复制一份送到观察端口，用于抓包分析。镜像可以在入口做，也可以在出口做，入口镜像能看到报文进入时的原始状态，出口镜像看到的是改写后的状态。镜像本身消耗带宽和复制资源，开得太多会影响正常转发。

下表把入口段的配套动作、依据和后果整理出来。

| 动作 | 依据 | 后果 | 是否可覆盖前序决策 |
|---|---|---|---|
| 服务质量分类 | 自带标记或入口策略 | 决定内部队列与优先级 | 可覆盖自带标记 |
| 流量监管 | 速率契约与令牌桶 | 超限丢弃或重标记 | 可改写服务质量等级 |
| 访问控制动作 | 多维匹配规则 | 允许、丢弃、重定向 | 可改写目标端口 |
| 入口镜像 | 镜像会话配置 | 复制报文到观察口 | 不改变原报文去向 |

一个工程判断：当"报文通了但服务质量不对"时，优先查入口分类和信任边界，而不是去查出口队列。因为队列调度只看内部优先级，内部优先级是入口定的——入口分类错了，后面怎么调度都救不回来。这类问题的现象往往很迷惑：报文能到、速率也对，就是延迟或丢包不符合预期，根源常在入口这一段。

## SWPIPE-07 交换与缓冲段：交换网、缓冲与队列

入口段做完决策，报文带着目标端口和内部优先级进入交换与缓冲段。这一段要解决两个问题：怎么把报文从入口搬到出口，以及目标端口忙的时候怎么办。

交换网是芯片内部的互连结构，负责把报文从入口侧送到目标出口侧。高端芯片采用多管道设计，每个管道有自己的交换网，管道之间还能互通。交换网的带宽必须足够高，否则即使端口速率再快，报文也会堵在内部。数据手册里常说的"交换容量""交换网带宽"就是这一段的能力指标——它通常要大于所有端口带宽之和，才能做到线速无阻塞。

缓冲是芯片里的片上内存，用来暂存等待发送的报文。缓冲区的设计直接影响拥塞表现：浅缓冲时延低但吸收微突发能力弱，深缓冲能吸收突发但时延高。现代高端芯片强调的不是缓冲容量有多大，而是缓冲吞吐有多高——能否在高带宽下快速存取，比存多少字节更关键。缓冲区通常由所有端口共享，配合动态阈值机制按需求分配，避免某个端口独占全部缓冲。

队列是缓冲区的逻辑组织方式。每个出口端口按优先级分成多个队列，调度器按策略决定哪个队列先发。队列数决定了服务质量能分多细——队列太少，不同业务的流量挤在一起；队列太多，管理开销上升。严格优先级、加权轮转、加权公平排队是常见调度算法，实际芯片往往支持多种算法的组合。

深入理解这一段，要抓住"缓冲是拥塞的物理载体"这句话。没有拥塞时，报文几乎不在缓冲里停留，直通转发的时延主要来自流水线各阶段；一旦目标端口速率低于入口汇聚速率，报文开始在队列里堆积，时延随之上升，队列满就开始丢包。所有拥塞控制机制——无论是主动丢包、显式标记还是暂停帧——本质上都是在管理这段缓冲的占用。理解了这一点，后面看拥塞控制就不会觉得是一堆孤立的开关。

## SWPIPE-08 拥塞控制：队列满了怎么办

缓冲段的队列会满，这是高密度端口环境的常态而不是异常。拥塞控制处理的核心问题是：队列快满时，是被动等它满了丢包，还是提前干预；是丢弃报文，还是标记让发送端减速；是整端口暂停，还是只影响特定流量。

被动丢包是最简单的，队列满了就丢尾部的报文，叫尾部丢弃。它的问题是丢包没有区分，重要和不重要的流量一起丢，而且发送端要等超时才知道丢了，恢复慢。主动队列管理改进了这一点：在队列还没满时按概率丢弃或标记，提前给发送端减速信号。加权随机早期检测是典型代表，它按队列深度计算丢弃概率，还能对不同优先级设置不同阈值。

显式拥塞通知是另一种思路：不丢包，而是在报文头里打一个"经历拥塞"的标记，接收端收到后通知发送端减速。它的好处是不丢数据，适合对丢包敏感的场景，代价是需要端侧配合。在数据中心无损网络里，显式拥塞通知与基于优先级的流控配合使用：流控负责在极端情况下不让队列溢出，显式拥塞通知负责在平时让发送端平滑降速。

基于优先级的流控是链路层的暂停机制。当某优先级队列快满时，交换机向上游发暂停帧，要求暂时停止发送该优先级的流量。它彻底避免了该类流量的丢包，是无损网络的基础，但也有副作用——暂停可能向上游传播形成队头阻塞，甚至造成死锁。所以工程上强调"流控加显式拥塞通知"的组合，用流控兜底、用显式拥塞通知做主调节。

下表对比几种手段的特点，便于理解为什么生产环境强调组合使用。

| 手段 | 作用位置 | 是否丢包 | 主要副作用 |
|---|---|---|---|
| 加权随机早期检测 | 队列上升期 | 概率丢弃 | 低优先级流量被多丢 |
| 显式拥塞通知 | 队列上升期 | 不丢包 | 需要端侧配合 |
| 基于优先级的流控 | 队列临界期 | 不丢包 | 队头阻塞与传播风险 |
| 尾部丢弃 | 队列溢出时 | 直接丢弃 | 无区分、恢复慢 |

一个常被误解的点要澄清：拥塞控制不是在配置里打开某个开关就万事大吉。这些机制有参数——阈值、概率、权重、暂停时长——需要根据实际流量特征调优。在人工智能训练网络里，象流和微突发共存，参数没调好就会出现"明明开了无损，还是丢包"或者"暂停帧满天飞，吞吐反而下降"。判断拥塞控制是否生效，要看队列深度曲线、暂停帧计数、显式拥塞标记计数这些遥测数据，而不是只看配置有没有下发。

## SWPIPE-09 组播与复制：一份报文变多份

有些转发不是一对一的，广播、组播和未知单播都要把一份报文复制成多份送到不同端口。这件事放在流水线的哪一段做，直接影响性能和资源消耗。

复制可以在入口做，也可以在出口做。入口复制在报文刚进入时就生成多个副本，每个副本走自己的交换路径；出口复制则让报文先以一份的形式到达交换网，在出口段再复制。两种方式的取舍在于：入口复制会成倍消耗交换网带宽，因为多个副本都要穿过交换网；出口复制让报文在交换网里只占一份，到出口再展开，节省内部带宽，但需要出口侧有复制能力。

复制还涉及 VLAN 成员关系和生成树状态。报文要复制给哪些端口，取决于目标虚拟局域网的成员端口，以及这些端口在生成树里是否处于转发状态。被生成树阻塞的端口不能转发，即使它是虚拟局域网成员。这就是为什么基础知识里强调"泛洪决策要结合生成树状态"——复制不是简单地向所有成员端口发，而是要先过滤掉阻塞端口。

大规格组播对芯片是个考验。一份报文复制到几百个端口，需要在镜像处理和缓冲管理上做特殊设计，否则会耗尽资源。高端芯片通常有专门的复制引擎和组播缓冲管理，把副本的元数据而非整个报文在内部传递，到出口才真正生成完整报文。

下图把入口复制与出口复制两条路径画在一起，对比它们的资源消耗位置。

node n1 "入口报文<br/>一份" blue
node n2 "入口复制<br/>生成多个副本" teal
node n3 "交换网<br/>多份穿越" amber
node n4 "交换网<br/>一份穿越" green

下表总结两种复制方式的取舍。

| 维度 | 入口复制 | 出口复制 |
|---|---|---|
| 复制时机 | 进入交换网之前 | 到达出口之后 |
| 交换网带宽 | 多份副本占用，消耗大 | 一份占用，消耗小 |
| 对出口要求 | 出口只需发送 | 出口需要复制能力 |
| 适用场景 | 小规模组播、简单实现 | 大规模组播、高带宽场景 |

排障时的一个线索：如果只有组播流量出问题、单播正常，不要去查单播转发表和路由表。先看虚拟局域网成员关系、生成树状态和组播转发表，再确认复制引擎的资源有没有耗尽。组播问题表现为"该收到的端口没收到"或"不该收到的端口收到了"，与单播的"通或不通"是完全不同的现象分类。

## SWPIPE-10 出口段：策略、改写与串行化

报文被调度选中后进入出口处理段。这一段的目标是把入口做的决策落地成对报文的实际修改，并准备好从端口发出。虽然叫"出口"，它做的事一点不少——很多在入口无法确定的处理，必须等到知道具体出口才能做。

出口处理首先执行出口策略。出口访问控制列表可以按出口端口做过滤，出口服务质量可以做重新分类和整形。然后是改写，这是出口段最核心的工作：三层转发要重写二层目的地址和源地址、递减生存时间、重算校验和；加虚拟局域网标签的端口要插入标签，剥标签的端口要去掉标签；隧道场景要封装或解封装。这些改写动作在入口是无法完成的，因为同一个报文从不同端口出去，改写内容不同。

改写动作在芯片里通常不是直接改原始报文，而是生成一组改写指令，在报文发送前按指令重排字节——可以把它理解为固定硬件里的"反解析"或重组过程。指令可能包括删除若干字节、插入一段预存模板、替换某个字段。把改写做成指令而非直接操作，是为了让同一套硬件支持不同组合的改写，这在固定功能芯片里是兼顾灵活性与线速的常用手段。

最后是串行化：把处理好的报文按端口速率转成比特流发出。这一段要处理帧间隙、最小帧长填充、物理编码子层编码。发送侧的速率必须与端口配置一致，否则会出现错包。

图中节点速览：n1 是被调度选中、准备发送的报文；n2 执行出口策略，做过滤和重新分类；n3 根据出口端口生成改写指令，不同端口的指令不同；n4 按指令重组报文，真正执行改写；n5 做串行化，把报文转成比特流并完成编码；n6 是出口端口，把信号送到线路上。整张图说明出口段的关键在于"按端口定制"——同一个报文去不同端口，n3 生成的改写指令不同，这是为什么改写必须放在出口而非入口。

下面用伪代码表达改写指令的生成与执行，帮助理解为什么改写是一种"编排"而非简单修改。

```c
/* 工程理解伪代码：出口改写指令的生成与执行 */
struct rewrite_plan {
    int  strip_vlan;
    int  push_vlan;
    uint16_t vlan_id;
    int  rewrite_l2;             /* 是否重写二层地址 */
    uint8_t new_dst_mac[6];
    uint8_t new_src_mac[6];
    int  dec_ttl;                /* 是否递减生存时间 */
};

struct rewrite_plan build_plan(struct decision *d, int egress_port)
{
    struct rewrite_plan p = {0};
    if (d->is_l3) {              /* 三层转发才需要这些改写 */
        p.rewrite_l2 = 1;
        copy_mac(p.new_dst_mac, d->adj.next_hop_mac);
        copy_mac(p.new_src_mac, port_mac(egress_port));
        p.dec_ttl = 1;
    }
    if (port_tagging_mode(egress_port) == TAG)
        p.push_vlan = 1;         /* 该出口要求带标签 */
    return p;
}

void apply_plan(struct packet *pkt, struct rewrite_plan *p)
{
    if (p->rewrite_l2)
        replace_l2_header(pkt, p->new_dst_mac, p->new_src_mac);
    if (p->dec_ttl)
        decrement_ttl_and_rechecksum(pkt);
    if (p->push_vlan)
        insert_vlan_tag(pkt, p->vlan_id);
}
```

对这段伪代码的判读：`build_plan` 以入口决策和目标端口为输入，说明改写内容是"按出口定制"的——同一个决策去不同端口，`port_tagging_mode` 不同，生成的计划就不同；`is_l3` 决定是否重写二层地址和递减生存时间，这对应三层转发的出口处理；`apply_plan` 才真正修改报文，把计划落地。把生成和执行分开，正是硬件里"改写指令加重组"模式的软件映射——先生成一组指令，再按指令重排字节。要注意这段伪代码不表示真实芯片的调用顺序，真实实现里这些动作由硬件在报文通过出口阶段时自动完成，开发者能通过配置控制的是改写策略，而不是逐包调用。

## SWPIPE-11 单遍与多遍：决定隧道性能的分水岭

前面的流水线假设报文从头走到尾只经过一次，这叫单遍处理。但在分布式网关这类场景里，一个报文可能需要做两次性质不同的处理：先解封装外层隧道，再按内层地址路由，然后可能还要重新封装。如果芯片不能在一次通过中完成这些动作，就必须把报文送回入口重走一遍流水线，这叫多遍处理。

单遍和多遍的差别不只是"多走一次"那么简单。多遍处理意味着报文要重新进入入口、重新查表、重新占用缓冲和交换网资源，吞吐接近减半，时延成倍增加。更麻烦的是，多遍处理会消耗额外的缓冲带宽和内部循环资源，在高负载时成为瓶颈。因此高端芯片把"单次虚拟扩展局域网"作为重要卖点——它保证解封装、路由、再封装在一次通过内完成。

判断一个芯片能否单遍处理某个功能组合，要看两点：解析深度够不够（能不能在一次解析里同时看到外层和内层字段），以及查表级数够不够（能不能在同一条依赖链上串起解封装查表、路由查表、封装查表）。这两点都受阶段资源约束，这正是为什么阶段数是选型的关键参数。

下图对比单遍和多遍两种路径，标出多遍带来的额外开销。

:::figure id=SWPIPE-11-01 | name=单遍处理与多遍处理的路径对比 | dir=TB

node n2 "单遍<br/>解封装加路由加封装" green
node n3 "一次出口<br/>直接发出" teal
node n4 "多遍第一遍<br/>解封装后送回入口" amber
node n5 "多遍第二遍<br/>重新解析与封装" purple

图中节点速览：n1 是收到隧道报文的入口；上方单遍路径由 n2 在一次通过中完成解封装、路由和封装，n3 直接从出口发出；下方多遍路径由 n4 在第一遍解封装后把报文送回入口，n5 在第二遍重新解析和封装，n6 经过两次出口，时延和吞吐都受损。整张图说明单遍与多遍的分歧在于处理链能否在一条流水线里排完，排不下就必须回炉重走。

下表列出影响单遍处理能力的可核对参数。

| 参数 | 作用 | 不足时的后果 |
|---|---|---|
| 解析深度 | 能否一次看到内外层字段 | 深层字段不可见，功能失效 |
| 查表级数 | 能否串起多次查表 | 超出则必须多遍 |
| 改写能力 | 能否一次完成多层改写 | 封装解封装分多次 |
| 内部回环资源 | 多遍时能否高效回送 | 多遍吞吐进一步下降 |

选型时有一个实用判断：把你要用的功能组合列出来——比如"虚拟扩展局域网加三层路由加访问控制加服务质量标记"——逐项问厂商能不能在一次通过内完成，并要求提供带载测试数据。不要只看功能清单里"支持虚拟扩展局域网"，因为"支持"和"单遍支持"是两回事。这个功能组合能否单遍完成，往往就是不同价位芯片的分水岭。

## SWPIPE-12 时延模型：时延花在哪里

流水线时延是岗位面试和方案设计里的高频话题，但常被说得含糊。要把时延讲清楚，得先分清两种转发模式，再拆开时延的组成部分。

直通转发指芯片收到报文的目的地址、做出转发决策后就开始发送，不必等整个报文收完。它的时延低且基本与报文长度无关——决定时延的是"处理到能做出决策"这一段。存储转发则要先收完整报文、校验无误后再转发，时延与报文长度成正比——长报文要花更长时间接收。两种模式没有绝对优劣：直通时延低但可能转发坏帧，存储转发能隔离错误但时延高。数据手册里标称的"低至多少纳秒"通常是直通模式的最优值，实际网络里开启各种功能后会漂移。

时延的组成部分可以拆成几块：物理层和前向纠错的固定时延，解析与查表的处理时延，交换网搬运时延，排队时延，出口改写与串行化时延。其中前几块是固定的、可预期的，属于芯片的确定性时延；排队时延是可变的，取决于拥塞程度，是尾时延的主要来源。所谓"确定性低时延"，重点不是平均值多低，而是可变部分多小——这解释了为什么缓冲区设计和拥塞控制对时延如此重要。

下表把时延的组成部分、是否可变和优化方向列出来。

| 组成 | 是否可变 | 影响因素 | 优化方向 |
|---|---|---|---|
| 物理层与纠错 | 固定 | 编码方式、纠错开销 | 由芯片设计决定 |
| 解析与查表 | 基本固定 | 阶段数、依赖链长度 | 减少级数、合并表 |
| 交换网搬运 | 基本固定 | 管道结构、内部带宽 | 保证带宽余量 |
| 排队 | 高度可变 | 拥塞程度、队列策略 | 拥塞控制、缓冲管理 |
| 出口改写与串行 | 固定 | 改写复杂度、端口速率 | 减少改写步骤 |

延迟排障要抓住"可变部分"。如果平均时延正常但尾时延高，问题几乎一定在排队这一段，去查拥塞、象流和微突发；如果所有报文时延都高且稳定，问题在固定部分，去查功能开启情况——是不是开了存储转发、是不是叠了多遍处理、是不是隧道解析很深。这个二分法能快速缩小排查范围。

## SWPIPE-13 真实芯片对照：公开到什么程度

把流水线的一般原理讲清楚后，回到具体芯片，必须诚实说明各厂商公开到什么程度——这直接决定你能依据什么做判断，哪些数字不能自己编。

博通 Tomahawk 系列没有公开逐阶段的微架构细节，比如具体的解析阶段数量、表项查找级数、内部模块名称。网上流传的所谓流水线框图多为第三方推测或基于早期产品的示意。因此能可靠引用的只有官方明确披露的能力点：线速二层三层转发、单次虚拟扩展局域网、大吞吐包缓冲架构、自适应路由和动态负载均衡、硬件链路切换。涉及具体阶段数和表项容量的数字，必须以官方数据手册和客户资料为准，不能用推测值。

Marvell Teralynx 系列相对开放，官方产品简介公开了功能框图。可以据此描述它的转发路径：端口与物理编码子层、入口策略与监管、二层三层转发与隧道、低时延交换网与大包缓冲、出口策略与重写。贯穿其中的是可置换弹性转发，表示协议相关逻辑可以通过软件加载。但这份框图是功能级的，仍不涉及解析阶段数、表项容量这类微架构数字。

Marvell Prestera 系列的情况又不同。它的软件开发套件源码里沉淀了大量资源信息——按器件配置档逐项定义的转发表容量、隧道表容量、路由下一跳数量、缓冲规格、流水线带宽。这些是SDK 内部的一手数据，但不是对外产品文档，引用时要说明来源是开发工具包而非公开规格书。

下表把三类芯片的流水线信息公开程度对比列出，明确每条信息的来源。

| 芯片系列 | 公开内容 | 未公开内容 | 可靠来源 |
|---|---|---|---|
| 博通 Tomahawk | 功能能力点、缓冲架构理念 | 解析阶段数、查表级数、模块名 | 官方新闻稿与产品简介 |
| Marvell Teralynx | 功能级框图、时延量级 | 微架构阶段数、表项容量 | 官方产品简介 |
| Marvell Prestera | 器件配置档与资源规格 | 详细时序与电气参数 | 软件开发套件源码 |

这里要建立一个重要的工程态度：面对未公开的信息，正确做法是标注"未公开、需以数据手册为准"，而不是找一张网上的示意图当成事实。岗位面试里，能说清楚"我知道这一层是公开的、那一层厂商没披露、要查文档确认"的人，比背了一堆来路不明数字的人更可信。流水线参数尤其如此——阶段数、查表级数、单遍能力，每个都直接影响方案成败，容不得编造。

## SWPIPE-14 从流水线视角看排障

学完流水线，最后要把它变成排障能力。排障的本质是把现象映射到阶段，再用该阶段的可观测手段验证。前面各章其实已经埋下了映射关系，这里系统整理一遍。

物理层问题的特征是链路不稳定、误码和校验错误计数增长，现象集中在端口 down 或 crc 错误，与转发逻辑无关。解析层问题的特征是深层字段失效——报文通了但基于内层字段的策略不生效，典型诱因是隧道嵌套过深或扩展头太多。查表层问题的特征是转发方向错误或表项加不进去，前者查键构造和依赖顺序，后者查表容量。缓冲与拥塞层问题的特征是时延抖动、尾时延高、丢包集中在突发时，要看队列深度和拥塞标记计数。出口改写出问题的特征是报文出去后头部不对——标签没加、地址没改、校验和错，现象是"通了但格式不对"。

下表把现象、可疑阶段和验证手段对应起来，作为排障速查表。

| 现象 | 可疑阶段 | 验证手段 |
|---|---|---|
| 端口起不来、误码高 | 物理层与编码 | 端口计数器、光模块信息 |
| 报文通但内层策略失效 | 解析层 | 解析深度核对、字段可见性 |
| 转发方向错误 | 查表层 | 转发表项、键构造、依赖顺序 |
| 表项加不进去 | 查表层资源 | 表容量、资源档位 |
| 尾时延高、突发丢包 | 缓冲与拥塞 | 队列深度、暂停帧、拥塞标记 |
| 通了但报文头不对 | 出口改写 | 抓包对照、改写策略配置 |

排障方法论可以浓缩成一句话：先按现象定位阶段，再用该阶段的计数器验证，不要在阶段之外乱猜。流水线的价值就在这里——它给了你一张地图，让你知道每一步会发生什么、每一步出问题会表现出什么现象。没有这张地图，排障只能靠试；有了它，排障是有方向的推理。

回看全篇，从端口接入到解析、查表、分类、交换、缓冲、拥塞、复制、出口改写、串行化，一个报文走完了完整旅程。每一段都有明确的任务、明确的资源约束、明确的失效现象。把这张图景装进脑子里，再去读任何一款交换芯片的数据手册，你都能知道它描述的每个参数落在流水线的哪个位置、影响哪一段行为。这正是从"会配交换机"到"懂交换机"的分界线。
