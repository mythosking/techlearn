# 交换机二三层功能与协议开发：从业务语义到芯片落地

## L2L3-01 先建立坐标系：什么是“二三层功能开发”

交换芯片资料里已经讲过转发流水线：报文怎么被解析、查表、改写、转发。这篇讲另一件事——**业务功能与协议开发**。二者关系可以这样理解：流水线是芯片提供的“能力”，二三层功能是网络操作系统用这些能力“实现出来的业务”。比如芯片提供 MAC 学习和 FDB 查表能力，工程师在此基础上实现 VLAN 隔离、端口安全、MAC 漂移抑制等功能；芯片提供 LPM 和邻接表能力，工程师在此基础上实现静态路由、动态路由对接、VRRP 网关冗余等特性。

岗位要求里“有二三层功能或者协议开发经验者优先”，指的就是这种能力：你不仅要知道 STP 是什么，还要知道在自研交换机上怎么把它做出来、怎么和芯片 SDK 对接、怎么和 FRR 这类控制面协议配合。这是区分“会配置网络”和“能开发交换机软件”的关键。

二三层功能开发通常横跨三个层面：**控制面协议**（运行协议、算状态，如 STP 计算拓扑、LLDP 发现邻居）、**管理层**（配置下发、状态展示，如 CLI/数据库）、**数据面落地**（把决策变成芯片表项）。一个完整特性往往要三层都动。理解这个跨层结构，才能把一个功能从需求讲到代码。

下表把常见二三层功能按层次归类，方便建立全局视野。

| 层次 | 二层功能 | 三层功能 | 主要协议或机制 |
|---|---|---|---|
| 控制面 | STP、LLDP、LACP | 路由协议、VRRP、BFD | 协议状态机 |
| 数据面 | VLAN、MAC 学习、FDB | 路由表、邻接表、ECMP | 芯片表项 |
| 管理层 | 端口配置、VLAN 配置 | 接口地址、静态路由 | 数据库与 CLI |
| 运维面 | MAC 表、STP 状态 | 路由表、邻居状态 | show 命令与遥测 |

这篇按功能族展开：先讲二层的值 VLAN 与 MAC、防环与发现，再讲链路聚合，然后进入三层的邻居、路由与网关冗余，最后是组播、QoS 和开发落地视角。

## L2L3-02 VLAN、端口类型与 MAC 学习：二层的地基

VLAN 是二层最基础的功能，它把一个物理交换机逻辑上切成多个广播域。802.1Q 在以太网帧里插入 4 字节标签，其中 12 位 VLAN ID 标识所属 VLAN。端口按处理方式分三类：**access 口**只属于一个 VLAN，进出帧不带标签；**trunk 口**可承载多个 VLAN，帧带标签传输，用于交换机互联；**hybrid 口**综合两者，可灵活控制标签的保留与剥离，在某些厂商设备和数据中心场景常见。

MAC 学习是二层转发的另一块地基。交换机收到帧时，记录“源 MAC + 源 VLAN + 入端口”的对应关系写入 FDB（转发数据库）；转发时按“目的 MAC + VLAN”查 FDB，命中则从指定端口转发，未命中则向 VLAN 内所有其他端口泛洪。FDB 表项有老化时间，长期不更新的表项会被删除，以适应终端位置变化。理解这套机制，才能解释为什么二层会泛洪、为什么会有 MAC 漂移。

下表对比三种端口类型的标签处理行为。

| 端口类型 | 入方向处理 | 出方向处理 | 典型用途 |
|---|---|---|---|
| access | 无标签帧打上端口默认 VLAN | 剥离标签发送 | 接终端主机 |
| trunk | 接收带标签帧，校验允许列表 | 保留标签发送（本征 VLAN 除外） | 交换机互联 |
| hybrid | 可配置是否接受无标签帧 | 可按 VLAN 决定是否带标签 | 复杂组网、IP 电话 |

下表列出 MAC 学习的常见开发要点。

| 开发要点 | 说明 | 芯片对接 |
|---|---|---|
| 老化时间 | FDB 表项超时删除 | 配置芯片老化定时器 |
| MAC 漂移 | 同一 MAC 在不同端口出现 | 上报事件或抑制更新 |
| 静态表项 | 手工配置不老化 | 下发静态 FDB 表项 |
| 端口安全 | 限制端口学习 MAC 数量 | 学习上限与违例动作 |

VLAN 和 MAC 学习看似基础，却是所有二层功能的地基，bonding、隧道、VXLAN 都建立在它之上。

## L2L3-03 STP、RSTP 与 MSTP：二层防环的实现视角

二层网络一旦出现环路，广播帧会无限循环，瞬间击穿带宽——这就是广播风暴。生成树协议（STP，802.1D）通过在交换机之间选举根桥、计算无环树、阻塞冗余链路来消除环路。它的基本单位是端口状态：禁用、阻塞、监听、学习、转发。根桥定期发配置消息，其他交换机转发并维护到根的最短路径；当拓扑变化，阻塞端口可以被激活，实现链路冗余。

STP 收敛慢（典型 30 到 50 秒），于是有了快速生成树 RSTP（802.1w），把端口角色细化为根端口、指定端口、替代端口、边缘端口，引入提议—同意（proposal-agreement）机制，把收敛压到秒级甚至亚秒级。多生成树 MSTP（802.1s）进一步把多个 VLAN 映射到少数几个生成树实例，在不同实例里阻塞不同链路，实现链路负载分担，避免单生成树把所有 VLAN 都压在同一条路径上。

从开发视角看，STP 的难点不在协议报文本身，而在**协议状态与芯片转发表的同步**。STP 决定某个端口阻塞后，必须立即让芯片停止在该端口的转发，否则协议层阻塞了、数据面还在转发，环路依然存在。这要求 STP 模块和芯片端口状态之间有可靠的联动接口。

下表对比三种生成树协议。

| 协议 | 标准 | 收敛速度 | VLAN 处理 | 适用场景 |
|---|---|---|---|---|
| STP | 802.1D | 30 至 50 秒 | 所有 VLAN 共用一棵树 | 老旧网络、兼容保守 |

| MSTP | 802.1s | 秒级 | 多 VLAN 映射多实例 | 大型网络、链路分担 |

下表列出防环相关的开发注意点。

| 注意点 | 说明 |
|---|---|
| 边缘端口 | 接终端的端口跳过监听学习，直接转发 |
| BPDU 保护 | 边缘端口收到 BPDU 则自动阻塞，防止私接交换机 |
| 根保护 | 限制端口成为根端口，保护根桥地位 |
| TC 处理 | 拓扑变化时正确刷新 FDB，避免临时错转 |

## L2L3-04 LLDP 与链路发现：让拓扑可见

链路层发现协议 LLDP（802.1AB）让网络设备向邻居宣告自己的身份和能力，同时接收邻居的宣告。每台设备周期性发送 LLDP 帧，帧里携带设备标识、端口标识、系统名称、能力集、管理地址等 TLV（类型—长度—值）信息。设备把收到的信息存进邻居表，运维人员通过 `show lldp neighbors` 就能看到“本端口连着谁”。这是网络拓扑自动发现、资产梳理和故障定位的基础。

LLDP 本身不参与转发决策，但它是很多高级功能的前置条件：数据中心里用它做链路自动布线核对，运营商网络里用它传递远端端口描述，一些自动化系统用 LLDP 邻居关系自动构建拓扑图。开发 LLDP 的要点是 TLV 的正确编解码、邻居表的老化维护，以及与 SNMP/遥测的对接。

下面是一段 LLDP 的配置与查看示例。

```text
# 全局开启 LLDP 并配置发送周期
configure terminal
 lldp enable
 lldp timer 30
 lldp holdtime 120
!
interface Ethernet1
 lldp transmit
 lldp receive
!
end
# 查看邻居信息
show lldp neighbors
show lldp neighbors detail
```

对这段配置的判读：`lldp enable` 全局启用协议，`lldp timer 30` 设置每 30 秒发送一次宣告，`lldp holdtime 120` 设置邻居信息 120 秒无更新则老化；接口下 `lldp transmit` 和 `lldp receive` 分别控制该端口是否发送和接收 LLDP 帧；最后两条 show 命令查看邻居摘要和详情。开发时要注意 holdtime 通常是 timer 的整数倍，且邻居表的老化要精确到端口粒度。

下表列出 LLDP 常见 TLV 及其用途。

| TLV | 携带信息 | 用途 |
|---|---|---|
| Chassis ID | 设备标识（常为 MAC） | 唯一识别邻居设备 |
| Port ID | 端口标识 | 识别对端具体端口 |
| System Name | 系统名称 | 人可读的设备名 |
| System Capabilities | 能力集（桥、路由等） | 判断邻居设备类型 |
| Management Address | 管理地址 | 便于管理层访问 |
| Port Description | 端口描述 | 布线与端口用途说明 |

LLDP 是“小功能大价值”的典型，实现不难，却是网络可观测性不可缺少的一环。

## L2L3-05 LACP 链路聚合：把多条物理链路当一条用

链路聚合把多条物理链路捆绑成一条逻辑链路，既增加带宽又提供冗余。静态聚合由手工配置，不协商；动态聚合用 LACP（802.3ad/802.1AX），通过 LACPDU 报文协商成员端口，自动检测链路故障并切换。聚合组（LAG）对上层协议呈现为一个逻辑接口，MAC 学习、路由、STP 都把它当作一条链路看待。

LACP 的关键概念包括：聚合组（Aggregator）、成员端口的选中/未选中状态、主备链路、以及分布式哈希。流量在成员链路间按哈希分担，哈希键常包含源目的 MAC、源目的 IP、四层端口等。哈希的关键是**同一条流始终走同一成员链路**，否则报文乱序会严重影响 TCP 性能。这就是“per-flow 哈希”而非“per-packet 哈希”的原因。

从开发视角看，链路聚合牵涉数据面的两条链路：一是聚合组到成员端口的映射表，二是哈希引擎。芯片通常用 LAG 表把聚合组 ID 映射到成员端口集合，再由哈希结果选出具体成员。开发要保证成员状态变化时映射表及时更新，且哈希稳定——成员增减时尽量只影响受影响的流（resilient hashing），避免大面积重哈希导致流量抖动。

|---|---|---|

| 配置复杂度 | 低 | 中 |
| 适用场景 | 简单互联 | 生产网络主流 |

|---|---|
| 哈希键选择 | 依据业务选择二层和三层哈希字段 |
| 弹性哈希 | 成员变化时减少受影响的流 |
| 成员上下线 | 及时更新映射表，避免黑洞 |
| 跨设备聚合 | MLAG/堆叠场景下的分布式聚合 |

## L2L3-06 ARP 与邻居发现：三层转发的地址 glue

三层转发要知道“下一跳的 MAC 是什么”，这个映射由 ARP（IPv4）和 ND（IPv6 邻居发现）提供。主机或交换机要发包给同网段的下一跳时，先查 ARP 表；查不到就发 ARP 请求广播，目标回复 ARP 应答，双方各自缓存映射。ARP 表项有老化时间，且会被 gratuitous ARP（免费 ARP）更新——这也带来 ARP 欺骗的风险面。

在交换机里，ARP 处理有个重要分工：**控制面 CPU 处理 ARP 协议报文，数据面 ASIC 维护 ARP 表项用于转发**。收到 ARP 请求，如果目标 IP 是本机接口地址，报文上送 CPU 回复；如果是转发请求，CPU 生成 ARP 应答并同时把结果写入数据面邻接表。后续数据报文直接查邻接表改写二层头，不再上送 CPU。理解这个分工，才能明白为什么“ARP 没学会”会导致转发失败。

下表对比 ARP 与 IPv6 邻居发现。

| 对比项 | ARP（IPv4） | ND（IPv6） |
|---|---|---|
| 报文类型 | ARP 请求与应答 | NS/NA/RS/RA |
| 地址解析 | 广播请求 | 组播请求（被请求节点组播） |
| 重复地址检测 | 免费 ARP | DAD（重复地址检测） |
| 路由器发现 | 依赖 DHCP | RA 报文自动发现 |
| 安全性 | 无内建认证 | 可选 SEND 安全机制 |

下表列出 ARP 相关的开发要点。

| 要点 | 说明 |
|---|---|
| 表项老化 | 定期清理过期 ARP，避免陈旧邻接 |
| ARP 限速 | 防止大量 ARP 请求冲击 CPU |
| 代理 ARP | 代答其他网段 ARP，特殊场景使用 |
| 邻接状态联动 | 链路故障时及时失效相关邻接 |

ARP 看着简单，却是“三层能不能通”的第一道门槛，也是排障时最先要确认的环节。

## L2L3-07 三层转发与 FIB：路由怎么变成转发表

三层转发的核心是路由表和邻接表配合。路由表（FIB）回答“去某个目的网段该走哪个下一跳”，用最长前缀匹配（LPM）查找；邻接表回答“这个下一跳的 MAC 是多少、从哪个口出去”，用于改写二层头。一次三层转发就是：按目的 IP 查 FIB 得到下一跳，再查邻接表得到二层封装信息，改写报文后从出端口发出。TTL 递减、校验和更新也在这一步完成。

路由来源多样：直连路由由接口地址自动生成，静态路由手工配置，动态路由由 OSPF/IS-IS/BGP 等协议计算。这些路由进入主路由表前要经过选路：不同协议有不同管理距离（AD），数值越小越优先；同协议内按各自度量选优。FRR 这款文档已经详细讲了 BGP 选路，这里补充的是更上游的“多协议路由如何汇总到内核 FIB”的视角。

ECMP（等价多路径）是三层转发的重要能力：当到同一目的有多条等价下一跳时，芯片按哈希把不同流分到不同路径，充分利用带宽。ECMP 表项是 FIB 表项的扩展，从“指向一个下一跳”变成“指向一组下一跳”。开发要保证 ECMP 成员变化时哈希稳定，且与 LAG 哈希协调——先选 ECMP 路径，再在路径内的 LAG 里选成员，两级哈希要有不同的盐值避免相关性。

:::figure id=L2L3-07-01 | name=三层转发查表与封装流程 | dir=LR
node n1 "目的 IP" blue
node n2 "FIB 最长前缀<br/>匹配" teal
node n3 "得到下一跳<br/>与 ECMP 组" amber
node n4 "邻接表<br/>查 MAC 与出接口" green
node n5 "改写二层头<br/>TTL 递减 转发" purple

:::

图中节点速览：n1 是报文的目的 IP；n2 在 FIB 里做最长前缀匹配；n3 得到下一跳，可能是 ECMP 组；n4 查邻接表得到下一跳 MAC 和出接口；n5 改写二层头、递减 TTL 后转发。整张图把三层转发拆成“查路由—查邻接—改写”三步，对应芯片里的两张关键表。

|---|---|---|
| 直连路由 | 0 | 接口地址自动生成，最可信 |
| 静态路由 | 1 | 手工配置 |

| IS-IS | 115 | 链路状态 IGP |
| BGP（eBGP） | 20 | 外部网关协议 |

下表列出三层转发的开发要点。

| 要点 | 说明 |
|---|---|
| LPM 表容量 | 芯片表项有限，需关注前缀规模 |
| 邻接可达性 | 下一跳不可达时路由要标记无效 |
| ECMP 哈希 | 成员变化时的稳定性与重哈希 |
| FIB 与 RIB 一致 | 控制面决策与数据面表项保持一致 |

三层转发是交换机的核心业务，也是笔试面试的高频考点，务必把 FIB 与邻接表的关系讲清楚。

## L2L3-08 VRRP 与网关冗余：默认网关的高可靠

终端访问外部网络要靠默认网关。如果网关设备宕机，整个网段的通信就中断了。VRRP（虚拟路由冗余协议）把多台路由器组成一个虚拟路由器，共享一个虚拟 IP 作为网关。组内一台为主（Master）承担转发，其余为备份（Backup）；主故障后，备份通过优先级选举接管虚拟 IP，终端无感知。这样就把单点网关变成高可靠网关。

VRRP 用组播通告报文（224.0.0.18）维持主备关系，主定期发送通告，备份在超时未收到后升级为主。优先级决定选举结果，取值范围 1 到 254，255 保留给 IP 地址拥有者。抢占模式决定高优先级备份是否主动夺回主角色。从开发视角看，VRRP 状态切换要联动两处数据面：一是虚拟 IP 对应的邻接或路由表项，二是免费 ARP 广播，让上游和终端更新 MAC 映射，否则流量还会发往旧主。

下图是 VRRP 主备切换与数据面联动。

:::figure id=L2L3-08-01 | name=VRRP 主备切换与数据面联动 | dir=LR

node n2 "备份监听<br/>超时判定" teal
node n3 "选举新主<br/>按优先级" amber
node n4 "接管虚拟 IP<br/>更新表项" green

:::

图中节点速览：n1 是主设备定期发送通告；n2 备份监听并在超时后判定故障；n3 按优先级选举新主；n4 新主接管虚拟 IP 并更新数据面表项；n5 发送免费 ARP 让网络刷新 MAC 映射。整张图强调切换不只是协议状态变化，还要刷新数据面和网络邻居认知。

下表是 VRRP 关键参数说明。

| 参数 | 作用 | 典型取值 |
|---|---|---|
| 虚拟路由器 ID | 标识一个 VRRP 组 | 1 至 255 |
| 虚拟 IP | 终端的默认网关地址 | 网段内可用地址 |
| 优先级 | 决定主备选举 | 1 至 254 |
| 通告间隔 | 主发送心跳周期 | 1 秒 |
| 抢占模式 | 高优先级是否夺回主角色 | 默认开启 |

下表列出 VRRP 与相关技术的对比。

| 技术 | 层次 | 特点 |
|---|---|---|
| VRRP | 三层网关冗余 | 标准协议，多厂商互通 |
| HSRP | 三层网关冗余 | 厂商私有，类似 VRRP |
| VRRP-E | 三层网关冗余 | 扩展版本，增强特性 |
| 堆叠或 MLAG | 设备级冗余 | 把多台设备虚拟成一台 |

VRRP 是“网关高可用”的标准答案，也是园区和数据中心边缘的常见配置。

## L2L3-09 组播、广播控制与 IGMP Snooping

二层默认对组播和广播帧泛洪，这在有大流量组播时会造成严重浪费。IGMP Snooping 让交换机监听主机与路由器之间的 IGMP 报文，了解哪个端口加入了哪个组播组，从而把组播帧只转发给真正感兴趣的端口，而不是泛洪。交换机维护一张组播转发表，键是 VLAN 加组播地址，值是成员端口集合。没有开启 IGMP Snooping 时，组播退化为广播泛洪。

广播控制方面，风暴抑制（storm control）限制广播、组播、未知单播三类流量占端口带宽的比例，超过阈值就丢弃或限速，防止广播风暴拖垮网络。DHCP Snooping 通过信任端口机制防止非法 DHCP 服务器，并生成绑定表供后续 ARP 防护使用。这些功能共同构成二层的安全与稳定性防线。

下表把组播与广播控制相关功能汇总。

| 功能 | 作用 | 数据面表项 |
|---|---|---|
| IGMP Snooping | 按需转发组播帧 | 组播组成员表 |
| 风暴抑制 | 限制广播组播未知单播速率 | 端口限速计数器 |
| DHCP Snooping | 防非法 DHCP 服务器 | DHCP 绑定表 |
| ARP 防护 | 基于绑定表校验 ARP | ARP 检测表 |

下表列出 IGMP Snooping 的开发要点。

| 要点 | 说明 |
|---|---|
| 查询器选举 | 确定由谁发送 IGMP 查询 |
| 成员老化 | 成员端口超时后从组播表移除 |
| 快速离开 | 处理 IGMP Leave 加快成员退出 |
| 与 MLD 对应 | IPv6 场景用 MLD Snooping |

组播与广播控制在视频分发、金融行情推送等场景尤为重要，是二层功能里容易被忽视但很实用的一块。

## L2L3-10 QoS、ACL 与功能落地到芯片的开发视角

QoS 和 ACL 是贯穿二三层的横切功能。QoS 通过流量分类、标记、排队、调度和丢弃策略，保证关键业务的服务质量——前面基础知识里已讲过 QoS 体系，这里从开发视角补充：QoS 的每一环都要落到芯片的对应表项和队列，比如分类对应 ACL 表，标记对应改写动作，调度对应端口队列配置。开发要做的是把管理层配置的策略翻译成芯片可执行的规则，并保证规则优先级一致。

ACL（访问控制列表）按规则匹配报文并执行允许或丢弃动作，是安全隔离和策略控制的基础。ACL 表项通常挂在 TCAM 里，支持按源目的 IP、端口、协议、VLAN 等多字段匹配。ACL 的执行顺序、优先级、以及与其他功能（如 QoS 分类）的共享，是开发中要仔细处理的问题——芯片 TCAM 资源有限，多个功能争用同一张表时要合理规划。

下面是一段 ACL 与 QoS 的配置示例，展示策略如何从管理层进入。

```text
configure terminal
 ip access-list extended ACL-GUARD
  permit tcp any any eq 179
  deny ip any any
 !
 class-map CM-NETWORK
  match access-group ACL-GUARD
 !
 policy-map PM-QOS
  class CM-NETWORK
   set dscp cs6
   priority
  class class-default
   set dscp default
 !
 interface Ethernet1
  service-policy input PM-QOS
 end
```

对这段配置的判读：先定义扩展 ACL“ACL-GUARD”，允许任何源到任何目的、目的端口为 179（BGP）的 TCP 流量，其余拒绝；class-map“CM-NETWORK”用这条 ACL 匹配流量；policy-map“PM-QOS”对匹配类设置 DSCP 为 CS6 并进入优先队列，默认类设为 default DSCP；最后在接口入方向应用该策略。开发视角下，这段配置会被翻译成 TCAM 表项（匹配规则）和队列配置（调度动作），下发到芯片。要注意 ACL 的 deny 与 QoS 的许可不是一回事，策略语义要在翻译时保持准确。

下表把功能开发的关键环节与芯片资源对应起来。

| 开发环节 | 管理层输入 | 芯片资源 | 一致性要点 |
|---|---|---|---|
| 功能配置 | 数据库与 CLI | 软件配置对象 | 配置校验 |
| 状态计算 | 协议与算法 | 决策结果 | 状态同步 |
| 表项翻译 | 决策结果 | TCAM、FDB、FIB、邻接 | 语义等价 |
| 硬件编程 | 表项 | 芯片寄存器与表 | 批量与事务 |
| 状态回读 | 芯片计数与状态 | 运维展示 | 可观测性 |

把二三层功能从“会用”做到“能开发”，核心就是掌握这张表的每一行：知道管理层配置怎么变成芯片表项，知道状态怎么在三层之间同步，知道怎么验证一致性。这正是岗位要求里“熟悉交换机业务功能、有二三层功能或协议开发经验”的实质。
