# P4 语言与可编程数据面：从协议无关架构到 P4Runtime

## P4LANG-01 先建立坐标系：P4 到底改变了什么

传统交换芯片的数据面是固定的：芯片出厂时就决定了它认识哪些协议、能查哪些表、能做哪些动作。要支持一个新协议，只能等芯片下一代流片。P4（Programming Protocol-independent Packet Processors）打破了这一点——它是一种专门用于描述包处理行为的领域特定语言，让你用代码定义“解析哪些报文头、查哪些表、执行什么动作”。同一份 P4 程序，经过不同目标编译器的编译，可以跑在软件交换机、ASIC、FPGA 或 DPU 上。

这里有两个关键词必须分清。**协议无关（protocol-independent）** 指的是芯片或目标不在硅片里固化协议逻辑，协议由 P4 程序描述；它不是说 P4 能解析任意协议——解析器能认什么、能查多深、能存多少状态，仍受目标硬件资源限制。**可编程（programmable）** 指的是数据面行为可以通过软件定义和重新编译改变，但改变的是“包处理逻辑”，不是控制面决策。P4 不替代 BGP 或控制器，它定义的是“怎么转发”，而不是“转发去哪”。

理解 P4 最好的对照是前面写过的固定流水线交换芯片。TOMAHAWK 6、TERALYNX 10 这类芯片的 Parser、Lookup、Rewrite 是固化的，功能全但不可改；P4 芯片把 Parser 和 Match-Action 阶段做成可编程的，牺牲一部分极致性能换取灵活性。岗位描述里“P4 可编程、在网计算、端网融合”，正是看中这种灵活性——可以在数据面里实现自定义隧道、遥测、负载均衡、在网聚合，而不必等芯片厂商支持。

| 典型代表 | 商用交换 ASIC | Tofino、软件交换机 |

P4 不是万能的，但当你需要在网络里做“芯片不认识的事”时，它几乎是唯一现实的选择。

## P4LANG-02 P4 数据面模型：Parser、Match-Action 与 Deparser

P4 程序的核心模型来自协议无关交换架构（PISA），它把包处理抽象成几个阶段：**Parser（解析器）** 按程序定义的状态机逐层识别报文头，把字段抽取到头部和元数据中；**Match-Action 流水线**由若干阶段组成，每个阶段查一张或多张表，根据匹配结果执行动作，动作可以修改字段、更新状态；**Deparser（反解析器）** 把处理后的头部重新序列化成报文发出。 ingress 和 egress 各有一套这样的处理，中间还夹着流量管理（Traffic Manager）做排队和调度。

这个模型的关键约束是：解析器只能抽取它认识的字段，后续表项只能匹配这些已抽取的字段。如果你想按某个自定义头部里的字段做转发，必须先在 Parser 里定义并解析这个头。这是 P4 编程最常见的思维转变——从“芯片认识所有字段”变成“我只认识我写出来的字段”。元数据（metadata）是流水线各阶段之间传递信息的载体，它不来自报文本身，而是芯片提供或程序计算的中间量，比如入端口、队列长度、哈希值。

下表列出 P4 数据面模型的关键概念。

| 概念 | 作用 | 类比固定芯片 |
|---|---|---|
| Header | 报文头字段集合 | 芯片认识的协议头 |
| Metadata | 阶段间传递的中间量 | 芯片内部标记 |
| Parser state | 解析状态机的状态 | 解析器状态 |
| Table | 匹配—动作规则表 | ACL、FDB、路由表 |
| Action | 匹配命中后执行的动作 | 转发、丢弃、改写 |
| Register | 可读写的有状态存储 | 芯片计数器与状态 |

理解这张表，就理解了 P4 程序的基本词汇。

## P4LANG-03 P4_16 语言要素：头、解析器、表与动作

P4 语言目前主流版本是 P4₁₆（语言规范 v1.2.5，2024 年 10 月）。一个最小的 P4 程序包含几个要素：用 `header` 定义报文头结构，用 `struct` 定义元数据，用 `parser` 定义解析状态机，用 `table` 和 `action` 定义匹配—动作逻辑，用 `control` 把各阶段组织起来，最后用 `package` 和 `main` 把程序实例化到具体架构上。

下面是一段精简的 P4₁₆ 代码示例，展示解析以太网头并按目的 MAC 查表转发的骨架。

```p4
#include <core.p4>
#include <v1model.p4>

header ethernet_t {
    bit<48> dstAddr;
    bit<48> srcAddr;
    bit<16> etherType;
}

struct metadata { }
struct headers { ethernet_t ethernet; }

parser ParserImpl(packet_in packet, out headers hdr,
                  inout metadata meta, inout bit<32> tm) {
    state start {
        packet.extract(hdr.ethernet);
        transition accept;
    }
}

control IngressImpl(inout headers hdr, inout metadata meta,
                    inout bit<32> tm) {
    action forward(bit<9> egress_port) {
        tm = egress_port;
    }
    table fdb {
        key = { hdr.ethernet.dstAddr : exact; }
        actions = { forward; }
        size = 1024;
    }
    apply { fdb.apply(); }
}
```

对这段代码的判读：header 定义了以太网头的三个字段；parser 的 start 状态从报文里 extract 出以太网头；control 里定义了 forward 动作，把参数写到元数据 tm（在这个简化模型里代表出端口）；fdb 表以目的 MAC 为精确匹配键，匹配命中就执行 forward；apply 块调用 fdb.apply() 触发查表。要点是：表只匹配“解析器抽出来的字段”，动作只做“程序允许的动作”，这就是协议无关的实质——协议和动作都由程序员定义，而不是芯片固化。

下表列出 P4₁₆ 的主要语言要素与用途。

| 要素 | 关键字 | 用途 |
|---|---|---|
| 报文头 | `header` | 定义字段布局 |
| 元数据 | `struct` / `metadata` | 定义阶段间中间量 |
| 解析器 | `parser` / `state` | 定义解析状态机 |
| 表 | `table` / `key` | 定义匹配键与表规格 |
| 动作 | `action` | 定义命中后执行的操作 |
| 控制块 | `control` / `apply` | 组织处理阶段 |
| 外部对象 | `extern` | 调用目标特定能力 |

P4₁₆ 的设计刻意保持精简，把复杂能力交给架构（architecture）和目标（target）去扩展，这也是它能跨多种硬件的关键。

## P4LANG-04 匹配—动作表：匹配类型与有状态处理

表是 P4 程序的核心数据结构。匹配类型决定了表的灵活性：exact（精确匹配）最快、资源占用最少；ternary（三态匹配，支持通配符和掩码）灵活但耗资源，通常用于 ACL；lpm（最长前缀匹配）专用于路由查表。不同匹配类型在芯片里映射到不同硬件资源——精确匹配多用哈希或内容寻址存储，三态匹配用 TCAM，这解释了为什么 ACL 表项通常比路由表项更“贵”。

动作分无状态和有状态两类。无状态动作如修改字段、丢弃、转发，每次执行互不影响；有状态动作依赖 register、counter、meter 等有状态对象，能实现流量统计、速率限制、连接跟踪等。P4 对有状态操作有严格约束：一张表的一次 apply 里，同一状态通常只能被读写一次，这是为了适配硬件流水线的确定性时序。理解这些限制，才能写出“能编译到硬件”的 P4 程序，而不是只在软件模型里跑得通。

下表对比三种匹配类型的特性。

| 匹配类型 | 匹配方式 | 硬件资源 | 典型用途 |
|---|---|---|---|
| exact | 字段完全相等 | 哈希或 SRAM | FDB、精确 ACL |
| lpm | 最长前缀匹配 | 专用 LPM 引擎 | 路由表 |
| ternary | 掩码加优先级 | TCAM | 复杂 ACL、策略 |

下表列出常见有状态对象及其用途。

| 对象 | 作用 | 典型场景 |
|---|---|---|
| counter | 计数 | 流量统计、丢包计数 |
| meter | 计量与着色 | 限速、QoS 标记 |
| register | 通用读写存储 | 状态跟踪、在网计算 |
| digest | 上送控制面摘要 | 异常流量上报 |

匹配类型和状态对象的选择，直接影响程序的硬件可行性和资源占用，是 P4 开发者必须权衡的核心问题。

## P4LANG-05 P4Runtime：控制面与数据面的标准接口

P4 程序定义了数据面的“能力”，但谁来告诉数据面具体填什么表项？这就是 P4Runtime 的角色。P4Runtime 是一个控制面 API 规范（当前 v1.4.1，2024 年 10 月），用 gRPC 和 Protocol Buffers 定义控制器与交换机之间的通信。编译器在编译 P4 程序时会产出一份 P4Info 文件，它描述了程序里有哪些表、动作、计数器、寄存器及其 ID 和类型。控制器读 P4Info 就知道“我能操作哪些对象”，再通过 P4Runtime 的 `TableEntry` 消息增删查改表项。

P4Runtime 的工作流是：编译 P4 程序生成 P4Info 和设备配置，控制器加载 P4Info 建立对设备的认识，通过 gRPC 连接设备，用 `SetForwardingPipelineConfig` 下发流水线，然后用 `Write` 和 `Read` 操作表项。它还定义了主备仲裁（election_id），允许多个控制器竞争主键角色，保证只有一个控制器能写。这种设计让控制面和数据面解耦——换一个控制器，只要遵循 P4Runtime，就能操作同一份 P4 数据面。

node n2 "编译器<br/>产 P4Info 与配置" teal
node n3 "控制器<br/>读 P4Info" amber
node n4 "gRPC<br/>P4Runtime 通道" green
node n5 "交换机<br/>表项与状态" purple
edge n1 -> n2 "编译"
edge n2 -> n3 "提供描述"
edge n3 -> n4 "下发表项"
edge n4 -> n5 "编程数据面"
:::

图中节点速览：n1 是 P4 源程序；n2 是编译器，产出 P4Info 和设备配置；n3 是控制器，读取 P4Info 了解可编程对象；n4 是 gRPC 通道，承载 P4Runtime 消息；n5 是交换机，接收表项并编程数据面。整张图说明 P4Runtime 是控制面与数据面之间的标准契约，P4Info 是这份契约的“接口定义”。

下面是一段用 Python 通过 P4Runtime 下发表项的示意代码。

```python
# 通过 P4Runtime 向 FDB 表插入一条表项（示意，省略连接与仲裁建立）
from p4runtime_pb2 import TableEntry, Write
from p4runtime_pb2 import Update

entry = TableEntry()
entry.table_id = p4info_lookup("fdb")           # 从 P4Info 查表 ID
mf = entry.match[0]                               # 精确匹配字段
mf.field_id = p4info_field("fdb", "dstAddr")
mf.exact.value = bytes.fromhex("aabbccddeeff")
act = entry.action.action
act.action_id = p4info_action("forward")
act.params[0].value = (3).to_bytes(1, "big")     # egress_port = 3

update = Update()
update.type = Write.INSERT
update.entity.table_entry.CopyFrom(entry)
# stream_channel.Write(WriteRequest(updates=[update]))
```

对这段代码的判读：先构造一个 TableEntry，通过 P4Info 查出 fdb 表的 ID；第一个匹配字段设为精确匹配，值是目的 MAC；动作设为 forward，参数 egress_port 为 3；把表项包成 INSERT 类型的 Update，最后通过 gRPC 流通道下发。要点是控制器不硬编码 ID，而是查 P4Info——这保证了程序改了表结构后，控制器不用改代码就能适配，这正是 P4Runtime 解耦的价值。

下表列出 P4Runtime 的核心能力与用途。

| 能力 | 说明 |
|---|---|
| 表项管理 | 增删查改匹配—动作表项 |
| P4Info 描述 | 声明可编程对象及 ID |
| 主备仲裁 | 多控制器下的写权限管理 |
| 管道配置 | 下发编译后的流水线 |
| 摘要上送 | 接收 digest 等事件 |

P4Runtime 是 P4 生态里连接“程序”与“设备”的关键一环，也是实现软件定义数据面的基础。

## P4LANG-06 目标架构：PSA、PNA 与 v1model

同一份 P4 程序要跑在不同硬件上，需要一个中间层描述“这类目标提供什么能力”，这就是目标架构（architecture）。P4₁₆ 定义了几个标准架构：**PSA（Portable Switch Architecture）** 描述交换机类设备的通用能力，包括 ingress/egress 流水线、流量管理、多播等；**PNA（Portable NIC Architecture）** 描述网卡类设备的能力，面向 DPU、SmartNIC 这类场景；**v1model** 是 BMv2 软件交换机用的经典架构，很多教学和原型都基于它。

架构的作用类似“抽象接口”：程序按架构提供的 extern 和元数据编写，编译器按架构把程序映射到具体硬件。这带来一个重要现实——**架构版本不等于实现支持**。一个设备可能只实现架构的部分能力，或提供厂商私有扩展。写 P4 程序前必须确认目标支持哪个架构、哪些 extern、哪些匹配类型，否则程序编译得过但跑不起来，或者根本编译不过。这一点在工程上比语言语法本身更容易踩坑。

下表对比几种常见目标架构。

| 架构 | 面向目标 | 特点 |
|---|---|---|
| PSA | 交换机 ASIC | 标准交换能力，端口与流量管理 |
| PNA | 网卡与 DPU | 面向主机侧包处理 |
| v1model | BMv2 软件交换机 | 教学与原型常用 |
| Tofino 架构 | Intel Tofino | 厂商特定，含专用 extern |

下表列出选择架构时的考虑因素。

| 考虑因素 | 说明 |
|---|---|
| 目标硬件 | 设备实际支持哪个架构 |
| extern 能力 | 需要的特有能力是否可用 |
| 编译器支持 | p4c 或厂商编译器是否支持 |
| 可移植性 | 是否需要跨目标复用程序 |

架构是 P4“一次编写、多处编译”承诺的落地机制，理解它才能正确评估程序的可移植性。

## P4LANG-07 工具链与开发流程：从代码到线速转发

P4 的开发工具链围绕开源编译器 p4c 和软件交换机 BMv2 构建。典型流程是：编写 P4 程序，用 p4c 针对目标编译，生成设备配置和 P4Info；在 BMv2 软件模型上做功能验证，用 packet test framework 打流测试；验证通过后，用目标厂商的编译器编译到真实硬件（如 Tofino 用 Intel P4 Studio），加载流水线；再用 P4Runtime 控制器下发表项，用计数器和抓包观察实际行为。

这里有个重要区分：**改程序逻辑要重新编译并重载流水线，改表项只需通过 P4Runtime 更新**。前者相当于给设备“换固件”，可能影响转发、需要谨慎灰度；后者相当于“改配置”，可以热更新。理解这个区别，才能设计合理的发布流程——把经常变化的策略做成表项，把稳定的处理逻辑写进程序。

下表列出 P4 工具链的主要组件。

| 组件 | 作用 |
|---|---|
| p4c | 开源 P4 编译器 |
| BMv2 | 软件交换机，用于验证 |
| P4Runtime | 控制面 API |
| PTF | 包测试框架 |
| 厂商 SDE | 如 Intel P4 Studio，编译到硬件 |

开发流程的关键纪律是：把流水线变更当软件发布对待——评审、灰度、可回滚；把表项变更当配置对待——热更新、可观测、可审计。

## P4LANG-08 P4 的典型应用：从自定义隧道到在网遥测

P4 的价值在具体应用里体现得最清楚。**自定义封装与隧道**是典型场景：当网络需要芯片不认识的自定义头部或隧道时，P4 可以解析、插入、改写这些头部，实现 VXLAN、GENEVE、SRv6 或私有协议的灵活处理。**在网遥测（INT）** 让报文在转发途中携带路径、队列、时延等信息，网络据此实现逐包、逐跳的可观测性，这是固定芯片难以做到的。**负载均衡**可以在数据面按流做路径选择，把四层负载均衡下沉到交换机。**网络安全**可以实现 ACL、DDoS 快速过滤、租户隔离等，把简单策略放在线速数据面。

但要清醒认识 P4 的边界：它适合“固定宽度、流式、可并行”的操作，不适合复杂算法、大状态、加密解密、深度包检测——这些仍属于 CPU、DPU 或专用加速器的范畴。岗位描述里“端网融合、在网计算、芯片卸载”的正确理解是：用 P4 做适合数据面的那部分，把不适合的部分交给主机或 DPU，二者协同，而不是指望 P4 包办一切。

下表把 P4 的典型应用与适配度整理出来。

| 应用 | 适配度 | 说明 |
|---|---|---|
| 自定义隧道封装 | 高 | 解析与改写自定义头部 |
| 在网遥测 INT | 高 | 逐包路径与队列信息 |
| 负载均衡 | 高 | 按流选路，线速转发 |
| ACL 与过滤 | 高 | 简单规则线速匹配 |
| 在网聚合计算 | 中 | 固定宽度的流式聚合 |
| 深度包检测 | 低 | 应交由 CPU 或专用设备 |
| 加密解密 | 低 | 计算复杂，不适合流水线 |

下表列出 P4 应用的可行性判断要点。

| 判断要点 | 说明 |
|---|---|
| 操作是否流式 | 逐包、无复杂依赖更合适 |
| 状态是否有限 | 大状态超出芯片存储能力 |
| 宽度是否固定 | 变长复杂运算不适合 |
| 资源是否够用 | 表项与阶段数受硬件限制 |

会用 P4 更重要是会判断“什么该用 P4 做”，这是从会写代码到能做架构设计的分水岭。

## P4LANG-09 P4 与 SONiC、SAI 的关系

在自研交换机语境里，P4 不是孤立的，它要和 SONiC、SAI 这些已熟悉的组件协同。SONiC 通过 SAI 抽象层操作交换芯片，而 SAI 背后可以是固定流水线芯片，也可以是 P4 可编程芯片。当数据面是 P4 时，一种常见架构是：SONiC 继续负责 L2/L3 的常规功能，P4 程序负责差异化的数据面处理（如自定义隧道、遥测、在网计算），两者在同一芯片上分工。Intel 的 Tofino 就提供 SAI 支持，便于接入 SONiC。

这里的工程难点是**两套数据面能力的协调**：SONiC 的 SAI 视图和 P4 的表项视图如何共享芯片资源？谁拥有解析器、谁配置表项、地址空间如何划分？不同方案有不同取舍：有的让 P4 程序实现完整数据面，SONiC 通过适配层把配置翻译成 P4 表项；有的让两者各占一部分流水线阶段。理解这些模式，才能在自研设备里把 P4 和现有 NOS 结合起来，而不是各做各的。

下表列出 P4 与 SONiC 协同的几种模式。

| 模式 | 说明 | 适用 |
|---|---|---|
| P4 全数据面 | P4 实现全部转发，SONiC 做配置翻译 | 高度定制设备 |
| P4 旁路加速 | 常规转发走 SAI，特定功能走 P4 | 增量创新 |
| 双流水线 | 芯片多流水线，分工运行 | Tofino 多 pipeline |
| 独立协处理 | P4 作为加速卡外接 | 灵活部署 |

岗位描述里“超融合可编程平台、芯片卸载”，本质上就是要把 P4、DPU、FPGA 这些可编程能力与现有网络软件栈整合，这需要在架构层做大量权衡。

## P4LANG-10 小结与在岗位中的位置

把这篇的内容串起来：P4 用协议无关的方式描述数据面，核心模型是 Parser—Match-Action—Deparser；P4₁₆ 语言用 header、parser、table、action、control 等要素组织程序；匹配类型与状态对象决定程序的硬件可行性；P4Runtime 用 P4Info 和 gRPC 把控制面与数据面解耦；目标架构（PSA、PNA、v1model）保证程序能跨硬件编译；工具链遵循“先软件验证、后硬件编译、编译与配置分离”的流程。

回到岗位要求，这篇 P4 语言与可编程数据面直接对应两点：一是“利用 P4 可编程研发高性能网络解决方案”的底层能力，二是“网络可编程方向、超融合可编程平台”的语言基础。掌握 P4，你就能理解为什么它适合在网计算和端网融合——因为它能在数据面里做定制处理，把原本要上送主机或专用设备的工作，前移到线速转发的网络里完成。

下一篇将深入 P4 可编程芯片本身，以 Intel Tofino 为代表，讲清楚可重配置流水线、芯片资源和 P4 Studio 开发环境，把这篇的语言知识落到真实硬件上。
