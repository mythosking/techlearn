# C 语言系统编程实践：内联汇编、内存对齐与无锁队列

## CSYS-01 为什么交换机软件工程师要练这三件事

岗位要求里写着"编程基础扎实，精通 C/C++、Python、Go"。这句话看起来泛泛，但放在自研交换机、路由器、网关的语境里，真正拉开差距的往往不是会不会写 C，而是能不能写出贴近硬件、能被编译器正确优化、还能在多核上稳定跑的 C。这类能力集中在三个点：内联汇编、内存对齐、无锁队列。

为什么是这三件？因为它们分别对应三层现实。内联汇编解决"编译器不认识、但硬件提供了"的能力，比如读时间戳、发内存屏障、访问特殊寄存器；内存对齐解决"数据结构怎么摆才符合硬件和缓存的脾气"，这是报文解析、DMA、表项操作的地基；无锁队列解决"多个核之间怎么零拷贝、无阻塞地传数据"，这是数据面流水线和控制面异步任务的基础设施。

这三件事还有一个共同特点：写错了不会崩在原地，而是表现为偶发的丢包、时延抖动、性能上不去、在特定芯片上才复现。这类问题最难查，也最能体现一个工程师的底子。把它们练扎实，比多背几个协议的状态机更有价值。

下表把三项能力与岗位条款、典型场景对应起来。

| 能力 | 对应岗位条款 | 典型场景 | 写错的表现 |
|---|---|---|---|
| 内联汇编 | 要求二、要求五 | 时间戳打点、内存屏障、特殊寄存器访问 | 优化后语义改变、平台不可移植 |
| 内存对齐 | 要求二、要求四、要求五 | 报文头解析、DMA 缓冲、表项结构体 | 非对齐访问异常、伪共享、性能骤降 |
| 无锁队列 | 要求二、要求四 | 核间报文传递、异步任务分发、遥测采样 | 偶发丢包、死锁、数据竞争 |

一个提醒：这三项不是为了炫技而存在。能不用汇编就不用，能用标准原子就不要手写屏障，能用成熟队列库就别自己造轮子。真正的功力体现在知道什么时候该用、什么时候不该用，以及出了问题能定位到是哪一层。

## CSYS-02 先搞懂重排序：编译器和处理器各有各的秩序

无锁代码最难的地方，不是 CAS 怎么写，而是"我以为的顺序"和"实际执行的顺序"不是一回事。重排序有两个来源：编译器和处理器。

编译器在优化时会重排没有依赖关系的语句，只要单线程结果不变就行。比如先写数据再置标志位，编译器可能觉得两个变量不相关，把置标志位提到前面。单线程看没问题，另一个核却可能看到标志位已经置上、数据还是旧的。

处理器这一层更复杂。现代 CPU 为了流水线效率会乱序执行，写操作先进 store buffer 再慢慢刷到缓存；x86 提供了较强的顺序保证，通常只有"先写后读不同地址"这一种重排，而 ARM、PowerPC 这类弱内存序架构允许的乱序要多得多。同一个无锁算法在 x86 上跑得好好的，移植到 ARM 交换机的管理 CPU 上就出问题，根源就在这里。

这里必须澄清一个高频误解：`volatile` 不是原子操作，也不是内存屏障。它只保证编译器每次都从内存读写这个变量，不把它缓存在寄存器里，也不参与某些编译期重排。它不提供原子性，也不阻止处理器的乱序执行。把 `volatile` 当同步原语用，是很多初学者写无锁代码踩的第一个坑。

下表把几种常见的"看起来都能同步"的手段区分清楚。

| 手段 | 作用层次 | 阻止什么 | 不阻止什么 |
|---|---|---|---|
| volatile 限定符 | 编译期 | 变量被缓存到寄存器、部分编译期重排 | 不保证原子性，不阻止处理器乱序 |
| 编译器屏障 | 编译期 | 跨屏障的编译期内存访问重排 | 不产生任何机器指令，不管处理器 |
| 原子操作加内存序 | 语言级到硬件级 | 按所选内存序约束编译期与运行期重排 | 不解决算法层面的 ABA 等逻辑问题 |
| 处理器屏障指令 | 运行期 | 特定方向的读写乱序与 store buffer 可见性 | 不约束编译器，需配合编译器屏障 |

C11 及 C++11 之后的原子库提供了六档内存序：relaxed 只保证原子性不保证顺序；acquire 用于读，保证它之后的读写不会被提前；release 用于写，保证它之前的读写不会被延后；acq_rel 用于读改写；seq_cst 提供全局顺序，代价最大。实践中的经验法则是：计数器用 relaxed 就够，生产者写数据后以 release 发布标志、消费者以 acquire 读取标志，这是无锁编程里最常见也最够用的组合；只有确实需要所有线程看到统一顺序时才上 seq_cst。

下面这段代码的要点是区分编译器屏障与处理器屏障。第二行只挡编译器，不生成指令；第三行是 ARM 上的完整屏障，既挡编译器也挡处理器。

```c
/* 纯编译器屏障：只影响编译器，CPU 层面什么都没做 */
#define COMPILER_BARRIER() asm volatile("" ::: "memory")

/* ARM 全屏障：dmb ish 挡处理器，memory 破坏项挡编译器 */
#define smp_mb()  asm volatile("dmb ish"   ::: "memory")
#define smp_wmb() asm volatile("dmb ishst" ::: "memory")   /* 仅写屏障 */
#define smp_rmb() asm volatile("dmb ishld" ::: "memory")   /* 仅读屏障 */

/* x86 上 acquire/release 通常由普通 mov 就够了，TSO 模型天然保证；
   只有 seq_cst 场景才需要 mfence 或带 lock 前缀的指令 */
```

对这段代码的判读：`asm volatile` 里的 `volatile` 防止编译器因为"没有输出"而整条删掉；`:::` 后面跟的是破坏列表，`memory` 告诉编译器这段汇编可能读写任意内存，于是它会把该刷到内存的寄存器值刷出去、把缓存的值重新装载。要注意 GCC 文档说得很清楚：这个破坏项只构成对编译器的读写屏障，并不阻止处理器跨越这条语句做推测读取，所以弱序架构上必须配真正的屏障指令。ARMv8 之后 `ldar` 和 `stl` 这类自带获取/释放语义的指令比单独加 `dmb` 更划算，新代码优先考虑它们。

## CSYS-03 GCC 扩展内联汇编：五段式语法拆开看

内联汇编在交换机软件里不是常态，但关键时刻绕不开。GCC 的扩展汇编语法看起来吓人，其实就五段：

```c
asm volatile(
    "汇编模板"        /* 第一段：指令文本 */
    : "=r" (out)      /* 第二段：输出操作数 */
    : "r" (in)        /* 第三段：输入操作数 */
    : "cc", "memory"  /* 第四段：破坏列表 */
    : label           /* 第五段：跳转标签，可选 */
);
```

第一段是汇编模板，`%0`、`%1` 按后面操作数的出现顺序引用。第二段是输出，约束前的 `=` 表示只写，`+` 表示读写。第三段是输入，常见的约束有 `r` 表示放到通用寄存器、`m` 表示直接用内存操作数、`g` 表示寄存器内存都可。第四段列出被这条汇编改掉、但编译器没从输出里看出来的东西，`cc` 是条件码寄存器，`memory` 是前面说的编译器屏障。第五段用于 `asm goto`，让汇编能跳到 C 标签，这在实现分支优化时有用。

下表列出写内联汇编时最常用的约束和破坏项。

| 符号 | 含义 | 使用场景 |
|---|---|---|
| `=r` | 输出到通用寄存器 | 汇编计算的结果要拿回 C 变量 |
| `+r` | 读写通用寄存器 | 累加、自增这类既读又写的场景 |
| `r` | 输入放通用寄存器 | 绝大多数标量输入 |
| `m` | 内存操作数 | 明确访问某段已知内存 |
| `cc` | 破坏条件码 | 汇编里做了比较或算术改变标志位 |
| `memory` | 破坏内存假设 | 汇编读写了未列在操作数里的内存 |

看一个读时间戳的完整例子，它把 x86 的 `rdtscp` 封装成 C 函数。

```c
static inline uint64_t rdtscp_start(void)
{
    uint32_t lo, hi;
    /* rdtscp 比 rdtsc 多一层序列化语义，边界更清晰 */
    asm volatile("rdtscp\n\t"
                 "mov %%edx, %0\n\t"
                 "mov %%eax, %1\n\t"
                 "cpuid"
                 : "=r" (hi), "=r" (lo)
                 :
                 : "rax", "rcx", "rdx", "memory");
    return ((uint64_t)hi << 32) | lo;
}
```

对这段代码的判读：两个输出操作数分别接 `%0` 和 `%1`，对应 `hi` 和 `lo`，所以模板里先把 `edx` 移到 `%0`、把 `eax` 移到 `%1`；末尾的 `cpuid` 是常见的防乱序手法，因为 `rdtscp` 之后的指令仍可能越过它开始执行；破坏列表里列出 `rax`、`rcx`、`rdx`，告诉编译器这些寄存器被用掉了，不能拿来放别的值。这里带 `memory` 是为了阻止编译器跨越打点重排内存访问，否则测出来的时间窗不准。

第二条例子是 ARM 上的原子比较交换，展示读改写怎么落到一个指令里。

```c
static inline int cas_u32(volatile uint32_t *ptr, uint32_t old, uint32_t newv)
{
    uint32_t tmp, ok;
    asm volatile(
        "1: ldrex   %0, [%3]\n\t"          /* 独占加载 */
        "   cmp     %0, %4\n\t"
        "   movne   %1, #0\n\t"            /* 不相等，失败 */
        "   bne     2f\n\t"
        "   strex   %1, %5, [%3]\n\t"      /* 独占存储，返回是否成功 */
        "   cmp     %1, #0\n\t"
        "   bne     1b\n\t"                /* 失败则重试 */
        "2:"
        : "=&r" (tmp), "=&r" (ok)
        : "r" (ptr), "r" (old), "r" (newv)
        : "cc", "memory");
    return ok == 0;
}
```

对这段代码的判读：`ldrex` 和 `strex` 是一对独占访问指令，只有期间没有其他核写过该地址，`strex` 才会成功；`=&r` 里的 `&` 是早期破坏约束，告诉编译器这个输出在输入读完之前就会被写，不能和输入共用寄存器，否则逻辑会错；失败后跳回标签 1 重试，这正是 CAS 循环的本质。实际项目里优先用 `__atomic_compare_exchange` 或 C11 `atomic_compare_exchange_strong`，编译器会按目标架构生成合适指令，比手写可移植得多。

写内联汇编有三条纪律。第一，能用编译器内建函数就不用汇编；第二，能明确列出操作数就别用 `memory` 兜底，因为它会强制刷寄存器、性能代价不小；第三，汇编一旦写下去就要写清注释说明它依赖哪套架构和哪条指令，换芯片平台时第一时间复查。

## CSYS-04 内联汇编在交换机软件里的真实触点

脱离场景谈指令容易变成背诵。交换机软件里内联汇编真正出现的场合大致有五类，理解它们比记住语法更重要。

第一类是延时与时间戳。丢包定位、队列时延测量、PTP 时间同步都要高精度计时，x86 上读 TSC、ARM 上读虚拟计数器，都需要内联汇编或者编译器内建函数。第二类是寄存器访问。芯片 SDK 的底层往往把 MMIO 读写封装成内联函数，中间夹带屏障，保证配置写入的顺序。第三类是预取。数据面在处理当前报文时提前把下一个报文或下一张表项拉进缓存，用预取指令掩盖内存延迟。第四类是位操作。CRC、校验和、字节序交换这类操作有专用指令，手写汇编有时比编译器自动生成更紧凑。第五类是无锁原语，像前面看到的 CAS 循环。

下表把这些触点、常用指令和注意事项整理成速查。

| 触点 | 常见指令或内建函数 | 注意事项 |
|---|---|---|
| 时间戳 | rdtsc、rdtscp、ARM 虚拟计数器 | 注意频率校准与跨核一致性 |
| 寄存器访问 | 内存屏障加 volatile 指针 | MMIO 访问必须保序，不能随意合并 |
| 数据预取 | prefetch 指令、builtin_prefetch | 过度预取会污染缓存、反而变慢 |
| 位与字节操作 | bswap、rbit、popcnt | 编译器内建函数通常已足够 |
| 原子原语 | ldrex/strex、cmpxchg | 优先用标准原子接口，便于移植 |

一个真实工程里的判断标准：如果一段汇编写完之后，你需要花很大力气解释它为什么正确，那多半应该改成更易读的写法。性能优化要用数据说话，先用性能分析工具确认热点，再决定要不要下探到汇编这一层。没有测量依据的"优化"，经常只是把代码变得更难维护。

## CSYS-05 内存对齐：结构体的布局不是字段顺序那么简单

C 结构体在内存里的布局由对齐规则决定。每个基本类型有自己的自然对齐要求，通常等于它的大小：char 是 1 字节，short 是 2，int 是 4，指针和 long 在 64 位系统上是 8。编译器会在字段之间插入填充字节，让每个字段落在合适的地址上，还会在结构体末尾补齐，使得结构体数组里每个元素依然对齐。

举个典型例子：一个结构体依次是 char、uint64_t、char，直觉上占 10 字节，实际在 64 位系统上通常是 24 字节。第一个 char 后面要填 7 字节才能让 uint64_t 落在 8 的倍数地址上，最后的 char 之后还要补 7 字节，让下一个结构体元素仍从 8 的倍数开始。如果把两个 char 挪到一起，大小能从 24 降到 16。这不是学术细节：当这个结构体是千万级表项时，差 8 字节就是几百兆内存。

对齐在交换机软件里有三个实际影响面。一是报文头解析。很多人习惯把以太网头、IP 头定义成 packed 结构体直接往报文缓冲区上强转，这在 x86 上通常能跑，在 ARM 上可能触发非对齐访问异常，或者退化成多次访问导致性能下降。更稳妥的做法是按字节偏移逐字段拷贝，让编译器把对齐访问优化掉。二是 DMA。网卡和芯片访问内存时往往要求缓冲区按特定边界对齐，大页和 mbuf 的对齐设计就是为此。三是缓存。热字段如果挤在同一个缓存行里被多个核写，就会引发伪共享，下一节专门讲。

下表是常见基础类型在 64 位系统上的大小与对齐，写结构体时可以据此估算布局。

| 类型 | 大小（字节） | 自然对齐（字节） | 说明 |
|---|---|---|---|
| char / uint8_t | 1 | 1 | 无对齐要求 |
| short / uint16_t | 2 | 2 | 网络端口号、VLAN 标签常用 |
| int / uint32_t | 4 | 4 | IPv4 地址、掩码常用 |
| long / uint64_t | 8 | 8 | 计数器、时间戳常用 |
| 指针 | 8 | 8 | LP64 模型下固定 8 字节 |
| 数组 | 元素大小乘个数 | 与元素相同 | 数组本身不额外加大对齐 |

下面是三个实用技巧的代码示例：用 offsetof 检查字段偏移、用静态断言固化布局假设、用对齐说明符明确要求。

```c
#include <stddef.h>
#include <stdalign.h>

struct flow_key {
    uint32_t sip;
    uint32_t dip;
    uint16_t sport;
    uint16_t dport;
    uint8_t  proto;
    uint8_t  pad[3];       /* 手动补齐，避免编译器随机填充 */
};

/* 编译期断言：协议字段必须落在预期偏移，防止跨平台布局漂移 */
_Static_assert(offsetof(struct flow_key, dip) == 4, "dip offset changed");
_Static_assert(sizeof(struct flow_key) == 16, "flow_key must be 16 bytes");

/* 明确要求按 64 字节对齐，常用于每核独立数据 */
struct lcore_stats alignas(64) {
    uint64_t rx_pkts;
    uint64_t tx_pkts;
    uint64_t drops;
};
```

对这段代码的判读：`offsetof` 在编译期算出字段偏移，配合 `_Static_assert` 可以在布局意外变化时直接编译失败，这比运行期才发现报文解析错位强得多；手动加 `pad` 数组能让结构体大小确定，避免不同编译器填充策略不同；`alignas(64)` 把结构体对齐到 64 字节，主要是为了后面讲的避免伪共享。要注意 `packed` 是把双刃剑，它会取消填充、让结构体紧凑，但代价是字段可能非对齐访问，还可能让编译器生成更慢的代码。在需要严格匹配线上格式的场景可以用它，但要么只在拷贝后的副本上用，要么确保目标平台支持非对齐访问并评估过性能。

## CSYS-06 缓存行与伪共享：性能杀手往往藏在结构体里

现代处理器的缓存以缓存行为单位搬运数据，主流架构是 64 字节。缓存一致性也是以缓存行为粒度维护的：只要一个核写了某个缓存行里的任何字节，其他核持有的这一行副本就失效。

伪共享指的就是这种情况：两个核各写各的变量，逻辑上毫无关系，但这两个变量恰好落在同一个缓存行里。结果每次写都让对方的缓存行失效，两个核在缓存一致性协议上反复来回，性能可能比真正共享一个变量还差。这类问题在多核数据面上尤其常见，因为快路径代码习惯把各种计数器、状态字放在一个结构体里，如果没注意对齐，热字段很容易挤到同一行。

定位伪共享靠猜不行，要用工具。Linux 上的 perf c2c 能报告缓存行粒度的争用，perf stat 看 cache-misses 和 IPC 的异常也能提供线索。一个经验信号是：单核跑很快，多核跑反而吞吐不涨甚至下降，往往就是缓存行争用或内存带宽瓶颈。

下图用最简单的形态展示伪共享是怎么发生的。

node n2 "核心一<br/>写计数器乙" blue
node n3 "同一缓存行<br/>六十四字节" amber

图中节点速览：n1 和 n2 是两个独立工作的核心；n4 与 n5 是各自要写的计数器，逻辑上不相干；n3 指出它们落在同一个 64 字节缓存行里；n6 是结果，缓存一致性协议让这一行在两个核之间反复失效。整张图的关键结论是：变量不共享不等于缓存行不共享，这才是伪共享的根源。

下表总结伪共享的识别与处理办法。

| 方面 | 表现 | 处理办法 |
|---|---|---|
| 现象 | 核数增加但吞吐不线性增长 | 用 perf c2c 定位热点缓存行 |
| 成因 | 不同核写的热字段落在同一行 | 把每核数据按缓存行对齐并隔开 |
| 简单对策 | 字段之间填充字节 | 用 alignas 或编译器属性明确对齐 |
| 结构对策 | 全局结构体被多核频繁写 | 改成按核索引的数组，各写各的槽位 |
| 框架对策 | 自己管理 mbuf 与队列元数据 | 采用 DPDK 的 rte_cache_aligned 约定 |

下面的代码展示把全局计数器改成按核独立、且每个槽位独占缓存行的写法。

```c
/* 每个槽位占满一个缓存行，避免相邻核心互相失效 */
#define CACHE_LINE 64

struct per_lcore_counter {
    uint64_t rx;
    uint64_t tx;
    uint64_t drop;
    uint8_t  reserve[CACHE_LINE - 3 * sizeof(uint64_t)];
};

static struct per_lcore_counter stats[RTE_MAX_LCORE]
    __attribute__((aligned(CACHE_LINE)));
```

对这段代码的判读：`reserve` 数组把结构体补足到正好一个缓存行，这样数组里相邻槽位不会共享缓存行；外层的 `aligned(64)` 保证数组起点也是缓存行边界，否则前面的填充会被起始偏移抵消。用的时候每个核只写自己的 `stats[lcore_id]`，统计汇总阶段再统一读取相加。这样写还有个附带好处：写入不再需要原子操作，因为根本不存在竞争。要注意这个技巧只对"写多读少"的计数场景最合适，如果所有核都要实时读总计数，就得换思路，比如分层聚合或者批量同步。

## CSYS-07 大页、DMA 与缓存一致性：内存这条线怎么走通

数据面的内存问题比一般应用复杂，因为它同时面对 CPU 缓存、TLB 和设备 DMA 三套机制。

先说大页。普通页是 4KB，海量报文缓冲会导致 TLB 表项频繁失效，查页表的代价在高速转发里非常明显。DPDK 一类框架普遍使用 2MB 或 1GB 大页，用更少的页覆盖同样的内存，TLB 命中率大幅提高。大页一旦分配就常驻内存，不会被换出，这对 DMA 也是必需的——设备拿到的是物理地址，内存被换出去就全乱了。

再说 DMA 地址。设备访问内存用的是 IOVA，也就是设备视角的地址。在 IOMMU 开启的场景下，IOVA 可以是虚拟地址，由 IOMMU 做映射；没有 IOMMU 或者用了特定驱动时，IOVA 就是物理地址。写驱动或者适配 SDK 时，搞错这两者会导致设备读写到错误的内存，而且往往表现为难以复现的丢包。

第三是缓存一致性。设备写的内存如果还在 CPU 缓存里有旧副本，CPU 读到的就是过期数据；反过来 CPU 写了数据还在缓存里没刷出去，设备读到的也是旧的。x86 上缓存一致性硬件做得比较足，很多场景不用手工干预；但在一些 ARM 平台上，DMA 缓冲区需要显式做缓存的清理或失效操作。这也是为什么芯片 SDK 会在 DMA 描述符处理前后夹带特定调用。

下图从大页一路画到 mbuf，说明这几层是怎么串起来的。

下表列出数据面内存设计里的关键关注点。

| 关注点 | 为什么重要 | 常见做法 |
|---|---|---|
| 页大小 | 减少 TLB 失效 | 使用 2MB 或 1GB 大页 |
| 地址类型 | 设备与 CPU 视角不同 | 明确 IOVA 是虚拟还是物理 |
| 缓存一致性 | 避免读到过期数据 | 必要时手工清理或失效缓存 |
| 对象对齐 | 匹配缓存行与设备要求 | mbuf 与描述符按缓存行对齐 |
| NUMA 本地性 | 跨 socket 访问延迟高 | 在报文所在 NUMA 节点分配内存 |

工程上有一条很实用的原则：缓冲区大小、队列长度、对象个数尽量取 2 的幂。一来用位与替代取模又快又简单，二来很多硬件描述符环本身要求 2 的幂长度。DPDK 的 ring 创建函数就明确要求元素个数是 2 的幂，除非额外指定精确容量标志，这条约束背后是环形索引的掩码运算。

## CSYS-08 原子操作与 CAS：无锁的地基

无锁编程的地基是原子操作。所谓原子，就是这个操作要么整体发生、要么整体没发生，其他核不会看到中间状态。GCC 提供 `__atomic_` 系列内建函数，C11 提供 `stdatomic.h`，两者语义基本一致。新代码推荐用标准头文件，可移植性更好。

CAS 是 compare-and-swap 的缩写，语义是：如果当前值等于期望的旧值，就把它换成新值并返回成功，否则返回失败并把当前值写回期望值。把它放进循环，就能实现"读—改—写"的原子更新。这是无锁队列、无锁栈、引用计数的基础。

CAS 有个经典问题叫 ABA：一个位置的值从 A 变成 B 又变回 A，CAS 看到当前值还是 A，就以为没人动过，于是成功写入，但实际上中间发生过变化。在指针型无锁结构里，这意味着节点被释放又重新分配，地址一样但内容完全不同。解决办法通常是给值带上版本号，把指针和计数打包成一个 64 位数比较；更复杂的场景要用危险指针或者 RCU 来保证节点生命周期。

下图是 CAS 循环的执行流程，理解它对后面读队列代码很关键。

图中节点速览：n1 先读取共享位置的当前值；n2 基于它算出要写的新值；n3 发起原子比较交换；n4 判断是否成功；失败时走 n5 重新读取并回到 n1 重试，成功时走 n6 结束。整张图说明 CAS 循环的关键是"失败就重来"，因此高竞争场景下重试次数会上升，这也是无锁算法不一定比锁快的根本原因。

下表给出内存序的选择建议，写原子代码时可以直接对照。

| 场景 | 推荐内存序 | 理由 |
|---|---|---|
| 纯计数、统计累加 | relaxed | 只要原子性，不关心与其他数据的顺序 |
| 发布数据后置就绪标志 | release 写 | 保证之前的写入对获取方可见 |
| 读取就绪标志后取数据 | acquire 读 | 保证之后的读取能看到发布方写入 |
| 简单的读改写计数 | relaxed | 原子性足够，无跨数据顺序需求 |
| 多变量需全局一致视图 | seq_cst | 提供全序，代价最高，谨慎使用 |

下面是一段典型的"发布—获取"代码，它展示了无锁编程里最常用的一对配合。

```c
#include <stdatomic.h>

struct message {
    uint32_t seq;
    uint8_t  payload[56];
};

static struct message slot;
static _Atomic int ready;

/* 生产者：先写数据，再以 release 发布 */
void publish(uint32_t seq)
{
    slot.seq = seq;
    for (int i = 0; i < 56; i++)
        slot.payload[i] = (uint8_t)(seq + i);
    atomic_store_explicit(&ready, 1, memory_order_release);
}

/* 消费者：先以 acquire 看到标志，再读数据 */
int consume(uint32_t *out)
{
    if (atomic_load_explicit(&ready, memory_order_acquire) == 0)
        return 0;
    *out = slot.seq;                 /* 此处必然看到生产者写入的数据 */
    atomic_store_explicit(&ready, 0, memory_order_relaxed);
    return 1;
}
```

对这段代码的判读：生产者对所有普通字段的写在 `release` 存储之前完成，消费者通过 `acquire` 加载看到标志为 1 时，保证能看到这些写；如果这里把内存序换成 relaxed，编译器和处理器都可能把 `ready` 的写入提前到数据写入之前，消费者就会读到半初始化的数据，而且这种问题在 x86 上往往不复现，到了 ARM 平台上才暴露。清零 `ready` 用 relaxed 是可以的，因为它不承载新的数据发布。这个模式是无锁队列里 head 和 tail 更新的基础，把 `ready` 换成索引就是队列的核心逻辑。

## CSYS-09 SPSC 无锁队列：单生产者单消费者环形缓冲

SPSC 是 single-producer single-consumer 的缩写，只有一个生产者和一个消费者。这是最简单也最快的一类无锁队列，因为不需要 CAS：生产者独占写 head，消费者独占写 tail，双方只读对方维护的索引。

环形缓冲用数组实现，容量取 2 的幂，索引对容量减一做位与就得到数组下标。空和满的区分需要牺牲一个槽位：当 tail 追上 head 时是空，当 head 比 tail 多走一整圈时是满。另一种做法是保留一个计数变量，但要保证它本身被正确同步，反而更复杂。

正确性依赖两点：一是索引本身用原子变量发布，二是数据写入必须先于 head 更新生效、数据读取必须在看到 head 更新之后进行。这就需要前面讲的 release 和 acquire 配对。另外，生产者和消费者写的热字段必须分到不同缓存行，否则又回到伪共享问题。

下图展示 SPSC 环形缓冲的结构与两个索引的运动方向。

node n3 "消费者 tail<br/>只写不读" amber
node n4 "已写入区域<br/>尚未消费" green

:::

图中节点速览：n1 是槽位数组，容量取 2 的幂；n2 是生产者独占的 head 索引；n3 是消费者独占的 tail 索引；n4 是已经写入但还没被消费的区域；n5 是空闲区域；n6 是掩码运算，把增长的索引映射成数组下标。整张图的关键点是两个索引分别由一侧独占写入，所以不需要 CAS，只需要用内存序保证对方能看到正确的更新。

下面的代码是一个精简但正确的 SPSC 队列骨架。

```c
#define CACHE_LINE 64
#define RING_SIZE  1024              /* 必须是 2 的幂 */
#define RING_MASK  (RING_SIZE - 1)

struct spsc_ring {
    void *slots[RING_SIZE];
    /* 两个索引分开放置，避免生产者和消费者伪共享 */
    alignas(CACHE_LINE) _Atomic unsigned head;
    alignas(CACHE_LINE) _Atomic unsigned tail;
};

int spsc_push(struct spsc_ring *r, void *obj)
{
    unsigned h = atomic_load_explicit(&r->head, memory_order_relaxed);
    unsigned t = atomic_load_explicit(&r->tail, memory_order_acquire);
    if ((h - t) == RING_MASK)        /* 只剩一个空槽，视为满 */
        return -1;
    r->slots[h & RING_MASK] = obj;   /* 普通写：先放数据 */
    atomic_store_explicit(&r->head, h + 1, memory_order_release); /* 再发布 */
    return 0;
}

void *spsc_pop(struct spsc_ring *r)
{
    unsigned t = atomic_load_explicit(&r->tail, memory_order_relaxed);
    unsigned h = atomic_load_explicit(&r->head, memory_order_acquire);
    if (h == t)                      /* 相等即空 */
        return NULL;
    void *obj = r->slots[t & RING_MASK];
    atomic_store_explicit(&r->tail, t + 1, memory_order_release);
    return obj;
}
```

对这段代码的判读：`head` 用 relaxed 读取是安全的，因为只有生产者自己写它；读对方的 `tail` 用 acquire，是为了看到消费者释放槽位时的写入；数据写入在前、`head` 以 release 发布在后，消费者 acquire 读到新的 `head` 后读槽位，就一定能看到生产者写入的对象指针。注意 `head` 和 `tail` 用 `alignas(64)` 强行分开，否则它们很可能落进同一缓存行，把一个本来无争用的队列变成伪共享热点。这个骨架适合单生产单消费的流水线级间传递；一旦出现多个生产者，就必须换成带 CAS 的 MPMC 实现。

## CSYS-10 MPMC 与 rte_ring：把无锁队列用到生产环境

多生产者多消费者队列的难点在于 head 不能再由一方独占。多个生产者同时要写槽位，必须先用 CAS 抢到一段连续空间：大家各自读当前 head，算出自己要的位置，然后 CAS 尝试把 head 推到新值，成功者拿到这段空间，失败者重新读 head 再试。tail 的推进则要保证顺序，不能让后完成的线程先把 tail 推过去，否则消费者会读到还没写完的槽位。

DPDK 的 rte_ring 是这类队列的成熟实现，值得逐项理解。它维护四个索引：生产者的 `prod_head` 与 `prod_tail`、消费者的 `cons_head` 与 `cons_tail`。head 表示已经预留的位置，tail 表示已经完成的位置，两者的差值就是尚未完成的操作。生产者先用一次 CAS 推进 `prod_head` 拿到空间，写入对象后再等待并把 `prod_tail` 追上去；消费者同理。因为索引是 32 位无符号数，差值计算依赖无符号回绕，天然支持无限次循环而不用处理溢出。

rte_ring 提供多种同步模式，这是它比一般环形队列更实用的地方。

| 同步模式 | 适用场景 | 特点 |
|---|---|---|
| MP/MC | 多个生产者和多个消费者，默认模式 | 用 CAS 抢 head，完成较对称 |
| SP/SC | 明确只有一个生产者一个消费者 | 无需 CAS，速度最快 |
| MP_RTS/MC_RTS | 超订核、线程可能被抢占 | 尾值由最后一个线程更新，缓解锁持有者被抢占 |
| MP_HTS/MC_HTS | 需要线程安全的窥视操作 | 生产消费完全串行化，支持 start 与 finish 分段 |

下表把这些模式的选择依据整理成速查，实际选型时可以先从默认模式起步，只有性能分析显示队列是瓶颈时才切换。

| 判断条件 | 建议模式 | 预期收益 |
|---|---|---|
| 一个收包核、一个处理核 | SP/SC | 消除 CAS 开销 |
| 多个核向同一队列投递任务 | MP/MC | 正确性优先的通用选择 |
| 核数超过物理核、存在超订 | RTS 系列 | 减少尾值自旋等待 |
| 需要查看队首再决定是否取出 | HTS 系列 | 提供线程安全的分段接口 |

下面是 rte_ring 的典型使用方式，注意容量必须是 2 的幂，且实际可用容量是设置值减一。

```c
#include <rte_ring.h>

/* 创建：容量 2048，实际可用 2047 个对象，单生产单消费 */
struct rte_ring *rx_ring = rte_ring_create(
        "rx_to_worker", 2048, rte_socket_id(),
        RING_F_SP_ENQ | RING_F_SC_DEQ);

/* 批量入队：失败时返回实际入队个数，必须检查 */
unsigned n = rte_ring_enqueue_burst(rx_ring, (void **)bufs, nb_bufs, NULL);
if (n < nb_bufs)
    drop_unprocessed(bufs + n, nb_bufs - n);   /* 背压处理 */

/* 批量出队：拿不到就返回 0，快路径不要在这里自旋 */
unsigned m = rte_ring_dequeue_burst(rx_ring, (void **)out, budget, NULL);
for (unsigned i = 0; i < m; i++)
    process_packet(out[i]);
```

对这段代码的判读：创建时用 `RING_F_SP_ENQ` 和 `RING_F_SC_DEQ` 声明单生产单消费，rte_ring 会省掉 CAS，这和上一节手写的 SPSC 队列在语义上是一致的；`rte_ring_enqueue_burst` 返回实际成功入队的数量，满队列时不会阻塞，调用方必须处理没投进去的报文，这是数据面背压设计的一部分；出队同样是非阻塞的，快路径里拿到多少处理多少，不要原地自旋等待，否则一个核卡住会拖垮整条流水线。文档还特别提醒 rte_ring 是不可抢占的数据结构，不适合在可能频繁被抢占的线程间高频使用，超订场景要选 RTS 或 HTS 模式。

最后说工程取舍。无锁不等于更快。竞争不激烈时，一个简单的自旋锁或者互斥锁可读性更好、出问题时更容易排查；只有当性能分析明确显示锁是瓶颈、且并发模型确实适合无锁结构时，才值得引入这些复杂度。无论选哪种，都要用线程 sanitizer 做竞态检查、用压测工具跑长时间稳定性测试、用性能分析工具确认优化真的生效。交换机软件出问题往往在长时间高负载之后，几分钟的功能测试说明不了问题。

写到这里可以把三项能力串起来看：内联汇编让你在必要时拿到精确指令，内存对齐让数据结构匹配缓存和设备的脾气，无锁队列让多核之间高效协作。它们共同的目标不是"写得底层"，而是让软件在确定性和性能之间找到可靠的平衡。这也是自研交换机岗位对 C 功力的真实期待。
