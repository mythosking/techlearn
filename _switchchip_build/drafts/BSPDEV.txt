# 交换机 BSP 开发：从上电到 NOS 的完整启动链

## BSP-01 BSP 到底是什么：在自研交换机里的位置

BSP 是 board support package 的缩写，中文叫板级支持包。它的职责一句话能说完：让一份通用的操作系统能在某块具体的板卡上跑起来，并且能正确识别和使用板上的硬件。但这句话展开来，覆盖面相当大——从上电第一条指令、内存初始化、串口输出，到设备树描述、PCIe 枚举、Flash 布局、CPLD 管理，再到内核驱动和诊断工具，都是 BSP 的活。

在自研交换机这个语境里，BSP 比通用服务器更重要。服务器有成熟的 BIOS 或 UEFI 标准，操作系统基本不用操心板级差异；交换机则是各家自主设计主板，CPU 架构可能是 x86、ARM 或 PowerPC，交换芯片通过 PCIe 或内部总线挂在主控上，电源时序、复位、LED、风扇都由 CPLD 管理。这些差异必须有人抹平，BSP 就是那个抹平层。

岗位要求里写"熟悉交换机硬件结构，有 BSP 开发经验者优先"，背后的真实期待是：你能不能把一块新板子从上电调试一路带到能装 NOS、能配端口、能跑业务。这不是写几个驱动那么简单，而是要理解整条链路上每一环的依赖。

下表把 BSP 的主要工作内容和对应阶段列出来。

| 工作内容 | 所处阶段 | 关键产出 |
|---|---|---|
| 启动固件移植 | 上电初期 | 能跑起来的 U-Boot 或 GRUB |
| 内存与时钟初始化 | 上电初期 | 可用的内存控制器与外设时钟 |
| 设备树编写 | 内核启动前 | 准确描述板卡资源的 DTS 文件 |
| PCIe 与总线枚举 | 内核启动期 | 识别交换芯片、网卡等外设 |
| Flash 分区规划 | 固件与安装期 | 分区表与升级策略 |
| CPLD 与 BMC 对接 | 全流程 | 电源、复位、散热、LED 管理 |
| ONIE 适配 | 首次部署 | 可自动安装 NOS 的环境 |
| 诊断工具 | 交付与运维 | 硬件检测与故障定位手段 |

有一点要先建立认知：BSP 不是一次性的交付物，而是伴随板卡全生命周期的基础设施。新板 bring-up 阶段它天天被改，量产阶段它被固化，运维阶段还要通过它做固件升级和硬件诊断。把 BSP 当成"启动时跑一下就结束"的东西，是新人常见的误解。

## BSP-02 完整启动链：从按下电源到业务进程跑起来

理解 BSP 最快的方法，是把一次完整启动从头到尾走一遍。不同架构细节有差异，但主干是相通的。

第一阶段是硬件复位和第一阶段引导程序。CPU 从固定的复位向量取指，执行一小段固化代码。ARM 和 PowerPC 平台上通常是 U-Boot 的 SPL，它体积极小，职责是把 DDR 控制器初始化起来，然后把完整的 U-Boot 从 Flash 加载到内存。x86 平台则由 BIOS 或 UEFI 承担类似职责。SPL 阶段能做的事很有限，串口能打印就谢天谢地，调试往往依赖 JTAG。

第二阶段是主引导程序。完整 U-Boot 起来后提供命令行、环境变量、网络、存储访问能力。它读取环境变量里的 bootcmd，决定从哪里加载内核、用什么参数启动。这是 BSP 工程师最常打交道的阶段，因为绝大多数启动问题都能在 U-Boot 命令行里定位。

第三阶段是 ONIE 或 NOS 内核。如果板卡是全新白盒、还没有装 NOS，bootcmd 会启动 ONIE 内核，进入安装环境；如果已经装了 NOS，bootcmd 会直接启动 NOS 内核，跳过 ONIE。这个切换由 NOS 安装器设置的启动命令控制，后面有专门章节展开。

第四阶段是内核初始化与驱动加载。内核解析设备树，枚举 PCIe 总线，加载网卡、I2C、MDIO、SPI 等驱动，识别交换芯片。这一步的教学重点是：内核不会猜你的硬件长什么样，一切依赖设备树和驱动里的匹配表。设备树写错一个 compatible 字符串，驱动就不会绑定，端口自然起不来。

第五阶段是 NOS 初始化。SONiC 这类系统此时启动数据库、容器、接口配置服务，加载 SAI，由 SAI 调用芯片 SDK 完成表项初始化，最后拉起路由协议和业务进程。到这一步，交换机才真正开始转发报文。

下表列出每个阶段的验证手段，排障时按阶段取证效率最高。

| 阶段 | 验证手段 | 典型失败现象 |
|---|---|---|
| SPL | JTAG、串口 early print | 无任何串口输出 |
| U-Boot | U-Boot 命令行、printenv | 卡在启动日志、环境变量丢失 |
| 启动目标选择 | 查看 bootcmd 与 ONIE 模式 | 反复进 ONIE、装完 NOS 仍不启动 |
| 内核与设备树 | dmesg、dtc 反编译 | 驱动未绑定、设备缺失 |
| 驱动绑定 | lspci、/sys/bus 目录 | 交换芯片识别不到 |
| NOS 与 SAI | 容器状态、SAI 日志 | 端口起不来、表项为空 |

排障的第一原则是分段确认，不要跳步。如果串口连 early print 都没有，问题一定在内存初始化或时钟配置；如果 U-Boot 命令行能进但内核起不来，重点看 bootargs 和内核镜像地址；如果内核起来了但端口没有，先看设备树和 PCIe 枚举结果，再往 SDK 方向查。按链路走，比到处乱试快得多。

## BSP-03 U-Boot：环境变量、bootcmd 与固件加载

U-Boot 是白盒交换机上最常见的引导程序，ARM 和 PowerPC 平台基本是标配。理解 U-Boot 有两个抓手：环境变量和 bootcmd。

环境变量是一组持久化的键值对，存在 Flash 的专用分区里，保存了启动命令、内核加载地址、串口波特率、管理口地址等信息。`printenv` 查看，`setenv` 修改，`saveenv` 写回 Flash。误改环境变量是现场常见的"设备起不来"原因，尤其是改了 bootcmd 却没保存成功，重启后行为不符合预期。

bootcmd 是开机自动执行的命令串，它决定从哪个设备、哪个分区加载内核，用什么参数启动。典型流程是：从 Flash 或网络读取内核镜像到内存指定地址，读取设备树二进制文件到另一个地址，然后执行 bootm 或 booti。在支持 ONIE 的平台上，bootcmd 还会在 ONIE 启动命令和 NOS 启动命令之间做选择，通常通过 NOS 安装器写入的 `nos_bootcmd` 实现。

U-Boot 还有一个重要能力是网络加载。`tftpboot` 可以从服务器上拉内核镜像，这在 bring-up 阶段极其好用——内核改一次不用烧 Flash，重启就能试新版本。生产环境则要关闭这类入口，避免被利用。

下面是几个实际排障中高频使用的 U-Boot 命令。

```text
=> printenv bootcmd                    # 查看当前启动命令
=> setenv bootcmd 'run nos_bootcmd'    # 改为直接启动已安装的 NOS
=> saveenv                             # 写回 Flash，否则重启丢失
=> sf probe                            # 探测 SPI Flash
=> sf read 0x10000000 0x100000 0x800000 # 从 Flash 偏移读内核到内存
=> tftpboot 0x10000000 sonic-vmlinuz  # 从 TFTP 服务器加载内核
=> fdt addr 0x12000000                 # 指定设备树在内存中的位置
=> bootm 0x10000000 - 0x12000000      # 带设备树启动内核
```

对这段命令的判读：`sf read` 的三个参数依次是目标内存地址、Flash 内偏移、读取长度，偏移量必须和分区布局严格对应，读错地方就会拿到一堆无效数据；`tftpboot` 依赖环境变量里的服务器地址和本机管理口地址，bring-up 阶段要先用 `ping` 确认网络通；`bootm` 后面的两个横杠占位表示不使用 initramdisk，第三个参数才是设备树地址。要特别注意 `saveenv` 这一步，很多人改完环境变量忘了保存，重启后以为修改没生效，其实是回退了。

U-Boot 的设备树操作也值得熟悉。`fdt addr` 指定设备树位置，`fdt print` 查看节点，`fdt set` 临时改属性。bring-up 阶段经常需要临时改设备树来验证某个驱动行为，确认有效后再回去改源码重新编译，这样迭代更快。

下表列出 U-Boot 阶段常见问题的定位思路。

| 现象 | 可能原因 | 定位方法 |
|---|---|---|
| 串口无输出 | 波特率不对、串口驱动未初始化 | 换波特率、用 JTAG 看复位向量 |
| U-Boot 能进但自动启动失败 | bootcmd 写错、nos_bootcmd 缺失 | printenv 逐项核对 |
| 内核加载后校验失败 | Flash 数据损坏、读取偏移错误 | 重新烧写、核对分区表 |
| 设备树加载失败 | 地址错误、文件损坏 | fdt addr 与 fdt print 检查 |
| 环境变量反复丢失 | 环境分区写保护或校验失败 | 检查分区属性与 Flash 状态 |

## BSP-04 设备树：把板卡硬件准确描述给内核

设备树是描述硬件的一种数据结构，源文件叫 DTS，编译后得到 DTB 二进制文件。它的意义在于把板级差异从内核代码里拿出来：同一份内核镜像配上不同的设备树，就能跑在不同的板卡上。对交换机来说，设备树要描述 CPU、内存、串口、SPI Flash、PCIe 控制器、I2C 总线、MDIO 总线、GPIO 以及挂在这些总线上的各种器件。

设备树由节点组成，节点有属性和子节点。几个关键属性必须理解：`compatible` 是驱动匹配的依据，内核和驱动用字符串表来匹配，写错一个字母驱动就不会绑定；`reg` 描述寄存器地址或设备地址，格式取决于总线的 `#address-cells` 和 `#size-cells`；`phandle` 是节点引用机制，用来表达"这个中断控制器是那个设备的中断父节点"这类关系；`status` 设为 disabled 可以让节点不生效，常用于同一份 DTS 适配不同板型。

交换机的特殊性在于，很多外设不是标准 PCI 设备，而是通过 MDIO 管理 PHY、通过 I2C 读传感器、通过 GPIO 控制复位。这些关系都必须在设备树里写清楚，否则驱动找不到资源。比如某个端口的 PHY 地址、复位 GPIO 编号、链路中断的 GPIO，都是设备树条目。

下面是一段简化但结构完整的设备树示例，展示交换机板卡上几类典型节点。

```dts
/dts-v1/;
/ {
    model = "Switch Reference Board";
    compatible = "vendor,switch-ref", "vendor,switch-soc";

    cpus { /* CPU 节点，省略 */ };

    soc {
        #address-cells = <1>;
        #size-cells = <1>;
        compatible = "simple-bus";
        ranges;

        serial0: uart@12000 {
            compatible = "ns16550a";
            reg = <0x12000 0x100>;
            interrupts = <5>;
            clock-frequency = <1843200>;
            status = "okay";
        };

        spi0: spi@20000 {
            compatible = "vendor,spi-controller";
            reg = <0x20000 0x1000>;
            #address-cells = <1>;
            #size-cells = <0>;
            flash@0 {
                compatible = "jedec,spi-nor";
                reg = <0>;
                spi-max-frequency = <25000000>;
                partitions {
                    compatible = "fixed-partitions";
                    #address-cells = <1>;
                    #size-cells = <1>;
                    partition@0 {
                        label = "u-boot";
                        reg = <0x0 0x80000>;
                    };
                    partition@80000 {
                        label = "u-boot-env";
                        reg = <0x80000 0x20000>;
                    };
                };
            };
        };

        mdio@30000 {
            compatible = "vendor,mdio";
            reg = <0x30000 0x100>;
            #address-cells = <1>;
            #size-cells = <0>;
            phy1: ethernet-phy@1 {
                reg = <1>;
                reset-gpios = <&gpio0 12 0>;
            };
        };
    };
};
```

对这段设备树的判读：`compatible` 字符串按 specificity 从高到低排列，内核优先匹配最具体的那个；`serial0:` 是标签，其他地方可以用 `&serial0` 引用这个节点；`spi0` 节点里的 `#address-cells = <1>` 表示它的子节点用单个单元描述片选号，所以 `flash@0` 的 `reg = <0>` 表示片选零；`fixed-partitions` 节点把 Flash 划成 U-Boot 和环境变量两个区，这个划分必须和 U-Boot 里烧写时的偏移一致；`reset-gpios` 用了 `&gpio0` 这个 phandle 引用，指向 GPIO 控制器节点的标签，第二个数字是引脚编号。这四类写法覆盖了交换机设备树里最常见的模式。

下表列出设备树编写时的常见错误，这些都是 bring-up 阶段的高频坑。

| 错误类型 | 后果 | 检查方法 |
|---|---|---|
| compatible 字符串写错 | 驱动不绑定，设备消失 | 对照驱动源码里的匹配表 |
| reg 地址或长度错误 | 访问错误寄存器，可能挂死 | 对照芯片数据手册的地址映射 |
| 缺少 ranges 属性 | 子节点地址转换失败 | 检查父总线的地址空间配置 |
| phandle 引用错误 | 编译报错或引用到错误节点 | 用 dtc 编译并检查警告 |
| status 未设为 okay | 节点被忽略 | grep 设备树中的 status 字段 |
| 时钟或复位未声明 | 驱动初始化失败 | 对照参考设计和原理图 |

## BSP-05 PCIe 枚举：CPU 怎么找到交换芯片

PCIe 是白盒交换机里主控 CPU 和交换芯片、网卡之间的主要通路。虽然数据报文走的是交换芯片的端口，但控制面配置、表项下发、状态读取往往要通过 PCIe 完成。理解 PCIe 枚举，是理解"为什么内核里看不到芯片"的关键。

枚举从宿主桥开始。内核扫描每个 PCIe 总线上的设备，读取配置空间里的厂商号和设备号，判断设备是否存在。每个设备用总线号、设备号、功能号三元组定位，简称 BDF。配置空间通过 ECAM 机制映射到内存地址，内核按标准偏移访问。

接下来是资源分配。设备通过 BAR 声明自己需要多少地址空间、是内存还是 I/O、是否支持 64 位。内核汇总所有设备的 BAR 请求，分配不冲突的地址范围写回 BAR。这一步如果失败，设备虽然能被识别，但驱动无法访问它的寄存器。现代系统由 firmware 或内核按 ACS 和 IOMMU 要求统一分配，BSP 层面要保证设备树或 ACPI 表里的桥接配置正确。

中断是第三个重点。传统 INTx 是共享的线中断，效率低成本高；MSI 通过写内存地址发中断，MSI-X 支持多个独立中断向量，适合多队列网卡和交换芯片的多类事件。设备树或驱动里要正确声明中断号，否则设备能枚举到但收不到事件。

下表列出 PCIe 子系统的排障命令和它们能回答的问题。

| 命令或手段 | 能回答的问题 | 典型输出线索 |
|---|---|---|
| lspci | 设备是否被枚举到 | 厂商设备号是否正确 |
| lspci -vvv | BAR 是否分配、驱动是否绑定 | Memory at 行、Kernel driver in use |
| lspci -t | 拓扑层级是否正确 | 桥与设备的父子关系 |
| /proc/interrupts | 中断是否到达 | 对应设备的计数是否增长 |
| dmesg | 枚举过程有无报错 | BAR 分配失败、链路训练失败 |

下面是一组按顺序执行的 PCIe 排障命令，从"有没有"一路查到"能不能用"。

```text
# 第一步：设备到底有没有被枚举到
lspci -nn | grep -i 厂商关键字

# 第二步：看资源分配和驱动绑定情况
lspci -vvv -s 03:00.0    # 换成实际的 BDF 号
#   关注 Memory at 行是否有地址、Kernel driver in use 是否非空

# 第三步：确认拓扑层级，判断挂在哪个桥下
lspci -t

# 第四步：确认中断是否真的到达
watch -n 1 'grep 设备关键字 /proc/interrupts'

# 第五步：回看内核枚举日志中的报错
dmesg | grep -iE 'pcie|bar|link|switch'
```

对这组命令的判读：第一步用 `-nn` 显示原始厂商号和设备号，不受本地设备名数据库影响，能直接和数据手册对照；第二步的 `Memory at` 如果显示为空，说明 BAR 没分配到地址，驱动基本没法访问寄存器，`Kernel driver in use` 为空则说明没有驱动绑定；第三步的树状输出能看出设备挂在哪个桥下，多switch 级联时尤其有用；第四步用 watch 持续观察中断计数，计数不增长说明中断配置或硬件有问题；第五步从内核日志里找链路训练失败和 BAR 分配失败的痕迹。这五步走完，PCIe 层面的问题基本无处可藏。

一个和交换机特别相关的经验：交换芯片通过 PCIe 暴露的往往不是网卡，而是一个管理接口。内核里看到的设备号可能和预期的网卡完全不同，驱动也可能来自芯片厂商而不是标准网卡驱动。bring-up 时先确认芯片在 PCIe 总线上被识别到，再去看厂商 SDK 的初始化日志，顺序反了会浪费大量时间。另外，链路训练失败经常和硬件设计有关，比如参考时钟、走线长度、均衡参数，这类问题软件只能发现现象，解决办法往往要回到硬件设计。

## BSP-06 Flash 布局与 CPLD：启动固件的存放与板级管理

交换机主板上通常有几颗非易失存储器：一颗 SPI NOR Flash 存放引导程序、环境变量和 ONIE；一颗或两颗 eMMC 或 SATA 盘存放 NOS 镜像和业务数据；还有 CPLD 负责板级管理。搞清楚它们的分工，才能理解固件升级和故障恢复。

NOR Flash 容量通常不大，十六到六十四兆字节是常见规格，里面按顺序划出几个区：U-Boot 镜像、环境变量、ONIE 镜像，可能还有诊断固件和保留区。分区表和 U-Boot 里的烧写偏移必须严格一致，不一致的后果是升级后系统起不来。环境变量区通常有主备两份，防止写一半掉电导致配置全丢。

CPLD 是复杂可编程逻辑器件，在交换机里扮演"大管家"角色。它负责电源上电时序、复位信号分发、风扇转速控制、LED 状态指示、温度传感器读取，有时还承担看门狗和 BMC 通信。软件通过 I2C 或 GPIO 访问 CPLD 的寄存器，读取硬件状态或者下发控制命令。CPLD 固件本身也能升级，但风险比软件高得多——刷坏了整块板可能变砖，所以通常有恢复机制。

下表把几类固件的存放位置和升级风险整理出来。

| 固件类型 | 存放位置 | 升级风险 | 恢复手段 |
|---|---|---|---|
| U-Boot | NOR Flash 前端分区 | 高，刷坏则无法启动 | JTAG 或编程器烧录 |
| 环境变量 | NOR Flash 专用分区 | 中，主备副本可回退 | 恢复默认环境变量 |
| ONIE | NOR Flash 或独立分区 | 中 | 网络或 U 盘重装 |
| NOS 镜像 | eMMC、SATA 或 Flash | 低 | 双分区切换或重装 |
| CPLD 逻辑 | CPLD 自身配置存储 | 很高，可能导致板卡不可用 | 专用恢复引脚或编程器 |

固件升级有一条铁律：永远保留可回退的路径。NOS 用双分区 A/B 切换，U-Boot 尽量不升级，CPLD 升级前确认恢复机制可用。现场变砖的案例大多不是升级本身出错，而是升级中断电且没有备份路径。工程上宁可多花点时间设计回退机制，也不要赌升级过程万无一失。

## BSP-07 ONIE：白盒交换机怎么自动装上 NOS

ONIE 是 open network install environment 的缩写，中文叫开放网络安装环境。它解决的是白盒交换机的"先有鸡还是先有蛋"问题：硬件厂商不预装 NOS，用户买回来怎么把 NOS 装进去。ONIE 就是固化在 Flash 里的一小套 Linux 环境，唯一职责是找到 NOS 安装器、执行它、然后让位。

一个支持 ONIE 的系统包含五个部分：支持 ONIE 的硬件平台、支持 ONIE 的引导程序、ONIE 的 Linux 内核、发现与执行应用，以及 NOS 厂商提供的安装器。其中发现与执行应用简称 ODE，是整个机制的核心。

ODE 的发现顺序值得记住，因为它直接决定排障思路。它先查本地文件，比如 U 盘上的安装器；再通过 DHCP 获取安装器地址，现代实现常用默认的 URL 选项，早期实现也用 TFTP 服务器名和启动文件名；还支持通过 IPv6 邻居发现和 mDNS 或 DNS-SD 定位。找到安装器后通过 HTTP 或 TFTP 下载并执行。安装器是自解压归档，把 NOS 写进 Flash 或磁盘，然后标记启动环境直接进 NOS，重启生效。

一个容易踩的坑是 ONIE 的安装模式是粘性的。如果设备进了安装模式但 NOS 没装成功，它会一直停在安装模式。这时候如果只是想进去看一眼，应该用救援模式而不是安装模式，救援模式不会自动搜索安装器，而是直接给一个 shell。另外，装完 NOS 后如果启动命令失效，U-Boot 会回落到 ONIE，表现为"设备怎么总是进 ONIE"。

下表把 ONIE 和 ZTP 这两个常被混淆的机制区分开。

| 对比项 | ONIE | ZTP |
|---|---|---|
| 作用时机 | NOS 还没装 | NOS 已装好、首次启动 |
| 主要任务 | 找安装器并安装 NOS | 拉取配置并初始化业务 |
| 发现方式 | 本地文件、DHCP、IPv6 邻居、组播发现 | NOS 通过 DHCP 拿配置文档地址 |
| 执行内容 | 自解压安装程序 | JSON 步骤或脚本插件 |
| 失败影响 | 设备没有操作系统 | 设备有系统但配置不完整 |

要特别强调：ONIE 只负责把 NOS 装进去，它不保证镜像适合这块板。拿错 ASIC 家族的镜像强行安装，ONIE 会给出警告，继续下去也只是装了一个跑不起来的系统。安装前要核对平台标识和镜像文件名，比如不同芯片家族的 SONiC 镜像名字就不同。这是运维自动化里很容易被忽略的一环。

下表列出 ONIE 常见故障与处理方向。

| 现象 | 常见原因 | 处理方向 |
|---|---|---|
| 一直停在 ONIE 安装模式 | NOS 安装失败、模式粘住 | 修复安装源或改用救援模式 |
| 找不到安装器 | DHCP 选项缺失、网络不通 | 检查管理口与 DHCP 服务器配置 |
| 安装后仍进 ONIE | nos_bootcmd 未写入或失效 | 在 U-Boot 里检查启动命令 |
| 镜像不匹配警告 | 平台标识不在镜像支持列表 | 换用对应芯片家族的镜像 |
| 装完 NOS 端口起不来 | 镜像与硬件不符、驱动缺失 | 回到设备树与驱动排查 |

## BSP-08 BSP 与芯片 SDK、SAI 的衔接

BSP 不是终点，它要把硬件准备到芯片 SDK 和 SAI 能接手的程度。这条衔接链上最容易出问题的是资源对应关系。

内核起来后，交换芯片应该已经在 PCIe 总线上被识别，对应的厂商驱动完成探测，映射寄存器空间，申请中断。芯片 SDK 在此基础上初始化内部资源：配置 SerDes、初始化表项、设置缓冲区、建立和主控的通信通道。SAI 再把芯片能力抽象成标准接口，供 NOS 调用。如果 BSP 阶段 PCIe 枚举失败或者设备树资源描述不全，SDK 会卡在初始化阶段，表现为 NOS 起不来或者端口全 down。

MDIO 和 I2C 是另外两条要打通的线。MDIO 负责管理 PHY，端口速率、双工、链路状态都从这里读；I2C 上挂着光模块 EEPROM、温度传感器、风扇控制器和 CPLD。这些总线控制器必须在设备树里声明，驱动才能绑定。一个典型现象是光模块插上去识别不到，多半是 I2C 节点没配或者光模块驱动没加载。

下表列出衔接层的常见故障与定位顺序。

| 故障现象 | 优先检查 | 对应层次 |
|---|---|---|
| 芯片未在总线出现 | PCIe 枚举、设备树桥配置 | BSP 与内核 |
| 驱动探测失败 | compatible 匹配、中断资源 | 内核驱动 |
| SDK 初始化超时 | 寄存器映射、复位状态 | SDK 与硬件 |
| 端口全 down | MDIO 与 PHY 驱动、SerDes 配置 | 驱动与 SDK |
| 光模块不识别 | I2C 节点、模块驱动 | 设备树与驱动 |
| SAI 接口调用报错 | SDK 初始化是否完整 | SAI 与 SDK |

排障时沿着这张表从上往下走，不要看到端口 down 就直接去查 PHY。如果芯片在总线上都不存在，查 PHY 是白费力气。反过来，如果 SDK 已经正常初始化、SAI 也能读到芯片信息，那问题多半在业务配置而不是底层。

## BSP-09 Bring-up 实战：一块新板怎么带起来

新板 bring-up 最能体现 BSP 工程师的功力。这个过程不是按部就班执行清单，而是不断在硬件和软件之间做判断。下面是经过提炼的通用顺序。

第一步是确认硬件基本活着。量电源轨、看时钟、确认复位信号释放，用 JTAG 连上 CPU。这一步不行就别写代码，先找硬件问题。第二步是让串口出字符。把串口引脚、波特率、时钟源配对，early print 能输出就说明 CPU 和内存初始化基本通了。第三步是把 DDR 跑起来，SPL 能加载完整 U-Boot。DDR 参数不对是 bring-up 阶段最常见的卡点，往往要靠芯片厂商的配置工具和反复试验。

第四步是把 Flash、PCIe、I2C、MDIO 这些总线逐个打通。每打通一个就在 U-Boot 或内核里验证一遍，不要攒到最后一起测。第五步是设备树和驱动，先把串口、Flash 这些必需节点配好，再配交换芯片和 PHY。第六步是引导 ONIE 并安装 NOS，第七步才是业务功能验证。

下图把 bring-up 的顺序画成阶段门，每个阶段通过才进入下一阶段。

node n2 "串口输出<br/>early print" teal
node n3 "内存初始化<br/>SPL 加载主镜像" amber
node n4 "总线逐个打通<br/>Flash PCIe I2C" green
node n5 "设备树与驱动<br/>识别交换芯片" purple
node n6 "引导 NOS<br/>业务功能验证" blue

edge n2 -> n3 "通过后"
edge n3 -> n4 "通过后"
edge n4 -> n5 "通过后"
edge n5 -> n6 "通过后"

图中节点速览：n1 是硬件基本检查；n2 让串口能输出字符；n3 完成内存初始化并加载主引导程序；n4 逐个打通各类总线；n5 通过设备树和驱动识别交换芯片；n6 引导 NOS 并验证业务。整张图强调阶段门的概念：上一阶段没通过就进入下一阶段，只会让问题更难定位。

下表列出每个阶段的通过标准，团队协作用它来做进度对齐很有效。

| 阶段 | 通过标准 | 常见卡点 |
|---|---|---|
| 硬件检查 | 各电源轨电压正常、时钟有输出 | 焊接问题、电源时序错误 |
| 串口输出 | 能看到 first stage 打印 | 引脚复用、波特率设置 |
| 内存初始化 | SPL 能加载并跳转 U-Boot | DDR 时序参数不匹配 |
| 总线打通 | 每条总线上设备可访问 | 地址映射、时钟门控 |
| 设备树与驱动 | lspci 能看到芯片、驱动绑定 | compatible 不匹配 |
| 引导 NOS | 系统启动、端口可配置 | 镜像不适配、SDK 初始化失败 |

bring-up 有一条经验值得写下来：一次只改一件事。同时改设备树、换内核、调 U-Boot 参数，出了问题根本不知道是哪个改动引起的。每改一处就验证一次、记录一次，看似慢，实际上是最快的方法。另外，保留一份已知能工作的最小配置，出问题先回退到它，再逐步加回功能。

## BSP-10 工程规范：版本、安全与可维护性

BSP 代码容易被当成"一次性移植"来对待，这是很危险的想法。它运行在系统最底层，出问题影响面最大，而且现场修复成本极高。工程上有几条规范值得坚持。

版本管理要覆盖全部固件组件。U-Boot、SPL、设备树、CPLD 逻辑、ONIE 镜像都要有明确的版本号和变更记录。设备树尤其容易被忽略，因为它常常散落在多个仓库里，改了没记录就会造成"某个板型突然不工作"的怪现象。建议把设备树当成正式代码管理，改动走评审。

安全启动要尽早规划。引导链上任何一环被篡改，后面所有防护都失去意义。安全启动通过签名验证逐级建立信任链，代价是固件升级流程变复杂、密钥管理要跟上。自研设备如果面向企业客户，这一条迟早会变成硬性要求，越早设计成本越低。

诊断能力要内置。串口日志、启动阶段标记、硬件状态寄存器、带外管理接口，这些在出问题时就是唯一的线索。很多团队把诊断当成事后补的东西，结果现场出问题只能返厂。更稳妥的做法是在 BSP 阶段就规划好日志等级、状态上报和恢复手段。

下表把 BSP 工程的关注点、风险和推荐做法汇总起来。

| 关注点 | 风险 | 推荐做法 |
|---|---|---|
| 版本管理 | 固件与板型不匹配、改动无记录 | 全组件版本化、变更留痕 |
| 安全启动 | 引导链被篡改 | 逐级签名验证、密钥托管 |
| 固件升级 | 断电导致变砖 | 双分区、保留回退路径 |
| 诊断能力 | 现场无有效线索 | 内置日志与状态上报 |
| 跨平台适配 | 一份代码硬套多种板型 | 设备树差异化、公共代码收敛 |
| 文档沉淀 | 知识集中在个别人身上 | 记录 bring-up 过程与踩坑 |

回到岗位要求：熟悉硬件结构、有 BSP 开发经验，真正的含义不是"改过几行设备树"，而是你能不能独立负责一块新板从硬件检查到 NOS 可用的全过程，能不能在启动失败时按链路定位到具体环节，能不能设计出安全可回退的固件升级方案。把这些能力条分缕析地准备好，面试和实际工作里都会更有底气。

把这篇和前一篇对照着看，会发现系统编程和 BSP 是同一件事的两端：一端是在既定硬件上把代码写到极致，另一端是从硬件出发把系统带起来。两者都需要对计算机体系结构有真实理解，而不只是会调用 API。这正是自研交换机岗位对候选人最看重的部分。
