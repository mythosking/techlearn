# EVPN、VXLAN 与 BGP 相关协议生态全景：五层协议族、关系辨析与芯片落表

**配套篇：承接 07《EVPN、VXLAN、BGP 协议详解与芯片表项映射》，把三协议周边的完整协议生态补齐**

## ECO-01 总览：三协议是主干，周边还有一整片生态

上一篇把边界网关协议、以太虚拟专用网络和虚拟扩展局域网三者的分工与落表讲透了，但真正做方案或排障时，会发现现场从来不是三个协议在跑。控制面有地址族扩展、路由目标、指定转发器选举和地址解析抑制；数据面有同类封装竞品；底层有承载网协议和快速检测；再往外还有建模、遥测和镜像。这些协议不参与"地址在哪里"这个核心问题的回答，却决定了方案能不能落地、收敛够不够快、出了问题查得到查不到。

本篇按五层把生态铺开：控制面协议族、数据面封装族、底层承载网协议、二层三层基础协议、运维管理配套。每层都回答四个问题——这一层解决什么、包含哪些协议、和核心三协议是什么关系、最终落到芯片哪张表。这样读下来，看到任何一个协议名都能立刻定位它在哪一层、该和谁配合、出问题该查哪张表。

## ECO-02 控制面协议族：从边界网关协议派生出的整棵树

### 1. 主干：边界网关协议与多协议扩展

边界网关协议第四版是整个控制面的底座，规定了会话建立、路径属性和选路框架。多协议扩展在它之上增加了两类网络层可达信息字段，用地址族标识和子地址族标识区分承载内容。没有这一步，边界网关协议只能发布网际协议单播路由；有了这一步，同一个会话就能携带以太虚拟专用网络、虚拟专用网络、组播等各种路由。以太虚拟专用网络对应地址族标识二十五、子地址族标识七十。

理解这一点就能解释一个常见现象：为什么配置以太虚拟专用网络也要配边界网关协议邻居？因为以太虚拟专用网络根本不是独立进程，而是边界网关协议的一个地址族。邻居起不来，再多以太虚拟专用网络配置也不生效。

### 2. 以太虚拟专用网络的分支

以太虚拟专用网络基础规范定义了路由类型，后续各篇规范不断往里加枝。下面这张表把工程上会碰到的协议按标准列全，并标出它到底解决什么问题。

| 协议或规范 | 标准编号 | 解决的问题 | 与核心三协议的关系 |
|---|---|---|---|
| 边界网关协议第四版 | RFC 4271 | 自治系统间交换可达性 | 底座与承载 |
| 多协议扩展 | RFC 4760 | 让边界网关协议承载非网际协议单播路由 | 以太虚拟专用网络得以存在的前提 |
| 以太虚拟专用网络基础 | RFC 7432 | 定义路由类型与地址族 | 控制面核心 |
| 虚拟扩展局域网上的以太虚拟专用网络 | RFC 8365 | 控制面与虚拟扩展局域网数据面对接 | 数据中心主流组合 |
| 集成路由与桥接 | RFC 9135 | 对称与不对称网关的媒体地址通告 | 三层网关场景必用 |
| 网际协议前缀路由 | RFC 9136 | 第五类路由发布网段前缀 | 跨虚拟网络标识三层与外部网络 |
| 以太虚拟专用网络专线 | RFC 8214 | 点到点二层专线 | 另一种业务形态 |
| 运营商骨干桥接以太虚拟专用网络 | RFC 7623 | 运营商级扩展 | 与骨干桥接结合 |
| 以太树 | RFC 8317 | 根叶二层隔离 | 多租户二层隔离 |
| 指定转发器选举扩展 | RFC 8584 | 多归属站点的选举框架 | 避免重复与环路 |
| 地址解析协议与新发现协议代理 | RFC 9161 与 RFC 9047 | 抑制地址解析广播 | 减少广播开销 |
| 广播未知单播组播流程更新 | RFC 9572 | 修正泛洪类流量处理 | 影响复制表行为 |
| 优化的子网间组播转发 | RFC 9625 | 组播跨虚拟网络标识优化 | 组播场景增强 |
| 边界网关协议隧道封装属性 | RFC 9012 | 通告隧道封装信息 | 自动建立隧道参数 |
| 二层三层虚拟专用网络建模 | RFC 9181 | 配置数据模型 | 与运维配套衔接 |

一句话记忆：基础规范是根，虚拟扩展局域网对接、集成路由与桥接、网际协议前缀这三根枝是数据中心最常用的部分，其余都是特定场景的扩展。

### 3. 配置示例：地址族与路由目标

下面是一段接入交换机的配置片段，展示邻居、地址族、路由目标与本地地址解析抑制的组合。

```text
router bgp 65001
 bgp router-id 10.0.0.1
 neighbor 10.0.0.9 remote-as 65001
 !
 address-family l2vpn evpn
  neighbor 10.0.0.9 activate
  neighbor 10.0.0.9 route-reflector-client
  advertise-all-vni
 exit-address-family
!
vrf default
 route-target both 65000:10100
!
vni 10100 l2
 rd 10.0.0.1:10100
 route-target both 65000:10100
```

对这段配置的判读：本地自治系统六万五千零一，邻居是汇聚层的路由反射器；在以太虚拟专用网络地址族下激活邻居并设为反射客户端，这一步不能漏，否则路由不会被反射；通告所有虚拟网络标识让对端自动获知；路由目标用自治系统号加网络标识拼成，导入导出都设为同一个值，保证同一租户的路由互相可见；路由区分符用环回口地址加网络标识，保证不同站点的同一网络标识路由不冲突。工程上最常见的错误是两端路由目标不匹配——控制面能收到路由但导入失败，现象是邻居正常、表项为空。

### 4. 从协议规范到路由类型

规范编号与路由类型要分开记：规范定义"规则"，路由类型定义"数据"。下表把常用路由类型与工程用途对应，这是查表映射的基础。

| 路由类型 | 规范来源 | 携带的关键信息 | 生成的芯片表项 | 典型用途 |
|---|---|---|---|---|
| 第一类 | 基础规范 | 以太网段标识符与标签 | 以太网段状态表 | 多归属与指定转发器选举 |
| 第二类 | 基础规范与集成路由与桥接 | 媒体地址、网际协议地址、标签、端点地址 | 媒体地址表与邻接表 | 地址通告与抑制 |
| 第三类 | 基础规范 | 网际协议前缀与标签 | 头端复制表 | 广播类流量复制清单 |
| 第四类 | 基础规范 | 组播组地址与源地址 | 组播转发表 | 组播场景增强 |
| 第五类 | 网际协议前缀规范 | 网际协议前缀、网关地址、标签 | 最长前缀匹配表 | 跨网络标识三层转发 |

## ECO-03 数据面封装族：虚拟扩展局域网和它的同类竞品

### 1. 为什么会有多个封装

虚拟扩展局域网解决的是"二层帧怎么跨越三层网络"，但它不是唯一答案。不同厂商在不同时期给出了不同方案，差别集中在两点：标识放哪里、能不能携带额外元数据。虚拟扩展局域网把二十四位标识放在固定头里，简单高效但无法扩展；通用封装用可变长选项字段换取灵活性；通用路由封装则把标识塞进隧道键值。三者是并列竞争关系，不是上下游配合关系。

下表把主流封装按字段与端口对照。

| 封装 | 标准 | 承载协议与端口 | 租户标识 | 元数据能力 | 典型生态 |
|---|---|---|---|---|---|
| 虚拟扩展局域网 | RFC 7348 | 用户数据报协议端口四七八九 | 二十四位网络标识 | 固定头无扩展 | 最广泛 |
| 虚拟扩展局域网通用协议扩展 | 草案 | 用户数据报协议端口四七九零 | 可变 | 支持多协议负载 | 特定设备场景 |
| 通用网络虚拟化封装 | RFC 8926 | 用户数据报协议端口六零八一 | 二十四位虚拟网络标识 | 可变长选项字段 | 现代软件定义网络 |
| 网络虚拟化通用路由封装 | RFC 7637 | 通用路由封装协议四十七 | 二十四位虚拟专用网络标识 | 依赖通用路由封装键值 | 微软路线 |
| 通用路由封装 | RFC 2784 与 RFC 2890 | 网际协议协议号四十七 | 键值字段 | 基础 | 封装底座 |
| 多协议标签交换 | RFC 3031 | 标签 | 标签 | 标签栈 | 运营商传统 |
| 运营商骨干桥接 | IEEE 802.1ah | 介质访问控制重写 | 骨干标识 | 服务实例 | 运营商扩展 |

注：运营商骨干桥接是电气电子工程师学会标准，工程文档里直接引用标准编号即可，不必展开拼写。

node n3 "通用网络虚拟化封装<br/>端口六零八一 可变选项" amber

图中节点速览：n1 是待封装的原始二层帧；n2、n3、n4 是三条并列的封装路线，分别对应标准方案、可扩展方案和特定厂商路线；n5 是物理网络，无论选哪条路线，底层看到的都只是外层网际协议报文。这说明封装选型影响的是端点能力和元数据空间，不影响底层承载方式。

### 2. 芯片视角：封装字段怎么被解析

交换芯片不关心封装名字，只关心解析器能不能抽出需要的字段。以虚拟扩展局域网为例，必须抽出的字段包括用户数据报协议目的端口、网络标识、内层目的媒体地址、内层目的网际协议地址和内层虚拟局域网标识。不同封装的字段位置不同，解析器模板和隧道终止表的查找键也要跟着改。

```text
解析模板 VXLAN:
  外层以太网 -> 外层网际协议 -> 用户数据报协议(目的端口 == 4789)
  -> 虚拟扩展局域网头(取出 VNI) -> 内层以太网 -> 内层网际协议
  元数据写入: tunnel_type=VXLAN, vni=VNI, inner_dmac, inner_dip
解析模板 GENEVE:
  外层以太网 -> 外层网际协议 -> 用户数据报协议(目的端口 == 6081)
  -> 通用网络虚拟化封装头(取出 VNI 与选项 TLV)
  -> 内层以太网 -> 内层网际协议
  元数据写入: tunnel_type=GENEVE, vni=VNI, option_list, inner_dmac
隧道终止表查找键: tunnel_type + 外层目的地址 + VNI
```

上面这段伪代码的价值在于揭示一件事：换封装不是改一个端口那么简单，解析器模板、元数据字段和隧道终止表的键都要同步改。自研设备支持多封装时，通常做法是在解析器里按目的端口分流到不同模板，再把统一的元数据交给后续查表阶段——这样后面的媒体地址表和路由表不用为每种封装各写一套。

### 3. 选型判断

选型时不需要背全部标准，按需求判断即可。

| 需求 | 推荐封装 | 理由 | 注意事项 |
|---|---|---|---|
| 生态成熟、设备互通要求高 | 虚拟扩展局域网 | 支持最广，运维资料多 | 元数据扩展能力有限 |
| 需要在封装里携带自定义元数据 | 通用网络虚拟化封装 | 可变长选项字段 | 确认两端设备都支持 |
| 已有通用路由封装网络 | 网络虚拟化通用路由封装 | 复用现有承载 | 与虚拟扩展局域网生态隔离 |
| 运营商已有标签交换网络 | 多协议标签交换 | 与现有控制面一致 | 芯片需要标签转发能力 |

## ECO-04 底层承载协议：覆盖网络下面的那层功臣

### 1. 底层不感知租户，但决定覆盖网络能不能用

覆盖网络的隧道端点之间必须网际协议可达，这件事由底层协议负责。底层不感知虚拟网络标识和租户，只做普通路由转发和链路聚合。但底层出问题，覆盖网络立刻表现为大面积隧道中断——这也是排障时最容易找错层的地方。

node n2 "内部网关协议或外部网关协议" teal
node n3 "快速检测" amber
node n4 "等价多路由与链路聚合" green
node n5 "隧道端点可达" purple
node n6 "覆盖网络隧道建立" blue
edge n1 -> n2 "发布地址"

edge n4 -> n5 "形成可达性"
edge n5 -> n6 "封装目的地确定"
:::

图中节点速览：n1 是交换机环回口，作为隧道端点的稳定地址；n2 把它发布到底层；n3 在毫秒级发现故障；n4 把流量分摊到多条路径；n5 形成端点间的可达性；n6 才能让覆盖隧道正常工作。这条链任何一环断了，上层路由反射器再正确也没用。

### 2. 承载协议清单

| 协议 | 标准或编号 | 在覆盖网络里的作用 | 什么时候必须有 | 影响的芯片表项 |
|---|---|---|---|---|
| 开放最短路径优先 | RFC 2328 | 底层内部网关协议 | 设备规模较小、单自治系统 | 最长前缀匹配表 |
| 中间系统到中间系统 | ISO 10589 | 底层内部网关协议 | 运营商或大型网络 | 最长前缀匹配表 |
| 外部边界网关协议 | RFC 4271 | 每台设备一个自治系统的底层架构 | 大型闭合网络 | 最长前缀匹配表与等价多路由表 |
| 双向转发检测 | RFC 5880 | 毫秒级故障检测 | 要求快速收敛 | 邻接表活性标记 |
| 协议无关组播与互联网组管理协议 | 相关请求注释系列 | 底层组播复制 | 用组播方式复制广播类流量 | 组播转发表 |
| 标签分发协议与段路由 | 相关请求注释系列 | 标签交换或段路由承载 | 采用标签交换底层 | 标签转发表 |
| 链路聚合控制协议 | IEEE 802.1AX | 物理链路聚合 | 多链路扩容 | 链路聚合表与哈希 |

一个实用判断：用头端复制时不需要底层组播，用组播复制时才需要协议无关组播；把底层改成外部边界网关协议并配合双向转发检测，是大型闭合网络收敛最快也最常见的组合。

### 3. 配置示例：底层外部边界网关协议与快速检测

```text
router bgp 65001
 neighbor 192.0.2.2 remote-as 65002
 neighbor 192.0.2.2 bfd
 !
 address-family ipv4 unicast
  neighbor 192.0.2.2 activate
  maximum-paths 8
 exit-address-family
!
bfd interval 300 min_rx 300 multiplier 3
!
interface PortChannel1
 lacp fast-switchover
```

对这段配置的判读：底层用外部边界网关协议互联，邻居地址是直连口地址；启用双向转发检测后，链路故障在毫秒级上报，不必等保活计时器超时；等价多路由上限设为八，配合链路聚合把带宽用满；检测间隔三百毫秒、倍数三，即约九百毫秒判定失效。要注意检测间隔过小会带来误报和中央处理器开销，生产环境通常三百到五百毫秒起步。

## ECO-05 二层三层基础协议：被增强还是被取代

覆盖网络不是凭空出现的，它替代了传统二层三层的若干协议。搞清楚替代关系，才能解释为什么某些配置在新架构里完全不需要。

:::figure id=ECO-05-01 | name=传统协议到覆盖网络的替代关系 | dir=LR
node n1 "虚拟局域网四千零九十六个标识" blue
node n2 "虚拟网络标识二十四位" teal
node n3 "地址解析协议广播泛洪" amber
node n4 "第二类路由抑制" green
node n5 "生成树阻塞链路" purple
node n6 "三层等价多路由全链路可用" blue
edge n1 -> n2 "标识空间扩展"
edge n3 -> n4 "广播变控制面通告"
edge n5 -> n6 "二层防环变三层路由"
:::

图中节点速览：三组对照各自成立——n1 到 n2 解决标识数量不足，n3 到 n4 把广播压成控制面通告，n5 到 n6 把阻塞链路变成全链路可用。共同点是传统二层机制被"控制面通告加三层承载"取代，这也是覆盖网络的核心价值。

| 传统协议 | 传统作用 | 在覆盖网络里的处境 | 什么时候还需要 |
|---|---|---|---|
| 虚拟局域网与八零二点一Q | 二层隔离与标识 | 仍存在但只作为本地桥接域，跨机架靠网络标识 | 接入侧 vlan 规划仍要做 |
| 地址解析协议与新发现协议 | 地址到媒体地址解析 | 被第二类路由抑制，广播大幅减少 | 抑制未开启或异构网络 |
| 虚拟路由器冗余协议与热备用路由器协议 | 网关冗余 | 被分布式任播网关取代 | 传统网络未改造部分 |
| 生成树与快速生成树与多实例生成树 | 二层防环 | 被三层底层加等价多路由绕开 | 接入层仍有二层环路风险时 |
| 虚拟专用局域网服务与虚拟专用专线服务 | 运营商二层专线 | 以太虚拟专用网络是它们的演进替代 | 存量运营商网络 |

特别提醒：生成树被绕开不等于可以彻底忽略。接入交换机下面如果还挂着支持生成树的设备，本地二层环路仍会打穿覆盖网络，所以接入侧仍要保留防环配置，只是不再依赖它做全局拓扑控制。

## ECO-06 运维管理配套：不转发，但决定能不能上线

自研交换机最容易低估的就是这一层。协议跑通只是第一步，能不能批量配置、能不能看到状态、能不能定位异常，决定方案能否上线。

:::figure id=ECO-06-01 | name=配置与观测的运维闭环 | dir=LR
node n1 "数据模型" blue
node n2 "配置下发接口" teal
node n3 "状态遥测采集" amber
node n4 "镜像与带内观测" green
node n5 "异常定位与参数回调" purple
edge n1 -> n2 "定义配置结构"
edge n2 -> n3 "触发状态变化"
edge n3 -> n4 "异常时细看报文"
edge n4 -> n5 "形成闭环"
edge n5 -> n1 "修正模型参数"
:::

图中节点速览：n1 定义配置结构，n2 把配置下发到设备，n3 持续采集状态，n4 在异常时提供报文级视图，n5 完成定位并反过来修正参数。这是一个闭环，不是一次性动作——覆盖网络参数众多，没有遥测闭环基本无法规模运维。

| 配套能力 | 代表协议或工具 | 作用 | 与芯片的关系 |
|---|---|---|---|
| 数据建模 | 网络配置模型与第二层三层虚拟专用网络模型 | 统一配置结构 | 字段最终映射到芯片表项 |
| 配置下发 | 网络配置协议与远程过程调用接口 | 批量配置与状态获取 | 通过抽象层写硬件表 |
| 状态遥测 | 遥测协议与流式采集 | 持续采集队列与表项状态 | 读取芯片计数器 |
| 带内网络遥测 | 带内网络遥测与镜像 | 定位丢包与路径异常 | 依赖镜像表与采样表 |
| 流量采样 | 采样流与远程镜像 | 容量规划与异常发现 | 依赖采样器与镜像出口 |

### 配置与观测示例

下面是一段订阅表达示例，展示如何持续采集某个虚拟网络标识的媒体地址表项数量与队列丢弃计数。

```text
订阅目标: /evpn/vni[VNI=10100]/state/mac-count
采集周期: 1000 毫秒
订阅目标: /interfaces/interface[name=Ethernet1]/statistics/out-queue-drops
采集周期: 500 毫秒
过滤条件: interface name matches "Ethernet*"
输出: 时序数据库 + 阈值告警
告警规则: mac-count 在 10 秒内下降超过 20% 时提示邻居或路由目标异常
```

这段示例的关键不是语法，而是思路：把芯片表项的规模变化和接口丢弃计数一起看。媒体地址表项突然减少通常意味着第二类路由没收到或路由目标不匹配；队列丢弃增长则可能是封装后报文变大导致底层拥塞。两者结合才能把控制面问题和拥塞问题区分开。

## ECO-07 关系辨析：三组最容易搞混的说法

协议生态里最容易出错的不是记不住标准编号，而是把并列关系当成配合关系。下面三组辨析建议背下来。

:::figure id=ECO-07-01 | name=三组易混关系的正确打开方式 | dir=LR
node n1 "以太虚拟专用网络" blue
node n2 "边界网关协议地址族而非独立协议" teal
node n3 "虚拟扩展局域网" amber
node n4 "可独立泛洪但规模受限" green
node n5 "通用网络虚拟化封装<br/>与网络虚拟化通用路由封装" purple
node n6 "同类竞品而非配套协议" blue
edge n1 -> n2 "本质归属"
edge n3 -> n4 "能否单独工作"
edge n5 -> n6 "相互关系"
:::

图中节点速览：n1 与 n2 说明以太虚拟专用网络的本质是边界网关协议地址族；n3 与 n4 说明虚拟扩展局域网可以脱离控制面工作但规模上不去；n5 与 n6 说明通用网络虚拟化封装和网络虚拟化通用路由封装是虚拟扩展局域网的竞品而非配套。三组都是概念归属问题，和配置无关。

| 常见说法 | 对不对 | 正确理解 | 工程影响 |
|---|---|---|---|
| 以太虚拟专用网络是独立路由协议 | 不对 | 它是边界网关协议的地址族扩展 | 排障先查边界网关协议邻居 |
| 用了虚拟扩展局域网必须配以太虚拟专用网络 | 不对 | 可纯数据面泛洪学习，只是规模受限 | 小规模测试可简化，生产建议用控制面 |
| 通用网络虚拟化封装是虚拟扩展局域网的增强版配套 | 不对 | 二者是并列的封装竞品 | 两端必须选同一种，不能互操作 |
| 生成树在覆盖网络里完全不用管 | 不对 | 全局拓扑不用它，接入侧防环仍需要 | 接入交换机保留防环配置 |
| 双向转发检测能加快路由收敛 | 对但要补一句 | 它只加快故障发现，重算与表项更新仍要时间 | 收敛慢时还要查表项刷新速度 |

## ECO-08 生态协议落到芯片：哪些表会被谁改写

上一篇讲过核心三协议的落表，这一节把周边协议也补进表里。芯片视角下，协议名称不重要，重要的是谁改写了哪张表的哪个字段。

:::figure id=ECO-08-01 | name=周边协议到芯片表项的写入关系 | dir=TB

| 协议或机制 | 改写的芯片表项 | 查找键 | 写入内容 | 失效时的现象 |
|---|---|---|---|---|
| 边界网关协议普通路由 | 最长前缀匹配表与邻接表 | 虚拟路由转发加目的地址 | 下一跳与出口封装索引 | 目的网段不可达 |
| 以太虚拟专用网络第二类路由 | 媒体地址表 | 网络标识加内层媒体地址 | 远端端点地址与标签 | 同网络标识二层不通 |
| 以太虚拟专用网络第三类路由 | 头端复制表 | 网络标识 | 端点清单与复制份数 | 广播类流量不通 |
| 以太虚拟专用网络第五类路由 | 最长前缀匹配表 | 虚拟路由转发加内层目的地址 | 三层网络标识与下一跳 | 跨网段不通 |
| 地址解析抑制 | 媒体地址表 | 网络标识加网际协议地址 | 解析结果或抑制标记 | 广播量激增 |
| 双向转发检测 | 邻接表活性标记 | 邻接标识 | 可用或不可用 | 路由在但流量黑洞 |
| 链路聚合控制协议 | 链路聚合表 | 聚合组编号 | 成员端口与哈希键 | 带宽下降或单成员转发 |
| 镜像与采样 | 镜像表与采样表 | 端口或流标识 | 目的端口与采样率 | 观测数据缺失 |

## ECO-09 选型与排障：把生态知识变成动作

### 1. 按场景选协议组合

| 场景 | 控制面选择 | 数据面选择 | 底层选择 | 关键理由 |
|---|---|---|---|---|
| 新建数据中心闭合网络 | 以太虚拟专用网络加路由反射器 | 虚拟扩展局域网 | 外部边界网关协议加快速检测 | 生态成熟、收敛快 |
| 运营商已有标签交换网络 | 以太虚拟专用网络 | 多协议标签交换 | 标签分发或段路由 | 复用现有承载 |
| 需要自定义元数据透传 | 以太虚拟专用网络扩展 | 通用网络虚拟化封装 | 普通三层底层 | 可变长选项字段 |
| 小规模测试或实验室 | 静态配置或泛洪学习 | 虚拟扩展局域网 | 静态路由 | 减少控制面依赖 |
| 存量虚拟机迁移 | 分布式网关加地址解析抑制 | 虚拟扩展局域网 | 现有内部网关协议 | 保留二层语义 |

### 2. 按现象查协议与表

| 现象 | 先查哪一层 | 具体动作 | 最可能的根因 |
|---|---|---|---|
| 邻居卡在活跃状态 | 底层 | 查传输控制协议连通性与自治系统号 | 不可达或参数不匹配 |
| 邻居正常但没有路由 | 控制面 | 查地址族是否激活、路由目标导入导出 | 路由目标不匹配 |
| 路由表有但转发表没有 | 控制面到芯片 | 查下一跳递归解析与邻接表 | 下一跳无法解析 |
| 同网络标识二层不通 | 控制面与芯片 | 查第二类路由与媒体地址表的网络标识键 | 标识映射不一致 |
| 广播流量异常膨胀 | 控制面 | 查地址解析抑制是否生效 | 抑制未开启 |
| 链路故障后流量黑洞 | 底层 | 查快速检测状态与邻接活性标记 | 检测未联动邻接 |
| 吞吐低于预期 | 数据面与芯片 | 查是否退化成多遍处理、哈希是否按内层字段 | 解析深度或哈希配置 |
| 遥测数据缺失 | 运维配套 | 查订阅路径与芯片计数器 | 模型字段未映射 |

### 3. 排障命令序列

下面是一段从底层往上的排障顺序，建议按顺序执行，不要跳层。

```text
1. 底层可达性: ping 隧道端点环回口，确认承载网正常
2. 邻居状态: show bgp summary，确认已建立状态
3. 路由接收: show bgp l2vpn evpn route，确认收到第二类与第五类路由
4. 路由目标: 核对本地导入导出与目标端是否一致
5. 表项落硬件: show mac-address table vni <VNI> 与 show route vrf <VRF>
6. 邻接活性: show adjacency detail，确认下一跳标记为可用
7. 链路聚合: show lacp neighbor，确认成员端口全部选中
8. 报文级验证: 镜像抓包，确认外层端点与网络标识正确
```

这个顺序的原则是先证明底层可达，再证明控制面收到，最后证明表项写进芯片。跳层的代价是经常被假象误导——比如邻居正常就以为控制面没问题，实际上路由目标不匹配导致一条路由都没导入。

## ECO-10 小结：把生态地图记成一句话

整个协议生态可以用一句话串起来：**边界网关协议提供会话与路径框架，多协议扩展让它能装载以太虚拟专用网络，以太虚拟专用网络算出地址结论，虚拟扩展局域网或同类封装把结论变成线上格式，底层协议保证端点可达，基础协议被逐步替代，运维配套负责配置和观测，最后所有结论都要写进芯片表项才生效**。

对交换芯片工程师而言，最值得带走的不是协议清单本身，而是三条判断习惯：看到一个协议先问它在哪一层、它改写哪张表、它失效时哪张表会空。养成这个习惯以后，再遇到没见过的协议扩展，也能很快定位它和核心三协议的关系，不至于在配置、邻居和表项之间来回猜测。

本篇与既有资料的分工是：三协议的原理与表项映射在 07 文档里展开，路由协议栈细节在 02 文档里，逐阶段查表位置在 06 文档里。本篇负责把周边生态补齐，三篇合起来构成从协议规范到芯片实现的完整视图。
