# 相关协议精讲：从报文字段到状态机再到芯片表项

**08 篇给出生态地图，本篇逐协议深挖机制——每个协议讲清它是什么、为什么这样设计、交互怎么走、字段落到芯片哪里**

## PROTO-00 小白导读：先用生活比喻建立直觉

### 1. 先忘掉协议名，从寄快递说起

如果你第一次看到这些名词，会被缩写淹没。先记住一件事：网络里所有协议，本质上都是"大家约定好的沟通规则"。就像寄快递要写地址、贴单、分拣、装车、运输、派送，每一步都有规矩。数据包就是包裹，交换机就是分拣中心，协议就是每一步的操作手册。

把一个包裹从北京寄到上海，快递公司不会让一辆车直接从你家开到我家。它先到你所在城市的集散点，贴一张写有目的地的新面单，装上进城的大车；到了上海再拆掉外面那张面单，按里面的地址派送。网络里的数据包也是这样一层层套着走的——这就是后面反复讲的"封装"。

### 2. 三个必须先建立的概念

**控制面和数据面。** 想象一个分拣中心有两块区域：一间办公室负责查地址、画路线、写分拣清单；一个大车间负责真的搬箱子。办公室自己不搬箱子，但车间搬哪个箱子、从哪个口出去，全听办公室写的清单。办公室就是控制面，车间就是数据面。边界网关协议、以太虚拟专用网络在办公室里工作；虚拟扩展局域网封装和查表转发在车间里发生。

这里有一句全文最重要的话：**办公室算出来的结论，必须写成清单交给车间，才有用**。清单就是芯片表项，"落表"这个词在全文出现几十次，说的就是这件事。办公室算得再快，清单写不下去，车间照样干瞪眼。

**封装就是套信封。** 你要把一封中文信寄到国外，外国邮局看不懂中文地址。办法是把整封信塞进一个英文信封，外面写国际地址。里面的信一个字不动，外面的信封负责跨国运输。虚拟扩展局域网就是那个外层信封：里面是租户的原始二层帧，外面套一层普通的网际协议报文，底层网络只需要看懂外面的地址就行。信封上写着客户编号，就是网络标识；进出口邮局就是隧道端点。

**表项就是分拣清单。** 车间不认识"租户""客户"这些抽象词，它只认识一行行清单：拿什么查、查到什么。比如"看到客户编号一百、收件地址是某媒体地址，就从三号口出去，并贴上某标签"。协议算出来的所有结论，最终都要变成这种一行行的键和值，硬件才能线速执行。这就是为什么本文每讲一个协议，最后都要落到"写进哪张表"。

### 3. 为什么需要这么多协议

用一次跨城快递把分工讲清楚，每个协议只管其中一件事。

| 快递里的环节 | 对应协议 | 它管的事 |
|---|---|---|
| 把客户地址告诉所有分拣点 | 以太虚拟专用网络 | 通告"某地址在某站点后面" |
| 负责把通知可靠送到 | 边界网关协议 | 建会话、传消息、选路 |
| 包裹套外层信封 | 虚拟扩展局域网等封装 | 定义报文长什么样 |
| 车走哪条路 | 开放最短路径优先、外部边界网关协议等底层协议 | 让隧道端点之间可达 |
| 路断了多快发现 | 双向转发检测 | 毫秒级发现故障 |
| 地址别每次都问一遍 | 地址解析抑制 | 把地址对提前记下来 |
| 一封信要发给多个点 | 头端复制组播 | 复制并分别封装 |
| 两个点都连着同一客户谁发 | 指定转发器选举 | 避免重复和环路 |
| 设备怎么配置和查看状态 | 配置协议与遥测 | 下发配置、采集状态 |

所以协议多不是因为设计复杂，而是因为分工细。每一种协议只解决一个小问题，组合起来才是一张能跑的网络。

## PROTO-01 BGP-4 精讲之一：路径矢量模型与会话状态机

### 1. 为什么是路径矢量

边界网关协议第四版和内部网关协议的根本差别，不在于报文格式，而在于"通告的是什么"。链路状态协议通告的是拓扑事实——我有哪些链路、每条链路代价多少，收到全部通告后每台设备自己算出全图最短路径。路径矢量协议通告的是现成结论——到这个网段，走这条自治系统路径。这个差别带来两个直接后果：

第一，策略控制能力极强。路径随路由一起传递，每一跳自治系统都能在路径前面加上自己、改写属性、或直接过滤掉不想要的路由。这是运营商和多租户数据中心能做精细流量工程的基础。第二，收敛依赖邻居告知，设备看不到全局拓扑，只能根据收到的若干条候选路径做比较。所以边界网关协议收敛天然比链路状态慢，这也是为什么需要快速链路故障检测来补它。

自治系统是策略边界。同一自治系统内部跑内部边界网关协议，要求全互联或用路由反射器解决可扩展性问题；不同自治系统之间跑外部边界网关协议。数据中心的典型做法是每台接入交换机一个自治系统、每台汇聚交换机一个自治系统，之间全部跑外部边界网关协议——这样天然避免内部协议的全互联要求，也能借自治系统路径做环路避免。控制面路由则借汇聚交换机做路由反射器反射给所有接入交换机。

### 2. 会话状态机六步

邻居建立要经历六个状态，理解每一步正在做什么，排障时才能知道卡在哪里。

| 状态 | 正在做的事 | 成功条件 | 卡住的典型原因 |
|---|---|---|---|
| 空闲 | 查路由表有没有到邻居地址的可达路径 | 找到可达路径 | 底层路由缺失或地址写错 |
| 连接 | 发起传输控制协议连接，目的端口一百七十九 | 三次握手完成 | 访问控制列表拦截、端口不可达 |
| 活跃 | 连接失败后重置并重连 | 连接成功 | 自治系统号不匹配、更新源地址错误 |
| 打开发送 | 发送打开报文，协商自治系统号、路由器标识、保持时间 | 收到对端打开确认 | 路由器标识冲突、保持时间不一致 |
| 打开确认 | 已收到对端打开报文，等待确认 | 收到保活或更新 | 能力协商失败、地址族未激活 |
| 已建立 | 交换更新与保活报文 | 持续收到保活 | 策略过滤导致无路由 |

最常卡住的是活跃状态。看到这个状态，先查传输控制协议连通性，再查两端自治系统号和更新源地址是否一致；卡在打开发送或打开确认，多半是路由器标识冲突或能力不匹配。

### 3. 五种报文

打开报文建邻，携带版本号、自治系统号、保持时间、路由器标识和可选能力；更新报文发布或撤销路由，是携带路径属性的主体；通知报文报告错误并立即关闭会话，错误码与子码直接说明原因；保活报文维持会话，通常按保持时间的三分之一发送；路由刷新报文请求对端重发指定地址族的路由，避免全量重发。

排障时通知报文最有价值。错误码二表示打开报文错误，子码二是对端自治系统号错误、子码三是路由器标识冲突、子码五是能力不支持；错误码三表示更新报文错误，子码四是属性Flags错误、子码十一是下一跳属性非法。把错误码对照上表，能跳过大量无效排查。

### 4. 状态判读示例

```text
BGP router identifier 10.0.0.1, local AS number 65001
Neighbor        V  AS    MsgRcvd MsgSent  TblVer  InQ OutQ  Up/Down  State/PfxRcd
10.0.0.9        4  65001  18234   18240     891    0   0  3d04h      128
192.0.2.2       4  65002      0       0       0    0   0  never      Active
```

判读要点：第一行邻居自治系统号与本地相同，是内部边界网关协议邻居，已建立三天四小时，收到一百二十八条路由，收发报文计数接近且持续增长，说明会话健康；第二行邻居自治系统不同，状态是活跃，收发计数都是零，说明传输控制协议连接从未建立成功——先查底层路由和访问控制列表，不要浪费时间查地址族。

## PROTO-02 BGP-4 精讲之二：路径属性与选路决策

### 1. 更新报文里装了什么

一条更新报文由三部分构成：撤销路由列表列出要删除的前缀，路径属性集合描述这批路由的元信息，网络层可达信息列出新发布的前缀。多协议扩展后，旧的前缀字段改为只在网际协议单播场景使用，其他地址族的可达与不可达信息放进专门的属性里。

路径属性按四个维度分类，这个分类决定了属性在自治系统之间怎么传播、设备遇到不认识的属性怎么处理。

| 类别 | 是否必须识别 | 是否跨自治系统传播 | 代表属性 | 遇到不认识时 |
|---|---|---|---|---|
| 强制公认 | 是 | 是 | 起源、自治系统路径、下一跳 | 报错关闭会话 |
| 可选公认 | 否 | 是 | 本地优先级、聚合器 | 静默忽略但保留 |
| 可选过渡 | 否 | 是 | 团体、多协议可达信息 | 原样转发给下一跳 |
| 可选非过渡 | 否 | 否 | 多出口区分符、源前缀 | 丢弃不转发 |

理解这个表的关键是"过渡"二字：可选过渡属性即使本机不认识，也要原样带给下游，因为它们可能对下游有意义；可选非过渡属性只在本地自治系统内有意义，不认识就可以丢掉。

### 2. 选路决策顺序

同一前缀收到多条路由时按固定顺序比较，直到分出胜负。顺序本身是协议实现约定的，记住关键前几步就足够工程使用。

| 顺序 | 比较项 | 方向 | 工程用途 |
|---|---|---|---|
| 一 | 权重，思科私有且本地有效 | 越大越优 | 本机强制选路 |
| 二 | 本地优先级 | 越大越优 | 控制本自治系统出口 |
| 三 | 本地产生优于学到的 | 本地优先 | 优先发布自有路由 |
| 四 | 自治系统路径长度 | 越短越优 | 减少穿越自治系统数 |
| 五 | 起源类型 | 内部优于外部优于不完全 | 区分路由来源可信度 |
| 六 | 多出口区分符 | 越小越优 | 影响对端进入本系统的方向 |
| 七 | 外部路由优于内部路由 | 外部优先 | 外部路径通常更短 |
| 八 | 到下一跳的内部代价 | 越小越优 | 选最近的出口 |

等价多路由是重要例外：当关键属性完全相同，多条路径都进转发表，数据面用哈希分摊。数据中心闭合网络正是靠这个把汇聚到接入的多条链路全部用起来。要注意哈希输入——虚拟扩展局域网封装后如果只看外层五元组，同一租户的流可能全落一条链路，所以高端芯片支持按内层字段哈希。

### 3. 策略工具的分工

路由映射、前缀列表和团体属性是三件常配套使用的工具。前缀列表只匹配前缀和掩码范围，是专用的高效匹配器；路由映射可以匹配前缀、属性、路径等多种条件，并可执行设置动作；团体属性是给路由打的标签，便于在下游批量匹配而不必逐个前缀写策略。

```text
ip prefix-list PL-INTERNAL permit 192.168.0.0/16 le 24
!
route-map RM-OUT permit 10
 match ip address prefix-list PL-INTERNAL
 match community CM-ALLOW
 set local-preference 200
 set community 65000:100 additive
!
route-map RM-OUT deny 100
```

判读：前缀列表允许十六位网段内掩码不超过二十四位的所有前缀；路由映射第十条同时命中前缀列表与团体列表才执行设置动作，把本地优先级设为二百并追加团体属性；末尾一百条拒绝是显式兜底，比隐含拒绝更利于排障——你能从计数器看到命中了多少条被拒绝的路由。要特别注意路由映射自上而下匹配、命中即停，顺序写反会导致预期动作永远不执行。

### 4. 路径属性的字节级格式

前面讲的是属性"表达什么"，这一小节讲它"长什么样"。所有路径属性都按同一种类型长度值结构编码：一字节标志位、一字节类型码、一或多字节长度、接着是属性值。长度字段占几字节由标志位里的扩展长度位决定——该位置一时长度字段为两字节，否则为一字节。

| 标志位 | 掩码 | 含义 | 排障时的用法 |
|---|---|---|---|
| 可选位 | 0x80 | 置一表示可选属性 | 为一是可选，为零是强制公认 |
| 过渡位 | 0x40 | 置一表示跨自治系统保留 | 为一是过渡，为零是非过渡 |
| 部分位 | 0x20 | 置一表示路径上某设备部分处理过 | 能看出属性是否被中间设备改写 |
| 扩展长度位 | 0x10 | 置一表示长度为两字节 | 决定从哪个偏移开始读属性值 |
| 本地管理位 | 0x08 | 特定属性使用 | 常见于扩展团体 |

类型码是判断属性身份的直接依据：一为起源、二为自治系统路径、三为下一跳、四为多出口区分符、五为本地优先级、八为团体、十四为多协议可达信息、十五为多协议不可达信息、十六为扩展团体。抓包时看到类型码十四，就知道后面是承载以太虚拟专用网络路由的属性。

```text
40 01 01 00        -> 标志 0x40 强制公认可过渡, 类型 1 起源, 长度 1, 值 0 (内部起源)
40 02 0c 02 05 65 00 01 65 00 02 65 00 03
                   -> 类型 2 自治系统路径, 长度 12, 段类型 2, 段长 3,
                      自治系统路径 65000 65001 65002
40 03 04 0a 00 00 01 -> 类型 3 下一跳, 长度 4, 10.0.0.1
80 0e 24 ...         -> 类型 14 多协议可达, 长度 36, 后面是地址族与网络层可达信息
c0 10 10 00 02 65 00 64 65 00 64 ... -> 类型 16 扩展团体, 标志 0xc0
```

上面这段十六进制序列的价值在于：当设备报"属性错误"或路由莫名被过滤时，直接看报文里的标志位和类型码，就能判断是对端发了不认识的可选属性、还是强制属性字段非法。例如标志位为零但类型码是扩展团体，就属于编码错误，对端会按协议要求关闭会话。

## PROTO-03 MP-BGP 精讲：地址族、可达信息与路由标识

### 1. 多协议扩展解决了什么

传统边界网关协议只能发布网际协议第四版单播路由。多协议扩展在更新报文里增加两个属性：多协议可达信息用来发布路由，多协议不可达信息用来撤销路由。属性里带地址族标识和子地址族标识，接收端据此把路由交给对应的地址族处理。这一步看似简单，却是整个以太虚拟专用网络存在的前提——没有它，边界网关协议无法承载媒体地址这类非网际协议信息。

| 地址族标识与子地址族标识 | 承载内容 | 典型用途 |
|---|---|---|
| 一斜杠一 | 网际协议第四版单播 | 底层承载与外网路由 |
| 一斜杠一百二十八 | 虚拟专用网络第四版 | 传统三层虚拟专用网络 |
| 一斜杠一百二十九 | 虚拟专用网络第六版 | 传统三层虚拟专用网络第六版 |
| 二十五斜杠七十 | 二层虚拟专用网络以太虚拟专用网络 | 本篇核心 |
| 一斜杠三十二 | 网际协议第四版组播 | 组播路由分发 |

配置上必须同时做两件事：在邻居下激活地址族，以及在地址族下激活邻居。少任何一步，邻居虽然能建立，但不会交换该地址族的路由。这是最常见的"邻居正常却学不到以太虚拟专用网络路由"的原因。

### 2. 路由区分符与路由目标

这两个都是六十四位或一百六十位的扩展团体属性，写法相似但用途完全不同，是新手最容易混淆的一对。

路由区分符的作用是让不同站点的相同网际协议前缀在控制面变成不同的路由。比如两个站点都有 192.168.1.0/24，路由区分符分别是 10.0.0.1:100 和 10.0.0.2:100，加上路由区分符后它们就成了两条不同的虚拟专用网络路由，可以同时存在、分别选路。它只影响控制面的路由唯一性，不影响数据面查表。

路由目标的作用是决定一条路由该被哪些虚拟路由转发导入。每条路由携带一个或多个导出路由目标，每个虚拟路由转发配置一个或多个导入路由目标；只有导入导出有交集，路由才会被放进该虚拟路由转发表。它实现的是租户隔离——同一网络标识的站点配相同路由目标，不同租户配不同路由目标，控制面的路由就不会串到错误的租户表里。

| 对比项 | 路由区分符 | 路由目标 |
|---|---|---|
| 属性类型 | 路由区分符扩展团体 | 路由目标扩展团体 |
| 作用范围 | 控制面路由唯一性 | 路由导入导出决策 |
| 是否影响数据面查表 | 不影响 | 间接影响，决定表项是否存在 |
| 典型编码 | 环回口地址冒号网络标识 | 自治系统号冒号网络标识 |
| 配错的症状 | 相同前缀互相覆盖 | 邻居正常但表项为空 |

### 3. 路由判读示例

```text
BGP routing table entry for 10.0.0.1:10100:192.168.10.0/24, version 891
Paths: (1 available, best #1)
  Advertised to update-groups: 2
  Local
    0.0.0.0 from 0.0.0.0 (10.0.0.1)
      Origin incomplete, metric 0, localpref 100, valid,internal,best
      Extended Community: RT:65000:10100
```

判读：前缀前面带路由区分符 10.0.0.1:10100，说明这是虚拟专用网络路由而非普通网际协议路由；只有一条路径且被选为最优；扩展团体里路由目标是 65000:10100，只有导入这个目标的虚拟路由转发才会接收。如果目的端配的是 65000:10200，这条路由到了也会被丢弃——现象是"邻居收到了路由，但表项为空"，查导入导出比查邻居有意义得多。

## PROTO-04 EVPN 精讲之一：五类路由逐类拆解

### 1. 第一类路由：以太网自动发现路由

第一类路由的学名是以太网段自动发现路由，核心字段是路由区分符、以太网段标识符、以太网标签和起源路由器地址。它的作用是告诉其他站点：某个以太网段标识符后面连着哪些站点、每条路径用哪个标签转发。多归属场景下同一个以太网段标识符会出现在多条第一类路由里，接收方据此知道哪些站点属于同一个多归属组，哪些转发器之间有竞争关系。

字段里最值得注意的是标签。如果标签值为零，表示这是 per-ESI 标签，所有从该以太网段来的流量统一用它；如果标签非零，通常是 per-VLAN 标签。芯片拿到这个标签后写入封装表，发送时直接作为虚拟扩展局域网头里的标签字段或内部标签。

### 2. 第二类路由：媒体地址与网际协议地址通告

这是数据面用得最多的一类。它携带媒体地址长度、媒体地址、网际协议地址长度、网际协议地址、路由区分符、以太网段标识符、以太网标签和隧道端点地址。一条第二类路由可以同时带媒体地址和网际协议地址，这正是地址解析抑制能成立的原因——对端已经知道某个网际协议地址对应的媒体地址和隧道端点，不必再发广播去问。

工程上第二类路由有三种常见形态：只带媒体地址用于纯二层通告；同时带媒体地址和网际协议地址用于地址解析抑制；只带网际协议地址用于分布式网关的主机路由。三种形态写进芯片的字段不同：第一种只写媒体地址表；第二种还要写地址解析抑制表；第三种写最长前缀匹配表的三十二位主机路由。

### 3. 第三类路由：组播以太网标签路由

第三类路由携带路由区分符、以太网标签、起源路由器地址和网际协议地址。它的作用是让所有站点知道：某个虚拟网络标识的广播未知单播组播流量该发给哪些隧道端点。收到这类路由后，设备为每个虚拟网络标识构造一张头端复制表，表项是远端端点地址列表。发送广播类流量时，数据面按这张表复制报文并逐个封装，不需要底层网络支持组播。

头端复制的代价是入口设备要做 N 次封装，端点越多开销越大。超过一定规模后改用底层组播更划算——这时第三类路由里的网际协议地址就是底层组播组地址，数据面只封装一次，由底层网络复制。两种模式的选择直接影响芯片的头端复制表大小和入口处理时延。

### 4. 第四类与第五类路由

第四类是以太网段路由，携带以太网段标识符和起源路由器地址，用于在同一个以太网段内的站点之间选举指定转发器。它不直接生成数据面表项，但选举结果会写进指定转发器状态表，决定广播类流量由哪个站点转发。

第五类是网际协议前缀路由，携带路由区分符、以太网标签、网际协议前缀和网关地址，还有是否包含网关地址的标志位。它解决的是跨网段转发：目的地址不在本地虚拟网络标识时，查最长前缀匹配表得到下一跳和三层网络标识。带网关地址的版本支持对称集成路由与桥接，不带网关地址的版本用于纯三层通告。

### 5. 五类路由字段速查

| 路由类型 | 关键字段 | 控制面作用 | 数据面表项 | 缺失时的现象 |
|---|---|---|---|---|
| 第一类 | 以太网段标识符、标签、起源地址 | 多归属组成员发现 | 标签表与多归属状态表 | 多归属冗余失效 |
| 第二类 | 媒体地址、网际协议地址、端点地址、标签 | 地址通告与解析抑制 | 媒体地址表与邻接表 | 同网络标识二层不通、广播增多 |
| 第三类 | 以太网标签、网际协议地址 | 广播类流量复制清单 | 头端复制表 | 广播未知单播组播流量不通 |
| 第四类 | 以太网段标识符、起源地址 | 指定转发器选举 | 指定转发器状态表 | 多归属站点重复转发 |
| 第五类 | 网际协议前缀、网关地址、标签 | 跨网段与外网可达 | 最长前缀匹配表 | 跨网段不通 |

### 6. 路由类型在网络层可达信息里的字节布局

所有以太虚拟专用网络路由共用一层外壳：一字节路由类型、一字节长度，后面是该类型专属字段。长度字段指示专属字段的总字节数，接收端据此定位下一条路由。真正决定芯片读到什么的是专属字段的顺序和长度。

| 路由类型 | 专属字段按顺序展开 | 固定长度（网际协议第四版场景） |
|---|---|---|
| 第一类 | 路由区分符、以太网段标识符、以太网标签、标签 | 二十五字节 |
| 第二类 | 路由区分符、以太网段标识符、以太网标签、媒体地址长度与地址、网际协议地址长度与地址、网关地址长度与地址、标签 | 四十四字节 |
| 第三类 | 路由区分符、以太网段标识符、以太网标签、网际协议地址长度与地址 | 二十九字节 |
| 第四类 | 路由区分符、以太网段标识符、网际协议地址长度与地址 | 二十五字节 |
| 第五类 | 路由区分符、以太网段标识符、以太网标签、前缀长度与前缀、网关地址、标签 | 三十六字节 |

媒体地址长度与网际协议地址长度字段本身各占一字节，且允许为零——这就是第二类路由三种形态的编码方式：只带媒体地址时网际协议地址长度为零；同时带两者时都非零；只带网际协议地址时媒体地址长度为零。芯片侧读到长度为零就知道该跳过对应字段，不需要为该表项写媒体地址或地址解析抑制项。

```text
02 2c                          -> 路由类型 2, 专属字段长度 44
  00 00 00 00 00 00 00 01      -> 路由区分符 0:1
  00 00 00 00 00 00 00 00 00 00 -> 以太网段标识符 0 (单归属)
  00 00 03 eb                  -> 以太网标签 1003
  06 00 11 22 33 44 55         -> 媒体地址长度 6, 00:11:22:33:44:55
  04 0a 64 01 0a               -> 网际协议地址长度 4, 10.100.1.10
  04 0a 64 01 01               -> 网关地址长度 4, 10.100.1.1
  00 00 64                     -> 标签 100
```

按这段字节展开看，第二类路由一次携带了三样芯片最需要的东西：媒体地址写媒体地址表，网际协议地址加媒体地址写地址解析抑制表，端点地址由边界网关协议下一跳属性另外携带、与这里的标签一起写邻接表。如果抓包发现网际协议地址长度为零，就能解释为什么数据面广播量没降下来——控制面根本没通告地址对。

## PROTO-05 EVPN 精讲之二：以太网段标识符与指定转发器选举

### 1. 多归属为什么要选举

一台客户设备双挂到两台交换机时，从下游交换机来的广播类流量如果两台都转发，客户侧会收到两份副本；如果两台都不转发，流量就丢了。指定转发器选举解决的就是"同一个以太网段的多归属站点里，谁有资格转发广播类流量"。选举发生在控制面，结果写进指定转发器状态表，数据面查这张表决定是否复制。

选举输入是以太网段标识符和每台站点的网际协议地址。算法按以太网段标识符算出一组候选转发器，再按约定规则从中选出一个指定转发器。所有站点用相同输入算出相同结果，因此不需要额外的协商报文——这一点很关键，说明指定转发器选举是分布式确定性算法，不是主站选举协议。

### 2. 单活与全活

单活模式下只有指定转发器转发所有流量，备用站点完全不转发。优点是行为简单、不会重复，缺点是备用链路空闲。全活模式下指定转发器只负责广播未知单播组播流量，单播流量由所有站点按本地偏置原则转发——目的地址 locally 可达就本地转发，否则才发往远端。这是数据中心更常用的模式，因为两条上行链路都能承载单播。

本地偏置的判读要注意：如果目的媒体地址在本机媒体地址表里存在，直接本地转发，不查远端；如果不存在，才查第二类路由找远端端点。全活模式下如果本地偏置没生效，会出现单播流量绕远路甚至来回震荡。

edge n4 -> n6 "广播单活"
:::

图中节点速览：n1 双挂产生多归属组，n2 交换标识，n3 分布式算出结果写入 n4；n4 之后分两条路——n5 单播全活用本地偏置，n6 广播类只由指定转发器转发。这个分流正是全活模式既提高链路利用率又不产生重复帧的原因。

### 3. 常见故障

| 现象 | 根因 | 排查入口 |
|---|---|---|
| 客户侧收到重复帧 | 两端指定转发器选举结果不一致 | 核对两端以太网段标识符与站点地址 |
| 广播类流量完全不通 | 没有站点被选为指定转发器 | 查第四类路由是否收到 |
| 单播流量绕远端 | 本地偏置未生效 | 查本地媒体地址表是否有该地址 |
| 一条上行链路空闲 | 配成了单活模式 | 核对全活模式配置 |

## PROTO-06 EVPN 精讲之三：地址解析抑制与集成路由与桥接

### 1. 地址解析抑制的完整流程

传统二层网络里，主机要找同一网段的另一台主机，先发地址解析协议广播请求，所有人都收到，只有目标主机应答。虚拟机规模一大，这种广播会吃掉大量带宽，而且无线场景里广播还要低速发送，问题更严重。

以太虚拟专用网络把这个过程变成控制面通告：主机上线时接入交换机通过数据面学习到它的媒体地址和网际协议地址，生成第二类路由发给路由反射器；反射器扩散给所有站点；其他站点把该地址写进媒体地址表和地址解析抑制表。后续有主机要访问这个地址，接入交换机直接查抑制表，用查到的媒体地址和隧道端点封装报文发出——广播请求根本不需要发出。

抑制表的关键字段是网络标识加网际协议地址，查得结果是媒体地址和远端端点地址。注意抑制表有老化机制：如果第二类路由被撤销或超过老化时间，表项删除，设备退回广播流程。所以排障时看到广播量突然上升，先查第二类路由是否还在、抑制表是否老化过快。

:::figure id=PROTO-06-01 | name=地址解析抑制替代广播的流程 | dir=LR
node n1 "主机上线" blue
node n2 "本地学习地址对" teal
node n3 "第二类路由通告" amber
node n4 "各站点写抑制表" green
node n5 "后续请求直接查表封装" purple
node n6 "广播请求被抑制" blue
edge n1 -> n2 "产生地址对"

edge n3 -> n4 "扩散并落表"
edge n4 -> n5 "提供查找键"
edge n5 -> n6 "不再泛洪"
:::

图中节点速览：n1 到 n4 是控制面学习扩散，n5 到 n6 是数据面效果。这条链说明抑制的本质是"把广播要问的信息提前放进表项"，而不是拦截广播包——没有第二类路由，抑制就无从谈起。

### 2. 对称与非对称集成路由与桥接

集成路由与桥接解决的是跨网段网关问题。非对称模式下，网关功能只在第一跳接入交换机完成：报文进入时查二层表转发到目的网段，出口交换机再做三层路由。它的配置简单，但每个虚拟网络标识都要配网关地址，网关地址不统一。

对称模式下，每个站点都配相同的任播网关地址和统一的虚拟路由转发，入口交换机做完二层查表后直接按三层网络标识路由，出口交换机只做二层查表。优势是网关地址统一、虚拟机迁移不换网关，代价是配置更复杂、需要第五类路由配合。

| 对比项 | 非对称模式 | 对称模式 |
|---|---|---|
| 网关位置 | 仅入口交换机 | 所有站点统一网关 |
| 需要第二类路由携带网际协议地址 | 是 | 是 |
| 需要第五类路由 | 通常不需要 | 需要 |
| 配置复杂度 | 低 | 高 |
| 虚拟机迁移体验 | 网关可能变化 | 网关不变 |
| 芯片查表次数 | 入口二层出口三层 | 入口二层加三层出口二层 |

### 3. 对称模式配置判读

```text
vni 10100 l3
 rd 10.0.0.1:50100
 route-target both 65000:50100
!
interface Vlan100
 vrf forwarding RED
 ip address 10.100.0.1 255.255.255.0
!
vrf RED
 ip routing
!
router bgp 65001
 address-family l2vpn evpn
  advertise ipv4 unicast
```

判读：先创建三层网络标识并配路由区分符与路由目标，这是第五类路由的载体；虚拟局域网接口加入虚拟路由转发并配网关地址；虚拟路由转发开启路由功能；最后在以太虚拟专用网络地址族下宣告网际协议第四版单播路由，这一步不做就不会产生第五类路由。常见的错误是只配了三层网络标识但忘了最后一条宣告命令，结果二层网络标识正常、跨网段不通。

## PROTO-07 EVPN 扩展协议精讲

基础以太虚拟专用网络之外，一组扩展规范把它带进更多场景。这些协议不常用，但看到名字要能立刻定位它解决什么问题。

| 协议 | 标准 | 解决的问题 | 与基础以太虚拟专用网络的关系 |
|---|---|---|---|
| 以太虚拟专用网络专线 | RFC 8214 | 点到点二层专线 | 同一地址族的另一种业务形态 |
| 运营商骨干桥接以太虚拟专用网络 | RFC 7623 | 运营商级二层扩展 | 以太虚拟专用网络控制面加骨干桥接数据面 |
| 以太树 | RFC 8317 | 根叶二层隔离 | 增加端口角色与水平分割规则 |
| 优化的子网间组播转发 | RFC 9625 | 组播跨网络标识优化 | 减少组播复制开销 |
| 边界网关协议隧道封装属性 | RFC 9012 | 自动通告隧道封装参数 | 减少手工配置 |
| 广播未知单播组播流程更新 | RFC 9572 | 修正泛洪流程边界情况 | 影响第三类路由处理 |

以太树值得单独理解：它给每个端口分配根、叶或中间角色，规则是叶到叶不通、根到叶可通、根到根可通。这样在同一个二层域里就能实现类似虚拟专用网络的端口隔离，而不需要额外的虚拟网络标识。芯片侧体现为访问控制表里多一条端口角色匹配条件——这再次说明无论控制面多复杂，数据面最终都是键值查表。

## PROTO-08 VXLAN 数据面精讲：封装、端点与查表

### 1. 封装头逐字段

虚拟扩展局域网把原始二层帧装进用户数据报协议，对外层网络来说就是一个普通的网际协议报文。最外层是以太网头，接着是外层网际协议头，源地址是本端隧道端点地址、目的地址是远端隧道端点地址；再往里是用户数据报协议头，目的端口固定四千七百八十九，源端口通常由内层流哈希得到，以便底层做等价多路由时能把同一条流稳定送到同一条链路；然后是八字节的虚拟扩展局域网头；最里面是原始二层帧。

虚拟扩展局域网头只有八字节，字段如下：第一字节最高位是标志位，必须置一表示网络标识有效，其余七位保留；接下来两字节保留；再接下来三字节是二十四位网络标识；最后一字节保留。头部极简是它的优点也是缺点——没有地方放元数据，想携带额外信息只能换通用网络虚拟化封装。

:::figure id=PROTO-08-01 | name=虚拟扩展局域网封装层次与芯片读取字段 | dir=TB
node n1 "外层以太网头" blue
node n2 "外层网际协议头<br/>端点地址" teal
node n3 "用户数据报协议头<br/>目的端口四七八九" amber
node n4 "虚拟扩展局域网头<br/>二十四位网络标识" green
node n5 "内层以太网头<br/>租户媒体地址" purple
node n6 "内层网际协议头<br/>租户地址与五元组" blue
edge n1 -> n2 "承载"
edge n2 -> n3 "承载"
edge n3 -> n4 "定位隧道"
edge n4 -> n5 "标识租户"
edge n5 -> n6 "业务报文"
:::

图中节点速览：从 n1 到 n6 是由外向内的封装层次。芯片解析时只关心三个字段——n3 的目的端口判封装类型、n4 的网络标识查隧道终止表、n5 与 n6 的内层地址查媒体地址表和路由表。外层地址只用于底层转发，不参与租户决策。

### 2. 隧道端点的两种形态

隧道端点是封装和解封装的终点，可以配在物理交换机上，也可以跑在虚拟交换机里。硬件端点性能高、时延稳定，适合物理网络和高性能虚拟机；软件端点灵活、可以随虚拟机迁移，但消耗中央处理器资源。自研交换机通常只做硬件端点，软件端点由宿主机承担。

端点地址通常用环回口地址，原因有三：环回口永远在线，不会因为物理链路故障而消失；一个物理设备只有一个稳定标识，便于底层路由收敛；故障时隧道端点不变，只需要更新底层路由，控制面不需要重新通告所有地址。

### 3. 单播与广播类流量的两条路

已知单播走查表路径：入口查隧道终止表确定网络标识，查媒体地址表找到远端端点，查邻接表得到封装参数，出口封装发出。这条路径完全确定，不需要泛洪。

广播未知单播组播走复制路径：入口查头端复制表得到端点清单，按清单复制 N 份并分别封装。复制份数等于清单长度，这也是头端复制的开销所在。用底层组播时，清单变成一个组播组地址，数据面只发一份，由底层网络设备复制。

| 对比项 | 头端复制 | 底层组播 |
|---|---|---|
| 复制位置 | 每个入口设备各自复制 | 底层网络设备复制 |
| 入口封装次数 | 端点数量 N 次 | 一次 |
| 对底层要求 | 只需单播可达 | 需要协议无关组播 |
| 表项 | 头端复制表存端点清单 | 头端复制表存组播地址 |
| 适用规模 | 端点较少时 | 端点较多时 |

### 4. 最大传输单元与哈希

封装增加了五十到五十四字节开销。底层链路最大传输单元如果还是一千五百字节，内层一千五百字节的报文封装后必然分片或丢弃。生产环境必须把底层最大传输单元提到一千六百字节以上，或者把虚拟机侧最大传输单元降到一千四百五十字节。排障时"小包通、大包不通"几乎都是这个原因。

等价多路由哈希也要专门处理。如果芯片只看外层五元组，源端口取自内层哈希虽然有一定分散度，但同一条内层流的所有报文封装后源端口相同，会稳定落到同一链路——这本来是好事，但如果租户数量少而流数多，分散度不够。高端芯片支持把内层五元组纳入哈希输入，让同一租户的不同流也能分摊。

### 5. 芯片查表链

```text
入口解析: 读取 UDP.dport=4789 -> tunnel_type=VXLAN
入口元数据: vni=VNI字段, inner_dmac, inner_smac, inner_dip, inner_sip
隧道终止表键: tunnel_type + outer_dip + vni -> 桥接域 / 虚拟路由转发
媒体地址表键: 桥接域 + inner_dmac -> 本地端口 或 远端端点 + 标签
邻接表键: 远端端点 -> 外层封装模板索引
出口改写: 外层源目的地址 + UDP源端口(内层哈希) + VNI + 内层帧
```

这段伪代码揭示了两个工程要点。第一，隧道终止表的键必须包含 tunnel_type——支持多种封装时，同样的虚拟网络标识值在不同封装里属于不同租户空间。第二，邻接表给出的是封装模板索引而非完整报文头，这样同一远端端点的多条流可以共享模板，节省表项空间。

### 6. 头部八字节逐字节与源端口推导

虚拟扩展局域网头只有八字节，值得逐字节看清楚，因为芯片的解析模板就是按这个布局写的。

| 字节偏移 | 字段 | 长度 | 取值与作用 |
|---|---|---|---|
| 第零字节 | 标志位 | 一字节 | 最高位为一表示网络标识有效，其余七位必须为零 |
| 第一到二字节 | 保留 | 两字节 | 发送端置零，接收端忽略 |
| 第三到五字节 | 网络标识 | 三字节 | 二十四位租户标识，芯片按它查隧道终止表 |
| 第六字节 | 保留 | 一字节 | 发送端置零，接收端忽略 |

标志位不是随便设的。如果收到标志位最高位为零的报文，说明网络标识字段无意义，接收端应丢弃——这是防止把其他协议的报文误认成虚拟扩展局域网的基本校验。源端口的取值同样有讲究：它取自内层五元组的哈希，落在动态端口范围。这样底层做等价多路由时，同一条内层流的报文源端口相同、哈希结果相同、走同一条链路，不会出现同一条流的包乱序；不同流则分散到不同链路。

```text
外层以太网: 目的 00:11:22:33:44:55  源 66:77:88:99:aa:bb  类型 0x0800
外层网际协议: 源 10.0.0.1  目的 10.0.0.2  协议 17
用户数据报协议: 源端口 49168 (内层流哈希)  目的端口 4789  长度 1088
虚拟扩展局域网头: 08 00 00 00 27 71 00   -> 标志 0x08, 网络标识 0x2771 = 10097
内层以太网: 目的 00:55:66:77:88:99  源 aa:bb:cc:dd:ee:ff  类型 0x0800
内层网际协议: 源 192.168.10.10  目的 192.168.20.20
```

这段抓包展开可以直接对照芯片元数据：网络标识 10097 是隧道终止表的查找键之一；内层目的媒体地址是媒体地址表的查找键；内层目的网际协议地址是虚拟路由转发最长前缀匹配表的查找键；用户数据报协议源端口 49168 是底层等价多路由哈希的输入。四个字段分属三张表，却都在同一个报文里——这正是单遍处理能成立的前提。

## PROTO-09 Geneve 与虚拟扩展局域网通用协议扩展精讲

### 1. 为什么需要可变长选项

虚拟扩展局域网的固定头无法携带元数据。现代软件定义网络需要在封装里传递的东西很多：源虚拟网络标识、负载均衡器标签、服务链路径标识、安全组标签、分布式防火墙上下文。通用网络虚拟化封装用可变长选项字段解决这件事，它把每个元数据编码成一个选项，多个选项顺序排列。

通用网络虚拟化封装头固定部分八字节：版本两位、选项长度六位、标志位八位、协议类型十六位、虚拟网络标识二十四位、保留八位。选项长度以四字节为单位，后面跟着若干个选项，每个选项由类别、类型、保留位和长度组成，长度同样以四字节为单位。接收端按选项长度跳过整个选项区——这就是可扩展性的来源：新选项加进来，老设备虽然不认识，但能正确跳过，不会解析错乱。

node n3 "协议类型与虚拟网络标识" amber
node n4 "选项区<br/>类别与类型" green
node n5 "选项一<br/>服务链标签" purple

edge n4 -> n5 "可跳过的选项"

:::

图中节点速览：n1 是固定头，n2 与 n3 是其中的关键字段，n4 是选项区；n5 与 n6 是具体选项。老设备即使不认识 n5 或 n6，也能靠选项长度字段跳过它们继续解析内层报文——这正是通用网络虚拟化封装优于固定头封装的核心。

### 2. 芯片支持的代价

可变长选项对交换机芯片不友好。固定头解析是硬件线速的，可变长选项需要逐项解析、判断长度、提取关心的选项，这些操作会占用解析器状态和阶段资源。因此很多硬件交换机对通用网络虚拟化封装的支持是"解析虚拟网络标识、跳过选项区"，不提取选项内容；要按选项内容做策略，可能要退化到软件或多遍处理。

选型时必须确认芯片能力：如果业务只需要虚拟网络标识隔离，通用网络虚拟化封装没问题；如果要按服务链标签或安全上下文做硬件策略，先确认芯片能不能把这些选项字段放进匹配动作的键里。

| 对比项 | 虚拟扩展局域网 | 通用网络虚拟化封装 |
|---|---|---|
| 头部长度 | 固定八字节 | 八字节加可变选项 |
| 目的端口 | 四七八九 | 六零八一 |
| 元数据能力 | 无 | 可变长选项 |
| 硬件解析复杂度 | 低 | 中到高 |
| 生态成熟度 | 最高 | 逐步普及 |
| 典型场景 | 通用数据中心 | 服务链与安全上下文 |

虚拟扩展局域网通用协议扩展是另一条路线，它在虚拟扩展局域网头里增加通用协议扩展字段，目的端口四七九零，可以承载多种协议负载。它保留了虚拟扩展局域网的简洁性，同时提供一定扩展能力，但生态支持度远不如前两者，多见于特定厂商设备之间的互联。

## PROTO-10 网络虚拟化通用路由封装、通用路由封装、标签交换与骨干桥接精讲

### 1. 网络虚拟化通用路由封装

微软路线把二十四位虚拟专用网络标识放进通用路由封装的键值字段，透明桥接以太网负载。它不需要用户数据报协议，直接跑在通用路由封装协议号四十七上。优点是复用已有的通用路由封装基础设施，缺点是无法使用用户数据报协议源端口做等价多路由哈希——哈希只能依赖外层网际协议五元组，分散度不如虚拟扩展局域网。

芯片侧要支持通用路由封装解析，再按键值字段构造虚拟网络标识。如果设备原本不支持通用路由封装，增加支持意味着解析器模板和隧道终止表键都要改，这是选型时容易被低估的成本。

### 2. 标签交换路线

运营商网络里以太虚拟专用网络常承载在标签交换数据面上。控制面还是以太虚拟专用网络路由，但数据面用标签栈而不是用户数据报协议封装。第一类路由和第二类路由携带的标签直接成为标签栈的标签，外层标签用于底层标签交换转发，内层标签标识租户或站点。

这与虚拟扩展局域网最大的区别是：底层网络是标签交换网络而不是普通网际协议网络，中间设备不需要解析覆盖封装，只按外层标签转发。优势是转发效率高、服务质量机制成熟；劣势是底层必须全网支持标签分发和标签交换，改造成本高。

### 3. 运营商骨干桥接

骨干桥接把客户媒体地址帧再包一层骨干媒体地址头，用骨干媒体地址和业务实例标识隔离租户。以太虚拟专用网络与它结合后，控制面用以太虚拟专用网络分发地址，数据面用骨干桥接封装。芯片侧要多查一张骨干实例表，把业务实例标识映射到桥接域。

| 封装 | 底层网络 | 标识位置 | 芯片主要表项 | 适用场景 |
|---|---|---|---|---|
| 虚拟扩展局域网 | 普通网际协议网络 | 用户数据报协议后的头 | 隧道终止表与媒体地址表 | 数据中心 |
| 通用网络虚拟化封装 | 普通网际协议网络 | 固定头加选项 | 隧道终止表与选项匹配表 | 需要元数据 |
| 网络虚拟化通用路由封装 | 普通网际协议网络 | 通用路由封装键值 | 通用路由封装解析表 | 微软生态 |
| 标签交换 | 标签交换网络 | 标签栈 | 标签转发表 | 运营商 |
| 骨干桥接 | 二层骨干网络 | 骨干媒体地址与实例 | 骨干实例表 | 运营商扩展 |

## PROTO-11 底层内部网关协议精讲：开放最短路径优先与中间系统到中间系统

### 1. 两种协议的共同骨架

开放最短路径优先和中间系统到中间系统都是链路状态协议，骨架完全相同：先建邻居、再泛洪链路状态信息、每台设备算出全图、用最短路径算法算出到每个目的的路径、写进路由表。差别在封装和术语——开放最短路径优先直接跑在网际协议协议号八十九上，中间系统到中间系统跑在数据链路层；开放最短路径优先的信息单元叫链路状态通告，中间系统到中间系统的叫链路状态报文；开放最短路径优先的广播网络指定路由器对应中间系统到中间系统的指定中间系统。

区域设计是两者共同的核心。骨干区域负责跨区域转发，非骨干区域只能通过骨干区域互通。这样做的好处是每台设备只维护本区域的详细拓扑，其他区域用汇总路由，大幅降低链路状态数据库规模。

| 对比项 | 开放最短路径优先 | 中间系统到中间系统 |
|---|---|---|
| 承载 | 网际协议协议号八十九 | 数据链路层 |
| 信息单元 | 链路状态通告 | 链路状态报文 |
| 广播网络代表 | 指定路由器 | 指定中间系统 |
| 区域边界 | 区域边界路由器 | 边界中间系统 |
|  metric 粒度 | 接口开销 | 接口代价 |
| 典型场景 | 企业与数据中心 | 运营商 |

### 2. 邻居建立与状态

邻居建立经历关闭、尝试、初始化、双向、交换、加载、完全邻接几个阶段。双向状态是重要分水岭——到达这一步说明双向通信正常，但还没有同步数据库。广播网络上只有指定路由器与所有设备建立完全邻接，非指定路由器之间停留在双向状态，这是为了减少邻接数量。

卡在双向状态通常是链路状态数据库同步失败；卡在初始化往往是 hello 参数不匹配，比如区域号、认证、网络类型、hello 间隔或失效间隔不一致。

### 3. 在覆盖网络里的作用

底层内部网关协议只负责让交换机环回口互相可达，不感知任何租户信息。它产生的路由写进最长前缀匹配表，下一跳是直连设备的接口地址，邻接表由地址解析协议解析得到。以太虚拟专用网络路由的下一跳是远端环回口，要靠底层路由递归解析才能找到出口——这就是底层路由缺失会导致"以太虚拟专用网络路由学到了但表项写不进"的原因。

```text
show ip route 10.0.0.2
  Routing entry for 10.0.0.2/32
  Known via "ospf 1", distance 110, metric 20
  Last update from 192.0.2.2 on Ethernet1
  Routing Descriptor Blocks:
  * 192.0.2.2, from 10.0.0.2, via Ethernet1
```

判读：目的地址是远端环回口三十二位主机路由，由开放最短路径优先学到，下一跳是直连地址 192.0.2.2，出接口是以太网一口。如果这条路由消失，所有以 10.0.0.2 为下一跳的以太虚拟专用网络路由都无法递归解析，现象是路由表里还有以太虚拟专用网络路由但数据面表项为空。

## PROTO-12 外部边界网关协议底层架构精讲

### 1. 为什么大型闭合网络用外部边界网关协议

数据中心的闭合网络如果跑内部网关协议，所有设备在同一自治系统，需要全互联或路由反射器，链路状态数据库规模随设备数增长；而每台设备一个自治系统、全部跑外部边界网关协议时，每台设备只需知道直连邻居，路由通过自治系统路径传递，天然避免环路，也天然支持等价多路由。这是大型闭合网络的主流选择。

### 2. 关键配置要点

每台设备一个自治系统，环回口宣告进边界网关协议，邻居用环回口或直连口建立。为了让下一跳可达，通常配置下一跳自身；为了让所有设备都能学到所有环回口，需要合理的路由反射或全互联策略。等价多路由上限要显式调大，默认值通常只有一或二。

```text
router bgp 65001
 bgp router-id 10.0.0.1
 bgp log-neighbor-changes
 neighbor 192.0.2.2 remote-as 65002
 neighbor 192.0.2.2 bfd
 !
 address-family ipv4 unicast
  neighbor 192.0.2.2 next-hop-self
  neighbor 192.0.2.2 activate
  maximum-paths 16
  network 10.0.0.1 mask 255.255.255.255
 exit-address-family
```

判读：本地自治系统六万五千零一，邻居是对端自治系统；启用快速检测；在网际协议单播地址族下对邻居设置下一跳自身，让对端学到的路由下一跳指向本机而不是更后面的设备；等价多路由上限十六，充分利用多链路；宣告本机环回口三十二位路由。注意下一跳自身只对外部边界网关协议邻居生效，对内部邻居默认不改下一跳。

### 3. 收敛的三段构成

底层收敛时间由三段构成：故障检测、路由重算、表项刷新。快速检测把第一段从秒级压到毫秒级；外部边界网关协议的对等体撤销和路由撤回决定第二段；芯片表项批量更新能力决定第三段。只优化其中一段，整体收敛可能仍卡在最慢的那段——这是"配了快速检测但收敛还是慢"的常见原因。

## PROTO-13 双向转发检测精讲

### 1. 检测机制

双向转发检测是一种独立的轻量hello机制，不依赖路由协议自己的保活计时器。会话两端周期性发送检测报文，如果在检测倍数乘发送间隔的时间内收不到对端报文，就判定会话失效，并通知绑定的路由协议。控制报文走用户数据报协议端口三千七百八十四，回声报文走三千七百八十五。

会话有四种状态：管理关闭、关闭、初始化、正常。任何一端进入关闭，绑定的路由邻居就失效；恢复要从初始化重新协商。会话是全双工独立的——一端失效就通知本地路由协议，不需要等对端确认。

:::figure id=PROTO-13-01 | name=双向转发检测与路由协议的联动 | dir=LR
node n1 "周期性检测报文" blue
node n2 "计时器超时" teal
node n3 "会话状态转为关闭" amber
node n4 "通知路由协议邻居失效" green
node n5 "撤销路由并重算" purple
node n6 "刷新芯片邻接表" blue
edge n1 -> n2 "收不到对端"
edge n2 -> n3 "超过倍数"
edge n3 -> n4 "触发回调"
edge n4 -> n5 "路由收敛"
edge n5 -> n6 "表项更新"
:::

图中节点速览：n1 到 n3 是检测层，n4 到 n6 是路由与数据面层。这条链说明快速检测只解决 n1 到 n3 这段——后面两段该花的时间一点没少，所以收敛优化必须端到端看。

### 2. 参数与误区

典型配置是发送间隔三百毫秒、接收间隔三百毫秒、倍数三，即约九百毫秒判定失效。间隔太小会带来两个问题：一是中央处理器或转发芯片的定时精度不够，产生误报；二是大量会话的检测报文本身成为负担。生产环境三百到五百毫秒起步，关键链路可以更激进。

一个常见误区是认为快速检测能感知所有故障。它感知的是检测路径上的双向可达性。如果中间设备只丢弃业务报文而不丢检测报文，检测仍然正常，流量却已经黑洞。所以快速检测要和业务层探测、接口错误计数一起看。

### 3. 检测报文格式与状态迁移细节

双向转发检测的会话状态藏在检测报文的状态字段里，理解这几个字段就能从抓包直接判断会话为什么起不来。

| 字段 | 位数 | 含义 | 判读要点 |
|---|---|---|---|
| 版本 | 三 | 协议版本，当前为一 | 不匹配直接丢弃 |
| 诊断码 | 五 | 最近一次会话 down 的原因 | 零为无诊断，一为检测超时，三为邻居会话关闭 |
| 状态 | 二 | 管理关闭、关闭、初始化、正常四态 | 是最常看的字段 |
|  Poll 与最终位 | 各一 | 用于参数协商 | 建邻阶段置一 |
| 控制与认证位 | 各一 | 控制平面辅助与认证指示 | 影响处理路径 |
| 主动与按需位 | 各一 | 是否主动发送、是否按需模式 | 按需模式不周期发包 |
| 检测倍数 | 八 | 判定失效的倍数 | 与接收间隔相乘得超时时间 |
| 长度 | 八 | 整个检测报文长度 | 不含认证时通常二十四字节 |
| 本端与对端鉴别符 | 各三十二 | 唯一标识会话两端 | 对端鉴别符为零说明还没收到对端报文 |
| 发送与接收间隔 | 各三十二 | 微秒单位的期望与要求间隔 | 两端取较大值生效 |

状态迁移遵循确定性规则：本端关闭且收到对端关闭时进入初始化；本端初始化且收到对端初始化或正常时进入正常；本端正常且收到对端关闭或检测超时时退回关闭；管理置位则进入管理关闭并对外通告。两端状态不一致是建邻失败时最常见的原因——一端卡在初始化、另一端仍是关闭，通常是一端的检测报文没送到对端。

```text
帧长 24 字节, 关键字段展开:
  版本 1, 诊断码 0 (无诊断), 状态 2 (初始化)
   Poll 位 1, Final 位 1 (正在协商参数)
  检测倍数 3, 报文长度 24
  本端鉴别符 0x00000001, 对端鉴别符 0x00000000
  期望发送间隔 300000 微秒, 要求接收间隔 300000 微秒
判读: 状态为初始化且对端鉴别符为零, 说明本端发过报文但从未收到对端回应,
      先查底层可达与访问控制, 不要急着改检测倍数
```

抓包时最实用的三个字段是状态、对端鉴别符和诊断码：状态看卡在哪一步，对端鉴别符看是否收到过对端报文，诊断码看上次断开是谁触发的。这三者结合，能区分"从未建邻"和"建邻后震荡"两类完全不同的问题。

## PROTO-14 链路聚合与底层组播精讲

### 1. 链路聚合控制协议

链路聚合把多条物理链路绑成一条逻辑链路，带宽叠加且提供冗余。链路聚合控制协议通过对端交互链路聚合控制协议报文协商成员状态：两端各自有系统优先级和系统标识，端口有端口优先级和端口号，组合成系统标识加端口标识的二元组。一端选出主端口，对端根据主端口标识选择一组成员，只有两端都选中的成员才能转发。

成员选择有几条硬约束：速率必须一致、双工模式必须一致、虚拟局域网配置必须一致、最大传输单元必须一致。配置不一致的成员会被置为未选中，现象是聚合口带宽不足但没有明显报错。

| 状态 | 含义 | 排查方向 |
|---|---|---|
| 已选中 | 两端协商一致，可转发 | 状态正常 |
| 未选中 | 本端或远端不同意 | 查速率双工与虚拟局域网配置 |
| 等待 | 暂时不可用 | 查链路物理状态 |
| 挂起 | 手工关闭 | 查管理配置 |

跨设备链路聚合把两台汇聚交换机虚拟成一台，客户设备双挂的两条链路属于同一个聚合组。这要求两台汇聚交换机之间同步聚合状态与媒体地址表，控制面开销不小，但换来的是全活冗余和简化的二层拓扑。以太虚拟专用网络的多归属是另一种思路——不虚拟成一台设备，而是用以太网段标识符和指定转发器选举协调两台设备。

### 2. 底层组播协议

用组播复制广播类流量时，底层要跑协议无关组播。它建立从组播源到接收者的树，树有两种：源特定组播建立最短路径树，任意源组播先建共享树再可能切换到最短路径树。第三类路由携带的网际协议地址就是组播组地址，数据面封装后按底层组播转发表复制。

排障时要区分"组播控制面没建起来"和"以太虚拟专用网络没通告组播地址"。前者查协议无关组播的邻居与上游接口，后者查第三类路由是否携带了预期的组播组地址。两者任何一个缺失，广播类流量都不通，但排查入口完全不同。

## PROTO-15 二层三层基础协议精讲

### 1. 虚拟局域网与八零二点一Q

虚拟局域网把一个物理二层网络切成多个逻辑广播域。八零二点一Q 在以太网帧里插入四字节标签，其中十二位是虚拟局域网标识，总共四千零九十六个值，扣除保留值后可用约四千个。标签还包含三位优先级和一位丢弃资格指示，用于服务质量。交换机端口分接入模式和干道模式：接入模式只属于一个虚拟局域网，发出帧不带标签；干道模式承载多个虚拟局域网，发出的帧带标签。

虚拟局域网的价值不只是隔离，还有控制广播域大小。一个二层域里主机数量越多，广播和未知单播泛洪越严重。虚拟局域网把大域切成小域，是虚拟扩展局域网出现前最主要的手段。但四千个标识撑不起多租户云，这正是虚拟扩展局域网把标识扩展到二十四位的动因。

| 字段 | 位数 | 作用 | 芯片用途 |
|---|---|---|---|
| 优先级 | 三 | 服务质量等级 | 查服务质量表与队列映射 |
| 丢弃资格指示 | 一 | 拥塞时优先丢弃 | 丢弃策略输入 |
| 虚拟局域网标识 | 十二 | 广播域隔离 | 媒体地址表与桥接域查找键 |

### 2. 地址解析协议与新发现协议

地址解析协议把网际协议地址解析成媒体地址：主机发广播请求，目标主机单播应答。新发现协议在网际协议第六版里承担同样职责，用组播请求和应答替代广播。两者的共同问题是泛洪——每台主机都要处理别人的请求，规模一大就成瓶颈。

以太虚拟专用网络的地址解析抑制把这个过程搬到控制面，但传统网络里仍有几个优化手段值得知道：代理地址解析让网关代答，减少广播域内的泛洪；无偿地址解析用于检测地址冲突；静态绑定用于关键设备。在覆盖网络里，这些手段逐步被第二类路由取代，但接入侧如果还有未改造的传统网段，它们仍有价值。

### 3. 生成树与网关冗余

生成树通过阻塞冗余链路消除二层环路。它选举根桥，每台设备算到根的最短路径，阻塞不在最短路径上的端口。链路故障时重新计算并打开阻塞端口，收敛时间从几秒到几十秒不等。快速生成树把收敛压到秒级，多实例生成树让不同虚拟局域网跑不同的生成树实例，避免所有虚拟局域网共用一条阻塞链路。

虚拟路由器冗余协议和热备用路由器协议提供网关冗余：多台网关设备共享一个虚拟网际协议地址，一台主用负责转发，其他备用在主用失效时接管。在覆盖网络里，这套机制被分布式任播网关取代——所有站点都配相同的网关地址，每台设备都直接转发本地主机的网关流量，不需要主备切换。

| 传统机制 | 解决的问题 | 在覆盖网络里的去处 |
|---|---|---|
| 虚拟局域网 | 广播域隔离与标识 | 保留为本地桥接域，跨机架交给网络标识 |
| 地址解析协议 | 地址解析 | 被第二类路由抑制 |
| 生成树 | 二层防环 | 全局拓扑不用，接入侧仍保留 |
| 网关冗余协议 | 网关高可用 | 被分布式任播网关取代 |
| 虚拟专用局域网服务 | 运营商二层专线 | 被以太虚拟专用网络演进替代 |

## PROTO-16 从虚拟专用局域网服务到以太虚拟专用网络的演进精讲

### 1. 前代技术为什么被替代

虚拟专用局域网服务和虚拟专用专线服务是早期的运营商二层虚拟专用网络技术。它们都能把相隔两地的二层网络连起来，但有几个共同短板：控制面依赖标签分发且扩展能力有限；媒体地址学习靠数据面泛洪，规模上不去；多归属支持弱，冗余能力有限；配置复杂，跨运营商互通困难。

以太虚拟专用网络把控制面换成边界网关协议，直接带来三个好处：媒体地址通过路由通告而不是泛洪学习；路由目标提供灵活的地址隔离与导入导出控制；多归属通过以太网段标识符和指定转发器选举标准化。今天新建的二层虚拟专用网络几乎都以以太虚拟专用网络为控制面，老技术只在存量网络里还能见到。

### 2. 演进中的概念对应

理解老文档时，做个概念对应会快很多：虚拟专用局域网服务的客户边缘设备对应以太虚拟专用网络的客户边缘设备，但后者的控制面是边界网关协议邻居；前者的虚拟专用网络实例路由区分符和路由目标与后者同名但语义一致；前者靠标签分发协议分发的标签，在后者由第一类或第二类路由直接携带；前者的泛洪学习在后者变成第二类路由通告。

| 概念 | 前代技术 | 以太虚拟专用网络 |
|---|---|---|
| 控制面 | 边界网关协议加标签分发协议或专用协议 | 边界网关协议多协议扩展 |
| 地址学习 | 数据面泛洪 | 第二类路由通告 |
| 租户隔离 | 路由目标 | 路由目标，语义更完整 |
| 多归属 | 厂商私有扩展 | 以太网段标识符加指定转发器选举 |
| 可扩展性 | 中等 | 高 |

### 3. 迁移注意事项

存量网络迁移不可能一次切完，常见做法是双跑：老的控制面继续服务存量业务，新的以太虚拟专用网络控制面逐步接管。这时要特别注意两类问题：一是同一媒体地址从两条控制面学来，可能写进同一张媒体地址表互相覆盖，需要在表项里加来源标识；二是路由目标规划要兼容老网络，否则迁移过程中业务中断。

## PROTO-17 运维配套协议精讲

### 1. 建模语言与配置协议

网络配置协议用可扩展标记语言承载配置，支持候选配置、运行配置、启动配置三层模型，可以做配置锁定、变更校验和回滚。它解决了批量配置和变更可追溯的问题，缺点是报文冗长、交互复杂。远程过程调用接口用协议缓冲区编码，配合建模语言定义的数据结构，提供获取与设置两类操作，效率更高，是现代设备的首选。

建模语言本身不是协议，而是数据结构的定义方式。第二层三层虚拟专用网络的模型把虚拟网络标识、以太网段、路由目标、邻居等对象标准化，让不同厂商设备用相同路径表达相同配置。对交换芯片工程师来说，模型的字段最终要映射到芯片表项——字段设计得合不合理，直接决定配置能否高效落硬件。

### 2. 遥测与带内网络遥测

传统命令行取值是拉取模式，间隔长、粒度粗。流式遥测改成推送模式，设备按订阅周期主动上报计数器、队列深度、表项规模等数据，粒度可以做到亚秒级。这对定位瞬时拥塞和微突发非常关键——秒级采样根本看不到毫秒级的队列峰值。

带内网络遥测更进一步：源节点在报文里插入遥测指令，途经节点按指令把自身状态写进报文，目的节点收集整条路径的状态。它能回答"这个包到底经过了哪些设备、在哪个节点排了多久"这类传统手段无法回答的问题。代价是报文变大、需要目的端收集分析，而且芯片要支持遥测指令的插入与提取。

| 能力 | 采集方式 | 时间粒度 | 能回答的问题 |
|---|---|---|---|
| 命令行取值 | 拉取 | 秒到分钟 | 当前状态快照 |
| 流式遥测 | 推送订阅 | 亚秒级 | 状态随时间的变化趋势 |
| 带内网络遥测 | 报文内嵌 | 逐包逐跳 | 单个报文的实际路径与时延 |
| 镜像与采样 | 复制报文 | 按采样率 | 报文内容与异常流量 |

### 3. 镜像与采样

远程镜像把指定端口或流的报文复制到观察端口，再送到分析设备。芯片侧要有镜像表，键是端口或流标识，结果是目的端口和封装参数。采样流则按比例抽样，用采样概率控制开销，适合大流量场景的容量规划和异常发现。

两者的取舍：镜像看到全部报文但开销大，适合小范围精确定位；采样有统计意义但可能漏掉关键报文，适合发现趋势。排障时通常先用采样发现异常时间段和流，再用镜像在该时间段精确抓包。

## PROTO-18 协议协作全景与排障精讲

### 1. 一次报文旅程里的协议接力

把前面所有协议放进一次跨机架报文的旅程，会看到一条清晰的接力链。控制面先行：底层内部网关协议或外部边界网关协议让环回口可达；路由反射器通过以太虚拟专用网络第二类路由通告媒体地址，第三类路由通告复制清单，第五类路由通告网段；路由目标决定哪些站点接收；指定转发器选举决定谁能转发广播类流量；地址解析抑制把地址对提前写进表项。

数据面随后：报文进入入口交换机，解析器按目的端口识别封装，隧道终止表按网络标识确定桥接域与虚拟路由转发；媒体地址表决定本地交付还是远端转发；最长前缀匹配表处理跨网段；邻接表给出封装参数；头端复制表处理广播类流量；链路聚合表选成员链路；服务质量表决定队列与丢弃优先级；出口改写生成完整封装并串行化发出。底层网络只按外层地址做普通转发，完全不感知内层租户。

### 2. 分层排障法

排障的原则是自底向上、逐层证明，不要跳层。每证明一层，就把问题范围缩小一半。

| 层级 | 证明方法 | 通过后得到什么 | 不通过时查什么 |
|---|---|---|---|
| 物理层 | 接口状态与错误计数 | 链路可用 | 光模块、线缆、速率双工 |
| 链路聚合 | 成员选中状态 | 逻辑链路可用 | 两端配置一致性 |
| 底层路由 | 隧道端点可达性 | 端点之间可转发 | 内部网关协议邻居与路由 |
| 边界网关协议邻居 | 已建立状态 | 控制面通道可用 | 传输控制协议、自治系统号、更新源 |
| 地址族路由 | 收到第二类与第五类路由 | 控制面有结论 | 地址族激活、路由目标 |
| 芯片表项 | 媒体地址表与最长前缀匹配表 | 数据面有依据 | 递归解析、表项容量、写入失败 |
| 数据面转发 | 镜像抓包与计数器 | 报文按预期改写 | 解析模板、封装参数、哈希 |

### 3. 三组高频误区

第一组是把"邻居正常"等同于"控制面正常"。邻居只证明会话建立，路由是否收到、是否被导入、是否写进硬件表，是完全不同的三件事，要分别证明。

第二组是把"路由表有"等同于"转发表有"。边界网关协议路由的下一跳往往不是直连地址，递归解析失败时路由表里好好的，转发表里却没有。查邻接表和下一跳解析比反复看路由更有用。

第三组是把"协议问题"等同于"性能问题"。吞吐不达预期时，先确认是不是退化成多遍处理、哈希是否按内层字段、封装后报文是否超过最大传输单元——这些是数据面能力问题，改协议配置解决不了。

### 4. 收尾

这一篇把 08 篇列出的协议逐个拆到了报文字段、状态机、算法和芯片表项这一层。回头看会发现，协议再多，落到交换芯片上只有几类动作：解析出字段、用字段查表、按查表结果改写报文、按状态表决定复制与丢弃。之所以要精讲协议，是因为只有知道每个协议往哪张表写了什么，才能在表项异常时反推出是哪一层出了问题。

三篇文档的分工到这里就完整了：07 讲核心三协议如何协同并落表，08 给出完整生态地图与选型，本篇逐协议深挖机制。按 07 → 08 → 本篇的顺序读，先建主干、再看全景、最后深入细节；排障时则反过来，从本篇的现象定位表项开始。

## PROTO-19 芯片表项工程精讲：容量、键值与更新

### 1. 表项容量的三个维度

芯片表项不是一个抽象的"能存多少条"，而是由三个维度共同约束：键宽决定每条表项占多少存储单元，深度决定最多能存多少条，并发查表数决定一个报文周期内能查几次。三个维度互相制约——增加键宽会减少同样芯片面积下能容纳的表项数；增加深度会增加访问时延；增加并发查表数会增加功耗和面积。

工程上评估容量不能只看"路由表有多少条"。以虚拟扩展局域网场景为例，一万台主机意味着媒体地址表至少一万条，但如果每台主机同时有网际协议地址要抑制，抑制表还要再来一万条；每个租户一个网络标识，每个网络标识一张头端复制表，复制表条目数是端点数乘网络标识数；所有远端端点都要有邻接项。把这些加起来，实际容量需求往往是路由条目的数倍。

| 表项类型 | 查找键 | 查得结果 | 典型容量量级 | 更新触发 |
|---|---|---|---|---|
| 隧道终止表 | 封装类型加端点地址加网络标识 | 桥接域与虚拟路由转发 | 万级 | 隧道接口配置与网络标识映射 |
| 媒体地址表 | 桥接域加内层目的媒体地址 | 本地端口或远端端点加标签 | 十万级 | 第二类路由与本地学习 |
| 地址解析抑制表 | 网络标识加网际协议地址 | 媒体地址与端点 | 万级 | 第二类路由携带地址对 |
| 最长前缀匹配表 | 虚拟路由转发加目的地址 | 下一跳标识与出接口 | 十万级 | 第五类路由与底层路由 |
| 邻接表 | 下一跳标识 | 媒体地址与封装模板索引 | 万级 | 递归解析与链路状态 |
| 头端复制表 | 网络标识或组播组 | 端点清单与复制份数 | 千级 | 第三类路由 |
| 访问控制表 | 网络标识加内层五元组 | 允许丢弃重定向与标记 | 万级 | 策略下发 |

### 2. 键值设计的讲究

复合键的设计直接决定查表次数。以媒体地址表为例，如果只用内层目的媒体地址做键，不同租户的相同媒体地址会互相覆盖，必须用桥接域加媒体地址做复合键——这正是网络标识必须参与查找的原因。同理，最长前缀匹配表要带虚拟路由转发标识，否则不同租户的相同网段会冲突。

但键不是越多越好。每增加一个键字段，表项宽度增加，同样芯片面积下深度下降，而且键值构造要占用解析器元数据。工程上的取舍是：能由上游阶段收窄的字段不放进键。比如隧道终止表已经把网络标识映射成桥接域，媒体地址表就只需桥接域而不必再带网络标识——桥接域已经表达了租户归属。

### 3. 更新的一致性问题

控制面下发一条路由要改最长前缀匹配表、邻接表和可能的多路径表。如果芯片逐条写入，中间状态会出现"路由指向还没建好的邻接"，数据面查到空邻接就丢包。高并发场景下这种瞬态黑洞可能持续几十毫秒，对金融类流量不可接受。

主流解决办法有三种。一是批量原子提交：控制面把一组更新放进事务缓冲，芯片以内部锁存方式一次性切换。二是两阶段写入：先写不生效的影子表项，全部写完后再翻转生效位。三是版本化表项：表项带版本号，报文按当前版本号查对应版本。三种办法的代价分别是需要额外缓冲、需要双倍表项空间、需要版本管理逻辑。

```text
事务开始
  写邻接表项 A(状态=未生效, 引用计数+1)
  写最长前缀匹配项 P -> A(状态=未生效)
  写多路径组 ECMP-1 成员 +A
  校验引用完整性: P->A 存在, A 已分配, ECMP 成员有效
事务提交: 原子翻转生效位
  旧表项 A-old 引用计数-1, 归零后回收
事务结束
```

这段伪代码的重点是校验与回收：提交前必须检查引用完整性，否则会出现悬空指针；提交后旧表项不能立即删除，要等引用计数归零，否则正在处理中的报文可能还在用旧表项。自研设备常见的表项泄漏，根源就是回收时机没处理好。

### 4. 表项老化的边界

数据面学到的媒体地址要老化，控制面通告的第二类路由不能按同样方式老化——它由路由撤销驱动。两套机制混在一起会出问题：数据面把控制面下发的表项老化掉了，控制面却认为路由还在，不再重发，结果表项永久丢失。

正确做法是在表项里标记来源位：本地学习项允许硬件老化，控制面下发项只允许路由撤销删除。地址解析抑制表同理，本地探测生成的项可老化，第二类路由生成的项跟随路由生命周期。

## PROTO-20 控制面与数据面交互时序精讲

### 1. 从主机上线到首包转发

主机上线这件事，控制面和数据面是并行工作的：数据面靠本地学习先建立表项，控制面靠路由通告让其他站点知道。理解这个时序，才能解释"为什么有时候刚上线就能通，有时候要等几秒"。

| 时刻 | 触发事件 | 控制面动作 | 数据面动作 | 表项状态 |
|---|---|---|---|---|
| T0 | 主机发出第一个报文 | 尚未感知 | 解析内层地址，本地学习写入媒体地址表 | 只有本地项 |
| T1 | 本地学习完成 | 生成第二类路由发给反射器 | 后续已知单播可本地转发 | 本地项生效 |
| T2 | 反射器收到路由 | 反射给所有站点 | 无 | 对端尚未感知 |
| T3 | 对端收到并导入 | 写远端媒体地址项与抑制项 | 已知单播可直接封装 | 跨站点项生效 |
| T4 | 对端主机发起访问 | 无 | 查抑制表直接封装，不泛洪地址解析请求 | 抑制生效 |
| T5 | 后续广播类流量 | 第三类路由已就位 | 按头端复制表复制 | 复制表生效 |

T0 到 T3 之间是不通窗口：目的站点还没收到第二类路由，只能按未知单播泛洪，靠数据面学习补齐。这就是刚上线时前几个包可能丢失或延迟的原因。如果地址解析抑制已开启，对端在 T3 之后不再发广播请求，广播量下降的时间点比 T3 略晚一点。

:::figure id=PROTO-20-01 | name=主机上线到跨站点转发的时序 | dir=TB
node n1 "T0 主机上线发首包" blue
node n2 "T1 本地学习写表" teal
node n3 "T2 生成第二类路由" amber
node n4 "T3 对端导入写远端项" green
node n5 "T4 抑制地址解析请求" purple
node n6 "T5 广播类按复制表转发" blue
edge n1 -> n2 "触发学习"
edge n2 -> n3 "产生路由"
edge n3 -> n4 "反射并落表"
edge n4 -> n5 "抑制生效"
edge n5 -> n6 "复制表就位"
:::

图中节点速览：n1 到 n2 是纯数据面，n3 到 n4 是纯控制面，n5 与 n6 回到数据面效果。这条时序说明一个常被忽略的事实——控制面收敛时间和数据面首包时延不是同一件事，首包可以在控制面收敛前靠泛洪出去，但广播量要等控制面完成后才下降。

### 2. 路由撤销的逆时序

撤销比上线更危险。路由撤销时控制面先删表项，数据面可能还有在途报文引用旧表项；如果旧表项被立即回收，在途报文会查到空项而丢弃。所以撤销时序要与更新时序相反：先标记表项失效但保留内容，等在途引用清零，再真正回收。

链路故障时的顺序也很关键：双向转发检测先发现、邻接表标记不可用、路由协议撤路由、最长前缀匹配表更新、最后芯片表项刷新。如果邻接表没先标记，路由重算期间数据面还在往故障链路发包，形成黑洞。这也是为什么双向转发检测必须绑定邻接而不是只绑定路由邻居。

### 3. 时序日志判读

```text
T+0.000  主机 192.168.10.10 上线, 首包到达入口
T+0.002  本地学习: MAC 00:11:22:33:44:55 -> 端口 Ethernet1
T+0.004  生成第二类路由 RD 10.0.0.1:10100, 发往反射器
T+0.031  反射器收到, 反射给 3 个站点
T+0.048  对端 10.0.0.2 导入路由, 写远端媒体地址项
T+0.049  对端写地址解析抑制项, 后续请求不再泛洪
T+0.052  首包在源端按未知单播泛洪, 目的端收到并学习
```

这段日志的时间刻度很有代表性：本地学习是毫秒级，路由反射是几十毫秒级，芯片表项写入又是毫秒级。整体不通窗口约五十毫秒。如果现场观测到几秒级窗口，问题不在协议本身，多半在路由反射器性能、路由目标匹配或芯片批量更新能力上。

## PROTO-21 典型故障案例精讲

### 1. 案例一：邻居正常但表项为空

现象是边界网关协议邻居已建立，路由反射器也在反射，但接入交换机的媒体地址表没有任何远端项。定位链是：先确认地址族是否激活——没激活时邻居能建但不会交换该地址族路由；再确认收到的路由是否被导入——查看路由的路由目标与本地虚拟路由转发的导入目标是否有交集；最后确认表项写入是否成功——查芯片表项计数与写入错误日志。

这类问题九成出在路由目标。路由目标写法在两端必须完全一致，包括自治系统号和网络标识。常见错误是一端用 network-identifier 十六进制、另一端用十进制，控制面看起来都有配置，实际值不同。修复后不需要重建邻居，只要重发路由刷新即可。

### 2. 案例二：路由表有但转发表没有

现象是路由表里能看到目的前缀，最长前缀匹配表里却查不到，数据面丢包。原因是下一跳递归解析失败——边界网关协议路由的下一跳是远端环回口，设备要先查底层路由找到怎么到达这个环回口，再解析出二层地址。底层路由缺失、邻接表项没建好、或者环回口地址被策略过滤，都会导致递归失败。

定位顺序：查底层路由有没有下一跳的三十二位主机路由；查邻接表里下一跳是否解析成功；查是否有策略把底层路由过滤掉。修复底层问题后路由会自动重新递归，不需要动边界网关协议配置。

### 3. 案例三：同一网络标识二层不通

现象是两台主机在同一个虚拟网络标识，互相 ping 不通，但其他网络标识正常。先查隧道终止表——网络标识映射是否与对端一致；再查媒体地址表——桥接域加内层媒体地址的键是否正确；最后查第二类路由是否携带了正确的网络标识标签。

最常见的根因是虚拟局域网到网络标识的映射两端不一致。控制面通告的标签是一套值，数据面配置的映射是另一套值，路由学进来了但查表用另一个键，结果表项永远空。这类问题在改造扩容时高发——新增机架时复制了旧配置但忘了改映射。

### 4. 案例四：广播量突然暴涨

现象是地址解析协议广播在几秒内增长一个数量级，中央处理器占用随之升高。先查第二类路由有没有被撤销——路由撤销会连带删除抑制项；再查抑制项是否因为来源标记错误被硬件老化掉；最后查是否有大量主机同时上线——这是正常现象，抑制表还没建立。

前面讲过的来源位是这里的关键：控制面下发的抑制项如果没标记来源，硬件会按本地学习项的老化时间把它删掉，而控制面认为路由还在、不会重发，于是抑制项永久丢失。修复方式是给表项加来源位并区分老化策略。

### 5. 案例五：小包通、大包不通

现象是网际协议探针可以通，传输控制协议大包传输失败或严重分片。几乎都是封装后超过底层最大传输单元。虚拟扩展局域网增加五十到五十四字节，通用网络虚拟化封装增加更多且选项区可变。底层链路最大传输单元一千五百时，内层一千五百字节报文封装后必然超限。

验证方法：逐步减小网际协议探针的有效负载，找到临界值；临界值减去封装开销就是底层最大传输单元。修复要么提高底层最大传输单元到一千六百以上，要么把虚拟机侧最大传输单元降到一千四百五十。只有一端改不行，必须整条路径统一。

### 6. 案例六：吞吐低于预期

现象是链路带宽十吉，实际转发只有三四吉，接口没有错误计数。排查顺序：确认是否退化成多遍处理——某些字段组合触发多遍后吞吐会腰斩；确认哈希是否按内层字段——只看外层五元组时同一租户的流可能全落一条链路，链路利用率极不均衡；确认封装后报文长度——小包比例高时每秒包数才是瓶颈。

```text
排查命令组合:
  show interfaces counters detail     -> 看每条成员链路的流量是否均衡
  show platform forwarding resource   -> 看解析深度与多遍处理计数
  show platform qos queue-statistics  -> 看是否有队列持续拥塞
  show platform tbl utilization       -> 看表项是否接近容量上限触发退化
判读: 成员链路流量差异超过 3 倍 -> 哈希不均;
      多遍处理计数持续增长 -> 字段组合超出单遍能力;
      队列深度周期性冲顶 -> 缓冲区或调度参数需调整
```

这四个命令分别对应四个不同的瓶颈维度——链路利用率、解析能力、队列调度、表项容量。吞吐问题不要凭直觉调服务质量参数，先用命令把瓶颈维度定下来。

## PROTO-22 数据面性能调优精讲

### 1. 单遍与多遍的分界

单遍处理指报文从入口到出口只走一次解析和查表流水线，中途不回到前面的阶段。多遍则是查表结果要求重新解析或再次查表——比如隧道解封装后要按内层报文重新走一遍二层三层查表，或者访问控制结果要求重定向到另一张表。

决定能否单遍的关键是查表依赖链。如果后续阶段需要的键在前一阶段就能算出来，就能单遍；如果必须等前一阶段查完才知道下一阶段的键，且中间隔了不支持转发的阶段，就要多遍。虚拟扩展局域网场景里，隧道终止表给出桥接域后媒体地址表才能查——如果这两张表在同一入口阶段内，就是单遍；如果隧道终止在入口、媒体地址查表在出口，就要多遍。

| 处理方式 | 吞吐影响 | 时延影响 | 触发条件 | 优化方向 |
|---|---|---|---|---|
| 单遍 | 基线 | 基线 | 键都在入口可得 | 维持 |
| 两遍 | 约降一半 | 增加 | 解封装后需重查 | 把内层表前移到入口 |
| 查表依赖串行 | 视级数而定 | 每级累加 | 后级键依赖前级结果 | 并行预取与键构造前移 |
| 回环到入口 | 降幅最大 | 最大 | 重定向或复杂服务链 | 尽量在出口完成 |

### 2. 解析深度与字段提取

解析器能提取的字段数量和位置有硬件上限。虚拟扩展局域网加内层网际协议第六版加扩展头可能超出解析深度，超出后芯片只能提取部分字段，策略匹配就不完整。调优的常用手段是按需解析——只提取真正会用于查表的字段，把不用的字段留在报文里不动。

字段提取的另一个坑是元数据宽度。隧道类型、网络标识、桥接域、虚拟路由转发、内层地址、哈希值都要写进元数据，元数据寄存器位宽有限，字段多了要复用或分阶段覆盖。设计不当会出现后一阶段覆盖了前一阶段还需要的值——这种问题表现为特定字段组合下策略失效，单字段测试却正常。

### 3. 哈希熵与均衡度

等价多路由的均衡度取决于哈希输入的熵。只看外层五元组时，同一虚拟扩展局域网隧道里的所有报文外层源目的地址相同、目的端口相同，只有源端口有变化；如果源端口哈希算法对内层字段覆盖不全，熵就不够。把内层五元组纳入哈希能显著提升均衡度。

哈希算法本身也有讲究。简单的异或哈希对某些地址模式会产生聚集，取模运算对二的幂次成员数友好但对非幂次不友好。高端芯片用对称哈希或流量感知哈希，动态调整成员权重。排障时如果发现某条成员链路流量是其他链路的数倍，先确认哈希输入字段和算法，不要急着改链路聚合配置。

node n2 "解析深度<br/>字段能否提取" teal

### 4. 调优顺序

先测基线吞吐与丢包点，确认瓶颈维度；再按影响从大到小调整——查表级数通常影响最大，其次是哈希均衡，再次是队列参数；每改一项重新测一次，不要一次改多项。表项容量接近上限时优先扩容或压缩键宽，不要靠调调度参数掩盖。

```text
1. 单流打流测基线: 确认单流能否达到线速, 排除芯片能力问题
2. 多流打流测均衡: 观察各成员链路流量分布, 计算标准差
3. 小包长包混合测: 记录每秒包数拐点, 确认是否包数瓶颈
4. 突发流量测: 用微突发确认缓冲区深度是否足够
5. 满载查表测: 表项填充到 80% 以上, 观察查表时延是否上升
```

这五步的顺序不能颠倒。第一步排除芯片本身能力问题，否则后面调的都是白费；第二步定位均衡问题；第三步区分带宽瓶颈和包数瓶颈；第四步验证缓冲；第五步验证表项规模下的稳定性。

## PROTO-23 协议栈软件实现架构精讲

### 1. 从协议进程到芯片的落表链路

自研交换机的协议栈通常分三层：路由协议进程负责跑边界网关协议、内部网关协议等协议，算出路由结论；路由管理层负责把各协议的路由汇总、选路、做策略，形成统一的转发信息库；芯片适配层负责把转发信息库翻译成具体芯片的表项写入操作。三层之间通过进程间通信或内部接口传递变化事件。

这个分层的关键价值是隔离：协议进程不需要知道芯片表项长什么样，芯片适配层不需要知道路由是怎么算出来的。换芯片时只改适配层，换协议时只加协议进程。代价是链路变长——一次路由变化要经过多次转换才能落到硬件，每一层都可能引入延迟或状态不一致。

:::figure id=PROTO-23-01 | name=协议结论落到芯片的三层软件架构 | dir=TB

node n2 "路由管理层<br/>路由信息库与选路策略" teal
node n3 "转发信息库<br/>统一转发表" amber
node n4 "芯片适配层<br/>键值翻译与批量事务" green
node n5 "芯片硬件表项<br/>最长前缀匹配 邻接 媒体地址" purple
node n6 "状态回读<br/>计数器与写入确认" blue
edge n1 -> n2 "上报路由"
edge n2 -> n3 "选出最优"
edge n3 -> n4 "下发变化"
edge n4 -> n5 "写入硬件"
edge n5 -> n6 "读回状态"
edge n6 -> n2 "一致性校验"
:::

图中节点速览：n1 到 n5 是自上而下的写入链，n6 是回读校验链。很多自研项目只做了写入链，没做回读链，结果软件认为表项已写入、硬件实际写入失败，问题一直积累到业务不通才暴露。回读链不是可选项，是必备的可观测性通道。

### 2. 三层之间的数据结构

路由信息库存所有协议学来的候选路由，转发信息库只存选出的最优路由，这个区分是理解选路策略生效位置的前提：策略改的是路由信息库的候选集或选路比较结果，不是直接改转发信息库。芯片适配层看到的只有转发信息库变化事件，它不知道也不关心策略细节。

| 数据结构 | 内容 | 谁写入 | 谁读取 | 变化频率 |
|---|---|---|---|---|
| 协议路由表 | 某协议学来的全部路由与属性 | 协议进程 | 路由管理层 | 高 |
| 路由信息库 | 多协议汇总后的候选集 | 路由管理层 | 选路模块 | 高 |
| 转发信息库 | 选出的最优路由与下一跳 | 选路模块 | 适配层 | 中 |
| 邻接表软件副本 | 下一跳解析结果与二层地址 | 解析模块 | 适配层 | 中 |
| 硬件表项影子副本 | 期望的硬件表项内容 | 适配层 | 校验模块 | 中 |
| 硬件实际状态 | 芯片回读的表项与计数器 | 硬件 | 校验模块 | 低 |

影子副本与实际状态的对比是最实用的校验手段：软件期望写进去的值和硬件回读的值不一致，说明写入链路有问题；两者一致但业务不通，说明问题在协议结论本身。这个判断能把"软件问题还是硬件问题"的扯皮时间压缩到几分钟。

### 3. 事件驱动与批量处理

路由变化是突发且成批的：一次链路故障可能带来几千条路由重算。逐条通知适配层会导致芯片被几千次小事务打断，效率极低。成熟实现会把短时间内的变化合并成一个批次，批量翻译、批量写入、一次提交。合并窗口通常几毫秒——太短失去合并意义，太长增加收敛延迟。

线程模型上要注意锁的粒度。全局锁简单但会让协议进程和适配层互相阻塞；按表项或按前缀分段加锁并发度高但实现复杂。常见折中是读多写少的表用读写锁，热点表项按哈希分段。

```text
事件循环:
  while 有变化事件:
    事件 = 取事件(等待窗口 3 毫秒)
    批次加入事件
    若批次满 1024 条 或 窗口到期:
       翻译批次 -> 生成芯片操作序列
       检测操作冲突(同一键多次修改 -> 只保留最后一条)
       提交事务 -> 等待硬件确认
       回读校验 -> 更新影子副本
       清空批次
```

这段伪代码里有两个容易被忽略的点。一是同一键的多次修改要合并——批次内同一前缀先加后删等于没变化，不做合并会白白写两次硬件。二是要等硬件确认再更新影子副本，否则回读校验永远得到"一致"的假象，因为比的是期望值和期望值自己。

### 4. 接口设计的坑

芯片适配层的接口如果设计成"设置一条路由"，会天然鼓励逐条写入，批量优化无从做起。好的接口应该暴露批量能力：一次传入一组变化，由适配层内部决定合并与提交时机。另一个坑是接口只提供写、不提供读——没有回读能力就无法做一致性校验，也无法在启动时做表项重建。

还有版本兼容问题。控制面软件和芯片可能独立升级，适配层接口要有版本号，避免新版软件往老芯片写不认识的表项字段。字段缺失时要有明确降级策略，而不是静默忽略——静默忽略是最难排查的一类问题，因为所有日志都显示成功。

### 5. 验证手段

协议栈的验证分三层。单元测试验证单条路由翻译是否正确，构造各种键值组合检查输出；一致性测试验证软件影子副本与硬件回读是否一致，可以做成后台常驻巡检；硬件在环测试验证端到端业务，构造真实拓扑和故障注入，观察收敛时间和丢包量。

故障注入尤其重要。把链路抖动、邻居震荡、芯片写入失败、表项满等各种异常注入进去，看系统能否正确恢复。很多问题只在异常路径上出现——正常路径测试通过不代表系统可靠。

| 验证层级 | 验证对象 | 典型手段 | 能发现的问题 |
|---|---|---|---|
| 单元测试 | 单条路由翻译 | 构造键值组合比对输出 | 字段错位、编码错误 |
| 一致性测试 | 影子与硬件状态 | 后台定时回读比对 | 写入失败、状态漂移 |
| 集成测试 | 多协议协同 | 构造拓扑观察表项 | 路由冲突、资源竞争 |
| 故障注入 | 异常恢复路径 | 注入链路与写入故障 | 状态机卡死、表项泄漏 |
| 性能测试 | 收敛与吞吐 | 批量路由变化与打流 | 批量更新过慢、收敛超时 |

### 6. 收束

协议栈实现看起来是软件工程问题，但它的每一步都受芯片能力约束：批量窗口受表项更新速度约束，锁粒度受查表并发约束，接口设计受表项结构约束。反过来说，芯片设计也要考虑软件怎么把协议结论写进来——键值太复杂、没有批量接口、不支持回读，都会把成本转移到软件层，最终表现为收敛慢、排障难。

到这里，本篇从协议报文字段讲到状态机，从状态机讲到芯片表项，再讲到把表项写进去的软件架构。整条链走完，再看任何一个协议扩展，都能问出三个问题：它产生什么结论、结论写进哪张表、谁负责把结论送到表里。这三个问题能覆盖从岗位面试到线上排障的绝大多数场景。

三篇文档的分工是：07 讲核心三协议如何协同并落表，08 给出完整生态地图与选型，本篇逐协议深挖机制并补齐工程实现视角。按 07 → 08 → 本篇的顺序读，先建主干、再看全景、最后深入细节；排障时则反过来，从本篇的现象定位表项开始。

### 2. 初学者最该记住的五句话

第一，协议只负责算结论，结论写进芯片表项才生效。第二，以太虚拟专用网络是边界网关协议的地址族，不是独立协议。第三，虚拟扩展局域网只是信封，可以没有以太虚拟专用网络，但规模上不去。第四，第二类路由管主机在哪里，第五类路由管网段怎么走，第三类路由管广播发给谁。第五，排障从底层往上逐层证明，不要跳层。

把这几句话记住，再看任何一个新协议扩展，都能先问出三个问题：它产生什么结论、写进哪张表、谁负责把结论送进去。这三个问题，就是阅读整篇文档的钥匙。
