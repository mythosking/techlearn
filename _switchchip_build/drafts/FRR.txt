# FRR 与 BGP：交换机软件工程师的路由协议栈实战

## FRR-01 先建立坐标系：FRR 在交换机软件栈里的位置

做交换机软件，绕不开“路由从哪来、怎么进芯片”这个问题。FRR（FRRouting）回答的是前半段：它是运行在控制面的路由协议套件，负责和邻居交换路由信息、计算最优路径、把结果交给内核或数据面。它本身不转发任何一个报文，真正的转发发生在内核协议栈或交换芯片的 ASIC 里。把这句话记牢，就不会把“路由协议”和“转发流水线”混为一谈。

FRR 不是凭空出现的。它的谱系是 Zebra → Quagga → FRR，至今二十多年，Cumulus Linux、SONiC、VyOS、DENT 等网络操作系统都在用它。在 SONiC 里，FRR 跑在一个独立的容器里，通过 Zebra 把计算好的路由写进内核，再经由 SAI 落到交换芯片。理解 FRR，就是理解自研交换机控制面最重要的一块拼图。

**为什么自研设备要懂 FRR**：一是很多场景直接用 FRR 当控制面，二是即便自研协议栈，也要和 FRR 对接互通，三是面试和工程实践里，“有 FRR/BGP 开源研发经验”是硬通货。这三点决定了这篇文档的价值不只是知识，更是岗位匹配度。

下表把交换机软件栈各层与 FRR 的关系整理出来。

| 软件层 | 核心职责 | 与 FRR 的关系 | 典型接口 |
|---|---|---|---|
| 运维控制层 | 配置下发、状态查询、遥测采集 | 通过 vtysh 或 YANG 模型配置 FRR | CLI、gNMI、REST |
| 控制面 | 协议交互、路由计算、策略执行 | FRR 本身就是这一层主体 | BGP/OSPF/IS-IS |
| 内核网络栈 | 维护 RIB/FIB、邻居表 | FRR 经 Zebra 写入内核路由表 | netlink |
| 芯片抽象层 | 屏蔽厂商差异、统一表项语义 | SAI 读取内核路由并编程芯片 | SAI API |
| 数据面 | 线速转发、查表、改写 | 不直接感知 FRR，只执行表项 | ASIC 寄存器与表 |

这一层的分工要形成一个心智模型：FRR 负责“算”，内核负责“存”，SAI 负责“翻译”，芯片负责“转发”。后面所有章节都围绕这个模型展开。

## FRR-02 进程架构：Zebra 中枢与协议守护进程

传统路由软件把所有协议塞进一个进程，而 FRR 采用多守护进程架构：每种协议一个独立进程，再加一个居中调度的 Zebra。bgpd 跑 BGP，ospfd 跑 OSPF，isisd 跑 IS-IS，ripd 跑 RIP，bfdd 跑 BFD，它们彼此隔离，通过 Zebra 交换路由信息。这样设计的好处是故障隔离——一个协议的崩溃不会拖垮其他协议，也便于按需启用协议、独立扩展。

Zebra 是这套架构的中枢，它扮演两个角色：对内，它是各协议守护进程的路由信息交换中心，收集各协议的路由、执行选路、决定谁进主路由表；对外，它是和内核之间的唯一桥梁，通过 netlink 把最优路由写入内核 RIB/FIB。协议守护进程之间不直接通信，一律经过 Zebra，这让选路逻辑集中、可审计。

图中节点速览：n1、n2、n3 是各类协议守护进程，分别负责 BGP、IGP 和链路检测；n4 是 Zebra 中枢，汇聚所有协议的路由并执行选路；n5 是内核 netlink 接口，接收最优路由；n6 是 vtysh 统一前端，通过一个 UNIX socket 连到各守护进程。整张图说明 FRR 是“多进程协作 + 单一中枢”的结构，Zebra 是唯一的对外出口。

下表列出常见守护进程及其职责。

| 守护进程 | 协议或功能 | 关键职责 | 备注 |
|---|---|---|---|
| zebra | 路由中枢 | 管理 RIB、与内核通信、选路下发给 FIB | 必须运行 |
| bgpd | BGP | 路径矢量协议、域间与数据中心互联 | 本文重点 |
| ospfd / ospf6d | OSPFv2/v3 | 链路状态 IGP、区域内路由 | 园区与数据中心常见 |
| isisd | IS-IS | 链路状态 IGP、运营商与大型 DC | 与 OSPF 二选一常见 |
| bfdd | BFD | 毫秒级链路故障检测 | 加速 BGP 收敛 |
| staticd | 静态路由 | 手工配置路由项 | 独立于 zebra 配置 |
| pbrd | 策略路由 | 基于策略的转发表 | 高级场景 |

这个架构直接映射到排障思路：BGP 邻居问题先看 bgpd，路由没进内核先看 Zebra，转发表不对再看内核与 SAI。分层定位，效率最高。

## FRR-03 vtysh 与配置体系：把多进程当成一个设备来配

多进程架构带来一个现实问题：每个守护进程都有自己的配置文件和控制端口，难道要逐个登录配置吗？FRR 用 vtysh 解决这个问题。vtysh 通过 UNIX domain socket 连接所有守护进程，把用户输入代理转发给对应的进程，让工程师看到的是一个统一的、类似 Cisco IOS 的命令行界面。你在 vtysh 里敲 `router bgp`，实际配置的是 bgpd；敲 `ip route`，配置的是 zebra，但你感觉不到切换。

配置持久化有两种方式。传统方式是每个守护进程各存一个配置文件（bgpd.conf、zebra.conf 等）；集成方式是用 `frr.conf` 单文件保存全部配置，由 vtysh 的 `write memory` 统一写出。生产环境多用后者，便于版本管理和自动化下发。较新的 FRR 还在推进基于 YANG 数据模型的新配置系统，目标是让 FRR 成为完全可编程的路由栈，这对 gNMI 这类标准接口尤其重要。

下面是一段典型的 vtysh 配置片段，展示如何同时配置接口地址、静态路由和 BGP 邻居。

```text
frr defaults traditional
hostname leaf-01
service integrated-vtysh-config
!
interface Ethernet1
 ip address 10.0.0.1/30
!
interface Vlan100
 ip address 192.168.100.1/24
!
router bgp 65001
 bgp router-id 10.0.0.1
 neighbor 10.0.0.2 remote-as 65000
 !
 address-family ipv4 unicast
  network 192.168.100.0/24
  neighbor 10.0.0.2 activate
 exit-address-family
!
line vty
!
end
```

对这段配置的判读：前三行设定默认风格、主机名和集成配置文件开关；两个 interface 块分别给物理口和 VLAN 口配地址，这部分实际由 zebra 执行；`router bgp 65001` 声明本地 AS 号并进入 BGP 配置，`bgp router-id` 设定路由器标识；`neighbor ... remote-as` 定义一个 eBGP 邻居；address-family 块里 `network` 宣告要发布的网段，`activate` 激活该邻居的 IPv4 单播地址族。要特别注意：接口地址属于 zebra，BGP 配置属于 bgpd，vtysh 把它们写进同一个 frr.conf，但运行时分属不同进程。

下表把 vtysh 常用命令按用途归类。

| 用途 | 命令 | 作用 |
|---|---|---|
| 进入配置 | `configure terminal` | 进入全局配置模式 |
| 查看路由 | `show ip route` | 显示内核 IPv4 路由表 |
| 查看 BGP | `show ip bgp summary` | 显示邻居状态与路由数量 |
| 查看邻居 | `show bgp neighbor` | 显示单个邻居详细状态 |
| 保存配置 | `write memory` | 写入 frr.conf 持久化 |
| 进程状态 | `show daemons` | 查看各守护进程运行情况 |

掌握 vtysh 是操作 FRR 的基本功，也是从“看懂配置”到“能排障”的分水岭。

## FRR-04 BGP 基础：AS、邻居与状态机

BGP 是路径矢量协议，它的核心思想不是“我到某个网段的最短路径”，而是“我到某个网段经过了哪些 AS”。这个区别很重要：OSPF 这类 IGP 在同一管理域内用链路状态算最短路径，BGP 则在不同自治系统（AS）之间传递可达性信息，并通过 AS 路径避免环路。数据中心内部大量使用 eBGP，就是看中它的策略能力和成熟生态。

建立 BGP 会话的过程有严格的状态机：Idle → Connect → Active → OpenSent → OpenConfirm → Established。只有到达 Established，邻居才算真正建立，才能交换路由。排障时邻居卡在哪个状态，直接指向不同原因：卡在 Active 通常是 TCP 连不上或没有收到 Open；卡在 OpenSent/OpenConfirm 多是参数不匹配，如 AS 号、Router-ID、认证、hold time。

下图是 BGP 有限状态机的完整迁移。

:::figure id=FRR-04-01 | name=BGP 邻居状态机 | dir=LR
node n1 "Idle<br/>初始" blue
node n2 "Connect<br/>发起 TCP" teal
node n3 "Active<br/>等待连接" teal
node n4 "OpenSent<br/>发出 Open" amber
node n5 "OpenConfirm<br/>等待 Keepalive" amber
node n6 "Established<br/>交换路由" green
edge n1 -> n2 "start"
edge n2 -> n3 "连接失败"

edge n6 -> n1 "错误或复位"
:::

图中节点速览：n1 是空闲初始态；n2 发起 TCP 连接；n3 在连接失败后进入主动等待；n4 连接建立后发出 Open 报文；n5 收到对端 Open 后等待 Keepalive 确认；n6 是最终建立态，此时才开始交换 Update 路由。整张图是一条带回退的主线，工程排障时定位到具体状态，就能把问题范围缩小到 TCP、参数协商或路由策略某一环。

下表把六个状态与典型故障原因对应起来。

| 状态 | 正在发生什么 | 卡住的典型原因 |
|---|---|---|
| Idle | 尚未启动，等待 start 事件 | 未配置邻居、被策略抑制 |
| Connect | 发起 TCP 三次握手 | 对端不可达、ACL 拦截 179 端口 |
| Active | TCP 失败后被动等待 | 对端未发起连接、地址错误 |
| OpenSent | 已发 Open，等对方 Open | AS 号不匹配、Router-ID 冲突 |
| OpenConfirm | 收到 Open，等 Keepalive | 参数协商不一致、认证失败 |
| Established | 会话建立，交换路由 | 路由策略过滤、地址族未激活 |

BGP 有三种主要报文：Open 用于建连协商，Keepalive 用于保活，Update 用于发布和撤销路由，还有 Notification 用于报错断开。记住这四种报文，理解状态机就顺理成章。

## FRR-05 路径属性与选路决策：BGP 怎么挑最优路径

BGP 的精髓在于选路。当到达同一目的地有多条路径时，BGP 按一套严格的优先级顺序挑选最优路径，这套顺序就是路径属性（Path Attribute）的比较过程。常见属性包括：ORIGIN（来源类型）、AS_PATH（经过的 AS 序列）、NEXT_HOP（下一跳）、LOCAL_PREF（本地优先级，越大越优）、MED（多出口鉴别器，越小越优）、COMMUNITY（团体属性，用于打标批量处理）等。

选路的简化顺序是：先比较权重（Weight，思科私有，FRR 里对应本地优先级机制），再比 LOCAL_PREF，然后看是否是本地始发，接着比 AS_PATH 长度，再比 ORIGIN 类型，然后比 MED，之后在 eBGP 与 iBGP 之间取舍，最后比 IGP 到下一跳的开销，仍持平则用 Router-ID 等打破僵局。理解这个顺序，才能解释“为什么我配的路由没生效”。

下图把选路决策画成一棵逐层收敛的决策树。

node n3 "本地始发<br/>优先" teal
node n4 "AS_PATH<br/>越短越优" amber

图中节点速览：从 n1 候选路径集合出发，依次经过 n2 本地优先级、n3 本地始发、n4 AS 路径长度、n5 来源类型、n6 MED、n7 eBGP 优于 iBGP，最后 n8 用 IGP 开销和 Router-ID 打破平局。整张图是一条逐层过滤的链，每一层筛掉次优路径，直到只剩一条最优。工程上调整选路，本质就是在这条链的某一层施加影响。

下表把关键路径属性按作用分类。

| 属性 | 作用范围 | 取值偏好 | 典型用途 |
|---|---|---|---|
| LOCAL_PREF | AS 内部 | 越大越优 | 控制出访流量走哪个出口 |
| AS_PATH | 全程传递 | 越短越优 | 选最短路径、防环 |
| MED | 传给相邻 AS | 越小越优 | 影响对方进入本 AS 的入口 |
| ORIGIN | 全程传递 | IGP 优于 EGP 优于 incomplete | 区分路由来源 |
| NEXT_HOP | 逐跳传递 | 需可达 | 决定实际转发下一跳 |
| COMMUNITY | 全程传递 | 无大小之分 | 打标批量策略处理 |

这里有一个常见误区：MED 只在同一相邻 AS 内比较，且通常只影响入站流量；LOCAL_PREF 只在 AS 内部传播，不影响外部。搞不清作用范围，策略就会“配了没效果”。

## FRR-06 路由策略：前缀列表、route-map 与团体属性

BGP 的强大不在选路算法本身，而在策略的可控性。FRR 提供一套分层策略工具：前缀列表（prefix-list）按网段匹配，AS 路径列表（as-path access-list）按 AS 序列匹配，团体列表（community-list）按 COMMUNITY 标签匹配，最后由 route-map 把这些匹配条件组合起来，并执行 permit/deny 或改写属性。这套工具和 Cisco IOS 高度相似，降低了学习成本。

策略的挂载点有两个方向：入方向（in）在接收路由时过滤或改写，出方向（out）在发布路由时过滤或改写。入方向决定“我接收哪些路由”，出方向决定“我对外通告哪些路由”。数据中心里常见的做法是：对上行走出方向聚合、对下行走入方向默认路由，既减少路由表规模，又控制流量走向。

下面是一段 route-map 配置示例，展示如何给特定网段打团体属性并在出方向过滤。

```text
ip prefix-list PL-INTERNAL seq 10 permit 192.168.0.0/16 le 24
ip community-list standard CL-NO-EXPORT permit 65000:999
!
route-map RM-EXPORT permit 10
 match ip address prefix-list PL-INTERNAL
 set community 65000:100 additive
!
route-map RM-EXPORT deny 20
 match community CL-NO-EXPORT
!
route-map RM-EXPORT permit 100
!
router bgp 65001
 neighbor 10.0.0.2 route-map RM-EXPORT out
```

对这段配置的判读：prefix-list 定义了允许 192.168.0.0/16 内掩码不超过 24 位的网段；community-list 定义了“禁止导出”团体 65000:999；route-map 按序号从小到大匹配，序号 10 匹配内网网段并追加团体 65000:100，序号 20 拒绝带 NO-EXPORT 团体的路由，序号 100 放行其余；最后在 BGP 邻居的出方向挂载这张 route-map。要点是 route-map 自上而下匹配、命中即停、末尾隐含拒绝，所以最后那条 permit 100 用来兜底放行，否则其余路由全被丢弃。

下表把策略工具按匹配对象与典型场景归类。

| 工具 | 匹配对象 | 典型场景 |
|---|---|---|
| prefix-list | IP 前缀与掩码范围 | 只允许特定网段进出 |
| as-path access-list | AS_PATH 正则 | 过滤经过特定 AS 的路由 |
| community-list | COMMUNITY 标签 | 批量识别打标路由 |
| route-map | 组合上述条件并执行动作 | 过滤、改写属性、设下一跳 |
| distribute-list | 简化的前缀过滤 | 快速过滤，不能改属性 |

策略排障有个黄金命令：`show ip bgp <前缀>` 能看到这条路由的属性和选路决策，`show bgp neighbor <地址> advertised-routes` 能看到实际发出去的路由。用它们对照配置，策略是否生效一目了然。

## FRR-07 数据中心 BGP：eBGP、路由反射与 ECMP

传统企业网络里 iBGP 占主导，但现代数据中心普遍采用 eBGP：每个 Leaf 用不同 AS 号，和 Spine 建立 eBGP 会话。这么做的原因有三：eBGP 没有 iBGP 的全互联要求，扩展性更好；eBGP 的 AS_PATH 天然提供防环，不需要路由反射器那套复杂机制；eBGP 的策略边界清晰，便于按租户、按 Pod 做流量工程。典型的两层 Clos 里，每台 Leaf 与所有 Spine 建 eBGP，服务器网段通过 Leaf 通告，Spine 只做透传和 ECMP 分担。

当规模继续扩大，iBGP 仍会在 AS 内部出现（比如同一 Pod 内多台设备共享 AS），这时就要用路由反射器（RR）来避免全互联。RR 允许把从一台 iBGP 邻居学来的路由反射给其他邻居，打破“iBGP 学到的路由不再传给其他 iBGP 邻居”的限制。此外，BFD 常与 BGP 联动：BFD 用毫秒级心跳检测链路，一旦故障立刻通知 BGP 拆邻居，把收敛时间从秒级压到亚秒级。

下图是两层 Clos 中的 eBGP 互联关系。

:::figure id=FRR-07-01 | name=两层 Clos 的 eBGP 邻居关系 | dir=TB
node n1 "Spine-1<br/>AS 65000" blue
node n2 "Spine-2<br/>AS 65000" blue
node n3 "Leaf-1<br/>AS 65101" teal
node n4 "Leaf-2<br/>AS 65102" teal
node n5 "Leaf-3<br/>AS 65103" teal
node n6 "服务器网段<br/>租户 A B" green
edge n1 -> n3 "eBGP"
edge n1 -> n4 "eBGP"

图中节点速览：n1、n2 是两台 Spine，同属 AS 65000，只做高速透传；n3、n4、n5 是三台 Leaf，各有独立 AS，与两台 Spine 分别建立 eBGP；n6 是接入的服务器网段，由 Leaf 向 Spine 宣告。整张图体现了 Clos 的核心：每台 Leaf 到每个 Spine 都有等价路径，BGP 通过 ECMP 把流量分摊到多条上行链路，任一 Spine 故障都能快速收敛。

下表总结数据中心 BGP 的关键设计点。

| 设计点 | 常见做法 | 目的 |
|---|---|---|
| 邻居类型 | Leaf-Spine 间用 eBGP | 免全互联、天然防环 |
| AS 规划 | 每 Leaf 独立 AS，Spine 共享 AS | 边界清晰、便于策略 |
| 多路径 | maximum-paths 开启 ECMP | 充分利用等价链路 |
| 快速收敛 | BGP 联动 BFD | 亚秒级故障感知 |
| 路由聚合 | 向 Spine 宣告汇总网段 | 减小路由表规模 |
| 默认路由 | Spine 向 Leaf 下发默认路由 | Leaf 只需少量路由 |

这套设计是字节、火山引擎这类超大规模数据中心的常见骨架，也是岗位描述里“骨干网、边缘、云场景”的技术底座。

## FRR-08 从 RIB 到 FIB：FRR 与数据面的对接

前面讲的所有路由计算，最终都要落到芯片的表项里才有用。这条链路是：各协议把路由交给 Zebra，Zebra 维护 RIB（路由信息库）并执行选路，选出最优路由后写入内核的 FIB（转发信息库），内核再通过 netlink 通知下游，SONiC 里由 SAI 读取这些路由并编程到 ASIC。理解这条链路，才能回答面试官的经典问题：“BGP 学到一条路由，怎么变成芯片里的一条转发表项？”

这里要分清三个表：RIB 是所有协议路由的集合，可能同一前缀有多条候选；FIB 是选路后的最优路由集合，是真正用来转发的；ASIC 表项是芯片内部硬件表，由 FIB 翻译而来。FRR 的 `show ip route` 看到的是内核 FIB，而 `show ip bgp` 看到的是 BGP 的 RIB，两者可能不一致——这正是排障的切入点。

下图把从协议到芯片的完整链路画出来。

:::figure id=FRR-08-01 | name=从协议路由到芯片表项的链路 | dir=LR
node n1 "协议 RIB<br/>bgpd 等" blue
node n2 "Zebra 主 RIB<br/>选路" teal
node n3 "内核 FIB<br/>netlink" amber
node n4 "SAI 适配<br/>表项翻译" green
node n5 "ASIC 硬件表<br/>LPM 邻接" purple
edge n1 -> n2 "注入候选路由"
edge n2 -> n3 "写入最优路由"
edge n3 -> n4 "读取并翻译"
edge n4 -> n5 "编程硬件表"
:::

图中节点速览：n1 是各协议的 RIB，存放候选路由；n2 是 Zebra 主 RIB，执行选路决策；n3 是内核 FIB，通过 netlink 接收最优路由；n4 是 SAI 适配层，把通用路由翻译成芯片表项；n5 是 ASIC 硬件表，最终由 LPM 表和邻接表承载转发。整张图说明路由要跨越“协议—内核—抽象层—芯片”四道边界，每一道都可能是问题所在。

下表把这条链路上每一环的排查方法列出来。

| 环节 | 查看命令或位置 | 判断依据 |
|---|---|---|
| 协议 RIB | `show ip bgp` | 是否学到路由、属性是否正确 |
| Zebra 主 RIB | `show ip route` | 最优路由是否写入内核 |
| 内核 FIB | `ip route show` | 内核路由表是否有该前缀 |
| SAI 适配 | SAI 日志与 debug counters | 路由是否被正确翻译 |
| ASIC 表项 | 芯片 SDK 表项查询 | 硬件表是否存在对应条目 |

排障时按这条链逐段验证，能快速定位问题是出在“没学到”“没选上”“没写进内核”还是“没编进芯片”。

## FRR-09 BGP 在 SONiC 中的落地：容器、数据库与 bgpd

SONiC 把 FRR 跑在独立的 bgp 容器里，通过 Redis 数据库与系统其他模块交互。控制面的配置从 CONFIG_DB 下发，路由结果写入 APPL_DB 等数据库，再由 orchagent 调用 SAI 编程芯片。这里的关键点是：SONiC 里 FRR 不再是孤立的路由套件，而是整个 NOS 数据驱动架构中的一个环节，路由的流入流出都经过数据库这一层。

对交换机软件工程师来说，需要理解 SONiC 如何把 BGP 配置翻译成 bgpd 的配置。用户在 CONFIG_DB 里写 BGP 邻居和网段，bgpcfgd 这个守护进程监听数据库变化，生成对应的 frr.conf 片段并通知 bgpd 重载。反过来，bgpd 计算出的路由通过 fpmsyncd 写入 APPL_DB，触发后续编程。这套机制让 BGP 配置可以像其他 SONiC 配置一样被统一管理和自动化下发。

下面是一段 SONiC 里通过配置数据库设置 BGP 邻居的示例。

```text
# 在 CONFIG_DB 中设置 BGP 邻居（sonic-cfggen 或 config db 方式）
config db set BGP_NEIGHBOR '10.0.0.2|65000' remote_asn 65000
config db set BGP_NEIGHBOR '10.0.0.2|65000' interface Ethernet1
# 宣告网络
config db set BGP_NETWORK '192.168.100.0/24' ipv4 true
# 查看生成的 FRR 配置与邻居状态
show bgp summary
show ip bgp neighbors 10.0.0.2
```

对这段配置的判读：前两条命令在 CONFIG_DB 的 BGP_NEIGHBOR 表里以“邻居地址|对端 AS”为键，设置 remote_asn 和出接口；第三条在 BGP_NETWORK 表里宣告要发布的网段；这些数据库变更由 bgpcfgd 监听并生成 bgpd 配置。最后两条 show 命令验证结果——`show bgp summary` 看邻居是否 Established，`show ip bgp neighbors` 看邻居详细状态。要记住：在 SONiC 里直接改 frr.conf 会被数据库的配置覆盖，正确做法是改 CONFIG_DB。

下表把 SONiC 中 BGP 相关组件按职责归类。

| 组件 | 所在层 | 职责 |
|---|---|---|
| bgp 容器 | 容器层 | 隔离运行 FRR |
| bgpcfgd | 配置同步 | 监听 CONFIG_DB，生成 bgpd 配置 |
| fpmsyncd | 路由同步 | 把 FRR 路由写入 APPL_DB |
| CONFIG_DB | 配置数据库 | 存放用户 BGP 配置 |
| APPL_DB | 应用数据库 | 存放路由等运行时数据 |
| orchagent | 编排层 | 读 APPL_DB，调用 SAI 编程芯片 |

SONiC 这一层是岗位描述里“有 SONiC 开源研发经验优先”直接对应的能力，把 FRR 和 SONiC 两条线打通，是这个岗位最看重的组合技能之一。

## FRR-10 运维排障、可观测性与学习路径

FRR 的运维围绕“状态可见、变更可控、故障可查”三件事展开。状态可见靠 show 命令族和遥测，变更可控靠配置版本管理和灰度发布，故障可查靠日志、调试命令和抓包。BGP 作为域间协议，任何配置变更都可能影响流量走向，所以生产环境的 BGP 变更要格外谨慎：先在测试环境验证、再小范围灰度、全程监控路由数量和邻居状态、准备好回滚方案。

常见故障可以归纳成几类：邻居建不起来（查状态机、TCP、参数）、路由学不到（查策略过滤、地址族激活）、路由选不中（查路径属性、选路顺序）、路由进不了芯片（查 RIB→FIB→SAI 链路）。每一类都有对应的黄金命令，把这些命令固化成排障清单，能显著提升效率。日志方面，FRR 支持 syslog 输出，关键事件（邻居状态变化、路由抖动）要接入集中日志系统长期留存。

下表把常见故障现象、排查方向与命令整理成一份速查清单。

| 现象 | 首要排查方向 | 关键命令 |
|---|---|---|
| 邻居卡在 Active | TCP 可达性、179 端口 | `show bgp neighbor`、ping、telnet |
| 邻居卡在 OpenConfirm | 参数协商、认证 | `show bgp neighbor`、日志 |
| 邻居 Established 但无路由 | 入方向策略、地址族 | `show ip bgp`、route-map |
| 路由存在但非最优 | 路径属性、选路顺序 | `show ip bgp <前缀>` |
| 内核无路由 | Zebra 与内核同步 | `show ip route`、`ip route` |
| 转发不通但路由在 | SAI 与芯片表项 | SAI 日志、SDK 表项查询 |

学习 FRR/BGP 建议按这条路径推进：先在虚拟机里用两台 Linux 跑通 eBGP 邻居，理解状态机和配置；再练习 prefix-list 与 route-map，观察策略如何改变选路；然后搭建两层 Clos 的多机拓扑，配置 ECMP 和 BFD；最后把它放进 SONiC 环境，理解数据库驱动的配置方式。每一步都用 show 命令验证，形成“配置—观察—解释”的闭环。

回到岗位要求：熟练掌握 FRR/BGP，配合前面写过的 SONiC 资料，就覆盖了“有 SONIC、FRR(BGP) 开源软件研发经验优先”这一条。下一步可以把 BGP 和交换芯片的二三层功能结合起来看——路由最终要靠芯片的 LPM 和邻接表落地，这正是下一篇“交换机二三层功能”要讲的内容。
