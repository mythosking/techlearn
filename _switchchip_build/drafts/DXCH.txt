# Marvell Prestera DXCH 家族谱系与 98DX 料号归属

## DXCH-01 先建立坐标系：family、device、flavor 与代号

很多人第一次看 Marvell 交换芯片资料时会被两层命名绕晕：一层是 xCat、Lion、Bobcat2 这类看起来像动物代号的名字，另一层是 98DX8216、98CX8296 这种像料号的名字。要判断“98DX 属于哪个 family”，必须先分清四个概念：产品品牌、SDK family、具体器件、资源档位。

**产品品牌**是对外市场口径，例如 Prestera DX、Prestera CX。Marvell 官网和新闻稿常用这一层称呼，它回答的是“这是哪条产品线”。**SDK family** 是 CPSS 软件内部的大类，例如 `CPSS_PP_FAMILY_DXCH_XCAT_E`、`CPSS_PP_FAMILY_DXCH_LION2_E`、`CPSS_PP_FAMILY_DXCH_BOBCAT2_E`。同一 family 内的器件共享大量初始化代码、寄存器模型和表项布局。**具体器件**是 98DX、98CX、98FX 开头的料号，在 CPSS 里对应 `CPSS_PP_DEVICE_TYPE` 宏。**资源档位（flavor）** 是同一 family 内部的配置细分，例如 Bobcat2 下的 control plane、Carrier small、DC metro，以及前面查证过的 Drake。

最容易出问题的地方是：AlleyCat、PonCat、TomCat、Bobcat 这些猫科名字，在 CPSS 里通常是**具体器件组的别名**，不是 family；而 xCat、xCat2、xCat3、Lion、Lion2、Lion3、Bobcat2、Bobcat3 才是 family 级名称。一个典型例子是 98DX4100 系列在源码注释里叫 Bobcat-GE，但它属于 `CPSS_PP_FAMILY_DXCH_XCAT_E`，不属于 Bobcat2 family。只听“Bobcat”三个字会把两代产品混为一谈。

图中节点速览：n1 是对外品牌层，常见写法是 Prestera DX 或 Prestera CX；n2 是 CPSS 的 family 层，例如 xCat、Lion、Bobcat2；n3 是具体器件层，也就是 98DX、98CX、98FX 料号；n4 是 family 内部的资源档位，例如 Drake、Caelum、Cetus；n5 是最终文档结论，必须按“料号—family—flavor”的顺序写，不能把别名当 family。整张图说明：看到 98DX 时先查器件宏，再反查 family，最后看是否还有 flavor。

下表把四层概念与例子对应起来。

| 层级 | 回答的问题 | 典型名字 | 文档写法 |
|---|---|---|---|
| 对外品牌 | 这是哪条产品线 | Prestera DX、Prestera CX | 作为背景说明 |
| SDK family | 代码里属于哪一大类 | xCat、Lion2、Bobcat2 | 写 `CPSS_PP_FAMILY_DXCH_*_E` |
| 具体器件 | 硬件料号是什么 | 98DX8216、98CX8296 | 写完整 98DX 或 98CX 编号 |
| 资源档位 | 同 family 内如何细分 | Drake、Caelum、Cetus | 标注为内部代号或 flavor |

下面这段伪代码把判定顺序固定下来。它不是真实 SDK 接口，只是把工程师读源码时的脑子里的过程写出来，便于后面照着核对。

```text
# 工程理解伪代码：从一个 98DX 料号反查 family 与 flavor
pn = "98DX8216"
device_macro = lookup_macro(pn)                 # CPSS_98DX8216_CNS
family = family_from_device_macro(device_macro) # CPSS_PP_FAMILY_DXCH_BOBCAT2_E
group  = device_group_from_table(device_macro)  # devs_Bobcat2_control_plane
flavor = flavor_comment_from_group(group)       # Drake, Medium Scale 16/24G
print(pn, family, group, flavor)
```

对这段伪代码的判读：第一行把料号转成 CPSS 器件宏；第二行从器件宏反查 family；第三行到初始化表里找它属于哪个 device group；第四行读取该 device group 的注释，看有没有内部 flavor。以 98DX8216 为例，最终得到的是“Bobcat2 family、control plane device group、Drake flavor”。注意 flavor 只能解释资源和定位，不能替代 family。

## DXCH-02 谱系总览：从 Cheetah 到 Bobcat3

CPSS 的 DXCH family 枚举列在 `cpssTypes.h` 中，依次为 Cheetah、Cheetah2、Cheetah3、xCat、xCat3、Lion、xCat2、Lion2、Lion3、Bobcat2、Bobcat3、Aldrin。这个枚举顺序大体反映代码积累的代际，但**不是严格发布时间线**：例如 xCat3 在枚举中排在 xCat 后面，而 xCat2 又排在 Lion 后面；真实产品发布时间要看新闻稿和产品简介。本文聚焦用户指定的三组：xCat 三兄弟、Lion 三兄弟、Bobcat2 与 Bobcat3，同时把 Aldrin 放在速查表里避免漏项。

从定位看，xCat 系列是集成 ARM 与 PHY 的接入交换SoC，广泛用于 SMB、园区接入和简单路由；xCat2 与 xCat3 继续沿着接入市场演进，但侧重点不同：xCat2 更偏 2.5GbE 多速率接入，xCat3 更偏高集成 1GbE 接入与双核控制。Lion 与 Lion2 主要面向数据中心、城域和运营商接入，容量和 SerDes 规模明显上一个台阶；Lion3 在这份 CPSS 4.1 源码里只留下仿真占位。Bobcat2 是 28nm 一代，覆盖 10GbE 接入、汇聚、控制面和交换矩阵；Bobcat3 面向 25GbE，公开报道称 2016 年已送样，但这版 SDK 只列了仿真器件。

## DXCH-03 xCat 家族：AlleyCat、PonCat、TomCat 与老 Bobcat

xCat 是 CPSS 中最庞大的接入家族之一。源码在 `cpssTypes.h` 第 1143 行到第 1237 行给出 `xCat device start` 到 `xCat device end` 的完整列表。它的特点是把交换引擎、多个 FE 或 GE 端口、堆叠端口、片上处理器和外设接口集成在一颗芯片里，面向中小企业、园区边缘、非网管与简单网管交换机。

xCat 内部按内部代号分成几条支线。**AlleyCat** 是基础接入款，有 FE 版 98DX1000 系列和 GE 版 98DX3000 系列；源码注释区分了 unmanaged 与 websmart 两种管理形态，前者 333MHz、零缓存、片内 SRAM，后者 333MHz、零缓存、SPI 与 DDR2。**PonCat** 与 AlleyCat 接近，常见 FE 系列是 98DX102x，GE 系列是 98DX303x。**TomCat** 定位略高，源码注释写的是 SMB L2+，FE 系列为 98DX1100/1200，GE 系列为 98DX3100，城域版为 98DX3200，CPU 主频 600MHz，带 16KB 指令缓存与 128KB 数据缓存。**Bobcat** 在 xCat 家族里是 L3+ 与 Metro 定位，FE 系列 98DX2100、GE 系列 98DX4100，CPU 主频 800MHz，带 16KB 指令缓存与 256KB 数据缓存。

这里必须强调：**xCat 里的 Bobcat 是老一代 Bobcat，不等于 Bobcat2 family**。98DX2101/2122/2123/2151 与 98DX4101/4121/4122/4123/4124/4125 都在 xCat 段内；而 Bobcat2 family 的料号从 98DX4251、98DX4220 等开始，架构与 28nm 代际完全不同。用户过去适配过 Bobcat、Alleycat、Lion，这正好横跨了 xCat 接入线与 Lion 高密度线。

xCat 的料号很多，但读法有规律：前两位 98DX 表示 Prestera DX 数字器件；中间数字段大致区分内部代号与能力档；尾缀 B、C、J、H 等常表示封装、端口或衍生版本。真正判断 family 时不要靠“看起来像哪一档”，而要看源码的 `xCat device start` 与 `xCat device end` 区间，或看 `PRV_CPSS_DXCH_XCAT_*_DEVICES` 宏。

还有一个细节：有些料号在后续家族的源码段里仍被标注为 `/*XCAT*/`，说明它们虽然出现在后文兼容列表里，实际 family 仍是 xCat。最典型的是 98DX3036、98DX3036A、98DX3136、98DXZ366、98DXH336 与 98DXH337。这类“段落在 xCat2、family 仍是 xCat”的例外，是手工整理谱系时最容易漏掉的点。

## DXCH-04 xCat2 家族：AlleyCat2、PonCat2、VonCat2 与第二代接入

xCat2 在 CPSS family 枚举中排在 Lion 之后，源码段从第 1400 行 `xCat2 device start` 到第 1464 行 `xCat2 device end`。它继续服务接入市场，但端口组合从纯 FE/GE 扩展到 2.5GbE 相关堆叠与上行形态，内部代号从 AlleyCat、PonCat 演进到 AlleyCat2、PonCat2，并新增 VonCat2。公开新闻稿在 2015 年推广 2.5GbE、5GbE、10GbE 和 40GbE 企业边缘与中小企业交换器件，可作为 xCat2 所处市场背景；但料号归族仍应以 CPSS 源码为准。

xCat2 的典型料号包括 AlleyCat2 非网管 GE 系列 98DX3011B、3011C、3021B、3021C；AlleyCat2 WebSmart FE 系列 98DX1033、1034、1035、1053、1055；AlleyCat2 WebSmart GE 系列 98DX3027B、3033B、3034B、3035B、3053、3054、3055；PonCat2 FE 系列 98DX1133、1134、1135、1163、1165；PonCat2 GE 系列 98DX3031B、3133、3134、3135、3163、3165；VonCat2 系列 98DX1083、1085、3083、3085；DHX 形态还有 98DXH335。

下表把 xCat2 的内部代号与料号段对应起来。

| 料号段 | 内部代号 | 端口形态 | 备注 |
|---|---|---|---|
| 98DX3011B/C、3021B/C | AlleyCat2-GE | 16 或 24 GE | 非网管，带 2 或 4 个堆叠 |
| 98DX1033/1034/1035 | AlleyCat2-FE | 8、16、24 FE | WebSmart，333MHz |
| 98DX1053/1055 | AlleyCat2-FE | 8、24 FE | WebSmart 变体 |
| 98DX3027B、3033B 至 3055 | AlleyCat2-GE | 8、16、24 GE | WebSmart 与堆叠组合 |
| 98DX1133/1134/1135、1163/1165 | PonCat2-FE | 8、16、24 FE | 第二代 PonCat 接入 |
| 98DX3031B、3133 至 3165 | PonCat2-GE | 8、16、24 GE | 2.5G 堆叠能力提升 |
| 98DX1083/1085、3083/3085 | VonCat2 | FE 或 GE | 同代补充支线 |
| 98DXH335 | AlleyCat2-GE DHX | 24 GE | DHX 形态 |

xCat2 的边界必须和 Bobcat2-bobk 分清。2015 年公开资料里常一起出现 98DX4210/4211 与 98DX8208/8212，它们看起来像 xCat2 的 42xx、82xx 数字段，但在 CPSS 源码里属于 Bobcat2 下的 BobK 子系列：4210/4211 是 Caelum，8208/8212 是 Cetus。换句话说，不能只看“98DX3xxx 是接入、98DX4xxx 是另一档”这种粗规则；必须查源码段或 device list。

另一个边界是 2016 年以后出现的 98DX325x、98DX83xx 等料号。这些在 Marvell 公开资料中属于后续 Prestera 产品，但在本文依据的 CPSS 4.1 镜像 `cpssTypes.h` 中没有对应宏，因此不能硬塞进 xCat2 或 xCat3 表。工程上如果要适配这些料号，应使用对应版本 SDK 的头文件重新核对。

## DXCH-05 xCat3 家族：AlleyCat3 与 PonCat3

xCat3 是接入家族中更晚的一支，源码段从第 1239 行到第 1276 行。它只有两条主支线：AlleyCat3 与 PonCat3。AlleyCat3-FE 对应 98DX1233、1235；AlleyCat3-GE 对应 98DX3223_1、3224、3225、3226、3233、3234、3235、3236，以及 98DXH333、98DXT323、98DXT321、98DXC323、98DXN323。PonCat3-FE 对应 98DX1333、1335、1336；PonCat3-GE 对应 98DX3333、3334、3335、3336。

公开训练资料和书籍给出的工程口径能补充说明 xCat3 的能力。MOVE.B 的 PONCAT3/ALLEYCAT3 课程把这两款器件描述为 1G 交换机/路由器，课程覆盖 CPU 子系统、分布式交换架构、交换核心适配器、网络接口与 MAC、隧道终止与接口、策略引擎、桥接引擎、IPv4/IPv6 路由引擎、端口聚合、监管与标记、缓冲与拥塞管理、QoS、VLAN、安全控制、流量监控与桥端口扩展。阿里云开发者社区一本书的节选给出 98DX3236 的具体资源：120Mpps 包转发率、84Gbps 背板带宽、12 个可配置 SerDes，其中 6 个可配置为 1 至 10Gbps、6 个可配置为 1 至 5Gbps、片内 1.5MB 包缓存；AlleyCat3 为单核 ARMv7 400MHz，PonCat3 为双核 ARMv7 800MHz。这些数值属于公开二手资料，工程落地仍应以 Marvell 数据手册和所用 SDK 为准。

下表汇总 xCat3 的料号归属。

| 料号 | 内部代号 | FE 或 GE | 堆叠或 SerDes 形态 |
|---|---|---|---|
| 98DX1233、1235 | AlleyCat3-FE | 8 或 24 FE | 2 或 4 个堆叠端口 |
| 98DX3223_1、3224、3225 | AlleyCat3-GE | 8、16、24 GE | 4 个 GE 堆叠 |
| 98DX3226、3236 | AlleyCat3-GE | 24 GE | 4 个 XG 堆叠 |
| 98DX3233、3234、3235 | AlleyCat3-GE | 8、16、24 GE | 4 个 GE 堆叠 |
| 98DXH333、98DXT323、98DXT321 | AlleyCat3-GE 变体 | 8 或 24 GE | 2 或 4 个堆叠端口 |
| 98DXC323、98DXN323 | AlleyCat3-GE 变体 | 24 GE | 2 个 GE 或 4 个 XG 堆叠 |
| 98DX1333、1335、1336 | PonCat3-FE | 8 或 24 FE | 2 个 GE 或 4 个 XG 堆叠 |
| 98DX3333、3334、3335、3336 | PonCat3-GE | 8、16、24 GE | GE 或 XG 堆叠 |

xCat3 与 xCat2 的区别，可以概括为“更聚焦的 1G 接入平台”。xCat2 的料号里还能看到大量 2.5G 堆叠与多速率组合，xCat3 的公开课程强调 1G 交换机/路由器、分布式交换架构和完整的三层引擎；源码注释则显示 xCat3 的端口列只保留 FE、GE、XG 与堆叠，没有 xCat 早期那些复杂的 10/12GE 堆叠列。对于适配过 AlleyCat2 的工程师，xCat3 的学习重点不是端口速率，而是 CPU 子系统、隧道终止、策略与路由引擎的组织方式。

## DXCH-06 Lion / Lion2 / Lion3：从高密度 10G 到多芯片平台

Lion 系列在 CPSS 里对应 `CPSS_PP_FAMILY_DXCH_LION_E`，源码段从第 1279 行到第 1301 行。它的料号大多数使用 **98CX** 前缀，而不是 98DX，这是 Prestera CX 产品线的典型编号。代表器件包括 98CX8248、98CX8112、98CX8224、98CX8203、98CX8113、98CX8222、98CX8223、98CX8234、98CX8265、98CX8266、98CX8267。源码注释给出端口形态：48 端口 RXAUI、12 端口 RXAUI、24 端口 XAUI、16 XAUI 加 2 个 40GbE、24 RXAUI 加 2 个 40GbE、32 RXAUI 加 4 个 40GbE，以及 4 XAUI 加 8 RXAUI 加 16 HGS2 等。另有 98DX5178、98DX5198 两个 98DX 器件和 98FX9216 交叉矩阵器件也列在 Lion 段内，说明前缀不是 family 的绝对判据。

公开资料对 Prestera CX 的描述与源码注释一致：它是面向云存储和服务器互连的高密度 40GbE/10GbE 数据包处理器，包处理范围从 160G 到 1.28T，支持模块化平台上的以太网背板，并用于 IP RAN、基站与分组传输等需要计时和同步的场景。对学习交换芯片的人，Lion 的价值在于把视角从“单芯片接多少 GE 口”推进到“多 SerDes、多端口组、多芯片背板”。

Lion2 对应 `CPSS_PP_FAMILY_DXCH_LION2_E`，源码分为 Data Center/Metro 与 Hooper 两组。Data Center/Metro 组包含 98CX8296、98CX8297、98CX8308、98CX8297_1，以及交换矩阵器件 98FX9287、98FX9288。Hooper 组包含 98CX8121、98CX8123、98CX8124、98CX8129。公开资料把 98CX8129 称为面向运营商与企业的高密度 40GbE/10GbE 包处理器，并提到它与 IP Infusion ZebIC 方案整合，用于软件定义网络和 IP RAN。这说明 Lion2 不只是更大带宽，还承担控制平面与数据平面解耦、跨芯片组和精确时钟等系统级能力。

Lion3 在这份 CPSS 4.1 源码里非常特殊：`start Lion3 devices` 与 `End Of Lion3 devices` 之间只有 `CPSS_98CXEEEF_CNS`，注释写明这是 Bobcat2、Caelum、Bobcat3 的仿真占位。不能据此断言 Marvell 没有 Lion3 产品，只能说**这份 SDK 未把 Lion3 量产料号写进 cpssTypes.h**。写文档时应把它标为“仿真占位 family”，不要给读者编造 98DX 料号。

## DXCH-07 Bobcat2 与 Bobcat3：28nm 10G 与 25G 一代

Bobcat2 对应 `CPSS_PP_FAMILY_DXCH_BOBCAT2_E`，是这版 CPSS 里资料最丰富、分组最细的一代。`cpssTypes.h` 第 1341 至 1358 行列出 Bobcat2 基础器件：98DX4251、98DX4220、98DX4221、98DX4222、98DX4223、98DX8216、98DX8219、98DX8224、98DX4253，以及仿真占位 98DX42XX。后面的 device list `PRV_CPSS_BOBCAT2_DEVICES` 也逐项列出这些宏，说明它们是同一个 family 下的不同资源和端口配置。

Bobcat2 之下还有 BobK 子系列，源码分为 Caelum 与 Cetus 两组。Caelum 包含 98DX4203、98DX4204、98DX4211、98DX4210，以及仿真占位 98DX42KK；Cetus 包含 98DX4235、98DX8212、98DX8208。2015 年 Marvell 新闻稿推广的 98DX4210、98DX4211、98DX8212、98DX8208 正是这组器件，公开定位是 2.5GbE、5GbE、10GbE 与 40GbE 企业边缘和中小企业交换。它们虽然内部代号是 Caelum/Cetus，但 family 仍按 Bobcat2 相关代码处理，不能因为名字不是 Bobcat2 就另起 family。

Drake 也出现在 Bobcat2 这一层。`cpssDxChHwInit.c` 第 3142 至 3149 行定义 `devs_Bobcat2_control_plane[]`，包含 98DX8216、98DX8219、98DX8224；第 3505 至 3570 行给这个 device group 的注释是 `Drake - Control Plane Medium Scale (16/24G)`，并配置 FDB 64K、tunnelTerm 18K、tunnelStart 8K、routerNextHop 8K、policers 6K、buffer 32M、LPM 48K、pipeBW 168Gbps。公开 98DX8216/24 product brief 只写 Prestera DX 第八代、16/24 个 10GbE、eBridging、802.1BR、集成 10G PHY、ARM v7 host/co-processor，全文没有 Drake；因此 Drake 应写成 SDK 与芯片手册内部代号，而不是对外料号。

下面这段伪代码把 Drake 的判定过程写成可复用步骤，也适用于其他内部代号。

```text
# 工程理解伪代码：判断一个内部代号是不是 family
family_list = read_enum("CPSS_PP_FAMILY_TYPE_ENT")
device_list = read_macro_list("PRV_CPSS_BOBCAT2_DEVICES")
if "DRAKE" in family_list:
    level = "family"
elif device_macro("98DX8216") in device_list and "Drake" in flavor_comment:
    level = "device flavor under Bobcat2"
else:
    level = "unknown, need more evidence"
print("Drake =", level)
```

对这段伪代码的判读：第一步读 family 枚举，Drake 不在其中；第二步读 Bobcat2 的 device list，确认 98DX8216 属于 Bobcat2；第三步在 resource table 的注释中找到 Drake，于是把它归类为 Bobcat2 下的 device flavor。这里的关键不是记住 Drake，而是掌握方法：先看枚举，再看 device list，最后看 flavor 注释。

## DXCH-09 如何自己判定：从 SDK 源码到文档的核对流程

谱系表会随 SDK 版本变化，真正可靠的是核对流程。建议每次遇到新料号都走五步：先在 `cpssTypes.h` 搜 `CPSS_<料号>_CNS`；再看它落在哪个 `device start` 与 `device end` 段；再查 `PRV_CPSS_*_DEVICES` 宏确认 family 级设备列表；再到 `cpssDxChHwInit.c` 查 device group 和 flavor 注释；最后用公开产品简介核对市场定位，但不要用市场定位反推 SDK family。

为什么最后一步不能提前？因为公开资料经常使用品牌名而非 SDK family 名。例如 Avnet 的 Prestera DX 页面把 98DX8212 写成 control plane and embedded applications，把 98DX8216 写成 native 10GbE server connectivity；而 CPSS 把 8212 列在 BobK Cetus，把 8216 列在 Bobcat2 control plane group。两种说法服务于不同目的：前者是市场场景，后者是软件兼容性和资源配置。写技术文档时，公开资料用于解释“为什么这样设计”，源码用于回答“代码里怎么归类”。

下表给出本文实际使用的源码锚点，便于后续复核。

| 源码文件 | 位置 | 内容 | 用途 |
|---|---|---|---|
| cpssTypes.h | 732 至 745 行 | CPSS PP family 枚举 | 判断是否存在独立 family |
| cpssTypes.h | 875 至 964 行 | xCat 器件总注释 | 建立内部代号与端口形态 |
| cpssTypes.h | 1143 至 1237 行 | xCat device start/end | 判定 xCat 料号 |
| cpssTypes.h | 1239 至 1276 行 | xCat3 device start/end | 判定 xCat3 料号 |
| cpssTypes.h | 1279 至 1339 行 | Lion、Lion2、Lion3 段 | 判定 98CX 与特殊 98DX |
| cpssTypes.h | 1341 至 1464 行 | Bobcat2、BobK、xCat2 段 | 判定三组交叉边界 |
| cpssTypes.h | 2741 至 2831 行 | device list 宏 | 确认 family 级设备集合 |
| cpssDxChHwInit.c | 3142 至 3149 行 | control plane device group | 确认 Drake 对应料号 |
| cpssDxChHwInit.c | 3505 至 3570 行 | Drake 资源档注释 | 确认 flavor 与资源参数 |

下面这段伪代码把上述流程写成检查清单，可直接用于新料号或新 SDK 版本。

```text
# 工程理解伪代码：新料号归属核对
pn = "98DX3236"
hit = grep_sdk("CPSS_" + pn + "_CNS")
section = nearest_start_end_comment(hit)
family_macro = family_enum_for_section(section)
devlist = find_device_list_macro(hit)
flavor = find_flavor_comment(devlist)
public_doc = fetch_product_brief(pn)
assert family_macro in public_doc or public_doc is branding_only
write_doc(pn, family_macro, devlist, flavor, public_doc)
```

对这段伪代码的判读：先搜器件宏，找到后看最近的 start/end 段，得到 family；再用 device list 宏交叉确认；然后查 flavor 注释；最后用公开资料核对市场定位。最后一行断言的意思是：公开资料如果不写 SDK family，也是正常的，因为它可能只写品牌名；这时不能拿公开资料否定源码归类。把四个来源分层记录，才是可复核的文档。

还需要提醒一个版本问题：本文依据的是工作区内 sparse checkout 的 CPSS 4.1 时代源码树，路径前缀为 `_cpss_mirror/trunk/package/utils/jwcpss/cpss/`。用户记忆中的 SDK 可能是 CPSS 4.0 或 4.1x，而且芯片手册可能使用内部代号；两者并不矛盾。若换到更高版本 CPSS，family 枚举和料号列表可能增加，本文的速查表应按上述流程重新生成。

## DXCH-10 小结与选型语境

这篇文档的核心不是背下所有料号，而是建立一套不会混淆的判断框架。下面十条可作为阅读和写作检查清单。

- family 是软件大类，device 是硬件料号，flavor 是 family 内的资源或市场定位细分；三者不能互相替代。
- xCat 是大接入家族，内部代号 AlleyCat、PonCat、TomCat、Bobcat 都是 device 级别名。
- xCat 里的 Bobcat 是老一代接入与城域器件，不属于 Bobcat2 family；98DX2100 与 98DX4100 系列是典型例子。
- xCat2 继续接入路线，重点是多速率与 2.5GbE 形态；但 98DX3036 等带 `/*XCAT*/` 标注的例外仍归 xCat。
- xCat3 聚焦高集成 1GbE 接入，AlleyCat3 与 PonCat3 的公开资料显示其 CPU 子系统、策略、桥接、路由与隧道引擎完整。
- Lion 与 Lion2 主要使用 98CX 前缀，面向高密度 10G/40G、数据中心、城域和运营商场景；98DX5178/5198 与 98FX9216 是 Lion 段的例外。
- Lion3 在这份 SDK 中只有 98CXEEEF 仿真占位，不能据此编造量产 98DX 料号。
- Bobcat2 覆盖 98DX42xx、821x、822x 与 BobK Caelum/Cetus；Drake 是 8216/8219/8224 所在 control plane medium scale 档的内部代号。
- Bobcat3 是 25G 一代，公开报道有送样信息，但这版 SDK 只列 98DX42FF 仿真占位。
- 判断新料号时，先查源码的 family 枚举、device 段和 device list，再用公开资料解释市场定位；不要用品牌词反推 family。

从选型语境看，xCat 三兄弟解决的是“接入端口够不够、成本够不够低、要不要集成 CPU 和 PHY”；Lion 与 Lion2 解决的是“高密度 10G/40G、多芯片背板和城域能力”；Bobcat2 解决的是“28nm 下 10G 接入、控制面、交换矩阵与更丰富的资源档”；Bobcat3 则把目标抬到 25G。理解这条主线之后，98DX 料号就不再是一串随机数字，而是一张可以追溯的代码—芯片—产品地图。
