# 可编程芯片流水线深度解析：PISA 模型如何落到硅片阶段

## PPIPE-01 可编程芯片为什么也必须讲流水线

很多人对可编程芯片有一个误解，觉得"可编程"就意味着软件随便写、硬件不再是约束。这个误解害人不浅。可编程芯片确实让你能改数据面行为，但它改的是"每一段流水线做什么"，而不是"流水线有几段、每段有多少资源"。换句话说，可编程性是在固定的硬件骨架上填内容，骨架本身仍然是流水线，而且阶段的刚性比固定芯片更明显——固定芯片的阶段由厂商设计好了，可编程芯片的阶段要你自己去分配、去填满、去满足时序。

这就是为什么学可编程芯片必须先学流水线。一个 P4 程序写完之后，能不能编译到芯片上、能不能跑线速，取决于它能否被映射到有限的硬件阶段里。表太多放不下、依赖链太长跨阶段开销太大、状态太大存不进片上内存——这些都是流水线资源约束，不是语言问题。不懂流水线，你写的 P4 程序会不停地在编译阶段碰壁，却不知道为什么。

这一篇和 P4 语言分册、Tofino 芯片分册的分工是：语言分册讲 P4 语法和 PISA 抽象模型，芯片分册讲 Tofino 的规格与开发环境，本篇回答中间的桥接问题——抽象模型里的"解析器、匹配动作阶段、反解析器"到底对应硅片上的什么，一个 P4 程序从源码到上板，中间经过了怎样的阶段映射，资源约束具体卡在哪。把这座桥搭起来，你才算真正理解了可编程数据面。

## PPIPE-02 PISA 抽象模型与真实流水线的对应

协议无关交换架构简称 PISA，是可编程交换芯片的主流抽象模型。它把数据面拆成四段：可编程解析器、入口匹配动作阶段、流量管理器、出口匹配动作阶段，最后加一个反解析器重组报文。这个模型描述的是"能力边界"，而真实芯片要把它变成具体的硅片电路。

抽象模型里的"解析器"在硅片上是一组可配置的解析阶段。开发者用 P4 描述要识别哪些协议头、按什么顺序解析，编译器把它编译成解析状态机，映射到硬件的解析电路上。这里的关键词是"可配置"——解析的字段和顺序能改，但解析阶段的物理数量和每阶段能处理的头数量是固定的。

抽象模型里的"匹配动作阶段"在硅片上是匹配动作单元，简称 MAU。多个 MAU 串成一条链，每个 MAU 里有查找引擎和算术逻辑。P4 程序里的每一张表、每一个动作，都要被编译器分配到某个 MAU 的某个阶段上。表与表之间的依赖关系决定了它们能不能放在同一阶段——无依赖的能并行塞进一个阶段，有依赖的必须排到不同阶段。

流量管理器这一段通常是半可编程的。队列、调度、缓冲管理这些能力是硬件固化的，你能配置参数（比如队列数、阈值、调度权重），但不能像匹配动作那样自由编程。原因很实际：流量管理对时序极其敏感，完全可编程会牺牲确定性和性能。反解析器与解析器对应，按出口改写指令重组报文，它的能力同样受硬件约束。

| 反解析器 | 中，按改写指令重组 | 支持的改写动作类型 |

## PPIPE-03 可编程解析器：阶段化的头识别

可编程解析器是整个流水线的入口，它的任务是把报文头按 P4 定义的顺序剥开，提取字段供后面的表使用。它和固定芯片的解析器在功能上类似，区别在于"解析哪些协议、按什么顺序"是程序定义的。

解析器的硬件实现是状态机加阶段资源。P4 里每定义一种头、一种跳转，编译器就把它翻译成状态机的一个状态；每剥一层头，就消耗一个解析阶段。硬件提供的解析阶段数有限，状态数量也有上限。一个典型的多层隧道报文——外层以太网、虚拟扩展局域网、内层网际协议、传输层——每一层都要占用状态和资源，嵌套越深，消耗越多。

解析器的一个关键产出是字段提取。解析出的字段被放到头向量里，供后续匹配动作阶段当查找键使用。这里有个重要约束：不是所有解析出的字段都能被后面的表用，字段要能跨阶段传递，而跨阶段传递占用连线资源。所以有经验的 P4 开发者会控制解析深度，只提取真正需要的字段——解析出来的字段如果没人用，白白消耗资源。

下面是一段 P4 解析器的示例代码，展示状态机如何逐层解析，以及它对应的阶段消耗。

```p4
parser IngressParser(packet_in pkt, out headers_t hdr)
{
    state start {
        pkt.extract(hdr.ethernet);              /* 以太网头，消耗一个解析动作 */
        transition select(hdr.ethernet.etherType) {
            0x0800: parse_ipv4;                 /* 网际协议版本四 */
            0x8100: parse_vlan;                 /* 虚拟局域网标签 */
            0x6558: parse_tunnel;               /* 隧道封装 */
            default: accept;
        }
    }

    state parse_vlan {
        pkt.extract(hdr.vlan);                  /* 标签头，再消耗一个 */
        transition select(hdr.vlan.etherType) {
            0x0800: parse_ipv4;
            default: accept;
        }
    }

    state parse_ipv4 {
        pkt.extract(hdr.ipv4);                  /* 三层头 */
        transition select(hdr.ipv4.protocol) {
            6: parse_tcp;                       /* 传输控制协议 */
            17: parse_udp;
            default: accept;
        }
    }

    state parse_tunnel {
        pkt.extract(hdr.tunnel);                /* 隧道头 */
        pkt.extract(hdr.inner_eth);             /* 内层以太网 */
        transition parse_inner_ipv4;            /* 继续解析内层 */
    }

    state parse_inner_ipv4 {
        pkt.extract(hdr.inner_ipv4);
        transition accept;
    }

    state parse_tcp { pkt.extract(hdr.tcp); transition accept; }
    state parse_udp { pkt.extract(hdr.udp); transition accept; }
}
```

对这段代码的判读：`start` 状态先提取以太网头，再按类型字段跳转，这是典型的解析状态机结构；`parse_vlan`、`parse_ipv4`、`parse_tunnel` 各提取一层头，每提取一次就消耗解析资源；`parse_tunnel` 里连续提取隧道头和内层以太网头，再跳到 `parse_inner_ipv4`，说明隧道路径是消耗资源最多的一条——它比普通转发多解析了两三层。要点是：这段 P4 代码看起来只是描述"怎么解析"，但编译器要把它翻译成硬件状态机，状态数、转移分支数、提取层次数都要塞进有限的解析资源里。如果芯片的解析阶段不够，或者提取的字段太多传不到后续阶段，编译就会失败。写解析器时要养成习惯：只解析后面真正要用的头，能在一层解决的不要拆成两层。

## PPIPE-04 匹配动作单元：一个阶段内部发生什么

匹配动作单元是匹配动作阶段的核心硬件，理解它内部的结构，才能明白 P4 的表和动作是怎么变成硅片操作的。一个 MAU 内部大致分三块：键构造、匹配查找、动作执行。

键构造负责从字段缓存里挑出需要的字段，拼成查找键。P4 表定义的 key 决定了这一步——哪些字段参与匹配、各占多少位。键构造不是免费的，字段跨阶段传递、拼接宽度、哈希计算都消耗资源和时序。

匹配查找用片上内存和查找引擎完成。精确匹配通常用哈希加静态随机存取内存，三元匹配或范围匹配用内容寻址存储器。内容寻址存储器容量小、功耗高，但支持掩码和优先级匹配，适合访问控制类规则；静态随机存取内存容量大，适合转发表这类精确匹配。一张 P4 表占哪种资源、占多少，取决于它的匹配类型和容量——这正是资源报告要告诉你的信息。

动作执行用算术逻辑单元对报文头或元数据做修改。动作里对同一个字段的多次读写会形成依赖，可能被拆到不同阶段；动作若涉及查另一张表，就产生新的依赖链。这是为什么"动作写得好不好"直接影响阶段占用。

下表把 P4 概念与 MAU 硬件资源对应起来，这是理解资源报告的基础。

| P4 概念 | 对应硬件资源 | 消耗取决因素 |
|---|---|---|
| 表的 key | 键构造逻辑与连线 | 字段数与总位宽 |
| 表的匹配类型 | 哈希引擎或三元匹配引擎 | 精确还是掩码匹配 |
| 表的容量 | 片上内存条目数 | 表项数量 |
| 动作的字段修改 | 算术逻辑单元 | 修改字段的数量与依赖 |
| 表间依赖 | 阶段排列顺序 | 依赖链长度 |

## PPIPE-05 阶段分配：P4 程序如何被摆到硅片上

编译器把 P4 程序变成硬件配置，最核心的工作是阶段分配——决定每张表、每个动作落在哪个阶段。这不是简单的顺序搬运，而是一个受多重约束的优化问题。

第一个约束是依赖。如果表乙的键依赖表甲的结果，乙必须排在甲之后的阶段，不能提前。第二个约束是资源。每个阶段的内存容量、匹配引擎数量、连线带宽有限，一张表放不下就得占多个阶段，或者拆表。第三个约束是时序。阶段之间的信号传递要满足时序要求，跨阶段的长距离传递代价高。编译器在这些约束下寻找可行的排列，找不到就报资源不足。

理解阶段分配，最有用的实践是看资源报告。编译成功后，开发环境会给出每张表落在哪个阶段、每个阶段用了多少内存、依赖链有多长。有经验的开发者会盯着这份报告优化：合并能合并的表、缩短依赖链、减少跨阶段字段传递。这些优化的目标不是让代码更短，而是让它放得下、跑得快。

下面是一段展示"资源意识"的 P4 代码对比——把两张独立的表合并，减少阶段占用。

```p4
/* 优化前：两张表各占一个阶段，串成依赖链 */
table acl_src {
    key = { hdr.ipv4.srcAddr : exact; }
    actions = { permit; deny; }
}
table acl_dst {
    key = { hdr.ipv4.dstAddr : exact; }
    actions = { permit; deny; }
}
apply {
    if (acl_src.apply().hit) { /* ... */ }
    if (acl_dst.apply().hit) { /* ... */ }
}

/* 优化后：合并成一张表，用通配符覆盖两种匹配，占一个阶段 */
table acl_combined {
    key = {
        hdr.ipv4.srcAddr : ternary;
        hdr.ipv4.dstAddr : ternary;
    }
    actions = { permit; deny; }
    const entries = {
        (0x0a000000 &&& 0xff000000, _) : permit;  /* 匹配源网段 */
        (_, 0x0a000000 &&& 0xff000000) : permit;  /* 匹配目的网段 */
    }
}
apply {
    acl_combined.apply();
}
```

对这段代码的判读：优化前两张表各占阶段，而且顺序执行，依赖链长度是二；优化后合并成一张三元匹配表，用掩码加通配符表达两种匹配语义，链长降为一。但要注意权衡——三元匹配表项比精确匹配表项"贵"得多，占内存更多、功耗更高。所以这种合并未必总是划算，必须用编译器的资源报告验证：合并后阶段数减少的收益，是否超过表项成本上升的代价。真正靠谱的做法永远是看报告，而不是凭直觉。这段代码的工程价值在于展示一种思维方式：写 P4 时心里要有阶段账，每加一张表都要问它占哪个阶段、和谁依赖、能不能合并。

## PPIPE-06 流量管理阶段：为什么它基本不可编程

流量管理器是可编程数据面里一个特殊的存在——它是 PISA 模型的一段，但可编程程度远低于解析和匹配动作。理解为什么，就能理解可编程芯片在"灵活"与"确定"之间的取舍。

流量管理器的职责是把报文按决策送到目标、排队、调度、处理拥塞、必要时复制。这些操作对时序极其敏感：队列深度每时每刻都在变，调度决策要在极短周期内完成，拥塞反馈要实时响应。如果把这段做成完全可编程的，让程序自由定义调度逻辑，就会引入不可预测的时延，破坏线速确定性。所以厂商的做法是把流量管理电路固化，只开放参数配置——你能设队列数、调度权重、缓冲阈值，但不能写一个新的调度算法。

这对开发者意味着什么？意味着在 P4 程序里，你无法改变流量管理的行为，只能通过元数据与它交互。入口匹配动作阶段产生的决策——目标端口、队列、优先级、是否复制——作为元数据交给流量管理器，后者按固化逻辑处理。你能做的是保证这些元数据被正确设置，而不是改变流量管理器怎么用它们。

一个实际的判断：如果业务需求涉及"自定义调度算法""自定义拥塞控制逻辑"，要清醒地认识到标准可编程交换芯片未必支持。这类需求要么在端侧实现，要么用能编程流量管理的专用硬件，要么接受用固化的机制加参数调优。把"可编程"理解成"什么都可编程"，会在方案设计阶段就埋下隐患。

下表把各段的可编程程度与典型需求对照，帮助你判断需求能否落地。

| 需求类型 | 实现段 | 可编程程度 | 落地方式 |
|---|---|---|---|
| 自定义协议解析 | 解析器 | 高 | P4 定义解析状态机 |
| 自定义转发表与动作 | 匹配动作阶段 | 高 | P4 定义表与动作 |
| 自定义队列调度 | 流量管理器 | 低 | 通常只能参数配置 |
| 自定义拥塞控制 | 流量管理器 | 低 | 需端侧配合或专用硬件 |
| 自定义报文改写 | 出口匹配动作 | 高 | P4 定义改写动作 |

## PPIPE-07 反解析器与出口改写：报文如何被重组

报文经过出口匹配动作阶段完成改写决策后，要由反解析器把改写后的头重新组装成完整的报文发出。反解析器与解析器是镜像关系：解析器按状态机剥开头，反解析器按改写指令重组头。

在 P4 模型里，出口动作对头的修改——添加虚拟局域网标签、替换地址、递减生存时间——并不会立即改动报文原始字节，而是记录成改写指令。反解析器在发送前按这些指令重组报文：删除某些头、插入某些头、替换字段值。这种"先指令后重组"的设计让同一套硬件能支持各种改写组合，同时保持线速。

反解析器的能力受硬件约束。它能执行哪些改写动作、能同时处理多少层头、能插入多长的模板，都是固定的。P4 程序里如果定义了一个硬件不支持的改写组合，编译器会报错。比如某些芯片不支持在反解析器里做任意长度的字段插入，只支持从预存模板里取内容——这就要求开发者把要插入的内容预先准备好。

一个实用建议：调试出口改写问题时，要同时看 P4 动作写的字段和反解析器的头定义。很多时候问题不是动作没执行，而是反解析器没有把修改后的头纳入重组列表——字段改了但没被发送出去，抓包看到的还是旧值。这类问题在固定芯片里表现为"改写策略没生效"，在可编程芯片里则多一层"反解析器配置是否覆盖了修改后的头"的排查维度。

## PPIPE-08 有状态处理：寄存器与跨包状态

可编程数据面最有价值的能力之一是有状态处理——让流水线记住之前报文的信息，用于后续报文的决策。这在固定芯片里很难做到，在 P4 里却是一等公民。但有状态处理恰恰是资源约束最紧的地方。

有状态处理靠寄存器实现。P4 里的寄存器是定义在某个阶段的一组存储单元，报文处理时可以读、改、写。典型应用包括流量统计、连接状态跟踪、速率限制、在网计算的梯度累加。因为寄存器存在特定阶段，访问它要满足阶段约束——只有报文走到那个阶段才能访问，而且读写同一寄存器的多次操作会形成依赖。

寄存器的资源约束体现在几方面。容量有限，寄存器数组的大小受片上内存限制；位宽有限，能存的值有上限；访问带宽有限，每个阶段每周期能读写的次数固定。一个需要频繁读写寄存器的算法，可能因为访问带宽不足而无法线速运行。另外，跨阶段访问寄存器代价高，因为状态要跨阶段传递。

下图把有状态处理的数据流画出来，说明寄存器如何嵌入流水线阶段。

:::figure id=PPIPE-08-01 | name=寄存器嵌入流水线的有状态处理 | dir=TB

node n2 "读取寄存器<br/>取出历史状态" teal

node n4 "写回寄存器<br/>更新状态" green
node n5 "后续报文<br/>读到更新后的状态" purple

edge n1 -> n2 "到达"
edge n2 -> n3 "作为输入"
edge n3 -> n4 "产生新状态"

:::

图中节点速览：n1 是当前报文进入某个阶段；n2 从寄存器读出历史状态；n3 把状态与当前报文结合做决策；n4 把更新后的状态写回寄存器；n5 是后续报文，读到更新后的状态，体现跨包的状态延续；n6 标注容量、位宽、带宽三类资源约束。整张图说明有状态处理的本质是跨报文的信息传递，而寄存器所在阶段、容量和访问带宽决定了这种处理能做到多复杂。

下面是一段有状态处理的 P4 示例，展示寄存器如何用于流量统计。

```p4
/* 有状态处理示例：按源地址统计报文数 */
register<bit<32>>(1024) pkt_counter;

action count_and_mark(in bit<32> index)
{
    bit<32> current;
    pkt_counter.read(current, index);       /* 读历史计数 */
    current = current + 1;                  /* 累加 */
    pkt_counter.write(index, current);      /* 写回新值 */
    if (current > 1000)
        hdr.meta.marked = 1;                /* 超阈值打标记 */
}

table count_by_src {
    key = { hdr.ipv4.srcAddr : exact; }
    actions = { count_and_mark; }
}
```

对这段代码的判读：`pkt_counter` 是定义在一组存储单元里的寄存器数组，容量 1024；`count_and_mark` 先读出当前计数、累加、写回，这是典型的读改写序列，三步操作形成依赖，必须排在包含该寄存器的阶段；`if (current > 1000)` 用状态做决策，体现有状态处理的价值——后续报文的行为依赖前面报文的累积结果。要点是这段逻辑对寄存器有三次访问（一读两写中的写算一次、读算一次，实际是一次读一次写），占用该阶段的访问带宽；如果这个表被高频命中，带宽可能成为瓶颈。真实项目里还要考虑并发语义——多个报文同时更新同一寄存器时的行为由硬件保证，但程序要理解这种保证的边界。有状态处理让可编程数据面能做的事情上了一个台阶，但代价是资源约束最紧，写之前一定要评估容量和带宽够不够。

## PPIPE-09 单遍与多遍：可编程芯片里的回炉问题

和固定芯片一样，可编程芯片也面临单遍与多遍的问题，而且因为有状态处理和灵活改写，情况更复杂。单遍指报文从头到尾只走一次流水线，多遍指报文处理到一半被送回入口重走。

在 P4 可编程芯片里，多遍通常发生在两种场景。一是隧道的解封装后再处理：报文在第一遍解封装外层隧道，露出的内层报文需要重新解析和查表，如果芯片不支持在同一遍里完成"解析外层—解封装—重新解析内层"，就必须回炉。二是复杂的有状态处理链：某些算法需要报文多次经过同一组寄存器，一遍排不下就要分遍。

多遍的代价在可编程芯片里同样沉重：吞吐下降、时延上升、内部回环资源被占用。而且可编程芯片因为有状态处理，多遍还可能带来状态一致性问题——同一报文两次经过时，寄存器状态已经被自己或别的报文改过，逻辑要能正确处理。因此高端可编程芯片把"单遍完成复杂处理"作为重要能力，选型和写程序时都要朝这个目标努力。

判断一个 P4 程序能否单遍完成，看两点：解析阶段能否一次看到所需字段，匹配动作阶段能否在一条依赖链里排完所有表。这两点都受阶段资源约束——这正是为什么阶段数越多的芯片，能支持的程序越复杂。

下表列出影响单遍能力的程序侧因素。

| 因素 | 对单遍的影响 | 优化方向 |
|---|---|---|
| 解析深度 | 深层字段一次看不到就要回炉 | 精简解析层次 |
| 表的数量 | 表太多排不下 | 合并表、删冗余表 |
| 依赖链长度 | 链太长跨阶段过多 | 重排逻辑、减少依赖 |
| 有状态访问 | 多次访问排不开 | 集中状态处理 |

## PPIPE-10 固定流水线与可编程流水线逐段对照

现在可以把两类芯片放到一起对照了。固定 ASIC 和可编程芯片在流水线的骨架上高度相似——都是入口、交换缓冲、出口三大段，都做解析、查表、改写——差别在于每一段的自由度、资源归属和开发方式。

固定 ASIC 的流水线由厂商设计并固化，每一段做什么、查几张表、怎么改写都是定死的。优势是极致的性能和功耗——硬件只为既定功能设计，没有可编程的额外开销；劣势是灵活性差，新协议要等下一代芯片。开发者面对它主要做配置，不改数据面逻辑。

可编程芯片的流水线骨架固化、内容可编程。解析和匹配动作阶段能由 P4 定义，开发者要自己分配阶段、管理资源；流量管理段仍然固化。优势是新功能能靠软件升级实现，劣势是同等工艺下吞吐功耗时延通常不如深度优化的固定逻辑，而且开发门槛高——要懂语言、懂架构、懂资源约束。

下表逐段对照两类芯片，这是本篇的核心总结。

| 流水线段 | 固定 ASIC | 可编程芯片 |
|---|---|---|
| 解析器 | 厂商固化，支持既定协议 | P4 定义，受阶段数约束 |
| 查表 | 固定的表集合与容量 | P4 定义表，受内存与阶段约束 |
| 动作 | 固定的动作集 | P4 定义动作，受逻辑单元约束 |
| 流量管理 | 固化加参数配置 | 同样固化加参数配置 |
| 改写 | 固定的改写组合 | P4 定义，受反解析器能力约束 |
| 有状态处理 | 有限支持 | 寄存器支持，受容量带宽约束 |
| 开发方式 | 配置驱动 | 编程驱动，需编译映射 |

一个工程上的判断标准：需求稳定、追求极致性能和成本，选固定 ASIC；需求快速演进、要自定义数据面、要细粒度在网遥测，选可编程芯片；很多场景其实两者并用——固定芯片承担主干转发，可编程芯片承担创新功能。理解流水线，才能判断某个具体需求该交给谁。这不是口号，而是要在流水线的每一段上逐项比对：这个功能固定芯片能不能做，可编程芯片做的话占几个阶段、会不会挤掉别的功能。这样的对比才是可落地的选型依据。

## PPIPE-11 调试与优化：从资源报告到实际验证

可编程芯片的开发闭环里，调试和优化占大头，而它们都围绕流水线展开。

第一阶段是编译期验证。写完 P4 程序先编译，看是否通过资源检查。编译失败通常是资源不足——阶段放不下、内存不够、依赖链太长。这时候要看资源报告，定位是哪张表、哪个阶段超了，然后按前面讲的方法优化：合并表、缩短依赖、减少字段传递。

第二阶段是仿真验证。没有硬件时，可以用软件模型或芯片仿真器加载程序，打流验证功能逻辑。这一阶段重点看功能对不对——解析有没有识别预期的头、表项有没有命中、动作有没有执行、改写是否生效。仿真不看线速，只看逻辑正确性。

第三阶段是上板验证。真实硬件上要看性能——能不能跑线速、时延多少、资源占用如何。这一阶段要结合实际流量，观察队列、拥塞、状态处理的表现。特别是有状态处理，仿真时状态变化简单，真实流量下并发更新同一状态的行为要重点验证。

下表把三个阶段的目标、手段和常见问题列出来。

| 阶段 | 目标 | 主要手段 | 常见问题 |
|---|---|---|---|
| 编译期 | 程序能落到硬件 | 资源报告 | 阶段不足、内存不够、依赖太长 |
| 仿真期 | 功能逻辑正确 | 软件模型打流 | 解析错、表项未命中、改写不生效 |
| 上板期 | 性能与稳定性 | 真实流量测试 | 跑不到线速、状态并发问题 |

一个贯穿三阶段的经验：优化要基于证据，不要凭感觉。编译期看资源报告，知道阶段和内存花在哪；仿真期看打流结果，确认逻辑对不对；上板期看性能计数，找到真正的瓶颈。跳过任何一步直接优化，往往优化了不是瓶颈的地方。这也呼应了前面反复强调的观点——可编程芯片的复杂度在流水线资源上，而资源问题只能靠数据定位。

## PPIPE-12 小结：把可编程芯片当成流水线来理解

把这篇串起来：PISA 抽象模型的五段都能落到硅片上，但自由度不同——解析和匹配动作高度可编程，流量管理基本固化，反解析器中度可编程；P4 程序通过编译器映射到硬件阶段，依赖、资源、时序三类约束决定程序能否落地；解析器按状态机逐层剥头，消耗解析阶段；匹配动作单元由键构造、查找引擎、动作执行三部分组成，一张表加一个动作大体对应一个单元的占用；有状态处理靠寄存器实现，容量、位宽、带宽是最紧的约束；单遍还是多遍决定隧道与复杂处理的性能。

最重要的结论只有一个：可编程芯片的可编程性，是在固定流水线骨架上填内容。骨架的刚性——阶段数、内存容量、依赖链、解析深度——才是真正限制你的东西。写 P4 程序本质上是在做一次资源规划：把有限的逻辑塞进有限的阶段，同时满足时序、保住线速。理解了这一点，你就不会再问"为什么这么写编译不过"，而是会问"这张表该放哪个阶段、能不能和那张合并、依赖链能不能缩短"——后者才是工程思维。

回到岗位要求里"利用可编程芯片研发超融合可编程平台"这句话，它需要的正是这种能力：不只是会写 P4，而是知道程序落在硬件的哪里、代价多大、能不能落地。流水线知识就是把 P4 从"一门语言"变成"一项工程能力"的那座桥。

对照交换芯片流水线分册看，你会发现两类芯片的骨架惊人地一致——都是入口解析查表、交换缓冲、出口改写发送。可编程芯片并没有推翻这套骨架，只是把其中几段的控制权交给了程序员。所以交换芯片流水线是基础，可编程流水线是在它之上的进阶；两篇一起读，才能对"数据面到底怎么工作"形成完整图景。
