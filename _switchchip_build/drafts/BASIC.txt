# 交换芯片技术资料 · 交换芯片基础知识总纲

## BASIC-01 网络与交换机基础：从分层到整机

在讲交换芯片怎么转发之前，先把"被转发的东西"和"装它的机器"讲清楚。这一章是全书的地基：如果你还不清楚一个以太网帧长什么样、IP 地址和 MAC 地址各管什么、一台交换机里到底有哪些部件，那么后面讲的 FDB、LPM、TCAM 都只是名词。本章用六节补齐这些前置知识。

### 1. OSI 与 TCP-IP 分层：数据如何被层层封装

网络通信的本质是把数据一层层包起来、送出去，再一层层拆开。业界用两个模型描述这件事：OSI（开放系统互连）七层模型是教学用的参考框架，TCP/IP 四层模型是实际互联网使用的协议栈。两者可以这样对应——TCP/IP 的应用层对应 OSI 的应用层、表示层、会话层；传输层对应传输层；网际层对应网络层；网络接口层对应数据链路层和物理层。

对交换机学习者，真正需要记住的是**每一层给数据加了什么头、这个头被谁读取**：

- **应用层**：产生要传的数据，例如 HTTP 请求、DNS 查询。交换机不关心这一层的内容（除非做深度包检测）。
- **传输层**：加上 TCP 或 UDP 头，写入源端口、目的端口。端口用来区分同一台主机上的不同应用——80 是网页、443 是加密网页、53 是域名解析。交换机做负载均衡哈希时用的五元组，就有这两个端口。
- **网络层**：加上 IP 头，写入源 IP、目的 IP、TTL。路由器和三层交换机读这个头决定往哪个网段转发。
- **数据链路层**：加上以太网头，写入源 MAC、目的 MAC、可能的 VLAN 标签。二层交换机只认这一层——这是它得名"二层"的原因。
- **物理层**：把 bit 变成电信号或光信号，通过网线或光纤传出去。SerDes 就工作在这一层。

这个"层层加头"的过程叫**封装（encapsulation）**，接收端反向剥掉叫**解封装（decapsulation）**。一个关键结论是：每一层只看自己那层的头，下层对上层透明。二层交换机读以太网头就够了，不需要理解 IP；三层交换机读 IP 头，但也不会去解析 HTTP。理解这一点，就能明白为什么交换芯片的解析引擎（parser）只要识别到某几层就能做转发决策。下图把封装层次画出来。

### 2. 以太网帧与 IP 报文：交换芯片真正看到的东西

协议栈是抽象的，交换芯片实际处理的是一个个具体的帧。以太网帧以 7 字节前导码和 1 字节帧起始定界符开始，随后是 6 字节目的 MAC、6 字节源 MAC；如果带 VLAN，则插入 4 字节的 802.1Q 标签（其中 12 位是 VLAN ID，这正是 VLAN 最多只有 4096 个的原因）；接着 2 字节类型字段指明载荷协议（0x0800 表示 IPv4，0x86DD 表示 IPv6）；然后是 46 到 1500 字节的载荷；最后 4 字节帧校验序列（FCS）用于检错。

IP 报文紧接在以太网头之后。IPv4 头至少 20 字节，关键字段包括：版本与首部长度、总长度、TTL（每过一跳减一）、协议号（6 为 TCP、17 为 UDP）、源 IP 与目的 IP。交换芯片在三层转发时要读的正是这些字段——查路由表用目的 IP，改写时用 TTL，区分协议用协议号。

这里有一个容易被忽略的细节：**帧长是有限制的**。标准以太网的最大传输单元（MTU）是 1500 字节，超过就要分片（IPv4 支持分片，IPv6 通常由源端避免）。VXLAN 这类隧道封装会额外增加约 50 字节开销，所以 underlay 网络常把 MTU 调到 1600 以上，否则封装后的报文会被分片或丢弃——这是讲解 VXLAN 时经常踩的坑。下表把帧和报文中与转发相关的关键字段列出来。

| 层级 | 关键字段 | 长度 | 被谁读取 | 转发中的用途 |
|---|---|---|---|---|
| 以太网 | 目的 MAC | 6 字节 | 二层交换机 | 查 MAC 表决定出口 |
| 以太网 | 源 MAC | 6 字节 | 二层交换机 | 学习，写入 MAC 表 |
| 以太网 | VLAN ID | 12 位 | 二三层交换机 | 区分二层域、隔离广播 |
| IPv4 | 目的 IP | 4 字节 | 三层交换机/路由器 | 查路由表做 LPM |
| IPv4 | TTL | 1 字节 | 三层设备 | 递减防环，为 0 丢弃 |
| 传输层 | 目的端口 | 2 字节 | 负载均衡/ACL | 哈希选路、策略匹配 |

理解字段与用途的对应关系很重要：后面讲到 L2 查表用 MAC、L3 查表用 IP、负载均衡哈希用五元组、TTL 递减要重算校验和，都能在这张表里找到依据。芯片的解析引擎做的事，本质上就是从帧里把这些字段抽出来，组成查表的键。

### 3. MAC 地址、IP 地址、子网与网关

地址体系是转发决策的基础，三者分工不同，初学者最容易混淆。

**MAC 地址**是烧在网卡上的 48 位物理地址，写成六组十六进制数，如 `00:11:22:33:44:55`。它在同一个二层域（同一个 VLAN）内有效，用来回答"这个帧该交给本网段的哪块网卡"。MAC 地址是扁平的、没有层次，因此无法像 IP 那样做聚合——这也是二层转发表只能精确匹配、规模受限的原因。

**IP 地址**是 32 位逻辑地址（IPv4），写成点分十进制，如 `192.168.1.10`。它是分层的，由网络位和主机位两部分组成，靠子网掩码区分。分层带来两个好处：可以做路由聚合（一条路由覆盖一个网段），可以在不同网段复用私有地址。三层转发查的正是目的 IP。

**子网掩码**告诉我们 IP 地址里哪几位是网络位。例如 `255.255.255.0`（写作 /24）表示前 24 位是网络号，后 8 位是主机号。`192.168.1.10/24` 与 `192.168.1.20/24` 属于同一子网，可以直接二层通信；`192.168.2.10/24` 就是另一个子网，必须经过网关。

**网关**是连接不同网段的设备接口地址。主机发现目的 IP 不在本地子网时，会把帧的目的 MAC 写成网关的 MAC，请网关代转发。前面讲 L2/L3 协同时提到的 SVI（交换虚拟接口），就是交换机上充当网关的接口——它的 MAC 让芯片知道"这个帧要交给三层处理"。

一次完整判断可以概括为：拿目的 IP 与自己的掩码做按位与，若结果等于本子网网络号，就二层直连（ARP 找对方 MAC）；否则交给网关（ARP 找网关 MAC）。下面的伪代码把这个判断写出来，它正是主机发包前的必经步骤，也是理解"为什么 ARP 请求是广播"的钥匙。

```text
# 工程理解伪代码：主机判断目的地址是否在本地子网（非真实系统接口）
dst_ip   = 192.168.2.10
my_ip    = 192.168.1.10
mask     = 255.255.255.0                     # /24
if (dst_ip & mask) == (my_ip & mask):
    arp_target = dst_ip                      # 同子网：直接找目的主机
else:
    arp_target = gateway_ip                  # 跨子网：找网关
dst_mac  = arp_resolve(arp_target)           # 广播 ARP 请求，单播应答
send_frame(dst_mac, dst_ip)                  # 用解析到的 MAC 封装并发送
```

对这段伪代码的判读：`dst_ip & mask` 与 `my_ip & mask` 分别算出目的与本机所在的网络号，相等说明在同一子网。同子网时 `arp_target` 是目的主机本身，跨子网时是网关——这一步决定了后续 ARP 请求问的是谁。`arp_resolve` 内部会发一个目的 MAC 为全 F 的广播帧，因为此时还不知道目标 MAC；应答则是单播。最后用解析到的 MAC 封装帧。这段伪代码解释了两个常见现象：arp 请求为什么是广播，以及为什么跨网段通信的第一跳 MAC 是网关的而不是最终目的主机的。

### 4. 一台交换机由什么组成

到目前为止我们一直在说"芯片怎么转发"，但一台能插网线、能配置的交换机远不止一颗芯片。理解整机组成，才能把芯片知识落到真实设备上。

一台典型的盒式交换机包含这些部件：**交换 ASIC** 是核心，负责线速转发，就是本资料的主角；**CPU（控制面处理器）** 跑网络操作系统和协议栈，负责处理不能由硬件转发的报文（如 ARP 请求、路由协议 hello）以及响应用户配置；**端口模块与光模块** 完成光电转换与 SerDes 串行化；**片外存储器** 存放 MAC 表、路由表等大容量表项和报文缓冲；**管理接口**（管理网口、Console、USB）用于带外管理。

这里要建立一个重要概念：**CPU 与 ASIC 的分工**。绝大多数数据报文由 ASIC 直接转发，CPU 不参与——这叫"硬件转发"。但有些报文必须交给 CPU，例如上送的 ARP 请求、未知协议报文、需要软件处理的控制协议——这叫"punt（上送）"或"软件转发"。如果攻击流量把大量报文逼上 CPU，控制面就会被淹没，所以要配置 CoPP（控制面限速）保护 CPU。前面在运维面提到 CoPP，这里给出了它存在的根本原因。下图把整机组成画出来。

node n3 "CPU 控制面<br/>协议与配置" amber
node n4 "端口与光模块<br/>光电转换" green

图中节点速览：n1 是交换机整机的总纲；n2 是交换 ASIC，负责线速转发，是全书主角；n3 是 CPU 控制面，运行协议栈与响应配置；n4 是端口与光模块，完成光电转换；n5 是片外存储，存放表项与缓冲；n6 是管理接口，用于带外管理；n2 与 n3 之间标出"报文上送"，表示需要软件处理的报文会从 ASIC 交给 CPU。整张图说明芯片只是整机的一部分，CPU 与芯片通过上送通道协作。

整机视角还引出两个常见形态：**盒式交换机**固定端口、成本低，常用于接入层；**框式交换机**由主控板、线卡、交换网板组成，端口密度高、可冗余，用于核心层。两者转发原理相同，区别在规模与可靠性。白盒交换机则指硬件与网络操作系统解耦、可自由安装 NOS（如 SONiC）的机型，这正是 SAI 抽象层要解决的问题。

### 5. VLAN 与端口类型：trunk、access 与 hybrid

前面多次提到 VLAN（虚拟局域网），但一直没系统讲它到底是什么、端口怎么"属于"某个 VLAN。这是初学者最容易卡住的一组概念，也是读懂交换机配置的必经门槛——排障章节里反复出现的"trunk 是否放行目标 VLAN"，根源就在这里。

**VLAN 解决什么问题**。一台交换机的所有端口默认在同一个二层域里，广播帧会泛洪到所有端口。VLAN 的价值是把一个物理交换机切成多个逻辑上独立的交换机：不同 VLAN 的端口之间默认二层不通，广播也被限制在各自 VLAN 内。这样既隔离了广播域、提升性能，又实现了安全隔离——财务和访客即使插在同一台交换机上，也互相看不见。VLAN ID 是 12 位，因此最多 4096 个（0 和 4095 保留，可用 1～4094），这正是前一章帧结构里"802.1Q 标签含 12 位 VLAN ID"的实际含义。

**带标签与不带标签的帧**。以太网帧里那个 4 字节的 802.1Q 标签，完整叫法是"标签协议标识（TPID）+ 标签控制信息（TCI）"，TCI 里 12 位是 VLAN ID、3 位是前面 QoS 章提到的 802.1p 优先级、1 位用于丢弃指示。带标签的帧叫 tagged，不带的叫 untagged。**关键问题来了**：一台交换机有几十个端口，怎么决定某个端口收进来的 untagged 帧属于哪个 VLAN、发出去的帧要不要带标签？答案就是端口类型。

三种端口类型的行为差别，是本节的核心：

- **access（接入端口）**：只属于一个 VLAN，通常连接终端（PC、打印机、摄像头）。收到 untagged 帧时给它打上本端口的 VLAN 标签；发送时剥掉标签还原成 untagged 帧发给终端——因为普通网卡不认识 VLAN 标签。可以把它理解为"终端侧的翻译员"。
- **trunk（干道端口）**：承载多个 VLAN，通常连接另一台交换机或路由器。收到的 tagged 帧按原有 VLAN 转发，只在**允许列表（allowed VLAN）**里的 VLAN 才放行；发送时保持标签，让对端知道这个帧属于哪个 VLAN。这是多交换机环境下 VLAN 能跨设备延伸的关键。
- **hybrid（混合端口）**：兼具两者特性，可配置多个 VLAN 带标签发送、另一个 VLAN 不带标签发送。它在部分厂商（如华为）设备上是默认类型，在思科体系里较少见——遇到时需按厂商文档核对行为差异。

还有一个容易踩坑的概念：**native VLAN（本征 VLAN）**。trunk 上可以指定一个 VLAN 为 native，这个 VLAN 的帧在 trunk 上**不带标签**发送。两端 trunk 的 native VLAN 必须配置一致，否则会出现"VLAN 泄漏"——一边的 untagged 帧被另一边归到不同 VLAN。这是一个经典的配置错误，也是排障时要重点核对的项。

**VLAN 间通信**。同一 VLAN 内靠二层交换即可；不同 VLAN 之间默认不通，必须经过三层转发——这正是前面 L2/L3 协同讲的 SVI（交换虚拟接口）或单臂路由（router-on-a-stick）的用武之地。可以把 VLAN 理解为"二层域的边界"，跨边界就必须上三层。下图把三种端口对标签的处理画出来。

| 端口类型 | 典型连接对象 | 收到 untagged 帧 | 发送帧 | 承载 VLAN 数 |
|---|---|---|---|---|
| access | 终端 PC、打印机 | 打上本端口 VLAN 标签 | 剥标签，发 untagged | 1 个 |
| trunk | 交换机、路由器 | 归入 native VLAN | 保留标签（native 除外） | 多个，按允许列表 |
| hybrid | 终端或交换机 | 归入配置的 untagged VLAN | 按配置决定带或不带 | 多个，混合 |

下面这段伪代码把端口收发时的标签处理固定成过程，便于对照真实配置理解。

```text
# 工程理解伪代码：端口收发时的 VLAN 标签处理（非真实系统接口）
# 入方向：收到帧，按端口类型确定它属于哪个 VLAN
if port.type == ACCESS:
    frame.vlan = port.access_vlan          # 给 untagged 帧打上接入 VLAN
elif port.type == TRUNK:
    if frame.has_tag:
        if frame.vlan not in port.allowed: # 不在允许列表：丢弃
            drop(frame)
    else:
        frame.vlan = port.native_vlan      # untagged 归入本征 VLAN
# 出方向：按端口类型决定保留还是剥掉标签
if port.type == ACCESS:
    send(untag(frame), port)               # 终端不认标签，剥掉
elif port.type == TRUNK:
    if frame.vlan == port.native_vlan:
        send(untag(frame), port)           # 本征 VLAN 不带标签
    else:
        send(frame, port)                  # 其余保留标签
```

对这段伪代码的判读：入方向的三条分支体现 access 直接打标签、trunk 先查允许列表、untagged 帧归入 native VLAN 的差异；`if frame.vlan not in port.allowed` 的丢弃动作，正是排障章节"trunk 是否放行目标 VLAN"这条检查项的代码化。出方向里 access 一律剥标签、trunk 只对 native VLAN 剥标签，其余保留——这是两端 native VLAN 必须一致的直接原因：若 A 端剥了标签发出，B 端会把它归入 B 端自己的 native VLAN，两边配置不同就会串VLAN。理解这段伪代码，绝大多数 VLAN 配置问题都能自己推导出来。

VLAN 还有两个进阶概念值得知道。**QinQ（VLAN 堆叠）** 在原有标签外再套一层标签，让运营商能用一层 VLAN 承载客户的多个 VLAN，是城域网和运营商二层专线的基础。**VLAN 聚合（Super VLAN）** 把多个 VLAN 共用一个网关地址，节省 IP 地址，常见于用户密集的场景。这两者都属于"在 12 位 VLAN ID 不够用或需要层次化"时的扩展手段，了解其存在即可，具体配置按厂商文档执行。

### 6. 物理层与链路基础：冲突域、双工与自协商

VLAN 之上还有一层更基础、但同样常被跳过的内容：端口和链路本身是怎么工作的。这几个概念看着"不重要"，却解释了为什么换根网线就能解决丢包、为什么两端速率不一致会导致端口 down。

**冲突域与广播域**。早期的集线器（hub）所有端口共享一条总线，两台设备同时发送就会冲突，这叫一个冲突域；交换机则每个端口就是一个独立冲突域，配合全双工基本消除了冲突。广播域是另一回事——广播帧能到达的范围，交换机的所有端口默认在同一广播域，VLAN 的作用就是切分广播域。一句话记住：**交换机隔离冲突域，VLAN 隔离广播域，路由器隔离两者**。这是理解"为什么需要 VLAN"和"为什么需要路由器"的共同基础。

**双工与自协商**。半双工（half duplex）指同一时刻只能发或收，是早期共享介质的产物；全双工（full duplex）指收发可以同时进行，是现代交换网络的常态。两端端口通过自协商（auto-negotiation）自动确定速率与双工模式——网线里特定的电信号脉冲告诉对方自己支持哪些速率（10M/100M/1G/2.5G/5G/10G 等）。**自协商失败是经典故障源**：一端强制全双工、另一端自协商时，可能协商成半双工，表现为大量冲突和丢包；网线质量差时，万兆端口可能降速到千兆甚至起不来。排障时核对端口的实际速率与双工状态，是物理层检查的第一步。

**接口形态与介质**。RJ45 电口用双绞线（五类、六类等），常见 1G/2.5G/10G，传输距离受线材限制（通常 100 米内）；光口用光模块加光纤，按形态有 SFP、SFP+、QSFP28、QSFP-DD 等，按距离有短距多模与长距单模。前面容量章讲的光模块形态与 SerDes 速率，落到这里就是"端口物理上长什么样、能插什么模块"。高速端口（400G/800G）基本都是光口或直接铜缆（DAC），因为电口在那样速率下走不了多远。

**PoE（以太网供电）**。通过网线在传数据的同时给终端供电，供电端叫 PSE（如 PoE 交换机），受电端叫 PD（如 IP 电话、摄像头、无线 AP）。标准从 802.3af（约 15W）演进到 802.3at（约 30W）和 802.3bt（最高约 90W）。部署 PoE 交换机的实际约束是**整机供电功率预算**——所有端口的供电需求加起来不能超过电源能力，这也是选型时要单独核对的参数。

### 7. 小结：把地基与后面的章节连起来

本章建立了六块地基，后面每一章都会用到：

1. **分层与封装**：帧的每一层头都被特定的设备读取——这是解析引擎只识别若干层就能转发的依据。
2. **字段与用途**：目的 MAC 用于二层查表，目的 IP 用于三层 LPM，端口用于哈希，TTL 用于防环——这是查表键设计的依据。
3. **地址体系**：MAC 扁平、IP 分层、掩码定网段、网关连网段——这是 L2/L3 协同判断的依据。
4. **整机组成**：ASIC 转发、CPU 控制、两者靠上送协作——这是控制面与数据面分工的依据。
5. **VLAN 与端口类型**：VLAN 切分广播域，access 打标签、trunk 透传标签、hybrid 混合，native VLAN 两端必须一致——这是理解交换机配置与二层排障的依据。
6. **物理层与链路**：交换机隔离冲突域、VLAN 隔离广播域；自协商决定速率与双工，介质形态与 PoE 预算决定部署——这是物理层排障与选型的依据。

带着这四块地基再回头看"交换芯片用硬件在纳秒级完成查表—搬运—排队—改写"，每个词就都有了具体所指。下一章从交换芯片的一句话本质讲起，正式进入正题。


## BASIC-02 常见网络机制：地址获取、网关冗余与多机扩展

前一章补上了 trunk 与物理层这些"配置里天天见、书里却不讲"的基础。这一章继续沿着同一条思路，补齐另一批入门必备却几乎空白的机制：终端怎么拿到地址、网关怎么做到不单点、交换机之间怎么堆成一台、以及路由表里的路由从哪里来。这些内容不是交换芯片内部的转发流水线，但**不懂它们就读不懂网络配置、也看不懂排障输出**——把它们放在入门地基之后、正式进入芯片之前，是为了让后面讲"芯片查什么表"时，你能知道那些表项最初是从哪来的。

### 1. DHCP 与 DNS：终端如何获得地址与找到名字

一台 PC 插上网线后，并不会天生知道自己该用什么 IP。它靠两个基础服务解决"我是谁"和"对方在哪"的问题。

**DHCP（动态主机配置协议）**负责分发地址与配置。终端开机后以广播方式发出发现报文（Discover，源 IP 为 0.0.0.0、目的为 255.255.255.255），网络里的 DHCP 服务器回应提供（Offer），终端再请求（Request），服务器确认（Ack）——四步合称 DORA。除 IP 地址外，DHCP 还下发子网掩码、默认网关、DNS 服务器地址与租约时间。这里有两个与交换机直接相关的点：第一，Discover 是广播，必须靠 VLAN 内的泛洪送达服务器，若服务器不在同一 VLAN 就需要 **DHCP 中继（relay）**——通常由三层接口或交换机配置 helper 地址来转发；第二，前面端口安全章讲的 DHCP Snooping，正是监听这个过程建立"IP-MAC-端口"绑定表，防止有人私设服务器下发假网关。

**DNS（域名系统）**负责把域名解析成 IP。你在浏览器输入域名，终端向 DNS 服务器查询，拿到目的 IP 后才会发起后续连接。对交换机而言，DNS 查询本身只是普通 UDP 报文，按路由正常转发即可——交换机不关心查询内容，除非部署了深度包检测。**但有一个例外值得记住**：白盒交换机上运行网络操作系统时，设备自己也会作为客户端去查 DNS（比如解析遥测采集器地址），这时若 DNS 配置错误，表现就是"某个遥测功能起不来"，而数据转发完全正常——这类问题常被误判为芯片故障。

### 2. 子网划分与 CIDR：从掩码到前缀长度

前面讲过子网掩码决定网络位与主机位，但有一个更简洁的记法必须掌握，否则读不懂路由表和配置。**CIDR（无类域间路由）**用斜杠加位数表示掩码长度，例如 `192.168.1.0/24` 等价于掩码 `255.255.255.0`，`/8` 等价于 `255.0.0.0`。位数越大，网络位越多、主机位越少，每个子网能容纳的主机越少。

在这个记法上做**子网划分（subnetting）**很直观：把原本的主机位借几位当网络位。比如一个 `/24` 有 256 个地址，借 1 位就切成两个 `/25`，每个 128 个地址。反过来，**路由聚合（supernetting / 汇总）**是把多个连续网段合并成一条更短前缀的路由——`192.168.0.0/24` 和 `192.168.1.0/24` 可以聚合成 `192.168.0.0/23`。聚合是控制路由表规模的核心手段，也是前面表项预算章"FIB 表项不足时靠前缀聚合"的具体做法。

还需要知道 **VLSM（可变长子网掩码）**：同一个网络的不同子网可以用不同长度的前缀——连接两台路由器的点对点链路用 `/30` 就够，而用户网段用 `/24`，这样不浪费地址。读懂一张地址规划表时，看到同一主网下出现多种前缀长度，就是 VLSM 在起作用。

下面这段伪代码把"判断同网段"和"聚合"两个常见操作写成可复核的形式，与前一章的掩码判断衔接。

```text
# 工程理解伪代码：CIDR 记法的同网段判断与聚合（非真实系统接口）
def in_same_subnet(ip_a, ip_b, prefix):
    mask = prefix_to_mask(prefix)              # /24 -> 255.255.255.0
    return (ip_a & mask) == (ip_b & mask)       # 网络号相同即同网段
# 聚合判断：两个 /24 是否可合成一个 /23
net1 = 0xC0A80000   # 192.168.0.0
net2 = 0xC0A80100   # 192.168.1.0
if (net1 ^ net2) >> 9 == 0 and (net1 >> 23) == (net2 >> 23):
    summary = apply_prefix(net1, 23)           # 得到 192.168.0.0/23
```

对这段伪代码的判读：`prefix_to_mask` 把 `/24` 这样的记法还原成掩码，`(ip & mask)` 相等即同网段，这与前一章主机判断的逻辑完全一致，只是写法更通用。聚合判断里 `net1 ^ net2` 的异或结果若只差在主机位（右移 9 位后为 0），且两者落在同一个 `/23` 块里，就可以合并成一条 `/23` 路由。这段伪代码说明：**CIDR 不只是书写习惯，它是路由聚合与表项压缩的运算基础**——理解了前缀位怎么借、怎么还，就能理解为什么精心规划的地址能让路由表小一个数量级。

### 3. 路由表里的路由从哪来：直连、静态与动态

前面讲 L3 流水线时说"查 FIB 表做最长前缀匹配"，但没有交代 FIB 里的内容是怎么来的。对交换机学习者，考察路由表的来源比考察路由协议细节更重要。

**直连路由**：接口配置了 IP 且状态为 up，设备自动产生指向该网段的路由。它不需要任何协议，是路由表最基础的部分。

**静态路由**：管理员手工写下的固定路径，例如"去往 10.0.0.0/8 走下一跳 192.0.2.1"。优点是确定、无协议开销；缺点是拓扑变化时不会自动调整。默认路由（`0.0.0.0/0`）是静态路由的特例，表示"所有未知目标都走这里"，是接入层交换机的常见配置。

**动态路由**：设备通过协议自动学习路径。内部网关协议常见 OSPF（开放最短路径优先），基于链路状态计算全网最短路径；外部网关协议是 BGP（边界网关协议），运营商与大型数据中心之间用它交换可达性。前面 EVPN 章节讲的 BGP，就是把它从"只是运营商协议"拉进了数据中心 overlay。动态路由的价值是拓扑变化时自动收敛，代价是协议计算与控制面开销——这正是前面控制面章"收敛速度由表项更新速率决定"的来源。

当同一个目的有多条来源不同的路由时，设备靠**管理距离（administrative distance）**决定信谁：直连最优先，静态次之，动态按协议可信度排序。理解这个优先级，就能解释"为什么我加了静态路由却不生效"——很可能被更优先的直连路由盖过了。

下表把三类路由的来源、配置与适用场景并列，便于对照路由表输出。

| 路由来源 | 产生方式 | 拓扑变化响应 | 典型场景 | 开销 |
|---|---|---|---|---|
| 直连 | 接口 up 且配 IP 自动生成 | 接口 down 自动撤销 | 本地直连网段 | 无 |
| 静态 | 管理员手工配置 | 不自动调整，需手动改 | 默认路由、简单拓扑、固定出口 | 极低 |
| 动态（OSPF） | 协议自动学习 | 自动收敛，秒级 | 企业网内部、园区网 | 控制面 CPU 与协议报文 |
| 动态（BGP） | 协议自动学习 | 策略可控，收敛较慢 | 运营商、数据中心 EVPN | 表项与策略复杂度高 |

### 4. 网关冗余：VRRP 与网关切换

默认网关是终端访问外网的必经之路，如果网关设备宕机，整个网段的通信就断了。网关冗余解决这个问题：让两台（或多台）设备共同对外呈现一个**虚拟 IP**，终端把网关指向这个虚拟地址，由主设备实际转发，主设备故障时备设备接管。

**VRRP（虚拟路由冗余协议）**是开放标准，工作方式类似：参与的设备组成一个冗余组，按优先级选出一个 Master，只有 Master 响应针对虚拟 IP 的 ARP 请求并转发流量；Backup 持续监听 Master 的通告，若一段时间内收不到就升为主。对终端而言，网关 IP 始终不变，只是 ARP 解析到的 MAC 换成了新主设备的——切换过程终端无感知。**HSRP（热备份路由协议）**是厂商私有方案，概念类似，术语不同（Active/Standby）。两者解决同一问题，看到配置时按所属厂商区分即可。

这里有一个与交换芯片直接相关的衔接点：**网关切换依赖 ARP 与 MAC 表的更新**。新主设备接管后，需要让下游设备刷新 ARP 缓存——通常靠发送**免费 ARP（gratuitous ARP）**，即主动广播自己的 IP 与 MAC 映射，让其他设备更新缓存；交换机侧则要靠 MAC 表老化或主动刷新，避免继续把发给虚拟 IP 的帧送往旧主设备的端口。如果免费 ARP 被抑制、或 MAC 表老化时间过长，就会出现"网关切过去了但流量还往旧设备走"的现象。这是网关冗余排障中最常见的坑，也是把前面 ARP/MAC 学习知识和实际高可用场景连起来的关键一环。

图中节点速览：n1 是终端，网关配置始终指向虚拟 IP；n2 是主网关，平时响应 ARP 并承担转发；n3 是备网关，监听主设备通告；n4 表示主设备故障导致通告中断；n5 是备机升主并发出免费 ARP；n6 表示终端刷新 ARP 缓存、交换机刷新 MAC 表，流量改道到新主设备。这张图强调切换的落点不是"改配置"而是"改 ARP 与 MAC 表"——这正是网关冗余与交换芯片知识交叉的地方。

### 5. 网桥、交换机与三层交换机：几个易混叫法

阅读资料时会遇到"网桥""二层交换机""三层交换机""路由器"四种叫法，它们的关系值得理清，否则容易在概念上打架。

**网桥（bridge）**是交换机的前身，工作在二层，根据 MAC 地址在两个网段间转发帧，早期端口很少、靠软件转发。**二层交换机**本质是多端口的硬件网桥——用 ASIC 实现转发、端口密度高、线速处理，所以现代语境下"交换机"默认指它。**三层交换机**在二层交换基础上增加了硬件路由能力，能查 FIB 表做 IP 转发——它是本资料的主角，既有二层交换的线速，又有三层路由的能力。**路由器**更强调控制面的协议灵活性与复杂路由计算，接口类型广（广域网、隧道等），数据面吞吐通常不及同代交换芯片。

前面本质章说过一句话："功能集合相同，实现重心不同"——网桥到交换机是**转发介质的硬件化**，交换机到三层交换机是**在硬件里增加了路由查表**，而路由器与三层交换机的差别主要是**控制面灵活性与数据面吞吐的取舍**。这样串起来，四种设备就不是并列关系，而是一条演进链。

一个常见的实践概念是**单臂路由（router-on-a-stick）**：只有一条物理链路连接交换机与路由器，通过 trunk 承载多个 VLAN，路由器在这条链路上做 VLAN 间路由。它是理解"trunk 承载多 VLAN"与"VLAN 间必须走三层"的综合案例——前面讲 VLAN 时提到过，这里给出了它的完整语境：在没有三层交换机或要集中做策略时，用一台路由器加一条 trunk 就能实现多 VLAN 互通。

### 6. 多机扩展：堆叠、MLAG 与虚拟化

单台交换机的端口密度和可靠性有限，规模网络里要把多台设备"变成一台"来用，主要有三条路线。

**堆叠（stacking）**：用专用堆叠线缆或高速端口把多台交换机连成一个逻辑整体，共享一个控制面——配置一次下发到所有成员，管理像一台设备。缺点是堆叠链路成为故障域，且成员通常要求同型号。

**MLAG（多链路聚合）与 vPC（虚拟端口通道）**：两台独立交换机通过 peer link 同步状态，在下游设备看来像一台逻辑设备，可以用 LACP 把链路同时连到两台机而不用跑生成树。与堆叠的关键区别是**控制面仍然独立**——两台机各自运行协议，只同步必要状态，故障隔离更好，是数据中心高可用的主流方案。前面负载均衡章讲的 LACP，在 MLAG 场景里正是这样跨两台设备使用的。

**框式交换机的分布式架构**：主控板负责控制面，线卡负责数据面，通过交换网板互联——这可以看成" chassis 内部的堆叠"，但内部总线带宽与冗余远高于外部堆叠。前面整机章提到的框式交换机属于这一类。

理解这三条路线，就能看懂选型时的一个高频问题："要 48 个万兆口，是买一台高密度设备还是两台做 MLAG？"答案取决于对故障域隔离、控制面简化与成本的综合权衡——堆叠管理简单但故障域大，MLAG 隔离好但配置复杂。

### 7. 管理 VLAN、NTP 与带内带外管理

最后补一组"网络能转发却管不好"时最常遇到的基础概念。

**管理 VLAN** 是专门用来访问设备管理接口的 VLAN。把管理流量与业务 VLAN 分开，既便于统一管控，也避免业务广播风暴影响管理通道。前面整机章讲的带外管理网口是**独立物理通道**，不依赖业务网络；而管理 VLAN 属于**带内管理**，管理流量与业务流量共享物理链路，只是逻辑隔离——两者是互补而非替代，关键设备通常两者都配。

**NTP（网络时间协议）** 负责全网设备的时间同步。它看着不起眼，却是排障的隐形基础：日志时间戳、遥测数据的时间对齐、安全审计的事件排序、证书有效期判断，全都依赖一致的时钟。全网时间不同步时，最典型的表现是"两台设备的日志对不上，无法还原故障顺序"——这类问题在排障时极易被忽略。

**SNMP（简单网络管理协议）** 是传统的设备管理机制，前面运维面章讲过它"轮询式、间隔长"的局限，这里补上它在入门配置里的位置：绝大多数设备默认开启 SNMP，用它做基础健康检查与存量资产采集，而精细遥测则走 gNMI 流式推送。两者在运维体系里各有位置，不是简单的新旧替代。

把这三个概念放在一起，是因为它们都回答同一个问题：**设备转发正常之后，怎么被稳定地管理和观测**。这也是前面运维排障章"可观测性工程要点"的落地前提。

### 8. IPv6 体系：地址、邻居发现与扩展头

前面地址体系只讲了 IPv4，但 IPv6 在现代数据中心与运营商网络里的占比持续上升，而且它给交换芯片带来的影响比"地址变长了"要深得多。这一节把 IPv6 中影响转发的关键点讲清楚，与 IPv4 形成对照。

**为什么需要 IPv6**。最直接的原因是 IPv4 地址耗尽——32 位地址约 43 亿个，早已分配完毕。IPv6 用 128 位地址，数量几乎无限。但 IPv6 不只是"地址更长"：它取消了广播（用组播代替）、取消了 IPv4 头部的校验和（交给上层）、头部字段更规整（固定 40 字节基本头），并把很多可选功能移到**扩展头**里。这些变化直接影响交换芯片的解析与查表。

**地址写法与类型**。IPv6 地址写成八组十六进制数，如 `2001:db8::1`，中间连续的零可以用双冒号 `::` 压缩（只能用一次）。三类主要地址：**单播**（类似 IPv4 的普通地址）、**组播**（以 `ff` 开头，取代 IPv4 广播的一部分功能）、**任播**（同一个地址分配给多个接口，发给最近的一个，DNS 根服务器常用）。与 IPv4 对照，IPv6 没有广播地址，也没有网络号与主机号的"子网掩码"写法，改用**前缀长度**（如 `2001:db8::/32`），这一点与前面 CIDR 章的 `/24` 记法是同一套逻辑。

**NDP 与 SLAAC**：IPv6 用邻居发现协议（NDP，Neighbor Discovery Protocol）取代 IPv4 的 ARP，做地址解析（找邻居的链路层地址）、重复地址检测与路由器发现。更重要的变化是 **SLAAC（无状态地址自动配置）**：主机可以从路由器通告的网络前缀加上自己的接口标识自动生成地址，无需 DHCP 服务器——这与 IPv4 必须靠 DHCP 或手工配置形成鲜明对比。当然 IPv6 也可以用 DHCPv6 获取地址与其他参数，两者并存。

**扩展头对交换芯片的影响**。这是本节最关键的一点。IPv6 把分片、路由、目的选项等可选功能放进基本头之后的扩展头链里，形成"基本头 → 扩展头1 → 扩展头2 → ... → 上层头"的结构。对解析器而言这意味着：**不能像 IPv4 那样读固定偏移就找到 TCP/UDP 头**，必须沿着"下一头"字段逐级跳过扩展头。扩展头层数不确定，直接消耗前面解析章讲的"解析阶段数"预算——层数多到超出上限时，芯片就无法看到四层端口，基于五元组的 ACL 与 ECMP 哈希随之失效。这是 IPv6 场景下"解析深度"比 IPv4 更紧张的根本原因，也是选型时要专门核对芯片"支持解析几层 IPv6 扩展头"的原因。

下表把 IPv4 与 IPv6 在影响转发的关键维度上并列对照。

| 维度 | IPv4 | IPv6 |
|---|---|---|
| 地址长度 | 32 位，约 43 亿个 | 128 位，几乎无限 |
| 地址配置 | DHCP 或手工 | SLAAC 自动配置或 DHCPv6 |
| 地址解析 | ARP 广播 | NDP 组播 |
| 广播 | 有广播地址 | 无广播，用组播 |
| 可选功能 | 基本头内的选项字段 | 基本头之后的扩展头链 |
| 对解析器的影响 | 固定偏移找四层头 | 须逐级跳扩展头，消耗阶段数 |
| 对表项的影响 | 表项键较短 | 表项键翻倍，FIB 容量需求更大 |

最后一点值得展开：IPv6 地址是 128 位，是 IPv4 的 4 倍，用于查表的键更长、占用的表项存储更多——同样条数的路由表，IPv6 消耗的 TCAM/SRAM 资源明显更大。前面表项资源章讲"FIB 容量按现网前缀加冗余估算"时，如果是双栈网络，就要分别核算 IPv4 与 IPv6 表项，不能只看一个数字。

下面这段伪代码把"沿扩展头找到四层头"的过程写出来，与解析章的伪代码衔接。

```text
# 工程理解伪代码：解析器跳过 IPv6 扩展头（非真实硬件接口）
cur = parse_ipv6_base_header(pkt)              # 固定 40 字节基本头
while cur.next_header in EXTENSION_HEADERS:    # 下一头是扩展头
    cur = skip_extension(pkt, cur)             # 逐级跳过，消耗解析阶段
    if parse_stages_used > MAX_STAGES:
        return UNPARSED_L4                     # 超出预算：看不到四层
l4 = parse_l4(pkt, cur.next_header)            # 终于找到 TCP/UDP
key = five_tuple(l4.src_port, l4.dst_port, ...)# 才能做 ACL 与 ECMP
```

对这段伪代码的判读：`while` 循环体现扩展头层数不固定，`skip_extension` 每跳一次就消耗一个解析阶段，`if parse_stages_used > MAX_STAGES` 直接对应前面解析章的硬约束——超出预算时返回 `UNPARSED_L4`，后续依赖四层端口的功能（ACL、ECMP、负载均衡哈希）全部失效。这段伪代码说明：**IPv6 对芯片的真正挑战不是地址变长，而是可变长的扩展头链与解析流水线深度之间的矛盾**。理解了它，就能看懂为什么具体芯片资料会单独标注"IPv6 扩展头解析能力"。

### 9. VRF 与三层多租户：与 VNI 的对照

前面隧道章讲 VXLAN 用 VNI 在二层做租户隔离，网关冗余章讲 VRRP 提供网关高可用。这一节补上三层隔离的另一半：**VRF（虚拟路由转发，Virtual Routing and Forwarding）**。

**VRF 解决什么问题**。一台路由器或三层交换机默认只有一张路由表，所有接口共享它。VRF 允许在一台设备上创建多张相互独立的路由表，每张表有自己的接口、路由与转发表。不同 VRF 之间默认不通，就像把一台设备逻辑上拆成多台。这在多租户场景里非常有用：同一个物理网络同时承载多个客户或业务，每个客户一套独立的地址空间（甚至可以使用重叠的 IP 地址段），互不干扰——因为隔离发生在三层路由表层面，而不是靠 VLAN 或 VNI。

**VRF 与 VNI 的分工**。这是最容易混淆的一组概念，可以用一句话区分：**VNI 隔离二层，VRF 隔离三层**。VXLAN 的 VNI 让不同租户的二层帧互不可见，解决"虚拟机在同一二层域里怎么隔离"；VRF 让不同租户的路由表互不可见，解决"三层路由怎么隔离"。在 EVPN VXLAN 的完整方案里，两者常常配合使用：VPN 实例把 VNI 与 VRF 绑定起来，报文进入 VXLAN 隧道前先确定租户的 VRF，转发时再按该 VRF 的路由表查表。这样二层和三层的隔离就统一在同一个租户上下文里。

下表把几种隔离手段放在同一张表里，建立完整的隔离层次感。

| 隔离手段 | 工作层次 | 隔离对象 | 典型场景 |
|---|---|---|---|
| VLAN | 二层 | 广播域 | 园区网、传统数据中心 |
| VNI（VXLAN） | 二层覆盖网 | 租户二层域 | 多租户数据中心 Overlay |
| VRF | 三层 | 路由表 | 多租户路由、重叠地址空间 |
| 物理隔离 | 一层/二层 | 整条链路 | 高安全要求场景 |

**VRF-lite 与策略路由**。实践中常听到 VRF-lite，指不使用 MPLS VPN、仅在本机划分多张路由表的简化用法——在园区网与数据中心里很常见。另一个相关概念是策略路由（PBR，Policy-Based Routing），它让转发不只看目的地址，还能按源地址、协议、端口等条件选路。VRF 与 PBR 结合，可以实现"不同业务走不同路径"的精细控制——比如管理流量走独立链路、备份流量走低成本路径。对交换芯片而言，这意味着查表不再只是"目的 IP 查 FIB"，还要先按入接口或报文属性确定 VRF，再在该 VRF 的转发表里查——多了一步"选表"，这正是前面表项资源章"查找键要包含租户上下文"的现实来源。

下面这段伪代码把"先选 VRF 再查表"的过程写出来，呼应隧道章内外层字段分工的代码。

```text
# 工程理解伪代码：按 VRF 选择路由表（非真实设备接口）
pkt = receive(pkt)                              # 收到报文
vrf_id = port.vrf if port.bound_vrf else classify_by_policy(pkt)  # 入接口绑定或策略分类
fib = vrf_tables[vrf_id]                        # 选中该租户的转发表
nexthop = fib.lookup(pkt.dst_ip)                # 在选定表里查路由
# 若与 VXLAN 配合：VNI 也映射到同一租户上下文
assert vni_to_vrf[outer.vni] == vrf_id          # 二层与三层隔离须一致
```

对这段伪代码的判读：`vrf_id` 的确定有两种方式——入接口绑定（简单确定）或按策略分类（灵活但更耗资源），`fib = vrf_tables[vrf_id]` 体现"先选表再查表"的两步过程，这也是 VRF 相比单表转发多出的开销。最后的 `assert` 行点出 VXLAN 与 VRF 配合时的核心要求：**二层 VNI 与三层 VRF 必须映射到同一租户**，否则会出现"二层通了三层不通"或更严重的租户串网。这段伪代码把隧道章的租户隔离与本章的三层隔离连成了一个整体。

### 10. 小结与交叉引用

1. **地址获取**：DHCP 用 DORA 四步下发 IP、掩码、网关与 DNS；广播 Discover 跨网段要靠 DHCP 中继，DHCP Snooping 借这个过程建立绑定表。
2. **名字解析**：DNS 把域名变成 IP，对交换机是普通转发流量；但设备自身查 DNS 失败会导致遥测等管理功能异常，易被误判为转发故障。
3. **子网与聚合**：CIDR 用前缀长度表示掩码，子网划分借主机位、路由聚合还主机位，VLSM 允许同一网络内多种前缀——这是控制路由表规模的基础。
4. **路由来源**：直连自动生成、静态手工配置、动态由 OSPF/BGP 学习，同目的冲突时按管理距离选信谁；FIB 里的内容由此而来。
5. **网关冗余**：VRRP/HSRP 用虚拟 IP 实现主备切换，切换落点是免费 ARP 刷新终端缓存与交换机 MAC 表——这是高可用与二层转发的交叉点。
6. **设备演进**：网桥到二层交换机是转发硬件化，再到三层交换机是硬件内增加路由；路由器侧重控制面灵活，三层交换机侧重数据面吞吐。
7. **多机扩展**：堆叠共享控制面、故障域大；MLAG/vPC 控制面独立、隔离更好；框式是机箱内的分布式架构。
8. **可管理性**：管理 VLAN 做带内隔离、带外网口做独立通道，NTP 保证时间一致，SNMP 与流式遥测分工——三者共同构成可观测基础。

本章与前后章节的衔接：掩码判断与网关概念见 BASIC-01；FIB 表项的来源与容量预算见表项资源章与性能指标章；LACP 在 MLAG 中的使用见数据面进阶功能章；DHCP Snooping 与 DAI 见进阶协议与可靠性章；SNMP 与 gNMI 的分工见运维与遥测面章。

## BASIC-03 数据中心网络架构：Spine-Leaf 与 Clos

前面两章讲的是"单台交换机怎么工作"，但现代数据中心的交换机从来不是孤立部署的——几十到上百台交换机按特定拓扑互联，才构成一张能承载数万服务器的网络。这一章补上这个全局视角。它解释了一个关键问题：**为什么交换芯片需要 51.2T、102.4T 这么大的容量，为什么 ECMP、深缓冲、快速故障检测如此重要**。这些参数不是为了参数本身，而是被拓扑结构"逼"出来的。理解这一章，前面十几章的技术点才有了落地的场景。

### 1. 为什么传统三层架构不够用

早期的企业网络采用**三层树形架构**：接入层连接终端，汇聚层做策略与聚合，核心层高速互联。这套架构是为"南北向流量"设计的——大部分流量从终端上行到数据中心出口，再返回，层级越往上带宽越大即可。

数据中心的东西向流量（服务器与服务器之间）打破了这一假设。分布式计算、存储副本同步、微服务调用产生大量横向流量，两台同机架甚至同机柜的服务器通信，在传统架构里可能要"爬到汇聚层甚至核心层再下来"，路径长、跳数多、带宽被上层收敛。更糟的是生成树（STP）为了防环会阻塞冗余链路，让一半的带宽闲置。传统架构在东西向流量面前显得又慢又浪费。

### 2. Spine-Leaf 架构：两层无阻塞的 Clos

**Spine-Leaf（脊叶架构）** 是当前的主流答案。它本质上是两层 Clos 网络：

- **Leaf（叶交换机）**：接入层，直接连接服务器、存储等设备，也连接边界网络设备。每台 Leaf 都上行到**所有** Spine。
- **Spine（脊交换机）**：骨干层，只连接 Leaf，不接终端。每台 Spine 连接**所有** Leaf。

关键性质有两条。第一，**任意两台 Leaf 之间都恰好经过两跳**（Leaf → Spine → Leaf），路径长度恒定，时延可预测——这对分布式计算至关重要。第二，**带宽无收敛（non-blocking）**：只要 Leaf 的上行链路总带宽不小于其下行接入带宽，任意两台 Leaf 之间就能跑满，不会像树形架构那样在汇聚层被压缩。代价是线缆数量爆炸——每台 Leaf 要连所有 Spine，Spine 端口密度要求极高，这正是高 Radix 交换芯片的市场来源。

### 3. 为什么用三层 ECMP 而不是大二层

Spine-Leaf 的一个反直觉之处是：**它通常不跑二层生成树，而是让每台 Leaf 都做三层路由**。原因是三层路由天然无环——IP 包有 TTL，路由协议本身有防环机制，所以所有物理链路都能转发，不必像二层那样用 STP 阻塞冗余链路。转发靠 ECMP（等价多路径）：到同一个目的有多条等代价路径，芯片用哈希把不同流分散到不同路径上，既用满带宽又不产生环路。

这正是前面负载均衡章讲的五元组哈希的用武之地——在 Spine-Leaf 里，ECMP 哈希不是"锦上添花"，而是整个架构能用起来的前提。前面进阶协议章也提到"较大规模 Clos 网络往往不跑 STP"，这里给出了完整上下文。

**收敛比（oversubscription ratio）** 是描述拓扑带宽的关键指标：Leaf 下行接入总带宽除以上行到 Spine 的总带宽。1:1 是完全无收敛（上行带宽等于下行），现实数据中心常用 3:1 或 4:1（上行带宽是下行的四分之一）以节省成本，但 AI 训练这类东西向流量密集的场景往往要求 1:1——否则 GPU 之间的通信会被上行链路卡住。理解收敛比，就能理解为什么 AI 集群对交换芯片容量和端口密度如此敏感。

### 4. Clos 的规模扩展与 Underlay/Overlay 分工

当单级 Spine-Leaf 的端口规模不够时，可以扩展为多级 Clos（三级甚至五级），把 Spine 也分成两级。规模扩展的代价是跳数增加、时延变大，所以现代数据中心倾向用**单级 Spine-Leaf 加高 Radix 芯片**来覆盖更大规模，而不是堆层级——这又回到了芯片的端口密度与容量。

在这个三层网络之上，还有前面隧道章讲的 Overlay（VXLAN/EVPN）：Underlay 就是这套 Spine-Leaf 三层网络，只负责 IP 可达；Overlay 在其上构建二层的租户网络，让虚拟机能跨 Leaf 迁移。两者的分工可以概括为：**Underlay 用 ECMP 保证高速无环转发，Overlay 用 VNI 提供多租户隔离**。这也是为什么理解交换芯片要同时懂"物理拓扑"和"逻辑覆盖网"。

下面这段伪代码把 Leaf 上的转发选择写成过程，连接本章与前面的 ECMP 章节。

```text
# 工程理解伪代码：Leaf 上的 ECMP 选路（非真实设备接口）
pkt = receive_from_server()                    # 从本机下挂服务器收到包
nexthops = route_table.lookup(pkt.dst_ip)      # 目的在别的 Leaf 下：多个 Spine 下一跳
if len(nexthops) > 1:
    hash_key = five_tuple(pkt)                 # 取五元组做哈希
    chosen = nexthops[hash(hash_key) % len(nexthops)]  # 选中一个 Spine
else:
    chosen = nexthops[0]
send_to_spine(chosen, pkt)                     # 发往选中的 Spine，两跳到对端 Leaf
```

对这段伪代码的判读：`nexthops` 有多个候选，正是 ECMP 的前提；`five_tuple` 哈希保证同一条流固定走同一路径（避免乱序），不同流分散到不同 Spine（用满带宽）。`% len(nexthops)` 是取模选路，真实芯片还会用弹性哈希在成员变化时减少扰动。这段伪代码说明：**Spine-Leaf 的"无阻塞"不是靠更多硬件堆出来，而是靠每跳都把流量均匀摊到所有可用链路上**——这是理解高 Radix 芯片为何必须配强哈希与 ECMP 能力的关键。

### 5. 对交换芯片提出的要求

把拓扑需求翻译成芯片指标，本章的结论就落到前面各章的参数上：

- **高 Radix 与容量**：每台 Leaf 要连所有 Spine，Spine 要有极高端口密度——这直接推动芯片做到 51.2T、102.4T。
- **强 ECMP 与哈希**：所有链路都要用起来，哈希质量决定带宽利用率；弹性哈希减少成员变化时的扰动。
- **深缓冲或快速拥塞控制**：微突发在多打一场景里必然出现，靠 PFC/ECN/DCQCN 与缓冲吸收。
- **快速故障检测与收敛**：一条 Spine 链路故障要立刻改道，靠 BFD 硬件卸载与硬件保护切换。
- **低时延与确定性**：两跳路径要快且稳定，cut-through 与可编程转发因此重要。

下表把拓扑需求与芯片能力对应起来，作为本章与全书其他章节的索引。

| 拓扑需求 | 对芯片的要求 | 对应章节 |
|---|---|---|
| 每台 Leaf 连所有 Spine | 高 Radix、大容量 | 交换容量与 SerDes 章 |
| 所有链路同时转发 | 强 ECMP 与哈希 | 数据面进阶功能章 |
| 东西向微突发 | 深缓冲与拥塞控制 | 交换架构与 QoS 章 |
| 链路故障快速改道 | BFD 卸载与保护切换 | 控制面与可靠性章 |
| 租户隔离 | VXLAN 与 VNI | 隧道封装与 EVPN 章 |

### 6. 小结与交叉引用

1. 传统三层架构为南北向流量设计，东西向流量导致路径长、带宽收敛，STP 还阻塞冗余链路。
2. Spine-Leaf 是两层 Clos：每台 Leaf 连所有 Spine，任意两台 Leaf 恒两跳，配合 ECMP 做到无收敛，代价是端口密度与线缆数量。
3. 三层路由天然无环，所以 Spine-Leaf 用 ECMP 而非 STP；收敛比（上下行带宽比）决定网络是否成为瓶颈，AI 场景常要求 1:1。
4. 规模扩展靠高 Radix 芯片而非堆层级；Underlay 负责 ECMP 转发，Overlay 负责租户隔离，两者分工明确。
5. 拓扑需求直接转化为芯片指标：高 Radix、强哈希、深缓冲、快速收敛、低时延——这是读具体芯片参数的上下文。

本章与前后章节的衔接：ECMP 与哈希的细节见数据面进阶功能章；VXLAN 与 EVPN 的 Overlay 见隧道封装与进阶协议章；微突发与缓冲见交换架构章；BFD 与保护切换见控制面章；容量与端口密度见交换容量与 SerDes 章。

## BASIC-04 交换芯片是什么：一句话本质与三大功能平面

### 1. 一句话本质

交换芯片（switch ASIC）是一种专用集成电路，它的本质是用硬件在纳秒级完成"查表—搬运—排队—改写"这一串动作：把报文从正确的入口端口搬到正确的出口端口，并在搬运过程中做到不丢、不乱、可管。

要理解它和通用 CPU、和路由器软件转发的区别，关键不在功能种类的多少——它们要做的判断其实差不多——而在执行方式。交换芯片把这些判断固化成硅片上的流水线，用片上表项存储转发表，用硬件逻辑并行查表，每个报文以线速（端口满速率）通过，不经过软件中断、不占用通用处理器周期。正是这种"功能不变、执行方式彻底硬件化"的定位，决定了它的一切设计取舍：能不能线速、查表容量多大、缓冲多深、时延多低，都是这同一件事的不同侧面。

一个常见误解是"交换芯片功能比路由器少"。实际上现代高端交换芯片支持的协议与功能已经非常丰富——二层交换、三层路由、隧道封装、组播、质量控制、遥测、安全加密一应俱全。真正的差别是：路由器更强调控制面的协议灵活性与复杂路由计算，交换芯片更强调数据面的线速吞吐与确定性时延。两者是"同一个功能集合，不同的实现重心"。

### 2. 三大功能平面

把交换芯片的全部基础功能按"是否处理每一个报文"来划分，可以归成三个平面，这是理解整份资料的组织框架：

1. **数据面（data plane）**：每一个报文经过芯片时都要执行的处理。包括报文解析、查表转发、缓冲与交换架构、转发模式选择、调度与拥塞管理、报文改写、组播复制。这是交换芯片的"主业"，也是衡量性能的核心。
2. **控制与管理面（control/management plane）**：不碰每一个包，但决定数据面怎么转发。包括转发表项的下发与老化、SDK 与驱动、寄存器访问、与网络操作系统的对接（SAI）。这是"大脑"。
3. **运维与遥测面（operations/telemetry plane）**：让网络状态可见、可控、可恢复。包括计数器统计、流量镜像、带内网络遥测与采样流、可靠性保护机制、安全与加密。这是"眼睛和免疫系统"。

### 3. 为什么按平面理解很重要

初学时容易把交换芯片的功能当成一长串互不相干的清单去背——MAC 学习、最长前缀匹配、VXLAN、PFC、ECN、MACsec……清单越背越长，却记不住彼此关系。按平面组织的好处是：任何一个具体功能，都能立刻归位到"它是处理包的、配置表的、还是看状态的"。

更重要的是，这个框架能解释两册具体芯片资料的差异。后面会看到，Tomahawk 6 的差异化能力集中在数据面（缓冲吞吐）与运维面（自适应路由、快速故障检测），而 Teralynx 10 的差异化集中在数据面（低时延可编程转发）与运维面（Flashlight 遥测）。它们都没有跳出这三个平面，只是在同一框架的不同格子里做得更深。理解了框架，再看具体芯片参数就不会迷失在数字里。

## BASIC-05 数据面：每个报文都要走的处理

### 1. 报文处理主路径

数据面是交换芯片的主业。一个报文从进入芯片到离开，走过的是一条固定的功能链路，链路上每一段各司其职。这条链路是理解所有数据面功能的骨架，也对应着具体芯片资料里"流水线"一章所描述的内容。

图中节点速览：n1 是入口端口，完成收包与 SerDes 串行/并行转换；n2 是报文解析，识别各层协议头并提取查表字段；n3 是查表转发，决定报文去往哪个出口；n4 是交换矩阵，负责缓冲与把报文从入口搬移到出口；n5 是调度与拥塞处理，含排队、报文改写与组播复制；n6 是出口端口，完成发包。整张图是单向的主路径，表达"每个报文都要依次经过这五段处理"，后面各小节逐一展开每一段。

### 2. 逐段展开：从解析到改写

**报文解析（parser）**：芯片识别以太网、VLAN、IPv4/IPv6、TCP/UDP 以及各种隧道头，提取出供查表使用的字段——目的 MAC、目的 IP、五元组、DSCP 等。解析的深度决定了后面能查哪些表、能做哪些策略，因此它是数据面能力的"入口约束"：解析不到的字段，后续就无从判断。

**查表转发（lookup）**：这是数据面的核心。二层查 MAC 地址表做桥接，三层做最长前缀匹配（LPM）路由，再叠加 ACL/TCAM 做策略过滤与优先级判定。查表命中后得到"去哪个出口、做什么动作"。查表容量与查表速率是芯片的关键指标——表项装不下就要溢出到慢速存储，速率跟不上就达不到线速。

**缓冲与交换架构（fabric + buffer）**：当多个入口同时涌向同一个出口时，报文必须暂存并接受仲裁。这里分共享内存与分布式缓冲（VOQ，虚拟输出队列）两大流派：前者所有端口共享一片缓冲池，利用率高但存在队头阻塞风险；后者按目的出口分队列，抗阻塞好但需要更大片上存储。这一层直接决定芯片的抗微突发能力与时延表现，也是不同高端芯片拉开差距的主战场。

**转发模式**：cut-through（转发模式）收到目的地址就直接转发，时延最低但会转发坏包；store-and-forward（存储转发）收完整包并校验后再转，可靠性高但时延多一个包长。现代芯片多按场景自适应或按端口配置。

**调度与拥塞管理**：队列调度决定哪个队列先发（严格优先级、加权轮转 WRR 等）；拥塞避免用 RED/WRED、ECN 在队列将满时提前标记；无损流控用 PFC（基于优先级的流控）在以太网上实现不丢包。AI 网络里的 RoCEv2 能否做到零丢包，几乎全靠这一层。

**报文改写（rewrite）**：出口处修改报文——减 TTL、重写 MAC 地址、增删或替换 VLAN 标签、VXLAN/GRE 隧道的封装与解封装、以及把报文复制一份做镜像。

**组播与复制**：一份报文要发往多个出口时，由硬件按组播树复制，避免逐端口软件拷贝带来的吞吐损失。

### 3. 三层转发表的分工示意

下面用示意性的查表伪代码，把二层、三层、ACL 三种表的分工与先后关系讲清楚。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：一次转发的查表顺序（非真实 SDK 接口）
pkt     = ingress(port)
hdr     = parse(pkt)                       # 解析各层协议头
l2      = lookup_mac(hdr.dst_mac)          # 二层：查 MAC 表
l3      = lookup_lpm(hdr.dst_ip)           # 三层：最长前缀匹配
policy  = lookup_acl(hdr.five_tuple)       # 策略：ACL/TCAM 过滤与优先级
if policy.deny:
    drop(pkt)                              # 命中拒绝策略则丢弃
egress_port = select(l2, l3, policy)       # 综合三者决定出口
enqueue(egress_port.queue, pkt)            # 入出口队列，等待调度
```

对这段伪代码的判读：三类查表不是竞争关系而是互补关系——`lookup_mac` 负责同一二层域内的桥接，`lookup_lpm` 负责跨网段的路由，`lookup_acl` 负责在转发之上叠加策略（过滤、限速、优先级）。`policy.deny` 的检查放在转发决策之前，意味着策略判定优先于转发——这是交换芯片的通用原则。最后 `enqueue` 把报文交给出口队列，从这里开始进入调度与拥塞管理的范畴。需要强调，真实芯片的查表顺序可能因架构而异，有的会把 ACL 并行查、有的会多次通过，这段伪代码只用于建立概念分工。

### 4. L2 转发流水线：从解析到桥接决策

上一节把二层、三层、ACL 三类查表放在同一张图里讲分工，本节开始逐条深入真实芯片里的转发流水线（pipeline）。先看二层，也就是桥接（bridging）。二层转发的本质只有一句话：按目的 MAC 地址，把报文从正确的端口发出去。围绕这句话，流水线要依次完成四件事——学习（learn）、查表（lookup）、泛洪判定（flood decision）与出口决策（egress decision）。

**第一步：源 MAC 学习（learning）**。报文进入端口后，芯片先取源 MAC 与入端口（通常还有 VLAN ID），写入一张 MAC 地址表（也叫 FDB，Forwarding Database）。这张表记录"某个 MAC 在哪个端口上"，是后续转发查表的依据。学习是自动完成的——交换芯片 observing 到源地址就记住，无需控制面逐条下发。表项带老化时间，长时间不见该 MAC 的流量就会被清除，以免表项被无效条目占满。

**第二步：目的 MAC 查表**。取报文的目的 MAC 查同一张表，命中结果告诉芯片这个 MAC 在哪个端口。这里的查找键通常是"VLAN + MAC"，因为不同二层域里可以有相同的 MAC 地址，必须靠 VLAN 区分。查表用哈希（hash）而非逐条比较，因此即使表项有几十万条，也能在一个时钟周期内得到结果。

**第三步：泛洪判定**。并不是每个目的 MAC 都能查到。命中（known unicast，已知单播）就直接发往对应端口；未命中（unknown unicast，未知单播）就要向同 VLAN 的所有其他端口泛洪；广播与组播同样需要复制多份。泛洪是二层转发的兜底机制——它保证"不知道往哪发"时报文仍能到达，但也意味着二层域里广播域过大就会浪费带宽，这正是 VLAN 要划分广播域的原因。

**第四步：出口决策与改写**。确定出口集合后，报文被复制到各个出口队列。出口处要做改写：剥离或添加 VLAN 标签、按出口端口的 tagging 模式处理、可能还要做 ACL 与 QoS 标记。下图把这条二层流水线画出来。

下面用示意伪代码把二层转发流水线串起来，重点是学习、查表与泛洪判定三者的先后关系。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：L2 桥接转发流水线（非真实 SDK 接口）
pkt       = ingress(port)                         # 入口收包
hdr       = parse_l2(pkt)                          # 解析二层头，取 src/dst MAC 与 VLAN
fdb.learn(hdr.src_mac, vlan, port)                 # 源 MAC 学习，刷新老化计时
hit       = fdb.lookup(vlan, hdr.dst_mac)          # 目的 MAC 查表，键为 VLAN+MAC
if hit:                                            # 已知单播：定向转发
    egress_ports = [hit.port]
elif hdr.dst_mac.is_multicast:                     # 组播：按成员端口复制
    egress_ports = multicast_members(vlan, hdr.dst_mac)
else:                                              # 未知单播：同 VLAN 泛洪
    egress_ports = all_ports_in_vlan(vlan) - [port]
for p in egress_ports:                             # 逐个出口改写并入队
    enqueue(p.queue, rewrite_l2(pkt, p))
```

对这段伪代码的判读：流程严格按"先学习、后查表、再判定"的顺序——`fdb.learn` 用源 MAC 更新表项，`fdb.lookup` 用目的 MAC 查转发方向，二者的地址字段不同，不可颠倒。`if hit` 的分支体现已知单播的定向转发；`elif` 处理组播，按成员端口复制而非盲目泛洪；`else` 兜底处理未知单播，向同 VLAN 除入端口外的所有端口泛洪。最后 `rewrite_l2` 对每个出口单独改写——因为不同端口的 VLAN tagging 模式可能不同。需要说明，真实芯片里学习与查表往往在同一查找引擎里完成，泛洪决策也会结合生成树状态（阻塞端口不转发），这段伪代码只用于建立流水线的概念顺序。

### 5. L3 路由流水线：最长前缀匹配与邻接解析

二层按 MAC 转发，三层（IP 路由）则按 IP 地址转发，流水线更复杂。核心变化是：目的地址从定长的 MAC 变成变长前缀的 IP，查表方式从精确哈希匹配变成最长前缀匹配（LPM，Longest Prefix Match）；转发决策也不止"去哪个端口"，还要决定"交给哪个下一跳"。三层流水线可以拆成五步——入口处理、路由查表、邻接解析、TTL 与校验和改写、出口转发。

**第一步：入口处理（ingress processing）**。报文进来后先做合法性检查：IP 头校验和、TTL 是否为零、是否为本机需要处理的控制协议报文。需要上送控制面的报文（如 ARP 请求、路由协议 hello）会被"punt"到 CPU，不进入硬件转发路径。

**第二步：路由查表（LPM lookup）**。取目的 IP，在路由表（FIB，Forwarding Information Base）里找最长匹配的前缀。之所以叫"最长前缀"，是因为可能有多条规则同时匹配（如 10.0.0.0/8 与 10.1.0.0/16 都匹配 10.1.2.3），要选掩码最长的那条。LPM 在硬件里通常用 TCAM 实现——TCAM 支持"掩码匹配"且所有表项并行比较，一个周期出结果，但功耗与成本高，容量也有限。这是三层表项容量通常小于二层 MAC 表容量的根本原因。

**第三步：邻接解析（adjacency / ARP-ND resolution）**。LPM 命中的结果不是直接的出口端口，而是"下一跳 IP"。要真正发包，还得知道下一跳的 MAC 地址——这靠邻接表（adjacency table）完成，它是 ARP（IPv4）或 ND（IPv6）解析结果的硬件缓存。查到下一跳 MAC 后，才能构造二层帧头。

**第四步：TTL 递减与校验和改写**。每经过一跳路由器，IP 头里的 TTL 要减一，减到零就丢弃（防止环路）；因为 TTL 变了，IP 头校验和必须重算。这两步都是每包必做的硬件改写动作，是三层转发相对二层转发的主要额外开销。

**第五步：出口转发**。按下一跳对应的端口入队，重写二层目的 MAC 为下一跳 MAC、源 MAC 为出口端口 MAC，然后发送。下图把这条三层流水线画出来。

node n2 "LPM 查表<br/>最长前缀匹配" teal
node n3 "邻接解析<br/>下一跳转 MAC" teal
node n4 "TTL递减<br/>重算校验和" amber
node n5 "二层头改写<br/>目的与源 MAC" purple

图中节点速览：n1 是入口处理，完成报文校验与是否上送控制面的判定；n2 是 LPM 查表，按目的 IP 做最长前缀匹配；n3 是邻接解析，把下一跳 IP 换成下一跳 MAC；n4 是 TTL 递减与校验和重算；n5 是二层头改写，重写目的与源 MAC；n6 是出口端口，入队并发送。整张图是三层转发的五步流水线，与二层相比多出了 LPM 查表、邻接解析、TTL 与校验和改写这几段，这正是三层转发的额外成本所在。

下面的伪代码把三层路由流水线串起来，突出 LPM、邻接与改写三者的依赖顺序。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：L3 路由转发流水线（非真实 SDK 接口）
pkt       = ingress(port)
hdr       = parse_l3(pkt)                          # 解析三层头，取目的 IP
if hdr.ttl <= 1 or not checksum_ok(hdr):           # TTL 耗尽或校验错误
    drop_or_punt(pkt)                              # 丢弃或上送控制面
    return
nexthop   = fib.lpm_lookup(hdr.dst_ip)             # 路由表最长前缀匹配
if not nexthop:                                    # 无匹配路由
    drop_or_punt(pkt)
    return
dst_mac   = adjacency.lookup(nexthop.ip)           # 邻接表查下一跳 MAC
if not dst_mac:                                    # 邻接未建立，触发 ARP/ND
    punt_arp_request(nexthop.ip)
    return
hdr.ttl -= 1                                       # TTL 递减
hdr.checksum = recompute_checksum(hdr)             # 重算 IP 头校验和
set_l2_header(pkt, dst=dst_mac, src=port_mac)      # 改写二层头
enqueue(nexthop.port.queue, pkt)
```

对这段伪代码的判读：开头对 TTL 与校验和的检查体现三层入口的合法性验证，异常报文不能进入正常转发。`fib.lpm_lookup` 是全流水线最关键的一步，它返回的是下一跳而非最终端口——这是三层与二层查表的本质差别。`adjacency.lookup` 把下一跳 IP 解析成 MAC，查不到时 `punt_arp_request` 上送控制面发起 ARP/ND，说明数据面与控制面在此处协同。只有拿到下一跳 MAC 后，才做 TTL 递减、校验和重算与二层头改写，最后入队。这段伪代码把三层转发的"查路—找邻—改写"三段依赖讲清楚，真实芯片还会在其中插入 ECMP（等价多路径）选路、VRF（虚拟路由转发）隔离等步骤，具体实现需以数据手册为准。

### 6. L2 与 L3 的协同：一次转发里谁先谁后

前面两节分别讲了二层与三层流水线，但一个真实报文往往同时涉及两者。理解它们如何协同，是读懂芯片转发行为的关键。这里要给一个常被混淆的结论：二层和三层不是二选一，而是一次转发中可能先后发生的两个阶段。

典型场景是"VLAN 间路由"（inter-VLAN routing）：主机 A 在 VLAN 10，主机 B 在 VLAN 20，A 要访问 B。报文从 A 发出时，目的 MAC 是网关（路由接口）的 MAC，源 MAC 是 A 的 MAC。芯片收到后，先按二层规则查表——发现目的 MAC 是本机网关 MAC，于是判定这不是纯二层桥接，而要进入三层路由。随后按目的 IP 做 LPM，查到下一跳，改写二层头后从 VLAN 20 的端口发出。所以一次报文经历了"二层查表判断 → 三层路由转发"的串联，而非只在某一层转发。

这也解释了一个常见疑问：为什么交换机要配 IP 地址（SVI，交换虚拟接口）？因为 SVI 的 MAC 就是网关 MAC，它的存在让芯片知道"哪些报文要交给三层处理"。没有它，同 VLAN 内可以直接二层桥接，跨 VLAN 就必须靠外部路由器。

那么表项资源怎么分配？二层查 MAC 表、三层查路由表与邻接表，它们是不同的硬件表，各有容量上限。设计时若三层表项不足，路由就要"溢出"到软件或更小容量的表，性能随之下降——这正是选型时要分别核对 MAC 表容量与 FIB 容量的原因。下表把二层与三层流水线的关键差异并列对照。

| 对比维度 | L2 桥接流水线 | L3 路由流水线 |
|---|---|---|
| 查表依据 | 目的 MAC（精确匹配） | 目的 IP（最长前缀匹配） |
| 核心表项 | MAC/FDB 表 | FIB 路由表 + 邻接表 |
| 硬件实现 | 哈希查找，容量大、成本低 | TCAM 并行匹配，容量小、成本高 |
| 报文改写 | VLAN 标签、二层头 | TTL、校验和、二层头 |
| 典型耗时 | 更短，路径固定 | 更长，多段查表与改写 |
| 是否改 TTL | 不改，非 IP 层处理 | 递减，每跳必做 |

需要强调，上表的"耗时"与"容量"是架构层面的一般规律，具体数值因芯片而异；高端芯片通过把 L2/L3 查表放在同一查找引擎的不同阶段来压缩时延，实现"看起来像一次查表"的效果。下图把二三层协同的判定关系画出来，作为本节的收束。

:::figure id=BASIC-05-04 | name=L2 与 L3 转发协同判定 | dir=TB
node n1 "入口报文<br/>解析二层头" blue
node n2 "目的MAC<br/>是否本机网关" teal
node n3 "是：进入三层<br/>LPM与邻接" amber
node n4 "否：纯二层<br/>查MAC表桥接" green
node n5 "出口改写<br/>入队发送" purple

edge n2 -> n3 "是"

:::

图中节点速览：n1 是入口报文，解析二层头取出目的 MAC；n2 是判定节点，检查目的 MAC 是否为本机网关 MAC；n3 是"是"分支，进入三层做 LPM 与邻接解析；n4 是"否"分支，按纯二层查 MAC 表桥接；n5 是出口改写与入队发送，两条分支在此汇合。整张图说明二层与三层是串联协同关系——先用二层判断报文是否要交给三层，再决定走哪条路径，最终都在出口改写后发出。

## BASIC-06 报文解析与可编程数据面：能力边界从哪来

前面讲数据面时反复出现一个前提："解析出的字段决定后面能查什么表"。但解析本身到底怎么做、为什么有的芯片认得新协议而有的认不得、厂商宣传的"可编程转发"究竟改变了什么，这些还没展开。这一章专门回答这三个问题。理解它，就能看懂两册具体芯片资料里"可编程数据面""Flex-forwarding""Cognitive Routing"这类差异化名词的真实含义，也能明白为什么面对新协议时，有些芯片靠升级软件就能支持，有些却必须换硬件。

### 1. 报文解析：从比特流到查找键

解析器（parser）是数据面的第一道真正处理。它面对的不是"一个 IP 包"，而是一串从以太网帧开始的、可能层层嵌套的字节。它的工作可以概括为两件事：**沿着协议栈逐层识别头部**，并**把后续查表需要的字段抽取成查找键（key）**。

识别靠的是"协议类型链"：读到以太网头的 `ether_type` 字段，若为 0x0800 就知道后面是 IPv4，若为 0x86DD 则是 IPv6，若为 0x8100 则先有一层 VLAN 标签再往后读；进入 IP 头后看 `protocol` 字段判断是 TCP、UDP 还是 ICMP；若是 UDP 且目的端口为 4789，则再往后是 VXLAN 头，里面藏着内层以太网帧。解析器就是这样一层层"剥洋葱"，每剥一层就确认一种协议，直到遇到不认识的协议或达到解析深度上限才停下。

抽取则是把识别过程中看到的关键字段存进一张临时表——目的 MAC、源 MAC、VLAN ID、目的 IP、源 IP、四层端口、DSCP、VNI 等。这些字段随后被拼接成不同查找键：查 MAC 表只需要 VLAN 加目的 MAC，查路由表要目的 IP，查 ACL 可能要完整的五元组。所以解析器不是"看懂报文"就够了，它必须**恰好抽出后面所有查表动作需要的字段**，少抽一个字段，对应的策略就永远无法执行。

下面这张图把一个带 VLAN 和 VXLAN 封装的报文解析过程画成一棵判定树，每个分叉都是一次协议类型判断，每个叶子都是一次字段提取。

node n2 "VLAN 标签<br/>提取 VLAN ID" teal

:::

图中节点速览：n1 读取以太网头的类型字段决定后续协议；n2 识别 VLAN 标签并提取 VLAN ID；n3 进入 IPv4 头并读取上层协议号；n4 判断是 UDP 且端口为 VXLAN 的 4789；n5 解析 VXLAN 头并提取 VNI；n6 继续解析被封装的内层以太网帧得到内层 MAC；n7 汇总所有提取字段形成查找键集合。图中主干是"外层封装逐层剥开"的路径，同时 n3 有一条旁路直接把 IP 与五元组送入查找键，说明解析过程中每一步都可以抽取字段，不必等到最内层。

### 2. 解析的硬约束：为什么不能"什么都认得"

既然解析是逐层判断，理论上似乎可以无限嵌套、认识所有协议。现实里做不到，因为解析是**线速硬件逻辑**，有三个硬约束。

**第一是解析阶段数有限**。每剥一层头就要消耗一个处理阶段，芯片的解析流水线深度是固定的（常见十几级）。一个套了 VLAN、VXLAN、IPv6、TCP 的报文已经吃掉大半预算，再叠几层隧道就超出上限，解析器只能停止，后面的字段就"看不见"了。

**第二是查找键长度有限**。抽取的字段要拼接成固定宽度的键送进查找引擎，这个宽度是硬件设计时定死的（常见几百比特）。字段越多、越长，键越宽，成本和功耗都上升。所以芯片文档里"支持解析 N 层隧道""键宽 X 比特"这类参数不是可有可无的注脚，而是直接决定能实现哪些功能。

**第三是新协议需要"认识它"**。解析逻辑靠类型字段导航，如果一种新封装用了芯片不认识的类型值，它就会在这一层停止解析——不是算不过来，而是根本不知道后面还有内容。这正是固定功能芯片面对新协议时的根本困境：硬件里的解析规则在流片时就确定了，无法通过学习获得。

下表把三种约束与它们的直接后果并列，选型时可以用它把"协议支持列表"这类宣传口径翻译成真实能力。

| 约束维度 | 硬件层面的限制 | 对使用者的直接后果 |
|---|---|---|
| 解析阶段数 | 流水线深度固定，常见十几级 | 隧道嵌套层数有上限，超出部分无法解析 |
| 查找键宽度 | 键长在流片时确定，常见数百比特 | 字段过多的复合策略可能无法一次查表完成 |
| 协议识别表 | 类型值与解析动作的映射固化 | 新封装类型若不识别，解析在该层终止 |
| 抽取字段集 | 能抽取的字段位置预先定义 | 未预设的字段无法用于查表或策略 |

需要说明：上表的具体数值因芯片代际和定位差异很大，应当以目标芯片的数据手册为准；这里只给出"存在约束且约束会传导到功能"这一判断框架。下面这段伪代码用一个解析器的处理循环，把"逐层识别—抽取—遇未知即停止"的逻辑固定下来，便于对照真实芯片的解析表配置项。

```text
# 工程理解伪代码：解析器的逐层识别与字段抽取（非真实硬件接口）
hdr_stack = [read_ethernet_header(pkt)]        # 从二层头开始
keys = {}                                       # 查找键的字段集合
for depth in range(MAX_PARSE_STAGES):           # 阶段数上限是硬约束
    cur = hdr_stack[-1]
    if cur.type not in PARSE_TABLE:             # 不认识的类型：停止解析
        break
    keys.update(extract_fields(cur))            # 抽取该层预设字段
    nxt = PARSE_TABLE[cur.type]                 # 按类型表决定下一层协议
    if nxt is None:
        break
    hdr_stack.append(parse_next(pkt, cur, nxt))
# 得到 keys 后，后续查表只能使用 keys 里已有的字段
mac_key  = keys['vlan'] + keys['dst_mac']       # 二层查表键
ip_key   = keys['dst_ip']                       # 三层查表键
acl_key  = keys['five_tuple']                   # 策略查表键
```

对这段伪代码的判读：循环上界 `MAX_PARSE_STAGES` 直接体现"阶段数有限"，`PARSE_TABLE` 体现"协议识别表"，`extract_fields` 只抽取预设字段体现"字段集固定"。三个 `break` 分支说明解析可以在任何一层提前终止——这解释了为什么未知协议或过深嵌套会导致后续字段不可用。最后三行强调：**所有查表键都只能从 `keys` 里取**，如果某个字段没被抽取，后面任何依赖它的表项都无法命中。这是理解"解析是能力入口约束"的最直接方式。

### 3. 从固定功能到可编程数据面

理解了解析的三大约束，就能理解"可编程数据面"要解决什么。它的发展大致分三档。

**第一档是固定功能 ASIC**。解析规则、查表动作、报文字段全部在流片时固化。优点是吞吐最高、功耗最低、时延最确定；缺点是面对新协议或新隧道类型无能为力，只能等下一代芯片。早期交换芯片基本都是这一档。

**第二档是可配置解析**。解析阶段数和键宽仍然固定，但"类型值到解析动作的映射"做成了可写的表。出现新封装时，只要它的类型值能被映射、需要的字段在预设集合里，就可以通过更新解析表支持，不必换芯片。这是很多现代芯片已经具备的能力，也常被宣传为"支持新协议可编程"——需要注意它可编程的只是解析映射，不是整个转发逻辑。

**第三档是真正的可编程流水线**。以 P4（Programming Protocol-independent Packet Processors，协议无关报文处理语言）为代表，它把数据面抽象成"可配置的解析器加匹配—动作表（match-action table）阵列"。开发者用类 C 的语言描述"解析哪些头、抽哪些字段、按什么表匹配、匹配后执行什么动作"，再由编译器映射到芯片的硬件资源上。NVIDIA 在 Spectrum 系列上推的 NPL（Network Programming Language，网络编程语言）也属于这一思路。它的价值在于：新协议、新隧道、自定义拥塞控制都可以通过更新程序实现，而不必等待芯片换代。

代价同样明确：可编程意味着要用一部分硬件资源去实现"可配置性"，在同等工艺下，纯可编程方案的吞吐、功耗和时延通常不如为特定功能深度优化的固定逻辑。因此高端芯片往往走混合路线——把最常用、最吃性能的路径（L2/L3 转发、标准隧道封装）做成硬化的固定流水线，把创新空间留给可配置的解析与匹配—动作段。这正是"硬化转发 + 可编程增强"成为主流架构的原因。

下图把三档方案在"灵活性—性能"轴上并置，帮助理解为什么没有一种方案能通吃所有场景。

### 4. 与两册具体芯片的呼应

有了这一章的框架，回头看两册芯片资料的差异化名词就很清楚。

Teralynx 10 强调的"可编程转发"与 Flex-forwarding，落点主要在**第二档到第三档之间**：解析与转发动作具备可配置性，使同一颗芯片能适配不同的转发语义和定制需求，而不是只能按出厂固化的一种方式转发。Tomahawk 6 的 Cognitive Routing 2.0 则更多落在**运维面与转发策略的可编程结合**上——它根据网络状态动态调整转发行为，前提是解析与匹配—动作环节允许按自定义规则选取路径。

需要强调，厂商宣传口径里的"可编程"可能指上述任一档，差异很大。核对时应当追问三个具体问题：解析器有几级、键宽多少、哪些字段可抽取（对应本章第 2 节的约束）；新协议是通过更新映射表支持，还是需要重写匹配—动作程序（对应第 3 节的分档）；硬化主路径与可编程段各覆盖哪些功能（对应"混合架构"的现实）。三个问题问清楚，就能把营销语言还原成可比较的工程能力。

### 5. 小结与交叉引用

1. 解析器逐层识别协议头并抽取查找键，是数据面能力的"入口约束"：**没解析出的字段，后续任何查表与策略都用不上**。
2. 解析受三个硬约束：阶段数有限、键宽固定、协议识别表固化；隧道嵌套过深或遇到未知协议会在中途停止。
3. 可编程分三档：固定功能、可配置解析、可编程匹配—动作流水线；灵活性与吞吐/功耗/时延存在权衡，高端芯片走混合路线。
4. 选型核对"可编程"时要追问解析约束、新协议支持方式、硬化与可编程的功能分工，把宣传语还原为工程能力。

本章与前后章节的衔接：解析在数据面主路径中的位置见 BASIC-05 第 1、2 节；解析深度对 VXLAN 这类隧道的实际影响见 BASIC-07（数据面进阶功能）与 BASIC-08（隧道封装全景）；表项与查找键如何落到具体硬件资源，见 BASIC-11 表项资源与查找引擎。

## BASIC-07 数据面进阶功能：负载均衡、组播广播与 VXLAN

前面两章讲的是"普通单播"怎么在二层和三层转发。现实网络里还有四类高频出现的转发形态：把流量摊到多条路径的负载均衡、一对多的广播与组播、以及把二层网络架到三层之上的 VXLAN 叠加。它们都跑在数据面，复用前面学到的解析、查表、改写流水线，只是查的表和改写的字段不同。本章逐一讲清楚。

### 1. 负载均衡：ECMP 与链路聚合

负载均衡（load balancing）解决的是"有多条路可走时，怎么把流量摊开"。网络里有两处最典型：

- **链路聚合（LAG，Link Aggregation）**：在二层把多条物理链路绑成一条逻辑链路，标准协议是 LACP（802.3ad）。对上层看是一条更粗的链路，带宽叠加且一条成员链路故障时其余顶上。
- **等价多路径（ECMP，Equal-Cost Multi-Path）**：在三层，当路由表对同一目的有多条开销相同的下一跳时，把流量分摊到这些路径。

两者实现机制几乎一样：用**哈希（hash）**选路。芯片把报文的五元组（源 IP、目的 IP、源端口、目的端口、协议）送进哈希函数，得到一个数，再对路径数取模，选中其中一条。用五元组而非随机，是为了让"同一条连接的所有包走同一条路径"——否则同一 TCP 流的包乱序到达，接收端要重排，性能反而下降。

这里有个经典难题：**大象流（elephant flow）**。少数大流占据带宽大头，哈希一旦把它们钉在同一条路径，就会出现"有的链路挤爆、有的空闲"。业界的应对是动态负载均衡（DLB）和 flowlet 切换——检测流中的空闲间隙（flowlet），在间隙处把后续流量换到轻载路径，既避开热点又不造成乱序。还有一致性哈希（resilient hashing），让成员数变化时只有少量流需要重新映射，减少扰动。

需要分清"网络级负载均衡"和"服务器级负载均衡"。ECMP/LAG 是无状态的：芯片不记连接，每个包独立哈希。而真正的服务器负载均衡（SLB）要有会话表，记住"这个连接发给哪台服务器"，还要做健康检查、NAT 改写——这通常由负载均衡器、智能网卡或专门设备承担，不在普通交换芯片的能力范围。下表把两种聚合方式对照。

| 对比维度 | 链路聚合 LAG | 等价多路径 ECMP |
|---|---|---|
| 工作层次 | 二层 | 三层 |
| 绑定对象 | 多条物理链路 | 多条等价路由下一跳 |
| 典型协议 | LACP（802.3ad） | OSPF/ISIS/BGP 等价路由 |
| 选路依据 | 五元组哈希 | 五元组哈希 |
| 故障收敛 | 成员口 down 后重分布 | 下一跳失效后重算 |
| 状态性 | 无状态，逐包哈希 | 无状态，逐包哈希 |

下面的伪代码把哈希选路讲清楚，重点是"同一条流固定走一条路径"。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：ECMP/LAG 哈希选路（非真实 SDK 接口）
pkt      = ingress(port)
key      = five_tuple(pkt)                       # 取五元组作为哈希键
h        = hash(key)                             # 芯片哈希引擎算出哈希值
if layer == "L2":
    members = lag.member_ports(group_id)         # LAG：取成员链路
else:
    members = route.ecmp_nexthops(prefix)        # ECMP：取等价下一跳
idx      = h % len(members)                      # 哈希取模选一条
forward(pkt, members[idx])                       # 同一条流固定选中同一条
```

对这段伪代码的判读：`five_tuple` 取出的键保证同一条连接的包哈希值相同，`h % len(members)` 因此把它们送到同一成员口，避免乱序——这是哈希选路必须用流字段而非随机数的原因。`if layer` 分支说明 LAG 与 ECMP 只是取的成员集合不同（成员口 vs 下一跳），选路算法一致。需要指出，成员数变化（链路故障或新增）会让取模结果改变，部分流因此换路，这正是 resilient hashing 要缓解的扰动；这段伪代码只用于建立无状态哈希分发的概念。

### 2. 广播与组播：一对多的两种形态

一对多转发有两种：广播和组播。它们的差别在"发给谁"。

**广播（broadcast）**发给二层域里的所有人。目的 MAC 是全 F（`FF:FF:FF:FF:FF:FF`），芯片收到后向同 VLAN 的所有其他端口泛洪。ARP 请求、DHCP 发现都靠广播——因为此时还不知道对方在哪。广播的代价是"每个人都要处理"，且广播域（通常等于 VLAN）越大，浪费越多；环路里的广播会无限复制形成广播风暴，所以要靠生成树和风暴控制来约束。

**组播（multicast）**只发给"加入了这个组"的人。目的 IP 是 D 类地址（224.0.0.0/4），映射到组播 MAC（`01:00:5e` 开头）。主机通过 IGMP（IPv4）或 MLD（IPv6）告诉网络自己想加入哪个组。

组播在二层和三层的处理不同：

- **二层组播：IGMP Snooping**。交换机监听主机与路由器之间的 IGMP 报文，建立"组地址 → 成员端口"表。这样组播帧只发给真正加入组的端口，而不是在 VLAN 里泛洪。没有 Snooping 时，组播会被当成广播处理——这是很多网络组播性能差的根源。
- **三层组播：PIM**。路由器之间跑 PIM 协议建立组播分发树，维护 (S,G) 或 (*,G) 组播路由表，并用 RPF（反向路径转发）检查防止环路。

对交换芯片而言，组播的关键能力是**硬件复制**：一份报文进入芯片后，由复制引擎在出口复制成多份，而不是靠软件逐端口拷贝。复制能力（最大副本数、复制带宽）是芯片的一项指标，AI 集群的集合通信也在重新重视组播。下表把单播、广播、组播三者并列对照。

| 维度 | 单播 | 广播 | 组播 |
|---|---|---|---|
| 目的 | 一个接收者 | 二层域内全部 | 加入组的成员 |
| 目的地址 | 单播 MAC/IP | 全 F MAC | D 类 IP / 01:00:5e MAC |
| 芯片动作 | 查表定向转发 | 泛洪到所有端口 | 按成员表复制 |
| 典型应用 | 常规通信 | ARP、DHCP | IPTV、集合通信 |
| 成员管理 | 无需 | 无需 | IGMP/MLD、PIM |

edge n2 -> n6 "需抑制"
edge n3 -> n5 "按成员表"
:::

图中节点速览：n1 是按目的地址判定的二层报文入口；n2 是广播分支（目的为全 F，发给所有人），n3 是组播分支（目的为 01:00:5e，发给组成员）；n4 是广播的泛洪动作，向 VLAN 内所有端口发送；n5 是组播的 IGMP Snooping 动作，只发给成员端口；n6 是广播的风暴控制，抑制过度泛洪。整张图说明广播是无差别泛洪、需要抑制，组播是按成员表精确复制，二者的一对多效率差别很大。

### 3. VXLAN：把二层架到三层之上

VXLAN 解决三个问题：VLAN 只有 4096 个标识不够多租户用；虚拟机迁移时二层域要能跨三层物理网络延伸；租户之间要隔离。它的做法是**MAC-in-UDP 封装**：把原始二层帧整个塞进一个 UDP 报文里，在物理网络（underlay）上传输，逻辑上形成一张叠加网（overlay）。

几个关键概念：

- **VTEP（VXLAN Tunnel Endpoint）**：封装和解封装的端点，通常在网络设备或服务器虚拟交换机上。源 VTEP 把二层帧封装，目的 VTEP 解封装还原。
- **VNI（VXLAN Network Identifier）**：24 位标识，能表示约 1600 万个逻辑网络，彻底解决 VLAN 数量不够的问题。封装时 VNI 写在 UDP 载荷里的 VXLAN 头中。
- **外层 UDP 端口 4789**：这是 VXLAN 的知名端口，underlay 网络按外层 IP 头做普通三层路由即可，无需感知内层二层帧。
- **BUM 流量**：Broadcast、Unknown unicast、Multicast 三类流量的统称。VXLAN 里这些流量要靠头端复制（ingress replication，源 VTEP 复制多份分别封装）或 underlay 组播来送达——这是 VXLAN 设计里的一个重点和难点。

跨 VNI 通信要靠**分布式网关**（IRB，Integrated Routing and Bridging）：网关功能下沉到每台 VTEP，报文在本机完成"从 VNI A 路由到 VNI B"，避免绕行集中网关。

对交换芯片来说，**VXLAN 封装解封装必须硬件线速完成**，否则叠加网络会成为性能瓶颈。芯片要能在一次查表里同时用 VNI 和内层 MAC 做转发决策（single-pass VXLAN），这是高端芯片的卖点——前面两册具体芯片资料里提到的"单次 VXLAN"能力，本质就是这一节讲的硬件卸载。下表把 VLAN 与 VXLAN 对照。

| 对比维度 | VLAN | VXLAN |
|---|---|---|
| 标识位数 | 12 位（4096 个） | 24 位（约 1600 万） |
| 封装 | 802.1Q 标签 | MAC-in-UDP |
| 承载网络 | 二层 | 三层 underlay |
| 端点 | 无封装端点 | VTEP |
| 跨三层迁移 | 不支持 | 支持 |
| 硬件开销 | 加标签，很低 | 封装解封装，需卸载 |

下面的伪代码把 VXLAN 的封装与解封装讲清楚。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：VXLAN 封装与解封装（非真实 SDK 接口）
# 发送方向：源 VTEP 封装
frame    = l2_frame(src_mac, dst_mac, vlan)       # 原始二层帧
vni      = lookup_vni(vlan, dst_mac)              # 查表得到目的 VNI 与远端 VTEP
outer    = vxlan_encap(frame, vni=vni,            # 加 VXLAN 头（含 VNI）
                       udp_dst=4789,              # 外层 UDP 目的端口
                       src_ip=local_vtep, dst_ip=remote_vtep)
forward_underlay(outer)                           # 按外层 IP 在 underlay 路由
# 接收方向：目的 VTEP 解封装
inner    = vxlan_decap(outer)                     # 去掉外层头，还原二层帧
lookup_and_forward(inner.vni, inner.dst_mac)      # 按 VNI + 内层 MAC 转发
```

对这段伪代码的判读：发送方向先用 `lookup_vni` 由内层 VLAN 与目的 MAC 查到目标 VNI 和远端 VTEP 地址，再由 `vxlan_encap` 加上 VXLAN 头（写入 VNI）、外层 UDP 头（目的端口 4789）和外层 IP 头；`forward_underlay` 让封装后的报文按外层 IP 做普通三层转发，underlay 网络因此无需理解内层二层。接收方向 `vxlan_decap` 还原出原始帧，再按 `VNI + 内层 MAC` 转发——这正是一次查表同时用两个键的 single-pass 能力。需要说明，BUM 流量的处理不在单播路径里：广播或未知单播需要源 VTEP 把帧封装多份发给所有相关 VTEP，这段伪代码只覆盖单播 VXLAN 的关键路径。

- **广播**不需要查表，按 VLAN 泛洪；**组播**查"组地址到成员端口"表，用硬件复制到多个出口。

## BASIC-08 隧道封装全景：从 VXLAN 到通用 Overlay

上一章的进阶功能里已经用一节讲过 VXLAN：它用 MAC-in-UDP 把二层帧架到三层网络之上，靠 VTEP 与 VNI 隔离租户。但 VXLAN 只是众多隧道技术中的一种。在真实的数据中心与运营商网络里，还会遇到 Geneve、NVGRE、GRE、IPIP、MPLS、GTP 等封装；它们解决的问题相近，封装层次与硬件代价却差别很大。这一章把它们放到一张全景里对照，并重点讲清两件事：**封装发生在哪里**，以及**内外层字段各由谁来决定转发**。理解这两点，就能判断一种新隧道在当前芯片上是"软件能补"还是"必须硬件支持"。

### 1. 为什么需要隧道：Overlay 与 Underlay 解耦

隧道的本质是**把一种报文装进另一种报文里传送**。外层报文负责在承载网（underlay）里被转发，内层报文是真正要送达的原始数据。这样做有两个根本价值。

**第一是解耦地址域**。数据中心的虚拟机或容器需要二层连通，但承载网只跑三层路由。把二层帧封装进 UDP 后，underlay 只需要按外层 IP 路由到目标主机，完全不需要知道内层 MAC 在哪——二层域被"拉伸"到了三层之上。租户地址因此可以重复使用而不冲突，因为隔离靠的是隧道标识（如 VNI）而非全局唯一的地址。

**第二是解耦拓扑**。业务网络的逻辑拓扑不必与物理网络一致。两个逻辑上相邻的租户端点，物理上可能隔着多层 Clos 架构，隧道把它们"拉直"，而 underlay 只需提供普通的 IP 可达性。这使网络规划从"为每种业务铺一张网"变成"一张承载网 + 若干逻辑覆盖网"。

代价也很直接：**封装增加字节开销，解封装需要解析能力**。每多一层封装，报文变大、MTU 更容易触发分片，解析器也要多剥一层头。这正是上一章"解析阶段数有限"与"键宽固定"两个约束在实际中的体现——隧道能力与解析能力是绑定的。

### 2. 常见隧道类型全景对照

各种隧道的差别主要体现在三点：装在什么协议里、用什么字段做隔离标识、以及是否被广泛硬件卸载。下表把常见类型并列，便于按场景选用与核对芯片支持。

| 隧道类型 | 封装形式 | 隔离标识 | 典型场景 | 硬件卸载情况 |
|---|---|---|---|---|
| VXLAN | 二层帧装进 UDP，目的端口 4789 | VNI，24 比特 | 数据中心多租户 overlay，事实标准 | 广泛硬化支持，多数高端芯片单次处理 |
| Geneve | 通用 UDP 封装，端口 6081，可变长选项头 | VNI 加选项 TLV | 需要扩展元数据的高级 overlay（如 NSX） | 支持度增长中，需核对可变长选项解析 |
| NVGRE | 二层帧装进 GRE | VSID，24 比特 | 早期微软虚拟化方案 | 支持较少，逐步被 VXLAN/Geneve 取代 |
| GRE | 通用路由封装，可承载多种三层协议 | 无固定隔离字段 | 站点互联、承载非原生协议 | 常见，但开销与解析深度需评估 |
| IPIP | IP 包直接装进另一个 IP 包 | 无标准隔离字段 | 简单隧道、IPv6 过渡 | 实现简单，硬件支持普遍 |
| MPLS | 在二三层之间插入标签栈 | 标签，20 比特 | 运营商 VPN、流量工程 | 运营商级芯片支持，园区芯片较少 |
| GTP | GTP-U 承载用户面，装进 UDP | TEID 隧道端点标识 | 移动通信核心网用户面 | 专用场景，需核对芯片是否支持 |

读这张表要抓住一条主线：**VXLAN 之所以成为事实标准，是因为它在"够用的隔离能力"与"硬件好实现"之间取得了平衡**——固定 8 字节头、固定 UDP 端口、24 比特 VNI，解析器剥起来简单，键宽也好规划。Geneve 提供了更强的扩展能力（可变长选项头携带自定义元数据），但"可变长"恰恰是硬件解析的麻烦所在：长度不固定意味着解析阶段数无法预先确定，因此支持 Geneve 的芯片必须核对它对选项头的解析上限。NVGRE 与 GRE 的式微则说明，一种隧道能否普及，技术先进性不是唯一因素，**硬件卸载的成熟度往往更关键**。

需要说明的是，上表的"硬件卸载情况"是产业界的一般规律，具体到某一型号必须以数据手册的协议支持列表为准；尤其 Geneve 这类带可变选项的封装，"支持 Geneve"可能只意味着支持最简头部，不代表能解析全部选项。

### 3. 封装与解封装发生在哪里

隧道处理在数据面里的位置，可以用"进入 overlay 时封装、离开 overlay 时解封装"来概括，但落到交换芯片上，不同位置的实现难度差别很大。

**入口封装（encap）**：报文从租户侧进入芯片时，要判断它属于哪个 VNI、对应的远端 VTEP 是谁，然后插入隧道头与外层 IP/UDP 头。这需要查一张"内层地址到 VNI 与外层下一跳"的映射表，属于数据面查表动作的一种。

**出口解封装（decap）**：报文从承载网侧进入芯片时，要剥掉外层头、取出 VNI 与内层帧，再按内层目的 MAC 或 IP 做正常转发。解析器必须能识别外层类型并正确剥层，这直接受上一章解析深度的约束。

**分布式网关场景**：当网关功能下沉到每台接入交换机（IRB，集成路由与桥接），同一颗芯片可能同时承担"先解封装再路由"或"先路由再封装"。这类场景最考验实现效率：如果必须把报文送回芯片重新走一遍流水线（multi-pass，多遍处理），时延与吞吐都会明显恶化；若能在一次-through 中完成解封装、路由、再封装（single-pass，单遍处理），性能就好得多。两册芯片资料里 Tomahawk 6 与 Teralynx 10 都强调"单次 VXLAN"，指的就是这种单遍处理能力——它是隧道性能的关键分水岭。

下图把帧在芯片内的封装路径画成"入向解封装—查表—出向封装"的链路，并标出分布式网关场景中两次隧道动作的位置。

:::figure id=BASIC-08-01 | name=隧道封装解封装在芯片内的位置 | dir=LR

node n2 "解析外层头<br/>提取 VNI 与内层帧" teal

### 4. 内外层字段的分工：谁决定转发

隧道场景里最容易混淆的是"到底按哪层字段转发"。答案取决于看的是哪一段路径。

**在 underlay 里，外层字段决定转发**。承载网设备只关心外层目的 IP、ECMP 哈希用的外层五元组、以及 QoS 标记（通常从内层复制到外层）。内层 MAC、内层 IP、VNI 对 underlay 完全不可见——这正是 VXLAN 实现地址域解耦的原理。underlay 的转发行为因此与租户无关，一张承载网服务所有租户。

**在 overlay 里，内层字段与隧道标识共同决定转发**。VTEP 解封装后，按 VNI 确定租户上下文，再按内层目的 MAC 做二层桥接或按内层目的 IP 做三层路由。同一个内层 IP 在不同 VNI 里指向不同租户，所以 VNI 是转发查找键的一部分——查表键必须同时包含 VNI 与内层地址，否则租户会串网。

**策略与遥测可能同时看内外两层**。ACL 可能按内层五元组做过滤，也可能按外层 IP 做 underlay 限速；遥测按外层路径统计承载网质量，按内层流统计租户业务。这要求解析器把内外层字段都抽取到查找键集合里，再次呼应上一章"键宽与抽取字段集"的约束。

下面这段伪代码把"外层查 underlay、内层加 VNI 查 overlay"的分工固定成过程，便于对照真实配置。

```text
# 工程理解伪代码：隧道场景的内外层查表分工（非真实硬件接口）
outer = parse_outer_headers(pkt)               # 解析外层头
inner = parse_inner_headers(pkt)               # 解析内层头，受解析深度约束
# underlay 段：只看外层
underlay_nh = fib.lookup(outer.dst_ip)         # 外层目的 IP 路由
hash_key = outer.five_tuple                    # ECMP 用外层五元组
qos_mark = copy_or_remark(inner.dscp, outer)   # QoS 从内层复制或重标记
# overlay 段：VNI 加内层地址
tenant_ctx = vni_table.lookup(outer.vni)       # VNI 决定租户上下文
if tenant_ctx.l2_mode:
    egress = fdb.lookup(tenant_ctx.vni, inner.dst_mac)   # VNI + 内层 MAC
else:
    egress = fib.lookup(tenant_ctx.vni, inner.dst_ip)    # VNI + 内层 IP
```

对这段伪代码的判读：`fib.lookup(outer.dst_ip)` 与 `hash_key = outer.five_tuple` 说明 underlay 转发完全基于外层字段，与租户无关；`vni_table.lookup` 先确定租户上下文，随后两次 overlay 查表都把 `tenant_ctx.vni` 作为键的一部分，说明 VNI 隔离不是附加检查而是查找键的组成部分。`copy_or_remark` 体现内外层 QoS 的传递关系。整段代码的前提是 `parse_inner_headers` 成功——如果解析深度不够，内层字段根本不存在，overlay 查表就无从谈起，这正是把隧道能力归到解析能力的原因。

### 5. 小结与交叉引用

1. 隧道用外层报文承载内层报文，实现地址域解耦与拓扑解耦；代价是封装开销与解析深度消耗。
2. 常见隧道在封装形式、隔离标识与硬件卸载上差异很大；VXLAN 因固定头与固定端口成为事实标准，Geneve 的扩展能力以解析复杂度为代价。
3. 封装发生在入口、解封装发生在出口；分布式网关若能单遍完成解封装—查表—封装（single-pass），性能显著优于多遍处理。
4. 转发看哪层字段取决于路径段：underlay 看外层，overlay 看 VNI 加内层地址，策略与遥测可能同时看两层。

本章与前后章节的衔接：VXLAN 的封装格式、VTEP/VNI 与 BUM 处理见本章前一章的数据面进阶功能；解析深度与键宽约束见 BASIC-06 报文解析与可编程数据面；隧道表项占用的资源与查找引擎实现见 BASIC-11 表项资源与查找引擎。

## BASIC-09 贯穿式实例：一次 ping 的完整转发过程

前面几章把转发拆成解析、查表、缓冲、调度、改写等一段段来讲。分开讲便于理解，但也容易让学习者只见树木不见森林。这一章用一个最简单也最典型的场景——两台主机通过交换机通信——把碎片串成一条完整时序。读懂这一章，前面所有概念会第一次连成一条线。

### 1. 场景与拓扑

设定一个最小场景：主机 A（IP 为 192.168.1.10，MAC 为 AA:AA:AA:AA:AA:AA）和主机 B（IP 为 192.168.1.20，MAC 为 BB:BB:BB:BB:BB:BB）接在同一台二层交换机 SW1 上，同属 VLAN 10、同一网段 /24。A 执行 `ping 192.168.1.20`。我们把这个过程拆开，看看交换机里究竟发生了什么。

这里先明确一个前提：**主机 A 一开始并不知道 B 的 MAC 地址**。它只知道 B 的 IP。以太网帧必须填目的 MAC 才能发出，所以 A 的第一件事不是发 ping，而是想办法问出"B 的 MAC 是什么"。这个"问"的过程就是 ARP（地址解析协议），也是整个时序的第一步。下图把场景拓扑画出来。

:::figure id=BASIC-09-01 | name=ping 实验的拓扑与地址 | dir=LR
node n1 "主机 A<br/>IP .10 MAC AA" blue
node n2 "交换机 SW1<br/>VLAN 10 端口1与2" teal
node n3 "主机 B<br/>IP .20 MAC BB" green
node n4 "初始 MAC 表<br/>空表" amber
edge n1 -> n2 "端口1"
edge n2 -> n3 "端口2"
edge n2 -> n4 "MAC 表待学习"
:::

图中节点速览：n1 是主机 A，IP 尾号 .10、MAC 为 AA；n2 是交换机 SW1，VLAN 10 上有端口 1 和端口 2；n3 是主机 B，IP 尾号 .20、MAC 为 BB；n4 是交换机初始为空的 MAC 表，等待学习。整张图说明实验起点：两台主机在同一二层域，交换机还没有任何转发表项，一切从 ARP 开始。

### 2. 同网段转发：ARP 泛洪、MAC 学习与查表转发

现在按时间顺序走一遍。整个过程可以分成两大阶段——先用 ARP 找到 MAC，再用 ICMP 真正通信。

**阶段一：ARP 解析**

1. A 广播一个 ARP 请求："谁是 192.168.1.20？请告诉 192.168.1.10"。这个帧的目的 MAC 是全 F，源 MAC 是 A 的 AA。
2. 交换机从端口 1 收到这个帧。它做两件事：**学习**——把"源 MAC AA 在端口 1"写入 MAC 表；**查表**——目的 MAC 是全 F，是广播，于是在 VLAN 10 内向除端口 1 外的所有端口泛洪。
3. 主机 B 收到 ARP 请求，发现问的是自己的 IP，于是单播一个 ARP 应答："192.168.1.20 的 MAC 是 BB"，目的 MAC 是 AA。
4. 交换机从端口 2 收到应答，学习"源 MAC BB 在端口 2"；查表发现目的 MAC AA 已在表中对应端口 1，于是**单播**转发到端口 1，不再泛洪。
5. A 收到应答，得到 B 的 MAC，ARP 缓存里记下 192.168.1.20 → BB:BB:...。

注意这一步的关键：交换机在转发过程中**悄悄学会了两个 MAC 地址**，MAC 表从空表变成有两条表项。这就是第二章讲的"源 MAC 学习"在真实时序里的样子。

**阶段二：ICMP 通信**

6. A 构造 ICMP 回显请求（echo request），目的 IP 是 B，目的 MAC 是 BB，从端口 1 发出。
7. 交换机查 MAC 表，BB 命中端口 2，定向转发。这一次不再泛洪——因为已知单播。
8. B 收到请求，构造 ICMP 回显应答（echo reply），目的 MAC 是 AA，从端口 2 发出。
9. 交换机查表，AA 命中端口 1，定向转发回 A。
10. A 收到应答，ping 成功，显示往返时延。

下表把这十步中交换机的动作按阶段归拢，方便对照。

| 步骤 | 报文 | 目的 MAC | 交换机学习 | 交换机转发动作 |
|---|---|---|---|---|
| 1 | ARP 请求 | 全 F 广播 | 学到 A 在端口 1 | 泛洪到端口 2 |
| 2 | ARP 应答 | AA 单播 | 学到 B 在端口 2 | 查表命中，单播端口 1 |
| 3 | ICMP 请求 | BB 单播 | 无新表项 | 查表命中，单播端口 2 |
| 4 | ICMP 应答 | AA 单播 | 无新表项 | 查表命中，单播端口 1 |

这张表揭示了一个重要规律：**泛洪只发生在"不知道目的 MAC"时**。一旦通过源 MAC 学习建立了表项，后续全部是精确的单播转发。这也是为什么二层网络里 ARP 请求会泛洪、而正常数据流量不会——理解这一点，就理解了广播域大小为什么影响网络效率。

### 3. 跨网段转发：网关、路由与邻接

现在把场景变一变：主机 A（192.168.1.10/24）要 ping 主机 C（192.168.2.10/24），两者不在同一网段，中间由一台三层交换机（或路由器）R1 连接，R1 在 VLAN 10 的接口 IP 是 192.168.1.1，在 VLAN 20 的接口 IP 是 192.168.2.1。这里第一行判断就变了——A 用掩码一算，发现 C 不在本地子网，于是把帧交给网关。

跨网段时序如下：

1. A 发出 ARP 请求，但问的是**网关** 192.168.1.1 的 MAC，而不是 C 的。交换机学到 A 的 MAC，广播 ARP。
2. R1 的网关接口应答，给出自己的 MAC（记作 R1-MAC-A）。交换机学到 R1 该接口的 MAC。
3. A 构造 ICMP 请求，目的 IP 是 C，但**目的 MAC 是 R1-MAC-A**，发给网关。
4. R1 收到后进入三层转发：解析 IP 头，目的 IP 192.168.2.10 查路由表，LPM 命中直连网段 192.168.2.0/24；查邻接表得到 C 的 MAC；把 TTL 减一、重算 IP 校验和；把二层头改写为"源 MAC = R1 在 VLAN 20 的接口 MAC，目的 MAC = C 的 MAC"，从 VLAN 20 端口发出。
5. C 收到 ICMP 请求，回应的路径对称：C 把应答发给自己的网关 192.168.2.1，R1 再做一次三层转发回给 A。

这里出现了与同网段场景完全不同的几个动作，正是第三章 L3 流水线讲的内容：**目的 MAC 是网关**（触发三层处理）、**查路由表而不是 MAC 表**、**TTL 递减与校验和重算**、**二层头重写**。下面用一段伪代码把 R1 的三层转发决策写出来，与第三章的 L3 流水线伪代码对照着看。

```text
# 工程理解伪代码：网关 R1 对跨网段 ICMP 请求的转发（非真实 SDK 接口）
pkt       = ingress(port_vlan10)
hdr_l2    = parse_l2(pkt)
if hdr_l2.dst_mac == gateway_mac_vlan10:       # 目的 MAC 是本机网关 → 进入三层
    hdr_l3    = parse_l3(pkt)
    if hdr_l3.ttl <= 1:
        drop(pkt); return                       # TTL 耗尽，丢弃
    nexthop   = fib.lpm_lookup(hdr_l3.dst_ip)   # 查路由表命中 192.168.2.0/24
    dst_mac   = adjacency.lookup(nexthop)       # 邻接表查 C 的 MAC
    hdr_l3.ttl -= 1                             # 递减 TTL
    hdr_l3.checksum = recompute(hdr_l3)         # 重算校验和
    rewrite_l2(pkt, src=mac_vlan20, dst=dst_mac)# 重写二层头
    egress(nexthop.port, pkt)
```

对这段伪代码的判读：第一行的判断是三层转发的入口条件——目的 MAC 是不是本机网关 MAC，这正好呼应第二章 L2/L3 协同判定图里的分支。确认要三层转发后，依次做 TTL 检查、LPM 查路由、邻接解析、TTL 递减与校验和重算、二层头重写，最后从下一跳端口发出。注意 `src=mac_vlan20`——源 MAC 换成了 R1 在出方向接口上的 MAC，这正是"每过一跳二层头都被重写"的体现。这段伪代码把前面分散在多个章节的动作串成了一条真实路径。

### 4. 从实例回到流水线：一次 ping 用到了哪些能力

现在回头对照，一次最简单的 ping 其实调动了全书的几乎所有核心能力。把两个场景用到的能力列出来：

- **解析（parser）**：识别以太网头、ARP、IPv4、ICMP——对应数据面主路径的解析段。
- **MAC 学习**：从源 MAC 学得表项——对应 L2 流水线的学习步。
- **查表**：二层查 MAC 表、三层查 FIB 与邻接表——对应 L2/L3 两条流水线。
- **泛洪与复制**：ARP 请求广播、组播复制——对应第二章的泛洪判定与第三章的组播。
- **改写**：TTL 递减、校验和重算、二层头重写——对应 L3 流水线的改写步。
- **缓冲与调度**：报文在入出口排队、按队列调度——对应交换架构与拥塞管理。
- **控制面协作**：ARP 应答若由本机处理会上送 CPU——对应控制面与 punt 机制。

## BASIC-10 QoS 体系：从标记到调度

前面的章节解决了"把报文送到正确出口"的问题。但网络里还有一个同样重要的问题：当多个报文争抢同一条链路时，谁先走、谁被丢？QoS（Quality of Service，服务质量）就是回答这个问题的机制体系。它不决定报文去哪，而决定报文以什么优先级、什么待遇被转发出去。这一章把 QoS 从标记到调度串成一条完整链路。

### 1. 为什么需要 QoS：尽力而为的局限

以太网默认是"尽力而为"（best-effort）服务——所有报文一视同仁，谁先到谁先走，拥塞时一起丢。这对普通上网没问题，但有两类流量无法忍受：

- **实时流量**：语音、视频会议要求低时延、低抖动，包晚了就没有意义。
- **无损流量**：AI 训练里的 RDMA（远程直接内存访问）要求零丢包，丢一个包会导致整个计算任务重传、效率骤降。

QoS 的目标就是**差异化服务**：把流量分类，让重要的流量优先、保证带宽、避免丢弃，让不重要的流量在拥塞时被牺牲。对交换芯片而言，QoS 是数据面的核心能力之一——前面在调度那一节提过严格优先级、加权轮转、ECN、PFC，这一章把它们放回一个完整框架里。

理解 QoS 有个关键视角：**它是一个流水线，不是一堆开关**。从报文进入交换机到离开，会依次经过分类、监管、排队、调度、拥塞控制几个环节，每个环节各管一件事。下图先把这条链路画出来，后面逐段展开。

### 2. 分类与标记：给报文贴标签

QoS 的第一步是**识别哪些报文重要**，这靠读取报文里的优先级字段：

- **二层：802.1p（CoS）**。VLAN 标签里有 3 位优先级字段，可取 0 到 7，值越大优先级越高。
- **三层：DSCP**。IP 头里的服务类型字段前 6 位是 DSCP，可取 0 到 63。常见约定是 EF（46）给语音等低时延流量，AF 系列给有保证的流量，BE（0）是默认尽力而为。

有了字段还不够，交换机要决定**信不信这个标记**，这就是**信任边界（trust boundary）**。默认配置下，很多交换机不信任入口报文自带的 DSCP，会把它重写为 0；只有把端口配置为"信任 DSCP"或"信任 CoS"，才按报文自带的标记分类。为什么要这样设计？因为终端用户可以随意给自己的流量打高优先级标记，若无条件信任，一个人就能独占所有带宽。信任边界通常设在可控设备（如 IP 电话、受管理的交换机端口）一侧。

分类完成后，交换机把报文映射到一个**内部队列**。这是关键一步：无论入口标记是 DSCP 还是 CoS，最终都归到芯片内部的若干队列（常见 4 到 8 个），后续所有调度都基于队列而非原始标记。下面的伪代码把"读取标记—信任判断—映射队列"写出来。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：QoS 分类与队列映射（非真实 SDK 接口）
pkt       = ingress(port)
if port.trust == "dscp":
    mark = parse_l3(pkt).dscp                    # 信任三层 DSCP
elif port.trust == "cos":
    mark = parse_l2(pkt).cos                     # 信任二层 802.1p
else:
    mark = port.default_mark                     # 不信任：用端口默认标记重写
queue_id  = mark_to_queue[mark]                  # 按映射表归到内部队列
set_internal_priority(pkt, queue_id)             # 打上内部优先级，供后续调度
enqueue(queue_id, pkt)
```

对这段伪代码的判读：`port.trust` 决定读哪个字段——信任 DSCP 就读三层头，信任 CoS 就读二层 VLAN 标签，都不信任则用端口默认值覆盖。`mark_to_queue` 是核心映射表，把外部标记（DSCP 或 CoS）转成芯片内部的队列号——不同厂商的默认映射不同，这也是 QoS 配置中最常需要对齐的地方。`set_internal_priority` 把内部优先级写在报文的元数据里，后面排队和调度只看它。这段伪代码说明了信任边界的实际作用：它决定了"用谁写的标记来分类"。

### 3. 监管与整形：控制流量速率

分类之后，要对流量速率做控制，这里有两个容易混淆但方向相反的机制：

- **监管（policing）**：超出速率的报文直接丢弃或降级标记。它像交警，超速就罚款（丢包），动作即时、粗暴，用于限制某类流量的上限。
- **整形（shaping）**：超出速率的报文先缓存起来，慢慢发。它像收费站前排队，把突发流量抹平再送出，时延增加但少丢包。

两者都用**令牌桶（token bucket）**算法实现：系统按固定速率往桶里放令牌，报文发送要消耗令牌；桶里有令牌就放行，没有就按监管或整形的规则处理。令牌桶有两个关键参数——**承诺速率（CIR）**控制平均速率，**突发尺寸（Bc）**允许短时突发。下表把监管与整形并列对照。

| 维度 | 监管 policing | 整形 shaping |
|---|---|---|
| 超限动作 | 丢弃或降级标记 | 缓存后延迟发送 |
| 时延影响 | 不增加时延 | 增加时延 |
| 丢包 | 可能丢包 | 通常不丢 |
| 典型位置 | 入口 | 出口 |
| 适用场景 | 限制违规流量 | 平滑突发、匹配下游速率 |

理解两者的差别很重要：语音流量宁可丢弃也不愿排队（迟到没意义），适合监管；而批量数据传输可以慢一点但要完整，适合整形。在交换机里，监管通常放在入口（一进来就限速），整形通常放在出口（发送前平滑）。

### 4. 排队、调度与拥塞控制

经过分类与限速，报文进入内部队列。剩下的三件事决定它何时被发出去、拥塞时是否被丢。

**排队（queuing）**：每个端口有多个队列，报文按内部优先级进入对应队列。队列是 QoS 的落脚点——前面所有分类工作，最终就是把报文分到不同的队列里。

**调度（scheduling）**：决定多个队列谁先发。三种典型算法：
- **严格优先级（SP，Strict Priority）**：高优先级队列永远先发。时延最低，但低优先级可能被"饿死"。
- **加权轮转（WRR，Weighted Round Robin）**：按权重分配发送机会，更公平，但时延不可控。
- **混合方式**：高优先级用 SP 保证时延，其余队列用 WRR 分配带宽——这是实际网络中最常见的组合。

**拥塞控制**：当队列快满时，与其等到溢出丢包，不如提前通知发送端降速。两种核心机制：
- **ECN（显式拥塞通知）**：在 IP 头里打标记，接收端通知发送端降速，端到端地缓解拥塞。
- **PFC（基于优先级的流控）**：在二层发暂停帧，让上游暂停某个优先级的发送，实现"不丢包"。RoCEv2 的无损传输就靠 PFC 加 ECN 组合实现——这正是 AI 网络里 QoS 的核心战场。

需要说明的是，PFC 用不好会引入"PFC 死锁"和"队头阻塞"等问题，需要配合 ECN 与合理的缓冲配置。这些是数据中心网络运维的深水区，本节只建立概念。下面的伪代码把入队与调度决策串起来，与第二章的调度伪代码对照着看。

```text
# 工程理解伪代码：入队、调度与拥塞标记（非真实 SDK 接口）
enqueue(queue_id, pkt)                          # 按内部优先级入对应队列
for queue in port.queues:                       # 检查各队列深度
    if queue.depth > ecn_threshold:
        mark_ecn(queue.head)                    # 超阈值打 ECN，通知源端降速
    if queue.depth > pfc_threshold:
        send_pfc_pause(queue.priority)          # 逼近满载发 PFC 暂停帧
while egress_has_credit:                        # 出口有发送机会时调度
    q = scheduler.pick()                        # SP 或 WRR 选一个队列
    pkt = q.dequeue()
    transmit(pkt)
```

对这段伪代码的判读：`enqueue` 把报文放入分类阶段确定的队列；随后两个阈值检查体现主动拥塞管理——`ecn_threshold` 用 ECN 标记通知降速，`pfc_threshold` 用 PFC 暂停帧实现无损，二者都刻意早于队列溢出。`scheduler.pick()` 是调度的核心，按 SP 或 WRR 策略选队列出队。需要强调，真实芯片的调度器是硬件状态机、阈值按端口和队列独立配置，这段伪代码只用于建立"分类—排队—调度—拥塞控制"的概念链条。

### 5. 小结与交叉引用

本章把 QoS 串成一条五段流水线：分类与标记决定待遇、监管与整形控制速率、排队与调度决定次序、拥塞控制避免丢包。几个要点：

1. **差异化服务**是 QoS 的目的，实时流量要低时延、无损流量要零丢包，尽力而为无法兼顾。
2. **信任边界**决定用谁的标记分类，不信任时按端口默认标记重写，防止用户滥用高优先级。
3. **标记最终映射到内部队列**，调度只看内部优先级，不看原始 DSCP 或 CoS。
4. **监管丢弃、整形缓存**，令牌桶是两者共同的实现基础。
5. **SP 保时延、WRR 保公平**，实际多用混合；ECN 与 PFC 是 AI 无损网络的关键。

- 队列调度、ECN、PFC 在数据面主路径中的基础位置：本资料 BASIC-05 数据面章节。
- 计数器、遥测如何观测队列深度与丢包：本资料运维与遥测面章节。
- RoCEv2 与 AI 网络无损传输的更广泛讨论：交换芯片具体分册与相关网络技术资料。

## BASIC-11 表项资源与查找引擎：芯片真正的"记忆力"

前面各章反复提到表项容量：MAC 表装多少条、FIB 表装多少条、ACL 表够不够用。但"表项"在芯片里到底是什么、为什么不同表容量差别那么大、为什么 LPM 表天生就比 MAC 表贵，这些一直没系统讲。这一章专门回答。理解表项资源，才能把选型参数表里的"MAC 表 256K 条、路由表 128K 条"从数字变成对芯片能力的判断，也才能明白为什么"表项溢出"会直接导致性能塌陷。

### 1. 三种匹配类型：决定表项成本的根本因素

芯片里的表不是同一种东西。按匹配方式分，主要有三类，它们的硬件成本相差一个数量级以上。

**精确匹配（exact match）**：键和表项逐位完全相同才算命中，典型代表是 MAC 地址表与邻接表。这种匹配可以用哈希（hash）实现——把任意长度的键通过哈希函数映射成短索引，再查一片规整的存储阵列。哈希查找只需要普通 SRAM（静态随机存储器），容量可以做得很大、成本较低，是"便宜大碗"的方案。代价是哈希冲突需要额外处理（链式或再哈希），且无法表达"一段地址范围"这种语义。

**最长前缀匹配（LPM，longest prefix match）**：路由表的核心。键是目的 IP，表项是带掩码长度的前缀，多条前缀可能同时匹配，要选掩码最长的那条。这要求"所有表项同时比较、按优先级选最长"，普通 SRAM 做不到——它一次只能查一个位置。硬件上通常用 TCAM（ternary content-addressable memory，三态内容寻址存储器）实现：每个比特可以存 0、1 或"不关心"（掩码），查询时整个表并行比较，一个周期得出命中的最高优先级表项。TCAM 快但贵：并行比较电路让功耗和面积都很大，容量做到几十万条已属不易。

**范围与掩码匹配（range/mask match）**：ACL 与 QoS 分类表常见，条件可能是"端口在 1024 到 2048 之间"或"IP 前 24 位等于某值"。这类匹配同样依赖 TCAM 的"不关心"位能力，或用多级查找与区间树拆分实现。它比精确匹配贵，但比纯 LPM 灵活。

三类匹配的差别，可以概括成一句话：**匹配语义越复杂，能用的存储就越"专用"，容量越小、成本越高**。这解释了为什么 MAC 表动辄几十万条而路由表往往只有几万到十几万条——不是厂商不愿意做大，而是两者根本不在同一种存储上。

### 2. 存储介质：SRAM、TCAM 与外部存储的分工

表项落在不同介质上，性能与容量的权衡截然不同。下表把三种主要介质并列对照。

| 介质类型 | 匹配方式 | 速度 | 容量与成本 | 典型用途 |
|---|---|---|---|---|
| 片上 SRAM | 哈希精确匹配 | 一个或几个周期，线速 | 容量大、成本相对低 | MAC 表、邻接表、ECMP 成员表 |
| TCAM | 并行三态匹配 | 一个周期，全表并行 | 容量小、功耗与成本高 | FIB 路由表、ACL、QoS 分类 |
| 外部 DRAM/HBM | 哈希或索引查找 | 慢，需预取与流水线隐藏 | 容量很大、成本较低 | 超大路由表溢出、计数与统计 |

读表要抓住一条主线：**越靠近数据面线速路径的存储越贵、越小**。SRAM 规整便宜所以容量大，TCAM 因为并行比较电路昂贵所以容量受限，外部动态随机存储器（DRAM）虽然便宜量大但访问延迟高，只能放在"不要求每包都查"的位置。

这也解释了实际芯片里的一个重要设计：**表项分层**。热门表项放在片上 SRAM/TCAM 保证线速，冷门或超出的表项溢出到外部存储，由软件或慢路径处理。代价是溢出部分不再线速——这就是选型时"表项容量不够会掉性能"的机制。需要说明，上表是架构层面的一般规律，具体某型号采用几级存储、容量如何分配，必须查数据手册；这里给出的是判断框架。

### 3. 查找引擎：从哈希到并行比较

查找引擎是把"键"变成"结果"的硬件逻辑。理解它的两种基本实现，就能理解表项参数如何影响转发性能。

**哈希查找引擎**：把键送进哈希函数算出索引，再从 SRAM 阵列的对应位置读出结果。为了处理冲突，常配合多路组相联或桶结构。它的优点是容量大、功耗低、易于扩展；缺点是只能做精确匹配，且哈希冲突会带来最坏情况下的额外访问。MAC 表、邻接表、ECMP 成员表都走这条路。

**TCAM 查找引擎**：把键同时送到所有表项的比较电路，一拍之内找出所有匹配项，再由优先级编码器选出掩码最长的那条。它的优点是"全表并行、语义灵活、时延确定"；代价是并行比较电路面积大、功耗高，且每次比较都要驱动整块 TCAM，容量越大越贵。FIB 与 ACL 是它的主战场。

现代芯片常把两者放进同一条查找流水线的不同阶段：入口先做精确匹配（MAC、VLAN），中间做 LPM 路由，出口再做 ACL 策略校验。高端芯片会强调"查表阶段数"和"每阶段可用的查找带宽"——这两个参数决定了一次转发里能串起多少次查表，也决定了复杂策略能否在单遍处理内完成。

下图把两类引擎与典型表项串成一条查找路径，帮助建立"什么表走什么引擎"的对应关系。

:::figure id=BASIC-11-01 | name=精确匹配与并行匹配的查找引擎分工 | dir=LR
node n1 "查找键<br/>来自解析器抽取" blue
node n2 "哈希引擎<br/>精确匹配" teal
node n3 "片上 SRAM<br/>MAC 与邻接表" green
node n4 "TCAM 引擎<br/>并行三态匹配" amber

edge n2 -> n3 "算索引查表"

:::

图中节点速览：n1 是解析器输出的查找键；n2 是哈希引擎，负责精确匹配类查找；n3 是片上 SRAM，承载 MAC 表与邻接表等大容量精确匹配表；n4 是 TCAM 引擎，负责前缀与掩码类并行匹配；n5 是 TCAM 阵列，承载容量较小但语义复杂的 FIB 与 ACL；n6 合并两类结果，形成最终出口与动作。这张图的关键不是两条路径谁优谁劣，而是**一条流水线里两者并存**：不同表走不同引擎，芯片文档里的查表阶段数就是把这些引擎串起来的级数。

### 4. 表项容量预算：从需求反推需要多少条

选型时最容易犯的错是只看"支持 L3 路由"，不核算表项够不够。下面给出一套实用的估算思路。

**MAC 表看"这台交换机直接连多少 MAC"**。每个接入端口下挂的主机、虚拟机、容器都可能产生 MAC，预留 2 到 3 倍冗余。例如 48 个千兆口每台下挂 100 个虚拟机，就需要约 4800 条活跃 MAC，考虑冗余与 churn（频繁上下线）应准备 15000 条以上。这个量级 SRAM 通常轻松满足。

**FIB 看"整网有多少条路由前缀"**。每台三层交换机都要装下全网的路由前缀，规模取决于网络边界。企业网几万条、运营商全表几十万到近百万条。由于 FIB 用 TCAM，容量是最紧张的指标——必须按实际路由表规模加 30% 以上冗余核算，并确认芯片是否支持前缀压缩或外部表项扩展。

**邻接表看"下一跳数量"**。每条直连或间接下一跳都要占用邻接表项，规模通常远小于 FIB，但突发拓扑变化时会快速膨胀，同样要留冗余。

**ACL/QoS 看"策略条数"**。按安全与 QoS 规则数量估算，注意一条复杂规则可能占用多条 TCAM 表项（范围匹配常被拆成多条）。

**隧道表看"VTEP 与 VNI 规模"**。每个远端 VTEP、每个 VNI 都要有对应表项，分布式网关场景还要加上内层地址映射，这部分常被忽略却在大规模 overlay 里消耗可观资源。

下面这段伪代码把估算过程写成可复核的形式，便于选型时逐项填写。

```text
# 工程理解伪代码：表项容量预算（非真实工具接口）
mac_need  = access_ports * mac_per_port * redundancy      # 二层：端口×主机×冗余
fib_need  = current_prefixes * (1 + growth_margin)       # 三层：现网前缀×增长冗余
adj_need  = next_hops * (1 + churn_margin)                # 邻接：下一跳×抖动冗余
acl_need  = policy_rules * avg_tcam_entries_per_rule      # ACL：规则×拆分系数
tun_need  = vteps * vnis_per_vtep + inner_route_entries   # 隧道：VTEP×VNI + 内层路由
# 逐项与芯片数据手册核对，任何一项超出都要降级方案：
#   FIB 超 -> 前缀聚合 / 外部表项 / 更大的 TCAM 型号
#   MAC 超 -> 减少二层域规模 / 增大 MAC 表型号
#   ACL 超 -> 合并规则 / 改用精确匹配字段
```

对这段伪代码的判读：五项估算分别对应前面讲的五类表，其中 `acl_need` 乘以拆分系数、`tun_need` 显式加上内层路由，是两处最容易被漏算的地方。末尾的降级方案把"容量不足"变成具体动作：FIB 不足靠聚合与外部表项，MAC 不足靠缩小二层域，ACL 不足靠规则优化——这比笼统地说"选大芯片"更有工程价值。要强调的是，这些是估算框架而非精确公式，实际数字必须取自目标网络与数据手册。

### 5. 表项更新与一致性：收敛速度的隐藏瓶颈

容量之外，表项更新速率同样关键。网络拓扑变化时（链路故障、虚拟机迁移、路由收敛），控制面要在很短时间内改写大量表项。这里有三个容易被忽略的问题。

**更新粒度**：有些芯片支持单条表项原子更新，有些只能整块表重写。后者在批量更新时会产生中间状态，短暂出现"新旧规则并存"的不一致窗口。

**更新与查表的冲突**：数据面正在线速查表，控制面同时写表，硬件必须保证写操作不会让查表读到半写入的脏数据。高端芯片会做"先写后备表再原子切换"的设计，代价是需要双份表项资源。

**老化与回收**：MAC 表项靠老化机制回收，但老化扫描本身要占用表项带宽。扫描过快影响查表，过慢则僵尸表项占满容量——这是个需要按流量特征调优的参数，而非越大越好。

这三点合起来解释了为什么"表项更新速率"这个参数在选型中常被低估：它不体现在是否支持某功能上，却直接决定网络故障时业务中断多久。

### 6. 小结与交叉引用

1. 表项按匹配方式分三类：精确匹配用哈希加 SRAM，容量大成本低；LPM 与范围匹配用 TCAM，并行灵活但容量小、功耗高。匹配语义越复杂，存储越专用、越贵。
2. 存储介质分工明确：片上 SRAM 装大容量精确表，TCAM 装 FIB/ACL，外部 DRAM 承接溢出但不再线速；"表项溢出导致性能塌陷"由此而来。
3. 查找引擎分哈希与 TCAM 两类，现代芯片把它们串在同一条流水线的不同阶段；查表阶段数与每阶段带宽决定复杂策略能否单遍完成。
4. 容量预算要按 MAC/FIB/邻接/ACL/隧道五类分别估算并留冗余，尤其注意 ACL 规则拆分系数与隧道内层路由这两处漏算点。
5. 更新速率、更新粒度、写查冲突与老化回收共同决定收敛速度，是选型中容易被低估的指标。

本章与前后章节的衔接：解析出的字段如何成为查找键见 BASIC-06；LPM 与邻接解析在 L3 流水线中的位置见 BASIC-05；隧道表项在 overlay 中的作用见 BASIC-08；表项容量在选型参数表中的呈现见 BASIC-16 性能指标体系；控制面如何下发与老化表项见 BASIC-12 控制与管理面。

## BASIC-12 控制与管理面：决定怎么转发

### 1. 转发表项管理

控制面最核心的职责是维护数据面依赖的那些表：MAC 地址表、路由表、邻接表、ACL 表。具体包括表项的下发（写入）、查询、删除与老化（aging）。这里有两个关键指标：

- **表项容量**：能装多少条表项。装不下时，路由要退回软件或溢出到容量更大但更慢的外部存储，直接影响转发性能。
- **更新速率**：每秒能下发多少条表项。网络拓扑变化时（如链路故障、虚拟机迁移），表项要快速收敛，更新速率慢意味着业务中断时间长。

数据面查的是表的"结果"，控制面管的是表的"内容"——两者通过表项存储这条纽带连接。这是理解"为什么控制面不碰每个包却至关重要"的关键：它不改变流水线，但它决定流水线每一步查到什么。

下面用示意性的表项操作序列，展示控制面如何把三类表写进芯片、以及老化如何回收表项。这不是任何真实 SDK 接口，调用名需对照实际平台核验。

```text
# 工程理解伪代码：控制面表项下发与老化（非真实 SDK 接口）
mac_tbl.add(mac="00:11:22:33:44:55", port=3, vlan=100)   # 二层：写 MAC 表
route_tbl.add(prefix="10.0.0.0/8", nexthop="192.0.2.1")  # 三层：写路由表
acl_tbl.add(match=five_tuple, action="permit", prio=10)   # 策略：写 ACL 表
mac_tbl.set_aging(seconds=300)                            # 配置老化时间
stats = route_tbl.get_stats()                             # 查询表项统计
mac_tbl.remove_stale()                                    # 回收超时表项
```

对这段伪代码的判读：前三条 `add` 调用分别对应二层 MAC 表、三层路由表与 ACL 策略表，正好呼应数据面的三类查表——控制面写什么，数据面就查什么。`set_aging` 与 `remove_stale` 体现老化机制：MAC 表项若长时间没有流量刷新就会被回收，否则表项会被"僵尸条目"占满，导致新主机无法学习。`get_stats` 是运维面读取表项状态的入口，说明控制面与运维面也共享同一份表项存储。整段序列说明控制面的工作本质是"维护数据面依赖的表"，而非直接参与转发。

### 2. SDK、驱动与寄存器访问

上层软件配置芯片的唯一通道是 SDK（软件开发工具包）与寄存器访问。SDK 把芯片内部成百上千个寄存器封装成可编程接口，驱动把它们接入操作系统，网络操作系统再通过驱动下发配置。对使用者而言，这一层的成熟度往往比硅片参数更影响项目成败：一款纸面参数领先的芯片，若 SDK 文档不全、接口不稳定、bug 修复缓慢，实际落地会非常痛苦。

### 3. 与网络操作系统的对接：SAI

白盒交换机用 SAI（Switch Abstraction Interface，交换抽象接口）这一层标准抽象，让网络操作系统（NOS，如 SONiC）不依赖具体芯片。理论上，只要芯片提供符合规范的 SAI 实现，同一个 NOS 就能跑在不同厂商的芯片上。

但需要客观说明：SAI 的成熟度在不同芯片、不同分支版本上差异明显。大型云厂商往往有自己的定制分支并完成深度适配，而通用场景下的 SAI 特性完备性需按具体 SKU 核验。选型时若目标是 SONiC，务必确认所用 SAI 分支对该芯片型号的特性支持是否齐全——这是"纸面支持"与"生产可用"之间的现实差距。

### 4. 表项下发的一致性：从软件意图到硬件生效

第 1 节讲的是"下发哪些表"，这一节讲"怎么安全地下发"。控制面与数据面之间隔着一个关键问题：数据面每纳秒都在按现有表项转发，控制面却要同时改写这些表项。若处理不当，就会出现报文按"半新半旧"的规则转发的中间状态。

工程上有三种典型做法。**逐条更新**最简单，一条一条写入，但批量变更时存在前后不一致的窗口——比如先把下一跳改了、路由还没改，流量就会在一段时间内走向错误路径。**先写后备再原子切换**则维护两份表项，控制面把新表完整写入后备区，再一次性切换指针，保证任何时刻查表看到的都是完整的新表或完整的旧表；代价是需要双份表项资源，这正是高端芯片表项资源紧张的原因之一。**两阶段提交**把变更拆成"准备"与"生效"两步，先让所有相关表项就位但标记为未启用，再统一启用，适合跨多张表的联动变更。

对使用者而言，这些细节平时不可见，但在故障场景会直接暴露：一次链路故障需要同时改动路由、邻接、ECMP 成员表，若没有原子性保障，收敛过程中就会出现短暂丢包。因此评估"收敛速度"时，不能只看协议计算多快，还要看表项批量更新是否有原子机制、更新带宽是否足够。这与表项资源章节讨论的"更新粒度与写查冲突"是同一个问题的两面。

### 5. 快速收敛：把故障检测放进硬件

传统网络故障检测依赖控制面协议报文的交互，发现时间以秒计。对普通业务尚可接受，但对 AI 训练、金融交易这类场景，一秒中断就意味着任务回退或交易失败。交换芯片因此把两项检测能力下放到硬件。

**BFD 硬件卸载**：双向转发检测（BFD，Bidirectional Forwarding Detection）原本是跑在控制面的轻量协议，靠快速互发探测包发现链路故障。卸载到芯片后，探测报文的收发与超时判定由硬件完成，故障发现时间从秒级压到毫秒级，且不占用控制面 CPU。

**硬件链路保护切换**：检测到故障后，不等路由协议重新计算，硬件直接按预先备份的路径改道——这就是运维与遥测面章节提到的"免疫系统"在控制面的延伸。它依赖预先下发的备份表项，因此本质上是"用表项资源换收敛时间"。

两者结合，形成一个清晰的分工：硬件负责"快"——毫秒级发现与切换；控制面负责"准"——在硬件兜底之后慢慢完成全局路由重算与表项刷新。理解这个分工，就能明白为什么具体芯片资料会把快速故障检测列为独立卖点：它不是某个协议的软件优化，而是需要硬件表项与检测逻辑配合的系统能力。

## BASIC-13 运维与遥测面：让状态可见可控

### 1. 计数器与统计

最基础的运维功能是各类计数器：每端口、每队列收发字节数、包数、丢包数、错误数。它们是网络监控与故障定位的原始数据，也是所有高级遥测的基础。计数器看似简单，但在高速端口上要做到线速不丢计数、且读取时不影响转发，同样需要硬件支持。

### 2. 流量镜像与带内遥测

- **流量镜像（SPAN/ERSPAN）**：把指定流量复制一份送到分析端口或远端分析器，用于抓包排障与入侵检测。
- **INT（带内网络遥测）**：让报文携带遥测指令，逐跳把交换机内部状态（队列深度、时延、拥塞）写入报文，接收端据此还原整条路径的真实转发过程。
- **sFlow 等采样流**：周期性采样报文头部与计数器，以极低开销提供全网流量画像。

这一类功能把网络从"出问题后排查"变成"实时可见、自动隔离"。前面提到的 Teralynx 10 的 Flashlight 遥测，本质就是这一平面能力的加强版。

### 3. 可靠性与保护

链路聚合（LACP）把多条物理链路绑成一条逻辑链路，既增加带宽又提供冗余；BFD 硬件卸载把快速故障检测放到芯片里，缩短故障发现时间；硬件链路故障切换在链路down时立即改道，不等控制面收敛——这三项合起来，构成交换芯片的"免疫系统"。对 AI 训练这类对中断极度敏感的场景，故障切换速度直接决定任务是否停顿。

### 4. 安全与加密

ACL 过滤在入口就丢弃非法流量；MACsec 在二层做线速加密，保证链路上的报文机密性与完整性；风暴控制抑制广播/组播风暴；CoPP（控制面限速）保护控制面不被过量报文压垮。这些功能都属于运维与遥测面——它们的特点是"改变处理方式但不改变转发的本质目的地"。

### 5. 计数器如何做到线速且不干扰转发

第 1 节把计数器称为"所有高级遥测的基础"，但它的实现难度常被低估。在 800G 这样的线速端口上，每秒要处理十几亿个报文，如果每个包都去读写一次计数器，计数器本身就成为瓶颈。

硬件上的解法有三层。**分布与聚合**：不设单一全局计数器，而是按端口、队列、优先级分设多个计数存储体，让并发读写分散开。**批量更新**：不在每个包到达时立刻写计数，而是累积一批后在空闲周期批量写入，牺牲极小的精度换取吞吐。**无干扰读取**：运维读取计数器不能暂停查表或阻塞数据通路，因此采用双缓冲或快照机制——读操作拿到的是某一时刻的一致快照，而非正在被改写的实时值。

这三点解释了为什么参数表里的"计数器精度"和"读取开销"值得关注：采样型遥测（如 sFlow）本就不要求逐包精确，而计费、合规审计等场景则要求计数不丢不重，两者对硬件计数能力的要求不同。

### 6. 从轮询到流式遥测：数据模型的变化

传统运维靠 SNMP（简单网络管理协议）轮询：管理系统定时问设备"现在堆里有多少包"，设备逐项回答。这种方式简单，但在大规模网络里问题明显——轮询周期长（常见几分钟），瞬时微突发捕捉不到；轮询本身消耗控制面 CPU；返回的是离散点而非连续时间序列。

现代遥测改成设备主动推流：交换机按配置周期性把计数器、队列深度、光模块功率等数据以流式方式送到采集器，间隔可低至亚秒级。配合 gNMI（gRPC 网络管理接口）这类标准接口，数据以结构化的树状模型（YANG 模型）组织，不同厂商设备的遥测数据可以采用一致的语义。Teralynx 10 的 Flashlight 遥测就属于这一方向的能力增强——它把更细粒度的芯片内部状态以更低开销送出来。

两种模式并非替代关系：轮询适合低频健康检查与兼容性要求高的场景，流式适合需要高分辨率、捕捉微突发的场景。理解这一区别，才能判断"支持遥测"这类宣传是否满足自己的可观测性需求——关键要看推送间隔、数据模型覆盖范围，以及遥测采集本身是否占用转发资源。

### 7. 精确时间同步：PTP 与 IEEE 1588

前面讲带内遥测时提到"时间同步是跨设备时延分析的前提"，但没有展开。这一节补上这个在运维、金融与 AI 场景里越来越关键的基础能力。

**为什么 NTP 不够**。前面常见机制章讲过 NTP（网络时间协议），它把设备时钟同步到毫秒级——对日志时间戳、证书校验足够。但有些场景需要更精确的时间：金融交易要按时间顺序撮合与审计（监管常要求微秒级）、无线前传要精确的空中接口定时、分布式测量要对比不同设备的纳秒级事件（比如定位一次丢包发生在哪一跳）。NTP 的毫秒级精度在这些场景完全不够，需要 PTP。

**PTP 的基本原理**。**PTP（精确时间协议，Precision Time Protocol，标准号 IEEE 1588）** 通过在主从设备间交换时间戳报文来同步时钟，关键是**在硬件里给报文打时间戳**——报文进出端口的瞬间由PHY 或 MAC 层的硬件记录时刻，避开软件协议栈的不确定延迟。同步过程大致是：主时钟发 Sync 报文并携带发送时刻，从设备记录接收时刻，再结合 Follow_up 报文传递精确时间、Delay_Req/Delay_Resp 测量链路往返时延，最终算出时钟偏差与链路时延。

**硬件时间戳是关键**。PTP 的精度高度依赖时间戳在哪里打：如果靠 CPU 在软件里打，操作系统调度延迟会带来几十微秒甚至更大的抖动，精度就上不去；如果在交换芯片或网卡的硬件里打，可以把抖动压到纳秒级。这就是为什么交换机资料会把"支持 PTP 硬件时间戳""每个端口支持硬件时间戳"列为独立特性——它不是软件功能，而是需要芯片端口逻辑支持的能力。选型时要核对的是：是否每个端口都支持硬件时间戳、支持哪些 PTP Profile（如电信的 G.8275、电力场景的配置）、精度指标是多少。

**PTP 与网络的关系**。PTP 报文本身在网络里传输，交换设备如果参与转发，会引入排队时延——这个时延是不确定的（取决于拥塞），会破坏同步精度。解决办法有两种：一是让 PTP 报文走高优先级队列（配合前面 QoS 章的严格优先级调度），尽量减少排队；二是用**透明时钟（transparent clock）**——交换设备测量 PTP 报文在自己内部的驻留时间，并把这个时间写进报文的修正字段，让从设备能扣除它。支持透明时钟的交换机对 PTP 精度的贡献是决定性的，这也是数据中心与运营商网络选型时的核对项。

**与遥测和微突发的联系**。回到本节开头：为什么时间同步是跨设备时延分析的前提？因为 INT（带内网络遥测）记录的逐跳队列深度与时延，只有在各设备时钟一致时才能拼成一条可信的路径时延曲线；微突发分析要对比不同设备在同一时刻的队列状态，时钟不同步就无法对齐。前面可观测性章说"跨设备的时延分析依赖精确时钟（PTP/1588），否则各设备的计数对不上"——这里给出了完整解释。

下面这段伪代码把主从设备计算时钟偏差的过程固定下来，便于理解"时间戳加往返时延"的逻辑。

```text
# 工程理解伪代码：PTP 主从时钟偏差计算（非真实协议实现）
t1 = master.send_sync()                        # 主设备硬件打发送时间戳
t2 = slave.recv_sync(t1)                       # 从设备硬件打接收时间戳
t3 = slave.send_delay_req()                    # 从设备发时延请求
t4 = master.recv_delay_req(t3)                 # 主设备打接收时间戳
# 假设往返路径对称，链路单程时延：
delay = ((t4 - t1) + (t2 - t3)) / 2
# 从设备相对主设备的时钟偏差：
offset = ((t2 - t1) - (t4 - t3)) / 2
slave.adjust_clock(-offset)                    # 校正本地时钟
```

对这段伪代码的判读：四个时间戳 `t1` 到 `t4` 全部由硬件打点，避开软件延迟；`delay` 用往返时间的一半估计单程时延，前提是路径对称；`offset` 是从设备时钟相对主设备的偏差，校正它即完成同步。这段伪代码说明两件事：**第一，PTP 的精度来自硬件时间戳与对称路径假设，任何一处软件参与或路径不对称都会引入误差；第二，交换机的排队时延必须通过高优先级调度或透明时钟来消除，否则 `delay` 估计就不准**。这正是 PTP 与 QoS、芯片硬件能力紧密相关的原因。

需要说明，上述之外的 PTP 实现细节（如 Announce 报文的主从选举、UTC 闰秒处理、域与 Profile 配置）相当复杂，本节只建立"为什么需要它、它怎么工作、对芯片有什么要求"的框架，具体部署按设备文档与行业标准执行。

## BASIC-14 交换容量、SerDes 与端口速率

### 1. 容量口径：最容易踩的第一个坑

读懂任何交换芯片参数表的第一步，是搞清楚"交换容量"怎么算。厂商普遍按**端口名义速率之和**定义容量：64 个 800GbE 端口等于 51.2Tbps，128 个 800GbE 等于 102.4Tbps。这里的关键是不把收发双向重复计算——一个 800G 端口虽然是全双工（收发各 800G），但容量只按 800G 计一次。

这个口径解释了一个常见困惑：同一代芯片在不同资料里容量相差一倍。若某处写"Tomahawk 5 是 102.4T"、另一处写"51.2T"，多半不是事实错误，而是前者按双向叠加、后者按名义端口速率。理解和统一口径，是进行任何横向对比的前提。下表给出常见端口配置与容量的对应关系。

| 端口配置 | 名义容量 | SerDes 需求（按 100G/lane） | 典型代际 |
|---|---|---|---|
| 32 × 400GbE | 12.8T | 128 lane | 早期 12.8T 芯片 |
| 64 × 400GbE | 25.6T | 256 lane | 25.6T 芯片 |
| 64 × 800GbE | 51.2T | 512 lane | Tomahawk 5 一代 |
| 128 × 800GbE | 102.4T | 1024 lane | Tomahawk 6 一代 |
| 64 × 1.6TbE | 102.4T | 512 lane（200G/lane） | Condor 类高速 SerDes |

注：表中 SerDes 需求为示意，实际 lane 数与端口聚合方式、SerDes 速率代际相关，需以具体芯片数据手册为准。

### 2. SerDes：速率演进的真正引擎

交换芯片容量为什么能约两年翻一倍？答案在物理层——SerDes（Serializer/Deserializer，串行器/解串器）。它是芯片与外部世界之间的高速串行接口，把芯片内部的并行数据转成高速串行信号发送，或反过来把收到的串行信号还原成并行数据。

容量的提升来自两个乘数的增长：**单 lane 速率 × lane 数量**。单 lane 速率从早期的 28G、56G PAM4 演进到 112G PAM4，再到最新的 212.5G PAM4；lane 数则从 128 增加到 512、1024。两者相乘得到总带宽。所谓 PAM4（四电平脉冲幅度调制），是在一个符号周期内传 2 个比特（相比传统 NRZ 的 1 个比特翻倍），代价是抗噪声能力下降、对链路质量要求更高——这就是为什么高速率芯片的铜缆传输距离更短、更依赖光模块。

图中节点速览：n1 是交换容量，定义为端口名义速率之和；n2 与 n3 是容量的两个乘数——单 lane 速率（从 28G 到 212.5G PAM4 演进）与 lane 数量（从 128 到 1024）；n4 指出容量等于两者相乘，因此约两年翻倍；n5 是 PAM4 提高速率的代价——抗噪声能力下降；n6 是这一代价的后果——链路要求提高，铜缆传输距离变短、更依赖光模块。整张图说明容量增长的本质是 SerDes 物理层演进，而非逻辑架构变化。

### 3. 端口聚合与光模块形态

lane 数的增加最终要落到端口上，这就是端口聚合：把多条 lane 绑成一个高速端口，例如 4 条 100G lane 组成 400G 端口、8 条组成 800G 端口。同样的 1024 条 lane，聚合成 512 个 200G 端口得到最高 Radix，聚合成 128 个 800G 端口则得到更少但更快的端口——这是同一芯片的两种整机形态。

链路介质同样需要理解DAC（无源铜缆，便宜、距离最短约 1 至 3 米）、AEC（有源电缆，距离中等）、LPO（线性直驱光模块，低功耗）、CPO（共封装光学，把光引擎与芯片封在一起，功耗与密度最优但维修复杂）这几类形态的取舍。下面的示意配置展示容量口径与端口聚合的关系。

```text
# 工程理解示意：同样 1024 条 100G lane 的两种端口聚合（非真实配置）
total_lanes = 1024
profile_A:
  lane_rate  = 100G
  ports      = total_lanes / 4 = 256 x 400GbE
  capacity   = 256 * 400G = 102.4T
profile_B:
  lane_rate  = 100G
  ports      = total_lanes / 8 = 128 x 800GbE
  capacity   = 128 * 800G = 102.4T
```

对这段配置的判读：两个 profile 的 lane 总数相同（1024）、单 lane 速率相同（100G），因此名义容量必然相同（102.4T）——这再次印证了容量口径。差别在聚合粒度：profile_A 用 4 lane 聚合成 400G 端口，得到 256 个端口；profile_B 用 8 lane 聚合成 800G 端口，得到 128 个端口。端口聚合方式由整机的目标拓扑决定，而非芯片本身——同一颗芯片可以做成不同形态的交换机。选型时要先明确需要多少端口、每端口多快，再反推聚合方式与介质形态。

### 4. 信号完整性：FEC、眼图与误码率

前面第 2 节讲了 SerDes 速率从 56G 到 224G 的演进，但有一个关键问题没回答：**速率翻倍时，电信号在铜线和 PCB 上传输的物理极限怎么突破**？答案是三样东西——更好的调制、更强的均衡、以及前向纠错。理解它们，才能明白为什么同样标称速率的芯片，实际可用带宽与时延表现会不同。

**从 NRZ 到 PAM4**。早期 SerDes 用 NRZ（不归零）编码，每个符号传 1 比特，112G 需要 112 GBaud 的符号率——物理上难以实现。PAM4（四电平脉冲幅度调制）每个符号传 2 比特，把 112G 的符号率降到 56 GBaud，代价是信号幅度被分成四档，相邻电平之间的噪声容限只有 NRZ 的三分之一。这带来一个直接后果：**PAM4 的误码率天然比 NRZ 高得多**，必须配合更强的技术手段。这就是 224G 时代 PAM4 成为主流、但"误码率"成为核心指标的由来。

**误码率与 FEC**。误码率（BER，Bit Error Rate）是传输错误的比特占比。光通信或高速电链路的原始误码率可能在 1e-6 量级（每百万比特错一个），这对网络完全不可接受。FEC（前向纠错，Forward Error Correction）的思路是在发送端按规则加入冗余校验位，接收端据此纠正一定数量内的错误，把误码率压到 1e-15 甚至更低（相当于"万亿分之一"）。代价有两个：**冗余位吃掉有效带宽**（常见开销约 7% 到 15%），以及**编解码引入时延**（几十到几百纳秒）。这两点都是实实在在的成本——前面指标章说"标称速率与实测速率有差距"，FEC 开销正是重要原因之一；前面低时延场景强调 cut-through，FEC 时延则是另一处来源。

不同代际的 FEC 标准不同（如 RS(528,514)、RS(544,514)，以及更强的 KP4 FEC），纠错能力与开销各异。选型时"支持 FEC"只是起点，要问的是"用哪套 FEC、开销多少、时延几何"。

**眼图与信号质量**。眼图（eye diagram）是把大量比特波形叠加显示形成的图形，因形状像眼睛而得名。眼睛张得越开，说明信号质量越好、噪声越小；眼睛闭合或中间被杂散信号填满，就说明误码风险高。眼高（垂直张开度）反映噪声容限，眼宽（水平张开度）反映时序裕量。工程师用眼图判断链路设计是否达标——这也是为什么高速芯片的评估板调试离不开示波器：参数表告诉你"支持 224G"，眼图告诉你"在你的 PCB 和线缆上实际跑得多稳"。

**均衡技术**。为了在接收端"把闭合的眼睛睁开"，SerDes 用了多种均衡：TX 端的预加重（de-emphasis）提前补偿高频衰减，RX 端的 CTLE（连续时间线性均衡）放大高频分量、DFE（判决反馈均衡）消除码间干扰。这些技术能显著改善信号质量，但都消耗功耗、增加复杂度。理解它们，就能理解为什么高速端口的功耗随速率增长得如此之快——前面容量章讲"SerDes 是功耗的主要来源"，均衡电路正是其中的大头。

### 5. 光模块与光纤选型：距离、波长与形态

前面第 3 节讲了光模块的封装形态（SFP、QSFP28、QSFP-DD 等），但没讲"具体该选哪一种"。这节补上实操判断，核心是三个变量：距离、波长、光纤类型。

**距离决定模块档次**。光模块按传输距离大致分档：SR（短距，多模光纤，通常 100 米以内，用于机架内与相邻机架）、DR（500 米，单模）、FR（2 公里，单模）、LR（10 公里，单模）、ER（40 公里，单模）。距离越长，激光器功率与接收灵敏度要求越高，模块成本也越高。选型的铁律是**按实际距离留余量但不过度配置**——用 LR 模块跑 10 米虽然能通，但成本高且可能因为光功率过强需要加衰减器。

**单模与多模**。多模光纤芯径粗（50 或 62.5 微米），允许多个模式的光同时传播，配合便宜的 LED 或 VCSEL 光源，成本低但模式色散限制距离与带宽，适合短距。单模光纤芯径细（约 9 微米），只传一个模式，配合激光器，带宽高、距离远，适合中长距。判断方法很简单：**看距离——超过几百米基本就是单模，机架内短距多用多模**。

**波长与波分复用**。常见波长有 850nm（多模短距）、1310nm 与 1550nm（单模长距）。当光纤资源紧张时，用波分复用（WDM）在一根光纤上同时传多个不同波长的信号，成对增加容量——这正是 400G/800G 模块常用的手段（如 8 个波长各传 50G 或 100G）。理解波长与 WDM，就能看懂模块型号里那些数字的含义。

**光功率预算与 DOM**。链路能否可靠工作，取决于光功率预算：发送功率减去光纤衰减与连接器损耗，必须高于接收灵敏度，并留足余量。这个计算在长距链路里尤其重要。现代光模块普遍支持 DOM（数字光监控），可实时读取发送功率、接收功率、温度、电压等——这些数值正是前面运维章讲的遥测数据源，也是排障时判断"是光模块问题还是光纤问题"的直接依据。排障章讲"物理层检查"时，看光功率就是第一步。

下表把常见光模块类型与距离、光纤、波长并列，作为选型速查。

| 类型 | 典型距离 | 光纤 | 波长 | 典型场景 |
|---|---|---|---|---|
| SR | 100 米以内 | 多模 | 850nm | 机架内、相邻机架 |
| DR | 500 米 | 单模 | 1310nm | 同一数据中心内跨机架 |
| FR | 2 公里 | 单模 | 1310nm | 园区内建筑间 |
| LR | 10 公里 | 单模 | 1310nm | 城域接入、跨园区 |
| ER | 40 公里 | 单模 | 1550nm | 运营商与长距互联 |

需要说明，上表的距离是典型值而非绝对上限，实际受光纤质量、连接器数量与模块规格影响；具体选型必须查模块数据手册并用光功率预算核算。此外还有 DAC（直连铜缆）与 AOC（有源光缆）两种短距形态：DAC 便宜、低时延、距离极短（通常 3 米内），常用于同一机架内交换机到服务器；AOC 用光纤但模块固定不可拆，距离与成本介于 DAC 与光模块之间。前面端口章提到 DAC，这里补上了它与光模块的适用边界。

## BASIC-15 交换架构与转发模式

### 1. 共享内存与分布式缓冲

当多个入口同时涌向同一出口时，报文必须暂存。怎么暂存，是交换架构的核心问题，业界有两大流派。

**共享内存架构**：所有端口共享一片片上缓冲池。优点是缓冲利用率高——空闲端口的缓冲可以被拥塞端口借用；缺点是容易出现队头阻塞（Head-of-Line blocking），且一个端口的突发可能挤占其他端口的缓冲。

**分布式缓冲（VOQ，虚拟输出队列）**：按目的出口为每个入口分配独立队列。优点是彻底避免队头阻塞，因为发往不同出口的包各自排队；缺点是需要更多片上存储，芯片面积与功耗代价更大。高端芯片常采用"共享 + 分布式"的混合形态，在利用率与抗阻塞之间取平衡。

这两种架构的差异，直接决定芯片面对微突发（microburst，极短时间内的大量报文）时的表现。深缓冲方案靠"装得多"吸收突发，低时延方案靠"排得快"减少驻留——这是一对经典的取舍，没有绝对优劣，取决于目标场景。下图把两种缓冲架构并列画出。

node n3 "分布式缓冲 VOQ<br/>按目的出口分队列" teal
node n4 "利用率高<br/>队头阻塞风险" amber
node n5 "抗阻塞好<br/>片上存储代价大" amber

图中节点速览：n1 是多个入口同时到达的场景，是所有交换架构要处理的问题起点；n2、n3 是两种方案——共享内存（所有端口共享缓冲池）与分布式缓冲 VOQ（按目的出口分队列）；n4 是共享内存的特点（利用率高但有队头阻塞风险），n5 是 VOQ 的特点（抗阻塞好但片上存储代价大）；n6 是二者的共同取舍——深缓冲靠容量吸收突发、低时延靠速度减少驻留。整张图说明两种架构各有代价，最终取舍取决于目标场景对突发吸收与时延的权重。

### 2. cut-through 与 store-and-forward

转发模式是另一个基础但重要的取舍。cut-through（直通）在收到报文的目的地址后就开始转发，不等整包收完，时延最低（可低至纳秒级），但可能把校验错误的坏包也转发出去。store-and-forward（存储转发）收完整包并校验通过后才转发，可靠性高，但时延至少增加一个完整包长的接收时间。

现代芯片多支持按端口或按场景配置：对时延敏感的 AI 训练流量用 cut-through，对可靠性要求高的场景用 store-and-forward。厂商标称的超低时延几乎都是 cut-through 理想值，实际带载、开启 VLAN 改写或深缓冲后时延会上升——这是读参数时必须注意的口径。下表把两种模式并列对照。

| 维度 | cut-through（直通） | store-and-forward（存储转发） |
|---|---|---|
| 转发时机 | 收到目的地址即转发 | 收完整包并校验后转发 |
| 时延 | 最低，纳秒级 | 至少多一个包长时间 |
| 坏包处理 | 可能转发错误包 | 校验失败丢弃 |
| 适用场景 | AI 训练、低时延交易 | 可靠性优先的通用网络 |
| 厂商标称口径 | 多为该模式理想值 | 带载后时延上升 |

### 3. 队头阻塞与调度的关系

队头阻塞值得单独理解：在简单的先进先出队列里，如果队首的包因目标出口拥塞而发不出去，后面本可发往其他空闲出口的包也被堵住——就像一条车道上前车抛锚，后面所有车都动不了。这正是 VOQ 要解决的问题：按目的出口分队列后，发往空闲出口的包不会因为发往拥塞出口的包而受阻。

调度则解决另一个问题：当多个队列都有包要发时，谁先走。严格优先级（SP）让高优先级队列优先，但可能饿死低优先级；加权轮转（WRR）按比例分配带宽，更公平。调度与缓冲架构配合，共同决定芯片的拥塞行为。下面的伪代码把入队决策与转发模式的关系讲清楚。

```text
# 工程理解伪代码：入队与转发模式决策（非真实 SDK 接口）
pkt       = ingress(port)
dst_port  = lookup_forward(pkt)             # 查表得到目的端口
queue     = voq_select(port, dst_port)      # 按目的出口选虚拟输出队列
if queue.depth > threshold:
    mark_congestion(pkt)                    # 超阈值标记 ECN，通知源端降速
enqueue(queue, pkt)                         # 入队等待调度
if forward_mode == "cut_through" and hdr_ready(pkt):
    start_forward(pkt)                      # 收到头即转发，不等整包
else:
    if crc_ok(pkt):                         # 存储转发：先校验
        start_forward(pkt)
```

对这段伪代码的判读：`voq_select` 体现分布式缓冲的核心思想——按目的端口选队列，从机制上避免队头阻塞；`mark_congestion` 是主动拥塞管理，队列超阈值就给报文打 ECN 标记，让接收端通知发送端降速，而非等队列溢出再丢包；最后的条件分支对比两种转发模式——cut-through 只要头部就绪就 `start_forward`，store-and-forward 则要等 `crc_ok` 校验通过。需要强调，这段伪代码是概念示意，真实芯片的队列与调度机制远比这复杂，具体实现需以数据手册为准。

图中节点速览：n1 是交换芯片选型的总纲；n2 到 n6 是五类指标——容量与端口、时延与吞吐、缓冲与拥塞、表项与特性、功耗与生态，都由 n1 指向"看"；n7 是组合判断，五类指标共同汇入，强调按场景定权重而非单看某一项。整张图说明选型是多维决策，没有一颗芯片在所有指标上都最优。

### 2. 标称值与实测值的差距

参数表里最容易误判的是时延与功耗。厂商标称时延通常是 cut-through、空载或轻载下的理想值，实际网络中一旦开启 VLAN 改写、深缓冲、组播复制，时延就会上升；标称功耗是典型场景值，满载所有端口时功耗更高。因此严肃的选型要索取带载时延报告与满载功耗数据，而不是直接引用宣传数字。

另一个常见误区是只看容量数字。容量相同的两颗芯片，可能因 Radix 不同、缓冲架构不同、时延特性不同，适合完全不同的场景——102.4T 既能做成高 Radix 的扁平 scale-out 交换机，也能做成低时延的 scale-up 互联，取决于端口聚合与架构取舍。

### 3. 从需求反推配置的选型思路

正确的选型顺序是"从场景反推参数"，而不是"从参数挑芯片"。下面用示意伪代码展示这个思路：先明确拓扑与流量特征，再推导所需的 Radix、缓冲与特性组合。

```text
# 工程理解示意：从场景反推芯片配置（非真实工具）
scenario = "AI_scaleout"          # 场景：AI 横向扩展集群
xpu_count = 100000                # 加速器数量
if xpu_count > 50000:
    need_radix = "high"           # 大规模 → 高 Radix 减少拓扑层数
if scenario.startswith("AI"):
    need_lossless = True          # AI/RDMA → 需要无损（PFC/ECN）
    need_low_tail_latency = True  # 集合通信 → 关注尾时延
config = {
    "radix": need_radix,
    "buffer": "deep" if need_lossless else "shallow",
    "features": ["RoCEv2", "adaptive_routing", "telemetry"]
}
```

对这段伪代码的判读：起点是场景与规模（`scenario`、`xpu_count`），而非芯片参数；`xpu_count` 很大时推导出 `need_radix = high`，因为高 Radix 能用更少层数连接同等规模集群，直接减少跳数与光模块；AI 场景进一步推导出需要无损传输与低尾时延，因为 RDMA 对丢包敏感、集合通信对最慢节点敏感；最终得到的 `config` 是一组需求特征，拿这组特征去匹配具体芯片，比先挑容量数字再勉强适配要可靠得多。这套思路把前面几章的知识串成了一个完整的决策链。

## BASIC-17 进阶协议与可靠性：防环、EVPN 与无损网络

到这里，读者已经能读懂芯片的转发流水线、一次 ping 的全程和 QoS 体系。但要真正精通交换机，还需要理解几类"让网络可靠工作"的协议机制：二层如何避免环路、VXLAN 的转发表由谁建立、AI 网络如何做到零丢包。这些主题有的在前面章节零星出现过（生成树、PFC/ECN、VXLAN 数据面），这一章把它们系统展开。

### 1. 二层防环：STP、RSTP 与 MSTP

二层转发的泛洪机制有个致命弱点：如果网络中存在物理环路，广播帧会在环路里无限循环复制，形成**广播风暴**，几秒钟就能耗尽带宽和 CPU。二层网络又常常为了冗余特意拉双线，环路风险天然存在。生成树协议（STP，Spanning Tree Protocol）就是为解决这个问题而生。

STP 的思路很巧妙：**逻辑上阻塞冗余链路，把有环的物理拓扑剪成无环的树**。它工作分三步：

1. **选举根桥（root bridge）**：所有交换机按桥 ID（优先级加 MAC）选出一个根，作为树的根。
2. **选举根端口（root port）**：每台非根交换机选出离根桥最近的端口，作为通往根的方向。
3. **选举指定端口（designated port）并阻塞其余端口**：每个网段选一个指定端口转发，剩下的冗余端口进入阻塞状态，不转发用户流量。

被阻塞的端口并非永远不用——当主链路故障时，STP 会重新计算，把阻塞端口打开，恢复连通。这就是冗余的意义：平时不浪费、故障时顶上。

**RSTP（快速生成树，802.1w）**是 STP 的改进版，把收敛时间从几十秒缩短到秒级甚至亚秒级，通过端口角色快速切换实现。**MSTP（多生成树，802.1s）**进一步允许多个 VLAN 映射到不同的生成树实例，避免所有 VLAN 都走同一条路径造成的链路浪费——它与 VLAN、Trunk 配合，是园区网的常见配置。

需要指出一个现代数据中心的现实：较大规模的 Clos 架构网络往往**不跑 STP**，而是靠三层路由和 ECMP 天然无环（路由的 TTL 与路由协议本身防环），把二层域压缩到极小。STP 主要活在园区网和传统二层环境里。下表把三代生成树对照。

| 协议 | 标准 | 收敛时间 | 多 VLAN 支持 | 典型场景 |
|---|---|---|---|---|
| STP | 802.1D | 30 至 50 秒 | 单一生成树 | 老旧网络 |
| RSTP | 802.1w | 秒级 | 单一生成树 | 中小园区网 |
| MSTP | 802.1s | 秒级 | 多实例，按 VLAN 映射 | 大型园区网 |

### 2. EVPN：VXLAN 的控制面

前面讲 VXLAN 时留下一个关键问题：源 VTEP 怎么知道目的 MAC 在哪个远端 VTEP 后面？如果靠数据面泛洪（BUM 流量头端复制）来学习，效率低、浪费带宽。EVPN（Ethernet Virtual Private Network）就是来解决这个问题的——它是 VXLAN 的**控制面**。

EVPN 的本质是：**用 BGP 协议在 VTEP 之间发布主机可达性信息**。本地 VTEP 通过数据面学习到一台主机的 MAC/IP 后，不把它闷在本地，而是通过 BGP EVPN 路由公告给其他 VTEP；远端 VTEP 收到后，在本地转发表里写入"这个 MAC/IP 在那个 VTEP 后面"。这样后续通信就是精确的单播封装，无需泛洪查找。

EVPN 有几个关键优势：

- **抑制泛洪**：主机位置通过控制面传播，ARP 请求可以由 VTEP 代答（ARP suppression），大幅减少 BUM 流量。
- **支持多归属（multihoming）**：一台主机可以双归到两台 VTEP，实现链路冗余，且能避免环路。
- **统一二三层**：EVPN 路由类型既发布 MAC 也发布 IP，能同时支持二层桥接和三层网关，配合分布式 IRB 实现对称转发。

### 3. 无损网络：RoCE、PFC 与 DCQCN

AI 训练集群里，GPU 之间要通过 RDMA over Converged Ethernet（RoCEv2）直接读写远端内存。RDMA 对丢包极度敏感——传统 TCP 丢包只重传一个段，RDMA 丢一个包往往导致整个消息重传，训练效率断崖式下降。所以 AI 网络追求**无损（lossless）**：拥塞时不丢包。

交换芯片层面实现无损靠两件事，都在 QoS 章节讲过：

- **PFC（基于优先级的流控）**：队列快满时向上游发暂停帧，让上游停止该优先级发送，从链路上避免丢包。
- **ECN（显式拥塞通知）**：在报文里打标记，让接收端通知发送端降速，从源头上缓解拥塞。

但仅有 PFC 不够。PFC 是"暂停—恢复"的粗粒度开关，容易引发 **PFC 风暴**（暂停帧逐级向上游传播，导致大面积停流）和**死锁**（多个优先级互相等待，谁也发不了）。业界用 **DCQCN**（数据中心量化拥塞通知）来解决：它把 ECN 标记与速率控制结合，让发送端根据拥塞程度平滑降速，而不是靠 PFC 硬暂停。DCQCN 是 RoCEv2 网络里端到端拥塞控制的事实标准。

对交换芯片而言，支撑无损需要：足够深的缓冲吸收微突发、精细的队列阈值配置、PFC 与 ECN 的硬件卸载、以及拥塞状态的细粒度遥测（这正是具体芯片分册里强调的能力）。下表把三种机制的作用层次列出来。

| 机制 | 作用层次 | 触发方式 | 解决什么 |
|---|---|---|---|
| PFC | 逐跳、二层 | 队列超阈值发暂停帧 | 链路级不丢包 |
| ECN | 端到端、三层 | IP 头打标记 | 通知源端降速 |
| DCQCN | 端到端、源端 | 基于 ECN 反馈调速 | 平滑降速，避免 PFC 风暴 |

### 4. 端口安全：从 ACL 到 DHCP Snooping

交换机的安全能力分布在多个章节里，这里做一个系统梳理，按"防谁、在哪防"分层：

- **ACL（访问控制列表）**：最通用，按五元组、MAC、端口等字段匹配，允许或丢弃。前面在数据面与运维面都提过，它是跨二三层的基础过滤手段。
- **端口安全（port security）**：限制一个端口能学到的 MAC 地址数量，防止攻击者伪造大量 MAC 耗尽转发表（MAC 泛洪攻击）。
- **DHCP Snooping**：监听 DHCP 过程，只信任连接正规 DHCP 服务器的端口，防止攻击者私设 DHCP 服务器下发错误网关（中间人攻击）。它还生成"IP-MAC-端口"绑定表，供后续防护使用。
- **DAI（动态 ARP 检测）**：利用 DHCP Snooping 的绑定表检查 ARP 报文，丢弃伪造的 ARP 应答，防 ARP 欺骗。
- **IP Source Guard**：基于绑定表过滤源 IP，防止主机伪造源地址。
- **MACsec**：在二层做线速加密，保护链路上的报文机密性与完整性，前面在运维面提到过。

这几项能力层层递进：ACL 是通用过滤，端口安全管 MAC 学习，DHCP Snooping 建立可信绑定表，DAI 和 IP Source Guard 用这张表防欺骗，MACsec 管链路加密。理解它们的依赖关系，就不难明白为什么 DHCP Snooping 常常是其他防护的前提。

### 5. 小结与交叉引用

本章把几类"让网络可靠工作"的机制串起来：

1. **生成树**用逻辑阻塞把有环拓扑剪成树，STP 到 RSTP 到 MSTP 逐步改善收敛与 VLAN 利用；大型 Clos 网络则用三层无环设计绕开它。
2. **EVPN 是 VXLAN 的控制面**，用 BGP 发布主机可达性，抑制泛洪、支持多归属、统一二三层——没有它，VXLAN 只能靠泛洪学习。
3. **无损网络**靠 PFC 做逐跳不丢包、ECN 做端到端通知、DCQCN 做平滑调速，三者配合支撑 RoCEv2。
4. **端口安全**从 ACL 到 DHCP Snooping 到 DAI 层层递进，DHCP Snooping 的绑定表是多项防护的基础。

- VXLAN 数据面封装、PFC/ECN 基础、ACL 与 MACsec：本资料数据面进阶功能与运维面章节。
- 具体芯片对 PFC、ECN、拥塞遥测的硬件支持：Tomahawk 6、Teralynx 10 分册。

## BASIC-18 运维排障与可观测性：从看状态到定位问题

能配置、能转发，还不算精通。精通的标志是**出了问题能定位**：ping 不通、时通时断、时延忽高忽低，该从哪里下手。这一章把排障方法论与可观测性工具放在一起讲——前者是思路，后者是手段，二者配合才能从现象走到根因。

### 1. 排障总思路：分层与分段

排障最忌讳凭直觉乱试。系统化的方法有两个维度：

**分层排查（按 OSI 自下而上）**：
- **物理层**：链路是否 up、光模块功率是否正常、有无 CRC 错误。
- **二层**：VLAN 是否一致、MAC 表是否学到、Trunk 是否放行目标 VLAN、有无环路。
- **三层**：IP 与掩码是否正确、路由是否存在、邻接是否建立、网关是否可达。
- **传输与应用层**：端口是否监听、防火墙是否拦截、应用本身状态。

**分段排查（按路径逐跳定位）**：从源到目的把路径切成若干段，逐段测试，先确定"问题在哪一跳"，再在这一跳上深挖。这比一上来就抓全包高效得多。

两个维度结合，就是"先分层定性质、再分段定位置"。下图把排障的分层决策画出来。

node n3 "二层<br/>VLAN MAC 环路" teal
node n4 "三层<br/>路由 邻接 网关" amber

图中节点速览：n1 是故障现象，包括不通、时断、时延高；n2 是物理层检查，看链路状态、CRC 错误与光功率；n3 是二层检查，看 VLAN、MAC 表与环路；n4 是三层检查，看路由、邻接与网关；n5 是传输与应用层检查，看端口监听与防火墙；n6 是最终定位的根因。整张图体现"自下而上、逐层排除"的排障思路，每层正常才进入下一层。

### 2. 三类典型问题的定位路径

把常见故障归成三类，各自有典型的定位路径。

**问题一：完全不通**。按分层顺序查：
- 物理层：端口是否 up，`show interfaces` 看状态与错误计数。
- 二层：`show mac address-table` 看是否学到对端 MAC；MAC 没学到，可能是 VLAN 不一致、Trunk 未放行、或物理不通。
- 三层：`show ip route` 看路由是否存在；跨网段还要看邻接表 `show ip adjacency` 是否建立。
- 对照本章的贯穿实例：完全不通往往卡在 ARP 没学会（二层）或路由/邻接缺失（三层）。

**问题二：时通时断**。这类多为间歇性问题，重点查：
- 物理层：CRC 错误计数是否增长（线缆或光模块问题）。
- 环路：STP 端口是否在频繁切换、是否有广播风暴。
- 拥塞：队列深度是否周期性打满、是否触发 PFC 暂停。
- 路由震荡：路由表项是否频繁变化（可看路由翻动计数）。

**问题三：时延高或抖动**。重点查：
- 拥塞：出队列是否持续排队，尾时延是否升高。
- 微突发：短时流量尖峰是否超出缓冲，可被 PFC 或 ECN 标记捕捉。
- 转发模式：是否因开启存储转发或深缓冲导致时延增加——这呼应交换架构章节里 cut-through 与 store-and-forward 的取舍。

### 3. show 命令与可观测性：用数据说话

排障靠数据而非猜测。交换机提供的可观测性手段分几类：

- **表项查询**：`show mac address-table`、`show ip route`、`show ip adjacency`——直接看转发表的现状，是判断"学没学到、有没有路由"的第一手段。
- **计数器统计**：`show interfaces counters`、`show queue`——看收发包数、丢包数、错误数、队列深度，判断是否有拥塞或错误。
- **抓包与镜像**：SPAN/ERSPAN 把流量复制到分析口，用 Wireshark 抓包看报文内容——这是定位协议交互问题的终极手段，前面在 DPDK 资料里讲过 extcap 抓包接口，思路一致。
- **遥测**：INT（带内网络遥测）让报文携带路径状态，sFlow 提供全网流量画像，适合长期观测而非单点排障。

下面用一段示意命令序列，展示一次"ping 不通"的典型排查流程。这不是任何真实平台的命令集，具体语法需对照所用 NOS 核验。

```text
# 工程理解示意：ping 不通的分层排查命令序列（非真实 NOS 接口）
show interfaces status                          # 1. 端口是否 up
show interfaces counters errors                # 2. 有无 CRC 等错误
show vlan brief                                 # 3. VLAN 与端口归属是否正确
show mac address-table address BB:BB:BB:BB:BB:BB # 4. 是否学到对端 MAC
show ip route 192.168.2.0                       # 5. 目标网段有无路由
show ip adjacency                               # 6. 邻接是否建立
show platform queue congestion                  # 7. 队列是否拥塞
monitor session 1 source interface Eth1/2       # 8. 必要时镜像抓包
```

对这段命令序列的判读：命令按"物理层到三层"的顺序排列——先看端口状态与错误计数（第 1、2 条），排除物理问题；再看 VLAN 归属与 MAC 表（第 3、4 条），排除二层问题；接着看路由与邻接（第 5、6 条），排除三层问题；最后看队列拥塞（第 7 条）并在必要时镜像抓包（第 8 条）。这条序列正是前面分层排障思路的落地。需要强调，不同 NOS 的命令语法差异很大，这里只用于建立排查顺序的概念，实际使用要查对应平台的命令手册。

### 4. 可观测性的工程要点

做好可观测性有几个容易被忽视的要点：

- **计数器的精度与读取开销**：高速端口上要线速不丢地计数，且读取时不能影响转发——这需要硬件支持，也是芯片能力的体现。
- **遥测的采样率取舍**：sFlow 等采样流开销低但精度有限，INT 精度高但要在报文里写状态，需按场景权衡。
- **时间同步**：跨设备的时延分析依赖精确时钟（PTP/1588），否则各设备的计数对不上。
- **基线（baseline）的重要性**：没有正常运行时的基线数据，异常时就难以判断"这个队列深度算不算高"。平时留存基线，排障时才有参照。

这些都指向一个结论：可观测性不是排障时才想起来的功能，而是要在网络设计和配置阶段就规划好的能力。

### 5. 小结与全书收束

## BASIC-19 三面协同、与具体芯片的关联及小结

### 1. 三个平面如何协同

三个平面不是孤立的，它们通过两条纽带协同工作：转发表项与配置。控制面把转发表项写入芯片存储，数据面逐包查这些表做决策；运维面采集转发过程中的计数器与遥测数据，反过来指导控制面调整表项与策略。下图把这条闭环画出来。

:::figure id=BASIC-19-01 | name=三平面协同闭环 | dir=LR
node n1 "控制与管理面<br/>下发转发表项与配置" blue
node n2 "数据面<br/>逐包查表转发" teal
node n3 "运维与遥测面<br/>采集计数器与遥测" amber
node n4 "表项存储<br/>两plane的纽带" blue
node n5 "反馈调整<br/>策略 路由 队列" purple
edge n1 -> n4 "写入"
edge n4 -> n2 "查表"
edge n2 -> n3 "产生状态"
edge n3 -> n5 "分析"
edge n5 -> n1 "优化配置"
:::

图中节点速览：n1 是控制与管理面，负责下发转发表项与配置；n2 是数据面，逐包查表转发；n3 是运维与遥测面，采集计数器与遥测数据；n4 是表项存储，是控制面与数据面之间的纽带；n5 是反馈调整环节，运维面分析数据后指导控制面优化配置。整张图是一个闭环：控制面写表、数据面查表、运维面看结果、再把结论反馈给控制面。这条闭环说明三个平面是协作关系，而非各自独立的功能堆砌。

### 2. 与两册具体芯片的对应关系

理解了基础框架，可以把前面两册具体芯片资料的差异化能力对应到框架中的格子：

| 功能平面 | Tomahawk 6 的强化点 | Teralynx 10 的强化点 |
|---|---|---|
| 数据面 | 102.4T 包缓冲架构、单次 VXLAN、高 Radix | 低时延可编程转发、Flex-forwarding |
| 控制面 | StrataXGS 软件兼容、成熟生态 | 开放 SDK、OCP SAI、SONiC 支持 |
| 运维面 | Cognitive Routing 2.0、快速故障检测、报文修剪 | Flashlight 细粒度遥测、微突发检测 |
| 可靠性 | 硬件链路故障切换 | 需按具体 SKU 核验 |

这张对照表说明：两款芯片的基础功能集合是一致的，差异只在于"哪些格子做得更深"。Tomahawk 6 用大缓冲与认知路由解决 AI 象流与微突发，Teralynx 10 用低时延与 Flashlight 打开差异化切入。理解了基础功能框架，再读具体芯片参数就能迅速定位"这个参数属于哪个平面、解决什么问题"。

### 3. 小结与交叉引用

1. **网络地基**：数据按分层逐层封装，帧与报文的字段决定转发依据；MAC 扁平、IP 分层、掩码定网段、网关连网段；一台交换机由 ASIC、CPU、端口与存储组成，CPU 与芯片靠报文上送协作。
2. **常见机制**：DHCP 四步下发地址、DNS 解析名字、CIDR 借还主机位做子网与聚合；路由表由直连、静态与动态协议填充；VRRP 靠免费 ARP 刷新网关切换；IPv6 的 NDP 与 SLAAC、VRF 的三层多租户补全了地址与隔离体系。
3. **网络架构**：Spine-Leaf 两层 Clos 让任意两叶恒两跳，配合三层 ECMP 做到无收敛；收敛比决定东西向是否卡在带宽上，拓扑直接推动高 Radix、强哈希、深缓冲与快速收敛的芯片需求。
4. **本质**：交换芯片用硬件在纳秒级完成"查表—搬运—排队—改写"，功能与软件转发同类，差别在执行方式的彻底硬件化。
5. **框架**：全部基础功能归为三个平面——数据面（逐包处理）、控制与管理面（表项配置）、运维与遥测面（可见性与安全）。
6. **数据面**：解析、查表、缓冲、调度、改写、组播复制是固定主路径；查表容量与速率、缓冲架构、转发模式是核心指标。
7. **L2/L3 流水线**：L2 按 MAC 走"学习—查 FDB—泛洪判定—改写"；L3 按 IP 走"LPM 查表—邻接解析—TTL/校验和改写"，二者在一次转发中串联协同，表项分别对应 FDB 与 FIB 加邻接表。
8. **进阶转发**：负载均衡用五元组哈希在 ECMP/LAG 里选路；广播按 VLAN 泛洪、组播按成员表硬件复制；VXLAN 用 MAC-in-UDP 把二层架到三层之上，靠 VTEP 与 VNI 隔离租户，封装需硬件卸载。
9. **解析与可编程**：解析器逐层识别协议头并抽取查找键，是数据面的入口约束；固定功能、可配置解析与可编程匹配—动作表三档各有取舍，高端芯片走硬化加可编程的混合路线。
10. **隧道全景**：VXLAN 因固定头与固定端口成为事实标准；underlay 按外层转发、overlay 按 VNI 加内层地址转发；分布式网关的 single-pass 能力是隧道性能分水岭。
11. **贯穿实例**：一次 ping 串起 ARP 泛洪、MAC 学习、查表转发、网关路由与改写，让各章概念连成一条完整时序。
12. **QoS**：分类、监管、排队、调度、拥塞控制构成五段流水线；信任边界决定用谁的标记，标记最终映射到内部队列，ECN 与 PFC 支撑无损网络。
13. **表项与查找引擎**：精确匹配用哈希加 SRAM、LPM 与 ACL 用 TCAM，匹配语义越复杂容量越小；表项分层与溢出决定性能是否塌陷；容量需按五类分别预算，更新原子性决定收敛速度。
14. **控制面**：表项下发要避免半新半旧的中间状态，先写后备再原子切换是常用做法；BFD 硬件卸载与硬件保护切换负责毫秒级故障兜底，SDK 成熟度与 SAI 完备性是落地关键。
15. **运维面**：计数器靠分布、批量更新与快照做到线速无干扰；遥测从 SNMP 轮询走向亚秒级推流与结构化数据模型，镜像、INT、可靠性与安全共同让网络可见可控。
16. **物理层与时钟**：PAM4 缩小噪声容限，靠均衡、眼图与 FEC 换取可用带宽；光模块按距离与波长选型；PTP 的硬件时间戳与透明时钟是纳秒级测量与对齐的前提。
17. **进阶协议**：生成树靠阻塞冗余链路防环，EVPN 作为 VXLAN 控制面同步主机位置，PFC 加 DCQCN 实现无损，端口安全层层递进防欺骗。
18. **协同与排障**：控制面写表、数据面查表、运维面反馈，三面连成闭环；排障按分层定位、分段排查，用表项、计数器与镜像验证。
