# 交换芯片技术资料 · 交换芯片基础知识总纲

## BASIC-01 网络与交换机基础：从分层到整机

在讲交换芯片怎么转发之前，先把"被转发的东西"和"装它的机器"讲清楚。这一章是全书的地基：如果你还不清楚一个以太网帧长什么样、IP 地址和 MAC 地址各管什么、一台交换机里到底有哪些部件，那么后面讲的 FDB、LPM、TCAM 都只是名词。本章用四节补齐这些前置知识。

### 1. OSI 与 TCP-IP 分层：数据如何被层层封装

网络通信的本质是把数据一层层包起来、送出去，再一层层拆开。业界用两个模型描述这件事：OSI（开放系统互连）七层模型是教学用的参考框架，TCP/IP 四层模型是实际互联网使用的协议栈。两者可以这样对应——TCP/IP 的应用层对应 OSI 的应用层、表示层、会话层；传输层对应传输层；网际层对应网络层；网络接口层对应数据链路层和物理层。

对交换机学习者，真正需要记住的是**每一层给数据加了什么头、这个头被谁读取**：

- **应用层**：产生要传的数据，例如 HTTP 请求、DNS 查询。交换机不关心这一层的内容（除非做深度包检测）。
- **传输层**：加上 TCP 或 UDP 头，写入源端口、目的端口。端口用来区分同一台主机上的不同应用——80 是网页、443 是加密网页、53 是域名解析。交换机做负载均衡哈希时用的五元组，就有这两个端口。
- **网络层**：加上 IP 头，写入源 IP、目的 IP、TTL。路由器和三层交换机读这个头决定往哪个网段转发。
- **数据链路层**：加上以太网头，写入源 MAC、目的 MAC、可能的 VLAN 标签。二层交换机只认这一层——这是它得名"二层"的原因。
- **物理层**：把 bit 变成电信号或光信号，通过网线或光纤传出去。SerDes 就工作在这一层。

这个"层层加头"的过程叫**封装（encapsulation）**，接收端反向剥掉叫**解封装（decapsulation）**。一个关键结论是：每一层只看自己那层的头，下层对上层透明。二层交换机读以太网头就够了，不需要理解 IP；三层交换机读 IP 头，但也不会去解析 HTTP。理解这一点，就能明白为什么交换芯片的解析引擎（parser）只要识别到某几层就能做转发决策。下图把封装层次画出来。

### 2. 以太网帧与 IP 报文：交换芯片真正看到的东西

协议栈是抽象的，交换芯片实际处理的是一个个具体的帧。以太网帧以 7 字节前导码和 1 字节帧起始定界符开始，随后是 6 字节目的 MAC、6 字节源 MAC；如果带 VLAN，则插入 4 字节的 802.1Q 标签（其中 12 位是 VLAN ID，这正是 VLAN 最多只有 4096 个的原因）；接着 2 字节类型字段指明载荷协议（0x0800 表示 IPv4，0x86DD 表示 IPv6）；然后是 46 到 1500 字节的载荷；最后 4 字节帧校验序列（FCS）用于检错。

IP 报文紧接在以太网头之后。IPv4 头至少 20 字节，关键字段包括：版本与首部长度、总长度、TTL（每过一跳减一）、协议号（6 为 TCP、17 为 UDP）、源 IP 与目的 IP。交换芯片在三层转发时要读的正是这些字段——查路由表用目的 IP，改写时用 TTL，区分协议用协议号。

这里有一个容易被忽略的细节：**帧长是有限制的**。标准以太网的最大传输单元（MTU）是 1500 字节，超过就要分片（IPv4 支持分片，IPv6 通常由源端避免）。VXLAN 这类隧道封装会额外增加约 50 字节开销，所以 underlay 网络常把 MTU 调到 1600 以上，否则封装后的报文会被分片或丢弃——这是讲解 VXLAN 时经常踩的坑。下表把帧和报文中与转发相关的关键字段列出来。

| 层级 | 关键字段 | 长度 | 被谁读取 | 转发中的用途 |
|---|---|---|---|---|
| 以太网 | 目的 MAC | 6 字节 | 二层交换机 | 查 MAC 表决定出口 |
| 以太网 | 源 MAC | 6 字节 | 二层交换机 | 学习，写入 MAC 表 |
| 以太网 | VLAN ID | 12 位 | 二三层交换机 | 区分二层域、隔离广播 |
| IPv4 | 目的 IP | 4 字节 | 三层交换机/路由器 | 查路由表做 LPM |
| IPv4 | TTL | 1 字节 | 三层设备 | 递减防环，为 0 丢弃 |
| 传输层 | 目的端口 | 2 字节 | 负载均衡/ACL | 哈希选路、策略匹配 |

理解字段与用途的对应关系很重要：后面讲到 L2 查表用 MAC、L3 查表用 IP、负载均衡哈希用五元组、TTL 递减要重算校验和，都能在这张表里找到依据。芯片的解析引擎做的事，本质上就是从帧里把这些字段抽出来，组成查表的键。

### 3. MAC 地址、IP 地址、子网与网关

地址体系是转发决策的基础，三者分工不同，初学者最容易混淆。

**MAC 地址**是烧在网卡上的 48 位物理地址，写成六组十六进制数，如 `00:11:22:33:44:55`。它在同一个二层域（同一个 VLAN）内有效，用来回答"这个帧该交给本网段的哪块网卡"。MAC 地址是扁平的、没有层次，因此无法像 IP 那样做聚合——这也是二层转发表只能精确匹配、规模受限的原因。

**IP 地址**是 32 位逻辑地址（IPv4），写成点分十进制，如 `192.168.1.10`。它是分层的，由网络位和主机位两部分组成，靠子网掩码区分。分层带来两个好处：可以做路由聚合（一条路由覆盖一个网段），可以在不同网段复用私有地址。三层转发查的正是目的 IP。

**子网掩码**告诉我们 IP 地址里哪几位是网络位。例如 `255.255.255.0`（写作 /24）表示前 24 位是网络号，后 8 位是主机号。`192.168.1.10/24` 与 `192.168.1.20/24` 属于同一子网，可以直接二层通信；`192.168.2.10/24` 就是另一个子网，必须经过网关。

**网关**是连接不同网段的设备接口地址。主机发现目的 IP 不在本地子网时，会把帧的目的 MAC 写成网关的 MAC，请网关代转发。前面讲 L2/L3 协同时提到的 SVI（交换虚拟接口），就是交换机上充当网关的接口——它的 MAC 让芯片知道"这个帧要交给三层处理"。

一次完整判断可以概括为：拿目的 IP 与自己的掩码做按位与，若结果等于本子网网络号，就二层直连（ARP 找对方 MAC）；否则交给网关（ARP 找网关 MAC）。下面的伪代码把这个判断写出来，它正是主机发包前的必经步骤，也是理解"为什么 ARP 请求是广播"的钥匙。

```text
# 工程理解伪代码：主机判断目的地址是否在本地子网（非真实系统接口）
dst_ip   = 192.168.2.10
my_ip    = 192.168.1.10
mask     = 255.255.255.0                     # /24
if (dst_ip & mask) == (my_ip & mask):
    arp_target = dst_ip                      # 同子网：直接找目的主机
else:
    arp_target = gateway_ip                  # 跨子网：找网关
dst_mac  = arp_resolve(arp_target)           # 广播 ARP 请求，单播应答
send_frame(dst_mac, dst_ip)                  # 用解析到的 MAC 封装并发送
```

对这段伪代码的判读：`dst_ip & mask` 与 `my_ip & mask` 分别算出目的与本机所在的网络号，相等说明在同一子网。同子网时 `arp_target` 是目的主机本身，跨子网时是网关——这一步决定了后续 ARP 请求问的是谁。`arp_resolve` 内部会发一个目的 MAC 为全 F 的广播帧，因为此时还不知道目标 MAC；应答则是单播。最后用解析到的 MAC 封装帧。这段伪代码解释了两个常见现象：arp 请求为什么是广播，以及为什么跨网段通信的第一跳 MAC 是网关的而不是最终目的主机的。

### 4. 一台交换机由什么组成

到目前为止我们一直在说"芯片怎么转发"，但一台能插网线、能配置的交换机远不止一颗芯片。理解整机组成，才能把芯片知识落到真实设备上。

一台典型的盒式交换机包含这些部件：**交换 ASIC** 是核心，负责线速转发，就是本资料的主角；**CPU（控制面处理器）** 跑网络操作系统和协议栈，负责处理不能由硬件转发的报文（如 ARP 请求、路由协议 hello）以及响应用户配置；**端口模块与光模块** 完成光电转换与 SerDes 串行化；**片外存储器** 存放 MAC 表、路由表等大容量表项和报文缓冲；**管理接口**（管理网口、Console、USB）用于带外管理。

这里要建立一个重要概念：**CPU 与 ASIC 的分工**。绝大多数数据报文由 ASIC 直接转发，CPU 不参与——这叫"硬件转发"。但有些报文必须交给 CPU，例如上送的 ARP 请求、未知协议报文、需要软件处理的控制协议——这叫"punt（上送）"或"软件转发"。如果攻击流量把大量报文逼上 CPU，控制面就会被淹没，所以要配置 CoPP（控制面限速）保护 CPU。前面在运维面提到 CoPP，这里给出了它存在的根本原因。下图把整机组成画出来。

图中节点速览：n1 是交换机整机的总纲；n2 是交换 ASIC，负责线速转发，是全书主角；n3 是 CPU 控制面，运行协议栈与响应配置；n4 是端口与光模块，完成光电转换；n5 是片外存储，存放表项与缓冲；n6 是管理接口，用于带外管理；n2 与 n3 之间标出"报文上送"，表示需要软件处理的报文会从 ASIC 交给 CPU。整张图说明芯片只是整机的一部分，CPU 与芯片通过上送通道协作。

整机视角还引出两个常见形态：**盒式交换机**固定端口、成本低，常用于接入层；**框式交换机**由主控板、线卡、交换网板组成，端口密度高、可冗余，用于核心层。两者转发原理相同，区别在规模与可靠性。白盒交换机则指硬件与网络操作系统解耦、可自由安装 NOS（如 SONiC）的机型，这正是 SAI 抽象层要解决的问题。

### 5. 小结：把地基与后面的章节连起来

本章建立了四块地基，后面每一章都会用到：

1. **分层与封装**：帧的每一层头都被特定的设备读取——这是解析引擎只识别若干层就能转发的依据。
2. **字段与用途**：目的 MAC 用于二层查表，目的 IP 用于三层 LPM，端口用于哈希，TTL 用于防环——这是查表键设计的依据。
3. **地址体系**：MAC 扁平、IP 分层、掩码定网段、网关连网段——这是 L2/L3 协同判断的依据。
4. **整机组成**：ASIC 转发、CPU 控制、两者靠上送协作——这是控制面与数据面分工的依据。

带着这四块地基再回头看"交换芯片用硬件在纳秒级完成查表—搬运—排队—改写"，每个词就都有了具体所指。下一章从交换芯片的一句话本质讲起，正式进入正题。


## BASIC-02 交换芯片是什么：一句话本质与三大功能平面

### 1. 一句话本质

交换芯片（switch ASIC）是一种专用集成电路，它的本质是用硬件在纳秒级完成"查表—搬运—排队—改写"这一串动作：把报文从正确的入口端口搬到正确的出口端口，并在搬运过程中做到不丢、不乱、可管。

要理解它和通用 CPU、和路由器软件转发的区别，关键不在功能种类的多少——它们要做的判断其实差不多——而在执行方式。交换芯片把这些判断固化成硅片上的流水线，用片上表项存储转发表，用硬件逻辑并行查表，每个报文以线速（端口满速率）通过，不经过软件中断、不占用通用处理器周期。正是这种"功能不变、执行方式彻底硬件化"的定位，决定了它的一切设计取舍：能不能线速、查表容量多大、缓冲多深、时延多低，都是这同一件事的不同侧面。

一个常见误解是"交换芯片功能比路由器少"。实际上现代高端交换芯片支持的协议与功能已经非常丰富——二层交换、三层路由、隧道封装、组播、质量控制、遥测、安全加密一应俱全。真正的差别是：路由器更强调控制面的协议灵活性与复杂路由计算，交换芯片更强调数据面的线速吞吐与确定性时延。两者是"同一个功能集合，不同的实现重心"。

### 2. 三大功能平面

把交换芯片的全部基础功能按"是否处理每一个报文"来划分，可以归成三个平面，这是理解整份资料的组织框架：

1. **数据面（data plane）**：每一个报文经过芯片时都要执行的处理。包括报文解析、查表转发、缓冲与交换架构、转发模式选择、调度与拥塞管理、报文改写、组播复制。这是交换芯片的"主业"，也是衡量性能的核心。
2. **控制与管理面（control/management plane）**：不碰每一个包，但决定数据面怎么转发。包括转发表项的下发与老化、SDK 与驱动、寄存器访问、与网络操作系统的对接（SAI）。这是"大脑"。
3. **运维与遥测面（operations/telemetry plane）**：让网络状态可见、可控、可恢复。包括计数器统计、流量镜像、带内网络遥测与采样流、可靠性保护机制、安全与加密。这是"眼睛和免疫系统"。

### 3. 为什么按平面理解很重要

初学时容易把交换芯片的功能当成一长串互不相干的清单去背——MAC 学习、最长前缀匹配、VXLAN、PFC、ECN、MACsec……清单越背越长，却记不住彼此关系。按平面组织的好处是：任何一个具体功能，都能立刻归位到"它是处理包的、配置表的、还是看状态的"。

更重要的是，这个框架能解释两册具体芯片资料的差异。后面会看到，Tomahawk 6 的差异化能力集中在数据面（缓冲吞吐）与运维面（自适应路由、快速故障检测），而 Teralynx 10 的差异化集中在数据面（低时延可编程转发）与运维面（Flashlight 遥测）。它们都没有跳出这三个平面，只是在同一框架的不同格子里做得更深。理解了框架，再看具体芯片参数就不会迷失在数字里。

edge n4 -> n5 "出队决策"
edge n5 -> n6 "发送"
:::

图中节点速览：n1 是入口端口，完成收包与 SerDes 串行/并行转换；n2 是报文解析，识别各层协议头并提取查表字段；n3 是查表转发，决定报文去往哪个出口；n4 是交换矩阵，负责缓冲与把报文从入口搬移到出口；n5 是调度与拥塞处理，含排队、报文改写与组播复制；n6 是出口端口，完成发包。整张图是单向的主路径，表达"每个报文都要依次经过这五段处理"，后面各小节逐一展开每一段。

### 2. 逐段展开：从解析到改写

**报文解析（parser）**：芯片识别以太网、VLAN、IPv4/IPv6、TCP/UDP 以及各种隧道头，提取出供查表使用的字段——目的 MAC、目的 IP、五元组、DSCP 等。解析的深度决定了后面能查哪些表、能做哪些策略，因此它是数据面能力的"入口约束"：解析不到的字段，后续就无从判断。

**查表转发（lookup）**：这是数据面的核心。二层查 MAC 地址表做桥接，三层做最长前缀匹配（LPM）路由，再叠加 ACL/TCAM 做策略过滤与优先级判定。查表命中后得到"去哪个出口、做什么动作"。查表容量与查表速率是芯片的关键指标——表项装不下就要溢出到慢速存储，速率跟不上就达不到线速。

**缓冲与交换架构（fabric + buffer）**：当多个入口同时涌向同一个出口时，报文必须暂存并接受仲裁。这里分共享内存与分布式缓冲（VOQ，虚拟输出队列）两大流派：前者所有端口共享一片缓冲池，利用率高但存在队头阻塞风险；后者按目的出口分队列，抗阻塞好但需要更大片上存储。这一层直接决定芯片的抗微突发能力与时延表现，也是不同高端芯片拉开差距的主战场。

**转发模式**：cut-through（转发模式）收到目的地址就直接转发，时延最低但会转发坏包；store-and-forward（存储转发）收完整包并校验后再转，可靠性高但时延多一个包长。现代芯片多按场景自适应或按端口配置。

**调度与拥塞管理**：队列调度决定哪个队列先发（严格优先级、加权轮转 WRR 等）；拥塞避免用 RED/WRED、ECN 在队列将满时提前标记；无损流控用 PFC（基于优先级的流控）在以太网上实现不丢包。AI 网络里的 RoCEv2 能否做到零丢包，几乎全靠这一层。

**报文改写（rewrite）**：出口处修改报文——减 TTL、重写 MAC 地址、增删或替换 VLAN 标签、VXLAN/GRE 隧道的封装与解封装、以及把报文复制一份做镜像。

**组播与复制**：一份报文要发往多个出口时，由硬件按组播树复制，避免逐端口软件拷贝带来的吞吐损失。

### 3. 三层转发表的分工示意

下面用示意性的查表伪代码，把二层、三层、ACL 三种表的分工与先后关系讲清楚。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：一次转发的查表顺序（非真实 SDK 接口）
pkt     = ingress(port)
hdr     = parse(pkt)                       # 解析各层协议头
l2      = lookup_mac(hdr.dst_mac)          # 二层：查 MAC 表
l3      = lookup_lpm(hdr.dst_ip)           # 三层：最长前缀匹配
policy  = lookup_acl(hdr.five_tuple)       # 策略：ACL/TCAM 过滤与优先级
if policy.deny:
    drop(pkt)                              # 命中拒绝策略则丢弃
egress_port = select(l2, l3, policy)       # 综合三者决定出口
enqueue(egress_port.queue, pkt)            # 入出口队列，等待调度
```

对这段伪代码的判读：三类查表不是竞争关系而是互补关系——`lookup_mac` 负责同一二层域内的桥接，`lookup_lpm` 负责跨网段的路由，`lookup_acl` 负责在转发之上叠加策略（过滤、限速、优先级）。`policy.deny` 的检查放在转发决策之前，意味着策略判定优先于转发——这是交换芯片的通用原则。最后 `enqueue` 把报文交给出口队列，从这里开始进入调度与拥塞管理的范畴。需要强调，真实芯片的查表顺序可能因架构而异，有的会把 ACL 并行查、有的会多次通过，这段伪代码只用于建立概念分工。

### 4. L2 转发流水线：从解析到桥接决策

上一节把二层、三层、ACL 三类查表放在同一张图里讲分工，本节开始逐条深入真实芯片里的转发流水线（pipeline）。先看二层，也就是桥接（bridging）。二层转发的本质只有一句话：按目的 MAC 地址，把报文从正确的端口发出去。围绕这句话，流水线要依次完成四件事——学习（learn）、查表（lookup）、泛洪判定（flood decision）与出口决策（egress decision）。

**第一步：源 MAC 学习（learning）**。报文进入端口后，芯片先取源 MAC 与入端口（通常还有 VLAN ID），写入一张 MAC 地址表（也叫 FDB，Forwarding Database）。这张表记录"某个 MAC 在哪个端口上"，是后续转发查表的依据。学习是自动完成的——交换芯片 observing 到源地址就记住，无需控制面逐条下发。表项带老化时间，长时间不见该 MAC 的流量就会被清除，以免表项被无效条目占满。

**第二步：目的 MAC 查表**。取报文的目的 MAC 查同一张表，命中结果告诉芯片这个 MAC 在哪个端口。这里的查找键通常是"VLAN + MAC"，因为不同二层域里可以有相同的 MAC 地址，必须靠 VLAN 区分。查表用哈希（hash）而非逐条比较，因此即使表项有几十万条，也能在一个时钟周期内得到结果。

**第三步：泛洪判定**。并不是每个目的 MAC 都能查到。命中（known unicast，已知单播）就直接发往对应端口；未命中（unknown unicast，未知单播）就要向同 VLAN 的所有其他端口泛洪；广播与组播同样需要复制多份。泛洪是二层转发的兜底机制——它保证"不知道往哪发"时报文仍能到达，但也意味着二层域里广播域过大就会浪费带宽，这正是 VLAN 要划分广播域的原因。

**第四步：出口决策与改写**。确定出口集合后，报文被复制到各个出口队列。出口处要做改写：剥离或添加 VLAN 标签、按出口端口的 tagging 模式处理、可能还要做 ACL 与 QoS 标记。下图把这条二层流水线画出来。

node n3 "目的 MAC 查表<br/>键=VLAN+MAC" teal
node n4 "泛洪判定<br/>命中或泛洪" amber
node n5 "已知单播<br/>单端口转发" green

图中节点速览：n1 是入口端口，负责收包与解析；n2 是源 MAC 学习，把"源 MAC + 端口 + VLAN"写入 FDB 表项；n3 是目的 MAC 查表，查找键为 VLAN 加 MAC；n4 是泛洪判定，根据是否命中决定后续路径；n5 是已知单播分支，命中后单端口转发；n6 是未知单播或组播分支，未命中后向多端口复制；n7 是出口改写，处理 VLAN 标签与标记。整张图是二层转发的四步流水线——学习、查表、泛洪判定、出口改写，两条分支在出口汇合。

下面用示意伪代码把二层转发流水线串起来，重点是学习、查表与泛洪判定三者的先后关系。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：L2 桥接转发流水线（非真实 SDK 接口）
pkt       = ingress(port)                         # 入口收包
hdr       = parse_l2(pkt)                          # 解析二层头，取 src/dst MAC 与 VLAN
fdb.learn(hdr.src_mac, vlan, port)                 # 源 MAC 学习，刷新老化计时
hit       = fdb.lookup(vlan, hdr.dst_mac)          # 目的 MAC 查表，键为 VLAN+MAC
if hit:                                            # 已知单播：定向转发
    egress_ports = [hit.port]
elif hdr.dst_mac.is_multicast:                     # 组播：按成员端口复制
    egress_ports = multicast_members(vlan, hdr.dst_mac)
else:                                              # 未知单播：同 VLAN 泛洪
    egress_ports = all_ports_in_vlan(vlan) - [port]
for p in egress_ports:                             # 逐个出口改写并入队
    enqueue(p.queue, rewrite_l2(pkt, p))
```

对这段伪代码的判读：流程严格按"先学习、后查表、再判定"的顺序——`fdb.learn` 用源 MAC 更新表项，`fdb.lookup` 用目的 MAC 查转发方向，二者的地址字段不同，不可颠倒。`if hit` 的分支体现已知单播的定向转发；`elif` 处理组播，按成员端口复制而非盲目泛洪；`else` 兜底处理未知单播，向同 VLAN 除入端口外的所有端口泛洪。最后 `rewrite_l2` 对每个出口单独改写——因为不同端口的 VLAN tagging 模式可能不同。需要说明，真实芯片里学习与查表往往在同一查找引擎里完成，泛洪决策也会结合生成树状态（阻塞端口不转发），这段伪代码只用于建立流水线的概念顺序。

### 5. L3 路由流水线：最长前缀匹配与邻接解析

二层按 MAC 转发，三层（IP 路由）则按 IP 地址转发，流水线更复杂。核心变化是：目的地址从定长的 MAC 变成变长前缀的 IP，查表方式从精确哈希匹配变成最长前缀匹配（LPM，Longest Prefix Match）；转发决策也不止"去哪个端口"，还要决定"交给哪个下一跳"。三层流水线可以拆成五步——入口处理、路由查表、邻接解析、TTL 与校验和改写、出口转发。

**第一步：入口处理（ingress processing）**。报文进来后先做合法性检查：IP 头校验和、TTL 是否为零、是否为本机需要处理的控制协议报文。需要上送控制面的报文（如 ARP 请求、路由协议 hello）会被"punt"到 CPU，不进入硬件转发路径。

**第二步：路由查表（LPM lookup）**。取目的 IP，在路由表（FIB，Forwarding Information Base）里找最长匹配的前缀。之所以叫"最长前缀"，是因为可能有多条规则同时匹配（如 10.0.0.0/8 与 10.1.0.0/16 都匹配 10.1.2.3），要选掩码最长的那条。LPM 在硬件里通常用 TCAM 实现——TCAM 支持"掩码匹配"且所有表项并行比较，一个周期出结果，但功耗与成本高，容量也有限。这是三层表项容量通常小于二层 MAC 表容量的根本原因。

**第三步：邻接解析（adjacency / ARP-ND resolution）**。LPM 命中的结果不是直接的出口端口，而是"下一跳 IP"。要真正发包，还得知道下一跳的 MAC 地址——这靠邻接表（adjacency table）完成，它是 ARP（IPv4）或 ND（IPv6）解析结果的硬件缓存。查到下一跳 MAC 后，才能构造二层帧头。

**第四步：TTL 递减与校验和改写**。每经过一跳路由器，IP 头里的 TTL 要减一，减到零就丢弃（防止环路）；因为 TTL 变了，IP 头校验和必须重算。这两步都是每包必做的硬件改写动作，是三层转发相对二层转发的主要额外开销。

**第五步：出口转发**。按下一跳对应的端口入队，重写二层目的 MAC 为下一跳 MAC、源 MAC 为出口端口 MAC，然后发送。下图把这条三层流水线画出来。

node n2 "LPM 查表<br/>最长前缀匹配" teal
node n3 "邻接解析<br/>下一跳转 MAC" teal
node n4 "TTL递减<br/>重算校验和" amber
node n5 "二层头改写<br/>目的与源 MAC" purple
node n6 "出口端口<br/>入队发送" green

edge n4 -> n5 "改写IP头"

图中节点速览：n1 是入口处理，完成报文校验与是否上送控制面的判定；n2 是 LPM 查表，按目的 IP 做最长前缀匹配；n3 是邻接解析，把下一跳 IP 换成下一跳 MAC；n4 是 TTL 递减与校验和重算；n5 是二层头改写，重写目的与源 MAC；n6 是出口端口，入队并发送。整张图是三层转发的五步流水线，与二层相比多出了 LPM 查表、邻接解析、TTL 与校验和改写这几段，这正是三层转发的额外成本所在。

下面的伪代码把三层路由流水线串起来，突出 LPM、邻接与改写三者的依赖顺序。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：L3 路由转发流水线（非真实 SDK 接口）
pkt       = ingress(port)
hdr       = parse_l3(pkt)                          # 解析三层头，取目的 IP
if hdr.ttl <= 1 or not checksum_ok(hdr):           # TTL 耗尽或校验错误
    drop_or_punt(pkt)                              # 丢弃或上送控制面
    return
nexthop   = fib.lpm_lookup(hdr.dst_ip)             # 路由表最长前缀匹配
if not nexthop:                                    # 无匹配路由
    drop_or_punt(pkt)
    return
dst_mac   = adjacency.lookup(nexthop.ip)           # 邻接表查下一跳 MAC
if not dst_mac:                                    # 邻接未建立，触发 ARP/ND
    punt_arp_request(nexthop.ip)
    return
hdr.ttl -= 1                                       # TTL 递减
hdr.checksum = recompute_checksum(hdr)             # 重算 IP 头校验和
set_l2_header(pkt, dst=dst_mac, src=port_mac)      # 改写二层头
enqueue(nexthop.port.queue, pkt)
```

对这段伪代码的判读：开头对 TTL 与校验和的检查体现三层入口的合法性验证，异常报文不能进入正常转发。`fib.lpm_lookup` 是全流水线最关键的一步，它返回的是下一跳而非最终端口——这是三层与二层查表的本质差别。`adjacency.lookup` 把下一跳 IP 解析成 MAC，查不到时 `punt_arp_request` 上送控制面发起 ARP/ND，说明数据面与控制面在此处协同。只有拿到下一跳 MAC 后，才做 TTL 递减、校验和重算与二层头改写，最后入队。这段伪代码把三层转发的"查路—找邻—改写"三段依赖讲清楚，真实芯片还会在其中插入 ECMP（等价多路径）选路、VRF（虚拟路由转发）隔离等步骤，具体实现需以数据手册为准。

### 6. L2 与 L3 的协同：一次转发里谁先谁后

前面两节分别讲了二层与三层流水线，但一个真实报文往往同时涉及两者。理解它们如何协同，是读懂芯片转发行为的关键。这里要给一个常被混淆的结论：二层和三层不是二选一，而是一次转发中可能先后发生的两个阶段。

典型场景是"VLAN 间路由"（inter-VLAN routing）：主机 A 在 VLAN 10，主机 B 在 VLAN 20，A 要访问 B。报文从 A 发出时，目的 MAC 是网关（路由接口）的 MAC，源 MAC 是 A 的 MAC。芯片收到后，先按二层规则查表——发现目的 MAC 是本机网关 MAC，于是判定这不是纯二层桥接，而要进入三层路由。随后按目的 IP 做 LPM，查到下一跳，改写二层头后从 VLAN 20 的端口发出。所以一次报文经历了"二层查表判断 → 三层路由转发"的串联，而非只在某一层转发。

这也解释了一个常见疑问：为什么交换机要配 IP 地址（SVI，交换虚拟接口）？因为 SVI 的 MAC 就是网关 MAC，它的存在让芯片知道"哪些报文要交给三层处理"。没有它，同 VLAN 内可以直接二层桥接，跨 VLAN 就必须靠外部路由器。

那么表项资源怎么分配？二层查 MAC 表、三层查路由表与邻接表，它们是不同的硬件表，各有容量上限。设计时若三层表项不足，路由就要"溢出"到软件或更小容量的表，性能随之下降——这正是选型时要分别核对 MAC 表容量与 FIB 容量的原因。下表把二层与三层流水线的关键差异并列对照。

| 对比维度 | L2 桥接流水线 | L3 路由流水线 |
|---|---|---|
| 查表依据 | 目的 MAC（精确匹配） | 目的 IP（最长前缀匹配） |
| 核心表项 | MAC/FDB 表 | FIB 路由表 + 邻接表 |
| 硬件实现 | 哈希查找，容量大、成本低 | TCAM 并行匹配，容量小、成本高 |
| 报文改写 | VLAN 标签、二层头 | TTL、校验和、二层头 |
| 典型耗时 | 更短，路径固定 | 更长，多段查表与改写 |
| 是否改 TTL | 不改，非 IP 层处理 | 递减，每跳必做 |

需要强调，上表的"耗时"与"容量"是架构层面的一般规律，具体数值因芯片而异；高端芯片通过把 L2/L3 查表放在同一查找引擎的不同阶段来压缩时延，实现"看起来像一次查表"的效果。下图把二三层协同的判定关系画出来，作为本节的收束。

:::figure id=BASIC-03-04 | name=L2 与 L3 转发协同判定 | dir=TB
node n1 "入口报文<br/>解析二层头" blue
node n2 "目的MAC<br/>是否本机网关" teal
node n3 "是：进入三层<br/>LPM与邻接" amber
node n4 "否：纯二层<br/>查MAC表桥接" green
node n5 "出口改写<br/>入队发送" purple
edge n1 -> n2 "取目的 MAC"
edge n2 -> n3 "是"
edge n2 -> n4 "否"
edge n3 -> n5 "路由转发"
edge n4 -> n5 "桥接转发"
:::

图中节点速览：n1 是入口报文，解析二层头取出目的 MAC；n2 是判定节点，检查目的 MAC 是否为本机网关 MAC；n3 是"是"分支，进入三层做 LPM 与邻接解析；n4 是"否"分支，按纯二层查 MAC 表桥接；n5 是出口改写与入队发送，两条分支在此汇合。整张图说明二层与三层是串联协同关系——先用二层判断报文是否要交给三层，再决定走哪条路径，最终都在出口改写后发出。

## BASIC-04 数据面进阶功能：负载均衡、组播广播与 VXLAN

前面两章讲的是"普通单播"怎么在二层和三层转发。现实网络里还有四类高频出现的转发形态：把流量摊到多条路径的负载均衡、一对多的广播与组播、以及把二层网络架到三层之上的 VXLAN 叠加。它们都跑在数据面，复用前面学到的解析、查表、改写流水线，只是查的表和改写的字段不同。本章逐一讲清楚。

### 1. 负载均衡：ECMP 与链路聚合

负载均衡（load balancing）解决的是"有多条路可走时，怎么把流量摊开"。网络里有两处最典型：

- **链路聚合（LAG，Link Aggregation）**：在二层把多条物理链路绑成一条逻辑链路，标准协议是 LACP（802.3ad）。对上层看是一条更粗的链路，带宽叠加且一条成员链路故障时其余顶上。
- **等价多路径（ECMP，Equal-Cost Multi-Path）**：在三层，当路由表对同一目的有多条开销相同的下一跳时，把流量分摊到这些路径。

两者实现机制几乎一样：用**哈希（hash）**选路。芯片把报文的五元组（源 IP、目的 IP、源端口、目的端口、协议）送进哈希函数，得到一个数，再对路径数取模，选中其中一条。用五元组而非随机，是为了让"同一条连接的所有包走同一条路径"——否则同一 TCP 流的包乱序到达，接收端要重排，性能反而下降。

这里有个经典难题：**大象流（elephant flow）**。少数大流占据带宽大头，哈希一旦把它们钉在同一条路径，就会出现"有的链路挤爆、有的空闲"。业界的应对是动态负载均衡（DLB）和 flowlet 切换——检测流中的空闲间隙（flowlet），在间隙处把后续流量换到轻载路径，既避开热点又不造成乱序。还有一致性哈希（resilient hashing），让成员数变化时只有少量流需要重新映射，减少扰动。

需要分清"网络级负载均衡"和"服务器级负载均衡"。ECMP/LAG 是无状态的：芯片不记连接，每个包独立哈希。而真正的服务器负载均衡（SLB）要有会话表，记住"这个连接发给哪台服务器"，还要做健康检查、NAT 改写——这通常由负载均衡器、智能网卡或专门设备承担，不在普通交换芯片的能力范围。下表把两种聚合方式对照。

| 对比维度 | 链路聚合 LAG | 等价多路径 ECMP |
|---|---|---|
| 工作层次 | 二层 | 三层 |
| 绑定对象 | 多条物理链路 | 多条等价路由下一跳 |
| 典型协议 | LACP（802.3ad） | OSPF/ISIS/BGP 等价路由 |
| 选路依据 | 五元组哈希 | 五元组哈希 |
| 故障收敛 | 成员口 down 后重分布 | 下一跳失效后重算 |
| 状态性 | 无状态，逐包哈希 | 无状态，逐包哈希 |

下面的伪代码把哈希选路讲清楚，重点是"同一条流固定走一条路径"。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：ECMP/LAG 哈希选路（非真实 SDK 接口）
pkt      = ingress(port)
key      = five_tuple(pkt)                       # 取五元组作为哈希键
h        = hash(key)                             # 芯片哈希引擎算出哈希值
if layer == "L2":
    members = lag.member_ports(group_id)         # LAG：取成员链路
else:
    members = route.ecmp_nexthops(prefix)        # ECMP：取等价下一跳
idx      = h % len(members)                      # 哈希取模选一条
forward(pkt, members[idx])                       # 同一条流固定选中同一条
```

对这段伪代码的判读：`five_tuple` 取出的键保证同一条连接的包哈希值相同，`h % len(members)` 因此把它们送到同一成员口，避免乱序——这是哈希选路必须用流字段而非随机数的原因。`if layer` 分支说明 LAG 与 ECMP 只是取的成员集合不同（成员口 vs 下一跳），选路算法一致。需要指出，成员数变化（链路故障或新增）会让取模结果改变，部分流因此换路，这正是 resilient hashing 要缓解的扰动；这段伪代码只用于建立无状态哈希分发的概念。

### 2. 广播与组播：一对多的两种形态

一对多转发有两种：广播和组播。它们的差别在"发给谁"。

**广播（broadcast）**发给二层域里的所有人。目的 MAC 是全 F（`FF:FF:FF:FF:FF:FF`），芯片收到后向同 VLAN 的所有其他端口泛洪。ARP 请求、DHCP 发现都靠广播——因为此时还不知道对方在哪。广播的代价是"每个人都要处理"，且广播域（通常等于 VLAN）越大，浪费越多；环路里的广播会无限复制形成广播风暴，所以要靠生成树和风暴控制来约束。

**组播（multicast）**只发给"加入了这个组"的人。目的 IP 是 D 类地址（224.0.0.0/4），映射到组播 MAC（`01:00:5e` 开头）。主机通过 IGMP（IPv4）或 MLD（IPv6）告诉网络自己想加入哪个组。

组播在二层和三层的处理不同：

- **二层组播：IGMP Snooping**。交换机监听主机与路由器之间的 IGMP 报文，建立"组地址 → 成员端口"表。这样组播帧只发给真正加入组的端口，而不是在 VLAN 里泛洪。没有 Snooping 时，组播会被当成广播处理——这是很多网络组播性能差的根源。
- **三层组播：PIM**。路由器之间跑 PIM 协议建立组播分发树，维护 (S,G) 或 (*,G) 组播路由表，并用 RPF（反向路径转发）检查防止环路。

对交换芯片而言，组播的关键能力是**硬件复制**：一份报文进入芯片后，由复制引擎在出口复制成多份，而不是靠软件逐端口拷贝。复制能力（最大副本数、复制带宽）是芯片的一项指标，AI 集群的集合通信也在重新重视组播。下表把单播、广播、组播三者并列对照。

| 维度 | 单播 | 广播 | 组播 |
|---|---|---|---|
| 目的 | 一个接收者 | 二层域内全部 | 加入组的成员 |
| 目的地址 | 单播 MAC/IP | 全 F MAC | D 类 IP / 01:00:5e MAC |
| 芯片动作 | 查表定向转发 | 泛洪到所有端口 | 按成员表复制 |
| 典型应用 | 常规通信 | ARP、DHCP | IPTV、集合通信 |
| 成员管理 | 无需 | 无需 | IGMP/MLD、PIM |

### 3. VXLAN：把二层架到三层之上

VXLAN 解决三个问题：VLAN 只有 4096 个标识不够多租户用；虚拟机迁移时二层域要能跨三层物理网络延伸；租户之间要隔离。它的做法是**MAC-in-UDP 封装**：把原始二层帧整个塞进一个 UDP 报文里，在物理网络（underlay）上传输，逻辑上形成一张叠加网（overlay）。

几个关键概念：

- **VTEP（VXLAN Tunnel Endpoint）**：封装和解封装的端点，通常在网络设备或服务器虚拟交换机上。源 VTEP 把二层帧封装，目的 VTEP 解封装还原。
- **VNI（VXLAN Network Identifier）**：24 位标识，能表示约 1600 万个逻辑网络，彻底解决 VLAN 数量不够的问题。封装时 VNI 写在 UDP 载荷里的 VXLAN 头中。
- **外层 UDP 端口 4789**：这是 VXLAN 的知名端口，underlay 网络按外层 IP 头做普通三层路由即可，无需感知内层二层帧。
- **BUM 流量**：Broadcast、Unknown unicast、Multicast 三类流量的统称。VXLAN 里这些流量要靠头端复制（ingress replication，源 VTEP 复制多份分别封装）或 underlay 组播来送达——这是 VXLAN 设计里的一个重点和难点。

跨 VNI 通信要靠**分布式网关**（IRB，Integrated Routing and Bridging）：网关功能下沉到每台 VTEP，报文在本机完成"从 VNI A 路由到 VNI B"，避免绕行集中网关。

对交换芯片来说，**VXLAN 封装解封装必须硬件线速完成**，否则叠加网络会成为性能瓶颈。芯片要能在一次查表里同时用 VNI 和内层 MAC 做转发决策（single-pass VXLAN），这是高端芯片的卖点——前面两册具体芯片资料里提到的"单次 VXLAN"能力，本质就是这一节讲的硬件卸载。下表把 VLAN 与 VXLAN 对照。

| 对比维度 | VLAN | VXLAN |
|---|---|---|
| 标识位数 | 12 位（4096 个） | 24 位（约 1600 万） |
| 封装 | 802.1Q 标签 | MAC-in-UDP |
| 承载网络 | 二层 | 三层 underlay |
| 端点 | 无封装端点 | VTEP |
| 跨三层迁移 | 不支持 | 支持 |
| 硬件开销 | 加标签，很低 | 封装解封装，需卸载 |

下面的伪代码把 VXLAN 的封装与解封装讲清楚。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：VXLAN 封装与解封装（非真实 SDK 接口）
# 发送方向：源 VTEP 封装
frame    = l2_frame(src_mac, dst_mac, vlan)       # 原始二层帧
vni      = lookup_vni(vlan, dst_mac)              # 查表得到目的 VNI 与远端 VTEP
outer    = vxlan_encap(frame, vni=vni,            # 加 VXLAN 头（含 VNI）
                       udp_dst=4789,              # 外层 UDP 目的端口
                       src_ip=local_vtep, dst_ip=remote_vtep)
forward_underlay(outer)                           # 按外层 IP 在 underlay 路由
# 接收方向：目的 VTEP 解封装
inner    = vxlan_decap(outer)                     # 去掉外层头，还原二层帧
lookup_and_forward(inner.vni, inner.dst_mac)      # 按 VNI + 内层 MAC 转发
```

对这段伪代码的判读：发送方向先用 `lookup_vni` 由内层 VLAN 与目的 MAC 查到目标 VNI 和远端 VTEP 地址，再由 `vxlan_encap` 加上 VXLAN 头（写入 VNI）、外层 UDP 头（目的端口 4789）和外层 IP 头；`forward_underlay` 让封装后的报文按外层 IP 做普通三层转发，underlay 网络因此无需理解内层二层。接收方向 `vxlan_decap` 还原出原始帧，再按 `VNI + 内层 MAC` 转发——这正是一次查表同时用两个键的 single-pass 能力。需要说明，BUM 流量的处理不在单播路径里：广播或未知单播需要源 VTEP 把帧封装多份发给所有相关 VTEP，这段伪代码只覆盖单播 VXLAN 的关键路径。

### 4. 小结：四类功能在流水线里的位置

本章四类功能没有跳出第二章的通用流水线，它们是"查不同的表、改不同的字段"：

- **负载均衡**改的是"选哪条路径"——用五元组哈希在 ECMP 下一跳或 LAG 成员口里选一个，不查新表。
- **广播**不需要查表，按 VLAN 泛洪；**组播**查"组地址到成员端口"表，用硬件复制到多个出口。
- **VXLAN**在解析阶段多识别一层封装头，查表用"VNI + 内层 MAC/IP"，在改写阶段做封装或解封装。

## BASIC-05 贯穿式实例：一次 ping 的完整转发过程

前面几章把转发拆成解析、查表、缓冲、调度、改写等一段段来讲。分开讲便于理解，但也容易让学习者只见树木不见森林。这一章用一个最简单也最典型的场景——两台主机通过交换机通信——把碎片串成一条完整时序。读懂这一章，前面所有概念会第一次连成一条线。

### 1. 场景与拓扑

设定一个最小场景：主机 A（IP 为 192.168.1.10，MAC 为 AA:AA:AA:AA:AA:AA）和主机 B（IP 为 192.168.1.20，MAC 为 BB:BB:BB:BB:BB:BB）接在同一台二层交换机 SW1 上，同属 VLAN 10、同一网段 /24。A 执行 `ping 192.168.1.20`。我们把这个过程拆开，看看交换机里究竟发生了什么。

这里先明确一个前提：**主机 A 一开始并不知道 B 的 MAC 地址**。它只知道 B 的 IP。以太网帧必须填目的 MAC 才能发出，所以 A 的第一件事不是发 ping，而是想办法问出"B 的 MAC 是什么"。这个"问"的过程就是 ARP（地址解析协议），也是整个时序的第一步。下图把场景拓扑画出来。

### 2. 同网段转发：ARP 泛洪、MAC 学习与查表转发

现在按时间顺序走一遍。整个过程可以分成两大阶段——先用 ARP 找到 MAC，再用 ICMP 真正通信。

**阶段一：ARP 解析**

1. A 广播一个 ARP 请求："谁是 192.168.1.20？请告诉 192.168.1.10"。这个帧的目的 MAC 是全 F，源 MAC 是 A 的 AA。
2. 交换机从端口 1 收到这个帧。它做两件事：**学习**——把"源 MAC AA 在端口 1"写入 MAC 表；**查表**——目的 MAC 是全 F，是广播，于是在 VLAN 10 内向除端口 1 外的所有端口泛洪。
3. 主机 B 收到 ARP 请求，发现问的是自己的 IP，于是单播一个 ARP 应答："192.168.1.20 的 MAC 是 BB"，目的 MAC 是 AA。
4. 交换机从端口 2 收到应答，学习"源 MAC BB 在端口 2"；查表发现目的 MAC AA 已在表中对应端口 1，于是**单播**转发到端口 1，不再泛洪。
5. A 收到应答，得到 B 的 MAC，ARP 缓存里记下 192.168.1.20 → BB:BB:...。

注意这一步的关键：交换机在转发过程中**悄悄学会了两个 MAC 地址**，MAC 表从空表变成有两条表项。这就是第二章讲的"源 MAC 学习"在真实时序里的样子。

**阶段二：ICMP 通信**

6. A 构造 ICMP 回显请求（echo request），目的 IP 是 B，目的 MAC 是 BB，从端口 1 发出。
7. 交换机查 MAC 表，BB 命中端口 2，定向转发。这一次不再泛洪——因为已知单播。
8. B 收到请求，构造 ICMP 回显应答（echo reply），目的 MAC 是 AA，从端口 2 发出。
9. 交换机查表，AA 命中端口 1，定向转发回 A。
10. A 收到应答，ping 成功，显示往返时延。

下表把这十步中交换机的动作按阶段归拢，方便对照。

| 步骤 | 报文 | 目的 MAC | 交换机学习 | 交换机转发动作 |
|---|---|---|---|---|
| 1 | ARP 请求 | 全 F 广播 | 学到 A 在端口 1 | 泛洪到端口 2 |
| 2 | ARP 应答 | AA 单播 | 学到 B 在端口 2 | 查表命中，单播端口 1 |
| 3 | ICMP 请求 | BB 单播 | 无新表项 | 查表命中，单播端口 2 |
| 4 | ICMP 应答 | AA 单播 | 无新表项 | 查表命中，单播端口 1 |

这张表揭示了一个重要规律：**泛洪只发生在"不知道目的 MAC"时**。一旦通过源 MAC 学习建立了表项，后续全部是精确的单播转发。这也是为什么二层网络里 ARP 请求会泛洪、而正常数据流量不会——理解这一点，就理解了广播域大小为什么影响网络效率。

### 3. 跨网段转发：网关、路由与邻接

现在把场景变一变：主机 A（192.168.1.10/24）要 ping 主机 C（192.168.2.10/24），两者不在同一网段，中间由一台三层交换机（或路由器）R1 连接，R1 在 VLAN 10 的接口 IP 是 192.168.1.1，在 VLAN 20 的接口 IP 是 192.168.2.1。这里第一行判断就变了——A 用掩码一算，发现 C 不在本地子网，于是把帧交给网关。

跨网段时序如下：

1. A 发出 ARP 请求，但问的是**网关** 192.168.1.1 的 MAC，而不是 C 的。交换机学到 A 的 MAC，广播 ARP。
2. R1 的网关接口应答，给出自己的 MAC（记作 R1-MAC-A）。交换机学到 R1 该接口的 MAC。
3. A 构造 ICMP 请求，目的 IP 是 C，但**目的 MAC 是 R1-MAC-A**，发给网关。
4. R1 收到后进入三层转发：解析 IP 头，目的 IP 192.168.2.10 查路由表，LPM 命中直连网段 192.168.2.0/24；查邻接表得到 C 的 MAC；把 TTL 减一、重算 IP 校验和；把二层头改写为"源 MAC = R1 在 VLAN 20 的接口 MAC，目的 MAC = C 的 MAC"，从 VLAN 20 端口发出。
5. C 收到 ICMP 请求，回应的路径对称：C 把应答发给自己的网关 192.168.2.1，R1 再做一次三层转发回给 A。

这里出现了与同网段场景完全不同的几个动作，正是第三章 L3 流水线讲的内容：**目的 MAC 是网关**（触发三层处理）、**查路由表而不是 MAC 表**、**TTL 递减与校验和重算**、**二层头重写**。下面用一段伪代码把 R1 的三层转发决策写出来，与第三章的 L3 流水线伪代码对照着看。

```text
# 工程理解伪代码：网关 R1 对跨网段 ICMP 请求的转发（非真实 SDK 接口）
pkt       = ingress(port_vlan10)
hdr_l2    = parse_l2(pkt)
if hdr_l2.dst_mac == gateway_mac_vlan10:       # 目的 MAC 是本机网关 → 进入三层
    hdr_l3    = parse_l3(pkt)
    if hdr_l3.ttl <= 1:
        drop(pkt); return                       # TTL 耗尽，丢弃
    nexthop   = fib.lpm_lookup(hdr_l3.dst_ip)   # 查路由表命中 192.168.2.0/24
    dst_mac   = adjacency.lookup(nexthop)       # 邻接表查 C 的 MAC
    hdr_l3.ttl -= 1                             # 递减 TTL
    hdr_l3.checksum = recompute(hdr_l3)         # 重算校验和
    rewrite_l2(pkt, src=mac_vlan20, dst=dst_mac)# 重写二层头
    egress(nexthop.port, pkt)
```

对这段伪代码的判读：第一行的判断是三层转发的入口条件——目的 MAC 是不是本机网关 MAC，这正好呼应第二章 L2/L3 协同判定图里的分支。确认要三层转发后，依次做 TTL 检查、LPM 查路由、邻接解析、TTL 递减与校验和重算、二层头重写，最后从下一跳端口发出。注意 `src=mac_vlan20`——源 MAC 换成了 R1 在出方向接口上的 MAC，这正是"每过一跳二层头都被重写"的体现。这段伪代码把前面分散在多个章节的动作串成了一条真实路径。

### 4. 从实例回到流水线：一次 ping 用到了哪些能力

现在回头对照，一次最简单的 ping 其实调动了全书的几乎所有核心能力。把两个场景用到的能力列出来：

- **解析（parser）**：识别以太网头、ARP、IPv4、ICMP——对应数据面主路径的解析段。
- **MAC 学习**：从源 MAC 学得表项——对应 L2 流水线的学习步。
- **查表**：二层查 MAC 表、三层查 FIB 与邻接表——对应 L2/L3 两条流水线。
- **泛洪与复制**：ARP 请求广播、组播复制——对应第二章的泛洪判定与第三章的组播。
- **改写**：TTL 递减、校验和重算、二层头重写——对应 L3 流水线的改写步。
- **缓冲与调度**：报文在入出口排队、按队列调度——对应交换架构与拥塞管理。
- **控制面协作**：ARP 应答若由本机处理会上送 CPU——对应控制面与 punt 机制。

## BASIC-06 QoS 体系：从标记到调度

前面的章节解决了"把报文送到正确出口"的问题。但网络里还有一个同样重要的问题：当多个报文争抢同一条链路时，谁先走、谁被丢？QoS（Quality of Service，服务质量）就是回答这个问题的机制体系。它不决定报文去哪，而决定报文以什么优先级、什么待遇被转发出去。这一章把 QoS 从标记到调度串成一条完整链路。

### 1. 为什么需要 QoS：尽力而为的局限

以太网默认是"尽力而为"（best-effort）服务——所有报文一视同仁，谁先到谁先走，拥塞时一起丢。这对普通上网没问题，但有两类流量无法忍受：

- **实时流量**：语音、视频会议要求低时延、低抖动，包晚了就没有意义。
- **无损流量**：AI 训练里的 RDMA（远程直接内存访问）要求零丢包，丢一个包会导致整个计算任务重传、效率骤降。

QoS 的目标就是**差异化服务**：把流量分类，让重要的流量优先、保证带宽、避免丢弃，让不重要的流量在拥塞时被牺牲。对交换芯片而言，QoS 是数据面的核心能力之一——前面在调度那一节提过严格优先级、加权轮转、ECN、PFC，这一章把它们放回一个完整框架里。

理解 QoS 有个关键视角：**它是一个流水线，不是一堆开关**。从报文进入交换机到离开，会依次经过分类、监管、排队、调度、拥塞控制几个环节，每个环节各管一件事。下图先把这条链路画出来，后面逐段展开。

### 2. 分类与标记：给报文贴标签

QoS 的第一步是**识别哪些报文重要**，这靠读取报文里的优先级字段：

- **二层：802.1p（CoS）**。VLAN 标签里有 3 位优先级字段，可取 0 到 7，值越大优先级越高。
- **三层：DSCP**。IP 头里的服务类型字段前 6 位是 DSCP，可取 0 到 63。常见约定是 EF（46）给语音等低时延流量，AF 系列给有保证的流量，BE（0）是默认尽力而为。

有了字段还不够，交换机要决定**信不信这个标记**，这就是**信任边界（trust boundary）**。默认配置下，很多交换机不信任入口报文自带的 DSCP，会把它重写为 0；只有把端口配置为"信任 DSCP"或"信任 CoS"，才按报文自带的标记分类。为什么要这样设计？因为终端用户可以随意给自己的流量打高优先级标记，若无条件信任，一个人就能独占所有带宽。信任边界通常设在可控设备（如 IP 电话、受管理的交换机端口）一侧。

分类完成后，交换机把报文映射到一个**内部队列**。这是关键一步：无论入口标记是 DSCP 还是 CoS，最终都归到芯片内部的若干队列（常见 4 到 8 个），后续所有调度都基于队列而非原始标记。下面的伪代码把"读取标记—信任判断—映射队列"写出来。这不是任何真实芯片的 SDK 接口，字段名需对照实际平台核验。

```text
# 工程理解伪代码：QoS 分类与队列映射（非真实 SDK 接口）
pkt       = ingress(port)
if port.trust == "dscp":
    mark = parse_l3(pkt).dscp                    # 信任三层 DSCP
elif port.trust == "cos":
    mark = parse_l2(pkt).cos                     # 信任二层 802.1p
else:
    mark = port.default_mark                     # 不信任：用端口默认标记重写
queue_id  = mark_to_queue[mark]                  # 按映射表归到内部队列
set_internal_priority(pkt, queue_id)             # 打上内部优先级，供后续调度
enqueue(queue_id, pkt)
```

对这段伪代码的判读：`port.trust` 决定读哪个字段——信任 DSCP 就读三层头，信任 CoS 就读二层 VLAN 标签，都不信任则用端口默认值覆盖。`mark_to_queue` 是核心映射表，把外部标记（DSCP 或 CoS）转成芯片内部的队列号——不同厂商的默认映射不同，这也是 QoS 配置中最常需要对齐的地方。`set_internal_priority` 把内部优先级写在报文的元数据里，后面排队和调度只看它。这段伪代码说明了信任边界的实际作用：它决定了"用谁写的标记来分类"。

### 3. 监管与整形：控制流量速率

分类之后，要对流量速率做控制，这里有两个容易混淆但方向相反的机制：

- **监管（policing）**：超出速率的报文直接丢弃或降级标记。它像交警，超速就罚款（丢包），动作即时、粗暴，用于限制某类流量的上限。
- **整形（shaping）**：超出速率的报文先缓存起来，慢慢发。它像收费站前排队，把突发流量抹平再送出，时延增加但少丢包。

两者都用**令牌桶（token bucket）**算法实现：系统按固定速率往桶里放令牌，报文发送要消耗令牌；桶里有令牌就放行，没有就按监管或整形的规则处理。令牌桶有两个关键参数——**承诺速率（CIR）**控制平均速率，**突发尺寸（Bc）**允许短时突发。下表把监管与整形并列对照。

| 维度 | 监管 policing | 整形 shaping |
|---|---|---|
| 超限动作 | 丢弃或降级标记 | 缓存后延迟发送 |
| 时延影响 | 不增加时延 | 增加时延 |
| 丢包 | 可能丢包 | 通常不丢 |
| 典型位置 | 入口 | 出口 |
| 适用场景 | 限制违规流量 | 平滑突发、匹配下游速率 |

理解两者的差别很重要：语音流量宁可丢弃也不愿排队（迟到没意义），适合监管；而批量数据传输可以慢一点但要完整，适合整形。在交换机里，监管通常放在入口（一进来就限速），整形通常放在出口（发送前平滑）。

### 4. 排队、调度与拥塞控制

经过分类与限速，报文进入内部队列。剩下的三件事决定它何时被发出去、拥塞时是否被丢。

**排队（queuing）**：每个端口有多个队列，报文按内部优先级进入对应队列。队列是 QoS 的落脚点——前面所有分类工作，最终就是把报文分到不同的队列里。

**调度（scheduling）**：决定多个队列谁先发。三种典型算法：
- **严格优先级（SP，Strict Priority）**：高优先级队列永远先发。时延最低，但低优先级可能被"饿死"。
- **加权轮转（WRR，Weighted Round Robin）**：按权重分配发送机会，更公平，但时延不可控。
- **混合方式**：高优先级用 SP 保证时延，其余队列用 WRR 分配带宽——这是实际网络中最常见的组合。

**拥塞控制**：当队列快满时，与其等到溢出丢包，不如提前通知发送端降速。两种核心机制：
- **ECN（显式拥塞通知）**：在 IP 头里打标记，接收端通知发送端降速，端到端地缓解拥塞。
- **PFC（基于优先级的流控）**：在二层发暂停帧，让上游暂停某个优先级的发送，实现"不丢包"。RoCEv2 的无损传输就靠 PFC 加 ECN 组合实现——这正是 AI 网络里 QoS 的核心战场。

需要说明的是，PFC 用不好会引入"PFC 死锁"和"队头阻塞"等问题，需要配合 ECN 与合理的缓冲配置。这些是数据中心网络运维的深水区，本节只建立概念。下面的伪代码把入队与调度决策串起来，与第二章的调度伪代码对照着看。

```text
# 工程理解伪代码：入队、调度与拥塞标记（非真实 SDK 接口）
enqueue(queue_id, pkt)                          # 按内部优先级入对应队列
for queue in port.queues:                       # 检查各队列深度
    if queue.depth > ecn_threshold:
        mark_ecn(queue.head)                    # 超阈值打 ECN，通知源端降速
    if queue.depth > pfc_threshold:
        send_pfc_pause(queue.priority)          # 逼近满载发 PFC 暂停帧
while egress_has_credit:                        # 出口有发送机会时调度
    q = scheduler.pick()                        # SP 或 WRR 选一个队列
    pkt = q.dequeue()
    transmit(pkt)
```

对这段伪代码的判读：`enqueue` 把报文放入分类阶段确定的队列；随后两个阈值检查体现主动拥塞管理——`ecn_threshold` 用 ECN 标记通知降速，`pfc_threshold` 用 PFC 暂停帧实现无损，二者都刻意早于队列溢出。`scheduler.pick()` 是调度的核心，按 SP 或 WRR 策略选队列出队。需要强调，真实芯片的调度器是硬件状态机、阈值按端口和队列独立配置，这段伪代码只用于建立"分类—排队—调度—拥塞控制"的概念链条。

### 5. 小结与交叉引用

本章把 QoS 串成一条五段流水线：分类与标记决定待遇、监管与整形控制速率、排队与调度决定次序、拥塞控制避免丢包。几个要点：

1. **差异化服务**是 QoS 的目的，实时流量要低时延、无损流量要零丢包，尽力而为无法兼顾。
2. **信任边界**决定用谁的标记分类，不信任时按端口默认标记重写，防止用户滥用高优先级。
3. **标记最终映射到内部队列**，调度只看内部优先级，不看原始 DSCP 或 CoS。
4. **监管丢弃、整形缓存**，令牌桶是两者共同的实现基础。
5. **SP 保时延、WRR 保公平**，实际多用混合；ECN 与 PFC 是 AI 无损网络的关键。

- 队列调度、ECN、PFC 在数据面主路径中的基础位置：本资料 BASIC-03 数据面章节。
- 计数器、遥测如何观测队列深度与丢包：本资料运维与遥测面章节。
- RoCEv2 与 AI 网络无损传输的更广泛讨论：交换芯片具体分册与相关网络技术资料。

## BASIC-07 控制与管理面：决定怎么转发

### 1. 转发表项管理

控制面最核心的职责是维护数据面依赖的那些表：MAC 地址表、路由表、邻接表、ACL 表。具体包括表项的下发（写入）、查询、删除与老化（aging）。这里有两个关键指标：

- **表项容量**：能装多少条表项。装不下时，路由要退回软件或溢出到容量更大但更慢的外部存储，直接影响转发性能。
- **更新速率**：每秒能下发多少条表项。网络拓扑变化时（如链路故障、虚拟机迁移），表项要快速收敛，更新速率慢意味着业务中断时间长。

数据面查的是表的"结果"，控制面管的是表的"内容"——两者通过表项存储这条纽带连接。这是理解"为什么控制面不碰每个包却至关重要"的关键：它不改变流水线，但它决定流水线每一步查到什么。

下面用示意性的表项操作序列，展示控制面如何把三类表写进芯片、以及老化如何回收表项。这不是任何真实 SDK 接口，调用名需对照实际平台核验。

```text
# 工程理解伪代码：控制面表项下发与老化（非真实 SDK 接口）
mac_tbl.add(mac="00:11:22:33:44:55", port=3, vlan=100)   # 二层：写 MAC 表
route_tbl.add(prefix="10.0.0.0/8", nexthop="192.0.2.1")  # 三层：写路由表
acl_tbl.add(match=five_tuple, action="permit", prio=10)   # 策略：写 ACL 表
mac_tbl.set_aging(seconds=300)                            # 配置老化时间
stats = route_tbl.get_stats()                             # 查询表项统计
mac_tbl.remove_stale()                                    # 回收超时表项
```

对这段伪代码的判读：前三条 `add` 调用分别对应二层 MAC 表、三层路由表与 ACL 策略表，正好呼应数据面的三类查表——控制面写什么，数据面就查什么。`set_aging` 与 `remove_stale` 体现老化机制：MAC 表项若长时间没有流量刷新就会被回收，否则表项会被"僵尸条目"占满，导致新主机无法学习。`get_stats` 是运维面读取表项状态的入口，说明控制面与运维面也共享同一份表项存储。整段序列说明控制面的工作本质是"维护数据面依赖的表"，而非直接参与转发。

### 2. SDK、驱动与寄存器访问

上层软件配置芯片的唯一通道是 SDK（软件开发工具包）与寄存器访问。SDK 把芯片内部成百上千个寄存器封装成可编程接口，驱动把它们接入操作系统，网络操作系统再通过驱动下发配置。对使用者而言，这一层的成熟度往往比硅片参数更影响项目成败：一款纸面参数领先的芯片，若 SDK 文档不全、接口不稳定、bug 修复缓慢，实际落地会非常痛苦。

### 3. 与网络操作系统的对接：SAI

白盒交换机用 SAI（Switch Abstraction Interface，交换抽象接口）这一层标准抽象，让网络操作系统（NOS，如 SONiC）不依赖具体芯片。理论上，只要芯片提供符合规范的 SAI 实现，同一个 NOS 就能跑在不同厂商的芯片上。

但需要客观说明：SAI 的成熟度在不同芯片、不同分支版本上差异明显。大型云厂商往往有自己的定制分支并完成深度适配，而通用场景下的 SAI 特性完备性需按具体 SKU 核验。选型时若目标是 SONiC，务必确认所用 SAI 分支对该芯片型号的特性支持是否齐全——这是"纸面支持"与"生产可用"之间的现实差距。

## BASIC-08 运维与遥测面：让状态可见可控

### 1. 计数器与统计

最基础的运维功能是各类计数器：每端口、每队列收发字节数、包数、丢包数、错误数。它们是网络监控与故障定位的原始数据，也是所有高级遥测的基础。计数器看似简单，但在高速端口上要做到线速不丢计数、且读取时不影响转发，同样需要硬件支持。

### 2. 流量镜像与带内遥测

- **流量镜像（SPAN/ERSPAN）**：把指定流量复制一份送到分析端口或远端分析器，用于抓包排障与入侵检测。
- **INT（带内网络遥测）**：让报文携带遥测指令，逐跳把交换机内部状态（队列深度、时延、拥塞）写入报文，接收端据此还原整条路径的真实转发过程。
- **sFlow 等采样流**：周期性采样报文头部与计数器，以极低开销提供全网流量画像。

这一类功能把网络从"出问题后排查"变成"实时可见、自动隔离"。前面提到的 Teralynx 10 的 Flashlight 遥测，本质就是这一平面能力的加强版。

### 3. 可靠性与保护

链路聚合（LACP）把多条物理链路绑成一条逻辑链路，既增加带宽又提供冗余；BFD 硬件卸载把快速故障检测放到芯片里，缩短故障发现时间；硬件链路故障切换在链路down时立即改道，不等控制面收敛——这三项合起来，构成交换芯片的"免疫系统"。对 AI 训练这类对中断极度敏感的场景，故障切换速度直接决定任务是否停顿。

### 4. 安全与加密

ACL 过滤在入口就丢弃非法流量；MACsec 在二层做线速加密，保证链路上的报文机密性与完整性；风暴控制抑制广播/组播风暴；CoPP（控制面限速）保护控制面不被过量报文压垮。这些功能都属于运维与遥测面——它们的特点是"改变处理方式但不改变转发的本质目的地"。

## BASIC-09 交换容量、SerDes 与端口速率

### 1. 容量口径：最容易踩的第一个坑

读懂任何交换芯片参数表的第一步，是搞清楚"交换容量"怎么算。厂商普遍按**端口名义速率之和**定义容量：64 个 800GbE 端口等于 51.2Tbps，128 个 800GbE 等于 102.4Tbps。这里的关键是不把收发双向重复计算——一个 800G 端口虽然是全双工（收发各 800G），但容量只按 800G 计一次。

这个口径解释了一个常见困惑：同一代芯片在不同资料里容量相差一倍。若某处写"Tomahawk 5 是 102.4T"、另一处写"51.2T"，多半不是事实错误，而是前者按双向叠加、后者按名义端口速率。理解和统一口径，是进行任何横向对比的前提。下表给出常见端口配置与容量的对应关系。

| 端口配置 | 名义容量 | SerDes 需求（按 100G/lane） | 典型代际 |
|---|---|---|---|
| 32 × 400GbE | 12.8T | 128 lane | 早期 12.8T 芯片 |
| 64 × 400GbE | 25.6T | 256 lane | 25.6T 芯片 |
| 64 × 800GbE | 51.2T | 512 lane | Tomahawk 5 一代 |
| 128 × 800GbE | 102.4T | 1024 lane | Tomahawk 6 一代 |
| 64 × 1.6TbE | 102.4T | 512 lane（200G/lane） | Condor 类高速 SerDes |

注：表中 SerDes 需求为示意，实际 lane 数与端口聚合方式、SerDes 速率代际相关，需以具体芯片数据手册为准。

### 2. SerDes：速率演进的真正引擎

交换芯片容量为什么能约两年翻一倍？答案在物理层——SerDes（Serializer/Deserializer，串行器/解串器）。它是芯片与外部世界之间的高速串行接口，把芯片内部的并行数据转成高速串行信号发送，或反过来把收到的串行信号还原成并行数据。

容量的提升来自两个乘数的增长：**单 lane 速率 × lane 数量**。单 lane 速率从早期的 28G、56G PAM4 演进到 112G PAM4，再到最新的 212.5G PAM4；lane 数则从 128 增加到 512、1024。两者相乘得到总带宽。所谓 PAM4（四电平脉冲幅度调制），是在一个符号周期内传 2 个比特（相比传统 NRZ 的 1 个比特翻倍），代价是抗噪声能力下降、对链路质量要求更高——这就是为什么高速率芯片的铜缆传输距离更短、更依赖光模块。

图中节点速览：n1 是交换容量，定义为端口名义速率之和；n2 与 n3 是容量的两个乘数——单 lane 速率（从 28G 到 212.5G PAM4 演进）与 lane 数量（从 128 到 1024）；n4 指出容量等于两者相乘，因此约两年翻倍；n5 是 PAM4 提高速率的代价——抗噪声能力下降；n6 是这一代价的后果——链路要求提高，铜缆传输距离变短、更依赖光模块。整张图说明容量增长的本质是 SerDes 物理层演进，而非逻辑架构变化。

### 3. 端口聚合与光模块形态

lane 数的增加最终要落到端口上，这就是端口聚合：把多条 lane 绑成一个高速端口，例如 4 条 100G lane 组成 400G 端口、8 条组成 800G 端口。同样的 1024 条 lane，聚合成 512 个 200G 端口得到最高 Radix，聚合成 128 个 800G 端口则得到更少但更快的端口——这是同一芯片的两种整机形态。

链路介质同样需要理解DAC（无源铜缆，便宜、距离最短约 1 至 3 米）、AEC（有源电缆，距离中等）、LPO（线性直驱光模块，低功耗）、CPO（共封装光学，把光引擎与芯片封在一起，功耗与密度最优但维修复杂）这几类形态的取舍。下面的示意配置展示容量口径与端口聚合的关系。

```text
# 工程理解示意：同样 1024 条 100G lane 的两种端口聚合（非真实配置）
total_lanes = 1024
profile_A:
  lane_rate  = 100G
  ports      = total_lanes / 4 = 256 x 400GbE
  capacity   = 256 * 400G = 102.4T
profile_B:
  lane_rate  = 100G
  ports      = total_lanes / 8 = 128 x 800GbE
  capacity   = 128 * 800G = 102.4T
```

对这段配置的判读：两个 profile 的 lane 总数相同（1024）、单 lane 速率相同（100G），因此名义容量必然相同（102.4T）——这再次印证了容量口径。差别在聚合粒度：profile_A 用 4 lane 聚合成 400G 端口，得到 256 个端口；profile_B 用 8 lane 聚合成 800G 端口，得到 128 个端口。端口聚合方式由整机的目标拓扑决定，而非芯片本身——同一颗芯片可以做成不同形态的交换机。选型时要先明确需要多少端口、每端口多快，再反推聚合方式与介质形态。

## BASIC-10 交换架构与转发模式

### 1. 共享内存与分布式缓冲

当多个入口同时涌向同一出口时，报文必须暂存。怎么暂存，是交换架构的核心问题，业界有两大流派。

**共享内存架构**：所有端口共享一片片上缓冲池。优点是缓冲利用率高——空闲端口的缓冲可以被拥塞端口借用；缺点是容易出现队头阻塞（Head-of-Line blocking），且一个端口的突发可能挤占其他端口的缓冲。

**分布式缓冲（VOQ，虚拟输出队列）**：按目的出口为每个入口分配独立队列。优点是彻底避免队头阻塞，因为发往不同出口的包各自排队；缺点是需要更多片上存储，芯片面积与功耗代价更大。高端芯片常采用"共享 + 分布式"的混合形态，在利用率与抗阻塞之间取平衡。

这两种架构的差异，直接决定芯片面对微突发（microburst，极短时间内的大量报文）时的表现。深缓冲方案靠"装得多"吸收突发，低时延方案靠"排得快"减少驻留——这是一对经典的取舍，没有绝对优劣，取决于目标场景。下图把两种缓冲架构并列画出。

node n4 "利用率高<br/>队头阻塞风险" amber

### 2. cut-through 与 store-and-forward

转发模式是另一个基础但重要的取舍。cut-through（直通）在收到报文的目的地址后就开始转发，不等整包收完，时延最低（可低至纳秒级），但可能把校验错误的坏包也转发出去。store-and-forward（存储转发）收完整包并校验通过后才转发，可靠性高，但时延至少增加一个完整包长的接收时间。

现代芯片多支持按端口或按场景配置：对时延敏感的 AI 训练流量用 cut-through，对可靠性要求高的场景用 store-and-forward。厂商标称的超低时延几乎都是 cut-through 理想值，实际带载、开启 VLAN 改写或深缓冲后时延会上升——这是读参数时必须注意的口径。下表把两种模式并列对照。

| 维度 | cut-through（直通） | store-and-forward（存储转发） |
|---|---|---|
| 转发时机 | 收到目的地址即转发 | 收完整包并校验后转发 |
| 时延 | 最低，纳秒级 | 至少多一个包长时间 |
| 坏包处理 | 可能转发错误包 | 校验失败丢弃 |
| 适用场景 | AI 训练、低时延交易 | 可靠性优先的通用网络 |
| 厂商标称口径 | 多为该模式理想值 | 带载后时延上升 |

### 3. 队头阻塞与调度的关系

队头阻塞值得单独理解：在简单的先进先出队列里，如果队首的包因目标出口拥塞而发不出去，后面本可发往其他空闲出口的包也被堵住——就像一条车道上前车抛锚，后面所有车都动不了。这正是 VOQ 要解决的问题：按目的出口分队列后，发往空闲出口的包不会因为发往拥塞出口的包而受阻。

调度则解决另一个问题：当多个队列都有包要发时，谁先走。严格优先级（SP）让高优先级队列优先，但可能饿死低优先级；加权轮转（WRR）按比例分配带宽，更公平。调度与缓冲架构配合，共同决定芯片的拥塞行为。下面的伪代码把入队决策与转发模式的关系讲清楚。

```text
# 工程理解伪代码：入队与转发模式决策（非真实 SDK 接口）
pkt       = ingress(port)
dst_port  = lookup_forward(pkt)             # 查表得到目的端口
queue     = voq_select(port, dst_port)      # 按目的出口选虚拟输出队列
if queue.depth > threshold:
    mark_congestion(pkt)                    # 超阈值标记 ECN，通知源端降速
enqueue(queue, pkt)                         # 入队等待调度
if forward_mode == "cut_through" and hdr_ready(pkt):
    start_forward(pkt)                      # 收到头即转发，不等整包
else:
    if crc_ok(pkt):                         # 存储转发：先校验
        start_forward(pkt)
```

对这段伪代码的判读：`voq_select` 体现分布式缓冲的核心思想——按目的端口选队列，从机制上避免队头阻塞；`mark_congestion` 是主动拥塞管理，队列超阈值就给报文打 ECN 标记，让接收端通知发送端降速，而非等队列溢出再丢包；最后的条件分支对比两种转发模式——cut-through 只要头部就绪就 `start_forward`，store-and-forward 则要等 `crc_ok` 校验通过。需要强调，这段伪代码是概念示意，真实芯片的队列与调度机制远比这复杂，具体实现需以数据手册为准。

## BASIC-11 性能指标体系与选型视角

### 1. 读懂一张参数表

掌握了容量口径与架构原理，就可以系统地读一张交换芯片参数表。关键指标可以归为五类：

- **容量与端口**：交换容量、端口速率与数量、Radix（同速率端口数）、SerDes 速率与 lane 数。Radix 决定网络拓扑层数，是 AI 集群选型的第一指标。
- **时延与吞吐**：厂商标称时延（注意多为 cut-through 理想值）、线速能力（是否所有端口全速同时转发无阻塞）、尾时延（拥塞时的最差时延）。
- **缓冲与拥塞**：缓冲容量与架构（共享/分布式）、是否支持 ECN/PFC、能否做到无损。
- **表项与特性**：MAC/路由/ACL 表项容量、单次 VXLAN、组播能力、遥测与安全特性。
- **功耗与生态**：典型功耗、制程、SDK/SAI/NOS 成熟度、生命周期状态。

### 2. 标称值与实测值的差距

参数表里最容易误判的是时延与功耗。厂商标称时延通常是 cut-through、空载或轻载下的理想值，实际网络中一旦开启 VLAN 改写、深缓冲、组播复制，时延就会上升；标称功耗是典型场景值，满载所有端口时功耗更高。因此严肃的选型要索取带载时延报告与满载功耗数据，而不是直接引用宣传数字。

另一个常见误区是只看容量数字。容量相同的两颗芯片，可能因 Radix 不同、缓冲架构不同、时延特性不同，适合完全不同的场景——102.4T 既能做成高 Radix 的扁平 scale-out 交换机，也能做成低时延的 scale-up 互联，取决于端口聚合与架构取舍。

### 3. 从需求反推配置的选型思路

正确的选型顺序是"从场景反推参数"，而不是"从参数挑芯片"。下面用示意伪代码展示这个思路：先明确拓扑与流量特征，再推导所需的 Radix、缓冲与特性组合。

```text
# 工程理解示意：从场景反推芯片配置（非真实工具）
scenario = "AI_scaleout"          # 场景：AI 横向扩展集群
xpu_count = 100000                # 加速器数量
if xpu_count > 50000:
    need_radix = "high"           # 大规模 → 高 Radix 减少拓扑层数
if scenario.startswith("AI"):
    need_lossless = True          # AI/RDMA → 需要无损（PFC/ECN）
    need_low_tail_latency = True  # 集合通信 → 关注尾时延
config = {
    "radix": need_radix,
    "buffer": "deep" if need_lossless else "shallow",
    "features": ["RoCEv2", "adaptive_routing", "telemetry"]
}
```

对这段伪代码的判读：起点是场景与规模（`scenario`、`xpu_count`），而非芯片参数；`xpu_count` 很大时推导出 `need_radix = high`，因为高 Radix 能用更少层数连接同等规模集群，直接减少跳数与光模块；AI 场景进一步推导出需要无损传输与低尾时延，因为 RDMA 对丢包敏感、集合通信对最慢节点敏感；最终得到的 `config` 是一组需求特征，拿这组特征去匹配具体芯片，比先挑容量数字再勉强适配要可靠得多。这套思路把前面几章的知识串成了一个完整的决策链。

## BASIC-12 进阶协议与可靠性：防环、EVPN 与无损网络

到这里，读者已经能读懂芯片的转发流水线、一次 ping 的全程和 QoS 体系。但要真正精通交换机，还需要理解几类"让网络可靠工作"的协议机制：二层如何避免环路、VXLAN 的转发表由谁建立、AI 网络如何做到零丢包。这些主题有的在前面章节零星出现过（生成树、PFC/ECN、VXLAN 数据面），这一章把它们系统展开。

### 1. 二层防环：STP、RSTP 与 MSTP

二层转发的泛洪机制有个致命弱点：如果网络中存在物理环路，广播帧会在环路里无限循环复制，形成**广播风暴**，几秒钟就能耗尽带宽和 CPU。二层网络又常常为了冗余特意拉双线，环路风险天然存在。生成树协议（STP，Spanning Tree Protocol）就是为解决这个问题而生。

STP 的思路很巧妙：**逻辑上阻塞冗余链路，把有环的物理拓扑剪成无环的树**。它工作分三步：

1. **选举根桥（root bridge）**：所有交换机按桥 ID（优先级加 MAC）选出一个根，作为树的根。
2. **选举根端口（root port）**：每台非根交换机选出离根桥最近的端口，作为通往根的方向。
3. **选举指定端口（designated port）并阻塞其余端口**：每个网段选一个指定端口转发，剩下的冗余端口进入阻塞状态，不转发用户流量。

被阻塞的端口并非永远不用——当主链路故障时，STP 会重新计算，把阻塞端口打开，恢复连通。这就是冗余的意义：平时不浪费、故障时顶上。

**RSTP（快速生成树，802.1w）**是 STP 的改进版，把收敛时间从几十秒缩短到秒级甚至亚秒级，通过端口角色快速切换实现。**MSTP（多生成树，802.1s）**进一步允许多个 VLAN 映射到不同的生成树实例，避免所有 VLAN 都走同一条路径造成的链路浪费——它与 VLAN、Trunk 配合，是园区网的常见配置。

需要指出一个现代数据中心的现实：较大规模的 Clos 架构网络往往**不跑 STP**，而是靠三层路由和 ECMP 天然无环（路由的 TTL 与路由协议本身防环），把二层域压缩到极小。STP 主要活在园区网和传统二层环境里。下表把三代生成树对照。

| 协议 | 标准 | 收敛时间 | 多 VLAN 支持 | 典型场景 |
|---|---|---|---|---|
| STP | 802.1D | 30 至 50 秒 | 单一生成树 | 老旧网络 |
| RSTP | 802.1w | 秒级 | 单一生成树 | 中小园区网 |
| MSTP | 802.1s | 秒级 | 多实例，按 VLAN 映射 | 大型园区网 |

### 2. EVPN：VXLAN 的控制面

前面讲 VXLAN 时留下一个关键问题：源 VTEP 怎么知道目的 MAC 在哪个远端 VTEP 后面？如果靠数据面泛洪（BUM 流量头端复制）来学习，效率低、浪费带宽。EVPN（Ethernet Virtual Private Network）就是来解决这个问题的——它是 VXLAN 的**控制面**。

EVPN 的本质是：**用 BGP 协议在 VTEP 之间发布主机可达性信息**。本地 VTEP 通过数据面学习到一台主机的 MAC/IP 后，不把它闷在本地，而是通过 BGP EVPN 路由公告给其他 VTEP；远端 VTEP 收到后，在本地转发表里写入"这个 MAC/IP 在那个 VTEP 后面"。这样后续通信就是精确的单播封装，无需泛洪查找。

EVPN 有几个关键优势：

- **抑制泛洪**：主机位置通过控制面传播，ARP 请求可以由 VTEP 代答（ARP suppression），大幅减少 BUM 流量。
- **支持多归属（multihoming）**：一台主机可以双归到两台 VTEP，实现链路冗余，且能避免环路。
- **统一二三层**：EVPN 路由类型既发布 MAC 也发布 IP，能同时支持二层桥接和三层网关，配合分布式 IRB 实现对称转发。

### 3. 无损网络：RoCE、PFC 与 DCQCN

AI 训练集群里，GPU 之间要通过 RDMA over Converged Ethernet（RoCEv2）直接读写远端内存。RDMA 对丢包极度敏感——传统 TCP 丢包只重传一个段，RDMA 丢一个包往往导致整个消息重传，训练效率断崖式下降。所以 AI 网络追求**无损（lossless）**：拥塞时不丢包。

交换芯片层面实现无损靠两件事，都在 QoS 章节讲过：

- **PFC（基于优先级的流控）**：队列快满时向上游发暂停帧，让上游停止该优先级发送，从链路上避免丢包。
- **ECN（显式拥塞通知）**：在报文里打标记，让接收端通知发送端降速，从源头上缓解拥塞。

但仅有 PFC 不够。PFC 是"暂停—恢复"的粗粒度开关，容易引发 **PFC 风暴**（暂停帧逐级向上游传播，导致大面积停流）和**死锁**（多个优先级互相等待，谁也发不了）。业界用 **DCQCN**（数据中心量化拥塞通知）来解决：它把 ECN 标记与速率控制结合，让发送端根据拥塞程度平滑降速，而不是靠 PFC 硬暂停。DCQCN 是 RoCEv2 网络里端到端拥塞控制的事实标准。

对交换芯片而言，支撑无损需要：足够深的缓冲吸收微突发、精细的队列阈值配置、PFC 与 ECN 的硬件卸载、以及拥塞状态的细粒度遥测（这正是具体芯片分册里强调的能力）。下表把三种机制的作用层次列出来。

| 机制 | 作用层次 | 触发方式 | 解决什么 |
|---|---|---|---|
| PFC | 逐跳、二层 | 队列超阈值发暂停帧 | 链路级不丢包 |
| ECN | 端到端、三层 | IP 头打标记 | 通知源端降速 |
| DCQCN | 端到端、源端 | 基于 ECN 反馈调速 | 平滑降速，避免 PFC 风暴 |

### 4. 端口安全：从 ACL 到 DHCP Snooping

交换机的安全能力分布在多个章节里，这里做一个系统梳理，按"防谁、在哪防"分层：

- **ACL（访问控制列表）**：最通用，按五元组、MAC、端口等字段匹配，允许或丢弃。前面在数据面与运维面都提过，它是跨二三层的基础过滤手段。
- **端口安全（port security）**：限制一个端口能学到的 MAC 地址数量，防止攻击者伪造大量 MAC 耗尽转发表（MAC 泛洪攻击）。
- **DHCP Snooping**：监听 DHCP 过程，只信任连接正规 DHCP 服务器的端口，防止攻击者私设 DHCP 服务器下发错误网关（中间人攻击）。它还生成"IP-MAC-端口"绑定表，供后续防护使用。
- **DAI（动态 ARP 检测）**：利用 DHCP Snooping 的绑定表检查 ARP 报文，丢弃伪造的 ARP 应答，防 ARP 欺骗。
- **IP Source Guard**：基于绑定表过滤源 IP，防止主机伪造源地址。
- **MACsec**：在二层做线速加密，保护链路上的报文机密性与完整性，前面在运维面提到过。

这几项能力层层递进：ACL 是通用过滤，端口安全管 MAC 学习，DHCP Snooping 建立可信绑定表，DAI 和 IP Source Guard 用这张表防欺骗，MACsec 管链路加密。理解它们的依赖关系，就不难明白为什么 DHCP Snooping 常常是其他防护的前提。

### 5. 小结与交叉引用

本章把几类"让网络可靠工作"的机制串起来：

1. **生成树**用逻辑阻塞把有环拓扑剪成树，STP 到 RSTP 到 MSTP 逐步改善收敛与 VLAN 利用；大型 Clos 网络则用三层无环设计绕开它。
2. **EVPN 是 VXLAN 的控制面**，用 BGP 发布主机可达性，抑制泛洪、支持多归属、统一二三层——没有它，VXLAN 只能靠泛洪学习。
3. **无损网络**靠 PFC 做逐跳不丢包、ECN 做端到端通知、DCQCN 做平滑调速，三者配合支撑 RoCEv2。
4. **端口安全**从 ACL 到 DHCP Snooping 到 DAI 层层递进，DHCP Snooping 的绑定表是多项防护的基础。

- VXLAN 数据面封装、PFC/ECN 基础、ACL 与 MACsec：本资料数据面进阶功能与运维面章节。
- 具体芯片对 PFC、ECN、拥塞遥测的硬件支持：Tomahawk 6、Teralynx 10 分册。

## BASIC-13 运维排障与可观测性：从看状态到定位问题

能配置、能转发，还不算精通。精通的标志是**出了问题能定位**：ping 不通、时通时断、时延忽高忽低，该从哪里下手。这一章把排障方法论与可观测性工具放在一起讲——前者是思路，后者是手段，二者配合才能从现象走到根因。

### 1. 排障总思路：分层与分段

排障最忌讳凭直觉乱试。系统化的方法有两个维度：

**分层排查（按 OSI 自下而上）**：
- **物理层**：链路是否 up、光模块功率是否正常、有无 CRC 错误。
- **二层**：VLAN 是否一致、MAC 表是否学到、Trunk 是否放行目标 VLAN、有无环路。
- **三层**：IP 与掩码是否正确、路由是否存在、邻接是否建立、网关是否可达。
- **传输与应用层**：端口是否监听、防火墙是否拦截、应用本身状态。

**分段排查（按路径逐跳定位）**：从源到目的把路径切成若干段，逐段测试，先确定"问题在哪一跳"，再在这一跳上深挖。这比一上来就抓全包高效得多。

### 2. 三类典型问题的定位路径

把常见故障归成三类，各自有典型的定位路径。

**问题一：完全不通**。按分层顺序查：
- 物理层：端口是否 up，`show interfaces` 看状态与错误计数。
- 二层：`show mac address-table` 看是否学到对端 MAC；MAC 没学到，可能是 VLAN 不一致、Trunk 未放行、或物理不通。
- 三层：`show ip route` 看路由是否存在；跨网段还要看邻接表 `show ip adjacency` 是否建立。
- 对照本章的贯穿实例：完全不通往往卡在 ARP 没学会（二层）或路由/邻接缺失（三层）。

**问题二：时通时断**。这类多为间歇性问题，重点查：
- 物理层：CRC 错误计数是否增长（线缆或光模块问题）。
- 环路：STP 端口是否在频繁切换、是否有广播风暴。
- 拥塞：队列深度是否周期性打满、是否触发 PFC 暂停。
- 路由震荡：路由表项是否频繁变化（可看路由翻动计数）。

**问题三：时延高或抖动**。重点查：
- 拥塞：出队列是否持续排队，尾时延是否升高。
- 微突发：短时流量尖峰是否超出缓冲，可被 PFC 或 ECN 标记捕捉。
- 转发模式：是否因开启存储转发或深缓冲导致时延增加——这呼应交换架构章节里 cut-through 与 store-and-forward 的取舍。

### 3. show 命令与可观测性：用数据说话

排障靠数据而非猜测。交换机提供的可观测性手段分几类：

- **表项查询**：`show mac address-table`、`show ip route`、`show ip adjacency`——直接看转发表的现状，是判断"学没学到、有没有路由"的第一手段。
- **计数器统计**：`show interfaces counters`、`show queue`——看收发包数、丢包数、错误数、队列深度，判断是否有拥塞或错误。
- **抓包与镜像**：SPAN/ERSPAN 把流量复制到分析口，用 Wireshark 抓包看报文内容——这是定位协议交互问题的终极手段，前面在 DPDK 资料里讲过 extcap 抓包接口，思路一致。
- **遥测**：INT（带内网络遥测）让报文携带路径状态，sFlow 提供全网流量画像，适合长期观测而非单点排障。

下面用一段示意命令序列，展示一次"ping 不通"的典型排查流程。这不是任何真实平台的命令集，具体语法需对照所用 NOS 核验。

```text
# 工程理解示意：ping 不通的分层排查命令序列（非真实 NOS 接口）
show interfaces status                          # 1. 端口是否 up
show interfaces counters errors                # 2. 有无 CRC 等错误
show vlan brief                                 # 3. VLAN 与端口归属是否正确
show mac address-table address BB:BB:BB:BB:BB:BB # 4. 是否学到对端 MAC
show ip route 192.168.2.0                       # 5. 目标网段有无路由
show ip adjacency                               # 6. 邻接是否建立
show platform queue congestion                  # 7. 队列是否拥塞
monitor session 1 source interface Eth1/2       # 8. 必要时镜像抓包
```

对这段命令序列的判读：命令按"物理层到三层"的顺序排列——先看端口状态与错误计数（第 1、2 条），排除物理问题；再看 VLAN 归属与 MAC 表（第 3、4 条），排除二层问题；接着看路由与邻接（第 5、6 条），排除三层问题；最后看队列拥塞（第 7 条）并在必要时镜像抓包（第 8 条）。这条序列正是前面分层排障思路的落地。需要强调，不同 NOS 的命令语法差异很大，这里只用于建立排查顺序的概念，实际使用要查对应平台的命令手册。

### 4. 可观测性的工程要点

做好可观测性有几个容易被忽视的要点：

- **计数器的精度与读取开销**：高速端口上要线速不丢地计数，且读取时不能影响转发——这需要硬件支持，也是芯片能力的体现。
- **遥测的采样率取舍**：sFlow 等采样流开销低但精度有限，INT 精度高但要在报文里写状态，需按场景权衡。
- **时间同步**：跨设备的时延分析依赖精确时钟（PTP/1588），否则各设备的计数对不上。
- **基线（baseline）的重要性**：没有正常运行时的基线数据，异常时就难以判断"这个队列深度算不算高"。平时留存基线，排障时才有参照。

这些都指向一个结论：可观测性不是排障时才想起来的功能，而是要在网络设计和配置阶段就规划好的能力。

## BASIC-14 三面协同、与具体芯片的关联及小结

### 1. 三个平面如何协同

三个平面不是孤立的，它们通过两条纽带协同工作：转发表项与配置。控制面把转发表项写入芯片存储，数据面逐包查这些表做决策；运维面采集转发过程中的计数器与遥测数据，反过来指导控制面调整表项与策略。下图把这条闭环画出来。

:::figure id=BASIC-14-01 | name=三平面协同闭环 | dir=LR
node n1 "控制与管理面<br/>下发转发表项与配置" blue
node n2 "数据面<br/>逐包查表转发" teal
node n3 "运维与遥测面<br/>采集计数器与遥测" amber
node n4 "表项存储<br/>两plane的纽带" blue
node n5 "反馈调整<br/>策略 路由 队列" purple
edge n1 -> n4 "写入"
edge n4 -> n2 "查表"
edge n2 -> n3 "产生状态"
edge n3 -> n5 "分析"
edge n5 -> n1 "优化配置"
:::

图中节点速览：n1 是控制与管理面，负责下发转发表项与配置；n2 是数据面，逐包查表转发；n3 是运维与遥测面，采集计数器与遥测数据；n4 是表项存储，是控制面与数据面之间的纽带；n5 是反馈调整环节，运维面分析数据后指导控制面优化配置。整张图是一个闭环：控制面写表、数据面查表、运维面看结果、再把结论反馈给控制面。这条闭环说明三个平面是协作关系，而非各自独立的功能堆砌。

### 2. 与两册具体芯片的对应关系

理解了基础框架，可以把前面两册具体芯片资料的差异化能力对应到框架中的格子：

| 功能平面 | Tomahawk 6 的强化点 | Teralynx 10 的强化点 |
|---|---|---|
| 数据面 | 102.4T 包缓冲架构、单次 VXLAN、高 Radix | 低时延可编程转发、Flex-forwarding |
| 控制面 | StrataXGS 软件兼容、成熟生态 | 开放 SDK、OCP SAI、SONiC 支持 |
| 运维面 | Cognitive Routing 2.0、快速故障检测、报文修剪 | Flashlight 细粒度遥测、微突发检测 |
| 可靠性 | 硬件链路故障切换 | 需按具体 SKU 核验 |

这张对照表说明：两款芯片的基础功能集合是一致的，差异只在于"哪些格子做得更深"。Tomahawk 6 用大缓冲与认知路由解决 AI 象流与微突发，Teralynx 10 用低时延与 Flashlight 打开差异化切入。理解了基础功能框架，再读具体芯片参数就能迅速定位"这个参数属于哪个平面、解决什么问题"。

### 3. 小结与交叉引用

1. **网络地基**：数据按分层逐层封装，帧与报文的字段决定转发依据；MAC 扁平、IP 分层、掩码定网段、网关连网段；一台交换机由 ASIC、CPU、端口与存储组成，CPU 与芯片靠报文上送协作。
2. **本质**：交换芯片用硬件在纳秒级完成"查表—搬运—排队—改写"，功能与软件转发同类，差别在执行方式的彻底硬件化。
3. **框架**：全部基础功能归为三个平面——数据面（逐包处理）、控制与管理面（表项配置）、运维与遥测面（可见性与安全）。
4. **数据面**：解析、查表、缓冲、调度、改写、组播复制是固定主路径；查表容量与速率、缓冲架构、转发模式是核心指标。
5. **L2/L3 流水线**：L2 按 MAC 走"学习—查 FDB—泛洪判定—改写"；L3 按 IP 走"LPM 查表—邻接解析—TTL/校验和改写"，二者在一次转发中串联协同，表项分别对应 FDB 与 FIB 加邻接表。
6. **进阶转发**：负载均衡用五元组哈希在 ECMP/LAG 里选路；广播按 VLAN 泛洪、组播按成员表硬件复制；VXLAN 用 MAC-in-UDP 把二层架到三层之上，靠 VTEP 与 VNI 隔离租户，封装需硬件卸载。
7. **贯穿实例**：一次 ping 串起 ARP 泛洪、MAC 学习、查表转发、网关路由与改写，让各章概念连成一条完整时序。
8. **QoS**：分类、监管、排队、调度、拥塞控制构成五段流水线；信任边界决定用谁的标记，标记最终映射到内部队列，ECN 与 PFC 支撑无损网络。
9. **控制面**：表项容量与更新速率决定收敛速度；SDK 成熟度与 SAI 完备性是落地关键。
10. **运维面**：计数器、镜像、INT、可靠性与安全让网络可见可控，是差异化的高发区。
11. **进阶协议**：生成树靠阻塞冗余链路防环，EVPN 作为 VXLAN 控制面同步主机位置，PFC 加 DCQCN 实现无损，端口安全层层递进防欺骗。
12. **协同与排障**：控制面写表、数据面查表、运维面反馈，三面连成闭环；排障按分层定位、分段排查，用表项、计数器与镜像验证。
