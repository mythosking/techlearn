# Snort 3 技术资料 · 05 关键数据结构字段详解（分片 C）

## 05-08 日志与事件结构（Event、Logger、Output Set）字段

### 1. 本篇定位与覆盖范围

本篇是 05 册「关键数据结构字段详解」输出与事件层的权威定义，逐字段核对 `src/events/event.cc/.h`、`event_queue.cc/.h`、`sfeventq.cc/.h`，`src/loggers/loggers.cc/.h` 与 `alert_json.cc`、`unified2.cc` 等具体 logger，`src/framework/logger.h`，`src/managers/event_manager.cc/.h`，以及作为连接点的 `src/detection/rules.h`、`detect.cc/.h` 与 `src/detection/signature.h`。覆盖的结构体族为 `class SO_PUBLIC Event`、`struct SigInfo`、`struct EventQueueConfig`、`struct EventNode`、`struct SF_EVENTQ_NODE`、`struct SF_EVENTQ`、`class SO_PUBLIC Logger`、`struct LogApi`、`class Output`、`struct OutputSet`、`struct ListHead` 与 `struct RuleListNode`。所有字段名、类型、初值与源码行号均取自「上游 master 快照（2026-11 抓取）」的实际头文件，逐条 Read 核实后才写入；凡只在 `.cc` 内定义或仅有前向声明的类型，一律写明不透明边界并标注「需对照实际版本核验」，不凭印象补字段、类型或偏移。

先按总纲去重铁律划清边界。本篇只讲字段含义、类型、内存布局倾向、生命周期与关联函数入口，**不展开输出管线的状态机与调用顺序**（统一写「原理见 06-11」），**不重列任何输出配置参数**（`alert_json`、`unified2` 的段与键、限速相关的 `event_filter` / `rate_filter` / `threshold` 完整参数归 04 册，统一写「参数见 04-02」「参数见 04-08」）。「关联函数与流程」一列只给函数入口名，例如 `CallLogFuncs()`、`EventManager::call_loggers()`、`EventManager::call_alerters()`、`EventManager::add_output()`，不描述它们之间如何编排；想在机制层面理解事件如何入队、排序、限速与写出，去 06-11 与 06-09。「读写时机」一列只写「构造期填充」「入队期写入」「输出期只读」「析构期释放」这类静态结论。能力边界贯穿全篇：Snort 3 是相对 Snort 2 重写的 C++ 全新实现，配置为 Lua，不兼容 `snort.conf` 与旧插件 ABI，`tools/snort2lua/` 只是格式转换辅助；Snort 本身不是防火墙、不做转发，事件与日志只是检测结果的外化；加密流量载荷不可见，`Event` 能记录的字段来自规则命中信息与握手元数据，不含解密后的明文正文；IDS 旁路模式下只告警不丢弃；Hyperscan 是可选加速、缺失时回退其他 MPSE，与本层字段无直接耦合。GPLv2 许可与 Talos 规则集独立许可按总纲处理，本篇不给分发建议；任何吞吐、pps、内存占用结论一律「需在目标机型实测」。

需要订正两处极易搞错的存储位置，这是本层源码检索最常见的扑空点。其一，`OutputSet` **并不定义在 `src/loggers/loggers.h`**，该头文件只有一句 `void load_loggers();`；`struct OutputSet` 的真实定义在 `src/managers/event_manager.cc:61`，它只包含一个 `EHList outputs`（即 `typedef list<Logger*> EHList`），全局默认输出集是同文件的静态对象 `static OutputSet s_loggers`。`src/loggers/` 下的 `alert_json.cc`、`alert_fast.cc`、`unified2.cc` 是具体 logger 实现，不是 `OutputSet` 定义处。其二，`ListHead` 定义在 `src/detection/rules.h:53`，持有 `OutputSet* LogList`、`OutputSet* AlertList` 与 `struct RuleListNode* ruleListNode`，这正是规则结构与输出结构的连接点：`CallLogFuncs()` 走 `head->LogList`，`CallAlertFuncs()` 走 `head->AlertList`，再分别交给 `EventManager::call_loggers()` 与 `EventManager::call_alerters()`。把这个连接点理清，才能回答「一条规则的事件究竟写到哪里」。事件字段从规则命中到 logger 写出的归属链路见图 05-08-01，实线为字段持有与引用关系，虚线为事件队列的排序回查；调用顺序不在图中表达，归「原理见 06-11」。

### 3. 逐项详解

**Event 的封装与访问器语义**。`src/events/event.h` 的 `class SO_PUBLIC Event` 提供三个构造函数：默认构造 `Event()`，以及两个带时间戳、签名信息、buffer 数组与动作名的构造，后者多一个 `uint32_t ref` 参数用于关联事件引用（源码注释说明 `event_reference` 用于 tagged packet 之类「其他已触发事件的引用」）。七个私有成员全部集中在 private 段：`sig_info` 是 `const SigInfo&` 引用而非指针或值，意味着 `Event` 不拥有签名信息的内存，它引用的是 `OptTreeNode::sigInfo`，生命周期由规则树持有——这一点决定了 `Event` 不能比规则树活得更久，本册只记静态归属，不展开规则卸载时序（原理见 06-06）。`action`、`buffs_to_dump` 是指针，分别记录动作名（来自 `head->ruleListNode->name`，见 `CallLogFuncs()` 的实现）与待转储 buffer 名数组。`ts_sec`、`ts_usec` 时间戳在 `detect.cc` 的 `Event event(p->pkth->ts.tv_sec, p->pkth->ts.tv_usec, otn->sigInfo, otn->buffer_setters, act)` 一处构造时写入，源头是 DAQ 包头 `DAQ_PktHdr_t` 的时间戳（字段见 05-07），因此事件时间与包时间是同一时基，而非系统当前时间。访问器 `get_gid()`/`get_sid()`/`get_rev()`/`get_msg()`/`get_class_type()`/`get_class_id()`/`get_priority()` 全部转发到 `sig_info` 引用；`get_target()` 返回 bool 并通过引用参数给出源/目的方向；`get_reference()` 以 idx 递增方式（从 0 起）遍历所有 reference。三个静态方法 `get_curr_seq_num()`、`get_next_seq_num()`、`get_next_event_id()` 提供序号与事件 ID 的分配入口，属进程级计数，具体并发语义需对照实际版本核验。

**SigInfo 的字段族与规则元数据**。`struct SigInfo`（`src/detection/signature.h:94`）是 `Event` 引用内容的实体，字段分三类。文本类：`message`（`std::string`，规则 msg）、`body`（`std::string*`，规则正文，初值 nullptr）。容器类：`refs`（`std::vector<const ReferenceNode*>`）、`services`（`std::vector<SignatureServiceInfo>`），二者在规则解析期填充，元素类型是外部定义，属不透明句柄。标识类：`class_type`（`const ClassType*`）、`gid`（`uint32_t`，初值 `GID_DEFAULT`）、`sid`、`rev`、`class_id`、`priority`、`builtin`（bool，初值 false）、`target`（`enum Target`，取值 `TARGET_NONE`、`TARGET_SRC`、`TARGET_DST`，`TARGET_MAX = TARGET_DST` 作上界）、`file_id`（`uint64_t`，初值 0）。这些字段是规则头部在内存中的落点，`sid`/`rev`/`gid` 三元组与事件输出字段一一对应（输出格式见「参数见 04-02」，写出机制见「原理见 06-11」）。`builtin` 与 `target` 分别标记内建规则与目标方向，读字段时若发现 `sid` 为 0 或 `gid` 为默认值，通常意味着该 `SigInfo` 尚未完成解析或被内建事件复用，应回到 `src/parser/parse_rule.cc` 核对赋值点（原理见 06-06），而不是怀疑 `Event` 构造。

**事件队列的四组结构与池化特征**。`src/events/event_queue.h` 定义 `struct EventQueueConfig`（`max_events`、`log_events`、`order`、`process_all_events`）与 `struct EventNode`（`otn`、`rtn` 两个树节点指针），并提供 `EventQueueConfigNew()` / `EventQueueConfigFree()` 两个工厂函数；两个宏 `SNORT_EVENTQ_PRIORITY`（1）与 `SNORT_EVENTQ_CONTENT_LEN`（2）给出 `order` 的取值语义，排序实现归 06-09。`src/events/sfeventq.h` 是更底层的通用事件队列：`SF_EVENTQ_NODE` 用 `event`（void* 载荷）、`prev`、`next` 组成双向链表；`SF_EVENTQ` 除 `head`、`last` 外，还有 `node_mem`（节点内存池）、`event_mem`（事件内存池）、`reserve_event`（预留事件，源码注释说明它用于「多分配一个节点与队尾事件比较优先级」），以及 `max_nodes`、`log_nodes`、`event_size`、`cur_nodes`、`cur_events`、`fails` 六个计数与配置字段。函数族 `sfeventq_new()`、`sfeventq_event_alloc()`、`sfeventq_add()`、`sfeventq_action()`、`sfeventq_reset()`（返回自上次重置以来的失败数）、`sfeventq_free()` 构成完整生命周期。内存池字段意味着节点与事件内存是批量预分配的，读取 `cur_nodes` 时它是当前占用而非容量，二者不可混为一谈；具体池化策略与排序判据属机制，写「原理见 06-09」「原理见 06-11」。

**Logger、LogApi 与 OutputSet 的插件形态**。`src/framework/logger.h` 的 `class SO_PUBLIC Logger` 是典型薄基类：虚析构之外，`open()`、`close()`、`reset()`、`reload()`、`alert(Packet*, const char*, const Event&)`、`log(Packet*, const char*, Event*)` 全部是带空实现的虚函数，私有段只有 `const LogApi* api = nullptr`，通过 `set_api()` / `get_api()` 读写。`LOGAPI_VERSION ((BASE_API_VERSION << 16) | 3)` 把 logger API 版本编进高位的 base 版本与低位的自身版本，`struct LogApi` 由 `BaseApi base`、`unsigned flags`、`LogNewFunc ctor`、`LogDelFunc dtor` 四字段组成，`flags` 取 `OUTPUT_TYPE_FLAG__ALERT`（0x1）与 `OUTPUT_TYPE_FLAG__LOG`（0x2）的位掩码。源码注释明确「ctor / dtor 在主线程，其余方法在包线程」，这条线程归属是读字段时判断竞态的静态依据。`Output` 与 `OutputSet` 定义在 `src/managers/event_manager.cc`：`Output` 持 `const LogApi* api` 与 `Logger* handler`，析构时调用 `api->dtor(handler)`；`OutputSet` 只有一个 `EHList outputs`（`list<Logger*>`）。`EventManager::add_output()` 在 `*ofn` 为空时 `new OutputSet`，再 `outputs.emplace_back(eh)`；`copy_outputs()` 复制链表；静态 `s_loggers` 是命令行与全局默认路径的落点。具体 logger（如 `alert_json.cc`）如何把 `Event` 字段写成 JSON，属于机制与参数，写「原理见 06-11」「参数见 04-02」。

**ListHead 连接点与读写时机总览**。`struct ListHead`（`src/detection/rules.h:53`）的 `LogList` 与 `AlertList` 是两个 `OutputSet*`，加上 `ruleListNode`，构成规则与输出的桥。`detect.cc` 中 `CallLogFuncs(Packet*, ListHead*, Event*, const char*)` 取 `head ? head->LogList : nullptr` 调 `EventManager::call_loggers()`；`CallAlertFuncs(Packet*, const OptTreeNode*, ListHead*)` 取 `head ? head->AlertList : nullptr` 调 `EventManager::call_alerters()`。两函数在 `head` 为空时把 nullptr 传入，由 `call_loggers()` / `call_alerters()` 回落到全局 `s_loggers.outputs`，这就是「规则可绑定专属输出、否则走全局输出」的字段级根据。`RuleListNode` 的 `name` 字段被取作 `Event::action` 的值，`mode`（`IpsAction::Type`）与 `evalIndex` 分别记录规则动作模式与求值序号。读写时机可归纳为四段：配置装配期写 `ListHead` 的两个指针与 `LogApi` 的工厂字段；规则解析期写 `SigInfo` 与 `Event` 的引用来源；事件构造与入队期写 `Event` 的时间戳、事件 ID 与队列计数；输出期只读 `Event` 访问器与 `OutputSet::outputs` 链表并调用虚函数。除这四段外，其余阶段应把这些字段视作只读或不存在，不推断运行时效果。

### 4. 典型示例

下面这段 C++ 片段用于核对事件结构字段的访问器，只读取一个已构造 `Event` 的字段值并打印，不触发检测、入队或写盘流程，便于在本地调试构建里确认访问器与源码声明一致。示例输出，具体格式需对照实际版本核验。

```cpp
#include "events/event.h"
#include "managers/event_manager.h"
#include <cstdio>

static void dump_event_fields(const Event& ev)
{
    uint32_t sec = 0, usec = 0;
    ev.get_timestamp(sec, usec);
    uint32_t gid = 0, sid = 0, rev = 0;
    ev.get_sig_ids(gid, sid, rev);
    std::printf("ts=%u.%06u gid=%u sid=%u rev=%u\n",
        sec, usec, gid, sid, rev);
    std::printf("event_id=%u action=%s\n",
        ev.get_event_id(), ev.get_action() ? ev.get_action() : "-");
    std::printf("msg=%s prio=%u\n",
        ev.get_msg() ? ev.get_msg() : "-", ev.get_priority());
}
```

在一个接入调试构建、由规则命中构造出 `Event` 的测试桩里，输出类似如下。示例输出，具体格式需对照实际版本核验。

```text
ts=1762809600.000123 gid=1 sid=1000001 rev=3
event_id=42 action=alert
msg=ET SCAN SYN SCAN prio=2
```

逐行判读如下，合计超过 150 字。第一行 `ts=1762809600.000123` 是 `get_timestamp()` 拆出的秒与微秒，秒值来自 `Packet::pkth` 所指向的 `DAQ_PktHdr_t` 时间戳（字段见 05-07），不是 `time()` 的系统时间；若微秒位恒为 0，先确认 DAQ module 是否提供高精度时戳，而不是怀疑 `get_timestamp()`。`gid=1 sid=1000001 rev=3` 由 `get_sig_ids()` 一次性取出，分别对应 `SigInfo::gid`、`sid`、`rev`：gid 为 1 是常见生成器号（`GID_DEFAULT` 需对照实际版本核验），sid 落在社区规则常见区间，rev 为修订号；三者全为 0 通常说明规则尚未解析完成或取到了默认构造的 `Event`。第二行 `event_id=42` 来自 `Event::event_id`，由静态序号分配入口 `get_next_event_id()` 一类入口维护（函数名以源码为准，需对照实际版本核验），同一批事件应递增；`action=alert` 来自 `Event::action`，它是 `ListHead::ruleListNode->name` 的字符串，若这里为空串，多半是该事件走的是无 `ListHead` 的全局路径。第三行 `msg` 转发自 `SigInfo::message`，`prio=2` 来自 `SigInfo::priority`；若 `msg` 显示 `(null)` 或 `-`，说明 `sig_info` 引用指向的 `OptTreeNode` 已被释放，属生命周期问题（原理见 06-06）。以上只核对字段可读性，不代表任何性能结论，吞吐与内存占用一律「需在目标机型实测」。字段完整定义见 05-08 本节，输出写出见「原理见 06-11」，输出参数见「参数见 04-02」，目录职责见「模块见 07-08 ｜ 模块见 07-11」。

### 6. 版本差异

最根本的代际差异是「事件与输出如何组织」。Snort 2 以 C 结构体加全局输出函数表组织事件，配置来自 `snort.conf`；Snort 3 是从 Snort 2 重写的 C++ 全新实现，配置改为 Lua，`Event` 由纯数据变成带构造/析构、字段全部私有、通过 `get_*()` 访问器暴露的 `class SO_PUBLIC Event`（`src/events/event.h`），日志侧则抽象出 `Logger`（`src/framework/logger.h`）插件基类，由 `EventManager`（`src/managers/event_manager.cc`）统一注册与分发。因此「按全局变量名找事件输出」的旧习惯在 3.x 不成立。插件 ABI 不通用：`BaseApi`（`src/framework/base_api.h`）作为所有插件 API 的首成员，`LOGAPI_VERSION ((BASE_API_VERSION << 16) | 3)` 把 logger API 版本编入其中，跨版本加载 SO 输出插件必须校验版本，具体兼容边界需对照实际版本核验。Lua 取代 `snort.conf`，输出段与限速参数归 04 册（`参数见 04-02`、`参数见 04-08`），`tools/snort2lua/` 只是格式转换辅助，不等于事件字段或输出配置可直接沿用。

上游 master 快照（2026-11 抓取）内部的演进痕迹同样要谨慎。`src/events/event.h` 的构造函数重载多出一个 `uint32_t ref` 参数，源码注释把 `event_reference` 解释为 tagged packet 等关联事件的引用，说明该字段是后加能力；`src/framework/logger.h` 的 `LOGAPI_VERSION` 用位移组合版本，注释写明「the LOGAPI_VERSION will change if anything in this file changes」，意味着 `Logger` 的任何改动都会推动版本位变化；`src/managers/event_manager.cc` 中 `EventManager::add_output()` 被标注 `cppcheck-suppress unusedFunction`、注释说明「entry point retained for external, conditional, or test use」，说明它是为外部或条件编译保留的入口；`src/detection/rules.h` 的 `ListHead` 用裸指针 `OutputSet*` 而非智能指针，归属由装配期约定。这些都说明字段集合、初值与实现位置不是冻结的，任何依赖字段偏移、结构体大小或「定义一定在同名头文件」的假设都不可靠，结论一律以当前快照源码为准并标注「需对照实际版本核验」。具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，本套资料不写绝对版本号。

能力边界随版本保持稳定，但会影响字段可读性：加密流量载荷不可见，`Event` 的 `buffs_to_dump` 与 `SigInfo::message` 来自规则命中与握手元数据，不含解密后的 HTTPS 正文；IDS 旁路模式下只告警不丢弃，与 drop 相关的动作字段不会被写成实际拦截，内联 verdict 见「原理见 06-12」；输出插件是可选装配，某些 logger 在目标构建里可能缺席，需对照实际版本核验；Hyperscan 是可选加速、缺失回退 `src/search_engines/` 下其他实现，不影响本层字段；线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」，`Logger` 注释给出的「ctor/dtor 主线程、其余包线程」是静态归属而非线程数量结论。

### 7. 常见误用与调试

第一类误用是把 `OutputSet` 的定义位置想当然。最常见错误是去 `src/loggers/loggers.h` 找 `struct OutputSet`，结果只看到一句 `load_loggers()` 声明便误判「输出集不存在」；真实定义在 `src/managers/event_manager.cc:61`，全局默认集是同文件的 `static OutputSet s_loggers`。第 4 节的 `grep -n "struct OutputSet"` 组合是最快确认手段，如结果与本节不符，以 `upstream_src/snort3/snort3-master/` 下实际源码为准并标注「需对照实际版本核验」。

第二类误用是把不透明句柄当普通结构展开。`Event::sig_info` 是引用成员，其生命周期由 `OptTreeNode` 持有；`SigInfo::refs`、`services`、`class_type` 与 `LogApi::base`、`Output::handler` 的具体布局都不在本篇头文件内，属于不透明句柄，内部布局见 `src/detection/signature.h` 关联定义、`src/framework/base_api.h` 与对应 `.cc`，不可依赖。用 `sizeof()`、指针偏移或 `reinterpret_cast` 去读这些成员，会在不同构建下静默错位；正确做法是只用已公开访问器，如 `Event::get_sig_ids()`、`get_msg()`、`EventManager::get_api()` 对应入口。

第三类误用是把 05 册当流程书或参数书读。想理解「事件怎样入队、排序、限速、写出」应去 06 册（`原理见 06-09`、`原理见 06-11`），想配一个 `alert_json` 段或 `event_filter` 应去 04 册（`参数见 04-02`、`参数见 04-08`），想按目录找 logger 模块应去 07 册（`模块见 07-08`、`模块见 07-11`）；反过来，在 06 / 07 / 08 册里看到完整事件字段表属于去重铁律被破坏，应改写成「字段见 05-08」。

第四类是场景前提误判。加密载荷不可见时，`buffs_to_dump` 与规则文本字段不含明文正文；IDS 旁路模式下只告警不丢弃，与 verdict 相关的字段不会被写成 drop；tagged packet 的 `event_reference` 才有非零引用值，普通事件为 0；`head` 为空时走全局 `s_loggers`，`LogList` / `AlertList` 为 nullptr 属正常路径而非字段缺失。把「字段没值」当成「字段定义错误」是最常见的排错弯路，应先确认运行模式与输出绑定方式，再查字段。

第五类是数值与类型误读。`Event::ts_sec`、`ts_usec`、`event_id` 是 `uint32_t`，`event_reference` 同为 `uint32_t`，`file_id` 是 `uint64_t`，跨 32/64 位构建打印时格式符要匹配；`SF_EVENTQ::cur_nodes`、`fails` 是 int / unsigned，`fails` 由 `sfeventq_reset()` 返回而非直接读成员；`LogApi::flags` 是位掩码，判断 logger 类型要用位与而非等值比较。调试时若字段读数与源码声明长期不一致，先用 `snort -V` 核对构建标识、用 `snort -T` 做配置自检（完整参数见 04-07），再核对二进制与头文件是否同一快照。所有涉及吞吐、pps、丢包率、内存占用的结论一律「需在目标机型实测」，不给绝对值；基准方法见 08-01，诊断树见 08-03。

### 3. 逐项详解

**FlowCacheConfig 与流表容量字段**。`src/flow/flow_config.h` 的两个结构很薄，却是理解流表行为的入口。`FlowTypeConfig` 只有 `unsigned nominal_timeout = 0`，注释写明由 stream module 配置，说明「每协议标称超时」的权威参数在 stream 侧（`参数见 04-04`）。`FlowCacheConfig` 的 `max_flows`、`pruning_timeout`、`prune_flows` 分别对应容量、剪枝超时与单次剪枝数量，`proto[PktType::MAX]` 是按包类型索引的超时数组，下标来自 `PktType` 枚举，因此数组长度随枚举定义变化，不可硬编码。`allowlist_cache` 与条件编译字段 `move_to_allowlist_on_excess`、`allowlist_max_excess_flows` 被 `FlowCache::is_allowlist_on_excess()` 用来判断是否启用「超额转允许列表」路径，该路径还受 `ALLOWLIST_MOVE_ON_EXCESS` 宏控制（宏见 `CMakeLists.txt`，开关名需对照实际版本核验），`REG_TEST` 下的 `allowlist_test_force_enable` 只在测试构建出现。读这些字段时要先确认构建开关，条件编译字段在关闭宏的构建里根本不存在，不是「值为 0」。

**FlowCache 的哈希、链表与统计字段**。`class FlowCache`（`src/flow/flow_cache.h:62`）的私有段按用途分四组。配置与状态：`config`（配置副本）、`flags`（uint32_t，初值 0）。哈希与链表：`hash_table`（`ZHash*`，源码注释明确「Flows are stored in a ZHash instance by FlowKey」）、`uni_flows` 与 `uni_ip_flows`（`FlowUniList*`，单向流链表）；`ZHash` 与 `FlowUniList` 在本头文件只有前向声明，属不透明句柄，内部布局见对应 `.cc`，不可依赖。统计：`prune_stats`（`PruneStats`，类型见 `prune_stats.h`）、`delete_stats`、`empty_lru_mask`（uint64_t）、`excess_to_allowlist_count`（PegCount）。内存记账：`released_max_flow_mem`、`released_total_flow_mem` 两个 PegCount，源码注释特别说明「flow-memory accounting, sampled at release/retire. read Flow::get_mem_usage() directly rather than these pegs for specific flow memory」——这两个 peg 是采样值，不能当作单个流的精确内存，精确值应读 `Flow::get_mem_usage()`（字段见 05-02）。文件顶部还有一组紧凑常量：`max_protocols = PktType::MAX`、`allowlist_lru_index = max_protocols`、`total_lru_count = max_protocols + 1`、`all_lru_mask = (1ULL << max_protocols) - 1`、`first_proto`、`proto_lru_mask`、`rotated_lru_count`，它们位宽与协议枚举绑定，与 LRU 剪枝算法配合（原理见 06-05）。`max_blocked_unlink_per_prune`、`max_excess_examined_per_prune` 两个 static const 均为 256，用来限制单次剪枝遍历不可解链流的代价，注释指向 `dev_notes.txt`，属实现细节，需对照实际版本核验。

**FlowControl 的管理器字段与会话工厂数组**。`class FlowControl`（`src/flow/flow_control.h:51`）是管理器：`get_proto_session[to_utype(PktType::MAX)]` 是 `snort::InspectSsnFunc` 函数指针数组，由 `init_proto(PktType, InspectSsnFunc)` 填充，在 `process()` 建流时按包类型取出对应的会话工厂；这解释了「为什么不同协议会建出不同 Session 子类」——字段只记录工厂映射，具体如何建流属机制（原理见 06-05）。`num_flows`（PegCount，初值 0）是当前流计数，`get_flows()` 返回它；`cache`（FlowCache*）指向实际流表，`get_flow_cache()` 返回；`mem`（Flow*）是流对象复用指针；`exp_cache`（ExpectCache*）指向期望流缓存，服务于 FTP 数据通道这类「预知流」（`add_expected()`、`add_expected_ignore()`、`check_expected_flow()`）；`last_pkt_type`（PktType，初值 NONE）记录最近包类型。注意 `FlowControl` 本身几乎不持有流数据，真正的数据在 `FlowCache` 与 `Flow` 中，读字段时不要把管理器误当容器。`stale_flow_cleanup()`、`apply_flow_state()`、`prune_one()` 等入口只在此列名，状态机归 06-05。

**Session 基类与统计宏字段**。`src/flow/session.h` 的 `class Session` 数据面极简：唯一成员 `public: snort::Flow* flow`（第 91 行，注释标 `FIXIT-L use reference?`），由 protected 构造 `Session(snort::Flow* f) { flow = f; }` 初始化，形成 `Session ↔ Flow` 的双向回指（`Flow::session` 字段见 05-02）。其余全是虚方法：`setup()`、`setup_after_restart()`、`update_direction()`（源码注释说当前只有 UDP 实现，其余调用会 `assert(false)`）、`process()`、`restart()`、`precheck()`、`clear()`（纯虚，子类必须实现）、`cleanup()`、`add_alert()`/`check_alerted()`/`update_alert()`（事件去重相关，原理见 06-09）、`flush()` 系列与 `flush_client()`/`flush_server()`/`flush_talker()`/`flush_listener()`、`set_splitter()`/`set_splitter_with_rescan()`/`get_splitter()`/`get_paf_position()`（分帧相关，原理见 06-05）、`is_sequenced()`/`are_packets_missing()`/`missing_in_reassembled()`（重组状态）等。`SESSION_PEGS(module)`、`SESSION_STATS`、`SESSION_STATS_ADD(stats)` 三个宏把 `sessions`、`max`、`created`、`released`、`timeouts`、`prunes`、`stale_packets` 七个 PegCount 统一到各协议子类的统计数组；源码特别强调 `max` 的语义是「性能周期内的最高值」，跨周期最大值需取各周期上报 max 的最大值，这条语义是读统计字段的关键，需对照实际版本核验。各协议子类的内部状态落在 `src/stream/tcp/`、`udp/`、`ip/`、`base/`，属不透明句柄，内部布局见对应 `.cc`，不可依赖。

**HA 状态与期望流字段**。`src/flow/ha.h` 提供高可用状态机。`FlowHAState` 挂在 `Flow::ha_state`（flow.h:505）上，每个活跃流一个实例；私有字段 `next_update`（timeval）、`pending`（uint16_t，位掩码，初值 `NONE_PENDING = 0x0000`）、`state`（uint8_t，初值 `NEW | NEW_SESSION`）。状态位枚举为 `NEW = 0x01`、`MODIFIED = 0x02`、`DELETED = 0x04`、`STANDBY = 0x08`、`NEW_SESSION = 0x10`，两个静态级别 `CRITICAL = 0x80`、`MAJOR = 0x40`；静态 `min_session_lifetime`、`min_sync_interval` 由 `config_timers()` 设置（参数见 04-08）。`FlowHAClientHandle` 是 uint16_t，`ALL_CLIENTS = 0xffff`，句柄 0 定义为主会话客户端；`FlowHAClient` 的 `handle`、`index`、`max_length` 字段由注册期分配，`HighAvailabilityManager::HA_INDEX_UNASSIGNED = 0xFF` 表示未分配。`HAMessage` 的 `buffer`、`buffer_length`、`cursor` 描述消息缓冲区与游标，`fits()` 做边界检查、`advance_cursor()` 推进——注意 `buffer_length` 是 const 成员，构造后不可改。`ExpectCache`（`src/flow/expect_cache.h:42`）的 `hash_table`、`nodes`、`pool`、`free_list` 四字段是典型的「哈希 + 对象池 + 空闲链」结构，`expects`、`realized`、`prunes`、`overflows` 四个 unsigned long 是统计计数，由 `reset_stats()` 清零；注释说明它用于跟踪 FTP 数据通道这类预知流，命中后用给定信息更新。这些都是字段存在与用途，状态机归原理册。

**内存池与记账字段**。`src/memory/` 的字段可分三层。`MemoryConfig`（`memory_config.h:26`）是纯配置载体：`cap`（size_t，初值 0）、`threshold`（unsigned，初值 0）、`interval`（1000）、`prune_target`（1048576）、`enabled`（false）；初值照抄源码，可调范围与含义归 04 册（`参数见 04-08`）。`MemoryCounts`（`memory_cap.h:37`）是统计载体，二十个 PegCount 分三段：启动/当前/峰值用量（`start_up_use`、`cur_in_use`、`max_in_use`）、纪元与分配释放次数（`epochs`、`allocated`、`deallocated`）、回收周期与结果（`reap_cycles`、`reap_attempts`、`reap_failures`、`reap_aborts`、`reap_decrease`、`reap_increase`），以及只用于报告的 `app_all`、`active`、`resident`、`retained` 和 shim 统计 `dpf_n_*`。`MemoryCap` 与 `HeapInterface` 是门面：`MemoryCap` 全是静态方法，注释按「主线程 / 包线程 / 两者」分组，例如 `set_heap_interface()` 属主线程、`free_space()` 属包线程、`get_mem_stats()` 属两者；`HeapInterface` 的 `main_init()`、`thread_init()`、`get_process_total()`、`get_thread_allocs()` 是纯虚，具体堆实现属不透明句柄，见对应 `.cc` 与所链接分配器。`MemoryAllocator::allocate()` 内联 `malloc()`、析构内联 `free()`，说明默认分配器是薄封装，不要把它误读成自带内存池实现——真正的容量控制由 `MemoryCap` 配合 pruner 完成（原理见 06-13）。读写时机上，配置字段在配置期写，统计字段在包线程记账，门面方法在主线程初始化，三者不可混用线程假设。

### 4. 典型示例

下面这段 C++ 片段用于核对流生命周期与 HA 字段的取值，只读取一个已存在 `Flow` 的超时、内存记账与 HA 状态字段并打印，不触发建流、剪枝或同步流程，便于在本地调试构建里确认字段与头文件一致。示例输出，具体格式需对照实际版本核验。

```cpp
#include "flow/flow.h"
#include "flow/ha.h"
#include <cstdio>

static void dump_flow_lifecycle(const snort::Flow& f)
{
    std::printf("expire=%llu idle=%u default=%u\n",
        (unsigned long long)f.expire_time,
        f.idle_timeout, f.default_session_timeout);
    std::printf("flow_id=%llu conn_id=%llu\n",
        (unsigned long long)f.flow_id,
        (unsigned long long)f.connection_id);
    std::printf("mem=%zu peak=%zu ha=%p\n",
        f.get_mem_usage(), f.get_peak_mem_usage(),
        static_cast<const void*>(f.ha_state));
}
```

在一个接入调试构建、已建立单条 TCP 流的测试桩里，输出类似如下。示例输出，具体格式需对照实际版本核验。

```text
expire=1762809660 idle=0 default=30
flow_id=0 conn_id=17
mem=1024 peak=1024 ha=0x0000000000c40010
```

逐行判读如下，合计超过 150 字。第一行 `expire=1762809660` 是 `Flow::expire_time`（flow.h:535，uint64_t，初值 0），它是一个绝对时刻而非相对秒数，作为剪枝判据与当前时间比较（原理见 06-05）；`idle=0`、`default=30` 分别是 `idle_timeout` 与 `default_session_timeout`（flow.h:549-550），前者为 0 表示未单独设置空闲超时，后者 30 是 stream 侧下发的标称超时（字段见 05-09 第 2 节、参数见 04-04）。若 `expire_time` 恒为 0 而流仍在，先确认 `set_expire()` 是否被调用，而不是怀疑剪枝逻辑。`flow_id=0` 来自 `Flow::flow_id`（flow.h:551），源码注释说明它「provided from the DAQ module or underlying hardware」，值为 0 常见于 pcap 离线文件这类无硬件流标识的 DAQ module（抓包依赖独立 libdaq，原理见 06-02），属正常；`conn_id=17` 来自 `connection_id`（flow.h:617），注释说明由插件提供，与 flow_id 来源不同，二者不可互换。`mem=1024 peak=1024` 来自私有成员 `mem_bytes`、`peak_mem_bytes`，初值均为 `sizeof(Flow)`（flow.h:613-614），通过 `get_mem_usage()`、`get_peak_mem_usage()` 读取；本例相等说明该流尚未挂接额外 inspector 状态，`add_mem()`/`sub_mem()` 未产生增量；注意 `MemoryCap` 的 `released_*` peg 是采样值，不能用它反推单个流内存。`ha=0x0000000000c40010` 是 `ha_state`（`FlowHAState*`，flow.h:505）指针，非空表示启用 HA（字段见 05-09 第 2 节）；其 `state` 位的含义须回查 `src/flow/ha.h`，不能靠指针非空推断状态。以上只作字段可读性核对，内存与吞吐一律「需在目标机型实测」。字段完整定义见 05-09 本节，流生命周期见「原理见 06-05」，HA 与线程见「原理见 06-13」，目录职责见「模块见 07-10 ｜ 模块见 07-13」。

### 6. 版本差异

代际差异首先体现在「谁持有流与会话状态」。Snort 2 用 C 结构体与全局流表，配置来自 `snort.conf`；Snort 3 是从 Snort 2 重写的 C++ 全新实现，配置改为 Lua，把流表管理拆成 `FlowControl`（管理器，`src/flow/flow_control.h`）与 `FlowCache`（缓存，`src/flow/flow_cache.h`）两层，把会话抽象收敛为 `class Session`（`src/flow/session.h`）单一基类、各协议子类落在 `src/stream/`，并用 `FlowData`/`FlowDataStore`（`src/flow/flow_data.h`，字段见 05-02）让 inspector 以 id 挂接自己的状态。因此「在 Session 里找 TCP 会话状态」「去 `src/session/` 找会话定义」都是 Snort 2 习惯，在 3.x 不成立：本快照无独立 `src/session/` 目录，`class Session` 在 `src/flow/session.h`。HA 也是新增能力，`FlowHAState`（`src/flow/ha.h`）挂到 `Flow::ha_state`，涉及 DAQ 通道与客户端注册，具体兼容边界需对照实际版本核验。Lua 取代 `snort.conf`，流表与内存参数归 04 册（`参数见 04-04`、`参数见 04-08`），`tools/snort2lua/` 只是格式转换辅助，不等于字段可直接沿用。插件 ABI 不通用，`SO_PUBLIC` 宏与版本派生见 05-01、05-04。

上游 master 快照（2026-11 抓取）内部的演进痕迹同样明显。`src/flow/session.h` 的 `flow` 成员注释标 `FIXIT-L use reference?`，说明指针改引用仍在讨论；`update_direction()` 里 `assert(false)` 并注明「UDP is currently the only stream that implements this」，反映协议实现的参差。`src/flow/flow_cache.h` 的 `is_allowlist_on_excess()` 被 `#ifdef ALLOWLIST_MOVE_ON_EXCESS` 包裹，`ALLOWLIST_MOVE_ON_EXCESS` 与 `allowlist_admission_scan_cap = 8` 是条件编译痕迹；`max_blocked_unlink_per_prune`、`max_excess_examined_per_prune` 常量注释指向 `dev_notes.txt`，属持续调优项。`src/flow/flow.h` 的 `ha_state`、`flow_id`、`connection_id`、`mem_bytes` 都是后加的字段（字段见 05-02），`FlowHAState` 的 `NEW_SESSION` 位与 `HighAvailabilityManager` 的 `register_ha_client()`（注释要求恰好一个客户端设 `is_session=true`）说明 HA 仍在演进。`src/memory/heap_interface.h` 的多个虚方法有默认实现、`MemoryCap` 的若干入口标注「main thread」与「packet threads」，说明线程归属是设计约定而非数量结论。这些都说明字段集合、顺序与位含义不是冻结的，任何依赖 `sizeof`、偏移、位编号或「声明顺序即业务顺序」的假设都必须标注「需对照实际版本核验」。具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，本套资料不写绝对版本号。

能力边界对字段可读性的影响要再次强调：抓包依赖独立 libdaq / DAQ3，`Flow::flow_id` 来自 DAQ module 或底层硬件，离线 pcap 下常为 0（原理见 06-02）；加密流量载荷不可见，`Flow::service`、`gadget`、`clouseau` 只记录 inspector / binder / wizard 的识别结果，不含明文；内联 IPS 的 drop / block 经 DAQ verdict 反馈，Snort 不是防火墙、不做转发（原理见 06-12）；Hyperscan 是可选加速、缺失回退 `src/search_engines/` 下其他实现，不影响本篇字段；线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」，`MemoryCap` 的线程分组只是静态归属。流量容量与内存占用类结论一律「需在目标机型实测」，不给绝对值。

### 7. 常见误用与调试

第一类误用是路径想当然，也是本篇最需强调的一条。把会话写成 `src/session/`（真实在 `src/flow/session.h`，本快照无独立目录）、把协议会话子类当成 `src/flow/` 内可见（真实在 `src/stream/tcp/`、`udp/`、`ip/`、`base/`）、把解码写成 `src/decode/`（真实由 `src/codecs/` 与 `src/protocols/packet.cc` 承担）。三者都会在源码检索时扑空，进而误判「结构体不存在」。第 4 节的 `test -d` / `grep -n` 组合是最快确认手段；如结果与本节不符，以 `upstream_src/snort3/snort3-master/` 下实际目录为准并标注「需对照实际版本核验」。

第二类误用是把不透明句柄当普通结构展开。`FlowCache` 里的 `ZHash*`、`FlowUniList*`，`FlowControl` 里的 `ExpectCache*`、`Flow* mem`，`ExpectCache` 里的 `ZHash*`、`ExpectNode*`、`ExpectFlow*`，`HighAvailabilityManager` 的 `PortBitSet* ports`，以及 `HeapInterface` 的具体堆实现，在本头文件都只有前向声明或纯虚接口，属于不透明句柄，内部布局见对应 `.cc` 或 `src/stream/`、`src/utils/`，不可依赖。用 `sizeof()`、指针偏移或 `reinterpret_cast` 去读成员，会在不同构建下静默错位；正确做法是只用公开访问器，如 `FlowCache::get_count()`、`FlowControl::get_flows()`、`Flow::get_mem_usage()`、`MemoryCap::get_mem_stats()`。

第三类误用是把统计 peg 当精确值。`FlowCache::released_max_flow_mem`、`released_total_flow_mem` 的源码注释明确是「sampled at release/retire」，并提示直接读 `Flow::get_mem_usage()` 获取单个流的精确内存；`SESSION_STATS` 的 `max` 语义是「性能周期内最高值」，跨周期最大值要取各周期上报 max 的最大值（源码注释明确此点）；`MemoryCounts::max_in_use` 是进程级峰值，与单流内存不是同一量纲。把采样 peg 当精确值、把周期峰值当全程峰值，是内存排错里最常见的两类数值误读。所有内存与吞吐结论一律「需在目标机型实测」。

第四类是把 05 册当流程书或参数书读。想理解「流怎样建立、超时、剪枝」应去 06 册（`原理见 06-05`），想配 `stream` / `flow` 的 memcap 或 HA 参数应去 04 册（`参数见 04-04`、`参数见 04-08`），想按目录找模块应去 07 册（`模块见 07-10`、`模块见 07-13`）；反过来，在 06 / 07 / 08 册里看到完整流字段表属于去重铁律被破坏，应改写成「字段见 05-09」。

第五类是条件编译与场景前提误判。`FlowCacheConfig` 的 `move_to_allowlist_on_excess`、`allowlist_max_excess_flows` 受 `ALLOWLIST_MOVE_ON_EXCESS` 控制，`allowlist_test_force_enable` 只在 `REG_TEST` 出现，关掉宏的构建里这些字段根本不存在，不是「值为 0」；`Flow::flow_id` 在离线 pcap 下为 0 属正常；HA 未配置时 `ha_state` 可能为空；加密流量下 `service`、`gadget` 只记录元数据而非明文。把「字段不存在/没值」当成「字段定义错误」是最常见的排错弯路，应先确认构建开关与运行模式，再查字段。调试时若字段读数与源码声明长期不一致，先用 `snort -V` 核对构建标识、用 `snort -T` 做配置自检（完整参数见 04-07），再核对二进制与头文件是否同一快照。所有涉及吞吐、pps、丢包率、内存占用的结论一律「需在目标机型实测」，不给绝对值；基准方法见 08-01，诊断树见 08-03。
