# Snort 3 技术资料 · 05 关键数据结构字段详解（分片 B）

## 05-06 RuleOption、PatternMatcher、MPSE 与 Hyperscan 结构字段

### 1. 本篇定位与覆盖范围

本篇是 05 册「检测与配置层」中专门讲规则选项对象、快速模式匹配数据与多模式搜索引擎字段的权威篇目。按总纲第 2 节唯一权威源约定，全集只有 05 册允许出现结构体逐字段定义；本篇只讲字段含义、类型、内存布局倾向、生命周期与关联函数入口，不展开机制流程（统一写「原理见 06-06」「原理见 06-07」），不重列配置参数（统一写「参数见 04-06」「参数见 04-01」）。事实基准统一写「上游 master 快照（2026-11 抓取）」；具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，本套资料不抄具体版本号进正文，凡未在快照中核验到的一律写「需对照实际版本核验」。本篇服务于两类读者：一类是想知道某条规则的 `content` 究竟落在哪个对象、哪个字段的检测规则编写者，另一类是要在 `src/` 里快速定位搜索引擎实现、又不愿被调用链淹没的源码研读者。两类需求都只在本篇得到字段层面的答案，机制与参数分别转向 06 册与 04 册。

本篇覆盖的源码面横跨四个真实目录。其一是 `src/ips_options/`：所有 IPS 规则关键字都实现为 `IpsOption` 的子类，在规则解析期实例化，关键词注册经 `src/managers/ips_manager.cc`。其二是 `src/detection/`：规则编译与快速模式相关结构集中在 `pattern_match_data.h`、`fp_config.h`、`fp_create.h/.cc`、`fp_detect.h/.cc`、`pcrm.h/.cc`，枚举 `option_type_t` 定义在 `src/detection/rule_option_types.h`。其三是 `src/framework/`：`mpse.h`、`mpse.cc`、`mpse_batch.h`、`mpse_batch.cc` 定义搜索引擎抽象基类与批处理结构。其四是 `src/search_engines/`：`hyperscan.cc`、`acsmx2.h/.cc`、`ac_bnfa.cc`、`ac_full.cc`、`bnfa_search.h/.cc`、`search_common.h`、`search_tool.h/.cc`，以及 `src/managers/mpse_manager.cc` 的注册入口。需要特别说明，`IpsOption` 与 `Mpse` 都是薄基类加厚子类的形态——基类字段极少，真正的业务数据落在 `src/ips_options/ips_*.cc` 的内部类与各搜索引擎实现文件里，这些子类对象在本快照中属于不透明句柄，内部布局见对应 `.cc`，不可依赖。因此本篇对子类只写「基类可见字段 + 子类所在文件 + 不透明边界」，不臆造子类内部成员名。

本篇把上述对象分成四族来讲。第一族是 RuleOption / IpsOption 族，包括 `option_type_t` 的四个取值、`IpsOption` 基类的两个私有字段、`EvalStatus` 四种求值返回、`CursorActionType` 七种游标动作、`RuleDirection` 三种方向，以及注册结构 `IpsApi`。第二族是 PatternMatcher 族，包括 `PatternMatchData` 与其标志位、`PmdLastCheck`、`MpseAgent`、`MpseMatch` 回调类型、`PatternMatchVector`。第三族是 MPSE 族，包括 `Mpse` 基类、`PatternDescriptor`、`MpseApi`、`MpseGroup`、`MpseBatch`、`MpseBatchItem`、`MpseBatchKey` 与 `FastPatternConfig`。第四族是 Hyperscan 与回退实现族，包括 `HyperscanMpse`、`Pattern`、`ScanContext`、`FullCounts`，以及 AC 实现的 `ACSM_STRUCT2`、`ACSM_PATTERN2`、`trans_node_t`。四族之间的数据归属与字段引用关系见图 05-06-01，图中实线为编译期构建链，虚线为运行期引用回查。

还要守住能力边界，避免把结构体的存在误读成能力。Hyperscan 是可选 search_engine 加速（`src/search_engines/hyperscan.cc`，构建开关见 `CMakeLists.txt`，选项名需对照实际版本核验），缺失时回退 `src/search_engines/` 下 `ac_bnfa.cc`、`ac_full.cc`、`acsmx2.cc`、`bnfa_search.cc` 等其他多模式匹配实现，不得写成必需依赖或唯一实现；因此本篇同时给出 Hyperscan 与 AC 回退两套结构字段，`hs_database_t`、`hs_scratch_t` 来自外部 Hyperscan 库，仓库内不可展开，属不透明句柄。规则关键字与 Snort 2 有差异（`src/ips_options/`、`src/parser/parse_rule.cc`、`src/detection/`），不宣称完全兼容。加密流量载荷不可见，与明文正文相关的缓冲字段在 HTTPS 场景取不到预期内容，这是场景前提而非字段定义错误。内联 IPS 的 drop / block 通过 DAQ verdict 反馈，Snort 本身不是防火墙、不做转发，verdict 相关字段归 05-07。许可按 GPLv2 处理，Talos 规则集另有独立许可约束；规则编译期内存与吞吐结论一律标注「需在目标机型实测」，不给绝对值，基准方法见 08-01。

### 3. 逐项详解

以下按四族逐族详解。每族给出「权威头文件 → 字段族特征 → 生命周期 → 不透明边界 → 归口」，全部字段以源码为准，凡未核验到的一律写「需对照实际版本核验」。

**第一族 RuleOption / IpsOption。** 入口为 `src/framework/ips_option.h`、`src/detection/rule_option_types.h` 与 `src/framework/cursor.h`、`pdu_section.h`。源码注释写得很清楚：所有 IPS 规则关键字都实现为 IpsOption，并在规则解析时实例化。`option_type_t` 只有四个取值：`RULE_OPTION_TYPE_LEAF_NODE` 供规则编译器内部使用，`RULE_OPTION_TYPE_CONTENT`、`RULE_OPTION_TYPE_FLOWBIT` 旁注为「ideally would be eliminated」，`RULE_OPTION_TYPE_OTHER` 收容所有新增的缓冲无关选项——这组枚举是识别「老式专用类型」与「新式通用类型」的关键，读 `get_type()` 的返回值即可判断。`IpsOption` 基类私有段只有 `const char* name` 与 `option_type_t type` 两个字段，构造受保护；除了 `eval()`、`hash()`、`operator==()` 等虚方法，还用一组静态方法在实例化期回写规则元信息，例如 `set_gid()`、`set_sid()`、`set_rev()`、`set_message()`、`set_classtype()`、`set_priority()`、`set_enabled()`、`set_flowbits_check()`、`set_detection_filter()`、`set_stateless()`、`set_to_client()`、`set_to_server()`、`set_file_id()`、`add_reference()`、`add_service()`、`set_tag()` 等。生命周期上，这些静态方法只在 `IpsNewFunc` 实例化窗口内可用，运行期包线程调用的是 `eval(Cursor&, Packet*)`、`action(Packet*)`、`retry(Cursor&)`、`hash()` 等，`eval()` 返回 `EvalStatus` 四值 `NO_MATCH`、`MATCH`、`NO_ALERT`、`FAILED_BIT`。`get_cursor_type()` 返回 `CursorActionType`，七值为 `CAT_NONE`、`CAT_READ`、`CAT_ADJUST`、`CAT_SET_OTHER`、`CAT_SET_RAW`、`CAT_SET_FAST_PATTERN`、`CAT_SET_SUB_SECTION`；`is_buffer_setter()` 以返回值是否大于 `CAT_ADJUST` 判断该选项是否设置缓冲。`get_pattern()` 与 `get_alternate_pattern()` 是 fast pattern 选项的钩子，默认返回空指针。`RuleDirection` 三值 `RULE_FROM_CLIENT`、`RULE_FROM_SERVER`、`RULE_WO_DIR` 描述方向。注册结构 `IpsApi` 首成员是 `BaseApi base`，随后 `RuleOptType type`（`OPT_TYPE_LOGGING`、`OPT_TYPE_DETECTION`、`OPT_TYPE_META`、`OPT_TYPE_MAX`）、`int max_per_rule`（零为不限、负为告警）、`unsigned protos`（`PROTO_BIT_*` 位掩码）以及 `pinit`、`pterm`、`tinit`、`tterm`、`ctor`、`dtor`、`verify` 七个函数指针。`IPSAPI_VERSION` 为 `((BASE_API_VERSION << 16) | 4)`，跨版本加载 SO 规则必须校验，兼容边界需对照实际版本核验。字段归本篇，关键字全集见 04-06，解析与求值链见 06-06、06-08，模块见 07-01。

**第二族 PatternMatcher。** 入口为 `src/detection/pattern_match_data.h` 与 `src/search_engines/search_common.h`。`PatternMatchData` 是 content 类选项承载模式的核心结构，`struct PmdLastCheck` 与其同文件。源码在 `sticky_buf` 之后写有分隔注释「data above this point is for framework use only」，把结构分成框架段与业务段：框架段是 `PmdLastCheck* last_check` 与 `const char* sticky_buf`，其中 `last_check` 仅在 `exception_flag` 置位时才分配，用于否定 content 的上次检测复核；业务段依次是 `const char* pattern_buf`、`unsigned pattern_size`、`int offset`、`unsigned depth`、`uint16_t flags`、`uint16_t mpse_flags`、`uint16_t fp_offset = 0`、`uint16_t fp_length = 0`。标志位枚举为 `NEGATED = 0x01`、`NO_CASE = 0x02`、`RELATIVE = 0x04`、`LITERAL = 0x08`、`FAST_PAT = 0x10`、`NO_FP = 0x20`、`SUB_SECT = 0x40`，配套 `set_negated()`、`set_no_case()` 等置位方法与 `is_negated()`、`is_fast_pattern()` 等查询方法；`is_unbounded()` 以 `depth` 为零判定无界。`PmdLastCheck` 四字段为 `struct timeval ts`、`uint64_t context_num`、`uint32_t rebuild_flag`、`uint16_t run_num`。本族有两个值得记住的内联判定：`can_be_fp()` 要求 `pattern_buf` 与 `pattern_size` 非空且未置 `NO_FP`，否定 content 还须非相对、无 offset、无 depth 且大小写不敏感，否则不参与快速模式；`has_alpha()` 在 `fp_offset` 起、`fp_length`（为零则用 `pattern_size`）止的区间内找字母。`PatternMatchVector` 是 `std::vector<PatternMatchData*>` 的别名。`MpseAgent`（`search_common.h`）是五个回调指针构成的小结构：`build_tree`、`negate_list`、`user_free`、`tree_free`、`list_free`，它是搜索引擎与规则树之间的桥；`MpseMatch` 定义为 `typedef int (* MpseMatch)(void* user, void* tree, int index, void* context, void* list)`，命中回调用它把规则树交回检测侧。生命周期上，本族对象在规则解析期创建、编译期被读出构建自动机、运行期只读，字段归本篇，fast pattern 选择原理见 06-07，关键字见 04-06，模块见 07-05。

**第三族 MPSE。** 入口为 `src/framework/mpse.h`、`mpse_batch.h` 与 `src/detection/fp_config.h`。`Mpse` 是抽象基类，`SEAPI_VERSION` 为 `((BASE_API_VERSION << 16) | 3)`，注释明确「此文件任何改动都会改变 SEAPI_VERSION」。公开 nested 类型 `PatternDescriptor` 五字段：`bool no_case`、`bool negated`、`bool literal`、`bool multi_match`、`unsigned flags`，构造函数带默认值，它决定模式以何种语义插入引擎。`MpseType` 两值 `MPSE_TYPE_NORMAL`、`MPSE_TYPE_OFFLOAD`；`MpseRespType` 三值 `MPSE_RESP_COMPLETE_FAIL`、`MPSE_RESP_NOT_COMPLETE`、`MPSE_RESP_COMPLETE_SUCCESS`。纯虚接口是 `add_pattern()`、`prep_patterns(SnortConfig*)`、`search()`，另有 `search_all()`、`search(MpseBatch&, MpseType)`、`receive_responses()`、`poll_responses()`、`set_opt()`、`print_info()`、`get_pattern_count()`、`serialize()`、`deserialize()`、`get_hash()` 等，多数有默认实现，便于回退引擎少写方法。私有段只有 `std::string method`、`int verbose = 0`、`const MpseApi* api = nullptr` 三字段，外部经 `get_method()`、`set_verbose()`、`get_api()`、`get_pattern_count()` 访问，本册不臆造访问器。`MpseApi` 首成员 `BaseApi base`，随后 `uint32_t flags`（`MPSE_BASE 0x00`、`MPSE_REGEX 0x02`、`MPSE_ASYNC 0x04`、`MPSE_MTBLD 0x08` 的位掩码）、`activate`、`setup`、`start`、`stop`、`ctor`、`dtor`、`init`、`print`、`poll` 九个函数指针。`MpseGroup` 持有 `Mpse* normal_mpse`、`Mpse* offload_mpse` 与 `bool normal_is_dup`、`bool offload_is_dup`，`get_offload_mpse()` 在 offload 未配置时回落到 normal，`can_fallback()` 以两者是否不同判断能否回退。`MpseBatchItem` 有 `std::vector<MpseGroup*> so`、`bool done`、`bool error`、`int matches`；`MpseBatchKey` 模板两字段 `BUF buf`、`LEN len` 加相等比较；`MpseBatch` 聚合 `MpseMatch mf`、`void* context`、`std::unordered_map<MpseBatchKey<>, MpseBatchItem, MpseBatchKeyHash> items` 与 `search()`、`receive_responses()`、`offload_search()`、`search_sync()` 等方法。`FastPatternConfig` 是 MPSE 工厂，私有段字段为两个 `const MpseApi*` 指针 `search_api`、`offload_search_api`，布尔 `inspect_stream_insert = true`、`split_any_any = false`、`debug = false`、`dedup = true`，数值 `max_queue_events = 5`、`bleedover_port_limit = 1024`、`max_pattern_len = 0`、`queue_limit = 0`、`portlists_flags = 0`、`num_patterns_truncated = 0`，以及仅在 `HAVE_HYPERSCAN` 下存在的 `std::string rule_db_dir`。生命周期上，配置在解析期写入、编译期消费，运行期多为只读；字段归本篇，构建选项见 04-01，规则选项参数见 04-06，注册与检索原理见 06-07，模块见 07-01 与 07-05。

**第四族 Hyperscan 与回退 AC。** 入口为 `src/search_engines/hyperscan.cc` 与 `acsmx2.h`。`hyperscan.cc` 内部匿名命名空间的 `struct Pattern` 七字段：`std::string pat`、`unsigned len`、`unsigned flags`、`bool no_case`、`bool negate`、`void* user`、`void* user_tree`、`void* user_list`；构造函数把 `Mpse::PatternDescriptor` 翻译过来，按 `no_case` 置 `HS_FLAG_CASELESS`、按 `multi_match` 取反置 `HS_FLAG_SINGLEMATCH`，`escape()` 处理字面量转义。`HyperscanMpse : public Mpse` 私有段为 `const MpseAgent* agent`、`PatternVector pvector`、`hs_database_t* hs_db = nullptr`、`bool compiled = false`，公开静态计数 `instances`、`patterns`；`add_pattern()` 构造 `Pattern` 推入 `pvector` 并递增计数，`prep_patterns()` 里经 `hs_valid_platform()`、`hs_compile_multi(..., HS_MODE_BLOCK, ...)` 生成 `hs_db`，`serialize()` 用 `hs_serialize_database()`、`deserialize()` 用 `hs_deserialize_database()`，`get_hash()` 提供摘要。`hs_database_t`、`hs_scratch_t` 属外部库类型，仓库内不可展开，是不透明句柄。`ScanContext` 四字段 `HyperscanMpse* mpse`、`MpseMatch match_cb`、`void* match_ctx`、`int nfound = 0`，在 `search()` 中栈上构造，经 `hs_scan()` 回调累加 `nfound`，scratch 来自 `SnortConfig::get_conf()->state[get_instance_id()][scratch_index]`，由 `ScratchAllocator` 按实例分配。`FullCounts` 三字段 `PegCount searches`、`matches`、`bytes`，`hyper_pegs[]` 与之对应。`HyperscanModule` 是 `Module` 子类，`get_pegs()`、`get_counts()`、`get_profile()` 提供统计。回退侧 `ACSM_STRUCT2`（`acsmx2.h`）字段最丰富：`ACSM_PATTERN2* acsmPatterns`、`acstate_t* acsmFailState`、`ACSM_PATTERN2** acsmMatchList`、`trans_node_t** acsmTransTable`、`acstate_t** acsmNextState`、`const MpseAgent* agent`、五个整型 `acsmMaxStates`、`acsmNumStates`、`acsmNumTrans`、`acsmAlphabetSize`、`numPatterns`，以及 `int sizeofstate`；`ACSM_PATTERN2` 有 `next`、`patrn`、`casepatrn`、`udata`、`rule_option_tree`、`neg_list`、`n`、`nocase`、`negative`；`trans_node_t` 三字段 `acstate_t key`、`acstate_t next_state`、`trans_node_t* next`，源码注释说明把 `key` 声明为 `acstate_t` 是为避免跨缓存行重建。`#define AC32` 使 `acstate_t` 为 `unsigned int`、`ACSM_FAIL_STATE2` 为 `0xffffffff`。字段归本篇，选择与回退原理见 06-07，构建开关参数见 04-01，模块见 07-06。

### 4. 典型示例

下面给出一段字段级核验用的 C++ 片段，把 `IpsOption`、`PatternMatchData`、`Mpse`、`FastPatternConfig` 中若干已核验字段经公开访问器打印出来，用于确认本地快照的字段与接口确实存在。这不是流程代码，不触发规则编译或收包，仅作读源码对字段的核对手段。

```cpp
#include "framework/ips_option.h"
#include "detection/pattern_match_data.h"
#include "framework/mpse.h"
#include "detection/fp_config.h"
#include <cstdio>

void dump_fp_fields(const snort::IpsOption& opt,
    const PatternMatchData& pmd, const snort::Mpse& mpse,
    const FastPatternConfig& fpc)
{
    std::printf("name=%s type=%d buffer_setter=%d\n",
        opt.get_name(), static_cast<int>(opt.get_type()),
        static_cast<int>(opt.is_buffer_setter()));
    std::printf("size=%u offset=%d depth=%u fp=%d\n",
        pmd.pattern_size, pmd.offset, pmd.depth,
        static_cast<int>(pmd.is_fast_pattern()));
    std::printf("method=%s patterns=%d\n",
        mpse.get_method(), mpse.get_pattern_count());
    std::printf("dedup=%d maxq=%u bleed=%d\n",
        static_cast<int>(fpc.deduplicate()),
        fpc.get_max_queue_events(), fpc.get_bleed_over_port_limit());
}
```

在一个把上述函数接入调试构建、并加载少量含 content 规则的测试桩里，会得到类似下面的输出。示例输出，具体格式需对照实际版本核验。

```text
name=content type=1 buffer_setter=1
size=6 offset=0 depth=0 fp=1
method=hyperscan patterns=0
dedup=1 maxq=5 bleed=1024
```

逐行判读如下，合计超过 150 字。第一行 `name=content` 来自 `IpsOption::get_name()`，返回的是构造时传入的 `name` 私有字段；若这里出现空串，说明实例化时传入了空关键字名，应回查 `src/ips_options/ips_content.cc` 的构造函数而非怀疑访问器。`type=1` 对应 `option_type_t` 的 `RULE_OPTION_TYPE_CONTENT`，因为源码注释写明该值「ideally would be eliminated」，新关键字多用 `RULE_OPTION_TYPE_OTHER`，所以当看到新选项返回 3 属正常，返回 1 则多为 content 与 flowbit 这类历史类型。`buffer_setter=1` 是 `is_buffer_setter()` 的结果，它比较 `get_cursor_type()` 是否大于 `CAT_ADJUST`，content 通常设置快速模式相关游标，因此为真合理；若某 sticky buffer 选项返回 0，需确认其 `get_cursor_type()` 是否停留在 `CAT_READ`。第二行 `size=6` 是 `pattern_size`，与规则里 content 的字节数一致；`offset=0`、`depth=0` 表示未限定搜索范围，`is_unbounded()` 会返回真；`fp=1` 说明该 content 被选为快速模式，前提是 `can_be_fp()` 成立，即未置 `NO_FP`、非相对否定等条件均满足。第三行 `method=hyperscan` 来自 `Mpse::get_method()`，对应构造 `Mpse("hyperscan")` 时写入的私有 `method`；若构建未启用 Hyperscan，这里应是 `ac-bnfa`、`ac-full` 或 `acsmx2` 等回退方法名，具体名称需对照实际版本核验；`patterns=0` 来自 `get_pattern_count()`，表示尚未向该引擎加入模式，若已编译规则则应为非负计数，其取值由具体引擎实现决定。第四行 `dedup=1`、`maxq=5`、`bleed=1024` 分别对应 `FastPatternConfig` 的 `dedup`、`max_queue_events`、`bleedover_port_limit` 默认值，与 `fp_config.h` 私有段声明逐一吻合；若实测与此不符，多半是 `lua/snort.lua` 的对应段改写了配置（参数见 04-06），而非头文件字段变更。以上判读只覆盖字段取值，字段完整定义见本篇第 2、3 节，快速模式选择链见 06-07，回退行为见 08-04。

### 6. 版本差异

最根本的代际差异是规则选项与搜索引擎的承载方式。Snort 2 以 C 结构体加全局配置表组织规则与匹配，Snort 3 是从 Snort 2 重写的 C++ 全新实现，配置为 Lua（`lua/snort.lua`、`lua/snort_defaults.lua`），不兼容 Snort 2 的 `snort.conf` 与插件 ABI，`tools/snort2lua/` 只是格式转换辅助工具。规则关键字由 `IpsOption` 子类实现并在解析期实例化（源码注释明确这一点），`option_type_t` 只保留四值且 `CONTENT`、`FLOWBIT` 被标注为理想情况下应消除，说明新设计倾向让所有选项统一走 `RULE_OPTION_TYPE_OTHER` 与 sticky buffer 机制；这与 Snort 2 的关键字注册模型不同，规则关键字与 Snort 2 有差异，不宣称完全兼容。插件 ABI 不通用：`BaseApi`（`src/framework/base_api.h`，`BASE_API_VERSION`）作为所有插件 API 的首成员，`IPSAPI_VERSION` 为 `((BASE_API_VERSION << 16) | 4)`、`SEAPI_VERSION` 为 `((BASE_API_VERSION << 16) | 3)`，跨版本加载 SO 规则或搜索引擎插件必须校验，具体兼容边界需对照实际版本核验。

上游 master 快照（2026-11 抓取）内部的演进痕迹同样要谨慎。`src/framework/ips_option.h` 里 `set_detection_filter()` 旁注「don't install header」，`IpsApi::max_per_rule` 用负值触发告警，`CursorActionType` 出现 `CAT_SET_SUB_SECTION` 这样的新增值，都说明接口在持续扩张。`src/detection/pattern_match_data.h` 的「FIXIT-L wasting some memory here」注释与 `PmdLastCheck` 仅在 exception 时分配，反映否定 content 处理是后来补入的；该文件的「data above this point is for framework use only」分隔注释意味着字段位置有语义，不可随意前后移动。`src/framework/mpse.h` 把 `search(MpseBatch&, MpseType)`、`receive_responses()`、`poll_responses()` 加进基类并暴露 `MpseType` 的 offload 值，说明批量与异步检索是较新能力；`src/framework/mpse_batch.h` 的 `normal_is_dup`、`offload_is_dup` 与 `can_fallback()` 进一步佐证这一点。`src/detection/fp_config.h` 的 `rule_db_dir` 被 `#ifdef HAVE_HYPERSCAN` 包裹，未启用该构建的布局缺少此字段。这些都是版本演进中的真实痕迹，任何依赖字段偏移、结构体大小或声明顺序即业务顺序的假设都不可靠，结论一律以当前快照源码为准并标注「需对照实际版本核验」。具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，本套资料不写绝对版本号。

Hyperscan 始终是可选加速，构建开关见 `CMakeLists.txt`（选项名需对照实际版本核验），缺失时回退 `src/search_engines/` 下 AC / BNFA 实现，`FastPatternConfig::rule_db_dir` 之类的字段不改变这一事实；因此本篇同时保留 `HyperscanMpse` 与 `ACSM_STRUCT2` 两套字段，不能只按 Hyperscan 布局假设。许可始终按 GPLv2 处理，Talos 规则集另有独立许可约束；加密载荷不可见，与明文正文相关的缓冲字段在 HTTPS 场景取不到预期内容。线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」，`SnortConfig` 里的相关字段只说明存在、不推断数量；批量检索计数与吞吐结论一律标注「需在目标机型实测」。

### 7. 常见误用与调试

第一类误用是把薄基类当厚对象展开。`IpsOption` 私有段只有 `name`、`type` 两个字段，`Mpse` 私有段只有 `method`、`verbose`、`api` 三个字段，很多人照着 Snort 2 的经验去找 content 的偏移、depth 或 AC 的状态表，结果在基类里找不到就断言「字段不存在」。正确做法是顺着 `get_pattern()` 找到 `PatternMatchData`，顺着 `get_api()` 与 `MpseGroup` 找到具体引擎对象；各关键字子类与各引擎实现文件在本快照属于不透明句柄，内部布局见 `src/ips_options/ips_*.cc` 与 `src/search_engines/*.cc`，不可依赖。用 `sizeof()`、指针偏移或 `reinterpret_cast` 去读这些子类的成员，会在不同构建、不同引擎选择下静默错位。

第二类误用是把可选依赖当必需依赖。Hyperscan 未启用时 `method=hyperscan` 不会出现，与 Hyperscan 专属结构（`hs_db`、`ScanContext`、`rule_db_dir`）相关的字段也不可用；此时回退的是 `ac_bnfa`、`ac_full`、`acsmx2` 等实现，`ACSM_STRUCT2` 的字段才有意义。排错时应先用第 4 节的命令确认构建开关与 `get_method()` 返回值，再判断某字段是否应当存在，而不是反过来用字段不存在推断引擎缺失。同理，加密流量载荷不可见，sticky buffer 中本应放明文正文的字段在 HTTPS 场景取不到预期内容，这是场景前提而非字段定义错误。

第三类误用是把 05 册当流程书或参数书读。想理解 fast pattern 怎么从规则编译成自动机、命中后如何回到 option 链，应去 06 册（`原理见 06-06`、`原理见 06-07`、`原理见 06-08`）；想配一个 content 修饰符或 Hyperscan 构建开关，应去 04 册（`参数见 04-06`、`参数见 04-01`）；想按目录找 `ips_options` 与 `search_engines` 模块，应去 07 册（`模块见 07-06`）。反过来，在 06 / 07 / 08 册里看到完整字段表属于去重铁律被破坏，应改写成「字段见 05-06」。

第四类是跨版本字段假设与标志位误读。`IPSAPI_VERSION`、`SEAPI_VERSION` 随框架改动抬升，`#ifdef HAVE_HYPERSCAN`、`AC32` 等编译开关改变布局，`PatternMatchData::flags` 的位定义、`MpseApi::flags` 的 `MPSE_*` 位掩码都以当前头文件为准，硬编码数值或位序会失效。调试时若读到看似合理但明显不对的值，先确认二进制与所用头文件是否同一快照，再用 `snort -V` 核对构建标识、用 `snort -T` 做配置自检（两条命令的完整参数见 04-07），最后回到源码逐字段比对。所有涉及吞吐、pps、内存占用的结论一律标注「需在目标机型实测」，不给绝对值；基准方法见 08-01，诊断树见 08-03，Hyperscan 未启用导致吞吐变化的案例见 08-04。

## 05-07 DAQ 与 packet I/O 结构（DAQ_PktHdr、Verdict）字段

### 1. 本篇定位与覆盖范围

本篇是 05 册 DAQ / 包 I/O 层字段的权威定义篇，逐字段核对 `src/packet_io/sfdaq.cc/.h`、`sfdaq_instance.cc/.h`、`sfdaq_config.cc/.h`、`sfdaq_module.cc/.h`、`active.cc/.h`、`active_action.h`、`trough.cc/.h`、`sfdaq_static_modules.h.in`，以及 `src/connectors/`、`src/side_channel/`、`src/protocols/packet.h` 中的 DAQ 相关字段。覆盖对象族为 `SFDAQ`、`SFDAQInstance`、`SFDAQConfig`、`SFDAQModuleConfig`、`SFDAQModule`、`DAQStats`、`Active`、`ActiveAction`、`ActiveSuspendContext`，以及来自 libdaq 的 `DAQ_PktHdr_t`、`DAQ_Msg_h`、`DAQ_Verdict`、`DAQ_Stats_t`、`DAQ_Instance_h` 等类型。所有字段名、类型、默认值与源码行号取自「上游 master 快照（2026-11 抓取）」的实际头文件，逐条 Read / Grep 后写出；凡本快照未给出定义、或定义落在外部库的类型，一律写明不透明边界并标注「需对照实际版本核验」。本篇只讲字段含义、类型、内存布局倾向、生命周期与关联函数入口，不展开抓包与 verdict 机制（统一写「原理见 06-02」「原理见 06-12」），不重列 DAQ 配置参数（统一写「参数见 04-03」），不展开目录职责（统一写「模块见 07-07」）。

必须先说清不透明边界，这是本篇最重要的阅读前提。对 `sfdaq.h`、`sfdaq_instance.h`、`sfdaq_module.h`、`active.h` 的核验显示，这些文件都 `#include <daq_common.h>`，而在本快照的仓库树内用 `find` 找不到该头文件——它来自独立的 libdaq / DAQ3 依赖，不在 Snort 仓库中。因此 `DAQ_PktHdr_t`、`DAQ_Msg_h`、`DAQ_Verdict`、`DAQ_Stats_t`、`DAQ_Instance_h`、`DAQ_Config_h`、`DAQ_RecvStatus`、`DAQ_IoctlCmd` 都是不透明句柄，内部布局见所装 libdaq 头文件，不可依赖。本册能确认的只有几件事实：Snort 侧以指针或句柄形式保存它们；`SFDAQ::verdict_to_string()` 直接转调 libdaq 的 `daq_verdict_string()`；`SFDAQ::forwarding_packet()` 读取 `DAQ_PktHdr_t` 的 `flags` 字段与 `DAQ_PKT_FLAG_NOT_FORWARDING`；`Packet` 的访问器读取 `pkth->flags` 的 `DAQ_PKT_FLAG_SIGNIFICANT_GROUPS` 以及 `pkth->ingress_group`、`pkth->egress_group`；`sfdaq_module.cc` 用 `static_assert(MAX_DAQ_VERDICT == 6)` 约束 verdict 计数数组长度。凡涉及这些类型内部字段的准确成员名与偏移（例如包头的秒/微秒时间戳、caplen 字段的拼写），一律写「需对照实际版本核验」并给出 `src/packet_io/` 与所装 libdaq 头文件两个定位方向，不凭印象补字段名。这个边界也解释了为什么本篇要同时给出 Snort 侧包装结构与 libdaq 侧句柄两层字段：前者可核验，后者只能写存在与用途。

本篇把对象分成三族来讲。第一族是 DAQ 配置与会话族：`SFDAQConfig` 承载总体配置（`module_dirs`、`inputs`、`batch_size`、`mru_size`、`timeout`、`module_configs`），`SFDAQModuleConfig` 承载单个 module 的 `name`、`mode`、`variables`，`SFDAQModule` 承接 Lua `daq` 段，`SFDAQInstance` 承载运行期批次与消息池。第二族是 Packet 与包头族：`DAQ_Msg_h`、`DAQ_PktHdr_t` 在 `Packet` 中的借用指针 `daq_msg`、`pkth`，与 `pktlen`、`dsize`、`active`、`action` 等相邻字段，以及 `SFDAQ` 静态门面类。第三族是 verdict 与主动响应族：`DAQ_Verdict` 的六种取值、`DAQStats::verdicts[]` 计数槽、`Active` 的动作与状态枚举族、`ActiveAction` 的优先级与延迟执行、`ActiveSuspendContext` 的 RAII 挂起。三族的数据归属与字段引用关系见图 05-07-01，图中实线为收包到回传的主链，虚线为消息池释放与配置注入的辅助关系。

还要守住能力边界。抓包依赖独立 libdaq / DAQ3，`src/packet_io/sfdaq*.cc`、`sfdaq_config.cc`、`sfdaq_module.cc` 与 `daqs/` 是适配层，不得写成 Snort 自带抓包、与 DAQ 无关；DAQ module 决定抓包与内联能力（具体 module 名需对照实际版本核验）。内联 IPS 的 drop / block 通过 DAQ verdict 反馈（`src/actions/act_drop.cc`、`act_block.cc`、`act_reject.cc`、`src/packet_io/active.cc`），Snort 本身不是防火墙、不做 IP 转发、不做路由；IDS 旁路模式只告警不丢弃，因此 verdict 相关字段在旁路模式下不会被写成 drop，这是场景前提而非字段缺失。线程 / 进程模型以实际版本为准，不确定的一律标注需对照实际版本核验，禁止断言默认线程数；`SFDAQInstance` 的 `instance_id`、`batch_size` 只说明字段存在，不推断运行期实例数。性能、丢包率、内存占用一律标注「需在目标机型实测」，不给绝对值，DAQ 统计判读见 08-01、08-06，内联不 drop 的案例见 08-04。许可按 GPLv2 处理，Talos 规则集另有独立许可约束。

### 3. 逐项详解

以下按三族逐族详解。每族给出「权威头文件 → 字段族特征 → 生命周期 → 不透明边界 → 归口」，全部字段以源码为准，凡未核验到的一律写「需对照实际版本核验」。

**第一族 DAQ 配置与会话。** 入口为 `src/packet_io/sfdaq_config.h`、`sfdaq_module.h`、`sfdaq_instance.h` 与 `sfdaq_static_modules.h.in`。该头文件先把 DAQ 变量抽象成 `using DaqVar = std::pair<std::string, std::string>` 与 `using DaqVarList = std::vector<DaqVar>`，再在两个结构里分层承载配置。`SFDAQModuleConfig` 内嵌四值 `SFDAQMode`：`SFDAQ_MODE_UNSET`、`SFDAQ_MODE_PASSIVE`、`SFDAQ_MODE_INLINE`、`SFDAQ_MODE_READ_FILE`，字段为 `std::string name`、`SFDAQMode mode = SFDAQ_MODE_UNSET`、`DaqVarList variables`，并提供 `set_variable()`。`SFDAQConfig` 则是总体配置，字段为 `std::vector<std::string> module_dirs`、`std::vector<std::string> inputs`、`uint32_t batch_size`、`int mru_size`、`unsigned int timeout`、`std::vector<SFDAQModuleConfig*> module_configs`；常量 `BATCH_SIZE_UNSET = 0`、`SNAPLEN_UNSET = -1`、`BATCH_SIZE_DEFAULT = 64`、`SNAPLEN_DEFAULT = 1518`、`TIMEOUT_DEFAULT = 1000` 为静态成员，`get_batch_size()` 与 `get_mru_size()` 在字段为 UNSET 时回落到默认值。两结构均为 `struct`，字段是公开的，但本册只写含义与读写时机，不鼓励外部直接改写。这组默认值是理解「为什么批大小常是 64」的字段层依据，但运行期实际值取决于配置，参数见 04-03。`SFDAQModule` 是 `snort::Module` 子类，私有段只有 `SFDAQConfig* config` 与 `SFDAQModuleConfig* module_config` 两个指针，重写 `set()`、`begin()`、`end()` 接收 Lua 段，重写 `get_pegs()`、`get_counts()`、`prep_counts()`、`reset_stats()` 暴露统计，`counts_need_prep()` 返回真、`get_usage()` 返回 `GLOBAL`。`SFDAQInstance` 私有段十二个字段：`std::string input_spec`、`uint32_t instance_id = 0`、`DAQ_Instance_h instance = nullptr`、`DAQ_Msg_h* daq_msgs = nullptr`、`unsigned curr_batch_size = 0`、`unsigned curr_batch_idx = 0`、`uint32_t batch_size = 0`、`uint32_t pool_size = 0`、`uint32_t pool_available = 0`、`int dlt = -1`、`DAQ_Stats_t daq_instance_stats = { }`、`uint16_t daq_tunnel_mask = 0`。其中 `next_message()` 只用 `curr_batch_idx < curr_batch_size` 判断并返回 `daq_msgs[curr_batch_idx++]`，是纯字段访问的内联函数；`get_batch_size()`、`get_pool_available()` 直接返回对应字段。生命周期上，配置对象在解析期创建、装配期被读出，实例对象在 `init()` 期拿到 libdaq 句柄、收包期滚动批游标、终止期释放；`daq_msgs` 指向的是 libdaq 消息池中的句柄，Snort 只借用不拥有。字段归本篇，DAQ 段参数见 04-03，抓包与消息池原理见 06-02，模块见 07-07。

**第二族 Packet 与包头。** 入口为 `src/protocols/packet.h` 与 `src/packet_io/sfdaq.h`。`Packet` 中本族相关字段集中在 `reset()` 分隔符之后：`Active* active = nullptr`、`Active* active_inst = nullptr`、`ActiveAction** action = nullptr`、`ActiveAction* action_inst = nullptr`、`DAQ_Msg_h daq_msg = nullptr`（注释写明「DAQ message this packet came from」）、`SFDAQInstance* daq_instance = nullptr`、`const DAQ_PktHdr_t* pkth = nullptr`（注释「packet meta data」）、`uint32_t pktlen = 0`、`uint16_t dsize = 0`。这一串指针是包与 DAQ 的唯一接缝：`daq_msg` 与 `pkth` 是借用指针，包结束随消息池释放而失效，禁止跨包缓存；`pktlen` 是原始帧长度、`dsize` 是载荷长度，二者与 `alt_dsize` 的取值关系由 `get_dsize()` 依 `PKT_DETECT_LIMIT` 决定。包头内部字段的读取在源码中可见几处：`SFDAQ::forwarding_packet()` 以 `default_daq_mode == DAQ_MODE_INLINE && !(h->flags & DAQ_PKT_FLAG_NOT_FORWARDING)` 判定是否转发，`Packet` 的分组访问器读 `pkth->flags & DAQ_PKT_FLAG_SIGNIFICANT_GROUPS`、`pkth->ingress_group`、`pkth->egress_group`；这证明 `flags`、`ingress_group`、`egress_group` 是 `DAQ_PktHdr_t` 的可访问成员，但准确类型与其余成员仍属不透明句柄，需对照实际版本核验。`SFDAQ` 是静态门面类，`sfdaq.h` 未声明实例数据成员，全部为静态方法：`load()`、`unload()`、`print_types()`、`verdict_to_string()`、`init()`、`term()`、`init_instance()`、`get_input_spec()`、`default_type()`、`get_stats()`、`can_inject()`、`can_inject_raw()`、`can_replace()`、`can_run_unprivileged()`、`get_tunnel_bypass()`，`set_local_instance()`、`get_local_instance()`、`get_base_protocol()`、`inject()`、`forwarding_packet()` 等，若干方法标注 `SO_PUBLIC`。`verdict_to_string()` 的实现只有一行 `return daq_verdict_string(verdict)`，说明 verdict 到字符串的映射完全由 libdaq 掌握，本册不复制其枚举表。字段归本篇与 05-02，verdict 原理见 06-12，解码字段读取见 06-03，模块见 07-07 与 07-09。

**第三族 verdict 与主动响应。** 入口为 `src/packet_io/active.h`、`active_action.h`、`sfdaq_module.h`、`sfdaq_module.cc`。`DAQ_Verdict` 来自外部 `daq_common.h`，本仓库不可展开，属不透明类型；本册能给的确定事实是 `sfdaq_module.cc` 的 `static_assert(MAX_DAQ_VERDICT == 6)`，以及 `daq_names[]` 中连续六个求和计数项按序为 `allow`、`block`、`replace`、`whitelist`、`blacklist`、`ignore`，对应 `DAQStats::verdicts[MAX_DAQ_VERDICT]` 的六个槽；`SFDAQInstance::finalize_message(DAQ_Msg_h, DAQ_Verdict)` 是把判定回传给 libdaq 的入口。`DAQStats`（`sfdaq_module.h`）共二十二个字段，除前述 `pcaps`、`received`、`analyzed`、`dropped`、`filtered`、`outstanding`、`outstanding_max`、`injected`、`verdicts[6]` 外，还有 `internal_blacklist`、`internal_whitelist`、`skipped`、`idle`、`rx_bytes`、`expected_flows`、`retries_queued`、`retries_dropped`、`retries_processed`、`retries_discarded`、`sof_messages`、`eof_messages`、`other_messages`；`sfdaq_module.cc` 的减法运算符逐字段相减，`prep_counts()` 还用 `DAQ_Stats_t` 的差值刷新统计，注意源码注释「daq stats are cumulative」，不能简单清零。`Active` 是 verdict 语义的本地承载，私有段为静态 `act_str[ACT_MAX][AST_MAX]`、整数 `active_tunnel_bypass = 0`、`const char* drop_reason = nullptr`、四个枚举状态 `active_status = AST_MAX`、`active_would_reason = WHD_EXIT`、`active_action = ACT_MAX`、`delayed_active_action = ACT_MAX`，以及 `ActiveAction* delayed_reject = nullptr`。四组枚举分别是 `ActiveStatus` 五值 `AST_ALLOW`、`AST_CANT`、`AST_WOULD`、`AST_FORCE`、`AST_MAX`；`ActiveWouldReason` 八值 `WHD_NONE`、`WHD_INTERFACE_IDS`、`WHD_IPS_INLINE_TEST`、`WHD_NAP_INLINE_TEST`、`WHD_TIMEOUT`、`WHD_PRUNE`、`WHD_RELOAD`、`WHD_EXIT`；`ActiveSuspendReason` 五值 `ASP_NONE`、`ASP_PRUNE`、`ASP_TIMEOUT`、`ASP_RELOAD`、`ASP_EXIT`；`ActiveActionType` 九值 `ACT_TRUST`、`ACT_ALLOW`、`ACT_HOLD`、`ACT_RETRY`、`ACT_REWRITE`、`ACT_DROP`、`ACT_BLOCK`、`ACT_RESET`、`ACT_MAX`。多个查询方法直接由字段推导：`can_act()` 判 `active_status` 是否为 `AST_ALLOW` 或 `AST_FORCE`，`packet_was_dropped()` 判 `active_action >= ACT_DROP`，`session_was_blocked()` 判 `active_action >= ACT_BLOCK`，`is_packet_held()` 判 `active_action == ACT_HOLD`，`get_tunnel_bypass()` 判 `active_tunnel_bypass > 0`。`Active::Counts` 七字段为 `injects`、`failed_injects`、`direct_injects`、`failed_direct_injects`、`holds_denied`、`holds_canceled`、`holds_allowed`，与 verdict 计数分属不同统计通道。`ActiveAction`（`active_action.h`）是注入动作的抽象基类，受保护成员只有 `ActionPriority action`，构造默认 `AP_MAX`，`ActionPriority` 六值 `AP_LOCAL`、`AP_MODIFY`、`AP_PROXY`、`AP_RESET`、`AP_REMOTE`、`AP_MAX`，`delayed_exec()` 默认空实现；源码注释说明实例在检测期排队、由 `Analyzer` 在末尾执行。`ActiveSuspendContext` 是 RAII 包装，构造调 `Active::suspend()`、析构调 `Active::resume()`。字段归本篇，verdict 与内联原理见 06-12，动作类见 07-07 以外由动作模块归口，统计判读见 08-01。

### 4. 典型示例

下面给出一段字段级核验用的 C++ 片段，把 `SFDAQInstance`、`Packet`、`Active` 中若干已核验字段经公开访问器打印出来，并把一个 libdaq verdict 转成字符串，用于确认本地快照的字段与接口确实存在。这不是收包代码，不启动 DAQ，仅作读源码对字段的核对手段。

```cpp
#include "packet_io/sfdaq_instance.h"
#include "packet_io/sfdaq.h"
#include "packet_io/active.h"
#include "protocols/packet.h"
#include <cstdio>

void dump_daq_fields(const snort::SFDAQInstance& inst,
    const snort::Packet& p, const snort::Active& act, DAQ_Verdict verdict)
{
    std::printf("batch=%u pool=%u base=%d\n",
        inst.get_batch_size(), inst.get_pool_available(), inst.get_base_protocol());
    std::printf("daq_msg=%p pkth=%p pktlen=%u dsize=%u\n",
        (const void*)p.daq_msg, (const void*)p.pkth, p.pktlen, p.dsize);
    std::printf("action=%s dropped=%d held=%d can_act=%d\n",
        act.get_action_string(), (int)act.packet_was_dropped(),
        (int)act.is_packet_held(), (int)act.can_act());
    std::printf("verdict=%s\n", snort::SFDAQ::verdict_to_string(verdict));
}
```

在一个把上述函数接入调试构建、并喂入一个合成包的测试桩里，会得到类似下面的输出。示例输出，具体格式需对照实际版本核验。

```text
batch=64 pool=48 base=1
daq_msg=0x00007f2c8401a200 pkth=0x00007f2c8401a260 pktlen=74 dsize=40
action=allow dropped=0 held=0 can_act=1
verdict=allow
```

逐行判读如下，合计超过 150 字。第一行 `batch=64` 来自 `SFDAQInstance::get_batch_size()`，对应私有字段 `batch_size`，其默认基准 `BATCH_SIZE_DEFAULT = 64` 在 `sfdaq_config.h` 中定义；若实测不是 64，通常是 `daq` 段显式设置了批大小（参数见 04-03），而不是字段变更。`pool=48` 是 `get_pool_available()` 返回的 `pool_available`，表示当前消息池可用数，它随收包与释放波动，不宜当作容量常量；`base=1` 是 `get_base_protocol()` 的结果，与 `dlt` 字段相关，取值含义由 libdaq 定义，需对照实际版本核验。第二行 `daq_msg` 与 `pkth` 都是非空地址，说明该 `Packet` 确实来自某条 DAQ 消息；若这里恒为空，通常意味着样本包是合成包或测试桩没有走收包路径，属于取用时点不对，而不是字段缺失。`pktlen=74`、`dsize=40` 分别是原始帧长与载荷长，正常应 `dsize` 不大于 `pktlen`，异常时回查 `src/protocols/packet.h` 的赋值处与解码链（原理见 06-03）。第三行 `action=allow` 来自 `get_action_string()`，由 `active_action` 与 `active_status` 两个枚举共同索引 `act_str[ACT_MAX][AST_MAX]`；`dropped=0`、`held=0` 说明当前动作既非 drop 也非 hold，与 `active_action` 处于 `ACT_ALLOW` 一致；`can_act=1` 表示状态为 `AST_ALLOW` 或 `AST_FORCE`，即具备执行主动响应的前提。第四行 `verdict=allow` 是 `SFDAQ::verdict_to_string()` 转调 `daq_verdict_string()` 的结果，映射由 libdaq 掌握，本册不写枚举数值；若输出为 block 或 replace，才说明内联判定生效，IDS 旁路场景通常只会看到 allow（原理见 06-12）。以上判读只覆盖字段取值，字段完整定义见第 2、3 节。

再给一条用于核对头文件归属与外部依赖边界的命令示例，验证第 1 节的不透明句柄判断。命令按前置检查、执行、复核的闭环书写，不改动任何文件。

```bash

test -f src/packet_io/active.h && echo "active in packet_io"

grep -n "SFDAQ_MODE_INLINE" src/packet_io/sfdaq_config.h
```

示例输出，具体格式需对照实际版本核验。

这段输出逐行印证第 1 节的判断。前两行确认 `sfdaq_instance.h` 与 `active.h` 都在 `src/packet_io/`，是 Snort 侧可核验的包装层。第三条 `find` 没有列出任何 `daq_common.h` 路径，说明本快照仓库树内不含该头文件，`DAQ_PktHdr_t`、`DAQ_Msg_h`、`DAQ_Verdict` 等类型确实来自独立安装的 libdaq，属不透明句柄，字段需对照所装 libdaq 头文件核验；正因为无输出，示例里下一行直接就是 `grep` 的结果，几条命令是彼此独立的。第四行给出 `MAX_DAQ_VERDICT == 6` 的真实行号与断言文本，说明 verdict 计数槽长度为 6 是编译期约束；第五行的 `SFDAQ_MODE_INLINE` 位于 `SFDAQModuleConfig` 内嵌的 `SFDAQMode` 枚举内，佐证配置层确实区分被动、内联与读文件三种模式。行号会随上游提交漂移，需对照实际版本核验。

### 6. 版本差异

最根本的代际差异是抓包依赖的组织方式。Snort 2 把抓包与解码视为一体，Snort 3 是从 Snort 2 重写的 C++ 全新实现，配置为 Lua，抓包依赖独立 libdaq / DAQ3；`src/packet_io/sfdaq*.cc`、`sfdaq_config.cc`、`sfdaq_module.cc`、`sfdaq_static_modules.h.in` 与 `daqs/` 是适配层，DAQ module 决定抓包与内联能力（具体 module 名需对照实际版本核验）。这意味着本篇三族字段里，只有 Snort 侧包装结构能随仓库快照核验，libdaq 侧句柄的字段必须随所装 libdaq 版本另行核对，跨版本不能假设 `DAQ_PktHdr_t` 的布局不变。插件 ABI 也不通用：`BaseApi`（`src/framework/base_api.h`，`BASE_API_VERSION`）作为所有插件 API 的首成员，DAQ 相关模块同样受版本约束，具体兼容边界需对照实际版本核验。

上游 master 快照（2026-11 抓取）内部的演进痕迹要谨慎。`src/packet_io/active.h` 里 `ActiveActionType` 出现 `ACT_REWRITE`、`ACT_HOLD` 等值，`ActiveWouldReason` 细分到 `WHD_IPS_INLINE_TEST`、`WHD_NAP_INLINE_TEST`，`drop_reason` 与 `map_drop_reason_id()`、`send_reason_to_daq()` 的存在，说明 verdict reason 与主动响应是持续增强的能力；文件里「FIXIT-M」注释还提示部分枚举应改用真正的 Action 对象。`src/packet_io/sfdaq_instance.h` 的 `next_message()` 内联实现、`curr_batch_size` 与 `curr_batch_idx` 双游标、`pool_size` 与 `pool_available` 并列，反映消息池语义较早期实现更细。`src/packet_io/sfdaq_config.h` 用 `get_batch_size()`、`get_mru_size()` 在 UNSET 时回落到默认值，说明默认值本身可能被版本调整。`src/packet_io/sfdaq_module.cc` 的 `static_assert(MAX_DAQ_VERDICT == 6)` 把计数槽长度钉在编译期，一旦 libdaq 增加 verdict 类型，这里必须同步修改，否则断言失败。这些都是演进中的真实痕迹，任何依赖字段偏移、结构体大小或默认值的假设都不可靠，结论一律以当前快照源码为准并标注「需对照实际版本核验」。具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，本套资料不写绝对版本号。

能力边界随版本保持稳定，但会影响字段可读性：Snort 本身不是防火墙、不做转发，因此 `forwarding_packet()` 的判定依赖 DAQ 模式与包头 flags，不能据字段名推断 Snort 自己转发；IDS 旁路模式只告警不丢弃，verdict 字段不会被写成 drop；加密载荷不可见，与明文正文相关的缓冲字段在 HTTPS 场景取不到预期内容，这是场景前提而非字段错误；线程 / 进程模型以实际版本为准，禁止断言默认线程数，`instance_id`、`batch_size` 只说明字段存在，不推断实例数量。抓包、丢包率、内存占用一律标注「需在目标机型实测」，DAQ 统计判读见 08-01，上线清单见 08-06。

### 7. 常见误用与调试

第一类误用是把不透明句柄当普通结构展开。仓库树内找不到 `daq_common.h`，`DAQ_PktHdr_t`、`DAQ_Msg_h`、`DAQ_Verdict`、`DAQ_Stats_t`、`DAQ_Instance_h` 都来自独立安装的 libdaq。用 `sizeof()`、指针偏移或 `reinterpret_cast` 去读它们的成员，会在不同 libdaq 版本下静默错位；就算本册点出 `flags`、`ingress_group`、`egress_group` 几个可访问成员，也不能据此推断整个包头布局。正确做法是只用 Snort 侧公开入口，例如 `SFDAQInstance::next_message()`、`finalize_message()`、`SFDAQ::verdict_to_string()`、`Packet` 的分组访问器，内部布局一律视为不透明句柄，内部布局见所装 libdaq 头文件与 `src/packet_io/`，不可依赖。

第二类误用是混淆 verdict 三层语义。本册里至少有三套相关但不等价的字段：`DAQ_Verdict` 是回传给 libdaq 的判定、`Active::active_action` 与 `active_status` 是 Snort 内部的动作与可执行状态、`DAQStats::verdicts[6]` 是统计槽。把 `active_action >= ACT_DROP` 直接当成已写入 verdict，或把 `verdict=allow` 当成没有命中规则，都是常见错误；前者还需经 `finalize_message()` 回传、后者在旁路模式下本就为 allow。判定链与内联机制见 06-12，排错时按「先确认运行模式、再看 Active 状态、最后看 verdict 计数」的顺序排查，内联不 drop 的完整案例见 08-04。

第三类误用是把 05 册当流程书或参数书读。想理解 DAQ 怎么收包、消息池怎么滚动、verdict 怎么反馈，应去 06 册（`原理见 06-02`、`原理见 06-12`）；想配 `daq` 段、module、mode 或命令行 `--daq`，应去 04 册（`参数见 04-03`）；想按目录找 packet_io 模块与 connectors，应去 07 册（`模块见 07-07`）。反过来，在 06 / 07 / 08 册里看到完整字段表属于去重铁律被破坏，应改写成「字段见 05-07」。

第四类是跨版本默认值与计数假设。`BATCH_SIZE_DEFAULT = 64`、`SNAPLEN_DEFAULT = 1518`、`TIMEOUT_DEFAULT = 1000` 是快照中的默认基准，不是运行期保证；`MAX_DAQ_VERDICT == 6` 是编译期断言，随 libdaq 演进可能改变；`DAQStats` 的统计是累计值，`prep_counts()` 必须做差，直接清零会导致统计错乱。调试时若发现取值异常，先确认二进制与所用 libdaq 头文件是否同一版本，再用 `snort -V` 核对构建标识、用 `snort -T` 做配置自检（两条命令的完整参数见 04-07），然后用第 4 节的字段打印确认是配置改写还是字段变更，最后回到 `src/packet_io/` 源码逐字段比对。所有涉及吞吐、pps、丢包率、内存占用的结论一律标注「需在目标机型实测」，不给绝对值；基准方法见 08-01，诊断树见 08-03。
