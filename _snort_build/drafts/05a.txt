# Snort 3 技术资料 · 05 关键数据结构字段详解（分片 A）

## 05-01 全册结构分层与跨文档索引

### 1. 本篇定位与覆盖范围

本篇是 05 册「关键数据结构字段详解」的开篇，也是整册乃至全集的**结构体地图与跨文档索引**。按总纲第 2 节的唯一权威源约定，全集只有 05 册允许出现结构体逐字段定义，其余各册遇到结构体一律只点名、给真实源码路径并写「字段见 05-xx」；反过来，05 册只讲字段含义、类型、内存布局倾向、生命周期与关联函数入口，**不展开机制流程**（统一写「原理见 06-xx」），**不重列配置参数**（统一写「参数见 04-xx」）。因此本篇不承担任何流程讲解，它的任务是把 05-02 至 05-09 八篇正文所覆盖的结构体族，安放到一张按包处理层次划分的坐标系里，并交代每层对应的真实头文件、对象生命周期，以及和 04 册参数、06 册原理、07 册模块之间的反查关系。事实基准统一写「上游 master 快照（2026-11 抓取）」；`CMakeLists.txt` 与 `ChangeLog.md` 中的版本字样只作核验依据，具体版本号以二者为准，本套资料不抄具体版本号进正文，需要说明来源时写「需对照实际版本核验」。

必须先说清事实锚点与路径形态。上游快照解压在 `_snort_build/upstream_src/snort3/`，其下还有一层 GitHub master 分支归档目录 `snort3-master/`，真实仓库根为 `upstream_src/snort3/snort3-master/`；本套资料正文中的路径一律采用去掉这一归档层前缀的仓库内惯用写法，例如 `src/framework/`、`src/protocols/packet.h`、`lua/snort.lua`。核验中还发现三处容易出错的命名习惯，需要在此一并订正，后续各篇不再重复解释：其一，`src/framework/` 目录下**没有** `packet.h`，`struct Packet` 的完整定义在 `src/protocols/packet.h`，`src/framework/` 里与包解码相关的是 `decode_data.h`、`codec.h`、`pdu_section.h`；其二，本快照**没有独立的 `src/session/` 目录**，会话基类 `class Session` 定义在 `src/flow/session.h`，与 `src/flow/flow.h`、`flow_cache.h`、`flow_control.h`、`flow_data.h` 同处 `src/flow/`；其三，本快照**没有独立的 `src/decode/` 目录**，解码职责由 `src/codecs/` 与 `src/protocols/packet.cc`、`packet_manager.cc` 承担。标题与大纲里出现的 `src/decode`、`src/session` 是惯用名，凡涉及这些目录名一律标注「需对照实际版本核验」，不得当成真实路径引用。

本篇把 05 册覆盖的结构体族划成五层。**第一层是 DAQ / 包 I/O 层**，入口头文件为 `src/packet_io/sfdaq.h`、`sfdaq_config.h`、`sfdaq_instance.h`、`active.h`，对应 `DAQ_Msg_h`、`DAQ_PktHdr_t`、`DAQ_Verdict`、`SFDAQInstance`、`Active` 等对象，字段归 05-07。**第二层是包与解码层**，入口为 `src/protocols/packet.h`、`packet_manager.h`、`layer.h` 与 `src/framework/decode_data.h`、`codec.h`，对应 `Packet`、`DecodeData`、`Layer`、`IpApi`，字段归 05-02。**第三层是流与会话层**，入口为 `src/flow/flow.h`、`flow_key.h`、`flow_data.h`、`session.h` 与 `src/stream/`，对应 `Flow`、`FlowKey`、`FlowData`、`Session`，字段归 05-02 与 05-09。**第四层是检测与配置层**，入口为 `src/main/snort_config.h`、`policy.h`、`src/framework/module.h`、`parameter.h`、`value.h`、`inspector.h`、`ips_option.h`、`src/detection/`（`detection_engine.h`、`detect.h`、`rules.h`、`fp_detect.h`、`treenodes.h`、`ips_context.h`），对应 `SnortConfig`、`PolicyMap`、`Module`、`Parameter`、`Value`、`Inspector`、`Module`、`IpsOption`、`RuleTreeNode`、`OptTreeNode`、`DetectionEngine`、`IpsContext`，字段归 05-03、05-04、05-05、05-06。**第五层是输出与事件层**，入口为 `src/loggers/loggers.h` 与 `src/events/event.h`、`event_queue.h`，对应 `Event`、`Logger`、`Output Set`，字段归 05-08。五层之间是数据归属关系，不是调用顺序；调用顺序属于「原理见 06-01」。五层结构、对象生命周期与各册反查关系见图 05-01-01，图中实线为包内数据的归属链，虚线为跨册反查链。

还要守住能力边界，避免把结构体的存在误读成能力。Snort 3 是相对 Snort 2 重写的全新 C++ 实现，配置为 Lua（`lua/snort.lua`、`lua/snort_defaults.lua`），不兼容 Snort 2 的 `snort.conf` 与插件 ABI，`tools/snort2lua/` 只是格式转换辅助工具；抓包依赖独立 libdaq / DAQ3，`src/packet_io/sfdaq*.cc` 是适配层而非自带抓包，因此第一层里的 `DAQ_PktHdr_t`、`DAQ_Msg_h` 是本快照对 DAQ 头类型的前向引用与包装，具体字段以 `src/packet_io/sfdaq*.cc` 与所装 libdaq 头文件为准，需对照实际版本核验。内联 IPS 的 drop / block 通过 DAQ verdict 反馈（`src/actions/`、`src/packet_io/active.cc`），Snort 本身不是防火墙、不做 IP 转发；加密流量载荷不可见，应用识别依赖 inspector / binder / wizard；Hyperscan 是可选 search_engine 加速，缺失时回退 `src/search_engines/` 下其他多模式匹配实现。这些边界决定了某些字段在加密或旁路场景下取不到有效值，本篇只标注字段存在与读写时机，不推断运行时效果。许可按 GPLv2（顶层 `COPYING` / `LICENSE`）处理，Talos 规则集另有独立许可约束（`lua/talos.lua`）。

### 3. 逐项详解

以下按五层逐层详解。每层给出「入口头文件 → 代表结构的字段族特征 → 生命周期 → 不透明边界 → 归口」，全部字段以源码为准，凡未核验到的一律写「需对照实际版本核验」。

**第一层 DAQ / 包 I/O 层**。入口为 `src/packet_io/sfdaq.h`、`sfdaq_config.h`、`sfdaq_instance.h`、`sfdaq_module.h`、`active.h`、`active_action.h` 与 `src/connectors/`、`src/side_channel/`。本层结构体的共同特征是「句柄化」：`Packet` 里保存的 `DAQ_Msg_h daq_msg`、`SFDAQInstance* daq_instance`、`const DAQ_PktHdr_t* pkth` 三个字段在 `src/protocols/packet.h` 中只以指针/句柄形式出现，`DAQ_Msg_h` 与 `DAQ_PktHdr_t` 的类型本体来自 libdaq 的 `daq_common.h`，在本仓库内不可展开；`SFDAQInstance` 定义在 `src/packet_io/sfdaq_instance.h`，其成员函数可见但内部布局需对照实际版本核验。这几类对象属于**不透明句柄，内部布局见 `src/packet_io/sfdaq.cc` 与所装 libdaq 头文件，不可依赖**。`ActiveAction`（`src/packet_io/active_action.h`）是本层少数可直接看到字段的抽象基类，仅有一个 `ActionPriority action` 保护成员与 `delayed_exec()` 虚方法；`enum ActionPriority` 取值 `AP_LOCAL`、`AP_MODIFY`、`AP_PROXY`、`AP_RESET`、`AP_REMOTE`、`AP_MAX`。生命周期上，DAQ 消息随收包产生、随包释放，`Packet` 只借用其指针，不拥有所有权；verdict 由动作层写回，字段归 05-07，原理见 06-02 与 06-12，模块见 07-07。

**第二层包与解码层**。`src/protocols/packet.h` 的 `struct Packet` 是本层核心，字段按「reset() 是否清零」分成两段：源码在 `PduSection sect` 之后有一行注释「nothing after this point is zeroed by reset() ...」，其上是 `flow`、`endianness`、`obfuscator`、`packet_flags`、`xtradata_mask`、`proto_bits`、`alt_dsize`、`num_layers`、`ip_proto_next`、`disable_inspect`、`filtering_state`、`sect` 等每次复位会清零的字段；其下是 `context`、`active`、`active_inst`、`action`、`action_inst`、`daq_msg`、`daq_instance`、`pkth`、`pkt`、`pktlen`、`data`、`dsize`、`ptrs`、`layers`、`pseudo_type`、三个 `user_*_policy_id`、`inspection_started_timestamp`、`vlan_idx`、`vlan_idx_outer`、`ts_packet_flags` 等跨包保留或由解码阶段设置的字段。这个分段是理解 `Packet` 生命周期的关键：`Packet(bool packet_data = true)` 构造、`~Packet()` 析构、拷贝构造与赋值被显式 `= delete`，复用依靠 `reset()` 与 `release_helpers()`，属于池化对象的典型形态（池化实现见 `src/protocols/packet_manager.cc`，原理见 06-01，模块见 07-09）。`DecodeData`（`src/framework/decode_data.h`）内嵌于 `Packet::ptrs`，只有 `tcph`、`udph`、`icmph` 三个协议头指针、`sp`、`dp`、`decode_flags`、`type`、`ip_api`、`mplsHdr` 共九个成员，源码注释明确要求「NOTHING else should be added」，因为前三个指针被高频引用；`Layer`（`src/protocols/layer.h`）只有 `start`、`prot_id`、`length` 三个字段，`Packet::layers` 指向其数组。字段归 05-02。

**第三层流与会话层**。`src/flow/flow.h` 的 `class Flow` 源码注释写明「this struct is organized by member size for compactness」，即字段按尺寸排序以压缩空洞，因此读表时不能假定声明顺序等于业务顺序。可核验的字段族包括：哈希与链表指针 `key`、`prev`、`next`、HA 状态 `ha_state`；会话与检查器指针 `session`、`ssn_client`、`ssn_server`、`clouseau`、`gadget`、`assistant_gadget`、`data`、`service`、`stream_intf`；地址与状态 `client_ip`、`server_ip`、`ssn_state`、`previous_ssn_state`、`flowstats`、`context_chain`、`last_data_seen`；计时与策略 `expire_time`、`default_session_timeout`、`idle_timeout`、`network_policy_id`、`inspection_policy_id`、`ips_policy_id`、`reload_id`；端口与协议 `client_port`、`server_port`、`ip_proto`、`pkt_type`、`ssn_policy`、`session_state`、`flow_state`；以及一个 22 位的 `flags` 位域结构体与 `connection_id`、`flow_id`、`last_verdict`、`filtering_state`、`data_log_filtering_state`。私有段还有 `inspection_duration`（`std::atomic_ullong`）、`inspected_packet_count`、`mem_bytes`、`peak_mem_bytes` 用于内存记账。`FlowKey`（`src/flow/flow_key.h`）用 `PADDING_GUARD_BEGIN/END` 包裹，字段为 `ip_l[4]`、`ip_h[4]`、`mplsLabel`、`addressSpaceId`、条件编译的 `tenant_id`、`port_l`、`port_h`、`group_l`、`group_h`、`vlan_tag`、`padding`、`ip_protocol`、`pkt_type`、`version` 与三位的 `flags` 位域；`#ifndef DISABLE_TENANT_ID` 使 `tenant_id` 随构建开关变化（该开关见 04-01），因此 `sizeof(FlowKey)` 不是跨构建常量，禁止硬编码偏移。`Session`（`src/flow/session.h`）是抽象基类，公开字段只有 `snort::Flow* flow`，其余全是 `setup()`、`process()`、`clear()`、`flush()` 等虚方法，具体协议子类落在 `src/stream/tcp/`、`udp/`、`ip/`、`base/`，属于**不透明句柄，内部布局见 `src/stream/` 各子类 `.cc`，不可依赖**。字段归 05-02 与 05-09，原理见 06-05，模块见 07-10 与 07-04。

**第四层检测与配置层**。这是 05 册篇幅最大的一层，横跨 05-03、05-04、05-05、05-06。`src/main/snort_config.h` 的 `struct SnortConfig` 等四个 `SFDAQConfig`、`FastPatternConfig`、`EventQueueConfig`、`ThresholdConfig`、`RateFilterConfig`、`DetectionFilterConfig`、`PolicySelector`、`GHash`、`XHash`、`PORT_RULE_MAP`、`srmm_table_t`、`sopg_table_t`、`ProfilerConfig`、`TraceConfig`、`ThreadConfig`、`MemoryConfig` Parameter* params`，参数以 `name`、`type`、`range`、`deflt`、`help` 五字段描述一个 Lua 键，值以 `type`（`VT_BOOL/VT_NUM/VT_UNUM/VT_STR/VT_REAL`）、`unum`、`num`、`real`、`str`、`origin_str`、`ss`、`param` ### 4. 典型示例

下面给出一段字段级核验用的 C++ 片段，作用是把 `Packet` 与 `FlowKey` 中若干已核验字段打印出来，用于确认本地快照的字段确实存在、类型与声明一致。这不是流程代码，不触发任何收包或检测动作，仅作为「读源码 → 对字段」的核对手段。

```cpp
#include "protocols/packet.h"
#include "flow/flow_key.h"
#include <cstdio>

void dump_anchor_fields(const snort::Packet& p, const snort::FlowKey& k)
{
    std::printf("flow=%p pktlen=%u dsize=%u\n",
        static_cast<const void*>(p.flow), p.pktlen, p.dsize);
    std::printf("proto_bits=0x%08x flags=0x%08llx\n",
        p.proto_bits, static_cast<unsigned long long>(p.packet_flags));
    std::printf("num_layers=%u ip_proto=%u\n",
        p.num_layers, static_cast<unsigned>(k.ip_protocol));
    std::printf("port_l=%u port_h=%u vlan=%u\n",
        k.port_l, k.port_h, k.vlan_tag);
}
```

在一个把上述函数接入调试构建、并喂入一个合成包的测试桩里，会得到类似下面的输出。示例输出，具体格式需对照实际版本核验。

```text
flow=0x0000000000b1f2a0 pktlen=74 dsize=40
proto_bits=0x0000080a flags=0x0000000000000008
num_layers=3 ip_proto=6
port_l=12345 port_h=80 vlan=0
```

逐行判读如下，合计超过 150 字。第一行 `flow=` 为一个非空地址，说明该 `Packet` 已绑定到某个 `Flow`；若这里恒为 `(nil)`，通常意味着样本包取自解码前、或测试桩没有走流绑定，属于取值时点不对，而不是字段缺失。`pktlen=74` 是 `Packet::pktlen` 的 `uint32_t` 值，`dsize=40` 是 `Packet::dsize` 的 `uint16_t` 值，二者分别对应原始帧长度与载荷长度，正常情况下 `dsize` 不大于 `pktlen`；若出现 `dsize` 大于 `pktlen`，应回查 `src/protocols/packet.h` 中 `data`、`dsize` 的赋值处与 `PacketManager::decode()`（`原理见 06-03`），而不是怀疑打印函数。第二行 `proto_bits=0x0000080a` 是按 `src/framework/decode_data.h` 的 `PROTO_BIT__*` 宏组合出的位掩码，本例可拆出 `PROTO_BIT__ETH`（`0x000800`）、`PROTO_BIT__TCP`（`0x000002`）与 `PROTO_BIT__IP`（`0x000001`）等位，具体组合以实际解码结果为准；`flags=0x8` 对应 `packet.h` 的 `PKT_STREAM_EST`（`0x00000008`），表示该包来自已建立的流。第三行 `num_layers=3` 是 `Packet::num_layers`，对应 eth/ip/tcp 三层封装；`ip_proto=6` 来自 `FlowKey::ip_protocol`，值为 6 即 TCP，与 `pkt_type` 及 `DecodeData::type` 应保持一致。第四行 `port_l=12345`、`port_h=80` 是 `FlowKey` 归一化后的低/高端口，`vlan_tag=0` 表示未带 VLAN；注意 `FlowKey` 被 `PADDING_GUARD` 包裹且 `tenant_id` 受 `DISABLE_TENANT_ID` 条件编译影响（`参数见 04-01`），因此不要用 `sizeof(FlowKey)` 或字段偏移去反推内存布局，跨构建必须重新核验。以上判读只覆盖字段取值，字段的完整定义见 05-02，收包与解码链路见 06-02、06-03，`DAQ_PktHdr_t` 的真实字段见 05-07。

### 6. 版本差异

最根本的代际差异是结构体承载方式。Snort 2 以 C 结构体加全局变量组织状态，配置来自 `snort.conf`；Snort 3 是从 Snort 2 重写的 C++ 全新实现，配置改为 Lua，`SnortConfig`（`src/main/snort_config.h`）把原先散落的全局配置收进单一对象，并通过 `static SnortConfig* get_conf()` 与 `get_main_conf()` 提供运行期只读访问（`src/main/snort_config.cc`），因此「按全局变量名找配置」的旧习惯在 3.x 完全失效。`Packet` 由纯数据结构变成带构造/析构、删除拷贝、提供 `reset()` 与大量 `is_*()` 访问器的 `struct SO_PUBLIC Packet`（`src/protocols/packet.h`），`Flow` 变成 `class SO_PUBLIC Flow` 并引入 `FlowData`/`FlowDataStore`（`src/flow/flow_data.h`）承载检查器状态，`Module`/`Parameter`/`Value`（`src/framework/`）取代硬编码解析表。插件 ABI 也不通用：`BaseApi`（`src/framework/base_api.h`，`BASE_API_VERSION 29`）作为所有插件 API 的首成员，`INSAPI_VERSION`、`ACTAPI_VERSION`、`IPSAPI_VERSION` 分别派生，跨版本加载 SO 插件必须校验版本，具体兼容边界需对照实际版本核验。

上游 master 快照（2026-11 抓取）内部的演进痕迹同样要谨慎。`src/flow/flow.h` 里保留「fields are organized by initialization and size to minimize void space」注释，说明字段顺序随紧凑化调整过；`src/flow/flow_key.h` 的 `PADDING_GUARD_BEGIN/END` 与 `#ifndef DISABLE_TENANT_ID` 表明键结构随构建选项改变；`src/main/snort_config.h` 顶部写着「FIXIT-L privatize most of this stuff」，并有多处 `#ifdef REG_TEST`、`#ifdef SHELL` 条件字段；`src/framework/decode_data.h` 有「NOTHING else should be added」的强约束注释；`src/detection/treenodes.h` 的 `struct alignas(64) OtnState` 显式对齐以适配缓存行。这些都是版本演进中的真实痕迹，任何依赖字段偏移、结构体大小或「声明顺序即业务顺序」的假设都不可靠，结论一律以当前快照源码为准并标注「需对照实际版本核验」。具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，本套资料不写绝对版本号。

能力边界随版本保持稳定，但会影响字段可读性：Hyperscan 始终是可选加速，缺失时回退 `src/search_engines/` 下 AC / BNFA 实现，`SnortConfig::hyperscan_literals` 之类的开关不改变这一事实；DAQ 始终是独立依赖，第一层字段随 libdaq 版本变化，需对照实际版本核验；许可始终按 GPLv2 处理，Talos 规则集另有独立许可约束；规则关键字与 Snort 2 有差异、不宣称完全兼容，规则结构的字段名（`src/detection/treenodes.h`、`src/ips_options/`）也不可直接照搬旧版。线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」，`SnortConfig::thread_config`、`max_procs` 等字段只说明存在，不推断数量。

### 7. 常见误用与调试

第一类误用是路径想当然。最常见的三种：把 `Packet` 定义写成 `src/framework/packet.h`（真实在 `src/protocols/packet.h`）、把会话写成 `src/session/`（真实在 `src/flow/session.h`，本快照无独立目录）、把解码写成 `src/decode/`（真实由 `src/codecs/` 与 `src/protocols/packet.cc` 承担，本快照无独立目录）。三者都会在源码检索时扑空，进而误判「结构体不存在」。第 4 节给出的 `test -f` / `test -d` / `grep -n` 组合是最快的确认手段；如结果与本节不符，以 `upstream_src/snort3/snort3-master/` 下实际目录为准并标注「需对照实际版本核验」。

第二类误用是把不透明句柄当普通结构展开。`SnortConfig` 里的 `SFDAQConfig*`、`FastPatternConfig*`、`EventQueueConfig*`、`PORT_RULE_MAP*`、`GHash*`、`XHash*`，`Flow` 里的 `FlowHAState*`、`BitOp*`，`Inspector` 里的 `ThreadSpecificData`，以及 `Session` 的各协议子类，在本头文件都只有前向声明。用 `sizeof()`、指针偏移或 `reinterpret_cast` 去读它们的成员，会在不同构建、不同 libdaq 版本下静默错位。正确做法是只用已公开的访问器（如 `SnortConfig::get_conf()`、`Flow::get_flow_data()`、`Inspector::get_service()`），内部布局一律视为**不透明句柄，内部布局见对应 `.cc`，不可依赖**。

第三类误用是把 05 册当流程书或参数书读。想理解「包怎么从 DAQ 走到告警」应去 06 册（`原理见 06-01`），想配一个 `stream_tcp` 或 `HOME_NET` 应去 04 册（`参数见 04-02`、`参数见 04-04`），想按目录找模块应去 07 册（`模块见 07-12`）；在 05 册里找调用链或参数全集只会得到交叉引用。反过来，在 06 / 07 / 08 册里看到完整字段表属于去重铁律被破坏，应改写成「字段见 05-xx」。

第四类是跨版本字段假设。把 Snort 2 的 `Packet` 字段、`snort.conf` 全局或旧插件 ABI 的字段偏移套到 3.x，或把 `sizeof(FlowKey)`、`offsetof(Packet, flow)` 硬编码进外部工具，都会因 `PADDING_GUARD`、条件编译（`DISABLE_TENANT_ID`、`REG_TEST`、`SHELL`）与字段紧凑化而失效。调试时若发现读到「看似合理但明显不对」的值，先确认二进制与所用头文件是否同一快照，再用 `snort -V` 核对构建标识、用 `snort -T` 做配置自检（这两条命令的完整参数见 04-07），最后回到源码逐字段比对。第五类是忽视能力边界造成的字段误判：加密载荷不可见，因此与明文正文相关的缓冲字段在 HTTPS 场景下取不到预期内容；IDS 旁路模式下只告警不丢弃，与 verdict 相关的字段不会被写成 drop；Hyperscan 未启用时回退其他 MPSE 实现，与 Hyperscan 专属结构相关的字段不可用。这些都不是字段定义错误，而是场景前提不同，排错时应先确认运行模式再查字段。所有涉及吞吐、pps、内存占用的结论一律标注「需在目标机型实测」，不给绝对值；基准方法见 08-01，诊断树见 08-03。

### 3. 逐项详解

**Packet 的构造与生命周期**。`Packet(bool packet_data = true)` 与 `~Packet()` 在 `src/protocols/packet.cc` 实现，拷贝构造与赋值被显式 `= delete`，说明它不可按值传递；复用通过 `reset()` 与 `release_helpers()` 完成，属于池化对象（池的分配策略见 `src/protocols/packet_manager.cc`，原理见 06-01，模块见 07-09）。`reset()` 的清零界线是本节最重要的静态事实：界线上方的 `packet_flags`、`proto_bits`、`num_layers`、`alt_dsize`、`filtering_state`、`sect`、`flow` 等每次复位回到零或空，界线下方的 `context`、`active`、`daq_msg`、`pkth`、`pkt`、`pktlen`、`data`、`dsize`、`layers`、`ptrs` 则保留旧值，依赖 `PacketManager::decode()` 逐项覆盖。由此可推出一条调试准则：读到「上一个包的残留值」时，优先怀疑解码未覆盖某个下方字段，而不是怀疑 `reset()` 失效。`endianness`、`obfuscator` 属于按需创建的辅助对象，由 `release_helpers()` 释放；`allocated`（私有）标记内存是否自分配，`max_dsize` 是 `static const uint32_t`，注释说明「IP_MAXPACKET is the minimum allowable max_dsize」，且留有可扩容的余地，故不可把 `IP_MAXPACKET` 当成绝对上限写进外部工具。

**Packet 的访问器与位标志语义**。`Packet` 提供大量内联 `is_*()`：`is_eth()` 读 `proto_bits`，`has_ip()`、`is_ip4()`、`is_ip6()`、`is_tcp()`、`is_udp()`、`is_icmp()` 走 `ptrs.ip_api` 或 `ptrs.get_pkt_type()`，`is_cooked()`、`is_fragment()`、`is_rebuilt()`、`is_retry()`、`is_full_pdu()`、`has_parent()` 等读 `packet_flags` 的宏位。`src/protocols/packet.h` 定义了从 `PKT_REBUILT_FRAG`（`0x00000001`）到 `PKT_TCP_INJECT_BLOCKED`（`0x0000000400000000ULL`）的一整套宏，其中高 32 位的三个宏用 `ULL` 后缀，说明 `packet_flags` 是 `uint64_t` 而非 `uint32_t`，这是容易读错的一处。`set_detect_limit(uint16_t n)` 同时写 `alt_dsize` 并置 `PKT_DETECT_LIMIT`，`get_detect_limit()` 据此在 `alt_dsize` 与 `dsize` 间选择。`get_ip_proto_next()` 返回 `ip_proto_next`，另有 `get_ip_proto_next(uint8_t&, IpProtocol&)` 供循环遍历多层 IP。`PseudoPacketType` 枚举给出 `PSEUDO_PKT_IP`、`PSEUDO_PKT_TCP`、`PSEUDO_PKT_UDP_QUIC`、`PSEUDO_PKT_USER`、`PSEUDO_PKT_DCE_SEG`、`PSEUDO_PKT_DCE_FRAG`、`PSEUDO_PKT_SMB_SEG`、`PSEUDO_PKT_SMB_TRANS`、`PSEUDO_PKT_MAX` 九个取值，`pseudo_type` 仅在 `PKT_PSEUDO` 置位时有效。`MAX_PORTS = 65536`、`NUM_IP_PROTOS = 256`、`TCP_OPTLENMAX = 40`、`DEFAULT_LAYERMAX = 40` 是同文件的四个 `constexpr`，可作为外部校验常量，但需对照实际版本核验。

**DecodeData 的紧凑约束与枚举**。`DecodeData` 内嵌于 `Packet::ptrs`（不是指针），包含三个协议头指针、`sp`、`dp`、`decode_flags`、`type`、`ip_api`、`mplsHdr`。源码注释「these three pointers are each referenced literally dozens if not hundreds of times. NOTHING else should be added!!」说明这三个指针的热度，任何「顺手加个字段」的改动都被上游明确劝阻，因此该结构可作稳定锚点。`enum class PktType : std::uint8_t` 取值 `NONE, IP, TCP, UDP, ICMP, USER, FILE, PDU, MAX`；`enum class LruType` 与之同源并多出 `ALLOW_LIST`；`enum DecodeFlags : std::uint32_t` 给出 `DECODE_ERR_CKSUM_IP/TCP/UDP/ICMP`、`DECODE_ERR_BAD_TTL`、`DECODE_PKT_TRUST`、`DECODE_FRAG`、`DECODE_MF`、`DECODE_DF`、`DECODE_C2S`、`DECODE_SOF`、`DECODE_EOF`、`DECODE_GTP`、`DECODE_TCP_MSS/TS/WS`、`DECODE_ERR_LEN` 等标志，以及 `DECODE_ERR_CKSUM_ALL`、`DECODE_ERR_FLAGS` 组合掩码。`PROTO_BIT__*` 一串宏定义协议位，`PROTO_BIT__TUNNEL_DECAP`（`0x800000`）被注释为「Derived state, deliberately outside PROTO_BIT__ALL」，这类位在 `Packet::proto_bits` 中使用，读字段时要区分「协议位」与「派生状态位」。`ip_api`（`snort::ip::IpApi`）与 `mplsHdr`（`snort::mpls::MplsHdr`）是外部类型，属于**不透明句柄，内部布局见 `src/protocols/ip.h` 与 `src/protocols/mpls.h`，不可依赖**；本册只记录字段存在与类型名。

**Layer 与 TunnelInfo**。`src/protocols/layer.h` 的 `struct Layer` 只有三个字段：`const uint8_t* start`（本层起始字节）、`ProtocolId prot_id`（协议标识）、`uint16_t length`（本层长度）。`Packet::layers` 指向该结构数组，配合 `num_layers` 使用；`layer` 命名空间提供 `get_root_layer()`、`get_eth_layer()`、`get_vlan_layer()`、`set_inner_ip_api()`、`get_encapsulation_layers()` 等访问函数（`原理见 06-03`）。同文件还定义 `struct TunnelInfo`：`tunnel_type`（`ProtocolId`）、`src_ip`、`dst_ip`（`SfIp`）、`src_port`、`dst_port`（`uint16_t`）、`ip_proto`（`IpProtocol`）、`has_ports`（`bool`），用于多封装可见性；这些是 `src/protocols/layer.h` 中可核验的完整字段，不属于 `Packet` 直接成员，列在此处便于对照 `Flow::mpls_client`/`mpls_server` 的 `Layer*` 用途。

**FlowKey 的哈希键布局**。`src/flow/flow_key.h` 的 `struct SO_PUBLIC FlowKey` 被 `PADDING_GUARD_BEGIN`/`PADDING_GUARD_END` 包裹，注释写明「the data members are sequenced to avoid void space」。可核验字段：`uint32_t ip_l[4]`（低地址 IP）、`uint32_t ip_h[4]`（高地址 IP）、`uint32_t mplsLabel`、`uint32_t addressSpaceId`、条件编译的 `uint32_t tenant_id`（`#ifndef DISABLE_TENANT_ID`，该开关见 04-01）、`uint16_t port_l`/`port_h`（ICMP 时为 0）、`int16_t group_l`/`group_h`、`uint16_t vlan_tag`、`uint16_t padding`、`uint8_t ip_protocol`、`PktType pkt_type`、`uint8_t version`，以及位域 `struct { bool group_used:1; bool tunnel_encapsulated:1; uint8_t padding_bits:6; } flags`。三个 `init()` 重载分别处理普通流、带 `DAQ_PktHdr_t` 的流与 IP 分片键，另有 `init_mpls()`、`init_vlan()`、`init_address_space()`、`init_groups()` 与 `static is_equal()`（内部用 `memcmp(k1, k2, sizeof(FlowKey))`）。正因为 `is_equal()` 直接按字节比较，且 `tenant_id` 受构建开关控制，`FlowKey` 的任何字段增删或 Padding 变化都会改变哈希语义，**禁止外部工具硬编码 `sizeof(FlowKey)` 或按字段偏移读取**，跨构建必须重新核验。哈希运算由 `FlowHashKeyOps`（`do_hash()`、`key_compare()`）承担，机制见 06-05。

**Flow 的字段族与内存记账**。`src/flow/flow.h` 的 `class SO_PUBLIC Flow` 注释写明「fields are organized by initialization and size to minimize void space」，并另有一句「these fields are always set; not zeroed」，指的是 `prev`、`next`、`session`、`ssn_client`、`ssn_server`、`ips_cont` 这一组。可核验字段按族归纳：哈希/链表/HA 为 `key`（`const FlowKey*`）、`bitop`（`BitOp*`）、`ha_state`（`FlowHAState*`）、`prev`、`next`；会话与检查器为 `session`（`Session*`）、`ssn_client`、`ssn_server`、`clouseau`（服务识别器）、`gadget`（服务处理器）、`assistant_gadget`、`data`、`service`（`const char*`）、`stream_intf`（`StreamFlowIntf*`）、`ips_cont`（`Continuation*`）；地址与统计为 `client_ip`、`server_ip`（`SfIp`）、`flowstats`（`FlowStats`）、`ssn_state`、`previous_ssn_state`（`LwState`）、`context_chain`（`IpsContextChain`）、`last_data_seen`（`long`）、`mpls_client`、`mpls_server`（`Layer*`）；计时与策略为 `expire_time`（`uint64_t`）、`default_session_timeout`、`idle_timeout`、`network_policy_id`、`inspection_policy_id`、`ips_policy_id`、`reload_id`、`prev_packet_time`（`timeval`）；端口协议为 `client_port`、`server_port`、`ip_proto`、`pkt_type`、`ssn_policy`、`session_state`、`flow_state`（`enum class FlowState : uint8_t`，取值 `SETUP/INSPECT/BLOCK/RESET/ALLOW`）、四个 TTL 字段与 `response_count`、`dump_code`；此外还有 `data_log_filtering_state`（`std::bitset<64>`）、`filtering_state`（`FilteringState`）、`last_verdict`（`DAQ_Verdict`，初值 `MAX_DAQ_VERDICT`）、`flow_id`、`connection_id`（`uint64_t`）与一个 22 位的 `flags` 位域。私有段 `inspection_duration`（`std::atomic_ullong`）、`inspected_packet_count`（`uint16_t`）、`mem_bytes`、`peak_mem_bytes`（`size_t`，初值均为 `sizeof(Flow)`）用于内存与延迟记账，由 `add_mem()`、`sub_mem()`、`get_mem_usage()`、`get_peak_mem_usage()` 访问；这不是可供外部直接读的字段，需对照实际版本核验。`DeferredTrust deferred_trust`、`FlowStash stash{this}`、`FlowDataStore flow_data{this}` 是保护段成员。

**辅助结构与不透明边界**。`struct FilteringState` 只有 `uint8_t generation_id` 与 `bool matched`，配 `clear()`、`was_checked()`、`set_matched()`；`Packet::filtering_state` 被 `mutable` 修饰，便于 const 访问器改写。`struct FlowStats` 有 `client_pkts`、`server_pkts`、`client_bytes`、`server_bytes`（均 `uint64_t`）、`start_time`（`timeval`）、`total_flow_latency`、`total_rule_latency`。`struct LwState` 有 `uint32_t session_flags`、`int16_t ipprotocol`、`SnortProtocolId snort_protocol_id`、`char direction`、`char ignore_direction`。`class FlowData`（`src/flow/flow_data.h`）保护段为 `Flow* owner_flow`，私有段为 `std::shared_ptr<Plugin> plugin`、`static unsigned flow_data_id`、`unsigned id`，配 `get_id()`、`create_flow_data_id()`、`size_of()` 与三个 `handle_*` 虚方法；`class FlowDataStore` 私有段为 `std::vector<FlowData*> flow_data` 与 `Flow* const owner_flow`。`class Session`（`src/flow/session.h`）公开字段只有 `snort::Flow* flow`，`clear()` 是纯虚，其余 `setup()`、`process()`、`flush()`、`set_splitter()` 等为虚方法；具体协议子类落在 `src/stream/tcp/`、`udp/`、`ip/`、`base/`，属于**不透明句柄，内部布局见 `src/stream/` 各子类 `.cc`，不可依赖**。`SSNFLAG_*`、`STREAM_STATE_*` 两族宏定义了 `session_flags` 与 `session_state` 的位含义，读字段时应回到 `src/flow/flow.h` 核对，需对照实际版本核验。

**补充：内联辅助函数与访问器清单**。除上述数据成员外，`src/protocols/packet.h` 在结构体之后还定义了一组内联辅助，读字段时经常一并遇到：`#define BIT(i) (0x1 << ((i)-1))` 与 `inline void SetExtraData(Packet* p, const uint32_t xid) { p->xtradata_mask |= BIT(xid); }` 说明 `xtradata_mask` 的置位方式；`extract_16bits()`、`extract_32bits()`、`alignedNtohs()`、`alignedNtohl()`、`alignedNtohq()` 用 `std::memcpy` 配合 `ntoh*` 与条件编译的字节序处理读取协议字段，其中 `WORDS_BIGENDIAN` 分支是平台适配点（`模块见 07-13`）。`Packet` 的 `get_type()`、`get_pseudo_type()`、`get_inner_pkt_offset()`、`get_flow_vlan_id()`、`get_flow_vlan_id_outer()`、`get_flow_geneve_vni()`、`get_geneve_options()`、`test_session_flags()`、`get_snort_protocol_id()`、`set_snort_protocol_id()`、`is_detection_enabled()`、`inject()` 等是声明后落在 `.cc` 的成员入口，本册只列名不展开实现。`src/flow/flow.h` 的访问器同样密集：`init(PktType)`、`flush()`、`reset()`、`restart()`、`clear()`、`markup_packet_flags()`、`set_client_initiate()`、`set_direction()`、`set_expire()`、`expired()`、`set_ttl()`、`set_mpls_layer_per_dir()`、`swap_roles()`、`set_service()`、`add_mem()`、`sub_mem()`、`get_mem_usage()`、`get_peak_mem_usage()`、`update_session_flags()`、`set_session_flags()`、`get_session_flags()`、`clear_session_flags()`、`set_to_client_detection()`、`set_to_server_detection()`、`block()`、`set_block_flags()`、`was_blocked()`、`full_inspection()`、`set_state()`、`set_client()`、`set_server()`、`set_clouseau()`、`set_gadget()`、`set_data()`、`handle_allowlist()`、`trust()` 等。`SSNFLAG_*` 宏从 `SSNFLAG_SEEN_CLIENT`（`0x00000001`）到 `SSNFLAG_KEEP_FLOW`（`0x80000000`）共二十余位，`STREAM_STATE_*` 从 `STREAM_STATE_NONE` 到 `STREAM_STATE_RELEASING` 九值，二者分别由 `ssn_state.session_flags` 与 `session_state` 承载；`SSNFLAG_SEEN_BOTH`、`SSNFLAG_BLOCK` 是组合掩码，`Flow::two_way_traffic()`、`was_blocked()`、`is_proxied()`、`is_hard_expiration()` 等访问器直接读这些位。`FlowDataStore` 另有 `static constexpr unsigned FLOW_DATA_INCREMENTS = 7` 与 `enum FlowDataHandlerType { HANDLER_RETRANSMIT, HANDLER_EOF }`（`src/flow/flow_data.h`），`Flow::call_handlers()` 依此分派；`FlowData` 提供 `handle_expected()`、`handle_retransmit()`、`handle_eof()` 三个虚钩子与 `size_of()`，并用 `FLOW_DATA_SIZE_OF`、`FLOW_DATA_SIZE_OF_EXTRA` 两个宏让子类报告自身尺寸。这些入口与常量只用于按字段名反查，涉及调用顺序与超时剪枝的部分一律「原理见 06-05」。

### 4. 典型示例

下面这段 C++ 片段用于核对 `Packet`、`DecodeData` 与 `FlowKey` 的字段取值，只做读取与打印，不触发收包、解码或检测流程，便于在本地调试构建里确认字段与头文件是否一致。

```cpp
#include "protocols/packet.h"
#include "framework/decode_data.h"
#include "flow/flow_key.h"
#include <cstdio>

void dump_packet_fields(const snort::Packet& p)
{
    std::printf("pkt=%p pktlen=%u data=%p dsize=%u\n",
        static_cast<const void*>(p.pkt), p.pktlen,
        static_cast<const void*>(p.data), p.dsize);
    std::printf("layers=%p num_layers=%u type=%d\n",
        static_cast<const void*>(p.layers), p.num_layers,
        static_cast<int>(p.ptrs.get_pkt_type()));
    std::printf("sp=%u dp=%u decode_flags=0x%08x\n",
        p.ptrs.sp, p.ptrs.dp, p.ptrs.decode_flags);
    std::printf("flow=%p context=%p pkth=%p\n",
        static_cast<const void*>(p.flow),
        static_cast<const void*>(p.context),
        static_cast<const void*>(p.pkth));
}
```

在一个接入调试构建、喂入合成 TCP 包的测试桩里，输出类似如下。示例输出，具体格式需对照实际版本核验。

```text
pkt=0x0000000000c31000 pktlen=74 data=0x0000000000c31022 dsize=40
layers=0x0000000000b28010 num_layers=3 type=2
sp=12345 dp=80 decode_flags=0x00000000
flow=0x0000000000b1f2a0 context=0x0000000000b2c000 pkth=0x0000000000c30000
```

逐行判读如下，合计超过 150 字。第一行给出 `pkt` 与 `data` 两个指针以及 `pktlen=74`、`dsize=40`：正常情形下 `data` 落在 `pkt` 地址之后且 `pkt + pktlen` 之内，`dsize` 不大于 `pktlen`；本例两者相差 `0x22`（34 字节），对应以太网头加 IP/TCP 头的典型长度，属于合理范围。若 `data` 为 `(nil)` 而 `dsize` 非零，或 `dsize` 大于 `pktlen`，应回查 `PacketManager::decode()` 对 `data`、`dsize` 的赋值（`原理见 06-03`），而不是怀疑打印代码。第二行 `layers` 非空、`num_layers=3` 表示已解出三层封装，`type=2` 是 `PktType` 的数值（`NONE=0, IP=1, TCP=2, UDP=3, ICMP=4 ...`），本例为 TCP，应与 `proto_bits` 中的 `PROTO_BIT__TCP`、`FlowKey::ip_protocol=6` 相互印证；若三者不一致，通常是重组包或伪包导致 `ptrs.type` 与原始协议不同，需结合 `packet_flags` 的 `PKT_REBUILT_STREAM`、`PKT_PSEUDO` 位判断。第三行 `sp=12345`、`dp=80` 来自 `DecodeData::sp/dp`，`decode_flags=0` 表示本次解码未置任何 `DECODE_ERR_*` 或 `DECODE_FRAG` 位；一旦出现 `0x1`、`0x2` 等校验和错误位，检查器可能丢弃该包，取值时应与 `SnortConfig` 的校验和策略一起看（`参数见 04-03`）。第四行三个指针均非空，说明 `flow`、`context`、`pkth` 都已绑定；`pkth` 指向 `DAQ_PktHdr_t`，其本体字段不在本仓库头文件内展开，见 05-07 并需对照实际版本核验。需要强调的是，本例所有数值只作字段可读性核对，不代表任何性能结论；吞吐、pps、内存占用一律标注「需在目标机型实测」，不给绝对值。字段的完整定义见 05-02 本节，DAQ 头字段见 05-07，解码与流重组链路见 `原理见 06-03 ｜ 原理见 06-05`，目录职责见 `模块见 07-09 ｜ 模块见 07-10`，相关配置见 `参数见 04-03 ｜ 参数见 04-04`。

### 6. 版本差异

代际差异首先体现在「谁拥有状态」。Snort 2 用 C 结构体与全局流表，`Packet` 与会话状态耦合较紧；Snort 3 把每包状态收进 `struct SO_PUBLIC Packet`（`src/protocols/packet.h`），把跨包状态收进 `class SO_PUBLIC Flow`（`src/flow/flow.h`），并用 `FlowData`/`FlowDataStore`（`src/flow/flow_data.h`）让各 inspector 以 `id` 挂接自己的状态，避免把所有协议的字段塞进同一个大结构。因此「在 `Packet` 里找 TCP 会话状态」「在 `Flow` 里找原始帧指针」都是 Snort 2 习惯，在 3.x 不成立。配置也换了体系：Lua 取代 `snort.conf`，影响 `Packet::user_*_policy_id`、`Flow::*_policy_id` 的来源（`参数见 04-02`），`tools/snort2lua/` 只是格式转换辅助工具，不等于字段可直接沿用。插件 ABI 不通用，`SO_PUBLIC` 宏、`BaseApi` 前缀与版本派生宏见 05-04，具体兼容边界需对照实际版本核验。

上游 master 快照（2026-11 抓取）内部的演进痕迹同样明显。`src/protocols/packet.h` 里有一条 `// FIXIT-M Consider moving ip_proto_next below pkth.` 与 `// FIXIT-M packet flags should always be thread safe` 注释，说明 `ip_proto_next`、`ts_packet_flags` 的位置与线程安全性仍在调整；`PKT_TCP_INJECT_BLOCKED` 等三个宏已用 `0x...ULL` 扩到 64 位，`packet_flags` 相应为 `uint64_t`。`src/framework/decode_data.h` 的 `PROTO_BIT__TUNNEL_DECAP` 注释为「Derived state, deliberately outside PROTO_BIT__ALL」，是后加的派生位。`src/flow/flow.h` 有 `// FIXIT-M privatize if possible`、`// FIXIT-L shared_ptr?` 等标注，`flags` 位域近年新增了 `efd_flow`、`retry_queued`、`ha_flow`、`disable_reassembly_by_ips`、`do_not_decrypt` 等位；`src/flow/flow_key.h` 的 `tenant_id` 受 `DISABLE_TENANT_ID` 条件编译控制（开关见 04-01）。这些都说明字段集合、顺序与位含义不是冻结的，任何依赖 `sizeof`、偏移、位编号或「声明顺序即业务顺序」的结论都必须标注「需对照实际版本核验」。具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，本套资料不写绝对版本号。

能力边界对字段可读性的影响要再次强调：抓包依赖独立 libdaq / DAQ3，`pkth`、`daq_msg`、`daq_instance` 的类型本体随 libdaq 版本变化（字段见 05-07，需对照实际版本核验）；加密流量载荷不可见，`data`/`dsize` 不含解密明文，`Flow::flags.data_decrypted` 之类的位只反映状态而非内容；内联 IPS 的 drop / block 通过 DAQ verdict 反馈，`Flow::last_verdict` 只是记录，Snort 本身不是防火墙、不做 IP 转发；Hyperscan 是可选加速，缺失回退 `src/search_engines/` 其他实现，不影响本篇字段；线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」，`ts_packet_flags` 与 `context` 的并发语义需对照实际版本核验。

### 7. 常见误用与调试

第一类误用是把 `packet_flags` 当 32 位读。源码明确 `uint64_t packet_flags = 0`，且 `PKT_TCP_INJECT_BLOCKED`、`PKT_HTTP_INJECT_ALLOWED`、`PKT_HTTP_INJECT_BLOCKED` 三个宏带 `ULL` 后缀落在高 32 位。若外部工具用 `uint32_t` 截断，注入相关判断会静默失效。同理 `xtradata_mask` 是 `uint32_t`、`ts_packet_flags` 是 `uint8_t`，三者不要混用位运算宽度。第二类误用是忽略 `reset()` 清零界线：把 `context`、`pkth`、`data` 当成「每包自动清零」，在池化复用时读到上一个包的残留值。定位方法是先打印 `packet_flags` 与 `num_layers` 确认是否新包，再检查 `PacketManager::decode()` 是否覆盖了对应下方字段（`原理见 06-03`）。

第三类误用是对 `FlowKey` 做字节级假设。`FlowKey::is_equal()` 用 `memcmp` 比较整个 `sizeof(FlowKey)`，且结构被 `PADDING_GUARD` 包裹、`tenant_id` 受条件编译影响；硬编码 `sizeof(FlowKey)`、按偏移读 `ip_l[4]`，或假设「`group_l` 紧邻 `port_h`」，在不同构建（尤其开了 `DISABLE_TENANT_ID` 的构建，`参数见 04-01`）下都会错位。正确做法是使用 `FlowKey::init()` 与 `FlowHashKeyOps`（`原理见 06-05`），并把 `FlowKey` 视为不透明键。第四类是把不透明句柄当普通结构：`Session` 子类、`IpApi`、`MplsHdr`、`FlowHAState`、`BitOp`、`StreamFlowIntf`、`SFDAQInstance`、`Active`、`ActiveAction` 的具体布局都不在本篇头文件中，属于**不透明句柄，内部布局见对应 `.cc` 或 `src/stream/`、`src/packet_io/`，不可依赖**；应改用公开访问器，如 `Flow::get_flow_data()`、`Flow::get_session_flags()`、`Packet::get_ip_proto_next()`。

第五类是场景前提误判。加密载荷不可见时，`data`/`dsize` 指向可见载荷而非明文正文；IDS 旁路模式下 `last_verdict` 不会被写成 drop；伪包（`PKT_PSEUDO`）的 `pkt`/`pktlen` 与线包不同，`pseudo_type` 才有意义；重组包（`PKT_REBUILT_STREAM`）的 `ptrs.type` 可能是 `PDU` 而非 `TCP`。把「字段没值」当成「字段定义错误」是最常见的排错弯路，应先确认运行模式与包类型。第六类是数值误读：`dsize` 为 `uint16_t`，`max_dsize` 只是注释里说的「minimum allowable」，不要写成绝对上限；`FlowStats` 的字节与包计数是 `uint64_t`，`mem_bytes`/`peak_mem_bytes` 是 `size_t`，跨 32/64 位构建打印时格式符要匹配。所有涉及吞吐、pps、丢包率、内存占用的结论一律标注「需在目标机型实测」，不给绝对值；基准方法见 08-01，调优见 08-02。配置自检用 `snort -T`、构建标识用 `snort -V`（完整参数见 04-07）；若字段读数与源码声明长期不一致，优先核对二进制与头文件是否来自同一快照，需对照实际版本核验。

必须先划清一条容易越界的线：本篇列的是 `SnortConfig` 的**成员字段**，即 C++ 结构体在内存里的数据成员，不是 `lua/snort.lua` 的参数全集。CMake 选项、Lua 顶层段、DAQ 与 inspector 参数、规则关键字、命令行与 shell 控制的完整清单归 04 册，本篇一律写「参数见 04-01」「参数见 04-02」「参数见 04-03」「参数见 04-07」，不解释某个字段对应哪个 Lua 键、不列取值表、不给配置建议。同理，配置如何被加载、如何做 `snort -T` 自检、如何在重载时交换，属于机制链路，统一写「原理见 06-01」「原理见 06-13」；本篇只在「读写时机」列标注「配置加载期写入」「运行期只读」「重载期交换」这类静态结论。能力边界同样适用：Lua 配置是相对 Snort 2 的全新实现，不兼容 `snort.conf` 与旧插件 ABI，`tools/snort2lua/` 只是格式转换辅助；抓包依赖独立 libdaq / DAQ3，`SnortConfig::daq_config` 只是适配层配置的指针；Hyperscan 是可选加速，`SnortConfig::hyperscan_literals`、`pcre_to_regex` 等布尔字段不构成必需依赖。

**SnortConfig 的整体形态与静态访问**。`src/main/snort_config.h` 顶部注释「SnortConfig encapsulates all data loaded from the config files」与「FIXIT-L privatize most of this stuff」表明它是把原先散落的全局配置收进单一对象，且封装仍在收敛。构造有两个重载：`SnortConfig(const char* exclude_name = nullptr)` 与 `SnortConfig(ProtocolReference* protocol_reference)`，析构 `~SnortConfig()`，拷贝构造被 `= delete`；私有 `init(ProtocolReference*, const char*)` 做实际初始化。运行期访问靠三个静态函数：`static const SnortConfig* get_conf()`（包线程只读，源码注释明确「prefer access via packet->context->conf」）、`static SnortConfig* get_main_conf()`（仅主线程特殊场景）、`static void set_conf(SnortConfig*)`。这组函数是理解「配置在运行期不可随意改写」的关键：检测线程应通过 `Packet::context->conf` 或直接 `get_conf()` 只读访问，写操作集中在主线程的配置装配与重载期。`src/main/snort_config.cc` 中可核验的成员函数包括 `init()`（174 行）、`setup()`（335 行）、`post_setup()`（369 行）、`update_scratch(ControlConn*)`（381 行）、`merge(const SnortConfig*)`（387 行）、`verify() const`（517 行）、以及大量 `set_*()` 与 `get_*()`；`merge()` 负责把命令行配置合并进主配置，`verify()` 做校验，二者都属于「原理见 06-01」的链路，本篇只列入口名。`static_hash()`、`cleanup_fatal_error()`、`get_static_name()`、`get_classification_id()`、`request_scratch()`、`release_scratch()` 是同文件的静态工具入口。

**`run_flags` 与三族标志宏**。`src/main/snort_config.h` 定义 `enum RunFlag`、`enum OutputFlag`、`enum LoggingFlag`、`enum TunnelFlags`、`enum DumpConfigType` 五组枚举/宏。`RunFlag` 从 `RUN_FLAG__READ`（`0x00000001`）到 `RUN_FLAG__DROP_STALE_PACKETS`（`0x04000000`），中间含 `RUN_FLAG__INLINE`、`RUN_FLAG__PAUSE`、`RUN_FLAG__TEST`、`RUN_FLAG__CONF_ERROR_OUT`、`RUN_FLAG__PROCESS_ALL_EVENTS` 等；注意 `RUN_FLAG__SHELL` 被 `#ifdef SHELL`、`RUN_FLAG__EXIT_AFTER_RELOAD` 被 `#ifdef REG_TEST` 包裹，说明 `run_flags` 的可用位随构建开关变化，外部工具不可硬编码位编号。`OutputFlag` 含 `OUTPUT_FLAG__LINE_BUFFER`、`__VERBOSE_DUMP`、`__CHAR_DATA`、`__APP_DATA`、`__SHOW_DATA_LINK`、`__USE_UTC`、`__INCLUDE_YEAR`、`__OBFUSCATE`、`__ALERT_IFACE`、`__NO_TIMESTAMP`、`__ALERTS`、`__WIDE_HEX`、`__ALERT_REFS`、`__LOG_BUFFERED`，其中 `OUTPUT_FLAG__OBFUSCATE` 的注释明确「using this alters the packet - can't be used inline」。`LoggingFlag` 三个值 `LOGGING_FLAG__VERBOSE/QUIET/SYSLOG`。`TunnelFlags` 给出 `TUNNEL_GTP/TEREDO/6IN4/4IN6/4IN4/6IN6/GRE/MPLS/VXLAN/GENEVE` 十位，`tunnel_mask`（`uint16_t`）与 `tunnel_bypass_enabled(uint16_t)` 配套。`DumpConfigType` 取值 `DUMP_CONFIG_NONE/JSON_ALL/JSON_TOP/TEXT`。这些宏是读 `run_flags`、`output_flags`、`tunnel_mask` 的字典，但**不是**参数表：具体怎么在 Lua 或命令行里设置，全部写「参数见 04-02」「参数见 04-07」。

**不透明句柄密集区**。`SnortConfig` 里超过二十个字段是指向仅前向声明类型的指针：`SFDAQConfig`、`FastPatternConfig`、`EventQueueConfig`、`PayloadInjectorConfig`、`ThresholdConfig`、`RateFilterConfig`、`DetectionFilterConfig`、`IpsActionsConfig`、`FrameworkConfig`、`RulePortTables`、`PORT_RULE_MAP`、`srmm_table_t`、`sopg_table_t`、`XHash`、`GHash`、`ProtocolReference`、`RuleStateMap`、`ProfilerConfig`、`ProfilerNodeMap`、`LatencyConfig`、`MemoryConfig`、`ThreadConfig`、`HighAvailabilityConfig`、`TraceConfig`、`ReloadResourceTuner`、`ScratchAllocator`、`ControlConn`。在 `snort_config.h` 中它们只有 `struct XXX;` 或 `class XXX;` 的前置声明，字段本体定义在各自的 `.cc` / 头文件里，例如 `sfdaq_config.cc`、`fp_config.cc`、`event_queue.cc`、`src/utils/` 下的哈希实现。按本册纪律，这些一律表述为**不透明句柄，内部布局见对应实现文件，不可依赖**；本册只写指针字段的存在、用途与读写时机，不臆造其成员。特别提醒 `otn_map`（`GHash*`）、`detection_option_hash_table`、`detection_option_tree_hash_table`、`rtn_hash_table`（`XHash*`）这几张规则编译期哈希表，以及 `prmIpRTNX`、`prmIcmpRTNX`、`prmTcpRTNX`、`prmUdpRTNX` 四个 `PORT_RULE_MAP*`、`srmmTable`、`spgmmTable`、`sopgTable`，它们的注释在 `snort_config.h` 里说明了「按协议/端口 O(1) 选出规则组」的用途，但字段结构归 05-06 与「原理见 06-06」，本篇不展开。

### 4. 典型示例

下面这段 C++ 片段演示如何以只读方式核对 `SnortConfig` 与 `Value` 的字段取值，不修改任何配置、不触发加载流程，适合在调试构建里确认字段与头文件一致。

```cpp
#include "main/snort_config.h"
#include "framework/value.h"
#include <cstdio>

void dump_conf_fields(const snort::SnortConfig* sc, const snort::Value& v)
{
    if ( !sc )
        return;
    std::printf("run_flags=0x%08x output_flags=0x%08x\n",
        sc->run_flags, sc->output_flags);
    std::printf("pkt_cnt=%llu max_continuations=%u\n",
        static_cast<unsigned long long>(sc->pkt_cnt), sc->max_continuations);
    std::printf("num_layers=%u max_ip_layers=%u mpls_agnostic=%d\n",
        sc->get_num_layers(), sc->max_ip_layers,
        static_cast<int>(sc->get_mpls_agnostic()));
    std::printf("value_type=%d uint64=%llu\n",
        static_cast<int>(v.get_type()),
        static_cast<unsigned long long>(v.get_uint64()));
}
```

在一个把该函数接入配置装配完成之后的调试桩里，输出类似如下。示例输出，具体格式需对照实际版本核验。

```text
run_flags=0x00000010 output_flags=0x00000000
pkt_cnt=0 max_continuations=1024
num_layers=40 max_ip_layers=0 mpls_agnostic=1
value_type=2 uint64=1500
```

逐行判读如下，合计超过 150 字。第一行 `run_flags=0x00000010` 对应 `src/main/snort_config.h` 的 `RUN_FLAG__INLINE`（`0x00000010`），说明该配置处于内联模式；这里要注意 `RUN_FLAG__SHELL`、`RUN_FLAG__EXIT_AFTER_RELOAD` 分别受 `#ifdef SHELL`、`#ifdef REG_TEST` 包裹（开关见 04-01），因此同一数值在不同构建下可解释的位集合不同，外部工具不要把位编号写死。`output_flags=0` 表示未启用 `OUTPUT_FLAG__*` 任何位，若读到 `0x80` 则对应 `OUTPUT_FLAG__OBFUSCATE`，源码注释提示该标志会改写包、不能用于内联，排错时要与 `run_flags` 一起看。第二行 `pkt_cnt=0` 是 `uint64_t` 初值，表示未设包数上限（对应 `-n`，完整参数见 04-07）；`max_continuations=1024` 照抄源码成员初值，属于字段默认值而非推荐配置值，具体可调范围见「参数见 04-02」。第三行 `num_layers=40` 来自 `get_num_layers()`，与 `packet.h` 的 `DEFAULT_LAYERMAX = 40` 数值一致但语义不同：前者是 `SnortConfig` 的解码层数上限字段，后者是 `Packet` 侧的编译期常量，切勿混为一谈；`max_ip_layers=0` 表示未设 IP 层上限（`hit_ip_maxlayers()` 返回 false）；`mpls_agnostic=1` 对应源码初值 `true`。第四行 `value_type=2` 是 `Value::ValueType` 的数值（`VT_BOOL=0, VT_NUM=1, VT_UNUM=2, VT_STR=3, VT_REAL=4`），本例为 `VT_UNUM`，`uint64=1500` 与 `Value::unum` 一致；若 `type` 与所用的 `get_*()` 不匹配，读到的数值是联合式存储里的另一种解释，应先 `get_type()` 再选转换方法。以上判读只覆盖字段取值，字段定义见本节，配置参数的完整清单见「参数见 04-02」，加载与重载链路见「原理见 06-01 ｜ 原理见 06-13」，目录职责见「模块见 07-12 ｜ 模块见 07-01」。

### 6. 版本差异

代际差异的核心是「配置从文件全局变量变成单一对象」。Snort 2 用 `snort.conf` 加大量全局变量与解析表；Snort 3 是从 Snort 2 重写的 C++ 实现，配置改为 Lua（`lua/snort.lua`、`lua/snort_defaults.lua`），`SnortConfig`（`src/main/snort_config.h`）把配置收进一个对象，通过 `static get_conf()` 提供运行期只读访问，解析则交给 `Module`/`Parameter`/`Value` 三件套（`src/framework/`）。因此「按全局变量名找配置」「直接改全局开关」在 3.x 都不成立；`tools/snort2lua/` 只转配置格式，不迁移字段语义，规则关键字与 Snort 2 有差异、不宣称完全兼容。插件 ABI 也不通用，`BaseApi` 前缀与 `BASE_API_VERSION` 的版本派生见 05-04，具体兼容边界需对照实际版本核验。

上游 master 快照（2026-11 抓取）内部的演进痕迹很多。`snort_config.h` 顶部「FIXIT-L privatize most of this stuff」说明公开字段仍会收敛；同文件有一段「FIXIT-L command line only stuff, add to conf / module」与「FIXIT-L non-module stuff - separate config from derived state?」，把 `run_prefix`、`id_offset`、`id_subdir`、`id_zero`、`stdin_rules`、`pid_filename`、`max_procs` 等标为待整理；`pcre_match_limit*` 上有「FIXIT-L pcre_match_limit* are interdependent」注释；`max_pdu = 16384` 上有「FIXIT-L this is temporary for legacy paf_max」注释。`#ifdef REG_TEST` 让 `output_flags` 初值在 REG_TEST 构建下为 `OUTPUT_FLAG__WIDE_HEX`、`#ifdef SHELL` 让 `RUN_FLAG__SHELL` 存在、`#ifdef HAVE_UUID` 让 `uuid_t` 类型变化；`service_extension` 用内联初值写死 `http -> {http2, http3}` 与 `netbios-ssn -> {dcerpc}`。这些都说明字段集合、初值与条件位不是冻结的，任何依赖具体初值、位编号或「字段一定公开」的结论都要标注「需对照实际版本核验」。具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，本套资料不写绝对版本号。

能力边界对字段的影响：抓包依赖独立 libdaq / DAQ3，`daq_config` 指向的 `SFDAQConfig` 随 libdaq 版本变化（字段见 05-07，需对照实际版本核验）；内联 IPS 的 drop / block 通过 DAQ verdict 反馈，`RUN_FLAG__INLINE`、`POLICY_MODE__INLINE` 只反映模式，Snort 本身不是防火墙、不做 IP 转发；加密载荷不可见，`enable_esp`、`address_anomaly_check_enabled` 不改变这一事实；Hyperscan 是可选加速，`hyperscan_literals`、`pcre_to_regex` 缺失时回退 `src/search_engines/` 其他实现；规则关键字与 Snort 2 有差异，`rule_lists`、`evalOrder`、`prm*RTNX` 的形态随规则编译器演进；线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」，`offload_threads`、`thread_config`、`watchdog_min_thread_count` 只说明字段存在，不推断数量。许可按 GPLv2 处理，Talos 规则集另有独立许可约束（`lua/talos.lua`）。

### 7. 常见误用与调试

第一类误用是把字段当参数手册用。看到 `pcre_match_limit = 1500`、`max_continuations = 1024`、`tagged_packet_limit = 256` 就照抄成「推荐配置」，或试图在本篇找 Lua 键名与取值表，都是越界：这些是 C++ 成员初值，配置全集在 04 册（`参数见 04-02`、`参数见 04-03`），运行期是否生效还取决于模块是否编入（`参数见 04-01`）。第二类误用是硬编码 `run_flags` / `output_flags` 的位编号：`RUN_FLAG__SHELL`、`RUN_FLAG__EXIT_AFTER_RELOAD` 受条件编译控制，`OUTPUT_FLAG__OBFUSCATE` 会改写包且不能用于内联，位集合必须回查 `src/main/snort_config.h` 的枚举定义，需对照实际版本核验。

第三类误用是把不透明句柄当结构展开。`SFDAQConfig`、`FastPatternConfig`、`EventQueueConfig`、`ThresholdConfig`、`RateFilterConfig`、`DetectionFilterConfig`、`PolicySelector`、`GHash`、`XHash`、`PORT_RULE_MAP`、`srmm_table_t`、`sopg_table_t`、`ProfilerConfig`、`TraceConfig`、`ThreadConfig`、`MemoryConfig`、`HighAvailabilityConfig`、`ScratchAllocator`、`ServicePig`、`TrafficPig`、`GlobalPig`、`VarEntry` 在 `snort_config.h` / `policy.h` 里只有前向声明，属于**不透明句柄，内部布局见对应 `.cc` 或 `src/utils/`、`src/managers/`，不可依赖**；用 `sizeof()` 或偏移读它们的成员会静默错位，正确做法是使用公开访问器或 `get_conf()` 返回的只读指针。第四类是误用 `Value`：它用 `type` 加多个私有数值字段承载值，若不看 `get_type()` 就调 `get_uint64()`，在 `VT_STR` 或 `VT_REAL` 的情况下得到的是另一种解释，应先用 `get_as_string()` 或按类型分支，且注意 `mask_bits = 52` 隐含的整数精度约束。同理 `Parameter::range` 是 `const void*`，形态随 `type` 变化，不能一律当 `const char*` 用。

第五类是运行期写配置。`SnortConfig` 的写操作集中在主线程装配与重载期，检测线程应通过 `get_conf()` 或 `packet->context->conf` 只读访问；在包处理路径里改 `run_flags`、`output_flags` 会引发线程安全隐患，重载语义见「原理见 06-13」。第六类是同名混淆：`SnortConfig::num_layers` 是解码层数上限配置，`Packet::num_layers` 是当前包已解出的层数（字段见 05-02）；`IpsPolicy::policy_mode` 与 `SnortConfig::run_flags` 的 `RUN_FLAG__INLINE` 也不是同一层级的判断，应优先用 `ips_inline_mode()` 这类访问器。调试时先用 `snort -V` 核对构建标识、用 `snort -T` 做配置自检（完整参数见 04-07），再用第 4 节的只读打印确认字段值；若字段读数与源码声明长期不一致，优先核对二进制与头文件是否来自同一快照。所有涉及吞吐、pps、内存占用的结论一律标注「需在目标机型实测」，不给绝对值；基准方法见 08-01，调优见 08-02，配置类故障案例见 08-04。

### 3. 逐项详解

**BaseApi 与版本派生机制**。`src/framework/base_api.h` 定义 `#define BASE_API_VERSION 29`、`#define PLUGIN_DEFAULT 0x0`、`#define PLUGIN_SO_RELOAD 0x1`（注释「assumed for PT_SO_RULE」）、`#define API_RESERVED 0`（注释「the reserved field is now called features」），以及 `enum PlugType { PT_CODEC, PT_INSPECTOR, PT_IPS_ACTION, PT_IPS_OPTION, PT_SEARCH_ENGINE, PT_SO_RULE, PT_LOGGER, PT_CONNECTOR, PT_POLICY_SELECTOR, PT_MP_TRANSPORT, PT_TRACE, PT_MAX }` 共 12 个类型（含 `PT_MAX` 哨兵）。`BaseApi` 的十字段里，`type`、`size`、`api_version` 三者共同承担版本与兼容性校验：`api_version` 按 `(BASE_API_VERSION << 16) | plugin-api-version` 拼装，`src/framework/inspector.h` 的 `INSAPI_VERSION ((BASE_API_VERSION << 16) | 5)`、`ips_option.h` 的 `IPSAPI_VERSION ((BASE_API_VERSION << 16) | 4)`、`ips_action.h` 的 `ACTAPI_VERSION ((BASE_API_VERSION << 16) | 3)` 都是同一模式。由此可推出一条调试准则：加载 SO 插件报「版本不匹配」时，先核对这三个宏与 `BaseApi::size`，而不是改字段。具体兼容边界需对照实际版本核验，插件装配见「原理见 06-14」，模块目录见「模块见 07-01」。

**Inspector 与 InspectApi**。`class SO_PUBLIC Inspector` 的私有段只有 `api`（`const InspectApi*`）、`thread_specific_data`（`std::shared_ptr<ThreadSpecificData>`）、`ref_count`（`std::atomic_uint*`）、`snort_protocol_id`（`SnortProtocolId`，初值 0）、`alias_name`（`std::string`）、`network_policy_user_id`（`uint64_t`，初值 0）六个字段，其余全为虚方法：`configure(SnortConfig*)`、`tear_down(SnortConfig*, bool)`、`disable(SnortConfig*)`、`show()`、`tinit()`、`tterm()`、`likes(Packet*)`、`eval(Packet*)`、`clear(Packet*)`、三族 `get_buf()`、`get_splitter(bool)`、`install_reload_handler(SnortConfig*)`、`adjust_log_packet()` 等。`struct InspectionBuffer` 只有 `const uint8_t* data`、`unsigned len`、`bool is_accumulated = false` 三字段，其 `enum Type` 给出 `IBT_VBA`、`IBT_JS_DATA`、`IBT_KEY`、`IBT_HEADER`、`IBT_BODY`、`IBT_MAX`，源码注释把前两个标为「only generic rule options」，把中间三个标为「FIXIT-M all of these should be eliminated」。`enum InspectorType` 八值：`IT_PASSIVE`（仅配置或数据消费）、`IT_PACKET`（只处理原始包）、`IT_STREAM`（流跟踪与重组）、`IT_NETWORK`（无服务的包处理）、`IT_SERVICE`（提取并分析服务 PDU）、`IT_CONTROL`（检测前处理全部包）、`IT_PROBE`（检测后处理全部包）、`IT_PROBE_FIRST`（检测前处理全部包）、`IT_MAX`。`InspectApi` 十二字段已在第 2 节表列出，其中 `buffers` 是 `const char**` 且注释为「null terminated list of exported buffers」，`service` 在非 `IT_SERVICE` 时为 `nullptr`。四个 `typedef` 定义函数指针形态：`InspectNew`（`Inspector* (*)(Module*)`）、`InspectDelFunc`、`InspectFunc`、`InspectSsnFunc`（`Session* (*)(Flow*)`）。`struct ReloadSurvivorSubscriptions` 私有段为 `NetworkPolicy& np`、`InspectionPolicy& ip`、`Inspector& survivor`，用于重载存活订阅（`原理见 06-13`）。`ThreadSpecificData`、`BitOp` 等外部类型属于**不透明句柄，内部布局见 `src/framework/inspector.cc` 与相关 `.cc`，不可依赖**。

**Module / Command / RuleMap**。`class SO_PUBLIC Module` 的字段已在 05-03 逐项给出：私有 `name`、`help`、`params`（`const Parameter*`）、`list`、`table_level`，保护 `dump_stats_initialized`、`counts`、`dump_stats_counts`、`dump_stats_results`、`num_counts`。本篇补充其插件侧语义：`enum Usage { GLOBAL, CONTEXT, INSPECT, DETECT }` 由 `get_usage()` 返回，`SnortModule` 覆盖为 `GLOBAL`（字段见 05-03）；`verified_begin()`、`verified_set()`、`verified_end()` 是「检查列表不是表」的包装入口；`get_commands()` 返回 `const Command*`，`get_rules()` 返回 `const RuleMap*`，`get_pegs()` 返回 `const PegInfo*`。`struct Command` 五字段 `name`、`func`（`using LuaCFunction = int(*)(lua_State*)`）、`params`（`const Parameter*`）、`help`、`bool can_run_in_parallel = false`，注释说明该标志决定命令能否与其他控制命令并行执行。`struct RuleMap` 两字段 `unsigned sid`、`const char* msg`，是内置规则的 sid 到消息映射。`Module` 的构造有两个重载（`Module(const char*, const char*)` 与带 `const Parameter*` 的四参版本），`set_params()` 供派生类设置参数表。这些字段讲「模块是什么」，至于模块如何被 `module_manager.cc`、`inspector_manager.cc` 注册装配，属于「原理见 06-14」「模块见 07-11」。

### 4. 典型示例

下面这段 C++ 片段演示如何只读核对 `Inspector`、`RuleTreeNode`、`OptTreeNode` 与 `SigInfo` 的字段，不触发插件装配或规则编译流程，便于在调试构建里确认字段与头文件一致。

```cpp
#include "framework/inspector.h"
#include "detection/treenodes.h"
#include "detection/signature.h"
#include <cstdio>

void dump_rule_fields(const snort::Inspector& ins,
    const RuleTreeNode& rtn, const OptTreeNode& otn)
{
    std::printf("inspector=%s service_id=%d\n",
        ins.get_name(), static_cast<int>(ins.get_service()));
    std::printf("rtn.action=%u rtn.flags=0x%02x refs=%u\n",
        static_cast<unsigned>(rtn.action), rtn.flags, rtn.otnRefCount);
    std::printf("otn.gid=%u otn.sid=%u rev=%u\n",
        otn.sigInfo.gid, otn.sigInfo.sid, otn.sigInfo.rev);
    std::printf("otn.evalIndex=%u ruleIndex=%u longest=%u\n",
        otn.evalIndex, otn.ruleIndex, otn.longestPatternLen);
}
```

在一个把该函数接到规则编译完成之后、传入已构造节点的调试桩里，输出类似如下。示例输出，具体格式需对照实际版本核验。

```text
inspector=http_inspect service_id=0
rtn.action=1 rtn.flags=0x63 refs=1
otn.gid=1 otn.sid=1000001 rev=1
otn.evalIndex=0 ruleIndex=42 longest=18
```

逐行判读如下，合计超过 150 字。第一行 `inspector=http_inspect` 来自 `Inspector::get_name()`，其内部返回 `api->base.name`，说明插件名取自 `BaseApi::name`；`service_id=0` 是 `snort_protocol_id` 初值，非 `IT_SERVICE` 检查器通常保持 0，若读到非零应与 `InspectApi::service` 对照。第二行 `rtn.action=1` 是 `snort::IpsAction::Type`（`uint8_t`），数值含义由动作注册表决定（字段见 05-05、`原理见 06-09`），不要按字面猜成 `alert`；`rtn.flags=0x63` 可拆为 `ENABLED(0x01) | ANY_SRC_PORT(0x02) | ANY_DST_PORT(0x04) | BIDIRECTIONAL(0x10) | ANY_SRC_IP(0x20) | ANY_DST_IP(0x40)` 中的若干位，本例表示规则头已启用且地址端口含任意值，具体位必须回查 `src/detection/treenodes.h` 的 `Flag` 常量，禁止硬编码；`refs=1` 是 `otnRefCount`，表示有一个 OTN 引用该 RTN，多策略下可能大于 1。第三行 `gid=1` 对应 `GID_DEFAULT`，`sid=1000001`、`rev=1` 来自 `SigInfo`，是规则的标识三元组；`builtin=false` 时这些值来自规则文件，内置规则则不同。第四行 `evalIndex=0`、`ruleIndex=42` 分别是规则在求值集中的位置与全局唯一序号，`longest=18` 是 `longestPatternLen`，反映该规则最长 content 的长度，与 fast pattern 选择相关（`原理见 06-07`），但不等于匹配结果。以上判读只覆盖字段取值，字段定义见本节，规则关键字清单见「参数见 04-06」，插件装配与规则编译链路见「原理见 06-14 ｜ 原理见 06-06」，目录职责见「模块见 07-01 ｜ 模块见 07-05 ｜ 模块见 07-06」，`SnortConfig` 侧字段见「字段见 05-03」。

### 6. 版本差异

代际差异体现在「插件与规则都是全新实现」。Snort 2 用 C 预处理式插件与 `snort.conf`，规则树以 `RuleTreeNode`/`OptTreeNode` 的旧形态存在；Snort 3 是从 Snort 2 重写的 C++ 实现，插件统一以 `BaseApi` 为前缀（`src/framework/base_api.h`，`BASE_API_VERSION 29`），检查器变成 `class SO_PUBLIC Inspector` 的虚方法体系，规则选项变成 `class SO_PUBLIC IpsOption` 的 `eval(Cursor&, Packet*)` 体系，配置改为 Lua。规则关键字与 Snort 2 有差异、不宣称完全兼容，`src/ips_options/` 与 `src/parser/parse_rule.cc` 的注册解析是差异集中区，需对照实际版本核验；插件 ABI 也不通用，`tools/snort2lua/` 只转配置格式。因此「把 Snort 2 的 SO 插件直接加载」「按旧 `OptTreeNode` 字段偏移读规则」都不成立。

上游 master 快照（2026-11 抓取）内部演进痕迹密集。`src/framework/inspector.h` 顶部注释「the INSAPI_VERSION will change if anything in this file changes」，当前 `INSAPI_VERSION ((BASE_API_VERSION << 16) | 5)`，`ips_option.h` 为 `| 4`、`ips_action.h` 为 `| 3`，三者不同步，说明各 API 独立演进；`InspectionBuffer::Type` 里三个值被标「FIXIT-M all of these should be eliminated」；`Inspector` 有 `// FIXIT-L` 与「cppcheck-suppress unusedFunction ; installed inspector API accessor」注释，说明部分访问器为已安装 API 保留。`src/detection/treenodes.h` 有「FIXIT-L use bit mask to determine what header checks to do cheaper than traversing a list」与「FIXIT-L factor the profiling stuff out」注释，`struct alignas(64) OtnState` 是缓存行对齐的后期优化；`ips_flow.cc` 的 `FlowCheckOption` 标 `// FIXIT-L privatize`；`src/framework/ips_option.h` 的 `get_pattern()` 注释「temporary until IpsOption api updated」出现在 `packet.h` 的 `PKT_FAST_PAT_EVAL`。这些都说明字段集合、枚举值与对齐方式会继续变化，任何依赖 `sizeof(RuleTreeNode)`、位编号、枚举数值或「`OptFpList` 一定按声明顺序求值」的结论都要标注「需对照实际版本核验」。具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，本套资料不写绝对版本号。

能力边界对字段的影响：Lua 配置取代 `snort.conf`，`Module`/`Parameter` 的字段已在 05-03 给出，本篇不重复；抓包依赖独立 libdaq / DAQ3，与 `Inspector` 字段无直接关系但决定 `proto_bits` 可见的协议范围（`模块见 07-07`）；加密载荷不可见，`IT_SERVICE` 检查器能拿到的是握手元数据与缓冲，不含 HTTPS 明文正文，应用识别依赖 inspector / binder / wizard（`原理见 06-04`）；Hyperscan 是可选加速，`longestPatternLen`、`normal_fp_only`、`offload_fp_only` 只反映规则编译结果，缺失时回退 `src/search_engines/` 其他实现；线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」，`Inspector::ref_count` 是 `std::atomic_uint*`、`tinit()`/`tterm()` 的并发语义需对照实际版本核验。许可按 GPLv2 处理，Talos 规则集另有独立许可约束（`lua/talos.lua`）。

### 7. 常见误用与调试

第一类误用是把薄基类当厚结构。`Inspector` 只有六个私有字段、`IpsOption` 只有两个私有字段，具体关键字的数据在 `src/ips_options/ips_*.cc` 的内部类里。想读 `content` 的模式串却去 `IpsOption` 里找 `pattern_buf`，必然扑空；正确路径是先确认该关键字对应的 `.cc`，再看其内部结构（`ContentData::pmd` 等），并把这些类型视为**不透明句柄，内部布局见各 `ips_*.cc`，不可依赖**。第二类误用是硬编码枚举与位：`RuleTreeNode::flags` 的八个 `Flag` 常量、`OptTreeNode::flags` 的八个 `Flag` 常量、`InspectorType` 的 `IT_*`、`CursorActionType` 的 `CAT_*`、`RuleOptType` 的 `OPT_TYPE_*` 都可能随版本增删，位编号与数值必须回查头文件，需对照实际版本核验。

第三类误用是混淆 `Module` 与 `Inspector`。`Module` 承载配置参数表（`params`），`Inspector` 承载运行期包处理状态与 `api`；`InspectApi::ctor` 的类型是 `Inspector* (*)(Module*)`，说明构造期把 `Module` 数据交给 `Inspector`，二者不是同一对象的两个视角。把 `Module::params` 当成 `Inspector` 字段，或反过来在 `Module` 里找 `eval()`，都会定位错文件。第四类是把 API 版本派生宏当常量用：`INSAPI_VERSION`、`IPSAPI_VERSION`、`ACTAPI_VERSION` 各带不同的插件子版本，且 `BaseApi::api_version` 由 `(BASE_API_VERSION << 16) | plugin-api-version` 拼装，加载 SO 插件失败时先核对 `BaseApi::size` 与 `api_version`，不要改字段或跳过校验（`原理见 06-14`）。

第五类是忽视不透明边界。`ThreadSpecificData`、`BitOp`、`sfip_var_t`、`PortObject`、`TagData`、`THD_NODE`、`OutputSet`、`IpsInfo`、`ByteData`、`RangeCheck`、`Base64DecodeData`、`LiteralSearch` 等在本篇头文件里只有前向声明，属于**不透明句柄，内部布局见对应 `.cc`，不可依赖**；应改用公开访问器，如 `Inspector::get_service()`、`IpsOption::get_name()`、`RuleTreeNode::enabled()`。第六类是把规则结构与流程混读：`RuleTreeNode`/`OptTreeNode` 的字段讲「规则在内存里长什么样」，至于规则如何解析、如何分组、如何挂 fast pattern、如何求值，全部是「原理见 06-06」「原理见 06-07」「原理见 06-08」；在 05 册里找调用链只会得到交叉引用。调试时先用 `snort -T` 验证规则能否加载（完整参数见 04-07），未知关键字报错回查 `src/managers/ips_manager.cc` 与 `src/ips_options/`（`模块见 07-06`），再用第 4 节的只读打印确认字段值。所有涉及吞吐、pps、内存占用的结论一律标注「需在目标机型实测」，不给绝对值；基准方法见 08-01，规则集规模与 fast_pattern 的调优见 08-02，规则加载类故障案例见 08-04。

### 3. 逐项详解

**DetectionEngine 的静态门面形态**。`src/detection/detection_engine.h` 的 `class SO_PUBLIC DetectionEngine` 顶部注释「DetectionEngine manages a detection context. To detect a rebuilt packet (PDU), first call set_next_packet() ... then instantiate a new DetectionEngine to detect that packet.」说明它是按包实例化的门面，但状态并不住在它里面。私有段仅 `static bool offload_enabled` 与 `IpsContext* context = nullptr`；构造 `DetectionEngine()` 与析构 `~DetectionEngine()` 在 `detection_engine.cc` 管理上下文的获取与归还。公开方法全是 `static`：`init()`、`thread_init()`、`thread_term()`、`reset()`、`get_context()`、`get_current_packet()`、`get_current_wire_packet()`、`set_next_packet(const Packet*, Flow*)`、`get_next_context()`、`get_next_buffer(unsigned&)`、`enable_offload()`、`offload(Packet*)`、`onload()`、`idle()`、`set_encode_packet()`、`set_file_data()` 两重载、`get_file_data()` 两重载、`get_buffer(unsigned&)`、`get_alt_buffer()`、`acquire_alt_buffer()`、`reset_alt_buffer()`、`set_data()`/`get_data()`、`add_replacement()`/`get_replacement()`/`clear_replacement()`、`detect(Packet*, bool)`、`inspect(Packet*)`、`queue_event()` 两重载、`log_builtin_event()`、`clear_events()`、`set_packet_abandoned()`、`disable_all()`、`disable_content()`、`get_detects()`/`set_detects()`、`set_check_tags()`、`wait_for_context()`、`get_pub_id()`；私有静态还有 `get_event_queue()`、`do_offload()`、`offload_thread()`、`complete()`、`resume()`、`resume_ready_suspends()`、`log_events()`、`finish_inspect()`、`finish_packet()` 等。三个内联辅助 `get_alt_buffer()`、`acquire_alt_buffer()`、`reset_alt_buffer()` 直接操作 `p->context->alt_data`，是「字段见 05-05」与「字段见 05-02」的交汇点。这些入口名只作字段关联，调用顺序一律「原理见 06-08」「原理见 06-13」。

**detect.h 的「无字段」事实**。`src/detection/detect.h` 全文只有 `extern THREAD_LOCAL snort::ProfileStats eventqPerfStats;` 与若干函数声明：`bool snort_ignore(snort::Packet*)`、`bool snort_log(snort::Packet*)`、`void CallLogFuncs(...)` 两重载、`void CallAlertFuncs(...)`、`void enable_tags()`、`void check_tags(snort::Packet*)`，以及前向声明 `struct ListHead`、`struct OptTreeNode`。它没有任何 `struct` / `class` 数据成员。这一点必须写明：把 `detect.h` 当成「检测引擎主结构体」去列字段会产出空表或臆造字段，正确的做法是把检测状态定位到 `IpsContext`，把告警输出函数留在 `detect.h`，字段归 05-05（本事实）与 05-08（事件侧）。

**IpsContext 的字段族与生命周期**。`class SO_PUBLIC IpsContext` 的注释「IpsContext provides access to all the state required for detection of a single packet. the state is stored in IpsContextData instances, which are accessed by id.」点明它是单包状态的容器。构造 `IpsContext(unsigned size = 0)`（注释「defaults to max id」），析构 `~IpsContext()`，拷贝与赋值 `= delete`；`setup()`、`clear()` 做上下文的复用清理，`snapshot_flow(Flow*)` 保存流快照。三个枚举：`using Callback = void(*)(IpsContext*)`、`enum State { IDLE, BUSY, SUSPENDED }`、`enum ActiveRules { NONE, NON_CONTENT, CONTENT }`。公开字段按族归纳：包与配置指针 `packet`、`wire_packet`、`encode_packet`、`pkth`、`buf`、`conf`；匹配相关 `searches`（`MpseBatch`）、`stash`（`MpseStash*`）、`otnx`（`OtnxMatchData*`）、`regex_req_it`、`equeue`（`SF_EVENTQ*`）、`matched_buffers`；文件与备用缓冲 `file_data`、`file_data_id`、`file_data_drop_sse`、`file_data_no_sse`、`alt_data`、`file_pos`、`file_type_process`；计数与状态 `context_num`、`packet_number`、`active_rules`、`state`、`check_tags`、`clear_inspectors`；替换列表 `rpl`（`vector<Replacement>`，`Replacement` 为 `std::string data` 与 `unsigned offset` 两字段）。私有段 `flow`（`FlowSnapshot`，两字段 `uint32_t session_flags` 与 `SnortProtocolId proto_id`）、`data`（`vector<IpsContextData*>`）、`ids_in_use`、`post_callbacks`、`depends_on`、`next_to_process`、`remove_gadget`；`link()`/`unlink()`/`abort()` 用 `depends_on` 与 `next_to_process` 组织挂起上下文链，`post_detection()` 触发 `post_callbacks`。两个静态常量 `buf_size = Codec::PKT_MAX` 与 `max_ips_id = 8`（注释「Only 5 inspectors currently use the ips context data」）。`IpsContextData`、`MpseStash`、`SF_EVENTQ`、`RegexRequest`、`MpseBatch` 属于**不透明句柄，内部布局见 `src/detection/ips_context_data.cc`、`src/framework/mpse_batch.cc`、`src/events/`，不可依赖**。

**Cursor 的定位语义**。`src/framework/cursor.h` 的 `class SO_PUBLIC Cursor` 注释「Cursor provides access to the current buffer pointer used by IpsOptions during signature evaluation.」十个私有字段全靠方法读写：`buf_size`、`current_pos`、`delta`（注释 loop offset）、`file_pos`（注释 file pos）、`buf`、`name`（注释举例 rule option name 如 `pkt_data`、`http_uri`）、`data`（`CursorDataVec*`，即 `std::vector<CursorData*>`）、`extensible`（注释「if the buffer could have more data in a continuation」）、`buf_id`（注释 source buffer ID）、`is_accumulated`、`re_eval`。四个 `set()` 重载分别接受 `(name, buf, n, ext)`、`(name, buf, n, pos_file, ext)`、`(name, id, buf, n, ext)`、`(name, id, buf, n, pos_file, ext)`，共同把 `current_pos`、`delta` 归零并按 `ext and n > 0` 计算 `extensible`。读取侧 `buffer()`、`size()`、`endo()`（注释「the NEXT octect after last in buffer (this pointer is out of bounds)」）、`start()`（`buf + current_pos`）、`length()`（`buf_size - current_pos`）、`get_pos()`、`get_delta()`；推进侧 `add_pos(unsigned)`、`set_pos(unsigned)`（同时把 `re_eval` 置 false）、`set_pos_file(unsigned)`、`set_delta(unsigned)`；`awaiting_data()` 两重载判 `extensible and current_pos >= buf_size`；`get_next_pos()` 在 `current_pos >= buf_size` 前提下返回 `current_pos - buf_size`。析构会遍历 `*data` 删除 `CursorData*` 再 `delete data`。`class CursorData` 私有段 `static unsigned cursor_data_id` 与 `unsigned id`，公开 `clone()` 纯虚、`get_id()`、`create_cursor_data_id()`。赋值 `operator=` 被 `= delete`，拷贝构造存在。`Cursor` 与 `IpsOption::eval(Cursor&, Packet*)` 直接对接，`CursorActionType` 的 `CAT_*` 决定是否切换缓冲（字段见 05-04），机制见「原理见 06-08」。

**IpsAction / ActionApi / ActiveAction**。`src/framework/ips_action.h` 的 `class SO_PUBLIC IpsAction` 注释「IpsAction provides custom rule actions that are executed when a detection event is generated regardless of whether the event is logged」，`using Type = uint8_t`；`enum IpsActionPriority : uint16_t` 给出 `IAP_OTHER = 1`、`IAP_LOG = 10`、`IAP_ALERT = 20`、`IAP_REWRITE = 30`、`IAP_DROP = 40`、`IAP_BLOCK = 50`、`IAP_REJECT = 60`、`IAP_PASS = 70`、`IAP_MAX = IAP_PASS`，数值间隔 10 是刻意为后续动作留位。私有段只有 `const char* name` 与 `ActiveAction* active_action`；纯虚 `exec(Packet*, const ActInfo&)`，虚 `drops_traffic()` 默认 false，静态 `get_string()`、`get_type()`、`get_max_types()`、`is_valid_action()`、`get_default_priorities(bool)`，实例方法 `log_it()`、`get_file_id()`、`pass()`、`log()`、`alert()`。`struct ActionApi` 字段为 `BaseApi base`、`IpsAction::IpsActionPriority priority`、四个 `IpsActFunc`（`pinit`、`pterm`、`tinit`、`tterm`）、`ActNewFunc ctor`、`ActDelFunc dtor`；`#define ACTAPI_VERSION ((BASE_API_VERSION << 16) | 3)`；`register_action_pegs(const char*, const PegInfo*)` 用于把动作统计聚合到 `ips_actions`。`src/packet_io/active_action.h` 的 `class SO_PUBLIC ActiveAction` 注释「These are injection actions ... queued into the packet at inspection / detection time and executed at the end by Analyzer」，保护段仅 `ActionPriority action`，`enum ActionPriority { AP_LOCAL, AP_MODIFY, AP_PROXY, AP_RESET, AP_REMOTE, AP_MAX }`，构造 `ActiveAction(ActionPriority a = ActionPriority::AP_MAX)`，虚 `delayed_exec(Packet*)`，`get_action()`。`ActInfo`、`ActiveAction` 的派生实现属于**不透明句柄，内部布局见 `src/actions/act_*.cc` 与 `src/packet_io/active.cc`，不可依赖**。动作优先级如何决定 alert / drop / pass 的先后、verdict 如何写回，属于「原理见 06-09」「原理见 06-12」。

**检测缓冲与分段枚举**。`src/detection/detection_buf.h` 定义 `#define DECODE_BLEN 65535`，`struct DataPointer { const uint8_t* data; unsigned len; }`（构造 `DataPointer(const uint8_t*, unsigned)`），`struct DataBuffer { static constexpr unsigned decode_blen = DECODE_BLEN; uint8_t* const data = nullptr; unsigned len = 0; ... }`（拷贝删除、析构 `delete [] data`、`allocate_data()` 分配 `DECODE_BLEN`），`struct MatchedBuffer { const char* const name = nullptr; const uint8_t* const data = nullptr; unsigned size = 0; }`（构造三参、默认构造删除）。`src/framework/pdu_section.h` 定义 `enum PduSection { PS_NONE = 0, PS_HEADER, PS_HEADER_BODY, PS_BODY, PS_TRAILER, PS_MAX = PS_TRAILER, PS_ERROR }` 与 `using section_flags = uint16_t`、`inline section_flags section_to_flag(PduSection) { return 1<<sect; }`；注释说明 `PS_HEADER_BODY` 为「能同时作用于 header 和 body 的选项」，`PS_ERROR` 表示非法分段组合，且「When updating this enum, also update section_to_str」。`src/detection/fp_detect.h` 的 `struct MatchInfo` 四字段与 `struct OtnxMatchData` 两字段已在表中列出，配 `fpAddMatch()`、`fp_set_context()`、`fp_clear_context()`、`fp_full()`、`fp_partial()`、`fp_complete()`、`fp_eval_service_group()`、`fpLogEvent()`、`fp_eval_rtn()`、`fp_eval_option()` 等入口；`extern THREAD_LOCAL ProfileStats mpsePerfStats`、`rulePerfStats`。`src/detection/rule_option_types.h` 的 `option_type_t` 与 `src/framework/ips_option.h` 的 `EvalStatus`、`CursorActionType` 已在 05-04 给出，本篇只在 `Cursor` 与 `IpsOption::eval()` 的语境里引用，不重列。

### 4. 典型示例

下面这段 C++ 片段演示如何只读核对 `Cursor`、`IpsContext` 与 `IpsAction` 的字段取值，不触发检测或动作执行流程，便于在调试构建里确认字段与头文件一致。

```cpp
#include "framework/cursor.h"
#include "detection/ips_context.h"
#include "framework/ips_action.h"
#include <cstdio>

void dump_detect_fields(const Cursor& c, const snort::IpsContext& ctx,
    const snort::IpsAction& act)
{
    std::printf("cursor=%s size=%u pos=%u len=%u\n",
        c.get_name(), c.size(), c.get_pos(), c.length());
    std::printf("awaiting=%d re_eval=%d delta=%u\n",
        static_cast<int>(c.awaiting_data()),
        static_cast<int>(c.is_re_eval()), c.get_delta());
    std::printf("ctx.state=%d active_rules=%d context_num=%llu\n",
        static_cast<int>(ctx.state), static_cast<int>(ctx.active_rules),
        static_cast<unsigned long long>(ctx.context_num));
    std::printf("action=%s drops=%d\n",
        act.get_name(), static_cast<int>(act.drops_traffic()));
}
```

在一个把该函数接到选项求值前、传入已 `set()` 的 `Cursor` 与已绑定上下文的调试桩里，输出类似如下。示例输出，具体格式需对照实际版本核验。

```text
cursor=pkt_data size=40 pos=0 len=40
awaiting=0 re_eval=0 delta=0
ctx.state=1 active_rules=2 context_num=7
action=alert drops=0
```

逐行判读如下，合计超过 150 字。第一行 `cursor=pkt_data` 是 `Cursor::name`，代表默认包载荷缓冲；`size=40` 是 `buf_size`，`pos=0` 是 `current_pos`，`len=40` 由 `buf_size - current_pos` 得出，三者满足 `size = pos + len`。若读到 `len` 大于 `size`，说明 `current_pos` 被越界写坏，应回查 `add_pos()` / `set_pos()` 的调用，而不是怀疑 `length()` 的实现。第二行 `awaiting=0` 表示 `extensible` 为 false 或 `current_pos` 未到缓冲尾，本例 `pos=0` 且 `size=40`，自然不等待续接；`re_eval=0` 是 `re_eval` 初值，`set_pos()` 会把它清零；`delta=0` 是循环偏移初值。要注意 `awaiting_data()` 在续接场景下为 true 时，选项应返回重求值而非直接判不匹配，这属于「原理见 06-08」，本篇只解释字段。第三行 `ctx.state=1` 对应 `enum State { IDLE=0, BUSY=1, SUSPENDED=2 }`，本例上下文正忙；`active_rules=2` 对应 `enum ActiveRules { NONE=0, NON_CONTENT=1, CONTENT=2 }`，表示启用含 content 的规则集；`context_num=7` 是 `uint64_t` 上下文序号，也是 `PmdLastCheck`（字段见 05-06）用来判断「同一上下文内是否已检查过」的依据。第四行 `action=alert` 来自 `IpsAction::name`，`drops=0` 是 `drops_traffic()` 默认 false；`alert` 不丢弃流量，而 `drop` / `block` 一类动作会返回 true，但真正是否丢弃取决于内联模式与 DAQ verdict（`原理见 06-12`），不能仅凭该字段下结论。以上判读只覆盖字段取值，字段定义见本节，检测 eval 与动作执行链路见「原理见 06-08 ｜ 原理见 06-09」，规则关键字与动作参数见「参数见 04-06」，目录职责见「模块见 07-05 ｜ 模块见 07-01」，`Packet` 与 `SnortConfig` 侧字段见「字段见 05-02 ｜ 字段见 05-03」。

### 6. 版本差异

代际差异的核心是「状态从全局散落变成按包上下文」。Snort 2 用大量全局与线程变量承载检测状态；Snort 3 是从 Snort 2 重写的 C++ 实现，把单包状态收进 `IpsContext`（`src/detection/ips_context.h`），把缓冲定位收进 `Cursor`（`src/framework/cursor.h`），把动作抽成 `IpsAction` 插件（`src/framework/ips_action.h`），`DetectionEngine` 退化为几乎无字段的静态门面。配置改为 Lua，插件 ABI 不通用，`tools/snort2lua/` 只转配置格式；规则关键字与 Snort 2 有差异、不宣称完全兼容，`eval(Cursor&, Packet*)` 的接口形态与旧版检测插件不同，需对照实际版本核验。因此「在 `DetectionEngine` 里找每包状态」「按旧版全局变量名找检测标志」在 3.x 都不成立。

上游 master 快照（2026-11 抓取）内部的演进痕迹清晰可辨。`src/detection/detection_engine.h` 的 `get_alt_buffer()`、`acquire_alt_buffer()`、`reset_alt_buffer()` 三个内联函数直接操作 `p->context->alt_data`，注释「cppcheck 2.21 misses Analyzer's inline-helper call」是后期为静态分析补的抑制；`src/detection/ips_context.h` 的 `max_ips_id = 8` 带注释「FIXIT-L eliminate max_ips_id and just resize data vector. Only 5 inspectors currently use the ips context data.」，说明槽位上限是过渡设计；`ids_in_use` 标「FIXIT-P evaluate alternatives」；`src/framework/cursor.h` 的四个 `set()` 重载与 `re_eval`、`is_accumulated` 字段是续接与累积缓冲需求加入后逐步扩充的；`src/framework/pdu_section.h` 注释「When updating this enum, also update section_to_str」提示 `PduSection` 曾增删；`src/framework/ips_action.h` 的 `IpsActionPriority` 以 10 为间隔留位，`ACTAPI_VERSION ((BASE_API_VERSION << 16) | 3)` 与 `INSAPI_VERSION`、`IPSAPI_VERSION` 不同步；`src/framework/base_api.h` 的 `BASE_API_VERSION 29` 是所有派生版本的基数。这些都说明字段集合、枚举数值、槽位上限与 API 版本会继续变化，任何依赖 `sizeof(IpsContext)`、枚举数值、`max_ips_id` 或「`Cursor` 私有字段顺序」的结论都必须标注「需对照实际版本核验」。具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，本套资料不写绝对版本号。

能力边界对字段的影响：内联 IPS 的 drop / block 通过 DAQ verdict 反馈，`IpsAction::drops_traffic()`、`ActiveAction::action` 只是动作侧字段，IDS 旁路模式下只告警不丢弃，Snort 本身不是防火墙、不做 IP 转发；加密载荷不可见，`Cursor::buf` 与 `IpsContext::file_data` 指向解码或检查器提供的可见缓冲，不含 HTTPS 明文正文，应用识别依赖 inspector / binder / wizard（`原理见 06-04`）；Hyperscan 是可选加速，`MpseBatch searches`、`MpseStash* stash` 不表示 Hyperscan 必需，缺失时回退 `src/search_engines/` 其他实现（`原理见 06-07`）；线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」，`IpsContext::state` 的 `SUSPENDED`、`offload_enabled`、`post_callbacks` 的并发语义需对照实际版本核验。许可按 GPLv2 处理，Talos 规则集另有独立许可约束（`lua/talos.lua`）。

### 7. 常见误用与调试

第一类误用是在 `DetectionEngine` 或 `detect.h` 里找字段。前者只有 `offload_enabled` 与 `context` 两个成员，后者一个结构体都没有；检测状态应去 `IpsContext`，输出函数声明留在 `detect.h`。第 4 节的 `grep -c "struct " src/detection/detect.h` 返回 0 是最直接的证据，遇到「检测引擎结构体字段表」这类需求应先做这个核验，避免产出空表或臆造字段。第二类误用是直接读 `Cursor` 的私有字段：`buf_size`、`current_pos`、`delta`、`buf`、`name` 等全是 `private`，只应通过 `size()`、`get_pos()`、`buffer()`、`get_name()`、`awaiting_data()` 访问；用 `reinterpret_cast` 或偏移读私有成员会在字段顺序调整后静默错位。

第三类误用是把动作字段当成实际丢包结论。`drops_traffic()` 默认 false，只有部分动作覆盖为 true；即便返回 true，是否真正丢弃还取决于内联模式与 DAQ verdict（`原理见 06-12`），`IpsActionPriority` 的 `IAP_DROP=40`、`IAP_BLOCK=50`、`IAP_REJECT=60`、`IAP_PASS=70` 只是优先级数值，不等于生效顺序，顺序由动作注册表决定（`原理见 06-09`）。第四类是把不透明句柄当结构展开：`IpsContextData`、`MpseBatch`、`MpseStash`、`SF_EVENTQ`、`RegexRequest`、`ActInfo`、`ActiveAction` 派生类、`ProfileStats` 在本篇头文件里只有前向声明，属于**不透明句柄，内部布局见 `src/detection/`、`src/framework/mpse_batch.cc`、`src/events/`、`src/actions/`，不可依赖**；应改用 `set_data()`/`get_data()`、`get_active_action()` 等公开入口。

第五类是忽视续接与分段语义。`Cursor::extensible`、`awaiting_data()`、`re_eval`、`is_accumulated` 与 `PduSection` 的 `PS_HEADER_BODY`、`PS_ERROR` 共同决定选项在 PDU 分段下的行为；把 `awaiting_data()` 为 true 的情形直接判 `NO_MATCH`，或把 `PS_ERROR` 当普通分段处理，都会造成漏报。这些字段的取值解释见本节，求值链路一律「原理见 06-08」。第六类是硬编码常量：`DECODE_BLEN 65535`、`max_ips_id = 8`、`MAX_EVENT_MATCH 100`、`MAX_NUM_RULE_TYPES 16`、`buf_size = Codec::PKT_MAX` 都可能随版本调整，`IpsActionPriority` 的数值间隔也只是当前约定；外部工具不要把它们写死。调试时先用 `snort -T` 验证配置与规则（完整参数见 04-07），再用第 4 节的只读打印确认 `Cursor` 与 `IpsContext` 字段值；若字段读数与源码声明长期不一致，优先核对二进制与头文件是否来自同一快照，需对照实际版本核验。所有涉及吞吐、pps、内存占用的结论一律标注「需在目标机型实测」，不给绝对值；基准方法见 08-01，检测侧调优见 08-02，无告警与吞吐类故障案例见 08-04。
