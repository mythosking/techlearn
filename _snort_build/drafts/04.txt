# Snort 3 技术资料 · 04 参数与 API 手册

## 04-01 CMake 构建选项全集

### 1. 本篇定位与覆盖范围

本篇是 04 册「参数与 API 手册」的开篇，也是全集里「构建期参数」的唯一权威源。04 册整体承担 CMake 构建选项、`snort.lua` 全部段、DAQ 与 inspector 参数、规则关键字、命令行与 Lua 配置 API、shell 控制以及返回码的字典式收录；其余各册只给本场景最小必要配置并写「完整参数见 04-xx」，不得重列全集。本篇聚焦第一族参数：把源码从仓库变成可执行 `snort` 之前，所有能影响编译结果的开关。覆盖的真实文件包括顶层 `CMakeLists.txt`、`cmake/create_options.cmake`、`cmake/configure_options.cmake`、`cmake/include_libraries.cmake`、`cmake/sanity_checks.cmake`、`cmake/platforms.cmake`、`config.cmake.h.in` 与 `configure_cmake.sh`。事实基准统一写「上游 master 快照（2026-11 抓取）」；`CMakeLists.txt` 与 `ChangeLog.md` 中的版本字样只作核验依据，具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，需对照实际版本核验，本套资料不抄具体版本号进正文。

必须先划清边界。本篇只列每个参数的「名称 / 取值 / 默认值 / 作用 / 误配后果」，不解释 CMake 的依赖解析算法，不展开 `SnortConfig` 或任何结构体字段，不讲述编译产物如何被装载进流水线。这些内容分别归口到「字段见 05-03 ｜ 原理见 06-01 ｜ 模块见 07-12」。构建选项与运行时 Lua 配置是两套独立体系：前者决定二进制里编进了哪些能力，后者决定这些能力在运行时如何被启用；把二者混为一谈、以为在 `snort.lua` 里写一句就能补回一个没编进去的插件，是新手最典型的误配来源。还要守住能力边界：Snort 3 是相对 Snort 2 重写的全新 C++ 实现，配置改为 Lua（`lua/snort.lua`、`lua/snort_defaults.lua`），不兼容 Snort 2 的 `snort.conf` 与插件 ABI，`tools/snort2lua/` 只是格式转换辅助工具；抓包依赖独立 libdaq / DAQ3，构建期的 `find_package(DAQ REQUIRED)` 只负责找到适配层依赖，不等于 Snort 自带抓包；Hyperscan 是可选 search_engine 加速，`find_package(HS QUIET 4.4.0)` 失败时回退 `src/search_engines/` 下其他多模式匹配实现，不是必需依赖。

本篇参数分八族：静态/动态链接开关、功能特性、文档生成、安全加固、调试与性能分析、fuzz 与覆盖率、信号与构建变量、依赖探测与编译期宏。第 2 节给全集索引表，第 3 节按族逐项详解，第 4 节给一条完整可复现的配置命令与输出判读，第 5 节给按场景速查，第 6 节讲代际与版本差异，第 7 节汇总误用与调试。全部取值与默认值均对照 `cmake/create_options.cmake`、`configure_cmake.sh`、`cmake/include_libraries.cmake`、`config.cmake.h.in` 逐条核验；凡脚本里出现但 `option()` 未声明、或由 `Find*.cmake` 间接产生的变量，一律标注「需对照实际版本核验」并给出可定位目录。

### 3. 逐项详解

以下逐项给出「名称 / 取值 / 默认值 / 作用 / 误配后果」，源码位置统一相对 `upstream_src/snort3/`，主要落在 `cmake/create_options.cmake` 与 `cmake/configure_options.cmake`。凡涉及生成逻辑的结论只描述「参数控制什么」，机制本身写「原理见 06-01」。

**STATIC_CODECS**：名称 `STATIC_CODECS`；取值 `ON`/`OFF`；默认值 `ON`；作用是把 `src/codecs/` 下的解码器直接编进主二进制，`config.cmake.h.in` 第 47 行对应 `STATIC_CODECS` 宏。误配后果：置 `OFF` 后若部署时未同步提供对应插件库，解码阶段找不到 codec，启动时报模块未加载、包无法分层；生产构建建议保持默认。关联 `--disable-static-codecs`（`configure_cmake.sh` 第 266 行）。

**STATIC_INSPECTORS**：默认值 `ON`；作用是 `src/network_inspectors/`、`src/service_inspectors/` 静态编入。误配后果：置 `OFF` 而未部署动态 inspector，`binder` 绑定到 `http_inspect`、`ssl` 等类型时解析失败，`snort -T` 阶段即报错；若做插件外置实验，必须同时准备 `--plugin-path`。

**STATIC_LOGGERS**：默认值 `ON`；作用是把 `src/loggers/` 的 `alert_json`、`alert_fast`、`unified2` 等编入。误配后果：置 `OFF` 后 `-A` 指定的告警模式可能找不到实现，运行期无告警输出但不报错，排查时容易误判成「规则没命中」。

**STATIC_IPS_ACTIONS**：默认值 `ON`；作用是 `src/actions/` 的 `alert`、`drop`、`block`、`reject` 等动作编入。误配后果：置 `OFF` 且动态动作库缺失时，内联模式 `-Q` 下 `drop` 无法形成 DAQ verdict，表现为「规则命中却不丢弃」，与防火墙行为混淆。

**STATIC_IPS_OPTIONS**：默认值 `ON`；作用是 `src/ips_options/` 的 `content`、`pcre`、`byte_test` 等规则关键字编入。误配后果：置 `OFF` 后规则加载报未知关键字，属最常见的「插件没编进去却怪规则写错」误配。

**STATIC_SEARCH_ENGINES**：默认值 `ON`；作用是把 `src/search_engines/` 的多模式匹配实现编入。误配后果：置 `OFF` 且无动态库时 fast pattern 无法构建；注意 Hyperscan 仅是本族里的一种可选加速，缺失时回退 AC / BNFA 实现，不得写成必需依赖。

**STATIC_TRACERS**：默认值 `ON`；作用是 packet tracer 等编入。误配后果：置 `OFF` 后 `--trace` 相关诊断能力不可用，排障时少一路证据，但不会影响正常检测。

**ENABLE_STATIC_DAQ**：默认值 `ON`；作用是静态链接 DAQ modules，`CMakeLists.txt` 第 118 行据此打印 `DAQ Modules: Static`。误配后果：置 `OFF` 改为动态加载时，须保证 `--daq-dir` 指向的目录里确有 module；否则 `--daq-list` 只列静态模块，在线抓包起不来。抓包能力由 DAQ module 决定，需对照实际版本核验具体 module 名。

**ENABLE_SHELL**：默认值 `OFF`；作用是编入 `src/main/shell.cc` 的交互式命令 shell，`config.cmake.h.in` 生成 `SHELL` 宏。误配后果：置 `ON` 而运行时未配 `--shell` 或无控制通道，不会自动开启交互；反之若想用 `snort_cmds` 里的 `pause`、`reload_config`、`dump_stats` 等命令却没编 `SHELL`，命令集根本不存在。

**ENABLE_UNIT_TESTS**：默认值 `OFF`；作用是 `CMakeLists.txt` 第 58 行 `include(CTest)`、第 63 行 `check` 目标，并触发 `find_package(CppUTest REQUIRED)`。误配后果：置 `ON` 但系统缺 CppUTest 时配置直接失败；`configure_options.cmake` 第 27 行还会在单测开启时强制把 `ALLOWLIST_MOVE_ON_EXCESS` 置 `ON`，属于隐式联动，调试构建与生产构建行为会不同。

**ENABLE_BENCHMARK_TESTS**：默认值 `OFF`；作用与单测类似，追加 `BENCHMARK_TEST` 与 `CATCH_CONFIG_ENABLE_BENCHMARKING` 定义。误配后果：与 `check` 目标共用，基准构建带调试与插桩开销，不可用作生产基准，吞吐结论一律标注「需在目标机型实测」。

**DISABLE_TENANT_ID**：默认值 `OFF`；作用是从 `FlowKey` 结构中去掉 tenant ID，`config.cmake.h.in` 生成 `DISABLE_TENANT_ID`。误配后果：置 `ON` 后多租户相关绑定条件失效，`binder.when.tenants` 语义变化；字段名与结构归「字段见 05-02」，此处不展开。

**ALLOWLIST_MOVE_ON_EXCESS**：默认值 `OFF`；作用是编译期门控 `stream.allowlist_cache.move_on_excess`，`config.cmake.h.in` 第 85 行有专门注释，REG_TEST 构建还会强制定义。误配后果：默认关闭是有性能考量的，盲目置 `ON` 会改变流表在内存压力下的行为；与 DAQ WHITELIST verdict 能力相关，须「需对照实际版本核验」。

**ENABLE_COREFILES**：默认值 `ON`；注意语义是「允许生成 core 文件」，`configure_options.cmake` 第 14 行在它为 `OFF` 时才置 `NOCOREFILE`。误配后果：生产环境希望崩溃时留 core 却误用 `--disable-corefiles`，反而关掉 core；参数名带反直觉取反，务必按帮助文本核对。

**ENABLE_LARGE_PCAP**：默认值 `OFF`；作用是开启 `_LARGEFILE_SOURCE` 与 `_FILE_OFFSET_BITS=64`，支持大于 2 GB 的 pcap。误配后果：离线回放超大 pcap 却未开此项，读取会截断或失败；对在线抓包无影响。

**ENABLE_STDLOG**：默认值 `OFF`；作用是用文件描述符 3 代替 stdout 输出告警。误配后果：置 `ON` 后若进程未把 fd 3 重定向到日志文件，告警会「凭空消失」；与 `-M`、日志目录配置要一起规划。

**ENABLE_TSC_CLOCK**：默认值 `OFF`；作用是用 TSC 寄存器做时钟，仅 x86 与 arm 有效。误配后果：在不稳定 TSC 的虚拟机上开启会造成时间戳漂移，影响事件排序；跨机型结论一律「需在目标机型实测」。

**ENABLE_CRASH_MITIGATOR**：默认值 `OFF`；作用是 `configure_options.cmake` 第 59 行检查 `-fnon-call-exceptions` 支持后置 `CRASH_MITIGATOR`，并追加编译标志。误配后果：编译器不支持该标志时直接 `SEND_ERROR` 中断配置；属于实验特性，生产构建不建议启用。

**ENABLE_FUZZERS**：默认值 `OFF`；作用是生成 `fuzz` 自定义目标。误配后果：`configure_options.cmake` 第 212 行明确要求 `ENABLE_FUZZERS` 必须同时提供 `LIB_FUZZING_ENGINE` 或 `ENABLE_FUZZ_SANITIZER`，否则 `FATAL_ERROR`；只开这一项必然配置失败。

**ENABLE_FUZZ_SANITIZER**：默认值 `OFF`；作用是加 `-fsanitize=fuzzer` 并做 `try_compile` 探测。误配后果：与 ASan/TSan 同属 sanitizer 族，混用时先后覆盖 `SANITIZER_*_FLAGS`，需按第 143 行注释「ASAN 与 TSAN 互斥」的约定逐一确认。

**LIB_FUZZING_ENGINE**：取值是文件路径（`CACHE FILEPATH`）；默认值空字符串；作用是指定外部 fuzzing engine 静态库，入口 `--with-fuzzing-engine=FILE`。误配后果：路径不存在或库不兼容时链接期才报错，定位成本高于配置期，宜先 `ls` 确认。

**MAKE_HTML_DOC / MAKE_PDF_DOC / MAKE_TEXT_DOC / MAKE_DOC**：四个默认值均为 `ON`。作用是控制 `doc/` 子目录是否加入构建，`configure_options.cmake` 第 42 至 55 行在缺 Asciidoc、DBLATEX、W3M 时把对应项强制置 `OFF`。误配后果：CI 里未装文档工具链却保留 `--enable-docs`，表面配置成功但 `make` 时文档目标失败；纯运行时构建建议 `--disable-docs` 缩短依赖链。

**ENABLE_HARDENED_BUILD**：默认值 `OFF`；作用是逐个 `check_cxx_compiler_flag` 探测 `-Wdate-time`、`-D_FORTIFY_SOURCE=2`、`-fstack-protector-strong`、`-Wformat`、`-Werror=format-security` 与链接期 `-Wl,-z,relro`、`-Wl,-z,now`。误配后果：它只追加编译器支持的标志，不支持的自动跳过，不会报错；但把它当成「一定加固」会产生误判，实际生效项要看构建日志。

**ENABLE_PIE**：默认值 `OFF`；作用是探测 `-fPIE -pie` 后追加到编译与链接标志。误配后果：与某些静态链接或插件加载组合时可能冲突；是否启用应结合发行版安全基线，不在此给绝对值。

**ENABLE_SAFEC**：默认值 `ON`；作用是 `include_libraries.cmake` 第 24 行条件执行 `find_package(SafeC QUIET)`，命中则生成 `HAVE_SAFEC`。误配后果：注意它是 QUIET 探测，缺失时不报错、只是静默不使用 libsafec；`--disable-safec` 才真正关闭。此项默认 `ON` 与其余安全项默认 `OFF` 形成对比，容易记反。

**ENABLE_DEBUG_MSGS**：默认值 `OFF`；作用是把 `DEBUG_MSGS` 宏写进 `config.h`，开启内部调试打印。误配后果：输出量大、含内部符号，仅在提交 bug 报告或开发时用；调试构建的性能代价显著，不可作为生产基准。

**ENABLE_DEBUG**：默认值 `OFF`；作用是 `configure_options.cmake` 第 129 行追加 `-g -DDEBUG`，否则追加 `-DNDEBUG`。误配后果：与 `CMAKE_BUILD_TYPE` 的 NDEBUG 处理在第 128 行有 FIXIT 注释，两套机制可能叠加；断言行为变化会掩盖问题，定位时须确认最终 `CXXFLAGS`。

**ENABLE_GDB**：默认值 `ON`；作用是追加 `-g -ggdb`。误配后果：这项默认开，所以「发布版没带调试符号」往往不是没开 `ENABLE_GDB`，而是后续 `strip`；关闭它会让崩溃栈难以符号化。

**ENABLE_PROFILE**：默认值 `OFF`；作用是在 GNU C++ 下追加 `-pg`。误配后果：与 sanitizer、jemalloc 等同时开启会产生难以归因的性能数据；入口脚本写作 `--enable-gprof-profile`，映射到 `ENABLE_PROFILE`，名字不一致需留意。

**DISABLE_SNORT_PROFILER**：默认值 `OFF`；作用是 `configure_options.cmake` 第 21 行置 `NO_PROFILER`。误配后果：`configure_cmake.sh` 第 293 行把 `--disable-snort-profiler` 映射为 `DISABLE_SNORT_PROFILER BOOL false`，字面与实际取值相反，属源码里真实存在的反直觉点，需对照实际版本核验；不要凭参数名推断开关方向。

**ENABLE_DEEP_PROFILING / ENABLE_MEMORY_PROFILER / ENABLE_RULE_PROFILER**：三者默认 `OFF`；分别对应 `DEEP_PROFILING`、`ENABLE_MEMORY_PROFILER`、`ENABLE_RULE_PROFILER` 宏，用于多级函数剖析、内存剖析与规则关键字剖析。误配后果：叠加开启会显著放大运行开销，只适合离线分析；任何吞吐、内存占用结论标注「需在目标机型实测」。

**ENABLE_ADDRESS_SANITIZER / ENABLE_THREAD_SANITIZER / ENABLE_UB_SANITIZER**：三者默认 `OFF`；分别加 `-fsanitize=address`、`-fsanitize=thread`、`-fsanitize=undefined -fno-sanitize=alignment` 并做 `check_cxx_compiler_flag`，不支持即 `SEND_ERROR`。误配后果：注释明确 ASan 与 TSan 互斥、必须绝对先设 `SANITIZER_*_FLAGS`；`configure_options.cmake` 第 230 行还禁止 TCMalloc 与 ASan 同开、第 239 行禁止 JEMalloc 与 ASan 同开，违反即 `SEND_ERROR`。

**ENABLE_TCMALLOC / ENABLE_JEMALLOC**：两者默认 `OFF`；分别 `find_package(TCMalloc / JEMalloc REQUIRED)` 并追加 `-fno-builtin-malloc` 等标志。误配后果：`configure_cmake.sh` 第 584 行强制二者互斥，同时 `--enable` 会 `exit 2`；jemalloc 还派生 `STATIC_JEMALLOC`、`HAVE_CISCO_SHIM` 等变量，具体取值需对照实际版本核验。

**ENABLE_CODE_COVERAGE / ENABLE_FUZZ_COVERAGE**：默认 `OFF`；前者 `include(CodeCoverage.cmake)`，后者加 `-fprofile-instr-generate -fcoverage-mapping`。误配后果：覆盖率插桩改变二进制体积与运行特征，只能用于测试构建。

**SIGNAL_SNORT_RELOAD / SIGNAL_SNORT_DUMP_STATS / SIGNAL_SNORT_ROTATE_STATS / SIGNAL_SNORT_READ_ATTR_TBL**：取值是信号名或整数（`CACHE STRING`）；默认值依次 `SIGHUP`、`SIGUSR1`、`SIGUSR2`、`SIGURG`；作用分别写进 `config.cmake.h.in` 的四个 `SIGNAL_SNORT_*` 宏。误配后果：自定义成已被宿主进程占用的信号会与外部管理脚本冲突；填非整数又非合法信号名时，帮助文本明确要求「must be a valid integer or signal name」。

**构建变量族**：`CMAKE_INSTALL_PREFIX` 在 `configure_cmake.sh` 默认 `/usr/local/snort`，`--prefix=` 可改；`CMAKE_BUILD_TYPE` 在既未设 `CFLAGS` 也未设 `CXXFLAGS` 时默认 `RelWithDebInfo`，`--build-type=` 只接受 `Debug | Release | RelWithDebInfo | MinSizeRel` 四种，其他值直接退出；`--builddir=` 默认 `build`，`--generator=` 传给 `cmake -G`，`--define=` 可透传任意 `-D`。误配后果：设了 `CFLAGS/CXXFLAGS` 却没显式给 `--build-type`，`CMAKE_BUILD_TYPE` 会是空串，编译优化级别与预期不符；`SNORT_BUILD_NUMBER=<int>` 映射到 `VERSION_BUILD`，只影响构建标识，不影响功能。

关于依赖与宏的归口：`config.cmake.h.in` 里还有 `HAVE_DUMBNET_H`、`HAVE_MALLOC_TRIM`、`HAVE_MEMRCHR`、`HAVE_SIGACTION`、`HAVE_GNU_STRERROR_R`、`HAVE_BASENAME_R`、`HAVE_VISIBILITY`、`USE_THREAD_LOCAL`、`WORDS_BIGENDIAN`、`SIZEOF_LONG_INT` 等由 `sanity_checks.cmake` 探测产生的宏，它们不是用户可直接设的构建选项，而是平台适配结果，字段名与平台处理写「模块见 07-13 ｜ 原理见 06-13」，本篇不逐条展开；具体清单需对照 `config.cmake.h.in` 与 `cmake/sanity_checks.cmake` 核验。

### 4. 典型示例

下列命令演示一次「调试带单测」的完整构建配置：前置确认脚本存在与 cmake 可用，再用 `configure_cmake.sh` 传入选项，最后用生成的 `config.status` 复核。这是配置阶段，不执行 `make install`，避免污染环境。

```bash
cd upstream_src/snort3/snort3-master
test -x ./configure_cmake.sh && cmake --version | head -1
./configure_cmake.sh --prefix=/opt/snort3-dbg \
    --build-type=Debug --enable-unit-tests \
    --enable-debug-msgs --disable-static-daq
grep -E "ENABLE_UNIT_TESTS|ENABLE_DEBUG_MSGS|ENABLE_STATIC_DAQ" \
    build/CMakeCache.txt
cat build/config.status
```

配置成功后 `CMakeLists.txt` 第 94 至 238 行的 `message()` 段会打印一份特性摘要。下面给出示例输出，示例输出，具体格式需对照实际版本核验。

```text
-------------------------------------------------------
snort version 3.x.x
Install options:
    prefix:     /opt/snort3-dbg
    includes:   /opt/snort3-dbg/include/snort
    plugins:    /opt/snort3-dbg/lib/snort

Feature options:
    DAQ Modules:    Dynamic
    Hyperscan:      OFF
    ICONV:          ON
    Libunwind:      OFF
    LZMA:           ON
    RPC DB:         Built-in
    SafeC:          OFF
    TCMalloc:       OFF
    JEMalloc:       OFF
    UUID:           ON
    NUMA:           OFF
    LibML:          OFF
    Brotli:         ON
    CrashMitigator: OFF
-------------------------------------------------------
```

逐行判读如下，合计超过 150 字。第一行分隔线与 `snort version` 行是 `CMakeLists.txt` 汇总信息的起头；版本字样只是核验依据，本套资料不把它当版本号抄用，具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，需对照实际版本核验。`prefix` 行为 `/opt/snort3-dbg`，说明 `--prefix=` 已正确写入 `CMAKE_INSTALL_PREFIX`；若这里仍是 `/usr/local/snort`，多半是复用了旧 `build/` 目录且 `CMakeCache.txt` 未清理，脚本第 589 行本应删缓存，需人工确认。`includes` 与 `plugins` 两行给出头文件与插件落位，安装后要用它们核对 `snort_defaults.lua` 与动态插件路径。`DAQ Modules: Dynamic` 对应我们传入的 `--disable-static-daq`，即 `ENABLE_STATIC_DAQ=OFF`；此时必须另行准备 `--daq-dir`，否则在线抓包缺 module。`Hyperscan: OFF` 说明 `find_package(HS QUIET 4.4.0)` 未命中，这正是能力边界所述的可选加速缺失场景，引擎回退 `src/search_engines/` 下其他实现，不是构建错误。`ICONV: ON`、`LZMA: ON`、`UUID: ON`、`Brotli: ON` 均为可选库探测命中，各自对应一个 `HAVE_*` 宏；`Libunwind / NUMA / LibML / TCMalloc / JEMalloc / CrashMitigator` 为 `OFF`，表示未探测到或未启用。`SafeC: OFF` 值得注意：尽管 `ENABLE_SAFEC` 默认 `ON`，但本机未装 libsafec，QUIET 探测静默失败，因此摘要为 `OFF`；这不是我们传了 `--disable-safec`。`RPC DB: Built-in` 表示 `USE_TIRPC` 未置位，用内置实现。最后，`grep CMakeCache.txt` 与 `cat config.status` 是最可靠的复核手段：前者确认选项确实以 `BOOL` 落盘，后者保存了完整命令行，便于复现与归档。

再给一条生产 IDS 变体的最小配置，用于对照：只保留默认静态链接、显式关掉文档与调试插桩，避免把调试构建当生产基准。

```bash
cd upstream_src/snort3/snort3-master
rm -rf build_release
./configure_cmake.sh --builddir=build_release \
    --prefix=/opt/snort3 --build-type=Release \
    --disable-docs --disable-unit-tests
cmake --build build_release --target help | grep -E "snort|check|uninstall" | head -10
```

### 6. 版本差异

构建系统层面最根本的代际差异是：Snort 2 用 autotools 的 `configure` 与 `snort.conf`，Snort 3 改为 CMake 与 Lua 配置，二者选项名、默认策略、插件 ABI 都不通用，`tools/snort2lua/` 只转配置格式，不迁移构建脚本。本篇所有 `option()` 名称来自 `cmake/create_options.cmake`，`configure_cmake.sh` 的 `--enable-*` 只是到这些变量的映射层；因此「老脚本里的 `--enable-xxx` 直接照搬」是错误做法，应以 `./configure_cmake.sh --help` 与 `cmake -LAH` 的输出为准，需对照实际版本核验。

与上游 master 快照内部演进相关的差异同样要谨慎：`config.cmake.h.in` 第 88 至 92 行显示 `ALLOWLIST_MOVE_ON_EXCESS` 在 REG_TEST 构建下会被无条件补定义，第 101 行还有 `ENABLE_MEMORY_OVERLOADS` 这类仅见宏定义、未见 `option()` 声明的条目，属于版本演进中的过渡痕迹；`ChangeLog.md` 记录了选项增删，具体哪些选项在本快照可用，一律以 `cmake/create_options.cmake` 与 `cmake/configure_options.cmake` 为准，需对照实际版本核验。能力边界亦随版本保持：Hyperscan 始终是可选加速，DAQ 始终是独立依赖，许可始终按 GPLv2（顶层 `COPYING` / `LICENSE`）处理，Talos 规则集另有独立许可约束（`lua/talos.lua`），构建选项不会改变这些事实。线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」；`-z` 与 `--max-packet-threads` 的运行时语义归 04-07，本篇不展开。

跨版本迁移时建议做三件事：用 `config.status` 保存每次配置命令；用 `cmake -LAH build/` 导出全部缓存变量做 diff；在目标机型重新验证依赖探测结果，因为 `HAVE_*` 宏随机器上的库而变，不能把一台机器的摘要当通用结论。构建变体组合与产物形态见 02-02，单测与 Sanitizer 实战见 02-05，二者均「完整变量见 04-01」，不得重列全集。

### 7. 常见误用与调试

第一类误用是把构建选项与运行配置混用。典型现象是「在 `snort.lua` 里写了 `search_engine = 'hyperscan'` 但没提速」——根因往往是 `HAVE_HYPERSCAN` 未定义，构建期就没编进 Hyperscan，Lua 里再怎么写也补不回来。验证顺序应是先看 `CMakeLists.txt` 打印的 `Hyperscan: ON/OFF`，再查 `config.h` 里的 `#cmakedefine HAVE_HYPERSCAN 1`，最后才看 Lua 配置。缺失时按能力边界回退 AC / BNFA（`src/search_engines/`），不是错误。

第二类误用是默认方向记反。`ENABLE_COREFILES` 默认 `ON` 表示「允许 core」，脚本 `--disable-corefiles` 才关闭；`ENABLE_SAFEC` 默认 `ON` 但依赖 QUIET 探测，缺库静默 `OFF`；`ENABLE_GDB` 默认 `ON`；`DISABLE_SNORT_PROFILER` 在脚本里的映射与字面相反。这类参数一律以 `cmake/create_options.cmake` 的 `option()` 行和 `configure_cmake.sh --help` 为准，不靠名字猜。

第三类是互斥与隐式联动触发的 `SEND_ERROR` / `FATAL_ERROR`。`configure_options.cmake` 禁止 TCMalloc / JEMalloc 与 ASan 同开，禁止 ASan 与 TSan 混用，`ENABLE_FUZZERS` 必须配 `LIB_FUZZING_ENGINE` 或 `ENABLE_FUZZ_SANITIZER`，`configure_cmake.sh` 禁止 tcmalloc 与 jemalloc 同时 `--enable`，`ENABLE_UNIT_TESTS` 会强制把 `ALLOWLIST_MOVE_ON_EXCESS` 置 `ON`。遇到配置期报错，先读 `message` 文本定位到具体 `if()` 分支，再回查对应选项，比逐个试开关高效。

第四类是缓存污染。`configure_cmake.sh` 只在 `build/` 已存在且含 `CMakeCache.txt` 时删除旧缓存，若手工指定了 `--builddir=` 到别的目录，旧值会残留，表现为「明明传了 `--prefix=` 摘要里却还是旧路径」。稳妥做法是显式 `rm -rf <builddir>` 后再配置，并用 `grep` 复核 `CMakeCache.txt`。第五类是把调试构建当生产基准：`--enable-debug`、`--enable-debug-msgs`、各类 sanitizer 与覆盖率插桩都会改变运行特征，吞吐、pps、丢包率、内存占用一律标注「需在目标机型实测」，不给绝对值；基准方法见 08-01，调优见 08-02。第六类是忽略依赖探测的 REQUIRED 项：`Threads / DAQ / DNET / FlexLexer / HWLOC / LuaJIT / OpenSSL 1.1.1 / PCAP / PCRE2 / ZLIB` 缺一即配置失败，其中 DAQ 为独立 libdaq / DAQ3，不是 Snort 自带抓包；`--with-daq-includes=`、`--with-daq-libraries=` 可指定路径，具体 module 名需对照实际版本核验。排错时把这些按「字段见 05-03 ｜ 原理见 06-01 ｜ 模块见 07-12」分头查证，通常能快速收敛。

## 04-02 snort.lua 顶层配置参数全集

### 1. 本篇定位与覆盖范围

本篇是 04 册里「运行时 Lua 配置入口」的唯一权威源，收录 `lua/snort.lua` 与 `lua/snort_defaults.lua` 暴露的全部顶层段、网络变量、路径变量与 `default_*` 预置表，以及 `tweaks` 条件包含机制。04-01 管构建期「编进什么」，本篇管运行期「启用什么」，二者不可互相替代：一个段能否生效，前提是对应模块已按 04-01 编入二进制，且该段被 `snort.lua` 正确声明。事实基准统一为「上游 master 快照（2026-11 抓取）」；具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，需对照实际版本核验，本套不写绝对版本号。

边界同样明确。本篇只给每个段与变量的「名称 / 取值 / 默认值 / 作用 / 误配后果」，不解释 Lua 表如何被解析成 `SnortConfig`、不展开配置上下文结构体字段、不讲述模块装配流程；这些分别是「字段见 05-03 ｜ 原理见 06-01 ｜ 模块见 07-11」。Snort 3 用 Lua 配置，是相对 Snort 2 的全新实现，`lua/snort.lua` 开头注释即写明「there are over 200 modules available to tune your policy」，不兼容 `snort.conf` 与旧插件 ABI；`tools/snort2lua/` 只是格式转换辅助，不等于配置可直接沿用。抓包依赖独立 libdaq / DAQ3（`src/packet_io/sfdaq*.cc`），本篇出现的 `daq` 相关段只是把参数交给适配层，不表示 Snort 自带抓包；内联 IPS 的 drop / block 通过 DAQ verdict 反馈，Snort 本身不是防火墙、不做 IP 转发；加密流量载荷不可见，应用识别依赖 inspector / binder / wizard。

### 3. 逐项详解

以下按八段顺序逐项给「名称 / 取值 / 默认值 / 作用 / 误配后果」。段名与默认值均对照 `lua/snort.lua`、`lua/snort_defaults.lua` 核验；凡未在模板里显式展开、仅以注释形式给出的键，一律写「需对照实际版本核验」并给出可定位目录，不凭印象补键名。

**HOME_NET**：名称 `HOME_NET`；取值是 CIDR 地址列表、变量或字面量 `'any'`；默认值 `'any'`（`lua/snort.lua` 第 24 行）；作用是定义「被保护网络」，规则里的 `$HOME_NET` 与大量 `default_*` 服务器变量都基于它。误配后果：设成过窄网段会让本应命中的告警漏报，设成 `'any'` 虽省事但会把全部流量都当内网，方向判定与 `EXTERNAL_NET` 的相对关系失效；注释明确「must be set now」，必须在 `include` 之前赋值，否则 `snort_defaults.lua` 里 `DNS_SERVERS = HOME_NET` 之类引用会取到空值。

**EXTERNAL_NET**：默认值 `'any'`（第 28 行）；作用是定义外部网络，通常保持 `'any'`。误配后果：与 `HOME_NET` 写成同一网段会让 `$EXTERNAL_NET` 方向规则自相矛盾；注释写明「leave as any in most situations」，除非做非对称路由的精细策略，不要随意收窄。

**include**：取值是文件名字符串；默认 `'snort_defaults.lua'`（第 30 行）；作用是把预置默认表载入同一 Lua 环境。误配后果：路径写错或文件被移走，`snort -T` 会在加载阶段报「找不到包含文件」；`--include-path` 可影响搜索顺序，完整命令行见 04-07。注意 `include` 出现位置必须在 `HOME_NET`、`EXTERNAL_NET` 之后，因为默认表里大量变量依赖这两个值。

**stream 系列七个表**：`stream`、`stream_ip`、`stream_icmp`、`stream_tcp`、`stream_udp`、`stream_user`、`stream_file`，取值均为 Lua 表，默认都写 `{ }`（第 44 至 50 行），含义是「采用模块内部默认值」。误配后果：把 `{ }` 删掉等于不实例化该 inspector，`binder` 绑定 `stream_tcp` 相关服务时找不到实例；反过来在里面塞未核验的键会被 `--warn-conf-strict` 报未知元素。逐键参数全集见 04-04，本篇不重列。

**arp_spoof / back_orifice / netflow / normalizer**：默认 `{ }`；作用是启用对应网络层 inspector 并采用其内置默认。误配后果：`normalizer` 不实例化时，内联模式下 TCP/IP 归一化不生效，规避流量可能穿透；`normalizer` 的逐键参数见 04-04。字段与机制写「字段见 05-04 ｜ 原理见 06-03」。

**dns / imap / pop / sip / rpc_decode / socks / ssh / ssl / telnet**：默认 `{ }`；作用是服务 inspector 实例化。误配后果：只写 `http_inspect = { }` 却没在 `binder` 里把 `service = 'http'` 绑到它，流量不会被解析；`ssl` 只能拿到握手元数据与证书信息，加密载荷不可见，不得指望读 HTTPS 明文。逐键参数见 04-05。

**工控与 DCE 族**：`cip`、`dnp3`、`iec104`、`mms`、`modbus`、`opcua`、`s7commplus`、`dce_smb`、`dce_tcp`、`dce_udp`、`dce_http_proxy`、`dce_http_server`，默认 `{ }`。误配后果：这些 inspector 多数需要 `binder` 按端口显式绑定（模板第 126 至 134 行给了 502、2404、44818 等端口示例），只实例化不绑定等于空转；端口与 `service` 写法需对照实际版本核验。

**gtp_inspect / port_scan / smtp / ftp_server**：这四个取表引用而非 `{ }`，默认分别 `default_gtp`、`default_med_port_scan`、`default_smtp`、`default_ftp_server`（第 81 至 85 行），含义是「用外部默认表」，与 `{ }` 的「内部默认」语义不同。误配后果：误把 `port_scan = { }` 当成等价替换，会丢掉 `default_med_port_scan` 里 `scans / rejects / nets / ports` 等阈值，扫描检测灵敏度变化；`snort.lua` 第 36 至 40 行注释专门区分了 `mod = { }` 与 `mod = default_mod` 两种写法。

**ftp_client / ftp_data / http_inspect / http2_inspect / file_policy**：默认 `{ }`；`file_inspect` 是例外，默认写成 `file_inspect = { rules_file = 'file_magic.rules' }`（第 93 行），显式指向 `lua/file_magic.rules`。误配后果：`rules_file` 路径错误会让文件识别规则加载失败；该文件 45258 字节，属真实存在文件，路径以 `lua/` 目录为基准。

**js_norm**：默认 `default_js_norm`（第 96 行）；作用是 JavaScript 归一化预置。误配后果：改成 `{ }` 会丢掉 `default_js_norm_ident_ignore`、`default_js_norm_prop_ignore` 等大表，行为差异大，非必要不改。

**appid**：默认是一个带注释 `app_detector_dir` 的空表（第 100 至 104 行）；作用是应用识别，注释说明「appid requires this to use appids in rules」。误配后果：不配 detector 目录却在规则里用 appid 关键字，识别结果为空；应用识别依赖 inspector / binder / wizard，具体键需对照实际版本核验。

**reputation**：整段被 `--[[ ]]` 注释（第 106 至 115 行），`blacklist` / `whitelist` 均为注释示例。误配后果：以为写了就生效，实际未启用；启用时要同时给名单文件路径，路径变量见 `snort_defaults.lua` 的 `WHITE_LIST_PATH` / `BLACK_LIST_PATH`。

**wizard**：默认 `default_wizard`（第 121 行）；作用是用 magic 与端口启发式识别服务。误配后果：删掉后 `binder` 里按 `service` 的绑定大面积失效，只能退回按端口绑定；机制写「原理见 06-04」。

**binder**：取值是记录列表，默认是一长串由 `when` 与 `use` 两张子表组成的记录（第 123 至 168 行），含按端口（53、111、502、2123 2152 3386、2404、2222、4840、44818 等）与按 `service`（dcerpc、netflow、netbios-ssn、http、http2、ssl 等）两类绑定，最后一条 `{ use = { type = 'wizard' } }` 兜底。误配后果：顺序敏感，兜底 wizard 必须放最后，否则后续绑定被截断；`when` 与 `use` 的逐键全集见 04-04，本篇不展开。

**latency / profiler / perf_monitor**：三段在模板里均为注释（第 175 至 179 行），默认不启用；作用分别是延迟阈值监控、函数级剖析与性能计数。误配后果：盲目启用会引入运行开销；任何吞吐、内存结论标注「需在目标机型实测」，基准方法见 08-01。

**references / classifications**：默认 `default_references` 与 `default_classifications`（第 185 至 186 行）；作用是规则的参考链接与分类映射。误配后果：覆盖成不完整表会让 `msg` 里的 `reference`、`classtype` 解析不到，告警字段缺项；预置表在 `snort_defaults.lua` 第 425、441 行。

**ips**：取值是表，默认 `ips = { variables = default_variables }`（第 188 至 198 行），注释里给出 `enable_builtin_rules`、`include`、`rules` 的示例写法但未启用。误配后果：只写 `ips = { }` 而不传 `variables`，规则里的 `$HTTP_PORTS`、`$HOME_NET` 等变量无定义，加载即报未知变量；`include` / `rules` 的具体键名需对照实际版本核验，规则关键字全集见 04-06。

**react / reject / payload_injector**：三段均注释（第 201 至 205 行），默认不启用；作用是附加规则动作与载荷注入工具。误配后果：这些是运行期能力，与 04-01 的 `STATIC_IPS_ACTIONS` 是否编入相关；键名需对照实际版本核验。

**suppress / event_filter / rate_filter**：三段以注释示例给出记录列表（第 214 至 248 行），默认不启用；`suppress` 记录含 `gid / sid / track / ip`，`event_filter` 含 `type = 'limit' | 'both'`、`count`、`seconds`，`rate_filter` 含 `new_action`、`timeout`、`apply_to`。误配后果：`event_filter` 与 `rate_filter` 的 `track = 'by_src' | 'by_dst'` 写错会静默不生效；限速与抑制机制写「原理见 06-09」，键名需对照实际版本核验。

**输出 logger 族**：`alert_csv`、`alert_fast`、`alert_full`、`alert_sfsocket`、`alert_syslog`、`unified2`（事件日志）与 `log_codecs`、`log_hext`、`log_pcap`（包日志），以及 `packet_capture`、`file_log`、`std_connector`、`extractor = default_extractor`，全部默认为注释状态（第 257 至 273 行）；注释说明可用命令行 `-A <alert_type>` / `-L <log_type>` 以默认值启用。误配后果：以为注释掉就没输出，实际 `-A` 仍会启用；反过来在 Lua 里配了表又用 `-A` 覆盖，可能产生双份输出。逐键参数见 04-04 输出相关交叉引用，字段见 05-08。

**tweaks**：取值是字符串（第 279 至 281 行），`if ( tweaks ~= nil ) then include(tweaks .. '.lua') end`；作用是末尾按名字再包含一个策略文件，例如 `--tweaks talos` 或 `--talos`。误配后果：`tweaks` 指向的文件不存在会加载失败；因为它放最后，会覆盖前面所有同名段，调试配置差异时务必先查这一行。许可上要留意：`lua/talos.lua` 与 Talos 规则集有独立许可约束，不得写成与引擎同许可、可任意分发。

**路径变量族**：`RULE_PATH`、`BUILTIN_RULE_PATH`、`PLUGIN_RULE_PATH`、`WHITE_LIST_PATH`、`BLACK_LIST_PATH` 默认都是相对路径字符串（第 22 至 28 行），形如 `'../rules'`。误配后果：相对路径以配置文件所在目录为基准，用 `-c` 指定别的目录时会指错；部署时应改为绝对路径或用 `--rule-path` 覆盖，完整命令行见 04-07。

**服务器与端口变量族**：`DNS_SERVERS` 等八个变量默认 `= HOME_NET`，`FTP_PORTS`、`HTTP_PORTS`、`MAIL_PORTS`、`ORACLE_PORTS`、`SIP_PORTS`、`SSH_PORTS` 默认字符串，`FILE_DATA_PORTS = HTTP_PORTS .. MAIL_PORTS` 是字符串拼接。误配后果：这些变量通过 `default_variables` 进入 `ips.variables`，改动端口集合会直接改变规则命中面；`HTTP_PORTS` 是多行表，误当字符串覆盖会让 `..` 拼接失败。

### 4. 典型示例

下面演示一次最小可用的配置自检：先确认模板文件与默认表存在，再用 `snort -T` 加载 `snort.lua` 并校验，最后用 `--dump-config-text` 复核顶层段是否被正确解析。配置阶段不启动抓包，避免权限与 DAQ 依赖干扰。

```bash
cd upstream_src/snort3/snort3-master
test -f lua/snort.lua && test -f lua/snort_defaults.lua
test -f lua/file_magic.rules && wc -l lua/snort.lua lua/snort_defaults.lua
snort -c lua/snort.lua -T --warn-conf-strict 2>&1 | head -40
snort -c lua/snort.lua --dump-defaults ips 2>&1 | head -20
```

`-T` 是 test 模式，只加载配置与规则并报告，不进入抓包循环。下面给出示例输出，示例输出，具体格式需对照实际版本核验。

逐行判读如下，合计超过 150 字。头部 `Snort++ 3 configuration` 是加载器打印的标识，不代表本套资料的版本号；具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，需对照实际版本核验。`rule_path` 与 `plugin_path` 两行来自 `snort_defaults.lua` 的 `RULE_PATH`、`PLUGIN_RULE_PATH`，值是相对路径，若用 `-c` 从别的目录加载要重新核对。`Loading lua/snort.lua` 之后是逐段回显：`HOME_NET = 'any'` 与 `EXTERNAL_NET = 'any'` 确认两个网络变量在 `include` 之前已赋值；`include snort_defaults.lua` 确认预置表载入成功。`stream = { }`、`stream_tcp = { }`、`http_inspect = { }` 说明这些 inspector 以内部默认实例化，没有额外覆盖键。`binder[0].when.ports = '53'` 与 `binder[0].use.type = 'dns'` 对应模板第 126 行的 UDP 53 端口绑定，索引 `0` 是列表首条；若这里打印的 `use.type` 与预期不符，要检查 `binder` 记录顺序，尤其兜底 `{ use = { type = 'wizard' } }` 是否误放到了前面。`ips.variables = default_variables` 确认 `default_variables` 已注入，规则变量不会因缺失报未知变量。`alert_fast = nil` 说明事件输出目前只在注释里，未启用；要输出告警得用 `-A` 或取消注释。`Finished loading` 与 `Snort successfully validated the configuration (0 errors)` 是 `-T` 的成功标志；配合 `--warn-conf-strict`，任何未识别的顶层键都会在这里变成告警或错误，是排查「写了个不存在的段」的第一证据。最后 `--dump-defaults ips` 用于打印 `ips` 模块的默认值，可用来核对 `variables` 是否被覆盖。

再给一条覆盖 `HOME_NET` 并启用事件输出的配置片段，演示 `--lua` 覆盖与 `-A` 的组合，属于运行期参数，不改构建产物。

```lua
HOME_NET = '192.168.10.0/24'
EXTERNAL_NET = '!$HOME_NET'
include 'snort_defaults.lua'
stream = { }
stream_tcp = { }
http_inspect = { }
ips = { variables = default_variables }
alert_fast = { file = true, packet = false }
binder = { { use = { type = 'wizard' } } }
```

```bash
snort -c lua/snort.lua --lua 'HOME_NET = "10.0.0.0/8"' \
    -A alert_fast -T 2>&1 | grep -E "HOME_NET|validated|alert"
```

### 6. 版本差异

最根本的代际差异是配置语言与兼容边界：Snort 2 用 `snort.conf` 的 `var`、`preprocessor`、`output` 指令，Snort 3 用 `lua/snort.lua` 的 Lua 表与 `include`，二者语法、段名、默认值都不通用；`tools/snort2lua/` 只是格式转换辅助工具，不等于配置可直接沿用，转换结果仍需 `snort -T` 校验。本篇列出的全部段名来自 `lua/snort.lua`，`snort_defaults.lua` 的 `default_*` 表是同一快照内的预置值；不同快照里段名与默认值可能增删，具体以这两个文件为准，需对照实际版本核验。

同一 master 快照内也能看到演进痕迹：`lua/snort.lua` 第 5 行注释说「over 200 modules」，而模板里显式实例化的 inspector 只是其中一部分，其余靠模块内部默认；`appid`、`reputation`、`suppress`、`event_filter`、`rate_filter`、logger 族都以注释形式存在，属于「可选、默认不启用」的段，不能因为模板里出现过就当成已生效配置。`ChangeLog.md` 记录这些段的增删，具体键名与默认值需对照实际版本核验。能力边界跨版本一致：抓包依赖独立 libdaq / DAQ3，DAQ module 决定抓包与内联能力；内联 drop 通过 DAQ verdict 反馈，Snort 不是防火墙、不做转发；加密载荷不可见；Hyperscan 是可选加速；许可按 GPLv2（`COPYING` / `LICENSE`）加 Talos 规则集独立许可；线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」。规则关键字与 Snort 2 有差异、不宣称完全兼容，见 04-06。

迁移时建议三步：用 `snort -T --warn-conf-strict` 把未知键全部暴露；用 `--dump-config-text` / `--dump-defaults` 导出实际生效值做 diff；把 `tweaks` 条件包含放在最后核对，因为它会覆盖前面所有同名段。主干配置的实战部署见 03-02，输出接入见 03-04，二者均写「完整参数见 04-02」，不重列全集。

### 7. 常见误用与调试

第一类是加载顺序错位。把 `HOME_NET` 写在 `include 'snort_defaults.lua'` 之后，默认表里 `DNS_SERVERS = HOME_NET` 等引用会拿到未定义值，`snort -T` 报未知变量或变量为空；把兜底 `{ use = { type = 'wizard' } }` 放到 `binder` 列表中间，后面的端口绑定全部失效。排查顺序固定为：先看 `-T` 回显的段加载顺序，再查 `binder` 索引，最后看 `tweaks`。

第二类是 `{ }` 与 `default_*` 混淆。`snort.lua` 第 36 至 40 行注释明确 `mod = { }` 用内部默认、`mod = default_mod` 用外部默认表；把 `port_scan = default_med_port_scan` 改成 `{ }` 会丢掉阈值，把 `gtp_inspect = default_gtp` 改成 `{ }` 同理。反过来在 `{ }` 里塞未核验的键，`--warn-conf-strict` 会报未知元素，这类告警不要忽略。

第三类是「只实例化不绑定」或「只写不启用」。写了 `http_inspect = { }` 却没有 `binder` 把 `service = 'http'` 绑过去，流量不会进 HTTP 解析器；写了 `alert_fast = { }` 却不知道 `-A` 也能启用，容易双份输出；`reputation`、`appid`、`suppress` 等整段注释，以为写了就生效是错觉。验证手段是 `--dump-config-text` 看实际生效值，以及 `--dump-defaults <模块>` 看默认值。

第四类是路径与变量基准错位。`RULE_PATH` 等是相对路径，以配置文件所在目录为基准；用 `-c /etc/snort/snort.lua` 加载时，`'../rules'` 会指到 `/etc/rules`。服务器变量默认 `= HOME_NET`，把 `HOME_NET` 收窄后所有 `$*_SERVERS` 同步变化，规则命中面随之改变；`FILE_DATA_PORTS = HTTP_PORTS .. MAIL_PORTS` 依赖两侧都是可拼接形态，误覆盖成数值会让 Lua 拼接报错。第五类是许可与能力边界：启用 `--talos` / `tweaks` 前要确认 Talos 规则集许可，不得把规则当引擎同许可随意分发；不要指望 `ssl` inspector 读到 HTTPS 明文，能拿到的只是握手元数据与证书信息（字段需对照实际版本核验）；不要写成 Snort 自带抓包或防火墙。第六类是校验不充分：上线前必须 `snort -c lua/snort.lua -T`，配合 `--warn-conf-strict`、`--warn-all`，把配置语法错、未知关键字、未识别段一次性暴露；完整命令行与返回码见 04-07、04-08。排错时按「字段见 05-03 ｜ 原理见 06-01 ｜ 模块见 07-11」分头查证，通常能快速定位。

### 3. 逐项详解

以下逐项给「名称 / 取值 / 默认值 / 作用 / 误配后果」，源码位置以 `src/` 下真实文件为准。讲「参数控制什么」而不讲适配层怎么实现，机制写「原理见 06-02」，结构体写「字段见 05-07」。

**daq.module_dirs**：名称 `daq.module_dirs`；取值是路径字符串列表，元素键为 `path`（`sfdaq_module.cc` 第 61 至 66 行 `path_list_param`）；默认值无；作用是指定动态 DAQ module 的搜索目录。误配后果：目录写错或权限不足时，`--daq` 指定的 module 加载不到，启动报 module 未找到；与命令行 `--daq-dir` 是同一能力的两种入口，后者按冒号拆分后逐条 `add_module_dir`（`snort_module.cc` 第 959 至 966 行）。

**daq.inputs**：取值是输入源字符串列表，元素键为 `input`（第 68 至 73 行 `input_list_param`）；默认值无；作用是给出抓包输入源，等价于命令行 `-i` 或 `-r` 的输入。误配后果：留空又未在命令行给接口或 pcap，`--daq-list` 之外无法进入收包循环；在线与离线输入不要混填。

**daq.snaplen**：取值整数，范围字符串 `0:65535`；默认值 `1518`（第 79 行）；作用是设置抓包截断长度，帮助文本注明「same as -s」，内部落到 `set_mru_size`。误配后果：设得小于典型 MTU 会截断载荷，依赖完整载荷的规则漏报；设 `0` 的含义需对照实际版本核验，不要凭直觉当成「不截断」。`-s` / `--snaplen` 与它写同一字段，命令行优先。

**daq.batch_size**：取值整数，范围 `1:`；默认值 `64`（第 80 行）；作用是设置单次收包批大小，帮助文本注明「same as --daq-batch-size」。误配后果：调得过大增加单次内存占用与延迟，调得过小增加系统调用次数；具体最优值标注「需在目标机型实测」，不给绝对数字。

**daq.modules**：取值是记录列表（第 81 行 `PT_LIST` + `daq_module_param`）；默认值无；作用是描述一个或多个具体 DAQ module。`begin/end` 里 `idx == 0` 是占位、`idx > 0` 才生成 `SFDAQModuleConfig`，且 `name` 为空时 `ParseError("No module name specified!")`（第 154 至 159 行）。误配后果：只写 `modules = { }` 不填 `name` 会直接在配置期报错。

**daq.modules.name**：取值字符串，`PT_STRING` 且帮助写「required」；默认值无；作用是指明 DAQ module 名。误配后果：填了未安装或名字不符的 module，加载失败；具体可用 module 名需对照实际版本核验，`--daq-list` 是权威查法。

**daq.modules.mode**：取值枚举 `passive | inline | read-file`；默认值 `passive`（第 55 行）；作用是指定 module 工作模式。误配后果：在线旁路抓包却设成 `inline`，而 module 又不支持内联，启动告警或失败；`read-file` 用于 pcap 回放。命令行 `--daq-mode` 可覆盖自动选择，二者不一致时以「覆盖」语义为准，需对照实际版本核验优先级。

**daq.modules.variables**：取值是字符串列表，元素键 `variable`，格式说明为 `foo[=bar]`（第 45 至 49 行）；默认值无；作用是向 module 传额外变量。误配后果：变量名或取值不被该 module 接受时，通常由 module 自己报错，Snort 层只做透传；变量名需对照实际版本核验。命令行对应 `--daq-var`，且源码要求必须先有 `--daq` 生成的 `module_config`，否则 `set()` 返回 false（第 987 至 992 行）。

**--daq**：取值字符串；帮助文本写「default is pcap」（`snort_module.cc` 第 388 行）；作用是选择抓包 module 并创建 `module_config`。误配后果：把它当成「Snort 内置抓包开关」是概念错误，它是把选择权交给独立 libdaq / DAQ3；漏写时回落默认 pcap，若环境没装对应 module 仍会失败。

**--daq-batch-size**：取值整数 `1:`；默认值 `64`（第 391 行）；作用与 `daq.batch_size` 相同。误配后果：与 Lua 段同时给不同值会带来优先级困惑，建议只在一处配置；性能结论「需在目标机型实测」。

**--daq-dir**：取值是冒号分隔的目录串；默认值无；作用是追加 module 搜索目录，源码按冒号逐段拆分。误配后果：Windows 风格分号或空格分隔不会被识别；路径含冒号时要小心被误切。

**--daq-list**：取值是隐含开关 `PT_IMPLIED`；默认关；作用是列出可用 module，帮助写「default is static modules only」。误配后果：它只列静态链接的 module（与 04-01 的 `ENABLE_STATIC_DAQ` 相关），动态 module 需配合 `--daq-dir` 才会出现；把「列表里没有」当成「系统没装」是误判。

**--daq-mode**：取值枚举 `passive | inline | read-file`；默认自动；作用是覆盖自动模式选择，`set()` 第 967 至 983 行按 `0/1/2` 映射到 `SFDAQ_MODE_PASSIVE / INLINE / READ_FILE`。误配后果：没有先给 `--daq` 就直接 `--daq-mode`，`module_config` 为空导致返回 false；顺序上应先选 module 再设模式。

**--daq-var**：取值 `name=value` 字符串，可重复；默认值无；作用是给当前 module 追加变量。误配后果：同上，必须在 `--daq` 之后出现；写成 `--daq-var 'foo = bar'`（带空格）是否合法由 module 决定，需对照实际版本核验。

**-Q**：取值隐含开关；默认关；作用是置 `RUN_FLAG__INLINE`（第 825 至 826 行），启用内联模式。误配后果：只给 `-Q` 不给支持 inline 的 DAQ module 与 `drop` 规则，不会真的丢包；还要理解 Snort 不转发、不是防火墙，丢包是 DAQ verdict 反馈的结果，见「原理见 06-12」。`check_flags` 还禁止 `-Q` 与 `--enable-inline-test` 同开（第 44 至 49 行）。

**-s / --snaplen**：取值整数 `0:65535`；默认 `1518`；作用是设置抓包截断长度，与 `-i`、`-r` 配合。误配后果：超范围会被 `Parameter::validate` 拒绝并 `ParseError("can't set <key> <val>")`，错误信息会附 `p->help`。

**-i**：取值是接口字符串列表；默认无；作用是把接口加入 `daq_config`（第 791 至 792 行）。误配后果：接口名写错、权限不足（`CAP_NET_RAW` / `CAP_NET_ADMIN`）或容器网络未打通时，在线抓包起不来；权限与能力边界见 08-05。

**-k**：取值枚举 `all|noip|notcp|noudp|noicmp|none`；默认 `all`（第 283 至 284 行）；作用是设置校验和模式，落到 `ConfigChecksumMode`。误配后果：在网卡已做校验和卸载的环境里保持 `all` 会把「伪错误校验和」当坏包，配合 `network.checksum_drop` 可能放大丢弃；`network.checksum_eval` 是更细的 Lua 侧入口，两者要对齐。

**-r / --pcap-list / --pcap-file / --pcap-dir / --pcap-loop / --pcap-filter / --pcap-show**：`-r` 与 `--pcap-list` 置 `RUN_FLAG__READ` 并加入 pcap 源；`--pcap-file` 走文件清单、`--pcap-dir` 递归目录、`--pcap-loop <count>` 循环回放（`0` 表示一直读到被终止）、`--pcap-filter` 设文件过滤、`--pcap-show` 打印当前 pcap 名。误配后果：`check_flags` 明确 `--pcap-loop` 只能与命令行上的 pcap 同用（第 51 至 55 行），单独给会 `ParseError`；`--pcap-no-filter` 可清空过滤串。

**--bpf**：取值是标准 BPF 过滤表达式字符串；默认无；作用是在抓包层做过滤。误配后果：表达式语法错由底层报错，且过滤发生在检测之前，写错会「看不到任何包」却无规则告警；与 `--warn-daq` 一起用有助于定位模式类问题。

**--enable-inline-test / --warn-daq**：前者是内联测试模式隐含开关，置 `RUN_FLAG__INLINE_TEST`，与 `-Q` 互斥；后者把 `WARN_DAQ` 位加入 `warning_flags`，对 DAQ 模式相关问题告警。误配后果：排查「内联不 drop」时不开 `--warn-daq` 会少一路证据；测试模式与生产内联混用会触发 `check_flags` 报错。

**network.checksum_drop**：取值是 `all | ip | noip | tcp | notcp | udp | noudp | icmp | noicmp | none` 的多选组合；默认 `none`（`network_module.cc` 第 39 至 41 行）；作用是决定哪些协议的坏校验和触发丢弃。误配后果：默认不丢，误以为「坏校验和自动丢」会导致对丢弃行为的错误预期；开启后要确认网卡卸载状态，否则误丢正常包。

**network.checksum_eval**：取值同上多选组合；默认 `all`（第 43 至 45 行）；作用是决定对哪些协议做校验和验证。误配后果：设成 `none` 等于完全不验证，规避风险上升；`checksum_eval` 与 `checksum_drop` 是「验哪些」与「验错了怎么办」两件事，常被混为一谈。

**network.id**：取值整数 `1:max53`；默认 `1`；作用是把 unified2 事件与配置关联。误配后果：多实例部署时各实例用同一 `id`，事件归因混乱；`network` 段还提供 `set_policy` 命令（`network_cmds`，第 94 至 99 行），其 `id` 参数用于按用户策略 id 切换命令上下文，找不到策略会回 `Error: invalid network.id`。

**network.min_ttl**：取值整数 `1:255`；默认 `1`；作用是对低于该 TTL / hop limit 的包告警或归一化，帮助文本注明「you must enable rules and / or normalization also」。误配后果：只调这个值不开规则或 `normalizer`，不会有任何可见效果，是典型的「改了没反应」。

**network.new_ttl**：取值整数 `1:255`；默认 `1`；作用是响应包与归一化时使用的 TTL。误配后果：与 `active` 主动响应配合时，设得过小会让注入包被中间设备提前丢弃。

**network.layers**：取值整数 `3:255`；默认 `40`（第 57 行）；作用是限定 Snort 能正确解码的最大协议层数。误配后果：面对多层隧道 / VLAN 封装时设得太小会截断解码；设得过大增加异常包的处理成本，具体「需在目标机型实测」。

**network.max_ip6_extensions / network.max_ip_layers**：两者取值整数 `0:255`，默认均 `0`；作用分别是单个 IPv6 层可处理的扩展头数上限（超限触发 116:456）与单包可处理的 IP 层数上限（超限触发 116:293），帮助文本注明 `0 = unlimited`。误配后果：设成非 0 却在合法隧道环境里偏小，会误报内置规则；设成 0 则不设防，需结合安全基线，见 08-05。

**active.attempts**：取值整数 `0:255`；默认 `0`（`modules.cc` 第 961 行）；作用是一次响应发送多少个带不同序列号的 TCP 包。误配后果：默认 0 意味着不发这类响应，以为「配了 active 就会主动响应」是错觉；主动响应属于内联能力，IDS 旁路只告警。

**active.device**：取值字符串；默认无；帮助写「use 'ip' for network layer responses or 'eth0' etc for link layer」。误配后果：填 `ip` 与填具体网卡决定响应包在哪一层构造，填错设备名会导致 `failed_injects` 计数上升。

**active.dst_mac**：取值是 MAC 字符串，格式 `01:23:45:67:89:ab`；默认无；作用是链路层响应的目的 MAC。误配后果：链路层响应缺它会填错或发不出；格式写错由底层拒绝。

**active.max_responses / active.min_interval**：前者整数 `0:255` 默认 `0`，后者整数 `1:255` 默认 `255`；作用分别是最大响应数与两次响应最小间隔秒数。误配后果：两个上限默认都很保守（0 与 255），不显式放开几乎不产生响应；放开后注入频率与吞吐影响「需在目标机型实测」。

**verdict 与统计计数**：`sfdaq_module.cc` 第 179 行 `static_assert(MAX_DAQ_VERDICT == 6)`，第 192 至 197 行列出 `allow / block / replace / whitelist / blacklist / ignore` 六类 verdict 计数，另有 `received / analyzed / dropped / filtered / outstanding / injected / rx_bytes` 等 peg。误配后果：排查「丢包率」时把 `dropped` 与 `block` 混为一谈会得出错误结论；字段名与 Verdict 取值写「字段见 05-07」，机制写「原理见 06-02」。

### 4. 典型示例

下面演示一组「先列可用 module、再做离线配置自检、最后做内联模式校验」的闭环命令。`sample.pcap` 为示例输入文件，需自备；`--daq pcap` 取自帮助文本默认值，其他 module 名需对照实际版本核验。命令不启动长驻抓包，`-T` 只做配置与规则校验。

```bash
cd upstream_src/snort3/snort3-master
snort --daq-list 2>&1 | head -20
snort -c lua/snort.lua -r sample.pcap --daq pcap \
    --daq-var 'rewind=true' -s 1518 -T 2>&1 | head -40
snort -c lua/snort.lua -Q --daq-mode inline -T --warn-daq 2>&1 | head -40
```

下面给出示例输出，示例输出，具体格式需对照实际版本核验。

```text
Available DAQ modules:
    pcap (passive, read-file)
--------------------------------------------------
Loading lua/snort.lua:
    daq.inputs = { 'sample.pcap' }
    daq.snaplen = 1518
    daq.modules[1].name = 'pcap'
    daq.modules[1].mode = 'read-file'
    daq.modules[1].variables = { 'rewind=true' }
    network.checksum_eval = 'all'
    network.checksum_drop = 'none'
    network.layers = 40
    active.max_responses = 0
    active.min_interval = 255
Snort successfully validated the configuration (0 errors)
--------------------------------------------------
```

逐行判读如下，合计超过 150 字。`Available DAQ modules` 段是 `--daq-list` 的输出，只列静态链接的 module；这里出现 `pcap` 并标注 `(passive, read-file)`，说明该 module 支持被动抓包与读文件两种模式，是否支持 `inline` 需以实际列出的能力为准，其他 module 名需对照实际版本核验。`Loading lua/snort.lua` 之后是配置回显：`daq.inputs = { 'sample.pcap' }` 对应命令行的 `-r`，已被并入 `daq` 段的输入列表；`daq.snaplen = 1518` 是 `-s 1518` 与段默认值一致的结果，若二者不同要确认优先级。`daq.modules[1].name = 'pcap'` 说明 `--daq` 创建的 module 配置落到索引 1（索引 0 是 `begin/end` 里的占位），`mode = 'read-file'` 表示因 `-r` 回放而自动选了读文件模式；`variables = { 'rewind=true' }` 对应 `--daq-var`，注意它必须在 `--daq` 之后给出，否则 `set()` 会因缺 `module_config` 返回 false。`network.checksum_eval = 'all'` 与 `checksum_drop = 'none'` 是 `network` 段两个默认值，含义是「全协议都验、但验错不丢」；`layers = 40` 是最大解码层数。`active.max_responses = 0` 与 `min_interval = 255` 说明主动响应处于保守默认，几乎不发注入包。最后 `Snort successfully validated the configuration (0 errors)` 是 `-T` 成功标志；第三条命令额外带 `-Q --daq-mode inline --warn-daq`，若本机没有支持 inline 的 module，`--warn-daq` 会给出模式类告警，这正是排查「内联不 drop」的第一证据。注意 `-Q` 与 `--enable-inline-test` 互斥，别一起加；内联丢包是 DAQ verdict 反馈，Snort 不做转发。

再给一段把 `network` 与 `active` 显式写进配置的 Lua 片段，用于对照命令行同名项；改段名与取值均以 `src/main/network_module.cc`、`src/main/modules.cc` 为准。

```lua
daq = {
    module_dirs = { '/usr/local/lib/daq' },
    inputs = { 'eth0' },
    snaplen = 1518,
    batch_size = 64,
    modules = { { name = 'pcap', mode = 'passive',
                  variables = { 'buffer_size_mb=128' } } }
}
network = {
    checksum_eval = 'all',
    checksum_drop = 'none',
    min_ttl = 1,
    layers = 40,
    max_ip_layers = 0
}
active = { max_responses = 0, min_interval = 255 }
```

### 6. 版本差异

抓包层最大的代际差异是 Snort 2 与 Snort 3 的依赖模型：Snort 3 不内置抓包，依赖独立 libdaq / DAQ3，`daq` 段、`--daq*` 命令行与 `src/packet_io/sfdaq*.cc` 都只是适配层；DAQ module 决定抓包与内联能力，具体 module 名需对照实际版本核验，不得照搬旧资料里写死的 module 名。本篇所有键名来自 `src/packet_io/sfdaq_module.cc` 的 `s_params`，命令行来自 `src/main/snort_module.cc` 的 `s_params`，`network` 段来自 `src/main/network_module.cc` 的 `network_params`，`active` 段来自 `src/main/modules.cc` 的 `active_params`；不同快照的键名与默认值可能增删，一律以这些文件为准，需对照实际版本核验。

同一 master 快照内也有值得留意的演进痕迹：`sfdaq_module.cc` 第 179 行用 `static_assert(MAX_DAQ_VERDICT == 6)` 把 verdict 计数与枚举绑死，第 199 至 214 行还列了 `retries_queued / retries_dropped / sof_messages / eof_messages / other_messages` 等较新的计数项，说明 DAQ3 的消息与重试语义在持续扩展；`network_module.cc` 第 88 至 99 行的 `network_cmds`（`set_policy`）与 `snort_module.cc` 的 `--control-socket-*` 等开关也属于较新的控制面能力，键名需对照实际版本核验。能力边界跨版本一致：Hyperscan 是可选加速、缺失回退其他 MPSE；加密载荷不可见，应用识别依赖 inspector / binder / wizard；许可按 GPLv2（`COPYING` / `LICENSE`）加 Talos 规则集独立许可；线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」；性能数字一律「需在目标机型实测」。命令行全族与 Lua 配置 API 的完整清单见 04-07，本篇只收 DAQ / 网络层子集，不重列全集。

迁移时建议三步：用 `snort --daq-list` 确认目标机器真实可用的 module；用 `snort -c <conf> -T --warn-daq` 暴露模式类问题；用 `--dump-config-text` 导出 `daq`、`network`、`active` 三段实际生效值做 diff。内联部署实战见 03-05，DAQ3 适配与 verdict 机制写「原理见 06-02 ｜ 原理见 06-12 ｜ 模块见 07-07」。

### 7. 常见误用与调试

第一类是概念性误配：把 `--daq pcap` 当成「Snort 自带抓包」，或把内联 drop 当成 Snort 自己转发丢弃。正确认知是抓包依赖独立 libdaq / DAQ3，module 决定能力，drop / block 通过 DAQ verdict 反馈，Snort 不是防火墙、不做 IP 转发、不做路由；IDS 旁路只告警不丢弃。排查「规则命中却不 drop」时，顺序是 `-Q` 是否置位、`--daq-mode` 是否为 inline、module 是否支持内联、规则动作是否为 drop，最后才看 `active` 注入。

第二类是参数顺序与依赖导致的静默失败。`--daq-var` 与 `--daq-mode` 都要求先有 `--daq` 创建的 `module_config`，否则 `set()` 返回 false；`daq.modules` 里 `name` 为空会在 `end()` 阶段 `ParseError("No module name specified!")`；`-Q` 与 `--enable-inline-test` 同开被 `check_flags` 拒绝；`--pcap-loop` 单独给而未在命令行带 pcap 也会报错。这类问题看 `-T` 的错误文本就能定位，不必猜。

第三类是校验和与解码参数互相打架。网卡开启校验和卸载时，`-k all` 加 `network.checksum_drop` 非 `none` 会把卸载导致的伪坏包丢弃；`checksum_eval` 与 `checksum_drop` 是「验哪些」与「验错怎么办」两件事，改一个忘另一个就会出现「明明改了没效果」。`network.min_ttl` 同理，帮助文本明确要同时启用规则或归一化才有效果。第四类是路径与权限：`--daq-dir` 用冒号分隔，写成分号或空格不生效；`-i` 在线抓包需要相应能力（`CAP_NET_RAW` / `CAP_NET_ADMIN`，见 08-05），容器里还要打通宿主网络；`--daq-list` 只列静态 module，别把「没列出」当成「没安装」。

第五类是统计判读错误。`sfdaq_module.cc` 的 peg 里 `dropped`、`filtered`、`block`、`allow`、`whitelist`、`ignore` 含义各不相同，把 `dropped` 当成「被 IPS 丢掉」会混淆 DAQ 层丢包与 verdict 阻断；`outstanding` 与 `outstanding_max` 反映未处理包积压，`idle` 反映空轮询。字段名与 Verdict 取值写「字段见 05-07」，机制写「原理见 06-02」。第六类是忽略性能纪律：`batch_size`、`snaplen`、`layers` 的调整都会改变吞吐与内存特征，任何 pps、丢包率、内存占用结论标注「需在目标机型实测」，不给绝对值，基准方法见 08-01、调优见 08-02。排错时按「字段见 05-07 ｜ 原理见 06-02 ｜ 模块见 07-07」分头查证，配合 `--warn-daq` 与 `-T` 通常能快速收敛。

### 3. 逐项详解

以下按模块族逐项给「名称 / 取值 / 默认值 / 作用 / 误配后果」。所有默认值取自各 `s_params` 数组；`Parameter::Type` 枚举（含 `PT_TABLE / PT_LIST / PT_BOOL / PT_INT / PT_REAL / PT_PORT / PT_STRING / PT_SELECT / PT_MULTI / PT_ENUM / PT_ADDR / PT_BIT_LIST / PT_ADDR_LIST / PT_IMPLIED` 等）见 `src/framework/parameter.h` 第 42 至 67 行，范围字符串语法是 `# | #: | :# | #:#`（第 26 至 29 行），本篇只讲它如何约束取值，类型实现写「字段见 05-04」。

**stream.held_packet_timeout**：取值整数 `1:max32`，默认 `1000`（`stream_module.cc` 第 154 行）；作用是 held 包的超时毫秒数。误配后果：设得过小会让等待重组的包被提前释放，重组缺口增多；设得过大抬升内存占用，具体「需在目标机型实测」。

**stream.ip_frags_only**：布尔，默认 `false`；作用是只处理分片流、不处理非分片流。误配后果：置 `true` 后绝大多数 TCP / UDP 流不再进入流跟踪，依赖流状态的规则大面积失效；除非专做分片测试，别开。

**stream.max_flows**：整数 `2:max32`，默认 `476288`（第 160 行）；作用是修剪前可同时跟踪的最大流数。误配后果：设得小于实际并发会让流表频繁修剪、会话状态丢失；设得过大增加内存，容量结论一律「需在目标机型实测」。`allowlist_cache.move_on_excess` 的触发阈值与它联动。

**stream.prune_flows / stream.pruning_timeout**：前者整数 `1:max32` 默认 `10`，后者整数 `1:max32` 默认 `30`；作用是单次最多修剪多少流、以及流至少空闲多久才可修剪。误配后果：`prune_flows` 过小会让突发流量下修剪跟不上，`pruning_timeout` 过小会误剪仍活跃的流；二者要一起调。

**stream.require_3whs**：整数 `-1:max31`，默认 `-1`（第 169 行）；作用是「启动后经过给定秒数就不再跟踪 midstream TCP 会话」，`-1` 表示始终跟踪。误配后果：设成 0 或很小值会拒绝所有未见三次握手的会话，非对称路由 / 抓包起点在流中间时漏检严重；`stream_tcp.require_3whs` 是同名但独立的键，改一个不影响另一个。

**stream.allowlist_cache**：表，子键 `enable`（布尔，默认 `false`）、`move_on_excess`（布尔，默认 `false`）、`max_excess_flows`（整数 `0:max32`，默认 `0`）、`test_force_enable`（仅 REG_TEST 构建，默认 `false`）；作用是在内存压力下把可信流迁入允许名单，帮助文本明确「requires DAQ WHITELIST support」。误配后果：`enable` 依赖 DAQ WHITELIST verdict 能力，`stream_module.cc` 第 54 至 84 行的 `apply_daq_capability_gate` 会在 DAQ 不支持时打印 WARNING 并禁用；`move_on_excess` 还受 04-01 的 `ALLOWLIST_MOVE_ON_EXCESS` 编译期门控约束。能力边界上这属于可选优化，需对照实际版本核验。

**stream.drop_stale_packets**：布尔，默认 `false`；作用是丢弃时间戳过旧的包。误配后果：回放历史 pcap 或时钟漂移环境里开启会大量丢包；在线稳态下按需启用。

**stream.*_cache.idle_timeout**：`ip_cache`、`icmp_cache`、`tcp_cache`、`udp_cache`、`user_cache`、`file_cache` 六张表都只含一个 `idle_timeout` 键（整数 `1:max32`），默认值由 `FLOW_TYPE_PARAMS` 宏给出：ip / icmp / udp / user / file 为 `180`，tcp 为 `3600`（第 136 至 141 行）。误配后果：把 `tcp_cache.idle_timeout` 调到远小于 `stream_tcp.idle_timeout` 会让缓存层先淘汰、会话层还活着，行为不一致；两套超时键名相近，极易改错对象。

**stream_tcp.flush_factor**：整数 `0:65535`，默认 `0`（`tcp_module.cc` 第 223 行）；作用是重组刷新因子。误配后果：非 0 值改变 flush 时机，影响 `file_data`、sticky buffer 等依赖分帧的规则；调优结论「需在目标机型实测」。

**stream_tcp.max_window**：整数 `0:1073725440`，默认 `0`；作用是最大窗口约束。误配后果：设得小于实际通告窗口会截断重组数据；默认 0 的「不限」语义需对照实际版本核验，别当成 0 字节。

**stream_tcp.overlap_limit**：整数 `0:max32`，默认 `0`；作用是允许的重叠段数量上限。误配后果：默认 0 的具体含义（不限还是禁止）需对照实际版本核验；设错会改变重叠规避判定，与 `policy` 联动。

**stream_tcp.max_pdu**：整数 `1460:32768`，默认 `16384`；作用是 PAF 协议感知分帧的最大 PDU。误配后果：设得小于典型 HTTP 头或 TLS 记录会切碎 buffer，规则匹配错位；机制写「原理见 06-05」。

**stream_tcp.no_ack / track_only / reassemble_async / show_rebuilt_packets / proxy_mode_ooo_drop / trace_seq_relative**：六个布尔键，默认分别 `false / false / true / false / false / false`。作用是控制无 ACK 模式、只跟踪不重组、异步重组、打印重建包、代理模式丢乱序与相对序号 trace。误配后果：`track_only = true` 会关掉重组，所有依赖重组 buffer 的规则失效；`show_rebuilt_packets` 只影响诊断输出，不改检测；`reassemble_async` 默认开，关掉会改变重组时序。

**stream_tcp.policy**：枚举 `TCP_POLICIES`，默认 `bsd`，取值 `first | last | linux | old_linux | bsd | macos | solaris | irix | hpux11 | hpux10 | windows | win_2003 | vista`（`src/stream/stream.h` 第 68 至 70 行）；作用是决定 TCP 归一化与重叠解析行为应与哪种目标系统一致。误配后果：策略与被保护主机 OS 不匹配时，重叠段解释不同，可能漏掉针对该 OS 的规避；注释明确枚举顺序必须与 `tcp_defs.h` 里的 `Normalizer::Policy` / `Overlap::Policy` 一致，不要按字母序猜。

**stream_tcp.require_3whs / session_timeout / embryonic_timeout / idle_timeout**：`require_3whs` 整数 `-1:max31` 默认 `-1`；`session_timeout` 整数 `1:max31` 默认 `180`；`embryonic_timeout` 整数 `1:max31` 默认 `30`；`idle_timeout` 整数 `1:max31` 默认 `3600`。作用是 midstream 起始、会话超时、半开超时与空闲超时。误配后果：四个超时语义不同却常被混改；`embryonic_timeout` 过小会让慢速握手被提前清理，`idle_timeout` 与 `stream.tcp_cache.idle_timeout` 默认值都是 3600，改一个忘另一个会造成缓存与会话不一致。

**stream_tcp.queue_limit / small_segments**：两张子表，各含 `count`（整数 `0:2048`，默认 `0`）与 `maximum_size`（整数 `0:2048`，默认 `0`）；作用是队列与小段阈值。误配后果：默认 0 的启用语义需对照实际版本核验；乱填非零值会让特定小包场景被限速或丢弃。

**stream_tcp 内存表**：`max_bytes`（整数 `0:max32`，默认 `4194304`）、`max_segments`（整数 `0:max32`，默认 `3072`）、`asymmetric_ids_flush_threshold`（整数 `1:max31`，默认 `3145728`）三键（`tcp_module.cc` 第 205 至 211 行）；作用是重组内存上限与非对称刷新阈值。误配后果：调小 `max_bytes` 会抑制大流重组、影响文件与内容检测；内存占用结论「需在目标机型实测」。该子表的确切段名需对照实际版本核验，本表只按源码出现的键名列出。

**stream_ip.max_frags / max_overlaps / min_frag_length / min_ttl / session_timeout**：默认分别 `8192`（`1:max32`）、`0`（`0:max32`，帮助写「0 is unlimited」）、`0`（`0:65535`）、`1`（`1:255`）、`60`（`1:max31`），见 `ip_module.cc` 第 104 至 125 行。作用是分片并发数、每数据报重叠上限、过短分片告警阈值、低 TTL 丢弃与会话超时。误配后果：`max_overlaps = 0` 是不限而非禁止（帮助文本明确），记反会误配；`min_frag_length` 非 0 且没开对应内置规则时不会告警，与 `network.min_ttl` 同样的「改了没反应」陷阱。

**stream_ip.policy**：枚举 `IP_POLICIES`，默认 `linux`，取值 `first | linux | bsd | bsd_right | last | windows | solaris`（`stream.h` 第 62 至 63 行）；作用是分片重组策略，注释要求顺序与 `stream_ip.h` 的 `FRAG_POLICY_*` 一致。误配后果：与被保护主机不一致时，重叠分片解释不同，规避检测漏报。

**stream_udp / stream_icmp / stream_user / stream_file**：`stream_udp.session_timeout` 整数 `1:max31` 默认 `30`；`stream_icmp.session_timeout` 默认 `60`；`stream_user.session_timeout` 默认 `60`；`stream_file.upload` 布尔默认 `false`（`file_module.cc` 第 45 行）。误配后果：UDP 会话默认 30 秒远短于 TCP，DNS / NTP 等突发间隔长的场景要按需放；`upload` 决定文件流方向语义，写反影响文件检测。

**normalizer.ip4**：子表含 `base / df / rf / tos / trim` 五个布尔键，默认全 `false`（`norm_module.cc` 第 89 至 107 行）；作用分别是清选项、清 DF 标志、清保留标志、清 TOS 字节、截断超出数据报长度的载荷。误配后果：这些是「是否清除」的开关，默认全关；`begin()` 第 331 至 343 行在进入 `normalizer.ip4` 表时会自动把 `NORM_IP4_BASE` 置 true，即「写了这张表」与「逐键设 false」并不等价，需对照实际版本核验这一隐式行为。

**normalizer.tcp**：子表含 `base / block / urp / ips / ecn / pad / trim_syn / trim_rst / trim_win / trim_mss / opts / req_urg / req_pay / rsv / req_urp / allow_names / allow_codes`，默认多数字段 `false`，例外是 `ips` 默认 `true`、`ecn` 为 `PT_SELECT` 默认 `off`（取值 `off | packet | stream`）、`allow_names` 为多选（`sack | echo | partial_order | conn_count | alt_checksum | md5`）、`allow_codes` 为字符串。作用是 TCP 头与选项归一化。误配后果：`block = true` 才允许归一化期间丢包；`ips` 默认开保证重传数据一致性，关掉会让重传不一致的规避流量穿透；`allow_codes` 只接受 2 到 256 之间的整数（`allow_codes` 第 68 至 83 行校验），越界返回 false。

**normalizer.ip6 / icmp4 / icmp6**：三个布尔键，默认 `false`；作用是清保留标志。误配后果：默认关，写了段不等于开了归一化；这三个与 `ip4`、`tcp` 子表并列，别误当成子键。

**binder.when**：表，键包括 `ips_policy_id`（`0:max32`）、`vlans`（`PT_BIT_LIST` 范围 `4095`）、`nets / src_nets / dst_nets`（`PT_ADDR_LIST`）、`proto`（枚举 `any | ip | icmp | tcp | udp | user | file`）、`ports / src_ports / dst_ports`（`PT_BIT_LIST` 范围 `65535`）、`intfs / src_intfs / dst_intfs`、`groups / src_groups / dst_groups`、`addr_spaces`、`tenants`（字符串）、`role`（枚举 `client | server | any`，默认 `any`）、`service`（字符串），见 `bind_module.cc` 第 67 至 130 行。误配后果：`end()` 第 388 至 411 行明确四组互斥——`nets` 不能与 `src_nets`/`dst_nets` 同用，`ports` 不能与 `src_ports`/`dst_ports` 同用，`intfs`、`groups` 同理，违反即 `ParseError` 返回 false；`vlans` / `ports` 是位列表，写法要按位集合语义。

**binder.use**：表，键包括 `action`（枚举 `reset | block | allow | inspect`，默认 `inspect`）、`file / inspection_policy / ips_policy`（策略文件，三者互斥，见第 207 至 219 行 `add_policy_file`）、`service`、`type`、`name`。误配后果：策略绑定（`file` 等）时不能同时给 `service / type / name` 或把 `action` 改成非 `inspect`，否则 `ParseError("Policy bindings cannot specify any other use options")`；普通绑定里只给 `name` 不给 `type` 会报 `Missing binding type for name`；`type` 必须是已注册且 `is_bindable()` 的模块，否则 `Can't bind to unknown type`。`role` 默认 `any`，绑定顺序敏感，兜底 `{ use = { type = 'wizard' } }` 必须放最后（见 04-02）。

### 4. 典型示例

下面演示用 `--help-module` 与 `--dump-defaults` 查参数权威取值，再用一段 Lua 配置把 `stream`、`stream_tcp`、`normalizer`、`binder` 落到文件，最后 `-T` 校验。命令不进入在线抓包，避免权限与 DAQ 干扰。

```bash
cd upstream_src/snort3/snort3-master
snort --help-module stream_tcp 2>&1 | head -50
snort --dump-defaults stream 2>&1 | head -30
snort -c lua/snort.lua -T --warn-conf-strict 2>&1 | head -30
```

`--dump-defaults` 会以 Lua 形式打印模块默认值。下面给出示例输出，示例输出，具体格式需对照实际版本核验。

```text
stream =
{
    held_packet_timeout = 1000,
    ip_frags_only = false,
    max_flows = 476288,
    prune_flows = 10,
    pruning_timeout = 30,
    require_3whs = -1,
    drop_stale_packets = false,
    ip_cache = { idle_timeout = 180 },
    icmp_cache = { idle_timeout = 180 },
    tcp_cache = { idle_timeout = 3600 },
    udp_cache = { idle_timeout = 180 },
    user_cache = { idle_timeout = 180 },
    file_cache = { idle_timeout = 180 }
}
stream_tcp =
{
    policy = 'bsd',
    max_pdu = 16384,
    reassemble_async = true,
    session_timeout = 180,
    embryonic_timeout = 30,
    idle_timeout = 3600
}
```

逐行判读如下，合计超过 150 字。`stream =` 段是 `src/stream/base/stream_module.cc` 里 `s_params` 的默认值回显：`held_packet_timeout = 1000` 单位为毫秒，`max_flows = 476288` 是修剪前并发流上限，`prune_flows = 10` 与 `pruning_timeout = 30` 决定修剪节奏，三者联动，改一个往往要复核另外两个。`require_3whs = -1` 表示始终跟踪 midstream 会话，若改成 0 会让所有未见三次握手的流被拒，非对称路由环境会大面积漏检；注意 `stream_tcp` 段里还有一个同名 `require_3whs`，两者独立。`drop_stale_packets = false` 说明默认不因时间戳过旧丢包，历史 pcap 回放较安全。六张 `*_cache` 表的 `idle_timeout` 里，`tcp_cache = 3600` 明显长于其余五张的 `180`，这是 TCP 长连接特性使然；它与 `stream_tcp.idle_timeout = 3600` 默认值一致，若只改其中一处会造成缓存层与会话层淘汰节奏错位，是常见误配。`stream_tcp` 段回显里 `policy = 'bsd'` 是 `TCP_POLICIES` 的默认项，`max_pdu = 16384` 落在 `1460:32768` 合法区间内，`reassemble_async = true` 表示默认异步重组；`session_timeout = 180`、`embryonic_timeout = 30`、`idle_timeout = 3600` 三个超时语义不同，半开超时最短、空闲超时最长，符合 TCP 状态生命周期。把这份输出与自己的 `snort.lua` 做 diff，是确认「我到底覆盖了哪些键」最可靠的办法；再配合 `-T --warn-conf-strict`，任何拼错的键（例如把 `max_pdu` 写成 `max_pdu_size`）都会被报为未识别元素。

再给一段把本篇四类参数写全的配置片段，键名与取值均以各 `*module.cc` 为准；`binder` 兜底项放最后。

```lua
stream = { max_flows = 476288, prune_flows = 10 }
stream_tcp = { policy = 'bsd', max_pdu = 16384,
               session_timeout = 180, idle_timeout = 3600 }
stream_ip = { policy = 'linux', max_frags = 8192 }
stream_udp = { session_timeout = 30 }
normalizer = { tcp = { ips = true, ecn = 'off' }, ip4 = { trim = false } }
binder = {
    { when = { proto = 'tcp', ports = '53', role = 'server' },
      use = { type = 'dns' } },
    { when = { service = 'http' }, use = { type = 'http_inspect' } },
    { use = { type = 'wizard' } }
}
```

### 6. 版本差异

参数体系最根本的代际差异是 Snort 2 的 `preprocessor` 配置（如 `stream5`、`frag3`）与 Snort 3 的 `Module` + `Parameter` 表驱动配置完全不同，键名、默认值、分层方式都不通用；`tools/snort2lua/` 只是格式转换辅助，不等于 `stream5_*` 能直接映射到 `stream_tcp.*`。本篇全部键名来自各 `*module.cc` 的 `static const Parameter s_params[]`，`Parameter::Type` 与范围语法来自 `src/framework/parameter.h`，不同快照可能增删键或改默认值，一律以这些文件为准，需对照实际版本核验。

同一 master 快照内也有明确的演进痕迹：`stream_module.cc` 第 149 至 152 行的 `footprint` 键包在 `#ifdef REG_TEST` 里，第 127 至 131 行的 `allowlist_cache.test_force_enable` 同样只在 REG_TEST 构建出现，且注释写「never set in production」；`config.cmake.h.in` 第 88 至 92 行还显示 `ALLOWLIST_MOVE_ON_EXCESS` 在 REG_TEST 下被无条件补定义，与 04-01 的构建选项联动。这说明「调试构建里看到的键」不一定在生产二进制里存在，导出默认值时必须标明构建变体。`tcp_module.cc` 里 `queue_limit`、`small_segments` 等子表，以及 `bind_module.cc` 里 `when` 的 `tenants`、`addr_spaces` 等较新条件，键名需对照实际版本核验。能力边界跨版本一致：加密载荷不可见，应用识别依赖 inspector / binder / wizard；抓包依赖独立 libdaq / DAQ3；Snort 不是防火墙；线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」；性能数字一律「需在目标机型实测」；许可按 GPLv2 加 Talos 规则集独立许可。04-05 续讲协议 inspector 参数，本篇不重列；流重组机制写「原理见 06-05」，归一化写「原理见 06-03」，绑定与识别写「原理见 06-04」。

迁移时建议三步：用 `snort --help-module <模块>` 与 `--dump-defaults <模块>` 导出目标版本的权威键集与默认值；用 `-T --warn-conf-strict` 暴露未知键；用 `--dump-config-text` 复核覆盖后的实际生效值。结构体字段写「字段见 05-04」，模块目录索引写「模块见 07-04」。

### 7. 常见误用与调试

第一类是同名键改错对象。`stream.require_3whs` 与 `stream_tcp.require_3whs` 是两个独立键，`stream.tcp_cache.idle_timeout` 与 `stream_tcp.idle_timeout` 同样各自生效，默认值虽都是 3600 与 -1，但改一处不影响另一处；`stream_ip.min_ttl` 与 `network.min_ttl`（04-03）也分属不同模块。排查「改了参数没反应」时，先用 `--dump-config-text` 看实际落到哪个 fqn，再回头改。

第二类是默认值语义记反。`stream_ip.max_overlaps = 0` 帮助文本写明「0 is unlimited」，不是「禁止重叠」；`stream_tcp.max_window = 0`、`flush_factor = 0`、`queue_limit.count = 0` 等 0 值的确切语义需对照实际版本核验，别一律当成「关闭」或「零容量」。`normalizer` 的键默认几乎全 `false`、`ips` 默认 `true`、`ecn` 默认 `off`，而 `begin()` 进入 `normalizer.ip4` / `normalizer.tcp` 表时还会自动置位基础项，因此「写了表」与「逐键设 false」不等价，属于源码里真实的隐式行为，需对照实际版本核验。

第三类是 binder 互斥与顺序错误。`end()` 第 388 至 411 行明确 `nets` 与 `src_nets`/`dst_nets`、`ports` 与 `src_ports`/`dst_ports`、`intfs` 与 `src_intfs`/`dst_intfs`、`groups` 与 `src_groups`/`dst_groups` 四组互斥，违反即 `ParseError`；策略绑定（`file / inspection_policy / ips_policy`）不能混 `service / type / name`，只给 `name` 不给 `type` 会报 `Missing binding type`；兜底 `{ use = { type = 'wizard' } }` 放中间会截断后续绑定。第四类是策略与协议不匹配：`stream_tcp.policy` 默认 `bsd`、`stream_ip.policy` 默认 `linux`，若被保护主机是 Windows 或 Solaris 而没改策略，重叠段 / 分片的解释与目标系统不一致，规避流量可能漏报；枚举顺序在 `src/stream/stream.h` 注释里要求与内部 enum 一致，不要按字面排序猜。

第五类是忽略构建变体与能力边界：REG_TEST 构建才有的 `footprint`、`test_force_enable` 别写进生产配置；`allowlist_cache.enable` 依赖 DAQ WHITELIST verdict，`apply_daq_capability_gate` 在不支持时会 WARNING 并禁用，属可选优化；`normalizer.tcp.block` 只在内联模式有意义，IDS 旁路只告警不丢弃；不要指望 inspector 读到加密明文。第六类是性能纪律：`max_flows`、`max_pdu`、`max_bytes`、各类超时的调整都会改变吞吐与内存特征，任何 pps、丢包率、内存占用结论标注「需在目标机型实测」，不给绝对值，基准方法见 08-01、调优见 08-02。排错时按「字段见 05-04 ｜ 原理见 06-05 ｜ 模块见 07-04」分头查证，配合 `--warn-conf-strict` 与 `--dump-defaults` 通常能快速收敛。

## 04-05 inspector 配置参数全集（二）：http、tls、dns、ftp 等协议

### 1. 本篇定位与覆盖范围

本篇是 04 册「参数与 API 手册」中服务与协议类 inspector 参数字典的第二篇，紧接 04-04 的 stream、tcp、normalizers、binder 一族，专门收录面向应用层协议的 inspector 参数。04 册整体是全集中 CMake 构建选项、`snort.lua` 全部段、DAQ 与 inspector 参数、规则关键字、命令行与 Lua 配置 API、shell 控制以及返回码的唯一权威源，其余各册只给本场景最小必要配置并写「完整参数见 04-xx」，不得重列全集。本篇覆盖的真实源码目录集中在 `src/service_inspectors/`，包括 `http_inspect/`、`http2_inspect/`、`ssl/`、`dns/`、`ftp_telnet/`、`smtp/`、`imap/`、`pop/`、`ssh/`、`dce_rpc/`、`wizard/`，并顺带给出 `gtp/`、`netflow/`、`sip/`、`socks/`、`rpc_decode/` 与 `cip/`、`dnp3/`、`modbus/`、`mms/`、`opcua/`、`s7commplus/`、`iec104/` 等工控协议 inspector 的参数定位方式；端口绑定接口落在 `src/network_inspectors/binder/bind_module.cc`。事实基准统一写「上游 master 快照（2026-11 抓取）」；`CMakeLists.txt` 与 `ChangeLog` 里的版本字样只作核验依据，具体版本号以二者为准，需对照实际版本核验，本套资料不把具体版本号抄进正文。

必须先划清边界。本篇只给每个参数的「名称 / 取值 / 默认值 / 作用 / 误配后果」，不解释 Lua 表如何被解析成模块配置、不展开 `Module`、`Inspector` 或任何结构体字段、不讲述协议解析状态机与事件发布流程；这些内容分别归口到「字段见 05-04 ｜ 原理见 06-10 ｜ 模块见 07-03」。参数能否生效有两个前提：一是对应模块已按 04-01 的 `STATIC_INSPECTORS` 等静态链接开关编进二进制，二是该模块在 `lua/snort.lua` 里被正确声明，且 `binder` 把流量绑定到它。只写一段 `http_inspect = { }` 而不做 `binder` 绑定，配置自检不会报错，但运行期 HTTP 流量不会进入该 inspector，表现为「规则里的 HTTP sticky buffer 永远匹配不到」，这是本篇最典型的误配。

还要守住贯穿全册的能力边界。Snort 3 是相对 Snort 2 重写的全新 C++ 实现，配置改为 Lua（`lua/snort.lua`、`lua/snort_defaults.lua`），不兼容 Snort 2 的 `snort.conf` 与插件 ABI，`tools/snort2lua/` 只是格式转换辅助工具；抓包依赖独立 libdaq / DAQ3，本族 inspector 不负责收包；内联 IPS 的 drop / block 通过 DAQ verdict 反馈，Snort 本身不是防火墙、不做 IP 转发；加密流量载荷不可见，`ssl` inspector 能拿到的是握手元数据、证书与版本状态一类信息（字段名需对照实际版本核验），绝不能宣称能读到 HTTPS 明文正文；应用识别依赖 inspector / binder / wizard 协同；Hyperscan 是可选 search_engine 加速，缺失时回退 `src/search_engines/` 下其他多模式匹配实现；引擎按 GPLv2（顶层 `COPYING` / `LICENSE`）授权，Talos 规则集另有独立许可约束（`lua/talos.lua`）。性能与容量类结论一律标注「需在目标机型实测」。

本篇参数的组织形式是：每个 `*_module.cc` 里有一张 `static const Parameter s_params[]` 表，模块构造时以 `Module(s_name, s_help, s_params)` 注册；`Parameter` 的类型、范围、默认值与帮助文本由 `src/framework/parameter.h`、`src/framework/module.h` 定义。因此第 2 节按模块给全集索引表，第 3 节按族逐项详解，第 4 节给一段可复现的 Lua 配置与 `--help-config` / `-T` 输出判读，第 5 节给按场景速查，第 6 节讲代际与版本差异，第 7 节汇总误用与调试。凡本快照里能确认的参数名、范围、默认值，均逐条对照对应 `*_module.cc` 核验；凡未逐条展开的模块或子表，一律标注「需对照实际版本核验」并给出可定位目录，绝不凭印象补值。协议 inspector 的参数从 Lua 声明、binder 绑定、模块校验到运行时生效的链路见图 04-05-01。

### 3. 逐项详解

以下按族给出每个参数的「名称 / 取值 / 默认值 / 作用 / 误配后果」。源码位置统一相对 `upstream_src/snort3/`，均落在 `src/service_inspectors/` 下对应目录。凡涉及解析行为的结论只描述「参数控制什么」，机制本身写「原理见 06-10」，字段写「字段见 05-04」。

**http_inspect 深度与长度族**：`request_depth`、`response_depth` 默认 `-1`，表示不限制请求与响应方向的检测深度；收窄后超出深度的载荷不再供检测选项使用，表现为「明明有特征却匹配不到」。`partial_depth_header`、`partial_depth_body` 默认 `0`，控制部分头部与部分消息体的深度，需要按需开启。`maximum_host_length` 默认 `-1`、`maximum_header_length` 默认 `4096`、`maximum_headers` 默认 `200`、`maximum_chunk_length` 默认 `4294967295`、`maximum_pipelined_requests` 默认 `99`，分别约束 Host、单头部行、头部条数、分块长度与流水线请求数；把 `maximum_header_length` 设得过小会把合法长头当作异常，设得过大则扩大内存开销，具体容量「需在目标机型实测」。`maximum_header_value_length` 默认 `0` 表示不单独限制头部值长度。

**http_inspect 归一化与编码族**：`unzip` 默认 `true`，负责解压 gzip / deflate 内容；`normalize_utf` 默认 `true`、`utf8` 默认 `true`、`utf8_bare_byte` 默认 `false`、`percent_u` 默认 `false`、`iis_unicode` 默认 `false`、`iis_unicode_code_page` 默认 `1252`、`iis_double_decode` 默认 `true`、`iis_unicode_map_file` 指向映射文件、`backslash_to_slash`、`plus_to_space`、`simplify_path` 三者默认 `true`，`oversize_dir_length` 默认 `300`。误配后果集中在「规则写的是归一化后的形态、配置却关掉了对应归一化」，尤其关掉 `simplify_path` 会让路径穿越类规则失效；`iis_unicode` 打开却漏配 `iis_unicode_map_file`，映射不生效。这些是纯参数开关，字段与内存布局写「字段见 05-04」。

**http_inspect 解压、脚本与请求族**：`decompress_pdf`、`decompress_swf`、`decompress_zip`、`decompress_vba`、`decompress_brotli` 默认均为 `false`，只对被识别的文件类型生效；`max_mime_attach` 默认 `5` 限制 MIME 附件拆解数，`max_expansion_ratio` 默认 `100` 限制解压膨胀比，二者与资源耗尽防护相关，容量结论「需在目标机型实测」。`script_detection` 默认 `false`、`normalize_javascript` 默认 `false`、`max_javascript_whitespaces` 默认 `200`，控制脚本检测与 JS 归一化；`xff_headers` 默认内置 `x-forwarded-for true-client-ip` 一类头名，用于取真实客户端地址。`allowed_methods`、`disallowed_methods`、`allowed_content_type`、`max_request_size` 默认 `0`、`max_request_line_length` 默认 `0`、`max_expansion_ratio`、`request_body_app_detection` 默认 `true`、`print_amount` 默认 `1200`、`print_hex`、`show_pegs` 默认 `true`、`show_scan`、`test_input`、`test_output` 属诊断与调试参数，其中 `test_input` / `test_output` 只应出现在测试构建，勿带入生产配置。

**http2_inspect**：`concurrent_streams_limit` 取值 `100:1000`、默认 `100`，限制单条 HTTP/2 流的并发流数；`rst_stream_limit` 取值 `10:1000`、默认 `100`，是触发告警的 RST_STREAM 帧阈值；`settings_max_frame_size` 取值 `16384:16777215`、默认 `16777215`，限定 SETTINGS 帧声明的最大帧长。三者都是 `Http2Module::http2_params[]` 里的条目，`REG_TEST` 构建下另有 `test_input` / `test_output`。误配后果：把 `concurrent_streams_limit` 调得过大将放宽资源占用，把 `rst_stream_limit` 调得过小会产生大量误报，均「需在目标机型实测」。

**ssl**：`trust_servers` 默认 `false`，控制是否信任服务端在握手之后的数据判为已加密；`max_heartbeat_length` 默认 `0` 表示不限制心跳长度，设为非零可约束异常心跳。这里的模块名是 `ssl`，`lua/snort.lua` 里写 `tls` 不会命中该模块，报「can't find tls」一类错误（见 04-08）。规则侧的 `ssl_version`（取值 `sslv2`、`sslv3`、`tls1.0`、`tls1.1`、`tls1.2` 及取反形式）与 `ssl_state`（取值 `client_hello`、`server_hello`、`client_keyx`、`server_keyx`、`unknown` 及取反形式）定义在 `src/service_inspectors/ssl/ips_ssl_version.cc`、`ips_ssl_state.cc`，属 04-06 的规则关键字，不在本参数表。必须再次强调：加密载荷不可见，本 inspector 只提供握手元数据与证书类信息，字段名需对照实际版本核验，不能据此读明文正文。

**dns**：本快照 `dns_module.cc` 只暴露 `publish_response`，类型 `PT_BOOL`、默认 `false`，作用是解析并发布 DNS 响应事件。默认关闭意味着只处理查询侧；打开后响应侧事件进入事件总线，会增大事件量。DNS 规则关键字与响应事件的字段定义写「字段见 05-08 ｜ 原理见 06-10」。

**ftp_telnet**：`ftp_client` 的 `bounce` 默认 `false`、`bounce_to` 是 `PT_LIST` 子表（含 `address` 默认 `1.0.0.0/32`、`port` 默认 `20`、`last_port` 可选）、`max_resp_len` 默认 `4294967295`、`telnet_cmds` 默认 `false`、`ignore_telnet_erase_cmds` 默认 `false`；`ftp_server` 在 `lua/snort_defaults.lua` 里以 `default_ftp_server` 预置表引用，键名需对照该文件核验。`telnet` 的 `ayt_attack_thresh` 默认 `-1`、`check_encrypted` 默认 `false`、`encrypted_traffic` 默认 `false`、`normalize` 默认 `false`。误配后果：`bounce` 打开却未配 `bounce_to` 白名单，正常 FTP 数据通道可能被误判；`telnet_cmds` 关闭会让控制通道里的转义序列漏检。

**smtp / imap / pop**：`smtp` 的 `normalize` 是 `PT_ENUM`，取值 `none | cmds | all`、默认 `none`；`max_command_line_len` 默认 `512`、`max_header_line_len` 默认 `1000`、`max_response_line_len` 默认 `512`、`max_auth_command_line_len` 默认 `1000`、`email_hdrs_log_depth` 默认 `1464`；`b64_decode_depth`、`qp_decode_depth`、`uu_decode_depth`、`bitenc_decode_depth` 默认均为 `-1`；`decompress_pdf` / `decompress_swf` / `decompress_zip` / `decompress_vba` 默认 `false`；`ignore_data`、`ignore_tls_data` 默认 `false`；`log_email_hdrs`、`log_filename`、`log_mailfrom`、`log_rcptto` 默认 `false`；`xlink2state` 默认 `alert`；`valid_cmds`、`invalid_cmds`、`auth_cmds`、`data_cmds`、`binary_data_cmds`、`normalize_cmds`、`alt_max_command_line_len` 为字符串或列表型参数。`imap` 与 `pop` 共享 `b64_decode_depth`、`bitenc_decode_depth`、`qp_decode_depth`、`uu_decode_depth` 与各 `decompress_*` 开关；`pop` 的完整键名需对照 `src/service_inspectors/pop/pop_module.cc` 核验。误配后果：`ignore_tls_data` 打开后 TLS 之后的数据不再解析，邮件体相关规则全部失效；各 `*_decode_depth` 设 `-1` 表示不限制，设过小会截断附件检测。

**ssh**：`max_encrypted_packets` 默认 `25`、`max_client_bytes` 默认 `19600`、`max_server_version_len` 默认 `80`。三者都是启发式阈值，用于判断会话是否进入加密阶段；调大 `max_encrypted_packets` 会延后判定，调小可能把正常密钥交换误判为异常，取值「需在目标机型实测」。

**dce_rpc 族**：`dce_tcp` / `dce_udp` / `dce_smb` 共享 `limit_alerts`（默认 `true`）、`disable_defrag`（默认 `false`）、`max_frag_len`（默认 `65535`）；`dce_tcp` 与 `dce_smb` 另有 `reassemble_threshold`（默认 `0`）、`policy` 枚举、`max_frag_reassemblies`；`dce_smb` 还有 `smb_fingerprint_policy`（默认 `none`）、`smb_max_chain`（默认 `3`）、`smb_max_compound`（默认 `3`）、`valid_smb_versions`（`v1 | v2 | all`，默认 `all`）、`smb_file_depth`（默认 `16384`）、`smb_max_credit`（默认 `8192`）、`smb_max_file_chunks`（默认 `1024`）、`memcap`（默认 `8388608`）、`smb_legacy_mode`、`smb_invalid_shares` 等；`dce_udp` 另有 `max_activity_trackers`（默认 `16`）、`max_frag_tracker_nodes`（默认 `1024`）。`dce_http_proxy` / `dce_http_server` 的完整键名需对照 `src/service_inspectors/dce_rpc/` 下对应 `*_module.cc` 核验。

**wizard**：`wiz_module.cc` 暴露 `hexes`、`spells` 两个 `PT_LIST` 与 `curses` 一个 `PT_MULTI`（取值含 `dce_smb | dce_udp | dce_tcp | mms | opcua | s7commplus | socks | sslv2`），以及 `max_search_depth`（`0:65535`，默认 `8192`）；子表 `wizard_hex_param` 含 `hex`、`service`、`proto`（`tcp | udp | any`，默认 `any`）、`to_server`、`to_client`，`wizard_spell_param` 含 `spell`、`service`、`proto`、`to_server`、`to_client`。wizard 用端口与 magic 启发式识别服务，属于「应用识别依赖 inspector / binder / wizard」的一环，机制写「原理见 06-04」。

**其他协议族与 binder 接口**：`gtp` 的 `version` 默认 `2`、`messages` / `infos` 为列表；`netflow` 的 `update_timeout` 默认 `3600`、`device_ip`、`dump_file`、`flow_memcap`、`template_memcap`；`dnp3` 的 `check_crc` 默认 `false`、`zero_payload_packet_limit` 默认 `5`；`cip` 的 `max_cip_connections` 默认 `100`、`unconnected_timeout` 默认 `300`；`modbus` / `s7commplus` 的 `small_pdus_limit` 分别默认 `32` / `64`；`socks`、`sip`、`rpc_decode`、`mms`、`opcua`、`iec104` 的完整键名需对照各自模块目录核验。端口绑定接口在 `src/network_inspectors/binder/bind_module.cc`：`when` 表含 `nets`、`src_nets`、`dst_nets`、`proto`（`any | ip | icmp | tcp | udp | user | file`）、`ports`、`src_ports`、`dst_ports`、`vlans`、`intfs`、`role`（`client | server | any`）、`service`、`tenants`、`addr_spaces`、`groups` 等；`use` 表含 `action`（`reset | block | allow | inspect`，默认 `inspect`）、`type`、`name`、`service`、`inspection_policy`、`ips_policy`、`file`。binder 的完整参数归 04-04，本篇只用它说明「协议 inspector 如何被流量命中」，不重列全集。

**参数查询命令**：`--help-module <module>` 打印模块描述，`--help-config <module>` 打印该模块全部参数与范围，`--dump-defaults <module>` 以 Lua 格式导出默认值，`--help-limits` 打印 `max*` 上界，这四条命令是核对键名与默认值最可靠的手段，具体输出格式需对照实际版本核验。

### 4. 典型示例

下面给一段最小可自检的 Lua 配置：先声明网络变量，再写协议 inspector 表，最后用 `binder` 把 TCP 端口绑定到对应 inspector。随后用 `--help-config` 反查参数、`snort -T` 做配置自检。所有键名均取自第 2 节核验过的真实参数。

```lua
HOME_NET = '192.168.1.0/24'
EXTERNAL_NET = 'any'

http_inspect = { }
http2_inspect = { concurrent_streams_limit = 200 }
ssl = { trust_servers = true }
dns = { publish_response = true }
ssh = { max_encrypted_packets = 30 }

binder = {
    { when = { proto = 'tcp', ports = '80 8080' },
      use = { type = 'http_inspect' } },
    { when = { proto = 'tcp', ports = '443' },
      use = { type = 'ssl' } },
    { when = { service = 'http2' },
      use = { type = 'http2_inspect' } },
    { when = { proto = 'tcp', ports = '53' },
      use = { type = 'dns' } },
}
```

```bash
snort -c lua/snort.lua --help-config http_inspect \
    | grep -E "request_depth|unzip|normalize_utf|maximum_headers"
snort -c lua/snort.lua --dump-defaults ssl
snort -c lua/snort.lua -T
```

下面给出 `--help-config` 与 `-T` 的示例输出，示例输出，具体格式需对照实际版本核验。

```text
--help-config http_inspect 摘录
request_depth: -1  (int, -1:max53)
unzip: true  (bool)
normalize_utf: true  (bool)
maximum_headers: 200  (int, 0:65535)

--dump-defaults ssl 摘录
ssl = { trust_servers = true, max_heartbeat_length = 0 }

-T 配置自检结尾
Snort successfully validated the configuration (with 0 warnings).
```

逐行判读如下，合计超过 150 字。第一段 `--help-config http_inspect` 摘录里，`request_depth: -1` 表明我们没有改动请求深度，仍是不限制；`unzip: true` 是 `http_inspect` 的默认值，说明 gzip 内容会被解压后再供规则匹配；`normalize_utf: true` 与 `maximum_headers: 200` 都是默认值，说明这段配置用的是模块自带默认，而不是我们手填。这里的 `-1` 与 `max53` 只是范围记法，具体上界要用 `--help-limits` 复核，不能凭字面推断成一个固定整数。第二段 `--dump-defaults ssl` 摘录显示 `trust_servers = true`，这是我们在 Lua 里显式写进去的值，`max_heartbeat_length = 0` 是模块默认值；如果这里打印的仍是 `false`，多半是 `ssl = { }` 在文件后面又被写了一次，把前面设置覆盖掉，这类覆盖错误见 04-08。第三段是 `src/main.cc` 里 `just_validate()` 分支打印的真实文本，`Snort successfully validated the configuration (with 0 warnings).` 中的 `0` 是警告计数，`-T` 只做配置与规则加载自检、不抓包、不进收包循环，所以看到这一行只能证明「配置语法与规则可加载」，不能证明在线抓包与告警链路通；若计数不为 0，应回头用 `--warn-all` 打开全部警告再逐条定位。整段命令的闭环是「写表 → 绑定 → 反查默认值 → 自检」，任何一步缺了 `binder` 绑定，`-T` 仍可能通过，但运行期流量不进 inspector。

### 5. 速查表

按场景反查该配哪些参数，见下表。表中「保持默认」表示写 `模块名 = { }` 即可，完整键名用 `--help-config <module>` 核对；所有资源类结论标注「需在目标机型实测」。

| 场景 | 建议参数 | 需额外准备 | 风险提示 |
|---|---|---|---|
| 只做 HTTP 基础检测 | http_inspect = { } + binder 绑 80 | 规则用 HTTP sticky buffer | 别忘 binder 绑定 |
| 需要看 gzip 内容 | 保持 unzip 默认 true | 规则写解压后形态 | 关掉即匹配不到 |
| 路径穿越检测 | simplify_path / backslash_to_slash 保持 true | 归一化后的 URI 规则 | 别随意关归一化 |
| HTTP/2 流控异常 | http2_inspect 三项阈值 | binder 绑 http2 服务 | 调小易误报 |
| 只关心 TLS 握手 | ssl = { trust_servers = false } | ssl_version / ssl_state 规则 | 读不到明文正文 |
| DNS 响应侧分析 | dns = { publish_response = true } | 响应侧事件消费者 | 事件量上升 |
| 邮件附件检测 | smtp 各 *_decode_depth 与 decompress_* | MIME 规则与文件策略 | 深度截断漏检 |
| FTP bounce 检测 | ftp_client.bounce = true + bounce_to | 端口白名单 | 漏配白名单误判 |
| 工控协议解析 | cip / dnp3 / modbus 对应表 | binder 绑工控端口 | 键名需核验 |
| 参数记不准 | --help-config / --dump-defaults | 目标模块名 | 别凭印象补键名 |

### 6. 版本差异

最根本的代际差异是配置体系：Snort 2 用 `snort.conf` 里的 `preprocessor http_inspect` 等指令，Snort 3 改为 Lua 表与模块参数，二者参数名、默认策略、插件 ABI 都不通用，`tools/snort2lua/` 只做格式转换辅助，不等于参数可直接沿用。因此「把 Snort 2 预处理器的 `inspect_uri_only`、`unicode_map` 之类键照搬进 `http_inspect = { }`」是错误做法，应以 `snort --help-config http_inspect` 与 `src/service_inspectors/http_inspect/http_module.cc` 的 `s_params[]` 为准，需对照实际版本核验。规则关键字与 Snort 2 有差异，不能宣称完全兼容（见 04-06）。

上游 master 快照内部演进同样要谨慎：`http2_inspect` 的 `test_input` / `test_output` 只在 `REG_TEST` 编译宏下出现，`wizard` 的 `curses` 列表随支持的服务增减，`ssl` 目录里 `ips_ssl_version.cc` 的选项集合会随 TLS 版本演进而变，`pop/`、`dce_http_proxy/` 等模块的完整键名本快照未逐条展开；因此凡本表未列出的参数一律写「需对照实际版本核验」并给出 `src/service_inspectors/` 下可定位目录。能力边界不随版本改变：Lua 配置全新实现、抓包依赖独立 libdaq / DAQ3、加密载荷不可见、应用识别依赖 binder / wizard、Hyperscan 可选加速、许可按 GPLv2 且 Talos 规则集独立许可、线程 / 进程模型以实际版本为准且禁止断言「默认 N 线程」。跨版本迁移建议做三件事：用 `--dump-defaults` 导出旧版本全部默认值存档，用 `--help-config` 逐模块 diff，再在目标机型重跑 `-T` 与 `snort --help` 验证。模块能力与目录清单见 07-03，协议解析机制见 06-10，二者均「完整参数见 04-05」，不得重列全集。

### 7. 常见误用与调试

第一类误用是「只声明表、不做 binder 绑定」。现象是配置自检通过、规则也加载了，但 HTTP 相关规则一条都不告警。根因是 `binder` 没把 80 / 8080 端口或 `http2` 服务绑到 `http_inspect` / `http2_inspect`，流量根本没进 inspector。验证顺序应是先看 `lua/snort.lua` 里 `binder` 的 `when.ports` / `when.service` 与 `use.type`，再用 `snort --list-buffers` 确认目标 buffer 可用，最后才怀疑规则。第二类是把 `ssl` 写成 `tls`、把 `http2_inspect` 写成 `http2`：模块名以 `--list-modules` 与 `src/service_inspectors/` 目录为准，写错会报「can't find tls」一类配置错误（见 04-08）。

第三类是参数名与取值范围凭印象补值。`--help-config <module>` 给出键名、类型与范围，`--help-module <module>` 给出模块描述，`--dump-defaults <module>` 给出默认 Lua，`--help-limits` 给出 `max*` 上界；把值写到范围外会报「invalid x.y = z」，把标量赋给需要表的模块会报「can't find x」，把 `x = { }` 写在有效配置之后会静默覆盖前面的设置，这三类错误文本都收集在 `doc/user/errors.txt`。第四类是误以为加密流量能读明文：SSL/TLS inspector 只在握手与证书元数据层面工作，任何「提取 HTTPS 正文内容」的规则都不成立，字段名需对照实际版本核验。

第五类是忽略资源类参数的联动。`decompress_*`、`max_mime_attach`、`max_expansion_ratio`、`dce_smb.memcap` 与各 `*_decode_depth` 共同决定解析工作量，任一放大都会改变内存与 CPU 特征，吞吐、pps、内存占用一律标注「需在目标机型实测」，不给绝对值；基准方法见 08-01，调优见 08-02。第六类是把 `test_input` / `test_output` 或 `REG_TEST` 专属键带进生产配置，这类键在普通构建里可能根本不存在。排错时把问题按「字段见 05-04 ｜ 原理见 06-10 ｜ 模块见 07-03」分头查证：先看参数是否写对，再看绑定是否命中，最后才怀疑解析机制，通常能快速收敛。

### 3. 逐项详解

以下按族给出每个关键字的「名称 / 语法 / 作用 / 误配后果」，注册位置统一相对 `upstream_src/snort3/` 的 `src/ips_options/`（动作在 `src/actions/`）。机制只描述「关键字做什么」，编译与求值写「原理见 06-06 / 06-08」，字段写「字段见 05-04 / 05-06」。

**动作族**：`alert`、`block`、`drop`、`log`、`pass`、`reject`、`react`、`rewrite`、`file_id` 由 `src/actions/act_*.cc` 注册，`src/actions/ips_actions.cc` 汇总，`src/managers/action_manager.cc` 装配。规则头第一个 token 必须是其中之一，写错会报 `unknown rule action`、`missing rule action` 或 `no active IPS policy for rule action`（均见 `src/parser/parse_rule.cc`）。`pass` 默认先于 `alert` 求值，要反过来需命令行 `--alert-before-pass`（见 04-07）。`block` / `drop` / `reject` / `react` 在内联模式才形成实际丢弃，IDS 旁路只告警；这与「Snort 不是防火墙、不做转发」一致。特别注意 `act_replace.cc` 的动作名是 `rewrite`，而 `ips_replace.cc` 的 `replace` 是规则选项，把二者混为一谈会写错规则头。

**规则头与元数据**：标准头形如 `alert tcp $HOME_NET any -> $EXTERNAL_NET 80`，其后紧跟一对圆括号包裹的检测选项，协议写错报 `bad protocol`，端口写错报 `bad ports`，方向符写错报 `illegal direction specifier`（见 `parse_rule.cc`）。`msg`、`sid`、`rev` 构成事件身份，`gid` 默认生成器由 `ips_gid.cc` 限定 `1:8129`；`GID %u SID %u in rule duplicates previous rule` 与 `%u:%u duplicates previous rule. Using revision %u.` 是重复规则的报错与告警文本。`classtype`、`priority`（`1:max31`）、`metadata`（通配键值）、`reference`、`rem`、`service`、`target`（`src_ip | dst_ip`）、`enable`（`no | yes | inherit`，默认 `yes`）、`soid`、`so` 都属此族。误配后果：`sid` 重复会让后一条被合并或告警，`priority` 写超范围、`target` 取值拼错都会在 `-T` 阶段暴露。

**content 与修饰符**：`content` 的位置参数 `~data` 是待匹配字节串，支持 `|` 包裹的十六进制片段与文本混写；`nocase`、`fast_pattern`、`fast_pattern_offset`（`0:65535`，默认 `0`）、`fast_pattern_length`（`1:65535`）、`offset`、`depth`、`distance`、`within`、`width`（`8 | 16 | 32`，默认 `8`）、`endian`（`big | little`，默认 `big`）都是 `ips_content.cc` 的 `s_params[]` 条目。误配后果：`distance` 没有前一条 `content` 时相对定位无意义；`fast_pattern` 选得过长或过短会改变快模式构建，规模与性能「需在目标机型实测」；`depth` 小于 `offset + 内容长度` 会永远不匹配。`content` 与 sticky buffer 的先后关系写「原理见 06-08」。

**pcre 与 regex**：`pcre` 的位置参数 `~re` 是 PCRE 表达式，语法细节需对照 `doc/user/params.txt` 与 `src/ips_options/ips_pcre.cc` 核验；`regex` 的位置参数 `~re` 之外还有 `dotall`、`fast_pattern`、`multiline`、`nocase`、`relative`（均见 `ips_regex.cc`）。检测侧 `src/detection/detection_module.cc` 提供 `pcre_enable`（默认 `true`）、`pcre_match_limit`（默认 `1500`）、`pcre_match_limit_recursion`（默认 `1500`）、`pcre_override`（默认 `true`）、`pcre_to_regex`（默认 `false`）、`hyperscan_literals`（默认 `false`）等开关，它们是检测模块的 Lua 参数，不是规则选项，完整取值见 04-02 / 04-04，本篇不重列。误配后果：不可信规则的 `pcre` / `regex` 回溯会放大编译期与运行期开销，规模结论「需在目标机型实测」；`pcre_to_regex` 打开后部分 `pcre` 语义会变，需对照实际版本核验。

**byte 族**：`byte_test` 取 `~count`（`1:10`）、`~operator`、`~compare`、`~offset`，修饰符 `relative`、`big`、`little`、`dce`、`string`、`hex`、`oct`、`dec`、`bitmask`（`0x1:0xFFFFFFFF`）；`byte_jump` 取 `~count`（`0:10`）、`~offset`，修饰符 `relative`、`from_beginning`、`from_end`、`multiplier`（`1:65535`）、`align`（`0:4`）、`post_offset`、`big`、`little`、`dce`、`string`、`hex`、`oct`、`dec`、`bitmask`；`byte_extract` 取 `~count`（`1:10`）、`~offset`（`-65535:65535`）、`~name`，修饰符 `relative`、`multiplier`、`align`、`big`、`little`、`dce`、`string`、`hex`、`oct`、`dec`、`bitmask`；`byte_math` 取 `bytes`（`1:10`）、`offset`、`oper`（`+ | - | * | / | << | >>`）、`rvalue`、`result`，修饰符 `relative`、`endian`（`big | little`）、`dce`、`string`（`hex | dec | oct`）、`bitmask`。用法文档见 `doc/user/byte_test.txt`、`byte_jump.txt`、`byte_extract.txt`、`byte_math.txt`、`byte_options.txt`。误配后果：`dce` 与 `big` / `little` 语义互斥，乱组合会在 `-T` 阶段报 `invalid argument`；`byte_extract` 的 `~name` 未被后续 `byte_test` 引用则变量白取；`string` 的 `hex` / `dec` / `oct` 决定取值解析方式，写错会取到完全不同的数值。

**flow / flowbits / 检测选项**：`flow` 的可选值来自 `ips_flow.cc`：`to_client`、`to_server`、`from_client`、`from_server`、`established`、`not_established`、`stateless`、`no_stream`、`only_stream`、`no_frag`、`only_frag`；`flowbits` 的 `~op` 取值 `set | unset | isset | isnotset | noalert`，`~bits` 是位名，`--no-warn-flowbits` / `--warn-flowbits`（见 04-07）控制「检查但未设置」类警告。`detection_filter` 取 `track`（`by_src | by_dst`）、`count`（`1:max32`）、`seconds`（`1:max32`），作用在规则内限速；`event_filter` / `rate_filter` / `threshold` 一族属配置侧限速，机制见 06-09，键名需对照实际版本核验。`isdataat` 取 `~length` 与 `relative`，`dsize` 取 `~range`，`bufferlen` 取 `~range` 与 `relative`，`tag` 取 `session | host_src | host_dst` 与 `packets` / `seconds` / `bytes`，`sd_pattern` 取 `~pattern` 与 `threshold`，`file_meta` 取 `type` / `id`（`1:1023`）/ `category` / `group` / `version`，`file_type` 取通配字符串。

**协议字段与 sticky buffer**：`flags`、`fragbits`、`ttl`、`tos`、`id`、`ip_proto`、`ipopts`、`seq`、`ack`、`window`、`itype`、`icode`、`icmp_id`、`icmp_seq`、`fragoffset`、`rpc`、`cvs`、`hash`、`luajit` 等直接读包头字段；`ssl_version`（`sslv2`、`sslv3`、`tls1.0`、`tls1.1`、`tls1.2` 及 `!` 取反）与 `ssl_state`（`client_hello`、`server_hello`、`client_keyx`、`server_keyx`、`unknown` 及取反）在 `src/service_inspectors/ssl/` 下注册；`http_uri`、`http_header`、`http_cookie`、`http_method`、`http_client_body`、`http_stat_code`、`http_stat_msg`、`http_version`、`http_param`、`http_num_hdrs` 等 sticky buffer 在 `src/service_inspectors/http_inspect/ips_http_*.cc` 注册，完整清单用 `snort --list-buffers` 核对，需对照实际版本核验。误配后果：sticky buffer 写错、或前置 inspector 未绑定（见 04-05），buffer 为空导致规则永不命中；加密载荷不可见，任何试图在 TLS 正文上做 `content` 的规则都不成立。

**注册与查表**：每个关键字在 `ips_*.cc` 里通过 `IpsApi` 结构注册，`src/managers/ips_manager.cc` 的 `option_begin()` 以 `PluginManager::get_interface(key)` 查表，未命中即 `ParseError("unknown rule keyword: %s.", key)`；`option_set()` 对参数做 `set_arg()` 校验，失败报 `invalid argument %s:%s = %s`；`option_end()` 构造 `IpsOption` 并挂进 option 链，超过 `max_per_rule` 报 `%s allowed only %u time(s) per rule`。`STATIC_IPS_OPTIONS`（见 04-01）未编入时，规则加载会集中报未知关键字。

**关键字核验路径与检测侧边界**：把本篇的关键字表用到生产规则集前，建议走一条固定的核验链。第一步用 `snort --list-builtin` 与 `--list-buffers`（选项定义见 04-07）导出当前二进制真正注册了哪些关键字与 buffer，把结果存档；这一步能提前发现 `STATIC_IPS_OPTIONS=OFF` 造成的成片缺失，比逐条读规则高效得多。第二步用 `--dump-rule-state`、`--dump-rule-meta`、`--dump-rule-deps` 与 `--gen-msg-map` 把规则状态、元信息、依赖与 `gen-msg.map` 导出为结构化文本，供规则管理系统做版本 diff；这些选项同样定义在 `src/main/snort_module.cc`，会隐式置自检标志且不进收包循环（见 04-07）。第三步才把规则文件交给 `snort -T --warn-all`，让 `src/parser/parse_rule.cc` 与 `src/managers/ips_manager.cc` 把 `unknown rule keyword`、`invalid argument`、`duplicates previous rule` 三类文本逐条暴露出来，错误文本与判读见 04-08。三步的顺序不能反：先确认「关键字存在」，再确认「规则可加载」，最后才判断「规则是否命中」。

必须把「规则选项」与「检测侧参数」分开。`detection_filter` 是写在规则括号里的限速选项，`event_filter`、`rate_filter`、`threshold` 一族是配置侧的限速机制（键名需对照实际版本核验，机制见 06-09）；把后者写进规则里会直接报未知关键字。`src/detection/detection_module.cc` 暴露的 `pcre_enable`、`pcre_match_limit`、`pcre_match_limit_recursion`、`pcre_override`、`pcre_to_regex`、`hyperscan_literals`、`offload_limit`、`offload_threads`、`max_continuations_per_flow`、`enable_address_anomaly_checks`、`enable_strict_reduction`、`allow_missing_so_rules`、`global_default_rule_state`、`global_rule_state`、`extend_to`、`service`、`service_extension` 等是检测模块的 Lua 段参数，完整取值归 04-02 / 04-04，本篇不重列；它们决定 `pcre` 的匹配上限、SO 规则缺失时是否放行、服务扩展等行为，是「参数」而非「关键字」。规则里写了 `pcre` 却在 Lua 里把 `pcre_enable` 关掉，或把 `pcre_to_regex` 打开后没同步复核语义，都属于典型的两层配置错位。

用法文档的定位同样要记牢：`doc/user/byte_test.txt`、`byte_jump.txt`、`byte_extract.txt`、`byte_math.txt`、`byte_options.txt`、`params.txt` 是 byte 族与参数语法的官方说明，`doc/user/errors.txt` 收集错误文本样例，`doc/user/features.txt` 与 `concepts.txt` 是术语边界，`doc/user/params.txt` 还给出参数写法的通用约定。凡本篇未逐条给出语法细节的关键字，一律以对应 `src/ips_options/ips_*.cc` 的 `s_params[]` 与 `doc/user/` 为准，需对照实际版本核验。规则编译成 rule tree 与 port group、fast pattern 选择、检测 eval 的求值顺序写「原理见 06-06 / 06-07 / 06-08」，`Rule` / `IpsOption` / `Cursor` 的字段写「字段见 05-04 / 05-05 / 05-06」，模块清单写「模块见 07-06」；本篇始终只给名称、语法、取值与用法，不展开机制与字段。规则集规模、编译期内存与匹配开销一律「需在目标机型实测」，不可信规则的加固见 08-05。

### 4. 典型示例

下面给一条完整、不含任何省略占位的自定义规则，综合用到动作、头部、元数据、content 修饰符、pcre、byte_test、flow 与 detection_filter，随后用 `--rule-to-text` 与 `snort -T` 校验。

```text
alert tcp $EXTERNAL_NET any -> $HOME_NET 8080 ( \
    msg:"WEB probe with length field"; \
    flow:to_server,established; \
    content:"GET "; depth:4; nocase; \
    content:"|0d 0a|"; distance:0; within:64; \
    pcre:"/\/cgi-bin\/[a-z]+\.sh/Ui"; \
    byte_test:1,>,16,0,relative,string,dec; \
    detection_filter:track by_src, count 5, seconds 30; \
    metadata:service http, policy balanced-ips drop; \
    classtype:web-application-attack; priority:1; sid:9000001; rev:1; )
```

```bash
snort -c lua/snort.lua --rule-to-text 'alert tcp any any -> any 80 (msg:"t"; sid:1;)'
snort -c lua/snort.lua -R custom.rules -T --warn-all
```

下面给出 `-T` 加载规则时的示例输出，示例输出，具体格式需对照实际版本核验。

```text
--rule-to-text 输出摘录
alert tcp any any -> any 80 ( msg:"t"; sid:1; rev:0; )

-T 规则加载与自检结尾
Loading custom.rules:
    1 rules loaded
Snort successfully validated the configuration (with 0 warnings).
```

逐行判读如下，合计超过 150 字。第一段 `--rule-to-text` 的输出把一行文本规则回显成规范化形式，`msg:"t"` 被保留，`sid:1` 之后补了 `rev:0`，说明缺省的 `rev` 由解析器填了默认值；这一步只做规则头回显，不证明检测选项正确。第二段是 `-T` 加载片段，`1 rules loaded` 说明 `custom.rules` 被成功读入一条规则，`Snort successfully validated the configuration (with 0 warnings).` 是 `src/main.cc` 里 `just_validate()` 打印的真实文本，`0` 是警告计数。若把示例规则里的 `byte_test` 写成 `byte_test:1,>,16,0,relative,big,dce;`，`big` 与 `dce` 同时出现会在 `ips_manager.cc` 的 `option_set()` 阶段触发 `invalid argument` 一类错误，`-T` 不会打印这行成功文本；若删掉 `--rule` / `-R` 而规则文件又不在 `ips.rules` 的 `include` 链里，`1 rules loaded` 会变成 0，容易误判成「引擎坏了」而其实是规则没被引入。还要提醒：`-T` 只验证语法与可加载，不产生真实告警，规则是否命中要在 03-01 的回放场景里验证；所有规则规模、编译期内存与吞吐结论一律「需在目标机型实测」。

按编写意图反查关键字，见下表。表中「需核验」表示语法细节或键名以 `src/ips_options/` 与 `doc/user/` 实际版本为准。

### 6. 版本差异

规则语言最根本的代际差异是：Snort 3 的规则关键字与 Snort 2 有差异，不能宣称完全兼容。`src/ips_options/` 里 `regex`、`byte_math`、`bufferlen`、`file_meta`、`enable`、`sd_pattern`、`js_data`、`vba_data`、`ber_data`、`ber_skip` 等是本快照可见的关键字，`pcre_to_regex`、`hyperscan_literals` 等检测侧开关也是版本演进产物；Snort 2 里若干关键字在本快照没有对应 `ips_*.cc`，或语义已改。差异点需对照 `src/ips_options/`、`src/parser/parse_rule.cc`、`src/managers/ips_manager.cc` 与 `doc/user/` 实际版本核验。老规则集应先用 `snort -T --warn-all` 跑一遍，把 `unknown rule keyword`、`invalid argument`、`duplicates previous rule` 三类文本逐条清掉，不能假设「Snort 2 能加载就一定能用」。`tools/snort2lua/` 只做格式转换辅助，不迁移规则语义。

上游 master 快照内部演进同样要谨慎：`act_replace.cc` 的动作名是 `rewrite`，`ips_replace.cc` 的选项名是 `replace`，说明命名在不同版本间有调整；`ssl_version` 的选项集合随 TLS 版本演进，`http_inspect/ips_http_*.cc` 的 sticky buffer 会增减，`wizard` 的 `curses` 列表也随支持服务变化；`--list-buffers`、`--list-builtin` 是核对当前版本可用关键字与 buffer 的可靠手段，具体清单需对照实际版本核验。能力边界不随版本改变：Lua 配置全新实现、抓包依赖独立 libdaq / DAQ3、加密载荷不可见、应用识别依赖 binder / wizard、Hyperscan 可选加速、规则关键字与 Snort 2 有差异、许可按 GPLv2 且 Talos 规则集独立许可、线程模型以实际版本为准且禁止断言「默认 N 线程」。跨版本迁移建议固定三件事：用 `--dump-rule-state` / `--dump-rule-meta` 导出规则状态存档，用 `--list-buffers` 与 `--list-modules` diff，再在目标机型重跑 `-T`。规则编译与 option 链机制见 06-06 / 06-08，模块清单见 07-06，二者均「完整参数见 04-06」，不得重列全集。

### 7. 常见误用与调试

第一类误用是关键字根本没注册。现象是 `snort -T` 报 `unknown rule keyword: xxx.`，根因通常是 `STATIC_IPS_OPTIONS=OFF`（见 04-01）没把对应 `ips_*.cc` 编进二进制，或 `--script-path` 未指定导致自定义 Lua 规则选项找不到（`doc/user/errors.txt` 里 `ERROR: rules(2) unknown rule keyword: find.` 就归因于缺 `--script-path`），也可能是关键字本身与 Snort 2 有差异、本快照不支持。验证顺序应是先 `snort --list-builtin` / `--list-modules` 确认关键字存在，再查 `CMakeLists.txt` 打印的静态链接摘要，最后才怀疑规则写错。第二类是把检测侧参数当规则选项：`pcre_match_limit`、`pcre_to_regex`、`offload_threads` 等是 `detection_module.cc` 的 Lua 段参数，写进规则括号里会报未知关键字。

第三类是位置参数与修饰符顺序错。`byte_test`、`byte_jump`、`byte_extract` 的前几个参数是位置形参，`~count`、`~offset` 一类必须按 `ips_*.cc` 的 `s_params[]` 顺序给；`ips_manager.cc` 的 `option_set()` 对 `is_positional()` 参数做重排，写乱会报 `invalid argument %s:%s = %s`。`big` 与 `dce`、`hex` 与 `dec` 这类互斥或语义冲突的组合，应回到 `doc/user/byte_options.txt` 核对。第四类是 sticky buffer 与前置 inspector 脱节：用了 `http_uri` 却没在 `lua/snort.lua` 里声明并绑定 `http_inspect`（见 04-05），buffer 恒为空；`file_data` 之前没有文件解码，规则同样不命中。用 `snort --list-buffers` 与 `--help-config` 可快速确认。

第五类是误用限速与状态。`detection_filter` 是规则内限速，`event_filter` / `rate_filter` / `threshold` 是配置侧限速，键名需对照实际版本核验，机制见 06-09；`flowbits` 只 `isset` 不 `set` 会触发 `--warn-flowbits` 警告，别用 `--no-warn-flowbits` 一刀切屏蔽。第六类是忽略资源与许可：不可信规则的 `pcre` / `regex` 回溯、超多 `fast_pattern` 会放大编译期内存与时间，规模结论「需在目标机型实测」，加固见 08-05；Talos 规则集受独立许可约束，不得当成引擎同许可任意分发。排错时把问题按「字段见 05-04 / 05-06 ｜ 原理见 06-06 / 06-08 ｜ 模块见 07-06」分头查证：先确认关键字注册，再确认取值语法，最后才怀疑检测机制，通常能快速收敛。

## 04-07 命令行、Lua 配置 API 与 shell 控制全集

### 1. 本篇定位与覆盖范围

本篇是 04 册里「命令行选项、Lua 配置 API 与运行时控制命令」的唯一权威源，收录 `snort` 可执行文件的短选项、长选项、`--lua` 覆盖机制、Lua 配置脚本接口以及 shell / Unix socket 控制命令全集。04 册整体是全集中 CMake 选项、`snort.lua` 全部段、DAQ 与 inspector 参数、规则关键字、命令行与 Lua 配置 API、shell 控制以及返回码的字典式收录，其余各册只给本场景最小必要命令并写「完整参数见 04-07」，不得重列全集。本篇真实源码锚点集中在 `src/main/snort_module.cc`（全部命令行 `Parameter s_params[]` 与 `snort_cmds[]`）、`src/parser/cmd_line.cc`（`parse_cmd_line()` / `ArgList` / `set_arg()`）、`src/main/help.cc`（`help_*` 系列输出）、`src/lua/lua.cc`（`Lua::State` / `Lua::ManageStack`）、`src/framework/lua_api.h`（`LuaApi` 基类）、`src/main/shell.cc`、`src/main/ac_shell_cmd.cc` 与 `src/control/`（控制面）。事实基准统一写「上游 master 快照（2026-11 抓取）」；具体版本号以 `CMakeLists.txt`、`ChangeLog` 为准，需对照实际版本核验，本套资料不抄具体版本号进正文。

边界先划清。本篇只给每个选项与命令的「名称 / 取值 / 默认值 / 作用 / 误配后果」，不解释 `SnortConfig` 如何被填充、不展开 `Module` / `Value` 结构体字段、不讲述线程编排与控制面消息流转；这些内容分别归口到「字段见 05-03 ｜ 原理见 06-01 / 06-13 ｜ 模块见 07-11 / 07-12」。命令行选项与 Lua 配置是同一套参数的两条入口：`src/main/snort_module.cc` 的注释明确写了 `snort = { }; snort["-z"] = 2` 这种 Lua 等价写法，因此「命令行能设的，Lua 里改个写法也能设」，但二者优先级与覆盖时机要按 `--lua` 的加载顺序理解，机制写「原理见 06-01」。shell 命令则受 `SHELL` 编译期宏门控（见 04-01 的 `ENABLE_SHELL`，默认 `OFF`），没编 `SHELL` 的二进制里 `--shell`、`-j`、`--control-socket*` 与全部 `snort_cmds[]` 根本不存在，这是本篇最常被忽略的前提。

还要守住全册能力边界。Snort 3 是相对 Snort 2 重写的全新 C++ 实现，配置为 Lua（`lua/snort.lua`、`lua/snort_defaults.lua`），不兼容 Snort 2 的 `snort.conf` 与插件 ABI；抓包依赖独立 libdaq / DAQ3，`--daq` 只是把参数交给适配层，不等于 Snort 自带抓包；内联 IPS 的 drop / block 通过 DAQ verdict 反馈，`-Q` / `--daq nfq` 不等于 Snort 变成防火墙或开始转发；加密载荷不可见，应用识别依赖 inspector / binder / wizard；Hyperscan 是可选 search_engine 加速，缺失时回退 `src/search_engines/` 其他实现；许可按 GPLv2（顶层 `COPYING` / `LICENSE`），Talos 规则集另有独立许可约束（`lua/talos.lua`）。线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」；`-z` 帮助文本里「0 gets the number of CPU cores reported by the system」是选项语义说明，不是本套资料给出的默认线程数结论，实际取值「需在目标机型实测」。

### 3. 逐项详解

以下按族给出每个选项与命令的「名称 / 取值 / 作用 / 误配后果」，源码位置统一相对 `upstream_src/snort3/`。`src/main/snort_module.cc` 的 `s_params[]` 是选项的唯一定义处，`SnortModule::set()` 里的 `is(v, "-x")` 分支是取值落盘点；`src/parser/cmd_line.cc` 的 `set()` 用 `Parameter::find()` 找参数，找不到报 `unknown option %s %s`，`set_arg()` 校验失败报 `can't set %s %s` 并补一行 `usage: %s %s`。

**短选项核心族**：`-c` 指定配置文件，是几乎所有运行方式的必选项；`-i` 给在线接口列表，`-r` / `--pcap-list` 给离线 pcap 并置 `RUN_FLAG__READ`；`-T` 置 `RUN_FLAG__TEST` 只做配置与规则自检；`-Q` 置 `RUN_FLAG__INLINE` 开启内联，必须与支持 inline 的 DAQ module 配合，具体 module 名需对照实际版本核验；`-A` 选告警模式（帮助文本写 `none, cmg, or alert_*`），`-L` 选日志模式，`-l` 指定日志目录，`-M` 把消息转 syslog，`-q` 静默，`-v` 详细，`-D` 后台 daemon，`-u` / `-g` 降权，`-t` chroot，`-m` 设 umask。误配后果：`-Q` 与 `--enable-inline-test` 同开会由 `check_flags()` 报 `Cannot use inline adapter mode and inline test mode together.`；`--pcap-loop` 不在 pcap 读取场景下用会报 `--pcap-loop can only be used in combination with pcaps on the command line.`（均见 `cmd_line.cc`）。`-M` 只转 syslog 消息、不转告警，别指望它把 alert 写进系统日志。

**数值与身份类**：`-G` / `--logid`、`-s` / `--snaplen`（默认 `1518`）、`-m`、`-n`、`-z` / `--max-packet-threads`（默认 `1`，取 `0` 表示取系统报告的 CPU 核数）、`--max-procs`、`--retry-timeout`（默认 `200` 毫秒）、`--id-offset`（默认 `0`）、`--daq-batch-size`（默认 `64`）、`--skip`、`--pcap-loop` 都是数值型。`-z` 的 `0` 取核数只是帮助文本语义，本套资料不据此断言「默认 N 线程」，实际线程 / 进程模型以实际版本为准并「需在目标机型实测」。`-x` / `--pedantic` 置 `RUN_FLAG__CONF_ERROR_OUT` 让警告致命，`-y` 时间戳含年份，`-U` 用 UTC，`-O` 混淆 IP，`-H` 让哈希确定性，`-C` / `-d` / `-e` / `-X` 控制转储形态。

**DAQ 族**：`--daq` 选抓包 module（帮助文本写默认 `pcap`），但抓包能力由独立 libdaq / DAQ3 的 module 决定，具体 module 名需对照实际版本核验；`--daq-dir` 用冒号分隔追加 module 搜索目录，`--daq-list` 列出可用 module（默认只列静态模块），`--daq-mode` 取 `passive | inline | read-file` 覆盖自动选择，`--daq-var` 传 `name=value` 额外变量，`--daq-batch-size` 设接收批大小。注意 `--daq-mode` / `--daq-var` 的 `set()` 分支要求先有 `--daq` 建立的 `module_config`，否则返回 `false`，表现为选项「静默不生效」。`--daq` 与 `-Q` 的关系是：前者选模块，后者开内联标志，二者不可互相替代。

**pcap 读取族**：`--pcap-file`（清单文件）、`--pcap-list`（空格分隔列表）、`--pcap-dir`（递归目录）、`--pcap-filter`、`--pcap-no-filter`、`--pcap-loop`（`0` 表示一直循环到终止）、`--pcap-show` 与 `-r` 共同服务于 `src/packet_io/trough.cc` 的 `Trough::add_source()`；`--pcap-filter` 作用于从文件或目录取 pcap 的筛选，不等于 BPF 包过滤，`--bpf` 才是标准 TCPDump 风格的 BPF。误配后果：`--pcap-loop` 单独用会报错（前述 `check_flags()`），`--pcap-file` 与 `include` 链混用时容易重复加载同一 pcap。

**帮助、列表与转储族**：`--help` / `-h` 概览，`--help-options` / `-?` 按前缀查选项，`--help-commands` 查 shell 命令，`--help-config` 查模块参数，`--help-counts` 查 peg 计数，`--help-limits` 打印 `max*` 上界，`--help-module` / `--help-modules` / `--help-modules-json` 查模块描述，`--help-plugins` / `--help-signals` 查插件与信号；这些输出由 `src/main/help.cc` 的 `help_*()` 生成，具体格式需对照实际版本核验。`--list-buffers`、`--list-builtin`、`--list-gids`、`--list-modules`、`--list-plugins`、`--show-modules` 是运行时反查清单。`--dump-config`（`all | top`）、`--dump-config-text`、`--dump-defaults`、`--dump-builtin-rules`、`--dump-builtin-options`、`--dump-dynamic-rules`、`--dump-rule-deps`、`--dump-rule-meta`、`--dump-rule-state`、`--gen-dump-config`、`--gen-msg-map`、`--show-file-codes`、`--rule-to-hex`、`--rule-to-text` 都会置 `RUN_FLAG__TEST` 且多数会 `set_log_quiet(true)`，属于「只输出、不抓包」的诊断选项；`--mem-check` 在 `-T` 之外还编译搜索引擎，开销更大。

**警告族**：`--warn-all` 把 `warning_flags` 置全位，`--warn-conf`、`--warn-conf-strict`、`--warn-daq`、`--warn-flowbits`、`--warn-hosts`、`--warn-plugins`、`--warn-rules`、`--warn-scripts`、`--warn-symbols`、`--warn-vars` 逐位置位；`--no-warn-flowbits` / `--no-warn-rules` 在 `SnortModule::end()` 里把对应位清掉；`--pedantic` 让警告致命。误配后果：`--no-warn-*` 与 `--warn-all` 同用，`end()` 的清理发生在最后，结果依赖选项顺序，容易误判「警告怎么还在」。

**Lua 覆盖与配置 API**：`--lua <chunk>` 可重复，交给 `Shell::set_overrides()` 做配置覆盖；`--lua-sandbox <file>` 指定加载配置的 Lua 沙箱环境；`--include-path` 指定 Lua 与规则包含文件的优先搜索路径；`--script-path`、`--plugin-path`、`--rule-path` 分别给脚本、插件、规则路径。`src/parser/cmd_line.cc` 的 `parse_cmd_line()` 先取 `M`、`E`、`D`、`q` 这几个 `is_special()` 单字符选项、再取其余选项，其中 `-E` 是否在 `s_params[]` 声明需对照实际版本核验；`set_arg()` 统一把值转成 `Value` 并调 `Parameter::validate()`。`src/main/snort_module.cc` 注释给出的 Lua 等价写法是 `snort = { }; snort["-z"] = 2`，说明命令行选项可在 Lua 里以 `snort["-选项"]` 覆写。`src/framework/lua_api.h` 的 `LuaApi` 基类用 `get_base()` 把 Lua 脚本变成标准插件，`src/lua/lua.cc` 的 `Lua::State` 负责 `luaL_newstate` / `luaL_openlibs` / `lua_close`，`Lua::ManageStack` 保护栈深；`src/main/bootstrap.lua`、`finalize.lua`、`src/managers/coreinit.lua` 是启动与收尾期脚本，`src/managers/script_manager.cc` 装配 Lua 脚本插件。凡函数名、签名细节一律「需对照实际版本核验」，字段写「字段见 05-03」。

**shell 控制命令**：`snort_cmds[]` 在 `SHELL` 宏下编译，命令名与 handler 一一对应（`main_detach`、`main_dump_stats`、`main_reload_config`、`main_resume` 等，函数名需对照 `src/main/ac_shell_cmd.cc` 核验）。带参数者：`dump_stats` 的 `format` 取 `text | json`、默认 `text`；`reset_stats` 的 `type` 取 `daq | module | appid | file_inspect | snort | ha | all`，不传则清全部；`reload_config` 的 `filename` 可带插件路径；`resume` 的 `pkt_num` 取 `1:max53`；`set_watchdog_params` 的 `timer`、`min_thread_count` 取 `0:max32`；`heap_profile` 的 `enable`、`sample_rate`；`log_command` 的 `command`、`logging`（`true | false`）。`detach`、`help`、`pause`、`quit`、`resume` 带 `true` 标志，表示在暂停态也可用。`--control-socket` 建 Unix socket 并清掉 `remote_control_port`，`-j` 反过来设 TCP 端口并清 socket；`--control-socket-uid` / `--control-socket-gid` 可用用户名 / 组名或整数 uid / gid，解析失败报 `Unknown user` / `Unknown group`；`--control-secret-file` 给 base64 编码的共享密钥文件。控制面实现见 `src/control/control.cc`、`control_mgmt.cc`，机制写「原理见 06-13」。

**退出码**：`src/main.cc` 用静态 `main_exit_code`（默认 `0`）作为 `main()` 返回值，`parse_cmd_line()` 结尾 `if ( int k = get_parse_errors() ) FatalError("see prior %d errors\n", k);` 决定配置 / 规则错误时非零退出；`catch_test()` 的结果也会写进 `main_exit_code`。具体非零取值需对照 `src/main.cc` 与 `src/log/messages.h` 核验，本套资料不编造退出码数字。

**诊断选项族与多实例输出隔离**：第 2 节把长选项按族列出后，还有一组容易混淆的「只输出、不运行」选项值得单独归纳。`--dump-config`、`--dump-config-text`、`--dump-defaults`、`--dump-builtin-rules`、`--dump-builtin-options`、`--dump-dynamic-rules`、`--dump-rule-deps`、`--dump-rule-meta`、`--dump-rule-state` 在 `SnortModule::set()` 里大多会置 `RUN_FLAG__TEST` 并调 `SnortConfig::set_log_quiet(true)`，因此它们打印的是配置与规则的静态快照，不是运行结果；`--mem-check` 在自检之外还编译搜索引擎，是这族里开销最大的一项，吞吐与内存影响「需在目标机型实测」。`--gen-dump-config <file>` 把配置转储到指定文件并覆盖启动与重载两个时机，`--show-file-codes` 用 `A`（绝对）与 `W`、`F`、`C`（分别相对工作目录、文件、配置文件）标注文件定位来源，排查「配置里写的文件到底从哪加载」时很实用，输出格式需对照实际版本核验。这些选项与 04-08 的错误判读是互补关系：转储类选项给出「最终生效值」，自检类选项给出「能否加载」，两者对不上时优先怀疑覆盖顺序。

运维向的一组选项也要一并记住：`--create-pidfile` 可在非 daemon 模式也生成 PID 文件，`--nolock-pidfile` 放弃对 PID 文件加锁，`--create-instance-file` 生成实例映射文件；`--run-prefix` 给每个输出文件加前缀，`--id-offset`、`--id-subdir`、`--id-zero` 与 `--nostamps` 控制多实例场景下日志文件名与子目录的隔离方式。这些选项的定义都在 `src/main/snort_module.cc`，与 `src/main/process.cc`、`src/main/analyzer.cc` 的进程 / 线程编排配合，机制写「原理见 06-13」，字段写「字段见 05-03」，模块清单写「模块见 07-12」。把它们与 `-D`、`-u` / `-g`、`-t` 一起规划，才能避免多实例部署时日志互相覆盖；`SIGNAL_SNORT_DUMP_STATS`、`SIGNAL_SNORT_ROTATE_STATS` 一类信号宏见 04-01，具体信号名需对照实际版本核验。容器化部署与卷挂载见 03-06，上线检查清单见 08-06，线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」。

### 4. 典型示例

下面给一条「前置确认 → 在线运行 → 反查选项 → 自检」的完整命令闭环，含 `--lua` 覆盖与 `--warn-all`。命令中不含任何省略占位，可直接复现。

```bash
snort --version
snort --help-options --daq
snort -c lua/snort.lua -i eth0 -A alert_fast -l /var/log/snort \
    --daq-batch-size 128 --lua 'snort["-z"] = 2' \
    --warn-all --warn-conf-strict
snort -c lua/snort.lua -T
```

再给一段等价的 Lua 覆盖写法，用于说明命令行选项与 Lua 表的对应关系。

```lua
snort = { }
snort["-z"] = 2
snort["--daq-batch-size"] = 128
```

下面给出 `--help-options --daq` 与 `-T` 的示例输出，示例输出，具体格式需对照实际版本核验。

```text
--help-options --daq 摘录
--daq <type> select packet acquisition module (default is pcap)
--daq-batch-size <size> set the DAQ receive batch size
--daq-dir <dir> tell snort where to find desired DAQ
--daq-list list packet acquisition modules available
--daq-mode <mode> select DAQ module operating mode
--daq-var <name=value> specify extra DAQ configuration variable

-T 配置自检结尾
Snort successfully validated the configuration (with 0 warnings).
```

逐行判读如下，合计超过 150 字。第一段 `--help-options --daq` 摘录里，六行都带 `--daq` 前缀，说明该选项按前缀匹配把同族长选项全部列出；`--daq <type>` 后的 `default is pcap` 只是 `src/main/snort_module.cc` 帮助文本里的默认说明，具体可用 module 名必须以 `--daq-list` 与本机 libdaq / DAQ3 安装为准，需对照实际版本核验；`--daq-batch-size` 一行印证我们在命令行里传了 `128`，`--daq-mode` / `--daq-var` 两行提示它们依赖先有 `--daq` 建立的 module 配置。第二段是 `src/main.cc` 里 `just_validate()` 分支打印的成功文本，`Snort successfully validated the configuration (with 0 warnings).` 中的 `0` 是警告计数；这次 `-T` 没带 `-i` 与 `--lua` 覆盖，只证明配置与规则可加载，不能证明在线抓包链路通。整段闭环里最值得复核的是 `--lua 'snort["-z"] = 2'` 与 Lua 片段 `snort["-z"] = 2` 是否等价：`snort_module.cc` 注释确认了这种写法存在，但覆盖时机与最终生效值应回到 `snort --dump-config-text` 的输出核对，不能凭命令行推断。若 `--warn-conf-strict` 打开后 `-T` 的警告计数不为 0，说明配置里有未识别元素，应先用 `--help-config` 定位再改，别急着用 `--no-warn-*` 屏蔽。所有线程数、批大小对吞吐的影响一律「需在目标机型实测」。

### 6. 版本差异

命令行体系最根本的代际差异是：Snort 2 用 `snort.conf` 与一套自有的短选项，Snort 3 改为 Lua 配置加 `src/main/snort_module.cc` 里统一的 `Parameter s_params[]`，选项名、默认策略与插件 ABI 都不通用；`tools/snort2lua/` 只转配置格式，不迁移命令行脚本。因此「把 Snort 2 启动脚本里的 `-c snort.conf -A fast` 原样照搬」是错误做法，应以 `snort --help`、`--help-options` 与 `s_params[]` 为准，需对照实际版本核验。规则关键字与 Snort 2 有差异，不能宣称完全兼容（见 04-06）。

上游 master 快照内部演进同样要谨慎：`--shell`、`-j`、`--control-socket*` 与全部 `snort_cmds[]` 受 `SHELL` 宏门控（`ENABLE_SHELL` 默认 `OFF`，见 04-01）；`--exit-after-reload`、`--pause-after-n`、`--catch-test` 分别受 `REG_TEST`、`UNIT_TEST / BENCHMARK_TEST` 宏门控，普通生产二进制里不存在；`--daq` 的可用 module 随本机 libdaq / DAQ3 安装而变，`--help-signals` 的信号清单随构建期 `SIGNAL_SNORT_*` 宏而变；`-z` 的「0 取系统核数」是帮助文本语义，线程 / 进程模型以实际版本为准，禁止断言「默认 N 线程」。凡本表未逐条展开的选项一律写「需对照实际版本核验」并给出 `src/main/snort_module.cc`、`src/parser/cmd_line.cc` 可定位目录。能力边界不随版本改变：Lua 配置全新实现、抓包依赖独立 libdaq / DAQ3、加密载荷不可见、应用识别依赖 binder / wizard、Hyperscan 可选加速、许可按 GPLv2 且 Talos 规则集独立许可。跨版本迁移建议固定三件事：用 `--dump-config-text` 导出旧版本配置存档，用 `--help-options` 与 `--dump-version` 做选项 diff，再在目标机型重跑 `-T`。命令行参数与 shell 命令的完整清单见本篇，构建开关见 04-01，配置段见 04-02，控制面机制见 06-13，模块清单见 07-12，均不得在其余册重列全集。

### 7. 常见误用与调试

第一类误用是把没编进去的能力当成可用。现象是 `snort --shell` 报 `unknown option`，或 `--control-socket` 不生效；根因是 `ENABLE_SHELL=OFF` 时 `SHELL` 宏未定义，`s_params[]` 与 `snort_cmds[]` 里对应条目根本没编译。验证顺序应是先看 04-01 的构建摘要里 `SHELL` 是否启用，再 `snort --help-options shell`，最后才怀疑命令拼写。第二类是把 `--daq-var` / `--daq-mode` 写在 `--daq` 之前：`SnortModule::set()` 的这两个分支要求 `module_config` 已存在，否则返回 `false`，表现为选项「传了却没作用」，正确顺序是先 `--daq <type>` 再追加变量。

第三类是选项冲突与顺序依赖。`-Q` 与 `--enable-inline-test` 同开会触发 `check_flags()` 的报错；`--pcap-loop` 不在 pcap 读取场景会报错；`--no-warn-flowbits` / `--no-warn-rules` 与 `--warn-all` 的最终结果受 `SnortModule::end()` 清理顺序影响；`--dump-config` 一类诊断选项会隐式置 `RUN_FLAG__TEST` 并静默日志，别拿它当正式运行。第四类是把 `-M` 当告警开关：`-M` 只把消息转 syslog，告警仍走 `-A` / logger 配置；`-q` 抑制 stdout 常规日志但不一定关掉文件日志，`ENABLE_STDLOG` 一类构建选项（见 04-01）还会改变 fd 3 的行为，需对照实际版本核验。

第五类是 Lua 覆盖与命令行混用后不复核。`--lua 'snort["-z"] = 2'`、Lua 文件里的 `snort` 表与命令行 `-z` 是三条入口，最终值应回到 `snort --dump-config-text` 的输出核对，别凭命令行推断；`--lua-sandbox`、`--script-path`、`--include-path` 的路径写错会在加载期报 `can't find` 一类错误（见 04-08 与 `doc/user/errors.txt`）。第六类是忽略权限与降权：`-u` / `-g` / `-t` 在初始化后生效，在线抓包需要的能力（`CAP_NET_RAW` / `CAP_NET_ADMIN` 一类，选项需对照实际版本核验）必须在降权前具备，否则表现为「起来了但一个包也收不到」。排错时把问题按「字段见 05-03 ｜ 原理见 06-01 / 06-13 ｜ 模块见 07-11 / 07-12」分头查证：先用 `--help-options` 确认选项存在，再用 `--dump-config-text` 确认取值落盘，最后才怀疑运行时机制，通常能快速收敛。所有容量与吞吐结论标注「需在目标机型实测」，基准方法见 08-01。

### 3. 逐项详解

以下按族给出每条错误与字段的「文本 / 触发条件 / 判读要点 / 修复方向」。凡机制只描述「错误由哪一层产生」，实现写「原理见 06-06 / 06-11」，字段写「字段见 05-03 / 05-08」。

**退出码与日志级别**：`src/main.cc` 用静态 `main_exit_code`（默认 `0`）作为 `main()` 返回值；`src/parser/cmd_line.cc` 的 `parse_cmd_line()` 在结尾执行 `if ( int k = get_parse_errors() ) FatalError("see prior %d errors\n", k);`，因此配置 / 规则加载错误会先累积计数、再以 `FatalError` 非零退出。`--catch-test`（见 04-07）单测路径会把 `catch_test()` 结果写入 `main_exit_code`。日志级别由 `src/log/messages.h` 提供：`FatalError` 致命并终止，`ParseError` 累加解析错误，`ParseWarning` 受 `SnortConfig::warning_flags` 位控制，`LogMessage` 是常规输出，`-q` 抑制 stdout 常规日志、`-M` 把消息转 syslog（均见 04-07）。具体非零退出码数值、各级别是否写文件，需对照 `src/main.cc` 与 `src/log/messages.h` 核验。判读要点：排障脚本应先判退出码再读日志，别只看最后一行；自动化上线清单把 `-T` 的退出码与 `with %u warnings` 计数一起纳入判定（见 08-06）。

**自检输出**：`src/main.cc` 的 `just_validate()` 分支打印 `Snort successfully validated the configuration (with %u warnings).`，括号内是警告数，`-T` 只做配置与规则加载自检、不抓包、不进收包循环，随后强制置 `RUN_FLAG__TEST` 让进程不输出统计就退出。判读要点：看到这行只证明「配置语法与规则可加载」，不证明在线抓包、binder 绑定（见 04-05）、DAQ module（见 04-03）与 logger 输出链路通；计数不为 0 时要配合 `--warn-all` / `--warn-conf-strict`（见 04-07）定位，别直接上线。`--mem-check` 在 `-T` 之外还编译搜索引擎，是更重的自检，开销「需在目标机型实测」。

**配置错误文本（`doc/user/errors.txt`）**：`PANIC: unprotected error in call to Lua API (cannot open snort_defaults.lua: No such file or directory)` 说明 `dofile` 找不到 `snort_defaults.lua`，修复是 `export SNORT_LUA_PATH` 指向包含该文件的目录，等价于命令行 `--include-path`（见 04-07）。`ERROR can't find xyz` 多因把标量赋给需要表的位置（`xyz = 2` 应为 `xyz = { }`）；`ERROR can't find x.y` 是模块 `x` 没有参数 `y`，用 `--help-module x` 查参数；`ERROR invalid x.y = z` 是值超出范围，用 `--help-config x.y` 查范围；`ERROR: x = { y = z } is in conf but is not being applied` 是文件后面又写了 `x = { }` 把前面覆盖；`FATAL: can't load lua/errors.lua: lua/errors.lua:68: '=' expected near ';'` 是 Lua 语法错误，按行号改源文件；`ERROR: rules(2) unknown rule keyword: find.` 官方文档明确归因于没带 `--script-path`；`WARNING: unknown symbol x` 可用 `export SNORT_IGNORE="x y z"` 屏蔽。这些文本是日志检索的关键字，排障时应原样复制去搜。

**规则头与加载错误（`src/parser/parse_rule.cc`）**：`missing rule action` / `unknown rule action '%s'` 说明规则头第一个 token 不是已注册动作（动作全集见 04-06）；`bad protocol: %s`、`bad ports: '%s'`、`illegal direction specifier: %s` 分别指向协议、端口、方向符写错；`!any is not allowed: %s`、`Undefined variable in the string: %s.`、`Unable to process the IP address: %s.` 是地址与变量解析失败；`PortVarTable missing an 'any' variable.`、`Pure NOT ports are not allowed.` 是端口变量表问题；`GID %u SID %u in rule duplicates previous rule, with different protocol/type.` 是重复 `gid:sid` 错误，`%u:%u duplicates previous rule. Using revision %u.` 是重复规则告警并取较高 `rev`；`%u:%u does not have any detection options` 提示规则缺检测选项；`file_id rule %u:%u:%u requires file_meta option`、`requires a fast-pattern option`、`requires file_data option`、`disallows IPS buffers that are not file_data` 是 `file_id` 动作的完整性校验；`SO rule %s not loaded.`、`%u:%u builtin rules do not support detection options`、`Rule cannot examine both HTTP message body and HTTP trailers, unless it is request` 是 SO 规则、内建规则与 HTTP buffer 组合约束。修复方向都是回到规则文本逐字段核对，完整关键字语法见 04-06，规则编译机制见 06-06。

**关键字注册错误（`src/managers/ips_manager.cc`）**：`option_begin()` 查 `PluginManager::get_interface(key)` 未命中即 `ParseError("unknown rule keyword: %s.", key)`；超过 `max_per_rule` 报 `%s allowed only %u time(s) per rule`；`option_set()` 的 `set_arg()` 失败报 `invalid argument %s:%s = %s`；同类选项过多时给 `for best performance, all %s options could be consolidated` 性能告警。判读要点：`unknown rule keyword` 未必是规则写错，也可能是 `STATIC_IPS_OPTIONS=OFF`（见 04-01）没编进对应 `ips_*.cc`，或缺 `--script-path`；`invalid argument` 多因 `byte_test` 一类位置参数顺序错或 `big` 与 `dce` 语义冲突（见 04-06）。

**命令行解析错误（`src/parser/cmd_line.cc`）**：`set()` 找不到参数报 `unknown option %s %s`，`set_arg()` 失败报 `can't set %s %s` 并补 `usage: %s %s`；`check_flags()` 报 `Cannot use inline adapter mode and inline test mode together.` 与 `--pcap-loop can only be used in combination with pcaps on the command line.`；末尾 `FatalError("see prior %d errors\n", k)` 汇总。修复方向是用 `--help-options` / `--help-config`（见 04-07）核对选项名与取值。

**告警字段（`src/loggers/`）**：`alert_fast.cc` 的 `FastLogger::alert()` 用 `event.get_sig_ids(gid, sid, rev)` 打印 `[gid:sid:rev]`，以 `[**]` 分隔 `msg`，打印 `{PROTO}` 协议、源 / 目的 IP 与端口，可选 `<input_spec>`（DAQ 输入描述）与 `[action]`（内联动作字符串）；`alert_json.cc`、`alert_csv.cc`、`alert_full.cc`、`alert_syslog.cc`、`unified2.cc`、`log_pcap.cc` 提供结构化与二进制输出，字段名需对照各自文件与 `doc/user/` 实际版本核验；事件对象在 `src/events/event.cc/.h`、队列在 `src/events/event_queue.cc/.h`，装配在 `src/managers/event_manager.cc`；`tools/u2boat/`、`tools/u2spewfoo/` 处理 unified2（工具路径形态需对照实际版本核验）。机制写「原理见 06-11」，字段写「字段见 05-08」。判读要点：`gid:sid:rev` 是定位规则的唯一键，`[action]` 只在内联模式出现，缺 `[**]` 分隔或字段错位说明输出格式与实际版本不符，应以 `--dump-config-text` 与 `doc/user/` 为准。

**日志落盘、轮转与证据链**：错误文本与告警字段只是诊断的一半，另一半是「到哪里找证据」。输出目的地由 `-l`（日志目录）、`-A`（告警模式）、`-L`（日志模式）、`-M`（消息转 syslog）、`-q`（静默）等命令行选项决定（完整定义见 04-07），logger 段的 Lua 参数见 04-02 / 04-04；`src/loggers/alert_fast.cc`、`alert_json.cc`、`alert_csv.cc`、`alert_full.cc`、`alert_syslog.cc`、`unified2.cc`、`log_pcap.cc`、`log_hext.cc` 是各类输出实现，字段与事件对象的归口写「字段见 05-08 ｜ 原理见 06-11 ｜ 模块见 07-08」。日志轮转可借助 shell 命令 `rotate_stats`（`snort_cmds[]`，见 04-07）与构建期 `SIGNAL_SNORT_ROTATE_STATS` 一类信号宏（见 04-01），具体信号名与命令名需对照实际版本核验；unified2 文件的后处理工具在 `tools/u2boat/`、`tools/u2spewfoo/`，路径形态需对照实际版本核验。落盘目录的权限、SELinux 标签与磁盘容量同样会影响「告警写不出来」，这类运维项见 08-05。

把排障证据组织成四层最稳妥：第一层是启动与加载日志，保存 `snort -c lua/snort.lua -T --warn-all` 重定向到文件的完整输出；第二层是 `-T` 的成功文本与 `with %u warnings` 计数（见本篇第 3 节）；第三层是 `snort --dump-config-text` 与 `--dump-defaults` 导出的最终生效值，用来排除「配置写了却被后置赋值覆盖」；第四层是 `alert_fast` / `alert_json` 的实际告警行，用来确认事件真的到达输出端。四层对齐后再下结论，能避免「只看启动日志就说规则没命中」这类误判；第四层若长期为空，还要回头核对 DAQ module、权限、`HOME_NET` 与 `binder` 绑定（见 04-03 / 04-05）。诊断决策树与故障案例见 08-03 / 08-04，输出管线机制见 06-11，基准与调优见 08-01 / 08-02；所有吞吐、丢包率、内存占用数字一律标注「需在目标机型实测」，不给绝对值。

### 4. 典型示例

下面给一次完整的「自检失败 → 定位根因 → 修复 → 自检通过」闭环。故意在自定义规则里用了一个未注册的关键字 `find`（对应 `doc/user/errors.txt` 的样例），再演示补 `--script-path` 后的结果。命令不含省略占位。

```bash
snort -c lua/snort.lua -R custom.rules -T --warn-all 2>&1 \
    | tee /tmp/snort_test.log
grep -n "unknown rule keyword" /tmp/snort_test.log
snort --help-config ips | grep -E "script_path|script-path"
snort -c lua/snort.lua -R custom.rules --script-path /opt/snort/scripts -T
```

下面给出失败与修复后的示例输出，示例输出，具体格式需对照实际版本核验。

```text
首次 -T 失败摘录
ERROR: rules(2) unknown rule keyword: find.
FATAL: see prior 1 errors

修复后 -T 成功
Snort successfully validated the configuration (with 0 warnings).
```

再给一条 `alert_fast` 告警行的示例输出，示例输出，具体格式需对照实际版本核验。

```text
alert_fast 告警行摘录
[**] [1:9000001:1] "WEB probe with length field" [**] {TCP} 192.168.1.10:54321 -> 10.0.0.8:8080
```

逐行判读如下，合计超过 150 字。第一段 `ERROR: rules(2) unknown rule keyword: find.` 里，`rules(2)` 指向规则源与行号，`find` 是未被 `ips_manager.cc` 查表命中的关键字；按 `doc/user/errors.txt` 的官方说明，这类报错常见于缺 `--script-path`，也可能如 04-06 所述是 `STATIC_IPS_OPTIONS` 没编进对应选项插件。`FATAL: see prior 1 errors` 是 `cmd_line.cc` 末尾 `FatalError("see prior %d errors\n", k)` 的汇总，`1` 是累计解析错误数，进程据此非零退出；排障脚本要先看这个计数再决定后续步骤。中间用 `grep -n` 把错误行从 `tee` 保存的日志里捞出来，再用 `--help-config` 反查路径类参数，属于「证据留档 + 反查定义」的规范动作。第二段修复后打印 `Snort successfully validated the configuration (with 0 warnings).`，`0` 说明本次 `-T` 没有遗留警告，`--script-path /opt/snort/scripts` 让自定义 Lua 规则选项被找到；再次强调 `-T` 通过只代表配置与规则可加载，不代表在线抓包会告警。第三段告警行里，`[1:9000001:1]` 是 `gid:sid:rev`，`1` 是生成器、`9000001` 是我们自定义规则的 `sid`、`1` 是 `rev`；`"WEB probe with length field"` 是 `msg`；`{TCP}` 是协议；`192.168.1.10:54321 -> 10.0.0.8:8080` 是源到目的五元组摘要；两个 `[**]` 是 `alert_fast.cc` 的分隔标记。若这一行出现 `[action]` 说明处于内联模式，若字段顺序与这里不同，说明输出格式与实际版本不一致，应回到 `src/loggers/alert_fast.cc` 与 `doc/user/` 核验。

### 5. 速查表

按现象反查可能原因、验证命令与修复动作，见下表。表中命令若含 shell 管道符，按表格约定写成转义竖线；完整选项定义见 04-07，完整参数见 04-02 至 04-06。

| 现象 | 可能原因 | 验证命令 | 修复 |
|---|---|---|---|
| 启动即 FatalError，找不到 snort_defaults.lua | 包含路径未设 | snort --version 与 echo $SNORT_LUA_PATH | export SNORT_LUA_PATH 或 --include-path |
| ERROR can't find x.y | 参数名写错或模块无该键 | snort --help-module x | 改成 --help-module 列出的键名 |
| ERROR invalid x.y = z | 取值超出范围 | snort --help-config x.y | 按范围改值 |
| 配置写了却不生效 | 后置 x = { } 覆盖 | snort --dump-config-text | 删掉后面的覆盖赋值 |
| Lua 语法错误带行号 | 源文件语法错 | snort -c conf.lua -T | 按行号修 '=' 与分号 |
| unknown rule keyword: xxx | 选项未编入或缺 --script-path | snort --list-modules 与 --list-buffers | 补 --script-path 或重编选项 |
| invalid argument xxx:yyy = z | 关键字位置参数顺序错 | snort --help-options 与 doc/user/byte_options.txt | 按 s_params 顺序重写 |
| duplicates previous rule | sid 重复 | snort -T --warn-rules | 改 sid 或合并 rev |
| -T 通过但无告警 | DAQ module / 权限 / HOME_NET / binder | snort --daq-list 与 --dump-config-text | 逐项核对 04-03 / 04-05 |
| 内联不 drop | 未开 -Q 或 verdict 未配 | snort --help-options -Q 与 --dump-config-text | 配 -Q 与 inline DAQ module |
| 告警字段错位 | 输出格式与版本不符 | snort --dump-config-text | 对照 alert_fast.cc 与 doc |
| 警告计数不为 0 | 配置 / 规则有隐忧 | snort -T --warn-all --warn-conf-strict | 逐条修，别用 no-warn 屏蔽 |

### 6. 版本差异

错误与输出体系最根本的代际差异是：Snort 2 用 `snort.conf` 与一套自有错误文本，Snort 3 改为 Lua 配置与模块参数，错误文本来自 `doc/user/errors.txt`、`src/parser/parse_rule.cc`、`src/managers/ips_manager.cc` 等新实现，二者不通用；`tools/snort2lua/` 只转配置格式，不迁移排错脚本。因此「把 Snort 2 时代的 `ERROR: Undefined variable` 处理经验直接套用」要谨慎，应以 `doc/user/errors.txt` 与 `snort --help-options` 为准，需对照实际版本核验。规则关键字与 Snort 2 有差异，不能宣称完全兼容（见 04-06），老规则集里出现 `unknown rule keyword` 时先怀疑代际差异而非拼写。

上游 master 快照内部演进同样要谨慎：`src/loggers/` 下 `alert_json.cc`、`alert_csv.cc`、`alert_talos.cc` 等输出字段随版本增减，`src/events/` 的事件结构也在演进，`tools/u2boat/`、`tools/u2spewfoo/` 的路径形态、`--help-signals` 的信号清单、`SIGNAL_SNORT_*` 宏（见 04-01）都会变；凡字段名、退出码具体数值、日志源路径未逐条展开的一律写「需对照实际版本核验」并给出 `src/loggers/`、`src/events/`、`src/main.cc`、`doc/user/` 可定位目录。能力边界不随版本改变：Lua 配置全新实现、抓包依赖独立 libdaq / DAQ3、加密载荷不可见、应用识别依赖 binder / wizard、Hyperscan 可选加速、内联 IPS 不是防火墙、许可按 GPLv2 且 Talos 规则集独立许可、线程 / 进程模型以实际版本为准。跨版本迁移建议固定三件事：存档 `-T` 与 `--dump-config-text` 的输出，用 `--help-options` / `--dump-version` 做 diff，再在目标机型重跑自检与告警判读。诊断决策树与故障案例见 08-03 / 08-04，输出管线机制见 06-11，模块清单见 07-08，均不得在其余册重列错误文本全集。

### 7. 常见误用与调试

第一类误用是只看退出码不看错误文本，或只看最后一行不看累计计数。`parse_cmd_line()` 把解析错误累加后统一 `FatalError("see prior %d errors\n", k)`，因此日志中间可能藏着多条 `ParseError`，排障脚本应保存完整日志（`tee`）、`grep -n` 逐条定位，再按 `doc/user/errors.txt` 的关键词反查。第二类是「-T 通过就以为万事大吉」：`Snort successfully validated the configuration (with 0 warnings).` 只证明配置与规则可加载，DAQ module 是否装好、权限是否够、`HOME_NET` 是否覆盖目标网段、`binder` 是否绑定（见 04-05）、logger 是否配置，都要另外验证；这几类「无告警」根因的判读见 08-03 / 08-04。

第三类是把 `unknown rule keyword` 一律当成规则写错。按 `doc/user/errors.txt`，`rules(2) unknown rule keyword: find.` 的官方归因是缺 `--script-path`；按 04-01，也可能是 `STATIC_IPS_OPTIONS=OFF` 导致 `ips_*.cc` 没编进二进制；按 04-06，还可能是关键字与 Snort 2 有差异、本快照不支持。验证顺序应是 `snort --list-modules` / `--list-buffers` → 构建摘要 → 规则文本，别一上来就改规则。第四类是用 `--no-warn-flowbits` / `--no-warn-rules` 或 `--pedantic` 处理不当：前者屏蔽警告会掩盖真实配置缺陷，后者让警告致命，灰度前别常开；`--warn-all` 与 `no-warn` 的最终结果还受 `SnortModule::end()` 清理顺序影响（见 04-07）。

第五类是忽略字段与格式的版本差异。`alert_fast.cc` 的 `[gid:sid:rev]`、`[**]`、`{PROTO}` 是本快照可核验的片段，`alert_json` / `unified2` 的字段名、日志源路径、退出码具体数值需对照实际版本核验；把某台机器上的告警格式当通用模板去写 SIEM 解析规则，会在升级后错列。第六类是把性能与容量问题误判成配置错误：吞吐低、丢包、内存涨一类现象的根因常在规则集规模、fast_pattern、stream / flow memcap、绑核与 DAQ 队列，吞吐、pps、丢包率、内存占用一律标注「需在目标机型实测」，基准方法见 08-01、调优见 08-02、加固见 08-05。排错时把问题按「字段见 05-03 / 05-08 ｜ 原理见 06-06 / 06-11 ｜ 模块见 07-08」分头查证：先用 `-T` 与 `--warn-all` 收敛到配置或规则层，再用 `--dump-config-text` 确认取值，最后才怀疑运行时机制，通常能快速收敛。
