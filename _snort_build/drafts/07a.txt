# Snort 3 技术资料 · 07 模块与特性介绍（分片 A）

## 07-01 src/framework 模块框架

### 1. 模块定位与职责边界

`src/framework/` 是整个 Snort 3 插件化体系的地基，它不解析任何一个具体协议，也不执行任何一条具体规则，而是定义「插件长什么样、如何被创建、如何被装配、彼此如何通信」这套公共契约。从包处理流水线的视角看，framework 处于横切位置：DAQ 收包（原理见 06-02）交给 codec 解码（原理见 06-03）用到 `Codec`，binder 绑定与 wizard 识别（原理见 06-04）产出各类 `Inspector`，fast pattern 与检测（原理见 06-07、06-08）依赖 `Mpse` 与 `IpsOption`，命中后的动作（原理见 06-09、06-12）依赖 `IpsAction`，日志输出（原理见 06-11）依赖 `Logger`。这些形形色色的插件之所以能插进同一台引擎，正是因为 framework 为每一类插件规定了基类、API 结构和工厂函数签名。

理解 framework 的价值，可以从「为什么需要它」切入。Snort 3 相对 Snort 2 是一次重写，核心变化之一就是把原本分散在预处理程序与检测代码里的能力，收敛成统一插件模型（原理见 06-14）。如果没有 framework，每一种 codec、inspector、ips_option、logger 都要各自定义创建方式、生命周期回调与版本标识，装配层就得为每一类写一套专属逻辑，插件之间也无法用统一方式通信。framework 用「一个 `BaseApi` 头部 + 一类一个基类 + 一个工厂函数指针」把这件事标准化：任何插件只要按约定填好结构、导出符号，就能被 `PluginManager` 识别并装载。这也是为什么本目录里几乎看不到 `if (strcmp(name, "http"))` 这类硬编码分支——名字与类型的匹配交给 manager 按 `PlugType` 完成，framework 自身保持对具体插件的无知。对阅读源码的人而言，这意味着可以先读 framework 建立「插件应该长什么样」的心智模型，再逐个业务目录对照实现，而不必在几十个插件里反复猜测公共约定藏在哪里。

必须先讲清本目录的边界，避免与相邻目录混淆。framework 只负责「抽象定义」，不负责「注册与装配的具体执行」：把各插件的 API 结构收集起来、按类型实例化、挂到配置上的工作由 `src/managers/` 承担（模块见 07-11），framework 里只提供 `BaseApi` 这个被所有 API 结构共享的头部。同样，framework 提供 `Module` 这个承载参数的基类，但把 Lua 参数映射成配置对象的解析入口位于 `src/parser/` 与 `src/lua/`（参数见 04-02），framework 的 `Parameter`、`Value` 只是参数与值的类型载体。插件体系的运行机制与装载链路是 06-14 的主题（原理见 06-14），本篇只回答「framework 这个目录里有什么、每个文件干什么、边界在哪、它如何被装配」，不重讲机制流程。

本篇事实基准统一为「上游 master 快照（2026-11 抓取）」。需要特别提醒：framework 中的类是全套资料被引用最多的结构，其字段明细统一由 05 册权威定义，本篇第 3 节只点类名与真实头文件并标注「字段见 05-xx」，绝不重列字段表；插件的配置键与命令由 04 册权威给出，本篇涉及处一律写「参数见 04-xx」。把握住「framework 定义契约、managers 执行装配、parser 解析配置、各业务目录实现插件」这一定位，就能理解为何这个目录文件数量众多却几乎没有业务流程代码。

### 4. 对外接口与扩展点

framework 对外的接口就是一套「基类 + API 结构 + 工厂函数」的三元组约定，任何新增插件都遵循同一模板。以 inspector 为例，插件实现文件里必然出现三个要素：一个继承 `Inspector` 的具体类，一个以 `BaseApi` 打头的 `InspectApi` 结构实例，以及一个导出符号（惯用名 `nin_*` 或 `*_api`）指向该结构。`BaseApi` 作为结构首成员的设计（base_api.h 72、73 行附近注释明确说明「BaseApi must be the prefix, ie 1st member of all plugin api」）是 C++ 里用静态初始化列表构造 API 结构的前提；`type` 字段填 `PlugType` 之一，`api_version` 由 `BASE_API_VERSION` 左移 16 位再或上插件自身版本，`mod_ctor` / `mod_dtor` 指向模块的创建与销毁函数。这组约定把「插件实现」与「插件管理」解耦：framework 不认识任何具体插件名，managers 只按 `BaseApi` 头部统一处理（模块见 07-11）。

从生命周期看，framework 契约串起了一条清晰的装配链：启动期由 `PluginManager` 按 `BaseApi` 收集插件并校验版本，配置解析期由 `Module` 的 `Parameter` 接收 Lua 键并写入 `SnortConfig`（参数见 04-02、字段见 05-03），实例化期由 `mod_ctor` 产生具体 `Module`、再由各类 `*NewFunc` 产生插件对象，运行期由基类虚函数承接包处理回调，配置热重载时由 `ReloadSurvivorSubscriptions` 一类设施保留必要的订阅状态（字段见 05-04）。理解这条链，就能明白为什么 framework 里的类大多同时提供「配置侧」与「运行侧」两套接口：它们不是冗余，而是分别服务于配置解析线程与包处理线程这两个不同阶段，跨线程共享状态时必须谨慎，模型细节以实际版本为准（原理见 06-13）。这条「从 API 结构到运行期回调」的装配链路见图 07-01-01。

图中实线是框架契约的主链路，`BaseApi` 作为所有 API 结构的公共头部被 `PluginManager` 统一识别；虚线表示模块与参数之间的绑定关系。要特别说明，framework 只是定义这套契约，真正执行装载的是 managers（模块见 07-11），真正填充各 API 结构槽位的是各业务插件目录（模块见 07-02 至 07-08）。

扩展点集中在两个方向。其一是**新增一类插件**：需要在 `base_api.h` 的 `PlugType` 增加枚举项、在 framework 增加对应基类与 API 结构、在 `src/managers/` 增加相应 manager，并在 `PluginManager` 登记版本；这类改动涉及 ABI，风险高，版本号需同步 escalation，具体步骤需对照实际版本核验。其二是**在既有类别下新增一个插件**：这是日常扩展的主路径，只需实现基类、填好 API 结构、导出符号，再由所属目录的装载函数（如 network_inspectors 的 `load_network_inspectors()`，模块见 07-02）交给 `PluginManager::load_plugins`。此外，`Module` 的 `Command` 与 `Parameter` 提供运行期命令与配置键的扩展入口（参数见 04-07），`DataBus` 的 `publish` / `subscribe` 提供插件间解耦通信（原理见 06-10、06-14），`PigPen` 提供线程本地存储以承载每线程状态（原理见 06-13）。要强调能力边界：`Inspector` 的 buffer 来自解码与 stream 提供的可见缓冲，加密载荷不可见（原理见 06-03、06-10）；`IpsAction` 的 drop / block 最终通过 DAQ verdict 反馈实现，framework 本身不转发、不做路由（原理见 06-12）。

下面给出一个插件 API 结构的典型形态（节选自通用模板，字段与签名细节需对照实际版本核验），说明 framework 契约如何被具体插件落地：

```cpp
// 通用插件 API 结构模板（示意，字段需对照实际版本核验）
struct InspectApi
{
    BaseApi base;                 // 必须是首成员，承载类型与版本
    InspectFunc init;             // 一次性初始化回调
    InspectSsnFunc ssn_new;       // 为新流创建 Session
    InspectDelFunc dtor;          // 销毁 Inspector
    // 其余生命周期与 buffer 回调成员见真实头文件
};

// 导出符号供 PluginManager 装载
extern const BaseApi* nin_example;
```

这段代码印证第 4 节的约定：`InspectApi` 以 `BaseApi base` 开头，`PluginManager` 只读这个头部即可完成按类型登记与版本校验；`ssn_new`、`dtor` 等函数指针把生命周期回调交给插件实现，framework 不介入具体协议逻辑。需要强调，具体的 inspector 插件（binder、normalize 等）如何填这些槽位、如何被 `load_network_inspectors()` 装载，属于 network_inspectors 模块（模块见 07-02），本篇只给契约模板，完整 API 见 04-07。

### 6. 与其他模块的关系及常见误用

framework 是「被依赖」的底座，与几乎所有目录都有关系，但关系性质必须分清。**与 managers（模块见 07-11）**：framework 定义 `BaseApi` 与各 `*Api` 结构，managers 负责 `PluginManager::load_plugins` 收集、按 `PlugType` 分派、创建实例并挂到 `SnortConfig`（字段见 05-03）；二者是「契约 vs 装配」的关系，常见误用是把装载逻辑写进 framework，导致插件类型与 manager 脱节。**与 parser / lua（模块见 07-11）**：`Parameter`、`Value`、`Command` 只是配置载体，真正的 Lua 解析在 `src/lua/lua.cc` 与 `src/parser/`（参数见 04-02），误用是试图在 framework 里解析配置文本。**与各业务插件目录**：`src/network_inspectors/`、`src/service_inspectors/`、`src/detection/`、`src/search_engines/`、`src/loggers/`、`src/actions/` 都是 framework 基类的实现者（模块见 07-02 至 07-08），framework 不反向依赖它们，依赖方向必须是单向的，否则会形成循环依赖。

四类常见误用需要重点提示。第一，**把 framework 当成插件实现库去找协议解析代码**：这里是抽象基类，找不到 HTTP、TLS、TCP 的具体逻辑，那些在 service_inspectors 与 stream（模块见 07-03、07-04）。第二，**随意改动 `BaseApi` 头部或 `PlugType` 顺序**：这属于 ABI 变更，会导致所有插件版本校验失败，必须同步 `BASE_API_VERSION` 与所有 API 结构，风险极高（原理见 06-14），需对照实际版本核验后再动手。第三，**混淆 `Module` 与 `Inspector` 的职责**：`Module` 是配置与命令的载体、随配置创建，生命周期跟随 `SnortConfig`；`Inspector` 是包处理期的工作对象、可每流创建，二者通过 `InspectApi` 的工厂关联（字段见 05-04）。把它们当成一个对象会导致配置态与运行态状态串味。第四，**误以为 framework 的 `test/` 是示例插件实现**：`test/` 里的 `api_def.cc` 与 `data_bus_test.cc` 是单元测试与桩代码，用于验证契约与总线行为，不能当作可直接复制的插件模板，真正的插件范本应去看业务目录（模块见 07-02 至 07-08）。还要守住能力边界：framework 不提供抓包（依赖独立 DAQ3，模块见 07-07）、不提供转发（不是防火墙，原理见 06-12）、不读加密明文（原理见 06-10）、不规定固定线程数（原理见 06-13）。所有吞吐、内存类结论一律标注「需在目标机型实测」，不给绝对值。

### 7. 小结与延伸阅读

本篇把 `src/framework/` 定位为插件化体系的契约层：以 `base_api.h` 的 `BaseApi` + `PlugType` 统一所有插件的 ABI 头部，以 `Inspector`、`Module`、`Mpse`、`IpsOption`、`IpsAction`、`Codec`、`Logger`、`Connector` 等基类定义各类插件的形态，以 `Parameter`、`Value`、`Command` 承载配置，以 `DataBus`、`PigPen` 提供通信与线程本地存储，以 `test/` 提供契约级单元测试。它的边界是「只定义、不装配、不解析、不实现协议」，装配归 managers、解析归 parser/lua、协议实现归各业务目录。把握住这条主线，就能理解为何 framework 文件众多却几乎没有业务流程代码。延伸阅读：插件 API 结构与工厂约定见 06-14；`Inspector`、`Module`、`Cursor`、`Logger` 等字段见 05-04、05-05、05-02、05-08；插件配置键与命令见 04-07；`src/managers/` 装配职责见 07-11；各插件实现目录见 07-02 至 07-08。上述文件清单与宏值均以「上游 master 快照（2026-11 抓取）」为准，个别文件与字段需对照实际版本核验。
## 07-02 src/network_inspectors 模块

### 1. 模块定位与职责边界

`src/network_inspectors/` 是网络层 inspector 插件的汇集地，它实现的是「在网络层与传输层这个粒度上，对包和流做什么」，与 `src/service_inspectors/` 实现的「在某个具体应用协议上做什么」形成明确分工（模块见 07-03）。本目录里的插件不产生告警、不执行规则动作：它们是包处理流水线中位于解码之后、检测之前的加工与观测环节。典型职责包括把流量绑定到合适的 inspector（binder）、把被篡改的报文恢复成规范形态（normalize）、识别应用与客户端（appid）、统计吞吐与流信息（perf_monitor）、记录声誉名单匹配（reputation）、检测端口扫描（port_scan）、做资产与指纹识别（rna）、检测 ARP 欺骗（arp_spoof）、把包落地为 pcap（packet_capture），以及机器学习推理与数据流抽取（snort_ml、extractor）。这些能力共同回答「这个包属于哪个应用、它的规范形态是什么、该交给谁继续处理、顺便记录哪些观测数据」。

从包处理流水线的位置看，network_inspectors 位于解码完成之后、检测求值之前，是「让后续环节拿到干净、可归属、可观测的输入」的关键一段。解码层给出的 `Packet` 只携带各层协议指针与原始载荷，并不知道这段流量属于哪个应用、是否需要按服务拆分缓冲、是否因分片或选项填充而存在歧义；binder 决定把流交给谁，normalize 把报文恢复成无歧义形态，appid 标注应用身份，perf_monitor 与 reputation 等旁路记录观测数据。没有这一段，service inspector 就无从按服务解析事务，检测引擎也只能基于粗糙的端口与全局缓冲工作。值得一提的是，本目录里既有处在主链路上的 binder、normalize，也有完全旁路的 perf_monitor、port_scan、rna，理解它们在流水线上的挂接位置，比记住每个插件的名字更重要——前者影响后续处理结果，后者只做观测与记录，二者的故障特征与排障思路截然不同。

必须先说清能力边界，这是本套资料反复强调的事实：应用识别依赖 inspector / binder / wizard 协同（原理见 06-04），**加密流量载荷不可见**，能拿到的只是握手元数据、证书信息等可见部分（字段名需对照实际版本核验），不得宣称本目录能读到 HTTPS 明文正文。同样，这里的 perf_monitor 只做计数与统计呈现，不替代 08 册的基准方法（运维见 08-01）；packet_capture 只是把包写出为 pcap，真正的抓包依赖独立 libdaq / DAQ3 适配层（模块见 07-07），不能说成「Snort 自带抓包」。binder 的绑定结果是后续 service inspector 与检测的输入，但判定规则成立与否属于 detection 模块（原理见 06-08），本目录不越界。

本篇事实基准为「上游 master 快照（2026-11 抓取）」。装配入口在 `src/network_inspectors/network_inspectors.cc` 的 `load_network_inspectors()`（57 行附近），具体插件实现分布在各子目录。插件基类的字段由 05 册权威定义（`Inspector`、`Module` 见 05-04），各 inspector 的配置键由 04 册给出（`binder`、`normalizer` 见 04-04，`appid` 等见 04-05），绑定与识别机制见 06-04，归一化原理见 06-03。本篇作为 07 册的组成部分，是模块功能与目录归属的唯一权威源，只回答「这个目录有什么、每个文件干什么、边界在哪、怎么被装配」，不重讲机制流程，也不重列字段与参数全集。

### 4. 对外接口与扩展点

本目录对外的接口就是 `network_inspectors.h` 导出的 `load_network_inspectors()`，它由启动期的装配流程调用（原理见 06-01、06-14），把所有网络层 inspector 的 `BaseApi` 交给 `PluginManager::load_plugins`。装配有明确的分组与条件：静态数组 `network_inspectors[]` 包含 `nin_binder`、`nin_normalize`、`nin_reputation` 三项，无条件装载；随后单独装载 `nin_appid`、`nin_extractor`、`nin_perf_monitor`、`nin_port_scan`、`nin_rna`；`nin_snort_ml_engine` 与 `nin_snort_ml` 受 `HAVE_LIBML` 或 `USE_LIBML_MOCK` 保护；`nin_arp_spoof` 与 `nin_packet_capture` 受 `STATIC_INSPECTORS` 保护（源码 29 至 75 行附近）。这个分组结构极其重要：它说明哪些 inspector 是默认可用核心、哪些是可选增强、哪些只在静态链接变体中存在，排障时先确认构建变体再谈功能缺失（构建见 02-02）。

新增 inspector 的扩展点遵循 framework 契约（模块见 07-01）：派生 `Inspector`、实现 `InspectApi`、导出 `nin_*` 符号，再把符号加进 `load_network_inspectors()` 的相应分组。若为可选能力，应仿照 snort_ml 用宏保护，避免给所有构建变体引入硬依赖。配置侧通过 `BinderModule`、`NormalizeModule` 等 `Module` 子类的 `Parameter` 暴露键（参数见 04-04、04-05），运行期通过 `DataBus` 发布事件供日志与检测订阅（原理见 06-10、06-14）。需要守住边界：本目录不直接定义规则关键字，`ips_appid` 只是一个规则选项，其语义与参数归 04-06（参数见 04-06）；应用识别结果受加密载荷不可见约束（原理见 06-04）；任何计数与吞吐结论需在目标机型实测。

下面给出装载函数的真实片段（节选自上游 master 快照，具体形态需对照实际版本核验），直观呈现分组与条件编译：

```cpp
// src/network_inspectors/network_inspectors.cc（节选）
static const BaseApi* network_inspectors[] =
{
    nin_binder, nin_normalize, nin_reputation, nullptr
};

void load_network_inspectors()
{
    PluginManager::load_plugins(network_inspectors);
    PluginManager::load_plugins(nin_appid);
    PluginManager::load_plugins(nin_extractor);
    PluginManager::load_plugins(nin_perf_monitor);
    PluginManager::load_plugins(nin_port_scan);
    PluginManager::load_plugins(nin_rna);
#if defined(HAVE_LIBML) || defined(USE_LIBML_MOCK)
    PluginManager::load_plugins(nin_snort_ml_engine);
    PluginManager::load_plugins(nin_snort_ml);
#endif
#ifdef STATIC_INSPECTORS
    PluginManager::load_plugins(nin_arp_spoof);
    PluginManager::load_plugins(nin_packet_capture);
#endif
}
```

这段代码把第 4 节的分组讲得很清楚：核心三项进静态数组，`appid`、`extractor`、`perf_monitor`、`port_scan`、`rna` 无条件装载，`snort_ml` 与 `arp_spoof`、`packet_capture` 分别受宏保护。排障时若发现某类 inspector 未生效，应先对照 `CMakeLists.txt` 确认 `HAVE_LIBML`、`STATIC_INSPECTORS` 等是否定义，再查 `snort.lua` 对应段是否加载该模块（参数见 04-04、04-05），而不是怀疑 inspector 实现有缺陷。这里可以套用一个通用判断顺序：先看构建变体是否包含该插件（宏保护决定符号是否存在）→ 再看 `load_network_inspectors()` 是否把它交给 `PluginManager`（装载分组决定可选集）→ 再看配置段是否实例化并启用（Lua 参数决定运行期是否工作）→ 最后才看插件自身的运行日志与统计（观测能力见 08-01、08-03）。这个顺序把「编不出来」「没装载」「没启用」「不生效」四类问题分开，避免把正常的条件编译跳过误判为故障。同一思路也适用于搜索引擎的 Hyperscan 可选性（原理见 06-07），这是本套资料反复强调的排障习惯。

### 6. 与其他模块的关系及常见误用

**与 framework（模块见 07-01）**：本目录是 `Inspector`、`Module` 等基类的实现者，依赖方向单向指向 framework；`Binder`、`Normalizer`、`ArpSpoof`、`PacketCapture` 均以 `public Inspector` 派生，字段见 05-04。误用是把 framework 契约改在这里实现，导致插件类型与 manager 脱节。**与 service_inspectors（模块见 07-03）与 wizard**：binder 负责把流量绑到合适的 inspector，wizard 用 magic 与端口启发式做服务识别，二者协同才能把协议数据交给 http_inspect、ssl 等服务检查器（原理见 06-04）；误用是把应用识别完全寄望于端口，忽略加密载荷不可见这一事实。**与 stream / flow（模块见 07-04、07-10）**：normalize 处理的是包级规范形态，stream 提供重组后的流缓冲，二者阶段不同；rna、perf_monitor 依赖 flow 记录，字段见 05-09。**与 detection（模块见 07-05）与 loggers（模块见 07-08）**：本目录通过 `DataBus` 发布观测事件供检测与日志消费（原理见 06-10），自身不产生告警、不执行 drop。**与 packet_io（模块见 07-07）**：packet_capture 写出 pcap 不等于抓包，抓包由 DAQ3 适配层完成。

四类常见误用需重点提示。第一，**把 perf_monitor 的计数当成性能基准**：它提供运行时观测，但吞吐、pps、丢包率、内存占用一律需在目标机型实测，不给绝对值（运维见 08-01）。第二，**误以为 snort_ml 默认可用**：它受 `HAVE_LIBML` 或 `USE_LIBML_MOCK` 保护，未满足构建条件时符号不存在、装载自然跳过，与 Hyperscan 的可选性同理，排查先看构建变体（构建见 02-02）。第三，**把 arp_spoof、packet_capture 当成所有构建都有的能力**：它们受 `STATIC_INSPECTORS` 保护，仅在静态链接 inspector 的变体中存在，需对照实际版本核验。第四，**混淆 appid 与 service inspector 的职责**：`appid` 识别应用与客户端，`ips_appid` 只是规则选项，具体协议解析在 service_inspectors（模块见 07-03），规则关键字参数归 04-06（参数见 04-06）。还要守住能力边界：Snort 3 不转发、不是防火墙（原理见 06-12），Lua 配置不兼容 Snort 2（参数见 04-02），本目录不提供例外。

### 7. 小结与延伸阅读

本篇把 `src/network_inspectors/` 定位为网络层 inspector 插件的汇集地：顶层 `network_inspectors.cc` 的 `load_network_inspectors()` 按「核心三项进静态数组、五类常规装载、snort_ml 受 `HAVE_LIBML` 保护、arp_spoof 与 packet_capture 受 `STATIC_INSPECTORS` 保护」的分组结构装配全部插件；各子目录分别承担绑定、归一化、应用识别、性能统计、声誉匹配、端口扫描、资产指纹、ARP 欺骗检测、抓包落地、机器学习推理与数据流抽取。它的边界是「加工与观测」，不产告警、不做转发、不读加密明文，真正的协议解析在 service_inspectors，抓包在 packet_io。把握住「按分组装载、按网络层职责分工、依赖 framework 基类、通过 DataBus 对外供数」这条主线，就能把本目录与相邻模块的边界理清。延伸阅读：插件基类契约见 07-01；服务检查器目录见 07-03；service 与 packet_io 职责见 07-03、07-07；绑定与识别原理见 06-04、归一化见 06-03；`Inspector`、`Module` 字段见 05-04；`binder`、`normalizer` 配置见 04-04、appid 见 04-05；基准方法见 08-01。上述文件清单与符号均以「上游 master 快照（2026-11 抓取）」为准，个别文件、符号与宏条件需对照实际版本核验。
