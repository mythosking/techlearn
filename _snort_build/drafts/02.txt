# Snort 3 技术资料 · 02 编译与构建

## 02-01 源码获取、仓库目录结构与依赖矩阵

### 1. 背景与动机

要把 Snort 3 从源码编出来，第一步并不是急着敲 `cmake`，而是先认清三件事：源码究竟落在哪一层目录、构建系统由哪些文件驱动、引擎到底依赖哪些外部库。这三件事在 01 册只作为能力边界被点名，到 02 册必须落到可核验的文件、函数与命令上。原因很直接：Snort 3 是相对 Snort 2 重写的全新实现（`project (snort CXX C)`、`set (CMAKE_CXX_STANDARD 17)`、`set (CMAKE_C_STANDARD 99)` 见顶层 `CMakeLists.txt`），构建系统也从 Automake 换成了 CMake，配置从 `snort.conf` 换成了 `lua/snort.lua`；沿用旧经验去找 `configure` 或去改旧式指令文件，会在第一道工序就走错方向。01 册已经说明，抓包不内置、依赖独立的 libdaq / DAQ3，Hyperscan 只是可选加速，这些边界在本册会直接体现为「必选依赖」与「可选依赖」两栏，不能写反。

本套资料的版本基准统一写「上游 master 快照（2026-11 抓取）」。具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，需对照实际版本核验；`CMakeLists.txt` 里的 `VERSION_MAJOR`、`VERSION_MINOR`、`VERSION_PATCH`、`VERSION_SUBLEVEL` 等变量只是构建期版本字样，只作核验依据，不抄进正文当作本套版本号。事实核验的唯一锚点是 `_snort_build/upstream_src/snort3/snort3-master/`：上游快照解压在 `_snort_build/upstream_src/snort3/` 下，真实仓库根是其中多出来的一层 `snort3-master/`（GitHub master 分支归档目录）。规范 0.1 节的必查文件表给出的路径已带 `snort3-master/` 前缀，去掉前缀便是仓库内惯用写法，例如 `CMakeLists.txt`、`lua/snort.lua`、`src/packet_io/sfdaq.cc`。下文凡出现路径，均相对该仓库根。

归档多一层这件事看着琐碎，却是本册最该先讲清的实操陷阱。若直接在 `_snort_build/upstream_src/snort3/` 下执行 `./configure_cmake.sh`，脚本并不存在；若把 `snort3-master/` 里的文件平铺到上一层再构建，`sourcedir="$( cd "$( dirname "$0" )" && pwd )"` 解析出的源码根、`configure_file` 用到的 `${PROJECT_SOURCE_DIR}` 与 `${CMAKE_SOURCE_DIR}` 都会随之改变，`cmake/` 模块、相对头文件路径与 `add_subdirectory` 的组织一并错位。正确做法是把 `snort3-master/` 当作唯一源码根，在其中操作，构建产物统一落到它下面新建的 `build/` 子目录。

还有一层定位需要先声明：02 册讲「怎么组合、怎么验证」，不展开构建变量全集。所有 `option`、`find_package`、缓存变量、命令行开关的名称、默认值与依赖条件，是 04-01「CMake 构建选项全集」的权威范围，本册只在必要处点名族与用法，并统一写「完整清单见 04-01」。同样，结构体逐字段交给 05 册，机制与状态机交给 06 册，目录级模块能力交给 07 册，运维场景与基准交给 08 册。本篇的交叉引用按（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-01）执行。凡本册标注「需对照实际版本核验」的字段、函数名、DAQ module 名与命令选项，均以对应源码文件为准，不凭印象补值；任何构建耗时、产物体积、吞吐类结论一律标注需在目标机型实测，不给绝对值。

### 2. 核心概念

仓库根由「顶层构建文件 + 六个一级目录」构成。顶层已核验存在 `CMakeLists.txt`、`configure_cmake.sh`、`config.cmake.h.in`、`snort.pc.in`、`cmake_uninstall.cmake.in`、`COPYING`、`LICENSE`、`ChangeLog.md`、`README.md`、`crusty.cfg`、`.clang-tidy`、`.gitignore`；一级目录为 `cmake/`、`src/`、`lua/`、`doc/`、`tools/`、`daqs/`。`CMakeLists.txt` 是工程入口，首部 `cmake_minimum_required (VERSION 3.5)` 与 `project (snort CXX C)` 定义工程名与语言，`set (CMAKE_MODULE_PATH "${PROJECT_SOURCE_DIR}/cmake")` 把自定义模块目录挂到模块搜索路径，随后 `include` 进 `macros.cmake`、`create_options.cmake`、`include_libraries.cmake`、`platforms.cmake`、`configure_options.cmake`、`sanity_checks.cmake` 六个模块，并在尾部 `include` 进 `packaging_data.cmake` 与 `create_pkg_config.cmake`。`GNUInstallDirs` 提供安装目录变量，`set (INSTALL_SUFFIX "${CMAKE_PROJECT_NAME}")` 把安装后缀定为工程名，`INCLUDE_INSTALL_PATH`、`LIB_INSTALL_PATH`、`PLUGIN_INSTALL_PATH`（即 `${LIB_INSTALL_PATH}/plugins`）据此推导。

依赖矩阵是本册的核心概念，其权威落点是 `cmake/include_libraries.cmake`。该文件把依赖分成「必选」与「可选」两栏：必选一栏逐行是 `find_package(Threads REQUIRED)`、`find_package(DAQ REQUIRED)`、`find_package(DNET REQUIRED)`、`find_package(FlexLexer REQUIRED)`、`find_package(HWLOC REQUIRED)`、`find_package(LuaJIT REQUIRED)`、`find_package(OpenSSL 1.1.1 REQUIRED)`、`find_package(PCAP REQUIRED)`、`find_package(PCRE2 REQUIRED)`、`find_package(ZLIB REQUIRED)`，另有 `if (ENABLE_UNIT_TESTS) find_package(CppUTest REQUIRED) endif ()` 把单测依赖挂到单测开关上；可选一栏用 `find_package` 的 QUIET 形式 探测 `Atomic`、`LibLZMA`、`Asciidoc`、`DBLATEX`、`Ruby`、`HS`、`SafeC`（在 `ENABLE_SAFEC` 为真时）、`ICONV`、`UUID`、`Libunwind`、`NUMA`、`ML`、`Brotli`。注意这里用的是 `find_package`，不是 `pkg_check_modules`；`pkg_check_modules` 出现在 `cmake/FindDAQ.cmake` 与若干 `Find*.cmake` 内部，属于查找模块的实现细节。`README.md` 的 DEPENDENCIES 一节则从使用者角度列出 CMake、DAQ（libdaq）、dnet、flex、C++17 编译器、hwloc、LuaJIT、OpenSSL、pcap、PCRE2、pkgconfig、zlib，并说明可选包提供额外特性。依赖的最低版本约束写在源码里，具体数值需对照实际版本核验。

「必选」与「可选」的差别不只是装不装，而是能否构建成功。必选项缺失会由 `find_package_handle_standard_args` 一类机制在配置期报错；可选项缺失则由 `sanity_checks.cmake` 的探测结果决定 `config.cmake.h.in` 里 `#cmakedefine HAVE_HYPERSCAN 1`、`#cmakedefine HAVE_LZMA 1`、`#cmakedefine HAVE_ICONV 1` 等编译期宏是否被定义。这正好对应能力边界里的两条硬约束：其一，抓包依赖独立 libdaq / DAQ3，`find_package(DAQ REQUIRED)` 与 `snort.pc.in` 中 `cpp_opts=DAQ LUAJIT` 是这一依赖的元数据佐证，`src/packet_io/sfdaq*.cc` 与 `daqs/` 只是适配层与示例 module，不能写成「Snort 自带抓包、与 DAQ 无关」；其二，Hyperscan 是可选 search_engine 加速，`find_package(HS QUIET)` 与 `HAVE_HYPERSCAN` 只是开关，`src/search_engines/` 内 `hyperscan.cc`、`ac_bnfa.cc`、`ac_full.cc`、`acsmx2.cc`、`bnfa_search.cc` 并存，缺失时回退其他多模式匹配实现，不得写成必需依赖或唯一实现（原理见 06-07，完整清单见 04-01）。

`config.cmake.h.in` 是「构建期变量 → 编译期宏」的模板，经 `CMakeLists.txt` 中 `configure_file ("${PROJECT_SOURCE_DIR}/config.cmake.h.in" "${PROJECT_BINARY_DIR}/config.h")` 生成 `build/config.h`，再由 `add_definitions( -DHAVE_CONFIG_H )` 让源码可见。模板里的 `#define PACKAGE @PROJECT_NAME@`、`#define VERSION "@VERSION@"` 与 `#cmakedefine` 族分别承接工程名、版本字样与 `HAVE_*` / `STATIC_*` / `UNIT_TEST` 等开关。也就是说，「依赖有没有」「选项开没开」最终都以宏的形式进入编译单元，这解释了为什么排障时要先看配置期输出、再看 `config.h`，而不是直接去改源码。`snort.pc.in` 则由 `cmake/create_pkg_config.cmake` 用 `configure_file` 的 @ONLY 形式 生成 `snort.pc` 并安装到 `${CMAKE_INSTALL_LIBDIR}/pkgconfig/`，供第三方插件用 pkg-config 拿到一致的编译选项（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-01）。

### 3. 关键数据结构与源码位置

本节所谓「结构」不是引擎的结构体，而是构建期的文件族、目录族与变量族，按总览册约束只点名、给真实路径，不展开字段表、不重列参数全集；引擎侧的结构体逐字段一律交给 05 册（`Packet`、`SnortConfig`、`BaseApi`、`DAQ_Verdict` 等字段见 05-01 ~ 05-09）。先看 `src/` 顶层：本快照实际存在 `CMakeLists.txt`、`main.cc`、`main.h`、`dev_notes.txt`、`lua_wrap.sh`，以及 `actions/`、`catch/`、`codecs/`、`connectors/`、`control/`、`decompress/`、`detection/`、`dump_config/`、`events/`、`file_api/`、`filters/`、`flow/`、`framework/`、`hash/`、`helpers/`、`host_tracker/`、`ips_options/`、`js_norm/`、`latency/`、`log/`、`loggers/`、`lua/`、`main/`、`managers/`、`memory/`、`mime/`、`mitigator/`、`mp_transport/`、`network_inspectors/`、`packet_io/`、`parser/`、`payload_injector/`、`policy_selectors/`、`ports/`、`profiler/`、`protocols/`、`pub_sub/`、`search_engines/`、`service_inspectors/`、`sfip/`、`sfrt/`、`side_channel/`、`stream/`、`target_based/`、`time/`、`trace/`、`tracer/`、`utils/` 等目录。需要特别说明两处目录事实：大纲中偶见的 `src/decode`、`src/session` 属惯用名，本快照无独立同名目录，解码由 `src/codecs/` 与 `src/protocols/packet.cc` 承担，会话定义位于 `src/flow/session.h` 与 `src/stream/`，均需对照实际版本核验（模块见 07-09、07-10）。

再看 `cmake/`：本快照实际有 `CodeCoverage.cmake`、`compiler_features.cmake`、`configure_options.cmake`、`create_options.cmake`、`create_pkg_config.cmake`、`include_libraries.cmake`、`macros.cmake`、`packaging_data.cmake`、`platforms.cmake`、`sanity_checks.cmake` 十个通用模块，以及 `FindAsciidoc.cmake`、`FindAtomic.cmake`、`FindBrotli.cmake`、`FindCppUTest.cmake`、`FindDAQ.cmake`、`FindDBLATEX.cmake`、`FindDNET.cmake`、`FindFlexLexer.cmake`、`FindHS.cmake`、`FindHWLOC.cmake`、`FindICONV.cmake`、`FindJEMalloc.cmake`、`FindLibunwind.cmake`、`FindLuaJIT.cmake`、`FindML.cmake`、`FindNUMA.cmake`、`FindPCAP.cmake`、`FindPCRE2.cmake`、`FindSafeC.cmake`、`FindTCMalloc.cmake`、`FindTIRPC.cmake`、`FindUUID.cmake` 等查找模块。`Find*` 与 `cmake/` 下的通用模块是「怎么组合」的支点：前者回答「库在哪」，后者回答「开关怎么变成宏、目标怎么组织」。`src/framework/test/`、`src/packet_io/test/`、`src/flow/test/` 等 `test/` 子目录则属于单测设施，本篇只点名，展开见 02-05。

其余三个目录各有明确职责。`lua/` 内已核验 `CMakeLists.txt`、`snort.lua`、`snort_defaults.lua`、`talos.lua`、`inline.lua`、`max_detect.lua`、`balanced.lua`、`connectivity.lua`、`sandbox.lua`、`security.lua`、`sensitive_data.rules`、`file_magic.rules`；`lua/CMakeLists.txt` 用 `LUA_SCRIPTS` 列表 收集这些文件并 `install (FILES ${LUA_SCRIPTS} DESTINATION "${CMAKE_INSTALL_SYSCONFDIR}/snort")`，这就是 `snort.lua` 模板的落位来源。`doc/` 内有 `CMakeLists.txt` 与 `user/`、`reference/`、`upgrade/`、`devel/` 四个子目录，`doc/reference/building.txt` 是本册最直接的官方构建说明。`tools/` 内有 `CMakeLists.txt`、`appid_detector_builder.sh` 与 `snort2lua/`、`u2boat/`、`u2spewfoo/`、`show_flows/` 四个工具目录，`tools/CMakeLists.txt` 逐一 `add_subdirectory`；`daqs/` 内有 `CMakeLists.txt`、`daq_file.c`、`daq_hext.c`、`daq_user.h`。顶层文件与职责的对照见下表。

`src/CMakeLists.txt` 是引擎主体的装配点，值得单独点名：它用 `EXTERNAL_LIBRARIES` 列表 汇总 `DAQ_LIBRARIES`、`DNET_LIBRARIES`、`CLANG_CXX_LIBRARY`、`CMAKE_DL_LIBS`、`CMAKE_THREAD_LIBS_INIT`、`HWLOC_LIBRARIES`、`LUAJIT_LIBRARIES`、`OPENSSL_CRYPTO_LIBRARY`、`PCAP_LIBRARIES`、`PCRE2_LIBRARIES`、`ZLIB_LIBRARIES`，再按 `HAVE_HYPERSCAN`、`HAVE_ICONV`、`HAVE_LIBUNWIND`、`HAVE_LZMA`、`HAVE_NUMA`、`HAVE_SAFEC`、`HAVE_UUID`、`USE_TIRPC`、`HAVE_LIBML`、`HAVE_BROTLI` 等条件 `LIST(APPEND)` 追加可选库；`include_directories(BEFORE ${LUAJIT_INCLUDE_DIR})` 保证 LuaJIT 头优先；`add_executable` 的 `snort` 目标 把各目录的 OBJECT 库与 `${STATIC_CODEC_PLUGINS}`、`${STATIC_NETWORK_INSPECTOR_PLUGINS}`、`${STATIC_SERVICE_INSPECTOR_PLUGINS}` 等静态插件目标收拢成可执行文件，最后 `target_link_libraries( snort ${EXTERNAL_LIBRARIES} ${EXTRA_LIBRARIES})` 与 `install (TARGETS snort RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR})`。这条装配链就是把依赖矩阵变成二进制的地方（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-11）。

### 4. 关键流程与调用链

依赖探测链是理解「为什么先装依赖」的最短路径，其真实调用顺序可以从 `cmake/FindDAQ.cmake` 逐行还原：模块先 `find_package(PkgConfig)`，再 `pkg_check_modules(PC_DAQ libdaq>=3.0.29)`（这是 libdaq 的最低版本约束，具体数值需对照实际版本核验），随后 `find_path(DAQ_INCLUDE_DIR NAMES daq.h HINTS ${DAQ_INCLUDE_DIR_HINT} ${PC_DAQ_INCLUDEDIR} ${PC_DAQ_INCLUDE_DIRS} NO_SYSTEM_ENVIRONMENT_PATH)` 定位 `daq.h`，`find_library(DAQ_LIBRARIES NAMES daq HINTS ${DAQ_LIBRARIES_DIR_HINT} ${PC_DAQ_LIBDIR} ${PC_DAQ_LIBRARY_DIRS})` 定位库文件，再由 `include(FindPackageHandleStandardArgs)` 与 `find_package_handle_standard_args(DAQ REQUIRED_VARS DAQ_LIBRARIES DAQ_INCLUDE_DIR)` 判定成败，最后 `mark_as_advanced(DAQ_INCLUDE_DIR DAQ_LIBRARIES)` 收束缓存项。`configure_cmake.sh` 的 `--with-daq-includes=`、`--with-daq-libraries=` 正是把值写进 `DAQ_INCLUDE_DIR_HINT` 与 `DAQ_LIBRARIES_DIR_HINT` 两个 hint 变量，优先级高于 pkg-config 结果，这也是非标准安装路径能生效的原因。DAQ module 的具体名称需对照实际版本核验，定位目录为 `src/packet_io/sfdaq_module.cc` 与 `daqs/`（原理见 06-02）。

静态 DAQ 模块还有一条并行的探测链。同一文件里 `if (PKG_CONFIG_EXECUTABLE AND ENABLE_STATIC_DAQ)` 分支执行 `execute_process` 调用 `pkg-config --list-all`，用 `string(REGEX MATCHALL "libdaq_static_[^ ]+" AVAILABLE_STATIC_MODULES)` 捞出所有静态模块名，`foreach (STATIC_MODULE IN LISTS AVAILABLE_STATIC_MODULES)` 里以 `string(REGEX REPLACE "^libdaq_static_" "" MODULE_NAME)` 去掉前缀、`list(APPEND DAQ_STATIC_MODULES)` 收集模块名、`pkg_check_modules(PC_${STATIC_MODULE})` 与 `find_library(STATIC_MODULE_LIB)` 收集 `DAQ_STATIC_MODULE_LIBS`，最终把两个列表 以 `set` 的 `CACHE INTERNAL` 形式写入缓存。这两个列表会一路供到 `CMakeLists.txt` 的 Feature options 打印（`DAQ Modules: Static (${DAQ_STATIC_MODULES})`）、`src/CMakeLists.txt` 的 `LIST(APPEND EXTERNAL_LIBRARIES ${DAQ_STATIC_MODULE_LIBS})` 与 `src/packet_io/CMakeLists.txt` 的头文件生成，展开见 02-04。

系统能力探测链落在 `cmake/sanity_checks.cmake`：`include(CheckCXXSourceCompiles)`、`include(CheckFunctionExists)`、`include(CheckTypeSize)`、`include(TestBigEndian)` 之后，`test_big_endian(WORDS_BIGENDIAN)`、`check_function_exists(malloc_trim HAVE_MALLOC_TRIM)`、`check_function_exists(memrchr HAVE_MEMRCHR)`、`check_function_exists(sigaction HAVE_SIGACTION)`、`check_function_exists(basename_r HAVE_BASENAME_R)`、`check_type_size("long int" SIZEOF_LONG_INT)` 逐项写进缓存；`if (HS_FOUND) check_library_exists (${HS_LIBRARIES} hs_scan "" HAVE_HYPERSCAN)` 与 `check_function_exists(hs_compile_lit HAVE_HS_COMPILE_LIT)` 决定 Hyperscan 相关宏，`lzma_code` → `HAVE_LZMA`、`numa_num_possible_cpus` → `HAVE_NUMA`、`backtrace` → `HAVE_LIBUNWIND`、`printf_s` → `HAVE_SAFEC`、`uuid_parse` → `HAVE_UUID` 同理。这些 `HAVE_*` 变量与 `config.cmake.h.in` 里的 `#cmakedefine HAVE_* 1` 一一对应，正是「探测结果变成编译期开关」的闭环。另有 `getrpcent` 缺失时 `find_package(TIRPC)` 回退到 `USE_TIRPC`，属于平台兼容分支。

上述三条链汇合到 `configure_file`：顶层 `CMakeLists.txt` 用它生成 `build/config.h`，`cmake/create_pkg_config.cmake` 用它生成 `build/snort.pc`，`src/packet_io/CMakeLists.txt` 用它生成 `sfdaq_static_modules.h`。三者都是「模板 + 探测变量 → 构建期产物」，区别只在模板内容与消费方。依赖探测与编译期开关生成链路见图 02-01-01。

本册只给「怎么组合、怎么验证」所需的最小命令，构建变量与选项全集一律交给 04-01（完整清单见 04-01）。先看源码获取与仓库确认的闭环：`README.md` 的 DOWNLOAD 一节给出 `git clone https://github.com/snort3/snort3.git` 与源码 tarball 两种获取方式，本套资料以本地快照为准，故用目录列举与 grep 完成「前置检查 → 执行 → 验证输出 → 清理」中的前置检查。


逐行判读如下。第一行是「示例输出」声明，提示文件清单、行号与 grep 结果随快照版本变化，必须以目标版本实际输出为准，不能把行号当固定值。第二到第五行对应第一条 `ls`：四个顶层文件齐备，说明当前工作目录就是真实仓库根 `snort3-master/`；若报 `No such file`，说明还停在上一层的 `snort3/` 归档目录，应再进一层，而不是去别处找脚本。第六到第十七行是 `cmake/` 目录的前十二项，用来确认 `FindDAQ.cmake`、`FindHS.cmake`、`FindLuaJIT.cmake` 一类查找模块与 `CodeCoverage.cmake` 一类通用模块都在；若 `FindDAQ.cmake` 缺失，`find_package(DAQ REQUIRED)` 会在配置期找不到查找模块而失败，正常应为「存在」。第十八行 `cmake/include_libraries.cmake:4:find_package(DAQ REQUIRED)` 是本篇最关键的判据：`REQUIRED` 表明 libdaq 是必选依赖，缺了就无法完成配置；结合 `README.md` 的「DAQ from https://github.com/snort3/libdaq for packet IO」，可确认抓包依赖独立 libdaq / DAQ3，而不是引擎自带（原理见 06-02）。第十九行 `cpp_opts=DAQ LUAJIT` 与第二十行 `cpp_opts_other=DNET HWLOC HYPERSCAN LZMA OPENSSL PCAP PCRE2 UUID` 是 `snort.pc.in` 的依赖分组：前者是核心编译选项，后者是可选特性对应的包；`HYPERSCAN` 出现在 `cpp_opts_other` 而非 `cpp_opts`，正与「Hyperscan 是可选加速、缺失时回退 AC / BNFA」的边界一致（原理见 06-07）。整个检查只读取文件、不生成构建产物、不接流量，属于零副作用的前置核验，清理环节即无文件需要删除，可直接在确认后的目录进入 02-02 的配置步骤。

下面这段摘自 `cmake/FindDAQ.cmake`，用于说明「非标准路径如何被 hint 变量接住」，是本册讲组合方式时最该看的一段真实代码。

```cmake
find_package(PkgConfig)
pkg_check_modules(PC_DAQ libdaq>=3.0.29)
find_path(DAQ_INCLUDE_DIR
    NAMES daq.h
    HINTS ${DAQ_INCLUDE_DIR_HINT} ${PC_DAQ_INCLUDEDIR} ${PC_DAQ_INCLUDE_DIRS}
    NO_SYSTEM_ENVIRONMENT_PATH
)
find_library(DAQ_LIBRARIES
    NAMES daq
    HINTS ${DAQ_LIBRARIES_DIR_HINT} ${PC_DAQ_LIBDIR} ${PC_DAQ_LIBRARY_DIRS}
)
```

这段里 `HINTS` 的先后顺序就是优先级：`DAQ_INCLUDE_DIR_HINT` / `DAQ_LIBRARIES_DIR_HINT` 来自 `configure_cmake.sh` 的 `--with-daq-includes=` / `--with-daq-libraries=`，排在 pkg-config 给出的 `PC_DAQ_INCLUDEDIR` / `PC_DAQ_LIBDIR` 之前。因此当系统里装了多份 libdaq 时，显式指定路径能覆盖默认查找结果；反过来，若 hint 写错而 pkg-config 又找不到，配置期就会报「Could NOT find DAQ」。`NO_SYSTEM_ENVIRONMENT_PATH` 进一步约束了头文件查找范围，避免误命中不相关的同名头。依赖矩阵按必选 / 可选分组归纳见下表，具体查找项与版本约束以 `cmake/include_libraries.cmake`、`README.md` 为准，需对照实际版本核验。

| 分组 | 代表性查找项 | 缺失后果 |
|---|---|---|
| 必选 `REQUIRED` | `DAQ`、`DNET`、`FlexLexer`、`HWLOC` | 配置期报错，无法生成构建文件 |
| 必选 `REQUIRED` | `LuaJIT`、`OpenSSL`、`PCAP`、`PCRE2`、`ZLIB`、`Threads` | 配置期报错，无法生成构建文件 |
| 单测条件必选 | `CppUTest`（`ENABLE_UNIT_TESTS` 开启时） | 单测配置失败，展开见 02-05 |
| 可选 `QUIET` | `HS`、`LibLZMA`、`ICONV`、`Libunwind`、`NUMA` | 对应 `HAVE_*` 宏不定义，功能回退 |
| 可选 `QUIET` | `SafeC`、`UUID`、`ML`、`Brotli`、`Atomic` | 对应 `HAVE_*` 宏不定义，功能回退 |
| 文档相关 | `Asciidoc`、`DBLATEX`、`Ruby` | `MAKE_*_DOC` 被自动关闭 |

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是归档层级。真实仓库根是 `upstream_src/snort3/snort3-master/`，多一层 `snort3-master/`；把脚本或 `cmake/` 平铺到上一层，会让 `sourcedir`、`PROJECT_SOURCE_DIR` 与 `add_subdirectory` 的相对路径整体错位。第二个陷阱是照抄 `doc/reference/building.txt` 里的 `./configure --help`：该文档用的是 Automake 时代的惯用名，本快照对应的真实脚本是 `./configure_cmake.sh --help`，`CMakeLists.txt` 与 `cmake/` 才是当前构建系统，需对照实际版本核验。第三个陷阱是把 DAQ 写成内置抓包：`find_package(DAQ REQUIRED)`、`snort.pc.in` 的 `cpp_opts=DAQ LUAJIT` 与 `src/packet_io/sfdaq*.cc` 共同说明抓包依赖独立 libdaq / DAQ3，DAQ module 决定抓包与内联能力，module 名需对照实际版本核验（原理见 06-02、模块见 07-07）。第四个陷阱是把 Hyperscan 写成必需依赖或唯一实现：`find_package(HS QUIET)` 是可选探测，`config.cmake.h.in` 的 `HAVE_HYPERSCAN` 只是编译期开关，`src/search_engines/` 内 AC / BNFA 回退实现齐备（原理见 06-07）。

第五个陷阱是把配置期 `HAVE_*` 宏当成运行期能力开关。`sanity_checks.cmake` 的探测结果在 `configure_file` 时一次性写入 `config.h`，运行期再改环境变量不会影响已编译的分支；要改变功能面必须重新配置并重新编译。第六个陷阱是忽略 `README.md` 与 `cmake/include_libraries.cmake` 的口径差异：前者是面向使用者的依赖清单，后者是面向构建系统的查找项，二者互补而非重复；例如 `README.md` 明确列出 pkgconfig 用于定位构建依赖，而 `FindDAQ.cmake` 内部正是 `find_package(PkgConfig)` + `pkg_check_modules`。第七个陷阱是把依赖版本约束抄成本套资料的版本号：`pkg_check_modules(PC_DAQ libdaq>=3.0.29)`、`find_package(OpenSSL 1.1.1 REQUIRED)`、`find_package(HS QUIET 4.4.0)` 一类是外部库的最低版本约束，具体数值需对照实际版本核验，本套资料统一写「上游 master 快照（2026-11 抓取）」。第八个陷阱是给绝对性能数字：构建耗时、二进制体积、依赖编译时长一律需在目标机型实测，不给跨机型通用值。

最佳实践可归纳为四步。第一步先定位：进入 `snort3-master/`，用 `ls` 与 `grep` 确认 `CMakeLists.txt`、`configure_cmake.sh`、`cmake/FindDAQ.cmake`、`cmake/include_libraries.cmake` 齐备，避免在上层空目录里折腾。第二步再对齐依赖：按 `cmake/include_libraries.cmake` 的 REQUIRED 一栏逐项安装，libdaq / DAQ3 单独装、且版本约束需对照实际版本核验；可选依赖按需装，装不上就接受对应 `HAVE_*` 宏不定义、功能回退，不要为了「全 ON」硬凑。第三步做一次只读核验：用 `grep` 看 `cpp_opts` 分组、用 `pkg-config` 看 libdaq 是否被系统识别，确认后再进入 02-02 的配置步骤。第四步守去重：本篇只讲目录、依赖与探测链，具体选项名称、默认值、误配后果一律写「完整清单见 04-01」，结构体写「字段见 05-xx」，机制写「原理见 06-xx」，目录能力写「模块见 07-xx」，运维与基准写「见 08-xx」。许可方面记住引擎为 GPLv2（顶层 `COPYING` / `LICENSE`），Talos 规则集有独立许可约束，不能把规则与引擎按同一许可任意分发（详见 01-04）。

## 02-02 CMake 构建配置与构建变体全解

### 1. 背景与动机

认清仓库结构与依赖矩阵之后，真正把源码变成可执行文件的是一条四段链路：`./configure_cmake.sh` → `cmake` → `make`（或 `cmake --build`）→ `make install`。这条链在 `README.md` 的 BUILD SNORT 一节被写成最简形式：`export my_path=/path/to/snorty`、`./configure_cmake.sh --prefix=$my_path`、`cd build`、`make -j $(nproc) install`；但「最简」不等于「只有一种」。Snort 3 把大量能力做成编译期开关：静态 / 动态插件、静态 / 动态 DAQ、debug 与调试消息、单元测试、Sanitizer、文档构建、内存分配器、安全加固等，各开关还会互相约束。若不清楚它们在哪一层被解析、在哪一层变成宏、在哪一层影响链接，就很容易出现「选项明明传了却没生效」「两个开关一起开导致配置期报错」这类问题。本篇的目标不是罗列开关——那是 04-01 的职责——而是把「怎么组合、怎么验证」讲透，并统一写「完整清单见 04-01」。

先声明口径。本套资料版本基准统一为「上游 master 快照（2026-11 抓取）」，具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，需对照实际版本核验；`CMakeLists.txt` 中的 `VERSION_MAJOR` 等变量只作核验依据，不抄作本套版本号。事实锚点仍是 `upstream_src/snort3/snort3-master/`。性能方面，构建耗时、产物体积、不同变体的运行吞吐一律标注需在目标机型实测，不给绝对值；调试构建的性能代价尤其不能拿来做生产基准（基准方法见 08-01）。能力边界继续生效：抓包依赖独立 libdaq / DAQ3，Hyperscan 是可选加速且缺失时回退 AC / BNFA，Snort 不是防火墙、不做 IP 转发，加密载荷不可见，引擎为 GPLv2 且 Talos 规则集有独立许可约束。

「怎么组合」的关键在于理解 `configure_cmake.sh` 只是包装脚本，不是构建系统本体。它的自述注释写着「Convenience wrapper for easily viewing/setting options that the project's CMake scripts will recognize」，开头 `set -e` 与 `type cmake > /dev/null 2>&1` 检查 先确认 CMake 存在；随后把形如 `--enable-FEATURE`、`--disable-FEATURE`、`--with-PACKAGE=DIR`、`--build-type=<类型>` 的参数翻译成 CMake 的 `-D NAME:TYPE=VALUE` 缓存项，最终拼出一条 `cmake` 命令。换言之，跳过它直接用 `cmake -DENABLE_FOO=ON` 一类写法 完全合法，`README.md` 也明说「If you are familiar with cmake, you can run cmake/ccmake instead of configure_cmake.sh」，而 `cmake/create_options.cmake` 的注释甚至直接给出 `cmake -DENABLE_FOO=ON -DCMAKE_INSTALL_PREFIX=/my/install/path $cmake_src_path` 的写法。理解这一点，就能把「脚本选项」与「CMake 缓存变量」看成同一件事的两种入口。

### 2. 核心概念

`configure_cmake.sh` 的组织可以拆成四段。第一段是默认值：`builddir=build`、`prefix=/usr/local/snort`、`CMakeCacheEntries=""`，并由 `append_cache_entry () { CMakeCacheEntries="$CMakeCacheEntries -D $1:$2=$3"; }` 定义统一的缓存项追加函数，首次调用即 `append_cache_entry CMAKE_INSTALL_PREFIX PATH $prefix`。第二段是构建类型推断：`build_type=""`，且 `[ -z "$CFLAGS" ] && [ -z "$CXXFLAGS" ] && build_type="RelWithDebInfo"`，即仅当两个环境变量都为空时才默认 `RelWithDebInfo`；`--build-type=` 只接受 `Debug`、`Release`、`RelWithDebInfo`、`MinSizeRel` 四种取值，否则 `echo` 报无效构建类型 并 `exit 1`。第三段是参数解析：`while [ $# -ne 0 ]` 里用 `case "$1" in` 逐项匹配，`--enable-*` / `--disable-*` 经 `append_cache_entry` 写入 `BOOL` 类型的缓存项，`--with-*-includes=` / `--with-*-libraries=` 写入 `PATH` 类型的 hint 变量，`--define=`、`--generator=`、`--builddir=`、`--prefix=` 各有对应分支，`SNORT_BUILD_NUMBER=` 一类落到 `STRING` 缓存项。第四段是执行与留痕：若 `$builddir` 已存在且含 `CMakeCache.txt` 则 `rm -f $builddir/CMakeCache.txt`（避免被上一次配置污染），否则 `mkdir -p $builddir`；`echo "Build Directory : $builddir"` 与 `echo "Source Directory: $sourcedir"` 打印路径，`cd $builddir` 后拼出 `cmake "$gen" -DCMAKE_CXX_FLAGS:STRING="$CXXFLAGS $CPPFLAGS" -DCMAKE_C_FLAGS:STRING="$CFLAGS $CPPFLAGS" -DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DCMAKE_BUILD_TYPE:STRING=$build_type $CMakeCacheEntries $sourcedir`；最后写 `config.status`（首行注释 `# This is the command used to configure this build`，随后 `echo $command`、`chmod u+x config.status`）留作可复现记录。

CMake 侧的骨架由顶层 `CMakeLists.txt` 给出：`cmake_minimum_required (VERSION 3.5)`、`project (snort CXX C)`、语言标准 `set (CMAKE_CXX_STANDARD 17)` / `set (CMAKE_C_STANDARD 99)`、`set (CMAKE_EXPORT_COMPILE_COMMANDS ON)`（便于 clangd 等 IDE 工具读取 `compile_commands.json`），再由 `set (CMAKE_MODULE_PATH "${PROJECT_SOURCE_DIR}/cmake")` 与一串 `include` 载入 `macros.cmake`、`create_options.cmake`、`include_libraries.cmake`、`platforms.cmake`、`configure_options.cmake`、`sanity_checks.cmake`。模块各司其职：`create_options.cmake` 用一连串 `option` 与 `set` 的 CACHE 形式 声明所有用户可选项并写进缓存；`include_libraries.cmake` 做依赖查找；`platforms.cmake` 处理 `APPLE` / `CMAKE_SKIP_RPATH` / `-fvisibility=hidden` 等平台差异；`configure_options.cmake` 把 cmake 选项映射为编译期宏与编译标志；`sanity_checks.cmake` 做系统能力探测；`macros.cmake` 定义 `add_dynamic_module`、`add_dynamic_daq_module`、`add_cpputest`、`add_catch_test`、`add_fuzzer` 等构建函数。选项全集、默认值与依赖条件属于 04-01，本册不重列，只按族点名（完整清单见 04-01）。

「选项 → 宏 → 标志」的三层转换是本篇最该建立的概念。`cmake/configure_options.cmake` 开头就写明「map cmake options to compiler defines and do miscellaneous further configuration work」，其映射如 `set ( SHELL ${ENABLE_SHELL} )`、`set ( UNIT_TEST ${ENABLE_UNIT_TESTS} )`、`set ( _LARGEFILE_SOURCE ${ENABLE_LARGE_PCAP} )`、`set ( USE_STDLOG ${ENABLE_STDLOG} )`、`set ( NO_PROFILER ${DISABLE_SNORT_PROFILER} )`、`set ( DEBUG_MSGS ${ENABLE_DEBUG_MSGS} )`，这些变量随后被 `config.cmake.h.in` 的 `#cmakedefine` 消费。另一路是编译标志：`if ( ENABLE_DEBUG ) string ( APPEND DEBUGGING_C_FLAGS " -g -DDEBUG" ) else () string ( APPEND DEBUGGING_C_FLAGS " -DNDEBUG" )`、`if ( ENABLE_GDB )` 追加 `" -g -ggdb"`，以及 `ENABLE_HARDENED_BUILD` 下逐条 `check_cxx_compiler_flag` 后追加 `-Wdate-time`、`-D_FORTIFY_SOURCE=2`、`-fstack-protector-strong`、`-Wformat`、`-Werror=format-security`、`-Wl,-z,relro`、`-Wl,-z,now`。末尾 `EXTRA_C_FLAGS`、`EXTRA_CXX_FLAGS`、`EXTRA_LINKER_FLAGS` 三个变量 把各路标志汇总，顶层 `CMakeLists.txt` 再用 `string(APPEND CMAKE_C_FLAGS " ${EXTRA_C_FLAGS}")`、`string(APPEND CMAKE_CXX_FLAGS " ${EXTRA_CXX_FLAGS}")`、`string(APPEND CMAKE_EXE_LINKER_FLAGS " ${EXTRA_LINKER_FLAGS}")` 注入全局编译环境——注意注释明确要求这些 `string(APPEND)` 必须在所有测试做完之后、任何 `add_subdirectory` 之前执行，顺序错了标志就传不到子目录。

验证面同样有两处产物。其一是配置期输出：`CMakeLists.txt` 尾部的 `message` 块逐条打印 `Install options`（`prefix`、`includes`、`plugins`）、`Compiler options`（`CC`、`CXX`、`CFLAGS`、`CXXFLAGS`、`EXE_LDFLAGS`、`MODULE_LDFLAGS`）与 `Feature options`（`DAQ Modules: Static (${DAQ_STATIC_MODULES})` / `Dynamic`、`Hyperscan: ON/OFF`、`ICONV`、`Libunwind`、`LZMA`、`RPC DB`、`SafeC`、`TCMalloc`、`JEMalloc`、`UUID`、`NUMA`、`LibML`、`Brotli`、`CrashMitigator`），这是判断「组合是否生效」的第一现场。其二是 `cmake/create_pkg_config.cmake`：它设置 `prefix`、`exec_prefix`、`bindir`、`libdir`、`includedir` 等 pkg-config 变量，按 `ENABLE_MEMORY_PROFILER`、`DISABLE_TENANT_ID`、`CRASH_MITIGATOR`、`ENABLE_RULE_PROFILER`、`DISABLE_SNORT_PROFILER`、`ENABLE_DEEP_PROFILING`、`ENABLE_TSC_CLOCK`、各 `*_INCLUDE_DIR` 等条件拼出 `*_CPPFLAGS`，再 `configure_file("${CMAKE_SOURCE_DIR}/snort.pc.in" "${CMAKE_BINARY_DIR}/snort.pc" @ONLY)` 并 `install` 规则装到 `${CMAKE_INSTALL_LIBDIR}/pkgconfig/`。生成的 `snort.pc` 里 `cpp_opts=DAQ LUAJIT`、`cpp_opts_other=DNET HWLOC HYPERSCAN LZMA OPENSSL PCAP PCRE2 UUID`、`Cflags: -I${includedir}/snort` 开头 会带上本次组合的编译开关，第三方插件据此对齐 ABI（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-01）。

### 3. 关键数据结构与源码位置

本节只点名构建期的选项族、宏族与产物，不展开字段表、不重列参数全集；引擎侧结构体一律写「字段见 05-xx」。`cmake/create_options.cmake` 的 `option` 声明 按注释分组可归为六族：静态 / 动态族（`STATIC_CODECS`、`STATIC_INSPECTORS`、`STATIC_LOGGERS`、`STATIC_IPS_ACTIONS`、`STATIC_IPS_OPTIONS`、`STATIC_SEARCH_ENGINES`、`STATIC_TRACERS`、`ENABLE_STATIC_DAQ`）、特性族（`ENABLE_SHELL`、`ENABLE_UNIT_TESTS`、`ENABLE_BENCHMARK_TESTS`、`DISABLE_TENANT_ID`、`ALLOWLIST_MOVE_ON_EXCESS`、`ENABLE_LARGE_PCAP`、`ENABLE_STDLOG`、`ENABLE_TSC_CLOCK`、`ENABLE_CRASH_MITIGATOR`、`ENABLE_FUZZERS`）、文档族（`MAKE_HTML_DOC`、`MAKE_PDF_DOC`、`MAKE_TEXT_DOC`、`MAKE_DOC`）、安全族（`ENABLE_HARDENED_BUILD`、`ENABLE_PIE`、`ENABLE_SAFEC`）、调试族（`ENABLE_DEBUG_MSGS`、`ENABLE_DEBUG`、`ENABLE_GDB`、`ENABLE_PROFILE`、`DISABLE_SNORT_PROFILER`、`ENABLE_DEEP_PROFILING`、`ENABLE_MEMORY_PROFILER`、`ENABLE_RULE_PROFILER`、`ENABLE_ADDRESS_SANITIZER`、`ENABLE_THREAD_SANITIZER`、`ENABLE_UB_SANITIZER`、`ENABLE_TCMALLOC`、`ENABLE_JEMALLOC`、`ENABLE_CODE_COVERAGE`）、信号族（`SIGNAL_SNORT_RELOAD "SIGHUP"`、`SIGNAL_SNORT_DUMP_STATS "SIGUSR1"`、`SIGNAL_SNORT_ROTATE_STATS "SIGUSR2"`、`SIGNAL_SNORT_READ_ATTR_TBL "SIGURG"`）。以上仅为定位用点名，具体默认值、依赖条件与误配后果属于 04-01（完整清单见 04-01）。

`config.cmake.h.in` 的宏族与上述选项一一呼应：用户选项区有 `DEBUG_MSGS`、`PROFILE`、`NOCOREFILE`、`SHELL`、`STATIC_CODECS`、`STATIC_INSPECTORS`、`STATIC_IPS_ACTIONS`、`STATIC_IPS_OPTIONS`、`STATIC_LOGGERS`、`STATIC_SEARCH_ENGINES`、`STATIC_TRACERS`、`UNIT_TEST`、`USE_STDLOG`、`USE_TSC_CLOCK`、`NO_PROFILER`、`ENABLE_MEMORY_PROFILER`、`DISABLE_TENANT_ID`、`ALLOWLIST_MOVE_ON_EXCESS`、`ENABLE_RULE_PROFILER`、`DEEP_PROFILING`、`ENABLE_MEMORY_OVERLOADS`、`CRASH_MITIGATOR` 与四个 `SIGNAL_SNORT_*`；库可用区有 `HAVE_HYPERSCAN`、`HAVE_HS_COMPILE_LIT`、`HAVE_ICONV`、`HAVE_LIBUNWIND`、`HAVE_LZMA`、`HAVE_SAFEC`、`HAVE_JEMALLOC`、`HAVE_CISCO_SHIM`、`HAVE_UUID`、`USE_TIRPC`、`HAVE_NUMA`、`HAVE_LIBML`、`USE_LIBML_MOCK`、`HAVE_BROTLI`；函数可用区有 `HAVE_MALLOC_TRIM`、`HAVE_MEMRCHR`、`HAVE_SIGACTION`、`HAVE_GNU_STRERROR_R`、`HAVE_BASENAME_R`；编译器区有 `HAVE_VISIBILITY`、`USE_THREAD_LOCAL`。模板顶部 `#ifndef __CONFIG_H__` / `#define __CONFIG_H__` 与注释里「go to your build directory, and type `ccmake ${PATH_TO_SOURCE}`」也提示了另一种改选项的入口。构建期模块职责对照见下表。

| 构建期文件 | 职责 | 关联产物 |
|---|---|---|
| `configure_cmake.sh` | 选项翻译为 `-D` 缓存项 | `build/`、`config.status` |
| `cmake/create_options.cmake` | 声明 `option` 与缓存变量 | CMake 缓存 |
| `cmake/include_libraries.cmake` | 必选 / 可选依赖查找 | `*_FOUND` 变量 |
| `cmake/configure_options.cmake` | 选项映射为宏与编译标志 | `EXTRA_*_FLAGS` |
| `cmake/sanity_checks.cmake` | 系统函数与库符号探测 | `HAVE_*` 变量 |
| `config.cmake.h.in` | 编译期宏模板 | `build/config.h` |
| `cmake/create_pkg_config.cmake` | 生成 pkg-config 元数据 | `build/snort.pc` |
| `CMakeLists.txt` | include 顺序、子目录、Feature 输出 | 构建树与安装树 |

`src/CMakeLists.txt` 是这些宏与标志的最终消费方之一：`if (ENABLE_UNIT_TESTS) enable_testing()`、`set( UNIT_TESTS_LIBRARIES $<TARGET_OBJECTS:catch_tests>)`、`add_subdirectory(catch)`、`add_executable` 的 `snort` 目标、`target_link_libraries( snort ${EXTERNAL_LIBRARIES} ${EXTRA_LIBRARIES})`、`if ( CRASH_MITIGATOR ) target_link_libraries( snort mitigator )`、`set_property(TARGET snort PROPERTY ENABLE_EXPORTS 1)`、`install (TARGETS snort RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR})`。`src/codecs/CMakeLists.txt` 则给出静态插件挂接的最小样本：`if (STATIC_CODECS)` 时把 `$<TARGET_OBJECTS:ip_codecs>`、`link_codecs`、`misc_codecs`、`root_codecs` 收进 `STATIC_CODEC_PLUGINS`，`else()` 时只收 `ip_codecs` 与 `misc_codecs`，两者都 `CACHE INTERNAL "STATIC_CODEC_PLUGINS"`。可见「静态 / 动态」不是抽象说法，而是直接决定哪些 OBJECT 库被收进 `snort` 可执行文件（模块见 07-01、07-09，字段见 05-04）。

### 4. 关键流程与调用链

把四段链路按调用顺序展开，配置期是这样的：`configure_cmake.sh` 解析参数生成 `CMakeCacheEntries` → 处理 `builddir`（删旧 `CMakeCache.txt` 或新建）→ `cd $builddir` → 执行 `cmake` 命令带 `$CMakeCacheEntries` 与 `$sourcedir` → CMake 读取顶层 `CMakeLists.txt` → `include(GNUInstallDirs)` 与六个 `cmake/` 模块 → `create_options.cmake` 声明缓存项、`include_libraries.cmake` 做 `find_package`、`platforms.cmake` 处理平台标志、`configure_options.cmake` 做选项到宏 / 标志的映射、`sanity_checks.cmake` 做 `check_*` 探测 → `configure_file` 生成 `config.h` → `add_definitions( -DHAVE_CONFIG_H )` → `string(APPEND CMAKE_*_FLAGS " ${EXTRA_*_FLAGS}")` → `add_subdirectory (src)`、`(tools)`、`(lua)`、`(daqs)` 与条件性的 `(doc)` → 尾部 `include(packaging_data.cmake)`、`include(create_pkg_config.cmake)` 与 `message` 打印 Install / Compiler / Feature options → 生成构建文件与 `snort.pc`、`config.status`。这条链里，`configure_options.cmake` 的 `EXTRA_*_FLAGS` 必须早于 `add_subdirectory` 注入，是「组合生效」的关键时序点。

构建期与安装期随之展开：`make -j $(nproc)`（或 `cmake --build build -j`）按 `src/CMakeLists.txt` 的 OBJECT 库与 `add_executable` 的 `snort` 目标 编译链接，`make install` 按各处 `install` 规则 落位——`snort` 到 `${CMAKE_INSTALL_BINDIR}`、Lua 脚本由 `lua/CMakeLists.txt` 装到 `${CMAKE_INSTALL_SYSCONFDIR}/snort`、`snort.pc` 到 `${CMAKE_INSTALL_LIBDIR}/pkgconfig/`、头文件到 `${INCLUDE_INSTALL_PATH}` 各子目录、DAQ 示例 module 到 `${LIB_INSTALL_PATH}/daq`、插件到 `${PLUGIN_INSTALL_PATH}`（即 `${LIB_INSTALL_PATH}/plugins`）。`README.md` 里 `$my_path/bin/snort`、`$my_path/etc/snort/snort.lua`、`$my_path/share/doc/snort/snort_manual.pdf` 正是这些安装路径的具体化。配置注入与四段链路的关系见图 02-02-01。

图 02-02-01 中实线是配置到产物的主链，`n5 → n6` 与 `n5 → n7` 是同一个「选项映射」动作的两条出口：一条生成编译期宏模板，一条注入全局编译标志；`n1 → n8` 的虚线表示 `config.status` 只是可复现留痕，不参与编译。若某个开关看起来「没生效」，按图排查的顺序应是先看 `n2` 的缓存项是否写对、再看 `n5` 是否被映射、最后看 `n6` 的 `config.h` 里对应宏是否存在，而不是一上来改源码。

三种典型变体的差别只在「组合哪些开关」，不改动链路本身，归纳见下表；具体选项名称与取值属于 04-01（完整清单见 04-01），本表只给语义化组合。生产 IDS 变体偏向静态插件、关闭调试与单测、按需启用加固与可选加速；内联 IPS 变体在此基础上强调 DAQ 相关组合与 verdict 能力，但必须记住 Snort 不是防火墙、不做 IP 转发，丢弃经 DAQ verdict 反馈（原理见 06-12）；调试带单测变体启用 `ENABLE_UNIT_TESTS` 与调试消息 / Sanitizer，并接受明显的性能代价，不可用作生产基准（展开见 02-05，基准方法见 08-01）。

| 变体 | 组合侧重 | 产物形态与约束 |
|---|---|---|
| 生产 IDS | 静态插件、关闭调试与单测、按需加固 | 精简 `snort` 可执行文件，可选加速需实测 |
| 内联 IPS | 在生产组合上叠加 DAQ 与内联相关组合 | 依赖独立 libdaq / DAQ3，非防火墙 |
| 调试带单测 | debug / debug-msgs / 单测 / Sanitizer | 含 `check` 与测试目标，性能代价高 |
| 文档构建 | `MAKE_DOC` 及其 HTML / PDF / TEXT 子项 | 需 `Asciidoc` 等工具，缺则自动关闭 |

### 5. 配置/命令/代码实例

下面这组是「前置检查 → 执行 → 验证输出 → 清理」闭环的最小完整写法，命令形态参考 `README.md` 的 BUILD SNORT 与 `configure_cmake.sh` 的参数（具体选项需对照实际版本核验，完整清单见 04-01）。

```bash
export my_path=/opt/snorty
./configure_cmake.sh --prefix=$my_path --builddir=build
cd build
make -j "$(nproc)"
make install
```

逐行判读如下。第一行是「示例输出」声明，提示版本字样、路径、编译器与 Feature 开关的实际排版随版本与本机环境变化，不能当固定格式解析，更不能把该行的版本字样抄成本套版本号。第二、三行是 `configure_cmake.sh` 里 `echo "Build Directory : $builddir"` 与 `echo "Source Directory: $sourcedir"` 的真实输出，正常应看到 `build` 与真实仓库根；若 `Source Directory` 指向上一层归档目录，说明又踩了「多一层 `snort3-master/`」的坑，应回到 02-01 重新定位。第四行起是 `CMakeLists.txt` 尾部 `message` 块的分隔线与版本行，`VERSION` 来自构建期变量，只用于确认「当前构建对应哪份源码」，不用于推断功能边界。第五到第七行是 `Install options`：`prefix` 应等于 `--prefix` 传入值，`includes` 由 `${CMAKE_INSTALL_FULL_INCLUDEDIR}/${INSTALL_SUFFIX}` 推导，`plugins` 由 `${CMAKE_INSTALL_FULL_LIBDIR}/${INSTALL_SUFFIX}` 推导；三者不一致通常意味着 `CMAKE_INSTALL_PREFIX` 被别的 `-D` 覆盖，应查 `config.status` 与 `CMakeCache.txt`。第八到第十一行是 `Compiler options`：`CC` / `CXX` 反映实际编译器，`CFLAGS` / `CXXFLAGS` 已含 `configure_options.cmake` 汇总的 `EXTRA_*_FLAGS`，若发现 `-g -DDEBUG` 或 `-fsanitize=address` 出现在预期为生产的构建里，说明调试 / Sanitizer 开关被误开，需重新配置（调试与 Sanitizer 展开见 02-05）。第十二到第十七行是 `Feature options`：`DAQ Modules: Dynamic` 对应 `if (ENABLE_STATIC_DAQ)` 为假时的分支，若为 `Static` 形式 则会列出 `DAQ_STATIC_MODULES`（展开见 02-04）；`Hyperscan: OFF` 说明本次未探测到 HS 或开关未开，属于可接受状态，因为 Hyperscan 是可选加速、缺失时回退 `src/search_engines/` 内 AC / BNFA 实现（原理见 06-07）；`TCMalloc` / `JEMalloc` / `NUMA` 为 OFF 同样是可选项未启用，不是故障。最后一行 `config.status` 由脚本尾部写出，可用于复现本次配置；清理环节若需换变体，应删除 `build/CMakeCache.txt` 或换一个 `--builddir`，脚本本身也会在复用目录时主动删除旧缓存。整个流程不接流量、不改源码，属于可重复的构建验证。

下面这段摘自顶层 `CMakeLists.txt`，用于说明「选项映射后的标志如何注入、子目录如何组织」，是本册讲组合方式时最该看的一段真实代码。

```cmake
configure_file (
    "${PROJECT_SOURCE_DIR}/config.cmake.h.in"
    "${PROJECT_BINARY_DIR}/config.h"
)
add_definitions( -DHAVE_CONFIG_H )
string(APPEND CMAKE_C_FLAGS " ${EXTRA_C_FLAGS}")
string(APPEND CMAKE_CXX_FLAGS " ${EXTRA_CXX_FLAGS}")
string(APPEND CMAKE_EXE_LINKER_FLAGS " ${EXTRA_LINKER_FLAGS}")
include_directories (${PROJECT_BINARY_DIR})
include_directories (${PROJECT_SOURCE_DIR})
if (ENABLE_UNIT_TESTS)
    include(CTest)
endif (ENABLE_UNIT_TESTS)
if (ENABLE_UNIT_TESTS OR ENABLE_BENCHMARK_TESTS)
    add_custom_target (check COMMAND ${CMAKE_CTEST_COMMAND})
endif (ENABLE_UNIT_TESTS OR ENABLE_BENCHMARK_TESTS)
add_subdirectory (src)
add_subdirectory (tools)
add_subdirectory (lua)
add_subdirectory (daqs)
if ( MAKE_DOC )
    add_subdirectory (doc)
endif ( MAKE_DOC )
```

`configure_file` 与 `add_definitions` 让每个编译单元都能看到 `config.h`；三条 三条 `string(APPEND)` 语句 把 `configure_options.cmake` 汇总的 `EXTRA_C_FLAGS` / `EXTRA_CXX_FLAGS` / `EXTRA_LINKER_FLAGS` 注入全局，注释明确要求这一步必须在 `add_subdirectory` 之前，否则子目录里的 OBJECT 库拿不到标志。`if (ENABLE_UNIT_TESTS)` 分支 `include(CTest)` 与 `add_custom_target (check COMMAND ${CMAKE_CTEST_COMMAND})` 是单测入口（展开见 02-05）；末尾四个 `add_subdirectory` 与条件性的 `doc` 对应图 02-02-01 的 `n7`。这段也解释了为什么 `--disable-static-codecs` 一类开关能影响最终二进制：它经缓存项 → `configure_options.cmake` → `STATIC_CODECS` 宏 → `src/codecs/CMakeLists.txt` 的 `if (STATIC_CODECS)` → `STATIC_CODEC_PLUGINS` → `add_executable` 的 `snort` 目标，是一整条可追溯的链。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是复用构建目录却不清理缓存。`configure_cmake.sh` 会主动 `rm -f $builddir/CMakeCache.txt`，但直接用 `cmake` 的人若沿用旧 `build/`，上一次的 `-D` 缓存项仍在，很容易出现「换了开关却没变化」；稳妥做法是换 `--builddir` 或显式删缓存后重新配置。第二个陷阱是环境变量与 `build_type` 的相互作用：脚本里 `[ -z "$CFLAGS" ] && [ -z "$CXXFLAGS" ] && build_type="RelWithDebInfo"` 说明只要任一变量非空，默认构建类型就为空，此时 `--build-type=` 的显式指定更重要；`cmake` 调用里 `-DCMAKE_CXX_FLAGS:STRING="$CXXFLAGS $CPPFLAGS"` 也会把外部标志带进来，排障时要一并核对。第三个陷阱是互斥开关：`configure_cmake.sh` 里 `if ((tcm == 1)) ; then if ((jem == 1))` 会报 `--enable-jemalloc and --enable-tcmalloc are mutually exclusive; enable at most one` 并 `exit 2`；`cmake/configure_options.cmake` 里 ASAN 与 TSAN 有一段注释写明「ASAN and TSAN are mutually exclusive」，TCMalloc / JEMalloc 与 ASAN 同开还会 `message ( SEND_ERROR "TCMalloc cannot be used at the same time as address sanitizer!" )`；`ENABLE_FUZZERS` 在既无 `LIB_FUZZING_ENGINE` 又无 `ENABLE_FUZZ_SANITIZER` 时会 `FATAL_ERROR`。这些约束属于「怎么组合」的硬边界，展开见 02-05。

第四个陷阱是把 `--prefix` 默认值当成推荐值。脚本默认 `prefix=/usr/local/snort`，生产部署应显式 `--prefix` 到独立目录，避免与系统包混装；`README.md` 也用 `export my_path=/path/to/snorty` 演示独立路径。第五个陷阱是以为文档一定会被构建：`cmake/configure_options.cmake` 里 `if ( NOT ASCIIDOC_FOUND )` 分支把 `MAKE_HTML_DOC` 强制设为 OFF、`if ( NOT (DBLATEX_FOUND AND ASCIIDOC_FOUND) )` 与 `if ( NOT (W3M_FOUND AND ASCIIDOC_FOUND) )` 会在工具缺失时强制关闭对应 `MAKE_*_DOC`，顶层 `CMakeLists.txt` 的 `if ( MAKE_DOC ) add_subdirectory (doc)` 又是一道总闸。第六个陷阱是忽略 `config.h` 与 `snort.pc` 的一致性：`create_pkg_config.cmake` 按本次组合生成 `*_CPPFLAGS`，第三方插件若用旧的 `snort.pc` 编译，宏定义可能与引擎二进制不一致，重新配置后应一并重新安装 pkg-config 文件。第七个陷阱是把调试变体当生产基准或用绝对吞吐数字下结论：调试构建带 `-g -DDEBUG`、profiling 与 Sanitizer 插桩，性能代价明显，任何吞吐、pps、内存占用一律需在目标机型实测（基准方法见 08-01、调优见 08-02）。第八个陷阱是在本册重列选项全集：02 册只讲组合与验证，选项名称、默认值、依赖条件、误配后果一律「完整清单见 04-01」。

最佳实践可归纳为「一记录、二核对、三隔离」。一记录：每次配置都保留 `config.status`，并用 `--builddir` 给不同变体独立目录，便于回溯与 A/B 对照。二核对：配置完成后先读 `message` 打印的 Install / Compiler / Feature options 三段，再 `grep` 生成的 `config.h` 确认关键宏，最后用 `snort -V`、`snort --help`、`snort -T` 一类命令验证二进制（具体选项需对照实际版本核验，完整命令见 04-07，配置自检展开见 02-03）。三隔离：生产变体与调试 / 单测变体分开构建与安装，不让 Sanitizer 或 debug 标志混入生产二进制；涉及 DAQ 与内联的组合单独验证 verdict 行为，但始终记住 Snort 不是防火墙、不做 IP 转发（原理见 06-12）。许可与规则集方面，引擎按 GPLv2、Talos 规则集独立许可，不混同分发（详见 01-04）。

### 7. 小结与延伸阅读

本篇把 02 册的核心链路钉成一句话：`configure_cmake.sh` 把 `--enable-*` / `--disable-*` / `--with-*` 翻译成 `-D NAME:TYPE=VALUE` 缓存项并调用 `cmake`，顶层 `CMakeLists.txt` 依次 `include` 六个 `cmake/` 模块，`create_options.cmake` 声明选项、`include_libraries.cmake` 查依赖、`platforms.cmake` 处理平台、`configure_options.cmake` 把选项映射为编译期宏与 `EXTRA_*_FLAGS`、`sanity_checks.cmake` 做系统探测，再由 `configure_file` 生成 `config.h` 与 `snort.pc`、`string(APPEND)` 注入全局、`add_subdirectory` 组织 `src`/`tools`/`lua`/`daqs`/`doc`，最后 `make` 与 `make install` 落位。三种典型变体（生产 IDS、内联 IPS、调试带单测）只是组合不同，链路不变；图 02-02-01 给出配置注入点，配置期 `message` 输出与 `config.status` 则是「怎么验证」的两个第一现场。

延伸阅读按用途分：使用者视角读 `README.md` 的 BUILD SNORT 与 `doc/reference/building.txt`（后者点明 `--enable-shell`、`--enable-tsc-clock` 必须显式启用，hyperscan / iconv / libunwind / lzma / safec 依赖满足即自动启用，并给出 `--with-pkg-includes`、`--with-pkg-libraries` 的非标准路径写法）；链路视角读 `configure_cmake.sh`、顶层 `CMakeLists.txt`、`cmake/create_options.cmake`、`cmake/configure_options.cmake`、`cmake/platforms.cmake`、`cmake/create_pkg_config.cmake` 与 `config.cmake.h.in`、`snort.pc.in`；装配视角读 `src/CMakeLists.txt` 与 `src/codecs/CMakeLists.txt`。本册衔接篇为 02-01（目录与依赖矩阵）、02-03（从零构建实战）、02-04（DAQ3 与插件构建）、02-05（调试与单测）。跨册随查统一按（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-01）执行；凡标注「需对照实际版本核验」的选项名、版本字样、命令参数与 DAQ module 名，均以 `_snort_build/upstream_src/snort3/snort3-master/` 下对应文件为准，本套资料不编造未经核验的路径与取值，性能与容量结论一律需在目标机型实测。

## 02-03 从零构建实战：Linux 编译、测试与安装

### 1. 目标与拓扑

本篇给一次可复现的落地：在一台 Linux 主机上，从安装依赖开始，经 `./configure_cmake.sh` 配置、`cmake --build` 编译、`ctest` 跑单测、`make install` 落位，最后用 `snort -V`、`snort --help`、`snort -T` 验证二进制与配置，形成「前置检查 → 执行 → 验证输出 → 清理」的完整闭环。02-02 讲的是链路与变体，本篇讲的是一次具体的操作序列，二者互补：链路里的每一步在这里都有对应命令，命令背后的开关仍写「完整清单见 04-01」，不重列构建变量全集。版本基准统一为「上游 master 快照（2026-11 抓取）」，具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，需对照实际版本核验；事实锚点是 `_snort_build/upstream_src/snort3/snort3-master/`，注意归档多一层 `snort3-master/`。

拓扑上有四个彼此分离的位置，先分清才不会互相污染。第一是源码根，即 `snort3-master/`，只读，不在其中生成中间文件；第二是构建目录，默认 `build/`，由 `configure_cmake.sh` 自动 `mkdir -p`，所有 `config.h`、`snort.pc`、`CMakeCache.txt`、OBJECT 库与可执行文件都落在其中；第三是安装前缀，由 `--prefix=` 指定，`make install` 把 `snort` 可执行文件、Lua 配置模板、头文件、pkg-config 文件按各自 `install` 规则复制过去，与构建目录解耦；第四是系统依赖位置，即 libdaq / DAQ3、LuaJIT、pcap、PCRE2、OpenSSL、zlib 等由包管理器或源码安装到系统路径的库，运行时靠动态链接器或 `LD_LIBRARY_PATH` 找到。把构建目录与安装前缀分开，是为了能同时保留多个变体、也便于升级时单独回滚安装树。

必须贯穿全篇的边界有四条。其一，抓包依赖独立 libdaq / DAQ3，`cmake/include_libraries.cmake` 的 `find_package(DAQ REQUIRED)` 是配置期硬门槛，`src/packet_io/sfdaq*.cc` 与 `daqs/` 只是适配层与示例 module，DAQ module 名需对照实际版本核验（原理见 06-02）。其二，Hyperscan 是可选加速，`find_package(HS QUIET)` 缺失时回退 `src/search_engines/` 内 AC / BNFA 实现，不是构建能否成功的前提（原理见 06-07）。其三，Snort 不是防火墙、不做 IP 转发，内联丢弃经 DAQ verdict 反馈（原理见 06-12）。其四，任何构建耗时、产物体积、启动后的吞吐与内存占用一律需在目标机型实测，不给绝对值。

### 2. 前置条件与环境

依赖清单以 `cmake/include_libraries.cmake` 与 `README.md` 为准。必选一栏是 `find_package(Threads REQUIRED)`、`find_package(DAQ REQUIRED)`、`find_package(DNET REQUIRED)`、`find_package(FlexLexer REQUIRED)`、`find_package(HWLOC REQUIRED)`、`find_package(LuaJIT REQUIRED)`、`find_package(OpenSSL 1.1.1 REQUIRED)`、`find_package(PCAP REQUIRED)`、`find_package(PCRE2 REQUIRED)`、`find_package(ZLIB REQUIRED)`；`README.md` 从使用者角度补充 CMake、dnet、flex、C++17 编译器、hwloc、LuaJIT、OpenSSL、pcap、PCRE2、pkgconfig、zlib 与 DAQ（libdaq）。可选一栏如 `HS`、`LibLZMA`、`ICONV`、`Libunwind`、`NUMA`、`SafeC`、`UUID` 以 QUIET 方式探测，装不上不影响构建成功，只是 `config.cmake.h.in` 里对应 `HAVE_*` 宏不定义。依赖的最低版本约束写在源码里，具体数值需对照实际版本核验，本套资料不抄作自身版本号。

libdaq / DAQ3 值得单独说。它是独立仓库、独立安装的依赖，`cmake/FindDAQ.cmake` 用 `find_package(PkgConfig)`、`pkg_check_modules(PC_DAQ)`、`find_path(DAQ_INCLUDE_DIR NAMES daq.h)`、`find_library(DAQ_LIBRARIES NAMES daq)` 定位；若装在非标准目录，`configure_cmake.sh` 的 `--with-daq-includes=`、`--with-daq-libraries=` 会把路径写进 `DAQ_INCLUDE_DIR_HINT` 与 `DAQ_LIBRARIES_DIR_HINT` 两个 hint 变量，优先级高于 pkg-config 结果。DAQ module 决定实际抓包与内联能力，具体名称需对照实际版本核验（`src/packet_io/sfdaq_module.cc`、`daqs/`；原理见 06-02）。不要把它理解成「装了 libdaq 就一定能抓在线流量」：module 是否可用、运行期是否有足够权限，是另外两道关。

环境侧还要准备四类条件。构建工具需要 `cmake` 与 `make`（或直接用 `cmake --build`），`configure_cmake.sh` 开头 `type cmake > /dev/null 2>&1` 检查就是第一道关；编译器需支持 C++17，`CMakeLists.txt` 里 `set (CMAKE_CXX_STANDARD 17)` 与 `CMAKE_CXX_STANDARD_REQUIRED ON` 是硬要求，`README.md` 也把 C++17 编译器列为依赖；`pkgconfig` 用于定位构建依赖，`FindDAQ.cmake` 直接依赖它。权限方面，安装前缀必须可写，运行期在线抓包往往需要 `CAP_NET_RAW` / `CAP_NET_ADMIN` 一类能力或相应账户权限，具体选项需对照实际版本核验（参数见 04-07）。动态库方面，若依赖装在非默认路径，运行时要设 `LD_LIBRARY_PATH` 或执行 `ldconfig`，否则 `snort -V` 会报共享库找不到。`lua/CMakeLists.txt` 用 `LUA_SCRIPTS` 列表收集 `snort.lua`、`snort_defaults.lua` 等模板并 `install (FILES ${LUA_SCRIPTS} DESTINATION "${CMAKE_INSTALL_SYSCONFDIR}/snort")`，所以安装后配置模板落在安装前缀的 `etc/snort/` 一类目录，`README.md` 的 `$my_path/etc/snort/snort.lua` 正是这个位置。前置条件归纳见下表。

| 前置条件 | 核验依据 | 缺失时的表现 |
|---|---|---|
| 必选依赖齐备 | `cmake/include_libraries.cmake` REQUIRED 一栏 | 配置期报找不到某个包 |
| 独立 libdaq / DAQ3 | `cmake/FindDAQ.cmake`、`README.md` | `find_package(DAQ REQUIRED)` 失败 |
| C++17 编译器与 CMake | `CMakeLists.txt`、`configure_cmake.sh` | 无法启动配置或编译报错 |
| pkgconfig 可用 | `FindDAQ.cmake` 的 `find_package(PkgConfig)` | DAQ 定位失败 |
| 安装前缀可写 | `--prefix=` 与 `install` 规则 | `make install` 阶段权限错误 |
| 单测依赖 CppUTest | `ENABLE_UNIT_TESTS` 条件查找 | 单测变体配置失败 |
| 运行期库路径 | `LD_LIBRARY_PATH` / `ldconfig` | 启动报共享库找不到 |

### 3. 分步操作

下面给出完整闭环的最小命令序列。命令形态参考 `README.md` 的 BUILD SNORT 与 `configure_cmake.sh` 的参数，具体选项与包名需对照实际版本核验；本册不重列构建变量全集，完整清单见 04-01。

```bash
export my_path=/opt/snorty
cd /path/to/snort3-master
./configure_cmake.sh --prefix=$my_path --builddir=build --enable-unit-tests
cmake --build build -j "$(nproc)"
cd build && ctest --output-on-failure
cd .. && cmake --install build
export LD_LIBRARY_PATH=$my_path/lib:$LD_LIBRARY_PATH
ls -1 $my_path/etc/snort/snort.lua $my_path/bin/snort
```

逐步说明如下。第一步 `export my_path=/opt/snorty` 只设定安装前缀变量，避免把路径写死在多条命令里；`README.md` 用 `export my_path=/path/to/snorty` 演示同样的做法。第二步 `cd /path/to/snort3-master` 进入真实仓库根，这一步用来规避「归档多一层 `snort3-master/`」的坑；若当前目录已经是仓库根，可省略。第三步 `./configure_cmake.sh --prefix=$my_path --builddir=build --enable-unit-tests` 同时完成三件事：`--prefix` 写入 `CMAKE_INSTALL_PREFIX`，`--builddir=build` 指定独立构建目录，`--enable-unit-tests` 经 `append_cache_entry ENABLE_UNIT_TESTS BOOL true` 打开单测，从而让 `cmake/include_libraries.cmake` 额外 `find_package(CppUTest REQUIRED)`、让 `CMakeLists.txt` 走 `include(CTest)` 与 `add_custom_target (check COMMAND ${CMAKE_CTEST_COMMAND})` 分支。若只想编生产二进制，去掉 `--enable-unit-tests` 即可，此时 `ctest` 无测试目标属于正常情况（展开见 02-05）。

第四步 `cmake --build build -j "$(nproc)"` 等价于 `cd build && make -j $(nproc)`，按 `src/CMakeLists.txt` 的 OBJECT 库与 `add_executable` 目标编译链接出 `build/src/snort`；`README.md` 给的 `src/snort -V` 正是构建目录内未安装的可执行文件。第五步 `cd build && ctest --output-on-failure` 跑单测，`--output-on-failure` 让失败用例打印细节；也可等价地用 `make check`，因为 `CMakeLists.txt` 里 `check` 目标直接 `COMMAND ${CMAKE_CTEST_COMMAND}`。第六步 `cmake --install build`（或 `cd build && make install`）按各处 `install` 规则落位：`snort` 到 `${CMAKE_INSTALL_BINDIR}`，Lua 模板到 `${CMAKE_INSTALL_SYSCONFDIR}/snort`，`snort.pc` 到 `${CMAKE_INSTALL_LIBDIR}/pkgconfig/`，头文件到 `${INCLUDE_INSTALL_PATH}` 各子目录，DAQ 示例 module 到 `${LIB_INSTALL_PATH}/daq`，插件到 `${PLUGIN_INSTALL_PATH}`。第七步导出 `LD_LIBRARY_PATH` 并 `ls` 确认 `snort.lua` 与 `snort` 两个关键产物到位，属于安装后的即时核验；若系统已把 `$my_path/lib` 纳入动态链接器配置，可改用 `ldconfig` 而不必设环境变量。清理环节：构建目录 `build/` 与安装前缀 `$my_path` 保留即为可复现产物，需要换变体时另取 `--builddir`，脚本本身也会在复用目录时主动删除旧 `CMakeCache.txt`。

### 4. 验证方法与预期结果

本节的「预期输出 + 判读要点」是 C 实战型篇章的硬要求，命令形态需对照实际版本核验，完整命令见 04-07。验证分三层：二进制能不能起来、帮助面是否完整、配置与规则能否在不接流量的前提下自检。验证命令如下。

```bash
$my_path/bin/snort -V
$my_path/bin/snort --help
$my_path/bin/snort -c $my_path/etc/snort/snort.lua -T
```

预期输出（示例输出，具体格式需对照实际版本核验）：

```text
示例输出，具体格式需对照实际版本核验
命令一：snort -V 输出版本与构建描述，具体字样由构建期变量注入
命令二：snort --help 列出 -c / -r / -i / -T / -V / --help 等类别
命令三：Lua 配置加载，HOME_NET / EXTERNAL_NET 已解析
命令三：外部默认 snort_defaults.lua 已 include
命令三：模块装配 stream / binder / wizard / ips 完成
命令三：规则编译 0 条文本规则，0 项 fast pattern
命令三：DAQ 校验，未指定在线输入，进入配置自检模式
命令三：Snort successfully validated the configuration (with 0 warnings).
```

判读要点如下，逐行说明。第一行是「示例输出」声明，提示版本字样、帮助文本与自检日志的排版、字段顺序、措辞随版本变化，必须以目标版本实际输出为准，不能把示例当固定格式解析。第二行对应 `snort -V`：它回答「当前二进制由哪份构建产生」，正常应给出版本与构建描述；若报命令不存在或共享库缺失，先查 `LD_LIBRARY_PATH` 与 `ldconfig`，不要据此推断引擎能力，也不要把其中的数字抄成本套资料的版本号。第三行对应 `snort --help`：`README.md` 把 `$my_path/bin/snort --help` 列为第一组示例，输出应能查到配置 `-c`、读文件 `-r`、在线接口 `-i`、自检 `-T`、版本 `-V` 与帮助 `--help` 等类别；具体选项清单需对照实际版本核验（`src/parser/cmd_line.cc`、`src/main/help.cc`；完整命令见 04-07）。第四到第六行是 `snort -T` 的加载过程：`HOME_NET`、`EXTERNAL_NET` 来自 `lua/snort.lua` 开头，`src/parser/vars.cc`、`src/lua/lua.cc` 负责解析，正常应为「已解析」；`snort_defaults.lua` 由 `include 'snort_defaults.lua'` 引入，正常应成功，报文件找不到多为工作目录与 `RULE_PATH` 一类路径变量未对齐（完整变量见 04-02）；模块装配对应 `src/managers/` 与 `src/framework/module.h` 的参数校验，正常应各模块名齐备，某模块报错多为键名与实际版本不一致。第七行规则编译对应 `src/parser/parse_rule.cc`，本例未给规则文件故为 0 条，属于正常值；生产环境若加载了规则集却仍显示 0 条，应检查 `ips` 段的 `include` 与 `variables`（参数见 04-06）。第八行对应 `src/main.cc` 的 `just_validate()` 分支，说明当前处于自检而非收包状态。最后一行是 `set_mode()` 中已核验的真实字符串，`with 0 warnings` 表示零告警，正常值应为 0；出现非零 warning 时应逐条核对配置而不宜忽略，因为 Snort 3 会「Report all errors」而非遇错即停。整个验证不接流量、不产生常驻进程，自检结束自行退出，属于零副作用闭环。

若第三步改用带规则文件的命令（如 `README.md` 里的 `-R $my_path/etc/snort/sample.rules`），规则编译一行的计数应变为正整数；若仍为 0，按「路径变量 → `ips.include` → 规则语法」的顺序排查。配置自检的底层链路是 `src/main.cc` 的 `set_mode()` 检查 `get_parse_errors()` / `get_parse_warnings()`，命中 `just_validate()` 时打印成功字符串并置 `sc->run_flags |= RUN_FLAG__TEST`，随后不进入收包循环（原理见 06-01）。统一交叉引用写法为（字段见 05-03 ｜ 参数见 04-07 ｜ 原理见 06-01 ｜ 模块见 07-12）：配置上下文逐字段去 05，命令全集去 04，启动与自检机制去 06，`src/main/` 与控制面能力去 07。

### 5. 常见失败与排错

第一类失败是 libdaq 缺失或版本不匹配。`find_package(DAQ REQUIRED)` 在配置期报「Could NOT find DAQ」时，按 `cmake/FindDAQ.cmake` 的查找顺序排查：先用 `pkg-config --modversion libdaq` 确认系统能识别，再查 `daq.h` 是否在 `DAQ_INCLUDE_DIR` 指向的路径；若装在非标准目录，补 `--with-daq-includes=`、`--with-daq-libraries=`。DAQ module 的具体名称与最低版本约束需对照实际版本核验，不能凭印象补值。第二类失败是 LuaJIT 相关：找不到头或库时，用 `--with-luajit-includes=`、`--with-luajit-libraries=` 指定路径；`CMakeLists.txt` 的 `include_directories(BEFORE ${LUAJIT_INCLUDE_DIR})` 说明 LuaJIT 头必须优先可见，版本差异需对照实际版本核验。第三类是 Hyperscan 头缺失：这与前两类性质不同，因为 `find_package(HS QUIET)` 是可选探测，缺失时 `HAVE_HYPERSCAN` 不定义、`src/search_engines/` 回退 AC / BNFA，构建仍应成功；若把 `Hyperscan: OFF` 误判为致命错误，反而会做多余处置（原理见 06-07）。

第四类失败在运行期：`snort -V` 报共享库找不到，多为 `LD_LIBRARY_PATH` 未含安装前缀的 `lib` 目录或 `ldconfig` 未刷新；在线抓包报权限不足，多为缺少 `CAP_NET_RAW` / `CAP_NET_ADMIN` 一类能力，具体选项需对照实际版本核验（参数见 04-07）。第五类是 `snort -T` 的 Lua 语法 / 路径错误：`lua/snort.lua` 是 Lua 脚本而非 `snort.conf` 指令文本，缩进、引号、`include` 路径写错都会在解析阶段报错；`tools/snort2lua/` 只是把旧配置映射成 Lua 表的转换辅助工具，转换结果仍须人工逐项比对并用 `snort -T` 验证，不能当成一键迁移（详见 01-02）。第六类是 CppUTest 缺失：仅当 `--enable-unit-tests` 打开时 `find_package(CppUTest REQUIRED)` 才成为硬门槛，若只是想编生产二进制，去掉该开关即可（展开见 02-05）。失败现象与处置的对照见下表。

| 现象 | 可能原因 | 验证命令 | 修复方向 |
|---|---|---|---|
| 配置期报找不到 DAQ | 独立 libdaq 未装或路径不对 | `pkg-config --modversion libdaq` | 装 libdaq 或用 `--with-daq-*` 指定 |
| 配置期报找不到 LuaJIT | 头或库在非标准路径 | `ls` 检查 luajit 头与库 | 用 `--with-luajit-*` 指定 |
| `Hyperscan: OFF` | 可选依赖未装，非致命 | 读配置期 Feature options | 接受回退或按需装 HS |
| 启动报共享库缺失 | 动态库路径未纳入搜索 | `ldd $my_path/bin/snort` | 设 `LD_LIBRARY_PATH` 或 `ldconfig` |
| `-T` 报 Lua 解析错 | 缩进、引号、include 路径 | `snort -c snort.lua -T` 看错误行 | 修 `snort.lua` 与路径变量 |
| `-T` 规则计数为 0 | `ips.include` 或路径变量未对齐 | `snort --help-module ips` | 核对规则文件路径 |

排错时始终记住两条边界。其一，`snort -T` 是配置自检、不接流量，能过自检不代表在线一定能收包，DAQ module 与权限是另一道关（原理见 06-02）。其二，许可方面引擎为 GPLv2（顶层 `COPYING` / `LICENSE`），Talos 规则集有独立许可约束，不能把规则与引擎按同一许可任意分发（详见 01-04）。涉及性能与容量的判断一律需在目标机型实测，基准方法见 08-01。

### 6. 小结

本篇给了一次可复现的 Linux 构建闭环：先按 `cmake/include_libraries.cmake` 与 `README.md` 装齐必选依赖、单独装独立 libdaq / DAQ3，再用 `./configure_cmake.sh --prefix=$my_path --builddir=build`（按需 `--enable-unit-tests`）配置，`cmake --build` 编译、`ctest` 跑单测、`cmake --install` 落位，最后用 `LD_LIBRARY_PATH` / `ldconfig` 处理动态库，并以 `snort -V`、`snort --help`、`snort -c snort.lua -T` 三层验证收口。图 02-03-01 给出分步与验证点，第 4 节给出「预期输出 + 判读要点」的完整 text 块与逐行判读，第 5 节给出六类常见失败的现象 → 原因 → 验证 → 修复对照。配置自检命中 `src/main.cc` 的 `just_validate()` 分支、打印 `Snort successfully validated the configuration (with 0 warnings).` 并置 `RUN_FLAG__TEST`，是这套验证里最可靠的成功信号。

配置期的证据链值得单独拆开看。`configure_cmake.sh` 把每个 `--enable-*` / `--with-*` 经 `append_cache_entry` 累积进 `CMakeCacheEntries`，最终以 `cmake` 带 `$CMakeCacheEntries` 与 `$sourcedir` 一次性提交，这意味着脚本里 `echo` 报无效构建类型之前的选择都会直接决定 `build/CMakeCache.txt` 的内容。核对配置是否生效，最可靠的不是回看命令行历史，而是回读缓存：`CMAKE_INSTALL_PREFIX` 是否等于 `--prefix` 传入的 `$my_path`、`ENABLE_UNIT_TESTS` 是否为 `BOOL=true`、`CMAKE_BUILD_TYPE` 是否与 `--build-type` 一致，三项都对齐才算配置落地。`config.status` 记录本次调用形态，`config.h` 则由 `config.cmake.h.in` 经 `configure_file` 的 @ONLY 形式生成，二者同读才能把「我传了什么」与「引擎编进了什么」对上；`HAVE_*` 一类宏的有无，直接决定后续编译期分支。字段见 05-06 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-12，具体键名与生成路径需对照实际版本核验，完整清单见 04-01。

安装与运行期的两段验证也要分层。`cmake --install build` 按 `CMakeLists.txt` 与各子目录 `install` 规则把二进制、`lua/snort.lua` 一类脚本、`snort.pc` 的 pkg-config 元数据分别落到 `--prefix` 下的对应目录；`snort.pc.in` 由 `cmake/create_pkg_config.cmake` 生成，其中 `Cflags: -I${includedir}/snort` 一类取值决定第三方插件能否用同一套头与宏编译，落位错误常表现为「引擎能起、插件编不过」。安装完成后先 `snort -V` 确认可执行文件与链接的库来自本次构建，再用 `ldd` 看 `libdaq` 等动态依赖是否解析到预期路径；若报找不到共享库，用 `LD_LIBRARY_PATH` 临时指定或 `ldconfig` 刷新缓存，二者作用域不同，前者只对当前会话有效。`snort --help` 用来确认 DAQ 相关选项确实进了这一版二进制，`snort -c snort.lua -T` 才做配置自检；三层顺序不能颠倒，任何一层失败都在对应层收口，错误文本与退出码需对照实际版本核验。字段见 05-06 ｜ 参数见 04-07 ｜ 原理见 06-02 ｜ 模块见 07-01。

延伸阅读：首次 IDS 运行与输出管道读 03-01、03-04，命令与返回码全集读 04-07、04-08，配置加载与自检机制读 06-01，`src/main/` 与控制面能力读 07-12，上线清单与回滚读 08-06。本册另两篇为 02-04（libdaq / DAQ3 与插件构建）、02-05（调试与单测）。跨册随查统一按（字段见 05-03 ｜ 参数见 04-07 ｜ 原理见 06-01 ｜ 模块见 07-12）执行；凡标注「需对照实际版本核验」的依赖版本约束、DAQ module 名、运行期权限选项与命令参数，均以 `_snort_build/upstream_src/snort3/snort3-master/` 下对应文件为准，本套资料不编造未经核验的路径与取值，性能与容量结论一律需在目标机型实测。

## 02-04 libdaq / DAQ3 与插件、扩展构建

### 1. 背景与动机

02-01 把 libdaq 列为必选依赖、02-03 把它列为独立安装的外部库，本篇要回答的是「这条边界在构建期到底怎么落地」。Snort 3 不内置抓包，抓包与内联能力由独立 libdaq / DAQ3 及所选 DAQ module 决定；`src/packet_io/sfdaq*.cc`、`sfdaq_config.cc`、`sfdaq_instance.cc`、`sfdaq_module.cc` 与 `daqs/` 是适配层与示例 module，不是抓包实现本身。把这条边界落到构建期，就是三件事：DAQ 如何被查找、DAQ 模块如何以静态或动态两种方式进入二进制、以及引擎插件（inspector / ips_option / logger / codec）如何按同一套静态 / 动态开关装配。理解了这三件事，才能解释「为什么装了 libdaq 仍要选 module」「为什么 `--disable-static-daq` 会改变链接结果」这类问题。

本套资料版本基准统一为「上游 master 快照（2026-11 抓取）」，具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，需对照实际版本核验；事实锚点为 `upstream_src/snort3/snort3-master/`。DAQ module 的具体名称、静态模块列表在不同 libdaq 版本下会变化，一律标注需对照实际版本核验，定位目录为 `src/packet_io/sfdaq_module.cc` 与 `daqs/`。能力边界继续生效：抓包依赖独立 libdaq / DAQ3 而非自带，内联 IPS 的 drop / block / reject 通过 DAQ verdict 反馈、Snort 本身不是防火墙也不做 IP 转发，Hyperscan 是可选加速且缺失时回退 AC / BNFA，加密载荷不可见，引擎为 GPLv2 且 Talos 规则集有独立许可约束。构建变量与选项全集属于 04-01，本册只讲组合与验证并写「完整清单见 04-01」。

插件化是重写的另一条主线。`src/framework/base_api.h` 定义 `struct BaseApi`（含 `type`、`size`、`api_version`、`version`、`features`、`options`、`name`、`help`、`mod_ctor`、`mod_dtor` 等成员，字段见 05-04）与 `enum PlugType`（`PT_CODEC`、`PT_INSPECTOR`、`PT_IPS_ACTION`、`PT_IPS_OPTION`、`PT_SEARCH_ENGINE`、`PT_SO_RULE`、`PT_LOGGER`、`PT_CONNECTOR`、`PT_POLICY_SELECTOR`、`PT_MP_TRANSPORT`、`PT_TRACE`、`PT_MAX`），并以 `BASE_API_VERSION` 与 `API_OPTIONS` 约束插件与引擎的匹配；`src/managers/` 下 `inspector_manager.cc`、`module_manager.cc`、`ips_manager.cc`、`action_manager.cc`、`plugin_manager.cc`、`mpse_manager.cc`、`script_manager.cc`、`codec_manager.cc`、`event_manager.cc`、`so_manager.cc` 负责装配。这套 ABI 与 Snort 2 的 preprocessor / output 插件不兼容，`tools/snort2lua/` 只是配置文本转换辅助工具（模块见 07-01、07-11，原理见 06-14）。`README.md` 还提到单独的 `snort3_extra` 仓库用于演示插件构建，本快照不含该仓库内容，需对照实际版本核验。

### 2. 核心概念

DAQ 侧的适配层文件在本快照 `src/packet_io/` 下已核验齐备：`sfdaq.cc/.h`、`sfdaq_config.cc/.h`、`sfdaq_instance.cc/.h`、`sfdaq_module.cc/.h`、`active.cc/.h`、`trough.cc/.h`、`packet_tracer.cc/.h`、`packet_constraints.cc/.h`、`packet_tracer_module.cc/.h`、`active_action.h`、`active_counts.h`、`dev_notes.txt` 与 `sfdaq_static_modules.h.in`，另有 `CMakeLists.txt` 与 `test/`。`01-01`、`01-03` 已核验 `SFDAQ::load`、`SFDAQ::init`、`SFDAQ::init_instance`、`SFDAQ::term`、`SFDAQ::get_input_spec`、`SFDAQ::default_type`、`SFDAQ::can_inject`、`SFDAQ::can_replace`、`SFDAQ::get_stats`、`SFDAQ::forwarding_packet`、`SFDAQ::verdict_to_string(DAQ_Verdict)` 等函数（字段见 05-07，原理见 06-02）。这些是适配层，DAQ module 决定实际抓包与内联能力，module 名需对照实际版本核验。

静态与动态 DAQ 是两种构建形态。`cmake/create_options.cmake` 里 `option ( ENABLE_STATIC_DAQ "link static DAQ modules" ON )` 默认让静态模块参与链接；`cmake/FindDAQ.cmake` 在 `if (PKG_CONFIG_EXECUTABLE AND ENABLE_STATIC_DAQ)` 分支用 `pkg-config --list-all` 捞出 `libdaq_static_*` 命名的模块，生成 `DAQ_STATIC_MODULES`（模块名列表）与 `DAQ_STATIC_MODULE_LIBS`（附加库列表）两个 `CACHE INTERNAL` 变量。`CMakeLists.txt` 的 Feature options 据此打印 `DAQ Modules: Static (${DAQ_STATIC_MODULES})` 或 `DAQ Modules: Dynamic`；`src/CMakeLists.txt` 以 `if ( ENABLE_STATIC_DAQ ) LIST(APPEND EXTERNAL_LIBRARIES ${DAQ_STATIC_MODULE_LIBS})` 把附加库并入链接。`src/packet_io/CMakeLists.txt` 则在 `if (ENABLE_STATIC_DAQ)` 里 `foreach (STATIC_MODULE_NAME IN LISTS DAQ_STATIC_MODULES)` 拼出 `DAQ_STATIC_MODULE_EXTERNS` 与 `DAQ_STATIC_MODULE_DATA_ARRAY`，再 `configure_file` 由 `sfdaq_static_modules.h.in` 生成 `sfdaq_static_modules.h`，并给 `sfdaq.cc` 设 `COMPILE_DEFINITIONS ENABLE_STATIC_DAQ`。模板内容真实验证了这一点：`#include <daq_module_api.h>`、`@DAQ_STATIC_MODULE_EXTERNS@`、`static DAQ_Module_h static_daq_modules[] = { @DAQ_STATIC_MODULE_DATA_ARRAY@ nullptr };`。

动态形态由 `daqs/CMakeLists.txt` 与 `cmake/macros.cmake` 支撑。`daqs/` 内 `CMakeLists.txt`、`daq_file.c`、`daq_hext.c`、`daq_user.h` 是示例 module；前者定义 `macro ( add_daq_module libname )` 转调 `add_dynamic_daq_module ( ${libname} ${ARGN} )`，再 `add_daq_module ( daq_file daq_file.c )`、`add_daq_module ( daq_hext daq_hext.c )`，并把 `daq_user.h` 装到 `${INCLUDE_INSTALL_PATH}/daq`。`cmake/macros.cmake` 的 `macro (add_dynamic_daq_module libname )` 用 `add_library ( ${libname} MODULE ${sources} )` 建 MODULE 库、用 `set_target_properties` 设 `COMPILE_FLAGS "-DBUILDING_SO"` 与空 `PREFIX` 去掉前缀，最后 `install (TARGETS ${libname} LIBRARY DESTINATION "${LIB_INSTALL_PATH}/daq")`。同文件的 `macro (add_dynamic_module libname install_path)` 则把引擎插件装到 `${PLUGIN_INSTALL_PATH}/${install_path}`，两者共用 `-DBUILDING_SO` 与 `PREFIX ""` 的处理，APPLE 下还追加 `-undefined dynamic_lookup`。

引擎插件的静态挂接与 DAQ 同构但落点不同。`cmake/create_options.cmake` 的 `STATIC_CODECS`、`STATIC_INSPECTORS`、`STATIC_LOGGERS`、`STATIC_IPS_ACTIONS`、`STATIC_IPS_OPTIONS`、`STATIC_SEARCH_ENGINES`、`STATIC_TRACERS` 决定各目录的 OBJECT 库是否收进可执行文件；`src/codecs/CMakeLists.txt` 的 `if (STATIC_CODECS)` 分支把 `ip_codecs`、`link_codecs`、`misc_codecs`、`root_codecs` 的 OBJECT 目标收进 `STATIC_CODEC_PLUGINS`，`else()` 分支只收 `ip_codecs` 与 `misc_codecs`；`src/CMakeLists.txt` 的 `add_executable` 再把 `${STATIC_CODEC_PLUGINS}`、`${STATIC_NETWORK_INSPECTOR_PLUGINS}`、`${STATIC_SERVICE_INSPECTOR_PLUGINS}`、`${STATIC_POLICY_SELECTOR_PLUGINS}`、`${UNIT_TESTS_LIBRARIES}` 等一并收拢。可见静态 / 动态不是抽象描述，而是直接决定哪些目标进入二进制、哪些以 MODULE 库形式落盘（模块见 07-01、07-07，字段见 05-04）。

### 3. 关键数据结构与源码位置

本节只点名构建期的文件、模板与变量，不展开结构体字段表；`BaseApi`、`PlugType`、`DAQ_ModuleAPI_t`、`DAQ_Module_h`、`Verdict` 等逐字段定义一律写「字段见 05-04、05-07」。DAQ 与插件构建相关的真实文件清单归纳见下表，便于按目录定位。

### 4. 关键流程与调用链

静态 DAQ 的完整链路可以逐段还原：`ENABLE_STATIC_DAQ` 为真 → `cmake/FindDAQ.cmake` 的 `if (PKG_CONFIG_EXECUTABLE AND ENABLE_STATIC_DAQ)` 分支执行 `execute_process` 调用 `pkg-config --list-all` 并写入 `_pkgconfig_list_result` → `string(REGEX MATCHALL "libdaq_static_[^ ]+" AVAILABLE_STATIC_MODULES ${_pkgconfig_list_result})` 与 `list(REMOVE_DUPLICATES)` → `foreach` 里 `string(REGEX REPLACE "^libdaq_static_" "" MODULE_NAME ${STATIC_MODULE})` 去前缀、`list(APPEND DAQ_STATIC_MODULES ${MODULE_NAME})`、`pkg_check_modules(PC_${STATIC_MODULE} ${STATIC_MODULE})`、`find_library(STATIC_MODULE_LIB)` 收集附加库 → `set` 把 `DAQ_STATIC_MODULE_LIBS` 写成 `CACHE INTERNAL` 变量 与 `set` 把 `DAQ_STATIC_MODULES` 写成 `CACHE INTERNAL` 变量 → `src/CMakeLists.txt` 的 `LIST(APPEND EXTERNAL_LIBRARIES ${DAQ_STATIC_MODULE_LIBS})` → `src/packet_io/CMakeLists.txt` 的 `foreach` 拼 `extern const DAQ_ModuleAPI_t <name>_daq_module_data;` 与数组元素 → `configure_file` 生成 `sfdaq_static_modules.h` → `set_source_files_properties(sfdaq.cc PROPERTIES COMPILE_DEFINITIONS ENABLE_STATIC_DAQ)` 让 `sfdaq.cc` 看到静态数组 → `add_library (packet_io OBJECT)` 与最终链接。这条链路把「libdaq 里有哪些静态模块」直接编译进二进制，静态模块名与数量随 libdaq 版本变化，需对照实际版本核验。静态 DAQ 模块探测到头文件生成链路见图 02-04-01。

### 5. 配置/命令/代码实例

下面这组命令用于「非标准路径安装 libdaq」这一最常见场景，命令形态参考 `configure_cmake.sh` 的 usage 与 `README.md` 的 fuzz 构建示例（具体选项需对照实际版本核验，完整清单见 04-01）。

```bash
export my_path=/opt/snorty
./configure_cmake.sh --prefix=$my_path \
    --with-daq-includes=/opt/libdaq/include \
    --with-daq-libraries=/opt/libdaq/lib \
    --disable-static-daq
cmake --build build -j "$(nproc)"
```

对应配置期输出（示例输出，具体格式需对照实际版本核验）：

```text
示例输出，具体格式需对照实际版本核验
Build Directory : build
Source Directory: /path/to/snort3-master
Install options:
    prefix:     /opt/snorty
    includes:   /opt/snorty/include/snort
    plugins:    /opt/snorty/lib/snort
Feature options:
    DAQ Modules:    Dynamic
    Hyperscan:      OFF
    SafeC:          OFF
    NUMA:           OFF
-------------------------------------------------------
config.status 已记录本次配置命令
```

逐行判读如下。第一行是「示例输出」声明，提示路径、Feature 开关与排版随版本变化，不能当固定格式解析。第二、三行仍是 `configure_cmake.sh` 打印的 `Build Directory` 与 `Source Directory`，正常应为 `build` 与真实仓库根；若指向上一层归档目录，回到 02-01 重新定位。第四到第六行是 `Install options`，`prefix` 应等于 `--prefix` 传入值，`includes` 与 `plugins` 由 `${CMAKE_INSTALL_FULL_INCLUDEDIR}/${INSTALL_SUFFIX}`、`${CMAKE_INSTALL_FULL_LIBDIR}/${INSTALL_SUFFIX}` 推导；`plugins` 这一项正是 `${PLUGIN_INSTALL_PATH}` 的上级，动态引擎插件会装到它下面的 `plugins/` 子目录。第七到第十行是 `Feature options`：本例显式传了 `--disable-static-daq`，脚本把它翻译成 `ENABLE_STATIC_DAQ BOOL false`，因此 `DAQ Modules: Dynamic` 是预期值——这与图 02-04-01 的静态链互斥，说明静态模块探测分支未执行；若不传该开关，默认 `ENABLE_STATIC_DAQ` 为 ON，且系统提供了 `libdaq_static_*` 命名的模块，这里会显示 `Static` 并列出 `DAQ_STATIC_MODULES`（模块名需对照实际版本核验）。`Hyperscan: OFF`、`SafeC: OFF`、`NUMA: OFF` 是可选项未启用，不是故障；Hyperscan 缺失时回退 `src/search_engines/` 内 AC / BNFA 实现（原理见 06-07）。最后一行 `config.status` 记录本次命令，便于复现。清理环节：本例只是配置与编译，若要换回静态 DAQ，去掉 `--disable-static-daq` 并另取 `--builddir` 重新配置即可，脚本会主动删除复用目录里的旧 `CMakeCache.txt`。

下面两段分别摘自 `src/packet_io/CMakeLists.txt` 与 `daqs/CMakeLists.txt`，用于说明「静态模块头文件如何生成」与「动态示例 module 如何构建」，都是本册讲组合方式时最该看的真实代码。

```cmake
if (ENABLE_STATIC_DAQ)
    foreach (STATIC_MODULE_NAME IN LISTS DAQ_STATIC_MODULES)
        string(APPEND DAQ_STATIC_MODULE_EXTERNS "extern const DAQ_ModuleAPI_t ${STATIC_MODULE_NAME}_daq_module_data;\n")
        string(APPEND DAQ_STATIC_MODULE_DATA_ARRAY "    &${STATIC_MODULE_NAME}_daq_module_data,\n")
    endforeach ()
    configure_file (
        "${CMAKE_CURRENT_SOURCE_DIR}/sfdaq_static_modules.h.in"
        "${CMAKE_CURRENT_BINARY_DIR}/sfdaq_static_modules.h"
    )
    set_source_files_properties(sfdaq.cc PROPERTIES COMPILE_DEFINITIONS ENABLE_STATIC_DAQ)
endif ()
```

```cmake
macro ( add_daq_module libname )
    add_dynamic_daq_module ( ${libname} ${ARGN} )
endmacro ( add_daq_module )
set ( DAQS_HEADERS daq_user.h )
add_daq_module ( daq_file daq_file.c )
add_daq_module ( daq_hext daq_hext.c )
install (FILES ${DAQS_HEADERS}
    DESTINATION "${INCLUDE_INSTALL_PATH}/daq"
)
```

第一段里 `foreach` 把每个静态模块名拼成一条 `extern` 声明与一个数组元素，`configure_file` 再把 `@DAQ_STATIC_MODULE_EXTERNS@` 与 `@DAQ_STATIC_MODULE_DATA_ARRAY@` 填进 `sfdaq_static_modules.h.in`；`COMPILE_DEFINITIONS ENABLE_STATIC_DAQ` 让 `sfdaq.cc` 编译时能看到 `static_daq_modules[]`。第二段里 `add_daq_module` 转调 `cmake/macros.cmake` 的 `add_dynamic_daq_module`，后者建 MODULE 库、设 `-DBUILDING_SO` 与空 `PREFIX`，并装到 `${LIB_INSTALL_PATH}/daq`。静态与动态两种形态的对照见下表，具体开关与默认值属于 04-01（完整清单见 04-01）。

| 维度 | 静态形态 | 动态形态 |
|---|---|---|
| 触发开关 | `ENABLE_STATIC_DAQ` / `STATIC_*` 为真 | 对应静态开关为假 |
| 探测来源 | `FindDAQ.cmake` 的 `pkg-config --list-all` | 无编译期探测 |
| 进入方式 | `configure_file` 生成头文件并编入 | `add_library` 建 MODULE 库 |
| 安装位置 | 随 `snort` 可执行文件 | `${LIB_INSTALL_PATH}/daq`、`plugins/` |
| 依赖条件 | 需提供 `libdaq_static_*` 命名的模块 | 运行期可找到对应 module |
| 变更成本 | 换模块需重新配置编译 | 换 module 文件即可，需核验 |

### 6. 注意事项、陷阱与最佳实践

第一，别把 DAQ 写成内置抓包。`find_package(DAQ REQUIRED)`、`snort.pc.in` 的 `cpp_opts=DAQ LUAJIT`、`cmake/FindDAQ.cmake` 的查找链与 `src/packet_io/sfdaq*.cc` 适配层共同说明抓包依赖独立 libdaq / DAQ3；DAQ module 决定抓包与内联能力，module 名需对照实际版本核验（原理见 06-02、模块见 07-07）。第二，别把内联 IPS 当防火墙：drop / block / reject 经 `src/actions/act_drop.cc`、`act_block.cc`、`act_reject.cc` 与 `src/packet_io/active.cc` 把裁定通过 DAQ verdict 反馈，Snort 不做 IP 转发、不做路由（原理见 06-12）。第三，别把 `--daq-dir` 一类运行期选项与构建期开关混为一谈：前者用于运行期指定 DAQ module 搜索目录，具体选项需对照实际版本核验（`src/parser/cmd_line.cc`；完整参数见 04-03），后者是 `ENABLE_STATIC_DAQ` / `STATIC_*` 一类 CMake 选项，二者作用层不同。

第四，别把 `tools/snort2lua/` 当一键迁移：它只把 Snort 2 配置文本映射成 Lua 表，`config_states/`、`keyword_states/` 里还有处理「旧指令无对应物」的状态文件，转换后必须人工比对并用 `snort -T` 验证；插件 ABI 不兼容，二进制插件不可迁移（详见 01-02，原理见 06-14）。第五，别忽略静态模块的编译期耦合：`ENABLE_STATIC_DAQ` 为真时，`DAQ_STATIC_MODULES` 直接决定 `sfdaq_static_modules.h` 的内容，升级 libdaq 后若不重新配置编译，静态列表可能与实际安装不一致；换形态应另取 `--builddir` 重新配置。第六，别把 `Hyperscan: OFF` 当致命错误：它是可选加速，`HAVE_HYPERSCAN` 只是编译期开关，缺失时回退 `src/search_engines/` 内其他多模式匹配实现（原理见 06-07）。第七，别在表格或正文里编造 DAQ module 名：`lua/inline.lua` 用 `name = 'pcap'` 与 `mode = 'read-file'`，`lua/talos.lua` 用 `name = 'dump'`，其余在线 module 名需对照实际版本核验（`src/packet_io/sfdaq_module.cc`、`daqs/`）。第八，别给绝对性能数字：静态 / 动态形态对启动与吞吐的影响一律需在目标机型实测（基准方法见 08-01）。

最佳实践可归纳为「先定形态、再验模块、后核落位」。先定形态：明确本次是要把 DAQ 模块静态编入（`ENABLE_STATIC_DAQ` 默认 ON）还是运行期动态加载（`--disable-static-daq`），并在 `config.status` 里留痕。再验模块：配置期读 Feature options 的 `DAQ Modules` 行，静态时核对 `DAQ_STATIC_MODULES` 是否来自预期的 libdaq 安装；动态时确认 `${LIB_INSTALL_PATH}/daq` 下有对应 module 文件，且运行期有足够权限。后核落位：安装完成后 `ls` 检查 `plugins/` 与 `daq/` 目录、`snort.pc` 与 `snort.lua` 是否齐备，再用 `snort --help`、`snort -T` 验证（完整命令见 04-07）。许可方面引擎按 GPLv2、Talos 规则集独立许可，不混同分发（详见 01-04）。

### 7. 小结与延伸阅读

本篇把「抓包边界在构建期怎么落地」拆成三条链：DAQ 查找链（`cmake/FindDAQ.cmake` 的 `pkg_check_modules`、`find_path`、`find_library`、`find_package_handle_standard_args`）、静态模块生成链（`ENABLE_STATIC_DAQ` → `DAQ_STATIC_MODULES` / `DAQ_STATIC_MODULE_LIBS` → `src/packet_io/CMakeLists.txt` 的 `foreach` + `configure_file` → `sfdaq_static_modules.h` → `sfdaq.cc`）、动态模块与插件装配链（`cmake/macros.cmake` 的 `add_dynamic_daq_module` / `add_dynamic_module` → MODULE 库 → `${LIB_INSTALL_PATH}/daq` 与 `${PLUGIN_INSTALL_PATH}`；`STATIC_*` 开关 → `STATIC_*_PLUGINS` → `add_executable`）。图 02-04-01 给出静态探测链，图 02-04-02 给出静态 / 动态两类落点；`daqs/` 的 `daq_file.c`、`daq_hext.c` 与 `tools/snort2lua/` 则分别是示例 module 与配置转换辅助工具。

静态 DAQ 模块的生成链是本篇最容易被跳过的一段。`src/packet_io/CMakeLists.txt` 先用 `execute_process` 调用 `pkg-config --list-all` 拿到本机已注册的库清单，再以 `string(REGEX MATCHALL "libdaq_static_[^ ]+" AVAILABLE_STATIC_MODULES)` 过滤出候选、用 `string(REGEX REPLACE "^libdaq_static_" "" MODULE_NAME)` 逐个去掉前缀，随后对每个模块名走 `pkg_check_modules(PC_${STATIC_MODULE})` 与 `find_library(STATIC_MODULE_LIB)`，最终把 `DAQ_STATIC_MODULES` 与 `DAQ_STATIC_MODULE_LIBS` 以 `set` 的 `CACHE INTERNAL` 形式写入缓存。这组变量随后喂给 `src/packet_io/sfdaq_static_modules.h.in`，由 `configure_file` 展开成 `sfdaq_static_modules.h` 里的 `Static` 形式模块表，编译期固定进二进制。由此可得一条判读规则：静态模块清单不是手写的，而是由构建机上 libdaq 的 pkg-config 注册情况决定；换机器、换 libdaq 版本后清单可能变化，具体模块名与数量需对照实际版本核验，绝不能把某次 `config.h` 里的静态表抄成通用结论。字段见 05-06 ｜ 参数见 04-03 ｜ 原理见 06-02 ｜ 模块见 07-03，完整清单见 04-01。

动态插件的构建面集中在 `cmake/macros.cmake`。其中 `add_dynamic_daq_module` 与通用 `add_plugin` 一类宏把「建 MODULE 库、去掉默认 `lib` 前缀、注入 `-DBUILDING_SO` 编译宏」封装成一次调用：`add_library` 建 MODULE 库，`set_target_properties` 设 `COMPILE_FLAGS` 的 `-DBUILDING_SO` 与空 `PREFIX`，`daqs/CMakeLists.txt` 与各插件子目录据此挂接。这与静态插件的路径不同——`src/codecs/CMakeLists.txt` 里 `STATIC_CODEC_PLUGINS` 一类变量把目标对象直接并入主可执行文件，不产生 `.so`。加载侧的兼容性由 `src/framework/base_api.h` 的 `BASE_API_VERSION` 与 `API_OPTIONS` 把关：动态插件必须用与当前引擎一致的头编译，否则启动期可能被拒；`snort3_extra` 一类外部仓库需先对齐快照的 API 版本再重编，不能复用旧二进制。字段见 05-06 ｜ 参数见 04-03 ｜ 原理见 06-14 ｜ 模块见 07-01，版本比对的确切行为需对照实际版本核验。

还要把查找链与运行链分开记。`cmake/FindDAQ.cmake` 负责配置期定位：先 `pkg_check_modules(PC_DAQ)` 探 `libdaq` 的包元数据，再 `find_path(DAQ_INCLUDE_DIR NAMES daq.h)`、`find_library(DAQ_LIBRARIES NAMES daq)`，末了 `find_package_handle_standard_args(DAQ REQUIRED_VARS DAQ_LIBRARIES DAQ_INCLUDE_DIR)` 判定成败，版本下限由该文件内的约束表达，具体数值需对照实际版本核验。它只保证「编译链接时有头有库」，不保证「运行时能收到包」；后者由 `src/packet_io/sfdaq_config.cc`、`sfdaq_module.cc` 解析的 module 选择与 `src/parser/cmd_line.cc` 的命令行选项决定。于是 `snort -T` 通过却在线收不到包时，应先查运行期 module 与权限，而不是回头改 `ENABLE_STATIC_DAQ`；把两层混在一起，是 DAQ 排障里最典型的误判。字段见 05-06 ｜ 参数见 04-03 ｜ 原理见 06-02 ｜ 模块见 07-03。

部署形态的一致性还有一条容易漏掉的检查。静态 DAQ 列表来自构建机上的 libdaq，编进二进制后不依赖目标机是否装有同名动态 module；反过来，`--disable-static-daq` 的产物只保留运行期动态加载能力，目标机上必须存在对应版本的 module `.so` 且落在引擎的搜索目录里，否则启动即报模块不可用。因此跨主机交付前，应把「构建机 libdaq 版本 / 目标机 libdaq 版本 / 本次静态或动态形态」三项并列登记，再决定是重编还是随包分发 module；`cmake/FindDAQ.cmake` 里的版本约束只覆盖构建期，不能替目标机做保证。同理，插件若以动态 `.so` 形式分发，`src/framework/base_api.h` 的 API 版本必须与目标引擎一致。字段见 05-06 ｜ 参数见 04-03 ｜ 原理见 06-14 ｜ 模块见 07-03，具体 module 名、搜索目录与版本比对行为需对照实际版本核验。

延伸阅读：DAQ 查找与版本约束读 `cmake/FindDAQ.cmake`、`README.md` 的 DEPENDENCIES；静态模块生成读 `src/packet_io/CMakeLists.txt` 与 `src/packet_io/sfdaq_static_modules.h.in`；动态构建宏读 `cmake/macros.cmake`、`daqs/CMakeLists.txt`；插件挂接读 `src/CMakeLists.txt`、`src/codecs/CMakeLists.txt`、`src/framework/base_api.h`；插件注册与扩展开发读 `doc/devel/extending.txt`（原理见 06-14）。本册衔接篇为 02-01（依赖矩阵）、02-03（构建实战）、02-05（调试与单测）。跨册随查统一按（字段见 05-07 ｜ 参数见 04-03 ｜ 原理见 06-02 ｜ 模块见 07-07）执行；凡标注「需对照实际版本核验」的 DAQ module 名、静态模块列表、运行期 `--daq*` 选项与版本号，均以 `_snort_build/upstream_src/snort3/snort3-master/` 下对应文件为准，本套资料不编造未经核验的路径与取值，性能与容量结论一律需在目标机型实测。

## 02-05 调试构建、Sanitizer、单元测试与静态分析

### 1. 背景与动机

生产构建追求精简与稳定，调试构建追求可观测与可定位，二者的目标不同、产物也不同。02-02 把「调试带单测」列为三种典型变体之一，本篇展开这条变体在源码里究竟由哪些开关、哪些宏、哪些构建函数支撑：debug 与调试消息如何变成编译标志，ASan / TSan / UBSan 如何经 `check_cxx_compiler_flag` 注入，CppUTest 与 Catch 两类单测目标如何挂到 `ctest`，以及 `.clang-tidy` 与 `crusty.cfg` 在静态分析与代码风格中扮演什么角色。理解这些，才能回答「为什么这个二进制跑得慢」「为什么 `ctest` 无测试可跑」「为什么两个 Sanitizer 一起开会报错」。

先声明三条口径。其一，版本基准统一写「上游 master 快照（2026-11 抓取）」，具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，需对照实际版本核验；事实锚点为 `upstream_src/snort3/snort3-master/`。其二，调试构建带调试符号、断言与 Sanitizer 插桩，性能代价明显，绝不可用作生产基准；任何吞吐、pps、内存占用、构建耗时一律需在目标机型实测，不给绝对值（基准方法见 08-01、调优见 08-02）。其三，CI 产物的具体形态（哪些目标、哪些报告、如何归档）本快照没有可直接核验的清单，一律标注需对照实际版本核验，定位目录为顶层 `CMakeLists.txt`、`cmake/` 与 `src/` 各 `test/` 子目录。构建变量与选项全集属于 04-01，本册只讲组合与验证并写「完整清单见 04-01」。

能力边界继续生效：抓包依赖独立 libdaq / DAQ3 而非自带，Hyperscan 是可选加速且缺失时回退 AC / BNFA，Snort 不是防火墙、不做 IP 转发、不做路由，加密载荷不可见，线程 / 进程模型以实际版本为准、不断言「默认 N 线程」，引擎为 GPLv2 且 Talos 规则集有独立许可约束。交叉引用统一按（字段见 05-04 ｜ 参数见 04-01 ｜ 原理见 06-13 ｜ 模块见 07-01）执行：插件与上下文结构逐字段去 05，CMake 选项全集去 04-01，线程与插件机制去 06，`src/framework` 目录能力去 07。

### 2. 核心概念

调试开关分几族，落在 `cmake/create_options.cmake`：`ENABLE_DEBUG_MSGS`、`ENABLE_DEBUG`、`ENABLE_GDB`、`ENABLE_PROFILE`、`DISABLE_SNORT_PROFILER`、`ENABLE_DEEP_PROFILING`、`ENABLE_MEMORY_PROFILER`、`ENABLE_RULE_PROFILER`、`ENABLE_ADDRESS_SANITIZER`、`ENABLE_THREAD_SANITIZER`、`ENABLE_UB_SANITIZER`、`ENABLE_TCMALLOC`、`ENABLE_JEMALLOC`、`ENABLE_CODE_COVERAGE`、`ENABLE_FUZZ_COVERAGE` 等，另有 `ENABLE_UNIT_TESTS`、`ENABLE_BENCHMARK_TESTS`、`ENABLE_FUZZERS`、`ENABLE_FUZZ_SANITIZER`。这些名称只作定位用点名，默认值、依赖条件与误配后果属于 04-01（完整清单见 04-01）。`configure_cmake.sh` 的 usage 里对应着 `--enable-debug`、`--enable-debug-msgs`、`--enable-address-sanitizer`、`--enable-thread-sanitizer`、`--enable-ub-sanitizer`、`--enable-unit-tests`、`--enable-code-coverage`、`--enable-tcmalloc`、`--enable-jemalloc` 等写法，二者是同一批缓存项的两种入口。

「选项 → 宏 / 标志」的映射在 `cmake/configure_options.cmake`。`set ( DEBUG_MSGS ${ENABLE_DEBUG_MSGS} )`、`set ( UNIT_TEST ${ENABLE_UNIT_TESTS} )` 把选项写成供 `config.cmake.h.in` 消费的变量，`#cmakedefine UNIT_TEST 1`、`#cmakedefine DEBUG_MSGS 1`、`#cmakedefine PROFILE 1`、`#cmakedefine NO_PROFILER 1`、`#cmakedefine ENABLE_MEMORY_PROFILER 1`、`#cmakedefine ENABLE_RULE_PROFILER 1`、`#cmakedefine DEEP_PROFILING 1` 等宏随之生效。编译标志一路是 `if ( ENABLE_DEBUG ) string ( APPEND DEBUGGING_C_FLAGS " -g -DDEBUG" ) else () string ( APPEND DEBUGGING_C_FLAGS " -DNDEBUG" )`、`if ( ENABLE_GDB )` 追加 `-g -ggdb`、`if ( ENABLE_PROFILE AND CMAKE_COMPILER_IS_GNUCXX )` 追加 `-pg`；末尾 `EXTRA_C_FLAGS`、`EXTRA_CXX_FLAGS`、`EXTRA_LINKER_FLAGS` 把 `HARDENED_*`、`DEBUGGING_*`、`SANITIZER_*`、`TCMALLOC_*`、`COVERAGE_*` 等汇总，顶层 `CMakeLists.txt` 再以 `string(APPEND CMAKE_CXX_FLAGS " ${EXTRA_CXX_FLAGS}")` 注入全局。注释明确要求这些 `string(APPEND)` 必须在所有测试做完之后、任何 `add_subdirectory` 之前执行。

Sanitizer 三类各自独立又有互斥约束。`ENABLE_ADDRESS_SANITIZER` 分支设 `ASAN_CXX_FLAGS "-fsanitize=address -fno-omit-frame-pointer"`、`ASAN_LINKER_FLAGS "-fsanitize=address"`，用 `check_cxx_compiler_flag ( "${ASAN_CXX_FLAGS}" HAVE_ADDRESS_SANITIZER )` 验证，不支持则 `message ( SEND_ERROR "Could not enable the address sanitizer!" )`；`ENABLE_THREAD_SANITIZER` 用 `-fsanitize=thread -fno-omit-frame-pointer` 与 `HAVE_THREAD_SANITIZER`；`ENABLE_UB_SANITIZER` 用 `-fsanitize=undefined -fno-sanitize=alignment -fno-omit-frame-pointer` 并用 `string ( APPEND)` 向 `SANITIZER_CXX_FLAGS` 追加内容。源码注释写明「ASAN and TSAN are mutually exclusive, so have them absolutely set SANITIZER_*_FLAGS first」，即 AddressSanitizer 与 ThreadSanitizer 不能同时开；此外 `ENABLE_TCMALLOC` / `ENABLE_JEMALLOC` 分支里有 `if ( ENABLE_ADDRESS_SANITIZER ) message ( SEND_ERROR "TCMalloc cannot be used at the same time as address sanitizer!" )` 一类互斥检查。Fuzzer 相关还有 `ENABLE_FUZZ_SANITIZER` 的 `-fsanitize=fuzzer` 与 `try_compile(HAVE_FUZZ_SANITIZER)`、`ENABLE_FUZZERS AND NOT LIB_FUZZING_ENGINE AND NOT ENABLE_FUZZ_SANITIZER` 时的 `FATAL_ERROR`。

单测设施分两套，从 `cmake/macros.cmake` 可见。`function (add_cpputest testname)` 在 `ENABLE_UNIT_TESTS` 打开时 `cmake_parse_arguments(CppUTest "" "" "${multiValueArgs}" ${ARGN})`、`add_executable` 建 `EXCLUDE_FROM_ALL` 目标、`target_compile_options(${testname} PRIVATE "-DUNIT_TEST_BUILD")`、`target_link_libraries(${testname} ${CPPUTEST_LIBRARIES} ${CppUTest_LIBS})`、`add_test(${testname} ${testname})` 并 `add_dependencies(check ${testname})`；`function (add_catch_test testname)` 在 `ENABLE_UNIT_TESTS OR ENABLE_BENCHMARK_TESTS` 时建目标、`$<TARGET_OBJECTS:catch_main>`、按需 `-DCATCH_TEST_BUILD`，同样 `add_test` 与 `add_dependencies(check)`。`src/framework/test/CMakeLists.txt` 是前者的真实例子：`add_cpputest( data_bus_test SOURCES ../data_bus.cc ../reload_survivor_subscriptions.cc)`、`add_cpputest( mp_data_bus_test SOURCES ../mp_data_bus.cc)`、`add_cpputest( reload_survivor_subscriptions_test SOURCES ../data_bus.cc ../reload_survivor_subscriptions.cc)`，并在 `ENABLE_UNIT_TESTS` 下 `add_library(api_def api_def.cc)` 配 `-E` 预处理选项。静态分析侧，顶层 `.clang-tidy` 的 `Checks:` 行列出 `clang-diagnostic-*`、`clang-analyzer-*`、`readability-*`、`bugprone-*`、`performance-*`、`modernize-*` 等检查族，`crusty.cfg` 则是 `Uncrustify 0.60` 的代码风格配置（如 `newlines = lf`、`indent_columns = 4`、`code_width = 119`、`cmt_width = 99`）。`CMakeLists.txt` 的 `set (CMAKE_EXPORT_COMPILE_COMMANDS ON)` 生成 `compile_commands.json`，正是 clangd 与 clang-tidy 消费的输入。

### 3. 关键数据结构与源码位置

本节只点名文件、宏族与目标，不展开结构体字段表；插件与上下文结构逐字段一律写「字段见 05-04、05-05」。`CMakeLists.txt` 里与本篇直接相关的分支有 `if (ENABLE_UNIT_TESTS) include(CTest)`、`if (ENABLE_UNIT_TESTS OR ENABLE_BENCHMARK_TESTS) add_custom_target (check COMMAND ${CMAKE_CTEST_COMMAND})`、`if (ENABLE_FUZZERS) add_custom_target (fuzz)`；`src/CMakeLists.txt` 里有 `if ( ENABLE_UNIT_TESTS ) enable_testing()`、`if ( ENABLE_UNIT_TESTS OR ENABLE_BENCHMARK_TESTS ) set( UNIT_TESTS_LIBRARIES $<TARGET_OBJECTS:catch_tests>) add_subdirectory(catch)`，并把 `${UNIT_TESTS_LIBRARIES}` 收进 `add_executable` 目标。`cmake/configure_options.cmake` 里还有一条容易被忽略的联动：`if ( ENABLE_UNIT_TESTS AND NOT ALLOWLIST_MOVE_ON_EXCESS )` 会 `message ( STATUS "ALLOWLIST_MOVE_ON_EXCESS forced ON because ENABLE_UNIT_TESTS is ON" )` 并强制打开该项，`config.cmake.h.in` 里也有 `REG_TEST` 条件下的 `#define ALLOWLIST_MOVE_ON_EXCESS 1` 兜底。调试、单测与静态分析相关文件归纳见下表。

### 4. 关键流程与调用链

单测链路可以逐段还原：`--enable-unit-tests` 经 `append_cache_entry ENABLE_UNIT_TESTS BOOL true` 成为缓存项 → `cmake/include_libraries.cmake` 的 `if (ENABLE_UNIT_TESTS) find_package(CppUTest REQUIRED)` → 顶层 `CMakeLists.txt` 的 `include(CTest)` 与 `add_custom_target (check COMMAND ${CMAKE_CTEST_COMMAND})` → `src/CMakeLists.txt` 的 `enable_testing()`、`set( UNIT_TESTS_LIBRARIES $<TARGET_OBJECTS:catch_tests>)`、`add_subdirectory(catch)` → 各 `src/*/test/CMakeLists.txt` 调用 `add_cpputest` / `add_catch_test` → `cmake/macros.cmake` 里 `add_executable` 建 `EXCLUDE_FROM_ALL` 目标、`add_test(${testname} ${testname})`、`add_dependencies(check ${testname})` → 构建期 `make check` 或 `ctest` 真正执行。注意 `EXCLUDE_FROM_ALL` 意味着常规 `make` 不会构建测试可执行文件，只有 `check` 目标或显式构建测试目标时才编译，这是「为什么打开了开关却没看到测试二进制」的答案。

Sanitizer 链路是另一条：`--enable-address-sanitizer` 一类开关 → `cmake/configure_options.cmake` 设 `ASAN_CXX_FLAGS` / `ASAN_LINKER_FLAGS` 并 `check_cxx_compiler_flag` 得 `HAVE_ADDRESS_SANITIZER` → 成功则 `set ( SANITIZER_CXX_FLAGS "${ASAN_CXX_FLAGS}" )` 与 `SANITIZER_LINKER_FLAGS` → 末尾 `EXTRA_CXX_FLAGS` 汇总时把 `${SANITIZER_CXX_FLAGS}` 拼进去 → 顶层 `CMakeLists.txt` 的 `string(APPEND CMAKE_CXX_FLAGS " ${EXTRA_CXX_FLAGS}")` 注入全局 → 所有 OBJECT 库与 `snort` 目标带 `-fsanitize=address -fno-omit-frame-pointer` 编译链接。若编译器不支持，`SEND_ERROR` 会让配置失败而不是静默降级，这属于「组合的硬边界」。调试标志同理：`ENABLE_DEBUG` 决定 `-g -DDEBUG` 还是 `-DNDEBUG`，`ENABLE_GDB` 追加 `-g -ggdb`，`ENABLE_PROFILE` 在 GNU 编译器下追加 `-pg`。调试、单测与静态分析的整体链路见图 02-05-01。

### 5. 配置/命令/代码实例

下面这组是「调试带单测」变体的最小构建与验证闭环，命令形态参考 `README.md` 与 `configure_cmake.sh` 的 usage（具体选项需对照实际版本核验，完整清单见 04-01）。

```bash
export my_path=/opt/snorty-debug
./configure_cmake.sh --prefix=$my_path --builddir=build-debug \
    --enable-debug --enable-debug-msgs --enable-unit-tests \
    --enable-address-sanitizer
cmake --build build-debug -j "$(nproc)"
cd build-debug && ctest --output-on-failure
```

对应 `ctest` 输出（示例输出，具体格式需对照实际版本核验）：

```text
示例输出，具体格式需对照实际版本核验
Test project /path/to/snort3-master/build-debug
    Start 1: data_bus_test
1/3 Test #1: data_bus_test                 Passed
    Start 2: mp_data_bus_test
2/3 Test #2: mp_data_bus_test              Passed
    Start 3: reload_survivor_subscriptions_test
3/3 Test #3: reload_survivor_subscriptions_test  Passed
100% tests passed, 0 tests failed out of 3
Total Test time (real) = 0.42 sec
```

逐行判读如下。第一行是「示例输出」声明，提示测试数量、用例名、耗时与排版随版本和本机环境变化，用例名来自 `src/framework/test/CMakeLists.txt` 的 `add_cpputest` 对 `data_bus_test` 等用例的调用，不能当固定清单解析。第二行 `Test project` 是 `include(CTest)` 后 `ctest` 的标准抬头，正常应指向本次 `--builddir=build-debug`；若路径是别的构建目录，说明 `cd` 错了或复用了旧缓存。第三到第八行是三个用例的 `Start` 与结果行，`Passed` 为正常；`1/3`、`2/3`、`3/3` 表示进度与总数，总数应与 `add_test` 注册数一致。若某行是 `Failed` 或 `Timeout`，配合 `--output-on-failure` 看具体断言，根因按 `src/framework/test/` 对应源文件定位（`data_bus_test.cc`、`mp_data_bus_test.cc`、`reload_survivor_subscriptions_test.cc`），不要直接改引擎源码。第九行 `100% tests passed, 0 tests failed out of 3` 是本例的预期收口，正常应为 0 failed；出现非零 failed 时，先确认是 Sanitizer 报出的内存问题还是逻辑断言失败，二者处置不同。第十行 `Total Test time` 只是本机耗时，任何构建耗时、测试耗时与运行吞吐一律需在目标机型实测，不给跨机型通用值。若输出为 `No tests were found` 或 `0 tests`，按图 02-05-01 的 `n1 → n5 → n6 → n7` 检查 `--enable-unit-tests` 是否真的传入、`ENABLE_UNIT_TESTS` 是否出现在 `CMakeCache.txt`、以及 `check` 目标是否被 `add_dependencies` 挂上；注意 `EXCLUDE_FROM_ALL` 会让常规 `make` 不构建测试可执行文件，需要 `make check` 或 `ctest` 触发。整个流程不接流量、不改源码，属于可重复的验证闭环；清理环节为保留 `build-debug/` 供回溯，生产构建另用独立 `--builddir`。

下面两段分别摘自 `cmake/configure_options.cmake` 与 `cmake/macros.cmake`，用于说明「Sanitizer 标志如何被验证并注入」以及「单测目标如何挂到 check」，都是本册讲组合方式时最该看的真实代码。

```cmake
if ( ENABLE_ADDRESS_SANITIZER )
    set ( ASAN_CXX_FLAGS "-fsanitize=address -fno-omit-frame-pointer" )
    set ( ASAN_LINKER_FLAGS "-fsanitize=address" )
    set ( CMAKE_REQUIRED_FLAGS "${ASAN_LINKER_FLAGS}" )
    check_cxx_compiler_flag ( "${ASAN_CXX_FLAGS}" HAVE_ADDRESS_SANITIZER )
    unset ( CMAKE_REQUIRED_FLAGS )
    if ( HAVE_ADDRESS_SANITIZER )
        set ( SANITIZER_CXX_FLAGS "${ASAN_CXX_FLAGS}" )
        set ( SANITIZER_LINKER_FLAGS "${ASAN_LINKER_FLAGS}" )
    else ()
        message ( SEND_ERROR "Could not enable the address sanitizer!" )
    endif ()
endif ( ENABLE_ADDRESS_SANITIZER )
```

```cmake
function (add_cpputest testname)
    if ( ENABLE_UNIT_TESTS )
        set(multiValueArgs SOURCES LIBS)
        cmake_parse_arguments(CppUTest "" "" "${multiValueArgs}" ${ARGN})
        add_executable(${testname} EXCLUDE_FROM_ALL ${testname}.cc ${CppUTest_SOURCES})
        target_compile_options(${testname} PRIVATE "-DUNIT_TEST_BUILD")
        target_include_directories(${testname} PRIVATE ${CPPUTEST_INCLUDE_DIR})
        target_link_libraries(${testname} ${CPPUTEST_LIBRARIES} ${CppUTest_LIBS})
        add_test(${testname} ${testname})
        add_dependencies(check ${testname})
    endif ( ENABLE_UNIT_TESTS )
endfunction (add_cpputest)
```

第一段里 `check_cxx_compiler_flag` 是「组合是否可行」的闸门：编译器不支持 ASan 时直接 `SEND_ERROR`，而不是静默关闭；成功后 `SANITIZER_CXX_FLAGS` 会被 `EXTRA_CXX_FLAGS` 汇总、再注入全局。第二段里 `add_test(${testname} ${testname})` 与 `add_dependencies(check ${testname})` 是 `ctest` 与 `make check` 能找到用例的关键，`EXCLUDE_FROM_ALL` 则说明测试目标默认不参与常规构建。三类 Sanitizer 与主要约束见下表，具体开关名、默认值与依赖关系属于 04-01（完整清单见 04-01）。

| Sanitizer | 编译标志要点 | 主要约束 |
|---|---|---|
| AddressSanitizer | `-fsanitize=address -fno-omit-frame-pointer` | 与 TSan、TCMalloc / JEMalloc 互斥 |
| ThreadSanitizer | `-fsanitize=thread -fno-omit-frame-pointer` | 与 ASan 互斥，源码注释明确 |
| UndefinedBehaviorSanitizer | `-fsanitize=undefined -fno-sanitize=alignment` | 可与其他标志叠加 |
| Fuzzer sanitizer | `-fsanitize=fuzzer` 与 `try_compile` 探测 | 需 Clang，`ENABLE_FUZZERS` 有前置条件 |

### 6. 注意事项、陷阱与最佳实践

第一，别把 ASan 与 TSan 同时打开。`cmake/configure_options.cmake` 的注释写明「ASAN and TSAN are mutually exclusive」，两者都设 `SANITIZER_CXX_FLAGS` 会相互覆盖；应分两次构建、各用独立 `--builddir`。第二，别把 TCMalloc / JEMalloc 与 ASan 同时打开：源码里 `ENABLE_TCMALLOC` 与 `ENABLE_JEMALLOC` 分支都有 `if ( ENABLE_ADDRESS_SANITIZER )` 的 `SEND_ERROR`，`configure_cmake.sh` 里也有 `--enable-jemalloc and --enable-tcmalloc are mutually exclusive` 的 `exit 2` 检查。第三，别在既无 `LIB_FUZZING_ENGINE` 又无 `ENABLE_FUZZ_SANITIZER` 时开 `ENABLE_FUZZERS`：`configure_options.cmake` 里 `if ( ENABLE_FUZZERS AND NOT LIB_FUZZING_ENGINE AND NOT ENABLE_FUZZ_SANITIZER )` 会以 `FATAL_ERROR` 直接终止配置；fuzz 构建还需 Clang，形态见 `README.md` 的 FUZZ TESTING，需对照实际版本核验。

第四，别忽略 `ENABLE_UNIT_TESTS` 的联动：`cmake/include_libraries.cmake` 会额外要求 `CppUTest`，`configure_options.cmake` 里 `ENABLE_UNIT_TESTS AND NOT ALLOWLIST_MOVE_ON_EXCESS` 会强制打开 `ALLOWLIST_MOVE_ON_EXCESS`，`src/CMakeLists.txt` 会 `add_subdirectory(catch)` 并把 `${UNIT_TESTS_LIBRARIES}` 收进 `snort` 目标——也就是说单测开关不只是「多编几个测试」，还会改变主二进制的构成。第五，别把调试构建当生产基准：`-g -DDEBUG`、profiling 与 Sanitizer 插桩带来明显性能代价，吞吐、pps、内存占用一律需在目标机型实测（基准方法见 08-01、调优见 08-02）。第六，别把 `.clang-tidy` / `crusty.cfg` 当成构建开关：前者是静态分析检查集（`Checks:` 行），后者是 `Uncrustify 0.60` 代码风格配置，二者都不参与编译，靠 `set (CMAKE_EXPORT_COMPILE_COMMANDS ON)` 生成的 `compile_commands.json` 供 clangd / clang-tidy 消费。第七，别断言「默认 N 线程」：线程 / 进程模型与资源隔离以实际版本为准（`src/main/analyzer.cc`、`process.cc`、`numa.cc`、`swapper.cc`），需对照实际版本核验（原理见 06-13）。第八，别抄 CI 产物形态或具体版本号：本快照无可直接核验的 CI 清单，需对照实际版本核验；本套资料统一写「上游 master 快照（2026-11 抓取）」。

最佳实践可归纳为「三分离、两留痕」。三分离：调试 / 单测变体与生产变体用独立 `--builddir`、独立 `--prefix`；ASan、TSan、UBSan 分次构建，不叠加互斥开关；fuzz / 覆盖率构建按 `README.md` 的形态单独组织。两留痕：保留每次 `config.status` 与 `ctest` 输出，便于回溯「哪次构建开了哪些开关、哪些用例失败」；保留 `compile_commands.json`，便于用 `.clang-tidy` 的检查集与 `crusty.cfg` 的风格配置做本地静态分析。验证顺序建议为：配置期读 Feature options 与 `CMakeCache.txt` 确认开关 → `cmake --build` 编译 → `ctest --output-on-failure` 跑用例 → `snort -V` / `snort -T` 确认二进制仍可用（完整命令见 04-07）。许可方面引擎按 GPLv2、Talos 规则集独立许可，不混同分发（详见 01-04）。

### 7. 小结与延伸阅读

本篇把「调试带单测」变体拆成三条链：选项链（`cmake/create_options.cmake` 的 debug / Sanitizer / 单测 `option` → `configure_cmake.sh` 的 `--enable-*` → `cmake/configure_options.cmake` 的宏与 `EXTRA_*_FLAGS` → 顶层 `CMakeLists.txt` 的 `string(APPEND)`）、单测链（`ENABLE_UNIT_TESTS` → `find_package(CppUTest REQUIRED)` → `include(CTest)` / `enable_testing()` → `add_cpputest` / `add_catch_test` 的 `add_test` 与 `add_dependencies(check)` → `ctest`）、静态分析链（`CMAKE_EXPORT_COMPILE_COMMANDS` 生成 `compile_commands.json` → `.clang-tidy` 的 `Checks:` 与 `crusty.cfg` 的 Uncrustify 配置）。图 02-05-01 给出三链的汇合点，第 5 节给出「命令 + 预期输出 + 逐行判读」的完整闭环，第 6 节给出 ASan / TSan 互斥、TCMalloc / JEMalloc 与 ASan 互斥、`ENABLE_FUZZERS` 前置条件等硬边界。

把「开关名」追到「宏名」是读懂调试构建的关键。`cmake/create_options.cmake` 用 `option` 声明 `ENABLE_DEBUG`、`ENABLE_DEBUG_MSGS`、`ENABLE_GDB`、`ENABLE_PROFILE`、`ENABLE_DEEP_PROFILING`、`ENABLE_MEMORY_PROFILER`、`ENABLE_RULE_PROFILER`、`ENABLE_UNIT_TESTS`、`DISABLE_SNORT_PROFILER` 一类缓存变量；`configure_cmake.sh` 把 `--enable-*` 翻成 `-D NAME:TYPE=VALUE`，`cmake/configure_options.cmake` 再把取值落到 `EXTRA_C_FLAGS`、`EXTRA_CXX_FLAGS`、`EXTRA_LINKER_FLAGS` 与 `SANITIZER_CXX_FLAGS` 上，例如 `if ( ENABLE_GDB )` 分支追加 `-g -ggdb` 一类标志、Sanitizer 分支用 `string ( APPEND)` 叠加内容。最终 `config.cmake.h.in` 以 `#cmakedefine` 一类占位生成 `config.h` 里的 `NO_PROFILER`、`HAVE_*` 宏，`snort.pc.in` 的 `Cflags` 行又带 `@NO_PROFILER_CPPFLAGS@` 一类占位把同一组定义写给第三方插件。于是「选项开了但行为没变」时，正确顺序是回读 `config.h` 与 `snort.pc` 确认宏确实落地，而不是反复改命令行。字段见 05-06 ｜ 参数见 04-01 ｜ 原理见 06-09 ｜ 模块见 07-12，占位符与宏名的确切写法需对照实际版本核验，完整清单见 04-01。

单测的挂接链同样值得逐段核对。`CMakeLists.txt` 里 `include(CTest)` 打开测试支持、`add_custom_target (check COMMAND ${CMAKE_CTEST_COMMAND})` 提供统一入口、`set (CMAKE_EXPORT_COMPILE_COMMANDS ON)` 保证 `compile_commands.json` 稳定产出；`cmake/include_libraries.cmake` 仅在 `ENABLE_UNIT_TESTS` 打开时才 `find_package(CppUTest REQUIRED)`，因此不带 `--enable-unit-tests` 的构建里 `ctest` 无用例属于正常。`src/framework/test/CMakeLists.txt` 用 `add_cpputest` / `add_catch_test` 把 `data_bus_test` 一类用例经 `add_executable` 建成 `EXCLUDE_FROM_ALL` 目标，再由 `add_dependencies(check)` 挂到 `check`、由 `add_test` 注册到 CTest。由此可得判读要点：用例没跑，先查 `ENABLE_UNIT_TESTS` 与 CppUTest 是否就位，再查 `check` 目标依赖，最后看 `LastTest.log`；把「变体没开单测」误判成「用例编译失败」，会让人在错误方向上反复重建。字段见 05-06 ｜ 参数见 04-01 ｜ 原理见 06-09 ｜ 模块见 07-12，用例全集与产物路径需对照实际版本核验。

最后要记住两类硬约束。`cmake/configure_options.cmake` 用 `try_compile(HAVE_FUZZ_SANITIZER)` 探测编译器能力，并对互斥的 Sanitizer 组合以 `FATAL_ERROR` 直接终止配置，`cmake/sanity_checks.cmake` 也会用 `SEND_ERROR` / `FATAL_ERROR` 拦下不合规组合，所以 ASan、TSan、UBSan 必须分次构建、各自独立 `--builddir`，叠加开关不是「更全」而是「配不过」。静态分析侧，`crusty.cfg` 的 `code_width = 119` 与 `.clang-tidy` 的 `Checks:` 给出一致基线，`doc/CMakeLists.txt` 里 `if ( NOT ASCIIDOC_FOUND )` 分支把 `MAKE_HTML_DOC` 强制设为 OFF，说明工具缺失时构建会静默降级而非报错——这类「功能被悄悄关掉」比编译失败更难查，配置后应回读 `message` 打印的 Feature 汇总逐项确认。字段见 05-06 ｜ 参数见 04-01 ｜ 原理见 06-09 ｜ 模块见 07-12，具体检查项与降级行为需对照实际版本核验。

调试符号与优化级别也要成对核对。`ENABLE_GDB` 一类开关只负责追加 `-g -ggdb`，并不阻止编译器按 `CMAKE_BUILD_TYPE` 带上优化；带优化的内联与寄存器分配会让断点跳跃、变量不可见，因此排查逻辑问题时通常把构建类型设为不优化或低优化的调试型，和 `ENABLE_DEBUG_MSGS` 一起用。`CMAKE_BUILD_TYPE` 与 `--build-type` 的对应关系、`configure_cmake.sh` 中 `echo` 报无效构建类型的分支、以及 `cmake/platforms.cmake` 对平台差异的处理，共同决定最终的编译命令，回读 `compile_commands.json` 能看到每条命令的真实参数。断点现象与源码行对不上时，先确认 `compile_commands.json` 里的优化标志，而不是怀疑源码被改过。字段见 05-06 ｜ 参数见 04-01 ｜ 原理见 06-09 ｜ 模块见 07-12，具体标志与平台分支需对照实际版本核验。
