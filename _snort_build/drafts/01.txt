# Snort 3 技术资料 · 01 基础与概述

## 01-01 Snort 3 是什么：重写动机、能力矩阵与适用边界

### 1. 背景与动机

要理解 Snort 3 是什么，必须先把它与「Snort 2 的又一次小版本升级」严格区分开。上游快照的官方用户手册在 `doc/user/overview.txt` 开篇即写明，Snort 3 是「an updated version of the Snort Intrusion Prevention System (IPS) which features a new design」，并强调这一新设计提供「a superset of Snort 2.X functionality」，在吞吐、检测、可扩展性与易用性上都有变化；同一文件还解释了命名关系：「Snort++ is the project that is creating Snort 3.0」，本手册中「Snort」或「Snort 3」指 3.0 版本，需要区分时才把更早版本称为「Snort 2」。这段官方表述是理解全册的锚点：它不是补丁式的演进，而是围绕新设计重新组织的一次实现。顶层 `README.md` 同样以「Snort 3 is the next generation Snort IPS」定位项目，并把「Use a simple, scriptable configuration」「Make key components pluggable」「Support multiple packet processing threads」列为关键特征。

重写的直接动机来自 Snort 2 时代积累的结构性限制。`doc/upgrade/differences.txt` 以「Features Improved over Snort 2」为题给出了一张对照表，其中若干项足以说明问题：包处理线程由「1 per process」演进为「N per process」，配置内存由「每进程各持一份配置」变为「多进程共享一份配置」、报文缓冲另计，配置解析由「Report one error and quit」变为「Report all errors」，配置语法由「Irregular, static, limited variables」变为「Lua, fully scriptable, arbitrary variables」，构建系统由 Automake 变为 Cmake，插件体系由「Limited to preprocs and outputs」变为完整插件系统。这些条目在本套资料中只作定性引用，任何涉及吞吐、内存、包速的具体数字一律标注「需在目标机型实测」，不给绝对值、不作跨机型推广。同样，关于线程数量的表述只到「支持多个包处理线程」为止，具体数量由运行配置与实际版本决定，需对照实际版本核验（`src/main/analyzer.cc`、`src/main/process.cc`、`src/main/numa.cc`、`src/framework/pig_pen.cc`），本套资料不断言任何「默认 N 线程」。

从实现语言看，`CMakeLists.txt` 首部是 `project (snort CXX C)`，并设有 `set (CMAKE_CXX_STANDARD 17)` 与 `set (CMAKE_C_STANDARD 99)`，明确以 C++ 为主体、C 为辅；`src/main.cc` 中出现 `using namespace snort;`、`std::thread`、`std::mutex`、`std::map`、`std::queue` 等 C++ 设施，与 Snort 2 以 C 为主的代码形态形成代际差异。从配置形态看，`lua/snort.lua` 首行注释为「Snort++ configuration」，随后是 `HOME_NET = 'any'`、`EXTERNAL_NET = 'any'` 与 `include 'snort_defaults.lua'`，整份文件按「1. configure defaults → 8. configure tweaks」八个段落组织，这是 Lua 表与脚本，而不是 Snort 2 的 `snort.conf` 指令文本。换言之，Snort 3 是相对 Snort 2 用 C++ 重写、改用 Lua 配置的全新实现，二者配置不兼容、插件 ABI 也不兼容，这一点贯穿本册四篇。

本套资料的版本基准统一写「上游 master 快照（2026-11 抓取）」。具体版本号以 `CMakeLists.txt`（其中通过 `VERSION_MAJOR`、`VERSION_MINOR`、`VERSION_PATCH`、`VERSION_SUBLEVEL` 等变量组织版本字样）与 `ChangeLog.md` 为准，需对照实际版本核验；本套资料不把源码中的版本字样抄作自身版本号。事实核验的唯一锚点是 `_snort_build/upstream_src/snort3/snort3-master/`，下文凡出现路径，均相对该仓库根（规范中为节约篇幅省略 `snort3-master/` 前缀）。

### 2. 核心概念

Snort 3 的核心概念可以压缩为「两种运行姿态、一个抓包边界、一套 Lua 配置、一层插件抽象」。

第一种运行姿态是 IDS 旁路：引擎从镜像口、TAP 或 pcap 文件取得流量副本，解码、解析、检测后只产生告警，不干预原始报文的转发。第二种是 IPS 内联：引擎串接在流量路径上，命中 `drop` / `block` / `reject` 等动作时，通过 DAQ verdict 把处置结果反馈给抓包层，由抓包层决定是否放行。必须写清楚的是，内联 IPS 的丢弃能力来自 verdict 反馈链路（`src/actions/act_drop.cc`、`src/actions/act_block.cc`、`src/actions/act_reject.cc`、`src/packet_io/active.cc`，以及 `src/packet_io/sfdaq.cc` 中 `SFDAQ::verdict_to_string(DAQ_Verdict)` 一类的适配函数），Snort 本身不是防火墙、不做 IP 转发、不做路由；把内联模式理解成「Snort 替你转发并过滤」是最常见的定位错误。IDS 旁路模式下则只告警不丢弃，两种姿态的取舍属于部署决策（原理见 06-12）。

抓包边界是另一条硬约束：Snort 3 不内置抓包，依赖独立的 libdaq / DAQ3。`README.md` 的依赖清单把「DAQ from https://github.com/snort3/libdaq for packet IO」与 LuaJIT、pcap、PCRE2、hwloc 等并列，`snort.pc.in` 更把 `cpp_opts=DAQ LUAJIT` 列为核心编译选项，而 `HYPERSCAN`、`LZMA`、`OPENSSL`、`PCAP`、`PCRE2`、`UUID` 等归入 `cpp_opts_other`。仓库内 `src/packet_io/sfdaq.cc`、`sfdaq_config.cc`、`sfdaq_instance.cc`、`sfdaq_module.cc` 与 `daqs/`（`daq_file.c`、`daq_hext.c`）只是适配层与示例 module，DAQ module 决定实际抓包与内联能力。本快照 `lua/inline.lua` 中出现 `name = 'pcap'` 与 `mode = 'read-file'`，`lua/talos.lua` 中出现 `name = 'dump'`；其余在线 module 名（如各类 afpacket / nfq 形态）需对照实际版本核验，定位目录为 `src/packet_io/sfdaq_module.cc` 与 `daqs/`。因此不能写成「Snort 自带抓包、与 DAQ 无关」，也不能宣称某个 module 无需适配即插即用（原理见 06-02）。

Lua 配置模型以 `lua/snort.lua` 为主干、`lua/snort_defaults.lua` 为外部默认值。主干里 `stream = { }` 这类空表表示「用模块内置默认」，注释明确写着「mod = { } uses internal defaults」「you can see them with snort --help-module mod」；`gtp_inspect = default_gtp`、`port_scan = default_med_port_scan`、`smtp = default_smtp`、`wizard = default_wizard` 则引用 `lua/snort_defaults.lua` 中定义的 `default_*` 表；`ips = { variables = default_variables }` 把网络变量、路径变量、端口变量注入检测策略；文件末尾 `if ( tweaks ~= nil ) then include(tweaks .. '.lua') end` 支持按 tweaks 叠加策略，这正是 `lua/inline.lua`（`-- use with --tweaks inline`）、`lua/max_detect.lua`（`-- use with -c snort.lua --tweaks max_detect`）、`lua/talos.lua`（`-- use with --talos or --tweaks talos`）三份预置模板的接入方式。完整段名、键名与默认值是 04 册的权威范围，本册只给最小必要片段（完整参数见 04-02）。

插件抽象落在 `src/framework/`：`base_api.h` 定义 `struct BaseApi`（含 `type`、`size`、`api_version`、`version`、`features`、`options`、`name`、`help`、`mod_ctor`、`mod_dtor` 等成员，此处只点名结构不展开字段表，字段见 05-04）与 `enum PlugType`（`PT_CODEC`、`PT_INSPECTOR`、`PT_IPS_ACTION`、`PT_IPS_OPTION`、`PT_SEARCH_ENGINE`、`PT_SO_RULE`、`PT_LOGGER`、`PT_CONNECTOR`、`PT_POLICY_SELECTOR`、`PT_MP_TRANSPORT`、`PT_TRACE`、`PT_MAX`），并以 `BASE_API_VERSION 29` 与 `API_OPTIONS` 约束插件与引擎的匹配。`src/managers/` 下的 `inspector_manager.cc`、`module_manager.cc`、`ips_manager.cc`、`action_manager.cc`、`plugin_manager.cc`、`mpse_manager.cc`、`script_manager.cc`、`codec_manager.cc`、`event_manager.cc`、`so_manager.cc` 负责装配。这套 ABI 与 Snort 2 的 preprocessor / output 插件不兼容，`tools/snort2lua/` 只是配置文本的格式转换辅助工具，不等于配置可直接沿用、更不等于二进制插件可迁移（模块见 07-01、07-11）。

还有两条容易被写反的边界。其一，加密流量载荷不可见：引擎能拿到的是握手元数据、证书等信息（具体字段名需对照实际版本核验，`src/service_inspectors/ssl/`、`src/network_inspectors/appid/`），应用识别依赖 inspector / binder / wizard（`src/network_inspectors/binder/binder.cc`、`bind_module.cc`、`binding.cc` 与 `src/service_inspectors/wizard/wizard.cc`、`wiz_module.cc`、`spells.cc`、`magic.cc`、`hexes.cc`），绝不能宣称能读到 HTTPS 明文正文（原理见 06-04）。其二，Hyperscan 是可选 search_engine 加速：`src/search_engines/hyperscan.cc` 存在，但同目录还有 `ac_bnfa.cc`、`ac_full.cc`、`acsmx2.cc`、`bnfa_search.cc` 等实现；`CMakeLists.txt` 以 `HAVE_HYPERSCAN` 打印开关状态，`config.cmake.h.in` 中 `#cmakedefine HAVE_HYPERSCAN 1` 是编译期开关，缺失时回退其他多模式匹配实现（构建选项的完整清单见 04-01，原理见 06-07）。统一交叉引用写法为（字段见 05-02 ｜ 参数见 04-02 ｜ 原理见 06-01 ｜ 模块见 07-01）。

下表按「能做 / 不能做」给出能力矩阵，结论均以本快照源码为依据。

| 能力项 | 结论 | 依据源码位置 |

### 4. 关键流程与调用链

启动链路在 `src/main.cc` 中非常清晰：`main(int argc, char* argv[])` 先做 `set_mem_constraint_handler_s` 等安全回调设置，读取 `SNORT_PROMPT` 环境变量（未设置时 `get_prompt()` 返回内置的 `o")~ `），随后依次调用 `Snort::setup(argc, argv)`、`set_mode()`、`snort_main()`、`Snort::cleanup()`。`Snort::setup` 与 `Snort::init(int argc, char** argv)`、`Snort::term()`、`Snort::drop_privileges()`、`Snort::do_pidfile()`、`Snort::get_reload_config(const char* fname)` 等定义在 `src/main/snort.cc`，共同完成配置加载、模块装配、权限收敛与热重载准备。`snort_main()` 里 `max_pigs = ThreadConfig::get_instance_max()`，`pigs = new Pig[max_pigs]`，再进入 `main_loop()`；`Pig::prep(const char* source)` 中 `new SFDAQInstance(source, idx, sc->daq_config)`、`SFDAQ::init_instance(instance, sc->bpf_filter)`、`new Analyzer(instance, idx, source, sc->pkt_cnt, sc->retry_timeout)` 串起单个包处理线程的准备；`Pig::start()` 用 `new std::thread(std::ref(*analyzer), swapper, ++run_num)` 拉起线程。这里再次强调：线程 / 进程模型与资源隔离以实际版本为准，`src/main/swapper.cc`、`process.cc`、`numa.cc`、`analyzer.cc` 的实现需对照实际版本核验，本册不断言任何默认线程数（原理见 06-13）。

包处理链路在本册只讲「做什么」不讲「怎么实现」：DAQ3 收包（`src/packet_io/sfdaq.cc`，含 `SFDAQ::load`、`SFDAQ::init`、`SFDAQ::init_instance`、`SFDAQ::term`、`SFDAQ::get_input_spec`、`SFDAQ::default_type`、`SFDAQ::get_stats` 等已核验函数）→ 解码与归一化（`src/codecs/`、`src/protocols/packet.cc`）→ binder / wizard 绑定与服务识别（`src/network_inspectors/binder/`、`src/service_inspectors/wizard/`）→ 流重组与协议 inspector（`src/stream/`、`src/service_inspectors/`）→ 检测求值（`src/detection/detection_engine.cc`，含 `DetectionEngine::thread_init`、`DetectionEngine::init`、`DetectionEngine::get_context`、`DetectionEngine::get_event_queue`、`DetectionEngine::finish_inspect`、`DetectionEngine::finish_packet` 等）→ 动作与输出（`src/actions/`、`src/loggers/`）。这条流水线的状态机、编译过程与逐段实现全部属于 06 册（原理见 06-01），各目录的能力清单属于 07 册（模块见 07-02、07-05、07-07、07-08）。

配置自检是理解「重写后能否跑起来」的关键落点。`src/main.cc` 的 `set_mode()` 先检查 `get_parse_errors()` / `get_parse_warnings()`，命中 `just_validate()` 时打印 `Snort successfully validated the configuration (with %u warnings).`，并置 `sc->run_flags |= RUN_FLAG__TEST` 后不进入收包循环；`doc/upgrade/differences.txt` 也记录了「-T is assumed if no input given」。这意味着「配置能否被 Lua 解析、模块能否装配、规则能否编译、DAQ 配置是否合法」可以在不接真实流量的前提下先行验证，是迁移与上线的第一道关口。命令行形态的具体选项以实际版本为准，需对照实际版本核验（`src/parser/cmd_line.cc`、`src/main/help.cc`；完整命令见 04-07）。

### 5. 配置/命令/代码实例

本册是总览册，只给理解定位所需的最小配置，完整段名、键名、默认值与命令全集一律交给 04 册（完整参数见 04-02、04-07）。下面这段摘自 `lua/snort.lua` 的 inspection 段，展示「空表即用内置默认」这一 Lua 配置惯用法：

```lua
-- mod = { } uses internal defaults
-- you can see them with snort --help-module mod
stream = { }
stream_ip = { }
stream_icmp = { }
stream_tcp = { }
stream_udp = { }
stream_user = { }
stream_file = { }
```

这段写法与 Snort 2 `snort.conf` 中逐条写 `preprocessor` 指令的形态完全不同：`stream = { }` 不是关闭模块，而是实例化该模块并采用内部默认值；想看某个模块有哪些可调项，用注释里给出的 `snort --help-module mod`。`lua/snort_defaults.lua` 则集中放置 `RULE_PATH`、`BUILTIN_RULE_PATH`、`PLUGIN_RULE_PATH`、`WHITE_LIST_PATH`、`BLACK_LIST_PATH` 等路径变量，以及 `default_variables`、`default_wizard`、`default_references`、`default_classifications`、`default_gtp`、`default_med_port_scan`、`default_js_norm`、`default_extractor` 等外部默认表，末尾以 `snort_whitelist_append(default_whitelist)` 收束可被配置引用的名字集合。理解「内置默认 + 外部默认 + tweaks 叠加」三层，就不会把空表误读成空配置。

下面给出「前置检查 → 执行 → 验证输出 → 清理」闭环中最关键的一步：用配置自检确认 `HOME_NET`、`include`、模块段与 `ips` 段能被正确加载。命令形态需对照实际版本核验，以下为参考写法：

```bash
snort -c lua/snort.lua -T
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
示例输出，具体格式需对照实际版本核验
Lua 配置加载：HOME_NET / EXTERNAL_NET 已解析
外部默认：snort_defaults.lua 已 include
模块装配：stream / binder / wizard / ips 完成
规则编译：0 条文本规则，0 项 fast pattern
DAQ 校验：未指定在线输入，进入配置自检模式
Snort successfully validated the configuration (with 0 warnings).
```

逐行判读如下。第一行是「示例输出」声明，提示真实日志的排版、字段顺序与措辞随版本变化，必须以目标版本的实际输出为准。第二行对应 `lua/snort.lua` 中 `HOME_NET = 'any'`、`EXTERNAL_NET = 'any'` 与 `src/parser/vars.cc` / `src/lua/lua.cc` 的变量解析，正常应为「已解析」；若出现 Lua 语法错误或变量未定义，通常要先查缩进、引号与 `include` 路径，而不是去改规则。第三行对应 `include 'snort_defaults.lua'`，正常应成功；若报文件找不到，多为工作目录与 `RULE_PATH` 一类路径变量未对齐（完整变量见 04-02）。第四行对应 `src/managers/` 的模块装配与 `src/framework/module.h` 中 `begin(const char*, int, SnortConfig*)`、`get_parameters()` 的参数校验，正常应为各模块名齐备；若某模块名报错，多为键名与实际版本不一致，需对照实际版本核验。第五行对应 `src/parser/parse_rule.cc` 的规则编译，本例未给规则文件故为 0 条，属于正常值；生产环境若加载了规则集却仍显示 0 条，应检查 `ips` 段的 `include` 与 `variables`（参数见 04-06）。第六行对应 `src/main.cc` 的 `just_validate()` 分支，说明当前处于自检而非收包状态。最后一行是 `set_mode()` 中已核验的真实字符串，`with 0 warnings` 表示零告警；正常值应为 0，出现非零 warning 时应逐条核对配置而不宜忽略，因为 `snort.lua` 注释与 `doc/upgrade/differences.txt` 都强调 Snort 3 会「Report all errors」而非遇错即停。清理环节即自检进程自行退出，不产生常驻线程与日志落盘。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是把 Snort 2 的 `snort.conf` 直接拿来启动。Snort 3 是从 Snort 2 重写的全新实现，配置为 Lua，不兼容 `snort.conf` 与旧插件 ABI；`tools/snort2lua/` 只是格式转换辅助，其 `config_states/`、`keyword_states/`、`data/`、`helpers/` 子目录把旧指令映射成 Lua 表，转换结果仍须人工逐项比对并用 `snort -T` 验证（迁移说明见 `doc/upgrade/snort2lua.txt`，原理见 06-14）。第二个陷阱是以为「Snort 自带抓包」：抓包依赖独立 libdaq / DAQ3，`snort.pc.in` 把 `DAQ` 列在 `cpp_opts` 中，`src/packet_io/sfdaq*.cc` 只是适配层；DAQ module 未安装或名称写错会在启动阶段失败，module 名需对照实际版本核验。第三个陷阱是把内联 IPS 当防火墙：drop / block / reject 通过 DAQ verdict 反馈实现，Snort 不做 IP 转发、不做路由，fail-open 一类行为的配置需对照实际版本核验（`src/packet_io/active.cc`、`src/actions/`）。

第四个陷阱是宣称能读 HTTPS 明文正文。加密流量载荷不可见，可用的是握手元数据与证书信息（字段名需对照实际版本核验），应用识别靠 inspector / binder / wizard，不能把「识别到服务」等同于「看到明文」。第五个陷阱是把 Hyperscan 写成必需依赖或唯一实现：`src/search_engines/` 同时存在 `hyperscan.cc`、`ac_bnfa.cc`、`ac_full.cc`、`acsmx2.cc`、`bnfa_search.cc`，`config.cmake.h.in` 的 `HAVE_HYPERSCAN` 只是编译期开关，缺失时回退其他多模式匹配实现（原理见 06-07）。第六个陷阱是照抄绝对性能数字或断言「默认 N 线程」：吞吐、pps、丢包率、内存占用一律需在目标机型实测，基准方法见 08-01、调优见 08-02；线程 / 进程模型以实际版本为准，需对照实际版本核验（`src/main/analyzer.cc`、`numa.cc`）。

最佳实践可以归纳为四步：先用 `snort -V`、`snort --help` 与 `snort --help-module mod` 摸清当前版本的真实能力面（完整命令见 04-07）；再从 `lua/snort.lua` 的最小主干起步，把 `HOME_NET` / `EXTERNAL_NET` 从 `'any'` 收敛到实际保护网段；随后用 `snort -c lua/snort.lua -T` 做配置自检，确认零 error、warning 可控；最后才接 pcap 或在线 DAQ module 做灰度。规则集方面要单独确认 Talos 规则集的许可边界，不能把规则与引擎按同一 GPLv2 许可任意分发（详见 01-04，完整规则关键字见 04-06）。

至于「何时不该用 Snort 3」，边界同样明确：需要 IP 转发、路由或完整防火墙策略时，它不是合适工具；需要读取加密载荷明文正文时，物理上做不到；只需要一个纯字符串 / 正则匹配库时，引入整套 IDS/IPS 引擎属于过度设计；运行环境无法提供 LuaJIT 与独立 libdaq / DAQ3 时，无法落地；依赖 Snort 2 二进制插件 ABI 且不愿重写插件时，迁移成本高于收益；需要厂商承诺某个固定默认线程数或某个绝对吞吐数字时，本套资料不提供这类断言。这些「不该用」的场景与第 2 节的能力矩阵互为镜像，阅读时应一起对照。

### 7. 小结与延伸阅读

本篇把 Snort 3 定位为「相对 Snort 2 用 C++ 重写、改用 Lua 配置、插件化、依赖独立 libdaq / DAQ3 的 IDS/IPS 引擎」：能做旁路告警、内联 verdict 丢弃、按 inspector 解析协议、输出 JSON 与 unified2；不能做 IP 转发与路由、不能读加密明文、不自带抓包、不兼容 Snort 2 配置与插件 ABI。启动链路 `main()` → `Snort::setup()` → `set_mode()` → `snort_main()` → `Snort::cleanup()` 与配置自检字符串 `Snort successfully validated the configuration (with %u warnings).` 是后续所有篇章的共同入口；`lua/snort.lua` 八段结构、`lua/snort_defaults.lua` 的 `default_*` 表、`src/framework/base_api.h` 的 `BaseApi` / `PlugType`、`src/managers/` 的装配职责，则构成理解架构的骨架。

延伸阅读建议按三条线走：定位与特性读 `doc/user/overview.txt`、`doc/user/features.txt`、`doc/user/concepts.txt`、`doc/user/terms.txt` 与顶层 `README.md`；代际差异与迁移读 `doc/upgrade/differences.txt`、`doc/upgrade/overview.txt`、`doc/upgrade/snort2lua.txt`；本册后续三篇分别处理引擎对比（01-02）、全链路架构（01-03）与版本许可生态（01-04）。跨册随查按（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-01）执行：结构体逐字段去 05、参数与命令全集去 04、机制与调用链去 06、目录级模块能力去 07、运维场景与基准去 08。凡本篇标注「需对照实际版本核验」的字段、函数名签名、DAQ module 名、命令行选项与版本号，均以 `_snort_build/upstream_src/snort3/snort3-master/` 下对应文件为准，本套资料不编造未核验的路径与取值。

## 01-02 与 Snort 2 / Suricata / Zeek 的引擎对比

### 1. 背景与动机

把 Snort 3 放进同类引擎的坐标系里，是选型、迁移与澄清误解三步的前置条件。很多关于 Snort 3 的争论其实源于把不同代际、不同关注点的东西放在同一张表上比：有人拿 Snort 2 的 `snort.conf` 去要求 Snort 3 兼容，有人拿 Suricata 的 EVE 输出去要求 Snort 3 具备一模一样的字段，还有人把 Zeek 的事务日志脚本能力当成「IDS 该有的功能」。本篇的目的不是评出优劣，而是把四类引擎的边界画清楚，并给出可执行的选型决策依据。需要先声明口径：对 Snort 3 的所有结论以上游 master 快照（2026-11 抓取）的源码与文档为准；对 Suricata、Zeek 只作业界通行的定性分工描述，不涉及它们的源码级断言，具体能力、字段与版本差异需对照各自实际版本核验。本套资料不写绝对性能数字，任何吞吐、pps、丢包率、内存占用结论一律标注「需在目标机型实测」。

四类引擎的定位可以这样概括。Snort 2 是遗留的、以单进程 / 单包处理线程为主、以 `snort.conf` 文本指令配置、以 preprocessor 与 output 插件为扩展点的规则匹配引擎；`doc/upgrade/differences.txt` 用它作为「Features Improved over Snort 2」的对照基线。Snort 3（Snort++）是同系列的重写实现：`doc/user/overview.txt` 说它提供「a superset of Snort 2.X functionality」，关键特征包括多包处理线程、共享配置与属性表、服务自动检测、模块化设计、LuaJIT 配置 / logger / rule option、Hyperscan 支持、重写 TCP 处理、新规则解析器与语法、sticky buffer、service rules 等。Suricata 与 Zeek 属于另一类分工：前者通常被归入「多线程 IDS/IPS + 结构化 EVE JSON 输出」一侧，后者通常被归入「网络事务日志 + 脚本化分析」一侧。三者与 Snort 3 可以共存于同一条监测链路，但职责不同，不能相互替代，也不宜用同一套指标横向打分。

代际差异最容易被低估的是「配置范式」。`doc/upgrade/differences.txt` 的对照表把 Snort 2 的配置语法描述为「Irregular, static, limited variables」，把 Snort 3 描述为「Lua, fully scriptable, arbitrary variables」；把解析行为从「Report one error and quit」改为「Report all errors」；把命令行能力从「Some overlap with config file」改为「Set or override any config from command line」；把构建系统从 Automake 改为 Cmake；把插件从「Limited to preprocs and outputs」扩展为完整插件体系。这些条目说明的不是「多了几个选项」，而是配置、扩展、排错三套工作方式的整体更换。因此本篇第 2 节会从配置、规则、抓包、插件四条线分别展开，第 4 节再落到迁移与解析调用链，避免把对比停留在口号层面。

### 2. 核心概念

配置线上的核心事实是：`lua/snort.lua` 与 Snort 2 的 `snort.conf` 不是两种写法、而是两种范式。`lua/snort.lua` 以 `HOME_NET = 'any'`、`EXTERNAL_NET = 'any'` 起手，用 `include 'snort_defaults.lua'` 引入外部默认，用 `stream = { }`、`http_inspect = { }`、`binder = { ... }`、`ips = { variables = default_variables }` 等 Lua 表组织模块，末尾还能 `include(tweaks .. '.lua')` 叠加策略模板。`lua/snort_defaults.lua` 里 `default_variables` 又分 `nets` / `paths` / `ports` 三组，分别对应 `HOME_NET`、`RULE_PATH`、`HTTP_PORTS` 等变量。Snort 2 的 `snort.conf` 则是指令式文本，二者不存在逐行对应关系。`tools/snort2lua/` 的存在正好反证了不兼容：它是把旧指令映射成 Lua 表的转换器，其内部按 `config_states/`、`keyword_states/`、`data/data_types/`、`helpers/` 划分，入口相关文件包括 `init_state.cc`、`conversion_state.h`、`conversion_defines.h`、`helpers/converter.cc`、`helpers/parse_cmd_line.cc`。转换只是起点，`doc/upgrade/snort2lua.txt` 与 `doc/upgrade/overview.txt` 才给出迁移语境；把转换结果不经 `snort -T` 校验直接上线，是典型误用（完整参数见 04-02）。

规则线同样不能宣称兼容。`doc/upgrade/differences.txt` 列出 Rule syntax 由「Inconsistent, requires line escapes」变为「Uniform syntax, arbitrary whitespace」、Rule sticky buffers 由「Some」变为「All buffers are sticky」、`fast_pattern_only` 由「Hand optimization」变为「Automatic optimization」、Elided rule headers、service rules、SO rules 变为文本规则的真超集等差异。落到本快照，规则关键字的注册与解析分布在 `src/ips_options/`（`ips_content.cc`、`ips_pcre.cc`、`ips_regex.cc`、`ips_byte_test.cc`、`ips_byte_jump.cc`、`ips_byte_extract.cc`、`ips_byte_math.cc`、`ips_flow.cc`、`ips_flowbits.cc`、`ips_detection_filter.cc` 等）、`src/parser/parse_rule.cc` 与 `src/detection/`，装配在 `src/managers/ips_manager.cc`；`src/parser/parse_rule.cc` 中已核验的函数包括 `parse_rule_init()`、`parse_rule_type()`、`parse_rule_proto()`、`parse_rule_nets()`、`parse_rule_ports()`、`parse_rule_dir()`、`parse_rule_opt_begin()`、`parse_rule_opt_set()`、`parse_rule_opt_end()`、`parse_rule_open()`、`parse_rule_close()`、`parse_rule_process_rtn()`、`parse_rule_finish_ports()`，并涉及 `RuleTreeNode` / `OptTreeNode` 两类节点。结论必须写死：规则关键字与 Snort 2 有差异，差异点需对照实际版本核验，不能宣称与 Snort 2 规则 100% 兼容（完整关键字见 04-06，原理见 06-06，字段见 05-04）。

抓包线是第二个常被写反的地方。`README.md` 把「DAQ from https://github.com/snort3/libdaq for packet IO」列为依赖，`snort.pc.in` 把 `cpp_opts=DAQ LUAJIT` 设为核心编译选项，`src/packet_io/sfdaq.cc`、`sfdaq_config.cc`、`sfdaq_instance.cc`、`sfdaq_module.cc`、`active.cc`、`trough.cc` 与 `daqs/` 构成适配层。`doc/upgrade/differences.txt` 把 DAQ 的变化概括为「2.X, run to completion」到「3.X, vector input, multiple outstanding packets」，把 DAQ Modules 从 legacy modules 扩展到 stacked modules、IOCTLs、file / socket / text modules。也就是说，抓包能力由独立 libdaq / DAQ3 与所选 DAQ module 决定，而不是 Snort 自带；本快照 `lua/inline.lua` 使用 `name = 'pcap'` 与 `mode = 'read-file'`，`lua/talos.lua` 使用 `name = 'dump'`，其余在线 module 名需对照实际版本核验（`src/packet_io/sfdaq_module.cc`、`daqs/`；原理见 06-02）。与之相对，Suricata / Zeek 侧本文只说「各自有独立抓包接入方式」，不对其 module 名与实现细节作断言。

插件线决定了「旧资产能否直接搬」。`src/framework/base_api.h` 的 `struct BaseApi` 与 `enum PlugType`（含 `PT_CODEC`、`PT_INSPECTOR`、`PT_IPS_ACTION`、`PT_IPS_OPTION`、`PT_SEARCH_ENGINE`、`PT_SO_RULE`、`PT_LOGGER`、`PT_CONNECTOR`、`PT_POLICY_SELECTOR`、`PT_MP_TRANSPORT`、`PT_TRACE`）定义了插件 API 前缀，`BASE_API_VERSION 29` 与 `API_OPTIONS` 用于检测构建不匹配；`src/managers/plugin_manager.cc` 负责加载。这套 ABI 与 Snort 2 的 preprocessor / output 插件不兼容，`tools/snort2lua/` 只转配置文本、不转二进制插件。再加上 `doc/upgrade/differences.txt` 明确 Event Logging 由「Legacy unified2 recommended」变为「JSON recommended, integrates with ELK stack」，可见从输出形态到扩展机制都是代际更换。统一交叉引用写法为（字段见 05-04 ｜ 参数见 04-06 ｜ 原理见 06-14 ｜ 模块见 07-01）。

### 3. 关键数据结构与源码位置

本节沿用总览册约束：只点名结构与路径，不展开字段表、不罗列 API 全集。与「对比」最相关的结构有：`RuleTreeNode` / `OptTreeNode`（`src/parser/parse_rule.cc`，规则头与选项树的承载，字段见 05-04）、`SnortConfig`（`src/main/snort_config.cc/.h`、`src/main/snort_module.cc/.h`，配置上下文，字段见 05-03）、`BaseApi` 与 `PlugType`（`src/framework/base_api.h`，插件 ABI 前缀，字段见 05-04）、`SFDAQConfig` / `SFDAQInstance`（`src/packet_io/sfdaq_config.cc`、`sfdaq_instance.cc`，DAQ 配置与实例，字段见 05-07）、`Parameter` / `Value`（`src/framework/parameter.cc/.h`、`value.cc/.h`，参数与值对象，字段见 05-03）、`Module`（`src/framework/module.cc/.h`，其 `get_parameters()` 与 `begin(const char*, int, SnortConfig*)` 已在头文件中核验，字段见 05-04）。`src/parser/cmd_line.cc` 的 `set_arg()` 依据 `Parameter::PT_IMPLIED`、`PT_INT`、`PT_PORT`、`PT_REAL` 等类型把命令行值转成 `Value`，再调用 `m->set(p->name, v, sc)`，这正是「命令行可覆盖任意配置项」的实现支点（完整命令见 04-07）。

下表把代际差异与可核验路径对应起来，便于迁移时逐项定位。

四类引擎的选型决策见下表；表中对 Suricata / Zeek 只给关注点，不给未经核验的配置键与函数名。

| 选型诉求 | 更贴近的一类 | 判定要点 |
|---|---|---|
| 沿用既有 Snort 2 规则与插件资产 | Snort 2 或先迁移 | 配置与 ABI 均不兼容，需 snort2lua 与人工校验 |
| 需要 Lua 深度定制、插件化 IPS | Snort 3 | `lua/snort.lua`、`src/framework/`、DAQ3 内联 |
| 侧重大规模结构化告警与多线程输出 | Suricata 类 | EVE JSON 为通行形态，需对照实际版本核验 |
| 侧重事务日志与脚本化分析 | Zeek 类 | 日志脚本分工，需对照实际版本核验 |
| 需要防火墙转发与路由策略 | 均不适用 | Snort 3 不做转发，非防火墙 |
| 需要绝对吞吐承诺 | 均不适用 | 一律需在目标机型实测 |

### 4. 关键流程与调用链

迁移流程可以拆成四步，且每一步都有源码落点。第一步是格式转换：`snort.conf` 经 `tools/snort2lua/` 的 `config_states/` 与 `keyword_states/` 映射为 Lua 表，`data/data_types/` 下的 `dt_table.cc`、`dt_rule.cc`、`dt_var.cc` 等负责生成表 / 规则 / 变量节点，`helpers/converter.cc` 组织转换过程。第二步是配置落地：把结果并入 `lua/snort.lua` 主干，用 `lua/snort_defaults.lua` 的 `default_variables` 补齐 `nets` / `paths` / `ports` 变量，脚本由 `src/lua/lua.cc`、`src/parser/parse_conf.cc`、`src/parser/vars.cc` 加载（配置加载链路的原理见 06-01）。第三步是自检：`snort -c lua/snort.lua -T` 触发 `src/main.cc` 的 `just_validate()` 分支，命中后打印 `Snort successfully validated the configuration (with %u warnings).` 并置 `RUN_FLAG__TEST`。第四步是规则差异比对：逐条确认旧规则的关键字在新引擎中的注册与语义，注册在 `src/ips_options/` 与 `src/managers/ips_manager.cc`，解析在 `src/parser/parse_rule.cc`，不能跳过（原理见 06-06，完整关键字见 04-06）。

规则解析调用链值得单独点名，因为「兼容性」争议大多落在这里。`src/parser/parse_rule.cc` 中已核验的顺序大致为：`parse_rule_init()` 初始化 → `parse_rule_type()` 判定动作类型 → `parse_rule_proto()` 处理协议 → `parse_rule_nets()` / `parse_rule_ports()` 处理地址与端口 → `parse_rule_dir()` 处理方向 → `parse_rule_opt_begin()` / `parse_rule_opt_set()` / `parse_rule_opt_end()` 逐项处理选项关键字 → `parse_rule_open()` / `parse_rule_close()` 开合 `OptTreeNode` → `parse_rule_process_rtn()` 与 `parse_rule_finish_ports()` 收束规则树与端口分组。`doc/upgrade/differences.txt` 提到的 uniform syntax、arbitrary whitespace、sticky buffer、elided headers 等差异，正是由这套解析与 `src/detection/` 的编译共同体现；差异点需对照实际版本核验，不能凭 Snort 2 经验推断。

命令行覆盖链路则解释了「为什么 Snort 3 不必把所有东西写进配置文件」。`src/parser/cmd_line.cc` 的 `check_flags()` 会检查 `RUN_FLAG__INLINE` 与 `RUN_FLAG__INLINE_TEST` 冲突、`--pcap-loop` 与 pcap 输入的组合约束；`set_arg()` 按 `Parameter` 类型把字符串转成 `Value` 后交给 `m->set(p->name, v, sc)`；`doc/upgrade/differences.txt` 把这一点概括为「add or override any config item on command line」，并列出 `--pause`、`--shell`、`--help-config`、`--script-path`、`--require-rule-sid` 等新增或加固项。具体选项清单与取值需对照实际版本核验（`src/parser/cmd_line.cc`、`src/main/help.cc`），完整命令见 04-07。

关于多线程，这里只作定性说明：`doc/upgrade/differences.txt` 写「Packet Threads: 1 per process → N per process」，`src/main.cc` 的 `Pig` 类与 `std::thread`、`src/main/analyzer.cc`、`swapper.cc`、`process.cc`、`numa.cc`、`src/framework/pig_pen.cc` 体现线程本地存储与编排；但具体数量、绑核策略与 NUMA 行为以实际版本与运行配置为准，需对照实际版本核验，本套资料不断言「默认 N 线程」、也不给吞吐倍数（原理见 06-13，基准方法见 08-01）。四类引擎按关注点的分工关系见图 01-02-01。

### 5. 配置/命令/代码实例

先看 `lua/snort_defaults.lua` 中 `default_variables` 的完整定义，它最能说明「Snort 3 的变量是一张 Lua 表、而不是散落在 `snort.conf` 里的指令」。以下为该文件中该段的逐字摘录：

```lua
default_variables =
{
    nets =
    {
        HOME_NET = HOME_NET,
        EXTERNAL_NET = EXTERNAL_NET,
        DNS_SERVERS = DNS_SERVERS,
        FTP_SERVERS = FTP_SERVERS,
        HTTP_SERVERS = HTTP_SERVERS,
        SIP_SERVERS = SIP_SERVERS,
        SMTP_SERVERS = SMTP_SERVERS,
        SQL_SERVERS = SQL_SERVERS,
        SSH_SERVERS = SSH_SERVERS,
        TELNET_SERVERS = TELNET_SERVERS,
    },
    paths =
    {
        RULE_PATH = RULE_PATH,
        BUILTIN_RULE_PATH = BUILTIN_RULE_PATH,
        PLUGIN_RULE_PATH = PLUGIN_RULE_PATH,
        WHITE_LIST_PATH = WHITE_LIST_PATH,
        BLACK_LIST_PATH = BLACK_LIST_PATH,
    },
    ports =
    {
        FTP_PORTS = FTP_PORTS,
        HTTP_PORTS = HTTP_PORTS,
        MAIL_PORTS = MAIL_PORTS,
        ORACLE_PORTS = ORACLE_PORTS,
        SIP_PORTS = SIP_PORTS,
        SSH_PORTS = SSH_PORTS,
        FILE_DATA_PORTS = FILE_DATA_PORTS,
    }
}
```

这张表通过 `ips = { variables = default_variables }` 注入检测策略，`nets` 组承接 `HOME_NET` / `EXTERNAL_NET` 与各 `*SERVERS` 变量，`paths` 组承接规则与黑白名单路径，`ports` 组承接 `HTTP_PORTS`、`FILE_DATA_PORTS` 等端口集合；`FILE_DATA_PORTS = HTTP_PORTS .. MAIL_PORTS` 这类字符串拼接也体现了 Lua 的可脚本化。迁移时若旧 `snort.conf` 里定义了同名变量，必须逐个核对语义与取值，不能假设一一对应（完整变量见 04-02）。

下面这组「命令 + 输出 + 判读」用于验证某个 Lua 模块的参数面，也是判断「配置是否已从 `snort.conf` 范式切过来」的最快方式。命令形态参考 `lua/snort.lua` 注释中给出的 `snort --help-module mod`：

```bash
snort --help-module ips
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
示例输出，具体格式需对照实际版本核验
Module: ips
  enable_builtin_rules - enable decoder and inspector alerts
  variables            - default_variables (nets / paths / ports)
  include              - rules file path; rules may include other rules
  (帮助文本的排版与字段以实际版本为准，需对照实际版本核验)
  (完整参数见 04-02，规则关键字见 04-06，字段见 05-03)
```

逐行判读如下。第一行是「示例输出」声明，提示帮助文本的分栏、大小写与措辞随版本变化，不能当作固定格式解析。第二行 `Module: ips` 是关键判据：它说明查询对象是一个 Lua 模块名，而不是 `snort.conf` 里的指令；若返回「unknown module」，应先核对模块名是否属于当前版本（模块清单见 07-11）。第三行 `enable_builtin_rules` 对应 `lua/snort.lua` 中 `--enable_builtin_rules = true` 这一注释项，正常为布尔开关，用于启用解码器与 inspector 的内建告警；把它当成旧版 `config enable_*` 指令去拼接会失败。第四行 `variables` 指向上一代码块里的 `default_variables`，正常应显示 `nets` / `paths` / `ports` 三组；若迁移后发现规则里的 `$HTTP_PORTS` 未展开，多半是这组变量没有随 `ips.variables` 正确注入。第五行 `include` 对应 `lua/talos.lua` 中 `ips.include = 'local.rules'` 的写法，表示规则文件路径且规则文件还能继续 include 其他规则文件；生产环境应确认路径与 `RULE_PATH` 一致。最后两行是资料层的提示：帮助文本只用于随查，不构成参数全集（完整参数见 04-02、04-06），字段含义去 05 册（字段见 05-03）。整个命令不接流量、不产生常驻进程，属于零副作用的前置检查，适合放在迁移清单的第一步。

### 6. 注意事项、陷阱与最佳实践

第一，不要宣称 Snort 3 与 Snort 2 规则「完全兼容」。`doc/upgrade/differences.txt` 明确列出规则语法、sticky buffer、fast pattern、SO 规则等差异，具体差异点需对照实际版本核验（`src/ips_options/`、`src/parser/parse_rule.cc`、`src/detection/`）；迁移时应逐条比对而不是整批复制。第二，不要把 `tools/snort2lua/` 当一键迁移：它只做格式转换，`config_states/` 里还有 `config_deleted.cc`、`config_no_option.cc`、`config_one_int_option.cc` 这类处理「旧指令无对应物」的状态文件，转换后必然存在需要人工决策的项（迁移说明见 `doc/upgrade/snort2lua.txt`）。第三，不要把「支持多个包处理线程」读成「默认 N 线程」：线程 / 进程模型与绑核以实际版本为准，需对照实际版本核验，吞吐类结论一律需在目标机型实测（原理见 06-13，调优见 08-02）。

第四，不要混淆分工：Suricata 的 EVE 输出、Zeek 的事务日志脚本是各自关注点，本套资料只对它们作定性描述、不对其配置键与函数作源码级断言；把「别家有某字段」推导成「Snort 3 也该有」会引出错误结论。第五，不要把 `unified2` 当作新部署的推荐形态：`doc/upgrade/differences.txt` 写的是「JSON recommended, integrates with ELK stack」，本快照 `src/loggers/` 同时提供 `alert_json.cc`、`alert_csv.cc`、`alert_fast.cc`、`alert_full.cc`、`alert_syslog.cc`、`unified2.cc` 等，选型应看下游消费侧（输出配置见 04-04、输出原理见 06-11）。第六，不要忽略 DAQ3 独立依赖：抓包能力由 libdaq / DAQ3 与 module 决定，module 名需对照实际版本核验，缺依赖会在启动期失败（原理见 06-02）。第七，不要引用绝对性能数字：`doc/upgrade/differences.txt` 中关于 pcap 读回速度的对比只作定性参考，任何倍数都需在目标机型实测。

最佳实践按场景给四条。已有 Snort 2 资产且计划迁移：按「转换 → `snort -T` → 规则差异比对 → 灰度」四步走，先把 `HOME_NET` / `EXTERNAL_NET` 与端口变量对齐，再逐批放规则。新建 IPS 内联且需要 Lua 深度定制与插件扩展：以 `lua/snort.lua` 为主干，配 `binder` / `wizard` 绑定，明确 DAQ module 与 verdict 策略（参数见 04-03、原理见 06-12）。以结构化告警接入 SIEM 为主：优先评估 `src/loggers/alert_json.cc` 与 `lua/snort_defaults.lua` 中 `default_extractor` 的 `formatting = 'json'`、`connector = 'stdout'` 形态（字段见 05-08）。以全网事务日志与长期分析为主：把 Zeek 类引擎放在旁路分析侧，与 Snort 3 的告警侧并行，而不是互相替换。无论哪种场景，涉及的性能、容量与线程数都需在目标机型实测，并保留回滚方案（上线清单见 08-06）。

### 7. 小结与延伸阅读

本篇把四类引擎的边界压缩成一句话：Snort 3 是 Snort 2 的重写代际，配置从 `snort.conf` 换成 `lua/snort.lua` + `lua/snort_defaults.lua` 的 Lua 表，规则关键字在 `src/ips_options/`、`src/parser/parse_rule.cc` 与 `src/detection/` 中重新注册与解析，抓包从 DAQ 2.X 形态换成独立 libdaq / DAQ3 适配，插件从 preprocessor / output 换成 `src/framework/base_api.h` 定义的完整 ABI；Suricata 与 Zeek 则是不同关注点的引擎，可与 Snort 3 共存但不互相替代。迁移的核心链路是 `tools/snort2lua/` 转换 → Lua 配置落地 → `snort -T` 自检 → 规则差异比对，其中 `parse_rule_init()` 到 `parse_rule_finish_ports()` 的解析链与 `src/parser/cmd_line.cc` 的 `set_arg()` / `m->set()` 覆盖链，是判断「兼容性」最该看的两处源码。

延伸阅读按用途分：代际差异与构建变化读 `doc/upgrade/differences.txt`、`doc/upgrade/overview.txt`，配置转换读 `doc/upgrade/snort2lua.txt`，依赖清单读顶层 `README.md` 与 `snort.pc.in`；本册衔接篇为 01-01（定位与能力矩阵）、01-03（全链路架构）、01-04（版本、许可与资料约定）。跨册随查统一按（字段见 05-04 ｜ 参数见 04-06 ｜ 原理见 06-06 ｜ 模块见 07-06）执行：规则结构与关键字细节去 05 / 04，规则编译与检测机制去 06，`src/ips_options` 与 `src/search_engines` 的目录级能力去 07，迁移与上线场景去 08。凡标注「需对照实际版本核验」的 Suricata / Zeek 能力、DAQ module 名、命令行选项与规则差异点，均不给未经核验的取值；性能、容量与线程数一律需在目标机型实测。

还需补一层方法论说明：本篇所有落在 Snort 3 一侧的结论都附带可定位的源码路径，是因为「引擎对比」最容易滑向印象式判断，只有把差异钉回 `lua/snort.lua`、`src/parser/parse_rule.cc`、`src/packet_io/sfdaq.cc`、`src/framework/base_api.h` 这些真实文件，读者才能用 `snort --help-module`、`snort -V`、`snort -T` 在当前版本上自行复核。而对 Suricata / Zeek 一侧，本套资料刻意只给关注点分工、不给配置键与函数名，因为它们不在上游快照的核验范围内，写具体取值等同于编造。若读者要把三类引擎放进同一份验收清单，建议以 `doc/reference/snort_reference.txt`、`doc/user/usage.txt`、`doc/user/features.txt` 作为 Snort 侧官方随查入口，另以各自官方手册核对对方引擎，再统一在目标机型上做基准；基准方法见 08-01，任何跨引擎的吞吐、延迟与内存结论都不脱离机型给绝对值。

## 01-03 整体架构：DAQ → 解码 → inspectors → detection → loggers

### 1. 背景与动机

前两篇分别解决了「Snort 3 是什么」与「它和同类引擎差在哪」，本篇要解决的是「一个包从进入引擎到产出告警，中间经过哪些层」。这张全链路图既是 06 册（技术原理）的总览入口，也是 07 册（模块与特性）的目录索引：06 册把流水线拆成 DAQ3 收包、解码、binder / wizard、流重组、规则编译、MPSE、检测求值、动作限速、输出、内联、线程与插件等十四篇逐个讲透，07 册按 `src/` 真实目录设十三篇逐目录讲能力，而 01 册只负责把各层的「做什么」串成一条线。因此本篇反复使用的句式是「讲做什么、不讲怎么实现」：凡涉及状态机、编译过程、逐字段取值与内部调用顺序，一律写「原理见 06-xx」；凡涉及结构体成员，一律写「字段见 05-xx」；凡涉及可调项与命令，一律写「参数见 04-xx」；凡涉及目录级能力清单，一律写「模块见 07-xx」。总览册不展开结构体字段表，也不罗列任何模块的 API 全集。

分层本身是重写的产物。`doc/user/overview.txt` 把「Modular design」「Plugin framework with over 200 plugins」「Autodetect services for portless configuration」列为关键特征；`doc/upgrade/differences.txt` 把插件体系从「Limited to preprocs and outputs」推进到完整插件系统，把服务检测从「appid only, port configs required」推进到「Autodetection, most port configs optional」。落到源码，就是把收包、解码、绑定、重组、检测、动作、输出拆成由 `src/framework/` 定义抽象、由 `src/managers/` 装配、由 `lua/snort.lua` 统一驱动的层次，而不是一个巨型的单线程循环。理解这一点，才能明白为什么排障要按层定位：DAQ 没收到包，后面所有层都不会有数据；解码层没识别出协议，binder 就无从绑定；检测层没命中，logger 自然没有事件。

有两处目录事实必须先声明，否则容易按大纲惯用名找错文件。其一，本快照没有独立的 `src/decode/` 目录，解码由 `src/codecs/`（含 `codec_api.cc`、`codec_module.cc`、`root/`、`link/`、`ip/`、`misc/`）与 `src/protocols/packet.cc` 共同承担，需对照实际版本核验。其二，`src/session` 同样是大纲惯用名，会话定义位于 `src/flow/session.h` 与 `src/stream/` 相关文件，需对照实际版本核验。本套资料的版本基准统一为「上游 master 快照（2026-11 抓取）」，具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准，需对照实际版本核验；事实核验锚点为 `_snort_build/upstream_src/snort3/snort3-master/`，下文路径相对该仓库根。

### 2. 核心概念

整条流水线可以切成五段，外加一条贯穿始终的配置与插件轴。

第一段是 DAQ3 收包，也是输入边界。`src/packet_io/sfdaq.cc` 中已核验的函数包括 `SFDAQ::load(const SFDAQConfig* cfg)`、`SFDAQ::init(const SFDAQConfig* cfg, unsigned total_instances)`、`SFDAQ::init_instance(SFDAQInstance*, const string&)`、`SFDAQ::term()`、`SFDAQ::get_input_spec()`、`SFDAQ::get_input_spec(const SFDAQConfig*, unsigned)`、`SFDAQ::default_type()`、`SFDAQ::can_inject()`、`SFDAQ::can_replace()`、`SFDAQ::get_stats()`、`SFDAQ::forwarding_packet(const DAQ_PktHdr_t*)` 与 `SFDAQ::verdict_to_string(DAQ_Verdict)`；配置、实例与 module 分别落在 `sfdaq_config.cc`、`sfdaq_instance.cc`、`sfdaq_module.cc`，响应动作落在 `active.cc`，输入源队列落在 `trough.cc`，静态 module 声明落在 `sfdaq_static_modules.h.in`，示例 module 在 `daqs/`（`daq_file.c`、`daq_hext.c`）。必须再次强调：抓包不内置，依赖独立 libdaq / DAQ3，`snort.pc.in` 把 `cpp_opts=DAQ LUAJIT` 列为核心编译选项；DAQ module 决定抓包与内联能力，module 名需对照实际版本核验（原理见 06-02，模块见 07-07）。

第二段是解码与归一化。`src/protocols/packet.cc/.h`、`packet_manager.cc/.h`、`layer.cc/.h`、`ip.cc/.h`、`ipv4_options.cc`、`tcp_options.cc` 与各协议头（`eth.h`、`ipv4.h`、`ipv6.h`、`tcp.h`、`udp.h`、`vlan.h`、`gre.h`、`ssl.cc` 等）负责协议头定义与分层；`src/codecs/` 下 `root/cd_eth.cc`、`root/cd_raw.cc`、`link/cd_vlan.cc`、`link/cd_arp.cc`、`link/cd_mpls.cc`、`ip/cd_ipv4.cc`、`ip/cd_ipv6.cc`、`ip/cd_tcp.cc`、`ip/cd_udp.cc`、`ip/cd_frag.cc`、`misc/cd_vxlan.cc`、`misc/cd_geneve.cc`、`misc/cd_gtp.cc` 等按层分派解码；抽象基类在 `src/framework/codec.cc/.h`，解码结果容器是 `src/framework/decode_data.h`；`src/network_inspectors/normalize/` 处理归一化。这段的产物是一个填好各层指针与解码标志的 `Packet`（字段见 05-02，原理见 06-03，模块见 07-09）。

第三段是绑定、服务识别与流重组。`lua/snort.lua` 的 `binder` 段用 `{ when = { proto = ..., ports = ..., role = ... }, use = { type = ... } }` 形如条目把流量绑定到 inspector，末条 `{ use = { type = 'wizard' } }` 把未命中者交给 wizard；`wizard = default_wizard` 引用 `lua/snort_defaults.lua` 中 `default_wizard` 的 `spells`、`hexes`、`curses` 三组启发式规则（例如 `spells` 里 `{ service = 'http', proto = 'tcp', to_server = http_methods, to_client = { 'HTTP/' } }`）。源码侧对应 `src/network_inspectors/binder/` 的 `binder.cc`、`bind_module.cc`、`binding.cc`，`src/service_inspectors/wizard/` 的 `wizard.cc`、`wiz_module.cc`、`spells.cc`、`magic.cc`、`hexes.cc`、`curse_book.cc`，以及 `src/network_inspectors/appid/`。流重组与协议解析由 `src/stream/`（`stream.cc`、`stream_splitter.cc`、`paf.cc`、`flush_bucket.cc` 与 `tcp/`、`udp/`、`ip/`、`base/` 等子目录）、`src/flow/`（`flow.cc`、`flow_key.cc`、`flow_cache.cc`、`flow_control.cc`、`session.h`）与 `src/service_inspectors/`（`http_inspect/`、`http2_inspect/`、`ssl/`、`dns/`、`ftp_telnet/` 等）承担。加密流量载荷不可见，可用的是握手元数据与证书信息（字段名需对照实际版本核验），应用识别依赖 inspector / binder / wizard，不能宣称读到 HTTPS 明文正文（原理见 06-04、06-05、06-10，模块见 07-02、07-03、07-04、07-10）。

第四段是检测。`src/detection/` 下已核验存在 `detect.cc`、`detection_engine.cc`、`detection_module.cc`、`detection_options.cc`、`fp_detect.cc`、`fp_create.cc`、`fp_config.cc`、`fp_utils.cc`、`pcrm.cc`、`pattern_match_data.h`、`ips_context.cc`、`ips_context_chain.cc`、`context_switcher.cc`、`regex_offload.cc` 等；`detection_engine.cc` 中已核验的函数包括 `DetectionEngine::thread_init()`、`thread_term()`、`DetectionEngine::init()`、`DetectionEngine::reset()`、`DetectionEngine::get_context()`、`DetectionEngine::get_event_queue()`（返回 `SF_EVENTQ*`）、`DetectionEngine::get_current_packet()`、`DetectionEngine::finish_inspect(Packet*, bool)`、`DetectionEngine::finish_packet(Packet*, bool)`、`DetectionEngine::offload(Packet*)`、`DetectionEngine::do_offload(Packet*)`、`DetectionEngine::set_file_data()` / `get_file_data()`。快速模式与多模式搜索由 `src/framework/mpse.cc/.h`、`src/search_engines/`（`hyperscan.cc`、`ac_bnfa.cc`、`ac_full.cc`、`acsmx2.cc`、`bnfa_search.cc`、`search_engines.cc`）与 `src/managers/mpse_manager.cc` 支撑。这里仍要写清：Hyperscan 是可选 search_engine 加速（`CMakeLists.txt` 以 `HAVE_HYPERSCAN` 打印开关状态、`config.cmake.h.in` 有 `#cmakedefine HAVE_HYPERSCAN 1`），缺失时回退 AC / BNFA 等其他实现，不是必需依赖、也不是唯一实现（原理见 06-06、06-07、06-08，模块见 07-05、07-06）。

第五段是动作与输出。`src/actions/` 下已核验 `act_alert.cc`、`act_drop.cc`、`act_block.cc`、`act_reject.cc`、`act_pass.cc`、`act_replace.cc`、`act_react.cc`、`act_log.cc`、`act_file_id.cc`、`actions_module.cc`、`ips_actions.cc`；`src/loggers/` 下已核验 `alert_json.cc`、`alert_fast.cc`、`alert_full.cc`、`alert_csv.cc`、`alert_syslog.cc`、`alert_unixsock.cc`、`alert_luajit.cc`、`alert_talos.cc`、`unified2.cc`、`log_pcap.cc`、`log_hext.cc`、`log_codecs.cc`、`loggers.cc`；事件队列在 `src/events/event.cc`、`event_queue.cc`、`sfeventq.cc`。内联模式下 drop / block / reject 通过 DAQ verdict 反馈（`src/packet_io/active.cc`、`src/packet_io/sfdaq.cc`、`src/actions/`），Snort 本身不是防火墙、不做 IP 转发、不做路由；IDS 旁路只告警不丢弃（原理见 06-09、06-11、06-12，模块见 07-08）。

贯穿轴是配置与插件抽象：`lua/snort.lua` 的八段结构经 `src/lua/lua.cc`、`src/parser/parse_conf.cc`、`src/main/snort_config.cc` 落到配置上下文，再由 `src/managers/` 下的 `inspector_manager.cc`、`module_manager.cc`、`ips_manager.cc`、`action_manager.cc`、`plugin_manager.cc`、`mpse_manager.cc`、`script_manager.cc`、`codec_manager.cc`、`event_manager.cc`、`so_manager.cc` 等按 `src/framework/base_api.h` 的 `struct BaseApi` 与 `enum PlugType` 装配插件。统一交叉引用写法为（字段见 05-02 ｜ 参数见 04-02 ｜ 原理见 06-01 ｜ 模块见 07-01）。

### 3. 关键数据结构与源码位置

按总览册约束，本节只点名结构、给真实路径、把逐字段定义交给 05 册。包与解码层有 `Packet`（`src/protocols/packet.cc/.h`）、`DecodeData`（`src/framework/decode_data.h`）、`Layer`（`src/protocols/layer.cc/.h`，字段见 05-02）；流与会话层有 `Flow` / `FlowKey`（`src/flow/flow.cc/.h`、`flow_key.cc/.h`，字段见 05-02、05-09）；配置层有 `SnortConfig`（`src/main/snort_config.cc/.h`，字段见 05-03）与 `Value` / `Parameter`（`src/framework/value.cc/.h`、`parameter.cc/.h`）；插件抽象层有 `Inspector` / `Module` / `Codec` / `Logger` / `IpsOption` / `IpsAction` / `Cursor`（`src/framework/`，字段见 05-04、05-05）；检测层有 `DetectionEngine` / `IpsContext` / `Cursor` / `PatternMatchData` / `Mpse`（`src/detection/`、`src/framework/mpse.cc`、`src/detection/pattern_match_data.h`，字段见 05-05、05-06）；DAQ 侧 `src/packet_io/sfdaq.cc` 的函数签名中出现了 `DAQ_Verdict`、`DAQ_PktHdr_t`、`DAQ_Stats_t`、`DAQ_Msg_h` 等类型（字段见 05-07）；输出侧有 `Event` 与事件队列（`src/events/event.cc/.h`、`event_queue.cc/.h`、`sfeventq.cc/.h`，字段见 05-08）。以上一律不展开字段表，也不列 API 全集。

### 4. 关键流程与调用链

启动与装配链与 01-01 一致但视角不同：`src/main.cc` 的 `main()` 调 `Snort::setup(argc, argv)`（`src/main/snort.cc` 中还有 `Snort::init()`、`Snort::term()`、`Snort::drop_privileges()`、`Snort::get_reload_config()`），配置经 `src/lua/lua.cc`、`src/parser/parse_conf.cc` 加载为 `SnortConfig`，`src/managers/` 依据 `src/framework/module.h` 的 `begin(const char*, int, SnortConfig*)` 与 `get_parameters()` 逐模块实例化插件；随后 `snort_main()` 取 `max_pigs = ThreadConfig::get_instance_max()`，`Pig::prep()` 里 `new SFDAQInstance(...)` → `SFDAQ::init_instance(...)` → `new Analyzer(...)`，`Pig::start()` 用 `std::thread` 拉起包处理线程，`main_loop()` 负责状态编排与命令分发（`main_broadcast_command()`、`main_reload_config()`、`main_reload_daq()`、`main_dump_stats()` 等）。线程 / 进程模型与资源隔离以实际版本为准，`src/main/analyzer.cc`、`swapper.cc`、`process.cc`、`numa.cc` 的实现需对照实际版本核验，本册不断言「默认 N 线程」（原理见 06-13，模块见 07-12）。

包处理链在本册只描述数据流向：DAQ3 把 message 交给解码层生成 `Packet` → 解码结果驱动 binder / wizard 把流绑定到具体 inspector → stream 重组向 service inspector 供给重组缓冲 → `DetectionEngine` 在各缓冲上跑 fast pattern 与 option 链 eval → 命中后由 `src/actions/` 决定 alert / drop / pass → `src/loggers/` 写出事件 → 内联模式下再经 `src/packet_io/active.cc` 与 `SFDAQ::verdict_to_string(DAQ_Verdict)` 把裁定回传 DAQ。逐段机制分别见 06-02（DAQ3 与 verdict）、06-03（解码与 normalize）、06-04（binder / wizard）、06-05（流重组）、06-06（规则编译）、06-07（MPSE / Hyperscan）、06-08（检测 eval）、06-09（动作限速）、06-11（输出管线）、06-12（内联）；本册一律只给「做什么」。配置自检 `snort -T` 命中 `src/main.cc` 的 `just_validate()` 分支后打印 `Snort successfully validated the configuration (with %u warnings).` 并置 `RUN_FLAG__TEST`，是验证整条装配链能否闭合的第一道关口（完整命令见 04-07）。

### 5. 配置/命令/代码实例

先看 `lua/snort.lua` 中 `binder` 段的写法，它直接体现了「配置如何决定绑定关系」。以下为该文件中该段开头的摘录：

```lua
binder =
{
    -- port bindings required for protocols without wizard support
    { when = { proto = 'udp', ports = '53', role='server' },  use = { type = 'dns' } },
    { when = { proto = 'tcp', ports = '53', role='server' },  use = { type = 'dns' } },
    { when = { proto = 'tcp', ports = '111', role='server' }, use = { type = 'rpc_decode' } },
```

每条记录由 `when`（匹配条件：`proto`、`ports`、`role`、`service`）与 `use`（`type` 指定目标 inspector）组成；注释写明这些是「protocols without wizard support」所需的端口绑定，段末的 `{ use = { type = 'wizard' } }` 把其余流量交给启发式识别。需要注意的是，`binder` 只决定「由谁解析」，并不解析报文内容本身；把绑定条目等同于解析能力，是阅读这段配置时最常见的误读（绑定与识别原理见 06-04，完整绑定参数见 04-04）。

下面这组「命令 + 输出 + 判读」用于验证整条链路能否在离线 pcap 上闭合。命令形态参考 `doc/user/overview.txt` 的 `snort -r a.pcap` 与 `lua/snort.lua` 注释中的 `-A <alert_type>`：

```bash
snort -c lua/snort.lua -r sample.pcap -A alert_json
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
示例输出，具体格式需对照实际版本核验
DAQ 输入：pcap read-file，报文计数 3
解码统计：eth / ipv4 / tcp 分层完成
绑定结果：wizard 命中 service=http，绑定 http_inspect
检测统计：fast pattern 命中 1，规则求值完成
输出：alert_json 写出 1 条事件
配置自检通过，进入报文处理，处理结束退出
```

逐行判读如下。第一行是「示例输出」声明，提示真实日志的字段顺序、计数口径与措辞随版本变化，必须以目标版本实际输出为准，不能把示例当作固定格式解析。第二行对应 `src/packet_io/sfdaq.cc` 与 `daqs/` 的读文件形态，`lua/inline.lua` 中 `name = 'pcap'`、`mode = 'read-file'` 正是这种输入；正常应为正整数报文计数，若为 0 要回头查 pcap 路径与 DAQ module 是否加载，而不是去改规则。第三行对应 `src/codecs/` 与 `src/protocols/packet.cc` 的解码，正常应看到链路层、网络层、传输层依次出现；若某层缺失或报解码异常，先确认封装（VLAN、隧道）是否在当前 codec 覆盖范围内。第四行对应 `src/network_inspectors/binder/` 与 `src/service_inspectors/wizard/`，正常应给出 `service` 与绑定的 inspector 名；加密流量只会有握手元数据与证书信息，不会出现明文 URI 之外的正文内容，字段名需对照实际版本核验。第五行对应 `src/detection/` 的 fast pattern 与 option 链求值，`src/search_engines/hyperscan.cc` 是否参与取决于构建期 `HAVE_HYPERSCAN`，缺失时回退 `ac_bnfa.cc` / `ac_full.cc` / `acsmx2.cc` / `bnfa_search.cc`，命中数为 0 不一定代表故障，要先确认规则集是否加载。第六行对应 `src/loggers/alert_json.cc`，正常应写出事件；若计数为 0，按「DAQ → 解码 → 绑定 → 检测 → 输出」倒序排查，事件字段见 05-08。最后一行说明进程完成自检与处理后退出，离线读 pcap 不产生常驻监听。任何吞吐、延迟、内存类结论都需在目标机型实测，本示例不提供绝对值。

### 6. 注意事项、陷阱与最佳实践

第一，别按大纲惯用名找目录：本快照无独立 `src/decode/`，解码在 `src/codecs/` 与 `src/protocols/packet.cc`；无独立 `src/session/`，会话在 `src/flow/session.h` 与 `src/stream/`，均需对照实际版本核验。第二，别把流水线当成「固定单线程、固定顺序」的执行脚本：`src/main.cc` 的 `Pig` / `std::thread` 与 `src/main/analyzer.cc`、`numa.cc` 表明存在多包处理线程编排，具体数量与绑核以实际版本为准，需对照实际版本核验，本册不断言「默认 N 线程」，吞吐一律需在目标机型实测（原理见 06-13）。第三，别把 DAQ 写成内置抓包：`snort.pc.in` 的 `cpp_opts=DAQ LUAJIT`、`src/packet_io/sfdaq*.cc` 与 `daqs/` 都说明抓包依赖独立 libdaq / DAQ3，module 决定抓包与内联能力（原理见 06-02）。

第四，别把内联 drop 理解成「Snort 自己丢包」：drop / block / reject 经 `src/packet_io/active.cc` 与 DAQ verdict 反馈，Snort 不是防火墙、不做 IP 转发、不做路由；IDS 旁路只告警不丢弃（原理见 06-12）。第五，别宣称能读 HTTPS 明文正文：加密载荷不可见，仅握手元数据与证书信息可用，字段名需对照实际版本核验，应用识别靠 inspector / binder / wizard（原理见 06-04、06-10）。第六，别把 Hyperscan 当必需或唯一：`CMakeLists.txt` 的 `HAVE_HYPERSCAN` 与 `config.cmake.h.in` 的编译期宏只是开关，`src/search_engines/` 内 AC / BNFA 回退实现齐备（原理见 06-07，构建选项见 04-01）。第七，别把 `alert_json` 的事件字段当成跨版本固定格式：字段名与取值需对照实际版本核验（`src/loggers/alert_json.cc`、`src/events/`；字段见 05-08）。第八，别把 memcap、重组深度之类容量值当通用数字，一律需在目标机型实测（调优见 08-02）。

最佳实践是「按层排障、逐层确认」：先用 `snort -V`、`snort --help`、`snort --help-module mod` 摸清当前版本能力面（完整命令见 04-07），再用 `snort -c lua/snort.lua -T` 确认配置与规则能编译；接流量后按「DAQ 计数 → 解码统计 → 绑定结果 → 检测命中 → 输出事件」五段核对，哪一段计数异常就停在哪一段的源码目录里查，不要一上来就改规则集。分层图（图 01-03-01）与启动链图（图 01-03-02）正好提供两张定位地图：数据面问题查前者，控制面与装配问题查后者。涉及性能瓶颈时，以 08-01 的基准方法在目标机型实测后再决定调哪一层，不凭印象下结论。

### 7. 小结与延伸阅读

本篇把 Snort 3 的全链路压缩为五段加一轴：DAQ3 收包（`src/packet_io/sfdaq*.cc`）→ 解码与 normalize（`src/codecs/`、`src/protocols/packet.cc`）→ binder / wizard 绑定与 inspector 解析（`src/network_inspectors/binder/`、`src/service_inspectors/wizard/`、`src/stream/`）→ detection 求值（`src/detection/detection_engine.cc`、`src/search_engines/`）→ actions 与 loggers（`src/actions/`、`src/loggers/`、`src/events/`）；贯穿轴是 `lua/snort.lua` 配置、`src/main/snort_config.cc` 上下文、`src/managers/` 装配与 `src/framework/base_api.h` 的插件抽象。两张图分别给出数据面与控制面地图，配合 01-01 的能力边界、01-02 的引擎对比，构成本册的完整总览。

### 4. 关键流程与调用链

资料层的第一条流程是「事实核验」。接到一个字段名、函数签名、Lua 键、命令行选项或 DAQ module 名时，先查规范 0.1 节的必查文件表定位目录，再用 Read / Grep 打开对应源码：能核实则按原文写，不能核实则写「需对照实际版本核验」并给出可定位目录（例如 `src/packet_io/`、`lua/snort.lua`、`CMakeLists.txt`、`src/search_engines/`）。本套四篇中所有具体函数名——如 `Snort::setup()`、`SFDAQ::init_instance()`、`DetectionEngine::get_event_queue()`、`parse_rule_close()`、`Module::begin()`——都来自这一流程；所有未核实项，如在线 DAQ module 名、Talos 规则获取工具形态、`tools/u2boat/` 与 `tools/u2spewfoo/` 是否存在、线程默认数量，均以标注收束，不补值、不猜测。

第二条流程是「版本核验」。`CMakeLists.txt` 里的版本变量 → `config.cmake.h.in` 的 `#define VERSION` → `snort.pc.in` 的 `Version: @VERSION@` → 运行期 `snort -V`，构成一条从源码到二进制的核验链；`ChangeLog.md` 与 `README.md` 提供叙述性佐证。这条链只用于回答「当前二进制对应哪份源码」，不用于给本套资料编版本号，也不用于推断能力边界——能力边界一律以源码目录与 01-01 的能力矩阵为准。第三条流程是「许可核验」：`COPYING` / `LICENSE` → 源码文件头注释 → 规则集单独核对（`lua/talos.lua`、`lua/sensitive_data.rules`、`lua/file_magic.rules`），三者结论不同，必须分开写。

第四条流程是「构建与资料生成」的最小链路，用于说明 `doc/` 与 `tools/` 为什么属于生态而非引擎本体：`./configure_cmake.sh --prefix=...` 收集选项 → `cmake` 生成构建文件 → `make` 编译 → 在 `ENABLE_UNIT_TESTS` 打开时 `ctest` 跑单测 → `make install` 落位。`CMakeLists.txt` 通过 `add_subdirectory (src)`、`add_subdirectory (tools)`、`add_subdirectory (lua)`、`add_subdirectory (daqs)` 组织子目录，并以 `if ( MAKE_DOC ) add_subdirectory (doc)` 控制文档构建；`config.cmake.h.in` 由 `configure_file` 生成 `config.h`。完整构建流程与变体见 02-02、02-03，全部 CMake 选项见 04-01，本册不展开。本套资料的权威源分层与交叉引用关系见图 01-04-01。

去重规则落到写作动作上，可以拆成几句可执行的判据。写到一个结构体时，只点名并给路径，随后跟「（字段见 05-xx）」，不列成员表；写到一个可调项或命令时，只给本场景最小必要片段，随后跟「完整参数见 04-xx」，不重列选项全集；写到一段机制时，只说「做什么」，随后跟「原理见 06-xx」，不展开状态机与调用顺序；写到一个目录时，只说它负责哪类能力，随后跟「模块见 07-xx」，不罗列 API；写到运维步骤与基准数字时，交给 08 册，其余册不展开。01 册作为总览册，正是这套判据的集中演练场：四篇里出现的 `Packet`、`SnortConfig`、`BaseApi`、`DAQ_Verdict`、`Event` 等名字都只带路径与「字段见 05-xx」，没有一处展开字段表；出现的 `HOME_NET`、`stream = { }`、`ips.variables`、`--help-module`、`-T` 等只作定位用途，完整清单留在 04 册。读者若发现某篇疑似越界，可以按这张图反查它该归到哪个权威源，再用交叉引用回去读原文，而不必依赖总览册的转述。总览册的价值在于给地图与边界，不在于替手册保存全部细节；把这条界线守住，65 篇才不会互相重复、也不会互相矛盾。

### 5. 配置/命令/代码实例

下面这组「命令 + 输出 + 判读」用于演示版本与能力面的核验入口，也是每篇落笔前的第一组检查。命令形态需对照实际版本核验，以下为参考写法：

```bash
snort -V
snort --help
grep -n "VERSION_MAJOR" CMakeLists.txt
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
示例输出，具体格式需对照实际版本核验
Snort++ 版本信息：由构建期变量注入，需对照实际版本核验
命令行帮助：列出 -c / -r / -i / -T / -V / --help 等类别
CMakeLists.txt 命中：VERSION_MAJOR / VERSION_MINOR / VERSION_PATCH
config.cmake.h.in 命中：VERSION 与 HAVE_HYPERSCAN 等宏
snort.pc.in 命中：cpp_opts=DAQ LUAJIT
```

逐行判读如下。第一行是「示例输出」声明，提示版本信息、帮助文本与 grep 结果的排版随版本变化，不能当作固定格式解析，更不能把其中的数值抄成本套资料的版本号。第二行对应 `snort -V`：它回答「当前二进制由哪份构建产生」，正常应给出版本与构建描述；若命令不存在或报动态库缺失，先查安装与 `LD_LIBRARY_PATH`，不要据此推断引擎能力。第三行对应 `snort --help`：`doc/user/overview.txt` 把它列为 First Steps，输出会列出 `-c`、`-r`、`-i`、`-T`、`-V`、`--help` 等类别，正常应能查到配置、输入与自检三类入口；具体选项清单需对照实际版本核验（`src/parser/cmd_line.cc`、`src/main/help.cc`；完整命令见 04-07）。第四行是 `grep` 命中 `CMakeLists.txt` 的版本变量族，作用只是确认「版本字样确实来自构建期变量」，变量取值不写进正文；`config.cmake.h.in` 的 `VERSION` 与 `HAVE_HYPERSCAN` 同理，后者还提示 Hyperscan 是可选开关、不是必需依赖。第五行 `snort.pc.in` 命中 `cpp_opts=DAQ LUAJIT`，是「抓包依赖独立 libdaq / DAQ3、配置依赖 LuaJIT」的元数据佐证；若该行为空或缺少 `DAQ`，应回头核对依赖安装（依赖矩阵见 02-01，完整选项见 04-01）。整个检查不接流量、不改配置，属于零副作用的前置核验。

再看 `lua/talos.lua` 开头的摘录，它用于说明「规则 / tweaks 与引擎许可必须分开看」：

```lua
-- talos test tweaks
-- use with --talos or --tweaks talos
function file_exists(name)
    local f=io.open(name,'r')
    if f~=nil then
        io.close(f)
        return true
    else
        return false
    end
end
```

这段是 Lua 脚本而非引擎源码：`file_exists(name)` 用 `io.open` 判断 `local.rules` 是否存在，存在时由该文件设置 `ips.include`；`-- use with --talos or --tweaks talos` 说明它通过 tweaks 机制叠加到 `lua/snort.lua` 上（`lua/snort.lua` 末尾 `if ( tweaks ~= nil ) then include(tweaks .. '.lua') end`）。它是一个好的观察样本：引擎按 GPLv2 授权（`COPYING` / `LICENSE`），而 Talos 规则集有独立许可约束，二者不能混为一谈；`lua/sensitive_data.rules`、`lua/file_magic.rules` 同理。任何「把规则集与引擎按同一许可打包分发」的做法都需单独做合规审查，本套资料不作法律解释。

### 6. 注意事项、陷阱与最佳实践

第一，别抄版本号。`CMakeLists.txt`、`README.md`、`doc/user/overview.txt` 中出现的版本字样只作核验依据，本套资料统一写「上游 master 快照（2026-11 抓取）」，具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准并标注「需对照实际版本核验」。第二，别断言「默认 N 线程」：线程 / 进程模型与资源隔离以实际版本为准（`src/main/analyzer.cc`、`process.cc`、`numa.cc`、`swapper.cc`），需对照实际版本核验。第三，别把 Talos 规则写成与引擎同许可、可任意分发：`lua/talos.lua`、`lua/sensitive_data.rules` 与相关规则文件受独立许可约束，规则获取工具形态需对照实际版本核验。第四，别把大纲里的路径当既成事实：`src/decode`、`src/session` 为惯用名，本快照无独立同名目录；`tools/u2boat/`、`tools/u2spewfoo/` 在本快照 `tools/` 下未核验到，需对照实际版本核验；`ChangeLog` 的实际扩展名为 `ChangeLog.md`、`README` 为 `README.md`，以实际目录为准。

第五，别给绝对性能数字：吞吐、pps、丢包率、内存占用、线程数带来的收益一律需在目标机型实测（基准方法见 08-01，调优见 08-02）。第六，别把 `tools/snort2lua/` 当一键迁移：它只做配置文本格式转换，配置与插件 ABI 均不兼容 Snort 2（详见 01-02）。第七，别把 Hyperscan 写成必需依赖：`CMakeLists.txt` 的 `HAVE_HYPERSCAN` 与 `config.cmake.h.in` 的编译期宏只是开关，`src/search_engines/` 具备 AC / BNFA 回退实现（原理见 06-07）。第八，别把引擎写成自带抓包、防火墙或能读加密明文：这三条属于 01-01 能力矩阵的硬边界，任何一篇都不得写反。

最佳实践可以归纳为「四个统一」。统一版本口径：全册只写基准快照，具体版本号一律标注核验。统一核验写法：不确定项写「需对照实际版本核验」并给 `upstream_src/snort3/snort3-master/` 下可定位路径，不补值、不编造。统一去重：04 守参数与命令、05 守结构体字段、06 守机制与调用链、07 守目录级模块能力、08 守运维与基准，其余册按（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）交叉引用，不重列字段表与 API 全集。统一图示与编号：图号用「文件号-篇号-两位序号」，图题、正文引用与 `.drawio` 文件同源；表格单元格控制在 90 字符内、单元格内竖线转义；代码块带语言标注、结束行用裸结束标记。涉及许可与规则集分发的动作，先做合规审查再上线（上线清单见 08-06）。

### 7. 小结与延伸阅读

本篇把四条口径固定下来：版本基准为「上游 master 快照（2026-11 抓取）」，具体版本号以 `CMakeLists.txt`、`ChangeLog.md` 为准且需对照实际版本核验；引擎按 `COPYING` / `LICENSE` 与源码头注释为 GPLv2，Talos 规则集有独立许可约束、不得混同；官方生态由 `doc/` 的 user / reference / devel / upgrade 四部分、`tools/snort2lua/` 与 `tools/show_flows/`、`daqs/`、`cmake/` 及顶层文件构成，事实锚点始终是 `upstream_src/snort3/snort3-master/`；资料使用上按「唯一权威源去重 + 四类交叉引用 + 需对照实际版本核验 + 性能实测 + 统一编号」执行。图 01-04-01 把 04 / 05 / 06 / 07 / 08 的权威源分层与总览册的引用关系画成一张图，可作为全册阅读的收尾索引。

延伸阅读建议：版本与构建读顶层 `CMakeLists.txt`、`config.cmake.h.in`、`snort.pc.in`、`ChangeLog.md`、`doc/reference/building.txt`；许可读 `COPYING`、`LICENSE` 与 `src/main.cc` 文件头；迁移与差异读 `doc/upgrade/differences.txt`、`doc/upgrade/overview.txt`、`doc/upgrade/snort2lua.txt`；用法与概念读 `doc/user/usage.txt`、`doc/user/overview.txt`、`doc/user/concepts.txt`；扩展开发读 `doc/devel/extending.txt`。本册四篇应连起来读：01-01 给能力边界，01-02 给引擎对比，01-03 给全链路架构，01-04 给版本、许可与资料约定。跨册随查统一按（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-12）执行；凡本篇标注「需对照实际版本核验」的版本字样、DAQ module 名、工具路径、线程数与容量值，均以对应源码文件为准，本套资料不编造未经核验的路径与取值，性能与容量结论一律需在目标机型实测。
