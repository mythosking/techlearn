> 本册是整套资料的概述层，负责建立关于 DPDK 的整体心智模型：它究竟解决什么问题、与相邻技术怎样分工、源码如何分层、版本与社区怎样运作。落到具体细节时，参数全集、结构体逐字段定义、机制与调用链、库与驱动模块功能分别由 04、05、06、07 各册作为唯一权威源展开，本册只做点名、给出真实源码路径并交叉引用，不重列命令清单与字段表，以免口径冲突。版本基准为 DPDK 23.11 LTS、24.11 与 master 开发主线。

## 01-01 DPDK 是什么：用户态高速数据包处理框架概览

### 1. 背景与动机

理解 DPDK 的出发点，是理解通用操作系统网络协议栈在高速链路下暴露出的结构性开销。以万兆以太网为例，在 64 字节小包、线速收发的情况下，包到达速率约为 14.88 Mpps，平均到每个报文身上只有约 67 纳秒的处理预算；当链路提升到 25G、100G 乃至更高速率时，单包预算会被进一步压缩到十几纳秒乃至几纳秒。在这段极其有限的时间里，传统路径需要依次经历硬中断触发、软中断调度、内核协议栈逐层解析、套接字缓冲区分配、内核态到用户态的上下文切换以及一次甚至多次内存拷贝，同时还要承担自旋锁竞争、缓存行在多个处理器核之间反复失效、页表项与 TLB 未命中等隐性代价。任何一个环节多花几十纳秒，整条流水线在突发流量下就会开始排队，进而触发丢包与重传，吞吐与时延都变得不可预测。

这些开销并不是某一处代码写得不好，而是通用性设计为兼容海量场景付出的必然代价。内核协议栈要同时服务阻塞式与非阻塞式套接字、复杂的路由与邻居子系统、状态防火墙、连接跟踪、TCP 拥塞控制、多进程公平调度以及 tcpdump 之类的丰富观测工具生态，因此必须保留中断驱动、严格的分层抽象、通用的 skb 元数据结构和细粒度的锁保护。可是对于「从某个端口把包收进来、按一张规则表查一下、再从另一个端口发出去」这类转发型负载来说，这套机制里有相当一部分能力自始至终都不会被用到，却要在每个包上照常支付成本。换一个角度看，问题并不在于内核慢，而在于把专用数据面强行塞进为通用性优化的执行框架里，二者的优化目标本身就是错位的。

DPDK（Data Plane Development Kit，数据平面开发套件）正是针对这一矛盾给出的系统性答案。它把网卡驱动从内核态搬到用户态，用持续轮询取代中断通知，用预先分配的大页内存与定长对象池消除频繁分配与地址翻译，用一次处理一批报文的批量接口把每次函数调用的固定成本摊薄到几十个包上，并用每逻辑核独占的数据结构与无锁环形队列消除跨核同步。它并不试图替代内核协议栈去跑完整的 TCP 连接，而是为网关、防火墙、负载均衡器、虚拟交换机、抓包探针、网络功能虚拟化网元等专用数据面提供一套行为可预测、吞吐可逼近网卡线速的用户态基础设施。项目最初由 Intel 发起并开源，后来转入 Linux Foundation 托管，逐步演化为高性能用户态网络编程领域事实上的标准底座。

需要在一开始就明确本套资料的版本口径。全册以 DPDK 23.11 LTS、24.11 以及 master 开发主线为叙述基准，但发布节奏、精确版本号、头文件所在目录以及若干接口签名都可能随版本调整。凡涉及具体版本号、函数签名、EAL 参数写法、testpmd 命令与工具输出格式之处，都应当以实际使用的源码树与 dpdk.org 官方发布页为准，写作中统一标注「需对照实际版本核验」并给出可定位的源码目录或头文件路径，绝不以推测代替事实。这一点在概述层尤其重要，因为后面各册会在此基础上逐层展开，若概述层埋下想当然的说法，后续引用会把偏差一路放大。

### 2. 核心概念

所谓「用户态高速数据包处理框架」，可以拆成几个互相咬合的核心概念。第一个是内核旁路（kernel bypass）：网卡收到报文后不再进入内核网络协议栈，而是由用户态驱动直接把描述符环里的报文取走，控制权始终留在应用程序手里。第二个是轮询模式驱动（Poll Mode Driver，PMD）：与「网卡来包才打断 CPU」的中断模型相反，PMD 让一组逻辑核在死循环里不断检查接收队列，只要队列里就有包立刻取走处理，没有包也保持自旋。这样做看似浪费 CPU，却换掉了中断、调度与上下文切换的全部不确定延迟，也把每个包的处理节奏完全交给应用掌控，代价是这些核会被长期占满。第三个是环境抽象层（Environment Abstraction Layer，EAL）：它把「预留大页、探测 PCI 设备、把线程钉到指定核、建立跨进程共享内存、统一日志与时钟」这些和操作系统、硬件拓扑强相关的脏活集中起来，向上提供一套与具体平台无关的初始化入口，源码集中在 `lib/eal/` 目录，其初始化主流程的原理见 06-01。

在此之上还有一组描述运行时模型的概念。逻辑核（lcore）是 DPDK 对「一个被绑定、被独占、参与数据面处理的线程」的抽象，应用通过 lcore 编号来编排收发与转发任务；大页（hugepage）是用 2 MB 或 1 GB 页替代默认 4 KB 页来承载报文池，显著减少 TLB 缺失并提高 DMA 地址翻译效率；`rte_mbuf` 是贯穿全数据面的报文缓冲区对象，`rte_mempool` 是预分配这些对象的定长内存池，`rte_ring` 是连接各处理阶段的无锁队列；burst（批量）指 `rte_eth_rx_burst` / `rte_eth_tx_burst` 一次调用收发一组报文而非一个，把函数调用、内存屏障与 PCIe 事务的固定开销摊薄；run-to-completion（运行到完成）则是典型的编程范式，一个 lcore 从收包、查表、改包到发包一路做完再取下一批，尽量避免阶段间交接与缓存失效。这些对象之间的关系、生命周期与字段含义分别由 05 册（字段见 05-02、05-03、05-06）与 06 册（原理见 06-03、06-04）承接，本册只建立名字与分工。

从吞吐目标看，DPDK 追求的是线速转发能力：在足够多的 lcore、正确的 NUMA 亲和以及充足的大页条件下，让 64 字节小包也能接近端口理论包速率，且把尾时延控制在一个稳定区间。它擅长的是「单位时间内处理多少个包」，而不是「一条连接能跑多复杂的协议」。这也决定了它的典型用户是需要自己实现或裁剪协议栈的转发类系统，而不是通用的 Web 服务器。理清这一点，后面阅读 01-02 的架构对比时就不会被「谁更快」这种笼统问题带偏，而会去问「在哪条数据路径上、以什么内存模型、面向哪类负载更快」。

### 3. 关键数据结构与源码位置

概述层对数据结构采取「点名、定位、交出去」的处理方式：只给出对象名、它所在的真实源码目录、以及后续字段字典的篇号，绝不在此展开逐字段表格。这样做的目的是让读者先建立全局地图，等到真正要读某个结构体的内存布局时再回查 05 册，避免在尚未理解分层之前就陷进字段细节。DPDK 源码树顶层大致分为 `lib/`（核心库）、`drivers/`（各类轮询驱动，其中网卡 PMD 在 `drivers/net/`）、`app/`（参考应用，如 testpmd）、`examples/`（入门与演示程序）、`usertools/`（设备绑定等辅助脚本）、`config/` 与 `buildtools/`（构建期配置与工具）、`doc/`（官方文档）。

与数据面最相关的一组结构可以这样定位：报文缓冲对象 `rte_mbuf` 位于 `lib/mbuf/`，头文件可按 `lib/mbuf/rte_mbuf.h` 检索（字段见 05-02）；对象池 `rte_mempool` 及其缓存、内存头位于 `lib/mempool/`（字段见 05-03）；以太网设备抽象 `rte_eth_dev` 与相关配置结构位于 `lib/ethdev/`（字段见 05-04）；无锁队列 `rte_ring` 位于 `lib/ring/`（字段见 05-06）；大页内存段 `rte_memseg`、`rte_memseg_list` 与 `rte_memzone` 位于 `lib/eal/`（字段见 05-07）；流规则相关结构位于 `lib/ethdev/rte_flow.h`（字段见 05-08）。这些头文件在不同版本里可能调整目录层级，精确路径需对照实际版本核验，但 `lib/` 下按库名分目录这一组织方式在 23.11 LTS 与 24.11 之间是稳定的。

### 4. 关键流程与调用链

一个最小的 DPDK 应用从零到跑起来，大致会走这样一条链：系统启动阶段预留大页并把目标网卡从内核驱动解绑、绑定到 vfio-pci 或 uio 类用户态驱动；应用进入 `main` 后首先调用 `rte_eal_init`（`lib/eal/`）完成大页映射、lcore 线程拉起、PCI 设备扫描与日志时钟初始化；随后创建 `rte_mempool` 作为报文池、通过 `lib/ethdev/` 的配置接口设置端口与收发队列、启动端口；最后在每个 lcore 上进入主循环，反复调用 `rte_eth_rx_burst` 批量取包、按业务逻辑处理、再调用 `rte_eth_tx_burst` 批量发出，处理完的 mbuf 归还内存池。这条链的每一段在 06 册都会拆成逐帧级别的函数调用与内存序分析（原理见 06-01、06-03、06-04），本册只给出骨架，不展开内部实现。

从这条链可以看出 DPDK 性能模型的两个要点。其一，所有昂贵的准备工作——大页预留、设备探测、队列与内存池建立——都集中在初始化阶段一次性完成，热路径上只剩「取一批、处理一批、发一批、还一批」这几个动作，几乎不涉及动态内存分配与系统调用。其二，热路径是围绕 lcore 严格串行的：一个核上的数据结构尽量独占，跨核通信才借助 `rte_ring` 这样的无锁结构，从而把锁冲突和缓存一致性流量压到最低。至于描述符环怎样回填、DD 状态位怎样判定、DMA 与内存屏障在哪里配对，这些机制细节统一交给 06 册（原理见 06-04、06-05），概述层只需知道「批量」与「旁路」是贯穿始终的两条主线。

下面给出示例输出，具体格式需对照实际版本核验。

```text
EAL: Detected 8 lcore(s)
EAL: Detected 1 NUMA node(s)
EAL: Multi-process socket /var/run/dpdk/rte/mp_socket
EAL: Selected IOVA mode 'VA'
hello from core 1
hello from core 0
TELEMETRY: No legacy callbacks, legacy socket not created
```

对上面这段输出逐行判读如下。`EAL: Detected 8 lcore(s)` 表示 EAL 探测到当前进程可见的可用逻辑核数量，正常值应当大于或等于 `-l` 参数指定的核数；若该值为 0 或明显小于物理核数，通常是容器 cpuset 配额、进程亲和性掩码或 `isolcpus` 隔离参数把 CPU 藏起来了。`EAL: Detected 1 NUMA node(s)` 表示 NUMA 节点数，它直接决定 `--socket-mem` 该按几个 socket 分配内存，双路服务器正常应显示 2，显示 1 往往意味着 BIOS 关闭了 NUMA 或跑在虚拟机里。`Multi-process socket` 一行给出 primary 与 secondary 进程通信所用的 UNIX 域套接字路径，多实例共存时必须靠 `--file-prefix` 把路径隔开，否则第二个进程会因抢占同名 socket 而失败。`Selected IOVA mode 'VA'` 说明 IO 虚拟地址选择了 VA 模式，当 IOMMU 不可用或配置受限时可能回退到 PA 模式，这一行是排查设备探测失败的重要线索。最后两行 `hello from core X` 由各远程 lcore 打印，正常应覆盖 `-l` 指定的全部核；若只出现一行，说明远程启动未成功。异常特征方面，任何以 `EAL: Error` 开头、`Cannot init memory` 或 `No free hugepages` 字样的输出都指向大页预留不足，应回到 03-02 核验 `/proc/meminfo`，而不是反复改应用参数。以上输出为示例，具体格式需对照实际版本核验。

### 6. 注意事项、陷阱与最佳实践

第一类是环境类陷阱。最容易踩的是「应用写对了但根本没跑起来」：大页没预留、网卡还绑在内核驱动上、IOMMU 未开启、当前用户没有访问 vfio 设备节点的权限，这四类问题占初次部署失败的绝大多数。最佳实践是严格按 03 册的顺序做前置检查——先 `numactl -H` 看清拓扑，再核验 `/proc/meminfo` 的大页数量，再用设备绑定脚本确认目标 PCI 地址已经处于用户态驱动之下，最后才启动应用。不要在尚未确认大页与绑卡状态的情况下反复调整 EAL 参数，那只会把环境问题和参数问题混在一起，增加定位难度。

第二类是资源与拓扑类陷阱。轮询模型会长期占满 lcore，因此务必把这些核从内核调度器里隔离出来，并与网卡所在的 NUMA socket 对齐，否则跨 socket 访存带来的额外延迟会悄悄吃掉一部分吞吐收益。内存池大小也要按「端口数 × 队列数 × 描述符数 × 突发流量余量」估算，池子过小会在突发时表现为周期性丢包，池子过大则浪费大页这一稀缺资源。另一个常见误区是照搬示例程序的单核配置直接上多口生产环境，结果所有端口挤在一个 lcore 上形成瓶颈；正确做法是按端口与队列规模规划 lcore 分组，让每个核负责固定的收发队列，保持数据结构的核内局部性。

第三类是开发与调试类陷阱。DPDK 应用多数需要以较高权限运行，生产环境应通过能力收敛、设备组权限与容器设备白名单来降低攻击面，而不是长期以 root 直接跑。调试时建议保留符号表、开启适度日志级别，并优先使用 telemetry 与 procinfo 这类旁路观测手段，避免在生产热路径里插打印语句——一次控制台输出足以让小包吞吐出现明显抖动。还有一点容易被忽略：DPDK 版本升级可能带来 ABI 与 API 调整，跨版本迁移时务必对照 08-05 的回归清单核验构建选项与废弃接口，不要假设旧二进制可以直接替换新库。

最后是一条方法论层面的最佳实践：把「可观测」当作功能的一部分。上线前就应当明确每端口收发包计数、每核轮询占用、内存池余量、丢包计数这几项指标的采集口径，出现性能回退时才能按「先环境、再拓扑、后代码」的顺序收敛。概述层之所以反复强调分层与唯一权威源，正是为了让这种收敛有章可循：遇到参数问题去 04，遇到字段问题去 05，遇到机制问题去 06，遇到模块问题去 07，遇到排障方法去 08，而不是在某一篇里堆满所有细节。

### 7. 小结与延伸阅读

本篇回答了「DPDK 是什么」：它是一套以用户态轮询、内核旁路、大页内存、批量收发和每核独占为核心手段的数据面开发框架，用确定性的热路径换取逼近线速的包处理能力，代价是把协议栈能力、CPU 占用与运维复杂度一并交还给应用开发者。它不替代内核协议栈，而是补上了通用协议栈在专用转发场景下力不从心的那一块。理解 EAL 管环境、PMD 管收发、`lib/` 管通用能力、`app/` 与 `examples/` 管消费，就掌握了后续所有章节的坐标系。

延伸阅读建议按主线推进：想先把环境跑通，读 02-02 的 meson 构建实战与 03 册的大页、绑卡、NUMA 配置；想查某个参数怎么用，直接回查 04-01；想弄清 `rte_mbuf`、mempool、ethdev 的字段布局，回查 05-02 至 05-04；想深入 `rte_eal_init` 与 PMD 收发调用链，读 06-01 与 06-04；想按模块了解库与驱动全貌，读 07-01。官方文档入口在源码树 `doc/` 目录与 dpdk.org 站点，精确的版本说明与发布信息需对照实际版本核验。下一篇 01-02 会把 DPDK 放到更大的技术版图里，与内核协议栈、OVS、VPP 与 RDMA 做逐维度对照。

## 01-02 DPDK 与内核协议栈 / OVS / VPP / RDMA 的架构对比

### 1. 背景与动机

只讲 DPDK 自身，很容易产生一种错觉：仿佛「用户态轮询」是所有网络性能问题的唯一答案。真实系统里，DPDK 几乎从不单独出现，它要么被拿来和内核协议栈做取舍，要么作为 OVS、VPP 这类用户态网络功能框架的底座，要么与 RDMA 这类同样宣称「内核旁路」的技术被放在一起比较。工程师在选型会上被问到的往往不是「DPDK 快不快」，而是「这一层转发到底该放在内核、放在 DPDK 应用、放在 OVS-DPDK、放在 VPP，还是干脆走 RDMA」。要回答这类问题，需要的不是零散的印象，而是一张覆盖数据路径、内存模型、编程接口与适用场景的统一对照表。

这几类技术之所以容易被混为一谈，是因为它们都在不同程度上绕开了传统套接字路径，但绕开的层次、绕开之后由谁接管、以及为此付出的编程代价完全不同。内核协议栈把报文留在内核态，用完整的 TCP/IP 能力换取通用性；DPDK 把网卡驱动搬到用户态，只提供最朴素的二层收发与一批库，把协议栈的实现责任交给应用；OVS 与 VPP 是构建在 DPDK 之上的「用户态网络功能框架」，前者以流表与虚拟交换语义见长，后者以图节点流水线与可编程转发见长；RDMA 则把数据搬运本身卸载到网卡硬件，用远端内存语义替代「收包再处理」的整条思路。把它们放在同一张表上，才能看清「谁负责搬运、谁负责决策、谁负责协议」这条分工线。

还有一层动机来自排障与沟通。生产环境里经常出现这样的对话：应用说收不到包，运维说网卡已经 up，开发怀疑是 DPDK 参数，最后发现设备还绑在内核驱动上，或者反过来——OVS-DPDK 已经接管了端口，另一个 DPDK 进程又去抢同一个 PCI 地址。这类冲突的根源，正是不同架构对「同一块网卡由谁独占」的默认假设不一致。先用七维对照把各自的数据路径画清楚，再谈部署与调优，能把大量跨团队的误解消灭在设计阶段。本篇的定位因此是「架构地图」：只讲分工与边界，具体命令、字段与机制仍分别交给 04、05、06、07 各册。

### 2. 核心概念

做对比之前，先统一七个维度的含义，避免各说各话。数据路径位置指报文从网卡到最终消费者之间经过哪些执行态与层次；收包驱动方式指靠中断、靠轮询还是靠硬件完成事件来驱动；内存模型与拷贝指缓冲区谁分配、在内核态还是用户态、是否发生数据拷贝；编程接口形态指开发者面对的是系统调用、C 库 API、流表与图节点，还是 verbs 语义；协议栈能力指该方案自带多少网络协议处理；吞吐与时延目标指它优化的是通用吞吐、小包线速、虚拟交换密度还是远端访问延迟；典型适用场景则把前面六项收敛到可落地的业务形态。这七个维度合起来，基本能刻画一个数据面架构的「性格」。

四类架构在这张地图上的位置可以这样概括。内核协议栈位于最内层，一切报文都要经过内核，接口是 socket，优势是协议完备、工具成熟、应用无需关心驱动，劣势是每个包都要交中断、锁与拷贝的税。DPDK 用户态 PMD 位于「旁路内核」一侧，接口是 `rte_` 前缀的 C API 加 EAL 参数，只把网卡收发与一批基础库交到用户手里，协议栈要自己写或自己接（模块见 07-01）。OVS 与 VPP 严格说并不是与 DPDK 对立的第四种驱动，而是「站在 DPDK 肩膀上的网络功能框架」：它们复用 PMD 的轮询与大页内存（原理见 06-04），在其上补齐流表、桥接、路由、隧道、ACL 等转发语义，因此常被称为 OVS-DPDK 与 VPP 的 DPDK 数据面。RDMA 则走得更远，它让网卡直接把数据写到预先注册的用户态内存区，CPU 几乎不参与搬运，接口是 libibverbs 的 verbs，语义是「读／写远端内存」而不是「收一个包再决定往哪发」。

读这张图要抓住两个要点。第一，OVS 与 VPP 并非另起炉灶，图中「构建于其上」与「依赖 PMD」两条边说明它们的数据面仍然由 DPDK 的 PMD 驱动，差异在于上层用流表还是用图节点来组织转发逻辑。第二，RDMA 与 DPDK 虽然都绕过内核，但绕法不同：DPDK 是「CPU 搬到用户态来搬包」，RDMA 是「让网卡替 CPU 搬数据」，因此二者面向的编程范式与业务场景几乎没有重叠。把这两点弄清楚，再用下面这张七维对照表逐项对齐，就不会把它们误读成「四个互相替代的选项」。七维架构对照关系见下表。

| 对比维度 | 内核协议栈 | DPDK 用户态 PMD | OVS / VPP（基于 DPDK） | RDMA |
|---|---|---|---|---|
| 数据路径位置 | 报文在内核态逐层解析与转发 | 完全旁路内核、用户态直驱网卡 | 用户态转发面、控制面可独立部署 | 旁路内核、由硬件完成远端搬运 |
| 收包驱动方式 | 硬中断加 NAPI 软中断 | PMD 持续轮询、常态无中断 | 多继承 PMD 轮询或事件驱动 | 完成队列、可轮询可事件通知 |
| 内存模型与拷贝 | skb 分配释放并伴随拷贝与切换 | 大页预分配、mbuf 全程零拷贝 | 复用 mbuf 与 mempool 池 | 注册内存区后网卡直接 DMA 到用户缓冲 |
| 编程接口形态 | socket 与 POSIX 系统调用 | rte_ 前缀 C API 加 EAL 参数 | OVS 流表或 VPP 图节点编排 | libibverbs 的 verbs 语义 |
| 协议栈能力 | 完整 TCP/IP 与丰富内核特性 | 仅提供二层收发、协议栈需自建 | 自带二三层转发与控制平面 | 侧重远端内存语义、非通用协议栈 |
| 吞吐与时延目标 | 通用场景、受中断与锁开销约束 | 面向线速与小包高吞吐低时延 | 面向虚拟交换与 NFV 服务链 | 极低时延高带宽并卸载 CPU |
| 典型适用场景 | 通用服务器与主机网络 | 网关、防火墙、探针与自研数据面 | 云网络、虚机交换与服务链 | HPC、分布式存储与远端内存访问 |

上表把「搬运—决策—协议」三条线拆开来看：内核协议栈把三件事都留在内核态完成，接口最省心但每个包交的税最重；DPDK 只负责把报文高效搬进搬出用户态，决策与协议完全交给应用；OVS 与 VPP 在同样的搬运底座上把决策层补齐，用流表或图节点换来对复杂组网的覆盖；RDMA 则连软件转发环都交给硬件，语义从「处理包」变成「访问远端内存」。读表时若只盯「吞吐与时延目标」一行容易得出片面的快慢结论，必须结合「协议栈能力」与「典型适用场景」两行一起判断，才能落到可落地的选型上。

### 3. 关键数据结构与源码位置

对比类篇章的数据结构点名，重点是说明「同一份报文在不同架构里由谁承载」。内核协议栈一侧，报文载体是内核的 skb 及其关联的网络设备与套接字结构，定义在内核源码树中，不在 DPDK 仓库内；DPDK 一侧，报文载体是 `rte_mbuf`（`lib/mbuf/rte_mbuf.h`，字段见 05-02），承载它的池是 `rte_mempool`（`lib/mempool/`，字段见 05-03），端口抽象是 `rte_eth_dev`（`lib/ethdev/`，字段见 05-04），阶段间队列常用 `rte_ring`（`lib/ring/`，字段见 05-06）。OVS-DPDK 与 VPP 在底层同样消费 `rte_mbuf`，区别是它们各自在用户态再包一层自己的报文元数据与转发上下文；RDMA 一侧则围绕注册内存区、队列对与完成队列组织，相关结构属于 verbs 与内核 RDMA 子系统，也不在 DPDK 源码树中。

源码定位上还有一条容易混淆的线索：DPDK 仓库里与「和别的系统集成」相关的目录，并不都叫集成层。`examples/` 里有大量演示如何与 virtio、vhost、IPsec 等配合的示例（模块见 07-10、07-07）；`drivers/net/` 下既有物理网卡 PMD，也有 virtio、memif、af_packet 等虚拟设备 PMD（模块见 07-11），这些正是 OVS-DPDK、VPP 与容器网络对接 DPDK 时常用的端口类型；`app/` 目录中的参考应用则展示了如何把上述库与驱动串成一个可运行进程。换句话说，DPDK 仓库本身只提供「零件」，OVS 与 VPP 是拿这些零件组装成的整机，它们的源码在各自的项目仓库里。凡涉及这些外部项目的精确结构体名与头文件路径，需对照对应项目与实际版本核验，本册不代为列举字段表。

把「报文载体」这一维度单独拎出来，是因为它直接决定了零拷贝是否成立：skb 在内核态分配，最终往往要拷进用户缓冲区；`rte_mbuf` 从一开始就在用户态大页内存里，DMA 直接填入，应用与驱动看到的是同一块内存，才谈得上零拷贝；RDMA 的注册内存区同样在用户态，但由网卡硬件直接读写，连「取描述符」这一步都省了。这三类载体的生命周期、引用计数与释放路径由 05 册与 06 册分别承接（字段见 05-02、原理见 06-03），概述层只需记住「载体在哪、谁分配、要不要拷」这三个问题。

### 4. 关键流程与调用链

把一次收包流程在四类架构里并排走一遍，差异会非常直观。内核协议栈路径是：网卡硬中断 → 软中断与 NAPI 轮询 → 驱动把 skb 入队 → 网络层与传输层逐层处理 → 套接字接收队列 → 应用通过 recv 类系统调用把数据拷到用户缓冲区。DPDK 路径是：应用启动时由 EAL 完成大页、lcore 与设备探测（原理见 06-01），PMD 把接收描述符环映射到用户态，主循环直接调用 `rte_eth_rx_burst`（`lib/ethdev/rte_ethdev.h`）批量取走已经由 DMA 填好的 `rte_mbuf`，处理完经 `rte_eth_tx_burst` 发出（原理见 06-04）。OVS-DPDK 与 VPP 路径在前半段与 DPDK 完全一致，差别发生在取到 mbuf 之后：前者按流表匹配执行动作，后者沿图节点流水线逐级处理，二者最终仍回到 DPDK 的发送接口。RDMA 路径则是：应用预先注册内存并下发工作请求，网卡把远端数据直接写入本地内存，完成后通过完成队列或事件通知应用，全程没有「收包—解析—再决策」的软件转发环。

由此可见，「内核旁路」这四个字在不同架构里的含金量并不相同。DPDK 旁路的是内核协议栈与中断，但保留了 CPU 上完整的包处理循环；OVS 与 VPP 旁路之后还额外承担了本该由内核完成的交换与路由决策；RDMA 旁路得最彻底，连包处理循环都交给了硬件。这也解释了为什么吞吐对比不能只给一个数字：在小包转发场景里，DPDK 类方案优化的是每秒包数与每包周期数；在存储与高性能计算场景里，RDMA 优化的是端到端延迟与 CPU 占用率；在虚机与容器密集的云网络里，OVS-DPDK 与 VPP 优化的是单台宿主机能承载的端口密度与隧道封装能力。四条流程各自的机制细节分别见 06-04、07-01、07-10 与 08-01，本册只保留到「谁在哪个环节做决策」这一层。

还有一条工程上很重要的流程差异：设备归属。内核协议栈下，网卡由内核驱动管理，接口名与 ifconfig 类工具可见；DPDK 类方案要求先把设备从内核驱动解绑、绑定到 vfio-pci 之类的用户态驱动，此后接口名消失，设备由单个 primary 进程独占（原理见 06-10）；OVS-DPDK 与 VPP 作为长期运行的数据面进程，通常就是那个独占者，其他 DPDK 应用若想共用同一端口，要么走 vhost-user 或 memif 这类虚拟设备与之对接，要么通过多进程模型共享（模块见 07-11）。RDMA 则由 RDMA 子系统与网卡固件管理，设备节点与权限模型又是另一套。部署前不问清「这块卡归谁」，是跨平台集成最常见的翻车点。

### 5. 配置/命令/代码实例

```text

============================================
0000:af:00.0 'Ethernet Controller X710' drv=vfio-pci unused=i40e

0000:af:00.1 'Ethernet Controller X710' if=eno2 drv=i40e unused=vfio-pci
```

逐行判读如下。输出被分成两个段落，第一段 `using DPDK-compatible driver` 列出已经绑定到 vfio-pci、uio 类用户态驱动的设备，这些设备正是 DPDK 应用、OVS-DPDK 或 VPP 可以通过 EAL 允许列表接管的端口；第二段 `using kernel driver` 列出仍归内核驱动管理的设备，它们带着 `if=eno2` 这样的接口名，属于传统协议栈路径。`0000:af:00.0` 是 PCI 的域、总线、设备、功能地址，正常应为四位十六进制域加两位总线、两位设备与一位功能；应用用 `-a` 或 `--allow` 指定端口时引用的就是它。`drv=` 给出当前生效的驱动，`unused=` 给出可切换过去的候选驱动，二者共同说明该设备是否具备用户态接管条件。异常特征很明确：若目标网卡出现在第二段且带 `if=` 接口名，说明它还没解绑，此时 DPDK 应用去 `-a` 该地址必然探测失败；若第一段为空，通常意味着 vfio-pci 模块未加载、IOMMU 未开启或当前用户无权访问设备节点。另一个隐蔽异常是同一块双口卡的两个端口被分到不同段落，这正是「一半跑内核、一半跑 DPDK」的典型形态，做对比测试前必须统一归属，否则流量根本没有走上预期的数据路径。以上为示例输出，具体格式需对照实际版本核验。

### 6. 注意事项、陷阱与最佳实践

第一，不要用「谁更快」代替「在哪条路径上更快」。内核协议栈在需要完整 TCP、连接跟踪、复杂 QoS 与成熟工具链的通用主机网络里仍然是最稳妥的选择；DPDK 类方案的优势集中在可自建协议栈、可独占端口、追求小包线速的转发面；RDMA 的优势在远端内存访问与极低 CPU 占用，但它并不提供通用 IP 转发能力。把三者放进同一张性能测试图里比绝对吞吐，得出的结论往往没有工程意义。选型时应先锁定业务的数据路径形态，再看七维对照表里对应的那几行。

第二，警惕「同一块网卡被两套架构同时接管」。既然 DPDK 类方案要求设备从内核驱动解绑并通常由单个 primary 进程独占，就不能一边让 OVS-DPDK 把端口用于虚机交换，一边又让另一个自研 DPDK 进程直接 `-a` 同一个 PCI 地址；正确做法是让自研进程通过 vhost-user、memif 或 virtio-user 这类虚拟设备接入已有数据面（模块见 07-10、07-11）。同理，RDMA 设备与以太端口的用途划分要在 BIOS、驱动与固件层就规划好，不要指望在应用层临时混用。

第三，注意 OVS 与 VPP 的「上层语义」不是免费的。它们复用 PMD 带来零拷贝与轮询收益，但流表匹配、图节点调度、隧道封装与连接跟踪同样消耗 CPU 周期；在核数固定的宿主机上，究竟把 lcore 分给转发面还是分给虚机，需要按 08-02 的指标分层来决策，而不是默认全部塞给数据面。另一个常见陷阱是版本配套：OVS、VPP 与 DPDK 三者的版本兼容性、构建选项与 ABI 需要成组核验，跨版本升级时对照 08-05 的迁移清单逐项回归，不要只升级其中一层。

第四，跨架构排障要有「先归属、再路径、后性能」的固定顺序。先用设备绑定状态确认网卡归谁，再用端口统计确认报文是否真的进入预期数据面，最后才分析每包周期数与丢包。若跳过前两步直接调参，很容易把「设备根本没接管」误判成「RSS 不均」或「内存池不足」。把这条顺序写进运维手册，能显著缩短跨团队问题的定位时间。

### 7. 小结与延伸阅读

本篇用七个维度把内核协议栈、DPDK 用户态 PMD、OVS / VPP（基于 DPDK）与 RDMA 并列对照，核心结论是：它们并非四个互相替代的选项，而是四种不同的「搬运—决策—协议」分工。内核协议栈留在内核、协议完备；DPDK 旁路内核、只提供收发与基础库；OVS 与 VPP 在 PMD 之上补齐交换与路由语义；RDMA 把搬运本身卸载到硬件。理解设备归属由谁独占、报文载体在谁的内存里、决策发生在哪一层，就能在选型与排障时快速对号入座。图 01-02-01 与七维对照表合起来，可作为后续读 07 册模块篇与 08 册性能篇的索引图。

延伸阅读建议：想弄清 OVS-DPDK、VPP 与 DPDK 之间到底通过哪些虚拟设备对接，读 07-10 与 07-11；想深入 PMD 收发调用链与零拷贝机制，读 06-04 与 06-05；想按场景做性能基准与口径对齐，读 08-01 与 08-02；设备绑定与允许列表的参数细节见 04-02，绑定步骤见 03-03。OVS、VPP 与 RDMA 相关项目的精确版本配套关系需对照各自官方发布页与实际版本核验。下一篇 01-03 会把镜头收回到 DPDK 仓库内部，讲清 `lib/`、`drivers/`、`app/` 与 `examples/` 怎样分层协作。

## 01-03 整体架构：EAL、PMD、核心库与应用分层

### 1. 背景与动机

打开一份 DPDK 源码树，初学者的第一反应往往是目录太多、角色太杂：`lib/` 下几十个子目录、`drivers/` 下按厂商与设备类型铺开、`app/` 里放着能直接跑的程序、`examples/` 里又是一堆看起来功能相近的演示。若只按目录名去猜，很容易把「库」「驱动」「应用」三件事混在一起，进而在编译时不知道该链哪个目标、在改代码时不知道该动哪一层、在排障时不知道该看哪个模块的日志。更麻烦的是，DPDK 是单一仓库却同时承担四种角色：它既是给应用链接的函数库集合，又是网卡驱动的集合，又是若干参考应用的集合，还是一份可以被 meson 按选项裁剪的构建工程。没有一个清晰的分层心智模型，后面读 06 册的机制篇与 07 册的模块篇就会像在没有坐标系的地图上找路。

分层的价值具体体现在三处。其一是依赖方向：搞清楚「谁调用谁」之后，就能判断某个接口属于稳定的上层抽象还是随硬件变化的下层实现，改代码时不会逆着依赖去动底层。其二是构建单元：meson 把每个 `lib/` 子库、`drivers/` 下的每个驱动、`app/` 与 `examples/` 里的每个程序都做成可独立开关的构建目标，理解分层才能读懂 `-Ddisable_drivers` 之类的选项到底裁掉了什么（构建选项见 02-03）。其三是运行期职责：一次收包从网卡到应用会依次经过 PMD、ethdev 抽象、mbuf 与 mempool、最后到应用逻辑，出问题时按层收敛比全局翻日志高效得多。本篇的任务就是把这张分层地图画清楚，只讲「有哪些层、各管什么、怎么依赖」，具体字段、机制与模块功能分别交给 05、06、07 册。

还有一层动机来自跨版本维护。DPDK 的目录结构在从 Makefile 迁移到 meson 的过程中做过整理，头文件位置、库的组织方式乃至部分示例程序的命名都可能随版本调整。因此概述层给出的是「稳定的职责划分」而不是「逐文件清单」：层次关系与依赖方向在 23.11 LTS、24.11 与 master 之间是连续的，但某个头文件究竟在 `lib/eal/include/` 还是别处、某个示例二进制叫不叫 `dpdk-l2fwd`，都必须对照实际版本核验。把稳定骨架和易变细节分开记，是阅读大型开源工程的基本功。

### 2. 核心概念

DPDK 的运行时可以收敛成四层。最底下是环境抽象层 EAL（`lib/eal/`），它贴近操作系统与硬件拓扑，负责预留并映射大页、拉起并把线程绑定到 lcore、扫描 PCI 设备、建立跨进程共享内存、统一日志与时钟，一句话概括就是「把跑起来所需的环境准备好」。往上是以 `lib/` 各子目录承载的核心库层，提供与具体网卡无关的数据面通用能力：报文缓冲 `rte_mbuf`、对象池 `rte_mempool`、无锁队列 `rte_ring`、查表用的 `rte_hash` 与 `rte_lpm`、以及把网卡收发抽象成端口与队列的 ethdev 库。再往下贴硬件的一侧是 PMD 驱动层（`drivers/net/`），各厂商驱动实现具体的描述符环操作与收发回调。最上面是应用与示例层（`app/`、`examples/`），testpmd、l2fwd、l3fwd 等程序把下面三层的能力串成可运行的进程。

这四层之间的依赖方向是严格单向的：应用调用核心库的公开 API，核心库依赖 EAL 提供的内存与 lcore 环境，而核心库与 PMD 之间并不是直接互相 include，而是隔着一层 ethdev 抽象。ethdev 是全篇最该记住的解耦点：上层应用眼里只有「端口 id、队列 id、一次 burst 收上来的 mbuf 数组」，下层 `drivers/net/` 里的 ixgbe、i40e、mlx5、virtio 等 PMD 各自实现 probe、配置、收发回调并注册到 ethdev 框架。正因为有这层间接，同一个 l2fwd 程序换一块网卡几乎不用改代码，只要对应 PMD 被编进构建产物并在 EAL 初始化时被探测到即可（模块见 07-01，探测流程原理见 06-01）。

驱动「被探测到」这件事本身值得多说一句，因为它解释了为什么 DPDK 程序看起来没有显式初始化驱动。PMD 通过注册机制把自己的驱动描述挂到一个全局链表上，EAL 初始化阶段扫描 PCI 总线、按设备标识匹配已注册的驱动并调用其 probe 回调，随后端口才对应用可见。这套「构造函数式注册 + 初始化期扫描」的机制在静态链接与共享链接下对链接参数有不同要求（链接方式见 02-04，机制原理见 06-01），概述层只需记住结论：驱动不是应用手工 new 出来的，而是由 EAL 在数据面启动前装配好的。与分层相伴的还有公共头文件的约定：应用包含的是安装后的 `rte_*.h` 公共头，内部结构头则留在各库目录内，这条边界正是 ABI 稳定性的第一道防线。

最后把「构建期分层」与「运行期分层」区分开。构建期，meson 按 `lib/`、`drivers/`、`app/`、`examples/` 生成一张依赖图，决定哪些目标被编译、以静态库还是共享库形式产出；运行期，真正流动的是 mbuf 与控制权，沿着 PMD → ethdev → mempool / mbuf → 应用的方向被逐层向上交付。前者关心「谁链谁」，后者关心「谁调谁」，两张图叠在一起才是完整的架构视图。图 01-03-01 画的是后者加上层次归属，下面第四节会结合它再走一遍。

把这棵目录树按职责收敛成四层，层次划分、对外接口与依赖方向见下表。

| 层次 | 源码路径 | 对外接口或代表入口 | 依赖方向 |
|---|---|---|---|
| 应用与示例层 | `app/` 与 `examples/` | testpmd、l2fwd、helloworld | 调用下层公开库 |
| 核心库层 | `lib/` 各子目录 | `rte_ethdev.h`、`rte_mbuf.h`、`rte_ring.h` | 依赖 EAL，经 ethdev 调 PMD |

| 驱动层 | `drivers/net/` | 各 PMD 的 probe 与 burst 回调 | 实现 ethdev 抽象，贴近硬件 |

读这张表时，请把「对外接口」一列当作跨层边界而非完整清单。例如 `rte_ethdev.h` 声明的批量收发接口是应用与设备之间最稳定的契约，而 PMD 内部怎样填描述符、怎样更新尾寄存器则属于驱动私有实现，应用不应直接触达（原理见 06-04、06-05）。至于报文载体 `rte_mbuf`（`lib/mbuf/`，字段见 05-02）、对象池 `rte_mempool`（`lib/mempool/`，字段见 05-03）、设备对象 `rte_eth_dev`（`lib/ethdev/`，字段见 05-04）、无锁队列 `rte_ring`（`lib/ring/`，字段见 05-06）与 EAL 内存段结构（`lib/eal/`，字段见 05-07），本册一律只点名与定位，不展开任何字段表。按「先认清它属于哪一层、再回查 05 册对应篇」的路线走，就不会在概述阶段被成片的字段定义淹没。

### 4. 关键流程与调用链

把一次「从源码到转发」的过程按层走一遍，分层图的意义就清楚了。构建阶段，meson 依据 `meson.build` 与各子目录的定义，把 EAL、核心库、被启用的 PMD 编译成库目标，再把 `app/` 与 `examples/` 里的程序链到这些库上；链接阶段要保证 PMD 的注册构造函数不被优化掉或漏链，否则运行期会发现「设备明明在，却一个端口都没有」。启动阶段，`rte_eal_init`（`lib/eal/`）完成大页映射、lcore 拉起与 PCI 扫描，驱动 probe 把可用端口登记进 ethdev 层（原理见 06-01）。随后应用创建 `rte_mempool`、配置端口与队列、启动设备，进入主循环：底层 PMD 把 DMA 填好的描述符转成 mbuf，经 ethdev 的 `rte_eth_rx_burst` 批量交给应用，应用处理后再经 `rte_eth_tx_burst` 交回驱动发出（原理见 06-04）。整条链上，每一层只和紧邻层打交道，跨层直连是被明确禁止的。

### 6. 注意事项、陷阱与最佳实践

第一，绝不逆着依赖方向写代码。应用应当只调用 `lib/` 提供的公开 API 与 ethdev 抽象，不要为了「省一次调用」直接去 include `drivers/net/` 里的驱动私有头或直接操作描述符环；那样做会把程序绑死在某块网卡上，也会在 PMD 内部实现调整时瞬间失效。确需硬件相关能力时，正确路径是通过 ethdev 的卸载配置、`rte_flow` 规则或 devargs 传入（命令见 04-02，模块见 07-01、07-06），而不是穿透抽象层。ethdev 之所以被设计成稳定边界，就是为了让上层与驱动各自演进。

第二，重视链接与注册的隐性约束。前面提到 PMD 靠注册构造函数在初始化期被装配，静态链接时若没把驱动目标链进来、或链接器把「看似未被引用」的注册段丢弃，运行期就会表现为「EAL 正常、端口为零」。这类问题在自研构建系统里尤其常见，排查时应回到 02-04 核对链接顺序与 whole-archive 类选项，并用设备与端口枚举类命令确认驱动是否真的被编入（命令见 04-02、04-05）。不要一上来就怀疑应用逻辑，那是典型的层间误判。

第三，理解构建期裁剪对运行期分层的影响。用 `-Ddisable_drivers` 之类选项把某类 PMD 关掉之后，即便硬件在、EAL 也扫到了设备，ethdev 层同样不会有对应端口可用。构建选项与运行期可见端口之间是因果对应的，跨环境迁移时务必连同 `meson_options.txt` 的配置一起复现，避免「在这台机器能跑、换台机器少一半端口」。同理，把某个核心库裁掉可能让依赖它的示例程序直接编译失败，这属于依赖图的正常约束，不是代码缺陷。

第四，跨版本阅读源码时先认层再认文件。目录职责是稳定的，具体头文件路径、库名后缀与示例二进制名可能变化；遇到「按老教程找不到文件」的情况，先在 `lib/` 与 `drivers/` 下按职责定位，再对照实际版本核验精确路径，不要凭记忆硬套。把「层次—职责—目录」三者绑定记忆，比为每个文件背路径更可靠，也更贴合 05、06、07 册按维度展开的组织方式。

### 7. 小结与延伸阅读

本篇把 DPDK 收敛成四层：最底层的 EAL 管环境与装配，其上的 `lib/` 核心库提供与硬件无关的通用能力，`drivers/net/` 的 PMD 贴硬件实现收发，`app/` 与 `examples/` 消费这些能力；四层之间以 ethdev 为关键解耦点，依赖方向严格单向，构建期的目标划分与运行期的调用方向彼此呼应。记住「应用 → 核心库 → EAL」与「核心库经 ethdev → PMD」这两条主线，就等于拿到了阅读整套资料的坐标系。图 01-03-01 与目录树、分层表三者合看，可在几秒内判断任意一段代码该归到哪一层。

延伸阅读建议：想亲手把整棵树编出来并看懂每一步，读 02-02 的 meson 实战与 02-03 的构建选项；想弄清链接顺序与驱动注册为什么会影响端口枚举，读 02-04；想查 `rte_mbuf`、`rte_mempool`、`rte_eth_dev` 的字段，回查 05-02 至 05-04；想深入 EAL 初始化、大页内存布局与 PMD 收发调用链，读 06-01、06-02、06-04；想按模块逐一了解 ethdev、mempool、ring、查表与各 PMD，读 07 全册。源码目录与头文件精确位置需对照实际版本核验。下一篇 01-04 把视角从代码结构移到时间轴，讲版本演进、LTS 与社区生态。

## 01-04 版本演进、LTS 与 dpdk.org 社区生态

### 1. 背景与动机

到上一篇为止，我们一直把 DPDK 当成一幅静态的分层图来看，仿佛 `lib/`、`drivers/`、`app/` 的位置与接口生来如此。但真实工程里，DPDK 是一个持续演进的活跃开源项目：构建体系换过、目录整理过、ABI 策略调整过、每年都有新版本发布、若干版本被选为长期支持线维护数年。对应用开发者来说，这些变化不是背景噪音，而是会直接落到能不能编译、能不能链接、升级后会不会行为漂移的现实问题。OVS、VPP 以及大量商用网元都把 DPDK 当作底座，底座的版本策略一旦没吃透，下游项目就会在升级窗口里被动挨打。因此概述层必须补上「时间轴」这一维，回答版本从哪里来、怎样被维护、社区怎样协作。

为什么要单独强调 LTS（Long Term Support，长期支持）？因为 DPDK 的发布节奏偏快，主线持续合入新特性、新驱动与新实验接口，生产系统却需要一条只收缺陷修复与安全补丁、不轻易引入行为变化的稳定线。稳定线由维护者从主线甄别并回溯合入修复，下游据此获得可预期的升级路径。理解「主线求新、稳定线求稳」这条分工，才能解释为什么同一个问题在 master 上早已修好、在某个 LTS 版本里却仍要等一次回溯，也才能理解为什么跨大版本升级必须做 ABI 与构建选项的回归。本篇不编造精确的发布月份与 LTS 清单，凡涉及具体版本号、日期与维护策略之处，一律标注「需对照实际版本核验」并指向可定位的源码或官方文档入口。

还有一层更现实的动机：本套资料以 23.11 LTS、24.11 与 master 为版本基准，而读者手里的源码可能是其中任意一种，甚至更新的版本。若概述层把某个头文件路径、某个宏名或某个版本号写成「铁律」，后续各册引用时就会把偏差放大成系统性错误。所以本篇同时承担一个方法论任务：教会读者用「可定位路径 + 核验标注」的方式阅读版本相关信息，而不是死记一串会过期的数字。这与 01-01 里强调的「不确定不编造」是一脉相承的。

### 2. 核心概念

先建立版本相关的几组概念。其一是发布节奏：DPDK 按年度推出主版本，通常在一个相对固定的时间窗口发布，随后进入下一轮特性开发；精确到月份的发布日历需对照 dpdk.org 官方发布页与实际版本核验，本册不逐月列举。其二是 LTS 与稳定分支：部分年度版本被选为长期支持线，在主线之外单独维护一段时间，期间只合入经过甄别的缺陷修复与安全补丁，维护者按 backport（回溯合入）的方式把主线上的修复移植过来；哪些版本属于 LTS、各维护多久，需对照实际版本核验。其三是 ABI 与 API 稳定性：DPDK 通过符号版本脚本、实验性接口标记与版本号宏来管理「哪些接口可以放心用、哪些可能变」，标记为实验性的接口不承诺跨版本稳定，应用若依赖它们，升级时就要格外小心（策略与迁移见 08-05）。

其四是构建体系的迁移。DPDK 早期以 Makefile 加 defconfig 类配置文件组织构建，后来全面转向 meson 与 ninja，构建选项、驱动与库开关、交叉编译方式都随之改变。这次迁移不只是换了个命令，它把「按层裁剪」变成了可声明的配置，也直接影响了 02 册整册的内容组织。迁移发生的具体版本时间点需对照实际版本核验，但「从 Makefile 到 meson」这一方向在 23.11 LTS 与 24.11 的语境下已是既成事实，源码树顶层的 `meson.build`、`meson_options.txt` 与 `buildtools/` 就是它的落地证据（构建体系见 02-01、02-02）。

其五是社区治理与协作方式。DPDK 托管在 Linux Foundation 之下，开发以邮件列表评审、patchwork 跟踪补丁、维护者签署与技术委员会协调为主要形态，仓库里的 `MAINTAINERS` 文件标明各子系统负责人，`doc/` 目录承载官方设计文档与发布说明，dpdk.org 站点集中发布版本、路线图与治理规则。对使用者而言，最有实践价值的一条是：遇到「这个接口为什么这样设计」「某个版本改了什么」，优先查对应版本的发布说明、git 提交历史与邮件列表归档，而不是二手博客；治理细节与流程需对照官方站点与实际版本核验。

### 3. 关键数据结构与源码位置

版本类信息不像 `rte_mbuf` 那样有逐字段结构可讲，它的「数据结构」其实是散落在源码树里的若干可定位锚点。第一类是版本宏与运行时版本查询：相关声明集中在 `lib/eal/` 下的版本头文件（安装后为 `rte_version.h`），构建系统还会生成带版本号的配置文件；精确宏名、函数签名与生成文件路径需对照实际版本核验。第二类是构建与 ABI 元数据：顶层 `meson.build`、`meson_options.txt`、`config/`、`buildtools/` 以及各库目录下的符号版本脚本，记录着版本号、ABI 版本与导出符号集合；这些文件的命名规则需对照实际版本核验。第三类是治理与文档：`MAINTAINERS`、`doc/` 下的发布说明与治理文档，以及 dpdk.org 站点的发布页。

把版本演进涉及的可定位线索收敛成一张表，各维度的核验入口见下表。

| 演进维度 | 代表特征 | 源码或文档定位 | 核验提示 |
|---|---|---|---|
| 构建体系 | 由 Makefile 与 defconfig 转向 meson 与 ninja | `meson.build`、`meson_options.txt`、`buildtools/` | 迁移时间点需对照实际版本核验 |
| 版本发布 | 年度主版本节奏与 LTS 维护分支 | `doc/`、`MAINTAINERS` | 具体发布月份需对照官方发布页核验 |
| ABI 策略 | 符号版本脚本与实验性接口标记 | 各库目录版本脚本、`config/` | 宏名与文件名需对照实际版本核验 |
| 社区治理 | 邮件列表、patchwork 与技术委员会 | `MAINTAINERS`、dpdk.org | 治理规则需对照官方站点核验 |
| 版本基准 | 23.11 LTS、24.11 与 master 主线 | `lib/eal/` 版本头、`meson.build` | 精确版本号需对照实际版本核验 |

表里反复出现「需对照实际版本核验」，并非推脱，而是这类信息最容易被二手资料写死。举个具体的例子：某个版本头里既有主版本、次版本之类的宏，也可能提供返回版本字符串的运行时接口，但它们的精确拼写与所在路径会随目录整理而变；应用若要按版本做条件编译，正确做法是先在安装后的 `rte_version.h` 与构建生成的配置头里确认可用宏，再写分支，而不是照抄网上的片段。结构体与配置对象的逐字段定义统一见 05 全册（字段见 05-01 的跨文档索引），各库与驱动模块在不同版本里的功能差异见 07-01，本篇不展开任何字段表。

### 4. 关键流程与调用链

把「一个修复怎样从开发者手里走到用户升级的系统里」按时间走一遍，版本流程就活了。开发者在 master 主线提交补丁，经邮件列表评审、维护者确认后合入；主线持续累积特性，到发布窗口切出候选版本、经回归测试后成为年度主版本；若该版本被选为 LTS，则建立稳定分支，此后只接受经过甄别的缺陷与安全修复，由维护者把主线上的相关提交 backport 到稳定线，再以小版本形式发布；下游项目在自己的升级窗口里，从当前 LTS 小版本升到新小版本，或跨大版本迁移到新 LTS。这条链上，「主线求新」与「稳定线求稳」始终是并行的两条轨道，二者通过 backport 而非直接合并来联系。

对应用团队来说，由此派生出三条可操作的流程结论。第一，报问题先说清版本线与具体版本号，因为同一个现象在 master 与某个 LTS 上的根因与修复状态可能完全不同。第二，不要直接从 master 摘补丁到生产用的 LTS，那等于绕过了维护者的甄别与回归，可能带入未评估的行为变化；正确做法是确认修复是否已 backport 到对应稳定分支。第三，跨大版本升级要把「构建选项、废弃接口、ABI 版本、行为变更」当成一组回归项整体核验，而不是只换一个库文件；完整的迁移清单与回归验证方法见 08-05。版本回溯与主线回流的关系在图 01-04-01 里已用「回流」虚线标出，可与本节对照阅读。

还有一条与日常开发更贴近的调用链：编译时，应用包含的公共头来自所链接 DPDK 版本的安装目录；链接时，符号版本脚本决定导出哪些 ABI；运行时，`rte_eal_init` 之前加载的库版本与头文件版本若不一致，轻则出现符号找不到，重则出现结构体布局错配这类极难定位的问题（原理见 06-01）。因此「头文件、库、运行时」三者必须同版本或多版本共存时严格隔离，这条约束是版本演进落到工程实践上最硬的一条。

### 5. 配置/命令/代码实例

本节给出一组最小的版本核验命令，用来确认「我手里的这份 DPDK 到底是什么版本」。命令只给最小形态，涉及 EAL 参数的全集完整参数见 04-01，构建与打包背景见 02-04；版本号、标签名与输出格式需对照实际版本核验。

```bash

pkg-config --modversion libdpdk
git -C dpdk describe --tags
git -C dpdk tag -l
```

下面给出示例输出，具体格式需对照实际版本核验。

```text
23.11.0
v23.11
v23.11
v24.11
```

判读说明如下。`pkg-config --modversion libdpdk` 输出的 `23.11.0` 是已安装库对外声明的版本号，正常应为「主版本.次版本.修订号」形式，且必须与编译时包含的公共头、链接到的库文件来自同一次安装；若该值与预期不符，或命令直接报 `Package libdpdk was not found`，说明 pkg-config 搜索路径里没有对应的 `.pc` 文件，通常是未执行安装步骤、或 `PKG_CONFIG_PATH` 未指向安装目录下的 `libdpdk.pc`（打包与 pkg-config 用法见 02-04）。`git describe --tags` 输出的 `v23.11` 表示当前检出点相对最近标签的位置，正常应是一个可达的发布标签；若输出带额外后缀，说明检出点位于标签之后的若干提交之上，属于开发态而非纯净发布点。`git tag -l` 列出仓库中已有的标签，示例里同时出现 `v23.11` 与 `v24.11`，提示这份源码树能追溯到多个年度版本。异常特征方面，若三个来源给出的版本互相矛盾——比如 `.pc` 是 23.11 而 git 标签停在 24.11——极可能是「装了一份、编译用了另一份」，此时任何性能或行为结论都不可信，应先统一环境再继续。以上为示例输出，具体格式需对照实际版本核验。

### 6. 注意事项、陷阱与最佳实践

第一，把「版本一致」当成硬约束。头文件、库文件、运行时加载的共享对象、以及 pkg-config 报告的版本必须来自同一次安装；多版本共存时要用独立的安装前缀与环境变量严格隔离。三者错配是升级后最隐蔽的一类故障，表现为结构体字段读错、符号解析失败或行为莫名漂移，排查成本远高于事先做一次版本核对。容器化部署时尤其要确认镜像里只带一个版本的 DPDK，别让基础镜像与构建阶段各装一份。

第二，警惕实验性接口与 ABI 边界。标记为实验性的 API 不承诺跨版本稳定，生产代码若大量依赖，等于把升级风险绑定到每一次版本变更；能走稳定公开接口的场合尽量走稳定接口，确需实验特性时把影响面收敛在少数封装层内，并在升级清单里单独标注。跨大版本迁移前，按 08-05 逐项核对废弃接口、构建选项变更与符号版本脚本差异，不要假设「重新编过就没事」。

第三，尊重 LTS 的维护边界。生产系统优先选择处于维护期内的 LTS 小版本，并及时跟进其修复版本；但不要自行把 master 的补丁 cherry-pick 到稳定线上，那会绕过社区甄别与回归。报缺陷时附版本号、复现步骤与所用构建选项，能显著加快维护者判断「这是主线已修待 backport，还是新引入的回归」。至于哪些版本属于 LTS、维护到何时、每月或每季度有哪些修复版本，需对照 dpdk.org 官方发布页与实际版本核验，切勿依据记忆中的清单做升级决策。

第四，区分「事实」与「印象」。发布月份、LTS 名单、ABI 版本号、头文件路径、乃至某个工具是否存在，都属于易变信息；本册与后续各册凡是拿不准的一律写了「需对照实际版本核验」并给出 `lib/eal/`、`config/`、`doc/`、`MAINTAINERS` 等可定位入口，就是希望读者养成「先定位、再引用」的习惯。把版本相关信息固化进自己项目的构建脚本时，也应从实际安装结果读取，而不是硬编码一串数字。

### 7. 小结与延伸阅读

本篇补上了 DPDK 的时间轴：构建体系从 Makefile 与 defconfig 迁移到 meson 与 ninja，年度主版本与 LTS 稳定分支构成「主线求新、稳定线求稳」的双轨，backport 把主线修复回流到长期支持线，ABI 与实验性接口标记管理着跨版本兼容边界，而邮件列表、patchwork、`MAINTAINERS` 与 dpdk.org 共同支撑起社区协作。图 01-04-01 把这条演进梯次与双向回流关系浓缩在一张图里，配合 01-03 的分层图，读者就同时有了「空间结构」与「时间结构」两幅坐标系。贯穿全篇的方法论只有一句：不确定的版本号、字段、签名与日期不编造，标注「需对照实际版本核验」并给出可定位路径。

延伸阅读建议：想弄清 meson 迁移后的完整构建与打包，读 02-01、02-02、02-04；想系统做跨版本升级与 ABI 回归，读 08-05；想查版本相关结构体与配置对象的字段，回查 05-01 的跨文档索引；想了解各库与驱动在不同版本里的功能差异，读 07-01；想在生产环境落地版本与变更管理，读 08-06 的运维检查清单。官方发布日历、LTS 清单、治理规则与精确版本号均需对照 dpdk.org 官方页面与实际版本核验。至此 01 册四篇从「是什么」到「与谁比」、再到「怎么分层」与「怎样演进」，已经给出整套资料所需的概述层坐标系，后续各册可在此之上按唯一权威源逐维展开。
