# DPDK 技术资料 · 04 EAL 参数与工具命令行

## 04-01 EAL 初始化参数全集

### 1. 本篇定位与覆盖范围

本篇是全册的第一篇，也是整部资料中「EAL 初始化参数」的唯一权威索引。DPDK 没有类似 VPP 中 `startup.conf` 那样的集中式配置文件，绝大多数运行期行为都由进程启动瞬间的命令行参数决定；其中由环境抽象层（EAL）在 `rte_eal_init()` 阶段解析的那一批参数，正是本篇要穷举的对象。理解本篇的第一要务，是建立一条清晰的命令行边界：任何 DPDK 应用，无论是 `testpmd`、`l2fwd`、`l3fwd` 还是自研程序，其整条命令行都被一个独立的 `--` 分隔符切成两段，`--` 之前是 EAL 通用参数，由所有基于 DPDK 的进程共享同一套解析逻辑；`--` 之后才是应用自有参数，例如 testpmd 的 `-i`、`--portmask`、`--nb-cores`，那一部分属于 04-03 与 04-04 的范围。本篇只负责前一段，且只负责其中与「初始化」直接相关的通用项。

在功能上，本篇把 EAL 参数划分为六大族，逐族给出完整表与逐项详解。第一族是 lcore 拓扑族，决定哪些逻辑核参与数据面轮询、主逻辑核（main lcore）是谁、以及逻辑核编号与物理 CPU 编号之间的映射关系，对应 `-l`、`-c`、`--lcores`、`--main-lcore` 等。第二族是内存族，决定大页内存的来源、每个 NUMA 节点各分多少、大页文件放在哪里、IOVA 采用虚拟地址还是物理地址编址，对应 `--socket-mem`、`--huge-dir`、`--iova-mode`、`--no-huge` 等。第三族是进程族，决定本进程是 primary 还是 secondary，以及多实例之间共享内存与运行时文件的命名空间，对应 `--proc-type` 与 `--file-prefix`。第四族是总线通道族，属于历史遗留的内存通道数与 rank 提示，即 `-n` 与 `-r`，在新版本里作用已明显弱化。第五族是日志与调试族，本篇只给出 `--log-level`、`--syslog`、`--log-timestamp` 这类入口的形状，分域语法、`rte_log` 八级枚举、trace 点与缓冲策略的完整展开统一放到 04-06，避免重复。第六族是杂项开关族，覆盖 HPET、telemetry、SIMD 位宽上限、VFIO 中断模式、外部驱动加载等开关。

需要特别重申本册的去重铁律：04 全册只列参数、命令与用法，不解释模块内部转发原理，不展开 `rte_mbuf`、`rte_eth_dev`、`rte_mem_config` 等结构体的完整字段表。本篇谈及某个参数如何生效时，只描述「该参数被哪个源文件解析、写入哪一份内部配置结构、影响初始化流程中的哪一步」，绝不涉及 PMD 收发包调用链、描述符环回填或 mempool 对象布局。凡需要这些背景的地方，一律写「（原理见 06-xx ｜ 字段见 05-xx ｜ 模块见 07-xx）」。例如谈到 `--socket-mem` 时只讲配额写法与 NUMA 分配结果，不讲 memseg 链表的组织方式；谈到 `--iova-mode=pa` 时只讲取值与启用条件，不讲 IOMMU 映射的建立过程。

版本基准为 DPDK 23.11 LTS、24.11 以及 master 分支。EAL 参数集合在历史上增删相当频繁：早期版本的核心参数如 `-n` 内存通道数，在新版本中已被弱化甚至不再产生实质影响；而 `--force-max-simd-bitwidth`、`--huge-unlink` 的取值模式、`--main-lcore` 取代 `--master-lcore` 的改名，都是较晚演进的结果。因此本篇对任何没有十足把握的取值、默认值或长选项拼写，都写明「需对照实际版本核验」，并给出 `lib/eal/` 下可直接定位的源码路径，绝不臆造。参数定义的权威位置是 `lib/eal/common/eal_common_options.c` 中的长选项表 `eal_long_options[]` 与 `eal_parse_common_option()`；各长选项对应的枚举常量在 `lib/eal/common/eal_options.h`；帮助文本由同文件的 usage 打印函数输出，因此在本机执行 `应用 --help` 得到的就是一份最可靠、且与当前编译版本严格一致的参数全集，这也是排错时应当优先采信的依据。初始化主流程在 `lib/eal/linux/eal.c` 与 `lib/eal/common/` 下，内部配置的承载结构定义于 `lib/eal/common/eal_internal_cfg.h`（字段见 05-07），本篇只引用其存在，不列字段。

### 3. 逐项详解

**lcore 拓扑族**。这一族参数共同回答「用哪些核、谁是主核、逻辑核与物理核怎么对应」三个问题，解析结果写入 EAL 内部 lcore 配置（字段见 05-07），供后续线程创建使用。

`-l` 或 `--corelist` 以列表形式指定参与的逻辑核集合，语法支持逗号分隔的单个编号与连字符表示的闭区间，例如 `1-4,7` 表示启用 lcore 1、2、3、4 与 7。它是当前最常用、最可读的写法，尤其当 CPU 编号不连续时比位掩码直观得多。需要注意 lcore 是从 0 开始编号的 DPDK 内部逻辑编号，只有在没有使用 `--lcores` 显式映射时，才默认与操作系统的 CPU 编号一一对应；一旦操作系统通过 `isolcpus`、cgroup cpuset 或容器配额限制了可见 CPU 集合，这种一一对应关系就可能失真，此时应改用 `--lcores` 写明真实映射。该参数与 `-c` 互斥，同一命令行只应出现其一，否则 EAL 会报参数冲突。

`-c` 或 `--coremask` 以十六进制位掩码指定逻辑核集合，第 n 位为 1 表示启用 lcore n，例如 `0x0e` 的二进制低四位为 1110，对应 lcore 1、2、3。位掩码是 DPDK 最早期就存在的写法，在脚本里用位运算拼装时很方便，但当核数超过 64 或编号跨度很大时可读性急剧下降，且容易因少写一个十六进制位而静默少启用若干个核。它与 `-l` 二选一，功能上等价，本篇推荐日常使用 `-l`，仅在需要按位拼装的自动化脚本里保留 `-c`。掩码允许的最大位数与 `RTE_MAX_LCORE` 编译期上限相关，超出会被解析阶段拒绝。

`--lcores` 用于打破「lcore 编号等于 CPU 编号」的默认假设，其典型写法是把一个 lcore 集合映射到一组物理 CPU，例如 `(0-3)@(4,5,6,7)` 表示 lcore 0 到 3 依次绑定到 CPU 4 到 7，也支持 `1@(8-11)` 这类把单个 lcore 绑定到一组 CPU 以允许该线程在这组 CPU 间漂移的写法。它在容器、CPU 隔离、以及在已被 `taskset` 限定亲和性的环境里尤其关键：若外部已把进程限定在 CPU 8 到 11，而命令行仍写 `-l 0-3`，DPDK 会尝试把线程绑到 CPU 0 到 3 并可能失败或落到错误的核上。此参数的精确语法在不同版本间有过调整，圆括号、方括号与逗号分隔的具体形式需对照实际版本核验，可查阅 `lib/eal/common/eal_common_options.c` 中的解析分支与 `lib/eal/common/eal_common_thread.c` 的绑定逻辑。

`--main-lcore` 指定主逻辑核，即执行 `rte_eal_init()` 初始化并通常承载控制面与主循环的线程所在 lcore，默认取启用集合中的最小编号。在交互型应用如 testpmd 中，把主核与数据面转发核分开是常见做法，例如 `-l 0-3 --main-lcore 0` 让 CLI 与统计打印跑在 lcore 0，转发跑在其余核上。旧版本使用 `--master-lcore` 这一名称，新版本逐步改为 `--main-lcore`，旧拼写是否仍作为兼容别名保留需对照实际版本核验；若两个名字同时出现或使用了已废弃的名字，EAL 会在解析阶段给出未知参数或弃用提示。

**内存与大页族**。这一族决定 DPDK 进程向操作系统申请多少内存、从哪个 hugetlbfs 挂载点取、以及这些内存如何映射到设备可见的地址空间。

`--socket-mem` 按 NUMA 节点逐一给出内存配额，取值是逗号分隔的 MB 数，第 n 个数对应 socket n，例如 `1024,1024` 表示两个节点各预留 1024 MB，`1024,0` 表示只在 socket 0 预留。它是多 NUMA 机器上最重要的内存参数：把内存与网卡所在 socket 对齐能避免跨节点访存代价（原理见 06-09）。若某个节点配额写成 0，该节点上将不创建 mempool 后备内存，凡从该节点分配的 mbuf 都可能失败，因此当应用显式指定 `--socket-num` 或使用跨节点端口时要格外小心。该参数与 `-m` 互斥：`-m` 给出总量但不区分节点，由 EAL 自行分摊，在 NUMA 环境中可控性较差，仅在单节点或实验环境使用。配额之和不应超过 `/proc/meminfo` 中已预留的大页总量，否则启动阶段会打印 hugepage 不足的错误。

`--socket-limit` 为每个 socket 设置内存上限，形状与 `--socket-mem` 类似，用于限制运行时动态扩展可占用的上限，与 `--socket-mem` 的预留量是两个不同概念。该参数在部分版本中的具体语义与默认值存在差异，需对照实际版本核验，并以 `lib/eal/linux/eal_memory.c` 与 `lib/eal/common/eal_common_options.c` 为准。一般建议只在启用 `--legacy-mem` 或需要显式封顶动态分配的场景下才动它，常规部署保持默认即可。

`--huge-dir` 指定 hugetlbfs 的挂载点，例如 `/mnt/huge_2M` 或 `/dev/hugepages`。当系统上同时挂载了 2 MB 与 1 GB 两种大页时，明确给出目录能避免 EAL 选错页大小；结合 `mount -t hugetlbfs -o pagesize=1G` 的挂载选项，可以精确控制使用哪一种页。若未指定，EAL 会扫描已挂载的 hugetlbfs 并自行选择，容器中经常需要显式指定，因为挂载点是通过 volume 透传进来的、路径与宿主机不同。相关探测逻辑在 `lib/eal/linux/eal_hugepages.c` 与 `lib/eal/linux/eal_memory.c`。

`--no-huge` 是一个布尔开关，指示 EAL 不使用大页，改用普通 4 KB 页并通过 `--socket-mem` 之类配额控制用量。它主要服务于无法预留大页的容器、CI 与快速功能验证，代价是 TLB 命中率下降、性能明显偏低，绝不可用于生产数据面或性能基准。启用该开关后通常还需配合 `--iova-mode=va`，因为普通页下物理地址连续性假设不再成立。是否需要同时给出 `--no-shconf` 取决于部署方式，需对照实际版本核验。

`--iova-mode` 强制指定设备 DMA 使用的 IOVA 编址模式，常见取值为 `pa`（物理地址）与 `va`（虚拟地址），留空时由 EAL 依据 IOMMU 与驱动能力自动探测。在 VFIO 且 IOMMU 开启的现代平台上，`va` 通常是更稳妥的选择；在 `igb_uio`、无 IOMMU 或某些需要物理连续地址的老驱动场景下可能需要 `pa`。当自动探测结果与驱动能力冲突时，EAL 会打印 `Selected IOVA mode` 或相应报错，此时用本参数显式固定即可。该参数的具体取值字符串在版本间可能微调，需对照 `lib/eal/common/eal_common_options.c` 与 `lib/eal/linux/eal.c` 核验。

`--legacy-mem`、`--single-file-segments`、`--match-allocations` 属于内存模型相关的遗留开关，分别对应旧式预留全部大页、让多个 memseg 共享单个大页文件、以及释放内存时立即归还等历史行为。自 18.x 引入动态内存模型后，这些开关多数场景已不再需要，仅在与旧 secondary 进程互通、或复现特定内存排布问题时才会用到；每一项是否仍在当前版本生效、默认值如何，均需对照实际版本核验，定位在 `lib/eal/linux/eal_memory.c` 与 `lib/eal/common/eal_common_options.c`。

`--base-virtaddr` 强制指定 EAL 预留内存区的起始虚拟地址，用于多进程场景下保证 primary 与 secondary 把共享内存映射到相同地址，从而让共享指针有效（原理见 06-10）。现代版本借助更稳健的映射协商后，手工指定基址的必要性已大幅降低；取值必须是合法且未被占用的对齐地址，写法与是否接受 `0x` 前缀需对照实际版本核验。

`-m` 或 `--memory` 以 MB 为单位给出预留内存总量，与 `--socket-mem` 互斥。它不区分 NUMA 节点，由 EAL 按探测到的节点数量分摊，因此在双路服务器上写 `-m 2048` 可能得到每节点 1024 MB 的结果，也可能因探测差异而不同，可预测性不如 `--socket-mem`。本篇把它列为「了解但不推荐用于多节点」的参数，生产环境一律建议显式使用 `--socket-mem`。

**进程族**。这一族决定多进程协作中的角色与命名空间隔离。

`--proc-type` 取值 `primary`、`secondary` 或 `auto`。primary 负责创建并初始化共享内存、大页与设备，secondary 附着到已有 primary 的共享内存上，只读地观测或辅助处理，`dpdk-procinfo`、`dpdk-pdump` 都是典型的 secondary（用法见 04-05）。`auto` 会依据共享配置文件是否已存在自动判断角色，适合脚本化启动但可预测性较差。角色判断逻辑在 `lib/eal/common/eal_common_proc.c` 与 `lib/eal/linux/` 下的多进程实现中。

`--file-prefix` 给共享内存文件、多进程 socket 与运行时目录加前缀，用于在同一台主机上并行运行多个互不干扰的 DPDK 实例。凡是 secondary 要附着到某个 primary，两者的 `--file-prefix` 必须一致，否则会找不到共享内存或直接另起炉灶，这是 `dpdk-procinfo` 报「无法连接」时最先要核对的参数。容器多实例、CI 并发测试、以及一台机器上同时跑 testpmd 与业务进程时，都应显式给出不同前缀。其影响范围涵盖 mp_socket、fbarray 内存文件与 telemetry socket，路径拼接逻辑在 `lib/eal/common/eal_common_proc.c` 与 `lib/eal/linux/eal_filesystem.c` 附近。

`--no-shconf` 禁止创建共享配置文件，使进程退出后不留下可供 secondary 附着的运行时文件，常用于一次性、无多进程协作的短生命周期任务。启用后 secondary 将无法附着，因此绝不能与需要被 `dpdk-procinfo` 或 `dpdk-pdump` 观测的部署同时使用。

**通道历史族**。`-n` 或 `--memory-channels` 与 `-r` 或 `--memory-ranks` 是早期用于提示内存通道数与 rank 数、辅助 EAL 做地址交错与 mempool 对齐的参数。随着内存子系统重写与动态内存模型引入，它们在现代版本中的实际作用已明显弱化，很多场景下只是被解析后不影响结果，部分版本甚至可能不再接受。是否仍有效、默认值多少需对照实际版本核验，定位在 `lib/eal/common/eal_common_options.c`。本篇保留它们，是因为大量存量脚本与网上命令示例仍携带 `-n 4`，读者需要知道它「是什么、为何如今常常可以忽略」，而不是照抄。

**日志与调试族入口**。`--log-level` 是本篇唯一详细列出形状的日志参数，它既接受一个数字级别（数值到级别的映射见 04-06），也接受 `域名:级别` 的分域写法如 `--log-level=lib.eal:debug`，并且可以在同一条命令行上重复出现，用于对不同库或不同 PMD 分别设定级别。`--log-level=help` 会打印当前版本注册的所有日志域，是排查「为什么看不到某模块日志」的第一步。分域匹配的完整规则、`rte_log` 八级枚举、以及 trace 相关开关全部在 04-06 展开，本篇不重复。`--syslog` 控制日志是否转发到系统日志，取值形态需核验；`--log-timestamp` 为每行日志加时间戳，便于与内核或外部日志对齐时间线，二者解析同样在 `eal_common_options.c`。

**杂项开关族**。`--no-telemetry` 关闭本进程的 telemetry 服务端点，CI 里常用来避免 socket 残留与端口占用；遥测端点的读取方法见 04-07。`--no-hpet` 关闭 HPET 高精度计时器依赖，在缺少 HPET 或计时源不稳定的虚拟化环境中有用。`--force-max-simd-bitwidth` 限制进程可用的最大向量指令位宽，便于在异构集群上强制走标量或 AVX2 路径做可复现基准，具体可接受取值需对照实际版本核验。`-h` / `--help` 打印 usage，`-v` 打印版本后退出，短名 `-v` 是否存在需对照实际版本核验；二者都在参数解析极早期处理，不会触发大页预留。

### 4. 典型示例

下面给出一条双 NUMA 节点上的最小可运行 testpmd 启动命令，随后是它对应的 EAL 初始化日志。命令中 `--` 之前全部是本篇覆盖的 EAL 参数，之后 `-- -i --portmask 0x3` 是 testpmd 应用参数（见 04-03）。

```bash
testpmd -l 0-3 --main-lcore 0 --socket-mem 1024,0 \
  --huge-dir /dev/hugepages --file-prefix pg0 \
  --proc-type primary --iova-mode=va \
  --log-level=lib.eal:info --no-telemetry \
  -- -i --portmask 0x3 --nb-cores 2
```

示例输出，具体格式需对照实际版本核验：

```text
EAL: Detected CPU lcores: 16
EAL: Detected NUMA nodes: 2
EAL: Detected shared linkage of DPDK
EAL: Multi-process socket /var/run/dpdk/pg0/mp_socket
EAL: Selected IOVA mode 'VA'
EAL: 512 hugepages of size 2097152 reserved, but no mounted hugetlbfs found for that size
EAL: Probing VFIO support...
EAL: VFIO support initialized
EAL: Using IOMMU type 1 (Type 1)
EAL: Probe #1: PCI device 0000:01:00.0 on NUMA socket 0
EAL:   probe driver: net_ixgbe
EAL: Main lcore 0 is ready (tid=0x7f1c4a3d1700)
EAL: lcore 1 is ready (tid=0x7f1c49bcf700)
EAL: lcore 2 is ready (tid=0x7f1c493ce700)
EAL: lcore 3 is ready (tid=0x7f1c48bcd700)
Interactive-mode selected
testpmd>
```

逐行判读说明如下。第 1 行 `Detected CPU lcores: 16` 是 EAL 探测到的可用逻辑核总数，用于校验 `-l 0-3` 是否落在合法范围内，若这里显示的数字小于 4，说明容器或 cpuset 限制了可见 CPU，应改用 `--lcores` 重映射。第 2 行 `NUMA nodes: 2` 决定 `--socket-mem 1024,0` 的逗号字段个数是否匹配；本例两个节点、配额只有第一项非零，表示有意只在 socket 0 预留内存，需确认两张网卡确实都位于 socket 0，否则第二张卡分配 mbuf 会失败。第 4 行多进程 socket 路径中的 `pg0` 正是 `--file-prefix pg0` 生效的证据，后续 `dpdk-procinfo` 必须携带同样的前缀才能附着（见 04-05）。第 5 行 `Selected IOVA mode 'VA'` 表明 `--iova-mode=va` 被采纳，若这里出现 `PA` 且与预期不符，应检查 IOMMU 与驱动能力。第 6 行是关于 2 MB 大页与挂载点的提示，出现 `no mounted hugetlbfs found` 时必须核对 `--huge-dir` 是否指向正确挂载点，这类提示在页大小混挂环境里很常见，需结合实际版本输出措辞核验。第 7 到 9 行是 VFIO 与 IOMMU 探测结果，`VFIO support initialized` 表示设备可以走 VFIO 路径；若打印 `VFIO support failed` 或回退到 UIO，设备绑定状态就要回头用 `dpdk-devbind.py --status` 复查（见 04-05）。第 10、11 行显示 PCI 设备被 `net_ixgbe` 驱动成功 probe，这是 `-a` 白名单或自动扫描的结果（见 04-02）。第 12 行标明主 lcore 0 已就绪，印证 `--main-lcore 0` 生效；随后四个 `lcore is ready` 对应 `-l 0-3` 启用的四个线程均已创建并完成亲和绑定。最后 `Interactive-mode selected` 与 `testpmd>` 提示符说明已进入交互 CLI，此后输入的 `start`、`show port stats all` 等属于 04-03 的运行时命令。整段输出里没有任何 `EAL: Error` 或 `PANIC` 行，可判定初始化阶段全部通过；一旦任意一行出现 `Cannot get hugepage information`、`failed to parse` 或 `Cannot init memory`，就应回到本篇第 7 节按参数族排查。

再看一组专门用于确认日志域与参数全集的命令，它在排错第一步非常有用。

```bash
testpmd --log-level=help --help
```

该组合会先让 EAL 打印当前构建注册的全部日志域清单，再打印 usage；前者是写 `--log-level=pmd.xxx:debug` 时域名的唯一可靠来源，后者是本机版本参数拼写与默认值的唯一可靠来源。两者都以「需对照实际版本核验」为原则，直接从目标二进制取得，避免跨版本照抄文档造成拼写错误。

### 5. 速查表

下表按常见部署目标给出参数组合，读者可整行复制后按实际核数与 NUMA 拓扑微调。

| 部署目标 | 推荐参数组合 | 注意点 |
|---|---|---|
| 单机单节点快速验证 | `-l 0-3 -m 1024 --no-huge --iova-mode=va` | 性能低，仅功能验证 |
| 双路 NUMA 生产转发 | `-l 0-7 --socket-mem 2048,2048 --huge-dir /dev/hugepages` | 网卡与核同 socket |
| 多实例隔离 | `--file-prefix pg0` 与 `--file-prefix pg1` 分别启动 | 前缀必须互异 |
| 被 procinfo 观测 | primary 带 `--file-prefix pg0`，secondary 同名 | 不加 `--no-shconf` |
| 容器无大页 | `--no-huge --iova-mode=va --no-telemetry` | 仅 CI 使用 |
| 指定主核 | `-l 0-3 --main-lcore 0` | 主核与转发核分离 |
| 可复现基准 | `--force-max-simd-bitwidth=...` 需核验取值 | 避免向量路径差异 |
| 静默日志 | `--log-level=lib.eal:warning --no-telemetry` | 分域名以 help 为准 |

下表列出参数之间的互斥与依赖关系，误配时 EAL 通常在解析阶段就报错，提前知道可少走弯路。

| 参数 A | 参数 B | 关系 | 处理建议 |
|---|---|---|---|
| `-l` | `-c` | 互斥 | 只保留其一 |
| `-m` | `--socket-mem` | 互斥 | 多节点用后者 |
| `--proc-type=secondary` | `--no-shconf` | 冲突 | primary 不要加 no-shconf |
| `--no-huge` | `--huge-dir` | 无意义组合 | 去掉 huge-dir |
| `--iova-mode=pa` | 开启 IOMMU 的 VFIO | 可能不兼容 | 改用 va 或自动 |
| `--lcores` | `-l` | 覆盖关系 | 二选一表达更清晰 |

为便于脚本拼装，下面把「参数族模板」以变量形式集中列出，长清单不塞进表格单元格。

```bash
LCORE="-l 0-7 --main-lcore 0"
MEM="--socket-mem 2048,2048 --huge-dir /dev/hugepages"
PROC="--proc-type primary --file-prefix pg0"
MISC="--iova-mode=va --no-telemetry --log-level=lib.eal:info"
testpmd $LCORE $MEM $PROC $MISC -- -i --portmask 0x3 --nb-cores 4
```

### 6. 版本差异

本节只谈「参数集合与拼写」随版本的变化，不涉及机制演进（原理见 06-xx）。首先是最容易踩到的改名：`--master-lcore` 在较新版本中被 `--main-lcore` 取代，这是社区移除含歧视性术语命名时统一调整的一部分；23.11 LTS 与 24.11 是否仍保留旧名作为兼容别名，不能直接断定，必须在目标版本执行 `--help` 确认，源码依据是 `lib/eal/common/eal_common_options.c` 的长选项表与其在 `lib/eal/common/eal_options.h` 中的枚举。若脚本从旧集群迁到新集群后出现「unknown option」报错，这一改名是首要嫌疑。

其次是内存相关开关的增删。`--legacy-mem`、`--single-file-segments`、`--match-allocations` 是动态内存模型切换期的产物，在 23.11 LTS 与 24.11 中是否仍被接受、是否已被标记为弃用或彻底移除，需对照实际版本核验；`--huge-unlink` 从早期单纯的布尔开关演进为可接受 `existing`、`always`、`never` 一类模式值，具体取值集合同样需核验，定位在 `lib/eal/linux/eal_memory.c` 与 `eal_common_options.c`。`--socket-limit` 与 `-n`、`-r` 这些历史参数在新版本里可能只是被兼容解析而不再产生实质行为，读者在 04-08 的「最小可复现命令集」里会看到本篇据此推荐的最小参数集合，即尽量只用 `-l`、`--socket-mem`、`--huge-dir`、`--file-prefix`、`--iova-mode`、`--log-level` 这六个高频项。

第三类是新近引入的参数。`--force-max-simd-bitwidth`、`--no-telemetry` 以及 telemetry 相关的 `--telemetry` 家族开关，在不同分支上的名字与默认值可能不同；`--syslog` 的取值从早期布尔形态变为 `auto` / `always` / `never` 一类枚举，也都需对照实际版本核验。日志库在较新版本中从 `lib/eal/` 拆分到 `lib/log/`，`rte_log` 相关解析虽仍经 EAL 参数入口，但底层实现路径变了，这在 04-06 会结合 `lib/log/log.c` 再说明。总之，面对跨版本差异，最稳妥的工程做法不是记忆某一篇文档的取值表，而是把「目标二进制 `--help` 输出」作为唯一事实源，本篇表格负责给出功能族与语义框架，具体拼写以核验为准。

### 7. 常见误用与调试

第一类高频误用是把 `-l` 与 `-c` 同时写上。有人既想用列表又顺手贴了掩码，EAL 解析阶段会直接报参数冲突并退出，日志里出现 `cannot have both` 一类提示。正确做法是二者只留其一，现代部署统一用 `-l`。第二类是把 lcore 编号误当成物理 CPU 编号：在容器或 `taskset` 限定的环境里，`-l 0-3` 可能试图绑定到根本不在允许集合中的 CPU，表现为线程创建后亲和设置失败或转发核全部空转，此时应改用 `--lcores` 显式写明 `lcore@CPU` 映射，并用 `dpdk-procinfo` 或直接读 `/proc/<pid>/task/<tid>/status` 核对亲和结果。

第三类是 `--socket-mem` 的字段数与 NUMA 节点数不匹配。双路机器上只写一个数字，或把某一节点配额写成 0 却让该节点的网卡参与转发，会表现为 `start` 之后某端口 `rx_nombuf` 持续上涨甚至无包可收。排查顺序是先看 EAL 启动日志的 `Detected NUMA nodes`，再看 `/sys/bus/pci/devices/<BDF>/numa_node`，最后按节点顺序对齐 `--socket-mem`。第四类是 `--file-prefix` 在 primary 与 secondary 之间不一致，`dpdk-procinfo` 或 `dpdk-pdump` 会报找不到共享内存或连接到一个空实例；这类问题的特征是 secondary 侧报「cannot init」而 primary 侧毫无异常，务必两端前缀逐字符比对。

第五类是 `--no-shconf` 与观测工具并用：一旦 primary 加了 `--no-shconf`，后续任何 secondary 都无法附着，报错看似内存问题，实为进程族配置。第六类是 `--iova-mode=pa` 与开启 IOMMU 的 VFIO 组合，可能在 probe 阶段报 DMA 映射失败，改用 `va` 或干脆让 EAL 自动探测通常即可解决。第七类是照抄旧脚本里的 `-n 4`、`--master-lcore` 或已废弃的内存开关，在新版本上轻则被忽略、重则报未知选项；处理办法是执行一次 `--help` 重建参数清单，再按第 5 节的最小集合裁剪。

统一的调试入口建议按以下顺序执行，逐步收敛到具体参数域。

```bash
testpmd --help
testpmd --log-level=help
cat /proc/meminfo | grep -i huge
numactl -H
```

第一条确认本机参数拼写与默认值，第二条拿到可用于分域日志的域名清单，第三条确认大页预留量是否够 `--socket-mem` 之和，第四条确认 NUMA 节点数与节点编号顺序。四步都通过后再回去核对 `--lcores`、`--file-prefix`、`--iova-mode` 这三个最容易与外部环境耦合的参数，绝大多数初始化失败都能定位到某一行的某个具体取值。错误现象到参数域的完整映射表见 04-08，本篇不重复。

## 04-02 设备与驱动管理参数

### 1. 本篇定位与覆盖范围

本篇是 DPDK「设备与驱动管理参数」的唯一权威源，覆盖所有在 EAL 段解析、用于决定「哪些设备被允许、哪些被阻止、设备以什么参数被驱动探测、虚拟设备如何声明」的参数与语法。它与 04-01 同属 EAL 参数，但边界清晰：04-01 管的是初始化框架本身（用哪些核、多少内存、何种进程角色），本篇管的是挂到这条框架上的设备清单。二者共同位于 `--` 分隔符之前，任何一条真实命令行通常都会同时携带两族参数。

本篇要穷举的对象包括四组。第一组是设备允许与阻止，即 `-a` / `--allow` 与 `-b` / `--block`，它们构成设备白名单与黑名单，是 PCIe 设备密集的服务器上控制「哪张卡归 DPDK」的核心手段。第二组是 devargs 语法，即附加在设备标识后面的一组 `键=值` 参数，用于把驱动私有配置、代表名、端口表示等信息随设备一起传给 PMD probe 过程。第三组是 PCI 地址与代表名，讲清 `0000:01:00.0` 这种 BDF 的字段含义、多函数设备、以及 SR-IOV 场景下 VF 与代表端口（representor）的书写方式。第四组是虚拟设备与外部驱动，即 `--vdev`、`-d`、`--no-pci`、`--create-uio-dev`、`--vfio-intr` 等，覆盖 net_tap、net_pcap、net_memif、virtio-user 这类不依赖物理 PCI 总线的设备声明，以及运行时加载外部 PMD 共享库的方式。

去重铁律在本篇同样严格：只讲「参数怎么写、写到哪个文件解析、产生什么可见结果」，不讲 ethdev 设备抽象、probe 回调注册、驱动与设备匹配的内部流程（模块见 07-01），不展开 `rte_devargs`、`rte_pci_addr`、`rte_eth_dev_data` 等结构体的字段表（字段见 05-04、05-07），也不讲 RSS 或 rte_flow 规则如何下发到硬件（原理见 06-06）。例如谈到 `representor=` 时只讲语法与 netdev 命名结果，不讲代表端口在内核与 PMD 之间的报文流向；谈到 `-d` 时只讲加载路径与常见报错，不讲构造函数注册机制（原理见 06-01）。

源码定位集中在三处：`lib/eal/common/eal_common_options.c` 负责 `-a`、`-b`、`--vdev`、`-d` 的命令行解析；`lib/eal/common/eal_common_devargs.c` 与 `lib/eal/include/rte_devargs.h` 负责 devargs 字符串的拆解、策略标记与链表管理；`lib/eal/common/eal_common_dev.c` 与 `lib/eal/linux/eal_dev.c` 负责把 allow/block 决策应用到总线扫描结果。PCI 地址解析与设备扫描在 `drivers/bus/pci/` 下，虚拟设备总线在 `drivers/bus/vdev/`，网卡绑定工具在 `usertools/dpdk-devbind.py`（其命令见 04-05，本篇只引用）。版本基准仍为 23.11 LTS / 24.11 / master，devargs 的策略字段、代表名语法、以及各工具脚本名在不同版本间差异明显，凡无把握处一律标注「需对照实际版本核验」并给出上述路径。

### 3. 逐项详解

**设备允许与阻止**。`-a` 或 `--allow` 把某个设备加入允许列表，参数值既可以是纯 PCI 地址 `0000:01:00.0`，也可以是「地址 + 逗号 + devargs」的形式，例如 `-a 0000:01:00.0,representor=[0-3]`。当命令行里出现任意 `-a` 时，EAL 会转为白名单模式：只有被显式允许的设备才进入 probe，其余 PCI 设备即使已绑定到 vfio-pci 也不会被 DPDK 接管。这一行为在多网卡服务器上极其重要，因为未被允许但仍绑定在 DPDK 驱动上的设备会导致系统其他服务失去网卡，白名单能把影响面收敛到指定端口。解析在 `lib/eal/common/eal_common_options.c`，决策落到 `lib/eal/common/eal_common_dev.c` 的扫描过滤逻辑。`-a` 可以重复出现多次，顺序一般不影响结果，但建议按 BDF 升序书写便于核对。

`-b` 或 `--block` 与之相反，把某个设备加入阻止列表。它用于黑名单模式：扫描全部设备，但显式排除指定的几个，例如 `-b 0000:02:00.0` 让那张管理网卡留给内核。`-a` 与 `-b` 同时出现时的优先级、以及是否允许对同一设备既 allow 又 block，不同版本处理略有差异，需对照实际版本核验，源码在 `eal_common_devargs.c` 的策略合并部分。工程上的稳妥做法是同一条命令行只用一种模式：要么全是 `-a` 白名单，要么全是 `-b` 黑名单，避免语义歧义。无论哪种模式，未被 DPDK 接管的设备是否仍显示为内核网卡，要用 `usertools/dpdk-devbind.py --status` 复核（命令见 04-05）。

**devargs 语法**。devargs 是附加在设备标识之后、由逗号分隔的一组 `键=值` 对，形如 `键1=值1,键2=值2`，它们随设备一起被保存，并在 PMD probe 时由对应驱动读取。因此 devargs 的合法键集合完全由驱动决定，EAL 只负责拆解与透传，并不理解每个键的含义。这一点是排错的关键：写了一个驱动不认识的键，EAL 阶段通常不报错，直到 probe 时该驱动才提示参数无效或干脆忽略。总线层通用的键包括用于按类别匹配的 `class=`、按名称匹配的 `name=`、以及较新 devargs 策略模型中的策略标记字段（具体拼写与取值需对照 `lib/eal/include/rte_devargs.h` 与实际版本核验）。驱动私有键的例子有 net_pcap 的 `rx_pcap`、`tx_pcap`，net_tap 的 `iface`、`speed`，以及 mlx5 一类驱动的 `representor`。拆解与链表管理在 `lib/eal/common/eal_common_devargs.c` 的 `rte_devargs_parse()` 与 `rte_devargs_insert()` 附近，本篇只描述「字符串被拆成键值并挂到设备对象上」这一可见结果，不列 `rte_devargs` 结构体字段（字段见 05-07）。

**PCI 地址与代表名**。PCI 地址采用 `domain:bus:devid:function` 四段十六进制书写，通常简写为 `0000:01:00.0`：域 0000、总线 01、设备 00、功能 0。多端口网卡常以同一 devid 下不同 function 呈现，例如 `0000:01:00.0` 与 `0000:01:00.1` 是同一张双口卡的两个端口，用 `-a` 时必须分别列出，只写 `.0` 不会自动带上 `.1`。VF（SR-IOV 虚拟功能）同样占用独立 BDF，通常呈现为另一个 devid 或更高的 function 号，在 VF 透传场景里要对 VF 的 BDF 单独做 allow。解析在 `drivers/bus/pci/` 下的地址解析代码，可用 `lspci -D` 或 `dpdk-devbind.py --status` 取得准确 BDF，切勿凭网口名猜测。

代表名（representor）是 SR-IOV 与 switchdev 模式下表示 VF 对应端口的写法，常见于 mlx5 等驱动，形态如 `representor=[0-3]`、`pf0vf[0-3]` 或范围与列表混合的写法，并作为 devargs 键随允许项一起给出，例如 `-a 0000:01:00.0,representor=[0-3],dv_flow_en=1`。它决定 PMD 创建出多少个 ethdev 端口以及端口名如何编号，是后续 `testpmd --portmask` 与 `show port info` 看到的端口集合的直接来源。由于该语法高度依赖具体驱动与内核版本，取值范围、方括号与 `pfXvfY` 的拼写、以及是否需要额外开关（如启用 switchdev 模式的键）都需对照实际版本核验，并以对应驱动在 `drivers/net/` 下的 devargs 文档为准。本篇只强调一点：representor 是「设备声明层的写法」，它产生的端口列表会进入 04-03 的 port 配置命令，二者通过端口编号衔接。

**虚拟设备与外部驱动**。`--vdev` 声明一个不经过 PCI 总线扫描、由 vdev 总线创建的虚拟设备，语法是「设备名 + 逗号 + devargs」，可重复出现以创建多个。典型例子有 `--vdev net_tap0,iface=tap0` 创建 TAP 口、`--vdev net_pcap0,rx_pcap=/tmp/in.pcap,tx_pcap=/tmp/out.pcap` 从 pcap 文件回放与落盘、`--vdev net_memif0,socket=/tmp/memif.sock` 创建 memif 口，以及 virtio-user 一类对接 vhost 的虚拟端口。设备名的数字后缀与 devargs 键名均由具体驱动定义，需对照 `drivers/bus/vdev/` 与对应 `drivers/net/*` 的文档核验；一个常见错误是把不同驱动的键混用，例如给 net_tap 写 `rx_pcap`，probe 阶段会报参数未知。`--vdev` 与 `-a` 不冲突，前者走 vdev 总线、后者走 PCI 总线，二者可同时出现。

`-d` 加载外部 PMD 共享库（`.so`），用于把未编译进主二进制的驱动在启动时动态挂入，例如使用树外驱动或分发时精简了驱动集合的场景。路径可以是相对或绝对，多个库重复给出多个 `-d`。其长选项拼写在不同资料里写法不一，是否确为 `--driver-path` 需对照实际版本核验，源码在 `lib/eal/common/eal_common_options.c` 与 `lib/eal/common/eal_common_options.c` 中处理插件初始化的分支；相关加载机制（原理见 06-01）。失败时的典型现象是 `cannot open shared object file`，应检查 LD_LIBRARY_PATH 与库架构是否匹配。

`--no-pci` 完全禁用 PCI 总线扫描，常用于只跑虚拟设备、或容器里根本不透传 PCI 设备的纯软件测试。启用后即使 `-a` 写了 BDF 也不会生效，所有端口都只能来自 `--vdev`。`--create-uio-dev` 让 EAL 为 UIO 驱动创建 `/dev/uioX` 设备节点，主要用于 igb_uio 场景且当前用户有权限时，是否与 `--no-pci` 并存需核验。`--vfio-intr` 指定 VFIO 中断模式（如 legacy、msi、msix 一类取值，具体集合需对照实际版本核验），`--vfio-vf-token` 用于 SR-IOV VF 与 PF 之间的令牌认证，二者都属于 VFIO 相关的高级开关，仅在特定驱动与内核组合下需要，常规 vfio-pci 转发无需设置。

### 4. 典型示例

下面演示「白名单 + 两个物理端口 + 一个 pcap 虚拟端口」的完整声明。假设目标机器上 `0000:01:00.0` 与 `.1` 已绑定到 vfio-pci，另有 `0000:02:00.0` 是留给内核的管理网卡，必须排除。

```bash
dpdk-testpmd -l 0-3 --socket-mem 1024,0 --file-prefix pg0 \
  -a 0000:01:00.0 \
  -a 0000:01:00.1 \
  -b 0000:02:00.0 \
  --vdev net_pcap0,rx_pcap=/tmp/in.pcap,tx_pcap=/tmp/out.pcap \
  -- -i --portmask 0x7
```

示例输出，具体格式需对照实际版本核验：

```text
EAL: Probe #1: PCI device 0000:01:00.0 on NUMA socket 0
EAL:   probe driver: net_ixgbe
EAL:   PCI memory mapped at 0x7f1c40000000
EAL: Probe #2: PCI device 0000:01:00.1 on NUMA socket 0
EAL:   probe driver: net_ixgbe
EAL:   PCI memory mapped at 0x7f1c40002000
EAL: Blocked device 0000:02:00.0 by user
EAL: vdev net_pcap0 created from rx_pcap=/tmp/in.pcap
EAL:   ethdev port 2 registered as net_pcap0
EAL: All devices probed, 3 ethdev ports available
testpmd> show port info 0
  Port 0: driver net_ixgbe, MAC 00:11:22:33:44:55
testpmd> show port info 2
  Port 2: driver net_pcap0, MAC 00:00:00:00:00:02
```

逐行判读说明如下。前两行与第四、五行分别显示两个物理 PCI 端口被扫描并由 `net_ixgbe` 驱动成功 probe，BDF 与命令行里两条 `-a` 一一对应，说明白名单模式生效，且多端口卡的 `.0` 与 `.1` 必须分别声明这一规则得到印证；`PCI memory mapped at` 行是 BAR 映射成功的普通提示，地址值无需关心。第六行 `Blocked device 0000:02:00.0 by user` 明确证实 `-b` 黑名单把管理网卡排除在 DPDK 之外，这张卡仍由内核驱动持有，若这一行缺失且该卡也被 probe，说明 allow 与 block 混用导致策略未按预期合并，应改为纯白名单。第七、八行显示 `--vdev` 声明的 net_pcap0 经 vdev 总线创建，并注册为 ethdev 端口 2，注意虚拟端口的编号排在物理端口之后，因此 `--portmask 0x7` 的低三位正好覆盖端口 0、1、2；若端口编号顺序与预期不符，后续所有 port 相关命令都要按 `show port info` 的实际编号调整。第九行 `3 ethdev ports available` 是整条命令的收尾结论，它把「两条 `-a` 加一条 `--vdev`」折算成可见端口总数，是验证设备声明是否完整的最快指标。随后两条 `show port info` 的输出分别给出驱动名与 MAC，用来区分物理口与 pcap 口；pcap 口的 MAC 通常是占位值，属正常现象。整段没有任何 `probe failed`、`unknown devargs` 或 `no Ethernet ports found` 报错，可判定设备声明层配置正确；若出现 `unknown parameter rx_pcap`，说明把 pcap 的键写到了不识别它的虚拟设备上，需回到第 3 节按驱动核对 devargs 键集合。

再看一组专门验证「设备绑定状态」的命令，它属于 04-05 的完整工具集，这里只给出与本例配套的最小调用，用于在启动前后确认 BDF 归属。

```bash
dpdk-devbind.py --status
```

示例输出，具体格式需对照实际版本核验：

```text
Network devices using DPDK-compatible driver
============================================
0000:01:00.0 '82599ES 10-Gigabit' drv=vfio-pci unused=ixgbe
0000:01:00.1 '82599ES 10-Gigabit' drv=vfio-pci unused=ixgbe

Network devices using kernel driver
===================================
0000:02:00.0 'I350 Gigabit' if=eno1 drv=igb unused=igb_uio,vfio-pci
```

这里三段输出把「两张卡归 DPDK、一张卡归内核」的预期状态直接呈现：`drv=vfio-pci` 与 `-a` 的两个 BDF 对应，管理网卡带 `if=eno1 drv=igb` 与 `-b` 对应。若启动前这里显示 `drv=ixgbe` 而命令行却写了 `-a`，probe 阶段就会失败，说明设备声明与绑定状态脱节，须先用 `dpdk-devbind.py -b vfio-pci <BDF>` 完成绑定（完整命令见 04-05）。

### 5. 速查表

下表按场景给出设备声明的最小写法，devargs 键均以「需对照实际版本核验」为前提。

| 场景 | 声明写法 | 注意点 |
|---|---|---|
| 只接管两张卡 | 两条 `-a <BDF>` | 进入白名单模式 |
| 排除管理网卡 | `-b <BDF>` | 建议纯黑名单或纯白名单 |
| 双端口卡 | `-a ...:00.0 -a ...:00.1` | 每个 function 单独写 |
| 加 TAP 口 | `--vdev net_tap0,iface=tap0` | 键名由驱动定义 |
| 加 pcap 回放 | `--vdev net_pcap0,rx_pcap=...` | 见下方命令示例 |
| 加 memif 口 | `--vdev net_memif0,socket=...` | 需与对端一致 |
| 代表端口 | `-a <BDF>,representor=[0-3]` | 语法需核验 |
| 仅虚拟设备 | `--no-pci` 加若干 `--vdev` | 不要写 `-a` |
| 外挂 PMD | `-d /path/to/librte_pmd_xxx.so` | 检查库路径 |

下表汇总常见报错文本与最可能出错的设备声明项，完整映射见 04-08。

| 报错关键词 | 可疑项 | 处理方向 |
|---|---|---|
| `no Ethernet ports` | `-a` 缺失或 BDF 错误 | 用 devbind 核对 BDF |
| `unknown devargs` | devargs 键名 | 按驱动文档核对 |
| `probe failed` | 绑定驱动或 iova 模式 | 见 04-01 内存族 |
| `cannot open shared object` | `-d` 路径 | 检查 LD_LIBRARY_PATH |
| `representor` 相关 | 代表名语法 | 对照驱动版本核验 |
| `Blocked device` 意外出现 | allow 与 block 混用 | 改为单一模式 |

下面把多端口与虚拟设备混用的完整清单集中给出，便于复制改 BDF。

```bash
PHY0=0000:01:00.0
PHY1=0000:01:00.1
MGT=0000:02:00.0
ARGS="-a $PHY0 -a $PHY1 -b $MGT"
VDEV="--vdev net_pcap0,rx_pcap=/tmp/in.pcap,tx_pcap=/tmp/out.pcap"
testpmd -l 0-3 $ARGS $VDEV -- -i --portmask 0x7
```

### 6. 版本差异

本节只谈设备声明层「参数与语法」的版本变化。最显著的是 devargs 策略模型的演进：早期 `-a` / `-b` 只是简单的允许/阻止列表，较新版本在 `lib/eal/include/rte_devargs.h` 中引入了更通用的设备策略概念，允许在 devargs 里表达 allow 或 block 的意图，并支持按 `class=`、`name=` 等设备属性做通配匹配，而不必逐条写 PCI BDF。这类策略字段的具体键名、取值以及是否已在 23.11 LTS / 24.11 / master 中全面启用，需对照实际版本核验，定位在 `lib/eal/common/eal_common_devargs.c` 与 `rte_devargs.h`。若脚本里出现按名称匹配设备的写法却报解析失败，多半是目标版本尚未支持该策略。

其次是代表名与 switchdev 相关 devargs 的变化。`representor=` 的取值语法、以及 mlx5 一类驱动用于启用硬件卸载的键（形如 `dv_flow_en` 的开关在不同版本名字可能不同）在版本间调整较多，且强依赖内核与固件，本篇不列具体开关名，一律写「需对照实际版本核验」并指向 `drivers/net/` 下对应驱动的文档与 `lib/eal/common/eal_common_devargs.c`。`--vfio-vf-token` 是较晚加入的 VF 认证相关参数，是否在三个基准版本中都可用同样需核验。

第三类是工具脚本名本身。`dpdk-devbind.py` 在部分发行版与构建方式下可能以 `dpdk-devbind` 或带路径的脚本形式提供，`dpdk-pdump`、`dpdk-procinfo` 等也可能有 `dpdk-` 前缀与无前缀两种安装形态（见 04-05）；本篇为保持可读统一写带前缀的形式，实际调用名以 `usertools/` 与安装后的 `which` 结果为准。`--vdev` 的驱动名与 devargs 键随驱动演进而增删，例如 pcap 与 tap 的键相对稳定，而较新虚拟设备的键则变动频繁，最可靠的核验方式仍是在目标版本执行对应驱动的 help 或查阅 `drivers/net/` 下该驱动的源码注释。总线扫描与 probe 的实现从早期 `lib/eal/` 逐步拆分到 `drivers/bus/pci/` 与 `drivers/bus/vdev/`，但这属于模块归属变化（模块见 07-01），不影响本篇命令行写法。

### 7. 常见误用与调试

第一类误用是「写了 `-a` 却忘了核对绑定状态」。`-a` 只是让 EAL 允许某设备，并不会替你把网卡从内核驱动抢过来；若 `dpdk-devbind.py --status` 显示 `drv=ixgbe`，probe 必然失败或该端口不出现。正确顺序是先绑定、再 allow、再启动，三者缺一不可。第二类是把双端口卡只写一半：只 `-a 0000:01:00.0` 而漏掉 `.1`，结果 `show port info` 里少一个端口，`--portmask` 却按两个端口写，转发时出现端口不存在或统计恒为零。第三类是 allow 与 block 混用，尤其在同一条命令里既白名单又黑名单，某些版本下策略合并顺序不直观，表现为某张卡「明明 allow 了却被 blocked」；解决方法是改用纯白名单，把不需要的卡干脆不写。

第四类是 devargs 键张冠李戴。EAL 只拆解不透传校验，把 `rx_pcap` 写给 net_tap、把 `iface` 写给 net_pcap，都不会在参数解析阶段报错，而是到 probe 时才由驱动提示参数未知或直接忽略，现象是虚拟端口没建出来或参数没生效。排查时先确认设备名对应的驱动，再按该驱动文档逐键核对。第五类是代表名语法照抄跨驱动资料：不同厂商、不同内核版本下 `representor=[0-3]` 能否被接受、是否要先启用 switchdev 模式、端口编号如何生成都不一样，必须先在小规模环境用 `show port info all` 验证端口集合，再写进生产脚本。

第六类是 `--no-pci` 与 `-a` 同时出现。既然禁用了 PCI 扫描，`-a` 写的 BDF 就完全无效，若还期待物理端口出现就会得到 `no Ethernet ports found`；纯虚拟设备测试应只保留 `--vdev`。第七类是 `-d` 外挂驱动路径问题，报 `cannot open shared object file` 时按「文件是否存在 → 架构是否匹配 → 依赖库是否可解析 → LD_LIBRARY_PATH 是否包含目录」四步排查，必要时用 `ldd` 检查。

统一的设备层调试顺序建议如下。

```bash
dpdk-devbind.py --status
lspci -D | grep -i ethernet
testpmd -a 0000:01:00.0 -- -i
```

第一条确认驱动绑定归属，第二条拿到准确的 domain 格式 BDF（避免漏写 `0000:` 域段造成的地址不匹配），第三条用最小设备集启动并进入交互 CLI，再用 `show port info all` 验证端口数量与驱动名。若最小集正常而完整命令行异常，则问题一定出在新增的 devargs、代表名或 `--vdev` 上，按二分法逐条加回即可定位。错误现象到参数域的完整映射见 04-08，本篇不重复。

### 3. 逐项详解

**启动模式族**。`-i` 或 `--interactive` 让 testpmd 完成 EAL 初始化与端口配置后，不立即进入转发循环，而是停在 `testpmd>` 提示符上读取标准输入。这是手工调试的默认形态，几乎所有 `show` 与 `set` 命令都只在 interactive 下有意义；若未加 `-i`，进程会按 `--forward-mode` 指定的引擎直接开始转发，标准输入被忽略。参数解析在 `app/test-pmd/parameters.c`，CLI 主循环在 `app/test-pmd/testpmd.c` 与 `app/test-pmd/cmdline.c`。`--auto-start` 与 `-i` 可以共存，表示进入 CLI 的同时立即启动转发，适合想边跑边看统计的场景，此时无需手工敲 `start`。

`--tx-first` 指示在正式开始双向转发之前，先从各端口发出一批报文，常用于 txonly 或需要对端先有流量才能回环的拓扑，例如与流量发生器对接时打破「双方都在等对方先发」的死锁。它与 `--auto-start` 组合时行为需对照实际版本核验，启动参数解析在 `parameters.c`。`--cmdline-file` 是较新版本用于把运行时命令写进文件、由 testpmd 启动后自动顺序执行的入口，属于 04-07 脚本化的核心参数；其是否在当前三个基准版本中提供、以及是 testpmd 应用段参数还是 EAL 段参数，需对照实际版本核验，定位在 `app/test-pmd/parameters.c` 与 `app/test-pmd/cmdline.c`。`--stats-period N` 让进程每 N 秒自动打印一次端口统计，无需进入 CLI 手工敲 `show port stats all`，常用于无人值守的长时间测试，输出字段判读见 04-04。

**端口与核族**。`--nb-cores N` 指定参与转发循环的 lcore 数量，这些核来自 EAL 段 `-l` 启用的集合，通常主核之外各取一个；若 N 大于可用 lcore 数，启动会报错或转发核不足。`--nb-ports N` 声明期望使用的端口数，与 `--portmask`、`--portlist` 共同决定哪些端口进入转发拓扑。`--portmask 0x3` 以位掩码选中端口 0 与 1，与 EAL 段 `-a` 生成的端口编号对应（见 04-02），掩码位数超过实际端口数会导致端口不存在告警；`--portlist 0,1,2` 以显式列表达到同样目的，二者选其一，具体拼写与是否共存需对照实际版本核验。`--port-numa-config` 与 `--ring-numa-config` 用于把端口与 ring 显式绑定到指定 NUMA 节点，形状是端口或 ring 到节点的映射串，语法需对照实际版本核验；`--socket-num` 指定内存分配所在 socket，与 04-01 的 `--socket-mem` 配额必须一致，否则该节点无内存可用。这些参数全部解析于 `app/test-pmd/parameters.c`，端口编号的来源是 04-02 设备声明的结果。

**队列与内存族**。`--rxq` / `--txq` 设置每个端口的收发队列数，多队列通常配合 RSS 把流量分散到多个 lcore（原理见 06-06）；`--rxd` / `--txd` 设置描述符环深度，深度越大越能吸收突发但占用更多内存，两者都是性能调优的常见旋钮。`--mbcache` 设置 mempool 的 per-lcore 本地缓存大小，`--total-num-mbufs` 直接指定 mbuf 总数，`--mbuf-size` 指定单个 mbuf 数据区大小，三者共同决定内存池规模；若总量不足，运行时会看到 `rx_nombuf` 上涨（判读见 04-04）。`--max-pkt-len` 设定可接收的最大包长，超过该长度的巨型帧会被丢弃或需要开启分散接收，相关字段见 05-02、原理见 06-04。`--eth-peer` 为指定端口设置对端 MAC，供 `mac` 类转发引擎改写目的地址时使用；`--forward-mode` 直接给出初始转发引擎名，等价于启动后在 CLI 里执行 `set fwd`。`--enable-rx-cksum`、`--disable-crc-strip` 及 noisy 族参数属于卸载与扰动开关，名字与是否仍存在需对照实际版本核验，均在 `parameters.c`。

**运行时控制族**。`help` 打印当前版本注册的全部运行时命令及简要说明，是确认某条命令拼写的最可靠途径；部分版本支持 `help <命令>` 查看单条用法。`start` 启动转发引擎，`stop` 停止并把本轮统计归零，`quit` 结束进程并释放端口。要特别注意 `start` 与 `port start all` 不是一回事：后者只是让端口进入已启动的 ethdev 状态，前者才真正拉起收发循环，端口未先启动就 `start` 是常见报错来源。`show config` 一次性打印当前转发引擎、核数、端口数、队列数、burst 大小等汇总，是排错时第一眼要看的命令，能快速确认启动参数是否按预期落地。

**显示统计族**。`show port info all` 给出每个端口的驱动名、MAC、队列与 NUMA 归属，用来核对 04-02 的设备声明是否正确；`show port stats all` 打印收发包数、字节数、丢包与错误计数，字段含义与判读完整展开在 04-04，本篇只列命令形状；`clear port stats all` 把计数清零，便于在改变某个参数后重新计时对比。`show port xstats all` 打印驱动私有的扩展统计（如各队列的丢弃、校验和错误细分），可用项集合完全由 PMD 决定，需对照实际版本核验，源码在 `app/test-pmd/config.c` 与 `lib/ethdev/` 的相关接口附近，本篇不列扩展项字段表（字段见 05-04）。这些命令都可用 `all` 或具体端口编号 `X` 替换作用范围，例如 `show port stats 1`。

**参数调整族**。`set fwd <mode>` 选择转发引擎，模式全集与语义在 04-04；`set verbose N` 调整打印详细度，N 越大越啰嗦，调试期常用 1，压测期建议关掉以减少控制台开销；`set burst N` 设置每轮 `rte_eth_rx_burst` / `rte_eth_tx_burst` 的批量大小，是影响吞吐与时延的关键旋钮（原理见 06-04）；`set promisc all on` 或 `off` 开关混杂模式，抓包与非本机 MAC 流量测试时需要开启；`port config all` 带一长串子项用于批量配置队列、卸载、速率等，子命令形态需对照实际版本核验并参考 `help` 输出；`port start all` / `port stop all` 控制 ethdev 端口状态，修改多数 port 配置前都需要先 `port stop all`。`set nbport` / `set nbcore` 属于较老的动态调整命令，是否仍可用需对照实际版本核验。

### 4. 典型示例

下面演示一条典型的交互启动命令与紧随其后的一段 CLI 会话。EAL 段沿用 04-01 的最小集合，应用段用 `-i` 进入交互、`--nb-cores 2` 指定两个转发核、`--portmask 0x3` 选中两个端口、`--stats-period 0` 关闭周期打印以免干扰手工观察。

```bash
testpmd -l 0-2 --socket-mem 1024,0 --file-prefix pg0 \
  -a 0000:01:00.0 -a 0000:01:00.1 \
  -- -i --nb-cores 2 --portmask 0x3 --forward-mode io
```

进入提示符后依次输入以下命令。

```text
testpmd> show config
testpmd> set promisc all on
testpmd> set fwd io
testpmd> start
testpmd> show port stats all
testpmd> quit
```

示例输出，具体格式需对照实际版本核验：

```text
testpmd> show config
  Interactive-mode selected
  io packet forwarding - ports=2 cores=2 nb_pkts=32
  RX queues=1 TX queues=1 RX desc=512 TX desc=512
  port 0: RX queue 0 -> lcore 1
  port 1: RX queue 0 -> lcore 2
testpmd> set promisc all on
  Promiscuous mode: ON for all ports
testpmd> set fwd io
  Set io packet forwarding mode
testpmd> start
  io packet forwarding - CRC stripping disabled - packets/burst=32
  nb forwarding cores=2 - nb forwarding ports=2
testpmd> show port stats all
  ######################## NIC statistics for port 0  ########################
  RX-packets: 12004512  RX-missed: 0          RX-bytes:  768288768
  RX-errors: 0
  TX-packets: 12004512  TX-errors: 0          TX-bytes:  768288768
  ####################################################################
testpmd> quit
  Stopping port 0... done
  Stopping port 1... done
  Bye...
```

逐行判读说明如下。`show config` 的输出里 `io packet forwarding` 与 `ports=2 cores=2` 直接印证 `--forward-mode io`、`--portmask 0x3`、`--nb-cores 2` 三项启动参数已落地；`nb_pkts=32` 是默认 burst 大小，可用 `set burst` 调整，压测时通常会加大到 64 或更高再观察吞吐变化。`RX queues=1 TX queues=1` 与 `RX desc=512 TX desc=512` 是 `--rxq` / `--txq` / `--rxd` / `--txd` 的默认值，若曾显式指定，这里应同步变化，未变化就说明参数被新版本忽略或拼写有误。中间两行 `port 0: RX queue 0 -> lcore 1` 与 `port 1: RX queue 0 -> lcore 2` 是端口到转发核的映射，正常情况下应把两个端口分散到两个不同 lcore，若两个端口都挂到同一个核，说明 `--nb-cores` 未生效或 lcore 集合不足，单核将成为吞吐瓶颈。`set promisc all on` 回显 `Promiscuous mode: ON` 表示混杂模式开启成功，做非本机目的 MAC 的回环测试时这一项必须开，否则端口会直接丢弃不属于自己的帧。`set fwd io` 与 `start` 的两行回显确认引擎切换与转发循环启动；`start` 回显里再次出现的 `packets/burst=32` 与 `show config` 一致，是核对当前批大小的第二处证据。`show port stats all` 的统计块里，`RX-packets` 与 `TX-packets` 同为 12004512、`RX-missed: 0`、`RX-errors: 0`、`TX-errors: 0` 是健康回环的典型特征：io 引擎把收到的包原样从对端发出，因此两端口收发计数应基本相等，任何一侧长期为 0 说明接线、对端或端口映射有问题；`RX-missed` 非 0 表示描述符环或 PCI 带宽已到瓶颈开始丢包，`RX-bytes` 与 `TX-bytes` 相等说明没有分片或截断。字段的逐项判读与异常阈值在 04-04 展开。最后 `quit` 的三行回显显示两个端口被有序停止并打印 `Bye...`，属于正常退出；若这里出现 `port X failed to stop`，说明端口状态异常，需先 `port stop all` 再退出。整段没有 `Invalid port`、`Command not found` 或 `Not all ports are up` 一类的报错，可判定启动参数与运行时命令的链条全部打通。

再看一组用于确认本机运行时命令拼写的最小调用，它在跨版本迁移脚本时应当先跑一遍。

```bash
printf 'help\nquit\n' | testpmd -l 0-1 --no-huge --iova-mode=va -- -i
```

示例输出，具体格式需对照实际版本核验：

```text
testpmd> help
  help ............................ show this help
  start ........................... start packet forwarding
  stop ............................ stop packet forwarding
  quit ............................ quit the application
  show ............................ show various information
  set ............................. set parameters
  port ............................ configure ports
testpmd> quit
  Bye...
```

这里通过标准输入把 `help` 与 `quit` 喂给交互会话，演示了命令行式执行运行时命令的最朴素形态（完整脚本化方案见 04-07）。`help` 输出的是当前二进制实际注册的命令族，凡本篇表格里标注「需核验」的命令，都应以这里是否出现为准；脚本中若使用了目标版本没有的命令，会在此处暴露为 `Command not found`，从而在 CI 早期拦截兼容性问题。

### 6. 版本差异

本节只谈命令与参数拼写层面的版本变化。`--cmdline-file` 属于较晚引入的能力，用于把运行时命令写入文件自动执行；在 23.11 LTS、24.11 与 master 中是否可用、是 testpmd 应用段参数还是需要配合 EAL 段参数、以及文件内命令的语法限制，都需对照实际版本核验，定位在 `app/test-pmd/parameters.c` 与 `app/test-pmd/cmdline.c`。04-07 会以「需对照实际版本核验」为前提给出脚本化模板，本篇不预设其存在。

转发引擎名与 `set fwd` 可选值随版本增删较明显：早期有 `ieee1588`、`5tswap` 一类专用引擎，较新版本加入了 `shared-rxq`、`noisy` 等，某些老引擎可能已被移除或合并；具体集合由 `help` 与 `app/test-pmd/` 下的引擎注册表决定，本篇把模式全集交给 04-04 并结合版本差异说明，此处只强调「以目标版本 `help` 输出为准」。类似地，`--enable-rx-cksum`、`--disable-crc-strip` 这类卸载开关，随着 ethdev 卸载模型改为通过 `rte_eth_conf` 协商（字段见 05-04），在新版本可能已变为默认行为或改名，是否仍作为启动参数存在需核验。

端口配置命令 `port config all` 的子项在版本间变化很大，队列、卸载、速率限制、DCB 等子命令的拼写不断调整，因此本篇不逐条固化子项，只写「需对照实际版本核验并用 `help port` 查当前子项」。`--portlist`、`--port-numa-config`、`--ring-numa-config` 的引入时间不一，老版本只能用 `--portmask`，跨版本脚本应尽量使用最稳定的 `--portmask` 与 `--nb-cores`。`show port xstats` 是否提供、扩展项命名由 PMD 驱动版本决定，`start tx_first` 是否作为 `start` 的子形式存在也需核验。总之，testpmd 是 DPDK 中命令面最活跃的应用之一，最稳妥的工程习惯是把 `testpmd --help` 与交互态 `help` 的输出纳入 CI 的兼容性检查，而不是依赖任何静态清单。

### 7. 常见误用与调试

第一类误用是「没加 `-i` 却往标准输入敲命令」。进程按 `--forward-mode` 直接开始转发后，CLI 根本不存在，任何输入都被忽略，表现为「命令没反应」；若要交互，启动段必须带 `-i`。第二类是把 `start` 当成端口启动：端口尚未 `port start all`，直接 `start` 会得到端口未就绪的报错，正确顺序是先确认 `show port info all` 里端口状态，再 `port start all`，最后 `start`。第三类是端口掩码与实际端口数不匹配：`--portmask 0x3` 选了两个端口，但 04-02 的 `-a` 只声明了一张卡，`start` 时会报端口不存在；端口编号来自设备声明结果，两端必须对齐。

第四类是核数与端口数失衡：`--nb-cores 1` 配两个端口时，两个端口共用同一个转发核，吞吐上不去且统计看起来「一边快一边慢」，应把 `--nb-cores` 至少设到端口数或队列数。第五类是 `set verbose` 开得过大做压测，逐包打印把 CPU 耗在控制台 I/O 上，统计里表现为速率明显偏低，压测期应关掉或设为 0。第六类是 `set burst` 设得过大导致时延上升、或设得过小导致吞吐不足，调整前后都要用 `show port stats all` 对比，判读方法见 04-04。第七类是照抄旧脚本里的 `show fwd stats`、`set nbport` 等命令，新版本可能已改名或移除，报 `Command not found` 时先用 `help` 核对，再决定是否改用 `show config` 或启动参数替代。

统一的命令层调试顺序建议如下。

```bash
testpmd --help
printf 'help\nshow config\nquit\n' | testpmd -l 0-1 --no-huge --iova-mode=va -- -i
```

第一条确认应用段启动参数拼写，第二条用最小 EAL 环境进入交互态并核对 `help` 与 `show config` 的输出，二者分别覆盖第二层与第三层命令集合。若最小环境正常而完整命令行异常，问题一定出在新增的端口、队列、mbuf 或转发模式参数上，按二分法逐条加回即可定位。错误现象到参数域的完整映射见 04-08，本篇不重复。

## 04-04 testpmd 转发场景与统计命令

### 1. 本篇定位与覆盖范围

本篇是「testpmd 转发引擎、流量配置与统计命令」的唯一权威源，与 04-03 构成同一应用的上下篇：04-03 穷举启动参数与运行时命令的形状，本篇聚焦其中两组最关键的命令——决定「报文怎么被处理」的转发引擎族，以及决定「处理结果怎么看」的统计与清空族。源码同样位于 `app/test-pmd/`，转发模式的实现分散在该目录下以各引擎命名的源文件与统一的转发循环里，统计命令的实现主要在 `app/test-pmd/config.c`，底层统计项由 `lib/ethdev/` 的 ethdev 统计接口取得（模块见 07-01）。

本篇覆盖四类内容。第一类是转发引擎全集，即 `set fwd` 可接受的 io、mac、macswap、rxonly、txonly、flowgen、csum、icmpecho、noisy、5tswap 等模式（各名字是否在当前版本存在需对照实际版本核验），逐一给出「做什么、典型用途、需要哪些前置命令」。第二类是流量生成与整形命令，包括 `set txpkts`、`set txip`、`set txudp`、`set txether`、`set burst`、`start tx_first` 以及 flowgen 相关的速率参数。第三类是统计与清空命令，即 `show port stats all`、`show port stats X`、`show port xstats all`、`clear port stats all`、`clear port xstats all`，以及启动期的 `--stats-period`。第四类是统计输出判读，把 RX-packets / RX-missed / RX-errors / TX-packets / TX-errors / RX-bytes / TX-bytes / rx_nombuf 这类输出项逐一解释，给出正常值范围、异常特征与对应参数域。

### 3. 逐项详解

**转发引擎族**。`set fwd io` 是最常用的双向回环引擎，把某端口收到的报文原样从配对端口发出，两个端口互为收发对，配合背靠背接线或环回即可做零丢包吞吐测试。它要求至少两个端口且端口掩码成对，`start` 后 `show port stats all` 里两个端口的 RX-packets 与 TX-packets 应大致对称，任何一侧恒为 0 都说明接线或端口配对有误。`set fwd mac` 在 io 的基础上改写源 MAC 为本端口 MAC、目的 MAC 为对端 MAC，通常需要 `--eth-peer` 或 `set eth-peer` 指定对端地址，用于验证二层转发与 MAC 学习；`set fwd macswap` 只交换源目的 MAC，不改 IP，属于更轻量的二层改写，常用于快速压测。三者的实现都在 `app/test-pmd/` 下对应引擎源文件，本篇只描述可对命令行观察到的行为，改写动作的内部实现（原理见 06-04）不展开。

`set fwd rxonly` 只收包、不发包，收到后直接释放 mbuf，用于测量「纯收包」路径的上限与 CPU 占用，前提是对端有持续流量打入；此模式下本端 TX-packets 恒为 0 属正常，不要误判为故障。`set fwd txonly` 完全由本端构造并发送报文，不依赖收包，是发包限速、包长扫描、链路带宽打满测试的主力；报文内容由 `set txpkts`、`set txip`、`set txudp`、`set txether` 一组命令配置，缺省时会使用内置的默认报文模板。`set fwd flowgen` 生成具有多条五元组流的报文，配合 `--rxq` 多队列与 RSS 观察流分散是否均匀（原理见 06-06），速率与流数参数需对照实际版本核验。`set fwd csum` 用于验证硬件校验和卸载，`set fwd icmpecho` 回应 ICMP echo 请求以验证三层连通，`set fwd noisy` 在转发路径上附加额外内存访问以模拟干扰，`set fwd 5tswap` 交换五元组做流分类测试；后四个引擎是否存在、是否需要额外开关，均需对照实际版本核验，并以交互态 `help` 列出的引擎清单为准。

**流量整形族**。`set txpkts <len>` 设置 txonly 与 flowgen 生成报文的长度，接受单个长度如 `64`，也接受逗号分隔的多段长度以生成混合包长（例如 `64,128,256,512,1024`），具体语法与是否支持多段需对照实际版本核验。包长直接影响 pps 与 Gbps 的换算关系：同样 pps 下包越长带宽越高，做 RFC2544 类测试时这是首要变量（方法学见 08-01）。`set txip`、`set txudp`、`set txether` 分别设置生成报文的源目的 IP、UDP 端口与源 MAC，用于构造可被对端或交换机规则识别的流；这几个命令的名字与参数个数在版本间有差异，需对照实际版本核验，定位在 `app/test-pmd/cmdline.c` 与 `app/test-pmd/txonly.c` 附近。`set burst N` 设置每轮收发的批量大小，N 越大单次调用处理包数越多、摊销开销越低，但时延与缓存压力上升；它与 04-03 启动段看到的 `nb_pkts` 是同一量，调整后可用 `show config` 核对。`start tx_first` 让 txonly 类引擎在正式循环前先发一批报文，用于打破两端互等的死锁，是否作为 `start` 的子形式存在需核验。flowgen 的速率、流数、包长分布参数在版本间差异较大，本篇不列具体键名，统一写「需对照实际版本核验」。

**统计与清空族**。`show port stats all` 打印所有端口的基础统计，作用范围也可换成具体端口号如 `show port stats 0`；`clear port stats all` 把这些计数清零，常用于「改一个参数、跑固定时长、再读差值」的对比测试，注意 `stop` 在部分版本也会顺带复位统计，若要保留历史值应先读后停。`show port xstats all` 打印驱动私有的扩展统计，例如各队列丢包、校验和错误、Rx 中断次数等，可用项集合完全由 PMD 决定，需对照实际版本核验，源码在 `app/test-pmd/config.c` 调用 `lib/ethdev/` 的 xstats 接口处；`clear port xstats all` 是否提供同样需核验。`--stats-period N` 是 04-03 的启动段参数，让进程每 N 秒自动打印一次统计，等价于无人值守地反复执行 `show port stats all`，字段判读与手工执行完全一致。

**统计输出判读族**。基础统计块常见项的含义如下：`RX-packets` 与 `TX-packets` 是本端口累计收发包数，`RX-bytes` 与 `TX-bytes` 是累计字节数，四者在稳态下应随时间单调递增，若长时间不动说明链路无流量或转发循环未启动。`RX-missed`（部分版本显示 `RX-missed` 或 `imissed`）表示因描述符环满或 PCI 背压导致的收包丢弃，健康状态应为 0，一旦持续增长说明收包能力已到瓶颈，应回头检查 `--rxd`、`--rxq`、`--nb-cores` 与 `set burst`（见 04-03）。`RX-errors` 与 `TX-errors` 是错误帧计数，正常为 0，非 0 通常指向 CRC、包长或对端配置问题。`rx_nombuf`（不同版本位置可能不同，需核验）表示因 mempool 无可用 mbuf 而丢弃的收包，非 0 时说明 `--total-num-mbufs` 或 `--socket-mem` 不足（见 04-01、04-03）。速率类信息在部分版本由 `--stats-period` 打印为 `pps` 与 `Gbps` 两列，判读时要注意区分「线速百分比」与「绝对吞吐」，以及小包场景下 pps 先到顶、大包场景下带宽先到顶的差别（方法学见 08-01）。本篇不列 `rte_eth_stats` 结构体字段表（字段见 05-04），只把命令行输出项与可观察结论对应起来。

### 4. 典型示例

下面演示一次「io 回环 + 周期统计 + 手工判读」的完整会话。EAL 段与 04-03 示例相同，应用段用 `--auto-start` 与 `--stats-period 5` 让进程启动即转发并每 5 秒打印一次统计。

```bash
testpmd -l 0-2 --socket-mem 1024,0 --file-prefix pg0 \
  -a 0000:01:00.0 -a 0000:01:00.1 \
  -- --auto-start --forward-mode io --portmask 0x3 --nb-cores 2 --stats-period 5
```

另开一个交互会话做手工核对，输入以下命令。

```text
testpmd> show config
testpmd> show port stats all
testpmd> clear port stats all
testpmd> show port stats 0
```

示例输出，具体格式需对照实际版本核验：

```text
  ######################## NIC statistics for port 0  ########################
  RX-packets: 24880128  RX-missed: 0          RX-bytes:  1592328192
  RX-errors: 0
  TX-packets: 24880128  TX-errors: 0          TX-bytes:  1592328192
  ######################## NIC statistics for port 1  ########################
  RX-packets: 24880128  RX-missed: 0          RX-bytes:  1592328192
  RX-errors: 0
  TX-packets: 24880128  TX-errors: 0          TX-bytes:  1592328192
  ####################################################################
testpmd> clear port stats all
  Statistics cleared for all ports
testpmd> show port stats 0
  ######################## NIC statistics for port 0  ########################
  RX-packets: 1024       RX-missed: 0          RX-bytes:  65536
  RX-errors: 0
  TX-packets: 1024       TX-errors: 0          TX-bytes:  65536
  ####################################################################
```

逐行判读说明如下。第一段两个端口的统计块完全对称：port 0 与 port 1 的 `RX-packets` 同为 24880128、`TX-packets` 同为 24880128、`RX-bytes` 与 `TX-bytes` 同为 1592328192，这是 io 引擎背靠背回环最健康的形态——每个端口收到的包都被发到对端，对端收到后再发回来，因此两端四个计数同步增长。字节数除以包数等于 64 字节，说明链路上跑的是 64 字节小包，与 `set txpkts 64` 或默认最小帧一致；若这个比值明显偏大，说明对端在发大包或存在巨型帧，做吞吐换算时要按实际平均包长重算。`RX-missed: 0` 与 `RX-errors: 0`、`TX-errors: 0` 表明当前速率下描述符环没有溢出、没有错误帧，即尚未触达丢包点；压测继续加流时，第一个开始非零的通常就是 `RX-missed`，它出现的位置就是该配置下的零丢包吞吐上限（方法学见 08-01）。`clear port stats all` 回显 `Statistics cleared for all ports`，确认计数已复位；紧接着 `show port stats 0` 只显示 1024 包、65536 字节这一小段增量，正是清零后到这条命令执行之间新产生的流量，这个「清零 → 等待固定时长 → 读差值」的三步法，是把累计计数换算成瞬时速率的标准做法，比直接看累计值可靠得多。若清零后计数长时间保持 0，说明转发循环已停或对端已停发，需回到 `start` 与 `show config` 检查引擎状态。需特别注意，不同版本可能把 mempool 耗尽显示为独立的 `rx_nombuf` 项或并入 `RX-missed`，也可能把丢包拆到 xstats 的各队列项里，因此「统计块没有丢包」并不总等于零丢包，压测时应再跑一次 `show port xstats all` 交叉确认，该项是否可用需对照实际版本核验。

再看一组 txonly 发包场景的命令与输出形态，用于说明「只发不收」时统计的非对称性。

```text
testpmd> set fwd txonly
testpmd> set txpkts 128
testpmd> set burst 64
testpmd> clear port stats all
testpmd> start
testpmd> show port stats all
```

示例输出，具体格式需对照实际版本核验：

```text
  ######################## NIC statistics for port 0  ########################
  RX-packets: 0          RX-missed: 0          RX-bytes:  0
  RX-errors: 0
  TX-packets: 8388608    TX-errors: 0          TX-bytes:  1073741824
  ####################################################################
```

这里 `RX-packets` 与 `RX-bytes` 恒为 0、`TX-packets` 持续增长，是 txonly 引擎的正常特征，不应误判为收包故障；`TX-bytes` 除以 `TX-packets` 等于 128，印证 `set txpkts 128` 已生效。若这里 TX 计数也为 0，则通常是端口未 `start`、对端未接或对端把流给滤掉了，应按 04-03 的顺序从 `show config` 与 `show port info all` 查起。

### 5. 速查表

下表按测试目标给出引擎与流量参数组合。

| 测试目标 | 引擎与命令 | 关键判读项 |
|---|---|---|
| 双向零丢包吞吐 | `set fwd io` 加 `start` | 两端计数对称 |
| 纯收包上限 | `set fwd rxonly` | RX-missed 是否增长 |
| 纯发包限速 | `set fwd txonly` 加 `set txpkts` | TX-packets 增量 |
| 多流 RSS 分散 | `set fwd flowgen` 加 `--rxq 4` | xstats 各队列 |
| 二层改写 | `set fwd mac` 加 `--eth-peer` | 对端是否收到 |
| 校验和卸载 | `set fwd csum` | RX-errors 与 xstats |
| 混合包长 | `set txpkts 64,128,512` 需核验 | 平均包长换算 |
| 固定窗口速率 | `clear` 后等待再 `show` | 差值除以时长 |

下表把统计输出项与最可能相关的参数域对应起来，用于从异常值反查配置。完整错误映射见 04-08。

| 输出项异常 | 含义 | 应回查的参数域 |
|---|---|---|
| `RX-missed` 增长 | 收包环溢出 | `--rxd` `--rxq` `--nb-cores` |
| `rx_nombuf` 增长 | mbuf 耗尽 | `--total-num-mbufs` `--socket-mem` |
| `RX-errors` 非零 | 错误帧 | `--max-pkt-len` CRC 开关 |
| 单侧计数恒 0 | 接线或配对 | `--portmask` 端口映射 |
| 两端计数不对称 | 引擎或过滤 | `set fwd` 混杂模式 |
| pps 偏低 | 批量或核数 | `set burst` `--nb-cores` |

下面把「清零 → 定时 → 读差值」的速率换算脚本骨架集中列出，完整自动化方案见 04-07。

```python
before = read_stats_via_telemetry("/ethdev/stats,0")
time.sleep(10)
after = read_stats_via_telemetry("/ethdev/stats,0")
pps = (after["ipackets"] - before["ipackets"]) / 10
print("RX pps =", pps)
```

### 6. 版本差异

本节聚焦转发引擎与统计项的版本变化。引擎名集合是 testpmd 中变动最频繁的部分之一：`io`、`mac`、`rxonly`、`txonly`、`flowgen` 长期稳定，`macswap`、`csum`、`icmpecho` 在多数版本可用，而 `5tswap`、`noisy`、`shared-rxq`、`ieee1588` 一类专用引擎在不同分支上可能被加入、改名或移除；`noisy` 引擎还带一组以 `--noisy-` 为前缀的启动参数，其拼写与数量随版本变化明显。因此本篇表格里的引擎清单是「功能族框架」，具体可用集合必须以目标版本交互态 `help` 与 `app/test-pmd/` 下的引擎注册为准，凡标注「需核验」者不得直接写进生产脚本。

统计侧的变化主要有三处。一是基础统计项的命名与呈现：不同版本可能把 mempool 耗尽显示为独立 `rx_nombuf` 行、并入 `RX-missed`，或只在 xstats 里给出队列级细分；`RX-missed` 与 `imissed`、`RX-errors` 与 `ierrors` 这类长短名并存的情况也常见，需对照实际版本核验，定位在 `app/test-pmd/config.c` 的打印逻辑与 `lib/ethdev/` 的统计接口。二是 xstats 项集合完全由 PMD 驱动决定，同一块网卡在不同驱动版本下扩展项名字可能不同，任何依赖具体 xstats 名的脚本都应先枚举再取值。三是周期统计 `--stats-period` 的输出格式，早期只打印基础累计计数，较新版本可能附带 pps 与线速百分比，字段是否出现需核验。

流量生成命令同样有演进：`set txpkts` 的多段包长语法、`set txip` / `set txudp` / `set txether` 的参数形式、flowgen 的速率与流数键名，在 23.11 LTS、24.11 与 master 之间可能并不一致，定位在 `app/test-pmd/cmdline.c` 与各引擎源文件。校验和卸载相关的 `--enable-rx-cksum`、`--disable-crc-strip` 等启动开关，随着 ethdev 卸载模型统一（字段见 05-04），可能退化为默认行为或改名。工程上的一致建议是：把 `help`、`show port stats all` 的真实字段集、`show port xstats all` 的真实项集合，作为每个目标版本上线前必须采集的三份基线，再据此固化脚本里的引擎名与统计键，而不是跨版本照抄任何静态表。

### 7. 常见误用与调试

第一类误用是把 rxonly / txonly 的非对称统计当成故障。rxonly 下 TX 恒为 0、txonly 下 RX 恒为 0 都是设计行为，误判后往往白白去查接线；判断依据是 `show config` 里的当前引擎名，而非单看某一侧计数。第二类是不清零就读累计值：累计计数从进程启动算起，混入了配置调试期的低速流量，直接拿去除以时长会得到偏低的速率；正确做法是 `clear port stats all` 后等待固定窗口再读差值，如第 5 节脚本所示。第三类是只看基础统计就下「零丢包」结论：`RX-missed` 为 0 并不总意味着没有丢包，mempool 耗尽或队列级丢弃可能只出现在 xstats，压测必须双通道交叉确认。

第四类是包长与速率换算错位：用 64 字节小包跑出的 pps 很高但带宽未必高，用 1500 字节大包则相反，把两者直接比较会得出错误结论；判读时先用 `RX-bytes / RX-packets` 求出实际平均包长，再换算 pps 与 Gbps，方法学见 08-01。第五类是 flowgen 或 txonly 未配流量参数就用默认模板，导致对端规则不匹配、流被丢弃，表现为 TX 有计数但对端收不到；应显式用 `set txpkts`、`set txip`、`set txudp` 等构造可被识别的流（具体命令需核验）。第六类是 `set burst` 与 `--rxd` 搭配失衡，burst 大于描述符环深度或远大于核数时，容易看到 `RX-missed` 增长，应按「核数 → 队列数 → 环深度 → burst」顺序逐项调。

第七类是多队列 RSS 场景只看总统计：总吞吐正常但各队列严重不均时，单核已成为隐性瓶颈，需借助 `show port xstats all` 的队列级项或 telemetry 指标（见 04-05、04-07）定位，原理见 06-06。统一的统计层调试顺序建议如下。

```text
show config
show port stats all
show port xstats all
clear port stats all
show port stats all
```

先用 `show config` 确认引擎与核数端口数，再读基础统计看收发与丢包，再读 xstats 看队列级细分，随后清零并隔一小段时间复读以确认计数确实在增长。四条命令构成最小判读闭环；若闭环里任何一步的输出与预期不符，按第 5 节第二张表反查参数域即可。错误现象到参数域的完整映射见 04-08，本篇不重复。

## 04-05 诊断与观测工具命令

### 1. 本篇定位与覆盖范围

本篇是 DPDK `dpdk-*` 诊断与观测工具命令的唯一权威源，覆盖 `dpdk-procinfo`、`dpdk-pdump`、`dpdk-telemetry`、`dpdk-hugepages`、`dpdk-devbind` 五个随发行版提供的工具。与前面四篇不同，本篇的对象既有 C 编写的独立进程，也有 Python 编写的用户态脚本，因此「命令形态」差异较大：有的需要先解析 EAL 参数再用 `--` 分隔应用参数，有的则是纯 Python 命令行选项。理解这一点是正确使用它们的前提。

按工作方式可把这五个工具分成两类。第一类是 secondary 进程类，包括 `dpdk-procinfo` 与 `dpdk-pdump`。它们本身是基于 EAL 的独立进程，启动时必须先经过 `rte_eal_init()`，以 `--proc-type=secondary` 的角色附着到某个正在运行的 primary 进程所创建的共享内存上，再读取状态或复制报文；因此它们的命令行同样分成 `--` 之前的 EAL 段与之后的应用段，且 `--file-prefix` 必须与 primary 完全一致（该参数见 04-01），否则会找不到共享内存。第二类是 Python 脚本类，包括 `usertools/dpdk-devbind.py`、`usertools/dpdk-hugepages.py` 与作为遥测客户端的 `usertools/dpdk-telemetry.py`，它们不经过 EAL 初始化，直接以命令行选项操作 sysfs、hugetlbfs 或 unix socket。

源码与目录定位如下：secondary 类主程序在 `app/proc-info/main.c` 与 `app/pdump/main.c`，pdump 的抓包能力由 `lib/pdump/` 提供，要求 primary 侧编译时启用了 pdump 库；遥测服务端在 `lib/telemetry/`，交互客户端脚本在 `usertools/dpdk-telemetry.py`；大页配置脚本在 `usertools/dpdk-hugepages.py`；设备绑定脚本在 `usertools/dpdk-devbind.py`。这些脚本在较老版本曾位于 `tools/` 目录，新版本统一迁到 `usertools/`，具体安装路径与是否带 `dpdk-` 前缀需对照实际版本核验。

去重铁律在本篇同样适用：只讲「命令怎么写、输出怎么读、前置条件是什么」，不讲 ethdev 统计结构体、mempool 或 ring 的字段定义（字段见 05-04、05-06、05-07），不讲 telemetry 库的内部注册与序列化机制（模块见 07-12），也不讲多进程共享内存通信的原理（原理见 06-10）。例如 `dpdk-procinfo --show-mempool` 打印出的对象池信息，本篇只解释命令行里每一列大致对应什么、异常时该回查哪个参数，不列 `rte_mempool` 成员。遥测 socket 的 Python 读取脚本属于 04-07 的自动化集成，本篇只讲交互客户端的用法与输出形状。凡是选项名、子命令名、socket 路径在 23.11 LTS / 24.11 / master 中不确定的，一律写「需对照实际版本核验」并给出上述目录路径。

### 3. 逐项详解

**dpdk-procinfo**。它是附着到 primary 的 secondary 进程，读取 primary 创建的共享内存中的端口、mempool、ring 等状态，用于「不重启业务进程就能看内部状态」。命令行形如 `dpdk-procinfo --file-prefix pg0 -- --stats`，其中 `--` 之前是 EAL 段：`--file-prefix` 必须与 primary 一致，`--proc-type` 通常可省略，因为 procinfo 默认以 secondary 角色运行；若 primary 加了 `--no-shconf`（见 04-01），则任何 secondary 都无法附着，procinfo 会报共享内存初始化失败。`--` 之后是应用段：`--stats` 打印端口基础收发统计，与 04-04 的 `show port stats all` 字段同源但视角不同；`--xstats` 打印驱动私有扩展统计；`--show-port`、`--show-mempool`、`--show-ring` 分别打印端口配置、对象池与 ring 概要；`--info`、`--collectd-format`、`--host-id`、`--iterations`、`-m` 等是否可用、拼写如何需对照实际版本核验，定位在 `app/proc-info/main.c` 的参数解析部分。它是只读观测，不会改变 primary 的转发状态，因此在生产环境排查时比重启更安全。主程序调用 `rte_eth_stats_get` 一类接口取数（模块见 07-01），本篇不展开其字段表（字段见 05-04）。

**dpdk-pdump**。它同样以 secondary 角色附着到 primary，但目的是把指定端口、指定队列上收发的报文复制一份写到 pcap 文件，实现旁路抓包。核心应用段参数是 `--pdump`，其值是一个逗号分隔的配置串，典型形如 `port=0,queue=*,rx-dev=/tmp/rx.pcap`，表示把端口 0 所有队列的收包写到 `/tmp/rx.pcap`；把 `rx-dev` 换成 `tx-dev` 即抓发包，`port` 与 `queue` 也可用具体编号或 `*` 通配。配置串里还可带 `ring-size`、`mbuf-size`、`total-num-mbufs` 一类控制抓包缓冲的键，具体键名与默认值需对照实际版本核验，定位在 `app/pdump/main.c` 与 `lib/pdump/rte_pdump.c`。重要前置条件是 primary 侧必须编译并启用了 pdump 库，否则 secondary 侧会报无法初始化 pdump 或抓不到任何包；pdump 通过多进程消息请求 primary 在收发路径上挂复制回调（原理见 06-10），本篇只强调「命令怎么给、前置库要开、输出 pcap 落在哪」。抓包会额外消耗 CPU 与内存，生产环境只宜短时开启。

**dpdk-telemetry**。这里指作为客户端的 `usertools/dpdk-telemetry.py`，它连接到 primary 进程由 `lib/telemetry/` 创建的 unix domain socket，以文本命令查询运行期指标。启动交互客户端后，输入 `/` 可列出当前注册的全部命令，输入形如 `/ethdev/stats,0` 的命令读取端口 0 的统计，输入 `/eal/lcores` 查询 lcore 状态，输入 `/info` 查询版本与进程名，输入 `/help` 或 `/` 查看命令清单；上述命令名与返回 JSON 的字段集合在不同版本差异明显，需对照实际版本核验，以 `lib/telemetry/` 下的命令注册与 `dpdk-telemetry.py` 的客户端实现为准。socket 路径通常位于 `/var/run/dpdk/<file-prefix>/telemetry` 一类位置，前缀受 `--file-prefix` 影响（见 04-01），具体路径需核验；若 primary 启动时加了 `--no-telemetry`（见 04-01），端点根本不存在，客户端会报连接拒绝。客户端返回的是 JSON 对象，便于脚本解析，Python 侧读取的完整示例见 04-07，本篇只讲交互用法。遥测库本身的注册与编码机制（模块见 07-12）不在本篇展开。

**dpdk-hugepages**。它是配置大页的 Python 脚本，替代手工写 `/proc/sys/vm/nr_hugepages` 与 `mount -t hugetlbfs`。`--show` 打印当前各 NUMA 节点、各页大小的预留与挂载状态，是配置前后都要跑的核对命令；`-s SZ` 或 `--setup SZ` 按指定大小预留并挂载大页，`--pagesize 2M` 或 `1G` 选择页大小，`--node N` 把预留限定在特定 NUMA 节点；`--clear` 清除预留，`--mount` 与 `--unmount` 只处理挂载点而不动预留计数。选项的具体长短名组合、以及 `-s` 的单位在不同版本可能不同，需对照实际版本核验，定位在 `usertools/dpdk-hugepages.py`。它与 04-01 的 `--socket-mem`、`--huge-dir` 直接呼应：脚本负责「系统里有没有大页、挂在哪」，EAL 参数负责「进程用多少、从哪个目录取」，两者必须一致，否则启动会报大页不足。脚本通常需要 root 权限，容器中挂载点路径与宿主机不同，务必用 `--show` 复核。

**dpdk-devbind**。它是网卡驱动绑定的 Python 脚本，是 04-02 设备声明得以生效的前置步骤。`-s` 或 `--status` 按「使用 DPDK 兼容驱动」「使用内核驱动」「其他设备」分段列出每个 BDF 的驱动归属、内核网口名与可用驱动；`-b DRIVER BDF` 把指定 BDF 绑定到 `vfio-pci`、`uio_pci_generic` 或 `igb_uio` 之一；`-u BDF` 解绑设备使其回到无驱动状态；`--force` 允许修改当前正被内核驱动占用、有网口名的设备，风险较高，使用前必须确认该网卡不是管理网口；`--status-dev` 按设备类型过滤显示。选项名与可用驱动列表需对照实际版本核验，定位在 `usertools/dpdk-devbind.py`。绑定顺序是「先绑定、再在 04-02 用 `-a` 允许、最后启动应用」，任何一步缺失都会导致 `no Ethernet ports found`（见 04-08）。

逐行判读说明如下。`dpdk-devbind.py --status` 的第一段 `Network devices using DPDK-compatible driver` 列出两张 `drv=vfio-pci` 的网卡，它们的 BDF 应与 04-02 的两条 `-a` 完全一致；第二段 `Network devices using kernel driver` 里带 `if=eno1 drv=igb` 的管理网卡仍归内核，说明绑定操作没有误伤管理口，若这里反而显示 `drv=vfio-pci`，就必须立刻解绑，否则 ssh 可能中断。`dpdk-hugepages.py --show` 的 `node0: 2M 512 pages total, 512 free` 表示 socket 0 预留且空闲 512 个 2 MB 页、合计约 1 GB，与 04-01 的 `--socket-mem 1024,0` 配额吻合；`node1` 全为 0 也符合配额第二项为 0 的设定；`mounted /dev/hugepages` 印证 `--huge-dir /dev/hugepages` 指向了正确挂载点。这三行是判断「大页够不够、挂没挂对」最直接的依据，若 `free` 远小于配额，启动或运行期就会出现大页不足或 mempool 分配失败。`dpdk-procinfo` 附着成功后打印的端口统计块里 `RX-packets` 与 `TX-packets` 同为 48231104、`RX-missed: 0`、`TX-errors: 0`，与 04-04 判读口径一致，说明 primary 正处于健康回环且计数随时间增长，procinfo 作为 secondary 读到的正是同一份共享统计；若这里全为 0 而 primary 侧 `show port stats all` 有数，说明 `--file-prefix` 不一致导致附着到了另一个空实例。最后 mempool 段落 `size=8192, available=7936, in_use=256` 显示对象池总量与当前占用，`available` 长期接近 0 是 `rx_nombuf` 增长的前兆，应回查 `--total-num-mbufs` 与 `--socket-mem`（见 04-01、04-03）；本篇只列命令输出项的含义，不展开 `rte_mempool` 字段表（字段见 05-03）。整段没有 `cannot init`、`failed to attach` 或 `Permission denied` 一类报错，可判定绑定、大页、附着三条链路都通。

### 6. 版本差异

本节只谈工具名、目录与选项层面的版本变化。最直观的是目录迁移：`dpdk-devbind.py`、`dpdk-hugepages.py` 等用户脚本在较老版本位于源码树 `tools/`，新版本统一迁到 `usertools/`；安装到系统后的可执行名可能带 `dpdk-` 前缀，也可能不带，甚至以 Python 模块方式调用，因此本篇统一写带前缀形式，实际以 `which dpdk-devbind.py` 与安装清单为准，需对照实际版本核验。

其次是 secondary 类工具的应用段子命令变化。`dpdk-procinfo` 早期以 `-m` / `--misc` 打印杂项、以 `--stats` / `--xstats` 打印端口统计，较新版本可能加入 `--show-port`、`--show-mempool`、`--show-ring`、`--show-crypto`、`--collectd-format`、`--host-id`、`--iterations` 等，也有把某些子命令改名或合并的情况；具体集合以目标版本 `dpdk-procinfo -- --help` 输出为准，源码在 `app/proc-info/main.c`。`dpdk-pdump` 的 `--pdump` 配置串里可用键（如 `ring-size`、`mbuf-size`、`total-num-mbufs`）与默认值在版本间也有调整，定位在 `app/pdump/main.c`。

第三类是遥测协议的演进。`lib/telemetry/` 早期版本使用基于 JSON 对象的 v1 协议，客户端发送形如 `{"action": ...}` 的请求；较新版本改用 v2 的文本命令风格，即以 `/命令,参数` 的形式查询，返回统一 JSON。两种协议对应的客户端脚本用法、命令名与 socket 文件名都不同，本篇示例采用 v2 风格，但 v2 是否在 23.11 LTS / 24.11 / master 全面启用、以及 `/ethdev/stats,0` 这类命令的确切拼写，均需对照实际版本核验。`/` 返回的命令清单、`/ethdev/stats` 的 JSON 键名（如 `ipackets` 与 `rx_nombuf` 是否出现）同样由服务端注册决定，脚本必须容错。

最后是输出格式与权限细节：`dpdk-hugepages.py --show` 的排版、`dpdk-devbind.py --status` 的分段标题、以及容器里默认 socket 目录的差异都较常见。工程上的一致做法是把「工具 `--help` 输出」「`--show` 基线」「遥测 `/` 命令清单」作为每个目标版本上线前采集的三份基线，再固化自动化脚本里的命令与键名，而不是跨版本照抄静态表。

### 7. 常见误用与调试

第一类误用是 secondary 忘记带 `--file-prefix`。`dpdk-procinfo` 与 `dpdk-pdump` 默认是 secondary，若 primary 用了 `--file-prefix pg0` 而观测命令没带，会附着到一个不存在或空的共享内存实例，表现为统计全 0 或 `failed to attach`；两端前缀必须逐字符一致，这是本篇最高频的故障。第二类是 primary 加了 `--no-shconf`（见 04-01），共享配置文件被禁，任何 secondary 都无法附着，报错看似内存问题，实为进程族配置，去掉该开关即可。第三类是 pdump 前置库未启用：primary 编译时没有 `lib/pdump/` 支持，secondary 侧 `--pdump` 不报错但 pcap 里一个包都没有，须确认构建选项后重新编译。

第四类是遥测端点连不上。原因通常有三：`--no-telemetry` 被加上、socket 路径随 `--file-prefix` 变化却按默认路径去找、或权限不允许访问 `/var/run/dpdk/`；用 `dpdk-telemetry.py` 打印的 `Connecting to ...` 行核对路径，用 `ls -l` 确认 socket 存在与权限。第五类是 `dpdk-devbind.py -b` 误绑管理口：带 `if=eno1` 的网卡一旦被绑到 vfio-pci，ssh 会立即断开，因此 `--force` 必须慎用，绑定前先用 `--status` 确认 BDF 与网口名对应关系。第六类是 `dpdk-hugepages.py` 在非 root 或容器内执行，预留失败或挂载点路径与 EAL 的 `--huge-dir` 不一致，表现为脚本 `--show` 有预留、启动却报大页不足；处理办法是统一容器挂载点与 `--huge-dir`，并用 `--show` 复核。

第七类是把 procinfo 当成可写工具：它是只读观测，试图用它的输出去「修改」配置是方向性错误，改配置应回到 04-01 至 04-03 的启动参数与 CLI 命令。统一的诊断顺序建议如下。

```bash
dpdk-hugepages.py --show
dpdk-devbind.py --status
dpdk-procinfo --file-prefix pg0 -- --help
dpdk-procinfo --file-prefix pg0 -- --stats
```

先看系统侧的大页与绑定是否满足前置条件，再用 `--help` 确认本机 procinfo 的子命令拼写，最后附着读取统计。若前三步都正常而 `--stats` 全 0，问题一定在 primary 的转发状态或前缀一致性上，回到 04-04 与 04-01 排查。错误现象到参数域的完整映射见 04-08，本篇不重复。

## 04-06 日志、trace 与调试命令

### 1. 本篇定位与覆盖范围

本篇是 DPDK「日志、trace 与调试命令」的唯一权威源，承接 04-01 中只给了一个入口形状的 `--log-level`，把日志分域、级别枚举、输出控制与 trace 相关开关完整展开。DPDK 的日志与 trace 是两套互补的可观测手段：日志是离散的、按级别过滤的文本事件，用于启动期与运行期的状态提示与错误定位；trace 是低开销的、按点采样的事件流，用于分析转发路径上的时序与耗时（原理见 06-xx）。本篇只讲「怎么开、怎么配、输出到哪、怎么读」，不展开任何内部机制。

### 3. 逐项详解

**日志级别族**。`rte_log` 定义了从 `RTE_LOG_EMERG` 到 `RTE_LOG_DEBUG` 的八级枚举（见上表），数值越小越严重，级别过滤的语义是「只输出严重程度不低于设定值的消息」，换言之设定值越大、输出的日志越详细。`--log-level` 接受两种形态：一种是全局数字，例如 `--log-level=8` 等价于全局开到 DEBUG；另一种是 `域名:级别` 的分域写法，例如 `--log-level=lib.eal:debug` 只把 EAL 库开到调试、`--log-level=pmd.net.mlx5:info` 把某个 PMD 设为信息级。分域写法可重复出现多次，用于对不同库、不同驱动分别设级别；同时出现全局与分域时，分域通常覆盖该域的全局值，优先级细节需对照实际版本核验，定位在 `lib/log/log.c` 与 `lib/eal/common/eal_common_options.c`。级别名与数值的对应、以及是否接受 `warning` 与 `warn` 一类别名，均以 `lib/eal/include/rte_log.h` 与本机 `--help` 为准。

`--log-level=help` 是一个特殊值，它让 EAL 打印当前构建里所有已注册的日志域后退出，不启动应用。这是写分域参数时唯一可靠的域名来源：新版本普遍采用点分小写域名，如 `lib.eal`、`lib.ethdev`、`lib.mempool`、`pmd.net.ixgbe`、`pmd.net.mlx5`，以及供应用自定义使用的 `user1` 至 `user8`；较老版本可能使用 `EAL`、`PMD`、`MALLOC` 一类大写短名，二者是否并存需对照实际版本核验。日志域由各库与驱动通过 `rte_log_register()` 一类接口注册（模块见 07-xx），本篇只要求读者会用 `help` 查到域名，不展开注册机制。运行期若需在不重启的情况下调整级别，可调用 `rte_log_set_level()` 或按模式匹配的 `rte_log_set_level_pattern()`，这两个接口的名字与签名需对照实际版本核验，声明在 `lib/eal/include/rte_log.h`；本篇只点出「存在运行期改级别的入口」，不展开其内部字段（字段见 05-07）。

**日志输出族**。`--syslog` 控制日志是否转发到系统日志，较新版本接受 `auto`、`always`、`never` 一类枚举值，`auto` 通常在标准输出不是终端时自动转发，`never` 强制只写 stderr，具体取值集合与默认行为需对照实际版本核验，解析在 `eal_common_options.c`。`--log-timestamp` 为每行日志加时间戳，便于把 DPDK 日志与内核日志、外部流量发生器日志对齐到同一时间线，排查「某一刻突然丢包」这类时序问题时很有用；它只影响输出格式，不影响级别过滤。`--log-color` 控制终端彩色输出，属于较新的可选项，是否提供、是否默认开启需对照实际版本核验。三者都是纯输出侧开关，与日志级别、日志域是正交关系：先由级别与域决定「哪些消息产生」，再由这些开关决定「以什么形式、写到哪里」。

**trace 开关族**。`--trace=<regex>` 以正则串选择要启用的 trace 点，例如 `--trace='.*'` 启用全部、`--trace='lib.eal.*'` 只启用某一族；DPDK 的 trace 点是编译期通过宏注册的命名事件，运行时按名字匹配后开启，因此正则能否命中完全取决于目标版本实际注册了哪些点，具体名字需对照实际版本核验，宏入口为 `RTE_TRACE_POINT` 与 `RTE_TRACE_POINT_FP`（只列名字，不展开实现，原理见 06-xx）。`--trace-dir=<path>` 指定 CTF 输出目录，默认路径在不同版本可能是用户主目录下的固定子目录或运行时目录，需对照实际版本核验；目录必须可写，否则进程启动或退出时会报错。`--trace-buf-size=<bytes>` 设置单个 per-lcore 缓冲的字节数，缓冲越大越能容纳长时采样，但占用内存越多；`--trace-num-buffers` 控制缓冲数量，是否提供与默认值需核验。`--trace-mode` 决定缓冲写满后的行为，常见取值为 `overwrite`（覆盖最旧事件，保留最新）与 `discard`（丢弃新事件，保留最早），具体取值集合与拼写需对照实际版本核验，定位在 `lib/eal/common/eal_common_trace.c` 附近。这些参数的语义是「开哪些点、写到哪、缓冲多大、满了怎么办」，本篇不展开缓冲的内存布局与写入路径（原理见 06-xx）。

trace 的输出采用 CTF（Common Trace Format）风格，目录里通常包含 `metadata` 描述文件与若干按 lcore 命名的通道数据文件；离线查看可用 babeltrace 生态的 `babeltrace2` 或 DPDK 随版本提供的转换工具，工具名与调用方式需对照实际版本核验，并给出 `lib/eal/common/` 与 `usertools/` 下可定位路径。运行期显式落盘的接口常见为 `rte_trace_save()`，元数据打印为 `rte_trace_metadata_dump()`，二者的确切名字与签名同样需核验，声明在 `lib/eal/include/rte_trace.h` 一类头文件。本篇只要求读者知道「trace 产物是一组 CTF 文件、需要外部工具转成可读文本」，不展开 CTF 结构与事件字段（字段见 05-xx）。

**调试组合族**。日志与 trace 参数都属于 EAL 段，必须写在 `--` 之前，与 04-01 的 `-l`、`--socket-mem`、`--file-prefix` 并列；testpmd 的 `-i`、`--forward-mode` 等仍在 `--` 之后（见 04-03）。一个典型调试命令行会把全局级别设为 info、把某个域单独开到 debug、开启时间戳、并把 trace 落到临时目录。需要注意 DEBUG 级日志与全量 trace 都会显著增加 CPU 与 I/O 开销，压测或生产环境应关闭，只在复现问题时短时开启；日志与 trace 也不应替代 04-04 的统计命令与 04-05 的观测工具，三者定位不同。

日志级别、分域、trace 开关与 CTF 产物之间的关系如图 04-06-01 所示。

### 4. 典型示例

下面演示「枚举日志域 + 分域开调试 + 开启 trace」的一组命令。第一条单独执行，只用于取域名清单。

```bash
testpmd --log-level=help
testpmd -l 0-3 --socket-mem 1024,0 --file-prefix pg0 \
  --log-level=lib.eal:debug --log-level=pmd:info \
  --log-timestamp --syslog=never \
  --trace='lib.eal.*' --trace-dir=/tmp/dpdk-trace --trace-mode=discard \
  -- -i
```

示例输出，具体格式需对照实际版本核验：

```text
  registered log types:
    lib.eal          (id 1)  level debug
    lib.ethdev       (id 2)  level info
    lib.mempool      (id 3)  level info
    lib.mbuf         (id 4)  level info
    lib.telemetry    (id 5)  level notice
    pmd.net.ixgbe    (id 6)  level info
    pmd.net.mlx5     (id 7)  level info
    user1            (id 8)  level info

EAL: Detected CPU lcores: 16
EAL: Timestamp 1731234567.123456  Selected IOVA mode 'VA'
EAL: Timestamp 1731234567.123512  lib.eal debug: memzone reserved
EAL: Timestamp 1731234567.123540  lib.eal debug: mempool populated
EAL: Timestamp 1731234567.125001  pmd.net.ixgbe info: port 0 configured
```

逐行判读说明如下。`testpmd --log-level=help` 的输出是一份「域名 → 数值 id → 当前级别」的三列清单，它是写分域参数时域名的唯一可靠来源：本例里 EAL 域名为 `lib.eal`、ixgbe 驱动域名为 `pmd.net.ixgbe`，若照抄旧资料写成大写 `EAL` 或 `PMD`，在新版本可能匹配不到任何域，分域设置静默失效，这正是「日志开了却看不到」的首要原因。清单里每个域后面的 `level` 是该域默认级别，注意它与命令行设定的全局级别可能不同，分域写法会覆盖对应域。第二段是正式启动后的日志样例：首行 `Detected CPU lcores: 16` 是常规启动摘要，随后每行开头的 `Timestamp 1731234567.xxxxxx` 正是 `--log-timestamp` 生效的证据，时间戳采用秒加微秒形式，便于与外部事件对齐；`lib.eal debug:` 前缀的两行说明 `--log-level=lib.eal:debug` 已把 EAL 域开到调试级，出现了 `memzone reserved`、`mempool populated` 这类启动期细节，正常情况下这些信息在 info 级别是看不到的；`pmd.net.ixgbe info:` 一行说明 `--log-level=pmd:info` 这一较宽的模式命中了 ixgbe 驱动域并保留了信息级输出。整段没有任何 `EAL: Error` 或 `PANIC` 行，说明参数拼写与域名匹配都正确。需特别注意，域名清单、级别名、时间戳的具体格式在不同版本差异较大，本段仅为形状示意，一律以本机 `--log-level=help` 与实际输出为准，需对照实际版本核验。若某条预期出现的 debug 日志没有打印，排查顺序是「域名是否拼对 → 该域级别是否被后续分域参数覆盖 → 全局级别是否更低 → 该消息是否属于别的域」。

再看 trace 落盘后的目录形态，用一条普通目录命令即可确认产物是否生成。

```bash
ls -l /tmp/dpdk-trace
```

示例输出，具体格式需对照实际版本核验：

```text
total 2048
-rw-r--r-- 1 root root    8192 Nov 10 09:10 metadata
-rw-r--r-- 1 root root  262144 Nov 10 09:10 channel0_0
-rw-r--r-- 1 root root  262144 Nov 10 09:10 channel1_0
-rw-r--r-- 1 root root  262144 Nov 10 09:10 channel2_0
```

这里 `metadata` 是 CTF 元数据描述文件，三个 `channelX_0` 对应各 lcore 的事件通道数据文件，文件大小与 `--trace-buf-size` 的设置一致。若目录为空或没有 `metadata`，通常是 `--trace-dir` 不可写、`--trace` 正则没有命中任何已注册点、或进程异常退出未及落盘；可用 `babeltrace2 /tmp/dpdk-trace` 一类命令把 CTF 转成可读文本，具体工具名与调用方式需对照实际版本核验。本篇不展开 CTF 事件字段（字段见 05-xx）。

### 5. 速查表

下表按调试目标给出日志与 trace 参数组合，均为 EAL 段参数。

| 目标 | 参数组合 | 注意点 |
|---|---|---|
| 查本机域名 | `--log-level=help` | 不启动应用 |
| 全局详细日志 | `--log-level=8` 或 `debug` | 压测期关闭 |
| 只开 EAL 调试 | `--log-level=lib.eal:debug` | 域名以 help 为准 |
| 只开某 PMD | `--log-level=pmd.net.mlx5:info` | 需核验域名 |
| 加时间戳 | `--log-timestamp` | 便于对齐时间线 |
| 写系统日志 | `--syslog=always` 需核验 | 与 no 的区别 |
| 全量 trace | `--trace='.*' --trace-dir=...` | 开销大 |
| 只留最早事件 | `--trace-mode=discard` | 需核验取值 |

下表把常见日志现象与最可能的参数误配对应起来，完整映射见 04-08。

| 现象 | 可疑原因 | 处理方向 |
|---|---|---|
| 分域设置了却无输出 | 域名拼错 | 用 help 核对 |
| 日志刷屏拖慢转发 | 全局开到 debug | 降回 info 或 warning |
| 时间戳格式不对 | 参数未生效 | 核对拼写与版本 |
| trace 目录为空 | 正则未命中或不可写 | 缩小正则并查权限 |
| trace 事件被截断 | 缓冲过小或覆写模式 | 增大 buf-size |
| syslog 里没有日志 | `--syslog` 取值 | 改 always 需核验 |

下面把「问题复现期」与「压测期」两套参数模板集中列出，便于直接切换。

```bash
DEBUG_FLAGS="--log-level=lib.eal:debug --log-timestamp --trace='.*' --trace-dir=/tmp/tr"
QUIET_FLAGS="--log-level=lib.eal:warning --syslog=never"
testpmd -l 0-3 $DEBUG_FLAGS -- -i
testpmd -l 0-3 $QUIET_FLAGS -- -i --forward-mode io
```

### 6. 版本差异

本节只谈日志与 trace 参数、名字、工具层面的版本变化。最显著的是日志实现位置的迁移：早期日志逻辑集中在 `lib/eal/common/eal_common_log.c`，较新版本拆分出独立的 `lib/log/` 库（`lib/log/log.c`），`rte_log` 级别枚举仍保留在 `lib/eal/include/rte_log.h`。这一迁移不改变 `--log-level` 的命令行写法，但会影响排错时该去哪个文件找实现，本篇已同时给出两处路径，具体以目标版本目录为准，需对照实际版本核验。

其次是域名体系的变化。较老版本使用 `EAL`、`PMD`、`MALLOC` 一类大写短日志类型，较新版本统一为点分小写域名如 `lib.eal`、`pmd.net.*`、`user1` 至 `user8`；两类名字是否并存、`--log-level` 是否仍接受旧名，需对照实际版本核验。因此任何写死域名的脚本都应先跑 `--log-level=help` 采集目标版本的清单，而不是跨版本照抄。`--syslog` 从早期布尔形态演进为 `auto` / `always` / `never` 枚举，`--log-color` 是较新加入的可选项，二者的取值与默认值同样需核验，定位在 `lib/eal/common/eal_common_options.c`。

第三类是 trace 能力的引入与演进。trace 框架自 20.05 前后引入并在后续版本持续完善，`--trace`、`--trace-dir`、`--trace-buf-size`、`--trace-mode` 的可用性与取值集合在 23.11 LTS、24.11 与 master 之间可能不同；`--trace-num-buffers`、`--trace-mode` 的确切取值拼写（是否写作 `overwrite` 与 `discard`）需核验，定位在 `lib/eal/common/eal_common_trace.c` 与 `lib/eal/include/rte_trace*.h`。离线工具名差异更大：早期资料可能提到 `dpdk-trace` 或基于 babeltrace 的脚本，较新版本普遍推荐 `babeltrace2`，本篇不固化任何工具名，统一写「需对照实际版本核验」并指向 `lib/eal/common/` 与 `usertools/`。`RTE_TRACE_POINT`、`RTE_TRACE_POINT_FP`、`rte_trace_save()` 等接口名也应以目标版本头文件为准。工程上的一致做法是把「`--log-level=help` 域名清单」「trace 参数 `--help`」「CTF 查看工具是否可用」作为每个目标版本上线前的三项基线采集。

### 7. 常见误用与调试

第一类误用是分域域名照抄旧资料。把 `lib.eal` 写成 `EAL`、把 `pmd.net.mlx5` 写成 `MLX5_PMD`，在采用点分域名的新版本里匹配不到任何域，参数被接受但静默失效，表现为「明明设了 debug 却看不到日志」；唯一可靠的做法是先跑 `--log-level=help` 取域名。第二类是全局与分域混用导致优先级误判：一条命令行里既写 `--log-level=8` 又写 `--log-level=lib.eal:warning`，本意可能是「全局调试但 EAL 别太吵」，但覆盖方向与预期不符时会出现「该详细的没详细、该安静的反而刷屏」，应减少层级、逐条验证。第三类是在压测或生产环境长期开 DEBUG 与全量 trace，逐条日志与 CTF 写入会显著吃掉 CPU 与 I/O，统计里表现为吞吐莫名下降，这类可观测开销必须在基准测试前关闭（方法学见 08-01）。

第四类是 trace 正则没命中任何点却以为 trace 已开：`--trace='mylib.*'` 在当前版本没有注册对应点时，目录里只有空的 metadata，排查时先用 `--trace='.*'` 确认产物能生成，再逐步收窄正则。第五类是 `--trace-dir` 指向不可写路径或容器中不存在的目录，进程退出时落盘失败，应先用 `mkdir -p` 并确认权限。第六类是 `--trace-buf-size` 过小配合 `overwrite` 模式，长时采样下早期事件被覆盖，事后分析发现时间线缺头，若关注启动阶段应改用 `discard` 或增大缓冲（取值需核验）。第七类是把 trace 当成统计工具：trace 看的是事件时序，端口速率与丢包仍应回到 04-04 的统计命令与 04-05 的观测工具，二者不可互相替代。

统一的日志与 trace 调试顺序建议如下。

```bash
testpmd --log-level=help
testpmd -l 0-1 --no-huge --iova-mode=va --log-level=lib.eal:debug --log-timestamp -- -i
ls -l /tmp/dpdk-trace
```

第一条取域名清单，第二条用最小 EAL 环境验证分域与时间戳是否生效，第三条确认 trace 产物是否落地。三步分别覆盖「域名是否正确」「级别与格式是否生效」「trace 是否可用」，任何一步异常都按第 5 节第二张表回查对应参数。错误现象到参数域的完整映射见 04-08，本篇不重复。

## 04-07 脚本化与自动化集成

### 1. 本篇定位与覆盖范围

本篇是 DPDK「脚本化与自动化集成」的唯一权威源，把前六篇里一条条手工敲的命令，收敛为可重复、可无人值守、可放进 CI 的自动化方案。手工调试时，工程师在终端里拼一条 EAL 命令行、进入 `testpmd>` 敲几条 `set` 与 `show`、再开另一个终端跑 `dpdk-procinfo`，这套流程在回归测试、批量基准、容器化部署中必须变成脚本；本篇讲的就是「怎么把交互变成非交互、把命令行变成模板、把统计变成可解析数据」。

覆盖内容分四组。第一组是从文件读取参数，即以 `--cmdline-file` 一类入口把超长 EAL 参数或 testpmd 运行时命令写入文件（具体参数名、归属段与可用版本需对照实际版本核验）。第二组是交互式会话的脚本化，包括标准输入重定向、heredoc、`printf` 管道、`expect` / `pexpect` 处理提示符，以及退出码与超时控制。第三组是 telemetry socket 的 Python 侧读取，即用 unix domain socket 连接 primary 的遥测端点、发送文本命令、解析 JSON、换算速率，这是把 testpmd 统计接入监控系统的标准做法。第四组是 CI 中的参数模板，包括容器里最小可运行参数集、用 `--file-prefix` 做并发实例隔离、超时与残留清理、日志与指标归档。

去重铁律：本篇只讲「脚本怎么写、命令怎么拼、数据怎么读」，不讲 telemetry 库的内部注册与编码（模块见 07-12），不讲多进程共享内存通信原理（原理见 06-10），不列 `rte_telemetry` 相关结构体字段（字段见 05-xx）。例如 telemetry 客户端只需知道「连哪个 socket、发什么文本、收到什么 JSON」，不需要知道服务端如何注册命令。统计项含义与判读回指 04-04，工具命令形状回指 04-05，EAL 参数形状回指 04-01 与 04-02，本篇不重复任何参数全集。

源码与路径定位：EAL 参数解析在 `lib/eal/common/eal_common_options.c`，testpmd 应用段参数与运行时命令分别在 `app/test-pmd/parameters.c` 与 `app/test-pmd/cmdline.c`，交互式 CLI 主循环在 `app/test-pmd/testpmd.c`；遥测服务端在 `lib/telemetry/`，官方交互客户端脚本在 `usertools/dpdk-telemetry.py`，它是写 Python 客户端时最直接的参考实现；CI 相关的大页与绑定脚本在 `usertools/dpdk-hugepages.py` 与 `usertools/dpdk-devbind.py`。版本基准仍为 23.11 LTS / 24.11 / master，凡命令名、socket 类型、协议形态、返回键名不确定的，标注「需对照实际版本核验」并给出上述路径。

### 3. 逐项详解

**参数文件族**。当 EAL 参数或运行时命令多到命令行长度受限、或需要版本化管理时，把它们写进文件再让进程加载，比在 shell 里拼一大串更可靠。`--cmdline-file` 一类入口正是为此而来，常见动机是 Windows 命令行长度限制、容器的 entrypoint 长度限制、以及把一套基准参数纳入代码评审。需要注意的是，这类入口究竟是 EAL 段参数（位于 `--` 之前、由 `lib/eal/common/eal_common_options.c` 解析）还是 testpmd 应用段参数（位于 `--` 之后、由 `app/test-pmd/parameters.c` 解析）、文件内是「每行一个参数」还是「整条命令行」、以及在 23.11 LTS / 24.11 / master 中是否提供，均需对照实际版本核验；可从 `lib/eal/common/eal_common_options.c` 的长选项表与 `app/test-pmd/parameters.c` 的解析分支直接确认。即使目标版本没有该入口，本篇给出的「shell 变量拼装 + heredoc 喂 stdin」方案也能等价达成同样的可版本化效果。

**会话脚本化族**。最朴素的做法是标准输入重定向：`testpmd ... -i < commands.txt`，文件里每行一条运行时命令，末尾放 `quit` 让进程正常退出并返回退出码。与之等价的是 heredoc，即把命令序列内联在脚本里用 `<<'CMDS'` 喂给进程（见第 2 节代码块）；单引号包裹的 heredoc 定界符能避免 shell 对 `$` 与反斜杠展开，写命令更安全。`printf 'show config\nquit\n' | testpmd ... -i` 则是更轻量的单行形式，适合只跑一两条命令的冒烟测试。三者都依赖 `-i` 交互模式，因为只有交互态才会从 stdin 逐行读取并交给 `app/test-pmd/cmdline.c` 解析；若同时给了 `--auto-start`，进程会一边转发一边读 stdin，命令仍可执行，但要注意 `quit` 之前转发循环不会自己停。

更复杂的场景需要 `expect` 或 Python 的 `pexpect`：当脚本必须等待特定提示符（如 `testpmd>`）再发送下一条命令、或要根据上一条输出决定分支时，单纯的重定向不够用。`pexpect.spawn()` 启动进程、`expect('testpmd>')` 等待提示符、`sendline('show port stats all')` 发送命令，再读回一段输出做断言，是这类脚本的骨架；超时必须显式设置，否则转发循环挂住会让 CI 永久等待。无论用哪种方式，退出码检查都不能省：`quit` 正常退出应返回 0，非零退出或超时都应在 CI 里判失败并保留日志。命令行式执行运行时命令的完整形状见 04-03，本篇只讲「怎么把它变成非交互」。

**遥测读取族**。这是把 testpmd 接入监控与自动化判读的关键。primary 进程由 `lib/telemetry/` 在 unix domain socket 上暴露端点，路径通常随 `--file-prefix` 变化（见 04-01、04-05），具体路径与 socket 类型需对照实际版本核验；官方客户端 `usertools/dpdk-telemetry.py` 是最可靠的参考实现。较新版本采用 v2 文本协议：客户端连接后，服务端通常先发送一段含版本信息的 JSON 问候，客户端需要先读取它，再发送形如 `/ethdev/stats,0\n` 的命令，随后读回一段 JSON 对象；v1 协议则发送 `{"action": ...}` 一类请求。两种协议的连接步骤、是否需要先读问候、命令拼写、返回键名以及 socket 是 `SOCK_SEQPACKET` 还是 `SOCK_STREAM`，全部需对照实际版本核验，定位在 `lib/telemetry/` 与 `usertools/dpdk-telemetry.py`。

Python 客户端的骨架是：用 `socket.socket(socket.AF_UNIX, socket.SOCK_SEQPACKET)` 建连（类型需核验）、`connect(TELEMETRY_PATH)`、先 `recv` 问候并 `json.loads`、再 `send` 命令文本、`recv` 回复并 `json.loads`，取出 `/ethdev/stats` 字典里的 `ipackets`、`opackets`、`imissed`、`rx_nombuf` 等键（键名需核验）。有了两次采样，就能用「差值除以采样间隔」换算 pps，例如间隔 10 秒内 `ipackets` 增量除以 10 即为 RX pps，这与 04-04 里「清零 → 等待 → 读差值」的手工方法等价，但更适合无人值守。脚本必须容错处理缺失键、socket 不存在、以及 primary 重启导致的连接中断；把 `TELEMETRY_PATH` 提成变量、并对 `--file-prefix` 保持一致，是避免连错实例的关键。遥测命令清单与返回字段见 04-05，服务端模块见 07-12，本篇不列结构体字段（字段见 05-xx）。

**CI 参数模板族**。CI 环境与生产环境诉求不同：优先「能稳定跑完并给出明确退出码」，而非吞吐。因此模板里通常带 `--no-huge --iova-mode=va` 规避大页预留、`--no-telemetry` 避免 socket 残留、`-l 0-1` 收敛核数以适配 cpuset、`--log-level=lib.eal:warning` 减少日志 I/O、以及用 `--file-prefix ci_${CI_JOB_ID}` 让同一台 runner 上并发的多个 job 互不干扰（该参数见 04-01）。是否加 `--no-shconf` 要权衡：一次性任务加上可避免残留共享文件，但会阻止任何 secondary 观测，若 CI 里还要跑 `dpdk-procinfo` 就不能加。外层用 `timeout 60` 包住进程，并用 heredoc 末尾的 `quit` 触发正常退出，二者共同保证 job 不会挂死。

一次完整的 CI job 还应包含三段收尾：进程退出后检查退出码与日志中是否出现 `EAL: Error` / `PANIC`；用 `dpdk-hugepages.py --show` 与 `dpdk-devbind.py --status` 记录系统基线，便于失败时回溯；清理 `/var/run/dpdk/<prefix>/` 下的残留 socket 与共享内存文件，避免影响下一个 job。清理动作要谨慎，尤其不要在共享 runner 上贸然解绑设备或清除大页，这类操作属于前置配置而非本 job 的私有状态。把 EAL 段提成 `EAL_FLAGS` 变量、把前缀提成 `PREFIX` 变量，是让同一份脚本在开发机、容器与 CI 三处复用的最小抽象，无需引入额外框架。

### 4. 典型示例

下面给出一个完整的 Python 遥测读取脚本，以及它在一次 10 秒采样窗口里的输出。脚本里所有与版本相关的形态都标注为「需对照实际版本核验」，可直接作为 CI 里取数的骨架。

```python
import json
import socket
import time

TELEMETRY_PATH = "/var/run/dpdk/ci_local/telemetry"

def read_stats(port=0):
    sock = socket.socket(socket.AF_UNIX, socket.SOCK_SEQPACKET)
    sock.connect(TELEMETRY_PATH)
    greeting = json.loads(sock.recv(4096).decode())
    print("server version:", greeting.get("version"))
    sock.send(("/ethdev/stats,%d\n" % port).encode())
    reply = json.loads(sock.recv(16384).decode())
    sock.close()
    return reply["/ethdev/stats"]

before = read_stats(0)
time.sleep(10)
after = read_stats(0)
delta = after["ipackets"] - before["ipackets"]
print("RX pps =", int(delta / 10))
print("missed =", after.get("imissed", 0))
print("rx_nombuf =", after.get("rx_nombuf", 0))
```

示例输出，具体格式需对照实际版本核验：

```text
server version: DPDK 24.11.0
server version: DPDK 24.11.0
RX pps = 14880922
missed = 0
rx_nombuf = 0
```

逐行判读说明如下。两行 `server version: DPDK 24.11.0` 分别来自 `read_stats()` 被前后两次调用时读取的服务端问候，说明脚本按「先 recv 问候、再 send 命令」的顺序与 v2 端点完成了握手；如果目标版本没有这段问候，第一次 `recv` 就会阻塞或解析失败，此时应改为连接后直接发命令，具体以 `usertools/dpdk-telemetry.py` 的实际实现为准，需对照实际版本核验。`RX pps = 14880922` 是核心结果：它等于 10 秒窗口内 `ipackets` 增量除以 10，即每秒约一千四百万包，这个量级对应 64 字节小包的万兆线速附近，与 04-04 的手工差值法完全等价；若该值为 0，通常不是换算错误，而是 primary 未启动转发、端口掩码不对、或 `TELEMETRY_PATH` 连到了另一个空闲实例，应回到 `--file-prefix` 与 `show config` 核对。`missed = 0` 与 `rx_nombuf = 0` 取自返回 JSON 的 `imissed` 与 `rx_nombuf` 键，分别对应 04-04 里的 `RX-missed` 与 mempool 耗尽计数，二者为 0 表明该速率下尚未触达丢包点；脚本用 `after.get(键, 0)` 容错，是因为不同版本返回的键集合可能不同（键名需核验），缺失时按 0 处理比直接抛异常更适合无人值守，但正式监控里应把「键缺失」单独记为告警，避免把「没采到」误当成「没丢包」。整段没有连接异常与 JSON 解析异常，可判定 socket 路径、协议顺序、命令拼写、键名四者与当前版本一致；任何一环不匹配，最稳妥的定位方式都是先跑官方 `dpdk-telemetry.py` 手工执行同样的命令，确认返回形状后再固化脚本。

再看一组完整的 CI 冒烟脚本，它把 EAL 模板、heredoc 命令注入、超时与退出码检查串在一起。

```bash
#!/usr/bin/env bash
set -euo pipefail
PREFIX="ci_${CI_JOB_ID:-local}"
EAL="-l 0-1 --no-huge --iova-mode=va --file-prefix $PREFIX --no-telemetry --log-level=lib.eal:warning"
timeout 60 testpmd $EAL -- -i --portmask 0x1 --auto-start <<'CMDS' | tee smoke.log
show config
show port stats all
quit
CMDS
grep -q "Interactive-mode selected" smoke.log
echo "smoke test passed for $PREFIX"
```

示例输出，具体格式需对照实际版本核验：

```text
Interactive-mode selected
io packet forwarding - ports=1 cores=1 nb_pkts=32
  RX-packets: 0  RX-missed: 0  RX-bytes: 0
  TX-packets: 0  TX-errors: 0  TX-bytes: 0
Bye...
smoke test passed for ci_local
```

这里 `Interactive-mode selected` 被 `grep -q` 作为冒烟通过的判据，它证明 `-i` 生效、进程确实进入了 CLI 并读到了 heredoc 里的命令；`io packet forwarding - ports=1 cores=1` 是 `show config` 的输出，印证 `--portmask 0x1` 与核数收敛按模板落地。统计块全 0 属于预期：该 job 没有接真实流量，目的只是验证「能启动、能执行运行时命令、能带 `quit` 正常退出」，而非测吞吐，因此不应把全 0 判为失败。`Bye...` 表明 `quit` 被正确执行、进程以 0 退出，`set -euo pipefail` 与 `timeout 60` 共同保证任何异常或挂死都会让 job 失败。最后一行 `smoke test passed for ci_local` 是脚本自身打印的结论，前缀值来自 `CI_JOB_ID`，并发 job 会各自得到不同前缀，从而避免共享内存与 socket 冲突（见 04-01）。若要在该模板里追加观测，可另起一个 `dpdk-procinfo --file-prefix "$PREFIX" -- --stats`，但那样就不能加 `--no-shconf`，这是模板取舍的关键点。

### 5. 速查表

下表按自动化目标给出最小方案，均为可直接套用的形式。

| 目标 | 方案 | 注意点 |
|---|---|---|
| 版本化参数 | 写文件加 `--cmdline-file` 需核验 | 确认归属段 |
| 批量跑命令 | `testpmd -i < cmds.txt` | 末尾放 `quit` |
| 内联命令 | `<<'CMDS'` heredoc | 单引号防展开 |
| 按提示符分支 | `pexpect` | 必须设超时 |
| 取实时指标 | Python 连 telemetry socket | 键名需核验 |
| 并发隔离 | `--file-prefix ci_${ID}` | 全链路一致 |
| 防挂死 | 外层 `timeout` | 配合退出码 |
| 失败留痕 | `tee` 加日志归档 | 查 `EAL: Error` |

下表把自动化常见失败与最可能的原因对应起来，完整映射见 04-08。

| 现象 | 可疑原因 | 处理方向 |
|---|---|---|
| 脚本卡住不退出 | 缺 `quit` 或没超时 | 加 `quit` 与 `timeout` |
| `Connection refused` | 前缀不一致或加了 no-telemetry | 核对端点 |
| JSON 首包解析失败 | 问候处理不符版本 | 对照官方客户端 |
| 并发 job 串数据 | `--file-prefix` 相同 | 用 job id 隔离 |
| 命令未执行 | 忘加 `-i` | 补交互开关 |
| 键缺失误判为零丢包 | 返回键集合变化 | 缺失记告警 |

下面把「开发机 / 容器 / CI」三处复用的参数模板骨架集中列出，长清单不塞进表格单元格。

```bash
COMMON="-l 0-1 --log-level=lib.eal:warning"
CONTAINER="--no-huge --iova-mode=va --no-telemetry"
ISOLATION="--file-prefix ${PREFIX:-local}"
EAL="$COMMON $CONTAINER $ISOLATION"
testpmd $EAL -- -i --portmask 0x1 --auto-start --forward-mode io
```

### 6. 版本差异

本节只谈脚本化入口、协议与工具名层面的版本变化。`--cmdline-file` 一类从文件加载参数的能力属于较晚加入的特性，其引入版本、归属 EAL 段还是 testpmd 应用段、文件内语法（每行一项还是整条命令行）、以及是否支持注释与引号，在 23.11 LTS / 24.11 / master 之间可能不同，需对照实际版本核验，定位在 `lib/eal/common/eal_common_options.c` 与 `app/test-pmd/parameters.c`。04-01 与 04-03 都把它列为「需核验」入口，本篇同样不预设其存在；即便目标版本没有，shell 变量拼装与 heredoc 方案也完全等价。

遥测协议是自动化脚本里版本敏感度最高的一环。v1 协议基于 JSON 请求对象，v2 协议改为 `/命令,参数` 文本并在连接后先发版本问候；两种协议下 socket 类型（`SOCK_SEQPACKET` 或 `SOCK_STREAM`）、socket 文件路径、命令名（如 `/ethdev/stats` 与 `/ethdev/xstats`）、返回键名（`ipackets`、`imissed`、`rx_nombuf` 是否出现）都可能不同，全部需对照实际版本核验，定位在 `lib/telemetry/` 与 `usertools/dpdk-telemetry.py`。因此 Python 客户端不应把任何键名写死为唯一事实，而应把「`/` 返回的命令清单」与「一次真实查询的返回键集合」作为目标版本基线采集后再固化，并对缺失键做显式处理。

工具脚本名与目录也有变化：`usertools/dpdk-devbind.py`、`usertools/dpdk-hugepages.py`、`usertools/dpdk-telemetry.py` 在较老版本可能位于 `tools/`，安装后的可执行名可能带或不带 `dpdk-` 前缀，具体以 `which` 与安装清单为准，需对照实际版本核验。CI 模板里 `--no-huge`、`--iova-mode=va`、`--no-telemetry`、`--log-level` 这些参数本身较稳定，但 `--log-level` 的分域名体系（点分小写与大写旧名）与 `--syslog` 取值在版本间调整过（见 04-06），模板若写死了域名也要随版本更新。工程上的一致做法是把「官方客户端一次成功查询的原始输出」「`testpmd --help`」「`help` 命令清单」三份基线纳入 CI 的兼容性门禁，版本升级时先跑这三步再放行业务脚本。

### 7. 常见误用与调试

第一类误用是「脚本里没放 `quit`」。`testpmd -i < commands.txt` 或 heredoc 若以 `show` 结尾而没有 `quit`，转发循环不会自行退出，CI job 会一直挂到被外层 `timeout` 杀掉，且退出码非零被误判为失败；每条批处理命令序列都必须以 `quit` 收尾。第二类是把 `timeout` 当成可选项：即使写了 `quit`，端口异常或驱动 hang 也可能让进程卡住，外层超时是最后一道保险，二者要同时具备。第三类是并发 job 共用同一个 `--file-prefix`，导致两个 testpmd 抢同一份共享内存与 telemetry socket，表现为「统计串了」「偶尔起不来」这类难以复现的问题；前缀必须带上 job id 或随机后缀，且从 EAL 段到 `dpdk-procinfo`、到 Python 的 `TELEMETRY_PATH` 全链路保持一致。

第四类是 Python 客户端把协议形态写死。连接后不读问候直接发命令、用了错误的 socket 类型、或把 v1 的 JSON 请求发给 v2 端点，都会得到空回复或解析异常；正确做法是先跑一次官方 `dpdk-telemetry.py`，照抄它实际的连接与收发顺序，再把版本相关部分标注核验。第五类是把「键缺失」静默当成 0：脚本里 `after.get("imissed", 0)` 若用于正式监控，会把「该版本不返回这个键」误报成「零丢包」，应把缺失键单独记为告警或改用 `show port xstats all` 交叉确认（见 04-04）。第六类是 CI 里为了「干净」加了 `--no-shconf`，随后又想用 `dpdk-procinfo` 观测，secondary 根本附着不上；二者取舍要在模板设计阶段定死，不要临时混搭。

第七类是清理动作越界：在共享 runner 上用 `dpdk-devbind.py -u` 解绑设备、或用 `dpdk-hugepages.py --clear` 清除大页，会影响同一机器上的其他 job，甚至切掉管理网口；清理只应针对本 job 私有的 `/var/run/dpdk/<prefix>/` 残留与临时日志，系统级前置配置由专门的环境准备阶段负责。统一的自动化调试顺序建议如下。

```bash
testpmd --help
printf 'help\nquit\n' | testpmd -l 0-1 --no-huge --iova-mode=va -- -i
dpdk-telemetry.py
```

第一条确认本机参数拼写，第二条用最小 EAL 环境验证「stdin 注入 + quit 退出」这条链路可用，第三条用官方客户端确认遥测端点与命令清单。三步都通过后再把结果固化进 CI 模板与 Python 脚本，可把绝大多数兼容性问题拦在业务脚本之前。错误现象到参数域的完整映射见 04-08，本篇不重复。

### 3. 逐项详解

**大页内存族**。这一族的现象集中在启动期：日志里出现大页不足、无法预留、或找不到挂载点一类措辞，进程在 `rte_eal_init()` 阶段退出。首选动作是 `dpdk-hugepages.py --show` 看各 NUMA 节点各页大小的 total 与 free，再 `cat /proc/meminfo` 交叉确认，最后把结果与 `--socket-mem` 的逗号配额逐项对齐（完整参数见 04-01）。三类高频根因分别是：配额之和大于已预留大页数；`--huge-dir` 指向的挂载点页大小与配额不一致（例如系统上挂了 1 GB 页、命令行却按 2 MB 用）；双路机器上只给了一个 socket 配额，却让另一节点上的网卡参与转发。修复方向是先用 `dpdk-hugepages.py -s` 补足预留并挂载正确页大小，再让 `--socket-mem` 的字段数、字段值、`--huge-dir` 三者与 `/proc/meminfo` 一致。容器场景还要额外核对挂载点路径是否与宿主机不同。该族只涉及参数取值与系统前置状态，内存布局机制不讲（原理见 06-02 ｜ 字段见 05-07）。

**设备绑定与声明族**。现象是 `no Ethernet ports found`、某端口 probe 失败、或 `unknown devargs`。排查顺序固定为「绑定 → 允许 → 参数」三步：`dpdk-devbind.py --status` 确认目标 BDF 的 `drv=` 是否为 `vfio-pci` 一类 DPDK 兼容驱动；再核对 04-02 里 `-a` 是否把该 BDF 写进白名单、多端口卡的每个 function 是否分别声明；最后确认 devargs 键属于该设备对应的驱动。绑定与允许是两件事，只做了后者不会把网卡从内核驱动抢过来，这是本族最高频的误用。若报 `probe failed`，还要回看 `--iova-mode` 与 IOMMU 状态（见 04-01）。设备抽象与 probe 内部流程不展开（模块见 07-01）。

**lcore 与亲和族**。现象包括线程亲和设置失败、转发核空转、或启动日志里 `lcore is ready` 行数少于预期。根因通常是把 lcore 编号误当物理 CPU 编号：在 `isolcpus`、cgroup cpuset 或容器配额限定的环境里，`-l 0-3` 试图绑定到根本不在允许集合中的 CPU，表现为亲和失败或速率异常低。首选 `numactl -H` 与 `/proc/<pid>/task/<tid>/status` 核对可见 CPU 与亲和结果，必要时用 `--lcores` 写明 `lcore@CPU` 映射（见 04-01）。另一类是 `--nb-cores` 大于 `-l` 启用的核数，testpmd 会报转发核不足（见 04-03）。核数与端口数、队列数是否匹配，可先用 `show config` 一眼确认。

**NUMA 与 IOVA 族**。现象是启动日志里 `Selected IOVA mode` 与预期不符、VFIO 相关报错、或跨节点端口收不到包。处理动作是读启动日志里探测到的 NUMA 节点数与 IOVA 模式行，用 `/sys/bus/pci/devices/<BDF>/numa_node` 确认网卡所在节点，再把 `--socket-mem` 的节点顺序与网卡节点对齐；`--iova-mode=pa` 与开启 IOMMU 的 VFIO 组合可能不兼容，改用 `va` 或让 EAL 自动探测通常即可（见 04-01）。跨节点访存带来的性能下降属于机制层（原理见 06-09），本篇只要求把配额与节点对齐。日志里 `VFIO support failed` 一类措辞还需与 04-05 的绑定状态联合判读。

**进程隔离族**。现象几乎都出现在 secondary 侧：`dpdk-procinfo`、`dpdk-pdump` 报 `failed to attach` 或 `cannot init`，而 primary 侧毫无异常。九成根因是 `--file-prefix` 两端不一致，次要根因是 primary 加了 `--no-shconf` 导致共享配置根本没创建（见 04-01）。排查时把 primary 与 secondary 命令行里的前缀逐字符比对，并确认没有 `--no-shconf`；遥测端点路径同样随前缀变化，连不上时一并核对（见 04-05）。多进程通信本身不展开（原理见 06-10）。

**testpmd 命令族**。现象是 `Invalid port`、`Command not found`、`port X is not up`、或统计恒为零。`Invalid port` 与端口不存在通常源于 `--portmask` 选中的端口数多于 04-02 实际声明的端口数，先用 `show port info all` 看真实端口编号再改掩码；`port X is not up` 说明只执行了 `start` 而没先 `port start all`（见 04-03）；`Command not found` 一律用交互态 `help` 核对命令拼写，跨版本脚本尤其容易踩到改名或移除；统计恒为零要按 04-04 的顺序确认引擎、混杂模式、对端流量与接线。`rx_nombuf` 增长则回查 `--total-num-mbufs` 与 `--socket-mem`（见 04-03、04-04）。命令形状见 04-03，统计判读见 04-04，本篇不重列。

**观测工具族**。现象是遥测 `Connection refused`、pdump 无报文、或 `Permission denied`。遥测连不上先确认 primary 没加 `--no-telemetry`、socket 路径随 `--file-prefix` 变化却按默认路径去找、以及 `/var/run/dpdk/` 权限；pdump 无报文先确认 primary 编译时启用了 `lib/pdump/`；`Permission denied` 多因非 root 或设备节点权限，用 `ls -l` 核对（见 04-05）。这一族的共同特点是「primary 正常、工具侧异常」，因此排查重点永远在两端一致性与前置条件，而不是转发逻辑。

```text
testpmd> show config
  Interactive-mode selected
  io packet forwarding - ports=0 cores=1 nb_pkts=32
testpmd> show port info all
  No ports configured
testpmd> show port stats all
testpmd> quit
  Bye...
```

逐行判读说明如下。前两行是系统基线：`node0: 2M 512 pages ... mounted /dev/hugepages` 说明大页已预留且挂载点正确，可排除大页不足这一大类；`drv=vfio-pci` 说明目标 BDF 已绑定到 DPDK 兼容驱动，可排除「未绑定」这一大类，问题范围由此收敛到「设备声明与端口配置」。启动日志里 `Detected CPU lcores: 16`、`NUMA nodes: 2`、`Selected IOVA mode 'VA'`、`lcore 0/1 is ready` 四行表明 EAL 初始化阶段全部通过，`--no-huge --iova-mode=va -l 0-1` 这组最小参数没有触发内存、IOVA 或亲和类故障，最小命令集 L1 验证成功。关键转折在 `show config` 的 `ports=0 cores=1`：端口数为 0，与基线里明明存在一张已绑定网卡形成矛盾，说明本条命令行根本没有写 `-a` 把该 BDF 声明进来（见 04-02），因此 `show port info all` 回显 `No ports configured`、`show port stats all` 没有任何统计块，而 `quit` 仍能正常退出打印 `Bye...`。这一组输出完整演示了排错的核心逻辑：先用 L0 基线排除系统前置问题，再用 L1 最小启动证明 EAL 层健康，最后把矛盾点定位到「设备声明缺失」这一个参数域，修复只需在 `--` 之前补上 `-a 0000:01:00.0`（命令见 04-02），然后按 L2 重新验证端口数变为 1。若补了 `-a` 仍为 0，再按图 04-08-02 的链条继续查 `--no-pci`、BDF 拼写与绑定状态，逐层推进而不是一次改动所有参数。整段没有 `EAL: Error` 与 `PANIC`，印证「初始化通过但配置不全」这类故障的特征：进程能起来、能进 CLI、能退出，唯独业务端口为空。

再看最小可复现命令集的完整六层清单，它是本篇最可直接复制的产物；每层都在上一层通过后才加入新参数。

```bash
dpdk-hugepages.py --show
dpdk-devbind.py --status
numactl -H
testpmd -l 0-1 --no-huge --iova-mode=va --file-prefix diag0 -- -i
testpmd -l 0-1 --no-huge --iova-mode=va --file-prefix diag0 -a 0000:01:00.0 -- -i
testpmd -l 0-1 --socket-mem 1024,0 --huge-dir /dev/hugepages --file-prefix diag0 -a 0000:01:00.0 -- -i --portmask 0x1
testpmd -l 0-2 --socket-mem 1024,0 --huge-dir /dev/hugepages --file-prefix diag0 -a 0000:01:00.0 -a 0000:01:00.1 -- -i --portmask 0x3 --nb-cores 2 --forward-mode io
dpdk-procinfo --file-prefix diag0 -- --stats
```

示例输出，具体格式需对照实际版本核验：

```text
L0 OK: hugepages 512 free, device drv=vfio-pci, nodes=2
L1 OK: Interactive-mode selected, ports=0
L2 OK: port 0 registered as 0000:01:00.0
L3 OK: no hugepage error, mempool populated on socket 0
L4 OK: io forwarding, RX-packets and TX-packets increasing
L5 OK: procinfo attached with prefix diag0
```

这里把六层的预期结论压成六行摘要：L0 三项基线齐备、L1 最小启动成功但端口为 0（符合未声明设备的预期）、L2 加入 `-a` 后端口 0 出现、L3 换用 `--socket-mem` 与 `--huge-dir` 后无大页报错、L4 加双端口与转发引擎后收发计数开始增长、L5 secondary 以同前缀附着成功。任何一层失败，就把「上一层通过、这一层失败」之间新增的那几个参数作为嫌疑集，用二分法逐条加回定位，这正是最小可复现命令集的价值：它把「一条二十个参数的命令行起不来」变成「某两个参数组合起不来」。六层命令里的参数形状分别见 04-01、04-02、04-03、04-05，本篇只给组合与判读，不重列含义。

### 6. 版本差异

本节只谈「排错动作与关键词」随版本的变化。最直接影响排错的是报错文本本身：同一类大页不足，在不同版本可能打印 `Cannot get hugepage information`、`No free hugepages` 或 `Cannot allocate memory`，分段标题、大小写与前缀 `EAL:` 是否出现都不完全一致；因此本篇映射表里的关键词一律标注「示例措辞，具体需对照实际版本核验」，工程师应以本机真实日志为准，用语义而非逐字匹配去归类。把某一版本的报错文本写死进自动化告警规则，是跨版本升级后告警失效的常见原因。

其次是参数与命令改名带来的排错变化。`--master-lcore` 到 `--main-lcore` 的改名（见 04-01）、日志域从大写短名到点分小写的迁移（见 04-06）、telemetry 从 v1 JSON 请求到 v2 文本命令的演进（见 04-05、04-07）、以及 testpmd 若干运行时命令与转发引擎名的增删（见 04-03、04-04），都会让「昨天还能用的排错命令」今天报 `unknown option` 或 `Command not found`。因此本篇把「先跑 `testpmd --help`、交互态 `help`、`--log-level=help`」列为一切排错的第一步，正是用目标二进制自身的事实源抵消版本差异。

第三类是工具脚本名与目录差异：`dpdk-devbind.py`、`dpdk-hugepages.py`、`dpdk-procinfo`、`dpdk-telemetry.py` 的所在目录从 `tools/` 迁到 `usertools/`、安装后是否带 `dpdk-` 前缀、以及遥测 socket 的默认路径，都可能随版本变化（见 04-05、04-07）。容器与包管理器安装还会进一步改变可执行名，排错脚本里应先用 `which` 定位再调用，而不是写死路径。最小可复现命令集之所以坚持「L1 用 `--no-huge --iova-mode=va` 这种最稳定的参数起步」，就是为了尽量避开版本敏感项，把跨版本差异留到 L3 之后才逐层引入。工程上的一致做法是把「本机 `--help` 输出、一次成功的 L1 启动日志、一次成功的 L5 观测输出」作为每个目标版本的三份排错基线归档，升级时先对比基线再更新映射表与告警关键词。

### 7. 常见误用与调试

本篇本身是误用汇总，本节专讲「排错方法论」层面的误用，与前六族的具体参数坑互为补充。第一类是一上来就改一堆参数：看到起不来，同时调 `--socket-mem`、`--iova-mode`、`-a`、`--lcores`、日志级别，结果即使修好了也不知道是哪个参数起的作用，下次复发依旧抓瞎；正确做法是用第 4 节的六层最小集，保持上层通过、只改一层，用二分法把嫌疑集收敛到一两个参数。第二类是不采基线就跨版本照抄命令：把 20.11 时代的 `-n 4`、`--master-lcore`、大写日志域名、v1 遥测请求直接搬到 24.11，报错后却按「内存问题」去查，方向全错；第一步永远是 `testpmd --help` 与交互态 `help`，用目标二进制的事实源校准拼写。

第三类是忽略系统前置与业务配置的边界：把大页不足、设备未绑定这类 L0 问题，误当成 testpmd 的 `--portmask` 或 `set fwd` 问题，在 CLI 里反复敲命令却毫无进展；判断依据是「进程能否进 CLI」——进不去多半是 EAL 层或前置层，进得去但端口为空才是设备声明层，进得去且端口齐但没流量才是转发与统计层。第四类是只读累计统计、不做清零差值，或只盯 `RX-missed` 不看 `rx_nombuf` 与 xstats，得出「零丢包」的错误结论；判读方法见 04-04，本篇不重复。第五类是在压测或生产环境长期开着 DEBUG 日志、全量 trace、pdump 抓包来「方便排错」，这些手段本身会显著改变被测对象的行为，使吞吐变低、时延变高，排错反而制造了新的干扰；可观测手段应在复现期短时开启、基准期一律关闭（见 04-06、08-01）。

第六类是忽略残留状态：上一次异常退出留下的共享内存文件、telemetry socket、或仍绑定在 vfio-pci 上的网卡，会让下一次「最小命令集」莫名其妙地失败，表现为端口串了、前缀冲突、或大页 free 数对不上；每次排错前用新 `--file-prefix`、必要时清理 `/var/run/dpdk/<prefix>/`，并谨慎区分「本 job 私有残留」与「系统级前置配置」，后者不要随手清除（见 04-07）。第七类是把观测工具当修复工具：`dpdk-procinfo` 只读、`dpdk-telemetry.py` 只查，它们能告诉你「哪里不对」，但不能替你改配置；真正的修复始终要回到 04-01 至 04-03 的参数与命令。

统一的收尾调试顺序建议如下，它把本篇所有映射收敛成一条可执行的链路。

```bash
testpmd --help
dpdk-hugepages.py --show
dpdk-devbind.py --status
testpmd -l 0-1 --no-huge --iova-mode=va --file-prefix diag0 -- -i
dpdk-procinfo --file-prefix diag0 -- --stats
```

先校准参数拼写，再排除大页与绑定两项系统前置，接着用最小 EAL 集把 L1 跑通并逐层加参数，最后用 secondary 观测确认指标可读。五步覆盖了「拼写 → 前置 → 初始化 → 声明 → 观测」完整链条，任一步失败都按第 2 节映射表反查参数域，按第 4 节六层法定位具体参数。本篇作为 04 册收尾，不重列任何参数全集或命令清单：完整参数见 04-01、设备命令见 04-02、testpmd 命令见 04-03、统计判读见 04-04、工具用法见 04-05、日志 trace 见 04-06、自动化模板见 04-07；机制、字段与模块分别回指（原理见 06-xx ｜ 字段见 05-xx ｜ 模块见 07-xx），场景化深入排错回指 08-04。至此 04 册八篇构成 EAL 参数与工具命令行的唯一权威源，可供其余各册按需回查。
