# DPDK 技术资料 · 02 编译与构建

> 本册聚焦「把 DPDK 从源码变成可链接、可安装、可交付的产物」这一完整链路：源码获取与目录组织、meson/ninja 构建体系、配置选项与驱动库开关、静态与动态链接、交叉编译、以及打包与容器镜像。版本基准为 DPDK 23.11 LTS、24.11 与 master，凡涉及具体选项名、驱动名、链接参数、版本号与输出格式之处，凡记忆不确切者一律写明「需对照实际版本核验」并给出可定位的 `meson_options.txt`、`meson.build`、`config/` 或文档路径。本册严格遵守唯一权威源去重约定：运行时 EAL 参数只给最小必要引用并写「完整参数见 04-01」，运行时结构体只点名加源码路径并写「（字段见 05-xx）」，内部机制不展开而写「原理见 06-xx」，库与驱动模块功能不重列而写「模块见 07-xx」。本册的全部篇幅都用于「构建期」问题。

## 02-01 源码获取、目录结构与依赖

### 1. 背景与动机

任何一套 DPDK 技术资料，都必须先回答一个看似朴素却极其关键的问题：拿到一份 DPDK 源码之后，究竟要经过哪些步骤，才能在目标机器上得到一组可以被应用程序链接、可以被操作系统加载、可以被打包分发的库与工具。这个问题的答案，就是本册《编译与构建》要系统展开的内容。之所以把「编译与构建」独立成册，而不是塞进基础概述或部署配置里，根本原因在于 DPDK 自 20.11 版本起完成了从 GNU Makefile 体系向 meson 与 ninja 体系的全面迁移（这一演进脉络见 01-04），构建过程本身已经演化成一套拥有独立配置语言、独立依赖探测机制、独立交叉编译模型与独立产物安装规则的完整子系统。理解这套子系统，是后续一切工作的前置条件。

从工程实践的角度看，构建环节的复杂度主要来自四个方面的叠加。其一是源码规模巨大：DPDK 的仓库同时容纳了数十个核心库、上百个轮询模式驱动、若干官方应用、大量示例程序，以及面向多种 CPU 架构的适配代码，目录层级之深、文件数量之多，远超一般中间件项目。其二是版本形态多样：用户既可以从官方 git 仓库克隆 master 开发分支，也可以检出某个 LTS 长期维护分支，还可以下载经过签名与哈希校验的发行 tarball，不同形态对应的依赖准备、补丁状态与构建行为并不完全相同。其三是依赖分层：编译期需要 meson、ninja、编译器、Python 及其模块、若干开发库头文件，运行时还需要大页内存、VFIO 或 UIO 内核支持与用户态工具，二者一旦混淆，常常表现为「编译通过但程序起不来」或「链接期缺符号」。构建期只处理编译期依赖与产物，运行时大页与设备绑定属于 03 册的范围。

其四是配置生成：DPDK 并不把全部编译期开关硬编码在源码里，而是由 meson 在配置阶段根据目标架构、平台与用户传入的选项，动态生成一批头文件与构建描述文件，例如由构建系统写出的 `rte_build_config.h` 与安装时提供的 `libdpdk.pc`。这些生成物不在源码树中，而在独立的构建树里，这正是「源码树与构建树分离」这一现代构建理念在 DPDK 中的落地。对初学者而言，最常见的困惑恰恰是「为什么源码目录里找不到某个头文件」——因为它是在 `meson setup` 阶段才被生成到 `build/` 目录下的。

在本套资料的阅读主线中，本册位于「先跑起来」的起点：00 总纲给出的推荐路径明确把 02-02 列为首次接触 DPDK 的必读环节，随后才进入 03 册的绑卡与大页。换言之，只有先把编译与构建这条链路打通，读者才有可能在自己机器上复现后续的部署、参数、原理与模块实验。与此同时，本册必须时刻守住去重边界：02 册讲清楚「怎么把库造出来、怎么链进程序、怎么打包」，但不讲某个 EAL 参数在运行时如何生效（完整参数见 04-01），不讲收发包调用链（原理见 06-04），也不逐个罗列 ethdev、mempool、ring 等库的功能（模块见 07-01 至 07-12）。这条边界既避免了全套资料的重复注水，也让每一册的定位足够锋利。

### 2. 核心概念

要读懂 DPDK 的构建体系，先要厘清几个贯穿全册的核心概念。第一个是源码树与构建树的分离。所谓源码树，就是通过 git clone 或解压 tarball 得到的原始目录，其中包含 `meson.build`、`meson_options.txt`、`lib/`、`drivers/` 等只读或半只读的源文件；所谓构建树，是 `meson setup build` 命令在单独目录下创建出来的工作区，其中包含探测结果缓存、生成的头文件、`build.ninja` 以及编译产生的目标文件与最终库。DPDK 采用严格的 out-of-tree 构建，强烈不建议在源码根目录下直接编译，因为一旦把生成物混进源码树，切换分支、打补丁、清理构建产物都会变得异常困难，也容易让 `git status` 被大量未跟踪文件污染。

第二个概念是版本基准与发布形态。本册以 23.11 LTS、24.11 与 master 三套代码为讨论对象：LTS 分支追求长期稳定与向后兼容，适合生产环境；年度稳定版（如 24.11）包含较新的驱动与特性；master 则是滚动开发主线，构建选项变动最频繁。三者同名选项的取值与默认值可能不同，因此凡涉及 `meson_options.txt` 中具体条目，都应到所检出版本的该文件里核对，标注「需对照实际版本核验」。发行 tarball 与 git 仓库也有区别：前者是已经整理好的快照，通常附带校验文件与签名，适合离线与可复现构建；后者带完整提交历史，便于追踪某个构建选项在哪个提交被引入或改名。

第三个概念是编译期依赖与运行时依赖的分层。编译期依赖指配置与编译阶段必须存在的工具链与开发包，典型包括 meson、ninja、C 编译器（gcc 或 clang）、`pkg-config`、Python 3 及 `pyelftools`/`elftools` 模块、以及一组提供头文件的开发库（如 libnuma 的开发包、libpcap 的开发包、OpenSSL 或 zlib 的开发包、rdma-core 相关开发包等，具体清单随启用的驱动而变，需对照实际版本核验）。运行时依赖则指程序真正跑起来需要的资源：大页内存、被 VFIO 或 UIO 驱动接管的网卡、IOMMU 配置、以及动态库加载路径，这些属于 03 册而非本册。二者通过「构建选项」发生关联：例如启用某个 crypto PMD 会在配置阶段额外探测 OpenSSL 头文件，若缺失则配置失败或该驱动被自动跳过，这就是编译期依赖对产物形态的直接影响。

第四个概念是配置生成与头文件注入。DPDK 顶层与各子目录的 `meson.build` 会在配置阶段调用 `configure_file()`、`add_project_arguments()` 等机制，把架构宏、最大 lcore 数、最大以太网端口数、是否启用某驱动等信息写入生成的头文件，并注入全局编译参数。因此两个使用不同 `-D` 选项配置出来的构建树，即使源自同一份源码，编出的库在能力集上也可能明显不同。理解这一点，才能明白为什么 02-03 要把构建配置选项单独成篇、为什么排查「某个驱动没编进来」时第一步总是回看 `meson configure` 的输出。

第五个概念是产物的统一出口。现代 DPDK 的 meson 构建会把众多内部库聚合为统一的链接入口，并通过安装阶段生成的 `libdpdk.pc`（pkg-config 元数据文件）向外部应用暴露编译与链接参数。应用程序几乎不该手工去猜该链哪些 `.a` 或 `.so`，而应通过 `pkg-config --cflags --libs libdpdk` 获取。这一点是 02-04 的核心，也是 02-06 编译示例程序的依据。

### 3. 关键数据结构与源码位置

本节所说「数据结构」在构建语境下，指的是构建系统的描述文件与源码目录的组织结构，而非运行时内存中的 C 结构体；后者是 05 册的唯一权威源，本册只在必要时点名并给出路径，例如 `rte_mbuf`（`lib/mbuf/rte_mbuf.h`，字段见 05-02）、`rte_eth_dev`（`lib/ethdev/`，字段见 05-04）、`rte_memseg`（`lib/eal/`，字段见 05-07），一律不展开字段表，其内部机制亦写「原理见 06-xx」。

DPDK 的构建描述以顶层 `meson.build` 为总入口，以顶层 `meson_options.txt` 为全局选项字典，再通过 `subdir()` 逐层下钻到各个子目录。下面给出与构建最相关的源码地图，实际目录名与文件清单需对照所检出版本核验。

```tree
dpdk/
├── meson.build                 顶层构建入口，定义项目与全局依赖
├── meson_options.txt           全局构建选项定义（option 条目）
├── config/                     架构与平台配置总目录
│   ├── meson.build             架构探测、机器参数与宏定义
│   ├── x86/                    x86 架构相关配置
│   ├── arm/                    arm/aarch64 架构与 SoC 配置
│   ├── ppc/                    ppc64le 架构配置
│   └── riscv/                  riscv64 架构配置
├── buildtools/                 构建辅助脚本、版本脚本与生成器
├── lib/                        核心库：eal、ethdev、mbuf、mempool、ring
├── drivers/                    PMD 驱动：net、crypto、event、common
├── app/                        官方应用：testpmd、procinfo 等
├── examples/                   示例程序：helloworld、l2fwd、l3fwd
├── usertools/                  运维脚本：dpdk-devbind.py、dpdk-hugepages.py
├── devtools/                   开发者校验与检查脚本
├── doc/                        官方文档与 getting started 指南
└── kernel/                     内核模块目录（是否保留需对照实际版本核验）
```

下表把上述目录按「构建角色」做一次归类，帮助读者在排查构建问题时快速定位应该看哪个目录，而不是在整棵源码树里盲目搜索。

| 目录或文件 | 构建期角色 | 典型排查场景 |
|---|---|---|
| `meson.build`（顶层） | 项目声明、依赖探测、全局编译参数、递归入口 | 配置阶段报错、依赖找不到 |
| `meson_options.txt` | 定义所有 `-D` 可传选项的名称、类型与默认值 | 选项名写错、取值不合法 |
| `config/` 及子目录 | 按 CPU 架构与平台注入宏、机器参数与交叉配置 | 交叉编译、机器类型不匹配 |
| `buildtools/` | 生成版本脚本、map 文件、pkg-config 元数据与辅助检查 | 符号导出、`libdpdk.pc` 内容异常 |
| `lib/` | 核心库源码，每个库自带 `meson.build` | 某个库未被编入、禁用库选项 |
| `drivers/` | 各类 PMD 源码，按 net、crypto、event 等分类 | 驱动开关、驱动依赖缺失 |
| `app/` | testpmd 等官方应用的构建定义 | 应用未生成、工具缺失 |
| `examples/` | 示例程序及其 `meson.build` | `-Dexamples` 未生效 |
| `usertools/` | 安装到系统的 Python 运维脚本 | 安装后命令找不到 |
| `doc/` | 官方构建与入门文档，可定位选项说明 | 选项含义与版本差异核验 |

其中 `config/` 目录值得单独说明。它不是运行时配置文件，而是「架构相关的构建配置」集合：`config/meson.build` 负责根据 host machine 的 CPU 家族选取实现、设置缓存行大小与指令集相关宏，`config/x86/`、`config/arm/`、`config/ppc/`、`config/riscv/` 分别承载对应架构的机器定义与 SoC 参数（尤其在 arm 平台上，不同 SoC 的 `platform` 取值会显著改变实现选择）。交叉编译时用户提供的 cross file 往往要与 `config/` 下的架构定义配合，具体文件名与可用取值需对照实际版本核验。另一个高频访问点是 `buildtools/`：这里集中了被 `meson.build` 调用的生成脚本，负责产出链接用的版本脚本、ABI 映射以及安装到 `libdir/pkgconfig` 的 `libdpdk.pc`，理解它有助于解释「为什么链接一个简单示例需要带上那么多参数」。

### 4. 关键流程与调用链

从「拿到源码」到「生成可编译的构建树」，DPDK 在配置阶段形成一条相对固定的调用链，理解这条链对定位配置期故障至关重要。整个链路可以概括为：获取源码与校验完整性 → 准备编译期依赖 → meson 读取顶层 `meson.build` 并解析 `meson_options.txt` → 探测工具链、头文件与库 → 依据 host machine 进入 `config/` 下的架构分支 → 通过 `subdir()` 递归进入 `lib/`、`drivers/`、`app/`、`examples/` 等子目录，各子目录的 `meson.build` 依据选项决定哪些目标被纳入 → 调用 `buildtools/` 中的脚本生成配置头文件、版本脚本与 `libdpdk.pc` 模板 → 写出 `build.ninja` 与配置缓存 → 交由 02-02 的编译与安装阶段消费。

这条链的关键在于「递归」二字。顶层 `meson.build` 并不直接枚举每一个源文件，而是把决定权下放：例如 `lib/meson.build` 维护一份库清单，并按 `disable_libs`/`enable_libs` 之类的选项过滤（具体选项名需对照实际版本核验）；`drivers/meson.build` 与 `drivers/net/meson.build` 等则维护驱动清单，并结合依赖探测结果与 `disable_drivers`/`enable_drivers` 选项，决定每个 PMD 是编译、跳过还是报错；`examples/meson.build` 依据 `-Dexamples` 决定哪些示例被加入构建。因此「某个目标有没有被编出来」这个问题，几乎总能沿 `subdir()` 的递归路径，在对应子目录的 `meson.build` 与最终生效的选项组合里找到答案。

需要强调的是，这条配置链的输出是「构建描述」而非「二进制」。真正把源文件编译成目标文件、再归档成库、最后安装到前缀目录的动作，是 02-02 中 `ninja -C build` 与 `ninja install` 的职责。把配置期与编译期在概念上分开，是理解 meson/ninja 分工的基础：meson 类似传统 autotools 里的 configure，负责「决定要构建什么、用什么参数」；ninja 类似 make，负责「按依赖图高效执行编译」。二者之间的契约，就是配置阶段写出的 `build.ninja`。

### 5. 配置/命令/代码实例

下面给出一组从零获取 DPDK 源码并核对构建前置条件的完整命令。示例以 git 仓库为主，tarball 方式作对照；命令中的版本号、分支名与仓库地址仅示意，实际取值需对照官方发布页与所检出版本核验。

```bash
# 方式一：克隆官方仓库并检出指定版本
git clone https://dpdk.org/git/dpdk dpdk-src
cd dpdk-src
git tag --list
git checkout v23.11

# 方式二：下载发行 tarball 并做哈希校验
wget https://fast.dpdk.org/rel/dpdk-23.11.tar.xz
sha256sum dpdk-23.11.tar.xz
tar -xf dpdk-23.11.tar.xz

# 核对编译期工具链是否齐备
meson --version
ninja --version
pkg-config --version
python3 -c "import elftools; print(elftools.__version__)"
gcc --version | head -n 1
```

【输出判读】第一段 `Cloning` 与 `Receiving objects` 表明源码仓库完整拉取成功，若中途出现 `RPC failed` 或长时间停滞，多为网络或浅克隆参数问题，可考虑增大 `http.postBuffer` 或使用浅克隆后再按需 `fetch --unshallow`。`git tag --list` 的输出用于确认可用的版本标签，务必挑选与资料基准一致的 LTS 或稳定版标签，而不应直接在 master 上做可复现构建；`HEAD is now at ... version: 23.11.0` 则确认检出点是一个明确的发布提交，这一行是后续所有「需对照实际版本核验」结论的锚点。`sha256sum` 打印 `OK` 表示 tarball 的哈希与官方校验文件一致，若显示 `FAILED` 必须立即丢弃该包重新下载，切勿跳过完整性校验，否则可能引入被篡改或传输损坏的源码。工具版本区里，`meson --version` 应不低于该 DPDK 版本在 `meson.build` 中 `meson_version` 约束所要求的最低值，`ninja`、`pkg-config` 只需存在且可执行；`python3 -c "import elftools"` 能打印版本号说明 `pyelftools` 已安装，若抛 `ModuleNotFoundError` 则是最常见的配置期失败源之一，需通过发行包或 pip 补装。`gcc --version` 的首行用于确认默认编译器，交叉编译或多编译器共存环境下还要额外核对其目标架构。整体而言，只要这些值都在合理范围且无 `command not found`、`No module named` 之类的异常特征，就可以判定编译期前置条件已满足，可以进入 02-02 的配置与构建。

下表汇总最常见的编译期依赖及其缺失症状，作为上机前的自检清单；具体包名随发行版与 DPDK 版本变化，需对照实际版本核验。

| 依赖类别 | 典型包名（需核验） | 缺失时的典型症状 |
|---|---|---|
| 构建工具 | meson、ninja-build | `meson: command not found` 或版本过低报错 |
| 编译器 | gcc、clang | 配置阶段 `C compiler cannot create executables` |
| 元数据工具 | pkg-config | 依赖探测全部失败、无法定位头文件 |
| Python 模块 | python3-pyelftools | `Program python3 found` 之后构建脚本导入失败 |
| NUMA 开发库 | libnuma-dev（或 numactl-devel） | NUMA 相关头文件缺失，部分库被跳过 |
| 抓包开发库 | libpcap-dev | pcap PMD 被跳过或配置报错 |
| 加密开发库 | libssl-dev、zlib1g-dev | crypto 类 PMD 依赖探测失败 |
| RDMA 开发库 | librdmacm-dev、libibverbs-dev | mlx5 等依赖 rdma-core 的驱动无法启用 |

> 提示：只安装运行时库（例如仅 `libnuma1`）而不安装对应的 `-dev`/`-devel` 包，是「依赖装了却仍报错」的高频原因。构建需要的是头文件与链接桩，务必安装开发包。

### 6. 注意事项、陷阱与最佳实践

第一，务必锁定版本并保留检出证据。生产构建应基于明确的 tag 或 LTS 分支，而不是 master 的随意某个提交；建议把 `git describe`、`HEAD` 提交号、`meson --version` 与所用 `-D` 选项一起记录到构建日志，形成可复现的构建清单。发行 tarball 与 git 源码不要混用：不要把 tarball 解压出的目录再挂到某个 git 工作树上，也不要在含大量生成物的目录里切分支。

第二，警惕系统自带 meson 过旧。许多发行版仓库中的 meson 版本落后于 DPDK `meson.build` 里 `meson_version` 的约束，此时应通过 pip 在用户目录安装较新 meson，或用 `python3 -m mesonbuild.mesonmain` 指定版本，而非去改动 DPDK 的版本约束来「迁就」旧工具。同理，`pyelftools` 缺失在部分最小化安装环境里非常普遍，应提前验证导入。

第三，守住 out-of-tree 原则。始终让构建树与源码树分离，例如源码在 `dpdk-src/`，构建在 `dpdk-src/build/` 或并列的独立目录。这样清理只需删除构建目录，切换版本或对比不同选项组合时也能保留多份互不干扰的构建树。源码路径建议避免空格与非 ASCII 字符，减少脚本与工具链的边缘问题。

第四，正确区分编译期与运行时依赖。本册只在编译期依赖上用力：大页、VFIO 绑定、IOMMU、容器设备透传等属于 03 册，不必在构建阶段纠结；反过来，也不要把「大页没配」误判成「编译失败」。二者症状完全不同：前者是链接成功后运行期报内存或设备错误，后者是配置或编译阶段直接中断。

第五，留足磁盘与内存。完整构建 DPDK（尤其启用调试符号与大量示例时）会占用可观的磁盘空间，调试构建与静态库体积更大；并行编译虽快，但在内存受限的虚拟机上把 ninja 并行度开得过高可能触发 OOM，可按需用 `-j` 控制。

第六，把「需对照实际版本核验」当成纪律而非托辞。目录名（如 `kernel/` 是否仍保留）、选项名（`disable_drivers` 与 `enable_drivers` 的并存情况）、默认库策略、以及 `config/arm/` 下 SoC 配置文件的命名，都可能随版本变化。遇到与本文描述不一致时，正确的做法是直接打开所检出版本的 `meson_options.txt`、对应子目录的 `meson.build` 与 `doc/` 下的构建指南核对，而不是凭记忆硬套。

### 7. 小结与延伸阅读

本篇建立了全册的地基：明确了「编译与构建」为何独立成册，区分了源码树与构建树、编译期依赖与运行时依赖、配置生成与产物安装三组核心概念，给出了以 `meson.build`、`meson_options.txt`、`config/`、`buildtools/`、`lib/`、`drivers/`、`app/`、`examples/` 为骨架的源码地图，并沿 `subdir()` 递归梳理了从源码获取到写出 `build.ninja` 的配置链（图 02-01-01、图 02-01-02）。读者应带走的最重要结论是：DPDK 的构建是「配置期决定构建什么、编译期执行构建、安装期交付产物」的三段式，且源码与生成物严格分离。

下一步，02-02 将把本篇停留在概念层的配置链，落成 `meson setup build` → `ninja -C build` → `ninja install` 三条可复制命令，并逐步给出典型输出与验证方法；02-03 深入 `meson_options.txt` 与驱动库开关；02-04 讲清静态库、动态库与 `--whole-archive` 的链接语义；02-05 处理交叉编译；02-06 收束到打包、容器镜像与示例程序编译。延伸阅读建议直接查阅所检出版本的 `doc/guides/linux_gsg/build_dpdk.rst`（具体路径需对照实际版本核验）与顶层 `meson_options.txt`，二者分别是官方构建流程与选项字典的第一手依据。运行时参数请回查 04-01，结构体字段请回查 05 全册，机制调用链请回查 06 全册，模块功能请回查 07 全册。

## 02-02 meson / ninja 构建体系实战

### 1. 目标与拓扑

本篇是 C 型实战篇，目标非常具体：在一台干净的 x86_64 Linux 主机上，从 02-01 已准备好的 DPDK 源码出发，用三条核心命令 `meson setup build`、`ninja -C build`、`ninja install` 完成配置、编译与安装，并把产物安装到一个可控的前缀目录；随后通过一组验证手段确认库、pkg-config 元数据与示例程序都真实可用。全程给出可复制的命令、典型输出与逐行判读，使读者能够在自己机器上按图索骥地复现，而不是停留在概念描述。

之所以把这三步单列为一篇实战，是因为它们是 DPDK 构建体系的「主干道」：meson 负责配置并生成 `build.ninja`，ninja 依据该文件并行编译所有被选中的库、驱动、应用与示例，最后 `ninja install` 把头文件、库、pkg-config 文件、工具脚本与示例可执行文件复制到安装前缀。三者之间以构建目录为纽带，任何一步的疏漏都会在下一段暴露出来。理解其拓扑，也就理解了 meson 与 ninja 的分工边界：meson 是「生成器」，ninja 是「执行器」，安装是「交付动作」。

下图给出本篇要落地的三段式拓扑，图 02-02-01 中的产物会成为 02-04 链接与 02-06 打包的输入。

本拓扑刻意把「构建树」画成独立节点，是为了强调：验证环节大量命令都以 `build/` 为工作对象（`ninja -C build -t targets`、`meson configure build`），而安装产物在另一个目录（由 `-Dprefix` 决定）。把这两个目录分清楚，可以避免「改了配置却看了旧产物」这类常见误判。本篇只使用最小必要的命令与参数，凡属运行时 EAL 参数一律不展开，完整参数见 04-01。

### 2. 前置条件与环境

开始前需确认以下条件。第一，源码就位：已按 02-01  clone 或解压得到一份明确的 DPDK 版本，且 `git describe` 或 tarball 版本号可查。第二，工具链齐备：meson 版本满足顶层 `meson.build` 中 `meson_version` 的约束，ninja、`pkg-config`、gcc 或 clang、Python 3 与 `pyelftools` 可用，验证命令见 02-01。第三，编译期依赖到位：至少安装 NUMA 开发包，若计划启用 pcap、crypto 或 mlx5 等驱动，还需对应开发包，否则相关驱动会在配置阶段被跳过或被显式报错，具体包名需对照实际版本核验。第四，权限与空间：安装前缀若选在系统目录（如 `/usr/local`）则 `ninja install` 阶段需要相应写权限，建议先用用户可写的前缀（如 `/opt/dpdk` 或 `$HOME/dpdk-install`）走通全流程；源码加构建产物需要数 GB 量级磁盘，需对照实际版本核验。

建议的目录约定如下：源码位于 `~/work/dpdk-src`，构建树为 `~/work/dpdk-src/build`，安装前缀为 `~/work/dpdk-install`。使用用户可写前缀可以让整个流程无需 `sudo`，把排错范围收敛到构建本身。下面用一组命令核对环境并导出后续要用的变量。

```bash
# 设定本篇统一使用的路径变量
export DPDK_SRC="$HOME/work/dpdk-src"
export DPDK_BUILD="$DPDK_SRC/build"
export DPDK_PREFIX="$HOME/work/dpdk-install"
export PKG_CONFIG_PATH="$DPDK_PREFIX/lib/x86_64-linux-gnu/pkgconfig:$PKG_CONFIG_PATH"

cd "$DPDK_SRC"
meson --version
ninja --version
git describe --always --tags
df -h . | tail -n 1
```

以下为示例输出，具体格式需对照实际版本核验。

```text
1.3.2
1.11.1
v23.11
/dev/sda1        80G   32G   44G  44% /home
```

【输出判读】前两行分别是 meson 与 ninja 的版本，重点核对 meson 是否达到所检出版本 `meson.build` 中 `meson_version` 的下限；若低于下限，`meson setup` 会直接在开头报版本不满足并中止，这一步提前发现可省去后续无谓排查。`git describe --always --tags` 输出 `v23.11`，确认当前正处在一个明确的发布标签上，这是保证构建可复现的关键证据；若输出是形如 `v23.11-37-gabcdef` 的形式，说明工作点位于标签之后的若干提交，属于可接受但需记录的状态，若输出仅为短哈希则说明可能不在任何标签上，应警惕。`df -h` 一行显示挂载点剩余 44G、使用率 44%，对于完整构建通常足够；若使用率已很高或剩余不足，应提前清理，否则可能在链接大型静态库时因磁盘写满而失败。环境变量 `PKG_CONFIG_PATH` 这里提前指向了安装前缀下的 `pkgconfig` 目录，其中 `lib/x86_64-linux-gnu` 这类多级库目录名随发行版与 `-Dlibdir` 设置而变，属于必须「需对照实际版本核验」的点，若实际安装到 `lib64` 或 `lib` 需相应修正。`DPDK_PREFIX` 选择用户目录，意味着后续 `ninja install` 不需要 root 权限，这既是最佳实践也降低了误写系统目录的风险。

### 3. 分步操作

下面进入本篇主干，严格按 `meson setup build` → `ninja -C build` → `ninja install` 三步推进，每步都给出完整命令与预期输出。所有命令均可直接复制，续行命令的最后一行都带有完整参数、没有悬空反斜杠。

**步骤一：清理旧构建树（首次可跳过）**。若此前已用不同选项配置过，建议从干净状态开始，避免配置缓存与新选项冲突。

```bash
cd "$DPDK_SRC"
rm -rf build
```

**步骤二：配置——`meson setup build`**。这是决定「构建什么、用什么参数」的一步。核心命令就是 `meson setup build`；下面给出带若干常用选项的完整形式，读者可先用最简形式走通，再按需叠加。所有选项名与合法取值需对照所检出版本的 `meson_options.txt` 核验。

```bash
cd "$DPDK_SRC"
meson setup build \
  -Dbuildtype=release \
  -Dprefix="$DPDK_PREFIX" \
  -Ddefault_library=static \
  -Dexamples=l2fwd,l3fwd,helloworld \
  -Dwerror=false
```

以下为示例输出，具体格式需对照实际版本核验（不同版本的库与驱动清单、行数会有差异）。

【输出判读】开头的 `Version / Source dir / Build dir` 三行确认 meson 版本与源码树、构建树路径，务必核对 `Build dir` 正是期望的 `build` 目录而非源码根。`Project name: DPDK` 与 `Project version: 23.11.0` 确认项目与版本被正确识别，版本号应与 `git describe` 一致。`C compiler for the host machine` 与 `C linker` 两行给出被选中的编译器与链接器，交叉编译时这里会变成对应的交叉工具链（见 02-05）；`Host machine cpu family: x86_64` 与 `cpu: x86_64` 说明配置阶段识别到的目标架构，若与预期不符应立即停下检查环境或 cross file。`Program dpdk-gen-build-h found: YES` 与 `Configuring rte_build_config.h` 正是 02-01 所说的「配置生成」落地证据：生成的配置头文件被写入构建树而非源码树。依赖探测区里 `Dependency libnuma found: YES` 表示 NUMA 开发库可用，`drivers/net/mlx5 skipped: missing dependency, libibverbs` 则是一个典型的「驱动被自动跳过」提示——它说明 mlx5 依赖的 rdma-core 开发包缺失，meson 选择跳过而非报错，这类 `skipped` 行在排错时价值极高，因为它解释了「为什么某驱动没编出来」。`Build targets in project: 1187` 给出最终纳入构建的目标总数，是判断选项是否生效的量化指标：增减 `-Dexamples` 或驱动开关后，这个数字应随之变化。末尾 `User defined options` 逐行回显用户传入的 `-D` 值，用于确认没有拼写错误或类型错误；`Found ninja-1.11.1` 表明 meson 已成功定位 ninja 并写出 `build.ninja`，配置阶段到此圆满结束。若输出中出现 `ERROR:`、`Dependency ... found: NO` 后跟 `meson.build:...: ERROR: Problem encountered` 之类的异常特征，则配置失败，需按第 5 节处理。

**步骤三：复核配置——`meson configure build`（可选但强烈推荐）**。在编译前回看选项全貌，可避免「编完才发现选项没生效」。

```bash
meson configure build | grep -E "prefix|buildtype|examples|default_library"
```

若需临时改某个选项，不必删掉构建树，`meson configure build -Dexamples=l2fwd` 即可重配置并重生成 `build.ninja`（选项名需对照实际版本核验）。

**步骤四：编译——`ninja -C build`**。这是把源文件真正变成库的一步，也是三条核心命令中的第二条。

```bash
ninja -C build -j 4
```

```text
[1187/1187] Linking target app/dpdk-testpmd
```

【输出判读】首行 `ninja: Entering directory` 确认进入的是 `build` 目录，等价于在目录内执行 `ninja`。`[n/1187]` 形式的进度计数器分母应与配置阶段 `Build targets in project` 的数量大致对应，分子持续增长即表示编译正常推进；若长时间卡在某个目标且 CPU 占用为零，多为依赖脚本等待或环境异常。`Compiling C object ... .c.o` 行显示正在编译的具体源文件与所属库（如 `lib/librte_eal.a.p/`、`drivers/libtmp_rte_net_ixgbe.a.p/`），这一路径信息在定位某个文件的编译错误时非常有用。`Linking static target lib/librte_eal.a` 与 `lib/libdpdk.a` 表明静态库归档动作发生，`libdpdk.a` 正是 02-04 要讨论的聚合静态库；`Linking target examples/dpdk-l2fwd`、`app/dpdk-testpmd` 说明示例与应用可执行文件被成功链接，也反证 `-Dexamples=l2fwd,l3fwd,helloworld` 已生效。整个块以最后一条 `[1187/1187]` 且无 `FAILED:` 收尾即代表编译成功；任何 `FAILED:` 后跟编译器 `error:` 的行都是异常特征，应结合其上方源文件路径排查头文件缺失、选项冲突或源码与编译器不兼容等问题。

**步骤五：安装——`ninja install`**。这是三条核心命令中的第三条。推荐用 `ninja -C build install` 明确指定构建目录；它等价于先进入 `build` 再执行 `ninja install`，两种写法本文都列出以保证与不同资料的表述对齐。

```bash
ninja -C build install
# 等价写法：先进入构建目录再安装
cd build && ninja install
```

以下为示例输出，具体格式需对照实际版本核验。

```text
ninja: Entering directory `build'
[1/1] Installing files.
Installing /home/user/work/dpdk-install/include/rte_eal.h to /home/user/work/dpdk-install/include
Installing /home/user/work/dpdk-install/lib/x86_64-linux-gnu/libdpdk.a to /home/user/work/dpdk-install/lib/x86_64-linux-gnu
Installing libdpdk.pc to /home/user/work/dpdk-install/lib/x86_64-linux-gnu/pkgconfig
Installing /home/user/work/dpdk-src/usertools/dpdk-devbind.py to /home/user/work/dpdk-install/bin
Installing examples/dpdk-l2fwd to /home/user/work/dpdk-install/bin
```

【输出判读】`[1/1] Installing files.` 表明进入安装动作。逐行 `Installing ... to ...` 明确给出每个产物被复制到的目标位置：头文件进入 `include/`，聚合静态库 `libdpdk.a` 进入库目录，而 `Installing libdpdk.pc to .../pkgconfig` 是本篇最该关注的一行——它生成了供外部应用通过 pkg-config 获取编译与链接参数的元数据文件，是 02-04 与 02-06 的基础。`dpdk-devbind.py` 与示例可执行文件被安装到 `bin/`（具体安装子目录随版本与选项变化，需对照实际版本核验）。请特别核对库目录名 `lib/x86_64-linux-gnu`：它必须与步骤二里 `PKG_CONFIG_PATH` 的设定一致，否则后续 `pkg-config --libs libdpdk` 会找不到 `.pc` 文件。由于 `DPDK_PREFIX` 是用户目录，这里全程无需 root；若把前缀设为 `/usr/local` 且当前用户无写权限，末段会出现 `Permission denied` 之类的异常特征，应改用 `DESTDIR` 或调整权限，而不是盲目 `sudo` 掩盖路径设计问题。

**步骤六：让系统找到产物**。安装后刷新动态库缓存（共享库场景）并确认 pkg-config 可用。

```bash
export PKG_CONFIG_PATH="$DPDK_PREFIX/lib/x86_64-linux-gnu/pkgconfig:$PKG_CONFIG_PATH"
pkg-config --modversion libdpdk
```

其中库目录的多级名称需按步骤五的实际输出修正，属于必须核验的点。

### 4. 验证方法与预期结果

安装完成不等于「可用」，还需从构建树与安装前缀两个维度验证。第一维看构建树：`ninja -C build -t targets` 列出全部构建目标，`meson configure build` 回看最终选项；第二维看安装前缀：`pkg-config` 能否解析 `libdpdk`，头文件与库是否齐全，以及能否用 `pkg-config` 真正编译出一个示例。下面给出一组递进的验证命令，并配图说明其关系（图 02-02-02）。

:::figure id=02-02-02 | name=构建产物的三层验证链 | dir=TD
node n1 "构建树目标清单" blue
node n2 "安装前缀产物" teal
node n3 "libdpdk.pc 元数据" amber
node n4 "pkg-config 查询" purple
node n5 "编译最小示例" green
node n6 "运行期加载" gray
edge n1 -> n2 "ninja install"
edge n2 -> n3 "生成 pc 文件"
edge n3 -> n4 "--cflags --libs"
edge n4 -> n5 "驱动链接"
edge n5 -> n6 "执行验证"
edge n4 -> n1 dashed "不一致回查配置"
:::

```bash
# 第一层：构建树内目标是否齐全
ninja -C build -t targets all | grep -E "libdpdk|dpdk-l2fwd|dpdk-testpmd"

# 第二层：安装前缀中的关键产物
find "$DPDK_PREFIX" -name "libdpdk*" -o -name "libdpdk.pc"

# 第三层：pkg-config 元数据与一个最小编译验证
pkg-config --modversion libdpdk
pkg-config --cflags libdpdk
pkg-config --libs libdpdk --static

# 用安装好的头文件与库编译 examples 自带示例（路径需对照实际版本核验）
cc "$DPDK_SRC/examples/helloworld/main.c" -o /tmp/dpdk-helloworld \
  $(pkg-config --cflags --libs libdpdk)
```

以下为示例输出，具体格式需对照实际版本核验。

```text
lib/libdpdk.a: phony
examples/dpdk-l2fwd: phony
app/dpdk-testpmd: phony
/home/user/work/dpdk-install/lib/x86_64-linux-gnu/libdpdk.a
/home/user/work/dpdk-install/lib/x86_64-linux-gnu/pkgconfig/libdpdk.pc
23.11.0
-I/home/user/work/dpdk-install/include
-L/home/user/work/dpdk-install/lib/x86_64-linux-gnu -ldpdk
```

【输出判读】`ninja -C build -t targets` 的输出里出现 `lib/libdpdk.a`、`examples/dpdk-l2fwd`、`app/dpdk-testpmd` 三个目标，说明聚合库、示例与应用都在构建图中，且 `phony` 只是 ninja 对聚合目标的标注，属正常值。`find` 的两行分别定位到安装后的 `libdpdk.a` 与 `libdpdk.pc`，二者必须同时存在：只有库没有 `.pc` 会让 pkg-config 链路断裂，只有 `.pc` 没有库则是安装不完整。`pkg-config --modversion libdpdk` 返回 `23.11.0`，与配置、安装阶段打印的项目版本一致，是版本一致性的强校验。`--cflags` 返回 `-I.../include`，`--libs` 返回 `-L.../lib/x86_64-linux-gnu -ldpdk`（静态构建下 `--static` 还会展开大量 `-l` 依赖与链接器参数，具体清单需对照实际版本核验），这两行是应用程序编译命令的直接来源，也印证了 02-04 将展开的「用 pkg-config 而非手工链库」原则。最后一条 `cc` 命令若能无错误生成 `/tmp/dpdk-helloworld`，说明头文件、库与链接参数三者自洽，整条构建链路真正闭环。本阶段常见的异常特征是 `Package libdpdk was not found in the pkg-config search path`，它几乎总意味着 `PKG_CONFIG_PATH` 与步骤五实际库目录不一致，按安装输出修正即可。此处只验证「能否编译链接」，并不运行程序；运行期所需的大页、设备绑定与 EAL 参数属于 03 册与 04-01，本篇不展开。

下表把本篇三条核心命令与各自的验证点一一对应，便于作为上机检查表使用。

| 阶段 | 核心命令 | 成功标志 | 失败时的第一排查点 |
|---|---|---|---|
| 配置 | `meson setup build` | 打印 `Found ninja` 与选项回显 | 看 `ERROR:` 前的依赖或选项 |
| 编译 | `ninja -C build` | 末行进度满且无 `FAILED:` | 定位 `FAILED:` 上方源文件 |
| 安装 | `ninja install` | 出现 `libdpdk.pc` 安装行 | 前缀写权限与库目录名 |
| 验证 | `pkg-config --libs libdpdk` | 返回 `-ldpdk` 与库路径 | `PKG_CONFIG_PATH` 是否对齐 |

### 5. 常见失败与排错

其一，`meson setup` 阶段报 meson 版本过低或 `meson_version` 不满足。处理方式是升级用户态 meson，而非修改 DPDK 的约束；可用 `pip3 install --user meson` 后确认 `which meson` 指向新版本。其二，配置期 `Dependency ... found: NO` 或 Python 模块导入失败。最常见的是缺 `pyelftools` 或只装了运行时库没装 `-dev` 包，应回到 02-01 的依赖清单补齐；若某个驱动因此被 `skipped`，而该驱动又是必需的，则补齐依赖后重新 `meson setup`（或清理构建树重配），不能只重跑 ninja，因为驱动清单在配置期就已确定。

其三，`ninja: command not found` 或 `Found ninja` 未出现。说明 ninja 未安装或不在 PATH，补装后重跑 `meson setup`，让 meson 重新探测并写出 `build.ninja`。其四，编译期出现 `fatal error: xxx.h: No such file or directory`。通常与依赖头文件路径或架构配置有关，先确认对应开发包与 `config/` 探测结果；若为交叉编译场景，参见 02-05。其五，并行编译 OOM 或磁盘写满。用 `ninja -C build -j 2` 降低并行度，并清理磁盘；调试构建与静态库尤其占空间。

其六，`ninja install` 报 `Permission denied`。若前缀是系统目录，要么改用用户可写前缀，要么用 `DESTDIR` 暂存后由打包流程安装（见 02-06），不建议直接以 root 覆盖式安装掩盖路径问题。其七，安装后 `pkg-config` 找不到 `libdpdk`。九成是 `PKG_CONFIG_PATH` 与安装输出里的多级库目录不一致，尤其 Debian/Ubuntu 系常见 `lib/x86_64-linux-gnu`、其他发行版可能是 `lib64` 或 `lib`，需按实际安装行修正；共享库还需 `ldconfig` 或设置 `LD_LIBRARY_PATH`（属 02-04 范畴）。其八，`meson configure` 改了选项但产物没变。记住配置变更只重生成 `build.ninja`，必须重新执行 `ninja -C build` 与 `ninja install` 才会反映到产物上。

下表把典型错误信息与根因域做映射，便于快速收敛；具体报错文本随版本与工具链变化，需对照实际版本核验。

| 现象关键词 | 所属阶段 | 根因域 |
|---|---|---|
| `Meson version is` 且低于要求 | 配置 | 工具版本 |
| `No module named elftools` | 配置 | Python 依赖 |
| `Dependency libibverbs found: NO` | 配置 | 开发包缺失 |
| `C compiler cannot create executables` | 配置 | 工具链或 sysroot |
| `FAILED:` 伴 `error:` | 编译 | 源码或头文件 |
| `Permission denied` | 安装 | 前缀权限 |
| `Package libdpdk was not found` | 验证 | pkg-config 路径 |

### 6. 小结

本篇以 C 型实战的方式，把 02-01 的配置链落成了可复制的三条主干命令：`meson setup build` 决定「构建什么」并写出 `build.ninja`，`ninja -C build` 按依赖图完成编译与归档，`ninja install`（等价于 `ninja -C build install`）把库、头文件、`libdpdk.pc`、工具与示例交付到安装前缀。每一步都给出了典型输出与逐行判读，并强调 `skipped` 行、`Build targets in project`、`libdpdk.pc` 安装行、`PKG_CONFIG_PATH` 一致性这几个高价值观测点。验证环节从构建树目标清单、安装前缀产物、pkg-config 元数据到「编译一个最小示例」层层递进，确保构建结果不是「看起来成功」而是真正可用。

读者应带走三条经验：配置期决定产物形态，选项变更后必须重编译重安装；安装前缀与 `PKG_CONFIG_PATH` 中的库目录名必须与实际安装输出对齐；编译验证与运行验证要分开，本篇只保证到「能链接」，运行期的大页、设备与 EAL 参数分别见 03 册与 04-01。下一篇 02-03 将深入 `meson_options.txt`，逐一解释 `buildtype`、`default_library`、`examples`、`disable_drivers`、`machine` 等选项的作用域与作用域边界，把本篇「按选项决定构建什么」的机制讲透。延伸阅读：所检出版本的 `doc/guides/linux_gsg/build_dpdk.rst` 与 `meson_options.txt`（路径需对照实际版本核验）。

## 02-03 构建配置选项与驱动 / 库开关

### 1. 背景与动机

在 02-02 的实战流程里，读者已经反复看到 `-Dbuildtype=release`、`-Ddefault_library=static`、`-Dexamples=l2fwd,l3fwd` 这类写法，也看到 `meson configure build` 会把所有用户选项回显出来。这些 `-D` 参数并不是可有可无的点缀，而是 DPDK 构建体系的「方向盘」：同一份源码、同一套工具链，仅仅因为配置选项不同，最终可以编出体量相差数倍、能力集截然不同的产物——可能是只含少数几个网络 PMD 的精简静态库，也可能是启用全部驱动、示例、测试与文档的庞大构建树。因此，把选项体系单独成篇，讲清楚「有哪些选项、各自管什么范围、如何生效、版本间会怎么变」，是把 02-02 的「会敲命令」提升到「知道为什么这样敲」的关键一步。

从工程角度看，DPDK 的选项体系之所以值得深究，有三层原因。其一，选项数量多且分层：既有 meson 内建的通用选项（如 `buildtype`、`prefix`、`b_lto`、`b_sanitize`），也有 DPDK 项目自定义选项（如 `examples`、`machine`、`max_lcores`、`disable_drivers`），二者都以 `-D` 传入，却由不同层次的代码读取，混为一谈容易在排错时找错地方。其二，作用域不同：有的选项影响全局编译参数，有的只过滤 `lib/` 下的库清单，有的只作用于 `drivers/` 下某类 PMD，还有的要与 `config/` 里的架构分支配合才能生效。其三，版本漂移明显：`disable_drivers` 与 `enable_drivers` 在不同版本中的并存关系、`developer_mode` 的类型、`platform` 在 arm 平台上的取值集合都可能变化，凡是记忆不确切的选项名与合法取值，本册一律写「需对照实际版本核验」并指向 `meson_options.txt` 与对应子目录的 `meson.build`。

本篇与全册的去重边界保持一致：这里讨论的是「构建期选项」，即决定编什么、不编什么的开关，不涉及运行时 EAL 参数（完整参数见 04-01），也不展开某个驱动被编入后如何收发包的内部机制（原理见 06-04）或该驱动的功能清单（模块见 07-01 至 07-12）。例如我们会解释 `disable_drivers` 如何让某个 PMD 不进入构建图，但不会讲这个 PMD 的队列、描述符与卸载能力；我们会提到 `max_lcores` 是一个编译期上限宏，但不会展开 lcore 线程模型（原理见 06-01）。守住这条边界，本篇才能始终聚焦「构建配置」这一件事。

### 2. 核心概念

理解选项体系，先要理解 meson 中「选项」这一抽象本身。顶层 `meson_options.txt` 用一条条 `option()` 声明定义项目可用的选项，每条声明至少包含名称、类型与默认值，类型常见有 `boolean`（真/假）、`combo`（从有限集合里选一个）、`string`（字符串）、`array`（字符串数组）、`integer`（整数）与 `feature`（三态：enabled、disabled、auto）。用户在 `meson setup` 时通过 `-Dname=value` 覆盖默认值，在已配置的构建树上则用 `meson configure build -Dname=value` 重配置；所有生效值最终存储在构建树的配置缓存里，并可通过 `meson configure build` 完整回显。下面给出一段 `meson_options.txt` 条目示意，具体条目以所检出版本为准，需对照实际版本核验。

```text
option('examples', type: 'string', value: '',
       description: 'Comma-separated list of examples to build')
option('tests', type: 'boolean', value: false,
       description: 'Build unit tests')
option('machine', type: 'combo', choices: ['default', 'native'],
       value: 'default', description: 'Machine type to optimize for')
option('disable_drivers', type: 'string', value: '',
       description: 'Comma-separated list of drivers to disable')
option('max_lcores', type: 'string', value: '',
       description: 'Maximum number of lcores, empty means default')
```

需要特别区分的是「项目自定义选项」与「meson 内建选项」。`buildtype`、`prefix`、`libdir`、`includedir`、`default_library`、`b_lto`、`b_sanitize`、`werror`、`c_args`、`c_link_args` 等属于 meson 内建或 DPDK 借用的通用选项，往往带 `b_` 前缀或由 meson 直接解释；而 `examples`、`disable_drivers`、`machine`、`platform`、`max_lcores`、`max_ethports`、`enable_docs` 等是 DPDK 在 `meson_options.txt` 里自己声明的。二者都通过 `-D` 设置，但读取方不同：内建选项由 meson 在生成编译命令时直接消费，项目选项则由各 `meson.build` 通过 `get_option('name')` 读取后参与条件判断。排错时若某个 `-D` 没起作用，先判断它属于哪一类，再决定是去看 meson 文档还是去看 DPDK 的 `meson.build`。

`feature` 类型是另一个易混淆点。它不像 `boolean` 那样只有真假，而是 `enabled`、`disabled`、`auto` 三态：`auto` 表示「依赖满足就启用、不满足就跳过」，`enabled` 表示「依赖不满足就报错」，`disabled` 表示「一定不启用」。DPDK 中部分可选能力与驱动探测会用到类似语义，这解释了为什么 02-02 的输出里会出现 `skipped: missing dependency` 而不是直接失败——那正是 `auto` 类行为的表现。具体哪些选项采用 `feature` 类型需对照实际版本核验。

第三个概念是「选项作用域」。`prefix`、`buildtype`、`werror` 这类是全局性的，影响整个构建；`disable_libs`/`enable_libs` 只作用于 `lib/meson.build` 维护的库清单；`disable_drivers`/`enable_drivers` 只作用于 `drivers/` 下的驱动清单；`examples` 只作用于 `examples/meson.build`；`machine` 与 `platform` 则要配合 `config/` 下按架构选择实现。理解作用域，就能把「某类目标没编出来」快速定位到应该检查的 `meson.build`。最后一个概念是「配置与编译的时序」：选项只在配置期被读取并固化进 `build.ninja` 与生成的头文件，`meson configure` 改值后只重生成构建描述，必须重新执行 `ninja -C build` 才会改变产物——这一点在 02-02 已埋下伏笔，本篇会反复印证。

### 3. 关键数据结构与源码位置

与 02-01 一致，本节的「结构」指构建描述的组织，而非运行时 C 结构体；运行时结构体一律点名加路径并写「（字段见 05-xx）」，例如 `rte_eth_dev`（`lib/ethdev/`，字段见 05-04）、`rte_mempool`（`lib/mempool/`，字段见 05-03），不展开字段，内部机制写「原理见 06-xx」。

选项体系的源码落点可以被归纳为「一个字典、若干清单、一批读取点」。一个字典即顶层 `meson_options.txt`，是所有项目自定义选项的唯一声明处；若干清单指 `lib/meson.build` 里的库列表、`drivers/meson.build` 与各子目录（如 `drivers/net/meson.build`、`drivers/crypto/meson.build`、`drivers/event/meson.build`）里的驱动列表、`examples/meson.build` 里的示例列表、`app/meson.build` 里的应用列表；一批读取点则是这些 `meson.build` 中调用 `get_option()` 并据以 `foreach` 过滤目标的位置，以及 `config/meson.build` 里依据 `machine`/`platform` 注入宏的位置。下表把常见选项按作用域归类，取值集合与默认值均需对照实际版本核验。

| 选项名（需核验） | 类型 | 作用域 / 读取点 | 作用简述 |
|---|---|---|---|
| `buildtype` | combo（内建） | meson 全局 | 优化与调试等级，如 release 或 debug |
| `default_library` | combo（内建） | meson 全局 | 产物为 static、shared 或 both |
| `prefix` | string（内建） | meson 全局 | 安装前缀，install 阶段生效 |
| `werror` | boolean | meson 全局 | 把编译警告提升为错误 |
| `examples` | string | `examples/meson.build` | 逗号分隔的示例名清单 |
| `tests` | boolean | `app/test/meson.build` | 是否构建单元测试 |
| `enable_docs` | boolean | `doc/meson.build` | 是否构建文档 |
| `disable_drivers` | string | `drivers/` 各层 | 逗号分隔的驱动禁用清单 |
| `enable_drivers` | string | `drivers/` 各层 | 白名单式驱动启用清单 |
| `disable_libs` | string | `lib/meson.build` | 逗号分隔的库禁用清单 |
| `machine` | combo | `config/meson.build` | 目标机器优化类型 |
| `max_lcores` | string | 生成配置头 | lcore 数量编译期上限 |
| `max_ethports` | string | 生成配置头 | 以太网端口数编译期上限 |
| `platform` | combo | `config/arm/` 等 | arm SoC 或平台实现选择 |

`config/` 目录在选项体系里扮演「架构放大器」的角色：`machine` 取 `native` 时构建会针对本机 CPU 做优化，产物可移植性下降；取 `default` 时走通用实现；在 arm 平台上 `platform` 的取值还会决定 `config/arm/` 下选用哪组 SoC 参数与指令集实现。由于这类取值集合随版本持续扩充，任何具体列表都必须回到所检出版本的 `config/meson.build` 与 `config/arm/meson.build` 核对，标注「需对照实际版本核验」。另一个值得记住的落点是 `buildtools/`：选项影响到的宏与导出符号，最终经这里的脚本写入生成的头文件与版本脚本；因此当怀疑「选项改了但能力没变」时，除了看 `meson configure`，还应检查构建树里生成的 `rte_build_config.h`（文件名需对照实际版本核验）。

### 4. 关键流程与调用链

一个 `-D` 选项从命令行走到最终产物，经历的是一条清晰但分散的链路。以 `meson setup build -Ddisable_drivers=net/mlx5,crypto/qat` 为例：meson 首先解析 `meson_options.txt`，把用户值写入构建树的配置缓存；随后顶层 `meson.build` 通过 `subdir('drivers')` 进入驱动层，`drivers/meson.build` 与各分类子目录的 `meson.build` 调用 `get_option('disable_drivers')` 取得禁用清单，在遍历驱动列表时把命中的驱动标记为不构建；对未被禁用的驱动，再逐个执行依赖探测（如 mlx5 需要 rdma-core 开发包），依赖缺失时依据 `feature` 语义选择跳过或报错；所有通过过滤的目标被登记进构建图，最终写入 `build.ninja`；到了 02-02 的 `ninja -C build` 阶段，ninja 只编译登记过的目标，被禁用的驱动连目标文件都不会产生。这一链路解释了「选项—清单—依赖—构建图—产物」的因果，也说明为何选项必须在配置期确定、编译期无法补救。

### 5. 配置/命令/代码实例

下面给出一组围绕选项的常用命令：先查看某构建树的全部选项，再演示重配置、驱动开关与示例开关，最后观察目标数量的变化。所有选项名、取值与输出条目需对照实际版本核验。

```bash
# 查看构建树当前所有选项（含默认值与生效值）
meson configure build | head -n 40

# 重配置：只改动个别选项，不删除构建树
meson configure build -Dbuildtype=debugoptimized -Dexamples=l2fwd,l3fwd

# 用黑名单裁掉不需要的驱动类别（写法需对照实际版本核验）
meson setup build-min -Ddisable_drivers=net/mlx5,crypto/qat \
  -Dexamples= -Dbuildtype=release

# 对比两份配置的目标数量，确认过滤生效
ninja -C build -t targets all | wc -l
ninja -C build-min -t targets all | wc -l
```

以下为示例输出，具体格式需对照实际版本核验。

```text

  Source dir /home/user/work/dpdk-src

  buildtype          debug     [debug, debugoptimized, release]
```

【输出判读】`meson configure build` 的输出分为 `Core properties`、`Main project options` 与 `User defined options` 三段，这是判读的关键框架。`Core properties` 里的 `Source dir` 与 `Build dir` 再次确认正在查看的是哪棵构建树，避免改错目录。`Main project options` 逐行给出选项的「当前值」与「合法取值集合」：`buildtype debug [debug, debugoptimized, release]` 表示当前为 debug、合法值是一个 combo 集合，若传入集合外的值，meson 会在配置阶段直接报取值非法；`default_library static [shared, static, both]` 说明当前构建静态库，合法值为三者之一，这类方括号是判断 combo 选项写法的直接依据。`examples l2fwd (just set)` 中的 `(just set)` 表示该值刚被本次 `meson configure` 修改、尚未固化到编译产物，正好印证「重配置只改描述、必须重新编译」的时序。末尾 `User defined options` 回显用户显式传入的值，用于确认没有把 `debugoptimized` 之类的 combo 值拼错。最后两段 `wc -l` 的输出 `1187` 与 `402` 是本篇最直观的量化证据：启用多个示例与全部驱动的完整构建，目标数远大于用 `-Ddisable_drivers` 与空 `-Dexamples` 裁剪后的精简构建。若两个数字几乎相同，说明 `disable_drivers` 选项名或取值写法在该版本不生效，应回到 `meson_options.txt` 核对（需对照实际版本核验）。异常特征还包括 `ERROR: Value "xxx" for option "yyy" is not one of the choices` 与 `Unknown option`，前者是 combo 取值越界，后者是选项名在该版本不存在或已改名，二者都属于典型的版本漂移问题。

下表把几类高频配置意图与推荐做法对应起来，作为速查；单元格中的逗号列表写法与选项名需对照实际版本核验。

| 配置意图 | 推荐选项组合 | 预期效果与注意点 |
|---|---|---|
| 生产精简构建 | `buildtype=release` 加黑名单 | 关闭调试符号，裁掉无用驱动 |
| 开发调试构建 | `buildtype=debug` 加 `werror=false` | 保留符号，便于断点与单步 |
| 只出共享库 | `default_library=shared` | 产物为 .so，需处理加载路径 |
| 静态与动态都要 | `default_library=both` | 两份产物并存，磁盘占用翻倍 |
| 指定安装位置 | `prefix=/opt/dpdk` | install 阶段才生效 |
| 针对本机优化 | `machine=native` | 可移植性下降，勿用于分发 |
| 增编示例 | `examples=l2fwd,l3fwd` | 目标数应随之上升 |
| CI 严格门禁 | `werror=true` | 警告即失败，新编译器易误报 |

### 6. 注意事项、陷阱与最佳实践

第一，把「需对照实际版本核验」落实为动作。`disable_drivers` 与 `enable_drivers` 在不同版本中的支持情况、`developer_mode` 的类型（boolean 还是 feature）、`platform` 的合法取值、以及 `max_lcores`/`max_ethports` 究竟是 integer 还是 string，都可能与本文示意不同。遇到 `Unknown option` 或取值报错，正确做法是打开 `meson_options.txt` 与对应 `meson.build`，而不是照搬其他版本的命令。

第二，注意类型与写法。`string` 类型的多值选项（如 `examples`、`disable_drivers`）通常用逗号分隔且不加空格；`combo` 只能取声明集合内的值；`array` 类型在某些版本里要用方括号或分号分隔（需对照实际版本核验）；`feature` 的 `auto` 与 boolean 的 `true` 语义不同。把「`static` 或 `shared`」这类二选一关系误当成可一次传入的值，是常见的低级错误——`default_library` 一次只能取一个 combo 值，要两份产物应选 `both`。

第三，牢记时序。改动任何选项后，`meson configure build` 只是更新了配置缓存与 `build.ninja`，必须重新 `ninja -C build` 与 `ninja install` 才会反映到库与安装前缀上。「改了选项却看旧产物」是最容易浪费时间的误判，建议每次重配置后都重跑一次 `meson configure build` 回显确认，并观察目标数或 `libdpdk.pc` 是否变化。

第四，谨慎使用库开关。`disable_libs` 看似能显著缩小产物，但 DPDK 库之间存在依赖，贸然禁用基础库可能导致上层库或应用连带被跳过甚至配置失败；裁剪前应先看清 `lib/meson.build` 中的依赖关系（依赖本身是否显式声明需对照实际版本核验）。相比之下，驱动黑名单对产物体积的影响更直接、副作用更可控，是首选的裁剪手段。

第五，区分构建期上限与运行时参数。`max_lcores`、`max_ethports` 等选项决定的是编译期数组与位图规模，属于构建配置；它们与运行时通过 EAL 参数指定 lcore 掩码、端口白名单是两回事，后者完整参数见 04-01，本篇不重列，也不展开 lcore 线程模型（原理见 06-01）。把二者混为一谈，常导致「改了编译期上限却指望它限制运行时行为」的困惑。

第六，慎用 `machine=native` 与 `werror=true` 做分发构建。前者会把产物绑定到构建机 CPU，迁移到不同型号机器可能触发非法指令；后者在 CI 换用新版编译器时容易被新增警告卡住。生产构建通常选 `machine=default` 加固定工具链，并把 `werror` 留给专门的代码门禁作业。

### 7. 小结与延伸阅读

本篇把 02-02 里零散出现的 `-D` 参数系统化：先区分项目自定义选项与 meson 内建选项、阐明 `boolean`/`combo`/`string`/`array`/`feature` 等类型与 `-D` 传参语法，再以「一个字典（`meson_options.txt`）、若干清单（`lib/`、`drivers/`、`examples/`、`app/` 下的 `meson.build`）、一批读取点（`get_option()`）」勾勒源码落点，最后沿「命令行 → 配置缓存 → 各层 `meson.build` → 清单过滤 → 依赖探测 → `build.ninja` → 编译产物」梳理了选项传播链（图 02-03-01），并用图 02-03-02 说明驱动与库开关受白名单、黑名单与依赖探测共同约束。读者应带走的核心结论是：选项是编译期决策，改值后必须重编译重安装；裁剪优先用驱动黑名单而非库黑名单；凡选项名与取值集合，一律以所检出版本的 `meson_options.txt` 为准。

## 02-04 静态库、动态库与链接方式

### 1. 背景与动机

在 02-03 的选项表里，`default_library` 是一个看似普通、实则影响深远的 combo 选项：它决定 DPDK 最终以 `.a` 静态库、`.so` 共享库还是两者并存的形式交付。对刚接触 DPDK 的开发者而言，最容易踩、也最容易被忽视的坑，恰恰出现在这里——用静态库链接一个简单示例时，程序能编译、能链接、能启动，却「看不到任何网卡」，排查半天才发现是驱动根本没被注册。这个现象背后的机制，是 DPDK 依靠构造函数把 PMD 注册进全局链表，而静态链接时链接器默认只从归档中抽取被直接引用的目标文件，导致承载注册逻辑的目标文件被丢弃。要解决它，必须理解 `--whole-archive`、链接顺序与 `pkg-config` 的分工。这正是本篇要系统讲清的内容。

把链接方式独立成篇，还有三层现实理由。其一，DPDK 的产物形态经历过变化：早期版本与 Makefile 时代交付的是一大批 `librte_*.a`，应用程序需要手工罗列冗长的库清单；现代 meson 构建则把内部库聚合为统一的 `libdpdk.a` 或 `libdpdk.so`，并通过安装阶段生成的 `libdpdk.pc`（pkg-config 元数据）对外暴露编译与链接参数。两种形态对应的链接命令差别很大，混用旧资料里的手工清单极易出错（具体聚合策略需对照实际版本核验）。其二，静态与动态在运行期行为上不同：静态库把代码复制进可执行文件，部署简单、不依赖目标机上的 DPDK 运行时；共享库则涉及 `rpath`、`LD_LIBRARY_PATH`、`ldconfig`、SONAME 与 ABI 兼容性，容器与跨机分发时尤须小心。其三，`pkg-config` 是连接「构建产物」与「应用程序」的统一出口，02-06 编译 `examples/`、02-02 的验证环节都依赖它，但 `--cflags`、`--libs`、`--static` 各自返回什么、为什么静态链接必须加 `--static`，需要一篇专门说明。

本篇严格守住构建边界：讨论的是「库怎么被链接进程序」「链接参数从哪来」，不展开构造函数注册之后 EAL 如何枚举设备（原理见 06-01、06-04），不罗列驱动功能（模块见 07-01），不重列运行时 EAL 参数（完整参数见 04-01），涉及运行时结构体只点名加路径并写「（字段见 05-xx）」。

### 2. 核心概念

第一个概念是静态库与共享库的本质差异。静态库（`.a`）是若干目标文件（`.o`）的归档，链接时链接器从归档中「按需抽取」：只有被可执行文件中未解析符号引用到的目标文件才会被复制进最终产物，其余直接丢弃；链接完成后可执行文件不再依赖库文件。共享库（`.so`）则在链接期只记录一个依赖声明，真正的代码在程序加载或运行时由动态链接器映射进来，因此产物小、多进程可共享同一份代码，但要求目标环境存在匹配版本的 `.so`。DPDK 的 `default_library=static / shared / both` 正是控制这一形态的开关，取值集合需对照实际版本核验。

第二个概念是聚合库与 pkg-config 元数据。现代 DPDK 把 EAL、ethdev、mbuf、mempool、ring 以及各 PMD 等内部库聚合成单一链接入口（常见为 `libdpdk.a` 或 `libdpdk.so`，实际名称与是否仍保留分库需对照实际版本核验），同时安装一个 `libdpdk.pc` 文件。该 `.pc` 文件用 `prefix`、`libdir`、`includedir` 定位路径，用 `Cflags` 提供头文件包含参数，用 `Libs`/`Libs.private` 提供链接参数，用 `Requires.private` 声明私有依赖。应用程序的正确姿势是 `cc app.c -o app $(pkg-config --cflags --libs libdpdk)`，让 `.pc` 替自己拼出完整命令，而不是手工猜测该链哪些库。

第三个、也是本篇最关键的概念，是 `--whole-archive` 与构造函数注册。DPDK 的驱动与部分库通过「构造函数」在 `main` 之前自动完成注册（相关注册宏的准确名称需对照实际版本核验，常见形如基于编译器 `__attribute__((constructor))` 的封装），把 PMD 挂到全局的设备/驱动链表上，供后续初始化阶段枚举（原理见 06-01、模块见 07-01）。问题在于：静态链接时，如果应用代码只显式调用了 `rte_eal_init` 等少数符号，链接器只会从 `libdpdk.a` 里抽取包含这些符号的目标文件，而那些「只通过构造函数起作用、没有任何外部符号被直接引用」的驱动目标文件就会被丢弃，注册自然无从发生。解决办法是用链接器参数 `-Wl,--whole-archive ... -Wl,--no-whole-archive` 把聚合库整体链入，强制保留全部目标文件。共享库不存在此问题：动态加载 `.so` 时其所有构造函数都会被执行。

第四个概念是链接顺序与循环依赖。静态链接对库的出现顺序敏感，若库之间存在相互引用，可能需要 `-Wl,--start-group ... -Wl,--end-group` 让链接器反复扫描；此外 `--as-needed` 会剔除「看似未使用」的共享库依赖，也可能误伤仅靠构造函数生效的库。`libdpdk.pc` 的 `Libs.private` 字段通常已经把 `--whole-archive`、线程库、动态加载库、`libnuma` 等依赖按正确顺序列好，这正是「用 pkg-config 而非手写链接命令」的根本原因。

第五个概念是运行期加载路径。使用共享库时，可执行文件需要能在运行时找到 `libdpdk.so` 及其依赖：可通过链接期写入的 `rpath`、环境变量 `LD_LIBRARY_PATH`、`/etc/ld.so.conf` 加 `ldconfig`，或把库装到系统默认路径解决。SONAME 与 ABI 版本则决定不同 DPDK 版本之间能否平滑替换，属于 08-05 迁移主题的前置知识，本篇只点到为止。

### 3. 关键数据结构与源码位置

同样，本节聚焦构建产物与元数据，不展开运行时 C 结构体；例如 `rte_eth_dev`（`lib/ethdev/`，字段见 05-04）、`rte_mempool`（`lib/mempool/`，字段见 05-03）只在此点名，机制写「原理见 06-xx」。

链接相关的源码落点主要有四处。其一是 `lib/meson.build` 与各库子目录的 `meson.build`：它们定义每个内部库的源文件与依赖关系，并决定最终如何聚合成 `libdpdk.a`/`libdpdk.so`（聚合策略需对照实际版本核验）。其二是各库目录下的版本脚本（常见命名如 `version.map`，实际文件名需对照实际版本核验）：它们控制哪些符号被导出，直接决定应用程序的可见 API 面。其三是 `buildtools/`：这里集中了生成 `libdpdk.pc`、版本脚本与安装规则的脚本，是「为什么 `Libs.private` 里会有 `--whole-archive`」的答案所在。其四是 `examples/meson.build` 与各示例目录：现代 DPDK 的示例通过 `dependency('libdpdk')` 声明对聚合库的依赖，由 meson 自动套用 `.pc` 提供的参数，是「正确链接姿势」的官方范例。

下面给出一份 `libdpdk.pc` 的内容示意，字段与取值需对照实际版本核验。

```ini
prefix=/home/user/work/dpdk-install
libdir=${prefix}/lib/x86_64-linux-gnu
includedir=${prefix}/include

Name: libdpdk
Description: The Data Plane Development Kit (DPDK)
Version: 23.11.0
Requires.private: libnuma, libpcap
Libs: -L${libdir} -ldpdk
Libs.private: -Wl,--whole-archive -L${libdir} -ldpdk -Wl,--no-whole-archive -lpthread -ldl -lm -lnuma
Cflags: -I${includedir}
```

```tree

│   ├── rte_eal.h

├── lib/x86_64-linux-gnu/
```

下表把 `libdpdk.pc` 的关键字段与用途逐一对应，帮助读者在 `pkg-config` 返回异常时定位到具体字段。

| 字段 | 含义 | 对链接的影响 |
|---|---|---|
| `prefix` | 安装根路径 | 其余路径变量的基准 |
| `libdir` | 库文件目录 | 生成 `-L` 参数 |
| `includedir` | 头文件目录 | 生成 `-I` 参数 |
| `Version` | DPDK 版本 | `pkg-config --modversion` 的返回 |
| `Libs` | 公开链接参数 | 动态链接常用路径 |
| `Libs.private` | 静态链接私有参数 | 含 whole-archive 与系统库 |
| `Requires.private` | 私有依赖声明 | 静态链接时展开依赖 |
| `Cflags` | 编译参数 | 提供头文件包含路径 |

关于「运行时数据结构」与本节的关系，只需记住一点：`libdpdk.pc` 里的 `Requires.private` 之所以列出 `libnuma`、`libpcap` 等，是因为某些库与 PMD 在编译期用到了它们；这与运行时「大页如何分配」「设备如何绑定」无关，后者属于 03 册与 06 全册。结构体字段定义一律见 05 全册。

### 4. 关键流程与调用链

从一条链接命令到「驱动在运行时可用」，存在两条略有差异的链路。静态链接链为：应用源码调用 DPDK API → `cc $(pkg-config --cflags --libs --static libdpdk)` 展开参数 → 链接器遇到 `-Wl,--whole-archive` 后把 `libdpdk.a` 中全部目标文件纳入 → 承载注册逻辑的目标文件被保留 → 程序加载时，这些目标文件里的构造函数在 `main` 之前执行，把 PMD 注册进全局链表 → `rte_eal_init` 阶段能够枚举到设备（初始化流程见 06-01、驱动层见 07-01）→ 应用可用。若省略 `--whole-archive`（也就是没用 `pkg-config --static` 提供的 `Libs.private`），链接器只抽取被直接引用的目标文件，驱动注册目标被丢弃，后续初始化便「看不到设备」——这就是本篇开头那个经典坑的完整因果。

动态链接链则短得多：链接期只在可执行文件里记录 `NEEDED` 项指向 `libdpdk.so`，加载时由动态链接器映射该 `.so`，其构造函数随加载自动执行完成注册，无需 `--whole-archive`。代价是运行期必须能解析到 `.so` 及其依赖。两条链路的差异，也正是 `default_library` 选项在运行期表现出来的区别。

### 5. 配置/命令/代码实例

下面给出一组对比命令：先看 `pkg-config` 在不同参数下返回什么，再分别用静态与动态方式编译同一个示例，最后用 `ldd` 与 `nm` 验证产物。所有参数与输出需对照实际版本核验。

```bash
# 观察 cflags、libs 与 static 三种查询的差异
pkg-config --cflags libdpdk
pkg-config --libs libdpdk
pkg-config --libs --static libdpdk

# 静态方式编译示例（--static 会带上 Libs.private 的 whole-archive）
cc "$DPDK_SRC/examples/l2fwd/main.c" -o /tmp/l2fwd-static \
  $(pkg-config --cflags --libs --static libdpdk)

# 动态方式编译示例
cc "$DPDK_SRC/examples/l2fwd/main.c" -o /tmp/l2fwd-shared \
  $(pkg-config --cflags --libs libdpdk)

# 验证产物依赖与注册相关符号是否存在
ldd /tmp/l2fwd-shared | grep dpdk
nm /tmp/l2fwd-static | grep -c "rte_"
```

以下为示例输出，具体格式需对照实际版本核验。

```text
-I/home/user/work/dpdk-install/include
-L/home/user/work/dpdk-install/lib/x86_64-linux-gnu -ldpdk
-L/home/user/work/dpdk-install/lib/x86_64-linux-gnu -Wl,--whole-archive -ldpdk -Wl,--no-whole-archive -lpthread -ldl -lm -lnuma -lpcap
        libdpdk.so.24 => /home/user/work/dpdk-install/lib/x86_64-linux-gnu/libdpdk.so.24 (0x00007f2c1a200000)
4127
```

【输出判读】前三行是三次 `pkg-config` 查询的返回，构成本篇最核心的对照。`--cflags` 只返回 `-I.../include`，负责让编译器找到 `rte_eal.h` 等公共头文件。`--libs` 返回 `-L.../lib/x86_64-linux-gnu -ldpdk`，这是动态链接所需的全部参数——仅仅声明库路径与库名，运行时再由加载器映射 `.so`。`--libs --static` 的返回明显更长：除了同样的 `-L` 与 `-ldpdk`，还出现了 `-Wl,--whole-archive` 与 `-Wl,--no-whole-archive` 这对包裹参数，以及 `-lpthread -ldl -lm -lnuma -lpcap` 等系统依赖。这对包裹参数正是 02-04 反复强调的关键，它保证 `libdpdk.a` 的全部目标文件被链入，从源头避免驱动注册目标被丢弃；后面的系统库则来自 `Libs.private` 与 `Requires.private`，静态链接时由于没有动态依赖传递，必须显式列出。若 `--static` 的返回里缺少 `--whole-archive`，应检查所检出版本 `libdpdk.pc` 的 `Libs.private` 写法（需对照实际版本核验）。`ldd` 一行显示动态产物依赖 `libdpdk.so.24` 并给出解析到的绝对路径，说明 `rpath` 或 `LD_LIBRARY_PATH` 已正确生效；若此处出现 `not found`，即是运行期加载路径配置问题。最后 `nm | grep -c "rte_"` 返回 `4127`，表示静态产物中包含了大量 `rte_` 前缀符号，间接印证聚合库被整体链入；若这个数字异常小，往往意味着 `--whole-archive` 没生效、大量符号随目标文件一起被丢弃。需要提醒的是，本组只验证「链接与符号是否齐全」，并不实际运行程序；运行所需的大页、设备绑定与 EAL 参数属于 03 册与 04-01，本篇不展开。

下表把静态与动态两种方式在关键维度上的差异做一次收敛，便于按部署场景选型。

| 维度 | 静态库（.a） | 共享库（.so） |
|---|---|---|
| 链接参数来源 | `Libs.private` 加 `--static` | `Libs` 常规查询 |
| whole-archive | 必需，否则丢驱动 | 不需要 |
| 可执行文件体积 | 较大，代码复制进产物 | 较小，只记依赖 |
| 运行期库依赖 | 无需目标机安装 DPDK | 需可解析到匹配 .so |
| 加载路径处理 | 一般不涉及 | rpath、LD_LIBRARY_PATH 或 ldconfig |
| 多进程共享代码 | 否，各自一份 | 是，同一物理页可共享 |
| 版本升级影响 | 需重新链接应用 | 替换 .so 即可，须顾及 ABI |
| 容器镜像适配 | 常用来减少运行时依赖 | 需一并打包 .so 与依赖 |

### 6. 注意事项、陷阱与最佳实践

第一，把「静态链接看不到驱动」列为首要检查项。凡是静态方式链接的应用出现「设备为零」「PMD 没注册」一类现象，先确认编译命令里用了 `pkg-config --static`，且 `Libs.private` 里确实有 `--whole-archive` 包裹。手工拼链接命令时漏掉这一对参数，是 DPDK 新手最典型的故障源；不要试图用「在代码里多调用几个 API」来变相引用驱动目标，那既脆弱又不可维护。

第二，优先使用 pkg-config，而非手写库清单。旧资料里一长串 `-lrte_eal -lrte_ethdev -lrte_mbuf ...` 的写法对应的是分库时代，现代聚合库下应统一改为 `$(pkg-config --cflags --libs ...)`；当构建产物形态与示例不一致时，以所检出版本的 `libdpdk.pc` 为准（需对照实际版本核验）。

第三，区分 `--libs` 与 `--libs --static` 的使用场景。动态链接用前者即可；一旦产物是静态库、或 `default_library=static`，就必须用后者引入 `Libs.private`。二者混用的典型症状是「编译能过、链接报一堆未定义符号」或「链接能过、运行看不到设备」，分别对应系统依赖未展开与 whole-archive 缺失。

第四，妥善处理共享库的运行期路径。动态方式编译出的可执行文件，在目标机上要靠 `rpath`、`LD_LIBRARY_PATH` 或 `ldconfig` 找到 `libdpdk.so`；建议构建时写入相对 `rpath`（如 `$ORIGIN/../lib`）或安装到系统默认库目录，避免依赖登录环境里的临时变量。容器镜像中若采用动态库，务必把 `.so` 与其私有依赖一并拷入，这一点在 02-06 会进一步展开。

第五，关注 ABI 与 SONAME 一致性。`ldd` 输出里的 `libdpdk.so.24` 这类带版本后缀的名字（具体 SONAME 需对照实际版本核验）意味着应用绑定了特定 ABI；跨版本替换共享库前须确认兼容策略（迁移细节见 08-05）。静态库不受此约束，但升级 DPDK 后必须重新链接应用。

第六，注意链接顺序与 `--as-needed`。若因特殊原因手工组织多个静态库，库间循环引用可能需要 `--start-group`/`--end-group`；而某些发行版默认开启的 `--as-needed` 可能剔除「看似未使用」的共享库依赖，遇到构造函数型库被误删时，应检查链接参数。把这些细节交给 `libdpdk.pc` 管理，是降低风险的最佳实践。

第七，守住去重边界。本篇所有内容都围绕「链接期参数与产物」，不展开构造函数注册之后 EAL 如何枚举设备（原理见 06-01）、PMD 如何收发包（原理见 06-04）、驱动功能清单（模块见 07-01），也不重列运行时 EAL 参数（完整参数见 04-01）；涉及 `rte_eth_dev` 等结构体只点名加路径并写「（字段见 05-04）」。

### 7. 小结与延伸阅读

本篇顺着 02-03 的 `default_library` 选项，系统讲清了 DPDK 的链接方式：静态库按需抽取目标文件的特性，与 DPDK 依赖构造函数注册 PMD 的机制相冲突，因此静态链接必须借助 `-Wl,--whole-archive ... -Wl,--no-whole-archive` 整体纳入聚合库；共享库随加载自动执行构造函数，无需该参数，但要处理 `rpath`、`LD_LIBRARY_PATH`、`ldconfig` 与 SONAME/ABI。贯穿全篇的最佳实践只有一句——用 `pkg-config --cflags --libs [--static] libdpdk` 获取参数，让安装阶段生成的 `libdpdk.pc` 统一管理头文件路径、`Libs.private` 与系统依赖，而不是手工拼链接命令。图 02-04-01 与图 02-04-02 分别呈现了两种产物形态与 whole-archive 的注册因果链。

读者应能据此解释并修复「静态链接程序看不到网卡」这一经典问题，也能按部署场景在静态与动态之间做出选择：追求部署简单、镜像精简选静态并记得 `--static`，追求多进程共享与灵活升级选动态并管好加载路径。下一篇 02-05 将把构建从「本机」推向「异构」：讲解 meson cross file 的写法、x86_64 与 aarch64 的架构差异、交叉工具链与 NUMA/加密依赖的处理，以及 `config/` 下各架构分支如何配合。延伸阅读建议查阅所检出版本的 `libdpdk.pc`、`buildtools/` 下生成脚本、`examples/meson.build` 与 `doc/` 下链接相关指南（路径需对照实际版本核验）；跨版本 ABI 迁移见 08-05，运行时参数见 04-01，字段定义见 05 全册。

## 02-05 交叉编译与多架构

### 1. 背景与动机

到此为止，本册讨论的都是「在本机为本机构建」的 native build：`meson setup build` 探测到的是构建机自身的编译器、头文件与 CPU 架构，产出的库也只能在同架构机器上运行。但 DPDK 的真实部署场景远不止 x86_64 服务器一种。随着 arm 架构服务器、边缘计算设备、智能网卡与嵌入式转发平台的普及，为 aarch64、ppc64le 乃至 riscv64 目标机构建 DPDK 已经成为常态；很多目标机本身算力有限、磁盘小、甚至没有安装编译工具链与开发头文件，把整套构建环境搬到目标机上既不现实也不经济。于是「在性能充足的构建机上、用交叉工具链产出目标架构产物」的交叉编译，就成了 02 册必须覆盖的一环。

选择交叉编译而非目标机原生编译，通常出于四类考虑。其一是资源：构建机 CPU 核数与内存充足，ninja 并行编译远快于资源受限的目标板。其二是环境一致性：CI 用统一的构建镜像为多个架构产出二进制，避免每台目标机各自装一套工具链导致产物漂移。其三是可复现：交叉工具链与 sysroot 可以被版本化锁定，比「在目标机上 apt 装什么就编出什么」更可控。其四是批量交付：一次构建产出多架构包，配合 02-06 的打包与镜像流程直接分发。

交叉编译的难点也恰在这里，它不是简单地把 `cc` 换成 `aarch64-linux-gnu-gcc` 就能了事。第一，配置阶段 meson 需要「运行」一些辅助程序来探测能力或生成文件，而生成的是目标架构二进制、无法在构建机上直接执行，需要 `exe_wrapper`（如 qemu-user-static）或由 meson 改用 host 本机工具。第二，依赖探测必须指向目标架构的头文件与库，若 `pkg-config` 误用构建机的 `/usr/lib`，会悄无声息地链进 x86_64 的 `.so`，直到目标机加载时才失败。第三，架构相关代码路径不同：缓存行大小、字节序、原子指令、SIMD 实现、以及各厂商 PMD 依赖的加速库，都由 `config/` 下按架构分支的 `meson.build` 决定，交叉时必须让 meson 正确识别 host machine。第四，NUMA、加密、RDMA 等外部依赖都需要目标架构版本，缺失时相应驱动会被跳过（这一机制见 02-03）。

本篇只讲「构建期的交叉配置」，不展开运行时差异：跨架构的 lcore 亲和与 NUMA 行为属于 03 册与 06-09，运行时 EAL 参数完整参数见 04-01，各架构驱动的功能清单见 07 全册，涉及运行时结构体只点名加路径并写「（字段见 05-xx）」。凡 cross file 的字段、`config/` 下架构文件名、`platform` 取值与官方自带示例文件名，一律标注「需对照实际版本核验」并给出可定位路径。

### 2. 核心概念

meson 用「cross file」描述一次交叉构建。它是一个 ini 格式的文本文件，最核心的段有四个。`[binaries]` 段指定交叉工具链：`c` 与 `cpp` 指向交叉编译器，`ar`、`strip`、`pkg-config` 指向对应工具，必要时用 `exe_wrapper` 指定能在构建机上运行目标架构程序的解释层（如 `qemu-aarch64-static`）。`[host_machine]` 段描述产物要跑在哪台机器上，包含 `system`（一般为 linux）、`cpu_family`（如 aarch64、x86_64、ppc64、riscv）、`cpu`（更具体的型号）与 `endian`（little 或 big）。`[properties]` 段可放置 `sys_root`、`pkg_config_libdir` 等属性，帮助依赖探测定位目标 sysroot。`[builtin options]` 段可预设 `c_args`、`c_link_args`、`cpp_args` 等编译链接参数，常用来传 `--sysroot` 或架构优化开关。段名与字段在不同 meson 版本中可能有增删，需对照实际版本核验。

理解 cross build，先要分清 meson 术语里的三台机器：build machine 是执行编译的机器（构建机），host machine 是产物将要运行的机器（目标机），target machine 只在编译「编译器本身」这类特殊场景才出现，DPDK 常规交叉编译不涉及。native build 时三者合一，cross build 时 build 与 host 不同，这正是 `[host_machine]` 存在的意义：meson 据此进入 `config/` 下对应架构分支并注入正确的宏。与之配套的还有 `native: true/false` 的概念——构建期需要运行的辅助工具（如代码生成器）应以 build machine 的原生编译器构建，而不能交叉编成目标架构后又在构建机上执行；meson 通过 `native` 关键字与 `exe_wrapper` 共同处理这一矛盾。

`exe_wrapper` 是交叉编译独有的关键概念。当构建过程确实需要运行一个目标架构的可执行文件（例如某些生成配置头或校验能力的小工具）时，meson 会通过 `exe_wrapper` 包一层用户态模拟器来间接执行；若没有配置它、而构建又需要运行此类程序，配置或编译阶段会报「无法执行目标架构程序」之类的错误。是否真的需要 `exe_wrapper`，取决于所检出版本构建脚本里构建期辅助程序的组织方式，需对照实际版本核验。

`sysroot` 与「交叉化 pkg-config」是另一组核心概念。交叉工具链自带或另配一套目标架构的根文件系统，里面放着目标架构的头文件与库；编译链接时通过 `--sysroot` 指向它。与此同时，`pkg-config` 必须被约束到目标架构的 `.pc` 文件目录（典型做法是设置 `PKG_CONFIG_LIBDIR` 或使用 cross file 中的 `pkg-config` 包装），否则它会返回构建机 x86_64 的 `-L/usr/lib/x86_64-linux-gnu`，把主机库路径混进目标产物——这是交叉编译最隐蔽也最高频的错误。最后，`machine` 与 `platform` 选项在交叉语境下意义更重：`machine` 决定通用实现还是针对具体 CPU 优化，`platform` 在 arm 上选择 SoC 实现族（如各类 arm 服务器或网卡 SoC 的配置），二者必须与 `[host_machine]` 及 `config/` 下实际存在的架构定义相匹配，具体取值集合需对照实际版本核验。

### 3. 关键数据结构与源码位置

本节聚焦构建描述与架构配置，不涉及运行时 C 结构体；例如 `rte_eth_dev`（`lib/ethdev/`，字段见 05-04）、`rte_mempool`（`lib/mempool/`，字段见 05-03）只点名，机制写「原理见 06-xx」，驱动功能写「模块见 07-xx」。

交叉编译最该熟悉的源码落点是 `config/` 目录。顶层 `config/meson.build` 依据 meson 探测到的 `cpu_family` 选择架构分支，`config/x86/`、`config/arm/`、`config/ppc/`、`config/riscv/` 分别承载各架构的机器定义、缓存行参数、指令集宏与 SoC 实现；arm 平台尤其丰富，`config/arm/` 下往往按 SoC 组织多组实现参数，并由 `platform` 选项挑选。官方仓库通常也会附带若干可直接参考的 cross file 示例（常见位于 `config/arm/` 等目录，文件名形如某架构加编译器的组合，具体名称与是否仍随版本保留需对照实际版本核验），它们是写自建 cross file 时最可靠的第一手模板。

第二个落点是 `meson_options.txt` 中的 `machine` 与 `platform` 选项，以及 `config/meson.build` 里读取它们的位置。第三个落点是 `drivers/` 下各 PMD 的依赖声明：某些驱动依赖厂商或架构相关的用户态库（例如 mlx5 依赖 rdma-core 系列，部分 arm SoC 的 crypto 与 event 驱动依赖特定加速库；具体驱动与依赖清单需对照实际版本核验），交叉时这些库必须有目标架构版本，否则驱动会像 02-03 所述被跳过。第四个落点是 `buildtools/` 中在构建期运行的生成脚本——它们决定了本次构建是否真的需要 `exe_wrapper`。

下表把常见目标架构与构建要点做一次对照，具体 `cpu_family` 取值与可用 `platform` 需对照实际版本核验。

| 目标架构 | cpu_family 示意 | 典型工具链前缀 | 关注点 |
|---|---|---|---|
| x86_64 本机 | x86_64 | 空或 x86_64-linux-gnu | 基线，一般无需交叉 |
| aarch64 服务器 | aarch64 | aarch64-linux-gnu- | SoC 实现与 platform 选择 |
| armv7 嵌入式 | arm | arm-linux-gnueabihf- | 字节序与浮点 ABI |
| ppc64le | ppc64 | powerpc64le-linux-gnu- | 小端约定与向量实现 |
| riscv64 | riscv64 | riscv64-linux-gnu- | 实现成熟度与工具链版本 |

下表把 cross file 的四个核心段与字段职责对应起来，作为编写时的检查清单；段名与字段以所检出 meson 版本支持为准，需对照实际版本核验。

| 段名 | 关键字段 | 职责 |
|---|---|---|
| `[binaries]` | `c`、`cpp`、`ar`、`strip` | 指定交叉工具链可执行文件 |
| `[binaries]` | `pkg-config`、`exe_wrapper` | 约束依赖探测与运行目标程序 |
| `[host_machine]` | `system`、`cpu_family` | 决定 config 架构分支 |

需要强调的是，cross file 本身是「构建输入」，应纳入版本管理并与工具链版本、sysroot 版本一起记录，才能像 02-01 强调的那样保证可复现。它描述的是构建期映射，与运行时如何配置大页、如何绑定设备完全无关，后者属于 03 册与 06 全册。

### 4. 关键流程与调用链

一次完整的交叉编译，链路可以拆成「准备 → 配置 → 编译 → 转移验证」四段。准备段：安装交叉工具链与目标 sysroot，备齐目标架构的外部依赖开发包，必要时安装 qemu-user-static 作为 `exe_wrapper`，并写好 cross file。配置段：`meson setup build-arm --cross-file aarch64.ini` 读取 cross file，meson 依据 `[binaries]` 用交叉编译器做能力探测、依据 `[host_machine]` 把 cpu_family 定为 aarch64、进而进入 `config/arm/` 分支注入架构宏，依赖探测通过交叉化 pkg-config 命中 sysroot 里的目标库，构建期辅助程序按需要经 `exe_wrapper` 运行，最终写出面向 aarch64 的 `build.ninja`。编译段：`ninja -C build-arm` 用交叉编译器产出目标架构的库与应用。转移验证段：把产物拷到目标机（或用 qemu 在构建机上做基本加载验证），用 `file`、`readelf` 等确认架构，再进入 03 册的运行时配置。

### 5. 配置/命令/代码实例

下面给出一份面向 aarch64 的 cross file 示意，以及基于它的完整配置、编译与产物架构验证命令。文件字段、工具链前缀与路径均需对照实际版本与本机环境核验。

```ini
[binaries]
c = 'aarch64-linux-gnu-gcc'
cpp = 'aarch64-linux-gnu-g++'
ar = 'aarch64-linux-gnu-ar'
strip = 'aarch64-linux-gnu-strip'
pkg-config = 'pkg-config'
exe_wrapper = 'qemu-aarch64-static'

[host_machine]
system = 'linux'
cpu_family = 'aarch64'
cpu = 'armv8-a'
endian = 'little'

[properties]
sys_root = '/opt/sysroot-aarch64'
pkg_config_libdir = '/opt/sysroot-aarch64/usr/lib/aarch64-linux-gnu/pkgconfig'

[builtin options]
c_args = ['--sysroot=/opt/sysroot-aarch64']
c_link_args = ['--sysroot=/opt/sysroot-aarch64']
```

```bash
# 用 cross file 配置一份独立构建树
export PKG_CONFIG_LIBDIR=/opt/sysroot-aarch64/usr/lib/aarch64-linux-gnu/pkgconfig
meson setup build-arm --cross-file aarch64.ini \
  -Dbuildtype=release \
  -Ddefault_library=static \
  -Dexamples=l2fwd

# 编译并确认产物架构
ninja -C build-arm -j 4
file build-arm/lib/libdpdk.a
aarch64-linux-gnu-readelf -h build-arm/examples/dpdk-l2fwd | grep Machine
```

以下为示例输出，具体格式需对照实际版本核验。

```text
The Meson build system
Version: 1.3.2
Build type: cross build
C compiler for the host machine: aarch64-linux-gnu-gcc (gcc 11.4.0)
Host machine cpu family: aarch64
Host machine cpu: armv8-a
Program dpdk-gen-build-h found: YES
Dependency libnuma found: YES 2.0.14
Message: Using arm config from config/arm
Build targets in project: 963
ninja: Entering directory `build-arm'
[963/963] Linking target examples/dpdk-l2fwd
build-arm/lib/libdpdk.a: current ar archive
Machine: Advanced Micro Devices X86-64
```

【输出判读】配置输出里最关键的一行是 `Build type: cross build`，它确认 meson 确实进入了交叉模式而非误判为 native；若这里写的是 `native build`，说明 `--cross-file` 没被正确传入或 cross file 未被识别，后续一切都要重新检查。`C compiler for the host machine: aarch64-linux-gnu-gcc` 表明能力探测用的是目标架构编译器，而 `Host machine cpu family: aarch64` 与 `cpu: armv8-a` 证明 `[host_machine]` 段生效、meson 会据此进入 arm 分支；`Using arm config from config/arm` 则直接印证 02-03 与本篇反复强调的架构分支选择。`Dependency libnuma found: YES` 说明依赖探测命中了 sysroot 里的目标架构库而非构建机库，这是交叉编译成败的分水岭——若此处为主机路径，产物会混入错误架构的库。`Build targets in project: 963` 给出目标总数。编译段 `[963/963]` 满进度且无 `FAILED:` 表示交叉编译成功。验证段两行需要合起来看：`file` 显示 `libdpdk.a: current ar archive`，这只说明它是归档文件、无法区分架构（`.a` 不带机器头，属正常值，不能据此判定为 x86）；而 `readelf -h` 对可执行文件返回 `Machine: Advanced Micro Devices X86-64` 则是一个典型的异常特征——它本应显示 `AArch64`，出现 x86-64 说明交叉工具链或 `--cross-file` 未真正生效，产物其实是本机架构。正确结果应为 `Machine: AArch64`（具体字符串需对照实际版本核验）。因此本例特意保留这处「异常」以示范判读方法：先确认交叉模式、再看编译器与 host 架构、最后用 `readelf` 对可执行文件做架构终检，三者一致才算交叉成功。

下表把交叉编译的高频观测点与预期值对应起来，便于作为验收清单；具体字符串需对照实际版本核验。

| 观测点 | 预期值 | 异常时的含义 |
|---|---|---|
| `Build type` | cross build | 写成 native 即未启用交叉 |
| host 编译器 | 交叉工具链前缀 | 出现 cc 即探测错工具链 |
| `Host machine cpu family` | 目标架构 | 与预期不符即 cross file 有误 |
| `Dependency libnuma` | YES 且来自 sysroot | 命中主机库是重大隐患 |
| 可执行文件 `readelf -h` | 目标 Machine | 显示 X86-64 即未交叉 |
| 聚合库 `file` | ar archive | 仅凭此无法区分架构 |

### 6. 注意事项、陷阱与最佳实践

第一，把「pkg-config 拉到主机库」列为头号陷阱。务必通过 `PKG_CONFIG_LIBDIR`、cross file 的 `[properties]` 或专门的交叉 pkg-config 包装，把 `.pc` 搜索路径锁定到目标 sysroot；配置后用 `meson configure build-arm` 与 `meson introspect` 之类手段（具体命令需对照实际版本核验）确认依赖路径。这类错误在编译期毫无症状，只在目标机加载时才爆发，排查成本极高。

第二，正确对待 `exe_wrapper`。若构建期确实需要运行目标架构辅助程序，应安装 qemu-user-static 并在 `[binaries]` 中如实声明；反过来，若构建脚本已把生成工具改为 build machine 原生构建，就不要强行引入模拟器，以免徒增复杂度。是否需要、以及如何配置，以所检出版本 `buildtools/` 中的构建期脚本为准，需对照实际版本核验。

第三，管好 sysroot 与运行时版本的对应关系。sysroot 里的 glibc、内核头文件、以及各类 `-dev` 包版本，应与目标机实际运行环境尽量一致；用过高版本 sysroot 编出的产物，可能在目标机因 glibc 符号版本不匹配而无法启动。这与 02-04 讨论的 ABI 问题同源，跨架构时更敏感。

第四，字节序、缓存行与指令集参数不要想当然。`endian` 必须按目标机如实填写；`machine=native` 在交叉编译中尤其危险，因为它优化的是「构建机」或探测到的错误 CPU，应改用通用值或明确的目标型号；缓存行大小、原子与向量实现由 `config/` 下架构分支决定，不要手工覆盖（相关宏的含义属构建期配置，不展开内部机制，原理见 06-xx）。

第五，逐个确认外部依赖的目标架构版本。NUMA、OpenSSL、zlib、rdma-core、libpcap 等依赖若只有构建机版本，相应库或驱动会被跳过；需要某驱动时，必须先在 sysroot 中备好对应架构的开发包。驱动被跳过的判读方法见 02-02 与 02-03。

第六，保留官方 cross file 作为模板并锁定版本。`config/arm/` 等目录下的示例文件、字段命名与可用 `platform` 取值会随版本变化，遇到 `Unknown option`、架构分支不匹配等问题时，应直接比照所检出版本的 `config/` 与 `meson_options.txt`，标注「需对照实际版本核验」。

第七，把交叉编译纳入 02-01 的可复现纪律：记录工具链版本、sysroot 版本、cross file 内容、`meson setup` 的全部 `-D` 选项与目标总数，让多架构产物可被追溯。产物转移后的运行时配置（大页、设备绑定、EAL 参数）属于 03 册与 04-01，本篇只负责「编出正确架构的二进制」。

### 7. 小结与延伸阅读

本篇把构建从「本机」推广到「异构」：先说明交叉编译的动机与四类难点，再系统讲解 meson cross file 的 `[binaries]`、`[host_machine]`、`[properties]`、`[builtin options]` 四个核心段，以及 build/host/target 三台机器、`exe_wrapper`、sysroot 与交叉化 pkg-config 等概念；随后把源码落点收敛到 `config/` 下按 cpu_family 分支的架构定义、`config/arm/` 的 SoC 实现、`meson_options.txt` 的 `machine`/`platform`、`drivers/` 的架构依赖与 `buildtools/` 的构建期脚本；最后用图 02-05-01、图 02-05-02 呈现「构建机—目标机」拓扑与配置阶段内部链条，并借一份带异常特征的 `readelf` 输出示范了「确认交叉模式 → 核对编译器与 host 架构 → 终检产物 Machine」的验收方法。读者应带走的核心结论是：交叉编译的本质，是用一份 cross file 把 meson 的能力探测、架构分支与依赖查找全部导向目标机，而 pkg-config 误用主机库是其中最隐蔽的陷阱。

下一篇 02-06 作为全册收束，将把「构建产物」变成「可交付物」：讲解 DESTDIR 暂存与打包、多阶段容器镜像、以及 `examples/` 的编译验证，把 02-01 到 02-05 串成一条从源码到分发的完整链路。延伸阅读建议查阅所检出版本 `config/` 下的架构目录、官方自带 cross file 示例、`meson_options.txt` 与 `doc/` 下的交叉编译指南（路径需对照实际版本核验）。运行时 EAL 参数见 04-01，NUMA 与内存机制见 06-09，字段定义见 05 全册，模块功能见 07 全册。

## 02-06 打包、容器镜像与示例程序编译

### 1. 背景与动机

经过 02-01 到 02-05，读者已经能够获取源码、用 meson/ninja 配置编译、按需裁剪驱动库、正确处理静态与动态链接、甚至为异构架构产出二进制。但「在我的构建机上编出来了」与「能稳定交付到几十台生产机」之间，还隔着最后一道工序：把构建产物变成可分发、可安装、可复现、且带上必要运行时环境的交付物。这就是本篇的主题——打包、容器镜像与示例程序编译，也是全册从「构建」走向「交付」的收束。

为什么需要专门讨论这一步，原因有三。其一，`ninja install` 只是把文件复制到某个前缀目录，它默认按构建机的绝对路径布局安装，直接把这个目录拷给别人往往不可用：路径写死、pkg-config 文件里的 `prefix` 不对、共享库加载路径缺失。要做出规范的系统包（rpm/deb）或可搬运的离线目录，需要 `DESTDIR` 这类暂存机制重新组织安装根。其二，DPDK 程序的运行环境特殊：它依赖大页内存、被 VFIO 或 UIO 接管的网卡、以及特定内核能力，这些资源不属于「镜像里装了什么」，而属于「容器启动时挂载了什么」。把二者混为一谈，是容器化 DPDK 时最常见的认知错误；本篇只负责镜像内产物的组织，运行时大页与设备配置属于 03-02、03-03、03-06（运行时 EAL 参数完整参数见 04-01）。其三，示例程序是验证整条构建链路是否闭环的「最后一公里」：无论是通过 `-Dexamples` 在构建树内生成，还是安装后用 `pkg-config` 独立编译，`examples/` 能否编出来、能否链上 `libdpdk`，都是对 02-02 到 02-04 全部工作的综合检验，同时也是交付物里最直观的演示内容。

从交付形态看，本册关注三类常见做法：其一是系统包或离线 tar 包，适合传统物理机与虚拟机部署，核心是 `DESTDIR` 暂存加打包脚本；其二是容器镜像，适合云原生与 CI 流水线，核心是多阶段构建与运行时挂载；其三就是示例程序本身，它既是验证手段，也常被直接打进镜像作为冒烟测试工具。三者共享同一批产物：聚合库、`libdpdk.pc`、头文件、`usertools/` 脚本与示例可执行文件，差别只在于「怎么摆」和「带不带运行时」。

本篇严格守住构建边界：讲镜像里放什么、怎么放、怎么验证，不展开运行时大页分配机制（原理见 06-02）、VFIO 绑定流程（属 03-03）、设备透传与 K8s 编排（属 03-06），不重列 EAL 参数（完整参数见 04-01），不展开驱动功能（模块见 07 全册），涉及运行时结构体只点名加路径并写「（字段见 05-xx）」。凡 Dockerfile 基础镜像版本、安装路径、`examples` 选项名与官方打包脚本位置，一律标注「需对照实际版本核验」并给出可定位路径。

### 2. 核心概念

第一个概念是 `prefix` 与 `DESTDIR` 的分工。`prefix` 是 meson 的内建选项，决定产物「逻辑上」安装到哪里，并会被写进 `libdpdk.pc` 的 `prefix` 字段；`DESTDIR` 则是安装阶段的一个环境变量，它在不改变 `prefix` 的前提下，把整个安装树临时重定向到 `DESTDIR/${prefix}` 之下。举例说，配置时设 `prefix=/usr/local`，安装时设 `DESTDIR=/tmp/staging`，文件实际落到 `/tmp/staging/usr/local/...`，但 `libdpdk.pc` 里记录的仍是 `/usr/local`——这正是打 rpm/deb 或 tar 包所需要的：打进包里的路径是目标机的正式路径，构建机上只是暂存。把 `DESTDIR` 误当成 `prefix` 来改，会导致 `.pc` 文件里写死暂存路径，安装到目标机后 pkg-config 全部失效。

第二个概念是多阶段容器构建。builder 阶段基于带编译工具链与开发包的镜像，执行 02-02 的 `meson setup` 与 `ninja`，把 DPDK 编译出来；runtime 阶段基于精简的基础镜像，只从 builder 拷贝安装好的库、头文件（可选）、`libdpdk.pc`、工具脚本与示例可执行文件，不保留编译器、meson、ninja 与源码。这样既显著缩小镜像体积，也避免把构建期依赖与潜在漏洞带进生产镜像。两个阶段的基础镜像应尽量同源同版本，尤其 glibc 要兼容，否则 builder 编出的二进制在 runtime 里可能启动失败——这与 02-05 的 sysroot 版本一致性是同一个道理。

第三个概念是「镜像内产物」与「运行时挂载」的边界。镜像里能放的，是库、可执行文件、配置元数据等静态文件；镜像里放不了的，是大页内存、被接管的 PCI 设备、IOMMU 组与 `/dev/vfio` 节点——它们在容器启动时由编排层挂载或映射进来（hugetlbfs、设备节点、权限等，属 03-02、03-03、03-06）。因此一个「构建正确」的 DPDK 镜像，即使 `docker run` 时什么都没挂，也能正常显示版本与帮助信息，但一跑数据面就会因缺资源而失败；这不是镜像的问题，而是运行时配置的问题。把这条边界讲清楚，能省去大量容器化排错时间。

第四个概念是示例程序的两种编译路径。其一是「构建树内编译」：在 `meson setup` 时通过 `-Dexamples=l2fwd,l3fwd` 把示例纳入构建图，`ninja -C build` 直接在 `build/examples/` 下生成可执行文件（这正是 02-02、02-03 反复使用的做法）。其二是「安装后独立编译」：在已经装好 `libdpdk.pc` 的环境里，用 `cc main.c $(pkg-config --cflags --libs --static libdpdk)` 单独把某个示例源码编成可执行文件，用来验证安装产物自洽（这正是 02-02 验证环节与 02-04 链接实践的组合）。两种方式分别服务于「随 DPDK 一起构建」与「验证外部可用性」，交付时应至少保留其一作为冒烟测试。

第五个概念是镜像与包的版本锁定。基础镜像 tag、`prefix`、选项组合、DPDK 版本、以及 02-01 强调的检出提交号，都应写入构建参数或标签，保证镜像可复现、可追溯；这与 08-05 的版本迁移主题相衔接，本篇只要求在交付时「记录清楚」，不展开升级策略。

### 3. 关键数据结构与源码位置

本节关注交付物相关的源码与安装布局，不展开运行时 C 结构体；例如 `rte_mbuf`（`lib/mbuf/rte_mbuf.h`，字段见 05-02）、`rte_eth_dev`（`lib/ethdev/`，字段见 05-04）只点名，机制写「原理见 06-xx」。

与打包和示例最相关的源码落点有五处。其一是 `examples/meson.build` 与 `examples/` 下各示例目录（如 `examples/helloworld/`、`examples/l2fwd/`、`examples/l3fwd/`）：前者定义 `-Dexamples` 如何被解析、示例如何链接聚合库，后者提供每个示例的 `main.c` 与各自的 `meson.build`。其二是 `meson_options.txt` 中的 `examples` 选项（回顾 02-03）。其三是 `buildtools/`：这里包含安装规则与 `libdpdk.pc` 的生成逻辑，决定了打包时究竟会有哪些文件、落到哪些子目录（实际清单需对照实际版本核验）。其四是 `usertools/`：其中的 `dpdk-devbind.py`、`dpdk-hugepages.py` 等脚本会随 `ninja install` 进入 `bin/`（脚本名与安装路径需对照实际版本核验），是交付物里常被用到的一组运维工具。其五是 `app/`：`dpdk-testpmd` 等官方应用也常被一并打进镜像，作为现场诊断工具。至于发行包 spec 或 debian 规则文件是否随仓库提供、位于何处，随版本与发行方而变，需对照实际版本核验。

### 4. 关键流程与调用链

交付链路有两条主线。打包主线为：在构建机按 02-02 完成 `meson setup` 与 `ninja -C build` → 用 `DESTDIR=/tmp/staging ninja -C build install` 把产物暂存到一个干净根目录 → 校验暂存树内 `.pc` 文件的 `prefix` 仍为目标机正式路径 → 由打包脚本把暂存树封成 rpm/deb 或 tar → 分发到目标机后按 `prefix` 安装 → 设置 `PKG_CONFIG_PATH` 与动态库路径。这条链的关键是「暂存不改变逻辑前缀」，让包在任何机器上装到相同位置。

容器主线为：builder 阶段基于带工具链的镜像执行完整构建与 `ninja install`（可直接装到镜像内的正式 `prefix`）→ runtime 阶段从 builder 只拷贝库、`libdpdk.pc`、工具与示例 → 在 runtime 镜像里设好 `LD_LIBRARY_PATH` 与 `PKG_CONFIG_PATH` → 交付镜像；运行时由编排层另挂大页与设备。示例编译链则嵌在这两条主线中：构建时经 `-Dexamples` 生成可执行文件，或安装后用 `pkg-config` 独立编译源码完成冒烟验证。

两条链路都只描述产物组织与交付，不展开大页分配（原理见 06-02）、设备绑定（属 03-03）、PMD 收发包（原理见 06-04）或运行时参数全集（完整参数见 04-01）。把镜像理解为「静态产物的载体」、把运行时资源理解为「启动时的外部注入」，就抓住了容器化 DPDK 的本质。

### 5. 配置/命令/代码实例

下面给出一份多阶段 Dockerfile 示意，以及配套的构建、暂存打包与示例独立编译命令。基础镜像 tag、路径、选项名与示例源码位置均需对照实际版本核验。

```dockerfile
# ---------- builder 阶段 ----------
FROM ubuntu:22.04 AS builder
RUN apt-get update && apt-get install -y build-essential meson ninja-build pkg-config python3-pyelftools libnuma-dev libpcap-dev
COPY dpdk-src /src/dpdk
WORKDIR /src/dpdk
RUN meson setup build -Dbuildtype=release -Dprefix=/opt/dpdk -Ddefault_library=static -Dexamples=l2fwd,helloworld
RUN ninja -C build -j 4
RUN DESTDIR=/tmp/stage ninja -C build install

# ---------- runtime 阶段 ----------
FROM ubuntu:22.04 AS runtime
RUN apt-get update && apt-get install -y libnuma1 libpcap0.8 && rm -rf /var/lib/apt/lists/*
COPY --from=builder /tmp/stage/opt/dpdk /opt/dpdk
ENV LD_LIBRARY_PATH=/opt/dpdk/lib/x86_64-linux-gnu
ENV PKG_CONFIG_PATH=/opt/dpdk/lib/x86_64-linux-gnu/pkgconfig
ENV PATH=/opt/dpdk/bin:$PATH
WORKDIR /opt/dpdk
CMD ["/opt/dpdk/bin/dpdk-helloworld"]
```

```bash
# 构建镜像并打上可追溯标签
docker build -t dpdk-runtime:23.11 -f Dockerfile .

# 冒烟验证：镜像内示例能加载并打印信息（不依赖大页与设备）
docker run --rm dpdk-runtime:23.11 dpdk-helloworld

# 离线 tar 包：用 DESTDIR 暂存后整目录归档
DESTDIR=/tmp/dpdk-stage ninja -C build install
tar -C /tmp/dpdk-stage -czf dpdk-23.11-x86_64.tar.gz opt/dpdk

# 安装后独立编译示例，验证 libdpdk.pc 自洽
cc /opt/dpdk/share/dpdk/examples/helloworld/main.c -o /tmp/helloworld-verify \
  $(PKG_CONFIG_PATH=/opt/dpdk/lib/x86_64-linux-gnu/pkgconfig pkg-config --cflags --libs --static libdpdk)
```

以下为示例输出，具体格式需对照实际版本核验。

```text
Successfully built 3f9a2c1b7e04
Successfully tagged dpdk-runtime:23.11
EAL: Detected 8 lcore(s)
EAL: Detected 1 NUMA nodes
hello from core 1
hello from core 2
opt/dpdk/lib/x86_64-linux-gnu/libdpdk.a
opt/dpdk/lib/x86_64-linux-gnu/pkgconfig/libdpdk.pc
```

【输出判读】`Successfully built` 与 `Successfully tagged dpdk-runtime:23.11` 两行确认多阶段构建完成，标签中带版本号是 02-01 可复现纪律在镜像上的体现，应避免使用浮动 tag。`docker run` 后打印的 `EAL: Detected 8 lcore(s)` 与 `EAL: Detected 1 NUMA nodes` 表明镜像内的库能被动态或静态正确加载、EAL 基础探测可以执行，这是「镜像内产物组织正确」的强证据；随后的 `hello from core 1` 等行来自 helloworld 示例，说明示例可执行文件确实被拷入并能在 runtime 镜像里运行。需要特别判读的是：本命令没有挂载大页、没有映射 VFIO 设备，因此它只能验证「加载与基础初始化」，不能证明数据面可用；若换成需要端口的示例而仍不挂载资源，出现设备相关报错属于预期，而非镜像缺陷，运行时资源配置属 03 册、EAL 参数完整参数见 04-01。`tar -C /tmp/dpdk-stage -czf ... opt/dpdk` 之后列出的 `opt/dpdk/lib/.../libdpdk.a` 与 `opt/dpdk/lib/.../pkgconfig/libdpdk.pc` 两行，是检查离线包是否把聚合库与 pkg-config 元数据一并收进来的要点，二者缺一都会让目标机上的独立编译失败。最后一条 `cc` 命令用 `PKG_CONFIG_PATH` 显式指向包内 `.pc` 目录，若能无错误生成 `/tmp/helloworld-verify`，则证明 `prefix`、`libdir`、`Cflags`、`Libs.private` 在安装后依然自洽——这正是 02-04 链接方式与 `DESTDIR` 正确性的一次综合验收。整组中若出现 `Package libdpdk was not found`、`error while loading shared libraries` 或 `cannot find -ldpdk` 等异常特征，应分别回查 `PKG_CONFIG_PATH`、`LD_LIBRARY_PATH` 与库目录名是否与 `ninja install` 的实际输出一致。

下表把冒烟验证的观测点与结论对应起来，作为镜像交付前的检查清单；输出文本需对照实际版本核验。

| 观测点 | 期望结果 | 不满足时的含义 |
|---|---|---|
| 镜像 tag | 带明确版本号 | 浮动 tag 不可复现 |
| EAL lcore 探测行 | 打印检测到的 lcore | 库加载或初始化失败 |
| helloworld 输出 | 各 core 打印问候 | 示例未拷入或链库有误 |
| tar 内 `libdpdk.a` | 存在 | 离线包缺聚合库 |
| tar 内 `libdpdk.pc` | 存在 | 离线包缺元数据 |
| 独立编译示例 | 生成可执行文件 | pc 路径或链接参数不自洽 |

### 6. 注意事项、陷阱与最佳实践

第一，正确区分 `DESTDIR` 与 `prefix`。打包时用 `DESTDIR` 暂存、保留配置期的正式 `prefix`；切勿为了「让路径看起来对」而在配置阶段把 `prefix` 设成暂存目录，否则 `libdpdk.pc` 会写死暂存路径，包一到目标机就失效。打包前应打开暂存树里的 `.pc` 文件确认 `prefix` 字段，这是最容易被忽略的一步。

第二，保证 builder 与 runtime 的运行时库兼容。两阶段尽量使用同源同版本基础镜像，尤其 glibc 与 `libnuma`、`libpcap` 等运行时库版本要匹配；若追求最小镜像，可优先考虑 02-04 的静态链接，让 runtime 几乎不需要 DPDK 相关的 `.so`，但静态方式务必带上 `--static` 与 whole-archive（见 02-04）。采用动态库时，则必须在镜像里设置好 `LD_LIBRARY_PATH` 或写入 rpath，并把 `.so` 与其私有依赖一并拷入。

第三，别把运行时资源塞进镜像。大页、hugetlbfs 挂载点、VFIO 设备节点、IOMMU 权限都是「启动时注入」的资源，打进镜像既无意义也不可移植；镜像只负责库、元数据、工具与示例。相应地，不要把运行时 EAL 参数硬编码进镜像的 `CMD` 或 `ENTRYPOINT`，应留作启动参数由编排层传入（完整参数见 04-01），多实例隔离之类的需求只做最小引用、不展开。

第四，让示例成为常驻的冒烟测试。无论交付形态是包还是镜像，建议至少保留 helloworld 或 l2fwd 之一，并配一条「不依赖大页与设备即可运行」的验证命令；同时保留「安装后用 pkg-config 独立编译示例」的检查，用它持续验证 `libdpdk.pc` 的自洽性。示例本身通过 `-Dexamples` 构建，若镜像内不需要示例源码，可只拷可执行文件而不拷 `share/dpdk/examples`（是否安装该目录需对照实际版本核验）。

第五，收紧镜像体积与攻击面。runtime 阶段只装运行时库，及时清理 `apt` 缓存，不保留编译器、meson、ninja、源码与构建树；用 `.dockerignore` 排除主机上无关的 `build/` 目录，避免把本机产物误拷进上下文。多阶段构建的顺序也影响层缓存：把变动少的依赖安装放在前面、把源码 `COPY` 与构建放在后面。

第六，落实版本与可复现记录。把 DPDK 版本或提交号、基础镜像 tag、`prefix`、`-D` 选项组合、工具链版本写进镜像标签、构建参数或一份清单文件，与 02-01、02-05 的记录纪律一致；这与 08-05 的版本迁移相衔接，本篇只要求交付时记录清楚。

第七，守住去重边界。本篇讲的是「产物怎么打包、怎么进镜像、怎么被验证」，不展开运行时大页分配（原理见 06-02）、VFIO 绑定（属 03-03）、容器与 K8s 部署细节（属 03-06），不重列 EAL 参数（完整参数见 04-01），不罗列驱动功能（模块见 07 全册），涉及 `rte_mbuf`、`rte_eth_dev` 等结构体只点名加路径并写「（字段见 05-02）」「（字段见 05-04）」。

### 7. 小结与延伸阅读

作为全册收束，本篇把 02-01 到 02-05 的产物变成可交付物：先厘清 `prefix` 与 `DESTDIR` 的分工，说明打包时「暂存不改变逻辑前缀」的原则；再以多阶段 Dockerfile 为例，讲清 builder 与 runtime 之间「只拷产物」的边界、glibc 兼容与库路径注入；随后明确「镜像内静态产物」与「运行时挂载资源」的划分，避免把大页与设备误当作镜像内容；最后把 `examples/` 的两种编译路径（`-Dexamples` 构建树内生成、安装后 `pkg-config` 独立编译）定位成交付前的综合冒烟测试。图 02-06-01、图 02-06-02 分别呈现多阶段构建链与镜像产物、运行时挂载的协作关系，一组带判读的构建输出则把「能加载」「能编译」「数据面可用」三种层次区分开来。

至此，02 册形成一条完整链路：02-01 认识源码与依赖，02-02 用 `meson setup build` → `ninja -C build` → `ninja install` 完成配置、编译与安装，02-03 用选项裁剪驱动与库，02-04 用 pkg-config 与 whole-archive 正确处理链接，02-05 用 cross file 把产物推广到多架构，02-06 用 DESTDIR、多阶段镜像与示例验证把产物交付出去。读者应能独立从一份 DPDK 源码出发，产出可在目标环境安装、可被应用程序链接、可被容器分发的成品。后续内容按唯一权威源分工展开：部署与大页、绑卡、容器运行时配置见 03 册，EAL 参数与工具命令完整参数见 04-01，结构体逐字段定义见 05 全册，机制与调用链见 06 全册，库与驱动模块功能见 07 全册，运维与性能排障见 08 全册。延伸阅读建议查阅所检出版本的 `examples/meson.build`、`buildtools/` 安装规则、`usertools/` 脚本清单、`doc/` 下构建与容器相关指南，以及发行方提供的打包脚本（路径需对照实际版本核验）。
