# SONiC 技术资料 · 05 关键数据结构字段详解（分片 B）

## 05-03 SonicDBConfig、Table、ProducerStateTable 结构字段

### 1. 本篇定位与覆盖范围

本篇是 05 册「DB 访问层」字段的权威定义，逐项核对 `sonic-py-swsssdk/sonic-py-swsssdk-master/src/swsssdk/dbconnector.py`、`configdb.py`、`test/config/database_config.json`，以及 `sonic-swss/sonic-swss-master/cfgmgr/intfmgr.h`、`orchagent/orch.h`、`orchagent/orch.cpp` 中的真实调用点。按总纲第 2 节与 SPEC 第 4 节的唯一权威源约定，全集只有 05 册允许给出结构体逐字段表；本篇只讲字段含义、类型、生命周期与读写时机，**不展开配置下发机制**（统一写「原理见 06-02」「原理见 06-03」），**不重列 DB 编号与 schema 参数**（统一写「参数见 04-04」），**不展开 Python 封装模块的目录职责**（统一写「模块见 07-05」）。事实基准为「上游 master 快照（2026-11 抓取）」，凡定义落在快照外的一律写明边界并标注「需对照实际版本核验」，不臆造字段名、类型与偏移。

必须先说清证据的强弱分层。第一层是**可直接核验的 Python 侧**：`dbconnector.py:14` 定义的 `class SonicDBConfig` 给出了五个类级字段（两个配置文件路径、一个目录常量、两个初始化标志）与一个配置字典，以及 `get_dbid()`、`get_separator()`、`get_socket()` 等一组静态方法；`dbconnector.py:239` 的 `class SonicV2Connector` 与 `configdb.py:26` 的 `class ConfigDBConnector` 给出了实例字段和全部读写入口；`test/config/database_config.json` 则给出 `DATABASES` 与 `INSTANCES` 的真实 JSON 键形态。第二层是**只能看到使用点、看不到定义体的 C++ 侧**：`Table`、`ProducerStateTable` 与 `FieldValueTuple` 属 `sonic-swss-common`，本快照中 `sonic-buildimage/sonic-buildimage-master/src/sonic-swss-common/` 是空目录，真实定义不在快照内；可核验的是 `cfgmgr/intfmgr.h:5` 包含了 `producerstatetable.h`、`cfgmgr/intfmgr.h:32` 声明了 `ProducerStateTable m_appIntfTableProducer`、`orchagent/orch.cpp:473` 构造了 `Table(db, tableName)`。第三层是**跨篇归口**：`FieldValueTuple` 的逐字段定义归 05-02，本篇只在反查时点名，不重复其字段表。三类证据混用会直接导致「把调用点当成定义」的错误，本篇在表格「源码位置」列对每一类都作了区分。

还要守住能力边界。Redis 数据库的编号不是源码常量，而是运行时 `database_config.json` 里 `["DATABASES"][db_name]["id"]` 的值（`dbconnector.py:224-229`），因此任何把 `CONFIG_DB` 写成固定号码的写法都违反事实纪律（参数见 04-04）。配置链路是 `CONFIG_DB` → 各 `*mgrd` → `APPL_DB` → `orchagent` → `ASIC_DB` → `syncd` → SAI 的异步流水线，Python 侧 `ConfigDBConnector` 只负责把表项写进 `CONFIG_DB`，`set_entry()` 返回成功不代表硬件已下发（原理见 06-01）。`ConfigDBConnector` 是 `swsscommon` 的 Python 封装，`swsscommon` 本体在 `sonic-swss-common`，不在本快照（模块见 07-05）。本篇覆盖的结构与连接关系见图 05-03-01，图中实线为字段持有或调用链，虚线为跨册反查链。

### 3. 逐项详解

SonicDBConfig 的类级字段可以分成三组。第一组是三个路径相关常量：`SONIC_DB_GLOBAL_CONFIG_FILE` 指向 `/var/run/redis/sonic-db/database_global.json`，`SONIC_DB_CONFIG_FILE` 指向 `/var/run/redis/sonic-db/database_config.json`，`_sonic_db_config_dir` 保存目录 `/var/run/redis/sonic-db`（`dbconnector.py:15-17`）。三者都是类级字符串，进程生命周期内只读，作用是在首次解析前告诉 `load_sonic_db_config()` 与 `load_sonic_global_db_config()` 去哪里读文件。值得注意的是 `load_sonic_db_config()` 在指定文件不存在时会回落到包内 `config/database_config.json` 并打日志告警（`dbconnector.py:94-97`），这说明这两个路径常量不是绝对可靠的运行时事实，部署差异必须核验（参数见 04-04）。

第二组是两个初始化标志与配置字典。`_sonic_db_config` 是一个以命名空间字符串为键、以解析后的 JSON 字典为值的容器；本地命名空间用空字符串 `''` 作键（`dbconnector.py:100`），其它命名空间由全局配置里的 `INCLUDES` 项逐个载入（`dbconnector.py:41-77`）。`_sonic_db_config_init` 与 `_sonic_db_global_config_init` 都是布尔标志，分别在本地配置、全局配置加载完成后置为 `True`，用于保证加载幂等：两个 `load_*` 方法开头都先检查对应标志，已加载就直接返回（`dbconnector.py:34-35`、`dbconnector.py:90-91`）。`isInit()` 只暴露本地标志（`dbconnector.py:107-109`），而 `namespace_validation()` 对非空命名空间额外要求全局标志已置位（`dbconnector.py:119-123`），否则抛 `RuntimeError`。因此调用顺序是有约束的：跨命名空间查询必须先 `load_sonic_global_db_config()`，这属于字段状态机而非业务流程，本篇只记录读写时机（原理见 06-02）。

第三组是 JSON 配置里的运行库字段。`DATABASES` 下每个库有 `id`、`separator`、`instance` 三个键，`INSTANCES` 下每个实例有 `hostname`、`port`、`unix_socket_path` 三个键，这在 `test/config/database_config.json` 中可逐行核验。`get_dbid()` 的实现是「归一化命名空间 → 确保已加载 → 校验库名 → 返回 `["DATABASES"][db_name]["id"]`」（`dbconnector.py:224-229`），这条链把「DB 编号来自运行时配置」坐实为代码事实；`get_socket()`、`get_hostname()`、`get_port()` 则通过 `get_instance()` 先取实例字典再取具体键（`dbconnector.py:179-221`）。`get_separator()` 返回的是 `DATABASES[db].separator`，`ConfigDBConnector.db_connect()` 在连接时用 `get_db_separator()` 的返回值覆盖 `TABLE_NAME_SEPARATOR` 与 `KEY_SEPARATOR`（`configdb.py:76-79`），这解释了为什么 `CONFIG_DB` 的键常以竖线分层而 `APPL_DB` 多用冒号——分隔符是配置值，不是硬编码（参数见 04-04）。

SonicV2Connector 的实例字段只有三个。`dbintf` 是 `DBInterface` 对象，在 `__init__` 中由传入的关键字参数构造（`dbconnector.py:246`），`connect()` 时再按 `use_unix_socket_path` 决定把 `unix_socket_path` 还是 `host` 与 `port` 写进 `dbintf.redis_kwargs`，最后用 `get_dbid()` 的返回值调用 `dbintf.connect(db_id, db_name, retry_on)`（`dbconnector.py:258-268`）。`use_unix_socket_path` 在构造时按 `use_unix_socket_path and os.getuid() == 0` 计算，非 root 恒为假（`dbconnector.py:247`），这是「默认走 TCP、root 才可用套接字」的字段级依据。`namespace` 保存目标命名空间，未传时为 `None`，`get_db_list()` 等方法把它原样传给 `SonicDBConfig`（`dbconnector.py:273-292`）。`__init__` 最后还用 `setattr()` 为每个库名挂一个同名属性（`dbconnector.py:254-256`），这是动态字段，源码里搜不到字面定义，读代码时不要误判为缺失。

ConfigDBConnector 的实例字段承载「表项语义」。构造时 `serialize_key` 与 `deserialize_key` 被绑定到实例方法上，以实现静态与实例方法的重载（`configdb.py:50-53`）；`TABLE_NAME_SEPARATOR`、`KEY_SEPARATOR` 初值均为竖线，`handlers` 初始化为空字典（`configdb.py:55-57`）。`INIT_INDICATOR` 是类常量 `CONFIG_DB_INITIALIZED`，`__wait_for_db_init()` 用它订阅 keyspace 通知等待配置库初始化完成（`configdb.py:59-74`）。`db_name` 不是构造参数，而是 `db_connect()` 的第一个赋值语句写入（`configdb.py:76-79`），随后 `set_entry()`、`get_entry()`、`get_keys()`、`get_table()` 都以它拼出 `TABLE|KEY` 形式的 Redis 键。需要特别注意 `typed_to_raw()` 与 `raw_to_typed()` 对字段值的编码：`{}` 被写成 `{"NULL": "NULL"}` 占位，列表值以字段名加 `@` 后缀、逗号连接存储（`configdb.py:126-157`），这属于字段的序列化形态，逐字段含义见 05-02（字段见 05-02）。

C++ 侧的 `Table` 与 `ProducerStateTable` 必须作为不透明句柄处理。两者定义在 `sonic-swss-common`，本快照只有空目录，没有任何头文件可展开；可核验的只有包含与使用点：`cfgmgr/intfmgr.h` 包含 `producerstatetable.h`（第 5 行）并声明 `ProducerStateTable m_appIntfTableProducer` 与 `m_appSagTableProducer`（第 32 行），其任务函数以 `std::vector<FieldValueTuple>` 为参数（第 53-57 行）；`orchagent/orch.h` 包含 `table.h`、`consumertable.h`、`consumerstatetable.h`，`orch.cpp:473` 与 `orch.cpp:480` 用 `auto table = Table(db, tableName)` 构造只读表以回填同步队列，`orch.cpp:1219` 用 `ConsumerStateTable(db, tableName, gBatchSize, pri)` 构造消费者。以上只能证明这些类型存在、构造形态如何，不能推出其成员布局；用 `sizeof()`、指针偏移或 `reinterpret_cast` 去读其内部成员会在不同 `sonic-swss-common` 版本下静默错位。模块职责归 07-05，producer / consumer 机制归 06-02，本册只写字段与入口。生命周期上，类级配置与两个标志是进程级单例，`SonicV2Connector` 与 `ConfigDBConnector` 是按进程或线程构造的连接对象，`handlers` 随订阅注册而增长，C++ 的 `ProducerStateTable` 随各 `*mgrd` 对象存活；凡跨线程共享连接对象，都应先确认该版本的线程安全约束（需对照实际版本核验）。

### 4. 典型示例

下面给出一组字段级核验示例：先用 Python 读出 `SonicDBConfig` 暴露的库编号与分隔符，再用 `redis-cli` 按读出的编号查 `CONFIG_DB` 表项。示例不写死 DB 编号，以体现「编号来自运行时配置」这一事实。代码在测试桩中执行，不改动任何设备配置。

```python
from swsssdk import ConfigDBConnector, SonicDBConfig

SonicDBConfig.load_sonic_db_config()
for db in ("CONFIG_DB", "APPL_DB", "ASIC_DB"):
    print(db, "id=", SonicDBConfig.get_dbid(db),
          "sep=", SonicDBConfig.get_separator(db))
print("inst=", SonicDBConfig.get_instancename("CONFIG_DB"))

cfg = ConfigDBConnector()
cfg.connect(wait_for_init=False)
print("PORT keys=", cfg.get_keys("PORT")[:2])
print("Ethernet1 =", cfg.get_entry("PORT", "Ethernet1"))
```

```bash
dbid=$(python3 -c 'from swsssdk import SonicDBConfig; print(SonicDBConfig.get_dbid("CONFIG_DB"))')
echo "CONFIG_DB id=$dbid"
redis-cli -n "$dbid" --raw KEYS 'PORT|*' | head -5
redis-cli -n "$dbid" HGETALL 'PORT|Ethernet1'
```

逐行判读如下，合计超过 150 字。前三行来自 `get_dbid()` 与 `get_separator()`，分别给出三个逻辑库的编号与分隔符；本例的 `4`、`0`、`1` 只是 `test/config/database_config.json` 中 `DATABASES` 各项 `id` 的示意值，真实编号必须运行时读取，绝不可写死（参数见 04-04）。若三者取值相同或为空，通常说明 `load_sonic_db_config()` 读到了错误的配置文件、或 `namespace` 未正确传入，应回查 `dbconnector.py:86-105` 的加载路径而不是怀疑 Python 环境。第四行 `inst= redis` 来自 `get_instancename()`，它返回 `DATABASES[db].instance` 的值，是后续 `get_socket()`、`get_hostname()`、`get_port()` 的键；这里必须与 `INSTANCES` 中真实存在的实例名一致，否则 `inst_name_validation()` 会抛 `RuntimeError`（`dbconnector.py:153-162`）。第五、六行来自 `ConfigDBConnector`：`get_keys("PORT")` 用 `TABLE_NAME_SEPARATOR` 拼出匹配模式并剥去表名前缀，返回的是元组或字符串键；`get_entry()` 把 Redis 哈希经 `raw_to_typed()` 转成字典，`admin_status`、`mtu` 是 `configdb.py` 能直接核验的字段处理路径，字段名本身需对照实际版本核验（字段见 05-02）。第七行是 shell 侧回显，用来证明 `dbid` 由 Python 读出而非硬编码；若这里直接写数字，示例就违反了事实纪律。第八至十二行是 `KEYS 'PORT|*'` 的结果，证明 `CONFIG_DB` 用竖线分层、键形如 `PORT|Ethernet1`，与 `get_separator()` 的返回值一致；若模式写成分隔符为冒号，则查不到任何表项，这是常见的排查误区。最后四行是 `HGETALL` 的键值交错输出，`admin_status` 与 `mtu` 各占两行，值 `up`、`9100` 均为字符串或经 `raw_to_typed()` 处理前的原始形态。需要强调：`set_entry()` 或 `mod_entry()` 写入 `CONFIG_DB` 后仅代表配置入库，后续还要经过 `*mgrd` 与 `orchagent` 的多段流转才可能下发到 ASIC（原理见 06-01）；`swsssdk` 本体所在模块见 07-05。

### 6. 版本差异

最显著的差异来自「Python 封装与 C++ 实现分离」。`SonicDBConfig` 在本快照中只有 `sonic-py-swsssdk` 的 Python 实现，而 C++ 侧连接与表访问类（`DBConnector`、`Table`、`ProducerStateTable`）属 `sonic-swss-common`，不在本快照；同一个逻辑库在两套 API 里有不同字段名与构造方式，跨语言比较字段时必须先声明证据边界。本快照还显示 `_sonic_db_config` 以命名空间为键、`load_sonic_global_db_config()` 解析 `INCLUDES`，说明多命名空间支持是相对晚近的增量能力；早期版本若没有全局配置与 `namespace_validation()`，跨命名空间查询的行为会不同，具体兼容边界需对照实际版本核验。`use_unix_socket_path` 受 `os.getuid() == 0` 限制、`INIT_INDICATOR` 用于等待 `CONFIG_DB` 初始化，这两处字段语义在旧版本是否一致需对照实际版本核验。

第二组差异来自运行时配置文件本身。`database_config.json` 与 `database_global.json` 是部署期产物，由 `dockers/docker-database/database_config.json.j2` 一类模板生成；字段 `id`、`separator`、`instance`、`unix_socket_path`、`hostname`、`port` 的名称在本快照测试配置中可核验，但取值随平台、容器网络模式与多 ASIC 配置变化（参数见 04-04）。`test/config/database_config.json` 中 `PFC_WD_DB` 与 `FLEX_COUNTER_DB` 共用同一 `id`，提示编号并非全局唯一语义标识，而是 Redis 实例内的库号；据此推断「某库固定是某号」或「编号唯一对应库名」都是错误结论。

第三组差异来自能力边界。配置链路始终是异步的，`ConfigDBConnector` 的写入入口在不同版本中保持 `set_entry`、`mod_entry`、`get_entry`、`get_table` 这一组名字（本快照可核验），但字段编码规则里 `NULL:NULL` 占位与列表字段的 `@` 后缀带有明显的兼容历史，新版本是否改用基于 schema 的类型化机制需对照实际版本核验（`configdb.py:137` 的待改进注释已写明这一点）。`sonic-swss-common` 的 `Table`、`ProducerStateTable` 内部字段随该仓版本演进，本册不给任何成员名或偏移；`warmrestart/`、多 ASIC 与 chassis 场景下的命名空间行为受平台与版本限制（原理见 06-11），不得宣称全平台无条件支持。性能、容量与下发时延一律标注「需在目标机型实测」，不给绝对值（基准方法见 08-01）。

### 7. 常见误用与调试

第一类误用是写死 Redis 数据库编号。最常见的错误是把 `CONFIG_DB` 直接写成某个固定数字，或用 `redis-cli -n <数字>` 硬编码连接。`get_dbid()` 的实现已经证明编号来自 `["DATABASES"][db_name]["id"]`（`dbconnector.py:224-229`），`test/config/database_config.json` 里两个库共用编号也说明编号不是库名的唯一标识。正确做法是先 `load_sonic_db_config()` 再 `get_dbid()`，把返回值传给连接命令；若取值异常，先确认进程读的是 `/var/run/redis/sonic-db/database_config.json` 还是回落到的包内配置（`dbconnector.py:94-97`），再核对 `namespace` 参数（参数见 04-04）。

第二类误用是把不透明句柄当普通结构展开。`swss::Table`、`swss::ProducerStateTable` 与 `FieldValueTuple` 的定义都不在本快照，`sonic-buildimage-master/src/sonic-swss-common/` 是空目录。用 `sizeof()`、指针偏移或 `reinterpret_cast` 去读它们的成员，会在不同 `sonic-swss-common` 版本下静默错位；正确做法是只用公开构造与访问接口，并在字段表中写「不在本快照，需对照实际版本核验」。同理，`ConfigDBConnector` 在 `__init__` 里用 `setattr()` 动态挂上的库名属性（`dbconnector.py:254-256`）在源码中搜不到字面定义，不应据此判断字段缺失（字段见 05-02 ｜ 模块见 07-05）。

第三类误用是忽视加载顺序与命名空间状态。`_sonic_db_config_init` 与 `_sonic_db_global_config_init` 是两个独立标志，非空命名空间查询要求先加载全局配置，否则 `namespace_validation()` 抛 `RuntimeError`（`dbconnector.py:119-123`）；本地命名空间用空字符串 `''` 作键（`dbconnector.py:100`），传 `None` 与传 `''` 的归一化行为由 `EMPTY_NAMESPACE()` 决定（`dbconnector.py:133-138`）。调试时遇到「配置库读不到」应先检查这两个标志与传入的命名空间，而不是先怀疑 Redis 服务。第四类是把 05 册当流程书或参数书读：想知道配置怎么逐段走到芯片应读 06 册（原理见 06-01、原理见 06-02），想查 DB 编号与 schema 应读 04 册（参数见 04-04、参数见 04-02），想按目录找封装模块应读 07 册（模块见 07-05）；反过来，在 06 / 07 / 08 册看到完整字段表属于去重铁律被破坏，应改写成「字段见 05-03」。

第五类是跨版本与类型化假设。把旧版本 Python 封装的字段名、分隔符默认值或 `NULL:NULL` 编码规则套到当前快照，或假定 `get_separator()` 对所有库返回同一字符，都会导致键模式拼错、查询为空；字段编码规则在 `configdb.py:137` 已标注待改成基于 schema 的类型化机制，具体演进需对照实际版本核验。加密或聚合场景不会改变这些字段的存在性，但会影响表项内容的可读性；凡涉及吞吐、pps、内存占用的结论一律标注「需在目标机型实测」，不给绝对值。排错时若读到「看似合理但明显不对」的值，先确认二进制与所用 `swsssdk` 版本来自同一快照，再按「路径 → 标志 → 命名空间 → 键模式 → 字段编码」的顺序逐项回查源码（诊断树见 08-03）。本篇关于 DB 访问结构的字段定义至此收束，Table 与 ProducerStateTable 的内部布局须回到 sonic-swss-common 核验。

### 3. 逐项详解

先说证据边界。`SAI/` 目录在本快照为空，构建期由 SAI 头文件生成的 `saimetadata.h` 也不在快照内；`syncd/SaiObj.h`、`syncd/SaiAttr.h` 都以 `extern "C" { #include "saimetadata.h" }` 的方式引入这些类型（`SaiObj.h:3-5`、`SaiAttr.h:3-5`）。因此 `sai_object_id_t`、`sai_attribute_t`、`sai_object_meta_key_t`、`sai_attr_metadata_t` 的完整字段表属于「不在本快照，需对照实际版本核验」。本篇给出的字段，要么是 sairedis 自己在代码里定义的位段与类成员，要么是这些外部类型在快照代码中的真实访问表达式。任何声称「SAI 属性结构体共有 N 个字段」的写法都超出了证据范围。

虚拟 ID 的位布局是本册最硬的字段事实。`VirtualObjectIdManager.cpp:11-14` 用两条 `static_assert` 固定 `sai_object_id_t` 为 64 位且大小等于 `uint64_t`；随后定义五段位宽：switch index 8 位、global context 8 位、object type 8 位、extensions flag 1 位、object index 39 位（第 16-34 条宏），并有一条 `static_assert` 校验五段之和恰为 64（第 36-43 行）。源码注释（第 54-71 行）把格式写成：bits 63..56 为 switch index、bits 55..48 为 object type、bits 47..40 为 global context、bit 39 为扩展标志、bits 38..0 为 object index。`constructObjectId()`（第 369-394 行）用左移拼接这五段：switch index 左移 56 位、object type 左移 48 位、global context 左移 40 位、扩展标志左移 39 位、object index 不移位。注释还给出两个编码实例：`SAI_OBJECT_TYPE_VIRTUAL_ROUTER` 的 VID 为 `0x0003000000000001`，`SAI_OBJECT_TYPE_DASH_ACL_GROUP` 为 `0x0003008000000001`，后者正是扩展标志置位的情形。读这段字段时务必记住：这是 sairedis 为虚拟交换机与多上下文场景设计的编码，不是 SAI 规范对真实对象 ID 的位级承诺（原理见 06-05）。

`sai_object_status_t` 枚举定义在 `syncd/SaiObj.h:18-56`，四个取值分别为 `SAI_OBJECT_STATUS_NOT_PROCESSED`（值为 0，源码要求必须最先声明）、`SAI_OBJECT_STATUS_MATCHED`（上一视图中匹配到相同 VID/RID，属性可能仍需处理）、`SAI_OBJECT_STATUS_REMOVED`（当前视图对象在子节点处理中被移除）、`SAI_OBJECT_STATUS_FINAL`（已完成匹配、设置或创建，并产生差异动作）。`SaiObj` 构造时把 `m_createdObject` 置 `false`、`m_objectStatus` 置 `NOT_PROCESSED`（`SaiObj.cpp:31-38`）。`m_createdObject` 的注释说明它标记对象是否已创建且当前没有 RID（`SaiObj.h:143-147`），这与 VID 到 RID 的转换是两类不同状态，不能混读。

`SaiObj` 的其余字段决定了「对象视图」的可读范围。`m_str_object_type` 与 `m_str_object_id` 是对象类型与 ID 的序列化字符串，主要出现在日志与错误分支，例如 `getSaiAttr()` 找不到属性时会打印 `m_str_object_id`（`SaiObj.cpp:70`）。`m_meta_key` 是对象的元键，`getObjectType()` 直接返回 `m_meta_key.objecttype`（`SaiObj.cpp:104-109`），`getVid()` 先经 `isOidObject()` 检查，只有 OID 类型对象才返回 `m_meta_key.objectkey.key.object_id`，否则抛异常（`SaiObj.cpp:127-137`）。`m_info` 是指向 `sai_object_type_info_t` 的指针，`isOidObject()` 读 `m_info->isobjectid`（`SaiObj.cpp:40-45`）。`m_attrs` 以 `sai_attr_id_t` 为键存放 `std::shared_ptr<SaiAttr>`，`setAttr()` 用属性自身的 `getSaiAttr()->id` 作键（`SaiObj.cpp:111-117`），`getSaiAttr()` 未命中会遍历全部属性打日志后抛异常，`tryGetSaiAttr()` 则未命中返回空指针（`SaiObj.cpp:54-87`）。

`SaiAttr` 的四个私有字段构成「字符串—元数据—C 值」三态。`m_str_attr_id` 是构造时传入且不可变，`m_str_attr_value` 可被 `updateValue()` 用 `sai_serialize_attr_value(*m_meta, m_attr)` 重写（`SaiAttr.cpp:135-139`）。构造函数先用 `sai_deserialize_attr_id()` 解析出 `m_meta`，再令 `m_attr.id = m_meta->attrid`，最后调用 `sai_deserialize_attr_value(str_attr_value, *m_meta, m_attr, false)`（`SaiAttr.cpp:8-25`）；析构函数调用 `sai_deserialize_free_attribute_value(m_meta->attrvaluetype, m_attr)` 释放列表类属性分配的内存（`SaiAttr.cpp:46-51`）。`getOid()` 只在 `m_meta->attrvaluetype` 为 `SAI_ATTR_VALUE_TYPE_OBJECT_ID` 时返回 `m_attr.value.oid`，或为 `SAI_ATTR_VALUE_TYPE_ACL_ACTION_DATA_OBJECT_ID` 且 `m_attr.value.aclaction.enable` 为真时返回嵌套的 `m_attr.value.aclaction.parameter.oid`，否则抛异常（`SaiAttr.cpp:53-69`）；`isObjectIdAttr()` 返回 `m_meta->isoidattribute`（`SaiAttr.cpp:89-93`）。拷贝构造与赋值被显式删除，原因是属性可能含指向列表的指针、拷贝会导致双重释放（`SaiAttr.h:20-32`）。

`meta/SaiObject` 是另一套表示，必须与 `syncd::SaiObj` 区分。它定义在 `meta/SaiObject.h:11-51`，私有字段只有 `m_metaKey`（`sai_object_meta_key_t`）与 `m_attrs`（`sai_attr_id_t` 到 `std::shared_ptr<SaiAttrWrapper>` 的映射），同样删除了拷贝构造与赋值。两者的共同点是都持有元键与属性表，不同点是属性元素类型分别为 `SaiAttrWrapper` 与 `SaiAttr`、所属命名空间分别为 `saimeta` 与 `syncd`。生命周期上，VID 由 `VirtualObjectIdManager::allocateNewObjectId()` 分配并被 `m_switchIndexes` 记录（`VirtualObjectIdManager.h:66-93`），`AsicView` 用 `m_ridToVid`、`m_vidToRid`、`m_removedVidToRid` 三组映射维护 VID 与 RID 的对应关系（`AsicView.h:296-298`），并用 `m_vidReference` 记录引用计数（第 313 行）；`bindNewLinks()` 与 `releaseExisgingLinks()` 按属性里是否含 OID 来增减引用（`AsicView.h:63-120`）。这些字段只在比较与差异生成阶段被读写，其余阶段应视为只读（原理见 06-05）。

### 6. 版本差异

最根本的代际差异是「虚拟 ID 编码是 sairedis 的实现选择，不是 SAI 规范字段」。源码注释明确说明为了向后兼容，基础对象类型仍编码在 bits 55..48，而扩展类型从 `SAI_OBJECT_TYPE_EXTENSIONS_RANGE_START` 起算、编码为从 0 开始并置位扩展标志（`VirtualObjectIdManager.cpp:66-71`）；`SAI_OBJECT_TYPE_DASH_ACL_GROUP` 的示例 `0x0003008000000001` 说明这一机制是为 DASH 一类扩展对象类型引入的。旧版本若没有扩展标志，bit39 与 39 位 object index 的划分会不同，跨版本比较 OID 数值时必须先确认编码方案（需对照实际版本核验）。

第二组差异来自 SAI 头文件与元数据。`sai_object_id_t`、`sai_attribute_t`、`sai_attr_metadata_t` 的字段由 SAI 版本决定，`saimetadata.h` 在构建期生成，本快照 `SAI/` 为空目录，任何具体属性名、枚举取值、联合体成员都需对照实际版本核验（参数见 04-06）。`SaiAttr` 构造时使用的 `SAI_ATTR_VALUE_TYPE_OBJECT_ID`、`SAI_ATTR_VALUE_TYPE_ACL_ACTION_DATA_OBJECT_ID` 与 `m_meta->enummetadata->ignorevalues` 说明属性类型集合随 SAI 演进，新类型可能改变 `getOid()` 的分支；本册只给这些在快照中可见的访问表达式，不外推完整枚举。`static_assert(SAI_OBJECT_TYPE_MAX < 256)` 与扩展类型范围小于 256 的断言（`VirtualObjectIdManager.cpp:49-51`）说明对象类型必须压进 8 位，超出范围时需要调整编码，这是版本演进中的真实约束。

第三组差异来自对象表示与能力边界。`syncd::SaiObj` 与 `meta::SaiObject` 是两套并存结构，属性元素分别为 `SaiAttr` 与 `SaiAttrWrapper`，不同版本可能侧重其一，调试时必须先确认所在命名空间（模块见 07-04）。`m_createdObject`、`m_objectStatus` 与 `AsicView` 的三组 RID/VID 映射服务于 warm reboot 与视图比较，受平台与版本限制，不同 HWSKU 与版本能力不同，一律写「受平台与版本限制，需对照实际版本核验」，不得宣称全平台无条件支持（原理见 06-05、原理见 06-10）。厂商 SAI 实现闭源且不在本快照，RID 的内部含义对本册不透明；`orchagent` 不直接读写寄存器，一切吞吐、表项容量与下发时延标注「需在目标机型实测」，不给绝对值（基准方法见 08-01）。

### 7. 常见误用与调试

第一类误用是把 VID 当成 RID 或当成 SAI 规范字段。`sai_object_id_t` 在本册讨论的是 sairedis 虚拟 ID，其 64 位布局由 `VirtualObjectIdManager.cpp` 的宏与 `static_assert` 定义；真实对象 ID 由厂商 SAI 实现给出、不在本快照。把 VID 数值直接当 RID 传给厂商接口、或反过来用 RID 的位模式去解释 VID，都会在 `AsicView` 的 `m_vidToRid`、`m_ridToVid` 映射上错位。正确做法是用 `AsicView` 提供的映射与 `switchIdQuery()`、`objectTypeQuery()`、`getObjectIndex()` 等查询接口（`VirtualObjectIdManager.h:39-173`），而不是手工移位（原理见 06-05 ｜ 模块见 07-04）。

第二类误用是硬编码位布局或属性成员。`SAI_OBJECT_ID_BITS_SIZE` 为 64、`switchIndex` 与 `globalContext` 范围 0..255 是本快照的断言（`VirtualObjectIdManager.cpp:11-21`、`VirtualObjectIdManager.h:139-156`），但 bit39 扩展标志与 39 位 object index 属于 sairedis 编码；把 `0x012345e789abcdef` 这类测试常量或位移量写死进外部工具，跨版本必然失效。同理，`sai_attribute_t.value` 的哪个成员有效必须由 `m_meta->attrvaluetype` 判定，`getOid()` 只覆盖 OID 与 ACL 动作 OID 两种情形（`SaiAttr.cpp:53-69`）；不看元数据就直接读 `m_attr.value.oid` 会在列表、枚举等类型上得到无意义值。

第三类误用是忽视内存与拷贝约束。`SaiAttr` 的拷贝构造与赋值被显式删除，注释写明属性可能含指向列表的指针、拷贝会导致双重释放（`SaiAttr.h:20-32`）；析构必须经 `sai_deserialize_free_attribute_value()` 配对释放（`SaiAttr.cpp:46-51`）。试图用值拷贝复制属性、或绕过析构手工释放，都会造成内存问题。第四类是混淆两套对象表示：`saimeta::SaiObject`（`meta/SaiObject.h`）与 `syncd::SaiObj`（`syncd/SaiObj.h`）都持有元键与属性表，但属性元素类型与命名空间不同；在错误的结构上找字段会一无所获。第五类是把 05 册当流程书或参数书读：想理解 syncd 怎么消费 `ASIC_DB` 并调用 SAI 应读 06 册（原理见 06-05），想查 SAI 与 orchagent 参数应读 04 册（参数见 04-06），想按目录找 sairedis 模块应读 07 册（模块见 07-04）；反过来，在 06 / 07 / 08 册看到完整字段表属于去重铁律被破坏，应改写成「字段见 05-04」。第六类是版本与边界假设：`SAI/` 空目录、`saimetadata.h` 不在快照、厂商实现闭源，都不能据本快照补字段；`config` 返回成功不代表芯片已编程，加密或旁路场景不会改变字段存在性但会影响表项内容；凡涉及吞吐、pps、内存占用的结论一律标注「需在目标机型实测」，不给绝对值。排错时若读到「看似合理但明显不对」的值，先确认 sairedis 与 SAI 头文件来自同一快照，再按「位布局 → 元数据类型 → VID/RID 映射 → 属性序列化」顺序逐项回查源码（诊断树见 08-03）。
