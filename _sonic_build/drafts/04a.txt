# SONiC 技术资料 · 04 参数与 API 手册（分片 A）

## 04-01 构建变量与 Makefile 参数全集

### 1. 本篇定位与覆盖范围

本篇是 04 册参数与 API 手册的构建变量分册，承担一个明确而狭窄的职责：把 SONiC 镜像构建过程中出现的可调变量集中列成一张可反查的字典。它是全册关于「构建变量叫什么、取什么值、默认是什么、配错会怎样」的唯一权威源，其余各册涉及构建参数时只给本场景的最小必要调用并写「完整变量见 04-01」，不再重列。这样安排是为了避免同一个 `PLATFORM` 或 `BLDENV` 在构建册、部署册、运维册里各写一遍、彼此不一致。这里只回答「参数是什么」，不回答「构建流水线如何运作」「容器按什么顺序拉起」——后者属于机制范畴，统一写「原理见 06-13」「模块见 07-01」「镜像模块见 07-11」；字段级结构（如 `SonicDBConfig`、`FieldValueTuple`）属于 05 册，本篇不展开，统一写「字段见 05-03」。

覆盖范围以事实锚点为准，全部路径相对 `upstream_src/sonic-buildimage/sonic-buildimage-master/` 仓库根。具体包括四类文件族。第一类是顶层总控：`Makefile` 用 `%::` 通配目标把构建转交 `Makefile.work`，并按 `BLDENV` 进入不同的 `sonic-slave-*/` 构建容器，这里定义了 `NOJESSIE`、`NOBOOKWORM`、`NOTRIXIE` 等发行版开关与 `Q`、`MAKE_WITH_RETRY` 等总控变量。第二类是 `Makefile.work`，它的文件头注释列出构建者可以显式传入的参数，如 `PLATFORM`、`BUILD_NUMBER`、`SONIC_BUILD_JOBS`、`KEEP_SLAVE_ON`、`SONIC_DPKG_CACHE_METHOD` 等。第三类是 `slave.mk`，它承载路径与默认值体系，如 `SRC_PATH`、`TARGET_PATH`、`BLDENV`、`CONFIGURED_ARCH`、`IMAGE_DISTRO`、`SLAVE_DIR`。第四类是镜像装配配置 `onie-image.conf` 与 `rules/` 下的 `.mk`、`.dep` 规则，前者定义分区大小、产物文件名，后者把变量落实为镜像目标。

需要在一开始就划清三条边界，否则读者容易把本篇当成构建教程。其一，本篇不提供从零构建的操作步骤，那是 02-03 实战型章节的任务；这里只列变量，操作闭环写「完整流程见 02-02、02-03」。其二，本篇不写死任何绝对版本号。所有变量的默认值均标注来源，能在本快照源码核实的直接给真实值并注明所在文件，无法核实的写「需对照实际版本核验」，绝不凭印象补值——例如各子仓的精确版本字符串由构建过程生成，不在本篇给数字。其三，本篇涉及的平台、ASIC、chassis 相关开关（如多 ASIC 命名空间、warm reboot 相关构建项）一律写「受平台与版本限制，需对照实际版本核验」，不宣称全平台无条件支持。版本基准统一为「上游 master 快照（2026-11 抓取）」。

本篇的组织方式如下：第 2 节给出全参数索引与分族参数表，每行按「参数/键 → 取值 → 默认值 → 作用 → 误配后果」五列填写；第 3 节按变量族逐项详解，解释默认值来源与相互制约关系；第 4 节给两组可核验的命令与输出判读示例；第 5 节给一张按使用频率排序的速查表；第 6 节说明版本差异；第 7 节汇总常见误用与调试入口。读者若要顺着变量看它如何驱动容器启动，转 06-13 与 07-02；若要按变量改平台适配，转 02-04 与 07-10。交叉引用统一写作「字段见 05-xx ｜ 原理见 06-xx ｜ 模块见 07-xx」。

### 3. 逐项详解

**发行版开关族。** 顶层 `Makefile` 的前八行定义了六个 `NO*` 开关，语义统一：取值 0 表示「不跳过」，即启用对应发行版构建；取值 1 表示跳过。默认值里，`NOJESSIE`、`NOSTRETCH`、`NOBUSTER`、`NOBULLSEYE` 为 1，说明这四种老旧发行版默认关闭；`NOBOOKWORM` 与 `NOTRIXIE` 为 0，说明 bookworm 与 trixie 默认开启。这组开关通过 `ifeq` 条件块转换为 `BUILD_JESSIE`、`BUILD_TRIXIE` 等内部标记，再由 `%::` 通配目标决定向 `Makefile.work` 传入哪个目标与 `BLDENV`。这里有一个容易忽略的约束：`BAZEL_MIN_READINESS` 与发行版强绑定，快照中的错误提示明确写着 Bazel 组件只支持 trixie，一旦在非 trixie 构建启用，会拼接出 `BAZEL_NON_TRIXIE_BUILDS` 并触发 `$(error ...)` 直接中止。因此调发行版开关时必须同时核对 Bazel 相关变量，不能孤立修改。构建链如何按这些开关进入不同容器，属于机制内容，写「原理见 06-13」。

**总控与路径族。** `Makefile` 把任意目标 `%::` 转交给 `Makefile.work`，并拼上 `MAKE_WITH_RETRY`，其默认值为 `./scripts/run_with_retry $(MAKE)`，作用是在构建失败时按脚本策略重试；若该脚本缺失或被改动，所有目标的失败重试都会失效。`slave.mk` 定义了一组以路径为贵的变量：`SRC_PATH=src`、`RULES_PATH=rules`、`TARGET_PATH=target`、`DOCKERS_PATH=dockers`，它们共同决定源码、规则、产物与容器定义的位置。这组变量一般不直接改，但排障时必须能读懂，因为产物路径 `target/` 下的 deb、files、phony、python-debs、python-wheels 等子目录都由 `TARGET_PATH` 与 `BLDENV` 二次拼接而成。`PROJECT_ROOT` 取当前工作目录，`BUILD_WORKDIR=/sonic` 是容器内工作目录，二者不一致是「宿主路径与容器路径混淆」类问题的常见根因。`SLAVE_DIR` 默认 `sonic-slave-$(BLDENV)`，与 `BLDENV` 联动——`BLDENV` 的默认来源是 `lsb_release -cs` 的输出，这意味着在不同发行版的宿主上执行同一份 `Makefile` 可能选中不同 slave 容器，构建结果自然不同。

**平台与架构族。** `CONFIGURED_PLATFORM` 在 `slave.mk` 中优先读取 `.platform` 文件，文件不存在时回落到 `generic`；`PLATFORM` 若由命令行显式给出，则顶层 `Makefile` 用 `$(if $(PLATFORM),$(PLATFORM),$(CONFIGURED_PLATFORM))` 决定 `PLATFORM_PATH`。这套「命令行参数优先于文件、文件优先于默认值」的优先级链，是判断「为什么我改了 .platform 却没生效」的关键：多半是命令行仍带着 `PLATFORM=`。架构侧 `CONFIGURED_ARCH` 默认 `amd64`，并派生出 `DOCKER_BASE_ARCH`；当取 `armhf` 时改为 `arm32v7`、取 `arm64` 时改为 `arm64v8`，跨平台场景还会设置 `DOCKER_DEFAULT_PLATFORM` 与 `MULTIARCH_QEMU_ENVIRON`、`CROSS_BUILD_ENVIRON`。`IMAGE_DISTRO` 默认 `trixie`，`ENABLE_PY2_MODULES` 按 `BLDENV` 是否属于 bullseye、bookworm、trixie 决定取 n 或 y——这些联动关系说明，构建变量不是彼此孤立的开关，而是一张有优先级的约束网。平台适配的具体目录结构写「模块见 07-10」。

**Makefile.work 参数族。** `Makefile.work` 文件头以注释形式列出构建者可显式传入的参数，本篇表 04-01-C 已逐项收录。这批参数的特点是「多数无显式默认值或默认值需对照实际版本核验」，因为它们往往由 `rules/config` 或各 `.mk` 文件在具体上下文中赋值，不能脱离版本空谈默认值。以 `KEEP_SLAVE_ON` 为例，注释明确它把 slave 容器保留在构建结束后，但 `rm=true` 仍在，用户退出会话后容器会被删除；`SOURCE_FOLDER` 只在 `KEEP_SLAVE_ON=yes` 时有效，二者必须配对。又如 `ENABLE_TRANSLIB_WRITE`、`ENABLE_NATIVE_WRITE`、`ENABLE_DIALOUT` 默认未设置，取 `y` 才打开对应管理面写或外连能力，生产构建默认不应开启——这属于安全加固边界，具体写法见 08-05。缓存类三个变量 `SONIC_DPKG_CACHE_METHOD`、`SONIC_DPKG_CACHE_SOURCE`、`SONIC_DPKG_CACHE_METHOD_OVERRIDE` 共同决定 Debian 包从何处获取，误配的直接后果是拉到与快照不匹配的版本，破坏可复现性。并发数 `SONIC_BUILD_JOBS` 与 `VS_PREPARE_MEM` 影响构建资源：后者默认 `yes`，会在 vs 构建前清缓存压缩内存，设为 `no` 虽省去准备动作，却可能在大构建时内存不足。

**镜像装配变量族。** `onie-image.conf` 用 shell 的参数展开语法给变量赋默认值，形如 `: ${ONIE_IMAGE_PART_SIZE:=32768}`，含义是「若变量未设置或为空，则赋 32768」。这解释了为什么表 04-01-D 中这些值可以确认为真实默认值：它们直接写在文件里，而非运行时计算。分区相关变量里，`ONIE_IMAGE_PART_SIZE=32768` 即 32GB，`DOCKER_RAMFS_SIZE=3500M`，`RAW_IMAGE_DISK_SIZE=1700`（MB），`KVM_IMAGE_DISK_SIZE=16`（GB）；这些数字决定了产物能否装下完整系统，属于构建期约束而非性能结论，不需标注「需在目标机型实测」，但改动前须评估目标硬件的容量。产物名变量统一以 `OUTPUT_` 开头，其中 `OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin`、`OUTPUT_RAW_IMAGE`、`OUTPUT_KVM_IMAGE`、`OUTPUT_ABOOT_IMAGE`、`OUTPUT_DSC_IMAGE` 分别对应 ONIE、raw、KVM、aboot、DSC 五种形态；`TARGET_MACHINE` 默认为 `generic`，因此默认产物名形如 `target/sonic-generic.bin`。装配脚本如何把这些变量落实为 ONIE 安装包属于镜像模块职责，写「模块见 07-11」。

### 4. 典型示例

本节给两组示例。第一组用只读命令核验顶层发行版开关与路径变量的当前取值，第二组核验 onie-image.conf 的产物名与分区变量。所有输出块均注明「示例输出，具体格式需对照实际版本核验」，取值不得当作真实版本号引用。

第一组：在仓库根执行，核验 Makefile 中发行版开关的默认赋值。

```bash
grep -nE '^(NOJESSIE|NOSTRETCH|NOBUSTER|NOBULLSEYE|NOBOOKWORM|NOTRIXIE)\s*\?=' Makefile
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为示意，需与实际快照比对）
3:NOJESSIE ?= 1
4:NOSTRETCH ?= 1
5:NOBUSTER ?= 1
6:NOBULLSEYE ?= 1
7:NOBOOKWORM ?= 0
8:NOTRIXIE ?= 0
```

逐行判读如下。`grep` 用 `-n` 显示行号、`-E` 启用扩展正则，模式 `^(NOJESSIE|...)\s*\?=` 只匹配以这六个变量名开头、后接 `?=` 赋值符的行，`?=` 表示「仅当变量未定义时才赋值」，正是默认值语义。输出六行行号 3 到 8，与源码第 3 至第 8 行一一对应，说明命中的是顶层默认赋值而非条件块内的二次赋值。前四行 `NOJESSIE` 到 `NOBULLSEYE` 均为 1，表示四种老旧发行版默认跳过；第五行 `NOBOOKWORM ?= 0` 与第六行 `NOTRIXIE ?= 0` 表示 bookworm 与 trixie 默认启用，这与当前主线以 trixie 为目标的事实一致。若某行取值与这里不符，通常说明快照版本不同或有人改过默认值，应回到源码核对而非照抄本表。需要特别提醒：`?=` 允许命令行覆盖，所以运行时 `make NOJESSIE=0` 会让该变量变为 0，静态 grep 看到的默认值不代表最终生效值，这一点在排障时极易被忽略。发行版开关如何决定进入哪个 slave 容器属于机制范畴，写「原理见 06-13」。

第二组：核验产物名与镜像分区变量。

```bash
grep -nE '^(ONIE_IMAGE_PART_SIZE|TARGET_MACHINE|OUTPUT_ONIE_IMAGE|DOCKER_RAMFS_SIZE)' onie-image.conf
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为示意，需与实际快照比对）
7:: ${ONIE_IMAGE_PART_SIZE:=32768}
11:: ${TARGET_MACHINE:=generic}
31:DOCKER_RAMFS_SIZE=3500M
34:OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin
```

逐行判读如下。第一条命中 `ONIE_IMAGE_PART_SIZE:=32768`，其中 `:=` 的参数展开写法含义是「未设置或为空则赋 32768」，单位 MB，即默认 32GB 分区，与文件注释一致。第二条 `TARGET_MACHINE:=generic` 说明目标机器名默认 generic，它会进入后续产物文件名。第三条 `DOCKER_RAMFS_SIZE=3500M` 是普通赋值，直接给 docker ramfs 空间 3500M；注意这条没有用参数展开语法，意味着若脚本预先设置了同名变量，这里会覆盖它。第四条 `OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin` 展示产物名由 `TARGET_MACHINE` 插值而成，默认展开为 `target/sonic-generic.bin`；若 build 时传入 `TARGET_MACHINE=x86_64-generic-r0`，产物名随之改变。这组变量直接决定产物落点与容量，改动应同步检查 `installer/` 下的安装脚本是否按同样规则取名，安装链路属于镜像模块写「模块见 07-11」。以上输出均需对照实际版本核验，不得据示例数字下结论。

### 6. 版本差异

构建变量是随版本变动最频繁的一类参数，因此版本差异必须谨慎表述。本快照为「上游 master 快照（2026-11 抓取）」，表 04-01-A 与 D 中的默认值来自本快照可直接核实的源码行，读者在其它版本上应重新核对，不能直接套用。已知的变动趋势有三类，均不写成绝对结论。

第一类是发行版开关的演进。NO* 开关集合会随 SONiC 支持的 Debian 发行版增减而调整，本快照中 bookworm 与 trixie 默认开启、其余关闭，但更早或更晚的版本可能把默认值整体平移，例如把 NOBOOKWORM 翻转为 1、把更新发行版设为 0。`BAZEL_MIN_READINESS` 是本快照新出现 readiness 语义的体现，注释明确 Bazel 组件只支持 trixie，这类约束在旧版本中可能根本不存在。凡涉及发行版组合，一律写「受平台与版本限制，需对照实际版本核验」。

第二类是 Makefile.work 参数集合的增减。表 04-01-C 收录的参数来自文件头注释，本快照包含 gNMI 写开关、telemetry dialout、`GNMI_REDIS_POOL_SIZE` 等较新的管理面参数；这些参数在老版本可能缺失，在新版本可能继续增加。由于它们多数默认值由 `rules/config` 或各 `.mk` 在具体上下文赋值，脱离具体版本给出默认值没有意义，故本表统一标注「需对照实际版本核验」。读者若需要某参数的准确默认值，应回到对应版本的 `Makefile.work` 与 `rules/` 目录核实。

第三类是镜像装配变量的容量与命名演进。`ONIE_IMAGE_PART_SIZE=32768`、各类 `OUTPUT_*` 产物名在本快照可核实，但不同组织常在此处做本地化改动，例如调整分区大小、改为带日期的产物名、增加 DSC 或 aboot 之外的形态。因此这些值只能作为「本快照默认」使用，落到具体产品必须重新确认。跨版本比对时，建议固定一个最小变量集（发行版开关、平台、架构、产物名）做差异基线，其余变量按需扩展，对比命令与判读方法见 08 册基准章节。

### 7. 常见误用与调试

误用一：把静态默认值当成运行时生效值。表里的默认值来自源码赋值语句，但大量变量允许命令行覆盖。`?=` 与 `:=` 的参数展开都只在「未设置」时生效，一旦 build 命令显式传入，默认值不再起作用。典型症状是「我改了 .platform，产物平台却没变」，根因往往是命令行仍带着 `PLATFORM=`。调试入口是用只读命令核验运行时取值，第 4 节第一组示例演示了基本方法；更完整的构建日志分析写「原理见 06-13」。

误用二：把发行版开关当成彼此独立。六个 NO* 开关通过条件块联动，且受 `BAZEL_MIN_READINESS` 约束。把所有开关都设为 1 会导致没有任何目标执行；在非 trixie 构建启用 Bazel 会直接触发 `$(error ...)` 中止。调试时应先确认至少启用一个发行版，再单独核对 Bazel 相关变量，错误信息会明确指出需要哪些组合。

误用三：混淆宿主路径与容器路径。`PROJECT_ROOT` 是宿主当前目录，`BUILD_WORKDIR=/sonic` 是容器内工作目录，二者通过 slave 容器的挂载映射关联。排障时把宿主上的相对路径直接套到容器内、或反过来，是常见错误。`SOURCE_FOLDER` 只在 `KEEP_SLAVE_ON=yes` 时才挂载为 `/var/用户名/src`，单独设置不会生效，这类配对约束必须先满足前置条件。

误用四：把构建期容量数字当成性能结论。分区大小、ramfs 空间、镜像磁盘大小是构建与安装期的容量约束，不是转发性能或表项容量，不需标注「需在目标机型实测」；相反，收敛时间、下发时延、吞吐类数字一律标注「需在目标机型实测」，基准方法见 08-01。把两类数字混为一谈会得出错误结论。

误用五：误开管理面与调试开关。`ENABLE_TRANSLIB_WRITE`、`ENABLE_NATIVE_WRITE`、`ENABLE_DIALOUT`、`INSTALL_DEBUG_TOOLS` 默认未设置或按需设置，生产构建误开会扩大管理面写权限、引入外连或增大镜像与暴露面。这类开关的启用属于安全决策，须结合 08-05 的加固要求评估，不能因为是布尔开关就随手打开。

调试的通用顺序是：先用只读命令确认变量当前值，再对照本篇全表确认默认值来源与误配后果，然后判断是「静态默认值不符预期」还是「被命令行或环境覆盖」，最后才考虑修改。所有修改都应记录变更前后取值与产物路径，保证可复现。涉及机制的问题写「原理见 06-13」，涉及模块实现的问题写「模块见 07-01」「镜像模块见 07-11」，字段级结构写「字段见 05-03」，不在本篇展开。

## 04-02 CONFIG_DB 表与 schema 参数全集（一）：PORT、VLAN、INTERFACE

### 1. 本篇定位与覆盖范围

本篇是 04 册 schema 字典的第一分册，专门收录 `CONFIG_DB` 中与二层端口、VLAN 与三层接口直接相关的表：PORT、VLAN、VLAN_MEMBER、INTERFACE，以及与之紧邻的 MGMT_PORT。它的职责是回答「这几张表的键怎么拼、有哪些字段、字段取什么值、不填或填错会怎样」，并作为全册关于这些表 schema 的唯一权威源。其它册一旦涉及 PORT 或 VLAN 的表结构，只写「表结构与字段见 04-02」，不再重列字段清单。本篇不回答「这些字段如何被翻译成 ASIC 对象」——那是配置下发链路，写「原理见 06-06」；也不回答「字段在内存里如何表示成 `FieldValueTuple`」「`ConfigDBConnector` 如何封装读写」——那是结构字段范畴，写「字段见 05-02」；更不收录 `show` / `config` 的完整命令清单，那属于命令手册范围，本篇只在示例里给最小必要调用。

先说清 schema 的真实来源，这是本快照里最容易被写错的一点。按规范提示去 `files/image_config/config_db/` 找 schema 目录，在本快照中并不存在；schema 实际分散在三处。第一处是 `sonic-swss/doc/swss-schema.md`，其「Configuration DB schema」小节用 ABNF 语法给出 PORT、MGMT_PORT、NEIGH、WARM_RESTART、VXLAN_TUNNEL 等表的键与字段约束，这是最直接的字段来源。第二处是 `sonic-mgmt-common` 中的 YANG 模型：`cvl/testdata/schema/sonic-vlan.yang` 定义 VLAN 与 VLAN_MEMBER 的字段与取值范围，`models/yang/sonic/sonic-interface.yang` 定义 INTERFACE 的 `portname`、`ip_prefix`、`vrf-name`。第三处是字段常量与真实配置样例：`sonic-swss/orchagent/port/portschema.h` 以宏定义形式列出 PORT 表字段名（如 `PORT_SPEED`、`PORT_FEC`、`PORT_MTU`、`PORT_LEARN_MODE`），而 `device/<vendor>/<hwsku>/config_db*.json` 给出具体机型的填充值。撰写时凡能在这三处核实的写真实值，核实不了的写「需对照实际版本核验」，并给出可定位目录。

覆盖范围限定在「配置侧」。需要特别区分 `CONFIG_DB` 的 INTERFACE 表与 `APPL_DB` 的 INTF_TABLE：前者是用户与开机配置写入的三层地址意图，后者是 mgrd 翻译后的期望状态，字段集合并不相同——`scope`、`family`、`if_mtu` 出现在 APPL_DB 侧而非 CONFIG_DB 的 INTERFACE 表。本篇只列 CONFIG_DB 侧字段，下游表写「字段见 05-02」「原理见 06-06」。同理，PORT 表的 `oper_status`、`state` 属于 STATE_DB 的运行时状态，不在本篇的 CONFIG_DB 参数表内。版本基准统一为「上游 master 快照（2026-11 抓取）」，不写绝对版本号，也不写死任何 Redis DB 编号——库编号来自运行时配置，须按 `SonicDBConfig` 核验，写「字段见 05-03」。

本篇结构如下：第 2 节给表索引与三类表的全参数表，每行按「参数/键 → 取值 → 默认值 → 作用 → 误配后果」五列填写；第 3 节逐族详解字段约束与相互制约；第 4 节给配置片段与库查询两组示例及逐行判读；第 5 节给按场景组织的速查表；第 6 节说明版本差异；第 7 节汇总常见误用与调试顺序。读者若要顺着字段追到下发链路，转 06-06；若要按机型理解 lanes 与 speed 的来源，转 02-04 与「模块见 07-10」。交叉引用统一写作「字段见 05-xx ｜ 原理见 06-xx ｜ 模块见 07-xx」，本篇不自我引用。

### 2. 索引与全参数表

先给表索引。下表列出本篇覆盖的五张表、键的拼法、用途与 schema 来源；键中的竖线是 CONFIG_DB 的分隔符，在表格单元格里按规范转义书写。

### 3. 逐项详解

**PORT 表的字段约束与相互制约。** PORT 表描述的是交换 ASIC 管理的物理二层端口，管理口与逻辑口不在其中。`ifname` 作为键，必须在 PORT、INTF、VLAN、LAG 几类表之间保持唯一，这是因为下游按接口名索引，重名会让翻译层无法确定对象。字段中最容易出错的是 `speed`、`lanes`、`fec`、`interface_type` 这一组：它们描述的是同一条物理链路的不同侧面，必须与机型端口配置和实际光模块一致。例如 `speed` 以 Mbps 为单位，`200000` 表示 200G；`lanes` 给出承载这条端口的物理通道编号列表，来自 `device/<vendor>/<hwsku>/` 下的端口配置；`fec` 取 none、rs、fc、auto 之一，须与对端一致，否则即使链路 up 也会有高误码；`interface_type` 的枚举值在 portschema.h 中可核实，涵盖 cr、sr、lr、kr 系列与 caui、gmii、sfi、xfi、xgmii 等。默认值方面，本快照的 ABNF schema 只给出取值格式，未给统一默认值，真实默认依机型与版本而变，故全表标注「需对照实际版本核验」。`learn_mode`、`role`、`pt_interface_id`、`pt_timestamp_template` 属于较新或平台相关字段，前者决定 MAC 学习落到丢弃、硬件、CPU 陷落或通知等模式，后者多用于 chassis 与路径追踪，能力受平台与版本限制，写「受平台与版本限制，需对照实际版本核验」。

**PORT 字段的运行时对照。** 需要再次强调配置值与运行时值的分离：`admin_status` 在 CONFIG_DB 里是用户意图，`oper_status` 与 `state` 则出现在 STATE_DB，反映 ASIC 编程后的实际状态。把一个写成另一个、或期待写入 `admin_status` 后 `oper_status` 立刻变化，都是对异步流水线的误读——配置返回成功不代表硬件已下发。判断端口是否真正生效，要按 CONFIG_DB、APPL_DB、ASIC_DB、STATE_DB 的顺序逐段核对，完整诊断树写「原理见 06-01」「原理见 06-06」。字段在结构层面的载体写「字段见 05-02」，端口相关 Orch 的派生结构写「字段见 05-07」。

**VLAN 与 VLAN_MEMBER 的搭配规则。** VLAN 表以 `Vlan<vlanid>` 命名，YANG 中有一条 must 约束强制名称必须等于字符串 Vlan 拼接 vlanid，例如编号 100 对应名称 Vlan100；`vlanid` 为必填 uint16，范围 1 至 4095，越界会触发名为 vlanid-invalid 的校验错误并带相应 error-app-tag。MTU 为 uint32，范围 1312 至 9216，越界触发 mtu-invalid。`members` 是成员端口列表，引用的是端口名，若引用了不存在的端口，成员关系无法落地。VLAN_MEMBER 表以复合键 `Vlan<vlanid>` 加 `ifname` 定位单条成员关系，关键在于 `tagging_mode`：它取 tagged、untagged、priority_tagged 三种，YANG 明示默认值为 tagged。这一默认值在排障时尤其重要——「我以为没配就是 untagged」是常见误解，实际未显式指定时会按 tagged 处理，与对端 untagged 配置相遇就会造成标签错乱。VLAN 与成员如何被下发给 ASIC，写「原理见 06-06」。

**INTERFACE 表与下游表的区别。** INTERFACE 表承载三层地址意图：`portname` 可以是物理端口、VLAN 接口、PortChannel 或 Loopback，`ip_prefix` 是 IPv4 或 IPv6 前缀，`vrf-name` 把接口绑定到指定 VRF。在 YANG 里它由两条 list 分工表达，一条以 portname 为键描述接口与 VRF，一条以 portname 加 ip_prefix 为复合键描述地址。最需要澄清的区别是：本表的字段集合与 APPL_DB 的 INTF_TABLE 不同。后者由 mgrd 翻译产生，包含 `scope`（global 或 local）、`family`（IPv4 或 IPv6）、`if_mtu` 等字段，这些字段不出现在 CONFIG_DB 的 INTERFACE 表里；反过来，CONFIG_DB 侧的 `vrf-name` 也不等于下游表结构。把两层字段互相套用，会导致配置写到正确的库却用错字段名。下游字段写「字段见 05-02」，翻译链路写「原理见 06-06」。`vrf-name` 指向的 VRF 须先存在，其状态在 STATE_DB 的 VRF_TABLE 中体现，属于运行时观测范畴，不在本篇参数表内。

把三类表放在配置落地的位置上看，能看清字段误配会在哪一段暴露。下表字段经校验、翻译与编排逐级流向 ASIC，任何一级都可能因字段问题止步。本篇表字段的下游去向见图 04-02-01。

### 4. 典型示例

本节给两组示例。第一组是一段 `config_db.json` 配置片段，覆盖 PORT、VLAN、VLAN_MEMBER、INTERFACE 四表，字段名与键拼法按本快照 schema 书写；第二组用逻辑库名查询 PORT 表项并逐行判读。所有输出块均注明「示例输出，具体格式需对照实际版本核验」，取值不得当作真实设备数据引用。

第一组：配置片段。

```json
{
    "PORT": {
        "Ethernet1": {
            "alias": "Eth200GE0/1",
            "lanes": "25,26,27,28",
            "speed": "200000",
            "admin_status": "up",
            "mtu": "9100",
            "fec": "rs"
        }
    },
    "VLAN": {
        "Vlan100": {
            "vlanid": "100",
            "mtu": "9100",
            "admin_status": "up"
        }
    },
    "VLAN_MEMBER": {
        "Vlan100|Ethernet1": {
            "tagging_mode": "untagged"
        }
    },
    "INTERFACE": {
        "Vlan100|10.0.0.1/24": {},
        "Ethernet1|2001:db8::1/64": {}
    }
}
```

这段配置说明四件事。其一，PORT 表以 `Ethernet1` 为键，`lanes` 把四个物理通道绑成一条 200G 端口，`speed` 用 Mbps 表示，`fec` 取 `rs`，这些值须与机型端口配置及光模块一致，字段名可在 `sonic-swss/orchagent/port/portschema.h` 核实。其二，VLAN 表以 `Vlan100` 命名，`vlanid` 为 `100`，符合「名称等于 Vlan 拼接 vlanid」的约束，`mtu` 为 `9100`，落在 1312 至 9216 范围内。其三，VLAN_MEMBER 的键 `Vlan100|Ethernet1` 是复合键，把端口加入 VLAN，这里显式写 `untagged`，避免落到默认 `tagged` 造成与对端不一致——这正是第 3 节强调的默认值陷阱。其四，INTERFACE 表用 `portname|ip_prefix` 作键，IPv4 与 IPv6 地址各一条，空对象表示除地址外不附加其它字段；若需绑定 VRF，应另有以 portname 为键、携带 `vrf-name` 的表项。字段名与取值均需对照实际版本核验，逐字段结构写「字段见 05-02」。

第二组：用逻辑库名读取 PORT 表项，避免写死任何 Redis DB 编号。

```bash
sonic-db-cli CONFIG_DB HGETALL "PORT|Ethernet1"
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
"admin_status" "up"
"alias" "Eth200GE0/1"
"fec" "rs"
"lanes" "25,26,27,28"
"mtu" "9100"
"speed" "200000"
```

逐行判读如下。命令本体使用 `sonic-db-cli`，第一个参数是逻辑库名 `CONFIG_DB` 而非数字编号，这一点至关重要：库编号来自运行时 `database_config.json`，须按 `SonicDBConfig` 核验，禁止写死「某库是某号」，写「字段见 05-03」。`HGETALL` 读取键 `PORT|Ethernet1` 的全部字段，竖线是 CONFIG_DB 的键分隔符。输出六行均为「字段名 值」对：`admin_status` 为 `up`，是用户写入的管理意图，不等于操作状态已 up；`alias` 为面板别名，供 LLDP/SNMP 使用；`fec` 为 `rs`，须与对端一致；`lanes` 为四个通道，与 200G 速率匹配；`mtu` 为 `9100`；`speed` 为 `200000`，即 200000 Mbps。判读的关键不是逐字确认这些值，而是确认「配置库里确实有这条表项且字段齐全」——若这里缺字段或为空，问题在配置落地阶段；若这里正确但端口仍异常，则问题在下游 APPL_DB、ASIC_DB 或 STATE_DB，应按链路逐段核对，写「原理见 06-01」「原理见 06-06」。输出的字段顺序在不同版本可能不同，取值仅为格式示意，需对照实际版本核验。

### 5. 速查表

下表按排障场景组织，给出「想确认什么 → 看哪张表的哪个字段 → 该字段的约束」的快速映射。它不重复第 2 节全表，只提供定位入口。

| 场景 | 关注表与字段 | 约束或默认 |
|---|---|---|
| 端口起不来 | PORT 的 speed、lanes、fec、interface_type | 互相匹配且与机型一致，默认需核验 |
| 端口名或别名冲突 | PORT 的 ifname、alias | 跨 PORT/INTF/VLAN/LAG 唯一 |
| MAC 学习行为异常 | PORT 的 learn_mode | 六类枚举，取值影响转发学习 |
| VLAN 编号报错 | VLAN 的 vlanid、name | 1 至 4095，名称须等于 Vlan 拼接编号 |
| VLAN MTU 报错 | VLAN 的 mtu | 1312 至 9216 |
| VLAN 标签错乱 | VLAN_MEMBER 的 tagging_mode | 默认 tagged，需与对端一致 |
| IP 地址未生效 | INTERFACE 的 portname、ip_prefix | 接口须存在，前缀格式合法 |
| 接口 VRF 绑定失败 | INTERFACE 的 vrf-name | 指向的 VRF 须先存在 |
| 配置有但状态不对 | 对照 STATE_DB 的 oper_status、state | 不属 CONFIG_DB，按链路核对 |
| 读库时编号不明 | 逻辑库名而非数字编号 | 编号按 SonicDBConfig 核验 |

速查表的使用原则是「先定位、再回全表」：由此找到表名与字段后，回到表 04-02-A 至 C 核对取值、默认值与误配后果。凡涉及「配置正确但状态不对」的情形，一律转状态与链路章节，不在本表硬找答案。

### 6. 版本差异

schema 是随版本持续演进的内容，本篇所有表都应视为「本快照默认」。变动趋势有四类，均不写成绝对结论。

第一类是 schema 来源本身在演进。本快照中 PORT 的 ABNF 定义位于 `sonic-swss/doc/swss-schema.md`，字段常量位于 `orchagent/port/portschema.h`，VLAN 与 INTERFACE 的约束位于 `sonic-mgmt-common` 的 YANG 模型。不同版本里，这些定义可能迁移位置、拆分文件或改变严格程度；尤其 `sonic-swss-common` 不在本快照，字段级结构须写「不在本快照，需对照实际版本核验」。因此每到一个新版本，应先重新定位这几处 schema 文件，再逐字段比对，不能拿本篇的字段清单直接套用。

第二类是字段集合的增减。PORT 表在本快照除基础字段外，还包含 `learn_mode`、`role`、`pt_interface_id`、`pt_timestamp_template`、`media_type`、`fast_linkup`、`macsec` 等较新或平台相关字段；老版本可能没有，新版本可能继续增加。凡是平台相关字段，能力受平台与版本限制，写「受平台与版本限制，需对照实际版本核验」。VLAN 侧 `priority_tagged` 等 tagging 取值、INTERFACE 侧 `vrf-name` 的语义，也可能随 YANG 模型调整，须回到对应版本的 YANG 文件核实。

第三类是取值范围与默认值的调整。本快照可核实的范围包括 VLAN 的 vlanid 1 至 4095、mtu 1312 至 9216，以及 tagging_mode 默认 tagged。这些数字来自本快照的 YANG 文件，其它版本可能改变范围或默认，尤其是 mtu 上下界与 tagging 默认值，改动会直接影响配置校验结果。凡是本表标注「需对照实际版本核验」的默认值，都不应被理解为「没有默认值」或「默认空」，而是「本快照未给出可核实的统一默认」。

第四类是机型配置样例的差异。`device/<vendor>/<hwsku>/config_db*.json` 是具体机型的填充值，`lanes`、`speed`、`alias` 都与硬件强相关，不同 HWSKU 之间不可互换。把 A 机型的配置片段整段复制到 B 机型，是升级与批量部署中的高频错误，后果通常是端口无法映射硬件。机型适配的具体目录结构写「模块见 07-10」。跨版本比对时，建议固定一个最小字段集（端口键、speed、lanes、mtu、VLAN 编号与 tagging、接口地址）作为基线，其余字段按需扩展。

### 7. 常见误用与调试

误用一：键拼法与唯一性错误。CONFIG_DB 用竖线作分隔符，PORT 键为 `PORT|ifname`，VLAN_MEMBER 为 `VLAN_MEMBER|Vlan<vlanid>|ifname`，INTERFACE 为 `INTERFACE|portname|ip_prefix`。把分隔符写错、漏写复合键的一段、或让 ifname 在 PORT、INTF、VLAN、LAG 间重名，都会让下游无法定位对象。调试时先用只读命令确认键的实际拼法，再核对字段是否随键落在同一条表项上。

误用二：VLAN 名称与编号不一致。YANG 的 must 约束要求名称等于 Vlan 拼接 vlanid，写 `Vlan100` 却把 `vlanid` 填成 200 会触发校验错误；vlanid 取 0 或超过 4095 触发 vlanid-invalid；mtu 越出 1312 至 9216 触发 mtu-invalid。这类错误会在配置校验阶段被拦下，表现为配置未写入，而非硬件异常。

误用三：tagging_mode 默认值误判。未显式指定时按 YANG 默认的 tagged 处理，若对端按 untagged 接入，就会出现 VLAN 标签错乱、二层互通失败。正确做法是显式写出 tagging_mode 并与对端核对，而不是依赖默认。

误用四：混淆 CONFIG_DB 的 INTERFACE 与 APPL_DB 的 INTF_TABLE。前者是用户配置，字段为 portname、ip_prefix、vrf-name；后者是 mgrd 翻译后的期望状态，含 scope、family、if_mtu。把下游字段写进配置表、或期待在配置表里看到 oper 状态，都是层次错配。字段级区别写「字段见 05-02」，翻译链路写「原理见 06-06」。

误用五：把配置返回成功当成硬件已下发。PORT、VLAN、INTERFACE 都是异步流水线的输入，写入 CONFIG_DB 只是第一步。判断生效要按 CONFIG_DB、APPL_DB、ASIC_DB、STATE_DB 顺序逐段核对，再结合 `show` 输出，不能因命令返回成功就断言转发已生效，写「原理见 06-01」。

误用六：写死 Redis DB 编号或跨机型复制配置。库编号来自运行时配置，须按 `SonicDBConfig` 核验，写「字段见 05-03」；`lanes`、`speed`、`alias` 与机型强相关，跨 HWSKU 复制配置会导致端口无法映射硬件，写「模块见 07-10」。

调试的通用顺序是：先用逻辑库名读 CONFIG_DB，确认表项存在、键拼法正确、字段齐全；再核对本篇全表确认取值与默认；若配置正确但状态不对，转 APPL_DB、ASIC_DB、STATE_DB 逐段核对；若字段语义或结构有疑问，转 05 册；若追下发链路，转 06-06。所有结论均以「上游 master 快照（2026-11 抓取）」为基准，不确定的表名、字段、取值范围一律标注「需对照实际版本核验」并给出可定位目录，不凭印象补值。
