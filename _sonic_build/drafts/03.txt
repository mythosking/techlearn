# SONiC 技术资料 · 03 集成与部署

## 03-01 最小可用部署：虚拟交换机镜像启动与基本配置

### 1. 目标与拓扑

本篇要完成一件很具体的事：在一台普通的 x86 主机或虚拟机监控器上，把一个 SONiC 虚拟交换机（virtual switch，简称 vs）从镜像启动到能够登录、能够读到首屏状态、能够接受一条最基础的端口配置，并且每一步都给出可核对的预期输出与判读要点。这里的「最小可用」有明确边界：不追求转发性能，不追求业务协议齐全，只要求容器起来、配置库落地、命令行可读、端口状态可观察。之所以选 vs 作为部署教学的起点，是因为它是本套资料反复强调的唯一例外——SONiC 是白盒交换机网络操作系统，数据面在 ASIC，除 `platform/vs/` 虚拟交换机外不做软件转发；vs 用软件模拟转发，让没有真实交换 ASIC 的读者也能把整条启动链路走通，但它的性能数字绝不能外推到真实机型，一切吞吐、时延、收敛结论都需在目标机型实测（基准方法见 08-01）。

从本快照能核实到，虚拟交换机的全部素材集中在 `sonic-buildimage-master/platform/vs/`：这里有 `README.vsvm.md`、`README.vsdocker.md`、`README.gns3.md` 三份启动说明，`create_vnet.sh` 负责在宿主机上造出虚拟网卡与网络命名空间，`docker-sonic-vs.mk`、`docker-sonic-vs.dep`、`docker-syncd-vs.mk`、`docker-gbsyncd-vs.mk` 定义虚拟交换机与虚拟 syncd 镜像的构建规则，`sonic.xml` 与 `sonic_multiasic.xml` 是 libvirt 的虚拟机定义文件，`platform.conf` 与 `one-image.mk`、`raw-image.mk`、`kvm-image.mk` 决定镜像落盘形态。设备侧对应 `device/virtual/x86_64-kvm_x86_64-r0/`，其中有 `asic.conf`、`installer.conf` 与 `vs/platform.json`。也就是说，vs 不是一个凭空出现的软件，而是同一套构建体系在 `PLATFORM=vs` 下的产物；构建环节本身见 02-03 与 02-04，本篇只从「镜像已经具备」往下讲。

拓扑要分两种形态理解，它们共享同一份容器内部逻辑，只是外层承载不同。第一种是 Docker 形态：`README.vsdocker.md` 给出的路径是先用 `create_vnet.sh -n 2 sw` 造出两个前面板端口及对应的 `sw-srv0`、`sw-srv1` 网络命名空间，再用 `docker run --privileged --network container:sw` 启动 `docker-sonic-vs` 容器，使容器共享那组虚拟网卡；第二种是虚拟机形态：`README.vsvm.md` 给出的路径是用 libvirt 的 `virsh create sonic.xml` 创建域，通过 `telnet 127.0.0.1 7000` 的控制台或 `ssh -p 3040 admin@127.0.0.1` 登录，多 ASIC 场景还要先在 `asic.conf` 中写 `NUM_ASIC` 与 `DEV_ID_ASIC_*` 并准备 `topology.sh`。两种形态进入系统之后，看到的都是同一套容器化控制面与 Redis 分层库。

### 2. 前置条件与环境

第一类是镜像与源码前提。按能力边界，镜像构建必须在 `sonic-slave-*/` 构建容器内完成并经 ONIE 安装器产出，普通主机裸 `make` 得不到可安装镜像；vs 形态则按 `platform/vs/one-image.mk`、`kvm-image.mk`、`raw-image.mk` 产出可直接加载的虚拟磁盘或容器镜像。本篇假设读者已经拿到与「上游 master 快照（2026-11 抓取）」对应的镜像，具体版本号以对应构建文件为准、需对照实际版本核验。核验镜像来源是否混杂的一个简单办法是登录后执行 `show version` 看构建提交与时间是否同批，这类内容属于 04-05 的命令全集，本篇只用最小必要子集。

第二类是宿主机能力。Docker 形态需要宿主机具备 `docker` 命令、允许 `--privileged`，并能创建网络命名空间（`ip netns`）；`create_vnet.sh` 会用 `ip link` 建 veth 对并挂到命名空间，因此执行者需要 root 或等价权限。虚拟机形态需要 `libvirt-clients`、`qemu-kvm`、`libvirt-bin`（`README.vsvm.md` 第 3 行给出了 `sudo apt-get install libvirt-clients qemu-kvm libvirt-bin` 的安装示例），并确认 CPU 虚拟化已开启。两种形态都占用不少磁盘与内存，容量与资源规划需在目标机型实测，本篇不给绝对值。

第三类是配置与库前提。系统启动时会读取 `/etc/sonic/config_db.json`（这一默认路径可在 `sonic-utilities-master/config/main.py` 中核实，常量 `DEFAULT_CONFIG_DB_FILE = '/etc/sonic/config_db.json'`），必要时再由 `src/sonic-config-engine/sonic-cfggen` 从 `minigraph.xml` 渲染。Redis 各逻辑库的编号来自运行时 `/var/run/redis/sonic-db/database_config.json`，由 `sonic-py-swsssdk-master/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 解析，因此本篇不写死「某库是某号」，需要定位时写「参数见 04-04」并注明需对照实际版本核验。`swsscommon` 的实现本体、`sonic-swss-common`、Linux 内核与厂商 SAI 实现均不在本快照，涉及这些部分一律写「不在本快照，需对照实际版本核验」。

第四类是交叉引用约定，先把本篇会反复回查的坐标摆出来，避免后文重复展开：CONFIG_DB 表与 schema 的完整参数见 04-02、04-03，Redis 库对象见 04-04，`show` / `config` 命令全集见 04-05，容器与 supervisord 启动参数见 04-07；`FieldValueTuple`、`SonicDBConfig` 等结构字段见 05-02、05-03；配置流水线与容器编排原理见 06-01、06-13；vs 镜像与容器模块的职责见 02-04、07-02、07-11。统一写成（字段见 05-03 ｜ 参数见 04-05 ｜ 原理见 06-13 ｜ 模块见 07-02），实际行文按具体篇号替换。

### 3. 分步操作

整套操作按「前置检查 → 执行 → 验证输出 → 清理」闭环写，下面以 Docker 形态为主线，虚拟机形态在注释中给出对应动作。所有命令都在宿主机或容器内执行，示例中的镜像名、端口名与地址需对照实际版本与现场规划核验。

第一步，前置检查。在宿主机确认 `docker` 可用、镜像已加载、`create_vnet.sh` 存在且可执行，并检查没有同名容器或命名空间残留。对应 `platform/vs/` 目录应能列出 `create_vnet.sh`、`docker-sonic-vs.mk` 等文件；若镜像尚未构建，回到 02-03、02-04 处理。

第二步，造虚拟网络。执行 `create_vnet.sh -n 2 sw` 创建两个前面板端口，参数 `-n` 指定端口数、`sw` 是容器与命名空间的名字前缀，随后用 `ip netns list` 确认出现 `sw-srv0`、`sw-srv1`。这一步只在 Docker 形态需要；虚拟机形态跳过，改由 `virsh create sonic.xml` 创建域并按 `README.vsvm.md` 用控制台或 SSH 登录。

第三步，启动 vs 容器。用 `docker run --privileged --network container:sw --name vs -d docker-sonic-vs` 启动，`--network container:sw` 让容器共享第二步建好的网络命名空间，前面板端口因此在容器内表现为 `Ethernet0`、`Ethernet4` 等接口（端口编号与命名需对照实际版本核验）。`docker ps` 应看到 `vs` 处于 Up 状态。若使用虚拟机形态，则以 `sudo virsh` 进入交互终端后 `create sonic.xml` 启动，多 ASIC 还需按 `asic.conf` 与 `topology.sh` 先行配置并 `sudo systemctl start topology`。

第四步，进入容器做最小配置。`docker exec -it vs bash` 进入后，`README.vsdocker.md` 给出的两条最小配置是 `config interface ip add Ethernet0 10.0.0.0/31` 与 `config interface startup Ethernet0`，对 `Ethernet4` 做同样配置。这里要注意能力边界：`config` 写入的是 `CONFIG_DB`，后续要经各 `*mgrd` 到 `APPL_DB`、经 `orchagent` 到 `ASIC_DB`、再由 `syncd` 经 SAI 编程，命令返回不等于硬件已下发（原理见 06-01）。

第五步，核对配置落地。用 `show version` 看软件与平台标识，用 `show interfaces status` 看端口的管理态与操作态；必要时再在命名空间侧配好服务器地址，例如 `ip netns exec sw-srv0 ifconfig eth0 10.0.0.1/31`，然后用 `ping` 验证连通。若刚开机或刚做过配置加载，可用 `show platform summary` 辅助查看平台信息，命令名与输出格式需对照实际版本核验。

第六步，清理。教学或验证结束后，按「先停容器、再删网络命名空间」的顺序回收：宿主机上 `docker rm -f vs` 删除 vs 容器，`ip netns del sw-srv0`、`ip netns del sw-srv1` 删除命名空间，`docker rm -f sw` 清理承载网络名的 Debian 容器；虚拟机形态用 `virsh destroy sonic` 与 `virsh undefine sonic` 回收域。清理前确认没有还在跑的验证脚本，避免误删他人环境。

### 4. 验证方法与预期结果

验证分三层：登录与版本层、容器与库层、端口与连通层。只有三层都符合预期，才算「最小可用」达成。下面给出两组带输出的判读示例，每组都按「示例输出，具体格式需对照实际版本核验」标注。

第一组是首屏版本。执行 `show version`。

```bash
# 前置检查：确认已进入 vs 容器或已通过控制台登录
which show
# 执行：读取版本与平台标识
show version
# 验证输出见下方 text 块
# 清理：无需清理，只读命令
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意，不代表任何具体版本）
SONiC Software Version: SONiC.HEAD.000000-00000000
Distribution: Debian GNU/Linux 12 (bookworm)
Kernel: 6.1.0-0-amd64
Build commit: 0123456789abcdef
Build date: 2026-11-13 00:00:00 UTC
Built by: build-host
Platform: x86_64-kvm_x86_64-r0
HwSKU: vs
ASIC: vs
Uptime: 0 days, 00:07:12
```

逐行判读如下。第一行是软件版本标识，取值由构建产物决定，本套资料统一以「上游 master 快照（2026-11 抓取）」为基准，示例里的 `SONiC.HEAD.000000-00000000` 只是格式示意，不得当作真实版本号引用，具体版本号以对应构建文件为准、需对照实际版本核验；第二行发行版与第三行内核属于宿主基础系统，Linux 内核源码不在本快照，需对照实际版本核验；第四行构建提交与第五行构建时间用于把当前实例与某次构建对应，同批设备若这两项不一致，通常说明镜像来源混杂；第六行构建主机是排障线索；第七行 `Platform` 为 `x86_64-kvm_x86_64-r0`，与本快照 `device/virtual/x86_64-kvm_x86_64-r0/` 目录对应，说明机型文件加载方向正确；第八行 `HwSKU` 为 `vs`、第九行 `ASIC` 为 `vs`，共同表明这是虚拟交换机而非真实 ASIC，因此转发由软件模拟、性能数字需在目标机型实测，不能拿 vs 的吞吐外推真机；第十行 `Uptime` 反映启动后运行时长，若刚启动却显示很长，往往意味着连到了别的实例。整个输出来自 `sonic-utilities-master/show/main.py` 的 `version` 命令，它经 `swsscommon` 的连接器读取版本与平台信息，属于「CLI 只读状态、不编程 ASIC」的典型体现；`swsscommon` 本体在 `sonic-swss-common`，不在本快照，需对照实际版本核验（模块见 07-06 ｜ 参数见 04-05）。

第二组是端口状态。执行 `show interfaces status`。

```bash
# 前置检查：确认前面板端口已按第四步配置
show interfaces status
# 如需逐端口核对配置来源，可只读查询配置库变量（选项行为需对照实际版本核验）
sonic-cfggen -d -v "PORT"
# 清理：只读命令，无需清理
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
Interface   Lanes        Speed   MTU   Alias        Oper  Admin
Ethernet0   0,1,2,3      40000   9100  Eth1/1       up    up
Ethernet4   4,5,6,7      40000   9100  Eth1/2       down  up
```

逐行判读如下。第一行是列头：`Interface` 为端口名，`Lanes` 为物理通道编号，`Speed` 为速率，`MTU` 为最大传输单元，`Alias` 为面板别名，`Oper` 为操作状态，`Admin` 为管理状态；列名与顺序随版本变化，需对照实际版本核验。第二行 `Ethernet0` 的 `Oper` 与 `Admin` 同为 `up`，说明管理上启用且链路已起，是正常的期望结果。第三行 `Ethernet4` 的 `Admin` 为 `up` 但 `Oper` 为 `down`，是「管理已启用、链路未起」的典型特征，在 vs 环境里常因为对端命名空间侧接口未配置或未启用，也可能是 `CONFIG_DB` 的 `PORT` 表未写入、`APPL_DB` 未生成期望状态；正确排障顺序是按库逐段核对，而不是直接判定虚拟 ASIC 故障。示例中的 `Lanes`、`Speed`、`MTU` 数值要与 `device/tencent/x86_64-tencent_tcs8400-r0/config_db.TCS8400-24CC8CD.json` 里 `PORT` 表的 `lanes`、`speed`、`mtu` 字段对应理解，字段名与取值需对照实际版本核验、逐字段含义见 05-02；本快照没有 vs HWSKU 的 `config_db.json`，上面的端口取值仅为格式示意。第二块 `sonic-cfggen -d -v "PORT"` 只读打印配置库里的 `PORT`，`-d` 表示从配置库读取、`-v` 打印变量值，选项可在 `src/sonic-config-engine/sonic-cfggen` 的 `argparse` 段核实；若输出为空，说明 `PORT` 表尚未落地，应回到配置加载环节（原理见 06-03 ｜ 参数见 04-02）。

三种形态的判读结论小结如下：Docker 形态以 `ip netns list` 出现 `sw-srv0`、`sw-srv1`、`docker ps` 显示 `vs` 为 Up、容器内 `show interfaces status` 有端口行、命名空间侧 `ping` 通为最低通过线；虚拟机形态以 `virsh list` 域在运行、控制台或 `ssh -p 3040` 能登录、`show version` 与 `show platform summary` 有正常输出为最低通过线。二者共同的深层判据是配置库确实有表项、期望库与对象库按流水线推进，而不仅是命令行「看起来正常」（排障见 08-03）。

### 5. 常见失败与排错

vs 部署的失败面集中在容器、网络、配置三层，下面按「现象 → 可能原因 → 验证命令 → 修复要点」列出，表中命令名与日志路径需对照实际版本核验，单元格只写语义化简述。

| 现象 | 可能原因 | 验证命令 | 修复要点 |
|---|---|---|---|
| `docker run` 报权限错 | 未加 privileged 或用户不在 docker 组 | `docker ps -a` | 按 README 加 privileged |
| `ip netns list` 无命名空间 | create_vnet.sh 未执行或权限不足 | `ip netns list` | root 重跑脚本 |
| 容器起来但无 Ethernet0 | 未共享 sw 的网络命名空间 | `docker inspect vs` | 检查 network container 参数 |
| `show interfaces status` 无端口行 | PORT 表未落到配置库 | `sonic-cfggen -d -v PORT` | 重做配置加载 |
| 端口 Admin up 但 Oper down | 对端命名空间接口未配或未起 | `ip netns exec sw-srv0 ifconfig` | 配好服务器侧地址并启用 |
| ping 不通 | 地址掩码或默认路由写错 | `ip netns exec sw-srv0 ip route` | 按 README 修路由 |
| `config` 返回成功但状态不变 | 异步流水线尚未推进 | 逐段查 APPL_DB 与 ASIC_DB | 按库核对，勿判硬件故障 |
| `show version` 取值异常 | 镜像来源混杂或连错实例 | `show version`、`uptime` | 核对构建提交与 Uptime |

第一类失败是容器层。`docker run` 若缺少 `--privileged`，虚拟交换机无法操作宿主机网络资源，往往直接失败；`--network container:sw` 漏写则容器看不到前面板端口，表现为 `show interfaces status` 没有期望的 `Ethernet0`、`Ethernet4`。修复要点是回到 `README.vsdocker.md` 逐字核对命令，而不是改镜像。若容器反复重启，要用 `docker logs vs` 看启动日志，日志格式与路径需对照实际版本核验（参数见 04-08）。

第二类失败是网络层。`create_vnet.sh -n 2 sw` 依赖 `ip link` 与命名空间能力，权限不足或宿主机缺少 `iproute2` 都会导致 `ip netns list` 为空；命名空间建好后若服务器侧接口未配置，`README.vsdocker.md` 示例里的 `10.0.0.1/31` 与默认路由缺失，就会出现端口 `Oper down` 或 `ping` 不通。修复顺序是先确认命名空间存在，再确认容器内端口存在，最后确认两侧地址与路由成对出现。

第三类失败是配置层，也是最容易误判的一类。`config interface ip add` 返回成功只表示配置写进 `CONFIG_DB`，若等一会儿 `show interfaces status` 仍无变化，正确做法是按 `CONFIG_DB`、`APPL_DB`、`ASIC_DB`、`STATE_DB` 顺序逐段核对，并确认各 `*mgrd`、`orchagent`、`syncd` 进程在跑；不能把「命令成功」等同于「硬件已下发」。`config_db.json` 若为非法 JSON，配置加载会在 `sonic-cfggen -j ... --write-to-db` 环节失败，此时应先用 `python -m json.tool` 校验文件格式，再核对字段名；表结构见 04-02、04-03，字段含义见 05-02。需要强调的是，Redis 库编号须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 与实际版本核验，本篇一律不写死编号（原理见 06-02）。

第四类是事实边界陷阱。排障时不得把 vs 的软件转发等同于真实 ASIC 转发，也不得把 `orchagent` 写成直接读写寄存器；厂商 SAI 实现、FRR 协议源码、`sonic-swss-common` 与 Linux 内核都不在本快照，涉及这些部分写「不在本快照，需对照实际版本核验」，不得编造文件与版本。`warmrestart/`、多 ASIC 命名空间与 chassis 能力受平台与版本限制，vs 上的表现不能代表真机，需对照实际版本核验（模块见 07-04 ｜ 原理见 06-10 ｜ 06-11）。

### 6. 小结

本篇把虚拟交换机从镜像到最小可用走成了闭环：先按 `platform/vs/` 与 `device/virtual/x86_64-kvm_x86_64-r0/` 确认镜像与机型前提，再以 Docker 形态的 `create_vnet.sh`、`docker-sonic-vs` 或虚拟机形态的 `virsh create sonic.xml` 启动，用 `config interface ip add` 与 `config interface startup` 做最小配置，最后用 `show version`、`show interfaces status` 与按库核对完成判读，并以 `docker rm -f`、`ip netns del` 或 `virsh destroy` 收尾。图 03-01-01 与两张表把启动链路、失败面与判读顺序固定下来，核心结论只有一句：命令返回不等于生效，状态要按库逐段查。

需要再次提醒的是能力边界：SONiC 是白盒交换机 NOS，控制面容器化、数据面在 ASIC，vs 只是用于开发与测试的软件转发例外，性能数字需在目标机型实测；Redis 库编号来自运行时 `database_config.json` 而非源码常量，须对照 `SonicDBConfig` 核验；CLI 只读写各库、不编程 ASIC；构建依赖 `sonic-slave-*/` 与 ONIE 安装器，普通主机裸 `make` 得不到可安装镜像。本篇涉及的命令全集见 04-05、容器启动参数见 04-07（字段见 05-03 ｜ 参数见 04-05 ｜ 原理见 06-13 ｜ 模块见 07-02）。

下一篇 03-02 将把本篇里一带而过的「配置从哪来」展开：讲清 `/etc/sonic/config_db.json` 的落位、`minigraph.xml` 经 `src/sonic-config-engine/` 转换为配置库的全过程，以及 `config save` / `config load` / `config load_minigraph` 的闭环用法；表结构留在 04-02、04-03，字段含义留在 05 册，原理留在 06 册，跨册引用统一用（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）的写法，其中 `xx` 替换为具体篇号。版本基准始终为「上游 master 快照（2026-11 抓取）」，不写绝对版本号与 Redis DB 编号。

## 03-02 CONFIG_DB 与 minigraph / config_db.json 落地

### 1. 目标与拓扑

本篇要回答部署环节最容易被含糊带过的问题：配置到底从哪里来、以什么形态落在哪里、落地之后又怎样变成运行状态。所谓「落地」在本套资料里有两层含义。第一层是把人的意图写成 `CONFIG_DB` 里的表项，载体可以是开机时预置的 `/etc/sonic/config_db.json`，也可以是描述整机拓扑的 `minigraph.xml` 经配置生成引擎渲染后的结果；第二层是这些表项被后续进程逐段翻译，经各 `*mgrd` 到 `APPL_DB`、经 `orchagent` 到 `ASIC_DB`、再由 `syncd` 经 SAI 编程，最终反映到 `STATE_DB` 与 `show` 输出。只完成第一层就说「配置已生效」是错误的，因为 SONiC 的配置链路是异步流水线，`config` 返回成功不代表硬件已下发（原理见 06-01 ｜ 排障见 08-03）。

先明确三份关键输入各自的职责。`minigraph.xml` 是拓扑与设备关系的描述文件，本快照可在 `device/inventec/x86_64-inventec_d6254qs-r0/minigraph.xml` 等机型目录核实其存在；`port_config.ini` 一类端口文件描述端口到通道的映射，由 `src/sonic-config-engine/portconfig.py` 解析；`config_db.json` 则是可以直接写进配置库的 JSON 文件，本快照在 `device/tencent/x86_64-tencent_tcs8400-r0/config_db.TCS8400-24CC8CD.json` 中能核实到 `DEVICE_METADATA`、`PORT` 等表及字段。三者不是互斥关系：`minigraph.xml` 加端口文件经 `sonic-cfggen` 可以渲染出 `config_db.json`，`config_db.json` 经 `sonic-cfggen -j ... --write-to-db` 写进 `CONFIG_DB`；反过来，`config save` 又可以把当前配置库导出为 `config_db.json`，形成双向闭环。

落地的落点需要精确。本快照 `sonic-utilities-master/config/main.py` 中可核实的常量是 `SONIC_CFGGEN_PATH = '/usr/local/bin/sonic-cfggen'` 与 `DEFAULT_CONFIG_DB_FILE = '/etc/sonic/config_db.json'`，`save()` 的逻辑是执行 `sonic-cfggen -d --print-data > 文件`，`load()` 的逻辑是执行 `sonic-cfggen -j 文件 --write-to-db`，多 ASIC 时还会有 `/etc/sonic/config_db{NS}.json` 对应各命名空间。这一实现细节说明两件事：其一，`config_db.json` 的默认路径是配置库导出的「快照文件」，不是芯片配置本身；其二，真正把 JSON 变成库表项的是 `sonic-cfggen`。Redis 各逻辑库的编号来自运行时 `/var/run/redis/sonic-db/database_config.json`，由 `sonic-py-swsssdk-master/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 解析，本篇不写死编号（参数见 04-04）。

### 2. 前置条件与环境

第一类是生成引擎的可核验文件。`sonic-buildimage-master/src/sonic-config-engine/` 下有 `minigraph.py`、`minigraph_ext.py`、`portconfig.py`、`sonic-cfggen`、`config_samples.py` 与 `tests/` 等。其中 `minigraph.py` 可核实到 `parse_device()`、`parse_dpg()`、`parse_cpg()`、`parse_png()`、`parse_chassis_deviceinfo()` 等解析入口，并 `from portconfig import get_port_config`；`minigraph_ext.py` 提供 `parse_xml()`；`portconfig.py` 提供 `get_port_config()`、`parse_port_config_file()`、`get_system_port_config()`、`parse_platform_json_file()`、`get_breakout_mode()`、`get_child_ports()`。`sonic-cfggen` 顶部导入了 `minigraph_encoder`、`parse_device_desc_xml`、`get_port_config` 与 `swsscommon.swsscommon` 的 `ConfigDBConnector`、`SonicDBConfig`、`ConfigDBPipeConnector`，说明它同时具备「解析输入」与「写配置库」两种能力。`swsscommon` 本体在 `sonic-swss-common`，不在本快照，需对照实际版本核验（模块见 07-05 ｜ 参数见 04-02）。

第二类是 `sonic-cfggen` 的选项。其 `argparse` 段可核实到 `-m/--minigraph`（带 `const='/etc/sonic/minigraph.xml'`）、`-Y/--yang`（默认 `/etc/sonic/config_yang.json`）、`-k/--hwsku`、`-p/--port-config`（注释写明 used with -m or -k）、`-n/--namespace`、`-j/--json`、`-d/--from-db`、`-t/--template`、`-v/--var`、`--var-json`、`--print-data`、`-w/--write-to-db`、`-T/--template_dir`、`-a/--additional-data`、`-y/--yaml`、`-s/--redis-unix-sock-file`、`-K/--key`。脚本注释还给出三条典型用法：`sonic-cfggen -m -t /usr/share/template/bgpd.conf.j2` 渲染模板、`sonic-cfggen -d --print-data > db_dump.json` 导出配置库、`sonic-cfggen -j db_dump.json --write-to-db` 把 JSON 写回。本篇只使用这几条的最小子集，完整参数见 04-02 与 04-05。

第三类是文件与目录前提。系统侧应有 `/etc/sonic/minigraph.xml`（`-m` 的默认值）、`/etc/sonic/config_db.json`（配置导出默认文件）与 `/usr/local/bin/sonic-cfggen`（`config main.py` 中的路径）；机型侧的本快照可核验样例包括 `device/tencent/x86_64-tencent_tcs8400-r0/config_db.TCS8400-24CC8CD.json` 与 `device/inventec/x86_64-inventec_d6254qs-r0/minigraph.xml`，虚拟交换机侧则是 `device/virtual/x86_64-kvm_x86_64-r0/vs/platform.json`。要注意：vs 的 HWSKU 目录里没有 `config_db.json`，因此本文示例中的端口取值只作格式示意，真实字段需对照实际版本核验；`DEVICE_METADATA`、`PORT` 等表名可在上述腾讯机型文件中核实。

第四类是交叉引用与事实纪律。CONFIG_DB 表与 schema 全集见 04-02、04-03，Redis 库对象见 04-04，`show` / `config` 命令全集见 04-05；`FieldValueTuple` 与 `SonicDBConfig` 字段见 05-02、05-03；配置流水线、mgrd 校验与 orchagent 调度原理见 06-01、06-02、06-03、06-04；YANG 与 translib 管理面见 06-14、07-07。涉及 FRR 协议源码、Linux 内核、厂商 SAI 实现与 `sonic-swss-common` 时写「不在本快照，需对照实际版本核验」，涉及库编号时写「参数见 04-04」并注明需对照实际版本核验。统一写成（字段见 05-03 ｜ 参数见 04-02 ｜ 原理见 06-03 ｜ 模块见 07-05）。

### 3. 分步操作

所有操作按「前置检查 → 执行 → 验证输出 → 清理」闭环写。为便于对照，下面把三条路径并列：从已有 `config_db.json` 加载、从 `minigraph.xml` 重新生成、手工调用 `sonic-cfggen` 渲染并写库。命令名、路径与选项需对照实际版本核验。

第一步，前置检查。确认 `sonic-cfggen` 在 `/usr/local/bin/sonic-cfggen`，确认 `/etc/sonic/config_db.json` 存在且为合法 JSON（可用 `python -m json.tool /etc/sonic/config_db.json > /dev/null` 校验），确认 `minigraph.xml` 与端口文件存在。若文件缺失，不要凭印象补写字段，应回到 `src/sonic-config-engine/` 与 `device/<vendor>/<hwsku>/` 核对来源。

第二步，从已有 JSON 加载。执行 `config load`，它默认读取 `/etc/sonic/config_db.json`，内部按 `config main.py` 的逻辑调用 `sonic-cfggen -j /etc/sonic/config_db.json --write-to-db`；带 `-y` 可跳过确认提示，指定文件名则读指定文件，多 ASIC 场景需要按命名空间提供多个文件，文件数量不匹配会直接报错。执行前系统会提示现有配置将被覆盖，生产中应先备份（参数见 04-05）。

第三步，从 minigraph 重新生成。执行 `config load_minigraph`，`config main.py` 中该命令的文档字符串是 Reconfigure based on minigraph，它会停止相关服务、按命名空间从 minigraph 生成配置再写库；若带 `--override-config` 一类选项还会先做 golden config 的校验与依赖检查，选项行为需对照实际版本核验。这条路径适合机型或拓扑变更后的重新落地，但会中断业务，须在维护窗口执行（原理见 06-13）。

第四步，手工渲染并写库。执行 `sonic-cfggen -m /etc/sonic/minigraph.xml -k <hwsku> -p <port_config.ini> --print-data > /tmp/config_db.json`，先用 `-m` 指定拓扑、`-k` 指定 HwSKU、`-p` 指定端口文件，把渲染结果落到临时文件；核对无误后再执行 `sonic-cfggen -j /tmp/config_db.json --write-to-db` 写入配置库。`-p` 与 `-m` 或 `-k` 配套使用是脚本注释中写明的约束，`<hwsku>` 与 `<port_config.ini>` 的具体取值需对照现场机型目录核验。

第五步，验证输出。用 `sonic-cfggen -d -v "DEVICE_METADATA.localhost.hostname"` 只读打印某个变量，确认目标字段已进入配置库；用 `sonic-cfggen -d --print-data | head` 查看配置库导出的前几行；再用 `show interfaces status` 观察端口是否按配置呈现管理态。若字段为空，说明第二到第四步没有真正写库，应按第六步的排错顺序定位。

第六步，清理与持久化。删除临时文件 `rm -f /tmp/config_db.json`；若希望把当前运行状态固化，执行 `config save` 导出到 `/etc/sonic/config_db.json`（其内部是 `sonic-cfggen -d --print-data > 文件`），这样下次 `config load` 可复现；验证结束后用只读命令复核即可，无需清理配置库本身。要特别区分：`config save` 导出的是配置库快照，不是 ASIC 状态，不能作为「硬件已编程」的证据（原理见 06-01）。

### 4. 验证方法与预期结果

```bash
sonic-cfggen -m /etc/sonic/minigraph.xml -k sample-hwsku -p /usr/share/sonic/hwsku/port_config.ini --print-data > /tmp/config_db.json
# 验证输出见下方 text 与 json 块
python -m json.tool /tmp/config_db.json > /dev/null && echo JSON_OK
# 清理：核对后删除临时文件

```

第二组是配置库落地与导出。执行并观察提示。

```bash
# 前置检查：确认 JSON 合法且已备份当前配置
cp /etc/sonic/config_db.json /etc/sonic/config_db.json.bak
# 执行：把 JSON 写进配置库
config load -y /etc/sonic/config_db.json
# 验证：只读查询配置库变量与导出前几行
sonic-cfggen -d -v "DEVICE_METADATA.localhost.hostname"
sonic-cfggen -d --print-data | head -n 5
# 清理与持久化：导出当前配置库快照
config save -y
rm -f /etc/sonic/config_db.json.bak
```

```text
示例输出，具体格式需对照实际版本核验（下列取值仅为格式示意）
Loading config from '/etc/sonic/config_db.json'...
sonic
{
    "DEVICE_METADATA": {
        "localhost": {
            "hostname": "sonic",
```

逐行判读如下。第一行是 `config load` 的提示，表明命令读取了指定文件；`config main.py` 中 `load()` 的真实动作是拼出 `sonic-cfggen -j 文件 --write-to-db` 并执行，因此这条提示只说明「开始加载」，并不代表所有表项已写入，更不能代表 ASIC 已编程。第二行 `sonic` 是 `sonic-cfggen -d -v "DEVICE_METADATA.localhost.hostname"` 的返回值，`-d` 表示从配置库读取、`-v` 打印变量值，能取到值说明该字段确实落进了 `CONFIG_DB`；若返回空行，往往是文件未写库、字段名拼写不符或查询的库与写入的命名空间不一致，需按 `CONFIG_DB`、`APPL_DB`、`ASIC_DB` 顺序逐段核对（原理见 06-01 ｜ 排障见 08-03）。第三到第六行是 `sonic-cfggen -d --print-data | head -n 5` 的截断输出，能看到 `DEVICE_METADATA` 与 `localhost` 键已经开始出现，说明导出链路正常；`--print-data` 的选项行为可在 `src/sonic-config-engine/sonic-cfggen` 的 `argparse` 段核实。需要强调两点：一是 `config save` 内部执行的是 `sonic-cfggen -d --print-data > /etc/sonic/config_db.json`，它导出的是配置库快照，不是运行状态，也不是芯片状态；二是 `config load` 之后若 `show interfaces status` 长时间没有反映，应检查各 `*mgrd` 是否把表项翻译成 `APPL_DB` 意图、`orchagent` 是否消费并写入 `ASIC_DB`，而不是反复执行 `config load`（原理见 06-03 ｜ 06-04）。示例中的提示文字与输出格式需对照实际版本核验（参数见 04-05）。

三种落地方式的差异可归纳为一张对照表，表中命令与选项需对照实际版本核验，单元格只写语义化简述。

| 落地方式 | 输入来源 | 内部动作 | 适用场景 | 风险提示 |
|---|---|---|---|---|
| config load | config_db.json | sonic-cfggen -j 写库 | 已有配置快照需恢复 | 覆盖现有配置 |
| config load_minigraph | minigraph 与端口文件 | 停服务后重新生成写库 | 机型或拓扑变更 | 中断业务 |
| 手工 sonic-cfggen | minigraph 与端口文件 | 先 print-data 再 -j 写库 | 需要先审渲染结果 | 选项需核验 |
| config save | 当前配置库 | sonic-cfggen -d 导出 | 备份与持久化 | 非芯片状态 |

第一种 `config load` 最常用，适合把已知正确的配置快照恢复进来，但会覆盖当前配置，生产环境必须先备份。第二种 `config load_minigraph` 会按 `config main.py` 的逻辑先停止相关服务再重新生成，适合整机拓扑或 HWSKU 变化后的重新落地，必须在维护窗口执行；其 `--override-config` 一类选项会触发 golden config 校验，具体名称与行为需对照实际版本核验。第三种手工方式把渲染与写库拆成两步，优点是可以在写库前审 `--print-data` 的结果，适合排障与教学，缺点是 `-m`、`-k`、`-p` 的组合必须正确，脚本注释明确 `-p` 要与 `-m` 或 `-k` 配套。第四种 `config save` 是反向导出，用于备份与持久化，务必记住它导出的是配置库内容而非 ASIC 状态（排障见 08-03 ｜ 上线清单见 08-06）。

### 5. 常见失败与排错

落地环节的失败可以按「渲染、写库、生效、事实边界」四层定位，下表按「现象 → 可能原因 → 验证命令 → 修复要点」列出，命令名与路径需对照实际版本核验。

| 现象 | 可能原因 | 验证命令 | 修复要点 |
|---|---|---|---|
| --print-data 输出为空 | minigraph 或 HWSKU 不匹配 | ls 与 -v 变量 | 核对 device 目录 |
| JSON 校验失败 | 手工编辑破坏格式 | python -m json.tool | 从配置库重新导出 |
| config load 报文件不存在 | 路径或文件名不符 | ls /etc/sonic | 核对默认路径 |
| 写库后 -v 取值为空 | 未真正写库或字段错 | sonic-cfggen -d -v | 重做 -j 写库 |
| 端口状态无变化 | 流水线尚未推进 | 逐段查 APPL_DB 与 ASIC_DB | 按库核对 |
| 多 ASIC 报文件数不符 | 命名空间文件不齐 | 检查 config_db*.json | 补齐各 ASIC 文件 |
| config save 导出为空 | 配置库无表项 | sonic-cfggen -d --print-data | 先完成落地 |
| 引用了不存在的字段 | 凭印象补表名 | 对照 config_db 样例 | 标注需核验 |

第一类失败在渲染层。`--print-data` 输出为空或报解析错，通常是 `-m` 指向的 `minigraph.xml` 与 `-k` 指定的 HwSKU、`-p` 指定的端口文件不匹配，或机型目录根本没有相应文件。这里要回到 `src/sonic-config-engine/minigraph.py`、`portconfig.py` 与 `device/<vendor>/<hwsku>/` 核对，而不是改字段名硬凑。`minigraph.py` 的 `parse_device()`、`parse_dpg()`、`parse_cpg()` 与 `portconfig.py` 的 `get_port_config()`、`parse_port_config_file()` 是解析主入口，函数名后缀与签名需对照实际版本核验（字段见 05-09 ｜ 模块见 07-10）。

第二类失败在写库层。`config load` 报文件不存在，多半是默认路径 `/etc/sonic/config_db.json` 与现场实际路径不一致，或多 ASIC 场景下只给了一个文件而系统期望多个。本快照 `config main.py` 的 `save()` 与 `load()` 都按 `num_cfg_file` 计算期望文件数量，单 ASIC 为一个、多 ASIC 为宿主加各命名空间多个，文件数量不匹配会直接提示并 return；具体数量与命名需对照实际版本核验。若 JSON 校验失败，说明文件被手工编辑破坏，最稳妥的修复是从配置库重新 `config save` 导出，而不是逐字段猜测修复。

第三类失败在生效层，也是最容易写反的一层。`config load` 返回成功且 `-v` 能取到值，只说明配置库有表项；若 `show interfaces status` 长时间没有按配置呈现，必须按 `CONFIG_DB`、`APPL_DB`、`ASIC_DB`、`STATE_DB` 顺序核对，并确认 `cfgmgr/` 下各 `*mgrd` 已订阅、`orchagent/` 已消费、`syncd/` 已编程。任何把「写库成功」写成「硬件已下发」的表述都是错误的（原理见 06-01 ｜ 06-03 ｜ 06-04 ｜ 06-05）。收敛时间、配置下发时延等一切数字需在目标机型实测，本篇不给绝对值。

第四类是事实边界陷阱。Redis 库编号须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 与运行时 `database_config.json` 核验，不得写死；CONFIG_DB 表名与字段只能引用本快照可核实的文件，例如 `device/tencent/x86_64-tencent_tcs8400-r0/config_db.TCS8400-24CC8CD.json` 中的 `DEVICE_METADATA`、`PORT`，其余写「需对照实际版本核验」并给出 `src/sonic-config-engine/`、`cfgmgr/` 等目录。YANG 模型与 translib 转换在 `sonic-mgmt-common-master/models/yang/`、`translib/`，它们最终同样落到 `CONFIG_DB`，但键名与转换规则需对照实际版本核验（原理见 06-14 ｜ 模块见 07-07）。FRR 协议源码、Linux 内核、厂商 SAI 实现与 `sonic-swss-common` 不在本快照，涉及时写「不在本快照，需对照实际版本核验」；`warmrestart/`、多 ASIC 与 chassis 能力受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持（模块见 07-04 ｜ 原理见 06-10 ｜ 06-11）。

### 6. 小结

本篇把配置落地讲成了一条可核对的链路：`minigraph.xml` 与端口文件经 `src/sonic-config-engine/` 的 `minigraph.py`、`portconfig.py`、`sonic-cfggen` 渲染为 `config_db.json`，再由 `config load` 或 `-j ... --write-to-db` 写进 `CONFIG_DB`，继而经各 `*mgrd`、`orchagent`、`syncd` 异步翻译成 ASIC 状态；反向的 `config save` 用 `-d --print-data` 把配置库导出为快照。图 03-02-01 与两张表把输入输出、三条落地路径和失败面固定下来，核心结论仍是那句：写库成功不等于硬件已下发，状态要按库逐段核对。

需要重申的事实纪律：默认路径 `/etc/sonic/config_db.json` 与 `/usr/local/bin/sonic-cfggen` 可在 `sonic-utilities-master/config/main.py` 核实，`DEVICE_METADATA`、`PORT` 等表可在腾讯机型 `config_db.json` 核实，`sonic-cfggen` 的选项可在其 `argparse` 段核实；其余表名、字段、命令选项与函数签名一律写「需对照实际版本核验」并给出可定位目录。Redis 库编号来自运行时配置、须对照 `SonicDBConfig` 核验；CLI 只读写各库、不编程 ASIC；性能与容量数字需在目标机型实测。本篇涉及的完整参数与命令见 04-02、04-03、04-05（字段见 05-02 ｜ 参数见 04-02 ｜ 原理见 06-03 ｜ 模块见 07-05）。

下一篇 03-03 将在这份落地配置之上做端口、VLAN、IP 与 BGP 的基础配置实战，并把下发链路回指 06-06、06-07；管理面与 telemetry、gNMI 接入见 03-04，升级与配置持久化见 03-05，多设备与多 ASIC 见 03-06。跨册引用请始终使用（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）的写法，`xx` 替换为具体篇号。版本基准始终为「上游 master 快照（2026-11 抓取）」，不写绝对版本号与 Redis DB 编号。

## 03-03 端口、VLAN、IP 与 BGP 基础配置实战

### 1. 目标与拓扑

本篇把前两篇的准备工作落到一次可复现的配置闭环上。目标是在一台已经启动、容器齐备的 SONiC 设备上，依次完成四类最基础也最常用的业务配置：把物理端口划入二层 VLAN、为 VLAN 创建三层交换虚拟接口（SVI）并配置 IP 地址、与对端建立 eBGP 邻居并确认会话进入 Established 且路由可达。之所以把这四类配置放在一篇里串联，是因为它们恰好覆盖 SONiC 配置流水线的四个典型落点——端口速率与 VLAN 成员由 `sonic-swss/sonic-swss-master/cfgmgr/` 下的 `portmgrd.cpp`、`vlanmgrd.cpp` 承接，SVI 的 IP 由 `intfmgrd.cpp` 承接，BGP 则由 `sonic-buildimage-master/dockers/docker-fpm-frr/` 内的路由进程承接并经 `sonic-swss-master/fpmsyncd/` 回写 `APPL_DB`。读者如果能把这条链路上每一段的「配置已写入」和「硬件已下发」区分开，就掌握了 03 册乃至整个 SONiC 运维的核心方法论（原理见 06-06 ｜ 原理见 06-07 ｜ 模块见 07-06）。

拓扑上推荐两台设备背靠背直连：DUT-A 的 Ethernet1 与 DUT-B 的 Ethernet1 用一对光纤或虚拟链路相连，两端都把该端口加入 Vlan10；DUT-A 的 SVI 配置为 10.0.0.1/31，DUT-B 配置为 10.0.0.0/31；DUT-A 使用 AS 65001，DUT-B 使用 AS 65002，双方互指对端 IP 作为 eBGP 邻居。若只有一台虚拟交换机（vs）可用，也可在同一台设备上创建两个 VLAN 并分别配 IP 来模拟二层与三层，但 BGP 邻居仍需两台逻辑设备才能建连，因此两台 vs 实例是最小完整拓扑。端口名一律使用 SONiC 内部名 `Ethernet1` 而非面板别名 `Eth200GE0/1`，除非设备处于 alias 命名模式；命名模式由 `config_db.json` 与运行时配置决定，需对照实际版本核验（参数见 04-02 ）。需要强调的是，本文所有示例地址、AS 号与 VLAN ID 都是便于复现的规划值，不代表任何真实网络，实际取值需对照实际版本核验并按本网地址规划替换。

### 2. 前置条件与环境

在动手配置之前，必须先确认设备处于「可配置且可观测」的状态，否则一旦配置不生效，根因会混杂在启动故障里而无法定位。第一项前置是镜像与平台已正确落地：设备应已完成 03-01 的虚拟交换机启动与 03-02 的 `config_db.json` 初始化，`show version` 能返回 Platform、HwSKU 与 ASIC 类型。ASIC 取 `vs` 表示虚拟交换机，此时转发由软件模拟，一切速率与时延数字都需在目标机型实测、不得外推到真实硬件（参数见 04-01 ｜ 参数见 04-02）。第二项前置是关键容器处于运行态：`docker-database`、`docker-orchagent`、`docker-fpm-frr`、`docker-teamd` 等应正常，可用 `show feature status` 或 `docker ps` 检查；FRR / FRRouting 协议源码不在本快照，容器内集成方式需对照实际版本核验（模块见 07-02 ｜ 模块见 07-08）。

第三项前置是待配置端口的物理与链路状态。VLAN 成员与 SVI 都以端口可操作为前提，若端口因速率分组、线缆或拆线（breakout）配置不当而处于 `down`，后续 IP 与 BGP 验证就失去意义。应先用 `show interfaces status` 确认目标端口，必要时对照 `device/<vendor>/<hwsku>/` 下的端口配置文件（表名与字段需对照实际版本核验）。第四项前置是命名模式：SONiC 支持以内部名或面板别名两种模式显示与输入接口，命令里写 `Ethernet1` 还是 `Eth200GE0/1` 取决于当前命名模式，写错会直接报接口不存在；模式由配置决定，需对照实际版本核验（参数见 04-05）。第五项前置是配置持久化与备份：改动前先执行一次 `config save` 把当前运行配置落盘，并另存一份 `config_db.json` 副本，以便出错时回退，持久化与回滚机制见 03-05。最后，多数 `config` 写操作需要提权或属于特定用户组，权限不足会在执行阶段才暴露，务必在正式窗口前用一次无害的只读命令确认账号可用。

把上述前置做成一组前置检查命令，按「只读、无副作用」原则逐条执行。

```bash
show version
show feature status
show interfaces status Ethernet1
```

逐行判读如下。第一段 `show version` 里，`Software Version` 是构建产物决定的版本标识，本套资料统一以「上游 master 快照（2026-11 抓取）」为基准，示例中的 `SONiC.HEAD.000000-00000000` 只是格式示意、不得当作真实版本号引用；`Platform` 与 `HwSKU` 共同指向 `device/<vendor>/<hwsku>/` 机型目录，是判断端口配置是否加载正确的锚点；`ASIC` 为 `vs` 表明这是虚拟交换机，性能类结论需在目标机型实测；`Uptime` 若与预期启动时间不符，说明连到的并非目标实例。第二段 `show feature status` 中，`database`、`swss`、`bgp`、`teamd` 的 State 均为 `running` 且 AutoStart 为 `enabled`，是容器齐备的正常特征；若 `bgp` 为 `stopped` 或 `enabled` 与 `running` 不一致，源自 `dockers/` 的编排配置（参数见 04-07 ｜ 原理见 06-13），需先修复再继续。第三段 `show interfaces status Ethernet1` 中，`Admin` 为 `down` 表示管理上未启用，`Oper` 为 `down` 表示链路未起；这是待配置端口的常见初始态，执行 VLAN 成员与 IP 配置前应先把端口管理状态置 up，或确认对端已连线，否则后续验证会出现「配置写入了但链路不通」的假故障。三段输出共同构成「系统—容器—端口」三级前置快照，缺任何一级都不宜开始配置（排障见 08-03）。

为便于逐项核对，把前置条件、验证命令与失败处置归纳成下表；表中命令名与状态取值需对照实际版本核验。

| 前置项 | 验证命令 | 正常特征 | 失败处置 |
|---|---|---|---|
| 镜像与机型 | `show version` | Platform/HwSKU 与本机型一致 | 回到 03-01、03-02 检查启动与配置落地 |
| 关键容器 | `show feature status` | database/swss/bgp 均为 running | 查 `dockers/` 编排与容器日志，见 06-13 |
| 端口状态 | `show interfaces status` | 目标端口 Admin 为 up | 先启用端口或检查链路，见 08-03 |
| 命名模式 | 接口的别名/内部名 | 命令中的接口名可被识别 | 对照配置确认命名模式，见 04-05 |
| 配置备份 | `config save` 与另存副本 | 回退文件存在且可读 | 先备份再改，回滚见 03-05 |
| 账号权限 | 任一只读 `show` 命令 | 可正常返回 | 提权或加入相应用户组后再操作 |

### 3. 分步操作

配置按「前置检查 → 执行 → 验证输出 → 清理」的闭环推进，每一步都不把内容推给下一步，而是就地确认结果。第一步是端口与 VLAN：先用 `show vlan brief` 确认 Vlan10 尚不存在，避免重复添加；再执行 `config vlan add 10` 创建二层 VLAN，用 `config vlan member add 10 Ethernet1` 把端口加入为 untagged 成员；如需 tagged，则加对应的 tagging 选项（选项名需对照实际版本核验，完整命令见 04-05）。创建后再次 `show vlan brief` 核对 VLAN 与成员是否写入 `CONFIG_DB` 的 `VLAN`、`VLAN_MEMBER` 表（表名与字段需对照实际版本核验，字段见 05-02）。若端口此前为 `down`，还应先把端口管理状态置 up。清理用 `config vlan member del 10 Ethernet1` 与 `config vlan del 10`，删除成员先于删除 VLAN，顺序不可颠倒。

第二步是 SVI 与 IP：先用 `show ip interfaces` 确认 10.0.0.1 未被占用、避免地址冲突；再执行 `config interface ip add Vlan10 10.0.0.1/31` 给 SVI 配地址。命令中的掩码必须写成带斜杠的前缀形式，缺少掩码会被 CLI 直接拒绝（该校验逻辑在 `sonic-utilities/sonic-utilities-master/config/main.py`，命令名与选项需对照实际版本核验）。地址写入 `CONFIG_DB` 的 `VLAN_INTERFACE` 表后，由 `cfgmgr/intfmgrd.cpp` 翻译、经 `orchagent/intfsorch.cpp` 生成对象，最终落到 ASIC；因此配置返回只代表意图已进库。验证用 `show ip interfaces` 看地址是否出现在 Vlan10 上，并配合按库核对。清理用 `config interface ip del Vlan10 10.0.0.1/31`。

第三步是 eBGP：BGP 相关命令由 `config/main.py` 的 `bgp` 命令组与 `config/bgp_cli.py` 提供的设备全局配置扩展共同构成，本快照可核验到 `config bgp ...` 命令组以及 `config bgp shutdown all` 等子命令，但建立邻居的逐条命令名、参数顺序与 FRR 集成细节需在 `dockers/docker-fpm-frr/` 与实际版本核验后确定，本文不臆造完整语法（完整命令见 04-05 ｜ 模块见 07-08）。可行的最小闭环是：先在 DUT-A 与 DUT-B 上分别完成 ASN 与邻居地址的配置，执行后用 `show ip bgp summary` 观察会话状态；若能提供 `sonic-db-cli` 访问，还可直接查询 `CONFIG_DB` 中 BGP 相关表项确认配置已落库（表名与字段需对照实际版本核验）。以下代码块给出前两步的可执行闭环，命令中的接口名、VLAN ID 与地址需按本网规划替换。

```bash
# --- 第一步：端口与 VLAN（前置检查 → 执行 → 验证 → 清理）---
show vlan brief                              # 前置：确认 Vlan10 不存在
sudo config interface startup Ethernet1      # 端口管理状态置 up
sudo config vlan add 10                      # 执行：创建 Vlan10
sudo config vlan member add 10 Ethernet1     # 执行：加入 untagged 成员
show vlan brief                              # 验证：核对 VLAN 与成员

# --- 第二步：SVI 与 IP ---
show ip interfaces                           # 前置：确认地址未冲突
sudo config interface ip add Vlan10 10.0.0.1/31
show ip interfaces                           # 验证：确认地址已出现

# --- 清理（按相反顺序）---
sudo config interface ip del Vlan10 10.0.0.1/31
sudo config vlan member del 10 Ethernet1
sudo config vlan del 10
```

上面的闭环有三个容易被忽略的要点。其一，`config interface startup Ethernet1` 属于第一步的前置动作，若跳过它，端口 Admin 保持 `down`，即便 VLAN 与 IP 都写入正确，`show interfaces status` 仍显示链路未起，验证会失败。其二，`show vlan brief` 在前置与验证阶段各出现一次，形成对照：前置时 Vlan10 不存在、验证时存在且带 Ethernet1 成员，这种「前后对照」是判断配置真正生效的最小证据，比单次输出更可靠。其三，清理顺序必须与创建顺序相反——先删 IP、再删 VLAN 成员、最后删 VLAN，否则删除仍被成员引用的 VLAN 会失败。整段命令只触及 `CONFIG_DB` 的读写，不直接编程 ASIC，真正下发由后续流水线完成（原理见 06-01 ｜ 原理见 06-06）。

### 4. 验证方法与预期结果

验证要分层进行：CLI 层看 `show` 输出、配置库层看表项、期望与对象库层看流水线是否走通，三层结论一致才算配置真正生效。第一层用 `show vlan brief` 检查二层配置，第二层用 `show ip interfaces` 检查三层地址，第三层用 `show ip bgp summary` 检查控制面协议会话。下面给出 `show vlan brief` 的实例与判读。

```bash
show vlan brief
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
+-----------+-----------------+-----------------+---------------------------+
| VLAN ID   | IP Address      | Ports           | Ports (untagged)          |
+-----------+-----------------+-----------------+---------------------------+
| 10        | 10.0.0.1/31     |                 | Ethernet1                 |
+-----------+-----------------+-----------------+---------------------------+
Total number of VLANs: 1
```

逐行判读如下。列头 `VLAN ID`、`IP Address`、`Ports`、`Ports (untagged)` 表明该命令把 `VLAN`、`VLAN_INTERFACE`、`VLAN_MEMBER` 三张表合并展示，这一点可从 `sonic-utilities/sonic-utilities-master/show/vlan.py` 的 `brief()` 函数核实：它分别 `get_table('VLAN')`、`get_table('VLAN_INTERFACE')`、`get_table('VLAN_MEMBER')` 后拼装行，列名与顺序随版本变化、需对照实际版本核验。数据行中 `VLAN ID` 为 10，与 `config vlan add 10` 对应；`IP Address` 为 10.0.0.1/31，说明第二步的 SVI 地址已写入 `VLAN_INTERFACE` 并能在 CLI 层回显；`Ports (untagged)` 出现 `Ethernet1`，说明 `config vlan member add 10 Ethernet1` 已写入 `VLAN_MEMBER`，且端口以 untagged 方式加入；`Ports`（tagged 列）为空是预期结果，因为本次未加 tagged 选项。末行 `Total number of VLANs: 1` 应与创建数量一致，若显示 0 或缺失，说明前置检查阶段发现的问题未解决。特别要提醒：`show vlan brief` 读取的是 `CONFIG_DB`，它只能证明「配置已写入」，不能证明 ASIC 已建立 VLAN 与成员关系；后者要按库查 `APPL_DB`、`ASIC_DB` 与 `STATE_DB`，这正是下一节排错的核心（字段见 05-02 ｜ 原理见 06-06 ｜ 排障见 08-03）。

第二层 `show ip interfaces` 在前面前置检查中已出现，此处关注验证态：应能在 Vlan10 行看到 10.0.0.1/31，管理状态与操作状态符合预期；该命令底层调用 `ipintutil`，由 `sonic-utilities-master/show/main.py` 中 `ip` 命令组的 `interfaces` 实现，命令形式为 `show ip interfaces`（复数），大纲中「show ip interface」为简写，实际命令名需对照实际版本核验。第三层 `show ip bgp summary` 用来确认 BGP 会话，判读重点如下面的实例所示。

```bash
show ip bgp summary
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意，不代表任何具体版本）
IPv4 Unicast Summary:
BGP router identifier 10.0.0.1, local AS number 65001
Neighbor    V    AS    MsgRcvd  MsgSent  Up/Down  State/PfxRcd
10.0.0.0    4    65002 28       30       00:05:11 1
Total number of neighbors 1
```

逐行判读如下。首行 `IPv4 Unicast Summary` 表明这是 IPv4 单播地址族的汇总，具体输出格式随 FRR 集成方式变化、需对照实际版本核验。第二行给出本端 router identifier 与本地 AS，`10.0.0.1` 与规划的 DUT-A SVI 地址一致、`65001` 与规划 AS 一致，若取值不符通常是 BGP 全局配置未生效。第三行为列头，`V` 是协议版本、`AS` 是对端自治域、`MsgRcvd` 与 `MsgSent` 是收发报文计数、`Up/Down` 是会话时长、`State/PfxRcd` 是会话状态或收到的前缀数。第四行是对端 `10.0.0.0` 的实测值：`AS` 为 `65002` 与规划一致，`MsgRcvd` 与 `MsgSent` 均为正数且持续增长是会话活跃的正常特征，`Up/Down` 非零说明会话已建立过，`State/PfxRcd` 为 `1` 表示 Established 且收到一条前缀——不同版本可能显示 `Established` 文字而非数字，需对照实际版本核验。末行 `Total number of neighbors 1` 应与配置邻居数一致。最关键的判读纪律是：`State/PfxRcd` 正常只说明协议会话建立，并不等于路由已写进 `APPL_DB`、更不等于已下发 ASIC；按 SONiC 异步流水线，路由还要经 `fpmsyncd.cpp` 同步、`orchagent` 消费、`syncd` 编程，因此必须把 `show ip bgp summary` 与按库核对分开判读（原理见 06-07 ｜ 排障见 08-04）。

为把三层验证的关系固定下来，把验证目标、命令、证据库与「能证明什么」归纳成下表；命令名、表名与状态取值需对照实际版本核验。

| 层次 | 验证命令 | 主要证据来源 | 能证明 | 不能证明 |
|---|---|---|---|---|
| 二层 VLAN | `show vlan brief` | `CONFIG_DB` 的 VLAN 表 | VLAN 与成员已写入配置库 | ASIC 已建 VLAN 对象 |
| 三层 SVI | `show ip interfaces` | `CONFIG_DB` 与运行时 | 地址已配置 | 路由已进转发表 |
| 控制面 BGP | `show ip bgp summary` | FRR 协议进程 | 会话建立与前缀收发 | 路由已下发 ASIC |
| 下发链路 | `sonic-db-cli` 查库 | APPL_DB/ASIC_DB/STATE_DB | 流水线各段状态 | 链路物理质量 |
| 物理链路 | `show interfaces status` | STATE_DB 与端口状态 | Oper/Admin 状态 | 上层协议可达性 |

### 5. 常见失败与排错

排错的总原则是「先分段、再定因」：按图 03-03-01 的顺序，从 `CONFIG_DB` 一路查到 ASIC，看到哪一段断掉，就把根因范围收窄到那一两个进程。第一类是配置未入库：`config` 命令返回成功，但 `show vlan brief` 或 `show ip interfaces` 看不到预期内容。此时先用 `sonic-db-cli CONFIG_DB` 查对应表项，确认是否真的写入；若配置库无表项，问题在 CLI 输入（接口名、命名模式、掩码格式）或校验环节（`sonic-mgmt-common/sonic-mgmt-common-master/cvl/` 的校验，校验见 06-03）；若配置库有而 CLI 不显示，问题在 `show` 读取路径或命名模式显示差异。第二类是期望状态未生成：配置库有表项但 `APPL_DB` 无对应意图，通常是 `cfgmgr/` 的某个 `mgrd` 未运行或订阅失败，应查容器状态与日志（模块见 07-03 ｜ 原理见 06-03）。

第三类是 ASIC 未下发：`APPL_DB` 有意图但转发表无效果，应查 `ASIC_DB` 是否出现对象、`STATE_DB` 是否回写运行时状态；`orchagent` 未消费或 `syncd` 未编程都落在这段（原理见 06-04 ｜ 原理见 06-05）。第四类是物理与链路：端口 `Oper` 长期 `down`、VLAN 成员加不上、对端不可达，多与速率分组、breakout、线缆或对端配置有关，需回到前置检查并重查 `show interfaces status`。第五类是 BGP 专项：`State/PfxRcd` 长期为 `Idle` 或 `Active` 且收发计数为零，先查对端地址可达性与 AS 配置，再查 `CONFIG_DB` 的 BGP 表项；若会话 Established 但学不到路由，重点查路由策略与 `fpmsyncd/` 同步。所有收敛时间、下发时延与吞吐结论都需在目标机型实测，不给绝对值（基准方法见 08-01 ｜ 调优见 08-02）。

按库逐段核对可用以下命令组，执行时把库名与表名替换为实际版本对应值（库编号与表名需对照实际版本核验，参数见 04-04）。

```bash
sonic-db-cli CONFIG_DB keys 'VLAN*'
sonic-db-cli CONFIG_DB hgetall 'VLAN|10'
sonic-db-cli APPL_DB keys 'INTF_TABLE:*'
sonic-db-cli ASIC_DB keys 'ASIC_STATE:SAI_OBJECT_ID*'
sonic-db-cli STATE_DB keys 'PORT_TABLE*'
show interfaces status
show ip bgp summary
```

这组命令构成一条自下而上的证据链。第一条列出 `CONFIG_DB` 中VLAN 相关的键，预期能看到 `VLAN|10`、`VLAN_MEMBER|10|Ethernet1`、`VLAN_INTERFACE|Vlan10|10.0.0.1/31` 一类条目；第二条取 `VLAN|10` 的全部字段，确认 `vlanid` 为 10，字段含义见 05 册（字段见 05-02）。第三条查 `APPL_DB` 的接口表，预期出现 `INTF_TABLE:Vlan10` 一类键，说明 `intfmgrd` 已把配置翻译成期望状态；若缺失，问题定位在 `cfgmgr` 段。第四条查 `ASIC_DB` 的 ASIC 状态对象，预期能看到 SAI 对象条目，说明 `orchagent` 已写入、等待 `syncd` 编程；表前缀随版本变化、需对照实际版本核验。第五条查 `STATE_DB` 的端口表，可对照端口运行时状态。最后两条回到 CLI，用 `show interfaces status` 与 `show ip bgp summary` 做端到端确认。重要的是按「配置库 → 期望库 → 对象库 → 状态库 → CLI」顺序推进，而不是一上来怀疑硬件；这条顺序把 SONiC 的异步流水线变成了可逐段验证的诊断树（排障见 08-03 ｜ 案例见 08-04）。

### 6. 小结

本篇完成了一次覆盖端口、VLAN、SVI IP 与 eBGP 的配置闭环，核心成果不是记住几条 `config` 命令，而是建立了「配置写入 ≠ 硬件下发」的判读方法：先用 `show vlan brief`、`show ip interfaces`、`show ip bgp summary` 在 CLI 层确认，再用 `sonic-db-cli` 沿 `CONFIG_DB → APPL_DB → ASIC_DB → STATE_DB` 逐段核对，最后结合 `show interfaces status` 确认物理链路。图 03-03-01 给出了这条链路与每段落点，`cfgmgr/` 承接 VLAN 与 IP、`orchagent/` 翻译为对象、`syncd/` 经 SAI 编程，BGP 则经 `docker-fpm-frr/` 与 `fpmsyncd/` 进入同一条流水线（原理见 06-06 ｜ 原理见 06-07 ｜ 模块见 07-08）。命令、表名、字段名与状态取值均需对照实际版本核验，性能类结论需在目标机型实测（字段见 05-02 ｜ 参数见 04-02 ｜ 参数见 04-05）。

## 03-04 show / config CLI 与 telemetry、gNMI 接入

### 1. 目标与拓扑

前一篇用 `show`、`config` 与 `sonic-db-cli` 完成了从端口到 BGP 的配置闭环，但没有回答一个更基础的问题：这些命令本身从哪里接入交换机，除了 CLI 还有哪些入口能读写同一份配置与状态。本篇补齐这块，讲清 `sonic-utilities` 的 `show` / `config` CLI 接入、`sonic-buildimage-master/dockers/docker-sonic-telemetry/` 的遥测采集，以及 `dockers/docker-sonic-gnmi/` 承载的 gNMI 管理面，并把三条入口统一到一张接入图上（模块见 07-06 ｜ 模块见 07-07 ｜ 原理见 06-14）。

三条入口协议形态不同，最终都汇聚到 `CONFIG_DB` 与各状态库。`show` / `config` 由 `sonic-utilities/sonic-utilities-master/show/main.py` 与 `config/main.py` 用 click 构建命令树，`show` 经 `swsscommon` 的连接器读各库、`config` 经 `ConfigDBConnector` 写 `CONFIG_DB`（`swsscommon` 本体不在本快照，需对照实际版本核验）；gNMI 请求进入 `sonic-mgmt-common/sonic-mgmt-common-master/translib/` 的转换层，经 `cvl/` 的 YANG 校验后同样落到 `CONFIG_DB`；telemetry 则从 `STATE_DB`、`COUNTERS_DB` 等读取运行时状态与计数器并对外订阅推送。「三条入口、一个配置源」是本篇主线，相关结构字段见 05 册、命令全集见 04 册（字段见 05-03 ｜ 参数见 04-05 ｜ 原理见 06-14 ｜ 模块见 07-07）。

三种入口的语义差异也值得提前厘清。CLI 是面向人的、以设备为中心的接口，命令名与输出格式围绕运维习惯设计，优点是直观、可脚本化，缺点是没有统一的模型校验、不同版本命令名可能变化。gNMI 是面向机器的、以模型为中心的接口，请求路径来自 YANG 模型，Set 操作要经 `cvl/` 校验才能落到 `CONFIG_DB`，因此天然具备结构化与可验证性，适合编排系统批量下发；代价是客户端与模型版本需要对齐。telemetry 则是面向观测的流式接口，它不改写配置，只把状态与计数推送给采集器，与 CLI 的 `show` 形成互补——`show` 是拉取式的即时快照，telemetry 是推送式的持续序列。理解三者的定位差异，才能在排障时选对工具：查单台设备的瞬时状态用 CLI，做跨设备批量配置用 gNMI，做长时间趋势与告警用 telemetry（原理见 06-09 ｜ 原理见 06-14 ｜ 模块见 07-06）。

拓扑延续 03-03 的两台设备，另加一台管理站：管理站通过 SSH 使用 CLI、通过 gNMI 客户端使用 gNMI、通过遥测采集器接收 telemetry 数据流，三者都指向同一台 DUT 的管理口。外部 gNMI 客户端与遥测采集平台不在本快照，其命令名、选项与订阅路径需对照实际版本核验，本文只给接入形态与服务端可核验路径。三条入口与后端流水线见图 03-04-01。

### 2. 前置条件与环境

第一项前置是三类服务的载体齐备。CLI 由 `sonic-utilities-master/show/` 与 `config/` 提供；gNMI 服务端由 `dockers/docker-sonic-gnmi/` 承载，其 `gnmi-native.sh` 负责拼装启动参数、`telemetry_vars.j2` 从配置库渲染变量；telemetry 由 `dockers/docker-sonic-telemetry/` 承载，其 `telemetry.sh` 与 `docker-telemetry-entry.sh` 负责启动，`dialout.sh` 负责拨出模式。这些文件在本快照可核验，具体命令行选项与默认值需对照实际版本核验（模块见 07-02 ｜ 模块见 07-07）。第二项前置是管理面模型链可定位：`sonic-mgmt-common-master/models/yang/` 下有 `openconfig-interfaces.yang`、`openconfig-if-ip.yang` 等模型以及 `sonic/` 目录，`cvl/` 下有 `cvl.go`、`cvl_api.go`、`conf/` 与 `custom_validation/`，`translib/` 下有 `translib.go`、`app_interface.go`、`subscribe.go` 等，`generic_config_updater/` 提供补丁式更新入口；模型路径与键名需对照实际版本核验（模块见 07-07）。

这里补充 CLI 与配置更新链路的关系。`sonic-utilities-master/show/main.py` 与 `config/main.py` 是 click 命令树的两个入口，前者经 `swsscommon` 的连接器读库、后者经 `ConfigDBConnector` 写库；`swsscommon` 的实现在 `sonic-swss-common`，不在本快照，需对照实际版本核验。除逐条 `config` 命令外，`sonic-utilities-master/generic_config_updater/` 提供补丁式更新，其 `main.py`、`patch_sorter.py`、`change_applier.py` 等文件可在本快照核验，适合在大型 `config_db.json` 上做局部字段修改而避免整表覆盖；补丁格式、支持字段与回滚行为需对照实际版本核验（模块见 07-06 ｜ 参数见 04-05）。对运维而言，CLI 与 gNMI 是两条写入路径，GCU 是 CLI 侧的增量写入助手，它们最终都落到 `CONFIG_DB`，因此配置生效的异步特性完全一致。

第三项前置是 gNMI 与 telemetry 的监听配置。服务端脚本通过 `sonic-cfggen -d -t` 渲染 `telemetry_vars.j2` 后读取配置：gNMI 侧从 `CONFIG_DB` 的 `GNMI` 表取 `gnmi`、`certs` 子字段，`telemetry.sh` 侧从 `TELEMETRY` 表取同名字段，证书相关 `x509` 取自 `DEVICE_METADATA`；`GNMI` 未配置时，`telemetry.sh` 有默认端口 8080 的兜底逻辑。脚本支持 `--port`、`--server_crt`、`--server_key`、`--ca_crt`、`--noTLS`、`--insecure`、`--unix_socket`、`--gnmi_vrf`、`-zmq_port` 等参数，是否启用取决于 TLS 与监听模式配置，需对照实际版本核验（参数见 04-05 ｜ 参数见 04-07）。第四项前置是外部客户端与证书：如使用 gNMI 订阅，需要一台装有客户端工具的管理站以及与服务端的信任关系，客户端工具不在本快照，需对照实际版本核验。第五项前置仍是备份与权限，改动前用 `config save` 落盘并另存副本。

把管理面组件与本快照可核验路径归纳成下表，便于逐项核对；容器名、表名与文件名需对照实际版本核验。

| 组件 | 载体 | 职责 | 本快照可核验路径 |
|---|---|---|---|
| show / config CLI | sonic-utilities | `show` 读状态、`config` 写配置 | `show/main.py`、`config/main.py` |
| gNMI 服务端 | docker-sonic-gnmi | gNMI 监听与 dialout | `gnmi-native.sh`、`telemetry_vars.j2` |
| telemetry 服务端 | docker-sonic-telemetry | 订阅推送与拨出 | `telemetry.sh`、`telemetry_vars.j2` |

动手前先做一组只读前置检查，确认服务在运行、监听配置可读。

```bash
sonic-db-cli CONFIG_DB keys 'GNMI*'
sonic-db-cli CONFIG_DB keys 'TELEMETRY*'
```

```text
+-----------------+------------------+-----------+
| Feature         | State            | AutoStart |
+-----------------+------------------+-----------+
| gnmi            | running          | enabled   |
| telemetry       | running          | enabled   |
+-----------------+------------------+-----------+
gnmi            Up 2 hours
telemetry       Up 2 hours
database        Up 3 hours
GNMI|gnmi
TELEMETRY|gnmi
```

逐行判读如下。第一段 `show feature status` 中 `gnmi` 与 `telemetry` 的 State 均为 `running`、AutoStart 为 `enabled`，是两项服务已启用的正常特征；若 State 为 `stopped` 而 AutoStart 为 `enabled`，说明进程反复退出或启动被阻断，应先看容器日志（模块见 07-02 ｜ 原理见 06-13）。第二段 `docker ps` 中对应容器为 `Up 2 hours`，与第一段互相印证；若 `show feature status` 显示运行但容器不在列表里，通常是特性被禁用或镜像缺失，需回到 `dockers/` 与构建产物核查。第三、四段 `sonic-db-cli CONFIG_DB keys` 分别返回 `GNMI|gnmi` 与 `TELEMETRY|gnmi`，说明 gNMI 与 telemetry 各自的监听配置已在配置库落位；这里要注意两者是两张独立的表，gNMI 服务端读 `GNMI` 表、telemetry 服务端读 `TELEMETRY` 表，虽字段名相似但不可混写，表名与字段需对照实际版本核验。若查询返回空，则服务端会走脚本内的默认端口兜底，是否可用取决于版本实现。四段输出共同构成「服务—容器—配置」三级前置快照，缺任何一级都不宜开始接入测试（排障见 08-03）。

### 3. 分步操作

第一组是 CLI 接入闭环。CLI 入口在 `sonic-utilities-master/show/main.py` 与 `config/main.py`，命令树由 click 的 `group` / `command` 装饰器构建，常用只读命令包括 `show version`、`show interfaces status`、`show vlan brief`、`show ip interfaces`、`show ip bgp summary`、`show feature status`、`show processes`、`show logging` 等，写操作用 `config ...`（完整命令见 04-05）。闭环做法是：先 `show logging` 或 `show feature status` 看前置，再执行一条 `config` 写操作，随后用对应的 `show` 回显验证，最后用反向 `config` 清理。CLI 的特点是直接读写 `CONFIG_DB` 与各库，不经过 YANG 校验链，因此速度快但缺少模型层约束（原理见 06-01 ｜ 模块见 07-06）。

第二组是 gNMI 接入闭环。先确认 `GNMI` 表配置，必要时写入监听端口与证书字段；配置片段如下，字段名来自 `telemetry_vars.j2` 与 `gnmi-native.sh` 可核验的取值路径，具体结构需对照实际版本核验。写完重启 gnmi 特性使脚本重新渲染参数，再用管理站的外部客户端发起 Get 读取一个已知路径，确认返回与配置库一致；Set 操作则经 `translib/` 转换与 `cvl/` 校验后写入 `CONFIG_DB`，其返回成功同样不代表 ASIC 已下发（原理见 06-14 ｜ 模块见 07-07）。

```json
{
    "GNMI": {
        "gnmi": {
            "port": "50051",
            "certs": "/etc/sonic/credentials/gnmi"
        },
        "certs": {
            "server_crt": "/etc/sonic/credentials/server.crt",
            "server_key": "/etc/sonic/credentials/server.key"
        }
    }
}
```

```bash
sudo config feature state gnmi enabled      # 前置：确保 gnmi 特性启用
sonic-db-cli CONFIG_DB hgetall 'GNMI|gnmi'  # 验证：确认端口与证书字段
# 以下为外部客户端示例（工具不在本快照，命令与路径需对照实际版本核验）
gnmic -a <DUT管理IP>:50051 --insecure get --path /openconfig-interfaces:interfaces
```

第三组是 telemetry 接入闭环。telemetry 有拨入（dial-in，客户端主动连服务端订阅）与拨出（dial-out，设备主动向采集器推送）两种形态，分别由 `docker-telemetry-entry.sh` 与 `dialout.sh` 相关逻辑承载，路径黑名单在 `/etc/telemetry/paths_blacklist.txt`（需对照实际版本核验）。配置侧读 `TELEMETRY` 表，未配置时 `telemetry.sh` 有默认端口 8080 的兜底。闭环做法是：先确认 `TELEMETRY` 表与采集器地址，再用采集器建立一个对 `COUNTERS_DB` 或接口计数路径的订阅，观察计数器是否随流量增长；读取计数不编程 ASIC，这一点与 CLI 一致（原理见 06-09 ｜ 模块见 07-09）。

```bash
sonic-db-cli CONFIG_DB hgetall 'TELEMETRY|gnmi'   # 前置：确认监听配置
show feature status                                # 确认 telemetry running
# 外部采集器订阅命令不在本快照，需对照实际版本核验；命令行侧可用 show 交叉验证
show interfaces counters
```

### 4. 验证方法与预期结果

验证围绕「三条入口是否指向同一份配置」展开：CLI 侧用 `show` 回显、配置库侧用 `sonic-db-cli` 查表、gNMI 侧用 Get 返回。第二组命令已在前面给出，这里重点给 gNMI Get 的预期输出与判读。

```bash
gnmic -a <DUT管理IP>:50051 --insecure get --path /openconfig-interfaces:interfaces/interface=Ethernet1
```

```text
示例输出，具体格式需对照实际版本核验（外部客户端，取值仅为格式示意）
{
  "source": "<DUT管理IP>:50051",
  "timestamp": 1730000000000000000,
  "results": [
    {
      "path": "/openconfig-interfaces:interfaces/interface=Ethernet1",
      "values": {
        "name": "Ethernet1",
        "oper-status": "DOWN",
        "admin-status": "UP"
      }
    }
  ]
}
```

逐行判读如下。`source` 是 gNMI 服务端地址与端口，应与命令中 `-a` 指定的管理 IP 和 `GNMI` 表端口一致；若连接失败并提示超时，优先查端口监听、管理 VRF 与 TLS 设置。`timestamp` 是纳秒级时间戳，用来判断数据新鲜度，若与采集时刻相差过大，说明订阅通道可能有缓存或断连。`results[0].path` 是请求路径的回显，`openconfig-interfaces` 对应 `sonic-mgmt-common-master/models/yang/openconfig-interfaces.yang`，说明 gNMI 走的是 OpenConfig YANG 模型到 `CONFIG_DB` 的转换，路径与模型名需对照实际版本核验（模块见 07-07）。`values` 中 `name` 为 `Ethernet1` 与路径键一致；`oper-status` 为 `DOWN`、`admin-status` 为 `UP`，是「管理上启用但链路未起」的典型状态，与 03-03 前置检查里端口未接线的情形吻合，需回查 `show interfaces status`，而不是判定 gNMI 故障。最关键的一点：gNMI Get 读到的是模型/状态视图，它证明「管理面通道打通且数据可读」，既不代表配置已写入 `CONFIG_DB` 的某张具体表，也不代表 ASIC 已下发；验证写入要配合 `sonic-db-cli` 查表，验证下发要沿各库逐段核对（字段见 05-03 ｜ 参数见 04-05 ｜ 原理见 06-14 ｜ 模块见 07-07）。

把三条入口的验证目标与证据来源归纳成下表，便于定位和回归；命令名、表名与模型名需对照实际版本核验。

| 入口 | 验证命令 | 证据来源 | 关键判读 |
|---|---|---|---|
| CLI | `show version`、`show feature status` | 各 DB 与容器状态 | 服务运行、回显与配置一致 |
| CLI 写操作 | `config ...` 配 `show ...` | `CONFIG_DB` 表项 | 写入后能在对应 `show` 中回显 |
| gNMI | 外部客户端 Get | YANG 模型与配置库 | 路径有效、返回数据新鲜 |
| gNMI 写操作 | 外部客户端 Set | `translib/` 与 `cvl/` | 校验通过、落库、非即下发 |
| telemetry | 采集器订阅与 `show interfaces counters` | `COUNTERS_DB` | 计数随流量增长 |
| 逐段核对 | `sonic-db-cli` 查库 | APPL_DB/ASIC_DB/STATE_DB | 流水线各段状态一致 |

### 5. 常见失败与排错

三条入口的故障可以按「通道层—校验层—落库层—下发层」四层归类。通道层包括 SSH、gNMI 监听、telemetry 采集链路，症状是连不上或订阅不到数据；校验层主要是 gNMI 的 `translib/` 与 `cvl/`，症状是请求被拒绝并返回校验错误；落库层是 `CONFIG_DB` 写入，症状是请求成功但 `sonic-db-cli` 查不到表项；下发层则是 `cfgmgr/` 之后的流水线，症状是库里有表项但 `show` 或 ASIC 无反映。把症状先归到某一层，再在该层内选命令，可以避免「连不上就改证书、库里没表项就重启整机」这类盲目操作（排障见 08-03）。

第一类是 CLI 侧失败：命令不存在多半是命令名或命令树版本差异（命令全集见 04-05）；写操作报接口不存在常是命名模式不匹配；`show` 无输出可能是对应容器未起或库表为空。第二类是 gNMI 通道失败：客户端连不上时先查 `show feature status` 与容器是否运行，再查 `GNMI` 表的端口与证书字段、管理 VRF 与防火墙；TLS 握手失败通常指向 `server_crt`、`server_key`、`ca_crt` 路径或证书过期，需对照实际版本核验。第三类是 gNMI 数据失败：Get 路径报错多为 YANG 模型路径写错或该路径未实现，`cvl/` 校验失败则是配置数据不符合模型约束，二者都要回到 `models/yang/` 与 `translib/` 核查（模块见 07-07 ｜ 原理见 06-14）。第四类是 telemetry 失败：订阅无数据先查采集器地址与拨出配置，再查订阅路径是否被 `paths_blacklist.txt` 屏蔽；计数不涨时对照 `show interfaces counters` 与 `COUNTERS_DB`，并记住读取计数不编程 ASIC（原理见 06-09）。

所有入口共用的排错纪律是：把「管理面是否通」与「配置是否下发」分开判读。gNMI Set 返回成功、CLI `config` 返回成功，都只代表请求被接受并落到配置环节，后续仍要走 `cfgmgr/` → `APPL_DB` → `orchagent/` → `ASIC_DB` → `syncd/` 的异步流水线；因此排错顺序应是先确认入口通道、再按库逐段核对，最后才怀疑硬件（排障见 08-03 ｜ 案例见 08-04）。收敛与下发时延类结论需在目标机型实测。

按库与按容器核对可用以下命令组，库名、表名与容器名需对照实际版本核验（参数见 04-04 ）。

```bash
show feature status
show logging | grep -i gnmi
docker logs gnmi --tail 100
sonic-db-cli CONFIG_DB hgetall 'GNMI|gnmi'
sonic-db-cli CONFIG_DB hgetall 'TELEMETRY|gnmi'
sonic-db-cli APPL_DB keys 'PORT_TABLE:*'
show interfaces status
```

这组命令按「容器—日志—配置—状态—CLI」由外到内收窄。前两条看服务状态与日志中的 gNMI 相关报错；第三条直接看 `docker logs gnmi` 的末尾输出，是 TLS 与端口问题最直接的证据源；第四、五条确认两张监听表的字段是否符合预期；第六条查 `APPL_DB` 的端口表，验证管理面写入的配置是否已被 `cfgmgr/` 翻译成期望状态；末条回到 CLI 做端到端确认。若前三条异常，问题在管理面通道；若前六条正常而末条异常，问题在下发链路或物理层。这种分层判读把三条入口的排错统一到同一棵决策树上（排障见 08-03）。

### 6. 小结

本篇把三条管理面入口统一到一张图上：`show` / `config` CLI 由 `sonic-utilities/` 提供、直接读写各库；gNMI 由 `dockers/docker-sonic-gnmi/` 承载，经 `translib/` 与 `cvl/` 校验后写入 `CONFIG_DB`；telemetry 由 `dockers/docker-sonic-telemetry/` 承载，主要从 `STATE_DB`、`COUNTERS_DB` 采集推送。三者在 `CONFIG_DB` 汇合后共用同一条异步下发流水线，所以任何入口的「请求成功」都不等于 ASIC 已下发（原理见 06-14 ｜ 模块见 07-06 ｜ 模块见 07-07）。gNMI 服务端读 `GNMI` 表、telemetry 服务端读 `TELEMETRY` 表，这一区别是配置时最容易写错的地方。涉及的结构字段、命令全集、机制与模块分别见 05、04、06、07 册（字段见 05-03 ｜ 参数见 04-05 ｜ 原理见 06-14 ｜ 模块见 07-07）。

03 册至此完成「能启动—能落地—能配置业务—能管理观测—能升级—能多设备运维」的闭环。下一篇 03-05 转向升级、warm reboot 与配置持久化，把本篇和 03-03 写入的配置放到版本变更与状态恢复的场景里检验；跨册引用继续使用（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）的写法，本篇涉及的 CLI 命令写「参数见 04-05」、涉及的管理面机制写「原理见 06-14」、涉及的 YANG 与 CVL 模块写「模块见 07-07」。

## 03-05 升级、warm reboot 与配置持久化

### 1. 目标与拓扑

本篇要完成的是一台已上线 SONiC 白盒交换机的三件运维动作：把运行镜像升级到新版本、在升级或维护窗口里用 warm reboot 尽量缩短转发中断、并确保配置在重启与升级后仍然正确落盘。这三件事在 SONiC 里并不是「一条命令」能概括的，它们分属三个不同的子系统：镜像升级由管理面的 `sonic-installer` 负责，warm reboot 由 `STATE_DB` 的开关与 `orchagent` 的冻结检查协同完成，配置持久化则由 `config save` 经 `sonic-cfggen` 把 `CONFIG_DB` 导出成 `/etc/sonic/config_db.json`。把三者混为一谈，是这一主题最常见的误判来源（参数见 04-05 ｜ 模块见 07-06）。

先明确「升级」在 SONiC 里的确切含义。从 `sonic-utilities-master/sonic_installer/main.py` 可以核实，`sonic-installer` 是一个基于 `click` 的命令组，Upgrade 不是覆盖正在运行的根文件系统，而是把新的 ONIE 安装包通过 bootloader 登记为「下一次启动镜像」，再经重启切换。命令组同时提供 `list`、`set-default`、`set-next-boot`、`install`、`remove`、`cleanup`、`verify-next-image`、`upgrade-docker`、`rollback-docker` 等子命令，并在检测到用下划线调用旧名 `sonic_installer` 时打印弃用警告、建议改用连字符形式。也就是说，升级的落点是 bootloader 里的镜像列表与 Next 指针，而不是一个可以被即时打补丁的活进程（模块见 07-11）。

再明确 warm reboot 的边界。WARM_RESTART 相关的开关和配置分布在两个库：`config/main.py` 里的 `warm_restart` 命令组会把 `enable` 字段写进 `STATE_DB` 的 `WARM_RESTART_ENABLE_TABLE`，把 `bgp_timer`、`neighsyncd_timer` 等写进 `CONFIG_DB` 的 `WARM_RESTART` 表；`upgrade-docker` 的注释更直接写明「warm restart enable/disable config is put in stateDB, not persistent across cold reboot, not saved to config_DB.json file」。这意味着 warm 开关默认不跨冷重启保留，升级完成后必须重新确认。同时 `orchagent` 一侧通过 `RESTARTCHECK` 通知通道与 `orchagent_restart_check` 工具握手，只有收到成功回复才进入冻结状态。整个能力受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持（原理见 06-10 ｜ 字段见 05-09）。

把上述三个子系统的落点与数据流向画在一起，就得到本篇的主拓扑，见图 03-05-01。

:::figure id=03-05-01 | name=升级与 warm reboot 状态恢复链路 | dir=TD

图 03-05-01 用颜色区分语义：amber 是构建产物 ONIE 安装包，teal 是管理面与备份脚本，gray 是 bootloader 这一外部引导依赖，blue 是配置与状态数据库，purple 是 `orchagent` 控制面，green 是 `syncd` 与 SAI 运行时，red 是硬件数据面边界。读图时要抓住两条主线：上半段是「安装包经 `sonic-installer` 登记为 Next 镜像并触发配置备份」，下半段是「重启后 warm 开关经 `orchagent` 冻结检查、`syncd` 状态保留，尽量让 ASIC 转发不中断」。两条主线通过 bootloader 串接，这也解释了为什么升级与 warm reboot 必须在同一变更窗口内一起规划（原理见 06-10 ｜ 模块见 07-02）。

### 2. 前置条件与环境

动手之前，先把验证环境与权限边界确认清楚。所有 `sonic-installer` 命令都要求 root 权限：`main.py` 的 `sonic_installer` 组入口里有 `if os.geteuid() != 0: sys.exit("Root privileges required for this operation")`，普通用户执行会在任何实质动作之前直接退出。因此本篇命令默认在设备 root shell 下运行，示例输出一律注明「示例输出，具体格式需对照实际版本核验」，取值不得当作真实版本引用。

第二是镜像与 bootloader 的匹配。`sonic-installer install` 会先解析 URL：以 `http://` 或 `https://` 开头时走 `urlopen` 与 `urlretrieve` 下载到 bootloader 的默认路径，否则按本地相对路径处理；随后用 `bootloader.get_binary_image_version()` 校验文件是否为合法 SONiC 镜像，非法文件会在「Image file does not exist or is not a valid SONiC image file」处中止。`get_bootloader()` 从 `sonic_installer/bootloader/` 目录选择具体实现，该目录下可核实到 `grub.py`、`aboot.py`、`uboot.py`、`onie.py`、`bmc_uboot.py` 等，分别对应不同的引导栈；不同平台使用哪一种由构建与机型决定，需对照实际版本核验（模块见 07-11）。

第三是安装前置校验的顺序，它决定了失败时该看哪一行。`install` 在真正 `bootloader.install_image()` 之前依次检查：磁盘空间 `check_image_install_free_disk_space()`、安全启动类型一致性 `verify_secureboot_image()`、平台 ASIC 类型一致性 `verify_image_platform()`，若支持安全升级还会执行证书登记与签名验证 `enroll_image_secure_boot_keys()` 和 `verify_image_sign()`。镜像与当前平台 ASIC 类型不一致时，会提示用 `--skip-platform-check` 跳过——这是一个危险开关，跨越它之前必须确认目标镜像的 platform 与本机一致。内存不足时安装流程会经 `SWAPAllocator` 在 `/host/swapfile` 上临时建立 swap，磁盘空间低于阈值则报「Insufficient free disk space to install the image」。这些检查项与返回信息属于日志与返回码手册的范畴（参数见 04-08 ｜ 参数见 04-01）。

第四是配置持久化的常识。`config save` 默认把 `CONFIG_DB` 导出到 `DEFAULT_CONFIG_DB_FILE`，其实现通过 `sonic-cfggen -d --print-data` 生成 JSON 并排序落盘；`config load` 则是导入，并明确提示「loaded setting will be lost after system reboot. To preserve setting, run `config save`」。在多 ASIC 平台上，`save` 与 `load` 会为每个命名空间额外生成 `config_db0.json`、`config_db1.json` 等文件。升级流程本身也会调用 `config-setup backup` 备份当前配置，该脚本位于 `files/image_config/config-setup/config-setup`，usage 明确给出 `backup | boot | factory` 三种模式。因此「升级会不会丢配置」的正确答案是：升级流程会做备份，但日常改动仍需自己 `config save`（参数见 04-02 ｜ 模块见 07-11）。

第五是 warm reboot 的开关状态。前置检查要能读到三个事实：WARM_RESTART_ENABLE_TABLE 里对应模块的 `enable` 是否为 true、`CONFIG_DB` 的 WARM_RESTART 表里各 timer 取值、`orchagent` 是否处于可冻结的干净状态。前两者由 `show warm_restart config` 与 `show warm_restart state` 提供，第三者由 `orchagent_restart_check` 探测。把这些前置条件整理成一张清单，便于升级窗口前逐项打勾。

| 检查项 | 手段 | 期望特征 | 不满足的后果 |
|---|---|---|---|
| root 权限 | `id -u` | 返回 0 | 命令组入口直接退出 |
| 镜像合法 | `sonic-installer binary-version` | 打印版本字符串 | 安装中止并报非法镜像 |
| 平台一致 | `sonic-installer install` 自检 | 无类型告警 | 需 `--skip-platform-check`，风险自负 |
| 磁盘空间 | `check_image_install_free_disk_space` | 通过 | 报空间不足并中止 |
| 配置已备份 | `config save` 或安装脚本 backup | 文件存在且排序 | 升级后配置可能回退 |
| warm 开关 | `show warm_restart config` | enable 为 true | 退化为冷重启，中断变长 |

这张清单覆盖权限、镜像、平台、空间、配置、warm 六个维度，是升级窗口前的最小核验集；表中「需对照实际版本核验」的部分包括具体文件路径与字段取值，命令全集见 04-05。

### 3. 分步操作

下面按「前置检查 → 执行 → 验证输出 → 清理」的闭环，给出一次带 warm 语义的镜像升级与 warm reboot 完整操作。所有命令名与选项均来自 `sonic-utilities-master` 的可核验源码，选项是否在其他版本存在需对照实际版本核验。

**第一步，前置检查。** 先确认当前镜像、Next 镜像与镜像列表，再确认配置已落盘。

```bash
id -u
show version
sonic-installer list
sonic-installer binary-version ./sonic-image.bin
config save -y
```

执行后依次得到：root 用户 id 为 0；`show version` 打印当前软件版本与平台；`sonic-installer list` 列出当前与 Next 镜像；`binary-version` 打印安装包里的版本字符串；`config save -y` 静默导出当前配置。若 `binary-version` 打印「Image file does not exist or is not a valid SONiC image file」，说明安装包损坏或路径错误，不要继续。

**第二步，执行安装。** 用 `install` 子命令安装本地镜像；它会在内部完成下载校验、平台与安全校验、临时 swap、配置备份、环境更新、包迁移和三次 `sync`，最后打印 Done。

```bash
sonic-installer install -y ./sonic-image.bin
```

安装过程中若提示镜像类型与安全启动不一致，需判断是否确实要跨类型安装，再决定是否追加 `-f/--force`（谨慎）；若提示平台 ASIC 类型不一致，应停止并换用匹配镜像，而不是直接跳过平台检查。安装成功后，`install` 会把新镜像设为默认启动镜像。若只想在下次启动临时切到某个已安装镜像而不改默认，可改用 `sonic-installer set-next-boot <image>`；若要永久改默认，用 `sonic-installer set-default <image>`。

**第三步，配置 warm 开关并做冻结检查。** warm reboot 能否生效，取决于开关与 `orchagent` 状态。先看配置与状态，再开启，最后做干净状态探测。

```bash
show warm_restart config
show warm_restart state
config warm_restart enable
config warm_restart bgp_timer 1800
docker exec -i swss orchagent_restart_check -w 2000 -r 5
```

这里 `config warm_restart enable` 默认作用于 `system`，也可带模块名作用于 `bgp`、`swss`、`teamd` 等，模块名是否在 `FEATURE` 表里由命令校验。`enable` 写进 `STATE_DB`，`bgp_timer` 经 `mod_entry` 写进 `CONFIG_DB` 的 `WARM_RESTART` 表 `bgp` 键。`orchagent_restart_check` 的参数 `-w 2000 -r 5` 是超时与重试设置，其源码 `orchagent_restart_check.cpp` 通过向 `RESTARTCHECK` 通道发查询、监听 `RESTARTCHECKREPLY` 通道收回复，成功时打印成功信息并让 `orchagent` 进入冻结状态；未通过则明确拒绝 warm（原理见 06-10 ｜ 模块见 07-03）。

**第四步，触发重启并验证。** 冻结检查成功后执行重启，随后按第 4 节的方法逐项验证。

```bash
reboot
```

**第五步，清理。** 验证通过后，清理旧的、既非当前也非 Next 的镜像，释放磁盘空间；`cleanup` 会跳过当前与 Next 镜像。

```bash
sonic-installer cleanup
```

需要回滚时，若是整机镜像，用 `set-default` 指回旧镜像再重启；若是某个容器镜像的热升级，用 `sonic-installer rollback-docker <container_name>`，其源码对 `swss`、`bgp`、`teamd` 会提示「Cold reboot is required to restore system state after rollback」，即这些容器的回滚必须配合冷重启才能恢复状态。

### 4. 验证方法与预期结果

验证分为「升级是否成功」与「warm 状态是否恢复」两条线。先看镜像线与配置线，最直观的是 `sonic-installer list`。

```bash
sonic-installer list
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
Current: SONiC.HEAD.2026-11-13-a1b2c3d4
Next: SONiC.HEAD.2026-11-13-a1b2c3d4
Available:
SONiC.HEAD.2026-11-01-0e1f2a3b
SONiC.HEAD.2026-11-13-a1b2c3d4
```

逐行判读如下。第一行 `Current` 是 bootloader `get_current_image()` 返回的当前运行镜像，重启后若升级成功，它应指向新版本；若仍停留在旧版本，说明 Next 指针未生效或重启未真正发生。第二行 `Next` 来自 `get_next_image()`，表示下一次启动将加载的镜像；升级完成后 `Current` 与 `Next` 一致是正常特征，若二者长期不一致，需检查是否有一次性的 `set-next-boot` 仍悬而未决。第三行 `Available` 是已安装镜像列表的表头，来自 `get_installed_images()`，它决定 `set-default`、`remove`、`set-next-boot` 的合法参数集合——不在该列表中的镜像名会被拒绝。第四、五行是列表中两个具体镜像标识，命名模式由构建产物决定，本套资料统一按「上游 master 快照（2026-11 抓取）」表述，示例中的版本串只作格式示意，不得当作真实版本号引用，具体取值需对照实际版本核验。把这份输出与升级前对比，就能确认「新镜像是否进入 Available 并成为 Current」。输出块已注明示例输出与版本核验要求（参数见 04-05 ｜ 模块见 07-11）。

再看 warm 状态线。先读配置，再读运行时状态。

```bash
show warm_restart config
show warm_restart state
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
name    enable   timer_name        timer_duration   eoiu_enable
system  true     NULL              NULL             NULL
bgp     true     bgp_timer         1800             false
swss    false    neighsyncd_timer  NULL             NULL
name          restore_count    state
orchagent     1                reconciled
neighsyncd    1                reconciled
bgp           0                reconciled
```

对第二段输出做逐行判读。上半段是 `show warm_restart config`，列头 `name / enable / timer_name / timer_duration / eoiu_enable` 可在 `show/warm_restart.py` 的 `tablelize` 函数中核实；该函数把 `CONFIG_DB` 的 `WARM_RESTART` 表与 `STATE_DB` 的 `WARM_RESTART_ENABLE_TABLE|*` 合并。`system` 行 `enable` 为 true，说明系统级 warm 开关已打开；`bgp` 行 `bgp_timer` 为 1800，与前面 `config warm_restart bgp_timer 1800` 对应，`eoiu_enable` 为 false 是默认行为；`swss` 行 `enable` 为 false，意味着该模块的 warm 未开启，这是需要重点关注的差异——若期望 swss 也 warm，须补执行按模块的 `enable`。下半段是 `show warm_restart state`，列头 `name / restore_count / state`，直接读 `STATE_DB` 的 `WARM_RESTART_TABLE|*`，其中 `state` 为 `reconciled` 是 `upgrade-docker` 源码里 `exp_state = "reconciled"` 所等待的目标状态，表示应用已完成状态协调；`restore_count` 记录恢复次数，重启后取值大于零通常说明 warm 恢复确实发生过。若某应用 `state` 长期不是 `reconciled`，说明 warm 未完成，需按第 5 节排查（字段见 05-09 ｜ 原理见 06-10）。

验证配置持久化时，可对比 `config save` 落盘前后 `/etc/sonic/config_db.json` 的关键表项是否一致，并确认文件存在、内容经排序；导入侧用 `config load` 验证能否恢复。需要强调的是，`config load` 自身提示「loaded setting will be lost after system reboot. To preserve setting, run config save」，所以验证的终点始终是「重启后 `CONFIG_DB` 表项与预期一致」，而不是「load 命令返回成功」（参数见 04-02 ｜ 参数见 04-05）。

### 5. 常见失败与排错

第一类失败是安装前置校验中止。典型现象是 `sonic-installer install` 在真正安装前退出，并打印「Insufficient free disk space」「Image file is of a different platform ASIC type」或安全启动类型不一致提示。根因分别是磁盘空间不足、镜像 platform 与本机不匹配、安全启动类型不同。正确处理是先读提示定位到 `install` 流程的哪一道检查：空间不足就清理旧镜像（用 `cleanup`）或扩容；平台不匹配就换匹配镜像，不要轻易用 `--skip-platform-check` 越过；安全类型不一致要确认镜像来源可信后再决定是否用 `-f`。跳过这些检查虽然能让命令继续，但会把风险推迟到重启之后（参数见 04-08 ｜ 排障见 08-03）。

第二类失败是 warm reboot 没有按预期缩短中断，甚至退化为冷重启。最常见根因是 warm 开关没有跨重启保留——`upgrade-docker` 源码明确说明 enable/disable 配置在 `STATE_DB`、不写入 `config_db.json`、不跨冷重启持久化。因此升级重启后必须重新用 `show warm_restart config` 确认开关，必要时重开。第二常见根因是 `orchagent` 未通过冻结检查：`orchagent_restart_check` 会输出「RESTARTCHECK failed」或超时信息，此时系统不会进入 warm，应转而排查 `orchagent` 是否有未完成的任务，而不是强行 warm。第三类根因是模块级开关遗漏，例如系统级已 enable 但 `swss` 仍为 false，导致部分应用走冷启动路径（原理见 06-10 ｜ 字段见 05-09）。

第三类失败是升级后配置「回退」到旧状态。根因通常是改动只停留在 `CONFIG_DB` 运行时而未 `config save` 落盘，或升级流程的 `config-setup backup` 备份的是升级前快照、之后又执行了 factory 模式覆盖了配置。正确做法是把 `config save` 纳入变更流程的固定步骤，并在升级后对比 `config_db.json` 关键表项；若要恢复出厂，`config-setup factory` 会重建默认配置，须谨慎使用（模块见 07-11）。

第四类失败是容器热升级回滚后状态不一致。`sonic-installer rollback-docker` 源码要求镜像存在两个版本，否则报「Two images required」；对 `swss`、`bgp`、`teamd` 回滚后明确提示需要冷重启恢复系统状态。若忽略该提示，可能出现 `show warm_restart state` 中各应用状态与配置不匹配的现象，处理方式是按提示执行冷重启后重新核验（参数见 04-05 ｜ 排障见 08-04）。

把上述失败归纳成对照表，便于现场按现象快速定位。

| 现象 | 首要证据 | 可能根因 | 处理方向 |
|---|---|---|---|
| 安装提前退出 | 提示行内容 | 空间/平台/安全校验未过 | 按提示逐项修复 |
| warm 退化为冷启动 | show warm_restart config | enable 未跨重启保留 | 重启后重开开关 |
| 冻结检查失败 | RESTARTCHECK failed | orchagent 有未完成任务 | 排查控制面后再试 |
| 配置升级后回退 | config_db.json 对比 | 未 config save | 落盘后再升级 |
| 容器回滚异常 | rollback-docker 提示 | swss 等需冷重启 | 按提示冷重启 |

表中每一行都遵循「现象 → 证据 → 根因 → 处理」的顺序，目的是让读者先证据后结论，避免凭现象直接下判断。完整诊断树与案例见 08 册（排障见 08-03 ｜ 排障见 08-04）。

### 6. 小结

本篇把升级、warm reboot 与配置持久化三件事拆成了可核验的闭环。升级的落点是 bootloader 的镜像列表与 Next 指针，由 `sonic-installer` 的 `install`、`list`、`set-default`、`set-next-boot`、`cleanup` 等子命令操作；warm reboot 的开关位于 `STATE_DB` 的 `WARM_RESTART_ENABLE_TABLE`、timer 位于 `CONFIG_DB` 的 `WARM_RESTART` 表，且开关默认不跨冷重启持久化；配置持久化由 `config save` 经 `sonic-cfggen` 落盘到 `/etc/sonic/config_db.json`。图 03-05-01 给出三者在一次变更窗口内的衔接关系，两张表分别给出升级前检查清单与失败对照。

需要始终守住三条边界。其一，命令返回成功不等于升级或 warm 已完成，判读要落到 `sonic-installer list` 的 Current/Next、`show warm_restart state` 的 `reconciled` 状态与 `config_db.json` 的表项对比上。其二，warm reboot、多 ASIC 与 chassis 能力受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持；所有收敛时间、中断时长与吞吐数字一律标注「需在目标机型实测」（基准方法见 08-01）。其三，不确定的命令选项、表名与字段取值一律写「需对照实际版本核验」并给出 `sonic_installer/`、`config/`、`show/`、`warmrestart/` 等可定位目录，不凭印象补值。

跨册反查按统一约定：WARM_RESTART、PORT_STATE、platform.json 等结构字段见 05-09；sonic-installer、show/config 命令全集见 04-05，日志与返回码见 04-08；warm reboot 状态恢复机制见 06-10；sonic-utilities CLI 与 config 模块能力见 07-06、镜像与 onie/installer 模块见 07-11。综合起来即（字段见 05-09 ｜ 参数见 04-05 ｜ 原理见 06-10 ｜ 模块见 07-06）。下一篇 03-06 把视角从单机升级扩展到多设备、多 ASIC 与容器化运维部署。

## 03-06 多设备、多 ASIC 与容器化运维部署

### 1. 目标与拓扑

当运维对象从「一台交换机」变成「一批不同机型的交换机」乃至「一台内含多个转发 ASIC 的机箱」时，03-05 那套单机流程就会失效：不同机型的端口、lane、速率由不同的 HWSKU 决定，一台多 ASIC 设备内部又同时存在若干个彼此隔离的 Redis 命名空间，任何一个 `config` 命令都可能只作用在某一个命名空间里。本篇的目标是把部署维度从单机扩展到「多设备 + 多 ASIC + 容器化统一运维」三层，给出可执行的批量生成、分命名空间接入与状态核验方法（模块见 07-10 ｜ 模块见 07-02）。

先厘清三个容易混淆的概念。第一，「多设备」指数据中心里成百上千台白盒交换机，它们的共性是运行同一套 SONiC 软件、差异在机型与 HWSKU，因此配置生成的入口是 `device/<vendor>/<hwsku>/` 目录——本快照里可核实到 accton、arista、barefoot、celestica、dell、mellanox、marvell 等厂商下大量机型目录，每个目录含 `platform.json`、`minigraph.xml`、`config_db*.json`。第二，「多 ASIC」指一台设备内有多个转发芯片，每个 ASIC 对应一个 Linux 网络命名空间与一组独立的数据库实例，`sonic_py_common/multi_asic.py` 用 `get_num_asics()`、`is_multi_asic()`、`get_all_namespaces()` 来判定与枚举。第三，「chassis」指 supervisors 与线卡分离、或分布式、智能交换机形态，依靠 midplane 上的 chassis database 交换跨卡状态，`files/image_config/config-chassisdb/config-chassisdb` 脚本负责把它接入（原理见 06-11 ｜ 模块见 07-10）。

这三层能力都受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持。尤其要守住全册共识：SONiC 是白盒交换机 NOS，控制面在容器进程、数据面在 ASIC，除 `platform/vs/` 外不做软件转发；多 ASIC 只是把同一套控制面按命名空间复制成多份，并未改变「`CONFIG_DB` → `APPL_DB` → `ASIC_DB` → SAI」的异步流水线（原理见 06-01）。把多 ASIC 误解成「多个 SONiC 实例跑在一台机器上」虽有几分形似，但会忽略宿主命名空间里统一的管理面与 chassis 数据库这一关键黏合层（原理见 06-11）。

把多设备、多 ASIC 与命名空间的关系画在一起，得到本篇主拓扑，见图 03-06-01。

### 2. 前置条件与环境

第一项是确认设备是否真的处于多 ASIC 模式，而不是凭机型名称猜测。判定逻辑在 `sonic_py_common/multi_asic.py`：`get_num_asics()` 读取 asic 配置文件中的 `num_asic` 项，找不到配置文件时返回 1；`is_multi_asic()` 就是 `get_num_asics() > 1`；`get_all_namespaces()` 遍历每个 ASIC 命名空间，读取 `DEVICE_METADATA` 的 `localhost` 键下 `sub_role` 字段，按 `FRONTEND`、`BACKEND`、`FABRIC` 等取值把它们分入 `front_ns`、`back_ns`、`fabric_ns` 三组。因此现场判定的可信来源是 `show platform summary` 的 ASIC Count，加上 Python 侧的命名空间枚举，而不是端口数量或 ASIC 型号名称（字段见 05-09 ｜ 模块见 07-10）。

第二项是理解命名空间的命名与常量。`config/main.py` 与 `utilities_common/multi_asic.py` 中可核实到 `NAMESPACE_PREFIX = 'asic'`、`DEFAULT_NAMESPACE = ''`（空字符串代表 Linux 宿主命名空间），以及 `HOST_NAMESPACE = 'localhost'` 一类的取值；`sonic_py_common/multi_asic.py` 里还有 `ASIC_NAME_PREFIX`、`get_asic_id_from_name()`（从 `asicN` 名字里取编号）、`get_asic_device_id()`（读形如 `DEV_ID_ASIC_0=03:00.0` 的 PCI 设备号）、`get_asic_sub_role()`（读 `SUB_ROLE_ASIC_<id>`）等函数。这些常量与函数说明：命名空间不是命令行随手编的字符串，而是由 asic 配置与 `DEVICE_METADATA` 共同决定的合法集合，传入非法名字时 `config`、`show` 命令会报「Invalid namespace」（参数见 04-04 ｜ 字段见 05-09）。

第三项是数据库实例与逻辑库的命名空间化。`dockers/docker-database/multi_database_config.json.j2` 是多 ASIC / chassis 场景的数据库配置模板，其中可核实到 `redis`、`redis1` 到 `redis4`、`redis_chassis` 等多个 `INSTANCES`，以及 `CHASSIS_APP_DB`、`CHASSIS_STATE_DB` 等指向 `redis_chassis` 实例的库，各实例还带有 `persistence_for_warm_boot` 属性。对应地，`sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 提供 `load_sonic_global_db_config()`、`namespace_validation()`、`db_name_validation()`、`get_dblist(namespace)` 等接口，`source/swsssdk/configdb.py` 的 `ConfigDBConnector` 可带 `namespace` 与 `use_unix_socket_path` 参数连接指定命名空间。这印证了 01 册的纪律：DB 编号与实例是运行时配置决定的，须对照 `SonicDBConfig` 与实际版本核验，不得写死（字段见 05-03 ｜ 参数见 04-04）。

第四项是 chassis 的前置。对于 supervisor / 线卡分离或分布式形态，`files/image_config/config-chassisdb/config-chassisdb` 会在 `database-chassis` 服务启动前运行：它按 `PLATFORM` 找到 `chassisdb.conf`，判断 `is_supervisor`、`is_disaggregated_chassis`、`is_smartswitch`、`is_dpu`，从 midplane 接口（如 supervisor 的 `eth1-midplane`，或经 platform API 的 `get_midplane_ip()`）取出 IP，写入 `/etc/sonic/chassisdb_address` 并把 `chassis_db_address` 校验在 midplane 子网内，最后更新 `/etc/hosts` 里的 `redis_chassis.server` 映射。虚拟交换机场景（`asic_type` 为 `vs`）会跳过大部分平台 API 流程。这意味着 chassis 能力高度依赖平台实现，本快照无法核实具体机型的 midplane 行为，一律写「受平台与版本限制，需对照实际版本核验」（模块见 07-11 ｜ 原理见 06-11）。

把上述前置条件整理成一张核验清单，便于批量部署前逐项确认。

| 检查项 | 依据来源 | 期望特征 | 不满足时的影响 |
|---|---|---|---|
| 是否多 ASIC | `show platform summary` | ASIC Count 大于 1 | 命名空间命令无意义 |
| 命名空间集合 | `get_all_namespaces()` | 返回前/后端分组 | 非法命名空间被拒绝 |
| sub_role 字段 | `DEVICE_METADATA` | 前端/后端/fabric 取值 | 无法正确分组 |
| 数据库实例 | `multi_database_config.json.j2` | 每命名空间独立实例 | 数据串库风险 |
| chassis 地址 | `config-chassisdb` 脚本 | 地址在 midplane 子网 | 跨卡状态不可达 |

这张清单覆盖判定、命名空间、角色字段、数据库隔离与 chassis 五个维度；表中涉及的字段与模板路径均可在本快照定位，但具体取值需对照实际版本核验，配置与 schema 全集见 04-02、04-04。

### 3. 分步操作

下面按「前置检查 → 执行 → 验证输出 → 清理」的闭环，给出多设备批量配置与多 ASIC 分命名空间接入的操作。命令名与选项均来自可核验源码，其他版本是否存在需对照实际版本核验。

**第一步，前置检查。** 确认平台、ASIC 数量与命名空间枚举能力。

```bash
show platform summary
sonic-cfggen -H -v DEVICE_METADATA.localhost.platform
python3 -c "from sonic_py_common.multi_asic import get_num_asics, is_multi_asic, get_all_namespaces; print(get_num_asics(), is_multi_asic(), get_all_namespaces())"
```

第一条给出 Platform、HwSKU、ASIC、ASIC Count 等字段；第二条用 `sonic-cfggen -H` 取本机 platform（`config-chassisdb` 脚本正是用这一方式取 platform），是选择 `device/<vendor>/<hwsku>/` 目录的锚点；第三条直接调用 `multi_asic.py` 的三个函数，打印 ASIC 数量、是否多 ASIC 与按角色分组的命名空间字典。若第三条报错，通常说明 `sonic_py_common` 未就绪或 asic 配置缺失，先解决环境再继续（模块见 07-10）。

**第二步，执行批量配置生成。** 对每个 HWSKU 用 `sonic-cfggen` 从 minigraph 与端口配置渲染 `config_db.json`，再统一下发到目标设备。

```bash
sonic-cfggen -m /etc/sonic/minigraph.xml -k <hwsku> -p /usr/share/sonic/hwsku/port_config.ini -d --print-data > config_db.json
for host in leaf-01 leaf-02 leaf-03; do scp config_db.json "$host:/etc/sonic/config_db.json"; done
```

这里 `-m`、`-k`、`-p`、`-d`、`--print-data` 等选项的完整含义见 04-02，本册只给最小必要用法；`<hwsku>` 需替换为实际机型，各机型目录见 `device/<vendor>/<hwsku>/`。批量下发用 `scp` 只是示意，生产环境应通过配置管理通道下发并校验文件完整性（参数见 04-02 ｜ 参数见 04-05）。

**第三步，按命名空间接入与核验。** 在确认是多 ASIC 的设备上，用 `-n` / `--namespace` 选项逐命名空间查看端口与 warm 状态。

```bash
show interfaces status -n asic0
show warm_restart config -n asic0
sonic-cfggen -n asic0 -d --print-data
```

`config save` 的源码表明，多 ASIC 时会为每个命名空间额外生成 `config_db<NS>.json`（如 `config_db0.json`），单命名空间保存则调用 `sonic-cfggen -n <namespace> -d --print-data`。因此第三步既是验证也是排错入口：若 `show interfaces status -n asic0` 与 `-n asic1` 看到不同端口集合，说明命名空间隔离正常；若两者完全一致，需怀疑 `-n` 未生效或命令未实现命名空间选项（参数见 04-05 ｜ 模块见 07-06）。

**第四步，chassis 场景接入。** 在 supervisor / 线卡形态上，确认 chassis DB 地址落位后启动相关服务。

```bash
cat /etc/sonic/chassisdb_address
getent hosts redis_chassis.server
systemctl status database-chassis
```

`config-chassisdb` 脚本在 `/etc/sonic/chassisdb_address` 中写入 `chassis_db_address=<midplane IP>`，并在 `/etc/hosts` 中追加 `redis_chassis.server` 映射；`getent hosts` 用于确认该映射可被解析。若地址为空或不在 midplane 子网，脚本会报错退出，需回到 midplane 接口配置排查。非 chassis 平台可跳过本步（模块见 07-11 ｜ 原理见 06-11）。

**第五步，清理。** 删除批量下发的临时文件，恢复到干净状态。

```bash
rm -f /tmp/config_db.json /etc/sonic/chassisdb_address.bak
```

清理仅针对本次生成的临时产物，不触碰 `/etc/sonic/config_db.json` 与各命名空间正式配置；正式配置的变更须走 `config save` / `config load` 并留痕（参数见 04-05）。

### 4. 验证方法与预期结果

验证分三层：单机平台信息、多 ASIC 命名空间隔离、chassis 跨卡连通。先看单机平台信息，`show platform summary` 的输出来自 `show/platform.py` 的 `summary()`，字段可直接对照。

```bash
show platform summary
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
Platform: x86_64-some_vendor_some-platform-r0
HwSKU: some-hwsku-32x100G
ASIC: some_asic
ASIC Count: 2
Serial Number: SN0123456789
Model Number: MODEL-ABCD
Hardware Revision: RevA
Switch Type: switch
```

逐行判读如下。第一行 `Platform` 对应 `device/<vendor>/<hwsku>/` 目录的机型标识，是选择端口配置与 SAI 适配的锚点，示例中 `x86_64-some_vendor_some-platform-r0` 只是格式示意，具体取值需对照实际版本核验；第二行 `HwSKU` 指向同一目录下的 `config_db*.json` 与 `minigraph.xml`，是 03-02 所述配置落地的依据；第三行 `ASIC` 给出芯片类型，本套资料不写死具体厂商型号；第四行 `ASIC Count` 是判定是否多 ASIC 的关键，这里为 2，意味着应存在 `asic0`、`asic1` 两个前端/后端命名空间，与第三步的 `get_all_namespaces()` 结果相互印证，若 `ASIC Count` 为 1 却看到命名空间，说明环境不一致；第五至七行 Serial Number、Model Number、Hardware Revision 来自 chassis 信息与 EEPROM，用于资产核对，不同批次设备取值不同属正常；第八行 `Switch Type` 仅在平台提供该字段时输出，缺省时可 absent。以上字段的读取在 `show/platform.py` 中经 `device_info.get_platform_info()` 与 `get_chassis_info()` 完成，本快照不含这些实现细节，需对照实际版本核验。输出块已注明示例输出与版本核验要求，取值不得当作真实设备数据引用（模块见 07-10 ｜ 字段见 05-09）。

再看命名空间隔离的验证。逐命名空间取端口状态并比对，同时确认 `ASIC_DB` 对象是否分别落在各自实例中。

```bash
show interfaces status -n asic0 --display all
show interfaces status -n asic1 --display external
show ip interfaces -n asic0
```

`utilities_common/multi_asic.py` 提供 `--display` 选项（`DISPLAY_ALL` 与 `DISPLAY_EXTERNAL`）与 `--namespace`/`-n` 选项，并通过 `MultiAsic.get_ns_list_based_on_options()` 把前端、后端、fabric 命名空间按选项展开，`is_object_internal()` 判定某个端口、PortChannel 或 BGP 邻居是否为 ASIC 间内部对象，`skip_display()` 据此决定是否过滤。因此 `--display all` 会显示内部互连端口，`--display external` 只显示对外端口；若在多 ASIC 设备上不加区分地看汇总输出，容易把内部端口当成业务端口，或误判端口数量不足。判读要点是：同一命名空间内端口名与 `PORT` 表一致（表名与字段见 04-02），跨命名空间的内部端口不会出现在 `--display external` 结果里（原理见 06-11 ｜ 模块见 07-06）。

最后确认 chassis 跨卡连通：以 `redis_chassis.server` 解析结果与 `CHASSIS_APP_DB` / `CHASSIS_STATE_DB` 的可达性为准。由于这两个库指向 `redis_chassis` 实例并经 midplane 访问，只有 midplane IP 正确、`/etc/hosts` 映射生效、`database-chassis` 服务运行三者同时满足时才可判为正常。任一环节失败都应回到 `config-chassisdb` 脚本的报错信息定位，不得据此推断 ASIC 转发故障。所有收敛、时延与吞吐类结论一律标注「需在目标机型实测」（基准方法见 08-01 ｜ 调优见 08-02）。

### 5. 常见失败与排错

第一类失败是命名空间不存在或 `-n` 选项无效。现象是 `show ... -n asic0` 报「Invalid namespace: asic0」，或输出与不带 `-n` 时完全一致。根因通常是：`get_namespace_list()` 返回的合法集合里没有该名字（多 ASIC 判定为假时只有默认命名空间），或所用命令未实现命名空间选项。`show/warm_restart.py` 与 `config/main.py` 都会用 `multi_asic.get_namespace_list()` 校验传入的 namespace，非法值直接抛 `UsageError`。处理方向是先跑 `get_all_namespaces()` 确认合法集合，再检查命令是否支持 `-n`，不要凭端口数量推测命名空间名（原理见 06-11 ｜ 排障见 08-03）。

第二类失败是端口在汇总里「消失」。现象是 `show interfaces status` 看不到某些端口，尤其在多 ASIC 设备上。根因是 `--display` 默认为 `DISPLAY_EXTERNAL`（`multi_asic_display_default_option()` 在非单 ASIC 或 chassis 场景返回该值），内部互连端口被 `skip_display()` 过滤。处理方式是加 `--display all` 复查；若加了仍缺失，再按 `CONFIG_DB` → `APPL_DB` → `ASIC_DB` 顺序逐段核对，而不是直接怀疑芯片。这里再次体现全册共识：`config` 返回成功不等于硬件已下发，判读要落到各库表项（原理见 06-01 ｜ 排障见 08-03）。

第三类失败是配置下发到多 ASIC 设备后状态不一致。现象是宿主命名空间配置正确，但某个 `asic<N>` 命名空间端口起不来。根因通常是批量下发时只改了宿主 `config_db.json`、漏了 `config_db0.json` / `config_db1.json`，或 `config save` 在多 ASIC 下生成了多文件而下发时只取了其中一个。`config/main.py` 的 `save()` 明确在多 ASIC 时按 `NAMESPACE_PREFIX + inst` 生成 `config_db<NS>.json` 并逐个写盘，`load()` 同样按文件列表逐个导入。处理方向是核对每个命名空间对应的配置文件是否齐全、内容是否一致（参数见 04-05 ｜ 模块见 07-06）。

第四类失败是 chassis 跨卡状态不可达。现象是 `chassisdb_address` 为空、`getent hosts redis_chassis.server` 无解析，或 `CHASSIS_STATE_DB` 读不到线卡状态。根因可能是 midplane 接口未起、`chassisdb.conf` 缺失（脚本会打印「no chassisdb.conf found, bypass config-chassisdb service」并退出）、地址不在 midplane 子网（脚本报「chassis_db address does not belong to midplane subnet」），或 supervisor 的 `eth1-midplane` 在 180 秒重试内未拿到 IP。处理方式是按 `config-chassisdb` 的报错分支逐项排查 midplane 与 platform API；虚拟交换机场景会跳过大部分平台 API，不应据此推断真实机箱行为（模块见 07-11 ｜ 原理见 06-11）。

把失败按现象归并，便于现场快速定位。

| 现象 | 首要证据 | 可能根因 | 处理方向 |
|---|---|---|---|
| 命名空间被拒 | `get_all_namespaces()` | 名字不在合法集合 | 重新枚举命名空间 |
| 端口汇总缺失 | 加 `--display all` 复现 | 内部端口被过滤 | 切换显示选项 |
| 某 ASIC 状态异常 | 各 `config_dbN.json` | 分命名空间配置漏下发 | 逐命名空间补齐 |
| 跨卡状态不可达 | `chassisdb_address` | midplane 或地址配置错 | 排查 chassis 脚本分支 |

表中每行遵循「现象 → 证据 → 根因 → 处理」顺序；四行分别对应命名空间、显示、配置、chassis 四类高频问题。完整诊断树与案例见 08 册（排障见 08-03 ｜ 排障见 08-04）。

### 6. 小结

本篇把部署从单机扩展到三个维度。多设备维度以 `device/<vendor>/<hwsku>/` 为配置源，用 `sonic-cfggen` 按 HWSKU 渲染并批量下发，多 ASIC 时须同时生成宿主与各 `config_dbN.json`；多 ASIC 维度以 `sonic_py_common/multi_asic.py` 的 `get_num_asics()`、`is_multi_asic()`、`get_all_namespaces()` 为判定基础，通过 `-n` / `--namespace` 与 `--display` 选项分命名空间接入；容器化运维维度依靠 `dockers/` 容器族与统一 CLI，chassis 场景再由 `config-chassisdb` 接入 midplane 上的 chassis database。图 03-06-01 给出三者的衔接关系，两张表分别给出前置核验清单与失败对照。

需要守住三条边界。其一，多 ASIC、chassis 与 warm reboot 能力受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持；`asic_type` 为 `vs` 的虚拟交换机会跳过多数平台 API，不能用来推断真实机箱行为。其二，DB 编号与实例由运行时配置（`database_config.json`、`database_global.json` 及其模板）决定，须对照 `SonicDBConfig` 核验，不得写死；`config` 返回成功不等于硬件已下发，判读要落到各命名空间各库的表项与 `show` 输出（原理见 06-01）。其三，不确定的命令选项、表名、字段与函数签名一律写「需对照实际版本核验」并给出可定位目录，不凭印象补值；收敛、时延、吞吐一律标注「需在目标机型实测」（基准方法见 08-01）。

跨册反查按统一约定：`DEVICE_METADATA` 的 `sub_role`、`WARM_RESTART`、`platform.json`、`PORT_STATE` 等结构字段见 05-09，`SonicDBConfig` 字段见 05-03；Redis 命名空间、逻辑库与对象见 04-04，show/config 命令全集见 04-05，机型 schema 见 04-02；多 ASIC 与 chassis 数据库命名空间机制见 06-11，异步流水线见 06-01；platform/device/HWSKU 模块见 07-10，dockers 容器族见 07-02，镜像与 onie/installer 模块见 07-11。综合起来即（字段见 05-09 ｜ 参数见 04-04 ｜ 原理见 06-11 ｜ 模块见 07-10）。03 册至此收束：从 vs 启动、配置落地、基础配置、CLI 接入，到升级与 warm reboot，再到本篇的多设备与多 ASIC 部署，构成一条从单机到规模化的完整部署主线。
