# SONiC 技术资料 · 07 模块与特性介绍（分片 B）
## 07-03 sonic-swss / orchagent 模块

### 1. 模块定位与职责边界

本篇是 07 册「模块与特性介绍」分片 B 的第一篇，聚焦 `sonic-swss` 仓及其中的核心目录 `orchagent/`。06 册已经把配置流水线当作机制逐段讲过，本册换一个视角：不追求「怎么实现」，而是回答「哪个模块负责什么、目录如何归属、从哪个入口进去读代码」。这种视角转换是理解大型开源 NOS 的关键。SONiC 并非单一仓库，而是由 8 个子仓拼装而成，每个子仓解压后又有一层 `xxx-master/` 归档目录，真实仓库根是 `upstream_src/sonic-swss/sonic-swss-master/`（模块见 07-01）。把目录归属搞错，后面所有源码定位都会错位，因此先把「根在哪、边界在哪」钉死，是本篇的第一要务。

sonic-swss 在整个控制面里承担「业务编排 + 配置管理」双重职责，从目录上可再切成三块：`orchagent/` 负责把期望状态翻译成 ASIC 对象，`cfgmgr/` 负责把 CONFIG_DB 的用户配置校验、规范化后搬进 APPL_DB，一组 `*syncd/` 同步守护进程（如 `fpmsyncd/`、`portsyncd/`、`neighsyncd/`、`teamsyncd/`）负责把外部协议或内核状态同步进 APPL_DB。本篇以 `orchagent/` 为主体，`cfgmgr/` 与 `*syncd/` 作为它的直接上游邻居一并介绍，三者共同构成 APPL_DB 的生产者与消费者两端（原理见 06-02 ｜ 模块见 07-03）。

这里必须先把职责边界钉死，否则极易与下游的 sonic-sairedis 混淆。`orchagent/` 是异步配置流水线中最靠近 ASIC_DB 的一段：它消费 APPL_DB 的期望状态，把用户配置翻译成 SAI 对象与属性，写入 ASIC_DB，交给下游 syncd 经 SAI 编程芯片。它只写 ASIC_DB，不直接读写寄存器、不直接驱动芯片；真正调用 SAI、真正操作 ASIC 的是 `sonic-sairedis` 仓的 syncd（原理见 06-04 ｜ 模块见 07-04）。由此得到一条判读铁律：`config` 命令返回成功只代表配置进入 CONFIG_DB，orchagent 是否完成翻译、syncd 是否完成编程，要按库逐段核对，不能一句「已下发」带过（原理见 06-01 ｜ 排障见 08-03）。

还有两条边界要在开头立住。其一，`ProducerStateTable`、`Consumer`、`Select` 等通用通信原语属于 `sonic-swss-common`，不在本快照，涉及它们的字段与实现一律写「不在本快照，需对照实际版本核验」（模块见 07-05）。其二，厂商 SAI 实现闭源且不在本仓库，orchagent 通过对象类型与属性枚举和下游约定，不接触具体寄存器（原理见 06-12）。版本基准统一为「上游 master 快照（2026-11 抓取）」，本文所有路径均相对 `sonic-swss-master/` 根，函数签名不确定处标注核验要求。理解这条边界后，读者才能把 06 册的机制与 07 册的目录一一对应：机制讲「数据流怎么走」，模块篇讲「这段代码住在哪个目录、归哪个仓管」。

### 3. 关键类与入口函数

本节只点类名、真实路径与回查去向，不展开逐字段定义。Orch 派生结构的字段统一放在 05 册，Orch 基类与请求对象字段见 05-05，各业务派生结构字段见 05-07，启动与 SAI 相关参数见 04-06，调度机制见 06-04，即（字段见 05-05 ｜ 字段见 05-07 ｜ 参数见 04-06 ｜ 原理见 06-04 ｜ 模块见 07-03）。这样安排是为了让本篇聚焦「类住在哪里、入口叫什么」，而不是把字段表提前铺开。

框架主干落在三个文件。`orchagent/main.cpp` 的 `main()` 是进程入口，负责初始化上下文、构造 `OrchDaemon` 并进入运行循环。`orchagent/orchdaemon.h` 定义了 `OrchDaemon` 类（可核验其声明），它承担全部业务 Orch 的注册与统一调度；`orchagent/orchdaemon.cpp` 是其实现。`orchagent/orch.h` 定义了 `Orch` 基类（可核验其声明），`orchagent/orch.cpp` 实现了任务拉取、请求解析与重试框架。这三件套构成 orchagent 的骨架：main 起进程、OrchDaemon 管编排、Orch 定范式（字段见 05-05 ｜ 原理见 06-04）。

业务编排类是一组派生自 Orch 的具体实现，均有真实头文件可核验：`orchagent/portsorch.h` 的 `PortsOrch`、`orchagent/intfsorch.h` 的 `IntfsOrch`、`orchagent/neighorch.h` 的 `NeighOrch`、`orchagent/routeorch.h` 的 `RouteOrch`、`orchagent/aclorch.h` 的 `AclOrch`。它们各自消费不同的 APPL_DB 表、生成不同的 SAI 对象：端口与 VLAN 汇入 `PortsOrch`，三层接口归 `IntfsOrch`，邻居与下一跳归 `NeighOrch`，路由归 `RouteOrch`。这些派生结构的成员字段、继承关系与表项映射留待 05 册展开（字段见 05-07 ｜ 原理见 06-06）。

辅助组件同样有可核验落位：`orchagent/bulker.h` 提供批量下发封装，`orchagent/request_parser.h` 与 `request_parser.cpp` 负责把表项字段解析成请求对象，`orchagent/notifications.h` 与 `notifications.cpp` 负责通知的消费与分发，`orchagent/saihelper.h`、`saiattr.h` 封装 SAI 属性构造，`orchagent/return_code.h` 定义返回状态，`orchagent/retrycache.h` 支撑失败重试，`orchagent/orchagent_restart_check.cpp` 服务 warm reboot 状态检查。`response_publisher.cpp` 与 `zmqorch.cpp` 一类文件涉及响应发布与 ZeroMQ 通道（原理见 06-10 ｜ 字段见 05-08）。以上只列类名与位置，字段含义、成员类型与读写时机一律留待 05 册。

### 4. 对外接口与扩展点

orchagent 的「对外接口」不是传统意义上供进程调用的函数 API，而是一组数据库表契约与进程间约定，理解这一点是正确使用模块的前提。对上游，它通过 `Consumer` 消费 APPL_DB 的表项，表的名字、字段与键格式就是接口的一部分；对下游，它把 SAI 对象与属性写进 ASIC_DB，由 syncd 消费。这些表与对象的完整定义属 04 册权威源，本篇不重列（参数见 04-04 ｜ 参数见 04-06）。通知侧，它通过 `notifications.cpp` 一类组件消费来自下游或内核的事件，把异步事件转成编排动作（原理见 06-08 ｜ 字段见 05-08）。

从模块能力角度看，orchagent 暴露给使用者的「扩展点」主要有三类。第一类是新增一种业务编排：做法是派生一个新的 Orch 子类，实现其 `doTask()` 一类入口，在 `orchdaemon.cpp` 中注册，并让它订阅一张新的 APPL_DB 表——这是扩展 SONiC 支持新特性最标准的方式。第二类是批量与重试：通过 `bulker.h` 与 `retrycache.h` 一类封装，可以在不改动主流程的情况下调整下发节奏与失败处理（原理见 06-04 ｜ 调优见 08-02）。第三类是启动与状态恢复：`command line` 选项与 warm reboot 检查逻辑集中在 `main.cpp` 与 `orchagent_restart_check.cpp`（参数见 04-06 ｜ 原理见 06-10）。

需要特别点明扩展时的能力边界。新增 Orch 只能产出 ASIC_DB 对象与属性，不能自己调用 SAI、不能自己编程 ASIC——这是 sonic-swss 与 sonic-sairedis 的分工红线，越界会导致「同一个对象两边都改」的难查故障（模块见 07-04）。同样，字段与表结构的定义不在本仓：`ProducerStateTable`、`Consumer` 等来自 `sonic-swss-common`（不在本快照），CONFIG_DB 与 APPL_DB 的表 schema 由 04 册统一给出（参数见 04-02 ｜ 模块见 07-05）。

为了把「模块能力—职责—回查去向」串成索引，下面给出一组四段式反查关系，作为本篇所有交叉引用的统一写法：字段见 05-05 ｜ 参数见 04-06 ｜ 原理见 06-04 ｜ 模块见 07-03。读者从任一维度切入，都能沿着这条线索回到本篇的目录与入口，而不必在多个册之间反复猜测归属。这也是 07 册作为「模块功能与目录归属唯一权威源」的价值所在：它给出锚点，其余册围绕锚点展开细节。

第二组给出 `OrchDaemon` 注册与 `Orch` 分派的代码片段，用来印证「注册—调度—分派」的实现形态；下列片段依据本快照中可核验的类名组织，为便于阅读做了简化，真实函数签名与控制流需对照实际版本核验。

```cpp
// 代码形态示意，依据 orchdaemon.cpp / orch.cpp 中可核验的类名整理；签名需对照实际版本核验
OrchDaemon::OrchDaemon(DBConnector *db)
{
    // 注册各业务 Orch，每个 Orch 订阅自己的 APPL_DB 表
    m_orchList.push_back(new PortsOrch(db, portTableNames));
    m_orchList.push_back(new NeighOrch(db, neighTableNames));
    m_orchList.push_back(new RouteOrch(db, routeTableNames));
}

bool OrchDaemon::start()
{
    for (auto *orch : m_orchList) {
        orch->doTask();   // 由基类 Orch 完成表项拉取与请求分派
    }
    return true;
}
```

这段代码强化了一个核心判断：orchagent 的可扩展性来自「注册表 + 统一基类」的简单结构。构造函数把 `PortsOrch`、`NeighOrch`、`RouteOrch` 等业务类逐个加入列表，`start()` 再统一驱动各自的 `doTask()`。新增特性时，仿照这一范式派生新类并加入注册表即可，其余调度逻辑复用基类。片段中的成员名与参数作了语义化示意，真实源码中每个 Orch 订阅哪些表、如何处理返回与重试，需对照 `orchdaemon.cpp`、`orch.cpp` 与各 `*orch.cpp` 核验（字段见 05-05 ｜ 字段见 05-07 ｜ 原理见 06-04）。

### 6. 与其他模块的关系及常见误用

从全链路看，orchagent 上游接 `cfgmgr/` 与各 `*syncd/`，下游接 sonic-sairedis 的 syncd，横向依赖 `sonic-swss-common` 提供的通信原语。上游侧，`cfgmgr/` 的 `*mgrd` 进程把 CONFIG_DB 配置搬进 APPL_DB，`portsyncd/`、`neighsyncd/`、`fpmsyncd/` 则把内核链路、邻居与 FPM 路由状态同步进 APPL_DB，orchagent 是这些表项的共同消费者（模块见 07-03 ｜ 原理见 06-07）。下游侧，orchagent 写出的 ASIC_DB 对象由 syncd 消费并编程 ASIC；这是两个仓之间唯一的「握手面」，对象类型与属性枚举是共同语言（模块见 07-04 ｜ 原理见 06-05）。横向依赖的 `sonic-swss-common` 不在本快照，涉及 `ProducerStateTable`、`Consumer`、`Select` 的字段一律写「不在本快照，需对照实际版本核验」（模块见 07-05）。

第一类是定位混淆。最常见的错误是把 syncd 写进 sonic-swss 仓，或把 orchagent 说成直接驱动芯片的进程。事实上 syncd 主体在 `sonic-sairedis-master/syncd/`，`dockers/` 下也没有名为 `docker-syncd` 的目录；orchagent 只写 ASIC_DB，二者职责不可混写（模块见 07-04）。第二类是「配置即时生效」陷阱：`config` 返回成功只代表配置写入 CONFIG_DB，端口进入 up、VLAN 成员写入芯片都要等整条异步流水线走完；端口 `Oper up` 是运行时状态，不能反推某次 config 已使硬件下发（原理见 06-01 ｜ 排障见 08-04）。

第三类是事实纪律陷阱。`ProducerStateTable` 等通信原语、`FieldValueTuple` 等表项结构属 `sonic-swss-common`，不在本快照；函数名可核验，但字段、成员类型与函数签名的完整形式需对照实际版本核验，不确定的一律标注并给出 `orchagent/`、`cfgmgr/` 等可定位目录（字段见 05-02 ｜ 模块见 07-05）。第四类是 DB 编号陷阱：Redis 各库编号来自运行时 `database_config.json`，须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 核验，禁止写死某库是某号（参数见 04-04 ｜ 模块见 07-05）。

第五类是扩展越界陷阱。新增 Orch 时容易顺手在编排层直接构造 SAI 调用，正确做法是只产出 ASIC_DB 对象与属性，把 SAI 调用留给 syncd；跨层越界会造成「两边都改同一对象」的难查故障（模块见 07-04）。第六类是 warm reboot 与性能陷阱：`orchagent_restart_check.cpp`、`warmrestart/` 相关能力受平台与版本限制，需对照实际版本核验；批量下发时延、收敛时间与吞吐随机型、芯片、版本变化，一律标注「需在目标机型实测」，不给绝对值（原理见 06-10 ｜ 基准见 08-01）。

最佳实践可归纳为四条。其一，读代码时把路径写成 `upstream_src/sonic-swss/sonic-swss-master/` 下的相对路径，并同时给出对应类或入口（`OrchDaemon`、`PortsOrch`、`Orch::doTask()` 等），签名不确定就写「需对照实际版本核验」。其二，排障按图 07-03-01 先定位停在哪一段，再决定查哪个进程与哪张表，不做跳跃式判断。其三，跨册引用统一用四段式（字段见 05-07 ｜ 参数见 04-06 ｜ 原理见 06-04 ｜ 模块见 07-03），本篇涉及的派生结构字段写「字段见 05-07」、调度机制写「原理见 06-04」、启动参数写「参数见 04-06」，不在本篇展开字段表与参数全集。其四，遇到快照内无法核实的内容，宁可标注核验要求并给出目录，也不补值。

## 07-04 sonic-sairedis / syncd 模块

### 1. 模块定位与职责边界

本篇是 07 册「模块与特性介绍」分片 B 的第二篇，介绍 `sonic-sairedis` 仓及其核心进程 syncd。如果说 07-03 的 orchagent 负责「把配置翻译成 ASIC 对象」，那么 syncd 就是「把这些对象真正编程进芯片」的唯一执行者。06-05 已经把这条 SAI 调用链当作机制讲透，本篇仍沿用 07 册的固定视角：回答「这个模块的目录如何归属、从哪个入口进去、对外边界在哪里」，把机制留给 06 册、把字段留给 05 册、把参数留给 04 册（原理见 06-05 ｜ 模块见 07-04）。

先把仓库归属钉死，这是本篇最容易出错的地方。syncd 的主体位于 `upstream_src/sonic-sairedis/sonic-sairedis-master/syncd/`，属于 `sonic-sairedis` 仓，而不在 `sonic-swss` 仓；`dockers/` 下也并不存在名为 `docker-syncd` 的目录——syncd 是随 `docker-orchagent` 容器一并交付的进程（模块见 07-02 ｜ 模块见 07-03）。这个落位本身就揭示了它的定位：syncd 与 SAI 强绑定，属于「芯片适配」这条线，而非「业务编排」那条线。任何把它写进 sonic-swss 或某个独立 syncd 容器的说法，都与本快照的证据相悖。

syncd 的职责可概括为「双向翻译桥」。下行方向，它从 ASIC_DB 的 `ASIC_STATE` 表消费 orchagent 写下的对象操作命令，经 SAI 调用链翻译成厂商 API 调用，编程 ASIC；上行方向，它把芯片的对象视图、链路状态通知与计数器分别回写进 ASIC_DB、STATE_DB 与 COUNTERS_DB（原理见 06-05 ｜ 原理见 06-09）。这里有一条铁律必须立住：syncd 是控制面里唯一有资格经 SAI 访问 ASIC 的组件，但它自身并不实现 SAI——真正实现 SAI 的是厂商提供的库，多为闭源且不在本仓库。因此 syncd 做的是「Redis 键值与 SAI 对象属性之间的互译」，不是协议栈，也不是转发面；数据面转发始终发生在 ASIC（除虚拟交换机 `platform/vs/` 外不做软件转发，原理见 06-12）。

本快照的证据边界也要在开头讲清。`sonic-sairedis-master/SAI/` 在本快照是空目录，实际的 SAI 头文件与厂商实现均不在本快照；可核验的是 `meta/`（元数据）、`lib/`（Redis 与远端接口）、`vslib/`（虚拟 SAI）、`saidump/`、`saiplayer/` 等目录（模块见 07-04）。因而本篇凡是涉及具体 SAI 属性枚举、函数签名与版本号，一律写「需对照实际版本核验」并给出可定位目录，不据空目录编造内容。版本基准统一为「上游 master 快照（2026-11 抓取）」，本文所有路径均相对 `sonic-sairedis-master/` 根。

### 4. 对外接口与扩展点

syncd 的「对外接口」同样是契约式的，而非函数调用 API。对上游，它通过 ASIC_DB 的 `ASIC_STATE` 表消费 orchagent 写下的对象与操作命令；常量 `ASIC_STATE_TABLE`（值为 `"ASIC_STATE"`）可在 `lib/sairediscommon.h` 中核验，`lib/RedisChannel.cpp` 用它构造生产者通道。对下游，它通过 `VendorSai` 的函数指针表调用统一 SAI API，再由厂商库落到芯片；厂商实现不在本快照。回写侧则把对象视图、链路状态与计数分别写回 ASIC_DB、STATE_DB 与 COUNTERS_DB（参数见 04-04 ｜ 原理见 06-05 ｜ 模块见 07-12）。

从模块能力角度看，syncd 暴露的「扩展点」主要有三类。第一类是 SAI 版本与厂商适配：`VendorSai.cpp`、`meta/` 元数据与 `SAI/` 头文件共同定义可用对象与属性，替换厂商实现理论上只需对接 SAI API；但厂商库闭源且不在本仓库，具体适配步骤需对照实际版本核验（模块见 07-10）。第二类是传输通道选择：`Syncd.cpp` 与 `meta/` 下可核验到 `ZeroMQSelectableChannel`、`RedisSelectableChannel` 两种实现，通道选择属于启动与部署层面的配置（参数见 04-06 ｜ 原理见 06-02）。第三类是虚拟交换机：`vslib/` 提供虚拟 SAI 实现，使 SONiC 能在 `platform/vs/` 上以软件方式运行，用于开发与测试，但不代表真实芯片行为（模块见 07-10 ｜ 基准见 08-01）。

扩展时的能力边界必须点明。syncd 是唯一调用 SAI 的组件，任何「绕过 syncd 直接编程芯片」的扩展都会破坏 ASIC_DB 作为唯一视图的一致性，造成难查的双写故障；这也是 07-03 强调 orchagent 不得自己调用 SAI 的原因（模块见 07-03）。同时，SAI 属性是否真的受支持，需要用 `queryAttributeCapability()`、`queryStatsCapability()` 一类能力查询确认，不能仅凭对象出现在 ASIC_DB 就断言芯片已生效（原理见 06-05 ｜ 原理见 06-12）。

### 5. 典型用法与调用示例

图 07-04-01 用颜色区分职责：purple 为上游 orchagent 控制面，amber 为 ASIC_DB 对象表，green 为 syncd 主循环、VendorSai 与 FlexCounter 运行时组件，gray 为不在本快照的厂商 SAI 实现，red 为硬件边界，blue 为回写目标库。需要强调的是中间的「翻译」两步：`Syncd` 主循环之后，`processQuadEvent()`、`processOidCreate()` 等函数并不直接调用芯片，而是先把 Redis 键值还原成 SAI 对象与属性，这一步由 `SaiObj.cpp`、`SaiAttr.cpp` 支撑；随后 `VendorSai::create()`、`set()`、`get()` 才经函数指针表转到 SAI API（原理见 06-04 ｜ 模块见 07-03）。图中每一段都是异步的，上一节点完成不代表下一节点完成。

```cpp
// 代码形态示意，依据 syncd/Syncd.cpp 与 VendorSai.cpp 中可核验的函数整理；签名需对照实际版本核验
void Syncd::processSingleEvent(const std::string &op, entry)
{
    if (op == REDIS_ASIC_STATE_COMMAND_CREATE) {
        processOidCreate(entry);      // 还原属性后调用 VendorSai::create()
    } else if (op == REDIS_ASIC_STATE_COMMAND_SET) {
        processOidSet(entry);         // 调用 VendorSai::set()
    } else if (op == REDIS_ASIC_STATE_COMMAND_REMOVE) {
        processOidRemove(entry);      // 调用 VendorSai::remove()
    }
    sendApiResponse(status);          // 结果经通道回送 orchagent
}
```

这段代码印证了 syncd 的本质是「命令码分派器 + 翻译器」：分派靠 `REDIS_ASIC_STATE_COMMAND_*` 字符串常量比对，翻译靠 `SaiObj.cpp`、`SaiAttr.cpp`，真正编程靠 `VendorSai` 的函数指针表。片段中的参数与状态变量作了语义化示意，真实源码中每个 `processOid*()` 如何把属性数组交给 `VendorSai::create()`/`set()`/`get()`，以及失败时 `sai_status_t` 如何经 `sendApiResponse()` 返回，需对照 `Syncd.cpp` 核验（字段见 05-06 ｜ 原理见 06-05）。`saidump/`、`saiplayer/` 目录下的工具可作为工作之外的核验手段，其名称与选项需对照实际版本核验（模块见 07-04）。

### 6. 与其他模块的关系及常见误用

从全链路看，syncd 上游接 sonic-swss 的 orchagent，横向依赖 `sonic-swss-common` 提供的通信原语与 `sonic-py-swsssdk` 提供的 DB 访问封装，向下经厂商 SAI 接 ASIC，旁边还有 `platform/`、`device/` 的 HWSKU 适配与 `sonic-platform-common/` 的平台外设基类（模块见 07-03 ｜ 模块见 07-05 ｜ 模块见 07-10）。上游侧，orchagent 写出的 ASIC_DB 对象是 syncd 的唯一输入；这是两个仓之间唯一的握手面，对象类型与属性枚举是共同语言（原理见 06-05）。下游侧，syncd 经 SAI 访问 ASIC，厂商实现闭源且不在本仓库。平台侧的 `platform/vs/` 虚拟交换机依赖 `vslib/` 的虚拟 SAI，用于开发与测试，不代表真实芯片行为（模块见 07-10）。

第一类是定位混淆，这也是全册反复强调的高频错误。最常见的是把 syncd 写进 `sonic-swss` 仓或某个名为 `docker-syncd` 的容器：本快照里 syncd 主体在 `sonic-sairedis-master/syncd/`，`dockers/` 下没有 `docker-syncd` 目录，它随 `docker-orchagent` 一起交付（模块见 07-02 ｜ 模块见 07-04）。第二类是「直接驱动硬件」误判：syncd 经 SAI 抽象调用厂商实现，厂商 SAI 多为闭源且不在本仓库，`SAI/` 在本快照为空目录，不得据它编造头文件、属性枚举与版本；涉及厂商实现一律写「不在本快照，需对照实际版本核验」，并给出 `syncd/`、`meta/`、`vslib/` 等可定位目录（模块见 07-10 ｜ 原理见 06-12）。

第三类是「ASIC_DB 有对象等于芯片已生效」误判，这与全册异步铁律直接相关：`ASIC_STATE` 里出现对象只代表 syncd 已纳入视图，属性是否被厂商 SAI 支持、是否真正写入芯片，需经能力查询与状态回写确认，判读要按 CONFIG_DB、APPL_DB、ASIC_DB、STATE_DB 与 `show` 输出逐段推进，不能一上来怀疑硬件，也不能一句「已下发」带过（原理见 06-01 ｜ 排障见 08-03）。第四类是 DB 编号与表名陷阱：Redis 各库编号来自运行时 `database_config.json`，须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 与实际版本核验，禁止写死；`ASIC_STATE` 常量值 `"ASIC_STATE"` 可在 `lib/sairediscommon.h` 核验，但 STATE_DB、COUNTERS_DB 里的具体表名与字段需对照实际版本核验（参数见 04-04 ｜ 字段见 05-03 ｜ 模块见 07-05）。

第五类是 warm reboot 与多 ASIC 陷阱。`SaiDiscovery.cpp`、`WarmRestartTable.cpp`、`AsicView.cpp`、`ComparisonLogic.cpp` 以及 warmrestart 相关能力受平台与版本限制，不同 HWSKU 与版本行为不同，一律写「受平台与版本限制，需对照实际版本核验」，不得宣称全平台无条件支持；多 ASIC 命名空间同样受限制（原理见 06-10 ｜ 原理见 06-11）。第六类是回写误用：端口 `Oper up` 属运行时状态，不能反推「某次 config 命令已使硬件下发」，仍须按库逐段核对（排障见 08-04）。第七类是性能陷阱：一次批量下发的收敛时间、状态回写时延、计数器轮询开销与吞吐都随机型、芯片与版本变化，一律标注「需在目标机型实测」，不给绝对值（基准见 08-01 ｜ 调优见 08-02）。

最佳实践归纳为四条。其一，读 syncd 代码时把路径写成 `upstream_src/sonic-sairedis/sonic-sairedis-master/` 下的相对路径，并同时给出对应函数（`processEvent()`、`processOidCreate()`、`VendorSai::create()` 等），签名不确定就写「需对照实际版本核验」。其二，排障按图 07-04-01 先定位「哪一段」——是 ASIC_DB 无对象、syncd 未消费、SAI 调用失败，还是状态未回写——再按容器查日志，不做跳跃式判断。其三，跨册引用统一用四段式（字段见 05-06 ｜ 参数见 04-06 ｜ 原理见 06-05 ｜ 模块见 07-04），本篇涉及的 SAI 对象字段写「字段见 05-04」、计数回写写「原理见 06-09」、warm reboot 恢复写「原理见 06-10」，不在本篇展开字段表与参数全集。其四，遇到快照内无法核实的内容，宁可标注核验要求并给出目录，也不补值。

### 7. 小结与延伸阅读

本篇把配置流水线最后一棒的模块归属讲清：syncd 位于 `sonic-sairedis-master/syncd/`，入口经 `main.cpp`、`syncd_main.cpp` 到 `Syncd` 主循环，按 ASIC_DB 中 `ASIC_STATE` 表的命令码分派到 `processQuadEvent()`、`processOidCreate()` 等函数，经 `VendorSai` 的函数指针表调用厂商 SAI API 编程 ASIC，并通过 `FlexCounter`、`SwitchNotifications/NotificationHandler` 把对象视图、链路状态与计数回写到 ASIC_STATE、STATE_DB 与 COUNTERS_DB。VID/RID 映射由 `VirtualOidTranslator.cpp`、`SaiSwitch.cpp` 维护，供 warm reboot 恢复使用。图 07-04-01 与目录清单表是回查索引；三条纪律贯穿全篇——厂商 SAI 实现不在本快照、ASIC_DB 有对象不等于芯片已生效、DB 编号与表名须核验。
