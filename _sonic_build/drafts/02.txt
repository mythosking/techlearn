# SONiC 技术资料 · 02 编译与构建

## 02-01 源码获取、多仓结构与子模块依赖矩阵

### 1. 背景与动机

编译 SONiC 之前最先遇到的障碍往往不是某条命令，而是「代码到底在哪里、彼此什么关系」。与多数「一个仓库一个 `main()`」的开源项目不同，SONiC 的源码以主仓加若干子仓、再叠加 git 子模块的多层结构组织：事实锚点 `upstream_src/` 下有八个子仓，每个子仓解压后又各自带一层 `xxx-master/` 归档目录，真实仓库根形如 `upstream_src/sonic-buildimage/sonic-buildimage-master/`。如果读者把 `upstream_src/` 当成单一源码树、或把某个子模块误认成主仓文件，那么后续读 `Makefile`、`rules/` 与 `dockers/` 时会产生系统性错位。本篇的动机就是先把这张地图画准，再讲清子模块依赖矩阵从哪里核验（模块见 07-01 ｜ 模块见 07-13）。

第二个动机来自「依赖从哪里来」这个具体问题。SONiC 构建时引用的组件 far 不止本快照里的八个子仓：路由协议栈 FRR、Linux 内核、厂商 SAI 实现、`sonic-swss-common` 等都以 git 子模块或外部仓库形式参与，但其中相当一部分源码并不在本快照。主仓根目录的 `.gitmodules` 声明了子模块名、`path` 与 `url`，`validated-submodule-commits` 则把每个子模块钉在某个提交上。理解「声明」与「实际快照内容」的差别，是避免写成「所有这些组件都在本快照」的关键。凡本快照未包含的，一律写「不在本快照，需对照实际版本核验」（字段见 05-01 ｜ 参数见 04-01）。

第三个动机是给后续构建实战建立正确的预期。`make` 在 SONiC 里不是「编译一个可执行文件」，而是「驱动一套分层构建系统产出可安装的 ONIE 镜像」：顶层 `Makefile` 把目标转交 `Makefile.work`，后者在 `sonic-slave-*/` 构建容器内调用 `slave.mk`，`slave.mk` 再 include `rules/` 下数百个 `.mk` 与 `.dep` 规则。这条链路的每个环节都建立在本篇所述的目录与依赖结构之上。把结构讲清楚，02-02 才能顺利展开构建系统，02-03 的实战才不会在「路径拼错、子模块没拉全」上卡住。版本基准统一为「上游 master 快照（2026-11 抓取）」，不写绝对版本号（原理见 06-01 ｜ 原理见 06-13）。

### 2. 核心概念

第一组概念是「子仓」与「真实仓库根」。子仓指 `upstream_src/` 下并列的八个独立 git 仓库：`sonic-buildimage`、`sonic-swss`、`sonic-sairedis`、`sonic-utilities`、`sonic-mgmt-common`、`sonic-platform-common`、`sonic-py-swsssdk`、`sonic-dbsyncd`。「真实仓库根」则是每个子仓内部的 `xxx-master/` 归档目录，例如主仓的 `sonic-buildimage/sonic-buildimage-master/`。本套资料所有源码路径都相对这个真实根书写，拼接时可写成 `upstream_src/<子仓>/<子仓>-master/`。把归档层写漏，是新人最常见的路径错误。

第二组概念是「git 子模块」。子模块是嵌在主仓里的独立 git 仓库，由主仓根 `.gitmodules` 声明，每个条目含 `submodule "<名>"`、`path = <路径>`、`url = <地址>`。例如快照里可核验到 `submodule "sonic-sairedis"` 的 `path = src/sonic-sairedis`，`submodule "sonic-swss"` 的 `path = src/sonic-swss`，`submodule "sonic-swss-common"` 的 `path = src/sonic-swss-common`，以及 `submodule "sonic-linux-kernel"`、`submodule "src/sonic-frr/frr"` 等。子模块让主仓能精确引用外部组件的版本，但「声明存在」不等于「快照内含其代码」：`sonic-linux-kernel` 与 `src/sonic-frr/frr` 等虽在 `.gitmodules` 中声明，其源码仍属「不在本快照，需对照实际版本核验」的范畴。

第三组概念是「依赖钉定」。`validated-submodule-commits` 文件逐行给出子模块名与对应的提交哈希，形如 `src/sonic-sairedis=<提交>`、`src/sonic-swss=<提交>`、`buildimage=<提交>`，是构建可复现性的锚点。本套资料不抄写这些哈希当作版本号（版本基准统一为上游快照），只需知道「子模块版本由此类文件约束、具体值需对照实际版本核验」。第四组概念是「构建产物的分层目录」：`target/debs/<bldenv>/`、`target/files/<bldenv>/`、`target/python-wheels/<bldenv>/`、`target/` 下的 `docker-*.gz` 与 ONIE `.bin` 分别对应不同类型产物，这些在 02-02 展开。

还需区分「获取源码」与「快照核验」两种用途。本篇描述的子模块初始化命令面向从上游 git 拉取完整源码树的场景；而本套资料的写作事实锚点是已经解压好的 `upstream_src/` 快照，二者不可混用：前者需要联网并拉全子模块，后者只需要读取快照里已存在的目录。若为了核验字段而去执行拉取命令，反而可能把「上游最新代码」误当成本快照内容，违反版本基准。正确做法是先确认目标路径在 `upstream_src/<子仓>/<子仓>-master/` 下真实存在，再用读取工具核实其中文件名与变量。上述机制与字段的随查见（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-13 ｜ 模块见 07-01）。

与「源码获取与依赖钉定」直接相关的文件有三处。其一是主仓根的 `.gitmodules`，逐条声明子模块的 `path` 与 `url`，可核验到 `src/sonic-swss-common`、`src/sonic-sairedis`、`src/sonic-swss`、`src/sonic-dbsyncd`、`src/sonic-utilities`、`src/sonic-platform-common`、`src/sonic-mgmt-common`、`src/sonic-py-swsssdk` 等条目，以及 `src/sonic-frr/frr`、`src/sonic-linux-kernel` 这类源码不在本快照的声明。其二是主仓根的 `validated-submodule-commits`，把子模块钉到具体提交，是版本可复现的依据。其三是 `Makefile.work` 的 `init` 目标，其内容为 `git submodule update --init --recursive` 并对子模块 `.git` 指针做相对化修正，这是从干净克隆拉取全部子模块的实际入口（模块见 07-01 ｜ 参数见 04-01）。

主仓 `sonic-buildimage-master/` 顶层按职责可分几簇：构建总控有 `Makefile`、`Makefile.work`、`Makefile.cache`、`slave.mk`、`functions.sh`；镜像装配有 `build_image.sh`、`build_docker.sh`、`build_debian.sh`、`onie-image.conf`、`onie-mk-demo.sh`、`installer/`；构建容器有 `sonic-slave-bookworm/`、`sonic-slave-trixie/`、`sonic-slave-bullseye/`、`sonic-slave-buster/`、`sonic-slave-stretch/`、`sonic-slave-jessie/`；规则与容器定义有 `rules/`、`dockers/`（本快照可核验到 59 个 `docker-*` 目录）；平台与机型有 `platform/` 与 `device/`（后者含三十余个厂商目录，如 `device/tencent/`、`device/mellanox/` 等）；开机配置与测试有 `files/image_config/`、`src/sonic-config-engine/`、`scripts/`、`tests/`。`FRR / FRRouting`、`Linux 内核`、`厂商 SAI 实现`与 `sonic-swss-common` 的源码不在本快照，相关字段与版本需对照实际版本核验（模块见 07-10 ｜ 模块见 07-13）。

### 4. 关键流程与调用链

从拿到源码到形成可构建源码树的过程，本质是「选对仓库根、拉全子模块、确认钉定版本」三步，其依赖关系见图 02-01-01。

node b "sonic-buildimage<br/>真实仓库根" purple
node c ".gitmodules<br/>子模块声明" teal
node d "validated-submodule<br/>-commits 钉定" teal
node e "src/ 外部组件<br/>FRR 内核等" gray
node f "rules/*.mk<br/>*.dep 依赖" teal

edge b -> f "规则依赖"
edge f -> g "容器内构建"

edge h -> i "封装"
:::

图 02-01-01 用颜色区分了语义：blue 为源码输入、purple 为主仓控制中枢、teal 为配置管理与依赖声明、gray 为不在本快照的外部组件、green 为构建容器运行时、amber 为编译产物、red 为硬件边界。需要强调的是 `.gitmodules` 到 `src/ 外部组件` 这条边：它表示「声明指向外部仓库」，而非「本快照已含其代码」；`FRR`、`Linux 内核`、`厂商 SAI` 均属此类，撰写时一律写「不在本快照，需对照实际版本核验」。

从操作流程看，第一步是取得主仓并进入真实仓库根，第二步执行子模块初始化（对应 `Makefile.work` 的 `init` 目标），第三步用 `validated-submodule-commits` 或 `make showtag` 一类手段核对版本，第四步才进入 02-02 的 `make configure` 与构建。这里有一个容易写反的因果：子模块必须先拉全，`rules/` 中的 `.dep` 依赖计算才能正确读取子模块内文件（例如 `docker-orchagent.dep` 用 `git ls-files` 枚举 `DPATH` 下文件做缓存键），否则依赖缓存会失真（原理见 06-13 ｜ 模块见 07-01）。镜像与启动是更靠后的链：`Makefile` → `Makefile.work` → `sonic-slave-*/` → `build_image.sh` → ONIE 安装包，必须在 slave 容器内完成，普通主机裸 `make` 得不到可安装镜像（参数见 04-01 ｜ 原理见 06-13）。

### 5. 配置/命令/代码实例

本节只给源码获取所需的最小命令与最小文件片段，构建变量全集与命令全集分别见 04-01、04-05，本册不重列。先看一次典型的干净克隆与子模块初始化序列，命令格式与选项需对照实际版本核验。

```bash
git clone https://github.com/sonic-net/sonic-buildimage.git
cd sonic-buildimage
git checkout <目标提交>
make init
```

```text
示例输出，具体格式需对照实际版本核验（下列路径为格式示意）
Submodule 'src/sonic-sairedis' (...) registered for path 'src/sonic-sairedis'
Submodule 'src/sonic-swss' (...) registered for path 'src/sonic-swss'
Submodule 'src/sonic-swss-common' (...) registered for path 'src/sonic-swss-common'
Cloning into 'src/sonic-sairedis'...
Submodule path 'src/sonic-sairedis': checked out '<提交>'
Submodule path 'src/sonic-swss': checked out '<提交>'
```

逐行判读如下。第一行 `git clone` 取得主仓源码，实际使用时仓库地址与分支需对照实际版本核验，本套资料不写死具体提交或版本；进入 `sonic-buildimage` 即进入真实仓库根的父层，若快照结构为归档层形式则应进入 `sonic-buildimage-master/`。第二行 `git checkout <目标提交>` 用于把主仓切到待构建的确定提交，尖括号内容是占位说明而非可执行值，真实提交应以 `validated-submodule-commits` 或项目发布说明为准，需对照实际版本核验。第三行 `make init` 对应 `Makefile.work` 中的 `init` 目标，其真实内容是 `git submodule update --init --recursive` 并修正子模块 `.git` 指针，使容器内 git 能正确解析。输出段前两行 `Submodule ... registered for path` 表示 git 已根据 `.gitmodules` 注册相应子模块，`path` 与快照中可核验的 `src/sonic-sairedis`、`src/sonic-swss`、`src/sonic-swss-common` 一致；`Cloning into` 行表示正在拉取子模块内容；末两行 `checked out '<提交>'` 表示子模块已检出到钉定提交，尖括号占位处需对照实际版本核验。若某子模块显示为 `-` 前缀或报 `fatal: not a git repository`，通常是子模块未拉全或处于 worktree 构建未做 gitdir 修正，应回看 `Makefile.work` 中 worktree 相关处理；若输出中缺少 `src/sonic-sairedis` 等关键子模块，则后续 `rules/` 依赖计算会失真（原理见 06-13 ｜ 模块见 07-01）。输出块已注明示例输出与版本核验要求，占位符不得当作真实值引用。

再看最小文件片段：从 `.gitmodules` 与 `validated-submodule-commits` 中各取可核验的条目形态，展示「声明」与「钉定」如何分工。

```text
[submodule "sonic-sairedis"]
	path = src/sonic-sairedis
	url = https://github.com/sonic-net/sonic-sairedis
[submodule "sonic-swss-common"]
	path = src/sonic-swss-common
	url = https://github.com/sonic-net/sonic-swss-common
```

```text
src/sonic-sairedis=<提交>
src/sonic-swss=<提交>
src/sonic-swss-common=<提交>
```

第一段是 `.gitmodules` 的真实条目形态：`submodule "sonic-sairedis"` 给出逻辑名，`path = src/sonic-sairedis` 给出在主仓内的落位，`url` 给出上游地址；`sonic-swss-common` 条目同理。第二段来自 `validated-submodule-commits`，`src/sonic-sairedis=<提交>` 一类行把子模块钉到具体提交，尖括号处为占位说明，真实提交值需对照实际文件核验、本套资料不抄写。两段对照即可看出：`.gitmodules` 回答「有哪些子模块、放在哪、来自哪」，`validated-submodule-commits` 回答「每个子模块定在哪个版本」，前者是结构声明、后者是可复现性的版本钉定，二者缺一不可（字段见 05-01 ｜ 参数见 04-01）。

### 6. 注意事项、陷阱与最佳实践

第一类是路径陷阱。最常犯的是把 `upstream_src/` 当成单一源码根、或把 `sonic-buildimage-master/` 这一归档层写漏。必须反复确认：真实仓库根是 `upstream_src/<子仓>/<子仓>-master/`，本文所有路径都相对它书写；把路径写错会导致 `Makefile`、`rules/`、`dockers/` 全部定位失败。第二类是「声明与内容混淆」陷阱：`.gitmodules` 声明了 `src/sonic-frr/frr`、`src/sonic-linux-kernel`、`src/sonic-swss-common` 等子模块，但这不等于本快照包含其源码；涉及 FRR、Linux 内核、厂商 SAI 实现与 `sonic-swss-common` 的内容一律写「不在本快照，需对照实际版本核验」，不得据声明编造文件与字段（模块见 07-05 ｜ 模块见 07-08）。

第三类是版本陷阱。禁止编造具体版本号或把 `validated-submodule-commits` 里的提交哈希写成「本套版本号」；版本基准统一为「上游 master 快照（2026-11 抓取）」，具体版本以对应构建文件为准、需对照实际版本核验。第四类是可复现性陷阱：子模块未拉全就构建，会使 `rules/*.dep` 用 `git ls-files` 计算缓存键时读取不到子模块文件，导致增量缓存命中错误；因此「先 `make init`、再核对钉定、最后构建」的顺序不可颠倒（原理见 06-13 ｜ 模块见 07-01）。

第五类是多仓边界陷阱。本快照是主仓加七个子仓，不是单一仓库；`dockers/` 下没有名为 `docker-syncd` 的目录，`syncd` 主体在 `sonic-sairedis/syncd/`，而 `platform/vs/` 下的 `docker-syncd-vs` 属虚拟交换机专用，二者不可混写；`sonic-sairedis/SAI/` 在本快照是空目录，不得据它编造头文件与属性。第六类是构建依赖陷阱：构建依赖 `sonic-slave-*/` 容器与 ONIE 安装器（`onie-image.conf`、`installer/`），`make` 在 slave 容器内运行并产出 ONIE 安装包，普通主机裸 `make` 得不到可安装镜像；`warmrestart/`、多 ASIC 与 chassis 能力受平台与版本限制，需对照实际版本核验，一切性能、容量、收敛、时延数字标注「需在目标机型实测」（参数见 04-01 ｜ 基准方法见 08-01）。

最佳实践可归纳为四条：其一，读任何路径前先确认它位于 `upstream_src/<子仓>/<子仓>-master/` 下，写路径时带上可定位目录；其二，把「子仓」「真实仓库根」「git 子模块」「validated 钉定」四个概念分开表述，不把外部组件写成本快照内文件；其三，引用他册内容统一用（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx），本篇涉及的构建变量写「参数见 04-01」、结构索引写「字段见 05-01」、容器编排写「原理见 06-13」、顶层构建模块写「模块见 07-01」，不在本册展开字段表与变量全集；其四，对快照内无法核实的内容宁可写「需对照实际版本核验」并给出目录，也不补值。

### 7. 小结与延伸阅读

本篇确立了编译 SONiC 前的源码基线：`upstream_src/` 下是八个并列子仓，每个子仓内的 `xxx-master/` 才是真实仓库根；主仓根 `.gitmodules` 声明子模块的 `path` 与 `url`，`validated-submodule-commits` 把子模块钉到具体提交，`Makefile.work` 的 `init` 目标负责递归拉取；FRR、Linux 内核、厂商 SAI 实现与 `sonic-swss-common` 等虽被声明或引用，其源码不在本快照，需对照实际版本核验。图 02-01-01 与两张表格把「子仓地图」与「声明／钉定分工」固定为后续各篇回查的索引。

## 02-02 构建系统全解：Makefile / slave.mk / rules / sonic-slave 容器

### 1. 背景与动机

如果说 02-01 解决的是「代码在哪」，那么 02-02 要解决的是「这些代码如何变成一台交换机能安装的镜像」。SONiC 的构建系统不是单个 Makefile，而是一套分层的、以容器为边界的装配线：顶层 `Makefile` 负责按目标分发到不同基础发行版，`Makefile.work` 负责在宿主机上准备构建环境并拉起 `sonic-slave-*/` 容器，`slave.mk` 在容器内部汇总全部构建目标，`rules/` 下数百个 `.mk` 与 `.dep` 文件逐个声明「某个 deb、某个 docker 镜像、某个安装包如何产出」。把这条链拆开讲清，是理解「为什么不能裸 `make` 出镜像」「为什么改一个规则会触发一大片重建」的前提（模块见 07-01 ｜ 原理见 06-13）。

第二个动机是「可复现性」。镜像版本字符串、构建时间、提交号都由构建过程生成，`functions.sh` 的 `sonic_get_version()` 用 `git describe` 与 `BUILD_TIMESTAMP` 计算版本，`Makefile.work` 又用 `SOURCE_DATE_EPOCH` 与slave 镜像的 `sha1sum` 标签保证同源码可产出一致的构建产物。因此构建系统天然与「具体版本号」解耦——本套资料据此统一写「上游 master 快照（2026-11 抓取）」，不抄写任何具体版本字样。理解版本由构建生成，有助于避免把构建文件里的数字误当成资料的版本基准（参数见 04-01 ｜ 字段见 05-01）。

第三个动机是「隔离与边界」。全部构建都在 `sonic-slave-*/` 容器内进行：容器内建用户、挂源码、装构建工具、跑 dpkg 与 docker 构建，宿主机只负责调度与挂载。这种设计让不同发行版（jessie、stretch、buster、bullseye、bookworm、trixie）的构建互不污染，也带来一组特殊的失败面——容器拉取、代理与子网、overlay 模块、`j2` 依赖、root 用户禁用等。本篇在讲清链路的同时，会把这些边界写进陷阱与最佳实践，为 02-03 的实战排错打底（原理见 06-13 ｜ 模块见 07-11）。

还需分清「构建期」与「运行期」两件事，避免把本册与后续册混为一谈。本篇关心的是如何把源码编成 ONIE 安装包，产物落位在 `target/`；而镜像安装到设备后，`files/image_config/` 如何开机写库、`supervisord` 如何按依赖拉起容器、配置如何沿 `CONFIG_DB` → `APPL_DB` → `ASIC_DB` → SAI 异步下发，都是运行期话题，分别归 06-13、02-04 与 06 全册。构建成功只说明产物已生成，不等于设备上电后各容器与流水线必然正常，这两类结论不可互相替代（原理见 06-01 ｜ 模块见 07-11）。

### 2. 核心概念

第一组概念是「三层 Makefile 总控」。`Makefile` 顶部的 `NOJESSIE`、`NOSTRETCH`、`NOBUSTER`、`NOBULLSEYE`、`NOBOOKWORM`、`NOTRIXIE` 开关决定为哪些基础发行版构建，快照中 `NOBOOKWORM=0`、`NOTRIXIE=0`，其余多为 `1`，即默认构建 bookworm 与 trixie。它的 `%::` 通配目标把任意目标转交给 `Makefile.work`（带 `BLDENV`），并用 `./scripts/run_with_retry $(MAKE)` 做重试，最后执行 `docker-cleanup`。`Makefile.work` 是真正的「宿主机侧装配器」：它检查非 root 用户、`j2` 工具与 Docker 版本（快照要求不低于 17.06.1），按 `BLDENV` 选择 `SLAVE_DIR`（如 bookworm 对应 `sonic-slave-bookworm`），由 `Dockerfile.j2` 渲染出 `Dockerfile`，计算 slave 基础镜像标签，最后 `docker run` 进入容器执行 `make -f slave.mk`。`slave.mk` 则在容器内汇总目标清单。

第二组概念是「目标清单与规则 include」。`slave.mk` 定义 `SRC_PATH = src`、`RULES_PATH = rules`、`TARGET_PATH = target`、`DOCKERS_PATH = dockers` 等路径，用 `BLDENV := $(shell lsb_release -cs)` 取得容器内发行版代号，据此规划 `target/debs/<bldenv>/`、`target/files/<bldenv>/` 等产物目录。它的关键动作是 `include $(RULES_PATH)/config`、负包含的 `config.organization`、`config.user`、`include $(RULES_PATH)/functions`、`include $(RULES_PATH)/*.mk`，再 include 平台自己的 `rules.mk`。也就是说，`rules/` 下每个 `.mk` 都向 `SONIC_TARGET_LIST` 追加目标，`slave.mk` 只是把这张清单汇总起来。

第三组概念是「`.mk` 与 `.dep` 的分工」。`.mk` 文件声明目标属性：以 `rules/docker-orchagent.mk` 为例，它定义 `DOCKER_ORCHAGENT_STEM`、`DOCKER_ORCHAGENT = $(...).gz`，用 `_DEPENDS` 追加依赖 deb，用 `_PATH` 指向 `dockers/docker-orchagent`，用 `_LOAD_DOCKERS` 指定底层 layer，把镜像登记进 `SONIC_DOCKER_IMAGES`、`SONIC_INSTALL_DOCKER_IMAGES`，再以 `_RUN_OPT`、`_BASE_IMAGE_FILES`、`_FILES` 描述运行时挂载与文件。`.dep` 文件则负责依赖与缓存键：`rules/docker-orchagent.dep` 用 `git ls-files $(DPATH)` 枚举源码文件，设 `_CACHE_MODE := GIT_CONTENT_SHA`，并用 `add_dbg_docker` 关联调试镜像。简言之，`.mk` 管「怎么建、建成什么」、`.dep` 管「何时算过期」。

第四组概念是「缓存与调试的入口」。`slave.mk` 还会 include `Makefile.cache`，配合 `rules/config` 中的 `SONIC_CONFIG_BUILD_JOBS`、`SONIC_CONFIG_MAKE_JOBS` 等并行度设置调节构建开销；主仓根另有 `README.buildsystem.md`、`README.dpkg-cache.md` 等说明文档，以及 `docker-base.dep`、`docker-config-engine.dep` 一类基础层规则。这些机制决定了「改一处规则是否触发全量重建」，是 02-05 调试构建与 CI 产物形态的直接前置，本篇只点名其位置、不展开变量取值。上述对象与变量的字段随查见（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-13 ｜ 模块见 07-01）。

### 3. 关键数据结构与源码位置

本节只点名文件、变量与产物目录并给出可定位路径，不展开字段表与参数全集（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-13 ｜ 模块见 07-01）。下表把构建系统按层次列出，路径均相对主仓真实仓库根 `sonic-buildimage/sonic-buildimage-master/`。

| 层次 | 关键文件 / 变量 | 作用 |
|---|---|---|
| 顶层分发 | `Makefile`、`%::`、`NO*_` 开关 | 按发行版把目标转交 Makefile.work |
| 宿主机装配 | `Makefile.work`、`DOCKER_RUN`、`SONIC_BUILD_INSTRUCTION` | 校验环境、拉起 slave 容器 |
| 容器内总控 | `slave.mk`、`SONIC_TARGET_LIST`、`RULES_PATH` | include 规则并汇总全部目标 |
| 规则声明 | `rules/*.mk`、`rules/*.dep`、`rules/config` | 声明目标属性、依赖与缓存键 |
| 镜像装配 | `build_image.sh`、`build_docker.sh`、`functions.sh` | 产出 ONIE / KVM / docker 镜像 |
| 构建容器 | `sonic-slave-bookworm/Dockerfile.j2` 等 | 定义各发行版构建环境 |

与「总控链路」直接相关的对象分三处。其一是 `Makefile` 的 `%::` 通配目标与 `make_work` 宏：前者把任意目标按发行版转交 `Makefile.work`，后者被 `configure`、`clean`、`sonic-slave-build` 等目标复用；`freeze` 目标调用 `scripts/versions_manager.py freeze`。其二是 `Makefile.work` 的 `SONIC_BUILD_INSTRUCTION`，它是一条很长的 `make -f slave.mk VAR=...` 调用，把 `PLATFORM`、`BUILD_NUMBER`、`SONIC_IMAGE_VERSION`、`SLAVE_TAG`、各 `INCLUDE_*` 特性开关、代理变量等逐项传入容器内的 `slave.mk`；其 `%:: | sonic-build-hooks` 目标先构建构建钩子，再按 `SONIC_SLAVE_BASE_BUILD` 准备基础镜像，最终 `docker run` 进来执行 `su $(USER) -c '... make -f slave.mk $@ ...'`。其三是 `slave.mk` 的 `configure` 目标，它建立 `target/debs/`、`target/files/`、`target/python-wheels/` 等目录并写入 `.platform` 与 `.arch`，这是落 `PLATFORM` 的实际动作（参数见 04-01 ｜ 模块见 07-01）。

镜像装配侧的对象也有固定落位。`build_image.sh` 读取 `onie-image.conf`，按 `IMAGE_TYPE` 分支处理 `onie`、`raw`、`kvm`、`aboot`、`dsc`、`bfb`：`onie` 分支调用 `generate_onie_installer_image()`，后者整理 `installer/platforms/` 并调用 `onie-mk-demo.sh`；`kvm` 分支调用 `generate_kvm_image()`，并可按 `BUILD_MULTIASIC_KVM` 生成 4 ASIC 与 6 ASIC 镜像。`build_docker.sh` 用 `getopts` 解析 `-i`、`-t`，以 `dockers/$1` 为构建目录执行 `docker build --no-cache`。`functions.sh` 提供 `trap_push`、`warn`、`die`、`docker_try_rmi` 与 `sonic_get_version()`。产物形态由 `onie-image.conf` 决定：默认 `ONIE_IMAGE_PART_SIZE=32768`、`TARGET_PLATFORM=x86_64`、`TARGET_MACHINE=generic`，`OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin`，另有 raw、kvm、aboot、dsc 等输出名（参数见 04-01 ｜ 模块见 07-11）。`platform/vs/` 下则有 `docker-syncd-vs.mk`、`docker-gbsyncd-vs.mk`、`one-image.mk`、`onie.mk` 等虚拟交换机专用规则，注意与 `dockers/` 下的通用容器区分（模块见 07-10）。

把链路展开成时序，可归纳为六步：其一，用户执行 `make configure PLATFORM=<平台>`，顶层 `Makefile` 的 `%::` 按发行版转交 `Makefile.work`；其二，`Makefile.work` 校验非 root、检查 `j2` 与 Docker 版本，按 `BLDENV` 选 `SLAVE_DIR`，用 `j2 $(SLAVE_DIR)/Dockerfile.j2` 生成 `Dockerfile` 并计算 slave 镜像标签；其三，`SONIC_SLAVE_BASE_BUILD` 通过 `docker inspect` 判断基础镜像是否存在，不存在则构建或从 registry 拉取；其四，`docker run` 挂载源码进 `/sonic`，在容器内建用户并 `su` 到该用户执行 `make -f slave.mk`；其五，`slave.mk` include 全部规则，按依赖产出各类 deb、wheel 与 docker 镜像；其六，`build_image.sh` 把这些产物封装成 ONIE / KVM 等镜像。任何一步失败的表象都不同，但定位顺序应沿图 02-02-01 逐段推进，而不是一上来怀疑源码（参数见 04-01 ｜ 排障见 08-03）。

### 5. 配置/命令/代码实例

本节只给构建入口的最小命令与最小规则片段，构建变量全集与命令全集分别见 04-01、04-05，本册不重列。先看一次典型的配置与容器准备序列，命令与选项需对照实际版本核验。

```bash
make configure PLATFORM=vs
make showtag
make sonic-slave-build
```

```text
示例输出，具体格式需对照实际版本核验（下列标签为格式示意）
+++ Making configure +++
+++ Making showtag +++
sonic-slave-bookworm:<标签>
+++ Making sonic-slave-build +++
Image sonic-slave-bookworm:<标签> not found. Building...
```

逐行判读如下。第一行 `make configure PLATFORM=vs` 进入 02-01 所述的源码根后执行，`PLATFORM=vs` 表示选择虚拟交换机平台，对应 `platform/vs/` 目录；顶层 `Makefile` 的 `%::` 会把 `configure` 转交 `Makefile.work`，而 `slave.mk` 的 `configure` 目标负责建 `target/` 下各目录并写 `.platform`、`.arch`，平台取值与目录是否匹配是后续能否找到 `rules.mk` 的前提，需对照实际版本核验。第二行 `make showtag` 对应 `Makefile.work` 的 `showtag` 目标，输出形如 `sonic-slave-<发行版>:<标签>`，标签由 Dockerfile、sources.list 与版本文件做 `sha1sum` 得出，用于判断 slave 基础镜像是否需要重建。第三行 `make sonic-slave-build` 触发 `Makefile.work` 中同名目标，其前置依赖 `sonic-build-hooks` 会先构建构建钩子。输出段首两行 `+++ Making ... +++` 是顶层与各层 Makefile 的回显，表明目标已被正确转交；`sonic-slave-bookworm:<标签>` 是 `showtag` 打印的镜像名与标签，尖括号占位需对照实际版本核验，不得当作真实标签引用；末行 `Image ... not found. Building...` 来自 `SONIC_SLAVE_BASE_BUILD`，说明本地与 registry 均无该标签镜像、开始构建 slave 基础镜像。若出现 `Add your user account to docker group ... root or sudo are not supported`，说明用 root 执行了 make，这是 `Makefile.work` 的显式拒绝；若报 `Please install j2`，说明缺少 jinjanator；若报 `requires Docker version ... or later`，说明宿主机 Docker 版本过低。以上三类属于环境前置问题，应先按图 02-02-01 的第一段修复，再继续构建（原理见 06-13 ｜ 排障见 08-03）。输出块已注明示例输出与版本核验要求，占位符不得当作真实值引用。

再看最小规则片段，取自 `rules/docker-orchagent.mk` 与 `rules/docker-orchagent.dep`，展示 `.mk` 与 `.dep` 如何分工。

```text
$(DOCKER_ORCHAGENT)_DEPENDS += $(SWSS) $(LIB_SONIC_DASH_API)
$(DOCKER_ORCHAGENT)_PATH = $(DOCKERS_PATH)/$(DOCKER_ORCHAGENT_STEM)
$(DOCKER_ORCHAGENT)_LOAD_DOCKERS += $(DOCKER_SWSS_LAYER_TRIXIE)
SONIC_DOCKER_IMAGES += $(DOCKER_ORCHAGENT)
SONIC_INSTALL_DOCKER_IMAGES += $(DOCKER_ORCHAGENT)
$(DOCKER_ORCHAGENT)_CONTAINER_NAME = swss
```

```text
DPATH       := $($(DOCKER_ORCHAGENT)_PATH)
DEP_FILES   := $(SONIC_COMMON_FILES_LIST) rules/docker-orchagent.mk rules/docker-orchagent.dep
DEP_FILES   += $(shell git ls-files $(DPATH))
$(DOCKER_ORCHAGENT)_CACHE_MODE  := GIT_CONTENT_SHA
$(eval $(call add_dbg_docker,$(DOCKER_ORCHAGENT),$(DOCKER_ORCHAGENT_DBG)))
```

第一段是 `.mk` 的真实条目形态：`_DEPENDS` 声明镜像依赖的 deb 包，`_PATH` 把构建上下文指向 `dockers/docker-orchagent`，`_LOAD_DOCKERS` 指定底层 layer，`SONIC_DOCKER_IMAGES` 与 `SONIC_INSTALL_DOCKER_IMAGES` 把镜像登记进待构建与待安装清单，`_CONTAINER_NAME = swss` 给出运行时容器名——注意镜像名是 `docker-orchagent`、容器名却是 `swss`，这是排障时按容器名查状态的依据。第二段来自 `.dep`：`DPATH` 取出 `.mk` 声明的路径，`DEP_FILES` 汇总公共文件、本规则文件与 `git ls-files` 枚举的源码，`_CACHE_MODE := GIT_CONTENT_SHA` 表示用 git 内容哈希做缓存键，`add_dbg_docker` 关联调试镜像。两段对照即可看出：`.mk` 定义「目标是什么、依赖什么、挂什么」，`.dep` 定义「哪些文件变化会让缓存失效」，这也是 02-05 调试构建与缓存的入口（模块见 07-02 ｜ 参数见 04-01）。

### 6. 注意事项、陷阱与最佳实践

第一类是环境与权限陷阱。`Makefile.work` 明确禁止 root 与 sudo 构建，要求把用户加入 docker 组后用普通用户执行；必须安装 `j2`（jinjanator），宿主机 Docker 版本不得低于快照要求（文件里写的是 17.06.1，具体需对照实际版本核验）；overlay 模块未加载时 `OVERLAY_MODULE_CHECK` 会失败，提示 `sudo modprobe overlay`。这几项是构建的第一道门槛，应先于任何源码修改排查（原理见 06-13 ｜ 排障见 08-03）。

第二类是「裸 make 出镜像」陷阱。必须反复确认：构建依赖 `sonic-slave-*/` 容器与 ONIE 安装器（`onie-image.conf`、`installer/`），`make` 在 slave 容器内运行并产出 ONIE 安装包，普通主机裸 `make` 得不到可安装镜像；`Makefile` 的 `%::`、`Makefile.work` 的 `DOCKER_RUN`、`sonic-slave-bookworm/Dockerfile.j2` 三者共同构成这条容器边界，任何把它写成「x86 主机直接编译即镜像」的表述都是错的（参数见 04-01 ｜ 模块见 07-11）。

第三类是依赖与缓存陷阱。规则里 `.dep` 用 `GIT_CONTENT_SHA` 与 `git ls-files` 计算缓存键，若子模块未拉全（见 02-01）或 `_DEPENDS` 写错，缓存命中会失真，表现为「改了源码却没有重建」；`Makefile.work` 的 `SONIC_SLAVE_REUSE_*` 变量允许复用已有 slave 基础镜像，但设置不当会在开启 DPKG 缓存写模式时被拒绝，需对照 `make showtag` 的输出谨慎使用。第四类是平台与特性陷阱：`PLATFORM` 必须与 `platform/<平台>/` 及 `device/` 下机型目录匹配，多 ASIC 与 chassis、KVM 多 ASIC 镜像受 `BUILD_MULTIASIC_KVM` 等开关与平台限制，能力受平台与版本限制、需对照实际版本核验，不得宣称全平台无条件支持（模块见 07-10）。

第五类是事实纪律与性能陷阱。构建文件里的 `_VERSION` 字样、tag、时间戳只作核验依据，不得抄进正文当作本套版本号；版本基准统一为「上游 master 快照（2026-11 抓取）」。FRR / FRRouting 协议源码、Linux 内核、厂商 SAI 实现与 `sonic-swss-common` 不在本快照，涉及部分写「不在本快照，需对照实际版本核验」；`platform/vs/` 下的 `docker-syncd-vs` 属虚拟交换机专用，与 `syncd` 主体在 `sonic-sairedis/syncd/` 不可混写。一切编译耗时、镜像体积、转发吞吐与收敛时延数字标注「需在目标机型实测」，调试构建不作生产基准（基准方法见 08-01 ｜ 调优见 08-02）。

最佳实践归纳为四条：其一，按图 02-02-01 的顺序定位失败发生在哪一段，再查对应文件——环境看 `Makefile.work`、目标看 `slave.mk`、属性看 `rules/*.mk`、缓存看 `*.dep`；其二，改动平台或特性开关前先 `make configure` 重新落 `.platform`/`.arch`，并用 `make showtag` 记录 slave 标签；其三，引用他册内容统一用（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx），本篇涉及的构建变量写「参数见 04-01」、对象字段写「字段见 05-01」、容器编排写「原理见 06-13」、顶层构建与镜像模块写「模块见 07-01」「模块见 07-11」，不在本册展开变量全集；其四，对快照内无法核实的内容宁可写「需对照实际版本核验」并给出可定位目录，也不补值。

### 7. 小结与延伸阅读

本篇把构建系统拆成可回查的四层：`Makefile` 的 `%::` 按发行版分发目标，`Makefile.work` 校验环境并拉起 `sonic-slave-*/` 容器，`slave.mk` 在容器内 include `rules/*.mk` 汇总 `SONIC_TARGET_LIST`，`.dep` 用 `GIT_CONTENT_SHA` 决定依赖是否过期；`build_image.sh` 依据 `onie-image.conf` 把 `target/` 下的 deb、wheel 与 docker 镜像封装成 ONIE 镜像。图 02-02-01 与层次表把这条链路固定为索引，三条纪律贯穿全篇——构建必须在 slave 容器内完成、版本由构建过程生成而非写死、缓存键来自 git 内容哈希。

## 02-03 从零构建实战：编译标准镜像与 ONIE 安装镜像

### 1. 目标与拓扑

本篇要完成一次可复现的闭环：在一台干净的 x86_64 构建主机上，从 `upstream_src/sonic-buildimage/sonic-buildimage-master/` 这个真实仓库根出发，配置目标平台、在 sonic-slave 容器内编译，产出能被 ONIE 安装器识别的 SONiC 镜像，并用 `platform/vs/` 虚拟交换机镜像做一次对照。先把两个名字说清楚：所谓“标准镜像”，指交给安装器的 `target/sonic-<machine>.bin` 安装包；所谓“ONIE 安装镜像”，是同一产物从安装器视角的叫法——本快照 `onie-image.conf` 里 `OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin` 给出的正是它（参数见 04-01）。还要先立一条纪律：SONiC 的“编译”不是编译某个可执行文件，而是由 `Makefile` 的 `%::` 通配目标把工作转交 `Makefile.work`、再按 `BLDENV` 进入不同 `sonic-slave-*/` 容器，把几十个上游组件、容器镜像与文件系统装配成一个可安装镜像（原理见 06-13 ｜ 模块见 07-01）。普通 x86 主机裸跑 `make` 得不到可安装镜像，这是本篇反复要守住的能力边界（字段见 05-09 ｜ 参数见 04-01 ｜ 原理见 06-13 ｜ 模块见 07-11）。

构建拓扑按职责可拆成四条主线。第一条是“配置面”：`make init` 拉取子模块、`make configure PLATFORM=...` 选定 ASIC 平台，二者把意图固化进构建配置，具体变量全集见 04-01，本篇只给最小必要命令。第二条是“容器面”：`README.buildsystem.md` 明确 `Makefile`、`slave.mk` 与 `sonic-slave/Dockerfile` 是构建后端，每个构建片段都在名为 sonic-slave 的容器里执行，首次构建会先在本机生成该镜像；本快照把容器按发行版拆成 `sonic-slave-bookworm/`、`sonic-slave-trixie/` 等目录，`Makefile` 默认的 `NOBOOKWORM=0`、`NOTRIXIE=0` 表示 bookworm 与 trixie 两条线参与构建，其余发行版默认关闭。第三条是“规则面”：`slave.mk` 与 `rules/` 下的 `.mk`/`.dep` 文件决定哪些目标被构建，`rules/config.user` 可持久设定并发与内存上限。第四条是“装配面”：`build_image.sh` 读取 `onie-image.conf`，调用 `onie-mk-demo.sh` 把文件系统、dockerfs 与引导组件打包为 ONIE 安装包，或按 `IMAGE_TYPE` 产出 raw / KVM 镜像（模块见 07-01 ｜ 模块见 07-11 ｜ 参数见 04-01）。

### 2. 前置条件与环境

第一项是源码与子模块。`README.md` 给出的顺序是：克隆仓库、`git checkout` 到目标分支、`make init`（克隆后或子模块更新后执行一次）、再 `make configure PLATFORM=[ASIC_VENDOR]`。`make init` 之所以必须，是因为 `sonic-buildimage-master/.gitmodules` 列出了子模块，本快照以多仓加归档层的形态提供源码，真实仓库根是 `upstream_src/<子仓>/<子仓>-master/`，任何路径都要按这个归档层去读（模块见 07-01）。本套资料的事实锚点是“上游 master 快照（2026-11 抓取）”，不写绝对版本号；构建产物的版本字符串由 `SONIC_IMAGE_VERSION` 等构建变量决定，具体取值需对照实际版本核验。

第二项是 Docker 与磁盘。`README.buildsystem.md` 说明首次构建会构建 sonic-slave 镜像，因此主机必须能正常运行 Docker；`build_image.sh` 里多处 `sudo`，说明构建脚本假定执行用户具备 sudo 权限。磁盘方面，`onie-image.conf` 的 `ONIE_IMAGE_PART_SIZE` 默认是 `32768`（32GB），`DOCKER_RAMFS_SIZE=3500M`，`RAW_IMAGE_DISK_SIZE=1700`、`KVM_IMAGE_DISK_SIZE=16`，这些量级意味着构建主机要预留足够空间，否则会在打包阶段报磁盘不足一类的错误。并发与内存的关系在 `README.md` 里有说明：每个并行 C++ 编译任务会占用数 GB 内存，官方建议用 `rules/config.user` 里的 `SONIC_BUILD_MEMORY` 限制容器内存，避免 OOM 波及宿主进程；`SONIC_BUILD_JOBS=4` 是多数场景经过验证的选择。具体数值随版本与机型变化，需对照实际版本核验（参数见 04-01）。

第三项是平台选择。`README.md` 列出的受支持 ASIC 供应商包括 `barefoot`、`broadcom`、`marvell-prestera`、`marvell-teralynx`、`mellanox`、`centec`、`nvidia-bluefield`、`vs`。其中 `PLATFORM=vs` 是虚拟交换机，不依赖真实 ASIC，最适合在没有硬件的环境里跑通整条构建链；`PLATFORM=broadcom` 等真实平台还需要对应厂商 SAI 实现，而这些实现是闭源且不在本快照的，因此真实平台的完整构建与性能表现需对照实际版本核验、需在目标机型实测（模块见 07-10 ｜ 参数见 04-01）。`PLATFORM` 的取值决定 `Makefile` 里的 `PLATFORM_PATH := platform/$(if $(PLATFORM),$(PLATFORM),$(CONFIGURED_PLATFORM))`，进而决定包含哪一组的 `.mk` 规则——这就是“配置面”落到“规则面”的接缝。

第四项是代理与网络。sonic-slave 容器内部要拉取 Debian 包、Python 依赖与上游源码，主机若处于需要 HTTP/HTTPS 代理的网络，代理设置需要在容器构建阶段就注入，否则表现为 apt 超时或 pip 拉不到包；这类问题属于构建环境而非源码缺陷，排障时先看容器网络再看规则。下表把本节涉及的关键前置项与核验要求归纳在一起，便于开工前逐项对照。

| 前置项 | 核验要点 | 本快照依据 | 说明 |
|---|---|---|---|
| 子模块 | 克隆后执行 `make init` | `.gitmodules` | 不执行会导致源码缺失 |
| Docker | 能构建并运行 sonic-slave 镜像 | `README.buildsystem.md` | 首次构建自动生成镜像 |
| sudo | 构建脚本多处 `sudo` | `build_image.sh` | 执行用户需有相应权限 |
| 磁盘 | 预留分区与镜像所需空间 | `onie-image.conf` | 分区默认 32768 MB |
| 平台 | 选择受支持的 PLATFORM 值 | `README.md` | `vs` 无需真实 ASIC |
| 网络 | 代理与源可达 | 容器构建阶段 | 失败先查容器网络 |

### 3. 分步操作

下面按“前置检查 → 执行 → 验证输出 → 清理”的闭环给出最小命令序列，全部在 `sonic-buildimage-master/` 仓库根执行。完整构建变量、变体组合与命令全集见 04-01，本册不重列；这里只保留跑通 vs 构建所必需的四步。

第一步，确认当前路径与平台目录存在，再初始化子模块。`PLATFORM=vs` 对应 `platform/vs/`，本快照该目录真实存在，且 `platform/vs/rules.mk` 中 `include $(PLATFORM_PATH)/one-image.mk`、`$(PLATFORM_PATH)/onie.mk`、`$(PLATFORM_PATH)/kvm-image.mk` 说明它具备 one-image、ONIE 与 KVM 三类目标的装配规则。确认无误后执行 `make init` 拉取子模块（参数见 04-01）。

第二步，配置平台。执行 `make configure PLATFORM=vs`。这一步把 `CONFIGURED_PLATFORM` 固化为 `vs`，使后续 `PLATFORM_PATH` 指向 `platform/vs/`。注意 `README.md` 要求 `make configure` 在克隆后只执行一次，切换平台应重新 configure；平台取值拼写错误会导致包含不到对应 `.mk`，表现为“目标没有规则”。

第三步，执行构建。用 `make SONIC_BUILD_JOBS=4 all` 启动全流程；若只需单个 ONIE 安装包，可用 `make target/sonic-vs.bin` 这类具体目标，产物名由 `OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin` 与 `TARGET_MACHINE` 共同决定，需对照实际版本核验。为了在受限内存主机上构建，可先写 `rules/config.user`（其被 `.gitignore` 忽略、可在变基后保留），放入 `SONIC_BUILD_MEMORY` 与 `SONIC_BUILD_JOBS` 等持久值；需要快速迭代时用 `BUILD_SKIP_TEST=y` 跳过测试（模块见 07-12 ｜ 参数见 04-01）。

第四步，验证与清理。用 `ls -lh target/` 确认产物存在并查看体积，用 `show version`（在启动后的设备上）核对平台与 HwSKU 字段；构建缓存问题可用 `make clean` 或对应的 `<target>-clean` 目标处理，例如 `README.md` 给出 `make target/debs/swss_1.0.0_amd64.deb-clean` 这一形式的清理目标，具体目标名需对照实际版本核验。

```bash
# 在 sonic-buildimage-master/ 仓库根执行
pwd
ls -d platform/vs
make init
make configure PLATFORM=vs
printf 'SONIC_BUILD_MEMORY = 24g\nSONIC_BUILD_JOBS = 4\n' > rules/config.user
make SONIC_BUILD_JOBS=4 all
ls -lh target/
```

上面示例输出中的省略号用于代表冗长的编译日志，不是正文占位；真实构建日志会持续输出各 `rules/*.mk` 目标，本块只示意首尾。逐行判读如下。第一行的 `pwd` 输出用于确认当前确实在 `sonic-buildimage-master/` 仓库根，若路径里多出或少掉一层归档目录，后面所有相对路径都会失效，这是最容易被忽略的起点错误。第二行 `platform/vs` 是 `ls -d` 的结果，证明所选平台目录存在；若此行为空，说明 `PLATFORM` 取值拼写有误或快照不完整，应回到 `README.md` 的受支持平台列表核对。`make init` 与 `make configure PLATFORM=vs` 的输出因版本而异，关键是看有无报错退出；`make configure` 失败往往意味着平台不被支持，后续 `make` 会因找不到规则而立即失败。`printf ... > rules/config.user` 写入持久配置，使后续构建不必每次在命令行重复并发与内存参数，该文件被 `.gitignore` 忽略、可跨变基保留。`make SONIC_BUILD_JOBS=4 all` 是主构建命令，首次运行会先构建 sonic-slave 镜像（对应日志中的 “sonic-slave-bookworm 镜像构建”），随后才进入各目标编译；日志中途出现大量编译输出属正常，不能据此判断失败。最后的 `total` 与两行文件是验证重点：`sonic-vs.bin` 是 `OUTPUT_ONIE_IMAGE` 对应的 ONIE 安装包，`sonic-vs.img.gz` 是 KVM 虚拟镜像的压缩产物，二者的体积量级仅为示意，实际大小随版本与配置变化，需在目标环境核验；若 `target/` 下没有 `sonic-vs.bin`，应回到 `build_image.sh` 的 `IMAGE_TYPE=onie` 分支与 `onie-image.conf` 的变量检查，而不是笼统归咎于硬件（参数见 04-01 ｜ 模块见 07-11）。

### 4. 验证方法与预期结果

验证分三层，对应“产物—安装—启动”。第一层是产物完整性：用 `ls -lh target/` 看 `sonic-vs.bin` 是否存在、体积是否落在合理量级；再用 `file` 或解压工具确认它是安装器可识别的镜像格式，本快照 `onie-mk-demo.sh` 会向安装包写入 ONIE 头并用 `unzip` 处理 `INSTALLER_PAYLOAD`，因此格式异常通常指向装配阶段而非编译阶段（模块见 07-11）。需要提醒的是，`target/` 下的具体文件名随 `TARGET_MACHINE` 与构建变量而变，本册示例的 `sonic-vs.bin` 需对照实际版本核验。

第二层是安装器行为。`build_image.sh` 里 `IMAGE_TYPE=onie` 时调用 `generate_onie_installer_image`，后者把 `onie-mk-demo.sh` 与 `installer/install.sh`、`platform_conf_file` 等一起打包；`installer/install.sh` 中的 `install_env` 区分 `onie`、`sonic`、`build` 三种环境，并做了 ASIC 类型一致性检查——若目标设备与镜像的 `platform_asic` 不匹配，会提示仍在安装的风险并等待确认。这一层在虚拟交换机上通常跳过（vs 无真实 ASIC），但在真实硬件上是关键校验点（参数见 04-01 ｜ 模块见 07-11）。

第三层是启动后的首屏。虚拟交换机镜像启动后，用 `show version` 核对平台与 HwSKU 字段，判断构建时选定的 `PLATFORM` 与加载的 `device/<vendor>/<hwsku>/` 目录是否一致。下面给出一组最小验证命令与示例输出。

```bash
show version
show interfaces status
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
SONiC Software Version: SONiC.HEAD.000000-00000000
Distribution: Debian GNU/Linux 12 (bookworm)
Platform: x86_64-generic-r0
HwSKU: sample-hwsku
ASIC: vs
Interface   Lanes        Speed   MTU   Alias        Oper  Admin
Ethernet1   25,26,27,28  200000  9100  Eth200GE0/1  up    up
```

逐行判读如下。前四行来自 `show version`：`SONiC Software Version` 是由 `SONIC_IMAGE_VERSION` 等构建变量生成的版本字符串，本套资料统一以“上游 master 快照（2026-11 抓取）”为基准，示例里的 `SONiC.HEAD.000000-00000000` 只是格式示意，不得当作真实版本号引用；`Distribution` 反映构建所用基础发行版，与 `sonic-slave-bookworm/` 等构建容器对应，需对照实际版本核验；`Platform` 与 `HwSKU` 共同指向 `device/<vendor>/<hwsku>/` 下的机型目录，是判断端口配置是否加载正确的锚点，若与 `make configure PLATFORM=vs` 的预期不一致，说明镜像或配置文件混用。第五行 `ASIC: vs` 是构建成功的直接证据之一，表明这是虚拟交换机镜像、转发由软件模拟，任何吞吐与时延数字都需在目标机型实测、不得外推到真实 ASIC。后两行来自 `show interfaces status`，列头 `Lanes`、`Speed`、`MTU`、`Alias`、`Oper`、`Admin` 的含义与 `device/tencent/x86_64-tencent_tcs8400-r0/config_db.TCS8400-24CC8CD.json` 中 `PORT` 表的 `lanes`、`speed`、`mtu`、`alias`、`admin_status` 字段可对应（表名与字段需对照实际版本核验，逐字段含义见 05 册）；`Oper` 与 `Admin` 同为 `up` 是正常特征，若 `Admin=up` 而 `Oper=down`，应按 `CONFIG_DB`、`APPL_DB`、`ASIC_DB`、`STATE_DB` 顺序逐段核对，而不是直接判定构建或硬件失败（原理见 06-01 ｜ 排障见 08-03）。这两条命令来自 `sonic-utilities-master/show/main.py`，属于“CLI 只读状态、不编程 ASIC”的典型体现（模块见 07-06）。

### 5. 常见失败与排错

第一类是 slave 容器相关失败。若首次构建卡在拉取基础镜像或 apt/pip 阶段，先确认 Docker 服务可用、代理已在容器构建阶段注入、主机可访问软件源；这类问题发生在进入 `Makefile.work` 之前，与 SONiC 规则无关。`README.buildsystem.md` 提供 `make sonic-slave-bash` 进入容器排查、`make sonic-slave-build` 在 `sonic-slave/Dockerfile` 更新后重建镜像两个入口，可用来把“容器环境”与“源码构建”两个层面分开定位（模块见 07-01 ｜ 参数见 04-01）。

第二类是平台与规则缺失。`make configure` 阶段若 `PLATFORM` 拼写错误，或 `make` 阶段提示某目标没有规则，通常是 `PLATFORM_PATH` 没有指向预期的 `platform/<平台>/`，导致 `rules.mk` 里 include 的 `.mk` 文件不对。此时应核对 `Makefile` 中 `PLATFORM_PATH` 的赋值、`platform/vs/rules.mk` 的 include 清单，以及 `README.md` 的受支持平台列表，不要凭印象补平台名。

第三类是磁盘与内存不足。`onie-image.conf` 的分区默认 32GB、dockerfs  ramfs 3500M 等量级决定了构建主机要有足够空间；`README.md` 建议用 `rules/config.user` 的 `SONIC_BUILD_MEMORY` 限制容器内存、用 `SONIC_BUILD_JOBS` 控制并发，原则是并发任务数乘以单任务内存再加基础开销不超过可用内存。若构建中途被 OOM 终止，先降并发再重试，而不是反复空跑（参数见 04-01）。

第四类是子模块与产物缺失。克隆后未执行 `make init` 会导致源码不全、编译报“找不到文件”；`target/` 下没有预期安装包时，应回到 `build_image.sh` 检查 `IMAGE_TYPE` 分支与 `onie-image.conf` 的 `OUTPUT_ONIE_IMAGE`、`TARGET_MACHINE` 等变量，产物名需对照实际版本核验。第五类是真实平台的厂商依赖：broadcom、mellanox 等平台的完整构建依赖闭源 SAI 实现，本快照不含这些实现，相关失败需对照实际版本核验、需在目标机型实测，不得据本快照推断（模块见 07-10 ｜ 模块见 07-04）。

排错的顺序建议固定为“容器环境 → 平台规则 → 资源（磁盘/内存）→ 子模块 → 产物命名 → 厂商依赖”，先排除环境与配置，再怀疑源码与硬件。所有示例输出均已注明需对照实际版本核验，排障时以本快照真实文件为准（字段见 05-09 ｜ 参数见 04-01 ｜ 原理见 06-13 ｜ 模块见 07-11）。

### 6. 小结

本篇把一次从零构建拆成配置面、容器面、规则面、装配面四条主线，给出 `make init` → `make configure PLATFORM=vs` → `make SONIC_BUILD_JOBS=4 all` → `ls -lh target/` 的最小闭环，并用 `show version`、`show interfaces status` 完成产物到启动的验证。图 02-03-01 标出了每一步的产出与边界：teal 是配置与规则、gray 是 Docker 构建容器、amber 是安装包与虚拟镜像、red 是安装与 ASIC 边界。三条纪律贯穿全篇：构建必须在 sonic-slave 容器内经 ONIE 安装器完成，普通主机裸 `make` 得不到可安装镜像；产物名、版本号、分区与内存参数随版本变化，一律需对照实际版本核验；真实平台的厂商 SAI 实现闭源且不在本快照，性能需在目标机型实测（字段见 05-09 ｜ 参数见 04-01 ｜ 原理见 06-13 ｜ 模块见 07-11）。

延伸阅读按目标分流：要理解 `Makefile`、`slave.mk`、`rules/` 的总控链路，接读 02-02 与 07-01；要把镜像在虚拟交换机上跑起来并做首屏配置，接读 03-01、03-02；要系统掌握平台与 HWSKU 适配，接读 02-04 与 07-10；构建变量全集、并发与变体组合见 04-01，CI 产物与调试构建见 02-05 与 07-12。跨册引用统一写作（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx），其中 `xx` 为具体篇号。最后重申资料纪律：路径均相对各子仓 `xxx-master/` 根，示例输出均注明“示例输出，具体格式需对照实际版本核验”，性能与容量结论均标注“需在目标机型实测”，版本基准统一为“上游 master 快照（2026-11 抓取）”。

## 02-04 平台适配：device/、platform/、SAI 与虚拟交换机 vs

### 1. 背景与动机

02-03 解决的是“怎么编出一个镜像”，但同一个构建系统要产出适配不同白盒交换机的镜像，靠的不是改编译代码，而是替换一组与机型、平台和数据面相关的文件。平台适配正是要回答：SONiC 如何用一套控制面代码，去驱动端口形态、ASIC 型号、外设组成各不相同的几十种白盒设备。这个问题的答案集中在两个目录与一层抽象上——`device/<vendor>/<hwsku>/` 描述“具体这台机器长什么样”，`platform/<平台>/` 描述“这一族平台如何被构建与承载”，SAI（Switch Abstraction Interface）则把“控制面如何驱动 ASIC”统一成一套与芯片无关的 API（模块见 07-10 ｜ 模块见 07-04）。

先给一个强烈的事实：本快照 `sonic-buildimage-master/` 下 `device/` 有数十个厂商目录（accton、arista、broadcom、cisco、dell、mellanox、tencent 等），`platform/` 有 alpinevs、broadcom、mellanox、barefoot、p4、vs、centec 等目录，而控制面代码（如 `orchagent/`）并不因机型而分叉。机型差异被隔离在配置与平台文件里，这正是白盒 NOS 能“一次构建、多机部署”的工程基础（原理见 06-12 ｜ 模块见 07-10）。若把机型差异写进控制面进程，容器化与跨厂商复用都会失效，这点是理解平台适配的前提。

动机还来自一个常见误读：把“虚拟交换机 vs”当成 SONiC 的真实转发形态。事实恰恰相反，`platform/vs/` 只是开发与测试用的虚拟形态，用软件模拟 ASIC，本册所有吞吐、时延、表项容量结论一旦基于 vs 得出，都必须标注“需在目标机型实测”，不能外推到真实硬件（原理见 06-01 ｜ 模块见 07-10）。本篇因此把真实 ASIC 平台与虚拟交换机 vs 放在同一张图里对照，明确哪些适配对真实硬件成立、哪些只是测试替身。事实锚点仍是“上游 master 快照（2026-11 抓取）”，厂商 SAI 实现闭源且不在本快照，涉及它的字段与版本一律写“需对照实际版本核验”（字段见 05-09 ｜ 参数见 04-02 ｜ 原理见 06-12 ｜ 模块见 07-10）。

### 2. 核心概念

第一组概念是“HWSKU 与设备目录”。`device/<vendor>/<hwsku>/` 是具体机型的配置仓库，本快照可核实的例子如 `device/tencent/x86_64-tencent_tcs8400-r0/`，其下有 `config_db.TCS8400-24CC8CD.json`、`default_sku`、`platform_asic`、`installer.conf`、`platform_env.conf`、`dev.xml` 等文件，以及以 SKU 命名的子目录（如 `TCS8400-24CC8CD/`）。`minigraph.xml` 在部分机型目录（如 `device/inventec/x86_64-inventec_d6254qs-r0/`、`device/micas/x86_64-micas_m2-w5000-48con2sfp-r0/`）可核实。这里要分清两层：`device/<vendor>/` 下的目录名（如 `x86_64-tencent_tcs8400-r0`）是平台标识，其中的 SKU 子目录与 `config_db*.json` 才是具体硬件配置（字段见 05-09 ｜ 参数见 04-02）。

第二组概念是“平台目录与构建规则”。`platform/<平台>/` 决定这一族平台在构建时包含哪些规则与目标。以本快照 `platform/vs/` 为例，`rules.mk` 通过 `include $(PLATFORM_PATH)/syncd-vs.mk`、`docker-syncd-vs.mk`、`docker-gbsyncd-vs.mk`、`one-image.mk`、`onie.mk`、`kvm-image.mk`、`raw-image.mk` 等文件组装目标，并用 `SONIC_ALL += $(SONIC_ONE_IMAGE) $(SONIC_KVM_IMAGE) $(DOCKER_SONIC_VS) $(SONIC_RAW_IMAGE)` 声明该平台的产物集合；`docker-syncd-vs.mk`、`docker-gbsyncd-vs.mk` 与 README 提到的 `create_vnet.sh` 一起构成虚拟交换机的数据面替身。真实平台如 `platform/broadcom/` 则包含 `docker-syncd-brcm.mk`、`docker-saiserver-brcm.mk` 等，指向厂商专用容器（模块见 07-11 ｜ 参数见 04-01）。

第三组概念是“SAI 与虚拟 SAI”。SAI 定义与芯片无关的转发表象 API，`orchagent` 只经 `ASIC_DB` 与 SAI 属性同 `syncd` 交互，不直接读写寄存器（原理见 06-05）。本快照 `sonic-sairedis-master/SAI/` 是空目录，实际头文件与厂商实现需对照实际版本核验；可核验的是 `meta/`（约 80 个文件，元数据）与 `vslib/`（虚拟 SAI 实现，如 `Context.cpp`、`Buffer.cpp`），后者正是 `platform/vs/` 能模拟 ASIC 的关键（模块见 07-04）。第四组是“平台外设基类”，`sonic-platform-common-master/sonic_platform_base/` 下有 `platform_base.py`、`chassis_base.py`、`psu_base.py`、`fan_base.py`、`sfp_base.py`、`thermal_base.py` 等，为 PSU、风扇、光模块、温度传感器等外设提供统一基类，是整机监控（pmon）的适配入口（模块见 07-09 ｜ 字段见 05-09）。

### 3. 关键数据结构与源码位置

本节只点名结构与文件落位，不展开逐字段定义——结构体字段统一放在 05 册，命令与参数全集放在 04 册，机制流程放在 06 册，模块能力放在 07 册，即（字段见 05-09 ｜ 参数见 04-02 ｜ 原理见 06-12 ｜ 模块见 07-10）。下表把平台适配涉及的关键目录、文件与可核实依据归纳在一起，路径均相对各子仓 `xxx-master/` 根，具体字段名与文件名需对照实际版本核验。

| 层次 | 关键目录/文件 | 作用 | 本快照可核实依据 |
|---|---|---|---|
| 机型配置 | `device/<vendor>/<hwsku>/` | 端口与设备元数据 | tencent、broadcom 等厂商目录实存 |
| 初始配置 | `config_db*.json`、`minigraph.xml` | 渲染 CONFIG_DB 初值 | 见 tencent、inventec 机型 |
| 平台规则 | `platform/<平台>/rules.mk` | 组装该平台构建目标 | `platform/vs/rules.mk` 实存 |
| 虚拟数据面 | `platform/vs/` | 模拟 ASIC 与 veth 拓扑 | create_vnet.sh、syncd-vs.mk 实存 |
| SAI 抽象 | `sonic-sairedis/SAI/`、`meta/`、`vslib/` | 接口、元数据、虚拟实现 | SAI 空目录、meta 约 80 文件 |

与“机型配置如何变成运行配置”相关的结构集中在 `src/sonic-config-engine/`：`minigraph.py`、`minigraph_ext.py`、`portconfig.py`、`sonic-cfggen` 负责把 `device/<vendor>/<hwsku>/minigraph.xml` 与端口配置渲成 `CONFIG_DB` 初值；`device/<vendor>/<hwsku>/` 下的 `config_db*.json` 是渲染结果或可直接落地的配置样例。这些文件与字段在 01-01、03-02 已点名，本篇不重列字段，只强调它们在平台适配中的位置：设备目录是“输入”，配置引擎是“翻译器”，`CONFIG_DB` 是“产物”（参数见 04-02 ｜ 字段见 05-09 ｜ 原理见 06-12）。

与“平台如何承载数据面”相关的结构在 `platform/`：`platform/vs/rules.mk` 的 include 清单决定虚拟交换机包含 syncd-vs、docker-sonic-vs、docker-gbsyncd-vs 等目标，`create_vnet.sh` 用 `ip netns`、`veth` 与 `nsenter` 在虚拟交换机容器与模拟服务器之间建立链路（脚本里 `SERVERS=2`，通过 `docker inspect` 取容器 PID）；`platform/broadcom/`、`platform/mellanox/`、`platform/barefoot/`、`platform/p4/` 等则包含各自 `docker-syncd-*.mk` 与 `docker-saiserver-*.mk` 规则。厂商 SAI 实现多为闭源且不在本快照，这部分只能给目录、不能给字段（模块见 07-11 ｜ 模块见 07-04）。

图 02-04-01 中 teal 为平台与机型配置，blue 为 `CONFIG_DB`，purple 为 `orchagent` 控制面，green 为 `syncd` 与 SAI 运行时，red 为厂商实现与 ASIC 硬件边界，gray 为虚拟交换机 vs。图里有两条值得注意的边：一条是 `platform/<ASIC>` 指向 `device/<vendor>/<hwsku>` 的“平台与 HWSKU 目录”，说明 `PLATFORM` 决定去哪个目录找机型文件；另一条是 `platform/vs` 分别指向 `syncd 与 SAI` 与 `device` 的“虚拟 SAI 模拟”“复用机型配置”，说明 vs 复用同一套控制面与配置渲染，只是把 SAI 换成 `vslib/` 的虚拟实现（原理见 06-12 ｜ 模块见 07-10）。红色边“厂商 SAI 实现 → ASIC 编程数据面”标注为不在本快照，是因为真实芯片编程发生在闭源实现里，本册只能给链路形态、不能给内部字段（原理见 06-05 ｜ 模块见 07-04）。

从调用链看，平台适配发生在两条不同的时序里。构建时序：`PLATFORM` 决定 `PLATFORM_PATH`，`platform/<平台>/rules.mk` 的 include 决定包含哪些 `docker-syncd-*.mk` 与镜像目标，最终产出带对应厂商数据面容器的安装镜像（原理见 06-13 ｜ 参数见 04-01）。运行时序：设备启动后由 `config_db*.json` / `minigraph.xml` 经 `src/sonic-config-engine/` 渲染出 `CONFIG_DB`，各 `*mgrd` 写入 `APPL_DB`，`orchagent` 消费后写 `ASIC_DB`，`syncd` 经 SAI 编程芯片——这条链在 06 册逐段展开，本篇只强调“机型差异被隔离在设备目录与平台目录，控制面代码不分叉”（原理见 06-01 ｜ 原理见 06-06 ｜ 模块见 07-03）。外设监控另有一条链：`sonic-platform-common/sonic_platform_base/` 的基类被各机型的具体实现继承，为 pmon 容器提供统一的 PSU、风扇、SFP 与温度读取接口，具体实现随厂商而变、需对照实际版本核验（模块见 07-09）。

### 6. 注意事项、陷阱与最佳实践

第一类是“把 vs 当真实转发”的定位陷阱。必须反复确认：`platform/vs/` 是开发与测试用的虚拟交换机，数据面由 `sonic-sairedis-master/vslib/` 的虚拟 SAI 模拟，控制面仍复用 `orchagent`、`syncd` 与同一套 `device/` 配置；除 vs 外 SONiC 不做软件转发，它是白盒交换机 NOS、数据面在 ASIC、控制面经 SAI 下发（原理见 06-01 ｜ 模块见 07-10）。据此得出的吞吐、时延、表项容量一律标注“需在目标机型实测”。

第二类是“厂商 SAI 与仓库边界”陷阱。本快照 `sonic-sairedis-master/SAI/` 是空目录，头文件与厂商实现需对照实际版本核验；`meta/`、`vslib/` 才是可核实的元数据与虚拟 SAI。厂商 SAI 实现多为闭源且不在本快照，不得据本快照编造其文件、属性与版本；`orchagent` 只经 `ASIC_DB` 与 SAI 属性同 `syncd` 交互，不直接操作硬件（原理见 06-05 ｜ 模块见 07-04）。同时 `dockers/` 下没有名为 `docker-syncd` 的目录，`syncd` 主体在 `sonic-sairedis/syncd/`，`platform/vs/docker-syncd-vs` 属虚拟交换机专用，二者不可混写。

第三类是“平台与机型目录”陷阱。不要写死平台列表或机型文件名：`PLATFORM` 的受支持取值见 `README.md`，`device/<vendor>/<hwsku>/` 的目录名与 `config_db*.json`、`minigraph.xml` 是否存在须逐机核验；`platform/<平台>/rules.mk` 的 include 清单决定该平台的构建目标，切换平台必须重新 `make configure` 并核对 `PLATFORM_PATH`（参数见 04-01 ｜ 模块见 07-11）。外设方面，`sonic-platform-common/sonic_platform_base/` 只提供基类，各机型的具体实现随厂商而变，需对照实际版本核验（模块见 07-09）。

第四类是配置与事实纪律陷阱。Redis DB 编号不是源码常量，须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 与运行时配置核验，禁止写死；“配置已写入”不等于“硬件已下发”，`config` 返回成功不代表 ASIC 编程完成，必须按 `CONFIG_DB`、`APPL_DB`、`ASIC_DB`、`STATE_DB` 顺序逐段核对（原理见 06-01 ｜ 排障见 08-03）。`warmrestart/`、多 ASIC 与 chassis 能力（如 `chassisorch.cpp`、`files/image_config/config-chassisdb/`）受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持（原理见 06-11 ｜ 参数见 04-01）。

最佳实践可归纳为四条：其一，读平台适配代码时先分“构建时序”与“运行时序”，把 `platform/` 的构建作用与 `device/` 的运行配置作用分开；其二，任何机型字段、平台取值、文件名先 Read/Grep 核验，核实不了就按“需对照实际版本核验”“不在本快照，需对照实际版本核验”成文并给出可定位目录；其三，涉及性能与容量一律标注“需在目标机型实测”，尤其基于 vs 的结论不得外推；其四，跨册引用统一写作（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx），其中本篇涉及的机型配置字段写“字段见 05-09”、平台构建变量写“参数见 04-01”、SAI 链路写“原理见 06-05”、平台模块写“模块见 07-10”，不在此展开字段表与命令全集。

## 02-05 调试构建、docker 增量镜像与 CI 产物形态

### 1. 背景与动机

02-03 已经把「从零构建一套可安装的 ONIE 镜像」走通，02-04 又把 `device/` 与 `platform/` 的机型适配讲清，但如果据此认为 SONiC 的日常开发就是「改一行代码、全量重编一次镜像」，就完全误解了这条构建链的真实工作方式。主仓 `sonic-buildimage-master/` 是由几十个独立模块、上百个 `.deb` 包与数十个容器镜像拼装起来的系统，一次全量构建耗时极长；而工程师每天的迭代往往只改动一两个模块，CI 上每个拉取请求也要在有限时间内给出反馈。于是「如何让改动只重编受影响的目标」「如何产出一份带符号、可下断点的调试镜像」「CI 最终对外交付哪些产物形态」这三个问题，就成了 02 册收尾必须回答的内容。本篇的事实锚点仍是 `upstream_src/sonic-buildimage/sonic-buildimage-master/`，基准统一写「上游 master 快照（2026-11 抓取）」，具体版本号与取值以对应构建文件为准、需对照实际版本核验（参数见 04-01 ｜ 模块见 07-13）。

第一个动机来自构建成本的现实约束。既然全量构建昂贵，构建系统就必须具备「依赖不变则复用上次产物」的能力。本快照里这套能力集中在主仓根的 `Makefile.cache`，它是一套以依赖文件内容 SHA 为键的 DPKG 缓存框架：每个目标维护 `.flags`、`.dep`、`.dep.sha`、`.smdep`、`.smsha` 等旁路文件，命中缓存时直接从 `/dpkg_cache` 或本机 `target/cache` 解出 `.tgz`，跳过整个编译过程。理解这套框架，才能解释为什么大多数增量构建「几乎什么都没编」，也才能解释为什么改了一个公共开关会导致大面积失效。需要强调的是，这里的「增量」指构建系统按内容哈希跳过未变目标的重建，而不是 docker 层的分层复用——`build_docker.sh` 在构建镜像时显式使用 `docker build --no-cache`，这一点在下文会专门澄清（原理见 06-13 ｜ 模块见 07-01）。

第二个动机来自排障对调试符号的刚性需求。生产镜像为了体积与启动速度，通常把 DWARF 调试符号剥离到单独的 dbgsym 包；但一旦需要定位 `orchagent` 崩溃、`syncd` 与 SAI 交互异常这类问题，就必须有一份保留符号、未做优化的产物。本快照用 `SONIC_DEBUGGING_ON` 与 `SONIC_PROFILING_ON` 两个开关把「调试态」与「生产态」分开：前者让编译保留符号，后者在保留符号之外还关闭优化，且二者同时打开时以 profiling 为准。与之配套的还有 `INSTALL_DEBUG_TOOLS` 开关和以 `dbg` 为后缀的调试容器镜像。把「编译带符号」和「镜像里装了调试工具」这两件事混为一谈，是新手最常见的误读，本篇会在核心概念与陷阱两节反复纠正。

第三个动机来自交付的可复现性。一个开源网络操作系统要被大规模采纳，CI 不能只回答「编没编过」，还要回答「产物是什么形态、能不能追溯、有没有被缓存污染」。本快照的 `azure-pipelines.yml` 把流水线拆成缓存键完整性门禁、虚拟交换机构建、多平台构建、测试与 SBOM 漏洞扫描等多个阶段，并对不同平台产出 `.bin`、`.img.gz`、`.swi`、`.bfb`、`.tar` 等形态，以及 `-dbg`、`-rpc`、`-asan`、`-session-monitor` 等变体。读懂这份流水线，才能把「某台设备上的镜像」对应到「某次构建的某个阶段产物」。最后必须立一条纪律：调试构建与各类变体镜像用于定位问题，不作生产基准；收敛时间、下发时延、转发吞吐与表项容量等一切数字，一律标注「需在目标机型实测」，本册不给绝对值（基准方法见 08-01）。

### 2. 核心概念

第一组概念是「内容寻址的构建缓存」。`Makefile.cache` 把每个构建目标的缓存键拆成两段二十四字节 SHA：一段由目标的环境标志文件、依赖清单文件与子模块清单文件经 `git hash-object` 与 `sha1sum` 折算，另一段取决于缓存模式——`GIT_CONTENT_SHA` 从依赖文件内容计算，`GIT_COMMIT_SHA` 对子模块取最后一次提交号。两段拼接进缓存文件名 `<target>-<依赖 SHA>-<模块 SHA>.tgz`，因此「内容变则键变、键变则缓存失效」，这与基于时间戳的构建有本质差别。缓存方法 `SONIC_DPKG_CACHE_METHOD` 可取 `none`、`cache`、`rcache`、`wcache`、`rwcache` 等值，`rcache` 只读、`wcache` 只写、`rwcache` 读写兼顾；本快照 CI 变量 `CACHE_MODE` 取 `rcache`，而部分构建任务会显式设为 `none`，具体取值与语义需对照实际版本核验（参数见 04-01 ｜ 模块见 07-13）。

第二组概念是「两级缓存与公共标志」。缓存分全局与本地两级：全局缓存位于构建容器内的 `/dpkg_cache`，可被多台机器与 CI 共享；本地缓存位于 `target/cache`，用于依赖文件被改动、不宜污染全局缓存的目标。判断「哪些改动影响所有目标」靠 `SONIC_COMMON_FLAGS_LIST`，其中折叠了平台、架构、发行版构建环境、`DOCKER_DEFAULT_PLATFORM`、`SLAVE_BASE_TAG` 以及调试与性能开关等值；`SONIC_COMMON_FILES_LIST` 则枚举 `.platform`、`rules/functions`、`Makefile.cache` 这类公共文件。值得注意的是，本快照刻意没有把 `slave.mk` 全文纳入公共文件，而是用手工版本戳 `SONIC_CACHE_RECIPE_VER` 加一个基于 `slave.mk` 对象哈希的告警守卫来防止「改了构建配方却没升版本、从而误用陈旧缓存」——这是一种用人工审查换缓存命中率的取舍，实现细节需对照实际版本核验。

第三组概念是「调试变体的两条独立轴」。第一条轴是编译产物是否带符号：在 `rules/config` 中打开 `SONIC_DEBUGGING_ON` 会让 `slave.mk` 把 `DEB_BUILD_OPTIONS_GENERIC` 设为 `nostrip` 并把 `SPLIT_DBGSYM` 置为 `n`，使 DWARF 留在运行期 `.deb` 里、不再单独产出 dbgsym；打开 `SONIC_PROFILING_ON` 则设为 `nostrip noopt`，同时关闭优化，且它作为 debugging 的超集优先生效。第二条轴是镜像是否随安装器交付调试工具：`SONIC_INSTALL_DEBUG_TOOLS` 决定 `INSTALL_DEBUG_TOOLS`，进而影响 CI 是否额外产出 `*-dbg.bin`、`*-dbg.img.gz` 这类镜像。两条轴彼此独立——可以编译带符号的 `.deb` 却不随安装器发布 dbg 镜像，反之亦然。调试容器镜像本身以 `DBG_IMAGE_MARK = dbg` 为标志，产物名为 `*-dbg.gz`（原理见 06-13 ｜ 字段见 05-09）。

第四组概念是「docker 镜像的生成与分发」。`build_docker.sh` 以 `dockers/<目录>` 为构建上下文，先把 `deps/` 与 `files/` 拷入上下文，再 `docker build --no-cache`，随后把镜像 `docker save` 成 `target/<name>.gz`；若给出仓库参数，则调用 `push_docker.sh` 完成登录与推送。所谓「增量镜像」在这里体现为上游 `.deb` 命中缓存后跳过重编、从而不必重建镜像，而不是 docker 层被复用。分发端 `push_docker.sh` 从环境变量读取 `REGISTRY_PASSWD`，用 `--password-stdin` 登录，按标签逐个 `docker tag`、`docker push`、`docker rmi`，并从推送输出里提取 `digest: sha256:` 摘要；给定版本与平台时推送到 `sonic-dockers/<platform>/<image>:<version>` 路径，否则以日期加 `BUILD_NUMBER` 组成标签（模块见 07-02 ｜ 参数见 04-01）。

第五组概念是「CI 产物形态」。CI 既有面向整机安装的 `.bin`（ONIE 安装包）、`.img.gz`（虚拟交换机磁盘镜像）、`.swi`、`.bfb`、`.tar` 等主产物，也有 `.bin.cdx.json`、`.gz.sbom.cdx.json` 等 SBOM 伴生产物，还有 `tr.xml` 这类 jUnit 测试结果。变体通过文件名后缀区分，生产用主产物与调试、RPC、ASAN、会话监控等变体在同一流水线里分别构建。所有产物名、标签规则与存储路径均随版本变化，需对照实际版本核验（模块见 07-12 ｜ 模块见 07-13）。

与缓存直接相关的对象集中在 `Makefile.cache`。计算 SHA 的宏有 `GET_MOD_SHA` 与 `GET_MOD_DEP_SHA`，前者按 `GIT_COMMIT_SHA` 或 `GIT_CONTENT_SHA` 取值，后者把 `DEPENDS`、`RDEPENDS`、`DBG_DEPENDS`、`DBG_IMAGE_PACKAGES`、`LOAD_DOCKERS` 等依赖一并折进依赖哈希；读取与写回分别由 `LOAD_FROM_CACHE`、`SAVE_INTO_CACHE` 完成，外层再包一层 `LOAD_CACHE`、`SAVE_CACHE` 做条件判断。`SHOW_WHY` 把重建原因写入 `<target>.log`，`MOD_LOCK` 用 `flock` 加超时保护共享缓存的并发访问。旁路文件 `.flags`、`.dep`、`.dep.sha`、`.smdep`、`.smsha` 由 `FLAGS_DEP_RULES`、`SHA_DEP_RULES`、`SMSHA_DEP_RULES` 三组规则生成。清理目标有 `cclean`（清旁路文件）、`lcclean`（清本地缓存）、`cprune`（按 `NUMDAYS` 删除陈旧 `.tgz`），另有 `listall` 与 `show-%` 用于列举目标（字段见 05-09 ｜ 参数见 04-01）。

与调试变体相关的对象集中在 `slave.mk` 与 `rules/config`。`slave.mk` 中 `DBG_IMAGE_MARK = dbg`，`DOCKER_DBG_IMAGES` 目标匹配 `target/%-dbg.gz`，其配方依次调用 `LOAD_CACHE`、`build_debug_docker_j2.sh`、`j2`、`prepare_docker_buildinfo.sh`、`DOCKER_BUILD`、`collect_docker_version_files.sh`、`docker-image-save` 与 `SAVE_CACHE`；`DOCKER_DBG_IMAGE_REF` 与 `DOCKER_NO_CACHE_FLAG` 也在其中定义。`build_debug_docker_j2.sh` 生成的 Dockerfile.j2 片段以 `ARG BASE` 开头，先构造一个中间层安装 dbg 依赖包，再从基础镜像 `FROM $BASE` 用 `rsync --mount=type=bind,from=base,target=/changes-to-image` 把变更同步回基础层，达到「只保留一层差异」的效果。以上函数名、变量名与文件格式均需对照实际版本核验，本篇只给可定位的目录与名称（原理见 06-13 ｜ 模块见 07-02）。

与 CI 与测试相关的对象分布在顶层与 `.azure-pipelines/`。`azure-pipelines.yml` 定义 `CACHE_MODE: rcache` 与多个阶段，`.azure-pipelines/azure-pipelines-build.yml` 按 `dbg_image`、`swi_image`、`asan_image`、`docker_syncd_rpc_image` 等参数决定构建哪些变体。`pytest.ini` 内容刻意留空，仅用于让 pytest 把当前目录识别为根目录；`tests/` 下有 `test_check_install.py`，`src/sonic-config-engine/tests/` 下则存放 minigraph、端口配置样例与 `mock_tables/` 等测试夹具。`scripts/` 下有 `audit_dep_completeness.sh`、`verify_cache_equivalence.sh` 与一整套 SBOM 脚本，承担缓存键审计与产物可追溯性工作；具体清单需对照实际版本核验（模块见 07-12 ｜ 模块见 07-13）。

图 02-05-01 用颜色区分了语义：blue 为源码与依赖输入，teal 为构建配置与缓存逻辑，amber 为编译产物与缓存文件，purple 为容器构建控制面，gray 为外部镜像仓库，red 为阻断合入的门禁边界。图中「开关入 key」这条边是关键：调试与性能开关被折进 `SONIC_COMMON_FLAGS_LIST`，因此同一份源码在调试态与生产态下的缓存键不同，不会互相误用；而 `DBGOPT` 只切换脚本的 `set -x` 跟踪、不改变产物字节，故刻意不进键。门禁与扫描是 CI 的失败边界，命中问题会阻断拉取请求合入或产生告警（原理见 06-13 ｜ 模块见 07-13）。

缓存复用的完整调用链是：`LOAD_CACHE` 先调 `SHOW_WHY` 把重建原因写入日志，再由 `CHECK_RCACHE_ENABLED` 判断读缓存是否开启；开启时 `LOAD_FROM_CACHE` 依次调用 `GET_MOD_DEP_SHA` 与 `GET_MOD_SHA`，拼出 `<target>-<依赖 SHA>-<模块 SHA>.tgz`，先查本地 `target/cache`、再查全局 `/dpkg_cache`，命中则 `tar -x` 解出产物并标记 `CACHE_LOADED`，否则走正常编译并由 `SAVE_CACHE` 在 `MOD_LOCK` 保护下写回。若依赖文件被改动，日志会记录「global cache skipped」并改用本地缓存，避免污染共享缓存。这条链解释了两个常见现象：其一，改一个公共文件会让大批目标同时失效；其二，缓存命中时日志里根本没有编译输出，排障不能据此判断「代码没被编进去」（原理见 06-13 ｜ 字段见 05-09）。

调试镜像的生成链与普通镜像并行。`DOCKER_DBG_IMAGES` 目标在 `LOAD_CACHE` 未命中时，把 `DBG_DEPENDS`、`DBG_IMAGE_PACKAGES`、`DBG_APT_PACKAGES` 展开成环境变量，交给 `build_debug_docker_j2.sh` 生成 `Dockerfile-dbg.j2`，经 `j2` 渲染成 `Dockerfile-dbg`，再以带 `--no-cache` 的 `DOCKER_BUILD` 构建、以 `docker-image-save` 落盘为 `*-dbg.gz`，最后 `SAVE_CACHE`。`INSTALL_DEBUG_TOOLS` 决定这类 dbg 镜像是否随整机安装器交付。CI 侧在 `dbg_image: yes` 的平台额外执行 `make ... INSTALL_DEBUG_TOOLS=y target/sonic-<platform>.bin` 并改名为 `sonic-<platform>-dbg.bin`；虚拟交换机则产出 `sonic-vs-dbg.img.gz`。ASAN 变体构建后还会主动删除 `libsairedis` 与 `syncd-vs` 的中间 `.deb`，以防普通镜像的缓存键误取到 ASAN 产物。以上产物名与变量需对照实际版本核验（参数见 04-01 ｜ 模块见 07-11）。

CI 的阶段链是：仅在拉取请求上运行的 `CacheKeyLint` 以静态分析扫描 `rules/*.mk`、`rules/*.dep`、`slave.mk` 与 `Makefile.cache`，用 `--base` 模式相对合并基线比较，凡本次改动新引入的完整性缺口一律以 P0 阻断；随后 `BuildVS` 与 `Build` 并行构建多平台产物，`Test` 下载 `sonic-buildimage.vs` 制品、加载 `docker-sonic-vs.gz` 并运行 py.test、发布 `tr.xml`，`VulnScan` 在产物齐备后对 `.bin.cdx.json`、`.gz.sbom.cdx.json` 等 SBOM 做漏洞扫描。需要说明的是，本快照里 `vstest` 任务与 `VulnScan` 阶段带有 `condition: false` 而处于关闭状态，这属于流水线的配置现状，不代表能力缺失；是否启用、何时启用需对照实际版本核验（模块见 07-13 ｜ 排障见 08-03）。

### 5. 配置/命令/代码实例

本节只给理解增量与调试构建所需的最小命令与配置片段，构建变量全集见 04-01、容器与启动参数见 04-07，本册不重列。先看一组在构建容器内查询缓存命中与重建原因的命令，它演示「为什么这次构建几乎什么都没编」该如何自证。

```bash

grep -hE "REASON|CACHE::" target/debs/bookworm/sonic-utilities*.log | tail -12
make cprune NUMDAYS=7
make lcclean
```

逐行判读如下。第一块命令中，`make show-sonic-utilities` 对应 `Makefile.cache` 的 `show-%` 目标，用于列举该目标及其派生包，管道截取前二十行避免刷屏；第二行用 `grep -hE` 从目标日志里筛出 `REASON` 与 `CACHE::` 两类记录，这是判断「命中缓存还是真的编译了」的直接证据；`make cprune NUMDAYS=7` 调用缓存清理，删除七天未使用的 `.tgz`，`make lcclean` 清空本地 `target/cache`。输出第二段首行是目标路径，其中 `bookworm` 是发行版构建环境目录，取值随 `BLDENV` 变化、需对照实际版本核验；第二、三行列出主包与 dbgsym 包，说明该目标在生产态下会剥离符号、单独产出 dbgsym，若这两行缺失则要怀疑 `SPLIT_DBGSYM` 是否被改。第四行 `NEWER PREREQUISITES` 指出 `rules/sonic-utilities.mk` 比产物新，是 `SHOW_WHY` 记录的重建触发原因；第五行 `FLAGS FILE` 展示进入缓存键的公共标志，`SONIC_DEBUGGING_ON=n` 与 `SONIC_PROFILING_ON=n` 表明这是生产态，`SLAVE_BASE_TAG` 体现工具链身份已折进键。第六、七行 `CACHE::LOADED` 与随后的 `is loaded from cache` 说明产物是从全局缓存 `/dpkg_cache` 解出的，构建并未真正编译该包；缓存文件名由两段哈希拼接，前段是依赖 SHA、后段是模块内容 SHA，示例哈希仅示意格式。第八行 `CACHE::SKIPPED` 说明本地缓存未参与本次命中，第九行 `CACHE::SAVED` 则记录了一次本地写回。若日志里既无 `LOADED` 也无 `SAVED`，就要检查 `CACHE_MODE` 是否被设为 `none`。输出块已注明示例与版本核验要求，取值不得当作真实构建数据引用（参数见 04-01 ｜ 排障见 08-03）。

再看调试开关的配置片段，它来自 `rules/config`，以注释形式给出，启用时需按实际构建系统取消注释。

```ini
# rules/config 中的调试与性能开关（节选，需对照实际版本核验）
#SONIC_DEBUGGING_ON = y
#SONIC_PROFILING_ON = y
# INSTALL_DEBUG_TOOLS - installs debugging tools in baseline docker
# INSTALL_DEBUG_TOOLS = y
```

这段配置说明两件事：其一，`SONIC_DEBUGGING_ON` 与 `SONIC_PROFILING_ON` 默认都被注释，生产构建不带符号；注释文字明确指出二者是包含关系，profiling 是 debugging 的超集，同时启用时以 profiling 为准，因此实际使用应二选一。其二，`INSTALL_DEBUG_TOOLS` 与前面两个开关不在同一层面，它只决定调试工具是否随基线容器与整机镜像交付，与 `.deb` 是否带符号无关。把这三类开关的作用范围分清，是正确产出调试镜像的前提；取消注释后的具体取值与生效条件需对照实际版本核验（参数见 04-01 ｜ 原理见 06-13）。

这段输出的判读要点如下。`Loading image` 对应 `push_docker.sh` 里的 `docker load`，说明脚本先把 `docker save` 出来的 gz 还原为本地镜像，再操作；若这一步失败，通常是 gz 文件损坏或架构不匹配。第二行是首个标签的推送，镜像名取自 `DOCKER_IMAGE_FILE` 的基名第一段，因此 `docker-orchagent-dbg.gz` 变成 `docker-orchagent-dbg`；`-t` 未指定时默认标签为 `latest`。第三行 `Image sha256:` 是脚本从 `docker push` 输出里用 `sed` 提取的摘要，用于校验推送内容的一致性；若摘要为空，可能是仓库未返回 digest 行，需对照实际版本核验。第四行来自 `-v` 与 `-p` 同时给定的分支，脚本把镜像推送到 `sonic-dockers/<platform>/<image>:<version>` 这一带平台与版本的路径；若只给其中一项，则走 `BUILD_NUMBER` 加日期的回退分支。末行 `Job completed` 表示脚本正常结束，此前还会用 `trap` 清理临时 `DOCKER_CONFIG` 目录并登出仓库（模块见 07-02 ｜ 参数见 04-01）。

### 6. 注意事项、陷阱与最佳实践

第一类是「增量」概念陷阱。最常见的是把 SONiC 的 docker 增量镜像理解成 docker 层缓存复用：本快照的 `build_docker.sh` 与 `slave.mk` 都显式使用 `docker build --no-cache`，真正的增量来自上游 `.deb` 命中 DPKG 缓存后跳过重编，而不是镜像层被复用。第二类是把调试构建当成性能基准：`SONIC_DEBUGGING_ON` 保留符号、`SONIC_PROFILING_ON` 还关闭优化，产物体积与运行特征都不同于生产态，绝不能拿它测收敛、时延与吞吐；这类数字一律标注「需在目标机型实测」（基准方法见 08-01 ｜ 模块见 07-13）。第三类是把两条调试轴混为一谈：编译带符号由 `DEB_BUILD_OPTIONS_GENERIC` 与 `SPLIT_DBGSYM` 决定，镜像是否带调试工具由 `INSTALL_DEBUG_TOOLS` 决定，二者独立；同时打开 `SONIC_DEBUGGING_ON` 与 `SONIC_PROFILING_ON` 也属误用，profiling 会覆盖 debugging。

第四类是缓存陷阱。`slave.mk` 并未整体纳入公共文件，缓存正确性依赖 `SONIC_CACHE_RECIPE_VER` 手工版本戳与一个基于 `slave.mk` 对象哈希的告警守卫；忽视告警、改了构建配方却不升版本，就可能让缓存命中陈旧产物。`DOCKER_DEFAULT_PLATFORM` 决定镜像记录的架构，`SLAVE_BASE_TAG` 标识构建容器与工具链，二者都必须折进键，否则会跨架构或跨工具链误用缓存；口令类变量则只取短指纹，避免明文落进 `<pkg>.flags` 与日志。`touch cache.skip.common` 会缩小公共文件范围、提高命中率，但也扩大陈旧风险，须谨慎使用。`cprune` 默认按七天清理，`lcclean` 只清本地缓存，二者作用不同不可混用（原理见 06-13 ｜ 字段见 05-09）。

第五类是 CI 与产物陷阱。`CacheKeyLint` 只在拉取请求上运行，且以 `--base` 模式阻断本次新引入的完整性缺口，历史遗留问题不阻断，因此不能把「CI 通过」等同于「缓存键完备」。本快照中 `vstest` 任务与 `VulnScan` 阶段带 `condition: false` 而关闭，`dbg_image`、`asan_image` 等参数因平台而异，`CACHE_MODE` 在不同任务中可取 `rcache` 或 `none`；这些都是配置现状，需对照实际版本核验，不得据本快照断言全平台一律开启。产物名后缀、标签规则与仓库路径随版本变化，同样需对照实际版本核验（模块见 07-12 ｜ 模块见 07-13）。

第六类是事实纪律与能力边界陷阱。唯一事实锚点是 `upstream_src/` 下八个子仓的 `xxx-master/` 仓库根，凡未列出的路径或无法用 Read 与 Grep 核实的文件一律不写进正文；不确定的宏名、函数名、目标名与命令选项一律写「需对照实际版本核验」并给出 `rules/`、`slave.mk`、`scripts/` 等可定位目录。`sonic-swss-common`、FRR / FRRouting 源码、Linux 内核与厂商 SAI 实现都不在本快照，涉及这些部分写「不在本快照，需对照实际版本核验」。还要守住全册一致的能力边界：SONiC 是白盒交换机 NOS，控制面在容器进程、数据面在 ASIC、经 SAI 下发，除 `platform/vs/` 外不做软件转发；Redis DB 编号来自运行时配置、不得写死；`config` 返回成功不代表硬件已下发；`orchagent` 不直接操作硬件；`warmrestart/`、多 ASIC 与 chassis 受平台与版本限制（原理见 06-01 ｜ 参数见 04-04）。

最佳实践归纳为四条。其一，写任何缓存键、调试开关、产物名之前先 Read 与 Grep 对应源码，核实不了就按「需对照实际版本核验」成文，绝不补值。其二，判断构建是否真正生效，按「前置检查、执行、验证输出、清理」闭环操作，并用 `REASON` 与 `CACHE::` 日志自证，明确区分「命中缓存」与「重新编译」。其三，调试产物只用于定位问题，验证结论必须在生产态与目标机型上重做，性能数字一律标注「需在目标机型实测」。其四，跨册引用一律用具体篇号的四段式写法，本篇涉及的构建变量写「参数见 04-01」、平台状态结构写「字段见 05-09」、容器编排与缓存机制写「原理见 06-13」、测试与 CI 能力写「模块见 07-13」，不在本册展开变量全集与字段表。
