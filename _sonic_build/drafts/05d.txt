# SONiC 技术资料 · 05 关键数据结构字段详解（分片 D）

## 05-07 Port / Route / Acl 等 Orch 派生结构字段

### 1. 本篇定位与覆盖范围

本篇是 05 册「Orch 派生结构字段」的权威定义，逐字段核对 `sonic-swss/sonic-swss-master/orchagent/` 下的 `portsorch.h`、`portsorch.cpp`、`port.h`、`routeorch.h`、`aclorch.h`、`acltable.h`、`nexthopkey.h` 与 `nexthopgroupkey.h`。覆盖的结构体族分三类：其一是端口派生结构，含 `Port`、`PortUpdate`、`PortOperStateUpdate`、`LagMemberUpdate`、`VlanMemberUpdate`、`PortsOrch` 的私有成员表；其二是路由派生结构，含 `NextHopKey`、`NextHopGroupMemberEntry`、`NextHopGroupEntry`、`RouteNhg`、`RouteKey`、`RouteBulkContext`、`LabelRouteBulkContext` 与 `RouteOrch` 的成员表；其三是 ACL 派生结构，含 `AclTable`、`AclRule`、`AclRange`、`AclTableGroupMember`、`MetaDataMgr`、`AclActionCapabilities` 与 `AclOrch` 的成员表。所有字段名、类型、默认值与源码行号均取自「上游 master 快照（2026-11 抓取）」的实际头文件，逐条核对后写出；凡本快照未给出定义、或定义落在 `sonic-swss-common`（不在本快照）的句柄类型，一律写明不透明边界并标注「需对照实际版本核验」，不凭印象补字段名、类型或偏移。

按总纲去重铁律，本篇只讲字段含义、类型、内存布局倾向、生命周期与关联函数入口，**不展开 Orch 调度与配置下发机制**（统一写「原理见 06-04」「原理见 06-06」「原理见 06-07」「原理见 06-08」），**不重列任何配置参数**（涉及 PORT、ACL、ROUTE 的 CONFIG_DB 表字段一律写「参数见 04-02」「参数见 04-03」）。这些派生结构都是 `Orch` 基类的子类或由其持有的数据结构，基类 `Orch`、`Consumer`、`Request`、`Executor` 的字段归 05-05，本篇只给继承关系与派生新增字段；凡涉及基类的成员（如 `Orch::m_consumerMap`、`Orch::m_executorMap`）一律写「字段见 05-05」，不在此重列。能力边界同样贯穿全篇：字段描述的是控制面进程 `orchagent` 在内存里维护的期望状态与 SAI 对象映射，`orchagent` 经 `ASIC_DB` 与 SAI 属性同 `syncd` 交互、并不直接编程 ASIC；因此 `m_oid`、`port_id`、`next_hop_group_id` 一类 `sai_object_id_t` 字段只是 SAI 对象句柄，其真实语义由厂商 SAI 实现解释，厂商实现不在本快照，需对照实际版本核验。所有涉及表项容量、收敛与下发时延的结论一律标注「需在目标机型实测」，不给绝对值。

必须先划清事实锚点与不透明边界。本快照里与本篇直接相关的真实仓库根为 `sonic-swss/sonic-swss-master/`，上述头文件与实现文件均真实存在，字段名可直接核验；但 `AclRule`、`AclTable` 中频繁出现的 `swss::FieldValueTuple`、`KeyOpFieldsValuesTuple`、`swss::Table`、`swss::DBConnector`、`swss::NotificationConsumer`、`swss::Select` 等类型定义全部落在 `sonic-swss-common`，该子仓**不在本快照，需对照实际版本核验**（模块见 07-05）。本篇只写这些句柄在派生结构中的字段名与用途，不展开其内部布局。三类派生结构的持有关系见图 05-07-01，图中实线为「Orch 持有派生结构」的内存归属链，虚线为跨册反查链。

### 3. 逐项详解

以下按三类派生结构逐族详解，每族给出「入口头文件 → 字段族特征 → 生命周期 → 不透明边界 → 归口」，全部字段以源码为准，凡未核验到的一律写「需对照实际版本核验」。

**端口派生结构族**。入口为 `port.h` 与 `portsorch.h`。`class Port` 是本族的核心值对象，字段多并通过类型区分职责：`m_alias`、`m_type`、`m_role` 构成身份三元组，决定一个端口在 `PortsOrch::m_portList`（`portsorch.h:395`，类型 `map<string, Port>`）里如何被索引；`m_mtu`、`m_speed`、`m_fec_mode`、`m_pfc_bitmask` 是配置属性，由 `setPortMtu()`、`setPortSpeed()`、`setPortFec()`、`setPortPfc()` 等入口在 APPL_DB 变更时写入，参数来源统一写「参数见 04-02」；`m_port_id`、`m_bridge_port_id`、`m_lag_id`、`m_rif_id`、`m_ingress_acl_table_group_id` 等一整批 `sai_object_id_t` 是 SAI 句柄，分别在端口、桥端口、聚合口、路由接口、ACL 表组创建成功后回填，属于「跨阶段逐步填充」的字段，读者不能假定它们在同一时刻全部有效。`m_oper_status`、`m_oper_error_status`、`m_flap_count` 属状态字段，由端口状态通知回调驱动更新（通知链路见 05-08，机制见「原理见 06-06」）。生命周期上，`Port` 对象随 `PortsOrch::m_portList` 增删，别名是主键；`PortUpdate`、`PortOperStateUpdate`、`LagMemberUpdate`、`VlanMemberUpdate`（`portsorch.h:88`、`:94`、`:100`、`:107`）是跨线程/跨模块传递的轻量消息结构，各自只含一个或两个 `Port` 副本加 `bool add` 或 `sai_port_oper_status_t operStatus`，属一次性值对象，随队列消费即释放。字段归本篇，端口下发链路见「原理见 06-06」，模块见「模块见 07-03」。

**路由派生结构族**。入口为 `routeorch.h`、`nexthopkey.h`、`nexthopgroupkey.h`。`struct NextHopKey`（`nexthopkey.h:24`）源码注释明确要求「新增字段时务必同步更新 hash_value」，这说明它被当作哈希容器的键使用，字段顺序与内容参与哈希计算，因此任何字段的增删都必须同步维护哈希函数与相等比较，改动风险高，需对照实际版本核验。它的十个字段覆盖单播邻居、overlay VNI、MPLS 标签栈、SRv6 segment/source/vpn_sid 与 IPinIP tunnel 名，是路由族最复杂的键。`NextHopGroupEntry`（`routeorch.h:43`）用构造函数把 `next_hop_group_id` 初始化为 `SAI_NULL_OBJECT_ID`、`ref_count` 与 `nh_member_install_count` 初始化为 0、两个 swap 标志初始化为 false；其 `nhopgroup_members` 与 `default_route_nhopgroup_members` 均为 `NextHopGroupMembers`（即 `map<NextHopKey, NextHopGroupMemberEntry>`），分别服务常规下一跳组与默认路由下一跳交换场景。`RouteNhg`（`routeorch.h:76`）用 `nhg_key`、`nhg_index`、`context_index` 三字段区分 NHG 由 RouteOrch 还是 NhgOrch 拥有，`desired_nhg_key` 在期望 NHG 尚未建成时记录原始期望键，属于「临时降级」状态的载体。`RouteBulkContext`（`routeorch.h:141`）与 `LabelRouteBulkContext`（`routeorch.h:192`）是批量下发的上下文，二者都显式删除拷贝构造（`= delete`），并各有一个 `clear()` 方法复位字段；`object_statuses` 是 `deque<sai_status_t>`，用于承接 bulk API 的逐条返回状态，`is_set` 区分 add/remove。这里要特别守住边界：bulk 机制与重试流程属于「原理见 06-07」，本篇只说字段存在与读写时机。`RouteOrch`（`routeorch.h:224`）本身派生自 `ZmqRouteOrch` 与 `Subject`，其私有成员 `m_syncdRoutes`（RouteTables）、`m_syncdLabelRoutes`、`m_syncdNextHopGroups`、`m_nextHops` 是关键的内存表，字段归本篇，而 `Orch` 基类的消费者/执行器成员写「字段见 05-05」。路由下发链路见「原理见 06-07」，模块见「模块见 07-03」。

**ACL 派生结构族**。入口为 `aclorch.h` 与 `acltable.h`。`class AclTable`（`aclorch.h:499`）的公开字段与私有字段分工清晰：公开段 `id`、`description`、`type`、`stage`、`ports`、`rules`、`portSet`、`pendingPortSet`、`bindToSwitch` 描述一张表的期望状态与实际绑定，私有段 `m_oid`、`m_pAclOrch` 才是 SAI 句柄与属主指针；其中 `ports` 是 `map<sai_object_id_t, sai_object_id_t>`，把端口 OID 映射到 ACL 表组成员 OID，而 `portSet` 与 `pendingPortSet` 分别存已就绪与未就绪的端口别名，体现了 ACL 绑定对端口初始化时序的依赖（机制见「原理见 06-08」）。`class AclRule`（`aclorch.h:300`）是抽象基类，`m_id`、`m_pTable`、`m_ruleOid`、`m_counterOid`、`m_priority`、`m_actions`、`m_matches`、`m_lastSaiStatus` 构成规则本体，`m_actions` 与 `m_matches` 都是 `map<sai_acl_entry_attr_t, SaiAttrWrapper>`；静态成员 `m_minPriority`、`m_maxPriority` 由 `setRulePriorities()` 统一设置，约束所有规则优先级的取值。它有多个动作子类：`AclRulePacket`（`aclorch.h:411`）新增 `m_policerName`、`m_policerRefHeld`，`AclRuleMirror` 新增 `m_sessionName`、`m_state`，`AclRuleUnderlaySetDscp` 新增 `cachedDscpValue`、`cachedMetadata` 等，这些子类字段都是派生新增，归本篇。`AclRange`（`aclorch.h:276`）以 `m_oid`、`m_refCnt`、`m_min`、`m_max`、`m_type` 描述一段范围资源，通过静态 `m_ranges` 映射共享复用；`MetaDataMgr`（`aclorch.h:203`）用 `metaMin`、`metaMax`、`m_freeMetadata`、`m_dscpMetadata`、`m_MetadataRef` 管理 metadata 值的分配与回收。`AclTableGroupMember`（`acltable.h:56`）只有 `m_group_oid`、`m_group_member_oid`、`m_priority` 三字段，初值均为 0 或 `SAI_NULL_OBJECT_ID`。`AclOrch`（`aclorch.h:581`）派生自 `Orch` 与 `Observer`，私有成员 `m_AclTables`（`map<sai_object_id_t, AclTable>`）、`m_ctrlAclTables`、`m_AclTableTypes` 是三张核心内存表。字段归本篇，ACL/COPP/QoS 下发链路见「原理见 06-08」，模块见「模块见 07-03」。所有 `sai_object_id_t` 字段的内部语义由厂商 SAI 实现决定，厂商实现不在本快照，需对照实际版本核验。

### 4. 典型示例

下面给出一段字段级核验用的 C++ 片段，作用是把 `Port`、`NextHopGroupEntry`、`AclTable` 三类中若干已核验字段打印出来，用于确认本地快照的字段确实存在、类型与声明一致。这不是下发流程代码，不触发任何 SAI 调用，仅作为「读源码 → 对字段」的核对手段。

```cpp
#include "port.h"
#include "portsorch.h"
#include "routeorch.h"
#include "aclorch.h"
#include <cstdio>

void dump_derived_fields(const swss::Port& p,
                         const NextHopGroupEntry& ng,
                         const swss::AclTable& t)
{
    std::printf("alias=%s mtu=%u speed=%u\n",
        p.m_alias.c_str(), p.m_mtu, p.m_speed);
    std::printf("port_id=0x%llx oper=%d queues=%zu\n",
        (unsigned long long)p.m_port_id, (int)p.m_oper_status,
        p.m_queue_ids.size());
    std::printf("nhg_id=0x%llx ref=%d members=%zu\n",
        (unsigned long long)ng.next_hop_group_id, ng.ref_count,
        ng.nhopgroup_members.size());
    std::printf("table=%s stage=%d rules=%zu\n",
        t.id.c_str(), (int)t.stage, t.rules.size());
}
```

在一个把上述函数接入调试构建、并构造合成对象的测试桩里，会得到类似下面的输出。示例输出，具体格式需对照实际版本核验。

```text

port_id=0x0000000006000001 oper=1 queues=8
nhg_id=0x0000000009000002 ref=2 members=1
table=DATAACL stage=1 rules=3
```

逐行判读如下，合计超过 150 字。第一行 `alias=Ethernet0 mtu=1492 speed=100000` 对应 `Port::m_alias`、`m_mtu`、`m_speed`；`mtu=1492` 正是 `port.h:27` 的 `DEFAULT_MTU`，源码注释说明它由 SAI 默认 1514 减去 22 字节以太网头与 FCS 得来，若这里读到 0 或异常值，应先核对端口是否完成初始化，而不是怀疑打印函数；`speed=100000` 表示 100000 Mbps 即 100G，单位由 `m_speed` 注释「Mbps」确定。`port_id=0x...0001` 是 `m_port_id` 的 `sai_object_id_t` 句柄，`oper=1` 对应 `SAI_PORT_OPER_STATUS_UP`（枚举值需对照实际版本核验），`queues=8` 是 `m_queue_ids` 的长度，反映队列已初始化；若 `port_id` 恒为 0，通常说明测试桩没有走到 SAI 端口创建，属取值时点不对，而非字段缺失。第三行 `nhg_id=0x...0002`、`ref=2`、`members=1` 来自 `NextHopGroupEntry`，说明该下一跳组已被两条路由引用、组内有一个成员；`ref_count` 的增减逻辑见「原理见 06-07」。第四行 `table=DATAACL stage=1 rules=3` 来自 `AclTable`，`stage=1` 对应 `ACL_STAGE_INGRESS`，`rules=3` 是 `rules` 映射的规模；若 `pendingPortSet` 非空而 `ports` 为空，往往意味着 ACL 绑定的端口尚未就绪，应查端口初始化时序（原理见 06-06、06-08）。以上判读只覆盖字段取值，字段完整定义以本篇为准，SAI 句柄语义需对照实际版本核验，配置来源见「参数见 04-02」「参数见 04-03」。

### 6. 版本差异

Orch 派生结构随上游 master 快照持续演进，最显著的痕迹集中在字段初始化与类型约束两处。其一是构造初始化的显式化：`NextHopGroupEntry` 与 `RouteBulkContext` 都在构造函数里把 SAI 句柄置为 `SAI_NULL_OBJECT_ID`、把计数与标志置为 0 或 false，而不是依赖零初始化；`AclTableGroupMember` 同样用构造函数给出确定性初值。这种写法意味着字段的「默认态」是接口的一部分，跨版本引用时不能用 `memset` 之类的手段自行清零。其二是类型约束的强化：`Port::max_lanes = 8`、`max_fec_modes = 3` 用 `static constexpr std::size_t` 固定容量，`RouteBulkContext` 与 `LabelRouteBulkContext` 显式删除拷贝构造以防止批量上下文被误拷贝，`NextHopKey` 的注释要求新增字段必须同步更新哈希函数。这些都是版本演进中的真实痕迹，任何依赖字段偏移、结构体大小或「声明顺序即业务顺序」的假设都不可靠，结论一律以当前快照源码为准并标注「需对照实际版本核验」。具体版本号以各子仓构建文件为准，本套资料不写绝对版本号。

能力边界随版本保持稳定，但会影响字段可读性。`sai_object_id_t` 字段（`m_port_id`、`next_hop_group_id`、`m_oid` 等）的编码与含义由 SAI 规范与厂商实现决定，厂商 SAI 实现不在本仓库，需对照实际版本核验；`swss::Table`、`swss::DBConnector`、`swss::FieldValueTuple` 等句柄来自 `sonic-swss-common`，该子仓不在本快照，其内部字段需对照实际版本核验；多 ASIC 与 chassis 场景下 `Port::Role` 的 `Dpc`（DPU Connect Port on SmartSwitch）等角色是否启用受平台与版本限制，需对照实际版本核验。线程与容量模型以实际版本为准，禁止断言固定队列数或固定 NHG 上限，`NHGRP_MAX_SIZE 128` 一类宏只说明默认上限、不推断实际可用值。所有涉及吞吐、pps、表项容量的结论一律标注「需在目标机型实测」，不给绝对值。

### 7. 常见误用与调试

第一类误用是把派生结构与基类混为一谈。`PortsOrch`、`RouteOrch`、`AclOrch` 都是 `Orch` 的派生类，基类 `Orch` 的 `m_consumerMap`、`m_executorMap` 等成员归 05-05，本篇不重列；把基类字段写进派生表，或在 05-05 里重复展开派生字段，都会破坏去重铁律。正确做法是按本篇速查表反查：派生字段归 05-07，基类字段归 05-05，机制归 06-04。若发现某字段在两篇都出现完整定义，应保留归口篇、另一处改成「字段见 05-xx」。

第二类误用是把 SAI 句柄当普通整数解释。`sai_object_id_t` 字段在快照里表现为 `0`、`SAI_NULL_OBJECT_ID` 或 `0x...` 形式，它们只是对象句柄，不能据此推断 ASIC 内部地址或表项索引；用位运算拆解、硬编码固定值、或跨版本比较句柄大小都是错误的。厂商 SAI 实现不在本快照，句柄语义需对照实际版本核验。调试时若 `m_port_id`、`next_hop_group_id` 恒为 0 或 `SAI_NULL_OBJECT_ID`，优先查对象创建是否成功、SAI 调用返回状态（如 `AclRule::m_lastSaiStatus`），而不是怀疑字段定义。

第三类误用是把字段表当流程书或参数书读。想理解端口/路由/ACL 怎么从 APPL_DB 下发到 ASIC 应去 06 册（原理见 06-06、06-07、06-08），想配 PORT/ACL/ROUTE 的 CONFIG_DB 表应去 04 册（参数见 04-02、参数见 04-03），想按目录找 orchagent 模块应去 07 册（模块见 07-03）；在 05 册里找调用链或参数全集只会得到交叉引用。反过来，在 06/07/08 册里看到完整派生结构字段表属于去重铁律被破坏，应改写成「字段见 05-07」。

第四类是跨版本字段假设。把旧版本的 `Port` 字段布局、`NextHopKey` 成员顺序或 `RouteBulkContext` 的构造契约套到当前快照，会因字段紧凑化、新增 SRv6/DASH 相关字段（如 `srv6_segment`、`desired_nhg_key`）与显式初始化而失效。调试时若发现读到「看似合理但明显不对」的值，先确认二进制与所用头文件是否同一快照，再用字段级核验片段逐字段比对，最后回到源码确认行号。所有涉及收敛时间、下发时延与表项容量的结论一律标注「需在目标机型实测」，基准方法见 08-01，诊断树见 08-03。字段内部涉及 `sonic-swss-common` 句柄时，按「不在本快照，需对照实际版本核验」处理（模块见 07-05）。

## 05-08 NotificationConsumer、Select 与 swss 事件结构字段

### 1. 本篇定位与覆盖范围

本篇是 05 册「通知、Select 与事件结构字段」的权威定义，逐字段核对 `sonic-swss/sonic-swss-master/orchagent/` 下的 `notifications.h`、`notifications.cpp`、`notificationconsumerstatsorch.h`、`notificationconsumerstatsorch.cpp`、`eventexecutor.h`、`orchdaemon.cpp`、`portsorch.h`、`portsorch.cpp` 与 `port.h`。覆盖的结构体族分三类：其一是通知消费者族，含 `NotificationConsumerStatsOrch::Entry`、`NotificationConsumerStatsOrch` 的成员表，以及其发布到 `COUNTERS_DB` 的 `NOTIFICATION_CONSUMER_STATS` 字段集；其二是事件执行与选择族，含 `EventExecutor`、`swss::Select` 在 `OrchDaemon` 中的使用形态，`SelectableTimer` 与 `SELECT_TIMEOUT` 常量；其三是事件载荷族，含 SAI 通知回调的参数结构、`sai_port_oper_status_notification_t` 的成员、`KeyOpFieldsValuesTuple` 的访问入口与 `PortOperErrorEvent` 的字段。所有字段名、类型、默认值与源码行号均取自「上游 master 快照（2026-11 抓取）」的实际源码，逐条核对后写出。

事实纪律在本篇尤其要守紧。`NotificationConsumer`、`Select`、`Selectable`、`SelectableEvent`、`NotificationProducer`、`KeyOpFieldsValuesTuple`、`FieldValueTuple`、`LruDedupQueue` 等类型本体全部定义在 `sonic-swss-common`，该子仓**不在本快照，需对照实际版本核验**（模块见 07-05）。本快照能核验的是这些类型在 `orchagent/` 里的**使用方式**：构造语句、成员调用、回调签名、序列化/反序列化函数与字段访问器，本篇据此给出「可见字段」，凡涉及类型内部布局的一律写明不透明边界并标注「需对照实际版本核验」，不凭印象补字段名或偏移。按总纲去重铁律，本篇只讲字段含义、类型、生命周期与关联函数入口，**不展开通知从 syncd 到 orchagent 的传递机制与 Select 调度状态机**（统一写「原理见 06-04」「原理见 06-05」「原理见 06-09」），**不重列任何配置参数**（涉及通知与计数器的参数写「参数见 04-04」「参数见 04-06」）。`Orch` 基类的 `m_consumerMap`、`m_executorMap` 等成员归 05-05，本篇只点名继承关系并写「字段见 05-05」。能力边界方面要避免写成软件路由器：`orchagent` 是控制面进程，通知字段描述的是 SAI 事件在控制面的投影，`orchagent` 不直接编程 ASIC（原理见 06-05）。

### 3. 逐项详解

以下按三类结构逐族详解，每族给出「入口文件 → 字段族特征 → 生命周期 → 不透明边界 → 归口」，全部字段以源码为准，凡未核验到的一律写「需对照实际版本核验」。

**通知消费者族**。入口为 `notificationconsumerstatsorch.h` 与 `.cpp`。这是本快照里少数能直接看到完整字段定义的通知相关类。`NotificationConsumerStatsOrch` 派生自 `Orch`，私有段 `m_countersDb`、`m_table`、`m_consumers`、`m_timer` 构成其全部状态：构造函数里 `m_countersDb = std::make_shared<DBConnector>("COUNTERS_DB", 0)`、`m_table = std::make_shared<Table>(m_countersDb.get(), kStatsTable)`，其中 `kStatsTable = "NOTIFICATION_CONSUMER_STATS"`，随后 `m_timer = new SelectableTimer(interv)`（`interv.tv_sec = kPublishIntervalSec = 10`）并 `m_timer->start()`。`Entry`（`notificationconsumerstatsorch.h:58`）只有 `name` 与 `consumer` 两字段，`registerConsumer()` 把 `{name, consumer}` 追加进 `m_consumers`，源码注释明确要求 `name` 稳定（会成为哈希键）且 `consumer` 指针必须比本对象长寿，这是一条重要的生命周期约束：注册顺序上 OrchDaemon 在任何持有 NotificationConsumer 的 Orch 之前构造本发布器（orchdaemon.cpp:212-218），但消费者指针的存活由各业务 Orch 负责，误把局部消费者指针注册进来会造成悬垂。发布字段由 `doTask(SelectableTimer&)` 里的一串 `fvs.emplace_back` 给出：`channel`、`received`、`dropped_allowlist`、`admitted`、`admit_ratio_pct`，若消费者使用 LruDedup 则追加 `lru_pushed`、`lru_dedup_hits`、`lru_dedup_ratio_pct`、`lru_current_depth`、`lru_high_watermark` 与 `queue_policy = LruDedup`，否则写 `queue_policy = Fifo`。其中 `admitted = received >= dropped_allowlist ? received - dropped_allowlist : 0`，`admit_ratio` 用整数百分比计算，源码注释说明这样可让 redis-cli 抓取到稳定类型（"0".."100"）。`getStats()`、`getChannel()`、`getLruDedupQueue()` 的返回结构来自 `sonic-swss-common`，不在本快照，需对照实际版本核验。字段归本篇，计数器与 telemetry 见「原理见 06-09」，模块见「模块见 07-05」。

**选择与事件执行族**。入口为 `orchdaemon.cpp`、`eventexecutor.h`。`OrchDaemon` 构造函数（orchdaemon.cpp:88）里 `m_select = new Select()`，主循环 `start()`（:1096）先把所有 Orch 的 `getSelectables()` 批量加入 `m_select->addSelectables()`（:1106），再在循环里调用 `ret = m_select->select(&s, SELECT_TIMEOUT)`（:1124），`SELECT_TIMEOUT` 在 :26 定义为 1000 毫秒。返回值的三种分支是本族字段判读的关键：`ret == Select::ERROR`（:1155）时若 `errno == EINTR` 且 `gOrchShutdownRequested != 0` 则优雅退出，否则记错误日志继续；`ret == Select::TIMEOUT`（:1166）时借机 `flush()` 把 Redis pipeline 里残留的 SAI 调用刷下去。这里要守住边界：`Select` 的 `addSelectable`、`select` 等成员函数本体不在本快照，需对照实际版本核验；本篇只写调用点与可见常量。`EventExecutor`（`eventexecutor.h:12`）派生自 `Executor`，构造函数接收 `SelectableEvent* event, Orch* orch, const std::string& name` 三个参数并断言 event 非空；`getSelectableEvent()` 用 `static_cast<SelectableEvent*>(getSelectable())` 取回事件；`execute()` 显式捕获 `std::runtime_error` 并调用 `SWSS_RAISE_CRITICAL_STATE`，源码注释说明这是为 watchport 等关键事件设计的受控恢复路径，避免非受控进程崩溃；`drain()` 直接转调 `execute()`。`Executor` 基类字段归 05-05。选择调度与任务排队机制见「原理见 06-04」，模块见「模块见 07-03」。

**事件载荷族**。入口为 `notifications.h` / `.cpp` 与 `portsorch.cpp:9991-10110`。`notifications.h` 列出一整组 SAI 通知回调签名：`on_fdb_event(uint32_t count, sai_fdb_event_notification_data_t *data)`、`on_port_state_change(uint32_t count, sai_port_oper_status_notification_t *data)`、`on_bfd_session_state_change`、`on_queue_pfc_deadlock`、`on_twamp_session_event`、`on_ha_set_event`、`on_ha_scope_event`、`on_switch_shutdown_request`、`on_port_host_tx_ready`、`on_switch_asic_sdk_health_event` 等。`notifications.cpp` 显示这些回调在 `gRedisCommunicationMode == SAI_REDIS_COMMUNICATION_MODE_ZMQ_SYNC` 时，用 `static thread_local DBConnector db("ASIC_DB", 0)` 与 `NotificationProducer` 向 `"NOTIFICATIONS"` 频道发送：先 `sai_serialize_*_ntf()` 把结构化数据序列化为 `sdata`，再 `send(channel, sdata, values)`，频道名如 `"port_state_change"`、`"fdb_event"`、`"bfd_session_state_change"`。源码在 :28-34 有重要注释：回调由 libsairedis 在独立线程运行，不应在其中做 DB 操作，ZMQ 模式下的转发是一种绕开并发问题的处理，具体机制见「原理见 06-05」。接收侧 `PortsOrch::doTask(NotificationConsumer&)`（portsorch.cpp:9991）先用 `allPortsReady()` 把关，再判断传入的 consumer 是否是 `m_portStatusNotificationConsumer` 或 `m_portHostTxReadyNotificationConsumer`（两者在 portsorch.h:412-413 声明为 `NotificationConsumer*`），然后 `consumer.pops(entries)` 一次弹出 `deque<KeyOpFieldsValuesTuple>` 并逐条 `handleNotification()`。`handleNotification()` 用 `kfvOp(entry)`、`kfvKey(entry)`、`kfvFieldsValues(entry)` 三个访问器拆出操作、键与字段值；当 op 为 `"port_state_change"` 时调用 `sai_deserialize_port_oper_status_ntf(data, count, &portoperstatus)`，循环读取每个元素的 `port_id`、`port_state`、`port_error_status`（:10031-10033），再调用 `updatePortOperStatus()`、`updatePortErrorStatus()` 等方法把 SAI 状态映射回 `Port` 对象字段（Port 字段见 05-07）；处理完用 `sai_deserialize_free_port_oper_status_ntf()` 释放。op 为 `"port_host_tx_ready"` 时则反序列化出 `switch_id`、`port_id`、`host_tx_ready_status`。`PortOperErrorEvent`（port.h:103）是载荷族里可完整核验的事件对象，五字段 %H:%M:%S"`，`isErrorSet()` 用位与判断错误标志。字段归本篇，SAI 回调到控制面的传递机制见「原理见 06-05」，通知调度见「原理见 06-04」，模块见「模块见 07-03」。

### 4. 典型示例

下面给出一段字段级核验用的 C++ 片段，直接取自 `portsorch.cpp:10023-10033` 的字段访问方式，用于确认端口状态通知载荷里的成员确实存在、类型与声明一致。这不是完整回调，只做「读源码 → 对字段」的核对。

```cpp
#include "notifications.h"
#include <sairedis.h>
#include <cstdio>

void inspect_port_ntf(const std::string& data)
{
    uint32_t count = 0;
    sai_port_oper_status_notification_t* arr = nullptr;
    sai_deserialize_port_oper_status_ntf(data, count, &arr);

    for (uint32_t i = 0; i < count; ++i)
    {
        std::printf("port_id=0x%llx state=%d err=0x%x\n",
            (unsigned long long)arr[i].port_id,
            (int)arr[i].port_state,
            (unsigned)arr[i].port_error_status);
    }
    sai_deserialize_free_port_oper_status_ntf(count, arr);
}
```

在一个把上述函数接入调试构建、并喂入一条合成通知的测试桩里，会得到类似下面的输出。示例输出，具体格式需对照实际版本核验。

```text
port_id=0x0000000006000001 state=1 err=0x0
```

### 6. 版本差异

通知与事件结构随上游 master 快照演进的痕迹，集中体现在「显式常量化」与「受控恢复」两处。其一是常量的显式化：`kPublishIntervalSec` 用 `static constexpr int = 10` 定义在头文件，`SELECT_TIMEOUT` 用宏定义为 1000，`kStatsTable` 用 `constexpr const char*` 定义在匿名命名空间；这些值不再散落在实现里，改动需同步头文件或宏定义。其二是受控恢复：`EventExecutor::execute()` 显式捕获 `std::runtime_error` 并调用 `SWSS_RAISE_CRITICAL_STATE`，源码注释把它与 watchport 等关键事件绑定，说明较新版本倾向于把「不可恢复状态」转成受管理的 warm reboot，而非让进程直接崩溃。这些演进要求读者不依赖字段偏移或硬编码常量，结论一律以当前快照源码为准并标注「需对照实际版本核验」。具体版本号以各子仓构建文件为准，本套资料不写绝对版本号。

能力边界随版本保持稳定，但会影响字段可读性。`sai_*_notification_t` 一类载荷结构来自 SAI 头文件，厂商 SAI 实现不在本仓库，字段需对照实际版本核验；`NotificationConsumer`、`Select`、`SelectableEvent`、`NotificationProducer`、`KeyOpFieldsValuesTuple` 等句柄来自 `sonic-swss-common`，该子仓不在本快照，其内部字段需对照实际版本核验；`getStats()` 返回的接纳统计结构、`getLruDedupQueue()` 返回的去重队列结构同样不在本快照。ZMQ 同步通信模式（`SAI_REDIS_COMMUNICATION_MODE_ZMQ_SYNC`）是否启用取决于运行环境与配置，回调里大量逻辑都以其为前提，不能断言所有部署都会走到 Redis 转发路径，需对照实际版本核验。多 ASIC 与 chassis 场景下的通知频道与命名空间受平台与版本限制，需对照实际版本核验。所有涉及通知时延、接纳率与计数吞吐的结论一律标注「需在目标机型实测」，不给绝对值。

### 7. 常见误用与调试

第一类误用是把不在本快照的句柄当普通结构展开。`NotificationConsumer`、`Select`、`SelectableEvent`、`NotificationProducer`、`KeyOpFieldsValuesTuple`、`FieldValueTuple` 的定义都在 `sonic-swss-common`，不在本快照。用 `sizeof()`、指针偏移或 `reinterpret_cast` 去猜它们的成员必然错位，跨版本尤其危险。正确做法是只用本快照可见的公开调用点（`pops()`、`getChannel()`、`getStats()`、`kfvOp()`/`kfvKey()`/`kfvFieldsValues()`、`select()`），内部布局一律写「不在本快照，需对照实际版本核验」（模块见 07-05）。

第二类误用是混淆「回调线程」与「主循环线程」的字段读写。`notifications.cpp:28-34` 明确写着回调由 libsairedis 在独立线程运行、不应在其中做 DB 操作；字段的落库与状态更新发生在主循环的 `doTask(NotificationConsumer&)` 里。把回调里读到的 `sai_port_oper_status_notification_t` 字段直接拿去改 `PortsOrch::m_portList`（portsorch.h:395）而不经过主循环，会引发并发问题。排障时应区分「通知是否到达回调」与「主循环是否消费」，前者看 SAI 侧日志、后者看 pops 与 DB 更新，机制见「原理见 06-04」「原理见 06-05」。

第三类误用是忽视消费者生命周期约束。`Entry::consumer` 是指针且源码明确要求「must outlive this orch」，把局部或提前析构的消费者注册进 `m_consumers`，会在定时器遍历时悬垂。注册顺序由 OrchDaemon 保证统计发布器先构造（orchdaemon.cpp:212-218），但消费者存活由各业务 Orch 负责；新增注册点时应确认指针来源。调试统计字段全为 0 时，先查 `gNotifConsumerStatsOrch` 是否为空（单测或 fabric-only 进程中可能不构造，此时 registerConsumer 是空操作），再查定时器是否 start，而不是怀疑 `getStats()`。

第四类是跨版本字段假设。把旧版通知结构、旧 `Select` 返回语义或旧 `PortOperErrorEvent` 键名套到当前快照，会因 SAI 枚举扩展、LruDedup 队列字段新增（`lru_*` 系列）与受控恢复路径而失效。调试时若发现读到「看似合理但明显不对」的值，先确认二进制与所用头文件是否同一快照，再用本篇字段级核验片段或 `grep -n` 命令逐字段比对，最后回到源码确认行号。所有涉及接纳率、下发时延与通知吞吐的结论一律标注「需在目标机型实测」，基准方法见 08-01，诊断树见 08-03。把本篇当流程书或参数书读同样是误用：传递机制去 06 册（原理见 06-04、06-05），计数器参数去 04 册（参数见 04-04），模块能力去 07 册（模块见 07-05、07-03）。
