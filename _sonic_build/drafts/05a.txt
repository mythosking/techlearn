# SONiC 技术资料 · 05 关键数据结构字段详解（分片 A）

## 05-01 全册结构分层与跨文档索引

### 1. 本篇定位与覆盖范围

本篇是 05 册「关键数据结构字段详解」的开篇，也是整册乃至全集的结构体地图与跨文档索引。按总纲第 2 节的唯一权威源约定，全集只有 05 册允许出现结构体逐字段定义，其余各册遇到结构体一律只点名、给真实源码路径并写「字段见 05-xx」；反过来，05 册只讲字段含义、类型、内存布局倾向、生命周期与关联函数入口，不展开机制流程（统一写「原理见 06-xx」），不重列配置参数（统一写「参数见 04-xx」），不介绍模块能力（统一写「模块见 07-xx」）。因此本篇不承担任何流程讲解，它的任务是把 05-02 至 05-09 八篇正文所覆盖的结构体族，安放到一张按 Redis 分层与数据面边界划分的坐标系里，并交代每层对应的真实源码位置、对象生命周期，以及和 04 册参数、06 册原理、07 册模块之间的反查关系。事实基准统一写「上游 master 快照（2026-11 抓取）」；各子仓 `configure.ac`、`Makefile`、`setup.py` 中的版本字样只作核验依据，本套资料不抄具体版本号进正文，需要说明来源时写「需对照实际版本核验」。

必须先说清事实锚点与一个决定全册写法的硬事实。上游快照解压在 `_sonic_build/upstream_src/`，其下有八个子仓，每个子仓再解压出一层 `xxx-master/` 归档目录，真实仓库根为 `upstream_src/<子仓>/<子仓>-master/`：`sonic-buildimage`（构建、容器、平台、镜像）、`sonic-swss`（orchagent、cfgmgr、各 syncd）、`sonic-sairedis`（syncd、SAI 元数据、vslib）、`sonic-utilities`（show / config CLI）、`sonic-mgmt-common`（YANG、CVL、translib）、`sonic-platform-common`（平台外设基类）、`sonic-py-swsssdk`（Python DB 访问封装）、`sonic-dbsyncd`（LLDP 等数据同步）。本册正文路径一律写成去掉归档层前缀的仓库内惯用写法，例如 `orchagent/orch.h`、`src/swsssdk/dbconnector.py`、`src/sonic-config-engine/`。这里要特别指出：本快照**没有** `sonic-swss-common` 子仓，而 `FieldValueTuple`、`Table`、`ProducerStateTable`、`ConsumerStateTable`、`DBConnector`、`KeyOpFieldsValuesTuple` 等 C++ 类型的定义本体恰恰属于 `sonic-swss-common`；它们的惯用头文件写作 `common/fieldvaluetuple.h`、`common/table.h`、`common/dbconnector.h` 一类，但这些路径在本快照无法核实，凡涉及定义本体一律写「不在本快照，需对照实际版本核验」，只给可核实的「使用点」（如 `orchagent/orch.h`、`cfgmgr/teammgr.cpp`、`lib/recorder.cpp`）与惯用目录名，绝不臆造行号、成员偏移与类型细节。这一条决定了 05-01、05-02、05-03 三篇的取证边界，后续不再重复解释。

本篇把 05 册覆盖的结构体族划成五层，划分依据是「对象在流水线中处于哪一段、由谁持有」，不是调用顺序（调用顺序属「原理见 06-01」）。**第一层是数据库访问与连接层**：以 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig`、`SonicV2Connector` 与 C++ 侧 `DBConnector` 为代表，负责把逻辑库名解析成编号并建立连接，字段归 05-03。**第二层是表项与元组层**：以 `FieldValueTuple`、`KeyOpFieldsValuesTuple`、`Table`、`ProducerStateTable`、`ConsumerStateTable` 为代表，负责把「表—键—字段值」这一 Redis 数据模型封装成 C++ / Python 对象，是本篇姊妹篇 05-02 与 05-03 的核心。**第三层是控制面编排对象层**：以 `orchagent/orch.h`、`orch.cpp` 的 `Orch`、`Request`、`Consumer`、`Executor` 及各派生 Orch 为代表，消费期望状态、生成 ASIC 对象，字段归 05-05 与 05-07。**第四层是 SAI 对象与 ASIC_DB 层**：以 `sai_object_id_t`、SAI attribute、`sonic-sairedis/syncd/` 的 `SaiObj`、`FlexCounter` 为代表，字段归 05-04 与 05-06。**第五层是状态、事件与平台层**：以 `STATE_DB` 表项、`PORT_STATE`、`WARM_RESTART`、`platform.json` 及 `NotificationConsumer`、`Select` 为代表，字段归 05-08 与 05-09。五层之间的字段归属、与各册的反查关系见图 05-01-01，图中实线为层间数据归属链，虚线为跨册反查链。

### 3. 逐项详解

以下按五层逐层详解。每层给出「入口源码位置 → 代表对象的字段族特征 → 生命周期 → 不透明边界 → 归口」，全部字段以可核实源码为准，凡未核验到的一律写「需对照实际版本核验」。

**第一层数据库访问与连接层**。在 Python 侧，入口是 `sonic-py-swsssdk/src/swsssdk/dbconnector.py`，其中 `SonicDBConfig` 从 `/var/run/redis/sonic-db/database_config.json` 与 `database_global.json` 读取 `DATABASES` 与 `INSTANCES`，`get_dbid(db_name)` 取 `["DATABASES"][db_name]["id"]`，`SonicV2Connector.connect()` 用该编号建立连接；`configdb.py` 的 `ConfigDBConnector` 再向上提供 `set_entry`、`get_entry`、`get_table` 等读写封装。这组对象的字段族特征是「运行时配置驱动」：字段名如 `DATABASES`、`INSTANCES`、`id` 描述的是 JSON 配置结构，而非编译期常量，因此「某库是某号」在本层根本不成立。在 C++ 侧，入口是 `orchagent/orch.h` 所 include 的 `dbconnector.h`、`table.h`，`DBConnector`、`Table` 的定义在 `sonic-swss-common`、不在本快照；本快照能核实的是使用形态，如 `cfgmgr/buffermgrd.cpp` 的 `DBConnector applDb("APPL_DB", 0)`，其中第二参数含义需对照实际版本核验，不得当成数据库编号。生命周期上，连接对象随进程启动创建、随进程退出销毁，`SonicDBConfig` 的配置在连接建立期读入后基本只读。字段归 05-03，参数见 04-04，原理见 06-02，模块见 07-05。

**第二层表项与元组层**。这是 05-02 与 05-03 的主战场。SONiC 把一条配置或状态表达成「表名 + 键 + 若干字段值三元组」：`CONFIG_DB` 中一条端口配置在 Redis 里是一个 hash，表名如 `PORT`、键如 `Ethernet1`、字段如 `speed`、`mtu`，值一律是字符串。C++ 侧的 `FieldValueTuple` 就是「字段名—字段值」这一对的封装，使用点遍布 `orchagent/`：`vector<FieldValueTuple> fvVector` 反复出现，`FieldValueTuple("trap_ids", trap_id_list_str)` 表明两参数构造顺序为「先字段名、后字段值」，`cfgmgr/teammgr.cpp` 的 `fv.first == "mac"`、`fv.first == "lacp_key"`、`fv.first == "mtu"` 进一步确认 `first` 存字段名。更高一层是 `KeyOpFieldsValuesTuple`（`lib/recorder.cpp` 中使用），它由「键、操作、字段值集合」构成，访问器 `kfvKey()`、`kfvOp()`、`kfvFieldsValues()` 在 `warmrestart/warmRestartHelper.cpp`、`fpmsyncd/routesendcoalescer.cpp`、`fdbsyncd/fdbsync.cpp` 等处大量出现，操作取值有 `SET_COMMAND` 与 `DEL_COMMAND`。这些访问器与类型的定义本体同样来自 `sonic-swss-common`、不在本快照，本册只认使用形态。生命周期上，元组随一次变更事件产生，经队列传递、被消费后即释放，不跨事件持久；字段值不带类型信息，数值、布尔、列表都以字符串承载，解析责任在消费方。字段归 05-02 与 05-03，参数见 04-02 与 04-04，原理见 06-02，模块见 07-05。

**第三层控制面编排对象层**。入口是 `sonic-swss/orchagent/orch.h` 与 `orch.cpp`，`Orch` 基类持有一张「表名到处理函数」的映射，并在 `m_*Table` 成员中持有各业务表对象；`orchdaemon.cpp` 完成各派生 Orch 的注册，`main.cpp` 进入主循环。本节不列成员表（那是 05-05 的任务），只点出字段族特征：本层字段分两类，一类是「表连接器与消费者」对象（如 `ConsumerStateTable`），一类是「业务状态缓存」（如 `m_portTable`、`m_routeTable` 一类以 ASIC 对象为值的映射）；它们共同 consume `APPL_DB` 并 produce `ASIC_DB`。`orch.h` 中可核实的常量也属于本层的字段环境：`delimiter=':'`、`list_item_delimiter=','`、`ref_start='['`、`ref_end=']'`、`range_specifier='-'`、`config_db_key_delimiter='|'`、`state_db_key_delimiter='|'`，以及宏 `CONFIGDB_KEY_SEPARATOR "|"`、`DEFAULT_KEY_SEPARATOR ":"`、`VLAN_SUB_INTERFACE_SEPARATOR "."`；这些分隔符决定了复合键如何拆分，是读字段表前必须先建立的编码约定。生命周期上，Orch 对象随 `orchagent` 进程常驻，业务状态缓存在整个进程期有效，warm reboot 时还会经 `warmrestart/` 恢复。字段归 05-05 与 05-07，参数见 04-06，原理见 06-04，模块见 07-03。

**第四层 SAI 对象与 ASIC_DB 层**。SAI 定义与芯片无关的统一 API；本快照 `sonic-sairedis/SAI/` 是空目录，不得据它编造头文件与属性，可核验的是 `meta/`（元数据）、`vslib/`（虚拟 SAI）、`syncd/`（`Syncd.cpp`、`SaiSwitch.cpp`、`SaiObj.cpp`、`VendorSai.cpp`、`SaiDiscovery.cpp`、`FlexCounter.cpp`）与 `orchagent/main.cpp` 引入的 `sai.h`、`sairedis.h`。本层字段族以 `sai_object_id_t`（对象句柄）与 SAI attribute 为核心：orchagent 把端口、路由、邻居等翻译成 ASIC_DB 中的对象与属性，syncd 消费后经 SAI 编程芯片。关键边界是 `sai_object_id_t` 是句柄而非指针，不能解引用、不能跨版本持久化，属性值类型由 `meta/` 的元数据描述，厂商 SAI 实现闭源且不在本快照。生命周期上，对象随配置产生、随撤销删除，ASIC_DB 表项是 orchagent 交给 syncd 的待编程队列；`FlexCounter` 相关字段随计数器轮询配置启停。字段归 05-04 与 05-06，参数见 04-06，原理见 06-05，模块见 07-04。

**第五层状态、事件与平台层**。入口分散在 `STATE_DB` 表、`sonic-swss/lib/`（`recorder.cpp` 提供 `Recorder` 与 `SwSSRec`，可核验常量 `SWSS_FNAME = "swss.rec"`、`SAIREDIS_FNAME = "sairedis.rec"` 等）、`sonic-swss/orchagent/notifications.cpp` 与 `sonic-platform-common/sonic_platform_base/`。本层字段族包括运行时状态字段（`PORT_STATE`、`WARM_RESTART` 一类 STATE_DB 表项）、事件通知字段（NotificationConsumer 收到的通知负载）、平台外设字段（`platform.json` 描述的端口与外设映射）。`STATE_DB` 与 `CONFIG_DB` 一样使用竖线作复合键分隔符（`orch.h` 的 `state_db_key_delimiter` 与 `STATE_DB_KEY_SEPARATOR` 佐证这一编码约定，后者需对照实际版本核验）。生命周期上，状态字段由 syncd 与各 syncd 回写、随运行时变化，事件字段随通知产生、被消费后释放，平台字段在开机阶段读取后长期只读。字段归 05-08 与 05-09，参数见 04-04，原理见 06-10，模块见 07-09 与 07-10。

### 4. 典型示例

下面给出一段字段级核验用的 C++ 片段，作用是把 `orchagent/orch.h` 中可核实的分隔符常量打印出来，并用 FieldValueTuple 的使用形态展示「先字段名、后字段值」的构造约定。这不是流程代码，不触发任何配置下发，仅作为「读源码 → 对字段」的核对手段；其中 FieldValueTuple 的接口形态来自本快照使用点，定义本体不在本快照、需对照实际版本核验，故示例按惯用接口书写，编译前须以实际头文件为准。

```cpp
#include <iostream>
#include <string>
#include "dbconnector.h"

extern const char delimiter;
extern const char config_db_key_delimiter;
extern const char state_db_key_delimiter;
#define VLAN_SUB_INTERFACE_SEPARATOR "."

int main()
{
    std::cout << "delimiter=" << delimiter << "\n";
    std::cout << "config_db_key_delimiter=" << config_db_key_delimiter << "\n";
    std::cout << "vlan_sub_interface_separator=" << VLAN_SUB_INTERFACE_SEPARATOR << "\n";
    // 字段值二元组：字段名 "mtu"，字段值 "9100"，顺序见 cfgmgr/teammgr.cpp 使用点
    FieldValueTuple fv("mtu", "9100");
    std::cout << "field=" << fv.first << " value=" << fv.second << "\n";
    return 0;
}
```

在一个把上述片段接入调试构建、链接了实际 `sonic-swss-common` 头文件的核验桩里，会得到类似下面的输出。示例输出，具体格式需对照实际版本核验。

```text
delimiter=:
config_db_key_delimiter=|
vlan_sub_interface_separator=.
field=mtu value=9100
```

逐行判读如下，合计超过 150 字。第一行 `delimiter=:` 对应 `orchagent/orch.h:33` 的 `const char delimiter = ':'`，它是键内字段的默认分隔符；若打印结果与冒号不符，先确认链接的二进制与本快照头文件是否同一版本，而不是怀疑打印语句。第二行 `config_db_key_delimiter=|` 对应 `orch.h:39`，说明 `CONFIG_DB` 的复合键用竖线连接，例如表名与键的拼接形态为「PORT 竖线 Ethernet1」；这里的竖线是字段值的一部分，表格中书写时必须转义，且它不是 Redis 命令的分隔符。第三行 `vlan_sub_interface_separator=.` 对应 `orch.h:57` 的宏，用于 VLAN 子接口名中主接口与 VLAN 编号的切分，与默认冒号分隔符用途不同，混用会导致子接口键解析失败。第四行 `field=mtu value=9100` 印证 `FieldValueTuple` 的两参数构造顺序为「先字段名、后字段值」，与 `orchagent/copporch.cpp` 中 `FieldValueTuple("trap_ids", trap_id_list_str)` 的写法一致，`first` 为字段名、`second` 为字段值；需要强调的是，值 `9100` 在这里仍是字符串而非整数，任何数值解释都由消费方完成，这正是 SONiC 表项「值无类型」字段语义的直接体现。上述常量与接口只说明存在与取值，完整字段定义见 05-02 与 05-03，键如何进入流水线见「原理见 06-02」。

### 6. 版本差异

最根本的差异来自仓库边界。本快照是 `sonic-buildimage` 主仓加七个子仓，而 `sonic-swss-common` 不在其中；因此凡是属于公共 C++ 库的结构体（FieldValueTuple、Table、DBConnector 等），本套资料只能通过本快照的「使用点」反推形态，不能给出定义本体的行号与布局。上游完整源码树中这些类型有独立头文件与版本演进，但具体接口稳定性、成员增删与 ABI 边界需对照实际版本核验，本册一律写「不在本快照，需对照实际版本核验」。相对地，`sonic-py-swsssdk/src/swsssdk/` 与 `src/sonic-config-engine/` 在本快照可核实，Python 侧的 `SonicDBConfig`、`ConfigDBConnector` 字段与 JSON 配置结构是可以直接取证的部分。

第二个差异是「值无类型」这一模型跨版本保持稳定。`FieldValueTuple` 的字段名与字段值都以字符串承载，`CONFIG_DB` 的 `config_db.json` 里 `speed`、`mtu`、`admin_status` 也一律是字符串；无论具体版本如何演进，数值解析、布尔判断与列表拆分都在消费方完成。因此跨版本比对字段时，要看的是字段名与取值约定，而不是把某个值当成固定类型。默认值与合法取值范围属参数范畴，统一写「参数见 04-02 ｜ 参数见 04-04」，本册不列。

第三个差异是编码约定与条件字段。`orchagent/orch.h` 中的分隔符常量在本快照可核实，但不同版本可能调整复合键拼接规则或新增命名空间支持，凡出现多 ASIC、chassis 与 `VLAN_SUB_INTERFACE_SEPARATOR` 相关字段时，一律写「受平台与版本限制，需对照实际版本核验」，不得宣称全平台无条件支持（原理见 06-11 ｜ 模块见 07-10）。`warmrestart/` 相关字段随 warm reboot 能力演进，同样受平台与版本限制。性能、容量、收敛、时延与吞吐类结论一律标注「需在目标机型实测」，不给绝对值（基准方法见 08-01 ｜ 调优见 08-02）。

### 7. 常见误用与调试

第一类误用是把不在本快照的类型当成可展开结构。最常见的是直接断言 `FieldValueTuple` 或 `Table` 的成员声明与行号；正确做法是先确认定义本体的仓库是否在本快照内，若不在（如 `sonic-swss-common`），就写「不在本快照，需对照实际版本核验」，只给使用点（如 `orchagent/copporch.cpp` 的构造、`cfgmgr/teammgr.cpp` 的 `first` 访问、`lib/recorder.cpp` 的 `kfvFieldsValues`），不要臆造行号。第 4 节给出的 `test -d` / `grep -n` 组合是最快的确认手段；若结果与本节不符，以 `upstream_src/<子仓>/<子仓>-master/` 下实际目录为准并标注「需对照实际版本核验」。

第二类误用是把不透明句柄当普通结构展开。`sai_object_id_t` 是对象句柄，不能像指针那样解引用或算偏移；厂商 SAI 实现闭源且不在本快照，`sonic-sairedis/SAI/` 在本快照为空目录，任何据它编造的属性名与字段类型都不可靠。同理，跨版本持久化 `sai_object_id_t`、把 `ASIC_DB` 表项当成可直接读写的内存结构，都会在重启或升级后失效。正确做法是只用公开访问器与表项读写接口，内部布局一律写「需对照实际版本核验」。

第三类误用是把 05 册当流程书或参数书读。想理解「配置怎么从 `CONFIG_DB` 走到 ASIC」应去 06 册（原理见 06-01 ｜ 原理见 06-02），想查一张表有哪些字段与合法取值应去 04 册（参数见 04-02 ｜ 参数见 04-04），想按目录找模块应去 07 册（模块见 07-05）；在 05 册里找调用链或命令全集只会得到交叉引用。反过来，在 06 / 07 / 08 册里看到完整字段表属于去重铁律被破坏，应改写成「字段见 05-xx」。

第四类是跨版本字段假设与能力边界误判。把某个快照里的分隔符常量、字段名、JSON 结构当成永恒不变，或把 `config` 命令返回成功等同于硬件已下发，都是高频错误。排障时应按「`CONFIG_DB` 有表项、`APPL_DB` 有意图、`ASIC_DB` 有对象、`STATE_DB` 与 `show` 有结果」逐段核对，而不是一上来怀疑硬件（排障见 08-03）。同时守住九条能力边界：SONiC 是白盒交换机 NOS 而非软件路由器；控制面容器化、数据面在 ASIC、经 SAI 下发；不写死 Redis DB 编号；`orchagent` 不直接操作硬件；CLI 只读写 DB；warm reboot、多 ASIC 与 chassis 受平台与版本限制；镜像构建依赖 sonic-slave 容器与 ONIE；一切性能数字需实测。所有涉及吞吐、时延、容量的结论一律标注「需在目标机型实测」，基准方法见 08-01，诊断树见 08-03。

### 3. 逐项详解

以下按「表项组织结构 → 字段值元组 → 三元组与访问器 → 分隔符与键编码 → 具体表字段 → 生命周期」六组逐项详解，全部以可核实源码为准。

**第一组：表项的组织结构**。`CONFIG_DB` 与 `APPL_DB` 都是 Redis 逻辑库，一条表项在库里表现为一个哈希：外层是表名，键是哈希的 key，字段名与字段值是哈希的 field/value。`config_db.TCS8400-24CC8CD.json` 清楚展示了这个三层结构——顶层键 `DEVICE_METADATA` 与 `PORT` 是表名，第二层 `localhost` 与 `Ethernet1` 是键，第三层 `hwsku`、`platform`、`lanes`、`speed` 等是字段名，对应值是字符串。复合键用竖线连接：`ORCH` 侧的 `config_db_key_delimiter='|'`（orch.h:39）与 `CONFIGDB_KEY_SEPARATOR "|"`（orch.h:55）佐证了这一编码，即「表名与键」之间以竖线分隔，例如端口表项的 key 形如 `PORT` 加竖线加 `Ethernet1`。需要强调，这里的竖线是键字符串的一部分，不是 Redis 命令或表格语法符号；本册表格书写时若出现该字符一律转义为 `\|`，正文则用「竖线」表述以免混淆。表项名与 schema 的完整清单属 04 册（参数见 04-02 ｜ 参数见 04-04），本篇只讲结构。

**第二组：FieldValueTuple 字段语义**。`FieldValueTuple` 是「字段名—字段值」二元组的封装，从本快照使用点可确证三点。其一，构造顺序：`portmgr.cpp` 的 `FieldValueTuple fv(field, value)` 与 `copporch.cpp` 的 `FieldValueTuple("trap_ids", trap_id_list_str)` 均表明第一参数是字段名、第二参数是字段值。其二，`first` 是字段名：`teammgr.cpp` 中 `fv.first == "mac"`、`fv.first == "lacp_key"`、`fv.first == "admin_status"`、`fv.first == "mtu"` 多处比较，说明 `first` 承载字段名，用于筛选待处理的字段。其三，`second` 是字段值：`lib/recorder.cpp` 遍历 `kfvFieldsValues(entry.tuple)` 得到字段集并序列化，值以字符串参与拼接。综合三点，`FieldValueTuple` 属于 pair 语义：`first` / `second` 分别为字段名与字段值，二者均为字符串，值不携带类型信息——`speed` 的 `200000`、`mtu` 的 `9100`、`admin_status` 的 `up` 在元组层都是同样的 `std::string`，数值化与合法性判断留给消费方（原理见 06-03）。定义本体在 `sonic-swss-common`、不在本快照，内部是否另有成员、是否有别名需对照实际版本核验。

**第三组：KeyOpFieldsValuesTuple 与访问器**。队列传递的不是零散的 `FieldValueTuple`，而是更高一层的 `KeyOpFieldsValuesTuple`，它由「键、操作、字段值向量」三部分构成。`lib/recorder.cpp` 的 `recordTupleAsync(prefix, tuple)` 与序列化语句 `entry.prefix + kfvKey(entry.tuple) + "|" + kfvOp(entry.tuple)` 展示了三部分的取值方式：`kfvKey()` 取键、`kfvOp()` 取操作、`kfvFieldsValues()` 取字段值集。操作取值有 `SET_COMMAND` 与 `DEL_COMMAND`，`warmrestart/warmRestartHelper.cpp` 中 `kfvOp(iter->second) == DEL_COMMAND` 用于识别删除，`fpmsyncd/macsync.cpp` 的 `bool add = (kfvOp(entry) == SET_COMMAND)` 用于判断写入。一个值得记录的细节来自 `fpmsyncd/routesendcoalescer.cpp`：注释明确写着空的 SET 在线上等同于 DEL（`an empty SET is a DEL on the wire`），即 `kfvOp()` 为 SET 但 `kfvFieldsValues()` 为空时，语义上按删除处理。这是字段判读时的高频陷阱，必须在消费侧结合字段集是否为空来解读操作。这些类型与访问器的定义本体同样来自 `sonic-swss-common`、不在本快照，本册只认使用形态，内部实现需对照实际版本核验。

**第四组：分隔符与键编码**。`orchagent/orch.h` 定义了一组编码常量，是解读所有表项键的前置知识：`delimiter=':'`（键内字段分隔符）、`list_item_delimiter=','`（列表项分隔符）、`ref_start='['` 与 `ref_end=']'`（引用范围括号）、`range_specifier='-'`（范围连接符）、`config_db_key_delimiter='|'`（CONFIG_DB 复合键分隔符）、`state_db_key_delimiter='|'`（STATE_DB 复合键分隔符）；宏有 `CONFIGDB_KEY_SEPARATOR "|"`、`DEFAULT_KEY_SEPARATOR ":"`、`VLAN_SUB_INTERFACE_SEPARATOR "."`。这些常量解释了为什么 `PORT.Ethernet1.lanes` 的值 `25,26,27,28` 以逗号分隔、为什么 VLAN 子接口名以点号切分、为什么复合键以竖线拼接。读写时机上，它们都是编译期常量、运行期只读，不随运行时 `database_config.json` 变化；这与数据库编号形成鲜明对照——编号是运行时配置值，禁止写死（参数见 04-04）。多 ASIC 与命名空间场景可能改变键的编码规则，受平台与版本限制，需对照实际版本核验（原理见 06-11）。

**第五组：具体表字段逐项判读**。以本快照的 `config_db.TCS8400-24CC8CD.json` 为样本：`DEVICE_METADATA` 表只有 `localhost` 一个键，其 `hwsku` 为 `TCS8400-24CC8CD`、`platform` 为 `x86_64-tencent_tcs8400-r0`、`mac` 为 `58:69:6c:f1:23:12`、`hostname` 为 `sonic`；这四个字段在开机阶段由 `sonic-cfggen` 结合 minigraph 与机型目录渲染生成（参数见 04-02 ｜ 模块见 07-11）。`PORT` 表以端口名 `Ethernet1` 至多端口为键，每个键下有 `lanes`、`alias`、`index`、`speed`、`admin_status`、`mtu` 六个字段：`lanes` 是物理通道号列表，逗号分隔；`alias` 是面板可见别名；`index` 是端口序号；`speed` 是速率；`admin_status` 是管理状态；`mtu` 是最大传输单元。这六个字段由 `cfgmgr/portmgr.cpp` 订阅变更后校验并写入 `APPL_DB` 的端口表（`m_appPortTable.set(alias, field_values)`），再由 orchagent 消费（原理见 06-03 ｜ 原理见 06-06）。字段名与合法取值集合的权威来源在 04 册，本册只确认字段在本快照中真实存在。

**第六组：生命周期**。`CONFIG_DB` 表项在开机配置阶段写入、运行期长期存在，可经 CLI 修改；`FieldValueTuple` 随一次字段搬运在 `cfgmgr` 内构造、写入 `APPL_DB` 后即释放，不跨事件持久；`KeyOpFieldsValuesTuple` 随变更事件进入队列、被消费后释放；`APPL_DB` 表项是 orchagent 的期望状态输入，随配置变更更新。读写时机可归纳为：配置字段「开机写、mgrd 读」，元组字段「构造写、消费读」，访问器「消费期只读」，分隔符常量「编译期定、运行期只读」。贯穿全链路的一条纪律是：字段写入 `APPL_DB` 只代表期望状态就绪，不代表已下发 ASIC，判读必须按库逐段核对（原理见 06-01 ｜ 排障见 08-03）。

### 4. 典型示例

下面给出一组字段级核验实例。第一段用 `redis-cli` 直接读取表项，展示 `CONFIG_DB` 中一条真实端口表项在 Redis 里的哈希形态；第二段用 C++ 片段展示 `FieldValueTuple` 的构造与访问器判读。两段都不是流程代码，仅用于「读表 → 对字段」。命令中数据库以库名表达，不写死编号——库名到编号的映射由运行时 `database_config.json` 决定（参数见 04-04）。

```bash
# 前置检查：确认 redis 客户端可用、库配置存在（不写死库编号）
command -v redis-cli >/dev/null && echo "redis-cli ok"
ls /var/run/redis/sonic-db/database_config.json && echo "db config ok"
# 执行：读取 CONFIG_DB 中一条端口表项与元数据表项（库名映射见 04-04）
redis-cli -h 127.0.0.1 -p 6379 -n "$(sonic-cfggen -d -v 'DATABASES|\"CONFIG_DB\"|\"id\"')" \
  HGETALL "PORT|Ethernet1"
# 复核：确认字段集非空
redis-cli -h 127.0.0.1 -p 6379 -n "$(sonic-cfggen -d -v 'DATABASES|\"CONFIG_DB\"|\"id\"')" \
  HLEN "PORT|Ethernet1"
```

示例输出，具体格式需对照实际版本核验。

```text
redis-cli ok
db config ok
1) "lanes"
2) "25,26,27,28"
3) "alias"
4) "Eth200GE0/1"
5) "index"
6) "1"
7) "speed"
8) "200000"
9) "admin_status"
10) "up"
11) "mtu"
12) "9100"
12
```

逐行判读如下，合计超过 150 字。前两行是前置检查：`redis-cli ok` 说明客户端可用，`db config ok` 说明运行时库配置存在，这一步不可省，因为 SONiC 的库编号来自 `/var/run/redis/sonic-db/database_config.json`，不是源码常量（参数见 04-04）；命令用 `-n` 接一段 `sonic-cfggen -d` 取值来间接得到编号，正是「不写死编号」的写法，其中转义的竖线用于表达配置内的键路径，属 shell 层写法而非 Redis 语法。第三段 `HGETALL "PORT|Ethernet1"` 按「表名竖线键」读取端口表项，返回的十二行是六组 field/value：`lanes` 为 `25,26,27,28` 说明该端口绑定四个物理通道，逗号分隔与 `list_item_delimiter=','`（orch.h:34）一致；`alias` 为 `Eth200GE0/1` 是面板别名；`index` 为 `1`、`speed` 为 `200000`、`mtu` 为 `9100`、`admin_status` 为 `up`，与 `config_db.TCS8400-24CC8CD.json` 第 12 至 17 行逐字段吻合，说明本快照配置与库内表项一致，属正常特征。若 `speed` 返回空或与 `lanes` 数量不匹配，应先回查 `portmgr` 是否完成搬运（原理见 06-03），而不是怀疑硬件。最后一行 `HLEN` 返回 `12`，即六个字段的 field/value 总数，用来确认字段集非空——这正是「空字段集」判读的入口：在 `KeyOpFieldsValuesTuple` 语境下，操作为 SET 但字段集为空会被按 DEL 处理（`fpmsyncd/routesendcoalescer.cpp` 的注释佐证），因此读表后先确认字段集是否为空，是避免误判删除的关键步骤。整段输出只反映配置库内容，不代表期望状态已生成或已下发 ASIC，须按库逐段核对（原理见 06-01 ｜ 排障见 08-03）。

第二段示例用 C++ 片段展示元组字段的构造与访问器判读，接口形态来自本快照使用点，定义本体需对照实际版本核验。

```cpp
#include <iostream>
#include <string>
#include <vector>
#include "table.h"

using namespace swss;

void inspect_tuple(const KeyOpFieldsValuesTuple& entry)
{
    const std::string key = kfvKey(entry);
    const std::string op  = kfvOp(entry);
    const std::vector<FieldValueTuple> fvs = kfvFieldsValues(entry);
    std::cout << "key=" << key << " op=" << op << " fields=" << fvs.size() << "\n";
    for (const auto& fv : fvs)
    {
        std::cout << "  " << fv.first << "=" << fv.second << "\n";
    }
    // 空 SET 视为删除，判读时必须结合字段集是否为空
    if (op == SET_COMMAND && fvs.empty())
    {
        std::cout << "note: empty SET treated as DEL\n";
    }
}

int main()
{
    FieldValueTuple fv("mtu", "9100");
    inspect_tuple(KeyOpFieldsValuesTuple("PORT|Ethernet1", SET_COMMAND, {fv}));
    return 0;
}
```

在一个链接了实际 `sonic-swss-common` 的核验桩里会得到类似下面的输出。示例输出，具体格式需对照实际版本核验。

```text
key=PORT|Ethernet1 op=SET fields=1
  mtu=9100
```

这段输出印证三点。第一行 `key=PORT|Ethernet1` 说明 `kfvKey()` 返回的是完整复合键，竖线连接表名与键，与 `config_db_key_delimiter='|'`（orch.h:39）一致；`op=SET` 是 `kfvOp()` 的操作标记，来自 `SET_COMMAND`；`fields=1` 是 `kfvFieldsValues()` 返回的字段集大小。第二行 `mtu=9100` 展示 pair 语义：`fv.first` 为字段名 `mtu`、`fv.second` 为字段值 `9100`，与 `teammgr.cpp` 的 `fv.first == "mtu"` 写法和 `portmgr.cpp` 的 `FieldValueTuple fv(field, value)` 构造顺序一致；值 `9100` 仍是字符串，数值解释在消费方。注意示例中的 `FieldValueTuple`、`KeyOpFieldsValuesTuple`、`SET_COMMAND` 定义本体都不在本快照，接口形态需对照实际版本核验，本片段仅用于字段语义演示，不作为可直接编译的代码承诺（模块见 07-05）。

统一四段式反查写法为：`字段见 05-02 ｜ 参数见 04-02 ｜ 原理见 06-03 ｜ 模块见 07-05`。本篇内部字段可直接写「字段见本篇 05-02」或不再自引，但参数、原理、模块三项必须给具体篇号。全角竖线两侧各留一个空格；表格单元格内出现半角竖线必须写成转义的 `\|`，例如键示例写作 `PORT\|Ethernet1`。

### 6. 版本差异

第一处差异是定义本体的仓库边界。本快照没有 `sonic-swss-common`，因此 `FieldValueTuple`、`KeyOpFieldsValuesTuple` 与表连接器的完整定义、行号与成员列表无法在本快照核实；本篇只能从使用点确认「先字段名后字段值」的构造顺序、`first` 存字段名、`kfvKey` / `kfvOp` / `kfvFieldsValues` 三类访问器与 `SET_COMMAND` / `DEL_COMMAND` 操作取值。上游完整源码树中这些类型有独立头文件与演进历史，具体接口稳定性、成员增删与 ABI 边界需对照实际版本核验。相对地，`config_db.json` 的配置字段、`orch.h` 的分隔符常量、`cfgmgr/` 与 `lib/recorder.cpp` 的使用形态在本快照可直接取证。

第二处差异是「值无类型」模型的跨版本稳定性。`FieldValueTuple` 的 `first` / `second` 与 `config_db.json` 的字段值一律是字符串，`speed`、`mtu`、`admin_status` 在元组层没有类型区分；无论版本如何演进，数值化与合法性判断都在消费方完成。因此跨版本比对时，应关注字段名与取值约定，而非把某个字段当成固定类型。合法取值范围与默认值属参数范畴，统一写「参数见 04-02 ｜ 参数见 04-04」，本篇不列。

第三处差异是编码约定与空 SET 语义。`orch.h` 的分隔符常量在本快照可核实，但不同版本可能调整复合键拼接或新增命名空间，`VLAN_SUB_INTERFACE_SEPARATOR`、多 ASIC 与 chassis 相关字段一律写「受平台与版本限制，需对照实际版本核验」（原理见 06-11 ｜ 模块见 07-10）。`fpmsyncd/routesendcoalescer.cpp` 记录的「空 SET 视为 DEL」是字段判读的重要版本相关约定，不同版本对空字段集的处理可能不同，必须以当前版本源码为准。所有涉及收敛、下发时延、吞吐与容量的数字一律标注「需在目标机型实测」，不给绝对值（基准方法见 08-01 ｜ 调优见 08-02）。

### 7. 常见误用与调试

第一类误用是把不在本快照的元组定义当成可展开结构。最常见的错误是直接写出 `FieldValueTuple` 的完整成员列表与行号，或断言 `KeyOpFieldsValuesTuple` 的内部布局；正确做法是承认 `sonic-swss-common` 不在本快照，写「不在本快照，需对照实际版本核验」，只给使用点（`portmgr.cpp` 的构造、`teammgr.cpp` 的 `first` 访问、`recorder.cpp` 的访问器），不臆造行号与偏移。第 4 节的 `command -v`、`ls`、`redis-cli -n` 组合是确认库配置与字段是否真实存在的最快手段；若结果与本节不符，以 `upstream_src/<子仓>/<子仓>-master/` 下实际源码为准并标注「需对照实际版本核验」。

第二类误用是把 `first` / `second` 写反或把值当类型。`portmgr.cpp` 的 `FieldValueTuple fv(field, value)` 与 `teammgr.cpp` 的 `fv.first == "mtu"` 共同确认第一参数是字段名；把值写到 `first`、把字段名写到 `second`，会导致消费方按错误字段名筛选，最终表现为「配置写了但不生效」。同时要记住 `second` 的值一律是字符串，`9100` 不是整数、`up` 不是布尔，任何数值或布尔解释都必须由消费方显式完成（原理见 06-03）。

第三类误用是忽视空 SET 与操作语义。`fpmsyncd/routesendcoalescer.cpp` 明确记录空 SET 在线上等同 DEL，因此判读 `kfvOp()` 为 SET 的变更时，必须同时检查 `kfvFieldsValues()` 是否为空；只看操作标记就把空 SET 当成写入，会对删除事件产生完全相反的结论。同理，只看 `CONFIG_DB` 里有表项就认为硬件已下发，是违反异步流水线的典型误判，应按「配置库有表项、期望库有意图、对象库有对象、状态库有结果」逐段核对（原理见 06-01 ｜ 排障见 08-03）。

第四类是跨版本与能力边界误判。把某个快照的字段名、分隔符、键编码当成永恒不变，或把厂商 SAI 实现、`sonic-swss-common` 的内部结构写成本快照事实，都是高频错误。排障时先确认二进制与所用源码是否同一快照，再回查对应配置字段与元组使用点；涉及多 ASIC、chassis、warm reboot 的字段一律写「受平台与版本限制，需对照实际版本核验」。所有涉及吞吐、时延、容量的结论一律标注「需在目标机型实测」，不给绝对值，基准方法见 08-01，诊断树见 08-03。本篇字段的完整定义以源码为准，凡本快照无法核实的一律标注「需对照实际版本核验」，不得补值。
