# SONiC 技术资料 · 05 关键数据结构字段详解（分片 C）

## 05-05 Orch、Request、Consumer 与 Executor 结构字段

### 1. 本篇定位与覆盖范围

本篇是 05 册中「控制面编排框架」一组核心类型的字段权威定义，逐字段核对 orchagent 调度框架所依赖的四个基类与一组辅助类型。按总纲第 2 节与 SPEC 第 4 节的唯一权威源约定，全集只有 05 册允许出现结构体逐字段定义，其余各册遇到这些类型一律只点名、给真实源码路径并写「字段见 05-05」；反过来，本篇只负责交代字段名、类型、含义、源码位置、读写时机与关联函数入口，**不展开编排机制的流程与状态机**（统一写「原理见 06-04」），**不重列 SAI 与 orchagent 的配置参数**（统一写「参数见 04-06」），**不介绍 orchagent 模块的能力边界**（统一写「模块见 07-03」）。事实基准统一写「上游 master 快照（2026-11 抓取）」，不抄具体版本号，需要说明来源时写「需对照实际版本核验」。

必须先说清源码落点与路径形态。上游快照解压在 `_sonic_build/upstream_src/`，本组类型的真实头文件是 `sonic-swss/sonic-swss-master/orchagent/orch.h`（其中定义 `class Executor`、`class ConsumerBase`、`class Consumer`、`class RingBuffer`、`class Orch`、`class Orch2` 以及 `referenced_object`、`SyncMap`、`task_process_status`、`ref_resolve_status` 等辅助类型）与 `sonic-swss/sonic-swss-master/orchagent/request_parser.h`（其中定义 `class Request`、`request_description_t` 与 `request_types_t`）；实现分别在同目录的 `orch.cpp` 与 `request_parser.cpp`。本套资料正文中的路径一律采用去掉 `xxx-master/` 归档层前缀的仓库内惯用写法，例如 `orchagent/orch.h`、`orchagent/request_parser.h`。需要特别提醒的是，`Executor`、`Consumer`、`Orch` 这些类的若干方法签名里引用了 `swss::Selectable`、`swss::ConsumerTableBase`、`swss::KeyOpFieldsValuesTuple`、`swss::NotificationConsumer`、`ResponsePublisher`、`RetryCache` 等类型，其中相当一部分来自 `sonic-swss-common`——该子仓**不在本快照**（见 SPEC 第 2.1 节第 2 条），因此本篇只按 `orch.h` 中出现的指针/引用/成员形态记录其存在与用途，其内部布局一律写「不在本快照，需对照实际版本核验」，不得编造字段或偏移。

本篇把覆盖范围划成四组。**第一组是 Executor 执行器族**，包括 `Executor` 基类、`ConsumerBase` 中间基类、`Consumer` 具体类，以及 `Executor` 持有的 `m_selectable`、`m_orch`、`m_name` 与 `ConsumerBase` 的 `m_toSync`、`m_orderedQueue`、`m_toSyncQueue`、`m_recordable`，它们是「一个 Orch 可挂多个执行器、一个执行器只归属一个 Orch」这一设计假设的载体。**第二组是 RingBuffer 环形缓冲**，包括 `buffer`、`head`、`tail`、`m_consumerSet`、`idle_status`、`thread_created` 等字段，用于把执行器的任务投递到独立线程。**第三组是 Orch 编排基类**，包括 `m_consumerMap`、`m_retryCaches`、`m_publisher` 三个受保护成员，以及 `Orch2` 对 `Request&` 的持有。**第四组是 Request 请求解析器**，包括 `request_description_t` 的三字段描述结构与 `Request` 的操作、键、属性三段存储。四组之间的关系、以及它们同 APPL_DB / ASIC_DB 的归属链见图 05-05-01，图中实线为对象归属与调用入口，虚线为跨册反查链。

### 3. 逐项详解

以下按四组逐组详解。每组给出「入口头文件 → 字段族特征 → 生命周期 → 不透明边界 → 归口」，全部字段以源码为准，凡未核验到的一律写「需对照实际版本核验」。

**第一组 Executor 执行器族。** 入口为 `orchagent/orch.h:112` 的 `class Executor : public swss::Selectable`。源码在类定义前写下三条设计假设：一个 Orch 可以有一个或多个 Executor；一个 Executor 必须且只能属于一个 Orch；Executor 持有一个 new 出来的 selectable 指针并在析构时删除。这三条直接决定了字段布局。该类公开段有静态成员 `static std::shared_ptr<RingBuffer> gRingBuffer`（orch.h:145）与成员函数 `processAnyTask(AnyTask&&)`；受保护段的字段为 `swss::Selectable *m_selectable`（149）、`Orch *m_orch`（150）、`std::string m_name`（153）。其中 `m_selectable` 是被装饰的真实事件源，`Executor` 通过覆写 `getFd()`、`readData()`、`hasCachedData()`、`initializedWithData()`、`updateAfterRead()` 五个方法把调用转发给 `m_selectable`（orch.h:125-129），这是典型的装饰器形态；`m_orch` 是反向归属指针，由 `getOrch()`（144）返回；`m_name` 由 `getName()`（139）返回，是 RingBuffer 判定「是否由本执行器服务」的键。拷贝构造与赋值被显式 `= delete`（132-133），`execute()` 与 `drain()` 是空虚函数（136-137），等待派生类覆盖。生命周期上，`m_selectable` 由构造参数置入、由 `~Executor()`（122）删除，`m_orch` 与 `m_name` 在构造期绑定后只读。`class ConsumerBase : public Executor`（161）在继承三个字段之外新增：`SyncMap m_toSync`（182，存最新 golden 状态的任务多映射）、`bool m_orderedQueue = false`（197，是否改用有序队列）、`std::deque<swss::KeyOpFieldsValuesTuple> m_toSyncQueue`（198，按请求顺序维护、允许同键多次出现）、私有段 `bool m_recordable = true`（233，是否录制 swss.rec）；`m_toSyncQueue` 的相关注释明确「Orch2 暂不支持」。其方法包括 `dumpTuple()`、`dumpPendingTasks()`、`recordTuple()`、`recordTuples()`、`addToSync()`（三个重载，208-212）、`addToRetry()`（219）、`refillToSync()`（221-222）与 `setOrderedQueue()`（226）。`class Consumer`（270）再继承一层，覆写 `getConsumerTable()` 返回 `swss::ConsumerTableBase*`（277），并提供 `getDbConnector()`、`getDbId()`、`getDbName()` 与 `execute()`/`drain()` 覆写（299-300）；这些函数涉及的 `ConsumerTableBase`、`DBConnector` 来自 `sonic-swss-common`，**不在本快照，需对照实际版本核验**。字段归本篇，机制原理见 06-04，模块见 07-03。

**第二组 RingBuffer 环形缓冲。** 入口为 `orchagent/orch.h:236` 的 `class RingBuffer`，实现在 `orch.cpp:29-130`。私有字段为 `std::vector<AnyTask> buffer`（239，任务环）、`int head = 0`（240）、`int tail = 0`（241）、`std::set<std::string> m_consumerSet`（242，由哪些执行器名共享）、`std::condition_variable cv`（244）、`std::mutex mtx`（245）、`bool idle_status = true`（246）；公开字段为 `bool thread_created = false`（250）、`std::atomic<bool> thread_exited{false}`（251）。`RING_SIZE` 默认为 30（orch.h:59），`SLEEP_MSECONDS` 为 500（orch.h:60）。公开方法包括 `pauseThread()`、`notify()`、`IsFull()`、`IsEmpty()`、`IsIdle()`、`push(AnyTask)`、`pop(AnyTask&)`、`addExecutor(Executor*)`、`serves(const std::string&)`、`setIdle(bool)`。这组字段的读写时机是：`m_consumerSet` 在 `addExecutor()`（orch.cpp:82）注册期写入、`serves()` 判定期只读；`head`/`tail`/`buffer` 在 `push()`/`pop()` 的环形操作中更新；`idle_status` 经 `setIdle()` 与 `IsIdle()` 读写；`thread_created`/`thread_exited` 反映环形线程生命周期。`Executor::processAnyTask()`（orch.cpp:593）按三种情形分支：全局缓冲未初始化或线程未创建时立即执行任务；本执行器未被缓冲服务时等待缓冲清空后在主线程执行；被服务时把任务 `push()` 进环并 `notify()`。这些字段本身只承载状态，具体调度语义属于机制范畴（原理见 06-04）。 орch.h 中 `Executor` 与 `Orch` 各有一个同名静态 `gRingBuffer`，属环形缓冲的全局入口，具体初始化点需对照实际版本核验。

**第三组 Orch 编排基类。** 入口为 `orchagent/orch.h:318` 的 `class Orch`。它提供六个构造函数重载（321-326），分别接受单表、多表、双库双表、带优先级表、TableConnector 向量等形态，默认优先级 `default_orch_pri = 0`（orch.h:65）。受保护字段只有三个：`ConsumerMap m_consumerMap`（410，表名到 `shared_ptr<Executor>` 的映射，`ConsumerMap` 定义在 159 行）、`RetryCacheMap m_retryCaches`（411）、`ResponsePublisher m_publisher{"APPL_STATE_DB"}`（432）。`m_consumerMap` 在 `addExecutor()`（orch.cpp:1223）与 `addConsumer()`（1211）注册期填充，在 `doTask()`（934）遍历；`m_retryCaches` 经 `createRetryCache()`（149）、`getRetryCache()`、`addToRetry()`（180）、`retryToSync()`（199）读写；`m_publisher` 在 `flushResponses()`（987）里把响应回写。这三个字段之外，`Orch` 的大量成员是protected 方法（引用解析 `resolveFieldRefValue`、`setObjectReference`、`removeObject` 等，414-426），它们操作的是 `type_map`/`object_map` 等局部或参数结构，不是对象字段，本篇不将其误列为成员。`class Orch2 : public Orch`（439）新增私有成员 `Request& request_`（459），是请求解析式 Orch 的基类，构造函数把外部 `Request` 以引用持有，其 `doTask(Consumer&)` 与纯虚 `addOperation(const Request&)`/`delOperation(const Request&)`（455-456）构成模板方法。辅助类型方面，`referenced_object`（orch.h:77）含 `m_objsDependingOnMe`、`m_objsReferencingByMe`、`m_saiObjectId`、`m_pendingRemove` 四字段；`SyncMap`（98）是 `std::multimap<std::string, swss::KeyOpFieldsValuesTuple>`；枚举 `task_process_status`（67，含 `task_success`/`task_invalid_entry`/`task_failed`/`task_need_retry`/`task_ignore`/`task_duplicated`）与 `ref_resolve_status`（303）是返回码而非字段，供字段读写的结果判定使用。字段归本篇，调度机制见 06-04，参数见 04-06。

**第四组 Request 请求解析器。** 入口为 `orchagent/request_parser.h:36` 的 `class Request`，描述结构 `request_description_t` 定义在 29-34 行，含 `std::vector<request_types_t> key_item_types`、`std::unordered_map<std::string, request_types_t> attr_item_types`、`std::vector<std::string> mandatory_attr_items` 三字段；枚举 `request_types_t`（10-27）从 `REQ_T_NOT_USED` 到 `REQ_T_STRING_LIST`，覆盖布尔、字符串、MAC、包动作、IP、前缀、VLAN、整数及各类列表。`Request` 的私有字段可分三段：**元数据段**为 `const request_description_t& request_description_`（215）、`char key_separator_`（216）、`bool is_parsed_`（217）、`size_t number_of_key_items_`（218）、`bool relaxed_attr_parsing_`（220），在受保护构造函数（186-193）初始化；**操作与键段**为 `std::string table_name_`（222）、`operation_`（223）、`full_key_`（224），以及五个按位置索引的键容器 `key_item_strings_`（225）、`key_item_mac_addresses_`（226）、`key_item_ip_addresses_`（227）、`key_item_ip_prefix_`（228）、`key_item_uint_`（229）；**属性段**为 `attr_names_`（230）与一组按属性名索引的容器，含 `attr_item_strings_`（232）、`attr_item_bools_`（233）、`attr_item_bool_list_`（234）、`attr_item_mac_addresses_`（235）、`attr_item_packet_actions_`（236）、`attr_item_vlan_`（237）、`attr_item_ip_`（238）、`attr_item_ip_prefix_`（239）、`attr_item_uint_`（240）、`attr_item_set_`（241）、`attr_item_ip_list_`（242）、`attr_item_mac_addresses_list_`（243）、`attr_item_uint_list_`（244）、`attr_item_string_list_`（245）。关键是这些字段的读写时机高度集中：`parse(const KeyOpFieldsValuesTuple&)`（39）经私有的 `parseOperation()`/`parseKey()`/`parseAttrs()`（197-199）一次性写入，`is_parsed_` 置位；此后所有 getter 都以 `assert(is_parsed_)` 前置断言（42-183）——未解析就取值会触发断言失败，这是调试时最常见的崩溃来源。`clear()`（40）用于复位复用。属性类型到容器的映射是硬约束：用 `getAttrUint()` 去读一个被描述为字符串的字段会在 `.at()` 处抛 `std::out_of_range`，因此字段类型必须与 `request_description_t` 一致。字段归本篇，解析机制见 06-02，参数见 04-06。

### 4. 典型示例

下面给出一段字段级核验用的 C++ 片段，作用是把 `Executor`、`ConsumerBase`、`Orch`、`Request` 中若干已核验字段的可访问性打印出来，用于确认本地快照的成员确实存在、类型与声明一致。这不是流程代码，不触发任何收包、调度或 SAI 调用，仅作为「读源码 → 对字段」的核对手段；其中 `Request` 的 getter 依赖 `is_parsed_`，故示例先构造一个最小描述并调用 `parse()`。

```cpp
#include "orch.h"
#include "request_parser.h"
#include <cstdio>

// 仅演示字段读取，不含任何调度逻辑
void dump_orc_fields(Executor& ex, ConsumerBase& cb, Orch& orch,
                     const Request& req)
{
    std::printf("executor name=%s\n", ex.getName().c_str());
    std::printf("orch ptr=%p\n", static_cast<void*>(ex.getOrch()));
    std::printf("toSync size=%zu ordered=%d recordable=%d\n",
        cb.m_toSync.size(), cb.m_orderedQueue ? 1 : 0,
        cb.isRecordable() ? 1 : 0);
    std::printf("request op=%s key=%s\n",
        req.getOperation().c_str(), req.getFullKey().c_str());
}
```

### 6. 版本差异

最根本的差异是这条编排链路的实现形态。早期版本的 orchagent 以较简单的 consumer / 任务队列直接驱动业务，而本快照的 `orch.h` 已经演化出 `Executor` → `ConsumerBase` → `Consumer` 的三层继承、`RingBuffer` 环形缓冲、`RetryCacheMap` 重试缓存与 `m_orderedQueue` 有序队列等一组较新的结构，说明框架在往「可插拔执行器 + 线程化投递 + 失败重试」方向演进。具体证据是：`m_orderedQueue` 与 `m_toSyncQueue` 的注释明确写着「Orch2 暂不支持」，表明新特性与旧式 `Orch2` 之间存在能力代差；`addToRetry()`（orch.cpp:180）、`retryToSync()`（199）、`createRetryCache()`（149）一族方法表明重试机制是后期加入的；`Executor::processAnyTask()`（593）对 `gRingBuffer` 的三分支判定表明环形线程是可选路径。这些演进痕迹意味着任何依赖「字段固定存在」「执行器一定在主线程执行」「任务一定立即处理」的假设都不可靠，结论一律以当前快照源码为准并标注「需对照实际版本核验」。

另一类差异来自依赖边界。`Executor`、`Orch` 的签名里大量出现 `swss::Selectable`、`swss::ConsumerTableBase`、`ResponsePublisher`、`RetryCache`、`Task`、`Constraint` 等类型，其中相当一部分定义在 `sonic-swss-common`，该子仓**不在本快照**（SPEC 第 2.1 节第 2 条）；因此本篇只能确认它们以指针/引用/成员形态出现在 `orch.h` 中，其内部布局、构造签名与版本兼容性都需对照实际版本核验，不得据印象补字段。`Request` 一侧的差异则体现在解析策略：`request_description_t` 的 `mandatory_attr_items` 与构造参数 `relaxed_attr_parsing_`（request_parser.h:220）表明解析器支持「只关心部分属性」的宽松模式，不同版本的业务 Orch 对同一张表的属性约束可能不同；`key_separator_`（216）由构造参数传入，使键的分隔符不是单一硬编码值。因此跨版本比对时，不能假设同一张表的键格式与属性集合恒定。

能力边界随版本保持稳定，但会影响字段可读性：orchagent 始终是控制面进程，消费 APPL_DB、写 ASIC_DB，`m_publisher` 写入的是 APPL_STATE_DB 响应而非硬件状态，`m_toSync` 里积攒的任务在 `config` 命令返回后仍可能未被处理；任何「写成功即下发」的推断都是错的（参数见 04-06 ｜ 原理见 06-01）。DB 编号不是硬编码常量，须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 核验，不得写死（字段见 05-03 ｜ 参数见 04-04）。`gBatchSize` 等批量参数的取值会随版本与配置变化，凡涉及数量、时延、吞吐的结论一律标注「需在目标机型实测」，不给绝对值（基准方法见 08-01）。

### 7. 常见误用与调试

第一类误用是把不透明句柄当普通结构展开。`Executor::m_selectable` 指向的 `swss::Selectable`、`Consumer::getConsumerTable()` 返回的 `swss::ConsumerTableBase`、`Orch::m_publisher` 的 `ResponsePublisher`、`m_retryCaches` 的 `RetryCache`，其类型本体多在 `sonic-swss-common`，本快照未包含实现。用 `sizeof()`、指针偏移或 `reinterpret_cast` 去读它们的成员，会在不同版本间静默错位。正确做法是只用已公开的访问器（`getName()`、`getOrch()`、`getConsumerTable()`、`getRetryCache()` 等），内部布局一律视为**不在本快照，需对照实际版本核验**。

第二类误用是混淆「字段」与「方法」及返回码。`orch.h` 中 protected 段的 `resolveFieldRefValue`、`setObjectReference`、`removeObject` 等是成员函数，不是对象字段；`task_process_status`、`ref_resolve_status` 是枚举返回码，不是成员。把它们当字段列入表格会造成字段表失真。同样，`gRingBuffer` 是静态成员而非实例字段，引用时要注明其全局静态属性。第 4 节给出的 `grep -n "class ..."` 组合是区分类型定义与成员的快速手段。

第三类误用是把 05 册当原理书或参数书读。想理解「Consumer 如何把任务投递到 RingBuffer、Orch 如何调度」应去 06 册（原理见 06-04），想查 SAI 与 orchagent 的配置参数、批量开关应去 04 册（参数见 04-06），想按目录找 orchagent 模块应去 07 册（模块见 07-03）；在 05 册里找调用链或参数全集只会得到交叉引用。反过来，在 06 / 07 / 08 册里看到完整字段表属于去重铁律被破坏，应改写成「字段见 05-05」。

第四类是跨版本与解析期假设。把其他版本的 `Executor`/`Orch` 字段偏移套到本快照，或假设 `Request` 的 getter 在未 `parse()` 时可用，都会出错：所有 getter 都以 `assert(is_parsed_)` 前置，未解析就取值会直接触发断言；用错误的属性类型调用 getter 会在 `.at()` 处抛 `std::out_of_range`。调试时若读到「看似合理但明显不对」的值，先确认二进制与所用头文件是否同一快照，再用 `grep` 复核字段定义行号（见第 4 节），最后回到 `orch.cpp`/`request_parser.cpp` 的读写点逐字段比对。所有涉及吞吐、pps、内存占用的结论一律标注「需在目标机型实测」，不给绝对值（基准方法见 08-01 ｜ 诊断树见 08-03）。

### 4. 典型示例

下面给出一段字段级核验用的 C++ 片段，作用是把 `CommandLineOptions`、`SaiObj` 中已核验的公开字段与 `FlexCounter` 的公开访问器打印出来，用于确认本地快照的成员确实存在、声明一致。这不是流程代码，不触发任何 ASIC_DB 消费、SAI 调用或轮询线程；`FlexCounter` 的轮询字段为私有，示例只用 `isEmpty()` / `isDiscarded()` 观察其对外状态，私有字段的核对请用第 4 节末尾的 `grep` 方法。

```cpp
#include "syncd/CommandLineOptions.h"
#include "syncd/SaiObj.h"
#include "syncd/FlexCounter.h"
#include <cstdio>

// 仅演示字段读取，不含任何调度或轮询逻辑
void dump_syncd_fields(syncd::CommandLineOptions& opt,
                       syncd::SaiObj& obj,
                       syncd::FlexCounter& fc)
{
    // CommandLineOptions 字段均为 public（CommandLineOptions.h:67-114）
    std::printf("start=%d bulk=%d sync=%d\n",
        (int)opt.m_startType, opt.m_enableSaiBulkSupport ? 1 : 0,
        opt.m_enableSyncMode ? 1 : 0);
    // SaiObj 这组字段位于 public TODO 段（SaiObj.h:134-147）
    std::printf("obj type=%s id=%s created=%d\n",
        obj.m_str_object_type.c_str(), obj.m_str_object_id.c_str(),
        obj.m_createdObject ? 1 : 0);
    // FlexCounter 轮询字段为 private，只能用公开方法观察
    std::printf("fc empty=%d discarded=%d\n",
        fc.isEmpty() ? 1 : 0, fc.isDiscarded() ? 1 : 0);
}
```

在一个把上述函数接入调试桩、并以最小构造参数创建对象的测试环境中，会得到类似下面的输出。示例输出，具体格式需对照实际版本核验。

```text
start=0 bulk=1 sync=0
obj type=SAI_OBJECT_TYPE_PORT id=oid:0x1000000000001 created=1
fc empty=0 discarded=0
```

逐行判读如下，合计超过 150 字。第一行 `start=0 bulk=1 sync=0` 来自 `CommandLineOptions` 的三个公开字段：`m_startType` 取 0 对应 `SAI_START_TYPE_COLD_BOOT`（CommandLineOptions.h:20 的枚举定义），若这里出现 1 则为热启动、2 为快速启动、3 为 fastfast、4 为 express，取值超出枚举说明解析期出了错，应回查 `startTypeStringToStartType()`；`m_enableSaiBulkSupport=1` 表示启用 SAI 批量能力，与 `SaiSwitch` / `FlexCounter` 的 bulk 路径相呼应；`m_enableSyncMode=0` 表示未启用同步模式，若与预期不符应核对 `SYSTEM_DEFAULTS` 与启动脚本（参数见 04-06）。第二行 `obj type=SAI_OBJECT_TYPE_PORT id=oid:0x1000000000001 created=1` 来自 `SaiObj` 的 `m_str_object_type`、`m_str_object_id` 与 `m_createdObject`（SaiObj.h:136、137、147）；`oid:0x1000...` 是虚拟对象标识 VID 的序列化形式，高 32 位编码对象类型，若 `created=1` 却查不到对应 RID，说明 VID 到 RID 的翻译未命中，应回查 `VirtualOidTranslator`（原理见 06-05）。第三行 `fc empty=0 discarded=0` 来自 `FlexCounter::isEmpty()` 与 `isDiscarded()`（FlexCounter.cpp:4122、4131），前者为 0 表示实例下仍挂有计数器上下文、`m_counterContext` 非空，后者为 0 表示实例未被标记丢弃；若 `empty=1` 但 `COUNTERS_DB` 仍有数据，通常是实例被移除后计数残留，需按 `m_flexCounters` 的生命周期核对（原理见 06-09）。以上判读只覆盖字段取值，判定 `m_pollInterval`、`m_statsMode` 等私有字段需按下述方法读源码，机制见 06-09，全部启动参数见 04-06。

### 6. 版本差异

最根本的差异是 syncd 主对象字段的持续膨胀。早期版本的 `Syncd` 只持有 vendor SAI、命令行选项、VID 翻译器与 Redis 客户端等基本成员，而本快照的 `Syncd.h` 已经演化出 `m_asicInitViewMode`（537）、`m_initViewRemovedVidSet`（550）、`m_createdInInitView`（647）等一组 init view 字段，以及 `m_enableSyncMode`（595）、`m_enableAsyncRec`（CommandLineOptions.h:86）等可切换通信模式的字段；`CommandLineOptions` 还新增了 `m_enableConsistencyCheck`（76）、`m_enableAsyncRec`（86）、`m_enableAttrVersionCheck`（114）与 `sai_start_type_t` 中的 `SAI_START_TYPE_EXPRESS_BOOT`（CommandLineOptions.h:36）等较新项。这组演进表明 syncd 已从「消费 ASIC_DB 直接调 SAI」往「可先建临时视图再 apply、可开一致性校验、可异步回写」方向扩展。与此同时，`Syncd.h:653-693` 出现了一整组链路事件抑制字段（`m_portLinkEventDampingStates`、`m_dampingTimerThread`、`m_pendingNotifications` 等），其注释明确写有「AIED damping algorithm」「max_suppress_time」等能力，但这类能力受平台与版本限制，不同 HWSKU 与版本能力不同，一律写「受平台与版本限制，需对照实际版本核验」，不得宣称全平台无条件支持。

第二类差异来自依赖边界与不透明类型。`Syncd` 与 `FlexCounter` 的签名里大量出现 `swss::ConsumerTable`、`swss::Table`、`swss::DBConnector`、`swss::FieldValueTuple`、`sairedis::SaiInterface`、`sai_object_meta_key_t` 等类型，其中 `swss::*` 多在 `sonic-swss-common`，该子仓不在本快照（SPEC 第 2.1 节第 2 条），`sai_*` 类型对应的 `sonic-sairedis/SAI/` 在本快照是空目录；因此本篇只能确认它们以成员、指针或引用形态出现在头文件中，其内部布局与版本兼容性都需对照实际版本核验，不得据印象补字段。表中 `m_isTcpConn` 由 `swss::SonicDBConfig::getDbSock()` 推算（FlexCounter.cpp:3907），也说明连接行为依赖运行时 `database_config.json`，而非源码常量（字段见 05-03 ｜ 参数见 04-04）。

第三类差异集中在 FlexCounter 的轮询与批量能力。`FlexCounter.h:108-114` 的 `BaseCounterContext` 公开开关中，`use_sai_stats_ext = false`、`double_confirm_supported_counters`、`no_double_check_bulk_capability`、`default_bulk_chunk_size` 等同名能力在不同版本上默认值不同，直接决定走单次 `get_stats` 还是 `bulk_get_stats` 路径；`m_secondaryPollFactor`、`BULK_CHUNK_SIZE_PER_PREFIX_FIELD` 与 `m_plugIn2CounterType`、`m_objectTypeField2CounterType` 两张映射表的存在，说明计数器种类与插件映射随版本持续扩展（FlexCounter.cpp:76-111）。因此跨版本比对时，不能假设同一计数器组的 `POLL_INTERVAL`、`STATS_MODE`、可用 counter id 列表恒定。能力边界则保持稳定：syncd 只在 `ASIC_DB` 与 SAI 之间搬运对象，`FlexCounter` 只把统计值写 `COUNTERS_DB` / `RATES_TABLE`，计数读取不编程 ASIC；`m_enable` 为 false 或 `m_pollInterval` 为 0 都意味着轮询未真正启动，任何「组已配置即计数可用」的推断都是错的（参数见 04-06 ｜ 原理见 06-09）。`g` 开头的全局对象与具体轮询周期取值随版本与配置变化，凡涉及数量、时延、pps 的结论一律标注「需在目标机型实测」，不给绝对值（基准方法见 08-01）。

### 7. 常见误用与调试

第一类误用是把不透明句柄当普通结构展开。`Syncd::m_vendorSai` 指向的 `sairedis::SaiInterface`、`m_client` 的 `BaseRedisClient`、`m_flexCounter` 的 `swss::ConsumerTable`、`SaiObj::m_meta_key` 的 `sai_object_meta_key_t`，其类型本体多在 `sonic-swss-common`、`meta/` 或本快照为空目录的 `SAI/`。用 `sizeof()`、指针偏移或 `reinterpret_cast` 去读它们的成员，会在不同版本间静默错位。正确做法是只用已公开的访问器（`SaiObj::getVid()`、`FlexCounter::isEmpty()` / `isDiscarded()`、`FlexCounterManager::getInstance()` 等），内部布局一律视为**不在本快照，需对照实际版本核验**。

第二类误用是混淆「字段」「方法」与「常量/键格式」。`lib/sairediscommon.h` 里的 `ASIC_STATE_TABLE`、`REDIS_KEY_VIDCOUNTER`、`REDIS_TABLE_NOTIFICATIONS` 是预处理宏，`REDIS_ASIC_STATE_COMMAND_CREATE` 等是命令字串，`ASIC_STATE:SAI_OBJECT_TYPE_SWITCH:oid:0xYYYY` 是键的拼接格式，它们都不是对象字段；`Syncd.h` 中 `processOid()`、`syncUpdateRedisQuadEvent()` 等是成员函数，不是成员。把它们当字段列入表格会造成字段表失真。第 4 节给出的 `grep -n` 组合是区分宏、类型定义与成员的快速手段。

第三类误用是把 05 册当原理书或参数书读。想理解「syncd 如何把 `ASIC_STATE` 翻译成 SAI 调用、FlexCounter 如何按 `m_pollInterval` 聚合周期」应去 06 册（原理见 06-05 ｜ 原理见 06-09），想查启动选项、counterpoll 间隔与 DB 编号应去 04 册（参数见 04-06 ｜ 参数见 04-04），想按目录找 syncd 模块应去 07 册（模块见 07-04）；在 05 册里找调用链或参数全集只会得到交叉引用。反过来，在 06 / 07 / 08 册里看到完整字段表属于去重铁律被破坏，应改写成「字段见 05-06」。

第四类是跨版本与解析期假设。把其他版本的 `Syncd` / `FlexCounter` 字段偏移套到本快照，或假设 `FLEX_COUNTER_STATUS_FIELD` 写入后计数立即可读，都会出错：`m_enable` 由 `setStatus()` 经 `statusMap` 查表写入，非法值只打警告不生效；`m_pollInterval` 为 0 时轮询线程不会按预期周期取数；VID 到 RID 翻译失败会把 SET 降级为 DEL（Syncd.cpp:4226）。调试时若读到「看似合理但明显不对」的值，先确认二进制与所用头文件是否同一快照，再用 `grep` 复核字段定义行号（见第 4 节），最后回到 `Syncd.cpp` / `FlexCounter.cpp` 的读写点逐字段比对。所有涉及吞吐、pps、内存占用与收敛时延的结论一律标注「需在目标机型实测」，不给绝对值（基准方法见 08-01 ｜ 诊断树见 08-03）。
