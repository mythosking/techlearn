## 1. 结构设计与评审结论

本套资料沿用 VPP / DPDK / OpenVPN / wireguard-windows / Hyperscan / Suricata 六套资料集已验证的组织逻辑：
**按维度分册 → 唯一权威源去重 → 三类骨架 → `文件号-篇号` 编号 → 工具书前置于原理 → 运维收尾**。
针对 SONiC 作为「多子仓组成、容器化控制面 + Redis 分层数据库 + SAI 抽象、数据面在 ASIC 的白盒交换机 NOS」的特点，做了五处调整。

| 决策 | 理由 | 落地方式 |
|---|---|---|
| 03 册定为「集成与部署」 | SONiC 是整机 NOS，靠镜像启动、`config_db.json` 落地与 CLI / telemetry 接入决定它能否跑起来 | 03 全册按 C 实战型写：vs 镜像启动 → CONFIG_DB 落地 → 端口/VLAN/IP/BGP 配置 → CLI 与 gNMI → 升级与 warm reboot → 多设备与多 ASIC |
| 04 册定为「参数与 API 手册」 | 本项目的「配置」体现为构建变量、CONFIG_DB 表与 schema、Redis DB 对象、show / config 命令、SAI / orchagent 参数 | 04 成为构建变量、DB 表、命令、容器与启动参数的唯一权威源 |
| 05 册前置于 06 | `FieldValueTuple` / `SonicDBConfig` / `Orch` / SAI 对象是理解 producer / consumer 流水线的前置知识 | 05 定位「工具书·随查」，不参与线性阅读主线 |
| 06 册增加到 14 篇 | 核心复杂度集中在异步配置流水线：CONFIG_DB → *mgrd → APPL_DB → orchagent → ASIC_DB → syncd → SAI | 06 用多段讲流水线各段、状态与恢复、多 ASIC、容器编排与管理面 |
| 07 册按 8 个子仓真实目录设 13 篇 | 模块边界与 `upstream_src/` 下子仓 / 目录一一对应，避免「按概念编模块」的虚设章节 | 每篇对应一个真实子仓或目录族，给文件清单与关键入口 |

评审中明确排除的做法：

| 级别 | 曾经的风险 | 本套的处理 |
|---|---|---|
| 结构 | 按功能平铺 65 篇、无权威源，导致 CONFIG_DB 表与命令在多个文件重复 | 04 / 05 / 06 / 07 / 08 各定唯一权威源，其余册交叉引用 |
| 骨架 | 手册型章节套论述型骨架，出现空泛「背景与动机」 | 分 A 论述 / B 手册字典 / C 实战三类骨架 |
| 边界 | 把 SONiC 写成软件路由器、宣称 `config` 命令返回即硬件已下发、写死 Redis DB 编号 | 01-01、06-01、06-02、08-03 明确控制面/数据面分离、异步流水线、编号须核验 |
| 仓库 | 把 SONiC 写成单一仓库、把 FRR / 内核 / 厂商 SAI 写成本快照内文件 | 01-04、02-01、07-05 明确多子仓结构与「不在本快照，需对照实际版本核验」 |
| 版本与性能 | 编造具体版本号 / DB 编号，或给绝对吞吐与时延数字 | 版本统一写「上游 master 快照（2026-11 抓取）」；08 全册标注「需在目标机型实测」 |

## 2. 唯一权威源与去重规则

本套资料按内容性质划归唯一权威源，各册的写法约束如下表所示。

| 内容 | 唯一权威源 | 其余册的写法 |
|---|---|---|
| 构建变量 / Makefile 参数、CONFIG_DB 表与 schema、Redis DB 与对象、show / config 命令、SAI / orchagent 参数、容器与 supervisord 启动参数、日志 / 返回码 | **04 全册** | 只给本场景最小必要调用，写「完整参数见 04-xx」 |
| 结构体逐字段（FieldValueTuple / SonicDBConfig / Table / ProducerStateTable / SAI 对象 / Orch / Request / Consumer / syncd / FlexCounter / 各 Orch 派生结构 / platform.json / PORT_STATE / WARM_RESTART） | **05 全册** | 只点名 + 真实源码路径 +「（字段见 05-xx）」 |
| 机制、状态机与调用链（配置流水线、producer / consumer、mgrd、orchagent 调度、syncd 到 SAI、warm reboot、多 ASIC、容器编排、gNMI / YANG 管理面） | **06 全册** | 讲「做什么」不讲「怎么实现」，写「原理见 06-xx」 |
| 模块能力与特性（按 8 个子仓划分的 13 个模块） | **07 全册** | 写「模块见 07-xx」 |
| 运维场景组合、基准方法、诊断树、案例库、加固、上线清单、输出判读 | **08 全册** | 其余册不展开运维步骤 |

强制约束：

1. 06 / 07 / 08 全册禁止出现完整结构体字段表，改为 `（字段见 05-xx）`。
2. 07 全册每篇代码段最多 3–5 个本模块最典型的调用 / 命令，其余写「完整 API 见 04-xx」。
3. 08 全册禁止重列参数清单，只讲「在什么场景组合哪些参数、如何判读输出」。
4. 04 全册禁止讲模块内部原理与结构体字段；05 全册禁止展开机制流程。
5. 交叉引用统一写法：`（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）`。

## 6. 三类骨架模板

**A 论述型（7 节）**
背景与动机 → 核心概念 → 关键数据结构与源码位置（**引用 05，不重列字段**）→ 关键流程与调用链 → 配置/命令/代码实例（**引用 04，不重列参数**）→ 注意事项、陷阱与最佳实践 → 小结与延伸阅读。

**B 手册字典型（7 节）**
本篇定位与覆盖范围 → 索引与全参数表 → 逐项详解 → 典型示例 → 速查表 → 版本差异 → 常见误用与调试。
05 字段表统一列：`字段 | 类型 | 含义 | 源码位置 | 读写时机 | 关联函数与流程 | 版本差异`。

**C 实战型（6 节）**
目标与拓扑 → 前置条件与环境 → 分步操作 → **验证方法与预期结果** → 常见失败与排错 → 小结。
每篇必须给「预期输出 + 判读要点」，不是只给命令。

## 8. 全量大纲（65 篇）

### 01 基础与概述（4 篇，A 型）

**01-01 SONiC 是什么：白盒云网络 NOS、能力矩阵与适用边界**
从 `sonic-buildimage-master/` 的多子仓结构与 `Makefile` 入口讲清白盒 NOS 定位；能力矩阵（容器化控制面、`CONFIG_DB`/`APPL_DB`/`ASIC_DB` 分层、SAI 抽象、ASIC 数据面）；明确「除 `platform/vs/` 外不做软件转发」「不是单一仓库」；何时不该用 SONiC。

**01-02 与厂商 NOS / Cumulus / FRR / DENT 的对比**
与厂商封闭 NOS、Cumulus、FRR（仅路由协议栈）、DENT 的分工对比；从 `src/sonic-config-engine/` 与 `orchagent/` 看「NOS + 容器编排」与「单一路由栈」的差别；`dockers/docker-fpm-frr/` 说明 FRR 以容器集成、其源码不在本快照；四类选型决策表。

**01-03 整体架构：容器化组件、Redis 数据库分层、SAI 与 syncd**
按 `dockers/`（database、orchagent、bgp、teamd 等容器）→ Redis 数据库分层 → `orchagent/`（`orch.cpp`、`orchdaemon.cpp`）→ `ASIC_DB` → `sonic-sairedis/syncd/` → SAI 串起架构；`dockers/docker-orchagent/supervisord.conf.j2` 的进程编排；`files/image_config/` 的开机配置；全链路分层图。

**01-04 版本基准、许可、社区与资料使用约定**
统一写「上游 master 快照（2026-11 抓取）」，不写绝对版本号；各子仓 `LICENSE`、`MAINTAINERS` 与社区治理，`azure-pipelines.yml` 的 CI；本套资料的编号、去重、交叉引用与「需对照实际版本核验」「不在本快照，需对照实际版本核验」写法。

### 03 集成与部署（6 篇，C 型）

**03-01 最小可用部署：虚拟交换机镜像启动与基本配置**
