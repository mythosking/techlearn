# SONiC 技术资料 · 04 参数与 API 手册（分片 B）

## 04-03 CONFIG_DB 表与 schema 参数全集（二）：BGP、ACL、ROUTE、COPP

### 1. 本篇定位与覆盖范围

本篇是 04 册参数与 API 手册的第 3 篇，承接 04-02 对 PORT、VLAN、INTERFACE 三类基础表的整理，继续把 CONFIG_DB 中与控制面协议、安全策略和限速保护相关的四组表收进同一份可随查的参数全集。与 02 册讲构建、03 册讲部署、06 册讲流水线原理不同，本篇只回答一个很窄的问题：一张 BGP、ACL、ROUTE 或 COPP 相关的表，在配置里到底以什么表名出现、键怎么拼、有哪些字段、每个字段可以取什么值、默认值是什么、配错了会在哪一环出问题。凡涉及这些表如何被订阅、如何被翻译成 ASIC 对象、如何在 syncd 侧经 SAI 编程的内容，一律不在本篇展开，分别写「原理见 06-07 ｜ 原理见 06-08 ｜ 模块见 07-03 ｜ 模块见 07-08」；凡涉及结构体逐字段的内容，写「字段见 05-02 ｜ 字段见 05-07」。这种克制正是 04 册作为参数唯一权威源的写作纪律：把清单列全列准，把机制留给机制册，把字段留给字段册，不在一处把所有内容重复铺开。

覆盖范围上，本篇按四组表展开。第一组是 BGP 相关表，核心是 BGP_NEIGHBOR 与 DEVICE_METADATA 中的自治域字段，它们由 `dockers/docker-fpm-frr/` 容器内的协议进程消费，FRR 协议源码不在本快照、需对照实际版本核验；本篇只记录配置侧的键与字段，不讲协议状态机。第二组是 ACL 相关表，即 ACL_TABLE 与 ACL_RULE，其字段可从 `sonic-mgmt-common-master/models/yang/sonic/sonic-acl.yang` 逐项核验，是本篇中证据最完整的一组，枚举值与取值范围都来自该模型。第三组是 ROUTE 相关表，需要特别说明 CONFIG_DB 侧的静态路由表与 APPL_DB、ASIC_DB 侧的路由表不是同一张表，不能混写，本篇以 `src/sonic-config-engine/minigraph.py` 中可核实的 STATIC_ROUTE 为配置侧代表。第四组是 COPP 相关表，即 COPP_GROUP 与 COPP_TRAP，其模板与默认值可在 `files/image_config/copp/copp_cfg.j2` 中核实，是一份带 Jinja 条件渲染的配置模板而非固定值。四组表的字段名、取值枚举与默认值凡能在本快照内核实的都给出路径，核实不了的写「需对照实际版本核验」，绝不凭印象补值。

还有一条边界要先立住：本篇列的是「参数」而不是「命令」。怎么把这些表写进 Redis、用哪个 CLI 去看、返回码如何解释，属于 04-05 与 04-08 的范围；这些表如何经各 `*mgrd` 进入 APPL_DB、再经 orchagent 生成 ASIC 对象、最后经 syncd 下发，属于 06-07 与 06-08 的范围。本篇第 4 节会出现 redis-cli 与 show 命令，但那只是为了演示「如何核对一张表确实写对了」，命令全集与输出判读体系不在本篇，读者应把命令当作验证手段而非本篇主体。按此边界展开，四组表可以归纳为「一张 BGP 邻居表加一个自治域字段、两张 ACL 表、一张静态路由表加两类运行态路由表、两张 COPP 表」，索引见下节。四组表从配置写入到芯片编程的处理链路见图 04-03-01。

### 2. 索引与全参数表

下表按「表/键 → 字段/取值 → 默认值 → 作用 → 误配后果」五列给出四组表的全参数索引。表中凡标注「样例为」的取值来自 `src/sonic-config-engine/config_samples.py`、`copp_cfg.j2` 或 `sonic-acl.yang` 的本次快照内容，只用于说明格式与量级，不得当作所有版本的固定默认；其余写「需对照实际版本核验」的项目本快照未给出确定值，须回到对应子仓源码确认。单元格中的斜杠用于并列枚举，不表示范围；半角竖线一律以转义形式书写。

| 表/键 | 字段/取值 | 默认值 | 作用 | 误配后果 |
|---|---|---|---|---|
| BGP_NEIGHBOR（键为对端地址） | asn：对端自治域号 | 需对照实际版本核验 | 决定 BGP 会话对端 AS | 与对端不一致则会话无法建立 |
| BGP_NEIGHBOR | holdtime：字符串秒数 | 样例为 180 | 会话保持计时 | 过短易翻滚，过长收敛变慢 |
| BGP_NEIGHBOR | keepalive：字符串秒数 | 样例为 60 | 保活报文间隔 | 与保持时间不匹配会反复断连 |
| BGP_NEIGHBOR | local_addr：本端地址 | 需对照实际版本核验 | 指定会话源地址 | 源地址不可达则会话停在 Idle |
| BGP_NEIGHBOR | name：对端名称 | 需对照实际版本核验 | 标识邻居便于识别 | 只影响可读性，不影响协议 |
| BGP_NEIGHBOR | nhopself：0 或 1 | 样例为 0 | 是否把自身设为下一跳 | 配错导致路由下一跳异常 |

| ACL_TABLE | ports：端口名列表 | 需对照实际版本核验 | 绑定规则的端口集合 | 漏绑端口则规则不生效 |
| ACL_RULE（键 aclname 加 rulename） | PRIORITY：1 至 65535 | 需对照实际版本核验 | 规则优先级 | 重复或越界被校验拒绝 |
| ACL_RULE | PACKET_ACTION：FORWARD/DROP/REDIRECT | 必填 | 命中后的动作 | 漏配则规则无法下发 |
| ACL_RULE | IP_TYPE：ANY/IP/IPV4 等 | 必填 | 匹配的 IP 类型 | 与地址字段不匹配则失效 |
| ACL_RULE | SRC_IP 与 DST_IP：IPv4 地址 | 需对照实际版本核验 | 源目的 IPv4 匹配 | 掩码写错会误匹配或漏匹配 |

| COPP_GROUP | mode：sr_tcm | sr_tcm | 令牌桶模式 | 模式不匹配则限速不准 |
| COPP_GROUP | cir：提交信息速率 | default 组为 600 | 限速阈值 | 过低会丢弃协议报文 |
| COPP_GROUP | cbs：提交突发尺寸 | default 组为 600 | 突发容忍量 | 过低导致突发报文被丢 |
| COPP_GROUP | red_action：drop | drop | 超限动作 | 配错可能放大攻击面 |
| COPP_GROUP | trap_action：trap 或 copy | 依组而定 | 上送方式 | 两者用错影响协议处理 |
| COPP_GROUP | trap_priority：优先级 | 依组而定 | 陷阱优先级 | 配错影响高优先级协议 |
| COPP_TRAP（键为 trap 名） | trap_ids：陷阱名列表 | 依 trap 而定 | 关联的硬件陷阱 | 名字不匹配则陷阱不生效 |
| COPP_TRAP | trap_group：组名 | 依 trap 而定 | 指向 COPP_GROUP | 指向不存在的组则失效 |
| COPP_TRAP | always_enabled：true | 依 trap 而定 | 是否始终开启 | 漏配则特定场景不生效 |

表中最需要留意的是三类「同名不同库」的对象。其一是 ROUTE：CONFIG_DB 里有 STATIC_ROUTE，APPL_DB 与 ASIC_DB 里另有路由表，后者由协议同步进程与编排核心写入，不能把运行态字段写进配置表，也不能指望静态路由字段直接出现在 ASIC 对象里，两者的链路见「原理见 06-07」。其二是 COPP_GROUP 与 COPP_TRAP：它们以配置文件模板形式由开机流程写入 CONFIG_DB，模板里的 Jinja 条件会根据端口数量与设备类型渲染出不同取值，因此「默认值」一词在 COPP 场景只能理解为「本次快照模板中该产品类下的渲染结果」。其三是 ACL_TABLE 的 type：同一张表根据类型不同可用的匹配字段子集不同，字段之间的约束关系由 YANG 模型表达，逐字段语义见「字段见 05-07」。

### 3. 逐项详解

**BGP 组。** BGP_NEIGHBOR 是 CONFIG_DB 中以对端 IP 地址为键的表，样例配置生成函数 `generate_t1_sample_config()` 在 `src/sonic-config-engine/config_samples.py` 中一次性给出一个邻居所需的七个字段：`asn` 是对端自治域号，`name` 是对端名字，`local_addr` 是建立会话使用的本端地址，`nhopself` 与 `rrclient` 是取 0 或 1 的开关，`holdtime` 与 `keepalive` 是以字符串保存的秒数，该函数里分别给了 180 与 60。同一文件还把本端自治域写在 `DEVICE_METADATA` 的 `localhost` 键下，字段名为 `bgp_asn`，样例值 65100。需要强调，这些数字是样例生成器为了构造 t1 拓扑写下的示意值，不是协议强制默认，真正生效值必须回到实际设备的配置与对应版本核验。还要注意 CONFIG_DB 的表键与字段都以字符串保存，所以 `holdtime` 写的是字符串形式的「180」而不是整数，这一点在手工编辑 JSON 时极易写错类型；协议进程如何读取这些字段并建立会话属于「原理见 06-07」，容器如何承载协议进程属于「模块见 07-08」，本篇只保证键与字段的清单完整。

**ACL 组。** ACL_TABLE 以 `aclname` 为键，`sonic-acl.yang` 给出了五个字段：`policy_desc` 是一到二百五十五字符的描述；`stage` 是枚举，只能取 INGRESS 或 EGRESS，决定规则在入方向还是出方向生效；`type` 也是枚举，可取 MIRROR、MIRRORV6、L3、L3V6，决定这张表按二层镜像还是三层路由语义去匹配；`ports` 是对 PORT 表端口名的 leaf-list，列出规则要绑定的端口。ACL_RULE 以 `aclname` 加 `rulename` 为复合键，字段明显更多：`PRIORITY` 是一到六万五千五百三十五的无符号短整型，决定同一表内规则的先后；`PACKET_ACTION` 与 `IP_TYPE` 都标为 mandatory，前者可取 FORWARD、DROP、REDIRECT，后者可取 ANY、IP、IPV4、IPV4ANY、NON_IPV4、IPV6ANY、NON_IPV6；`IP_PROTOCOL` 取值范围被限定在若干协议号，`ETHER_TYPE` 用模式匹配限定在若干以太类型字符串；地址与四层端口字段按 IPv4、IPv6 分成 `SRC_IP`、`DST_IP`、`SRC_IPV6`、`DST_IPV6`、`L4_SRC_PORT`、`L4_SRC_PORT_RANGE`、`L4_DST_PORT`、`L4_DST_PORT_RANGE` 等，并通过 when 条件与 `IP_TYPE` 联动；此外还有 `TCP_FLAGS` 与 `DSCP`。这套约束说明 ACL 不是「随便写几个字段就下发」，字段之间存在强相关，模型校验会在配置进入 DB 前拦住不合法组合，校验环节属于「原理见 06-03」，规则如何进 ASIC 属于「原理见 06-08」，派生结构逐字段见「字段见 05-07」。

**ROUTE 组。** 配置侧的静态路由以 `src/sonic-config-engine/minigraph.py` 渲染出的 STATIC_ROUTE 为代表：该函数把目的前缀作为键，每个前缀是一个字典，至少包含 `nexthop`、`ifname` 与 `advertise`，在启用 BFD 的分支里还会写入 `bfd` 为真。其中 `nexthop` 与 `ifname` 都是把多个值用逗号拼成的字符串，分别对应下一跳地址列表与出接口列表，前缀键、下一跳与出接口三者必须一起写对，缺一项就无法形成可用路由；`advertise` 控制是否把这条静态路由向动态协议重分发，配错会改变路由通告行为。必须把这张配置表与运行态路由表严格区分：`orchagent/routeorch.cpp` 中出现的是 APP_ROUTE_TABLE_NAME 与 STATE_ROUTE_TABLE_NAME 这类运行态对象，前者在 APPL_DB、后者在 STATE_DB，它们由协议同步进程或编排核心写入，字段与配置侧不同。把两者混为一谈是本篇最常见的事实错误，正确的链路是配置侧意图经校验后进入期望态、再经编排生成 ASIC 对象，见「原理见 06-07」，路由族编排结构的逐字段说明见「字段见 05-07」，编排核心模块见「模块见 07-03」。

**COPP 组。** `files/image_config/copp/copp_cfg.j2` 是一份 Jinja 模板，渲染后得到 COPP_GROUP 与 COPP_TRAP 两张表。COPP_GROUP 以组名为键，模板里可见 `default`、`queue4_group1`、`queue4_group2`、`queue4_group3`、`queue3_group1`、`queue1_group1`、`queue1_group2`、`queue1_group3`、`queue2_group1` 等组；每组共有字段包括 `queue`、`meter_type`、`mode`、`cir`、`cbs`、`red_action`，部分组还有 `trap_action`、`trap_priority`，queue2_group1 额外带 `genetlink_name` 与 `genetlink_mcgrp_name`。`default` 组的模板值是 `queue` 为 0、`meter_type` 为 packets、`mode` 为 sr_tcm、`cir` 与 `cbs` 均为 600、`red_action` 为 drop；其他组的速率值差异较大，且 queue4_group3 与 queue3_group1 会依据设备类型是否为管理型渲染出不同的 `cir` 与 `cbs`，queue3_group1 的 `cbs` 还跟端口数量经表达式计算相关。COPP_TRAP 以 trap 名为键，字段是 `trap_ids`、`trap_group` 与可选的 `always_enabled`，模板中 bgp 陷阱的 `trap_ids` 为 bgp 与 bgpv6、`trap_group` 指向 queue4_group1，`lacp`、`arp`、`udld`、`ip2me`、`neighbor_miss` 等则带 `always_enabled` 为真。这里要特别说明：`trap_action` 的 trap 与 copy 代表两种上送语义，`cir` 与 `cbs` 决定限速曲线，配得过低会丢协议报文、配得过高会放大控制面压力；这些字段如何经编排落到 ASIC 属于「原理见 06-08」，外围容器与模板的模块归属见「模块见 07-09」。

### 4. 典型示例

下面用一段配置片段配合redis-cli查询演示「写完怎么核对」。片段把四组表各取一例，字段名均取自本快照可核实的源码，取值中的地址与自治域为格式示意；表名与字段需对照实际版本核验。

```json
{
  "BGP_NEIGHBOR": {
    "10.0.0.2": {
      "asn": "65200",
      "holdtime": "180",
      "keepalive": "60",
      "local_addr": "10.0.0.1",
      "name": "ARISTA01T2",
      "nhopself": "0",
      "rrclient": "0"
    }
  },
  "DEVICE_METADATA": {
    "localhost": {
      "bgp_asn": "65100"
    }
  },
  "ACL_TABLE": {
    "DATAACL": {
      "policy_desc": "sample data acl",
      "stage": "INGRESS",
      "type": "L3",
      "ports": ["Ethernet1", "Ethernet2"]
    }
  },
  "ACL_RULE": {
    "DATAACL|RULE1": {
      "PRIORITY": "10",
      "PACKET_ACTION": "DROP",
      "IP_TYPE": "IPV4",
      "SRC_IP": "192.168.1.0/24"
    }
  },
  "STATIC_ROUTE": {
    "20.0.0.0/24": {
      "nexthop": "10.0.0.2",
      "ifname": "Ethernet1",
      "advertise": "false",
      "bfd": "true"
    }
  },
  "COPP_TRAP": {
    "bgp": {
      "trap_ids": "bgp,bgpv6",
      "trap_group": "queue4_group1"
    }
  }
}
```

### 5. 速查表

下表把四组表的「现象 → 优先核对 → 可能原因 → 交叉引用」压成一行一条的形式，便于在排障现场快速反查。表中不重复第 2 节的字段清单，只给核对入口；机制与案例仍按交叉引用跳转到相应册。

| 现象 | 优先核对的表或字段 | 可能原因 | 交叉引用 |
|---|---|---|---|
| BGP 会话停在 Idle | BGP_NEIGHBOR 的 local_addr 与 asn | 源地址不可达或对端 AS 不符 | 原理见 06-07 |
| BGP 反复翻滚 | holdtime 与 keepalive | 计时比例不当或链路不稳 | 原理见 06-07 |
| ACL 规则未命中 | ACL_TABLE 的 stage、type、ports | 方向、类型或绑定端口错 | 原理见 06-08 |
| ACL 配置被拒 | PRIORITY 或 IP_TYPE | 越界、漏必填或与地址字段不匹配 | 原理见 06-03 |
| 静态路由不生效 | STATIC_ROUTE 的 nexthop 与 ifname | 下一跳不可达或出接口不存在 | 原理见 06-07 |
| 运行态无路由 | APPL_DB 路由表是否有期望态 | 配置未进期望态或被同步进程丢弃 | 原理见 06-07 |
| 协议报文被丢 | COPP_GROUP 的 cir 与 cbs | 限速阈值过低 | 原理见 06-08 |
| 陷阱未受保护 | COPP_TRAP 的 trap_group | 指向不存在的组或 trap_ids 名不符 | 原理见 06-08 |

速查表的使用方式是「先定位现象、再核对配置、最后跳机制」。以「静态路由不生效」为例，第一步只在 CONFIG_DB 里确认 STATIC_ROUTE 的 nexthop 与 ifname 写对，第二步按「原理见 06-07」看期望态有没有生成，第三步才看 ASIC 对象；如果跳过第一步直接进入源码阅读，往往会在编排代码里兜圈子。再以「协议报文被丢」为例，COPP 的 cir 与 cbs 决定限速阈值，若确实配低了，表现为协议振荡而非配置报错，因此配置层的自检不会发现，必须结合运行态计数与案例库判断，见「排障见 08-04」。这类「配置正确但表现异常」的场景正是速查表存在的意义。

### 6. 版本差异

四组表的版本差异来源不同，不能一概而论。BGP_NEIGHBOR 与 DEVICE_METADATA 的字段在样例生成器中出现，但样例值随拓扑模板变化，不同版本的 `config_samples.py` 可能增删字段或调整默认计时，本篇给的 180、60、65100 只代表本次快照的 t1 样例；真实设备上的字段集合须对照 `src/sonic-config-engine/config_samples.py` 与实际版本核验。ACL 的字段与枚举由 `sonic-acl.yang` 约束，YANG 模型在不同版本会扩展枚举、增加匹配字段或收紧 pattern，本篇列出的 stage、type、PACKET_ACTION、IP_TYPE 枚举来自本快照模型，若目标版本的模型新增枚举值，应以该版本模型为准，字段级差异见「字段见 05-07」。STATIC_ROUTE 的字段来自 minigraph 渲染逻辑，是否写入 `bfd`、是否带 `advertise` 取决于拓扑定义与版本分支，本篇只说「本快照可见」，不宣称全版本一致。COPP 的差异最复杂，因为 `copp_cfg.j2` 是带 Jinja 条件的模板，端口数量、设备类型、是否管理型节点都会改变渲染结果，模板结构本身也可能随版本调整，因此 COPP 的「默认值」必须理解为「特定输入下的渲染值」，需对照 `files/image_config/copp/copp_cfg.j2` 与实际版本核验。

还有一个跨版本的通用差异：逻辑库的编号与分隔符由运行时 `database_config.json` 决定，本篇第 4 节示例中的库号 4 来自本快照模板，不同版本或不同实例形态（多 ASIC、DPU、chassis）会改变库与实例的映射，绝不能把库号写死；编号体系的全集与核验方法由本册另一篇专门整理，本篇只在使用 redis-cli 时说明来源，不展开编号表，需要时按运行时配置文件与实际版本核验。同理，表名前缀如 APP_ROUTE_TABLE_NAME、STATE_ROUTE_TABLE_NAME 来自 `orchagent/routeorch.cpp` 的常量引用，具体字符串值需对照实际版本核验，本篇只强调「配置侧与运行态不是一张表」这一事实。把版本差异按来源拆开处理，才能避免「一个版本看到的值套到另一个版本」这类连锁错误。

### 7. 常见误用与调试

第一类误用是「同名对象混库」。最典型的是把 APPL_DB 或 ASIC_DB 的路由表字段写进 CONFIG_DB 的 STATIC_ROUTE，或者在排障时用运行态字段去核对配置表，结果两边对不上就误判为下发失败。正确做法是先按对象所属库分开：配置侧只认 STATIC_ROUTE，期望态与 ASIC 侧的路由表按「原理见 06-07」的链路逐段看，路由族编排结构见「字段见 05-07」。第二类是把样例值当默认值，把 `config_samples.py` 里的 65100、180、60 或 `copp_cfg.j2` 里的 600 抄成规范，忽略它们随拓扑、设备类型与版本变化的性质；凡样例值本篇一律标注「样例为」，不能外推。第三类是 ACL 字段的强相关被忽略，例如 IP_TYPE 选了 IPV4 却填了 IPv6 地址字段，或 stage 选成 EGRESS 却期望匹配入方向流量，这类错误往往在模型校验阶段就被拦住，校验机制见「原理见 06-03」，若绕过校验直接写库则会在下发阶段失败。

第四类是 COPP 的 trap 与 copy 语义混淆，以及 cir 与 cbs 的粒度误用：把 copy 写成 trap 会改变协议报文的上送路径，把限速值配得过低会丢协议报文、配得过高会失去保护作用，且这些表现都不会在配置写库时报错，必须结合运行态判读，下发链路见「原理见 06-08」，案例见「排障见 08-04」。第五类是验证层的误判：用 redis-cli 看到表项就宣称「BGP 已建立、ACL 已生效、路由已通、COPP 已保护」，这是把「配置已写入」当成「硬件已下发」的典型错误；SONiC 的配置链路是异步流水线，命令返回成功只代表意图进了某个库，必须按「原理见 06-01」逐段核对，诊断顺序见「排障见 08-03」。调试时建议固定一个顺序：先在 CONFIG_DB 确认表项与字段，再按各表的机制篇看 APPL_DB 与 ASIC_DB 有没有对应对象，最后用 show 与 STATE_DB 看运行态；每一步都记录时间点，避免把异步延迟误读成配置丢失。按此顺序，本篇的全参数表与速查表可以作为入口索引，机制与案例则按上述交叉引用跳转，不在本篇重复展开。

## 04-04 Redis 数据库编号与 APPL_DB / STATE_DB / COUNTERS_DB 对象全集

### 1. 本篇定位与覆盖范围

本篇是 04 册的第 4 篇，专门整理 SONiC 控制面所使用的 Redis 逻辑库编号体系，以及 APPL_DB、STATE_DB、COUNTERS_DB 三类库中的常见对象。这是全册最容易被写错的一篇，因为库编号不是某个源码文件里的固定常量，而是运行时由 `/var/run/redis/sonic-db/database_config.json` 决定的值；凭印象写「CONFIG_DB 是某号库」是明确禁止的。本篇的处理方式是：先给出本快照 `dockers/docker-database/database_config.json.j2` 模板中确实可见的 id 值与分隔符，逐项标注来源，再强调运行时配置文件才是最终依据，凡超出本快照模板范围的一律写「需对照实际版本核验」。这样既提供可核对的清单，又不把某个快照的模板值冒充全版本通则。

覆盖范围分三层。第一层是编号与分隔符全集，涵盖 CONFIG_DB、APPL_DB、ASIC_DB、COUNTERS_DB、STATE_DB 等常用库，以及 LOGLEVEL_DB、PFC_WD_DB、FLEX_COUNTER_DB、SNMP_OVERLAY_DB、RESTAPI_DB、GB_* 系列、CHASSIS_* 系列、APPL_STATE_DB、DPU_* 系列、EVENT_DB、BMP_STATE_DB 等按场景扩展的库。第二层是实例映射，说明各库落在哪个 Redis 实例上、单实例与多实例模板的区别。第三层是对象全集，重点是 APPL_DB 的期望态对象、STATE_DB 的运行时状态对象与 COUNTERS_DB 的计数器及名称映射对象；对象名凡能在本快照源码中定位到常量或字符串的给出路径，定位不到的写「需对照实际版本核验」。机制层面，producer 与 consumer 如何读写这些库属于「原理见 06-02」，SonicDBConfig 的逐字段结构属于「字段见 05-03」，py-swsssdk 模块的定位属于「模块见 07-05」，本篇只列参数与对象，不重列字段与机制。

表中最值得注意的是两处「同号不同库」与两处「条件存在」。PFC_WD_DB 与 FLEX_COUNTER_DB 在单实例模板中同为 id=5，DPU 场景与 BMP 场景的若干库也按条件展开；同号之所以不冲突，是因为它们在同一 Redis 实例内承担不同键空间，或在多实例模板中被拆到不同实例。DPU_APPL_DB 至 DPU_COUNTERS_DB 只在 `DATABASE_TYPE` 为 dpudb 时渲染，EVENT_DB 只在相关构建开关打开时渲染，BMP_STATE_DB 则在非 dpudb 分支出现；因此「编号全集」是「本快照模板可出现的全集」，任何一台具体设备只会拥有其中一部分，须按实际生成的配置文件核验。对象层面的三类库见下节逐项详解，字段层面见「字段见 05-03」。

### 3. 逐项详解

**编号是怎么来的。** `sonic-py-swsssdk-master/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 类定义了两个路径常量：`SONIC_DB_GLOBAL_CONFIG_FILE` 指向 `/var/run/redis/sonic-db/database_global.json`，`SONIC_DB_CONFIG_FILE` 指向 `/var/run/redis/sonic-db/database_config.json`。`load_sonic_db_config()` 读取本地命名空间的配置并存入 `_sonic_db_config['']`，`load_sonic_global_db_config()` 遍历全局配置中的 `INCLUDES`，按 `namespace` 把各命名空间的配置文件逐一载入；若 `/var/run` 下的文件不存在，代码会退化到包内 `src/swsssdk/config/database_config.json` 作为兜底。`get_dbid(db_name, namespace)` 的实现是从 `_sonic_db_config[namespace]["DATABASES"][db_name]["id"]` 取值，`get_separator()` 同理取 `"separator"`，`get_socket()`、`get_hostname()`、`get_port()` 则经 `get_instance()` 取实例信息。`SonicV2Connector.connect()` 先按 `use_unix_socket_path` 决定走套接字还是主机端口，再调用 `get_dbid()` 拿到编号，最后交给 `dbintf.connect()`。这条链路直接说明编号是「运行时配置的值」，而不是写死在代码里的常量，是本篇反对硬编码编号的根本依据，逐字段结构见「字段见 05-03」。

**分隔符与实例。** 分隔符决定了复合键的拼法：CONFIG_DB、STATE_DB、SNMP_OVERLAY_DB、RESTAPI_DB、CHASSIS_* 等使用竖线，APPL_DB、ASIC_DB、COUNTERS_DB、PFC_WD_DB、FLEX_COUNTER_DB、GB_* 等使用冒号。实例决定数据在哪个 Redis 服务上：`database_config.json.j2` 中 `redis` 实例的主机名取 HOST_IP、端口取 REDIS_PORT、套接字为 `/var/run/redis{{DEV}}/redis.sock`；`redis_chassis` 固定为 `redis_chassis.server` 的 6380 端口、套接字在 `/var/run/redis-chassis/`；`redis_bmp` 用 BMP_DB_PORT，`remote_redis` 用 REMOTE_DB_IP 与 REMOTE_DB_PORT。`multi_database_config.json.j2` 进一步演示多实例拆分：`redis1` 到 `redis4` 分别是 6378、6377、6376、6375 端口，并把 APPL_DB 放到 redis1、ASIC_DB 放到 redis2、COUNTERS_DB 与 PFC_WD_DB 放到 redis3，而 CONFIG_DB 与 STATE_DB 仍在 redis。同一模板里 SYSMON_DB 取 id=10、BMC_DB 取 id=12，与前表的 GB_COUNTERS_DB、CHASSIS_APP_DB 编号相同却落在不同实例，正说明「编号只在实例内有意义」，跨实例比较编号没有意义。

**APPL_DB 对象。** APPL_DB 保存的是经配置管理进程校验后的期望状态，键分隔符为冒号。`sonic-swss-master/orchagent/` 中可见大量以 `APP_` 开头、以 `_TABLE_NAME` 结尾的常量被传给 `ProducerStateTable` 或 `Table`，例如 `APP_ROUTE_TABLE_NAME`、`APP_PORT_TABLE_NAME`、`APP_INTF_TABLE_NAME`、`APP_NEIGH_TABLE_NAME` 分别在路由、端口、接口、邻居相关的编排代码中被引用，另有 `APP_FABRIC_MONITOR_PORT_TABLE_NAME` 取值为 `FABRIC_PORT_TABLE`、`APP_FABRIC_MONITOR_DATA_TABLE_NAME` 取值为 `FABRIC_MONITOR_TABLE`。这些常量的字符串值多由不在本快照的 `sonic-swss-common` 定义，本篇只点名常量与可核实的字符串值，其余写「需对照实际版本核验」，不臆造键名。对象层面要记住一条：APPL_DB 里的是「期望态」，由编排核心消费后生成 ASIC 对象，不是最终下发的硬件状态，消费与重试机制见「原理见 06-04 ｜ 原理见 06-07」。

**STATE_DB 对象。** STATE_DB 保存运行时状态，键分隔符为竖线。`orchagent/` 中可见 `STATE_ROUTE_TABLE_NAME`、`STATE_PORT_TABLE_NAME`、`STATE_LAG_TABLE_NAME` 等常量被用于状态表读写，另有若干以字符串直接定义的状态表，如 `STATE_FDB_SYNC_TABLE_NAME` 取值为 `FDB_SYNC`、`STATE_PROCESS_HEALTH_TABLE_NAME` 取值为 `PROCESS_HEALTH`、`STATE_FABRIC_CAPACITY_TABLE_NAME` 取值为 `FABRIC_CAPACITY_TABLE`、`STATE_PORT_CAPACITY_TABLE_NAME` 取值为 `PORT_CAPACITY_TABLE`、`STATE_MAC_MOVE_GUARD_TABLE_NAME` 取值为 `MAC_MOVE_GUARD`、`STATE_MMG_CAPABILITY_TABLE_NAME` 取值为 `MMG_CAPABILITY_TABLE`。逐字段语义见「字段见 05-09」，状态表在 warm reboot 中的恢复流程见「原理见 06-10」。STATE_DB 与 CONFIG_DB 的分隔符相同但语义完全不同，前者是运行时结果、后者是用户意图，混写会污染配置。

**COUNTERS_DB 对象。** COUNTERS_DB 保存计数器及其名称映射，键分隔符为冒号。`sonic-utilities-master` 中可见一组以 `COUNTERS_` 开头的名字：`COUNTERS_PORT_NAME_MAP`、`COUNTERS_QUEUE_NAME_MAP`、`COUNTERS_QUEUE_INDEX_MAP`、`COUNTERS_QUEUE_PORT_MAP`、`COUNTERS_LAG_NAME_MAP`、`COUNTERS_RIF_NAME_MAP`、`COUNTERS_RIF_TYPE_MAP`、`COUNTERS_PG_NAME_MAP`、`COUNTERS_PG_INDEX_MAP`、`COUNTERS_QUEUE_TYPE_MAP`、`COUNTERS_FABRIC_PORT_NAME_MAP` 等，此外还有 NAT、路由、调试相关的映射名。名称映射表的作用是把 ASIC 侧的计数器编号翻译成端口名、队列名等可读键，采集与展示依赖这些映射；具体表结构、字段与轮询时机须对照实际版本核验，计数器的生成链路见「原理见 06-09」，采集模块见「模块见 07-09」。读计数只从库里取值，不编程 ASIC，这是计数类操作与配置类操作的根本区别。

### 4. 典型示例

下面用 redis-cli 按编号查三类库的对象，再用 Python 片段演示 `SonicDBConfig` 的编号解析。示例中的库号来自本快照模板，运行时以实际 `database_config.json` 为准，需对照实际版本核验。

```bash
redis-cli -n 0 KEYS "PORT_TABLE*"
redis-cli -n 6 KEYS "PORT_TABLE*"
redis-cli -n 2 HGETALL "COUNTERS_PORT_NAME_MAP"
```

```python
from swsssdk import SonicDBConfig
SonicDBConfig.load_sonic_db_config()
print(SonicDBConfig.get_dbid("CONFIG_DB"))
print(SonicDBConfig.get_dbid("STATE_DB"))
print(SonicDBConfig.get_separator("APPL_DB"))
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
1) "PORT_TABLE:Ethernet1"
1) "PORT_STATE|Ethernet1"
1) "oid:0x1000000000001"
2) "Ethernet1"
3) "oid:0x1000000000002"
4) "Ethernet2"
4
6
:
```

逐行判读如下。第一条 `redis-cli -n 0 KEYS "PORT_TABLE*"` 查的是 0 号库即 APPL_DB，返回 `PORT_TABLE:Ethernet1`，冒号分隔符合 APPL_DB 的模板定义，说明端口期望态已从配置管理进程写入；但这一条只证明「期望态存在」，不代表端口已被 ASIC 编程。第二条切到 6 号库即 STATE_DB，返回 `PORT_STATE|Ethernet1`，竖线分隔符合 STATE_DB 的模板定义，说明状态库里已有该端口的运行时状态；对比前两条可见，同一端口在期望态库与状态库里用不同分隔符、不同表名记录，这正是「两类库不能混用」的直观证据。第三条在 2 号库即 COUNTERS_DB 中查名称映射，返回成对的 oid 与端口名，说明计数器编号已被翻译成 Ethernet1、Ethernet2 等可读键，采集侧据此展示端口计数；若该映射为空，即使计数器本身在增长，上层也可能因找不到名字而不显示。Python 片段先显式加载配置，再分别打印 CONFIG_DB、STATE_DB 的编号与 APPL_DB 的分隔符，输出 4、6、冒号与本快照模板一致；关键点在于这些值是运行时从 `database_config.json` 读出的，换一台设备或换一个版本就可能不同，因此永远不要把它们写进代码。输出块已注明示例输出与版本核验要求，所有返回值不得当作真实设备数据引用。

### 5. 速查表

下表把「现象 → 优先核对 → 可能原因 → 交叉引用」压成单行，便于现场按库定位。这里只给核对入口与跳转方向，库的全集见第 2 节，对象名以第 3 节给出的源码路径为准。

| 现象 | 优先核对的库或对象 | 可能原因 | 交叉引用 |
|---|---|---|---|
| 读不到配置表项 | CONFIG_DB 的编号与实例 | 连错实例或编号不符 | 模块见 07-05 |
| 期望态没有对象 | APPL_DB 的 APP_* 表 | 配置未进期望态 | 原理见 06-03 |
| 状态库为空 | STATE_DB 的 STATE_* 表 | 运行态尚未回写 | 原理见 06-05 |
| 计数器全为空 | COUNTERS_DB 名称映射 | 映射未建或连错库 | 原理见 06-09 |
| 路由对象查不到 | APPL_DB 与 ASIC_DB 路由表 | 同步或编排未走通 | 原理见 06-07 |
| chassis 数据缺失 | CHASSIS_* 库实例 | 连到本机实例而非 chassis 实例 | 原理见 06-11 |
| 多 ASIC 串库 | GB_* 库与实例映射 | 命名空间或多实例配置错 | 原理见 06-11 |
| 编号与文档不符 | 运行时 database_config.json | 版本或实例形态不同 | 字段见 05-03 |

速查表的使用要点是「先确认连接、再确认编号、最后确认对象」。以「计数器全为空」为例，第一步先用 `get_dbid` 或运行时配置确认连的是 2 号库，第二步查 `COUNTERS_PORT_NAME_MAP` 有没有映射，第三步才怀疑计数未启用；若跳过第一步，可能在错误的库里反复查询而一无所获。再以「状态库为空」为例，STATE_DB 有表项本身就是异步流水线的结果，配置刚写完就查通常是空的，应按「原理见 06-01」等待并逐段核对，而不是立刻判定故障。

### 6. 版本差异

编号体系的版本差异主要来自模板而非代码。`database_config.json.j2` 是本快照的 Jinja 模板，其中 `DATABASE_TYPE`、`REMOTE_DB_IP`、`REMOTE_DB_PORT`、`BMP_DB_PORT`、`HOST_IP`、`REDIS_PORT` 等变量由构建与运行环境注入，不同版本、不同平台、不同实例形态会渲染出不同的库集合与实例映射；DPU 分支、EVENT_DB 开关、BMP 分支都直接改变可用库的数量。`multi_database_config.json.j2` 又演示了另一套映射，把 APPL_DB、ASIC_DB、COUNTERS_DB 拆到不同端口的实例上，与单实例模板的「全部落在 redis」不同。因此本篇第 2 节的表只能理解为「本快照模板可见的全集」，任何一台具体设备的真实编号都必须回到实际生成的 `database_config.json` 核验，不得跨版本套用。

`SonicDBConfig` 的行为也在演进：本快照的 `dbconnector.py` 支持本地配置与全局配置双层加载、命名空间校验、包内兜底配置，这些能力的细节与默认值须对照实际版本核验；`sonic-swss-common` 中 `ProducerStateTable`、`ConsumerStateTable` 与 `Table` 的实现不在本快照，它们如何按编号与分隔符拼键属于该仓库的内容，需对照实际版本核验，本篇只描述 py-swsssdk 侧可见的解析接口，字段结构见「字段见 05-03」。对象名同样存在版本波动：APPL_DB、STATE_DB 的若干表名以常量形式在编排代码中引用，其字符串值由不在本快照的公共库定义；COUNTERS_DB 的映射名在本快照的 sonic-utilities 中可见，但不同版本可能增删映射或改名。结论只有一条：编号、分隔符、实例与对象名都按「运行时配置加对应版本源码」核验，不写死、不外推。

### 7. 常见误用与调试

第一类误用是「硬编码编号」。把 0、1、2、4、6 等数字直接写进脚本或文档，忽略这些值来自运行时配置，换设备或换版本后必然出错。正确做法是用 `SonicDBConfig.get_dbid()` 或在运行时读 `database_config.json`，本篇第 4 节的 Python 片段就是这个意思；字段细节见「字段见 05-03」。第二类是把分隔符弄反：CONFIG_DB 与 STATE_DB 用竖线、APPL_DB 与 ASIC_DB 与 COUNTERS_DB 用冒号，拼错分隔符就查不到键，尤其在手工构造复合键时最容易出错，须用 `get_separator()` 取得实际值再拼。第三类是混淆配置库与状态库：两者分隔符相同，但一个存用户意图、一个存运行时结果，把状态写进配置库会污染配置、把配置当成状态读会得到错误结论，混写后的现象往往表现为「配置丢失」或「状态不更新」，诊断顺序见「排障见 08-03」。

第四类是忽略实例与命名空间：CHASSIS_* 库落在 redis_chassis、BMP_STATE_DB 落在 redis_bmp、多 ASIC 场景有独立命名空间，若一律连本机默认实例，就会得到空结果并误判为功能缺失；这类能力受平台与版本限制，须对照实际版本核验，相关机制见「原理见 06-11」。第五类是「库里有对象就以为硬件已下发」：在 APPL_DB 看到期望态、在 ASIC_DB 看到对象，只能说明流水线的中间段走通了，最终是否编程成功还要看 STATE_DB 与 show 输出，这是把同步直觉套到异步流水线的典型错误，见「原理见 06-01 ｜ 原理见 06-05」。调试时建议固定顺序：先用运行时配置确认编号、分隔符与实例，再按 CONFIG_DB、APPL_DB、ASIC_DB、STATE_DB、COUNTERS_DB 的顺序逐库查对象，每步记录时间戳以区分「尚未写入」与「确实丢失」。按此顺序，本篇的编号表与速查表可作为入口索引，机制、字段、模块与案例则按上述交叉引用跳转，不在本篇重复展开。
