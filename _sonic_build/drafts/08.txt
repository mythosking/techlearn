# SONiC 技术资料 · 08 运维、性能基准与排障

## 08-01 性能基准方法：配置下发时延、收敛与转发吞吐实测

### 1. 背景与动机

前面各册回答的是「系统如何工作」，本册要回答的是「系统工作得多快、又如何确认它真的在工作」。对白盒交换机网络操作系统而言，性能从来不是一个可以脱离机型孤立谈论的数字：同一套软件跑在不同 ASIC、不同端口密度、不同软件版本上，配置下发时延、路由收敛时间与转发吞吐可能相差极大，任何脱离目标机型的绝对值都是误导。因此本篇把全部篇幅用于讲清三件事——测什么、怎么测、怎么判读，而不给出任何可以被称为「官方成绩」的数字。本套资料的版本基准统一为「SONiC master 快照（2026-11 抓取）」，本篇所有示例数字一律标注「示意值，需本机实测替换」，凡未经本机实测的结论都不得当成某一机型的定值（原理见 06-01 ｜ 基准方法见本篇 ｜ 调优见 08-02）。

第一个动机来自异步流水线这一全册铁律。06-01 讲明配置链路是 CONFIG_DB → 各 mgrd → APPL_DB → orchagent → ASIC_DB → syncd → SAI → ASIC 的多段异步过程，`config` 命令返回成功只代表配置写入 CONFIG_DB，不代表硬件已经下发。这意味着「配置下发时延」根本不是一次简单的时间差，而必须按流水线拆成分段测量：配置写入耗时、mgrd 搬运耗时、orchagent 翻译耗时、syncd 编程耗时、状态回写耗时。若把整条链路当成一个黑盒只量一个总时间，就既无法定位瓶颈在哪一段，也会在数值异常时无从下手。本篇因此反复强调「按段设点、逐段计时」的方法，而不是给读者一个诱人却无意义的单一数字（原理见 06-02 ｜ 原理见 06-04 ｜ 原理见 06-05）。

第二个动机是三个基准维度各自有独立的测量范式，不能混用。配置下发时延关心的是「一次控制面操作从发起到状态可见」的墙钟时间，测量点在各数据库表与 `show` 输出；收敛时间关心的是「网络拓扑或路由发生变化后，控制面重新达到稳定状态」所需的时间，测量点在邻居、路由与 FIB 的稳定；转发吞吐关心的是「数据面在 ASIC 上转发报文的速率」，这是唯一必须用流量发生器、且绝大部分工作发生在芯片内部的维度。三者分属控制面与数据面，量纲、工具与判读方式都不同，把它们写进同一张「性能表」并排比较是常见的概念错误。本篇会逐一给出它们的测量边界（原理见 06-07 ｜ 原理见 06-09 ｜ 排障见 08-03）。

第三个动机是把「可观测性」当成基准的前提条件来讲。没有可核验的测量点，所谓基准只是主观感觉。SONiC 的可观测性分散在若干处：STATE_DB 反映运行时状态、COUNTERS_DB 承载统计计数、telemetry 提供流式采集、`show` 与 `sonic-db-cli` 提供只读查询、orchagent 自身还能导出任务执行统计。基准方法本质上就是「在正确的段落选取正确的测量点，并明确时间戳的起止定义」。本篇把这套方法论固化成可复用的流程与检查表，让读者换一台机型、换一个版本仍能照着做，而不是背下某个数字（参数见 04-04 ｜ 参数见 04-05 ｜ 模块见 07-12）。

### 2. 核心概念

「配置下发时延」在本篇定义为：从一次配置意图被写入 CONFIG_DB 的时刻起，到该意图对应的运行时状态在 STATE_DB 或 `show` 输出中可见为止的墙钟时间。它有极强的分层属性：命令返回只覆盖第一层，后续每一层都由独立进程推进，因此严谨的基准会记录多个中间时刻，形成一条时间序列，而不是一个终点值。需要特别区分「配置时延」与「命令执行时延」——前者包含异步流水线全部段落，后者只含 CLI 自身的解析与写库开销，二者相差可达数个数量级，混为一谈是高频误判（原理见 06-03 ｜ 参数见 04-05）。

「收敛时间」指网络发生一次变化（如链路 up/down、BGP 邻居重建、路由撤销与重选）后，控制面重新达到稳定一致状态所需的时间。它强调「稳定」而非「首次出现」：路由表项第一次出现不等于选路已经收敛，邻居第一次 Up 不等于 FIB 已经写稳。判读收敛要观察状态是否在一定观察窗内不再变化，而不是抓住第一个瞬间值。由于收敛受协议计时器、重试次数、批量下发策略共同影响，任何收敛结论都必须写明「在目标机型、目标版本、目标拓扑下实测」（原理见 06-07 ｜ 基准见本篇）。

「转发吞吐」指数据面在 ASIC 上转发报文的速率，常用单位包括每秒报文数与每秒比特数。必须明确一个边界：SONiC 是白盒交换机 NOS，除虚拟交换机 `vs`（`platform/vs/`）外不做软件转发，数据面转发发生在 ASIC，控制面进程不参与逐包处理。因此吞吐测量的主角是流量发生器与 ASIC 计数器，控制面 CPU 占用只能作为旁证，绝不能用某个容器进程的 CPU 曲线去「推算」转发吞吐。吞吐还受报文长度、流表规模、ACL/QoS 复杂度影响，报告时必须连同测试条件一起给出（原理见 06-01 ｜ 模块见 07-10）。

「测量点与时间戳」是贯穿三者的公共概念。一个好的测量点应当满足三个条件：可被只读方式访问、不会因访问本身显著改变被测系统、其变化与被测阶段有一一对应关系。STATE_DB 的状态表、COUNTERS_DB 的计数、 orchagent 的任务统计都是候选测量点；而直接读 ASIC 内部寄存器既不在本快照能力内，也远超普通运维边界。时间戳的起止定义必须写进基准报告：起点是「命令发起」还是「配置落库」、终点是「状态出现」还是「状态稳定」，不同定义得到的数字不可比较（字段见 05-03 ｜ 参数见 04-04）。

「基线与分布」是把单次测量变成可信结论的关键。单次测量会被调度抖动、日志刷盘、计数器轮询等噪声污染，正确做法是重复多次、记录分布（如中位数与分位数）、并先建立未调优的基线，任何优化结论都必须与基线对照才有意义。本篇所有涉及具体数值的展示都只是「示意值，需本机实测替换」，用于说明判读方法而非代表真实性能（调优见 08-02 ｜ 排障见 08-04）。下表把三个基准维度的测量对象、主要测量点与结论口径对应起来，便于回查。

| 基准维度 | 测量对象 | 主要测量点 | 结论口径 |
|---|---|---|---|
| 配置下发时延 | 配置写入到状态可见 | 写入时刻、STATE_DB 与 show 输出 | 分段墙钟时间，示意需实测 |
| 收敛时间 | 拓扑或路由变化到稳定 | 邻居、路由、ASIC_DB 与 show 输出 | 多次取分布，不给单值 |
| 转发吞吐 | ASIC 数据面转发速率 | COUNTERS_DB 与流量发生器收发 | 需流量发生器，示意需实测量 |

### 3. 关键数据结构与源码位置

本节只点名与基准相关的可观测结构并给出可定位的真实路径，不展开逐字段定义。表项与 `FieldValueTuple` 字段见 05-02，Redis 数据库与 `FieldValueTuple` 结构字段见 05-03，SAI 对象与 attribute 字段见 05-04，FlexCounter 字段见 05-06；命令参数见 04-05，数据库对象与编号见 04-04；机制原理见 06-01 与 06-04；测试体系模块见 07-12。即（字段见 05-03 ｜ 参数见 04-05 ｜ 原理见 06-04 ｜ 模块见 07-12）。这样处理是为了让本篇聚焦「在哪个点测、怎么判读」，而不把字段表与参数全集提前铺开。

先看控制面可观测性的源码落位。orchagent 的任务级统计实现在 `sonic-swss/sonic-swss-master/orchagent/orchdaemon.cpp` 与 `orchdaemon.h`，其中可核验到 `OrchDaemon::start()`、`m_select->select(&s, SELECT_TIMEOUT)` 的事件循环，以及形如 `median_run_ns`、`q1_run_ns`、`q3_run_ns`、`max_run_ns`、`median_sched_ns`、`sched_max_ns` 的统计输出字段，对应 `m_taskStatsQuery` 一类查询入口。这些字段让「某一类任务跑了多久、被调度延迟了多久」变得可测，是测量 orchagent 段耗时的直接抓手；函数签名的完整形式需对照实际版本核验（字段见 05-05 ｜ 原理见 06-04）。

再看数据库与计数相关的落位。配置与状态分布在 CONFIG_DB、APPL_DB、ASIC_DB、STATE_DB、COUNTERS_DB 等多个逻辑库，库编号来自运行时 `database_config.json`，须对照 `sonic-py-swsssdk/sonic-py-swsssdk-master/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 与实际版本核验，禁止写死。计数器采集侧在 `orchagent/flexcounterorch.cpp` 可核验到 `flexCounterGroupMap` 与 `FLEX_COUNTER_DELAY_SEC` 等分组与延迟常量，分组涵盖 PORT、QUEUE、RIF、ACL 等；其底层写入 COUNTERS_DB 的计数表字段见 05-06（字段见 05-06 ｜ 参数见 04-04 ｜ 原理见 06-09）。`sonic-swss-common` 中的 `ProducerStateTable`、`Select` 等原语不在本快照，需对照实际版本核验（模块见 07-05）。

数据面可观测性方面，端口与队列计数可在 COUNTERS_DB 查询，命令入口在 `sonic-utilities/sonic-utilities-master/show/` 与 `counterpoll/`，完整的 `show`、`config`、`counterpoll` 命令见 04-05，本篇不重列。虚拟交换机 `vs` 的测试与流量注入工具位于 `sonic-buildimage/sonic-buildimage-master/tests/` 与 `platform/vs/`，PTF 测试体系见 07-12；这些路径在本快照可核验，但具体脚本、参数与可用选项需对照实际版本核验。厂商 SAI 内部行为与硬件寄存器不在本快照，任何吞吐的「理论上限」都不据推测补值（模块见 07-10 ｜ 模块见 07-12）。下表按可观测层次归纳基准相关的源码落位。

图 08-01-01 用颜色区分语义：blue 为输入与数据库可观测点，gray 为辅助的测量点定义与采集动作，teal 为负载注入，purple 为 orchagent 控制面流水线，green 为运行时汇总，red 为结论与硬件边界。图中「配置流水线」一段对应 06-01 的异步链路，正因为它分多段，时间戳才必须按段采集；「STATE_DB 与 COUNTERS_DB」一段是判读的主要依据，因为控制面状态与计数最终都落在这里（原理见 06-01 ｜ 字段见 05-03）。

配置下发时延的测量链按图 08-01-01 的左侧推进：先在 CONFIG_DB 写入时刻打点，再依次观察 APPL_DB 期望状态是否出现、ASIC_DB 对象是否生成、STATE_DB 与 `show` 输出是否反映运行时结果。每一对相邻时刻之差就是该段的耗时，各段相加得到端到端时延。这里的关键纪律是「以段落为界，不以命令返回为界」：命令返回成功只落在第一段的起点附近，不能当终点使用。若 APPL_DB 有表项而 ASIC_DB 无对象，瓶颈在 orchagent 翻译段；若 ASIC_DB 有对象而状态未变，瓶颈在 syncd 编程或回写段，应回到 06-05 的调用链排查（原理见 06-04 ｜ 原理见 06-05 ｜ 排障见 08-03）。

收敛时间的测量链以「变化注入」为起点：制造一次链路 down 或路由撤销，随后以固定间隔轮询邻居状态、路由表项与 `show` 输出，记录首次出现时刻与稳定时刻。稳定判据必须事先定义，例如「连续若干次观察窗口内表项集合不再变化」，否则不同人读同一组数据会得出不同收敛时间。由于收敛受重试与定时器影响，应重复多次取分布，并在报告中写明拓扑与版本；任何跨机型的收敛时间对比都不成立（原理见 06-07 ｜ 基准见本篇）。

转发吞吐的测量链与前面两条有本质区别：它由流量发生器注入已知速率的报文流，从 ASIC 侧计数器与流量发生器的收发差值读数，控制面容器只作旁证。测量前应确认计数器已启用并设定合适的轮询间隔，否则读到的是滞后的计数，计算出的吞吐会失真；轮询间隔本身也是调优项，见 08-02。报告吞吐必须同时给出报文长度、流表规模、双向或单向、是否启用 ACL/QoS 等条件，缺一项都不足以复现（参数见 04-04 ｜ 调优见 08-02 ｜ 原理见 06-09）。

### 5. 配置/命令/代码实例

本节给三组实例：一组用命令闭环完成一次配置下发时延的分段取样并作逐行判读，一组给出自动化多次采样的脚本，一组给出读取任务统计以定位 orchagent 段耗时的方法。完整命令见 04-05，命令参数与库对象见 04-04，本册不重列。所有命令需在有相应权限的环境执行，库名、表名、键格式与选项需对照实际版本核验；输出中的数值均为示意值，需本机实测替换。

先看配置下发时延的取样闭环，按「前置检查 → 执行打点 → 验证状态 → 清理」组织。下列命令名、容器名与选项需对照实际版本核验。

```bash
# 前置检查：确认数据库与关键容器可达
docker ps --format '{{.Names}}' | grep -E 'swss|syncd|database'
docker exec -it database redis-cli PING
# 执行：在配置写入前后打时间戳（示意，参数见 04-05）
date +%s.%N
config vlan add 100
date +%s.%N
# 验证：观察状态库与 show 输出是否反映（键格式需对照实际版本核验）
sonic-db-cli STATE_DB KEYS 'VLAN_TABLE*'
show vlan brief
# 清理：删除本次测试配置
config vlan del 100
```

```text
示例输出，示意值，需本机实测替换（具体格式需对照实际版本核验）
swss
syncd
database
PONG
1763000000.123456789
1763000000.457012345
VLAN_TABLE|100
+-----------+-----------------+
| VLAN ID   | Ports           |
+-----------+-----------------+
| 100       |                 |
+-----------+-----------------+
```

逐行判读如下。第一段 `docker ps` 过滤出 `swss`、`syncd`、`database` 三个容器名，分别对应 orchagent 与 syncd 所在运行环境与 Redis 数据库，确认三者都在运行是任何分段测量的前提；缺 `syncd` 说明该机型尚未完成芯片适配或容器未起，此时测时延毫无意义。`docker exec -it database redis-cli PING` 返回 `PONG`，证明数据库通道可达，若连不上应先查容器状态而非怀疑芯片。两个 `date +%s.%N` 输出 `1763000000.123456789` 与 `1763000000.457012345` 是配置写入前后的纳秒级时间戳，其差值约零点三三秒只是示意值，需本机实测替换，它覆盖的是命令解析与写 CONFIG_DB 的开销，并不包含后续异步流水线，绝不能当成端到端下发时延。`sonic-db-cli STATE_DB KEYS` 返回 `VLAN_TABLE|100`，说明运行时状态库已出现该 VLAN 表项，这是判读「配置是否已反映到状态层」的依据；`show vlan brief` 的数据行 `VLAN ID` 为 `100`、`Ports` 为空，与刚建的空 VLAN 相符，属正常特征。最关键的一点：从第二个时间戳到 `VLAN_TABLE|100` 出现之间还有 mgrd 搬运、orchagent 翻译、syncd 编程与回写多段，必须分别打点才能定位瓶颈；若只止步于命令返回，就落入了「配置即时生效」的陷阱（原理见 06-01 ｜ 排障见 08-03 ｜ 参数见 04-05）。

第二组给出自动化多次采样的脚本，用于把单次抖动平均成可比较的分布。重复采样能显著降低调度噪声对结论的影响，是建立基线与对照调优效果的必要手段。

```bash
# 多次采样降低抖动（示意值，需本机实测替换；命令与选项需对照实际版本核验）
for i in $(seq 1 10); do
  t0=$(date +%s.%N)
  config vlan add $((200+i))
  t1=$(date +%s.%N)
  echo "sample=$i latency=$(awk "BEGIN{printf \"%.3f\", $t1-$t0}")"
  config vlan del $((200+i))
done
```

这段脚本对十个 VLAN 各做一次「建、计时、删」，把每次差值打印成样本。读脚本时要清楚它量的仍只是命令加写库开销，要得到分段时延必须把 `STATE_DB` 轮询也放进循环、记录状态出现时刻；循环内的删除操作是为避免测试污染后续采样，体现「清理」这一闭环步骤。样本应记录成序列后算中位数与分位数，而不是只看某一次的最小值（基准见本篇 ｜ 调优见 08-02）。

第三组给出读取 orchagent 任务统计的方法，用于把图 08-01-01 中「配置流水线」一段进一步细分。相关统计字段在 `orchagent/orchdaemon.cpp` 可核验。

```bash
# 读取 orchagent 任务执行统计（命令需对照实际版本核验）
show platform summary
sonic-db-cli APPL_DB HGETALL 'ORCHAGENT_TASK_STATS'
```

统计输出中的 `median_run_ns`、`max_run_ns`、`median_sched_ns`、`sched_max_ns` 分别刻画任务执行时长分布与调度延迟分布，字段含义见 05-05；若某类任务的 `max_sched_ns` 远大于中位数，说明该任务曾被长时间阻塞，是调度瓶颈的线索。此类统计本身也有读取开销，基准时应与未读取时对照确认影响可忽略（字段见 05-05 ｜ 原理见 06-04）。

### 6. 注意事项、陷阱与最佳实践

第一类是「把示意值当官方成绩」的陷阱，这也是本篇最需要警惕的一条。任何脱离机型、版本、拓扑与报文条件的数字都不构成性能结论；本篇所有示例输出均标注「示意值，需本机实测替换」，读者不得截取其中的时间戳或吞吐数字当作某机型的实测成绩对外引用。正确的报告格式永远是「数值 + 机型 + 版本 + 拓扑 + 测试条件 + 重复次数与分布」（基准见本篇）。

第二类是「命令返回即下发完成」的陷阱。`config` 返回成功只覆盖配置写入 CONFIG_DB，后续 mgrd、orchagent、syncd 各段仍在进行；据此断言硬件已生效，会同时误导时延与收敛的测量。判读必须按 CONFIG_DB、APPL_DB、ASIC_DB、STATE_DB 与 `show` 输出逐段推进，端口 `Oper up` 只是运行时状态，不能反推某次配置已使硬件下发（原理见 06-01 ｜ 排障见 08-04）。

第三类是「测量点选错」的陷阱。直接读 ASIC 内部寄存器既超出本快照能力，也不属运维边界；厂商 SAI 实现闭源且不在本快照，任何据其内部行为的推断都不可用。应选择 STATE_DB、COUNTERS_DB、`show` 与 orchagent 任务统计这类可只读访问、与被测量阶段一一对应的点；不确定的表名与字段一律写「需对照实际版本核验」并给出 `dbconnector.py`、`orchagent/` 等可定位目录（字段见 05-03 ｜ 模块见 07-04）。

第四类是「控制面与数据面混淆」的陷阱。转发吞吐发生在 ASIC，不能用容器 CPU 曲线推算；反过来，配置下发时延与收敛是控制面指标，也不能用 ASIC 计数器直接代表。除 `vs` 外 SONiC 不做软件转发，这一边界在基准设计与结论表述中都必须成立（原理见 06-01 ｜ 模块见 07-10）。

第五类是「DB 编号与表名写死」的陷阱。Redis 各库编号来自运行时 `database_config.json`，须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 与实际版本核验，禁止写死某库是某号；STATE_DB 与 COUNTERS_DB 的具体表名与字段同样需对照实际版本核验（参数见 04-04 ｜ 字段见 05-03）。

第六类是「单次测量当结论」的陷阱。调度抖动、日志刷盘、计数器轮询都会污染单次读数，必须重复采样、先建基线、再看分布；任何优化结论都要与基线对照才有意义（调优见 08-02）。

第七类是平台与版本限制陷阱。warm reboot、多 ASIC 与 chassis 相关能力受平台与版本限制，不同 HWSKU 行为不同，基准若涉及这些场景一律写「受平台与版本限制，需对照实际版本核验」，不得宣称全平台通用（原理见 06-10 ｜ 原理见 06-11）。

最佳实践可归纳为四条。其一，把每项基准写成可复现的实验卡：目标维度、测量点定义、时间戳起止、注入负载、重复次数、机型与版本、判读口径一应俱全。其二，读可观测源码时把路径写成 `upstream_src/` 下各子仓 `xxx-master/` 根的相对路径，并同时给出对应结构或函数，签名不确定就写「需对照实际版本核验」。其三，命令与输出按「前置检查、执行打点、验证输出、清理」闭环写，示例输出注明「示意值，需本机实测替换」并附逐行判读。其四，跨册引用统一用四段式（字段见 05-03 ｜ 参数见 04-05 ｜ 原理见 06-01 ｜ 模块见 07-12），本篇涉及的数据库表字段写「字段见 05-03」、 orchagent 任务统计写「字段见 05-05」、异步流水线写「原理见 06-01」，不在本篇展开字段表与参数全集。

## 08-02 性能调优：数据库批量、orchagent、计数器与容器资源

### 1. 背景与动机

08-01 建立了「怎么测、怎么判读」的方法论，本篇回答下一个问题：测出瓶颈之后，有哪些真实的调节杠杆、各能改什么、又要付出什么代价。调优不是把某个旋钮拧到最大，而是在「时延、收敛、吞吐、资源占用、稳定性」之间做有依据的取舍；任何调优动作都必须以 08-01 的基线为对照，用同一套测量方法复测，才能判断是否真的改善。本篇聚焦四类在本快照中可核验的杠杆——数据库批量、orchagent 调度、计数器轮询与容器资源，逐一给出它们的源码落位、可调项、收益机理与代价边界（基准见 08-01 ｜ 原理见 06-04 ｜ 模块见 07-03）。

第一个动机来自批量下发对收敛的决定性影响。06-04 讲明 orchagent 把 APPL_DB 的期望状态翻译成 ASIC_DB 对象，如果每条路由、每个邻居都单独发起一次 SAI 调用，大规模表项下发会被调用次数本身拖垮。`sonic-swss` 的 `orchagent/` 目录里可核验到专门的批量基础设施 `bulker.h`，其中定义了 `EntityBulker` 模板类、`max_bulk_size` 上限与 `flush()` 提交逻辑，并在 `orchdaemon.cpp` 中给出 `DEFAULT_MAX_BULK_SIZE` 默认值；`main.cpp` 还提供 `-k bulk_size` 命令行选项用于设置全局批量上限。这些都是本快照里的真实存在，不是推测。本篇因此把「数据库批量」列为第一类杠杆，讲清它如何减少调用次数、又为何不能无限放大（原理见 06-04 ｜ 参数见 04-06 ｜ 模块见 07-03）。

第二个动机是 orchagent 自身的调度节奏直接决定控制面响应速度。`orchdaemon.cpp` 可核验到 `SELECT_TIMEOUT` 与 `m_select->select(&s, SELECT_TIMEOUT)` 的事件循环，以及一组任务级统计字段。事件循环的超时设置、任务被调度的延迟、单类任务的执行时长分布，共同决定了「配置变化多久被处理」。这里要特别强调：orchagent 只写 ASIC_DB、不直接操作硬件，调优它只能改善控制面翻译与分派的速度，不能改变 ASIC 的转发能力（原理见 06-04 ｜ 原理见 06-05 ｜ 字段见 05-05）。

第三个动机是计数器轮询的「时效性对 CPU 开销」取舍。`orchagent/flexcounterorch.cpp` 可核验到 `flexCounterGroupMap` 与 `FLEX_COUNTER_DELAY_SEC`，`sonic-utilities/counterpoll/main.py` 提供 `enable`、`disable` 与 `interval` 子命令，轮询间隔有明确取值范围。间隔调小能让 COUNTERS_DB 的计数更新更及时，代价是采集与写库开销上升；间隔调大则相反。这类取舍只有在明确了「谁在消费这些计数」（telemetry、`show` 或告警）之后才有意义（原理见 06-09 ｜ 参数见 04-05 ｜ 模块见 07-06）。

第四个动机是容器资源约束常常才是隐性瓶颈。编排进程跑在容器里，`dockers/docker-orchagent/` 下可核验到 `supervisord.conf.j2`、`supervisord.conf.common.j2`、`critical_processes.j2`、`watchdog_processes.j2` 与 `orchagent.sh` 等编排文件，进程是否常驻、异常是否被拉起、资源如何分配都在这里定义。本篇把容器资源列为第四类杠杆，但明确其边界：容器与 supervisord 的启动参数全集见 04-07，本篇只讲「在调优场景下该关注哪些约束、改动为何受平台与版本限制」，不重列参数（参数见 04-07 ｜ 模块见 07-02 ｜ 原理见 06-13）。

### 2. 核心概念

「数据库批量」在本篇指把多条同类对象操作合并成一次提交以减少往返与调用次数的机制。它发生在两个层面：其一是 orchagent 与 ASIC_DB 之间，由 `EntityBulker` 累积待创建、待设置、待删除的条目，在达到 `max_bulk_size` 或任务末尾时经 `flush()` 统一提交；其二是更下游经 SAI 批量 API 进入 syncd，批量操作码在 06-05 已有对应描述。批量的收益来自摊薄每次调用的固定开销，代价是单批变大后单次提交时延与内存占用上升，且错误模式需要审慎对待——`bulker.h` 中可见 `SAI_BULK_OP_ERROR_MODE_IGNORE_ERROR` 一类模式，意味着批内部分失败可能被忽略，必须靠返回值与日志核对（原理见 06-04 ｜ 原理见 06-05 ｜ 字段见 05-05）。

「orchagent 调度节奏」指事件循环处理 APPL_DB 变更的节拍。`orchdaemon.cpp` 的 `SELECT_TIMEOUT` 定义了没有事件时空转的等待时长，`m_select->select()` 负责在超时内等待可读事件；超时过长会让突发配置的响应变慢，过短则可能增加空转开销。任务级统计把「执行耗时」与「调度延迟」分开刻画，使运维能区分「任务本身慢」与「任务被堵住没轮上」两类问题，这是调优 orchagent 的关键判据（原理见 06-04 ｜ 字段见 05-05）。

「计数器轮询」指 FlexCounter 周期性读取 SAI 统计值并写入 COUNTERS_DB 的过程。`flexCounterGroupMap` 把 PORT、QUEUE、RIF、ACL 等对象映射到各自的计数分组，`counterpoll` 命令则对各分组的 `POLL_INTERVAL` 与 `FLEX_COUNTER_STATUS`（enable 或 disable）进行操作。要理解一个前提：只有被启用且轮询间隔合理的分组，其计数才具备时效性；关闭不消费的分组能省下采集开销，这是常见的「反向调优」手段（参数见 04-05 ｜ 字段见 05-06 ｜ 原理见 06-09）。

「容器资源」指编排进程运行所处的容器与进程管理约束。`supervisord.conf.j2` 等模板定义服务的启动与依赖，`critical_processes.j2` 标记关键进程，`watchdog_processes.j2` 关联看门狗。调优场景下关注的是：被调优的进程是否常驻、异常退出后是否被拉起、改动是否会因模板重建而丢失。由于容器与 supervisord 参数随版本与镜像构建方式变化，本篇只给关注点，具体参数写「需对照实际版本核验」，全集见 04-07（参数见 04-07 ｜ 模块见 07-02 ｜ 原理见 06-13）。

「收益与代价的取舍」是贯穿四类的元概念。批量加大减少调用却抬高单次时延与内存，轮询加快提升时效却抬高 CPU，超时缩短提升响应却可能增加空转，容器资源放宽能缓解瓶颈却可能影响同机其他服务。没有「全局最优」的旋钮组合，只有针对目标机型、目标负载、经基线复测验证的组合。下表把四类杠杆的源码落位、可调项与主要代价对应起来，便于回查。

| 调优杠杆 | 真实源码落位 | 可调项 | 主要代价 |
|---|---|---|---|
| 数据库批量 | `orchagent/bulker.h` | `max_bulk_size` 与 `flush()` | 批量过大时延与内存上升 |
| orchagent 调度 | `orchagent/orchdaemon.cpp` | `SELECT_TIMEOUT` 与 select 循环 | 超时过短空转开销增加 |
| 计数器轮询 | `flexcounterorch.cpp`、`counterpoll/main.py` | `POLL_INTERVAL` 与状态开关 | 间隔过小 CPU 开销上升 |
| 容器资源 | `dockers/docker-orchagent/` | supervisord 与关键进程编排 | 改动受平台与版本限制 |

图 08-02-01 用颜色区分语义：blue 为调优目标，amber 为批量与对象提交，purple 为 orchagent 控制面，teal 为计数轮询配置，gray 为辅助的容器运行环境，green 为 syncd 与运行时下发回写，red 为结论与硬件边界。需注意「计数器轮询」并非直接加快 ASIC 转发，而是改善计数的时效性，使 08-01 的吞吐判读不被滞后计数误导；「容器资源」则是保障调优后的进程有稳定运行环境（原理见 06-09 ｜ 原理见 06-13）。

批量提交链按图 08-02-01 的「批量维度」推进：orchagent 在处理路由、邻居等表项时，不再逐条调用 SAI，而是经 `EntityBulker` 把同类操作累积起来，达到 `max_bulk_size` 或任务末尾时由 `flush()` 统一提交。这条链的关键判断是「批量多大合适」：过小则调用次数仍多、收益有限，过大则单次提交停顿变长、内存占用升高，且 `SAI_BULK_OP_ERROR_MODE_IGNORE_ERROR` 一类模式可能掩盖批内部分失败。因此批量上限的调整必须配合失败日志核对，而非只看收敛变快（原理见 06-04 ｜ 字段见 05-05）。

调度优化链沿「调度维度」推进：通过任务统计区分「执行慢」与「调度慢」。若某类任务的 `max_sched_ns` 远大于中位数，说明它被阻塞等待调度；此时调 `SELECT_TIMEOUT` 或梳理事件源可能有效。若 `median_run_ns` 本身就高，则应回到该任务的实现去看单条处理逻辑，单纯调节奏不会改善。两类症状对应完全不同的动作，误判会导致「调了半天没效果」（原理见 06-04 ｜ 字段见 05-05）。

计数与容器两条链相对间接。计数链通过 `counterpoll` 调整各分组的轮询间隔与开关，使 COUNTERS_DB 的计数 Fresh 度满足消费方需求；关闭无人消费的分组可反向节省开销。容器链则确认被调优进程常驻、异常可拉起，并在改动 supervisord 模板后通过复测确认改动持久（参数见 04-05 ｜ 参数见 04-07 ｜ 原理见 06-13）。

第二组给出批量累积的代码形态，用来印证 `EntityBulker` 的累积与提交机制；下列片段依据本快照中可核验的类名与方法整理，签名需对照实际版本核验。

```cpp
// 代码形态示意，依据 orchagent/bulker.h 中可核验的 EntityBulker 整理；签名需对照实际版本核验
EntityBulker<sai_route_api_t> bulker(route_api, max_bulk_size);
bulker.create_entry(route_entry, attrs);   // 累积待创建条目
bulker.flush();                             // 达阈值或任务末尾统一提交
```

这段虽经简化，但机制是真实的：`EntityBulker` 以对象 API 与 `max_bulk_size` 构造，`create_entry` 一类入口把条目累积在内部容器，真正提交由 `flush()` 完成，`flush()` 内部再调用 `flush_creating_entries()` 等函数并传入批量错误模式。读源码时应重点看两处：一是条目何时被判定为「达到阈值」而提前提交，二是 `flush()` 之后返回的逐条状态如何被映射回业务重试逻辑——后者正是 `SAI_BULK_OP_ERROR_MODE_IGNORE_ERROR` 一类模式下必须人工核对的地方（字段见 05-05 ｜ 原理见 06-04）。

第三组给出读取任务统计以验证调度调优的命令，用于确认「执行慢」还是「调度慢」。相关字段在 `orchagent/orchdaemon.cpp` 可核验。

### 6. 注意事项、陷阱与最佳实践

第一类是「批量越大越好」的陷阱。批量加大确实能摊薄调用开销，但单批过大会抬高提交停顿与内存占用，并可能因 `SAI_BULK_OP_ERROR_MODE_IGNORE_ERROR` 一类模式掩盖批内部分失败。必须以基线复测确认净收益，并核对失败日志，不能只看收敛变快就认定调优成功（原理见 06-04 ｜ 字段见 05-05）。

第二类是「调了没验证」的陷阱。配置落库不等于运行时已按新值工作：轮询间隔改了要看 COUNTERS_DB 的更新节奏，supervisord 模板改了要确认改动在重建后仍持久，批量上限改了要观察任务统计与收敛复测结果。任何调优都以 08-01 同一套测量方法复测为准，不做「改完即走」（基准见 08-01 ｜ 原理见 06-13）。

第三类是「改错对象」的陷阱。orchagent 只写 ASIC_DB、不直接操作硬件，调优它只改善控制面翻译与分派，不能提升 ASIC 转发吞吐；计数器轮询改善的是计数时效性而非转发能力。把控制面指标与数据面吞吐混为一谈，会让调优方向南辕北辙（原理见 06-05 ｜ 基准见 08-01）。

第四类是「事实纪律」陷阱。批量与调度相关的类、函数与宏在 `bulker.h`、`orchdaemon.cpp`、`main.cpp` 中可核验，但函数签名的完整形式、参数全集与常量取值需对照实际版本核验；`sonic-swss-common`、厂商 SAI 实现与 Linux 内核不在本快照，不得据其编造字段或行为。不确定的一律标注并给出 `orchagent/`、`counterpoll/`、`dockers/` 等可定位目录（参数见 04-06 ｜ 模块见 07-05）。

第五类是「DB 编号与表名写死」的陷阱。Redis 各库编号来自运行时 `database_config.json`，须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 与实际版本核验；`FLEX_COUNTER_TABLE`、`ORCHAGENT_TASK_STATS` 等具体表名与字段需对照实际版本核验，禁止写死（参数见 04-04 ｜ 字段见 05-03）。

第六类是「容器改动随意化」的陷阱。`dockers/docker-orchagent/` 下的 `supervisord.conf.j2`、`critical_processes.j2`、`watchdog_processes.j2` 等随版本与镜像构建方式变化，直接改运行容器可能在上电或镜像重建后丢失；此类改动须走构建或配置下发路径，并标注「受平台与版本限制，需对照实际版本核验」（参数见 04-07 ｜ 模块见 07-02 ｜ 原理见 06-13）。

第七类是「成本被忽略」的陷阱。轮询加快抬高 CPU、批量过大抬高内存、超时缩短抬高空转，这些代价可能把同机其他服务挤到资源不足；调优必须连同资源监控一起看，并以单行验证确认无副作用（模块见 07-02 ｜ 基准见 08-01）。

最佳实践归纳为四条。其一，每次只改一类杠杆、只对照一个目标维度，避免多变量同时变化导致归因困难。其二，读源码时把路径写成 `upstream_src/` 下各子仓 `xxx-master/` 根的相对路径，并同时给出对应类或宏（`EntityBulker`、`flush()`、`SELECT_TIMEOUT`、`flexCounterGroupMap` 等），签名不确定就写「需对照实际版本核验」。其三，命令与输出按「前置检查、执行调整、验证状态、恢复」闭环写，示例输出注明「示意值，需本机实测替换」并附逐行判读。其四，跨册引用统一用四段式（字段见 05-05 ｜ 参数见 04-06 ｜ 原理见 06-04 ｜ 模块见 07-03），本篇涉及的批量结构字段写「字段见 05-05」、计数轮询命令写「参数见 04-05」、容器编排写「原理见 06-13」，不在本篇展开字段表与参数全集。

## 08-03 常见故障分类与诊断决策树

### 1. 背景与动机

08-01 给出了配置下发时延、收敛与转发吞吐的实测方法，08-02 给出了数据库批量、orchagent、计数器与容器资源的调优手段，二者解决的都是「系统正常时如何量化与提速」。本篇解决的是另一类问题：当系统表现异常时，如何把一句模糊的「网口不通」「配置没生效」「重启后起不来」落到具体的一段流水线上。SONiC 是控制面在容器进程、数据面在 ASIC 的白盒交换机 NOS，配置从 CONFIG_DB 到芯片要经过 cfgmgr、APPL_DB、orchagent、ASIC_DB、syncd 与 SAI 多个独立进程与逻辑库，这是一条异步流水线，任何一段没有推进，用户看到的都是「配置返回成功但业务没起来」（原理见 06-01 ｜ 原理见 06-02）。正因为跨了多进程、多数据库，故障现象与根因之间往往隔着若干层，一线最容易犯的错误是「看到现象就怀疑硬件」或「config 返回成功就宣布已下发」，前者会把排查引向错误的方向，后者会把真正的问题掩盖到故障扩大（原理见 06-05 ｜ 原理见 06-13）。

诊断之所以需要一棵决策树，而不是一份「现象对答案」的对照表，是因为同一个现象对应多个可能停驻的分段。以「配置不生效」为例：CONFIG_DB 里没有配置，可能是命令写错了表或 CVL 校验拒绝；CONFIG_DB 有而 APPL_DB 无表项，可能是对应 mgrd 没订阅或配置字段不被识别（原理见 06-03）；APPL_DB 有而 ASIC_DB 无对象，可能是 orchagent 没消费或属性不支持（原理见 06-04）；ASIC_DB 有而芯片未生效，则可能是 syncd 未调用成功或厂商 SAI 能力不足（原理见 06-05）。这几种情况的处置完全不同，若不逐段收敛而直接跳到结论，就会反复做无用功。决策树把「先看哪一段、依据什么证据、如何判定通过还是退回上层」固化成可重复的顺序，让不同经验的值班人员得到一致的判断路径（模块见 07-03 ｜ 模块见 07-04）。

本篇的证据纪律与全册一致：版本基准统一写「上游 master 快照（2026-11 抓取）」，不写绝对版本号、不写死 Redis DB 编号；命令名、选项、容器名与表名凡不能在本快照核实的，一律标注「需对照实际版本核验」并给出可定位目录；示例输出一律注明「示例输出，具体格式需对照实际版本核验」，凡涉及报错文案一律标注「文案需对照实际版本核验」，不据印象编造错误字符串；性能、容量、收敛与吞吐类结论一律标注「需在目标机型实测」，不给绝对值。本篇只讲「在什么现象下看什么证据、按什么顺序判定」，参数的完整语义见 04-08，字段的完整定义见 05 册，机制细节见 06 全册，模块能力见 07 全册。

### 2. 核心概念

「故障分类」是按停驻分段对异常现象做的归组，而不是按业务名做的罗列。本套资料把常见故障归为八类：配置不生效、容器未起、DB 无表项、端口 down、路由不通、计数不涨、warm reboot 失败、吞吐低。前四类多落在配置层、编排层与对象层，后四类则分别落在同步层、状态层、恢复层与硬件边界。分类的目的不是贴标签，而是把「现象」映射到一个可检查的分段集合，从而决定优先查哪个进程的日志与哪张库表。例如「端口 down」优先看物理链路与 STATE_DB 的端口状态回写，而不是先看 VLAN 配置；「路由不通」优先看 APPL_DB 的 ROUTE 表与 bgpd 邻居状态，而不是先看 ASIC 的转发表（原理见 06-06 ｜ 原理见 06-07）。

「证据来源」指可用于判定的四类可观测面，按侵入性从低到高排列：show 与 CLI 输出、容器与进程状态、各逻辑库的键表查询、进程日志。show 输出读的是数据库与状态，便于快速判断「配置层是否完成、运行时状态如何」，但不能证明芯片已下发；容器状态决定「这段流水线是否存在」，容器没起时谈表项没有意义；数据库查询能逐段定位「数据停在哪一层」，是异步流水线最有力的证据；日志用于确认进程内部发生了什么，但日志文案随版本变化，引用时必须标注核验要求。四类证据要组合使用，单看一类容易误判——例如仅凭 `show` 看到 VLAN 就断言已生效，是把状态当成了结果（参数见 04-05 ｜ 参数见 04-08）。

「分层判定」是把异步流水线按 CONFIG_DB、cfgmgr、APPL_DB、orchagent、ASIC_DB、syncd/SAI、ASIC 逐段切开，对每一段问「输入有没有、输出有没有」，从而定位停驻点的方法。它对应一个朴素但有效的判据：上游有而下游无，问题就在这一段及其衔接处；全链路都有而业务仍异常，问题在能力或硬件边界。判定顺序必须自上而下，先排除上游再深入下游，这样每前进一步都建立在「上游已确认正常」的前提上，避免在错误前提上越查越深。

「证据链」指把一次排查中采集到的各层证据按时间顺序串成可复核的记录，包含采集命令、采集时刻、关键字段取值与判定结论。证据链的价值在于可复现与可交接：值班交接时不必重复操作，复盘时可以对照当时的库表状态，升级或回滚后可以比较同口径证据。这与「越调越慢」式的凭感觉操作形成对照——没有证据链，就无法区分「改动有效」与「恰好恢复」（基准方法见 08-01 ｜ 调优见 08-02）。

下表把八类故障、典型现象、优先证据面与首查分段对应起来，作为诊断的入口索引；表中命令名与表名需对照实际版本核验。

| 故障分类 | 典型现象 | 优先证据面 | 首查分段 |
|---|---|---|---|
| 配置不生效 | config 返回成功但业务未变 | CONFIG_DB 与 APPL_DB 查询 | 配置层与搬运层 |
| 容器未起 | show 报错或进程缺失 | 容器状态与 supervisord 日志 | 进程编排层 |
| DB 无表项 | 上层有配置下层为空 | 逐库 KEYS 查询 | 相邻两层衔接处 |
| 端口 down | Oper 为 down | STATE_DB 与链路状态 | 物理链路与回写 |
| 路由不通 | BGP 邻居建立失败 | 邻居状态与 APPL_DB ROUTE | 协议与同步层 |
| 计数不涨 | 计数器长期为零 | COUNTERS_DB 与轮询开关 | 计数采集层 |
| warm reboot 失败 | 重启后未恢复 | 状态表与重启检查日志 | 状态恢复层 |
| 吞吐低 | 转发性能不达标 | 实测数据与丢弃计数 | 硬件边界与配置 |

### 4. 关键流程与调用链

把八类故障映射到异步流水线，并按「自上而下、缺则停、通过再进」的规则组织，就得到分层诊断决策树见图 08-03-01。图中实线表示逐层深入的正常判定路径，虚线表示「本层缺失即退回上游定位」的分支，二者合起来构成完整的分支判定逻辑。

:::figure id=08-03-01 | name=异步流水线分层诊断决策树 | dir=TD
node a "故障现象<br/>收集 show 输出" blue
node b "容器与服务<br/>docker ps" gray
node c "CONFIG_DB<br/>配置是否存在" blue
node d "APPL_DB<br/>期望状态是否存在" blue
node e "ASIC_DB<br/>对象是否存在" amber
node f "STATE_DB<br/>状态是否回写" amber
node g "syncd 与 SAI<br/>调用是否成功" green
node h "ASIC 与链路<br/>硬件边界" red
node i "结论：定位到<br/>故障分段" purple
edge a -> b "先看进程层"
edge b -> c "进程齐全"
edge c -> d "配置存在"
edge d -> e "期望存在"
edge e -> f "对象存在"
edge f -> g "状态异常"
edge g -> h "调用失败"
edge h -> i "逐段收敛"
edge d -> c dashed "无表项退配置层"
edge e -> d dashed "无对象退编排层"
edge g -> e dashed "调用失败退对象层"
:::

图 08-03-01 的颜色与全册语义一致：blue 为输入与数据库，gray 为辅助的进程编排观测，amber 为 ASIC_DB 与状态回写目标，green 为 syncd 与 SAI 运行时，red 为硬件边界，purple 为最终结论。读图的关键是先走实线：先确认容器与服务齐全，再依次确认 CONFIG_DB 有配置、APPL_DB 有期望状态、ASIC_DB 有对象、STATE_DB 有回写、syncd/SAI 调用成功，最后才落到 ASIC 与物理链路；每通过一层，就把「上游已正常」作为既定前提。任一层不通过时走虚线退回上游分段定位，而不是越过它继续往下——例如 APPL_DB 无表项时，正确动作是退回配置层检查 mgrd 是否运行、字段是否被识别，而不是去查 ASIC_DB（原理见 06-03 ｜ 原理见 06-04）。

分支判定要落在可执行的判据上，而不能停留在「看情况」。下表给出每层「通过」与「不通过」的判定条件及不通过时的首查动作；表中命令名、表名与日志文案需对照实际版本核验。

| 层级 | 通过判据 | 不通过判据 | 不通过时首查动作 |
|---|---|---|---|
| 进程层 | 相关容器均在运行 | 容器缺失或反复重启 | 查容器编排与启动日志 |
| 配置层 | CONFIG_DB 有目标配置 | 配置缺失或字段异常 | 查命令、校验与 mgrd 状态 |
| 搬运层 | APPL_DB 有期望状态 | 上层有而此层无 | 查对应 mgrd 与字段识别 |
| 编排层 | ASIC_DB 有对应对象 | 期望有而对象无 | 查 Orch 日志与属性支持 |
| 编程层 | 状态回写且调用成功 | 对象有而状态异常 | 查 syncd 与 SAI 能力 |
| 硬件层 | 链路与表项正常 | 以上均正常仍异常 | 查物理链路与机型限制 |

需要强调两个判定边界。其一，「通过」只说明这一层的数据已就绪，不等于下一层已完成：CONFIG_DB 有配置不代表 APPL_DB 已搬运，ASIC_DB 有对象不代表芯片已编程，端口 Oper up 属运行时状态，不能反推某次 config 已使硬件下发（原理见 06-01 ｜ 原理见 06-05）。其二，硬件层是最后的边界而不是第一嫌疑：只有在配置、搬运、编排、编程各层都确认通过之后，才把问题归到链路、光模块或厂商 SAI 能力，且涉及厂商实现时必须写「不在本快照，需对照实际版本核验」（模块见 07-04 ｜ 模块见 07-10）。吞吐低一类故障还要额外叠加 08-01 的实测方法，所有数字标注「需在目标机型实测」，不据单次观测下结论（基准方法见 08-01 ｜ 调优见 08-02）。

### 5. 配置/命令/代码实例

本节给一组完整的「逐段收敛」实例：以「创建了 VLAN 但成员端口不通」为场景，按决策树从进程层走到对象层，命令统一按「前置检查 → 执行 → 验证输出 → 清理」的闭环写。以下命令中容器名、可执行文件名、命令选项与键格式需对照实际版本核验，示例中的报错文案一律标注「文案需对照实际版本核验」，不据印象编造错误字符串。

```bash
# 前置检查：确认数据库容器与编排容器在运行（容器名需对照实际版本核验）
docker ps --format '{{.Names}}\t{{.Status}}'
# 逐段验证：先看配置层，再看搬运层与对象层（键格式需对照实际版本核验）
sonic-db-cli CONFIG_DB KEYS 'VLAN*'
sonic-db-cli APPL_DB KEYS 'VLAN_TABLE:*'
sonic-db-cli ASIC_DB KEYS 'ASIC_STATE:SAI_OBJECT_TYPE_VLAN:*'
# 首屏佐证：查看 VLAN 摘要与端口状态（命令选项需对照实际版本核验）
show vlan brief
show interfaces status Ethernet1
```

```text
示例输出，具体格式需对照实际版本核验（下列取值仅为格式示意，不代表任何具体版本或机型；报错文案需对照实际版本核验）
database                   Up 3 days
swss                       Up 3 days
VLAN|100
VLAN_MEMBER|100|Ethernet1
VLAN_TABLE:100
ASIC_STATE:SAI_OBJECT_TYPE_VLAN:oid:0x260000000001
+-----------+-----------------+------------------+
| VLAN ID   | Ports           | Ports(tagged)    |
+-----------+-----------------+------------------+
| 100       | Ethernet1       |                  |
+-----------+-----------------+------------------+
```

逐行判读如下。第一段 `docker ps` 列出 `database` 与 `swss` 两个容器且状态为 `Up`，说明决策树的进程层通过：数据库与编排服务都在运行，可以继续往下查；若这里某容器缺失或反复重启，应停在进程层查容器编排与启动日志，而不是继续查库表，容器名与输出格式需对照实际版本核验。第二段 `sonic-db-cli CONFIG_DB KEYS 'VLAN*'` 返回 `VLAN|100` 与 `VLAN_MEMBER|100|Ethernet1`，说明配置层已写入 VLAN 与成员配置，配置格式与键分隔符需对照实际版本核验；这一段通过才能排除「命令写错」一类问题。第三段查询 APPL_DB 返回 `VLAN_TABLE:100`，说明搬运层已把配置写入期望状态；若 CONFIG_DB 有而 APPL_DB 无，问题就落在 mgrd 搬运或字段识别上，应退回配置层与搬运层之间定位，这是决策树中第一条虚线分支的实际用法。第四段查询 ASIC_DB 返回一条 `SAI_OBJECT_TYPE_VLAN` 对象，说明编排层已生成芯片对象并写入 ASIC_DB；若 APPL_DB 有而此层无，问题在 orchagent 翻译或属性支持，对应第二条虚线分支。第五段 `show vlan brief` 列出 VLAN 100 与 untagged 成员 Ethernet1，`show interfaces status Ethernet1` 用于确认端口状态；这里必须守住一条判据：show 能列出 VLAN 只说明配置与状态可查询，不等于芯片的 VLAN 表已写入该成员，还需按图 08-03-01 继续确认 STATE_DB 回写与 syncd 调用成功（原理见 06-06 ｜ 排障见 08-04）。最后，若判断涉及计数不涨，可用 `counterpoll` 查看轮询开关，选项名需对照实际版本核验（参数见 04-05）。

第二组给出一段用于批量逐段探查的脚本骨架，把决策树的多层查询串成一次采集，便于留存证据链；脚本中的库名与键格式需对照实际版本核验。

```bash
# 证据链采集脚本骨架：把各层查询结果写入带时间戳的文件，便于交接与复盘
stamp=$(date +%Y%m%d-%H%M%S)
{
  echo "== containers =="; docker ps --format '{{.Names}}\t{{.Status}}'
  echo "== CONFIG_DB VLAN =="; sonic-db-cli CONFIG_DB KEYS 'VLAN*'
  echo "== APPL_DB VLAN =="; sonic-db-cli APPL_DB KEYS 'VLAN_TABLE:*'
  echo "== ASIC_DB VLAN =="; sonic-db-cli ASIC_DB KEYS 'ASIC_STATE:SAI_OBJECT_TYPE_VLAN:*'
  echo "== STATE_DB =="; sonic-db-cli STATE_DB KEYS 'VLAN*'
} > "diag-${stamp}.txt"
```

这段脚本的价值不在语法，而在把「同一时刻的跨层快照」固定下来：四个 echo 分段对应决策树的不同层，输出重定向到带时间戳的文件，形成可交接的证据链。排查时若逐条手工输入，各层查询之间可能隔了数分钟，期间状态变化会让结论失真；一次性采集能避免这种时间错位。需要提醒的是，`STATE_DB` 的键格式与 VLAN 相关表名需对照实际版本核验，脚本只作骨架；真正下结论仍要按第 4 节的判据逐层比对，不能因为「四个段都有输出」就直接宣称芯片已生效（原理见 06-02 ｜ 字段见 05-03）。

### 6. 注意事项、陷阱与最佳实践

第一类是「返回成功即已下发」陷阱。这是异步流水线最顽固的误判：`config` 命令返回成功只代表配置写入 CONFIG_DB，后面还有 mgrd 搬运、orchagent 翻译、syncd 编程三段；`show` 能看到配置也只是状态可查询，不等于芯片已生效。判定必须按决策树逐段推进，端口 Oper up 属运行时状态，不能反推某次配置已使硬件下发（原理见 06-01 ｜ 原理见 06-05 ｜ 排障见 08-04）。第二类是「跳段怀疑硬件」陷阱：在配置层、搬运层、编排层都没确认的情况下直接归因于光模块、链路或芯片，会把排查引入死胡同；硬件边界应作为最后一层，只有在其余各层都通过后才考虑，且厂商 SAI 实现不在本快照，相关判断须写「不在本快照，需对照实际版本核验」（模块见 07-04 ｜ 模块见 07-10）。

第三类是证据失真陷阱。日志文案、容器名、命令选项与键格式都随版本变化，照搬其它版本的错误字符串或表名会造成误判，因此凡引用一律标注「文案需对照实际版本核验」或「需对照实际版本核验」，并给出 `show/`、`config/`、`cfgmgr/`、`orchagent/` 等可定位目录（参数见 04-05 ｜ 参数见 04-08）。第四类是 DB 编号陷阱：Redis 各库编号来自运行时 `database_config.json`，须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 核验，禁止写死某库是某号；`sonic-db-cli` 用法与参数见 04-05（参数见 04-04 ｜ 字段见 05-03）。第五类是 warm reboot 与多 ASIC 陷阱：状态恢复能力受平台与版本限制，不同 HWSKU 行为不同，一律写「受平台与版本限制，需对照实际版本核验」，不得宣称全平台无条件支持（原理见 06-10 ｜ 原理见 06-11）。

第六类是性能结论陷阱：吞吐低、收敛慢一类现象受机型、芯片与版本影响，单次观测不能下通用结论，一律标注「需在目标机型实测」，按 08-01 的方法做 A/B 对照，按 08-02 的方法排查「越调越慢」的误操作，不给绝对值（基准方法见 08-01 ｜ 调优见 08-02）。第七类是证据链缺失陷阱：凭记忆排查、不记录命令与时刻，交接后无法复现，也无法区分「改动有效」与「恰好恢复」；应把各层查询固定为带时间戳的快照（见第 5 节脚本）。

最佳实践归纳为四条。其一，任何故障先按图 08-03-01 归段，再决定查哪个进程与哪张表，不做跳跃式判断。其二，逐段采集、记录、判定，形成可交接的证据链，命令与输出都注明核验要求，报错文案不编造。其三，跨册引用统一用四段式（字段见 05-06 ｜ 参数见 04-05 ｜ 原理见 06-04 ｜ 模块见 07-03），本篇涉及的 DB 字段写「字段见 05-02」、机制写「原理见 06-0x」、CLI 参数写「参数见 04-05」、进程能力写「模块见 07-03」，不在本篇展开字段表与参数全集。其四，遇到快照内无法核实的内容，宁可标注核验要求并给出目录，也不补值（参数见 04-08 ｜ 模块见 07-05）。

### 3. 分步操作

九个案例按五段式展开。为便于反查，每个案例标题即现象，定位过程中的命令与输出以代码块给出，输出均为示例并注明核验要求；根因、处置、预防以正文给出，便于只读定位与动作分离。

#### 案例一：config 返回成功但 APPL_DB 无表项

**现象**：执行 `config vlan add` 返回成功，但业务无变化，`show` 看不到对应 VLAN，怀疑配置未落库。

**定位过程**：按决策树先确认配置层有配置、搬运层无表项，再查搬运进程状态。

```bash
# 前置检查：确认配置写入（命令选项需对照实际版本核验）
config vlan add 200
sonic-db-cli CONFIG_DB KEYS 'VLAN*'
# 验证搬运层（键格式需对照实际版本核验）
sonic-db-cli APPL_DB KEYS 'VLAN_TABLE:*'
# 查搬运进程（容器名与命令需对照实际版本核验）
docker exec swss supervisorctl status
```

```text
示例输出，具体格式需对照实际版本核验（报错文案需对照实际版本核验）
VLAN|200
（APPL_DB 查询无输出）
vlanmgrd                         RUNNING   pid 123, uptime 0:00:05
```

逐行判读：`config vlan add 200` 返回成功只说明命令执行完毕，不代表配置已写入，故紧随其后查 CONFIG_DB；`CONFIG_DB KEYS 'VLAN*'` 返回 `VLAN|200`，确认配置层已有配置，可排除「命令写错表」。关键在第三行：`APPL_DB KEYS 'VLAN_TABLE:*'` 无输出，说明搬运层缺失，故障定位在 CONFIG_DB 与 APPL_DB 之间，即 mgrd 搬运段。第四行显示 `vlanmgrd` 状态为 `RUNNING` 但 uptime 仅数秒，提示进程可能刚重启、尚未完成预加载或配置字段未被识别。此处输出格式与字段名需对照实际版本核验。

**根因**：mgrd 在配置写入时尚未完成初始化，或配置字段在校验阶段未被识别，导致搬运未发生；对应 06-03 所述「配置未落 APPL_DB」场景（原理见 06-03）。

**处置**：确认 mgrd 稳定后重新写入配置，或按实际字段修正配置；必要时在实验环境重启对应 mgrd 并重新下发。命令名需对照实际版本核验。

**预防**：配置批量下发后固定检查 APPL_DB 表项，避免只凭 `config` 返回判断；把 mgrd 状态纳入上线检查（模块见 07-03 ｜ 参数见 04-08）。

**定位过程**：逐段对比 APPL_DB 与 ASIC_DB，再查 orchagent 日志。


```text
示例输出，具体格式需对照实际版本核验（日志文案需对照实际版本核验）

（ASIC_DB 查询无输出）
（日志中出现与属性处理相关的记录，文案需对照实际版本核验）
```

APPL_DB 有 `VLAN_TABLE:200` 而 ASIC_DB 无对象，判定停驻在 orchagent 翻译段；日志只作辅助佐证，具体文案随版本变化，不据片段下结论（原理见 06-04 ｜ 字段见 05-04）。

**处置**：核对配置属性与机型支持能力，修正后重新下发；若进程异常按 06-04 的调度机制排查重试逻辑（原理见 06-04）。


配置层有 `ACL_TABLE|DATAACL`，说明规则已写入；若 ASIC_DB 无对象或绑定端口不符，问题在编排与绑定段。ACL 与 COPP、QoS 的下发顺序见 06-08，字段需对照实际版本核验（原理见 06-08 ｜ 参数见 04-03）。

**根因**：规则未绑定到目标端口、表类型与实际场景不符，或 ASIC_DB 未生成对应对象；厂商 ACL 表项能力不在本快照，需对照实际版本核验。

**处置**：修正绑定端口与表类型后重新下发，按 06-08 的下发顺序核对（原理见 06-08 ｜ 模块见 07-03）。

**预防**：ACL 变更后用 `show acl` 与 ASIC_DB 双重核对，不只看配置是否存在（参数见 04-05）。

### 4. 验证方法与预期结果

九个案例共用一套验证方法。验证必须对照处置前的基线，按「配置层 → 搬运层 → 编排层 → 对象层 → 状态层 → 运行时」的顺序逐段复查，而不是只看最后一句 show 输出。下表给出每类案例的验证动作与预期结果；预期结果只描述应观察到的「有无与趋势」，不含绝对数值，命令名与表名需对照实际版本核验。

| 案例类别 | 验证动作 | 预期结果 | 判读要点 |
|---|---|---|---|
| 配置与搬运 | 复查 CONFIG_DB 与 APPL_DB | 两层均有对应表项 | 上层有下层无即未落地 |
| 编排与对象 | 复查 ASIC_DB 对象 | 期望状态生成对应对象 | 对象有无不证明芯片已生效 |
| 端口与 ACL | 复查 show 与状态库 | 状态与配置一致 | 区分运行时状态与配置结果 |
| 协议与计数 | 复查邻居与 COUNTERS_DB | 路由存在、计数变化 | 区分未建立与未采集 |
| 容器与恢复 | 复查容器与状态表 | 容器齐全、恢复完成 | 平台能力限制需另行核验 |

验证中有三条要点。其一，预期结果必须成对出现：既要有「配置层有表项」，也要有「ASIC_DB 有对象」，还要有「STATE_DB 已回写」，缺一即未闭环；这正是决策树分层判定的落地（排障见 08-03）。其二，`show` 输出是状态快照而非芯片已生效的证明，任何「看不到」都要先区分是「没配置」还是「没回写」，再决定下一步（原理见 06-01）。其三，涉及性能与容量的验证不做数值断言，吞吐、收敛与表项容量一律标注「需在目标机型实测」，按 08-01 的方法做 A/B 对照（基准方法见 08-01）。

### 5. 常见失败与排错

第一类失败是「只改不验」：处置后没有回到基线逐段复查，把「重启后恰好恢复」当成「改动有效」。排错办法是把第 4 节的成对预期写成检查清单，逐项打勾，并保留带时间戳的证据链（排障见 08-03）。第二类失败是「跨版本照搬」：把其它版本的报错文案、命令选项、容器名与表名直接套用，导致误判；凡引用一律标注「文案需对照实际版本核验」或「需对照实际版本核验」（参数见 04-05 ｜ 参数见 04-08）。

第三类失败是「混淆协议未建立与同步未发生」：BGP 邻居没起来时去查 ROUTE_TABLE，或计数器不涨时去查转发路径，方向从一开始就错；应按图 08-04-01 先归段，再选案例（原理见 06-07 ｜ 原理见 06-09）。第四类失败是「把平台限制当成配置错误」：warm reboot 与多 ASIC 能力受平台与版本限制，不满足前置条件时不是配置写错，而是流程本身不支持，一律写「受平台与版本限制，需对照实际版本核验」，不宣称全平台无条件支持（原理见 06-10 ｜ 原理见 06-11）。

第五类失败是「把 show 当成芯片视图」：ASIC_DB 有对象不等于芯片已生效，端口 Oper up 属运行时状态，不能反推某次配置已使硬件下发；厂商 SAI 实现不在本快照，能力判断写「不在本快照，需对照实际版本核验」（原理见 06-05 ｜ 模块见 07-04）。第六类失败是「硬件归因过早」：在配置、搬运、编排、编程各段未确认前就怀疑光模块或芯片，把排查引向死胡同；硬件边界应放到最后（模块见 07-10）。第七类失败是「给出绝对性能数字」：吞吐低、收敛慢随机型变化，一律标注「需在目标机型实测」，不给绝对值（调优见 08-02）。

### 6. 小结

本篇以九个独立案例把 08-03 的决策树落到处置动作：配置未落 APPL_DB 定位到 mgrd 搬运，orchagent 未消费与 ACL 不生效定位到编排层，PORT 不生效与 DB 不同步分别落到配置、对象与回写段，BGP 邻居建立失败与计数器不涨分别落到协议同步与采集层，容器未起落到进程编排层，warm reboot 失败落到状态恢复层。每个案例按「现象 → 定位过程 → 根因 → 处置 → 预防」五段式展开，命令与输出均注明核验要求，报错文案不编造。图 08-04-01 与速查表是反查索引；四条纪律贯穿全篇——逐段验证、成对预期、硬件边界后置、不确定处标注核验要求。

## 08-05 安全加固：管理面、Redis 暴露与镜像供应链

### 1. 背景与动机

SONiC 作为白盒交换机网络操作系统，其安全模型与通用 Linux 主机有本质差别。控制面并非集中在一个单体进程里，而是分散在 database、orchagent、bgp、teamd、snmp、sonic-gnmi、sonic-telemetry 等多个容器及其中的守护进程；数据面则在 ASIC 转发芯片上，控制面经 SAI 下发，除虚拟交换机 `platform/vs/` 外不做软件转发（原理见 06-01 ｜ 模块见 07-02）。这种「容器化控制面 + Redis 分层数据库 + SAI 抽象」的架构决定了安全加固不能照搬主机加固的套路：要害不在某一个登录 Shell，而在三个地方——外部能否触达管理面接入点、Redis 这条贯穿全系统的数据总线是否对不该访问的主体开放、以及把源码变成可安装镜像的供应链是否可信。本篇的动机就是把这三个面拆开讲清，给出可落地的检查与加固顺序，并明确哪些结论必须留到目标机型核验，版本基准统一为「上游 master 快照（2026-11 抓取）」。

为什么把 Redis 单列为加固面，是本篇最需要读者建立的直觉。CONFIG_DB、APPL_DB、ASIC_DB、STATE_DB、COUNTERS_DB 等逻辑库共同构成控制面的「中枢神经」：`config` 命令写 CONFIG_DB，各 `*mgrd` 搬运到 APPL_DB，orchagent 翻译进 ASIC_DB，syncd 经 SAI 编程 ASIC，状态与计数再回写 STATE_DB、COUNTERS_DB（原理见 06-02 ｜ 原理见 06-05）。这意味着谁能写 CONFIG_DB，谁就能间接改变转发行为；谁能读 ASIC_DB 与 STATE_DB，谁就能窥探拓扑与运行状态。因此 Redis 的绑定地址、保护模式与实例隔离，远比「给交换机设个密码」更接近问题的核心。把 Redis 暴露面收敛好，等于给整条异步流水线加了一道边界闸门。

管理面加固的动机来自接入方式的多样化。传统 CLI 之外，SONiC 通过 `dockers/docker-sonic-gnmi/` 与 `dockers/docker-sonic-telemetry/` 提供 gNMI 与 telemetry 接入，经 `sonic-mgmt-common/translib/` 转换、依赖 `models/yang/` 的模型与 `cvl/` 的校验（模块见 07-07 ｜ 原理见 06-14）。这些接口一旦暴露在管理网甚至业务网，若缺少认证、授权与传输保护，就等于把配置下发能力对外开放。AAA 是这道门的第一把锁：`sonic-utilities/config/aaa.py` 里可以核验到对 AAA 表 authentication、authorization、accounting 的读写，以及 login 方式在 ldap、radius、tacacs+、local 之间的切换。管理面加固不是关闭功能，而是「默认最小暴露、显式开启认证、传输加密、操作留痕」。

供应链加固的动机则来自构建链路的复杂性。SONiC 镜像不是在一台普通主机上裸 `make` 出来的，而是在 `sonic-slave-*/` 构建容器内、经 `Makefile`、`slave.mk`、`rules/` 与 `azure-pipelines.yml` 编排产出 ONIE 安装包（模块见 07-01 ｜ 模块见 07-13）。构建链上任一环被污染，都会把问题带进生产镜像，而且很难在运行期发现。本快照里可以核验到 `scripts/build_sbom.py`、`scripts/build_sbom.sh` 及一整族 `sbom_*.py` 脚本、`azure-pipelines.yml` 中的 SBOM 漏洞扫描阶段、`scripts/efi-sign.sh` 的 EFI 签名脚本，以及 `scripts/audit_dep_completeness.sh` 的缓存键完整性门禁。这些机制共同回答一个问题：镜像里的每个组件从哪来、有没有已知漏洞、构建产物有没有被签名与校验。把供应链纳入加固视野，是 SONiC 运维区别于「只管配置」的关键一步。

需要提前说清本篇的边界。第一，SONiC 是白盒 NOS，不是通用服务器操作系统，本文谈的加固都围绕容器化控制面与 Redis 分层数据库展开，不展开主机内核层的通用加固。第二，FRR / FRRouting 源码、Linux 内核、厂商 SAI 实现均不在本快照，涉及它们的加固细节一律写「不在本快照，需对照实际版本核验」。第三，Redis 各逻辑库的编号来自运行时 `database_config.json`，须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 与实际版本核验，本文不写死任何库号（参数见 04-04）。第四，所有加固项的开关名、路径与返回形态都需对照实际版本核验，本文给的是可定位目录与核验方法，而不是声称全平台通用的一步到位脚本。

### 2. 核心概念

理解三个加固面，先要建立「信任边界」这个概念。信任边界是系统中两个不同信任级别主体之间的交界，加固的本质就是让每次跨越边界都经过显式的检查。在 SONiC 里，管理终端与管理面接入点之间、外部主体与 Redis 实例之间、构建产物与生产镜像之间，各有一条信任边界。三条边界上的主体、凭据与校验方式都不同，但遵循同一原则：默认拒绝、最小权限、可审计。把它画出来就是图 08-05-01 的骨架，后面第四节的调用链会逐条展开。

管理面这一组概念要区分「接入协议」「转换层」与「认证授权」三个层次。接入协议指 gNMI、REST 与 CLI 这些外部可见的接口，分别落在 `dockers/docker-sonic-gnmi/`、`dockers/docker-sonic-telemetry/` 与 `sonic-utilities/` 的 show/config 命令族（命令全集见 04-05）。转换层是 `sonic-mgmt-common/translib/`，它把外部请求翻译成对 CONFIG_DB 等库的操作，并依赖 `models/yang/` 的模型与 `cvl/` 的校验来保证语义合法（模块见 07-07 ｜ 原理见 06-14）。认证授权层由 AAA 承担，`config/aaa.py` 中对 AAA 表的 authentication、authorization、accounting 三类配置分别对应「你是谁」「你能做什么」「你做了什么」三个问题。三者不可混为一谈：开了 gNMI 不等于做了认证，配了 AAA 不等于传输加密，三者要叠加才是完整的管理面加固。

Redis 暴露面这一组概念的关键是「监听形态」与「保护模式」两个词。`dockers/docker-database/database_config.json.j2` 为每个实例定义了 hostname、port 与 unix_socket_path 等字段，说明 Redis 既可能绑定 TCP 地址，也可能通过 Unix 域套接字提供本机访问；`supervisord.conf.j2` 里可以核验到 `redis-server` 的 `--bind`、`--port`、`--unixsocket` 等启动参数，以及依据 `is_protected_mode` 决定是否附加 `--protected-mode no` 的分支。所谓暴露面，就是这些监听端点的可达范围：绑定回环地址并配合保护模式，是把 Redis 收敛到容器内部；因特定场景（如 BMC 链路、linecard 中板）需要跨实例访问而放宽绑定或关闭保护模式，就等于扩大了攻击面。加固的目标是让每一次放宽都有明确理由与补偿控制，而不是无意识地沿用默认。

供应链这一组概念要抓住「可追溯」与「完整性」两条线。`sonic-slave-*/` 是构建容器的定义目录，`Makefile`、`slave.mk`、`rules/` 是装配规则，它们决定了「用什么环境、按什么步骤构建」（模块见 07-01）。`azure-pipelines.yml` 中的 SBOM 阶段与 `scripts/build_sbom.py`、`sbom_*.py` 脚本族负责生成软件物料清单并做漏洞扫描，回答「镜像里有什么、有没有已知漏洞」。完整性则由签名与校验回答：`scripts/efi-sign.sh` 用私钥与证书对 shim、grub、vmlinuz 等 EFI 文件签名，确保启动链上的固件未被篡改。可追溯解决「来源清不清楚」，完整性解决「途中有没有被改」，两者缺一不可。要强调这些脚本的存在只能在本快照核验其文件名与用途，签名密钥管理、证书链与验签的落地细节需对照实际版本核验。

最后要建立一个贯穿三面的判断习惯：配置动作与生效结果是两件事。写下一条 AAA 配置、调整一次 Redis 绑定、生成一份 SBOM，都不等于加固已经生效或风险已经消除；要按「前置检查 → 执行 → 验证输出 → 清理」的闭环，用 `show`、`config` 与 `sonic-db-cli` 读回状态来确认（参数见 04-05）。这一点与全册铁律「config 返回成功不等于硬件已下发」同源（原理见 06-01），只是这里的「硬件」换成了「安全状态」。带着这个习惯读后面的命令实例，才不会把「命令跑通了」误当成「系统安全了」。

### 3. 关键数据结构与源码位置

本节只点名关键结构与源码落位，逐字段内容一律留给 05 册，不在此重列字段表（字段见 05-02 ｜ 字段见 05-03）。管理面的核心落位是 `sonic-mgmt-common/sonic-mgmt-common-master/translib/` 与 `models/yang/`、`cvl/`，CLI 侧是 `sonic-utilities/sonic-utilities-master/config/aaa.py` 与 `show/`、`config/` 目录。Redis 暴露面的核心落位是 `sonic-buildimage/sonic-buildimage-master/dockers/docker-database/` 下的 `database_config.json.j2`、`database_global.json.j2`、`multi_database_config.json.j2`、`supervisord.conf.j2` 与 `docker-database-init.sh`。供应链的核心落位是顶层 `Makefile`、`Makefile.work`、`slave.mk`、`rules/`、`azure-pipelines.yml`、`scripts/` 下的 SBOM 与签名脚本族，以及 `sonic-slave-*/` 各构建容器目录（模块见 07-01 ｜ 模块见 07-13）。以上路径均相对各自子仓的 `xxx-master/` 根。

AAA 侧可以核验到的事实性细节有两类。其一是 `config/aaa.py` 中出现的模块级常量 `RADIUS_MAXSERVERS` 与 `RADIUS_PASSKEY_MAX_LEN`，以及 `is_secret`、`prompt_secret` 这类处理凭据的辅助函数，说明该模块确实承担了密钥输入与服务器数量约束；其二是可编程入口，`login()` 函数通过 `add_table_kv` 与 `del_table_key` 维护 AAA 表的 authentication/login 项，取值在 ldap、radius、tacacs+、local 之间切换，`authorization()` 与 `accounting()` 则维护对应的 authorization/login、accounting/login 项。这些函数名与常量名在本快照可核验，但它们写入的 AAA 表完整字段定义与校验规则需对照实际版本核验（字段见 05-02 ｜ 参数见 04-05）。特别提醒：这里只说「函数名真实存在」，不展开函数签名与参数全集。

Redis 启动侧的落位最值得逐字说明，因为它直接对应「暴露面」。`supervisord.conf.j2` 里 `redis-server` 的命令行可以核验到 `--bind {{ LOOPBACK_IP }} {{ redis_items['hostname'] }}`、`--port {{ redis_items['port'] }}`、`--unixsocket {{ redis_items['unix_socket_path'] }}` 等形态，以及依据 `not redis_items['is_protected_mode']` 决定是否附加 `--protected-mode no` 的 Jinja 分支。`docker-database-init.sh` 里可以核验到根据实例 hostname 是否为 127.0.0.1 来计算 `is_protected_mode` 的逻辑，以及当检测到 switch_bmc 场景时为主 redis 实例注入 bmc_link_ip、bmc_link_if 并关闭保护模式、当检测到 linecard 数据库时为暴露到中板而关闭保护模式的分支。这些是「为什么会放宽绑定」的真实成因，字段名与模板变量属配置层面，具体取值与生成结果需对照实际版本核验（参数见 04-04 ｜ 字段见 05-03）。

供应链侧的落位可以核验到一组明确的脚本与流水线阶段。`scripts/` 下有 `build_sbom.py`、`build_sbom.sh`、`install_sbom_tool.sh`、`sbom_emit_provenance.py`、`sbom_parse_lockfiles.py`、`sbom_resolve_licenses.py`、`sbom_cve_refs.py`、`sbom_diff.py` 等一整族与物料清单相关的工具，以及 `efi-sign.sh`、`convert-pfx-cert-format.sh` 这两个与签名、证书格式转换相关的脚本。`azure-pipelines.yml` 中可核验到 CacheKeyLint 这一 PR 门禁阶段（依赖 `scripts/audit_dep_completeness.sh` 做缓存键完整性审计），以及 SBOM 漏洞扫描阶段（发布 `sbom-vuln-scan-results` 工件）。`efi-sign.sh` 的用法提示里列出 `-p` 私钥、`-c` 证书、`-e` 待签 EFI 文件、`-s` 输出文件四个选项，并点明签名对象是 shim、grub、vmlinuz。这些只是「文件名与用途可核验」，签名密钥保管、证书链信任与验签流程的细节需对照实际版本核验（模块见 07-13）。

图 08-05-01 用颜色区分语义：gray 为外部输入，purple 为管理面的控制面接入与转换，teal 为认证授权，blue 为数据库与 Redis 实例，green 为容器内消费者，amber 为构建产物与 CI，red 为固件、硬件与数据面边界。读图要抓住两条主链。上半链是「运行时信任链」：管理终端的请求先到管理面接入点，经 AAA 鉴权后才被允许写 CONFIG_DB，CONFIG_DB 落到 Redis 实例，再由 mgrd、orchagent、syncd 逐级消费并最终下发 ASIC；任何一级鉴权或绑定缺失，都会让这条链在对应边界上失守（原理见 06-01 ｜ 原理见 06-14）。下半链是「构建完整性链」：构建与 CI 环节产出镜像并做 SBOM 与签名，镜像与固件经 EFI 验签后才被装载，最终承载数据面；这条链保证的是「跑起来的软件就是被审核过的那份」（模块见 07-13）。

先看运行时信任链的管理面一段。外部请求进入 `dockers/docker-sonic-gnmi/` 或 telemetry 容器后，由 `sonic-mgmt-common/translib/` 转换，转换过程受 `models/yang/` 模型与 `cvl/` 校验约束（模块见 07-07）；与此同时 AAA 决定这次请求是否被授权。`config/aaa.py` 里的 authentication/login 决定用 ldap、radius、tacacs+ 还是 local 做身份认证，authorization/login 决定授权来源，accounting/login 决定是否记录操作（参数见 04-05）。关键在于这三者是「与」的关系而非「或」：任何一项缺省都意味着对应边界没有检查。telemetry 的证书相关配置可从 `telemetry_vars.j2` 的 certs、gnmi、x509 字段看出有传输保护的位置，但证书如何签发、如何轮换需对照实际版本核验。管理面加固的正确顺序是「先确认接入面只暴露在管理网，再确认认证开启，最后确认传输加密与审计留痕」。

再看 Redis 绑定一段。CONFIG_DB 的写入最终落到某个 Redis 实例，而 `supervisord.conf.j2` 决定这个实例监听在哪里：`--bind` 后面跟的是 LOOPBACK_IP 与实例 hostname 的组合，`--protected-mode no` 是否附加取决于 `is_protected_mode`。`docker-database-init.sh` 里根据 hostname 是否为回环地址设定保护模式，并在 switch_bmc、linecard 等特定场景主动放宽绑定或关闭保护模式。运行时信任链在这一点的加固判据很具体：默认应当只绑定回环地址并开启保护模式，任何对 0.0.0.0 或非回环地址的绑定、任何 `--protected-mode no` 的出现，都要能追溯到明确的场景理由（如 BMC 链路、中板通信）并有网络层隔离作为补偿控制。读 `database_config.json.j2` 时还要注意它定义了 remote_redis 实例，跨实例访问的存在本身不是问题，问题是它是否暴露在不该可达的网络上（参数见 04-04 ｜ 字段见 05-03）。

最后看构建完整性链。`sonic-slave-*/` 定义了构建环境，`Makefile`、`slave.mk`、`rules/` 决定装配，`azure-pipelines.yml` 编排了 CacheKeyLint 门禁与 SBOM 漏洞扫描阶段（模块见 07-01 ｜ 模块见 07-13）。CacheKeyLint 通过 `scripts/audit_dep_completeness.sh` 在 PR 阶段拦截未被缓存键覆盖的依赖变更，防止缓存命中服务了陈旧产物——这是供应链里很隐蔽的一类风险。`scripts/build_sbom.py` 与 `sbom_*.py` 脚本族生成物料清单并解析锁文件、许可证与 CVE 引用，`efi-sign.sh` 用私钥与证书对 shim、grub、vmlinuz 签名。完整性链上的加固判据是：构建在受控的 slave 容器内进行、产物有 SBOM、关键固件有签名，且验签在启动时真实执行。需要强调，签名脚本与 SBOM 脚本的存在只能说明「机制具备」，密钥是否妥善保管、验签是否被绕过、SBOM 是否覆盖全部组件，都需对照实际版本与实际部署核验。三条链合起来还呼应一个贯穿全册的事实：即便前面全部正确，`config` 返回成功也只代表配置进了 CONFIG_DB，不等于 ASIC 已下发（原理见 06-01），加固状态同理需要读回验证。

### 5. 配置/命令/代码实例

本节给两组最小实例：一组用只读命令核对 Redis 绑定与保护模式的实际形态并作逐行判读，一组给出 AAA 配置与 gNMI/telemetry 证书字段的落位片段。完整的 show / config 命令见 04-05，Redis 对象与库映射见 04-04，字段定义见 05-02 与 05-03，本节不重列参数全集。所有示例输出均注明「示例输出，具体格式需对照实际版本核验」；库名、表名、容器名与命令选项需对照实际版本核验。先给一组只读核对命令：查看 Redis 实例的绑定地址与保护模式，再看一眼 AAA 与 gNMI/telemetry 的配置落位。以下命令需在具备相应权限的环境执行，属只读探查，不改变配置。

```bash
# 前置检查：确认数据库容器可达（容器名需对照实际版本核验）
docker exec -it database redis-cli PING
# 执行：读取主 Redis 实例的绑定地址与保护模式（端口与实例名需对照实际版本核验）
docker exec -it database redis-cli CONFIG GET bind
docker exec -it database redis-cli CONFIG GET protected-mode
# 验证：从配置库读回 AAA 认证方式与 gNMI 证书配置（表名与字段名需对照实际版本核验）
sonic-db-cli CONFIG_DB HGET 'AAA|authentication' login
sonic-db-cli CONFIG_DB HGET 'GNMI|certs' server_cert
```

逐行判读如下。第一段 `redis-cli PING` 返回 `PONG`，说明数据库容器内 Redis 通道可达，这是任何暴露面核对的前置条件；若连不上应先查容器状态而非怀疑加固配置。第二段 `CONFIG GET bind` 返回 `127.0.0.1`，表明该实例只绑定回环地址，外部网络无法直接连到这个 Redis，这是期望的默认收敛形态；若这里出现 `0.0.0.0` 或某个业务网地址，就要回到 `docker-database-init.sh` 查是否有 switch_bmc 或 linecard 分支被触发，并要求给出场景理由与网络隔离补偿。第三段 `CONFIG GET protected-mode` 返回 `yes`，说明保护模式开启，未认证的外部连接会被拒绝；若返回 `no`，则与 `supervisord.conf.j2` 里附加 `--protected-mode no` 的分支对应，属于需要重点审查的放宽项。第四段 `sonic-db-cli CONFIG_DB HGET 'AAA|authentication' login` 返回 `local`，说明登录认证采用本地方式，若期望集中认证则应看到 radius 或 tacacs+，需与 `config/aaa.py` 的取值集合核对。第五段读 `GNMI|certs` 的 server_cert 返回 `(nil)`，说明该字段未配置，意味着 gNMI 的服务端证书可能缺失，需要结合 `telemetry_vars.j2` 的 certs、gnmi、x509 三项与 `dockers/docker-sonic-gnmi/` 的实际启动参数判断传输是否受保护。整体看，这组命令把图 08-05-01 上半链的「Redis 绑定」与「认证授权」两个边界读回成可判读的取值，任何一项偏离预期都要顺着对应源码分支追原因，而不是改完就认定安全（参数见 04-04 ｜ 参数见 04-05 ｜ 原理见 06-14 ｜ 模块见 07-07）。

第二组给出 AAA 配置与证书字段的命令形态，用来说明「加固动作」如何落到配置库；这些命令会写配置，执行前需确认变更窗口与回退方案，配置项名称与取值需对照实际版本核验。

```bash
# 配置集中认证与授权、开启记账（命令形态依据 config/aaa.py 可核验函数整理，需对照实际版本核验）
config aaa authentication login tacacs+
config aaa authorization login tacacs+,local
config aaa accounting login tacacs+,local
# 配置 TACACS+ 服务器与密钥（服务器地址与密钥为示例值，实际需替换并安全保管）
config aaa tacacs add 192.0.2.10
config aaa tacacs key 192.0.2.10 <secret>
# 保存配置使变更在重启后保留（具体命令需对照实际版本核验）
config save
```

这段配置的意图是把认证、授权、记账三项都指向集中式 TACACS+，并用 local 作为授权回退，避免集中服务器不可达时完全失去登录能力。`config/aaa.py` 里 `login()`、`authorization()`、`accounting()` 分别写入 AAA 表的 authentication/login、authorization/login、accounting/login 项，`add_table_kv` 与 `del_table_key` 是其底层读写手段；`prompt_secret`、`is_secret` 说明密钥输入有专门的隐藏与校验处理。需要强调两点：其一，这里服务器地址 `192.0.2.10` 与 `<secret>` 仅为格式示例，不是可用值，实际部署必须替换并妥善保管密钥；其二，AAA 配置是否真正生效、集中服务器是否可达、传输是否加密，都要用第一组的只读命令与 `show` 输出回读确认，命令返回成功不等于认证已按预期工作（参数见 04-05 ｜ 模块见 07-06）。

第三组用一段模板片段印证「Redis 绑定如何由配置生成」，便于把运行期读回的取值与源码分支对上；片段依据 `dockers/docker-database/supervisord.conf.j2` 中可核验的 Jinja 形态整理，做了简化，真实模板需对照实际版本核验。

```jinja
{% if not redis_items['is_protected_mode'] %}
{%- set ADDITIONAL_OPTS = '--protected-mode no' %}
{% else %}
{%- set ADDITIONAL_OPTS = '' %}
{% endif %}
command=/bin/bash -c "... exec /usr/bin/redis-server /etc/redis/redis.conf \
  --bind {{ LOOPBACK_IP }} {{ redis_items['hostname'] }} --port {{ redis_items['port'] }} \
  --unixsocket {{ redis_items['unix_socket_path'] }} {{ ADDITIONAL_OPTS }}"
```

这段模板说明三件事：监听地址由 `LOOPBACK_IP` 与 `redis_items['hostname']` 共同决定，保护模式由 `is_protected_mode` 决定，Unix 域套接字路径由 `unix_socket_path` 给出。把它与第一组命令对照，就能从「运行期看到 bind=127.0.0.1、protected-mode=yes」反推出「生成时 hostname 为回环、is_protected_mode 为真」，从而定位到 `docker-database-init.sh` 里计算该标志的分支。这种「运行期取值 ↔ 生成期模板」的双向对照，是 Redis 暴露面排障最有效的方法（参数见 04-04 ｜ 字段见 05-03 ｜ 模块见 07-02）。

### 6. 注意事项、陷阱与最佳实践

第一类是「开了功能等于做了加固」的陷阱。最常见的是把 gNMI 或 telemetry 容器起来、把 AAA 命令敲完，就认定管理面安全了。实际上接入、转换、认证、授权、传输加密、审计是互相独立的不同层次：容器在跑只说明接入可用，AAA 配了 local 只说明有本地认证，证书字段为 nil 时传输可能仍是明文。判读必须按图 08-05-01 上半链逐层核对，缺哪一层补哪一层，不能用一层的成功掩盖另一层的缺失（原理见 06-14 ｜ 模块见 07-07）。

第二类是 Redis 保护模式的语义陷阱。`--protected-mode no` 并不等于「允许任意外部连接」，它只是关闭了 Redis 自带的保护模式；真正的可达性还取决于 `--bind` 的地址、容器网络与宿主机防火墙。反过来，绑定回环地址也不等于绝对安全：若同容器或同网络命名空间内有非受信进程，Unix 域套接字与回环 TCP 仍可被本地访问。因此放宽绑定与关闭保护模式这两件事要结合 `%docker-database-init.sh` 里 switch_bmc、linecard 等成因一起看，确认每一次放宽都有明确理由与补偿控制（参数见 04-04 ｜ 模块见 07-02）。这里的文件名以可核验的 `docker-database-init.sh` 为准。

第三类是事实纪律与编号陷阱。Redis 各逻辑库编号来自运行时 `database_config.json`，须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 核验，禁止写死某库是某号；`database_config.json.j2` 中出现的 id 字段是模板取值，本文不据此下结论（参数见 04-04）。FRR / FRRouting 源码、Linux 内核与厂商 SAI 实现不在本快照，涉及它们的加固细节一律写「不在本快照，需对照实际版本核验」，不得编造文件、字段名与版本。签名密钥保管、证书链信任与验签流程在本快照只能核验到脚本存在与选项形态，落地细节需对照实际版本核验（模块见 07-13）。

第四类是「配置生效」与「安全状态」混淆的陷阱。写下 AAA 配置、改完 Redis 绑定，都不等于加固已生效；`config` 返回成功与新状态下线是两件事，这与全册「config 返回不等于硬件已下发」的铁律同源（原理见 06-01）。正确的验证闭环是「前置检查 → 执行 → 用只读命令读回 → 对照预期判读 → 必要时清理或回退」，本节第一组命令就是这个闭环的示范。第五类是供应链陷阱：把「构建能出镜像」等同于「供应链可信」。能否构建只说明工具链齐全，而 SBOM 是否覆盖全部组件、CVE 扫描是否阻断高危项、EFI 验签是否在启动时真实执行，都需要单独核验；`azure-pipelines.yml` 里的 CacheKeyLint 与 SBOM 扫描阶段存在，只能说明机制具备（模块见 07-13）。

最佳实践归纳为四条。其一，按信任边界分层加固：管理面先收敛暴露面再开认证与加密，Redis 先默认收敛绑定与保护模式再为特定场景逐个开口，供应链先保证构建环境受控再叠加 SBOM 与签名。其二，所有加固项都用「运行期读回 ↔ 生成期模板」双向对照来验证，把取值反推到源码分支，而不是凭命令返回判定。其三，示例输出一律注明「示例输出，具体格式需对照实际版本核验」并附逐行判读，命令按闭环写全，密钥与地址用示例值并提醒替换。其四，跨册引用统一用四段式写法，本篇涉及的字段写「字段见 05-02 / 05-03」、命令参数写「参数见 04-04 / 04-05」、配置流水线与管理面原理写「原理见 06-01 / 06-14」、模块能力写「模块见 07-02 / 07-07 / 07-13」，不在本篇重列字段表与参数全集。任何容量、时延与吞吐类结论一律标注「需在目标机型实测」，不给绝对值（基准方法见 08-01 ｜ 调优见 08-02）。

### 7. 小结与延伸阅读

本篇把 SONiC 的安全加固拆成三个面：管理面、Redis 暴露面与镜像供应链。管理面的要害是接入、转换、认证、授权、传输加密与审计六层叠加，落位在 `sonic-mgmt-common/translib/`、`config/aaa.py` 与 gNMI/telemetry 容器；Redis 暴露面的要害是绑定地址与保护模式，落位在 `dockers/docker-database/` 的 `supervisord.conf.j2`、`database_config.json.j2` 与 `docker-database-init.sh`；供应链的要害是可追溯与完整性，落位在 `sonic-slave-*/`、`azure-pipelines.yml`、`scripts/build_sbom.py` 与 `scripts/efi-sign.sh`。图 08-05-01 把三条信任边界画在同一张图里，是回查索引；三条判断贯穿全篇——开了功能不等于做了加固、配置生效不等于安全状态、机制存在不等于落地有效。

## 08-06 上线 checklist 与运维手册

### 1. 目标与场景

本篇的目标是把前面各册分散讲述的部署、加固、基准与排障要点，收敛成一份可照着执行的上线检查清单和一本值班可翻的运维手册。SONiC 作为整机 NOS，上线并不是「把配置敲完」就结束：镜像要对、容器要起、配置要落到 CONFIG_DB 并逐级进入 APPL_DB、ASIC_DB，端口与协议要真正可用，计数要能读，安全边界要收口，回滚方案要备好（原理见 06-01 ｜ 模块见 07-02）。任何一个环节漏检，都可能在业务流量接入后变成难以定位的故障。checklist 的价值就在于把这些环节变成逐项打勾的动作，并用明确的「通过判据」取代模糊的「看起来没问题」。

适用场景有三类。第一类是新设备首次上线：从镜像启动、`config_db.json` 落地、端口与 BGP 配置，到接入监控与加固收口，按清单从头走一遍。第二类是升级或重新部署后的复核：用同一份清单确认新版本下各层状态 intact，避免「升级成功但某项能力悄悄退化」，升级与回滚的命令形态见 03-05，受平台与版本限制的 warm reboot 需对照实际版本核验。第三类是变更后的回归检查：改了 AAA、调整了 Redis 绑定、下发了一批 ACL 之后，用清单快速确认没有破坏其他层。三类场景共用一份清单，区别只在执行范围与抽样比例。

本篇与相邻篇的边界要划清。03 册讲「怎么把设备跑起来」的部署步骤，本篇讲「怎么确认设备可以上线并持续健康」的检查与判读；08-03、08-04 讲「出故障后按决策树反查」，本篇的「常见失败与排错」只做分诊与指向，不重复完整案例；08-05 讲加固项的来龙去脉，本篇把它的关键项变成清单条目；08-01、08-02 讲基准方法与调优，本篇只引用「需在目标机型实测」的结论，不给绝对值。换句话说，本篇是「把这些能力组合起来用」的运维视角，不重列任何参数全集（参数见 04-05）或字段表（字段见 05-02）。

版本基准统一为「上游 master 快照（2026-11 抓取）」。清单里的命令名、选项、表名、容器名与字段都需对照实际版本核验，本文给的是「用哪类命令、判读什么状态」的方法，而不是声称全平台无差别适用的脚本。所有容量、收敛、时延与吞吐数字一律标注「需在目标机型实测」，不给绝对值、不给跨机型通用数字（基准方法见 08-01 ｜ 调优见 08-02）。

### 2. 前置条件与环境

执行上线 checklist 之前，先把「人和工具」的条件备齐，否则清单本身会变成误判来源。访问条件上，需要可用的管理网通道与console带外通道：带外通道用于容器或网络异常时的兜底访问，不能只依赖在网管理地址。权限条件上，需要一个具备配置与查询权限的账号，且该账号的认证方式应与 08-05 的加固结论一致——若已切换到 TACACS+ 或 RADIUS，要先确认集中认证服务器可达，并保留 local 回退，避免加固后把自己锁在门外（模块见 07-06）。工具条件上，需要 `show` / `config` 命令族、`sonic-db-cli`、`docker` 命令与 `redis-cli` 可用；这些可执行文件与参数需对照实际版本核验。

信息条件同样关键。手里要有与目标版本匹配的镜像及其来源记录，最好能追溯到构建产物与 SBOM，确认供应链可核验（模块见 07-13）；要有与设备 `device/<vendor>/<hwsku>/` 匹配的 `config_db.json` 或 minigraph 生成结果，确认平台与 HWSKU 一致（模块见 07-10）；要有端口、VLAN、IP、BGP 与 AAA 的规划表，作为「通过判据」的比对基线；要有网络侧的预期状态，如对端设备、邻居 AS 与预期前缀数，否则 `show ip bgp summary` 的输出无从判读（参数见 04-02 ｜ 参数见 04-03）。

变更条件包括变更窗口、回退方案与备份。回退方案至少要能回答三件事：当前运行镜像是什么、能否切回上一版本、`config_db.json` 是否有可恢复的副本。升级与回滚走 `sonic_installer/` 相关命令，具体命令名与选项需对照实际版本核验（模块见 07-06）。配置持久化用 `config save` 一类命令保证变更在重启后保留，其具体形态需对照实际版本核验。若涉及 warm reboot，要先确认该能力受平台与版本限制，不能默认全平台支持（原理见 06-10）。

环境上还要明确「观察点」。各层状态的读取点不同：`show` 命令读的是对外呈现的状态，`sonic-db-cli` 读的是各逻辑库的原始表项，容器与进程状态要经 `docker` 或 `show processes` 一类命令查看。把这几个观察点分清，才能在清单执行中正确判读：例如 `show interfaces status` 看到端口 up 是运行时状态，`sonic-db-cli ASIC_DB` 里看到端口对象是芯片视图，两者不能互相替代（原理见 06-05 ｜ 排障见 08-03）。Redis 各库编号来自运行时配置，须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 核验，本文不写死库号（参数见 04-04）。

edge d -> e "逐段判读"
edge e -> f "业务可用"
edge f -> g "安全收口"
edge g -> h "受控放量"

图 08-06-01 的颜色语义与全册一致：gray 为输入与外部依赖，teal 为配置管理，blue 为数据库，purple 为控制面，green 为运行时与 SAI，red 为故障与硬件边界，amber 为产物与容量。读图要点是「顺序不可跳跃」：版本与镜像不对，后面全白查；容器没起，谈配置落地没有意义；CONFIG_DB 没落地，APPL_DB 与 ASIC_DB 必然为空；逐段判读通过，才谈得上业务可用与安全收口。最下面那条虚线回退路径提醒读者，上线检查不是单向流程，任何一层发现不可接受的结果，都要能退回上一状态。

### 4. 验证方法与预期结果

清单列完，关键是「怎么判定通过」。下面给一组按分层门禁组织的只读验证命令，并附示例输出与逐行判读。命令需在具备查询权限的环境执行，命令名、选项、容器名与表名需对照实际版本核验。

```bash
# 前置检查：版本与容器底座（命令与输出格式需对照实际版本核验）
show version
docker ps
# 执行：逐层读取配置与表项（库名、表名与键格式需对照实际版本核验）
sonic-db-cli CONFIG_DB KEYS 'PORT|*'
sonic-db-cli APPL_DB KEYS 'PORT_TABLE:*'
sonic-db-cli ASIC_DB KEYS 'ASIC_STATE:SAI_OBJECT_TYPE_PORT:*'
# 验证：对外呈现的业务状态
show interfaces status
show ip bgp summary
```

```text
示例输出，具体格式需对照实际版本核验（下列取值仅为格式示意，不代表任何具体版本或机型）
SONiC Software Version: SONiC.master.xxxx
Platform: x86_64-xxxx
HwSKU: xxxx
CONTAINER ID   IMAGE        STATUS        NAMES
a1b2c3d4e5f6   database     Up 2 hours    database
f6e5d4c3b2a1   orchagent    Up 2 hours    orchagent
PORT|Ethernet0

```

逐行判读如下。第一段 `show version` 输出里 `SONiC Software Version`、`Platform`、`HwSKU` 三项分别对应版本基准、平台与硬件 SKU，要与规划表和 `device/<vendor>/<hwsku>/` 目录一致；若 HwSKU 与预期不符，端口数、通道编号都会随之偏差，后续端口检查必然对不上（模块见 07-10）。第二段 `docker ps` 的 STATUS 列显示 database 与 orchagent 均为 `Up`，说明底座容器在跑；若关键容器不在列表或状态反复重启，应停在容器层排障，不要继续看配置（模块见 07-02）。第三段 `sonic-db-cli CONFIG_DB KEYS 'PORT|*'` 返回 `PORT|Ethernet0`，说明端口配置已落 CONFIG_DB，其中 `|` 是 CONFIG_DB 表键的分隔符，具体分隔符与键格式需对照实际版本核验。第四段 APPL_DB 的 `PORT_TABLE:Ethernet0` 说明配置已被搬运到 APPL_DB；若 CONFIG_DB 有而 APPL_DB 无，问题多在 cfgmgr 搬运环节（原理见 06-03）。第五段 ASIC_DB 的 `ASIC_STATE:SAI_OBJECT_TYPE_PORT:oid:...` 说明端口对象已进入芯片视图；但要注意 ASIC_STATE 出现对象只代表 syncd 已纳入视图，不等于厂商 SAI 已写入芯片并生效，属性是否受支持需能力查询确认（原理见 06-05）。第六段 `show interfaces status` 里 Ethernet0 的 Oper 状态为 `up`，是运行时链路状态，需接线与对端配置齐全；第七段 `show ip bgp summary` 里邻居 State 为 `Established`、MsgRcvd 与 MsgSent 持续增长，说明 BGP 会话正常，前缀数要与规划比对（原理见 06-07）。整组命令按「版本 → 容器 → 三层库 → 业务状态」推进，正是图 08-06-01 的逐段落地；任何一层缺失都停在该层，用 08-03 的决策树反查，不要一句「上线完成」带过（排障见 08-03 ｜ 参数见 04-05）。

验证方法上还要遵守三条原则。其一，判据要「可判读」，例如「邻居 Established」「计数随流量增长」是可以直接从输出读出的，而「网络正常」不是判据；写清单时把主观描述换成可观测字段。其二，分层要对号入座：`show` 看呈现状态、`sonic-db-cli` 看原始表项、容器命令看进程健康，三者互为印证又不可互相替代。其三，性能类验证必须标注「需在目标机型实测」，配置下发时延、收敛时间与转发吞吐不给绝对值（基准方法见 08-01 ｜ 调优见 08-02）。

### 5. 常见失败与排错

上线检查中失败最集中的地方，是「某一层有、下一层无」的断点。下表按现象组织分诊路径，给出证据来源、可能原因与修复方向；完整诊断树与案例见 08-03、08-04，本节只做指向。表中命令与表名需对照实际版本核验，单元格内的 `|` 已转义。

| 现象 | 首要证据 | 可能原因 | 修复方向 |
|---|---|---|---|
| config 成功但 APPL_DB 无 | CONFIG_DB 与 APPL_DB 对照 | 配置校验未过或 mgrd 未搬运 | 查 cvl 校验与 cfgmgr 日志 |
| APPL_DB 有但 ASIC_DB 无 | ASIC_DB 查询 | orchagent 未翻译或属性不支持 | 查 orchagent 日志与能力查询 |
| 端口 Oper 为 down | show interfaces status | 未接线、对端未配或速率不匹配 | 查物理链路与对端配置 |
| BGP 非 Established | show ip bgp summary | AS 或地址不匹配、网络不可达 | 核对规划与链路，FRR 细节需核验 |
| 计数不涨 | COUNTERS_DB 与接口计数 | FlexCounter 未采集或轮询未开 | 查 flexcounterorch 与轮询配置 |
| 容器反复重启 | docker ps 与 show logging | 依赖服务未起或资源不足 | 查启动顺序与容器资源 |
| 加固后无法登录 | AAA 与本地回退 | 集中认证不可达且无 local 回退 | 经带外恢复并保留 local 回退 |
| 升级后能力退化 | 清单复核对照 | 版本差异或平台能力变化 | 对照实际版本核验，必要时回退 |

这些现象的共同处理原则是「先分层定位、再查具体进程」。例如「config 成功但 APPL_DB 无」，先用 `sonic-db-cli` 对照 CONFIG_DB 与 APPL_DB 确认断点在搬运段，再查 `cfgmgr/` 的 mgrd 是否运行、`sonic-mgmt-common/cvl/` 的校验是否拒绝（原理见 06-03 ｜ 模块见 07-07）；若一上来就怀疑硬件或重启设备，既找不到根因又扩大了变更面。再如「APPL_DB 有但 ASIC_DB 无」，断点在 orchagent 翻译段，应查 `orchagent/orchdaemon.cpp` 的调度与属性是否被厂商 SAI 支持，而厂商 SAI 不在本快照，相关细节需对照实际版本核验（原理见 06-04 ｜ 原理见 06-05）。

有几类失败与运维操作本身直接相关，值得单列。一是「加固把自己锁在外面」：切换到集中认证后未保留 local 回退，集中服务器一旦不可达就失去登录能力，必须经带外通道恢复并调整 AAA 配置（见 08-05 ｜ 参数见 04-05）。二是「升级后能力退化」：不同版本对 warm reboot、多 ASIC 等能力支持不同，升级后要用同一份清单复核，能力受平台与版本限制，需对照实际版本核验（原理见 06-10 ｜ 原理见 06-11）。三是「缓存命中服务陈旧产物」：这类供应链风险在 `azure-pipelines.yml` 的 CacheKeyLint 阶段被拦截，上线时若发现产物与源码不一致，应回到构建环节核验而非在运行期修修补补（模块见 07-13）。四是「把状态当配置」：`show interfaces status` 的 up 是运行时状态，不能反推某次 config 已使硬件下发，判读要按图 08-06-01 逐段推进（原理见 06-01）。

### 6. 小结

本篇把上线与运维收敛成一份可执行的分层清单：以图 08-06-01 的八层门禁为骨架，用 24 项 checklist 覆盖版本镜像、容器进程、配置落地、流水线表项、业务状态、可观测性、安全收口与容量基线；用一组只读验证命令示范「版本 → 容器 → 三层库 → 业务状态」的逐段判读，并给出常见失败的分诊表。三条判断贯穿全篇：判据必须可判读，分层不可跳跃，性能必实测。与 08-05 呼应，加固项被落到「AAA 认证方式」「Redis 暴露面」两个具体检查条目；与 08-03、08-04 呼应，失败现象按断点分诊并指向完整案例。

延伸阅读按目标分流。想看部署步骤，接读 03-01 至 03-06；想看基准与调优，接读 08-01、08-02；想看诊断树与案例，接读 08-03、08-04；想看加固项的来龙去脉，接读 08-05；想补命令与参数，接读 04-02 至 04-05；想补字段定义，接读 05-02 与 05-03；想补模块能力，接读 07-02、07-06、07-07、07-10 与 07-13；想补底层原理，接读 06-01 至 06-14 相应各篇。跨册引用请始终使用「字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx」的写法，`xx` 替换为具体篇号。

最后重申资料纪律：本篇所有示例输出均注明「示例输出，具体格式需对照实际版本核验」并附逐行判读；命令名、选项、表名、容器名与字段名不确定处均标注核验要求并给出 `dockers/`、`orchagent/`、`cfgmgr/`、`src/swsssdk/` 等可定位目录；Redis 库编号一律不写死，须对照 `sonic-py-swsssdk` 的 `SonicDBConfig` 核验；FRR / Linux 内核 / 厂商 SAI 写「不在本快照，需对照实际版本核验」；warm reboot、多 ASIC 等受平台与版本限制的能力不宣称全平台无条件支持。版本基准始终为「上游 master 快照（2026-11 抓取）」，不写绝对版本号与 Redis DB 编号；性能、容量、收敛与时延类结论一律标注「需在目标机型实测」。至此 08 册运维、性能基准与排障六个篇目齐备，分片 C 的两篇以「加固收口」与「上线清单」完成全册落地。
