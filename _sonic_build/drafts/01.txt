# SONiC 技术资料 · 01 基础与概述
## 01-01 SONiC 是什么：白盒云网络 NOS、能力矩阵与适用边界

### 1. 背景与动机

要理解 SONiC，先要理解它要解决的不是「再写一个路由协议栈」，而是「把交换机操作系统从专用硬件里解放出来」。传统网络设备把转发芯片、板级驱动、协议进程、命令行与管理接口打包成一个不可拆分的封闭系统，采购一台交换机就等于同时锁定了一家厂商的软件、硬件与运维接口。大规模数据中心面对的是上万台端口形态各异、来自不同 ODM 的白盒设备，若每台都有自己的配置语法与状态模型，自动化编排的成本会随设备种类呈级数上升。SONiC 的出发点正是把这台「黑盒」拆成三层：底层是商用交换 ASIC 与厂商提供的 SAI（Switch Abstraction Interface）实现，中间是一套与芯片无关的控制面进程，上层是统一的配置与状态模型。本套资料把这一拆法概括为「容器化控制面加 ASIC 数据面」，这也是贯穿全册的第一条能力边界（原理见 06-01 ｜ 模块见 07-01）。

本套资料的事实锚点是 `upstream_src/` 下的上游 master 快照（2026-11 抓取）。在这个快照里，SONiC 不是一个仓库，而是 `sonic-buildimage` 主仓加七个子仓的集合，每个子仓解压后还有一层 `xxx-master/` 归档目录，真实仓库根形如 `upstream_src/sonic-buildimage/sonic-buildimage-master/`。这一点从 `sonic-buildimage-master/Makefile` 的 `%::` 通配目标把构建转交 `Makefile.work`、再按 `BLDENV` 进入不同 `sonic-slave-*/` 构建容器即可看出：整个系统的入口是「构建一套可安装镜像」，而不是「编译一个可执行文件」。因此阅读 SONiC 源码时，第一件事是建立多仓地图，而不是去找某一个 `main()`。

需要在开篇就划清适用边界：SONiC 是白盒交换机网络操作系统（NOS），目标是驱动真实交换 ASIC 完成线速转发，控制面进程运行在容器里，数据面始终在 ASIC；除虚拟交换机 `platform/vs/` 用于开发与测试外，不做通用软件转发。把它当成一台 Linux 软件路由器、或当成可直接跑在普通 x86 主机上的主机协议栈，都是对定位的误读。相应的性能结论（收敛时间、下发时延、转发吞吐、表项容量）一律标注「需在目标机型实测」，本册不给任何绝对值（基准方法见 08-01）。

### 2. 核心概念

「NOS」在这里指一整套让白盒交换机可管理、可配置、可运维的软件系统，而非单一进程。它至少包含四类职责：把用户意图落成配置（管理面与 `config_db.json`）、把配置翻译成各业务的期望状态（各 `*mgrd`）、把期望状态翻译成 ASIC 对象（`orchagent`）、再把对象经 SAI 编程进芯片（`syncd`）。这四段不是同一个函数调用，而是通过 Redis 逻辑库解耦的异步流水线，因此「命令返回成功」只代表意图被写入了配置的某个环节，绝不代表硬件已经完成编程（原理见 06-01）。

第二个核心概念是「容器化控制面」。快照里 `dockers/` 下有六十余个 `docker-*` 目录，`docker-database`、`docker-orchagent`、`docker-fpm-frr`、`docker-teamd`、`docker-lldp`、`docker-snmp`、`docker-sonic-gnmi`、`docker-sonic-telemetry`、`docker-nat`、`docker-macsec` 等各自封装一组进程与依赖；容器间通过 Redis 交换数据而非直接函数调用。把进程装进容器的好处是故障隔离、独立升级与按特性裁剪，代价是排障时必须按容器逐个查看状态与日志（模块见 07-02 ｜ 参数见 04-07）。

第三个概念是「SAI 抽象」。SAI 定义了一组与芯片无关的 API，`sonic-sairedis/SAI/` 中的头文件本应是接口声明处，但本快照里该目录为空目录，实际头文件与厂商实现均需对照实际版本核验；`meta/`、`vslib/` 则是元数据与虚拟 SAI 的实现所在。`orchagent` 通过 `ASIC_DB` 与 SAI 属性同 `syncd` 交互，从不直接读写寄存器，这是第五条能力边界最容易写反的地方。第四个概念是 Redis 分层：`CONFIG_DB` 存配置、`APPL_DB` 存期望状态、`ASIC_DB` 存 ASIC 对象，另有 `STATE_DB`、`COUNTERS_DB` 等按场景扩展的逻辑库；它们的编号不是硬编码常量，而是由运行时 `database_config.json` 决定，须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 核验，禁止写死「CONFIG_DB 是某号库」（字段见 05-03 ｜ 参数见 04-04）。

由此可给出能力矩阵。下表按「能力、实现载体、本快照可定位的源码位置、边界说明」四列归纳，表中路径均相对各子仓 `xxx-master/` 仓库根，表名与字段需对照实际版本核验。

| 能力维度 | 实现载体 | 本快照源码位置 | 边界说明 |
|---|---|---|---|
| 镜像构建与总控 | Makefile 家族 | `Makefile`、`slave.mk`、`rules/` | 依赖 sonic-slave 容器与 ONIE |
| 容器定义与编排 | 各 docker 镜像 | `dockers/`、`supervisord.conf.j2` | 控制面进程按依赖顺序拉起 |
| 配置生成引擎 | Python 脚本 | `src/sonic-config-engine/` | 由 minigraph 生成初始配置 |
| 配置分层库 | Redis 逻辑库 | `dockers/docker-database/` | DB 编号需对照实际版本核验 |
| 配置管理进程 | 各 `*mgrd` | `sonic-swss/cfgmgr/` | 订阅 CONFIG_DB 写 APPL_DB |
| 编排调度核心 | Orch 框架 | `sonic-swss/orchagent/` | 消费 APPL_DB 写 ASIC_DB |
| SAI 抽象与同步 | syncd 进程 | `sonic-sairedis/syncd/`、`meta/` | SAI 头文件与厂商实现不在本快照 |
| CLI 与状态读取 | show/config | `sonic-utilities/show/`、`config/` | 只读写 DB，不编程 ASIC |

最后是适用边界：需要白盒硬件统一运维、需要跨厂商 ASIC 复用同一套自动化、需要容器化按特性交付的云数据中心网络，是 SONiC 的典型场景；而只需要一台通用服务器做软件路由、只需要一个路由协议进程、或无法获得对应 ASIC 的厂商 SAI 实现时，都不该选它。FRR / FRRouting 源码、Linux 内核、各厂商 SAI 实现与 `sonic-swss-common` 均不在本快照，涉及这些部分一律写「不在本快照，需对照实际版本核验」，不得据本快照编造其文件与字段。

与「配置是什么」直接相关的结构集中在 `sonic-py-swsssdk-master/src/swsssdk/`。`dbconnector.py` 里的 `SonicDBConfig` 类从 `/var/run/redis/sonic-db/database_config.json` 与 `database_global.json` 读取 `DATABASES` 与 `INSTANCES` 配置，`get_dbid(db_name)` 从 `["DATABASES"][db_name]["id"]` 取出逻辑库编号，再由 `SonicV2Connector.connect()` 用该编号建立连接；换言之，DB 编号是「运行时配置文件的值」，不是源码里的常量，这正是禁止凭印象写死编号的依据。`configdb.py` 里的 `ConfigDBConnector` 继承 `SonicV2Connector`，对外提供 `set_entry`、`get_entry`、`get_table` 等读写方法，是 CLI 落地配置的主要封装（字段见 05-03）。

与「意图怎么翻译」相关的结构在 `sonic-swss-master/orchagent/` 与 `sonic-sairedis-master/syncd/`。前者 `orch.h`、`orch.cpp` 定义 `Orch` 基类与任务调度，`orchdaemon.cpp` 负责注册各业务 Orch，`main.cpp` 包含 `sai.h`、`sairedis.h` 与 `orchdaemon.h` 并进入主循环，`bulker.h` 提供批量写入支持；各派生实现按业务分布在 `portsorch.cpp`、`intfsorch.cpp`、`neighorch.cpp`、`aclorch.cpp`、`copporch.cpp`、`bufferorch.cpp`、`qosorch.cpp`、`fdborch.cpp`、`flexcounterorch.cpp`、`crmorch.cpp`、`mirrororch.cpp`、`chassisorch.cpp`、`mplsrouteorch.cpp`、`routeorch.cpp` 等文件（字段见 05-05 ｜ 原理见 06-04）。后者 `syncd/main.cpp` 只把 `main()` 转交给 `syncd_main()`，真正的启动逻辑在 `syncd_main.cpp`，核心对象分布在 `Syncd.cpp`、`SaiSwitch.cpp`、`SaiObj.cpp`、`VendorSai.cpp`、`SaiDiscovery.cpp`（字段见 05-06 ｜ 模块见 07-04）。

平台与初始化相关结构也有固定落位：`device/<vendor>/<hwsku>/` 下的 `config_db*.json` 与 `minigraph.xml` 描述具体机型的端口与设备元数据，`src/sonic-config-engine/` 下的 `minigraph.py`、`portconfig.py`、`sonic-cfggen` 负责把它们渲成初始配置，`files/image_config/` 下的 `constants/`、`copp/`、`interfaces/`、`hostname/`、`config-setup/`、`config-chassisdb/`、`config-topology/` 则是开机阶段写入各库的脚本与模板（字段见 05-09 ｜ 参数见 04-02）。以上只列名称与位置，字段名、成员类型与读写时机一律留待 05 册，函数名后缀与签名需对照实际版本核验。

图 01-01-01 用颜色区分了语义：teal 为管理面与配置管理，blue 为输入与数据库，purple 为控制面编排，amber 为 ASIC_DB，green 为 syncd 与 SAI 运行时，red 为硬件边界。需要强调的是，这是一条异步流水线而非同步调用。用户执行 `config` 命令后，`sonic-utilities-master/config/main.py` 经 `ConfigDBConnector` 把配置写入 `CONFIG_DB` 即返回；随后 `sonic-swss-master/cfgmgr/` 下的 `portmgrd.cpp`、`intfmgrd.cpp`、`vlanmgrd.cpp`、`buffermgrd.cpp`、`coppmgrd.cpp` 等订阅变更、校验并写入 `APPL_DB`；再由 `orchagent/` 的 `Orch` 调度消费 `APPL_DB`，生成对象写入 `ASIC_DB`；最后 `sonic-sairedis-master/syncd/` 消费 `ASIC_DB` 并经 SAI 完成芯片编程，同时把状态回写到 `STATE_DB` 与计数器库（原理见 06-01 ｜ 原理见 06-03 ｜ 原理见 06-04 ｜ 原理见 06-05）。

这条链路每一段都有对应的失败点，也决定了排障的基本顺序：配置不生效时，应先查 `CONFIG_DB` 是否写入、再查 `APPL_DB` 是否生成、再查 `ASIC_DB` 是否出现对象、最后看 `STATE_DB` 与 `show` 输出，而不是一上来就怀疑硬件。管理面还有一条并行路径：`sonic-mgmt-common-master/models/yang/` 的模型经 `cvl/` 校验、`translib/` 转换，最终同样落到 `CONFIG_DB`，`generic_config_updater/` 提供补丁式更新，gNMI 与 telemetry 分别由 `dockers/docker-sonic-gnmi/`、`dockers/docker-sonic-telemetry/` 承载（原理见 06-14 ｜ 模块见 07-07）。

镜像与启动是另一条链：`Makefile` 把目标转交 `Makefile.work`，在 `sonic-slave-bookworm/` 等构建容器内编译，`build_image.sh` 读取 `onie-image.conf` 中的 `ONIE_IMAGE_PART_SIZE`、`TARGET_MACHINE` 等变量，产出 `target/sonic-<machine>.bin` 这样的 ONIE 安装包；设备安装后由 `files/image_config/` 与 `dockers/docker-orchagent/supervisord.conf.j2` 按 `dependent_startup_wait_for` 顺序拉起 `portsyncd`、`orchagent`、`swssconfig`、`vlanmgrd`、`intfmgrd`、`portmgrd` 等进程（原理见 06-13 ｜ 参数见 04-01 ｜ 模块见 07-11）。由此可见，「在普通主机裸 `make` 就能得到可安装镜像」是不成立的，构建必须在 slave 容器内并经 ONIE 安装器完成。

### 6. 注意事项、陷阱与最佳实践

第一类是定位陷阱。最常见的是把 SONiC 写成「跑在 x86 上的软件路由器」。必须反复确认：它是白盒交换机 NOS，控制面在 `orchagent`、`syncd`、各 `*mgrd`、`bgpd`、`teamd` 等容器进程，数据面在 ASIC，控制面经 SAI 下发；除 `platform/vs/` 虚拟交换机外不做软件转发。第二类是把 `config` 命令返回成功等同于硬件已下发。由于流水线异步，正确的验证姿势是按 `CONFIG_DB`、`APPL_DB`、`ASIC_DB`、`STATE_DB` 顺序逐段核对，再结合 `show` 输出，配置即时生效的说法一律不成立（原理见 06-01 ｜ 排障见 08-03）。

第三类是事实纪律陷阱：不要写死 Redis DB 编号，也不要凭印象补 CONFIG_DB 表名、字段名与函数签名。`dbconnector.py` 的 `get_dbid()` 表明编号来自 `database_config.json` 的 `id` 值，编号与表字段须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 与实际版本核验；不确定的一律标注「需对照实际版本核验」并给出 `cfgmgr/`、`orchagent/`、`src/swsssdk/` 等可定位目录。第四类是把仓库写单一：本快照只有主仓加七个子仓，FRR / FRRouting 源码、Linux 内核、各厂商 SAI 实现、`sonic-swss-common` 都不在本快照，`sonic-sairedis/SAI/` 在本快照甚至是空目录，撰写相关字段时必须写「不在本快照，需对照实际版本核验」，不得编造文件与版本。

第五类是构建与平台陷阱。镜像构建依赖 `sonic-slave-*/` 容器与 ONIE 安装器（`onie-image.conf`、`installer/`），`make` 在 slave 容器内运行并产出 ONIE 安装包，普通主机裸 `make` 不能得到可安装镜像；`warmrestart/`、多 ASIC 命名空间与 chassis 支持（如 `orchagent/chassisorch.cpp`、`files/image_config/config-chassisdb/`）受平台与版本限制，不同 HWSKU 与版本能力不同，一律写「受平台与版本限制，需对照实际版本核验」，不得宣称全平台无条件支持。第六类是性能陷阱：收敛时间、配置下发时延、转发吞吐与表项容量一律标注「需在目标机型实测」，不给绝对值、不给跨机型通用数字（基准方法见 08-01 ｜ 调优见 08-02）。

最佳实践可归纳为四条：其一，先建立 8 子仓地图再读代码，路径一律写成 `upstream_src/<子仓>/<子仓>-master/` 下的相对路径；其二，任何配置改动都按「前置检查、执行、验证输出、清理」的闭环操作，并明确区分「已写入配置」与「已下发硬件」；其三，引用字段、参数、机制、模块时按（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）的约定交叉引用，不在总览册展开字段表与 API 全集；其四，遇到快照内无法核实的内容，宁可写「需对照实际版本核验」并给出目录，也不要补值。

### 7. 小结与延伸阅读

本篇确立了全册的基线：SONiC 是面向白盒交换机的网络操作系统，控制面容器化、数据面在 ASIC、二者经 SAI 解耦；配置以 `CONFIG_DB` → `APPL_DB` → `ASIC_DB` → SAI 的异步流水线生效；系统由八个子仓组成，事实核验以各子仓 `xxx-master/` 仓库根为唯一锚点；版本基准统一为「上游 master 快照（2026-11 抓取）」，不写绝对版本号与 Redis DB 编号；FRR、Linux 内核、厂商 SAI 实现与 `sonic-swss-common` 不在本快照。图 01-01-01 给出的分层关系与两张表格给出的能力矩阵、多仓地图，是后续各册反复回查的索引。

## 01-02 与厂商 NOS / Cumulus / FRR / DENT 的对比

### 1. 背景与动机

只从 SONiC 内部看 SONiC，很容易把「容器 + Redis + SAI」误当成某种通用软件架构，而看不清它究竟替代了什么、又不替代什么。数据中心网络团队在做技术选型时，面前通常摆着四类东西：传统厂商的封闭 NOS、以 Linux 网络栈为核心的开放 NOS（常被笼统称为 Cumulus 一类）、单纯的路由协议栈（FRR / FRRouting），以及面向轻量白盒的 DENT 一类系统。它们解决的层次并不相同，把它们放在同一张表上比「谁的功能多」没有意义，必须比「各自占哪一层、彼此是包含还是替代关系」。本篇的动机就是把这个分工讲清楚，避免读者把 FRR 当成 SONiC 的竞品、或把 SONiC 当成 FRR 的替代品。

从本快照能得到一个很强的证据：SONiC 里确实有路由协议进程，但它被装进 `dockers/docker-fpm-frr/` 容器，容器内 `frr/` 目录与 `docker_init.sh`、`vtysh.conf`、`zsocket.sh` 一起提供集成环境，而 FRR / FRRouting 的协议源码并不在本快照（模块见 07-08）。也就是说，FRR 在 SONiC 里是「被集成的组件」，不是「被替换的对手」。同理，`sonic-buildimage-master/src/sonic-config-engine/` 的 `minigraph.py`、`portconfig.py`、`sonic-cfggen` 负责在启动前生成整机配置，`sonic-swss-master/orchagent/` 负责把配置翻译成 ASIC 对象，这两类能力都不是一个单纯路由协议栈会提供的。把「NOS 加容器编排」与「单一路由栈」的差别看清，是本篇的核心任务（原理见 06-01 ｜ 模块见 07-01）。

对比还有一层现实意义：不同系统的配置生效路径不同，排障方式也随之不同。封闭 NOS 往往只有厂商 CLI 一条入口；纯路由栈主要通过 `vtysh` 类命令与内核路由表交互；而 SONiC 的配置要穿过 `CONFIG_DB`、`APPL_DB`、`ASIC_DB` 三段库与 `cfgmgr/`、`orchagent/`、`syncd/` 三组进程。若沿用了「改完协议配置就立即生效」的直觉，就会在 SONiC 上得出错误结论：命令返回成功不等于硬件已下发（原理见 06-01 ｜ 排障见 08-03）。因此本篇在讲选型的同时，也会把「配置路径差异」作为对比维度之一。

### 2. 核心概念

先给四个对象的定位定义。厂商封闭 NOS 指软硬件一体交付、配置接口与状态模型由单一厂商定义的系统，优点是软硬协同与统一支持，代价是设备与运维接口被锁定。Cumulus 一类开放 NOS 把 Linux 网络栈、交换芯片驱动与网络服务组合起来，强调在通用 Linux 工具链上管理网络；其具体发行形态与版本不在本快照，涉及实现细节需对照实际版本核验。FRR / FRRouting 是路由协议栈，实现 BGP、OSPF、IS-IS 等协议并把路由_INSTALL 到内核转发面，它不负责整机镜像、容器编排、端口与 VLAN 的 ASIC 编程，本快照内没有其源码。DENT 一类系统面向轻量白盒交换场景，同样强调 Linux 生态与较薄的 NOS 层，具体能力需对照实际版本核验。

SONiC 的定位与它们都不同：它是整机 NOS，覆盖「镜像构建、开机配置、容器化控制面、Redis 分层状态、SAI 抽象、ASIC 编程、CLI 与 gNMI 管理面」全链条。区分点可以归纳为三个。第一，范围：SONiC 管的是一台交换机的完整生命周期，FRR 只管路由协议那一段。第二，数据面：SONiC 的数据面在 ASIC，控制面经 SAI 下发，除 `platform/vs/` 外不做软件转发；纯路由栈通常依赖内核转发面。第三，配置模型：SONiC 用 Redis 逻辑库把「意图、期望状态、ASIC 对象」显式分层，任何一次 `config` 都要走异步流水线，这与「直接改协议进程配置」有本质差别（原理见 06-02 ｜ 字段见 05-02）。

还要明确「包含关系」而非「并列关系」：在 SONiC 里，FRR 以容器形式存在，`docker-fpm-frr/` 中的 `bgpd` 产生路由，`sonic-swss-master/fpmsyncd/` 下的 `fpmsyncd.cpp`、`fpmlink.cpp`、`routesync.cpp` 把路由同步进 `APPL_DB`，再由 `orchagent/` 的 `routeorch.cpp`、`mplsrouteorch.cpp` 等下发到 `ASIC_DB`（原理见 06-07 ｜ 模块见 07-08）。因此「SONiC 与 FRR 对比」准确的说法是「SONiC 如何集成并承载 FRR」，而非二者互斥。至于 Cumulus、DENT 与厂商 NOS，本快照没有它们的源码，只能作定位级对比，任何实现细节、命令名与版本号都写「需对照实际版本核验」，不得据本快照编造。

下表给出四类系统与 SONiC 的分工对比，作为本节的概念收束；表中「本快照可核验性」一列专门标注证据边界。

### 3. 关键数据结构与源码位置

本节点名用于支撑对比的结构与目录，不展开字段表或 API 全集（字段见 05-01 ｜ 参数见 04-02 ｜ 原理见 06-01 ｜ 模块见 07-03）。对比所需的证据分三组。

第一组证明「SONiC 是 NOS 而非路由栈」：`sonic-buildimage-master/src/sonic-config-engine/` 下的 `minigraph.py` 含 `parse_chassis_deviceinfo()`、`minigraph_encoder` 等解析与编码入口，`portconfig.py` 含 `get_port_config()`、`parse_port_config_file()`、`get_child_ports()` 等端口配置函数，`sonic-cfggen` 用 `argparse` 提供 `-m/--minigraph`、`-k/--hwsku`、`-p/--port-config`、`-t/--template`、`-d/--from-db`、`-v/--var` 等选项。这些脚本在开机前把 `device/<vendor>/<hwsku>/minigraph.xml` 与 `config_db*.json` 转成整机配置，是任何单一路由协议栈都不具备的「整机渲染」能力（字段见 05-09 ｜ 参数见 04-02）。

第二组证明「NOS 加容器编排」：`sonic-buildimage-master/dockers/` 下容器目录按职责分布，`dockers/docker-orchagent/supervisord.conf.j2` 引入 `supervisord.conf.common.j2`，后者用 `[program:orchagent]` 等段落与 `dependent_startup_wait_for=` 定义 `portsyncd`、`orchagent`、`swssconfig`、`vlanmgrd`、`intfmgrd`、`portmgrd`、`buffermgrd`、`neighsyncd`、`coppmgrd`、`vrfmgrd`、`nbrmgrd`、`vxlanmgrd`、`tunnelmgrd`、`fdbsyncd`、`enable_counters` 等进程的启动顺序与优先级（模块见 07-02 ｜ 参数见 04-07 ｜ 原理见 06-13）。这种「一组进程按依赖拉起、通过数据库解耦」的形态，与单一路由进程加内核转发面的形态截然不同。

第三组证明「FRR 被集成而非被替代」：`dockers/docker-fpm-frr/` 目录内有 `Dockerfile.j2`、`docker_init.sh`、`frr/`、`vtysh.conf`、`zsocket.sh` 与 `TS`、`TSA`、`TSB`、`TSC` 等文件，但 FRR 协议源码不在本快照；路由从协议进程进入 SONiC 世界的桥是 `sonic-swss-master/fpmsyncd/` 的 `fpmlink.cpp` 与 `routesync.cpp`，出口是 `orchagent/routeorch.cpp`（原理见 06-07 ｜ 模块见 07-08）。此外 `sonic-utilities-master/config/main.py` 引入 `minigraph`、`portconfig`、`generic_config_updater` 与 `swsscommon` 的 `ConfigDBConnector`、`ConfigDBPipeConnector`、`SonicV2Connector`，说明 CLI 走的是「配置库」而非「协议进程直连」；`swsscommon` 本体在 `sonic-swss-common`，不在本快照，需对照实际版本核验。

把配置路径并列起来，差异更清楚。封闭 NOS 的典型路径是「厂商 CLI → 厂商内部配置 → 芯片」，对外只有一条黑盒入口；纯路由栈的路径是「`vtysh` 类命令 → 协议进程 → 内核路由表 → 转发面」；而 SONiC 是「`config` / gNMI / YANG → `CONFIG_DB` → `cfgmgr/` → `APPL_DB` → `orchagent/` → `ASIC_DB` → `syncd/` → SAI → ASIC」（原理见 06-01 ｜ 原理见 06-14）。三者最实质的区别不是命令语法，而是 SONiC 把中间状态显式持久化到多个逻辑库，因而可逐段观测、可重放、可异步重试，但也因此不具备「即时生效」的语义。

以 BGP 为例可见「集成」的完整调用链：`docker-fpm-frr/` 内协议进程产生路由变更，`fpmsyncd/` 的 `fpmlink.cpp` 接收、`routesync.cpp` 解析并写入 `APPL_DB` 的路由表，`orchagent/` 的路由族 Orch 消费后写 `ASIC_DB`，`syncd/` 再经 SAI 编程；运维侧用 `show ip bgp summary` 看协议状态、用 `show` 与各库查询看下发状态，两者结论可能不同，这不是故障而是异步流水线的正常表现（原理见 06-07 ｜ 排障见 08-04）。上述表名、命令名与函数签名需对照实际版本核验，本册只给链路形态。

逐行判读如下。第一行是地址族标题，表明这是 IPv4 单播的 BGP 汇总，具体输出格式随版本与集成方式变化，需对照实际版本核验；第二行给出本端 router identifier 与本地 AS，属于协议进程状态，由 `docker-fpm-frr/` 内的协议栈提供，FRR 源码不在本快照；第三行是列头，`V` 为协议版本、`AS` 为对端自治域、`MsgRcvd` 与 `MsgSent` 为收发报文计数、`Up/Down` 为会话时长、`State` 为会话状态；第四行对端 `State` 为 `Established` 表示会话已建立，是正常值，计数持续增长也属正常；第五行对端 `State` 为 `Idle` 且收发计数为零，是未建连的典型异常特征，需查对端可达性与配置；第六行是邻居总数统计。最关键的一点：这里的 `Established` 只说明协议会话起来了，并不等于路由已经写进 `APPL_DB`、更不等于已下发 ASIC；按 SONiC 的异步流水线，还须经 `fpmsyncd/` 同步、`orchagent/` 消费、`syncd/` 编程，故排障时应把 `show ip bgp summary` 与 `APPL_DB`、`ASIC_DB`、`STATE_DB` 的查询分开判读（原理见 06-07 ｜ 排障见 08-03）。命令名与选项需对照实际版本核验，完整命令见 04-05。

### 6. 注意事项、陷阱与最佳实践

第一类陷阱是「层次错配」：把 FRR 与 SONiC 当作二选一的竞品。正确关系是 FRR 以 `docker-fpm-frr/` 容器集成进 SONiC，路由经 `fpmsyncd/` 进入 `APPL_DB` 再下发，FRR 协议源码不在本快照、需对照实际版本核验。第二类是把 Cumulus、DENT、厂商 NOS 的实现细节写进本套资料：它们不在本快照，任何命令、字段、版本号一律写「不在本快照，需对照实际版本核验」，不得据推测补值。第三类是把「协议状态正常」当成「转发正常」：`show ip bgp summary` 的 `Established` 与「路由已进 ASIC」是两件事，必须按（原理见 06-01 ｜ 排障见 08-03）逐段核对，配置返回成功同样不代表硬件已下发。

第四类陷阱涉及能力边界的整体一致性。对比时不得把 SONiC 写成软件路由器或通用主机协议栈：它是白盒交换机 NOS，控制面在容器进程、数据面在 ASIC、经 SAI 下发，除 `platform/vs/` 外不做软件转发。不得写死 Redis DB 编号，编号须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 与运行时 `database_config.json` 核验；不得把 `orchagent` 写成直接操作硬件，它只经 `ASIC_DB` 与 SAI 属性同 `syncd` 交互；不得把 CLI 写成编程 ASIC，`sonic-utilities/` 的 `show` / `config` 只读写各 DB。镜像构建依赖 `sonic-slave-*/` 容器与 ONIE 安装器，普通主机裸 `make` 得不到可安装镜像；`warmrestart/`、多 ASIC 与 chassis 能力受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持。

第五类是选型与性能表述陷阱。四类系统的取舍应基于「是否需要统一白盒运维、是否需要跨厂商 ASIC 复用自动化、是否只缺一个路由协议栈、是否无法获得厂商 SAI 实现」来判断，而不是基于功能数量对比；任何收敛时间、配置下发时延、转发吞吐与表项容量结论一律标注「需在目标机型实测」，不给绝对值（基准方法见 08-01 ｜ 调优见 08-02）。厂商封闭 NOS 与开放 NOS 的优劣不在本快照证据范围内，本册只作定位级对照，不作评测结论。

把四类对象落到可执行的判定上，可以按四个问题依次收敛，四类选型决策见下表。

| 判定问题 | 答案为「是」的指向 | 答案为「否」的指向 |
|---|---|---|
| 是否要管理整机白盒交换机 | 需要 NOS 级能力 | 路由栈或通用网络栈更轻 |
| 是否跨厂商 ASIC 复用自动化 | SAI 抽象收益明显 | 封闭 NOS 也可满足 |
| 能否获得对应 ASIC 的 SAI 实现 | 可完成芯片编程 | 功能对比失去意义 |
| 是否接受异步与容器化运维 | 适配 SONiC 模型 | 需先补齐流程与培训 |

第一问是「是否要管理整机白盒交换机」：若答案是否，只需要一台服务器跑路由协议，那么 FRR 一类路由栈或通用 Linux 网络栈更轻，SONiC 的镜像构建、ONIE 安装、HWSKU 适配与容器编排都会成为额外负担。第二问是「是否需要跨厂商 ASIC 复用同一套配置与自动化」：若是，SAI 抽象与 Redis 分层状态模型带来的统一运维收益才真正体现，这也是 SONiC 的主要适用场景。第三问是「能否拿到对应 ASIC 的厂商 SAI 实现」：拿不到就无法完成最后一段编程，厂商 SAI 实现闭源且不在本快照、需对照实际版本核验，此时再比较功能多少没有意义。第四问是「是否接受异步配置语义与容器化排障方式」：SONiC 的 `config` 返回不等于硬件已下发，运维必须按库逐段核对、按容器逐个查状态，团队若沿用封闭 NOS 的即时生效直觉，需要相应的流程与培训配套。四个问题都指向 SONiC 才是合理选型，只命中一两项往往说明层次错配；表中结论是定位级判断，不作跨系统评测，具体能力需对照实际版本核验。

最佳实践有三条。其一，做对比时先声明「本快照有什么、没有什么」，把可核验与不可核验分开写。其二，涉及 FRR 时明确写成「容器集成 + `fpmsyncd/` 同步」的链路，并标注协议源码不在本快照。其三，跨册引用统一用（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx），其中 `xx` 为具体篇号；本篇涉及的数据库配置应写「参数见 04-04」、涉及 `fpmsyncd` 机制应写「原理见 06-07」、涉及 FRR 容器应写「模块见 07-08」，不在总览册展开字段表与命令全集。

### 7. 小结与延伸阅读

本篇的结论可以压缩成一句话：四类对象不在同一层，SONiC 是整机白盒 NOS，FRR 是它以容器集成的路由协议组件，Cumulus、DENT 与厂商封闭 NOS 是定位对照对象且不在本快照。支撑这一结论的证据有三组：`src/sonic-config-engine/` 与 `orchagent/` 体现「整机配置渲染 + 编排」能力，`dockers/` 与 `supervisord.conf.common.j2` 体现容器化按依赖启动，`docker-fpm-frr/` 与 `fpmsyncd/` 体现 FRR 被集成并同步进 `APPL_DB`。图 01-02-01 与分工对比表把「包含关系」与「对照关系」区分开，是后续阅读的索引。

延伸阅读按疑问分流。想确认「配置到底怎么逐段走」，接读 01-03 的整体架构与 06-01、06-02、06-03、06-04、06-05；想弄清路由从协议进程到 ASIC 的完整链路，接读 06-07 与 07-08，并记住 FRR 源码不在本快照；想做实际选型与部署，接读 02-04（平台适配与 `platform/vs/`）、03-03（端口、VLAN、IP 与 BGP 配置）、03-04（CLI 与 gNMI 接入）。字段与参数的随查走 05、04 两册，模块能力走 07 册，运维判读与案例走 08-03、08-04。

## 01-03 整体架构：容器化组件、Redis 数据库分层、SAI 与 syncd

### 1. 背景与动机

01-01 给出了白盒 NOS 的分层与能力矩阵，01-02 给出了四类系统的分工，但读者手里仍缺一张「把进程、数据库与芯片放在同一张图上」的总图。这张图之所以必要，是因为 SONiC 的复杂度不在单个算法，而在状态被切成很多段、分布在不同容器与不同 Redis 逻辑库里：一次端口配置，管理面写进一个库，配置管理进程搬到另一个库，编排核心再翻译成对象写进第三个库，最后同步守护进程才经 SAI 编程芯片。任何一段没走通，表面现象都是「配置没生效」，但根因和排查入口完全不同。没有整体架构图，就容易把「库里没表项」误判成「芯片坏了」，或把「`config` 已返回」误判成「转发已生效」。

第二个动机来自多仓结构本身。本快照里没有单一的「SONiC 源码根目录」，八个子仓各自有 `xxx-master/` 真实仓库根：`dockers/` 与 `files/image_config/` 在 `sonic-buildimage/sonic-buildimage-master/`，`orchagent/` 与 `cfgmgr/` 在 `sonic-swss/sonic-swss-master/`，`syncd/` 在 `sonic-sairedis/sonic-sairedis-master/`，CLI 在 `sonic-utilities/sonic-utilities-master/`，DB 访问封装在 `sonic-py-swsssdk/sonic-py-swsssdk-master/`，管理面模型在 `sonic-mgmt-common/sonic-mgmt-common-master/`。要把一次配置变更追到底，必须能在这些仓库之间来回跳转，因此本篇把「组件—源码位置—调用链」三者绑定陈述，而不是按概念泛泛而谈（模块见 07-01 ｜ 模块见 07-03 ｜ 模块见 07-04）。

第三个动机是划清「控制面」与「数据面」的物理边界。控制面全部是容器里的 Linux 进程，数据面是交换 ASIC，二者之间隔着 SAI 这层抽象；`orchagent` 不直接读写寄存器，`show` / `config` 不直接编程芯片。这条边界一旦写反，整套资料的结论都会失真。本篇因此在讲架构时反复强调：Redis 库是控制面内部的状态分层，`ASIC_DB` 是控制面交给 `syncd` 的「待编程对象队列」，SAI 是 `syncd` 与芯片实现之间的接口，真正的数据转发始终发生在 ASIC（原理见 06-01 ｜ 原理见 06-05）。

### 2. 核心概念

第一组概念是「容器化组件」。`sonic-buildimage-master/dockers/` 下有六十余个 `docker-*` 目录，按职责可分为数据库容器、编排容器、协议容器、外围功能容器与管理面容器几类：`docker-database` 承载 Redis，`docker-orchagent` 承载 `orchagent` 与一众 `*mgrd`、`*syncd`，`docker-fpm-frr` 承载路由协议栈，`docker-teamd`、`docker-lldp`、`docker-snmp` 承载链路聚合、邻居发现与网管，`docker-sonic-gnmi`、`docker-sonic-telemetry` 承载管理面与采集，`docker-nat`、`docker-macsec` 承载特性容器。需要特别指出，`dockers/` 下并没有名为 `docker-syncd` 的目录，`syncd` 的主体在 `sonic-sairedis-master/syncd/`；`platform/vs/` 下则有 `docker-syncd-vs` 等虚拟交换机专用目录，二者不要混淆（模块见 07-02 ｜ 模块见 07-04）。

容器内进程的启动不是无序的。`dockers/docker-orchagent/supervisord.conf.j2` 定义了 `dependent-startup` 事件监听、`supervisor-proc-exit-listener-rs` 与 `rsyslogd`，并 `include` 了 `supervisord.conf.common.j2`；后者用 `[program:orchagent]` 等段落为 `gearsyncd`、`portsyncd`、`orchagent`、`swssconfig`、`restore_neighbors`、`coppmgrd`、`neighsyncd`、`vlanmgrd`、`intfmgrd`、`portmgrd`、`fabricmgrd`、`buffermgrd`、`enable_counters`、`vrfmgrd`、`nbrmgrd`、`vxlanmgrd`、`tunnelmgrd`、`fdbsyncd` 分别指定 `command`、`priority` 与 `dependent_startup_wait_for`。例如 `orchagent` 段以 `/usr/bin/orchagent.sh` 启动、依赖 `portsyncd:running`，`swssconfig` 依赖 `orchagent:running`，各 `mgrd` 又多以 `swssconfig:exited` 或 `orchagent:running` 为前置。这种显式依赖正是「容器化控制面」的工程落地（原理见 06-13 ｜ 参数见 04-07）。

第二组概念是「Redis 数据库分层」。配置与状态分布在 `CONFIG_DB`、`APPL_DB`、`ASIC_DB`、`STATE_DB`、`COUNTERS_DB` 等多个逻辑库，另有 `CHASSIS_APP_DB` 等按场景扩展的库。它们的语义分工是：`CONFIG_DB` 存用户与开机配置，`APPL_DB` 存经校验后的期望状态，`ASIC_DB` 存待编程的 ASIC 对象，`STATE_DB` 存运行时状态，`COUNTERS_DB` 存计数器。关键纪律是：这些库的编号不是源码常量，而是由运行时配置文件决定——`sonic-py-swsssdk-master/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 从 `/var/run/redis/sonic-db/database_config.json` 读取 `DATABASES`，`get_dbid(db_name)` 取其中 `id` 字段，`dockers/docker-database/database_config.json.j2` 与 `database_global.json.j2` 是生成该配置的模板。因此本套资料一律不写死「某库是某号」，编号须对照 `SonicDBConfig` 与实际版本核验（字段见 05-03 ｜ 参数见 04-04 ｜ 原理见 06-02）。

第三组概念是「SAI 与 syncd」。SAI 定义与芯片无关的统一 API；本快照里 `sonic-sairedis-master/SAI/` 是空目录，实际头文件与厂商实现均需对照实际版本核验，可核验的是 `meta/`（元数据，约八十个文件）、`vslib/`（虚拟 SAI）、`lib/`、`saidump/`、`saiplayer/` 等目录。`syncd` 位于 `sonic-sairedis-master/syncd/`：`main.cpp` 只把 `main()` 转交 `syncd_main()`，`syncd_main.cpp` 承担启动，`Syncd.cpp`、`SaiSwitch.cpp`、`SaiObj.cpp`、`VendorSai.cpp`、`SaiDiscovery.cpp`、`FlexCounter.cpp` 等分别处理主循环、交换对象、对象表示、厂商 API 装载、能力发现与计数器。厂商 SAI 实现多为闭源且不在本仓库，`orchagent` 只经 `ASIC_DB` 与 SAI 属性同 `syncd` 交互，从不直接驱动芯片（字段见 05-04 ｜ 字段见 05-06 ｜ 原理见 06-05 ｜ 模块见 07-04）。

### 4. 关键流程与调用链

把容器、库、进程与芯片串成一条链，得到本册的核心总图；全链路分层关系见图 01-03-01。

必须强调这是一条异步流水线。`sonic-utilities-master/config/main.py` 经 `ConfigDBConnector` 把配置写入 `CONFIG_DB` 后即返回，后续三段由各自进程独立驱动；`config` 返回成功不代表硬件已下发。判读状态要按库逐段查：`CONFIG_DB` 有没有表项、`APPL_DB` 有没有期望状态、`ASIC_DB` 有没有对象、`STATE_DB` 与 `show` 输出是否反映运行时结果。管理面还有并行入口：`sonic-mgmt-common-master/models/yang/` 的模型经 `cvl/` 校验、`translib/` 转换，最终同样落到 `CONFIG_DB`；`generic_config_updater/` 提供补丁式更新；gNMI 与 telemetry 分别由 `dockers/docker-sonic-gnmi/`、`dockers/docker-sonic-telemetry/` 承载（原理见 06-14 ｜ 模块见 07-07）。

启动链与构建链是这幅图的另外两条支撑线。启动链是：`Makefile` → `Makefile.work` → `sonic-slave-*/` 构建容器 → `build_image.sh` 读取 `onie-image.conf`（其中 `ONIE_IMAGE_PART_SIZE`、`TARGET_MACHINE`、`OUTPUT_ONIE_IMAGE` 等变量决定产物形态）→ ONIE 安装包 → 设备安装 → `files/image_config/` 开机写库 → `supervisord.conf.j2` 按 `dependent_startup_wait_for` 拉起 `portsyncd`、`orchagent`、`swssconfig` 与各 `mgrd`。构建必须在 slave 容器内并经 ONIE 安装器完成，不能在普通主机裸 `make` 出可安装镜像（原理见 06-13 ｜ 参数见 04-01 ｜ 模块见 07-11）。`warmrestart/`、多 ASIC 命名空间与 `chassisorch.cpp`、`config-chassisdb/` 相关能力受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持。

### 5. 配置/命令/代码实例

本节只给理解架构所需的最小片段：一段真实的进程编排模板、一条状态读取命令及其输出判读，以及一条按库核对的补充命令。完整启动参数见 04-07、完整命令全集见 04-05、完整 schema 见 04-02，本册不重列。

先看 `dockers/docker-orchagent/supervisord.conf.common.j2` 中 `orchagent` 段的模板原文，它说明控制面进程如何被按依赖拉起；内容节选自该文件，含 Jinja 变量，具体渲染值需对照实际版本核验。

```text
[program:orchagent]
command=/usr/bin/orchagent.sh
priority={{ swss_priority_base + 4 }}
autostart=false
autorestart=false
stdout_logfile=NONE
stdout_syslog=true
stderr_logfile=NONE
stderr_syslog=true
stdout_capture_maxbytes=1MB
dependent_startup=true
dependent_startup_wait_for={{ orchagent_dependent_startup_wait_for }}
```

这段模板里 `command` 指向启动脚本而非直接调用二进制，`autostart=false` 配合 `dependent_startup=true` 表示交给依赖调度，`dependent_startup_wait_for` 在通用模板中被赋为 `portsyncd:running`（fabric ASIC 场景会改为 `rsyslogd:running`），`priority` 是带 `swss_priority_base` 偏移的 Jinja 表达式。它印证了 2 节所说的「显式依赖 + 容器化编排」，也解释了为什么数据库容器必须先起、为什么 `orchagent` 之前要有 `portsyncd`。日志走 syslog 而非文件，是容器环境下排障要看 syslog 与容器日志、而不是找本地 `stdout_logfile` 的原因（参数见 04-07 ｜ 原理见 06-13）。

再看一次端口状态读取，用来演示「`show` 只读状态」以及异步流水线下的判读边界。

```bash
show interfaces status
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
Interface   Lanes        Speed   MTU   Alias        Oper  Admin
Ethernet1   25,26,27,28  200000  9100  Eth200GE0/1  up    up
Ethernet2   29,30,31,32  200000  9100  Eth200GE0/2  down  up
Ethernet3   41,42,43,44  200000  9100  Eth200GE0/3  up    up
```

逐行判读如下。第一行是列头：`Interface` 为端口名，`Lanes` 为物理通道编号，`Speed` 为速率，`MTU` 为最大传输单元，`Alias` 为面板别名，`Oper` 为操作状态，`Admin` 为管理状态；列名与顺序随版本变化，需对照实际版本核验。第二行 `Ethernet1` 的 `Oper` 与 `Admin` 同为 `up`，`Lanes` 为四个通道、`Speed` 为 `200000`、`MTU` 为 `9100`，与 `device/tencent/x86_64-tencent_tcs8400-r0/config_db.TCS8400-24CC8CD.json` 中 `PORT` 表 `Ethernet1` 的 `lanes`、`speed`、`admin_status`、`mtu` 字段可对应，是配置与状态一致的正常特征；表名与字段需对照实际版本核验、逐字段含义见 05 册。第三行 `Ethernet2` 的 `Admin` 为 `up` 但 `Oper` 为 `down`，是「管理上已启用、物理或链路未起」的典型异常特征，应先查 `CONFIG_DB` 的 `PORT` 表是否写入、再查 `APPL_DB` 是否生成期望状态、再查 `STATE_DB` 与 `ASIC_DB`，而不是直接判定芯片故障。第四行 `Ethernet3` 恢复正常，说明同批端口状态可以不同，逐端口判读比看汇总更可靠。整个输出来自 `sonic-utilities-master/show/main.py`，该模块经 `swsscommon` 的连接器读取各库，属于「CLI 只读状态、不编程 ASIC」；`swsscommon` 不在本快照、需对照实际版本核验。更重要的是，`Oper` 为 `up` 只代表运行时状态，不能反推「某次 `config` 命令已使硬件下发」，仍须按库逐段核对（原理见 06-01 ｜ 排障见 08-03）。输出块已注明示例输出与版本核验要求，取值不得当作真实设备数据引用。

### 6. 注意事项、陷阱与最佳实践

第一类是定位陷阱。必须把 SONiC 写成白盒交换机 NOS：控制面在 `orchagent`、`syncd`、各 `*mgrd`、`bgpd`、`teamd` 等容器进程，数据面在 ASIC，控制面经 SAI 下发；除 `platform/vs/` 虚拟交换机外不做软件转发，不得写成通用软件路由器或主机协议栈。第二类是把 `orchagent` 写成直接操作硬件：它只消费 `APPL_DB`、生成对象写入 `ASIC_DB`，经 SAI 属性同 `syncd` 交互，不读写寄存器、不直接驱动芯片。第三类是把 CLI 写成编程 ASIC：`sonic-utilities/` 的 `show` / `config` 主要读写 `CONFIG_DB` 与各 DB，配置生效依赖流水线（原理见 06-01 ｜ 原理见 06-05）。

第四类是数据库与状态陷阱。Redis 分层包含 `CONFIG_DB`、`APPL_DB`、`ASIC_DB`、`STATE_DB`、`COUNTERS_DB` 等多个逻辑库，DB 编号与表字段须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 与实际版本核验，禁止写死编号、禁止凭印象补表名与字段；不确定的一律写「需对照实际版本核验」并给出 `cfgmgr/`、`orchagent/`、`src/swsssdk/` 等可定位目录。第五类是把配置当同步生效：`config` 命令返回成功不代表硬件已下发，判读状态要查 `APPL_DB`、`ASIC_DB`、`STATE_DB` 与 `show` 输出，按「配置库有表项、期望库有意图、对象库有对象、状态库有结果」的顺序逐段推进，不得写「配置即时生效」。

第六类是仓库与 SAI 边界陷阱。本快照是主仓加七个子仓的多仓结构，不是单一仓库；FRR / FRRouting 源码、Linux 内核、各厂商 SAI 实现、`sonic-swss-common` 均不在本快照，涉及这些部分一律写「不在本快照，需对照实际版本核验」。尤其 `sonic-sairedis/SAI/` 在本快照是空目录，不得据它编造头文件、属性与版本；`meta/`、`vslib/` 才是可核验的元数据与虚拟 SAI 所在。`dockers/` 下没有 `docker-syncd` 目录，`syncd` 主体在 `sonic-sairedis/syncd/`，`platform/vs/` 下的 `docker-syncd-vs` 属虚拟交换机专用，二者不可混写。

第七类是构建、平台与性能陷阱。镜像构建依赖 `sonic-slave-*/` 容器与 ONIE 安装器（`onie-image.conf`、`installer/`），`make` 在 slave 容器内运行并产出 ONIE 安装包，普通主机裸 `make` 得不到可安装镜像；`warmrestart/`、多 ASIC 命名空间与 chassis 支持（如 `chassisorch.cpp`、`files/image_config/config-chassisdb/`）受平台与版本限制，不同 HWSKU 与版本能力不同，一律写「受平台与版本限制，需对照实际版本核验」。收敛时间、配置下发时延、转发吞吐、表项容量等一切数字标注「需在目标机型实测」，不给绝对值、不给跨机型通用数字（基准方法见 08-01 ｜ 调优见 08-02）。

最佳实践归纳为四条：其一，排障先按图 01-03-01 定位「哪一段」，再按容器查进程状态与日志，最后按库查表项，避免一上来怀疑硬件；其二，读代码时把路径写成 `upstream_src/<子仓>/<子仓>-master/` 下的相对路径，并同时给出对应函数或调用链；其三，跨册引用统一用（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx），其中 `xx` 为具体篇号，本篇涉及的库编号写「参数见 04-04」、`Orch` 字段写「字段见 05-05」、SAI 对象写「字段见 05-04」、`syncd` 机制写「原理见 06-05」、容器模块写「模块见 07-02」，不在总览册展开字段表与 API 全集；其四，对快照内无法核实的内容宁可标注「需对照实际版本核验」并给出目录，也不补值。

### 7. 小结与延伸阅读

本篇把 01-01 的分层与 01-02 的分工落成了可定位的架构：`dockers/` 定义容器族，`supervisord.conf.j2` 与 `supervisord.conf.common.j2` 定义进程依赖与启动顺序，`CONFIG_DB` / `APPL_DB` / `ASIC_DB` / `STATE_DB` / `COUNTERS_DB` 构成状态分层，`sonic-swss/orchagent/` 负责从意图到对象的翻译，`sonic-sairedis/syncd/` 负责从对象经 SAI 到芯片的编程，`files/image_config/` 与 `src/sonic-config-engine/` 负责开机配置，`sonic-utilities/` 与 `sonic-mgmt-common/` 负责管理面。图 01-03-01 与容器清单表、库语义表是后续各册反复回查的索引；三条纪律贯穿全篇——异步流水线不等于即时生效、CLI 不等于编程 ASIC、DB 编号不等于源码常量。

## 01-04 版本基准、许可、社区与资料使用约定

### 1. 背景与动机

一套技术资料最容易被写坏的，往往不是某个技术细节，而是「这套资料到底对应什么代码、凭什么可信、遇到查不到的东西怎么办」。SONiC 尤其如此：它是几十个仓库组成的生态，各子仓有各自的许可文件、维护者清单与 CI 配置，构建产物又随平台、HWSKU 与构建日期变化；如果资料里随手抄一个版本号、写死一个 Redis 库编号、或把某个快照里根本没有的文件当成事实，后续所有引用都会连锁失真。01-04 的动机就是把这些「元规则」一次性讲清楚，让 01 册乃至全九册在版本、许可、事实核验与交叉引用上有一致口径。

从本快照能直接看到这种复杂性。`sonic-buildimage-master/` 顶层同时存在 `LICENSE`、`MAINTAINERS`、`README.md`、`README.buildsystem.md`、`ThirdPartyLicenses.txt`、`azure-pipelines.yml`；`sonic-swss-master/` 有 `configure.ac`、`Makefile.am`、`azure-pipelines.yml`、`LICENSE`、`MAINTAINERS`；`sonic-sairedis-master/` 有 `configure.ac`、`Makefile.am`、`LICENSE`、`azure-pipelines.yml`，却没有 `MAINTAINERS`；`sonic-mgmt-common-master/` 用 `Makefile`、`go.mod`、`go.sum` 组织 Go 代码，连 `README.md` 都没有。也就是说，「各子仓都有 LICENSE、MAINTAINERS、CI」是错的，正确的写法必须基于逐仓核验。本篇第 3 节会给出一张真实核验的存在性矩阵（模块见 07-01 ｜ 模块见 07-13）。

第三个动机是「去重与交叉引用」的纪律。全九册共 65 篇，若 CONFIG_DB 表名、命令全集、结构体字段在每册都重列一遍，资料会既臃肿又互相矛盾。总纲第 2 节与 SPEC 第 4 节为此定了唯一权威源：04 管参数与命令，05 管结构体字段，06 管机制与调用链，07 管模块能力，08 管运维组合，其余册一律交叉引用。01 作为总览册尤其要克制——机制写「原理见 06-xx」、参数写「参数见 04-xx」、字段写「字段见 05-xx」，禁止展开结构体字段表与 API 全集。本篇把这些约定连同「需对照实际版本核验」「不在本快照，需对照实际版本核验」的写法固化下来（原理见 06-01 ｜ 模块见 07-01）。

### 2. 核心概念

第一个概念是「版本基准」。本套资料统一写「上游 master 快照（2026-11 抓取）」，禁止编造具体版本号与 Redis DB 编号。各子仓 `configure.ac`、`Makefile`、`setup.py`、`azure-pipelines.yml` 里的版本字样只作核验依据，不得抄进正文当作本套版本号；需要说明版本来源时写「具体版本号以对应构建文件为准，需对照实际版本核验」。这样处理的原因是：SONiC 镜像的版本字符串由构建过程生成，`onie-image.conf` 里的 `ONIEIMAGE_VERSION`、`OUTPUT_ONIE_IMAGE=target/sonic-<machine>.bin` 与 `build_image.sh` 读取的变量共同决定产物名，任何手写数字都与具体构建脱节。

第二个概念是「许可与第三方声明」。八个仓的 `xxx-master/` 根均可核验到 `LICENSE`，`sonic-buildimage-master/`、`sonic-swss-master/`、`sonic-platform-common-master/`、`sonic-py-swsssdk-master/` 还可核验到 `ThirdPartyLicenses.txt`。`LICENSE` 是各子仓的许可文本，`ThirdPartyLicenses.txt` 汇总第三方组件声明；具体许可名称、条款与第三方清单内容需对照实际文件核验，本册不转述条款、不推断授权范围。涉及合规判断时，正确做法是回到对应子仓 `LICENSE` 原文，而不是引用本套资料的转述。

第三个概念是「社区治理与 CI」。`MAINTAINERS` 是维护者清单，但并非八仓都有，实测仅 `sonic-buildimage`、`sonic-swss`、`sonic-py-swsssdk`、`sonic-dbsyncd` 四个仓根可核验到该文件；治理结构、评审流程与贡献规范的具体内容需对照实际版本核验。`azure-pipelines.yml` 在八个仓根均可核验到，是 CI 入口；`sonic-swss-master/` 还有 `azure-pipelines-dash.yml`、`lgtm.yml`，`sonic-mgmt-common-master/` 有 `renovate.json` 与 `patches/`，`sonic-buildimage-master/` 有 `pytest.ini`、`tests/`、`azure-pipelines.yml`、`Makefile.cache`。CI 产物的具体形态与流水线阶段需对照实际版本核验，调试构建不作生产基准，性能数字需在目标机型实测（模块见 07-12 ｜ 模块见 07-13）。

第四个概念是「事实核验与标注写法」。唯一事实锚点是 `upstream_src/` 下八个子仓的 `xxx-master/` 仓库根；凡 SPEC 第 0.1 节未列出的路径、或无法用 Read / Grep 核实的文件，一律不写进正文。不确定的字段名、结构体成员、函数签名、CONFIG_DB 表名与字段名、命令行选项、Redis DB 编号、容器名、模块文件名，一律写「需对照实际版本核验」并给出可定位目录；涉及 FRR / Linux 内核 / 厂商 SAI 实现 / `sonic-swss-common` 的内容写「不在本快照，需对照实际版本核验」；性能、容量、收敛、时延、吞吐类结论写「需在目标机型实测」；`warmrestart/`、多 ASIC 与 chassis 能力写「受平台与版本限制，需对照实际版本核验」。这四类标注不是免责套话，而是资料可复现的前提。

### 5. 配置/命令/代码实例

本节给两组实例：一组是逐仓核验治理文件的真实命令与输出，用来演示「事实核验」怎么做；一组是交叉引用与标注写法的示例文本。命令与选项需对照实际版本核验，完整命令见 04-05，完整构建变量见 04-01。

先看逐仓核验命令，它只依赖标准 shell，可在 `upstream_src/` 所在目录执行。

```bash
for r in sonic-buildimage sonic-swss sonic-sairedis sonic-utilities sonic-mgmt-common sonic-platform-common sonic-py-swsssdk sonic-dbsyncd; do
  p="upstream_src/$r/$r-master"
  printf "%s " "$r"
  for f in LICENSE MAINTAINERS azure-pipelines.yml; do
    if [ -e "$p/$f" ]; then printf "%s=Y " "$f"; else printf "%s=N " "$f"; fi
  done
  echo
done
```

```text
示例输出，具体格式需对照实际版本核验（下列 Y/N 为本次快照核验结果）
sonic-buildimage LICENSE=Y MAINTAINERS=Y azure-pipelines.yml=Y
sonic-swss LICENSE=Y MAINTAINERS=Y azure-pipelines.yml=Y
sonic-sairedis LICENSE=Y MAINTAINERS=N azure-pipelines.yml=Y
sonic-utilities LICENSE=Y MAINTAINERS=N azure-pipelines.yml=Y
sonic-mgmt-common LICENSE=Y MAINTAINERS=N azure-pipelines.yml=Y
sonic-platform-common LICENSE=Y MAINTAINERS=N azure-pipelines.yml=Y
sonic-py-swsssdk LICENSE=Y MAINTAINERS=Y azure-pipelines.yml=Y
sonic-dbsyncd LICENSE=Y MAINTAINERS=Y azure-pipelines.yml=Y
```

逐行判读如下。第一行命令本体：外层 `for` 遍历八个子仓名，`p` 拼接出 `upstream_src/<子仓>/<子仓>-master/` 真实仓库根，内层 `for` 依次检查 `LICENSE`、`MAINTAINERS`、`azure-pipelines.yml` 三个文件是否存在，`-e` 为真打印 `=Y`、否则 `=N`，`printf` 与 `echo` 控制每行一个仓；路径拼接方式正是 SPEC 第 0.1 节要求的归档层写法，命令本身不含任何版本号或 DB 编号。输出第二段首行 `sonic-buildimage` 三个文件全为 `Y`，说明主仓许可、维护者清单与 CI 齐备，是正常特征；第二行 `sonic-swss` 同样三项齐备。第三行 `sonic-sairedis` 的 `MAINTAINERS=N` 是「该仓根无维护者清单」的实测结果，并非文件损坏，撰写时不能据此推断治理缺失，只能写「需对照实际版本核验」；第四、五、六行的 `sonic-utilities`、`sonic-mgmt-common`、`sonic-platform-common` 同样 `MAINTAINERS=N`。第七、八行 `sonic-py-swsssdk`、`sonic-dbsyncd` 恢复 `MAINTAINERS=Y`。八行的 `LICENSE=Y` 与 `azure-pipelines.yml=Y` 全部一致，说明「许可文件与 CI 配置在八仓齐备」这一结论可核验，而「MAINTAINERS 在八仓齐备」不可核验。输出块已注明示例输出与版本核验要求，`Y/N` 结果随版本变化，不得跨版本套用；若某行出现 `LICENSE=N`，则属于需要复查快照完整性的异常特征（模块见 07-13 ｜ 排障见 08-06）。

再看标注与交叉引用写法的示例文本，它展示不确定处该如何成文而不是留空。

```text
DB 编号须对照 sonic-py-swsssdk/src/swsssdk/dbconnector.py 的 SonicDBConfig 核验，需对照实际版本核验。
CONFIG_DB 表名与字段需对照 src/sonic-config-engine/ 与实际版本核验，字段见 05-02。
FRR / FRRouting 源码不在本快照，需对照实际版本核验；见 dockers/docker-fpm-frr/。
厂商 SAI 实现不在本快照，需对照实际版本核验；见 sonic-sairedis/meta/。
收敛时间与转发吞吐需在目标机型实测，基准方法见 08-01。
warm reboot 受平台与版本限制，需对照实际版本核验；见 warmrestart/。
```

这几行不是占位，而是可直接用于正文的成文句式：第一行针对 DB 编号，第二行针对表名与字段并给出具体交叉引用「字段见 05-02」，第三、四行针对不在本快照的内容并给出可定位目录，第五行针对性能结论，第六行针对受平台限制的能力。它们把「不确定」转化为「有路径、有去向、有核验要求」的可复现表述，正是本套资料禁止占位写法之后的标准替代（原理见 06-01 ｜ 模块见 07-05）。

### 6. 注意事项、陷阱与最佳实践

第一类是版本陷阱。禁止编造具体版本号与 Redis DB 编号，版本基准统一写「上游 master 快照（2026-11 抓取）」；各子仓 `configure.ac`、`Makefile`、`setup.py`、`azure-pipelines.yml`、`onie-image.conf` 里的版本字样只作核验依据，不得抄进正文当作本套版本号；需要说明版本来源时写「具体版本号以对应构建文件为准，需对照实际版本核验」。第二类是许可陷阱：只能陈述可核验到 `LICENSE` 与 `ThirdPartyLicenses.txt`，不得转述条款、推断授权范围或把第三方清单内容写成本快照事实，具体条款需对照实际文件核验。

第三类是治理与 CI 陷阱：`MAINTAINERS` 仅四个仓可核验到，`README.md` 在 `sonic-mgmt-common-master/` 缺失，不得写「各子仓都有 MAINTAINERS」；`azure-pipelines.yml` 八仓齐备，但流水线阶段、产物形态与测试框架名称需对照实际版本核验；调试构建不作生产基准，性能数字需在目标机型实测。第四类是事实纪律陷阱：唯一事实锚点是 `upstream_src/` 下八个子仓的 `xxx-master/` 根，凡未列出的路径或无法用 Read / Grep 核实的文件一律不写进正文；不确定的字段名、结构体成员、函数签名、CONFIG_DB 表名与字段名、命令行选项、Redis DB 编号、容器名、模块文件名一律写「需对照实际版本核验」并给出 `cfgmgr/`、`orchagent/`、`src/swsssdk/`、`models/yang/`、`config/` 等可定位目录。

第五类是能力边界陷阱，九条须逐条守住且不得写反：SONiC 是白盒交换机 NOS、控制面容器化、数据面在 ASIC、经 SAI 下发，除 `platform/vs/` 外不做软件转发；它是多仓结构，FRR / Linux 内核 / 厂商 SAI 实现 / `sonic-swss-common` 不在本快照；Redis 分层含 `CONFIG_DB` 到 `COUNTERS_DB` 等多个逻辑库且编号须核验；配置链路是 `CONFIG_DB` → `APPL_DB` → `ASIC_DB` → SAI 的异步流水线，`config` 返回成功不代表硬件已下发；SAI 是抽象接口，`orchagent` 不直接操作硬件；CLI 只读写 DB；`warmrestart/`、多 ASIC 与 chassis 受平台与版本限制；镜像构建依赖 `sonic-slave-*/` 容器与 ONIE 安装器，普通主机裸 `make` 得不到可安装镜像；性能、容量、收敛、时延、吞吐一律标注「需在目标机型实测」、不给绝对值（基准方法见 08-01 ｜ 调优见 08-02）。

第六类是写作与去重陷阱。严禁一切占位写法：不得以省略号或省略字代替正文、不得把内容推给别处、不得让小节只留标题、代码块内不得出现裸省略行或空白占位；代码块开始行必须带语言标注、结束行必须是独占一行的裸结束标记；表格单元格内出现半角 `|` 必须写成转义形式、单元格不超过九十字符；图块节点文字单行宽度不超过三十八、节点数不超过十、边数不超过十二、每个节点至少连一条边、图号与正文引用一致。去重铁律不得破坏：06 / 07 / 08 无完整字段表、04 无原理与字段、05 无机制流程、交叉引用写法统一（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）。

最佳实践归纳为四条：其一，写任何字段、表名、函数、命令参数前先 Read / Grep 对应源码，核实不了就按四类标注成文；其二，引用他册内容一律用具体篇号的交叉引用，不在总览册展开字段表与 API 全集；其三，命令、配置与输出按「前置检查、执行、验证输出、清理」闭环写，示例输出一律注明「示例输出，具体格式需对照实际版本核验」并给逐行判读；其四，遇到快照外的系统（FRR、内核、厂商 SAI、Cumulus、DENT 等）一律写「不在本快照，需对照实际版本核验」，绝不补值。

### 7. 小结与延伸阅读

本篇把全册的元规则固定下来：版本基准是「上游 master 快照（2026-11 抓取）」，不写绝对版本号与 Redis DB 编号；事实锚点是八个子仓的 `xxx-master/` 仓库根，`LICENSE` 与 `azure-pipelines.yml` 八仓齐备、`MAINTAINERS` 仅四仓可核验，治理矩阵见第 3 节表；DB 编号来自运行时 `database_config.json` 而非源码常量，须对照 `SonicDBConfig` 核验；不确定处按「需对照实际版本核验」「不在本快照，需对照实际版本核验」「需在目标机型实测」「受平台与版本限制」四类成文；编号、去重与交叉引用统一为（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx），其中 `xx` 为具体篇号。图 01-04-01 给出四册唯一权威源与引用方向，是阅读其余各册的导航。

01 册至此收束：01-01 立定位与能力矩阵，01-02 明分工与选型，01-03 串架构与调用链，01-04 定版本、许可、社区与资料约定。四篇共同反复强调的是同一组边界——容器化控制面加 ASIC 数据面、多仓结构、异步配置流水线、SAI 抽象、CLI 只读写 DB、warm reboot 受平台限制、镜像构建依赖 sonic-slave、一切性能数字需实测。后续阅读可按目标分流：编译与构建走 02 全册，部署与接入走 03 全册，参数与命令随查走 04 全册，字段随查走 05 全册，机制原理走 06 全册，模块能力走 07 全册，运维、基准与排障走 08 全册。

最后给出本册通用约定清单，供后续各册对照：源码路径一律相对各子仓 `xxx-master/` 根并给出可定位目录；示例输出一律注明「示例输出，具体格式需对照实际版本核验」并附逐行中文判读；每张图有引导句、图号与正文引用一致；每个表格有引导句、单元格内半角 `|` 转义；每个代码块带语言标注且结束行为裸结束标记；交叉引用使用具体篇号；能力边界九条不得写反；性能、容量、收敛、时延、吞吐类结论一律标注「需在目标机型实测」。版本基准始终为「上游 master 快照（2026-11 抓取）」，具体版本号以对应构建文件为准、需对照实际版本核验。
