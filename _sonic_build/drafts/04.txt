# SONiC 技术资料 · 04 参数与 API 手册

## 04-01 构建变量与 Makefile 参数全集

### 1. 本篇定位与覆盖范围

本篇是 04 册参数与 API 手册的构建变量分册，承担一个明确而狭窄的职责：把 SONiC 镜像构建过程中出现的可调变量集中列成一张可反查的字典。它是全册关于「构建变量叫什么、取什么值、默认是什么、配错会怎样」的唯一权威源，其余各册涉及构建参数时只给本场景的最小必要调用并写「完整变量见 04-01」，不再重列。这样安排是为了避免同一个 `PLATFORM` 或 `BLDENV` 在构建册、部署册、运维册里各写一遍、彼此不一致。这里只回答「参数是什么」，不回答「构建流水线如何运作」「容器按什么顺序拉起」——后者属于机制范畴，统一写「原理见 06-13」「模块见 07-01」「镜像模块见 07-11」；字段级结构（如 `SonicDBConfig`、`FieldValueTuple`）属于 05 册，本篇不展开，统一写「字段见 05-03」。

覆盖范围以事实锚点为准，全部路径相对 `upstream_src/sonic-buildimage/sonic-buildimage-master/` 仓库根。具体包括四类文件族。第一类是顶层总控：`Makefile` 用 `%::` 通配目标把构建转交 `Makefile.work`，并按 `BLDENV` 进入不同的 `sonic-slave-*/` 构建容器，这里定义了 `NOJESSIE`、`NOBOOKWORM`、`NOTRIXIE` 等发行版开关与 `Q`、`MAKE_WITH_RETRY` 等总控变量。第二类是 `Makefile.work`，它的文件头注释列出构建者可以显式传入的参数，如 `PLATFORM`、`BUILD_NUMBER`、`SONIC_BUILD_JOBS`、`KEEP_SLAVE_ON`、`SONIC_DPKG_CACHE_METHOD` 等。第三类是 `slave.mk`，它承载路径与默认值体系，如 `SRC_PATH`、`TARGET_PATH`、`BLDENV`、`CONFIGURED_ARCH`、`IMAGE_DISTRO`、`SLAVE_DIR`。第四类是镜像装配配置 `onie-image.conf` 与 `rules/` 下的 `.mk`、`.dep` 规则，前者定义分区大小、产物文件名，后者把变量落实为镜像目标。

需要在一开始就划清三条边界，否则读者容易把本篇当成构建教程。其一，本篇不提供从零构建的操作步骤，那是 02-03 实战型章节的任务；这里只列变量，操作闭环写「完整流程见 02-02、02-03」。其二，本篇不写死任何绝对版本号。所有变量的默认值均标注来源，能在本快照源码核实的直接给真实值并注明所在文件，无法核实的写「需对照实际版本核验」，绝不凭印象补值——例如各子仓的精确版本字符串由构建过程生成，不在本篇给数字。其三，本篇涉及的平台、ASIC、chassis 相关开关（如多 ASIC 命名空间、warm reboot 相关构建项）一律写「受平台与版本限制，需对照实际版本核验」，不宣称全平台无条件支持。版本基准统一为「上游 master 快照（2026-11 抓取）」。

本篇的组织方式如下：第 2 节给出全参数索引与分族参数表，每行按「参数/键 → 取值 → 默认值 → 作用 → 误配后果」五列填写；第 3 节按变量族逐项详解，解释默认值来源与相互制约关系；第 4 节给两组可核验的命令与输出判读示例；第 5 节给一张按使用频率排序的速查表；第 6 节说明版本差异；第 7 节汇总常见误用与调试入口。读者若要顺着变量看它如何驱动容器启动，转 06-13 与 07-02；若要按变量改平台适配，转 02-04 与 07-10。交叉引用统一写作「字段见 05-xx ｜ 原理见 06-xx ｜ 模块见 07-xx」。

### 3. 逐项详解

**发行版开关族。** 顶层 `Makefile` 的前八行定义了六个 `NO*` 开关，语义统一：取值 0 表示「不跳过」，即启用对应发行版构建；取值 1 表示跳过。默认值里，`NOJESSIE`、`NOSTRETCH`、`NOBUSTER`、`NOBULLSEYE` 为 1，说明这四种老旧发行版默认关闭；`NOBOOKWORM` 与 `NOTRIXIE` 为 0，说明 bookworm 与 trixie 默认开启。这组开关通过 `ifeq` 条件块转换为 `BUILD_JESSIE`、`BUILD_TRIXIE` 等内部标记，再由 `%::` 通配目标决定向 `Makefile.work` 传入哪个目标与 `BLDENV`。这里有一个容易忽略的约束：`BAZEL_MIN_READINESS` 与发行版强绑定，快照中的错误提示明确写着 Bazel 组件只支持 trixie，一旦在非 trixie 构建启用，会拼接出 `BAZEL_NON_TRIXIE_BUILDS` 并触发 `$(error ...)` 直接中止。因此调发行版开关时必须同时核对 Bazel 相关变量，不能孤立修改。构建链如何按这些开关进入不同容器，属于机制内容，写「原理见 06-13」。

**总控与路径族。** `Makefile` 把任意目标 `%::` 转交给 `Makefile.work`，并拼上 `MAKE_WITH_RETRY`，其默认值为 `./scripts/run_with_retry $(MAKE)`，作用是在构建失败时按脚本策略重试；若该脚本缺失或被改动，所有目标的失败重试都会失效。`slave.mk` 定义了一组以路径为贵的变量：`SRC_PATH=src`、`RULES_PATH=rules`、`TARGET_PATH=target`、`DOCKERS_PATH=dockers`，它们共同决定源码、规则、产物与容器定义的位置。这组变量一般不直接改，但排障时必须能读懂，因为产物路径 `target/` 下的 deb、files、phony、python-debs、python-wheels 等子目录都由 `TARGET_PATH` 与 `BLDENV` 二次拼接而成。`PROJECT_ROOT` 取当前工作目录，`BUILD_WORKDIR=/sonic` 是容器内工作目录，二者不一致是「宿主路径与容器路径混淆」类问题的常见根因。`SLAVE_DIR` 默认 `sonic-slave-$(BLDENV)`，与 `BLDENV` 联动——`BLDENV` 的默认来源是 `lsb_release -cs` 的输出，这意味着在不同发行版的宿主上执行同一份 `Makefile` 可能选中不同 slave 容器，构建结果自然不同。

**平台与架构族。** `CONFIGURED_PLATFORM` 在 `slave.mk` 中优先读取 `.platform` 文件，文件不存在时回落到 `generic`；`PLATFORM` 若由命令行显式给出，则顶层 `Makefile` 用 `$(if $(PLATFORM),$(PLATFORM),$(CONFIGURED_PLATFORM))` 决定 `PLATFORM_PATH`。这套「命令行参数优先于文件、文件优先于默认值」的优先级链，是判断「为什么我改了 .platform 却没生效」的关键：多半是命令行仍带着 `PLATFORM=`。架构侧 `CONFIGURED_ARCH` 默认 `amd64`，并派生出 `DOCKER_BASE_ARCH`；当取 `armhf` 时改为 `arm32v7`、取 `arm64` 时改为 `arm64v8`，跨平台场景还会设置 `DOCKER_DEFAULT_PLATFORM` 与 `MULTIARCH_QEMU_ENVIRON`、`CROSS_BUILD_ENVIRON`。`IMAGE_DISTRO` 默认 `trixie`，`ENABLE_PY2_MODULES` 按 `BLDENV` 是否属于 bullseye、bookworm、trixie 决定取 n 或 y——这些联动关系说明，构建变量不是彼此孤立的开关，而是一张有优先级的约束网。平台适配的具体目录结构写「模块见 07-10」。

**Makefile.work 参数族。** `Makefile.work` 文件头以注释形式列出构建者可显式传入的参数，本篇表 04-01-C 已逐项收录。这批参数的特点是「多数无显式默认值或默认值需对照实际版本核验」，因为它们往往由 `rules/config` 或各 `.mk` 文件在具体上下文中赋值，不能脱离版本空谈默认值。以 `KEEP_SLAVE_ON` 为例，注释明确它把 slave 容器保留在构建结束后，但 `rm=true` 仍在，用户退出会话后容器会被删除；`SOURCE_FOLDER` 只在 `KEEP_SLAVE_ON=yes` 时有效，二者必须配对。又如 `ENABLE_TRANSLIB_WRITE`、`ENABLE_NATIVE_WRITE`、`ENABLE_DIALOUT` 默认未设置，取 `y` 才打开对应管理面写或外连能力，生产构建默认不应开启——这属于安全加固边界，具体写法见 08-05。缓存类三个变量 `SONIC_DPKG_CACHE_METHOD`、`SONIC_DPKG_CACHE_SOURCE`、`SONIC_DPKG_CACHE_METHOD_OVERRIDE` 共同决定 Debian 包从何处获取，误配的直接后果是拉到与快照不匹配的版本，破坏可复现性。并发数 `SONIC_BUILD_JOBS` 与 `VS_PREPARE_MEM` 影响构建资源：后者默认 `yes`，会在 vs 构建前清缓存压缩内存，设为 `no` 虽省去准备动作，却可能在大构建时内存不足。

**镜像装配变量族。** `onie-image.conf` 用 shell 的参数展开语法给变量赋默认值，形如 `: ${ONIE_IMAGE_PART_SIZE:=32768}`，含义是「若变量未设置或为空，则赋 32768」。这解释了为什么表 04-01-D 中这些值可以确认为真实默认值：它们直接写在文件里，而非运行时计算。分区相关变量里，`ONIE_IMAGE_PART_SIZE=32768` 即 32GB，`DOCKER_RAMFS_SIZE=3500M`，`RAW_IMAGE_DISK_SIZE=1700`（MB），`KVM_IMAGE_DISK_SIZE=16`（GB）；这些数字决定了产物能否装下完整系统，属于构建期约束而非性能结论，不需标注「需在目标机型实测」，但改动前须评估目标硬件的容量。产物名变量统一以 `OUTPUT_` 开头，其中 `OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin`、`OUTPUT_RAW_IMAGE`、`OUTPUT_KVM_IMAGE`、`OUTPUT_ABOOT_IMAGE`、`OUTPUT_DSC_IMAGE` 分别对应 ONIE、raw、KVM、aboot、DSC 五种形态；`TARGET_MACHINE` 默认为 `generic`，因此默认产物名形如 `target/sonic-generic.bin`。装配脚本如何把这些变量落实为 ONIE 安装包属于镜像模块职责，写「模块见 07-11」。

### 4. 典型示例

本节给两组示例。第一组用只读命令核验顶层发行版开关与路径变量的当前取值，第二组核验 onie-image.conf 的产物名与分区变量。所有输出块均注明「示例输出，具体格式需对照实际版本核验」，取值不得当作真实版本号引用。

第一组：在仓库根执行，核验 Makefile 中发行版开关的默认赋值。

```bash
grep -nE '^(NOJESSIE|NOSTRETCH|NOBUSTER|NOBULLSEYE|NOBOOKWORM|NOTRIXIE)\s*\?=' Makefile
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为示意，需与实际快照比对）
3:NOJESSIE ?= 1
4:NOSTRETCH ?= 1
5:NOBUSTER ?= 1
6:NOBULLSEYE ?= 1
7:NOBOOKWORM ?= 0
8:NOTRIXIE ?= 0
```

逐行判读如下。`grep` 用 `-n` 显示行号、`-E` 启用扩展正则，模式 `^(NOJESSIE|...)\s*\?=` 只匹配以这六个变量名开头、后接 `?=` 赋值符的行，`?=` 表示「仅当变量未定义时才赋值」，正是默认值语义。输出六行行号 3 到 8，与源码第 3 至第 8 行一一对应，说明命中的是顶层默认赋值而非条件块内的二次赋值。前四行 `NOJESSIE` 到 `NOBULLSEYE` 均为 1，表示四种老旧发行版默认跳过；第五行 `NOBOOKWORM ?= 0` 与第六行 `NOTRIXIE ?= 0` 表示 bookworm 与 trixie 默认启用，这与当前主线以 trixie 为目标的事实一致。若某行取值与这里不符，通常说明快照版本不同或有人改过默认值，应回到源码核对而非照抄本表。需要特别提醒：`?=` 允许命令行覆盖，所以运行时 `make NOJESSIE=0` 会让该变量变为 0，静态 grep 看到的默认值不代表最终生效值，这一点在排障时极易被忽略。发行版开关如何决定进入哪个 slave 容器属于机制范畴，写「原理见 06-13」。

第二组：核验产物名与镜像分区变量。

```bash
grep -nE '^(ONIE_IMAGE_PART_SIZE|TARGET_MACHINE|OUTPUT_ONIE_IMAGE|DOCKER_RAMFS_SIZE)' onie-image.conf
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为示意，需与实际快照比对）
7:: ${ONIE_IMAGE_PART_SIZE:=32768}
11:: ${TARGET_MACHINE:=generic}
31:DOCKER_RAMFS_SIZE=3500M
34:OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin
```

逐行判读如下。第一条命中 `ONIE_IMAGE_PART_SIZE:=32768`，其中 `:=` 的参数展开写法含义是「未设置或为空则赋 32768」，单位 MB，即默认 32GB 分区，与文件注释一致。第二条 `TARGET_MACHINE:=generic` 说明目标机器名默认 generic，它会进入后续产物文件名。第三条 `DOCKER_RAMFS_SIZE=3500M` 是普通赋值，直接给 docker ramfs 空间 3500M；注意这条没有用参数展开语法，意味着若脚本预先设置了同名变量，这里会覆盖它。第四条 `OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin` 展示产物名由 `TARGET_MACHINE` 插值而成，默认展开为 `target/sonic-generic.bin`；若 build 时传入 `TARGET_MACHINE=x86_64-generic-r0`，产物名随之改变。这组变量直接决定产物落点与容量，改动应同步检查 `installer/` 下的安装脚本是否按同样规则取名，安装链路属于镜像模块写「模块见 07-11」。以上输出均需对照实际版本核验，不得据示例数字下结论。

### 6. 版本差异

构建变量是随版本变动最频繁的一类参数，因此版本差异必须谨慎表述。本快照为「上游 master 快照（2026-11 抓取）」，表 04-01-A 与 D 中的默认值来自本快照可直接核实的源码行，读者在其它版本上应重新核对，不能直接套用。已知的变动趋势有三类，均不写成绝对结论。

第一类是发行版开关的演进。NO* 开关集合会随 SONiC 支持的 Debian 发行版增减而调整，本快照中 bookworm 与 trixie 默认开启、其余关闭，但更早或更晚的版本可能把默认值整体平移，例如把 NOBOOKWORM 翻转为 1、把更新发行版设为 0。`BAZEL_MIN_READINESS` 是本快照新出现 readiness 语义的体现，注释明确 Bazel 组件只支持 trixie，这类约束在旧版本中可能根本不存在。凡涉及发行版组合，一律写「受平台与版本限制，需对照实际版本核验」。

第二类是 Makefile.work 参数集合的增减。表 04-01-C 收录的参数来自文件头注释，本快照包含 gNMI 写开关、telemetry dialout、`GNMI_REDIS_POOL_SIZE` 等较新的管理面参数；这些参数在老版本可能缺失，在新版本可能继续增加。由于它们多数默认值由 `rules/config` 或各 `.mk` 在具体上下文赋值，脱离具体版本给出默认值没有意义，故本表统一标注「需对照实际版本核验」。读者若需要某参数的准确默认值，应回到对应版本的 `Makefile.work` 与 `rules/` 目录核实。

第三类是镜像装配变量的容量与命名演进。`ONIE_IMAGE_PART_SIZE=32768`、各类 `OUTPUT_*` 产物名在本快照可核实，但不同组织常在此处做本地化改动，例如调整分区大小、改为带日期的产物名、增加 DSC 或 aboot 之外的形态。因此这些值只能作为「本快照默认」使用，落到具体产品必须重新确认。跨版本比对时，建议固定一个最小变量集（发行版开关、平台、架构、产物名）做差异基线，其余变量按需扩展，对比命令与判读方法见 08 册基准章节。

### 7. 常见误用与调试

误用一：把静态默认值当成运行时生效值。表里的默认值来自源码赋值语句，但大量变量允许命令行覆盖。`?=` 与 `:=` 的参数展开都只在「未设置」时生效，一旦 build 命令显式传入，默认值不再起作用。典型症状是「我改了 .platform，产物平台却没变」，根因往往是命令行仍带着 `PLATFORM=`。调试入口是用只读命令核验运行时取值，第 4 节第一组示例演示了基本方法；更完整的构建日志分析写「原理见 06-13」。

误用二：把发行版开关当成彼此独立。六个 NO* 开关通过条件块联动，且受 `BAZEL_MIN_READINESS` 约束。把所有开关都设为 1 会导致没有任何目标执行；在非 trixie 构建启用 Bazel 会直接触发 `$(error ...)` 中止。调试时应先确认至少启用一个发行版，再单独核对 Bazel 相关变量，错误信息会明确指出需要哪些组合。

误用三：混淆宿主路径与容器路径。`PROJECT_ROOT` 是宿主当前目录，`BUILD_WORKDIR=/sonic` 是容器内工作目录，二者通过 slave 容器的挂载映射关联。排障时把宿主上的相对路径直接套到容器内、或反过来，是常见错误。`SOURCE_FOLDER` 只在 `KEEP_SLAVE_ON=yes` 时才挂载为 `/var/用户名/src`，单独设置不会生效，这类配对约束必须先满足前置条件。

误用四：把构建期容量数字当成性能结论。分区大小、ramfs 空间、镜像磁盘大小是构建与安装期的容量约束，不是转发性能或表项容量，不需标注「需在目标机型实测」；相反，收敛时间、下发时延、吞吐类数字一律标注「需在目标机型实测」，基准方法见 08-01。把两类数字混为一谈会得出错误结论。

误用五：误开管理面与调试开关。`ENABLE_TRANSLIB_WRITE`、`ENABLE_NATIVE_WRITE`、`ENABLE_DIALOUT`、`INSTALL_DEBUG_TOOLS` 默认未设置或按需设置，生产构建误开会扩大管理面写权限、引入外连或增大镜像与暴露面。这类开关的启用属于安全决策，须结合 08-05 的加固要求评估，不能因为是布尔开关就随手打开。

调试的通用顺序是：先用只读命令确认变量当前值，再对照本篇全表确认默认值来源与误配后果，然后判断是「静态默认值不符预期」还是「被命令行或环境覆盖」，最后才考虑修改。所有修改都应记录变更前后取值与产物路径，保证可复现。涉及机制的问题写「原理见 06-13」，涉及模块实现的问题写「模块见 07-01」「镜像模块见 07-11」，字段级结构写「字段见 05-03」，不在本篇展开。

## 04-02 CONFIG_DB 表与 schema 参数全集（一）：PORT、VLAN、INTERFACE

### 1. 本篇定位与覆盖范围

本篇是 04 册 schema 字典的第一分册，专门收录 `CONFIG_DB` 中与二层端口、VLAN 与三层接口直接相关的表：PORT、VLAN、VLAN_MEMBER、INTERFACE，以及与之紧邻的 MGMT_PORT。它的职责是回答「这几张表的键怎么拼、有哪些字段、字段取什么值、不填或填错会怎样」，并作为全册关于这些表 schema 的唯一权威源。其它册一旦涉及 PORT 或 VLAN 的表结构，只写「表结构与字段见 04-02」，不再重列字段清单。本篇不回答「这些字段如何被翻译成 ASIC 对象」——那是配置下发链路，写「原理见 06-06」；也不回答「字段在内存里如何表示成 `FieldValueTuple`」「`ConfigDBConnector` 如何封装读写」——那是结构字段范畴，写「字段见 05-02」；更不收录 `show` / `config` 的完整命令清单，那属于命令手册范围，本篇只在示例里给最小必要调用。

先说清 schema 的真实来源，这是本快照里最容易被写错的一点。按规范提示去 `files/image_config/config_db/` 找 schema 目录，在本快照中并不存在；schema 实际分散在三处。第一处是 `sonic-swss/doc/swss-schema.md`，其「Configuration DB schema」小节用 ABNF 语法给出 PORT、MGMT_PORT、NEIGH、WARM_RESTART、VXLAN_TUNNEL 等表的键与字段约束，这是最直接的字段来源。第二处是 `sonic-mgmt-common` 中的 YANG 模型：`cvl/testdata/schema/sonic-vlan.yang` 定义 VLAN 与 VLAN_MEMBER 的字段与取值范围，`models/yang/sonic/sonic-interface.yang` 定义 INTERFACE 的 `portname`、`ip_prefix`、`vrf-name`。第三处是字段常量与真实配置样例：`sonic-swss/orchagent/port/portschema.h` 以宏定义形式列出 PORT 表字段名（如 `PORT_SPEED`、`PORT_FEC`、`PORT_MTU`、`PORT_LEARN_MODE`），而 `device/<vendor>/<hwsku>/config_db*.json` 给出具体机型的填充值。撰写时凡能在这三处核实的写真实值，核实不了的写「需对照实际版本核验」，并给出可定位目录。

覆盖范围限定在「配置侧」。需要特别区分 `CONFIG_DB` 的 INTERFACE 表与 `APPL_DB` 的 INTF_TABLE：前者是用户与开机配置写入的三层地址意图，后者是 mgrd 翻译后的期望状态，字段集合并不相同——`scope`、`family`、`if_mtu` 出现在 APPL_DB 侧而非 CONFIG_DB 的 INTERFACE 表。本篇只列 CONFIG_DB 侧字段，下游表写「字段见 05-02」「原理见 06-06」。同理，PORT 表的 `oper_status`、`state` 属于 STATE_DB 的运行时状态，不在本篇的 CONFIG_DB 参数表内。版本基准统一为「上游 master 快照（2026-11 抓取）」，不写绝对版本号，也不写死任何 Redis DB 编号——库编号来自运行时配置，须按 `SonicDBConfig` 核验，写「字段见 05-03」。

本篇结构如下：第 2 节给表索引与三类表的全参数表，每行按「参数/键 → 取值 → 默认值 → 作用 → 误配后果」五列填写；第 3 节逐族详解字段约束与相互制约；第 4 节给配置片段与库查询两组示例及逐行判读；第 5 节给按场景组织的速查表；第 6 节说明版本差异；第 7 节汇总常见误用与调试顺序。读者若要顺着字段追到下发链路，转 06-06；若要按机型理解 lanes 与 speed 的来源，转 02-04 与「模块见 07-10」。交叉引用统一写作「字段见 05-xx ｜ 原理见 06-xx ｜ 模块见 07-xx」，本篇不自我引用。

### 2. 索引与全参数表

先给表索引。下表列出本篇覆盖的五张表、键的拼法、用途与 schema 来源；键中的竖线是 CONFIG_DB 的分隔符，在表格单元格里按规范转义书写。

### 3. 逐项详解

**PORT 表的字段约束与相互制约。** PORT 表描述的是交换 ASIC 管理的物理二层端口，管理口与逻辑口不在其中。`ifname` 作为键，必须在 PORT、INTF、VLAN、LAG 几类表之间保持唯一，这是因为下游按接口名索引，重名会让翻译层无法确定对象。字段中最容易出错的是 `speed`、`lanes`、`fec`、`interface_type` 这一组：它们描述的是同一条物理链路的不同侧面，必须与机型端口配置和实际光模块一致。例如 `speed` 以 Mbps 为单位，`200000` 表示 200G；`lanes` 给出承载这条端口的物理通道编号列表，来自 `device/<vendor>/<hwsku>/` 下的端口配置；`fec` 取 none、rs、fc、auto 之一，须与对端一致，否则即使链路 up 也会有高误码；`interface_type` 的枚举值在 portschema.h 中可核实，涵盖 cr、sr、lr、kr 系列与 caui、gmii、sfi、xfi、xgmii 等。默认值方面，本快照的 ABNF schema 只给出取值格式，未给统一默认值，真实默认依机型与版本而变，故全表标注「需对照实际版本核验」。`learn_mode`、`role`、`pt_interface_id`、`pt_timestamp_template` 属于较新或平台相关字段，前者决定 MAC 学习落到丢弃、硬件、CPU 陷落或通知等模式，后者多用于 chassis 与路径追踪，能力受平台与版本限制，写「受平台与版本限制，需对照实际版本核验」。

**PORT 字段的运行时对照。** 需要再次强调配置值与运行时值的分离：`admin_status` 在 CONFIG_DB 里是用户意图，`oper_status` 与 `state` 则出现在 STATE_DB，反映 ASIC 编程后的实际状态。把一个写成另一个、或期待写入 `admin_status` 后 `oper_status` 立刻变化，都是对异步流水线的误读——配置返回成功不代表硬件已下发。判断端口是否真正生效，要按 CONFIG_DB、APPL_DB、ASIC_DB、STATE_DB 的顺序逐段核对，完整诊断树写「原理见 06-01」「原理见 06-06」。字段在结构层面的载体写「字段见 05-02」，端口相关 Orch 的派生结构写「字段见 05-07」。

**VLAN 与 VLAN_MEMBER 的搭配规则。** VLAN 表以 `Vlan<vlanid>` 命名，YANG 中有一条 must 约束强制名称必须等于字符串 Vlan 拼接 vlanid，例如编号 100 对应名称 Vlan100；`vlanid` 为必填 uint16，范围 1 至 4095，越界会触发名为 vlanid-invalid 的校验错误并带相应 error-app-tag。MTU 为 uint32，范围 1312 至 9216，越界触发 mtu-invalid。`members` 是成员端口列表，引用的是端口名，若引用了不存在的端口，成员关系无法落地。VLAN_MEMBER 表以复合键 `Vlan<vlanid>` 加 `ifname` 定位单条成员关系，关键在于 `tagging_mode`：它取 tagged、untagged、priority_tagged 三种，YANG 明示默认值为 tagged。这一默认值在排障时尤其重要——「我以为没配就是 untagged」是常见误解，实际未显式指定时会按 tagged 处理，与对端 untagged 配置相遇就会造成标签错乱。VLAN 与成员如何被下发给 ASIC，写「原理见 06-06」。

**INTERFACE 表与下游表的区别。** INTERFACE 表承载三层地址意图：`portname` 可以是物理端口、VLAN 接口、PortChannel 或 Loopback，`ip_prefix` 是 IPv4 或 IPv6 前缀，`vrf-name` 把接口绑定到指定 VRF。在 YANG 里它由两条 list 分工表达，一条以 portname 为键描述接口与 VRF，一条以 portname 加 ip_prefix 为复合键描述地址。最需要澄清的区别是：本表的字段集合与 APPL_DB 的 INTF_TABLE 不同。后者由 mgrd 翻译产生，包含 `scope`（global 或 local）、`family`（IPv4 或 IPv6）、`if_mtu` 等字段，这些字段不出现在 CONFIG_DB 的 INTERFACE 表里；反过来，CONFIG_DB 侧的 `vrf-name` 也不等于下游表结构。把两层字段互相套用，会导致配置写到正确的库却用错字段名。下游字段写「字段见 05-02」，翻译链路写「原理见 06-06」。`vrf-name` 指向的 VRF 须先存在，其状态在 STATE_DB 的 VRF_TABLE 中体现，属于运行时观测范畴，不在本篇参数表内。

### 4. 典型示例

本节给两组示例。第一组是一段 `config_db.json` 配置片段，覆盖 PORT、VLAN、VLAN_MEMBER、INTERFACE 四表，字段名与键拼法按本快照 schema 书写；第二组用逻辑库名查询 PORT 表项并逐行判读。所有输出块均注明「示例输出，具体格式需对照实际版本核验」，取值不得当作真实设备数据引用。

第一组：配置片段。

```json
{
    "PORT": {
        "Ethernet1": {
            "alias": "Eth200GE0/1",
            "lanes": "25,26,27,28",
            "speed": "200000",
            "admin_status": "up",
            "mtu": "9100",
            "fec": "rs"
        }
    },
    "VLAN": {
        "Vlan100": {
            "vlanid": "100",
            "mtu": "9100",
            "admin_status": "up"
        }
    },
    "VLAN_MEMBER": {
        "Vlan100|Ethernet1": {
            "tagging_mode": "untagged"
        }
    },
    "INTERFACE": {
        "Vlan100|10.0.0.1/24": {},
        "Ethernet1|2001:db8::1/64": {}
    }
}
```

这段配置说明四件事。其一，PORT 表以 `Ethernet1` 为键，`lanes` 把四个物理通道绑成一条 200G 端口，`speed` 用 Mbps 表示，`fec` 取 `rs`，这些值须与机型端口配置及光模块一致，字段名可在 `sonic-swss/orchagent/port/portschema.h` 核实。其二，VLAN 表以 `Vlan100` 命名，`vlanid` 为 `100`，符合「名称等于 Vlan 拼接 vlanid」的约束，`mtu` 为 `9100`，落在 1312 至 9216 范围内。其三，VLAN_MEMBER 的键 `Vlan100|Ethernet1` 是复合键，把端口加入 VLAN，这里显式写 `untagged`，避免落到默认 `tagged` 造成与对端不一致——这正是第 3 节强调的默认值陷阱。其四，INTERFACE 表用 `portname|ip_prefix` 作键，IPv4 与 IPv6 地址各一条，空对象表示除地址外不附加其它字段；若需绑定 VRF，应另有以 portname 为键、携带 `vrf-name` 的表项。字段名与取值均需对照实际版本核验，逐字段结构写「字段见 05-02」。

第二组：用逻辑库名读取 PORT 表项，避免写死任何 Redis DB 编号。

```bash
sonic-db-cli CONFIG_DB HGETALL "PORT|Ethernet1"
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
"admin_status" "up"
"alias" "Eth200GE0/1"
"fec" "rs"
"lanes" "25,26,27,28"
"mtu" "9100"
"speed" "200000"
```

逐行判读如下。命令本体使用 `sonic-db-cli`，第一个参数是逻辑库名 `CONFIG_DB` 而非数字编号，这一点至关重要：库编号来自运行时 `database_config.json`，须按 `SonicDBConfig` 核验，禁止写死「某库是某号」，写「字段见 05-03」。`HGETALL` 读取键 `PORT|Ethernet1` 的全部字段，竖线是 CONFIG_DB 的键分隔符。输出六行均为「字段名 值」对：`admin_status` 为 `up`，是用户写入的管理意图，不等于操作状态已 up；`alias` 为面板别名，供 LLDP/SNMP 使用；`fec` 为 `rs`，须与对端一致；`lanes` 为四个通道，与 200G 速率匹配；`mtu` 为 `9100`；`speed` 为 `200000`，即 200000 Mbps。判读的关键不是逐字确认这些值，而是确认「配置库里确实有这条表项且字段齐全」——若这里缺字段或为空，问题在配置落地阶段；若这里正确但端口仍异常，则问题在下游 APPL_DB、ASIC_DB 或 STATE_DB，应按链路逐段核对，写「原理见 06-01」「原理见 06-06」。输出的字段顺序在不同版本可能不同，取值仅为格式示意，需对照实际版本核验。

### 5. 速查表

下表按排障场景组织，给出「想确认什么 → 看哪张表的哪个字段 → 该字段的约束」的快速映射。它不重复第 2 节全表，只提供定位入口。

| 场景 | 关注表与字段 | 约束或默认 |
|---|---|---|
| 端口起不来 | PORT 的 speed、lanes、fec、interface_type | 互相匹配且与机型一致，默认需核验 |
| 端口名或别名冲突 | PORT 的 ifname、alias | 跨 PORT/INTF/VLAN/LAG 唯一 |
| MAC 学习行为异常 | PORT 的 learn_mode | 六类枚举，取值影响转发学习 |
| VLAN 编号报错 | VLAN 的 vlanid、name | 1 至 4095，名称须等于 Vlan 拼接编号 |
| VLAN MTU 报错 | VLAN 的 mtu | 1312 至 9216 |
| VLAN 标签错乱 | VLAN_MEMBER 的 tagging_mode | 默认 tagged，需与对端一致 |
| IP 地址未生效 | INTERFACE 的 portname、ip_prefix | 接口须存在，前缀格式合法 |
| 接口 VRF 绑定失败 | INTERFACE 的 vrf-name | 指向的 VRF 须先存在 |
| 配置有但状态不对 | 对照 STATE_DB 的 oper_status、state | 不属 CONFIG_DB，按链路核对 |
| 读库时编号不明 | 逻辑库名而非数字编号 | 编号按 SonicDBConfig 核验 |

速查表的使用原则是「先定位、再回全表」：由此找到表名与字段后，回到表 04-02-A 至 C 核对取值、默认值与误配后果。凡涉及「配置正确但状态不对」的情形，一律转状态与链路章节，不在本表硬找答案。

### 6. 版本差异

schema 是随版本持续演进的内容，本篇所有表都应视为「本快照默认」。变动趋势有四类，均不写成绝对结论。

第一类是 schema 来源本身在演进。本快照中 PORT 的 ABNF 定义位于 `sonic-swss/doc/swss-schema.md`，字段常量位于 `orchagent/port/portschema.h`，VLAN 与 INTERFACE 的约束位于 `sonic-mgmt-common` 的 YANG 模型。不同版本里，这些定义可能迁移位置、拆分文件或改变严格程度；尤其 `sonic-swss-common` 不在本快照，字段级结构须写「不在本快照，需对照实际版本核验」。因此每到一个新版本，应先重新定位这几处 schema 文件，再逐字段比对，不能拿本篇的字段清单直接套用。

第二类是字段集合的增减。PORT 表在本快照除基础字段外，还包含 `learn_mode`、`role`、`pt_interface_id`、`pt_timestamp_template`、`media_type`、`fast_linkup`、`macsec` 等较新或平台相关字段；老版本可能没有，新版本可能继续增加。凡是平台相关字段，能力受平台与版本限制，写「受平台与版本限制，需对照实际版本核验」。VLAN 侧 `priority_tagged` 等 tagging 取值、INTERFACE 侧 `vrf-name` 的语义，也可能随 YANG 模型调整，须回到对应版本的 YANG 文件核实。

第三类是取值范围与默认值的调整。本快照可核实的范围包括 VLAN 的 vlanid 1 至 4095、mtu 1312 至 9216，以及 tagging_mode 默认 tagged。这些数字来自本快照的 YANG 文件，其它版本可能改变范围或默认，尤其是 mtu 上下界与 tagging 默认值，改动会直接影响配置校验结果。凡是本表标注「需对照实际版本核验」的默认值，都不应被理解为「没有默认值」或「默认空」，而是「本快照未给出可核实的统一默认」。

第四类是机型配置样例的差异。`device/<vendor>/<hwsku>/config_db*.json` 是具体机型的填充值，`lanes`、`speed`、`alias` 都与硬件强相关，不同 HWSKU 之间不可互换。把 A 机型的配置片段整段复制到 B 机型，是升级与批量部署中的高频错误，后果通常是端口无法映射硬件。机型适配的具体目录结构写「模块见 07-10」。跨版本比对时，建议固定一个最小字段集（端口键、speed、lanes、mtu、VLAN 编号与 tagging、接口地址）作为基线，其余字段按需扩展。

### 7. 常见误用与调试

误用一：键拼法与唯一性错误。CONFIG_DB 用竖线作分隔符，PORT 键为 `PORT|ifname`，VLAN_MEMBER 为 `VLAN_MEMBER|Vlan<vlanid>|ifname`，INTERFACE 为 `INTERFACE|portname|ip_prefix`。把分隔符写错、漏写复合键的一段、或让 ifname 在 PORT、INTF、VLAN、LAG 间重名，都会让下游无法定位对象。调试时先用只读命令确认键的实际拼法，再核对字段是否随键落在同一条表项上。

误用二：VLAN 名称与编号不一致。YANG 的 must 约束要求名称等于 Vlan 拼接 vlanid，写 `Vlan100` 却把 `vlanid` 填成 200 会触发校验错误；vlanid 取 0 或超过 4095 触发 vlanid-invalid；mtu 越出 1312 至 9216 触发 mtu-invalid。这类错误会在配置校验阶段被拦下，表现为配置未写入，而非硬件异常。

误用三：tagging_mode 默认值误判。未显式指定时按 YANG 默认的 tagged 处理，若对端按 untagged 接入，就会出现 VLAN 标签错乱、二层互通失败。正确做法是显式写出 tagging_mode 并与对端核对，而不是依赖默认。

误用四：混淆 CONFIG_DB 的 INTERFACE 与 APPL_DB 的 INTF_TABLE。前者是用户配置，字段为 portname、ip_prefix、vrf-name；后者是 mgrd 翻译后的期望状态，含 scope、family、if_mtu。把下游字段写进配置表、或期待在配置表里看到 oper 状态，都是层次错配。字段级区别写「字段见 05-02」，翻译链路写「原理见 06-06」。

误用五：把配置返回成功当成硬件已下发。PORT、VLAN、INTERFACE 都是异步流水线的输入，写入 CONFIG_DB 只是第一步。判断生效要按 CONFIG_DB、APPL_DB、ASIC_DB、STATE_DB 顺序逐段核对，再结合 `show` 输出，不能因命令返回成功就断言转发已生效，写「原理见 06-01」。

误用六：写死 Redis DB 编号或跨机型复制配置。库编号来自运行时配置，须按 `SonicDBConfig` 核验，写「字段见 05-03」；`lanes`、`speed`、`alias` 与机型强相关，跨 HWSKU 复制配置会导致端口无法映射硬件，写「模块见 07-10」。

调试的通用顺序是：先用逻辑库名读 CONFIG_DB，确认表项存在、键拼法正确、字段齐全；再核对本篇全表确认取值与默认；若配置正确但状态不对，转 APPL_DB、ASIC_DB、STATE_DB 逐段核对；若字段语义或结构有疑问，转 05 册；若追下发链路，转 06-06。所有结论均以「上游 master 快照（2026-11 抓取）」为基准，不确定的表名、字段、取值范围一律标注「需对照实际版本核验」并给出可定位目录，不凭印象补值。

## 04-03 CONFIG_DB 表与 schema 参数全集（二）：BGP、ACL、ROUTE、COPP

### 1. 本篇定位与覆盖范围

本篇是 04 册参数与 API 手册的第 3 篇，承接 04-02 对 PORT、VLAN、INTERFACE 三类基础表的整理，继续把 CONFIG_DB 中与控制面协议、安全策略和限速保护相关的四组表收进同一份可随查的参数全集。与 02 册讲构建、03 册讲部署、06 册讲流水线原理不同，本篇只回答一个很窄的问题：一张 BGP、ACL、ROUTE 或 COPP 相关的表，在配置里到底以什么表名出现、键怎么拼、有哪些字段、每个字段可以取什么值、默认值是什么、配错了会在哪一环出问题。凡涉及这些表如何被订阅、如何被翻译成 ASIC 对象、如何在 syncd 侧经 SAI 编程的内容，一律不在本篇展开，分别写「原理见 06-07 ｜ 原理见 06-08 ｜ 模块见 07-03 ｜ 模块见 07-08」；凡涉及结构体逐字段的内容，写「字段见 05-02 ｜ 字段见 05-07」。这种克制正是 04 册作为参数唯一权威源的写作纪律：把清单列全列准，把机制留给机制册，把字段留给字段册，不在一处把所有内容重复铺开。

覆盖范围上，本篇按四组表展开。第一组是 BGP 相关表，核心是 BGP_NEIGHBOR 与 DEVICE_METADATA 中的自治域字段，它们由 `dockers/docker-fpm-frr/` 容器内的协议进程消费，FRR 协议源码不在本快照、需对照实际版本核验；本篇只记录配置侧的键与字段，不讲协议状态机。第二组是 ACL 相关表，即 ACL_TABLE 与 ACL_RULE，其字段可从 `sonic-mgmt-common-master/models/yang/sonic/sonic-acl.yang` 逐项核验，是本篇中证据最完整的一组，枚举值与取值范围都来自该模型。第三组是 ROUTE 相关表，需要特别说明 CONFIG_DB 侧的静态路由表与 APPL_DB、ASIC_DB 侧的路由表不是同一张表，不能混写，本篇以 `src/sonic-config-engine/minigraph.py` 中可核实的 STATIC_ROUTE 为配置侧代表。第四组是 COPP 相关表，即 COPP_GROUP 与 COPP_TRAP，其模板与默认值可在 `files/image_config/copp/copp_cfg.j2` 中核实，是一份带 Jinja 条件渲染的配置模板而非固定值。四组表的字段名、取值枚举与默认值凡能在本快照内核实的都给出路径，核实不了的写「需对照实际版本核验」，绝不凭印象补值。

### 3. 逐项详解

**BGP 组。** BGP_NEIGHBOR 是 CONFIG_DB 中以对端 IP 地址为键的表，样例配置生成函数 `generate_t1_sample_config()` 在 `src/sonic-config-engine/config_samples.py` 中一次性给出一个邻居所需的七个字段：`asn` 是对端自治域号，`name` 是对端名字，`local_addr` 是建立会话使用的本端地址，`nhopself` 与 `rrclient` 是取 0 或 1 的开关，`holdtime` 与 `keepalive` 是以字符串保存的秒数，该函数里分别给了 180 与 60。同一文件还把本端自治域写在 `DEVICE_METADATA` 的 `localhost` 键下，字段名为 `bgp_asn`，样例值 65100。需要强调，这些数字是样例生成器为了构造 t1 拓扑写下的示意值，不是协议强制默认，真正生效值必须回到实际设备的配置与对应版本核验。还要注意 CONFIG_DB 的表键与字段都以字符串保存，所以 `holdtime` 写的是字符串形式的「180」而不是整数，这一点在手工编辑 JSON 时极易写错类型；协议进程如何读取这些字段并建立会话属于「原理见 06-07」，容器如何承载协议进程属于「模块见 07-08」，本篇只保证键与字段的清单完整。

**ACL 组。** ACL_TABLE 以 `aclname` 为键，`sonic-acl.yang` 给出了五个字段：`policy_desc` 是一到二百五十五字符的描述；`stage` 是枚举，只能取 INGRESS 或 EGRESS，决定规则在入方向还是出方向生效；`type` 也是枚举，可取 MIRROR、MIRRORV6、L3、L3V6，决定这张表按二层镜像还是三层路由语义去匹配；`ports` 是对 PORT 表端口名的 leaf-list，列出规则要绑定的端口。ACL_RULE 以 `aclname` 加 `rulename` 为复合键，字段明显更多：`PRIORITY` 是一到六万五千五百三十五的无符号短整型，决定同一表内规则的先后；`PACKET_ACTION` 与 `IP_TYPE` 都标为 mandatory，前者可取 FORWARD、DROP、REDIRECT，后者可取 ANY、IP、IPV4、IPV4ANY、NON_IPV4、IPV6ANY、NON_IPV6；`IP_PROTOCOL` 取值范围被限定在若干协议号，`ETHER_TYPE` 用模式匹配限定在若干以太类型字符串；地址与四层端口字段按 IPv4、IPv6 分成 `SRC_IP`、`DST_IP`、`SRC_IPV6`、`DST_IPV6`、`L4_SRC_PORT`、`L4_SRC_PORT_RANGE`、`L4_DST_PORT`、`L4_DST_PORT_RANGE` 等，并通过 when 条件与 `IP_TYPE` 联动；此外还有 `TCP_FLAGS` 与 `DSCP`。这套约束说明 ACL 不是「随便写几个字段就下发」，字段之间存在强相关，模型校验会在配置进入 DB 前拦住不合法组合，校验环节属于「原理见 06-03」，规则如何进 ASIC 属于「原理见 06-08」，派生结构逐字段见「字段见 05-07」。

**ROUTE 组。** 配置侧的静态路由以 `src/sonic-config-engine/minigraph.py` 渲染出的 STATIC_ROUTE 为代表：该函数把目的前缀作为键，每个前缀是一个字典，至少包含 `nexthop`、`ifname` 与 `advertise`，在启用 BFD 的分支里还会写入 `bfd` 为真。其中 `nexthop` 与 `ifname` 都是把多个值用逗号拼成的字符串，分别对应下一跳地址列表与出接口列表，前缀键、下一跳与出接口三者必须一起写对，缺一项就无法形成可用路由；`advertise` 控制是否把这条静态路由向动态协议重分发，配错会改变路由通告行为。必须把这张配置表与运行态路由表严格区分：`orchagent/routeorch.cpp` 中出现的是 APP_ROUTE_TABLE_NAME 与 STATE_ROUTE_TABLE_NAME 这类运行态对象，前者在 APPL_DB、后者在 STATE_DB，它们由协议同步进程或编排核心写入，字段与配置侧不同。把两者混为一谈是本篇最常见的事实错误，正确的链路是配置侧意图经校验后进入期望态、再经编排生成 ASIC 对象，见「原理见 06-07」，路由族编排结构的逐字段说明见「字段见 05-07」，编排核心模块见「模块见 07-03」。

**COPP 组。** `files/image_config/copp/copp_cfg.j2` 是一份 Jinja 模板，渲染后得到 COPP_GROUP 与 COPP_TRAP 两张表。COPP_GROUP 以组名为键，模板里可见 `default`、`queue4_group1`、`queue4_group2`、`queue4_group3`、`queue3_group1`、`queue1_group1`、`queue1_group2`、`queue1_group3`、`queue2_group1` 等组；每组共有字段包括 `queue`、`meter_type`、`mode`、`cir`、`cbs`、`red_action`，部分组还有 `trap_action`、`trap_priority`，queue2_group1 额外带 `genetlink_name` 与 `genetlink_mcgrp_name`。`default` 组的模板值是 `queue` 为 0、`meter_type` 为 packets、`mode` 为 sr_tcm、`cir` 与 `cbs` 均为 600、`red_action` 为 drop；其他组的速率值差异较大，且 queue4_group3 与 queue3_group1 会依据设备类型是否为管理型渲染出不同的 `cir` 与 `cbs`，queue3_group1 的 `cbs` 还跟端口数量经表达式计算相关。COPP_TRAP 以 trap 名为键，字段是 `trap_ids`、`trap_group` 与可选的 `always_enabled`，模板中 bgp 陷阱的 `trap_ids` 为 bgp 与 bgpv6、`trap_group` 指向 queue4_group1，`lacp`、`arp`、`udld`、`ip2me`、`neighbor_miss` 等则带 `always_enabled` 为真。这里要特别说明：`trap_action` 的 trap 与 copy 代表两种上送语义，`cir` 与 `cbs` 决定限速曲线，配得过低会丢协议报文、配得过高会放大控制面压力；这些字段如何经编排落到 ASIC 属于「原理见 06-08」，外围容器与模板的模块归属见「模块见 07-09」。

逐行判读如下。第一段是 BGP_NEIGHBOR 的哈希：`asn` 为 65200，与片段中写入值一致，须与对端实际自治域核对，不一致则会话无法建立；`holdtime` 为 180、`keepalive` 为 60，符合样例量级，且都以字符串返回，印证了配置库值皆为字符串的纪律；`local_addr` 为 10.0.0.1 是会话源地址，若该地址不在本机接口上，协议会停在 Idle；`name` 仅用于识别；`nhopself` 与 `rrclient` 均为 0，表示未启用自身下一跳与路由反射客户端角色。第二段是 ACL_TABLE：`stage` 为 INGRESS 表明规则作用于入方向，`type` 为 L3 表明按三层语义匹配，`ports` 以逗号串返回 Ethernet1 与 Ethernet2，说明绑定了两个端口，若实际流量从其他端口进入则不会被这条表匹配。第三段 `KEYS` 只返回一条 STATIC_ROUTE 键，前缀为 20.0.0.0/24，与片段一致，说明静态路由已写入；但注意这只证明配置库有表项，不代表路由已进入期望态或 ASIC。第四段 COPP_TRAP 的 `trap_ids` 为 bgp 与 bgpv6、`trap_group` 指向 queue4_group1，与模板一致，说明 BGP 报文会被纳入该限速组；若这里写成不存在的组名，陷阱会失去限速保护。整体判读的核心纪律是：redis-cli 查到表项只证明「配置已写入」，不等于协议会话已建立、ACL 已下发、路由已编程或 COPP 已生效，后续必须按「原理见 06-01 ｜ 原理见 06-07 ｜ 原理见 06-08」逐段核对，运行态检查与案例见「排障见 08-03 ｜ 排障见 08-04」。输出块已注明示例输出与版本核验要求，所有取值不得当作真实设备数据引用。

### 5. 速查表

下表把四组表的「现象 → 优先核对 → 可能原因 → 交叉引用」压成一行一条的形式，便于在排障现场快速反查。表中不重复第 2 节的字段清单，只给核对入口；机制与案例仍按交叉引用跳转到相应册。

| 现象 | 优先核对的表或字段 | 可能原因 | 交叉引用 |
|---|---|---|---|
| BGP 会话停在 Idle | BGP_NEIGHBOR 的 local_addr 与 asn | 源地址不可达或对端 AS 不符 | 原理见 06-07 |
| BGP 反复翻滚 | holdtime 与 keepalive | 计时比例不当或链路不稳 | 原理见 06-07 |
| ACL 规则未命中 | ACL_TABLE 的 stage、type、ports | 方向、类型或绑定端口错 | 原理见 06-08 |
| ACL 配置被拒 | PRIORITY 或 IP_TYPE | 越界、漏必填或与地址字段不匹配 | 原理见 06-03 |
| 静态路由不生效 | STATIC_ROUTE 的 nexthop 与 ifname | 下一跳不可达或出接口不存在 | 原理见 06-07 |
| 运行态无路由 | APPL_DB 路由表是否有期望态 | 配置未进期望态或被同步进程丢弃 | 原理见 06-07 |
| 协议报文被丢 | COPP_GROUP 的 cir 与 cbs | 限速阈值过低 | 原理见 06-08 |
| 陷阱未受保护 | COPP_TRAP 的 trap_group | 指向不存在的组或 trap_ids 名不符 | 原理见 06-08 |

速查表的使用方式是「先定位现象、再核对配置、最后跳机制」。以「静态路由不生效」为例，第一步只在 CONFIG_DB 里确认 STATIC_ROUTE 的 nexthop 与 ifname 写对，第二步按「原理见 06-07」看期望态有没有生成，第三步才看 ASIC 对象；如果跳过第一步直接进入源码阅读，往往会在编排代码里兜圈子。再以「协议报文被丢」为例，COPP 的 cir 与 cbs 决定限速阈值，若确实配低了，表现为协议振荡而非配置报错，因此配置层的自检不会发现，必须结合运行态计数与案例库判断，见「排障见 08-04」。这类「配置正确但表现异常」的场景正是速查表存在的意义。

### 6. 版本差异

四组表的版本差异来源不同，不能一概而论。BGP_NEIGHBOR 与 DEVICE_METADATA 的字段在样例生成器中出现，但样例值随拓扑模板变化，不同版本的 `config_samples.py` 可能增删字段或调整默认计时，本篇给的 180、60、65100 只代表本次快照的 t1 样例；真实设备上的字段集合须对照 `src/sonic-config-engine/config_samples.py` 与实际版本核验。ACL 的字段与枚举由 `sonic-acl.yang` 约束，YANG 模型在不同版本会扩展枚举、增加匹配字段或收紧 pattern，本篇列出的 stage、type、PACKET_ACTION、IP_TYPE 枚举来自本快照模型，若目标版本的模型新增枚举值，应以该版本模型为准，字段级差异见「字段见 05-07」。STATIC_ROUTE 的字段来自 minigraph 渲染逻辑，是否写入 `bfd`、是否带 `advertise` 取决于拓扑定义与版本分支，本篇只说「本快照可见」，不宣称全版本一致。COPP 的差异最复杂，因为 `copp_cfg.j2` 是带 Jinja 条件的模板，端口数量、设备类型、是否管理型节点都会改变渲染结果，模板结构本身也可能随版本调整，因此 COPP 的「默认值」必须理解为「特定输入下的渲染值」，需对照 `files/image_config/copp/copp_cfg.j2` 与实际版本核验。

还有一个跨版本的通用差异：逻辑库的编号与分隔符由运行时 `database_config.json` 决定，本篇第 4 节示例中的库号 4 来自本快照模板，不同版本或不同实例形态（多 ASIC、DPU、chassis）会改变库与实例的映射，绝不能把库号写死；编号体系的全集与核验方法由本册另一篇专门整理，本篇只在使用 redis-cli 时说明来源，不展开编号表，需要时按运行时配置文件与实际版本核验。同理，表名前缀如 APP_ROUTE_TABLE_NAME、STATE_ROUTE_TABLE_NAME 来自 `orchagent/routeorch.cpp` 的常量引用，具体字符串值需对照实际版本核验，本篇只强调「配置侧与运行态不是一张表」这一事实。把版本差异按来源拆开处理，才能避免「一个版本看到的值套到另一个版本」这类连锁错误。

### 7. 常见误用与调试

第一类误用是「同名对象混库」。最典型的是把 APPL_DB 或 ASIC_DB 的路由表字段写进 CONFIG_DB 的 STATIC_ROUTE，或者在排障时用运行态字段去核对配置表，结果两边对不上就误判为下发失败。正确做法是先按对象所属库分开：配置侧只认 STATIC_ROUTE，期望态与 ASIC 侧的路由表按「原理见 06-07」的链路逐段看，路由族编排结构见「字段见 05-07」。第二类是把样例值当默认值，把 `config_samples.py` 里的 65100、180、60 或 `copp_cfg.j2` 里的 600 抄成规范，忽略它们随拓扑、设备类型与版本变化的性质；凡样例值本篇一律标注「样例为」，不能外推。第三类是 ACL 字段的强相关被忽略，例如 IP_TYPE 选了 IPV4 却填了 IPv6 地址字段，或 stage 选成 EGRESS 却期望匹配入方向流量，这类错误往往在模型校验阶段就被拦住，校验机制见「原理见 06-03」，若绕过校验直接写库则会在下发阶段失败。

第四类是 COPP 的 trap 与 copy 语义混淆，以及 cir 与 cbs 的粒度误用：把 copy 写成 trap 会改变协议报文的上送路径，把限速值配得过低会丢协议报文、配得过高会失去保护作用，且这些表现都不会在配置写库时报错，必须结合运行态判读，下发链路见「原理见 06-08」，案例见「排障见 08-04」。第五类是验证层的误判：用 redis-cli 看到表项就宣称「BGP 已建立、ACL 已生效、路由已通、COPP 已保护」，这是把「配置已写入」当成「硬件已下发」的典型错误；SONiC 的配置链路是异步流水线，命令返回成功只代表意图进了某个库，必须按「原理见 06-01」逐段核对，诊断顺序见「排障见 08-03」。调试时建议固定一个顺序：先在 CONFIG_DB 确认表项与字段，再按各表的机制篇看 APPL_DB 与 ASIC_DB 有没有对应对象，最后用 show 与 STATE_DB 看运行态；每一步都记录时间点，避免把异步延迟误读成配置丢失。按此顺序，本篇的全参数表与速查表可以作为入口索引，机制与案例则按上述交叉引用跳转，不在本篇重复展开。

## 04-04 Redis 数据库编号与 APPL_DB / STATE_DB / COUNTERS_DB 对象全集

### 1. 本篇定位与覆盖范围

本篇是 04 册的第 4 篇，专门整理 SONiC 控制面所使用的 Redis 逻辑库编号体系，以及 APPL_DB、STATE_DB、COUNTERS_DB 三类库中的常见对象。这是全册最容易被写错的一篇，因为库编号不是某个源码文件里的固定常量，而是运行时由 `/var/run/redis/sonic-db/database_config.json` 决定的值；凭印象写「CONFIG_DB 是某号库」是明确禁止的。本篇的处理方式是：先给出本快照 `dockers/docker-database/database_config.json.j2` 模板中确实可见的 id 值与分隔符，逐项标注来源，再强调运行时配置文件才是最终依据，凡超出本快照模板范围的一律写「需对照实际版本核验」。这样既提供可核对的清单，又不把某个快照的模板值冒充全版本通则。

覆盖范围分三层。第一层是编号与分隔符全集，涵盖 CONFIG_DB、APPL_DB、ASIC_DB、COUNTERS_DB、STATE_DB 等常用库，以及 LOGLEVEL_DB、PFC_WD_DB、FLEX_COUNTER_DB、SNMP_OVERLAY_DB、RESTAPI_DB、GB_* 系列、CHASSIS_* 系列、APPL_STATE_DB、DPU_* 系列、EVENT_DB、BMP_STATE_DB 等按场景扩展的库。第二层是实例映射，说明各库落在哪个 Redis 实例上、单实例与多实例模板的区别。第三层是对象全集，重点是 APPL_DB 的期望态对象、STATE_DB 的运行时状态对象与 COUNTERS_DB 的计数器及名称映射对象；对象名凡能在本快照源码中定位到常量或字符串的给出路径，定位不到的写「需对照实际版本核验」。机制层面，producer 与 consumer 如何读写这些库属于「原理见 06-02」，SonicDBConfig 的逐字段结构属于「字段见 05-03」，py-swsssdk 模块的定位属于「模块见 07-05」，本篇只列参数与对象，不重列字段与机制。

还需明确本篇不做什么。本篇不展开 Redis 本身的命令语法与返回码，命令全集与返回码体系由本册另一篇专门整理；不展开这些对象如何被各 Orch 消费并下发 ASIC 的链路，那属于「原理见 06-01 ｜ 原理见 06-04 ｜ 原理见 06-05」；不展开 warm reboot 或 chassis 场景下的状态恢复流程，那属于「原理见 06-10 ｜ 原理见 06-11」。本篇出现的 redis-cli 命令只用于演示「如何按编号和分隔符核对对象确实存在」，命令全集不在本篇。按此边界，先给出编号来源与分层关系图，帮助读者建立「运行时配置决定编号、编号决定连接、连接决定看到哪些对象」的整体印象，分层关系见图 04-04-01。

### 3. 逐项详解

**编号是怎么来的。** `sonic-py-swsssdk-master/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 类定义了两个路径常量：`SONIC_DB_GLOBAL_CONFIG_FILE` 指向 `/var/run/redis/sonic-db/database_global.json`，`SONIC_DB_CONFIG_FILE` 指向 `/var/run/redis/sonic-db/database_config.json`。`load_sonic_db_config()` 读取本地命名空间的配置并存入 `_sonic_db_config['']`，`load_sonic_global_db_config()` 遍历全局配置中的 `INCLUDES`，按 `namespace` 把各命名空间的配置文件逐一载入；若 `/var/run` 下的文件不存在，代码会退化到包内 `src/swsssdk/config/database_config.json` 作为兜底。`get_dbid(db_name, namespace)` 的实现是从 `_sonic_db_config[namespace]["DATABASES"][db_name]["id"]` 取值，`get_separator()` 同理取 `"separator"`，`get_socket()`、`get_hostname()`、`get_port()` 则经 `get_instance()` 取实例信息。`SonicV2Connector.connect()` 先按 `use_unix_socket_path` 决定走套接字还是主机端口，再调用 `get_dbid()` 拿到编号，最后交给 `dbintf.connect()`。这条链路直接说明编号是「运行时配置的值」，而不是写死在代码里的常量，是本篇反对硬编码编号的根本依据，逐字段结构见「字段见 05-03」。

**分隔符与实例。** 分隔符决定了复合键的拼法：CONFIG_DB、STATE_DB、SNMP_OVERLAY_DB、RESTAPI_DB、CHASSIS_* 等使用竖线，APPL_DB、ASIC_DB、COUNTERS_DB、PFC_WD_DB、FLEX_COUNTER_DB、GB_* 等使用冒号。实例决定数据在哪个 Redis 服务上：`database_config.json.j2` 中 `redis` 实例的主机名取 HOST_IP、端口取 REDIS_PORT、套接字为 `/var/run/redis{{DEV}}/redis.sock`；`redis_chassis` 固定为 `redis_chassis.server` 的 6380 端口、套接字在 `/var/run/redis-chassis/`；`redis_bmp` 用 BMP_DB_PORT，`remote_redis` 用 REMOTE_DB_IP 与 REMOTE_DB_PORT。`multi_database_config.json.j2` 进一步演示多实例拆分：`redis1` 到 `redis4` 分别是 6378、6377、6376、6375 端口，并把 APPL_DB 放到 redis1、ASIC_DB 放到 redis2、COUNTERS_DB 与 PFC_WD_DB 放到 redis3，而 CONFIG_DB 与 STATE_DB 仍在 redis。同一模板里 SYSMON_DB 取 id=10、BMC_DB 取 id=12，与前表的 GB_COUNTERS_DB、CHASSIS_APP_DB 编号相同却落在不同实例，正说明「编号只在实例内有意义」，跨实例比较编号没有意义。

**APPL_DB 对象。** APPL_DB 保存的是经配置管理进程校验后的期望状态，键分隔符为冒号。`sonic-swss-master/orchagent/` 中可见大量以 `APP_` 开头、以 `_TABLE_NAME` 结尾的常量被传给 `ProducerStateTable` 或 `Table`，例如 `APP_ROUTE_TABLE_NAME`、`APP_PORT_TABLE_NAME`、`APP_INTF_TABLE_NAME`、`APP_NEIGH_TABLE_NAME` 分别在路由、端口、接口、邻居相关的编排代码中被引用，另有 `APP_FABRIC_MONITOR_PORT_TABLE_NAME` 取值为 `FABRIC_PORT_TABLE`、`APP_FABRIC_MONITOR_DATA_TABLE_NAME` 取值为 `FABRIC_MONITOR_TABLE`。这些常量的字符串值多由不在本快照的 `sonic-swss-common` 定义，本篇只点名常量与可核实的字符串值，其余写「需对照实际版本核验」，不臆造键名。对象层面要记住一条：APPL_DB 里的是「期望态」，由编排核心消费后生成 ASIC 对象，不是最终下发的硬件状态，消费与重试机制见「原理见 06-04 ｜ 原理见 06-07」。

**STATE_DB 对象。** STATE_DB 保存运行时状态，键分隔符为竖线。`orchagent/` 中可见 `STATE_ROUTE_TABLE_NAME`、`STATE_PORT_TABLE_NAME`、`STATE_LAG_TABLE_NAME` 等常量被用于状态表读写，另有若干以字符串直接定义的状态表，如 `STATE_FDB_SYNC_TABLE_NAME` 取值为 `FDB_SYNC`、`STATE_PROCESS_HEALTH_TABLE_NAME` 取值为 `PROCESS_HEALTH`、`STATE_FABRIC_CAPACITY_TABLE_NAME` 取值为 `FABRIC_CAPACITY_TABLE`、`STATE_PORT_CAPACITY_TABLE_NAME` 取值为 `PORT_CAPACITY_TABLE`、`STATE_MAC_MOVE_GUARD_TABLE_NAME` 取值为 `MAC_MOVE_GUARD`、`STATE_MMG_CAPABILITY_TABLE_NAME` 取值为 `MMG_CAPABILITY_TABLE`。逐字段语义见「字段见 05-09」，状态表在 warm reboot 中的恢复流程见「原理见 06-10」。STATE_DB 与 CONFIG_DB 的分隔符相同但语义完全不同，前者是运行时结果、后者是用户意图，混写会污染配置。

**COUNTERS_DB 对象。** COUNTERS_DB 保存计数器及其名称映射，键分隔符为冒号。`sonic-utilities-master` 中可见一组以 `COUNTERS_` 开头的名字：`COUNTERS_PORT_NAME_MAP`、`COUNTERS_QUEUE_NAME_MAP`、`COUNTERS_QUEUE_INDEX_MAP`、`COUNTERS_QUEUE_PORT_MAP`、`COUNTERS_LAG_NAME_MAP`、`COUNTERS_RIF_NAME_MAP`、`COUNTERS_RIF_TYPE_MAP`、`COUNTERS_PG_NAME_MAP`、`COUNTERS_PG_INDEX_MAP`、`COUNTERS_QUEUE_TYPE_MAP`、`COUNTERS_FABRIC_PORT_NAME_MAP` 等，此外还有 NAT、路由、调试相关的映射名。名称映射表的作用是把 ASIC 侧的计数器编号翻译成端口名、队列名等可读键，采集与展示依赖这些映射；具体表结构、字段与轮询时机须对照实际版本核验，计数器的生成链路见「原理见 06-09」，采集模块见「模块见 07-09」。读计数只从库里取值，不编程 ASIC，这是计数类操作与配置类操作的根本区别。

### 4. 典型示例

下面用 redis-cli 按编号查三类库的对象，再用 Python 片段演示 `SonicDBConfig` 的编号解析。示例中的库号来自本快照模板，运行时以实际 `database_config.json` 为准，需对照实际版本核验。

```bash
redis-cli -n 0 KEYS "PORT_TABLE*"
redis-cli -n 6 KEYS "PORT_TABLE*"
redis-cli -n 2 HGETALL "COUNTERS_PORT_NAME_MAP"
```

```python
from swsssdk import SonicDBConfig
SonicDBConfig.load_sonic_db_config()
print(SonicDBConfig.get_dbid("CONFIG_DB"))
print(SonicDBConfig.get_dbid("STATE_DB"))
print(SonicDBConfig.get_separator("APPL_DB"))
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
1) "PORT_TABLE:Ethernet1"
1) "PORT_STATE|Ethernet1"
1) "oid:0x1000000000001"
2) "Ethernet1"
3) "oid:0x1000000000002"
4) "Ethernet2"
4
6
:
```

逐行判读如下。第一条 `redis-cli -n 0 KEYS "PORT_TABLE*"` 查的是 0 号库即 APPL_DB，返回 `PORT_TABLE:Ethernet1`，冒号分隔符合 APPL_DB 的模板定义，说明端口期望态已从配置管理进程写入；但这一条只证明「期望态存在」，不代表端口已被 ASIC 编程。第二条切到 6 号库即 STATE_DB，返回 `PORT_STATE|Ethernet1`，竖线分隔符合 STATE_DB 的模板定义，说明状态库里已有该端口的运行时状态；对比前两条可见，同一端口在期望态库与状态库里用不同分隔符、不同表名记录，这正是「两类库不能混用」的直观证据。第三条在 2 号库即 COUNTERS_DB 中查名称映射，返回成对的 oid 与端口名，说明计数器编号已被翻译成 Ethernet1、Ethernet2 等可读键，采集侧据此展示端口计数；若该映射为空，即使计数器本身在增长，上层也可能因找不到名字而不显示。Python 片段先显式加载配置，再分别打印 CONFIG_DB、STATE_DB 的编号与 APPL_DB 的分隔符，输出 4、6、冒号与本快照模板一致；关键点在于这些值是运行时从 `database_config.json` 读出的，换一台设备或换一个版本就可能不同，因此永远不要把它们写进代码。输出块已注明示例输出与版本核验要求，所有返回值不得当作真实设备数据引用。

### 5. 速查表

下表把「现象 → 优先核对 → 可能原因 → 交叉引用」压成单行，便于现场按库定位。这里只给核对入口与跳转方向，库的全集见第 2 节，对象名以第 3 节给出的源码路径为准。

| 现象 | 优先核对的库或对象 | 可能原因 | 交叉引用 |
|---|---|---|---|
| 读不到配置表项 | CONFIG_DB 的编号与实例 | 连错实例或编号不符 | 模块见 07-05 |
| 期望态没有对象 | APPL_DB 的 APP_* 表 | 配置未进期望态 | 原理见 06-03 |
| 状态库为空 | STATE_DB 的 STATE_* 表 | 运行态尚未回写 | 原理见 06-05 |
| 计数器全为空 | COUNTERS_DB 名称映射 | 映射未建或连错库 | 原理见 06-09 |
| 路由对象查不到 | APPL_DB 与 ASIC_DB 路由表 | 同步或编排未走通 | 原理见 06-07 |
| chassis 数据缺失 | CHASSIS_* 库实例 | 连到本机实例而非 chassis 实例 | 原理见 06-11 |
| 多 ASIC 串库 | GB_* 库与实例映射 | 命名空间或多实例配置错 | 原理见 06-11 |
| 编号与文档不符 | 运行时 database_config.json | 版本或实例形态不同 | 字段见 05-03 |

速查表的使用要点是「先确认连接、再确认编号、最后确认对象」。以「计数器全为空」为例，第一步先用 `get_dbid` 或运行时配置确认连的是 2 号库，第二步查 `COUNTERS_PORT_NAME_MAP` 有没有映射，第三步才怀疑计数未启用；若跳过第一步，可能在错误的库里反复查询而一无所获。再以「状态库为空」为例，STATE_DB 有表项本身就是异步流水线的结果，配置刚写完就查通常是空的，应按「原理见 06-01」等待并逐段核对，而不是立刻判定故障。

### 6. 版本差异

编号体系的版本差异主要来自模板而非代码。`database_config.json.j2` 是本快照的 Jinja 模板，其中 `DATABASE_TYPE`、`REMOTE_DB_IP`、`REMOTE_DB_PORT`、`BMP_DB_PORT`、`HOST_IP`、`REDIS_PORT` 等变量由构建与运行环境注入，不同版本、不同平台、不同实例形态会渲染出不同的库集合与实例映射；DPU 分支、EVENT_DB 开关、BMP 分支都直接改变可用库的数量。`multi_database_config.json.j2` 又演示了另一套映射，把 APPL_DB、ASIC_DB、COUNTERS_DB 拆到不同端口的实例上，与单实例模板的「全部落在 redis」不同。因此本篇第 2 节的表只能理解为「本快照模板可见的全集」，任何一台具体设备的真实编号都必须回到实际生成的 `database_config.json` 核验，不得跨版本套用。

`SonicDBConfig` 的行为也在演进：本快照的 `dbconnector.py` 支持本地配置与全局配置双层加载、命名空间校验、包内兜底配置，这些能力的细节与默认值须对照实际版本核验；`sonic-swss-common` 中 `ProducerStateTable`、`ConsumerStateTable` 与 `Table` 的实现不在本快照，它们如何按编号与分隔符拼键属于该仓库的内容，需对照实际版本核验，本篇只描述 py-swsssdk 侧可见的解析接口，字段结构见「字段见 05-03」。对象名同样存在版本波动：APPL_DB、STATE_DB 的若干表名以常量形式在编排代码中引用，其字符串值由不在本快照的公共库定义；COUNTERS_DB 的映射名在本快照的 sonic-utilities 中可见，但不同版本可能增删映射或改名。结论只有一条：编号、分隔符、实例与对象名都按「运行时配置加对应版本源码」核验，不写死、不外推。

### 7. 常见误用与调试

第一类误用是「硬编码编号」。把 0、1、2、4、6 等数字直接写进脚本或文档，忽略这些值来自运行时配置，换设备或换版本后必然出错。正确做法是用 `SonicDBConfig.get_dbid()` 或在运行时读 `database_config.json`，本篇第 4 节的 Python 片段就是这个意思；字段细节见「字段见 05-03」。第二类是把分隔符弄反：CONFIG_DB 与 STATE_DB 用竖线、APPL_DB 与 ASIC_DB 与 COUNTERS_DB 用冒号，拼错分隔符就查不到键，尤其在手工构造复合键时最容易出错，须用 `get_separator()` 取得实际值再拼。第三类是混淆配置库与状态库：两者分隔符相同，但一个存用户意图、一个存运行时结果，把状态写进配置库会污染配置、把配置当成状态读会得到错误结论，混写后的现象往往表现为「配置丢失」或「状态不更新」，诊断顺序见「排障见 08-03」。

第四类是忽略实例与命名空间：CHASSIS_* 库落在 redis_chassis、BMP_STATE_DB 落在 redis_bmp、多 ASIC 场景有独立命名空间，若一律连本机默认实例，就会得到空结果并误判为功能缺失；这类能力受平台与版本限制，须对照实际版本核验，相关机制见「原理见 06-11」。第五类是「库里有对象就以为硬件已下发」：在 APPL_DB 看到期望态、在 ASIC_DB 看到对象，只能说明流水线的中间段走通了，最终是否编程成功还要看 STATE_DB 与 show 输出，这是把同步直觉套到异步流水线的典型错误，见「原理见 06-01 ｜ 原理见 06-05」。调试时建议固定顺序：先用运行时配置确认编号、分隔符与实例，再按 CONFIG_DB、APPL_DB、ASIC_DB、STATE_DB、COUNTERS_DB 的顺序逐库查对象，每步记录时间戳以区分「尚未写入」与「确实丢失」。按此顺序，本篇的编号表与速查表可作为入口索引，机制、字段、模块与案例则按上述交叉引用跳转，不在本篇重复展开。

## 04-05 sonic-cli / show / config 命令全集

### 1. 本篇定位与覆盖范围

本篇是 04 册命令族的唯一权威源，集中罗列 sonic-utilities 子仓对外暴露的命令行入口及其参数：包括交互式外壳 sonic-cli、只读状态的 show 族、写配置的 config 族，以及 clear、counterpoll、crm、debug 等辅助命令族。全册统一约定：命令「怎么敲、有哪些选项、默认值是什么、误配有什么后果」由本篇给出；命令背后的实现机制不在本篇展开，凡涉及「配置如何逐段下发到芯片」一律写「原理见 06-01 ｜ 原理见 06-14」；凡涉及命令读取的表项字段结构一律写「字段见 05-02 ｜ 字段见 05-03」；凡涉及命令族所在容器与模块边界一律写「模块见 07-06」。本套资料的版本基准是上游 master 快照（2026-11 抓取），命令名、选项名与默认值以本快照源码为准，凡本快照无法核实者一律标注「需对照实际版本核验」，不得凭印象补全。

先厘清三个词的关系，它们常被混为一谈。其一是 sonic-cli，它是 SONiC 的交互式命令外壳，提供一个可连续输入命令的会话环境，本身并不实现具体子命令，而是把输入分派给底层命令程序；其二是 show，它是只读命令族，负责从各数据库读取状态并格式化输出；其三是 config，它是写配置命令族，负责把用户意图写入配置库。三者的源码落点都可在 `sonic-utilities/sonic-utilities-master/` 内核实：CLI 程序与启动入口由 `setup.py` 的 `entry_points.console_scripts` 段声明，`show/main.py` 与 `config/main.py` 分别是 show 族与 config 族的 click 组定义与子命令注册处，`utilities_common/` 提供公共的连接与参数校验封装，各业务子命令则分散在 `show/`、`config/` 目录下的 `vlan.py`、`bgp_cli.py`、`feature.py`、`aaa.py` 等文件中（模块见 07-06）。

覆盖范围需要划清边界，避免与其他册重复。本篇只回答「命令层」的问题：一个命令叫什么、属于哪个命令族、接受哪些参数、默认值如何、输出大致什么形态、敲错会怎样。至于 `config` 写入 `CONFIG_DB` 后由哪些 `*mgrd` 搬到 `APPL_DB`、再由 `orchagent` 翻译成 ASIC 对象的完整异步链路，本篇不重列，统一写「原理见 06-01 ｜ 原理见 06-03 ｜ 原理见 06-04」；至于命令读写的 `PORT`、`VLAN`、`BGP` 等表的逐字段定义，属于 05 册范畴，写「字段见 05-02」，config 库表与 schema 参数全集见本册 04-02、04-03，DB 编号见 04-04，本篇同样不重复。需要强调的是，show 与 config 只读写数据库、不直接编程 ASIC，这是 CLI 的能力边界，任何把命令返回成功等同于硬件已下发的说法都与本套资料的结论冲突（原理见 06-01）。

事实核验方面，本篇的可信度建立在少数几个可定位的源码锚点上。`setup.py` 的 `console_scripts` 段给出了对外命令名到 Python 入口函数的映射，这是判断「某命令是否存在」的第一依据；`show/main.py` 与 `config/main.py` 中的 `click.group`、`add_command` 与 `@cli.command` 装饰器给出了命令族的子命令挂载关系；`show/main.py` 中 `version` 等函数的 `click.option`、`click.argument` 给出了具体选项与参数是否必填；`config/main.py` 顶部 `DEFAULT_CONFIG_DB_FILE = '/etc/sonic/config_db.json'` 等常量给出了 `config save` / `config load` 的默认文件路径。这些取值均可在本快照内核实，本篇据此成文；而具体输出格式、列宽、命令行提示语会随版本与集成方式变化，示例输出一律标注「示例输出，具体格式需对照实际版本核验」，不得当作任何具体版本的真实回显引用。

### 3. 逐项详解

先说 show 族的工作方式。show 族是一个 click 组，`show/main.py` 里以 `@cli.command()` 装饰的函数就是子命令，函数名默认即命令名，也可通过 `@cli.command('route-map')` 显式指定；`cli.add_command(...)` 把其他模块定义的命令组挂进来，因此 `show vlan`、`show feature`、`show platform`、`show processes` 等分别来自 `show/vlan.py`、`show/feature.py`、`show/platform.py`、`show/processes.py`。show 族在函数内部通过 `swsscommon` 的 `SonicV2Connector`、`ConfigDBConnector` 连接各逻辑库读取数据——`show/main.py` 顶部明确 import 了这两个连接器。这里要守住两条边界：其一，show 只读，不写配置、不编程 ASIC；其二，读到的只是某一时刻的数据库快照，异步流水线下数据库之间可能短暂不一致，因此「show 看到状态」与「硬件已下发」不是一回事（原理见 06-01 ｜ 字段见 05-03）。

`show version` 值得单独拆解，因为它是每次排障的首屏命令。`show/main.py` 中该函数只接受一个 `--brief` 标志，默认输出详尽信息；函数体调用 `device_info.get_sonic_version_info()`、`device_info.get_platform_info()` 与 `platform.get_chassis_info()` 取版本与平台数据，再拼出软件版本、发行版、内核、构建提交、构建日期、构建者、Platform、HwSKU、ASIC 类型与数量、序列号、型号、硬件版本、Uptime 与日期等行；非 `--brief` 时还会调用 `docker images` 打印镜像表。版本号来自构建产物，本套资料统一不写绝对版本号，凡涉及具体版本写「需对照实际版本核验」；`ASIC` 字段若为虚拟交换机取值，则转发由软件模拟，性能数字需在目标机型实测（模块见 07-10）。

再说 config 族的写路径。config 族同样是一个 click 组，且 `config/main.py` 中该组以 `clicommon.AbbreviationGroup` 为类，支持子命令缩写；各子命令通过 `@config.command()` 装饰并大量使用 `add_command` 挂载外部模块，例如 `config.add_command(vlan.vlan)`、`config.add_command(bgp_cli...)` 相关挂载、`config.add_command(feature.feature)` 等。写库动作通常经 `ValidatedConfigDBConnector` 或 `ConfigDBConnector` 完成——`config hostname` 的实现就用 `config_db.mod_entry` 修改 `DEVICE_METADATA` 表的 `localhost` 键的 `hostname` 字段，并在结尾提示改动在重启后会丢失、需运行 `config save` 持久化。这个细节很重要：它说明 config 命令改的是运行时配置库，持久化是独立的一步，二者不可混同（字段见 05-02 ｜ 原理见 06-02）。

`config save` 与 `config load` 是一对持久化命令。`config/main.py` 顶部定义了 `DEFAULT_CONFIG_DB_FILE = '/etc/sonic/config_db.json'` 与 `DEFAULT_GOLDEN_CONFIG_DB_FILE = '/etc/sonic/golden_config_db.json'`；`save` 带 `-y/--yes` 确认开关与可选文件名参数，作用是把当前配置库导出到磁盘文件；`load` 则从文件载入配置库。误用这两条命令的典型后果是：在改动尚未 `save` 时执行 `reload`，导致改动丢失；或把 `load` 指向过期文件，覆盖现行有效配置。因此命令闭环必须写成「前置检查、执行、验证输出、清理」四步，执行写操作前后都要有验证动作。至于 `config reload`、`config apply-patch`、`config load_minigraph` 等更重的命令，选项较多且随版本变化，本篇只点名存在与用途，具体选项需对照实际版本核验。

最后说辅助命令族。`counterpoll` 用于配置计数器轮询项，默认多数轮询关闭，误开会增加数据库写入与 CPU 负担，调优结论需在目标机型实测；`crm` 用于查看 CRM（资源计数）信息，读阈值误判资源耗尽是常见误用；`debug` 用于打开各类调试开关，遗留未关的开关会影响性能，是容易被忽视的隐患；`sonic-clear` 用于清计数与临时状态，清计数前务必留存排障证据；`acl-loader` 用于加载 ACL 规则，规则顺序错误会导致策略不按预期命中（原理见 06-08 ｜ 原理见 06-09）。这些命令族各有独立的 `main.py` 入口，均在 `setup.py` 的 `console_scripts` 段可核实。

### 6. 版本差异

命令族是 sonic-utilities 中演进最活跃的部分，版本差异主要体现在四个层面。第一层是命令的增删：`show/main.py` 的 `add_command` 列表会随版本加入新业务命令或移除废弃命令，本篇表只列代表项，完整清单以对应版本的 `show/`、`config/` 目录为准，需对照实际版本核验。第二层是选项的变化：例如 `show version` 的 `--brief` 在当前快照可核实，但早期版本未必提供；`config save` 的 `-y/--yes` 与确认提示语也可能调整，凡本快照未核实者一律标注。第三层是输出格式：各命令的列名、列宽、单位与排序随版本与集成方式变化，示例输出一律标注「示例输出，具体格式需对照实际版本核验」，不得跨版本套用。第四层是入口脚本的重组：`setup.py` 的 `console_scripts` 段会随版本调整命令名映射，个别命令可能被改名或由新入口替代，判断某命令是否存在应回到该版本 `setup.py` 核实。

还有一个与版本强相关的点是 sonic-cli 与 sonic-cli-gen。本快照 `setup.py` 中可核实的是 `sonic-cli-gen = sonic_cli_gen.main:cli` 这一生成入口，交互式 `sonic-cli` 壳的具体形态、命令补全与分派规则由生成器与运行时环境共同决定，本篇仅陈述其「交互式外壳、分派底层命令」的定位，不臆造其命令清单，细节需对照实际版本核验（模块见 07-06）。版本基准始终为上游 master 快照（2026-11 抓取），具体版本号以对应构建文件为准，需对照实际版本核验。

### 7. 常见误用与调试

第一类误用是把命令返回成功等同于硬件已下发。这是 SONiC 排障中最普遍的认知错误：`config` 命令写入配置库后即返回，后续要经过各 `*mgrd` 搬到 `APPL_DB`、`orchagent` 翻译成对象写入 `ASIC_DB`、`syncd` 经 SAI 编程芯片，是一段异步流水线（原理见 06-01 ｜ 原理见 06-03 ｜ 原理见 06-04 ｜ 原理见 06-05）。正确姿势是按库逐段核对，再结合 `show` 输出，而不是看到「成功」就判定转发正常。

第二类是把 `show` 的协议状态当成转发状态。以路由为例，`show ip route` 经 vtysh 读取的是协议侧路由，FRR 源码不在本快照（模块见 07-08）；它只能说明协议进程已知这条路由，不等于路由已进 `APPL_DB`、更不等于已下发 ASIC。判读时必须把 `show` 与各库查询分开，不一致时先怀疑流水线某段未走通，而非直接判定芯片故障（原理见 06-07 ｜ 排障见 08-04）。

第三类是配置持久化误用。前面已经看到，`config hostname` 明确提示改动重启后会丢失；忘做 `config save`、用 `config load` 载入过期文件、在未 `save` 时执行 `config reload`，都是高频事故。第四类是写错对象：config 子命令的参数多为表名、接口名或 VLAN 名，拼写错误可能写入错误表项而不立即报错，表现为「命令成功但业务异常」，因此写操作前后都要用 `show` 回读验证（字段见 05-02 ｜ 排障见 08-03）。

调试此类问题时，顺序建议固定为：先用 `show version` 确认平台与 HWSKU 是否匹配机型目录，再用 `show processes` 确认相关容器进程在跑，然后用对应 `show` 子命令读取目标状态，最后按 `CONFIG_DB`、`APPL_DB`、`ASIC_DB`、`STATE_DB` 顺序逐段核对表项。凡涉及具体命令选项、输出格式与返回码，一律以对应版本的 `show/`、`config/` 源码为准并标注「需对照实际版本核验」；日志路径与返回码速查见 04-08，容器进程与启动项见 04-07。遵守这套顺序，可以避免把「库里没表项」误判成「硬件坏了」，也能避免把「命令已返回」误判成「配置即时生效」。

### 3. 逐项详解

先深入 `orchagent` 的几组关键参数。通信模式 `-z` 是本快照中较重要的一项，`usage()` 明确写「redis_async|redis_sync|zmq_sync，默认 redis_async」，处理分支调用 `sai_deserialize_redis_communication_mode` 把字符串解析为枚举；`-s` 同步模式被标注「deprecated, use -z」，说明新版本应优先用 `-z` 而非 `-s`。选错通信模式会直接影响 orchagent 与数据库、与 syncd 之间的数据交换方式，进而影响下发正确性与吞吐，调优结论需在目标机型实测（原理见 06-04 ｜ 调优见 08-02）。

录制相关参数是一组，用于排障取证：`-r` 的取值是位掩码，`usage()` 给出 0 表示不录制、1 录制 `sairedis.rec`、2 录制 `swss.rec`、3 同时录制两者、7 三者全开（加入 `responsepublisher.rec`），处理分支检查取值必须在 0~15 之间，越界则打印用法并以失败状态退出；`-d` 指定录制目录，处理分支用 `access(..., W_OK)` 检查目录可写，不可写则退出；`-f`、`-j` 分别覆盖 `swss.rec` 与 `sairedis.rec` 两个默认文件名；`-A` 同时打开异步 SWSS 录制与异步路由状态发布。这组参数的误配后果主要是「想取证却没录到」——目录不可写、文件名写错、位掩码给成 0，都会导致关键排障材料缺失（排障见 08-04）。

批量与性能相关参数是另一组：`-b` 设置消费表 pop 操作的批量大小，默认 128，直接影响 orchagent 从数据库取任务的粒度；`-k` 设置 bulk 模式最大批量，默认 1000，处理分支只对正值生效，非正值会被记录错误并忽略、回退默认；`-I` 设置心跳间隔，默认 10 毫秒，负值会回退到 `HEART_BEAT_INTERVAL_MSECS_DEFAULT` 并报错；`-c` 选择计数器模式，`traditional` 与 `asic_db` 的计数口径不同，默认 `asic_db`；`-R` 打开 ring 线程特性，`-F` 打开 FIB 抑制。这组参数的共同点是都与性能相关，任何调整都必须「需在目标机型实测」，本篇不给绝对值也不给跨机型通用数字（基准方法见 08-01 ｜ 调优见 08-02）。

`orchagent` 还有几个与多 ASIC 和启动时序相关的参数：`-i` 指定多 ASIC 平台上的 ASIC instance_id，处理分支用 `strnlen` 限制长度不超过 `SAI_MAX_HARDWARE_ID_LEN`，超长会被截断并告警，误配会造成实例标识混淆；`-m` 设置交换机 MAC 地址，经 `MacAddress` 构造，非法值会导致构造失败；`-t` 覆盖建交换机超时秒数，处理分支把 `atoi` 结果赋给 `create_switch_timeout`，取值过小可能导致建交换机超时失败；`-v` 指定 VRF 名，默认空。这几个参数与平台强相关，具体默认值与约束需对照实际版本核验（模块见 07-03 ｜ 模块见 07-10）。

再说 `syncd`。它的 `-t/--startType` 取值在 `CommandLineOptions.h` 中以枚举固化：`cold`、`warm`、`fast`、`fastfast`、`express`，另有 `unknown` 作为错误哨兵；其中 `fastfast` 注释为 Mellanox 平台专用、`express` 为 Cisco 平台专用，说明这些启动类型受平台与版本限制，选错会导致状态恢复失败，需对照实际版本核验（原理见 06-10）。`-z/--redisCommunicationMode` 与 orchagent 同构，默认 `redis_async`；`-R/--asyncRec` 的注释特别指出仅在非虚拟、非 DPU 交换机且 ZMQ 南向有效时才生效，由 `SYSTEM_DEFAULTS|async_rec` 驱动，这是典型的「受平台与版本限制」参数（原理见 06-05）。

`syncd` 的看门狗与比较逻辑参数要成对理解：`-w` 设置正常操作的看门狗时长，`-W` 设置初始化阶段的时长，help 明确 `-W` 默认与 `-w` 相同；取值过小会在初始化或正常运行时误触发，导致进程被看门狗重启。`-b/--breakConfig` 指定比较逻辑的「break before make」配置文件，`-x/--contextConfig` 指定上下文配置，`-g/--globalContext` 从上下文配置中选取全局上下文索引，三者服务于多上下文与比较逻辑场景；`-C/--enableConsistencyCheck` 在比较逻辑后做库与 ASIC 的一致性检查，会增加额外比较开销。开关型的 `-l`、`-a`、`-U`、`-G`、`-B`、`-S`、`-d` 分别对应 SAI 批量、属性版本检查、元数据单测、按端口计数发现、批量计数器组、崩溃退出睡眠与诊断壳，多数默认关闭，生产环境不应随意打开（字段见 05-06 ｜ 原理见 06-05）。

SAI 部分的详解必须落到「可核验边界」上。本快照 `sonic-sairedis/sonic-sairedis-master/SAI/` 为空目录，这意味着_header 声明、具体属性名（例如端口速率、MTU、管理状态一类 attribute）与数值枚举都不在本快照内，任何具体的 SAI 属性名与数值都必须写「不在本快照，需对照实际版本核验」。可核验的是同仓的 `meta/`（属性元数据）、`vslib/`（虚拟 SAI 实现）、`lib/`、`saidump/`、`saiplayer/` 等目录；`syncd/` 下的 `SaiObj.cpp`、`VendorSai.cpp`、`SaiDiscovery.cpp` 等展示了对象与厂商 API 装载的代码形态（字段见 05-04 ｜ 模块见 07-04）。撰写 SAI 属性相关内容时，正确做法是给出可定位目录并标注核验要求，而不是凭印象填一个属性名。

下面给一组查看进程实际启动命令的示例。进程命令行通常以 supervisord 配置项形式给出，这里用文本示意其参数形态，具体命令由对应版本的 supervisord 模板决定、需对照实际版本核验。

```text
示例配置，具体格式需对照实际版本核验（取值仅为格式示意）
[program:orchagent]
command=/usr/bin/orchagent.sh -b 128 -z redis_async -c asic_db -I 10 -r 3
priority=<swss_priority_base + offset>
dependent_startup=true
dependent_startup_wait_for=portsyncd:running
```

逐行判读如下。`[program:orchagent]` 是 supervisord 中该进程的配置段名，说明 orchagent 由容器内的进程编排拉起，启动顺序见 04-07 与「原理见 06-13」。`command` 行给出实际命令行：脚本 `/usr/bin/orchagent.sh` 后面跟了一组参数，`-b 128` 表示消费表 pop 批量大小取默认 128，`-z redis_async` 显式指定异步 Redis 通信模式（与 usage 默认值一致），`-c asic_db` 指定计数器模式为 `asic_db`（同样与默认一致），`-I 10` 指定 10 毫秒心跳，`-r 3` 打开 `sairedis.rec` 与 `swss.rec` 两路录制。这里要理解：显式写出与默认一致的值，是为了让意图可读、不受默认值变更影响，排障时不能因为「和默认一样」就忽略它们。`priority` 是由 `swss_priority_base` 加偏移的表达式，决定同容器内启动优先级；`dependent_startup=true` 配合 `dependent_startup_wait_for=portsyncd:running` 表示 orchagent 要等 `portsyncd` 进入 running 才启动，这是依赖编排的体现。判读要点是：参数拼写与取值随版本变化，示例中的具体值仅为格式示意、需对照实际版本核验；录制开关 `-r` 在生产环境通常按取证需求设置，长期全量录制会占用磁盘与 CPU。

再看一组核对 syncd 启动类型的示例，用于区分冷启动与 warm 重启。

```text
示例配置，具体格式需对照实际版本核验（取值仅为格式示意）
[program:syncd]
command=/usr/bin/syncd_init_service.sh -t warm -z redis_async -l -a
```

逐行判读如下。`[program:syncd]` 是 syncd 的进程配置段；`command` 行中 `-t warm` 指定启动类型为 warm，对应 `CommandLineOptions.h` 中 `SAI_START_TYPE_WARM_BOOT` 枚举，意味着 syncd 要走状态恢复路径而非重建全部对象，warm reboot 受平台与版本限制、需对照实际版本核验（原理见 06-10）；`-z redis_async` 与 orchagent 保持同一通信模式，否则两端数据交换方式不一致会导致 `ASIC_DB` 异常；`-l` 打开 SAI 批量支持，属于性能相关开关，厂商不支持时会异常，调优需在目标机型实测；`-a` 打开属性版本检查，会在 SAI 发现阶段按属性版本校验，严格检查可能导致发现失败。这组参数共同说明：syncd 的启动参数与 orchagent 是「成对配置」的关系，尤其通信模式必须一致，启动类型必须与编排系统期望的重启方式匹配。示例中具体取值仅为格式示意、需对照实际版本核验，命令行形态由对应版本的 `syncd_init_service.sh` 与 supervisord 模板决定（模块见 07-04 ｜ 模块见 07-11）。

### 6. 版本差异

进程参数的版本差异比用户命令更隐蔽，主要体现在四处。其一是通信模式的演进：`-s` 同步模式在本快照被标注「deprecated, use -z」，而 `-z` 提供 `redis_async`、`redis_sync`、`zmq_sync` 三种模式，说明版本在从单一同步模式向可配置模式迁移；更早的版本可能只有 `-s` 而没有 `-z`，阅读旧资料时要能对应起来。其二是批量与异步特性：`-A` 异步录制与路由状态发布、`-q` ZMQ 地址、`-R` ring 线程等参数带有明显的版本演进痕迹，是否为默认值、是否受平台支持都需对照实际版本核验。其三是启动类型：`syncd` 的 `fastfast`、`express` 分别对应 Mellanox 与 Cisco 平台，属于平台相关的扩展类型，并非所有版本与机型都支持，一律写「受平台与版本限制，需对照实际版本核验」。

其四是 SAI 头文件与元数据的形态变化。本快照 `SAI/` 为空目录，但其他版本可能包含头文件；`meta/` 的元数据文件数量与属性覆盖范围也随 SAI 版本变化。因此不能据本快照断言「SAI 属性固定为某集合」，正确写法始终是：本快照 `SAI/` 为空、不列具体属性、写「不在本快照，需对照实际版本核验」，并给出 `meta/`、`vslib/` 目录（字段见 05-04 ｜ 模块见 07-04）。此外，`orchagent/main.cpp` 与 `syncd/CommandLineOptionsParser.cpp` 中的选项字符串会随版本改动，本篇所有表格值以本快照为准，具体版本是否一致需对照实际版本核验；版本基准始终为上游 master 快照（2026-11 抓取），具体版本号以对应构建文件为准。

### 7. 常见误用与调试

第一类误用是两端通信模式不一致。`orchagent` 与 `syncd` 都提供 `-z` 参数且默认 `redis_async`，若一端显式改为 `zmq_sync` 而另一端未改，会造成数据交换方式不匹配，表现为对象下发异常。调试时应先确认两端 `-z` 取值一致，再查其他原因（原理见 06-04 ｜ 原理见 06-05）。

第二类是把 `orchagent` 当成直接操作硬件的进程。必须反复确认：`orchagent` 只消费 `APPL_DB`、生成对象写入 `ASIC_DB`，经 SAI 属性同 `syncd` 交互，不读写寄存器、不直接驱动芯片；真正调用 SAI、经厂商适配编程 ASIC 的是 `syncd`（原理见 06-05 ｜ 模块见 07-03 ｜ 模块见 07-04）。第三类是把 SAI 当成可在本快照随意查阅的头文件集合：本快照 `SAI/` 为空目录，厂商实现闭源且不在本快照，任何具体属性名与数值都要写「不在本快照，需对照实际版本核验」，不可凭印象编造（字段见 05-04）。

第四类是性能与看门狗参数误配。批量大小 `-b`、批量上限 `-k`、心跳 `-I` 与 syncd 的看门狗 `-w`/`-W` 都属于时序与吞吐相关参数，任意放大或缩小都可能带来反效果：批量过大占内存、过小拖吞吐，看门狗过小会误触发重启。这类调优没有通用答案，一律「需在目标机型实测」（基准方法见 08-01 ｜ 调优见 08-02）。第五类是启动类型误配：syncd 的 `-t` 必须与编排系统期望的冷启动或 warm 重启一致，选错会导致状态恢复失败；`fastfast`、`express` 受平台限制，需对照实际版本核验（原理见 06-10）。

调试这类问题的顺序建议固定为：先用各进程 `-h` 核对当前版本选项拼写与默认值，再查 supervisord 中实际拼出的命令行（见 04-07），确认 `orchagent` 与 `syncd` 的通信模式与启动类型匹配，然后按 `APPL_DB`、`ASIC_DB`、`STATE_DB` 顺序逐段核对表项，必要时用 `-r` 打开录制取证，最后才怀疑厂商 SAI 实现或硬件边界。凡涉及具体选项、默认值、输出与返回码，一律以对应版本的 `orchagent/main.cpp`、`syncd/CommandLineOptionsParser.cpp`、`syncd/CommandLineOptions.h` 为准并标注「需对照实际版本核验」；日志与返回码速查见 04-08，DB 对象全集见 04-04，结构体字段见 05-05、05-06。遵守这套顺序，可以避免把「参数写反导致的不下发」误判成硬件故障，也能避免在 SAI 空目录上编造不存在的属性。

## 04-07 容器服务、supervisord 与启动参数全集

### 1. 本篇定位与覆盖范围

本篇是 04 参数与 API 手册中专门收拢「容器服务与启动参数」的字典分册，回答的是一个非常具体的问题：一台 SONiC 设备完成镜像安装后，各容器里的进程究竟由谁、按什么顺序、带哪些参数被拉起，异常时又该回到哪个配置文件里核对对应的键。本篇不讨论容器编排的内部实现机制，也不展开事件监听器的状态机细节；这些属于技术原理册的内容，统一写「原理见 06-13」。本篇同样不罗列容器镜像的构建规则、不展开各容器的能力清单，容器族的功能划分写「模块见 07-02」。本篇涉及的是可被逐项查询的配置键、取值、默认值与作用，而不是结构体字段；与进程运行时状态、WARM_RESTART 相关的字段写「字段见 05-09」。

覆盖范围可以分成三层。第一层是容器入口层，即 `sonic-buildimage/sonic-buildimage-master/dockers/` 下每个 `docker-*` 目录中的启动脚本与配置文件族，包括 `supervisord.conf`、`supervisord.conf.j2`、`supervisord.conf.common.j2` 以及基础镜像 `etc/supervisor/supervisord.conf`。第二层是 supervisord 参数层，包括 `[supervisord]` 全局段、`[unix_http_server]` 与 `[supervisorctl]` 通道段、`[eventlistener:*]` 事件监听段、以及数量最多的 `[program:*]` 程序段。第三层是启动依赖层，也就是 `dependent_startup` 与 `dependent_startup_wait_for` 这一类把「谁先起、谁后起、等到什么状态再起」显式声明出来的键。三层的证据均可在上游快照的 `dockers/` 目录逐一核实。

事实基准统一为「上游 master 快照（2026-11 抓取）」，路径相对各子仓 `xxx-master/` 仓库根。凡模板中的 Jinja 变量渲染值、`switch_type` 等条件分支的实际取值、以及命令行选项的完整语义，凡快照内无法核实的，一律标注「需对照实际版本核验」，不凭印象补值。需要提醒的是，容器名、程序段名与事件集合在不同发行分支、不同 HWSKU 上并不完全一致，本篇表格给出的是本快照可核验的形态，不能当作跨版本通用常量。

之所以把这些参数单独成篇，是因为 SONiC 把控制面拆进了多个容器，进程之间不靠函数调用而靠 Redis 逻辑库解耦，于是「启动顺序」无法用进程内依赖表达，只能交给 supervisord 的事件驱动依赖调度来声明。这种工程形态决定了排障时不能只看单个进程，而要按「容器入口 → 全局守护 → 事件监听 → 日志与数据库 → 各业务进程 → 编排与同步」的顺序逐段核对，参数表正是这条顺序的随查索引。

### 2. 索引与全参数表

下表按「参数 → 取值 → 默认值 → 作用 → 误配后果」组织，汇总 `dockers/` 下 supervisord 配置族中反复出现的关键键。表中「默认值」一列以本快照模板中能直接读到的为准，凡由 Jinja 表达式计算或随容器变化的，标注需对照实际版本核验；单元格中的逗号分隔值不是枚举全集，具体事件名与程序名需对照实际版本核验。

| 参数 | 取值 | 默认值 | 作用 | 误配后果 |
|---|---|---|---|---|
| nodaemon | true / false | true | 让 supervisord 以前台方式运行，充当容器主进程 | 设为 false 会使容器主进程退出，容器反复重启 |
| logfile_maxbytes | 字节数 | 1MB | 单个 supervisord 日志达到上限后轮转 | 过大易撑爆容器可写层，过小产生大量碎片文件 |
| logfile_backups | 整数 | 2 | 保留的轮转日志份数 | 过小丢失排障线索，过大占用持久化空间 |
| command | 可执行文件路径或 shell 串 | 无 | 定义程序段实际执行的命令 | 路径写错或脚本缺失会导致进程进入 FATAL |
| priority | 整数 | 视容器基数十进制偏移 | 决定无依赖时的启动先后 | 与依赖顺序冲突时会拉起尚未就绪的进程 |
| autostart | true / false | false | 是否随 supervisord 自动启动 | 误设 true 会在依赖未满足时提前启动 |
| autorestart | true / false / unexpected | false 或 unexpected | 定义退出后是否重启 | 误设 true 会掩盖反复崩溃，掩盖真实故障 |
| startsecs | 整数秒 | 0 或默认 | 判定「启动成功」前需保持运行的时长 | 设置过长拖慢依赖链，过短误判启动成功 |
| startretries | 整数 | 0 | 启动失败后的重试次数 | 过大延长故障暴露时间，过小错过瞬时恢复 |
| dependent_startup | true / false | true | 开启基于事件的状态依赖调度 | 关闭后依赖声明失效，顺序退化成 priority |
| dependent_startup_wait_for | 程序名加状态，如 portsyncd:running | 视模板变量 | 等待指定进程进入指定状态后再启动 | 引用不存在的程序会使本程序永不启动 |
| stdout_logfile | NONE 或路径 | NONE | 标准输出落文件开关 | 指定本地文件会绕开 syslog，日志分散难查 |
| stdout_syslog | true / false | true | 标准输出是否转发 syslog | 关闭后 `show logging` 看不到该进程输出 |
| stderr_logfile | NONE 或路径 | NONE | 标准错误落文件开关 | 与 stdout 同理，导致错误日志散落 |
| stderr_syslog | true / false | true | 标准错误是否转发 syslog | 关闭后异常堆栈无法进入系统日志 |
| stdout_capture_maxbytes | 字节数 | 1MB | 事件监听可捕获的 stdout 上限 | 过小截断通信内容，影响事件监听判读 |
| stopwaitsecs | 整数秒 | 60（teamd 段） | 停止时等待进程退出的秒数 | 过小强制杀进程，可能留下半成品状态 |
| exitcodes | 逗号分隔整数 | 0,3 | 事件监听器认为「正常」的退出码集合 | 漏配退出码会使正常退出被当作异常 |
| events | 事件名逗号分隔 | PROCESS_STATE 等 | 声明监听器订阅的进程事件集合 | 订阅不足会漏掉 FATAL 等关键事件 |
| buffer_size | 整数 | 1024 | 事件监听缓冲区大小 | 过小在高事件速率下丢事件 |
| user | 用户名 | root 或 redis | 以指定用户身份运行程序 | 误配权限会导致无法绑定端口或读写目录 |
| environment | 键值对 | 条件设置 | 注入环境变量，如 ASAN_OPTIONS | 路径不存在会使开启 ASAN 的镜像启动失败 |

紧随其后的是容器与配置文件族的对应关系，便于从「想改哪个进程」反查到「该编辑哪个文件」。下表列出本快照可直接核实的几个代表容器，表中程序名与文件名需对照实际版本核验。

| 容器目录 | 配置文件族 | 承载的代表程序 | 需重点核对的参数 |
|---|---|---|---|
| docker-orchagent | supervisord.conf.j2 与 common.j2 | orchagent、portsyncd、各 mgrd | priority、wait_for、autorestart |
| docker-database | supervisord.conf.j2 | redis-server 各实例、flushdb | command、user、dependent_startup |
| docker-teamd | supervisord.conf.common.j2 | teammgrd、teamsyncd、tlm_teamd | stopwaitsecs、startsecs、wait_for |
| docker-sonic-telemetry | supervisord.conf | start、telemetry、dialout | priority、wait_for、autorestart |
| docker-base 系列 | etc/supervisor/supervisord.conf | 基础通道与 include 定义 | logfile、serverurl、files |

索引的使用方法有三条。其一，先按「容器—配置文件族」表定位文件，再回到全参数表查键的含义，避免在几十个程序段里盲搜。其二，凡看到 `{{ ... }}` 形式的 Jinja 表达式，说明该值在渲染时才确定，须结合调用方传入的变量判断，不能直接把模板文本当成最终值。其三，参数表里的「默认值」描述的是本快照模板中可读到的常见形态，同一键在不同程序段可能取不同值，逐项详解会按段分组说明。

### 3. 逐项详解

先讲全局段。`[supervisord]` 段中的 `nodaemon=true` 是最关键的一行：它让 supervisord 以前台进程方式运行，从而占据容器的主进程位置；一旦误设为后台方式，容器主进程会立即退出，编排层会认为容器失败并反复重建。`logfile_maxbytes=1MB` 与 `logfile_backups=2` 共同约束守护进程自身日志的体量，避免日志无限增长撑爆容器可写层；这两个值偏小是容器环境的常见取舍，不能照搬到宿主机 syslog 的策略。基础镜像 `dockers/docker-base-bookworm/etc/supervisor/supervisord.conf` 还给出 `logfile=/var/log/supervisor/supervisord.log`、`pidfile=/var/run/supervisor/supervisord.pid`、`childlogdir=/var/log/supervisor` 与 `user=root`，并通过 `[unix_http_server]` 的 `file=/var/run/supervisor.sock`、`chmod=0700` 以及 `[supervisorctl]` 的 `serverurl=unix:///var/run/supervisor.sock` 建立本地控制通道；最后 `[include]` 用 `files=/etc/supervisor/conf.d/*.conf` 把各容器的程序段拼进来。

再讲事件监听段。`dockers/docker-orchagent/supervisord.conf.j2` 中 `[eventlistener:dependent-startup]` 以 `python3 -m supervisord_dependent_startup` 启动，`autostart=true`、`autorestart=unexpected`、`startretries=0`、`exitcodes=0,3`、`events=PROCESS_STATE`、`buffer_size=1024`。其中 `exitcodes=0,3` 的含义是这两个退出码被视为监听器正常退出，其余码触发 `autorestart=unexpected` 的策略；`events=PROCESS_STATE` 表明它订阅进程状态变化，这正是依赖调度得以工作的前提。紧随其后的 `[eventlistener:supervisor-proc-exit-listener]` 以 `/usr/bin/supervisor-proc-exit-listener-rs --container-name swss` 启动，`events` 列出 PROCESS_STATE_EXITED、PROCESS_STATE_RUNNING、PROCESS_COMMUNICATION_STDOUT、PROCESS_STATE_FATAL 等；`--container-name` 在不同容器里取值不同，database 容器为 database、telemetry 容器为 telemetry，需对照实际版本核验。这两个监听器是「依赖调度」和「异常退出上报」两条机制的落地载体，其机制写「原理见 06-13」。

然后讲程序段的通用键。`command` 指向启动脚本而非直接调用二进制，例如 orchagent 段用 `/usr/bin/orchagent.sh`，swssconfig 段用 `/usr/bin/swssconfig.sh`，这类包装脚本通常负责环境变量准备与参数拼装，脚本本体需对照实际版本核验。`priority` 在 swss 容器里以 `swss_priority_base` 为基数做十进制偏移，standalone 场景基数为 0，虚拟交换机场景基数会变化；teamd 容器则以 `teamd_priority_base` 为基数，默认 3。`autostart=false` 与 `dependent_startup=true` 成对出现，表示进程不自行启动，而交给依赖调度。`autorestart=false` 在多数业务进程段出现，意味着进程退出后不自动重启——这是有意设计，因为重启需经过更高层的容器级处理，误改为 true 反而会掩盖反复崩溃的事实。

最后讲依赖键与日志键。`dependent_startup_wait_for` 的取值决定启动门槛：orchagent 段默认是 `portsyncd:running`，当 `switch_type` 为 fabric 时改为 `rsyslogd:running`；swssconfig 段等待 `orchagent:running`；restore_neighbors、neighsyncd、vlanmgrd、intfmgrd、portmgrd、buffermgrd 等多数 mgrd 段在包含 swssconfig 时等待 `swssconfig:exited`，否则退回 `orchagent:running`。teamd 容器的 `teamd_wait_for` 默认 `start:exited`，teamsyncd 则等待 `teammgrd:running`。日志侧几乎统一使用 `stdout_logfile=NONE` 配合 `stdout_syslog=true`、`stderr_logfile=NONE` 配合 `stderr_syslog=true`，即标准输出与错误都进 syslog，而不是落到容器本地文件；这正是排障时要用系统日志命令而非去容器里找日志文件的原因，命令与判读留待 04-08。启用 ASAN 的镜像还会注入 `environment=ASAN_OPTIONS="log_path=/var/log/asan/...-asan.log:print_suppressions=0"`，具体后缀随程序变化，需对照实际版本核验。

图 04-07-01 的边并不表示数据流，而表示「等待前一个节点进入指定状态」的启动门槛；这与配置从 `CONFIG_DB` 到 `ASIC_DB` 的异步流水线是两件事，后者写「原理见 06-01」。

下面给出 `dockers/docker-orchagent/supervisord.conf.common.j2` 中 orchagent 程序段的模板原文，它集中体现了本节讲的多个键；内容节选自该文件，含 Jinja 变量，具体渲染值需对照实际版本核验。

```ini
[program:orchagent]
command=/usr/bin/orchagent.sh
priority={{ swss_priority_base + 4 }}
autostart=false
autorestart=false
stdout_logfile=NONE
stdout_syslog=true
stderr_logfile=NONE
stderr_syslog=true
stdout_capture_maxbytes=1MB
dependent_startup=true
dependent_startup_wait_for={{ orchagent_dependent_startup_wait_for }}
```

配合模板阅读，用一条命令查看容器内各程序的实时状态，输出块已注明示例输出与版本核验要求。

```bash
docker exec swss supervisorctl status
```

```text
示例输出，具体格式需对照实际版本核验（程序名与状态仅为格式示意）
gearsyncd                        RUNNING   pid 123, uptime 0:05:12
portsyncd                        RUNNING   pid 131, uptime 0:05:11
orchagent                        RUNNING   pid 145, uptime 0:05:09
swssconfig                       EXITED    Nov 16 01:20:33
coppmgrd                         RUNNING   pid 201, uptime 0:05:06
neighsyncd                       RUNNING   pid 208, uptime 0:05:05
```

逐行判读如下。`docker exec swss supervisorctl status` 进入名为 swss 的容器并调用本地控制通道，容器名在不同版本可能不同，需对照实际版本核验；它读取的是本节 `[unix_http_server]` 与 `[supervisorctl]` 建立的 socket，属于只读状态查询。输出第一段中 `gearsyncd` 与 `portsyncd` 均为 RUNNING，说明日志辅助与端口监听已就绪，这是 orchagent 得以启动的前置条件，与模板里 wait_for 的声明一致。第三行 `orchagent` 为 RUNNING 且 `uptime` 略短于前两者，符合依赖顺序的时间关系。第四行 `swssconfig` 为 EXITED 而非 RUNNING，这是正常特征：它是一次性加载程序，按设计应在完成后退出，若在此处看到 RUNNING 反而要怀疑脚本卡住；同时它的 `autorestart=false` 保证退出后不会被反复拉起。第五、六行 `coppmgrd`、`neighsyncd` 均为 RUNNING，对应模板中等待 `swssconfig:exited` 的一批 mgrd，进一步印证依赖链生效。若任意关键程序出现 FATAL，或 orchagent 的 uptime 反复归零，说明存在反复崩溃，此时不要只在容器内看本地日志，而应按 04-08 的日志口径到 syslog 中查对应程序的错误行，并结合 `原理见 06-13` 判断是依赖门槛未满足还是程序自身异常。

### 5. 速查表

下表把常见疑问压缩成「现象 → 先查文件 → 关键参数 → 处置方向」四列，供现场快速反查。表中处置方向只给到参数层，不展开运维步骤；涉及具体命令与输出判读写「完整命令见 04-05」，涉及日志检索写「日志方法见 04-08」。

| 现象 | 先查文件 | 关键参数 | 处置方向 |
|---|---|---|---|
| 容器反复重建、主进程秒退 | docker-base 的 supervisord.conf | nodaemon、user | 确认主进程以前台运行且用户有权限 |
| 后起进程提前退出 | docker-orchagent 的 common.j2 | dependent_startup_wait_for | 核对等待的程序名与状态是否拼对 |
| 全部程序同时起、顺序混乱 | 各容器 supervisord.conf.j2 | autostart、dependent_startup | 关闭 autostart，开启依赖调度 |
| 程序崩溃后无感知 | eventlistener 段 | events、exitcodes | 订阅 FATAL，核对退出码集合 |
| `show logging` 看不到进程输出 | 各 program 段 | stdout_syslog、stderr_syslog | 确认输出转发 syslog 而非落本地文件 |
| ASAN 镜像启动失败 | 各 program 段条件分支 | environment、ASAN_OPTIONS | 确认日志目录存在、路径可写 |
| teamd 容器停止缓慢 | docker-teamd 的 common.j2 | stopwaitsecs | 核对等待秒数与进程退出耗时 |
| 数据库实例未监听预期端口 | docker-database 的 supervisord.conf.j2 | command、user | 核对 bind、port、unixsocket 参数 |

使用速查表要注意两点。第一，「先查文件」列给出的是起点而非终点，很多问题的根因在调用方传入的 Jinja 变量里，模板文件本身看不出最终值。第二，「关键参数」列只点名一个最有区分度的键，实际排查往往要成组看 command、wait_for 与 autorestart 三者的组合，单看一个键容易得出片面结论。

### 6. 版本差异

容器与 supervisord 参数是全册中版本差异最集中的一类，原因有三。其一，`dockers/` 目录按发行分支演进，不同分支新增或下线容器，程序段名随之增减；本篇表格只呈现本快照可核验的代表性容器，不能当作所有版本的全集。其二，模板化程度不同：orchagent、database、teamd、lldp、snmp 等容器使用 `.j2` 模板并 include 公共片段，而 telemetry、nat、macsec、 sonic-gnmi 等容器多为静态 `supervisord.conf`，前者要连带看渲染变量，后者可直接读文本，二者排障入口不同。

其三，条件分支会改变实际参数集。以 orchagent 公共模板为例，`switch_type == "fabric"` 时 `is_fabric_asic` 置 1，gearsyncd、portsyncd 等段被跳过，orchagent 的等待对象从 `portsyncd:running` 改为 `rsyslogd:running`，并出现 fabricmgrd 段；`include_swssconfig` 为假时，swssconfig 与 enable_counters 段不生成，一批 mgrd 的等待对象退回 `orchagent:running`；`ENABLE_ASAN == "y"` 时各段追加 ASAN_OPTIONS 环境变量。这些分支在模板里可核实，但某机型实际走哪个分支由配置决定，需对照实际版本核验。

此外还有若干细节差异需留意。`autorestart` 的取值在不同容器并不统一：swss 与 telemetry 的 rsyslogd 段分别为 unexpected 与 true，database 容器为 false，需逐段核对而不能套用默认值。`--container-name` 参数随容器变化，影响异常退出上报的归属。`priority` 的基数在 standalone 与虚拟交换机场景不同，跨场景比较数值没有意义。凡涉及多 ASIC 命名空间、chassis 与 warm reboot 相关进程的启停，均「受平台与版本限制，需对照实际版本核验」，不得宣称全平台无条件支持。版本基准始终为「上游 master 快照（2026-11 抓取）」，具体版本号以对应构建文件为准。

### 7. 常见误用与调试

第一个高频误用是把 `priority` 当成启动顺序的唯一依据。实际上在开启 `dependent_startup` 后，真正决定先后的是 `dependent_startup_wait_for`；`priority` 只在没有依赖声明的进程之间起作用。把依赖改到 priority 上，表面上能跑起来，一旦系统负载导致进程就绪变慢，就会拉起尚未准备好的下游进程，产生难以复现的间歇故障。

第二个误用是把 `autorestart` 一律改成 true，以为这样更「健壮」。在 SONiC 的容器模型里，多数业务进程退出后由更高层的容器级机制统一处理，自动重启会掩盖反复崩溃的事实，让 `uptime` 归零这类关键线索消失。正确的做法是先按 `原理见 06-13` 理解容器级重启机制，再决定是否调整。第三个误用是去容器本地找 `stdout_logfile`，而模板里普遍是 NONE 加 syslog 转发，正确的检索入口是系统日志，见 04-08。

第四个误用是把模板文本当成最终配置。Jinja 表达式在渲染时才求值，`{{ swss_priority_base + 4 }}` 在不同场景结果不同；直接拿模板里的字符串当参数值，会得到错误结论。第五个误用是给事件监听器配置过窄的 `events` 集合，漏掉 PROCESS_STATE_FATAL，结果进程进入 FATAL 却无人上报，表现为「业务静默失效」。第六个是忽略 `exitcodes=0,3`，把监听器正常退出误判为异常，引发无意义的重启风暴。

调试建议按固定顺序推进，形成闭环。前置检查：确认目标容器名与配置文件族，读一遍相关 program 段的 command、wait_for、autorestart 三键。执行：用只读命令查看进程状态，记录 RUNNING、EXITED、FATAL 与 uptime。验证输出：把状态与依赖声明逐条对照，确认后起进程的等待对象确实进入了目标状态；对 EXITED 的一次性程序要确认它是按设计退出而非卡死。清理：若临时改过参数，恢复配置并确认容器回到稳定状态，避免把调试态带入生产。全程遵守「配置返回成功不等于进程就绪、更不等于硬件已下发」的边界，涉及 ASIC 编程状态写「原理见 06-01」。性能与容量类结论一律标注「需在目标机型实测」，本篇不给绝对值。

小结：本篇给出了容器服务的三层参数地图——容器入口与配置文件族、supervisord 各类配置键、以及以 `dependent_startup_wait_for` 为核心的启动依赖层；图 04-07-01 把从容器入口到 syncd 编程的启动门槛串成可核对的顺序，两张表分别提供参数字典与现象反查。需要记住的三条纪律是：依赖优先于 priority 决定顺序、多数进程不自动重启、日志进 syslog 而非本地文件。下一篇 04-08 将接着讲这些日志在哪里查、命令返回码如何判读，把本篇留下的检索入口补齐。

## 04-08 日志、返回码与排错速查手册

### 1. 本篇定位与覆盖范围

本篇是 04 参数与 API 手册中收尾的排错速查分册，目标是把散落在多个子仓里的「日志在哪里、命令返回什么码、看到现象往哪里查」三类信息整理成可随查的字典。它与 04-07 是配套关系：04-07 讲进程如何被拉起、日志往哪里转发，本篇接着讲这些日志如何检索、返回码如何判读。本篇只给参数、取值、来源与判读口径，不展开配置流水线的实现机制，机制统一写「原理见 06-01」；不展开容器编排与退出上报的内部状态机，写「原理见 06-13」；不罗列 CLI 模块的逐项能力，写「模块见 07-06」，也不展开 swss 事件监听器的结构体字段，写「字段见 05-08」。

覆盖范围同样分三层。第一层是日志层，包括系统日志的存放路径、`show logging` 命令的过滤参数、日志级别语义、以及 supervisord 事件监听器订阅的进程事件集合。第二层是返回码层，包括 Python CLI 通过 `sys.exit` 抛出的退出码、各工具自定义的返回码常量、以及标准 shell 的约定码。第三层是排错检索层，也就是把「现象 — 查哪条日志 — 看哪个返回码 — 反查哪一段配置」串起来的决策顺序。

事实基准统一为「上游 master 快照（2026-11 抓取）」，路径相对各子仓 `xxx-master/` 仓库根。日志证据主要来自 `sonic-utilities/sonic-utilities-master/show/main.py`、`dockers/` 下各 `supervisord.conf*` 以及 `sonic-swss/sonic-swss-master/orchagent/main.cpp`；返回码常量来自 `sonic-utilities/sonic-utilities-master/` 下 `consutil/lib.py`、`config/main.py`、`cpoutil/main.py`、`psuutil/main.py` 等文件。凡快照内无法核实的日志文案、退出码取值与命令选项，一律标注「需对照实际版本核验」，绝不编造报错文案——排错类内容一旦写入不存在的报错串，会把读者引向错误方向，危害远大于留白。

需要特别强调本篇的边界：它给的是「查什么、怎么判读」的方法与索引，不是故障处置的运维步骤。具体诊断树与案例写「排障见 08-03」「案例见 08-04」，本篇只负责把参数与判读口径备齐，避免在手册册里展开运维场景。

### 2. 索引与全参数表

先给日志检索参数表，按「参数或选项 → 取值 → 默认值 → 作用 → 误配后果」组织，依据 `sonic-utilities-master/show/main.py` 中 `logging` 命令的实现整理。表中路径与选项需对照实际版本核验，凡涉及具体文件是否存在的判断，以目标设备实际状态为准。

| 参数或选项 | 取值 | 默认值 | 作用 | 误配后果 |
|---|---|---|---|---|
| log_path | /var/log.tmpfs 或 /var/log | 依 tmpfs 是否存在 | 决定从哪个目录读 syslog | 路径判断错误会读到空日志或旧日志 |
| process | 进程名字符串 | 无 | 作为 grep 过滤关键字筛出某进程日志 | 关键字过宽混入无关行，过窄漏掉关键行 |
| -l 或 --lines | 整数 | 无 | 用 tail 取最后若干行 | 取值过小截断最早的错误，过大淹没重点 |
| -f 或 --follow | 标志位 | 关闭 | 用 tail -F 持续跟随日志 | 长时间跟随会占用会话，误当命令卡死 |
| --verbose | 标志位 | 关闭 | 打印实际执行的命令串 | 关闭时难确认过滤条件是否如预期 |
| syslog.1 | 文件名 | 存在才纳入 | 上一轮轮转的日志，一并纳入检索 | 忽略它会漏掉重启前的错误线索 |
| stdout_syslog | true / false | true | 进程标准输出是否进 syslog | 关闭后对应进程日志在检索中消失 |
| stderr_syslog | true / false | true | 进程标准错误是否进 syslog | 关闭后异常堆栈查不到 |
| exitcodes | 逗号分隔整数 | 0,3 | 事件监听器认定正常的退出码 | 漏配会把正常退出当异常上报 |
| events | 事件名逗号分隔 | PROCESS_STATE 等 | 监听器订阅的进程事件集合 | 漏订 FATAL 会错过致命退出 |

再给日志级别表，按 C++ 侧 `SWSS_LOG_*` 宏的常见级别整理，级别名可在 `sonic-swss-master/orchagent/main.cpp`、`sonic-sairedis-master/syncd/syncd_main.cpp` 中找到调用实例，宏定义本体所在的 `sonic-swss-common` 不在本快照，需对照实际版本核验。

| 级别 | 语义 | 典型场景 | 排障权重 |
|---|---|---|---|
| ERROR | 错误，操作失败 | 初始化失败、通知 syncd 失败、参数非法被忽略 | 最高，需优先定位 |
| WARN | 警告，可能影响功能 | 取值越界被限制、容量上限告警 | 中高，结合上下文判断 |
| NOTICE | 重要正常事件 | 启动里程碑、APPLY_VIEW 通知、批量参数设置 | 中，用于确认链路走通 |
| INFO | 一般信息 | 常规流程进展 | 低，用于还原时间线 |
| DEBUG | 调试信息 | 内部结构、逐项细节 | 低，默认通常不开启 |

最后给返回码速查表。这是本篇最需要克制的部分：同一个数字在不同工具里含义不同，必须从源码常量反查，不能套用通用 shell 约定。下表按「返回码 → 符号或出处 → 语义 → 判读要点」组织，符号与取值可在对应文件核实。

| 返回码 | 符号或出处 | 语义 | 判读要点 |
|---|---|---|---|
| 0 | 多处默认成功 | 命令执行成功 | 只代表该命令这一段成功，不代表硬件已下发 |
| 1 | ERR_DISABLE（consutil/lib.py） | 控制台相关功能被禁用 | 与同值的其它常量靠出处区分 |
| 1 | CONFIG_RELOAD_NOT_READY（config/main.py） | 配置重载条件未就绪 | 多为时序问题，需确认前置流程完成 |
| 1 | ERROR_PERMISSIONS（cpoutil、psuutil） | 权限不足 | 核对执行身份，不要盲目重试 |
| 2 | ERR_CMD（consutil/lib.py） | 命令不被接受 | 核对参数拼写与支持的子命令 |
| 2 | ERROR_CHASSIS_LOAD（psuutil/main.py） | 机箱信息加载失败 | 多与平台插件相关，受平台与版本限制 |
| 3 | ERR_DEV（consutil/lib.py） | 设备相关错误 | 核对目标设备是否存在或可用 |
| 4 | ERR_CFG（consutil/lib.py） | 配置错误 | 回到 CONFIG_DB 对应表项核对 |
| 5 | ERR_BUSY（consutil/lib.py） | 资源忙 | 多为并发占用，需确认无其它会话 |

使用三张表时有一条统一纪律：返回码必须连同「出处」一起读。脱离文件只谈「返回 1」没有意义，因为 consutil 的 ERR_DISABLE、config 的 CONFIG_RELOAD_NOT_READY 与 psuutil 的 ERROR_PERMISSIONS 都是 1，语义完全不同。这也是本篇把「符号或出处」单列一列的原因。

### 3. 逐项详解

先讲日志路径的选择逻辑。`sonic-utilities-master/show/main.py` 的 `logging` 命令在入口处判断 `/var/log.tmpfs` 是否存在：存在则以它为基础路径，否则用 `/var/log`。这个判断意味着同一条 `show logging` 在不同运行状态下可能读不同目录，排障时若发现日志「突然变少」，第一反应应是确认基础路径是否发生了切换，而不是急于断定进程没打日志。随后代码把 `syslog.1` 在存在时排在 `syslog` 之前，一起交给 `sudo cat`；这保证轮转前后的日志都能被检索到，忽略 `syslog.1` 会漏掉重启前的错误线索。

再讲过滤与跟随。`process` 参数被转成 `grep -h -- <process>`，其中 `-h` 让多文件检索时输出不带文件名，`--` 防止以减号开头的进程名被当成 grep 选项；`lines` 参数转成 `tail -n <n>`，放在管道末端。`-f` 分支不同，它直接执行 `sudo tail -F <path>/syslog` 并立即返回，不叠加 grep 与 tail，因此跟随模式下无法用进程名过滤，这是使用上的重要限制。`--verbose` 会把上述命令串打印出来，在结果为空或不符预期时，开启它是确认「过滤条件到底有没有生效」的最快办法。命令实现中特意让 `cat` 以 sudo 运行、而 `grep` 与 `tail` 以调用者身份运行，缩小了用户输入的进程名以 root 执行的风险面。

然后讲日志级别与事件。`SWSS_LOG_*` 系列宏在 orchagent 与 syncd 中大量使用：`main.cpp` 里 `SWSS_LOG_NOTICE("Notify syncd APPLY_VIEW")` 表示进入下发视图的正常里程碑，紧随其后的 `SWSS_LOG_ERROR("Failed to notify syncd APPLY_VIEW %d", status)` 表示这一步失败，两者成对出现，是判断编排是否走通的关键信号。同类还有 `SWSS_LOG_ERROR("Invalid switch type %s configured")`、`SWSS_LOG_WARN("ASIC instance_id length > SAI_MAX_HARDWARE_ID_LEN, LIMITING !!")` 等，分别对应配置非法与取值被限制。事件侧，`supervisord.conf.j2` 的 `supervisor-proc-exit-listener` 订阅 PROCESS_STATE_EXITED、PROCESS_STATE_RUNNING、PROCESS_COMMUNICATION_STDOUT、PROCESS_STATE_FATAL，配合 `exitcodes=0,3`，构成「哪些退出算正常、哪些要上报」的判定口径。程序内部的日志级别细节属于实现，写「原理见 06-01」；事件监听器的数据结构写「字段见 05-08」。

最后讲返回码的三类来源。第一类是 Python CLI 的 `sys.exit`：它既可能接收整数，也可能接收字符串，接收字符串时 shell 看到的退出码通常为 1，并把字符串打印到标准错误，因此「看到一段文字报错」和「返回 1」常常是同一件事的两面。第二类是模块级常量，`consutil/lib.py` 定义 ERR_DISABLE=1、ERR_CMD=2、ERR_DEV=3、ERR_CFG=4、ERR_BUSY=5；`config/main.py` 定义 CONFIG_RELOAD_NOT_READY=1；`cpoutil/main.py` 与 `psuutil/main.py` 定义 ERROR_PERMISSIONS=1，后者还定义 ERROR_CHASSIS_LOAD=2；`config/kdump.py` 中直接出现 `sys.exit(1)` 与 `sys.exit(2)`。第三类是 supervisord 侧的 `exitcodes=0,3`，它不面向终端用户，而是决定事件监听器是否触发重启策略。三类的作用域互不统属，跨类比较数值没有意义。

逐行判读如下。第一条命令用进程名 orchagent 作过滤、取最后 50 行，`-l` 对应源码中的 `--lines`，把结果交给 `tail -n 50`；第二条加 `--verbose`，会先打印实际执行的命令串，便于确认过滤条件，同样按进程名过滤 20 行；第三条 `-f` 进入跟随模式，按实现直接对 syslog 执行 `tail -F`，不再叠加进程过滤，因此看不到进程名筛选，这是使用限制而非故障。输出第一行是 NOTICE 级别的 `Notify syncd APPLY_VIEW`，表示编排侧进入下发视图，是正常里程碑；第二行 INFO 说明异步记录与路由状态发布已启用，属常规信息。第三行 NOTICE 给出 bulk size 取 128，说明批量模式生效。第四行是关键：ERROR 级且文案含 `Invalid input` 与 `use default interval`，含义是本次传入的心跳间隔参数非法，系统已回退到默认值 1000，属「参数被忽略并降级」而非致命故障，需回头查参数来源。第五行同样是 ERROR，`Failed to notify syncd APPLY_VIEW 1` 中的 1 是底层返回的状态值，需对照实际版本核验其确切含义，但不能忽略——它直接说明通知 syncd 这一步失败，应结合 `原理见 06-05` 继续查 syncd 侧日志。第六行 NOTICE 确认回退后的心跳间隔已设为 1000，与第四行形成因果印证。整体上，NOTICE 标记链路走通、ERROR 标出参数非法与通知失败两类问题，判读时要把它们按时间顺序串起来，而不是孤立看某一条；同时这些都是控制面日志，即便全部正常也不代表 ASIC 已编程，仍须按图 04-08-01 右半段逐段核对。

再看一组返回码核验，用标准 shell 变量读取上一条命令的退出状态，输出同样注明需对照实际版本核验。

```bash
config reload -y
echo "exit=$?"
```

```text
示例输出，具体格式需对照实际版本核验（退出码取值与输出文案仅为格式示意）
Running command: /usr/bin/config reload -y
[中间重启日志省略]
exit=1
```

逐行判读如下。前置检查阶段先确认命令名与参数在当前版本是否存在，命令全集写「完整命令见 04-05」；执行阶段运行 `config reload -y`，随后立刻用 `$?` 读取退出码——必须在下一条命令之前读取，否则会被后续命令的退出码覆盖。输出首行是命令回显，说明命令被接受并开始执行；末行 `exit=1` 是本组的关键：单独看「1」没有意义，必须结合出处判断。在 `config/main.py` 中，CONFIG_RELOAD_NOT_READY 被定义为 1，并在多处 `sys.exit(CONFIG_RELOAD_NOT_READY)` 使用，因此这里的 1 更可能指向「重载条件未就绪」这类时序问题，而不是笼统的「执行失败」。正确的下一步是确认前置流程是否完成、是否有其它会话占用，再决定是否重试，而不是简单重跑命令。若退出码为 2，在 consutil 语境下对应 ERR_CMD（命令不被接受），在 psuutil 语境下却对应 ERROR_CHASSIS_LOAD（机箱信息加载失败）——同一个数字因出处不同而语义迥异，这正是返回码必须与出处一起读的实证。清理阶段确认没有遗留的半配置状态，再决定后续动作。

### 5. 速查表

下表把高频现象压成「现象 → 首选检索 → 关键判据 → 反查去向」四列，供现场快速定位。表中反查去向只给到手册篇号，具体诊断树写「排障见 08-03」、案例写「案例见 08-04」。

| 现象 | 首选检索 | 关键判据 | 反查去向 |
|---|---|---|---|
| 配置命令返回成功但不生效 | 按库逐段查表项 | 期望状态与对象是否生成 | 原理见 06-01 |
| 日志里出现 APPLY_VIEW 失败 | show logging orchagent | 是否伴随 ERROR 级通知失败 | 原理见 06-05 |
| 参数被忽略并回退默认 | 查 ERROR 含 use default | 回退后的 NOTICE 是否出现 | 原理见 06-04 |
| 进程进入 FATAL 无感知 | supervisorctl 查状态 | events 是否漏订 FATAL | 原理见 06-13 |
| show logging 结果为空 | 核对 log_path 目录 | tmpfs 路径是否存在 | 模块见 07-06 |
| 跟随模式无法按进程过滤 | 理解 -f 分支实现 | -f 是否绕开 grep | 模块见 07-06 |
| 返回码 1 语义不明 | 按出处查常量 | 出自哪个模块文件 | 本册第 2 节 |
| 多 ASIC 场景日志不全 | 核对命名空间 | 是否查错实例目录 | 原理见 06-11 |

使用速查表要防止两种误判。一是把「日志里没有 ERROR」等同于「没有问题」：NOTICE 里程碑缺失同样能定位卡点，例如在预期位置看不到 APPLY_VIEW，就说明链路没走到那一步。二是把「命令返回 0」等同于「硬件已下发」：CLI 只读写配置库，返回 0 仅代表该命令这一段成功，这一点在本套资料中反复强调，排障时必须坚持按库逐段核对。

### 6. 版本差异

日志与返回码的版本差异集中在四个方向。第一，日志路径实现会演进：`show logging` 对 `/var/log.tmpfs` 的判断、是否纳入 `syslog.1`、以及 `grep` 与 `tail` 的特权边界，都是 `show/main.py` 中的具体实现，不同分支可能调整，需对照实际版本核验。第二，进程事件集合与退出码集合会变化：`supervisord.conf.j2` 中 `events` 列出的事件名、`exitcodes=0,3` 的取值，在不同容器、不同版本并不完全一致，telemetry 容器的 rsyslogd 段就与 swss 容器取不同 autorestart 策略。

第三，返回码常量是模块私有定义，不存在跨版本的统一表：consutil、config、cpoutil、psuutil、pddf 系列工具各自定义自己的错误码，同名常量在新增或下线工具时可能改变取值，本篇表格只反映本快照可核实的状态。第四，日志级别与文案随代码改动：`SWSS_LOG_*` 调用的字符串是开发时写入的，版本间可能增删改，排障时不能把某条文案当作稳定契约，只能当作当前版本的线索；宏定义所在的 `sonic-swss-common` 不在本快照，涉及宏本身的实现需对照实际版本核验。

此外，多 ASIC 命名空间、chassis 与 warm reboot 场景下的日志目录与实例划分「受平台与版本限制，需对照实际版本核验」，不得用单机假设套用。版本基准始终为「上游 master 快照（2026-11 抓取）」，具体版本号与文案以对应源码文件为准。凡本快照无法核实的内容，宁可标注核验要求并给出 `show/`、`dockers/`、`orchagent/`、`consutil/` 等可定位目录，也不补值。

### 7. 常见误用与调试

第一个高频误用是把返回码当通用约定读，看到 1 就认定「一般错误」、看到 2 就认定「用法错误」。在 SONiC 里，同一数字在不同工具中语义不同，必须连同出处一起判断；脱离 `consutil/lib.py`、`config/main.py`、`psuutil/main.py` 这样的来源，返回码就失去了意义。第二个误用是把 `config` 命令返回 0 等同于配置已在硬件生效，忽略从 `CONFIG_DB` 到 `ASIC_DB` 的异步流水线，结果在配置确实写入、但期望状态未生成时误判为正常，正确做法是按图 04-08-01 逐段核对，机制写「原理见 06-01」。

第三个误用是只搜 ERROR 级日志，忽略 NOTICE 里程碑的缺失或顺序错乱。在异步链路里，「本该出现的 NOTICE 没出现」往往比一条 ERROR 更能精确定位卡在哪一段。第四个误用是在跟随模式下仍期待进程过滤，发现 `-f` 输出里没有过滤效果就以为命令坏了，实际上按源码实现 `-f` 分支直接跟随 syslog，本就不叠加 grep。第五个误用是忽略 `syslog.1`，只看当前 syslog，结果漏掉轮转前的错误线索，尤其在设备刚重启后这一点格外关键。第六个误用是误改 `exitcodes` 或收窄 `events`，把正常退出当异常上报，或让 FATAL 静默，引发误重启或漏报。

调试同样按闭环推进。前置检查：确认命令名、选项与进程名在当前版本存在，记下要用的返回码出处文件。执行：先用 `show logging` 加 `--verbose` 取一段带命令串的日志，再用 `supervisorctl` 查关键进程状态，命令类问题则记录 `$?`。验证输出：把日志中的 NOTICE 里程碑按时间排开，确认链路走到哪一步；对 ERROR 行逐条分清是「参数被忽略并回退」的降级，还是「通知失败」这类实质故障；对返回码按出处还原语义。清理：撤销调试期开启的 verbose 等临时设置，确认无遗留会话与半配置状态，恢复稳定后再下结论。全程遵守「命令成功不等于硬件已下发」「日志正常不等于转发正常」两条边界；一切收敛时间、下发时延、吞吐类结论标注「需在目标机型实测」，本篇不给绝对值。

小结：本篇把日志检索参数、日志级别、返回码常量三张表与一张检索路径图整合为排错速查入口，图 04-08-01 给出从现象到逐段配置核对的决策顺序。三条纪律需要牢记：返回码必须与出处一起读、NOTICE 缺失同 ERROR 一样重要、命令返回成功不代表硬件已下发。至此 04 参数与 API 手册八个分册齐备，从构建变量、CONFIG_DB schema、Redis 对象、命令全集、SAI 与 orchagent 参数，到容器服务与本篇的日志返回码，构成一套可被逐项反查的参数字典；字段随查走 05 册，机制走 06 册，模块走 07 册，运维判读与案例走 08 册。
