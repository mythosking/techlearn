# SONiC 技术资料 · 07 模块与特性介绍（分片 A）
## 07-01 sonic-buildimage 顶层与构建规则模块

### 1. 模块定位与职责边界

07 册是整套资料里「模块功能与目录归属的唯一权威源」，而 07-01 是这个权威源的起点：它讲的是 `sonic-buildimage-master/` 这个**主仓**的顶层骨架与构建规则模块。必须先立住一个判断——sonic-buildimage 不是「装了 SONiC 的那个镜像」，而是**产出镜像的构建主仓**；它自身既不是运行时控制面进程，也不是数据面转发体，它的全部职责就是把分散在多个子仓里的源码、配置模板与平台文件，按一套 Makefile 规则编排、编译、打包，最终产出可安装的 ONIE 镜像与一组 Docker 容器归档（模块见 07-02 ｜ 模块见 07-11）。读者若把构建主仓与运行时容器混为一谈，后面所有「这个目录归谁」的判断都会错位。

从模块边界看，本篇只负责三块：顶层总控文件（`Makefile`、`Makefile.work`、`slave.mk`、`functions.sh` 等）、构建规则目录（`rules/` 下的 `.mk` 与 `.dep` 文件族），以及 orchestrate 这些规则的脚本入口（`build_image.sh`、`build_docker.sh`、`build_debian.sh`、`push_docker.sh` 等）。三块之外的内容都有各自明确的归属：容器镜像内部的 `Dockerfile.j2` 与 `supervisord.conf.j2` 归 07-02；`files/image_config/`、`onie-image.conf`、`installer/` 的开机配置与安装器归 07-11；`platform/`、`device/<vendor>/<hwsku>/` 与 HWSKU 适配归 07-10；`scripts/`、`tools/`、`azure-pipelines.yml` 的 CI 基础设施归 07-13。本篇在遇到这些边界时会明确写出「模块见 07-xx」，而不越过边界展开。

第二个边界是「多子仓」。`upstream_src/` 下共有 8 个子仓，每个子仓解压后还带一层 `xxx-master/` 归档目录，sonic-buildimage 只是其中之一，也是唯一被称作「主仓」的那个；orchagent、syncd、CLI、YANG 等能力分别来自 `sonic-swss`、`sonic-sairedis`、`sonic-utilities`、`sonic-mgmt-common` 等子仓，通过子模块与主仓的 rules 被拉入构建。FRR / FRRouting 源码、Linux 内核、厂商 SAI 实现与 `sonic-swss-common` 均不在本快照，涉及它们一律写「不在本快照，需对照实际版本核验」（模块见 07-05 ｜ 模块见 07-08）。因此本篇讲「构建规则怎么组织」，不讲「被构建的某个源文件内部怎么实现」。

第三个边界是构建环境本身。SONiC 镜像**不能**在普通主机上裸 `make` 得到：构建变量与 `PLATFORM` 类开关的完整清单见 04-01，构建机制与 slave 容器原理见 02-02；本篇只把顶层与 `rules/` 当作一个「目录与文件归属」问题来回答——这个目录有什么、每个文件干什么、边界在哪、怎么被装配进一次构建。具体变量名与默认值一律不在此重列，写「参数见 04-01」。版本基准统一为「上游 master 快照（2026-11 抓取）」，不写绝对版本号。

### 2. 目录与文件清单

下表是本篇的回查主干，按「文件/目录 → 职责 → 关键入口」三列给出顶层与构建规则模块的核心成员；表中路径均相对 `sonic-buildimage-master/` 仓库根，函数名与变量名为本快照可核验名称，完整签名与取值需对照实际版本核验。

| 文件/目录 | 职责 | 关键入口 |
|---|---|---|
| `Makefile` | 顶层总控，按发行版分派到 `Makefile.work` | `%::` 模式规则、`PLATFORM_PATH` |
| `Makefile.work` | 工作层 make，驱动 slave 容器内构建 | 由顶层 `make -f` 调用 |
| `slave.mk` | 定义路径与产出物变量，装配所有 target | `SRC_PATH`、`RULES_PATH`、`TARGET_PATH` |
| `rules/config` | 构建系统配置参数（是文件不是目录） | `SONIC_CONFIG_BUILD_JOBS` |
| `rules/*.mk` | 单个软件/镜像的构建规则 | `$(TARGET)_DEPENDS`、`_PATH` |
| `rules/*.dep` | 对应 `.mk` 的依赖声明 | 与同名 `.mk` 配对 |
| `functions.sh` | 复用 shell 函数库 | `sonic_get_version()`、`die()` |
| `build_image.sh` | 生成 ONIE 安装镜像 | `generate_kvm_image()` |
| `build_docker.sh` | 准备并可选推送 Docker 镜像 | `usage()`、`-i`/`-t` 选项 |
| `build_debian.sh` | 构造 Debian 文件系统与 deb 包 | 由 slave 构建链路调用 |
| `push_docker.sh` | 镜像推送到 registry | 由 CI 与发布链路调用 |
| `sonic-slave-*/` | 各发行版构建容器定义 | `Dockerfile.j2` |
| `dockers/` | 容器族定义目录（归属 07-02） | 各 `docker-*/` 子目录 |
| `scripts/` | 构建辅助脚本（归属 07-13） | `run_with_retry`、`build-dep-graph.py` |

先读顶层。本快照可核验的顶层文件包括 `Makefile`、`Makefile.work`、`Makefile.cache`、`slave.mk`、`functions.sh`、`rules/`、`dockers/`、`device/`、`platform/`、`files/`、`installer/`、`src/`、`tests/`、`tools/`、`scripts/`、`sonic-slave-*/` 六个发行版目录，以及 `onie-image.conf`、`onie-image-arm64.conf`、`onie-image-armhf.conf`、`onie-mk-demo.sh`、`build_image.sh`、`build_docker.sh`、`build_debian.sh`、`build_debug_docker_j2.sh`、`push_docker.sh`、`get_docker-base.sh`、`check_install.py`、`install_sonic.py`、`pytest.ini`、`azure-pipelines.yml`、`update_screen.sh`、`validated-submodule-commits`、`vex/` 与多份 `README.*`。其中 `validated-submodule-commits` 是子模块版本的核验锚点，但具体取值需对照实际版本核验，不据此编造版本号（参数见 04-01 ｜ 模块见 07-13）。

再看 `rules/`。本快照里这个目录是「一个目标一对文件」的密集规则集合：每个软件或镜像通常同时有一个 `.mk`（定义变量与规则）和一个 `.dep`（声明依赖），例如 `docker-orchagent.mk` 与 `docker-orchagent.dep`、`docker-database.mk` 与 `docker-database.dep`、`docker-fpm-frr.mk`、`docker-snmp.mk`、`docker-teamd.mk`、`docker-lldp.mk`、`docker-nat.mk`、`docker-macsec.mk`、`docker-platform-monitor.mk`、`docker-router-advertiser.mk`，以及非容器目标如 `swss.mk`、`swss-common.mk`、`syncd.mk`、`sonic-utilities.mk`、`telemetry.mk`、`supervisor.mk`、`thrift.mk`、`wpasupplicant.mk` 等；还有成组的发行版基础规则 `docker-base-*.mk`、`docker-config-engine-*.mk`、`docker-swss-layer-*.mk`。需要纠正一个易错点：规范文档里曾把 `rules/config` 写作目录，但本快照里它**是一个约 21 KB 的普通文件**，内容为构建系统配置参数，顶部注释为「Configuration parameters for SONiC build system」，含 `SONIC_CONFIG_PRINT_DEPENDENCIES` 与 `SONIC_CONFIG_BUILD_JOBS` 等开关；全文按文件对待，不编造 `rules/config/` 下的子文件（参数见 04-01）。

`sonic-slave-*/` 这一组目录是构建容器的定义，本快照可核验到 `sonic-slave-bookworm/`、`sonic-slave-bullseye/`、`sonic-slave-trixie/`、`sonic-slave-buster/`、`sonic-slave-stretch/`、`sonic-slave-jessie/` 六个，每个目录至少含一个 `Dockerfile.j2`（如 `sonic-slave-bookworm/` 下还可核验到 `pip.conf`、`disable-non-manylinux.patch`、`sonic-jenkins-id_rsa.pub`）。顶层 `Makefile` 用 `NOJESSIE`、`NOSTRETCH`、`NOBUSTER`、`NOBULLSEYE`、`NOBOOKWORM`、`NOTRIXIE` 六个开关决定参与构建的发行版集合，本快照里 bookworm 与 trixie 的默认值使二者参与、其余默认关闭；这是一组**构建矩阵开关**而非运行时特性开关，误配后果见 04-01，不在本篇展开（模块见 07-11 ｜ 参数见 04-01）。

### 3. 关键类与入口函数

构建系统不像 C++ 模块那样有「类」，本节的「关键类」按 make 目标、shell 函数与脚本入口三点名，只给真实路径与名称，不展开实现。结构字段统一在 05 册：涉及平台文件 `platform.json` 的字段写「字段见 05-09」，构建变量全集写「参数见 04-01」，构建机制写「原理见 02-02 ｜ 原理见 06-13」，模块归属写「模块见 07-02 ｜ 模块见 07-11」。本节的统一写法为（字段见 05-09 ｜ 参数见 04-01 ｜ 原理见 02-02 ｜ 模块见 07-02）。这样处理是为了让本篇聚焦「入口在哪、归谁所有」，而不是把变量表与字段表提前铺开。

顶层入口是 `Makefile` 的 `%::` 模式规则。本快照可核验到该规则以 `$(MAKE_WITH_RETRY)` 包裹，其中 `MAKE_WITH_RETRY := ./scripts/run_with_retry $(MAKE)`；规则按发行版分支，用 `$(MAKE) EXTRA_DOCKER_TARGETS=... -f Makefile.work <distro>` 的形式把控制权交给 `Makefile.work`。同文件里可核验到 `PLATFORM_PATH := platform/$(if $(PLATFORM),$(PLATFORM),$(CONFIGURED_PLATFORM))`、`PLATFORM_CHECKOUT := platform/checkout` 与 `BAZEL_MIN_READINESS` 的 trixie-only 校验分支——后者会在非 trixie 组合下直接 `$(error ...)` 失败，是「构建矩阵开关相互约束」的真实例子（参数见 04-01 ｜ 模块见 07-10）。

第二层入口是 `slave.mk`。本快照开头即声明 `.ONESHELL`、`SHELL = /bin/bash`、`.SHELLFLAGS += -e`，并用 `id -un`/`id -u`/`id -g` 取 `USER`/`UID`/`GUID`；当 `SONIC_IMAGE_VERSION` 为空时，它导出 `BUILD_TIMESTAMP`、`BUILD_NUMBER` 后 `. functions.sh` 并调用 `sonic_get_version` 生成版本号。紧随其后的路径变量组构成本模块最重要的「装配骨架」：`SRC_PATH = src`、`RULES_PATH = rules`、`TARGET_PATH = target`、`DOCKERS_PATH = dockers`、`BLDENV := $(shell lsb_release -cs)`，以及 `DEBS_PATH`、`FILES_PATH`、`PHONY_PATH`、`PYTHON_DEBS_PATH`、`PYTHON_WHEELS_PATH`、`PROJECT_ROOT`。这些变量说明一件事：所有构建产物按 `target/<类型>/<发行版>/` 分层落位，发行版由 `lsb_release -cs` 在构建容器内解析，而非写死（原理见 02-02 ｜ 参数见 04-01）。

第三层是 shell 函数与脚本入口。`functions.sh` 在本快照可核验到 `_trap_push()`、`warn()`、`die()`、`docker_try_rmi()`、`sonic_get_version()` 五个函数，其中 `sonic_get_version()` 被 slave.mk 直接复用。`build_image.sh` 顶部注释写明「generate an ONIE installer image based on a file system overload」，它把 `$PASSWORD` 取出后 `unset`，从 `.arch` 或默认 `amd64` 读 `CONFIGURED_ARCH`，再按架构选择 `platform/${CONFIGURED_PLATFORM}/onie-image-${CONFIGURED_ARCH}.conf` 或 `./onie-image.conf`，并强制校验 `ONIE_IMAGE_PART_SIZE` 与 `INSTALLER_PAYLOAD` 非空，否则 `exit 1`；其中可核验到 `generate_kvm_image()` 函数以 `NUM_ASIC`、`BOOT_FIRMWARE` 为参数。`build_docker.sh` 以 `set -e` 与 `. ./functions.sh` 开头，`usage()` 给出 `-i`（镜像名）、`-t`（镜像 tag）、`DOCKER_BUILD_DIR` 与可选 registry 参数。以上函数签名与选项的完整形式需对照实际版本核验（模块见 07-11 ｜ 模块见 07-13）。

### 4. 对外接口与扩展点

本模块对外的「接口」不是函数调用，而是三类可被上层或其他模块消费的契约。第一类是 make 目标与全局变量：外部通过 `make <target>`、`PLATFORM=<name>`、`SONIC_CONFIG_BUILD_JOBS=<n>` 等入口驱动构建，完整变量与默认值不在本篇重列，一律引用 04-01（参数见 04-01）。第二类是给 `dockers/` 与 `src/` 提供装配入口：`slave.mk` 的 `RULES_PATH = rules`、`DOCKERS_PATH = dockers` 把 `rules/*.mk` 与 `dockers/*/` 两个目录正式纳入构建图，07-02 讲解的每个容器目录正是经此被找到（模块见 07-02）。第三类是给平台与镜像模块提供变量载体：`PLATFORM_PATH` 指向 `platform/<name>/`，`onie-image.conf` 系列由 `build_image.sh` 读取，二者分别是 07-10 与 07-11 的接入点（模块见 07-10 ｜ 模块见 07-11）。把总控、规则、构建容器、容器模板到镜像归档的装配关系串起来，就得到图 07-01-01。

图 07-01-01 用颜色区分职责：purple 为顶层总控，teal 为构建规则与模板，gray 为辅助的构建容器与源码目录，amber 为编译产物与镜像归档，green 为镜像装配脚本，red 为最终交付的 ONIE 镜像边界。需要强调的是 `dockers/` 在本图中的位置：它作为「源码与模板目录」经 `DOCKERS_PATH` 被 `rules/*.mk` 引用，其内部的 `Dockerfile.j2` 才真正被渲染成镜像，因此本篇只把 `dockers/` 当作一个被装配的目录，内部细节留给 07-02（模块见 07-02 ｜ 原理见 02-02）。

扩展点最典型的是「新增一个镜像目标」。以本快照的 `rules/docker-orchagent.mk` 为例，它先声明 `DOCKER_ORCHAGENT_STEM = docker-orchagent` 与产物名 `DOCKER_ORCHAGENT = $(DOCKER_ORCHAGENT_STEM).gz`、`DOCKER_ORCHAGENT_DBG = $(DOCKER_ORCHAGENT_STEM)-$(DBG_IMAGE_MARK).gz`，再用一组「目标特定变量」描述装配关系：`$(DOCKER_ORCHAGENT)_DEPENDS += $(SWSS) ...`、`$(DOCKER_ORCHAGENT)_PATH = $(DOCKERS_PATH)/$(DOCKER_ORCHAGENT_STEM)`、`$(DOCKER_ORCHAGENT)_LOAD_DOCKERS += $(DOCKER_SWSS_LAYER_TRIXIE)`、`$(DOCKER_ORCHAGENT)_VERSION = 1.0.0`、`$(DOCKER_ORCHAGENT)_PACKAGE_NAME = swss`、`$(DOCKER_ORCHAGENT)_CONTAINER_NAME = swss`。最后通过追加到 `SONIC_DOCKER_IMAGES`、`SONIC_TRIXIE_DOCKERS`、`SONIC_INSTALL_DOCKER_IMAGES`（以及各自的 `_DBG_` 变体）把目标登记进不同清单。这套「STEM → 目标变量 → 清单登记」的三步，就是本模块对容器族的标准扩展范式（模块见 07-02 ｜ 参数见 04-07）。

第二组扩展点是关停顺序与运行参数。`docker-orchagent.mk` 里可核验到 `$(DOCKER_ORCHAGENT)_WARM_SHUTDOWN_BEFORE = syncd`、`$(DOCKER_ORCHAGENT)_FAST_SHUTDOWN_BEFORE = syncd`；`docker-fpm-frr.mk` 里可核验到 `$(DOCKER_FPM_FRR)_CONTAINER_NAME = bgp` 以及 `WARM_SHUTDOWN_BEFORE = swss`、`WARM_SHUTDOWN_AFTER = radv`；`docker-teamd.mk` 里是 `CONTAINER_NAME = teamd`、`WARM_SHUTDOWN_BEFORE = syncd`、`WARM_SHUTDOWN_AFTER = swss`。这些「before/after」变量把容器间的关停依赖显式化，机制由容器编排讲，本篇只确认它们落在 `rules/` 的归属（原理见 06-13 ｜ 模块见 07-02）。运行参数方面，`_RUN_OPT` 追加了 `--cap-add=NET_ADMIN` 与若干只读/可写卷挂载（如 `/etc/sonic:ro`、`/var/log/swss:rw`、`/zmq_swss:rw`），完整启动参数见 04-07（参数见 04-07）。第三组扩展点是调试变体：`DBG_IMAGE_MARK`、`*_DBG_DEPENDS`、`*_DBG_IMAGE_PACKAGES` 与 `build_debug_docker_j2.sh` 构成 debug 镜像链路，调试产物不作生产基准（模块见 07-13 ｜ 性能基准见 08-01）。

### 5. 典型用法与调用示例

本节给两组最小实例：一组用 `ls` 实际列出本模块的真实文件清单并作逐行判读，一组给出 `rules/docker-orchagent.mk` 的片段以印证「目标变量 + 清单登记」的扩展范式。完整构建变量见 04-01，容器启动参数见 04-07，本册不重列。所有命令需在具备相应权限与目录可读的环境下执行，路径与产物名需对照实际版本核验。

逐行判读如下。第一段 `ls -d` 同时确认 `Makefile`、`slave.mk`、`rules`、`dockers` 四个名字存在，输出四个名字并列，说明「顶层总控 + 构建规则 + 容器目录」三件套齐备；若其中任一缺失，说明当前目录不是构建主仓根或快照不完整，应先回到 `upstream_src/sonic-buildimage/sonic-buildimage-master/` 定位，而不是继续查构建。第二段 `ls -1` 列出五个总控文件名，`Makefile`、`Makefile.work`、`Makefile.cache`、`slave.mk`、`functions.sh` 同时出现，印证第 2 节所述「顶层总控 → 工作层 → 变量装配 → 函数库」的分层；这里 `Makefile.cache` 的存在还说明构建系统带缓存机制，其细节归 07-13。第三段列出 `rules/` 的成员，`rules/config`、一对 `docker-orchagent.mk`/`.dep` 与 `docker-database.mk` 都在，印证「一目标一对 `.mk`/`.dep`」的组织方式，也说明 database 容器同样由规则文件声明。最后一段 `ls -ld rules/config` 是关键辨伪：输出以 `-rw-r--r--` 开头，`-` 表示普通文件而非目录，大小约 21 KB，直接证明 `rules/config` 是配置文件不是 `rules/config/` 目录——这是最容易被规范文字误导的一处，必须以实际 `ls -ld` 为准。整个查询为只读探查，不改动任何构建状态，也不进入 slave 容器（参数见 04-01 ｜ 模块见 07-13）。

第二组给出规则片段，用来印证「目标变量 + 清单登记」的形态；下列片段依据本快照 `rules/docker-orchagent.mk` 中可核验的变量整理，为便于阅读做了节选，完整清单需对照实际版本核验。

```text
# 片段示意，依据 rules/docker-orchagent.mk 中可核验的变量整理；完整清单需对照实际版本核验
DOCKER_ORCHAGENT_STEM = docker-orchagent
DOCKER_ORCHAGENT = $(DOCKER_ORCHAGENT_STEM).gz
$(DOCKER_ORCHAGENT)_PATH = $(DOCKERS_PATH)/$(DOCKER_ORCHAGENT_STEM)
$(DOCKER_ORCHAGENT)_VERSION = 1.0.0
$(DOCKER_ORCHAGENT)_CONTAINER_NAME = swss
SONIC_DOCKER_IMAGES += $(DOCKER_ORCHAGENT)
SONIC_INSTALL_DOCKER_IMAGES += $(DOCKER_ORCHAGENT)
```

这段说明三件事：产物名由 `STEM` 加 `.gz` 后缀派生，说明容器镜像以归档形态交付；`_PATH` 用 `$(DOCKERS_PATH)/$(STEM)` 拼接，正是 `slave.mk` 里 `DOCKERS_PATH = dockers` 与容器目录名对接的地方；最后两行把目标追加到 `SONIC_DOCKER_IMAGES` 与 `SONIC_INSTALL_DOCKER_IMAGES`，前者决定构建、后者决定进入安装镜像（模块见 07-02 ｜ 模块见 07-11）。读真实的 `.mk` 时，应重点看 `_DEPENDS`、`_LOAD_DOCKERS`、`_DBG_DEPENDS` 如何把 07-02 与 07-05 的模块拉进同一张构建图，以及关停顺序变量如何与 06-13 的容器编排对应（字段见 05-09 ｜ 参数见 04-07）。

### 6. 与其他模块的关系及常见误用

关系上要把本模块放在构建链路的坐标里看。向上，它依赖 `sonic-slave-*/` 定义的构建容器与 `sonic-buildimage` 的子模块声明，FRR、内核、厂商 SAI 与 `sonic-swss-common` 都不在本快照，涉及它们写「不在本快照，需对照实际版本核验」；向下，它通过 `RULES_PATH` 与 `DOCKERS_PATH` 把 `rules/` 与 `dockers/` 接进构建图，容器内部细节交 07-02，开机配置与 ONIE 安装器交 07-11，平台与 HWSKU 交 07-10，CI 与辅助脚本交 07-13（模块见 07-05 ｜ 模块见 07-08 ｜ 模块见 07-10 ｜ 模块见 07-11 ｜ 模块见 07-13）。机制层面，本模块只回答「谁装配谁」，`config` 命令为何不等于硬件下发、容器启动顺序如何推进，分别属于 06-01 与 06-13，本篇不越界（原理见 06-01 ｜ 原理见 06-13）。

误用第一类是把 sonic-buildimage 当成运行时组件，或把「构建主仓」写成「单一仓库」。本快照有 8 个子仓且各有 `xxx-master/` 归档层，必须按「真实仓库根」写路径；任何把 FRR、内核、厂商 SAI 当成主仓内文件的写法都属编造（模块见 07-05 ｜ 模块见 07-08）。第二类是把 `rules/config` 写成目录、或在 `rules/` 下凭印象补不存在的 `.mk` 名——本快照的规则文件密集且发行版变体众多，写不出的文件一律标注核验并给出 `rules/` 这一可定位目录，不从记忆补值。第三类是「裸 `make` 出镜像」：构建依赖 sonic-slave 容器，`make` 在容器内跑，`PLATFORM` 与发行版开关还相互约束（`BAZEL_MIN_READINESS` 的非 trixie 组合会直接报错），不能写成「普通 x86 主机直接 make 即得可安装镜像」（参数见 04-01 ｜ 模块见 07-11）。

第四类是版本号与 DB 编号陷阱。`DOCKER_ORCHAGENT)_VERSION = 1.0.0` 是规则文件里的镜像版本字样，仅作核验依据，不得抄作本套资料的版本号；本套统一写「上游 master 快照（2026-11 抓取）」，Redis 各库编号须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 核验，禁止写死（参数见 04-01 ｜ 参数见 04-04）。第五类是性能与容量：构建耗时、镜像大小、并发任务数随主机与版本变化，一律标注「需在目标机型实测」，不给绝对值（基准见 08-01）。第六类是把调试产物当生产基准：`DBG_IMAGE_MARK` 与 `*_DBG_*` 生成的 debug 镜像仅用于问题定位，不作性能依据（模块见 07-13 ｜ 基准见 08-01）。最佳实践可归纳为四条：其一，路径一律写成 `upstream_src/sonic-buildimage/sonic-buildimage-master/` 下的相对路径；其二，凡「目录有什么」都以 `ls` 实测为准，不在正文凭印象补文件名；其三，命令按「前置检查、执行、验证」闭环写并附逐行判读；其四，跨册引用统一用四段式，本篇涉及平台字段写「字段见 05-09」、构建变量写「参数见 04-01」、构建机制写「原理见 02-02」、容器目录写「模块见 07-02」。

### 7. 小结与延伸阅读

本篇把 07 册的起点落在 sonic-buildimage 主仓的顶层与构建规则模块：`Makefile` 的 `%::` 模式规则把构建分派到 `Makefile.work`，`slave.mk` 以 `SRC_PATH`、`RULES_PATH`、`TARGET_PATH`、`DOCKERS_PATH` 等变量装配出 `target/<类型>/<发行版>/` 的分层产物，并以 `lsb_release -cs` 在构建容器内解析发行版；`rules/` 以「一目标一对 `.mk`/`.dep`」组织，`rules/config` 实为配置文件而非目录；`functions.sh`、`build_image.sh`、`build_docker.sh` 提供版本生成、ONIE 镜像生成与镜像准备入口；新增镜像遵循「STEM → 目标变量 → 清单登记」的扩展范式。几个判断贯穿全篇：这是构建主仓而非运行时组件、sonic-buildimage 只是 8 个子仓之一、构建依赖 sonic-slave 容器不能裸 `make`、目录清单以实测为准（模块见 07-02 ｜ 模块见 07-11 ｜ 参数见 04-01）。

## 07-02 dockers/ 容器族与镜像生成模块

### 1. 模块定位与职责边界

07-01 讲的是「构建规则怎么装配」，本篇讲的是「被装配的容器族目录里到底有什么」。`dockers/` 是 sonic-buildimage 主仓里定义**容器镜像内容**的目录族，它的产物是若干 `docker-*.gz` 镜像归档，而镜像里跑的进程——orchagent、syncd、bgpd、teamd、lldpd 等——其源码大多不在本目录，而分布在 `sonic-swss`、`sonic-sairedis`、`sonic-utilities` 等子仓。因此必须先立住本篇的核心边界：`dockers/` 是「容器怎么被做出来、里面装什么、进程怎么被拉起」的**定义与模板层**，不是「业务进程本身」。读者若在这里寻找 `orchagent.cpp` 的实现，就会找错地方；正确路径是 07-03（sonic-swss / orchagent）与 07-04（sonic-sairedis / syncd）（模块见 07-03 ｜ 模块见 07-04）。

从目录归属看，`dockers/` 下的每个 `docker-*/` 子目录对应一类镜像，目录内通常包含四类文件：`Dockerfile.j2`（或 `Dockerfile.common.j2`）镜像构建模板、`supervisord.conf.j2` 或 `supervisord.conf` 进程编排配置、`critical_processes`（或 `.j2`）关键进程清单，以及一批 `start.sh`、`*-init.sh`、`.json.j2`、`.conf.j2` 启动脚本与配置模板，外加一个 `base_image_files/` 存放要拷进镜像的文件。本篇的职责就是把这套「每类容器有什么、每个文件干什么、怎么被 rules 装配」讲清，作为 07 册「目录归属唯一权威源」的一部分。至于容器内进程的启动顺序、依赖关系与失败定位，属机制层，归 06-13；容器与 supervisord 的启动参数全集，归 04-07；本篇只确认这些参数的**存放位置**（原理见 06-13 ｜ 参数见 04-07）。

第二个边界是「容器族 vs 镜像生成链路」。本篇既讲 `dockers/` 的目录内容，也讲它如何经 `rules/docker-*.mk` 被渲染成镜像：07-01 已经确认 `$(TARGET)_PATH = $(DOCKERS_PATH)/$(STEM)` 把规则与目录对接，本篇则深入目录内部，说明 `Dockerfile.j2` 如何从 `dockerfile-macros.j2` 引入宏、如何以 `ARG BASE` 选择基础层、如何经 `j2` 渲染为真正的 `Dockerfile`。但渲染机制、slave 容器内构建与缓存细节不在这里展开，那是 02-02 与 07-13 的事（模块见 07-01 ｜ 模块见 07-13 ｜ 原理见 02-02）。

第三个边界是「不在本快照」的硬约束。`dockers/docker-fpm-frr/` 目录里能看到 FRR 的**集成文件**（`vtysh.conf`、`TS`/`TSA`/`TSB`/`TSC`、`frr/`、`docker_init.sh`），但 FRR / FRRouting 的源码本身不在本快照，写「不在本快照，需对照实际版本核验」；厂商 SAI 实现、Linux 内核同理。特别地，`dockers/` 下**没有**名为 `docker-syncd` 的目录——syncd 主体在 `sonic-sairedis-master/syncd/`，它随 `docker-orchagent` 容器一并交付，这个落位本身就是「容器族按功能划分而非按进程划分」的证据（模块见 07-04 ｜ 模块见 07-08）。版本基准统一为「上游 master 快照（2026-11 抓取）」，容器名、进程名与选项的完整形式需对照实际版本核验。

### 3. 关键类与入口函数

本节的「关键类」指模板文件、进程清单与启动脚本三类入口，只点名称与真实路径，不展开逐行内容。结构字段统一在 05 册：`database_config.json.j2` 涉及的 DB 编号与 `SonicDBConfig` 字段写「字段见 05-03」，平台与 `platform.json` 相关字段写「字段见 05-09」，supervisord 进程项与启动参数写「参数见 04-07」，编排机制写「原理见 06-13」，规则归属写「模块见 07-01」。统一写法为（字段见 05-03 ｜ 参数见 04-07 ｜ 原理见 06-13 ｜ 模块见 07-01）。

第一类是镜像模板。`dockers/dockerfile-macros.j2` 是本快照可核验的宏文件，`docker-orchagent/Dockerfile.j2` 顶部以 `{% from "dockers/dockerfile-macros.j2" import install_debian_packages, install_python_wheels, copy_files, rsync_from_builder_stage %}` 引入四个宏；随后 `ARG BASE=docker-swss-layer-trixie-{{DOCKER_USERNAME}}:{{DOCKER_USERTAG}}`、`FROM $BASE AS base`、`ARG docker_container_name`、`ENV DEBIAN_FRONTEND=noninteractive`，再以 `apt-get install -f -y` 安装 `ifupdown`、`arping`、`iproute2`、`ndisc6`、`tcpdump`、`bridge-utils`、`conntrack`、`ndppd`、`python3-protobuf`、`pciutils`、`python3-netifaces` 等包，并针对 armhf/arm64 增加 `gcc`、`iputils-ping`。这段说明基础层由 `ARG BASE` 参数化、包列表写在模板里、架构差异用 Jinja 条件分支处理（参数见 04-01 ｜ 模块见 07-01）。

第二类是进程编排模板。`dockers/docker-orchagent/supervisord.conf.j2` 可核验到 `[supervisord]` 段的 `nodaemon=true`、`logfile_maxbytes=1MB`、`logfile_backups=2`，两个 eventlistener——`eventlistener:dependent-startup`（`command=python3 -m supervisord_dependent_startup`，`events=PROCESS_STATE`，`exitcodes=0,3`）与 `eventlistener:supervisor-proc-exit-listener`（`command=/usr/bin/supervisor-proc-exit-listener-rs --container-name swss`），以及 `[program:rsyslogd]` 的 `priority=1`、`autostart=false`；文件末尾以 `{% set include_swssconfig = true %}`、`{% set swss_priority_base = 0 %}` 和 `{% include "supervisord.conf.common.j2" %}` 收束。这组入口说明进程启动有依赖顺序与退出监听两套机制，具体进程项全集见 04-07（原理见 06-13 ｜ 参数见 04-07）。

第三类是配置模板与启动脚本。`docker-database/` 下可核验到 `database_config.json.j2`、`database_global.json.j2`、`multi_database_config.json.j2`、`docker-database-init.sh`、`flush_unused_database`、`critical_processes.j2`、`supervisord.conf.j2`，它们决定 Redis 各逻辑库的运行时配置；其中 DB 编号与表字段必须对照 `sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 核验，不得写死（字段见 05-03 ｜ 参数见 04-04）。`docker-fpm-frr/` 下是 `docker_init.sh`、`vtysh.conf`、`zsocket.sh` 与 `TS`/`TSA`/`TSB`/`TSC` 文件，以及 `frr/` 与 `tests/` 目录；`docker-teamd/`、`docker-lldp/`、`docker-snmp/` 普遍有 `start.sh` 与 `*-init.sh`；`docker-sonic-telemetry/` 则是 `telemetry.sh`、`dialout.sh`、`docker-telemetry-entry.sh`。这些脚本的完整参数与用途需对照实际版本核验（模块见 07-08 ｜ 模块见 07-09 ｜ 模块见 07-12）。

图 07-02-01 中 teal 为镜像声明与模板，gray 为构建容器与素材目录，purple 为进程编排，amber 为镜像归档与安装登记，green 为运行时容器，red 为硬件边界。图中最关键的衔接是 `rules/docker-*.mk` 与 `dockers/<name>/` 之间那条「指向目录」：07-01 已确认 `_PATH = $(DOCKERS_PATH)/$(STEM)` 完成对接，本篇则确认目录内 `Dockerfile.j2` 是真正的模板输入（模块见 07-01 ｜ 原理见 02-02）。

第一个扩展点是模板参数化。`Dockerfile.j2` 通过 `ARG BASE`、`ARG docker_container_name` 与 `DOCKER_USERNAME`/`DOCKER_USERTAG`/`CONFIGURED_ARCH` 等由构建系统注入的变量完成定制，新增容器时只需在本目录写模板，不必改动构建主逻辑；变量全集见 04-01（参数见 04-01 ｜ 模块见 07-01）。第二个扩展点是进程编排：在 `supervisord.conf.j2`（或 `supervisord.conf`）中增加 `[program:xxx]` 段，设置 `command`、`priority`、`autostart`、`dependent_startup` 等项，并把关键进程写入 `critical_processes`/`critical_processes.j2`；这些进程项的完整清单见 04-07，启动依赖顺序见 06-13（参数见 04-07 ｜ 原理见 06-13）。第三个扩展点是规则登记：在 `rules/` 下新增同名 `.mk`/`.dep`，设置 `STEM`、`_PATH`、`_CONTAINER_NAME`、`_LOAD_DOCKERS` 与关停顺序 `_WARM_SHUTDOWN_BEFORE`/`_AFTER`，再把目标追加进 `SONIC_DOCKER_IMAGES` 与 `SONIC_INSTALL_DOCKER_IMAGES`（模块见 07-01 ｜ 参数见 04-07）。三者齐备，一个新容器目录才算真正接入构建与安装链路。

逐行判读如下。第一段 `ls -d` 确认三个容器目录与一个宏文件同时存在，输出并列四项，说明「容器目录 + 公共宏文件」的布局成立；若缺 `dockerfile-macros.j2`，说明快照不完整，应回到 `upstream_src/sonic-buildimage/sonic-buildimage-master/dockers/` 核对。第二段列出 `docker-database/` 的内部文件，`Dockerfile.common.j2` 与 `Dockerfile.j2` 同时出现，印证「模板 + 公共片段」的组织；`database_config.json.j2`、`database_global.json.j2`、`multi_database_config.json.j2` 三个模板说明 Redis 库配置由模板生成，DB 编号需对照 `SonicDBConfig` 核验而不是从模板字面读取；`supervisord.conf.j2` 与 `critical_processes.j2` 分别是进程编排与关键进程清单；`docker-database-init.sh` 与 `flush_unused_database` 是初始化与清理脚本。第三段列出 `docker-orchagent/` 的前若干文件，`buffermgrd.sh`、`enable_counters.py`、`arp_update.conf` 说明 swss 容器承载的不只 orchagent 一个进程，还含 buffer 管理与计数相关脚本，这与 07-03 的 `cfgmgr/` 模块呼应；最后一段 `ls -ld dockerfile-macros.j2` 以 `-rw-r--r--` 开头，证明它是文件不是目录，纠正「凡 dockers 下条目皆为目录」的误解。整个查询为只读探查，不改变构建或容器状态（参数见 04-07 ｜ 模块见 07-03）。

第二组给出进程编排片段，用来印证「eventlistener + 模板 include」的形态；下列片段依据本快照 `docker-orchagent/supervisord.conf.j2` 整理，为便于阅读做了节选，完整进程项需对照实际版本核验。

```ini
; 片段示意，依据 docker-orchagent/supervisord.conf.j2 整理；完整清单需对照实际版本核验
[supervisord]
nodaemon=true
logfile_maxbytes=1MB
logfile_backups=2

[eventlistener:dependent-startup]
command=python3 -m supervisord_dependent_startup
events=PROCESS_STATE
exitcodes=0,3

[eventlistener:supervisor-proc-exit-listener]
command=/usr/bin/supervisor-proc-exit-listener-rs --container-name swss

[program:rsyslogd]
command=/usr/sbin/rsyslogd -n -iNONE
priority=1
autostart=false
dependent_startup=true
```

这段说明三件事：`nodaemon=true` 表示 supervisord 以前台方式运行，符合容器主进程模型；两个 eventlistener 分别负责依赖启动与退出监听，`--container-name swss` 把 exit-listener 绑定到具体容器；`rsyslogd` 的 `priority=1`、`autostart=false` 与 `dependent_startup=true` 表明进程有优先级与依赖约束。片段省去了 `{% include %}` 等 Jinja 语句与大量进程项，读真实文件时应重点看 `supervisord.conf.common.j2` 里如何定义各 `program:` 的 `command` 与 `priority`，以及它们如何与 `critical_processes.j2` 对应（原理见 06-13 ｜ 参数见 04-07）。

### 6. 与其他模块的关系及常见误用

关系上，本模块是构建链路与运行时之间的「接缝」。向上，它经 `rules/docker-*.mk` 被 07-01 的规则装配，经 `Dockerfile.j2` 从 `dockerfile-macros.j2` 与 `sonic-slave` 构建容器取素材；向下，它产出的容器承载 07-03（orchagent）、07-04（syncd）、07-08（FRR/bgp）、07-09（teamd/lldp/snmp/pmon）等模块描述的进程。机制层，进程启动顺序与依赖归 06-13，DB 编号归 04-04，启动参数全集归 04-07，本模块只负责「这些参数放在哪个文件里」（模块见 07-01 ｜ 模块见 07-03 ｜ 模块见 07-04 ｜ 模块见 07-08 ｜ 模块见 07-09 ｜ 原理见 06-13）。

误用第一类是「按进程找容器目录」的落位错误。最典型的是去找 `dockers/docker-syncd/`——本快照没有这个目录，syncd 主体在 `sonic-sairedis-master/syncd/`，随 `docker-orchagent` 容器交付；写模块归属时必须以实测目录为准，不从进程名反推目录名（模块见 07-04）。第二类是「把集成当源码」：`docker-fpm-frr/` 里有 `vtysh.conf`、`frr/`、`TS`/`TSA`/`TSB`/`TSC` 等 FRR 集成文件，但 FRR 源码不在本快照，一律写「不在本快照，需对照实际版本核验」；厂商 SAI 与 Linux 内核同理（模块见 07-08）。第三类是「把模板当成品」：`Dockerfile.j2`、`supervisord.conf.j2`、`database_config.json.j2` 都是 Jinja 模板，经 `j2` 渲染后才成为真正的 `Dockerfile`、`supervisord.conf` 与 JSON 配置；直接把 `.j2` 当最终文件解读会误判变量与条件分支（参数见 04-01 ｜ 模块见 07-13）。

第四类是「模板一律化」：并非每个容器都有 `Dockerfile.common.j2` 与 `supervisord.conf.common.j2`，`docker-teamd/`、`docker-nat/`、`docker-macsec/` 等在本快照只有单模板，套用统一结构会写出不存在的路径。第五类是 DB 编号与进程名陷阱：库编号须对照 `SonicDBConfig`，容器名（swss、bgp、database 等）与进程名（orchagent 等）在本快照的 `.mk` 与 `supervisord.conf.j2` 中可核验为字符串，但完整取值需对照实际版本核验，不能编造（字段见 05-03 ｜ 参数见 04-04 ｜ 参数见 04-07）。第六类是性能与容量：镜像大小、容器启动时间、进程收敛时延随机型与版本变化，一律标注「需在目标机型实测」，不给绝对值（基准见 08-01）。最佳实践四条：其一，凡「目录有什么」一律用 `ls` 实测，目录名与文件名不凭记忆补；其二，读容器目录先用「模板 + 公共片段 + 进程清单 + 启动脚本 + base_image_files」五类框架归类，再逐个确认；其三，命令按「前置检查、执行、验证」闭环写并附逐行判读，输出注明核验要求；其四，跨册引用统一用四段式，本篇涉及 DB 配置写「字段见 05-03」、启动参数写「参数见 04-07」、编排机制写「原理见 06-13」、规则归属写「模块见 07-01」。

### 7. 小结与延伸阅读

本篇把 07 册的容器族模块落在 `dockers/` 这个目录上：它五十余个 `docker-*/` 子目录与一个 `dockerfile-macros.j2` 文件构成镜像定义层，每个容器目录以「镜像模板 + 进程编排 + 关键进程清单 + 启动脚本与配置模板 + base_image_files」五类文件组织；`Dockerfile.j2` 经 `ARG BASE` 与宏引入实现参数化，`supervisord.conf.j2` 用 eventlistener 与 `{% include %}` 完成进程编排，再经 `rules/docker-*.mk` 的 `_PATH` 对接、渲染、构建为 `docker-*.gz` 归档并登记进安装清单。几个判断贯穿全篇：`dockers/` 是模板与定义层而非业务进程源码、容器族按功能划分而非按进程划分（没有 `docker-syncd/`）、FRR 与厂商 SAI 不在本快照、目录清单以实测为准（模块见 07-01 ｜ 模块见 07-04 ｜ 模块见 07-08 ｜ 原理见 06-13）。

延伸阅读按疑问分流。想知道规则如何装配容器，回读 07-01；想看容器里跑的 orchagent 与 syncd 源码，接读 07-03、07-04；想看 bgp 与外围容器，接读 07-08、07-09；想看 ONIE 与安装器如何收下镜像归档，接读 07-11；想看 CI 与辅助脚本，接读 07-13；想补容器启动顺序与依赖，接读 06-13；想查启动参数全集，翻 04-07。字段随查走 05-03（DB 编号与 SonicDBConfig）与 05-09（平台文件结构），运维与基准走 08-01。跨册引用请始终使用「字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx」的写法，`xx` 替换为具体篇号。
