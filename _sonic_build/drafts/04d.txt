# SONiC 技术资料 · 04 参数与 API 手册（分片 D）
## 04-07 容器服务、supervisord 与启动参数全集

### 1. 本篇定位与覆盖范围

本篇是 04 参数与 API 手册中专门收拢「容器服务与启动参数」的字典分册，回答的是一个非常具体的问题：一台 SONiC 设备完成镜像安装后，各容器里的进程究竟由谁、按什么顺序、带哪些参数被拉起，异常时又该回到哪个配置文件里核对对应的键。本篇不讨论容器编排的内部实现机制，也不展开事件监听器的状态机细节；这些属于技术原理册的内容，统一写「原理见 06-13」。本篇同样不罗列容器镜像的构建规则、不展开各容器的能力清单，容器族的功能划分写「模块见 07-02」。本篇涉及的是可被逐项查询的配置键、取值、默认值与作用，而不是结构体字段；与进程运行时状态、WARM_RESTART 相关的字段写「字段见 05-09」。

覆盖范围可以分成三层。第一层是容器入口层，即 `sonic-buildimage/sonic-buildimage-master/dockers/` 下每个 `docker-*` 目录中的启动脚本与配置文件族，包括 `supervisord.conf`、`supervisord.conf.j2`、`supervisord.conf.common.j2` 以及基础镜像 `etc/supervisor/supervisord.conf`。第二层是 supervisord 参数层，包括 `[supervisord]` 全局段、`[unix_http_server]` 与 `[supervisorctl]` 通道段、`[eventlistener:*]` 事件监听段、以及数量最多的 `[program:*]` 程序段。第三层是启动依赖层，也就是 `dependent_startup` 与 `dependent_startup_wait_for` 这一类把「谁先起、谁后起、等到什么状态再起」显式声明出来的键。三层的证据均可在上游快照的 `dockers/` 目录逐一核实。

事实基准统一为「上游 master 快照（2026-11 抓取）」，路径相对各子仓 `xxx-master/` 仓库根。凡模板中的 Jinja 变量渲染值、`switch_type` 等条件分支的实际取值、以及命令行选项的完整语义，凡快照内无法核实的，一律标注「需对照实际版本核验」，不凭印象补值。需要提醒的是，容器名、程序段名与事件集合在不同发行分支、不同 HWSKU 上并不完全一致，本篇表格给出的是本快照可核验的形态，不能当作跨版本通用常量。

之所以把这些参数单独成篇，是因为 SONiC 把控制面拆进了多个容器，进程之间不靠函数调用而靠 Redis 逻辑库解耦，于是「启动顺序」无法用进程内依赖表达，只能交给 supervisord 的事件驱动依赖调度来声明。这种工程形态决定了排障时不能只看单个进程，而要按「容器入口 → 全局守护 → 事件监听 → 日志与数据库 → 各业务进程 → 编排与同步」的顺序逐段核对，参数表正是这条顺序的随查索引。

### 2. 索引与全参数表

下表按「参数 → 取值 → 默认值 → 作用 → 误配后果」组织，汇总 `dockers/` 下 supervisord 配置族中反复出现的关键键。表中「默认值」一列以本快照模板中能直接读到的为准，凡由 Jinja 表达式计算或随容器变化的，标注需对照实际版本核验；单元格中的逗号分隔值不是枚举全集，具体事件名与程序名需对照实际版本核验。

| 参数 | 取值 | 默认值 | 作用 | 误配后果 |
|---|---|---|---|---|
| nodaemon | true / false | true | 让 supervisord 以前台方式运行，充当容器主进程 | 设为 false 会使容器主进程退出，容器反复重启 |
| logfile_maxbytes | 字节数 | 1MB | 单个 supervisord 日志达到上限后轮转 | 过大易撑爆容器可写层，过小产生大量碎片文件 |
| logfile_backups | 整数 | 2 | 保留的轮转日志份数 | 过小丢失排障线索，过大占用持久化空间 |
| command | 可执行文件路径或 shell 串 | 无 | 定义程序段实际执行的命令 | 路径写错或脚本缺失会导致进程进入 FATAL |
| priority | 整数 | 视容器基数十进制偏移 | 决定无依赖时的启动先后 | 与依赖顺序冲突时会拉起尚未就绪的进程 |
| autostart | true / false | false | 是否随 supervisord 自动启动 | 误设 true 会在依赖未满足时提前启动 |
| autorestart | true / false / unexpected | false 或 unexpected | 定义退出后是否重启 | 误设 true 会掩盖反复崩溃，掩盖真实故障 |
| startsecs | 整数秒 | 0 或默认 | 判定「启动成功」前需保持运行的时长 | 设置过长拖慢依赖链，过短误判启动成功 |
| startretries | 整数 | 0 | 启动失败后的重试次数 | 过大延长故障暴露时间，过小错过瞬时恢复 |
| dependent_startup | true / false | true | 开启基于事件的状态依赖调度 | 关闭后依赖声明失效，顺序退化成 priority |
| dependent_startup_wait_for | 程序名加状态，如 portsyncd:running | 视模板变量 | 等待指定进程进入指定状态后再启动 | 引用不存在的程序会使本程序永不启动 |
| stdout_logfile | NONE 或路径 | NONE | 标准输出落文件开关 | 指定本地文件会绕开 syslog，日志分散难查 |
| stdout_syslog | true / false | true | 标准输出是否转发 syslog | 关闭后 `show logging` 看不到该进程输出 |
| stderr_logfile | NONE 或路径 | NONE | 标准错误落文件开关 | 与 stdout 同理，导致错误日志散落 |
| stderr_syslog | true / false | true | 标准错误是否转发 syslog | 关闭后异常堆栈无法进入系统日志 |
| stdout_capture_maxbytes | 字节数 | 1MB | 事件监听可捕获的 stdout 上限 | 过小截断通信内容，影响事件监听判读 |
| stopwaitsecs | 整数秒 | 60（teamd 段） | 停止时等待进程退出的秒数 | 过小强制杀进程，可能留下半成品状态 |
| exitcodes | 逗号分隔整数 | 0,3 | 事件监听器认为「正常」的退出码集合 | 漏配退出码会使正常退出被当作异常 |
| events | 事件名逗号分隔 | PROCESS_STATE 等 | 声明监听器订阅的进程事件集合 | 订阅不足会漏掉 FATAL 等关键事件 |
| buffer_size | 整数 | 1024 | 事件监听缓冲区大小 | 过小在高事件速率下丢事件 |
| user | 用户名 | root 或 redis | 以指定用户身份运行程序 | 误配权限会导致无法绑定端口或读写目录 |
| environment | 键值对 | 条件设置 | 注入环境变量，如 ASAN_OPTIONS | 路径不存在会使开启 ASAN 的镜像启动失败 |

紧随其后的是容器与配置文件族的对应关系，便于从「想改哪个进程」反查到「该编辑哪个文件」。下表列出本快照可直接核实的几个代表容器，表中程序名与文件名需对照实际版本核验。

| 容器目录 | 配置文件族 | 承载的代表程序 | 需重点核对的参数 |
|---|---|---|---|
| docker-orchagent | supervisord.conf.j2 与 common.j2 | orchagent、portsyncd、各 mgrd | priority、wait_for、autorestart |
| docker-database | supervisord.conf.j2 | redis-server 各实例、flushdb | command、user、dependent_startup |
| docker-teamd | supervisord.conf.common.j2 | teammgrd、teamsyncd、tlm_teamd | stopwaitsecs、startsecs、wait_for |
| docker-sonic-telemetry | supervisord.conf | start、telemetry、dialout | priority、wait_for、autorestart |
| docker-base 系列 | etc/supervisor/supervisord.conf | 基础通道与 include 定义 | logfile、serverurl、files |

索引的使用方法有三条。其一，先按「容器—配置文件族」表定位文件，再回到全参数表查键的含义，避免在几十个程序段里盲搜。其二，凡看到 `{{ ... }}` 形式的 Jinja 表达式，说明该值在渲染时才确定，须结合调用方传入的变量判断，不能直接把模板文本当成最终值。其三，参数表里的「默认值」描述的是本快照模板中可读到的常见形态，同一键在不同程序段可能取不同值，逐项详解会按段分组说明。

### 3. 逐项详解

先讲全局段。`[supervisord]` 段中的 `nodaemon=true` 是最关键的一行：它让 supervisord 以前台进程方式运行，从而占据容器的主进程位置；一旦误设为后台方式，容器主进程会立即退出，编排层会认为容器失败并反复重建。`logfile_maxbytes=1MB` 与 `logfile_backups=2` 共同约束守护进程自身日志的体量，避免日志无限增长撑爆容器可写层；这两个值偏小是容器环境的常见取舍，不能照搬到宿主机 syslog 的策略。基础镜像 `dockers/docker-base-bookworm/etc/supervisor/supervisord.conf` 还给出 `logfile=/var/log/supervisor/supervisord.log`、`pidfile=/var/run/supervisor/supervisord.pid`、`childlogdir=/var/log/supervisor` 与 `user=root`，并通过 `[unix_http_server]` 的 `file=/var/run/supervisor.sock`、`chmod=0700` 以及 `[supervisorctl]` 的 `serverurl=unix:///var/run/supervisor.sock` 建立本地控制通道；最后 `[include]` 用 `files=/etc/supervisor/conf.d/*.conf` 把各容器的程序段拼进来。

再讲事件监听段。`dockers/docker-orchagent/supervisord.conf.j2` 中 `[eventlistener:dependent-startup]` 以 `python3 -m supervisord_dependent_startup` 启动，`autostart=true`、`autorestart=unexpected`、`startretries=0`、`exitcodes=0,3`、`events=PROCESS_STATE`、`buffer_size=1024`。其中 `exitcodes=0,3` 的含义是这两个退出码被视为监听器正常退出，其余码触发 `autorestart=unexpected` 的策略；`events=PROCESS_STATE` 表明它订阅进程状态变化，这正是依赖调度得以工作的前提。紧随其后的 `[eventlistener:supervisor-proc-exit-listener]` 以 `/usr/bin/supervisor-proc-exit-listener-rs --container-name swss` 启动，`events` 列出 PROCESS_STATE_EXITED、PROCESS_STATE_RUNNING、PROCESS_COMMUNICATION_STDOUT、PROCESS_STATE_FATAL 等；`--container-name` 在不同容器里取值不同，database 容器为 database、telemetry 容器为 telemetry，需对照实际版本核验。这两个监听器是「依赖调度」和「异常退出上报」两条机制的落地载体，其机制写「原理见 06-13」。

然后讲程序段的通用键。`command` 指向启动脚本而非直接调用二进制，例如 orchagent 段用 `/usr/bin/orchagent.sh`，swssconfig 段用 `/usr/bin/swssconfig.sh`，这类包装脚本通常负责环境变量准备与参数拼装，脚本本体需对照实际版本核验。`priority` 在 swss 容器里以 `swss_priority_base` 为基数做十进制偏移，standalone 场景基数为 0，虚拟交换机场景基数会变化；teamd 容器则以 `teamd_priority_base` 为基数，默认 3。`autostart=false` 与 `dependent_startup=true` 成对出现，表示进程不自行启动，而交给依赖调度。`autorestart=false` 在多数业务进程段出现，意味着进程退出后不自动重启——这是有意设计，因为重启需经过更高层的容器级处理，误改为 true 反而会掩盖反复崩溃的事实。

最后讲依赖键与日志键。`dependent_startup_wait_for` 的取值决定启动门槛：orchagent 段默认是 `portsyncd:running`，当 `switch_type` 为 fabric 时改为 `rsyslogd:running`；swssconfig 段等待 `orchagent:running`；restore_neighbors、neighsyncd、vlanmgrd、intfmgrd、portmgrd、buffermgrd 等多数 mgrd 段在包含 swssconfig 时等待 `swssconfig:exited`，否则退回 `orchagent:running`。teamd 容器的 `teamd_wait_for` 默认 `start:exited`，teamsyncd 则等待 `teammgrd:running`。日志侧几乎统一使用 `stdout_logfile=NONE` 配合 `stdout_syslog=true`、`stderr_logfile=NONE` 配合 `stderr_syslog=true`，即标准输出与错误都进 syslog，而不是落到容器本地文件；这正是排障时要用系统日志命令而非去容器里找日志文件的原因，命令与判读留待 04-08。启用 ASAN 的镜像还会注入 `environment=ASAN_OPTIONS="log_path=/var/log/asan/...-asan.log:print_suppressions=0"`，具体后缀随程序变化，需对照实际版本核验。

图 04-07-01 的边并不表示数据流，而表示「等待前一个节点进入指定状态」的启动门槛；这与配置从 `CONFIG_DB` 到 `ASIC_DB` 的异步流水线是两件事，后者写「原理见 06-01」。

下面给出 `dockers/docker-orchagent/supervisord.conf.common.j2` 中 orchagent 程序段的模板原文，它集中体现了本节讲的多个键；内容节选自该文件，含 Jinja 变量，具体渲染值需对照实际版本核验。

```ini
[program:orchagent]
command=/usr/bin/orchagent.sh
priority={{ swss_priority_base + 4 }}
autostart=false
autorestart=false
stdout_logfile=NONE
stdout_syslog=true
stderr_logfile=NONE
stderr_syslog=true
stdout_capture_maxbytes=1MB
dependent_startup=true
dependent_startup_wait_for={{ orchagent_dependent_startup_wait_for }}
```

配合模板阅读，用一条命令查看容器内各程序的实时状态，输出块已注明示例输出与版本核验要求。

```bash
docker exec swss supervisorctl status
```

```text
示例输出，具体格式需对照实际版本核验（程序名与状态仅为格式示意）
gearsyncd                        RUNNING   pid 123, uptime 0:05:12
portsyncd                        RUNNING   pid 131, uptime 0:05:11
orchagent                        RUNNING   pid 145, uptime 0:05:09
swssconfig                       EXITED    Nov 16 01:20:33
coppmgrd                         RUNNING   pid 201, uptime 0:05:06
neighsyncd                       RUNNING   pid 208, uptime 0:05:05
```

逐行判读如下。`docker exec swss supervisorctl status` 进入名为 swss 的容器并调用本地控制通道，容器名在不同版本可能不同，需对照实际版本核验；它读取的是本节 `[unix_http_server]` 与 `[supervisorctl]` 建立的 socket，属于只读状态查询。输出第一段中 `gearsyncd` 与 `portsyncd` 均为 RUNNING，说明日志辅助与端口监听已就绪，这是 orchagent 得以启动的前置条件，与模板里 wait_for 的声明一致。第三行 `orchagent` 为 RUNNING 且 `uptime` 略短于前两者，符合依赖顺序的时间关系。第四行 `swssconfig` 为 EXITED 而非 RUNNING，这是正常特征：它是一次性加载程序，按设计应在完成后退出，若在此处看到 RUNNING 反而要怀疑脚本卡住；同时它的 `autorestart=false` 保证退出后不会被反复拉起。第五、六行 `coppmgrd`、`neighsyncd` 均为 RUNNING，对应模板中等待 `swssconfig:exited` 的一批 mgrd，进一步印证依赖链生效。若任意关键程序出现 FATAL，或 orchagent 的 uptime 反复归零，说明存在反复崩溃，此时不要只在容器内看本地日志，而应按 04-08 的日志口径到 syslog 中查对应程序的错误行，并结合 `原理见 06-13` 判断是依赖门槛未满足还是程序自身异常。

### 5. 速查表

下表把常见疑问压缩成「现象 → 先查文件 → 关键参数 → 处置方向」四列，供现场快速反查。表中处置方向只给到参数层，不展开运维步骤；涉及具体命令与输出判读写「完整命令见 04-05」，涉及日志检索写「日志方法见 04-08」。

| 现象 | 先查文件 | 关键参数 | 处置方向 |
|---|---|---|---|
| 容器反复重建、主进程秒退 | docker-base 的 supervisord.conf | nodaemon、user | 确认主进程以前台运行且用户有权限 |
| 后起进程提前退出 | docker-orchagent 的 common.j2 | dependent_startup_wait_for | 核对等待的程序名与状态是否拼对 |
| 全部程序同时起、顺序混乱 | 各容器 supervisord.conf.j2 | autostart、dependent_startup | 关闭 autostart，开启依赖调度 |
| 程序崩溃后无感知 | eventlistener 段 | events、exitcodes | 订阅 FATAL，核对退出码集合 |
| `show logging` 看不到进程输出 | 各 program 段 | stdout_syslog、stderr_syslog | 确认输出转发 syslog 而非落本地文件 |
| ASAN 镜像启动失败 | 各 program 段条件分支 | environment、ASAN_OPTIONS | 确认日志目录存在、路径可写 |
| teamd 容器停止缓慢 | docker-teamd 的 common.j2 | stopwaitsecs | 核对等待秒数与进程退出耗时 |
| 数据库实例未监听预期端口 | docker-database 的 supervisord.conf.j2 | command、user | 核对 bind、port、unixsocket 参数 |

使用速查表要注意两点。第一，「先查文件」列给出的是起点而非终点，很多问题的根因在调用方传入的 Jinja 变量里，模板文件本身看不出最终值。第二，「关键参数」列只点名一个最有区分度的键，实际排查往往要成组看 command、wait_for 与 autorestart 三者的组合，单看一个键容易得出片面结论。

### 6. 版本差异

容器与 supervisord 参数是全册中版本差异最集中的一类，原因有三。其一，`dockers/` 目录按发行分支演进，不同分支新增或下线容器，程序段名随之增减；本篇表格只呈现本快照可核验的代表性容器，不能当作所有版本的全集。其二，模板化程度不同：orchagent、database、teamd、lldp、snmp 等容器使用 `.j2` 模板并 include 公共片段，而 telemetry、nat、macsec、 sonic-gnmi 等容器多为静态 `supervisord.conf`，前者要连带看渲染变量，后者可直接读文本，二者排障入口不同。

其三，条件分支会改变实际参数集。以 orchagent 公共模板为例，`switch_type == "fabric"` 时 `is_fabric_asic` 置 1，gearsyncd、portsyncd 等段被跳过，orchagent 的等待对象从 `portsyncd:running` 改为 `rsyslogd:running`，并出现 fabricmgrd 段；`include_swssconfig` 为假时，swssconfig 与 enable_counters 段不生成，一批 mgrd 的等待对象退回 `orchagent:running`；`ENABLE_ASAN == "y"` 时各段追加 ASAN_OPTIONS 环境变量。这些分支在模板里可核实，但某机型实际走哪个分支由配置决定，需对照实际版本核验。

此外还有若干细节差异需留意。`autorestart` 的取值在不同容器并不统一：swss 与 telemetry 的 rsyslogd 段分别为 unexpected 与 true，database 容器为 false，需逐段核对而不能套用默认值。`--container-name` 参数随容器变化，影响异常退出上报的归属。`priority` 的基数在 standalone 与虚拟交换机场景不同，跨场景比较数值没有意义。凡涉及多 ASIC 命名空间、chassis 与 warm reboot 相关进程的启停，均「受平台与版本限制，需对照实际版本核验」，不得宣称全平台无条件支持。版本基准始终为「上游 master 快照（2026-11 抓取）」，具体版本号以对应构建文件为准。

### 7. 常见误用与调试

第一个高频误用是把 `priority` 当成启动顺序的唯一依据。实际上在开启 `dependent_startup` 后，真正决定先后的是 `dependent_startup_wait_for`；`priority` 只在没有依赖声明的进程之间起作用。把依赖改到 priority 上，表面上能跑起来，一旦系统负载导致进程就绪变慢，就会拉起尚未准备好的下游进程，产生难以复现的间歇故障。

第二个误用是把 `autorestart` 一律改成 true，以为这样更「健壮」。在 SONiC 的容器模型里，多数业务进程退出后由更高层的容器级机制统一处理，自动重启会掩盖反复崩溃的事实，让 `uptime` 归零这类关键线索消失。正确的做法是先按 `原理见 06-13` 理解容器级重启机制，再决定是否调整。第三个误用是去容器本地找 `stdout_logfile`，而模板里普遍是 NONE 加 syslog 转发，正确的检索入口是系统日志，见 04-08。

第四个误用是把模板文本当成最终配置。Jinja 表达式在渲染时才求值，`{{ swss_priority_base + 4 }}` 在不同场景结果不同；直接拿模板里的字符串当参数值，会得到错误结论。第五个误用是给事件监听器配置过窄的 `events` 集合，漏掉 PROCESS_STATE_FATAL，结果进程进入 FATAL 却无人上报，表现为「业务静默失效」。第六个是忽略 `exitcodes=0,3`，把监听器正常退出误判为异常，引发无意义的重启风暴。

调试建议按固定顺序推进，形成闭环。前置检查：确认目标容器名与配置文件族，读一遍相关 program 段的 command、wait_for、autorestart 三键。执行：用只读命令查看进程状态，记录 RUNNING、EXITED、FATAL 与 uptime。验证输出：把状态与依赖声明逐条对照，确认后起进程的等待对象确实进入了目标状态；对 EXITED 的一次性程序要确认它是按设计退出而非卡死。清理：若临时改过参数，恢复配置并确认容器回到稳定状态，避免把调试态带入生产。全程遵守「配置返回成功不等于进程就绪、更不等于硬件已下发」的边界，涉及 ASIC 编程状态写「原理见 06-01」。性能与容量类结论一律标注「需在目标机型实测」，本篇不给绝对值。

小结：本篇给出了容器服务的三层参数地图——容器入口与配置文件族、supervisord 各类配置键、以及以 `dependent_startup_wait_for` 为核心的启动依赖层；图 04-07-01 把从容器入口到 syncd 编程的启动门槛串成可核对的顺序，两张表分别提供参数字典与现象反查。需要记住的三条纪律是：依赖优先于 priority 决定顺序、多数进程不自动重启、日志进 syslog 而非本地文件。下一篇 04-08 将接着讲这些日志在哪里查、命令返回码如何判读，把本篇留下的检索入口补齐。

## 04-08 日志、返回码与排错速查手册

### 1. 本篇定位与覆盖范围

本篇是 04 参数与 API 手册中收尾的排错速查分册，目标是把散落在多个子仓里的「日志在哪里、命令返回什么码、看到现象往哪里查」三类信息整理成可随查的字典。它与 04-07 是配套关系：04-07 讲进程如何被拉起、日志往哪里转发，本篇接着讲这些日志如何检索、返回码如何判读。本篇只给参数、取值、来源与判读口径，不展开配置流水线的实现机制，机制统一写「原理见 06-01」；不展开容器编排与退出上报的内部状态机，写「原理见 06-13」；不罗列 CLI 模块的逐项能力，写「模块见 07-06」，也不展开 swss 事件监听器的结构体字段，写「字段见 05-08」。

覆盖范围同样分三层。第一层是日志层，包括系统日志的存放路径、`show logging` 命令的过滤参数、日志级别语义、以及 supervisord 事件监听器订阅的进程事件集合。第二层是返回码层，包括 Python CLI 通过 `sys.exit` 抛出的退出码、各工具自定义的返回码常量、以及标准 shell 的约定码。第三层是排错检索层，也就是把「现象 — 查哪条日志 — 看哪个返回码 — 反查哪一段配置」串起来的决策顺序。

事实基准统一为「上游 master 快照（2026-11 抓取）」，路径相对各子仓 `xxx-master/` 仓库根。日志证据主要来自 `sonic-utilities/sonic-utilities-master/show/main.py`、`dockers/` 下各 `supervisord.conf*` 以及 `sonic-swss/sonic-swss-master/orchagent/main.cpp`；返回码常量来自 `sonic-utilities/sonic-utilities-master/` 下 `consutil/lib.py`、`config/main.py`、`cpoutil/main.py`、`psuutil/main.py` 等文件。凡快照内无法核实的日志文案、退出码取值与命令选项，一律标注「需对照实际版本核验」，绝不编造报错文案——排错类内容一旦写入不存在的报错串，会把读者引向错误方向，危害远大于留白。

需要特别强调本篇的边界：它给的是「查什么、怎么判读」的方法与索引，不是故障处置的运维步骤。具体诊断树与案例写「排障见 08-03」「案例见 08-04」，本篇只负责把参数与判读口径备齐，避免在手册册里展开运维场景。

| 参数或选项 | 取值 | 默认值 | 作用 | 误配后果 |

| 级别 | 语义 | 典型场景 | 排障权重 |
|---|---|---|---|
| ERROR | 错误，操作失败 | 初始化失败、通知 syncd 失败、参数非法被忽略 | 最高，需优先定位 |

最后给返回码速查表。这是本篇最需要克制的部分：同一个数字在不同工具里含义不同，必须从源码常量反查，不能套用通用 shell 约定。下表按「返回码 → 符号或出处 → 语义 → 判读要点」组织，符号与取值可在对应文件核实。

| 返回码 | 符号或出处 | 语义 | 判读要点 |
|---|---|---|---|
| 0 | 多处默认成功 | 命令执行成功 | 只代表该命令这一段成功，不代表硬件已下发 |
| 1 | ERR_DISABLE（consutil/lib.py） | 控制台相关功能被禁用 | 与同值的其它常量靠出处区分 |
| 1 | CONFIG_RELOAD_NOT_READY（config/main.py） | 配置重载条件未就绪 | 多为时序问题，需确认前置流程完成 |
| 1 | ERROR_PERMISSIONS（cpoutil、psuutil） | 权限不足 | 核对执行身份，不要盲目重试 |
| 2 | ERR_CMD（consutil/lib.py） | 命令不被接受 | 核对参数拼写与支持的子命令 |
| 2 | ERROR_CHASSIS_LOAD（psuutil/main.py） | 机箱信息加载失败 | 多与平台插件相关，受平台与版本限制 |
| 3 | ERR_DEV（consutil/lib.py） | 设备相关错误 | 核对目标设备是否存在或可用 |
| 4 | ERR_CFG（consutil/lib.py） | 配置错误 | 回到 CONFIG_DB 对应表项核对 |
| 5 | ERR_BUSY（consutil/lib.py） | 资源忙 | 多为并发占用，需确认无其它会话 |

使用三张表时有一条统一纪律：返回码必须连同「出处」一起读。脱离文件只谈「返回 1」没有意义，因为 consutil 的 ERR_DISABLE、config 的 CONFIG_RELOAD_NOT_READY 与 psuutil 的 ERROR_PERMISSIONS 都是 1，语义完全不同。这也是本篇把「符号或出处」单列一列的原因。

### 3. 逐项详解

先讲日志路径的选择逻辑。`sonic-utilities-master/show/main.py` 的 `logging` 命令在入口处判断 `/var/log.tmpfs` 是否存在：存在则以它为基础路径，否则用 `/var/log`。这个判断意味着同一条 `show logging` 在不同运行状态下可能读不同目录，排障时若发现日志「突然变少」，第一反应应是确认基础路径是否发生了切换，而不是急于断定进程没打日志。随后代码把 `syslog.1` 在存在时排在 `syslog` 之前，一起交给 `sudo cat`；这保证轮转前后的日志都能被检索到，忽略 `syslog.1` 会漏掉重启前的错误线索。

再讲过滤与跟随。`process` 参数被转成 `grep -h -- <process>`，其中 `-h` 让多文件检索时输出不带文件名，`--` 防止以减号开头的进程名被当成 grep 选项；`lines` 参数转成 `tail -n <n>`，放在管道末端。`-f` 分支不同，它直接执行 `sudo tail -F <path>/syslog` 并立即返回，不叠加 grep 与 tail，因此跟随模式下无法用进程名过滤，这是使用上的重要限制。`--verbose` 会把上述命令串打印出来，在结果为空或不符预期时，开启它是确认「过滤条件到底有没有生效」的最快办法。命令实现中特意让 `cat` 以 sudo 运行、而 `grep` 与 `tail` 以调用者身份运行，缩小了用户输入的进程名以 root 执行的风险面。

然后讲日志级别与事件。`SWSS_LOG_*` 系列宏在 orchagent 与 syncd 中大量使用：`main.cpp` 里 `SWSS_LOG_NOTICE("Notify syncd APPLY_VIEW")` 表示进入下发视图的正常里程碑，紧随其后的 `SWSS_LOG_ERROR("Failed to notify syncd APPLY_VIEW %d", status)` 表示这一步失败，两者成对出现，是判断编排是否走通的关键信号。同类还有 `SWSS_LOG_ERROR("Invalid switch type %s configured")`、`SWSS_LOG_WARN("ASIC instance_id length > SAI_MAX_HARDWARE_ID_LEN, LIMITING !!")` 等，分别对应配置非法与取值被限制。事件侧，`supervisord.conf.j2` 的 `supervisor-proc-exit-listener` 订阅 PROCESS_STATE_EXITED、PROCESS_STATE_RUNNING、PROCESS_COMMUNICATION_STDOUT、PROCESS_STATE_FATAL，配合 `exitcodes=0,3`，构成「哪些退出算正常、哪些要上报」的判定口径。程序内部的日志级别细节属于实现，写「原理见 06-01」；事件监听器的数据结构写「字段见 05-08」。

最后讲返回码的三类来源。第一类是 Python CLI 的 `sys.exit`：它既可能接收整数，也可能接收字符串，接收字符串时 shell 看到的退出码通常为 1，并把字符串打印到标准错误，因此「看到一段文字报错」和「返回 1」常常是同一件事的两面。第二类是模块级常量，`consutil/lib.py` 定义 ERR_DISABLE=1、ERR_CMD=2、ERR_DEV=3、ERR_CFG=4、ERR_BUSY=5；`config/main.py` 定义 CONFIG_RELOAD_NOT_READY=1；`cpoutil/main.py` 与 `psuutil/main.py` 定义 ERROR_PERMISSIONS=1，后者还定义 ERROR_CHASSIS_LOAD=2；`config/kdump.py` 中直接出现 `sys.exit(1)` 与 `sys.exit(2)`。第三类是 supervisord 侧的 `exitcodes=0,3`，它不面向终端用户，而是决定事件监听器是否触发重启策略。三类的作用域互不统属，跨类比较数值没有意义。

逐行判读如下。第一条命令用进程名 orchagent 作过滤、取最后 50 行，`-l` 对应源码中的 `--lines`，把结果交给 `tail -n 50`；第二条加 `--verbose`，会先打印实际执行的命令串，便于确认过滤条件，同样按进程名过滤 20 行；第三条 `-f` 进入跟随模式，按实现直接对 syslog 执行 `tail -F`，不再叠加进程过滤，因此看不到进程名筛选，这是使用限制而非故障。输出第一行是 NOTICE 级别的 `Notify syncd APPLY_VIEW`，表示编排侧进入下发视图，是正常里程碑；第二行 INFO 说明异步记录与路由状态发布已启用，属常规信息。第三行 NOTICE 给出 bulk size 取 128，说明批量模式生效。第四行是关键：ERROR 级且文案含 `Invalid input` 与 `use default interval`，含义是本次传入的心跳间隔参数非法，系统已回退到默认值 1000，属「参数被忽略并降级」而非致命故障，需回头查参数来源。第五行同样是 ERROR，`Failed to notify syncd APPLY_VIEW 1` 中的 1 是底层返回的状态值，需对照实际版本核验其确切含义，但不能忽略——它直接说明通知 syncd 这一步失败，应结合 `原理见 06-05` 继续查 syncd 侧日志。第六行 NOTICE 确认回退后的心跳间隔已设为 1000，与第四行形成因果印证。整体上，NOTICE 标记链路走通、ERROR 标出参数非法与通知失败两类问题，判读时要把它们按时间顺序串起来，而不是孤立看某一条；同时这些都是控制面日志，即便全部正常也不代表 ASIC 已编程，仍须按图 04-08-01 右半段逐段核对。

再看一组返回码核验，用标准 shell 变量读取上一条命令的退出状态，输出同样注明需对照实际版本核验。

```bash
config reload -y
echo "exit=$?"
```

```text
示例输出，具体格式需对照实际版本核验（退出码取值与输出文案仅为格式示意）
Running command: /usr/bin/config reload -y
[中间重启日志省略]
exit=1
```

逐行判读如下。前置检查阶段先确认命令名与参数在当前版本是否存在，命令全集写「完整命令见 04-05」；执行阶段运行 `config reload -y`，随后立刻用 `$?` 读取退出码——必须在下一条命令之前读取，否则会被后续命令的退出码覆盖。输出首行是命令回显，说明命令被接受并开始执行；末行 `exit=1` 是本组的关键：单独看「1」没有意义，必须结合出处判断。在 `config/main.py` 中，CONFIG_RELOAD_NOT_READY 被定义为 1，并在多处 `sys.exit(CONFIG_RELOAD_NOT_READY)` 使用，因此这里的 1 更可能指向「重载条件未就绪」这类时序问题，而不是笼统的「执行失败」。正确的下一步是确认前置流程是否完成、是否有其它会话占用，再决定是否重试，而不是简单重跑命令。若退出码为 2，在 consutil 语境下对应 ERR_CMD（命令不被接受），在 psuutil 语境下却对应 ERROR_CHASSIS_LOAD（机箱信息加载失败）——同一个数字因出处不同而语义迥异，这正是返回码必须与出处一起读的实证。清理阶段确认没有遗留的半配置状态，再决定后续动作。

### 5. 速查表

下表把高频现象压成「现象 → 首选检索 → 关键判据 → 反查去向」四列，供现场快速定位。表中反查去向只给到手册篇号，具体诊断树写「排障见 08-03」、案例写「案例见 08-04」。

| 现象 | 首选检索 | 关键判据 | 反查去向 |
|---|---|---|---|
| 配置命令返回成功但不生效 | 按库逐段查表项 | 期望状态与对象是否生成 | 原理见 06-01 |
| 日志里出现 APPLY_VIEW 失败 | show logging orchagent | 是否伴随 ERROR 级通知失败 | 原理见 06-05 |
| 参数被忽略并回退默认 | 查 ERROR 含 use default | 回退后的 NOTICE 是否出现 | 原理见 06-04 |
| 进程进入 FATAL 无感知 | supervisorctl 查状态 | events 是否漏订 FATAL | 原理见 06-13 |
| show logging 结果为空 | 核对 log_path 目录 | tmpfs 路径是否存在 | 模块见 07-06 |
| 跟随模式无法按进程过滤 | 理解 -f 分支实现 | -f 是否绕开 grep | 模块见 07-06 |
| 返回码 1 语义不明 | 按出处查常量 | 出自哪个模块文件 | 本册第 2 节 |
| 多 ASIC 场景日志不全 | 核对命名空间 | 是否查错实例目录 | 原理见 06-11 |

使用速查表要防止两种误判。一是把「日志里没有 ERROR」等同于「没有问题」：NOTICE 里程碑缺失同样能定位卡点，例如在预期位置看不到 APPLY_VIEW，就说明链路没走到那一步。二是把「命令返回 0」等同于「硬件已下发」：CLI 只读写配置库，返回 0 仅代表该命令这一段成功，这一点在本套资料中反复强调，排障时必须坚持按库逐段核对。

### 6. 版本差异

日志与返回码的版本差异集中在四个方向。第一，日志路径实现会演进：`show logging` 对 `/var/log.tmpfs` 的判断、是否纳入 `syslog.1`、以及 `grep` 与 `tail` 的特权边界，都是 `show/main.py` 中的具体实现，不同分支可能调整，需对照实际版本核验。第二，进程事件集合与退出码集合会变化：`supervisord.conf.j2` 中 `events` 列出的事件名、`exitcodes=0,3` 的取值，在不同容器、不同版本并不完全一致，telemetry 容器的 rsyslogd 段就与 swss 容器取不同 autorestart 策略。

第三，返回码常量是模块私有定义，不存在跨版本的统一表：consutil、config、cpoutil、psuutil、pddf 系列工具各自定义自己的错误码，同名常量在新增或下线工具时可能改变取值，本篇表格只反映本快照可核实的状态。第四，日志级别与文案随代码改动：`SWSS_LOG_*` 调用的字符串是开发时写入的，版本间可能增删改，排障时不能把某条文案当作稳定契约，只能当作当前版本的线索；宏定义所在的 `sonic-swss-common` 不在本快照，涉及宏本身的实现需对照实际版本核验。

此外，多 ASIC 命名空间、chassis 与 warm reboot 场景下的日志目录与实例划分「受平台与版本限制，需对照实际版本核验」，不得用单机假设套用。版本基准始终为「上游 master 快照（2026-11 抓取）」，具体版本号与文案以对应源码文件为准。凡本快照无法核实的内容，宁可标注核验要求并给出 `show/`、`dockers/`、`orchagent/`、`consutil/` 等可定位目录，也不补值。

### 7. 常见误用与调试

第一个高频误用是把返回码当通用约定读，看到 1 就认定「一般错误」、看到 2 就认定「用法错误」。在 SONiC 里，同一数字在不同工具中语义不同，必须连同出处一起判断；脱离 `consutil/lib.py`、`config/main.py`、`psuutil/main.py` 这样的来源，返回码就失去了意义。第二个误用是把 `config` 命令返回 0 等同于配置已在硬件生效，忽略从 `CONFIG_DB` 到 `ASIC_DB` 的异步流水线，结果在配置确实写入、但期望状态未生成时误判为正常，正确做法是按图 04-08-01 逐段核对，机制写「原理见 06-01」。

第三个误用是只搜 ERROR 级日志，忽略 NOTICE 里程碑的缺失或顺序错乱。在异步链路里，「本该出现的 NOTICE 没出现」往往比一条 ERROR 更能精确定位卡在哪一段。第四个误用是在跟随模式下仍期待进程过滤，发现 `-f` 输出里没有过滤效果就以为命令坏了，实际上按源码实现 `-f` 分支直接跟随 syslog，本就不叠加 grep。第五个误用是忽略 `syslog.1`，只看当前 syslog，结果漏掉轮转前的错误线索，尤其在设备刚重启后这一点格外关键。第六个误用是误改 `exitcodes` 或收窄 `events`，把正常退出当异常上报，或让 FATAL 静默，引发误重启或漏报。

调试同样按闭环推进。前置检查：确认命令名、选项与进程名在当前版本存在，记下要用的返回码出处文件。执行：先用 `show logging` 加 `--verbose` 取一段带命令串的日志，再用 `supervisorctl` 查关键进程状态，命令类问题则记录 `$?`。验证输出：把日志中的 NOTICE 里程碑按时间排开，确认链路走到哪一步；对 ERROR 行逐条分清是「参数被忽略并回退」的降级，还是「通知失败」这类实质故障；对返回码按出处还原语义。清理：撤销调试期开启的 verbose 等临时设置，确认无遗留会话与半配置状态，恢复稳定后再下结论。全程遵守「命令成功不等于硬件已下发」「日志正常不等于转发正常」两条边界；一切收敛时间、下发时延、吞吐类结论标注「需在目标机型实测」，本篇不给绝对值。

小结：本篇把日志检索参数、日志级别、返回码常量三张表与一张检索路径图整合为排错速查入口，图 04-08-01 给出从现象到逐段配置核对的决策顺序。三条纪律需要牢记：返回码必须与出处一起读、NOTICE 缺失同 ERROR 一样重要、命令返回成功不代表硬件已下发。至此 04 参数与 API 手册八个分册齐备，从构建变量、CONFIG_DB schema、Redis 对象、命令全集、SAI 与 orchagent 参数，到容器服务与本篇的日志返回码，构成一套可被逐项反查的参数字典；字段随查走 05 册，机制走 06 册，模块走 07 册，运维判读与案例走 08 册。
