# SONiC 技术资料 · 03 集成与部署（分片 C）

## 03-05 升级、warm reboot 与配置持久化

### 1. 目标与拓扑

本篇要完成的是一台已上线 SONiC 白盒交换机的三件运维动作：把运行镜像升级到新版本、在升级或维护窗口里用 warm reboot 尽量缩短转发中断、并确保配置在重启与升级后仍然正确落盘。这三件事在 SONiC 里并不是「一条命令」能概括的，它们分属三个不同的子系统：镜像升级由管理面的 `sonic-installer` 负责，warm reboot 由 `STATE_DB` 的开关与 `orchagent` 的冻结检查协同完成，配置持久化则由 `config save` 经 `sonic-cfggen` 把 `CONFIG_DB` 导出成 `/etc/sonic/config_db.json`。把三者混为一谈，是这一主题最常见的误判来源（参数见 04-05 ｜ 模块见 07-06）。

先明确「升级」在 SONiC 里的确切含义。从 `sonic-utilities-master/sonic_installer/main.py` 可以核实，`sonic-installer` 是一个基于 `click` 的命令组，Upgrade 不是覆盖正在运行的根文件系统，而是把新的 ONIE 安装包通过 bootloader 登记为「下一次启动镜像」，再经重启切换。命令组同时提供 `list`、`set-default`、`set-next-boot`、`install`、`remove`、`cleanup`、`verify-next-image`、`upgrade-docker`、`rollback-docker` 等子命令，并在检测到用下划线调用旧名 `sonic_installer` 时打印弃用警告、建议改用连字符形式。也就是说，升级的落点是 bootloader 里的镜像列表与 Next 指针，而不是一个可以被即时打补丁的活进程（模块见 07-11）。

再明确 warm reboot 的边界。WARM_RESTART 相关的开关和配置分布在两个库：`config/main.py` 里的 `warm_restart` 命令组会把 `enable` 字段写进 `STATE_DB` 的 `WARM_RESTART_ENABLE_TABLE`，把 `bgp_timer`、`neighsyncd_timer` 等写进 `CONFIG_DB` 的 `WARM_RESTART` 表；`upgrade-docker` 的注释更直接写明「warm restart enable/disable config is put in stateDB, not persistent across cold reboot, not saved to config_DB.json file」。这意味着 warm 开关默认不跨冷重启保留，升级完成后必须重新确认。同时 `orchagent` 一侧通过 `RESTARTCHECK` 通知通道与 `orchagent_restart_check` 工具握手，只有收到成功回复才进入冻结状态。整个能力受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持（原理见 06-10 ｜ 字段见 05-09）。

把上述三个子系统的落点与数据流向画在一起，就得到本篇的主拓扑，见图 03-05-01。

### 2. 前置条件与环境

动手之前，先把验证环境与权限边界确认清楚。所有 `sonic-installer` 命令都要求 root 权限：`main.py` 的 `sonic_installer` 组入口里有 `if os.geteuid() != 0: sys.exit("Root privileges required for this operation")`，普通用户执行会在任何实质动作之前直接退出。因此本篇命令默认在设备 root shell 下运行，示例输出一律注明「示例输出，具体格式需对照实际版本核验」，取值不得当作真实版本引用。

第二是镜像与 bootloader 的匹配。`sonic-installer install` 会先解析 URL：以 `http://` 或 `https://` 开头时走 `urlopen` 与 `urlretrieve` 下载到 bootloader 的默认路径，否则按本地相对路径处理；随后用 `bootloader.get_binary_image_version()` 校验文件是否为合法 SONiC 镜像，非法文件会在「Image file does not exist or is not a valid SONiC image file」处中止。`get_bootloader()` 从 `sonic_installer/bootloader/` 目录选择具体实现，该目录下可核实到 `grub.py`、`aboot.py`、`uboot.py`、`onie.py`、`bmc_uboot.py` 等，分别对应不同的引导栈；不同平台使用哪一种由构建与机型决定，需对照实际版本核验（模块见 07-11）。

第三是安装前置校验的顺序，它决定了失败时该看哪一行。`install` 在真正 `bootloader.install_image()` 之前依次检查：磁盘空间 `check_image_install_free_disk_space()`、安全启动类型一致性 `verify_secureboot_image()`、平台 ASIC 类型一致性 `verify_image_platform()`，若支持安全升级还会执行证书登记与签名验证 `enroll_image_secure_boot_keys()` 和 `verify_image_sign()`。镜像与当前平台 ASIC 类型不一致时，会提示用 `--skip-platform-check` 跳过——这是一个危险开关，跨越它之前必须确认目标镜像的 platform 与本机一致。内存不足时安装流程会经 `SWAPAllocator` 在 `/host/swapfile` 上临时建立 swap，磁盘空间低于阈值则报「Insufficient free disk space to install the image」。这些检查项与返回信息属于日志与返回码手册的范畴（参数见 04-08 ｜ 参数见 04-01）。

第四是配置持久化的常识。`config save` 默认把 `CONFIG_DB` 导出到 `DEFAULT_CONFIG_DB_FILE`，其实现通过 `sonic-cfggen -d --print-data` 生成 JSON 并排序落盘；`config load` 则是导入，并明确提示「loaded setting will be lost after system reboot. To preserve setting, run `config save`」。在多 ASIC 平台上，`save` 与 `load` 会为每个命名空间额外生成 `config_db0.json`、`config_db1.json` 等文件。升级流程本身也会调用 `config-setup backup` 备份当前配置，该脚本位于 `files/image_config/config-setup/config-setup`，usage 明确给出 `backup | boot | factory` 三种模式。因此「升级会不会丢配置」的正确答案是：升级流程会做备份，但日常改动仍需自己 `config save`（参数见 04-02 ｜ 模块见 07-11）。

第五是 warm reboot 的开关状态。前置检查要能读到三个事实：WARM_RESTART_ENABLE_TABLE 里对应模块的 `enable` 是否为 true、`CONFIG_DB` 的 WARM_RESTART 表里各 timer 取值、`orchagent` 是否处于可冻结的干净状态。前两者由 `show warm_restart config` 与 `show warm_restart state` 提供，第三者由 `orchagent_restart_check` 探测。把这些前置条件整理成一张清单，便于升级窗口前逐项打勾。

| 检查项 | 手段 | 期望特征 | 不满足的后果 |
|---|---|---|---|
| root 权限 | `id -u` | 返回 0 | 命令组入口直接退出 |
| 镜像合法 | `sonic-installer binary-version` | 打印版本字符串 | 安装中止并报非法镜像 |
| 平台一致 | `sonic-installer install` 自检 | 无类型告警 | 需 `--skip-platform-check`，风险自负 |
| 磁盘空间 | `check_image_install_free_disk_space` | 通过 | 报空间不足并中止 |
| 配置已备份 | `config save` 或安装脚本 backup | 文件存在且排序 | 升级后配置可能回退 |
| warm 开关 | `show warm_restart config` | enable 为 true | 退化为冷重启，中断变长 |

这张清单覆盖权限、镜像、平台、空间、配置、warm 六个维度，是升级窗口前的最小核验集；表中「需对照实际版本核验」的部分包括具体文件路径与字段取值，命令全集见 04-05。

### 3. 分步操作

下面按「前置检查 → 执行 → 验证输出 → 清理」的闭环，给出一次带 warm 语义的镜像升级与 warm reboot 完整操作。所有命令名与选项均来自 `sonic-utilities-master` 的可核验源码，选项是否在其他版本存在需对照实际版本核验。

**第一步，前置检查。** 先确认当前镜像、Next 镜像与镜像列表，再确认配置已落盘。

```bash
id -u
show version
sonic-installer list
sonic-installer binary-version ./sonic-image.bin
config save -y
```

执行后依次得到：root 用户 id 为 0；`show version` 打印当前软件版本与平台；`sonic-installer list` 列出当前与 Next 镜像；`binary-version` 打印安装包里的版本字符串；`config save -y` 静默导出当前配置。若 `binary-version` 打印「Image file does not exist or is not a valid SONiC image file」，说明安装包损坏或路径错误，不要继续。

**第二步，执行安装。** 用 `install` 子命令安装本地镜像；它会在内部完成下载校验、平台与安全校验、临时 swap、配置备份、环境更新、包迁移和三次 `sync`，最后打印 Done。

```bash
sonic-installer install -y ./sonic-image.bin
```

安装过程中若提示镜像类型与安全启动不一致，需判断是否确实要跨类型安装，再决定是否追加 `-f/--force`（谨慎）；若提示平台 ASIC 类型不一致，应停止并换用匹配镜像，而不是直接跳过平台检查。安装成功后，`install` 会把新镜像设为默认启动镜像。若只想在下次启动临时切到某个已安装镜像而不改默认，可改用 `sonic-installer set-next-boot <image>`；若要永久改默认，用 `sonic-installer set-default <image>`。

**第三步，配置 warm 开关并做冻结检查。** warm reboot 能否生效，取决于开关与 `orchagent` 状态。先看配置与状态，再开启，最后做干净状态探测。

```bash
show warm_restart config
show warm_restart state
config warm_restart enable
config warm_restart bgp_timer 1800
docker exec -i swss orchagent_restart_check -w 2000 -r 5
```

这里 `config warm_restart enable` 默认作用于 `system`，也可带模块名作用于 `bgp`、`swss`、`teamd` 等，模块名是否在 `FEATURE` 表里由命令校验。`enable` 写进 `STATE_DB`，`bgp_timer` 经 `mod_entry` 写进 `CONFIG_DB` 的 `WARM_RESTART` 表 `bgp` 键。`orchagent_restart_check` 的参数 `-w 2000 -r 5` 是超时与重试设置，其源码 `orchagent_restart_check.cpp` 通过向 `RESTARTCHECK` 通道发查询、监听 `RESTARTCHECKREPLY` 通道收回复，成功时打印成功信息并让 `orchagent` 进入冻结状态；未通过则明确拒绝 warm（原理见 06-10 ｜ 模块见 07-03）。

**第四步，触发重启并验证。** 冻结检查成功后执行重启，随后按第 4 节的方法逐项验证。

```bash
reboot
```

**第五步，清理。** 验证通过后，清理旧的、既非当前也非 Next 的镜像，释放磁盘空间；`cleanup` 会跳过当前与 Next 镜像。

```bash
sonic-installer cleanup
```

需要回滚时，若是整机镜像，用 `set-default` 指回旧镜像再重启；若是某个容器镜像的热升级，用 `sonic-installer rollback-docker <container_name>`，其源码对 `swss`、`bgp`、`teamd` 会提示「Cold reboot is required to restore system state after rollback」，即这些容器的回滚必须配合冷重启才能恢复状态。

### 4. 验证方法与预期结果

验证分为「升级是否成功」与「warm 状态是否恢复」两条线。先看镜像线与配置线，最直观的是 `sonic-installer list`。

```bash
sonic-installer list
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
Current: SONiC.HEAD.2026-11-13-a1b2c3d4
Next: SONiC.HEAD.2026-11-13-a1b2c3d4
Available:
SONiC.HEAD.2026-11-01-0e1f2a3b
SONiC.HEAD.2026-11-13-a1b2c3d4
```

逐行判读如下。第一行 `Current` 是 bootloader `get_current_image()` 返回的当前运行镜像，重启后若升级成功，它应指向新版本；若仍停留在旧版本，说明 Next 指针未生效或重启未真正发生。第二行 `Next` 来自 `get_next_image()`，表示下一次启动将加载的镜像；升级完成后 `Current` 与 `Next` 一致是正常特征，若二者长期不一致，需检查是否有一次性的 `set-next-boot` 仍悬而未决。第三行 `Available` 是已安装镜像列表的表头，来自 `get_installed_images()`，它决定 `set-default`、`remove`、`set-next-boot` 的合法参数集合——不在该列表中的镜像名会被拒绝。第四、五行是列表中两个具体镜像标识，命名模式由构建产物决定，本套资料统一按「上游 master 快照（2026-11 抓取）」表述，示例中的版本串只作格式示意，不得当作真实版本号引用，具体取值需对照实际版本核验。把这份输出与升级前对比，就能确认「新镜像是否进入 Available 并成为 Current」。输出块已注明示例输出与版本核验要求（参数见 04-05 ｜ 模块见 07-11）。

再看 warm 状态线。先读配置，再读运行时状态。

```bash
show warm_restart config
show warm_restart state
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
name    enable   timer_name        timer_duration   eoiu_enable
system  true     NULL              NULL             NULL
bgp     true     bgp_timer         1800             false
swss    false    neighsyncd_timer  NULL             NULL
name          restore_count    state
orchagent     1                reconciled
neighsyncd    1                reconciled
bgp           0                reconciled
```

对第二段输出做逐行判读。上半段是 `show warm_restart config`，列头 `name / enable / timer_name / timer_duration / eoiu_enable` 可在 `show/warm_restart.py` 的 `tablelize` 函数中核实；该函数把 `CONFIG_DB` 的 `WARM_RESTART` 表与 `STATE_DB` 的 `WARM_RESTART_ENABLE_TABLE|*` 合并。`system` 行 `enable` 为 true，说明系统级 warm 开关已打开；`bgp` 行 `bgp_timer` 为 1800，与前面 `config warm_restart bgp_timer 1800` 对应，`eoiu_enable` 为 false 是默认行为；`swss` 行 `enable` 为 false，意味着该模块的 warm 未开启，这是需要重点关注的差异——若期望 swss 也 warm，须补执行按模块的 `enable`。下半段是 `show warm_restart state`，列头 `name / restore_count / state`，直接读 `STATE_DB` 的 `WARM_RESTART_TABLE|*`，其中 `state` 为 `reconciled` 是 `upgrade-docker` 源码里 `exp_state = "reconciled"` 所等待的目标状态，表示应用已完成状态协调；`restore_count` 记录恢复次数，重启后取值大于零通常说明 warm 恢复确实发生过。若某应用 `state` 长期不是 `reconciled`，说明 warm 未完成，需按第 5 节排查（字段见 05-09 ｜ 原理见 06-10）。

验证配置持久化时，可对比 `config save` 落盘前后 `/etc/sonic/config_db.json` 的关键表项是否一致，并确认文件存在、内容经排序；导入侧用 `config load` 验证能否恢复。需要强调的是，`config load` 自身提示「loaded setting will be lost after system reboot. To preserve setting, run config save」，所以验证的终点始终是「重启后 `CONFIG_DB` 表项与预期一致」，而不是「load 命令返回成功」（参数见 04-02 ｜ 参数见 04-05）。

### 5. 常见失败与排错

第一类失败是安装前置校验中止。典型现象是 `sonic-installer install` 在真正安装前退出，并打印「Insufficient free disk space」「Image file is of a different platform ASIC type」或安全启动类型不一致提示。根因分别是磁盘空间不足、镜像 platform 与本机不匹配、安全启动类型不同。正确处理是先读提示定位到 `install` 流程的哪一道检查：空间不足就清理旧镜像（用 `cleanup`）或扩容；平台不匹配就换匹配镜像，不要轻易用 `--skip-platform-check` 越过；安全类型不一致要确认镜像来源可信后再决定是否用 `-f`。跳过这些检查虽然能让命令继续，但会把风险推迟到重启之后（参数见 04-08 ｜ 排障见 08-03）。

第二类失败是 warm reboot 没有按预期缩短中断，甚至退化为冷重启。最常见根因是 warm 开关没有跨重启保留——`upgrade-docker` 源码明确说明 enable/disable 配置在 `STATE_DB`、不写入 `config_db.json`、不跨冷重启持久化。因此升级重启后必须重新用 `show warm_restart config` 确认开关，必要时重开。第二常见根因是 `orchagent` 未通过冻结检查：`orchagent_restart_check` 会输出「RESTARTCHECK failed」或超时信息，此时系统不会进入 warm，应转而排查 `orchagent` 是否有未完成的任务，而不是强行 warm。第三类根因是模块级开关遗漏，例如系统级已 enable 但 `swss` 仍为 false，导致部分应用走冷启动路径（原理见 06-10 ｜ 字段见 05-09）。

第三类失败是升级后配置「回退」到旧状态。根因通常是改动只停留在 `CONFIG_DB` 运行时而未 `config save` 落盘，或升级流程的 `config-setup backup` 备份的是升级前快照、之后又执行了 factory 模式覆盖了配置。正确做法是把 `config save` 纳入变更流程的固定步骤，并在升级后对比 `config_db.json` 关键表项；若要恢复出厂，`config-setup factory` 会重建默认配置，须谨慎使用（模块见 07-11）。

第四类失败是容器热升级回滚后状态不一致。`sonic-installer rollback-docker` 源码要求镜像存在两个版本，否则报「Two images required」；对 `swss`、`bgp`、`teamd` 回滚后明确提示需要冷重启恢复系统状态。若忽略该提示，可能出现 `show warm_restart state` 中各应用状态与配置不匹配的现象，处理方式是按提示执行冷重启后重新核验（参数见 04-05 ｜ 排障见 08-04）。

把上述失败归纳成对照表，便于现场按现象快速定位。

| 现象 | 首要证据 | 可能根因 | 处理方向 |
|---|---|---|---|
| 安装提前退出 | 提示行内容 | 空间/平台/安全校验未过 | 按提示逐项修复 |
| warm 退化为冷启动 | show warm_restart config | enable 未跨重启保留 | 重启后重开开关 |
| 冻结检查失败 | RESTARTCHECK failed | orchagent 有未完成任务 | 排查控制面后再试 |
| 配置升级后回退 | config_db.json 对比 | 未 config save | 落盘后再升级 |
| 容器回滚异常 | rollback-docker 提示 | swss 等需冷重启 | 按提示冷重启 |

表中每一行都遵循「现象 → 证据 → 根因 → 处理」的顺序，目的是让读者先证据后结论，避免凭现象直接下判断。完整诊断树与案例见 08 册（排障见 08-03 ｜ 排障见 08-04）。

### 6. 小结

本篇把升级、warm reboot 与配置持久化三件事拆成了可核验的闭环。升级的落点是 bootloader 的镜像列表与 Next 指针，由 `sonic-installer` 的 `install`、`list`、`set-default`、`set-next-boot`、`cleanup` 等子命令操作；warm reboot 的开关位于 `STATE_DB` 的 `WARM_RESTART_ENABLE_TABLE`、timer 位于 `CONFIG_DB` 的 `WARM_RESTART` 表，且开关默认不跨冷重启持久化；配置持久化由 `config save` 经 `sonic-cfggen` 落盘到 `/etc/sonic/config_db.json`。图 03-05-01 给出三者在一次变更窗口内的衔接关系，两张表分别给出升级前检查清单与失败对照。

需要始终守住三条边界。其一，命令返回成功不等于升级或 warm 已完成，判读要落到 `sonic-installer list` 的 Current/Next、`show warm_restart state` 的 `reconciled` 状态与 `config_db.json` 的表项对比上。其二，warm reboot、多 ASIC 与 chassis 能力受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持；所有收敛时间、中断时长与吞吐数字一律标注「需在目标机型实测」（基准方法见 08-01）。其三，不确定的命令选项、表名与字段取值一律写「需对照实际版本核验」并给出 `sonic_installer/`、`config/`、`show/`、`warmrestart/` 等可定位目录，不凭印象补值。

跨册反查按统一约定：WARM_RESTART、PORT_STATE、platform.json 等结构字段见 05-09；sonic-installer、show/config 命令全集见 04-05，日志与返回码见 04-08；warm reboot 状态恢复机制见 06-10；sonic-utilities CLI 与 config 模块能力见 07-06、镜像与 onie/installer 模块见 07-11。综合起来即（字段见 05-09 ｜ 参数见 04-05 ｜ 原理见 06-10 ｜ 模块见 07-06）。下一篇 03-06 把视角从单机升级扩展到多设备、多 ASIC 与容器化运维部署。

## 03-06 多设备、多 ASIC 与容器化运维部署

### 1. 目标与拓扑

当运维对象从「一台交换机」变成「一批不同机型的交换机」乃至「一台内含多个转发 ASIC 的机箱」时，03-05 那套单机流程就会失效：不同机型的端口、lane、速率由不同的 HWSKU 决定，一台多 ASIC 设备内部又同时存在若干个彼此隔离的 Redis 命名空间，任何一个 `config` 命令都可能只作用在某一个命名空间里。本篇的目标是把部署维度从单机扩展到「多设备 + 多 ASIC + 容器化统一运维」三层，给出可执行的批量生成、分命名空间接入与状态核验方法（模块见 07-10 ｜ 模块见 07-02）。

先厘清三个容易混淆的概念。第一，「多设备」指数据中心里成百上千台白盒交换机，它们的共性是运行同一套 SONiC 软件、差异在机型与 HWSKU，因此配置生成的入口是 `device/<vendor>/<hwsku>/` 目录——本快照里可核实到 accton、arista、barefoot、celestica、dell、mellanox、marvell 等厂商下大量机型目录，每个目录含 `platform.json`、`minigraph.xml`、`config_db*.json`。第二，「多 ASIC」指一台设备内有多个转发芯片，每个 ASIC 对应一个 Linux 网络命名空间与一组独立的数据库实例，`sonic_py_common/multi_asic.py` 用 `get_num_asics()`、`is_multi_asic()`、`get_all_namespaces()` 来判定与枚举。第三，「chassis」指 supervisors 与线卡分离、或分布式、智能交换机形态，依靠 midplane 上的 chassis database 交换跨卡状态，`files/image_config/config-chassisdb/config-chassisdb` 脚本负责把它接入（原理见 06-11 ｜ 模块见 07-10）。

这三层能力都受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持。尤其要守住全册共识：SONiC 是白盒交换机 NOS，控制面在容器进程、数据面在 ASIC，除 `platform/vs/` 外不做软件转发；多 ASIC 只是把同一套控制面按命名空间复制成多份，并未改变「`CONFIG_DB` → `APPL_DB` → `ASIC_DB` → SAI」的异步流水线（原理见 06-01）。把多 ASIC 误解成「多个 SONiC 实例跑在一台机器上」虽有几分形似，但会忽略宿主命名空间里统一的管理面与 chassis 数据库这一关键黏合层（原理见 06-11）。

把多设备、多 ASIC 与命名空间的关系画在一起，得到本篇主拓扑，见图 03-06-01。

### 2. 前置条件与环境

第一项是确认设备是否真的处于多 ASIC 模式，而不是凭机型名称猜测。判定逻辑在 `sonic_py_common/multi_asic.py`：`get_num_asics()` 读取 asic 配置文件中的 `num_asic` 项，找不到配置文件时返回 1；`is_multi_asic()` 就是 `get_num_asics() > 1`；`get_all_namespaces()` 遍历每个 ASIC 命名空间，读取 `DEVICE_METADATA` 的 `localhost` 键下 `sub_role` 字段，按 `FRONTEND`、`BACKEND`、`FABRIC` 等取值把它们分入 `front_ns`、`back_ns`、`fabric_ns` 三组。因此现场判定的可信来源是 `show platform summary` 的 ASIC Count，加上 Python 侧的命名空间枚举，而不是端口数量或 ASIC 型号名称（字段见 05-09 ｜ 模块见 07-10）。

第二项是理解命名空间的命名与常量。`config/main.py` 与 `utilities_common/multi_asic.py` 中可核实到 `NAMESPACE_PREFIX = 'asic'`、`DEFAULT_NAMESPACE = ''`（空字符串代表 Linux 宿主命名空间），以及 `HOST_NAMESPACE = 'localhost'` 一类的取值；`sonic_py_common/multi_asic.py` 里还有 `ASIC_NAME_PREFIX`、`get_asic_id_from_name()`（从 `asicN` 名字里取编号）、`get_asic_device_id()`（读形如 `DEV_ID_ASIC_0=03:00.0` 的 PCI 设备号）、`get_asic_sub_role()`（读 `SUB_ROLE_ASIC_<id>`）等函数。这些常量与函数说明：命名空间不是命令行随手编的字符串，而是由 asic 配置与 `DEVICE_METADATA` 共同决定的合法集合，传入非法名字时 `config`、`show` 命令会报「Invalid namespace」（参数见 04-04 ｜ 字段见 05-09）。

第三项是数据库实例与逻辑库的命名空间化。`dockers/docker-database/multi_database_config.json.j2` 是多 ASIC / chassis 场景的数据库配置模板，其中可核实到 `redis`、`redis1` 到 `redis4`、`redis_chassis` 等多个 `INSTANCES`，以及 `CHASSIS_APP_DB`、`CHASSIS_STATE_DB` 等指向 `redis_chassis` 实例的库，各实例还带有 `persistence_for_warm_boot` 属性。对应地，`sonic-py-swsssdk/src/swsssdk/dbconnector.py` 的 `SonicDBConfig` 提供 `load_sonic_global_db_config()`、`namespace_validation()`、`db_name_validation()`、`get_dblist(namespace)` 等接口，`source/swsssdk/configdb.py` 的 `ConfigDBConnector` 可带 `namespace` 与 `use_unix_socket_path` 参数连接指定命名空间。这印证了 01 册的纪律：DB 编号与实例是运行时配置决定的，须对照 `SonicDBConfig` 与实际版本核验，不得写死（字段见 05-03 ｜ 参数见 04-04）。

第四项是 chassis 的前置。对于 supervisor / 线卡分离或分布式形态，`files/image_config/config-chassisdb/config-chassisdb` 会在 `database-chassis` 服务启动前运行：它按 `PLATFORM` 找到 `chassisdb.conf`，判断 `is_supervisor`、`is_disaggregated_chassis`、`is_smartswitch`、`is_dpu`，从 midplane 接口（如 supervisor 的 `eth1-midplane`，或经 platform API 的 `get_midplane_ip()`）取出 IP，写入 `/etc/sonic/chassisdb_address` 并把 `chassis_db_address` 校验在 midplane 子网内，最后更新 `/etc/hosts` 里的 `redis_chassis.server` 映射。虚拟交换机场景（`asic_type` 为 `vs`）会跳过大部分平台 API 流程。这意味着 chassis 能力高度依赖平台实现，本快照无法核实具体机型的 midplane 行为，一律写「受平台与版本限制，需对照实际版本核验」（模块见 07-11 ｜ 原理见 06-11）。

把上述前置条件整理成一张核验清单，便于批量部署前逐项确认。

| 检查项 | 依据来源 | 期望特征 | 不满足时的影响 |
|---|---|---|---|
| 是否多 ASIC | `show platform summary` | ASIC Count 大于 1 | 命名空间命令无意义 |
| 命名空间集合 | `get_all_namespaces()` | 返回前/后端分组 | 非法命名空间被拒绝 |
| sub_role 字段 | `DEVICE_METADATA` | 前端/后端/fabric 取值 | 无法正确分组 |
| 数据库实例 | `multi_database_config.json.j2` | 每命名空间独立实例 | 数据串库风险 |
| chassis 地址 | `config-chassisdb` 脚本 | 地址在 midplane 子网 | 跨卡状态不可达 |

这张清单覆盖判定、命名空间、角色字段、数据库隔离与 chassis 五个维度；表中涉及的字段与模板路径均可在本快照定位，但具体取值需对照实际版本核验，配置与 schema 全集见 04-02、04-04。

### 3. 分步操作

下面按「前置检查 → 执行 → 验证输出 → 清理」的闭环，给出多设备批量配置与多 ASIC 分命名空间接入的操作。命令名与选项均来自可核验源码，其他版本是否存在需对照实际版本核验。

**第一步，前置检查。** 确认平台、ASIC 数量与命名空间枚举能力。

```bash
show platform summary
sonic-cfggen -H -v DEVICE_METADATA.localhost.platform
python3 -c "from sonic_py_common.multi_asic import get_num_asics, is_multi_asic, get_all_namespaces; print(get_num_asics(), is_multi_asic(), get_all_namespaces())"
```

第一条给出 Platform、HwSKU、ASIC、ASIC Count 等字段；第二条用 `sonic-cfggen -H` 取本机 platform（`config-chassisdb` 脚本正是用这一方式取 platform），是选择 `device/<vendor>/<hwsku>/` 目录的锚点；第三条直接调用 `multi_asic.py` 的三个函数，打印 ASIC 数量、是否多 ASIC 与按角色分组的命名空间字典。若第三条报错，通常说明 `sonic_py_common` 未就绪或 asic 配置缺失，先解决环境再继续（模块见 07-10）。

**第二步，执行批量配置生成。** 对每个 HWSKU 用 `sonic-cfggen` 从 minigraph 与端口配置渲染 `config_db.json`，再统一下发到目标设备。

```bash
sonic-cfggen -m /etc/sonic/minigraph.xml -k <hwsku> -p /usr/share/sonic/hwsku/port_config.ini -d --print-data > config_db.json
for host in leaf-01 leaf-02 leaf-03; do scp config_db.json "$host:/etc/sonic/config_db.json"; done
```

这里 `-m`、`-k`、`-p`、`-d`、`--print-data` 等选项的完整含义见 04-02，本册只给最小必要用法；`<hwsku>` 需替换为实际机型，各机型目录见 `device/<vendor>/<hwsku>/`。批量下发用 `scp` 只是示意，生产环境应通过配置管理通道下发并校验文件完整性（参数见 04-02 ｜ 参数见 04-05）。

**第三步，按命名空间接入与核验。** 在确认是多 ASIC 的设备上，用 `-n` / `--namespace` 选项逐命名空间查看端口与 warm 状态。

```bash
show interfaces status -n asic0
show warm_restart config -n asic0
sonic-cfggen -n asic0 -d --print-data
```

`config save` 的源码表明，多 ASIC 时会为每个命名空间额外生成 `config_db<NS>.json`（如 `config_db0.json`），单命名空间保存则调用 `sonic-cfggen -n <namespace> -d --print-data`。因此第三步既是验证也是排错入口：若 `show interfaces status -n asic0` 与 `-n asic1` 看到不同端口集合，说明命名空间隔离正常；若两者完全一致，需怀疑 `-n` 未生效或命令未实现命名空间选项（参数见 04-05 ｜ 模块见 07-06）。

**第四步，chassis 场景接入。** 在 supervisor / 线卡形态上，确认 chassis DB 地址落位后启动相关服务。

```bash
cat /etc/sonic/chassisdb_address
getent hosts redis_chassis.server
systemctl status database-chassis
```

`config-chassisdb` 脚本在 `/etc/sonic/chassisdb_address` 中写入 `chassis_db_address=<midplane IP>`，并在 `/etc/hosts` 中追加 `redis_chassis.server` 映射；`getent hosts` 用于确认该映射可被解析。若地址为空或不在 midplane 子网，脚本会报错退出，需回到 midplane 接口配置排查。非 chassis 平台可跳过本步（模块见 07-11 ｜ 原理见 06-11）。

**第五步，清理。** 删除批量下发的临时文件，恢复到干净状态。

```bash
rm -f /tmp/config_db.json /etc/sonic/chassisdb_address.bak
```

清理仅针对本次生成的临时产物，不触碰 `/etc/sonic/config_db.json` 与各命名空间正式配置；正式配置的变更须走 `config save` / `config load` 并留痕（参数见 04-05）。

### 4. 验证方法与预期结果

验证分三层：单机平台信息、多 ASIC 命名空间隔离、chassis 跨卡连通。先看单机平台信息，`show platform summary` 的输出来自 `show/platform.py` 的 `summary()`，字段可直接对照。

```bash
show platform summary
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
Platform: x86_64-some_vendor_some-platform-r0
HwSKU: some-hwsku-32x100G
ASIC: some_asic
ASIC Count: 2
Serial Number: SN0123456789
Model Number: MODEL-ABCD
Hardware Revision: RevA
Switch Type: switch
```

逐行判读如下。第一行 `Platform` 对应 `device/<vendor>/<hwsku>/` 目录的机型标识，是选择端口配置与 SAI 适配的锚点，示例中 `x86_64-some_vendor_some-platform-r0` 只是格式示意，具体取值需对照实际版本核验；第二行 `HwSKU` 指向同一目录下的 `config_db*.json` 与 `minigraph.xml`，是 03-02 所述配置落地的依据；第三行 `ASIC` 给出芯片类型，本套资料不写死具体厂商型号；第四行 `ASIC Count` 是判定是否多 ASIC 的关键，这里为 2，意味着应存在 `asic0`、`asic1` 两个前端/后端命名空间，与第三步的 `get_all_namespaces()` 结果相互印证，若 `ASIC Count` 为 1 却看到命名空间，说明环境不一致；第五至七行 Serial Number、Model Number、Hardware Revision 来自 chassis 信息与 EEPROM，用于资产核对，不同批次设备取值不同属正常；第八行 `Switch Type` 仅在平台提供该字段时输出，缺省时可 absent。以上字段的读取在 `show/platform.py` 中经 `device_info.get_platform_info()` 与 `get_chassis_info()` 完成，本快照不含这些实现细节，需对照实际版本核验。输出块已注明示例输出与版本核验要求，取值不得当作真实设备数据引用（模块见 07-10 ｜ 字段见 05-09）。

再看命名空间隔离的验证。逐命名空间取端口状态并比对，同时确认 `ASIC_DB` 对象是否分别落在各自实例中。

```bash
show interfaces status -n asic0 --display all
show interfaces status -n asic1 --display external
show ip interfaces -n asic0
```

`utilities_common/multi_asic.py` 提供 `--display` 选项（`DISPLAY_ALL` 与 `DISPLAY_EXTERNAL`）与 `--namespace`/`-n` 选项，并通过 `MultiAsic.get_ns_list_based_on_options()` 把前端、后端、fabric 命名空间按选项展开，`is_object_internal()` 判定某个端口、PortChannel 或 BGP 邻居是否为 ASIC 间内部对象，`skip_display()` 据此决定是否过滤。因此 `--display all` 会显示内部互连端口，`--display external` 只显示对外端口；若在多 ASIC 设备上不加区分地看汇总输出，容易把内部端口当成业务端口，或误判端口数量不足。判读要点是：同一命名空间内端口名与 `PORT` 表一致（表名与字段见 04-02），跨命名空间的内部端口不会出现在 `--display external` 结果里（原理见 06-11 ｜ 模块见 07-06）。

最后确认 chassis 跨卡连通：以 `redis_chassis.server` 解析结果与 `CHASSIS_APP_DB` / `CHASSIS_STATE_DB` 的可达性为准。由于这两个库指向 `redis_chassis` 实例并经 midplane 访问，只有 midplane IP 正确、`/etc/hosts` 映射生效、`database-chassis` 服务运行三者同时满足时才可判为正常。任一环节失败都应回到 `config-chassisdb` 脚本的报错信息定位，不得据此推断 ASIC 转发故障。所有收敛、时延与吞吐类结论一律标注「需在目标机型实测」（基准方法见 08-01 ｜ 调优见 08-02）。

### 5. 常见失败与排错

第一类失败是命名空间不存在或 `-n` 选项无效。现象是 `show ... -n asic0` 报「Invalid namespace: asic0」，或输出与不带 `-n` 时完全一致。根因通常是：`get_namespace_list()` 返回的合法集合里没有该名字（多 ASIC 判定为假时只有默认命名空间），或所用命令未实现命名空间选项。`show/warm_restart.py` 与 `config/main.py` 都会用 `multi_asic.get_namespace_list()` 校验传入的 namespace，非法值直接抛 `UsageError`。处理方向是先跑 `get_all_namespaces()` 确认合法集合，再检查命令是否支持 `-n`，不要凭端口数量推测命名空间名（原理见 06-11 ｜ 排障见 08-03）。

第二类失败是端口在汇总里「消失」。现象是 `show interfaces status` 看不到某些端口，尤其在多 ASIC 设备上。根因是 `--display` 默认为 `DISPLAY_EXTERNAL`（`multi_asic_display_default_option()` 在非单 ASIC 或 chassis 场景返回该值），内部互连端口被 `skip_display()` 过滤。处理方式是加 `--display all` 复查；若加了仍缺失，再按 `CONFIG_DB` → `APPL_DB` → `ASIC_DB` 顺序逐段核对，而不是直接怀疑芯片。这里再次体现全册共识：`config` 返回成功不等于硬件已下发，判读要落到各库表项（原理见 06-01 ｜ 排障见 08-03）。

第三类失败是配置下发到多 ASIC 设备后状态不一致。现象是宿主命名空间配置正确，但某个 `asic<N>` 命名空间端口起不来。根因通常是批量下发时只改了宿主 `config_db.json`、漏了 `config_db0.json` / `config_db1.json`，或 `config save` 在多 ASIC 下生成了多文件而下发时只取了其中一个。`config/main.py` 的 `save()` 明确在多 ASIC 时按 `NAMESPACE_PREFIX + inst` 生成 `config_db<NS>.json` 并逐个写盘，`load()` 同样按文件列表逐个导入。处理方向是核对每个命名空间对应的配置文件是否齐全、内容是否一致（参数见 04-05 ｜ 模块见 07-06）。

第四类失败是 chassis 跨卡状态不可达。现象是 `chassisdb_address` 为空、`getent hosts redis_chassis.server` 无解析，或 `CHASSIS_STATE_DB` 读不到线卡状态。根因可能是 midplane 接口未起、`chassisdb.conf` 缺失（脚本会打印「no chassisdb.conf found, bypass config-chassisdb service」并退出）、地址不在 midplane 子网（脚本报「chassis_db address does not belong to midplane subnet」），或 supervisor 的 `eth1-midplane` 在 180 秒重试内未拿到 IP。处理方式是按 `config-chassisdb` 的报错分支逐项排查 midplane 与 platform API；虚拟交换机场景会跳过大部分平台 API，不应据此推断真实机箱行为（模块见 07-11 ｜ 原理见 06-11）。

把失败按现象归并，便于现场快速定位。

| 现象 | 首要证据 | 可能根因 | 处理方向 |
|---|---|---|---|
| 命名空间被拒 | `get_all_namespaces()` | 名字不在合法集合 | 重新枚举命名空间 |
| 端口汇总缺失 | 加 `--display all` 复现 | 内部端口被过滤 | 切换显示选项 |
| 某 ASIC 状态异常 | 各 `config_dbN.json` | 分命名空间配置漏下发 | 逐命名空间补齐 |
| 跨卡状态不可达 | `chassisdb_address` | midplane 或地址配置错 | 排查 chassis 脚本分支 |

表中每行遵循「现象 → 证据 → 根因 → 处理」顺序；四行分别对应命名空间、显示、配置、chassis 四类高频问题。完整诊断树与案例见 08 册（排障见 08-03 ｜ 排障见 08-04）。

### 6. 小结

本篇把部署从单机扩展到三个维度。多设备维度以 `device/<vendor>/<hwsku>/` 为配置源，用 `sonic-cfggen` 按 HWSKU 渲染并批量下发，多 ASIC 时须同时生成宿主与各 `config_dbN.json`；多 ASIC 维度以 `sonic_py_common/multi_asic.py` 的 `get_num_asics()`、`is_multi_asic()`、`get_all_namespaces()` 为判定基础，通过 `-n` / `--namespace` 与 `--display` 选项分命名空间接入；容器化运维维度依靠 `dockers/` 容器族与统一 CLI，chassis 场景再由 `config-chassisdb` 接入 midplane 上的 chassis database。图 03-06-01 给出三者的衔接关系，两张表分别给出前置核验清单与失败对照。

需要守住三条边界。其一，多 ASIC、chassis 与 warm reboot 能力受平台与版本限制，需对照实际版本核验，不得宣称全平台无条件支持；`asic_type` 为 `vs` 的虚拟交换机会跳过多数平台 API，不能用来推断真实机箱行为。其二，DB 编号与实例由运行时配置（`database_config.json`、`database_global.json` 及其模板）决定，须对照 `SonicDBConfig` 核验，不得写死；`config` 返回成功不等于硬件已下发，判读要落到各命名空间各库的表项与 `show` 输出（原理见 06-01）。其三，不确定的命令选项、表名、字段与函数签名一律写「需对照实际版本核验」并给出可定位目录，不凭印象补值；收敛、时延、吞吐一律标注「需在目标机型实测」（基准方法见 08-01）。

跨册反查按统一约定：`DEVICE_METADATA` 的 `sub_role`、`WARM_RESTART`、`platform.json`、`PORT_STATE` 等结构字段见 05-09，`SonicDBConfig` 字段见 05-03；Redis 命名空间、逻辑库与对象见 04-04，show/config 命令全集见 04-05，机型 schema 见 04-02；多 ASIC 与 chassis 数据库命名空间机制见 06-11，异步流水线见 06-01；platform/device/HWSKU 模块见 07-10，dockers 容器族见 07-02，镜像与 onie/installer 模块见 07-11。综合起来即（字段见 05-09 ｜ 参数见 04-04 ｜ 原理见 06-11 ｜ 模块见 07-10）。03 册至此收束：从 vs 启动、配置落地、基础配置、CLI 接入，到升级与 warm reboot，再到本篇的多设备与多 ASIC 部署，构成一条从单机到规模化的完整部署主线。
