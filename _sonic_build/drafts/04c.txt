# SONiC 技术资料 · 04 参数与 API 手册（分片 C）

## 04-05 sonic-cli / show / config 命令全集

### 1. 本篇定位与覆盖范围

本篇是 04 册命令族的唯一权威源，集中罗列 sonic-utilities 子仓对外暴露的命令行入口及其参数：包括交互式外壳 sonic-cli、只读状态的 show 族、写配置的 config 族，以及 clear、counterpoll、crm、debug 等辅助命令族。全册统一约定：命令「怎么敲、有哪些选项、默认值是什么、误配有什么后果」由本篇给出；命令背后的实现机制不在本篇展开，凡涉及「配置如何逐段下发到芯片」一律写「原理见 06-01 ｜ 原理见 06-14」；凡涉及命令读取的表项字段结构一律写「字段见 05-02 ｜ 字段见 05-03」；凡涉及命令族所在容器与模块边界一律写「模块见 07-06」。本套资料的版本基准是上游 master 快照（2026-11 抓取），命令名、选项名与默认值以本快照源码为准，凡本快照无法核实者一律标注「需对照实际版本核验」，不得凭印象补全。

先厘清三个词的关系，它们常被混为一谈。其一是 sonic-cli，它是 SONiC 的交互式命令外壳，提供一个可连续输入命令的会话环境，本身并不实现具体子命令，而是把输入分派给底层命令程序；其二是 show，它是只读命令族，负责从各数据库读取状态并格式化输出；其三是 config，它是写配置命令族，负责把用户意图写入配置库。三者的源码落点都可在 `sonic-utilities/sonic-utilities-master/` 内核实：CLI 程序与启动入口由 `setup.py` 的 `entry_points.console_scripts` 段声明，`show/main.py` 与 `config/main.py` 分别是 show 族与 config 族的 click 组定义与子命令注册处，`utilities_common/` 提供公共的连接与参数校验封装，各业务子命令则分散在 `show/`、`config/` 目录下的 `vlan.py`、`bgp_cli.py`、`feature.py`、`aaa.py` 等文件中（模块见 07-06）。

覆盖范围需要划清边界，避免与其他册重复。本篇只回答「命令层」的问题：一个命令叫什么、属于哪个命令族、接受哪些参数、默认值如何、输出大致什么形态、敲错会怎样。至于 `config` 写入 `CONFIG_DB` 后由哪些 `*mgrd` 搬到 `APPL_DB`、再由 `orchagent` 翻译成 ASIC 对象的完整异步链路，本篇不重列，统一写「原理见 06-01 ｜ 原理见 06-03 ｜ 原理见 06-04」；至于命令读写的 `PORT`、`VLAN`、`BGP` 等表的逐字段定义，属于 05 册范畴，写「字段见 05-02」，config 库表与 schema 参数全集见本册 04-02、04-03，DB 编号见 04-04，本篇同样不重复。需要强调的是，show 与 config 只读写数据库、不直接编程 ASIC，这是 CLI 的能力边界，任何把命令返回成功等同于硬件已下发的说法都与本套资料的结论冲突（原理见 06-01）。

事实核验方面，本篇的可信度建立在少数几个可定位的源码锚点上。`setup.py` 的 `console_scripts` 段给出了对外命令名到 Python 入口函数的映射，这是判断「某命令是否存在」的第一依据；`show/main.py` 与 `config/main.py` 中的 `click.group`、`add_command` 与 `@cli.command` 装饰器给出了命令族的子命令挂载关系；`show/main.py` 中 `version` 等函数的 `click.option`、`click.argument` 给出了具体选项与参数是否必填；`config/main.py` 顶部 `DEFAULT_CONFIG_DB_FILE = '/etc/sonic/config_db.json'` 等常量给出了 `config save` / `config load` 的默认文件路径。这些取值均可在本快照内核实，本篇据此成文；而具体输出格式、列宽、命令行提示语会随版本与集成方式变化，示例输出一律标注「示例输出，具体格式需对照实际版本核验」，不得当作任何具体版本的真实回显引用。

|---|---|---|---|---|

config 族是写入侧，误配的破坏性更大，因此其参数与默认值更需逐项核对。下表中的 `save`、`load`、`hostname` 均可在 `config/main.py` 核实：`save` 带 `-y/--yes` 确认开关与可选 `filename` 参数，`hostname` 接受必填的 `new_hostname`，默认配置文件路径来自文件顶部常量；`config` 组本身使用 `AbbreviationGroup`，意味着子命令支持缩写匹配，这一点在排障时要特别留意。

| config 子命令 | 取值（参数） | 默认值 | 作用 | 误配后果 |
|---|---|---|---|---|
| `config save` | `-y/--yes`、文件名 | `/etc/sonic/config_db.json` | 导出当前配置库到文件 | 覆盖有效配置文件致配置丢失 |
| `config load` | 文件名、`-y` | 默认配置文件 | 从文件载入配置库 | 载入旧配置覆盖现行配置 |
| `config hostname` | `<new_hostname>` 必填 | 无 | 改 `DEVICE_METADATA` 主机名 | 拼写错误致主机名异常 |
| `config reload` | 多选项见源码 | 重启服务 | 重新加载并重启服务 | 未 `save` 即 reload 丢失改动 |
| `config apply-patch` | JSON 补丁 | 无 | 补丁式更新配置 | 补丁路径错致部分配置未生效 |
| `config vlan` | `add`/`del` 等 | 无 | VLAN 增删 | 成员口写错致转发异常 |

这三张表构成本篇的索引主干。需要说明，表只列最常用的代表项而非穷举，完整命令清单以 `show/` 与 `config/` 目录下的源码为准；凡本快照未能核实的选项名与默认值，均标注「需对照实际版本核验」。此外，`show ip route` 一类命令经 `vtysh_command` 转发给路由协议栈，而 FRR / FRRouting 源码不在本快照，相关命令的实际输出需对照实际版本核验（模块见 07-08）。

### 3. 逐项详解

先说 show 族的工作方式。show 族是一个 click 组，`show/main.py` 里以 `@cli.command()` 装饰的函数就是子命令，函数名默认即命令名，也可通过 `@cli.command('route-map')` 显式指定；`cli.add_command(...)` 把其他模块定义的命令组挂进来，因此 `show vlan`、`show feature`、`show platform`、`show processes` 等分别来自 `show/vlan.py`、`show/feature.py`、`show/platform.py`、`show/processes.py`。show 族在函数内部通过 `swsscommon` 的 `SonicV2Connector`、`ConfigDBConnector` 连接各逻辑库读取数据——`show/main.py` 顶部明确 import 了这两个连接器。这里要守住两条边界：其一，show 只读，不写配置、不编程 ASIC；其二，读到的只是某一时刻的数据库快照，异步流水线下数据库之间可能短暂不一致，因此「show 看到状态」与「硬件已下发」不是一回事（原理见 06-01 ｜ 字段见 05-03）。

`show version` 值得单独拆解，因为它是每次排障的首屏命令。`show/main.py` 中该函数只接受一个 `--brief` 标志，默认输出详尽信息；函数体调用 `device_info.get_sonic_version_info()`、`device_info.get_platform_info()` 与 `platform.get_chassis_info()` 取版本与平台数据，再拼出软件版本、发行版、内核、构建提交、构建日期、构建者、Platform、HwSKU、ASIC 类型与数量、序列号、型号、硬件版本、Uptime 与日期等行；非 `--brief` 时还会调用 `docker images` 打印镜像表。版本号来自构建产物，本套资料统一不写绝对版本号，凡涉及具体版本写「需对照实际版本核验」；`ASIC` 字段若为虚拟交换机取值，则转发由软件模拟，性能数字需在目标机型实测（模块见 07-10）。

再说 config 族的写路径。config 族同样是一个 click 组，且 `config/main.py` 中该组以 `clicommon.AbbreviationGroup` 为类，支持子命令缩写；各子命令通过 `@config.command()` 装饰并大量使用 `add_command` 挂载外部模块，例如 `config.add_command(vlan.vlan)`、`config.add_command(bgp_cli...)` 相关挂载、`config.add_command(feature.feature)` 等。写库动作通常经 `ValidatedConfigDBConnector` 或 `ConfigDBConnector` 完成——`config hostname` 的实现就用 `config_db.mod_entry` 修改 `DEVICE_METADATA` 表的 `localhost` 键的 `hostname` 字段，并在结尾提示改动在重启后会丢失、需运行 `config save` 持久化。这个细节很重要：它说明 config 命令改的是运行时配置库，持久化是独立的一步，二者不可混同（字段见 05-02 ｜ 原理见 06-02）。

`config save` 与 `config load` 是一对持久化命令。`config/main.py` 顶部定义了 `DEFAULT_CONFIG_DB_FILE = '/etc/sonic/config_db.json'` 与 `DEFAULT_GOLDEN_CONFIG_DB_FILE = '/etc/sonic/golden_config_db.json'`；`save` 带 `-y/--yes` 确认开关与可选文件名参数，作用是把当前配置库导出到磁盘文件；`load` 则从文件载入配置库。误用这两条命令的典型后果是：在改动尚未 `save` 时执行 `reload`，导致改动丢失；或把 `load` 指向过期文件，覆盖现行有效配置。因此命令闭环必须写成「前置检查、执行、验证输出、清理」四步，执行写操作前后都要有验证动作。至于 `config reload`、`config apply-patch`、`config load_minigraph` 等更重的命令，选项较多且随版本变化，本篇只点名存在与用途，具体选项需对照实际版本核验。

最后说辅助命令族。`counterpoll` 用于配置计数器轮询项，默认多数轮询关闭，误开会增加数据库写入与 CPU 负担，调优结论需在目标机型实测；`crm` 用于查看 CRM（资源计数）信息，读阈值误判资源耗尽是常见误用；`debug` 用于打开各类调试开关，遗留未关的开关会影响性能，是容易被忽视的隐患；`sonic-clear` 用于清计数与临时状态，清计数前务必留存排障证据；`acl-loader` 用于加载 ACL 规则，规则顺序错误会导致策略不按预期命中（原理见 06-08 ｜ 原理见 06-09）。这些命令族各有独立的 `main.py` 入口，均在 `setup.py` 的 `console_scripts` 段可核实。

```bash
show version --brief
```

逐行判读如下。第一行软件版本由构建产物决定，本套资料统一写「上游 master 快照（2026-11 抓取）」，不写绝对版本号，尖括号占位仅示意字段位置、需对照实际版本核验；第二行 OS 版本与第三行发行版属于宿主基础系统，Linux 内核源码不在本快照；第四行内核版本来自 `os.uname().release` 兜底，第五、六行构建提交与构建日期用于把设备对应到某次构建，同批设备取值不一致通常说明镜像来源混杂；第七行构建者同样来自构建元数据。空行之后，`Platform` 与 `HwSKU` 共同指向 `device/<vendor>/<hwsku>/` 下的机型目录，是判断端口配置是否加载正确的锚点；`ASIC` 与 `ASIC Count` 指出数据面类型与芯片数量，若为虚拟交换机则属软件模拟，性能数字需在目标机型实测；`Serial Number`、`Model Number`、`Hardware Revision` 来自机箱信息，用于资产核对；`Uptime` 反映启动后运行时长，若刚重启却显示很长往往不是预期实例；最后 `Date` 是命令执行时的系统时间。`--brief` 的作用是省略其后的 Docker 镜像清单段，仅保留上述版本与平台信息。整个输出来自 `show/main.py` 的 `version` 函数，属于「CLI 只读状态、不编程 ASIC」的典型（模块见 07-06 ｜ 模块见 07-10）。

再看一次写配置的闭环示例，演示 `hostname` 修改与持久化两步。

```bash
config hostname leaf-01
config save -y
show hostname
```

```text
示例输出，具体格式需对照实际版本核验（取值仅为格式示意）
Please note loaded setting will be lost after system reboot. To preserve setting, run `config save`.
```

逐行判读如下。第一条 `config hostname leaf-01` 把 `DEVICE_METADATA` 表 `localhost` 键的 `hostname` 字段改为 `leaf-01`，实现位于 `config/main.py` 的 `hostname` 函数，经 `ValidatedConfigDBConnector` 的 `mod_entry` 写入；字段名与表结构见「字段见 05-02」。第二条 `config save -y` 把当前配置库导出到默认的 `/etc/sonic/config_db.json`，`-y/--yes` 用于跳过覆盖确认提示，默认路径来自 `config/main.py` 顶部 `DEFAULT_CONFIG_DB_FILE` 常量；若不显式确认，交互环境下会提示「Existing files will be overwritten, continue?」。第三条 `show hostname` 用于回读主机名，验证写入是否生效。示例输出那一行是 `config hostname` 给出的提示语，明确告知改动在重启后会丢失、需 `config save` 持久化——这正是配置库与持久化文件分离的证据。判读要点有三：其一，命令返回成功只代表配置库被改写，**不等于硬件已下发**（原理见 06-01）；其二，未执行 `save` 的改动在重启后丢失；其三，`hostname` 这类改动通常不触发数据面重新编程，但其他改动会通过异步流水线逐段下发，验证时要按库逐段核对（原理见 06-02 ｜ 排障见 08-03）。输出块已注明示例输出与版本核验要求，提示语措辞随版本变化，不得当作真实回显引用。

### 5. 速查表

下表按「我想做什么 → 用哪个命令 → 注意点」给出随查入口，便于现场快速定位；命令是否可用、选项如何拼写需对照实际版本核验。

| 目的 | 命令 | 注意点 |
|---|---|---|
| 看版本与平台 | `show version` | 加 `--brief` 省略镜像段 |
| 看端口状态 | `show interfaces status` | `Admin` up 不代表 `Oper` up |
| 看路由 | `show ip route` | 经 vtysh，与 APPL_DB 分开判读 |

速查表的使用纪律：每条命令执行前先明确「这是只读还是写配置」，写操作一律走「前置检查、执行、验证输出、清理」闭环；`show` 类只读命令可以直接执行，但判读时要意识到数据库之间可能短暂不一致；`config` 与 `sonic-clear` 类命令会改变系统状态，执行前必须确认目标对象与影响范围（原理见 06-01 ｜ 排障见 08-03）。

### 6. 版本差异

命令族是 sonic-utilities 中演进最活跃的部分，版本差异主要体现在四个层面。第一层是命令的增删：`show/main.py` 的 `add_command` 列表会随版本加入新业务命令或移除废弃命令，本篇表只列代表项，完整清单以对应版本的 `show/`、`config/` 目录为准，需对照实际版本核验。第二层是选项的变化：例如 `show version` 的 `--brief` 在当前快照可核实，但早期版本未必提供；`config save` 的 `-y/--yes` 与确认提示语也可能调整，凡本快照未核实者一律标注。第三层是输出格式：各命令的列名、列宽、单位与排序随版本与集成方式变化，示例输出一律标注「示例输出，具体格式需对照实际版本核验」，不得跨版本套用。第四层是入口脚本的重组：`setup.py` 的 `console_scripts` 段会随版本调整命令名映射，个别命令可能被改名或由新入口替代，判断某命令是否存在应回到该版本 `setup.py` 核实。

还有一个与版本强相关的点是 sonic-cli 与 sonic-cli-gen。本快照 `setup.py` 中可核实的是 `sonic-cli-gen = sonic_cli_gen.main:cli` 这一生成入口，交互式 `sonic-cli` 壳的具体形态、命令补全与分派规则由生成器与运行时环境共同决定，本篇仅陈述其「交互式外壳、分派底层命令」的定位，不臆造其命令清单，细节需对照实际版本核验（模块见 07-06）。版本基准始终为上游 master 快照（2026-11 抓取），具体版本号以对应构建文件为准，需对照实际版本核验。

### 7. 常见误用与调试

第一类误用是把命令返回成功等同于硬件已下发。这是 SONiC 排障中最普遍的认知错误：`config` 命令写入配置库后即返回，后续要经过各 `*mgrd` 搬到 `APPL_DB`、`orchagent` 翻译成对象写入 `ASIC_DB`、`syncd` 经 SAI 编程芯片，是一段异步流水线（原理见 06-01 ｜ 原理见 06-03 ｜ 原理见 06-04 ｜ 原理见 06-05）。正确姿势是按库逐段核对，再结合 `show` 输出，而不是看到「成功」就判定转发正常。

第二类是把 `show` 的协议状态当成转发状态。以路由为例，`show ip route` 经 vtysh 读取的是协议侧路由，FRR 源码不在本快照（模块见 07-08）；它只能说明协议进程已知这条路由，不等于路由已进 `APPL_DB`、更不等于已下发 ASIC。判读时必须把 `show` 与各库查询分开，不一致时先怀疑流水线某段未走通，而非直接判定芯片故障（原理见 06-07 ｜ 排障见 08-04）。

第三类是配置持久化误用。前面已经看到，`config hostname` 明确提示改动重启后会丢失；忘做 `config save`、用 `config load` 载入过期文件、在未 `save` 时执行 `config reload`，都是高频事故。第四类是写错对象：config 子命令的参数多为表名、接口名或 VLAN 名，拼写错误可能写入错误表项而不立即报错，表现为「命令成功但业务异常」，因此写操作前后都要用 `show` 回读验证（字段见 05-02 ｜ 排障见 08-03）。

调试此类问题时，顺序建议固定为：先用 `show version` 确认平台与 HWSKU 是否匹配机型目录，再用 `show processes` 确认相关容器进程在跑，然后用对应 `show` 子命令读取目标状态，最后按 `CONFIG_DB`、`APPL_DB`、`ASIC_DB`、`STATE_DB` 顺序逐段核对表项。凡涉及具体命令选项、输出格式与返回码，一律以对应版本的 `show/`、`config/` 源码为准并标注「需对照实际版本核验」；日志路径与返回码速查见 04-08，容器进程与启动项见 04-07。遵守这套顺序，可以避免把「库里没表项」误判成「硬件坏了」，也能避免把「命令已返回」误判成「配置即时生效」。

### 3. 逐项详解

先深入 `orchagent` 的几组关键参数。通信模式 `-z` 是本快照中较重要的一项，`usage()` 明确写「redis_async|redis_sync|zmq_sync，默认 redis_async」，处理分支调用 `sai_deserialize_redis_communication_mode` 把字符串解析为枚举；`-s` 同步模式被标注「deprecated, use -z」，说明新版本应优先用 `-z` 而非 `-s`。选错通信模式会直接影响 orchagent 与数据库、与 syncd 之间的数据交换方式，进而影响下发正确性与吞吐，调优结论需在目标机型实测（原理见 06-04 ｜ 调优见 08-02）。

录制相关参数是一组，用于排障取证：`-r` 的取值是位掩码，`usage()` 给出 0 表示不录制、1 录制 `sairedis.rec`、2 录制 `swss.rec`、3 同时录制两者、7 三者全开（加入 `responsepublisher.rec`），处理分支检查取值必须在 0~15 之间，越界则打印用法并以失败状态退出；`-d` 指定录制目录，处理分支用 `access(..., W_OK)` 检查目录可写，不可写则退出；`-f`、`-j` 分别覆盖 `swss.rec` 与 `sairedis.rec` 两个默认文件名；`-A` 同时打开异步 SWSS 录制与异步路由状态发布。这组参数的误配后果主要是「想取证却没录到」——目录不可写、文件名写错、位掩码给成 0，都会导致关键排障材料缺失（排障见 08-04）。

批量与性能相关参数是另一组：`-b` 设置消费表 pop 操作的批量大小，默认 128，直接影响 orchagent 从数据库取任务的粒度；`-k` 设置 bulk 模式最大批量，默认 1000，处理分支只对正值生效，非正值会被记录错误并忽略、回退默认；`-I` 设置心跳间隔，默认 10 毫秒，负值会回退到 `HEART_BEAT_INTERVAL_MSECS_DEFAULT` 并报错；`-c` 选择计数器模式，`traditional` 与 `asic_db` 的计数口径不同，默认 `asic_db`；`-R` 打开 ring 线程特性，`-F` 打开 FIB 抑制。这组参数的共同点是都与性能相关，任何调整都必须「需在目标机型实测」，本篇不给绝对值也不给跨机型通用数字（基准方法见 08-01 ｜ 调优见 08-02）。

`orchagent` 还有几个与多 ASIC 和启动时序相关的参数：`-i` 指定多 ASIC 平台上的 ASIC instance_id，处理分支用 `strnlen` 限制长度不超过 `SAI_MAX_HARDWARE_ID_LEN`，超长会被截断并告警，误配会造成实例标识混淆；`-m` 设置交换机 MAC 地址，经 `MacAddress` 构造，非法值会导致构造失败；`-t` 覆盖建交换机超时秒数，处理分支把 `atoi` 结果赋给 `create_switch_timeout`，取值过小可能导致建交换机超时失败；`-v` 指定 VRF 名，默认空。这几个参数与平台强相关，具体默认值与约束需对照实际版本核验（模块见 07-03 ｜ 模块见 07-10）。

再说 `syncd`。它的 `-t/--startType` 取值在 `CommandLineOptions.h` 中以枚举固化：`cold`、`warm`、`fast`、`fastfast`、`express`，另有 `unknown` 作为错误哨兵；其中 `fastfast` 注释为 Mellanox 平台专用、`express` 为 Cisco 平台专用，说明这些启动类型受平台与版本限制，选错会导致状态恢复失败，需对照实际版本核验（原理见 06-10）。`-z/--redisCommunicationMode` 与 orchagent 同构，默认 `redis_async`；`-R/--asyncRec` 的注释特别指出仅在非虚拟、非 DPU 交换机且 ZMQ 南向有效时才生效，由 `SYSTEM_DEFAULTS|async_rec` 驱动，这是典型的「受平台与版本限制」参数（原理见 06-05）。

`syncd` 的看门狗与比较逻辑参数要成对理解：`-w` 设置正常操作的看门狗时长，`-W` 设置初始化阶段的时长，help 明确 `-W` 默认与 `-w` 相同；取值过小会在初始化或正常运行时误触发，导致进程被看门狗重启。`-b/--breakConfig` 指定比较逻辑的「break before make」配置文件，`-x/--contextConfig` 指定上下文配置，`-g/--globalContext` 从上下文配置中选取全局上下文索引，三者服务于多上下文与比较逻辑场景；`-C/--enableConsistencyCheck` 在比较逻辑后做库与 ASIC 的一致性检查，会增加额外比较开销。开关型的 `-l`、`-a`、`-U`、`-G`、`-B`、`-S`、`-d` 分别对应 SAI 批量、属性版本检查、元数据单测、按端口计数发现、批量计数器组、崩溃退出睡眠与诊断壳，多数默认关闭，生产环境不应随意打开（字段见 05-06 ｜ 原理见 06-05）。

SAI 部分的详解必须落到「可核验边界」上。本快照 `sonic-sairedis/sonic-sairedis-master/SAI/` 为空目录，这意味着_header 声明、具体属性名（例如端口速率、MTU、管理状态一类 attribute）与数值枚举都不在本快照内，任何具体的 SAI 属性名与数值都必须写「不在本快照，需对照实际版本核验」。可核验的是同仓的 `meta/`（属性元数据）、`vslib/`（虚拟 SAI 实现）、`lib/`、`saidump/`、`saiplayer/` 等目录；`syncd/` 下的 `SaiObj.cpp`、`VendorSai.cpp`、`SaiDiscovery.cpp` 等展示了对象与厂商 API 装载的代码形态（字段见 05-04 ｜ 模块见 07-04）。撰写 SAI 属性相关内容时，正确做法是给出可定位目录并标注核验要求，而不是凭印象填一个属性名。

下面给一组查看进程实际启动命令的示例。进程命令行通常以 supervisord 配置项形式给出，这里用文本示意其参数形态，具体命令由对应版本的 supervisord 模板决定、需对照实际版本核验。

```text
示例配置，具体格式需对照实际版本核验（取值仅为格式示意）
[program:orchagent]
command=/usr/bin/orchagent.sh -b 128 -z redis_async -c asic_db -I 10 -r 3
priority=<swss_priority_base + offset>
dependent_startup=true
dependent_startup_wait_for=portsyncd:running
```

逐行判读如下。`[program:orchagent]` 是 supervisord 中该进程的配置段名，说明 orchagent 由容器内的进程编排拉起，启动顺序见 04-07 与「原理见 06-13」。`command` 行给出实际命令行：脚本 `/usr/bin/orchagent.sh` 后面跟了一组参数，`-b 128` 表示消费表 pop 批量大小取默认 128，`-z redis_async` 显式指定异步 Redis 通信模式（与 usage 默认值一致），`-c asic_db` 指定计数器模式为 `asic_db`（同样与默认一致），`-I 10` 指定 10 毫秒心跳，`-r 3` 打开 `sairedis.rec` 与 `swss.rec` 两路录制。这里要理解：显式写出与默认一致的值，是为了让意图可读、不受默认值变更影响，排障时不能因为「和默认一样」就忽略它们。`priority` 是由 `swss_priority_base` 加偏移的表达式，决定同容器内启动优先级；`dependent_startup=true` 配合 `dependent_startup_wait_for=portsyncd:running` 表示 orchagent 要等 `portsyncd` 进入 running 才启动，这是依赖编排的体现。判读要点是：参数拼写与取值随版本变化，示例中的具体值仅为格式示意、需对照实际版本核验；录制开关 `-r` 在生产环境通常按取证需求设置，长期全量录制会占用磁盘与 CPU。

再看一组核对 syncd 启动类型的示例，用于区分冷启动与 warm 重启。

```text
示例配置，具体格式需对照实际版本核验（取值仅为格式示意）
[program:syncd]
command=/usr/bin/syncd_init_service.sh -t warm -z redis_async -l -a
```

逐行判读如下。`[program:syncd]` 是 syncd 的进程配置段；`command` 行中 `-t warm` 指定启动类型为 warm，对应 `CommandLineOptions.h` 中 `SAI_START_TYPE_WARM_BOOT` 枚举，意味着 syncd 要走状态恢复路径而非重建全部对象，warm reboot 受平台与版本限制、需对照实际版本核验（原理见 06-10）；`-z redis_async` 与 orchagent 保持同一通信模式，否则两端数据交换方式不一致会导致 `ASIC_DB` 异常；`-l` 打开 SAI 批量支持，属于性能相关开关，厂商不支持时会异常，调优需在目标机型实测；`-a` 打开属性版本检查，会在 SAI 发现阶段按属性版本校验，严格检查可能导致发现失败。这组参数共同说明：syncd 的启动参数与 orchagent 是「成对配置」的关系，尤其通信模式必须一致，启动类型必须与编排系统期望的重启方式匹配。示例中具体取值仅为格式示意、需对照实际版本核验，命令行形态由对应版本的 `syncd_init_service.sh` 与 supervisord 模板决定（模块见 07-04 ｜ 模块见 07-11）。

### 6. 版本差异

进程参数的版本差异比用户命令更隐蔽，主要体现在四处。其一是通信模式的演进：`-s` 同步模式在本快照被标注「deprecated, use -z」，而 `-z` 提供 `redis_async`、`redis_sync`、`zmq_sync` 三种模式，说明版本在从单一同步模式向可配置模式迁移；更早的版本可能只有 `-s` 而没有 `-z`，阅读旧资料时要能对应起来。其二是批量与异步特性：`-A` 异步录制与路由状态发布、`-q` ZMQ 地址、`-R` ring 线程等参数带有明显的版本演进痕迹，是否为默认值、是否受平台支持都需对照实际版本核验。其三是启动类型：`syncd` 的 `fastfast`、`express` 分别对应 Mellanox 与 Cisco 平台，属于平台相关的扩展类型，并非所有版本与机型都支持，一律写「受平台与版本限制，需对照实际版本核验」。

其四是 SAI 头文件与元数据的形态变化。本快照 `SAI/` 为空目录，但其他版本可能包含头文件；`meta/` 的元数据文件数量与属性覆盖范围也随 SAI 版本变化。因此不能据本快照断言「SAI 属性固定为某集合」，正确写法始终是：本快照 `SAI/` 为空、不列具体属性、写「不在本快照，需对照实际版本核验」，并给出 `meta/`、`vslib/` 目录（字段见 05-04 ｜ 模块见 07-04）。此外，`orchagent/main.cpp` 与 `syncd/CommandLineOptionsParser.cpp` 中的选项字符串会随版本改动，本篇所有表格值以本快照为准，具体版本是否一致需对照实际版本核验；版本基准始终为上游 master 快照（2026-11 抓取），具体版本号以对应构建文件为准。

### 7. 常见误用与调试

第一类误用是两端通信模式不一致。`orchagent` 与 `syncd` 都提供 `-z` 参数且默认 `redis_async`，若一端显式改为 `zmq_sync` 而另一端未改，会造成数据交换方式不匹配，表现为对象下发异常。调试时应先确认两端 `-z` 取值一致，再查其他原因（原理见 06-04 ｜ 原理见 06-05）。

第二类是把 `orchagent` 当成直接操作硬件的进程。必须反复确认：`orchagent` 只消费 `APPL_DB`、生成对象写入 `ASIC_DB`，经 SAI 属性同 `syncd` 交互，不读写寄存器、不直接驱动芯片；真正调用 SAI、经厂商适配编程 ASIC 的是 `syncd`（原理见 06-05 ｜ 模块见 07-03 ｜ 模块见 07-04）。第三类是把 SAI 当成可在本快照随意查阅的头文件集合：本快照 `SAI/` 为空目录，厂商实现闭源且不在本快照，任何具体属性名与数值都要写「不在本快照，需对照实际版本核验」，不可凭印象编造（字段见 05-04）。

第四类是性能与看门狗参数误配。批量大小 `-b`、批量上限 `-k`、心跳 `-I` 与 syncd 的看门狗 `-w`/`-W` 都属于时序与吞吐相关参数，任意放大或缩小都可能带来反效果：批量过大占内存、过小拖吞吐，看门狗过小会误触发重启。这类调优没有通用答案，一律「需在目标机型实测」（基准方法见 08-01 ｜ 调优见 08-02）。第五类是启动类型误配：syncd 的 `-t` 必须与编排系统期望的冷启动或 warm 重启一致，选错会导致状态恢复失败；`fastfast`、`express` 受平台限制，需对照实际版本核验（原理见 06-10）。

调试这类问题的顺序建议固定为：先用各进程 `-h` 核对当前版本选项拼写与默认值，再查 supervisord 中实际拼出的命令行（见 04-07），确认 `orchagent` 与 `syncd` 的通信模式与启动类型匹配，然后按 `APPL_DB`、`ASIC_DB`、`STATE_DB` 顺序逐段核对表项，必要时用 `-r` 打开录制取证，最后才怀疑厂商 SAI 实现或硬件边界。凡涉及具体选项、默认值、输出与返回码，一律以对应版本的 `orchagent/main.cpp`、`syncd/CommandLineOptionsParser.cpp`、`syncd/CommandLineOptions.h` 为准并标注「需对照实际版本核验」；日志与返回码速查见 04-08，DB 对象全集见 04-04，结构体字段见 05-05、05-06。遵守这套顺序，可以避免把「参数写反导致的不下发」误判成硬件故障，也能避免在 SAI 空目录上编造不存在的属性。
