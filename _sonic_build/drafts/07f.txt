# SONiC 技术资料 · 07 模块与特性介绍（分片 F）
## 07-11 image_config / onie / installer 镜像模块

### 1. 模块定位与职责边界

本篇是 07 册「模块与特性介绍」分片 F 的第一篇，聚焦 `sonic-buildimage` 主仓中与「镜像如何被装配、又如何落到目标设备」直接相关的三组内容：`files/image_config/`、`onie-image.conf` 与 `installer/`。前面 07-01 讲顶层 `Makefile` / `slave.mk` / `rules/` 的构建规则，07-02 讲 `dockers/` 容器族与镜像生成，本篇把镜头再推一层：容器与 Debian 根文件系统就绪之后，哪些脚本和模板负责把它们拼成一台可安装的 ONIE 镜像，哪些文件负责设备首次引导时的配置初始化。02-03 已经把「从零构建 ONIE 镜像」当作实战流程讲过，本篇仍沿用 07 册固定视角，只回答「这些文件住在哪个目录、归哪个目录族管、从哪个入口进去读」，把装配机制留给 02 册、把参数留给 04 册、把开机服务顺序留给 06 册（原理见 02-03 ｜ 参数见 04-01 ｜ 原理见 06-13 ｜ 模块见 07-01）。

先把仓库归属钉死。三组内容全部位于主仓，真实仓库根为 `upstream_src/sonic-buildimage/sonic-buildimage-master/`。`files/image_config/` 是根下 `files/` 的子目录族，`onie-image.conf`、`onie-image-arm64.conf`、`onie-image-armhf.conf`、`onie-mk-demo.sh` 位于仓根，`installer/` 是仓根下的独立目录，内含 `install.sh`、`default_platform.conf`、`sharch_body.sh`、`efi_sbatlevel.py` 与一个 `tests/` 子目录。这里要与 `src/` 下作为 git submodule 引入的同名组件区分：`src/sonic-config-engine/` 一类是独立子模块，而 `files/image_config/` 与 `installer/` 直接属于主仓，没有额外一层归档目录。把目录归属搞错，后面所有脚本定位都会错位。

三组内容的职责要分清边界。`files/image_config/` 是「开机配置与服务模板库」，下面每个子目录对应一类初始化任务：`interfaces/` 管管理网口、`hostname/` 管主机名、`copp/` 管控制面 policing、`config-setup/` 管首次启动配置落地、`config-chassisdb/` 管 chassis 场景数据库初始化、`config-topology/` 管拓扑配置。它们多以「配置文件 + `.sh` 脚本 + `.service` systemd 单元 + `.j2` Jinja 模板」的组合出现，systemd 单元在开机阶段拉起脚本，脚本渲染模板生成最终配置（原理见 06-13 ｜ 参数见 04-07）。`onie-image.conf` 是「镜像变量清单」，用 shell 变量声明分区大小、目标平台、根文件系统目录名、squashfs 与 installer 载荷文件名，以及各类输出产物名，由 `onie-mk-demo.sh` 与 `build_image.sh` 一类脚本 source（参数见 04-01）。`installer/` 是「设备侧安装器」：`install.sh` 在 ONIE 环境下把载荷写入目标盘，`default_platform.conf` 从内核命令行解析 console 参数，`tests/` 是对安装器自身的小规模自测。三者串起来就是「配置注入 → 镜像封装 → 设备落盘」一条链（模块见 07-02）。

还有两条边界要在开头立住。其一，`sonic-slave-*` 系列目录（本快照可核验到 `sonic-slave-bookworm/`、`sonic-slave-bullseye/`、`sonic-slave-trixie/`、`sonic-slave-buster/`、`sonic-slave-stretch/`、`sonic-slave-jessie/`）是「编译发生的地方」，不是镜像运行时的组成部分：`make` 在 slave 容器内跑，产出才交给 ONIE 安装器，不能在普通主机裸 `make` 得到可安装镜像（原理见 02-02）。其二，厂商 ONIE 固件、BIOS/UEFI 与具体平台分区布局不在本快照，`install.sh` 里大量平台分支依赖变量取值，需对照实际版本核验。版本基准统一为「上游 master 快照（2026-11 抓取）」，本文所有路径均相对 `sonic-buildimage-master/` 根，脚本签名与默认值不确定处标注核验要求。理解这条边界后，读者才能把 02 册的镜像机制与本篇的目录一一对应：02 册讲「镜像怎么编出来」，本篇讲「这段逻辑住在哪个目录、归谁管」。

### 3. 关键类与入口函数

本节只点入口脚本、关键函数与回查去向，不展开逐字段定义。与 07-03、07-04 的 C++ 类族不同，本篇主体是 shell 与 Python 脚本，「类」的形式意义较弱，因此这里以「入口函数 + 关键变量」代替类清单；涉及表项与结构的字段一律回查 05 册，涉及镜像与构建的参数回查 04 册，即（字段见 05-02 ｜ 参数见 04-01 ｜ 参数见 04-07 ｜ 原理见 06-13 ｜ 模块见 07-11）。这样安排是为了让本篇聚焦「脚本住在哪里、入口叫什么」，而不是把参数表提前铺开。

安装器入口落在 `installer/install.sh`。其中可核验到 `_trap_push()` 与 `read_conf_file()` 两个函数：`_trap_push()` 通过 `eval` 拼接 trap 命令，实现多个 `EXIT`/`INT`/`TERM`/`HUP` 陷阱的累加而非覆盖；`read_conf_file()` 用 `while IFS='=' read` 逐行解析配置，去掉回车换行、行内注释与首尾双引号后再 `eval` 赋值。脚本开头判断 `/etc/sonic` 是否存在，据此区分「在 SONiC 内安装」与「在 ONIE 环境安装」两种场景并设置 `install_env`。以上函数形态可核验，但完整控制流与平台分支需对照实际版本核验（模块见 07-11）。

平台默认值落在 `installer/default_platform.conf`。它从 `/proc/cmdline` 用 `grep -Eo` 提取 `console=ttyS[0-9]+` 模式，解析失败或匹配 `ttyS0` 时回退到 `CONSOLE_PORT=0x3f8`、`CONSOLE_DEV=0`（对应默认 console 语境）；这些默认值在本快照可核验，但不同机型的端口映射需对照实际版本核验。`installer/tests/` 下的 `sample_machine.conf`、`test_read_conf.sh`、`test_efi_sbatlevel.py` 构成安装器自测的样例与脚本（模块见 07-12）。

镜像变量集中在 `onie-image.conf`，没有函数，全部是 shell 变量赋值：`: ${ONIE_IMAGE_PART_SIZE:=32768}` 给出默认分区大小（MB，约 32GB）、`: ${TARGET_PLATFORM:=x86_64}` 与 `: ${TARGET_MACHINE:=generic}` 给出目标平台与机型、`ONIEIMAGE_VERSION=r0`、`FILESYSTEM_ROOT=./fsroot-${TARGET_MACHINE}`、`FILESYSTEM_SQUASHFS=fs.squashfs`、`INSTALLER_PAYLOAD=fs.zip`、`FILESYSTEM_DOCKERFS=dockerfs.tar.gz`、`DOCKERFS_DIR=docker`、`DOCKER_RAMFS_SIZE=3500M`。输出侧有一组 `OUTPUT_*`：`OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin`、`OUTPUT_RAW_IMAGE=target/sonic-$TARGET_MACHINE.raw`、`OUTPUT_KVM_IMAGE=target/sonic-$TARGET_MACHINE.img`、`OUTPUT_ABOOT_IMAGE=target/sonic-aboot-$TARGET_MACHINE.swi`、`OUTPUT_DSC_IMAGE=target/sonic-$TARGET_MACHINE.tar`，以及 `OUTPUT_KVM_4ASIC_IMAGE`、`OUTPUT_KVM_6ASIC_IMAGE` 多 ASIC 变体。这些变量由 `onie-mk-demo.sh` 与构建脚本 source，数值随版本变化，需对照实际版本核验（参数见 04-01 ｜ 原理见 06-11）。

开机配置侧，`files/image_config/` 各子目录的入口是「`.sh` 脚本 + 同名 `.service` systemd 单元 + `.j2` Jinja 模板」三件套。`interfaces/interfaces-config.sh` 配合 `interfaces.j2` 生成管理口配置，`hostname/hostname-config.sh` 写入主机名，`copp/copp-config.sh` 配合 `copp_cfg.j2` 生成 COPP 配置（COPP 表字段见 05-03 ｜ 参数见 04-03）。`config-setup/config-setup.conf` 中可核验到 `KEEP_BASIC_TABLES='["MGMT_PORT","MGMT_INTERFACE","MGMT_VRF_CONFIG","PASSW_HARDENING"]'`，用于首次启动时保留基础表。`config-chassisdb/`、`config-topology/` 与多 ASIC、chassis 场景相关，受平台与版本限制，需对照实际版本核验（原理见 06-11 ｜ 模块见 07-10）。以上只列入口与变量，字段含义与参数全集留待 05、04 册。

### 4. 对外接口与扩展点

本篇模块的「对外接口」不是供进程调用的函数 API，而是三类契约。其一是 `onie-image.conf` 暴露给构建系统的变量集合（`OUTPUT_*`、`FILESYSTEM_*`、`TARGET_*`、`ONIE_IMAGE_PART_SIZE` 等），构建脚本 source 它来决定产物名与路径（参数见 04-01）。其二是 `files/image_config/` 暴露给 systemd 的单元与模板接口，`*.service` 在开机阶段触发 `*.sh`，后者渲染 `*.j2` 写入配置（原理见 06-13 ｜ 参数见 04-07）。其三是 `install.sh` 暴露给 ONIE 固件的执行契约——由 ONIE 以约定方式调用，读取 `default_platform.conf` 与平台配置完成安装，具体调用约定需对照实际版本核验（模块见 07-02）。这些契约的完整参数表属 04 册权威源，本篇不重列。

从模块能力角度看，扩展点主要有三类。第一类是新增一类开机配置：在 `files/image_config/` 下建一个子目录，按「脚本 + service 单元 + j2 模板」三件套放入，由构建脚本烘进镜像，这是扩展开机配置最标准的方式；新增项要注意与 `config-setup.conf` 的保留表机制协调，避免首次启动时被重置（参数见 04-07）。第二类是新增一种镜像产物形态：在 `onie-image.conf` 增加 `OUTPUT_*` 变量并在 `onie-mk-demo.sh` 中接入封装流程，快照内已有 `.bin`、`.raw`、`.img`、`.swi`、`.tar` 多种产物与 4-ASIC/6-ASIC KVM 变体可参照（参数见 04-01）。第三类是适配新平台：通过 `installer/default_platform.conf` 与 `TARGET_MACHINE` 变量接入新机型的 console 与分区约定，平台相关分支需对照实际版本核验（模块见 07-10）。

扩展时的能力边界必须点明。其一，`files/image_config/` 只在构建期与开机期生效，不能把它当成运行时的配置下发通道——运行时配置仍走 CONFIG_DB → APPL_DB → ASIC_DB 的异步流水线（原理见 06-01）。其二，镜像封装依赖 `sonic-slave-*` 容器，普通主机裸 `make` 不得当作可安装镜像产出（原理见 02-02）。其三，`install.sh` 与厂商 ONIE 固件强耦合，平台相关逻辑不在本快照，越界补值会造成「看起来真实、实际错误」的安装脚本；涉及厂商固件与分区布局一律写「不在本快照，需对照实际版本核验」（模块见 07-02 ｜ 模块见 07-10）。

为把「模块能力—职责—回查去向」串成索引，下面给出一组四段式反查关系，作为本篇所有交叉引用的统一写法：字段见 05-02 ｜ 参数见 04-01 ｜ 原理见 02-03 ｜ 模块见 07-11。读者从任一维度切入，都能沿这条线索回到本篇的目录与入口，而不必在多个册之间反复猜测归属。这也是 07 册作为「模块功能与目录归属唯一权威源」的价值所在：它给出镜像这组文件的稳定锚点，其余册围绕锚点展开参数与机制细节。

### 5. 典型用法与调用示例

本节给两组最小实例：一组用命令观察镜像配置文件与产物并作逐行判读，一组给出 `read_conf_file()` 与 `onie-image.conf` 变量的脚本片段以印证「变量驱动封装、脚本解析配置」的形态。完整构建参数见 04-01，命令全集见 04-05，本册不重列。所有命令需在具备相应权限的环境下执行，路径、产物名与默认值需对照实际版本核验。先看一组观察命令，示例输出注明「示例输出，具体格式需对照实际版本核验」。

```bash
# 前置检查：确认本篇三组文件的入口存在（路径相对 sonic-buildimage-master/ 根）
ls -l onie-image.conf onie-mk-demo.sh installer/install.sh
# 执行：提取 ONIE 镜像的关键变量（取自 onie-image.conf，值需对照实际版本核验）
grep -E 'OUTPUT_ONIE_IMAGE|FILESYSTEM_SQUASHFS|INSTALLER_PAYLOAD|ONIE_IMAGE_PART_SIZE' onie-image.conf
# 验证：查看首次启动保留表清单（config-setup.conf；需对照实际版本核验）
grep 'KEEP_BASIC_TABLES' files/image_config/config-setup/config-setup.conf
```

```text
示例输出，具体格式需对照实际版本核验（下列文件名、取值与表清单仅为格式示意，不代表任何具体版本或机型）

-rw-r--r-- 1 user user  5740 Nov 13 20:14 onie-mk-demo.sh
```

逐行判读如下。第一段 `ls -l` 列出三个入口文件：主仓根下的 `onie-image.conf`、`onie-mk-demo.sh` 与 `installer/install.sh` 均真实存在，印证本篇三组内容的目录归属；若其中任一文件缺失，说明快照版本与本文基准不同，应先核验目录而不是继续推断，路径需对照实际版本核验。第二段 `grep -E` 从 `onie-image.conf` 抽出四个关键变量：`FILESYSTEM_SQUASHFS=fs.squashfs` 说明根文件系统被打包为 squashfs，`INSTALLER_PAYLOAD=fs.zip` 说明安装载荷以 zip 封装，`ONIE_IMAGE_PART_SIZE:=32768` 是默认分区约 32GB（MB 单位，`:=` 为 shell 默认值赋值、可被外部覆盖），`OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin` 说明产物名随 `TARGET_MACHINE` 变化，不能写死为某个固定文件名；这些取值随版本变化，需对照实际版本核验。第三段读取 `KEEP_BASIC_TABLES`，列表中的 `MGMT_PORT`、`MGMT_INTERFACE`、`MGMT_VRF_CONFIG`、`PASSW_HARDENING` 是首次启动时被保留的基础表，说明开机配置与运行时配置表存在交集但职责不同。整组命令为只读探查，不改动任何配置（参数见 04-01 ｜ 参数见 04-05）。三组内容在「配置注入—镜像封装—设备落盘」链路中的位置与内部结构见图 07-11-01。

第二组给出 `onie-image.conf` 变量与 `install.sh` 解析函数的代码片段，用来印证「变量驱动封装、脚本解析配置」的实现形态；下列片段依据本快照中可核验的变量与函数整理，为便于阅读做了简化，真实取值与函数签名需对照实际版本核验。

```sh
# 代码形态示意，依据 onie-image.conf 与 installer/install.sh 中可核验的变量与函数整理；取值需对照实际版本核验
# onie-image.conf 片段：全部为 shell 变量赋值，供构建脚本 source
: ${ONIE_IMAGE_PART_SIZE:=32768}
: ${TARGET_PLATFORM:=x86_64}
: ${TARGET_MACHINE:=generic}
FILESYSTEM_SQUASHFS=fs.squashfs
INSTALLER_PAYLOAD=fs.zip
OUTPUT_ONIE_IMAGE=target/sonic-$TARGET_MACHINE.bin

# install.sh 片段：解析配置文件的函数形态
read_conf_file() {
    local conf_file=$1
    while IFS='=' read -r var value || [ -n "$var" ]; do
        var=$(echo "$var" | tr -d '\r\n')
        value=$(echo "$value" | tr -d '\r\n')
        var=${var%#*}; value=${value%#*}
        [ -z "$var" ] && continue
        tmp_val=${value#\"}; value=${tmp_val%\"}
        eval "$var=\"$value\""
    done < "$conf_file"
}
```

这段代码印证了两个核心判断。其一，`onie-image.conf` 是纯变量清单：`:=` 赋值允许外部覆盖默认值（分区大小 32768MB、目标平台 x86_64），`OUTPUT_ONIE_IMAGE` 用 `$TARGET_MACHINE` 拼出产物名，说明同一套脚本可产出不同机型镜像，完整变量全集需对照实际版本核验（参数见 04-01）。其二，`install.sh` 的 `read_conf_file()` 用 `IFS='='` 拆分键值、逐项清洗换行与注释、去引号后 `eval` 赋值，是典型的 shell 配置解析范式；`_trap_push()` 一类的 trap 拼装则保证多个清理动作在退出时都能执行。真实源码中平台分支、错误处理与安装步骤远多于片段所示，需对照 `install.sh` 核验（模块见 07-11）。

### 6. 与其他模块的关系及常见误用

从全链路看，本篇三组内容上游接 07-01 的顶层构建规则与 `sonic-slave-*` 编译容器，下游接目标设备的 ONIE 固件与开机 systemd 服务，横向与 `dockers/` 容器族（`dockerfs.tar.gz` 的来源，`rules/docker-*.mk` 一类规则）、`src/sonic-config-engine/`（配置表 schema 的来源）及 `platform/`、`device/` 的平台数据相邻（模块见 07-01 ｜ 模块见 07-02 ｜ 模块见 07-10 ｜ 原理见 06-13）。

第一类是「编译时与运行时」混淆。最常见的是把 `files/image_config/` 当成运行时配置下发通道，或把 `onie-image.conf` 的变量当成设备运行参数。事实上前者只在构建期烘进镜像、开机期生成配置，后者只是构建期产物清单；运行时配置仍走异步流水线（原理见 06-01）。第二类是「裸机构建」误判：忽略 `sonic-slave-*` 容器，在普通主机直接 `make` 却期待得到可安装镜像，这是能力边界清单明令禁止的写法（原理见 02-02）。第三类是产物名写死：`OUTPUT_ONIE_IMAGE` 等变量含 `$TARGET_MACHINE`，产物名随机型变化，写死某固定文件名会与快照不符，需对照实际版本核验。

第四类是事实纪律陷阱。`files/image_config/constants/` 在本快照仅见 `bmc.json`，`installer/` 目录列出的条目有限，不得据目录名编造更多常量文件或安装脚本；`install.sh` 的平台分支与默认值需对照实际版本核验。第五类是首次启动覆盖误用：`config-setup.conf` 的 `KEEP_BASIC_TABLES` 决定哪些基础表在首次启动时保留，新增开机配置若不纳入保留清单，可能在开机初始化时被重置（参数见 04-07）。第六类是平台与版本陷阱：`config-chassisdb/`、`config-topology/`、多 ASIC 产物变体受平台与版本限制，一律写「受平台与版本限制，需对照实际版本核验」，不宣称全平台无条件支持（原理见 06-11 ｜ 模块见 07-10）。

最佳实践归纳为四条。其一，读源码时把路径写成 `upstream_src/sonic-buildimage/sonic-buildimage-master/` 下的相对路径，并同时给出对应入口（`read_conf_file()`、`onie-mk-demo.sh`、`interfaces.j2` 等），取值不确定就写「需对照实际版本核验」。其二，把三组内容按「配置注入—镜像封装—设备落盘」分段理解，排障时先定位停在哪一段，再决定查哪个脚本或产物（原理见 02-03）。其三，跨册引用统一用四段式（字段见 05-02 ｜ 参数见 04-01 ｜ 原理见 02-03 ｜ 模块见 07-11），本篇涉及的 COPP 表字段写「字段见 05-03」、镜像参数写「参数见 04-01」、开机服务顺序写「原理见 06-13」，不在本篇展开字段表与参数全集。其四，遇到快照内无法核实的内容，宁可标注核验要求并给出目录，也不补值。

### 4. 对外接口与扩展点

本篇模块的「对外接口」是测试框架的使用契约。对 pytest 一侧，`pytest.ini` 的空 `[pytest]` 段与 rootdir 定位是第一层契约——pytest 从仓库根发现配置并据此收集 `test_*.py`；命令行选项（如 `--imgname`、`--junitxml`、`--collect-only`）与 `conftest.py` 提供的 fixture 名构成第二层契约（参数见 04-05）。对 PTF 一侧，`dockers/docker-ptf/` 容器与 `rules/ptf*.mk` 的 deb 产物构成运行契约，测试通过容器注入数据面流量，框架 API 不在本快照（需对照实际版本核验）。对 CI 一侧，`azure-pipelines.yml` 与 `.azure-pipelines/` 下的模板（如 `run-test-template.yml`、`run-test-scheduler-template.yml`、`docker-ptf.yml`）定义了测试在流水线中的触发点（原理见 02-05 ｜ 模块见 07-13）。

从模块能力角度看，扩展点主要有三类。第一类是新增 pytest 用例：在对应仓的 `tests/` 下放一个 `test_*.py`，采用 `unittest.TestCase` 或 pytest fixture 风格，夹具数据放入同目录；主仓 `tests/test_check_install.py` 与 `src/sonic-config-engine/tests/` 提供可参考范式（字段见 05-02）。第二类是新增 DVS 集成用例：在 `sonic-swss/tests/` 下写 `test_*.py`，复用 `conftest.py` 与 `dvslib/` 的 fixture，通过 `run-tests.sh` 的 `--imgname` 指向目标镜像运行（原理见 06-04）。第三类是扩展 CI 测试阶段：在 `.azure-pipelines/` 增加模板或调整 `tests/`、`vstest-include`、`vstest-exclude` 清单，把新用例纳入流水线；该目录下已有 `azure-pipelines-build-vs.yml`、`official-build-vs-with-test.yml`、`azure-pipelines-build-vs-and-test.yml` 可参照（原理见 02-05）。

扩展时的能力边界必须点明。其一，pytest 单元测试与 PTF 数据面测试是互补关系而非替代关系：前者验配置生成与逻辑，后者验数据面收发，不能用一类结果替代另一类（模块见 07-12）。其二，本快照不含 `sonic-mgmt` 系统级测试框架，任何「在 sonic-mgmt 增加拓扑用例」的说法都超出快照证据范围，需对照实际版本核验（模块见 07-07）。其三，测试通过不等于配置已在硬件生效——DVS 与 vs 环境是软件/虚拟交换环境，不代表真实 ASIC 行为；数据面转发结论须在目标机型实测（原理见 06-01 ｜ 基准见 08-01）。

为便于回查，下面给出一组四段式反查关系，作为本篇所有交叉引用的统一写法：字段见 05-02 ｜ 参数见 04-05 ｜ 原理见 02-05 ｜ 模块见 07-12。读者从任一维度切入，都能沿这条线索回到本篇的目录与入口。这也体现了 07 册作为「模块功能与目录归属唯一权威源」的价值：它给出测试体系的稳定锚点，其余册围绕锚点展开参数与机制细节。

第二组给出 `test_check_install.py` 与 `run-tests.sh` 的代码片段，用来印证「参数回退测试、失败重试运行」的实现形态；下列片段依据本快照中可核验的函数与脚本整理，为便于阅读做了简化，真实签名与脚本细节需对照实际版本核验。

```python
# 代码形态示意，依据 tests/test_check_install.py 中可核验的形态整理；签名需对照实际版本核验
import unittest
from unittest import mock

LOGIN_SENTINEL = "login-S3cret!"   # 哨兵值，绝非真实凭据
NEW_SENTINEL = "new-S3cret!"

def parse_args_with_env(argv, env):
    with mock.patch.dict(check_install.os.environ, env, clear=True):
        parser = check_install.build_arg_parser()
        return parser.parse_args(argv)

class ArgDefaultsTest(unittest.TestCase):
    def test_login_password_env_var(self):
        args = parse_args_with_env([], {"SONIC_PASSWORD": LOGIN_SENTINEL})
        self.assertEqual(args.P, LOGIN_SENTINEL)
```

```bash
# run-tests.sh 运行形态示意，依据 sonic-swss/tests/run-tests.sh 整理；参数名需对照实际版本核验
IMAGE_NAME=$1
PY_TEST_PARAMS="$2"
TESTS="$3"
RETRY=$4
[ -z "$RETRY" ] && RETRY=1
JUNITXML=$(echo "$TESTS" | cut -d "." -f1)_tr.xml
for ((i=1; i<=$RETRY; i++)); do
    pytest -v --junitxml="$JUNITXML" $PY_TEST_PARAMS --imgname="$IMAGE_NAME" $TESTS && break
done
```

这段片段印证了两个核心判断。其一，`parse_args_with_env()` 用 `mock.patch.dict(..., clear=True)` 在受控环境里构造参数解析器，`ArgDefaultsTest` 据此验证 `-P` 的环境变量回退与 `-N` 的不回退；所有密码用 `*-S3cret!` 哨兵值，避免真实凭据进入用例，这是测试纪律的范例（模块见 07-12）。其二，`run-tests.sh` 接收镜像名、参数与用例名，用 `cut` 从用例名拼出 JUnit XML 文件名，再按 `RETRY` 循环调用 `pytest`，成功即 `break`、失败重试——这是 DVS 集成测试「按镜像运行、失败重试」的运行形态；`conftest.py` 提供的 DVS fixture 支撑这些用例访问数据库与对象（参数见 04-05 ｜ 原理见 06-04）。真实源码中的用例远多于片段所示，需对照各仓 `tests/` 核验。

### 6. 与其他模块的关系及常见误用

从全链路看，本篇测试体系上游接构建与 CI（07-01、07-02、07-13、02-05），横向与各功能模块的 `tests/` 目录相邻（sonic-swss、sonic-sairedis、sonic-utilities、sonic-dbsyncd、sonic-mgmt-common），下游服务对配置流水线与数据面行为的验证（06-01、08-01）。pytest 用例大量依赖配置表 schema 与命令行接口（04、05 册），DVS 用例依赖 swss 对象与 Redis 数据库（07-03、07-05），PTF 用例依赖 vs 虚拟交换机与 SAI 运行时（07-10、06-12）。

第一类是「测试层次混淆」。最常见的是把 pytest 单元测试通过等同于「配置已在硬件生效」，或把 PTF/DVS 结果当作真实 ASIC 的转发结论。单元测试只验生成逻辑，DVS 与 vs 是虚拟环境，不代表真实芯片行为，判读要按 06-01 的流水线与 08-01 的基准方法分期（原理见 06-01 ｜ 基准见 08-01）。第二类是「sonic-mgmt 误置」：把系统级测试写成 `sonic-mgmt/` 目录下的文件，但本快照只有 `sonic-mgmt-common`，该仓不在本快照，涉及 sonic-mgmt 的内容一律写「不在本快照，需对照实际版本核验」（模块见 07-07）。第三类是「空目录编造」：`src/ptf/`、`src/ptf-py3/` 在本快照为空，但 `rules/ptf*.mk` 证明 PTF 作为 deb 包被构建，不得从空目录编造框架内部 API（模块见 07-12）。

第四类是事实纪律陷阱。用例名、夹具文件名与模板名均可核验，但 `sonic-sairedis/tests/`、`sonic-utilities/tests/`、`sonic-dbsyncd/tests/`、`sonic-mgmt-common/cvl/tests/` 等目录的具体用例清单在本快照未逐一列出，需对照实际版本核验；不得凭印象补写用例类名（字段见 05-02 ｜ 模块见 07-12）。第五类是「哨兵值误用」：`test_check_install.py` 中密码均为哨兵值，若在用例中写入真实凭据或反过来把哨兵值当有效密码，都是纪律错误，需严格区分（模块见 07-12）。第六类是 CI 模板误配：`.azure-pipelines/` 下模板众多，`vstest-include`、`vstest-exclude`、`tests/`、`baseline_test` 等清单决定哪些用例在 vs 构建后执行，改动需对照实际版本核验，不宣称全平台无条件触发（原理见 02-05 ｜ 模块见 07-13）。

最佳实践归纳为四条。其一，读测试代码时把路径写成各子仓 `xxx-master/` 下的相对路径，并同时给出对应入口（`TestCfgGen`、`conftest.py`、`run-tests.sh`、`parse_args_with_env()` 等），不确定就写「需对照实际版本核验」。其二，按「单元测试—DVS 集成—PTF 数据面—CI 编排」四层理解测试体系，排障时先定位是哪一层失败，再看对应用例与夹具（原理见 02-05）。其三，跨册引用统一用四段式（字段见 05-02 ｜ 参数见 04-05 ｜ 原理见 02-05 ｜ 模块见 07-12），本篇涉及的表项字段写「字段见 05-02」、pytest 命令写「参数见 04-05」、DVS 机制写「原理见 06-04」，不在本篇展开字段表与参数全集。其四，遇到快照内无法核实的内容，宁可标注核验要求并给出目录，也不补值。
