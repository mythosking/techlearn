# OpenVPN 技术资料 · 02 编译与构建

## 02-01 源码获取、目录结构与依赖

### 1. 背景与动机

很多人把「编译」理解成 `./configure` 加 `make` 两条命令，敲完看到提示符返回就认为大功告成。对 OpenVPN 社区版来说，这种理解会埋下不少隐患。构建阶段探测出来的加密后端、压缩库、可选扩展与内核数据通道卸载支持，直接决定最终那个二进制「能做什么、不能做什么」；源码目录的分工，又决定了遇到链接错误、平台差异或特性缺失时该去哪个文件里找答案。换句话说，构建不是部署前的一道机械手续，而是理解整个软件的第一道门。若跳过这一步，后面读配置、读源码、做排障都会缺少一个稳固的参照系；你甚至无法判断一条指令不生效，究竟是配置写错了，还是这个二进制根本没把对应能力编进来。

为什么社区版尤其需要单独把「构建」拿出来讲。社区版没有唯一权威的二进制分发形态：不同发行版的包为了兼容性，往往关闭了一些可选特性，或者链接了与文档假设不一致的库版本；而在需要指定加密后端、启用数据通道卸载、加入某个插件、自定义安装前缀，或者做跨平台交叉编译时，「从源码构建」几乎是必经之路。把构建过程掌握在自己手里，才能得到一份能力可预期、版本可追溯、参数可复现的程序。这也是后续 03 册的部署与 08 册的排障能够建立在「我清楚这个二进制是怎么来的」之上的前提。

本篇在整册与全书里的坐标需要先摆正。02 册五篇依次解决五个问题：从哪里拿源码、目录怎么分、依赖有哪些（本篇 02-01）；怎样完整走一遍 `./configure`、`make`、`make check`、`make install` 并判读每一步输出（02-02）；构建选项与依赖开关怎么取舍（02-03）；Linux、Windows、macOS 三个平台与安装包怎么做（02-04）；以及 `ovpn-dco` 内核模块与配套组件怎么单独构建（02-05）。本篇是地基，只负责建立三张图：源码树地图、依赖分层图、从源码到二进制的产物链图。把这三张图立住，后面四篇就都是在具体环节上做展开，而不是反复回到「这个文件在哪」的原点。

去重与边界必须一开始就写清楚。按全书唯一权威源约定，运行时配置指令与命令行参数的完整清单属于 04 册，本篇凡涉及 `--` 形式的运行参数只作最小必要引用并写「完整指令见 04-01」；结构体的逐字段定义属于 05 册，本篇只点名并给真实源码路径，随后写「（字段见 05-xx）」；机制、状态机与调用链属于 06 册，本篇不展开，只写「原理见 06-xx」；模块能力与特性清单属于 07 册，本篇只作索引，写「模块见 07-xx」。因此本篇标题里「关键数据结构」一词，主要指构建元数据、自动生成宏与源码坐标，而不是运行期对象；这是构建册相对其它册最需要澄清的一处措辞。

最后是版本基准与核验纪律。本册以 OpenVPN 2.6.x 稳定分支、2.7 开发分支（master）以及独立的 `ovpn-dco` 内核模块为基准。configure 选项名、依赖库名、自动生成的宏名、目录与文件清单，都可能随版本调整，凡不确定处一律写「需对照实际版本核验」，并给出可定位的 `configure.ac`、`Makefile.am` 与 `doc/` 路径，绝不凭印象编造选项或版本号。读者应养成用 `./configure --help` 与仓库实际源码复核的习惯：文档里出现的每一个具体开关，都只是引导你去核对的线索，而不是可以照抄的结论。

### 2. 核心概念

先分清两种源码形态，这是第一个岔路口。官方发布的 release tarball 里已经预生成了 `configure` 脚本与 `Makefile.in`，解包之后可以直接 `./configure`；而从版本库检出的工作树只有 `configure.ac`、`Makefile.am` 这类「源」，必须先跑 `autoreconf` 或仓库自带的生成脚本，把构建脚本造出来。把两者混用是新手最常见的第一处卡点：在 git 工作树里翻来翻去找 `configure` 却找不到，误以为源码不完整。理解这一区别，也就能理解为什么 02-02 的分步操作里，会把「是否需要先生成 configure」单独列为一步。

接着把 Autotools 的链条拉直。`configure.ac` 是 Autoconf 的输入，描述版本初始化、编译器检查、库与头文件探测，以及全部 `--enable-*` 与 `--with-*` 开关；`Makefile.am` 是 Automake 的输入，描述要编译哪些源文件、生成哪些目标、链接哪些库；`autoreconf` 把前者变成 `configure`、把后者变成 `Makefile.in`；用户运行 `./configure` 之后，它结合本机环境生成最终的 `Makefile` 与 `config.h`。`config.h` 里那一批 `HAVE_*` 与 `ENABLE_*` 宏，就是「探测结果」落到 C 源码里的形式，决定哪些 `#ifdef` 分支会被编进二进制。这些文件名与宏名的确切拼写需对照实际版本核验，但「输入、生成、探测、产物」这四段关系是稳定的。

依赖要分层记，构建时心里才有一张能逐项打勾的清单。必需层是 C 编译器、make、autoconf、automake、libtool、pkg-config 这类工具链；加密后端层是 OpenSSL 或 mbedTLS 二选一，几乎决定整个 TLS 与加解密代码路径；压缩层 LZO 与 LZ4 属于可选加速；PKCS#11、systemd、libnl（与数据通道卸载相关）、PAM 插件属于按场景开启的扩展层；cmocka 之类只在 `make check` 阶段需要，归测试层。把层次画成图，见图 02-01-02。

把分层与典型探测方式列成下表，便于构建前逐项核对。表中加密后端一格写成 `OpenSSL\|mbedTLS`，竖线在这里表示「二选一」，按本套资料的表格约定必须转义为 `\|`，否则会被解析成列分隔而让整表错列。

| 层次 | 代表依赖 | 缺省状态 | 探测方式 |
|---|---|---|---|
| 工具链 | autoconf、automake、libtool、pkg-config | 必需 | 命令是否存在 |
| 加密后端 | OpenSSL\|mbedTLS | 二选一 | configure.ac 检测 |
| 压缩库 | LZO、LZ4 | 可选 | pkg-config 或库检测 |
| 扩展库 | pkcs11-helper、libsystemd、libnl | 按需开启 | PKG_CHECK_MODULES |
| 测试依赖 | cmocka | 仅 make check | 头文件与库检测 |

还有一条必须钉住的概念：编译期能力不等于运行期生效。`openvpn --version` 输出里方括号中的 `[SSL (OpenSSL)]`、`[LZO]`、`[LZ4]`、`[DCO]` 之类标签，是编译期链接结果的快照，只说明「这个二进制被编进了对某库的支持」，不等于运行期已经启用对应功能。例如数据通道卸载还需要内核模块加载与运行参数配合（原理见 06-xx、模块见 07-xx）。反过来，configure 没有把某个可选库编进来，即便运行时写了相关指令也不会生效，完整指令见 04-01。因此构建与运行之间，需要靠版本输出、config.log 与运行日志三者互相印证，任何单一证据都不足以定论。

最后把条件编译与去重坐标连起来。构建选项最终表现为条件编译：某个 `--enable-*` 开关让 `config.h` 定义对应宏，进而让 `Makefile.am` 把某个 `.c` 加进目标、让 `src/openvpn/` 里相关 `#ifdef` 代码生效。理解这一层，02-03 的开关表才不会变成死记硬背。这里具体选项名一律以 `./configure --help` 与 `configure.ac` 为准，需对照实际版本核验。本篇不展开任何运行时机制，所有结构体字段、调用链与模块功能一律按第 1 节的交叉引用处理。

### 3. 关键数据结构与源码位置

本节按 A 型骨架名为「关键数据结构与源码位置」，在构建册里应理解为「构建元数据与源码坐标」：`configure.ac`、`Makefile.am`、`config.h`、各源码目录，以及少量只在构建期有意义的条件编译宏。运行期对象如 `struct context`、`struct options` 一类，本节只点名并给 `src/openvpn/` 下路径，随后写「（字段见 05-xx）」，绝不展开字段。这样既不偏离骨架，也不越界到 05 册的字典型职责。

先看顶层构建文件。`configure.ac` 里通常能找到 `AC_INIT`、`AM_INIT_AUTOMAKE` 一类初始化宏，以及编译器检查、库探测和全部开关定义；顶层 `Makefile.am` 与 `src/`、`src/plugins/` 下各自的 `Makefile.am` 描述目标与源码清单；`autogen.sh` 是 git 检出时生成 `configure` 的便捷入口，其是否存在与确切内容需对照实际版本核验；版本定义可能落在 `version.m4`，也可能直接写在 `configure.ac` 里，决定 `--version` 输出的主版本。要特别强调：`config.h` 是 configure 的产物而非源码，不要手工编辑，改了也会被下次 configure 覆盖。

下面用一棵目录树把社区版源码树的主要坐标画出来，具体文件清单需对照实际版本核验。

```tree
openvpn/
├── configure.ac            # Autoconf 输入，开关与探测
├── Makefile.am             # Automake 输入，顶层目标
├── autogen.sh              # git 检出时生成构建脚本
├── config.h.in             # autoheader 生成的模板
├── src/
│   ├── openvpn/            # 主程序 C 源码与头文件
│   ├── compat/             # 平台兼容层，补齐缺失函数
│   ├── plugins/            # auth-pam、down-root 等插件
│   └── openvpnserv/        # Windows 服务组件
├── sample/                 # 示例配置、密钥与脚本
├── doc/                    # 手册分段与说明源
├── tests/                  # 单元与辅助测试
└── distro/                 # systemd、rpm 等发行版集成
```

对着这棵树逐一说明。`src/openvpn/` 是主程序所在，最终链接出 `openvpn` 可执行文件；`src/compat/` 是平台兼容层，为不同系统补齐缺失的函数与类型，很多条件编译的兼容 `.c` 就在这里；`src/plugins/` 放可独立编译的插件，例如认证与降权相关插件，各有自己的构建规则；`src/openvpnserv/` 与 `src/tapctl/`（目录名需对照实际版本核验）是 Windows 相关组件；`sample/` 提供示例配置、示例密钥与脚本，既是学习素材也是打包内容；`doc/` 存放手册与说明源，决定 man 页如何生成与安装；`tests/` 是 `make check` 的测试来源；`distro/` 放 systemd unit、rpm spec 等发行版集成材料。这些路径构成后面四篇反复出现的坐标。

把目录职责与构建阶段的关注点对应成下表，方便在报链接错误时快速定位应查哪一处。

| 目录 | 职责 | 构建阶段关注点 |
|---|---|---|
| src/openvpn/ | 主程序 C 源码与头文件 | 目标 openvpn 的源码清单 |
| src/compat/ | 缺失函数与类型的兼容实现 | 条件编译的兼容 .c |
| src/plugins/ | 可独立编译的插件 | 各插件 Makefile.am |
| sample/ | 示例配置、密钥与脚本 | 安装与打包内容 |
| doc/ | 手册与说明源 | man 页生成与安装 |
| tests/ | 单元与辅助测试 | make check 目标 |
| distro/ | systemd、rpm 等集成 | 打包与 service 文件 |

再补一层条件编译宏的落点。configure 探测到某库后，会在 `config.h` 定义 `HAVE_*` 或 `ENABLE_*` 之类宏（例如与 LZO、LZ4、数据通道卸载、PKCS#11 相关的宏，具体名称需对照实际版本核验）；`src/openvpn/` 里的 `#ifdef` 据此决定代码是否编入，`Makefile.am` 据此决定链接哪些 `-l` 参数。读者若想确认「某特性到底编没编进来」，最直接的证据就是 `config.h` 与 config.log，而不是凭版本输出的印象猜测。至于这些宏所影响的运行期结构体，一律（字段见 05-xx）。

### 4. 关键流程与调用链

本节的「调用链」不是运行时的函数调用，而是构建期的产物流。把它走一遍：`configure.ac` 连同 m4 宏经 `autoreconf` 变成 `configure` 脚本；用户运行 `./configure` 后，脚本探测本机编译器、头文件与库，生成 `Makefile` 与 `config.h`；`make` 依各目录 `Makefile.am` 规则编译 `src/openvpn/`、`src/compat/`、`src/plugins/` 等处的 `.c`，链接成 `openvpn` 可执行文件与插件；`make check` 跑 `tests/` 下的测试；`make install` 按 install 规则把二进制、man 页与示例装到 `--prefix` 指定的位置。理解这条链，才能在任何一步报错时准确定位「卡在哪一段」。把这条链画成图，见图 02-01-01。

configure 的探测动作值得单独拆开。它依次做编译器可用性检查、头文件检查、库与函数检查（如 `AC_CHECK_LIB`、`AC_CHECK_FUNCS` 一类宏），以及经 `pkg-config` 的 `PKG_CHECK_MODULES` 探测；这些宏的实际调用位置需对照 `configure.ac` 与仓库中 m4 辅助文件核验。每探测一项，就把「通过」或「未通过」连同具体编译命令写进 config.log，并把结论写进 `config.h`。关键在于：某个可选库探测失败时，configure 未必报错退出，很可能只是把对应特性悄悄关掉。这正是「构建看似成功、能力其实缺失」的根源，也是 02-02 里强调要逐段判读 configure 摘要的直接原因。

条件编译如何落到代码，可以用数据通道卸载作例子串一遍（具体选项名与宏名需对照实际版本核验）：某个 `--enable-*` 开关让 configure 检查 libnl 一类依赖，通过后定义相应宏，`Makefile.am` 把 `src/openvpn/` 下与该特性相关的 `.c` 加入目标，`#ifdef` 分支随之生效，链接阶段补上对应的 `-l` 参数；若依赖缺失，则整段代码被排除，最终版本输出里就不会出现对应标签。压缩库、PKCS#11、systemd 集成走的都是同一套「开关、探测、宏、源码、链接」五段式，这也正是 02-03 全参数表的底层逻辑。运行期机制不在此展开（原理见 06-xx）。

还要交代构建组织方式。configure 支持在源码目录之外单独建一个构建目录做 out-of-tree 构建，好处是不污染源码树、便于同时保留多套配置产物；`make` 可用 `-j` 并行加速。但插件、Windows 组件与内核模块各有独立构建节奏，不能都塞进同一条顶层 `make`，这条分界会在 02-04 与 02-05 展开。清理动作也有讲究：`make clean` 只删编译产物，`make distclean` 会连同 configure 生成的 `Makefile`、`config.h` 一并清掉，两者用错会导致「改了开关却不生效」的假象。

### 5. 配置/命令/代码实例

构建册的实例以命令为主；凡涉及运行时 `--` 参数只作最小引用并写「完整指令见 04-01」。下面先给从版本库获取源码、查看版本标记与顶层结构的命令。仓库地址、分支名与标签以官方发布页为准，需对照实际版本核验。

```bash
git clone https://github.com/OpenVPN/openvpn.git
cd openvpn
git describe --tags --always
ls -1
```

`ls -1` 列出的顶层清单，是判断「当前处于哪种源码形态」的第一手证据。以下为示例输出，具体格式需对照实际版本核验。

```text
Changes.rst
COPYING
INSTALL
Makefile.am
README
autogen.sh
config.h.in
configure.ac
distro
doc
sample
src
tests
version.m4
```

逐行判读这段输出，能把第 2 节与第 3 节的概念落到实处。看到 `configure.ac` 与 `Makefile.am` 同时出现，说明这是一份 git 检出形态的源码树：它带来的是 Autotools 的「输入」，而不是可直接运行的构建脚本，因此下一步必须先跑 `autoreconf` 或 `autogen.sh` 生成 `configure`，这一点在 02-02 会展开成完整命令。`config.h.in` 是 autoheader 生成的模板，configure 会据它产出真正的 `config.h`；`version.m4`（或 `configure.ac` 内的版本定义）是版本字符串的上游，决定 `--version` 报出的主版本；`distro`、`doc`、`sample`、`src`、`tests` 五个目录正好对应第 3 节目录地图里的发行版集成、手册、示例、主程序源码与测试。最该留意的是清单里并没有 `configure` 与 `Makefile` 这两个文件：tarball 才预生成它们，git 工作树里没有，所以不要一上来就敲 `./configure` 然后疑惑「为什么找不到文件」。此外，`git describe` 给出的往往是带提交数的开发版标记，与 release tarball 的正式版本号口径不同，记录版本时务必区分，任何具体文件名、标签与版本号都需对照实际版本核验，绝不能据这段示例去断定当前构建具备或缺少某项能力。

再补一组依赖版本探测命令，用来在 configure 之前先确认本机库是否到位。选项名与库名以 `./configure --help` 与 `configure.ac` 为准，需对照实际版本核验。

```bash
pkg-config --modversion openssl
pkg-config --modversion liblz4
```

这两条命令的意义在于「把探测前置」：若 `pkg-config` 返回 `Package ... was not found`（具体措辞需对照实际版本核验），说明对应开发包没装或不在搜索路径里，`./configure` 阶段极可能把相关特性静默关掉；返回一串版本号则只证明头文件与元数据在位，仍需看 configure 是否真正链接成功。这里再次强调，构建选项的具体拼写不去背，权威来源是 `./configure --help` 与 `configure.ac`，不确定处一律核验，绝不编造。

### 6. 注意事项、陷阱与最佳实践

第一处坑是 tarball 与 git 混用。拿到 tarball 却多跑一次 `autoreconf`，通常没事但可能覆盖随包附带的 `configure`，引来工具链版本差异；拿到 git 工作树却直接找 `configure`，则会卡在第一步。判断方法很简单：看顶层有没有 `configure` 这个文件，再对照 `autogen.sh` 与 `autoreconf` 的说明（见 `doc/` 下构建说明与 `INSTALL`，具体文件名需对照实际版本核验）。把这一步做对，后面一半的「玄学错误」都不会出现。

第二处、也是最隐蔽的坑，是可选依赖的静默降级。前面说过，configure 对某个可选库探测失败时未必报错，可能只是把特性关掉，于是 `make` 全程绿灯、`make install` 也成功，唯独 `--version` 里少了对应标签。对策是「四证合一」：看 configure 结尾的配置摘要、翻 config.log 里的失败探测记录、查 `config.h` 里的宏、再用 `openvpn --version` 复核编译期标签。更稳妥的做法是把关键开关显式写死成 `--enable-*` 或 `--disable-*`，不依赖自动探测的默认值；具体选项名以 `./configure --help` 与 `configure.ac` 为准，需对照实际版本核验。

第三处是 pkg-config 与多版本库冲突。系统自带 OpenSSL 与自行编译的 OpenSSL 并存时，`PKG_CONFIG_PATH`、`LDFLAGS`、`CPPFLAGS` 指错目录，会链接到与预期不符的库，轻则版本输出里的库版本不对，重则编译期宏与运行期行为错位。用 `ldd` 查看最终二进制链接到了哪个 `.so`，再回到 config.log 核对探测命令，是定位这类问题的标准动作。同理，交叉编译时尤其要确认 `pkg-config` 指向的是目标平台的 sysroot，而不是宿主系统。

第四处，把 config.log 当成排错第一手资料，而不是只盯屏幕上的 configure 输出。屏幕摘要高度概括，config.log 却保留了每一条探测用的编译命令、真实报错与退出码。「为什么这个库没被检测到」这类问题，答案几乎总在 config.log 里。养成构建失败先翻 config.log、再改环境、最后重跑 configure 的习惯，比反复盲试高效得多。

第五处是构建组织与清理。优先用 out-of-tree 构建保持源码树干净；`make -j` 加速时注意个别并行竞态，遇到诡异的链接错误先退回单任务复现；打包场景用 `DESTDIR` 配合 `--prefix` 把产物暂存到临时根目录，而不是直接装进系统；改过开关却感觉没生效时，先怀疑是不是 `make clean` 不够、该用 `make distclean` 重新 configure。这些动作朴素，却能把「配置看着对、行为却不对」的问题挡在前面。

最后收成一份纪律清单：版本基准始终锁定 2.6.x、2.7 开发分支与 `ovpn-dco`；凡选项名、库名、宏名、目录名不确定处，写「需对照实际版本核验」并给出 `configure.ac`、`Makefile.am`、`doc/` 的可定位路径；运行参数只在最小必要时引用并写「完整指令见 04-01」，结构体只点名并写「（字段见 05-xx）」，机制只写「原理见 06-xx」，模块只写「模块见 07-xx」。守住这些边界，本册就不会和四册权威源重复。

### 7. 小结与延伸阅读

用一句话收束本篇：从源码构建 OpenVPN，核心是先看懂「源码树地图、依赖分层图、产物链图」这三张图——知道 `configure.ac` 与 `Makefile.am` 是输入，`configure` 与 `config.h` 是产物，工具链、加密后端、压缩、扩展、测试五层依赖各管一段，`make` 到 `make install` 之间发生的是「探测结果变成条件编译、再变成二进制与安装内容」的过程。把这三张图立住，02-02 的分步命令就不再是一串要背的步骤，而是这张链条的逐段落地。

把交叉引用再明确一次：运行时配置与命令的完整清单见（完整指令见 04-01），结构体逐字段见（字段见 05-xx），机制与调用链见（原理见 06-xx），模块能力与特性见（模块见 07-xx），部署实战见 03-xx，运维与故障判读见 08-xx。本篇只负责构建视角的坐标与概念，既不与任何权威册重复，也不能替代它们；遇到具体选项名、字段名、宏名或版本号，一律回到 `./configure --help`、`configure.ac` 与实际源码核验。

想动手的读者，建议按这个顺序走：先读 `INSTALL` 与 `doc/` 下的构建说明（具体文件名需对照实际版本核验），再跑一次 `./configure --help` 把当前版本的开关清单抄下来，然后对照本篇第 3 节的目录树在 `src/openvpn/`、`src/compat/`、`src/plugins/` 里各挑一个文件看看它归哪条构建规则管。本册余下四篇各有分工：02-02 用实战型骨架给完整的 `./configure` → `make` → `make check` → `make install` 分步命令与逐段输出判读，02-03 把构建选项与依赖开关摊成一张可决策的表，02-04 讲三平台与打包，02-05 单讲 `ovpn-dco` 内核模块与配套组件。四篇合起来，读者应当既能独立编出一份能力可预期的二进制，也能在编错时迅速定位到具体环节。

## 02-02 从源码构建实战：configure / make / install

### 1. 目标与拓扑

本篇是一次可复现的构建实战，目标只有一件事：在一台干净的 Linux 主机上，从社区版源码完整走通 `./configure` → `make` → `make check` → `make install` 四步，得到一个能力可预期、版本可追溯的 `openvpn` 可执行文件，并且能对每一步的输出做出判读。这里的「可复现」不是口号：命令顺序、环境前提、预期输出与失败信号都会被写清楚，读者照着做应当得到同构的结果；若结果不同，也能根据第 5 节的排错表迅速定位到具体环节，而不是盲目重试。本篇只讲构建，任何运行时的 `--` 参数都只作最小引用并写「完整指令见 04-01」。

先把「拓扑」这个词在构建语境里说清楚。它指源码目录、构建目录、安装前缀与最终主机之间的位置关系。最直接的形态是 in-tree 构建：直接在解包或检出的源码根目录里跑 configure 与 make，产物也散落在源码树里。更推荐的是 out-of-tree 构建：另建一个空目录，从那里指向源码运行 `../openvpn/configure`，所有 `Makefile`、`config.h`、目标文件都落在构建目录，源码树保持干净，需要同时保留多套不同开关的产物时尤其方便。本篇命令以 in-tree 为主、并给出 out-of-tree 的等价写法，两种形态的流程完全一致。

安装前缀 `--prefix` 决定 `make install` 把二进制、man 页与示例放到哪里，缺省通常是 `/usr/local`，于是可执行文件落在 `/usr/local/sbin/openvpn`。打包场景还要引入 `DESTDIR`：它把安装动作整体重定向到一个临时根目录，用来生成 deb、rpm 或容器层，而不真的写进当前系统。这三者的关系（源码树、构建目录、prefix 加 DESTDIR 的落地点）是本章后续所有命令隐含的空间前提，先把它们摆正，才不会在「装完却找不到命令」或「打出来的包路径不对」时无从下手。

### 2. 前置条件与环境

构建前先确认工具链到位。必需的是 C 编译器、make、autoconf、automake、libtool 与 pkg-config。若拿到的是 release tarball，里面已预生成 `configure`，autoconf 一套其实可以不用；若拿到的是 git 检出，则必须靠 `autoreconf` 生成构建脚本，这几个工具一个都不能少。用 `autoreconf --version`、`make --version`、`pkg-config --version` 逐个确认存在即可，具体版本要求以 `doc/` 下构建说明与 `INSTALL` 为准，需对照实际版本核验。

再确认加密后端与可选库。社区版需要一个 SSL/TLS 与加密实现，通常是 OpenSSL，也可以改用 mbedTLS（选项名与取值需对照实际版本核验）；LZO、LZ4 属于可选压缩库；PKCS#11 相关功能依赖 pkcs11-helper；systemd 集成依赖 libsystemd；数据通道卸载相关构建依赖 libnl 一类库，但那属于 02-05 的范围。用 `pkg-config --modversion openssl` 之类命令先探一遍，能提前暴露「开发包没装」这类问题，具体库名以 `configure.ac` 与 `./configure --help` 为准。

把前置检查列成下表，每一项都给出「检查什么」与「异常信号」。表中源码形态一格写成 `tarball\|git`，竖线表示两种取值，按表格约定转义为 `\|`，避免被解析成列分隔。

| 检查项 | 代表工具或库 | 检查方式 | 异常信号 |
|---|---|---|---|
| 源码形态 | tarball\|git | 看有无 configure 文件 | 误跑 autoreconf 或缺脚本 |
| 编译器与 make | gcc、make | 命令加 --version | command not found |
| Autotools | autoconf、automake、libtool | 命令加 --version | git 检出时无法生成脚本 |
| pkg-config | pkg-config | 命令加 --version | 库探测整体失效 |
| 加密后端 | OpenSSL 或 mbedTLS | pkg-config 查版本 | 缺开发头文件或库 |
| 可选库 | LZO、LZ4、pkcs11-helper | pkg-config 查版本 | 特性被静默关闭 |

环境层面还有两点要提前定。一是权限：前四步（configure、make、check）在普通用户下即可，`make install` 要写入 `--prefix` 指向的系统目录，通常需要 root 或 `sudo`；若把 `--prefix` 指到自己家目录，则全程无需提权，也更安全。二是干净度：如果这台机器之前编译过，先用 `make distclean`（或删掉构建目录重来）清掉旧的 `config.h` 与 `Makefile`，否则改过的开关可能因为残留产物而不生效，表现为「命令敲了却没反应」。

最后强调版本基准。本篇命令与输出以 OpenVPN 2.6.x 稳定分支、2.7 开发分支（master）为参照，所有具体选项名、库名、目标文件名与输出格式都可能随版本变化，凡不确定处写「需对照实际版本核验」并给出 `configure.ac`、`Makefile.am`、`doc/` 的定位路径。读者手里的 `./configure --help` 才是当前版本选项名的最终权威，本篇不编造任何开关拼写。

### 3. 分步操作

下面按图中顺序给出完整分步命令。为便于判读，把命令与对应的典型输出分开列出；所有输出均写明「示例输出，具体格式需对照实际版本核验」，且刻意不使用任何省略行，每行都是一条完整示意记录。

**步骤一：生成 configure（仅 git 检出需要）**。tarball 用户可整步跳过。

```bash
cd openvpn
autoreconf -i -v -f
```

`autoreconf` 会按 `configure.ac` 与各级 `Makefile.am` 生成 `configure`、`Makefile.in`、`config.h.in` 等输入。参数含义：`-i` 补齐缺失的辅助文件，`-v` 打印详细过程，`-f` 强制重建。若这一步报「宏未找到」，通常是缺 libtool 或 pkg.m4 一类宏包，回到第 2 节补工具链即可。

**步骤二：运行 ./configure 探测本机并生成 Makefile 与 config.h**。

```bash
./configure --prefix=/usr/local
```

如需启用或关闭可选特性，可在这一行追加 `--enable-*` 或 `--disable-*` 开关，具体选项名以 `./configure --help` 与 `configure.ac` 为准，需对照实际版本核验，本篇不编造拼写。out-of-tree 写法是另建目录后运行 `../openvpn/configure --prefix=/usr/local`，其余步骤不变。以下是示例输出，具体格式需对照实际版本核验。

```text
checking build system type: x86_64-pc-linux-gnu
checking host system type: x86_64-pc-linux-gnu
checking for gcc: gcc
checking whether the C compiler works: yes
checking for pkg-config: /usr/bin/pkg-config
checking for openssl via pkg-config: yes
checking for lz4 via pkg-config: yes
config.status: creating Makefile
config.status: creating config.h
config.status: executing depfiles commands
OpenVPN 2.6.x configure summary
  crypto library: OpenSSL
  compression: LZO, LZ4
  prefix: /usr/local
```

这段输出值得逐行判读，它是整场构建最关键的一张「体检报告」。开头两行确认构建系统与宿主系统类型，交叉编译时这两行若不一致就要警惕工具链指错平台；`checking for gcc` 与 `whether the C compiler works` 确认编译器可用，任何一条是 `no` 都会直接中止；`checking for pkg-config` 给出探测工具的绝对路径，后续所有库探测都经由它，若这里为空，可选库大概率被静默跳过；`openssl`、`lz4` 两行的 `yes` 说明对应开发包被找到，若某行是 `no`，configure 未必报错，而会把相关特性悄悄关掉，这正是最需要盯住的地方；`config.status` 三行证明 `Makefile` 与 `config.h` 已真正生成，是「可以进入 make」的硬门槛；结尾的配置摘要用人类可读的方式复述加密后端、压缩库与安装前缀，务必与自己的预期逐项对照。特别提醒：摘要里的版本号、后端名称与标签格式都是示意，任何具体值都需对照实际版本核验，绝不能据这段示例断定当前构建具备某能力；看到摘要与预期不符，应立刻翻 config.log 查对应探测的真实报错，而不是继续往下敲 make。


**步骤四：运行单元测试**。这一步常被跳过，但它是把「编译通过」和「构建可信」分开的关键。

```bash
make check
```

以下是示例输出，具体格式需对照实际版本核验。

```text
PASS: test_crypto
PASS: test_buffer
PASS: test_packet_id
Testsuite summary
TOTAL: 3
PASS:  3
FAIL:  0
```

判读要点集中在 `TOTAL`、`PASS`、`FAIL` 三行：`FAIL` 必须为 0，任何非 0 值都说明某个测试没过，此时不要继续 install，应先看 `tests/` 下对应日志定位；`PASS` 的具体测试名与数量随版本变化，需对照实际版本核验，示例里的三个名字只是示意。若报「测试框架缺失」，通常是 cmocka 一类测试依赖没装，补齐后重跑即可。

**步骤五：安装**。

```bash
sudo make install
```

若 `--prefix` 指向自己有写权限的目录，可去掉 `sudo`。以下是示例输出，具体格式需对照实际版本核验。

```text
 /usr/bin/mkdir -p '/usr/local/sbin'
 /usr/bin/install -c openvpn '/usr/local/sbin/openvpn'
 /usr/bin/mkdir -p '/usr/local/share/man/man8'
 /usr/bin/install -c -m 644 doc/openvpn.8 '/usr/local/share/man/man8'
```

这几行说明安装器把 `openvpn` 二进制放进 `sbin`、把 man 页放进对应手册目录，路径由 `--prefix` 决定，需对照实际版本核验。若要做打包，把命令换成 `make install DESTDIR=/tmp/pkgroot` 一类写法，产物会整体落在临时根目录下而不是真实系统；`DESTDIR` 与 `--prefix` 是两个不同层次的重定向，不要混用。

### 4. 验证方法与预期结果

装完不等于构建正确，验证阶段要把「版本、能力标签、链接库」三件事逐一钉死。第一件是版本与编译期能力，用版本查询命令看方括号标签是否与 configure 摘要一致。以下为示例输出，具体格式需对照实际版本核验。

```bash
openvpn --version
```

```text
OpenVPN 2.6.x x86_64-pc-linux-gnu [SSL (OpenSSL)] [LZO] [LZ4] [EPOLL] [AEAD]
library versions: OpenSSL 3.x, LZO 2.x, LZ4 1.x
```

逐项判读：第一行给出主版本与构建目标平台，方括号里逐个列出编译期启用的能力，应与步骤二结尾摘要逐项对应——摘要说 OpenSSL 与 LZ4 被找到，这里就应出现 `[SSL (OpenSSL)]` 与 `[LZ4]`；若摘要里某项是 `yes` 而这里没有标签，或反过来，说明「探测」与「编入」之间出了偏差，必须回查 config.log 与 `config.h`。第二行的库版本决定实际链接的加密库行为。这里要克制：任何具体版本数字、库版本与年份都随发行版变化，需对照实际版本核验；且标签只表示编译期支持，不等于运行期已启用，是否真正生效还要结合配置与日志判断（完整指令见 04-01）。完整的运行时指令清单不在本篇范围。

第二件是确认装到哪、有没有真的落地。用 `ls -l /usr/local/sbin/openvpn` 看文件存在与权限，用 `command -v openvpn` 或 `which openvpn` 看 PATH 是否能找到；若 `--prefix` 用了非标准路径，要把对应 `sbin` 加进 PATH 或写全路径调用。第三件是链接库复核，用 `ldd /usr/local/sbin/openvpn` 查看实际链接到的 `.so`，确认加密后端与压缩库来自预期位置，而不是系统里另一个版本；这三件合起来，才构成「构建结果可预期」的完整证据链。

把验证动作与预期结果列成下表，失败时可直接反查。

| 验证动作 | 命令 | 预期结果 | 不符时的含义 |
|---|---|---|---|
| 版本与能力 | openvpn --version | 标签与摘要一致 | 探测或链接有偏差 |
| 落地位置 | ls -l 加 prefix 下 sbin | 文件存在且可执行 | 安装未成功或路径错 |
| 命令可见 | command -v openvpn | 返回完整路径 | PATH 未包含 sbin |
| 链接库 | ldd 加二进制路径 | 指向预期库文件 | 库版本或路径冲突 |

### 5. 常见失败与排错

第一类失败发生在 configure 阶段，典型是 `configure: error: ...` 后面跟一句「某库未找到」。此时不要急着改命令，先翻 config.log：它保留了每一条探测用的编译命令与真实报错，比屏幕摘要详细得多。常见根因是只装了运行库、没装开发包（头文件与 `.pc` 文件缺失），或 `PKG_CONFIG_PATH` 没指向自编译库的位置。补依赖后重新跑 `./configure`，必要时先 `make distclean`。

第二类是「静默降级」型的软失败：configure 没报错、make 也绿灯，唯独 `--version` 少了某个标签。这几乎总是可选库探测失败被悄悄略过。对策是把关键开关显式写死成 `--enable-*` 或 `--disable-*`（具体名以 `./configure --help` 与 `configure.ac` 为准，需对照实际版本核验），再用 02-03 讲的「摘要、config.log、config.h、版本输出」四证合一复核，避免依赖自动探测的默认值。

第三类是 make 阶段的编译或链接错误。先看报错落在哪个 `.c`，再判断是源码与当前库版本不兼容，还是缺了某个条件宏对应的依赖；`make -j` 并行下的偶发链接失败，用单任务 `make` 复现一次即可排除竞态。若改过开关却感觉没生效，多半是残留了旧的 `config.h` 与 `Makefile`，用 `make distclean` 重新 configure，而不是只 `make clean`。

第四类是 `make check` 失败。先看 `FAIL` 非 0 的那一项与 `tests/` 下对应日志，区分是测试依赖（如 cmocka）没装，还是真实的功能回归。测试依赖缺失属于环境问题，补齐重跑；若是真实回归，不要绕过测试直接 install，应记录版本与环境信息，回到对应源码定位。

第五类是 install 与安装后的失败。`make install` 报权限不足，说明 `--prefix` 指向系统目录却没提权，改用 `sudo` 或把前缀换到自己目录；装完敲 `openvpn` 提示找不到命令，多半是 `/usr/local/sbin` 不在 PATH，写全路径验证即可；打包时产物路径不对，通常是把 `DESTDIR` 与 `--prefix` 混为一谈，二者一个管「临时根」、一个管「最终安装前缀」，需要分开设置。把失败现象与所属阶段对应成下表，排错时按图索骥。

| 现象 | 所属阶段 | 优先查看 | 处理方向 |
|---|---|---|---|
| 报某库未找到 | configure | config.log | 补开发包与探测路径 |
| 能力标签缺失 | configure | 配置摘要与 config.h | 显式写死开关重配 |
| 并行链接报错 | make | 单任务复现 | 排除竞态或依赖冲突 |
| 测试 FAIL 非 0 | make check | tests 下日志 | 补测试依赖或定位回归 |
| 找不到命令 | install 后 | command -v 与 PATH | 补全路径或改 PATH |

### 6. 小结

用一句话收束：从源码构建 OpenVPN 的可信路径，是「先确认源码形态与工具链 → 必要时生成 configure → 用 `./configure` 探测并生成产物 → `make` 编译链接 → `make check` 自测 → `make install` 落地 → 用版本、位置、链接库三重验证复核」，其中 configure 结尾摘要、config.log、`config.h` 与 `--version` 四者互相印证，是判断「能力到底编没编进来」的核心方法。跳过 `make check` 或跳过验证，都容易把「编译绿灯」误当成「构建正确」。

本篇给出的全部命令与输出都以 2.6.x 与 2.7 开发分支为参照，凡选项名、库名、目标文件名与输出格式不确定处，一律写「需对照实际版本核验」并指向 `configure.ac`、`Makefile.am` 与 `doc/`；运行时参数只在最小必要时引用并写「完整指令见 04-01」，结构体只点名并写「（字段见 05-xx）」，机制只写「原理见 06-xx」，模块只写「模块见 07-xx」。读者若能把这套流程在自己的机器上完整复现一遍，并逐段判读输出，就真正掌握了社区版「构建」这件事，而不只是会背四条命令。

接下来 02-03 会把本篇刻意略过的构建选项与依赖开关摊开，讲清每个开关如何影响最终能力；02-04 把同样的链条搬到 Windows 与 macOS；02-05 单讲不在这条用户态链里的 `ovpn-dco` 内核模块。三篇共同的前提，正是本篇反复强调的那句话：先让二进制的来源可预期，再谈它运行时该做什么。

## 02-03 构建选项与依赖开关：OpenSSL / mbedTLS / LZO / LZ4 / PKCS#11 / systemd

### 1. 背景与动机

02-02 为了把主线讲清楚，只用了最基础的 `--prefix`，把一大片 `--enable-*` 与 `--with-*` 开关刻意留白。但真实项目里，「默认构建」往往不是想要的构建：发行版为了兼容性可能关掉某些特性，安全合规要求明确指定加密后端，硬件密钥场景需要 PKCS#11，服务托管环境希望带上 systemd 集成，而追求吞吐的环境又惦记数据通道卸载。构建选项因此不是可看可不看的附录，它直接决定最终二进制的能力边界，也决定后续配置、部署与排障能走哪条路。把这件事单独成篇，是为了让读者从「会敲构建命令」上升到「会定制一份能力可解释的构建」。

先划清一个极易混淆的边界：构建开关与运行时指令是两回事。构建开关出现在 `./configure` 的命令行上，作用是「把某段代码、某个库链接编进二进制」；运行时指令出现在配置文件或进程启动参数里，作用是「在已编好的能力范围内选择行为」。前者不存在的能力，后者写再多也唤不醒；反过来，前者编进来的能力，也未必在运行时自动启用。全书把运行时配置与命令的完整清单交给 04 册作唯一权威源，本篇凡涉及 `--` 形式的运行参数只作最小引用并写「完整指令见 04-01」，绝不重列指令族。

再讲清本篇与相邻篇的衔接。02-01 给了源码树与依赖分层，02-02 给了默认流程的完整分步与输出判读，本篇则回答「要改哪里、改了会怎样」：把 OpenSSL / mbedTLS、LZO、LZ4、PKCS#11、systemd 这几组最常见的开关按「作用、依赖库、源码落点、核验路径」摊成可决策的表，并给出一条开关从命令行传导到二进制的完整链。至于 `ovpn-dco` 相关的构建开关，因为它牵涉独立的内核模块与用户态配合，自成体系，统一留到 02-05 展开，本篇只在必要处点名，不抢它的内容。

版本基准与核验纪律依旧前置。本册以 OpenVPN 2.6.x 稳定分支、2.7 开发分支（master）与 `ovpn-dco` 为基准； configure 选项名、取值、依赖库名、自动生成的宏名都可能随版本调整，凡不确定处一律写「需对照实际版本核验」，并给出 `configure.ac`、`Makefile.am` 与 `doc/` 的可定位路径。读者手里 `./configure --help` 的输出才是当前版本开关拼写的最终权威，本篇任何具体选项名都只是引导核对的线索，不是可照抄的结论。结构体只点名并写「（字段见 05-xx）」，机制只写「原理见 06-xx」，模块只写「模块见 07-xx」。

### 2. 核心概念

Autotools 的开关大体分三类，先认清再谈取舍。`--enable-FEATURE` 与对应的 `--disable-FEATURE` 用于打开或关闭某个内建特性，通常带一个 `yes` 或 `no` 的缺省；`--with-PACKAGE` 用于指定「用哪个外部包或哪一种实现」，典型如加密后端的选择；此外还有 `--prefix`、`--host` 一类通用安装与平台选项，属于 Autoconf 约定而非本项目特有。三类开关在 `configure.ac` 里定义，在 `./configure --help` 里列出，在 `config.h` 里落成宏，最终在 `Makefile.am` 与源码里生效。

加密后端是「二选一」而非「多选多」。社区版需要一个 SSL/TLS 与加密实现来支撑控制通道握手、证书校验与数据通道加解密；常见选择是 OpenSSL，也可以改用 mbedTLS。这类选择通常经 `--with-crypto-library=...` 一类选项完成，具体选项名与合法取值需对照实际版本核验。要强调的是，后端一旦选定，影响的不是一两个文件，而是整片与 TLS、证书、加解密相关的代码路径与链接库，因此它属于「构建前就要想清楚」的决策，而不是构建后能随手切换的开关。运行期相关指令的完整清单见（完整指令见 04-01）。

可选依赖开关的语义要分清「自动探测」与「显式指定」两种模式。对 LZO、LZ4、PKCS#11、systemd 这类特性，configure 往往会先自动探测本机有没有对应开发包：探测到就默认启用，探测不到可能只是静默关闭。显式写 `--enable-*` 的意义，是把「要有」变成硬要求——依赖缺失时 configure 应当明确报错，而不是悄悄降级；显式写 `--disable-*` 则用于刻意裁剪，例如在不希望引入某压缩库的合规环境里。具体开关名以 `./configure --help` 与 `configure.ac` 为准，需对照实际版本核验。

再钉一次「编译期能力 ≠ 运行期启用」。开关把代码编进二进制后，`openvpn --version` 会出现对应能力标签；但标签只证明「支持」，不证明「生效」。压缩是否在隧道里真正使用、硬件令牌是否被调用、服务是否由 systemd 托管，都还要靠运行期配置与运行环境共同决定（原理见 06-xx、模块见 07-xx、完整指令见 04-01）。理解这一层，就不会把「我加了 `--enable-*`」误当成「功能已经在跑」。

### 3. 关键数据结构与源码位置

按 A 型骨架，本节名为「关键数据结构与源码位置」。在构建册里，它指的是「开关信息落在哪些文件」：选项定义在 `configure.ac`，条件目标在各级 `Makefile.am`（顶层、`src/`、`src/plugins/`），探测结果落在 configure 生成的 `config.h` 与 config.log，源码侧的生效点在 `src/openvpn/` 下的 `#ifdef` 分支与 `src/compat/` 的兼容实现。运行期结构体一律只点名并写「（字段见 05-xx）」，本节不展开任何字段。

把「开关族、依赖库、源码落点、核验路径」对应成下表，是本节最实用的一张坐标图。表中加密后端一格写成 `--with-crypto-library=openssl\|mbedtls`，竖线表示两种取值，按表格约定转义为 `\|`，否则整表错列。

| 开关族 | 依赖库 | 作用 | 源码与核验路径 |
|---|---|---|---|
| 加密后端 | OpenSSL\|mbedTLS | 选择 TLS 与加密实现 | configure.ac、src/openvpn/ |
| LZO 压缩 | liblzo2 | 启用 LZO 压缩支持 | Makefile.am、config.h |
| LZ4 压缩 | liblz4 | 启用 LZ4 压缩支持 | Makefile.am、config.h |
| PKCS#11 | pkcs11-helper | 硬件令牌与私钥访问 | src/openvpn/、doc/ |
| systemd | libsystemd | 服务集成与通知 | distro/、Makefile.am |
| 数据通道卸载 | libnl 一类 | 内核卸载用户态配合 | configure.ac（见 02-05） |

对着这张表补几处说明。依赖库一列写的是常见开发包名，具体名称与 `.pc` 文件名需对照实际版本核验；「源码与核验路径」一列给出的是定位方向而非精确文件，读者应回到 `configure.ac` 搜对应宏、到 `Makefile.am` 搜条件目标、到 `config.h` 搜生成的宏名。例如某个压缩开关打开后，`config.h` 里会出现相应的 `HAVE_*` 或 `ENABLE_*` 宏（确切拼写需对照实际版本核验），`src/openvpn/` 里对应 `.c` 才会被 `Makefile.am` 纳入目标。PKCS#11 与 systemd 两行还提示了 `doc/` 与 `distro/` 两个外围目录：前者放说明，后者放 service unit 一类集成材料。

本节不逐字段讲任何结构体。`struct options`、`struct context` 等运行期对象只在此点名，位于 `src/openvpn/` 下的头文件，字段一律（字段见 05-xx）；构建开关影响的是「哪些源码被编译、哪些宏被定义」，与这些结构体的字段语义不是同一层问题（原理见 06-xx）。把边界守住，本册才不会和 05、06 两册的权威内容重复。

### 4. 关键流程与调用链

一个开关从命令行走到二进制，要过五道关，这条链是本篇的主干。第一关，`./configure` 解析命令行上的 `--enable-*` / `--with-*`，交给 `configure.ac` 中对应的分支；第二关，configure 依选项执行探测（检查头文件、库函数，或经 `pkg-config` 的 `PKG_CHECK_MODULES` 一类宏），把结果记入 config.log；第三关，探测结论写成 `config.h` 里的条件宏；第四关，各级 `Makefile.am` 依据这些宏增删源码目标与链接库参数；第五关，`src/openvpn/` 里的 `#ifdef` 分支据宏决定哪段 C 代码被编译，最终链接进 `openvpn` 可执行文件，并在版本输出里体现为能力标签。把这条链画成图，见图 02-03-01。

edge n6 -> n1 dashed "标签回查开关"
:::

以 LZ4 为例把链走一遍（具体选项名与宏名需对照实际版本核验）：命令行上写对应 `--enable-*` 开关后，configure 在 `configure.ac` 的分支里经 `pkg-config` 检查 liblz4；检查通过，`config.h` 定义相应宏，`Makefile.am` 把与压缩相关的 `.c` 加入目标并补上链接参数，`src/openvpn/` 里 `#ifdef` 保护的实现被编入；最终 `--version` 里出现 `[LZ4]` 标签。若检查失败且开关是「自动探测」模式，链在第三关就断掉，后面全不发生，而 configure 屏幕可能毫无异常——这正是「四证合一」复核的必要性。PKCS#11、systemd、加密后端选择走的都是同一条链，差别只在第二关探测的库与第四关增删的源码不同。

还要补一条分界：这条链只负责「用户态二进制」。数据通道卸载相关的开关虽然在用户态侧也走类似流程，但它同时要求独立的内核模块与内核配置，链路横跨用户态与内核两半，因此本篇只把它列为表末一行并注明「见 02-05」，不在此展开。同理，切换加密后端会影响整片 TLS 与加密码路径，但那些代码怎么工作属于机制与模块范畴（原理见 06-xx、模块见 07-xx），本篇只讲「怎么把它编进来」，不讲「它运行时怎么跑」。

### 5. 配置/命令/代码实例

本节给三组实例：查询当前版本真实开关清单、按功能族组合一份带开关的 configure 命令、以及查看开关落成的 `config.h` 宏。所有选项名以 `./configure --help` 与 `configure.ac` 为准，需对照实际版本核验；运行时参数不在本节范围，涉及时写「完整指令见 04-01」。

第一组，也是最该先做的一组：查询当前版本的开关清单。

```bash
./configure --help
```

以下为示例输出，具体格式需对照实际版本核验。

```text
Optional Features:
  --disable-FEATURE       do not include FEATURE
  --enable-FEATURE=ARG    include FEATURE with ARG
  --enable-lzo            enable LZO compression support
  --enable-lz4            enable LZ4 compression support
Optional Packages:
  --with-PACKAGE=ARG      use PACKAGE with ARG
  --with-crypto-library=TYPE   select crypto library
```

逐行判读这份清单，能避免绝大多数「选项名写错」的低级故障。开头 `Optional Features` 段说明这一节列的是 `--enable-*` / `--disable-*` 开关，`--disable-FEATURE` 与 `--enable-FEATURE=ARG` 两条是 Autoconf 的通用模板，告诉你开关既可以只给名字、也可以带取值；随后两行是本项目具体特性开关的示意，压缩类开关就属于这一族。`Optional Packages` 段同理，列的是 `--with-*` 一类「选哪个包或哪种实现」的选项，加密后端的选择通常落在这一族。最关键的判读习惯是：不要把本篇或任何资料里写的具体选项名当成事实，而要回到当前源码的这份输出逐字核对；一旦把开关名拼错，configure 会报 `unrecognized option`，此时正确做法是回查帮助清单与 `configure.ac` 修正，而不是换一个近似的写法硬试。示例里的选项名、参数格式与分组标题都是示意，具体拼写、合法取值与分组方式均需对照实际版本核验。

第二组，按功能族组合一份完整的 configure 命令。多行用反斜杠续行，最后一行给完整参数收尾，不留悬空反斜杠。下列选项名按功能族示意，实际拼写与取值以 `./configure --help` 与 `configure.ac` 为准，需对照实际版本核验。

```bash
./configure --prefix=/usr/local \
    --with-crypto-library=openssl \
    --enable-lzo \
    --enable-lz4 \
    --enable-pkcs11 \
    --enable-systemd
```

这份命令的意图是「显式锁定加密后端为 OpenSSL、并显式要求 LZO、LZ4、PKCS#11 与 systemd 四项特性」。把关键开关显式写死，好处是缺依赖时 configure 会明确报错，而不是静默降级；代价是必须先把对应开发包装齐，否则在步骤二就会停下。若当前版本某个开关名不同，按 `--help` 输出替换即可。数据通道卸载开关未列入，因为它需要内核侧配合，见 02-05。

第三组，确认开关真的落成宏。configure 跑完后查看生成的 `config.h`，以下为示意片段，宏名需对照实际版本核验。

```c
#define HAVE_LZ4 1
#define ENABLE_PKCS11 1
#define ENABLE_SYSTEMD 1
```

这类宏就是第 4 节传导链第三关的产物：看到它们，才能确认「configure 不只是答应了，而是真的把结论写进了编译输入」。若 `--version` 里缺某个标签，回查 `config.h` 里有没有对应宏、config.log 里对应探测是否 `yes`，就能把问题锁定在第二关或第四关。注意 `config.h` 是 configure 生成的产物，不要手工编辑，改开关应重新 configure。

### 6. 注意事项、陷阱与最佳实践

第一，绝不凭记忆写选项名。开关拼写、合法取值、是否带 `=ARG`，都可能随版本变化；唯一权威是当前源码的 `./configure --help` 与 `configure.ac`。本篇与任何示例里的具体名字都只是功能族的示意，不确定处写「需对照实际版本核验」。拼错选项的代价看似很小，实则会让整份构建在错误的能力集合上继续往下走，后患比当场报错更大。

第二，关键开关显式化，别依赖自动探测的默认值。自动探测的便利背后是「静默降级」：某开发包没装，configure 不报错、直接把特性关掉，于是 `make` 全绿、`make install` 成功，唯独 `--version` 里少了标签。对加密后端、压缩、PKCS#11、systemd 这类你确实需要的能力，用 `--enable-*` 或 `--with-*` 写死，让缺依赖变成显式失败；对刻意不要的能力，用 `--disable-*` 主动裁剪。构建后用「配置摘要、config.log、config.h、`--version`」四证合一复核，是 02-02 已经强调过的方法，这里同样适用。

第三，加密后端切换是重决策。它影响整片 TLS 与加解密代码路径、链接库与证书相关行为，不是构建后能随手改的运行参数。切换前要确认目标后端的开发包版本、本机是否两套后端并存导致 `pkg-config` 指错，以及切换后相关能力标签是否如预期变化。后端在运行期怎么工作属于（原理见 06-xx）与（模块见 07-xx），本篇不展开；相关运行期指令的完整清单见（完整指令见 04-01）。

第四，压缩类开关要连着安全边界一起想。LZO、LZ4 把压缩能力编进来，只说明二进制支持，是否在隧道里启用、以及启用后的安全影响，是运行期配置与机制层面的问题（原理见 06-xx、模块见 07-xx），不要因为「编进去了」就默认它该被打开。同理，PKCS#11 依赖 pkcs11-helper 一类库，编进来只是打通了访问硬件令牌的通道，令牌怎么用由运行期决定；systemd 开关主要影响服务集成与 `distro/` 下的 unit 材料，与隧道协议本身无关。

第五，DCO 相关开关不要在本篇硬凑。它需要用户态开关、独立内核模块与内核配置三者配合，横跨两半，统一见 02-05；本篇表末那一行只是索引。强行把它和几个纯用户态开关并排写进同一条 configure 命令，很容易让人误以为「加个开关就等于卸载生效」，这是本册最需要避免的误解之一（原理见 06-xx、模块见 07-xx）。

最后收成一份可执行的习惯清单：构建前先跑 `./configure --help` 抄下当前版本开关；把需要的开关显式写死、不需要的显式关闭；跑完逐项对照摘要、`config.h`、config.log 与版本输出；把最终使用的那一条 configure 命令连同版本、依赖版本一起记进构建记录，保证可复现。凡选项名、库名、宏名不确定处，写「需对照实际版本核验」并指向 `configure.ac`、`Makefile.am`、`doc/`；运行参数只最小引用并写「完整指令见 04-01」，结构体只点名并写「（字段见 05-xx）」。

### 7. 小结与延伸阅读

用一句话收束：构建选项的本质，是把「我想要哪些能力」翻译成一条 `./configure` 命令，再经由「解析与探测 → `config.h` 宏 → `Makefile.am` 增删源码与库 → `src/openvpn/` 的 `#ifdef` → 能力标签」这条链，固化进最终二进制。看懂这条链，OpenSSL / mbedTLS 的二选一、LZO / LZ4 的压缩、PKCS#11 的硬件令牌、systemd 的服务集成，就不再是四个孤立的开关，而是同一套机制在不同依赖上的投影；而「显式写死关键开关 + 四证合一复核」，则是把「静默降级」这个最隐蔽的坑挡在门外的标准动作。

把交叉引用再明确一次：运行时配置与命令的完整清单见（完整指令见 04-01），结构体逐字段见（字段见 05-xx），机制与调用链见（原理见 06-xx），模块能力与特性见（模块见 07-xx），部署实战见 03-xx，运维与排障见 08-xx。本篇只负责「怎么把能力编进来」，既不与任何权威册重复，也不能替代它们；遇到具体选项名、宏名、库名或版本号，一律回到 `./configure --help`、`configure.ac` 与实际源码核验。

想继续深入的读者，建议按这个顺序走：先在自己机器上完整跑一次 `./configure --help`，把当前版本的开关清单与本篇第 3 节的表逐项对照；再挑一两个开关做对照实验，分别用「自动探测」与「显式 `--enable-*`」两种写法各构建一次，比较两次的配置摘要、`config.h` 与 `--version` 差异，亲手验证静默降级是怎么发生的；最后读 `configure.ac` 里对应分支，把「开关到宏」这一段源码对上。本册余下两篇各有分工：02-04 把这条链搬到 Linux、Windows、macOS 三个平台并讲打包，02-05 单讲 `ovpn-dco` 内核模块与配套组件，把本篇表末那一行索引展开成完整构建过程。读完三篇，读者应当既能定制一份能力可解释的构建，也能说清每个开关究竟改了源码里的哪一段。

## 02-04 跨平台构建：Linux / Windows / macOS 与打包

### 1. 背景与动机

到 02-03 为止，所有命令都默认发生在一台 Linux 主机上：用系统自带的编译器、系统自带的头文件与库，编出一个 Linux 可执行文件。但社区版的一个重要特征恰恰是可移植——同一份 `configure.ac` 与 `src/openvpn/` 源码，要能在 Windows 与 macOS 上落地。一旦把目标平台换掉，「编译」这件事的复杂度会陡增：编译器可能不是本机编译器，头文件与库来自另一套工具链，虚拟网卡的驱动形态完全不同，服务托管方式不同，连最终交付物也从「一个可执行文件」变成「带驱动与服务的安装包」。把这些差异平铺在同一篇里，正是本篇要解决的问题。

先说为什么跨平台值得单开一篇。Linux 上「编译加安装」几乎就是全部；Windows 上社区版通常走 MinGW-w64 交叉编译，产物还要配合虚拟网卡驱动、交互式服务与安装程序才能用；macOS 上则多为原生编译加第三方打包，虚拟设备与系统安全策略又有自己的一套。若把 Linux 的经验直接照搬，最典型的翻车是：`pkg-config` 探测到的是宿主系统的库而不是目标平台的库，configure 看起来全绿，编出来的二进制却根本不能在目标机器上运行。理解「原生构建」与「交叉编译」的分界，是跨平台构建的第一课。

本篇在整册里的坐标。02-01 给了源码树与依赖分层，02-02 给了默认流程，02-03 给了构建开关；本篇把同一条链搬到三个平台，重点讲「工具链怎么换、平台相关源码在哪、产物怎么打包」。结构仍按 A 型七节走：先立背景，再澄清原生与交叉编译、驱动与打包形态等概念，然后给平台相关源码坐标与三平台路径图，接着拆交叉编译与打包流程，之后给三平台命令实例与输出判读，再收拢陷阱与最佳实践，最后小结并指向 02-05。

去重与边界依旧前置。运行时配置指令与命令行参数的完整清单属于 04 册，本篇凡涉及 `--` 形式的运行参数只作最小引用并写「完整指令见 04-01」；结构体逐字段属于 05 册，只点名并写「（字段见 05-xx）」；机制与调用链属于 06 册，只写「原理见 06-xx」；模块能力与特性清单属于 07 册，尤其虚拟设备驱动的能力差异、wintun 与 TAP-Windows6 的选型，本篇只从「构建与打包需要哪些组件」的角度点名，具体能力写「模块见 07-xx」，不展开功能清单。本篇只讲「怎么把跨平台产物造出来」。

版本基准与核验纪律。以 OpenVPN 2.6.x 稳定分支、2.7 开发分支（master）与 `ovpn-dco` 为参照；工具链前缀、`--host` 取值、驱动名、打包脚本名、仓库目录名都可能随版本与构建体系变化，凡不确定处一律写「需对照实际版本核验」，并给出可定位的 `configure.ac`、`Makefile.am`、`distro/` 与 `doc/` 路径，绝不编造选项、驱动名或版本号。Windows 侧官方另有独立的构建脚本仓库，其具体名称与结构需对照官方发布说明核验。

### 2. 核心概念

第一组概念是原生构建与交叉编译。原生构建指「在本机编译、产物也在本机跑」，configure 探测到的编译器、头文件与库都来自当前系统；交叉编译指「在宿主机器上编出目标平台的二进制」，例如在一台 Linux 上用 MinGW-w64 编出 Windows 的 `.exe`。Autotools 用 `--build` 描述构建机器、`--host` 描述产物运行的机器，二者不同即进入交叉模式；工具链通常带前缀，如 `x86_64-w64-mingw32-gcc` 一类，具体前缀需对照实际版本核验。交叉模式最关键的纪律是：所有依赖探测必须指向目标平台的 sysroot 与 `.pc` 文件，而不是宿主系统。

第二组是三个平台的差异地图。Linux 原生编译，虚拟设备走内核提供的 tun/tap 字符设备，服务多由 systemd 托管，`distro/` 下放 unit 与 rpm 材料；Windows 侧通常由 MinGW-w64 交叉编译，虚拟网卡依赖 wintun 或 TAP-Windows6 一类驱动，服务形态涉及 `src/openvpnserv/` 等平台组件，最终打成安装程序；macOS 侧多为原生编译，依赖常经 Homebrew 提供，虚拟设备与系统扩展策略相关，产物常打成 `.pkg`。这里所有驱动名、目录名与打包工具名都需对照实际版本核验，能力差异写（模块见 07-xx）。

第三组是「构建产物」与「交付产物」的区别。`make` 产出的是 `openvpn` 可执行文件（及插件），而真正交到用户手里的往往是安装包：Linux 的 deb 或 rpm、macOS 的 pkg、Windows 的安装程序。把源码归档成发布 tarball 用 `make dist`（更严格的 `make distcheck` 会顺带验证解包后能否重新构建）；把已编译产物组装成系统包，则要借 `DESTDIR` 把 `make install` 重定向到临时根目录，再交给各平台打包工具。这几条路径汇聚成图 02-04-02，后面第 4 节会展开。

还要澄清一个易混点：平台相关源码并不分散在各处，而是集中在少数目录，由 `Makefile.am` 的条件目标决定哪些被编译。`src/openvpnserv/`、`src/tapctl/` 一类目录（确切名称需对照实际版本核验）只服务 Windows，`distro/` 下的 systemd 与 rpm 材料只服务 Linux 发行版集成，`src/compat/` 则承担补齐各平台缺失函数与类型的公共职责。configure 依据目标平台决定条件分支，这套「同一份源码、按平台挑选编译单元」的机制，是理解跨平台构建的骨架。

最后照例钉住去重与口径：本篇讲「怎么编、怎么打包」，虚拟设备驱动本身怎么工作、隧道在各平台上怎么跑属于（原理见 06-xx）与（模块见 07-xx），运行期参数完整清单见（完整指令见 04-01），结构体只点名并写「（字段见 05-xx）」。版本基准与不确定处的核验要求贯穿全篇。

### 3. 关键数据结构与源码位置

按 A 型骨架，本节点名「关键数据结构与源码位置」，在跨平台语境下指的是「平台相关构建输入落在哪些文件」。核心仍是 `configure.ac` 与各级 `Makefile.am`：前者定义 `--host` 相关分支与平台探测，后者用条件目标决定 `src/openvpn/`、`src/compat/`、`src/plugins/` 以及 Windows 专用目录里哪些源码进入构建。运行期结构体一律只点名并写「（字段见 05-xx）」，本节不展开字段。

把三个平台的构建要素列成下表，是最便于速查的一张坐标图。表中驱动一格写成 `wintun\|TAP-Windows6`、产物一格写成 `deb\|rpm` 之类，竖线表示多种取值，按表格约定转义为 `\|`，否则会被解析成列分隔而让整表错列。

| 平台 | 构建方式 | 工具链 | 虚拟设备相关 | 交付产物 | 核验路径 |
|---|---|---|---|---|---|
| Linux | 原生编译 | 系统 gcc 与库 | 内核 tun/tap | deb\|rpm\|tarball | distro/、Makefile.am |
| Windows | MinGW 交叉编译 | x86_64-w64-mingw32 前缀 | wintun\|TAP-Windows6 | 安装程序 exe | configure.ac、doc/ |
| macOS | 原生编译 | clang 与 Homebrew 依赖 | 系统虚拟设备接口 | pkg | Makefile.am、doc/ |

### 4. 关键流程与调用链

先把 Linux 原生流程作为基线复述一遍，它和 02-02 一致：确认工具链与依赖 → `./configure`（可带 02-03 的开关）→ `make` → `make check` → `make install`。跨平台时，这条链的骨架不变，变的是三处：configure 要加 `--host` 一类参数指向目标平台，依赖探测要改指目标 sysroot，安装产物要经打包工具二次加工。把「不变」与「变」分开记，跨平台才不会变成三套互不相干的命令。

交叉编译流程值得逐步拆开（以 Linux 上编 Windows 为例，具体前缀与选项需对照实际版本核验）：先准备 MinGW-w64 工具链与目标平台的依赖库（加密后端、压缩库等都要是目标平台版本），并让 `pkg-config` 指向目标平台的 `.pc` 文件；再运行 `./configure --host=x86_64-w64-mingw32 --prefix=...`，configure 检测到 `--build` 与 `--host` 不同便进入交叉模式，探测改用带前缀的工具链；随后 `make` 编出 Windows 可执行文件；最后把可执行文件、驱动、服务组件与示例配置交给安装程序脚本打成安装包。任何一步若探测到宿主系统的库，都会导致「编出来了但跑不起来」，这是交叉编译最核心的风险点。

打包这条支线再展开一层。`make dist` 依据 `Makefile.am` 的发布清单生成源码 tarball，`make distcheck` 会额外验证解包后能否独立 configure、build、check、install，是发布前最有价值的一道自检；`make install DESTDIR=/tmp/pkgroot` 把安装动作整体重定向到临时根目录，供 `dpkg-buildpackage`、`rpmbuild`、macOS 的 `pkgbuild` 或 Windows 安装脚本取用。这些工具的具体调用参数与脚本名需对照 `distro/` 与 `doc/` 核验，本篇不编造。运行期如何配置服务属于（部署见 03-xx、完整指令见 04-01），此处只讲「产物怎么被装进系统」。

最后补一条分界：用户态二进制的打包链，与 02-05 要讲的内核模块构建是两回事。DCO 模块面向特定内核、用 DKMS 或内核构建系统单独编译，不随 `make install` 落地，也不进普通安装包；把它误当成一个平台相关的用户态组件，是跨平台打包时常见的范围错误。这条分界会在 02-05 完整展开（原理见 06-xx、模块见 07-xx）。

### 5. 配置/命令/代码实例

本节给三组实例：Windows 交叉编译的 configure、macOS 依赖准备与构建、以及源码发布与系统打包命令。所有 `--host` 取值、工具链前缀、包名与脚本名以 `./configure --help`、`configure.ac`、`distro/` 与 `doc/` 为准，需对照实际版本核验；运行时参数不在本节范围，涉及时写「完整指令见 04-01」。

第一组，Linux 上交叉编译 Windows 版本。多行命令用反斜杠续行，最后一行给完整参数收尾，不留悬空反斜杠；下列工具链前缀与开关按功能族示意，实际取值需对照实际版本核验。

```bash
export PKG_CONFIG_PATH=/opt/mingw/sysroot/lib/pkgconfig
./configure --host=x86_64-w64-mingw32 \
    --build=x86_64-pc-linux-gnu \
    --prefix=/usr/local \
    --with-crypto-library=openssl
make -j4
```

第二组，macOS 上用 Homebrew 准备依赖后原生构建。具体配方名与路径需对照实际版本核验。

```bash
brew install openssl lzo lz4 pkg-config
export PKG_CONFIG_PATH="$(brew --prefix openssl)/lib/pkgconfig"
./configure --prefix=/usr/local
make -j4
make check
```

第三组，源码发布与系统打包的常用命令。`DESTDIR` 把安装重定向到临时根目录，供打包工具取用；确切参数需对照 `distro/` 与 `doc/` 核验。

```bash
make distcheck
make install DESTDIR=/tmp/pkgroot
dpkg-buildpackage -us -uc
rpmbuild -ba distro/rpm/openvpn.spec
```

交叉编译 configure 的输出最值得逐行判读，它是判断「有没有真的进入交叉模式」的关键证据。以下为示例输出，具体格式需对照实际版本核验。

```bash
./configure --host=x86_64-w64-mingw32 --build=x86_64-pc-linux-gnu
```

```text
checking build system type: x86_64-pc-linux-gnu
checking host system type: x86_64-w64-mingw32
checking whether we are cross compiling: yes
checking for x86_64-w64-mingw32-gcc: x86_64-w64-mingw32-gcc
checking for openssl via pkg-config: yes
config.status: creating Makefile
config.status: creating config.h
```

逐行判读这段输出，能把第 2 节的概念落到实处。第一行 `build system type` 是宿主机器，第二行 `host system type` 是产物运行的平台，二者不同即满足交叉编译的前提；第三行 `whether we are cross compiling: yes` 是 configure 自己的确认，若这里是 `no`，说明 `--host` 没生效或被覆盖，后面所有探测都会用错工具链，必须停下来排查；第四行确认编译器已经切到带前缀的 `x86_64-w64-mingw32-gcc`，而不是宿主的 `gcc`，这是交叉编译能否成立的核心；第五行的库探测 `yes` 要特别警惕，它只能说明「按当前 `PKG_CONFIG_PATH` 找到了某套库」，却不能证明这套库是目标平台版本，若 `PKG_CONFIG_PATH` 指错到宿主系统，编出来的二进制在 Windows 上根本无法加载。`config.status` 两行证明 `Makefile` 与 `config.h` 已生成，可进入 make。特别提醒：示例里的三元组、工具链前缀、探测措辞与路径都是示意，任何具体值都需对照实际版本核验；且「编出可执行文件」不等于「目标平台可用」，还要连带核对驱动、服务组件与运行库的齐备程度，那些属于（模块见 07-xx）与（部署见 03-xx）的范围。

### 6. 注意事项、陷阱与最佳实践

第一，交叉编译最危险的坑是 `pkg-config` 指错平台。若 `PKG_CONFIG_PATH` 仍指向宿主系统的 `.pc` 文件，configure 会探测到宿主库，探测全部 `yes`、编译全部通过，产物却在目标机器上因架构或依赖不符而加载失败。对策是显式设置目标平台的 `PKG_CONFIG_PATH`、`PKG_CONFIG_SYSROOT_DIR` 一类变量，并在 configure 摘要与 config.log 里逐项确认探测命令用的是带前缀的工具链。若摘要里出现 `whether we are cross compiling: no`，一律先停下来，不要继续 make。

第二，Windows 侧要分清「编译」与「可用」。编出 `.exe` 只是第一步，虚拟网卡驱动（wintun 或 TAP-Windows6 一类，名称需对照实际版本核验）、交互式服务组件、运行库与安装程序都要齐备，且驱动涉及签名与系统权限，安装过程比 Linux 复杂。能力差异与选型写（模块见 07-xx），本篇只强调「打包时别漏组件」；具体服务与驱动的安装步骤见（部署见 03-xx），相关运行期参数完整清单见（完整指令见 04-01）。macOS 侧同理，系统扩展与安全策略可能限制虚拟设备加载，构建成功不代表隧道能起。

第三，善用 `make distcheck` 与 `DESTDIR`。发布源码包前跑一次 `make distcheck`，它会验证解包后能否独立 configure、build、check、install，能提前暴露「发布清单漏了某个平台相关文件」这类问题；打包时用 `make install DESTDIR=...` 把产物暂存到临时根目录，再交给 deb、rpm、pkg 或安装脚本，绝不把 `DESTDIR` 与 `--prefix` 混为一谈——一个管临时根，一个管最终安装前缀。

第四，平台相关源码改动要回到条件分支。若某平台编译缺文件，优先查 `Makefile.am` 的条件目标与 `configure.ac` 的平台探测，而不是去改 `src/openvpn/` 的通用逻辑；`src/compat/` 承担的正是补齐平台差异的职责。所有目录名、条件宏名、打包脚本名都需对照实际版本核验，不确定处写「需对照实际版本核验」并指向 `configure.ac`、`Makefile.am`、`distro/` 与 `doc/`，绝不凭印象编造。

第五，守住去重与版本边界。运行参数只在最小必要时引用并写「完整指令见 04-01」，结构体只点名并写「（字段见 05-xx）」，机制只写「原理见 06-xx」，模块能力与驱动特性只写「模块见 07-xx」。版本基准始终是 2.6.x、2.7 开发分支与 `ovpn-dco`；Windows 侧官方独立构建脚本仓库的具体结构、三平台工具链前缀与打包参数，都应以官方发布说明与实际源码为准核验。

### 7. 小结与延伸阅读

用一句话收束：跨平台构建的内核仍是 02-02 那条「configure → make → check → install」链，变化的只是三处——用 `--host` 与带前缀的工具链把探测切到目标平台，用 `Makefile.am` 的条件目标挑选平台相关源码，用 `make dist` 与 `DESTDIR` 加打包工具把编译产物变成可交付的安装包。Linux 原生、Windows 交叉编译、macOS 原生三条路径共享同一份 `configure.ac`，差异集中在工具链、虚拟设备驱动与打包形态上；而 `whether we are cross compiling: yes` 那一行，是判断这条链有没有走对的第一道闸门。

把交叉引用再明确一次：运行时配置与命令的完整清单见（完整指令见 04-01），结构体逐字段见（字段见 05-xx），机制与调用链见（原理见 06-xx），模块能力与驱动特性见（模块见 07-xx），各平台部署实战见 03-xx，运维与排障见 08-xx。本篇只负责「怎么把跨平台产物造出来并装进去」，既不与任何权威册重复，也不能替代它们；遇到具体工具链前缀、`--host` 取值、驱动名、打包脚本名或版本号，一律回到 `./configure --help`、`configure.ac`、`Makefile.am`、`distro/` 与 `doc/` 核验。

想动手的读者，建议按这个顺序走：先在 Linux 上把 02-02 的默认流程跑通，作为基线；再准备一套 MinGW-w64 工具链与目标平台依赖，试着跑一次带 `--host` 的 configure，重点核对输出里的 cross compiling 与编译器前缀；最后用 `make distcheck` 验证发布清单、用 `DESTDIR` 试装一遍，观察临时根目录下的完整安装树。本册最后一篇 02-05 会把本篇反复点名却始终没展开的 `ovpn-dco` 内核模块与配套组件讲清：它是独立仓库、用 DKMS 或内核构建系统单独编译、不随 `make install` 落地，也正因如此才需要自成一篇。读完五篇，读者应当既能编出三个平台的社区版产物，也能说清用户态二进制与内核模块各自该怎么构建。

## 02-05 DCO 内核模块与配套组件构建：ovpn-dco / DKMS / 内核配置

### 1. 背景与动机

02-04 结尾反复提到一个「不随 `make install` 落地」的组件，本篇就是要把这个例外讲透。OpenVPN 传统上是纯用户态程序：控制通道与数据通道都在 `src/openvpn/` 的进程里跑。引入数据通道卸载（DCO）之后，数据面可以搬到内核模块里，控制通道与密钥协商仍留在用户态，于是架构从「全用户态」变成「控制面用户态、数据面可选内核态」。这一变化带来的性能收益显著，但代价是构建链条被劈成两半：用户态二进制要带对应开关与依赖，内核侧还要单独编译并加载一个模块。`ovpn-dco` 就是那个内核模块，它不在社区版主源码树里，而是独立维护的仓库，因此需要单独成篇。

为什么不能把它并进 02-03 的开关表里。02-03 讲的是「一个开关如何把某段代码编进用户态二进制」，链路全在 `configure.ac`、`config.h`、`Makefile.am` 与 `src/openvpn/` 之间闭合。DCO 不同：用户态开关只是第一半，它依赖 libnl 一类库并通过能力协商与内核通信；第二半是 `ovpn-dco` 内核模块的源码、面向当前内核的编译、以及加载进内核的动作，用的是 DKMS 或内核构建系统，产物是 `.ko` 文件而不是可执行文件。把这两半混在一条 `./configure` 命令里讲，最容易让人误以为「加个开关就等于卸载生效」，这正是本册要避免的误解（原理见 06-xx、模块见 07-xx）。

本篇在整册里的坐标。02-01 给源码树地图，02-02 给默认用户态流程，02-03 给开关机制，02-04 给跨平台与打包；本篇收尾，专讲「用户态二进制之外那一半怎么构建」。结构按 A 型七节：先立背景与两半分界，再澄清 `ovpn-dco`、DKMS、内核配置与能力协商等概念，接着给组件与源码坐标，然后拆「构建、加载、协商」流程，之后给 DKMS 与手动构建的命令实例与输出判读，再收拢陷阱与最佳实践，最后小结并回扣全册。

去重与边界必须写清。运行时配置与命令行参数的完整清单属于 04 册，本篇凡涉及 `--` 形式的运行参数只作最小引用并写「完整指令见 04-01」；结构体逐字段属于 05 册，只点名并写「（字段见 05-xx）」；数据通道卸载的机制、能力协商与用户态回退属于 06 册，本篇只写「原理见 06-xx」，不展开状态机与调用链；模块能力与启用条件属于 07 册，只写「模块见 07-xx」，不列功能清单。本篇只讲「怎么把内核模块与配套组件构建并加载起来」。

版本基准与核验纪律格外重要。本册以 OpenVPN 2.6.x 稳定分支、2.7 开发分支（master）与 `ovpn-dco` 为基准；内核模块仓库路径、UAPI 头文件名、用户态相关 `.c` 文件名、configure 开关名、DKMS 用法、内核配置 `CONFIG_` 项与驱动名都可能随版本变化，凡不确定处一律写「需对照实际版本核验」，并给出可定位的 `configure.ac`、`Makefile.am`、`doc/` 与 `ovpn-dco` 仓库内路径，绝不编造选项、驱动名、版本号或内核配置项。

### 2. 核心概念

先给 `ovpn-dco` 定性。它是面向 Linux 的内核模块，承担数据通道卸载：把已建立会话的数据面报文处理搬进内核，减少用户态与内核态之间的拷贝与上下文切换。控制通道仍由用户态 `src/openvpn/` 负责握手、证书校验、密钥协商与参数推送，用户态再通过一套通信接口把密钥与会话状态下发给内核模块。这套接口的具体形态（例如 Generic Netlink 一类机制）与头文件、宏名需对照实际版本核验，本篇不写死实现细节（原理见 06-xx）。要点只有一句：`ovpn-dco` 是独立仓库、独立编译、独立加载的内核组件，不是 `make install` 会顺带装上的东西。

第二组概念是 DKMS。内核模块必须与运行中的内核版本、配置与符号表匹配，内核一升级，原先编好的 `.ko` 可能就加载不了。DKMS（Dynamic Kernel Module Support）的作用，是把模块源码注册进一个框架，在每次内核升级时自动针对新内核重新编译并安装，避免「升级完隧道起不来」。它依赖一份 `dkms.conf` 描述模块名、版本与构建规则，具体字段与用法需对照实际版本核验。与之相对的是手动构建：直接借助当前内核的构建目录，用 `make -C ... M=... modules` 编译出模块，再 `insmod` 或 `modprobe` 加载。两条路径产物相同，维护成本不同。

第三组是内核配置与头文件。编译外部模块需要当前内核的构建树与头文件（通常位于 `/lib/modules/$(uname -r)/build` 一类路径，需对照实际版本核验），内核本身还要开启相关网络与加密支持；具体 `CONFIG_` 项名称、必选项与可选项必须以 `ovpn-dco` 仓库内的 Kconfig、README 与当前内核配置为准核验，本篇绝不编造配置项。若内核缺某能力，模块可能编译失败，或加载后能力协商不通过；这类问题属于「构建与运行环境」而非「用户态开关」，定位方向完全不同。

第四组是「版本配合」与「能力协商」。用户态二进制、内核模块、内核版本三者需要互相配合：用户态 configure 要带 DCO 相关开关（选项名需对照实际版本核验）并链接 libnl 一类依赖，内核模块要已加载且版本兼容，运行时还要完成能力协商，数据面才会真正卸载到内核；任何一环不满足，用户态都可能回退到传统数据通道（原理见 06-xx、模块见 07-xx）。因此 `openvpn --version` 里的 DCO 标签只说明「用户态编进了支持」，不等于模块已加载、更不等于卸载已生效——这与 02-03 反复强调的「编译期能力 ≠ 运行期启用」是同一条原则，在 DCO 上表现得尤其典型。

最后照例钉住去重：本篇讲「怎么编、怎么装、怎么确认加载」，数据通道卸载的机制、状态机与回退逻辑写（原理见 06-xx），模块启用条件与能力边界写（模块见 07-xx），运行期参数完整清单见（完整指令见 04-01），结构体只点名并写「（字段见 05-xx）」。版本基准与不确定处的核验要求贯穿全篇。

### 3. 关键数据结构与源码位置

### 4. 关键流程与调用链

把 DCO 从源码到生效的完整链走一遍。第一半在用户态：configure 带 DCO 相关开关（选项名需对照实际版本核验），经 `configure.ac` 探测 libnl 一类依赖，写 `config.h` 宏，`Makefile.am` 纳入相关源码与链接库，编出的 `openvpn` 二进制在版本输出里带上 DCO 标签。第二半在内核侧：取得 `ovpn-dco` 独立仓库源码，用 DKMS 或内核构建系统针对当前内核编译出 `.ko`，再 `insmod` 或 `modprobe` 加载进内核。第三半是接合：用户态启动时通过通信接口检测内核模块能力，完成协商后才把数据面卸载下去，否则回退到传统用户态数据通道（原理见 06-xx、模块见 07-xx）。三半齐备，才谈得上「卸载生效」。

DKMS 路径值得单独拆开，它把「一次编译」变成「跟随内核升级持续可用」。流程是：把模块源码与 `dkms.conf` 注册进 DKMS 树（add），针对当前内核编译（build），安装到模块目录（install），此后每当系统内核升级，DKMS 钩子会针对新内核自动重建。把这条生命周期画成图 02-05-02，虚线表示内核升级触发的自动重建回查。

手动路径则更直接，适合一次性验证：确认 `/lib/modules/$(uname -r)/build` 一类内核构建树存在，用 `make -C "$KDIR" M="$(pwd)" modules` 触发外部模块编译，得到 `.ko` 后 `insmod` 加载，`lsmod` 与 `modinfo` 复核。它不注册 DKMS 钩子，因此内核升级后需要重新手动编译。两条路径的取舍很清楚：生产环境图省事与可维护，倾向 DKMS；临时验证或排障，倾向手动。

还要补一条关键分界：这条链的终点是「数据面卸载是否生效」，而判定它需要用户态与内核两侧证据。版本输出里的 DCO 标签只覆盖第一半；模块是否加载看 `lsmod` 与 `modinfo`；是否真正卸载、以及能力协商失败时如何回退，属于（原理见 06-xx）与（模块见 07-xx）的范围，本篇不展开机制，只强调「构建与加载是前置条件，不是充分条件」。运行期参数完整清单见（完整指令见 04-01）。

最后把顺序固定下来，作为可执行的清单：先编带 DCO 支持的用户态二进制并确认标签，再准备内核头文件与配置，接着用 DKMS 或手动方式编译并加载 `ovpn-dco`，然后核对模块信息，最后才在运行期验证卸载行为。跳过前两步直接查「为什么没提速」，或跳过模块加载只看版本标签，都是这一主题下最常见的排障弯路。

### 5. 配置/命令/代码实例

本节给三组实例：用户态带 DCO 开关的 configure、DKMS 构建加载、以及手动内核模块构建与复核。所有开关名、模块名、版本号、`CONFIG_` 项与路径以 `./configure --help`、`configure.ac`、`doc/` 与 `ovpn-dco` 仓库内文件为准，需对照实际版本核验；运行时参数不在本节范围，涉及时写「完整指令见 04-01」。

第一组，用户态侧带 DCO 相关开关的 configure（选项名示意，需核验）。

```bash
./configure --prefix=/usr/local --enable-dco
make -j4
sudo make install
openvpn --version
```

第二组，DKMS 路径。模块版本不从记忆里编造，而是从仓库 `dkms.conf` 的 `PACKAGE_VERSION` 字段读出，具体字段名需对照实际版本核验。

```bash
cd ovpn-dco
MODVER=$(awk -F= '/^PACKAGE_VERSION/{print $2}' dkms.conf)
sudo dkms add .
sudo dkms build -m ovpn-dco -v "$MODVER"
sudo dkms install -m ovpn-dco -v "$MODVER"
sudo dkms status
sudo modprobe ovpn-dco
```

第三组，手动内核模块构建与复核。确切模块文件名与命令参数需对照实际版本核验。

```bash
KDIR=/lib/modules/$(uname -r)/build
make -C "$KDIR" M="$(pwd)" modules
sudo insmod ovpn-dco.ko
lsmod | grep ovpn
modinfo ovpn-dco
```

`modinfo` 的输出是判断「模块能不能被当前内核接受」的关键证据。以下为示例输出，具体格式需对照实际版本核验。

```text
filename:       /lib/modules/6.x/kernel/extra/ovpn-dco.ko
version:        0.x
license:        GPL
description:    OpenVPN data channel offload
depends:        udp_tunnel
vermagic:       6.x SMP mod_unload
```

逐行判读这段输出，能把第 2 节与第 4 节的概念连成一条线。`filename` 给出模块实际落盘位置，它必须处在与当前运行内核对应的模块目录下，若 `modinfo` 找不到文件或报路径不符，说明 DKMS 或手动安装没把 `.ko` 放对地方；`version` 是模块版本，需与用户态二进制及仓库说明互相配合，任何具体数字都需对照实际版本核验，不能据示例断定兼容性；`license` 与 `description` 用于确认找对了模块而不是同名异物；`depends` 列出模块依赖的内核组件，若其中某项缺失或未加载，`modprobe` 会失败或 `insmod` 报未知符号，这类问题要到内核配置与依赖模块层去查，而不是回头改用户态开关；`vermagic` 最该细看，它编码了内核版本与关键编译配置，模块与运行内核的 vermagic 不一致时加载会被直接拒绝，这正是「内核升级后模块失效、DKMS 自动重建」要解决的核心矛盾。特别提醒：示例里的版本号、依赖名、描述文字与路径全部是示意，任何具体值都需对照实际版本与仓库文件核验；且 `modinfo` 通过只证明「模块在位且元信息匹配」，不等于数据面卸载已经生效，后者还要看能力协商与运行期状态（原理见 06-xx、模块见 07-xx）。

### 6. 注意事项、陷阱与最佳实践

第一，先纠正方位感：`ovpn-dco` 是独立仓库，不在社区版主源码树里。02-01 那棵目录树里翻不到它，`make` 与 `make install` 也不会顺带把它编出来或装上。构建时必须分别准备用户态源码与内核模块源码，两条命令序列不要混成一条。这是本篇最基础、也最常被忽略的一点。

第二，内核头文件、构建树与运行内核必须匹配。编译外部模块需要 `/lib/modules/$(uname -r)/build` 一类内核构建树，它与当前运行内核版本不一致会导致 `vermagic` 不符、加载被拒；内核还要开启相关网络与加密支持，具体 `CONFIG_` 项需对照 `ovpn-dco` 仓库内 Kconfig、README 与当前内核配置核验，本篇不编造配置项。缺内核头、缺配置、版本不匹配，是模块编译与加载失败最常见的三类根因。

第三，DKMS 与签名、 Secure Boot 一类安全策略要一起考虑。DKMS 解决的是「内核升级后自动重建」，但启用安全启动的系统可能要求模块签名，未签名的模块即便编译安装成功也无法加载；这类策略性问题的表现是「`dkms status` 显示已安装、`lsmod` 却看不到」，定位方向是系统安全策略而非 DKMS 本身。具体策略名称与处理方式需对照实际发行版文档核验。

第四，别把「标签」「加载」「生效」混为一谈。版本输出里的 DCO 标签只说明用户态编进了支持；`lsmod` 与 `modinfo` 说明内核模块已加载且元信息匹配；数据面是否真正卸载、能力协商失败时如何回退到用户态，属于（原理见 06-xx）与（模块见 07-xx）。用户态二进制、内核模块、内核版本三者版本不配合时，最常见的结果不是报错，而是静默回退，看起来「一切正常但没有加速」。排障顺序应固定为：先确认用户态标签，再确认模块加载，最后才验证卸载行为。

第五，命令与名字一律核验。DKMS 用法、`dkms.conf` 字段名、模块名、`.ko` 文件名、UAPI 头路径、用户态 `.c` 文件名、configure 开关名、`CONFIG_` 项，都可能随版本变化，凡不确定处写「需对照实际版本核验」并给出 `configure.ac`、`Makefile.am`、`doc/` 与 `ovpn-dco` 仓库内可定位路径，绝不编造选项、驱动名或版本号。运行参数只在最小必要时引用并写「完整指令见 04-01」，结构体只点名并写「（字段见 05-xx）」。

最后收成一份可执行的习惯清单：把用户态 configure 命令、内核版本、模块版本与 `dkms.conf` 内容一并记进构建记录；优先用 DKMS 保证升级后可重建，临时验证用手动路径；每次内核升级后主动跑一次 `dkms status` 与 `modinfo` 复核；把「标签、加载、生效」三步的判定证据分开留存。版本基准始终锁定 2.6.x、2.7 开发分支与 `ovpn-dco`，守住这些边界，本册就不会和 04、05、06、07 四册权威源重复。

### 7. 小结与延伸阅读

用一句话收束：DCO 构建之所以要自成一篇，是因为它把「一次构建」劈成了两半——用户态二进制要带 DCO 相关开关并链接 libnl 一类依赖，内核侧的 `ovpn-dco` 则要作为独立仓库用 DKMS 或内核构建系统单独编译、单独加载，最后还要靠能力协商把两半接起来。`make install` 不会替你装内核模块，`openvpn --version` 里的标签也不等于卸载已生效；把「标签、加载、生效」三个层次分开验证，是这一主题下最重要的思维习惯。

把全册与全书的交叉引用一次性收齐：源码树与依赖分层见 02-01，默认构建分步与输出判读见 02-02，构建开关的传导链见 02-03，跨平台与打包见 02-04，本篇 02-05 收尾于内核模块与配套组件。运行时配置与命令的完整清单见（完整指令见 04-01），结构体逐字段见（字段见 05-xx），数据通道卸载机制、能力协商与回退见（原理见 06-xx），模块能力与启用条件见（模块见 07-xx），部署实战见 03-xx，运维、性能基准与排障见 08-xx。本册五篇只负责「怎么把社区版及其配套组件构建出来」，既不与任何权威册重复，也不能替代它们。

想动手的读者，建议按这个顺序走：先按 02-02 编出用户态二进制，再按 02-03 的方法显式写死 DCO 相关开关并用 `./configure --help` 核对拼写；随后准备与 `uname -r` 匹配的内核构建树，先在临时环境用手动路径编一次 `ovpn-dco` 并 `modinfo` 复核 `vermagic`，确认无误后再切到 DKMS 做长期维护；最后把「标签、加载、生效」三步的证据分别留存，形成可复现的构建记录。凡开关名、模块名、`CONFIG_` 项、UAPI 头路径与版本号不确定处，一律写「需对照实际版本核验」并回到 `configure.ac`、`Makefile.am`、`doc/` 与 `ovpn-dco` 仓库核验。读到这里，读者应当既能独立编出 Linux、Windows、macOS 三个平台的社区版产物，也能把数据通道卸载所需的内核模块与配套组件单独构建、加载并核对到位——这正是 02 册「编译与构建」五个篇目共同要交付的能力。
