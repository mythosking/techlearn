# OpenVPN 技术资料 · 01 基础与概述

## 01-01 OpenVPN 是什么：用户态 SSL/TLS VPN 的定位与能力边界

### 1. 背景与动机

在任何需要跨越不可信网络进行私密通信的场景里，工程上都面临同一组问题：分支机构要访问总部内网，运维人员要从公网登录机房设备，云上实例要与本地数据中心互通，出差员工要连回公司业务系统。承载这些流量的公网只提供尽力而为的分组转发，既不对通信对端的身份负责，也不保证数据在途中的机密性与完整性，更不会替你阻挡中间人的篡改与重放。于是「在现有 IP 网络之上再叠加一层经过认证与加密的隧道」成为长期存在的基础需求，虚拟专用网络正是为解决这组问题而生。

早期可选方案各有明显门槛。以 IPsec 为代表的内核态方案把安全关联与封装逻辑放进内核网络栈，策略语言复杂，安全关联与选择器配置繁琐，遇到网络地址转换与状态防火墙时往往还要额外的 UDP 封装与端口约定，不同操作系统上的实现差异又抬高了客户端部署与排障成本。一些专有或硬件绑定的方案虽然开箱即用，却带来许可、厂商锁定与生态封闭的代价。工程实践因此长期期待一种折中：不修改内核、尽量少依赖平台特性、以单个可执行程序交付、复用业界成熟的证书体系与标准加密库，并且能够比较容易地穿过常见的防火墙与地址转换设备。

OpenVPN 社区版正是对上述折中的回答。它把隧道端点放在一个用户态进程里，借助操作系统提供的虚拟网卡字符设备收发原始报文，把身份认证、密钥协商、机密性与完整性保护交给成熟的 SSL/TLS 实现。这样的取舍带来一连串直接好处：跨平台可移植性强，部署往往就是一份配置文件加一个进程；证书与吊销机制可以直接沿用公钥基础设施；协议既可以跑在 UDP 上，也可以改用更容易穿透的 TCP 端口；整个程序不需要往内核里打补丁。代价同样清楚，加解密、封装与报文搬运都在用户态完成，吞吐与时延受限于系统调用次数、内存拷贝与单进程的处理能力。理解这组取舍，是理解本册乃至整套资料的起点。

为什么要在开篇就先界定「是什么」。大量误解其实来自定位错配：有人把它当成一台功能完整的路由器，期待它承担复杂的动态路由与策略转发；有人拿它与内核态方案比拼线速吞吐，却忽略了两者根本不在同一性能量级；也有人把商业产品里才有的集中管理、集群与目录服务集成，当成开源守护程序天生自带的功能。若不先把能力边界划清，后续无论是读配置、读源码、做选型还是做容量规划，都会不断在同一个坑里反复跌倒。

本篇因此围绕三个问题展开：它在操作系统里究竟处在什么位置，它由哪几个必不可少的部件构成，它能可靠地做什么又明确不能做什么。回答完这三个问题，读者应当能够判断一个具体需求是否适合用它来解决，也能够看懂后续篇目里反复出现的「用户态」「双通道」「虚拟设备」「服务端复用」这些说法所指为何，而不至于把它们与内核态隧道或商用网关混为一谈。

还需要交代本篇的阅读坐标。本册属于概述层，只负责建立心智地图而不替代任何权威册：结构体只点名并给出真实源码路径，逐字段定义请转（字段见 05-xx）；配置只给能跑通的最小示例，完整指令族请转（指令见 04-xx）；机制只讲「做什么」与「从哪到哪」，状态机与调用链细节请转（原理见 06-xx）；模块能力只作索引，具体特性与组网请转（模块见 07-xx）。后续 01-02 做横向架构对比，01-03 拆开整体架构，01-04 收束版本演进与商业边界，四篇合起来构成全书的定位底座。

### 2. 核心概念

先给一个可操作的定义。OpenVPN 社区版是一个运行在用户态、以 SSL/TLS 为控制面基础的虚拟专用网络守护程序，其核心源码集中在 `src/openvpn/`。它不是内核模块，不是路由守护进程，也不是一整套网络操作系统，而是把「虚拟网卡、加密隧道、认证与密钥管理、以及多客户端服务能力」组合进单个进程的程序。用一句话概括它的职责：在不安全网络上建立经过认证与加密的点到点或多点接入通道，并把远端主机或网段接入到本地的转发视野里。

「用户态」三个字需要展开。它指进程完全通过标准系统调用与内核交互：先打开一个 tun 或 tap 虚拟设备，从该设备的文件描述符里读到的是原始 IP 报文或以太帧；完成加密与封装之后，再通过普通的 UDP 或 TCP 套接字把结果发出去，发出的仍然是内核能够正常路由的普通 IP 包。站在内核的角度，它只看见「某个进程在读写一个字符设备、某个进程在收发一个套接字」，完全不理解隧道内部的语义。这与把封装逻辑直接做进内核网络栈的方案形成根本分界，也解释了为什么它易于移植却难以达到内核线速。

再说「SSL/TLS VPN」的定位。它复用 SSL/TLS 协议栈来完成控制面的身份认证、证书链校验与密钥协商，再用协商产生的对称密钥去保护数据面的业务报文。证书体系成熟、吊销机制清晰、加密套件可以在握手期协商，是它相对许多轻量隧道的重要特征。这里要建立一个贯穿全书的二分：控制通道负责握手、密钥、参数推送与周期性重协商，数据通道负责承载真正的用户流量，二者复用同一条传输连接，靠通道标识区分，而不是各开一条物理连接（原理见 06-xx）。把这两条通道分开理解，后续读日志、看状态、定位握手失败都会轻松很多。

tun 与 tap 是另一个必须分清的概念。tun 工作在三层，读写的是 IP 报文，对应路由模式；tap 工作在二层，读写的是完整以太帧，对应桥接模式，能够承载广播与非 IP 协议。绝大多数远程接入与站点互连都应优先选择 tun，因为二层广播、地址解析与生成树语义会引入额外的复杂度与故障面。只有在确有二层邻接需求的场景里才考虑 tap（模块见 07-xx）。这一选型看似细节，实则决定了整套拓扑、地址规划与排障方式。

角色与形态同样需要澄清。它既可以是两端对等的点对点隧道，也可以是服务端模式下的多客户端接入点：后者在单个套接字上复用大量客户端实例，由服务端统一做地址分配、路由推送与状态维护（模块见 07-xx、原理见 06-xx）。无论哪种形态，构成要素都是同一套：一个虚拟设备、一对逻辑通道、一个传输套接字，以及由配置驱动的运行状态。理解这一点，就能明白为什么服务端与客户端其实共用绝大部分代码路径，差别主要落在初始化与调度策略上。

最后用一段话钉住能力边界。它能做的是「在不可信网络上建立经过认证与加密的隧道、把远端接入、并把访问控制交给证书与脚本钩子」；它不能做的是「替代内核转发平面、提供线速或多核轮询级吞吐、充当通用路由器或交换机、内置商业化的集中管理界面」。尤其要强调，商业版 Access Server 提供的 Web 控制台、集群、目录服务内置集成等属于另一套产品形态，绝不属于社区版 `src/openvpn/`，二者的分界会在 01-04 系统展开。

为便于快速对照，先把社区版的能力与非能力列成下表。

| 维度 | 属于社区版能力 | 不属于社区版能力 |
|---|---|---|
| 隧道建立 | 基于证书或账号的加密隧道 | 内核态 ESP 或 XFRM 封装 |
| 设备抽象 | tun 三层与 tap 二层虚拟网卡 | 通用交换机与生成树 |
| 认证体系 | X.509 证书、脚本与插件扩展 | 内置 LDAP 或 SAML 门户 |
| 运维形态 | 命令行、配置文件、管理接口 | Web 控制台与集群编排 |
| 性能定位 | 用户态加解密的单进程转发 | 内核线速或多核轮询转发 |

### 3. 关键数据结构与源码位置

本节只提供「源码坐标」，不展开任何字段。概述层的正确读法是先认目录、再认文件、再认对象，最后才在需要时去查字段；把顺序倒过来，很容易在几十个成员的头文件里迷失方向。所有结构体的逐字段定义、内存布局、读写时机与关联函数统一以（字段见 05-xx）为准，本篇一律只点名。

先看主干文件的分工。`src/openvpn/openvpn.c` 是程序入口，负责把命令行与配置文件交给解析层并拉起主流程；`src/openvpn/options.c` 把一条条指令解析成运行期配置，指令全集与命令行同构关系见（指令见 04-xx）；`src/openvpn/init.c` 负责初始化上下文、打开虚拟设备与链路套接字、按需下发系统路由，并在获得必要特权后完成权限降级；`src/openvpn/forward.c` 是事件循环的所在，负责在虚拟设备与网络套接字之间分派读写。这四个文件勾勒出「解析、初始化、运行」三段式主线。

再看控制面与数据面的落点。`src/openvpn/ssl.c` 及其相关头文件承载 TLS 控制通道的状态与握手逻辑，`src/openvpn/crypto.c` 承载数据通道的加解密与报文完整性校验，`src/openvpn/tun.c` 封装不同平台下 tun/tap 设备的打开与读写差异，`src/openvpn/multi.c` 实现服务端多客户端实例的复用与查找，`src/openvpn/socket.c` 处理链路套接字的建立与收发。把这些文件与上一节的两条逻辑通道对应起来，就能得到一张「哪个文件管哪件事」的地图（原理见 06-xx、模块见 07-xx）。

接着点名核心对象，但不展开字段。`struct context` 位于 `src/openvpn/openvpn.h`，是贯穿全局的运行上下文；`struct options` 位于 `src/openvpn/options.h`，是配置解析结果的载体；`struct tls_multi` 与 `key_state` 位于 `src/openvpn/ssl_common.h`，头文件位置需对照实际版本核验，二者描述控制通道的多会话与密钥状态；`struct buffer` 与 `struct frame` 分别位于 `src/openvpn/buffer.h` 与 `src/openvpn/mtu.h`，负责报文缓冲与长度推导；`struct multi_context` 与 `struct multi_instance` 位于 `src/openvpn/multi.h`，描述服务端实例表；`link_socket` 相关对象位于 `src/openvpn/socket.h`。以上对象的字段一律见（字段见 05-xx）。

外围目录也值得记住。`src/plugins/` 放置插件示例与插件接口相关实现，`sample/sample-config-files/` 提供可以直接改用的示例配置，`doc/` 存放手册与说明源，测试与辅助脚本位于仓库的其它目录，具体文件清单需对照实际版本核验。后续各册凡是出现「真实源码路径」，大多都能在这几处找到对应。版本基准以 2.6.x 稳定分支、2.7 开发分支以及 ovpn-dco 内核模块为准；凡是不确定的头文件位置、函数签名或宏名，都应回到 `src/openvpn/` 下实际源码核验，而不是凭印象书写。

### 4. 关键流程与调用链

本节只讲「从哪到哪」，不逐行展开状态机；完整的初始化流程、事件循环、握手状态迁移与封装细节统一以（原理见 06-xx）为准。对概述层而言，建立一张高阶链路地图，比背诵一串函数名更有价值，因为排障时首先要判断的是「问题落在哪一段」，而不是「某个函数第几行做了什么」。

启动链路可以这样走一遍：程序从 `src/openvpn/openvpn.c` 的入口开始，先把命令行参数与配置文件交给 `src/openvpn/options.c` 解析成运行期配置；随后 `src/openvpn/init.c` 完成上下文初始化，依次打开 tun 设备或 tap 设备、建立链路套接字、按需配置地址与系统路由，并把进程权限从启动时的高特权降到运行身份；一切就绪后进入 `src/openvpn/forward.c` 的事件循环。这条主线在任何部署形态下都成立，区别只在初始化阶段读了哪些配置、开了几个设备。

事件循环做什么，是理解整体行为的关键。它在一个线程里借助 I/O 多路复用同时等待虚拟设备描述符与网络套接字；哪一侧可读就先处理哪一侧，再按通道标识把控制报文交给 `src/openvpn/ssl.c` 相关路径、把数据报文交给 `src/openvpn/crypto.c` 相关路径。单线程模型带来的直接推论是：任何阻塞环节，无论是慢速脚本钩子、插件回调还是一次耗时很长的加解密，都可能拖累同一进程里的其它客户端（原理见 06-xx）。这条推论在服务端多客户端场景里尤其重要，也是后续做容量评估时的基本前提。

出站与入站两条方向值得单独记。出站方向，进程从 tun 设备读到原始 IP 报文，按当前会话的密钥完成加密与封装，再经链路套接字发往对端；入站方向，从套接字收到密文报文，做完整性校验与解密之后写回 tun 设备，由内核网络栈按普通 IP 包继续转发。控制通道则与业务数据并行工作，独立负责 TLS 握手、证书链校验、密钥协商、向客户端推送地址与路由参数，以及周期性的重协商。把「数据怎么走」和「控制怎么走」分开记，读日志时才不会被交织的输出绕晕。

服务端形态多一层调度。在 `src/openvpn/multi.c` 的多客户端模式下，服务端用单个套接字服务所有客户端，收到报文后按来源地址与会话标识查出对应的客户端实例，再把报文派发给该实例的状态机处理；实例表同时承载地址池分配、每客户端路由与状态维护（原理见 06-xx、模块见 07-xx）。这也是为什么服务端不需要为每个客户端各开一个监听端口，却能维持大量并发隧道。

引入 ovpn-dco 之后还要补一条分界：数据通道可以卸载到内核模块，控制通道与密钥协商仍留在用户态，于是「控制面在用户态、数据面可选内核态」成为更准确的架构描述，而不是把整个程序搬进内核。加载条件、能力协商与用户态回退都有专门机制（原理见 06-xx、模块见 07-xx）。理解这条分界，才能读懂 01-03 的分层图与 01-04 里数据面卸载的演进位置。

### 5. 配置/命令/代码实例

概述层只给能跑通的最小骨架，不重列指令全集，完整指令见 04-xx。下面是一份客户端侧的最小配置，用来体现「虚拟设备、传输方式、证书要素」三件套。

```conf
dev tun
proto udp
remote vpn.example.net 1194
ca ca.crt
cert client.crt
key client.key
```

`dev tun` 选择三层设备，`proto udp` 指定传输协议，`remote` 给出对端地址与端口，`ca`、`cert`、`key` 分别指向证书链、本机证书与私钥。真实部署还需要服务端校验、控制通道保护、密钥轮换等更多指令，且域名、端口、文件名都只是示例；把这些内容补全属于（指令见 04-xx）的范围，此处不展开。这份配置的最小意义在于说明：一个进程、一个虚拟设备、一份证书材料，就足以定义隧道的一端。

在排障或选型之前，先确认二进制的编译形态是最省事的一步。下面的命令与输出用来判断当前版本到底带有哪些能力；以下为示例输出，具体格式需对照实际版本核验。

```bash
openvpn --version
```

```text
OpenVPN 2.6.x x86_64-pc-linux-gnu [SSL (OpenSSL)] [LZO] [LZ4] [EPOLL] [AEAD] [DCO]
library versions: OpenSSL 3.x, LZO 2.x, LZ4 1.x
```

第一行给出主程序版本与构建目标平台，方括号里逐个列出编译期启用的能力：SSL 后端说明当前链接的是 OpenSSL 还是其它 TLS 实现，LZO 与 LZ4 是压缩库，EPOLL 说明事件循环可用的多路复用机制，AEAD 表示支持带认证的加密模式，DCO 表示构建时纳入了内核数据通道卸载支持。第二行的库版本决定当前实际链接的加密库行为，某些安全修复只有升级库之后才生效。正常输出应当看到明确的主版本、一个合法的 SSL 后端与 AEAD 能力；若缺少 AEAD 或 DCO，则说明该构建的能力边界偏旧，不能直接照搬新版本文档里的做法。需要特别克制的是，版本后缀里的具体数字、库版本以及任何年份都属于随发行版变化的内容，必须对照实际版本核验，绝不能凭示例输出里的数字下结论。另外，输出里出现某个特性标签，只表示编译期支持，不等于运行期已经启用，是否真正生效还要结合配置与日志判断。

### 6. 注意事项、陷阱与最佳实践

性能认知要摆正。它是用户态单进程，加解密、封装、内存拷贝与系统调用都在一个进程里完成，吞吐与时延受限于 CPU 单核与系统调用开销。拿它和内核态方案比性能时必须统一口径：是否启用数据通道卸载、用哪套加密套件、单流还是多流、MTU 与分片如何设置，方法见 08-xx。不要期待它达到线速，也不要用单一数值去概括所有场景。

角色错配是最常见的坑。别把它当路由器、交换机或防火墙的替代品；tap 桥接只解决特定二层邻接需求，广播与生成树语义要格外谨慎（模块见 07-xx）。更不要把 Access Server 的 Web 控制台、集群、内置目录服务集成写成社区版能力，边界在 01-04 会逐项列清。反过来也要避免另一种误解：社区版通过脚本钩子、插件与管理接口，确实能「组合」出外部认证与监控能力，但那是机制与外部组件的配合，不是产品化的内置功能（模块见 07-xx、指令见 04-xx）。

设备与承载协议选型。优先 tun 三层路由模式，只有确需广播、非 IP 协议或透明桥接时才考虑 tap。承载协议优先 UDP；在 TCP 之上再叠加可靠隧道会带来重传叠加的性能问题，端口与协议相关指令见（指令见 04-xx）。地址转换与状态防火墙环境下的保活、端口选择也要结合具体网络评估（部署见 03-xx）。

安全底线不能让步。始终保留对端证书校验，不要为了「先连上」就关掉验证；用控制通道保护机制降低握手面的暴露（模块见 07-xx、指令见 04-xx）；进程启动初期需要特权来打开设备、配置地址与下发路由，随后应尽快降权运行，相关指令见（指令见 04-xx）；系统时钟不准会直接导致证书校验失败，部署前务必先做时间同步。证书与私钥的保管、轮换与吊销属于长期运维动作，清单见 08-xx。

MTU 与分片是「能连上但大包不通」的高频根因。隧道封装增加额外头部，使有效载荷变小，路径 MTU 处理不当会表现为小包正常、大业务报文卡死。长度推导见（原理见 06-xx），相关指令见（指令见 04-xx），按现象反查的排障路径见 08-xx。

环境与排障顺序同样有章法。容器与云环境需要能访问 tun 设备并具备相应能力（部署见 03-xx）；定位问题时先看版本与编译形态，再看日志里是否出现初始化完成标志，然后才分段定位到控制通道或数据通道，工具与流程分别见（指令见 04-xx）与 08-xx。跳过前两步直接抓包，往往会在错误的方向上耗费大量时间。

把以上收敛成一份可执行的习惯清单：上线前登记版本输出、用最小配置先跑通再逐条增加指令、证书与私钥分权保管并定期轮换、变更留出回滚配置、升级前在测试环境做回归。这些动作看起来朴素，却能把绝大多数「配置看着对却连不上」的问题挡在前面，也能让后续的容量讨论建立在可复现的事实之上。

### 7. 小结与延伸阅读

用一句话收束：OpenVPN 社区版是「用户态进程 + SSL/TLS 控制面 + tun/tap 设备抽象 + 控制与数据双通道 + 单套接字多客户端复用」的组合，它以可移植性、成熟证书体系与防火墙适应性，交换了内核线速性能。它的能力边界清晰而稳定，这正是后续所有篇目展开的共同前提。

## 01-02 OpenVPN 与 IPsec / WireGuard / VPP / DPDK 的架构对比

### 1. 背景与动机

把 OpenVPN 放进整个网络技术版图里看，单靠「它是什么」还不够，还必须回答「它和邻居们差在哪」。工程选型时真正让人犹豫的，往往不是某个软件会不会用，而是面对一个具体需求，究竟该用成熟的用户态 SSL/TLS 隧道，该用内核态的 IPsec 或轻量隧道，还是该基于用户态数据面框架自己搭一套转发平面。若没有一张统一的架构对比地图，讨论很容易演变成各说各话的参数之争，甚至把不同抽象层的东西摆在一起比高低。

本篇选取四个常被拿来对照的对象：IPsec、WireGuard、VPP、DPDK。前两者与 OpenVPN 同属「能建立加密隧道」的范畴，后两者则是用户态高性能数据面领域的基础设施。这个组合不是随意拼的，它恰好覆盖了从「开箱即用的 VPN 产品」到「可用来构建 VPN 的底层框架」的整条光谱，也最容易暴露层级混淆。读者如果能把这四类技术的分工说清，就基本具备了在真实项目里做技术判断的能力。

需要先立一条重要前提：VPP 与 DPDK 并不是开箱即用的 VPN 产品，而是用来构建网络数据面的框架或套件；它们与 OpenVPN 不在同一抽象层。把它们和 IPsec、WireGuard 放在一起比「谁的隧道更好」是典型的关公战秦琼。本篇的对比因此分两层进行：对同为隧道的方案，比加密层次、握手、隧道模型、性能与可运维性；对数据面框架，只比「数据怎么被搬运、控制面留在哪里」这类架构思路，而不虚构它们并不具备的 VPN 成品能力。

对比维度的选择也有讲究。大纲给出的骨架是加密层次、握手、隧道模型、性能、可运维性五项，本篇在此基础上补上「运行空间与数据路径」以及「穿透、生态与抽象层边界」，凑成七个维度。加密层次决定机密性由谁实现，握手决定建链成本与身份模型，隧道模型决定地址与路由怎么规划，性能决定容量上限，可运维性决定长期成本，运行空间决定与内核的耦合程度，最后一项则用来防止层级错配。七个维度合起来，能覆盖一次选型里绝大多数真正影响决策的因素。

还要提醒读者警惕营销话术。任何脱离场景的「更快」「更现代」「更安全」都缺少意义：一个需要成熟证书体系、细粒度每客户端路由、跨代理与防火墙穿透的远程接入场景，与一个两端固定、追求极致轻量时延的站点互连场景，答案本就不同；而一个要自建运营商级转发平面的团队，考虑的又是完全不同的东西。本篇不给出「谁最好」的结论，只给出「在什么前提下谁更合适」的判断框架。

本篇仍属概述层：结构体只点名并给真实源码路径（字段见 05-xx），配置只给最小示例（完整指令见 04-xx），机制只讲「做什么」（原理见 06-xx），模块能力只作索引（模块见 07-xx）。涉及四个外部方案的实现细节，本套资料并不覆盖，凡具体内核子系统名、接口名或项目归属都标注需对照其官方文档核验，绝不臆造。

### 2. 核心概念

先逐一给四个对象定性。IPsec 是一组在 IP 层提供认证与加密的标准，典型实现把安全关联与 ESP 封装放在内核网络栈里，由用户态的 IKE 守护进程负责协商，策略由安全策略数据库驱动，站点到站点互连是它最经典的用场；跨网络地址转换时通常需要 UDP 封装配合。WireGuard 是较新的轻量隧道方案，以内核虚拟接口为形态，用 Noise 协议族完成一次往返握手，把「公钥即身份、允许 IP 即路由」压缩进极简的配置模型，并内建了地址漫游与密钥轮换。

再看另外两个。VPP 是用户态的向量报文处理框架，报文以「一批」而不是「一个」为单位流过一张由节点组成的有向图，每个节点对整批报文做同类处理，从而摊薄每包开销；它是构建路由器、网关、隧道端点的底座，本身不承诺交付一个成品 VPN。DPDK 是用户态轮询模式的数据面开发套件，通过绕过内核协议栈、绑定网卡、使用大页内存与轮询收发来换取极低时延与高吞吐，同样不定义隧道语义、身份认证或密钥协商。二者的具体项目归属、模块划分与版本信息需对照各自官方文档核验，本套资料只覆盖社区版 `src/openvpn/`。

把七个维度逐一说清，后面的对照表才读得懂。加密层次与运行空间，问的是机密性由用户态库还是内核子系统实现；握手与密钥协商，问的是建链用 TLS、IKE 还是 Noise，身份是证书还是公钥；隧道与封装模型，问的是虚拟设备、安全策略还是对等体允许 IP 来决定流量归属；数据路径与性能特征，问的是单包系统调用、内核封装、向量批处理还是轮询旁路；部署与可运维性，问的是依赖、配置形态与排障门槛；穿透与端口形态，问的是地址转换与防火墙下的可达性；生态定位与抽象层边界，问的是它究竟是成品隧道还是可搭建隧道的框架。

四个对比对象与 OpenVPN 并不都在同一抽象层，先把这层可比性列成下表，避免后文误读。

| 对象 | 抽象层 | 是否成品 VPN | 对比注意事项 |
|---|---|---|---|
| OpenVPN 社区版 | 用户态隧道进程 | 是 | 作为本册对比基准 |
| IPsec | 内核安全关联加用户态协商进程 | 是 | 同为隧道，可直接对比 |
| WireGuard | 内核虚拟接口 | 是 | 同为隧道，可直接对比 |
| VPP | 用户态向量协议栈框架 | 否 | 层级不同，只比数据面思路 |
| DPDK | 用户态轮询数据面套件 | 否 | 层级不同，只比转发思路 |

在这层前提之下，下表按七个维度把四种方案并列对照，以社区版 OpenVPN 为隐含参照基准，每格写该方案自身的典型特征。

| 维度 | IPsec | WireGuard | VPP | DPDK |
|---|---|---|---|---|
| 加密层次与运行空间 | 内核安全关联与 ESP 封装，用户态协商 | 内核模块内加密，接口轻量 | 用户态图节点处理，加密需节点承担 | 用户态轮询，加密需应用自行集成 |
| 握手与密钥协商 | IKE 协商安全关联，依赖外部守护进程 | Noise 一次往返握手，轮换内建 | 无内置 VPN 握手，需外部控制面 | 不定义隧道握手与密钥协商 |
| 隧道与封装模型 | 安全策略驱动的隧道或传输模式 | 虚拟接口加对等体公钥与允许 IP | 向量报文图，可插隧道处理节点 | 收发以太帧，不定义隧道语义 |
| 数据路径与性能特征 | 内核封装，可借硬件卸载 | 内核轻量路径，时延较低 | 用户态批处理向量，单核多包并行 | 用户态轮询旁路内核，需独占核 |
| 部署与可运维性 | 策略配置复杂，常配独立协商进程 | 配置与工具简洁，密钥分发需自理 | 需专门配置与启动脚本，门槛较高 | 需大页、网卡绑定与环境隔离 |
| NAT 穿透与端口形态 | 依赖 UDP 封装穿越地址转换 | 单一 UDP 端口，地址漫游内建 | 取决于具体应用与部署 | 不定义端到端穿透语义 |
| 生态定位与典型场景 | 站点互连、合规互操作 | 固定端点轻量互连与漫游接入 | 自建网关、路由器数据面 | 高速收发、旁路内核的转发底座 |

### 3. 关键数据结构与源码位置

本节只提供「去哪里定位差异」的源码坐标，不展开任何结构体字段（字段见 05-xx），也不重列配置指令（完整指令见 04-xx）。对架构对比而言，更重要的是知道「控制面落在哪个文件、数据面落在哪个文件」，而不是记住某个结构体有多少成员。

OpenVPN 侧的坐标是清晰的：`src/openvpn/ssl.c` 承载 TLS 控制通道的握手与状态，`src/openvpn/crypto.c` 承载数据通道的加解密与完整性校验，`src/openvpn/forward.c` 承载单线程事件循环的分派，`src/openvpn/tun.c` 承载虚拟设备的打开与读写，`src/openvpn/socket.c` 承载链路套接字，`src/openvpn/multi.c` 承载服务端多客户端实例的复用与查找，`src/openvpn/options.c` 承载配置解析。若构建纳入内核数据通道卸载，相关实现位于 `src/openvpn/` 下以 DCO 命名的源文件，具体文件名需对照实际版本核验。把这些文件按「控制面 / 数据面 / 设备 / 传输」归好类，就得到了与四个方案逐项对照的锚点（原理见 06-xx、模块见 07-xx）。

相应地，点名几个核心对象但不展开：`struct context` 位于 `src/openvpn/openvpn.h`，`struct tls_multi` 与 `key_state` 位于 `src/openvpn/ssl_common.h`（头文件位置需对照实际版本核验），`struct multi_context` 与 `struct multi_instance` 位于 `src/openvpn/multi.h`，`link_socket` 相关对象位于 `src/openvpn/socket.h`。它们分别对应全局上下文、控制通道多会话、服务端实例表与传输端点，字段一律见（字段见 05-xx）。

对照到另外四个方案时，必须克制：IPsec 的安全关联与安全策略位于内核子系统，由 IKE 守护进程从用户态下发，具体子系统名与接口需对照对应项目文档核验；WireGuard 的虚拟接口、对等体与允许 IP 表位于其内核模块内；VPP 的节点图与向量调度、DPDK 的轮询队列与大页内存都在各自项目源码里。本套资料不覆盖这些外部项目，也不臆造它们的路径或字段名。凡是涉及它们的结构、函数与版本，一律标注「需对照实际版本核验」。

于是本节可浓缩成一条可操作的方法：想判断某个能力差异，就回到 `src/openvpn/` 找控制面与数据面的分界；想判断外部方案的差异，就回到各自项目源码，而不是凭二手资料补脑。机制层面的差异请转（原理见 06-xx），模块层面的能力请转（模块见 07-xx）。

### 4. 关键流程与调用链

本节只讲「一次建链加一次报文各自怎么走」，不逐行展开状态机，具体实现见（原理见 06-xx）。把五条高阶路径并排看清，七个维度表里的「为什么」就都有了着落。

OpenVPN 的路径是：控制通道先经 TLS 完成证书校验、身份认证与密钥协商，派生出的密钥交给数据通道；业务报文从 tun 设备读出后加密封装，经链路套接字发出，入站反向解密写回；服务端模式下 `src/openvpn/multi.c` 按来源与会话标识查出客户端实例再分派。整条链路都在一个用户态进程里，内核只负责把字符设备与套接字的数据搬进搬出。

IPsec 的路径是：用户态的 IKE 守护进程协商出安全关联并下发到内核，内核按安全策略对匹配的流量做 ESP 封装或解封装，再交给普通路由转发。控制协商在用户态，真正的数据封装在内核，这是它与 OpenVPN 最本质的分工差异。WireGuard 的路径是：一次往返的 Noise 握手建立会话密钥，虚拟接口按对等体公钥与允许 IP 决定报文该发给谁、该收谁的，加解密在内核模块内完成；它没有证书体系与 TLS 握手，配置模型因此极简，但身份与分发方式也完全不同。

VPP 的路径是：报文以向量形式进入一张由节点组成的处理图，每个节点对整批报文执行同类操作，隧道的封装与解封装若需要，也只是图中的一类节点；DPDK 的路径是：轮询模式驱动从网卡批量收包，用户态应用直接处理，再轮询发回，全程不进入内核协议栈。二者都不自带「先握手、再派生密钥、再按会话加密」这条 VPN 控制链，把它们当成 VPN 来比握手是错配。

把五条路径叠起来看，差异主轴其实只有三问：控制面留在哪里，封装动作发生在哪里，报文以什么粒度被搬运。OpenVPN 是「控制与数据都在用户态、单包经系统调用、可选把数据面卸载到内核」；IPsec 是「协商在用户态、封装在内核」；WireGuard 是「握手极简、封装在内核」；VPP 与 DPDK 则把「搬运」本身做到了极致，却把「隧道」留给了上层应用（原理见 06-xx、模块见 07-xx）。

特别要澄清一个常见误读：引入 ovpn-dco 之后，OpenVPN 的数据通道可以卸载到内核模块，但控制通道依旧是基于证书的 TLS 握手与密钥协商，服务端的多客户端调度、参数推送与认证逻辑也仍在用户态。它不是「变成了 WireGuard」，而是「控制面与数据面分了家」（原理见 06-xx、模块见 07-xx）。这条分界既是理解 01-03 分层图的钥匙，也是 01-04 版本演进里数据面卸载那一支的前提。

### 5. 配置/命令/代码实例

概述层只给最小可运行示例，不重列指令全集，完整指令见 04-xx。下面是一份服务端侧最小配置，用来体现「监听、设备、证书、地址池」四要素；其中与版本相关的指令差异需对照（指令见 04-xx）与实际版本核验。

```conf
port 1194
proto udp
dev tun
ca ca.crt
cert server.crt
key server.key
dh dh.pem
server 10.8.0.0 255.255.255.0
```

`port` 与 `proto` 定义监听端点，`dev tun` 选择三层设备，`ca`、`cert`、`key` 给出服务端证书材料，`dh` 提供密钥交换参数（在偏好椭圆曲线密钥交换的配置里是否需要，需对照实际版本核验），`server` 一条指令展开地址池与服务端模式相关的多项默认行为。真实部署还需要控制通道保护、证书吊销、每客户端路由与日志级别等，全部属于（指令见 04-xx）的范围。

启动并用中等详细度观察初始化过程，是区分「用户态隧道」与「内核态隧道」最直观的办法。下面给出命令与典型输出；以下为示例输出，具体格式需对照实际版本核验。

```bash
openvpn --config /etc/openvpn/server.conf --verb 4
```

```text
OpenVPN 2.6.x x86_64-pc-linux-gnu [SSL (OpenSSL)] [LZO] [LZ4] [EPOLL] [AEAD] [DCO]
library versions: OpenSSL 3.x, LZO 2.x
TUN/TAP device tun0 opened
UDPv4 link local (bound): [AF_INET][undef]:1194
UDPv4 link remote: [AF_UNSPEC]

```

第一行与第二行是版本、编译目标与链接库信息，方括号里的能力标签只表示编译期支持，不等于运行期已启用。第三行「TUN/TAP device tun0 opened」是本篇最该盯住的一行：它说明进程在用户态打开了一个虚拟网卡字符设备，后续业务报文都要经这个设备进出，这正是用户态隧道区别于内核态方案的结构性证据；内核态的 IPsec 或 WireGuard 不会出现「进程打开 tun 字符设备并自行完成握手」这类日志，它们的安全关联或虚拟接口在内核里建立。第四、五行显示链路套接字已在本地端口绑定、对端尚未确定，属于服务端等待客户端接入的正常状态。第六行「Initialization Sequence Completed」是初始化完成标志，看到它才说明配置解析、设备打开、证书加载与控制通道就绪都已走通。判读异常时，缺第三行多半指向设备权限或内核模块缺失，卡在握手相关输出而迟迟没有完成标志，多半指向证书、密钥或控制通道保护参数不一致，端口绑定失败则指向地址占用或权限不足。日志里的具体版本号、库版本与格式都随发行版变化，需对照实际版本核验。

### 6. 注意事项、陷阱与最佳实践

最大的陷阱是层级错配。把 VPP 或 DPDK 与 OpenVPN 直接比「谁的 VPN 吞吐高」，等于拿发动机和整车比载客量：前者根本不定义隧道握手、证书与密钥协商，性能优势来自「不进内核协议栈、批量或轮询搬运报文」这一不同的前提。正确做法是先声明比较对象是否同为成品隧道，再统一加密套件、是否启用卸载、单流还是多流、MTU 与分片口径，方法见 08-xx。

第二个陷阱是把「内核态轻量」当成对 OpenVPN 的绝对否定。WireGuard 的极简来自它刻意收窄了能力集：没有 X.509 证书链与吊销体系，没有 TLS 之上的参数推送与每客户端路由分发，没有基于脚本与插件的可扩展认证，也没有 TCP 承载与代理穿透的现成路径。这些恰恰是远程接入、合规审计与复杂组网里常被要求的能力（模块见 07-xx、指令见 04-xx）。能力集不同，结论就不能只看时延一项。

第三个陷阱是把数据面卸载误读成身份改变。启用 ovpn-dco 后，OpenVPN 的控制面依旧是 TLS，服务端的多客户端调度与认证仍在用户态，加载条件与用户态回退都有专门机制（原理见 06-xx、模块见 07-xx）。文档里若出现「变成内核 VPN」之类说法，应回到源码核验而非照抄。同理，别把商业版 Access Server 的集群、Web 控制台与目录服务集成算进社区版能力，边界见 01-04。

性能数字尤其要克制。本篇不给出任何吞吐或时延的具体数值，因为这类数字高度依赖 CPU、网卡、加密套件、DCO 是否启用、单流多流与 MTU，脱离测试环境毫无意义；需要数字时应按 08-xx 的方法学自行实测并登记版本与构建形态。任何来自二手资料的「快几倍」都应当被复核。

把典型场景的选型建议汇总成下表，供快速初筛；最终仍需结合约束做验证。

| 场景诉求 | 优先评估 | 主要理由 |
|---|---|---|
| 远程接入、证书体系、跨代理与防火墙 | OpenVPN 社区版 | 成熟 PKI、TLS 与穿透形态灵活 |
| 端点固定、追求极简与低时延互连 | WireGuard 或 IPsec | 内核态轻量路径、配置模型简洁 |
| 合规互操作、与传统设备对接 | IPsec | 标准成熟、厂商互通性广 |
| 自建网关或路由器数据面 | VPP 或 DPDK | 向量批处理或轮询旁路内核 |
| 需要产品化集中管理与集群 | 商业版与社区版分开评估 | 能力边界不同，详见 01-04 |

落到最佳实践，可以归纳为四步：先写清需求里的硬约束（身份模型、穿透条件、吞吐目标、运维能力），再用七个维度逐项打分，接着用可复现的最小拓扑验证关键假设，最后把版本、构建形态与测试口径一并登记。这样得到的结论经得起复盘，也不会被一句「某某更快」带偏。

### 7. 小结与延伸阅读

把七个维度收束成一句话：IPsec 与 WireGuard 是同为隧道、封装在内核的对照面，VPP 与 DPDK 是把报文搬运做到极致却不含隧道语义的数据面框架，而 OpenVPN 社区版选择把控制与数据都放在用户态、用成熟证书体系与灵活穿透交换内核线速性能。谁更合适，取决于需求落在哪一组约束上，而非某个孤立的指标。

## 01-03 整体架构：tun/tap、双通道与服务端多路复用

### 1. 背景与动机

前两篇分别回答了「OpenVPN 是什么」以及「它和邻居们差在哪」，到这里镜头该拉回程序内部了。理解整体架构之所以必要，是因为这个软件把看起来毫不相干的几件事塞进了同一个进程：它要打开一张虚拟网卡、要在其上收发原始报文、要跑一套完整的 TLS 握手与证书校验、要对业务数据做对称加解密、还要在服务端模式下用一个套接字服务成百上千个客户端。若不先分层，读配置像在读一串互不相关的指令，读日志像在看几条交织的线索，排障时更分不清「连不上」到底卡在设备、握手还是路由。

本篇围绕三条主线展开。第一条是设备抽象，也就是 tun 与 tap：它决定了进程从内核拿到的是 IP 报文还是以太帧，进而决定整个拓扑是路由模式还是桥接模式。第二条是双通道，也就是控制通道与数据通道：二者复用同一条传输连接，却承担完全不同的职责，把它们拆开是读懂一切行为的前提。第三条是服务端多路复用：单进程、单套接字如何同时维护大量客户端实例，地址、路由与状态如何按实例分开。三条主线彼此咬合，合起来就是 `src/openvpn/` 的分层骨架。

从工程价值上看，架构图不是装饰。知道报文从 tun 描述符进来、经事件循环分派、由控制或数据通道分别处理、再经链路套接字出去，就能在日志停在某一行时立刻判断问题落在哪一段；知道服务端用实例表而不是每客户端一个端口，就能理解为什么一个慢客户端会拖累整体；知道数据面可以卸载到内核而控制面仍在用户态，就能明白启用卸载后某些 tun 读写路径为何不再出现。这些都是后续调优、扩容与故障定位的底层依据（原理见 06-xx、模块见 07-xx）。

本篇仍严格处在概述层。结构体只点名并给真实源码路径，逐字段定义请转（字段见 05-xx）；配置只给最小示例，完整指令族请转（完整指令见 04-xx）；机制只讲「做什么」与「从哪到哪」，状态机与调用链细节请转（原理见 06-xx）；模块能力只作索引，具体特性与组网请转（模块见 07-xx）。本篇的目标不是替代任何权威册，而是给出一张能随时回查的坐标图，让读者在后续深入某一册时不至于迷路。

与前后篇的衔接也顺带说明：01-01 建立了「用户态进程加双通道」的定位，01-02 把这套定位与其它方案做了七维度对照，本篇则是把定位里的每个名词拆成具体的层次与源码文件；到了 01-04，再把这些层次放进版本演进与商业边界的语境里收束。四篇由外而内、由静到动，构成完整的概述闭环。

### 2. 核心概念

先看整体分层。自下而上可以分成五层：最底下是应用进程与内核网络栈，负责产生和最终转发普通 IP 报文；其上是虚拟设备层，由 tun 或 tap 提供字符设备接口；再往上是用户态核心，也就是事件循环与上下文对象；然后是通道层，把流量分成控制通道与数据通道两条逻辑路径；最上面是传输层，通过链路套接字与对端收发密文或握手记录。分层的关键收益是职责隔离：设备层只管报文进出，通道层只管语义分派，传输层只管把字节送到对端（原理见 06-xx、模块见 07-xx）。

tun 与 tap 是设备层的两个选择。tun 工作在三层，进程从设备读到的是原始 IP 报文，写回的也是 IP 报文，对应路由模式，地址与路由由配置下发；tap 工作在二层，读到的是完整以太帧，能承载广播、地址解析与非 IP 协议，对应桥接模式。Linux 上这类能力通常经由 `/dev/net/tun` 字符设备提供，具体设备路径在不同平台与驱动下需对照实际版本核验（模块见 07-xx）。无论哪种，进程拿到的都是一个可读写的文件描述符，隧道语义完全由用户态代码解释，内核并不参与。

双通道是第二个必须建立的概念。控制通道负责 TLS 握手、证书链校验、密钥协商、向客户端推送地址与路由参数，以及周期性重协商，它要求可靠、有序、可重传；数据通道负责承载真正的业务报文，追求低开销与低时延，用对称密钥做加密与完整性保护。二者复用同一条传输连接，靠通道标识区分，而不是各开一条物理连接；这种设计既节省了端口与 NAT 映射，也让握手与业务可以独立演进（原理见 06-xx）。把这条分界记住，日志里交织的输出就有了读法。

服务端多路复用是第三个概念。在服务端模式下，进程并不为每个客户端各开一个监听套接字，而是用单个链路套接字接收所有客户端的报文，再按来源地址与会话标识查出对应的客户端实例，把报文派发给该实例的状态机；实例表同时承载地址池分配、每客户端路由与状态维护（原理见 06-xx、模块见 07-xx）。这也是为什么服务端能维持大量并发隧道，却只在系统上留下一个监听端口。

还有一个贯穿源码的组织方式值得点名：全局上下文按生命周期被分成若干层次，常见说法是 c0、c1、c2 三层，分别对应一次性初始化结果、连接级状态与每次重连可重建的运行状态。本篇只点名这一分层思路，`struct context` 位于 `src/openvpn/openvpn.h`，具体层次字段一律见（字段见 05-xx）。理解「哪些状态跨重连保留、哪些每次重建」，对读懂初始化与重协商行为很有帮助（原理见 06-xx）。

为便于选型，先把 tun 与 tap 的差异列成下表。

| 维度 | tun 三层 | tap 二层 |
|---|---|---|
| 读写单元 | 原始 IP 报文 | 完整以太帧 |
| 工作模式 | 路由模式，依赖地址与路由下发 | 桥接模式，可与物理网卡桥接 |
| 广播与地址解析 | 不承载二层广播 | 承载广播与地址解析报文 |
| 开销与复杂度 | 开销小、拓扑简单，优先选用 | 开销较大，易引入环路与广播域 |
| 典型场景 | 远程接入与站点路由互连 | 需要二层邻接或非 IP 协议 |

### 4. 关键流程与调用链

本节只讲分层视角下的「从哪到哪」，逐行状态机与封装细节请转（原理见 06-xx）。把出站与入站两条方向对照着看，最容易建立整体感。出站方向：应用产生的普通 IP 报文经内核路由进入 tun 设备，进程从设备描述符读到原始报文，事件循环按通道语义交给数据通道完成加密与封装，再经链路套接字发往对端。入站方向：套接字收到密文，校验与解密后写回 tun 设备，内核按普通 IP 包继续转发。控制通道的握手、参数推送与重协商则与业务数据并行，在同一条连接上以通道标识区分（原理见 06-xx）。

事件循环是这套分派的枢纽。`src/openvpn/forward.c` 在一个线程里用 I/O 多路复用同时等待虚拟设备与链路套接字，哪一侧可读就先处理哪一侧，再按报文属于控制还是数据分派到 `src/openvpn/ssl.c` 或 `src/openvpn/crypto.c` 相关路径。单线程模型意味着任何阻塞环节，无论是慢速脚本钩子、插件回调还是一次耗时加解密，都可能影响同一进程里的其它客户端；这条推论是服务端容量评估的基本前提（原理见 06-xx）。

服务端形态多一层调度：`src/openvpn/multi.c` 收到报文后，按来源地址与会话标识在实例表里查出对应客户端，再派发给该实例状态机；实例的创建、地址分配、路由推送与销毁也都由这一层协调（原理见 06-xx、模块见 07-xx）。点对点形态没有这层调度，其余链路基本一致，这正是「服务端与客户端共用大部分代码」的原因。

引入 ovpn-dco 之后要补一条分界：数据通道可卸载到内核模块，控制通道与密钥协商仍留在用户态，于是「控制面在用户态、数据面可选内核态」成为更准确的描述；加载条件、能力协商与用户态回退都有专门机制（原理见 06-xx、模块见 07-xx）。在分层图上，这相当于把数据通道那一支从用户态核心里部分移出，而控制通道、事件循环与服务端调度仍在原处。

为把双通道讲透，下表把两条逻辑通道逐项对照，配合分层图一起看更有效。

| 维度 | 控制通道 | 数据通道 |
|---|---|---|
| 主要职责 | 握手、认证、密钥与参数推送 | 承载加密后的业务报文 |
| 传输要求 | 可靠、有序、可重传 | 低开销、低时延 |
| 保护方式 | TLS 记录与证书体系 | 对称加密与完整性校验 |
| 关联源码 | ssl.c 与 ssl_common.h | crypto.c 与 buffer.c |
| 卸载后归属 | 仍留在用户态 | 可卸载到内核模块 |

### 5. 配置/命令/代码实例

概述层只给最小示例，不重列指令全集，完整指令见 04-xx。下面是一组与本篇主题直接相关的服务端侧最小配置片段，体现设备、拓扑、多客户端互通与保活几件事；具体指令语义与版本差异需对照（指令见 04-xx）核验。

```conf
dev tun
topology subnet
server 10.8.0.0 255.255.255.0
client-to-client
keepalive 10 120
```

`dev tun` 选三层设备，`topology subnet` 指定地址分配形态，`server` 展开地址池与服务端模式相关默认行为，`client-to-client` 允许客户端之间经服务端内部转发，`keepalive` 设定保活节奏。它只用来说明「一个设备加一条服务端地址池就能撑起多客户端复用」；证书、控制通道保护、每客户端路由与日志级别等一概留给（完整指令见 04-xx），此处不展开。

验证分层最直观的办法，是同时观察虚拟三层设备与监听套接字。下面给出命令与典型输出；以下为示例输出，具体格式需对照实际版本核验。

```bash
ip addr show tun0
ss -lunp
```

```text
3: tun0: <POINTOPOINT,MULTICAST,NOARP,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UNKNOWN group default qlen 500
    link/none
    inet 10.8.0.1 peer 10.8.0.2/32 scope global tun0
       valid_lft forever preferred_lft forever
Netid State Recv-Q Send-Q Local Address:Port Peer Address:Port
udp UNCONN 0 0 0.0.0.0:1194 0.0.0.0:*
```

第一段输出印证了设备层：`POINTOPOINT` 与 `NOARP`、`link/none` 说明这是一个三层的点对点虚拟接口，没有二层地址解析，正是 tun 而非 tap 的典型形态；`inet 10.8.0.1 peer 10.8.0.2/32` 体现服务端把地址与对端下发到了这张接口上，内核因此确实看见一个由用户态进程创建的虚拟设备（模块见 07-xx、原理见 06-xx）。`mtu 1500` 是设备 MTU，隧道封装还要在这之上扣除额外头部，实际可用载荷更小，长度推导见（原理见 06-xx）。第二段输出印证传输层与复用：`ss -lunp` 里只出现一条 UDP 1194 的监听记录，说明服务端用单个套接字承接所有客户端，而不是每客户端一个端口，这正是 `src/openvpn/multi.c` 多路复用的外在表现（原理见 06-xx、模块见 07-xx）。判读异常时，若接口缺少 UP 与 LOWER_UP，多半是设备未起或配置未下发；若没有 inet 地址，指向地址池与 ifconfig 相关配置；若端口未监听，指向进程未起、地址占用或权限不足；若意外出现多条监听，则应回查是否起了多实例。输出里的接口名、地址、端口、队列与状态字段都随环境变化，需对照实际版本核验。

### 6. 注意事项、陷阱与最佳实践

设备选型是第一道关。优先 tun 三层路由模式，只有确需二层邻接、广播或非 IP 协议时才选 tap；tap 桥接会把广播域与生成树语义带进隧道，环路与广播风暴的排查成本明显更高（模块见 07-xx）。选定设备后再规划地址与路由，顺序反了容易导致「能连上但不通网段」。

单线程事件循环必须时刻记在心里。一个慢客户端、一个阻塞的脚本钩子或插件回调，都可能拖累同一进程里的其它客户端；服务端容量评估不能只看带宽，还要看每客户端的控制面开销与钩子耗时（原理见 06-xx、模块见 07-xx）。这也是为什么高并发场景要谨慎使用同步阻塞的外部认证。

双通道共享同一连接带来 MTU 与分片边界问题。封装头部占用有效载荷，握手报文与业务报文在同一链路上竞争，路径 MTU 处理不当会表现为小包正常、大业务报文卡死；推导见（原理见 06-xx），相关指令见（指令见 04-xx），按现象反查见 08-xx。不要一上来就调大设备 MTU，先把封装开销算清。

服务端多路复用有几类专属风险：允许多客户端使用同一证书会带来地址与路由冲突，实例表里的每客户端配置与路由推送必须配合实例标识，客户端之间互通的开关也要按安全边界评估；这些能力的用法与风险属于（模块见 07-xx），对应指令见（完整指令见 04-xx）。此外，进程启动初期需要特权打开设备、配置地址与下发路由，随后应尽快降权运行，相关指令见（指令见 04-xx）。

启用 ovpn-dco 之后还要留意路径变化：数据面卸载到内核后，部分 tun 读写不再经过用户态，抓包与排障的观察点随之改变，能力协商失败时要能退回用户态路径（原理见 06-xx、模块见 07-xx）。容器与云环境则需确认进程能访问 tun 设备并具备相应能力，部署细节见 03-xx。

排障顺序同样有章法：先确认版本与编译形态，再看日志是否出现初始化完成标志，然后才分层定位到设备层、控制通道、数据通道或实例调度，工具与流程分别见（指令见 04-xx）与 08-xx。把这些收敛成习惯清单，就是「先跑通最小拓扑、再逐层加配置、每次变更留回滚、容量结论必须有实测」四句话，它们能把绝大多数架构类故障挡在早期。

### 7. 小结与延伸阅读

把三条主线各自收束一句：tun 与 tap 决定进程从内核拿到 IP 报文还是以太帧，进而决定路由还是桥接；控制通道与数据通道在同一条连接上以通道标识分派，一个管握手与密钥、一个管业务报文；服务端多路复用让单套接字凭借实例表服务大量客户端。三层叠加，就是 `src/openvpn/` 的分层骨架，也是 01-01 那句「用户态进程加双通道」的完全展开。

## 01-04 版本演进、社区生态与商业版边界

### 1. 背景与动机

写到本册最后一篇，需要把前面三篇建立的分层地图放进时间与产品两个维度里看。技术资料最容易被时间侵蚀的部分恰恰是版本：某个指令在这一版可用、在下一版被改名或废弃，某个加密套件从默认变成可协商，某个压缩开关因为安全考量被收紧，某个数据面能力从用户态挪到内核。读者若拿着一篇旧博客里的配置去套新版本，往往不是「配错了」，而是「配的是另一个时代的软件」。反过来，把新版本才有的能力写进旧版本文档，同样会误导部署。

比版本更容易出错的是产品边界。社区版与商业版共享一个名字，却不是同一套东西：前者是 `src/openvpn/` 下的开源守护程序，后者是带管理界面、集群与商业授权的产品。若把商业版的集中管理、目录服务内置集成或许可体系当成社区版自带能力，选型、预算、合规文档乃至整套运维方案都会从根上跑偏；若把社区版通过脚本与插件「组合」出来的外部能力，误当成内置产品功能，又会在交付时兑现不了承诺。本套资料从总纲起就把这条边界列为评审红线，本篇负责把它逐项钉清。

因此本篇有四个目标：给出社区版主线演进的段位而不是臆造的发布日期；说明几个关键能力（加密套件协商、控制通道保护、数据面卸载）在架构上的意义；勾勒社区生态由哪些部分构成；把社区版与商业版 Access Server 的能力边界列成可核对的表。全篇坚持一条硬规矩——凡不确定的版本号、字段名、函数签名、发布日期与维护策略，一律写「需对照实际版本核验」并给出可定位的 `src/openvpn/` 源码或头文件路径，绝不凭印象编造。

版本基准沿用全册口径：稳定分支 2.6.x、开发分支 2.7 master，以及配套的内核数据通道卸载模块 ovpn-dco。这里的「x」不是省略，而是刻意不填写具体小版本号：小版本号、发布时间、长期支持策略与各分支维护窗口都会随发行节奏变化，必须以官方发布页与 `src/openvpn/` 实际源码为准。本篇讲的是「怎么读演进、怎么自己核验」，而不是替读者记一串迟早过期的数字。

阅读坐标仍然不变。本篇属概述层：结构体只点名并给真实源码路径（字段见 05-xx），配置只给最小示例（完整指令见 04-xx），机制只讲「做什么」（原理见 06-xx），模块能力只作索引（模块见 07-xx），部署与升级回归分别见 03-xx 与 08-xx。凡是涉及指令全集、字段表、状态机或模块清单的内容，本篇一概不重列。

### 2. 核心概念

先把版本序列说清。社区版主线通常按稳定分支与开发分支来理解：2.6.x 是本套资料主要依据的稳定分支，2.7 master 是持续演进的开发分支，ovpn-dco 是与之配套、可把数据通道卸载到内核的独立内核模块，三者不在同一棵源码树里。中间还经过 2.4、2.5 等主线阶段，大纲把这条主线概括为「2.4 到 2.6」。本篇只把这些当作段位标签，用来定位「某一类能力大致属于哪个阶段」，不把它们当作特性的精确引入版本；任何「某特性从某小版本开始」的说法都需对照实际版本核验。

再看几个反复被提到的能力在架构上的意义，而不是它们的发布编号。加密套件协商，指的是控制通道握手期把数据通道可用的加密算法在两端之间协商确定，取代过去把单一算法写死在两侧配置里的做法；它让升级与算法轮换不必同时改所有客户端（原理见 06-xx）。控制通道保护，指的是在 TLS 握手之外再给控制报文加一层认证或加密包裹，降低握手面暴露与未授权探测的风险，相关能力通常以 tls-auth、tls-crypt 一类名字出现，具体指令名与可用选项见（指令见 04-xx）并需对照实际版本核验（模块见 07-xx）。带认证的加密模式，则把机密性与完整性合并在同一算法里，是现代数据通道的常见形态（原理见 06-xx）。

压缩相关的安全变更也值得单独记：压缩曾被用来提升低速链路的吞吐，后来因其与加密流量的交互会引入可被利用的侧信道，相关能力与默认值在不同版本里被反复调整。因此「照抄旧配置里的压缩开关」是升级时最常见的踩坑点之一，指令语义与迁移清单分别见（指令见 04-xx）与 08-xx。数据通道卸载则是另一条线：把成熟的对称加解密搬到内核模块去做，控制通道与密钥协商仍留在用户态，于是出现「控制面在用户态、数据面可选内核态」的分界（原理见 06-xx、模块见 07-xx）。

社区生态由几类角色共同构成：社区版源码仓库本身（`src/openvpn/` 是核心，`src/plugins/`、`sample/sample-config-files/`、`doc/` 分别提供插件示例、示例配置与手册源）；用于搭建公钥基础设施的 easy-rsa 一类独立工具；第三方客户端与发行版打包；社区交流与文档渠道；以及前面提到的 ovpn-dco 内核模块。这些组件的入口、版本与相互配套关系都可能变化，具体项目归属、仓库地址与维护入口需对照官方资料核验，本套资料只保证社区版 `src/openvpn/` 范围内的路径准确。

商业产品线要单独划出来。Access Server 是商业产品，通常带有 Web 管理控制台、集中用户与组管理、目录服务与多因素认证集成、产品化的高可用与集群、客户端安装包与自助门户，以及商业授权与订阅体系；此外还有商业客户端与云端服务等产品形态。它们都不属于社区版 `src/openvpn/`。这里要立一条精确的表述：社区版提供的是「机制与钩子」——证书体系、脚本钩子、插件接口与管理接口（模块见 07-xx、指令见 04-xx），管理员可以借此配合外部组件实现认证与监控；商业版提供的是「产品化集成」——把这些能力打包成开箱即用的界面与服务。二者不是「功能多少」的量的差别，而是产品形态与交付方式的差别。

社区版与商业版的能力边界是本篇最需要钉清的一张表，逐项对照如下；右列均为商业版能力，绝不可写成社区版自带。

| 能力项 | 社区版 src/openvpn/ | Access Server 商业版 |
|---|---|---|
| 产品形态 | 开源守护程序、配置文件与命令行 | 商业产品，含安装与许可体系 |
| 管理界面 | 命令行、配置文件与管理接口 | Web 管理控制台 |
| 用户与认证 | 证书、脚本钩子、插件与管理接口可扩展 | 内置用户组、目录服务与多因素集成 |
| 高可用 | 需借助外部组件自行搭建 | 产品化集群与故障转移 |
| 客户端分发 | 由管理员自行分发配置文件 | 产品化安装包与自助门户 |

### 3. 关键数据结构与源码位置

版本差异最终都会落到源码上，因此本节给出「去哪里核对」的坐标，不展开任何字段（字段见 05-xx），也不重列指令（完整指令见 04-xx）。把可定位的路径记牢，比记住一串版本号更可靠。

指令与默认值的变化集中在 `src/openvpn/options.c` 与 `src/openvpn/options.h`：一条指令是否被接受、默认值是什么、与其他指令如何互斥，都由解析层决定（指令见 04-xx）。控制通道与加密协商相关的状态在 `src/openvpn/ssl.c` 与 `src/openvpn/ssl_common.h`（头文件位置需对照实际版本核验），数据通道的加密后端在 `src/openvpn/crypto.c`，长度与帧推导在 `src/openvpn/buffer.h` 与 `src/openvpn/mtu.h`，服务端实例调度在 `src/openvpn/multi.c` 与 `src/openvpn/multi.h`。若构建纳入数据面卸载，相关实现位于 `src/openvpn/` 下以 DCO 命名的源文件，具体文件名与函数签名需对照实际版本核验；构建期开关则通常由仓库根部的配置脚本控制，具体文件名需核验。变更记录与发布说明一般位于 `doc/` 下，具体文件名同样需对照实际版本核验。

点名几个对象但不展开：`struct context`（`src/openvpn/openvpn.h`）、`struct options`（`src/openvpn/options.h`）、`struct tls_multi` 与 `key_state`（`src/openvpn/ssl_common.h`）、`struct multi_context`（`src/openvpn/multi.h`）、`link_socket` 相关对象（`src/openvpn/socket.h`）。它们的字段集合在不同版本间会有增删，因此更要坚持「字段见 05-xx」，由字段权威册按实际源码维护，而不是在概述层抄一份迟早过期的清单。

由此可以给出一条最实用的核验方法：想知道某个能力在当前二进制里是否存在，先跑版本输出看编译期特性标签，再回到 `src/openvpn/` 找对应文件与头文件确认，最后才查官方发布页或变更记录确认它属于哪个阶段。三个来源互相印证，任何单一来源都不该被当成结论。版本后缀里的具体数字、库版本、版权年份与维护窗口都随发行版变化，必须对照实际版本核验。

机制层面的能力协商、重协商与卸载回退请转（原理见 06-xx），模块层面的控制通道保护、卸载模块与插件接口请转（模块见 07-xx），指令与命令的精确名称请转（指令见 04-xx）。本篇只负责把「版本差异落在哪些文件」这层坐标交代清楚。

### 4. 关键流程与调用链

本节只讲版本演进在「做什么」层面的差别，不逐行展开状态机，具体实现请转（原理见 06-xx）。把三条线并排看，就能理解为什么升级会改变运行行为。

第一条是加密套件协商。过去常见做法是把单一数据通道算法写死在两端配置里，任一侧改动都会导致不匹配；协商式做法则在控制通道握手期把两端都支持的算法列表交换并选定，后续轮换与升级可以分批进行。由此带来的典型升级现象是：旧客户端与新服务端能否连上，取决于双方列表是否有交集，而不是某一侧写得对不对（原理见 06-xx、指令见 04-xx）。

第二条是控制通道保护。在 TLS 握手之外再加一层认证或加密包裹，改变的是握手报文进入进程之前的校验路径：未通过包裹校验的报文会被更早丢弃。升级时若两端对是否启用、用哪一层包裹理解不一致，握手会停在很早的阶段，日志里往往看不到明确的证书错误（原理见 06-xx、模块见 07-xx）。

第三条是数据面卸载。启用 ovpn-dco 后，对称加解密与部分报文搬运移到内核模块，控制通道、证书校验、密钥协商、参数推送与服务端实例调度仍留在用户态；能力协商失败时要能退回纯用户态路径。于是同样一份配置，在卸载启用与未启用两种构建下，数据路径不同、抓包观察点不同、性能特征也不同（原理见 06-xx、模块见 07-xx）。

把三条线叠起来看，升级之所以会「断流」，根因通常不在网络，而在「两端对能力集合的理解不再一致」：套件列表没有交集、控制通道保护参数不匹配、压缩与加密的组合被新版本拒绝、卸载能力协商后回退路径未验证。定位这类问题的顺序应是先确认两端版本与构建形态，再看控制通道是否握手成功，最后才看数据通道；回归清单见 08-xx。

### 5. 配置/命令/代码实例

概述层只给最小示例，不重列指令全集，完整指令见 04-xx。下面是一段与版本演进直接相关的最小配置片段，用来体现「把可用算法交给协商」这一思路；指令名、可用值与分隔写法需对照（指令见 04-xx）与实际版本核验。

```conf
data-ciphers AES-256-GCM:AES-128-GCM
auth SHA256
```

`data-ciphers` 给出本端可接受的数据通道算法列表，由控制通道握手期与对端协商；`auth` 与控制通道的完整性算法相关。旧版本里表达同类意图的指令名可能不同，把旧配置直接搬过来往往就是升级失败的起点，逐项差异见（指令见 04-xx）与 08-xx。此处只用来说明「新形态把选择权交给协商」，不展开任何指令全集。

确认当前构建究竟支持哪些算法，是升级前最省事的一步。下面给出命令与典型输出；以下为示例输出，具体格式需对照实际版本核验。

```bash
openvpn --show-ciphers
```

```text
AES-256-CBC  (256 bit key, 128 bit block)
AES-192-CBC  (192 bit key, 128 bit block)
AES-128-CBC  (128 bit key, 128 bit block)
AES-256-GCM  (256 bit key, 128 bit block)
AES-128-GCM  (128 bit key, 128 bit block)
CHACHA20-POLY1305  (256 bit key, stream cipher)
```

这个列表反映当前二进制链接的加密后端实际提供的算法，而不是文档里「理论上应该有的」算法。判读时先看成组出现的算法族：带 GCM 的一类属于带认证的加密模式，是协商式数据通道的常见选择；只带 CBC 的一类属于传统模式，通常需要单独的完整性算法配合；若列表里完全没有带认证的加密模式，说明构建偏旧或加密后端受限，不能直接套用新版本文档里的协商配置。再看长度与括注，它们用于判断算法强度与分组特征，具体括注格式随版本与后端变化，必须对照实际版本核验。最关键的判读结论是：这里列出的只是「可用」，是否与对端协商成功还要看控制通道握手结果（原理见 06-xx）；命令输出正常不等于隧道可用。异常特征包括列表为空、只出现极少数算法、或输出报错指向加密后端未初始化，这些都要求回到版本输出与 `src/openvpn/crypto.c` 相关构建配置核查。

从源码侧核对版本，同样应该可复现。下面两条命令用于查看当前检出点相对标签的描述以及仓库里可用的标签；标签命名规则、发布页与变更记录需对照实际版本核验，不要凭记忆填写版本号。

```bash
git -C openvpn/ describe --tags --always
git -C openvpn/ tag --list
```

第一条给出当前源码检出点相对最近标签的描述，第二条列出仓库中的标签集合。二者结合版本输出，就能把「我到底在跑哪一版」这件事钉死，而不是停留在「大概是某个系列」的猜测上；这一步在多人协作与跨环境排障时尤其重要。

### 6. 注意事项、陷阱与最佳实践

版本陷阱里最常见的是照抄旧资料。把旧博客里的单一算法指令、压缩开关或已被调整的默认行为直接搬进新版本，轻则告警，重则两端协商失败；反过来把新版本才有的指令写进旧版本，解析层会直接拒绝。正确做法是按（指令见 04-xx）逐项核对当前版本可用的指令与取值，并按 08-xx 的迁移清单做回归，而不是凭经验改配置。

第二条硬规矩是不编造。版本号、发布日期、长期支持策略、某个特性的精确引入版本、函数名与字段名，凡本套资料无法从 `src/openvpn/` 实际源码确认的，一律写「需对照实际版本核验」并给出可定位路径。本篇全篇不给出任何具体小版本号、日期或维护窗口，正是这条规矩的体现；读者也应以同样标准审视外部资料。

商业边界陷阱必须反复强调。不要把 Web 控制台、集群与故障转移、内置目录服务与多因素集成、许可与订阅写成社区版能力；不要把 Access Server 的部署文档套到 `src/openvpn/` 上；也不要把社区版通过脚本钩子、插件与管理接口「组合」出来的外部认证，宣传成内置产品功能。准确说法是：社区版给机制，商业版给产品（模块见 07-xx、指令见 04-xx）。许可与合规同样要分清：社区版遵循其开源许可，具体条款以仓库 LICENSE 为准并需对照实际版本核验；商业版需要商业授权，两者的合规要求不可混用。

卸载与生态配套也有坑。ovpn-dco 与用户态版本之间存在配套关系，能力协商失败要能退回用户态路径；插件接口、客户端版本、公钥基础设施工具与打包版本同样可能随主线变化，跨版本混用前应逐一核验（原理见 06-xx、模块见 07-xx）。把升级前该做的核对项汇总成下表。

| 检查项 | 说明 | 关联权威册 |
|---|---|---|
| 登记版本输出 | 记录版本与编译期能力标签 | 指令见 04-xx |
| 核对指令更名与废弃 | 加密与压缩相关指令逐项核对 | 指令见 04-xx、迁移见 08-xx |
| 验证两端兼容 | 确认套件列表存在交集 | 原理见 06-xx |
| 回归卸载路径 | 启用与回退两种情况都测 | 原理见 06-xx、模块见 07-xx |
| 保留回滚配置 | 变更前备份可运行的最小配置 | 运维见 08-xx |

落到最佳实践，可归纳为四句话：锁定并登记版本与构建形态；升级先在测试环境用最小拓扑跑通再灰度；每次变更保留可回滚配置；任何性能或能力结论都标注它对应的版本与口径。做到了这些，版本演进就不再是排障时的黑盒，而是可追溯、可复盘的工程变量。

### 7. 小结与延伸阅读
