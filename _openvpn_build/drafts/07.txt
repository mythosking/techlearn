# OpenVPN 技术资料 · 07 模块与特性介绍

## 07-01 tun/tap 设备抽象与平台驱动

### 1. 背景与动机

要理解 OpenVPN 为什么会专门设计一个设备抽象模块，必须先回到虚拟专用网最朴素的工程问题：一个运行在用户态的普通进程，凭什么能够「接管」一台主机发出的网络报文，又凭什么把远端发来的报文「送回」本机网络栈。OpenVPN 社区版本质上是一个单进程、用户态的 SSL/TLS VPN 程序，它没有内核模块身份，也不直接改写操作系统的协议栈与路由表，因此它必须借助操作系统提供的一个「虚拟网卡」作为内外层报文的交界点。应用程序照常把报文交给内核路由，内核按路由表把目的地指向这个虚拟网卡，虚拟网卡并不真正把比特流送到物理线路，而是把整段报文排队交给打开了它的用户态进程；进程完成加密、封装、完整性保护之后，再通过真实的 UDP 或 TCP 套接字把密文发往对端。反向路径同理：进程从链路套接字收到密文，解密还原出原始报文，再写回虚拟网卡，内核就像收到一张真实网卡送来的包一样继续处理。这个交界点，就是 tun 与 tap 两类虚拟设备。

问题在于，几乎每一个操作系统暴露虚拟网卡的方式都不一样。Linux 走的是字符设备加大规模 ioctl 的路子，Windows 需要安装内核态的 NDIS 驱动并依赖服务提权，macOS 用的是内核控制套接字而不是可读写的设备节点，FreeBSD 与 Solaris 又各有自己的克隆设备与命名约定。设备名字怎么起、地址怎么配、MTU 怎么设、读写出来的字节流前面有没有一段协议信息头、权限要不要管理员，这些细节如果不加收敛地散落在转发主循环里，代码将迅速变成一堆互相嵌套的条件编译，既无法移植也无法审计。于是 `src/openvpn/tun.c` 承担起一个很明确的职责：向上层提供一套稳定的「打开、关闭、读取、写入、配置地址、设置 MTU」接口，把全部平台差异压到文件内部按宏区分的分支里。上层事件循环只认一个 tun 文件描述符，完全不需要知道脚下跑的是 Linux 还是 Windows。

除了跨平台差异，tun 与 tap 在数据模型上的根本分野，是驱动这套抽象存在的第二个动机。tun 工作在第三层，读写的是不带以太网首部的裸 IP 报文，内核把它当成一条点到点的三层链路，天然适配路由模式、网段划分与 `topology` 拓扑；tap 工作在第二层，读写的是完整的以太网帧，包含源目的 MAC、类型字段以及 ARP、广播、组播，因而可以把远端的多个主机桥接进同一个二层广播域。二者并不是同一个功能的两种开关，而是两种截然不同的组网模型，选错之后往往要到部署后期、出现广播风暴或地址池冲突时才会暴露，代价很高。本篇作为模块功能与组网的权威源，重点正是把这种选型判断讲清楚（模块见 07-01）。

近年 `ovpn-dco` 内核数据通道卸载的引入，又给设备抽象层增加了一层新的责任：当条件满足时，加密后的数据通道可以下沉到内核，用户态只保留控制通道与密钥协商。但这并没有改变「用户态通过一组受控接口操作虚拟设备」这一基本边界，只是把接口背后的执行者从进程搬到了内核模块。DCO 的启用条件、能力协商与回退属于机制范畴，本篇只点明它与设备抽象层的挂接关系，深入的卸载流程与状态迁移请转到 06-12（原理见 06-12）。同样，报文在 tun 与 socket 之间如何被封装、封装时的内外层包头怎么叠加，属于数据通道机制，见 06-03（原理见 06-03）；本篇始终停留在「这个模块能做什么、有哪些平台实现、该怎么选」的层面。

### 2. 核心概念

tun 与 tap 是理解本模块的第一组概念。tun 是三层设备，内核交给进程的是一个 IP 包，进程写回的也必须是一个合法 IP 包；因为不含二层首部，它不承载 ARP，不做 MAC 学习，广播报文只能以受限形式出现，整个隧道表现为一条点到点或点到多点的路由链路。服务端通常用 `topology subnet` 配合地址池给每个客户端分配一个隧道内地址，再靠路由推送把后端网段引到隧道里，扩展性好、开销低，是绝大多数远程接入场景的默认选择。tap 是二层设备，读写以太帧，意味着 ARP 请求、DHCP 广播、NetBIOS、组播发现都会穿过隧道；好处是非 IP 协议与依赖二层的老应用可以原样透传，坏处是广播域被拉大、地址池与桥接配置复杂、无用流量占用带宽，因此只在确有二层互通需求时才用。

第二组概念是平台驱动。Linux 上对应的是 universal TUN/TAP 驱动，进程打开 `/dev/net/tun` 这个字符设备，随后用 `TUNSETIFF` ioctl 声明自己要建的是 `IFF_TUN` 还是 `IFF_TAP`，并可附带 `IFF_NO_PI` 决定是否在报文前保留四字节的协议信息头；设备名可由内核自动分配，也可通过 `dev-node` 固定，配合 `ip tuntap` 还能建出持久化设备。Windows 的情况最复杂：历史上依赖 TAP-Windows6，这是一个 NDIS 6 迷你端口驱动，以独立仓库 `tap-windows6` 维护，安装后在系统里呈现为一块可配置 TCP/IP 属性的虚拟网卡；较新的 2.6 系列开始支持 wintun，这是由 WireGuard 项目提供的高性能 NDIS 驱动，OpenVPN 通过动态加载其 DLL 使用，`--windows-driver` 可在这两者之间选择，具体取值与可用版本需对照实际版本核验。由于普通用户没有权限创建网络设备，Windows 上还有 `src/openvpnserv/` 里的交互式服务，负责替非管理员的 OpenVPN 进程完成设备打开与网络配置。macOS 没有 `/dev/tun` 节点，走的是 utun 内核控制套接字，设备名由内核生成、通常不可由用户指定；BSD 家族则提供 `if_tun` 与 `if_tap` 克隆设备。以上平台行为差异建议以 `src/openvpn/tun.c` 的条件编译分支为准逐项核验。

第三组概念是抽象接口与网络配置后端的分工。`tun.c` 里真正对上暴露的是一组围绕设备生命周期的函数，负责打开、读写、关闭与参数下发，函数名与签名需对照实际版本核验；而设备建好之后「给谁配地址、加哪条路由、设多大 MTU」则交给另一组后端：2.6 系列引入了基于 netlink 的 `networking_sitnl.c`，也保留了调用外部 `ip` 命令的 `networking_iproute2.c`，路由相关的公共逻辑集中在 `route.c`。把设备操作与网络配置拆开，是为了让同一套隧道逻辑既能跑在自带 netlink 的现代内核上，也能跑在只有 iproute2 工具链的精简环境里。此外 `dev-type`、`dev-node`、`ifconfig`、`tun-mtu` 这类指令是把上述能力暴露给运维的入口，本篇第 5 节只列最典型几条，完整指令族见 04-02（指令见 04-02）。

最后必须点明商业版边界。以上设备抽象、平台驱动适配与 wintun 支持都是社区版 `src/openvpn/` 内置能力，与商业版 Access Server 无关；资料集 01-04 已明确社区版只覆盖 `src/openvpn/` 主线，不会把集群、Web 管理界面等商业特性写成本模块功能。tun 与 tap 的能力差异与选型判据可结合图 07-01-02 一起看。

### 3. 关键数据结构与源码位置

本模块的核心对象是 `struct tuntap`，它把设备类型、文件描述符、设备名、MTU、平台私有句柄以及读写状态收敛到一处，供上层统一持有。按本套资料的去重约定，结构体逐字段定义统一由 05 册给出，本篇不重列字段表，只点名并给出可定位路径（字段见 05-02、字段见 05-07）。理解本模块所需的不是字段清单，而是「哪些源文件各管哪块能力」的地图，读者据此可以按图索骥去读源码。

下表按源文件列出本模块的能力分布，均为社区版 `src/openvpn/` 与相关目录下的真实位置，个别在 2.6 与 2.7(master) 之间可能增删的文件已标注需核验。

| 源文件 | 负责能力 | 平台与备注 |
|---|---|---|
| `src/openvpn/tun.c` | 设备打开关闭读写与 ioctl 封装 | 平台差异集中在条件编译分支 |
| `src/openvpn/tun.h` | `tuntap` 结构与抽象接口声明 | 字段见 05-xx |
| `src/openvpn/networking_sitnl.c` | 基于 netlink 的地址路由配置 | 现代 Linux 首选，需核验版本 |
| `src/openvpn/networking_iproute2.c` | 调用外部 `ip` 命令配置 | 精简环境后端，需核验版本 |
| `src/openvpn/route.c` | 路由增删与拓扑公共逻辑 | 与 07-09 路由模块衔接 |
| `src/openvpn/dco.c` | 数据通道卸载挂接 | 原理见 06-12 |
| `src/openvpnserv/` | Windows 交互式服务与提权 | 非管理员启动设备时使用 |

| `tap-windows6` 独立仓库 | NDIS 6 迷你端口驱动 | 非主仓库内，驱动单独安装 |
| wintun 驱动 DLL | 高性能 Windows 数据通道 | 由 WireGuard 项目提供 |

平台差异同样值得单独成表，因为它直接决定部署形态与权限模型。下表把主流平台的关键差别并列，选型时可先据此圈定可行范围，再回到正文第 6 节看陷阱。

| 平台 | 设备入口 | 命名可控性 | 权限要点 |
|---|---|---|---|
| Linux | `/dev/net/tun` 加 ioctl | 可用 `dev-node` 固定 | 需 CAP_NET_ADMIN 能力 |
| Windows wintun | 动态加载驱动 DLL | 由驱动分配 | 依赖 `src/openvpnserv/` 提权 |

需要再次强调，本节只做模块能力地图，不是字段手册也不是机制剖析：结构体里每个成员的类型、读写时机与生命周期见 05 册，报文经由 tun 进入加密封装、再交给 link socket 的完整调用链见 06-03（原理见 06-03），设备初始化挂到启动主流程的位置见 06-01（原理见 06-01）。把三层内容分开，是本套资料避免重复的关键约定。

### 4. 关键流程与调用链

从模块协作的角度看，设备抽象层在一次连接生命周期里大致经历五步，这里只描述「各模块之间交接什么」，不展开每一步内部的状态机与逐行实现。第一步，启动流程解析配置得到设备类型、设备名、拓扑与 MTU 等参数，这些解析结果挂在 options 相关对象上（字段见 05-03）。第二步，初始化代码调用设备抽象接口，由 `tun.c` 根据当前平台进入对应分支打开虚拟设备：Linux 分支走 `/dev/net/tun` 加 `TUNSETIFF`，Windows 分支在必要时先经 `src/openvpnserv/` 提权再打开 wintun 或 TAP-Windows6 适配器，macOS 与 BSD 分支走各自的控制套接字或克隆设备。第三步，设备建好后由网络配置后端下发地址、掩码、MTU 以及首条路由，并触发 up 脚本钩子，让运维可以插入自定义网络准备动作。第四步，设备文件描述符被登记进事件循环的可读集合，此后凡内核送来的原始报文都由转发逻辑读取，凡解密后的对端报文都写回该描述符，这一步与事件循环、帧封装的衔接属于机制，见 06-02 与 06-03（原理见 06-02、原理见 06-03）。第五步，连接结束或进程退出时按逆序撤销路由、关闭设备、释放平台私有句柄。

### 5. 配置/命令/代码实例

按去重约定，本篇只列本模块最典型的几条指令做演示，其余全部交给 04 册（完整指令族见 04-02）。下面这段配置展示的是 Linux 路由模式下把设备固定命名、指定三层类型并配好隧道地址的最小片段，能直观看出设备抽象层对外暴露了哪些旋钮。

```conf
dev tun
dev-type tun
dev-node ovpn-tun0
topology subnet
ifconfig 10.8.0.1 255.255.255.0
```

设备建好之后，运维最常做的验证是查看内核侧是否真的出现了一块符合预期的虚拟网卡。下面给出查询命令，随后是一段典型输出。示例输出，具体格式需对照实际版本核验，不同内核与 iproute2 版本的字段顺序、标志位命名会有差异。

```bash
ip -details link show dev ovpn-tun0
```

```text
7: ovpn-tun0: <POINTOPOINT,MULTICAST,NOARP,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UNKNOWN mode DEFAULT group default qlen 500
    link/none  promiscuity 0 minmtu 68 maxmtu 65535
    tun type tun pi off vnet_hdr off persist off
    inet 10.8.0.1/24 scope global ovpn-tun0
       valid_lft forever preferred_lft forever
```

下面对这段输出逐行判读。首行的 `POINTOPOINT` 与 `NOARP` 是三层 tun 设备的典型标志：前者说明它是一条点到点链路而非广播型以太网，后者说明内核不会在这块设备上发起 ARP 解析，这与 tun 不承载二层帧的语义完全吻合；如果这里意外出现 `BROADCAST` 且缺少 `NOARP`，往往意味着建成了 tap 或 `dev-type` 写错，需要回头核对配置。`UP,LOWER_UP` 表示管理状态与物理层状态都已就绪，只有 `UP` 而无 `LOWER_UP` 通常说明设备未被进程正确打开。`mtu 1500` 是隧道内 MTU，叠加外层封装后很可能超出物理链路 MTU，因此实际部署常配合 `tun-mtu` 与 `mssfix` 下调，具体取值见 07-11。第二行 `link/none` 再次印证 tun 没有链路层地址。第三行 `tun type tun pi off ... persist off` 是最关键的一行：`type tun` 确认三层类型，`pi off` 说明未启用协议信息头，读写的是纯 IP 包，若出现 `pi on` 则每个报文前会多出四字节头，与应用预期不符时会导致解包错位；`persist off` 表示进程退出后设备随之销毁，若看到 `persist on` 且地址残留，说明可能有上一次异常退出留下的持久化设备，重复启动会报设备已存在。末两段 `inet 10.8.0.1/24 scope global` 与 `valid_lft forever` 说明地址已正确下发且不会过期；若整段 `inet` 缺失，则路由永远不通，应检查网络配置后端与 up 脚本是否执行。综合来看，一段正常的输出应当同时满足「三层标志正确、状态双 UP、无 PI 头、地址就位」四个条件，任一处异常都能把排错范围收敛到设备抽象层或网络配置后端，而无需去翻加密与握手日志。

### 6. 注意事项、陷阱与最佳实践

第一，选型上默认选 tun 路由模式。除非明确需要跨隧道的二层广播、非 IP 协议透传或把远端主机桥进同一网段，否则不要开 tap。tap 会把 ARP、DHCP、组播发现等噪声一并灌进隧道，客户端一多就形成广播放大，地址池与桥接也更容易和现网冲突；多数「远程接入 + 访问后端网段」的需求用 tun 加路由推送即可满足，相关组网见 07-09。

第二，Windows 驱动要认真二选一。wintun 面向高性能三层转发，是现代部署的优先项；TAP-Windows6 兼容面更广、历史更久，但性能与安装体验较差，驱动还需单独安装并通过签名校验。用 `--windows-driver` 指定时，取值与客户端版本支持情况需对照实际版本核验，切勿在服务端统一推送一个客户端并不识别的值。若用 tap 二层模型，更要先确认所选驱动在该版本确实支持。

第三，权限与容器是最常见的启动失败来源。Linux 上进程必须持有 `CAP_NET_ADMIN` 才能创建 tun 设备并下发路由；在 Docker 里运行时要显式 `--device /dev/net/tun` 并追加 `--cap-add NET_ADMIN`，只挂载设备节点而缺能力，会卡在 ioctl 阶段。Windows 上普通用户态进程不要奢望自己建网卡，应依赖 `src/openvpnserv/` 交互式服务完成提权，服务未启动或权限配置错误会直接表现为设备打开失败。

第四，固定设备名要服务于多实例而非制造冲突。`dev-node` 在单实例、需要与防火墙规则或脚本按名匹配时很有用；但同一台机跑多个 OpenVPN 实例时若都写死同一个名字，第二个实例必然启动失败。多实例应让内核自动命名，或为每个实例分配互不冲突的 `dev-node`，并让 up/down 脚本按传入的设备名参数工作，不要硬编码。

第五，macOS 与 BSD 不要照搬 Linux 经验。utun 设备名由内核生成，通常无法用 `dev-node` 指定，依赖按名匹配的脚本要改写；BSD 的克隆设备命名规则也不同。凡是涉及设备名、PI 头、持久化标志的假设，都应以 `src/openvpn/tun.c` 对应平台分支为准核验，不能凭 Linux 上的输出想当然。

第六，MTU 与 PI 头要成对考虑。设备层看到的 MTU 与链路上实际能承载的密文长度不是一回事，外层封装、加密填充、可能的压缩都会吃掉空间；表现通常是小包通、大包卡、TCP 建连后传大文件停滞，这类「MTU 黑洞」的定位方法与 mssfix、fragment 的适用边界见 07-11（模块见 07-11）。同时确认 `IFF_NO_PI` 与上层读写预期一致，避免多出或少了协议信息头导致报文被静默丢弃。

### 7. 小结与延伸阅读

本篇把 tun/tap 设备抽象层定位为用户态进程与内核网络栈之间的受控交界：`src/openvpn/tun.c` 用一套稳定接口收敛了 Linux `/dev/net/tun`、Windows wintun 与 TAP-Windows6、macOS utun、BSD 克隆设备的巨大差异，`networking_sitnl.c` 与 `networking_iproute2.c` 把网络配置从设备操作中剥离，`src/openvpnserv/` 解决了 Windows 提权，DCO 则在同一边界上提供了可选的内核卸载。选型结论很清晰：绝大多数场景用 tun 路由模式，仅在确有二层互通需求时用 tap；Windows 优先评估 wintun，容器与权限场景先确认 `CAP_NET_ADMIN` 与设备节点。

延伸阅读建议按三条线走。想逐字段理解 `tuntap` 与 `link_socket` 等对象如何挂进 `context`，读 05-02 与 05-07（字段见 05-02、字段见 05-07）；想跟清楚一个报文从 tun 读出、经帧封装到 socket 发出的完整机制，读 06-03 与 06-04，想看设备初始化挂到启动主流程的位置读 06-01（原理见 06-01、原理见 06-03、原理见 06-04）；想查全 `dev`、`dev-type`、`dev-node`、`windows-driver`、`tun-mtu` 等参数的完整取值与版本差异，读 04-02（指令见 04-02）。部署侧的最小可用拓扑与桥接模式对照分别见 03-01 与 03-04，容器内设备与能力配置见 03-05，路由与桥接模块能力见 07-09，MTU 与分片调优见 07-11。

## 07-02 link socket 与传输层

### 1. 背景与动机

上一节讲的 tun/tap 设备，解决的只是「用户态进程如何读写本机网络栈里的原始报文」。但一份能穿过公网的 VPN，光有本地端点远远不够：加密后的密文必须经由某个真实的网络套接字送达对端，对端发来的密文也必须从这个套接字被读回来、解密、再写回虚拟设备。承担这一职责的就是 link socket 与传输层模块，它是 OpenVPN 用户态进程与外部网络之间的唯一出入口，也是把控制通道与数据通道复用到同一条链路上的地方。把传输能力单独抽象成一层，而不是让 TLS 握手代码和加密代码各自去调系统套接字 API，好处是链路参数、地址族、代理、重定向、连接迁移这些横切关注点可以集中管理，上层只需面对一组「初始化、读、写、关闭」接口。

传输协议的选择，是这个模块最核心、也最容易被外行误解的设计动机。OpenVPN 默认并且强烈推荐 UDP，而不是很多人直觉上更「可靠」的 TCP。原因是一个被称为 TCP-over-TCP meltdown 的经典问题：当隧道内层承载的是一个 TCP 连接，而外层又用 TCP 来搬运时，内层与外层各自维护独立的重传定时器与拥塞窗口；一旦外网丢包，外层 TCP 会重传并收缩窗口，内层 TCP 因为迟迟收不到确认也启动自己的重传，两层重传相互叠加、指数级放大，表现为吞吐骤降、时延抖动、连接假死。UDP 没有内建重传，把可靠性交给隧道内层的真实协议去管，反而避开了这层放大效应。当然 UDP 也有代价：控制通道握手报文本身需要可靠送达，这部分由可靠层用轻量重传补上，属于机制范畴，见 06-05（原理见 06-05）。因此本模块对外呈现为「以 UDP 为主、TCP 为兼容备选」的形态。

现实网络的复杂性又进一步催生了三项能力。其一是多 remote：企业网关或公网服务常部署多个入口，客户端需要一份按顺序或随机尝试的地址清单，在某个入口不可达时自动切换到下一个，这与高可用组网直接相关，见 03-06。其二是代理穿透：很多办公网只允许出方向的 HTTP CONNECT 或 SOCKS 代理，VPN 必须能先把链路包在代理隧道里再出去，才能连到公网服务端。其三是 float 与连接迁移：移动客户端从 Wi-Fi 切到蜂窝、或经过 NAT 后源端口被重新映射，对端看到的源地址会变化，若链路层死守初始五元组就会断流，因此需要允许在验证身份的前提下更新实际端点。

需要明确本篇边界。作为模块功能与组网的权威源，本篇讲传输层「提供哪些能力、各自适用什么场景、怎么选」，即 UDP 与 TCP 的取舍、多 remote 的组网、代理穿透的形态、float 的安全含义（模块见 07-02）。至于链路套接字如何登记进事件集、如何用 poll 或 epoll 做 I/O 多路复用、可靠层怎么重传握手包、服务端多路复用时怎么按端点查实例，都属于机制与调用链，分别见 06-02、06-05 与 06-10（原理见 06-02、原理见 06-05、原理见 06-10）。把「能力」与「机制」分开，读者才不会在两册之间反复读重复内容。

### 2. 核心概念

link socket 抽象是第一个概念。它把一条链路所需的全部要素收敛到几组对象里：真正的系统套接字描述符、地址族与协议类型、resolved 之后的 remote 地址列表、本地绑定地址与端口、代理协商状态，以及「实际对端」与「配置对端」的区别。源码里 `struct link_socket`、`struct link_socket_info` 与表示实际端点的 `link_socket_actual` 各自分工，逐字段定义统一在 05-07 给出，本篇不重列（字段见 05-07）。这里只强调一点设计意图：之所以要把「实际端点」单独拎出来，正是为了 float——配置里写的 remote 是初始目标，而运行时真正收发报文的端点可能随 NAT 或换网改变，二者不能混为一谈。

第二组是 UDP 与 TCP 的能力差异。UDP 模式无连接、开销低、无队头阻塞，是数据通道的默认选择，但要求防火墙与 NAT 放行相应 UDP 端口，且依赖 keepalive 之类的机制维持 NAT 映射；TCP 模式提供了一条有序字节流，需要额外的长度分帧来界定报文边界，好处是能穿过只放行 TCP 或必须经过 HTTP/SOCKS 代理的网络，坏处是前述 meltdown 风险与更高的头部开销。与此相关的还有服务端 TCP 连接管理：多客户端通过 TCP 接入时，套接字接受与连接对象的管理集中在 `src/openvpn/mtcp.c` 一类辅助文件里，具体文件是否在当前版本保留需核验。

第三组是多 remote 与连接策略。客户端可以配置多条 remote，按列表顺序或配合 `remote-random` 随机挑选起始入口，连接失败或超时后轮换到下一条；这既是容灾手段，也是一种简单的负载均衡。`remote` 可以带端口与协议提示，配合 `proto`、`port`、`lport`、`local`、`bind` 等参数决定本地与远端端点，本篇第 5 节只演示最典型的几条，完整指令族见 04-02（指令见 04-02）。需要注意多 remote 的切换是传输层的行为，与证书、CA 无关，切换后 TLS 握手要重新走一遍。

第四组是代理穿透。HTTP 代理通过 CONNECT 方法建立到目标地址与端口的隧道，SOCKS 代理通过协商握手转发连接；两者都要求外层是面向连接的流，因此几乎总是与 `proto tcp-client` 搭配，这也是「代理模式天生带 TCP meltdown 风险」的根源。代理认证、超时、重试以及是否支持 NTLM 等细节在不同版本差异较大，须以 `src/openvpn/socket.c` 里的代理建立逻辑为准核验，函数名与可用选项名需对照实际版本核验。

第五组是 float 与连接迁移。`--float` 允许服务端接受来自非初始地址的数据包，并把该地址更新为新的实际端点；因为端点可以被改变，安全性就完全依赖控制通道的认证与完整性保护——只有持有合法密钥、通过 TLS 校验的对端才能触发迁移，否则就成了可被任意伪造的会话劫持。这也解释了为什么 float 必须和 tls-auth、tls-crypt 这类控制通道保护配合，后者见 07-03（模块见 07-03）。此外 `port-share` 允许在同一 TCP 端口上把非 OpenVPN 流量转交给另一台本地服务，属于辅助能力，留到 07-12 展开（模块见 07-12）。以上均为社区版 `src/openvpn/` 内置能力，与商业版 Access Server 无关。

把典型传输形态并列成表，能更直观地看出每种形态的适用边界与代价；表中的「或」类二选一用转义竖线表示，避免与表格列分隔混淆。

| 传输形态 | 适用网络 | 主要代价 | 典型指令组合 |
|---|---|---|---|
| `proto udp` | 公网直连 | 需放行 UDP 并保 NAT 映射 | `remote` 加 `keepalive` |

| float | 移动或 NAT 重映射 | 需控制通道保护兜底 | `float` 加 `tls-crypt` |

### 4. 关键流程与调用链

从模块协作角度，一条链路从配置到可用大致经过六步，这里只讲各模块之间交接什么，不展开内部状态机。第一步，启动流程把 `proto`、`remote` 列表、端口、代理参数解析进 options 相关对象（字段见 05-03）。第二步，链路初始化接口解析并解析 remote 主机名，得到候选地址清单，按是否配置 `remote-random` 决定起始顺序。第三步，按协议创建套接字：UDP 模式建数据报套接字并按需绑定本地地址端口，TCP 模式建流套接字并发起连接。第四步，若配置了 HTTP 或 SOCKS 代理，则在 `socket.c` 的代理建立逻辑里先完成 CONNECT 或 SOCKS 协商，把后续流量包进代理隧道；这一步只在 TCP 外层成立。第五步，把可用的链路套接字登记进事件循环，控制通道与数据通道的报文都经由它收发，凡收到的密文都先交给上层判断属于哪个客户端或哪个通道。第六步，当启用 float 且发现对端地址变化时，在通过身份校验的前提下更新实际端点，后续报文改发新地址；整个过程与服务端实例查找、事件集管理的衔接属于机制，见 06-10 与 06-02（原理见 06-10、原理见 06-02）。

### 5. 配置/命令/代码实例

按去重约定，这里只列本模块最典型的几条指令演示，其余交给 04 册（完整指令族见 04-02）。下面配置展示的是「UDP 主链路 + 双入口冗余 + 允许连接迁移 + 随机挑选入口」这一最常见的客户端传输层组合。

```conf
proto udp
remote vpn.example.net 1194
remote vpn-backup.example.net 1194
remote-random
float
```

```bash
openvpn --config client.conf --verb 4
```

```text
2026-11-11 10:15:40 float: peer moved from 198.51.100.10 to 203.0.113.77
```

下面逐行判读。`UDPv4 link local (bound)` 一行说明本地 UDP 套接字已成功绑定到通配地址与 1194 端口，`[undef]` 表示未显式绑定本地 IP，这是客户端的常态；若这一行迟迟不出现，或出现 `Cannot bind` 一类字样，应检查 `lport`、`bind` 与端口占用，而不是去查证书。`UDPv4 link remote` 给出解析后的首选远端地址与端口，可据此核对 DNS 是否把 `vpn.example.net` 解析到了预期入口；配合 `remote-random` 时，实际选中的入口与配置顺序未必一致，属正常现象。`TLS: Initial packet` 表示链路上已经收到了对端的首个控制通道报文，说明 UDP 双向通路打通、防火墙至少放行了这一来一回；若卡在此行之前反复重传，多半是远端安全组未放行 UDP 或代理配置错误。`Peer Connection Initiated` 表明控制通道握手推进到可建立会话的阶段，但这之后还需完成认证与密钥协商，不能仅凭此行判定 VPN 已可用。最后一行 float 记录对端从 198.51.100.10 漂移到 203.0.113.77，是移动换网或 NAT 重映射的典型痕迹；健康的迁移应当只此一次、随后连接继续，若 float 行密集反复出现，则可能是对端网络不稳定或存在地址伪造尝试，需要结合控制通道保护日志一起核查。这一行的确切措辞需对照实际版本核验。综合看，一段正常的链路启动日志应当呈现「本地绑定、远端解析、首包到达、会话发起」的清晰递进，float 是可选支线；把每行对应的模块定位清楚，就能把绝大多数连通性问题直接收敛到传输层。

### 6. 注意事项、陷阱与最佳实践

第一，坚持 UDP 优先。除非网络确实只放行 TCP 或必须走 HTTP/SOCKS 代理，否则不要因为「TCP 更可靠」就改成 `proto tcp`。遇到「能连上但传大文件极慢、时延忽高忽低」时，先怀疑是不是外层用了 TCP 导致 meltdown，而不是急着调加密套件。TCP 模式下务必理解这是兼容方案，性能上限明显低于 UDP。

第二，代理穿透要认清代价。HTTP 与 SOCKS 代理都建立在 TCP 之上，因此配置代理时几乎必然要把 `proto` 切到 TCP 客户端模式，这同时引入了 meltdown 风险与代理本身的单点。代理认证方式、超时与是否支持特定扩展在不同版本差异明显，选项名与行为需对照 `src/openvpn/socket.c` 核验，切勿照搬旧版本配置。代理口令不要写进可读日志。

第三，float 必须与控制通道保护绑定。允许端点漂移等于允许五元组变化，若没有 tls-auth 或 tls-crypt 对控制通道做认证与完整性校验，攻击者就可能伪造源地址劫持会话。生产环境应把 `float` 与 07-03 讲的控制通道保护一起启用，并通过 TLS 层的身份校验兜底，而不是裸开 float（模块见 07-03）。迁移后对端实例如何保持、路由是否需要重新下发，涉及服务端机制，见 06-10。

第四，多 remote 要配合可达性验证。多条 `remote` 只是候选清单，主机名解析失败、DNS 返回不可达地址、切换时 TLS 重新握手都会消耗时间；建议为每个入口做独立的连通性演练，并明确切换期间会话会重建这一事实，避免误以为是「无缝热切换」。与共享 CA、CRL 配合的高可用组网见 03-06。

第五，防火墙与 NAT 映射要成对考虑。UDP 模式需要在两端安全组放行相应端口，NAT 后的长连接还要靠 keepalive 一类机制定期刷新映射，否则空闲一段时间后映射老化，表现为「连着但突然不通」。本地端口方面，多实例同机运行时要为各实例分配不同的 `lport` 或让系统自动分配，避免端口冲突；`bind`、`local` 的语义差异见 04-02（指令见 04-02）。

第六，端口复用要谨慎。`port-share` 可以把 443 端口上非 OpenVPN 的流量转交给本地 Web 服务，提升穿透性，但只在 TCP 模式成立且会带来识别与分流复杂度，启用条件与边界见 07-12（模块见 07-12）。此外所有传输层能力都是社区版 `src/openvpn/` 内置，不要把商业版 Access Server 的集群或连接管理当成这里的功能。

### 7. 小结与延伸阅读

本篇把 link socket 与传输层定位为用户态进程通往公网的唯一出入口：`src/openvpn/socket.c` 统一管理 UDP/TCP 套接字、remote 列表、代理协商与实际端点，默认 UDP 以规避 TCP-over-TCP meltdown，多 remote 提供容灾与随机接入，HTTP/SOCKS 代理解决受限网络穿透，float 在控制通道保护兜底下支持连接迁移，`ps.c` 与 `mtcp.c` 分别承接端口复用与 TCP 连接管理。选型主线是「能走 UDP 就走 UDP，代理与 TCP 作为兼容退路，float 必须配保护」。

延伸阅读按三条线展开。想逐字段理解 `link_socket`、`link_socket_info` 与 `link_socket_actual` 的区别，读 05-07（字段见 05-07）；想跟清楚链路套接字如何进入事件循环、控制通道丢包如何重传、服务端如何按端点查实例，读 06-02、06-05、06-10（原理见 06-02、原理见 06-05、原理见 06-10）；想查全 `proto`、`remote`、`float`、`http-proxy`、`socks-proxy`、`port-share` 等参数的完整取值，读 04-02（指令见 04-02）。多入口高可用与代理场景的部署分别见 03-06 与 03-05，控制通道保护见 07-03，端口复用辅助能力见 07-12。

## 07-03 TLS 后端与 crypto 后端

### 1. 背景与动机

OpenVPN 的安全能力建立在两个彼此独立又相互配合的通道上：控制通道负责身份认证、参数协商与密钥交换，数据通道负责把大量业务报文高速加密后搬运。两条通道的底层都要调用密码学库，但调用的层次并不相同——控制通道跑的是完整的 TLS 协议栈，需要证书、握手、会话恢复与重协商；数据通道跑的是对称加密与消息认证，追求的是每包低延迟与高吞吐。如果让业务代码直接绑死某一个密码库的 API，那么换库、适配嵌入式平台、满足特定许可或合规要求都会变成伤筋动骨的大改造。于是社区版把这两类能力各自抽象成「后端」：TLS 后端与 crypto 后端，通过一层统一的头文件接口向上提供服务，具体实现可在编译期选择 OpenSSL 或 mbedTLS。这正是本模块存在的根本动机。

为什么需要不止一种后端，值得单独说明。OpenSSL 功能最全、生态最广、性能优化与硬件加速支持最成熟，是桌面与服务器的主流选择；mbedTLS 体积小巧、采用宽松许可、易于裁剪，常见于嵌入式设备、路由器固件以及对依赖体积敏感的场景。不同平台的系统自带库不同，某些发行版或安全基线还要求使用特定实现甚至 FIPS 验证的库。把后端做成可替换，等于把「用哪个密码库」从代码问题降级成构建期的一个开关，构建选项的完整清单见 02-03（指令见 04-03 之外，构建开关见 02-03）。这也是为什么在源码里同一类接口会同时存在 `ssl_openssl.c` 与 `ssl_mbedtls.c`、`crypto_openssl.c` 与 `crypto_mbedtls.c` 两份实现。

控制通道保护的演进，是本模块的第二条动机。早期只靠裸 TLS 握手，服务端端口一旦被扫描，攻击者能识别出这是一台 OpenVPN 服务器，进而发起握手洪泛消耗 CPU；控制通道报文也缺乏额外的静态认证。为此社区版逐步引入了三层保护：`tls-auth` 用一份共享静态密钥对控制通道包做 HMAC，让不持密钥的报文在解析前就被丢弃，主要解决探测与简单 DoS；`tls-crypt` 进一步把控制通道加密并认证，连握手内容本身都隐藏起来，抗扫描能力更强；`tls-crypt-v2` 则为每个客户端生成独立密钥、支持服务端按客户端撤销，把保护粒度从「全实例一份」提升到「每客户端一份」。这条演进线是选型时最需要理解的能力差异（模块见 07-03）。

照例先划清边界。本篇是模块功能与选型的权威源，讲「有哪些后端、各自能做什么、控制通道保护怎么选、典型配置长什么样」；TLS 握手的三密钥状态机、密钥派生与重协商、数据通道 AEAD 与 HMAC 的内部实现都属于机制，分别见 06-06、06-07、06-08（原理见 06-06、原理见 06-07、原理见 06-08）。证书与 PKI 本身在 07-04 单独成篇（模块见 07-04），本篇只在加载证书这一接口层面点到为止。商业版 Access Server 的能力不在此列，本篇只覆盖社区版 `src/openvpn/` 主线。

### 2. 核心概念

第一组概念是「两个后端维度」的区分，这是最容易被混淆的地方。TLS 后端服务于控制通道，实现在 `ssl_openssl.c` 与 `ssl_mbedtls.c`，负责 TLS 上下文建立、证书加载、握手驱动与会话管理；crypto 后端服务于数据通道，实现在 `crypto_openssl.c` 与 `crypto_mbedtls.c`，负责对称加密上下文、HMAC 与摘要计算。二者通常同源选择，即用 OpenSSL 就两个都用 OpenSSL 实现，用 mbedTLS 就两个都用 mbedTLS 实现，构建期由配置开关决定，运行时一般不做混搭。抽象接口分别收敛在 `ssl_backend.h` 与 `crypto_backend.h` 一类头文件里，上层 `ssl.c` 与 `crypto.c` 只针对抽象接口编程；这些头文件的确切命名与是否存在需对照实际版本核验。

第二组概念是编译期绑定而非运行时插件。后端是在 `configure` 阶段通过 `--enable-*` 一类开关选定并编进二进制的，不像插件那样运行时动态加载；因此要看一台机器上编译进去的是哪个后端、支持哪些算法与特性，应以 `openvpn --version` 与 `openvpn --show-tls` 等自检输出为准，而不是凭配置文件猜测。构建开关全表见 02-03。

第三组，也是本篇的重头戏，是控制通道保护的三层能力。`tls-auth` 用静态 HMAC 密钥给每个控制通道包加认证标签，服务端在 TLS 解析之前就能丢弃无标签或标签错误的包，从而抵御端口扫描与初级 DoS；但它不加密，握手内容仍可被观察，且所有实例共享同一份密钥，泄露后影响面大，双向通信还要用 `key-direction` 区分方向以免写反。`tls-crypt` 用同一份静态密钥对控制通道做加密加认证，握手报文对外呈现为不可识别的随机流，既抗扫描又隐藏握手，且不再需要区分方向；它是 2.6 系列推荐的控制通道保护基线。`tls-crypt-v2` 在 `tls-crypt` 之上引入每客户端密钥与服务端可撤销机制，客户端密钥由服务端主密钥签发，服务端可针对单个客户端作废，适合大规模分发与精细化回收，代价是密钥生成、分发与生命周期管理更复杂。三者的确切指令名、子命令名与生成方式需对照实际版本核验，可定位到 `src/openvpn/` 下的 TLS 与 crypto 后端实现及 `--help` 输出。

第四组概念是数据通道算法协商。`cipher`、`data-ciphers`、`auth` 等参数决定数据通道用哪套加密与认证算法，2.6 系列以 NCP 协商为主，客户端与服务端在握手时自动对齐到双方都支持的 AEAD 套件（如 AES-GCM 或 ChaCha20-Poly1305）。这套协商属于密钥与参数机制，见 06-07（原理见 06-07）；本篇只在第 5 节用一两条最典型指令示意，完整指令族见 04-03（指令见 04-03）。三者关系可以概括为：TLS 后端决定控制通道怎么握手，crypto 后端决定数据通道怎么加密，控制通道保护决定握手报文在链路上以什么形态出现。

### 4. 关键流程与调用链

从模块协作看，后端与保护能力在一次连接里按四步接入，这里只描述交接关系，不展开内部状态机。第一步，启动阶段根据构建期选定的后端，完成密码库的全局初始化与算法登记；这一步对上层几乎透明，但决定了后续可用算法集合。第二步，控制通道初始化：TLS 后端加载 CA、证书、私钥与可选的控制通道保护密钥，建立 TLS 上下文，并挂好证书校验回调（回调详见 07-04）。第三步，握手过程中，控制通道报文在发送前经过保护层处理——`tls-auth` 加 HMAC 标签，`tls-crypt` 或 `tls-crypt-v2` 做加密加认证——接收端先做相应校验，校验不过的包在进入 TLS 解析之前即被丢弃，这一步正是抗扫描与抗 DoS 的落点。第四步，握手成功后协商出的数据通道密钥交给 crypto 后端建立对称加密上下文，此后每个业务报文由数据通道加解密路径处理。以上四步与握手状态机、密钥派生、每包加密封装的衔接属于机制，分别见 06-06、06-07、06-08（原理见 06-06、原理见 06-07、原理见 06-08）。

### 5. 配置/命令/代码实例

按去重约定，这里只列本模块最典型的几条指令，完整指令族见 04-03（指令见 04-03）。下面配置展示的是「启用 tls-crypt 控制通道保护 + 指定数据通道套件族 + 指定控制通道摘要」这一常见服务端片段， ca/cert/key 属于 PKI，留到 07-04 演示。

```conf
tls-crypt tc.key
data-ciphers AES-256-GCM:AES-128-GCM:CHACHA20-POLY1305
auth SHA256
```

判断一台机器上到底编译进了哪个后端、支持哪些算法，最可靠的做法是让二进制自己报告，而不是翻配置文件。下面给出生成控制通道密钥与自检的两个命令，随后是 `--show-ciphers` 的典型输出。示例输出，具体格式需对照实际版本核验；`--genkey` 的子命令名、`--show-ciphers` 的列名与列举顺序在不同版本间会有差异。

```bash
openvpn --genkey tls-crypt tc.key
openvpn --show-ciphers
```

```text
AES-256-GCM  (256 bit key, 128 bit block, TLS client/server mode only)
AES-128-GCM  (128 bit key, 128 bit block, TLS client/server mode only)
CHACHA20-POLY1305  (256 bit key, stream cipher, TLS client/server mode only)
AES-256-CBC  (256 bit key, 128 bit block)
AES-128-CBC  (128 bit key, 128 bit block)
```

下面逐行判读。前两行 `AES-256-GCM` 与 `AES-128-GCM` 属于 AEAD 套件，括号里同时给出密钥长度与分组长度，末尾的 `TLS client/server mode only` 提示这类套件依赖 TLS 模式下的协商，正是 2.6 系列 NCP 默认偏好；若实际输出里这两行缺失，说明当前构建或后端不支持对应算法，`data-ciphers` 里写了也协商不成功。`CHACHA20-POLY1305` 是流式的 AEAD 套件，在没有 AES 硬件加速的嵌入式或移动端常常更快，把它放进候选清单能明显改善这类设备的体验。`AES-256-CBC` 与 `AES-128-CBC` 是传统的 CBC 套件，不带 AEAD 标记，需要额外配合 `auth` 指定摘要做完整性保护；它们保留多为兼容老客户端，新部署不建议作为首选，2.6 系列在双方都支持时会自动优先选 AEAD。整体看，健康输出应当同时列出若干 AEAD 套件与少量 CBC 兼容项，且没有任何套件被标注为不可用或缺失；如果清单极短、只剩 CBC 一两行，要回头核对构建期是否启用了相应后端与算法（构建开关见 02-03）。需要特别注意，本示例中的 `--genkey tls-crypt` 子命令名与 `tls-crypt-v2` 相关的生成子命令名，均需对照实际版本核验，切勿凭记忆写死；控制通道保护密钥文件属敏感材料，生成后应立刻收紧文件权限，做法见第 6 节。把自检输出与 `data-ciphers` 配置对照一遍，是上线前确认「后端能力」与「配置意图」一致的最省力手段。

### 6. 注意事项、陷阱与最佳实践

第一，不要混淆 `tls-auth` 与 `tls-crypt`。前者只做 HMAC 认证、不加密，且需要 `key-direction` 正确区分双向，写反会导致单方向通、另一方向静默丢包，是历史配置里极高频的坑；后者加密加认证、免分方向，是新部署的推荐基线。二者不要为了「双重保险」同时叠加，语义重叠且增加排错难度。从 `tls-auth` 迁移到 `tls-crypt` 需两端同步更换密钥文件与指令，灰度期要分批滚动，升级注意点见 08-05。

第二，静态密钥要按高敏感材料管理。无论 `tls-auth` 还是 `tls-crypt`，共享密钥一旦泄露，抗扫描与认证兜底就同时失效，且影响所有实例。生成用 `openvpn --genkey` 一类命令（子命令名需核验），落地后立即设为仅服务账号可读，纳入密钥轮换周期，绝不写进版本库或共享配置模板。大规模分发时优先考虑 `tls-crypt-v2` 的每客户端密钥，把泄露与撤销的影响面收敛到单个客户端。

第三，逐版本核验 `tls-crypt-v2` 能力。它依赖后端实现、编译开关与最低版本，不能假定所有二进制都支持；上线前用 `openvpn --version`、`openvpn --show-tls` 确认，客户端密钥的生成、签发与撤销流程也要先在测试环境走通。把「服务端可撤销」当成运维能力之前，先确认密钥生命周期管理流程是否配套，否则反而增加负担。

第四，数据通道算法以协商结果为最终依据。`data-ciphers` 只是候选清单，真正用哪套由双方 NCP 协商决定（原理见 06-07）；配置里写了一个本机并不支持的套件，不会报错但会被跳过。排查「吞吐不达预期」时，应结合 `--show-ciphers` 与运行时协商日志确认最终套件，再判断是否需要硬件加速或改用 ChaCha20-Poly1305，而不是盲目堆参数。禁用已知不安全的老套件是必要的，但完整套件清单与版本差异见 04-03。

第五，后端选择是构建期决策，别想在运行时切换。OpenSSL 与 mbedTLS 的能力集合、TLS 特性支持与性能特征不同，选定后整条链路行为随之确定；交叉编译、依赖开关与嵌入式裁剪见 02-03 与 02-04。更换后端等于重新构建与回归测试，不能只改配置。

第六，明确商业版边界。以上后端抽象、控制通道三层保护、算法自检都是社区版 `src/openvpn/` 内置能力；不要把 Access Server 的商业特性当成这里的后端功能。证书链、CRL 与 PKCS#11 硬件密钥属于 PKI 模块，见 07-04（模块见 07-04）；握手状态机与加解密机制见 06-06、06-08（原理见 06-06、原理见 06-08）。

### 7. 小结与延伸阅读

本篇把 TLS 后端与 crypto 后端定位为两条通道各自的密码学实现层：`ssl_openssl.c` 与 `ssl_mbedtls.c` 支撑控制通道 TLS，`crypto_openssl.c` 与 `crypto_mbedtls.c` 支撑数据通道对称加密，二者构建期成对选定；控制通道保护沿 `tls-auth`、`tls-crypt`、`tls-crypt-v2` 逐级增强，从认证抗扫描、到隐藏握手、再到每客户端可撤销。选型主线是「新部署用 `tls-crypt`，大规模精细化分发评估 `tls-crypt-v2`，数据通道以 AEAD 协商结果为准，后端能力一律用自检输出确认」。

延伸阅读按三条线走。想逐字段理解 TLS 上下文、密钥材料与加密上下文对象，读 05-05（字段见 05-05）；想跟清楚 TLS 握手状态机、密钥派生与重协商、数据通道 AEAD 与 HMAC 的实现，读 06-06、06-07、06-08（原理见 06-06、原理见 06-07、原理见 06-08）；想查全 `tls-auth`、`tls-crypt`、`tls-crypt-v2`、`cipher`、`data-ciphers`、`auth` 等参数的完整取值，读 04-03（指令见 04-03）。证书与 PKI 见 07-04，构建期后端开关见 02-03，控制通道保护与 float 的配合见 07-02，版本升级与套件迁移见 08-05。

## 07-04 证书与 PKI 模块

### 1. 背景与动机

如果说 07-03 讲的是「用什么密码库把报文保护好」，那么 07-04 要回答的是另一个更前置的问题：通信双方凭什么相信对端就是它声称的那台机器、那个人。OpenVPN 控制通道的身份根基建立在 X.509 公钥基础设施之上，客户端要验证服务端身份，服务端也要验证客户端证书，双向证书校验是默认安全模型。相比一份所有客户端共用的预共享密钥，PKI 的好处是可扩展、可区分、可撤销：每签发一张客户端证书就多一个可独立管理的身份，某台设备丢失时可以只吊销那一张证书而不影响其余客户端，还能通过证书里的用途与名称字段表达更细的约束。这种「按实体签发、按实体回收」的能力，是任何稍具规模的远程接入方案都绕不开的。

一个必须讲清的部署事实是：社区版 OpenVPN 本身并不内置发证机构。它只负责在握手时加载并校验 CA、证书与私钥，签发、续期、吊销这些 PKI 生命周期操作由外部工具完成，最常用的是 easy-rsa，也可以直接用 openssl 命令行或企业已有的 CA 系统。easy-rsa 是独立的工具仓库而非 `src/openvpn/` 内的模块，把它误当成 OpenVPN 内置组件是常见的认知偏差；其初始化、签发与吊销命令的完整清单见 04-07，实际部署步骤见 03-02（指令见 04-07、部署见 03-02）。因此本模块的边界非常清楚：它是「消费与校验 PKI 材料」的一侧，不是「生产 PKI 材料」的一侧（模块见 07-04）。

把 PKI 简单理解成「配置里写上 ca、cert、key 三行」是远远不够的。一次可靠的校验至少串联了五个判断：证书链是否逐级上溯到一个被信任的根、签发者与有效期是否合法、该证书是否已被 CRL 撤销、证书用途是否匹配它在本次连接里扮演的角色、以及证书里的名称是否符合管理员的预期约束。少了用途约束，攻击者可能用一张合法客户端证书冒充服务端做中间人；少了 CRL，离职员工的证书在过期前始终能连进来；少了名称约束，客户端可能连到一个同样由该 CA 签发、但并非目标的服务器。这五项正是本模块对外提供的核心能力，也是本篇要逐一展开的选型要点。

照例划清边界。本篇是模块功能与组网的权威源，讲「PKI 模块能校验什么、有哪些校验钩子、硬件密钥怎么接、典型配置长什么样」；握手过程中校验回调被触发的时序与三密钥状态机属于机制，见 06-06（原理见 06-06），证书相关的字段对象见 05-05（字段见 05-05）。商业版 Access Server 自带的证书管理与 Web 界面不属于社区版 `src/openvpn/` 能力，本篇不涉及。

### 2. 核心概念

第一组概念是 X.509 链校验与信任锚。服务端与客户端各自持有一份 CA 集合，可以是一个打包文件 `ca`，也可以是一个包含多个哈希命名证书的目录 `capath`；握手时对方提交自己的证书链，校验回调逐级验证签名，直到链顶命中本地信任锚，同时检查每一级的有效期、基本约束与签名算法。链不完整是最典型的故障：只发了端实体证书而漏了中间 CA，对端又没缓存中间证书，就会报「无法获取本地签发者证书」。链深度、是否允许自签等细节由后端校验实现决定，相关逻辑见 `src/openvpn/ssl_verify.c` 及后端特定文件。

第二组概念是本端材料与用途约束。`cert` 与 `key` 指定本进程使用的证书与私钥；`remote-cert-tls` 则让客户端要求对端证书具备特定扩展用途（例如 server 用途），服务端也可要求对端是 client 用途。这个约束直接防住「用合法客户端证书伪造服务端」的中间人攻击，是双向证书模型里不可省的一环；历史上的 `ns-cert-type` 已在新版本中被取代，确切指令名与可用取值需对照实际版本核验。私钥可以来自文件，也可以来自硬件，见第四组概念。

第三组概念是撤销与名称约束。`crl-verify` 指定证书撤销列表文件，校验回调在链校验通过后查表，命中即拒绝；CRL 本身有有效期，过期后校验行为需要特别谨慎，见第 6 节。`verify-x509-name` 允许管理员把对端证书的某个名称字段与预期值比对，只有匹配才放行，相当于在 CA 信任之外再加一道「必须连到这一台」的锁，多入口或共享 CA 场景下尤其有用。两者都是策略钩子，完整取值与匹配模式见 04-03。

第四组概念是硬件密钥与平台证书存储。PKCS#11 让私钥留在智能卡或 HSM 里、只把签名运算交给库完成，私钥永不导出，安全等级更高；相关支持历史上集中在 `src/openvpn/pkcs11.c`，但 2.6 与 2.7(master) 是否仍保留该后端、依赖的辅助库与对应指令名差异较大，必须对照实际版本核验，可定位到 `src/openvpn/pkcs11.c` 与构建配置。Windows 平台还有 `cryptoapi.c` 一类实现，可从系统证书存储读取证书与私钥，确切文件名与能力需核验。以上都属于「私钥不出硬件、校验仍在软件」的组合，选型时要把驱动、中间件与 PIN 管理一并纳入。

最后重申：easy-rsa 是独立仓库，PKI 材料的生产在 03-02 与 04-07；本篇只讲社区版如何加载、校验与约束这些材料。校验能力的层次关系可结合图 07-04-01 一起理解。

### 3. 关键数据结构与源码位置

本模块涉及的证书上下文、校验状态等对象，逐字段定义统一由 05-05 给出，本篇不重列（字段见 05-05）。下表按源文件列出 PKI 校验能力地图，均为社区版真实或历史上存在的位置，凡在版本间可能增删的都标注了核验要求。

把五项校验能力并列成表，能更直观地看出每项防的是什么风险、以及配置缺失时的后果。表中含二选一的语义用转义竖线书写。

| 校验能力 | 防的主要风险 | 配置入口 | 缺失后果 |
|---|---|---|---|
| 链校验与信任锚 | 伪造身份 | `ca` \| `capath` | 任意 CA 签发证书均可信 |
| 有效期与深度 | 过期或越权证书 | 后端策略 | 过期证书仍被接受 |
| 用途约束 | 客户端冒充服务端 | `remote-cert-tls` | 中间人风险 |
| CRL 撤销 | 离职设备仍可连入 | `crl-verify` | 无法即时吊销 |
| 名称约束 | 连到同 CA 错误服务器 | `verify-x509-name` | 目标可被替换 |
| 硬件私钥 | 私钥文件被拷贝 | PKCS#11 \| CryptoAPI | 私钥可离线窃取 |

需要特别说明 PKCS#11 与 CryptoAPI 两行：它们不是所有构建都具备的能力，是否可用取决于编译开关、依赖库与版本，切勿在配置里直接写上未经核验的指令名；核验入口是 `src/openvpn/pkcs11.c`、`src/openvpn/cryptoapi.c` 与构建配置以及 `openvpn --version` 输出。本节只做模块地图与能力对照，字段定义见 05-05，握手时校验回调的触发时序见 06-06（原理见 06-06）。

### 4. 关键流程与调用链

从模块协作角度，一次证书校验大致串起六步，这里只讲各步骤交接什么，不展开回调内部的逐行实现。第一步，启动阶段加载本地信任锚 `ca` 或 `capath`、本端 `cert` 与 `key`，以及可选的 `crl-verify` 撤销列表，交给 TLS 后端建立上下文。第二步，握手时双方提交证书链，校验回调被触发。第三步，回调逐级上溯证书链，验证签名者、有效期与基本约束，直到命中本地信任锚。第四步，查询 CRL 判断是否已撤销。第五步，执行策略钩子：比对 `verify-x509-name` 期望名称、检查 `remote-cert-tls` 声明的用途扩展。第六步，全部通过则允许握手继续，任一环节失败立即中止并写日志。以上与 TLS 状态机、握手报文重传的衔接属于机制，见 06-06 与 06-05（原理见 06-06、原理见 06-05）。硬件密钥场景下，第五步之前的签名操作被转发到 PKCS#11 或系统证书存储完成，私钥本身不进入进程内存。

### 5. 配置/命令/代码实例

按去重约定，这里只列本模块最典型的几条指令，完整指令族见 04-03（指令见 04-03）。下面配置展示的是客户端侧「信任根 + 本端证书私钥 + 对端用途约束 + 撤销列表」这一最小安全集合，`verify-x509-name` 的用法在正文说明，不重复进配置片段。

```conf
ca ca.crt
cert client1.crt
key client1.key
remote-cert-tls server
crl-verify crl.pem
```

签发完成后，运维最该做的是在启动前用 openssl 独立核对证书内容，不要等握手失败再去猜。下面给出两条只读检查命令，随后是典型输出。示例输出，具体格式需对照实际版本核验，不同 OpenSSL 版本的字段大小写、日期格式与扩展呈现方式会有差异。

```bash
openssl x509 -in server.crt -noout -subject -issuer -dates
openssl verify -CAfile ca.crt server.crt
```

```text
subject=CN = vpn.example.net
issuer=C = CN, O = Example Org, CN = Example Root CA
notBefore=Nov  1 00:00:00 2026 GMT
notAfter=Oct 31 23:59:59 2028 GMT
server.crt: OK
```

下面逐行判读。`subject=CN = vpn.example.net` 给出服务端证书的主体名，这正是 `verify-x509-name` 可以匹配的字段之一；若这里与管理员预期的入口名不一致，即使链合法也应拒绝，说明证书签给了别的主机。`issuer=... CN = Example Root CA` 表明签发者是根 CA，配合后续链校验可判断是否命中本地信任锚；若实际部署用了中间 CA，这里应显示中间 CA 的名称，且客户端必须能拿到完整链，否则会报无法获取本地签发者证书。`notBefore` 与 `notAfter` 是有效期窗口，健康状态是「当前时间落在两者之间且离 `notAfter` 尚有合理余量」；常见问题一是两端主机时钟不同步导致证书被判为尚未生效，二是证书已临近过期却未续期，二者都表现为握手阶段直接失败，排查时应先对时再看证书。最后一行 `server.crt: OK` 是 `openssl verify` 的结论，说明该证书在指定 `CAfile` 下链校验通过；若出现 `unable to get local issuer certificate`，几乎总是中间证书缺失或 CA 文件不对，若出现 `certificate has expired` 或 `certificate is not yet valid`，则回到有效期与时钟。需要强调，这里的 `OK` 只覆盖链与有效期，并不检查 CRL 撤销、用途扩展与名称约束，那几项要靠 OpenVPN 侧的策略钩子补齐，因此「openssl 显示 OK 但 OpenVPN 仍拒绝」并不矛盾。把这几行与配置里的 `ca`、`remote-cert-tls`、`crl-verify`、`verify-x509-name` 一一对照，就能在启动前把绝大多数证书问题定位清楚，而不必去翻 TLS 握手日志。

### 6. 注意事项、陷阱与最佳实践

第一，务必提供完整证书链。使用中间 CA 的 PKI 体系里，端实体证书必须随链一起提交，或确保对端已缓存中间证书；只发一张叶子证书是最常见的握手失败原因。CA 文件也要包含到根为止的信任锚，`ca` 用打包文件还是 `capath` 用哈希目录，需与签发体系一致，取值见 04-03。

第二，CRL 是运维上的高风险点。`crl-verify` 加载的列表有有效期，过期后校验行为可能导致大范围拒绝连接，表现为「所有客户端突然都连不上」；生产环境必须把 CRL 的生成、分发、更新做成高可用流程，并把更新时间纳入监控，不能签一次就再也不管。证书生命周期与 CRL 分发的 checklist 见 08-06。

第三，时间同步是隐形前置条件。证书有效期判断依赖两端系统时钟，服务端或客户端 NTP 异常会触发「证书尚未生效」或「已过期」的误判，且这类错误看起来像证书本身坏了。上线前把时钟同步纳入环境检查，排障时把「对时」放在「换证书」之前。

第四，不要省掉用途与名称约束。`remote-cert-tls` 防止合法客户端证书被拿去冒充服务端，是双向证书模型的关键一环；多入口或共享同一 CA 的场景再加 `verify-x509-name` 锁定目标名称。两者都属策略钩子，指令名与匹配模式需对照实际版本核验，但「宁可多一道约束」的原则不变。

第五，私钥与硬件密钥按最高敏感级别管理。文件私钥设为仅服务账号可读，绝不入版本库、绝不写进日志；使用 PKCS#11 或系统证书存储时，先确认当前构建确实支持（核验 `src/openvpn/pkcs11.c`、`src/openvpn/cryptoapi.c` 与 `openvpn --version`），再把驱动、中间件、PIN 输入与无人值守启动一并设计好，否则硬件密钥反而会成为单点故障。不要凭记忆写指令名。

第六，分清 PKI 生产与消费的边界。easy-rsa 是独立仓库，签发、续期、吊销在 03-02 与 04-07，社区版只负责加载与校验；商业版 Access Server 的证书管理与 Web 界面不是这里的社区版能力。证书校验回调在握手状态机中的位置见 06-06（原理见 06-06），认证凭据与双因素属 07-05（模块见 07-05）。

### 7. 小结与延伸阅读

本篇把证书与 PKI 模块定位为「消费并校验 PKI 材料」的一侧：社区版 `src/openvpn/ssl_verify.c` 串起链校验、信任锚、CRL 撤销、名称约束与用途约束五道判断，本端材料来自 `ca`、`cert`、`key`，高安全场景可把私钥放进 PKCS#11 或系统证书存储，材料的生产则由独立仓库 easy-rsa 或企业 CA 完成。最核心的选型结论是：链要完整、用途与名称约束不能省、CRL 要持续更新、时钟要同步、私钥要按最高敏感级别保管。

延伸阅读按三条线走。想逐字段理解证书上下文与校验状态对象，读 05-05（字段见 05-05）；想跟清楚校验回调在 TLS 握手与三密钥状态机里的触发时序，读 06-06，握手丢包重传见 06-05（原理见 06-06、原理见 06-05）；想查全 `ca`、`cert`、`key`、`crl-verify`、`verify-x509-name`、`remote-cert-tls` 以及 PKCS#11 相关参数的完整取值，读 04-03（指令见 04-03）。PKI 部署与 easy-rsa 命令见 03-02 与 04-07，控制通道保护见 07-03，认证与双因素见 07-05，证书生命周期运维见 08-06。

## 07-05 认证模块

### 1. 背景与动机

07-04 讲的证书解决的是「这台设备持有的密钥是否可信」，但在真实远程接入场景里，仅有设备级身份往往不够：一张客户端证书可能被拷贝、一台笔记本可能多人共用、企业合规要求还能证明「此刻操作的是哪个自然人、且通过了第二重因子」。于是 OpenVPN 在证书校验之外再叠一层用户认证，形成「通道认证 + 用户认证」两阶段模型。认证模块正是承载第二阶段能力的集合，它把凭据收集、外部校验、动态质询、双因素以及重协商免重复输入这些需求，收敛成可组合的几条路径。理解这一点，就能明白为什么配置里既有证书指令，又有 `auth-user-pass` 一类凭据指令，二者不是二选一而是分层叠加。

第二重动机来自重协商体验。TLS 会话会周期性重协商密钥（机制见 06-07），如果每次重协商都要求用户重新输入一次用户名密码，在开启双因素的场景下几乎不可用——用户不可能守着屏幕每半小时输一次动态口令。`auth-token` 就是为解决这个问题引入的：首次认证通过后，服务端向客户端下发一个有时效的令牌，后续重协商用令牌代替原始凭据，用户无感。这把「安全性要求周期性换密钥」与「可用性要求不反复打扰用户」这对矛盾调和起来，是认证模块里非常关键但常被忽视的一环（原理见 06-07、模块见 07-05）。

第三重动机是外部系统集成。企业很少把用户目录直接塞进 VPN，通常已有 LDAP、RADIUS、PAM、数据库或统一身份认证平台。OpenVPN 社区版因此提供三类外接路径：`auth-user-pass-verify` 脚本钩子、可加载的插件（如 `src/plugins/auth-pam/` 的 PAM 插件）、以及通过 management interface 由外部程序提供凭据（后者见 07-06）。它们把「凭据对不对」的判断交给外部系统，VPN 只消费结论。异步认证、延迟判定这类进阶能力属于脚本与插件模块，见 07-07（模块见 07-07）。

照例划清边界。本篇是模块功能与组网的权威源，讲「有哪些认证方式、各自适用什么场景、怎么组合、典型配置长什么样」；凭据在握手里的传递时序、重协商触发条件、令牌如何进入密钥状态机属于机制，见 06-06 与 06-07（原理见 06-06、原理见 06-07），令牌与推送的字段对象见 05-09（字段见 05-09）。商业版 Access Server 的集成能力不在此列，本篇只覆盖社区版 `src/openvpn/` 与 `src/plugins/` 主线。

### 2. 核心概念

第一组概念是两阶段认证的分工。证书认证由 07-04 的校验链完成，决定 TLS 控制通道能否建立；用户认证在控制通道建立后进行，决定这个「人」是否被允许接入。二者可以组合，也可以在特定场景下放宽证书要求，但放宽会带来明显的安全降级，相关指令名与风险需对照实际版本核验。生产环境默认应保持双向证书 + 用户认证双开。

第二组概念是凭据的收集与校验。`auth-user-pass` 是客户端侧指令，指定凭据来源（交互式输入或文件）；服务端侧用 `auth-user-pass-verify` 指向一个校验脚本，或用 `plugin` 加载校验插件。脚本路径拿到用户名、密码与一批环境变量，返回结论即可；插件路径性能更好、可做异步，典型代表是 `src/plugins/auth-pam/auth-pam.c`，它把校验转给系统 PAM 栈，从而间接对接本地账号、LDAP 或 RADIUS。脚本与插件的完整指令族、环境变量全集见 04-05（指令见 04-05）。

第三组概念是令牌认证。`auth-gen-token` 让服务端在首次认证成功后生成令牌并推送给客户端，客户端在后续重协商时用令牌代替密码；令牌有生命周期，可配合服务端密钥做签发与校验，相关逻辑集中在 `src/openvpn/auth_token.c` 与 `auth_token.h`。多实例或重启场景下的令牌一致性、密钥配置与有效期取值需对照实际版本核验，可定位到 `src/openvpn/auth_token.c` 与 `options.c`。

第四组概念是 challenge/response 与双因素。静态质询让客户端在密码之外再提交一个字段，动态质询则允许服务端在认证中途发起「再要一次口令」的交互，典型用途是 TOTP 动态口令、短信验证码或硬件令牌；社区版里这类交互通常借助脚本配合认证控制文件、待处理文件一类机制完成，确切环境变量名与协议前缀需对照实际版本核验。2FA 的本质是「你知道的东西 + 你拥有的东西」，把它接进 VPN 时，必须同时考虑重协商：若没有 `auth-token`，每次重协商都会重新触发一次性口令，导致连接掉线，这正是令牌与双因素必须成对设计的原因。

第五组概念是凭据来源的多样性。除脚本与插件外，management interface 也能由外部程序应答用户名密码与挑战，适合已有 GUI 或编排系统的集成（模块见 07-06）；`push.c` 负责把令牌等认证结果回推给客户端（原理见 06-11）。以上能力均为社区版内置，与商业版无关。认证方式之间的协作关系可结合图 07-05-01 理解。

### 4. 关键流程与调用链

从模块协作角度，一次带双因素与令牌的认证大致走七步，这里只讲各模块之间交接什么。第一步，证书校验先通过，控制通道就绪（见 07-04）。第二步，客户端按 `auth-user-pass` 提交用户名密码，必要时附带静态质询字段。第三步，服务端把凭据分发给三条外接路径之一：脚本钩子、插件，或 management 外部程序。第四步，若启用动态质询，外接路径不立即给结论，而是发起 challenge，要求客户端再提交一次性口令，客户端应答后回到校验。第五步，校验通过，服务端建立会话并按配置用 `auth_token.c` 生成令牌、经 `push.c` 推送给客户端。第六步，后续重协商时客户端用令牌代替原始密码，令牌校验通过后无需再次触发双因素，用户无感。第七步，令牌失效或校验失败则回退到完整认证或断开。以上与握手状态机、重协商触发、推送机制的衔接属于机制，见 06-06、06-07、06-11（原理见 06-06、原理见 06-07、原理见 06-11）；异步 defer 与插件 API 细节见 07-07。

```conf
script-security 2
auth-user-pass-verify /etc/openvpn/check.sh via-env
auth-gen-token 3600
plugin /usr/lib/openvpn/plugins/openvpn-plugin-auth-pam.so login
```

认证链路是否真的走通，最直观的判据是服务端日志里凭据校验与会话建立的递进关系。下面给出以较高日志级别启动服务端的命令，随后是一段典型日志输出。示例输出，具体格式需对照实际版本核验；`AUTH-PAM` 前缀、deferred 措辞、soft reset 行的格式在不同版本与插件组合下会不同。

```bash
openvpn --config server.conf --verb 4
```

```text
2026-11-11 10:12:06 198.51.100.10:1194 TLS: Username/Password authentication deferred
2026-11-11 10:12:06 198.51.100.10:1194 AUTH-PAM: BACKGROUND: user 'alice' : OK
2026-11-11 10:12:06 198.51.100.10:1194 Control Channel: TLSv1.3, cipher TLSv1.3 TLS_AES_256_GCM_SHA384
2026-11-11 10:12:07 198.51.100.10:1194 [alice] Peer Connection Initiated with [AF_INET]198.51.100.10:1194
2026-11-11 10:42:07 198.51.100.10:1194 TLS: soft reset sec=0 bytes=0/0 pkts=0/0
```

下面逐行判读。首行 `Username/Password authentication deferred` 说明服务端没有同步阻塞等待校验，而是把凭据交给外部路径异步处理，这正是 `auth-user-pass-verify` 或插件配合 defer 的正常形态；若这一行后面长时间没有下文，应怀疑脚本或插件卡住、超时未回结论，而不是密码错误。第二行 `AUTH-PAM: BACKGROUND: user 'alice' : OK` 是 PAM 插件在后台线程完成校验的结论，`OK` 表示凭据与该用户被接受，`user 'alice'` 可与后续会话名对照；若出现 `FAIL` 或认证失败字样，则问题落在 PAM 栈、账号或凭据本身，属于外部系统而非 VPN。第三行 `Control Channel` 给出协商出的 TLS 版本与套件，说明证书校验与用户认证都已通过、控制通道参数落定，与 07-03 的后端能力吻合。第四行 `[alice] Peer Connection Initiated` 中括号里的用户名是关键信号——它表明会话已与该自然人绑定，后续计费、路由与日志都能按用户追溯；若这里没有用户名或显示为证书 CN，往往意味着只走了证书认证、用户认证并未生效，需回查配置。末行 `TLS: soft reset` 是一次重协商起点，健康状态下它之后应当靠 `auth-token` 静默完成、不再次出现 `deferred` 与双因素质询；如果每次 soft reset 都重新弹出凭据校验，说明令牌未启用或已失效，用户会在周期性重协商时被反复打断。综合来看，一段正常的认证日志应呈现「异步受理、外部通过、通道落定、按用户建会话、重协商无感」五段递进，把这五段与 `auth-user-pass-verify`、`plugin`、`auth-gen-token` 一一对应，就能把绝大多数认证问题收敛到具体模块，而不必去翻证书链或链路日志。

### 6. 注意事项、陷阱与最佳实践

第一，凭据与日志脱敏优先级最高。用户名密码、动态口令绝不能写进可读日志、配置模板或版本库；使用 `via-env` 传参的脚本要意识到环境变量在进程列表与子进程中可能被看到，高安全场景优先评估插件路径。认证失败的日志只记结论不记明文凭据，日志分级与脱敏见 08-06。

第二，脚本路径要管好 `script-security`。启用 `auth-user-pass-verify` 等钩子必须配合足够的 `script-security` 级别，但级别越高越要收紧脚本文件权限与内容审查，避免把可执行入口暴露给低权限账号。脚本环境变量全集、defer 异步协议与超时行为见 04-05 与 07-07（指令见 04-05、模块见 07-07），切勿凭记忆写环境变量名。

第三，令牌与双因素必须成对设计。开了 2FA 却不开 `auth-gen-token`，周期性重协商会反复触发一次性口令，表现为「连着连着就断」；反过来令牌有效期过长或签发密钥在多实例间不一致，又会带来安全与可用性问题。`auth-gen-token` 的有效期、密钥配置与多实例一致性需对照实际版本核验（见 `src/openvpn/auth_token.c` 与 `options.c`），令牌与重协商的机制见 06-07。

第四，插件与脚本按规模选型。小规模、策略经常变动的场景用脚本更灵活；对接已有 LDAP、RADIUS 或系统账号体系时，`src/plugins/auth-pam/` 一类插件更稳、性能更好、还能做异步判定。二者不要在同一条认证链上并行给出可能冲突的结论，明确一条主路径即可。

第五，放宽证书要求要极其谨慎。某些场景会用「仅用户名密码」或「不要求客户端证书」的指令组合降低部署门槛，但这等于把设备级身份这一层完全去掉，一旦凭据泄露即可接入；相关指令名与可用组合需对照实际版本核验，默认应保持双向证书与用户认证双开。

第六，明确商业版边界。以上脚本、插件、令牌、挑战都是社区版 `src/openvpn/` 与 `src/plugins/` 内置能力；不要把 Access Server 的目录集成或 Web 界面特性写成本模块功能。management 提供凭据的路径见 07-06，握手时序与令牌机制见 06-06、06-07（原理见 06-06、原理见 06-07）。

### 7. 小结与延伸阅读

本篇把认证模块定位为「通道认证之上的用户认证层」：证书校验通过后，`auth-user-pass` 收集凭据，脚本钩子、`src/plugins/auth-pam/` 插件或 management 外部程序给出结论，动态质询与 TOTP 构成双因素，`auth_token.c` 签发令牌让周期性重协商免于反复打扰用户，`push.c` 把结果回推客户端。选型主线是「默认双向证书加用户认证，外部系统集成优先插件，开双因素必配令牌，凭据全程脱敏」。

延伸阅读按三条线走。想逐字段理解令牌状态、插件句柄、脚本环境与 management 连接状态，读 05-09（字段见 05-09）；想跟清楚凭据在握手里的传递时序、重协商触发条件与推送机制，读 06-06、06-07、06-11（原理见 06-06、原理见 06-07、原理见 06-11）；想查全 `auth-user-pass`、`auth-user-pass-verify`、`auth-gen-token`、`plugin`、`script-security` 等参数的完整取值与脚本环境变量全集，读 04-05（指令见 04-05）。证书校验见 07-04，management 凭据应答见 07-06，插件 API 与 defer 异步见 07-07，日志脱敏与凭据生命周期见 08-06。

## 07-06 management interface 模块

### 1. 背景与动机

一个以守护进程方式运行的 OpenVPN，通常没有可交互的终端：它开机自启、静默地在后台搬运报文，管理员却仍然需要在运行中回答一连串问题——现在有哪些客户端连着、某个用户是什么状态、隧道是否已经建立、收发字节数涨到多少、要不要临时踢掉某个会话、要不要在启动阶段先按住连接等外部系统就绪。如果只能靠给进程发 UNIX 信号或去轮询一个周期性刷新的状态文件，这些需求会变得非常笨拙：信号粒度太粗，只能表达「重载」「退出」这类少数动作；状态文件是单向、有延迟、需要反复读取的快照，无法让外部程序实时感知状态迁移，更无法把管理员的决策回注给进程。management interface 模块就是为填补这个缺口而存在的，它在 OpenVPN 进程上开一个受控的双向字节流接口，让外部程序既能订阅运行时状态，又能下发控制命令。

把它和前几篇的模块放在一起看，层次会更清楚。07-02 的 link socket 是 VPN 与对端之间的数据面出入口，07-06 的 management socket 则是运维与编排系统之间的管理面出入口，二者方向完全不同：一个承载加密后的业务报文，一个承载明文的控制协议。07-05 讲认证时提到凭据可以由 management 外部程序提供，正是本模块能力的一种；07-12 的 status 文件、日志与 keepalive 等辅助能力也常与本模块配合，但那些是周期性快照与日志流，management 是实时双向会话（模块见 07-12）。理解这种「管理面与数据面分离」的定位，是避免把 management 误当成 VPN 流量入口或用户隧道的关键。

商业版边界在这里尤其需要讲清，因为最容易被混淆。社区版 management interface 只是一个基于 TCP 或 unix domain socket 的明文控制协议，外加一组查询与控制命令；它不提供 Web 管理界面、不提供集群管理、不提供用户门户，也不自带多节点编排。Access Server 的商业特性（Web UI、集群、集中用户与许可管理）不是社区版 `src/openvpn/` 的能力，不能因为都能「管理 OpenVPN」就画等号。本篇覆盖的始终是社区版主线里 `src/openvpn/manage.c` 这一套内置接口（模块见 07-06）。

照例划清边界与去重。本篇是模块功能与组网的权威源，讲「接口提供哪些能力、有哪两种监听形态、状态订阅与运行时控制怎么用、与外部系统怎么集成、安全边界在哪里」；全部 management 命令的逐项语法与返回格式由 04-06 给出（指令见 04-06），管理连接状态等字段对象见 05-09（字段见 05-09），命令回注事件循环、服务端按实例下发控制属于机制，见 06-02 与 06-10（原理见 06-02、原理见 06-10）。本篇配置段只列最典型的几条，绝不重列命令全集。

### 2. 核心概念

第一组概念是两种监听形态。`--management` 可以让进程在一个 TCP 地址与端口上监听，也可以在一个 unix domain socket 路径上监听；前者便于跨主机或容器边界访问，后者借文件系统权限天然限制本机访问。`management-client` 则是反向形态：进程主动以客户端身份去连某个管理端，适用于被管理端不便开放监听端口的场景。选择哪一种，首先取决于部署拓扑与网络边界，其次才是便利性。监听地址、端口与可选密码文件的确切参数形式需对照实际版本核验，可定位到 `src/openvpn/manage.c` 与 `src/openvpn/options.c`。

第二组概念是双向字节流协议。management 连接建立后，外部程序发来的每一行是一个命令，进程回一行或多行响应；与此同时，进程会主动推送以 `>` 前缀开头的实时事件行，例如状态迁移、日志、字节计数、凭据需求、暂停提示等。也就是说，同一个连接上同时存在「请求—响应」与「服务端主动推送」两种流量，外部客户端必须能区分二者：不带 `>` 的通常是命令响应或数据行，带 `>` 的是异步事件。这一区分是写集成程序时最容易出错的地方，`>STATE:`、`>LOG:`、`>BYTECOUNT:`、`>PASSWORD:`、`>ECHO:`、`>HOLD:`、`>INFO:` 等具体前缀需对照实际版本核验。

第三组概念是状态订阅。外部程序可以查询当前状态机所处的状态、请求客户端列表与路由表快照、开启字节计数的周期性推送、订阅日志流、以及用 echo 让一组配置参数按订阅方式回吐。这些能力让监控系统不必再解析日志文件，就能拿到结构化、近乎实时的运行视图。`status` 的不同详细级别、`state` 的字段含义、`bytecount` 的采样间隔、`log` 与 `echo` 的订阅与取消，逐项语法见 04-06（指令见 04-06）。

第四组概念是运行时控制。与管理面读能力相对的是写能力：断开指定客户端、向进程发信号、在启动阶段按住连接直到外部放行、以及配合外部认证对某个待认证客户端给出允许或拒绝的结论。`client-kill`、`client-deny`、`signal`、`hold release`、`client-auth` 一类命令让编排系统可以在不重启进程的前提下改变运行状态；它们最终要回注到事件循环与服务端实例表去执行，具体路径属于机制，见 06-02 与 06-10（原理见 06-02、原理见 06-10）。

第五组概念是凭据应答与外部认证。启用 `management-query-passwords` 后，进程在需要用户名密码、私钥口令或挑战应答时，通过 `>PASSWORD:` 一类提示向外部程序索要，外部程序用相应命令把凭据送回；配合 `management-client-auth`，还可以在客户端认证阶段由外部系统决定放行与否。这与 07-05 的脚本、插件路径并列，是第三种凭据来源（模块见 07-05）。第六组是安全边界：management 协议本身是明文、默认不带强认证，务必绑定到回环地址或受文件系统权限保护的 unix socket，并按需启用密码文件，绝不可直接暴露到公网。以上能力的模块协作关系可结合图 07-06-01 理解。

### 4. 关键流程与调用链

从模块协作角度，一次 management 集成大致串起六步，这里只讲各模块之间交接什么。第一步，启动阶段按 `management` 系列参数初始化监听：TCP 形态绑定地址端口，unix socket 形态创建路径并设置权限，必要时加载密码文件。第二步，外部客户端（GUI、编排系统或监控采集器）建立连接，进程先发出一个版本与帮助提示类的 `>INFO:` 行，标识接口协议版本。第三步，外部程序发命令，命令分发逻辑解析后交给对应处理函数：查询类命令从运行态对象取快照，控制类命令转成内部事件。第四步，订阅类命令生效后，进程在状态迁移、日志产生、字节计数刷新时，主动推送 `>STATE:`、`>LOG:`、`>BYTECOUNT:` 等实时行，外部程序据此更新视图。第五步，运行时控制与外部认证结论被回注到事件循环与服务端实例表，由 `signal.c`、`multi.c`、`push.c` 等落地执行。第六步，需要凭据时，进程通过 `>PASSWORD:` 一类提示向外部索取，外部用 username/password 类命令应答，结论回到认证路径。以上与事件循环、实例查找、推送机制的衔接属于机制，见 06-02、06-10、06-11（原理见 06-02、原理见 06-10、原理见 06-11）。

### 5. 配置/命令/代码实例

按去重约定，这里只列本模块最典型的几条监听侧参数，完整参数与全部命令见 04-06（指令见 04-06）。下面配置展示的是「绑定回环 TCP 端口 + 启用密码文件 + 启动阶段按住 + 由外部提供凭据」这一常见服务端组合；密码文件参数的确切形式需对照实际版本核验。

```conf
management 127.0.0.1 7505 /etc/openvpn/mgmt.pass
management-hold
management-query-passwords
management-log-cache 200
```

验证接口是否可用、并读取一份状态快照，最省事的做法是用 nc 连上监听端口后连发几条命令。下面给出一次性查询的示例，随后是典型输出。示例输出，具体格式需对照实际版本核验；`>INFO:` 文案、协议版本号、`>STATE:` 字段个数、`CLIENT_LIST` 列名与 `SUCCESS` 措辞在不同版本间会有差异。

```bash
printf 'version\nstate\nstatus 2\nquit\n' | nc 127.0.0.1 7505
```

```text
>INFO:OpenVPN Management Interface Version 5 -- type 'help' for more info
OpenVPN Version: OpenVPN 2.6.x
Management Interface Version: 5
>STATE:1762858323,CONNECTED,SUCCESS,10.8.0.6,198.51.100.10,1194,,
HEADER,CLIENT_LIST,Common Name,Real Address,Virtual Address,Bytes Received,Bytes Sent,Connected Since
CLIENT_LIST,alice,198.51.100.10:1194,10.8.0.6,84213,120944,2026-11-11 10:12:07
HEADER,ROUTING_TABLE,Virtual Address,Common Name,Real Address,Last Ref
ROUTING_TABLE,10.8.0.6,alice,198.51.100.10:1194,2026-11-11 10:15:02
GLOBAL_STATS,Max bcast/mcast queue length,0
END
SUCCESS: status command succeeded
```

下面逐行判读。第一行 `>INFO:` 是连接建立时进程主动推送的提示，带 `>` 前缀说明它是异步事件而非对某条命令的响应，`Management Interface Version 5` 给出协议版本，集成程序应据此判断可用命令集合；与外部程序发的 `version` 命令无关，不要把它当成 version 的回显。紧随其后的 `OpenVPN Version` 与 `Management Interface Version` 两行才是 `version` 命令的正常响应，可用于确认服务端版本与接口能力。`>STATE:` 行是本例最关键的一行：`CONNECTED` 表示隧道已建立，`SUCCESS` 是状态原因，`10.8.0.6` 是本地虚拟地址，`198.51.100.10` 与 `1194` 是对端地址端口，时间戳在前；健康状态下状态应是 `CONNECTED` 一类终态，若停留在 `CONNECTING`、`RECONNECTING`、`WAIT` 或出现 `AUTH_FAILED`、`GET_CONFIG` 长期不推进，就说明握手、认证或配置拉取卡住，需要回到 07-03、07-05 排查，而不是继续读状态文件。接下来的 `HEADER,CLIENT_LIST` 与 `CLIENT_LIST,alice,...` 是 `status 2` 的客户端列表：一行表头加一行数据，`alice` 是证书或认证得到的用户名，`10.8.0.6` 与前面 `>STATE` 一致可交叉验证，`Bytes Received`/`Bytes Sent` 是累计收发字节，长时间不增长而连接仍在，往往意味着数据通道不通或 MTU 黑洞。`HEADER,ROUTING_TABLE` 与 `ROUTING_TABLE` 行说明该客户端的虚拟地址已写入服务端实例路由表，若客户端已连上却没有对应路由行，后端网段访问会失败，属于 07-09 范畴。`GLOBAL_STATS` 是全局统计，`END` 标记本次 status 输出结束，最后 `SUCCESS: status command succeeded` 表示命令正常结束。综合来看，一段健康的输出应同时满足「版本可确认、状态为已连接、客户端列表与路由表各有一行、以 END 收尾」，把带 `>` 的实时行与不带前缀的命令响应分清，是写 management 集成程序的第一道基本功，也是排障时区分「接口读到旧快照」与「进程确实异常」的依据。

### 6. 注意事项、陷阱与最佳实践

第一，安全边界压倒一切。management 协议是明文、默认不强认证，TCP 形态务必绑定回环地址 `127.0.0.1` 或 `::1`，或改用受文件系统权限保护的 unix domain socket；若确需口令，启用密码文件并只给服务账号可读。绝不要把 management 端口暴露到公网或容器外可随意访问的网络，否则等于把踢除客户端、注入信号、读取状态的能力拱手让人。 unix socket 还要留意进程权限降级后是否仍可访问路径。

第二，分清实时推送与命令响应。带 `>` 前缀的行是进程主动推的事件，可能夹在任何命令的响应之间；集成程序不能用「发一条命令读一行」的同步假设去解析，必须按行分类处理，并对 `>STATE:`、`>PASSWORD:` 这类行做独立状态机。具体前缀拼写与字段个数需对照实际版本核验。

第三，`management-hold` 要与启动流程配合。开启后进程会按住连接、等外部放行才开始连对端，适合「先等配置或凭据就绪」的编排场景；但若外部系统没连上来或忘了发释放命令，VPN 会一直停住不工作，看起来像「进程活着却没流量」。上线前要把释放动作纳入编排的必经步骤并做超时兜底。

第四，订阅类命令要控制体量。`log` 全量订阅在高 verb 级别下会产生大量实时行，`bytecount` 采样间隔过密会增加处理开销，`echo` 订阅的参数范围也要收敛；监控采集器应只订阅真正需要的通道，并配合日志缓存一类参数平滑峰值，具体取值需对照实际版本核验。生产环境的日志分级与脱敏见 08-06。

第五，外部认证与凭据应答要做超时与失败兜底。`management-query-passwords`、`management-client-auth` 把认证结论交给外部系统，一旦外部程序卡住，客户端会悬在认证阶段；必须为应答设定超时路径，并明确失败时的拒绝策略，避免半开连接堆积。与脚本、插件三种凭据来源的选型见 07-05（模块见 07-05）。

第六，明确商业版与命令全集边界。以上监听形态、订阅、控制与外部认证都是社区版 `src/openvpn/manage.c` 内置能力；Access Server 的 Web UI、集群与集中管理不是社区版功能。全部 management 命令的逐项语法、返回格式与版本差异见 04-06（指令见 04-06），管理连接状态字段见 05-09（字段见 05-09），命令回注事件循环与实例查找见 06-02、06-10（原理见 06-02、原理见 06-10）。

### 7. 小结与延伸阅读

本篇把 management interface 定位为 OpenVPN 的管理面出入口：社区版 `src/openvpn/manage.c` 提供 TCP 与 unix domain socket 两种监听形态，以带 `>` 前缀的实时推送与请求—响应命令构成双向字节流，对外暴露状态订阅、计量与日志、运行时控制、客户端踢除、外部认证与凭据应答六类能力，并把控制结论回注主循环。最核心的实践结论是「管理面与数据面严格分离、明文接口只绑本机、实时行与命令响应分开解析、外部应答必须有超时兜底」。

延伸阅读按三条线走。想逐字段理解管理连接状态、订阅标志与待处理命令队列，读 05-09（字段见 05-09）；想跟清楚命令如何回注事件循环、服务端如何按客户端实例执行踢除、认证结论如何回推，读 06-02、06-10、06-11（原理见 06-02、原理见 06-10、原理见 06-11）；想查全 `management`、`management-hold`、`management-query-passwords`、`management-client-auth` 等启动参数以及 `status`、`state`、`bytecount`、`log`、`echo`、`kill`、`signal`、`client-kill`、`client-deny`、`hold` 等命令的逐项语法与返回格式，读 04-06（指令见 04-06）。凭据来源的另外两条路径见 07-05，脚本与插件的 defer 与环境变量见 07-07，status 文件与日志等辅助能力见 07-12，生产环境日志脱敏与监控见 08-06。以上六篇构成 07 册的前半部分，后半部分继续展开脚本与插件、多客户端服务端、路由桥接、DCO、压缩分片及辅助模块等主题。

## 07-07 脚本与插件模块

### 1. 背景与动机

要理解 OpenVPN 为什么专门设计一套脚本与插件扩展机制，得先回到它作为一个通用 VPN 引擎的处境：它无法内置每一种组织的认证后端与运维流程。有的单位要把用户名密码对接到 LDAP、RADIUS 或企业统一身份系统，有的要查业务数据库做二次校验，有的要在客户端上线时动态写防火墙规则、登记审计日志、给特定用户分配固定地址，还有的要接入一次性口令、短信网关乃至人工审批。这些逻辑因组织而异，且经常随管理政策变化，如果每来一种需求就改一次 C 源码、重新编译部署，既不现实也不安全；把它们硬塞进主配置又会迅速演变成一堆互相嵌套的条件分支。于是社区版在连接生命周期的关键节点预留了两类扩展出口：一类是脚本钩子，即在特定事件发生时由主进程去执行一个外部可执行文件；另一类是插件，即让主进程在启动时动态加载一个共享库，按约定的 C 接口在进程内回调。二者共同构成了 OpenVPN 与外界系统之间的粘合层，也是它从"一条隧道"变成"可集成平台"的关键。

两类出口的取舍，是选型的起点。脚本语言无关，Shell、Python、Perl 乃至编译好的二进制都能写，改起来快、隔离性好，单个脚本崩溃最多影响本次调用而不波及主进程；但每次调用都要经历 fork 加 exec、构造环境变量集合、等待退出码，在客户端频繁上下线或认证量很大的高并发服务端里，进程创建开销会明显累积。插件运行在进程内，调用几乎没有进程切换成本，还能长期持有状态、连接池与缓存，适合高频认证；代价是必须用 C 或兼容 C ABI 的语言编写，与主进程共享地址空间，一旦出现段错误、内存越界或死锁就会直接拖垮整个 VPN 进程，升级主版本时还要保证接口与头文件匹配。换句话说，脚本换来的是隔离与灵活，插件换来的是性能与状态保持，二者没有绝对优劣，只有场景适配。

第三个动机是安全边界。脚本与插件能看到的东西远比普通配置敏感：证书通用名、客户端真实地址、隧道内分配到的虚拟地址，乃至用户提交的明文口令。早期版本曾因默认允许外部程序、且把凭据随手放进环境变量而带来提权与信息泄露风险，因此引入了 `script-security` 这样的显式分级开关，把"能不能调用外部程序""能不能把密码类变量交给脚本"变成运维必须主动决策、逐档放开的选项，而不是默认打开的后门。本篇把这条边界作为重点之一，因为扩展能力用得越深，误配的代价越大。

照例先划清边界与去重。本篇是 07 册模块功能与组网的权威源，讲"有哪些扩展出口、各自适合什么场景、defer 异步认证解决什么问题、安全边界怎么划"；全部脚本钩子名称、调用时机、逐项语法与环境变量全集由 04-05 给出（指令见 04-05）；环境变量集合如何构造、认证结论如何回注 TLS 状态机属于机制，见 06-02 与 06-06（原理见 06-02、原理见 06-06）；环境变量集合、插件句柄与每客户端上下文等对象的字段见 05-09（字段见 05-09）。本篇配置段只列最典型的几条指令，绝不重列指令全集。还需强调商业版边界：社区版只覆盖 `src/openvpn/` 主线与 `src/plugins/` 下的内置示例，Access Server 的 Web 管理界面、集群与集中用户管理不是社区版能力，不能因为都能"对接用户"就画等号。

### 2. 核心概念

第一组概念是钩子类型，按触发时机可分三类。其一是进程与隧道生命周期类，如 up、ipchange、route-up、down，分别在虚拟设备建立、地址发生变化、路由就绪、隧道关闭时触发，常用来下发自定义路由、写 iptables 或 nftables 规则、登记连接日志。其二是客户端连接生命周期类，如 client-connect、client-disconnect、learn-address，服务端模式下每个客户端实例建立、销毁或学到地址时触发，用来做 per-client 的个性化配置与审计。其三是认证与校验类，如 auth-user-pass-verify、tls-verify、client-crresponse，分别在用户名口令校验、证书链校验、挑战应答阶段触发，用来对接外部认证后端。以上只是典型钩子的点名，完整清单、每个钩子的触发条件与参数形式一律见 04-05（指令见 04-05）。

第二组概念是插件 API 的契约。插件按 `src/openvpn/plugin.h` 暴露的一组函数与主进程对接：初始化时主进程调用 open 类型的入口，把配置参数与"关心的事件类型掩码"传给插件；事件发生时调用 func 类型的入口，并带上该事件的类型、环境变量数组与可选的每客户端句柄；卸载或异常时调用 close、abort 一类入口释放资源。函数命名带有版本后缀（如 v1、v3），确切签名、类型掩码常量（形如 `OPENVPN_PLUGIN_UP`、`OPENVPN_PLUGIN_AUTH_USER_PASS_VERIFY`）、以及 `OPENVPN_PLUGIN_MASK` 一类宏的拼写都需对照 `src/openvpn/plugin.h` 核验，不要凭记忆写死。func 入口的返回值决定结论，大体是成功、失败、以及"延后给结论"三种，其中"延后"正是异步认证的基础。插件示例实现可参考 `src/plugins/auth-pam/` 与 `src/plugins/down-root/`。

第三组概念是脚本环境变量与上下文。脚本不是被凭空调用的，主进程会把当前事件相关的信息组织成一组环境变量传进去：`script_type` 说明这次是哪个钩子，`common_name` 给出证书通用名，`trusted_ip` 与 `untrusted_ip` 一类变量区分已认证与未认证的来源地址，`ifconfig_pool_remote_ip` 一类变量给出分配到的隧道地址，`session_state`、`auth_control_file` 一类变量则服务于 defer 流程。脚本据此判断"我是谁、谁在连、分配到什么地址、该把结论写到哪里"。完整变量清单见 04-05（指令见 04-05）；环境变量集合的构造时机、传参路径与内存归属属于机制，见 06-02（原理见 06-02）。

第四组概念是 defer 异步认证。同步钩子里，主进程必须一直等到脚本或插件返回才能继续，而外部认证往往要查数据库、请求短信网关、等待人工审批，耗时从数百毫秒到数秒不等。OpenVPN 服务端是单线程事件循环模型（原理见 06-02），一个慢钩子会把所有已连接客户端一起卡住，表现成"整个 VPN 周期性停顿"。defer 机制让钩子先返回一个"暂不结论"的状态，主进程把该客户端挂起、继续服务其他客户端；外部逻辑在后台完成校验后，把允许或拒绝写进约定的控制文件（或通过相应接口回注），主进程再恢复该客户端的认证流程。这样慢认证就从"阻塞全局"变成"只阻塞一个会话"，是高并发服务端对接外部认证的关键能力。脚本侧常见做法是在 `auth-user-pass-verify ... via-file` 模式下把结论写入 `auth_control_file` 指向的文件，具体取值、文件协议与超时窗口需对照实际版本核验。

第五组概念是 `script-security` 分级。它把"调用外部程序"这一能力按风险切成几档：从完全禁止、只允许内置网络配置命令、允许自定义脚本，到允许把明文口令通过环境变量传给脚本。分级数字与每一档的精确语义在不同版本间可能有调整，需对照 `src/openvpn/options.c` 与实际版本的帮助输出核验；但原则不变——默认最低权限，只在确有需要时逐档放开，且尽量不要让密码类变量进入脚本环境。以上扩展出口与主进程、外部系统的协作关系见图 07-07-01。

| 实现语言 | Shell \| Python \| 任意可执行 | C 或兼容 C ABI 的语言 |
| 调用方式 | fork 加 exec 外部进程 | 进程内动态加载回调 |
| 单次开销 | 较高，含进程创建 | 低，无进程切换 |
| 故障隔离 | 崩溃只影响本次调用 | 崩溃可能拖垮主进程 |
| 状态保持 | 靠外部文件或缓存 | 可在进程内长期持有 |
| 敏感信息 | 经环境变量与参数传递 | 经参数与句柄传递 |
| 适用场景 | 运维脚本、低频事件 | 高频认证、连接池复用 |

需要强调，本节只是能力地图，不是字段手册也不是机制剖析：环境变量集合、插件句柄、每客户端上下文的字段定义见 05-09（字段见 05-09）；钩子如何被登记进事件集、认证结论如何回注 TLS 状态机见 06-02 与 06-06（原理见 06-02、原理见 06-06）；全部钩子名称、调用时机、参数形式与返回约定见 04-05（指令见 04-05）。把三层内容分开，是本套资料避免重复的关键约定。

### 4. 关键流程与调用链

从模块协作角度，一次脚本或插件调用大致串起六步，这里只讲各模块之间交接什么，不展开每一步内部的状态机与逐行实现。第一步，启动阶段解析配置，把钩子路径、插件路径、`script-security` 级别登记到运行态配置对象（字段见 05-03），插件路径在此刻被动态加载并调用初始化入口，声明自己关心的事件类型掩码。第二步，某个生命周期或认证事件发生，触发点可能是虚拟设备就绪、客户端实例建立、证书链校验或用户名口令提交。第三步，主进程为本次调用构造上下文：整理环境变量集合、填充事件类型、准备可选的控制文件路径与每客户端句柄。第四步，按配置分流执行：脚本路径 fork 加 exec 并等待退出码，插件路径直接调用 func 入口并接收返回值。第五步，读取结论——脚本看退出码或控制文件内容，插件看返回值；成功则放行，失败则拒绝该客户端并记日志。第六步，若返回的是"延后"，主进程把该会话挂起到待决队列，继续服务其他客户端，等后台把允许或拒绝写入控制文件后再恢复认证（该挂起与恢复的具体时机属于机制，见 06-02 与 06-06，原理见 06-02、原理见 06-06）。

插件侧给出一个最小骨架，演示 func 入口与"延后"返回值的用法。入口函数名、结构体成员、类型掩码常量与返回值的确切拼写需对照 `src/openvpn/plugin.h` 核验；这里只示意调用契约，不展开内部机制。

```c
#include "openvpn-plugin.h"

/* 入口原型、结构成员与常量以 plugin.h 为准，需对照实际版本核验 */
static int
on_event(const int type, const char *envp[])
{
    if (type == OPENVPN_PLUGIN_AUTH_USER_PASS_VERIFY)
    {
        /* 外部校验放到后台，先返回延后，避免阻塞事件循环 */
        return OPENVPN_PLUGIN_FUNC_DEFERRED;
    }
    return OPENVPN_PLUGIN_FUNC_SUCCESS;
}

int
openvpn_plugin_func_v3(const int v3structver,
                       struct openvpn_plugin_args_func_in_t const *in,
                       struct openvpn_plugin_args_func_out_t *out)
{
    out->return_list = NULL;
    return on_event(in->type, in->envp);
}
```

下面对这段输出逐行判读。首行 `PLUGIN_INIT` 说明插件在启动阶段被成功加载并完成初始化，如果这条缺失而配置里写了 `plugin`，多半是共享库路径错误、接口版本与主进程不匹配或依赖库缺失，应回到 `src/openvpn/plugin.c` 的加载日志继续看。第二行 `TLS: Initial packet` 标志着一个客户端握手开始，是后续所有认证事件的起点。第三行 `AUTH_USER_PASS_VERIFY: deferred authentication` 是本篇最关键的一行：它说明认证钩子没有同步给结论，而是走了 defer 路径，主进程已把该会话挂起；健康情况下这条之后不应立刻出现拒绝或超时，若日志在此停滞数秒后出现 `AUTH_FAILED` 或认证超时一类字样，则说明后台校验未在允许窗口内回注结论，需要检查外部系统可达性与超时设置。第四行是插件自己打印的后台校验启动记录，证明外部认证确实被触发而非钩子被跳过。第五行 `auth_control_file result: 1` 表示控制文件被写入了允许结论，`1` 为放行、`0` 为拒绝，具体取值需对照实际版本核验；这一行是 defer 链路闭环的证据。第六行 `PLUGIN_CALL ... status=SUCCESS` 是插件返回结论后的汇总，`status=ERROR` 或状态长期停留在延后都属异常，前者意味插件判定失败，后者意味挂起未被恢复。末行 `MULTI: primary virtual IP` 说明客户端最终通过认证、进入地址分配与实例建立阶段，隧道内虚拟地址为 `10.8.0.6`。综合来看，一段健康的 defer 认证日志应同时满足"插件已加载、明确出现 deferred、后台校验与结论回注成对出现、最终分配虚拟地址"四个条件，把同步结论与延后结论分清，是排查"客户端卡在认证"这类问题的第一道基本功。

### 6. 注意事项、陷阱与最佳实践

第一，`script-security` 按最小权限放开。默认应停留在最低可用档，仅为满足自定义脚本才逐档提升；能让脚本从受控文件读取凭据，就不要把明文口令放进环境变量。允许密码入环境变量的最高档风险最大，一旦脚本被替换、环境变量被子进程继承或被日志打印，口令即泄露。档位数字与语义需对照 `src/openvpn/options.c` 与实际版本核验。

第二，同步钩子绝不能做慢操作。OpenVPN 服务端是单线程事件循环（原理见 06-02），一个耗时的同步脚本会把所有已连接客户端一起卡住，表现为"整个 VPN 周期性停顿"。凡是要查库、请求外部网关、等待人工审批，一律走 defer 异步认证，把阻塞限制在单个会话。

第三，defer 要有超时与容量兜底。被挂起的会话会占用实例表、地址池条目与控制文件句柄（字段见 05-08、字段见 05-09），若外部系统长期不回注，半开连接会堆积，直至触发实例上限水位。必须为后台校验设定超时路径与明确的失败拒绝策略，并监控待决队列长度，避免"进程活着却谁也连不上"。

第四，防注入：环境变量与参数都是不可信输入。`common_name`、`username`、`untrusted_ip` 等来自对端或证书，脚本里绝不能直接拼进 shell 命令或文件路径，尤其 ccd 文件名由通用名派生时更要防路径穿越（模块见 07-08）；应做白名单校验、引号包裹与长度限制。把外部输入当数据而非代码，是写钩子脚本的底线。

第五，插件要管好接口、崩溃与资源。插件与主进程共享地址空间，段错误、内存泄漏、阻塞式锁都会直接拖垮 VPN 进程；升级主版本后要重新编译并用同版本头文件核验函数签名与类型掩码常量，卸载路径要释放每客户端句柄与连接池，避免长期运行后内存缓慢增长。内置示例见 `src/plugins/auth-pam/` 与 `src/plugins/down-root/`。

第六，文件权限与商业版边界。脚本与插件文件必须限定属主与可写权限，任何"普通用户可写"的脚本路径都等价于提权后门；`down` 类钩子若需要高权限，应参考 `src/plugins/down-root/` 的受控提权模式，而不是把整个进程长期跑在 root 下。以上扩展能力都是社区版 `src/openvpn/plugin.c` 与 `src/plugins/` 的内置特性，Access Server 的 Web 界面、集群与集中用户管理不属于社区版；全部钩子、环境变量与参数见 04-05（指令见 04-05），认证结论回注机制见 06-06（原理见 06-06）。

### 7. 小结与延伸阅读

本篇把脚本与插件模块定位为 OpenVPN 从封闭引擎走向可集成组件的粘合层：`src/openvpn/plugin.c` 提供进程内插件回调，`src/openvpn/misc.c` 一类文件构造脚本环境变量（拆分情况需核验），defer 把慢认证从全局阻塞降为单会话挂起，`script-security` 为这一切划出显式安全边界。选型结论很清晰：低频运维动作与快速对接用脚本，高频认证与需要长驻状态用插件；凡慢操作一律 defer；权限按最小档放开，外部输入一律当不可信数据处理。

延伸阅读建议按三条线走。想查全部钩子名称、调用时机、参数形式与环境变量全集，读 04-05（指令见 04-05）；想逐字段理解环境变量集合、插件句柄与每客户端上下文，读 05-09（字段见 05-09）；想跟清楚事件循环如何登记钩子、认证结论如何回注 TLS 状态机，读 06-02 与 06-06（原理见 06-02、原理见 06-06）。认证方式选型见 07-05，服务端多客户端实例与 ccd 见 07-08，management 实时接口见 07-06，生产日志脱敏与脚本权限管理见 08-06。

## 07-08 多客户端服务端与 ccd 模块

### 1. 背景与动机

点对点模式下一个进程只能伺候一个对端：一对配置文件、一条隧道、一个虚拟地址，适用于站点到站点的固定链路。但远程接入的真实需求是"一台服务端、成百上千个移动客户端"，如果每来一个用户就起一个进程、占一个端口、维护一套配置，端口资源、内存、证书分发与日常运维都会迅速失控。于是社区版提供了多客户端服务端模式：单个进程、单个监听套接字，靠 TLS 握手得到的证书通用名与客户端真实地址区分不同客户端，为每个客户端维护一份独立的实例状态，再从共享地址池里给它分配隧道内地址。这个从"一条链路"到"一片接入"的转变，是 OpenVPN 服务端部署的常态，本篇讲的就是撑起它的这套模块能力。

这个转变立刻带来三个新问题。第一，虚拟地址从哪来、断开后如何回收、客户端重连要不要尽量拿回原地址，才能和防火墙规则、审计记录按地址对齐；第二，不同客户端往往需要不同待遇——有的要固定虚拟地址，有的要把自己身后的局域网网段宣告给服务端，有的要被推送特定路由或 DNS，这些"按客户端差异化"的配置显然不能塞进一份全局配置；第三，多个客户端之间、客户端与服务端后端之间如何互访，路由表怎么按实例区分，而不是所有流量都走同一条路。地址池、per-client 实例与 ccd（client-config-dir）目录，正是为回答这三个问题而存在。

把相关模块串起来看，层次会更清楚：07-02 的 link socket 提供单端口复用入口，07-06 的 management 提供运行时查询与控制，07-09 的路由模块负责把后端网段引到具体实例，07-12 的 status 文件提供周期性快照，07-07 的脚本与插件钩子负责在客户端上下线时插入自定义动作。本篇聚焦"服务端如何同时 hold 住多个客户端、如何给每个客户端做个性化配置、以及 `duplicate-cn` 这类开关的风险"，是组网与选型的权威源。

照例划清边界与去重。全部服务端与客户端模式指令的逐项语法由 04-04 给出（指令见 04-04）；实例查找哈希、配置推送与路由下发属于机制，见 06-10 与 06-11（原理见 06-10、原理见 06-11）；`multi_context`、`multi_instance` 与地址池对象的字段见 05-08（字段见 05-08）。还需提醒商业版边界：社区版 `src/openvpn/multi.c` 主线不提供 Access Server 的 Web 界面、集群与集中许可管理，不要把"多客户端服务端"和商业版集群画等号。本篇配置段只列最典型的几条指令，其余写完整指令族见 04-04，绝不重列。

### 2. 核心概念

第一组概念是 `mode server` 与 `server` 宏。多客户端服务端并非单一开关，而是一组行为的组合：以 server 角色参与 TLS、启用地址池、按 topology 组织虚拟网段、向客户端推送默认路由与 DNS 等。`server` 指令是一个便捷宏，展开后等价于 `mode server`、`tls-server`、地址池与若干 `push` 指令的组合；展开出的确切指令集合与默认值需对照 `src/openvpn/options.c` 核验，不要凭记忆罗列。理解"它是宏而非原语"，有助于解释为什么手动逐条拼配置时容易漏项，以及为什么改一个宏参数会连带影响拓扑与推送。

第二组概念是地址池 `ifconfig-pool`。服务端持有一段虚拟网段，客户端连入时从中分配一个地址，断开后回收；`ifconfig-pool-persist` 可把"通用名到地址"的映射写到文件，让重连尽量复用原地址，便于防火墙规则与审计按地址对齐。地址池实现集中在 `src/openvpn/pool.c`，它与 topology（`net30`、`p2p`、`subnet`）紧密相关，`topology subnet` 是现代部署的默认选择，因为它给每个客户端一个真实子网地址，而不再像 `net30` 那样为每对端点浪费一个 /30 段。地址池与实例对象的字段见 05-08（字段见 05-08）。

第三组概念是 per-client 实例与查找。服务端为每个已认证客户端建立一个实例，按证书通用名或真实地址做键放进哈希表，该客户端的虚拟地址、路由、推送配置与密钥状态都挂在实例上。同一个 UDP 套接字上收到的密文，靠外层地址与内部会话标识分派到对应实例（该查找属于机制，见 06-10，原理见 06-10）。`max-clients` 限制实例总数，是容量水位的第一道闸；`client-to-client` 决定是否允许客户端之间经服务端互访，默认隔离更安全。

第四组概念是 ccd 目录。`client-config-dir` 指向一个目录，服务端在客户端连入时按通用名查找同名文件，把文件内容当作该客户端专属的配置片段执行。典型用途有三类：用 `ifconfig-push` 给特定客户端固定虚拟地址；用 `iroute` 宣告该客户端身后的后端网段，让服务端把去往这些网段的流量导向该实例；用 `push` 给该客户端单独推送路由、DNS 或其他选项。ccd 是"按人下菜碟"的核心，也是站点到站点分支接入的标准做法，相关组网细节见 07-09。

第五组概念是 `duplicate-cn` 与身份唯一性。默认假设一个通用名同时只能有一个连接，重连会顶掉旧实例；开启 `duplicate-cn` 允许同一证书从多个设备并发连入。它在"同一用户多终端"场景里有诱惑力，但会立刻带来地址与路由的歧义：两个实例抢同一通用名、ccd 里配置的 `iroute` 指向谁、固定地址 `ifconfig-push` 给谁、审计日志算谁，都会变得不确定。这是本模块最需要审慎评估的开关，第 6 节会展开。以上模块协作关系见图 07-08-01。

### 4. 关键流程与调用链

从模块协作角度，一个客户端从连入到断开大致串起六步，这里只讲各模块之间交接什么。第一步，启动阶段按 server 宏展开出的参数初始化监听套接字、虚拟网段、地址池与实例哈希表，并按需加载 `ifconfig-pool-persist` 恢复历史映射。第二步，客户端 TLS 握手到达，服务端从证书中提取通用名与真实地址，作为实例的身份键。第三步，按身份键查实例表：没有则新建实例，从地址池分配虚拟地址，有则按配置决定是复用还是顶替。第四步，读取 ccd 目录中与通用名同名的文件，把其中的 `ifconfig-push`、`iroute`、`push` 等 per-client 指令合并进该实例的配置上下文。第五步，生成推送列表下发给客户端，并把 `iroute` 形成的后端网段路由登记进实例路由表，使数据面知道去往该网段的包该交给哪个实例（推送与路由构建属于机制，见 06-11，原理见 06-11）。第六步，客户端断开或超时后销毁实例、回收地址、更新持久化文件，并触发 client-disconnect 一类钩子（模块见 07-07）。

### 5. 配置/命令/代码实例

按去重约定，这里只列本模块最典型的几条指令，其余交给 04-04（指令见 04-04，完整指令族见 04-04）。下面这段配置展示的是"subnet 拓扑 + 地址池持久化 + ccd 目录 + 实例上限"这一标准服务端组合；`server` 宏展开出的默认值需对照实际版本核验。

```conf
server 10.8.0.0 255.255.255.0
topology subnet
client-config-dir /etc/openvpn/ccd
ifconfig-pool-persist /var/lib/openvpn/ipp.txt 0
max-clients 100
```

ccd 目录里放一份以客户端通用名命名的文件，例如为 `branch-shanghai` 这个客户端固定地址并宣告其身后网段。文件名即通用名，内容与主配置同语法，但只对该客户端生效。

```ini
ifconfig-push 10.8.0.10 255.255.255.0
iroute 192.168.30.0 255.255.255.0
push "route 10.8.0.0 255.255.255.0"
```

验证实例是否按预期建立、地址是否按 ccd 固定、以及是否有重复通用名连入，最方便的是读一份 status 文件快照。下面给出查询命令，随后是典型输出。示例输出，具体格式需对照实际版本核验；`status-version` 不同档位的列名、字段个数与分隔符会有差异。

```bash
sed -n '1,30p' /var/run/openvpn/server.status
```

```text
OpenVPN CLIENT LIST
Updated,2026-11-11 10:15:02
Common Name,Real Address,Bytes Received,Bytes Sent,Connected Since
branch-shanghai,198.51.100.22:1194,312044,289110,2026-11-11 09:41:17
alice,198.51.100.10:1194,84213,120944,2026-11-11 10:12:07
ROUTING TABLE

10.8.0.10,branch-shanghai,198.51.100.22:1194,2026-11-11 10:14:55
192.168.30.0/24,branch-shanghai,198.51.100.22:1194,2026-11-11 10:14:55
10.8.0.6,alice,198.51.100.10:1194,2026-11-11 10:15:01

Max bcast/mcast queue length,0
END
```

下面对这段输出逐行判读。首行 `OpenVPN CLIENT LIST` 与 `Updated` 时间戳说明这份快照的刷新时刻，运维应重点看时间戳是否持续前进——若进程还活着但时间不再更新，往往是 status 写入被阻塞或进程卡死，需要回到 07-12 排查。紧随的表头列出通用名、真实地址、累计收发字节与连入时间。数据行里 `branch-shanghai` 与 `alice` 各占一行，表示服务端当前 hold 住两个实例；`Bytes Received` 与 `Bytes Sent` 是累计量，健康状态下会随业务增长，长时间不涨而连接仍在，通常指向数据通道不通或 MTU 黑洞（模块见 07-11）。`ROUTING TABLE` 段是本篇最该细看的部分：`10.8.0.10,branch-shanghai` 说明地址池确实按 ccd 里的 `ifconfig-push` 给该客户端分配了固定地址，而不是随机池地址，这正是 ccd 生效的证据；紧接着 `192.168.30.0/24,branch-shanghai` 是 `iroute` 登记进实例路由表的结果，意味着服务端已知道去往该后端网段的包要交给 `branch-shanghai` 实例，缺这一行则站点到站点分支网段永远不可达（组网见 07-09）。`10.8.0.6,alice` 是普通客户端从地址池拿到的地址。`GLOBAL STATS` 与 `END` 标记快照收尾。若启用 `duplicate-cn`，同一通用名可能在 CLIENT LIST 里出现多行、ROUTING TABLE 里出现互相冲突的地址或网段，这正是该开关风险的直观表现：审计与路由归属都变得不确定。综合来看，一份健康快照应同时满足"时间戳在刷新、通用名与预期一致、固定地址与 iroute 各有一行、无重复通用名冲突行"，这也是核对 ccd 与地址池是否按设计工作的最快方法。

### 6. 注意事项、陷阱与最佳实践

第一，`duplicate-cn` 谨慎开启。默认身份唯一性是有意的保护：同一证书并发会让 `ifconfig-push` 固定地址、`iroute` 后端网段、审计归属与计费全部产生歧义，重连还可能互相顶替。确需"一人多终端"时，更稳妥的做法是为每个设备签发独立证书，而不是放开 `duplicate-cn`；若必须开启，要同步评估 ccd 文件是否被多个实例共享以及地址池容量是否够用。

第二，ccd 文件名来自证书通用名，必须防路径穿越。服务端按通用名拼接目录路径读取文件，若通用名里含 `../`、斜杠或超长字符，就可能读到目录外的文件，构成越权读取；应启用证书校验阶段的通用名字符约束与 `verify-x509` 一类名称校验（模块见 07-04），并限定 ccd 目录权限。把通用名当不可信输入处理，与 07-07 的脚本注入防线是同一条原则。

第三，`ifconfig-push` 与地址池要划清边界。固定地址应落在池网段内但不与自动分配冲突，否则新客户端可能被分到已占用的地址；使用 `topology subnet` 时还要保证掩码与拓扑一致。持久化文件 `ipp.txt` 所在目录必须有写权限且只给服务账号，异常退出后的残留映射要能人工核对，避免"地址明明没人在用却分配不出去"。

第四，`iroute` 与 `route` 别混为一谈。ccd 里的 `iroute` 是"服务端内部把某网段指向这个实例"，`push "route ..."` 或全局 `route` 是"告诉客户端去往某网段走隧道"；站点到站点场景两者缺一不可，这也是 07-09 的重点。只配 `iroute` 不推送路由，客户端不知道怎么走；只推送路由不配 `iroute`，服务端不知道往哪交。

第五，容量与隔离要一起定。`max-clients` 要按内存、文件描述符与地址池大小设水位，配合 `client-to-client` 决定是否允许客户端互访——默认隔离更安全，放开后等于把服务端变成客户端之间的交换机，需在防火墙侧另做约束；容量水位与监控指标见 08-02。

第六，明确边界与去重。以上地址池、实例、ccd 与推送都是社区版 `src/openvpn/multi.c`、`src/openvpn/pool.c` 的内置能力；Access Server 的集群、Web 管理与集中许可不是社区版功能。全部服务端模式指令见 04-04（指令见 04-04），实例与地址池字段见 05-08（字段见 05-08），实例查找、推送与路由下发机制见 06-10、06-11（原理见 06-10、原理见 06-11）。

### 7. 小结与延伸阅读

本篇把多客户端服务端模块定位为"一个进程、一个监听套接字撑起整片远程接入"：`server` 宏把一组行为打包，`src/openvpn/pool.c` 管地址分配与持久化，`src/openvpn/multi.c` 按通用名维护实例表，ccd 目录按客户端合并个性化配置，`iroute` 把后端网段挂到具体实例。选型结论很清晰：默认 `topology subnet`、默认身份唯一、按设备签独立证书，ccd 只放真正需要差异化的客户端，`duplicate-cn` 能不用就不用。

## 07-09 路由与桥接模块

### 1. 背景与动机

隧道建立只解决了"两端能加密通信"，并不等于"能访问到想访问的网段"。客户端连上服务端之后，去往服务端后端局域网的报文默认仍按本机物理网卡的默认路由走，根本不知道该改走隧道；反过来，服务端收到去往某个客户端身后分支网段的报文，也不知道该交给哪一个客户端实例。路由模块就是把"隧道这条链路"真正接进两端真实路由表的那套能力，它决定了一个已经连通的 VPN 到底能通向哪里。很多部署在握手成功、日志显示已连接之后才发现业务不通，根因往往不在加密或证书，而在这一层。

需求可以拆成方向不同的三类。第一类是客户端访问服务端后端网段，靠 `route` 或服务端 `push "route ..."` 把目标网段引到隧道；第二类是把客户端的全部上网流量都塞进隧道，靠 `redirect-gateway` 改写默认路由，常见于公共 Wi-Fi 下的安全接入；第三类是服务端访问某个客户端身后的分支网段，靠 ccd 里的 `iroute` 把该网段登记到具体客户端实例。三者方向不同、指令不同、生效位置也不同，混用或漏配是最高频的排障来源，本篇第 6 节会重点拆解。

另一条分野是组网模型。tun 路由模式靠三层路由把网段引到隧道，扩展性好、开销低，是绝大多数场景的默认；tap 桥接模式靠二层把远端主机接进同一个广播域，能让依赖广播、组播或非 IP 协议的老应用原样透传，但会拉大广播域、地址池与网桥配置复杂、无用流量占用带宽。07-01 已从设备层讲过 tun 与 tap 的选型，本篇则从路由与桥接的组网能力角度补全"选了之后怎么把网段接通"。

照例划清边界与去重。本篇是模块功能与组网的权威源，讲"有哪些路由方向、push 与 iroute 各自管什么、redirect-gateway 怎么改默认路由、tap 桥接怎么组网、选型怎么定"；全部相关指令的逐项语法由 04-02 与 04-04 给出（指令见 04-02、指令见 04-04）；路由推送、ifconfig 与拓扑构建、实例路由表如何生成属于机制，见 06-11 与 06-10（原理见 06-11、原理见 06-10）；`route_list`、`push_list` 等对象的字段见 05-09（字段见 05-09）。本篇配置段只列最典型的几条指令。商业版边界同样要点明：社区版 `src/openvpn/route.c` 主线不提供 Web 界面、集群与集中策略下发，Access Server 的图形化路由管理不是社区版能力。

### 2. 核心概念

第一组概念是 `route` 与 `push "route ..."` 的分工。前者是客户端在自己本机路由表里加一条静态路由，后者是服务端把一组配置通过 push 列表下发给客户端，客户端接收后解析执行。OpenVPN 采用 pull 模型：客户端连入后发一个拉取配置的请求，服务端把 push 列表回给它，客户端再据此配置地址、路由与 DNS（该请求与回推属于机制，见 06-11，原理见 06-11）。若客户端不想接受服务端推送，可用 `route-nopull` 一类指令忽略推送、改由本地脚本自定义路由，逐项用法见 04-04。理解"push 是服务端说、route 是客户端做"，是理清双向路由的第一步。

第二组概念是 `redirect-gateway` 与默认路由。它把客户端的默认路由改指向隧道，实现全流量入隧道。常见写法带 `def1` 参数：不是删除原默认路由再替换，而是新增两条 /1 网段路由（覆盖 `0.0.0.0/1` 与 `128.0.0.0/1`），因为前缀比 /0 更具体，路由选择时优先命中，同时又保留了原默认路由，避免把"VPN 报文本身该从物理网卡出去"的出口路由一并冲掉、导致隧道立刻断流。`bypass-dhcp`、`bypass-dns` 一类参数用于保留本地 DHCP 或 DNS 服务器的直连路由，具体参数名与取值需对照 `src/openvpn/options.c` 与实际版本核验。全流量入隧道后还要特别留意 DNS：若 DNS 查询仍走本地解析，就会出现"流量进了隧道、域名解析却暴露在外"的泄露问题。

第三组概念是 `iroute`，它和前两组完全不在同一侧。ccd 文件里的 `iroute` 是服务端内部路由：告诉服务端"去往这个网段的包，交给当前这个客户端实例"。它必须放在按通用名命名的 ccd 文件里才与具体客户端绑定（模块见 07-08），且几乎总要与 `push "route ..."` 或 `route` 成对出现：只配 `iroute` 不推送路由，客户端不知道去往分支网段该走隧道；只推送路由不配 `iroute`，服务端不知道该把包交给谁。三者方向与生效位置的对照见本节末尾的图 07-09-01。

第四组概念是 tap 桥接组网。此时设备是二层 tap，服务端用 `server-bridge` 一类参数配合系统网桥（Linux 上把 tap 接口加进网桥，工具为 brctl 或 ip link），把远端主机桥进与服务端内网相同的二层广播域，DHCP、ARP、NetBIOS 广播都会穿过隧道。它适合确有二层互通需求的场景，代价是广播域被拉大、易起环路与广播风暴，地址池与网桥配置也更复杂；`dev tap` 与设备驱动的平台差异见 07-01。

第五组概念是路由下发后端与转发前提。`src/openvpn/route.c` 负责路由增删与拓扑的公共逻辑，真正把路由写进操作系统交给两个后端：现代 Linux 优先用基于 netlink 的 `src/openvpn/networking_sitnl.c`，精简环境则调用外部 `ip` 命令的 `src/openvpn/networking_iproute2.c`；`src/openvpn/list.c` 存放 route_list 与 push_list 容器（字段见 05-09）。此外服务端要转发不同网段之间的流量，内核转发开关 `net.ipv4.ip_forward` 必须打开，`client-to-client` 才允许客户端之间经服务端互访。以上路由方向与组网关系见图 07-09-01。

### 4. 关键流程与调用链

从模块协作角度，一条"客户端访问服务端后端网段"的路由大致串起六步，这里只讲各模块之间交接什么。第一步，启动阶段解析服务端配置里的 `route`、`push`、`redirect-gateway` 以及 ccd 中的 `iroute`，把它们登记进相应列表（字段见 05-09）。第二步，客户端连入并发起 pull 配置请求。第三步，服务端把全局 push 列表与 ccd 增量合并，生成一份针对该客户端的推送列表（合并与序列化属于机制，见 06-11，原理见 06-11）。第四步，客户端接收并解析推送列表，得到应下发的路由项。第五步，客户端调用路由后端把路由写进本机路由表：netlink 后端直接构造 netlink 消息，iproute2 后端调用外部 `ip` 命令。第六步，数据面转发时，服务端按实例路由表里 `iroute` 登记的后端网段，把去往该网段的包交给对应客户端实例。桥接模式是一条旁路：tap 接口被加进系统网桥，二层帧按网桥转发而非逐条三层路由。以上与事件循环、实例查找的衔接属于机制，见 06-02 与 06-10（原理见 06-02、原理见 06-10）。

### 5. 配置/命令/代码实例

按去重约定，这里只列本模块最典型的几条指令，其余交给 04-02 与 04-04（指令见 04-02、指令见 04-04，完整指令族见 04-04）。下面这段服务端配置展示的是"向客户端推送后端网段 + 重定向默认路由 + 启用 ccd"这一常见组合；`bypass-dhcp` 一类参数名需对照实际版本核验。

```conf
server 10.8.0.0 255.255.255.0
push "route 192.168.20.0 255.255.255.0"
push "redirect-gateway def1 bypass-dhcp"
client-config-dir /etc/openvpn/ccd
```

ccd 目录里为某个分支客户端宣告其身后网段，文件名即该客户端通用名，内容只有一条 `iroute`：

```ini
iroute 192.168.30.0 255.255.255.0
```

验证路由是否真正下发到客户端，最直接的办法是看本机路由表。下面给出查询命令，随后是典型输出。示例输出，具体格式需对照实际版本核验；不同内核、不同 iproute2 版本的字段顺序、metric 显示与路由标记会有差异。

```bash
ip route show | grep -E 'tun0|10.8.0|192.168.20|0.0.0.0/1'
```

```text
0.0.0.0/1 via 10.8.0.1 dev tun0
128.0.0.0/1 via 10.8.0.1 dev tun0
192.168.20.0/24 via 10.8.0.1 dev tun0
10.8.0.0/24 dev tun0 proto kernel scope link src 10.8.0.6
default via 192.168.1.1 dev eth0 metric 100
```

下面对这段输出逐行判读。前两行 `0.0.0.0/1` 与 `128.0.0.0/1` 是 `redirect-gateway def1` 生效的标志：两条 /1 网段合起来覆盖整个地址空间，前缀比 /0 更具体，因此路由选择时优先于第五行的原 `default`，同时又没有删除原默认路由，VPN 报文本身仍能从 `eth0` 出去，隧道不会因出口被冲掉而断流；如果这里只看到一条 `default ... dev tun0` 而没有两条 /1，说明没带 `def1` 或客户端侧解析不同，需对照实际版本核验。第三行 `192.168.20.0/24 via 10.8.0.1 dev tun0` 是 `push "route"` 下发成功的证据，缺这一行则客户端去往后端网段的流量仍走物理网卡，表现为"隧道连上了但访问不到内网"。第四行 `10.8.0.0/24 dev tun0 ... src 10.8.0.6` 是隧道内网段与客户端虚拟地址，说明 ifconfig 已就位。第五行保留的 `default via 192.168.1.1 dev eth0` 正是 def1 想要的"原出口还在"。需要特别提醒的是，ccd 里的 `iroute` 不会出现在客户端路由表里，它登记在服务端实例路由表，只能在 status 文件或 management 的路由表快照里看到（模块见 07-08、模块见 07-12），把 `iroute` 错当成客户端本该出现的路由行，是最典型的判读误区。综合来看，一份健康的路由表应同时满足"两条 /1 存在、后端网段指向 tun0、隧道网段就位、原默认路由仍在"，任一处缺失都能把排错范围收敛到 push 下发、redirect 参数或路由后端，而不必去翻加密日志。

### 6. 注意事项、陷阱与最佳实践

第一，`iroute` 与 `route` 必须成对理解。ccd 里的 `iroute` 决定"服务端把某网段交给哪个实例"，`push "route"` 或本地 `route` 决定"客户端把去往该网段的包送进隧道"；站点到站点分支接入两者缺一不可。只配其一，症状往往是"一端能 ping 通隧道地址，却怎么也到不了分支网段"，此时应先核对 ccd 文件名是否与证书通用名完全一致，再看实例路由表里有没有对应网段行。

第二，`redirect-gateway` 要守住出口与 DNS。务必带 `def1` 保留原默认路由，否则极易出现"一连上 VPN 就断流"；同时确认 `bypass-dhcp`、`bypass-dns` 一类参数在本版本确实可用（需对照实际版本核验），避免本地 DHCP 或 DNS 直连路由被覆盖。全流量入隧道后要专门验证 DNS 查询是否也走隧道，防止"流量进了隧道、域名解析暴露在外"的泄露。

第三，push 的引号与平台权限。服务端 `push "route ..."` 被引号包裹，写错引号或参数个数会让客户端解析失败且日志不总是醒目；Windows 客户端下发路由需要管理员权限，普通用户启动常表现为"连上了却没路由"，应检查客户端是否以足够权限运行。相关参数形式见 04-04（指令见 04-04）。

第四，tap 桥接要控制广播域。网桥会转发 ARP、DHCP、组播发现等所有二层流量，客户端一多就形成广播放大，环路还会引发广播风暴；应开启生成树一类防护、限制接入数量，并确认所选平台驱动确实支持 tap 二层模型（模块见 07-01）。除非确有非 IP 协议或二层互通需求，否则优先 tun 路由模式。

第五，`route-nopull` 与内核转发别漏。`route-nopull` 会忽略服务端全部推送，适合由本地脚本完全自定义路由的场景，但用了它就要自己补齐地址、路由与 DNS，漏配时症状与 push 失败很像；服务端若要转发不同网段流量，内核 `net.ipv4.ip_forward` 必须打开，否则路由再正确也不转发。这些都属部署前置条件，见 03-04。

第六，明确边界与去重。以上路由推送、iroute、redirect-gateway 与桥接都是社区版 `src/openvpn/route.c`、`src/openvpn/push.c` 的内置能力；Access Server 的图形化路由策略与集中管理不是社区版功能。全部相关指令见 04-02、04-04（指令见 04-02、指令见 04-04），字段见 05-09（字段见 05-09），推送与路由构建机制见 06-11（原理见 06-11）。

### 7. 小结与延伸阅读

本篇把路由与桥接模块定位为"把一条已连通的隧道接到真实网络"：`src/openvpn/route.c` 管路由增删与拓扑，`src/openvpn/push.c` 把配置从服务端推到客户端，ccd 里的 `iroute` 把分支网段挂到具体实例，`redirect-gateway def1` 用两条 /1 安全覆盖默认路由，tap 桥接则提供并列的二层组网路径。选型结论很清晰：默认 tun 路由模式，`route`、`iroute`、`redirect-gateway` 按方向各司其职，全流量场景守住出口与 DNS，只有确有二层需求才上 tap 桥接。

## 07-10 DCO 模块与性能特性

### 1. 背景与动机

OpenVPN 社区版长期是纯用户态程序，每一个数据报文都要经历"内核 socket 收包 → 拷贝到用户态 → 解密、封装、校验 → 再拷贝回内核 socket 发出"的往返，外加频繁的系统调用与加解密运算集中在单个线程。在低速链路或少量客户端时这套模型足够好用，但当链路升到千兆以上、客户端数量上去之后，内核态与用户态之间的反复拷贝与上下文切换就成了明显瓶颈，单核加密吞吐先于网卡到达上限。要突破这一点，思路与许多网络加速方案一致：把成熟、高频、规则固定的数据通道下沉到内核，只把复杂、低频、需要策略判断的部分留在用户态。ovpn-dco（OpenVPN Data Channel Offload）就是这条思路在 OpenVPN 上的落地。

它带来的边界变化很明确：控制通道不变，TLS 握手、证书校验、认证、密钥派生、配置推送仍由用户态的 `src/openvpn/ssl.c` 等完成；数据通道变，已协商好的密钥被安装到内核模块，由内核直接完成密文的封装、解封装与转发，用户态只负责在密钥轮换等节点把新密钥装下去。这样既保留了社区版成熟的控制面逻辑，又把最耗 CPU 的搬运工作交给内核，吞吐与时延通常有明显改善。

但 DCO 不是"打开就快"的万能开关，它有严格的启用条件与能力协商，条件不满足时会自动回退到用户态数据通道。理解"什么时候能启用、协商了什么、为什么回退、与多客户端特性怎么兼容"，比记住一个开关名重要得多，也是本篇作为模块特性权威源要讲清的内容。

照例划清边界与去重。DCO 的内核卸载流程、控制面与数据面状态迁移属于机制，见 06-12（原理见 06-12）；`ovpn-dco` 内核模块的编译、DKMS 与内核配置要求见 02-05；性能收益的实测口径与前后对比见 08-01、08-02。配置相关指令见 04-02、04-03（指令见 04-02、指令见 04-03），DCO 上下文等对象字段见 05-xx（字段见 05-xx）。本篇配置段只列最典型的几条指令，能力名与开关名不确定处一律写"需对照实际版本核验"并给出源码路径。还需强调商业版边界：DCO 是社区版主线配合独立内核模块的能力，与 Access Server 的商业特性无关。

### 2. 核心概念

第一组概念是控制面与数据面的分界。启用 DCO 后，用户态进程并没有被取代，它仍然负责监听、握手、认证、地址分配、配置推送以及密钥轮换，只是不再逐包搬运业务数据；内核模块维护一个 peer 表与密钥状态，收到密文后直接解密并注入虚拟设备，反之把虚拟设备发出的明文加密后从物理网卡送出。分界处最常见的动作是"密钥安装"：用户态在握手产出新密钥后，通过 netlink 通道把它装到内核（原理见 06-12）。这种分工决定了 DCO 不改变任何控制面行为，证书、认证、push、ccd 照旧工作。

第二组概念是启用条件，这是一组必须同时满足的合取条件，任一项不满足都会回退。大致包括：内核模块 `ovpn-dco` 已正确加载且版本与主进程匹配；Linux 内核版本达到模块要求（具体版本需对照实际版本核验）；设备类型为 `dev tun`，因为 tap 二层桥接不在内核数据通道卸载模型内；数据通道加密套件为内核支持的 AEAD 类，例如 AES-GCM、ChaCha20-Poly1305 一类（可用名称需对照实际版本核验），CBC 加 HMAC 的老组合通常不受支持；未启用压缩，未启用 `fragment` 内部分片；进程持有 `CAP_NET_ADMIN` 一类能力以操作 netlink 与内核接口；以及 `topology subnet` 等与内核 peer 模型兼容的拓扑。以上条件清单与内核能力标志的确切名称需对照 `src/openvpn/dco.c`、`src/openvpn/dco.h` 与独立仓库 `ovpn-dco` 核验，不要凭记忆写死。

第三组概念是能力协商。启动阶段，用户态通过 generic netlink 检查内核模块的 family 是否存在、读写其能力标志，再逐项比对本侧配置是否落在支持范围内。协商通过则继续创建内核接口与 peer；协商不通过并不报错退出，而是记录回退原因、降级到用户态数据通道。也就是说 DCO 是"能卸就卸、不能卸就照常跑"的自适应设计，功能不会因为卸载失败而丢失，只是性能不再提升。是否存在显式的启用或禁用开关（形如 `disable-dco` 一类）、其确切拼写需对照 `src/openvpn/options.c` 与实际版本核验。

第四组概念是用户态回退与日志判读。回退本身是正常行为，但运维需要知道"为什么没卸成功"，因此读日志比猜配置重要：常见回退原因是内核模块未加载、cipher 不被支持、开启了压缩或 fragment、用了 tap、内核版本过旧、权限不足。判读方法见第 5 节。

第五组概念是与多客户端的兼容边界。内核模块自己维护 peer 表，天然支持多客户端服务端，但部分 per-client 特性的支持程度随版本演进：ccd 里的 `iroute`、`client-to-client`、`auth-token`、`tls-crypt-v2` 以及某些 topology 组合是否完全由内核承载，需对照实际版本核验；不确定的组合应按"可能回退或部分回退"来评估，并在上线前实测。以上分界与协商关系见图 07-10-01 与图 07-10-02。

### 4. 关键流程与调用链

从模块协作角度，DCO 从启动到承载业务大致串起六步，这里只讲各模块之间交接什么。第一步，构建或打包阶段确认内核模块可用、头文件与用户态版本匹配（见 02-05）。第二步，启动初始化时 `src/openvpn/dco.c` 打开与内核通信的 netlink 通道，检查 generic netlink family 是否存在。第三步，能力协商：读取内核能力标志，逐项比对 cipher、压缩、分片、设备类型、拓扑与权限是否落在支持范围内。第四步，协商通过则创建内核接口与 peer，并在握手产出密钥后把密钥安装到内核；此后业务数据由内核数据通道承载，用户态只保留控制通道。第五步，协商不通过或运行中遇到不支持的配置变化，则记录原因并降级到用户态数据通道，功能照常工作。第六步，密钥轮换、客户端上下线等事件仍由用户态发起，经 netlink 同步到内核 peer 表（该同步属于机制，见 06-12，原理见 06-12）。以上与事件循环、实例管理、密钥协商的衔接分别见 06-02、06-10、06-07（原理见 06-02、原理见 06-10、原理见 06-07）。

### 5. 配置/命令/代码实例

按去重约定，这里只列本模块最典型的几条指令，其余交给 04-02、04-03（指令见 04-02、指令见 04-03，完整指令族见 04-02）。下面这段配置展示的是"三层设备 + subnet 拓扑 + AEAD 数据通道加密"这一满足 DCO 主要条件的组合；是否提供显式的启用或禁用开关需对照 `src/openvpn/options.c` 与实际版本核验，本例按"条件满足即自动启用"来说明，且刻意不写压缩与 fragment 指令。

```conf
dev tun
topology subnet
data-ciphers AES-256-GCM:CHACHA20-POLY1305
```

判断是否真正卸载成功，最可靠的是读启动日志里 DCO 相关行。下面给出检索命令，随后是典型输出。示例输出，具体格式需对照实际版本核验；不同版本的日志文案、能力名、模块版本号与 peer 表述会有差异，文中版本号仅为示意。

```bash
journalctl -u openvpn-server@server --no-pager | grep -i dco | tail -n 20
```

```text
Nov 11 10:12:07 gw openvpn[2210]: DCO: generic netlink family 'ovpn-dco' available
Nov 11 10:12:07 gw openvpn[2210]: DCO: kernel module ovpn-dco loaded
Nov 11 10:12:07 gw openvpn[2210]: DCO: capabilities check passed for AES-256-GCM
Nov 11 10:12:07 gw openvpn[2210]: DCO: data channel offload enabled for tun0
Nov 11 10:12:09 gw openvpn[2210]: DCO: peer 10.8.0.6 added
Nov 11 10:12:13 gw openvpn[2210]: DCO: peer 10.8.0.6 key installed
```

下面对这段输出逐行判读。前两行说明内核侧前提成立：generic netlink family 存在、内核模块已加载，这是卸载的地基；若这里出现 `family not found` 或 `module not loaded` 一类字样，应先回到 02-05 检查模块编译、DKMS 注册与加载状态，而不是去改 VPN 配置。第三行 `capabilities check passed` 是能力协商通过的关键证据，它把 cipher 与内核支持集对齐了；若换成 `not supported`、`cipher not offloadable` 一类措辞，通常意味着数据通道加密套件不是内核支持的 AEAD 类型，需核对 `data-ciphers` 取值。第四行 `offload enabled for tun0` 明确宣告数据通道已卸载，这是整段日志里最该确认的一行；没有它，即使前几行都正常也只是"具备条件但未启用"。第五、六行 `peer added` 与 `key installed` 说明多客户端场景下内核 peer 表已建立、密钥已安装，业务流量开始由内核承载；客户端连入时若迟迟没有这两行，可能是 per-client 特性触发了部分回退。综合来看，一段健康的 DCO 日志应同时满足"family 可用、模块已加载、能力检查通过、明确出现 offload enabled、peer 与密钥成对出现"，把"具备条件"与"确实启用"分清，是判断性能是否真的受益的第一道基本功。

作为对照，下面给出协商失败时的典型回退日志，便于识别降级特征。示例输出，具体格式需对照实际版本核验。

```text
Nov 11 10:12:07 gw openvpn[2210]: DCO: compression enabled, cannot use data channel offload
Nov 11 10:12:07 gw openvpn[2210]: DCO: falling back to userspace data channel
Nov 11 10:12:07 gw openvpn[2210]: Data Channel: using userspace tun handling
```

这段回退输出里第一行直接点出原因（本例为启用了压缩），第二行 `falling back` 宣告降级，第三行说明数据通道改回用户态。功能不受影响，但吞吐与 CPU 表现会回到未卸载水平；排障时应逐条对照第 3 节的条件表，找出被标红的那一项再决定是改配置还是升级内核模块。

### 6. 注意事项、陷阱与最佳实践

第一，不要为了启用 DCO 牺牲安全。数据通道加密套件应优先选择现代 AEAD 算法，绝不能为了"能被卸载"退回 CBC 加 HMAC 的老组合，也不要因为压缩能省一点带宽就重新打开压缩——压缩不仅有已知的安全风险（模块见 07-11），还会直接让 DCO 回退，得不偿失。

第二，压缩与 fragment 与 DCO 互斥。`compress`、`fragment` 一类能力属于用户态数据通道处理链，内核卸载路径不承担它们（模块见 07-11）。若现网确实依赖这两者，须在"保留功能"与"启用卸载"之间明确取舍，并在升级前实测回退行为。

第三，tap 桥接场景没有卸载收益。DCO 面向三层 tun 数据通道，`dev tap` 的二层桥接不在支持范围内；把桥接部署强行套 DCO 只会得到一条回退日志。二层需求应回到 07-01、07-09 评估设备与组网，而不是指望卸载加速。

第四，协商失败要读日志而不是猜。回退原因通常被明确记录（模块未加载、cipher 不支持、压缩开启、权限不足、内核版本过旧），先按第 5 节判读方法定位具体一项，再对照第 3 节条件表逐项核验能力名与版本，比反复试改配置高效得多。

第五，多客户端 per-client 特性要逐项核验。内核 peer 模型虽支持多客户端，但 ccd 里的 `iroute`、`client-to-client`、`auth-token`、`tls-crypt-v2` 等特性在不同版本的支持程度不同（模块见 07-08、模块见 07-03），上线前应在目标版本上实测"启用 DCO 后这些能力是否仍完整生效"，不要假设与用户态路径完全等价。

第六，版本匹配与商业版边界。`ovpn-dco` 是独立维护的内核模块，用户态版本、内核版本与模块版本要配套，升级内核或升级 OpenVPN 后需按 02-05 重新构建或重载模块；是否提供显式开关需对照 `src/openvpn/options.c` 核验。性能收益的实测口径与前后对比见 08-01、08-02；DCO 是社区版主线能力，与 Access Server 商业特性无关。

### 7. 小结与延伸阅读

本篇把 DCO 模块定位为"把成熟的数据通道下沉到内核、把复杂的控制面留在用户态"的性能特性：`src/openvpn/dco.c` 负责能力判定与挂接，generic netlink 连接用户态与 `ovpn-dco` 内核模块，一组严格的启用条件决定是否卸载，协商不通过则自动回退用户态、功能不丢但性能不提升。选型结论很清晰：三层 tun、AEAD 加密、不压缩不分片、模块与内核版本配套时优先启用；tap 桥接、依赖压缩或 fragment 的场景不强求；多客户端 per-client 特性逐项实测。

延伸阅读建议按三条线走。网络与加密相关指令全集见 04-02、04-03（指令见 04-02、指令见 04-03），DCO 相关对象字段见 05 册（字段见 05-xx）；控制面与数据面分界、密钥安装、能力协商与回退机制见 06-12（原理见 06-12），事件循环、实例管理与密钥协商分别见 06-02、06-10、06-07。内核模块构建见 02-05，性能基准与调优见 08-01、08-02，压缩分片取舍见 07-11，设备层 tun/tap 选型见 07-01，多客户端兼容边界见 07-08。

## 07-11 压缩、MTU 与分片模块

### 1. 背景与动机

隧道建好之后，报文并不是原样塞进物理链路的：它要叠加外层 IP 头、UDP 或 TCP 头、OpenVPN 自身的封装与序号、加密填充与完整性标签，启用压缩时还要带一段压缩帧信息。这些额外字节都要从物理链路的 MTU 里扣除，于是"隧道内一个 1500 字节的 IP 包"封装后往往变成一千五百多字节的密文，超过以太网的 1500 字节上限。若中间链路不允许分片、或报文带了 DF 禁止分片标志，超长报文就会被静默丢弃，形成典型的 MTU 黑洞：小包能通、大包卡住，TLS 握手在交换大证书时停滞，TCP 建连成功后一传大文件就假死。压缩、MTU 调整与分片这三组能力，本质上都是围绕"如何在有限的外层 MTU 里把内层载荷安全送过去"而设计的。

压缩的历史动机很朴素：早期低速链路上，先压缩再加密能省下可观带宽。但这个顺序在安全上被证明是有问题的。2018 年公开的 VORACLE 一类攻击指出，当明文在加密之前被压缩时，密文长度会随明文的冗余度变化，攻击者只要能向连接里注入可控内容并观察密文长度，就有机会逐字节推断出会话里的敏感字段（如令牌、Cookie）。压缩因此从"省带宽的优化项"变成"默认应关闭的风险项"，OpenVPN 2.6 前后对 `compress`、`comp-lzo`、`allow-compression` 的语义与默认值做了明显调整，本模块的一大重点正是把这条安全变更讲清楚。

分片的动机则是另一条线。面对 MTU 不够，有两条思路：让 TCP 主动把分段变小，或在 VPN 内部把大包切成多个小片再重组。前者是 `mssfix` 一类钳制 TCP MSS 的手段，后者是 `fragment` 这样的 OpenVPN 内部分片（注意它不是 IP 层分片）。随着链路条件改善与 DCO 内核卸载的引入，内部分片因开销、安全与兼容性问题已被边缘化，理解它"什么时候该禁用"比"怎么启用"更重要。

照例划清边界与去重。本篇是模块功能与组网的权威源，讲"压缩有哪些算法与安全边界、MTU 链怎么推导、mssfix 与 fragment 各自适用和禁用场景、怎么定位 MTU 黑洞"；帧结构、buffer 与 MTU 推导链、压缩与 OCC 参数协商属于机制，见 06-04 与 06-09（原理见 06-04、原理见 06-09）；相关指令的逐项语法由 04-02 给出（指令见 04-02）；`frame`、`buffer` 等对象字段见 05-06（字段见 05-06）。本篇配置段只列最典型的几条指令，能力名与取值不确定处一律写"需对照实际版本核验"并给出源码路径。压缩与 DCO 的互斥关系见 07-10，性能调优口径见 08-02。

### 2. 核心概念

第一组概念是压缩算法与框架。LZO 与 LZ4 是 OpenVPN 历史上支持的两种压缩算法，`src/openvpn/comp.c` 提供统一的压缩框架与算法分发，`src/openvpn/comp-lz4.c` 承载 LZ4 相关实现，LZO 则依赖外部 lzo 库（构建开关见 02-03）。`lz4-v2` 一类改进帧格式用于解决旧格式在某些边界条件下的行为差异，确切模式名需对照 `src/openvpn/comp.c`、`src/openvpn/comp-lz4.c` 与实际版本核验。

第二组概念是 `compress` 取代 `comp-lzo` 的安全变更。较新版本用 `compress` 指令统一表达压缩策略，其取值大致分三类：真正的压缩（如 `lzo`、`lz4`、`lz4-v2`）、不压缩但保留兼容帧的占位模式（如 `stub`、`stub-v2`）、以及用于平滑迁移的 `migrate` 一类模式。`stub` 类模式的价值在于：当对端是旧版本、仍期待收到压缩帧时，本端可以"不真的压缩、只补齐帧格式"来保持互通，既避开压缩风险又不断连。`allow-compression` 一类开关控制是否允许对端压缩数据，2.6 与 2.7(master) 的默认行为存在差异，需对照 `src/openvpn/options.c` 与实际版本核验。结论很明确：生产环境不要在公网数据通道启用真实压缩。

第三组概念是 VORACLE 风险的本质。压缩发生在加密之前，明文的重复程度会影响压缩比，进而影响密文长度；这个长度对被动或主动观察者是可见的。攻击者通过注入猜测内容并比较长度变化，能逐步逼近明文中的秘密字段。这与加密算法本身是否坚固无关，是"压缩与加密的组合顺序"带来的侧信道，因此缓解办法不是换更强的 cipher，而是关掉压缩，或至少确保被压缩的数据里不含攻击者可控且与秘密同处一上下文的内容。理解这一点，才能解释为什么压缩从默认优化变成了默认关闭。

第四组概念是 MTU 链。`tun-mtu` 设定隧道设备看到的内层 MTU，`link-mtu` 描述外层链路可承载的最大密文长度，`src/openvpn/frame.c` 依据二者与封装开销推导帧参数（字段见 05-06，原理见 06-04）。`mssfix` 不改动 IP 包本身，而是在 TCP 建连时改写 SYN 报文里的 MSS 选项，让两端把 TCP 分段控制在隧道能承载的范围内，从而避免大包被丢；其实现集中在 `src/openvpn/mssfix.c`，该文件在版本间的存在性与归属需对照实际版本核验。要注意 `mssfix` 只对 TCP 生效，UDP、ICMP 以及已经分片的流量不受它保护。

第五组概念是 `fragment` 内部分片。`src/openvpn/fragment.c` 在用户态把一个大的隧道报文切成若干内部小片发送，对端再重组，它不是 IP 层分片，也不依赖中间网络的 PMTU。历史上它用于 UDP 链路上规避 MTU 问题，但代价是额外开销、重组状态、对丢包更敏感，且与 DCO 内核卸载路径不兼容（模块见 07-10），现代部署普遍建议改用 `tun-mtu` 加 `mssfix` 的组合，把 `fragment` 视为应避免的能力。第六组是 `src/openvpn/occ.c` 的参数一致性协商：压缩、MTU、密钥等参数在两端不一致时会被检测并告警（原理见 06-09），这也是排查"一端能通一端不能通"的重要线索。以上处理链见图 07-11-01。

### 4. 关键流程与调用链

从模块协作角度，一个出站报文大致串起六步，这里只讲各模块之间交接什么。第一步，参数协商：`src/openvpn/occ.c` 在连接建立阶段比对两端的压缩、MTU 与密钥参数，不一致则告警（原理见 06-09）。第二步，出站报文从 tun 设备读入后，按配置进入压缩处理链：`src/openvpn/comp.c` 决定是真实压缩、占位帧还是不处理。第三步，`src/openvpn/frame.c` 依据 `tun-mtu`、`link-mtu` 与封装开销计算本帧可承载的载荷长度（原理见 06-04）。第四步，按协议分流：TCP 路径上 `mssfix.c` 改写 SYN 的 MSS 约束后续分段，UDP 大包路径上若启用 `fragment` 则由 `fragment.c` 切成内部小片。第五步，封装加密后交给 `src/openvpn/socket.c` 从链路发出（模块见 07-02）。第六步，对端按逆序重组内部小片、解压、还原报文并写回 tun 设备；启用 DCO 时这条用户态处理链会被绕过，压缩与 fragment 因此不兼容（模块见 07-10）。以上与事件循环、帧封装的衔接属于机制，见 06-02、06-03（原理见 06-02、原理见 06-03）。

### 5. 配置/命令/代码实例

按去重约定，这里只列本模块最典型的几条指令，其余交给 04-02（指令见 04-02，完整指令族见 04-02）。下面这段配置展示的是"下调隧道 MTU + 钳制 TCP MSS + 迁移期兼容帧"这一组合；`compress stub-v2` 只补齐帧格式、并不真正压缩，现代生产环境更推荐完全不写 `compress` 指令，取值需对照实际版本核验。

```conf
tun-mtu 1400
mssfix 1360
compress stub-v2
```

验证 MTU 是否调到位，最可靠的办法是用带 DF 标志的 ICMP 探测端到端可承载的最大尺寸。下面给出查询命令，随后是典型输出。示例输出，具体格式需对照实际版本核验；不同系统的 ping 实现、ICMP 头长度显示与时延字段会有差异。

```bash
ping -M do -s 1372 -c 3 10.8.0.1
```

```text
PING 10.8.0.1 (10.8.0.1) 1372(1400) bytes of data.
1380 bytes from 10.8.0.1: icmp_seq=1 ttl=64 time=8.21 ms
1380 bytes from 10.8.0.1: icmp_seq=2 ttl=64 time=8.44 ms
1380 bytes from 10.8.0.1: icmp_seq=3 ttl=64 time=8.19 ms
--- 10.8.0.1 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms
```

下面对这段输出逐行判读。首行 `1372(1400)` 是理解全段的关键：`-s 1372` 指定 ICMP 载荷 1372 字节，加上 8 字节 ICMP 头与 20 字节 IP 头正好是 1400 字节，与 `tun-mtu 1400` 对齐；`-M do` 设置 DF 禁止分片，因此任何超出端到端 MTU 的报文都会被丢弃并回报，这正是探测黑洞的手段。随后三行 `1380 bytes` 是对端回显的正常应答，`icmp_seq` 连续、`time` 在 8 毫秒上下稳定，说明该尺寸的报文端到端可通、没有静默丢弃；这里的 1380 与 1400 的差值来自回显路径上的封装细节，属正常范围。统计行 `3 received, 0% packet loss` 是健康结论，若出现 `100% packet loss` 或 `Frag needed and DF set` 一类报错，则表明该尺寸已超过链路可承载值，需要继续下调 `tun-mtu` 或增大 `mssfix` 的钳制力度。作为对照，把 `-s` 增大到 1400（总长 1428）时若立刻全丢，就复现了 MTU 黑洞的典型特征。需要特别提醒的是，`mssfix` 只改写 TCP SYN 的 MSS，对 ICMP、UDP 与已生成的大包无效，所以"ping 能通"并不等价于"TCP 大文件一定不卡"，上线前仍要用真实业务流量验证。综合来看，一次有效的 MTU 核验应满足"按头长精确换算尺寸、带 DF 标志、连续多包无丢、时延稳定"，并把 ICMP 结果与 TCP 业务表现分开判读，避免被单一探针误导。

作为对照，下面给出超过 MTU 时的典型失败输出，便于识别黑洞特征。示例输出，具体格式需对照实际版本核验。

```text
PING 10.8.0.1 (10.8.0.1) 1400(1428) bytes of data.
From 10.8.0.6 icmp_seq=1 Frag needed and DF set (mtu = 1400)
ping: local error: message too long, mtu=1400
--- 10.8.0.1 ping statistics ---
3 packets transmitted, 0 received, 100% packet loss, time 2044ms
```

这段失败输出里 `Frag needed and DF set (mtu = 1400)` 直接点出了链路可承载上限，`100% packet loss` 说明所有超长报文都被丢弃；此时应把 `tun-mtu` 定在不超过该上限的值，并让 `mssfix` 略小于它，为封装开销留出余量，而不是去打开 `fragment`。

### 6. 注意事项、陷阱与最佳实践

第一，生产环境禁用数据通道压缩。VORACLE 类攻击利用的是"压缩在加密前"这一顺序带来的长度侧信道，与 cipher 强度无关；不要为了省一点带宽重新打开 `lzo`、`lz4`，也不要把 `allow-compression` 放宽到接受对端压缩。`allow-compression` 的默认值与 `compress` 各模式语义在 2.6 与 2.7(master) 间有差异，务必对照 `src/openvpn/options.c` 与实际版本核验。确需兼容旧对端时，用 `stub` 一类的占位帧过渡，而不是恢复真实压缩。

第二，`fragment` 基本应视为禁用项。它与 DCO 内核卸载不兼容（模块见 07-10），带来重组状态与额外开销，对丢包更敏感，且只在 UDP 链路上有意义。不要把它与 `mssfix` 想当然叠加成"双保险"；正确做法是用 `ping -M do` 实测出一个合适的 `tun-mtu`，再配 `mssfix` 钳制 TCP 分段，把问题解决在源头。

第三，认清 `mssfix` 的作用边界。它只影响 TCP SYN 里的 MSS 选项，对 ICMP、UDP、以及不经过本端 SYN 协商的流量无效。因此"ping 通了"或"网页小图能开"都不能证明大流量没问题；视频、大文件传输、大证书 TLS 握手才是 MTU 黑洞最容易暴露的地方，排障要以真实业务为准。

第四，两端参数必须一致。`src/openvpn/occ.c` 会在压缩、MTU、密钥参数不一致时给出告警（原理见 06-09），这类告警常被忽略却正是"单方向不通"的根因。升级或改配置时应对两端一起改，并留意 `compress` 与 `tls-crypt` 一类控制通道保护叠加时的行为差异；是否存在 `mtu-test` 一类探测辅助指令需对照 `src/openvpn/options.c` 与实际版本核验。

第五，调 MTU 要留余量而不要盲目压小。`tun-mtu` 调得过小会浪费吞吐、`mssfix` 过小会让 TCP 分段过碎；应先用带 DF 的 ICMP 从物理链路 MTU 往下二分探测，扣除封装开销后定值，再留少量余量应对不同路径。压缩帧、加密填充、协议族（IPv4 与 IPv6 头长不同）都会影响开销，双栈部署尤其要分别验证。

第六，明确边界与去重。以上压缩、MTU 与分片能力都是社区版 `src/openvpn/comp.c`、`src/openvpn/frame.c`、`src/openvpn/fragment.c` 的内置特性，与商业版无关。全部相关指令见 04-02（指令见 04-02），`frame` 与 `buffer` 字段见 05-06（字段见 05-06），帧推导与 OCC 协商机制见 06-04、06-09（原理见 06-04、原理见 06-09），MTU 黑洞的性能侧定位与调优见 08-02、08-04。

### 7. 小结与延伸阅读

本篇把压缩、MTU 与分片模块定位为"在有限外层 MTU 里把内层载荷安全送过去"的一组手段：`src/openvpn/comp.c` 管压缩框架，但 VORACLE 风险让真实压缩在生产环境默认关闭；`src/openvpn/frame.c` 推导 tun-mtu 与 link-mtu，`src/openvpn/mssfix.c` 钳制 TCP MSS，`src/openvpn/fragment.c` 的用户态内部分片已趋边缘化；`src/openvpn/occ.c` 负责两端参数一致性。选型结论很清晰：不压缩、不分片，用实测的 `tun-mtu` 加 `mssfix` 解决 MTU 黑洞，靠带 DF 的 ICMP 探测验证，并留意与 DCO 的互斥关系。

延伸阅读建议按三条线走。网络与隧道相关指令全集见 04-02（指令见 04-02），构建期 LZO/LZ4 开关见 02-03；`frame` 与 `buffer` 字段见 05-06（字段见 05-06）；帧结构、buffer 与 MTU 推导、压缩与 OCC 参数协商机制见 06-04、06-09（原理见 06-04、原理见 06-09）。DCO 与压缩分片的互斥见 07-10，设备层 MTU 与 PI 头见 07-01，路由与隧道封装见 07-09、06-03，MTU 黑洞故障案例见 08-04，性能调优见 08-02。

## 07-12 辅助模块：日志、status、IPv6、keepalive、端口共享

### 1. 背景与动机

前面十一篇讲的是让隧道"建起来、跑起来、快起来"的主干模块：设备、传输、加密、证书、认证、管理接口、脚本插件、多客户端、路由桥接、DCO 卸载、压缩与 MTU。但一套真正可运维的 VPN，光有主干远远不够，还需要一组看似零散、缺一不可的辅助能力。本篇把它们收拢成一册收尾：日志解决"后台守护进程没有终端时怎么看见它"，status 解决"不连管理接口也能拿到周期性快照"，IPv6 解决"隧道本身如何承载双栈地址族"，keepalive 解决"静默链路怎么判断对端还活着"，port-share 解决"443 端口已经被 HTTPS 占用时怎么共存"。五者体量不大，却几乎出现在每一份生产配置里。

先看可观测性这对能力。OpenVPN 常以守护进程方式开机自启，没有可交互终端，管理员要知道发生了什么只能依赖日志与状态快照。日志是连续的事件流，粒度由 `verb` 分级控制，适合事后追查与实时排查；status 是周期性刷新的结构化快照，适合监控系统按固定间隔采集、画趋势、做告警。07-06 的 management interface 提供的是第三种形态——实时双向会话，既能订阅状态又能下发控制；三者定位不同，不能互相替代：把 status 文件当成实时接口会读到滞后的旧数据，把管理接口当日志流又会丢失历史上下文。理解这三种观测通道的分工，是设计监控方案的前提。

再看链路存活与地址族。UDP 是无连接的，中间 NAT 与防火墙会为一条"看起来没流量"的会话设定超时并悄悄删除映射，表现为"连着却突然不通、重连又好了"；keepalive 用周期性的 ping 保活与超时重启来对抗它。IPv6 则越来越不是可选项：客户端要拿到 IPv6 隧道地址、要访问 IPv6 后端网段，服务端也要能把 IPv6 路由下发下去，双栈部署若只配了 IPv4 一半，症状往往是"IPv4 全通、IPv6 全不通"。最后是端口复用，很多网络只放行 443，若它已被 Web 服务占用，OpenVPN 就需要一种机制在同一个 TCP 端口上把非 VPN 的 TLS 流量转交给后端服务，这就是 port-share。

照例划清边界与去重。本篇是模块功能与组网的权威源，讲"这五组能力各自解决什么、有哪些典型用法、选型与陷阱怎么定"；全部相关指令的逐项语法由 04-02、04-04、04-06、04-07 给出（指令见 04-02、指令见 04-04、指令见 04-06、指令见 04-07）；信号与定时器如何挂进事件循环属于机制，见 06-02（原理见 06-02）；`link_socket`、management 与状态相关对象的字段见 05-07、05-09（字段见 05-07、字段见 05-09）。本篇配置段只列最典型的几条指令。商业版边界照旧：社区版 `src/openvpn/` 主线不提供 Web 界面与集中监控，Access Server 的图形化运维不是社区版能力。

### 2. 核心概念

第一组概念是日志分级与输出。`verb` 是日志详细度主开关，取值大致从 0 到 11，默认档只输出启动与关键连接事件，档位越高越接近逐包调试；`src/openvpn/errlevel.c` 定义了各调试级别常量与级别到输出行为的映射，确切档位名需对照实际版本核验。`mute` 用于抑制重复日志，避免同一条告警刷屏淹没关键行；`log` 与 `log-append` 把输出从标准输出重定向到文件（前者覆盖、后者追加）；`suppress-timestamps` 一类参数在由 systemd 等外部系统统一加时间戳时使用，`writepid` 写出进程号文件便于服务管理。日志是本篇第一个要强调"能力越强、风险越大"的地方：高 verb 档可能把敏感字段带进日志，且逐包输出本身有性能开销。

第二组概念是 status 快照。`status` 指令指定输出文件路径，`status-version` 选择输出档位（常见 1、2、3），`src/openvpn/status.c` 周期性把客户端列表、路由表与全局统计写进去，典型段落为 CLIENT_LIST、ROUTING_TABLE、GLOBAL_STATS 与结尾的 END。它与 management 的 `status` 命令输出内容相近，但一个是周期刷新的文件、一个是即时查询的响应，采集系统要按"快照可能滞后一个刷新周期"来设计。刷新间隔、各档位的列名与字段个数需对照 `src/openvpn/status.c` 与实际版本核验。status 文件的路径权限与属主，是运维最容易漏掉的一项前置条件。

第三组概念是 IPv6 隧道。社区版支持在隧道内承载 IPv6：`tun-ipv6` 一类指令声明设备支持 IPv6，`ifconfig-ipv6` 配置隧道内 IPv6 地址，`server-ipv6` 在服务端宏层面分配 IPv6 网段，`route-ipv6` 与 `push "route-ipv6 ..."` 下发 IPv6 路由，`proto udp6`、`tcp6` 一类取值用于让链路本身走 IPv6（确切参数名需对照 `src/openvpn/options.c` 与实际版本核验）。双栈部署要两端一致：只在一端启用、或只下发 IPv6 路由却不给地址，都会造成单栈不通。还要留意 IPv6 默认路由与 DNS，防止"IPv4 进了隧道、IPv6 却从本地直出"的泄露，这与 07-09 的 redirect-gateway 思路是对应的。

第四组概念是 keepalive。`keepalive` 是一个便捷宏，展开为周期性的 `ping` 与超时后的 `ping-restart`（展开出的确切指令与默认值需对照 `src/openvpn/options.c` 与实际版本核验）：前者定期发保活报文维持 NAT 映射并检测对端，后者在连续收不到响应达到阈值时触发一次软重启，重新走握手而不是僵死。`src/openvpn/sig.c` 承载信号与软重启状态的落地（原理见 06-02）。它与 `inactive` 不同：后者按"空闲时长"主动断开长期无业务流量的会话，是资源回收；keepalive 是"哪怕没业务流量也要确认链路还活着"。还有 `ping-timer-rem` 一类参数控制重启计时器是否在没有远端时仍运行，取值需核验。

第五组概念是 port-share。`port-share` 让 OpenVPN 在 TCP 监听端口上把非 OpenVPN 的流量转发给指定的后端地址与端口，典型场景是 443 已被 HTTPS 占用时，把普通 TLS/HTTPS 连接转交给本机 Web 服务，而 OpenVPN 控制通道流量仍由自己处理。它只在 TCP 服务端形态（`proto tcp-server` 一类）下有意义，UDP 不适用；其分流判定在 `src/openvpn/socket.c` 与 `src/openvpn/ps.c`（后者存在性需对照实际版本核验）一条路径上完成。必须讲清边界：它识别的是"这不是 OpenVPN 流量"并转发，不是任意协议的通用端口复用器，性能、超时与可识别的协议范围都有约束，与 07-02 的 link socket 是挂接关系而非替代关系。以上五组辅助能力与主进程的协作关系见图 07-12-01。

### 4. 关键流程与调用链

从模块协作角度，五组辅助能力各有一条短链路，这里只讲各模块之间交接什么。日志链路：主循环与各模块在关键节点产生日志事件，`src/openvpn/errlevel.c` 按 `verb` 档位与 `mute` 规则过滤，再经 `log`/`log-append` 决定的输出目标写出。status 链路：定时器周期触发，`src/openvpn/status.c` 从实例表、路由表与全局计数取一份快照，按 `status-version` 格式化后写入文件，覆盖或追加由配置决定。keepalive 链路：周期性 ping 保活报文经数据通道发出，连续超时后 `src/openvpn/sig.c` 触发软重启信号，主循环据此重建连接（原理见 06-02）。port-share 链路：TCP 监听端口收到首个报文时，`src/openvpn/socket.c` 与 `ps.c` 判定它是否属于 OpenVPN 控制通道，不是则把连接转交后端 HTTPS 服务。IPv6 链路：`src/openvpn/options.c` 解析双栈参数，`src/openvpn/route.c` 把 IPv6 路由写进系统路由表，`tun.c` 配合下发 IPv6 地址。以上与事件循环、信号定时器、实例表的衔接属于机制，见 06-02、06-10（原理见 06-02、原理见 06-10）。

```text
10.8.0.7,bob,198.51.100.22:1194,2026-11-11 10:14:52
GLOBAL STATS
Max bcast/mcast queue length,0
END
```

下面对这段输出逐行判读，重点放在"这份文件本身是不是可信的最新快照"。首行标题与 `Updated` 时间戳是第一个要盯的字段：监控系统每次采集都应确认时间戳比上一次前进，若进程仍在但时间戳长期不动，通常说明 status 写入被阻塞、目录不可写或进程卡在别处，此时这份文件里的客户端列表是过期数据，不能用来判断"谁还在线"。表头列出通用名、真实地址、累计收发字节与连入时间；`alice` 与 `bob` 两行说明当前有两个实例，`Connected Since` 可用于核对会话是否经历过 keepalive 触发的软重启——若连接时间明显比预期短，而业务一直没断，就要回查是不是 ping-restart 反复重建。`Bytes Received` 与 `Bytes Sent` 是累计量，健康时随业务增长。`ROUTING TABLE` 段里 `10.8.0.6,alice` 与 `10.8.0.7,bob` 把虚拟地址与实例对应起来，`Last Ref` 反映该路由最近被引用的时刻，长时间不更新而客户端仍在，可能指向数据通道不通。`GLOBAL STATS` 与 `END` 标记一次完整快照收尾，采集程序应以 `END` 为界解析，避免读到写了一半的内容。还要留意 `status-version` 档位：换档后列名与字段个数会变，解析脚本必须跟着调整；若文件为空或只有标题没有数据行，先查 status 路径的写权限与进程权限降级后是否仍可访问。综合来看，一份可信的 status 快照应同时满足"时间戳持续前进、客户端与路由表成对出现、以 END 收尾、字段与档位匹配"，这也是区分"进程确实异常"与"读到了旧快照"的依据。

作为对照，下面给出 `verb 4` 档位下日志里的典型行，便于把日志流与 status 快照两种观测通道区分开。示例输出，具体格式需对照实际版本核验。

```text
2026-11-11 10:12:07 us=312004 OpenVPN 2.6.x x86_64-pc-linux-gnu
2026-11-11 10:12:07 us=312018 library versions: OpenSSL 3.x
2026-11-11 10:12:09 us=440118 198.51.100.10:1194 TLS: Initial packet
2026-11-11 10:12:10 us=901233 198.51.100.10:1194 VERIFY OK: depth=1
2026-11-11 10:12:11 us=112904 alice/198.51.100.10:1194 MULTI: Learn: 10.8.0.6
```

这几行是连续事件流而非周期性快照：启动版本、TLS 首包、证书链校验通过、学到虚拟地址，按时间顺序记录了同一个客户端从连入到就绪的过程。日志适合回答"刚才发生了什么"，status 适合回答"此刻有哪些人在线"，management 适合回答"现在立刻把状态给我并允许我下发控制"，三者不可混用（模块见 07-06）。

### 6. 注意事项、陷阱与最佳实践

第一，verb 档位按需要开、用完降回去。生产日常运行保持默认或 3 到 4 档即可，5 档以上会输出逐包与加解密细节，既有性能开销，也可能把口令、令牌一类的敏感字段带进日志；深度排障临时拉高，结束后务必恢复。配合 `mute` 抑制重复告警，避免刷屏淹没关键行；日志脱敏、留存与轮换策略见 08-06。

第二，status 文件要先解决"能不能写"。路径所在目录必须对运行账号可写，且进程权限降级后仍可访问，否则表现为文件不生成或长期不更新；采集系统应以 `Updated` 时间戳与 `END` 标记判断快照是否完整、是否过期，不要读到写了一半的内容。还要认清它比 management 的即时查询滞后一个刷新周期，做告警时要留出这个延迟（模块见 07-06）。

第三，keepalive 参数要贴合中间网络。周期与超时应小于 NAT/防火墙的 UDP 会话超时，否则映射已被删除、保活还没发出；也不宜过密，以免在大规模客户端下产生可观的控制流量。它与 `inactive` 语义不同：前者保活、后者按空闲回收资源，别指望用 `inactive` 替代保活。软重启会重建连接，若日志里频繁出现重连，应先核对 ping/ping-restart 阈值与链路丢包，而不是急着怀疑证书（原理见 06-02）。

第四，port-share 的能力边界要讲清。它只在 TCP 服务端形态下有效，识别的是"非 OpenVPN 流量"并转发给指定后端，不是任意协议的通用端口复用器；把它当反向代理用会踩到协议识别范围、超时与性能的约束，也不能与 UDP 形态混用。启用后要验证 443 上 HTTPS 与 VPN 两条路径互不干扰，并确认后端服务只监听在受控地址（模块见 07-02）。

第五，IPv6 要两端一致、双栈分别验证。`tun-ipv6`、`ifconfig-ipv6`、`route-ipv6`、`server-ipv6`、`proto udp6` 一类参数需对照实际版本核验；只配地址不下发路由、或只在一端启用，都会造成"IPv4 全通、IPv6 全不通"。尤其要检查 IPv6 默认路由与 DNS，防止出现"IPv4 进了隧道、IPv6 从本地直出"的泄露，思路与 07-09 的 redirect-gateway 一致。

第六，时间同步与边界收束。status 时间戳、日志时间戳与证书有效期都依赖系统时钟，时钟漂移会让快照判读、日志关联与证书校验同时失真，生产应统一时间源。以上五组辅助能力都是社区版 `src/openvpn/errlevel.c`、`status.c`、`sig.c`、`socket.c`、`route.c` 的内置特性，Access Server 的图形化监控与集中管理不是社区版功能；全部相关指令见 04-02、04-04、04-06、04-07（指令见 04-02、指令见 04-04、指令见 04-06、指令见 04-07），字段见 05-07、05-09（字段见 05-07、字段见 05-09），信号与定时器机制见 06-02（原理见 06-02）。

### 7. 小结与延伸阅读

本篇把五组辅助模块收拢为一套可运维能力：日志用 `verb` 分级把后台进程变成可观测的事件流，`src/openvpn/status.c` 用周期性快照支撑监控采集，IPv6 一族指令让隧道承载双栈地址族，`keepalive` 用 ping 与软重启对抗 NAT 超时，`port-share` 在 TCP 形态下把 443 上的非 VPN 流量转交后端服务。它们都不改变隧道主干，却几乎出现在每一份生产配置里。选型结论很清晰：日志按档位最小化、status 以时间戳与 END 判可信度、keepalive 阈值贴合中间网络、port-share 只在 TCP 且认清协议边界、IPv6 两端一致并分别验证双栈。
