## 01-01 WireGuard Linux 是什么：设计目标、能力矩阵与适用边界

### 1. 背景与动机

要理解 WireGuard Linux 是什么，必须先把它和「WireGuard 协议」以及「WireGuard 的其他实现」区分开。WireGuard 协议本身是一个由 Jason A. Donenfeld 设计的、基于 Noise_IK 的现代 VPN 协议，其规范与参考实现分布在多个仓库；而本篇讨论的 WireGuard Linux，特指把这一协议实现为 Linux 内核模块的那份代码，即上游 `wireguard-linux` 内核树中 `drivers/net/wireguard/` 目录下的驱动，加上与之配套的 `wireguard-tools` 用户态工具（wg 与 wg-quick）。本套资料的事实锚点是 `_wglinux_build/upstream_src/wireguard-linux-src/`（stable 分支内核驱动快照）与 `_wglinux_build/upstream_src/wireguard-tools/`（版本 1.0.20260223，2026-03 抓取），下文凡出现源码路径均相对这两个根目录，规范中为节约篇幅省略前缀。

先看模块自己怎么介绍自己。`drivers/net/wireguard/main.c` 的模块初始化函数 `wg_mod_init` 在成功加载后打印两行 `pr_info`：`WireGuard 1.0.0 loaded. See www.wireguard.com for information.` 与版权行；同一文件末尾用 `MODULE_LICENSE("GPL v2")`、`MODULE_DESCRIPTION("WireGuard secure network tunnel")`、`MODULE_VERSION(WIREGUARD_VERSION)`、`MODULE_ALIAS_RTNL_LINK(KBUILD_MODNAME)` 与 `MODULE_ALIAS_GENL_FAMILY(WG_GENL_NAME)` 声明模块身份。这里的 `WIREGUARD_VERSION` 定义在 `drivers/net/wireguard/version.h`，值为 `"1.0.0"`——注意这是驱动自身的版本字符串，不是 Linux 内核版本，也不是用户态工具版本，三者要分开。用户态 `wireguard-tools/src/version.h` 里 `WIREGUARD_TOOLS_VERSION` 为 `"1.0.20260223"`，又是一个独立版本号。把这三个版本号混为一谈是阅读上游资料时最常见的错误之一。

从设计目标看，WireGuard Linux 的定位是「内核态的、高性能的、极简配置面的安全网络隧道」。它以一个标准 `net_device`（网卡）的形态接入内核网络栈，接口名通常是 `wg0`、`wg1` 等；对内核来说它和普通网卡一样可被 `ip`、`ifconfig`、路由表操作，对应用层则完全透明——把流量路由到 wg0，内核就把它交给隧道封装加密后从真实物理网卡发出。`device.c` 的 `wg_setup` 负责初始化这个 `net_device`，`wg_newlink` 处理来自 rtnetlink 的建链请求，`MODULE_ALIAS_RTNL_LINK` 则让 `ip link add` 能自动加载本模块。这种「伪装成网卡」的设计是它区别于用户态 VPN 的根本：加解密在内核完成，不经过内核态与用户态之间的数据拷贝。

再看清单一面。整个内核驱动约 4800 行 C 代码（含头文件），核心源文件包括负责模块入口与 netdev 注册的 `main.c`、设备生命周期的 `device.c`、对等体管理的 `peer.c`、路由 trie 的 `allowedips.c`、握手引擎的 `noise.c`、消息布局的 `messages.h`、发送与接收的 `send.c` / `receive.c`、socket 与 endpoint 的 `socket.c`、定时器的 `timers.c`、sysfs 的 `sysfs.c`、限速的 `ratelimiter.c`、cookie 的 `cookie.c`，以及加密原语 `chacha20.c`、`poly1305.c`、`curve25519.c`、`blake2s.c`、`siphash.c`（后几者位于内核树 `lib/crypto/`，在本资料快照中置于 `wireguard-linux-src/lib/crypto/`）。用户态配置通过 netlink 通用族完成：uapi 头 `include/uapi/linux/wireguard.h` 定义了族名 `WG_GENL_NAME "wireguard"`、版本 `WG_GENL_VERSION 1`、两个命令 `WG_CMD_GET_DEVICE` 与 `WG_CMD_SET_DEVICE`，以及 device / peer / allowedip 三层属性枚举。这份 uapi 头顶部注明「auto-generated from Documentation/netlink/specs/wireguard.yaml」，说明当前上游已把 netlink 定义纳入 YAML 规范统一管理，这是阅读时需要注意的版本特征。

本套资料的版本基准统一写「wireguard-linux stable 分支内核驱动快照 + wireguard-tools 1.0.20260223」。凡涉及具体字段、函数名签名、命令选项与默认值，均以这两个快照为准并尽量给出源码路径；由于内核与工具链持续演进，个别细节需对照目标系统实际版本核验。这一点贯穿全册：本套资料提供的是「基于真实源码的深度解读」，不是「对某个发行版某个内核版本的逐字说明书」。

### 2. 核心概念

WireGuard Linux 的核心概念可以压缩为四句话：**一个网卡、两类密钥、三层状态、四个边界**。

一个网卡，指 wg0 是一个标准 `net_device`。`device.c` 中 `wg_setup` 把它的 `ndo_open`、`ndo_stop`、`ndo_start_xmit`、`ndo_get_stats64`、`ndo_set_config` 等操作挂到 WireGuard 的实现上（`wg_open`、`wg_stop` 等在 `device.c` 中定义）。内核协议栈按路由把出站包交给 `ndo_start_xmit`，WireGuard 据此进入发送路径；入站解密后的包通过 `netif_rx` 一类接口重新注入协议栈。理解「它是网卡」是理解全部配置与排障的前提——很多看似 WireGuard 的问题其实是路由问题。

两类密钥，指 Curve25519 密钥对与可选的预共享密钥（PSK）。每个接口有一把私钥（`WGDEVICE_A_PRIVATE_KEY`），由它派生出公钥；每个 peer 配置对端公钥（`WGPEER_A_PUBLIC_KEY`）；密钥长度由 `WG_KEY_LEN 32` 规定，即 32 字节。`wg genkey`、`wg pubkey`、`wg genpsk` 三个子命令分别生成私钥、由私钥导出公钥、生成预共享密钥。私钥只应留在本地接口配置中，绝不出现在配置文件分发的公钥里——这是密钥分发的基本纪律（密钥流程详见 03-03）。

三层状态，指接口（device）、对等体（peer）、地址前缀（allowedip）三个层级。netlink 属性枚举恰好对应这三层：`wgdevice_attribute`、`wgpeer_attribute`、`wgallowedip_attribute`。一个 device 下可有多个 peer，一个 peer 下可有多个 allowedip；allowedip 是「允许来自该 peer 的源地址范围」与「发往该范围应走该 peer」的双重语义，这正是 WireGuard 的路由模型（trie 实现见 05-04、原理见 06-07）。

四个边界，是理解能力范围的关键。第一，**内核态边界**：数据面加解密在内核完成，`net_device` 是唯一入口，不存在用户态转发进程。第二，**UDP 承载边界**：所有 WireGuard 报文封装在 UDP 中，默认监听端口 51820，uapi 里对应 `WGDEVICE_A_LISTEN_PORT`；它不直接跑在裸 IP 之上，也不监听 TCP。第三，**无内建密钥分发边界**：协议不定义任何中心服务器、证书体系或自动密钥交换，公钥分发完全交给运维或上层工具，这是「密钥即身份」哲学的直接后果。第四，**无内建地址管理边界**：协议不分配 VPN 地址、不下发路由，`AllowedIPs` 与地址配置由控制面（wg 工具或第三方控制面）显式写入。

下表按「能做 / 不能做」给出能力矩阵，结论均以本快照源码与工具为依据。

| 能力项 | 结论 | 依据源码位置 |
|---|---|---|
| 以网卡形态接入内核协议栈 | 能做，注册为 net_device | `drivers/net/wireguard/main.c`、`device.c` 的 `wg_setup` |
| 内核态加解密 | 能做，无用户态数据拷贝 | `send.c`、`receive.c`、`lib/crypto/` |
| 基于 Noise_IK 的握手与会话 | 能做 | `noise.c`、`noise.h` 的 `noise_handshake_state` |

### 3. 关键数据结构与源码位置

作为总览册，本节只点名关键结构与真实源码路径，逐字段定义统一交给 05 册，不在这里展开字段表。需要建立的结构地图分五层。

设备与 netdev 层以 `drivers/net/wireguard/device.c`、`main.c` 为代表，核心结构是 `wg_device`，它把 `net_device`、私钥、监听端口、 peer 哈希表、allowedips trie 与各类锁组织在一起（字段见 05-02）。对等体层以 `peer.c`、`peer.h` 为代表，核心结构 `wg_peer` 持有公钥、endpoint、握手状态、计数器与发送队列（字段见 05-03）。路由层以 `allowedips.c`、`allowedips.h` 为代表，核心结构 `wg_allowedips` 是 v4/v6 混合 trie（字段见 05-04）。握手与消息层以 `noise.c`、`noise.h`、`messages.h` 为代表，`noise_handshake_state` 枚举定义握手状态机，消息结构定义各类报文布局（字段见 05-05、原理见 06-02、06-04）。收发与网络层以 `send.c`、`receive.c`、`socket.c`、`cookie.c` 为代表（字段见 05-06、05-07）。时限与限速层以 `timers.c`、`ratelimiter.c`、`queueing.h` 为代表（字段见 05-08）。加密原语上下文见 05-09。

配置面的关键头是 `include/uapi/linux/wireguard.h`，它定义 `wgdevice_attribute`、`wgpeer_attribute`、`wgallowedip_attribute` 三层属性枚举、`wgdevice_flag` / `wgpeer_flag` / `wgallowedip_flag` 三组标志位，以及 `wg_cmd` 的两条命令；完整常量与标志交给 04-05、04-06。用户态工具侧的关键源在 `wireguard-tools/src/`，包括 `wg.c`（命令入口）、`config.c`（配置解析）、`encoding.c`（base64 与密钥编解码）、`curve25519.c`（密钥运算）、`ipc.c`（IPC 抽象）、`ipc-linux.h`（netlink 实现）与 `wg-quick` 脚本，模块能力交给 07-13。

### 4. 关键流程与调用链

模块加载链路在 `main.c` 中非常清晰。`wg_mod_init` 依次调用 `wg_allowedips_slab_init()`（为 trie 节点准备 slab 缓存），在 `DEBUG` 编译下运行 `wg_allowedips_selftest()`、`wg_packet_counter_selftest()`、`wg_ratelimiter_selftest()` 三项自检（失败则返回 `-ENOTRECOVERABLE`），随后 `wg_noise_init()`、`wg_peer_init()`、`wg_device_init()`、`wg_genetlink_init()`，全部成功后打印加载信息。这段初始化顺序体现了依赖关系：allowedips 与 noise 是基础，peer 依赖它们，device 依赖 peer，netlink 最后注册以便用户态配置。卸载函数 `wg_mod_exit` 按相反顺序 `wg_genetlink_uninit()`、`wg_device_uninit()`、`wg_peer_uninit()`、`wg_allowedips_slab_uninit()` 回收资源。任何一层初始化失败都通过 `goto` 标签回滚已完成的层，这是内核模块的标准写法（完整链路见 06-01）。

配置链路从用户态的 `wg` 命令开始：`wg` 通过 `wireguard-tools/src/ipc-linux.h` 中的 `mnlg_socket_open(WG_GENL_NAME, WG_GENL_VERSION)` 打开到 `wireguard` 通用族的 netlink 套接字，把配置序列化为 `WG_CMD_SET_DEVICE` 请求发给内核；内核侧在 netlink 层解析 `WGDEVICE_A_*` / `WGPEER_A_*` / `WGALLOWEDIP_A_*` 属性，更新对应的 device 与 peer 状态。查询方向则是 `WG_CMD_GET_DEVICE`，`wg show` 用它拉取接口与 peer 的运行状态（netlink 原理见 06-14，命令全集见 04-01）。

数据链路分收发两条。发送方向：内核按路由把包交给 wg0 的 `ndo_start_xmit`，进入 `send.c` 的发送逻辑，查 allowedips 找到目标 peer，构造数据消息、用会话密钥经 ChaCha20-Poly1305 加密、封装为 UDP 后从底层物理网卡发出。接收方向：`socket.c` 的 UDP socket 收到报文，经 `cookie.c` / `ratelimiter.c` 的防护检查，`receive.c` 解析消息类型（握手或数据），握手交 `noise.c` 处理，数据包验重放、解密、查 allowedips 校验源地址，最后注入内核协议栈。这两条链路的逐段实现分别在 06-05、06-06，模块职责在 07-07、07-08。

### 5. 配置/命令/代码实例

本篇作为总览册，只给理解定位所需的最小命令，完整参数交给 04 册，配置体系交给 03 册。下面这段是建立一个最小点对点隧道的两端配置，用 `wg` 工具的标准写法：

```bash
# 在两端各自生成私钥，并导出公钥
wg genkey | tee privatekey | wg pubkey > publickey

# 以本端私钥建立接口，监听 51820 端口
ip link add wg0 type wireguard
ip address add 10.0.0.1/24 dev wg0
wg set wg0 private-key ./privatekey listen-port 51820

# 添加对端：公钥、endpoint、允许的源地址段
wg set wg0 peer <对端公钥> endpoint 203.0.113.9:51820 allowed-ips 10.0.0.2/32
ip link set wg0 up
```

这段写法体现了三个要点：`wg genkey | tee privatekey | wg pubkey` 是管道式密钥生成，私钥落到本地文件 `privatekey`，公钥从同一私钥派生后单独保存；`ip link add wg0 type wireguard` 依赖 `MODULE_ALIAS_RTNL_LINK` 自动加载模块；`wg set` 的 `peer`、`endpoint`、`allowed-ips` 三个参数分别对应 `WGPEER_A_PUBLIC_KEY`、`WGPEER_A_ENDPOINT`、`WGALLOWEDIP_A_*` 属性（参数全集见 04-01、04-02）。

下面给出验证链路的典型输出，用 `wg show` 查看握手是否建立：

```bash
wg show wg0
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
interface: wg0
  public key: <本端公钥>
  private key: (hidden)
  listening port: 51820
peer: <对端公钥>
  endpoint: 203.0.113.9:51820
  allowed ips: 10.0.0.2/32
  latest handshake: 12 seconds ago
  transfer: 1.25 KiB received, 980 B sent
```

逐行判读如下。第一行 `interface: wg0` 是接口名，来自 `wg show` 对 netlink `WG_CMD_GET_DEVICE` 返回的 `WGDEVICE_A_IFNAME` 属性渲染，确认查询命中了正确的设备；若这里显示的是别的接口名，说明多接口环境下选错了对象。第二行 `public key` 由本端私钥经 Curve25519 派生，对应 `WGDEVICE_A_PUBLIC_KEY`，应与分发给对端的公钥完全一致；对端若配置了不同的公钥，握手将静默失败。第三行 `private key: (hidden)` 是工具刻意不回显私钥的表现，说明 wg 工具在展示层做了保护，真实私钥仍存在于内核接口的 `WGDEVICE_A_PRIVATE_KEY` 中；任何要求你「从 show 输出复制私钥」的说法都是错误的。第四行 `listening port: 51820` 对应 `WGDEVICE_A_LISTEN_PORT`，是 UDP 监听端口；若这里为空或为 0，通常是没有设置私钥或接口未 up。第五行 `peer:` 后是对端公钥，对应 `WGPEER_A_PUBLIC_KEY`，一个接口下可以有多个这样的 peer 段。第六行 `endpoint` 对应 `WGPEER_A_ENDPOINT`，是对端的可达地址加端口；NAT 后的 peer 若没有持久 keepalive，endpoint 可能显示为动态学习到的地址而非配置值（keepalive 见 06-11）。第七行 `allowed ips` 对应 `WGALLOWEDIP_A_IPADDR` 与 `WGALLOWEDIP_A_CIDR_MASK`，含义是「只接受源地址在此范围的该 peer 流量，且发往此范围的流量走该 peer」，写错掩码会导致隧道静默不通（原理见 06-07）。第八行 `latest handshake` 是握手距今时间，对应 `WGPEER_A_LAST_HANDSHAKE_TIME`；这是判断隧道是否真正可用的最关键一行——若长期为空或时间很旧，说明握手从未成功或已过期，应优先排查公钥、endpoint 与时钟（握手时序见 06-03）。第九行 `transfer` 分别对应 `WGPEER_A_RX_BYTES` 与 `WGPEER_A_TX_BYTES`，是累计收发字节数；只有握手成功且 allowedips 正确时这里才会增长，若握手成功但字节数为 0，多半是路由没有把目标流量送到 wg0（路由部署见 03-04）。清理环节：`ip link del wg0` 删除接口并释放内核资源，无需单独停止进程，因为数据面本就在内核中。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是把 WireGuard Linux 与 WireGuard 协议、与 wireguard-go / wireguard-nt 混为一谈。协议是规范，Linux 实现是内核模块，wireguard-go 是用户态 Go 实现，wireguard-nt 是 Windows 内核驱动，四者共享协议但代码、性能与部署形态完全不同。本套资料只讲 `drivers/net/wireguard/` 这份内核实现（与 Go 版本的性能差异已在 wireguard-windows 资料的 SUP 文档中讨论）。第二个陷阱是把它当用户态代理：数据面在内核，没有转发进程，用 `ps` 找不到「WireGuard 进程」是正常的，不要据此判断它没运行。

第三个陷阱是混淆三个版本号：`version.h` 的 `1.0.0`、`WIREGUARD_TOOLS_VERSION` 的 `1.0.20260223`、以及目标系统的内核版本，三者独立（版本基准见 01-04）。第四个陷阱是照抄绝对性能数字：吞吐、pps、握手速率一律需在目标机型实测，本套资料不给绝对值（基准方法见 08-01、调优见 08-02）。第五个陷阱是以为有内建密钥服务器：协议没有 CA、没有中心、没有自动分发，公钥交换全靠运维或上层控制面（控制面选型见 wireguard-windows 资料的 DESIGN-07）。

最佳实践可以归纳为四步：先用 `wg --version` 与 `ip link add ... type wireguard` 确认模块可用（构建见 02-03）；再从最小两点配置起步，用 `wg genkey`/`wg pubkey` 规范地生成与分发密钥，私钥永不出本机（密钥流程见 03-03）；随后用 `wg show` 的 `latest handshake` 与 `transfer` 两行确认隧道真正可用，而不是只看接口 up（排障见 08-03）；最后才把 allowedips 收敛到最小必要范围、配置 keepalive 与持久化（部署见 03-04、03-05）。

至于「何时不该用 WireGuard Linux」，边界同样明确：需要中心化用户管理、ACL、SSO 且不打算自建控制面时，单独的内核模块不够，需配合 wg-easy / Headscale 一类控制面；需要与非 WireGuard 协议（如 IPsec、OpenVPN）互通时，它是独立协议，无法直接互通；运行在无法加载内核模块的环境（如某些受限容器、非 Linux 平台）时，应改考虑 wireguard-go 或 wireguard-nt；需要厂商承诺某个绝对吞吐数字时，本套资料不提供这类断言。这些边界与第 2 节能力矩阵互为镜像，应一起对照。

### 7. 小结与延伸阅读

本篇把 WireGuard Linux 定位为「以标准 net_device 形态接入内核协议栈、数据面加解密在内核完成、通过 netlink 由 wg 工具配置、协议本身无内建密钥分发与地址管理的现代 VPN 隧道实现」：能做网卡接入、内核态加解密、Noise_IK 握手、netlink 配置、多 peer 与 AllowedIPs 路由、抗重放与限速；不做中心服务器、不做自动地址分配、不跑 TCP、不与 IPsec 互通。`wg_mod_init` 的分层初始化与 `wg_mod_exit` 的逆序回收、`wg_cmd` 的 GET/SET 两条命令、`wgdevice/wgpeer/wgallowedip` 三层属性枚举，构成后续所有篇章的共同骨架。

延伸阅读建议按三条线走：定位与协议背景读 `drivers/net/wireguard/main.c` 的模块声明与 `include/uapi/linux/wireguard.h`；实现细节按 05 册看结构字段、按 06 册看机制与调用链、按 07 册看模块职责；运维落地读 03 册部署、04 册参数、08 册排障。跨册随查按（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-01）执行：结构体逐字段去 05、参数与命令全集去 04、机制与调用链去 06、目录级模块能力去 07、运维场景与基准去 08。凡本篇标注「需对照实际版本核验」的字段、函数名签名、命令选项与版本号，均以 `_wglinux_build/upstream_src/` 下对应文件为准，本套资料不编造未核验的路径与取值。

## 01-02 与 IPsec / OpenVPN / wireguard-go / wireguard-nt 的实现对比

### 1. 背景与动机

选型与澄清误解都需要一张准确的对比图。关于 WireGuard 的许多争论，其实源于把「协议」与「具体实现」混为一谈：有人拿 IPsec 的吞吐量直接对比 wireguard-go，有人把 wireguard-nt 的 Windows 集成特性当成 Linux 内核版也具备，还有人以为 OpenVPN 和 WireGuard 是同一类东西的不同配置。本篇的目的不是评高下，而是按「实现形态」这一维度，把 WireGuard Linux 与四类常见对象摆到一起，给出可执行的判断依据。口径声明：对 WireGuard Linux 的所有结论以本快照源码为准；对 IPsec、OpenVPN 只作业界通行的定性描述，对 wireguard-go、wireguard-nt 依据其官方定位与架构特征，均不做源码级断言，具体能力需对照各自实际版本核验；本套资料不写绝对性能数字。

先看四个对比对象各自的实现形态。IPsec 是一组协议族（ESP/AH/IKE），在 Linux 上由内核的 xfrm 框架与用户态的 strongSwan / Libreswan 等 IKE 守护进程配合实现；它支持 AES-GCM、ChaCha20-Poly1305 等多种 AEAD，可借助 AES-NI、QAT 等硬件加速。OpenVPN 是用户态程序，基于 TLS 握手与自研的 UDP/TCP 承载，加密走 OpenSSL，数据面在用户态、存在内核与用户态拷贝。wireguard-go 是 WireGuard 协议的用户态 Go 实现，官方主页明确写着在 Linux 上应改用内核模块，因为内核模块「faster and better integrated into the OS」；它以 TUN 设备形态工作，依赖 Go runtime。wireguard-nt 是面向 Windows 的内核驱动，供 Windows 平台使用。WireGuard Linux 则是本篇主角：内核态、net_device 形态、netlink 配置。

为什么实现形态比协议本身更影响选型？因为数据面的位置决定了拷贝开销与并发模型。WireGuard Linux 的加解密在内核完成，包从网卡到隧道封装全程不跨用户态边界；wireguard-go 与 OpenVPN 的数据面在用户态，每个包要进出内核的 TUN 设备，引入拷贝与调度开销。这也是之前讨论高性能 VPN 时反复强调的结论：内核态实现（wireguard-linux、wireguard-nt）数据面性能最高，用户态的 wireguard-go 明显更低——不是实现优劣，而是架构决定的性能与兼容性取舍。

进一步拆开，用户态实现的开销来自三处：其一， packet 从内核协议栈经 TUN 设备读到用户态进程，再从用户态写回内核，至少两次跨边界拷贝；其二， Go 或 OpenSSL 的运行时调度与 GC（对 Go 而言）会在数据路径上引入不可预测的延迟抖动；其三，用户态程序无法直接利用网卡的多队列与内核的 GSO/GRO 卸载，批量处理能力受限。内核态实现则规避了这三处：包以 `sk_buff` 形态在内核各子系统间传递，加密函数直接调用内核 crypto 原语，多队列 RSS 与 padata 并行加密可与现有内核基础设施对接。当然，内核态并非没有代价——它必须遵守内核编程约束（不能睡眠的上下文、RCU 生命周期、内存分配限制），开发与调试难度显著高于用户态，这也是 wireguard-go 存在的意义：在无法加载内核模块的平台或需要快速迭代的场景，用户态实现仍有无可替代的价值（其平台适配细节见 wireguard-windows 资料 SUP-01）。

还有一个常被忽略的维度是「审计面」。WireGuard 协议的代码量本身很小（内核驱动约 4800 行，含头文件），这让它成为少数可以被完整审计的 VPN 实现；相比之下，OpenVPN 依赖庞大的 OpenSSL，IPsec 涉及 xfrm、IKE 守护进程与多套协议协商，审计面大得多。实现形态与此直接相关：内核态实现把协议逻辑压缩到数据结构的直接操作上，用户态实现则往往携带更多运行框架。选型时若「可审计性」是硬指标（如高安全场景），这一点应与性能同等看待。

### 2. 核心概念

对比的底层逻辑是「协议自由度」与「实现代价」的权衡。WireGuard 协议把对称加密固定为 ChaCha20-Poly1305、把握手固定为 Noise_IK，这带来极简的实现与审计面，但也意味着所有合规实现必须逐字节兼容，兼容性测试是持续投入。IPsec 与 OpenVPN 的加密套件、握手方式都是可协商的，灵活但复杂。这直接决定了一个关键判断：如果目标是与标准 WireGuard 对端互通，实现就必须遵循 WireGuard 的消息格式与状态机；如果两端都是自有设备，才可能考虑自定义（但这已不是 WireGuard）。

需要厘清「互通」的准确含义。WireGuard Linux 与 wireguard-go、wireguard-nt、官方 App、OpenBSD 内核版之间可以互通，因为它们是同一协议的不同实现，共享 `messages.h` 定义的消息布局、Noise_IK 握手、抗重放窗口与 cookie 机制。但它与 IPsec ESP、OpenVPN 之间不存在协议级互通——那是完全不同的协议，需要网关做协议转换，而转换两端的安全上下文无法直接传递。把「都能加密上网」等同于「可以互通」是常见误解。

下表按实现形态给出五者的对比，结论以各实现的官方定位与本快照源码为依据。

| 维度 | WireGuard Linux | wireguard-go | wireguard-nt | IPsec（Linux xfrm） | OpenVPN |
|---|---|---|---|---|---|
| 实现形态 | 内核模块 | 用户态 Go 程序 | Windows 内核驱动 | 内核 xfrm + 用户态 IKE | 用户态程序 |
| 数据面位置 | 内核态 | 用户态 | 内核态 | 内核态 | 用户态 |
| 接口形态 | net_device | TUN | Wintun 适配器 | xfrm 策略 | TUN/TAP |
| 配置面 | netlink + wg | wg(8) + UAPI | 命令行/服务 | strongSwan 等 IKE | 配置文件 + 管理接口 |
| 对称加密 | ChaCha20-Poly1305（固定） | 同协议 | 同协议 | 多种 AEAD 可协商 | OpenSSL 多种 |
| 协议互通 | 标准 WireGuard | 标准 WireGuard | 标准 WireGuard | IPsec | OpenVPN |

### 3. 关键数据结构与源码位置

本篇的对比落点仍回到 WireGuard Linux 的源码结构，借此说明「内核态实现」具体体现在哪些数据结构上。与「net_device 形态」对应的是 `device.c` 中的 `wg_device`，它内嵌 `struct net_device`，并注册 `wg_open`、`wg_stop`、`wg_start_xmit` 等 netdev 操作（字段见 05-02）；这是它区别于用户态 TUN 实现的根本——用户态实现拿的是文件描述符，内核态实现拿的是 netdev 结构。与「内核态加解密」对应的是 `send.c`、`receive.c` 直接操作 `sk_buff`，并调用 `lib/crypto/` 的加密函数，全程无用户态拷贝（字段见 05-06、原理见 06-05、06-06）。与「netlink 配置」对应的是 `include/uapi/linux/wireguard.h` 的属性枚举与 `main.c` 的 `wg_genetlink_init()`（原理见 06-14）。

对照之下，wireguard-go 的用户态形态决定了它依赖 TUN 设备与 Go runtime，其数据结构围绕 `net.Conn`、TUN 设备抽象与 goroutine 调度组织；wireguard-nt 的内核态形态类似 Linux 版但绑定 Windows 网络栈（Wintun、NDIS）。这些对照只作定性说明，本套资料不展开非本项目的源码结构。

理解这层差异，对阅读本套资料有个实际好处：当你看到 `wg_device` 内嵌 `net_device`、并挂接 `ndo_start_xmit` 时，就能明白「为什么配置 WireGuard 要先 `ip link add`」——因为内核必须先有一个 netdev 对象，WireGuard 的数据面入口才存在；而用户态实现不需要这一步，它启动的就是一个进程。同理，当你看到 `send.c` 直接操作 `sk_buff` 时，就能理解「为什么 WireGuard Linux 没有独立的转发进程」——数据包在内核子系统之间流转，不需要任何用户态程序介入。把数据结构的形态和运行时的进程形态对应起来，是读懂内核态实现的关键思维。这也提示了一种排障思路：内核态实现的故障往往表现为 netdev 状态、路由、netlink 属性层面的异常，而不是进程崩溃；`wg show` 输出的每一行都直接对应内核里的一个属性，这正是下一节命令实例要展示的。

### 4. 关键流程与调用链

从调用链角度最能看清五者差异。WireGuard Linux 的出站路径是「内核路由 → wg0 的 ndo_start_xmit → send.c 封装加密 → UDP socket 发出」，全程在内核态同步完成，没有上下文切换（完整链路见 06-05）。wireguard-go 的出站路径是「TUN 读 → Go 程序封装加密 → UDP socket 发出」，每个包要跨内核/用户态边界两次。OpenVPN 类似但有 TLS 记录层开销。IPsec 的出站路径是「内核路由 → xfrm 策略匹配 → ESP 封装加密 → 物理网卡」，同样在内核态，但策略与 SA 由 IKE 守护进程异步维护。

配置链路差异同样显著。WireGuard Linux 用 `wg` 通过 netlink 直接读写内核状态（`WG_CMD_SET_DEVICE` / `WG_CMD_GET_DEVICE`），配置即时生效且无独立守护进程；wireguard-go 通过 UAPI socket 配置，需要一个常驻进程；IPsec 需要 IKE 守护进程协商 SA 并维护内核 xfrm 状态；OpenVPN 多用配置文件与控制通道。这也解释了为什么 WireGuard 常被评价为「配置极简」：它没有守护进程、没有协商协议、没有证书体系，配置就是几条 `wg set`。

### 5. 配置/命令/代码实例

本篇给出一条有代表性的对照命令：查看 WireGuard Linux 接口状态用 `wg show`，而查看 IPsec 状态用 `ip xfrm state` 或 `swanctl --list-sas`，两者的输出形态差异正好体现配置模型的区别。

```bash
# WireGuard Linux：直接读内核接口的 netlink 状态
wg show wg0
# IPsec：读内核 xfrm SA（需先在用户态由 IKE 建立）
ip xfrm state
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
# wg show wg0 的输出
interface: wg0
  public key: <公钥>
  listening port: 51820
peer: <对端公钥>
  latest handshake: 3 minutes ago
  transfer: 4.02 KiB received, 3.10 KiB sent

# ip xfrm state 的输出
src 198.51.100.1 dst 198.51.100.2
  proto esp spi 0x0a1b2c3d reqid 1 mode tunnel
  auth-trunc hmac(sha256) <key> 96
  enc aes-gcm <key> 16
  replay-window 32
```

逐行判读如下。第一组是 `wg show wg0`：`interface` 与 `public key`、`listening port` 三行来自 `WG_CMD_GET_DEVICE` 返回的 device 属性，描述接口自身；`peer` 段来自 `WGPEER_A_*` 属性。`latest handshake` 是判断 WireGuard 隧道可用性的核心，WireGuard 是静默协议，认证失败只丢包不回错误，所以这一行是排障第一入口（排障见 08-03）。`transfer` 是累计收发字节，对应 `WGPEER_A_RX_BYTES` / `WGPEER_A_TX_BYTES`。第二组是 `ip xfrm state`：一条 SA 由 `src`/`dst`、`proto esp`、`spi`、`reqid`、`mode` 描述，`auth-trunc` 与 `enc` 给出认证与加密算法及密钥，`replay-window` 是抗重放窗口。对比可见，IPsec 的 SA 是由 IKE 协商出来的一组带生命周期的安全关联，需要守护进程维护；而 WireGuard 的 peer 状态是静态配置加握手演进的会话密钥，没有独立的 SA 协商层。这正是「配置极简」的具体含义——少了一整套 IKE 协商与 SA 生命周期管理。清理环节：WireGuard 用 `ip link del wg0` 删除接口即释放全部状态；IPsec 需 `ip xfrm state flush` 或停止 IKE 守护进程，步骤更多。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是把「协议相同」等同于「实现可互换」。五种实现共享 WireGuard 协议时可以互通，但 wireguard-go 的用户态实现与 WireGuard Linux 的内核实现在性能、部署形态、依赖上完全不同，不能因为协议一样就假设性能一样。第二个陷阱是把 wireguard-nt 的特性套到 Linux：wireguard-nt 是 Windows 驱动，其 Wintun 适配器、服务模型与 Linux 的 net_device、netlink 无关。

第三个陷阱是拿不同实现的绝对性能数字横比。加密是否走内核、是否有硬件加速、包长与 CPU 特性都会影响结果，脱离测试条件谈「A 比 B 快」没有意义；本套资料一律标注「需在目标机型实测」（基准方法见 08-01）。第四个陷阱是把互通范围夸大：WireGuard 与 IPsec、OpenVPN 不互通，需要网关转换且安全上下文无法透传。第五个陷阱是忽略许可差异：WireGuard Linux 是 GPLv2（`main.c` 的 `MODULE_LICENSE("GPL v2")`），wireguard-go 是 MIT，闭源商用时需分别评估（许可见 01-04）。

最佳实践：选型先问「对端是谁」——标准 WireGuard 对端就选 WireGuard Linux（Linux）或对应平台实现，需与 IPsec/OpenVPN 生态互通则考虑网关或改用对应协议；再问「数据面位置是否受限」——能加载内核模块就用内核态实现拿性能，受限环境才退回 wireguard-go；最后问「是否需要控制面」——内核模块只解决数据面，用户管理与密钥分发需另配（控制面选型见 wireguard-windows 资料 DESIGN-07）。这三个问题的顺序不能颠倒：先定互通范围，因为协议不兼容是硬约束，无法通过调优绕开；再定数据面形态，因为它决定性能上限与部署条件；最后才谈控制面，因为它是可叠加的上层能力，不影响底层协议选择。把顺序搞反，常见后果是先用 wireguard-go 跑通了功能、再发现性能不够，却已经把架构绑死在用户态，回头换成内核实现要重做整套部署与配置链路。

### 7. 小结与延伸阅读

本篇按实现形态把 WireGuard Linux 与 wireguard-go、wireguard-nt、IPsec、OpenVPN 做了对比：WireGuard Linux 的内核态 net_device 形态带来无用户态拷贝的数据面与极简的 netlink 配置面；wireguard-go 是用户态实现，官方在 Linux 上不优先推荐；wireguard-nt 面向 Windows；IPsec 与 OpenVPN 是不同协议，不与 WireGuard 互通。判断选型的核心是「实现形态决定性能与复杂度」，而非协议名称。

延伸阅读：协议与实现的关系见 wireguard-windows 资料 SUP-01；性能取舍见该资料 SUP-03；本册后续两篇分别处理架构（01-03）与版本许可生态（01-04）。跨册随查按（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-01）执行。凡需具体字段、常量与函数签名的细节，均以 `_wglinux_build/upstream_src/` 下对应文件为准，本套资料不编造未核验的路径与取值。
