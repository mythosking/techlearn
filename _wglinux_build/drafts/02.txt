# WireGuard Linux 技术资料 · 02 编译与构建

## 02-01 源码获取、内核树目录结构与依赖矩阵

### 1. 背景与动机

要编译 WireGuard Linux，第一步不是敲下 make，而是先搞清楚「编译的对象究竟是什么、源码从哪里来、它需要哪些内核能力作为前提」。这三件事看似基础，却是后续所有构建、集成与排障工作的地基。很多人在这一步栽跟头，不是因为编译命令写错，而是因为拿错了源码、看错了目录、或者漏掉了某个在 Kconfig 里被 `select` 拉进来的底层库，结果要么编译直接失败，要么模块勉强编出来却在运行时出现难以解释的行为。本篇的任务就是把这三件事一次性讲清楚：源码获取的来源与版本基准、内核树中 WireGuard 相关目录的层级结构、以及由 Kconfig 条目决定的依赖矩阵。需要先把边界说明在前面——本篇只负责「源码与依赖的静态地图」，真正的编译命令、insmod 与 dkms 操作留给 02-03，用户态工具的具体编译留给 02-04，调试与自检构建留给 02-05；至于运行期会用到的各种命令参数与常量全集，属于 04 册的权威范围，本篇只给理解构建所必需的最小片段，细节交叉引用到 04。

为什么强调「源码获取」看似多余？因为 WireGuard Linux 并不是一个可以单独拉下来、独立 configure 再编译的普通软件包。它的内核驱动部分寄生在 Linux 内核树的 Kbuild 体系里，源码分散在 `drivers/net/wireguard/`、`lib/crypto/`、`include/uapi/linux/` 等多个目录，构建时必须借助内核顶层的 Makefile 与配置系统。这意味着你获取的「源码」实际上是一整棵内核源码树，而不是一个独立的 WireGuard 目录。本套资料的事实锚点是 `_wglinux_build/upstream_src/` 下的两份快照：`wireguard-linux-src/`（stable 分支内核驱动快照）与 `wireguard-tools/`（版本 1.0.20260223，2026-03 抓取）。下文出现的路径若无特别说明，均相对这两个根目录。把这两份快照当作唯一权威，是为了避免把某个发行版二次打过补丁的版本、或者某个旧版本博客文章里的路径，误当成上游当前的实现。

版本基准必须在这里说清，因为它贯穿全册。WireGuard Linux 至少牵涉三个彼此独立的版本号：内核驱动自身的版本，写在 `drivers/net/wireguard/version.h`，值为 `WIREGUARD_VERSION "1.0.0"`；用户态工具的版本，写在 `wireguard-tools/src/version.h`，默认值为 `WIREGUARD_TOOLS_VERSION "1.0.20260223"`，同时工具的 Makefile 会用 `git describe --dirty` 动态覆盖它；以及目标系统实际运行的内核版本，它决定了这份驱动快照能否直接套用。三者没有任何同步关系：驱动版本号从 1.0.0 发布以来几乎不变，工具版本号却随每次发布滚动，而内核版本由发行版或自行编译决定。把这三个号混为一谈，是在阅读上游邮件列表和构建日志时最常见的误读来源之一（版本基准的完整约定见 01-04）。

还有一个容易被忽略的版本特征值得在动机部分点明：本快照的 uapi 头 `include/uapi/linux/wireguard.h` 顶部写着「Do not edit directly, auto-generated from: Documentation/netlink/specs/wireguard.yaml」，说明当前上游已经把 netlink 定义纳入 YAML 规范统一管理，对应的内核 Makefile 里也因此出现了 `netlink.o generated/netlink.o` 这样的条目，而更早的实现常见的是 `sysfs.c` 加手写 netlink 代码。这是一个真实的代际差异：如果你手里有一份旧资料，按图索骥去找 `sysfs.c` 或手写的 `netlink.c`，在本快照里是找不到的。换句话说，「源码目录长什么样」本身就带有版本信息，获取源码时必须同时记录它对应的代际，这也是本篇把「获取」与「目录结构」放在一起讲的原因。

### 2. 核心概念

理解本篇需要先把四个概念拧清楚：两套源码树的分工、Kbuild 的两级 Makefile 挂载、Kconfig 中 `depends on` 与 `select` 的语义差别、以及「手写源文件」与「生成源文件」的区别。

两套源码树的分工是第一层。内核树 `wireguard-linux-src/` 提供数据面：所有加解密、握手、收发、路由逻辑都在内核态，以 `net_device` 的形态接入协议栈；用户态工具树 `wireguard-tools/` 提供控制面：`wg` 命令通过 netlink 把配置写进内核，配套有 `wg-quick` 脚本、bash 补全与 systemd 单元。两棵树独立获取、独立编译、独立版本化，构建时互不依赖——编译内核模块不需要先编译工具，编译工具也不需要内核源码（只需要内核导出的 uapi 头，而那份头通常已随系统安装）。这种解耦是 WireGuard 设计哲学的一部分：控制面可以随意替换成第三方实现，数据面保持极简稳定。

Kbuild 的两级挂载是第二层。内核里任何驱动的编译都由两级 Makefile 接力完成：上层 `drivers/net/Makefile` 用 `obj-$(CONFIG_WIREGUARD) += wireguard/` 决定「要不要进入这个子目录」，下层 `drivers/net/wireguard/Makefile` 用 `wireguard-y` 列出源文件、用 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 把目标文件聚合成模块。注意这里的 `$(CONFIG_WIREGUARD)` 是一个由配置系统替换的变量：当配置为 `=m` 时它展开为 `m`，`obj-m` 触发可加载模块 `wireguard.ko` 的构建；当配置为 `=y` 时它展开为 `y`，`obj-y` 把代码直接编进内核镜像；当为 `=n` 时两处都不生效，目录被整体跳过。理解这个替换机制，就能明白为什么「打开一个 Kconfig 开关」会同时改变上下两级 Makefile 的行为。

`depends on` 与 `select` 的语义差别是第三层，也是依赖矩阵的核心。`depends on NET && INET` 表示本选项只有在 `NET` 与 `INET` 都已经启用时才可见、可选——这是「前置条件」，不满足时选项根本不会出现在配置菜单里，更无法打开。而 `select CRYPTO_LIB_CURVE25519` 等语句表示「一旦打开本选项，就自动把这些底层库也打开」，这是「反向拉取」，目的是保证用户不需要手动去理解和勾选一堆密码学依赖。前者是约束，后者是便利；前者不打开就无从谈起，后者不手动管也会被自动满足。混淆这两者，是阅读 Kconfig 时最典型的错误。

「手写源文件」与「生成源文件」的区别是第四层。在本快照的 `drivers/net/wireguard/Makefile` 里，`wireguard-y` 大部分条目是 `.c` 文件编译而来的 `.o`，对应仓库里真实存在的源文件；但 `generated/netlink.o` 不同，它的输入来自 netlink YAML 规范经工具生成的代码，在源码快照里往往并不落地为静态文件（本快照的 `generated/` 目录就是空的甚至不存在，构建时由 Kbuild 现场生成）。这意味着你在源码树里「看不到」某个 .o 对应的 .c，并不等于构建会失败——它是被生成出来的。这一点对建立正确的源码地图至关重要，后面第 3、6 节还会回到它。

最后用一个概念表把上述术语收拢，便于对照后文。

| 概念 | 含义 | 在本主题中的落点 |
|---|---|---|
| 内核树快照 | 含驱动与加密原语的整棵内核源码 | `wireguard-linux-src/` |
| 工具树快照 | 用户态控制面源码 | `wireguard-tools/` |
| 三态选项 | 可设为 Y / M / N 的配置项 | `config WIREGUARD` |
| depends on | 前置条件，不满足则选项不可见 | `NET && INET` |
| select | 打开本项时自动拉起依赖 | `CRYPTO_LIB_*` 等 |
| 生成源文件 | 由规范经工具生成的 .o | `generated/netlink.o` |

### 3. 关键数据结构与源码位置

作为构建册的静态地图，本节只点名目录与关键文件、给出真实路径，不展开任何结构体的逐字段定义（字段统一见 05 册，例如设备结构见 05-02、对等体结构见 05-03），也不深入运行机制（原理见 06-01）。把源码位置按「树—目录—文件」三级铺开，能得到一张清晰的地图。

第一级是内核树根。`wireguard-linux-src/` 下与本篇直接相关的有三个位置：`drivers/net/wireguard/` 是驱动主体目录，几乎所有内核态源文件都在这里；`lib/crypto/` 存放被 select 拉进来的加密原语实现，包括 ChaCha20-Poly1305、Curve25519、Blake2s 等；`include/uapi/linux/wireguard.h` 是用户态与内核态共享的 ABI 头，定义族名、版本、命令与属性枚举。此外 `Documentation/netlink/specs/wireguard.yaml` 被 uapi 头注释明确引用，是生成 netlink 代码的规范源，但在本快照中未随驱动一并落地，引用时需标注「需对照实际版本核验」。

第二级是驱动目录内部。`drivers/net/wireguard/Makefile` 是本篇与下一篇的主角，它决定了源文件如何聚合成模块；`version.h` 只有一行，定义驱动版本字符串。源文件按职责分布：`main.c` 是模块入口与 netdev 注册，`device.c` 管设备生命周期，`peer.c` 管对等体，`allowedips.c` 实现路由 trie，`noise.c` 与 `messages.h` 负责握手与消息布局，`send.c` / `receive.c` 负责收发，`socket.c` 管 UDP socket 与 endpoint，`timers.c` 管定时器，`ratelimiter.c` 与 `cookie.c` 负责限速与 DoS 防护，`queueing.h` 是队列相关的头文件。这些名字都能在 Makefile 的 `wireguard-y` 列表里一一对应（逐模块职责见 07 册，例如入口见 07-01、收发见 07-07、07-08）。

这里必须诚实指出一个快照特征：Makefile 里还列了 `peerlookup.o` 与 `netlink.o generated/netlink.o`，但本地 `drivers/net/wireguard/` 目录里并没有 `peerlookup.c`、`netlink.c`，也没有 `generated/` 子目录，`selftest/` 子目录则是空的。这说明本快照是一份经过挑选的源码切片，而非完整内核树。撰写与核验时，凡涉及这些「Makefile 引用但本地未落地」的文件，都要写清楚「本快照未包含，需对照完整内核源码树核验」，绝不能假装在目录里看到了它。这种诚实标注本身就是技术写作的一部分。

第三级是用户态工具树。`wireguard-tools/src/` 下与构建相关的是 `Makefile`（注意它在 `src/` 子目录，仓库根目录并没有 Makefile，任务描述里的「tools/Makefile 若存在」应以实际路径为准）、`wg.c`（命令入口）、`config.c`（配置解析）、`encoding.c`（密钥编解码）、`curve25519.c` 与两个 `curve25519-*.h`（密钥运算后端）、`ipc.c` 与 `ipc-linux.h` 等一族 IPC 抽象、`netlink.h`、`version.h`，以及 `wg-quick/`、`completion/`、`systemd/`、`man/`、`uapi/` 等子目录。仓库根还有 `COPYING`、`README.md` 与 `contrib/`。工具树的编译与内核模块完全分离，其 Makefile 会探测 `pkg-config`、bash 与 systemd 的安装位置来决定是否附带 wg-quick、bash 补全与 systemd 单元（这部分的完整构建流程见 02-04，模块职责见 07-13）。

下表把本篇反复引用、且确实存在于快照中的源码位置收拢成速查表。

| 关注点 | 真实源码路径 | 本册处理方式 |

### 4. 关键流程与调用链

从「拿到源码」到「产出模块」，存在一条可以逐段拆解的链路。第一段是源码获取：分别取得内核树快照与工具树快照，并记录各自的代际与版本。第二段是配置挂载：内核顶层的 `drivers/net/Kconfig` 提供 `config WIREGUARD` 与 `config WIREGUARD_DEBUG` 两个条目，用户通过 `make menuconfig` 一类界面把前者设为 M 或 Y。第三段是目录进入：`drivers/net/Makefile` 中的 `obj-$(CONFIG_WIREGUARD) += wireguard/` 在配置为 M 或 Y 时把构建流程引入驱动子目录。第四段是目标聚合：`drivers/net/wireguard/Makefile` 把 `wireguard-y` 列出的全部目标文件聚合为单一的 `wireguard.o`，再由 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 决定产出 `wireguard.ko`（=m）还是链入内核镜像（=y）。第五段是依赖解析：`select` 拉起的 `CRYPTO_LIB_*` 从 `lib/crypto/` 提供实现，`generated/netlink.o` 由 YAML 规范经工具现场生成。这条链路把本篇的三个主题——获取、目录、依赖——串成了一条时间线。

需要把「配置链路」与「数据链路」区分开，避免把本篇和 06 册混为一谈。本篇关心的是构建期的静态链路：Kconfig 符号如何展开成 Makefile 变量、目录如何被递归进入、目标文件如何聚合。而 `wg_mod_init` 里的 `wg_allowedips_slab_init`、`wg_noise_init`、`wg_peer_init`、`wg_device_init`、`wg_genetlink_init` 这条初始化链，以及运行期 `ndo_start_xmit` 到 `send.c`、UDP socket 到 `receive.c` 的数据链，属于启动与包处理流水线（原理见 06-01）。它们在源码里同样真实存在，但不是本篇要把读者带进去的地方；本篇只在「哪些源文件会被编进模块」这个层面提到它们的文件名。

### 5. 配置/命令/代码实例

本篇的实例不是去编译，而是用几条只读命令把「源码地图」与「依赖声明」实际取出来看。所有命令都在快照根目录下执行，且都只读、不修改任何文件。

```bash
# 1. 查看驱动目录里真实落地的文件
ls drivers/net/wireguard/

# 2. 取出 Kconfig 中 WireGuard 的依赖声明
grep -n -A 12 '^config WIREGUARD$' drivers/net/Kconfig

# 3. 确认上层 Makefile 如何进入子目录
grep -n 'WIREGUARD' drivers/net/Makefile

# 4. 确认两份快照各自的版本字符串
cat drivers/net/wireguard/version.h
cat ../../wireguard-tools/src/version.h
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
Makefile  allowedips.c  allowedips.h  cookie.c  cookie.h  device.c
main.c  messages.h  noise.c  noise.h  peer.c  queueing.h  ratelimiter.c
ratelimiter.h  receive.c  selftest  send.c  socket.c  timers.c  version.h

74:config WIREGUARD
75:	tristate "WireGuard secure network tunnel"
76:	depends on NET && INET
77:	select NET_UDP_TUNNEL
78:	select DST_CACHE
79:	select CRYPTO_LIB_CURVE25519
80:	select CRYPTO_LIB_CHACHA20POLY1305
81:	select CRYPTO_LIB_UTILS

13:obj-$(CONFIG_WIREGUARD) += wireguard/

#define WIREGUARD_VERSION "1.0.0"
#define WIREGUARD_TOOLS_VERSION "1.0.20260223"
```

逐行判读如下。第一段 `ls` 输出列出了目录里真实存在的文件，重点不在逐个文件，而在「缺了什么」：列表里没有 `peerlookup.c`、没有 `netlink.c`、没有 `sysfs.c`，也没有 `generated/` 子目录，`selftest` 是空的，这正印证了第 3 节所说的「快照是切片」——这些名字会出现在 Makefile 里，但本地没有对应源文件，核验时必须去完整内核树找。第二段是 `grep` 带出的 Kconfig 原文：第 74 行 `config WIREGUARD` 定义符号；第 75 行 `tristate` 表明它可取 Y/M/N 三态，引号内是配置菜单显示给用户的描述串；第 76 行 `depends on NET && INET` 是前置条件，要求通用网络与 IPv4 协议栈都已启用，否则该选项不可见；第 77 至 81 行是五条 `select`，分别把 UDP 隧道框架、目的地址缓存、Curve25519、ChaCha20-Poly1305 与密码学工具函数库拉进来，这正是依赖矩阵的源码依据。第三段第 13 行 `obj-$(CONFIG_WIREGUARD) += wireguard/` 说明上层 Makefile 用条件变量控制是否递归进入子目录，注意它用的是追加符号 `+=`，表示在 `drivers/net/` 已有的目标列表基础上增加一项。第四段两行 `version.h` 的内容给出两个独立版本号：驱动侧 `WIREGUARD_VERSION` 是 `1.0.0`，工具侧 `WIREGUARD_TOOLS_VERSION` 是 `1.0.20260223`，二者没有任何同步关系，也不等于目标系统的内核版本；这个差异是排障时判断「你用的是哪一代代码」的第一手证据。把这份输出与第 3 节的地图对照读，就能从「纸面结构」走到「眼见为实」。

需要补充第二个只读片段，把 uapi 头的生成属性也纳入视野。

```text
/* Do not edit directly, auto-generated from: */
/*	Documentation/netlink/specs/wireguard.yaml */
/* YNL-GEN uapi header */
/* To regenerate run: tools/net/ynl/ynl-regen.sh */
```

这几行注释直接来自 `include/uapi/linux/wireguard.h` 的开头，它说明两件事：其一，这份头不是手写的，而是由 `wireguard.yaml` 经 YNL 工具生成的，因此「改头文件」不是正确的扩展方式，正确做法是改规范再重新生成；其二，重新生成的入口脚本是 `tools/net/ynl/ynl-regen.sh`，属于内核树工具目录，本快照未包含。把这条信息与 Makefile 里的 `generated/netlink.o` 连起来看，就能理解为什么本代实现会同时出现「生成的 uapi 头」与「生成的 netlink 目标文件」，它们是同一套 YAML 规范驱动下的两个产物。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是混淆三个版本号。驱动的 `1.0.0`、工具的 `1.0.20260223` 与目标内核版本各自独立，讨论兼容性时必须说明指的是哪一个（版本约定见 01-04）。第二个陷阱是把这份驱动快照当成可以独立编译的软件包。它没有自己的顶层 configure，必须放进内核树的 Kbuild 体系，借 `drivers/net/Kconfig` 与 `drivers/net/Makefile` 才能被编译；直接对驱动目录跑 make 不会得到可用的内核模块。

第三个陷阱是照抄旧资料的目录清单。旧实现常见的 `sysfs.c`、手写 `netlink.c` 在本快照里都不存在，取而代之的是 `netlink.o generated/netlink.o` 的生成式代码；看到差异先怀疑版本代际，而不是怀疑自己拿错了分支。第四个陷阱是把用户态工具的 Makefile 与内核 Makefile 混为一谈。工具构建入口在 `wireguard-tools/src/Makefile`，用的是 `pkg-config`、`PREFIX`、`BINDIR` 这类变量；内核构建用的是 Kbuild 的 `obj-y`/`obj-m`、`ccflags-y` 与 `wireguard-y`，两者语法体系完全不同（工具构建流程见 02-04，内核构建配置见 02-02）。

第五个陷阱最隐蔽：看到 Makefile 列了 `peerlookup.o`、`netlink.o` 却在目录里找不到对应 `.c`，就断定源码不完整或构建必然失败。实际情况是快照经过挑选，加上部分目标由生成流程提供，本地缺失并不等于完整内核树里也缺失。正确做法是明确标注「本快照未包含，需对照完整内核源码树核验」，而不是给出武断结论。第六个陷阱是忽略依赖矩阵的业务含义：`select CRYPTO_LIB_CURVE25519` 与 `CRYPTO_LIB_CHACHA20POLY1305` 不是可有可无的装饰，它们分别对应密钥交换与对称加密所需的原语，缺了会导致链接失败；`NET_UDP_TUNNEL` 与 `DST_CACHE` 则关系到 UDP 承载与目的缓存路径（这些库的函数级原理见 06-03、06-12，本篇只需知道它们被依赖）。

最佳实践可以归纳成四步。第一步，获取源码时同时记录内核树快照的代际与工具树的版本字符串，必要时把 `git describe` 的结果一并留存，让后续任何一次构建都能回溯到确切的代码状态。第二步，在动编译命令之前，先用本篇第 5 节的只读命令把 Kconfig 依赖、Makefile 挂载点与版本号实际取出来核对一遍，确认「看到的」与「以为的」一致。第三步，把依赖矩阵当作编译前的检查清单：确认 `NET`、`INET` 已启用，确认五个 `select` 目标在当前内核配置下可满足，尤其是加密库在裁剪型内核里可能被裁剪掉（具体编译步骤见 02-03）。第四步，凡遇到快照缺失或生成代码相关的问题，先标注「需对照实际版本核验」，再去完整源码树或目标系统求证，不凭记忆下结论。这四步的共同精神是：把构建当成一条可观测的链路，而不是一串不可解释的咒语。

### 7. 小结与延伸阅读

本篇把 WireGuard Linux 的构建前置知识整理成一张静态地图：源码来自内核树快照 `wireguard-linux-src/` 与工具树快照 `wireguard-tools/` 两份，前者提供数据面并寄生在 Kbuild 体系中，后者提供独立的控制面；内核树里与构建直接相关的位置是 `drivers/net/wireguard/`（驱动主体与 Makefile、version.h）、`lib/crypto/`（被 select 拉起的加密原语）与 `include/uapi/linux/wireguard.h`（由 YAML 规范生成的 ABI 头）；依赖矩阵由 `config WIREGUARD` 的 `depends on NET && INET` 与五条 `select` 语句共同定义，分别约束可见性并自动拉取底层库。源码到模块的链路是「获取快照 → Kconfig 配置 → 上层 Makefile 进入目录 → 下层 Makefile 聚合目标 → 产出模块或内建镜像」，其中 `generated/netlink.o` 体现的是当前代际的生成式代码特征。三个独立版本号与「快照是切片、部分文件未落地」这两点，是阅读时最需要保持警觉的地方。

延伸阅读建议按三条线走：想要把目录里的每个文件对号入座，读 07 册各模块篇，入口见 07-01、收发见 07-07、07-08、工具见 07-13；想要理解被依赖的原语与握手机制，读 06 册，启动流水线见 06-01、密钥派生见 06-03、UDP 封装见 06-12；想要拿到命令、常量与 uapi 定义的全集，读 04 册，uapi 常量见 04-06。跨册随查按（字段见 05-01 ｜ 参数见 04-06 ｜ 原理见 06-01 ｜ 模块见 07-01）执行：结构体逐字段去 05、命令与常量全集去 04、机制与调用链去 06、目录级模块能力去 07、运维与基准去 08。本篇所有标注「需对照实际版本核验」的路径与取值，均以 `_wglinux_build/upstream_src/` 下对应文件为准；编译参数与具体操作细节是 04 册与 02-03 的范围，这里不做展开。下一篇将把目光从静态地图转向动态配置，逐行拆解 Kconfig 与 Makefile 的每一条语句。

## 02-02 内核 Kconfig / Makefile 与 CONFIG_WIREGUARD 构建配置

### 1. 背景与动机

上一篇给出了源码与依赖的静态地图，本篇要把地图上的两条关键配置线路逐行拆开：一条是 Kconfig，它决定「这个选项是否存在、可取哪些值、依赖谁、又拉起谁」；另一条是 Makefile，它决定「配置值如何变成编译动作、哪些源文件被聚合、最终产出什么」。这两条线在内核里并不是各说各话，而是通过同一个符号 `CONFIG_WIREGUARD` 咬合在一起——Kconfig 定义符号并让用户给它赋值，Makefile 读取这个符号并据此改变行为。理解这种「定义—消费」的对应关系，是读懂任何内核驱动构建配置的关键，也是本篇的中心任务。

先明确边界，避免与相邻篇章重叠。本篇只讲「构建配置」本身：Kconfig 条目怎么读、`obj-y`/`obj-m` 与 `wireguard-y` 怎么展开、调试开关如何影响编译参数。从零开始的实际编译、insmod 加载、dkms 兼容路径属于 02-03；用户态工具 wg 与 wg-quick 的构建属于 02-04；调试构建的更深用法、动态调试与静态检查属于 02-05。至于运行期命令的参数全集、netlink 属性常量全集、模块参数与 sysfs 接口全集，分别是 04-01、04-05、04-06、04-07 的权威范围，本篇只在需要说明配置语义时给出最小片段，细节一律交叉引用到 04。换句话说，本篇回答「为什么这样配置会产生这样的构建结果」，而不回答「某条命令有哪些参数」。

为什么值得花一整篇讲几条看似简单的语句？因为 Kconfig 与 Makefile 是内核构建系统的通用语言，WireGuard 只是这套语言的一个具体用例。同一套 `config`/`tristate`/`depends on`/`select` 语法支配着内核里几千个选项，同一套 `obj-y`/`obj-m`/`*-y` 约定支配着所有驱动的编译。把 WireGuard 的这几条语句吃透，等于掌握了一把能打开任意内核驱动构建配置的钥匙。而且这几条语句里藏着不少容易误读的细节：比如 `:=` 与 `+=` 的差别、`ccflags-y` 里 `pr_fmt` 的引号形式、`tristate` 与 `bool` 的取值集合、`select` 与 `depends on` 的方向性。这些细节平时不起眼，一旦理解偏差，就会在编译失败或行为异常时把排查引向错误方向。

本快照里与本篇直接相关的源码只有四处，但每一处都信息密集：`drivers/net/Kconfig` 第 74 至 101 行给出 `config WIREGUARD` 与 `config WIREGUARD_DEBUG` 两个条目；`drivers/net/Makefile` 第 13 行给出进入子目录的条件；`drivers/net/wireguard/Makefile` 全文十七行给出编译参数的设置与目标聚合；`drivers/net/wireguard/version.h` 给出驱动版本字符串。下面各节会反复回到这四处，做到「每一条结论都能指回具体行号」。凡本快照未落地的文件（如 `generated/netlink.c`、selftest 实现），一律标注「需对照实际版本核验」，不凭空补全。

### 2. 核心概念

本篇的核心概念可以压缩为五句话：三态取值、两级消费、两个开关方向、两类目标变量、一条调试链。

三态取值，指 `config WIREGUARD` 的 `tristate` 类型决定它可取 Y、M、N 三个值。Y 表示把代码直接编进内核镜像，随内核启动即生效，但无法在运行期单独卸载；M 表示编译成可加载模块 `wireguard.ko`，需要时再载入、不用时可卸载；N 表示不编译，相关代码完全不进入构建。与之相对，`config WIREGUARD_DEBUG` 的 `bool` 类型只能取 Y 或 N——它只是一个编译期开关，没有「编成模块」的中间态。把 `tristate` 与 `bool` 的取值集合搞混，是阅读 Kconfig 时的第一处常见失误。

两级消费，指 `CONFIG_WIREGUARD` 的值被上下两级 Makefile 分别消费。上层 `drivers/net/Makefile` 用 `obj-$(CONFIG_WIREGUARD) += wireguard/` 判断是否递归进入子目录；下层 `drivers/net/wireguard/Makefile` 用 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 判断产出模块还是内建目标。当符号为 M 时，两处的 `$(CONFIG_WIREGUARD)` 都展开为 `m`，于是上层执行 `obj-m += wireguard/`、下层执行 `obj-m := wireguard.o`，最终链接出 `wireguard.ko`；当符号为 Y 时，两处都展开为 `y`，代码链入 `vmlinux`；为 N 时两处分别是 `obj-n`，不产生任何目标。一个符号、两级展开、三种结果，这就是 Kbuild 的精妙之处。

两个开关方向，指 `depends on` 与 `select` 的方向性差别（上一篇已建立基本认识，这里从配置角度再强调）。`depends on NET && INET` 是「向上约束」：本选项依赖更基础的网络与 IPv4 支持，后者不满足时本选项不可选。五条 `select` 是「向下拉取」：一旦本选项打开，就自动把 `NET_UDP_TUNNEL`、`DST_CACHE`、`CRYPTO_LIB_CURVE25519`、`CRYPTO_LIB_CHACHA20POLY1305`、`CRYPTO_LIB_UTILS` 置为选中。对构建而言，前者意味着「不满足就无法构建 WireGuard」，后者意味着「构建 WireGuard 时这些依赖会自动满足，无需手动逐项勾选」。

两类目标变量，指 `obj-*` 与 `*-y` 的分工。`obj-y`/`obj-m`/`obj-n` 是 Kbuild 约定的「输出目标列表」，告诉构建系统本目录要产出什么；`wireguard-y` 是本驱动自定义的「输入源文件列表」，列出要聚合到 `wireguard.o` 里的所有目标文件。两者通过 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 关联：输入列表里的 `.o` 被链接成一个 `wireguard.o`，而这个 `wireguard.o` 又被放进输出列表。记住「`*-y` 是输入、`obj-*` 是输出」，就不难理解为什么 Makefile 里既有 `wireguard-y` 又有 `obj-...`。

一条调试链，指 `WIREGUARD_DEBUG` 从配置到编译参数再到运行行为的贯通。Kconfig 里 `config WIREGUARD_DEBUG` 是 `bool`，依赖 `WIREGUARD`；Makefile 里 `ccflags-$(CONFIG_WIREGUARD_DEBUG) += -DDEBUG` 在该开关为 Y 时向编译命令追加宏 `DEBUG`；源码 `main.c` 里 `#ifdef DEBUG` 包裹着三项自检 `wg_allowedips_selftest()`、`wg_packet_counter_selftest()`、`wg_ratelimiter_selftest()`，任一失败即返回 `-ENOTRECOVERABLE`。这形成「勾选项 → 编译宏 → 条件代码 → 启动期自检」的完整链条，是理解调试开关如何真正生效的范本（自检内容的机制细节见 02-05）。

最后一个容易被忽略的概念是 `ccflags-y` 里的 `pr_fmt`。Makefile 第一行 `ccflags-y := -D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'` 用带引号的宏定义，为驱动所有打印加上模块名前缀；第二行才是在调试开关下追加 `-DDEBUG`。`pr_fmt` 不依赖任何配置，属于「无条件编译参数」，而 `-DDEBUG` 属于「条件编译参数」，二者在 Makefile 里的写法差异（`:=` 与 `+=`）正好体现了「一次性赋值」与「条件追加」的区别。编译参数的完整讨论属于 04 册，这里只点明它们如何随配置变化。

### 3. 关键数据结构与源码位置

本节把四处源码逐行摊开，作为后续流程分析的事实底稿。由于构建册不展开任何运行时结构体（字段见 05-01），这里的「结构」指的是配置文件与 Makefile 的组织结构。

第一处，`drivers/net/Kconfig` 的 `config WIREGUARD` 段。类型为 `tristate`，菜单描述为 `WireGuard secure network tunnel`；`depends on NET && INET` 给出前置条件；五条 `select` 依次是 `NET_UDP_TUNNEL`、`DST_CACHE`、`CRYPTO_LIB_CURVE25519`、`CRYPTO_LIB_CHACHA20POLY1305`、`CRYPTO_LIB_UTILS`；`help` 文本把它描述为 IPsec 的轻量替代，并特别说明「safe to say Y or M here」，因为驱动很轻量、只在管理员添加接口时才被使用。紧随其后的 `config WIREGUARD_DEBUG` 类型为 `bool`，描述为 `Debugging checks and verbose messages`，`depends on WIREGUARD`，`help` 说明它会打印握手等事件的日志并做额外校验与单元测试，最后一句是「Say N here unless you know what you're doing」。这两段是本篇全部配置语义的源头。

第二处，`drivers/net/Makefile` 第 13 行 `obj-$(CONFIG_WIREGUARD) += wireguard/`。这一行夹在 `obj-$(CONFIG_IPVTAP) += ipvlan/`、`obj-$(CONFIG_DUMMY) += dummy.o` 与 `obj-$(CONFIG_OVPN) += ovpn/` 之间，说明 WireGuard 与其他虚拟网络设备并列注册在 `drivers/net/` 这一层。末尾的斜杠 `wireguard/` 表示这是一个子目录目标，Kbuild 会递归进入该目录继续处理它的 Makefile。

第三处，`drivers/net/wireguard/Makefile` 全文。第 1 行 `ccflags-y := -D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'` 设置无条件编译参数；第 2 行 `ccflags-$(CONFIG_WIREGUARD_DEBUG) += -DDEBUG` 在调试开关下追加宏；第 3 至 16 行用 `wireguard-y += ...` 逐项列出输入目标，顺序为 `main.o`、`noise.o`、`device.o`、`peer.o`、`timers.o`、`queueing.o`、`send.o`、`receive.o`、`socket.o`、`peerlookup.o`、`allowedips.o`、`ratelimiter.o`、`cookie.o`、`netlink.o generated/netlink.o`；第 17 行 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 完成聚合。注意第 17 行用的是 `:=`，与上一节 `obj-$(CONFIG_WIREGUARD) += wireguard/` 的 `+=` 并不相同，这个差别在第 6 节专门讨论。

第四处，`drivers/net/wireguard/version.h` 只有一行 `#define WIREGUARD_VERSION "1.0.0"`。它通过 `main.c` 的 `#include "version.h"` 进入 `MODULE_VERSION(WIREGUARD_VERSION)`，决定了 `modinfo wireguard` 看到的版本字符串。它不参与任何条件编译，是纯常量定义。

下面这张表把本篇涉及的符号与配置要素按「来源—类型—作用」收拢。

| 符号/语句 | 来源文件 | 类型或值 | 对构建的作用 |
|---|---|---|---|
| `config WIREGUARD` | `drivers/net/Kconfig` | tristate | 决定编译成模块、内建还是不编译 |
| `depends on NET && INET` | `drivers/net/Kconfig` | 前置条件 | 不满足时选项不可见、不可选 |

### 4. 关键流程与调用链

配置符号从「用户在菜单上按一下」到「编译出 .ko」，中间经过一条清晰的链路。第一段，用户通过 `make menuconfig` 一类界面把 `CONFIG_WIREGUARD` 设为 `m`；配置系统把这个选择写入内核根目录的 `.config` 文件，同时生成供 Makefile 读取的自动配置头与变量文件。第二段，顶层 Makefile 在递归遍历 `drivers/net/` 时读到 `obj-$(CONFIG_WIREGUARD) += wireguard/`，此时 `CONFIG_WIREGUARD` 的值已被替换为 `m`，于是该行等价于 `obj-m += wireguard/`，Kbuild 决定进入子目录并准备构建一个模块。第三段，进入 `drivers/net/wireguard/` 后，`wireguard-y` 列表里的每个 `.o` 由对应的 `.c` 编译产生；`ccflags-y` 定义的 `pr_fmt` 宏随每次编译注入。第四段，第 17 行把全部输入目标聚合为单一的 `wireguard.o`，并按 `obj-m` 的要求链接成 `wireguard.ko`。第五段，若同时把 `CONFIG_WIREGUARD_DEBUG` 设为 `y`，第 2 行的条件表达式成立，`-DDEBUG` 被追加进编译参数，`main.c` 的 `#ifdef DEBUG` 块生效，模块加载时会先跑三项自检。这条链把 Kconfig、Makefile、源码条件编译三者串成一条因果链。

调试链值得单独再走一遍，因为它是「配置如何改变运行行为」的最佳示例。`config WIREGUARD_DEBUG` 是 `bool` 且 `depends on WIREGUARD`，所以只有先打开 `WIREGUARD` 才能看到它；设为 Y 后，`ccflags-$(CONFIG_WIREGUARD_DEBUG)` 展开为 `ccflags-y`，`+= -DDEBUG` 把宏加进编译命令；`main.c` 里 `#ifdef DEBUG` 包裹的代码把 `ret` 预设为 `-ENOTRECOVERABLE`，依次调用 `wg_allowedips_selftest()`、`wg_packet_counter_selftest()`、`wg_ratelimiter_selftest()`，任一返回假就 `goto err_peer` 回滚；三项都通过才继续正常的 `wg_noise_init()` 等初始化。这意味着「打开调试开关」不只是多打几行日志，而是在启动路径上插入了一道硬性自检关卡——这正是 Kconfig 的 help 文本提醒「Say N unless you know what you're doing」的原因。本快照的 `selftest/` 目录为空，相关自检函数的实现未落地，具体仓库位置需对照实际版本核验，但调用关系在 `main.c` 里清晰可见。

需要再次划清边界：上面这条是「构建期配置链」，与 06 册讲的「运行期初始化链/数据链」不是一回事。后者从 `module_init(wg_mod_init)` 开始，经过 slab 缓存初始化、noise/peer/device/netlink 各层注册，最后打印加载信息；前者在编译阶段就已经决定「这些代码会被编进去、以什么形式存在」。本篇只在说明 `wireguard-y` 列表里有哪些源文件、以及 `DEBUG` 宏会激活哪些条件代码时触及运行期函数名，不深入它们的实现（机制见 06-01，模块职责见 07 册）。

### 5. 配置/命令/代码实例

本节把前文反复引用的 Kconfig 原文作为代码实例，再用只读命令观察配置值如何落到 `.config`，最后给出一段编译日志作为逐行判读的素材。

先看配置源码，这段直接来自 `drivers/net/Kconfig` 第 74 至 101 行。

```text
config WIREGUARD
	tristate "WireGuard secure network tunnel"
	depends on NET && INET
	select NET_UDP_TUNNEL
	select DST_CACHE
	select CRYPTO_LIB_CURVE25519
	select CRYPTO_LIB_CHACHA20POLY1305
	select CRYPTO_LIB_UTILS
	help
	  WireGuard is a secure, fast, and easy to use replacement for IPSec ...

config WIREGUARD_DEBUG
	bool "Debugging checks and verbose messages"
	depends on WIREGUARD
	help
	  This will write log messages for handshake and other events ...
	  Say N here unless you know what you're doing.
```

再看驱动 Makefile 的聚合部分，这段来自 `drivers/net/wireguard/Makefile` 第 1、2、17 行。

```makefile
ccflags-y := -D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'
ccflags-$(CONFIG_WIREGUARD_DEBUG) += -DDEBUG
obj-$(CONFIG_WIREGUARD) := wireguard.o
```

观察配置落地的只读命令如下，均在内核树根目录执行。

```bash
# 查看当前配置中 WireGuard 相关符号的取值
grep '^CONFIG_WIREGUARD' .config

# 编译 WireGuard 模块（目录由 02-03 详述，这里只看输出形态）
make M=drivers/net/wireguard
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
CONFIG_WIREGUARD=m
# CONFIG_WIREGUARD_DEBUG is not set
  CC [M]  drivers/net/wireguard/main.o
  CC [M]  drivers/net/wireguard/noise.o
  CC [M]  drivers/net/wireguard/device.o
  [中间编译行省略]
  LD [M]  drivers/net/wireguard/wireguard.o
  MODPOST 1 modules
  LD [M]  drivers/net/wireguard/wireguard.ko
```

逐行判读如下。第一行 `CONFIG_WIREGUARD=m` 确认符号取值为 m，对应 `tristate` 三态中的模块态，意味着顶层与下层 Makefile 的 `$(CONFIG_WIREGUARD)` 都展开为 `m`，最终走 `obj-m` 路径；若这里是 `=y`，产物就会是内建驱动而非 `.ko`，若整行不存在则为 `=n`、不参与构建。第二行 `# CONFIG_WIREGUARD_DEBUG is not set` 是内核配置系统表示「布尔项未选中」的标准写法，说明调试链没有激活，Makefile 第 2 行的 `ccflags-$(CONFIG_WIREGUARD_DEBUG)` 为空，`-DDEBUG` 不会进入编译参数，`main.c` 的 `#ifdef DEBUG` 自检块被跳过；反过来若设为 `=y`，这行就会变成 `CONFIG_WIREGUARD_DEBUG=y` 并在加载时触发三项自检。第三至第五行 `CC [M] ...main.o`、`noise.o`、`device.o` 是编译命令回显，方括号里的 `M` 标记这是模块构建目标，文件名与 `wireguard-y` 列表开头的三项一一对应，`[M]` 标签正来自 `obj-m` 的输出分类。省略号处对应列表中其余的 `peer.o`、`timers.o`、`send.o` 等，它们同样由 `CC [M]` 逐项编译。第六行 `LD [M] ...wireguard.o` 是聚合步骤，对应 Makefile 第 17 行 `obj-$(CONFIG_WIREGUARD) := wireguard.o`——所有输入目标被链接成单一的 `wireguard.o`，这一步正是 `wireguard-y` 列表与 `obj-*` 输出变量的接合点。第七行 `MODPOST 1 modules` 是内核模块后处理阶段，它生成模块元数据与符号版本信息，`1 modules` 表明本次只产出一个模块，与 WireGuard 只聚合为单一 `wireguard.ko` 的事实吻合。第八行 `LD [M] ...wireguard.ko` 是最终链接产物，即可加载模块文件，它对应 `make M` 在模块态下的终点；到这里，`CONFIG_WIREGUARD=m` 这个一开始的菜单选择，就完整走完了从配置到 artifact 的全程。把这段输出与第 4 节的链路对照读，每一行都能找到它在 Kconfig 或 Makefile 里的源头。

关于编译命令的完整参数、变量覆盖与交叉编译选项，本篇只借它说明输出形态，真正权威的讨论在 04 册，操作步骤在 02-03；此处不展开 `make` 的各种开关，以免与这两处重复。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是关于赋值符号的细节：本快照 `drivers/net/wireguard/Makefile` 第 17 行实际写的是 `obj-$(CONFIG_WIREGUARD) := wireguard.o`，用的是 `:=`，而上层 `drivers/net/Makefile` 第 13 行用的是 `+=`。任务口径中常见的 `+=` 写法与这里的源码并不一致，核验时必须以源码为准，不可照抄记忆中的形式。`+=` 与 `:=` 在 Kbuild 里语义不同：前者把目标追加到已有列表，后者直接赋值覆盖；虽然在这个具体驱动里两者结果相同（因为该目标此前没有其他值），但养成「按源码逐字核对」的习惯，是避免踩坑的根本。

第二个陷阱是 `ccflags-y` 第一行的引号形式。`-D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'` 里既有单引号包裹整个宏定义，又有宏值内部合法的 C 字符串双引号，还有转义。手写时极易漏掉某层引号，导致编译报出晦涩的宏展开错误。正确做法是从源码复制而非凭记忆重敲，并理解它的意图：为驱动所有 `pr_*` 打印统一加上模块名前缀。第三个陷阱是误以为打开 `WIREGUARD_DEBUG` 只是「多打日志」。如第 4 节所述，它会通过 `-DDEBUG` 激活 `main.c` 里的自检块，任一自检失败都会让模块加载返回 `-ENOTRECOVERABLE`；在精简或裁剪过的内核上，若自检依赖的功能被裁掉，可能出现「平时能加载、打开调试反而加载失败」的反直觉现象。

第四个陷阱是混淆 `=y` 与 `=m` 的运行期后果。`=y` 把驱动编进内核镜像，随内核启动即存在，但无法用 `rmmod` 卸载，更新驱动必须换内核；`=m` 产出 `wireguard.ko`，可用 `modprobe`/`rmmod` 按需管理（加载操作见 02-03）。选择哪种取决于部署形态：发行版通用内核通常选 M 以保留灵活性，嵌入式固定镜像可能选 Y 以减少启动依赖。第五个陷阱是以为 `select` 拉起的依赖必然可用。`select` 只保证配置项被打开，但在深度裁剪的内核里，被依赖的底层代码是否真正编进镜像，仍取决于其自身的依赖是否完整；构建失败时应沿着依赖矩阵逐层核对（依赖矩阵的源码依据见 02-01）。第六个陷阱是把 `tristate` 当成 `bool`：后者只有 Y/N，没有 M 态，一旦把 `WIREGUARD_DEBUG` 误设为 M 会在配置系统里报错，因为它根本不接受这个值。

最佳实践归纳为四步。第一步，把 Kconfig 与 Makefile 当作一份「契约」来读：先在 `drivers/net/Kconfig` 确认符号类型与依赖，再到两级 Makefile 确认该符号如何被消费，形成「定义—消费」的闭环认知。第二步，配置时用只读命令 `.config` 回读实际取值，不凭菜单记忆判断状态，尤其注意 `# CONFIG_X is not set` 这种「未选中」的规范写法。第三步，改动调试开关前，先理解它会通过 `-DDEBUG` 改变启动路径上的自检行为，并在可控环境验证，避免在生产内核上直接启用。第四步，凡涉及赋值符号、引号形式与生成文件这类易错点，一律以源码逐字核对为本，拿不准的标注「需对照实际版本核验」，再查完整源码树或目标系统。这四步的核心精神与上一篇一致：让每一条编译结果都能回溯到一条确切的配置语句。

### 7. 小结与延伸阅读

本篇逐行拆解了 WireGuard 内核构建配置的四条语句链：`drivers/net/Kconfig` 中 `config WIREGUARD` 是 `tristate`，`depends on NET && INET` 约束可见性，五条 `select` 自动拉取 UDP 隧道与加密库依赖；`config WIREGUARD_DEBUG` 是 `bool`，依赖前者并通过编译参数控制调试自检。`drivers/net/Makefile` 的 `obj-$(CONFIG_WIREGUARD) += wireguard/` 决定是否递归进入子目录，`drivers/net/wireguard/Makefile` 的 `wireguard-y` 列出输入目标、第 17 行 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 完成聚合，`ccflags-y` 提供无条件与条件两类编译参数。`CONFIG_WIREGUARD` 的 Y/M/N 三态分别导向内建、模块与跳过三种构建结果，而 `WIREGUARD_DEBUG=y` 会通过 `-DDEBUG` 激活 `main.c` 的自检块。理解「Kconfig 定义符号、Makefile 消费符号」这条主线，就掌握了打开任意内核驱动构建配置的通用方法。

延伸阅读建议按三条线走：想要实际动手编译、加载模块与走 dkms 兼容路径，读 02-03；想要理解被 `-DDEBUG` 激活的自检与静态检查细节，读 02-05；想要拿到命令参数、netlink 常量与模块接口的权威全集，读 04 册，其中命令参数见 04-01、netlink 属性见 04-05、uapi 常量见 04-06、模块参数与 sysfs 见 04-07。跨册随查按（字段见 05-01 ｜ 参数见 04-07 ｜ 原理见 06-01 ｜ 模块见 07-01）执行：结构体逐字段去 05、参数与接口全集去 04、机制与调用链去 06、目录级模块能力去 07、运维与基准去 08。本篇所有涉及具体路径、符号名与取值的内容，均以 `_wglinux_build/upstream_src/` 下对应文件为准；编译参数与操作细节是 04 册与 02-03、02-04、02-05 的范围，这里只建立构建配置的心智模型，不做重复展开。至此，02 册的「静态地图」与「配置语言」两块地基已经铺好，后续篇章将在此之上进入真实构建与调试操作。

## 02-03 从零构建实战：内核模块编译、insmod 与 dkms 兼容路径

### 1. 背景与动机

构建是把一份静态源码变成运行中内核模块的必经环节，也是许多"明明照着文档做了却加载不上"的问题的真正根源。WireGuard 的内核实现虽然已经进入 Linux 主线，但不同发行版、不同内核版本携带的驱动新旧不一：有的发行版内核较老、尚未合入 WireGuard，有的则出于稳定考虑冻结在某个旧版本，还有的场景需要对驱动打补丁、打开调试开关，或把它回溯移植到自定义内核上。这些情形都无法靠"发行版仓库里装一个包"解决，必须从源码自行构建。本篇要回答的就是这条链路上的三个实务问题：怎样把一个 `wireguard.ko` 从源码编译出来，怎样用 `insmod` / `modprobe` 把它正确加载进内核，以及在不把驱动编进内核树的场景下，怎样借 dkms 让模块随内核升级自动重建。

先明确本篇在整个构建册里的位置，避免与相邻篇重复。02-01 负责源码获取、内核树目录结构与依赖矩阵，告诉读者从哪里拿到 `wireguard-linux-src` 快照、需要哪些编译依赖；02-02 负责 Kconfig 与 Makefile 的构建配置，解释 `CONFIG_WIREGUARD` 这个配置符号如何在 Kconfig 中声明、在 `.config` 中取值；本篇 02-03 则承接这两篇，专讲"动手做"——从实际的 `drivers/net/wireguard/Makefile` 与 `main.c` 出发，把编译、加载、兼容路径这条操作链走通；02-05 再讲调试构建、动态调试与 selftest。换言之，本篇关心的是"命令怎么敲、产物是什么、加载时内核实际做了什么"，而配置符号的完整语义与调试开关的细节，分别让给 02-02 与 02-05（构建配置见 02-02，调试构建见 02-05）。

版本基准必须先厘清，否则读任何构建日志都会迷失。本套资料的内核驱动快照是 `wireguard-linux` stable 分支的 `drivers/net/wireguard/` 目录，其驱动的自身版本来自 `drivers/net/wireguard/version.h` 中的 `WIREGUARD_VERSION "1.0.0"`；这是驱动字符串，不是 Linux 内核版本，也不是用户态 `wireguard-tools` 的版本。用户态工具的 `src/version.h` 另定义为 `WIREGUARD_TOOLS_VERSION "1.0.20260223"`，而目标机器的内核版本又是一个独立取值，由 `uname -r` 决定。三者相互独立：构建内核模块时匹配的是内核版本与内核头文件版本，构建用户态工具时用的是工具版本（工具构建见 02-04），而 `wireguard.ko` 通过 `MODULE_VERSION` 暴露的则是那个 `"1.0.0"`。把这三个版本号混用，是阅读 `modinfo` 输出时最常见的误判来源。

需要特别说明 dkms 的定位。dkms（Dynamic Kernel Module Support，动态内核模块支持）并不属于上游 `wireguard-linux` 源码树，它是发行版与打包者用来管理树外内核模块的一套框架：当系统安装新内核时，dkms 会用新内核的头文件自动重新编译并注册已登记的树外模块，从而避免"内核升级后模块失效"的经典问题。因此本篇涉及 dkms 的部分讲的是工程实践与兼容思路，其具体目录布局、配置文件字段与命令行为需对照目标发行版的 dkms 版本核验，本套资料不把它伪装成上游源码里的文件；凡 dkms 相关断言，均按"需对照实际版本核验"处理。

最后交代本篇的证据边界。构建命令的具体输出格式、模块加载后的 `dmesg` 文本、乃至 dkms 状态行，都因内核版本、编译器与发行版而异，本篇给出的示例仅用于建立"输入—产物—内核反应"的对应关系，并统一标注"示例输出，具体格式需对照实际版本核验"。凡是函数、宏、常量与文件路径，则严格取自本快照的 `drivers/net/wireguard/Makefile`、`main.c` 与 `version.h`，绝不编造。读法是：把本篇当作一张围绕真实源码展开的"构建操作地图"，细节参数去 04 册、结构字段去 05 册、机制原理去 06 册、模块职责去 07 册。

### 2. 核心概念

理解从零构建，先要理解 kbuild 是怎样把一个目录里的 C 文件变成一个 `.ko` 文件的。核心线索在 `drivers/net/wireguard/Makefile` 里，只有十八行，却包含了三个关键概念。其一是复合目标：`wireguard-y := main.o` 开始，逐行 `+=` 追加 `noise.o`、`device.o`、`peer.o`、`timers.o`、`queueing.o`、`send.o`、`receive.o`、`socket.o`、`peerlookup.o`、`allowedips.o`、`ratelimiter.o`、`cookie.o`、`netlink.o` 与 `generated/netlink.o`，最后用 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 收口。这里的 `wireguard.o` 不是一个普通的单文件目标，而是由 kbuild 自动把 `wireguard-y` 列出的所有 `.o` 链接而成的复合模块；`obj-$(CONFIG_WIREGUARD)` 的写法则是 kbuild 的标准习语——当 `CONFIG_WIREGUARD=y` 时目标进入 `obj-y` 被编进内核，为 `m` 时进入 `obj-m` 生成可加载模块，为 `n` 时整行消失。这解释了为什么同一个 Makefile 能同时支持"编进内核"与"编成模块"两种形态。

其二是编译标志。`ccflags-y := -D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'` 定义了模块统一的打印前缀：`KBUILD_MODNAME` 在构建时被替换为模块名 `wireguard`，于是模块内所有 `pr_info`、`pr_err` 输出都会自动带上 `wireguard: ` 前缀——这正是加载成功后 `dmesg` 里那行 `wireguard: WireGuard 1.0.0 loaded.` 的来源，前缀并非手写在每个打印点，而是由这条 `pr_fmt` 宏统一注入。紧接着的 `ccflags-$(CONFIG_WIREGUARD_DEBUG) += -DDEBUG` 是条件编译：只有当 `CONFIG_WIREGUARD_DEBUG` 打开时才追加 `-DDEBUG`，从而激活 `main.c` 中用 `#ifdef DEBUG` 包裹的自检代码（调试开关的完整语义见 02-05）。

其三是模块身份声明，全部集中在 `main.c` 末尾。`module_init(wg_mod_init)` 与 `module_exit(wg_mod_exit)` 分别把 `wg_mod_init`、`wg_mod_exit` 注册为加载与卸载入口；这两个宏会把函数放入内核特殊的 `.init.text` 与 `.exit.text` 段，前者在初始化完成后其内存可被内核回收，后者在模块被静态编入内核时根本不会保留。`MODULE_LICENSE("GPL v2")` 声明许可为 GPLv2，这不仅是一行说明——内核会据此判断模块是否可以使用那些标记为 GPL-only 的导出符号，许可不符会导致加载时的符号解析失败。`MODULE_DESCRIPTION`、`MODULE_AUTHOR`、`MODULE_VERSION(WIREGUARD_VERSION)` 分别提供描述、作者与版本，其中版本正是 `version.h` 的 `"1.0.0"`。

模块别名是加载机制的另一个核心概念，也是"为什么 `ip link add wg0 type wireguard` 能自动加载模块"的答案。`MODULE_ALIAS_RTNL_LINK(KBUILD_MODNAME)` 声明这是一个 rtnetlink 链路类型模块，别名形如 `rtnl-link-wireguard`；`MODULE_ALIAS_GENL_FAMILY(WG_GENL_NAME)` 声明它承载名为 `WG_GENL_NAME`（即 `"wireguard"`）的通用 netlink 族，别名形如 `netlink-genl-wireguard`。构建时 modpost 工具会把这些别名写入 `modules.alias`，`modprobe` 在收到内核的模块请求时按别名查找并加载对应 `.ko`。这带来一个实务区分：`insmod` 只按文件路径加载指定模块，不解析依赖、不查别名；`modprobe` 则读取 `modules.alias` 与 `modules.dep`，支持按别名加载并自动处理依赖。构建完成后用 `depmod` 刷新这些索引，是让 `modprobe` 与自动加载正常工作的前提。

最后一个概念是 dkms 的"树外模块"身份。上游驱动是随内核树构建的，其 Makefile 依赖内核的 kbuild 体系；而内核树之外的模块要想用同样的 kbuild 规则编译，必须提供匹配当前运行内核的内核头文件（headers），并保证编译时的 ` vermagic`（内核版本魔数）与运行内核一致。dkms 的本质就是把"用哪个内核头文件编译、编译产物放到哪里、内核升级后如何重做"这三件事自动化。理解这一点后，dkms 不再是神秘的黑盒：它调用的仍是同一套 `make -C <内核构建目录> M=<模块目录> modules` 机制，区别只是把这个过程挂到了内核安装的钩子上。

### 4. 关键流程与调用链

构建链从一条 `make` 命令开始。在完整内核树内构建时，典型过程是先配置好 `.config`（确保 `CONFIG_WIREGUARD=m` 或 `=y`，配置语义见 02-02），再执行内核的模块构建目标；kbuild 进入 `drivers/net/wireguard/` 目录，读取该目录的 Makefile，把 `wireguard-y` 列出的每一个 `.o` 编译出来，再由 kbuild 把这一组对象链接成复合模块 `wireguard.o`，最终生成 `wireguard.ko`。链接阶段之后，modpost 工具扫描模块，生成 `Module.symvers`（导出符号校验）、`modules.alias`（由 `MODULE_ALIAS_*` 而来）与 `modules.dep`（依赖关系）。这一步解释了为什么构建产物不只是一个 `.ko` 文件——配套的别名与依赖索引，是后续 `modprobe` 与自动加载能工作的前提。

加载链从 `insmod wireguard.ko` 或 `modprobe wireguard` 开始。内核先做一系列一致性检查：模块格式是否正确、`vermagic` 是否与当前内核匹配、所依赖的符号是否都能在当前内核的符号表中找到、模块声明的许可是否满足 GPL-only 符号的要求。任何一项不满足，加载都会在入口函数执行之前失败，这正是"insmod 报 Invalid module format 或 Unknown symbol"的原因。检查通过后，内核调用 `module_init` 注册的 `wg_mod_init`，其内部顺序严格遵循依赖关系：先 `wg_allowedips_slab_init()` 为 trie 节点准备 slab 缓存，这是最基础的资源；在 `DEBUG` 编译下接着运行 `wg_allowedips_selftest()`、`wg_packet_counter_selftest()`、`wg_ratelimiter_selftest()` 三项自检，任一失败就把返回值设为 `-ENOTRECOVERABLE` 并 `goto err_peer`；随后 `wg_noise_init()` 初始化握手基础设施，`wg_peer_init()` 初始化对等体子系统，`wg_device_init()` 注册网络设备相关结构，最后 `wg_genetlink_init()` 注册通用 netlink 族，使配置通道可用。全部成功后，第 48、49 行两条 `pr_info` 打印加载信息与版权行——注意第一条正是 `pr_fmt` 前缀与 `WIREGUARD_VERSION` 拼接的结果。

回滚链与卸载链是同一段代码的镜像。`wg_mod_init` 中每一层初始化失败都通过 `goto` 跳到对应标签，逆序释放已经成功的层：`err_netlink` 先 `wg_device_uninit()` 再落到 `err_device` 回收 peer、`err_peer` 回收 slab；这种"逐层 goto 回滚"是内核模块的标准写法，保证任何中途失败都不留残余资源。`wg_mod_exit` 则在模块卸载时按 `wg_genetlink_uninit()`、`wg_device_uninit()`、`wg_peer_uninit()`、`wg_allowedips_slab_uninit()` 的逆序完整回收。理解这条链有个实际收益：当加载失败时，`dmesg` 里最后一条成功的打印与第一条失败的返回码，可以反过来定位是哪一层初始化出了问题（错误码速查见 04-08）。

dkms 兼容链则是把上述构建链"挂到内核升级钩子上"。其工作流可概括为：把驱动源码放入 dkms 约定的源码目录并提供一份描述文件（内容需对照实际版本核验），用 dkms 命令 add、build、install 把模块登记并安装到当前内核；此后每当系统安装新内核，dkms 的钩子会用新内核头文件重新执行同一套 kbuild 构建，并在新内核的模块目录中注册产物。关键点是 dkms 并未改变构建本身，它调用的仍是 `M=<模块目录>` 的树外构建流程，因此前文关于 `vermagic`、内核头文件匹配、符号解析的所有注意事项，在 dkms 场景下同样成立——dkms 只是把"再构建一次"自动化了，并不能绕开内核 ABI 兼容性这道硬约束。

### 5. 配置/命令/代码实例

先看构建入口本身。下面这段取自 `drivers/net/wireguard/Makefile` 的关键行，它决定了模块由哪些对象组成、以什么形态产出：

```makefile
ccflags-y := -D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'
ccflags-$(CONFIG_WIREGUARD_DEBUG) += -DDEBUG
wireguard-y := main.o
wireguard-y += noise.o
wireguard-y += device.o
wireguard-y += peer.o
wireguard-y += timers.o
wireguard-y += queueing.o
wireguard-y += send.o
wireguard-y += receive.o
wireguard-y += socket.o
wireguard-y += peerlookup.o
wireguard-y += allowedips.o
wireguard-y += ratelimiter.o
wireguard-y += cookie.o
wireguard-y += netlink.o generated/netlink.o
obj-$(CONFIG_WIREGUARD) := wireguard.o
```

这段 Makefile 有三处值得逐字读：`obj-$(CONFIG_WIREGUARD) := wireguard.o` 用变量展开决定模块形态；`wireguard-y +=` 的连续追加构成复合目标对象清单；`ccflags-y` 的 `pr_fmt` 定义让所有打印自动带 `wireguard:` 前缀。注意最后一行用 `:=` 而非 `+=`，是赋值而非追加，这是该文件收口模块目标的写法。

下面给出在内核树内构建并加载模块的一组命令（示例输出，具体格式需对照实际版本核验）：

```bash
# 确认已配置 CONFIG_WIREGUARD=m（配置语义见 02-02）
grep CONFIG_WIREGUARD .config

# 在内核树根构建该目录的模块
make -C /lib/modules/$(uname -r)/build M=$PWD/drivers/net/wireguard modules

# 安装模块并刷新依赖/别名索引
sudo make -C /lib/modules/$(uname -r)/build M=$PWD/drivers/net/wireguard modules_install
sudo depmod -a

# 按别名加载（推荐，能解析依赖）并查看模块身份
sudo modprobe wireguard
modinfo wireguard

# 卸载模块
sudo modprobe -r wireguard
```

执行上述命令后，验证链路的典型输出如下（示例输出，具体格式需对照实际版本核验）：

```text
CONFIG_WIREGUARD=m
  LD      M     drivers/net/wireguard/wireguard.o
  CC [M]  drivers/net/wireguard/main.o
  MODPOST drivers/net/wireguard/Module.symvers
filename:       /lib/modules/6.x.x/kernel/drivers/net/wireguard/wireguard.ko
version:        1.0.0
license:        GPL v2
description:    WireGuard secure network tunnel
author:         Jason A. Donenfeld <Jason@zx2c4.com>
vermagic:       6.x.x SMP preempt mod_unload
alias:          rtnl-link-wireguard
alias:          netlink-genl-wireguard
depends:
```

逐行判读如下。首行 `CONFIG_WIREGUARD=m` 来自 `.config`，`m` 表示构造成可加载模块而不是内建（`y`）或禁用（`n`），直接决定 Makefile 第 17 行 `obj-$(CONFIG_WIREGUARD)` 展开为 `obj-m`。第二行 `LD M ... wireguard.o` 是 kbuild 把 `wireguard-y` 清单里的所有对象链接为复合目标的动作，印证了 `wireguard.o` 并非单个 C 文件编译产物。第三行 `CC [M] ... main.o` 是编译 `main.c` 的过程，`[M]` 标记表明这是模块构建而非内建；`main.o` 里就包含 `wg_mod_init` 与那些 `MODULE_*` 声明。第四行 `MODPOST ... Module.symvers` 表明 modpost 正在扫描导出符号并生成校验文件，这一步同时产出 `modules.alias`。第五行 `filename` 显示模块的最终安装路径，位于内核版本对应的模块目录下，路径里含 `6.x.x` 正是 `vermagic` 必须匹配的内核版本。第六行 `version: 1.0.0` 直接来自 `MODULE_VERSION(WIREGUARD_VERSION)`，也就是 `version.h` 里的那个字符串，与内核版本、工具版本都无关。第七行 `license: GPL v2` 来自 `MODULE_LICENSE("GPL v2")`，它决定模块能否引用 GPL-only 导出符号。第八行 `description` 与第九行 `author` 分别来自 `MODULE_DESCRIPTION` 与 `MODULE_AUTHOR`。第十行 `vermagic` 是加载时一致性检查的核心字段，必须与运行内核完全匹配，否则 `insmod` 会以 `Invalid module format` 拒绝加载——这也是 dkms 必须在每次内核升级后重构建的根本原因。第十一行、第十二行两条 `alias` 分别来自 `MODULE_ALIAS_RTNL_LINK(KBUILD_MODNAME)` 与 `MODULE_ALIAS_GENL_FAMILY(WG_GENL_NAME)`，正是它们让 `modprobe` 能在 `ip link add wg0 type wireguard` 触发内核请求时找到本模块（netlink 原理见 06-14）。第十三行 `depends:` 为空，说明本模块没有依赖其他模块，这是因为加密原语等依赖已随主线内核编入。加载成功后若执行 `dmesg | tail`，会看到带 `wireguard:` 前缀的 `WireGuard 1.0.0 loaded. See www.wireguard.com for information.`，这个前缀正是 Makefile 第 1 行 `pr_fmt` 注入的效果，而非打印语句里手写。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是用 `insmod` 强行加载与内核不匹配的模块。由于 `insmod` 不做依赖解析、也不按别名查找，它只对指定文件做最基本的加载尝试；一旦 `vermagic` 与当前内核不一致，就会失败并可能留下难以理解的错误码。正确做法是用 `modprobe`：它读取 `modules.dep` 与 `modules.alias`，既能按别名加载又能处理依赖，配合加载前先 `depmod -a` 刷新索引，可避开绝大多数"模块就在磁盘上却加载不了"的问题。第二个陷阱是忽视内核头文件版本。树外构建必须用与目标运行内核完全一致的头文件和构建目录（`/lib/modules/$(uname -r)/build`），用错版本即便编译通过，`vermagic` 也会在加载时被拒；这一点在 dkms 场景下表现为"新内核装好后 dkms 重建失败"，需检查新内核的 headers 是否已安装。

第三个陷阱是许可不匹配。`MODULE_LICENSE("GPL v2")` 不是可有可无的说明文字：内核对标记为 GPL-only 的导出符号会拒绝非 GPL 兼容模块引用，若把声明改成不兼容许可，加载会在符号解析阶段失败。因此擅自修改 `main.c` 的许可声明是高危操作。第四个陷阱是误改 `__init` / `__exit` 语义。`wg_mod_init` 的 `__init` 段在初始化完成后其内存会被内核回收，若把它注册的函数在初始化之后再次调用，将访问已释放内存；这是内核模块与普通程序的关键差异，调试时不要试图在运行期"重入"初始化函数。

第五个陷阱是把调试构建的产物当生产件。`CONFIG_WIREGUARD_DEBUG` 打开时会追加 `-DDEBUG`，激活 `main.c` 中 `#ifdef DEBUG` 包裹的三项 selftest；自检失败会让初始化返回 `-ENOTRECOVERABLE`，调试构建因此在某些环境下更难加载成功。生产构建应关闭该开关，调试用途的单测与自检留给 02-05 处理。第六个陷阱是低估 dkms 的边界。dkms 解决的是"内核升级后自动重编译"，但无法解决"驱动源码与新版内核 API 不兼容"——若上游驱动在新内核上编译报错，dkms 只是忠实地把编译错误记录下来，仍需人工适配源码或换用更新版本；此外启用 Secure Boot 的系统还会要求模块签名，dkms 重构建的模块若未签名会被内核拒绝加载，这部分属于发行版安全策略，需对照实际环境核验。

最佳实践可以归纳为五步。其一，构建前先确认 `CONFIG_WIREGUARD=m` 与目标内核的头文件齐备（配置见 02-02）。其二，优先用内核树内的标准 `make ... M=... modules` 流程构建，保留完整的 `Module.symvers` 与 `modules.alias`，不要手工拼命令绕过 kbuild。其三，构建后先 `modinfo` 核对 `version`、`license`、`vermagic` 与两条 `alias` 是否与预期一致，再决定是否加载。其四，加载统一走 `modprobe` 并在安装后 `depmod -a`，让别名与依赖索引保持最新。其五，在需要跨内核升级长期维护的场景才引入 dkms，并为其配置好签名与头文件依赖；在一次性或受控环境里，手动构建反而更透明、更可审计。凡遇到加载失败，按"先看 `dmesg` 最后一条内核报错，再回查 `vermagic` 与符号依赖，最后确认许可"的顺序排查，通常能快速定位（排障思路见 08-03）。

### 7. 小结与延伸阅读

本篇围绕 `drivers/net/wireguard/Makefile` 与 `main.c`，把"从源码到运行中模块"的链路走了一遍：Makefile 用 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 把 `wireguard-y` 对象清单链接成复合模块，用 `pr_fmt` 统一日志前缀，用条件标志控制调试编译；`main.c` 用 `module_init` / `module_exit` 注册入口，`wg_mod_init` 按 allowedips、noise、peer、device、genetlink 的依赖顺序分层初始化，失败时逐层 `goto` 回滚，`wg_mod_exit` 逆序回收；五个 `MODULE_*` 声明分别提供许可、描述、作者、版本与两条别名，其中版本取自 `version.h` 的 `"1.0.0"`，别名使 `modprobe` 能按 rtnetlink 链路类型与 netlink 族名自动加载模块。dkms 的本质是把同一套树外 kbuild 流程挂到内核升级钩子上，它自动化了"重构建"却没有绕开 `vermagic` 与 ABI 兼容的硬约束。

延伸阅读按三条线展开：构建配置的符号语义（如 `CONFIG_WIREGUARD` 如何在 Kconfig 声明）读 02-02，调试构建与 selftest 读 02-05，源码获取与依赖矩阵读 02-01；想理解初始化各层究竟做了什么，按机制读 06-01 的启动注册总览、按模块职责读 07-01 的 `main.c` 入口与 07-02 的设备生命周期；需要字段细节查 05-02 的 `wg_device`，需要 `modinfo` 之外更多参数与错误码查 04-07 与 04-08；加载后的运维排障读 08-03。跨册随查按（字段见 05-02 ｜ 参数见 04-07 ｜ 原理见 06-01 ｜ 模块见 07-01）执行。凡本篇标注"需对照实际版本核验"的 dkms 配置字段、命令输出格式与发行版行为，均以目标系统实际环境为准，本套资料不编造未核验的路径与取值。

## 02-04 wireguard-tools 构建：wg、wg-quick 与 bash 补全

### 1. 背景与动机

内核模块只提供数据面，真正把配置写进内核、把接口拉起来的，是用户态的 `wireguard-tools`。这套工具包含两个面向使用者的程序：`wg(8)` 是配置与查询 WireGuard 接口的主命令，`wg-quick(8)` 则是一个读取 `wg` 风格配置文件并自动完成地址、路由、DNS 等附加设置的便捷脚本。前者是 C 程序，后者是 bash 脚本，二者共享同一个源码仓库。本篇要讲的是怎样从源码把这三者——`wg` 主程序、`wg-quick` 脚本、bash 补全文件——构建并安装到目标系统，以及构建过程中那些决定"装到哪里、装不装"的变量与探测逻辑。

为什么要从源码构建工具，而不是直接用发行版包？理由与内核模块类似但有工具自己的特点。其一是版本滞后：发行版仓库里的 `wireguard-tools` 可能落后于上游，缺少某些子命令或补全能力；其二是安装路径定制：打包者往往需要把程序装进特定 `PREFIX` 与 `DESTDIR`，并决定是否附带 man 手册、systemd unit 与 bash 补全；其三是可审计与可定制：工具源码量小、依赖极简，README 明确写着"There are no dependencies other than a good C compiler and a sane libc"，意味着在受限环境里从零构建非常轻量；其四是为了解工具本身——读懂 `wg.c` 的子命令分发表与两个补全脚本，才能真正理解 `wg` 为什么"没有守护进程"，以及按下 Tab 时 shell 到底在做什么。

版本基准仍要三分开。用户态工具的版本由 `src/version.h` 的 `WIREGUARD_TOOLS_VERSION "1.0.20260223"` 定义，这是本快照的基准；`wg --version` 打印的就是它。注意 Makefile 里还有一条更动态的取值路径：`WIREGUARD_TOOLS_VERSION = $(patsubst v%,%,$(shell GIT_DIR="$(PWD)/../.git" git describe --dirty 2>/dev/null))`，即优先用 `git describe` 从仓库标签推导版本并去掉 `v` 前缀，只有取不到时才回退到 `version.h` 里的默认值。这与内核驱动 `version.h` 的 `"1.0.0"`（见 01-01、02-03）和内核版本 `uname -r` 是三个独立取值（版本基准见 01-04）。把工具版本误当成驱动版本，是阅读 `wg --version` 与 `modinfo wireguard` 输出时最常见的混淆。

本篇的范围与分工需要交代清楚。`wg` 的全部命令行参数、子命令选项与配置语义属于参数权威册 04-01、04-02、04-03，本篇只在 `wg.c` 的子命令分发表层面点名，不展开每个子命令的选项（参数见 04-01）；`wg0.conf` 的配置体系与 `wg-quick` 的字段用法属于 03-02，本篇只讲脚本是怎样被构建和安装的；`wg` 通过 netlink 与内核通信的机制属于 06-14，本篇只点到 IPC 链路的存在（原理见 06-14）；工具内部各源文件（config、encoding、curve25519、ipc 等）的职责属于 07-13，本篇不逐一展开（模块见 07-13）。本篇专注的是"构建、安装、运行分发与补全"这条操作链。

最后给出证据口径。凡涉及函数名、变量名、默认值与文件路径，均取自本快照的 `wireguard-tools/README.md`、`src/Makefile`、`src/wg.c`、`src/version.h`、`src/completion/` 下两个补全脚本以及 `contrib/` 目录，尽量给出真实路径；凡涉及具体命令输出格式、发行版安装差异与第三方工具行为，统一标注"需对照实际版本核验"。本篇不写绝对版本号以外的性能或兼容性断言，也不把 `contrib/` 下的示例脚本说成生产组件——README 明确说它们"not immediately useful for production use"，只应作为灵感来源。

### 2. 核心概念

理解工具构建，第一个核心概念是"一个二进制，多个子命令"。`src/wg.c` 的 `main` 函数并不为每条命令生成一个独立可执行文件，而是维护一张 `subcommands[]` 分发表：表项是 `const char *subcommand`、函数指针 `int (*function)(int, const char**)` 与描述 `const char *description` 三者组成的结构，静态列出 `show`、`showconf`、`set`、`setconf`、`addconf`、`syncconf`、`genkey`、`genpsk`、`pubkey` 九个子命令。`main` 先处理 `-v/--version/version`（打印 `wireguard-tools v%s`）与 `-h/--help/help`（调用 `show_usage`），无参数时默认调用 `show_main`，有参数时遍历分发表按字符串比对，命中就把 `argc-1` 与 `argv+1` 交给对应函数。这里有两个容易忽略的细节：`setconf`、`addconf`、`syncconf` 三个子命令共用同一个 `setconf_main` 函数指针，`genkey` 与 `genpsk` 共用 `genkey_main`——区别由函数内部对子命令名的判断决定，而不是分发表里写了不同函数。这种"单二进制 + 表驱动分发"的设计，正是工具部署极简的原因：装一个 `wg` 文件就获得全部子命令。

第二个概念是 `wg-quick` 与补全文件的"非编译"属性。`wg-quick` 不是 C 程序，而是安装时从 `wg-quick/$(PLATFORM).bash` 拷贝并改名为 `wg-quick` 的脚本，所以它的"构建"本质是选择平台对应脚本并安装；bash 补全文件同理，是 `completion/wg.bash-completion` 与 `completion/wg-quick.bash-completion` 两个纯文本 shell 脚本，被安装到 `BASHCOMPDIR` 下。因此 `make` 阶段真正编译的只有 C 源文件，而 `make install` 阶段才把脚本、手册页、systemd unit 与补充分发到各自目录。理解这个区别，就不会奇怪为什么 `make` 之后目录里只有一个 `wg` 可执行文件。

第三个概念是构建变量的"可覆盖 + 自动探测"双层设计。`src/Makefile` 用 `?=` 定义了一组变量：`PREFIX ?= /usr`、`DESTDIR ?=`、`SYSCONFDIR ?= /etc`、`BINDIR ?= $(PREFIX)/bin`、`BASHCOMPDIR ?= $(PREFIX)/share/bash-completion/completions`、`RUNSTATEDIR ?= /var/run`、`PKG_CONFIG ?= pkg-config` 等；更特别的是 `SYSTEMDUNITDIR`，它用 `$(shell $(PKG_CONFIG) --variable=systemdsystemunitdir systemd ... || echo "$(PREFIX)/lib/systemd/system")` 查询 systemd 的 unit 目录，查不到就回退到默认路径。三个 `WITH_*` 开关 `WITH_BASHCOMPLETION`、`WITH_WGQUICK`、`WITH_SYSTEMDUNITS` 初始为空，走自动探测：当 `BASHCOMPDIR` 目录存在时打开 bash 补全，当 `$(BINDIR)/bash` 或 `$(DESTDIR)/bin/bash` 存在时打开 `wg-quick`，当 `SYSTEMDUNITDIR` 存在时打开 systemd unit。这套逻辑的实务含义是：打包时若想强制包含或排除某项，应显式把变量设为 `yes` 或 `no`，而不要依赖探测结果（安装与目标变量详见后文表格）。

第四个概念是平台推导与版本注入。`PLATFORM ?= $(shell uname -s | tr '[:upper:]' '[:lower:]')` 把内核名转成小写作为平台标识，`wg-quick/$(PLATFORM).bash` 据此选择脚本；若存在 `uapi/$(PLATFORM)/.` 目录，则 `CFLAGS` 追加 `-isystem uapi/$(PLATFORM)` 引入平台专用头文件。编译标志还包括 `-O3`、`-std=gnu99 -D_GNU_SOURCE -Wall -Wextra -MMD -MP` 与 `-DRUNSTATEDIR=...`，`DEBUG=yes` 时再追加 `-g`。版本则通过 `git describe` 注入为 `-D'WIREGUARD_TOOLS_VERSION="..."'`。最后是关于许可的一个易错点：整个项目按 README 是 GPLv2，但 `src/wg.c` 文件头的 SPDX 标注是 `GPL-2.0 OR MIT`；单文件许可与项目整体许可是两个层面，引用时应以 COPYING 与 README 的项目声明为准，并注意两者的区分（许可见 01-04）。

### 4. 关键流程与调用链

构建链从 README 给出的两条命令开始：`cd src` 后执行 `make`。Makefile 的 `.DEFAULT_GOAL` 是 `all`，而 `all: wg`，所以默认目标就是那个单二进制 `wg`。第 88 行 `wg: $(sort $(patsubst %.c,%.o,$(wildcard *.c)))` 用 `wildcard` 收集当前目录所有 C 源文件、把扩展名替换为 `.o` 并排序，作为 `wg` 的依赖；于是 `wg.c`、`config.c`、`encoding.c`、`curve25519.c`、`ipc.c` 等全部被编译为对象文件，再由隐式链接规则合成一个 `wg`。当 `V` 不等于 1 时，第 76–86 行把 `COMPILE.c`、`LINK.o`、`RM` 包装成只回显 `CC`、`LD`、`CLEAN` 的静默形式，这解释了构建日志里那些短前缀。若要看完整编译命令，设 `V=1` 即可关闭包装。

安装链由 `make install` 触发，其动作全部写在第 93–105 行，且多项受 `WITH_*` 开关约束：先用 `install -v -d` 建目录再拷贝，`wg` 以 `0755` 安装到 `$(DESTDIR)$(BINDIR)`，`man/wg.8` 以 `0644` 安装到 `$(MANDIR)/man8`；仅当 `WITH_BASHCOMPLETION=yes` 时安装 `completion/wg.bash-completion` 为 `$(BASHCOMPDIR)/wg`（`0644`）；仅当 `WITH_WGQUICK=yes` 时把 `wg-quick/$(PLATFORM).bash` 安装为 `$(BINDIR)/wg-quick`（`0755`），并以 `0700` 建立 `$(DESTDIR)$(SYSCONFDIR)/wireguard` 目录；`wg-quick.8` 手册页、wg-quick 补全文件与 systemd unit 同样各自受对应开关约束。理解这条链有个实际收益：打包时若发现某项没被安装，多半是自动探测把它判成了 `no`，应显式设 `WITH_*=yes`。

运行链从 `wg.c` 的 `main` 开始。它先把 `argv[0]` 存入全局 `PROG_NAME`，再依次判断版本请求、帮助请求与无参数情形，最后遍历 `subcommands[]` 按字符串匹配把控制权交给对应函数指针。以 `wg show` 为例，`show_main` 会通过 IPC 层（Linux 上是 netlink 通用族）向内核发 `WG_CMD_GET_DEVICE` 请求并渲染返回属性；`wg set`、`wg syncconf` 等则走 `WG_CMD_SET_DEVICE`。这条 IPC 链路的实现属于 06-14，本篇只点到为止（原理见 06-14）。

补全链是 shell 侧的独立流程。两个补全文件各自定义一个函数并用 `complete -F` 注册到对应命令：`wg.bash-completion` 末尾是 `complete -o nosort -F _wg_completion wg`，`wg-quick.bash-completion` 末尾是 `complete -o filenames -o nosort -F _wg_quick_completion wg-quick`。当用户按下 Tab，bash 设置 `COMP_WORDS` 与 `COMP_CWORD`，函数据此分派：`_wg_completion` 在第一个词位置用 `compgen -W` 补全九个顶层子命令，在第二个词位置调用 `wg show interfaces` 枚举已有接口，在 `show` 的第三个词位置补全 `public-key`、`private-key`、`listen-port`、`peers`、`allowed-ips` 等字段，在 `set` 子命令里用一组 `has_*` 标志位避免同一参数重复出现；`_wg_quick_completion` 则在第一个词位置补全 `up`/`down`，在 `up` 的第二个词位置扫描 `/etc/wireguard/*.conf`（FreeBSD/Darwin 追加 `/usr/local/etc/wireguard`）给出配置名，在 `down` 位置从 `wg show interfaces` 取活跃接口。

### 5. 配置/命令/代码实例

先看 `wg.c` 里决定"单二进制多子命令"的分发表，这是理解工具结构的钥匙：

```c
static const struct {
    const char *subcommand;
    int (*function)(int, const char**);
    const char *description;
} subcommands[] = {
    { "show", show_main, "Shows the current configuration and device information" },
    { "set", set_main, "Change the current configuration, add peers, remove peers, or change peers" },
    { "setconf", setconf_main, "Applies a configuration file to a WireGuard interface" },
    { "addconf", setconf_main, "Appends a configuration file to a WireGuard interface" },
    { "syncconf", setconf_main, "Synchronizes a configuration file to a WireGuard interface" },
    { "genkey", genkey_main, "Generates a new private key and writes it to stdout" },
    { "genpsk", genkey_main, "Generates a new preshared key and writes it to stdout" },
    { "pubkey", pubkey_main, "Reads a private key from stdin and writes a public key to stdout" }
};
```

注意 `setconf`、`addconf`、`syncconf` 三项都指向 `setconf_main`，`genkey`、`genpsk` 两项都指向 `genkey_main`；描述文字不同但函数指针相同，差别在函数内部判定。这说明分发表是"入口路由表"而非"实现清单"。

下面是从源码构建、安装并验证的一组命令（示例输出，具体格式需对照实际版本核验）：

```bash
cd wireguard-tools/src
make                          # 默认目标 all -> wg
V=1 make clean && V=1 make    # 想看完整编译命令时打开 V=1
./wg --version                # 验证版本字符串

# 打包到 staging 目录，显式打开全部可选项
make install DESTDIR=/tmp/stage PREFIX=/usr \
     WITH_BASHCOMPLETION=yes WITH_WGQUICK=yes WITH_SYSTEMDUNITS=yes
ls -l /tmp/stage/usr/bin/wg /tmp/stage/usr/bin/wg-quick \
      /tmp/stage/usr/share/bash-completion/completions/wg
```

执行后的典型输出如下（示例输出，具体格式需对照实际版本核验）：

```text
  CC      wg.o
  CC      config.o
  LD      wg
wireguard-tools v1.0.20260223 - https://git.zx2c4.com/wireguard-tools/
-rwxr-xr-x 1 root root  ... /tmp/stage/usr/bin/wg
-rwxr-xr-x 1 root root  ... /tmp/stage/usr/bin/wg-quick
-rw-r--r-- 1 root root  ... /tmp/stage/usr/share/bash-completion/completions/wg
-rw-r--r-- 1 root root  ... /tmp/stage/usr/share/bash-completion/completions/wg-quick
```

逐行判读如下。前三行 `CC wg.o`、`CC config.o`、`LD wg` 来自 Makefile 第 76–86 行的静默包装：当 `V` 不等于 1 时，`COMPILE.c` 被改成先回显 `CC $@` 再执行真实编译，`LINK.o` 同理回显 `LD $@`，所以看到的是短前缀而非完整命令行；`LD wg` 正对应第 88 行 `wg:` 目标把所有对象链接成单二进制。第四行 `wireguard-tools v1.0.20260223 - ...` 是 `wg.c` 的 `main` 在处理 `--version` 时用 `printf("wireguard-tools v%s - ...\n", WIREGUARD_TOOLS_VERSION)` 打印的结果，其中的版本号来自 `git describe` 注入或 `version.h` 的 `1.0.20260223`，与内核驱动的 `1.0.0` 无关。第五、六行是 `wg` 与 `wg-quick` 被安装到 `$(DESTDIR)$(BINDIR)` 的结果，权限 `0755` 对应 install 目标里的 `-m 0755`，`wg-quick` 来自 `wg-quick/$(PLATFORM).bash` 而非编译产物。第七、八行是两份补全文件被安装到 `$(BASHCOMPDIR)` 下并改名为 `wg`、`wg-quick`，权限 `0644` 对应 `-m 0644`，只有当 `WITH_BASHCOMPLETION=yes` 时这两行才会出现。整个 `DESTDIR=/tmp/stage` 的用法说明工具支持分阶段安装：先落到 staging 目录检查文件清单，再打包或同步到目标机，这正是打包者显式设置 `WITH_*` 变量的典型场景（安装变量全集见本册前文表格，参数见 04-01）。若此时运行 `wg show interfaces`，其可用接口列表也正是补全函数调用的同一个数据源，配置通道的细节见 06-14。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是依赖自动探测却不了解探测依据。`WITH_WGQUICK` 的探测检查的是 `$(BINDIR)/bash` 或 `$(DESTDIR)/bin/bash` 是否存在，而非系统里有没有 bash；在交叉构建或 staging 场景下，即便目标机有 bash，只要 staging 目录里没有对应路径，探测就可能判成 `no`，导致 `wg-quick` 没被安装。结论是打包时必须显式设置 `WITH_*` 变量，不要靠探测碰运气。第二个陷阱是 `DESTDIR` 与 `PREFIX` 混淆：`PREFIX` 决定安装前缀（默认 `/usr`），`DESTDIR` 只是打包时的暂存根目录（默认空），二者叠加成 `$(DESTDIR)$(BINDIR)`；把两者混为一谈会导致文件装到错误路径。

第三个陷阱是版本号来源。`wg --version` 的字符串优先来自 `git describe --dirty`，若源码不是 git 仓库或没有标签，注入就会落空，回退到 `version.h` 的默认值；因此从归档包构建与从 git 仓库构建，版本字符串可能不同，这不是错误。分发时应明确版本口径，避免把 `1.0.20260223` 误报成内核驱动版本。第四个陷阱是补全"不生效"。补全文件安装后还需要目标环境已启用 bash-completion 框架、`BASHCOMPDIR` 指向框架实际扫描的目录，且当前 shell 已重新加载补全——仅仅把文件拷到目录，并不会让已经打开的 shell 自动生效。若 `BASHCOMPDIR` 探测失败或被设为 `no`，两个补全函数根本不会被安装。

第五个陷阱是把 `contrib/` 当生产组件。README 明确这些脚本与示例"most of these are not immediately useful for production use"，它们用于启发自定义工具。特别要注意许可差异：`contrib/embeddable-wg-library` 的 `wireguard.c` / `wireguard.h` 因使用 libmnl 代码而是 LGPL-2.1+，与主程序的许可不同，嵌入专有项目前必须分别评估（许可见 01-04）。第六个陷阱是忽略跨平台分支。Makefile 对 FreeBSD、Haiku、Windows 各有不同的链接库与编译器设置，Windows 分支甚至改用 `x86_64-w64-mingw32-clang` 与 windres 生成资源；在 Linux 上验证过的构建命令不能原样套到其他平台，`PLATFORM` 的推导值与 `wg-quick/$(PLATFORM).bash` 的可用性需逐平台核验。

最佳实践可归纳为五步。其一，先用 `cd src && make` 加 `./wg --version` 快速确认工具能构建、版本符合预期。其二，打包时用 `make install DESTDIR=... PREFIX=...` 并显式设置三个 `WITH_*` 开关，避免探测不确定性。其三，核对安装清单中 `wg`、`wg-quick`、两份补全、man 手册页与 systemd unit 是否齐全、权限是否正确（可执行 `0755`、数据 `0644`、配置目录 `0700`）。其四，调试构建问题时用 `V=1 make` 展开完整编译命令，必要时 `DEBUG=yes` 追加 `-g`。其五，把 `contrib/` 当参考资料而非直接部署，引用其代码前先确认许可。凡遇到安装缺项，按"先看 `WITH_*` 是否被探测成 `no`，再核对 `DESTDIR`/`PREFIX` 拼接路径，最后检查平台脚本是否存在"的顺序排查（排障见 08-03）。

### 7. 小结与延伸阅读

本篇把 `wireguard-tools` 的构建与安装拆成三条链：构建链由 `src/Makefile` 的 `wg: $(sort $(patsubst %.c,%.o,$(wildcard *.c)))` 把所有 C 源文件编译并链接为单个 `wg`，`V=1` 可展开静默命令；安装链由 `install:` 目标按 `WITH_BASHCOMPLETION`、`WITH_WGQUICK`、`WITH_SYSTEMDUNITS` 三个开关把 `wg`（0755）、`wg-quick`（0755）、两份 bash 补全（0644）、man 手册页与 `/etc/wireguard`（0700）分发到 `$(DESTDIR)` 与 `PREFIX` 拼接出的路径；运行链由 `wg.c` 的 `subcommands[]` 表把九个子命令分发给对应函数，其中 `setconf`/`addconf`/`syncconf` 共用 `setconf_main`、`genkey`/`genpsk` 共用 `genkey_main`，并通过 IPC 走 netlink 与内核交互。`_wg_completion` 与 `_wg_quick_completion` 两个函数分别注册到 `wg` 与 `wg-quick`，把顶层子命令、接口名、配置字段与 `*.conf` 文件名做成 Tab 补全。版本字符串优先取 `git describe`、回退 `version.h` 的 `1.0.20260223`，与驱动版本 `1.0.0`、内核版本三者独立。

延伸阅读按三条线展开：想逐个掌握 `wg` 的子命令选项与 `wg-quick` 配置字段，读 04-01、04-02、04-03 与 03-02；想理解 `wg` 如何通过 netlink 把配置写进内核，读 06-14 与 06-01；想了解 config、encoding、curve25519、ipc 等源文件各自职责，读 07-13；结构字段查 05-09，许可与版本基准查 01-04，安装后的运维与排障查 08-03。跨册随查按（字段见 05-09 ｜ 参数见 04-01 ｜ 原理见 06-14 ｜ 模块见 07-13）执行。凡本篇标注"需对照实际版本核验"的安装输出格式、发行版探测行为与第三方工具细节，均以 `wireguard-tools/README.md` 与目标系统实际环境为准，本套资料不编造未核验的路径与取值。

## 02-05 调试构建、动态调试、selftest 与静态检查

### 1. 背景与动机

前面几篇解决的是「怎么把模块和工具编出来、装上去」，本篇解决一个更容易被忽略的问题：怎么确认你手里这份构建是可信的。WireGuard Linux 有一个很特别的性质——它是内核模块，没有独立进程，加载成功不等于工作正常。一个配置错误、宏没打开、或者某处数据结构操作越界的构建，完全可能安静地 `insmod` 成功、安静地丢弃所有报文，既不崩溃也不报错。用户态程序出问题时通常有段错误、有栈回溯、有 core dump 可查；内核模块出问题时的默认表现是「什么都没发生」，这恰恰是最难排查的状态。因此，上游在源码里预埋了多道「主动把问题喊出来」的机关，理解并正确使用它们，是从「会编译」走向「敢上线」的关键一步。

这些机关按介入时机可以分成四类。第一类是**编译期开关**：`drivers/net/Kconfig` 中的 `config WIREGUARD_DEBUG` 决定是否定义 `DEBUG` 宏，它把自检代码和详细日志一起编进模块。第二类是**加载期自检**：`drivers/net/wireguard/main.c` 的 `wg_mod_init` 在 `DEBUG` 下调用三个 `*_selftest()` 函数，任何一项失败就拒绝加载。第三类是**运行期日志**：散布在 `device.c`、`peer.c`、`timers.c`、`cookie.c` 中的 `pr_debug` 与 `net_dbg_ratelimited`，在调试构建下把握手、建链、销毁、限速等事件打印到内核日志。第四类是**用户态的离线检查**：`wireguard-tools/src/fuzz/` 下的六个 libFuzzer 目标用 ASan 兜住解析器的内存错误，`wireguard-tools/src/Makefile` 的 `check` 目标用 `scan-build` 跑 Clang 静态分析。四类手段作用在软件的不同阶段，合起来构成一条从「编码正确」到「解析正确」的验证链。

为什么要专门写一节讲这些？因为这几类手段在同一个仓库里用了**三个同名但语义完全不同的 `DEBUG`**，新手极易混淆：内核 Kconfig 的 `WIREGUARD_DEBUG`、内核 Makefile 里的 `-DDEBUG`、以及用户态工具 Makefile 里的 `DEBUG=yes`（它只加 `-g`，不启用任何自检）。把它们当成一回事，轻则以为打开了调试却什么日志都没有，重则把带大量日志和额外校验的调试构建当成生产构建部署。本篇的动机就是把这三者的边界、每一项检查的入口与覆盖对象、以及它们各自能证明什么和不能证明什么，逐一钉死在源码路径上。

口径声明：本篇所有结论以本快照 `_wglinux_build/upstream_src/wireguard-linux-src/` 与 `_wglinux_build/upstream_src/wireguard-tools/` 为准。一个必须提前说明的事实是——三个自检函数的**声明**与**调用点**都清晰可见，它们的**实现**通过 `#include "selftest/*.c"` 从 `selftest/` 目录注入，而该目录在本快照中为空。因此本篇只描述可核验的调用契约与覆盖意图，不臆造 selftest 内部代码；凡涉及自测具体实现细节，均标注「需对照实际版本核验」（构建主路径见 02-03，参数全集见 04-01）。

### 2. 核心概念

把本篇 jargon 压缩成一句话：**一个开关、三项自检、两类日志、六个 fuzz 目标，外加一个静态分析目标**。

「一个开关」指 `config WIREGUARD_DEBUG`。它在 `drivers/net/Kconfig:92` 定义为 bool，提示语是「Debugging checks and verbose messages」，依赖 `WIREGUARD`，帮助文本明确写着会「write log messages for handshake and other events」「perform some extra validation checks and unit tests at various points」，最后一句是「Say N here unless you know what you're doing」。这句话本身就是上游给出的最佳实践：调试构建是开发用的，不是默认选项。「一个开关」还包含一个落地动作——`drivers/net/wireguard/Makefile:2` 的 `ccflags-$(CONFIG_WIREGUARD_DEBUG) += -DDEBUG`，把 Kconfig 的选择翻译成编译器的 `-DDEBUG` 宏；同一文件第 1 行的 `ccflags-y := -D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'` 则给所有 `pr_*` 日志统一加上模块名前缀，所以你在 dmesg 里看到的行首是 `wireguard:`。

「三项自检」指 `wg_allowedips_selftest()`、`wg_packet_counter_selftest()`、`wg_ratelimiter_selftest()`。三者都返回 `bool`，且约定 **true 表示通过**——这一点从 `main.c` 的 `if (!fn1() || !fn2() || !fn3()) goto err_peer` 可以反推出来：取反后为真意味着失败。它们的声明分别藏在三个头文件的 `#ifdef DEBUG` 里：`allowedips.h:56-57`、`queueing.h:202-203`、`ratelimiter.h:15-16`。这种「声明在头文件、实现靠 include 注入」的写法很有讲究：实现文件 `allowedips.c:424` 末尾有 `#include "selftest/allowedips.c"`，`ratelimiter.c:223` 末尾有 `#include "selftest/ratelimiter.c"`，`receive.c:333` 末尾有 `#include "selftest/counter.c"`。selftest 代码因此能直接访问所在文件的 `static` 内部函数（比如 `add()`、`lookup()`、`wg_ratelimiter_allow()`），这是独立编译的测试文件做不到的。换言之，这些自检是**白盒测试**，不是外部黑盒工具。

「两类日志」指编译期受控的 `pr_debug` / `net_dbg_ratelimited`，以及断言式的 `WARN_ON(IS_ENABLED(DEBUG) && ...)`。前者如 `peer.c:63` 的 `Peer %llu created`、`timers.c:47` 的握手重试放弃、`cookie.c:230` 的 cookie 解密失败提示，属于「发生了什么」的叙事；后者如 `allowedips.c:45` 在 trie 栈深度达到 `MAX_ALLOWEDIPS_DEPTH`（该常量在 `allowedips.c:9` 定义为 129）时告警、`noise.c:351` 的握手路径校验，属于「不该发生却发生了」的告警。按内核通用语义，定义 `DEBUG` 时 `pr_debug` 会被无条件编入，未定义时通常依赖 `CONFIG_DYNAMIC_DEBUG` 在运行期控制（具体以目标内核配置为准）。

「六个 fuzz 目标」指 `wireguard-tools/src/fuzz/Makefile:5` 的 `FUZZERS := config uapi stringlist cmd set setconf`。它们都围绕 libFuzzer 的 `LLVMFuzzerTestOneInput` 入口工作，用 `fmemopen`、`hacked_fopen`、宏替换 `stat` 等手法，把原本要访问真实文件或 netlink 的用户态代码，改造成接受内存输入的纯函数。「一个静态分析目标」则是工具主 Makefile 第 107–108 行的 `check: clean` 规则，调用 `scan-build ... $(MAKE) wg`，用 Clang Static Analyzer 在编译过程中做路径敏感的检查。一个是「喂随机数据看会不会崩」，一个是「不运行只读代码找可疑路径」，两者互补而不互相替代。

### 3. 关键数据结构与源码位置

作为构建与检查主题，本节只点名被自检覆盖的关键结构与可核验的源码位置，字段逐项解释交给 05 册，不在这里展开字段表。

限速自检围绕 `ratelimiter.c:26-32` 的 `struct ratelimiter_entry` 展开：它把 `last_time_ns`、`tokens`、`ip`、`net`、自旋锁 `lock`、哈希节点 `hash` 与 RCU 回调 `rcu` 组织在一起（字段见 05-08）。同文件 `34-39` 行的匿名枚举给出令牌桶口径：`PACKETS_PER_SECOND = 20`、`PACKETS_BURSTABLE = 5`、`PACKET_COST = NSEC_PER_SEC / PACKETS_PER_SECOND`、`TOKEN_MAX = PACKET_COST * PACKETS_BURSTABLE`。`wg_ratelimiter_allow()`（`ratelimiter.c:84`）用 `hsiphash_2u32(net_word, ip, &key)` 给 IPv4 选桶，IPv6 则取源地址前 64 位用 `hsiphash_3u32` 选桶，注释明确说「ratelimit the whole /64」；表大小 `table_size` 在 `wg_ratelimiter_init()` 中按 `totalram_pages()` 计算，内存大于 1 GiB 时取 8192，`max_entries = table_size * 8`（原理见 06-10）。自检之所以能覆盖这些，是因为它和被测函数在同一个编译单元里。

allowedips 自检围绕 trie 节点与 `MAX_ALLOWEDIPS_DEPTH = 129` 的栈深度上限（`allowedips.c:9`），通过 include 注入后可直接调用 `static` 的 `add()`、`remove()`、`find_node()`、`lookup()`、`common_bits()` 等内部函数，验证 IPv4/IPv6 前缀的插入、精确匹配、最长前缀查找与删除回收（结构见 05-04，原理见 06-07）。packet counter 自检的实现由 `receive.c:333` 注入，覆盖 `queueing.h` 定义的包状态枚举在收发路径上的计数一致性（字段见 05-06）。cookie 本身在本快照中**没有**独立的 selftest include；`cookie.c` 提供的是 `wg_cookie_validate_packet()` 的四级判定状态机（`INVALID_MAC`、`VALID_MAC_BUT_NO_COOKIE`、`VALID_MAC_WITH_COOKIE_BUT_RATELIMITED`、`VALID_MAC_WITH_COOKIE`，见 `cookie.c:119-154`），其中限速那一环调用 `wg_ratelimiter_allow()`，因而被 ratelimiter 自检间接覆盖（cookie 原理见 06-09，模块见 07-09）。

### 4. 关键流程与调用链

编译链路只有三跳。`drivers/net/Kconfig:92` 的 `WIREGUARD_DEBUG` 被选中后，Kbuild 把 `CONFIG_WIREGUARD_DEBUG=y` 传给 Makefile；`drivers/net/wireguard/Makefile:2` 据此向 `ccflags` 追加 `-DDEBUG`；于是所有 `#ifdef DEBUG` 块参与编译。注意第 3–16 行的目标列表里并没有单独的 selftest 目标，因为自检代码是被 `#include` 拼进 `allowedips.o`、`ratelimiter.o`、`receive.o` 的——这也是为什么 `selftest/*.c` 不需要也不应该独立编译。

加载链路在 `main.c:20-61`。`wg_mod_init` 先 `wg_allowedips_slab_init()`，失败跳 `err_allowedips`；随后进入 `DEBUG` 块，把 `ret` 预设为 `-ENOTRECOVERABLE`，再依次取反调用三项自检，任一返回 false 就用短路或提前失败，统一跳到 `err_peer`。这里有两个容易看漏的细节：其一，`err_peer` 标签下只有 `wg_allowedips_slab_uninit()`，因为此刻 peer、device、netlink 都还没初始化，回滚范围必须精确；其二，`wg_noise_init()`（第 34 行）在自检之后、且没有检查返回值，说明它在此快照的接口是 void。自检全过之后才依次 `wg_peer_init()`、`wg_device_init()`、`wg_genetlink_init()`，每层失败各跳自己的 `err_*` 标签；全部成功后打印两行 `pr_info`（第 48–49 行），模块进入可用状态。卸载函数 `wg_mod_exit` 按 `wg_genetlink_uninit` → `wg_device_uninit` → `wg_peer_uninit` → `wg_allowedips_slab_uninit` 逆序回收。用户态 `wg` 的配置链路走 netlink（`WG_CMD_SET_DEVICE` / `WG_CMD_GET_DEVICE`），与自检链路完全独立——自检发生在加载瞬间，不受后续配置影响（netlink 原理见 06-14）。

用户态检查链路分两支。`fuzz/Makefile` 用 `clang` 加 `-fsanitize=fuzzer -fsanitize=address -std=gnu11 -idirafter ../uapi -D_GNU_SOURCE` 编译六个目标，每个目标把被测源文件直接 `#include` 进来以复用内部函数；libFuzzer 生成变长字节流，各 harness 将其切成参数、配置行或接口名，调用真实解析入口，ASan 负责捕获越界与释放后使用。主 Makefile 的 `check` 目标则先 `clean` 再 `scan-build --html-title=wireguard-tools -maxloop 100 --view --keep-going $(MAKE) wg`，在不运行程序的前提下扫描 `wg` 的编译过程。三条路径与两类检查的关系见图 02-05-01。

### 5. 配置/命令/代码实例

先看自检的调用契约，这是 `main.c:24-38` 的原样片段（省略空行）：

```c
ret = wg_allowedips_slab_init();
if (ret < 0)
    goto err_allowedips;

#ifdef DEBUG
ret = -ENOTRECOVERABLE;
if (!wg_allowedips_selftest() || !wg_packet_counter_selftest() ||
    !wg_ratelimiter_selftest())
    goto err_peer;
#endif
wg_noise_init();

ret = wg_peer_init();
if (ret < 0)
    goto err_peer;
```

再看两条Makefile 片段，左边是内核驱动、右边是用户态工具，对比最直观：

```makefile
# drivers/net/wireguard/Makefile（节选）
ccflags-y := -D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'
ccflags-$(CONFIG_WIREGUARD_DEBUG) += -DDEBUG
obj-$(CONFIG_WIREGUARD) := wireguard.o

# wireguard-tools/src/Makefile（节选）
CFLAGS ?= -O3
CFLAGS += -std=gnu99 -D_GNU_SOURCE
CFLAGS += -Wall -Wextra
ifeq ($(DEBUG),yes)
CFLAGS += -g
endif
check: clean
	scan-build --html-title=wireguard-tools -maxloop 100 --view --keep-going $(MAKE) wg
```

注意用户态的 `DEBUG=yes` 只追加 `-g`（调试符号），既不打开 `-DDEBUG`，也不影响自检；这与内核侧的 `WIREGUARD_DEBUG=y` 是两件不同的事。下面给出一次带自检的调试构建与加载命令，然后用内核日志验证三项自检是否真的跑过：

```bash
# 以模块方式构建并显式打开内核调试开关
make -C /lib/modules/$(uname -r)/build M=$PWD/drivers/net/wireguard \
     CONFIG_WIREGUARD=m CONFIG_WIREGUARD_DEBUG=y modules
sudo insmod drivers/net/wireguard/wireguard.ko
# 查看加载日志与自检相关信息
sudo dmesg | grep -i wireguard
```

用户态的 fuzz 与静态检查同样可以一键复现：

```bash
# 六个 fuzz 目标，需 clang 与 libFuzzer/ASan 运行库
make -C wireguard-tools/src/fuzz clean all
./wireguard-tools/src/fuzz/config -runs=10000 corpus_config
# 静态分析（扫描 wg 的编译过程，不运行程序）
make -C wireguard-tools/src check
```

`config` harness 的手法是六个目标里最易读的一个：它把输入首字节的最高位当作模式位（`file = !!(data[0] >> 7)`），余下字节复制成以 NUL 结尾的字符串；文件模式下逐行喂给 `config_read_line()`，遇到返回 false 就重新 `config_read_init()` 模拟新配置段，命令模式下按空格切词后调用 `config_read_cmd()`，最后统一 `free_wgdevice()`。这种「一个字节决定解析路径」的设计让 fuzzer 用极少输入就能同时覆盖两条分支。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是混淆三个 `DEBUG`。内核 `CONFIG_WIREGUARD_DEBUG=y` 打开三项自检与详细日志；`wireguard-tools/src/Makefile` 的 `make DEBUG=yes` 只追加 `-g`；`fuzz/Makefile` 里的 `-D'RUNSTATEDIR="/var/empty"'` 与 `-D'main(a,b)=wg_main(a,b)'`（见第 23 行）则是给 harness 改写入口与路径，与调试开关无关。给工具加 `DEBUG=yes` 不会让内核模块多打印一行，给内核加 `WIREGUARD_DEBUG=y` 也不会让 `wg` 多输出任何东西。

第二个陷阱是把本快照中为空的 `selftest/` 目录当成「上游没有自检」。恰恰相反，三个声明、三处调用、三处 `#include` 都真实存在，只是实现文件未随本快照分发；据此断言「自检不存在」或「自检内部如何如何」都不可靠，正确做法是标注需对照实际版本核验。第三个陷阱是认为调试构建可以上线。`WIREGUARD_DEBUG` 的帮助文本自己就写着「Say N here unless you know what you're doing」：额外校验、详细日志与 `WARN_ON` 会带来开销与噪声，生产构建应关闭（部署口径见 03-01，调优见 08-02）。

第四个陷阱是夸大 fuzz 的证明范围。六个 harness 都通过宏替换把外部依赖换成了内存桩，例如 `uapi.c:9` 用 `#define stat(a, b) ({ return hacked_userspace_interface_file(iface); 0; })` 劫持 `stat`，`setconf.c:38-42` 把 `struct hacked_pointers` 指针编码成十进制字符串再 `strtoul` 还原。这意味着 fuzz 验证的是**纯解析逻辑在受控桩下的内存安全**，不验证真实 socket、真实 netlink 与内核侧行为；ASan 没报错不等于协议实现正确。第五个陷阱是把静态分析当成正确性证明：`check` 目标只扫描编译期路径，不发现运行期竞态与协议逻辑错误；`--view` 还会尝试打开浏览器展示报告，在无图形环境需留意。第六个陷阱是把「自检通过」等同于「隧道可用」：自检只在模块加载瞬间跑一次，之后密钥、endpoint、路由任何一项配错都会让隧道静默不通，仍须用 `wg show` 的 `latest handshake` 与 `transfer` 判断（排障见 08-03）。

最佳实践按此顺序执行：先在构建阶段用 `CONFIG_WIREGUARD_DEBUG=y` 做一次开发验证，确认三行自检与两行 `pr_info` 齐全；再把 fuzz 与 `make check` 纳入持续集成，专门守住用户态解析面；随后用不带调试开关的干净构建做功能与性能验证（基准方法见 08-01）；最后才按生产配置关闭调试并上线（上线 checklist 见 08-06）。顺序不能颠倒——先在调试构建上跑通解析与加载，再切回生产构建，可以把「自检失败」与「生产配置差异」两类问题分开定位；反过来先上生产再补调试，往往要在客户现场重新编模块。

### 7. 小结与延伸阅读

本篇把 WireGuard Linux 的检查体系拆成四层：编译期由 `Kconfig:92` 的 `WIREGUARD_DEBUG` 经 `Makefile:2` 转成 `-DDEBUG`；加载期由 `main.c:28-33` 在 `DEBUG` 下短路调用 allowedips、packet counter、ratelimiter 三项白盒自检，失败以 `-ENOTRECOVERABLE` 拒绝加载；运行期靠 `pr_debug` 与 `WARN_ON(IS_ENABLED(DEBUG) && ...)` 输出事件与异常；用户态靠 `fuzz/` 六个 libFuzzer 目标和 `make check` 的 `scan-build` 守住解析器。三处自检声明都在头文件 `#ifdef DEBUG` 内、三处实现都靠 `#include "selftest/*.c"` 注入本快照为空的目录，这是本篇最需要对照实际版本核验的地方。

延伸阅读按三条线走：构建开关与命令全集回到 02 册前四篇，结构字段去 `05 册`（限速与队列见 05-08、trie 见 05-04），机制与调用链去 06 册（握手与包处理见 06-01、cookie 见 06-09、限速见 06-10），目录级模块职责去 07 册（网络模块见 07-09、时限与限速见 07-10）。跨册随查按（字段见 05-08 ｜ 参数见 02-02 ｜ 原理见 06-10 ｜ 模块见 07-10）执行：结构体逐字段去 05、构建参数去 02、令牌桶与哈希表原理去 06、限速模块职责去 07、运维与排障去 08。凡本篇标注「需对照实际版本核验」的自检实现细节与日志字符串，均以 `_wglinux_build/upstream_src/` 下对应文件为准，本套资料不编造未核验的路径与取值。
