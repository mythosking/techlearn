# WireGuard Linux 技术资料 · 01 基础与概述

## 01-01 WireGuard Linux 是什么：设计目标、能力矩阵与适用边界

### 1. 背景与动机

要理解 WireGuard Linux 是什么，必须先把它和「WireGuard 协议」以及「WireGuard 的其他实现」区分开。WireGuard 协议本身是一个由 Jason A. Donenfeld 设计的、基于 Noise_IK 的现代 VPN 协议，其规范与参考实现分布在多个仓库；而本篇讨论的 WireGuard Linux，特指把这一协议实现为 Linux 内核模块的那份代码，即上游 `wireguard-linux` 内核树中 `drivers/net/wireguard/` 目录下的驱动，加上与之配套的 `wireguard-tools` 用户态工具（wg 与 wg-quick）。本套资料的事实锚点是 `_wglinux_build/upstream_src/wireguard-linux-src/`（stable 分支内核驱动快照）与 `_wglinux_build/upstream_src/wireguard-tools/`（版本 1.0.20260223，2026-03 抓取），下文凡出现源码路径均相对这两个根目录，规范中为节约篇幅省略前缀。

先看模块自己怎么介绍自己。`drivers/net/wireguard/main.c` 的模块初始化函数 `wg_mod_init` 在成功加载后打印两行 `pr_info`：`WireGuard 1.0.0 loaded. See www.wireguard.com for information.` 与版权行；同一文件末尾用 `MODULE_LICENSE("GPL v2")`、`MODULE_DESCRIPTION("WireGuard secure network tunnel")`、`MODULE_VERSION(WIREGUARD_VERSION)`、`MODULE_ALIAS_RTNL_LINK(KBUILD_MODNAME)` 与 `MODULE_ALIAS_GENL_FAMILY(WG_GENL_NAME)` 声明模块身份。这里的 `WIREGUARD_VERSION` 定义在 `drivers/net/wireguard/version.h`，值为 `"1.0.0"`——注意这是驱动自身的版本字符串，不是 Linux 内核版本，也不是用户态工具版本，三者要分开。用户态 `wireguard-tools/src/version.h` 里 `WIREGUARD_TOOLS_VERSION` 为 `"1.0.20260223"`，又是一个独立版本号。把这三个版本号混为一谈是阅读上游资料时最常见的错误之一。

从设计目标看，WireGuard Linux 的定位是「内核态的、高性能的、极简配置面的安全网络隧道」。它以一个标准 `net_device`（网卡）的形态接入内核网络栈，接口名通常是 `wg0`、`wg1` 等；对内核来说它和普通网卡一样可被 `ip`、`ifconfig`、路由表操作，对应用层则完全透明——把流量路由到 wg0，内核就把它交给隧道封装加密后从真实物理网卡发出。`device.c` 的 `wg_setup` 负责初始化这个 `net_device`，`wg_newlink` 处理来自 rtnetlink 的建链请求，`MODULE_ALIAS_RTNL_LINK` 则让 `ip link add` 能自动加载本模块。这种「伪装成网卡」的设计是它区别于用户态 VPN 的根本：加解密在内核完成，不经过内核态与用户态之间的数据拷贝。

再看清单一面。整个内核驱动约 4800 行 C 代码（含头文件），核心源文件包括负责模块入口与 netdev 注册的 `main.c`、设备生命周期的 `device.c`、对等体管理的 `peer.c`、路由 trie 的 `allowedips.c`、握手引擎的 `noise.c`、消息布局的 `messages.h`、发送与接收的 `send.c` / `receive.c`、socket 与 endpoint 的 `socket.c`、定时器的 `timers.c`、sysfs 的 `sysfs.c`、限速的 `ratelimiter.c`、cookie 的 `cookie.c`，以及加密原语 `chacha20.c`、`poly1305.c`、`curve25519.c`、`blake2s.c`、`siphash.c`（后几者位于内核树 `lib/crypto/`，在本资料快照中置于 `wireguard-linux-src/lib/crypto/`）。用户态配置通过 netlink 通用族完成：uapi 头 `include/uapi/linux/wireguard.h` 定义了族名 `WG_GENL_NAME "wireguard"`、版本 `WG_GENL_VERSION 1`、两个命令 `WG_CMD_GET_DEVICE` 与 `WG_CMD_SET_DEVICE`，以及 device / peer / allowedip 三层属性枚举。这份 uapi 头顶部注明「auto-generated from Documentation/netlink/specs/wireguard.yaml」，说明当前上游已把 netlink 定义纳入 YAML 规范统一管理，这是阅读时需要注意的版本特征。

本套资料的版本基准统一写「wireguard-linux stable 分支内核驱动快照 + wireguard-tools 1.0.20260223」。凡涉及具体字段、函数名签名、命令选项与默认值，均以这两个快照为准并尽量给出源码路径；由于内核与工具链持续演进，个别细节需对照目标系统实际版本核验。这一点贯穿全册：本套资料提供的是「基于真实源码的深度解读」，不是「对某个发行版某个内核版本的逐字说明书」。

### 2. 核心概念

WireGuard Linux 的核心概念可以压缩为四句话：**一个网卡、两类密钥、三层状态、四个边界**。

一个网卡，指 wg0 是一个标准 `net_device`。`device.c` 中 `wg_setup` 把它的 `ndo_open`、`ndo_stop`、`ndo_start_xmit`、`ndo_get_stats64`、`ndo_set_config` 等操作挂到 WireGuard 的实现上（`wg_open`、`wg_stop` 等在 `device.c` 中定义）。内核协议栈按路由把出站包交给 `ndo_start_xmit`，WireGuard 据此进入发送路径；入站解密后的包通过 `netif_rx` 一类接口重新注入协议栈。理解「它是网卡」是理解全部配置与排障的前提——很多看似 WireGuard 的问题其实是路由问题。

两类密钥，指 Curve25519 密钥对与可选的预共享密钥（PSK）。每个接口有一把私钥（`WGDEVICE_A_PRIVATE_KEY`），由它派生出公钥；每个 peer 配置对端公钥（`WGPEER_A_PUBLIC_KEY`）；密钥长度由 `WG_KEY_LEN 32` 规定，即 32 字节。`wg genkey`、`wg pubkey`、`wg genpsk` 三个子命令分别生成私钥、由私钥导出公钥、生成预共享密钥。私钥只应留在本地接口配置中，绝不出现在配置文件分发的公钥里——这是密钥分发的基本纪律（密钥流程详见 03-03）。

三层状态，指接口（device）、对等体（peer）、地址前缀（allowedip）三个层级。netlink 属性枚举恰好对应这三层：`wgdevice_attribute`、`wgpeer_attribute`、`wgallowedip_attribute`。一个 device 下可有多个 peer，一个 peer 下可有多个 allowedip；allowedip 是「允许来自该 peer 的源地址范围」与「发往该范围应走该 peer」的双重语义，这正是 WireGuard 的路由模型（trie 实现见 05-04、原理见 06-07）。

四个边界，是理解能力范围的关键。第一，**内核态边界**：数据面加解密在内核完成，`net_device` 是唯一入口，不存在用户态转发进程。第二，**UDP 承载边界**：所有 WireGuard 报文封装在 UDP 中，默认监听端口 51820，uapi 里对应 `WGDEVICE_A_LISTEN_PORT`；它不直接跑在裸 IP 之上，也不监听 TCP。第三，**无内建密钥分发边界**：协议不定义任何中心服务器、证书体系或自动密钥交换，公钥分发完全交给运维或上层工具，这是「密钥即身份」哲学的直接后果。第四，**无内建地址管理边界**：协议不分配 VPN 地址、不下发路由，`AllowedIPs` 与地址配置由控制面（wg 工具或第三方控制面）显式写入。

下表按「能做 / 不能做」给出能力矩阵，结论均以本快照源码与工具为依据。

| 能力项 | 结论 | 依据源码位置 |
|---|---|---|
| 以网卡形态接入内核协议栈 | 能做，注册为 net_device | `drivers/net/wireguard/main.c`、`device.c` 的 `wg_setup` |
| 内核态加解密 | 能做，无用户态数据拷贝 | `send.c`、`receive.c`、`lib/crypto/` |
| 基于 Noise_IK 的握手与会话 | 能做 | `noise.c`、`noise.h` 的 `noise_handshake_state` |
| 通过 netlink 配置接口与 peer | 能做，GET/SET 两条命令 | `include/uapi/linux/wireguard.h` 的 `wg_cmd` |
| 多 peer 与 AllowedIPs 路由 | 能做，trie 实现 | `allowedips.c`、`allowedips.h` |
| 抗重放、cookie、限速 | 能做 | `cookie.c`、`ratelimiter.c`、`receive.c` |
| 内建中心服务器或证书 CA | 不做，协议无此设计 | uapi 属性中无相关定义 |
| 自动分配 VPN 地址与下发路由 | 不做，需控制面写入 | `WGDEVICE_A_*` / `WGPEER_A_*` 属性语义 |
| 直接跑在 TCP 或裸 IP 上 | 不做，仅 UDP 承载 | `socket.c` 的 UDP socket 操作 |
| 与 IPsec ESP 协议互通 | 不做，是独立协议 | `messages.h` 的消息类型定义 |

### 3. 关键数据结构与源码位置

作为总览册，本节只点名关键结构与真实源码路径，逐字段定义统一交给 05 册，不在这里展开字段表。需要建立的结构地图分五层。

设备与 netdev 层以 `drivers/net/wireguard/device.c`、`main.c` 为代表，核心结构是 `wg_device`，它把 `net_device`、私钥、监听端口、 peer 哈希表、allowedips trie 与各类锁组织在一起（字段见 05-02）。对等体层以 `peer.c`、`peer.h` 为代表，核心结构 `wg_peer` 持有公钥、endpoint、握手状态、计数器与发送队列（字段见 05-03）。路由层以 `allowedips.c`、`allowedips.h` 为代表，核心结构 `wg_allowedips` 是 v4/v6 混合 trie（字段见 05-04）。握手与消息层以 `noise.c`、`noise.h`、`messages.h` 为代表，`noise_handshake_state` 枚举定义握手状态机，消息结构定义各类报文布局（字段见 05-05、原理见 06-02、06-04）。收发与网络层以 `send.c`、`receive.c`、`socket.c`、`cookie.c` 为代表（字段见 05-06、05-07）。时限与限速层以 `timers.c`、`ratelimiter.c`、`queueing.h` 为代表（字段见 05-08）。加密原语上下文见 05-09。

配置面的关键头是 `include/uapi/linux/wireguard.h`，它定义 `wgdevice_attribute`、`wgpeer_attribute`、`wgallowedip_attribute` 三层属性枚举、`wgdevice_flag` / `wgpeer_flag` / `wgallowedip_flag` 三组标志位，以及 `wg_cmd` 的两条命令；完整常量与标志交给 04-05、04-06。用户态工具侧的关键源在 `wireguard-tools/src/`，包括 `wg.c`（命令入口）、`config.c`（配置解析）、`encoding.c`（base64 与密钥编解码）、`curve25519.c`（密钥运算）、`ipc.c`（IPC 抽象）、`ipc-linux.h`（netlink 实现）与 `wg-quick` 脚本，模块能力交给 07-13。

### 4. 关键流程与调用链

模块加载链路在 `main.c` 中非常清晰。`wg_mod_init` 依次调用 `wg_allowedips_slab_init()`（为 trie 节点准备 slab 缓存），在 `DEBUG` 编译下运行 `wg_allowedips_selftest()`、`wg_packet_counter_selftest()`、`wg_ratelimiter_selftest()` 三项自检（失败则返回 `-ENOTRECOVERABLE`），随后 `wg_noise_init()`、`wg_peer_init()`、`wg_device_init()`、`wg_genetlink_init()`，全部成功后打印加载信息。这段初始化顺序体现了依赖关系：allowedips 与 noise 是基础，peer 依赖它们，device 依赖 peer，netlink 最后注册以便用户态配置。卸载函数 `wg_mod_exit` 按相反顺序 `wg_genetlink_uninit()`、`wg_device_uninit()`、`wg_peer_uninit()`、`wg_allowedips_slab_uninit()` 回收资源。任何一层初始化失败都通过 `goto` 标签回滚已完成的层，这是内核模块的标准写法（完整链路见 06-01）。

配置链路从用户态的 `wg` 命令开始：`wg` 通过 `wireguard-tools/src/ipc-linux.h` 中的 `mnlg_socket_open(WG_GENL_NAME, WG_GENL_VERSION)` 打开到 `wireguard` 通用族的 netlink 套接字，把配置序列化为 `WG_CMD_SET_DEVICE` 请求发给内核；内核侧在 netlink 层解析 `WGDEVICE_A_*` / `WGPEER_A_*` / `WGALLOWEDIP_A_*` 属性，更新对应的 device 与 peer 状态。查询方向则是 `WG_CMD_GET_DEVICE`，`wg show` 用它拉取接口与 peer 的运行状态（netlink 原理见 06-14，命令全集见 04-01）。

数据链路分收发两条。发送方向：内核按路由把包交给 wg0 的 `ndo_start_xmit`，进入 `send.c` 的发送逻辑，查 allowedips 找到目标 peer，构造数据消息、用会话密钥经 ChaCha20-Poly1305 加密、封装为 UDP 后从底层物理网卡发出。接收方向：`socket.c` 的 UDP socket 收到报文，经 `cookie.c` / `ratelimiter.c` 的防护检查，`receive.c` 解析消息类型（握手或数据），握手交 `noise.c` 处理，数据包验重放、解密、查 allowedips 校验源地址，最后注入内核协议栈。这两条链路的逐段实现分别在 06-05、06-06，模块职责在 07-07、07-08。

### 5. 配置/命令/代码实例

本篇作为总览册，只给理解定位所需的最小命令，完整参数交给 04 册，配置体系交给 03 册。下面这段是建立一个最小点对点隧道的两端配置，用 `wg` 工具的标准写法：

```bash
# 在两端各自生成私钥，并导出公钥
wg genkey | tee privatekey | wg pubkey > publickey

# 以本端私钥建立接口，监听 51820 端口
ip link add wg0 type wireguard
ip address add 10.0.0.1/24 dev wg0
wg set wg0 private-key ./privatekey listen-port 51820

# 添加对端：公钥、endpoint、允许的源地址段
wg set wg0 peer <对端公钥> endpoint 203.0.113.9:51820 allowed-ips 10.0.0.2/32
ip link set wg0 up
```

这段写法体现了三个要点：`wg genkey | tee privatekey | wg pubkey` 是管道式密钥生成，私钥落到本地文件 `privatekey`，公钥从同一私钥派生后单独保存；`ip link add wg0 type wireguard` 依赖 `MODULE_ALIAS_RTNL_LINK` 自动加载模块；`wg set` 的 `peer`、`endpoint`、`allowed-ips` 三个参数分别对应 `WGPEER_A_PUBLIC_KEY`、`WGPEER_A_ENDPOINT`、`WGALLOWEDIP_A_*` 属性（参数全集见 04-01、04-02）。

下面给出验证链路的典型输出，用 `wg show` 查看握手是否建立：

```bash
wg show wg0
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
interface: wg0
  public key: <本端公钥>
  private key: (hidden)
  listening port: 51820
peer: <对端公钥>
  endpoint: 203.0.113.9:51820
  allowed ips: 10.0.0.2/32
  latest handshake: 12 seconds ago
  transfer: 1.25 KiB received, 980 B sent
```

逐行判读如下。第一行 `interface: wg0` 是接口名，来自 `wg show` 对 netlink `WG_CMD_GET_DEVICE` 返回的 `WGDEVICE_A_IFNAME` 属性渲染，确认查询命中了正确的设备；若这里显示的是别的接口名，说明多接口环境下选错了对象。第二行 `public key` 由本端私钥经 Curve25519 派生，对应 `WGDEVICE_A_PUBLIC_KEY`，应与分发给对端的公钥完全一致；对端若配置了不同的公钥，握手将静默失败。第三行 `private key: (hidden)` 是工具刻意不回显私钥的表现，说明 wg 工具在展示层做了保护，真实私钥仍存在于内核接口的 `WGDEVICE_A_PRIVATE_KEY` 中；任何要求你「从 show 输出复制私钥」的说法都是错误的。第四行 `listening port: 51820` 对应 `WGDEVICE_A_LISTEN_PORT`，是 UDP 监听端口；若这里为空或为 0，通常是没有设置私钥或接口未 up。第五行 `peer:` 后是对端公钥，对应 `WGPEER_A_PUBLIC_KEY`，一个接口下可以有多个这样的 peer 段。第六行 `endpoint` 对应 `WGPEER_A_ENDPOINT`，是对端的可达地址加端口；NAT 后的 peer 若没有持久 keepalive，endpoint 可能显示为动态学习到的地址而非配置值（keepalive 见 06-11）。第七行 `allowed ips` 对应 `WGALLOWEDIP_A_IPADDR` 与 `WGALLOWEDIP_A_CIDR_MASK`，含义是「只接受源地址在此范围的该 peer 流量，且发往此范围的流量走该 peer」，写错掩码会导致隧道静默不通（原理见 06-07）。第八行 `latest handshake` 是握手距今时间，对应 `WGPEER_A_LAST_HANDSHAKE_TIME`；这是判断隧道是否真正可用的最关键一行——若长期为空或时间很旧，说明握手从未成功或已过期，应优先排查公钥、endpoint 与时钟（握手时序见 06-03）。第九行 `transfer` 分别对应 `WGPEER_A_RX_BYTES` 与 `WGPEER_A_TX_BYTES`，是累计收发字节数；只有握手成功且 allowedips 正确时这里才会增长，若握手成功但字节数为 0，多半是路由没有把目标流量送到 wg0（路由部署见 03-04）。清理环节：`ip link del wg0` 删除接口并释放内核资源，无需单独停止进程，因为数据面本就在内核中。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是把 WireGuard Linux 与 WireGuard 协议、与 wireguard-go / wireguard-nt 混为一谈。协议是规范，Linux 实现是内核模块，wireguard-go 是用户态 Go 实现，wireguard-nt 是 Windows 内核驱动，四者共享协议但代码、性能与部署形态完全不同。本套资料只讲 `drivers/net/wireguard/` 这份内核实现（与 Go 版本的性能差异已在 wireguard-windows 资料的 SUP 文档中讨论）。第二个陷阱是把它当用户态代理：数据面在内核，没有转发进程，用 `ps` 找不到「WireGuard 进程」是正常的，不要据此判断它没运行。

第三个陷阱是混淆三个版本号：`version.h` 的 `1.0.0`、`WIREGUARD_TOOLS_VERSION` 的 `1.0.20260223`、以及目标系统的内核版本，三者独立（版本基准见 01-04）。第四个陷阱是照抄绝对性能数字：吞吐、pps、握手速率一律需在目标机型实测，本套资料不给绝对值（基准方法见 08-01、调优见 08-02）。第五个陷阱是以为有内建密钥服务器：协议没有 CA、没有中心、没有自动分发，公钥交换全靠运维或上层控制面（控制面选型见 wireguard-windows 资料的 DESIGN-07）。

最佳实践可以归纳为四步：先用 `wg --version` 与 `ip link add ... type wireguard` 确认模块可用（构建见 02-03）；再从最小两点配置起步，用 `wg genkey`/`wg pubkey` 规范地生成与分发密钥，私钥永不出本机（密钥流程见 03-03）；随后用 `wg show` 的 `latest handshake` 与 `transfer` 两行确认隧道真正可用，而不是只看接口 up（排障见 08-03）；最后才把 allowedips 收敛到最小必要范围、配置 keepalive 与持久化（部署见 03-04、03-05）。

至于「何时不该用 WireGuard Linux」，边界同样明确：需要中心化用户管理、ACL、SSO 且不打算自建控制面时，单独的内核模块不够，需配合 wg-easy / Headscale 一类控制面；需要与非 WireGuard 协议（如 IPsec、OpenVPN）互通时，它是独立协议，无法直接互通；运行在无法加载内核模块的环境（如某些受限容器、非 Linux 平台）时，应改考虑 wireguard-go 或 wireguard-nt；需要厂商承诺某个绝对吞吐数字时，本套资料不提供这类断言。这些边界与第 2 节能力矩阵互为镜像，应一起对照。

### 7. 小结与延伸阅读

本篇把 WireGuard Linux 定位为「以标准 net_device 形态接入内核协议栈、数据面加解密在内核完成、通过 netlink 由 wg 工具配置、协议本身无内建密钥分发与地址管理的现代 VPN 隧道实现」：能做网卡接入、内核态加解密、Noise_IK 握手、netlink 配置、多 peer 与 AllowedIPs 路由、抗重放与限速；不做中心服务器、不做自动地址分配、不跑 TCP、不与 IPsec 互通。`wg_mod_init` 的分层初始化与 `wg_mod_exit` 的逆序回收、`wg_cmd` 的 GET/SET 两条命令、`wgdevice/wgpeer/wgallowedip` 三层属性枚举，构成后续所有篇章的共同骨架。

延伸阅读建议按三条线走：定位与协议背景读 `drivers/net/wireguard/main.c` 的模块声明与 `include/uapi/linux/wireguard.h`；实现细节按 05 册看结构字段、按 06 册看机制与调用链、按 07 册看模块职责；运维落地读 03 册部署、04 册参数、08 册排障。跨册随查按（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-01）执行：结构体逐字段去 05、参数与命令全集去 04、机制与调用链去 06、目录级模块能力去 07、运维场景与基准去 08。凡本篇标注「需对照实际版本核验」的字段、函数名签名、命令选项与版本号，均以 `_wglinux_build/upstream_src/` 下对应文件为准，本套资料不编造未核验的路径与取值。

## 01-02 与 IPsec / OpenVPN / wireguard-go / wireguard-nt 的实现对比

### 1. 背景与动机

选型与澄清误解都需要一张准确的对比图。关于 WireGuard 的许多争论，其实源于把「协议」与「具体实现」混为一谈：有人拿 IPsec 的吞吐量直接对比 wireguard-go，有人把 wireguard-nt 的 Windows 集成特性当成 Linux 内核版也具备，还有人以为 OpenVPN 和 WireGuard 是同一类东西的不同配置。本篇的目的不是评高下，而是按「实现形态」这一维度，把 WireGuard Linux 与四类常见对象摆到一起，给出可执行的判断依据。口径声明：对 WireGuard Linux 的所有结论以本快照源码为准；对 IPsec、OpenVPN 只作业界通行的定性描述，对 wireguard-go、wireguard-nt 依据其官方定位与架构特征，均不做源码级断言，具体能力需对照各自实际版本核验；本套资料不写绝对性能数字。

先看四个对比对象各自的实现形态。IPsec 是一组协议族（ESP/AH/IKE），在 Linux 上由内核的 xfrm 框架与用户态的 strongSwan / Libreswan 等 IKE 守护进程配合实现；它支持 AES-GCM、ChaCha20-Poly1305 等多种 AEAD，可借助 AES-NI、QAT 等硬件加速。OpenVPN 是用户态程序，基于 TLS 握手与自研的 UDP/TCP 承载，加密走 OpenSSL，数据面在用户态、存在内核与用户态拷贝。wireguard-go 是 WireGuard 协议的用户态 Go 实现，官方主页明确写着在 Linux 上应改用内核模块，因为内核模块「faster and better integrated into the OS」；它以 TUN 设备形态工作，依赖 Go runtime。wireguard-nt 是面向 Windows 的内核驱动，供 Windows 平台使用。WireGuard Linux 则是本篇主角：内核态、net_device 形态、netlink 配置。

为什么实现形态比协议本身更影响选型？因为数据面的位置决定了拷贝开销与并发模型。WireGuard Linux 的加解密在内核完成，包从网卡到隧道封装全程不跨用户态边界；wireguard-go 与 OpenVPN 的数据面在用户态，每个包要进出内核的 TUN 设备，引入拷贝与调度开销。这也是之前讨论高性能 VPN 时反复强调的结论：内核态实现（wireguard-linux、wireguard-nt）数据面性能最高，用户态的 wireguard-go 明显更低——不是实现优劣，而是架构决定的性能与兼容性取舍。

进一步拆开，用户态实现的开销来自三处：其一， packet 从内核协议栈经 TUN 设备读到用户态进程，再从用户态写回内核，至少两次跨边界拷贝；其二， Go 或 OpenSSL 的运行时调度与 GC（对 Go 而言）会在数据路径上引入不可预测的延迟抖动；其三，用户态程序无法直接利用网卡的多队列与内核的 GSO/GRO 卸载，批量处理能力受限。内核态实现则规避了这三处：包以 `sk_buff` 形态在内核各子系统间传递，加密函数直接调用内核 crypto 原语，多队列 RSS 与 padata 并行加密可与现有内核基础设施对接。当然，内核态并非没有代价——它必须遵守内核编程约束（不能睡眠的上下文、RCU 生命周期、内存分配限制），开发与调试难度显著高于用户态，这也是 wireguard-go 存在的意义：在无法加载内核模块的平台或需要快速迭代的场景，用户态实现仍有无可替代的价值（其平台适配细节见 wireguard-windows 资料 SUP-01）。

还有一个常被忽略的维度是「审计面」。WireGuard 协议的代码量本身很小（内核驱动约 4800 行，含头文件），这让它成为少数可以被完整审计的 VPN 实现；相比之下，OpenVPN 依赖庞大的 OpenSSL，IPsec 涉及 xfrm、IKE 守护进程与多套协议协商，审计面大得多。实现形态与此直接相关：内核态实现把协议逻辑压缩到数据结构的直接操作上，用户态实现则往往携带更多运行框架。选型时若「可审计性」是硬指标（如高安全场景），这一点应与性能同等看待。

### 2. 核心概念

对比的底层逻辑是「协议自由度」与「实现代价」的权衡。WireGuard 协议把对称加密固定为 ChaCha20-Poly1305、把握手固定为 Noise_IK，这带来极简的实现与审计面，但也意味着所有合规实现必须逐字节兼容，兼容性测试是持续投入。IPsec 与 OpenVPN 的加密套件、握手方式都是可协商的，灵活但复杂。这直接决定了一个关键判断：如果目标是与标准 WireGuard 对端互通，实现就必须遵循 WireGuard 的消息格式与状态机；如果两端都是自有设备，才可能考虑自定义（但这已不是 WireGuard）。

需要厘清「互通」的准确含义。WireGuard Linux 与 wireguard-go、wireguard-nt、官方 App、OpenBSD 内核版之间可以互通，因为它们是同一协议的不同实现，共享 `messages.h` 定义的消息布局、Noise_IK 握手、抗重放窗口与 cookie 机制。但它与 IPsec ESP、OpenVPN 之间不存在协议级互通——那是完全不同的协议，需要网关做协议转换，而转换两端的安全上下文无法直接传递。把「都能加密上网」等同于「可以互通」是常见误解。

下表按实现形态给出五者的对比，结论以各实现的官方定位与本快照源码为依据。

| 维度 | WireGuard Linux | wireguard-go | wireguard-nt | IPsec（Linux xfrm） | OpenVPN |
|---|---|---|---|---|---|
| 实现形态 | 内核模块 | 用户态 Go 程序 | Windows 内核驱动 | 内核 xfrm + 用户态 IKE | 用户态程序 |
| 数据面位置 | 内核态 | 用户态 | 内核态 | 内核态 | 用户态 |
| 接口形态 | net_device | TUN | Wintun 适配器 | xfrm 策略 | TUN/TAP |
| 配置面 | netlink + wg | wg(8) + UAPI | 命令行/服务 | strongSwan 等 IKE | 配置文件 + 管理接口 |
| 对称加密 | ChaCha20-Poly1305（固定） | 同协议 | 同协议 | 多种 AEAD 可协商 | OpenSSL 多种 |
| 协议互通 | 标准 WireGuard | 标准 WireGuard | 标准 WireGuard | IPsec | OpenVPN |
| 跨平台 | Linux | 多平台（含 Linux） | Windows | 多平台 | 多平台 |
| 官方对 Linux 的建议 | 推荐 | 不优先推荐 | 不适用 | 独立生态 | 独立生态 |

### 3. 关键数据结构与源码位置

本篇的对比落点仍回到 WireGuard Linux 的源码结构，借此说明「内核态实现」具体体现在哪些数据结构上。与「net_device 形态」对应的是 `device.c` 中的 `wg_device`，它内嵌 `struct net_device`，并注册 `wg_open`、`wg_stop`、`wg_start_xmit` 等 netdev 操作（字段见 05-02）；这是它区别于用户态 TUN 实现的根本——用户态实现拿的是文件描述符，内核态实现拿的是 netdev 结构。与「内核态加解密」对应的是 `send.c`、`receive.c` 直接操作 `sk_buff`，并调用 `lib/crypto/` 的加密函数，全程无用户态拷贝（字段见 05-06、原理见 06-05、06-06）。与「netlink 配置」对应的是 `include/uapi/linux/wireguard.h` 的属性枚举与 `main.c` 的 `wg_genetlink_init()`（原理见 06-14）。

对照之下，wireguard-go 的用户态形态决定了它依赖 TUN 设备与 Go runtime，其数据结构围绕 `net.Conn`、TUN 设备抽象与 goroutine 调度组织；wireguard-nt 的内核态形态类似 Linux 版但绑定 Windows 网络栈（Wintun、NDIS）。这些对照只作定性说明，本套资料不展开非本项目的源码结构。

理解这层差异，对阅读本套资料有个实际好处：当你看到 `wg_device` 内嵌 `net_device`、并挂接 `ndo_start_xmit` 时，就能明白「为什么配置 WireGuard 要先 `ip link add`」——因为内核必须先有一个 netdev 对象，WireGuard 的数据面入口才存在；而用户态实现不需要这一步，它启动的就是一个进程。同理，当你看到 `send.c` 直接操作 `sk_buff` 时，就能理解「为什么 WireGuard Linux 没有独立的转发进程」——数据包在内核子系统之间流转，不需要任何用户态程序介入。把数据结构的形态和运行时的进程形态对应起来，是读懂内核态实现的关键思维。这也提示了一种排障思路：内核态实现的故障往往表现为 netdev 状态、路由、netlink 属性层面的异常，而不是进程崩溃；`wg show` 输出的每一行都直接对应内核里的一个属性，这正是下一节命令实例要展示的。

下表把五者按「数据面位置」归类，列出各项关注点的源码位置与本册处理方式。

|---|---|---|

| 内核态加解密 | `drivers/net/wireguard/send.c`、`receive.c` | 只点名，原理见 06-05、06-06 |
| netlink 配置面 | `include/uapi/linux/wireguard.h`、`main.c` | 只给枚举名，全集见 04-05 |

### 4. 关键流程与调用链

从调用链角度最能看清五者差异。WireGuard Linux 的出站路径是「内核路由 → wg0 的 ndo_start_xmit → send.c 封装加密 → UDP socket 发出」，全程在内核态同步完成，没有上下文切换（完整链路见 06-05）。wireguard-go 的出站路径是「TUN 读 → Go 程序封装加密 → UDP socket 发出」，每个包要跨内核/用户态边界两次。OpenVPN 类似但有 TLS 记录层开销。IPsec 的出站路径是「内核路由 → xfrm 策略匹配 → ESP 封装加密 → 物理网卡」，同样在内核态，但策略与 SA 由 IKE 守护进程异步维护。

配置链路差异同样显著。WireGuard Linux 用 `wg` 通过 netlink 直接读写内核状态（`WG_CMD_SET_DEVICE` / `WG_CMD_GET_DEVICE`），配置即时生效且无独立守护进程；wireguard-go 通过 UAPI socket 配置，需要一个常驻进程；IPsec 需要 IKE 守护进程协商 SA 并维护内核 xfrm 状态；OpenVPN 多用配置文件与控制通道。这也解释了为什么 WireGuard 常被评价为「配置极简」：它没有守护进程、没有协商协议、没有证书体系，配置就是几条 `wg set`。

### 5. 配置/命令/代码实例

本篇给出一条有代表性的对照命令：查看 WireGuard Linux 接口状态用 `wg show`，而查看 IPsec 状态用 `ip xfrm state` 或 `swanctl --list-sas`，两者的输出形态差异正好体现配置模型的区别。

```bash
# WireGuard Linux：直接读内核接口的 netlink 状态
wg show wg0
# IPsec：读内核 xfrm SA（需先在用户态由 IKE 建立）
ip xfrm state
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
# wg show wg0 的输出
interface: wg0
  public key: <公钥>
  listening port: 51820
peer: <对端公钥>
  latest handshake: 3 minutes ago
  transfer: 4.02 KiB received, 3.10 KiB sent

# ip xfrm state 的输出
src 198.51.100.1 dst 198.51.100.2
  proto esp spi 0x0a1b2c3d reqid 1 mode tunnel
  auth-trunc hmac(sha256) <key> 96
  enc aes-gcm <key> 16
  replay-window 32
```

逐行判读如下。第一组是 `wg show wg0`：`interface` 与 `public key`、`listening port` 三行来自 `WG_CMD_GET_DEVICE` 返回的 device 属性，描述接口自身；`peer` 段来自 `WGPEER_A_*` 属性。`latest handshake` 是判断 WireGuard 隧道可用性的核心，WireGuard 是静默协议，认证失败只丢包不回错误，所以这一行是排障第一入口（排障见 08-03）。`transfer` 是累计收发字节，对应 `WGPEER_A_RX_BYTES` / `WGPEER_A_TX_BYTES`。第二组是 `ip xfrm state`：一条 SA 由 `src`/`dst`、`proto esp`、`spi`、`reqid`、`mode` 描述，`auth-trunc` 与 `enc` 给出认证与加密算法及密钥，`replay-window` 是抗重放窗口。对比可见，IPsec 的 SA 是由 IKE 协商出来的一组带生命周期的安全关联，需要守护进程维护；而 WireGuard 的 peer 状态是静态配置加握手演进的会话密钥，没有独立的 SA 协商层。这正是「配置极简」的具体含义——少了一整套 IKE 协商与 SA 生命周期管理。清理环节：WireGuard 用 `ip link del wg0` 删除接口即释放全部状态；IPsec 需 `ip xfrm state flush` 或停止 IKE 守护进程，步骤更多。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是把「协议相同」等同于「实现可互换」。五种实现共享 WireGuard 协议时可以互通，但 wireguard-go 的用户态实现与 WireGuard Linux 的内核实现在性能、部署形态、依赖上完全不同，不能因为协议一样就假设性能一样。第二个陷阱是把 wireguard-nt 的特性套到 Linux：wireguard-nt 是 Windows 驱动，其 Wintun 适配器、服务模型与 Linux 的 net_device、netlink 无关。

第三个陷阱是拿不同实现的绝对性能数字横比。加密是否走内核、是否有硬件加速、包长与 CPU 特性都会影响结果，脱离测试条件谈「A 比 B 快」没有意义；本套资料一律标注「需在目标机型实测」（基准方法见 08-01）。第四个陷阱是把互通范围夸大：WireGuard 与 IPsec、OpenVPN 不互通，需要网关转换且安全上下文无法透传。第五个陷阱是忽略许可差异：WireGuard Linux 是 GPLv2（`main.c` 的 `MODULE_LICENSE("GPL v2")`），wireguard-go 是 MIT，闭源商用时需分别评估（许可见 01-04）。

最佳实践：选型先问「对端是谁」——标准 WireGuard 对端就选 WireGuard Linux（Linux）或对应平台实现，需与 IPsec/OpenVPN 生态互通则考虑网关或改用对应协议；再问「数据面位置是否受限」——能加载内核模块就用内核态实现拿性能，受限环境才退回 wireguard-go；最后问「是否需要控制面」——内核模块只解决数据面，用户管理与密钥分发需另配（控制面选型见 wireguard-windows 资料 DESIGN-07）。这三个问题的顺序不能颠倒：先定互通范围，因为协议不兼容是硬约束，无法通过调优绕开；再定数据面形态，因为它决定性能上限与部署条件；最后才谈控制面，因为它是可叠加的上层能力，不影响底层协议选择。把顺序搞反，常见后果是先用 wireguard-go 跑通了功能、再发现性能不够，却已经把架构绑死在用户态，回头换成内核实现要重做整套部署与配置链路。

### 7. 小结与延伸阅读

本篇按实现形态把 WireGuard Linux 与 wireguard-go、wireguard-nt、IPsec、OpenVPN 做了对比：WireGuard Linux 的内核态 net_device 形态带来无用户态拷贝的数据面与极简的 netlink 配置面；wireguard-go 是用户态实现，官方在 Linux 上不优先推荐；wireguard-nt 面向 Windows；IPsec 与 OpenVPN 是不同协议，不与 WireGuard 互通。判断选型的核心是「实现形态决定性能与复杂度」，而非协议名称。

延伸阅读：协议与实现的关系见 wireguard-windows 资料 SUP-01；性能取舍见该资料 SUP-03；本册后续两篇分别处理架构（01-03）与版本许可生态（01-04）。跨册随查按（字段见 05-01 ｜ 参数见 04-01 ｜ 原理见 06-01 ｜ 模块见 07-01）执行。凡需具体字段、常量与函数签名的细节，均以 `_wglinux_build/upstream_src/` 下对应文件为准，本套资料不编造未核验的路径与取值。

## 01-03 WireGuard Linux 整体架构：内核模块、netlink 配置面与 wg 工具的分工

### 1. 背景与动机

读懂一套系统，先要划清它的边界与层次。WireGuard Linux 常被笼统地称为「一个 VPN」，但从源码看，它其实是三套彼此协作、又各自独立的部件拼起来的：运行在内核态、承担加解密与包转发的**内核模块**；作为内核与用户态之间契约的 **netlink 通用族配置面**；以及运行在用户态、被人直接敲命令的 **wg 工具**。把这三层的职责混在一起，是初读上游代码时最常见的困惑来源——比如有人满世界找一个叫「wireguard 进程」的东西，却怎么也找不到，因为数据面根本没有进程；也有人以为 `wg set` 直接改了某个配置文件，实际上它只是把 netlink 属性序列化后发给了内核。本篇的任务就是把这三层拆开，说明每层做什么、不做什么、层与层之间靠什么接口通信，并用真实源码位置佐证每一个结论。

为什么这个拆解对后续阅读如此重要？因为本套资料后面十几册，本质上都是在这三层里往下钻。02 册讲怎么把内核模块和工具编译出来；03 册讲怎么把工具的配置落到一次隧道建立；04 册把工具命令与 netlink 属性的参数全集列成手册；05 册逐字段拆内核结构；06 册把调用链展开；07 册按目录讲每个模块文件的职责；08 册讲运维与排障。如果不在开篇建立一个准确的三层心智模型，读到「`wg genetlink init`」「`WG_CMD SET DEVICE`」「`ndo start xmit`」这些名字时就会失去坐标。本篇正是提供这个坐标的一篇。

先明确事实锚点与取数纪律。本篇所有关于函数、字段、常量、命令的结论，均来自本快照源码：`_wglinux_build/upstream_src/wireguard-linux-src/`（内核驱动快照）与 `_wglinux_build/upstream_src/wireguard-tools/`（工具快照），下文路径相对这两个根目录。需要特别说明一处快照特征：驱动 Makefile 中列出了 `netlink.o`、`generated/netlink.o` 与 `peerlookup.o` 等目标，`main.c` 也 `#include "netlink.h"` 并调用 `wg_genetlink_init()`，但本快照的 `drivers/net/wireguard/` 目录并未包含 `netlink.c`、`peerlookup.c` 以及 `device.h`、`peer.h`、`netlink.h` 这几个头文件。这与 uapi 头 `include/uapi/linux/wireguard.h` 顶部「auto-generated from Documentation/netlink/specs/wireguard.yaml」的注释相互印证，说明该快照对应的是 netlink 定义已纳入 YAML 规范、内核侧 netlink 粘合层部分生成化的版本形态。因此，凡涉及内核 netlink 回调的具体函数体，本篇只描述其在初始化序列中的位置与对外契约，不臆造文件内细节，并统一标注「需对照实际版本核验」。这种克制不是回避，而是本套资料「基于真实源码、不编造路径与取值」纪律的直接体现。

### 2. 核心概念

三层分工可以浓缩成一句话：**内核模块管数据，netlink 管契约，wg 管人**。下面把它们逐一拆开。

第一层是内核模块。它的载体是一个标准的 `net_device`，接口名通常是 `wg0`。`device.c` 的 `wg_setup` 把这个网卡的操作表设成 `wg_open`、`wg_stop`、`wg_xmit` 三项（`netdev_ops` 只挂了这三项），并把它标记为 `ARPHRD_NONE`、`IFF_POINTOPOINT | IFF_NOARP`，关闭 ARP、不需要硬件地址。内核协议栈按路由把出站包交给 `ndo_start_xmit`（这里对应 `wg_xmit`），WireGuard 就在内核里完成查路由、封装、加密、UDP 发出；入站则由 UDP socket 收包、验重放、解密、校验源地址后重新注入协议栈。整个过程没有用户态进程参与，也没有内核与用户态之间的数据拷贝。这是「内核态数据面」的准确含义。

第二层是 netlink 通用族配置面。它是内核与用户态之间的一组**约定**，由 uapi 头 `include/uapi/linux/wireguard.h` 定义：族名 `WG_GENL_NAME` 为 `"wireguard"`，版本 `WG_GENL_VERSION` 为 `1`，命令只有两条——`WG_CMD_GET_DEVICE`（读）与 `WG_CMD_SET_DEVICE`（写），属性分 `wgdevice_attribute`、`wgpeer_attribute`、`wgallowedip_attribute` 三层。注意 uapi 头本身只是「契约文本」，它不执行任何逻辑；真正的内核侧解析与响应由 netlink 粘合层完成（在本快照中其实现文件未随快照提供，需对照实际版本核验，机制详见 06-14）。契约的稳定性远大于实现：只要属性枚举与命令号不变，内核内部怎么改写都不影响工具互通。

第三层是 wg 工具，即 `wireguard-tools` 编译出的 `wg` 与 `wg-quick`。`wg.c` 的子命令表清晰地列出了它对外提供的能力：`show`、`showconf`、`set`、`setconf`、`addconf`、`syncconf`、`genkey`、`genpsk`、`pubkey`。`wg` 是**一次性命令**，跑完就退出，没有常驻守护进程；它把人类可读的配置解析成内核能懂的属性，通过 netlink 发出去，或从内核读回状态渲染成人可读文本。工具侧的 netlink 实现位于 `wireguard-tools/src/ipc-linux.h`，它用 libmnl 构造与解析 netlink 消息；这是「用户态控制面」的全部。

理解这三层，还要抓住两条「自动加载路径」。内核模块声明里有两个别名：`MODULE_ALIAS_RTNL_LINK(KBUILD_MODNAME)` 与 `MODULE_ALIAS_GENL_FAMILY(WG_GENL_NAME)`。前者让 `ip link add wg0 type wireguard` 能通过 rtnetlink 自动加载本模块（因为 `link_ops.kind` 就是 `KBUILD_MODNAME`）；后者让工具打开 `wireguard` 通用族时能按需触发模块加载。也就是说，用户即使没手动 `modprobe`，两条路径中的任意一条都会把模块带起来。这是「分工」在加载环节的具体体现：rtnetlink 负责「建网卡」，genetlink 负责「配置它」，二者缺一不可。

### 3. 关键数据结构与源码位置

作为架构篇，本节只点名每层的关键结构与真实源码路径，逐字段定义统一交给 05 册，不在这里展开字段表。需要建立的结构地图分四层。

**模块入口层**，以 `drivers/net/wireguard/main.c` 为代表。它本身不定义复杂结构，而是整个模块的生命周期网关：`wg_mod_init` 与 `wg_mod_exit` 在这里编排各层的初始化与回收，模块身份也在这里用 `MODULE_LICENSE`、`MODULE_VERSION`、`MODULE_ALIAS_*` 等宏声明。模块能力清单交给 07-01。

**设备与状态层**，以 `device.c`、`socket.c`、`peer.c`、`allowedips.c` 为代表，核心结构是 `wg_device` 与 `wg_peer`。`wg_device` 内嵌 `net_device`，把私钥、监听端口、peer 链表、allowedips trie、socket、工作队列与锁组织在一起（字段见 05-02）；`wg_peer` 持有公钥、endpoint、握手状态、计数器与发送队列（字段见 05-03）。`socket.c` 围绕 UDP socket 与 `endpoint` 组织收发（字段见 05-07），`allowedips.c` 实现 v4/v6 混合 trie（字段见 05-04）。本册只点名，不展开。

**netlink 契约层**，以 uapi 头 `include/uapi/linux/wireguard.h` 和内核 netlink 粘合层为代表。头里定义三层属性枚举、三组标志位与两条命令；完整常量与标志交给 04-05、04-06，uapi 配置结构字段交给 05-09。内核侧粘合层（Makefile 中的 `netlink.o`/`generated/netlink.o`）在本快照未含源码，其初始化入口 `wg_genetlink_init()` 仅能从 `main.c` 的调用顺序确认，细节需对照实际版本核验。

**用户态工具层**，以 `wireguard-tools/src/` 为代表：`wg.c` 是命令入口，`config.c` 解析 ini 配置，`encoding.c` 做 base64 与密钥编解码，`curve25519.c` 做密钥运算，`ipc.c` 与 `ipc-linux.h` 是 IPC 抽象及其 Linux netlink 实现，另有 `set.c`、`show.c`、`setconf.c` 等子命令文件与 `wg-quick` 脚本。工具各模块的职责交给 07-13，命令参数全集交给 04-01。

### 4. 关键流程与调用链

最先要看清的是内核模块的**分层初始化链**。`main.c` 的 `wg_mod_init` 顺序非常清晰：先调 `wg_allowedips_slab_init()` 为 trie 节点准备 slab 缓存；随后在 `DEBUG` 编译下运行 `wg_allowedips_selftest()`、`wg_packet_counter_selftest()`、`wg_ratelimiter_selftest()` 三项自检，任一失败就把返回值设为 `-ENOTRECOVERABLE` 并跳到错误标签；接着 `wg_noise_init()` 初始化握手引擎，`wg_peer_init()` 初始化对等体层，`wg_device_init()` 注册设备层，`wg_genetlink_init()` 最后注册 netlink 族；全部成功后才用两行 `pr_info` 打印加载信息。这个顺序体现的是依赖关系：allowedips 与 noise 是基础，peer 依赖它们，device 又依赖 peer，netlink 最后注册以便用户态能开始配置。卸载函数 `wg_mod_exit` 严格逆序回收：`wg_genetlink_uninit()`、`wg_device_uninit()`、`wg_peer_uninit()`、`wg_allowedips_slab_uninit()`。初始化中任何一层失败，都通过 `goto err_netlink`、`err_device`、`err_peer`、`err_allowedips` 等标签回滚已完成的层。这是内核模块的标准写法，也是「分层」二字最字面的体现（完整启动链见 06-01）。

第二要看清 `wg_device_init()` 内部做了什么。`device.c` 里它依次调用 `register_pm_notifier`、`register_random_vmfork_notifier`、`register_pernet_device`、`rtnl_link_register(&link_ops)`，每一步失败都回滚前一步。`link_ops` 的 `.kind` 是 `KBUILD_MODNAME`、`.priv_size` 是 `sizeof(struct wg_device)`、`.setup` 指向 `wg_setup`、`.newlink` 指向 `wg_newlink`。这解释了「为什么 `ip link add` 能建出 wg0」：rtnetlink 按 kind 找到这份 `link_ops`，先调 `wg_setup` 设定 netdev 的固定属性，再调 `wg_newlink` 做真正初始化。后者分配 peer 与 index 两张哈希表，创建 `wg-kex-%s`（握手收/发）与 `wg-crypt-%s`（加解密）三类工作队列，初始化 encrypt、decrypt、handshake 三个包队列与 ratelimiter，最后 `register_netdevice` 把网卡登记进内核。这些队列与工作队列是把加密从软中断上下文卸载到工作线程的机制基础（原理见 06-13）。

第三是**配置链**。工具侧 `ipc-linux.h` 的 `kernel_set_device` 先用 `mnlg_socket_open(WG_GENL_NAME, WG_GENL_VERSION)` 打开到 wireguard 族的 netlink 套接字，再用 `mnlg_msg_prepare(nlg, WG_CMD_SET_DEVICE, ...)` 准备一条 SET 消息，把 `WGDEVICE_A_IFNAME`、`WGDEVICE_A_PRIVATE_KEY`、`WGDEVICE_A_LISTEN_PORT`、`WGDEVICE_A_FWMARK` 等属性依次放入，随后嵌套 `WGDEVICE_A_PEERS`，每个 peer 再嵌套 `WGPEER_A_ALLOWEDIPS`；若消息过大则通过 `toobig_peers`、`toobig_allowedips` 标签分批发送。读方向的 `kernel_get_device` 则发 `WG_CMD_GET_DEVICE`，用 `read_device_cb` 一路 `parse_device`→`parse_peers`→`parse_peer`→`parse_allowedips` 把内核回包还原成本地结构，再用 `coalesce_peers` 合并同一公钥的 peer 段。此外 `kernel_get_wireguard_interfaces` 走的是另一条 netlink 路由：`NETLINK_ROUTE` 上的 `RTM_GETLINK` 请求，用 `IFLA_INFO_KIND` 等于 `WG_GENL_NAME` 过滤出所有 wireguard 接口。可见工具同时用到了 rtnetlink（枚举与建链）与 genetlink（读写配置）两套 netlink 通道。

第四是**数据链**。出站：`wg_xmit` 先做协议检查，再用 `wg_allowedips_lookup_dst` 按目的地址找到 peer，检查 endpoint 家族，处理 GSO 分段，把包挂入 `peer->staged_packet_queue`，最后 `wg_packet_send_staged_packets` 进入 `send.c`；`socket.c` 的 `send4`/`send6` 构造 `flowi4`/`flowi6`，`flowi4_proto` 为 `IPPROTO_UDP`、`flowi4_mark` 取 `wg->fwmark`，经 `udp_tunnel_xmit_skb` 从物理网卡发出。入站：`wg_socket_init` 建立 UDP socket 时用 `udp_tunnel_sock_cfg` 把 `.encap_rcv` 设为 `wg_receive`，后者拿到包就调 `wg_packet_receive` 进入 `receive.c`。三条链路的逐段实现分别在 06-05、06-06、06-14，本节只给骨架。

图中节点速览（便于在不渲染框内文字的预览器中阅读）：「用户与 wg 工具 一次性命令」把配置序列化为「netlink 契约 GET/SET 属性」，经 genetlink 到「内核 netlink 粘合 解析并更新状态」，落到「wg_device 状态 peer 与 allowedips」；另一路「rtnetlink ip link add wg0」直接建出这份状态。数据到来后由「wg_xmit 数据面 查 trie 选 peer」经「UDP socket 封装加密发出」，收包再由回调回到内核处理链。

### 5. 配置/命令/代码实例

下面用一组命令把三层同时「照出来」：既有工具层的版本与状态，也有内核层的模块身份与加载日志。完整参数交给 04 册，这里只取能说明分工的最小集。

```bash
# 第三层：用户态工具身份
wg --version

# 第二层：内核模块身份（版本、许可、别名、描述）
modinfo wireguard | grep -E '^(version|license|alias|description|author):'

# 第一层是否真的在内核里跑
lsmod | grep wireguard
dmesg | grep -i 'wireguard: WireGuard'

# 配置面的一次读操作：wg 通过 netlink GET 拉状态
wg show wg0
```

为了对照内核侧的层次，这里节选 `main.c` 的初始化骨架（保留原控制流，略去自检细节）：

```c
static int __init wg_mod_init(void)
{
	int ret = wg_allowedips_slab_init();
	if (ret < 0) goto err_allowedips;
	wg_noise_init();
	ret = wg_peer_init();     if (ret < 0) goto err_peer;
	ret = wg_device_init();   if (ret < 0) goto err_device;
	ret = wg_genetlink_init(); if (ret < 0) goto err_netlink;
	pr_info("WireGuard " WIREGUARD_VERSION " loaded.\n");
	return 0;
err_netlink: wg_device_uninit();
err_device:  wg_peer_uninit();
err_peer:    wg_allowedips_slab_uninit();
err_allowedips: return ret;
}
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
wireguard-tools v1.0.20260223 - https://git.zx2c4.com/wireguard-tools/
version:        1.0.0
license:        GPL v2
description:    WireGuard secure network tunnel
author:         Jason A. Donenfeld <Jason@zx2c4.com>
alias:          rtnl-link-wireguard
alias:          net-pf-16-proto-16-family-wireguard
wireguard              20480  0
wireguard: WireGuard 1.0.0 loaded. See www.wireguard.com for information.
interface: wg0
  public key: <本端公钥>
  private key: (hidden)
  listening port: 51820
peer: <对端公钥>
  endpoint: 203.0.113.9:51820
  allowed ips: 10.0.0.2/32
  latest handshake: 25 seconds ago
  transfer: 2.10 KiB received, 1.44 KiB sent
```

逐行判读如下。`wireguard-tools v1.0.20260223` 来自 `wg.c` 对 `WIREGUARD_TOOLS_VERSION` 的 `printf`，这是**第三层**工具的版本，与内核无关。`version: 1.0.0` 来自模块 `MODULE_VERSION(WIREGUARD_VERSION)`，而 `WIREGUARD_VERSION` 在 `drivers/net/wireguard/version.h` 定义为 `"1.0.0"`，这是**第一层**内核驱动的版本；两者独立，不可混谈（版本基准见 01-04）。`license: GPL v2` 对应 `main.c` 的 `MODULE_LICENSE("GPL v2")`，与每个源文件顶部的 `SPDX-License-Identifier: GPL-2.0` 一致（许可细节见 01-04）。`description` 与 `author` 分别对应 `MODULE_DESCRIPTION` 与 `MODULE_AUTHOR`。两条 `alias` 正是 `MODULE_ALIAS_RTNL_LINK` 与 `MODULE_ALIAS_GENL_FAMILY` 展开的结果，分别对应 rtnetlink 建链与 genetlink 配置两条自动加载路径——这是三层分工在模块元数据上的直接烙印。`wireguard 20480 0` 是 `lsmod` 输出，第三列引用计数为 0 说明没有其它模块依赖它，但模块确实已加载（数据面在内核，所以不会有「进程」出现在 `ps` 里）。那行 `wireguard: WireGuard 1.0.0 loaded` 来自 `wg_mod_init` 末尾的 `pr_info`，前缀 `wireguard:` 是 Makefile 里 `pr_fmt` 用 `KBUILD_MODNAME` 拼出来的，看到它就说明分层初始化全部成功走到了最后一步。最后 `wg show wg0` 的每一段则是**第二层**契约的渲染：`public key`/`private key`/`listening port` 来自 device 属性，`peer` 段来自 peer 属性，`allowed ips` 来自 allowedip 属性，`latest handshake` 与 `transfer` 分别来自 `WGPEER_A_LAST_HANDSHAKE_TIME`、`WGPEER_A_RX_BYTES`/`WGPEER_A_TX_BYTES`（字段见 05-03）。三行输出恰好把「工具—契约—内核」三层串成了一次可读的往返。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是把三层当成一层。典型表现是到用户态去找数据面进程，或在内核里找配置解析逻辑——两者都不存在。正确的心智是：转发与加解密只在内核模块里，`wg` 命令跑完即退出，netlink 只是两者之间的消息约定。任何把「工具配置」直接等同于「改文件」的说法都是错的：wg-quick 才会写 `wg0.conf`，而 `wg set` 走的是 netlink。

第二个陷阱是因快照缺文件而误判架构。本快照的 `drivers/net/wireguard/` 没有 `netlink.c`/`peerlookup.c` 与若干头文件，但 Makefile 明确引用了它们。这不是「内核不做 netlink」，而是本快照的生成化/裁剪形态所致。遇到引用了却找不到的文件，应标注「需对照实际版本核验」并转向权威册，而不是据此断言功能缺失。

第三个陷阱是把三个版本号混为一谈：`version.h` 的 `1.0.0` 是内核驱动版本，`WIREGUARD_TOOLS_VERSION` 的 `1.0.20260223` 是工具版本，`uname -r` 给出的又是第三个数（目标内核版本）。三者独立演进（版本基准见 01-04）。第四个陷阱是夸大 `wg` 的能力：它不含守护进程、不做密钥自动分发、不下发地址，这些都要靠上层控制面；命令全集见 04-01，配置体系见 03 册。

最佳实践可以归纳为四步排错顺序：**先看内核层**——用 `lsmod` 与 `dmesg` 确认模块已加载、分层初始化成功（构建见 02-03）；**再看建链**——用 `ip link show wg0` 确认 rtnetlink 路径通畅、网卡存在；**然后看配置面**——用 `wg show` 的 `latest handshake` 判断 netlink 写入是否生效、握手是否真的完成（排障见 08-03）；**最后才看数据面**——用 `transfer` 字节与路由表确认流量确实经过 wg0（路由见 03-04）。这个顺序不能颠倒，因为下层没起来时上层的现象具有迷惑性：模块没加载时 `wg set` 会报「No such device」，而路由没配好时握手成功但字节数为零，两种故障的定位方向完全不同。

### 7. 小结与延伸阅读

本篇把 WireGuard Linux 拆成三层：**内核模块**以 `net_device` 形态承载数据面，`wg_mod_init` 按 allowedips→noise→peer→device→netlink 的顺序分层初始化、`wg_mod_exit` 逆序回收；**netlink 配置面**以 uapi 头定义的 `WG_CMD_GET_DEVICE`/`WG_CMD_SET_DEVICE` 与 device/peer/allowedip 三层属性作为内核与用户态的稳定契约；**wg 工具**以一次性命令把人读配置翻译成 netlink 属性，无守护进程。两条模块别名 `MODULE_ALIAS_RTNL_LINK` 与 `MODULE_ALIAS_GENL_FAMILY` 分别对应「建网卡」与「配置网卡」两条自动加载路径，是三层分工在加载环节的具体体现。

延伸阅读建议按三条线走：想看模块入口与每一层的内部实现，读 `main.c` 并按 07-01、07-02、07-09、07-11 逐模块展开；想看 netlink 消息如何被解析与响应，读 06-14 与 04-05、04-06；想看工具如何把配置序列化，读 07-13 与 04-01。跨册随查按（字段见 05-02 ｜ 参数见 04-01 ｜ 原理见 06-14 ｜ 模块见 07-01）执行：结构体的逐字段定义去 05，命令与属性全集去 04，机制与调用链去 06，目录级模块职责去 07，运维与排障去 08。凡本篇标注「需对照实际版本核验」的 netlink 粘合层细节，均以 `_wglinux_build/upstream_src/` 下对应文件与实际内核版本为准，本套资料不编造未核验的路径与取值。

## 01-04 版本基准、源码地图、许可与资料使用约定

### 1. 背景与动机

一套基于源码的技术资料，必须先交代清楚「你读的是哪一份源码、按什么版本口径、依据什么纪律写成」，否则再详细的结论都可能因版本漂移而失效。这正是本篇的使命：它不深入任何一条调用链，也不展开任何一张字段表，而是为本套资料立四根柱子——**版本基准、源码地图、许可、使用约定**。看起来是「元信息」，实际决定了后面每一册的可信度。

先看为什么版本基准如此要紧。WireGuard Linux 至少同时存在三个互不相同的版本号，且各自独立演进：内核驱动自己的 `WIREGUARD_VERSION`，用户态工具的 `WIREGUARD_TOOLS_VERSION`，以及运行环境的 Linux 内核版本。把它们混为一谈，会直接导致排障方向错误——比如有人看到 `modinfo` 显示 `1.0.0`、而 `wg --version` 显示 `1.0.20260223`，就认定两者不配套、必须降级工具；实际上这是两个项目的独立版本，本来就该不同。反过来，若一台机器装的是发行版回移植的旧内核，即便工具是新版，某些 uapi 属性也可能不被内核识别。因此本套资料统一声明：事实锚点是 `_wglinux_build/upstream_src/wireguard-linux-src/`（内核驱动快照）与 `_wglinux_build/upstream_src/wireguard-tools/`（工具快照），二者版本分别为下述的具体值；凡落到目标机器，一律要求对照该机实际内核与工具版本核验。

再看源码地图的必要性。内核驱动、加密原语、uapi 头、用户态工具分散在两棵目录树里，且像 netlink 定义这样的部分已经从手写 C 迁移到 YAML 规范生成。若不在开篇给出一张「哪个目录放什么、哪个文件管什么」的地图，读者很容易在 `drivers/net/wireguard/` 里翻半天找不到 `netlink.c`，或误以为 `include/uapi/linux/wireguard.h` 是手写的、可以随意改。地图的作用就是把「找得到」变成「一开始就找对地方」。

最后是许可与资料纪律。WireGuard 内核驱动与用户态工具采用不同的许可组合，uapi 头又是一套双许可声明；闭源集成、再分发、内核 upstreaming 时，这些差异都会变成合规问题。而资料使用约定——尤其是「不编造路径与取值」「拿不准就标注核验」「非权威册用交叉引用让出细节」——是本套十几册能保持一致、不互相矛盾、不与权威册重复的根本保证。本篇把这三条规矩讲透，后面所有篇章都受它约束。

### 2. 核心概念

本篇的四个关键词对应四组核心概念，逐一厘清。

**版本基准**不是一个数，而是一组三元组：`drivers/net/wireguard/version.h` 定义的 `WIREGUARD_VERSION "1.0.0"`；`wireguard-tools/src/version.h` 定义的 `WIREGUARD_TOOLS_VERSION "1.0.20260223"`；以及目标系统的内核版本（由 `uname -r` 给出，本套资料不预设）。第一个值经 `MODULE_VERSION(WIREGUARD_VERSION)` 暴露给 `modinfo`，并在 `wg_mod_init` 里被 `pr_info` 打印；第二个值经 `wg.c` 的 `printf` 暴露给 `wg --version`。重要认识：这两个版本号分属两个 Git 项目，没有同步关系，出现差异是常态而非故障（版本基准与核验见 08-01）。

**源码地图**是按「职责域」划分的四块。内核驱动域是 `drivers/net/wireguard/`，负责 netdev、握手、收发、定时器、路由 trie、限速与 cookie；加密原语域位于内核树 `lib/crypto/`（本快照置于 `wireguard-linux-src/lib/crypto/`），提供 ChaCha20、Poly1305、Curve25519、BLAKE2s、SipHash 等实现；uapi 契约域是 `include/uapi/linux/wireguard.h`，由 YAML 规范生成；用户态工具域是 `wireguard-tools/src/`，提供 wg 与 wg-quick。四块通过 netlink 与 uapi 头连成一体。逐目录、逐文件的职责清单是 07 册的权威内容，本篇只给坐标，不抢其展开（模块见 07-01、07-12、07-13）。

**许可**在本项目里是分层的。内核驱动每个源文件的 `SPDX-License-Identifier` 是 `GPL-2.0`，模块整体又以 `MODULE_LICENSE("GPL v2")` 对外声明；uapi 头是 `((GPL-2.0 WITH Linux-syscall-note) OR BSD-3-Clause)` 的双许可；而 `wireguard-tools/src/` 下多数 C 文件是 `GPL-2.0 OR MIT`，其中 `ipc-linux.h` 单独标为 `MIT`。这组差异的实务含义是：把内核驱动当作 GPLv2 代码对待，把工具按其双许可条款对待，uapi 头因带 syscall-note 例外可安全地用于用户态头文件包含。需要注意的是，不同实现的许可各自独立（例如 wireguard-go 采用 MIT），跨实现复用代码时要分别评估。

**使用约定**是一套可执行的写作纪律，可概括为四条：事实来源唯一权威（只认本快照源码，不凭记忆写路径与取值）；不确定即标注（拿不准的统一写「需对照实际版本核验」）；权威册去重（04 管参数、05 管字段、06 管原理、07 管模块、08 管运维基准，其他册只给最小片段并交叉引用）；口径克制（不写绝对性能数字，一律「需在目标机型实测」）。四条里最容易违反的是第三条——看到字段就想顺手解释清楚，结果把 05 册的内容抄了一遍。本篇与 01-03 都严格克制，只点名、不给字段表。

### 4. 关键流程与调用链

作为「元信息」篇，这里的「流程」指版本号与许可信息从源码走向用户所见输出的**溯源链**，共三条。

第一条是内核驱动版本链。`version.h` 里的一行 `#define WIREGUARD_VERSION "1.0.0"` 是源头；`main.c` 通过 `#include "version.h"` 引入它，一方面用 `MODULE_VERSION(WIREGUARD_VERSION)` 把它写进模块元数据，另一方面在 `wg_mod_init` 末尾用 `pr_info("WireGuard " WIREGUARD_VERSION " loaded...")` 把它拼进加载日志；用户端分别用 `modinfo wireguard` 与 `dmesg` 看到这两个出口。链条上任何一环的版本差异都指向「源头不同」，而非「源码不一致」。

第二条是工具版本链。`wireguard-tools/src/version.h` 的 `#define WIREGUARD_TOOLS_VERSION "1.0.20260223"` 是源头；`wg.c` 包含该头后，在 `main` 里判断参数 `-v`/`--version`/`version`，命中就 `printf("wireguard-tools v%s - ...", WIREGUARD_TOOLS_VERSION)`。用户敲 `wg --version` 看到的就是这条链的终点。它与第一条链没有任何共享节点，这就是「两个版本号不必相等」的原因。

第三条是许可与契约的生成链。许可信息从每个文件的 `SPDX-License-Identifier` 注释出发，内核侧再经 `MODULE_LICENSE("GPL v2")` 汇总为模块级声明，最终由 `modinfo` 的 `license` 字段呈现；而 uapi 头则从 `Documentation/netlink/specs/wireguard.yaml` 出发，经 `tools/net/ynl/ynl-regen.sh` 生成，同时产出 `include/uapi/linux/wireguard.h` 与内核侧的 `generated/netlink.o` 相关代码。这也解释了 01-03 里那个悬案：netlink 粘合层之所以「在 Makefile 里、不在源码目录里」，是因为它由规范生成，而非手写。

三条溯源链见图 01-04-01。

### 5. 配置/命令/代码实例

下面这组命令用来「现场核验」本篇所有元信息。它们是核验动作，不是配置动作；参数全集见 04 册。

```bash
# 版本三元组：目标内核 + 驱动 + 工具
uname -r
cat drivers/net/wireguard/version.h
cat wireguard-tools/src/version.h
wg --version
modinfo wireguard | grep -E '^(version|license):'

# 许可：源码 SPDX 头与模块声明
grep -m1 SPDX drivers/net/wireguard/main.c
grep -m1 SPDX wireguard-tools/src/ipc-linux.h
grep 'MODULE_LICENSE' drivers/net/wireguard/main.c

# uapi 头的生成来源
head -5 include/uapi/linux/wireguard.h
```

三条溯源链的源码最小片段如下（保留原字面值）：

```c
/* drivers/net/wireguard/version.h */
#define WIREGUARD_VERSION "1.0.0"

/* wireguard-tools/src/version.h */
#define WIREGUARD_TOOLS_VERSION "1.0.20260223"

/* drivers/net/wireguard/main.c */
MODULE_LICENSE("GPL v2");
MODULE_VERSION(WIREGUARD_VERSION);

/* include/uapi/linux/wireguard.h 首行 */
/* SPDX-License-Identifier: ((GPL-2.0 WITH Linux-syscall-note) OR BSD-3-Clause) */
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
6.12.0-generic
#define WIREGUARD_VERSION "1.0.0"
#define WIREGUARD_TOOLS_VERSION "1.0.20260223"
wireguard-tools v1.0.20260223 - https://git.zx2c4.com/wireguard-tools/
version:        1.0.0
license:        GPL v2
// SPDX-License-Identifier: GPL-2.0
// SPDX-License-Identifier: MIT
MODULE_LICENSE("GPL v2");
/* SPDX-License-Identifier: ((GPL-2.0 WITH Linux-syscall-note) OR BSD-3-Clause) */
/* Do not edit directly, auto-generated from: */
/*	Documentation/netlink/specs/wireguard.yaml */
```

逐行判读如下。第一行 `6.12.0-generic` 来自 `uname -r`，是**目标系统内核版本**，与驱动、工具版本都不同，它是判断「快照是否适用于当前机器」的基准（性能基准方法见 08-01，注意那是性能基准，与版本基准不同）。第二行 `WIREGUARD_VERSION "1.0.0"` 出自驱动 `version.h`，是内核驱动版本源头；第三行 `WIREGUARD_TOOLS_VERSION "1.0.20260223"` 出自工具 `version.h`，是工具版本源头，两者并列出现恰好证明它们独立。第四行 `wireguard-tools v1.0.20260223` 是 `wg.c` 中 `printf` 加上 `WIREGUARD_TOOLS_VERSION` 的输出，说明工具链的终点与源头一致。第五、六行 `version: 1.0.0`、`license: GPL v2` 来自 `modinfo`，分别对应 `MODULE_VERSION` 与 `MODULE_LICENSE` 两个宏——注意 `modinfo` 显示的许可字符串是 `GPL v2` 而不是 SPDX 的 `GPL-2.0`，这是因为内核模块元数据用的是后者映射后的传统写法，二者语义一致、格式不同，不可当成两个许可。第七行驱动的 `SPDX-License-Identifier: GPL-2.0` 说明内核侧每个源文件按 SPDX 标注；第八行 `ipc-linux.h` 的 `SPDX-License-Identifier: MIT` 说明工具侧这个文件单独采用 MIT，与多数 `GPL-2.0 OR MIT` 的工具文件又不相同，复用代码时必须逐文件看 SPDX，不能按目录一概而论（许可见本节第 2 点）。第九行再次印证模块级 `MODULE_LICENSE("GPL v2")`。最后三行 `Do not edit directly`、`wireguard.yaml`、`auto-generated` 提醒读者：uapi 头是生成物，任何手写修改都会在下次 `ynl-regen.sh` 时被覆盖，要改命令与属性必须先改 YAML 规范（命令全集见 04-05）。这一组输出从版本到许可再到生成来源，把本篇四根柱子各核验了一遍。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是把三个版本号混为一谈。再强调一次：`1.0.0` 是驱动版本，`1.0.20260223` 是工具版本，`uname -r` 是内核版本，三者不必相等、也不应相等。看到差异先确认各自来源，不要贸然「对齐版本」。第二个陷阱是把 uapi 头当可编辑文件。`include/uapi/linux/wireguard.h` 顶部明写「Do not edit directly」，它由 YAML 生成；直接改头文件或手改 `generated/netlink.o` 都是无效且危险的，正确路径是改规范再重新生成。第三个陷阱是按目录推断许可：工具域里多数文件是 `GPL-2.0 OR MIT`，但 `ipc-linux.h` 单独是 `MIT`，uapi 头又是带 syscall-note 例外的双许可；闭源集成前必须逐文件读 SPDX 头，必要时寻求法务意见。

第四个陷阱是因快照缺文件而误判版本。本快照的驱动目录缺 `netlink.c`、`peerlookup.c`、`netlink.h` 等，但 Makefile 引用了它们；这属于生成化与收集范围问题，不是「该版本没有 netlink 功能」。遇到引用与文件对不上，正确做法是标注「需对照实际版本核验」并转向 06-14、07-11，而不是断言功能不存在。第五个陷阱是照抄绝对性能数字：吞吐、pps、握手速率一律需在目标机型实测，本套资料不给绝对值（基准方法见 08-01，调优见 08-02）。第六个陷阱是跨册重复展开细节：看到 `wg_device` 就想把字段全列出来，看到 `wg set` 就想把参数全抄一遍——这些都由 05、04 册负责，本篇只用交叉引用让出去。

最佳实践可归纳为四步。第一步，**先固定基准再谈细节**：任何讨论开始前，先用本篇命令组确认目标机器的内核、驱动、工具三者版本，把它写进排障记录。第二步，**每个结论都给真实路径**：写「`wg_xmit` 查 allowedips」就必须能指到 `device.c`，指不到就标注核验，绝不凭记忆编路径。第三步，**用权威册去重**：参数去 04、字段去 05、原理去 06、模块职责去 07、运维与性能去 08，本篇与 01-03 只做定位与约定；四段式交叉引用就是这套纪律的落地形式。第四步，**区分「快照事实」与「目标机事实」**：本套资料给出的是基于真实源码的深度解读，不是对某个发行版某个内核版本的逐字说明书；凡落到具体机器，都要以该机实际版本复核。把这两类事实分开，是正确使用本套资料的前提。

### 7. 小结与延伸阅读

本篇为全套资料立下四根柱子。**版本基准**是三元组：驱动 `1.0.0`、工具 `1.0.20260223`、目标内核 `uname -r`，三者独立，差异是常态。**源码地图**分四域：内核驱动 `drivers/net/wireguard/`、加密原语 `lib/crypto/`、uapi 契约 `include/uapi/linux/wireguard.h`、用户态工具 `wireguard-tools/src/`；其中 netlink 粘合层由 YAML 规范生成，故 Makefile 引用了本快照未含的 `netlink.o`/`generated/netlink.o`，相关细节一律标注需对照实际版本核验。**许可**分层：内核驱动 SPDX 为 `GPL-2.0` 且 `MODULE_LICENSE("GPL v2")`，uapi 头为 `((GPL-2.0 WITH Linux-syscall-note) OR BSD-3-Clause)`，工具多为 `GPL-2.0 OR MIT` 而 `ipc-linux.h` 单独为 `MIT`。**使用约定**四条：事实来源唯一权威、不确定即标注核验、权威册去重、口径克制不写绝对性能数字。

延伸阅读建议按三条线走：想核验版本与构建，读 02 册（源码获取见 02-01，构建配置见 02-02）与 08-01 的性能基准方法；想逐文件深入，按 07-01、07-02、07-11、07-12、07-13 展开模块职责；想查具体字段与参数，去 05 册与 04 册。跨册随查按（字段见 05-01 ｜ 参数见 04-05 ｜ 原理见 06-01 ｜ 模块见 07-01）执行：结构地图与逐字段定义去 05，命令与 netlink 属性全集去 04，启动与调用链去 06，目录级模块职责去 07，运维与基准去 08。凡本篇标注「需对照实际版本核验」的版本号、文件路径与生成物细节，均以 `_wglinux_build/upstream_src/` 下对应文件与目标系统实际版本为准，本套资料不编造未核验的路径与取值。
