# WireGuard Linux 技术资料 · 08 运维、性能基准与排障

## 08-01 性能基准方法、测试模型与实测口径

### 1. 背景与动机

关于 WireGuard 的性能，最常见的提问方式是「它到底有多快」。这个问题之所以很难有单一答案，是因为吞吐速率从来都不是协议本身的一个常量，而是协议实现与运行环境共同决定的系统属性。同样一份 `drivers/net/wireguard/` 驱动，在配备 AVX2 与 AVX-512 的服务器 CPU 上，与在低功耗 ARM 小板上，会给出完全不同的结果；64 字节的小包与 1500 字节的满帧会撞上不同的瓶颈；单条 TCP 流与十六条并行流对多核的利用程度也天差地别。脱离这些前置条件抛出一个「标准吞吐数字」，既不可复现，也没有工程价值。本册作为运维、性能基准与排障的唯一权威源，在这里先把口径立清楚：所有性能结论一律标注「需在目标机型实测验证」，示例输出中的数字仅用于说明命令格式与判读方法，绝不构成任何性能承诺。

那么性能基准究竟要解决什么问题？归纳起来有三层。第一层是**可复现**：让不同人、不同时间在相同环境下跑出可以互相比较的结果，为此必须固定包长、流数、测试时长、CPU 亲和性与内核版本，并把这些条件写进报告。第二层是**可归因**：当吞吐不达预期时，能把瓶颈定位到加密、队列、socket 封装、物理网卡还是对端，为此需要同时观察应用层的 iperf3 速率、WireGuard 接口层的 `wg show` 计数器和内核 netdev 的统计，三层口径互相印证。第三层是**可对照**：为调优（08-02）提供基线，任何优化措施都必须有调优前的基线数据作参照，否则无法证明改动是否真的带来收益。

WireGuard Linux 之所以具备良好的性能潜力，并不是偶然，而是有清晰的源码依据。它的数据面完全在内核态，包以 `sk_buff` 形态在协议栈各子系统之间传递，加解密函数直接调用内核 crypto 原语，全程不跨越内核态与用户态的边界，因而没有用户态 VPN 那种每包两次拷贝的开销（实现形态对比见 01-02）。更进一步，它在设计上就把并发放在第一位：`drivers/net/wireguard/device.h` 为设备定义了 `encrypt_queue`、`decrypt_queue`、`handshake_queue` 三个 `crypt_queue`，每个队列内嵌一个 `ptr_ring` 环形缓冲与一个 per-CPU 的 `multicore_worker` 指针；加解密工作被分发到多个 CPU 上并行执行，而不是挤在一个核上。理解这套「多队列 + 批量 + per-CPU worker」的设计，是读懂后面所有基准现象的钥匙——比如为什么单流跑不满多核、为什么小包场景 pps 会比吞吐更早撞墙。

本篇的事实锚点延续全册约定：内核驱动以 `_wglinux_build/upstream_src/wireguard-linux-src/` 下的 `drivers/net/wireguard/` 为准，用户态工具以 `_wglinux_build/upstream_src/wireguard-tools/`（版本 1.0.20260223）为准，凡涉及函数、字段与命令均先读源码核实。本篇聚焦「怎么测、怎么读、怎么算口径」，调优手段放到 08-02，具体字段展开放到 05 册，机制与调用链放到 06 册，绝不在此重复。

### 2. 核心概念

性能基准首先要厘清四个指标维度，它们度量的是不同事物，不能互相替代。**吞吐**（throughput）是单位时间传输的字节数，常用 Mbits/sec 或 Gbits/sec 表示，是 iperf3 默认报告的主指标。**包转发率**（pps，packets per second）是单位时间处理的包个数，在小包场景它往往比吞吐更早触顶——因为每个包都要走一遍封装、加密、查路由、socket 发送的固定流程，这部分开销与包长无关。**延迟**（latency）及其抖动（jitter）度量单个包穿过隧道的时间，对交互式应用比对批量传输更重要。**CPU 效率**通常用「每字节消耗的 CPU 周期」或「每 GHz 能跑出的吞吐」表示，是横向比较不同机器、不同实现时的归一化指标。一台机器吞吐高，可能只是核多，未必效率高。

第二个概念是**流模型**。单流（iperf3 不加 `-P`）只有一个 TCP 连接，其数据包通常落在同一条接收队列、由同一个加密 worker 处理，因此很难吃满多核——这与 WireGuard 的 per-CPU 队列设计直接相关（字段见 05-08，原理见 06-13）。多流（`-P N`）产生 N 条并行连接，内核可按流的哈希把包分散到不同队列，从而并行加解密。基准报告必须写明流数，否则「吞吐」数值无法解释。实践中应同时跑单流与多流：单流反映单核加密能力与延迟，多流反映整机聚合能力。

第三个概念是**包长模型**。包长直接决定 pps 与吞吐的比值，也决定是否触发分片。常见的测试点包括：1500 字节满帧（标准以太网 MTU 下的典型大包，吞吐友好）、1400 字节左右（为隧道封装预留余量的常见内层长度）、以及包含多种包长的 IMIX 混合模型（用于逼近真实业务流量分布，其具体比例依测试定义而异，需对照所用基准规范核验）。UDP 打流可用 iperf3 的 `-l` 指定包长，TCP 则由内核按 MSS 自动分段。选包长的原则是覆盖「小包看 pps、大包看吞吐、混合看综合」三种情形。

第四个概念是**测量层次与计数口径**。一次完整的性能观测至少涉及三层：应用层（iperf3 自己统计的传输字节与速率）、WireGuard 接口层（`wg show wg0 transfer` 展示的累计收发字节）、内核 netdev 层（`/sys/class/net/wg0/statistics/` 下由 `dev_sw_netstats` 维护的统计）。三层的字节口径并不相同，绝不能混为一谈。这里有一个极易踩坑的源码细节：`wg show` 的 transfer 字节来自 `wg_peer` 的 `rx_bytes` / `tx_bytes` 字段（字段见 05-03）。其中发送侧在 `socket.c` 的 `wg_socket_send_skb_to_peer` 里累加——函数先记录 `size_t skb_len = skb->len;`，在调用 `send4` / `send6` 经 `udp_tunnel_xmit_skb` 发出且确认无错后，执行 `peer->tx_bytes += skb_len`。这个 `skb_len` 是已完成加密、加上 `message_data` 头、认证标签与填充后的**WireGuard 数据消息长度**，既不含 UDP 与 IP 外层头，也不是原始内层明文。接收侧在 `receive.c` 的 `update_rx_stats` 中以 `message_data_len(len_before_trim)` 累加，口径与发送侧对称。因此 `wg show` 的字节与 iperf3 的应用层字节之间存在固定的封装开销差，直接拿两个数相除会得到错误结论。

第五个概念是**累计值与速率的区别**。`wg show` 的 transfer 与 netdev 的 `rx_bytes` / `tx_bytes` 都是自接口创建以来的累计量，且为 64 位无符号整数，正常运行时不会回绕（源码中 `REJECT_AFTER_MESSAGES` 为 `U64_MAX - COUNTER_WINDOW_SIZE - 1`，远早于字节计数回绕就会触发密钥轮换，见 `messages.h`）。要得到速率，必须在测试前后各取一次快照，用差值除以时间间隔。相比之下，iperf3 直接给出区间速率，更适合快速读数，但它是应用层的数，不能替代接口层口径。把「取两次快照做差」写进测试流程，是取得可复现数据的关键一步。

### 3. 关键数据结构与源码位置

性能观测落点集中在少数几个结构与函数上，本节只点名位置并给出与测量相关的字段语义，逐字段定义交给 05 册，不在这里展开字段表。

设备层的并发骨架在 `drivers/net/wireguard/device.h`：`struct crypt_queue` 由 `struct ptr_ring ring`、`struct multicore_worker __percpu *worker` 与 `int last_cpu` 组成；`struct wg_device` 持有 `encrypt_queue`、`decrypt_queue`、`handshake_queue` 三个队列，以及 `packet_crypt_wq`、`handshake_receive_wq`、`handshake_send_wq` 三个 workqueue。这些结构决定了「包会被放到哪个队列、由哪个 CPU 的 worker 处理」，是解释多流吞吐的唯一入口（字段见 05-02、05-08）。`drivers/net/wireguard/peer.h` 的 `struct wg_peer` 则持有 `tx_queue`、`rx_queue`（均为 `prev_queue`）、`napi`、`serial_work_cpu`，以及测量核心的 `u64 rx_bytes, tx_bytes`（字段见 05-03）。`drivers/net/wireguard/queueing.h` 定义了 `wg_cpumask_next_online` 与 `wg_cpumask_choose_online` 两个 CPU 选择函数，以及入队函数 `wg_queue_enqueue_per_device_and_peer`：它先把 skb 放入对等体的 `prev_queue`，再投入设备的 `ptr_ring`，最后用 `queue_work_on(cpu, wq, &per_cpu_ptr(device_queue->worker, cpu)->work)` 唤醒对应 CPU 的 worker（原理见 06-13）。

收发与统计相关的函数分布在四处。`send.c` 的 `wg_packet_encrypt_worker` 用 `ptr_ring_consume_bh` 从环形队列批量取出一组 skb，再以 `skb_list_walk_safe` 逐个调用 `encrypt_packet`；后者通过 `skb_to_sgvec` 构造 scatterlist 并调用 `chacha20poly1305_encrypt_sg_inplace` 原地加密，这是 CPU 成为加密瓶颈时的直接观察点（模块见 07-07）。`receive.c` 的 `wg_packet_decrypt_worker` 对称地做批量解密，`update_rx_stats` 负责累加 `peer->rx_bytes` 与 netdev 的 `dev_sw_netstats_rx_add`，`wg_packet_rx_poll` 作为 NAPI poll 函数以 `budget` 为上限处理接收队列，并在 `wg_packet_consume_data_done` 中通过 `napi_gro_receive` 把解密后的包重新注入协议栈（模块见 07-08）。`socket.c` 的 `wg_socket_send_skb_to_peer` 负责发送侧 `peer->tx_bytes` 累加，`send4` / `send6` 通过 `udp_tunnel_xmit_skb` 完成 UDP 封装，并设置 `skb->ignore_df = 1`（模块见 07-09）。用户态展示在 `wireguard-tools/src/show.c`：`transfer` 行由 `bytes(peer->rx_bytes)` 与 `bytes(peer->tx_bytes)` 渲染，`latest handshake` 由 `ago(&peer->last_handshake_time)` 渲染。

配置属性的权威定义在 `include/uapi/linux/wireguard.h`，与测量相关的是 `WGPEER_A_RX_BYTES`、`WGPEER_A_TX_BYTES` 与 `WGPEER_A_LAST_HANDSHAKE_TIME`（完整属性见 04-05、04-06）。`wg show` 命令的选项全集见 04-01。下表把本篇反复引用的源码位置收拢成速查。

### 4. 关键流程与调用链

把打流工具的流量与三处计数观察点叠在同一条链路上，读者就能明白「哪个数字在哪里产生」。出站方向：iperf3 客户端产生 TCP 或 UDP 数据，内核按路由把包交给 wg0 的 `ndo_start_xmit`，进入 `send.c` 的发送逻辑；`wg_packet_create_data` 调用 `wg_queue_enqueue_per_device_and_peer`，把 skb 同时挂到对等体 `tx_queue` 与设备 `encrypt_queue`，并唤醒某个 CPU 的加密 worker；`wg_packet_encrypt_worker` 批量取出并执行 `encrypt_packet`，完成后通过 `wg_queue_enqueue_per_peer_tx` 转交 `wg_packet_tx_worker`，后者调用 `wg_socket_send_skb_to_peer` 发出——正是在这里 `peer->tx_bytes` 增加。随后 `send4` / `send6` 经 `udp_tunnel_xmit_skb` 加上 UDP 与 IP 头，交给物理网卡。完整发送链路见 06-05，模块职责见 07-07。

入站方向：物理网卡收到 UDP 报文，经 `socket.c` 的 `wg_receive` 回调进入 `wg_packet_receive`；它按消息类型分发，数据消息走 `wg_packet_consume_data`，通过 `wg_queue_enqueue_per_device_and_peer` 投入 `decrypt_queue`；`wg_packet_decrypt_worker` 批量解密后经 `wg_queue_enqueue_per_peer_rx` 触发 `napi_schedule`；`wg_packet_rx_poll` 在 NAPI 上下文中先做 `counter_validate` 抗重放检查，再进入 `wg_packet_consume_data_done`，其中 `update_rx_stats` 累加 `peer->rx_bytes`，`napi_gro_receive` 把包注入协议栈，最终送达 iperf3 服务端。完整接收链路见 06-06，抗重放原理见 06-08，模块职责见 07-08。

### 5. 配置/命令/代码实例

下面给出一组可复现的测试命令。前提是一条已建立的 WireGuard 隧道，两端 wg0 地址已知、握手正常（握手可用性的判断见第 6 节与 01-01 的 `wg show` 判读）。第一组用 iperf3 打流，覆盖单流 TCP、多流 TCP 与指定包长的 UDP 三种情形：

```bash
# A 端启动服务端
iperf3 -s -p 5201

# B 端：单流 TCP，测 10 秒
iperf3 -c <A端wg0地址> -p 5201 -t 10

# B 端：4 条并行流 TCP
iperf3 -c <A端wg0地址> -p 5201 -t 10 -P 4

# B 端：UDP，指定 1400 字节包长，不设带宽上限
iperf3 -c <A端wg0地址> -p 5201 -u -l 1400 -b 0 -t 10
```

第二组在测试**前后各执行一次**，用于取得接口层与 netdev 层的累计计数快照，随后做差除以时长得到速率：

```bash
# 测试前快照
wg show wg0 transfer
cat /sys/class/net/wg0/statistics/rx_bytes /sys/class/net/wg0/statistics/tx_bytes

# 测试后再次执行同样两条命令，用后值减前值再除以测试秒数
```

第三组是 iperf3 单流测试的典型输出，紧接着给出判读。示例输出，具体格式需对照实际版本核验；示例数值需按实际环境验证，不作为承诺：

```text
Connecting to host 10.0.0.1, port 5201
[  5] local 10.0.0.2 port 52344 connected to 10.0.0.1 port 5201
[ ID] Interval           Transfer     Bitrate         Retr  Cwnd
[  5] 0.00-10.00  sec   112 MBytes  94.0 Mbits/sec    0   1.20 MBytes
[  5] 0.00-10.00  sec   112 MBytes  94.0 Mbits/sec    receiver
```

逐行判读如下。首行 `Connecting to host 10.0.0.1, port 5201` 表明客户端连的是对端 wg0 的地址与 iperf3 监听端口，确认流量确实要穿过隧道；若这里写成了物理网卡地址，测到的就是不经 WireGuard 的裸网性能，整个测试失去意义。第二行给出本地与对端的地址端口对，`local 10.0.0.2` 是本机 wg0 地址，说明源地址选在隧道网段，配合路由才能进入 wg0 的发送路径。表头行定义了后续各列：`Interval` 是统计区间，`Transfer` 是区间内传输字节，`Bitrate` 是换算后的速率，`Retr` 是重传次数，`Cwnd` 是拥塞窗口。第四行是发送端报告：`112 MBytes` 与 `94.0 Mbits/sec` 是应用层口径的传输量与速率，`Retr 0` 表示没有重传，说明隧道内没有明显丢包，`Cwnd 1.20 MBytes` 反映拥塞窗口大小；这一行的字节数是 iperf3 在应用层数的，与 `wg show` 的 `peer->tx_bytes` 存在封装开销差，二者不可直接相等。末行是接收端报告，`receiver` 标注表明这是对端回传的统计，正常情况下应与发送端接近；若接收端明显低于发送端，说明隧道内或物理链路上发生了丢包，需结合 `wg show` 的计数器与 netdev 的 `rx_errors` 等字段进一步定位（排障流程由本册后续篇章给出，此处不展开）。务必注意：这里的 `94.0 Mbits/sec` 只是示例数值，需在目标机型实测验证，不作为任何性能承诺；真实结果取决于 CPU、包长、流数与内核配置。最后强调口径：要把这次测试写成可复现记录，必须同时附上包长（TCP 由 MSS 决定、UDP 用 `-l` 指定）、流数（`-P`）、时长（`-t`）、内核版本与 `wg --version`，缺一项都可能导致他人无法复现你的数字。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是**只看单一指标**。只报吞吐不报包长与流数，等于没报——同样的机器跑 1500 字节大包和 64 字节小包，吞吐与 pps 的表现可能完全相反。最佳实践是固定一组「标准测试矩阵」：单流 TCP、多流 TCP、1500B UDP、小包 UDP、IMIX 混合，逐项记录。

第二个陷阱是**拿 iperf3 数字直接对比 `wg show` 字节**。如前所述，后者统计的是封装后的 WireGuard 数据消息，不含 UDP/IP 外层头，也不是原始明文；iperf3 数是应用层字节。两者的差值来自封装开销，属于预期现象，不是丢包。要核对是否丢包，应比较 iperf3 收发两端的差值，以及 netdev 统计里的 `rx_errors`、`rx_dropped`、`tx_dropped`。

第三个陷阱是**忽略累计值做差**。直接把 `wg show transfer` 的累计字节当成一次测试的吞吐，是典型错误。正确做法是在测试前后各取一次快照做差；由于该值是 64 位累计量且不会在正常测试时长内回绕，做差是安全的。

第四个陷阱是**测试工具本身成为瓶颈**。单流 iperf3 可能受限于发送端 CPU 的单核性能或 TCP 拥塞控制，而非 WireGuard；跑多流时若客户端与服务端在同一台物理机上，还会引入本机回环与中断竞争。应尽量用两台独立主机，服务端与客户端分别固定到不同 CPU（用 `taskset` 绑定 iperf3 进程），避免测试工具与加密 worker 争抢同一组核。

第五个陷阱是**忽略握手状态与 keepalive 的干扰**。测吞吐前应确认 `wg show` 的 `latest handshake` 是最近的值；若长期为空或很旧，说明握手从未成功或已过期，此时流量会被暂存或丢弃，测出的数字毫无意义。对于 NAT 后的 peer，缺少持久 keepalive 会导致 endpoint 漂移，进而中断打流（keepalive 原理见 06-11，参数见 04-01）。

第六个陷阱是**把环境差异误当成实现差异**。CPU 是否支持 SIMD、内核是否启用 GSO/GRO、网卡是否开 RSS 多队列、irqbalance 如何分配中断，都会显著改变结果。因此跨平台比较时必须逐项记录这些条件，这些维度的具体调优放在 08-02。可复现性清单建议包含：主机型号与 CPU 型号、内核版本、`wg --version`、iperf3 版本、包长、流数、时长、MTU、GSO/GRO 状态、网卡队列数与中断亲和性、两端是否为独立主机。

最后重申本册的口径纪律：任何没有附上上述条件的吞吐数字，都应视为不可复现；本套资料不提供「某型号必达多少 Gbps」这类断言，所有性能数值一律需在目标机型实测验证。

### 7. 小结与延伸阅读

本篇建立了 WireGuard Linux 性能基准的方法学：性能是系统属性而非协议常量，因此基准要解决可复现、可归因、可对照三个问题；基准围绕吞吐、pps、延迟、CPU 效率四个指标展开，并区分单流与多流、大包与小包/IMIX 两类模型；观测分为 iperf3 应用层、`wg show transfer` 接口层、内核 netdev 三层，三者口径不同——尤其 `peer->tx_bytes` 在 `socket.c` 累加的是封装后的 WireGuard 数据消息长度，`peer->rx_bytes` 在 `receive.c` 以 `message_data_len` 累加，二者都与 iperf3 的应用层字节存在封装开销差，累计值须做差才能得到速率。源码落点集中在 `device.h` 的三个 `crypt_queue`、`queueing.h` 的入队与 CPU 选择、`send.c` 与 `receive.c` 的批量加解密 worker、`socket.c` 的 UDP 封装与发送侧累加，以及 `show.c` 的展示渲染。所有示例数字均需在目标机型实测验证，不构成性能承诺。

延伸阅读建议按三条线走：想深入计数器对应的结构体字段去 05 册，想理解加解密与收发的完整调用链去 06 册，想知道各源文件承担什么职责去 07 册；命令与属性的全集去 04 册。调优手段（多队列、GSO/GRO、MTU、CPU 特性）见 08-02。跨册随查按（字段见 05-03 ｜ 参数见 04-01 ｜ 原理见 06-05 ｜ 模块见 07-07）执行：结构体逐字段去 05、参数与命令全集去 04、机制与调用链去 06、目录级模块能力去 07。凡本篇标注「需对照实际版本核验」的函数名、字段与命令选项，均以 `_wglinux_build/upstream_src/` 下对应文件为准。

## 08-02 性能调优：多线程、GSO、MTU 与 CPU 特性

### 1. 背景与动机

调优是建立在基准基线之上的定向改善，而不是凭感觉调整参数。08-01 已经把「怎么测、怎么读、怎么算口径」立清楚，本篇要回答的是「有哪些可调维度、每个维度改的是什么、如何判断改动有效」。WireGuard Linux 的性能由四个层面共同决定：包如何在多个 CPU 之间分发、发送与接收路径能否利用网卡的分段与聚合卸载、封装后的报文是否因 MTU 设置不当而触发分片或丢弃、以及底层加密原语能否吃到 CPU 的 SIMD 能力。这四层分别对应多线程与多队列、GSO/GRO、MTU/MSS、CPU 特性四个调优维度，本篇逐一展开。

必须先立两条纪律。第一，调优的每一步都要有基线对照：先按 08-01 的标准矩阵测出基线，再只改动一个维度重测，否则无法归因——同时改队列数和 MTU，出了问题根本不知道是哪一项导致的。第二，所有性能数值一律标注「需在目标机型实测验证」，本篇不给出「调到某值即可达到多少 Gbps」这类断言。不同 CPU、不同网卡、不同内核版本的最优配置并不相同，照抄他人的配置往往适得其反。

从源码看，WireGuard Linux 天生就是为多核与批量处理而设计的。`drivers/net/wireguard/device.h` 把每个设备的加解密工作拆成 `encrypt_queue`、`decrypt_queue`、`handshake_queue` 三个 `crypt_queue`，每个队列用 `ptr_ring` 做无锁环形缓冲、用 per-CPU 的 `multicore_worker` 承接工作；`send.c` 与 `receive.c` 的 worker 都是「一次取出一批 skb、逐个加解密」的批量模型。这意味着很多「调优」其实不是去改 WireGuard 的内部参数——它并没有暴露多少内部旋钮——而是去调整它所依赖的内核基础设施：网卡多队列、中断亲和性、GSO/GRO 开关、MTU 与 MSS、以及内核 crypto 后端的 SIMD 实现。理解这一点，才能明白为什么调优的命令大多是 `ethtool`、`taskset`、`ip` 与 `iptables/nftables`，而不是某条 WireGuard 专有命令（命令全集见 04-01、04-03）。

### 2. 核心概念

**多线程与多队列。** WireGuard 的并发单位是 per-CPU worker：`queueing.h` 的 `wg_queue_enqueue_per_device_and_peer` 通过 `wg_cpumask_next_online(&device_queue->last_cpu)` 在在线 CPU 之间轮转选核，再用 `queue_work_on` 把工作投递到该 CPU 的 worker。因此 worker 的数量实际上等于在线 CPU 数，并不是一个可直接配置的旋钮；换一个 peer 发送时，`wg_queue_enqueue_per_peer_tx` 用 `wg_cpumask_choose_online` 按 `peer->internal_id` 选择固定的 CPU，以保持同一 peer 的顺序性。真正可调的是「包从物理网卡到内核时能否分散到多个队列」——这由网卡的 RSS 多队列、中断亲和性与 irqbalance 决定。单流流量只有一条连接，哈希后通常落在同一队列、同一 worker，因此多队列对单流帮助有限；多流才能把负载摊到多个核。这是为什么基准必须同时测单流与多流（08-01）的根本原因。

**GSO 与 GRO。** GSO（Generic Segmentation Offload）是发送侧的卸载：协议栈先构造一个远大于 MTU 的「大包」，推迟到接近网卡时才分段，从而减少协议栈逐包处理的次数；GRO（Generic Receive Offload）是接收侧的聚合：把同类小包在交给协议栈前合并成大包，减少上层处理次数。就本快照而言，据源码据实说明：`receive.c` 的 `wg_packet_consume_data_done` 明确调用 `napi_gro_receive(&peer->napi, skb)`，因此接收侧走的是 NAPI + GRO 路径；而 `send.c` 的 `encrypt_packet` 是通过 `skb_cow_data` 处理非线性 skb、以 `skb_to_sgvec` 构造 scatterlist 后调用 `chacha20poly1305_encrypt_sg_inplace` 完成原地加密，本快照中并未出现显式的发送侧 GSO 分段逻辑（例如设置 `skb->encapsulation` 或调用分段辅助函数）。较新的内核版本是否为 WireGuard 加入了发送侧 GSO 支持，必须对照目标内核源码核验，不能据本快照下断言。这也提示一条实践原则：GSO/GRO 的行为高度依赖内核版本与网卡驱动，任何结论都要在实际环境用 `ethtool -k` 观察当前状态并实测验证。

**MTU 与 MSS。** WireGuard 把所有流量封装在 UDP 中，这带来了固定的封装开销。按本快照 `messages.h` 的定义：`struct message_data` 含 `header`（4 字节）、`key_idx`（4 字节）、`counter`（8 字节），合计 16 字节；`NOISE_AUTHTAG_LEN` 为 `CHACHA20POLY1305_AUTHTAG_SIZE`（16 字节）。两者相加，WireGuard 层开销为 32 字节；再叠加 UDP 头 8 字节与 IPv4 头 20 字节，IPv4 承载下总计约 60 字节（IPv6 承载因 40 字节 IP 头而约 80 字节，具体取值需对照实际版本核验）。因此物理口 MTU 为 1500 时，wg0 的内层 MTU 通常应设为 1500 减去这段开销（约 1440 或更低），否则内层满帧封装后会超过物理口 MTU，触发分片甚至被丢弃。TCP 场景还可用 MSS clamp 把 SYN 报文的 MSS 值压到合适大小，从源头避免分片。MTU 过大导致分片、过小导致有效载荷占比下降，两端都要兼顾。

**CPU 特性。** 这里有一个必须澄清的常见误解：WireGuard 协议把对称加密固定为 ChaCha20-Poly1305，而 AES-NI 是加速 AES 的指令集，对 ChaCha20 没有直接加速作用，所以「开启 AES-NI 提升 WireGuard 性能」的说法并不成立。ChaCha20 是 ARX（加-旋转-异或）结构流密码，其加速依赖 SIMD 把多个 32 位通道打包并行。据本快照 `lib/crypto/chacha.c`：通用实现 `chacha_crypt_generic` 以 `CHACHA_BLOCK_SIZE` 为单位循环生成密钥流并异或；只有在定义 `CONFIG_CRYPTO_LIB_CHACHA_ARCH` 时，才通过 `#include "chacha.h" /* $(SRCARCH)/chacha.h */` 引入体系结构相关实现，否则把 `chacha_crypt_arch` 直接定义为 `chacha_crypt_generic`。所以真正值得关注的是：目标内核是否编译了对应架构的 ChaCha20 SIMD 后端（如 x86 的 AVX2/AVX-512 变体）、CPU 是否支持相应指令、以及运行时是否真的选中了 SIMD 路径。这些因素的具体取值与加速幅度均需对照内核配置、`/proc/cpuinfo` 与实测结果核验，不能凭指令集名称臆断。

### 3. 关键数据结构与源码位置

调优涉及的源码落点与 08-01 高度重叠，但关注角度不同：08-01 看「计数在哪里累加」，本篇看「并发与卸载在哪里发生」。

设备与队列层在 `drivers/net/wireguard/device.h` 与 `drivers/net/wireguard/queueing.h`：`crypt_queue` 的 `ring`、`worker`、`last_cpu` 决定批量与轮转（字段见 05-08）；`wg_cpumask_next_online`、`wg_cpumask_choose_online` 与 `wg_queue_enqueue_per_device_and_peer` 决定包落到哪个 CPU（原理见 06-13）。`peer.h` 的 `wg_peer` 含 `serial_work_cpu` 与 `internal_id`，后者用于选择「同一 peer 固定 CPU」（字段见 05-03）。批量加解密在 `send.c` 的 `wg_packet_encrypt_worker` 与 `encrypt_packet`，以及 `receive.c` 的 `wg_packet_decrypt_worker`；`receive.c` 的 `wg_packet_rx_poll` 以 `budget` 为处理上限，`wg_packet_consume_data_done` 调用 `napi_gro_receive`（模块见 07-07、07-08，GSO/GRO 原理见 06-12）。封装与分片相关常量在 `messages.h`：`MESSAGE_PADDING_MULTIPLE = 16`、`MESSAGE_MINIMUM_LENGTH`、`SKB_HEADER_LEN`、`DATA_PACKET_HEAD_ROOM` 以及队列上限 `MAX_STAGED_PACKETS = 128`、`MAX_QUEUED_PACKETS = 1024`（常量全集见 04-06）。UDP 承载在 `socket.c`：`send4` / `send6` 调用 `udp_tunnel_xmit_skb` 并设置 `skb->ignore_df = 1`，`wg_socket_init` 把 `sk_sndbuf` 设为 `INT_MAX` 且调用 `sk_set_memalloc`（模块见 07-09，socket 原理见 06-12）。加密后端在 `lib/crypto/chacha.c` 与 `lib/crypto/poly1305.c`（模块见 07-12）。

下表把四个调优维度与对应的源码位置、外部操作对象收拢成速查。

| 调优维度 | 源码依据（本快照） | 外部操作对象 |
|---|---|---|
| 多线程与多队列 | `device.h` 的 `crypt_queue`、`queueing.h` 的 CPU 选择 | 网卡 RSS 队列、irqbalance、CPU 亲和性 |
| GSO / GRO | `receive.c` 的 `napi_gro_receive`、`send.c` 的 scatterlist | `ethtool -k` 的 gro/gso 开关 |
| MTU / MSS | `messages.h` 的 `message_data`、`NOISE_AUTHTAG_LEN` | `ip link set mtu`、`iptables/nftables` MSS clamp |
| CPU 特性 | `lib/crypto/chacha.c` 的 `CONFIG_CRYPTO_LIB_CHACHA_ARCH` | 内核 crypto 配置、CPU flags |

### 4. 关键流程与调用链

多线程调优的链路是：物理网卡的多个 RSS 接收队列产生多路中断，每路中断经 irqbalance 或手工亲和性绑定到不同 CPU；每个 CPU 上的软中断把包送入对应的 UDP socket，由 `socket.c` 的 `wg_receive` 回调进入 `wg_packet_receive`；随后 `wg_queue_enqueue_per_device_and_peer` 按 `last_cpu` 轮转把包投入 `decrypt_queue` 并唤醒对应 CPU 的 `wg_packet_decrypt_worker`。这样形成「网卡队列 → CPU → per-CPU worker」的映射。若 RSS 只有一条队列或中断全绑在同一核，即便机器有很多核，加解密也会挤在一个 worker 上，多流吞吐因此上不去（字段见 05-08，原理见 06-13）。

GSO/GRO 的链路要分两侧看。接收侧在 `wg_packet_consume_data_done` 里把解密后的 skb 通过 `napi_gro_receive` 注入协议栈，因此 GRO 是否有效与 NAPI 权重（`wg_packet_rx_poll` 的 `budget`）相关；发送侧本快照以 `skb_cow_data` + scatterlist 批量加密为主，没有显式 GSO 分段，较新内核的差异需核验（原理见 06-12）。MTU 则贯穿两端：入站 `prepare_skb_header` 对 UDP 长度做严格校验，封装后超过物理口 MTU 且被设置 `ignore_df` 的报文会依赖底层分片或丢弃；出站 `calculate_skb_padding` 以 `MESSAGE_PADDING_MULTIPLE` 对齐填充，MTU 设置直接影响最终报文大小（发送路径见 06-05，字段见 05-06）。

### 5. 配置/命令/代码实例

第一组命令调整多队列与 CPU 亲和性。先查看网卡支持的组合队列数，再按需设置，最后用 `taskset` 把打流进程固定到不承载网卡中断的核上，避免测试工具与加密 worker 争抢同一组核：

```bash
# 查看并设置网卡组合队列数（需网卡驱动支持）
ethtool -l eth0
ethtool -L eth0 combined 4

# 查看中断亲和性；关闭 irqbalance 后可手工绑核
cat /proc/irq/125/smp_affinity_list
echo 0-3 > /proc/irq/125/smp_affinity_list

# 把 iperf3 固定到指定 CPU 核
taskset -c 8,9 iperf3 -c <A端wg0地址> -t 10 -P 4
```

第二组命令调整 MTU 与 MSS。先看物理口与 wg0 的 MTU，再按封装开销设置 wg0 的 MTU，最后用 MSS clamp 让 TCP 从源头避免分片（规则仅为示例写法，需按实际防火墙框架与地址段调整）：

```bash
# 查看与设置 MTU（物理口 1500 时，wg0 需扣除封装开销）
ip link show eth0
ip link set wg0 mtu 1420

# iptables 方式：把正向 SYN 的 MSS 压到 1360
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu

# 查看当前卸载开关状态
ethtool -k eth0 | grep -E 'generic-segmentation-offload|generic-receive-offload'
```

第三组是一份「调优前现状核查」的示例输出，用于确认多队列、亲和性与 SIMD 后端是否处于预期状态。示例输出，具体格式需对照实际版本核验；示例数值需按实际环境验证，不作为承诺：

```text
$ ethtool -l eth0 | grep Combined
    Combined:  8
    Combined:  4
$ cat /proc/irq/125/smp_affinity_list
0-3
$ grep -m1 -o 'avx2\|avx512f' /proc/cpuinfo
avx2
$ wg show wg0 transfer
  transfer: 12.4 GiB received, 8.91 GiB sent
```

逐行判读如下。第一组 `ethtool -l ... | grep Combined` 输出两行，上一行是 Pre-set maximums（硬件上限 8），下一行是 Current hardware settings（当前生效 4）；当前值小于上限意味着还有提升多队列的余地，对应 `device.h` 中 per-CPU worker 能否被多路中断喂饱，但队列数并非越多越好，需结合 08-01 的多流基线实测。`cat /proc/irq/125/smp_affinity_list` 输出 `0-3`，表示 125 号中断被限制在 CPU 0 到 3，若所有网卡中断都落在这几个核，而 iperf3 又被 `taskset` 绑到 8、9 核，就形成了「软中断在 0-3、加密 worker 按在线 CPU 轮转、打流进程在 8-9」的拓扑，是否均衡要看实际 pps 分布。`grep -m1 -o 'avx2\|avx512f' /proc/cpuinfo` 输出 `avx2`，说明 CPU 支持 AVX2，但是否真的被 ChaCha20 SIMD 后端使用，还取决于内核是否定义了 `CONFIG_CRYPTO_LIB_CHACHA_ARCH`（见 `lib/crypto/chacha.c`），仅凭 CPU flags 不能下结论。`wg show wg0 transfer` 的 `12.4 GiB received, 8.91 GiB sent` 是自接口建立以来的累计量，来自 `peer->rx_bytes` / `peer->tx_bytes`（字段见 05-03），要评估某次调优的效果必须在调优前后各取一次快照做差，并把差值除以测试时长，绝不能把累计值当成单次吞吐；这里的数值同样是示例，需在目标机型实测验证、不作为承诺。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是**把 worker 数当成可配置旋钮**。WireGuard 的加密 worker 是 per-CPU 的，数量随在线 CPU 数而定，`queueing.h` 的 `wg_cpumask_next_online` 只是在这些 CPU 间轮转；并不存在一条「设置 worker 数」的 WireGuard 命令。真正能调的是上游的队列与亲和性，把包均匀喂给这些 worker。强行追求「更多 worker」而忽视中断分布，不会有收益。

第二个陷阱是**irqbalance 与手工亲和性互相打架**。若系统运行 irqbalance，手工写入 `/proc/irq/*/smp_affinity_list` 可能被守护进程覆盖。手工绑核前应先停止 irqbalance，并把「停止守护进程」这一动作记入变更单，因为它影响整机而非仅 WireGuard。操作前需确认这是目标机器的预期状态，避免影响同机其他业务。

第三个陷阱是**MTU 设置走向两个极端**。设得过大，内层满帧封装后超过物理口 MTU，`socket.c` 又设置了 `skb->ignore_df = 1`，报文依赖底层分片或被丢弃，表现为大包吞吐骤降甚至连接不通；设得过小，协议头占比升高，有效吞吐下降。正确做法是从物理口 MTU 扣除实际封装开销（IPv4 约 60 字节、IPv6 约 80 字节，需对照版本核验）设置 wg0，并用 `ping -M do -s <大小>` 逐点验证不通分片的最大载荷。MSS clamp 只解决 TCP，UDP 仍要靠 MTU 本身控制。

第四个陷阱是**夸大 GSO/GRO 的作用**。本快照接收侧确有 `napi_gro_receive`，但发送侧没有显式 GSO 分段，较新内核的差异必须核验；而且 GSO/GRO 的效果依赖网卡驱动与内核版本，打开不等于一定更快。调整前先用 `ethtool -k` 记录当前状态，只做单变量改动并复测。

第五个陷阱是**AES-NI 迷思**。再强调一次：WireGuard 固定用 ChaCha20-Poly1305，AES-NI 加速的是 AES，对 ChaCha20 无直接作用。应关注的是内核 crypto 的 ChaCha20 SIMD 后端与 CPU 的 AVX2/AVX-512 支持，且加速幅度需实测。AVX-512 在部分 CPU 上可能触发降频，不一定比 AVX2 更优，这也必须实测验证。

最佳实践可归纳为四步：一，按 08-01 跑出标准基线并完整记录环境；二，按「多队列与亲和性 → MTU/MSS → GSO/GRO → CPU 后端」的顺序逐项调整，每次只改一个维度；三，每项改动后重跑同一套测试矩阵，用 `wg show` 计数快照做差核算接口层速率，确认收益而非依赖主观感觉；四，把生效配置与前后数据一并归档，作为上线 checklist 的输入。任何一步得到的数值，若无完整环境说明与实测记录，都不应作为普遍结论传播。

### 7. 小结与延伸阅读

本篇围绕四个调优维度给出 WireGuard Linux 的性能优化框架：多线程与多队列的真正可调对象是网卡 RSS 队列、irqbalance 与 CPU 亲和性，因为加解密 worker 是 per-CPU 的（`device.h` 的 `crypt_queue`、`queueing.h` 的 CPU 选择），单流受限于单 worker、多流才能摊到多核；GSO/GRO 方面，本快照接收侧通过 `napi_gro_receive` 做 GRO，发送侧以 `skb_cow_data` + scatterlist 批量加密为主而未出现显式 GSO，较新内核差异需核验；MTU 须扣除 WireGuard 层 32 字节加 UDP/IP 头的封装开销，并配合 MSS clamp 从源头避免分片；CPU 特性上，ChaCha20 靠 SIMD 而非 AES-NI，是否启用体系结构后端取决于 `CONFIG_CRYPTO_LIB_CHACHA_ARCH` 与内核配置。所有调优都必须建立在 08-01 的可复现基线上，逐项单变量改动并实测验证，所有性能数值需在目标机型实测验证，不构成承诺。

延伸阅读：想深入队列与计数字段去 05 册，想理解批量加解密、GSO/GRO 与多核并发的完整机制去 06 册，想知道各源文件职责去 07 册，命令与常量全集去 04 册。跨册随查按（字段见 05-08 ｜ 参数见 04-07 ｜ 原理见 06-13 ｜ 模块见 07-07）执行：结构体逐字段去 05、参数与常量全集去 04、机制与调用链去 06、目录级模块能力去 07。凡本篇标注「需对照实际版本核验」的字段、常量与命令选项，均以 `_wglinux_build/upstream_src/` 下对应文件为准。

## 08-03 常见故障分类与诊断决策树

### 1. 背景与动机

WireGuard Linux 的排障之所以需要单独成册，根源在于它的一个设计取舍：这是一个「静默失败」（fail-silently）的协议实现。与 TLS、IKE 一类会向对端回送明确错误通知的协议不同，WireGuard 在认证失败、密钥不匹配、源地址不被允许、抗重放判定失败时，几乎从不对端发送任何错误响应，而是直接把报文丢弃。这种设计换来了极小的攻击面与协议复杂度，却把可观测性的负担完全推给了运维者——你很少能从一个错误码里读到「公钥写错了」，更多时候只能看到「什么都没发生」。本篇要解决的正是这个问题：把散落在内核源码各处的丢弃分支、限速触发点、握手状态机与用户态可观测信号串起来，建立一套从现象到根因的分类方法与诊断决策树。

第二个背景事实是运行形态。WireGuard Linux 的数据面在内核态，以标准 `net_device` 形态接入协议栈，`drivers/net/wireguard/main.c` 的 `wg_mod_init` 加载后并不派生任何独立的用户态守护进程。这意味着排障时不能用「进程是否存活」作为判断依据——`ps` 里找不到名为 WireGuard 的进程是正常现象。故障只能表现为三类可观测信号：net_device 的状态与统计计数器、通过 netlink 通用族 `WG_CMD_GET_DEVICE` 拉取并由 `wg show` 渲染的属性、以及开启动态调试后的内核日志。理解「内核态实现没有进程可看，只有状态可查」，是进入本篇全部排查流程的心理前提。

第三个背景事实是可观测信号的分布并不均匀。握手是否成功、最近一次握手距今多久、累计收发字节数，这几项由 `wg show` 直接给出，是最高价值的信号；而报文为什么被丢、被谁丢，则分布在 `receive.c` 的若干 `dishonest_*` 标签、`cookie.c` 的 MAC 状态机、`ratelimiter.c` 的令牌桶，以及 `send.c` / `device.c` 的若干返回码里，默认都不打印，需要动态调试或抓包才能看到。本篇的动机就是把这两层信号对应的源码位置讲清楚，让读者在看到某个现象时知道「该去看哪一行」。

本篇的口径声明如下：所有字段、函数、常量、命令选项均以本套资料的版本基准（`wireguard-linux` stable 分支内核驱动快照 + `wireguard-tools` 1.0.20260223）为准，源码路径相对 `_wglinux_build/upstream_src/wireguard-linux-src/` 与 `_wglinux_build/upstream_src/wireguard-tools/`。错误码的完整清单与语义归 04 册（完整参数与错误码见 04-08），结构体逐字段定义归 05 册，机制与调用链归 06 册，目录级模块职责归 07 册。本篇作为运维与排障的唯一权威源，只负责「分类、决策树、排查命令、判读方法」，不重复上述四册的细节，凡涉及即写交叉引用。

基于上述背景，本篇把常见故障归纳为五类，它们的区分完全依赖可观测信号而非主观描述：**接口不通**（内核里根本没有 wg0 或接口无法 up）、**握手失败**（接口存在但 `latest handshake` 长期为空或很旧）、**隧道通但无流量**（握手成功但 `transfer` 不增长）、**间歇性断流**（握手与流量都曾正常，随后时通时断）、**吞吐低**（链路可用但速率明显低于预期）。这五类在决策树上对应五条不同分支，根因集合互不重叠，先分类再定位可以显著压缩盲目尝试的范围。

### 2. 核心概念

要读懂本篇的决策树，需要先建立三个核心概念：静默失败的分层、可观测信号的三个层次，以及五类故障的判定标准。

**静默失败的分层。** WireGuard 的「安静」并非全无差别，而是分层发生的。配置面的失败通常是「响」的：`wg set` 遇到非法参数会通过 netlink 返回错误码，例如 net_device 发送路径中 `device.c` 的 `wg_xmit` 在按目的地址查不到 peer 时返回 `-ENOKEY`，或在 endpoint 未配置时返回 `-EDESTADDRREQ`，这些错误会沿 netlink 或 netdev 操作向上传递。握手面与数据面的失败则大多是「哑」的：`noise.c` 的 `wg_noise_handshake_consume_initiation` 在任何一步解密或查表失败时都只是 `goto out` 返回 `NULL`，`receive.c` 收到 `NULL` peer 后仅打印一条 `net_dbg_skb_ratelimited` 调试日志便 `return`；对端收不到任何响应，只会反复重传握手发起消息直至放弃。把「配置面会报错、握手与数据面静默丢弃」这条分界线记牢，就能理解为什么配置错误容易发现而密钥错误难以发现。

**可观测信号的三个层次。** 第一层是 `wg show`，它读取 netlink 属性并渲染：`interface` / `public key` / `listening port` 来自 device 属性，`peer` 段的 `endpoint` / `allowed ips` / `latest handshake` / `transfer` 分别对应 `WGPEER_A_ENDPOINT`、`WGALLOWEDIP_A_*`、`WGPEER_A_LAST_HANDSHAKE_TIME`、`WGPEER_A_RX_BYTES` 与 `WGPEER_A_TX_BYTES`（字段见 05-03）。第二层是 netdev 统计，`ip -s link show wg0` 或 `/proc/net/dev` 能看到 `rx_errors`、`rx_frame_errors`、`rx_length_errors`、`tx_dropped` 等计数，它们对应 `receive.c` 中各 `dishonest_*` 分支调用的 `DEV_STATS_INC`。第三层是内核调试日志与抓包：WireGuard 大量使用 `net_dbg_ratelimited` / `net_dbg_skb_ratelimited` 打印丢弃原因，前提是开启动态调试；抓包则能直接看到 WireGuard 四种消息类型在网线上的实际形态（消息类型常量定义见 06-04）。三层信号从粗到细，排查时遵循「先看 wg show 定类、再看计数器定向、最后用日志与抓包定因」的顺序。

**五类故障的判定标准。** 下表给出本篇的核心分类，判定只依据第一、二层信号，不依赖猜测。

| 故障类别 | `wg show` 关键判据 | netdev 计数器线索 | 首要怀疑对象 | 关键源码位置 |
|---|---|---|---|---|
| 接口不通 | `ip link show wg0` 无此接口，或 `wg show` 报无接口 | 无可用计数器 | 内核模块加载、`ip link add`、`set up` | `main.c` 的 `wg_mod_init`、`device.c` 的 `wg_newlink` |
| 握手失败 | `latest handshake` 为空或远旧，`transfer` 恒为 0 | `rx_errors` 可能增长 | 公钥、endpoint、时钟、cookie/限速 | `noise.c`、`cookie.c`、`ratelimiter.c` |
| 隧道通但无流量 | 握手正常但 `transfer` 不增长 | 计数器几乎不动 | AllowedIPs、系统路由、策略路由 | `allowedips.c`、`device.c` 的 `wg_xmit` |
| 间歇性断流 | 握手曾成功，之后时通时断 | `rx_errors` 间歇增长 | NAT 映射超时、keepalive、抗重放 | `timers.c`、`receive.c` 的 `counter_validate` |
| 吞吐低 | 握手正常、流量持续增长但速率低 | `tx_dropped` / `rx_dropped` 可能增长 | MTU 与分片、GSO、CPU 特性 | `send.c`、`socket.c`、`queueing.h` |

需要说明的是，五类之间并非完全割裂：例如 AllowedIPs 配错在发送侧表现为「隧道通但无流量」（`device.c` 返回 `-ENOKEY`），在接收侧却会因为源地址校验失败落入 `receive.c` 的 `dishonest_packet_peer` 分支而计入 `rx_errors`。同一配置错误在不同方向呈现不同信号，这正是必须以「分类 + 方向」而非单个症状下结论的原因（路由原理见 06-07）。

### 3. 关键数据结构与源码位置

作为运维册，本节只建立「排障关心哪个结构、在哪个文件、逐字段去哪里查」的地图，不展开字段表。需要建立的结构与源码位置分五层，与 01-01 的版本地图一致但视角不同：这里关心的是「哪个结构的状态会体现在哪个观测信号上」。

握手与会话层以 `noise.c` / `noise.h` 为代表，核心是 `noise_handshake` 的状态机与 `noise_keypair` 的收发计数器。`wg_noise_handshake_consume_initiation`（`noise.c` 第 584 行起）的任何一步失败都返回 `NULL`，对应 `receive.c` 第 145 行的 `!peer` 分支；`wg_noise_handshake_consume_response`（第 728 行起）的状态检查 `state != HANDSHAKE_CREATED_INITIATION` 失败则 `goto fail`。这些失败点在 `wg show` 上统一表现为 `latest handshake` 不更新（字段见 05-05，握手状态机原理见 06-02）。

路由与 peer 层以 `allowedips.c`、`peer.c` 为代表。发送侧 `wg_xmit` 在 `device.c` 第 153 行调用 `wg_allowedips_lookup_dst`，失败返回 `-ENOKEY`；接收侧 `receive.c` 第 404 行调用 `wg_allowedips_lookup_src`，返回的 `routed_peer` 与当前 `peer` 不等则跳到 `dishonest_packet_peer`。这两处是「AllowedIPs 配错」在双向上的落点（字段见 05-03、05-04）。

收发与丢弃层以 `receive.c` 为代表，这是排障时最该熟读的文件。`prepare_skb_header`（第 47 行起）在 IP 头、UDP 长度、消息长度任一校验失败时返回 `-EINVAL`；`wg_packet_receive`（第 542 行起）在握手队列超过 `MAX_QUEUED_INCOMING_HANDSHAKES / 2` 或 `ptr_ring` 生产失败时打印 `Dropping handshake packet`；数据面在 `wg_packet_consume_data_done`（第 335 行起）中定义了三个 `dishonest_*` 标签，各自累加不同的 netdev 计数器，详见下表（模块职责见 07-08）。

防护层以 `cookie.c`、`ratelimiter.c` 为代表。`cookie.h` 定义 `enum cookie_mac_state` 四态：`INVALID_MAC`、`VALID_MAC_BUT_NO_COOKIE`、`VALID_MAC_WITH_COOKIE_BUT_RATELIMITED`、`VALID_MAC_WITH_COOKIE`。`receive.c` 第 112 行以 `handshake_queue_len >= MAX_QUEUED_INCOMING_HANDSHAKES / 8`（即 4096/8 = 512）判定 `under_load`，负载中且仅有合法 MAC1 而无 cookie 的握手包会被回复 cookie 消息（`wg_packet_send_handshake_cookie`），而非进入正常握手消费；cookie 中又带 ratelimiter 检查 `wg_ratelimiter_allow`，其令牌桶参数为每秒 20 包、突发 5 包（`ratelimiter.c` 第 34 至 39 行）。这些触发条件直接解释「为什么对端一直握手但本端无反应」（字段见 05-07、05-08，机制见 06-09、06-10）。

时限与分片层以 `messages.h`、`timers.c`、`send.c` 为代表。`messages.h` 定义 `REKEY_TIMEOUT = 5`、`REKEY_AFTER_TIME = 120`、`REJECT_AFTER_TIME = 180`、`KEEPALIVE_TIMEOUT = 10`、`MAX_TIMER_HANDSHAKES = 90 / REKEY_TIMEOUT`（即 18 次）、`MAX_QUEUED_INCOMING_HANDSHAKES = 4096`。`timers.c` 的 `wg_expired_retransmit_handshake` 在重传超过上限后打印 `did not complete after %d attempts, giving up` 并清空待发报文。这些常量是判断「多久算握手超时」和「断流是否由 NAT 映射过期引起」的量化依据（原理见 06-11）。

下表把 `receive.c` 中三个 `dishonest_*` 丢弃分支的精确落点收拢，这是把计数器读数翻译成根因的关键对照表。

| 丢弃标签 | 触发条件（源码行） | 累加的计数器 | 调试日志关键词 | 常见根因 |
|---|---|---|---|---|
| `dishonest_packet_peer` | `wg_allowedips_lookup_src` 结果不等于来源 peer（第 404–409 行） | `rx_errors`、`rx_frame_errors` | `Packet has unallowed src IP` | 对端 AllowedIPs 含本不应出现的源段 |
| `dishonest_packet_type` | 解封后既非 IPv4 也非 IPv6（第 369–373、394–395 行） | `rx_errors`、`rx_frame_errors` | `neither ipv4 nor ipv6` | 对端封装了非 IP 负载或数据错乱 |
| `dishonest_packet_size` | IP 头长度字段与实际 skb 长度矛盾（第 386–399 行） | `rx_errors`、`rx_length_errors` | `incorrect size` | MTU 不匹配、分片重组异常 |

### 4. 关键流程与调用链

诊断流程本身也是一条调用链，只是它跨越了观测工具与内核两条路径。理解这两条路径如何汇合，才能明白每一条排查命令到底在读什么。

**观测链（用户态向下）。** `wg show wg0` 经 `wireguard-tools/src/ipc-linux.h` 的 `mnlg_socket_open(WG_GENL_NAME, WG_GENL_VERSION)` 打开到 `wireguard` 通用族的 netlink 套接字，发送 `WG_CMD_GET_DEVICE`；内核在 `main.c` 注册的 netlink 回调中把 `wg_device` 与各 `wg_peer` 的属性序列化回用户态，工具再渲染成人类可读文本。因此 `wg show` 的每一行都是某个内核属性的快照，它没有「计算」也没有「推断」，读到的就是此刻内核里的值（netlink 原理见 06-14，命令全集见 04-01）。这也解释了为什么 `wg show` 在接口未 up 或私钥未设置时字段会缺失——那些属性本就没有被写入。

**握手链（报文中向内）。** 发起方 `send.c` 构造 `MESSAGE_HANDSHAKE_INITIATION` 经 UDP socket 发出；接收方 `socket.c` 收到后进入 `receive.c` 的 `wg_packet_receive`，经 `prepare_skb_header` 校验后入握手队列；工作线程 `wg_packet_handshake_receive_worker` 调用 `wg_receive_handshake_packet`，先做 cookie 校验，再由 `wg_noise_handshake_consume_initiation` 尝试解密静态公钥字段并查 peer 哈希表。查不到 peer（公钥不匹配或未配置）即返回 `NULL`，在日志里表现为 `Invalid handshake initiation from ...`。响应方向同理，`wg_noise_handshake_consume_response` 若状态不是 `HANDSHAKE_CREATED_INITIATION` 或解密 `encrypted_nothing` 失败即 `goto fail`，对端 `latest handshake` 始终不更新。这条链上任何一环出问题，现象都收敛为同一个：握手不建立（完整握手时序见 06-03）。

**数据链（解密后校验）。** 数据包经 `wg_packet_consume_data` 用 `key_idx` 在 index 哈希表查 keypair，入解密队列；`wg_packet_decrypt_worker` 调用 `decrypt_packet` 做 ChaCha20-Poly1305 解密，失败置为 `PACKET_STATE_DEAD`；`wg_packet_rx_poll` 中 `counter_validate` 做 RFC6479 抗重放检查，失败打印 `Packet has invalid nonce`；通过的包进入 `wg_packet_consume_data_done`，再做源地址校验与协议类型校验，任一不符落入对应 `dishonest_*` 分支。这条链上的丢弃分别对应「间歇性断流」（抗重放判定）与「隧道通但无流量」（地址校验），落点均可由计数器与动态调试日志定位。

把上述三条链与五类故障的判定信号合起来，得到图 08-03-01 的诊断决策树。使用时从顶部「观察现象」开始，按每一步的判据只走一条分支，走到叶子节点即得到首查对象，再回第 5 节取对应命令。

### 5. 配置/命令/代码实例

本节给出一套可直接照抄的分层排查命令序列，并用一段带示例输出的判读演示如何把 `wg show` 的每一行翻译成内核状态。先给出按决策树取用的命令清单：

```bash
# 第 0 步：确认接口与模块存在
lsmod | grep wireguard
ip link show wg0
wg show wg0

# 第 1 步：读 netdev 统计，定位丢弃方向
ip -s link show wg0

# 第 2 步：开启动态调试，让 net_dbg_ratelimited 可见
echo 'module wireguard +p' > /sys/kernel/debug/dynamic_debug/control
# 随后复现故障，再读内核日志（按需替换日志入口）
dmesg -T | grep -i wireguard

# 第 3 步：抓包比对四种 Noise 消息类型（type=1/2/3/4）
tcpdump -ni any udp port 51820 -vv -w /tmp/wg.pcap
```

上面这组命令的层次与第 4 节三条链一一对应：第 0 步读 netlink 属性与 netdev 存在性，第 1 步读 netdev 计数器，第 2 步打开 `net_dbg_ratelimited` 的输出开关，第 3 步在 wireguard-tools 之外直接观察 UDP 承载的报文（消息类型 1 为 handshake initiation、2 为 response、3 为 cookie、4 为 data，常量见 `messages.h`）。需要提醒的是，动态调试开关与日志入口在不同发行版上位置不同，`/sys/kernel/debug/debug` 未必挂载，`dmesg` 也可能受 `dmesg_restrict` 限制；抓包文件需要用 `tshark` 或 Wireshark 进一步解析其加密字段，具体格式需对照实际抓包工具版本核验（参数全集见 04-01、调试构建见 02-05）。

下面给出一次典型「握手失败」现场的命令与输出，并做逐行判读。

```bash
wg show wg0
ip -s link show wg0 | grep -E 'RX|errors|dropped'
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
interface: wg0
  public key: 9X3...(本端公钥省略)
  private key: (hidden)
  listening port: 51820
peer: A1b...(对端公钥省略)
  endpoint: 203.0.113.9:51820
  allowed ips: 10.0.0.2/32
  latest handshake: 4 minutes ago
  transfer: 0 B received, 148 B sent
RX:  bytes packets errors dropped  missed mcast
     0      0      7      0       0     0
```

逐行判读如下。第一行 `interface: wg0` 来自 `WG_CMD_GET_DEVICE` 返回的 `WGDEVICE_A_IFNAME`，确认查询命中正确设备；多接口环境下若这里不是预期接口，先解决选错对象的问题。第二行 `public key` 对应 `WGDEVICE_A_PUBLIC_KEY`，是本端私钥经 Curve25519 派生的结果，发给对端的必须是它；若对端配置的公钥与此不符，握手发起消息中的 `encrypted_static` 字段将无法被本端正确解密。第三行 `private key: (hidden)` 是工具的刻意保护，不参与判读，真实私钥仍在内核的 `WGDEVICE_A_PRIVATE_KEY` 中。第四行 `listening port: 51820` 对应 `WGDEVICE_A_LISTEN_PORT`；端口存在说明私钥已设置且接口曾 up，可排除「未配置私钥」这一类原因。第五行 `peer:` 对应 `WGPEER_A_PUBLIC_KEY`，第六行 `endpoint` 对应 `WGPEER_A_ENDPOINT`，此处有值说明 peer 配置存在，但要注意它可能是动态学习到的地址而非配置值；endpoint 不可达是握手失败的常见原因。第七行 `allowed ips` 对应 `WGALLOWEDIP_A_IPADDR` 与 `WGALLOWEDIP_A_CIDR_MASK`，掩码写错会让本端在找不到匹配目的地址时于 `wg_xmit` 返回 `-ENOKEY`。第八行 `latest handshake: 4 minutes ago` 对应 `WGPEER_A_LAST_HANDSHAKE_TIME`，这是本例的核心异常——本端曾成功握手（否则会显示为空），但已 4 分钟未刷新，说明会话过期后重握手未成功，应优先怀疑 endpoint 可达性、对端配置或 NAT 映射（握手时序见 06-03）。第九行 `transfer: 0 B received, 148 B sent` 对应 `WGPEER_A_RX_BYTES` / `WGPEER_A_TX_BYTES`：只发出 148 字节而未收到任何字节，正好是一次握手发起消息的大小量级，说明本端一直在发握手包但收不到响应，故障方向指向「对端未回复」或「回复在路上被丢弃」。第十行是 netdev 统计，`errors 7` 说明已有 7 个报文被丢弃，若动态调试已开启，`dmesg` 中会出现 `Invalid handshake initiation` 或 `Dropping handshake packet` 之一：前者指向公钥/时间戳校验失败（`noise.c` 的 `wg_noise_handshake_consume_initiation`），后者指向握手队列压力或 `prepare_skb_header` 校验失败（`receive.c`）。把这两条日志与计数器的增长时机对齐，即可把根因收敛到具体分支。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是「只看接口 up 就认为隧道可用」。`ip link set wg0 up` 只把 net_device 置为运行状态，既不保证私钥已设置，也不保证握手成立。判断隧道可用的唯一可靠依据是 `wg show` 中 `latest handshake` 持续刷新且 `transfer` 双向增长；`latest handshake` 长期为空就必须按握手失败分支继续排查，这与接口是否 up 无关（部署验证见 03-01）。

第二个陷阱是把「WireGuard 静默」误解为「无法定位」。静默只意味着对端收不到错误响应，本端内核的丢弃原因仍可通过动态调试与计数器还原。`receive.c`、`noise.c`、`cookie.c` 在每条丢弃路径上都留有 `net_dbg_*` 日志，只是默认不输出；不去开动态调试就断言「没有任何线索」，等于主动放弃了最直接的证据。当然，动态调试开启后日志量可能很大，务必配合 `ratelimited` 特性与 `grep` 过滤，长期开启需评估开销（调试方法见 02-05）。

第三个陷阱是混淆配置面错误码与数据面静默丢弃。像 `-ENOKEY`、`-EDESTADDRREQ`、`-EINVAL` 这类返回码出现在 `wg set` 的回显或 `dmesg` 中时，是配置或发送路径的明确信号，其完整语义归 04 册（错误码全集见 04-08）；而 `dishonest_packet_peer` 一类丢弃不会向用户态返回任何错误码，只能在计数器与调试日志里看到。把两类信号混为一谈，常见后果是拿着 `-ENOKEY` 去抓包，或在计数器已经增长时仍反复检查配置文件语法。

第四个陷阱是忽略 cookie 与 ratelimiter 造成的「假握手失败」。当本端握手队列深度达到 `MAX_QUEUED_INCOMING_HANDSHAKES / 8`（512）时，`receive.c` 进入 `under_load` 状态，此后不带有效 cookie 的合法握手包会被回复 cookie 消息而非正常处理；带 cookie 的包还要过每秒 20 包、突发 5 包的 ratelimiter。在大量 peer 同时重握手或遭受泛洪时，正常 peer 也可能被卷入，表现为握手迟迟不建立。判据是抓包中出现 `type=3`（cookie）消息且 `latest handshake` 不刷新；这类问题不能靠改密钥解决，而应从降低握手风暴或缓解泛洪入手（机制见 06-09、06-10）。

第五个陷阱是拿绝对性能数字当作吞吐故障的判据。吞吐是否「低」只能在同机型、同包长、同并发下与基准对比后判断，脱离测试条件的数字没有意义（基准方法见 08-01，调优参数见 08-02）。

最佳实践可归纳为一条纪律与一套顺序。一条纪律是「一次只改一个变量」：WireGuard 的静默特性使得同时改动公钥、AllowedIPs、路由、MTU 后无法判断哪一项生效，每次只调整一个参数并复测 `wg show` 与计数器。一套顺序是「先分类、再定向、后定因」：先用 `wg show` 把现象归入五类之一，再用 `ip -s link` 判断丢弃发生在哪个方向，最后用动态调试日志或抓包把根因落到具体源码分支。按此顺序，绝大多数故障能在不改动任何配置的前提下先被准确定位，再进入修复（具体案例见 08-04）。

### 7. 小结与延伸阅读

本篇建立了 WireGuard Linux 排障的分类框架与诊断决策树：利用「配置面会返回错误码、握手与数据面静默丢弃」这一分层事实，把可观测信号划分为 `wg show` 属性、netdev 计数器、动态调试日志与抓包三个层次，并据此把常见故障归纳为接口不通、握手失败、隧道通但无流量、间歇性断流、吞吐低五类。诊断决策树以 `latest handshake` 与 `transfer` 为第一分叉点，五条分支分别首查模块加载、公钥与 endpoint、AllowedIPs 与路由、keepalive 与抗重放、MTU 与 CPU 特性。`receive.c` 的 `dishonest_packet_peer` / `dishonest_packet_type` / `dishonest_packet_size` 三个丢弃分支各自累加特定计数器，`cookie.c` 的四态 MAC 判定与 `ratelimiter.c` 的令牌桶参数，是把计数器读数翻译成根因的核心对照表。

延伸阅读建议按四条线走：需要逐字段确认某个属性含义时读 05 册（`noise_handshake`、`wg_peer`、`wg_allowedips` 等字段定义），需要完整错误码与命令参数时读 04 册，需要理解握手状态机、抗重放与 cookie 机制时读 06 册，需要确认某段逻辑属于哪个源文件时读 07 册。本篇作为运维与排障的唯一权威源，只提供分类、决策树与判读方法，不重复上述各册细节。跨册随查按（字段见 05-03 ｜ 参数见 04-08 ｜ 原理见 06-09 ｜ 模块见 07-08）执行：结构体逐字段去 05、参数与错误码全集去 04、机制与调用链去 06、目录级模块能力去 07、运维场景与基准去 08。凡本篇标注「需对照实际版本核验」的命令输出格式、日志入口与抓包工具行为，均以目标系统实际版本为准，本套资料不编造未核验的路径与取值。

## 08-04 故障案例库：握手失败到吞吐骤降

### 1. 背景与动机

决策树给出的是方法，案例库给出的是经验。本篇把 08-03 建立的五类故障落到五个可复现的具体场景上，每个场景都按「现象—根因—排查命令—修复」四段展开，让读者能把抽象的分类信号对应到真实现场。五个案例依次覆盖从完全不通到性能退化的全谱：案例一是公钥与私钥不匹配导致握手失败，属于「握手失败」类；案例二是 AllowedIPs 配错导致隧道通但无流量，属于「隧道通但无流量」类；案例三是 NAT 或防火墙阻断 UDP 导致握手超时，同属「握手失败」类但根因截然不同；案例四是 MTU 过大导致分片丢失、吞吐骤降，属于「吞吐低」类；案例五是时钟偏差导致握手被判为重放攻击，是「握手失败」类中隐蔽性最强的一种。

贯穿全部案例的核心线索是 WireGuard 的静默失败特性：无论根因是密钥、地址、路径还是时钟，对端几乎收不到任何错误响应，只表现为「握手建立不起来」或「有握手但没流量」这类同质化现象。因此案例之间的区分不能靠「看错误提示」，而要靠两个手段：一是把 `wg show` 的字段与 netdev 计数器按 08-03 的判读方法翻译成内核状态，二是抓包比对 Noise 消息的交互序列。后者尤其关键——WireGuard 在网线上只跑四种消息（`MESSAGE_HANDSHAKE_INITIATION` = 1、`MESSAGE_HANDSHAKE_RESPONSE` = 2、`MESSAGE_HANDSHAKE_COOKIE` = 3、`MESSAGE_DATA` = 4，定义见 `messages.h`），通过比较「我发出了 type=1 但收不到 type=2」「收到了 type=2 但随后没有 data」「只收到 type=3」等序列差异，就能把静默失败还原成一条可推理的协商过程（消息格式见 06-04）。

本篇的口径与 08-03 一致：结论以 `wireguard-linux` stable 分支内核驱动快照与 `wireguard-tools` 1.0.20260223 为准，命令输出格式、日志入口、抓包工具解析能力均标注「需对照实际版本核验」。错误码语义归 04 册、字段定义归 05 册、机制原理归 06 册、模块职责归 07 册，本篇只做运维视角的现象还原与修复动作，涉及即交叉引用。文中所有密钥串、地址、端口均为示例占位，不对应任何真实网络（密钥生成与分发流程见 03-03，接口地址与路由配置见 03-04）。

### 2. 核心概念

读懂案例需要先抓住三个概念：静默失败的三种典型表现、Noise 消息序列作为「对话记录」的判读方法，以及故障定位中方向与层次的对应关系。

**静默失败的三种表现。** 第一种是「发出无回应」：本端持续发送握手发起消息，但收不到响应，`transfer` 只增发送字节，`latest handshake` 为空。第二种是「回应不被接受」：本端收到了响应消息，但解密或状态检查失败，握手仍未建立，这类失败最容易被误判为网络不通，实则报文已经到达。第三种是「 handshake 成功但数据不通」：握手已刷新，但数据包因源地址校验或路由问题被丢弃，`transfer` 的一方或双方不增长。三种表现对应不同的抓包序列，是案例分类的底层依据。

**Noise 消息序列作为对话记录。** 一次成功握手在抓包上呈现清晰的请求—响应模式：发起方发 `type=1`（handshake initiation），响应方回 `type=2`（handshake response），随后双方用 `type=4`（data）传输数据或 keepalive；若响应方处于负载压力，会用 `type=3`（cookie）要求发起方先取 cookie 再重试。把这段序列当对话看，「只有 1 没有 2」说明请求没到对端或没被接受，「有 1 有 2 却没有 4」说明会话建立后数据面有问题，「出现 3」说明触发了 cookie 防护。这种判读不依赖任何解密，只看消息类型与方向即可完成，是静默协议排障最有力的工具（cookie 机制见 06-09）。

**方向与层次的对应关系。** 每个案例都要同时回答「哪个方向」和「哪一层」。方向指发送侧还是接收侧：例如 AllowedIPs 配错在发送侧表现为 `wg_xmit` 返回 `-ENOKEY`（`device.c` 第 155 行），在接收侧表现为 `receive.c` 的 `dishonest_packet_peer` 丢弃并计入 `rx_errors`。层次指配置面、握手面还是数据面：配置面错误通过 netlink 回显，握手与数据面错误只能靠计数器与日志。把方向、层次与消息序列三者对齐，才能避免「看到握手失败就改密钥」这类定向错误。

下面这张表把五个案例的核心指纹收拢，可作为现场快速比对的速查卡。

| 案例 | 现象指纹 | `wg show` 关键信号 | 抓包序列指纹 | 主要故障类别 |
|---|---|---|---|---|
| 一 密钥不匹配 | 双方接口都 up，`latest handshake` 始终空 | 两端 `public key` 与对方配置不符 | 有 type=1，无 type=2 | 握手失败 |
| 二 AllowedIPs 配错 | 握手成功但 ping 不通 | `latest handshake` 正常，`transfer` 近乎不动 | 有 type=1/2，几乎无 type=4 | 隧道通但无流量 |

### 3. 关键数据结构与源码位置

案例的根因都要落到具体源码，否则修复动作就只是「试出来的偏方」。这里按案例把关键结构、函数与常量列成地图，逐字段定义去 05 册，机制去 06 册，目录职责去 07 册。

案例一与案例五落在握手与会话层。案例一的失败点在 `noise.c` 的 `wg_noise_handshake_consume_initiation`（第 584 行起）：`message_decrypt(s, src->encrypted_static, ...)`（第 612 行）解密对端静态公钥字段，若本端私钥与对端所用公钥不构成匹配曲线对，解密失败即 `goto out` 返回 `NULL`；响应方向的 `wg_noise_handshake_consume_response`（第 728 行起）在 `message_decrypt(NULL, src->encrypted_nothing, ...)`（第 780 行）失败时 `goto fail`。案例五落在同一函数的时间戳检查：`tai64n_now(timestamp)`（第 565 行）生成 TAI64N 时间戳并加密进发起消息，接收侧第 633 行用 `memcmp(t, handshake->latest_timestamp, NOISE_TIMESTAMP_LEN) <= 0` 判定 `replay_attack`，若对端时钟显著倒退，时间戳不大于已记录值，握手被当作重放而丢弃（字段见 05-05，握手状态机原理见 06-02、密钥时序见 06-03）。

案例二落在路由与 peer 层。发送侧 `device.c` 的 `wg_xmit` 在第 153 行调用 `wg_allowedips_lookup_dst`，找不到匹配 peer 返回 `-ENOKEY` 并打印 `No peer has allowed IPs matching ...`；接收侧 `receive.c` 第 404 行调用 `wg_allowedips_lookup_src`，若来源地址不属于该 peer 的 AllowedIPs，`routed_peer != peer` 成立，跳到 `dishonest_packet_peer` 累加 `rx_errors` 与 `rx_frame_errors`（字段见 05-03、05-04，路由原理见 06-07）。

案例三落在时限与 socket 层。`messages.h` 定义 `REKEY_TIMEOUT = 5`、`MAX_TIMER_HANDSHAKES = 90 / REKEY_TIMEOUT`（18）、`REJECT_AFTER_TIME = 180`、`KEEPALIVE_TIMEOUT = 10`；`timers.c` 的 `wg_expired_retransmit_handshake`（第 41 行起）在重传超过上限时打印 `did not complete after %d attempts, giving up` 并清空待发报文，注释明确写出「没有 keypair 就丢包且不再重试」。endpoint 的源地址学习在 `wg_socket_set_peer_endpoint_from_skb`（`receive.c` 第 150、172 行）与 `wg_socket_clear_peer_endpoint_src`（重传时清除），NAT 映射过期后若没有 persistent keepalive 维持，endpoint 会失效（原理见 06-11、06-12）。

案例四落在分片与发包层。`send.c` 的 `calculate_skb_padding`（第 141 行起）用 `PACKET_CB(skb)->mtu` 与 `MESSAGE_PADDING_MULTIPLE`（16）计算填充，`encrypt_packet`（第 162 行起）组装密文，`PACKET_CB(skb)->mtu = skb->dev->mtu`（第 232 行）说明 MTU 取自 wg0 接口的 MTU；封装后 UDP 报文若超过路径 MTU 且 DF 位置位，会在物理网络中被丢弃，而 `receive.c` 的 `dishonest_packet_size` 分支（第 428 行）累加 `rx_length_errors`，是分片异常在 counters 上的落点（调优参数见 08-02，收发模块见 07-07）。

案例五的机制已在案例一中点出，补充常量：`NOISE_TIMESTAMP_LEN = sizeof(u64) + sizeof(u32)`（`messages.h` 第 20 行），时间戳由 64 位秒加 32 位纳秒构成，对端时钟偏移超过合理范围即可触发重放判定或使会话被提前视为过期（原理见 06-03）。

### 4. 关键流程与调用链

五个案例的排查都遵循 08-03 的「先分类、再定向、后定因」顺序，落到调用链上就是三条环环相扣的路径。

第一条是握手协商链。发起方 `send.c` 构造 `MESSAGE_HANDSHAKE_INITIATION`（含 `encrypted_static` 与 `encrypted_timestamp`），经 UDP socket 发出；响应方 `socket.c` 收到后由 `receive.c` 的 `wg_packet_receive` 做头部校验并入握手队列，工作线程经 cookie 校验后调用 `wg_noise_handshake_consume_initiation` 尝试解密与查 peer 表，成功则构造 `MESSAGE_HANDSHAKE_RESPONSE` 返回；发起方收到响应后由 `wg_noise_handshake_consume_response` 验证并调用 `wg_noise_handshake_begin_session` 派生会话密钥。案例一、三、五的失败点都在这一段，但位置不同：案例一在静态字段解密，案例三在报文根本没到，案例五在时间戳比较。抓包序列正是这条链的外在投影（完整握手时序见 06-02、06-03）。

第二条是数据封装链。出站包按路由交给 wg0 的 `ndo_start_xmit`，`wg_xmit` 查 AllowedIPs 选 peer，无匹配返回 `-ENOKEY`；有 peer 但无 endpoint 返回 `-EDESTADDRREQ`；随后经 `encrypt_packet` 填充加密、UDP 封装发出。入站包经解密、`counter_validate` 抗重放、源地址校验后注入协议栈。案例二在「查 peer」这一步失败，案例四在「封装后报文过路径 MTU」这一步失败，两者的抓包差异是：案例二几乎没有 data 消息，案例四有大 data 消息发出但无对应回包（发送路径见 06-05，接收路径见 06-06）。

第三条是反馈与观测链。配置面的错误沿 netlink 回显到 `wg set`；数据面与握手面的丢弃只在本端内核留下 `net_dbg_*` 日志与 netdev 计数器，需要通过动态调试与 `ip -s link` 读取。五案例 shared 的观测入口是 `wg show` 的 `latest handshake` 与 `transfer` 两行，它们分别对应 `WGPEER_A_LAST_HANDSHAKE_TIME` 和 `WGPEER_A_RX_BYTES` / `WGPEER_A_TX_BYTES`。把三条链按「哪个环节 broke」对齐到五个案例，即得到图 08-04-01 的案例—根因映射。

### 5. 配置/命令/代码实例

本节给出五个案例的完整现场。所有命令需在两端同时观察时，分别标为「本端」与「对端」；示例输出中的密钥与地址均为占位。

**案例一：公钥/私钥不匹配导致握手失败**

现象：两端 `ip link set wg0 up` 都成功，`wg show wg0` 显示接口与 peer 配置齐全，但 `latest handshake` 始终为空或永远停在初次配置时刻，`transfer` 只有发送字节增长。这是典型的静默失败——任何一端都不报告「密钥错了」。

根因：本端配置的私钥派生出的公钥，与对端 `peer` 段里配置的公钥不是一对。发起方用本端私钥与对端公钥做 Curve25519 运算 encrypt static 字段，响应方按 `noise.c` 第 612 行解密该字段失败即返回 `NULL`，`receive.c` 第 145 行只打印 `Invalid handshake initiation` 调试日志后丢弃。对端完全收不到「你的公钥不对」的反馈。

排查命令：先核对两端密钥的派生关系，再用抓包确认消息序列。

```bash
# 本端：由私钥重新派生公钥并打印
wg pubkey < /etc/wireguard/privatekey

# 对端：查看它为本端配置的 peer 公钥
wg show wg0 | grep -A6 'peer:'

# 抓包确认：只有 type=1 没有 type=2 即坐实请求未被接受
tcpdump -ni any udp port 51820 -vv -c 20
```

上面三条命令的输出需要交叉比对，下面给出一次现场的命令与输出并逐行判读。

```bash
wg pubkey < /etc/wireguard/privatekey
wg show wg0 | grep -E 'public key|latest handshake|transfer'
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
interface: wg0
  public key: 9X3abc...(=本端私钥派生结果)
  private key: (hidden)
  listening port: 51820
peer: B2q...(对端配置的本端公钥，与上一行不同)
  endpoint: 203.0.113.9:51820
  allowed ips: 10.0.0.2/32
  latest handshake: (never)
  transfer: 0 B received, 2.87 KiB sent
```

逐行判读如下。第一行 `interface: wg0` 对应 `WGDEVICE_A_IFNAME`，确认查的是正确接口。第二行 `public key` 是本端私钥经 Curve25519 派生的真实公钥，对应 `WGDEVICE_A_PUBLIC_KEY`，也是本端应当发给对端登记的值。第三行 `private key: (hidden)` 不参与判读。第四行 `listening port` 有值，说明私钥已设置、接口曾 up，排除「未配置密钥」这一伪故障。第五行 `peer:` 后的公钥对应 `WGPEER_A_PUBLIC_KEY`，是本端认为的对端身份；本例要比对的是「对端配置里登记的本端公钥」与这里第二行的派生结果是否一致——示例中对端把本端公钥误写成了另一个值 `B2q...`，这正是根因。第六行 `endpoint` 有值，说明配置齐全，排除「没配 peer」的伪故障。第七行 `allowed ips` 对应 `WGALLOWEDIP_A_IPADDR`，此时它不相关，因为握手尚未建立。第八行 `latest handshake: (never)` 对应 `WGPEER_A_LAST_HANDSHAKE_TIME` 为空，是握手从未成功的直接证据。第九行 `transfer` 中只发不收，字节量级是多次握手发起消息累积，说明本端在反复重试；结合抓包「只见 type=1 不见 type=2」，可把根因收敛到对端 decryption 失败，即公钥配置错误（握手失败分支定位见 08-03）。

修复：把对端 `peer` 的公钥改为本端 `wg pubkey` 的实际输出，用 `wg set wg0 peer <正确公钥> ...` 或修正 `wg0.conf` 后 `wg syncconf wg0 wg0.conf` 热加载，无需重启接口。修复后 `latest handshake` 应在 `REKEY_TIMEOUT`（5 秒）量级内刷新。注意私钥永远不出现在配置文件分发中，只在对端写本端公钥（密钥分发纪律见 03-03）。

**案例二：AllowedIPs 配错导致隧道通但无流量**

现象：握手正常，`latest handshake` 持续刷新，但 `ping 10.0.0.2` 不通，`transfer` 长时间不动。这是「隧道通但没流量」的典型，比握手失败更隐蔽，因为握手成功会给人「链路正常」的错觉。

根因分两支。发送侧：本端 AllowedIPs 未包含目标地址，`wg_xmit` 在 `device.c` 第 153 行 `wg_allowedips_lookup_dst` 返回空，第 155 行返回 `-ENOKEY` 并打印 `No peer has allowed IPs matching ...`，包根本没进隧道。接收侧：对端 AllowedIPs 未包含本端源地址，本端发出的包到达对端后，`receive.c` 第 404 行 `wg_allowedips_lookup_src` 得到的 peer 与来源 peer 不等，落入 `dishonest_packet_peer`，`rx_errors` 增长。

排查命令：

```bash
# 看本端 AllowedIPs 与路由是否覆盖目标
wg show wg0 allowed-ips
ip route get 10.0.0.2

# 看丢弃计数器是否增长（接收侧配错的证据）
ip -s link show wg0 | grep -E 'errors|frame'

# 开动态调试后复现，观察否定分支日志
echo 'module wireguard +p' > /sys/kernel/debug/dynamic_debug/control
dmesg -T | grep -i 'unallowed src\|No peer has allowed'
```

修复：把目标网段写入发送侧 `allowed-ips`，把本端源地址段写入对端 `allowed-ips`，注意两端是对称的「彼此允许」关系，而非任意一端单方面配置。典型点对点写法是两端各自 `allowed-ips 10.0.0.2/32` 与 `10.0.0.1/32` 互换（配置语义见 04-02，路由部署见 03-04）。若使用 wg-quick，`Address=` 与 `AllowedIPs=` 分工不同，前者配接口地址、后者配路由目标，不可混淆（wg-quick 参数见 04-03）。

**案例三：NAT/防火墙阻断 UDP 导致握手超时**

现象：隧道曾正常工作，某个时刻后 `latest handshake` 停在很旧的时间且不再刷新，`transfer` 只发不收。与案例一的区别是「曾经通过」——说明密钥本身正确，问题出在路径可达性或 endpoint 失效上。

根因：WireGuard 承载在 UDP 上，默认端口 51820（`WGDEVICE_A_LISTEN_PORT`）。若中间防火墙丢弃 UDP、或 NAT 映射在空闲后过期且没有 persistent keepalive 维持，发起方的握手发起消息无法到达对端，或响应回不来。`timers.c` 的 `wg_expired_retransmit_handshake` 每 `REKEY_TIMEOUT + jitter` 重传一次，超过 `MAX_TIMER_HANDSHAKES`（18）后打印 `did not complete after ... attempts, giving up` 并清空待发报文——此后即使路径恢复，用户态也不会自动重新积极尝试，直到有新的数据触发或配置变更。抓包上的指纹是持续出现 type=1 而无 type=2。

排查命令：

```bash
# 确认监听端口与实际可达性
wg show wg0 | grep 'listening port'
ss -lunp | grep 51820

# 从本端直接探测对端 UDP 端口（需对端有响应手段）
nc -vzu 203.0.113.9 51820

# 抓包看是否只有 out 没有 in
tcpdump -ni any udp port 51820 -nn -c 30
```

修复：在防火墙放行 UDP 端口；对 NAT 后的 peer 配置 `PersistentKeepalive = 25`（秒），使其小于常见 NAT 映射超时（30 秒量级），让 keepalive 周期刷新映射（keepalive 原理见 06-11）。修复后可用 `wg set wg0 peer <公钥> endpoint <新地址:端口>` 强制重设 endpoint，触发立即重握手。若对端在多出口 NAT 后，endpoint 应从连接侧主动发起而非双向都配 endpoint（部署实例见 03-06）。

**案例四：MTU 过大导致分片丢失、吞吐骤降**

现象：握手完全正常，小包（如少量 ICMP）能通，但大文件或大包测试时吞吐骤降甚至完全停滞，`transfer` 增长缓慢，`ip -s link` 中 `errors` 或 `dropped` 增长。这是「吞吐低」类中最常见的配置根因。

根因：WireGuard 在原始 IP 包外再封装 UDP 与 Noise 头，开销使实际报文大于内层 MTU。`send.c` 的 `calculate_skb_padding` 以 `PACKET_CB(skb)->mtu`（取 `skb->dev->mtu`，即 wg0 的 MTU）为基准计算填充，封装后报文若超过路径 MTU 且 DF 位不允许分片，会在中间链路被静默丢弃；被对端收到的截断包则可能落入 `receive.c` 的 `dishonest_packet_size`，累加 `rx_length_errors`。结果是「小包通、大包丢」，宏观上表现为吞吐骤降而非完全中断。

排查命令：

```bash
# 查看 wg0 与底层物理接口的 MTU
ip link show wg0 | grep mtu
ip link show eth0 | grep mtu

# 用不同包长探测路径 MTU 黑洞（DF 位固定，逐步减小）
ping -M do -s 1372 10.0.0.2
ping -M do -s 1200 10.0.0.2

# 观察长度错误计数
ip -s link show wg0 | grep -E 'length|errors'
```

修复：在 wg0 上设置更小的 MTU，典型值是底层链路 MTU 减去 WireGuard 封装开销；例如物理口 1500 时，wg0 设为 1420 或更小是常见起点，具体值需在目标链路上用 `ping -M do` 实测确定（本套资料不给绝对数字，基准方法见 08-01，调优参数见 08-02）。若使用 wg-quick，可在接口配置里写 `MTU = 1420` 固化（参数见 04-03）。同时确认 GSO 相关设置与网卡卸载特性是否匹配，避免软件分片带来额外开销（原理见 06-12、06-13）。

**案例五：时钟偏差导致握手被判为重放攻击**

现象：对端系统时间大幅偏离（如NTP 异常导致倒退数小时），握手反复失败，`latest handshake` 偶发刷新后立刻又变旧，抓包可见 type=1 与偶发 type=2，但连接始终不稳。这是比案例一更隐蔽的一种，因为密钥正确、报文可达，问题出在时间戳语义上。

根因：`send.c` 第 565 行用 `tai64n_now(timestamp)` 生成 TAI64N 时间戳并加密进发起消息；接收侧 `noise.c` 第 633 行用 `memcmp(t, handshake->latest_timestamp, NOISE_TIMESTAMP_LEN) <= 0` 判定 `replay_attack`，只要新时间戳不大于已记录值就丢弃。对端时钟大幅倒退时，其发出的时间戳持续小于本端最后一次记录值，握手被当作重放而拒绝；此外会话密钥的有效期判断也依赖时间，偏差会加速 `REJECT_AFTER_TIME` 到期。需要强调的是，WireGuard 用 TAI64N 是为了单调性，但它假设两端时钟大致同步，这个假设在本案例中不成立。

排查命令：

```bash
# 比对两端时间（需两端各执行一次）
date -u +%s
timedatectl status

# 抓包观察握手是否反复建立又迅速失效
tcpdump -ni any udp port 51820 -nn -c 30

# 开调试确认重放判定日志
dmesg -T | grep -i 'replay\|invalid handshake'
```

修复：用 NTP/ chrony 校准两端时钟，确保时间同步后再重建握手；这是唯一根治手段，改密钥或改 AllowedIPs 都无效（时序原理见 06-03）。修复后可 `wg set` 重新下发 peer 以触发立即重握手，观察 `latest handshake` 稳定刷新。运维上应把时钟同步纳入上线 checklist，避免此类隐蔽故障（上线检查见 08-06，加密原语见 07-12）。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是「同一现象套同一修复」。五个案例中有三个都表现为「握手失败」，但根因分别落在静态字段解密、报文可达性、时间戳比较三个不同环节。看到 `latest handshake` 为空就一律重装密钥，会案例三、五上完全无效。正确做法是先用抓包序列区分「只有 type=1」「有 type=1/2 但无 data」「有 type=3」三类指纹，再选修复路径（决策树见 08-03）。

第二个陷阱是忽略抓包中「响应到达但被拒绝」的情形。运维者常把「没收到回包」等同于「对端没收到请求」，但案例一与案例五中，本端其实可能收到了 type=2，只是本地解密或时间戳检查失败而未建会话。若只在本端抓包，会误判为网络不通；应在两端同时抓包比对，确认请求是否到达、响应是否发出、是否被接受。WireGuard 的静默特性使得「对端内核里发生了什么」只能靠它自己的日志与计数器还原（消息格式见 06-04）。

第三个陷阱是诊断 AllowedIPs 时只看一端。案例二强调过 AllowedIPs 的「双向对称」：发送侧决定包能否进隧道，接收侧决定包能否被接受。只修一侧会出现「能发不能收」或反过来，表现依然是不通。排查时务必在两端分别执行 `wg show wg0 allowed-ips` 与查看 `rx_errors`（路由原理见 06-07）。

第四个陷阱是 MTU 故障被误判为「网络不稳定」。案例四的丢包是确定性的、与包长相关，而非随机抖动。用固定包长从大到小做 `ping -M do` 探测，能清晰定位路径 MTU 黑洞；不要凭「有时快有时慢」的主观感受下结论（调优参数见 08-02）。

第五个陷阱是把示例数字当成普适值。端口 51820、keepalive 25 秒、wg0 MTU 1420、重传 18 次等，都是源码默认值或常见起点，具体部署需在目标环境核验；本套资料不声称任何绝对值适用所有场景（基准方法见 08-01）。所有命令输出格式、日志入口与抓包工具的解析能力均标注「需对照实际版本核验」。

最佳实践是一条三段式纪律：先用 `wg show` 的两个关键行把现象归入 08-03 的五类之一；再用双端抓包比对 Noise 消息序列，把「静默失败」还原成可推理的协商过程；最后才动配置，且每次只改一个变量并复测。修复后统一以 `latest handshake` 持续刷新、`transfer` 双向增长、`ip -s link` 计数器不再增长三项同时成立作为验收标准，缺一不可。

### 7. 小结与延伸阅读

本篇把 08-03 的决策树落到五个具体案例：公钥私钥不匹配（握手链静态字段解密失败）、AllowedIPs 配错（数据链查 peer 或源地址校验失败）、NAT/防火墙阻断 UDP（握手链报文不可达）、MTU 过大（数据链分片丢失）、时钟偏差（握手链时间戳被判重放）。每个案例都用「现象—根因—排查命令—修复」四段还原，并反复强调 WireGuard 的静默失败特性：对端不回错误，定位只能依赖 `wg show` 字段、netdev 计数器、动态调试日志与抓包序列四类证据。五个案例的抓包指纹各不相同——「只有 type=1」「有 1/2 无 4」「出现 type=3」「大包丢失」「type=2 偶发后失效」——这是把同质化现象拆成可区分根因的关键。

## 08-05 安全加固、密钥管理与边界约束

### 1. 背景与动机

WireGuard 的安全哲学可以浓缩成一句话：密钥即身份。协议把认证完全建立在 Curve25519 密钥对之上，既不内建证书颁发机构，也不内建中心化的密钥分发服务器，更不内建用户账号体系。这种极简设计大幅缩小了攻击面与审计面——内核驱动连同头文件约四千余行代码，是少数可以被完整审阅的 VPN 实现——但它同时把一大块安全责任从协议设计者转移到了运维者肩上。换句话说，协议本身很难被攻破，而绝大多数真实世界的安全事故，根源都不在密码学，而在私钥被写进版本库、公钥张冠李戴、AllowedIPs 放得太宽、以及日志里漏出了不该漏的东西。本篇作为运维册的安全权威源，不重复讲密码学原理（原理见 06-02、06-03），而是把「怎么把这套密钥模型安全地用起来」讲成可执行的边界约束。

要理解密钥的根从哪来，必须回到用户态工具的 `wireguard-tools/src/genkey.c`。该文件的 `get_random_bytes` 实现了一条清晰的三级熵源回退链：在 OpenBSD、macOS 10.12 以上、或 glibc 2.25 以上的环境，优先调用 `getentropy(out, len)`；若不可用且是 Linux，则退化到直接发起 `syscall(__NR_getrandom, out, len, 0)` 系统调用；若前两级都不可行，最后才 `open("/dev/urandom", O_RDONLY)` 逐字节读取。这条链还有一个前置保护：当请求长度 `len > 256` 时直接设置 `errno = EOVERFLOW` 返回失败，避免一次性索取过多熵。对运维的实际含义是：在受支持的现代系统上，密钥材料来自内核加密随机数发生器，而不是某个用户态伪随机库；只要系统熵池正常，`wg genkey` 生成的私钥就具备密码学强度。但「工具用对了」只是第一环，私钥落到磁盘之后的权限管理才是事故高发区。

`genkey_main` 在生成之前做了一件容易被忽略的安全提示：它用 `fstat(STDOUT_FILENO, &stat)` 检查标准输出是否为普通文件，若该文件带有 `S_IRWXO`（其他用户可读、写或执行）位，就向标准错误打印 `Warning: writing to world accessible file. Consider setting the umask to 077 and trying again.`。这不是失败错误，而是一句劝告——它明确告诉运维者：把私钥重定向到一个全局可读的文件是危险的，正确做法是先设 `umask 077` 再生成。这句警告本身就是理解 WireGuard 安全模型的钥匙：协议不管你的私钥落在哪里，它只保证生成过程不可预测；保护私钥的最后一公里，是运维纪律与主机权限共同构成的边界。

再看密钥的「形状」。`genkey_main` 在 `get_random_bytes` 之后，仅当子命令名是 `genkey` 时才调用 `curve25519_clamp_secret(key)`；而 `genpsk` 生成的预共享密钥不做这一步。这个差异在 `curve25519.h` 里只有两行，却决定了两类密钥的数学性质：`secret[0] &= 248` 清掉首字节低三位，`secret[31] = (secret[31] & 127) | 64` 清掉末字节最高位、并把次高位置一。这是标准 X25519 标量钳制（clamp），保证私钥落在正确的标量域、清除协因子相关的低位、固定标量大小，从而让 Curve25519 的标量乘法具备良好的群性质。也就是说，私钥不是随便 32 字节，而是经过钳制的标量；而 PSK 则是对称密钥，不需要也不应该被钳制。混淆这一点，会在自己实现密钥生成时埋下互不兼容的隐患。

### 2. 核心概念

WireGuard 的安全模型里有四类「秘密」，性质各不相同，必须分开管理。第一类是接口私钥（private key），32 字节经钳制的 Curve25519 标量，只在本地生成、本地保存，是身份的根，泄露即等于身份被冒用。第二类是接口公钥（public key），由私钥经 `curve25519_generate_public` 从固定基点 9 派生，可以公开分发，分发给对端作为配置里的 `PublicKey`。第三类是预共享密钥（PSK），同样是 32 字节随机值，但由 `wg genpsk` 生成、不经钳制，作为额外的对称密钥材料混入握手，为协议提供后量子防御。第四类是临时的 cookie 机密（checker secret），由 `wg_cookie_checker_init` 用 `get_random_bytes` 生成、长度 `NOISE_HASH_LEN`，只在内存中存在、定期轮换，用于 DoS 防护，永远不落盘。前三类需要运维建立生命周期，第四类完全由内核自动管理。

PSK 的价值需要准确理解，否则极易被误用。WireGuard 的握手是 Noise_IK，其椭圆曲线部分是 Curve25519 的 ECDH。在经典计算模型下，从公钥反推私钥不可行；但大规模量子计算机理论上能用 Shor 算法攻破离散对数，从而威胁这类 ECDH。PSK 的作用正是在此：即使 ECDH 被攻破，握手中混入的对称预共享密钥仍然只有通信双方知道，攻击者无法从公开信道恢复它，会话密钥因此保持机密。这就是所谓「后量子防御」——它不是量子安全密码的全部，而是一道纵深防线。需要强调，PSK 并不会提升经典环境下的安全性（ Curve25519 本身已经足够强），它防的是「未来量子计算机 + 现在抓包留存」这种威胁模型。因此 PSK 的正确定位是纵深加固，而不是私钥质量的替代品；一对配置错误或泄露的公私钥，不会因为加了 PSK 就变得安全。

基于以上模型，可以把运维侧的安全边界归纳为六条。其一，私钥保护：私钥只在接口所在主机生成、以 0600 权限落盘、永不进入配置文件分发链路、永不写入日志或聊天工具。其二，密钥轮换：私钥与 PSK 都需要有计划的更换流程，轮换要利用不中断会话的机制（见 08-06 的配置变更流程），并注意对端公钥的同步时序。其三，PSK 使用：为高价值链路配置 PSK，且 PSK 必须通过独立于公钥的带外信道分发，避免「公私钥和 PSK 走同一条渠道」导致一锅端。其四，firewall 与 AllowedIPs 最小权限：主机防火墙只开放必要的 UDP 端口与来源，AllowedIPs 收敛到对端真正需要的地址段，不写 `0.0.0.0/0` 除非确实要跑全流量。其五，内核模块权限：加载模块需要 `CAP_SYS_MODULE`，修改接口需要 `CAP_NET_ADMIN`，应据此收敛运行账户与 systemd 单元的权限，而非让配置进程以完全 root 长期驻留。其六，日志敏感信息：`wg show` 刻意隐藏私钥（`private key: (hidden)`），但 `wg showconf` 默认会输出私钥原文，任何把 showconf 输出贴到工单、日志采集系统或终端回放的行为都等同于泄露私钥。

除密钥边界外，还有一条入口防线必须纳入安全加固视野：DoS 防护。WireGuard 是静默协议，对未授权包不回错误、只丢弃，这本身抑制了反射放大，但攻击者仍可用伪造源地址的海量握手请求耗尽服务端 CPU。内核用两道机制应对：`cookie.c` 实现无状态 cookie 挑战，在握手路径上要求对端证明能收到发往其源地址的响应；`ratelimiter.c` 实现按源 IP 的令牌桶限速，限制单位时间内的握手尝试。这两者的原理分别在 06-09、06-10，模块职责在 07-09、07-10，本节只把它们作为「入口安全边界」的一环纳入检查清单，不重复展开状态机。理解它们的存在，有助于运维明白：WireGuard 的抗 DoS 是内建的，但仍需要与主机防火墙的限速规则配合，才能形成完整防线。

### 4. 关键流程与调用链

熵源回退链是密钥安全的起点。`genkey_main` 先把 32 字节的输出缓冲区 `key` 准备好，调用 `get_random_bytes(key, WG_KEY_LEN)`。在 `get_random_bytes` 内部，若编译目标满足 glibc 2.25 以上等条件，第一条尝试是 `getentropy(out, len)`，成功即返回；否则在 Linux 上走第二条 `syscall(__NR_getrandom, out, len, 0)`，返回值等于 `len` 即成功；最后一条路径是打开 `/dev/urandom`，用循环 `read` 直到凑满 `len` 字节，任何一步出错都会置 `errno` 并返回失败。这条链的设计意图是「优先使用现代、不会被 fork 后复用状态的接口，退而求其次仍保证来自内核熵池」。回到 `genkey_main`，取得随机字节后：若是 `genkey` 则 `curve25519_clamp_secret(key)` 钳制；随后 `key_to_base64` 编码，`puts(base64)` 输出。整条链没有任何环境配置开关，运维能施加的影响只有两点：保证系统熵源健康、保证输出文件权限正确。

cookie 验证链体现了「先便宜后昂贵」的防线设计。`wg_cookie_validate_packet` 首先用消息携带的公钥派生出 `message_mac1_key`，调用 `compute_mac1` 对整个消息（去掉 mac 尾部相关长度）做 BLAKE2s，与报文中的 `mac1` 比较；不等则返回 `INVALID_MAC` 直接丢弃——这一步纯对称运算、极廉价，能挡掉绝大多数根本不知道本端公钥的垃圾包。相等则状态置为 `VALID_MAC_BUT_NO_COOKIE`；若调用方不要求检查 cookie（`check_cookie == false`）就此返回。需要检查时，`make_cookie` 先判断 `checker->secret_birthdate` 是否超过 `COOKIE_SECRET_MAX_AGE`，超期则在写锁内更新生日并重新 `get_random_bytes` 生成机密，然后用 BLAKE2s 把源 IP（IPv4 的 `saddr` 或 IPv6 的 `saddr`）与 UDP 源端口摘要成 cookie；`compute_mac2` 再以该 cookie 为密钥算一次 MAC 与报文 `mac2` 比较。都不等则返回 `VALID_MAC_BUT_NO_COOKIE`；相等后还要过 `wg_ratelimiter_allow` 这一关，若被限速则返回 `VALID_MAC_WITH_COOKIE_BUT_RATELIMITED`，否则才是 `VALID_MAC_WITH_COOKIE`。四态枚举把「包是否可信、是否需挑战、是否被限速」表达得清清楚楚（原理见 06-09）。

令牌桶的判定同样值得写成一条链。`wg_ratelimiter_allow` 按 `skb` 的协议提取源地址：IPv4 取 `saddr`，IPv6 取前 64 位（注释明确说只取 64 位以便对整个 /64 限速），再与网络命名空间指针 `net` 一起经 `hsiphash` 定位到哈希表桶。命中已有条目后，在条目自旋锁内计算 `tokens = min(TOKEN_MAX, 旧 tokens + now - last_time_ns)`，更新 `last_time_ns`，若 `tokens >= PACKET_COST` 则放行并扣除一个 `PACKET_COST`。这里的 `PACKET_COST = NSEC_PER_SEC / PACKETS_PER_SECOND`，即 20 包每秒对应每包 50 毫秒；`TOKEN_MAX = PACKET_COST * PACKETS_BURSTABLE`，即允许 5 个包的突发。新条目以 `TOKEN_MAX - PACKET_COST` 初始化，创建即允许一个包。整个结构用 RCU 与 per-条目自旋锁保护，后台 `gc_work` 每秒回收空闲超过 1 秒的条目（原理见 06-10）。从安全视角看，这条链意味着即使攻击者伪造不同源 IP，也会受到哈希表容量 `max_entries` 与全局令牌速率的双重约束。

### 5. 配置/命令/代码实例

先看密钥的安全生成。下面这段命令把「umask 收紧、私钥落盘、公钥派生、PSK 独立生成、权限归位」串成一套可复制的动作。注意 `wg genkey` 与 `wg genpsk` 是两个独立子命令，前者产出钳制后的私钥，后者产出不钳制的对称 PSK（参数全集见 04-01）。

```bash
# 收紧掩码，确保随后创建的文件默认只有属主可读写
umask 077

# 生成私钥并落到受保护路径，同时由同一私钥派生公钥
wg genkey | tee /etc/wireguard/privatekey | wg pubkey > /etc/wireguard/publickey

# 独立生成 PSK，绝不复用私钥或把它与私钥放在同一文件
wg genpsk > /etc/wireguard/psk

# 明确权限：私钥与 PSK 仅属主可读写，公钥可读
chmod 600 /etc/wireguard/privatekey /etc/wireguard/psk
chmod 644 /etc/wireguard/publickey
```

下面这段把入口防线落到主机防火墙与接口配置上：防火墙只开放 WireGuard 的 UDP 端口并对新连接限速，`wg set` 则为 peer 配置收敛的 AllowedIPs 与 PSK。这里展示的是 iptables 写法，实际环境可用 nftables 或云安全组等价实现（参数见 04-01、04-02）。

```bash
# 仅允许必要来源访问 UDP 51820，并对新握手限速
iptables -A INPUT -p udp --dport 51820 -m conntrack --ctstate NEW \
  -m limit --limit 20/second --limit-burst 5 -j ACCEPT
iptables -A INPUT -p udp --dport 51820 -j DROP

# 为对端配置最小 AllowedIPs 与带外分发的 PSK
wg set wg0 peer <对端公钥> \
  allowed-ips 10.0.0.2/32 \
  preshared-key /etc/wireguard/psk \
  endpoint 203.0.113.9:51820
```

完成加固后，用 `wg show` 复核安全相关的运行状态。下面是典型输出。

```bash
wg show wg0
```

示例输出，具体格式需对照实际版本核验：

```text
示例输出，具体格式需对照实际版本核验
interface: wg0
  public key: <本端公钥>
  private key: (hidden)
  listening port: 51820
peer: <对端公钥>
  preshared key: (hidden)
  endpoint: 203.0.113.9:51820
  allowed ips: 10.0.0.2/32
  latest handshake: 38 seconds ago
  transfer: 2.41 KiB received, 1.87 KiB sent
```

逐行判读如下。首行是核验标注，不属于实际输出，仅提示格式需按版本核对；紧随其后的 `interface: wg0` 才是第一行真实输出，它来自 `WG_CMD_GET_DEVICE` 返回的 `WGDEVICE_A_IFNAME`，确认查询命中正确的接口，多接口环境下这一行是防误操作的锚点。第二行 `public key` 对应 `WGDEVICE_A_PUBLIC_KEY`，由本端私钥经 Curve25519 派生，它应与分发给对端的公钥逐字符一致，否则握手静默失败；这是核对「公钥有没有发错人」的关键一行。第三行 `private key: (hidden)` 是工具刻意不回显私钥的自我保护，说明展示层做了脱敏，真实私钥仍在内核接口的 `WGDEVICE_A_PRIVATE_KEY` 中；任何要求从 show 输出复制私钥的说法都是错误的（对比之下 `wg showconf` 默认会输出私钥原文，这才是泄露高发点）。第四行 `listening port: 51820` 对应 `WGDEVICE_A_LISTEN_PORT`，应与防火墙放行端口一致。第五行 `peer:` 后的对端公钥对应 `WGPEER_A_PUBLIC_KEY`，是身份校验的基准。第六行 `preshared key: (hidden)` 表示本 peer 已配置 PSK 且工具同样做了脱敏；若此行缺失，说明 PSK 没配或未被内核识别，后量子纵深就无从谈起。第七行 `allowed ips` 对应 `WGALLOWEDIP_A_IPADDR` 与 `WGALLOWEDIP_A_CIDR_MASK`，这里收敛到单个 `/32`，正是最小权限原则的体现；写成 `0.0.0.0/0` 则意味着接受该 peer 的任意源地址，须有明确理由。第八行 `latest handshake` 对应 `WGPEER_A_LAST_HANDSHAKE_TIME`，是判断隧道是否真正建立、PSK 是否匹配的核心——若长期为空，优先排查公钥、PSK、endpoint 与双方时钟。第九行 `transfer` 对应 `WGPEER_A_RX_BYTES` 与 `WGPEER_A_TX_BYTES`，累计收发字节只有在握手成功且 AllowedIPs 正确时才会增长。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是私钥文件的权限。`genkey_main` 那句 `Warning: writing to world accessible file` 不是噪音：若不设 `umask 077`，`wg genkey > key` 生成的文件很可能是 0644，同机其他用户可直接读取，身份随即失守。务必把私钥与 PSK 固定放在 0700 目录、0600 文件里，并在配置管理或容器镜像构建时检查是否有「把私钥 COPY 进镜像层」的动作——镜像层一旦推送就难以彻底撤回。

第二个陷阱是把公钥和私钥的角色搞反。公钥可以公开分发，私钥永不离开本机；常见错误是把整份 `wg0.conf`（其中含 `PrivateKey`）当作「配置模板」发给多个节点，导致所有节点共用一把私钥，任何一个节点失陷就等于全网失陷。正确做法是每个节点本地生成私钥，只交换各自公钥。第三个陷阱是误以为 PSK 能弥补密钥管理缺陷。PSK 是纵深加固，不是身份证；一对泄露的公私钥加上 PSK，攻击者只要同时拿到配置文件里的这两样（它们常在同一文件），伪装依然成立。PSK 必须走独立带外信道分发，且与公私钥分开存放。

第四个陷阱是 AllowedIPs 过度开放。把 `AllowedIPs = 0.0.0.0/0` 当成默认值，会让该 peer 被允许出现任意源地址，一旦对端被攻陷，攻击者可借隧道注入任意来源流量。应按下游真正需要的网段逐条收敛，IPv6 同理避免默认 `::/0`。第五个陷阱是误解内建 DoS 防护的边界：cookie 与 ratelimiter 主要抑制握手滥用与伪造源地址，无法阻止针对出口带宽的流量耗尽攻击，因此主机/边界防火墙的限速与上游清洗仍然必要，二者是互补而非替代（原理见 06-09、06-10）。

第六个陷阱是日志泄露。`wg show` 隐藏私钥，但 `wg showconf` 默认打印私钥原文；把 showconf 输出重定向到日志、贴进工单、或让配置采集代理定期上传，都会把最敏感的材料复制到防线之外。若确需备份配置，应对备份文件加密并限制访问，而不是明文集中存放。第七个陷阱是忽略权限边界：加载内核模块需要 `CAP_SYS_MODULE`，用 `wg` 改接口需要 `CAP_NET_ADMIN`；应让自动化只具备所需能力，避免为图省事让大量进程以完全 root 运行。

最佳实践可归纳为五条：用 `umask 077` 与 0600 权限保护私钥和 PSK；用独立的带外信道分发 PSK；把 AllowedIPs 与防火墙规则都收敛到最小；把握手时间、流量计数器纳入日常巡检（监控项见 08-06）；定期按不中断会话的流程轮换密钥，并在轮换后复核双方 `latest handshake` 与 `preshared key: (hidden)` 是否如预期。这五条覆盖了从密钥生成到运行监控的完整安全闭环。

### 7. 小结与延伸阅读

本篇从 WireGuard「密钥即身份」的模型出发，讲清了四类秘密（接口私钥、接口公钥、PSK、临时 cookie 机密）的不同性质，以及六条运维安全边界：私钥保护、密钥轮换、PSK 带外分发、firewall 与 AllowedIPs 最小权限、内核模块与 `CAP_NET_ADMIN` 权限收敛、日志敏感信息脱敏；并把内建 DoS 防护（cookie 四态验证、ratelimiter 令牌桶）纳入入口安全边界。核心结论是：协议保证了密钥生成的不可预测性与握手的抗滥用能力，但私钥落到磁盘之后的权限、分发、轮换与脱敏，完全取决于运维纪律——这也是绝大多数真实事故的根源。

延伸阅读建议按三条线走：想深入密钥派生与会话时序读 06-03，想深入 DoS 防护读 06-09、06-10，想落地到不中断会话的轮换与监控读 08-06。跨册随查按（字段见 05-07 ｜ 参数见 04-01 ｜ 原理见 06-03 ｜ 模块见 07-13）执行：结构体逐字段去 05、参数与命令全集去 04、机制与调用链去 06、目录级模块能力去 07、运维落地与基准去 08。凡本篇标注「需对照实际版本核验」的输出格式与命令选项，均以 `_wglinux_build/upstream_src/` 下对应文件为准，本册不编造未核验的路径与取值。

## 08-06 上线 checklist 与运维手册

### 1. 背景与动机

一套 WireGuard 隧道「配通」和「可运维地长期稳定运行」是两件不同的事。前者只需几条 `wg` 命令把接口拉起来、握手成功即可；后者要求把散落的命令固化成可重复、可审计、可在压力下照着执行的流程，让换班的人不靠记忆也能正确操作。本篇正是这套流程的载体，也是本套资料中运维场景的唯一权威源。要明确分工：`wg` 的每个参数怎么写、有哪些取值，归 04 册（参数见 04-01、04-02）；`wg_device`、`wg_peer` 等结构字段是什么，归 05 册（字段见 05-02、05-03）；握手、netlink、会话轮换的机制为何如此，归 06 册（原理见 06-03、06-14）；`setconf.c`、`wg-quick` 等目录级职责，归 07 册（模块见 07-13）。本篇不重复这些内容，只回答「上线前后具体按什么步骤做、每步用什么命令、做到什么程度算合格」。

checklist 的价值在第一线最容易被低估。人在深夜处理故障或赶上线窗口时，最不可靠的就是记忆：会忘记先设 `umask 077`、会忘记把防火墙规则同步改、会在改 peer 时误用全量替换导致所有会话中断、会忘记备份私钥就先重启。一张逐条勾选的清单把「记忆任务」变成「核对任务」，把每一步的预期结果写清楚，人就只需判断「是否符合」。这也是为什么本篇既给清单表格，也给可直接复制的命令块——表格用于核对，命令用于执行，两者配合才能既防遗忘又防误敲。运维手册的另一层价值是交接：一份写清楚「变更流程、轮换流程、监控项、备份恢复、升级注意、应急响应」的文档，能让团队能力不依赖某个人，这正是生产环境与实验环境最大的区别。

### 2. 核心概念

把 WireGuard 接口的生命周期拆开，运维工作可以归纳为八个依次推进又循环往复的阶段：部署前检查、部署与初始配置、配置变更、密钥轮换、监控巡检、备份与恢复、升级、应急响应。每个阶段都有明确的「输入—动作—合格判据」。部署前检查确认模块、工具、端口、时钟、权限齐备；部署阶段生成密钥并建立最小隧道；配置变更阶段用不中断机制下发改动；密钥轮换阶段按可控时序替换身份材料；监控巡检持续观察握手时间与流量计数器；备份恢复保证配置与密钥可回退；升级阶段处理内核模块与工具的版本关系；应急响应在异常发生时按预案止损。这八个阶段合起来构成一个闭环：监控与应急的发现会回流到配置变更或密钥轮换，因此运维不是一次性上线，而是持续循环。

其中「不中断连接」是配置变更阶段的核心机制，也是本篇最需要讲清的概念。`wg setconf` 是全量替换：它按配置文件重建接口的配置，未在文件中的 peer 会被移除，现有会话随之失效。而 `wg syncconf` 的 man 页写得很明确：「与 setconf 类似，但先读回现有配置，只做配置文件与接口之间显式不同的改动；它比 setconf 效率低得多，好处是不打断当前 peer 会话。」用源码语言说，`syncconf` 先把运行中的配置读回来，按公钥排序逐个比对：文件里没有、但运行中存在的 peer，被标记为 `WGPEER_REMOVE_ME` 加入本次提交；两边都有的 peer 只更新显式差异；最后一次性把差异提交给内核。未变的 peer 因此保持原会话，不停机。这正是生产环境应当默认采用 `syncconf` 而非 `setconf` 的原因，也是 systemd 单元里 `ExecReload` 选用 `wg syncconf` 的依据。

理解「读回—比对—增量提交」这一模式，就理解了运维手册里大部分规定的由来：为什么改一个 peer 的 endpoint 不该用 `setconf`；为什么从配置文件里删掉一个 peer 就等于撤销它；为什么 `syncconf` 在大 peer 规模下开销更大（它要把两边配置都解析并排序）；为什么密钥轮换要讲究先后顺序（旧公钥对应的 peer 若被提前从文件移除，会话会先断）。这些不是操作偏好，而是由 `sync_conf` 的实际逻辑决定的。本篇第 4 节会把这条链展开，帮助运维在异常时判断「改动到底有没有生效、会话为什么断了」。

### 3. 关键数据结构与源码位置

本节只点名与运维流程直接相关的实现落点，逐字段、逐参数、逐原理均让给对应权威册。配置变更的核心在 `wireguard-tools/src/setconf.c`：`setconf_main` 负责解析配置文件（经 `config_read_line`、`config_read_finish`），当子命令名为 `syncconf` 时调用 `sync_conf`；`sync_conf` 内部的结构 `peer_origin` 与比较函数 `peer_cmp` 实现「按公钥排序、文件优先」的比对，标志 `WGDEVICE_REPLACE_PEERS`、`WGPEER_REMOVE_ME` 决定哪些 peer 被替换或移除（模块见 07-13，参数语义见 04-02）。手册里 `systemctl reload wg-quick@wg0` 背后的命令来自 `wireguard-tools/src/systemd/wg-quick@.service` 中的 `ExecReload`，它用 `wg-quick strip` 去掉接口地址、MTU、PostUp 等非 `wg setconf` 字段后交给 `wg syncconf`（wg-quick 参数见 04-03）。

监控项的字段源头是 uapi：`wg show` 通过 `WG_CMD_GET_DEVICE` 读回属性，`latest handshake` 对应 `WGPEER_A_LAST_HANDSHAKE_TIME`，`transfer` 对应 `WGPEER_A_RX_BYTES` 与 `WGPEER_A_TX_BYTES`，`allowed ips` 对应 `WGALLOWEDIP_A_IPADDR` 与 `WGALLOWEDIP_A_CIDR_MASK`（字段见 05-02、05-03、05-04，常量全集见 04-05、04-06，netlink 原理见 06-14）。下表把运维动作与源码落点对应起来，便于按图索骥。

| 运维动作 | 实现落点／命令 | 本册处理方式 |
|---|---|---|
| 不中断变更 | `setconf.c` 的 `sync_conf`、`wg syncconf` | 讲流程，参数见 04-02 |
| reload 集成 | `wg-quick@.service` 的 `ExecReload` | 讲用法，模块见 07-13 |
| 监控握手与流量 | `wg show`／`WGPEER_A_*` 属性 | 讲判读，字段见 05-03 |
| 密钥生成 | `genkey.c`／`wg genkey`、`wg genpsk` | 讲流程，参数见 04-01 |
| 接口与路由状态 | `ip link`、`wg show` | 讲核对，命令见 04-01、04-04 |

### 4. 关键流程与调用链

把 `syncconf` 的调用链逐步展开，就能解释手册中每条变更规定的来历。`setconf_main` 先 `fopen` 配置文件，按行调用 `config_read_line` 解析，`config_read_finish` 得到一个 `wgdevice` 对象并写入接口名；随后判断子命令：若不是 `syncconf`（即 `setconf` 或 `addconf`），直接走到 `ipc_set_device` 提交。若是 `syncconf`，则进入 `sync_conf`：它先检查文件里是否有 peer，没有就无需同步；再用 `ipc_get_device(&runtime, file->name)` 读回运行中配置，若运行中也没有 peer 则直接返回。接着它清掉文件的 `WGDEVICE_REPLACE_PEERS` 标志（这是全量替换的标志，增量同步不能用），把文件侧 peer 与运行侧 peer 都放进 `peers` 数组，用 `qsort` 按 `peer_cmp` 排序——先按公钥字节序，再按「来自文件优先」。排序后遍历：来自运行侧、且在文件侧找不到同公钥 peer 的，构造一个只带公钥、`flags = WGPEER_REMOVE_ME` 的 peer 挂到文件链表头部；两边都有的 peer，若运行侧有 PSK 或 keepalive 而文件侧没有，则把文件侧的对应值清零并设置存在标志，以便提交时清除旧值。最后回到 `setconf_main` 调用 `ipc_set_device`，把这份「差异清单」一次性发给内核（原理见 06-14）。

systemd 的 reload 链把上面这套机制包装成一条运维命令：`systemctl reload wg-quick@wg0` 触发单元里的 `ExecReload=/bin/bash -c 'exec /usr/bin/wg syncconf %i <(exec /usr/bin/wg-quick strip %i)'`。这里 `wg-quick strip` 把 wg-quick 专用的键（Address、DNS、MTU、PostUp 等）滤掉，只留下 `wg setconf` 能识别的 `[Interface]` 与 `[Peer]` 字段，进程替换 `<(...)` 把它作为文件传给 `syncconf`。整条链的意义是：改完 `wg0.conf` 后执行 reload，接口地址、路由等由 wg-quick 管理的部分不动，WireGuard 的 peer 与密钥按差异增量更新，现有会话保持。这就是「配置变更不中断连接」在真实系统上的完整路径。

### 5. 配置/命令/代码实例

先给部署前检查清单。下表的每一项都应在上线窗口开始前逐条勾选，任一不合格都不应进入部署阶段。

| 检查项 | 合格判据 | 验证命令／依据 |
|---|---|---|
| 内核模块可用 | `ip link add` 能创建 wireguard 类型接口 | `ip link add wgtest type wireguard`（模块见 07-01） |
| 工具版本明确 | `wg --version` 输出版本可记录归档 | `wg --version`（参数见 04-01） |
| UDP 端口可达 | 防火墙放行既定端口与来源 | 防火墙规则核对（见 08-05） |
| 双方时钟同步 | 时差在容忍范围内，否则握手易失败 | `chronyc tracking` 等 |
| 密钥权限正确 | 私钥与 PSK 为 0600、目录 0700 | `stat -c '%a %n' /etc/wireguard/*key*` |
| 回退方案就位 | 有可恢复的配置与密钥备份 | 见本节备份命令 |

下面是部署前检查的可执行命令块，重点是「先确认能力、再动配置」。

```bash
# 1. 确认模块与工具
wg --version
ip link add wgtest type wireguard && ip link del wgtest && echo "module ok"

# 2. 确认时钟同步（输出应与预期时间源一致）
chronyc tracking 2>/dev/null || timedatectl status

# 3. 确认密钥文件权限（期望 privatekey/psk 为 600）
stat -c '%a %n' /etc/wireguard/privatekey /etc/wireguard/psk /etc/wireguard/publickey
```

下面是配置变更的标准流程。核心是：先在测试环境或配置管理里校验语法，再用 `syncconf` 增量下发，最后用 `wg show` 复核会话未被打断。若用 systemd 管理，等价于 `systemctl reload`（参数见 04-02）。

```bash
# 语法预检：确认配置文件可被解析（失败则不要下发）
wg syncconf wg0 /etc/wireguard/wg0.conf && echo "parse ok"

# 增量下发：未变更的 peer 会话保持，不中断连接
wg syncconf wg0 /etc/wireguard/wg0.conf
# 等价的 systemd 方式：systemctl reload wg-quick@wg0

# 变更后核对：握手时间不应被重置为很长
wg show wg0 latest-handshakes
```

下面是密钥轮换的流程。原则是「先让对端具备接受新身份的能力，再切换本端」，并在每一步后观察握手。

```bash
# 1. 在新目录生成新私钥与派生公钥（不影响运行中的接口）
umask 077
wg genkey | tee /etc/wireguard/privatekey.new | wg pubkey > /etc/wireguard/publickey.new

# 2. 把新公钥带外发给对端，由对端先添加到本 peer 的公钥列表
#    （对端操作完成后再继续，否则本端切换后会断连）

# 3. 原子替换本端私钥并增量下发
mv /etc/wireguard/privatekey.new /etc/wireguard/privatekey
wg syncconf wg0 /etc/wireguard/wg0.conf

# 4. 观察握手是否重新建立
wg show wg0 latest-handshakes
```

监控巡检以 `wg show` 为主。下面这条命令输出每个 peer 的关键运行量，是日常工作最常用的一屏。

```bash
wg show wg0
```

示例输出，具体格式需对照实际版本核验：

```text
示例输出，具体格式需对照实际版本核验
interface: wg0
  public key: <本端公钥>
  private key: (hidden)
  listening port: 51820
peer: <对端公钥A>
  endpoint: 203.0.113.9:51820
  allowed ips: 10.0.0.2/32
  latest handshake: 1 minute, 12 seconds ago
  transfer: 8.44 MiB received, 6.02 MiB sent
peer: <对端公钥B>
  endpoint: 198.51.100.4:51820
  allowed ips: 10.0.0.3/32
  latest handshake: 3 days, 4 hours ago
  transfer: 1.20 KiB received, 980 B sent
```

逐行判读如下。首行是核验标注而非真实输出，提示格式需按版本核对；`interface` 段三行来自 `WG_CMD_GET_DEVICE` 返回的 device 属性：`public key` 应与分发出去的公钥一致；`private key: (hidden)` 再次确认工具脱敏，能安全地在屏幕上查看；`listening port` 应与防火墙放行端口一致。第一个 peer 段里，`endpoint` 对应 `WGPEER_A_ENDPOINT`，是动态学习到的对端地址；`allowed ips` 对应 `WGALLOWEDIP_A_IPADDR` 与掩码，收敛在 `/32`；`latest handshake: 1 minute, 12 seconds ago` 对应 `WGPEER_A_LAST_HANDSHAKE_TIME`，一分钟内说明链路活跃健康；`transfer` 对应 `WGPEER_A_RX_BYTES` 与 `WGPEER_A_TX_BYTES`，数值持续增长说明双向数据流正常。第二个 peer 段才是巡检要抓的异常：`latest handshake: 3 days, 4 hours ago` 说明该 peer 已有三天没有成功握手，远超 keepalive 应有的刷新周期，`transfer` 也几乎停滞——这通常意味着对端下线、公钥错配、endpoint 失效或中间网络阻断，应作为告警项处理，而不是等到业务报错才发现。两个 peer 对比也能看出监控要点：单看接口 `up` 没有意义，必须逐 peer 看握手时间新鲜度与流量计数是否随时间增长，这正是把「配通」升级为「可运维」的关键判据。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是混用 `syncconf` 与 `setconf`。`setconf` 走全量替换，未在新文件中出现的 peer 会被移除，正在进行的会话随之中断；生产环境的任何在线改动都应默认用 `syncconf`。但要知道代价：`sync_conf` 要读回并排序两边配置，peer 数量很大时开销明显高于 `setconf`，超大集群应评估下发耗时，必要时分批变更。第二个陷阱是误删 peer。因为 `syncconf` 会把「文件中消失、运行中仍在」的 peer 标为 `WGPEER_REMOVE_ME`，所以从配置模板里删掉一个 peer 就等于撤销它；若只想临时停用，应先确认这是否是你想要的结果。

第三个陷阱是密钥轮换顺序颠倒。若先把本端私钥换掉、却没让对端提前接受新公钥，握手会立即失败、流量中断；正确顺序是先带外分发并让对端添加新公钥，确认对端就绪后再切本端私钥，并在每一步后看 `latest handshake`。第四个陷阱是备份泄露。备份若把含私钥的 `wg0.conf` 明文集中存放、或上传日志采集系统，等于把身份材料复制到防线之外；备份应加密并限制访问，且定期演练恢复流程——没有演练过的备份等于没有备份（安全边界见 08-05）。

第五个陷阱是升级时忽略版本独立性。内核驱动版本（`version.h` 的 `1.0.0`）、wireguard-tools 版本（`WIREGUARD_TOOLS_VERSION`）、目标系统内核版本三者独立；内核升级后若使用 DKMS，需要确认模块随新内核重建，否则可能加载失败。升级前务必备份配置与密钥、记录当前 `wg show` 基线，并准备回退路径。第六个陷阱是监控只看接口状态：`wg0` 显示 `up` 不代表隧道可用，必须逐 peer 检查握手时间新鲜度与流量计数是否增长，否则像本节示例里「三天未握手」的 peer 会被漏掉。第七个陷阱是应急响应缺少预案：疑似私钥泄露时应立即轮换密钥、撤销可疑 peer、并在防火墙侧封禁来源，而不是先慢慢排查；事前写好应急预案、明确责任人，才能在这种场景下止损。

最佳实践可归纳为：用清单驱动上线与变更，默认 `syncconf` 增量下发，密钥轮换遵循「对端先就绪、本端后切换」，监控以握手时间与流量计数器为核心，备份加密且定期演练恢复，升级前留基线、升级后核对版本与模块加载，应急按预案先止损后定位。这七条与 08-05 的安全边界互为表里：一个讲「边界怎么设」，一个讲「流程怎么走」，合起来才是完整的生产运维体系。

### 7. 小结与延伸阅读

本篇把 WireGuard 接口的运维工作组织成八个阶段（部署前检查、部署与初始配置、配置变更、密钥轮换、监控巡检、备份恢复、升级、应急响应）的闭环，并给出逐条可勾选的 checklist 表格与可执行命令。最关键的技术结论是：`wg syncconf` 通过「读回运行配置—按公钥排序比对—把文件缺失的 peer 标为 `WGPEER_REMOVE_ME`—一次性增量提交」实现不中断变更，systemd 的 `ExecReload` 正是借 `wg-quick strip` + `wg syncconf` 把这条链包装成一条 reload 命令；监控则必须落到逐 peer 的握手时间新鲜度与流量计数器增长上，而非仅看接口是否 `up`。

延伸阅读建议按三条线走：配置变更的参数全集读 04-02，netlink 配置通道原理读 06-14，用户态工具模块职责读 07-13；安全边界与密钥保护回到 08-05，故障诊断与案例回到本册 08-03、08-04。跨册随查按（字段见 05-02 ｜ 参数见 04-02 ｜ 原理见 06-14 ｜ 模块见 07-13）执行：结构体逐字段去 05、参数与命令全集去 04、机制与调用链去 06、目录级模块能力去 07、运维落地与基准去 08。凡本篇标注「需对照实际版本核验」的输出格式与命令选项，均以 `_wglinux_build/upstream_src/` 下对应文件为准，本册不编造未核验的路径与取值。
