## 04-01 wg 命令行参数全集

### 1. 背景与动机

本册是整套 WireGuard Linux 资料中「参数、命令、常量」的唯一权威源，而本篇 04-01 又是 wg 这个用户态命令的权威清单。之所以把参数单独立成一册，是因为其他各册在讲到配置时都会用到 `wg show`、`wg set`、`AllowedIPs`、`listen-port` 这样的名字，如果每一册都各自罗列一遍，既容易遗漏，也容易在版本演进后出现互相矛盾的说明。因此本册采取「一处写全、多处引用」的策略：凡涉及 wg 的子命令、开关、参数名与取值约束，都以本篇和紧接着的 04-02 为准，其他册只给最小片段并注明「完整参数见 04-01」。本篇的任务是把 wg 命令本身拆解到每一个子命令、每一个选项、每一个参数，逐项对照源码核实，不臆造任何一个开关。

wg 是 `wireguard-tools` 包提供的配置实用程序，其版本基准为 `WIREGUARD_TOOLS_VERSION` 所定义的 `1.0.20260223`（见 `wireguard-tools/src/version.h`）。需要特别强调的是，wg 只负责 WireGuard 专属的那部分配置——接口私钥、监听端口、fwmark、peer 公钥、endpoint、AllowedIPs、持久 keepalive 与预共享密钥。它不创建接口、不配置 IP 地址、不写路由：创建与删除接口由 `ip link add/del ... type wireguard` 完成，地址由 `ip address` 完成，路由由 `ip route` 完成。man 手册 `src/man/wg.8` 的 DESCRIPTION 第一段就把这条边界写得很清楚。理解这条边界非常重要，因为大量「wg 配了却不通」的问题，根源其实在地址或路由，而不在 wg 参数本身（部署流程见 03-01、排障思路见 08-03）。

wg 的入口逻辑集中在 `wireguard-tools/src/wg.c`，代码量不大却信息密集。它的 `main()` 先处理三个全局开关：当参数为 `-v`、`--version` 或 `version` 时，打印 `wireguard-tools v%s` 后返回；当参数为 `-h`、`--help` 或 `help` 时，调用 `show_usage()` 打印帮助后返回；当完全不带参数（`argc == 1`）时，把参数替换成 `{"show"}` 直接落到 show 子命令——这就是「wg 默认等于 wg show」的实现。其余情况用一个静态数组 `subcommands[]` 做字符串匹配：结构里每一项含 `subcommand` 名称、`function` 函数指针与 `description` 描述，遍历匹配成功后调用 `subcommands[i].function(argc - 1, argv + 1)`，也就是把子命令名从参数列表中剥掉再交给具体处理函数；匹配失败则打印 `Invalid subcommand` 并返回 1。整张分派表一共九个条目，加上两个全局开关，构成了 wg 命令的完整表面。

为什么把命令入口写得如此「薄」？因为真正的解析工作被下放到了各个子命令文件里，而配置语义又统一收敛到 `config.c`。这种「薄入口、厚解析」的结构带来两个直接好处：其一，所有需要写配置的命令（set、setconf、addconf、syncconf）都复用同一个 `config.c` 解析器，因此命令行参数与配置文件字段在语义上高度一致，不会出现「命令行支持但文件不支持」的偏差；其二，查询命令（show、showconf）只读不写，走 `ipc_get_device()`，配置命令才走 `ipc_set_device()`，读写路径在源码层面就是分开的。后续小节会沿着这两条路径，把每个子命令支持的开关逐一展开，并把它们与 uapi 属性对应起来，但属性的完整枚举交给 04-05、常量与标志交给 04-06，本篇只在必要处点名。

### 2. 核心概念

从使用目的看，wg 的九个可被子命令可以归为四组。第一组是查询类，包含 `show` 与 `showconf`：前者把运行态与配置态渲染成人可读的表格或脚本友好的字段，后者把当前配置导出成可回灌的 INI 格式文本。第二组是配置类，包含 `set`、`setconf`、`addconf`、`syncconf`：它们都改写内核接口状态，但改写方式差异很大，`set` 接受命令行键值对，`setconf` 用文件整体替换，`addconf` 在现有基础上追加，`syncconf` 则先读回现有配置再只改有差异的部分。第三组是密钥类，包含 `genkey`、`genpsk`、`pubkey`：它们不接触内核接口，只在标准输入输出上做随机数生成与 Curve25519 运算。第四组是元信息类，即 `help` 与版本开关，它们由 `main()` 直接处理，不在 `subcommands[]` 表里。把这四组分开理解，是掌握全部参数的前提。

第二个核心概念是「配置面与数据面分离」在命令层的体现。wg 的所有配置命令最终都通过 `ipc_set_device()` 把序列化的 `wgdevice` 交给 netlink 通用族 `WG_CMD_SET_DEVICE`，由内核更新 device/peer/allowedip 三层状态；查询命令通过 `ipc_get_device()` 发 `WG_CMD_GET_DEVICE` 读回。netlink 通道的细节见 06-14。这意味着 wg 本身没有任何常驻进程，也没有任何数据面职责——它是一次性执行的配置客户端。也正因为如此，wg 的参数集合与 netlink 属性集合几乎是一一对应的：每一个命令行开关背后都对应一个 `WGDEVICE_A_*`、`WGPEER_A_*` 或 `WGALLOWEDIP_A_*` 属性，以及一个 `*_HAS_*` 标志位。读源码时可以反向印证：`config.c` 里每成功解析一个参数，几乎都会给相应的 `flags` 置位，例如解析 listen-port 成功会置 `WGDEVICE_HAS_LISTEN_PORT`，解析 peer 公钥成功会置 `WGPEER_HAS_PUBLIC_KEY`。这种「值 + 标志位」的成对出现，是理解配置语义的关键，字段层面的展开见 05-09。

第三个核心概念是「同一个语义，两种输入形态」。`set` 走 `config_read_cmd()`，直接解析命令行参数数组；`setconf` 等走 `config_read_line()`，逐行解析 INI 文件。两条路径最终产出同一个 `struct wgdevice`，再交给同一个 `ipc_set_device()`。因此参数名在两处写法不同但含义一致：命令行用连字符小写形式 `listen-port`、`private-key`、`persistent-keepalive`、`allowed-ips`、`preshared-key`，而配置文件里用驼峰形式 `ListenPort`、`PrivateKey`、`PersistentKeepalive`、`AllowedIPs`、`PresharedKey`，`fwmark` 对应 `FwMark`，`endpoint` 对应 `Endpoint`，`peer` 后跟的公钥对应 `PublicKey`。解析时对配置文件键名使用 `strncasecmp`，也就是大小写不敏感，但对命令行的 `strcmp` 是大小写敏感的。这一差异在没有认真读 `config.c` 时很容易踩坑。

第四个核心概念是三个环境变量，它们改变输出与解析行为而不改变命令语法。`WG_COLOR_MODE` 取 `always`、`never` 或 `auto`（含未设置），决定 show 是否输出 ANSI 颜色；`WG_HIDE_KEYS` 取 `never` 时让 show 显示私钥与预共享密钥，其他情况显示 `(hidden)`——这一点在 `show.c` 的 `masked_key()` 里直接体现；`WG_ENDPOINT_RESOLUTION_RETRIES` 控制 endpoint DNS 解析的重试次数，默认 15，设为 `infinity` 表示无限重试，其解析在 `parse_dns_retries()` 中完成。这三个变量在排障脚本里很实用：设置 `WG_COLOR_MODE=never` 可以得到纯净文本，设置 `WG_HIDE_KEYS=never` 可以在受控环境里核对密钥是否写对（但仍应避免把密钥落到日志里）。

### 3. 关键数据结构与源码位置

wg 命令的参数全集可以从三组源码结构里完整还原。第一组是入口分派结构。在 `wireguard-tools/src/wg.c` 中，`subcommands[]` 是一个匿名结构体数组，字段为 `subcommand`（字符串）、`function`（`int (*)(int, const char**)` 函数指针）与 `description`（帮助文本）。这张表就是权威的子命令清单：show、showconf、set、setconf、addconf、syncconf、genkey、genpsk、pubkey。注意 `genpsk` 与 `genkey` 共用同一个 `genkey_main()`，区别仅在于 `argv[0]` 的名称——`genkey_main()` 里只有 `argv[0]` 等于 `"genkey"` 时才调用 `curve25519_clamp_secret()`，因此 `genpsk` 生成的是未经钳制的随机 32 字节。同理 `setconf`、`addconf`、`syncconf` 三者共用 `setconf_main()`，差异靠 `argv[0]` 判断（是否 addconf、是否 syncconf）。

第二组是配置解析上下文。`wireguard-tools/src/config.h` 定义了 `struct config_ctx`，含四个字段：`device` 指向正在构建的 `wgdevice`，`last_peer` 指向最近创建的 peer，`last_allowedip` 指向最近创建的 allowedip，以及两个布尔量 `is_peer_section` 与 `is_device_section` 标记当前处于哪个 INI 段。config.h 还声明了四个解析函数：`config_read_cmd()`（解析命令行数组）、`config_read_init()`（初始化上下文，参数 `append` 决定是否追加）、`config_read_line()`（解析单行）、`config_read_finish()`（收尾校验并返回设备）。这四个函数构成文件解析的完整生命周期。`struct wgdevice`、`struct wgpeer`、`struct wgallowedip` 本身定义在 uapi 相关头文件中，逐字段说明交给 05-09，本篇只把它们当作解析产物来引用。

第三组是各子命令的实现文件，它们决定了每个命令到底接受哪些开关。`show.c` 实现 `show_main()`，其中的 `ugly_print()` 用一个长长的 `if (!strcmp(param, ...))` 链穷举了全部 show 字段选项；`showconf.c` 实现 `showconf_main()`，把 `wgdevice` 反向渲染成 INI 文本；`set.c` 实现 `set_main()`，把参数数组交给 `config_read_cmd()`；`setconf.c` 实现 `setconf_main()` 与关键的 `sync_conf()`；`genkey.c` 同时承载 genkey 与 genpsk；`pubkey.c` 实现 `pubkey_main()`。表 04-01-A 把这些源码位置收拢成速查表。

读懂这三层结构有一个实际收益：当你想确认「某个参数到底存不存在、拼写如何」时，不必去猜或去搜网上的二手资料，只要按「子命令 → 实现文件 → 解析函数」的顺序定位即可。例如要确认 set 是否支持 `preshared-key`，直接看 `config.c` 的 `config_read_cmd()` 里有没有对应分支；要确认 show 是否支持 `latest-handshakes`，直接看 `show.c` 的 `ugly_print()` 与 bash 补全脚本 `src/completion/wg.bash-completion` 第 25 行的字段列表。本篇后续所有结论都按这个方式从源码得出。

### 4. 关键流程与调用链

主分派链路在 `wg.c` 的 `main()` 中：设置全局 `PROG_NAME` 为 `argv[0]`，先匹配版本与帮助开关，再处理无参数默认 show，最后遍历 `subcommands[]` 做字符串精确匹配并调用对应函数。这里所有比较都用 `strcmp`，因此子命令名是大小写敏感的，`wg SHOW` 会落到 `Invalid subcommand`。匹配成功后传给子函数的参数是 `argc - 1, argv + 1`，也就是把子命令本身去掉——这解释了为什么各子命令的 usage 里 `argv[0]` 就是子命令名（如 setconf.c 用它判断是否 addconf/syncconf）。

查询链路以 `wg show` 为例：`show_main()` 根据第一个参数分三种情况。若为 `all` 或省略，调用 `ipc_list_devices()` 拿到接口名列表，再对每个接口 `ipc_get_device()` 读回 `wgdevice`，逐个渲染；若为 `interfaces`，只打印接口名列表后返回；否则把该参数当作接口名直接 `ipc_get_device()`。读回后，若命令行给了第三个参数（字段名），走 `ugly_print()` 输出脚本友好格式；否则走 `pretty_print()` 输出人可读格式。`pretty_print()` 内部还会调用 `sort_peers()` 按最近握手时间排序，把从未握手的 peer 排到最后——这就是为什么 `wg show` 的输出顺序看起来「不稳定」，它其实是按握手新鲜度动态排序的。dump 模式是 `ugly_print()` 的一个特殊分支，转给 `dump_print()` 输出两段落的制表符分隔数据。

配置链路以 `wg set` 为例：`set_main()` 检查 `argc < 3` 则打印 usage，否则把 `argv + 2` 起的参数交给 `config_read_cmd()`，解析出 `wgdevice` 后写入接口名，再调用 `ipc_set_device()`。`setconf` 一族则走文件解析：`fopen()` 配置文件，`config_read_init(&ctx, append)` 初始化（只有 addconf 传 true），用 `getline()` 逐行喂给 `config_read_line()`，再 `config_read_finish()` 校验每个 peer 都有公钥，最后写入接口名；若子命令是 syncconf，额外调用 `sync_conf()` 后再 `ipc_set_device()`。密钥链路最短：`genkey_main()` 用 `get_random_bytes()` 取 32 字节随机数，genkey 时钳制私钥标量，再 `key_to_base64()` 输出；`pubkey_main()` 从 stdin 读定长 base64，`key_from_base64()` 解码后用 `curve25519_generate_public()` 派生公钥再编码输出。

下面给出一组覆盖查询、配置与密钥三类命令的实操序列：

```bash
# 版本与帮助：由 wg.c 的 main 直接处理
wg --version
wg help

# 查询：全部接口、接口名列表、单接口人可读、单字段脚本友好、dump
wg show
wg show interfaces
wg show wg0
wg show wg0 public-key
wg show wg0 dump

# 配置：设置接口参数与一个 peer 的完整子项
wg set wg0 listen-port 51820 fwmark 0xca6c private-key ./private.key
wg set wg0 peer <对端公钥> endpoint 203.0.113.9:51820 \
  persistent-keepalive 25 allowed-ips 10.0.0.2/32 \
  preshared-key ./psk.key

# 密钥：管道式生成密钥对与预共享密钥
umask 077
wg genkey | tee private.key | wg pubkey > public.key
wg genpsk > psk.key
```

```text
<对端公钥base64>  (none)  203.0.113.9:51820  10.0.0.2/32  1700000000  12800  9600  off
```

逐行判读如下。第一行首列是私钥 base64，由 `dump_print()` 里的 `maybe_key(device->private_key, ...)` 产生——注意 dump 模式会输出私钥（除非该字段缺失显示 `(none)`），这与 pretty 模式的 `(hidden)` 不同，因此 dump 输出必须当敏感数据保护。第二列是公钥，由 `maybe_key(device->public_key, ...)` 产生，由本端私钥经 Curve25519 派生。第三列 `51820` 是 `device->listen_port`，对应 uapi 的 `WGDEVICE_A_LISTEN_PORT`，若未设置则为 0，表示接口 up 时随机选端口。第四列 `off` 来自 `fwmark` 分支：当 `device->fwmark` 为 0 时打印 `off`，否则打印 `0x%x`。第二行进入 peer 部分：首列 `key(peer->public_key)` 是对端公钥，对应 `WGPEER_A_PUBLIC_KEY`；第二列 `(none)` 来自 `maybe_key(peer->preshared_key, ...)`，表示未配置预共享密钥，若配置则显示其 base64。第三列是 `endpoint()` 函数用 `getnameinfo()` 加 `NI_NUMERICHOST` 渲染的地址与端口，对应 `WGPEER_A_ENDPOINT`。第四列 `10.0.0.2/32` 由 `ip(allowedip)` 与 `allowedip->cidr` 拼接，对应 allowedip 的 IP 与掩码属性。第五列 `1700000000` 是 `peer->last_handshake_time.tv_sec` 的裸 Unix 时间戳（脚本友好，不做格式化），对应 `WGPEER_A_LAST_HANDSHAKE_TIME`，这是判断隧道是否真正握手的硬指标。第六、七列 `12800` 与 `9600` 分别是 `peer->rx_bytes` 与 `peer->tx_bytes`，对应 `WGPEER_A_RX_BYTES` 与 `WGPEER_A_TX_BYTES`；只有握手成功且路由正确时它们才增长。第八列 `off` 来自 `peer->persistent_keepalive_interval` 为零时的分支，非零则打印秒数。整行的列顺序与 man 手册 wg.8 的 dump 说明完全一致，也和 bash 补全脚本给出的字段集合吻合。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是把 `private-key` 与 `preshared-key` 当成可以直接跟在命令行上的值。无论是命令行还是配置文件，这两个参数都要求文件：在 `config.c` 中它们分别走 `parse_keyfile()`，而不是 `parse_key()`。man 手册明确说明，命令行参数在多数系统上不算私密，所以密钥必须来自文件；若使用 bash，可以用进程替换 `<(echo PRIVATEKEYSTRING)` 安全地传字符串。若指定 `/dev/null` 或其他空文件，工具会把密钥清零并视为删除——`parse_keyfile()` 在读不到内容且文件为空时返回全零密钥，这是「清空密钥」的正规做法，不要试图用空字符串。

第二个陷阱是误解 `allowed-ips` 的替换与增量语义。`parse_allowedips()` 一开始就把 `WGPEER_REPLACE_ALLOWEDIPS` 置位，意味着一次赋值默认替换该 peer 的全部 AllowedIPs；但如果某个条目带 `+` 前缀，会清掉 REPLACE 标志并走增量增加；带 `-` 前缀则额外置 `WGALLOWEDIP_REMOVE_ME` 表示删除。若传空字符串，会清空该 peer 的所有 AllowedIPs（函数里对空串直接返回 true，但 REPLACE 标志已置位）。配置文件里 `AllowedIPs` 写成 `10.0.0.2/32, 10.0.0.3/32` 是多值逗号分隔，而命令行里习惯多次写或在一次 `allowed-ips` 里用逗号；两条路径都收敛到同一个 `parse_allowedips()`，语义一致。掩码写错（例如把 `/32` 写成 `/24`）会让流量路由到错误的 peer，是静默故障的高发点（路由原理见 06-07）。

第三个陷阱是混淆 `show` 的人可读模式与脚本模式。不带字段参数时走 `pretty_print()`，会隐藏密钥、把时间戳格式化成「xx seconds ago」、把字节数格式化成 KiB/MiB，并按握手时间排序；一旦带上任一字段参数就走 `ugly_print()`，输出制表符分隔的原始值，不隐藏私钥（如 dump 所示）、时间戳是裸秒数、字节数是整数。写自动化脚本时务必显式指定字段，避免依赖人可读格式——后者会随终端宽度、颜色设置和语言而变化。

第四个陷阱是忽视环境变量的影响。`WG_HIDE_KEYS=never` 会让 pretty 模式也显示私钥与预共享密钥，运维脚本若要抓取公钥应改用 `wg show ... public-key`，避免误开密钥显示后把输出写入日志。`WG_COLOR_MODE=never` 可保证输出无 ANSI 转义序列，便于 diff 与正则 matching（此处指文本匹配）。第五个陷阱是照抄参数而不核验版本：本篇基于 wireguard-tools 1.0.20260223 快照，不同发行版打包的工具版本可能有细微差异，遇到行为不符时以 `wg --version` 与实际源码为准。

最佳实践：先用 `wg --version` 确认工具可用，再用 `wg show interfaces` 确认内核接口存在；配置时优先用 `setconf`/`syncconf` 管理文件、用 `set` 做临时改动；核对状态用 `wg show <iface>` 看人可读摘要、用 `wg show <iface> latest-handshakes` 与 `transfer` 做量化判断；生成密钥时先 `umask 077` 再管道操作，私钥文件权限设为仅本人可读；涉及热更新 peer 时优先考虑 syncconf 以保留会话（其完整语义见 04-02）。

### 7. 小结与延伸阅读

本篇把 wg 命令拆解到子命令与参数两级：`main()` 通过 `subcommands[]` 分派九个可调用子命令，外加版本与帮助两个全局开关；无参数时默认执行 show。四组子命令各司其职——查询类 show/showconf 走 `ipc_get_device()`，配置类 set/setconf/addconf/syncconf 走 `config.c` 解析后由 `ipc_set_device()` 写入，密钥类 genkey/genpsk/pubkey 只在本地做随机与 Curve25519 运算。表 04-01-B 与 04-01-C 给出了参数全集：show 支持十二个字段选项，set 支持三个接口级开关与六个 peer 子项，私钥与预共享密钥必须是文件，AllowedIPs 默认替换而 + / - 表示增量，persistent-keepalive 与 fwmark 支持 off/0 关闭。dump 输出的每一列都能逐一映射到 uapi 属性与 `show.c` 中的声明。

需要延续阅读的有三处：其一，syncconf 与 setconf、set 在配置语义上的深层差异，以及 config_ctx 的解析生命周期，见 04-02；其二，netlink 属性的完整枚举与标志位全集，见 04-05、04-06；其三，这些配置字段在内核结构里的落点，见 05-09。跨册随查按（字段见 05-09 ｜ 原理见 06-14 ｜ 模块见 07-13 ｜ 排障见 08-03）执行：结构体逐字段去 05、机制与调用链去 06、目录级模块能力去 07、运维场景与基准去 08；本篇所在的 04 册本身就是参数与命令的权威源，其他册凡涉及 wg 参数均回指本篇。凡标注「需对照实际版本核验」的开关、字段与语法，均以 `_wglinux_build/upstream_src/wireguard-tools/src/` 下对应文件为准，本套资料不编造未核验的路径与取值。

## 04-02 wg syncconf / set / setconf 与配置语义

### 1. 背景与动机

wg 提供四种改写配置的途径——`set`、`setconf`、`addconf`、`syncconf`——它们在 `wg.c` 的 `subcommands[]` 里被登记为四个名字，但其中后三个共用 `setconf_main()` 一个实现，第一个由 `set_main()` 单独实现。对使用者而言，这四种途径最令人困惑的地方不是参数拼写，而是「语义」：同样一份配置，用 setconf 应用和用 syncconf 应用，对现有隧道会话的影响完全不同。本篇专门处理这一层面的问题，把「配置如何被解析、如何被合并、最终如何落到内核」讲清楚。参数清单本身已在 04-01 给出，本篇不重复罗列每一个开关，而是聚焦它们之间的组合规则与差异。

先看一个真实场景。假设一条已经建立握手、正在传输数据的隧道，运维想给某个 peer 增加一条 AllowedIPs。若用 `wg set` 直接执行 `allowed-ips`，默认语义是替换该 peer 的全部 AllowedIPs，除非在条目上加 `+` 前缀；若用 `wg setconf` 整体灌入一份配置文件，由于配置初始化时会置 `WGDEVICE_REPLACE_PEERS`，内核会重建 peer 集合，正在进行的会话随之被打断；若改用 `wg syncconf`，工具会先通过 `ipc_get_device()` 读回当前运行态，把配置文件与运行态逐一比对，只对真正有差异的部分发出更改，从而不打断现有会话。man 手册 wg.8 在 syncconf 条目下明确写着它「much less efficient than setconf, but has the benefit of not disrupting current peer sessions」——这句是理解 syncconf 存在意义的钥匙。

为什么替换 peer 会打断会话？因为在内核里，peer 对象承载着握手状态、会话密钥、计数器与发送队列（字段见 05-03）。一旦配置通道把 peer 标记为删除再重建，这些运行态就被丢弃，对端必须重新握手。syncconf 的设计目标正是避免这种「无谓的重建」：它试图让「配置文件所描述的期望状态」与「内核中的当前状态」之间的差异最小化，只把差异写下去。代价是它要多做一次读回、一次按公钥排序的集合比较，因此效率低于直接覆盖式的 setconf。理解这层取舍，才能在实际运维中正确选择工具（热更新与部署流程见 03-05、08-06）。

从源码组织看，本篇的主战场是 `wireguard-tools/src/config.c` 与 `wireguard-tools/src/setconf.c`。前者提供统一的解析引擎，后者在解析之上实现「追加」与「差异同步」的额外逻辑。把这两份代码读透，就能回答几乎所有关于配置语义的问题：为什么配置文件键名大小写不敏感、为什么注释以 `#` 开头、为什么每个 peer 必须有公钥、为什么空的 AllowedIPs 会清空地址段、为什么 syncconf 对未列出的 peer 会执行删除。下面各节按「概念—结构—流程—实例—陷阱」的顺序展开。

### 2. 核心概念

第一个核心概念是四种配置语义的精确区分。`set` 是命令行增量更新：它只把你显式写出的开关下发，未提及的字段保持内核原样。`setconf` 是文件整体替换：`config_read_init()` 在 append 为 false 时置 `WGDEVICE_REPLACE_PEERS`，意味着配置里没写的 peer 会被删除。`addconf` 是文件追加：传入 append 为 true，不置 REPLACE_PEERS，因此配置里的 peer 叠加到现有集合之上。`syncconf` 是文件差异同步：它先把 REPLACE_PEERS 清掉，再通过 `sync_conf()` 计算出需要删除的 peer 并显式加入删除指令，最终达到「结果等于文件内容」但「尽量不扰动现有会话」的效果。一句话概括：setconf 是「覆盖」，addconf 是「叠加」，syncconf 是「对齐」，set 是「点改」。

第二个核心概念是标志位驱动的语义。`config.c` 在解析每个字段成功后都会置一个 `*_HAS_*` 标志，例如解析 PrivateKey 置 `WGDEVICE_HAS_PRIVATE_KEY`、解析 Endpoint 不置 HAS 标志但直接写 endpoint、解析 PublicKey 置 `WGPEER_HAS_PUBLIC_KEY`、解析 PresharedKey 置 `WGPEER_HAS_PRESHARED_KEY`、解析 PersistentKeepalive 置 `WGPEER_HAS_PERSISTENT_KEEPALIVE_INTERVAL`。这些标志告诉内核「这个字段这次被显式提供了」。除此之外还有几个「行为」标志：`WGDEVICE_REPLACE_PEERS` 表示替换全部 peer，`WGPEER_REMOVE_ME` 表示删除该 peer，`WGPEER_REPLACE_ALLOWEDIPS` 表示替换该 peer 的地址段，`WGALLOWEDIP_REMOVE_ME` 表示从地址段里删除某条。syncconf 的聪明之处就在于它精确操纵这几个行为标志，而不是简单覆盖。常量与标志的完整枚举见 04-06。

第三个核心概念是解析上下文 `config_ctx`。它把「正在构建的设备」「最近的 peer」「最近的 allowedip」「当前处于哪个 INI 段」四个状态穿在一条解析线上。因为 INI 是行式格式，`AllowedIPs = ...` 必须挂到最近一个 `[Peer]` 上，所以工具用 `last_peer` 记住归属；多条 AllowedIPs 行要串成链表，所以用 `last_allowedip` 记住链尾。理解这个上下文，就能理解为什么配置文件里字段的顺序有隐含约束：出现在任何 `[Peer]` 之前的字段会被当成 `[Interface]` 段或报错，而 `[Peer]` 里的字段必然归属于最近那个 peer。

第四个核心概念是两条解析路径的收敛。`config_read_cmd()` 处理命令行数组，只认小写连字符形式的参数名，且私钥来自文件；`config_read_line()` 处理 INI 行，用 `get_value()` 做大小写不敏感的前缀匹配，键名是驼峰形式。两条路径都调用同一批 `parse_port()`、`parse_fwmark()`、`parse_key()`、`parse_endpoint()`、`parse_allowedips()`、`parse_persistent_keepalive()` 辅助函数，因此取值约束完全一致：端口走 `getaddrinfo()` 解析，fwmark 支持十进制与 0x 十六进制及 off，Keepalive 为 1–65535 或 off，endpoint 支持 IPv4、方括号包裹的 IPv6 与主机名。这种「入口不同、约束相同」的设计，是配置语义一致性的根本保证。

### 3. 关键数据结构与源码位置

配置语义的全部秘密集中在三个结构里。`config_ctx` 定义于 `wireguard-tools/src/config.h`，含 `struct wgdevice *device`、`struct wgpeer *last_peer`、`struct wgallowedip *last_allowedip` 三个指针与 `is_peer_section`、`is_device_section` 两个布尔标志。`config_read_init()` 把它清零后分配一个空 device，并在非追加模式下置 `WGDEVICE_REPLACE_PEERS | WGDEVICE_HAS_PRIVATE_KEY | WGDEVICE_HAS_FWMARK | WGDEVICE_HAS_LISTEN_PORT` 四个标志——注意这里把三个 HAS 标志也置上了，意味着 setconf 即使文件里没写私钥、fwmark、listen-port，也会把它们当作「显式设置为零值」下发，从而清空原值，这正是「整体替换」的底层机制。

`peer_origin` 是 `setconf.c` 里为 syncconf 定义的小结构，含 `struct wgpeer *peer` 与 `bool from_file`。sync_conf 把配置文件里的 peer 标记为 `from_file = true`，把从内核读回的运行态 peer 标记为 `false`，然后把两者放进同一个数组按公钥排序。`peer_cmp()` 先按 `public_key` 做 `memcmp`，公钥相同时再按 `from_file` 区分（文件来的排前面），从而让「同一公钥的文件条目与运行态条目」相邻，便于配对比较。

`wgdevice`、`wgpeer`、`wgallowedip` 是解析的产物，其定义来自 uapi 头文件（字段见 05-09），本篇只把它们当作「携带值与标志位的容器」。表 04-02-A 把配置语义相关的源码位置收拢。

读懂这三组结构的关键，是建立「解析产物 = 值 + 标志位」的心智模型：解析器不直接改内核，而是先构建一棵带有丰富标志的设备树，再由 `ipc_set_device()` 一次性序列化下发。所有语义差异——替换、追加、对齐——都体现为「构建这棵树时置了哪些标志」，而不是下发阶段的不同逻辑。syncconf 之所以特殊，仅仅因为它在构建树之后、下发之前，多插入了一个 `sync_conf()` 步骤来修正标志与 peer 列表。

### 4. 关键流程与调用链

文件解析的完整生命周期有四步。`setconf_main()` 先 `fopen()` 配置文件，然后调用 `config_read_init(&ctx, append)`，其中 append 仅当 `argv[0]` 为 `addconf` 时为 true；接着用 `getline()` 逐行读入，每行交给 `config_read_line()`，该函数先截掉 `#` 之后的内容作为注释，再剔除所有空白字符，若清洗后为空行则跳过，否则交给 `process_line()`；所有行读完后调用 `config_read_finish()` 校验每个 peer 都有 `WGPEER_HAS_PUBLIC_KEY`，否则报 `A peer is missing a public key` 并返回失败；最后写入接口名，若为 syncconf 则先 `sync_conf()`，再 `ipc_set_device()`。

`process_line()` 的分派逻辑很清晰：行等于 `[Interface]` 时置 `is_device_section = true`、`is_peer_section = false`；行等于 `[Peer]` 时分配一个新 peer 挂到链表尾，并置 `is_peer_section = true`、`is_device_section = false`，同时给新 peer 置 `WGPEER_REPLACE_ALLOWEDIPS`；在 device 段里用 `key_match()` 匹配 `ListenPort`、`FwMark`、`PrivateKey`；在 peer 段里匹配 `Endpoint`、`PublicKey`、`AllowedIPs`、`PersistentKeepalive`、`PresharedKey`。这里 `key_match` 宏展开为 `get_value(line, key "=")`，而 `get_value()` 用 `strncasecmp`，所以键名大小写不敏感，且等号后紧跟值。

`parse_allowedips()` 是地址段语义的核心。它一开始置 peer 的 `WGPEER_REPLACE_ALLOWEDIPS`，然后对逗号分隔的每个条目调用 `parse_ip_prefix()`：若条目以 `-` 开头，置 `WGALLOWEDIP_REMOVE_ME` 并贯穿到 `+` 分支；`+` 分支清掉 peer 的 `WGPEER_REPLACE_ALLOWEDIPS` 并把指针前移跳过前缀。因此不带前缀的赋值是替换，带 `+` 是增加，带 `-` 是删除。随后 `parse_ip()` 区分 IPv4/IPv6，`strsep()` 拆出 CIDR，缺省掩码 IPv4 为 32、IPv6 为 128，`validate_netmask()` 校验主机位非零时仅打警告 `Warning: AllowedIP has nonzero host part` 而不拒绝。

syncconf 的 `sync_conf()` 算法值得逐段拆解。它先做两个早退：文件无 peer 时直接返回 true（意味着空的 syncconf 配置不会删除任何 peer），读回运行态失败则报错。随后清掉 `file->flags` 的 `WGDEVICE_REPLACE_PEERS`。接着把文件 peer 与运行态 peer 都放进 `peer_origin` 数组，按 `peer_cmp()` 排序。然后遍历数组，专注处理「来自运行态」（`from_file == false`）的条目：若在排序后的数组里找不到同公钥的文件条目，就构造一个 `WGPEER_REMOVE_ME` 的 peer 挂到文件 peer 链表头，表示删除这个多余 peer；若找到了同公钥的文件条目（相邻位置），则处理两种「清零」情形——运行态有预共享密钥而文件条目没有时，把文件条目的 preshared_key 清零并置 HAS 标志以确保下发删除；运行态有 keepalive 而文件条目没有时，把文件条目的 keepalive 置 0 并置 HAS 标志。这样 syncconf 最终下发的树，既表达了文件里显式写出的值，也补齐了「需要被清除」的字段，同时不触碰那些未变化的 peer 会话。

### 5. 配置/命令/代码实例

先给出一份典型的 INI 配置文件，它是 setconf 与 syncconf 的共同输入，也是 showconf 的输出格式：

```bash
cat > /etc/wireguard/wg0.conf <<'EOF'
[Interface]
PrivateKey = yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=
ListenPort = 51820
FwMark = 0xca6c

[Peer]
PublicKey = xTIBA5rboUvnH4htodjb6e697QjLERt1NAB4mZqp8Dg=
PresharedKey = I+Hm1nP3KjZ8rQ7vT2wL9xY4uB6cD0eF3gA5sN1mHk=
AllowedIPs = 10.0.0.2/32, 10.0.0.3/32
Endpoint = 203.0.113.9:51820
PersistentKeepalive = 25
EOF

# 三种应用方式：语义分别是对齐、覆盖、叠加
wg syncconf wg0 /etc/wireguard/wg0.conf
wg setconf wg0 /etc/wireguard/wg0.conf
wg addconf wg0 /etc/wireguard/wg0.conf
```

配置文件中注释以 `#` 开头，空白会被剔除，段名与键名大小写不敏感；`AllowedIPs` 一行给出多个逗号分隔的 CIDR。表 04-02-B 从语义维度对比四种配置途径，这是本节的核心表格。

表 04-02-B　四种配置途径语义对比
| 维度 | set | setconf | addconf | syncconf |
|---|---|---|---|---|
| 输入形态 | 命令行键值对 | INI 文件 | INI 文件 | INI 文件 |
| 解析函数 | config_read_cmd | config_read_line | config_read_line | config_read_line |
| REPLACE_PEERS | 不置 | 置位 | 不置 | 先清后置删除项 |
| 未列出的 peer | 保留 | 删除 | 保留 | 删除（显式 REMOVE_ME） |
| 未列出的接口字段 | 保留 | 清零 | 保留 | 保留 |
| 是否读回运行态 | 否 | 否 | 否 | 是（ipc_get_device） |
| 对现有会话影响 | 点改，局部 | 重建，打断 | 局部保留 | 尽量不打断 |
| 相对效率 | 高 | 高 | 高 | 较低 |
| 典型用途 | 临时改动、脚本 | 首次下发、全量替换 | 批量追加 peer | 热更新、保留会话 |

用 `wg showconf wg0` 可以把当前运行态导出为同样的 INI 格式，便于核对 syncconf 的结果。下面给出示例输出（示例输出，具体格式需对照实际版本核验）：

```text
示例输出，具体格式需对照实际版本核验
[Interface]
ListenPort = 51820
FwMark = 0xca6c
PrivateKey = yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=

[Peer]
PublicKey = xTIBA5rboUvnH4htodjb6e697QjLERt1NAB4mZqp8Dg=
PresharedKey = I+Hm1nP3KjZ8rQ7vT2wL9xY4uB6cD0eF3gA5sN1mHk=
AllowedIPs = 10.0.0.2/32, 10.0.0.3/32
Endpoint = 203.0.113.9:51820
PersistentKeepalive = 25
```

逐行判读如下。`[Interface]` 是 showconf.c 固定打印的段头，对应 config.c 的 `process_line()` 里 `[Interface]` 分支所识别的段名。[Interface] 段内三行的输出顺序由 showconf.c 的 printf 次序决定：先 `ListenPort`（`device->listen_port` 非零才打印），对应配置解析里的 `ListenPort` 键与 `parse_port()`；再 `FwMark`（非零才打印，格式为 `0x%x`），对应 `FwMark` 键与 `parse_fwmark()`；最后 `PrivateKey`（仅当 `WGDEVICE_HAS_PRIVATE_KEY` 置位才打印），对应 `PrivateKey` 键与 `parse_key()`。空行是 showconf.c 在 Interface 段末尾主动打印的分隔。
`[Peer]` 段头由 `for_each_wgpeer()` 循环内打印，每个 peer 一个段；`PublicKey` 由 `key_to_base64(peer->public_key)` 产生，是 config_read_finish() 强制要求存在的字段。`PresharedKey` 仅当 `WGPEER_HAS_PRESHARED_KEY` 置位才打印，对应解析里的 `PresharedKey` 键——syncconf 在文件条目缺该字段但运行态有时，会主动清零并置 HAS 标志，确保这里不再输出旧密钥。`AllowedIPs` 由遍历 `first_allowedip` 链表并用 `inet_ntop()` 加 `cidr` 拼接，多个条目以逗号分隔，正好能被 `parse_allowedips()` 读回。`Endpoint` 由 `getnameinfo()` 加 `NI_NUMERICHOST` 渲染，IPv6 会包方括号，对应 `parse_endpoint()` 支持的格式。`PersistentKeepalive` 仅在间隔非零时打印，对应 `parse_persistent_keepalive()`，值为 1–65535 秒。整段输出构成了一个可被 setconf/syncconf 原样回灌的闭合格式，这正是 showconf 的设计目的。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是以为 syncconf 只是「更温和的 setconf」。它确实不打断会话，但语义上仍以配置文件为准：`sync_conf()` 会把运行态里存在、文件里未列出的 peer 构造为 `WGPEER_REMOVE_ME` 并下发删除。因此用一份「只包含部分 peer」的配置文件做 syncconf，会删掉其余 peer，这和 setconf 的删除结果一致，只是过程更精细。唯一例外是空配置（无 peer）时 sync_conf 早退，不会删除任何 peer——这是一个容易误解的边界。

第二个陷阱是混淆「peer 级替换」与「地址段级替换」。`WGPEER_REPLACE_PEERS` 作用于整个接口的 peer 集合，由 setconf 置位；`WGPEER_REPLACE_ALLOWEDIPS` 作用于单个 peer 的地址段，在每个 `[Peer]` 段出现时由 config.c 置位。前者删除 peer，后者只清空该 peer 的 AllowedIPs。当你在配置里写了 `AllowedIPs =` 空值，`parse_allowedips()` 会把该 peer 的地址段清空，但 peer 本身仍在——这与删掉整个 `[Peer]` 段（配合 REPLACE_PEERS 才会删 peer）是两件事。

第三个陷阱是忽略接口字段在 syncconf 中的处理差异。对比表 04-02-B 可见：setconf 因 config_read_init 把 `WGDEVICE_HAS_PRIVATE_KEY | WGDEVICE_HAS_FWMARK | WGDEVICE_HAS_LISTEN_PORT` 都置上，未写出的接口字段会被清零；而 syncconf 清掉 REPLACE_PEERS 后走差异逻辑，只在文件里显式给出的字段才会改动，未列出的接口字段保持原值。这意味着若想用 syncconf 清空 fwmark，必须在文件里显式写 `FwMark = 0` 或 `off`，而不是省略该行。这一差异常被误用。

第四个陷阱是配置文件的格式细节。# 注释、行内空白剔除、大小写不敏感都是 config.c 实现的；但键名必须与 `key_match()` 里的字面量一致（如 `PersistentKeepalive` 而非 `PersistentKeepaliveInterval`），且每个 peer 必须有 `PublicKey`，否则 config_read_finish() 直接拒绝整份配置。另外私钥与 PresharedKey 在配置文件里直接写 base64 字符串（这与命令行要求文件路径不同），因此配置文件本身是敏感文件，必须限制权限（建议 0600）。

最佳实践：把「期望状态」完整地写进一份配置文件，日常热更新一律用 `syncconf`，既保证结果收敛又保留会话；首次部署或需要彻底重置时用 `setconf`；临时给正在运行的接口追加一个 peer 用 `addconf`；单点参数微调用 `set`，并记得 `allowed-ips` 默认替换、需要增量时加 `+`。每次改动后用 `wg show <iface> latest-handshakes` 确认会话未被打断、用 `wg showconf <iface>` 核对落盘结果（状态字段含义见 04-01、排障见 08-03）。涉及密钥的配置变更要同步更新分发与权限管理（密钥流程见 03-03）。

### 7. 小结与延伸阅读

本篇聚焦 syncconf、set、setconf 三种配置途径的语义差异：四者共用 `config.c` 的解析引擎，却在构建 `wgdevice` 树时置不同标志——set 点改、setconf 置 REPLACE_PEERS 覆盖、addconf 不清标志叠加、syncconf 通过 `sync_conf()` 读回运行态、按公钥排序比对、删除多余 peer 并补齐需清零字段，从而在不打断会话的前提下让状态对齐配置文件。解析生命周期为 `config_read_init` → `config_read_line`/`process_line` → `config_read_finish` → `sync_conf`（仅 syncconf）→ `ipc_set_device`；地址段的替换与 + / - 增量由 `parse_ip_prefix()` 操纵 `WGPEER_REPLACE_ALLOWEDIPS` 与 `WGALLOWEDIP_REMOVE_ME` 实现。showconf 的输出与解析器输入构成闭合格式，可原样回灌。
