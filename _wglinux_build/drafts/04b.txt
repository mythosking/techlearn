## 04-03 wg-quick 配置参数全集

### 1. 背景与动机

wg-quick 不是 C 程序，而是一段 bash 脚本，这是理解它全部参数的起点。在 wireguard-tools 源码树里，它的主体是 `src/wg-quick/linux.bash`（Linux 版本；同目录还有 darwin.bash、freebsd.bash、openbsd.bash 与 android.c 等平台变体），由 `src/wg-quick/wg` 这个包装脚本负责按当前平台分派到对应实现。它的权威手册是 `src/man/wg-quick.8`。本套资料的事实锚点是 wireguard-tools 1.0.20260223（`src/version.h` 中 `WIREGUARD_TOOLS_VERSION "1.0.20260223"`），下文所有键名、默认值、函数名与调用顺序均以该快照的 `linux.bash` 和 `wg-quick.8` 为准；平台变体之间的差异需对照实际系统核验。

为什么要单独为 wg-quick 的参数立一篇权威源？因为 wg-quick 在 `wg(8)` 的配置文件格式之上「额外」定义了一批键，而手册 wg.8 与 wg-quick.8 各讲一半，社区资料又常把两者混写，导致实践里频繁出现「把 Address 当成 wg 原生键」「以为 Table=off 只是不写路由」这类错误。source of truth 只有一个：`linux.bash` 的 `parse_options()` 函数里那个 `case "$key" in` 分支，它逐字列出了 wg-quick 自己吃掉、不再转发给 wg 的键；其余所有键都由 `set_config()` 原样交给 `wg addconf`。换句话说，wg-quick 的参数面 = wg 原生配置键（见 04-04 的统一格式描述）+ 九个 Interface 段扩展键 + 四个子命令。本篇把后两者完整、逐项、按源码列出，作为全册引用这些参数时的唯一权威出处。

从设计意图看，手册 wg-quick.8 开宗明义说它是「an extremely simple script for easily bringing up a WireGuard interface, suitable for a few common use cases」，是「just a simple script that wraps invocations to wg(8) and ip(8)」。这句话决定了它的参数风格：不是有一套独立的配置语言，而是用 wg 的 INI 文件做载体，在 `[Interface]` 段里塞进几个「脚本自己解释」的键，再自动完成地址分配、MTU 计算、路由推断、DNS 下发与防火墙规则。理解了「包装器」这一定位，就能明白为什么它的参数大多对应一条 or 多条 `ip` 命令：Address 对应 `ip address add`，MTU 对应 `ip link set mtu`，Table 对应 `ip route add ... table`，而 PreUp/PostUp 之类干脆就是让你自己塞任意 bash 命令的逃生口。对进阶需求，手册明确建议改用更完整的网络管理器或直接用 wg 与 ip——这条边界也应写进参数手册的适用说明里。

### 2. 核心概念

要准确掌握 wg-quick 的参数，先建立三组概念：**四个子命令、九个扩展键、一个转发规则**。

四个子命令来自 `wg-quick.8` 的 SYNOPSIS 与 `linux.bash` 末尾的参数分派：`up`（建接口并配置）、`down`（拆接口，可选先保存配置）、`save`（不拆接口，直接把当前状态写回配置文件）、`strip`（输出剔除 wg-quick 扩展键后的纯 wg 配置，常与 `wg syncconf` 配合热重载）。入口参数形式统一为 `wg-quick <up|down|save|strip> <CONFIG_FILE|INTERFACE>`；给接口名时按手册与 `parse_options()` 第 43 行展开为 `/etc/wireguard/<接口名>.conf`，并会继续搜索发行版特定路径。接口名必须符合正则 `[a-zA-Z0-9_=+.-]{1,15}`——这既是 `parse_options()` 第 43、45 行的校验，也是内核 netdev 名字长度限制的体现；`wg0`、`wgvpn0`、`nyc`、`paris` 都合法。

九个扩展键全部位于 `[Interface]` 段，由 `parse_options()` 在读到该段时截获：`Address`、`DNS`、`MTU`、`Table`、`PreUp`、`PostUp`、`PreDown`、`PostDown`、`SaveConfig`。关键判别细节是：`parse_options()` 用 `stripped="${line%%\#*}"` 先去掉 `#` 后的注释，再分别计算 `key` 与 `value`；但 Pre/Post 四个钩子键刻意使用 `unstripped_value`（第 54 行）——保留注释符号后的原文，因为防火墙命令里合法出现 `#` 的场景需要原样传给 bash。钩子里的特殊串 `%i` 在 `execute_hooks()` 第 294 行被替换为接口名；可重复出现，按出现顺序执行。这些是别的资料极少写清、却直接影响参数行为的细节。

一个转发规则指：除了上述九个键，`parse_options()` 会把【所有】其余行原样累积进 `WG_CONFIG`（第 72 行 `WG_CONFIG+="$line"$'\n'`），最终由 `set_config()` 通过 `cmd wg addconf "$INTERFACE" <(echo "$WG_CONFIG")` 交给 wg。因此 `[Peer]` 段的 PublicKey、AllowedIPs、Endpoint 等键，以及 `[Interface]` 段里的 PrivateKey、ListenPort、FwMark，都不是 wg-quick 的「自有参数」，而是 wg 原生配置键（其格式与解析规则见 04-04）。下表给出 wg-quick 自有参数的全集，逐项标注取值、默认、重复性与源码依据，作为权威速查。

### 3. 关键数据结构与源码位置

wg-quick 没有结构体，它的「状态」是 `linux.bash` 顶部的全局 shell 变量。理解这些变量与操作它们的函数，就等价于理解了它的内部数据结构。变量集中在第 14–28 行：`INTERFACE`（从配置文件名正则捕获的接口名）、`CONFIG_FILE`（规范化后的绝对路径）、`WG_CONFIG`（要转发给 wg 的配置文本）、`ADDRESSES`（地址数组）、`MTU`（标量字符串）、`DNS` 与 `DNS_SEARCH`（两个数组，分别存服务器与搜索域）、`TABLE`（路由表标量）、`PRE_UP`/`POST_UP`/`PRE_DOWN`/`POST_DOWN`（四个钩子数组）、`SAVE_CONFIG`（0/1 整数），以及两个流程标志 `HAVE_SET_DNS` 与 `HAVE_SET_FIREWALL`，用于 down 时判断是否要撤销 DNS 与防火墙改动。

函数分层很清晰。`parse_options()`（第 40–75 行）是唯一的解析入口，负责文件定位、权限警告、逐行切分与上面九个键的截获；`read_bool()`（第 77–83 行）只接受字面量 `true`/`false`，否则 `die`。配置生效由 `cmd_up()`（第 327–344 行）编排，依次调用 `add_if()`（第 89–97 行，`ip link add`，失败时回退 wireguard-go）、`execute_hooks()`（钩子执行）、`set_config()`（第 251–253 行，`wg addconf`）、`add_addr()`（第 120–124 行，按地址含冒号选 `-4`/`-6`）、`set_mtu_up()`、`set_dns()`、`add_route()`。拆卸侧由 `cmd_down()` 编排 `del_if()`（第 99–118 行）、`save_config()`（第 255–289 行）、`unset_dns()`、`remove_firewall()`。默认路由的特殊处理集中在 `add_default()`（第 213–249 行）与 `get_fwmark()`（第 182–188 行）。`save_config()` 会重建 `[Interface]` 头、再拼接 `wg showconf` 的输出；`cmd_strip()` 只回显 `WG_CONFIG`。这些函数的行号是后续交叉引用与排障的直接索引。

从文档与集成角度看，参数还有两个「外部接口」：手册 `src/man/wg-quick.8` 的 CONFIGURATION 段给出九个键的自然语言定义，`cmd_usage()`（第 300–325 行）则内嵌了一份等价的 `--help` 文本；`src/systemd/wg-quick@.service` 与 `wg-quick.target` 把 `wg-quick up %i` 接入 systemd，说明这些参数在开机启动时同样被 `parse_options()` 重新解析一遍，并不存在「systemd 专有参数」。bash 补全在 `src/completion/wg-quick.bash-completion`，负责键名补全。模块职责属于 07-13，这里只点名不展开。

### 4. 关键流程与调用链

`up` 流程最能体现参数如何变成命令。`cmd_up()` 先检查接口是否已存在（`ip link show dev`），再设置 `trap 'del_if; exit'` 保证中途失败能回滚，然后 `add_if` 建接口、`execute_hooks` 跑 PreUp、`set_config` 把 `WG_CONFIG` 喂给 `wg addconf`——注意这一步才真正写入 PrivateKey、ListenPort、Peer 等原生键。接着按 `ADDRESSES` 逐个 `add_addr`，`set_mtu_up` 设 MTU 并 up 接口，`set_dns` 经 resolvconf 下发 DNS。路由部分是一个循环：从 `wg show ... allowed-ips` 取所有前缀，按前缀长度降序（`sort -nr -k 2 -t /`）逐个 `add_route`；`add_route()` 遇到 `Table=off` 直接返回，遇到自定义表用 `ip route add ... table`，遇到 `*/0` 转 `add_default()`，其余用普通 `ip route add`。最后跑 PostUp 并解除 trap。

`add_default()` 是 wg-quick 最复杂的参数副作用。当 AllowedIPs 含默认路由且 `Table` 为 `auto` 或空时，`get_fwmark` 先读 `wg show fwmark`；若未设置则从 51820 起找一个未占用的表号，`wg set ... fwmark` 写入，再用 `ip rule add not fwmark <表号> table <表号>` 与 `ip rule add table main suppress_prefixlength 0` 做策略路由，默认路由写进该表，最后用 nftables 或 iptables 打上 `wg-quick(8) rule for <接口>` 注释的防泄漏规则，并按需打开 `net.ipv4.conf.all.src_valid_mark`。这就是「Table=auto 自动处理默认网关」的完整含义——它远不止一条路由。整个参数到命令的映射关系见图 04-03-01。

图中节点速览（便于在不渲染框内文字的预览器中阅读）：`parse_options` 截获九个扩展键，其余行进入 `WG_CONFIG` 转发给 wg；`cmd_up` 编排全流程，先 `add_if + add_addr` 建接口配地址，再 `set_mtu_up` 自动算 MTU 减 80，然后 `add_route` 做路由推断，遇到默认路由转 `add_default` 用 fwmark 与 ip rule 处理，钩子 `PreUp/PostUp` 由 `execute_hooks` 在首尾执行。

`down` 流程与 `up` 近似镜像：`cmd_down()` 先确认接口确为 WireGuard 接口，跑 PreDown，若 `SaveConfig=true` 则 `save_config()` 写回，再 `del_if()`——它会在 `Table` 为空或 `auto` 且存在 `/0` 时，按 fwmark 清掉策略路由规则，再 `ip link delete`；最后依次撤销 DNS、防火墙、跑 PostDown。`save` 只调用 `save_config()`，`strip` 只回显 `WG_CONFIG`，两者都不改接口状态。值得注意的是，`parse_options()` 对四个子命令一视同仁地先跑一遍，所以 `strip` 与 `save` 也会校验配置文件路径、打印权限警告——这是理解其报错来源的关键。

### 5. 配置/命令/代码实例

下面给出一个「全参数」客户端配置，把九个扩展键与必要的 wg 原生键放在同一文件里，文件名设为 `/etc/wireguard/wg0.conf`，可直接对应 `parse_options()` 的解析路径：

```ini
[Interface]
Address = 10.200.100.8/24, fd00::8/64
DNS = 10.200.100.1, 1.1.1.1, example.internal
MTU = 1420
Table = auto
PrivateKey = oK56DE9Ue9zK76rAc8pBl6opph+1v36lm7cXXsQKrQM=
PostUp = iptables -I OUTPUT ! -o %i -m mark ! --mark $(wg show %i fwmark) -j REJECT
PreDown = iptables -D OUTPUT ! -o %i -m mark ! --mark $(wg show %i fwmark) -j REJECT
SaveConfig = false

[Peer]
PublicKey = GtL7fZc/bLnqZldpVofMCD6hDjrK28SsdLxevJ+qtKU=
AllowedIPs = 0.0.0.0/0, ::/0
Endpoint = demo.wireguard.com:51820
PersistentKeepalive = 25
```

这里 `Address` 一行给了 IPv4 与 IPv6 两个地址，`parse_options()` 第 59 行按逗号拆成数组；两个 DNS IP 进 `DNS` 数组、`example.internal` 进 `DNS_SEARCH`；`PostUp`/`PreDown` 里的 `%i` 会在 `execute_hooks()` 中替换为 `wg0`；`AllowedIPs` 含 `0.0.0.0/0` 会触发 `add_default()`。执行启动命令：

```bash
wg-quick up wg0
```

对应输出（示例输出，具体格式需对照实际版本核验；`[#]` 行由 `cmd()` 第 31 行打印到 stderr）：

```text
[#] ip link add wg0 type wireguard
[#] wg addconf wg0 /dev/fd/63
[#] ip -4 address add 10.200.100.8/24 dev wg0
[#] ip -6 address add fd00::8/64 dev wg0
[#] ip link set mtu 1420 up dev wg0
[#] resolvconf -a tun.wg0 -m 0 -x
[#] wg set wg0 fwmark 51820
[#] ip -4 rule add not fwmark 51820 table 51820
[#] ip -4 rule add table main suppress_prefixlength 0
[#] ip -4 route add 0.0.0.0/0 dev wg0 table 51820
[#] iptables-restore -n
[#] iptables -I OUTPUT ! -o wg0 -m mark ! --mark $(wg show wg0 fwmark) -j REJECT
```

逐行判读如下。第一行 `ip link add wg0 type wireguard` 来自 `add_if()` 的 `cmd ip link add dev "$INTERFACE" type wireguard`，说明接口是从零创建的，若该命令失败且内核模块缺失，脚本会打印回退提示并调用 `wireguard-go`。第二行 `wg addconf` 来自 `set_config()`，参数是进程替换生成的 `/dev/fd/63`，其内容正是去掉九个扩展键后的 `WG_CONFIG`，证实 PrivateKey、Peer 等原生键是这一刻才写入内核的。第三、四行是 `add_addr()` 对 `ADDRESSES` 的两次调用：地址含冒号则选 `ip -6`，否则 `ip -4`，对应配置里逗号拆分出的两个地址。第五行 `ip link set mtu 1420 up` 来自 `set_mtu_up()` 的显式 MTU 分支（第 128–130 行），因为配置写了 `MTU=1420`，自动计算路径被跳过。第六行 `resolvconf -a tun.wg0 -m 0 -x` 来自 `set_dns()`，前缀 `tun.` 由 `resolvconf_iface_prefix()` 探测 `/etc/resolvconf/interface-order` 得到，说明两个 DNS IP 与搜索域已下发。第七行 `wg set wg0 fwmark 51820` 来自 `add_default()`，因为 `Table=auto` 且 AllowedIPs 含 `0.0.0.0/0` 而 fwmark 未预设，脚本从 51820 起选了空闲表号。第八、九行两条 `ip rule` 是策略路由核心：`not fwmark 51820 table 51820` 让打标流量走独立表，`table main suppress_prefixlength 0` 让主表默认路由被抑制，避免绕过隧道。第十行把默认路由写进 51820 表。第十一行 `iptables-restore -n` 是 `add_default()` 写入的防泄漏规则（带 `wg-quick(8) rule for wg0` 注释），第十二行才是配置里 `PostUp` 的自定义 kill-switch，其中 `$(wg show wg0 fwmark)` 已被 `%i` 替换与 shell 展开为实际 fwmark。整个输出验证了九个扩展键各自变成了哪几条系统命令，是理解参数语义最直接的证据。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是误以为 wg-quick 有自己的配置解析器。它只是 bash 字符串处理：`parse_options()` 用 `${line%%\#*}` 去注释、用 `${stripped%%=*}` 与 `${stripped#*=}` 切键值；没有转义、没有多行续行、没有引号语义。因此值里出现 `#` 会被截断（Pre/Post 钩子的 `unstripped_value` 例外），键名大小写虽因 `shopt -s nocasematch` 而不敏感，但值里的空格会被当作数组分隔；`SaveConfig` 的值则由 `read_bool()` 用精确的 `case true|false` 匹配，`True`、`TRUE` 都会触发 `die`，与键名的宽松形成鲜明对比。第二个陷阱是 `SaveConfig=true` 的破坏性：手册 wg-quick.8 明确警告「Any changes made to the configuration file before the interface is removed will therefore be overwritten」——`save_config()` 会用当前接口状态重建整个 `[Interface]` 头，你手改的注释、格式甚至扩展键顺序都可能丢失，运维上应把它当作「状态快照」而非「手写文件」。第三个陷阱是 `Table` 的三种语义混淆：`off` 完全不建路由（适合自己管路由），`auto`（默认）会触发默认路由的 fwmark 与策略路由全套机制，自定义表则只把路由加到你指定的表——三者行为差异极大，选错直接导致「隧道通但没路由」或「全局流量被劫持」。

第四个陷阱是 DNS 依赖：`set_dns()` 走的是 `resolvconf -a`，在 systemd-resolved 或 NetworkManager 管理的系统上可能不生效，手册也提示可用 PostUp/PostDown 自定义替代。第五个陷阱是 MTU 自动计算的取整：`set_mtu_up()` 先按每个 endpoint 做 `ip route get` 取链路 MTU，再减 80 字节封装开销，兜底值 1500 再减 80 得 1420；若 endpoint 是域名且解析受阻，可能退回兜底值，因此高丢包或分片场景应显式写 `MTU`。第六个陷阱是钩子的 `eval` 语义：`execute_hooks()` 第 296 行用 `(eval "$hook")`，意味着钩子在子 shell 中以当前用户（已 `auto_su` 提权到 root）执行，来源不可信的配置等于把 root 命令写进文件，配置文件权限必须收紧——`parse_options()` 第 47 行对 world-accessible 文件只打警告不阻断，这一点尤需注意。第七个陷阱是接口名正则 `[a-zA-Z0-9_=+.-]{1,15}` 同时用于文件定位与内核名，超长或含非法字符会在第 45 行 `die`。

还有一个隐蔽陷阱涉及钩子与 `set -e`：脚本第 7 行 `set -e -o pipefail` 意味着任一钩子返回非零会立刻中止整个 up/down 流程，而 `trap` 又会触发 `del_if` 回滚，表现为「接口建了又瞬间消失」。因此 PreUp/PostUp 里若写了可能失败的探测命令，务必自行用 `|| true` 兜底，把「探测失败」和「流程失败」区分开。与之相关的是 `down` 流程的幂等性：`cmd_down()` 第 347 行先检查接口是否在 `wg show interfaces` 列表中，重复执行 down 会直接 `die`，而在接口已被手工删除的情况下再跑 down 同样报错——编排脚本里应把这类错误视为可忽略，而不是当作严重故障。对 `Address` 还要注意 CIDR 语义：它只是给接口配地址，真正决定「哪些流量走隧道」的是 Peer 段的 `AllowedIPs`，两者写混是「有地址却不通」的常见根因。

最佳实践可归纳为四步：先用 `wg-quick strip wg0` 观察纯 wg 配置，确认原生键部分正确，再决定扩展键；再从最小配置（Address + PrivateKey + 一个 Peer）起步，用 `wg show wg0 latest-handshakes` 确认握手，而不是只看接口 up；随后按是否需要全局代理决定 `Table`——全隧道用默认 `auto` 并理解其 fwmark 副作用，分流或自建路由用 `off` 配合 PostUp；最后用 `wg syncconf wg0 <(wg-quick strip wg0)` 热重载 peer 变更而不中断现有会话（这条命令直接来自 wg-quick.8 的 EXAMPLES）。对 DNS、kill-switch、策略路由等高级需求，优先用 PostUp/PreDown 显式表达并配好撤销逻辑，确保 down 后系统干净。数据面原理与握手时序不在本篇展开（原理见 06-01 ｜ 命令全集见 04-01 ｜ 配置格式见 04-04 ｜ 字段见 05-09）。

### 7. 小结与延伸阅读

本篇把 wg-quick 的参数收敛为「四个子命令 + 九个 Interface 扩展键 + 一条转发到 wg addconf 的规则」：`up/down/save/strip` 由 `linux.bash` 末尾分派；`Address/DNS/MTU/Table/PreUp/PostUp/PreDown/PostDown/SaveConfig` 由 `parse_options()` 在 `[Interface]` 段截获并分别落到 shell 变量；其余行原样进入 `WG_CONFIG` 交给 wg。九个键的取值、默认、重复性与行号依据已在第 2 节表格中列全，参数层面不再有遗漏项。`cmd_up` 的调用链把每个参数翻译成具体的 `ip`/`wg`/`resolvconf` 命令，`add_default()` 则解释了 `Table=auto` 为何会牵动 fwmark、ip rule 与防火墙——这是 wg-quick 与裸 wg 最本质的区别。

延伸阅读建议按三条线走：参数层面，wg 命令行全集见 04-01、`setconf/syncconf` 语义见 04-02、配置文件格式与 ini 解析见 04-04；机制层面，默认路由的策略路由与 fwmark 原理见 06-14，握手与定时器见 06-02、06-11；模块层面，wg-quick 在用户态工具中的位置见 07-13，systemd 集成见 03-05。跨册随查按（字段见 05-09 ｜ 参数见 04-01 ｜ 原理见 06-14 ｜ 模块见 07-13）执行：结构体逐字段去 05、命令全集去 04 的对应篇、机制与调用链去 06、目录级模块能力去 07。凡本篇标注「需对照实际版本核验」的默认值、平台变体差异与发行版搜索路径，均以 `_wglinux_build/upstream_src/wireguard-tools/` 下 `src/wg-quick/linux.bash` 与 `src/man/wg-quick.8` 为准，本套资料不编造未核验的路径与取值。

## 04-04 配置文件格式与 ini 解析规则全集

### 1. 背景与动机

WireGuard 的配置「文件」不是一个独立发明的格式，而是构建在 INI 之上的一套极简约定，并且存在两个彼此独立的解析器：用户态 C 程序 wg 用 `src/config.c` 解析，wg-quick 脚本用 `src/wg-quick/linux.bash` 的 `parse_options()` 解析。本篇是这两套格式与解析规则的唯一权威源，落点是 `config.c`、`config.h`、`ctype.h`、`encoding.c` 与手册 `src/man/wg.8` 的 CONFIGURATION FILE FORMAT 段；wg-quick 侧双层解析的分工已在 04-03 交代，本篇只在差异处回指，不重复展开其九个扩展键。版本基准同为 wireguard-tools 1.0.20260223，所有函数名、行号、错误文本与常量均取自该快照，个别细节需对照实际版本核验。

为什么解析规则值得单独成篇？因为 wg 的配置看似朴素，实则藏着大量「只在此处成立」的判定：注释字符固定为 `#` 且在空白处被提前截断；键名匹配是大小写不敏感的前缀比较；整行会先删掉所有空白字符再做匹配；AllowedIPs 的 `+`/`-` 前缀会改变整批地址的替换语义；endpoint 的域名解析带指数退避重试；base64 密钥校验要求固定 44 字符加尾随 `=`。这些规则决定了「同样的文本写对还是写错」，却分散在十来个静态函数里。社区里关于「能不能写行内注释」「AllowedIPs 能不能写成 10.0.0.1/24 而不检查主机位」「域名写错为什么卡很久才报错」的争论，答案都可以在这几个函数里逐行找到，而无需猜测。

从设计哲学看，这套格式刻意保持「最小可解析面」：只有两个顶层段（`[Interface]`、`[Peer]`），键与值之间一个等号，没有嵌套、没有转义、没有多行续行、没有类型系统。手册 wg.8 第 132–134 行写明格式基于 INI，允许多个 `[Peer]` 段但只允许一个 `[Interface]` 段；第 180 行写明「Characters after and including a '#' are considered comments and are thus ignored」。这种极简让解析器可以用几百行 C 完成，也带来严格的书写纪律——理解这些纪律，比记住键名更重要。本篇的目标就是把纪律还原成可核查的函数与常量，而不是罗列「应该怎么写」的经验之谈。

### 2. 核心概念

解析的核心概念可以压缩为四句话：**两段结构、逐行状态机、标志位驱动、失败即回滚**。

两段结构指 `[Interface]` 与 `[Peer]` 两种顶层段。`process_line()`（第 436 行）用 `strcasecmp` 判断整行是否等于 `[Interface]` 或 `[Peer]`——注意是大小写不敏感的全行比较，所以 `[PEER]`、`[peer]` 都合法，但 `[Peer] # 注释` 不合法，因为注释已在 `config_read_line()` 里被剥掉、行首行尾空白也被删净。`[Interface]` 把 `ctx->is_device_section` 置 1；`[Peer]` 则 `calloc` 一个新 `struct wgpeer` 挂到链表尾，同时把 `ctx->last_allowedip` 清空、`WGPEER_REPLACE_ALLOWEDIPS` 置位。换句话说，每遇到一个 `[Peer]` 就新建一个 peer 对象，后续所有键都归属于「最近这个 peer」。

逐行状态机由 `config_ctx`（`config.h` 第 15–20 行）承载：`device` 指向根 `wgdevice`，`last_peer` 与 `last_allowedip` 指向当前正在填充的对象，两个布尔量标记当前在哪一段。`config_read_init()` 初始化上下文，`config_read_line()` 逐行喂入，`config_read_finish()` 收尾校验。标志位驱动指每个解析函数成功后都会给相应对象打上 `WGDEVICE_HAS_*` 或 `WGPEER_HAS_*` 位，例如 `parse_port()` 打 `WGDEVICE_HAS_LISTEN_PORT`、`parse_persistent_keepalive()` 打 `WGPEER_HAS_PERSISTENT_KEEPALIVE_INTERVAL`；这些位决定该字段是否真的下发到内核，未打位的字段等于没配置。失败即回滚指 `config_read_line()` 出错时调用 `free_wgdevice(ctx->device)` 释放整棵树，`config_read_finish()` 发现 peer 缺公钥时同样释放并返回 NULL。

下表把全部配置键按段归类，给出解析函数、取值规则与所置标志位，作为权威速查。表中「设备段」即 `[Interface]`，「对等段」即 `[Peer]`；注意 wg-quick 的九个扩展键不在此列（见 04-03）。

| 键 | 段 | 解析函数 | 取值规则 | 所置标志 |
|---|---|---|---|---|
| `PrivateKey` | 设备段 | `parse_key()` | base64，固定 44 字符加尾 `=`，解出 32 字节 | `WGDEVICE_HAS_PRIVATE_KEY` |
| `ListenPort` | 设备段 | `parse_port()` | 16 位端口，经 getaddrinfo 解析服务名，不可为空 | `WGDEVICE_HAS_LISTEN_PORT` |
| `FwMark` | 设备段 | `parse_fwmark()` | `off`/`0` 或 0–0xffffffff，支持 `0x` 十六进制 | `WGDEVICE_HAS_FWMARK` |
| `PublicKey` | 对等段 | `parse_key()` | base64 32 字节，peer 必填 | `WGPEER_HAS_PUBLIC_KEY` |
| `PresharedKey` | 对等段 | `parse_key()` | base64 32 字节，可选，叠加对称密钥抗量子 | `WGPEER_HAS_PRESHARED_KEY` |
| `AllowedIPs` | 对等段 | `parse_allowedips()` | 逗号分隔，可带 `/cidr`，可加 `+`/`-` 前缀，可重复 | `WGPEER_REPLACE_ALLOWEDIPS`（或清除/`WGALLOWEDIP_REMOVE_ME`） |
| `Endpoint` | 对等段 | `parse_endpoint()` | `ip:port` 或 `[IPv6]:port` 或 `域名:port` | 无标志，直接写 sockaddr |
| `PersistentKeepalive` | 对等段 | `parse_persistent_keepalive()` | `off`/`0` 或 1–65535 秒 | `WGPEER_HAS_PERSISTENT_KEEPALIVE_INTERVAL` |

### 3. 关键数据结构与源码位置

`config.h` 定义的 `struct config_ctx` 是整个解析过程的状态容器，仅五字段：指向 `wgdevice` 的 `device`、`last_peer`、`last_allowedip`，以及 `is_peer_section`、`is_device_section` 两个布尔量。它把「当前在哪个段、当前对象是谁」显式化，使逐行解析无需回溯。真正的配置树由 uapi 侧的 `struct wgdevice`、`struct wgpeer`、`struct wgallowedip` 组成：device 通过 `first_peer` 串起 peer 链表，peer 通过 `first_allowedip` 串起地址链表，每个节点还带 `flags` 字段记录上述 `HAS_*` 位。这些结构的逐字段定义属于 05-09，本篇只把它们当作解析的输出容器点名，不展开字段表。

解析函数集中在 `config.c`，可分三组。工具组：`get_value()`（第 25–37 行）做 `strncasecmp` 前缀匹配，`key_match(key)` 宏（第 465 行）展开为 `value = get_value(line, key "=")`；`char_is_space()`/`char_is_digit()` 来自 `ctype.h`，是实现为位运算的常量时间判定，不依赖 locale。字段组：`parse_port`、`parse_fwmark`、`parse_key`、`parse_keyfile`、`parse_ip`、`parse_endpoint`、`parse_persistent_keepalive`、`parse_allowedips`，各自负责把字符串变成 uapi 结构字段。流程组：`process_line()` 分派、`config_read_line()` 清洗、`config_read_init()`/`config_read_finish()` 生命周期，以及供命令行参数复用的 `config_read_cmd()`（第 588 行）。密钥编解码在 `encoding.c`：`key_from_base64()` 要求长度恰为 `WG_KEY_LEN_BASE64 - 1`（44）且倒数第二字符为 `=`，`key_to_base64()`、`key_to_hex()`、`key_from_hex()`、`key_is_zero()` 均为常量时间实现；`encoding.h` 给出 `WG_KEY_LEN_BASE64 = (((WG_KEY_LEN)+2)/3)*4+1`（即 45，含结尾 NUL）、`WG_KEY_LEN_HEX = WG_KEY_LEN*2+1`（即 65）。

这里有一个极易混淆的「同名不同义」必须点明：配置文件里的 `PrivateKey = <base64>` 走 `parse_key()` 直接解 base64，而命令行 `wg set wg0 private-key <文件路径>` 走 `parse_keyfile()` 从文件读 44 字符再解 base64（第 609–612 行）；`PresharedKey` 同理，配置里是内联 base64，命令行 `preshared-key` 是文件路径。`parse_keyfile()` 还允许文件尾部有空白字符（第 143–148 行逐字符检查是否 `char_is_space`），并把空文件（如 `/dev/null`）解释为「全零密钥」用于移除密钥（第 131–136 行）。同一语义两种写法，是阅读源码和配置时最容易踩的坑之一。

### 4. 关键流程与调用链

一次 `wg setconf wg0 file.conf` 的解析链路如下。先是 `config_read_init(ctx, append=false)`：`memset` 上下文，`calloc` 一个 device，因为不是追加模式，置 `WGDEVICE_REPLACE_PEERS | WGDEVICE_HAS_PRIVATE_KEY | WGDEVICE_HAS_FWMARK | WGDEVICE_HAS_LISTEN_PORT`，表示本次配置整体替换旧 peer 且四个设备字段即使缺省也要下发「清除」语义。随后调用方逐行读文件、每行调用 `config_read_line()`：它先用类似 `strchrnul` 的写法找 `#`（第 514 行 `strchr(input, COMMENT_CHAR)`，COMMENT_CHAR 定义为 `'#'`），把注释及其后内容截掉；再 `calloc` 一行缓冲区，把剩余字符中所有 `char_is_space` 为真者删除——注意这一步删除的不只是前后空格，而是行内所有空白（第 527–530 行）；若清洗后为空则跳过（空行与纯注释行合法）；否则调用 `process_line()`。

`process_line()` 先判段标题，再按当前段用 `key_match` 逐个尝试。设备段依次匹配 `ListenPort`、`FwMark`、`PrivateKey`；对等段依次匹配 `Endpoint`、`PublicKey`、`AllowedIPs`、`PersistentKeepalive`、`PresharedKey`；都不匹配则打印 `Line unrecognized: ...` 并返回 false。每个 `key_match` 命中后调用对应 `parse_*` 函数，任何解析失败都会让 `config_read_line()` 最终返回 false 并 `free_wgdevice`。所有行读完后 `config_read_finish()` 遍历每个 peer，凡未置 `WGPEER_HAS_PUBLIC_KEY` 者打印 `A peer is missing a public key` 并整体失败。整条链路的状态流转见图 04-04-01。

图中节点速览（便于在不渲染框内文字的预览器中阅读）：「原始配置行」经 `config_read_line` 截掉 `#` 注释，再「删除全部空白、空行则跳过」，进入 `process_line` 判断 `[Interface]/[Peer]` 段，再由 `key_match` 做大小写不敏感的前缀匹配，命中后调用 `parse_* 系列`解析字段并置标志位；全部读完后 `config_read_finish` 校验每个 peer 的公钥，任一环节失败都转到 `free_wgdevice` 整树回滚。

`config_read_cmd()` 是同一套 `parse_*` 函数的另一条入口：它不读文件，而是把 `wg set` 的 argv 按「listen-port/fwmark/private-key/peer/endpoint/allowed-ips/persistent-keepalive/preshared-key/remove」逐项解析，最终产出同样形状的 `wgdevice` 树。这意味着「配置文件写法」与「命令行写法」在字段语义上严格一致，差异只在键名连字符化（`ListenPort` → `listen-port`）与密钥的来源（内联 base64 vs 文件路径）。理解这一点，就能解释为什么 `wg syncconf` 与 `wg setconf` 能接受同一种文件格式、以及为什么 `wg showconf` 的输出可以直接回填为配置文件。

### 5. 配置/命令/代码实例

下面给出一个覆盖全部八键、包含行内注释与 IPv6 endpoint 的规范配置，用于说明解析规则的实际作用：

```ini
[Interface] # 接口段，可与 [PEER] 混用大小写
PrivateKey = yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=
ListenPort = 51820
FwMark = 0xca6c

[Peer]
PublicKey = xTIBA5rboUvnH4htodjb6e697QjLERt1NAB4mZqp8Dg=
PresharedKey = /UwcSPg38hW/D9Y3tcS1FOV0K1wuURMbS0sesJEP5ak=
AllowedIPs = 10.192.122.3/32, 10.192.124.1/24
AllowedIPs = +192.168.0.0/16
Endpoint = [2607:5300:60:6b0::c05f:543]:2468
PersistentKeepalive = 25
```

注意两处细节：一是 `[Interface] # 接口段...` 这类行内注释——`config_read_line()` 会先把 `#` 及之后全部截掉，留下 `[Interface]`，因此段标题仍然成立；二是第二条 `AllowedIPs = +192.168.0.0/16` 的加号，它会被 `parse_ip_prefix()` 识别，清除本 peer 的 `WGPEER_REPLACE_ALLOWEDIPS` 标志，从而把这条地址「增量追加」到前一条之后，而不是替换掉。把这段配置写入文件并应用：

```bash
wg setconf wg0 /etc/wireguard/wg0.conf
wg showconf wg0
```

`wg showconf` 是解析器输出树的逆向序列化，可用来核对解析结果（示例输出，具体格式需对照实际版本核验）：

```text
[Interface]
ListenPort = 51820
FwMark = 0xca6c
PrivateKey = yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=

[Peer]
PublicKey = xTIBA5rboUvnH4htodjb6e697QjLERt1NAB4mZqp8Dg=
PresharedKey = /UwcSPg38hW/D9Y3tcS1FOV0K1wuURMbS0sesJEP5ak=
AllowedIPs = 10.192.122.3/32, 10.192.124.1/24, 192.168.0.0/16
Endpoint = [2607:5300:60:6b0::c05f:543]:2468
PersistentKeepalive = 25
```

逐行判读如下。第一段 `[Interface]` 是 `showconf` 重新生成的段标题，与原始文件里的大小写写法无关，说明解析器只认 `strcasecmp` 结果、不保留原文。`ListenPort = 51820` 来自 `parse_port()`：它对字符串 "51820" 调用 `getaddrinfo`（`ai_socktype=SOCK_DGRAM`、`ai_protocol=IPPROTO_UDP`、`ai_flags=AI_PASSIVE`），取 `sin_port` 经 `ntohs` 得 51820，并置 `WGDEVICE_HAS_LISTEN_PORT`——所以端口其实支持服务名写法，并非只能填数字。`FwMark = 0xca6c` 来自 `parse_fwmark()`：因前缀 `0x` 按 16 进制 `strtoul` 得 0xca6c，置 `WGDEVICE_HAS_FWMARK`；若写 `off` 则得到 0 同样置位，表示关闭。`PrivateKey` 一行原样回显（在正常权限下 showconf 会显示私钥），它由 `parse_key()` 经 `key_from_base64()` 解出 32 字节，长度不符或尾字符不是 `=` 会直接报 `Key is not the correct length or format` 并清零缓冲区。转到 `[Peer]`：`PublicKey` 由 `wg pubkey` 从私钥派生，是 peer 唯一必填项，`config_read_finish()` 就靠它校验。`PresharedKey` 与 `PublicKey` 走同一个 `parse_key()`，只是置不同标志位。最关键的是 `AllowedIPs` 那行：原始文件写了两条，输出被合并成一条逗号列表，且 `+192.168.0.0/16` 的加号消失了——因为 `parse_ip_prefix()` 用掉加号后只留下标志语义，序列化时三条地址已平铺为同一链表；这也证明 `+` 是「增量」而非「字面前缀」。`Endpoint` 的 `[IPv6]:port` 写法来自 `parse_endpoint()` 的方括号分支：它要求匹配的 `]` 后紧跟冒号与端口，再用 `getaddrinfo` 解析成 sockaddr，域名形式还会触发重试。`PersistentKeepalive = 25` 由 `parse_persistent_keepalive()` 用 `strtoul` 得到 25 并置 `WGPEER_HAS_PERSISTENT_KEEPALIVE_INTERVAL`；写 `off` 则得 0 表示关闭。整段输出与输入的一一对应，正是「配置即解析结果」的最佳注脚。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是误判注释边界。`config_read_line()` 用 `strchr(input, COMMENT_CHAR)` 找第一个 `#`，注释可从行中任意位置开始；但 `wg-quick` 的 `parse_options()` 对 Pre/Post 钩子刻意保留原文（用 `unstripped_value`），所以「`#` 一定是注释」这条规则对钩子不成立——两套解析器在此分歧，跨工具复用配置时要格外小心。第二个陷阱是空白被全部删除：`config_read_line()` 删的是行内所有 `char_is_space`，不仅前后导。这意味着 `AllowedIPs = 10.0.0.1 / 32` 会被清洗成 `10.0.0.1/32` 而意外「合法」，与很多人以为的「空格导致错误」相反；但反过来，依赖空格分隔的钩子命令在交给 wg 解析时会被压掉，所幸这类键本就不属于 wg 原生配置。第三个陷阱是键名匹配的前缀特性：`get_value()` 只比较前 `keylen` 个字符且大小写不敏感，它并不校验键名边界，源码通过「先删空白、键后紧跟 `=`」的写法规避了大部分歧义，但自造类似 `ListenPortExtra = 1` 的键不会被当成 `ListenPort`——因为 `key_match("ListenPort=")` 要求等号紧跟，这一细节是安全的关键。

第四个陷阱是 CIDR 主机位。`parse_allowedips()` 在设置 cidr 后会调用 `validate_netmask()`，若网络前缀里主机位非零，只打印 `Warning: AllowedIP has nonzero host part` 而不拒绝——地址仍会被接受。把 `10.0.0.5/24` 当成「10.0.0.5 这个地址的 /24 网段」是常见误用，实际网段仍是 10.0.0.0/24，warning 是唯一提醒。缺省掩码规则也要记牢：IPv4 不带 `/` 时取 32，IPv6 取 128。第五个陷阱是 endpoint 解析的阻塞行为：`parse_endpoint()` 的 DNS 解析带重试，超时从 1 秒按 `×6/5` 递增、上限 20 秒，重试次数默认 15，可用环境变量 `WG_ENDPOINT_RESOLUTION_RETRIES` 调整（设为 `infinity` 表示无限）；写错域名或 DNS 不可用时，`wg setconf` 会「卡住」很久才报错，排障时应先确认解析。第六个陷阱是密钥编码的严格性：`key_from_base64()` 硬性要求 44 字符且倒数第二位为 `=`，`key_from_hex()` 要求 64 个十六进制字符，多一个换行或少一个填充符都失败——从网页复制密钥时带入不可见字符是高频故障。

最佳实践可归纳为四点：其一，配置写好后先用 `wg showconf` 往返一次，比对解析后的规范化输出，能立即暴露注释、空白、`+`/`-` 前缀造成的语义偏差；其二，私钥与预共享密钥用 `wg genkey`/`wg genpsk` 生成并妥善保管，内联写配置时确认无多余字符，命令行则用文件路径形式（走 `parse_keyfile()`，允许尾随空白）；其三，AllowedIPs 一律写规范网络地址并显式带掩码，不要依赖 `validate_netmask()` 的 warning 来纠正错误；其四，批量改动用 `wg syncconf` 而非 `wg setconf`，前者只读差异、不动未变化 peer，避免全量替换带来的会话抖动（语义见 04-02）。凡解析报错，先按 `Line unrecognized`、`Key is not the correct length or format`、`A peer is missing a public key` 这几条固定文本定位到对应函数，再回头核对原始行——错误消息本身就是最准确的导航。字段归属去 05-09，调用链机制去 06-14，模块职责去 07-13。

### 7. 小结与延伸阅读

本篇把 WireGuard 配置文件格式与 ini 解析规则还原为可核查的源码事实：格式基于 INI，只有 `[Interface]` 与 `[Peer]` 两段，允许多个 `[Peer]`、一个 `[Interface]`，`#` 起注释、行内空白被全删、键名大小写不敏感。解析由 `config_ctx` 状态机驱动，`config_read_line()` 清洗、`process_line()` 分派、`key_match` 匹配、`parse_*` 系列把字符串填入 uapi 结构并置 `WGDEVICE_*`/`WGPEER_*` 标志，`config_read_finish()` 强制每个 peer 有公钥，任何失败都 `free_wgdevice` 整树回滚。八个原生键的解析函数、取值规则与标志位已在第 2 节表格中列全；base64/hex 的严格长度、`+`/`-` 前缀的增量语义、endpoint 的重试退避、CIDR 主机位告警等易错点均已逐条标注。这套规则同时支撑 `setconf`、`addconf`、`syncconf` 与命令行 `set`，是全册配置语义的共同底座。

延伸阅读建议按三条线走：命令与参数层面，`wg` 命令全集见 04-01、`setconf/syncconf` 差异见 04-02、wg-quick 扩展键见 04-03；机制层面，netlink 配置通道见 06-14、AllowedIPs trie 的路由决策见 06-07；结构层面，uapi 配置结构与字段见 05-09，模块职责见 07-13。跨册随查按（字段见 05-09 ｜ 参数见 04-01 ｜ 原理见 06-14 ｜ 模块见 07-13）执行：结构体逐字段去 05、命令参数去 04 的对应篇、机制与调用链去 06、目录级模块能力去 07。凡本篇标注「需对照实际版本核验」的错误文本、默认值与重试参数，均以 `_wglinux_build/upstream_src/wireguard-tools/src/` 下 `config.c`、`config.h`、`ctype.h`、`encoding.c`、`encoding.h` 与 `man/wg.8` 为准，本套资料不编造未核验的路径与取值。
