## 02-01 源码获取、内核树目录结构与依赖矩阵

### 1. 背景与动机

要编译 WireGuard Linux，第一步不是敲下 make，而是先搞清楚「编译的对象究竟是什么、源码从哪里来、它需要哪些内核能力作为前提」。这三件事看似基础，却是后续所有构建、集成与排障工作的地基。很多人在这一步栽跟头，不是因为编译命令写错，而是因为拿错了源码、看错了目录、或者漏掉了某个在 Kconfig 里被 `select` 拉进来的底层库，结果要么编译直接失败，要么模块勉强编出来却在运行时出现难以解释的行为。本篇的任务就是把这三件事一次性讲清楚：源码获取的来源与版本基准、内核树中 WireGuard 相关目录的层级结构、以及由 Kconfig 条目决定的依赖矩阵。需要先把边界说明在前面——本篇只负责「源码与依赖的静态地图」，真正的编译命令、insmod 与 dkms 操作留给 02-03，用户态工具的具体编译留给 02-04，调试与自检构建留给 02-05；至于运行期会用到的各种命令参数与常量全集，属于 04 册的权威范围，本篇只给理解构建所必需的最小片段，细节交叉引用到 04。

为什么强调「源码获取」看似多余？因为 WireGuard Linux 并不是一个可以单独拉下来、独立 configure 再编译的普通软件包。它的内核驱动部分寄生在 Linux 内核树的 Kbuild 体系里，源码分散在 `drivers/net/wireguard/`、`lib/crypto/`、`include/uapi/linux/` 等多个目录，构建时必须借助内核顶层的 Makefile 与配置系统。这意味着你获取的「源码」实际上是一整棵内核源码树，而不是一个独立的 WireGuard 目录。本套资料的事实锚点是 `_wglinux_build/upstream_src/` 下的两份快照：`wireguard-linux-src/`（stable 分支内核驱动快照）与 `wireguard-tools/`（版本 1.0.20260223，2026-03 抓取）。下文出现的路径若无特别说明，均相对这两个根目录。把这两份快照当作唯一权威，是为了避免把某个发行版二次打过补丁的版本、或者某个旧版本博客文章里的路径，误当成上游当前的实现。

版本基准必须在这里说清，因为它贯穿全册。WireGuard Linux 至少牵涉三个彼此独立的版本号：内核驱动自身的版本，写在 `drivers/net/wireguard/version.h`，值为 `WIREGUARD_VERSION "1.0.0"`；用户态工具的版本，写在 `wireguard-tools/src/version.h`，默认值为 `WIREGUARD_TOOLS_VERSION "1.0.20260223"`，同时工具的 Makefile 会用 `git describe --dirty` 动态覆盖它；以及目标系统实际运行的内核版本，它决定了这份驱动快照能否直接套用。三者没有任何同步关系：驱动版本号从 1.0.0 发布以来几乎不变，工具版本号却随每次发布滚动，而内核版本由发行版或自行编译决定。把这三个号混为一谈，是在阅读上游邮件列表和构建日志时最常见的误读来源之一（版本基准的完整约定见 01-04）。

还有一个容易被忽略的版本特征值得在动机部分点明：本快照的 uapi 头 `include/uapi/linux/wireguard.h` 顶部写着「Do not edit directly, auto-generated from: Documentation/netlink/specs/wireguard.yaml」，说明当前上游已经把 netlink 定义纳入 YAML 规范统一管理，对应的内核 Makefile 里也因此出现了 `netlink.o generated/netlink.o` 这样的条目，而更早的实现常见的是 `sysfs.c` 加手写 netlink 代码。这是一个真实的代际差异：如果你手里有一份旧资料，按图索骥去找 `sysfs.c` 或手写的 `netlink.c`，在本快照里是找不到的。换句话说，「源码目录长什么样」本身就带有版本信息，获取源码时必须同时记录它对应的代际，这也是本篇把「获取」与「目录结构」放在一起讲的原因。

### 2. 核心概念

理解本篇需要先把四个概念拧清楚：两套源码树的分工、Kbuild 的两级 Makefile 挂载、Kconfig 中 `depends on` 与 `select` 的语义差别、以及「手写源文件」与「生成源文件」的区别。

两套源码树的分工是第一层。内核树 `wireguard-linux-src/` 提供数据面：所有加解密、握手、收发、路由逻辑都在内核态，以 `net_device` 的形态接入协议栈；用户态工具树 `wireguard-tools/` 提供控制面：`wg` 命令通过 netlink 把配置写进内核，配套有 `wg-quick` 脚本、bash 补全与 systemd 单元。两棵树独立获取、独立编译、独立版本化，构建时互不依赖——编译内核模块不需要先编译工具，编译工具也不需要内核源码（只需要内核导出的 uapi 头，而那份头通常已随系统安装）。这种解耦是 WireGuard 设计哲学的一部分：控制面可以随意替换成第三方实现，数据面保持极简稳定。

Kbuild 的两级挂载是第二层。内核里任何驱动的编译都由两级 Makefile 接力完成：上层 `drivers/net/Makefile` 用 `obj-$(CONFIG_WIREGUARD) += wireguard/` 决定「要不要进入这个子目录」，下层 `drivers/net/wireguard/Makefile` 用 `wireguard-y` 列出源文件、用 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 把目标文件聚合成模块。注意这里的 `$(CONFIG_WIREGUARD)` 是一个由配置系统替换的变量：当配置为 `=m` 时它展开为 `m`，`obj-m` 触发可加载模块 `wireguard.ko` 的构建；当配置为 `=y` 时它展开为 `y`，`obj-y` 把代码直接编进内核镜像；当为 `=n` 时两处都不生效，目录被整体跳过。理解这个替换机制，就能明白为什么「打开一个 Kconfig 开关」会同时改变上下两级 Makefile 的行为。

`depends on` 与 `select` 的语义差别是第三层，也是依赖矩阵的核心。`depends on NET && INET` 表示本选项只有在 `NET` 与 `INET` 都已经启用时才可见、可选——这是「前置条件」，不满足时选项根本不会出现在配置菜单里，更无法打开。而 `select CRYPTO_LIB_CURVE25519` 等语句表示「一旦打开本选项，就自动把这些底层库也打开」，这是「反向拉取」，目的是保证用户不需要手动去理解和勾选一堆密码学依赖。前者是约束，后者是便利；前者不打开就无从谈起，后者不手动管也会被自动满足。混淆这两者，是阅读 Kconfig 时最典型的错误。

「手写源文件」与「生成源文件」的区别是第四层。在本快照的 `drivers/net/wireguard/Makefile` 里，`wireguard-y` 大部分条目是 `.c` 文件编译而来的 `.o`，对应仓库里真实存在的源文件；但 `generated/netlink.o` 不同，它的输入来自 netlink YAML 规范经工具生成的代码，在源码快照里往往并不落地为静态文件（本快照的 `generated/` 目录就是空的甚至不存在，构建时由 Kbuild 现场生成）。这意味着你在源码树里「看不到」某个 .o 对应的 .c，并不等于构建会失败——它是被生成出来的。这一点对建立正确的源码地图至关重要，后面第 3、6 节还会回到它。

最后用一个概念表把上述术语收拢，便于对照后文。

| 概念 | 含义 | 在本主题中的落点 |
|---|---|---|
| 内核树快照 | 含驱动与加密原语的整棵内核源码 | `wireguard-linux-src/` |
| 工具树快照 | 用户态控制面源码 | `wireguard-tools/` |
| 三态选项 | 可设为 Y / M / N 的配置项 | `config WIREGUARD` |
| depends on | 前置条件，不满足则选项不可见 | `NET && INET` |
| select | 打开本项时自动拉起依赖 | `CRYPTO_LIB_*` 等 |
| 生成源文件 | 由规范经工具生成的 .o | `generated/netlink.o` |

### 3. 关键数据结构与源码位置

作为构建册的静态地图，本节只点名目录与关键文件、给出真实路径，不展开任何结构体的逐字段定义（字段统一见 05 册，例如设备结构见 05-02、对等体结构见 05-03），也不深入运行机制（原理见 06-01）。把源码位置按「树—目录—文件」三级铺开，能得到一张清晰的地图。

第一级是内核树根。`wireguard-linux-src/` 下与本篇直接相关的有三个位置：`drivers/net/wireguard/` 是驱动主体目录，几乎所有内核态源文件都在这里；`lib/crypto/` 存放被 select 拉进来的加密原语实现，包括 ChaCha20-Poly1305、Curve25519、Blake2s 等；`include/uapi/linux/wireguard.h` 是用户态与内核态共享的 ABI 头，定义族名、版本、命令与属性枚举。此外 `Documentation/netlink/specs/wireguard.yaml` 被 uapi 头注释明确引用，是生成 netlink 代码的规范源，但在本快照中未随驱动一并落地，引用时需标注「需对照实际版本核验」。

第二级是驱动目录内部。`drivers/net/wireguard/Makefile` 是本篇与下一篇的主角，它决定了源文件如何聚合成模块；`version.h` 只有一行，定义驱动版本字符串。源文件按职责分布：`main.c` 是模块入口与 netdev 注册，`device.c` 管设备生命周期，`peer.c` 管对等体，`allowedips.c` 实现路由 trie，`noise.c` 与 `messages.h` 负责握手与消息布局，`send.c` / `receive.c` 负责收发，`socket.c` 管 UDP socket 与 endpoint，`timers.c` 管定时器，`ratelimiter.c` 与 `cookie.c` 负责限速与 DoS 防护，`queueing.h` 是队列相关的头文件。这些名字都能在 Makefile 的 `wireguard-y` 列表里一一对应（逐模块职责见 07 册，例如入口见 07-01、收发见 07-07、07-08）。

这里必须诚实指出一个快照特征：Makefile 里还列了 `peerlookup.o` 与 `netlink.o generated/netlink.o`，但本地 `drivers/net/wireguard/` 目录里并没有 `peerlookup.c`、`netlink.c`，也没有 `generated/` 子目录，`selftest/` 子目录则是空的。这说明本快照是一份经过挑选的源码切片，而非完整内核树。撰写与核验时，凡涉及这些「Makefile 引用但本地未落地」的文件，都要写清楚「本快照未包含，需对照完整内核源码树核验」，绝不能假装在目录里看到了它。这种诚实标注本身就是技术写作的一部分。

第三级是用户态工具树。`wireguard-tools/src/` 下与构建相关的是 `Makefile`（注意它在 `src/` 子目录，仓库根目录并没有 Makefile，任务描述里的「tools/Makefile 若存在」应以实际路径为准）、`wg.c`（命令入口）、`config.c`（配置解析）、`encoding.c`（密钥编解码）、`curve25519.c` 与两个 `curve25519-*.h`（密钥运算后端）、`ipc.c` 与 `ipc-linux.h` 等一族 IPC 抽象、`netlink.h`、`version.h`，以及 `wg-quick/`、`completion/`、`systemd/`、`man/`、`uapi/` 等子目录。仓库根还有 `COPYING`、`README.md` 与 `contrib/`。工具树的编译与内核模块完全分离，其 Makefile 会探测 `pkg-config`、bash 与 systemd 的安装位置来决定是否附带 wg-quick、bash 补全与 systemd 单元（这部分的完整构建流程见 02-04，模块职责见 07-13）。

下表把本篇反复引用、且确实存在于快照中的源码位置收拢成速查表。

### 4. 关键流程与调用链

从「拿到源码」到「产出模块」，存在一条可以逐段拆解的链路。第一段是源码获取：分别取得内核树快照与工具树快照，并记录各自的代际与版本。第二段是配置挂载：内核顶层的 `drivers/net/Kconfig` 提供 `config WIREGUARD` 与 `config WIREGUARD_DEBUG` 两个条目，用户通过 `make menuconfig` 一类界面把前者设为 M 或 Y。第三段是目录进入：`drivers/net/Makefile` 中的 `obj-$(CONFIG_WIREGUARD) += wireguard/` 在配置为 M 或 Y 时把构建流程引入驱动子目录。第四段是目标聚合：`drivers/net/wireguard/Makefile` 把 `wireguard-y` 列出的全部目标文件聚合为单一的 `wireguard.o`，再由 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 决定产出 `wireguard.ko`（=m）还是链入内核镜像（=y）。第五段是依赖解析：`select` 拉起的 `CRYPTO_LIB_*` 从 `lib/crypto/` 提供实现，`generated/netlink.o` 由 YAML 规范经工具现场生成。这条链路把本篇的三个主题——获取、目录、依赖——串成了一条时间线。

需要把「配置链路」与「数据链路」区分开，避免把本篇和 06 册混为一谈。本篇关心的是构建期的静态链路：Kconfig 符号如何展开成 Makefile 变量、目录如何被递归进入、目标文件如何聚合。而 `wg_mod_init` 里的 `wg_allowedips_slab_init`、`wg_noise_init`、`wg_peer_init`、`wg_device_init`、`wg_genetlink_init` 这条初始化链，以及运行期 `ndo_start_xmit` 到 `send.c`、UDP socket 到 `receive.c` 的数据链，属于启动与包处理流水线（原理见 06-01）。它们在源码里同样真实存在，但不是本篇要把读者带进去的地方；本篇只在「哪些源文件会被编进模块」这个层面提到它们的文件名。

### 5. 配置/命令/代码实例

本篇的实例不是去编译，而是用几条只读命令把「源码地图」与「依赖声明」实际取出来看。所有命令都在快照根目录下执行，且都只读、不修改任何文件。

```bash
# 1. 查看驱动目录里真实落地的文件
ls drivers/net/wireguard/

# 2. 取出 Kconfig 中 WireGuard 的依赖声明
grep -n -A 12 '^config WIREGUARD$' drivers/net/Kconfig

# 3. 确认上层 Makefile 如何进入子目录
grep -n 'WIREGUARD' drivers/net/Makefile

# 4. 确认两份快照各自的版本字符串
cat drivers/net/wireguard/version.h
cat ../../wireguard-tools/src/version.h
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
Makefile  allowedips.c  allowedips.h  cookie.c  cookie.h  device.c
main.c  messages.h  noise.c  noise.h  peer.c  queueing.h  ratelimiter.c
ratelimiter.h  receive.c  selftest  send.c  socket.c  timers.c  version.h

74:config WIREGUARD
75:	tristate "WireGuard secure network tunnel"
76:	depends on NET && INET
77:	select NET_UDP_TUNNEL
78:	select DST_CACHE
79:	select CRYPTO_LIB_CURVE25519
80:	select CRYPTO_LIB_CHACHA20POLY1305
81:	select CRYPTO_LIB_UTILS

13:obj-$(CONFIG_WIREGUARD) += wireguard/

#define WIREGUARD_VERSION "1.0.0"
#define WIREGUARD_TOOLS_VERSION "1.0.20260223"
```

逐行判读如下。第一段 `ls` 输出列出了目录里真实存在的文件，重点不在逐个文件，而在「缺了什么」：列表里没有 `peerlookup.c`、没有 `netlink.c`、没有 `sysfs.c`，也没有 `generated/` 子目录，`selftest` 是空的，这正印证了第 3 节所说的「快照是切片」——这些名字会出现在 Makefile 里，但本地没有对应源文件，核验时必须去完整内核树找。第二段是 `grep` 带出的 Kconfig 原文：第 74 行 `config WIREGUARD` 定义符号；第 75 行 `tristate` 表明它可取 Y/M/N 三态，引号内是配置菜单显示给用户的描述串；第 76 行 `depends on NET && INET` 是前置条件，要求通用网络与 IPv4 协议栈都已启用，否则该选项不可见；第 77 至 81 行是五条 `select`，分别把 UDP 隧道框架、目的地址缓存、Curve25519、ChaCha20-Poly1305 与密码学工具函数库拉进来，这正是依赖矩阵的源码依据。第三段第 13 行 `obj-$(CONFIG_WIREGUARD) += wireguard/` 说明上层 Makefile 用条件变量控制是否递归进入子目录，注意它用的是追加符号 `+=`，表示在 `drivers/net/` 已有的目标列表基础上增加一项。第四段两行 `version.h` 的内容给出两个独立版本号：驱动侧 `WIREGUARD_VERSION` 是 `1.0.0`，工具侧 `WIREGUARD_TOOLS_VERSION` 是 `1.0.20260223`，二者没有任何同步关系，也不等于目标系统的内核版本；这个差异是排障时判断「你用的是哪一代代码」的第一手证据。把这份输出与第 3 节的地图对照读，就能从「纸面结构」走到「眼见为实」。

需要补充第二个只读片段，把 uapi 头的生成属性也纳入视野。

```text
/* Do not edit directly, auto-generated from: */
/*	Documentation/netlink/specs/wireguard.yaml */
/* YNL-GEN uapi header */
/* To regenerate run: tools/net/ynl/ynl-regen.sh */
```

这几行注释直接来自 `include/uapi/linux/wireguard.h` 的开头，它说明两件事：其一，这份头不是手写的，而是由 `wireguard.yaml` 经 YNL 工具生成的，因此「改头文件」不是正确的扩展方式，正确做法是改规范再重新生成；其二，重新生成的入口脚本是 `tools/net/ynl/ynl-regen.sh`，属于内核树工具目录，本快照未包含。把这条信息与 Makefile 里的 `generated/netlink.o` 连起来看，就能理解为什么本代实现会同时出现「生成的 uapi 头」与「生成的 netlink 目标文件」，它们是同一套 YAML 规范驱动下的两个产物。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是混淆三个版本号。驱动的 `1.0.0`、工具的 `1.0.20260223` 与目标内核版本各自独立，讨论兼容性时必须说明指的是哪一个（版本约定见 01-04）。第二个陷阱是把这份驱动快照当成可以独立编译的软件包。它没有自己的顶层 configure，必须放进内核树的 Kbuild 体系，借 `drivers/net/Kconfig` 与 `drivers/net/Makefile` 才能被编译；直接对驱动目录跑 make 不会得到可用的内核模块。

第三个陷阱是照抄旧资料的目录清单。旧实现常见的 `sysfs.c`、手写 `netlink.c` 在本快照里都不存在，取而代之的是 `netlink.o generated/netlink.o` 的生成式代码；看到差异先怀疑版本代际，而不是怀疑自己拿错了分支。第四个陷阱是把用户态工具的 Makefile 与内核 Makefile 混为一谈。工具构建入口在 `wireguard-tools/src/Makefile`，用的是 `pkg-config`、`PREFIX`、`BINDIR` 这类变量；内核构建用的是 Kbuild 的 `obj-y`/`obj-m`、`ccflags-y` 与 `wireguard-y`，两者语法体系完全不同（工具构建流程见 02-04，内核构建配置见 02-02）。

第五个陷阱最隐蔽：看到 Makefile 列了 `peerlookup.o`、`netlink.o` 却在目录里找不到对应 `.c`，就断定源码不完整或构建必然失败。实际情况是快照经过挑选，加上部分目标由生成流程提供，本地缺失并不等于完整内核树里也缺失。正确做法是明确标注「本快照未包含，需对照完整内核源码树核验」，而不是给出武断结论。第六个陷阱是忽略依赖矩阵的业务含义：`select CRYPTO_LIB_CURVE25519` 与 `CRYPTO_LIB_CHACHA20POLY1305` 不是可有可无的装饰，它们分别对应密钥交换与对称加密所需的原语，缺了会导致链接失败；`NET_UDP_TUNNEL` 与 `DST_CACHE` 则关系到 UDP 承载与目的缓存路径（这些库的函数级原理见 06-03、06-12，本篇只需知道它们被依赖）。

最佳实践可以归纳成四步。第一步，获取源码时同时记录内核树快照的代际与工具树的版本字符串，必要时把 `git describe` 的结果一并留存，让后续任何一次构建都能回溯到确切的代码状态。第二步，在动编译命令之前，先用本篇第 5 节的只读命令把 Kconfig 依赖、Makefile 挂载点与版本号实际取出来核对一遍，确认「看到的」与「以为的」一致。第三步，把依赖矩阵当作编译前的检查清单：确认 `NET`、`INET` 已启用，确认五个 `select` 目标在当前内核配置下可满足，尤其是加密库在裁剪型内核里可能被裁剪掉（具体编译步骤见 02-03）。第四步，凡遇到快照缺失或生成代码相关的问题，先标注「需对照实际版本核验」，再去完整源码树或目标系统求证，不凭记忆下结论。这四步的共同精神是：把构建当成一条可观测的链路，而不是一串不可解释的咒语。

### 7. 小结与延伸阅读

本篇把 WireGuard Linux 的构建前置知识整理成一张静态地图：源码来自内核树快照 `wireguard-linux-src/` 与工具树快照 `wireguard-tools/` 两份，前者提供数据面并寄生在 Kbuild 体系中，后者提供独立的控制面；内核树里与构建直接相关的位置是 `drivers/net/wireguard/`（驱动主体与 Makefile、version.h）、`lib/crypto/`（被 select 拉起的加密原语）与 `include/uapi/linux/wireguard.h`（由 YAML 规范生成的 ABI 头）；依赖矩阵由 `config WIREGUARD` 的 `depends on NET && INET` 与五条 `select` 语句共同定义，分别约束可见性并自动拉取底层库。源码到模块的链路是「获取快照 → Kconfig 配置 → 上层 Makefile 进入目录 → 下层 Makefile 聚合目标 → 产出模块或内建镜像」，其中 `generated/netlink.o` 体现的是当前代际的生成式代码特征。三个独立版本号与「快照是切片、部分文件未落地」这两点，是阅读时最需要保持警觉的地方。

延伸阅读建议按三条线走：想要把目录里的每个文件对号入座，读 07 册各模块篇，入口见 07-01、收发见 07-07、07-08、工具见 07-13；想要理解被依赖的原语与握手机制，读 06 册，启动流水线见 06-01、密钥派生见 06-03、UDP 封装见 06-12；想要拿到命令、常量与 uapi 定义的全集，读 04 册，uapi 常量见 04-06。跨册随查按（字段见 05-01 ｜ 参数见 04-06 ｜ 原理见 06-01 ｜ 模块见 07-01）执行：结构体逐字段去 05、命令与常量全集去 04、机制与调用链去 06、目录级模块能力去 07、运维与基准去 08。本篇所有标注「需对照实际版本核验」的路径与取值，均以 `_wglinux_build/upstream_src/` 下对应文件为准；编译参数与具体操作细节是 04 册与 02-03 的范围，这里不做展开。下一篇将把目光从静态地图转向动态配置，逐行拆解 Kconfig 与 Makefile 的每一条语句。

## 02-02 内核 Kconfig / Makefile 与 CONFIG_WIREGUARD 构建配置

### 1. 背景与动机

上一篇给出了源码与依赖的静态地图，本篇要把地图上的两条关键配置线路逐行拆开：一条是 Kconfig，它决定「这个选项是否存在、可取哪些值、依赖谁、又拉起谁」；另一条是 Makefile，它决定「配置值如何变成编译动作、哪些源文件被聚合、最终产出什么」。这两条线在内核里并不是各说各话，而是通过同一个符号 `CONFIG_WIREGUARD` 咬合在一起——Kconfig 定义符号并让用户给它赋值，Makefile 读取这个符号并据此改变行为。理解这种「定义—消费」的对应关系，是读懂任何内核驱动构建配置的关键，也是本篇的中心任务。

先明确边界，避免与相邻篇章重叠。本篇只讲「构建配置」本身：Kconfig 条目怎么读、`obj-y`/`obj-m` 与 `wireguard-y` 怎么展开、调试开关如何影响编译参数。从零开始的实际编译、insmod 加载、dkms 兼容路径属于 02-03；用户态工具 wg 与 wg-quick 的构建属于 02-04；调试构建的更深用法、动态调试与静态检查属于 02-05。至于运行期命令的参数全集、netlink 属性常量全集、模块参数与 sysfs 接口全集，分别是 04-01、04-05、04-06、04-07 的权威范围，本篇只在需要说明配置语义时给出最小片段，细节一律交叉引用到 04。换句话说，本篇回答「为什么这样配置会产生这样的构建结果」，而不回答「某条命令有哪些参数」。

为什么值得花一整篇讲几条看似简单的语句？因为 Kconfig 与 Makefile 是内核构建系统的通用语言，WireGuard 只是这套语言的一个具体用例。同一套 `config`/`tristate`/`depends on`/`select` 语法支配着内核里几千个选项，同一套 `obj-y`/`obj-m`/`*-y` 约定支配着所有驱动的编译。把 WireGuard 的这几条语句吃透，等于掌握了一把能打开任意内核驱动构建配置的钥匙。而且这几条语句里藏着不少容易误读的细节：比如 `:=` 与 `+=` 的差别、`ccflags-y` 里 `pr_fmt` 的引号形式、`tristate` 与 `bool` 的取值集合、`select` 与 `depends on` 的方向性。这些细节平时不起眼，一旦理解偏差，就会在编译失败或行为异常时把排查引向错误方向。

本快照里与本篇直接相关的源码只有四处，但每一处都信息密集：`drivers/net/Kconfig` 第 74 至 101 行给出 `config WIREGUARD` 与 `config WIREGUARD_DEBUG` 两个条目；`drivers/net/Makefile` 第 13 行给出进入子目录的条件；`drivers/net/wireguard/Makefile` 全文十七行给出编译参数的设置与目标聚合；`drivers/net/wireguard/version.h` 给出驱动版本字符串。下面各节会反复回到这四处，做到「每一条结论都能指回具体行号」。凡本快照未落地的文件（如 `generated/netlink.c`、selftest 实现），一律标注「需对照实际版本核验」，不凭空补全。

### 2. 核心概念

本篇的核心概念可以压缩为五句话：三态取值、两级消费、两个开关方向、两类目标变量、一条调试链。

三态取值，指 `config WIREGUARD` 的 `tristate` 类型决定它可取 Y、M、N 三个值。Y 表示把代码直接编进内核镜像，随内核启动即生效，但无法在运行期单独卸载；M 表示编译成可加载模块 `wireguard.ko`，需要时再载入、不用时可卸载；N 表示不编译，相关代码完全不进入构建。与之相对，`config WIREGUARD_DEBUG` 的 `bool` 类型只能取 Y 或 N——它只是一个编译期开关，没有「编成模块」的中间态。把 `tristate` 与 `bool` 的取值集合搞混，是阅读 Kconfig 时的第一处常见失误。

两级消费，指 `CONFIG_WIREGUARD` 的值被上下两级 Makefile 分别消费。上层 `drivers/net/Makefile` 用 `obj-$(CONFIG_WIREGUARD) += wireguard/` 判断是否递归进入子目录；下层 `drivers/net/wireguard/Makefile` 用 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 判断产出模块还是内建目标。当符号为 M 时，两处的 `$(CONFIG_WIREGUARD)` 都展开为 `m`，于是上层执行 `obj-m += wireguard/`、下层执行 `obj-m := wireguard.o`，最终链接出 `wireguard.ko`；当符号为 Y 时，两处都展开为 `y`，代码链入 `vmlinux`；为 N 时两处分别是 `obj-n`，不产生任何目标。一个符号、两级展开、三种结果，这就是 Kbuild 的精妙之处。

两个开关方向，指 `depends on` 与 `select` 的方向性差别（上一篇已建立基本认识，这里从配置角度再强调）。`depends on NET && INET` 是「向上约束」：本选项依赖更基础的网络与 IPv4 支持，后者不满足时本选项不可选。五条 `select` 是「向下拉取」：一旦本选项打开，就自动把 `NET_UDP_TUNNEL`、`DST_CACHE`、`CRYPTO_LIB_CURVE25519`、`CRYPTO_LIB_CHACHA20POLY1305`、`CRYPTO_LIB_UTILS` 置为选中。对构建而言，前者意味着「不满足就无法构建 WireGuard」，后者意味着「构建 WireGuard 时这些依赖会自动满足，无需手动逐项勾选」。

两类目标变量，指 `obj-*` 与 `*-y` 的分工。`obj-y`/`obj-m`/`obj-n` 是 Kbuild 约定的「输出目标列表」，告诉构建系统本目录要产出什么；`wireguard-y` 是本驱动自定义的「输入源文件列表」，列出要聚合到 `wireguard.o` 里的所有目标文件。两者通过 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 关联：输入列表里的 `.o` 被链接成一个 `wireguard.o`，而这个 `wireguard.o` 又被放进输出列表。记住「`*-y` 是输入、`obj-*` 是输出」，就不难理解为什么 Makefile 里既有 `wireguard-y` 又有 `obj-...`。

一条调试链，指 `WIREGUARD_DEBUG` 从配置到编译参数再到运行行为的贯通。Kconfig 里 `config WIREGUARD_DEBUG` 是 `bool`，依赖 `WIREGUARD`；Makefile 里 `ccflags-$(CONFIG_WIREGUARD_DEBUG) += -DDEBUG` 在该开关为 Y 时向编译命令追加宏 `DEBUG`；源码 `main.c` 里 `#ifdef DEBUG` 包裹着三项自检 `wg_allowedips_selftest()`、`wg_packet_counter_selftest()`、`wg_ratelimiter_selftest()`，任一失败即返回 `-ENOTRECOVERABLE`。这形成「勾选项 → 编译宏 → 条件代码 → 启动期自检」的完整链条，是理解调试开关如何真正生效的范本（自检内容的机制细节见 02-05）。

最后一个容易被忽略的概念是 `ccflags-y` 里的 `pr_fmt`。Makefile 第一行 `ccflags-y := -D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'` 用带引号的宏定义，为驱动所有打印加上模块名前缀；第二行才是在调试开关下追加 `-DDEBUG`。`pr_fmt` 不依赖任何配置，属于「无条件编译参数」，而 `-DDEBUG` 属于「条件编译参数」，二者在 Makefile 里的写法差异（`:=` 与 `+=`）正好体现了「一次性赋值」与「条件追加」的区别。编译参数的完整讨论属于 04 册，这里只点明它们如何随配置变化。

### 3. 关键数据结构与源码位置

本节把四处源码逐行摊开，作为后续流程分析的事实底稿。由于构建册不展开任何运行时结构体（字段见 05-01），这里的「结构」指的是配置文件与 Makefile 的组织结构。

第一处，`drivers/net/Kconfig` 的 `config WIREGUARD` 段。类型为 `tristate`，菜单描述为 `WireGuard secure network tunnel`；`depends on NET && INET` 给出前置条件；五条 `select` 依次是 `NET_UDP_TUNNEL`、`DST_CACHE`、`CRYPTO_LIB_CURVE25519`、`CRYPTO_LIB_CHACHA20POLY1305`、`CRYPTO_LIB_UTILS`；`help` 文本把它描述为 IPsec 的轻量替代，并特别说明「safe to say Y or M here」，因为驱动很轻量、只在管理员添加接口时才被使用。紧随其后的 `config WIREGUARD_DEBUG` 类型为 `bool`，描述为 `Debugging checks and verbose messages`，`depends on WIREGUARD`，`help` 说明它会打印握手等事件的日志并做额外校验与单元测试，最后一句是「Say N here unless you know what you're doing」。这两段是本篇全部配置语义的源头。

第二处，`drivers/net/Makefile` 第 13 行 `obj-$(CONFIG_WIREGUARD) += wireguard/`。这一行夹在 `obj-$(CONFIG_IPVTAP) += ipvlan/`、`obj-$(CONFIG_DUMMY) += dummy.o` 与 `obj-$(CONFIG_OVPN) += ovpn/` 之间，说明 WireGuard 与其他虚拟网络设备并列注册在 `drivers/net/` 这一层。末尾的斜杠 `wireguard/` 表示这是一个子目录目标，Kbuild 会递归进入该目录继续处理它的 Makefile。

第三处，`drivers/net/wireguard/Makefile` 全文。第 1 行 `ccflags-y := -D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'` 设置无条件编译参数；第 2 行 `ccflags-$(CONFIG_WIREGUARD_DEBUG) += -DDEBUG` 在调试开关下追加宏；第 3 至 16 行用 `wireguard-y += ...` 逐项列出输入目标，顺序为 `main.o`、`noise.o`、`device.o`、`peer.o`、`timers.o`、`queueing.o`、`send.o`、`receive.o`、`socket.o`、`peerlookup.o`、`allowedips.o`、`ratelimiter.o`、`cookie.o`、`netlink.o generated/netlink.o`；第 17 行 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 完成聚合。注意第 17 行用的是 `:=`，与上一节 `obj-$(CONFIG_WIREGUARD) += wireguard/` 的 `+=` 并不相同，这个差别在第 6 节专门讨论。

第四处，`drivers/net/wireguard/version.h` 只有一行 `#define WIREGUARD_VERSION "1.0.0"`。它通过 `main.c` 的 `#include "version.h"` 进入 `MODULE_VERSION(WIREGUARD_VERSION)`，决定了 `modinfo wireguard` 看到的版本字符串。它不参与任何条件编译，是纯常量定义。

下面这张表把本篇涉及的符号与配置要素按「来源—类型—作用」收拢。

### 4. 关键流程与调用链

配置符号从「用户在菜单上按一下」到「编译出 .ko」，中间经过一条清晰的链路。第一段，用户通过 `make menuconfig` 一类界面把 `CONFIG_WIREGUARD` 设为 `m`；配置系统把这个选择写入内核根目录的 `.config` 文件，同时生成供 Makefile 读取的自动配置头与变量文件。第二段，顶层 Makefile 在递归遍历 `drivers/net/` 时读到 `obj-$(CONFIG_WIREGUARD) += wireguard/`，此时 `CONFIG_WIREGUARD` 的值已被替换为 `m`，于是该行等价于 `obj-m += wireguard/`，Kbuild 决定进入子目录并准备构建一个模块。第三段，进入 `drivers/net/wireguard/` 后，`wireguard-y` 列表里的每个 `.o` 由对应的 `.c` 编译产生；`ccflags-y` 定义的 `pr_fmt` 宏随每次编译注入。第四段，第 17 行把全部输入目标聚合为单一的 `wireguard.o`，并按 `obj-m` 的要求链接成 `wireguard.ko`。第五段，若同时把 `CONFIG_WIREGUARD_DEBUG` 设为 `y`，第 2 行的条件表达式成立，`-DDEBUG` 被追加进编译参数，`main.c` 的 `#ifdef DEBUG` 块生效，模块加载时会先跑三项自检。这条链把 Kconfig、Makefile、源码条件编译三者串成一条因果链。

调试链值得单独再走一遍，因为它是「配置如何改变运行行为」的最佳示例。`config WIREGUARD_DEBUG` 是 `bool` 且 `depends on WIREGUARD`，所以只有先打开 `WIREGUARD` 才能看到它；设为 Y 后，`ccflags-$(CONFIG_WIREGUARD_DEBUG)` 展开为 `ccflags-y`，`+= -DDEBUG` 把宏加进编译命令；`main.c` 里 `#ifdef DEBUG` 包裹的代码把 `ret` 预设为 `-ENOTRECOVERABLE`，依次调用 `wg_allowedips_selftest()`、`wg_packet_counter_selftest()`、`wg_ratelimiter_selftest()`，任一返回假就 `goto err_peer` 回滚；三项都通过才继续正常的 `wg_noise_init()` 等初始化。这意味着「打开调试开关」不只是多打几行日志，而是在启动路径上插入了一道硬性自检关卡——这正是 Kconfig 的 help 文本提醒「Say N unless you know what you're doing」的原因。本快照的 `selftest/` 目录为空，相关自检函数的实现未落地，具体仓库位置需对照实际版本核验，但调用关系在 `main.c` 里清晰可见。

需要再次划清边界：上面这条是「构建期配置链」，与 06 册讲的「运行期初始化链/数据链」不是一回事。后者从 `module_init(wg_mod_init)` 开始，经过 slab 缓存初始化、noise/peer/device/netlink 各层注册，最后打印加载信息；前者在编译阶段就已经决定「这些代码会被编进去、以什么形式存在」。本篇只在说明 `wireguard-y` 列表里有哪些源文件、以及 `DEBUG` 宏会激活哪些条件代码时触及运行期函数名，不深入它们的实现（机制见 06-01，模块职责见 07 册）。

### 5. 配置/命令/代码实例

本节把前文反复引用的 Kconfig 原文作为代码实例，再用只读命令观察配置值如何落到 `.config`，最后给出一段编译日志作为逐行判读的素材。

先看配置源码，这段直接来自 `drivers/net/Kconfig` 第 74 至 101 行。

```text
config WIREGUARD
	tristate "WireGuard secure network tunnel"
	depends on NET && INET
	select NET_UDP_TUNNEL
	select DST_CACHE
	select CRYPTO_LIB_CURVE25519
	select CRYPTO_LIB_CHACHA20POLY1305
	select CRYPTO_LIB_UTILS
	help
	  WireGuard is a secure, fast, and easy to use replacement for IPSec ...

config WIREGUARD_DEBUG
	bool "Debugging checks and verbose messages"
	depends on WIREGUARD
	help
	  This will write log messages for handshake and other events ...
	  Say N here unless you know what you're doing.
```

再看驱动 Makefile 的聚合部分，这段来自 `drivers/net/wireguard/Makefile` 第 1、2、17 行。

```makefile
ccflags-y := -D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'
ccflags-$(CONFIG_WIREGUARD_DEBUG) += -DDEBUG
obj-$(CONFIG_WIREGUARD) := wireguard.o
```

观察配置落地的只读命令如下，均在内核树根目录执行。

```bash
# 查看当前配置中 WireGuard 相关符号的取值
grep '^CONFIG_WIREGUARD' .config

# 编译 WireGuard 模块（目录由 02-03 详述，这里只看输出形态）
make M=drivers/net/wireguard
```

对应输出（示例输出，具体格式需对照实际版本核验）：

```text
CONFIG_WIREGUARD=m
# CONFIG_WIREGUARD_DEBUG is not set
  CC [M]  drivers/net/wireguard/main.o
  CC [M]  drivers/net/wireguard/noise.o
  CC [M]  drivers/net/wireguard/device.o
  [中间编译行省略]
  LD [M]  drivers/net/wireguard/wireguard.o
  MODPOST 1 modules
  LD [M]  drivers/net/wireguard/wireguard.ko
```

逐行判读如下。第一行 `CONFIG_WIREGUARD=m` 确认符号取值为 m，对应 `tristate` 三态中的模块态，意味着顶层与下层 Makefile 的 `$(CONFIG_WIREGUARD)` 都展开为 `m`，最终走 `obj-m` 路径；若这里是 `=y`，产物就会是内建驱动而非 `.ko`，若整行不存在则为 `=n`、不参与构建。第二行 `# CONFIG_WIREGUARD_DEBUG is not set` 是内核配置系统表示「布尔项未选中」的标准写法，说明调试链没有激活，Makefile 第 2 行的 `ccflags-$(CONFIG_WIREGUARD_DEBUG)` 为空，`-DDEBUG` 不会进入编译参数，`main.c` 的 `#ifdef DEBUG` 自检块被跳过；反过来若设为 `=y`，这行就会变成 `CONFIG_WIREGUARD_DEBUG=y` 并在加载时触发三项自检。第三至第五行 `CC [M] ...main.o`、`noise.o`、`device.o` 是编译命令回显，方括号里的 `M` 标记这是模块构建目标，文件名与 `wireguard-y` 列表开头的三项一一对应，`[M]` 标签正来自 `obj-m` 的输出分类。省略号处对应列表中其余的 `peer.o`、`timers.o`、`send.o` 等，它们同样由 `CC [M]` 逐项编译。第六行 `LD [M] ...wireguard.o` 是聚合步骤，对应 Makefile 第 17 行 `obj-$(CONFIG_WIREGUARD) := wireguard.o`——所有输入目标被链接成单一的 `wireguard.o`，这一步正是 `wireguard-y` 列表与 `obj-*` 输出变量的接合点。第七行 `MODPOST 1 modules` 是内核模块后处理阶段，它生成模块元数据与符号版本信息，`1 modules` 表明本次只产出一个模块，与 WireGuard 只聚合为单一 `wireguard.ko` 的事实吻合。第八行 `LD [M] ...wireguard.ko` 是最终链接产物，即可加载模块文件，它对应 `make M` 在模块态下的终点；到这里，`CONFIG_WIREGUARD=m` 这个一开始的菜单选择，就完整走完了从配置到 artifact 的全程。把这段输出与第 4 节的链路对照读，每一行都能找到它在 Kconfig 或 Makefile 里的源头。

关于编译命令的完整参数、变量覆盖与交叉编译选项，本篇只借它说明输出形态，真正权威的讨论在 04 册，操作步骤在 02-03；此处不展开 `make` 的各种开关，以免与这两处重复。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是关于赋值符号的细节：本快照 `drivers/net/wireguard/Makefile` 第 17 行实际写的是 `obj-$(CONFIG_WIREGUARD) := wireguard.o`，用的是 `:=`，而上层 `drivers/net/Makefile` 第 13 行用的是 `+=`。任务口径中常见的 `+=` 写法与这里的源码并不一致，核验时必须以源码为准，不可照抄记忆中的形式。`+=` 与 `:=` 在 Kbuild 里语义不同：前者把目标追加到已有列表，后者直接赋值覆盖；虽然在这个具体驱动里两者结果相同（因为该目标此前没有其他值），但养成「按源码逐字核对」的习惯，是避免踩坑的根本。

第二个陷阱是 `ccflags-y` 第一行的引号形式。`-D'pr_fmt(fmt)=KBUILD_MODNAME ": " fmt'` 里既有单引号包裹整个宏定义，又有宏值内部合法的 C 字符串双引号，还有转义。手写时极易漏掉某层引号，导致编译报出晦涩的宏展开错误。正确做法是从源码复制而非凭记忆重敲，并理解它的意图：为驱动所有 `pr_*` 打印统一加上模块名前缀。第三个陷阱是误以为打开 `WIREGUARD_DEBUG` 只是「多打日志」。如第 4 节所述，它会通过 `-DDEBUG` 激活 `main.c` 里的自检块，任一自检失败都会让模块加载返回 `-ENOTRECOVERABLE`；在精简或裁剪过的内核上，若自检依赖的功能被裁掉，可能出现「平时能加载、打开调试反而加载失败」的反直觉现象。

第四个陷阱是混淆 `=y` 与 `=m` 的运行期后果。`=y` 把驱动编进内核镜像，随内核启动即存在，但无法用 `rmmod` 卸载，更新驱动必须换内核；`=m` 产出 `wireguard.ko`，可用 `modprobe`/`rmmod` 按需管理（加载操作见 02-03）。选择哪种取决于部署形态：发行版通用内核通常选 M 以保留灵活性，嵌入式固定镜像可能选 Y 以减少启动依赖。第五个陷阱是以为 `select` 拉起的依赖必然可用。`select` 只保证配置项被打开，但在深度裁剪的内核里，被依赖的底层代码是否真正编进镜像，仍取决于其自身的依赖是否完整；构建失败时应沿着依赖矩阵逐层核对（依赖矩阵的源码依据见 02-01）。第六个陷阱是把 `tristate` 当成 `bool`：后者只有 Y/N，没有 M 态，一旦把 `WIREGUARD_DEBUG` 误设为 M 会在配置系统里报错，因为它根本不接受这个值。

最佳实践归纳为四步。第一步，把 Kconfig 与 Makefile 当作一份「契约」来读：先在 `drivers/net/Kconfig` 确认符号类型与依赖，再到两级 Makefile 确认该符号如何被消费，形成「定义—消费」的闭环认知。第二步，配置时用只读命令 `.config` 回读实际取值，不凭菜单记忆判断状态，尤其注意 `# CONFIG_X is not set` 这种「未选中」的规范写法。第三步，改动调试开关前，先理解它会通过 `-DDEBUG` 改变启动路径上的自检行为，并在可控环境验证，避免在生产内核上直接启用。第四步，凡涉及赋值符号、引号形式与生成文件这类易错点，一律以源码逐字核对为本，拿不准的标注「需对照实际版本核验」，再查完整源码树或目标系统。这四步的核心精神与上一篇一致：让每一条编译结果都能回溯到一条确切的配置语句。

### 7. 小结与延伸阅读

本篇逐行拆解了 WireGuard 内核构建配置的四条语句链：`drivers/net/Kconfig` 中 `config WIREGUARD` 是 `tristate`，`depends on NET && INET` 约束可见性，五条 `select` 自动拉取 UDP 隧道与加密库依赖；`config WIREGUARD_DEBUG` 是 `bool`，依赖前者并通过编译参数控制调试自检。`drivers/net/Makefile` 的 `obj-$(CONFIG_WIREGUARD) += wireguard/` 决定是否递归进入子目录，`drivers/net/wireguard/Makefile` 的 `wireguard-y` 列出输入目标、第 17 行 `obj-$(CONFIG_WIREGUARD) := wireguard.o` 完成聚合，`ccflags-y` 提供无条件与条件两类编译参数。`CONFIG_WIREGUARD` 的 Y/M/N 三态分别导向内建、模块与跳过三种构建结果，而 `WIREGUARD_DEBUG=y` 会通过 `-DDEBUG` 激活 `main.c` 的自检块。理解「Kconfig 定义符号、Makefile 消费符号」这条主线，就掌握了打开任意内核驱动构建配置的通用方法。

延伸阅读建议按三条线走：想要实际动手编译、加载模块与走 dkms 兼容路径，读 02-03；想要理解被 `-DDEBUG` 激活的自检与静态检查细节，读 02-05；想要拿到命令参数、netlink 常量与模块接口的权威全集，读 04 册，其中命令参数见 04-01、netlink 属性见 04-05、uapi 常量见 04-06、模块参数与 sysfs 见 04-07。跨册随查按（字段见 05-01 ｜ 参数见 04-07 ｜ 原理见 06-01 ｜ 模块见 07-01）执行：结构体逐字段去 05、参数与接口全集去 04、机制与调用链去 06、目录级模块能力去 07、运维与基准去 08。本篇所有涉及具体路径、符号名与取值的内容，均以 `_wglinux_build/upstream_src/` 下对应文件为准；编译参数与操作细节是 04 册与 02-03、02-04、02-05 的范围，这里只建立构建配置的心智模型，不做重复展开。至此，02 册的「静态地图」与「配置语言」两块地基已经铺好，后续篇章将在此之上进入真实构建与调试操作。
