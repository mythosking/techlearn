# Suricata 技术资料 · 04 参数与 API 手册（分片 B）

## 04-05 规则关键字全集（一）：动作、协议、地址端口、方向与 meta

### 1. 本篇定位与覆盖范围

04 册是全集的「参数与 API 唯一权威源」，采用 B 手册字典型骨架，专门回答「某个名字叫什么、能取哪些值、默认是什么、配错会怎样」这一类随查问题。按 SPEC 第 4 节与总纲第 2 节的去重约定，其余各册遇到规则关键字时只给本场景最小必要写法并写「完整参数见 04-05、04-06」，不重复清单；反过来 04 册自身禁止讲模块内部实现与结构体逐字段定义，遇到「这段怎么工作」写「原理见 06-06」，遇到「这个对象里有哪些成员」写「字段见 05-05」，遇到「按目录归属哪个模块」写「模块见 07-04」。本篇 04-05 覆盖规则语法的「规则头」与「元信息选项」，也就是一条规则最外层、圆括号之前的那一段，以及圆括号内不承担载荷匹配、只描述规则身份、分类、引用与处置策略的选项；04-06 覆盖 content、pcre、byte_*、flow、flowbits、xbits、dataset 这些承担匹配逻辑的选项体关键字，04-07 覆盖命令行与 suricatasc 控制面，04-08 覆盖返回码与排错速查，四者边界必须分清，不可把「规则怎么写」与「命令怎么敲」混成一篇。

本套资料唯一事实锚点是 `upstream_src/suricata/suricata-main/`，版本基准统一写「上游 main 快照（2026-11 抓取）」；具体版本号以 `configure.ac`、`ChangeLog` 为准，正文不写绝对值。本篇所有关键字名、动作取值、配置文件格式均对照真实源码核验：规则头解析集中在 `suricata-main/src/detect-parse.c`，其中 `SigParseBasics`、`SigParseAddress`、`SigParsePort`、`DetectSetupDirection`、`ActionStringToFlags` 是可定位的入口；关键字注册清单在 `suricata-main/src/detect-engine-register.c`，以 `DetectSidRegister`、`DetectMsgRegister`、`DetectContentRegister` 一类 `Detect*Register` 调用逐项登记；meta 关键字各自的 `.name` 赋值分布在 `suricata-main/src/detect-sid.c`、`suricata-main/src/detect-gid.c`、`suricata-main/src/detect-rev.c`、`suricata-main/src/detect-msg.c`、`suricata-main/src/detect-classtype.c`、`suricata-main/src/detect-reference.c`、`suricata-main/src/detect-priority.c`、`suricata-main/src/detect-metadata.c`、`suricata-main/src/detect-target.c` 等文件；分类与引用配置在 `suricata-main/etc/classification.config`、`suricata-main/etc/reference.config`，加载路径键见 `suricata-main/suricata.yaml.in` 的 `rule-files`、`classification-file`、`reference-config-file`。凡拼写、取值、默认值无充分把握者一律写「需对照实际版本核验」并给出上述可定位目录，绝不凭印象补值。

有五条能力边界贯穿本篇，落笔不能写反。其一，Suricata 规则语法兼容 Snort 但有自有扩展，见 `suricata-main/src/detect-parse.c` 与 `suricata-main/src/detect-engine-register.c`，不能宣称百分之百兼容，遇到 Snort 特有的写法要按本快照实际支持情况核验。其二，Suricata 是 IDS / IPS / NSM 引擎，不做 IP 转发、不做路由、不是防火墙；`drop`、`reject` 这类动作在旁路 IDS 模式只产生告警或日志，真正丢包要依赖 NFQUEUE 或 AF_PACKET 桥接的 verdict，由内核或桥接对端执行，原理见 06-12。其三，引擎只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见，能拿到的是握手元数据、证书、SNI、JA3/JA4 一类信息，不得宣称能读 HTTPS 明文正文。其四，`suricata-update` 是与主程序分仓、独立发版的规则集工具，不参与 `src/` 主程序编译，本篇讲的规则文件是它下载合并后的产物，不得把工具写成主程序内建子命令。其五，`rust/` 与 Cargo 是构建的一部分，大量应用层解析器在 Rust 侧，规则里能用的 app-layer 协议关键字随之扩展，Suricata 不是纯 C 项目。

本篇按 B 手册字典型七节展开：先讲定位与覆盖范围，再给索引与全参数表，随后逐项详解每个规则头要素与 meta 关键字的名称、取值、作用与误配后果，接着给可复现的规则编写与自检示例并逐行判读输出，再收一张现象反查速查表，最后讨论版本差异与常见误用调试。全篇以「完整参数表加逐项详解」为主体，表格不空表、不省略，正文不写占位词，不展开 `Signature` 结构体有哪些成员、也不展开规则编译器如何分组这些实现细节。引用关系按统一写法收束为（字段见 05-05 ｜ 原理见 06-06 ｜ 模块见 07-04）：规则头最终落到的签名对象逐字段定义见 05-05；规则加载、解析与签名分组编译的机制见 06-06；detect 关键字族按目录归属的模块能力见 07-04。规则内容匹配关键字的用法续见 04-06，命令行与 `-T` 自检的参数见 04-07，加载失败的排错速查见 04-08。

### 2. 索引与全参数表

规则头五要素的对照见下表，取值形态一列给的是语法类别而非逐条枚举，确切拼写以 `suricata-main/src/detect-parse.c` 为准。

| 要素 | 关键字或取值 | 作用 | 源码锚点 | 误配后果 |
|---|---|---|---|---|
| 动作 | alert \| pass \| drop \| reject \| rejectsrc \| rejectdst \| rejectboth | 命中后的处置级别 | detect-parse.c 的 ActionStringToFlags | 旁路模式写 drop 不会真丢包 |
| 协议 | tcp \| udp \| icmp \| ip 及 app-layer 协议名 | 限定生效的协议族 | detect-parse.c 的 SigParseBasics | 协议名不支持则整条规则加载失败 |
| 地址 | 变量 \| any \| 取反 \| CIDR \| 列表 | 限定源与目的地址 | detect-parse.c 的 SigParseAddress | 变量未定义导致加载报错 |
| 端口 | 单值 \| 范围 \| 列表 \| any \| 取反 | 限定源与目的端口 | detect-parse.c 的 SigParsePort | 范围写法颠倒会解析失败 |
| 方向 | 单向符与双向符两种 | 决定地址端口对应关系 | detect-parse.c 的 DetectSetupDirection | 只支持单双向两种，写反即报错 |

meta 与身份类关键字见下表，它们不改变匹配条件，只描述规则本身的身份、分类、优先级与处置策略。注册表入口统一在 `suricata-main/src/detect-engine-register.c`，逐项 `.name` 赋值在各自 `src/detect-*.c` 文件。

| 关键字 | 作用 | 取值形态 | 源码锚点 | 误配后果 |
|---|---|---|---|---|
| msg | 告警可读性标题 | 双引号字符串 | detect-msg.c | 缺省则 EVE 里标题为空 |
| sid | 规则唯一编号 | 正整数 | detect-sid.c | 重复或与 gid 冲突即加载失败 |
| gid | 规则组编号 | 正整数，默认 1 | detect-gid.c | 与 sid 组合不唯一会冲突 |
| rev | 规则修订号 | 正整数 | detect-rev.c | 不递增会让下游误判未更新 |
| classtype | 分类与默认优先级 | 已登记短名 | detect-classtype.c | 短名不在 classification.config 会报错 |
| reference | 外部情报链接 | 系统名加标识 | detect-reference.c | 系统名未登记会告警或忽略 |
| priority | 覆盖分类优先级 | 整数，越小越紧急 | detect-priority.c | 与 classtype 优先级混用易误判 |
| metadata | 自定义标签 | 逗号分隔键值对 | detect-metadata.c | 仅作标注，不参与匹配 |
| target | 标记受攻击方向 | src_ip 或 dst_ip | detect-target.c | 取值需对照实际版本核验 |
| tag | 命中后追加记录 | 会话或包数等 | detect-tag.c | 长期开启会放大日志量 |
| threshold | 规则级阈值抑制 | 类型加计数加时间 | detect-threshold.c | 抑制过强会掩盖真实告警 |
| detection_filter | 按源或目的聚合 | 计数加时间窗口 | detect-detection-filter.c | 与 threshold 语义勿混 |
| noalert | 命中但不告警 | 无参数 | detect-flowbits.c 相关 | 常用于 flowbits 中间状态 |
| requires | 声明版本能力要求 | 关键字或版本标签 | detect-engine-register.c | 不满足则规则被跳过 |

按 SPEC 第 6 节约定，上表单元格内凡是出现「或」语义的竖线都写作转义的 `\|`；本表取值列同样以斜杠或逗号代替竖线，正是出于这个原因。图 04-05-01 与两张表合起来构成本篇索引：先按要素定位分组，再在 `suricata-main/src/detect-parse.c` 里按 `SigParseBasics`、`ActionStringToFlags` 检索确切解析入口，最后用 `suricata -T` 与 `suricata --list-keywords` 双向核对，这条「查表、查源码、查自检输出」的三步法贯穿全册。规则头与选项体的分界也提醒一点：`msg`、`sid` 写在圆括号内，动作、协议、地址、端口、方向写在圆括号外，把 `sid` 误写到括号外会得到解析错误，具体错误文本的判读见 04-08。

### 3. 逐项详解

**动作（action）**：动作写在规则最左端，`suricata-main/src/detect-parse.c` 的 `ActionStringToFlags` 把字符串映射成内部标志。已核验的取值有 `alert`（仅告警）、`pass`（放行并跳过后续检测）、`drop`（丢弃并告警）、`reject`、`rejectsrc`、`rejectdst`、`rejectboth`（丢弃并向一端或两端回送重置报文）。`drop` 实际返回 `ACTION_DROP` 与 `ACTION_ALERT` 的组合，`reject` 系还要经 `SigParseActionRejectValidate` 校验权限与编入支持，源码明确提示需要 root 或超级用户权限、且相应能力须已编译进程序，否则不能生效。此外在 firewall 模式下还有 `config` 一类专用动作，见 `detect-parse.c` 相关分支，是否受支持需对照实际版本核验。误配后果最典型的是「旁路 IDS 里写了 drop 却以为已经阻断」：Suricata 不做转发，丢包由 NFQUEUE 或桥接 verdict 执行，原理见 06-12。

**协议（proto）**：协议字段限定规则生效的传输或应用层协议，基础族为 `tcp`、`udp`、`icmp`、`ip`，app-layer 协议名随已编入的解析器扩展，可用 `suricata --list-rule-protos` 与 `suricata --list-app-layer-protos` 列出本构建支持的实际取值，选项见 04-07。协议名大小写与别名、以及某个 app-layer 协议是否登记，需对照 `suricata-main/src/detect-engine-register.c` 与 `suricata-main/src/detect-parse.c` 核验。误配后果是整条规则加载失败：未知协议名会在 `SigParseBasics` 阶段被拒，`suricata -T` 会把它计入失败规则数，错误文本判读见 04-08。切勿把协议字段写成端口或应用名，二者层次不同。

**地址（src / dst address）**：源、目的地址支持 `any`、取反前缀、CIDR 网段、逗号列表与地址变量，变量在 `suricata-main/suricata.yaml.in` 的 `vars` 段定义，如 `$HOME_NET`、`$EXTERNAL_NET`，键名需对照实际版本核验。解析入口是 `suricata-main/src/detect-parse.c` 的 `SigParseAddress` 与 `IPOnlySigParseAddress`；源码单测里可见 `[1.2.3.4, 5.6.7.8]`、`[80, 81]`、`::1` 这类列表与 IPv6 写法，说明列表和取反在同一地址位可组合。误配后果有三类：变量未定义导致加载报错、把 `HOME_NET` 方向写反导致规则永不命中、把整段地址列表塞进单元格超过 90 字符（表格约定见第 2 节），应把长清单移到代码块。地址与端口的配对关系由方向决定，字段见 05-05。

**端口（src / dst port）**：端口支持单值、`any`、范围（如 `1024:65535`）、列表与取反，解析入口是 `suricata-main/src/detect-parse.c` 的 `SigParsePort`。范围必须小值在前、大值在后，列表用方括号包裹、逗号分隔；`!` 取反与列表混用时的优先级需对照实际版本核验。误配后果是范围写反或列表括号不配对，规则在自检阶段被判为解析失败。端口与协议强相关：`tcp`、`udp` 才有端口语义，`icmp`、`ip` 规则的端口位通常写 `any` 或改用类型码关键字（见 04-06 的 `itype`、`icode` 一类族，需对照实际版本核验），把 HTTP 端口写进 `ip` 规则头是常见误用。

**方向（direction）**：方向符连接源与目的，本快照 `suricata-main/src/detect-parse.c` 明确只支持单向符 `->` 与双向符 `<>` 两种，源码里 `strcmp(parser->direction, "<>")` 的分支和「只支持这两种」的报错文本可直接核验，其余写法如 `<-` 会被拒。解析由 `DetectSetupDirection` 完成，双向规则还会走 `SigConsolidateDirection` 做方向合并，源码单测里有大量 `alert tcp 1.2.3.4 any <> 192.168.1.5 any` 形态的用例。单向符表示左侧为源、右侧为目的；双向符表示两端互为源目的，引擎会按地址与端口对称性处理。误配后果是把双向场景写成单向导致回程流量漏检，或用错符号直接加载失败。机制见 06-06，字段见 05-05。

**msg**：写在圆括号内，取双引号字符串，是 EVE JSON `alert.signature` 与 fast.log 里最直观的可读标题，`.name` 赋值见 `suricata-main/src/detect-msg.c`。它不参与匹配，纯粹用于人工判读与下游告警聚合。误配后果是缺省时告警标题为空、排查时无法定位规则，或字符串里未转义分号与双引号导致选项体提前截断，进而整条规则解析失败。建议每条规则都写、且带上团队可检索的前缀，例如统一的事件族名。输出字段与聚合方式见 04-04、06-11。

**sid / rev / gid**：三者共同构成规则的唯一身份。`sid` 是规则编号，`.name` 见 `suricata-main/src/detect-sid.c`；`gid` 是组编号，默认 1，见 `suricata-main/src/detect-gid.c`；`rev` 是修订号，见 `suricata-main/src/detect-rev.c`。`gid` 与 `sid` 的组合必须全局唯一，重复会被加载器拒绝；自定义规则通常用本地号段，避免与 `suricata-update` 合并后的公共规则撞号，工具独立发版的定位见 07-11。误配后果是重复 sid 导致规则被跳过、或 `rev` 不递增让下游缓存误判规则未更新。三者写入 `Signature` 后的字段定义见 05-05。

**classtype**：取已登记的分类短名，`.name` 见 `suricata-main/src/detect-classtype.c`，短名与默认优先级的对照表在 `suricata-main/etc/classification.config`，格式为 `config classification: 短名,描述,优先级`，例如 `not-suspicious,Not Suspicious Traffic,3`。解析时会用分类里的默认优先级填充规则优先级，随后可被显式 `priority` 覆盖。误配后果是短名未登记导致加载报错，或误以为分类能参与匹配——它只是元信息，真正决定命中与否的是 04-06 的匹配关键字。配置落位见 `suricata-main/suricata.yaml.in` 的 `classification-file`。

**reference**：取「系统名加标识」的形态，`.name` 见 `suricata-main/src/detect-reference.c`，系统名与 URL 前缀的映射在 `suricata-main/etc/reference.config`，格式为 `config reference: 系统名 URL`。它给告警附上外部情报链接，便于研判。误配后果是系统名未在 `reference.config` 登记时告警或该引用被忽略；把整条 URL 直接塞进 `reference` 而不写系统名也是常见错法。引用与分类两个配置文件都属于可信输入，其目录权限与信任边界见 08-05。

**priority**：取整数，数值越小越紧急，`.name` 见 `suricata-main/src/detect-priority.c`。它覆盖 `classtype` 带来的默认优先级，供下游按严重度分拣。误配后果是与 `classtype` 的默认优先级混用却没意识到覆盖关系，导致同一批告警严重度口径不一；另外 `priority` 只影响标注与部分排序，不具备 `pass` 那样的短路能力，不要拿它当过滤开关。优先级在 EVE 告警事件里的呈现见 04-04。

**metadata**：取逗号分隔的自定义键值对，`.name` 见 `suricata-main/src/detect-metadata.c`，常见写法如 `service http`、`created_at 2026_11_13` 一类标签。它不参与匹配，只作规则集管理、归属标注与工具链过滤的输入，具体键是否被引擎或外部工具消费需对照实际版本核验。误配后果是把元数据当成匹配条件，或写入含分号、竖线的值破坏选项体解析；表格里若出现「或」语义的竖线须写成 `\|`。规则集管理与标签约定见 03-03。

**target**：标记受攻击方向，`.name` 见 `suricata-main/src/detect-target.c`，常见取值为 `src_ip` 或 `dst_ip`，确切取值与语义需对照实际版本核验。它影响告警里「谁是被攻击方」的呈现，不改变匹配结果。误配后果是方向标反让研判结论颠倒，或在不支持该取值的构建里被判为未知选项。字段与事件呈现见 05-08、06-11。

**tag / threshold / detection_filter / noalert / requires**：这一组是「命中之后怎么收敛」的补充选项。`tag` 命中后追加记录会话或包，`.name` 见 `suricata-main/src/detect-tag.c`；`threshold` 做规则级阈值抑制，见 `suricata-main/src/detect-threshold.c`；`detection_filter` 按源或目的在窗口内聚合，见 `suricata-main/src/detect-detection-filter.c`；`noalert` 让规则命中但不产生告警，常用于 `flowbits` 的中间状态，注册与用法见 `suricata-main/src/detect-flowbits.c`、`suricata-main/src/detect-engine-register.c`；`requires` 声明规则对关键字或版本能力的要求，不满足时规则会被跳过，`suricata-main/src/detect-engine-loader.c` 的加载统计里专门有 `rules skipped` 一项与之呼应。误配后果是阈值设得过强掩盖真实攻击、`tag` 长期开启放大日志量、或把 `detection_filter` 与 `threshold` 语义混淆。状态与阈值的机制见 06-09。

**规则头整体解析链条**：把上述要素串起来看，`suricata-main/src/detect-parse.c` 的 `SigInitHelper` 读入一行规则文本，`SigParseBasics` 拆出动作、协议、地址、端口、方向，`DetectSetupDirection` 校验方向符，`SigParseAddress` 与 `SigParsePort` 分别填源目的，随后圆括号内的每个选项名到 `suricata-main/src/detect-engine-register.c` 登记的 `sigmatch_table` 里查找并调用对应 Setup 回调；找不到就报未知关键字，错误文本见 04-08。这里只讲「名字怎么对应到用法」，不展开 `Signature` 有哪些成员、也不展开分组编译流程，字段见 05-05，原理见 06-06，模块见 07-04。

### 4. 典型示例

下面给一条只含规则头与 meta 选项的最小规则，配合 `-T` 自检、协议清单查询与分类配置回查，形成「写规则、验规则、查拼写、查格式」的闭环。完整命令行参数见 04-07，`-T` 的输出判读与错误定位见 04-08，规则集的加载与合并见 03-03。规则全文如下，注意 `msg`、`sid` 等都在圆括号内，动作与地址端口在圆括号外。

```text
alert tcp $HOME_NET any -> $EXTERNAL_NET any (msg:"TEST rule header and meta"; classtype:misc-activity; priority:3; sid:1000001; rev:1; gid:1;)
```

规则加载所需的路径键在 `suricata-main/suricata.yaml.in` 中，片段如下，键名需对照实际版本核验。

```yaml
default-rule-path: /var/lib/suricata/rules
rule-files:
  - suricata.rules
  - local.rules
classification-file: /etc/suricata/classification.config
reference-config-file: /etc/suricata/reference.config
```

把规则写入独立文件并用 `-T` 只做配置与规则自检，不真正抓包；随后列出本构建支持的规则协议与关键字，最后回查分类配置格式。

```bash
cat > /tmp/local-04-05.rules <<'RULE'
alert tcp $HOME_NET any -> $EXTERNAL_NET any (msg:"TEST rule header and meta"; classtype:misc-activity; priority:3; sid:1000001; rev:1; gid:1;)
RULE

suricata -T -c /etc/suricata/suricata.yaml -S /tmp/local-04-05.rules

suricata --list-rule-protos
suricata --list-keywords=csv | grep -E ',(sid|gid|rev|msg|classtype|reference|priority|metadata|target),'

grep -n '^config classification:' /etc/suricata/classification.config | head -n 5
```

对上述命令组合的结果，以下是示例输出，具体格式需对照实际版本核验，版本字符串行按版本纪律不抄录具体版本号。

```text
<Notice> - Running suricata under test mode
<Info> - 1 rule files processed. 1 rules successfully loaded, 0 rules failed, 0 rules skipped
tcp
udp
icmp
ip
msg,sid,rev,gid,classtype,reference,priority,metadata,target
config classification: not-suspicious,Not Suspicious Traffic,3
```

逐行判读这段输出。第一行 `<Notice> - Running suricata under test mode` 是 `suricata -T` 进入测试模式的标志，说明本次只做配置与规则校验、不启动抓包线程，源码里对应的日志文本见 `suricata-main/src/suricata.c`；级别前缀是 `Notice`，日志级别体系见 04-08 与 `suricata-main/src/util-debug.h`。第二行是 `suricata-main/src/detect-engine-loader.c` 打印的加载统计：`1 rule files processed` 表示处理了一个规则文件，`1 rules successfully loaded` 表示成功一条，`0 rules failed` 与 `0 rules skipped` 表示无解析失败、无因 `requires` 不满足而跳过的规则；正常值应让前两项相等、后两项为零，若 `rules failed` 非零就要回到 `suricata.log` 找 `error parsing signature` 或 `unknown rule keyword` 定位，判读见 04-08。第三到第六行是 `--list-rule-protos` 列出的基础协议族，实际清单随构建所含解析器变化，app-layer 协议要用 `--list-app-layer-protos` 另查，不能据此断定某协议必然支持。第七行是 `--list-keywords=csv` 过滤出的 meta 关键字逗号行，用来核对 `sid`、`gid`、`classtype` 等确切拼写，避免把 `classification` 之类想当然的长名写进规则。第八行是 `classification.config` 的一条记录，三段依次是短名、描述、默认优先级，正好解释 `classtype:misc-activity` 如何取到优先级、又如何被显式 `priority:3` 覆盖。需要留意的是，日志级别前缀、统计行文、CSV 列顺序与协议清单都会随版本变化，示例仅示意结构，务必以本地结果为准。字段见 05-05 ｜ 原理见 06-06 ｜ 模块见 07-04。

把规则头与 meta 的高频问题收敛成现象反查速查表，便于按现象定位该查哪个要素。单元格内用逗号分隔，未出现竖线；完整取值见第 2 节两张表与 `suricata-main/src/detect-parse.c`。

| 现象 | 优先核对的要素 | 判读要点 | 关联册 |

### 6. 版本差异

版本基准仍是「上游 main 快照（2026-11 抓取）」，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当版本号。规则关键字是随版本演进最活跃的一类事实：新关键字会登记进 `detect-engine-register.c`，旧关键字会被标记 deprecated、由 `sigmatch_table[].alternative` 指向替代项，`suricata-main/src/detect-parse.c` 里可见 `keyword '%s' is deprecated` 一类告警文本；动作取值、协议别名、方向处理也会调整，因此本篇清单是「这份快照的事实」而非跨版本永久承诺。

本快照能直接观察到的差异点至少有三处。其一是动作的扩展：除 `alert`、`pass`、`drop` 外，`reject`、`rejectsrc`、`rejectdst`、`rejectboth` 已在 `ActionStringToFlags` 里登记，且 firewall 模式引入了 `config` 一类专用动作与 `ACTION_SCOPE_*` 作用域，这与旧资料只讲四大动作的口径不同，迁移规则集时要按 `suricata-main/src/detect-parse.c` 的实际分支核对。其二是关键字注册规模：`suricata-main/src/` 下 `detect-*.c` 文件数以百计，`detect-engine-register.c` 里 `Detect*Register()` 调用密集，说明关键字全集远大于 outline 列举的子集，04-05 与 04-06 只覆盖最核心的两组，其余如 `flow_age`、`flow_pkts`、`flow_elephant`、`requires`、`frame` 等较新的族是否在各场景可用需对照实际版本核验。其三是配置读取口径：`etc/classification.config` 与 `etc/reference.config` 的路径由 `suricata.yaml.in` 的 `classification-file`、`reference-config-file` 指定，旧资料里常见的相对路径写法在本快照是否仍被接受需对照实际版本核验，不能照搬。

由此得到一条通用版本纪律：任何「关键字叫什么」「动作取值有哪些」「某协议是否受支持」的问题，最终都要回到 `suricata-main/src/detect-parse.c`、`suricata-main/src/detect-engine-register.c`、`suricata-main/src/detect-*.c`、`suricata-main/etc/` 用 Read、Grep 核实；凡 0.1 节未列出或无法核实的文件一律不写进正文；不确定的关键字名、动作拼写、配置键一律写「需对照实际版本核验」并给出可定位目录。规则语法兼容 Snort 但有自有扩展，跨版本复用规则集前必须逐条用 `-T` 自检，不能宣称百分之百兼容。性能与容量类结论同样不跨版本照搬，一律标注「需在目标机型实测」，不给绝对值，基准方法见 08-01。规则头决定「对哪些包生效」，内容匹配见 04-06，命令与 RPC 见 04-07，返回码与排错见 04-08，机制差异见 06-06，模块归属见 07-04。

### 7. 常见误用与调试

第一类是规则头与选项体层次混淆。动作、协议、地址、端口、方向必须写在圆括号外，`msg`、`sid`、`classtype` 等必须写在圆括号内，把 `sid` 漏到括号外、或把选项体的分号漏写导致两项粘连，都会被 `SigParseBasics` 判为解析失败，`suricata -T` 的 `rules failed` 随即非零。方向符只支持单向 `->` 与双向 `<>`，写成 `<-` 或漏写方向都会报错，源码里「只支持这两种」的文本可直接核验。排查顺序固定为：先看 `suricata.log` 里 `error parsing signature` 指到的文件与行号，再回查该行的括号与分号，最后用 `-T` 复核，不要靠肉眼反复扫全量规则集。

第二类是把处置动作写成实际阻断。`drop`、`reject` 在旁路 IDS 模式只产生告警与 EVE 事件，真正丢包依赖 NFQUEUE 或 AF_PACKET 桥接的 verdict，且 `reject` 系还要求 root 权限与相应能力已编入程序，`SigParseActionRejectValidate` 的提示文本见 `suricata-main/src/detect-parse.c`。把「规则写了 drop」等同于「流量已被阻断」是最危险的误判之一，IPS 部署与 verdict 策略见 03-05，原理见 06-12；Suricata 不做 IP 转发、不做路由、不是防火墙，这条边界在任何一篇都不能写反。

第三类是身份与分类配置脱节。`sid` 与 `gid` 组合必须唯一，自定义规则撞上公共规则号段会被加载器跳过；`classtype` 的短名必须在 `classification.config` 登记、`reference` 的系统名必须在 `reference.config` 登记，两个文件的路径由 `suricata.yaml.in` 的 `classification-file`、`reference-config-file` 指定，配置段见 04-02。`suricata-update` 独立发版、负责规则下载合并，合并后要重新 `-T` 自检，不得把工具写成主程序内建子命令；`priority` 与 `classtype` 默认优先级的覆盖关系也要理清，否则同一批告警严重度口径会乱。分类与引用文件属于可信输入，权限与信任边界见 08-05。

第四类是纪律与能力边界。规则语法兼容 Snort 但有自有扩展，不能宣称百分之百兼容，遇到旧规则里的生僻关键字要用 `--list-keywords` 核对；引擎只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见，不得宣称能读 HTTPS 明文正文；多线程 runmode 不等于加线程必然线性提速；`metadata` 只作标注、`priority` 只影响严重度，都不能当过滤开关；`rust/` 与 Cargo 是构建的一部分，Suricata 不是纯 C 项目。任何吞吐、pps、丢包率、内存占用结论一律标注「需在目标机型实测」，不给绝对值。逐项字段定义见 05-05，加载与分组机制见 06-06，关键字模块归属见 07-04，加载错误文本判读见 04-08，常见误用与调试的完整案例见 08-04。

## 04-06 规则关键字全集（二）：content、pcre、byte_*、flow、flowbits、xbits、dataset

### 1. 本篇定位与覆盖范围

本套资料唯一事实锚点是 `upstream_src/suricata/suricata-main/`，版本基准统一写「上游 main 快照（2026-11 抓取）」；具体版本号以 `configure.ac`、`ChangeLog` 为准，正文不写绝对值。本篇所有关键字名均对照 `suricata-main/src/detect-*.c` 里的 `sigmatch_table[...].name` 赋值核验：`content` 见 `detect-content.c`、`pcre` 见 `detect-pcre.c`、`byte_test` 见 `detect-bytetest.c`、`byte_jump` 见 `detect-bytejump.c`、`byte_extract` 见 `detect-byte-extract.c`、`isdataat` 与 `endswith` 见 `detect-isdataat.c`、`flow` 见 `detect-flow.c`、`flowbits` 见 `detect-flowbits.c`、`xbits` 见 `detect-xbits.c`、`dataset` 见 `detect-dataset.c`、`datarep` 见 `detect-datarep.c`、`threshold` 见 `detect-threshold.c`、`dsize` 见 `detect-dsize.c`、`ttl` 见 `detect-ttl.c`、`file.data` 见 `detect-file-data.c`；修饰符 `nocase`、`depth`、`startswith`、`offset`、`distance`、`within`、`fast_pattern` 分别见 `detect-nocase.c`、`detect-depth.c`、`detect-offset.c`、`detect-distance.c`、`detect-within.c`、`detect-fast-pattern.c`。统一注册入口在 `suricata-main/src/detect-engine-register.c`，以 `DetectContentRegister`、`DetectPcreRegister`、`DetectFlowRegister`、`DetectFlowbitsRegister` 一类调用登记。凡选项拼写、参数顺序、默认值无充分把握者一律写「需对照实际版本核验」并给出上述可定位目录。

有四条能力边界贯穿本篇。其一，规则语法兼容 Snort 但有自有扩展，不能宣称百分之百兼容，`content` 修饰符、`sticky buffer`、`xbits`、`dataset` 等都是 Suricata 自有或扩展能力，旧规则集迁移前必须逐条 `-T` 自检。其二，引擎只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见，`content` 匹配不到 HTTPS 明文正文，能拿到的是握手元数据、证书、SNI、JA3/JA4 一类信息；`file.data` 等文件关键字也依赖重组深度，见 06-10。其三，Hyperscan 是可选的多模式匹配加速，`fast_pattern` 的选择与 `mpm-algo` 的实际效果依赖构建期是否编入 Hyperscan，缺失时回退 AC 等其他实现，见 `suricata-main/src/util-mpm-hs.c` 与 `configure.ac`，不得写成必需依赖或唯一实现，具体吞吐影响需在目标机型实测。其四，Suricata 是 IDS / IPS / NSM 引擎，不做 IP 转发、不做路由、不是防火墙，关键字只影响「是否告警或丢弃」，丢包执行见 06-12。

### 3. 逐项详解

**content 及修饰符族**：`content` 是载荷匹配的核心基元，`.name` 见 `suricata-main/src/detect-content.c`，取双引号字节串，串内可用竖线包围十六进制字节，例如同时含可打印字符与二进制字节的形态；表格里若出现「或」语义的竖线须写成 `\|`，规则文本里则按引擎语法写。修饰它的关键字各自独立注册：`nocase` 忽略大小写，见 `detect-nocase.c`；`depth` 从缓冲区起点限定最大匹配深度，见 `detect-depth.c`；`startswith` 要求内容从缓冲区开头匹配，同一文件里以 `DETECT_STARTS_WITH` 登记；`endswith` 要求内容在缓冲区末尾匹配，见 `detect-isdataat.c` 的 `DETECT_ENDS_WITH`；`offset` 指定匹配起点，见 `detect-offset.c`。误配后果是修饰符没有前置 `content` 可依附时解析报错，`suricata-main/src/detect-parse.c` 里有「请先使用 content 关键字」一类文本可直接核验；`nocase` 对纯二进制串没有意义，`depth` 与 `offset` 的先后口径要按实际版本核验。多模式匹配如何选用 `fast_pattern` 见 06-07，字段见 05-05。

**相对位置族 distance / within / fast_pattern / rawbytes / replace**：`distance` 指定本次 `content` 相对前一次匹配结束处的偏移，见 `detect-distance.c`；`within` 指定本次匹配必须落在距前一次结束处的窗口内，见 `detect-within.c`；两者都依赖「前面已有 content」，否则报依附错误。`fast_pattern` 显式指定交给多模式匹配器的候选串，见 `detect-fast-pattern.c`，参数 `only`、`chop` 一类取值需对照实际版本核验；选过短的串会放大候选集、拖慢检测，具体影响需在目标机型实测。`rawbytes` 与 `replace` 分别在 `detect-engine-register.c` 里以 `DetectRawbytesRegister`、`DetectReplaceRegister` 登记，前者匹配未规范化原始字节、后者与内联改写相关，是否受支持需对照实际版本核验；`replace` 涉及 IPS 内容改写，原理见 06-12。误配后果是相对位置写反导致永不命中，或 `fast_pattern` 选串不当放大编译期与运行期开销。

**pcre**：`.name` 见 `suricata-main/src/detect-pcre.c`，写法为斜杠包围的正则加尾部标志位，本快照底层用 PCRE2，源码里可见 `pcre2_match`、`PCRE2_UNGREEDY`、`PCRE2_HAVE_JIT` 以及 `pcre_match_limit`、`pcre_match_limit_recursion` 一类限制项，还有 `DETECT_PCRE_RELATIVE` 标志表明可相对前一匹配定位。标志位（大小写、点号匹配换行、相对、取反等）的确切字母与组合需对照实际版本核验，不能凭印象照搬 PCRE1 的写法。误配后果有两类：正则回溯复杂会显著拖慢检测，属 08-05 强调的不可信规则风险；表达式格式或标志写错会在 `-T` 时加载失败。`pcre` 是可选加速项之外的通用正则能力，与 Hyperscan 是否编入无直接依赖，原理见 06-08。

**byte_* 族**：`byte_test` 读取指定字节数并按操作与阈值比较，见 `suricata-main/src/detect-bytetest.c`；`byte_jump` 按读到的数值跳转检测光标，见 `suricata-main/src/detect-bytejump.c`；`byte_extract` 把读到的值存入命名变量供后续关键字引用，见 `suricata-main/src/detect-byte-extract.c`；`detect-engine-register.c` 里还有 `DetectBytemathRegister` 登记的 `byte_math` 做多步运算。参数通常包含字节数、偏移、相对标志、字节序、进制与变量名，确切顺序与取值需对照实际版本核验，不能把 `byte_test` 的 `oper`、`rvalue` 与 `byte_jump` 的偏移参数混用。误配后果是参数顺序错导致解析失败、读取越界导致规则永不命中、变量名冲突让 `byte_extract` 结果不可用。数值比较与 inspection 顺序见 06-08。

**isdataat**：`.name` 见 `suricata-main/src/detect-isdataat.c`，判断指定位置是否还有数据，可带取反语义，常与 `content` 配合限定载荷边界；同文件还登记了 `endswith`。确切参数（绝对位置、相对标志、取反写法）需对照实际版本核验。误配后果是把「有数据」与「无数据」判反，导致规则在短包上误命中、在长包上漏检。`dsize` 与它都涉及长度口径，但前者看整体载荷长度、后者看光标位置，二者不要互相替代。字段见 05-05，原理见 06-08。

**flow**：`.name` 见 `suricata-main/src/detect-flow.c`，取状态词组合，`suricata-main/src/detect-flow.c` 的解析分支已核验的取值有 `established`、`not_established`、`stateless`、`to_client`（别名 `from_server`）、`to_server`（别名 `from_client`）、`no_frag`、`only_frag`、`only_stream`、`no_stream`。它把规则限定在特定流建立状态、方向与分片或重组形态上。误配后果是方向词与规则头的 `->`、`<>` 冲突，或在只有单包的场景写 `established` 导致永不命中；`to_server` 与 `to_client` 要和实际流量方向对齐。流状态判定与重组机制见 06-04、06-08，字段见 05-03。`detect-engine-register.c` 里还登记了 `flow_age`、`flow_pkts`、`flow_pkts_to_server`、`flow_bytes`、`flow_elephant` 等扩展族，路径见 `suricata-main/src/detect-flow-age.c`、`detect-flow-pkts.c`、`detect-flow-elephant.c`，可用取值需对照实际版本核验。

**flowbits**：`.name` 见 `suricata-main/src/detect-flowbits.c`，命令词已核验为 `set`、`unset`、`isnotset`、`isset`、`noalert`，另有 `toggle` 一类用法，可在同一条流的规则之间传递布尔状态。典型组合是一条规则 `flowbits:set,名字; flowbits:noalert;` 只置位不告警，另一条规则 `flowbits:isset,名字;` 再据状态告警，这样把多步检测拆成规则链。误配后果是只写 `isset` 却没有对应 `set` 规则、或 `set` 与 `isset` 的名字大小写不一致（名字通常区分大小写，需对照实际版本核验），导致状态链断裂、规则永不命中；`noalert` 用错会把本该告警的规则静默掉。有状态存储与跨规则依赖见 06-09，字段见 05-03。

**xbits**：`.name` 见 `suricata-main/src/detect-xbits.c`，在 `flowbits` 基础上支持跨流、跨主机，命令词已核验为 `set`、`isset`、`unset`、`isnotset`、`toggle`、`noalert`，并带 `track` 与 `expire` 参数；`track` 的取值在源码里可见 `ip_src`、`ip_dst`、`ip_pair`，`expire` 指定过期秒数，确切取值范围需对照实际版本核验。误配后果是 `track` 写错让状态挂到错误维度、`expire` 过长导致状态长期占用内存、`track ip_pair` 的方向与预期不符。`hostbits` 在 `detect-engine-register.c` 里以 `DetectHostbitsRegister` 登记，是相近的跨主机能力，取值需对照实际版本核验。存储与过期机制见 06-09。

**dataset / datarep**：`dataset` 的 `.name` 见 `suricata-main/src/detect-dataset.c`，已核验的参数键有 `type`（取值 `md5`、`sha256`、`string`、`ipv4`、`ip`）、`save`、`load`、`state`，命令词有 `isset`、`set`、`unset`；`datarep` 见 `suricata-main/src/detect-datarep.c`，按信誉计数匹配，具体参数需对照实际版本核验。`dataset` 常把外部情报表加载进内存做成员判定，`load` 指向表文件、`save` 与 `state` 控制运行期持久化。误配后果是大表加载吃内存、`type` 与表内容格式不符导致加载失败、`load` 路径不可读时规则被跳过；不可信规则用超大 `dataset` 表是 08-05 明确点出的资源耗尽风险，容量影响需在目标机型实测。控制面还有 `dataset-add`、`dataset-remove` 一类运行期命令，见 `suricata-main/src/unix-manager.c` 与 04-07。

**threshold / detection_filter**：`threshold` 的 `.name` 见 `suricata-main/src/detect-threshold.c`，`detection_filter` 见 `suricata-main/src/detect-detection-filter.c`，两者都做告警收敛但语义不同：前者按规则在 `count`、`seconds`、`type` 维度抑制，后者按源或目的地址在窗口内聚合后再判定；`type` 的取值如 `limit`、`threshold`、`both` 一类需对照实际版本核验。与之相关的还有 `suricata.yaml.in` 侧的 `threshold.config` 全局抑制文件，见 03-03。误配后果是抑制过强把真实攻击淹没、把两个关键字混用导致计数口径不一致、`noalert`（04-05）与阈值叠加后完全无告警。阈值、抑制与有状态求值的机制见 06-09。

**dsize / ttl / file.data**：`dsize` 判定载荷长度，见 `suricata-main/src/detect-dsize.c`；`ttl` 判定 IP 首部 TTL，见 `suricata-main/src/detect-ttl.c`；`file.data` 是把后续匹配切到文件数据缓冲区的 sticky buffer，`.name` 见 `suricata-main/src/detect-file-data.c`。`dsize` 与 `ttl` 都支持整数、范围与比较或取反写法，确切语法需对照实际版本核验；分片与 TCP 重组会改变可见载荷长度，跨越多跳后 TTL 也会递减，写死单一数值容易漏检。`file.data` 依赖文件提取与重组深度，深度不足时看不到完整文件，见 06-10；加密传输里的文件内容同样受可见性限制。误配后果是在重组或隧道场景把它们当绝对判据，导致规则随环境变化而时灵时不灵。输出与文件事件字段见 04-04、06-10。

### 4. 典型示例

下面给一条组合了 `content` 修饰符、`flow`、`flowbits` 与 `pcre` 的规则，配合 `suricata -T` 自检与 `--list-keywords` 拼写核对，形成「写规则、验规则、查关键字」的闭环。完整命令行参数见 04-07，规则头与 meta 见 04-05，加载错误判读见 04-08。规则全文如下，注意 `distance`、`within` 必须跟在已有 `content` 之后，`flowbits:isset` 需另有 `set` 规则配合。

```text
alert tcp $HOME_NET any -> $EXTERNAL_NET 80 (msg:"TEST content and flowbits chain"; flow:established,to_server; content:"GET "; depth:4; content:"HTTP/1.1"; distance:0; within:32; pcre:"/\/index\.php\?id=\d+/U"; classtype:web-application-activity; sid:1000002; rev:1;)
```

把规则写入文件后先做自检，再核对关键字拼写与正则是否被接受，最后用 `--list-keywords` 过滤出本篇涉及的几组名字。

```bash
cat > /tmp/local-04-06.rules <<'RULE'
alert tcp $HOME_NET any -> $EXTERNAL_NET 80 (msg:"TEST content and flowbits chain"; flow:established,to_server; content:"GET "; depth:4; content:"HTTP/1.1"; distance:0; within:32; pcre:"/\/index\.php\?id=\d+/U"; classtype:web-application-activity; sid:1000002; rev:1;)
RULE

suricata -T -c /etc/suricata/suricata.yaml -S /tmp/local-04-06.rules

suricata --list-keywords=csv | grep -E ',(content|pcre|flow|flowbits|xbits|dataset|byte_test|isdataat|file\.data),'
```

对上述命令组合的结果，以下是示例输出，具体格式需对照实际版本核验，版本字符串行按版本纪律不抄录具体版本号。

```text
<Notice> - Running suricata under test mode
<Info> - 1 rule files processed. 1 rules successfully loaded, 0 rules failed, 0 rules skipped
content,pcre,flow,flowbits,xbits,dataset,byte_test,byte_jump,byte_extract,isdataat,file.data
<Warning> - keyword 'uricontent' is deprecated, use http_uri instead
```

逐行判读这段输出。第一行仍是 `-T` 进入测试模式的标志，日志级别 `Notice` 与 04-05 示例一致，级别体系见 04-08 与 `suricata-main/src/util-debug.h`。第二行是 `suricata-main/src/detect-engine-loader.c` 的加载统计：处理一个文件、成功一条、`rules failed` 与 `rules skipped` 均为零，说明 `content` 修饰符的依附关系、`pcre` 的格式、`flow` 的方向词、`classtype` 短名都被接受了；正常值应让前两项相等、后两项为零，若 `rules failed` 非零，最常见就是 `distance`、`within` 前面没有 `content`，或 `pcre` 标志位写法不被本快照接受，错误文本判读见 04-08。第三行是 `--list-keywords=csv` 过滤出的关键字拼写清单，可直接用来核对 `byte_test`、`file.data` 这类带下划线或点号的确切名字，避免把 `byte_test` 写成 `byteTest`、把 `file.data` 写成 `file_data`；清单里出现 `dataset` 也说明该能力已编入。第四行是一条 deprecated 告警示例，对应 `suricata-main/src/detect-parse.c` 里 `keyword '%s' is deprecated` 一类文本，说明旧关键字仍被识别但已由 `sigmatch_table[].alternative` 指向替代项，长期应改用新名，这类告警不计入 `rules failed` 但要在升级时清理。需要留意的是，CSV 列顺序、关键字全集、告警行文会随版本变化，示例仅示意结构，务必以本地结果为准；`pcre` 标志位是否被接受尤其要用 `-T` 实测。字段见 05-05 ｜ 原理见 06-08 ｜ 模块见 07-04。

### 6. 版本差异

版本基准仍是「上游 main 快照（2026-11 抓取）」，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当版本号。选项体关键字比规则头更容易漂移：修饰符会从「依附 content 的语法糖」升级为独立注册的关键字，sticky buffer 会新增，正则库会从 PCRE1 迁到 PCRE2，有状态关键字会从 `flowbits` 扩展到 `xbits`、`hostbits`，集合类会新增 `dataset`、`datarep`，因此本篇清单是「这份快照的事实」而非跨版本永久承诺。

本快照能直接观察到的差异点至少有三处。其一是正则底层：`suricata-main/src/detect-pcre.c` 里是 `pcre2_match`、`PCRE2_UNGREEDY`、`PCRE2_HAVE_JIT` 与 PCRE2 头的引用，说明本快照用 PCRE2，旧资料里针对 PCRE1 的标志位与 `pcre_match_limit_recursion` 口径不能直接照搬，标志位字母需对照实际版本核验。其二是修饰符注册形态：`startswith` 在 `suricata-main/src/detect-depth.c` 里以 `DETECT_STARTS_WITH` 登记、`endswith` 在 `suricata-main/src/detect-isdataat.c` 里以 `DETECT_ENDS_WITH` 登记，二者并不在 `detect-content.c` 里，这与「所有修饰符都在 content 实现里」的旧印象不同，检索时要按注册文件找。其三是关键字族的扩张：`suricata-main/src/detect-engine-register.c` 里除本篇所列，还有 `DetectBytemathRegister`、`DetectEntropyRegister`、`DetectRequiresRegister`、`DetectFrameRegister`、`DetectFlowAgeRegister`、`DetectFlowElephantRegister`、`DetectDatasetRegister`、`DetectDatarepRegister`、`DetectHostbitsRegister` 等大量登记项，`suricata-main/src/` 下 `detect-*.c` 文件数以百计，说明关键字全集远大于 outline 列举的子集，未列入项是否可用需对照实际版本核验。

由此得到一条通用版本纪律：任何「关键字叫什么」「修饰符取哪些参数」「正则标志位怎么写」的问题，最终都要回到 `suricata-main/src/detect-engine-register.c`、`suricata-main/src/detect-*.c` 用 Read、Grep 核实；凡 0.1 节未列出或无法核实的文件一律不写进正文；不确定的关键字名、参数顺序、标志字母一律写「需对照实际版本核验」并给出可定位目录。规则语法兼容 Snort 但有自有扩展，跨版本复用规则集前必须逐条 `-T` 自检，不能宣称百分之百兼容；`--list-keywords` 的输出是本构建最可靠的拼写依据。Hyperscan 是可选 MPM 加速、缺失回退 AC 实现，不得写成必需依赖或唯一实现；性能与容量类结论不跨版本照搬，一律标注「需在目标机型实测」，不给绝对值，基准方法见 08-01、调优见 08-02。规则头与 meta 见 04-05，命令与 RPC 见 04-07，返回码与排错见 04-08，机制差异见 06-07 至 06-10，模块归属见 07-04、07-05。

### 7. 常见误用与调试

第一类是修饰符依附与顺序错误。`distance`、`within`、`startswith`、`endswith`、`isdataat` 一类相对或边界关键字必须接在已有 `content` 之后，`suricata-main/src/detect-parse.c` 里有「请先使用 content 关键字」一类报错文本；`depth` 从缓冲区起点算、`offset` 指定起点、`distance` 相对前一匹配结束处，三者口径不同，混用或写反会让规则永不命中。`byte_test`、`byte_jump`、`byte_extract` 的参数顺序也极易记混，写错时 `-T` 直接计入 `rules failed`。排查顺序固定为：先看 `suricata.log` 的 `error parsing signature` 与行号，再回查该行关键字顺序，最后用 `-T` 复核。

第二类是有状态关键字链断裂。`flowbits` 只写 `isset` 却没有 `set` 规则、`set` 与 `isset` 名字大小写不一致、`noalert` 误加在本该告警的规则上，都会让规则看似加载成功却永不命中；`xbits` 的 `track` 取值（`ip_src`、`ip_dst`、`ip_pair`）与 `expire` 秒数也要和实际检测维度对齐，写错会挂到错误对象上。`flow` 的方向词 `to_server`、`to_client` 必须与规则头的 `->`、`<>` 一致，否则回程流量漏检。这类问题 `-T` 不会报失败，最可靠的办法是拿脱敏 pcap 做回放验证，回放方法见 08-01，状态机制见 06-09。

第三类是不可信规则与资源风险。复杂 `pcre` 回溯、超大 `dataset` 表、过多 `fast_pattern` 候选串，都会在编译期或运行期放大内存与时间开销，`suricata -T` 与引擎分析选项应作为加载前的强制门禁，选项见 04-07、加固见 08-05；`file.data` 依赖重组深度，深度不足时看不到完整文件，见 06-10；`dsize`、`ttl` 在分片、隧道、多跳场景下取值不稳定，不宜写死单一数值。任何吞吐、pps、丢包率、内存占用结论一律标注「需在目标机型实测」，不给绝对值。

第四类是纪律与能力边界。规则语法兼容 Snort 但有自有扩展，不能宣称百分之百兼容，遇到 deprecated 关键字要按 `sigmatch_table[].alternative` 指向的新名迁移；引擎只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见，`content` 匹配不到 HTTPS 明文正文，不得宣称能读 HTTPS 明文正文；Hyperscan 是可选加速、缺失回退 AC 等其他实现，不得写成必需依赖；多线程不等于必然线性提速；Suricata 是 IDS / IPS / NSM 引擎，不做 IP 转发、不做路由、不是防火墙，关键字只影响告警或丢弃判定，丢包执行见 06-12。逐项字段定义见 05-05，匹配链求值与 MPM 机制见 06-07、06-08，关键字模块归属见 07-04、07-05，加载错误文本判读见 04-08，常见误用与调试的完整案例见 08-04。

### 3. 逐项详解

**通用组 -c / -l / -T / -D / -v**：`-c` 指定主配置文件路径，是几乎每次启动都要给的选项；`-l` 指定默认日志目录，目录不可写会让 `suricata.log`、`eve.json`、`fast.log` 一并落盘失败；`-T` 是「测试配置文件」，帮助文本明确要求配合 `-c` 使用，它只做配置与规则校验、不启动抓包线程，源码里对应 `Running suricata under test mode` 的文本，输出判读见 04-08；`-D` 在非 Windows 构建里以守护进程方式运行；`-v` 可重复使用以增加日志详细度，生产长期开启会放大日志量。误配后果是漏写 `-c` 时按内置默认路径找配置、找不到即启动失败，`-T` 不带 `-c` 则校验对象不对。日志级别与输出目标见 04-02、04-08。

**通用组 --set / --include / --pidfile / --init-errors-fatal / --user / --group**：`--set name=value` 在运行期覆盖某个配置项，常见于不改 yaml 就临时调整 `stream.inline`、`copy-mode` 一类键，键名需对照 `suricata-main/suricata.yaml.in` 核验，写错的键通常被静默忽略，故必须用 `--dump-config` 复核；`--include` 追加一个配置文件；`--pidfile` 把进程号写入指定文件；`--init-errors-fatal` 把签名初始化错误提升为致命失败，适合上线前门禁；`--user`、`--group` 在编入 `HAVE_LIBCAP_NG` 时指定初始化后降权到的用户与组。误配后果是覆盖值与文件里的值口径冲突、`--include` 路径错导致启动失败、降权后失去抓包所需能力。权限与能力边界见 08-05，字段见 05-09。

**抓包与 IPS 组 -i / -q / -d / -F / -k**：`-i` 指定在线 pcap 模式的网卡名或 IP；`-q` 进入 NFQUEUE 内联模式，队列号可用冒号给出范围（如单个队列或一段队列），需与 iptables 或 nftables 的 NFQUEUE 规则对齐；`-d` 在编入 IPFW 时指定 divert 端口；`-F` 指定 BPF 过滤文件，表达式写错会把目标流量一并过滤掉；`-k` 只接受 `all` 与 `none`，分别强制校验和检查与禁用。误配后果是队列号不匹配导致「写了 drop 却不生效」、BPF 写错导致「在线跑通但无告警」。要重申 Suricata 不做 IP 转发、不做路由、不是防火墙，丢包由内核或桥接 verdict 执行，原理见 06-12，部署见 03-05。

**抓包后端长选项 --af-packet / --pcap / --dpdk / --netmap / --af-xdp**：这些选项选择抓包后端，多数可接受可选网卡参数，不给值时按 `suricata.yaml.in` 里的接口配置走，具体键见 04-03。各后端环境要求差异大：AF_PACKET 依赖内核 TPACKET 与 fanout，DPDK 需独占网卡、大页与 EAL 参数，Netmap 与 AF_XDP 有内核与驱动要求，pcap 多用于离线或低速率；PF_RING 在当前 main 快照是否仍为受支持后端、源文件与启用方式需对照 `configure.ac` 与 `src/source-*.c` 核验，不得编造 `source-pfring.c`。误配后果是后端与实机能力对不上，轻则收不到包、重则 configure 或起机阶段报错。原理见 06-02，模块见 07-06。

**抓包文件组 -r / --pcap-file-* / --erf-in**：`-r` 指定 pcap 文件或目录做离线回放，是基准与复现的常用入口，方法见 08-01；`--pcap-file-continuous` 让目录回放持续等待新文件，`--pcap-file-delete` 在处理完成后删除 pcap，`--pcap-file-recursive` 下钻子目录，`--pcap-file-buffer-size` 设置读缓冲，`--erf-in` 处理 ERF 文件。误配后果是 `--pcap-file-delete` 误删待复现样本、目录回放没配 continuous 导致提前退出。回放相关选项的确切组合需对照实际版本核验，性能数字一律标注「需在目标机型实测」。

**检测组 -s / -S / --disable-detection / --engine-analysis**：`-s` 在 yaml 已有规则清单之外附加加载一个规则文件，`-S` 则独占加载、覆盖 yaml 的 `rule-files` 清单，二者不可混用；`--disable-detection` 整体关闭检测，此时引擎仍能抓包解码但不加载规则、不告警，容易被误判为「规则集没配好」；`--engine-analysis` 打印引擎分析报告后退出，可配合 `suricata.yaml.in` 的 `engine-analysis` 段选择报告种类，段名与取值需对照实际版本核验。误配后果是把 `-S` 当成 `-s` 导致 yaml 里的规则全被丢掉，或误开 `--disable-detection` 让上线后零告警。规则加载机制见 06-06。

**信息组 -V / --build-info / --dump-config / --dump-features / --list-* 族**：`-V` 显示版本；`--build-info` 显示构建信息，用来核对 AF_PACKET、NFQ、Hyperscan、Rust、PCRE_JIT 等特性是否编入；`--dump-config` 把运行配置扁平化打印，是复核 yaml 与 `--set` 的首选；`--dump-features` 列出提供的特性；`--list-keywords` 列出关键字，帮助文本给出 `all`、`json`、`csv` 或单个关键字名等可选参数；`--list-runmodes` 列出支持的 runmode；`--list-app-layer-protos`、`--list-rule-protos`、`--list-app-layer-hooks`、`--list-app-layer-frames` 分别列出应用层协议、规则协议、hook 与 frame。误配后果是把 `--list-keywords` 的输出当成跨版本承诺，或 `--dump-config` 泄露敏感路径未加管控。精确取值需对照实际版本核验，参数解析入口见 `suricata-main/src/suricata.c`。

**测试组 -u / -U / --list-unittests / --fatal-unittests / --simulate-ips**：`-u` 运行内建单元测试后退出，需要 `UNITTESTS` 构建；`-U` 用正则过滤用例，帮助文本里也写作 `--unittest-filter`；`--list-unittests` 列出用例，`--fatal-unittests` 让用例失败成为致命错误，`--simulate-ips` 强制进入 IPS 模式供 QA 使用。误配后果是在生产构建里调用 `-u` 无此能力、或把调试构建的性能数据当生产基准。调试构建与单测见 02-05，基准纪律见 08-01。

**--unix-socket 与 unix-command 段**：服务端的 Unix socket 控制面由构建期 `--enable-unix-socket` 类开关决定能否使用，运行期由 `suricata.yaml.in` 的 `unix-command` 段与命令行 `--unix-socket`（可带可选 socket 文件路径）启用，段名与默认值需对照实际版本核验。socket 文件权限决定谁可以向引擎发命令，务必收紧到受控主体，`shutdown`、`reload-rules`、`memcap-set` 一类命令影响运行态，见 08-05。命令注册集中在 `suricata-main/src/unix-manager.c` 的 `UnixManagerRegisterCommand` 调用，已核验的有 `shutdown`、`command-list`、`help`、`version`、`uptime`、`running-mode`、`capture-mode`、`conf-get`、`dump-counters`、`reload-rules`、`ruleset-reload-rules`、`ruleset-reload-nonblocking`、`ruleset-stats`、`ruleset-failed-rules`、`add-hostbit`、`remove-hostbit`、`list-hostbit`、`reopen-log-files`、`memcap-set`、`memcap-show`、`memcap-list`、`dataset-add`、`dataset-remove`、`dataset-add-json`、`iface-stat`、`iface-list` 等，部分命令带 `UNIX_CMD_TAKE_ARGS` 标志表示需要参数。模块见 07-12，字段见 05-09。

**suricatasc 协议与返回结构**：客户端在 `suricata-main/rust/suricatasc/`，命令清单在 `src/unix/commands.rs`，协议版本在 `src/unix/client.rs`，源码里客户端先发 `{"version": "0.2"}` 一类的握手、再发 `{"command": "command-list"}` 一类请求；命令载体是 JSON 里的 `command` 字段，参数按各命令声明的 `name`、`type`、`required` 组织，例如 `pcap-file` 需要 `filename` 与 `output-dir`、`iface-stat` 需要 `iface`。服务端应答在 `suricata-main/src/unix-manager.c` 里以 `json_object_set_new(server_msg, "return", json_string("OK"))` 一类构造，取值 `OK` 或 `NOK`，并附 `message` 字段承载文本或数据，未知命令回 `Unknown command`，重载冲突回 `Reload already in progress`，停机回 `Closing Suricata`。误配后果是把 `message` 当结构化数据解析、或忽略 `return` 的 `NOK` 就认为命令已生效。跨语言边界与 cbindgen 见 06-14、07-10。

### 4. 典型示例

下面给一组「构建核对、配置校验、控制面查询」的闭环命令：先用 `--build-info` 确认特性，再用 `-T` 自检配置与规则，随后用 `--dump-config` 复核键，最后通过 `suricatasc` 查询运行态。完整 yaml 段见 04-02 至 04-04，规则写法见 04-05、04-06，返回码与错误判读见 04-08。

```yaml
unix-command:
  enabled: yes
  filename: /var/run/suricata/suricata-command.socket
```

```bash
suricata --build-info

suricata -T -c /etc/suricata/suricata.yaml

suricata --dump-config -c /etc/suricata/suricata.yaml | grep -E 'unix-command|default-log-dir|runmode'

suricata -c /etc/suricata/suricata.yaml --unix-socket -i eth0 -D

suricatasc -c /var/run/suricata/suricata-command.socket command-list
suricatasc -c /var/run/suricata/suricata-command.socket iface-stat eth0
suricatasc -c /var/run/suricata/suricata-command.socket dump-counters
```

对上述命令组合的结果，以下是示例输出，具体格式需对照实际版本核验，版本字符串行按版本纪律不抄录具体版本号。

```text

<Notice> - Running suricata under test mode
<Info> - 1 rule files processed. 1 rules successfully loaded, 0 rules failed, 0 rules skipped
unix-command.enabled = yes
unix-command.filename = /var/run/suricata/suricata-command.socket
{"return":"OK","message":{"command-list":["shutdown","reload-rules","dump-counters","iface-stat"]}}
{"return":"OK","message":{"eth0":{"pkts":0,"drop":0}}}
{"return":"NOK","message":"Unknown command"}
```

逐行判读这段输出。第一行是 `--build-info` 的版本行，按版本纪律只示意不抄具体版本号；第二行 `Features:` 是特性摘要，`NFQ`、`AF_PACKET`、`HAVE_PACKET_FANOUT` 说明抓包与内联后端已编入，`Hyperscan` 出现说明可选加速探测成功、缺失则回退 AC 实现，`Rust` 印证 Rust 组件是构建的一部分，`PCRE_JIT` 反映正则 JIT 支持，特性名与对齐会随构建变化。第三、四行是 `-T` 的测试模式标志与加载统计，正常值应让 `rules successfully loaded` 等于处理规模、`rules failed` 与 `rules skipped` 为零，非零时按 04-08 的错误文本定位。第五、六行是 `--dump-config` 扁平化后的两个键，`unix-command.enabled = yes` 说明控制面已开、`filename` 给出 socket 路径，客户端 `-c` 参数必须与之一致。第七行是 `command-list` 的应答：`return` 为 `OK` 表示命令执行成功，`message` 里是可用命令数组，实际清单比示例长得多。第八行是 `iface-stat eth0` 的应答，`message` 里是该接口的包与丢包计数，正常运行时 `pkts` 应随流量增长，`drop` 长期非零要查抓包后端与队列，判读见 08-01。第九行是一条失败应答示例，`return` 为 `NOK` 且 `message` 为 `Unknown command`，说明命令名拼错或本构建未登记该命令，此时应回查 `command-list` 而不是反复重试。需要留意的是，扁平化键名、JSON 字段与特性清单都会随版本变化，示例仅示意结构，务必以本地结果为准；`return` 的 `OK`、`NOK` 与 `message` 字段的构造见 `suricata-main/src/unix-manager.c`。字段见 05-09 ｜ 原理见 06-13 ｜ 模块见 07-12。

### 6. 版本差异

版本基准仍是「上游 main 快照（2026-11 抓取）」，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当版本号。命令行选项与控制面命令是随版本演进较快的一类事实：短选项字符串会增删字符、长选项会新增或改名、某个后端会从内建改为插件、`suricatasc` 的命令族会随 Rust 侧实现扩充，因此本篇清单是「这份快照的事实」而非跨版本永久承诺。

本快照能直接观察到的差异点至少有三处。其一是短选项字符串的具体形态：`suricata-main/src/suricata.c` 里定义的是 `c:TDhi:l:q:d:r:us:S:U:VF:vk:`，其中 `-F`（BPF 过滤文件）、`-k`（校验和 `all` 或 `none`）、`-d`（ipfw divert 端口）、`-U`（单测过滤）各有专门含义，不能按字面猜测；旧资料里若出现不同拼法，必须以本快照 `usage()` 与 `getopt_long` 的短选项串为准。其二是长选项族的规模：`long_opts[]` 里除常见的 `--build-info`、`--dump-config`、`--list-keywords`，还有 `--dump-features`、`--list-app-layer-frames`、`--strict-rule-keywords`、`--include`、`--plugin`、`--capture-plugin`、`--simulate-*`、`--firewall`、`--firewall-rules-exclusive` 等带新版本特征的项，`--list-keywords` 还带 `all`、`json`、`csv` 或单关键字名等可选参数，旧资料常只提前三者。其三是控制面命令的扩张：`suricata-main/src/unix-manager.c` 里除 `shutdown`、`reload-rules`、`dump-counters`，还有 `ruleset-reload-nonblocking`、`ruleset-failed-rules`、`memcap-set`、`dataset-add-json`、`register-tenant` 一类较新的命令，而客户端 `suricata-main/rust/suricatasc/src/unix/commands.rs` 里另有 `pcap-file-continuous`、`pcap-file-number`、`pcap-interrupt`、`add-hostbit` 等，两侧清单并不完全一一对应，跨版本复用脚本前必须逐项核对。

由此得到一条通用版本纪律：任何「选项叫什么」「参数取哪些值」「命令是否登记」的问题，最终都要回到 `suricata-main/src/suricata.c`、`suricata-main/src/unix-manager.c`、`suricata-main/rust/suricatasc/src/unix/` 用 Read、Grep 核实；凡 0.1 节未列出或无法核实的文件一律不写进正文；不确定的选项名、可选项、命令名一律写「需对照实际版本核验」并给出可定位目录。`--build-info` 与 `suricatasc` 的 `command-list` 是本构建最可靠的核对依据。`suricata-update` 独立发版、不是主程序内建子命令；PF_RING 支持状态需对照 `configure.ac` 与 `src/source-*.c` 核验；性能与容量类结论不跨版本照搬，一律标注「需在目标机型实测」，不给绝对值，基准方法见 08-01、调优见 08-02。构建选项见 04-01，yaml 段见 04-02 至 04-04，规则关键字见 04-05、04-06，返回码与排错见 04-08，机制差异见 06-13，模块归属见 07-12。

### 7. 常见误用与调试

第一类是必带参数与组合约束记反。`-T` 必须配合 `-c`，否则校验的不是目标配置；`-s` 是附加规则文件、`-S` 是独占规则文件，混用会把 yaml 规则清单整个丢掉；`-q` 的队列号要与 iptables 或 nftables 的 NFQUEUE 规则一致，`-i` 的网卡名要与实机一致，`-F` 的 BPF 表达式写错会静默过滤掉目标流量。排查顺序固定为：先 `suricata -T -c <配置>` 看加载统计，再 `suricata --dump-config` 看解析后的键，最后 `suricata --build-info` 看后端是否编入，三者对齐再谈收包。加载错误文本判读见 04-08。

第二类是覆盖值与持久化配置脱节。`--set name=value` 只影响本次运行，键名写错常被静默忽略而不报错，改完必须用 `--dump-config` 复核；`--include` 追加的配置文件与 `-c` 主配置的优先级、`--user`、`--group` 降权后的能力边界都要理清，降权后失去 `CAP_NET_RAW`、`CAP_NET_ADMIN` 会导致抓包失败。控制 socket 的 `unix-command` 段与 `--unix-socket` 路径、`suricatasc -c` 的路径三者必须一致，否则表现为「客户端连不上」，而 `shutdown`、`memcap-set`、`dataset-add` 一类命令一旦误发会直接改变运行态，socket 文件权限必须收紧，见 08-05。

第三类是构建期与运行期混淆、以及命令返回码误判。`--build-info` 里没有 NFQ 却按 IPS 部署、没有 Hyperscan 却以为 MPM 一定用它，都会让方案与实机能力对不上；Hyperscan 是可选加速、缺失回退 AC 实现，不得写成必需依赖。`suricatasc` 的应答要先看 `return` 字段，`NOK` 与 `Unknown command` 表示命令未生效，不能只看 `message` 里有内容就认为成功；`reload-rules` 只负责通知引擎重新加载，规则文件需先由独立工具合并落盘，`suricata-update` 不是主程序内建子命令，见 07-11。DPDK 需独占网卡、大页与 EAL 参数，PF_RING 支持状态需对照实际版本核验，不得即插即用地写。

第四类是纪律与能力边界。规则语法兼容 Snort 但有自有扩展，不能宣称百分之百兼容；引擎只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见，不得宣称能读 HTTPS 明文正文；多线程 runmode 不等于加线程必然线性提速，workers、autofp、single 与流亲和、RSS 共同决定扩展性，原理见 06-13；`rust/` 与 Cargo 是构建的一部分，`suricatasc` 本体在 Rust 侧，Suricata 不是纯 C 项目；Suricata 是 IDS / IPS / NSM 引擎，不做 IP 转发、不做路由、不是防火墙。任何吞吐、pps、丢包率、内存占用结论一律标注「需在目标机型实测」，不给绝对值。实例上下文字段见 05-09，runmode 机制见 06-13，控制面模块见 07-12，返回码与排错速查见 04-08，常见误用与调试的完整案例见 08-04。

| unknown rule keyword | 未知关键字 | detect-parse.c | 拼写或版本不支持 |
| invalid formatting or malformed option | 选项格式错 | detect-parse.c | 缺参数或多分号 |
| unexpected option to keyword | 关键字不该带此选项 | detect-parse.c | 参数写多余了 |
| keyword is deprecated | 关键字已弃用 | detect-parse.c | 按替代项迁移 |
| 先用 content 关键字 | 修饰符缺少依附 | detect-parse.c | 相对关键字前补 content |
| Unknown command | 控制面命令未登记 | unix-manager.c | 回查 command-list |
| return 为 OK 或 NOK | RPC 执行结果 | unix-manager.c | 先看 return 再读 message |

按 SPEC 第 6 节约定，两张表单元格内凡是出现「或」语义的竖线都写作转义的 `\|`；本表取值列以斜杠或逗号代替竖线，正是出于这个原因。图 04-08-01 与两张表合起来构成本篇索引：先按证据类型定位文本，再在 `suricata-main/src/util-debug.h`、`suricata.c`、`detect-engine-loader.c`、`detect-parse.c` 里核对格式串，最后用 `suricata -T`、`--dump-config`、`suricatasc` 复现并验证，这条三步法与 04-05 至 04-07 一致。需要提醒的是，日志级别前缀、统计行文与 EVE 字段集合会随版本变化，格式串里的占位符在本地输出里会被具体值替换，务必以本地结果为准；EVE 事件类型清单见 04-04 与 `suricata-main/src/output-json*.c`，具体字段需对照实际版本核验。

### 3. 逐项详解

**退出码 EXIT_SUCCESS / EXIT_FAILURE**：`suricata-main/src/suricata.c` 里以 `exit(EXIT_FAILURE)` 结束初始化或运行期的致命失败，正常结束用 `EXIT_SUCCESS`。对运维最实用的一条是：进程退出码非零时，根因几乎总在 `suricata.log` 的**第一条** `Error` 级别消息里，而不是最后一条；因为后续模块常因前置失败连锁报错。常见触发点有配置文件打不开、yaml 缩进错、规则文件路径不存在、网卡或队列不可用、日志目录不可写。判读时应把退出码、`suricata.log` 首条错误、`-T` 的统计三者对齐，不要只凭退出码猜。字段见 05-09。

**内部返回码 TM_ECODE_OK / TM_ECODE_FAILED**：这是 `suricata-main/src/suricata.c` 里各初始化阶段函数的返回值，源码注释明确写「成功返回 `TM_ECODE_OK`、失败返回 `TM_ECODE_FAILED`」。它比进程退出码更细：某个阶段失败会一路向上传递，最终变成 `EXIT_FAILURE`。它通常不直接暴露给用户，但在阅读日志与源码定位时很有用——看到某阶段失败，就该到 `suricata-main/src/` 对应模块查该阶段的错误文本。阶段划分与线程启动见 06-13，字段见 05-09。

**日志级别体系**：`suricata-main/src/util-debug.h` 的 `SCLogLevel` 枚举依次定义 `SC_LOG_ERROR`、`SC_LOG_WARNING`、`SC_LOG_NOTICE`、`SC_LOG_INFO`、`SC_LOG_PERF`、`SC_LOG_CONFIG`、`SC_LOG_DEBUG`，并以 `SC_LOG_DEF_LOG_LEVEL` 把默认级别设为 `SC_LOG_INFO`；`SCLogError`、`SCLogWarning`、`SCLogInfo`、`SCLogConfig`、`SCLogPerf` 等宏把消息打到对应级别。日志行前缀如 `<Error>`、`<Warning>`、`<Notice>`、`<Info>` 一类，是快速判读严重度的抓手。运行时日志级别与输出目标由 `suricata.yaml.in` 的 `logging` 段控制，具体键名与默认值需对照实际版本核验，配置段见 04-02。误配后果是把级别调得过低，关键错误被淹没；或生产长期开 `Debug` 级别放大日志量，性能代价不能用作基准。

**测试模式与加载统计**：`suricata -T -c <配置>` 进入测试模式，`suricata-main/src/suricata.c` 打印 `Running suricata under test mode`；`suricata-main/src/detect-engine-loader.c` 在加载收尾打印「`N rule files processed. N rules successfully loaded, N rules failed, N rules skipped`」。四个计数各有含义：`processed` 是处理的文件数，`successfully loaded` 是成功规则数，`failed` 是解析或校验失败数，`skipped` 是因 `requires` 声明的能力不满足而被跳过数。正常值是前两项符合预期、后两项为零；`failed` 非零就按后面的错误文本定位到文件与行号，`skipped` 非零要查规则对关键字或版本的要求。`No signatures supplied.` 表示一个规则都没读到，优先查 `rule-files` 与 `default-rule-path`。

**规则加载错误文本**：`suricata-main/src/detect-engine-loader.c` 里已核验的格式串有「`opening rule file %s:`」（打不开文件，多为路径或权限）、「`error parsing signature "%s" from ...`」（带文件名与行号，定位到具体规则）、「`Error adding sig`」（追加规则失败）、「`error expanding template`」（路径模板展开失败）。这些文本通常成对出现：先有 `unknown rule keyword` 一类解析错误，再有加载器的 `error parsing signature` 汇总。正确做法是打开 `suricata.log` 找第一条带行号的错误，按行号回查规则文件，而不是反复重跑 `-T`。规则加载机制见 06-06。

**解析期错误文本**：`suricata-main/src/detect-parse.c` 里已核验的格式串有「`unknown rule keyword '%s'.`」（关键字拼写错或本构建不支持）、「`invalid formatting or malformed option to %s keyword`」（选项缺参数、多分号或括号不配对）、「`unexpected option to %s keyword`」（该关键字不该带这个参数）、「`keyword '%s' is deprecated`」（已弃用、由 `sigmatch_table[].alternative` 指向替代项）、以及「请先使用 `content` 关键字再使用某修饰符」一类依附错误。它们分别对应 04-05 的规则头与 meta、04-06 的选项体：动作、协议、方向写错多落在规则头阶段，`distance`、`within` 缺前置 `content` 则落在选项体阶段。判读要点是把错误里的关键字名拿去 `suricata --list-keywords` 核对拼写，命令见 04-07。

**EVE 事件类型**：`eve.json` 以 `event_type` 区分事件，常见有 `alert`、`drop`、`stats`、`http`、`dns`、`tls`、`flow`、`file`、`anomaly` 等，实际可订阅类型由 `outputs.eve-log.types` 决定，键见 04-04，字段与构造见 `suricata-main/src/output-json*.c`，具体字段集合需对照实际版本核验。排错时最有用的是三处：`alert` 事件的 `alert.signature`、`signature_id`、`action` 用来确认哪条规则命中、是 `allowed` 还是丢弃；`drop` 事件确认内联是否真的丢了包；`stats` 事件的 capture、decoder、detect 类计数用来判断有没有收包、有没有解码、有没有进检测，计数项名称需对照实际版本核验。加密载荷正文不可见，TLS 事件只有握手元数据与证书一类信息，不得宣称能读 HTTPS 明文正文。输出机制见 06-11，字段见 05-08。

**控制面应答状态**：`suricata-main/src/unix-manager.c` 以 `json_object_set_new(server_msg, "return", json_string("OK"))` 一类构造应答，`return` 取 `OK` 或 `NOK`，`message` 承载文本或数据；未知命令回 `Unknown command`，停机回 `Closing Suricata`，重载冲突回 `Reload already in progress`。判读原则是**先看 `return` 再看 `message`**：`NOK` 表示命令未生效，不能因为 `message` 里有内容就以为成功；`OK` 也要结合 `message` 内容确认结果符合预期。命令全集与协议见 04-07，模块见 07-12。

**证据来源清单**：把上述来源按排查顺序收拢，建议固定为：进程退出码 → `suricata.log` 首条 `Error` → `suricata -T` 的加载统计 → `suricata --build-info` 的特性清单 → `suricata --dump-config` 的扁平键 → `eve.json` 的 alert/drop/stats 事件 → `suricatasc dump-counters` 的计数器。任何一步的结论都要能在下一步得到印证，避免只看单一证据就下判断。诊断决策树见 08-03，六个完整故障案例见 08-04，基准方法见 08-01。字段见 05-09 ｜ 原理见 06-06 ｜ 模块见 07-04。

### 4. 典型示例

下面给一组可复现的排错闭环：故意在规则里写一个不存在的选项，用 `-T` 复现加载失败，取回日志中的错误文本，再用 `--dump-config` 与 `suricatasc` 复核配置与运行态。完整命令行见 04-07，规则写法见 04-05、04-06，日志级别见表 2。

```bash
cat > /tmp/bad-04-08.rules <<'RULE'
alert tcp any any -> any any (msg:"TEST bad keyword"; nonexistent_option:1; sid:1000003; rev:1;)
RULE

suricata -T -c /etc/suricata/suricata.yaml -S /tmp/bad-04-08.rules 2>&1 | tee /tmp/04-08-check.log
echo "exit status: ${PIPESTATUS[0]}"

grep -n -E 'Error|error parsing|unknown rule keyword|rules failed' /tmp/04-08-check.log

suricata --dump-config -c /etc/suricata/suricata.yaml | grep -E 'default-rule-path|rule-files|logging'
```

对上述命令组合的结果，以下是示例输出，具体格式需对照实际版本核验，版本字符串行按版本纪律不抄录具体版本号。

```text
<Notice> - Running suricata under test mode
<Error> - unknown rule keyword 'nonexistent_option'.
<Error> - error parsing signature "alert tcp any any -> any any (msg:\"TEST bad keyword\"; nonexistent_option:1; sid:1000003; rev:1;)" from file /tmp/bad-04-08.rules at line 1
<Info> - 1 rule files processed. 0 rules successfully loaded, 1 rules failed, 0 rules skipped
exit status: 1
default-rule-path = /var/lib/suricata/rules
rule-files.0 = suricata.rules
logging.default-log-level = Notice
```

逐行判读这段输出。第一行 `<Notice> - Running suricata under test mode` 是 `-T` 进入测试模式的标志，级别 `Notice` 说明这只是状态提示、不是错误，级别体系见 `suricata-main/src/util-debug.h`。第二行 `<Error> - unknown rule keyword 'nonexistent_option'.` 是 `suricata-main/src/detect-parse.c` 打印的解析错误，把根因直接点名为「未知关键字」，这正是跨引擎复用规则或拼写错时最典型的一条；遇到它应先拿关键字名去 `suricata --list-keywords` 核对，而不是改规则里的其他部分。第三行是 `suricata-main/src/detect-engine-loader.c` 的汇总错误，`error parsing signature` 带上完整规则文本、文件名与行号，用来精确定位到 `/tmp/bad-04-08.rules` 第 1 行；注意它带的是文件名与行号，不是关键字名，两者要结合看。第四行是加载统计：`0 rules successfully loaded`、`1 rules failed` 与 `0 rules skipped`，正常值应让成功数等于有效规则数、`failed` 与 `skipped` 为零，这里 `failed` 为一说明整条规则被拒，引擎不会因为一条坏规则就带病启动。第五行 `exit status: 1` 是 shell 拿到的非零退出码，对应 `EXIT_FAILURE`，说明 `-T` 以失败告终，上线门禁应据此拦截。第六到八行是 `--dump-config` 的扁平键：`default-rule-path`、`rule-files.0` 说明规则从哪里加载，`logging.default-log-level` 说明当前日志级别，排错时可确认「日志级别没把 Error 过滤掉」以及「规则清单是否指向预期文件」。需要留意的是，级别前缀、格式串、扁平化键名与统计行文都会随版本变化，示例仅示意结构，务必以本地结果为准；`logging` 段的确切键名需对照实际版本核验。字段见 05-09 ｜ 原理见 06-06 ｜ 模块见 07-04。

### 6. 版本差异

版本基准仍是「上游 main 快照（2026-11 抓取）」，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当版本号。返回码、日志级别与错误文本是相对稳定的一类事实，但「稳定」不等于「跨版本一字不差」：日志级别会增删、级别前缀会调整、加载统计的措辞会补充字段、EVE 事件类型会新增、`suricatasc` 的 `return` 取值可能扩展，因此本篇清单是「这份快照的事实」而非跨版本永久承诺。

本快照能直接观察到的差异点至少有三处。其一是日志级别的完整集合：`suricata-main/src/util-debug.h` 里除 `SC_LOG_ERROR`、`SC_LOG_WARNING`、`SC_LOG_INFO`、`SC_LOG_DEBUG`，还有 `SC_LOG_NOTICE`、`SC_LOG_PERF`、`SC_LOG_CONFIG` 三项，默认级别由 `SC_LOG_DEF_LOG_LEVEL` 定为 `SC_LOG_INFO`；旧资料常只提前四者，按四级别去读本快照日志会漏掉 `Notice` 与 `Config` 类消息，`-T` 的测试模式提示正是 `Notice`。其二是加载统计的字段：`suricata-main/src/detect-engine-loader.c` 的收尾文本同时报告 `rule files processed`、`rules successfully loaded`、`rules failed`、`rules skipped` 四个计数，`skipped` 与 `requires` 关键字的能力声明相呼应，旧资料可能只报成功与失败两项，升级排错脚本时要按四计数解析。其三是关键字弃用机制：`suricata-main/src/detect-parse.c` 里可见 `keyword '%s' is deprecated` 一类告警、`suricata-main/src/detect-engine-register.c` 里有 `sigmatch_table[].alternative` 指向替代项，说明「加载成功但打了弃用告警」是一种独立状态，既不计入 `rules failed` 也不该长期保留，跨版本迁移规则集时要专门清理。

由此得到一条通用版本纪律：任何「级别叫什么」「错误文本怎么写」「统计有几项」「事件类型有哪些」的问题，最终都要回到 `suricata-main/src/util-debug.h`、`suricata-main/src/suricata.c`、`suricata-main/src/detect-engine-loader.c`、`suricata-main/src/detect-parse.c`、`suricata-main/src/output-json*.c` 用 Read、Grep 核实；凡 0.1 节未列出或无法核实的文件一律不写进正文；不确定的级别名、格式串、字段名一律写「需对照实际版本核验」并给出可定位目录。EVE 字段集合与事件类型清单尤其容易漂移，消费端 schema 需对照实际版本核验；规则语法兼容 Snort 但有自有扩展，不能宣称百分之百兼容；性能与容量类结论不跨版本照搬，一律标注「需在目标机型实测」，不给绝对值，基准方法见 08-01、调优见 08-02。构建选项见 04-01，yaml 段见 04-02 至 04-04，规则关键字见 04-05、04-06，命令行与 RPC 见 04-07，机制差异见 06-06、06-11，模块归属见 07-04、07-07，诊断决策树见 08-03，故障案例库见 08-04。

### 7. 常见误用与调试

第一类是只读最后一条错误、不看首条。进程以 `EXIT_FAILURE` 退出时，`suricata.log` 里常有一连串连锁报错，根因几乎总在**第一条** `Error` 级别消息：配置打不开会让后续模块全部失败，规则文件路径错会让加载器报 `opening rule file`。正确做法是按「退出码 → 首条 Error → `-T` 统计」的顺序收敛，再按错误文本里的文件名与行号回查规则，而不是反复重跑命令或盲目改 yaml。日志级别前缀与级别体系见 `suricata-main/src/util-debug.h`，配置段见 04-02。

第二类是三类同名对象与订阅遗漏混淆。`stats` 既是顶层全局统计段、又是 `outputs` 下的 stats 输出模块、还是 `eve-log.types` 里的 stats 子项，改错层次是高频误操作；`logging` 段是引擎自身运行日志，与 `outputs` 段的告警事件日志完全不是一回事。线上「缺 dns、tls、file 事件」时，第一嫌疑应是 `eve-log.types` 没订阅相应类型，而不是上游没产出；判读原则是看 `--dump-config` 打印的扁平键名前缀，按前缀定位层次最可靠。EVE 事件类型与输出参数见 04-04，输出机制见 06-11。

第三类是把能力边界写成排错结论。「IPS 写了 drop 却不丢包」先要确认是否在内联模式、队列号是否与 NFQUEUE 规则一致、`stream.inline` 与 fail-open 是否配好，而不是断定规则没写对；Suricata 不做 IP 转发、不做路由、不是防火墙，丢包由内核或桥接 verdict 执行，原理见 06-12。「在线跑通却无告警」要按网卡、权限、`vars` 的 `HOME_NET` 方向、`eve.json` 的 stats 事件逐层排查，不能因看不到 HTTPS 明文正文就怀疑规则，TLS 等加密载荷正文对引擎不可见，不得宣称能读 HTTPS 明文正文。`unknown rule keyword` 则常源于照搬 Snort 规则，规则语法兼容但有自有扩展，不能宣称百分之百兼容。

第四类是纪律与误判。`suricatasc` 应答要先看 `return` 的 `OK` 或 `NOK`，`NOK` 与 `Unknown command` 表示命令未生效；`reload-rules` 只通知引擎重载，新规则须先由独立工具合并落盘，`suricata-update` 不是主程序内建子命令，见 07-11；`--set` 覆盖值键名错常被静默忽略，改完必须 `--dump-config` 复核；`-T` 与调试构建的性能数据不能当生产基准；Hyperscan 是可选加速、缺失回退 AC 实现，不得写成必需依赖。任何吞吐、pps、丢包率、内存占用结论一律标注「需在目标机型实测」，不给绝对值。实例与日志上下文字段见 05-09，加载与输出机制见 06-06、06-11，加载器与检测模块归属见 07-04、07-07，命令行与 RPC 见 04-07，诊断决策树见 08-03，六个完整故障案例见 08-04。
