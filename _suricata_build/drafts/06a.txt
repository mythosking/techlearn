# Suricata 技术资料 · 06 技术原理（分片 A）
## 06-01 包处理流水线总览：从抓包到事件落盘

### 1. 背景与动机

理解 Suricata，最容易犯的错误是把它想象成「抓到一个包就立刻拿去和规则逐条比对」的单步程序。真实情况要复杂得多：一个以太网帧从网卡驱动进入用户态，到最终变成 `eve.json` 里的一行 JSON，中间要跨越抓包线程、包池与队列、解码器、流表、TCP 流重组、应用层协议解析器、检测引擎、日志模块等多个环节，还要在 C 与 Rust 两套运行时之间来回切换。这些环节由不同的 `TmModule` 承载，由 runmode 决定它们被串成怎样的线程与队列拓扑，任何一个环节配置不当或资源耗尽，都会让「没有告警」这一现象出现，而根因可能完全不在规则本身。正因如此，本册（06）被定为全集的机制与调用链唯一权威源，而本篇作为开篇，先给出一张可据以分段定位的全景地图。

必须先厘清定位。Suricata 是 IDS / IPS / NSM 引擎，不是防火墙，不做 IP 转发，也不做路由。在旁路 IDS 模式下它只对镜像或分光得到的副本做检测并告警；在内联 IPS 模式下它依靠 NFQUEUE 或 AF_PACKET 桥接的 verdict 决定「放行还是丢弃」，真正执行放行动作的是内核或桥接对端，而不是 Suricata 自己去转发报文。另一个不可回避的边界是可见性：引擎只对自身解码并重组到的流量做检测，TLS 等加密载荷的明文正文不可见，能拿到的是握手元数据、证书、SNI、JA3/JA4 一类指纹（相关 Rust 侧实现见 `rust/src/ja4.rs`，具体字段需对照实际版本核验），不能宣称能读到 HTTPS 明文。

从工程价值看，建立流水线视图有两个直接收益。其一是排障：当 `eve.json` 里迟迟不出现 `alert` 事件时，有经验的工程师不会立刻去改规则，而是按「收包计数是否增长 → 解码计数是否正常 → 流是否建立 → 应用协议是否识别 → 检测引擎是否命中 → 输出模块是否落盘」逐段收敛，这比盲目调参高效得多。其二是性能：只有知道包在哪些队列间搬运、在哪里发生锁竞争与内存分配，才能理解为什么简单增加线程数并不必然带来线性提速，以及为什么 RSS、fanout 与流亲和必须一起考虑（原理见 06-13）。本套资料的版本基准统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验；本篇所有函数名与路径均以此快照下 `upstream_src/suricata/suricata-main/` 内的真实文件为锚点。

### 2. 核心概念

先把贯穿全册的术语固定下来。`Packet` 是一次收包与解码的载体，承载原始帧、各层指针、时间戳、告警数组以及指向所属 `Flow` 的引用，它由包池统一分配与回收（字段见 05-02）。`Flow` 是以五元组为核心、附带 VLAN、livedev、递归层级等追踪维度聚合出的双向会话，是流表哈希、TCP 会话状态与应用层事务的挂接点（字段见 05-03）。`TmModule` 是线程模块抽象，每个模块提供 `ThreadInit`、`Func`、`ThreadDeinit` 等钩子；`TmSlotSetFuncAppend` 把若干模块按顺序挂到同一个 `ThreadVars` 上，形成所谓的 slot 链（字段见 05-07）。队列 handler（简称 `Tmqh`）负责在 slot 之间搬运 `Packet`，packetpool 是最常用的一种 handler。

由此可以把运行期的数据通路切成八个阶段：收包（`src/source-*.c`）→ 取包与入队（`src/tmqh-packetpool.c`）→ 解码（`src/decode.c` 与 `src/decode-*.c`）→ 流查找与 TCP 重组（`src/flow-worker.c`、`src/stream-tcp.c`）→ 应用层解析（`src/app-layer-parser.c`）→ 检测（`src/detect.c`）→ 日志与 EVE 输出（`src/output.c`、`src/output-json.c`）→ `Packet` 回池。这些阶段在 `workers` 模式下可能全部落在同一个线程内顺序执行，在 `autofp` 模式下则被拆到收包线程与多个检测线程，通过队列解耦；`single` 模式主要用于调试。三种 runmode 的取舍见 06-13，模块职责见 07-06、07-07。

还需要区分两类「断点」。丢弃点是设计上主动放弃报文的位置，例如解码校验和失败、隧道递归超限、IP 分片无法重组、IPS 模式下 verdict 为 drop、加密流超过重组深度后不再供给应用层。失败点是资源或配置异常，例如包池耗尽（`max-pending-packets` 相关，键名需对照实际版本核验）、流表或重组 memcap 触顶、队列没有配对的 reader 与 writer、输出目录不可写。二者在 `stats.log` 与 `suricata.log` 中的表现类似，都体现为「计数不增」或「事件缺失」，但处理方向完全不同。

最后强调去重约定：本篇只讲机制与调用链，结构体逐字段定义一律到 05，命令行与配置参数全集一律到 04，模块能力清单一律到 07。需要查字段时写「（字段见 05-xx）」，需要查参数时写「（参数见 04-xx）」，需要按目录索引能力时写「（模块见 07-xx）」，三者在本篇与后续各篇统一采用「字段见 05-xx ｜ 参数见 04-xx ｜ 模块见 07-xx」这样的交叉引用写法。

### 3. 关键数据结构与源码位置

本节只点名结构与真实路径，不重列任何字段。06 全册禁止出现完整结构体字段表，逐字段定义、类型、读写时机与生命周期由 05 全册统一承担。

- `Packet`、`PacketAlert`、`PacketEngineEvents`、`DecodeThreadVars`、`struct PacketQueue_`：定义与声明集中在 `src/decode.h` 与 `src/decode.c`，`Packet` 内还提供 `ReleasePacket`、`BypassPacketsFlow` 两个函数指针钩子，以及隧道场景指向根包的 `root` 指针（字段见 05-02）。`src/tmqh-packetpool.c` 在初始化时把 `p->ReleasePacket` 设为 `PacketPoolReturnPacket`，这正是流水线末端把包还回池子的钩子。
- `Flow`、`FlowBucket`、`FlowKey`、`FlowLookupStruct`：声明在 `src/flow.h`，哈希与查找实现在 `src/flow-hash.c`，流表全局数组 `flow_hash` 即定义于该文件（字段见 05-03）。
- `AppLayerParserState`、`AppLayerResult`、`AppLayerParserThreadCtx`、`AppLayerGetTxIterTuple`：声明在 `src/app-layer-parser.h`，实现主体在 `src/app-layer-parser.c`；Rust 侧的 `RustParser` 与 `ParseFn` 在 `rust/src/applayer.rs`（字段见 05-04）。
- `Signature`、`SigMatch`、`DetectEngineCtx`、`SigGroupHead`：定义与编译入口在 `src/detect.h`、`src/detect-engine*.c`、`src/detect-parse.c`（字段见 05-05、05-06），本篇只把它们当作检测阶段的输入。
- `ThreadVars`、`TmModule`、`PacketQueue`：`src/threadvars.h`、`src/tm-modules.h`、`src/tm-threads.h`、`src/tm-queues.h` 与 `src/tm-threads.c`；`tmm_modules[TMM_FLOWWORKER]`、`tmm_modules[TMM_FLOWMANAGER]` 这类注册表项是 runmode 拼装 slot 链的素材（字段见 05-07）。
- `LogFileCtx`、`OutputModule`、`SCInstance`、`ConfNode`：`src/output.h`、`src/output.c`、`src/suricata.c`（其中全局实例为 `SCInstance suricata`）、`src/conf.h`、`src/conf.c`（字段见 05-08、05-09）。

一个值得记住的细节是：`src/main.c` 才包含 `int main(int argc, char **argv)`，而 `src/suricata.c` 提供的是 `SuricataPreInit`、`SuricataInit`、`SuricataPostInit`、`SuricataMainLoop`、`SuricataShutdown`、`GlobalsDestroy` 这一组可被库化调用的生命周期函数；把入口误记在 `suricata.c` 是阅读源码时常见的偏差。配置树由 `SCConfInit`、`SCLoadYamlConfig` 建立，运行期通过 `SCConfGet`、`SCConfGetBool`、`SCConfGetInt` 系列读取，字段名与签名需对照实际版本核验。交叉引用：字段见 05-02、05-03、05-07、05-09 ｜ 参数见 04-02、04-07 ｜ 模块见 07-01、07-02、07-04、07-07。

### 4. 关键流程与调用链

启动链可以从 `src/main.c` 的 `main()` 逐行读出：依次调用 `SuricataPreInit(argv[0])`、`SCParseCommandLine(argc, argv)`、`SCFinalizeRunMode(argc)`、`SCStartInternalRunMode(argc, argv)`、`SCLoadYamlConfig()`、`SCEnableDefaultSignalHandlers()`、`SuricataInit()`、`SuricataPostInit()`、`SuricataMainLoop()`，退出前调用 `SuricataShutdown()` 与 `GlobalsDestroy()`。`SuricataPreInit` 内部经 `SCInstanceInit` 与 `InitGlobal` 完成全局初始化，而 `InitGlobal` 中调用 `RunModeRegisterRunModes()`，把 pcap、pcap-file、NFQ、IPFW、ERF、AF_PACKET、AF_XDP、Netmap、NFLOG、unix-socket、WinDivert、DPDK 等运行模式逐一注册进 `runmodes[]` 表。`SCParseCommandLine` 负责把 `-c`、`-i`、`-r`、`-q`、`--list-runmodes`、`--build-info`、`--dump-config` 等选项解析进 `SCInstance`（参数见 04-07）。

真正把静态模块表变成运行线程的是 `RunModeDispatch(int runmode, const char *custom_mode, const char *capture_plugin_name, const char *capture_plugin_args)`，定义在 `src/runmodes.c`，由 `SuricataInit` 末尾调用。它先用 `RunModeGetConfOrDefault` 与 `RunModeGetCustomMode` 选出目标 `RunMode`，再执行 `mode->RunModeFunc()`；这个回调由 `src/runmode-af-packet.c` 的 `RunModeIdsAFPRegister`、`RunModeIdsAFPAutoFp`、`RunModeIdsAFPSingle`，或 `src/runmode-dpdk.c` 的 `RunModeDpdkRegister` 等注册。这些 runmode 函数内部用 `TmThreadCreatePacketHandler` 建线程，用 `TmModuleGetByName` 取模块，用 `TmSlotSetFuncAppend` 把 `ReceiveAFP`→`DecodeAFP`→`FlowWorker`→`Detect`→`OutputLoggerLog` 之类模块依次挂成 slot 链，最后 `TmThreadSpawn` 启动、`TmThreadWaitOnThreadInit` 等待就绪。`RunModeDispatch` 收尾还会调用 `TmValidateQueueState()` 校验每个队列至少有一读一写，并拉起 `FlowManagerThreadSpawn`、`FlowRecyclerThreadSpawn`、`StatsSpawnThreads`、`LogMaintenanceThreadSpawn` 等管理线程，最后 `TmThreadsSealThreads()` 封板。整条包处理主线与事件落点见图 06-01-01。

稳态下单个 `Packet` 的旅程如下。收包模块的 `TmModuleReceiveAFPRegister` / `TmModuleReceivePcapRegister` / `TmModuleReceiveDPDKRegister` 把原始帧写入由 `PacketPoolGetPacket` 取得的 `Packet`；紧接着后端解码函数（`DecodeAFP`、`DecodePcap`、`DecodeDPDK`，均为真实符号）根据链路类型调用 `DecodeEthernet`、`DecodeSll`、`DecodeRaw`、`DecodeIPV4`、`DecodeIPV6`、`DecodeTCP`、`DecodeUDP` 等分派函数（声明见 `src/decode.h`），隧道与 VLAN 由 `decode.c` 的 `DecodeTunnel` 递归处理，解码完成后 `PacketDecodeFinalize` 收尾并做 `DecodeRegisterPerfCounters` 登记的计数。随后 `FlowWorker` 调用 `FlowHandlePacket` 完成流查找与绑定，`StreamTcp` 处理握手状态、ACK/SACK 与重组，重组出的连续流缓冲经 `StreamTcpReassembleAppLayer` 供给 `AppLayerParserParse`。检测阶段入口是 `Detect(ThreadVars *tv, Packet *p, void *data)`，内部走 `DetectRun`、`DetectRunTx`、`SigMatchSignatures` 完成匹配与告警排队。最后由 `OutputLoggerLog` 驱动各 `OutputModule` 把 `alert`、`flow`、`http`、`dns`、`tls` 等事件写成 EVE JSON（原理见 06-11），并通过 `p->ReleasePacket` 把 `Packet` 交还包池，形成图 06-01-01 中虚线所示的回池复用闭环。

本节只给最小必要实例，并显式指向权威源：`suricata.yaml` 全段、全部命令行与 `suricatasc` 命令、返回码见 04 全册（参数见 04-02、04-07、04-08），此处不重列参数全集。下面先给一条可用于对照 `src/main.c` 的启动调用链摘录，函数名与顺序均按真实源码书写，不构成完整实现。

下面是一组按「前置检查 → 执行 → 验证输出 → 清理」组织的完整闭环命令，适合在旁路 IDS 上验证流水线是否贯通。

```bash
# 前置检查：先做配置与规则自检，避免把加载失败误判为无告警
suricata -T -c /etc/suricata/suricata.yaml

# 执行：以 AF_PACKET 旁路模式在 eth0 上常驻运行
suricata -c /etc/suricata/suricata.yaml -i eth0 -D

# 验证输出：查看事件文件与解码统计计数
tail -n 3 /var/log/suricata/eve.json
grep -n "decoder.pkts" /var/log/suricata/stats.log | tail -n 2

# 清理：经控制面正常关闭，suricatasc 语法需对照实际版本核验
suricatasc -c shutdown
```

典型输出如下（示例输出，具体格式需对照实际版本核验）。

```text
# 示例输出，具体格式需对照实际版本核验
<Notice> - Configuration provided was successfully loaded. Exiting.
decoder.pkts                              | Total                     | 184233
decoder.bytes                             | Total                     | 132957120
detect.alert                              | Total                     | 17
{"event_type":"alert","src_ip":"192.0.2.15","dest_ip":"198.51.100.7","alert":{"signature":"ET TEST","signature_id":2100498}}
```

逐行判读如下。第一行是 `suricata -T` 的成功回显，关键词是 `successfully loaded`，它只证明配置与规则能被解析，不代表在线抓包已启动；若这里出现 `Error` 或规则解析失败文本，应回到 04-08 的排错速查。第二、三行来自 `stats.log`，`decoder.pkts` 是解码器成功处理的包数，`decoder.bytes` 是对应字节数：只要在线运行时这两个计数持续增长，就说明收包与解码两段是通的，正常值应随流量单调上升；若 `decoder.pkts` 长时间为零，而 `capture` 侧计数也不动，优先怀疑网卡名、权限或 AF_PACKET 未起来，若 `capture` 增长而 `decoder.pkts` 不动，则怀疑解码异常或包池耗尽，这两类异常特征必须区分开。第四行 `detect.alert` 是累计告警数，正常值可以很低甚至为零，只有在确认有命中规则的可测流量时才应上升；它为零而 `decoder.pkts` 正常增长，说明问题落在流建立、协议识别、规则加载或输出开关上，而不是抓包。第五行是 `eve.json` 的一条 `alert` 事件，`event_type` 标明事件类型、`src_ip` 与 `dest_ip` 标明双向地址、`alert.signature` 与 `signature_id` 标明命中规则；若该文件始终只有 `flow`、`stats` 而没有 `alert`，应检查规则是否加载、`HOME_NET` 是否覆盖测试地址，以及 `outputs` 里对应事件类型是否开启（参数见 04-02、04-04），字段名需对照实际版本核验。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是把「加线程」当成必然线性提速。runmode 从 `autofp` 切到 `workers`、或给 AF_PACKET 增加 threads 后，吞吐是否改善取决于 RSS 队列、fanout 的对称哈希、流亲和与绑核是否配套；队列锁竞争、跨 NUMA 访问与包池争用都可能让扩展曲线提前饱和，任何吞吐、pps、丢包率、内存占用结论一律标注「需在目标机型实测」，不给绝对值（原理见 06-13，调优见 08-02）。第二个陷阱是可见性误判：TLS 加密载荷的明文正文不可见，能用于检测与日志的是握手元数据、证书、SNI、JA3/JA4 等，不能把「明明有 HTTPS 请求却没匹配到 content 规则」当成引擎缺陷（原理见 06-12）。第三个陷阱是顺序颠倒：检测发生在解码、流绑定、重组与应用解析之后，把带 `http.uri`、`file.data`、`tls.sni` 之类 sticky buffer 的规则直接套到尚未解析的原始帧上，本身就是对流水线的误解（原理见 06-08）。

配置层面有几处高频问题。`RunModeDispatch` 末尾的 `TmValidateQueueState()` 会检查每个队列至少有一读一写，自定义 runmode 或队列 handler 配对写错时会直接报错退出，这是「启动即失败」的典型根因之一。包池、流表、重组 memcap 三类内存上限需要一起规划，只调大其中一个往往只是把瓶颈搬家；`max-pending-packets` 一类键名需对照 `suricata.yaml.in` 与 `src/` 实际版本核验。规则侧要注意 Suricata 语法兼容 Snort 但有自有扩展，不能宣称 100% 兼容；Hyperscan 只是可选 MPM 加速，缺失时回退 AC 等其他实现，不是必需依赖；`suricata-update` 是分仓独立工具，不参与 `src/` 主程序编译，别把它写成主程序内建子命令。IPS 场景还要区分 IDS 旁路（只告警）与内联（能 drop），且 `stream.inline`、fail-open 与 NFQUEUE 队列号必须一致，drop 不生效时按 08-04 的案例逐项排查。

最佳实践是建立「分段计数」习惯：上线前用 `suricata --build-info` 确认构建特性、`suricata --dump-config` 确认生效配置、`suricata -T` 确认规则可加载；运行中看 `stats.log` 的 `capture`、`decoder`、`flow`、`detect`、`tcp.reassembly_memuse` 等分段计数（计数项名称需对照实际版本核验），配合 `suricatasc dump-counters` 做即时快照。排障时严格按图 06-01-01 的顺序从前向后收敛，先证明「包进来了」，再证明「流建立了」，最后才讨论「规则为什么不命中」。日志轮转、EVE 落盘目录权限与 `etc/suricata.logrotate.in` 也要在上线清单里确认，避免检测全通却因磁盘写满而丢事件。
再补一条把图 06-01-01 用在排障上的经验规则。当 `stats.log` 显示 `capture` 计数增长而 `decoder.pkts` 停滞时，断点在收包与解码之间，优先查包池是否耗尽、解码器是否因校验和或隧道递归异常提前返回；当 `decoder.pkts` 正常而 `flow` 计数不涨时，断点在 `FlowWorker` 与流表，优先查 `flow.memcap` 与 VLAN tracking 掩码；当流正常但 `detect.alert` 为零时，断点在规则加载、协议识别或输出开关，而不是收包。把每一个「计数不动」精确映射到流水线的一段，是 06 全册后续各篇的共同方法：06-02 细化收包、06-03 细化解码、06-04 细化流与重组、06-05 细化应用解析、06-08 细化检测求值、06-11 细化输出。也正因如此，本篇不展开任何一段的内部实现，只负责把「在哪一段、由哪个函数接手、失败会表现为哪个计数」这张地图交到读者手里；需要逐字段定义时回到 05，需要参数全集时回到 04，需要按目录找模块时回到 07。


### 7. 小结与延伸阅读

本篇给出一条主线、两个权威源、三类边界。一条主线是「收包 → 入队 → 解码 → 流与重组 → 应用解析 → 检测 → 输出 → 回池」，它在 `src/main.c` 的生命周期函数与 `src/runmodes.c` 的 `RunModeDispatch` 中被装配，在 `TmSlotSetFuncAppend` 拼出的 slot 链上被逐段执行，最终由 `Packet->ReleasePacket` 收束成闭环。两个权威源是：结构体逐字段看 05，配置与命令参数看 04；本篇及 06 全册只负责机制与调用链，不越界重列字段表或参数全集。三类边界是：Suricata 不做转发、不是防火墙；加密载荷明文不可见；规则语法兼容 Snort 但非完全一致。把这三点记住，能避免大半望文生义的误判。

延伸阅读按流水线继续向后推进：抓包后端差异见 06-02，解码与隧道、VLAN、分片见 06-03，流管理与 TCP 重组见 06-04，应用层解析框架与 Rust parser 接入见 06-05，规则加载与签名分组见 06-06，多模式匹配与预过滤见 06-07，检测求值顺序见 06-08，EVE 输出与事件聚合见 06-11，IPS verdict 见 06-12，runmode 与负载均衡见 06-13。按目录查模块能力可跳到 07-01（decode）、07-02（flow）、07-04（detect）、07-06（source-*）、07-07（output 与 log-*）、07-08（stream-tcp）；按字段查结构可跳到 05-02、05-03、05-07；按参数查命令与配置可跳到 04-02、04-07、04-08。统一交叉引用写法：字段见 05-02、05-03、05-07 ｜ 参数见 04-02、04-07 ｜ 原理见 06-02 至 06-13 ｜ 模块见 07-01、07-02、07-04、07-06、07-07、07-08。版本基准始终为「上游 main 快照（2026-11 抓取）」，未核实的具体字段名、函数签名与配置键名均已标注「需对照实际版本核验」。

## 06-02 抓包后端原理：AF_PACKET、DPDK、PF_RING、Netmap 与 pcap

### 1. 背景与动机

抓包后端位于整条流水线的最前端，它决定三件根本性的事：引擎能不能拿到报文、以多高的速率拿到、以及为此要付出什么环境代价。与纯软件分析器不同，Suricata 是常驻的 IDS / IPS / NSM 进程，报文来源可能是交换机 SPAN 口送来的镜像副本、TAP 分光、虚拟化后端、NFQUEUE 内联队列，也可能只是一个离线 pcap 文件。不同来源对应完全不同的内核接口与驱动模型，选错后端轻则跑不起来，重则在生产流量下大面积丢包却不自知。理解后端差异，是把「引擎装上了」推进到「引擎可信地工作」的第一步。

必须先立住能力边界。Suricata 不是防火墙，不做 IP 转发，也不做路由；旁路 IDS 只收副本、只告警不丢弃，内联 IPS 的阻断依靠 NFQUEUE 或 AF_PACKET 桥接的 verdict，由内核或桥接对端决定是否放行。各后端的环境要求差异极大：DPDK 需要独占网卡、大页内存与 EAL 参数，不能与普通网卡即插即用；Netmap、AF_XDP 有内核版本与驱动要求；pcap 多用于离线回放或低速率在线；PF_RING 在当前 main 快照是否仍为受支持后端、对应源文件与启用方式，需对照 `configure.ac` 与 `src/source-*.c` 实际版本核验，绝不能凭印象补出一个 `source-pfring.c`。本套资料版本基准统一为「上游 main 快照（2026-11 抓取）」。

一个值得单独点明的事实是：本次核验的 `src/source-*.c` 真实清单包含 `source-af-packet.c`、`source-af-xdp.c`、`source-dpdk.c`、`source-erf-dag.c`、`source-erf-file.c`、`source-ipfw.c`、`source-lib.c`、`source-netmap.c`、`source-nflog.c`、`source-nfq.c`、`source-pcap.c`、`source-pcap-file.c`、`source-pcap-file-directory-helper.c`、`source-pcap-file-helper.c`、`source-windivert.c`，而 `src/runmodes.c` 的 `RunModeRegisterRunModes` 注册了 pcap、pcap-file、NFQ、IPFW、ERF、AF_PACKET、AF_XDP、Netmap、NFLOG、unix-socket、WinDivert、DPDK 等模式。两处清单里都没有 PF_RING 专用注册项，这正是必须写「需对照实际版本核验」而不是想当然的原因。本篇把后端抽象成「注册 → 装配 → 收包 → 解码」四步，逐一落到真实符号上。

### 2. 核心概念

后端的公共抽象是 `TmModule`。每个后端成对注册一个接收模块与一个解码模块，例如 AF_PACKET 的 `TmModuleReceiveAFPRegister` 与 `TmModuleDecodeAFPRegister`，分别填充 `tmm_modules[TMM_RECEIVEAFP]` 与 `tmm_modules[TMM_DECODEAFP]` 的 `name`、`Func`、`ThreadInit` 等钩子；DPDK 对应 `TmModuleReceiveDPDKRegister`、`TmModuleDecodeDPDKRegister` 与 `TMM_RECEIVEDPDK`、`TMM_DECODEDPDK`，pcap 对应 `TmModuleReceivePcapRegister`、`TmModuleDecodePcapRegister`。解码模块的 `Func` 通常就是 `DecodeAFP`、`DecodeDPDK`、`DecodePcap` 这类静态函数，它们从后端私有缓冲区里取出一帧，写入由包池分配的 `Packet`，再调用 `src/decode.h` 声明的解码分派函数。这种「接收与解码分离」的设计，让同一个解码器能被不同后端复用。

AF_PACKET 是 Linux 上最常用的在线后端，核心是内核 TPACKET 的 mmap 环形缓冲区。`src/source-af-packet.c` 里出现 `struct tpacket_req3` 与 `TPACKET_V2`、`TPACKET_V3` 两个版本常量，`AFPSetupRing` 负责按版本激活 ring，`AFPComputeRingParams` 计算块与帧的尺寸；多实例或多队列扩展靠 `以 `setsockopt` 在 `SOL_PACKET` 层传入 `PACKET_FANOUT` 选项` 把同一 fanout 组的套接字绑到一起，由内核按 cluster-type 做分流。`AFPCreateSocket` 完成套接字创建与绑定，`AFPSetBPFFilter` 挂 BPF 过滤，内联桥接场景还会走 `AFPWritePacket(p, TPACKET_V3)` 把报文从一网卡写到另一网卡。fanout 与 RSS 的关键语义是「对称哈希」：同一条双向流必须稳定落到同一个收包线程，否则 TCP 重组会拿到断裂的片段、应用层解析会看到缺口，告警自然失真，这就是流亲和。

DPDK 走的是另一条路：它绕过内核协议栈，由 EAL 初始化环境与大页，PMD 驱动在用户态轮询网卡队列，`source-dpdk.c` 中的 `rte_eth_rx_burst(ptv->port_id, ptv->queue_id, ptv->received_mbufs, burst_size)` 一次取回一批 mbuf，再交给 `DecodeDPDK` 转成 `Packet`。代价是网卡被独占、需要预先配置大页与 EAL 参数，收益是极少的拷贝与中断开销。Netmap 与 AF_XDP 同样追求零拷贝或低拷贝，但需要对应的内核接口与驱动支持。pcap 后端用 `pcap_dispatch` 从 libpcap 取包，`DecodePcap` 解码，适合离线 `-r` 回放与低速率在线；`source-nfq.c` 则是内联 IPS 的入口，`nfq_create_queue` 注册 `NFQCallBack`，最终由 `nfq_set_verdict` 给出 `NF_ACCEPT` 或丢弃决定（原理见 06-12）。交叉引用：字段见 05-02、05-07 ｜ 参数见 04-03、04-07 ｜ 模块见 07-06。

### 3. 关键数据结构与源码位置

本节只点名结构与真实路径，不重列字段；06 全册禁止完整结构体字段表，逐字段定义一律到 05。

- `TmModule`、`ThreadVars`、`PacketQueue`、`PacketQueueNoLock`：`src/tm-modules.h`、`src/threadvars.h`、`src/tm-threads.h`、`src/tm-queues.h`、`src/decode.h`（`struct PacketQueue_`），是后端注册与 slot 链装配的通用底座（字段见 05-07）。
- `Packet`、`DecodeThreadVars`：`src/decode.h`、`src/decode.c`，后端解码函数写入的目标载体（字段见 05-02）。
- `Flow` 与流表：`src/flow.h`、`src/flow-hash.c`，流亲和最终要保护的正是它（字段见 05-03）。
- `SCInstance`：`src/suricata.c`，保存 `run_mode`、`runmode_custom_mode`、`capture_plugin_name`、`capture_plugin_args` 等运行选择（字段见 05-09）。

后端私有上下文需要特别说明：`source-af-packet.c` 使用 `AFPThreadVars` 保存 `iface`、`socket`、`port_id`、`queue_id`、`received_mbufs` 等（DPDK 侧），`source-netmap.c`、`source-nfq.c`、`source-pcap.c` 各有自己的线程结构。这些是后端内部数据，不在 05 的通用结构体清单内，字段名与成员需对照 `src/source-*.c` 实际版本核验；通用线程与模块字段仍以「字段见 05-07」为准。`struct tpacket_req3` 来自内核头文件而非 Suricata 自身，其布局同样需对照实际内核版本核验。

文件落点整理如下：抓包源在 `src/source-af-packet.c`、`src/source-af-xdp.c`、`src/source-dpdk.c`、`src/source-netmap.c`、`src/source-nfq.c`、`src/source-nflog.c`、`src/source-ipfw.c`、`src/source-pcap.c`、`src/source-pcap-file.c`、`src/source-pcap-file-helper.c`、`src/source-pcap-file-directory-helper.c`、`src/source-erf-dag.c`、`src/source-erf-file.c`、`src/source-windivert.c`、`src/source-lib.c`；与之配对的 runmode 装配在 `src/runmode-af-packet.c`、`src/runmode-af-xdp.c`、`src/runmode-dpdk.c`、`src/runmode-netmap.c`、`src/runmode-nfq.c`、`src/runmode-pcap.c`、`src/runmode-pcap-file.c` 等；统一注册表在 `src/runmodes.c`。`suricata.yaml.in` 中 `af-packet`、`dpdk`、`threading` 等段的键名需对照实际版本核验（参数见 04-03）。交叉引用：字段见 05-02、05-07、05-09 ｜ 参数见 04-03 ｜ 模块见 07-06、07-09。

### 4. 关键流程与调用链

公共装配链从 `src/runmodes.c` 的 `RunModeRegisterRunModes(void)` 开始，它 `memset(runmodes, 0, sizeof(runmodes))` 后依次调用 `RunModeIdsPcapRegister`、`RunModeFilePcapRegister`、`RunModeIpsNFQRegister`、`RunModeIpsIPFWRegister`、`RunModeErfFileRegister`、`RunModeErfDagRegister`、`RunModeIdsAFPRegister`、`RunModeIdsAFXDPRegister`、`RunModeIdsNetmapRegister`、`RunModeIdsNflogRegister`、`RunModeUnixSocketRegister`、`RunModeIpsWinDivertRegister`、`RunModeDpdkRegister`，并在 `UNITTESTS` 下追加 `UtRunModeRegister`。`SuricataInit` 末尾的 `RunModeDispatch` 取出目标 `RunMode` 后执行 `mode->RunModeFunc()`；以 `src/runmode-af-packet.c` 的 `RunModeIdsAFPRegister` 为例，它把 `RunModeIdsAFPAutoFp`、`RunModeIdsAFPSingle` 等自定义模式连同 `AFPRunModeEnableIPS` 注册进表。这些 runmode 函数内部用 `TmThreadCreatePacketHandler` 建线程、`TmModuleGetByName` 取模块、`TmSlotSetFuncAppend` 拼 slot 链、`TmThreadSpawn` 启动，最后回到 `RunModeDispatch` 的 `TmValidateQueueState` 与管理线程拉起。各后端分流与流亲和落点见图 06-02-01。

AF_PACKET 的初始化链可以顺着真实符号读：`AFPCreateSocket` 建立 `AF_PACKET` 套接字并绑定网卡，`AFPComputeRingParams(ptv, order)` 计算 ring 参数，`AFPSetupRing(ptv, devname)` 通过 `setsockopt` 选择 `TPACKET_V3`（内核过老时回退或报错，`source-af-packet.c` 里有「kernel too old for TPACKET_V3」的日志文本），随后以 `PACKET_FANOUT` 把多线程套接字加入同一 fanout 组，`AFPSetBPFFilter` 挂过滤规则，`AFPPeersListAdd` 维护桥接对等端信息。稳态收包循环把 ring 中的帧交给 `DecodeAFP`，后者取 `PacketPoolGetPacket` 得到的 `Packet` 填充并送入解码分派；内联桥接时 `AFPWritePacket(p, TPACKET_V2)` 或 `AFPWritePacket(p, TPACKET_V3)` 把报文写到对端网卡，这正是 AF_PACKET 桥接 verdict 的落点（原理见 06-12）。

DPDK 的链路更短也更苛刻：`source-dpdk.c` 的接收循环调用 `rte_eth_rx_burst(ptv->port_id, ptv->queue_id, ptv->received_mbufs, burst_size)` 批量取 mbuf，再由 `DecodeDPDK(ThreadVars *tv, Packet *p, void *data)` 把 mbuf 内容转成 `Packet` 并继续解码；EAL 初始化、大页与端口配置发生在线程初始化阶段（具体函数名需对照实际版本核验）。pcap 链路是 ``pcap_dispatch` 以 `pcap_handle` 与 `packet_q_len` 为批量参数` 回调取包后交给 `DecodePcap`。Netmap 链路有 `DecodeNetmap(ThreadVars *tv, Packet *p, void *data)` 与 `NetmapWritePacket(NetmapThreadVars *ntv, Packet *p)`，分别对应接收解码与内联写出。NFQ 链路是 `nfq_create_queue(q->h, q->queue_num, &NFQCallBack, (void *)t)` 注册回调，回调里 `NFQCallBack` 把报文构造成 `Packet` 入流水线，末端由 `nfq_set_verdict` 给出 `NF_ACCEPT` 或 drop，队列号必须与 iptables / nftables 规则一致。无论哪条链路，`Packet` 最终都会被 `p->ReleasePacket` 回收，收包与回池在 `src/tmqh-packetpool.c` 里闭环。

| NFQUEUE | `src/source-nfq.c` | `NFQCallBack`、`nfq_set_verdict` | 内联 IPS，需 iptables/nftables 配对 |
| PF_RING | 需对照 `configure.ac` 与 `src/source-*.c` 核验 | 需对照实际版本核验 | 本快照注册列表未见，不臆造文件名 |

```text

DPDK support:                            no
```

逐行判读如下。前两行来自 `--build-info`：`AF_PACKET support: yes` 表示本次构建编入了 AF_PACKET 后端，可以放心用 `-i` 指定网卡；`DPDK support: no` 表示未启用 DPDK，此时即便配了 `dpdk` 段也不会生效，正常取值取决于 `configure.ac` 的构建开关，不能据本例的 yes/no 当作通用结论，特性名需对照实际版本核验。中间三行是 `--list-runmodes` 的表格片段，`IDS + AFPACKET` 下的 `workers` 与 `autofp` 是两种线程拓扑，`IDS + PCAP` 下的 `single` 是单线程调试模式；若这里没有目标模式，说明相应 runmode 未注册或构建被裁剪，应回到 02-02 的构建选项核对。后两行来自 `stats.log`：`capture.kernel_packets` 是内核 ring 交付的累计包数，在线运行时应随流量单调增长，长时间不动通常指向网卡名错误、权限不足或 fanout 未生效；`capture.kernel_drops` 是内核侧丢弃计数，健康系统应长期为零或极低，持续增长说明 ring 偏小、CPU 处理不过来或包池成为瓶颈，需要结合 `af-packet.threads`、cluster-type 与绑核一起排查（参数见 04-03，调优见 08-02）。任何吞吐与丢包率结论一律标注「需在目标机型实测」，不给绝对值。

### 6. 注意事项、陷阱与最佳实践

最高频的陷阱是把 DPDK 当成「插上网卡就能用」的通用后端。它要求把网卡从内核驱动解绑、预留大页、给出 EAL 参数，且一旦被 DPDK 独占，该网卡就不再出现在普通 `ip link` 视角里；容器与云主机往往不具备这些前提，硬套只会启动失败。与之相对，pcap 后端虽然部署最简单，但在高速链路上受 libpcap 拷贝与中断开销限制，多用于离线回放或低速率在线，把它当生产在线抓包同样不妥。Netmap 与 AF_XDP 依赖特定内核接口与驱动，启用前要核对 `configure.ac` 与 `src/source-*.c`；PF_RING 的支持状态按 SPEC 要求一律写「需对照实际版本核验」，本快照的 `RunModeRegisterRunModes` 清单里没有 PF_RING 注册项，更不能编造 `source-pfring.c` 或 `runmode-pfring.c` 之类文件名。

第二个陷阱是流亲和被破坏。AF_PACKET 多队列时若 fanout 的 cluster-type、cluster-id 配置不当，或 RSS 哈希不对称，同一条 TCP 流的两个方向可能落到不同收包线程，重组器看到的就是断裂片段，结果是「包都收到了但 HTTP/DNS 事件全无」。cluster-id 还要注意与同机其他 Suricata 实例错开，否则多个实例会加入同一 fanout 组互相抢包。权限方面，AF_PACKET 需要 `CAP_NET_RAW`、`CAP_NET_ADMIN`，容器里常见 `--net=host` 加 capability 的组合，`--privileged` 应作为最后手段而非默认（部署见 03-06）。内联 IPS 场景要严格区分 IDS 与 IPS：NFQUEUE 队列号必须与 iptables / nftables 规则一致，桥接模式要正确设置 copy-mode / copy-iface，`stream.inline` 与 fail-open 策略要与业务可用性匹配；drop 不生效时按 08-04 的案例逐项排查，而 Suricata 自始至终不做转发、不是防火墙（原理见 06-12）。

最佳实践是「先验构建、再验收包、后验检测」：`--build-info` 确认后端被编入，`--list-runmodes` 确认模式已注册，启动后先看 `capture.kernel_packets` 与 `capture.kernel_drops` 这对收包计数，再往下游看 `decoder.pkts`、`flow`、`detect.alert`。上线前用 `suricata -T` 验规则、`--dump-config` 验生效配置，避免把后端问题误判成规则问题。多线程扩展务必配合 RSS 队列数、对称哈希与 `threading.set-cpu-affinity` 一起做 A/B 对照，且所有性能数字标注「需在目标机型实测」。另需记住两条全册边界：Hyperscan 只是可选 MPM 加速、缺失回退 AC，不是任何后端的必需依赖；`suricata-update` 是独立发版工具，不参与 `src/` 编译，别把它和抓包后端混为一谈。
补充一层关于 fanout 与队列分配的机制说明，便于把配置与原理对上。AF_PACKET 的 `PACKET_FANOUT` 把多个套接字加入同一 fanout 组后，内核按 cluster-type 决定每个帧交给组内哪个套接字，常见语义围绕按流哈希、按 CPU、按队列与 rollover 展开，具体取值与可用模式需对照 `suricata.yaml.in` 的 `cluster-type` 与内核头文件核验，不能凭印象写死。无论哪种模式，目标都是让同一条双向流的两个方向稳定落到同一收包线程；哈希若不对称，客户端到服务器与服务器到客户端的帧会分到不同线程，重组器各看到半条流，`flow:established` 与 `http.uri` 一类规则随之失效。cluster-id 是 fanout 组的标识，同机多实例必须各不相同，否则会互相争抢同一组内的帧。DPDK 侧没有内核 fanout，取而代之的是网卡 RSS 队列与 `rte_eth_rx_burst(ptv->port_id, ptv->queue_id, ptv->received_mbufs, burst_size)` 里的 port_id 与 queue_id 绑定：每个收包线程固定消费自己的队列，队列数与线程数、RSS 重定向表必须配套，否则会出现部分队列饥饿。大页与 EAL 参数则决定 mbuf 内存池能否按预期分配，`src/source-dpdk.c` 的线程初始化阶段在配置为空时会直接报错，可见「DPDK configuration is NULL」的日志文本，这是 DPDK 模式启动失败最常见的一类证据。把这些与 06-13 的 runmode 一起看，就能理解为何「加线程」必须伴随队列与哈希的重新规划，而不能只改一个数字。


### 7. 小结与延伸阅读

本篇把五类后端收敛到同一套抽象：都由 `RunModeRegisterRunModes` 注册、由 `mode->RunModeFunc()` 装配、由成对的 `TmModuleReceiveXXXRegister` / `TmModuleDecodeXXXRegister` 落到 `tmm_modules` 注册表项，最终由 `DecodeXXX` 把帧写进 `Packet` 并交给通用解码链。差异集中在环境代价：AF_PACKET 靠 TPACKET_V3 ring 与 `PACKET_FANOUT` 做通用在线与流亲和；DPDK 靠 EAL、大页与 `rte_eth_rx_burst` 轮询换低开销，但必须独占网卡；Netmap / AF_XDP 依赖内核与驱动；pcap 适合离线；NFQUEUE 服务内联 verdict。PF_RING 则如实标注「需对照实际版本核验」，不臆造文件与函数。

## 06-03 解码器与隧道、VLAN、分片处理

### 1. 背景与动机

抓包后端交付的是一段没有语义的原始字节，而检测引擎需要的是「源目地址、协议、端口、各层头部指针、载荷边界、所属流」这样结构化的信息。把前者变成后者的正是解码器。它位于流水线的第二段，是后续流管理、TCP 重组、应用层解析与规则匹配共同的前置条件：引擎只对自身解码并重组到的流量做检测，一个在解码阶段就被判定异常或无法识别的报文，后面所有环节都无从谈起。把解码单独成篇，是因为它并非简单的「按以太网类型 switch 一下」，而要同时处理协议分层、隧道嵌套、VLAN / QinQ 标签栈、IP 分片重组、校验和验证、解码异常事件，以及递归层级与追踪维度这些容易被忽略的细节。

现实网络的复杂性直接压在解码层。同一条物理链路上可能同时跑原生 IPv4/IPv6、802.1Q VLAN、QinQ 双层标签、GRE / VXLAN / GENEVE / ERSPAN 隧道、PPPoE、MPLS、Teredo，还夹杂大量 IP 分片与校验和卸载（offload）造成的「伪错误」。Suricata 必须为每一种封装建立分派路径，并限制递归深度以免恶意构造的嵌套报文耗尽栈或绕过检测。本次核验的 `src/decode-*.c` 真实文件族达到三十个，涵盖 arp、chdlc、erspan、esp、etag、ethernet、events、geneve、gre、icmpv4、icmpv6、igmp、ipv4、ipv6、mpls、nsh、null、ppp、pppoe、raw、sctp、sll、sll2、tcp、template、teredo、udp、vlan、vntag、vxlan；分片重组另有 `src/defrag.c`、`src/defrag-config.c`、`src/defrag-hash.c`、`src/defrag-stack.c`、`src/defrag-timeout.c` 一族。这份清单本身就是解码复杂度的证据。

还要再次立住边界。解码器只解析报文结构，不做 IP 转发、不做路由；Suricata 整体是 IDS / IPS / NSM 而非防火墙。解码器也读不到加密载荷的明文，TLS 握手之后的记录层内容对它是不可见的，能用于检测与日志的是握手元数据、证书、SNI、JA3/JA4 一类指纹（相关实现见 `rust/src/ja4.rs`，具体字段需对照实际版本核验）。解码异常事件（decoder event）与「丢包」是两回事：多数异常只是登记为事件或统计项，报文本身仍可能继续走流水线或被静默忽略。本套资料版本基准统一为「上游 main 快照（2026-11 抓取）」，本篇所有函数名与路径均以此快照下 `upstream_src/suricata/suricata-main/` 内真实文件为锚点。

### 2. 核心概念

解码的核心模型是「分层分派 + 逐层填 `Packet`」。`src/decode.h` 以函数声明的形式固定了各层入口：链路层有 `DecodeEthernet`、`DecodeSll`、`DecodeSll2`、`DecodeNull`、`DecodeRaw`、`DecodePPP`、`DecodePPPOESession`、`DecodePPPOEDiscovery`；网络层有 `DecodeIPV4`、`DecodeIPV6`、`DecodeICMPV4`、`DecodeICMPV6`；传输层有 `DecodeTCP`、`DecodeUDP`、`DecodeSCTP`。这些函数签名一致地接收 `ThreadVars *`、`DecodeThreadVars *`、`Packet *`、指向当前层数据的指针与长度，逐层推进并填写 `Packet` 的各层指针、地址、端口、协议与 payload 边界。长度读写通过 `GET_PKT_LEN(p)`、`SET_PKT_LEN(p, len)` 两个宏完成，`DecodeThreadVars` 则是每线程解码上下文，承载计数与临时状态（字段见 05-02）。

隧道与 VLAN 的处理依赖递归与栈式结构。`src/decode.c` 的 `DecodeTunnel` 是隧道分派中枢，参数含 `ThreadVars *`、`DecodeThreadVars *`、`Packet *`、数据指针与长度以及隧道协议枚举，本次核验可见它按协议把内层数据再交给 `DecodePPP`、`DecodeIPV4`、`DecodeIPV6`、`DecodeVLAN`、`DecodeEthernet`；`src/decode.h` 提供 `PacketTunnelPktSetup` 与 `PacketTunnelPktSetupWithSession` 用于创建隧道子包，`Packet` 内的 `root` 指针指回最外层根包，从而把内层报文与同一条原始帧关联起来。VLAN 与 QinQ 本质是标签栈，`src/decode-vlan.c` 逐层剥离后再把 ethertype 交回分派；`src/decode-vntag.c`、`src/decode-etag.c`、`src/decode-mpls.c`、`src/decode-nsh.c`、`src/decode-gre.c`、`src/decode-vxlan.c`、`src/decode-geneve.c`、`src/decode-teredo.c`、`src/decode-erspan.c` 各自对应一种封装。递归层级必须受限，否则嵌套隧道可被用来放大处理成本或规避检测。

IP 分片重组是另一条独立支线。`src/decode-ipv4.c` 在检测到分片时调用 `Packet *rp = Defrag(tv, dtv, p)`（该文件第 536 行附近的真实代码），由 `src/defrag.c` 及其哈希、栈、超时、配置族把属于同一报文的分片拼回，再把重组后的 `Packet` 送回解码链；`DefragInit`、`DefragDestroy` 是这一子系统的初始化与销毁入口。解码异常由 `src/decode-events.c` 定义事件类型，登记到 `Packet` 的 `PacketEngineEvents`，并由 `DecodeRegisterPerfCounters`、`DecodeGlobalConfig` 建立统计计数；`PacketDecodeFinalize(ThreadVars *tv, DecodeThreadVars *dtv, Packet *p)` 是解码收尾函数。最后有一个常被忽略的配置维度：`src/suricata.c` 的 `SuricataInit` 会读取 `vlan.use-for-tracking`、`livedev.use-for-tracking`、`decoder.recursion-level.use-for-tracking` 三个布尔项，决定是否把 VLAN id、接入设备 id、递归层级纳入流比较（对应 `g_vlan_mask`、`g_livedev_mask`、`g_recurlvl_mask`），它们直接影响 `FlowKey` 的计算（原理见 06-04）。交叉引用：字段见 05-02 ｜ 参数见 04-02 ｜ 模块见 07-01。

一个易错点值得写明：`int main` 在 `src/main.c`，而 `DecodeGlobalConfig(void)`、`DecodeRegisterPerfCounters(DecodeThreadVars *, ThreadVars *)`、`PacketDecodeFinalize` 都在 `src/decode.c`；不要把这些初始化与收尾函数误记到某个 `decode-*.c` 分文件里。`PacketTunnelPktSetup`、`PacketTunnelPktSetupWithSession`、`DecodeThreadVarsAlloc`、`DecodeThreadVarsFree` 的声明集中在 `src/decode.h`。后端解码入口 `DecodeAFP`、`DecodePcap`、`DecodeDPDK`、`DecodeNetmap` 分别在各 `source-*.c` 中，它们调用上述分派函数而非自己解析各层。交叉引用：字段见 05-02、05-03、05-07 ｜ 参数见 04-02 ｜ 模块见 07-01、07-06。

### 4. 关键流程与调用链

单个报文的解码链从后端 `DecodeXXX` 开始：它从 `PacketPoolGetPacket` 取得一个 `Packet`，按数据链路类型调用 `DecodeEthernet`、`DecodeSll`、`DecodeRaw` 或 `DecodePPP` 等链路层入口；链路层依据 ethertype 调用 `DecodeIPV4` / `DecodeIPV6` / `DecodeVLAN` / `DecodeARP`；网络层依据 protocol 调用 `DecodeTCP` / `DecodeUDP` / `DecodeSCTP` / `DecodeICMPV4` / `DecodeICMPV6`。每深入一层都在同一个 `Packet` 上追加该层信息，隧道场景则由 `DecodeTunnel` 开一条递归支路，用 `PacketTunnelPktSetup` 挂出内层包并把 `root` 指向根包。解码完成后 `PacketDecodeFinalize` 收尾，`DecodeRegisterPerfCounters` 登记的计数器在此前后被更新，异常路径则写入 `src/decode-events.c` 定义的事件并反映到 `PacketEngineEvents` 与 `stats.log`。整条分层、隧道递归与分片分支见图 06-03-01。

隧道递归的具体分派可在 `src/decode.c` 的 `DecodeTunnel` 中读到：它依据协议枚举把内层数据交给 `DecodePPP`、`DecodeIPV4`、`DecodeIPV6`、`DecodeVLAN` 或 `DecodeEthernet`，不支持的协议走 `SCLogDebug` 记录「protocol not supported」并终止该分支。这种设计让 GRE、VXLAN、GENEVE、Teredo、ERSPAN 等外层封装共用一个递归入口，而具体封装的头部解析各自放在 `decode-gre.c`、`decode-vxlan.c` 等文件中。递归层级既影响处理成本，也参与流追踪：`SuricataInit` 里 `SCConfGetBool("decoder.recursion-level.use-for-tracking", &tracking)` 决定 `g_recurlvl_mask` 是否为零，从而决定不同嵌套深度的内层流量会不会被哈希成同一条 `Flow`。同理 `vlan.use-for-tracking` 与 `livedev.use-for-tracking` 通过 `g_vlan_mask`、`g_livedev_mask` 影响 `FlowKey`（字段见 05-03）。

分片链是解码期最容易被低估的一段。`DecodeIPV4` 在分片标志或偏移非零时调用 `Defrag(tv, dtv, p)`，`src/defrag-hash.c` 以分片标识维护跟踪器，`src/defrag-stack.c` 管理分片队列，`src/defrag-timeout.c` 处理超时清理，`src/defrag-config.c` 读取 memcap 与策略配置；重组成功返回一个新的 `Packet`（代码里即 `Packet *rp`），随后继续走 `DecodeTCP` / `DecodeUDP` 等上层分派，失败或超时则由 `src/decode-events.c` 登记异常。校验和验证由 `stream.checksum-validation` 一类的配置项控制（键名需对照实际版本核验），网卡开启 checksum offload 时抓到的帧可能带未计算的校验和，导致 `decoder.invalid` 虚高，这是典型的「配置没动但异常计数突然涨」的成因。收尾之后 `Packet` 进入 `FlowWorker` 做流查找与绑定，解码阶段至此结束。

### 6. 注意事项、陷阱与最佳实践

第一个陷阱是把三个 tracking 开关当成无关紧要的默认项。`vlan.use-for-tracking`、`livedev.use-for-tracking`、`decoder.recursion-level.use-for-tracking` 分别决定 VLAN id、接入设备 id、递归层级是否参与 `FlowKey` 比较；关闭它们会让不同 VLAN、不同入口、不同隧道深度的流量被合并成同一条 `Flow`，在 QinQ 或多租户镜像环境里可能引发流串扰与误报。反之，在确实不需要区分的单一链路里保留它们则能减少流表条目。调整前务必理解 06-04 的五元组与流表哈希语义，且键名需对照 `suricata.yaml.in` 与实际版本核验。第二个陷阱是隧道递归深度：嵌套封装既增加每包处理成本，也可能被用于规避基于外层特征的检测，遇到 GRE / VXLAN / GENEVE 密集的环境应结合 `decoder` 计数与异常事件一起观察，而不是盲目放大递归上限。

分片与校验和是另外两类高发问题。`Defrag` 依赖 `defrag-config.c` 的 memcap 与超时策略，分片洪泛或超时过短都会让重组失败，表现为「有分片但看不到完整流」；排查时要把 `defrag` 族与 `src/decode-events.c` 的异常事件一起看。校验和方面，若网卡开启了 checksum offload、GRO 或 LRO，抓到的帧校验和字段可能尚未被硬件填写，导致 `decoder.invalid` 虚高甚至触发 checksum 相关规则误判；生产上通常在抓包网卡侧关闭卸载，并由 `stream.checksum-validation` 一类键决定是否严格验证（键名需对照实际版本核验）。还需强调：解码异常事件不等于丢包，很多异常只是登记为事件后按策略处理，把 `decoder.invalid`  nonzero 直接解释成「引擎在丢包」会误导排障方向。

可见性边界必须贯穿始终：TLS 等加密载荷的记录层明文对解码器不可见，能拿到的是握手元数据、证书、SNI、JA3/JA4 等（原理见 06-05、06-12），不能宣称读到 HTTPS 正文。隧道场景还要注意内层与外层的 `Packet->root` 关系、`BypassPacketsFlow` 钩子对已 bypass 流的短路，以及 `Packet` 由 `ReleasePacket` 统一回池，避免把隧道子包当成独立帧重复计数。最佳实践是「先看 `capture`，再看 `decoder`，最后看 `flow` 与 `detect`」：用 `suricata -r` 回放脱敏样本建立各层计数的基线，再上在线流量对照；用 `--dump-config` 确认 tracking 与 checksum 类配置真正生效；任何吞吐、丢包率、内存占用结论一律标注「需在目标机型实测」，不给绝对值。解码模块的能力清单见 07-01，参数全集见 04-02、04-07。
补充两点关于封装差异与事件判读的经验。其一是不同隧道的头部开销与递归行为并不一致：GRE 只带最基本的标志与协议类型，VXLAN、GENEVE 在 UDP 之上叠加 VNI 与可选扩展头，ERSPAN 还带会话与镜像元数据，MPLS 与 NSH 则属于标签栈式转发面封装；`src/decode-gre.c`、`src/decode-vxlan.c`、`src/decode-geneve.c`、`src/decode-erspan.c`、`src/decode-mpls.c`、`src/decode-nsh.c` 各自解析完外层后，都会把内层数据交回 `DecodeTunnel` 或直接调链路层与网络层入口，因此「外层协议识别正确但内层没解出来」时，应顺着具体封装文件查它的内层分派条件，而不是笼统归咎于解码器。其二是事件与统计的对应关系：`src/decode-events.c` 定义的每个解码异常都可能同时表现为 `stats.log` 里的一个计数项与 EVE 里的一条 `anomaly` 事件，但两者并非一一对应，是否落盘取决于 `outputs` 里 `anomaly` 类型是否开启以及 `DecodeRegisterPerfCounters` 登记的计数是否被轮询；因此「计数涨了但 eve.json 没事件」不等于引擎丢事件，先核对输出类型开关。再强调一次，解码器读不到 TLS 记录层明文，隧道解密也不在其职责范围内，能用于检测的是外层地址、隧道元数据与握手期可观测字段。


### 7. 小结与延伸阅读

本篇把解码器归纳为「分层分派 + 递归隧道 + 分片重组 + 异常计数」四件事。分层分派由 `src/decode.h` 声明的 `DecodeEthernet` / `DecodeIPV4` / `DecodeTCP` 等函数逐级完成，逐层填充 `Packet`；隧道与 VLAN 由 `DecodeTunnel` 递归、`PacketTunnelPktSetup` 挂子包、`decode-vlan.c` 等专文件处理，并受递归层级限制；IP 分片由 `DecodeIPV4` 调用 `Defrag` 交 `src/defrag*.c` 族重组；异常与统计由 `src/decode-events.c`、`DecodeRegisterPerfCounters`、`PacketDecodeFinalize` 收口。三个 tracking 开关通过 `g_vlan_mask`、`g_livedev_mask`、`g_recurlvl_mask` 把解码结果直接耦合到流表，这是解码与流管理之间最容易被忽视的接口。

## 06-04 流管理、流超时与 TCP 流重组

### 1. 背景与动机

如果把解码器比作「把字节变成结构化报文」，那么流管理与 TCP 重组就是「把孤立报文还原成有上下文的会话」。检测引擎几乎不做纯逐包判断：`flow:established,to_server`、`flowbits`、`xbits` 依赖同一条流的状态，HTTP、DNS、TLS、SMB 等应用协议解析依赖连续有序的字节流，而 `content` 跨 TCP 段匹配更要求先把乱序、重传、重叠的片段拼成完整缓冲。没有流这一层，规则里绝大多数有状态语义都无从落地。理解本篇，也就理解了为什么 Suricata 不是「拿一帧匹配一次规则」的匹配器，而是一个带会话状态机的 IDS / IPS / NSM 引擎。

流与重组同时是资源消耗的大户。流表要为每个并发会话保留 `Flow` 与协议上下文，TCP 会话要保留 `TcpSession`、双向 `TcpStream` 与重组队列，重组缓冲还要单独受 memcap 约束。攻击者完全可以用海量短连接、半开连接或乱序分片去撑爆这些结构，因此引擎必须配套超时管理、备用池、紧急回收与 bypass 机制。本次核验的源码族也印证了这份复杂度：`src/flow.c`、`src/flow-hash.c`、`src/flow-worker.c`、`src/flow-manager.c`、`src/flow-timeout.c`、`src/flow-queue.c`、`src/flow-spare-pool.c`、`src/flow-storage.c`、`src/flow-bit.c`、`src/flow-var.c`、`src/flow-bypass.c`、`src/flow-callbacks.c`、`src/flow-util.c`，以及 `src/stream-tcp.c`、`src/stream-tcp-reassemble.c`、`src/stream-tcp-inline.c`、`src/stream-tcp-list.c`、`src/stream-tcp-sack.c`、`src/stream-tcp-util.c`、`src/stream-tcp-cache.c` 一族，头文件同样成体系（`src/flow.h`、`src/flow-private.h`、`src/stream-tcp.h`、`src/stream-tcp-private.h` 等）。

边界依旧要立住。Suricata 不做 IP 转发、不是防火墙、不做路由；重组深度与加密载荷共同决定可见性上限：TLS 握手之后的记录层明文不可见，能拿到的是握手元数据、证书、SNI、JA3/JA4 一类指纹（相关 Rust 侧实现见 `rust/src/ja4.rs`，具体字段需对照实际版本核验），超过 `stream.reassembly.depth` 之后的数据也不再向应用层解析器供给。任何吞吐、并发流数、内存占用结论一律标注「需在目标机型实测」，不给绝对值。本套资料版本基准统一为「上游 main 快照（2026-11 抓取）」。

### 2. 核心概念

流层的核心对象是 `Flow`：`src/flow.h` 中 `typedef struct FlowKey_`（第 311 行）、`typedef struct Flow_`（第 359 行）、`FlowStateType flow_state`（第 427 行）与 `struct FlowBucket_ *fb`（第 498 行）勾勒出「键 → 流 → 桶」的关系；`enum FlowState` 明确定义 `FLOW_STATE_NEW`、`FLOW_STATE_ESTABLISHED`、`FLOW_STATE_CLOSED`、`FLOW_STATE_LOCAL_BYPASSED`、`FLOW_STATE_CAPTURE_BYPASSED`（第 510 行起），`FlowUpdateState(Flow *f, enum FlowState s)` 负责迁移状态（字段见 05-03）。`FlowKey` 以五元组为基础，并可由 `src/suricata.c` 的 `g_vlan_mask`、`g_livedev_mask`、`g_recurlvl_mask` 决定是否叠加 VLAN id、接入设备与递归层级，这正是 06-03 三个 tracking 开关的下游落点。

流表是带桶锁的哈希表。全局数组 `FlowBucket *flow_hash` 定义于 `src/flow-hash.c`，`FlowKeyGetHash(FlowKey *fk)` 计算哈希，`CmpFlowKey` 做键比较，`FlowSetupPacket(Packet *p)` 预处理包内查找字段，`FlowGetFlowFromHash(ThreadVars *tv, FlowLookupStruct *fls, Packet *p, Flow **dest)` 完成「查不到就新建」，`FlowGetNew`、`FlowGetUsedFlow`、`TcpReuseReplace` 处理新建、复用与 TCP 会话替换，`FlowCompareKey`、`FlowGetExistingFlowFromHash`、`FlowGetFromFlowKey` 支撑按键反查。稳态下 `src/flow-worker.c` 的 `FlowWorker(ThreadVars *tv, Packet *p, void *data)` 是流水线上每个包的必经点，它调用 `FlowHandlePacket(tv, &fw->fls, p)` 完成流绑定与状态推进，`FlowFinish`、`CheckWorkQueue`、`FlowWorkerProcessLocalFlows`、`FlowWorkerProcessInjectedFlows` 负责收尾与工作队列消费；模块注册为 `tmm_modules[TMM_FLOWWORKER].Func = FlowWorker`。

超时与回收由独立管理线程承担。`src/flow-manager.c` 定义 `FlowManager`、`FlowManagerThreadInit`、`FlowManagerThreadDeinit`、`FlowManagerThreadSpawn`，以及 `FlowRecycler`、`FlowRecyclerThreadSpawn`，分别挂在 `TMM_FLOWMANAGER`、`TMM_FLOWRECYCLER`；`src/flow-timeout.c` 提供 `FlowNeedsReassembly(Flow *f)`、`FlowPseudoPacketSetup`、`FlowPseudoPacketGet`、`FlowSendToLocalThread`、`FlowRemoveHash`、`FlowWorkToDoCleanup` 等，核心手法是对超时但仍需冲刷重组缓冲的流构造「伪包」投递回本地线程，让检测与日志有机会收尾，再安全回收。`FlowInitConfig(bool quiet)`、`FlowShutdown()`、`FlowClearMemory`、`FlowSetProtoFreeFunc` 在 `src/flow.c` 负责流表与协议释放钩子的初始化与销毁，`flow-spare-pool.c`、`flow-queue.c` 管理备用流与待处理队列。

TCP 重组把 `Flow` 进一步具体化。`TcpSession` 挂在 `p->flow->protoctx`（`src/stream-tcp.c` 里可见 `p->flow->protoctx` 的强转），双向各有 `TcpStream`，相关定义分布在 `src/stream-tcp-private.h` 等头文件（字段名需对照实际版本核验）。主入口 `StreamTcp(ThreadVars *tv, Packet *p, void *data, PacketQueueNoLock *pq)`（第 6137 行）驱动三次握手状态、`StreamTcpValidateTimestamp`、`StreamTcpValidateAck`、`StreamTcpValidateRst`、`StreamTcpHandleFin` 等校验，`StreamTcpNewSession` 建会话，`StreamTcpPacketSetState` 更新包状态。重组链在 `src/stream-tcp-reassemble.c`：`StreamTcpReassembleInit(bool quiet)`、`StreamTcpReassembleDepthReached(Packet *p)`、`StreamTcpReassembleInsertSegment`、`StreamTcpReassembleHandleSegment`、`StreamTcpReassembleHandleSegmentUpdateACK`、`StreamTcpReassembleAppLayer`，把乱序段按序列号插入、按 ACK 推进、向应用层供给连续缓冲；`src/stream-tcp-sack.c` 的 `StreamTcpSackUpdatePacket`、`StreamTcpSackPruneList`、`StreamTcpSackFreeList` 处理 SACK，`src/stream-tcp-inline.c` 的 `StreamTcpInlineSegmentCompare` 服务内联重叠比较。配置侧 `StreamTcpInitConfig` 通过 `SCConfGetInt` / `SCConfGetBool` / `SCConfGetNonNull` 读取 `stream.max-sessions`、`stream.prealloc-sessions`、`stream.memcap`、`stream.midstream`、`stream.async-oneside`、`stream.checksum-validation`、`stream.inline`、`stream.bypass`、`stream.drop-invalid`、`stream.reassembly.memcap`、`stream.reassembly.memcap-policy`、`stream.reassembly.urgent.policy` 等键（键名需对照实际版本核验）；`stream-tcp.h` 里 `TcpStreamCnf`、`stream_config`、`STREAMTCP_INIT_FLAG_INLINE`、`TcpSessionSetReassemblyDepth`、`StreamNeedsReassembly` 是这条链的配置与辅助接口。交叉引用：字段见 05-03 ｜ 参数见 04-02、04-03 ｜ 模块见 07-02、07-08。

### 4. 关键流程与调用链

稳态下一个 TCP 包的流路径如下：解码完成后 `Packet` 进入 `FlowWorker`，先由 `FlowSetupPacket(p)` 准备好查找所需的规范化字段（例如把源目地址按 `FlowHashRawAddressIPv6GtU32` 规则排序以统一双向键），再 `FlowGetFlowFromHash(tv, fls, p, &dest)` 在 `flow_hash[hash % flow_config.hash_size]` 对应桶内查找；命中则复用现有 `Flow`，未命中则 `FlowGetNew` 或 `FlowGetUsedFlow` 从备用池取流并在紧急状态下回收，TCP 场景还可能走 `TcpReuseReplace` 处理端口复用。`FlowHandlePacket` 随之推进状态，`FlowUpdateState(f, FLOW_STATE_ESTABLISHED)` 一类迁移把 `new` 变为 `established`，此后 `flow:established` 类规则才成立。流绑定完成后进入 `StreamTcp`，由 `StreamTcpNewSession` 建 `TcpSession` 并挂到 `p->flow->protoctx`，再进入重组。流查找、状态机、重组与超时管理线程的关系见图 06-04-01。

重组链的细节值得展开。`StreamTcpReassembleHandleSegment` 收到一个带序列号的段后，经 `StreamTcpReassembleInsertSegment` 把载荷插入对应 `TcpStream` 的段队列，乱序先缓存、空洞后补齐；`StreamTcpSackUpdatePacket` 依据 SACK 选项更新已收范围，`StreamTcpSackPruneList` / `StreamTcpSackFreeList` 修剪与释放。对端 ACK 到达时 `StreamTcpReassembleHandleSegmentUpdateACK` 推进已确认边界，随后 `StreamTcpReassembleAppLayer(tv, ra_ctx, ssn, stream, p, dir)` 把连续缓冲按 `UPDATE_DIR_PACKET` / `UPDATE_DIR_OPPOSING` 等方向供给应用层解析器，这正是 06-05 中 `AppLayerParserParse` 的数据来源。深度控制由 `StreamTcpReassembleDepthReached(p)` 与 `ssn->reassembly_depth` 完成，`src/stream-tcp-reassemble.c` 中可读到按 `stream->isn + ssn->reassembly_depth` 截断的逻辑；`TcpSessionSetReassemblyDepth(TcpSession *ssn, uint32_t size)` 允许按会话覆盖深度。内联模式还要经 `StreamTcpInlineSegmentCompare` 做重叠段一致性检查，`stream.inline` 决定重组是否在 verdict 前给出确定性数据（原理见 06-12）。

超时与回收是另一条并行线。`RunModeDispatch` 在启动收尾处调用 `FlowManagerThreadSpawn()` 与 `FlowRecyclerThreadSpawn()`（以及按需的 `BypassedFlowManagerThreadSpawn()`），拉起 `FlowManager` 与 `FlowRecycler` 两个管理线程。`FlowManager` 周期扫描 `flow_hash` 各桶，对 `new`、`established`、`closed`、`bypassed` 等不同状态套用不同超时；`FlowNeedsReassembly(f)` 判断一条即将超时的流是否还有未冲刷的重组数据，若是则 `FlowPseudoPacketGet` 构造伪包、`FlowSendToLocalThread` 投递回工作线程，让 `FlowFinish` 有机会把剩余缓冲交给检测与日志，之后 `FlowRemoveHash` 摘链、`FlowClearMemory` 清理协议上下文、`FlowRecycler` 把 `Flow` 回收进备用池，形成图 06-04-01 中虚线所示的复用闭环。`StreamTcpSessionCleanup`、`StreamTcpSessionClear`、`StreamTcpStreamCleanup`、`StreamTcpSessionPktFree` 负责 TCP 侧资源释放，`flow-bit.c`、`flow-var.c`、`flow-storage.c` 挂接 flowbits、flowvar 与流级存储。

### 6. 注意事项、陷阱与最佳实践

第一类陷阱是三个 memcap 各管一摊、只调其一。`flow.memcap`（或对应流表容量）、`stream.memcap`、`stream.reassembly.memcap` 分别约束流表、TCP 会话、重组缓冲，任何一处触顶都会触发紧急回收或丢弃，但表现可能都是「告警变少」。排障时要同时看 `flow.total` 与 `tcp.reassembly_memuse`，并确认 `max-pending-packets`、`host-mode: auto` 等全局项没有先把包池卡住。第二类陷阱是超时策略失配：`new`、`established`、`closed`、`bypassed` 各状态超时不同，`FlowManager` 与 `FlowRecycler` 的节奏决定了 `FlowNeedsReassembly` 是否来得及用伪包冲刷剩余数据；超时过短会把长连接拦腰截断，过长则让内存与流表持续膨胀。第三类陷阱是可见性：`stream.reassembly.depth` 与 `use-stream-depth` 决定超过深度后是否还向应用层供给数据，TLS 加密流在密钥交换之后同样不可见，因此「文件提取拿不到完整文件」「长流后半段规则不命中」往往不是规则错误，而是重组深度与加密边界共同作用的结果（原理见 06-10、06-12）。

配置细节上有几处高频误用。`stream.midstream` 与 `stream.async-oneside` 决定抓包起点落在流中间、或只看到单方向流量时是否仍尝试建流与解析，镜像部署里若误关会造成大面积漏检；`stream.checksum-validation` 与网卡 checksum offload 组合会让合法流被判异常，应与 06-03 的解码校验一起核对；`stream.inline` 与 `stream.drop-invalid`、`stream.reassembly.memcap-policy`、`stream.reassembly.urgent.policy` 在内联 IPS 下直接影响 verdict 的正确性，改动前要理解 06-12。`stream.bypass` 与 `FLOW_STATE_LOCAL_BYPASSED`、`FLOW_STATE_CAPTURE_BYPASSED` 一旦生效，该流后续不再深度检测，排查「某些大流没有告警」时必须先确认它是不是被 bypass 了。SACK 与重叠段方面，`StreamTcpReassembleConfigEnableOverlapCheck`、`StreamTcpSackUpdatePacket`、`StreamTcpInlineSegmentCompare` 共同决定乱序与重传的处理方式，IDS 与 IPS 对重叠段的容忍度不同，不能照搬同一套假设。

最佳实践同样按分段收敛：先用 `suricata -T` 与 `--dump-config` 确认 `stream.*`、`flow.*` 类配置生效，再用脱敏 pcap 回放建立 `flow.total`、`tcp.reassembly_memuse` 的基线，最后上在线流量用 `suricatasc dump-counters` 做即时快照。看到「无告警」时，顺序应是 `capture` → `decoder` → `flow` → `tcp.reassembly_memuse` → `detect.alert`，而不是直接改规则。任何吞吐、并发流数、丢包率、内存占用结论一律标注「需在目标机型实测」，不给绝对值；调优方法见 08-02，基准见 08-01。另需记住全册边界：Hyperscan 只是可选 MPM 加速、缺失回退 AC；`suricata-update` 是独立工具；Suricata 规则语法兼容 Snort 但有自有扩展，不能宣称 100% 兼容。
再补充一层关于流状态与紧急回收的机制，便于把配置与现象对上。`enum FlowState` 的取值不是装饰：`FLOW_STATE_NEW` 用于握手未完成的半开流，超时最短；`FLOW_STATE_ESTABLISHED` 用于已确认的双向流，超时最长；`FLOW_STATE_CLOSED` 用于已见 FIN 或 RST 的收尾流；`FLOW_STATE_LOCAL_BYPASSED` 与 `FLOW_STATE_CAPTURE_BYPASSED` 分别对应本地与抓包侧 bypass，处于这两种状态的流不再走完整检测链。`FlowUpdateState` 的调用时机因此直接影响 `flow:established` 规则的命中面：若因为 midstream 抓包或校验和误判让流长期停在 `NEW`，所有要求 `established` 的规则都会静默失效。资源紧张时 `FlowGetUsedFlow` 会按紧急策略从超时的流里强制回收一个 `Flow` 给新流用，这解释了一个反直觉现象：流表 memcap 触顶后，老流的 `flow` 事件可能提前出现、新流计数继续增长，但 `tcp.reassembly_memuse` 会因缓冲被提前冲刷而波动。重组窗口侧，`StreamTcpReassembleHandleSegmentUpdateACK` 依据对端 ACK 决定哪些段可以交付给 `StreamTcpReassembleAppLayer`，`StreamTcpReassembleDepthReached` 依据序列号与 `ssn->reassembly_depth` 决定是否停止供给；`src/stream-tcp-sack.c` 的三个函数则保证乱序与重传不会让缓冲无限增长。`TcpSessionSetReassemblyDepth` 允许按会话覆盖深度，这正是 `suricata.yaml.in` 里 `use-stream-depth` 与全局 `#stream-depth` 注释所对应的机制。把这些与 `FlowNeedsReassembly` 的伪包刷新合起来看，就能理解为什么调超时不能只看「流活多久」，还要看「剩余重组数据有没有机会被检测与日志消费」。


### 7. 小结与延伸阅读

本篇把流层归纳为「查找绑定 → 状态推进 → TCP 重组 → 超时回收」四段闭环。`FlowSetupPacket` 与 `FlowGetFlowFromHash` 在带桶锁的 `flow_hash` 上完成查找，`FlowWorker` / `FlowHandlePacket` 完成绑定，`FlowUpdateState` 在 `FLOW_STATE_NEW`、`ESTABLISHED`、`CLOSED`、`LOCAL_BYPASSED`、`CAPTURE_BYPASSED` 之间迁移；`StreamTcp` 建 `TcpSession`，`StreamTcpReassembleHandleSegment` 与 `StreamTcpReassembleAppLayer` 把乱序段拼成连续缓冲并供给应用层，SACK 与内联比较补齐乱序与重叠处理；`FlowManager` / `FlowRecycler` 配合 `FlowNeedsReassembly`、`FlowPseudoPacketGet` 用伪包冲刷剩余数据后安全回收进备用池。三个 tracking 掩码、三个 memcap 与重组深度，是这一层与解码、配置、检测之间的关键接口。

延伸阅读：解码与隧道见 06-03，应用层解析与事务见 06-05，有状态关键字 `flowbits` / `xbits` 见 06-09，文件提取与 `file.data` 见 06-10，IPS verdict 与 `stream.inline` 见 06-12，runmode 与队列见 06-13；按目录查模块能力见 07-02（flow）、07-08（stream-tcp）；按字段查 `Flow` / `FlowBucket` / `FlowKey` 见 05-03，查 `Packet` 见 05-02，查 `TcpSession` / `TcpStream` 需对照 `src/stream-tcp-private.h` 实际版本核验；按参数查 `stream.*`、`flow.*`、`threading` 全键与命令行全集见 04-02、04-03、04-07。统一交叉引用写法：字段见 05-02、05-03、05-07 ｜ 参数见 04-02、04-03、04-07 ｜ 原理见 06-03、06-05、06-09、06-12 ｜ 模块见 07-02、07-08。版本基准始终为「上游 main 快照（2026-11 抓取）」，未核实的具体字段名、函数签名、状态枚举取值与配置键名均已标注「需对照实际版本核验」。

## 06-05 应用层解析框架、协议识别与 Rust parser 接入

### 1. 背景与动机

前四篇把报文从网卡搬到了「连续有序的 TCP 流缓冲」，但检测引擎真正需要的是协议语义：`http.uri`、`http.host`、`dns.query`、`tls.sni`、`file.data` 这类 sticky buffer，以及规则里 `flowbits`、`xbits` 所依赖的事务上下文，都不可能从原始字节里直接 grep 出来。应用层解析框架承担的正是「把字节流翻译成协议字段与事务」这一跃迁。它是整条流水线上抽象层次最高、也最庞杂的一段：几十种协议、双向状态机、事务生命周期、协议识别、日志构造、检测挂接，还要同时容纳 C 与 Rust 两套实现。没有统一的注册与状态框架，每新增一个协议都要把解码、流、检测、输出改一遍，工程上不可维护。

框架化的第二个动因是「端口不再等于协议」。现代网络里 HTTP 可能跑在 8080、8443 甚至任意端口，DNS 可能走 TCP 或 DoH 通道，SMB、QUIC、MQTT 也各有非标准部署。Suricata 因此把协议识别单独做成一层：先按端口给出候选，再用模式匹配与 probing parser 依据首包内容确认，最终得到 `AppProto`。第三个动因是语言边界。本快照的 `rust/src/` 下存在 `applayer.rs`、`frames.rs`、`jsonbuilder.rs`、`ja4.rs` 以及 `dns/`、`http2/`、`smb/`、`ftp/`、`ike/`、`quic/`、`mqtt/`、`ntp/`、`ldap/`、`sip/`、`snmp/`、`tftp/`、`websocket/`、`x509/`、`mime/` 等数十个协议目录，`rust/Cargo.toml.in`、`rust/Cargo.lock.in`、`rust/cbindgen.toml`、`rust/Makefile.am` 与 `rust/src/ffi/`、`rust/sys` 共同构成构建的一部分。Suricata 绝不是纯 C 项目，把 Rust parser 当成可选外挂是原则性错误。

边界再次强调。引擎只对自身解码并重组到的流量做检测，TLS 等加密载荷的记录层明文不可见，能拿到的是握手元数据、证书、SNI、JA3/JA4 一类指纹（`rust/src/ja4.rs`、`src/output-json-tls.c` 相关，具体字段需对照实际版本核验），不能宣称读到 HTTPS 正文；Suricata 不做 IP 转发、不是防火墙、不做路由；规则语法兼容 Snort 但有自有扩展，不能宣称 100% 兼容。本套资料版本基准统一为「上游 main 快照（2026-11 抓取）」，本篇所有函数名与路径均以此快照下 `upstream_src/suricata/suricata-main/` 内真实文件为锚点。

### 2. 核心概念

协议识别由 `src/app-layer-detect-proto.c` 负责。`AppLayerProtoDetectSetup(void)` 与 `AppLayerProtoDetectPrepareState(void)` 完成注册期与线程期准备，`AppLayerProtoDetectRegisterProtocol(AppProto alproto, const char *alproto_name)` 登记协议名，`AppLayerProtoDetectSupportedIpprotos(AppProto alproto, uint8_t *ipprotos)` 声明协议可跑在哪些 IP 协议之上；稳态入口是 `AppProto AppLayerProtoDetectGetProto`（接收识别线程上下文、`Flow`、缓冲与标志等参数），内部可经 `AppLayerProtoDetectPEGetProto(Flow *f, uint8_t flags)` 走 probing parser 路径，`AppLayerProtoDetectReset(Flow *f)` 在识别失败或协议变更时复位，`AppLayerProtoDetectDeSetup` 负责销毁。识别结果 `AppProto`（常写作 `alproto`）写入 `Flow`，成为后续所有解析、检测与日志的分派键。

解析框架由 `src/app-layer-parser.c` 与 `src/app-layer-parser.h` 定义。`AppLayerParserRegisterParser`（按 IP 协议与 `AppProto` 注册解析函数） 注册解析函数，`AppLayerParserRegisterStateFuncs` 注册状态分配/释放，`AppLayerParserRegisterGetTxIterator` 注册事务遍历器；主入口 `AppLayerParserParse(ThreadVars *tv, AppLayerParserThreadCtx *alp_tctx, Flow *f, AppProto alproto, uint8_t flags, const uint8_t *input, uint32_t input_len)` 把连续流缓冲交给对应协议的解析器。辅助函数包括 `AppLayerParserGetTx`、`AppLayerParserGetTxCnt`、`AppLayerParserTransactionsCleanup(Flow *f, const uint8_t pkt_dir)`、`AppLayerParserApplyTxConfig`、`AppLayerParserGetFrameIdByName`、`SCAppLayerParserConfParserEnabled`。类型层面，`AppLayerParserState`（`typedef struct AppLayerParserState_`）、`AppLayerResult`、`AppLayerParserThreadCtx`、`AppLayerGetTxIterTuple`、`AppLayerParserFPtr` 都在 `app-layer-parser.h`，`StreamSlice` 是传给解析器的输入切片，`APP_LAYER_OK`、`APP_LAYER_ERROR`、`APP_LAYER_INCOMPLETE(c,n)` 三个宏定义解析返回值（字段见 05-04）。

事务（tx）与方向是理解框架的关键。解析器按 `STREAM_TOSERVER` / `STREAM_TOCLIENT` 区分方向，为每一次请求/响应对建立一个 tx，检测引擎通过 `DetectRunTx` 在 tx 粒度上做匹配与状态记录，日志模块按 tx 输出 `http`、`dns`、`tls` 等 EVE 事件。缺口（gap）用 `STREAM_GAP` 标记：若解析器未设置 `APP_LAYER_PARSER_OPT_ACCEPT_GAPS`，`AppLayerParserParse` 会走 `SCAppLayerParserTriggerRawStreamInspection`、`StreamTcpDisableAppLayer(f)` 并累计 gap 错误，避免把断裂缓冲当成完整事务。Frame 机制（`src/app-layer-frames.c`、`rust/src/frames.rs`、`AppLayerParserGetFrameIdByName`）则把解析出的记录边界显式暴露给检测与日志。配置上，`SCAppLayerParserConfParserEnabled(const char *ipproto, const char *alproto_name)` 在 `app-layer-parser.c` 中拼接出 `app-layer.protocols.<name>.enabled` 形式的键，`suricata.yaml.in` 第 941 行附近可见 `app-layer:` 段及其 `error-policy` 注释、`app-layer.protocols.smtp.mime.body-md5` 一类样例（键名需对照实际版本核验）。注册入口集中在 `src/app-layer-register.c` 的 `SCAppLayerRegisterProtocolDetection`、`SCAppLayerRegisterParser(const struct AppLayerParser *p, AppProto alproto)`、`SCAppLayerRegisterParserAlias`。交叉引用：字段见 05-04 ｜ 参数见 04-02、04-06 ｜ 模块见 07-03、07-10。

### 4. 关键流程与调用链

注册期先于任何收包发生。`AppLayerProtoDetectSetup` 与 `AppLayerProtoDetectPrepareState` 建立协议识别上下文，各协议通过 `SCAppLayerRegisterProtocolDetection` 登记探测能力、通过 `SCAppLayerRegisterParser` 或 Rust 侧 `AppLayerRegisterParser(&RustParser, alproto)` 登记解析能力；`AppLayerProtoDetectRegisterProtocol` 把 `AppProto` 与可读名字绑定。Rust 静态库在 make 期由 Cargo 构建，cbindgen 依据 `rust/cbindgen.toml` 把 `#[no_mangle] extern "C"` 符号导出成 C 头文件，从而让 `src/app-layer-parser.c` 能像调用本地函数一样注册 Rust parser。这条 FFI 链说明：Rust 组件是构建的一部分，不是运行时动态加载的插件。

稳态链路从重组缓冲开始。`StreamTcpReassembleAppLayer` 把双向连续数据交给 `AppLayerProtoDetectGetProto`，后者结合端口候选、模式匹配与 `AppLayerProtoDetectPEGetProto` 的 probing 结果确定 `alproto`，写入 `Flow`；随后 `AppLayerParserParse` 依 `flags` 中的 `STREAM_TOSERVER` 决定方向、依 `f->protomap` 取 `alp_ctx.ctxs[alproto][f->protomap]`，检查 `p->StateAlloc` 是否存在，按需 `AppLayerParserStateAlloc` 建 `AppLayerParserState`，处理 `STREAM_GAP` 与 `APP_LAYER_PARSER_OPT_ACCEPT_GAPS`，构造 `StreamSlice`，最终调用该协议的 `AppLayerParserFPtr` 得到 `AppLayerResult`。解析产生或更新的 tx 供 `DetectRunTx` 检测、供 logger 输出，`AppLayerParserTransactionsCleanup` 与 `AppLayerParserApplyTxConfig` 负责事务回收与配置应用，`AppLayerParserGetFrameIdByName` 支撑 Frame 级挂接。协议识别、解析、事务与 Rust FFI 边界的关系见图 06-05-01。

再给一组按「前置检查 → 执行 → 验证输出 → 清理」组织的闭环命令，用含明文 HTTP 与 DNS 的样本 pcap 验证应用层事件是否生成。

```bash
# 前置检查：确认配置可加载，查看 app-layer 协议开关
suricata -T -c /etc/suricata/suricata.yaml
suricata --dump-config -c /etc/suricata/suricata.yaml | grep -i "app-layer.protocols" | head -n 8

# 执行：离线回放含 HTTP 与 DNS 的样本 pcap
suricata -c /etc/suricata/suricata.yaml -r /data/http_dns.pcap -l /var/log/suricata/

# 验证输出：统计两类 EVE 事件数量
grep -c '"event_type":"http"' /var/log/suricata/eve.json
grep -c '"event_type":"dns"' /var/log/suricata/eve.json

# 清理：移除本次产生的事件文件
rm -f /var/log/suricata/eve.json
```

典型输出如下（示例输出，具体格式需对照实际版本核验）。

```text
# 示例输出，具体格式需对照实际版本核验
app-layer.protocols.dns.enabled: yes
app-layer.protocols.http.enabled: yes
42
17
{"event_type":"http","flow_id":1902384712,"http":{"hostname":"example.test","url":"/index.html","http_method":"GET","status":200}}
{"event_type":"dns","flow_id":1902384713,"dns":{"type":"query","rrname":"example.test","rrtype":"A"}}
```

逐行判读如下。前两行来自 `--dump-config`：`app-layer.protocols.dns.enabled: yes` 与 `app-layer.protocols.http.enabled: yes` 表明 DNS、HTTP 解析器已启用，正常取值取决于 `suricata.yaml` 的 `app-layer.protocols` 段，若这里是 `no` 或缺省为关闭，则对应 `http.*`、`dns.*` sticky buffer 规则与 EVE 事件都不会产生，这是「明明有流量却没有应用层告警」最常见的根因之一；键名与默认值需对照实际版本核验。中间的 `42` 与 `17` 是两次 `grep -c` 的计数，分别表示 `http`、`dns` 事件条数，正常应随样本中的请求数增长，为零而 `capture` 与 `decoder` 计数正常时，应依次排查协议识别是否成功、`app-layer.protocols.<name>.enabled` 是否开启、重组深度是否截断、是否存在 `STREAM_GAP` 导致事务不完整。后两行是 `eve.json` 事件：`http` 事件中 `event_type` 标明类型、`flow_id` 把同一条流的 `alert`、`flow`、`http` 事件聚合起来、`http.hostname` 与 `url` 给出主机与路径、`http_method` 与 `status` 给出方法与响应码；`dns` 事件中 `type` 区分 query 与 answer、`rrname` 是查询名、`rrtype` 是记录类型。字段名需对照实际版本核验。必须注意：这些是明文 HTTP 与明文 DNS 才有的字段，HTTPS 场景下引擎只能拿到握手元数据、证书、SNI、JA3/JA4 等，读不到记录层明文，不能据本例推断能解析 HTTPS 正文。

### 6. 注意事项、陷阱与最佳实践

第一类陷阱是协议识别失败。非标准端口、加密封装、端口复用都会让「按端口猜协议」失准，此时要靠 `AppLayerProtoDetectGetProto` 的模式匹配与 `AppLayerProtoDetectPEGetProto` 的 probing 兜底；识别不到 `alproto`，`AppLayerParserParse` 就不会被分派，`http.*`、`dns.*`、`tls.*` 类规则与 EVE 事件随之全无。排障时先看 `app-layer` 事件与 `flow.app_proto` 一类字段，再回查流量本身是否被 TLS 加密、是否被隧道改写。第二类陷阱是开关误关：`SCAppLayerParserConfParserEnabled` 读取的 `app-layer.protocols.<name>.enabled` 与 `app-layer:` 段的 `error-policy` 共同决定解析器是否工作与出错时如何处置（取值需对照实际版本核验），为「省资源」批量关掉协议后，检测能力会静默退化，且不会在规则里报错。第三类陷阱是 gap 与重组深度：`STREAM_GAP` 出现且解析器未设置 `APP_LAYER_PARSER_OPT_ACCEPT_GAPS` 时，`AppLayerParserParse` 会触发 raw stream inspection 并 `StreamTcpDisableAppLayer(f)`，丢包因此会转化为事务不完整；`stream.reassembly.depth` 之后的缓冲不再供给应用层，长连接后半段的 `file.data`、文件提取与大事务同样看不到（原理见 06-04、06-10）。

Rust 接入有几条纪律必须守住。`RustParser`、`ParseFn`、`AppLayerRegisterParser` 属于 `rust/src/applayer.rs` 的注册路径，而 `SCAppLayerRegisterProtocolDetection`、`SCAppLayerRegisterParser` 属于 `src/app-layer-register.c` 的 C 侧注册路径，两者职责不同，不要混用或互相替代；`#[no_mangle] extern "C"` 符号与 `rust/cbindgen.toml` 生成的头构成 ABI 边界，升级 Rust 组件或改 `AppLayerParserState` 结构时要关注版本兼容，不能把 Suricata 写成纯 C 项目，也不能把 Rust parser 说成运行时可插拔插件。可见性边界再次强调：TLS 明文不可见，能用于检测与日志的是握手元数据、证书、SNI、JA3/JA4 等，宣称能读 HTTPS 正文属于原则性错误（原理见 06-12）。此外，规则语法兼容 Snort 但有自有扩展、Hyperscan 只是可选 MPM 加速且缺失回退 AC、`suricata-update` 是独立工具，这三条全册边界在本篇同样成立。

最佳实践是「先证明协议被识别，再证明事务被解析，最后看检测与日志」：用 `suricata -T` 与 `--dump-config` 确认 `app-layer.protocols` 开关，用脱敏 pcap 回放建立 `http`、`dns`、`tls` 事件基线，再上在线流量对照 `stats.log` 与 `eve.json`。看到应用层事件缺失时，按 `capture` → `decoder` → `flow` → `tcp.reassembly_memuse` → `app_proto` → `app-layer` 事件 → `detect.alert` 顺序收敛。任何吞吐、事务速率、内存占用结论一律标注「需在目标机型实测」，不给绝对值。配置与规则关键字全集见 04-02、04-05、04-06，模块能力见 07-03、07-10，新增解析器的扩展点见 06-14。
再补充三层容易被跳过的机制。第一层是协议识别的优先级。端口只提供候选，真正决定是否把缓冲交给某个解析器的是模式匹配与 probing parser：`AppLayerProtoDetectGetProto` 先按已知端口与 `AppLayerProtoDetectSupportedIpprotos` 收窄范围，再用 `AppLayerProtoDetectPEGetProto` 依据首包内容做确认，`AppLayerProtoDetectReset` 在识别失败或协议切换时复位 `Flow` 上的识别状态。这意味着一段跑在非标准端口上的明文 HTTP，只要 probing 命中仍能识别；反过来，把 TLS 流量强行标成 `http` 并不会让引擎读到明文，因为记录层内容根本不在可见范围内。识别结果还决定 `app-layer.protocols.<name>.enabled` 是否生效：开关关闭时即便识别出协议，`AppLayerParserParse` 也不会被有效分派。

第二层是事务、检测与日志的顺序。解析器的 `AppLayerParserFPtr` 返回 `AppLayerResult`，`APP_LAYER_INCOMPLETE(c,n)` 表示需要更多数据，框架据此保留 `AppLayerParserState` 等待下一段缓冲；事务一旦完成，`AppLayerParserGetTxCnt` 与 `AppLayerParserRegisterGetTxIterator` 注册的事务遍历器让 `DetectRunTx` 能在 tx 粒度上做匹配、让 logger 按 tx 输出 `http`、`dns`、`tls` 事件，`AppLayerParserTransactionsCleanup` 在合适时机回收已检测已记录的 tx，`AppLayerParserApplyTxConfig` 把逐事务配置套用上去。因此「有 flow 事件但没有 http 事件」往往不是输出模块坏了，而是事务尚未完成或解析器持续返回 incomplete；而 `flow_id` 之所以能把 `alert` 与 `http` 聚合起来，正是因为二者共享同一条 `Flow` 与同一套 tx 编号。

第三层是 FFI 的构建期语义。`rust/Cargo.toml.in` 与 `rust/Cargo.lock.in` 在 configure 与 make 期生成实际清单，`rust/Makefile.am` 把 Cargo 构建出的静态库链进主程序，`rust/cbindgen.toml` 依据 Rust 侧的 `extern "C"` 与 `#[no_mangle]` 符号生成 C 头文件，`rust/src/dns/dns.rs` 里 `SCDnsTxGetQueryName` 一类导出就是被检测关键字与 logger 直接调用的。换句话说，Rust parser 不是运行时动态加载的插件，而是与 C 一起编译进同一个二进制；新增或修改一个 Rust parser，要同时维护 `RustParser` 注册、cbindgen 导出符号与 C 侧调用点，任何一侧 ABI 不匹配都会在构建或链接期暴露。这也解释了为什么 `rust/` 必须随源码一起分发、为什么 Cargo 版本与 cbindgen 是 02-04 构建依赖矩阵的一部分。把这三层与 06-04 的重组供给、06-08 的 inspection 顺序、06-11 的 EVE 聚合连起来，应用层解析框架才算是完整闭环。


### 7. 小结与延伸阅读

本篇把应用层解析收敛为「识别 → 注册 → 解析 → 事务 → 检测与日志」五段。识别由 `AppLayerProtoDetectGetProto` 联合端口、模式与 probing 给出 `AppProto`；注册由 `SCAppLayerRegisterProtocolDetection`、`SCAppLayerRegisterParser` 与 Rust 侧 `AppLayerRegisterParser` 分别铺好 C / Rust 两条路径，经 `rust/cbindgen.toml` 生成头打通 ABI；解析由 `AppLayerParserParse` 在 `AppLayerParserState`、`StreamSlice`、`AppLayerResult` 之上分派到 `AppLayerParserFPtr`，并把方向、gap、深度与事务生命周期一并管理；事务与 Frame 由 `AppLayerParserGetTx`、`AppLayerParserGetTxCnt`、`DetectRunTx`、`app-layer-frames.c` 消费，最终落成 `http`、`dns`、`tls` 等 EVE 事件。`app-layer.protocols.<name>.enabled` 是整个子系统的总开关。

延伸阅读：包处理总览见 06-01、解码见 06-03、流与重组见 06-04、检测求值顺序见 06-08、有状态关键字见 06-09、文件提取见 06-10、EVE 输出见 06-11、IPS 与加密可见性见 06-12、Lua/Rust 扩展与插件见 06-14；按目录查模块能力见 07-03（app-layer）、07-10（rust/）；按字段查 `AppLayerParserState` 与事务结构见 05-04，查 `Flow` 见 05-03；按参数查 `app-layer` 全段、规则关键字与命令行全集见 04-02、04-05、04-06、04-07，Rust 与抓包后端构建见 02-04。统一交叉引用写法：字段见 05-03、05-04 ｜ 参数见 04-02、04-05、04-06、04-07 ｜ 原理见 06-04、06-08、06-11、06-14 ｜ 模块见 07-03、07-10。版本基准始终为「上游 main 快照（2026-11 抓取）」，未核实的具体字段名、函数签名、协议枚举与配置键名均已标注「需对照实际版本核验」。
