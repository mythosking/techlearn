# Suricata 技术资料 · 05 关键数据结构字段详解（分片 A）

## 05-01 全册结构分层与跨文档索引

### 1. 本篇定位与覆盖范围

05 册是全集的「结构体逐字段唯一权威源」，定位为工具书、随查使用，不参与 01 到 03 的线性阅读主线；按 SPEC 第 4 节与总纲第 2 节的去重约定，`Packet`、`Flow`、`Signature`、`DetectEngineCtx` 等结构体一旦需要逐字段展开，只在 05 册给出，其余各册遇到对象成员一律只点名并写「字段见 05-xx」，不得另起字段表。反过来 05 册自身也有两条硬边界：禁止展开抓包、解码、流重组、应用解析、规则编译、检测与输出这些机制的状态机与调用链，遇到「这段怎么工作」写「原理见 06-xx」；禁止重列 `configure` 选项、`suricata.yaml` 段、规则关键字、命令行与返回码的全集，遇到「怎么配」写「参数见 04-xx」。按目录归属哪个模块则写「模块见 07-xx」。本篇作为 05 册的开篇，承担的是「地图」职责：把全册九个篇号覆盖的结构体族按五层分好，给每层指到真实头文件与代表字段，并把查表、查源码、查产物的三步索引法固定下来，让后面 05-02 至 05-09 的逐字段详解有一个可反查的目录。

五层结构是本套资料对 Suricata 对象的统一划分，自下而上依次是：抓包与线程层，对应 `src/threadvars.h`、`src/tm-modules.h`、`src/tm-queues.h`、`src/packet-queue.h`、`src/tmqh-packetpool.h`；包与解码层，对应 `src/decode.h`、`src/decode.c` 及 `src/decode-*` 族；流与应用层，对应 `src/flow.h`、`src/flow-hash.h`、`src/app-layer-parser.h` 与 `src/app-layer-parser.c`；检测层，对应 `src/detect.h`、`src/detect-engine*.c` 与 `src/util-mpm.h`；输出与配置层，对应 `src/output.h`、`src/util-logopenfile.h`、`src/conf.h`、`src/suricata.h`、`src/host.h`。这五层不是运行顺序的严格切分，而是「按对象归属」的检索切分，读者要查某个字段时先判它属于哪层，再翻对应篇号。真实仓库根为 `upstream_src/suricata/suricata-main/`，本篇所有结构体名、代表字段、行号均对照该目录下的头文件与实现核验；版本基准统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准，正文不写绝对值。凡无充分把握的结构体名、成员类型或定义所在文件，一律写「需对照实际版本核验」并给出 `src/decode.h`、`src/flow.h`、`src/detect.h`、`src/app-layer-parser.c` 等可定位目录。

能力边界贯穿全册，落笔不能写反。Suricata 是 IDS / IPS / NSM 引擎，不做 IP 转发、不做路由、不是防火墙，内联阻断依靠 NFQUEUE 或 AF_PACKET 桥接的 verdict；只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见，能拿到的是握手元数据、证书、SNI、JA3 / JA4 一类信息；规则语法兼容 Snort 但有自有扩展，不能宣称百分之百兼容；EVE JSON 是主要输出；Hyperscan 是可选 MPM 加速、缺失回退 AC 等其他实现；`rust/` 与 Cargo 是构建的一部分，大量应用层解析器与 EVE 构造在 Rust 侧；`suricata-update` 是分仓独立工具；多线程不等于加线程必然线性提速。这些边界决定了字段表里的读写时机与关联函数怎样描述，任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」，不给绝对值。本篇按 B 手册字典型七节展开，引用关系统一收束为（参数见 04-02 ｜ 原理见 06-01 ｜ 模块见 07-01）：本篇只给索引与代表字段，不给出任何机制流程，也不列任何参数全集。

### 3. 逐项详解

**抓包与线程层**。`ThreadVars` 定义在 `src/threadvars.h:58`，是每线程变量容器，`tm_func` 是直接传给 `pthread_create` 的流水线入口，`name`、`printable_name`、`type`、`cpu_affinity`、`thread_priority` 记录线程身份与绑核，`inq`、`outq`、`tmqh_in`、`tmqh_out` 指向进出队列与处理器，`tm_slots` 是构成该线程流水线的 `TmSlot` 链，`decode_pq` 是隧道解码产生的临时无锁队列，`flags` 用 `SC_ATOMIC_DECLARE` 声明为原子量，`stats` 是私有计数存储，`storage[]` 是尾部柔性数组。`TmModule` 定义在 `src/tm-modules.h:47`，是一张纯函数指针表：`ThreadInit`、`ThreadDeinit`、`Func`、`PktAcqLoop`、`PktAcqBreakLoop`、`ThreadBusy`、`Management`、`Init`、`DeInit` 加 `cap_flags`、`flags`。`Tmq` 定义在 `src/tm-queues.h:30`，`PacketQueue` 与 `PacketQueueNoLock` 定义在 `src/packet-queue.h` 而非旧资料常写的 `src/tm-queues.h`，前者带 `SCMutex mutex_q` 与 `SCCondT cond_q`，后者无锁且源码注释明确要求两者除锁字段外保持相同布局；`PktPool` 定义在 `src/tmqh-packetpool.h:43`，管理 `head`、`pending_pool`、`return_stack` 三段。这些字段的逐项展开见 05-07 与 05-02，线程与 runmode 的关系原理见 06-13，按目录的模块归属模块见 07-01。

**包与解码层**。`Packet` 定义在 `src/decode.h:527`，是本层乃至全册最核心的对象，源码注释专门说明把 `src`、`dst`、`sp`、`dp`、`proto` 置于结构体顶端是为了能直接把 `Packet` 当哈希键用。其后再排 `recursion_level`、`tunnel_id`、`vlan_id[VLAN_MAX_LAYERS]`、`vlan_idx`、`flowflags`、`sig_mask`、`pkt_hooks`、`ttype`、`tproto`、`flags`、`flow`、`flow_hash`、`ts`，以及一个按编译宏选择的抓包后端变量联合体 `pcap_v`、`afp_v`、`nfq_v`、`dpdk_v`、`plugin_v` 等。`l2`、`l3`、`l4` 是三个分层头结构，`payload` 与 `payload_len` 指向载荷，`alerts`、`events`、`app_layer_events` 承载告警与事件，`root`、`tunnel_rtv_cnt`、`tunnel_tpr_cnt`、`tunnel_verdicted`、`persistent.tunnel_lock` 处理隧道与 verdict，`pool` 与柔性数组 `pkt_data[]` 处理池化与包体存储。`Address` 在 `src/decode.h:130` 用 `family` 加一个 `uint32_t / uint16_t / uint8_t / in6_addr` 四选一联合表示地址，`Port` 在 `src/decode.h:236` 就是 `uint16_t`。`DecodeThreadVars` 在 `src/decode.h:1014`，主体是 `app_tctx` 与一长串 `counter_*` 统计计数器标识。逐字段表见 05-02，解码分派与隧道处理原理见 06-03，模块见 07-01。

**流与应用层**。`Flow` 定义在 `src/flow.h:359`，源码有一段关键注释：地址、端口、协议、递归层构成的「flow header」在初始化后保持静态只读，因此无需加锁即可访问，其余可变字段由 `flow-mutex` 保护，且注释说明选互斥锁而非自旋锁是因为部分流操作代价较高。`Flow` 的 `alproto` 系列、`de_ctx_version`、`sgh_toserver` / `sgh_toclient`、`alparser`、`alstate`、`flowvar`、`fb` 把流与检测、应用解析、存储串在一起，`todstpktcnt`、`tosrcpktcnt`、`todstbytecnt`、`tosrcbytecnt` 做双向计数。`FlowKey` 在 `src/flow.h:311`，`FlowBucket` 在 `src/flow-hash.h:43` 带 `head`、`evicted`、`next_ts` 与一把编译期二选一的锁，`FlowConfig` 在 `src/flow.h:294`，`FlowLookupStruct` 在 `src/flow.h:548`。特别要提醒，`AppLayerParserState` 在 `src/app-layer-parser.h:34` 只有一句 `typedef struct AppLayerParserState_ AppLayerParserState;` 前向声明，属于不透明句柄，内部布局见 `src/app-layer-parser.c:160`，不可依赖其字段；`AppLayerParserProtoCtx` 与 `AppLayerParserCtx` 同样只在该 `.c` 内定义。逐字段见 05-03、05-04，流超时与重组原理见 06-04、应用解析原理见 06-05，模块见 07-02、07-03。

**检测层**。`Signature` 定义在 `src/detect.h:663`，`id`、`gid`、`rev`、`prio`、`action`、`msg`、`class_msg`、`references`、`metadata`、`sig_str` 是规则身份与元信息，`sm_arrays[DETECT_SM_LIST_MAX]`、`app_inspect`、`pkt_inspect`、`frame_inspect` 是编译后的匹配结构，`init_data` 指向仅在初始化期存活的 `SignatureInitData`（`src/detect.h:574`）。`SigMatch` 在 `src/detect.h:331`、`SigMatchData` 在 `src/detect.h:340`，两者是「链式」与「数组式」的匹配条件表示。`DetectEngineCtx` 在 `src/detect.h:966`，是检测引擎主上下文，`sig_list`、`sig_cnt`、`sig_array`、`signum`、`flow_gh[FLOW_STATES]`、`sgh_hash_table`、`mpm_hash_table`、`pattern_hash_table`、`sgh_array` 与一串 `*_inspect_engines`、`*_mpms_list`、`prefilter_hash_table` 构成编译产物，`version`、`ref_cnt`、`next`、`loader_id`、`last_reload` 管生命周期与热重载。`SigGroupHead` 在 `src/detect.h:1730`、`PrefilterEngine` 在 `src/detect.h:1657`、`MpmCtx` 在 `src/util-mpm.h:111`。逐字段见 05-05、05-06，规则编译与检测原理见 06-06 至 06-08，模块见 07-04。

**输出与配置层**。`OutputModule` 在 `src/output.h:56`、`LogFileCtx` 在 `src/util-logopenfile.h:85`、`OutputCtx` 在 `src/tm-modules.h:88`、`SCConfNode` 在 `src/conf.h:37` 用 `name`、`val`、`is_seq`、`final`、`parent`、`head`、`next` 组成配置树，`SCInstance` 在 `src/suricata.h:134` 用 `run_mode`、`pcap_dev`、`sig_file`、`conf_filename`、`daemon`、`offline`、`verbose` 等记录启动姿态，`Host` 在 `src/host.h:58`。本快照中 `src/conf.c` 的读取接口带 `SC` 前缀，为 `SCConfGet`、`SCConfGetInt`、`SCConfGetBool`、`SCConfSet` 等，旧资料常称 `ConfGet` 系列，命名差异需对照实际版本核验。逐字段见 05-08、05-09，EVE 与日志管线原理见 06-11，模块见 07-07、07-09。全册五层的字段表都不在此重复，读者按上表「逐字段详解篇」一列取用即可。

### 4. 典型示例

下面给出一段跨头文件的类型别名摘录，以及一组用于核验结构体定义位置的检索命令。摘录中的地址类型与端口类型均出自 `src/decode.h`，命令用于在本地快照里复核各结构体究竟定义在哪个文件、哪一行。

```c
/* src/decode.h:130-138，Address，跨层共用的地址表示 */
typedef struct Address_ {
    char family;
    union {
        uint32_t        address_un_data32[4];
        uint16_t        address_un_data16[8];
        uint8_t         address_un_data8[16];
        struct in6_addr address_un_in6;
    } address;
} Address;

/* src/decode.h:236，Port 就是 uint16_t */
typedef uint16_t Port;

/* src/app-layer-parser.h:34，仅前向声明，是不透明句柄 */
typedef struct AppLayerParserState_ AppLayerParserState;
```

### 6. 版本差异

本套资料统一以「上游 main 快照（2026-11 抓取）」为版本基准，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当本套资料的版本号；需要说明版本来源时写「具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验」。结构体字段恰是全项目最容易随版本漂移的一类事实：成员会被增删、类型会被换宽度、结构体会在头文件与实现文件之间迁移、尾部的柔性数组与编译期条件字段会随构建开关变化，因此第 2 节与后续各篇给出的行号与字段清单是「这份快照的事实」，不是跨版本永久承诺。

几处已经能在本快照里观察到的差异点值得单列。其一是命名前缀：`src/conf.h` 的结构体叫 `SCConfNode`、读取接口叫 `SCConfGet` 系列，而不少旧资料沿用 `ConfNode` 与 `ConfGet` 的写法，迁移脚本与检索关键字时要按带 `SC` 前缀的实际定义核对。其二是定义所在文件：`PacketQueue` 在本快照定义于 `src/packet-queue.h`，`tm-queues.h` 只提供 `Tmq` 等队列注册结构；旧资料把队列结构体归到 `src/tm-queues.h` 的说法需对照实际版本核验，按本快照grep到的真实行号为准。其三是 `AppLayerParserState` 的封装程度：头文件只留前向声明、真实字段全部收进 `src/app-layer-parser.c`，同一 `.c` 里还定义 `AppLayerParserProtoCtx` 与 `AppLayerParserCtx`，这种 opaque 化意味着字段布局属于实现细节，跨版本更不稳定，代码里绝不能依赖其偏移。其四是编译期条件字段：`Flow` 的锁在 `FLOWLOCK_RWLOCK` 与 `FLOWLOCK_MUTEX` 之间二选一，`FlowBucket` 的锁在 `FBLOCK_MUTEX` 与 `FBLOCK_SPIN` 之间二选一，`Packet` 的抓包后端联合体按 `NFQ`、`AF_PACKET`、`HAVE_DPDK` 等宏取舍，profiling 相关字段受 `PROFILING` 控制，这些字段是否存在取决于构建变体，写字段表时要注明条件而非当作恒定成员。其五是新增语义字段：`DetectEngineCtx`、`Signature`、`Packet` 中都能找到 firewall、hook、exception-policy 相关的较新成员，这类字段的取值与启用条件需对照实际版本核验，且绝不能据 `suricata.yaml.in` 里默认注释关闭的实验性 `firewall` 段把引擎写成网关或路由设备。

### 7. 常见误用与调试

第一类是「把 05 当线性章节通读」或「在别的册里又列一遍字段表」。05 是工具书，正确用法是主线里点名加「字段见 05-xx」，需要时再反查；反过来 06 / 07 / 08 若出现完整结构体字段表就破坏了去重铁律。排查资料一致性时，可把「是否出现逐字段清单」当作判定点：除 05 外的任何册都不应出现以「字段 | 类型 | 含义」开头的七列表。本篇第 2 节的两张表是索引而非逐字段详解，也不得被后续册整表照搬。

第二类是把不透明句柄当成可直接解引用的结构。`AppLayerParserState` 在头文件里只有前向声明，想读 `flags`、`inspect_id` 必须回 `src/app-layer-parser.c` 并通过 `SCAppLayerParserStateSetFlag`、`AppLayerParserGetTransactionInspectId` 一类接口；跨模块直接访问成员会在编译期报「不完整类型」，这类报错的根因不是缺头文件，而是该结构本就不对外暴露布局。同理，`AppLayerParserProtoCtx` 与 `AppLayerParserCtx` 的字段只在实现文件可见，插件与 Rust 侧应走注册接口与 cbindgen 暴露的 FFI 边界，原理见 06-05、模块见 07-10。

第三类是头文件路径与命名记忆出错。把 `PacketQueue` 记成在 `src/tm-queues.h`、把 `ConfNode` 当成不带 `SC` 前缀、把 `AppLayerParserState` 当成头文件里的完整定义，是检索不到字段的三大常见原因；稳妥做法是先 `grep -n "typedef struct X_"` 定位真实文件与行号，再 Read 往下读字段，最后与第 2 节索引表对齐。命令与 RPC 的完整清单参数见 04-07，`suricata --dump-config` 一类校验手段参数见 04-02，本篇不重列。

第四类是混淆「字段」「参数」「机制」「模块」四种问题的权威源，以及把能力边界写反。字段问 05、参数问 04、机制问 06、模块问 07，交叉引用统一写（参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）；若把 `SCInstance.run_mode` 的取值全集写进 05、或把 `DetectEngineCtx` 的分组构建过程写进 05，都是越界。同时守住全册边界：Suricata 不是防火墙、不做转发、加密载荷明文不可见、规则兼容 Snort 但有自有扩展、Hyperscan 为可选加速且缺失回退 AC、`suricata-update` 独立发版、多线程不等于必然线性提速。任何字段读出来的吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」，结构体的字节大小与成员偏移同样不跨版本照搬。字段本身常见问题见 05-02 至 05-09 各篇第 7 节，排错速查见 04-08，诊断决策树见 08-03。

### 1. 本篇定位与覆盖范围

本篇是 05 册中「包与解码层」的逐字段权威源，逐项覆盖 `src/decode.h:527` 的 `Packet`、`src/packet-queue.h` 的 `PacketQueue` 与 `PacketQueueNoLock`、`src/decode.h:1014` 的 `DecodeThreadVars`、`src/tmqh-packetpool.h:43` 的 `PktPool`，以及 `Address`、`Port`、`PacketAlerts`、`PacketEngineEvents`、`PktVar`、`PacketL2` / `PacketL3` / `PacketL4` 这些被 `Packet` 直接或间接引用的辅助类型。回答的是「这个包对象里有哪些成员、各是什么类型、什么阶段被谁写、又在哪被读走」这一类问题。按 SPEC 第 4 节的去重约定，本篇只讲字段含义、内存布局、生命周期与关联函数入口，禁止展开解码分派、隧道封装、VLAN 栈、分片重组这些机制的状态机与调用链，遇到「怎么解码」写「原理见 06-03」；禁止重列抓包后端、线程、地址变量的运行参数全集，遇到「怎么配」写「参数见 04-03」。按目录归属则写「模块见 07-01」。

`Packet` 是整条包处理流水线里承载一切的核心对象：抓包后端把原始字节放进 `pkt_data` 或 `ext_pkt`，解码器逐层填 `l2`、`l3`、`l4` 与 `src`、`dst`、`sp`、`dp`、`proto`，流管理回填 `flow` 与 `flow_hash`，检测引擎写 `alerts`、`action`、`flags`，输出模块读走告警与事件，最后包被归还 `pool`。源码 `src/decode.h:527` 上方有一段注释明确说明把五元组置于结构体顶端是为了「use the Packet as a hash key」，这句注释是理解前几十个字段排布顺序的钥匙：地址、端口、协议、递归层、VLAN 栈这一组构成流查找的键，必须与 `FlowKey` 的排布意图对齐。本篇的字段表按「头部与哈希键」「分层解码与载荷」「告警、隧道与池化」「队列与线程上下文」四组给出，不空表、不省略。

事实纪律与全册一致：唯一事实锚点是 `upstream_src/suricata/suricata-main/`，版本基准「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准但不写绝对值；凡字段名、类型、条件宏无充分把握者写「需对照实际版本核验」并给出 `src/decode.h`、`src/packet-queue.h`、`src/tmqh-packetpool.h` 等可定位目录，禁止编造成员与偏移。能力边界不得写反：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙；只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见，因此 `payload` 对加密会话能拿到的只是密文或握手元数据，不能宣称读到 HTTPS 明文；内联 drop 由 NFQUEUE 或 AF_PACKET 桥接 verdict 执行；性能、容量数字一律标注「需在目标机型实测」。本篇按 B 手册字典型七节展开，引用关系收束为（参数见 04-03 ｜ 原理见 06-03 ｜ 模块见 07-01）：抓包与队列的运行参数见 04-03，解码与隧道机制见 06-03，decode 目录模块见 07-01。

### 3. 逐项详解

**头部哈希键字段组**。`src`、`dst` 是 `Address` 类型，`src/decode.h:130` 显示它用 `char family` 加一个四选一联合表示 IPv4 与 IPv6 地址，联合里同时提供 `address_un_data32[4]`、`address_un_data16[8]`、`address_un_data8[16]` 与 `struct in6_addr`，`COPY_ADDRESS`、`SET_IPV4_SRC_ADDR`、`GET_IPV4_SRC_ADDR_U32` 等宏是读写它的标准入口。`sp`、`dp` 是 `Port`，`src/decode.h:236` 明确 `typedef uint16_t Port`，但它们各自包在一个匿名联合里，与 `icmp_s` / `icmp_d` 的 `type`、`code` 二选一，这是 ICMP 流用 type/code 代替端口的实现，读代码时不能只当端口用。`proto`、`recursion_level`、`tunnel_id`、`vlan_id[VLAN_MAX_LAYERS]`、`vlan_idx` 一起把隧道与 VLAN 维度并入哈希键，源码注释说明目的是防止隧道内外层恰好五元组相同而被攻击或误并流。这一组字段在建包与解码期一次写入后基本只读，字段见 05-03 的 `FlowKey` 与之呼应，解码机制原理见 06-03。

**状态位与流绑定字段**。`flowflags` 记录包在流里的方向，`FLOW_PKT_TOSERVER`、`FLOW_PKT_TOCLIENT` 等宏配合 `PKT_IS_TOSERVER`、`PKT_IS_TOCLIENT` 使用；`app_update_direction` 是应用更新方向枚举；`sig_mask` 是 `SignatureMask`，`pkt_hooks` 是 `SignatureHookPkt` 位集合，二者供检测引擎按掩码剪枝，`pkt_hooks` 与 `Signature` 的 hook 机制呼应（字段见 05-05）。`ttype` 取 `enum PacketTunnelType` 的 none / root / child，`tproto` 取隧道协议枚举。`flags` 是 `uint32_t` 的总状态字，`src/decode.h:1301` 起定义 `PKT_NOPACKET_INSPECTION`、`PKT_HAS_FLOW`、`PKT_WANTS_FLOW`、`PKT_STREAM_EST`、`PKT_IS_FRAGMENT`、`PKT_IS_INVALID`、`PKT_IGNORE_CHECKSUM`、`PKT_ZERO_COPY` 等一系列 `BIT_U32` 位，判定包状态时务必用宏而不是硬编码数字。`flow` 是 `struct Flow_ *`，`flow_hash` 是取模前的哈希原值，`FlowSetupPacket` 先算 `flow_hash` 并置 `PKT_WANTS_FLOW`，流查找成功后回填 `flow` 与 `PKT_HAS_FLOW`；没置 `PKT_HAS_FLOW` 时 `flow` 不可假定有效。`ts` 是 `SCTime_t` 类型的时间戳，类型名需对照实际版本核验，旧资料里的其它时间类型写法不可照搬。

**分层解码指针与载荷**。`l2`、`l3`、`l4` 分别是 `struct PacketL2`、`PacketL3`、`PacketL4`，定义在 `src/decode.h:449`、`456`、`488`，各自含一个类型枚举、一个校验和字段与一个头指针联合，例如 `l3.hdrs` 在 `ip4h`、`ip6h`、`arph` 间选择，`l4.hdrs` 在 `tcph`、`udph`、`icmpv4h`、`sctph`、`greh`、`esph` 等间选择。`payload` 与 `payload_len` 指向传输层载荷，检测引擎的 payload 匹配读的就是这里；要再次强调加密载荷正文不可见。`pktlen` 是包体总长度，`GET_PKT_LEN`、`SET_PKT_LEN` 是宏入口，`ext_pkt` 是当包体超出 `default_packet_size` 预分配时改用的堆缓冲，`GET_PKT_DATA` 宏用 `ext_pkt` 是否为空决定取 `pkt_data` 还是 `ext_pkt`，`pkt_data[]` 是结构体尾部柔性数组。`datalink` 是主机序链路类型，`nb_decoded_layers` 逐层递增用于防止解码层数过多导致栈耗尽。这些字段的读写几乎都在解码期完成，原理见 06-03，模块见 07-01。

**抓包后端变量与函数指针**。`Packet` 中段有一个大匿名联合，按 `HAVE_NFLOG`、`NFQ`、`IPFW`、`AF_PACKET`、`HAVE_NETMAP`、`WINDIVERT`、`HAVE_DPDK`、`HAVE_AF_XDP` 等宏分别编入 `nflog_v`、`nfq_v`、`ipfw_v`、`afp_v`、`netmap_v`、`windivert_v`、`dpdk_v`、`afxdp_v`，另有 `plugin_v[PLUGIN_VAR_SIZE]` 与 `pcap_v`。这意味着同一份源码在不同构建变体里 `Packet` 的布局并不完全相同，任何「偏移量恒定」的假设都不成立。`ReleasePacket` 与 `BypassPacketsFlow` 是两个函数指针，前者在归还期释放包与其数据，后者触发抓包层的 flow bypass，成功返回 1、失败返回 0，二者都由具体抓包后端在分配包时挂上。抓包后端的运行参数参数见 04-03，模块见 07-06。

**告警、事件与主机字段**。`alerts` 是 `PacketAlerts`（`src/decode.h:305`），含 `cnt`、`discarded`、`firewall_discarded`、`suppressed` 四个计数，一个 `PacketAlert *alerts` 数组与一个单独的 `drop` 槽，`PacketAlert`（`src/decode.h:266`）里有 `iid`、`action`、`flags`、`sub_state`、`s`、`tx_id`、`frame_id`、`json_info`，`PACKET_ALERT_FLAG_*` 一组位定义在 `src/decode.h:285` 起。`events` 是 `PacketEngineEvents`（`src/decode.h:328`），用 `cnt` 加定长 `events[PACKET_ENGINE_EVENT_MAX]` 存解码、重组、流事件；`app_layer_events` 是 `AppLayerDecoderEvents *`，在 `src/decode.h:127` 只有前向声明，属于不透明句柄，内部布局需对照实际版本核验。`host_src`、`host_dst` 指向 `Host` 对象（字段见 05-09），`action` 是 IPS 动作，`drop_reason` 把 `enum PacketDropReason` 压成 `uint8_t`，`src/decode.h:402` 起列出 `PKT_DROP_REASON_DECODE_ERROR`、`FLOW_MEMCAP`、`RULES`、`STREAM_MEMCAP`、`NFQ_ERROR`、`FW_RULES` 等取值，判读丢弃原因要按枚举名而非序号。

**隧道、回收与池化字段**。`next`、`prev` 是双链表指针，供队列与池链使用；`root` 在隧道场景指向需要真正下发 verdict 的最外层真实包，注释强调它应始终指向封装链最底层的包；`tunnel_rtv_cnt`、`tunnel_tpr_cnt` 是 ready-to-verdict 与引用计数，与 `tunnel_verdicted` 一起由 `persistent.tunnel_lock` 这把 `SCSpinlock` 保护，注释说明 `persistent` 段的内容跨 `Packet` reinit 存活，因此单独加锁。`tenant_id` 在多租户下写入，0 表示未分配。`pool` 指回分配该包的 `PktPool`，为 NULL 表示该包由 malloc 直接分配；`PktPool`（`src/tmqh-packetpool.h:43`）用 `head` / `cnt` 管本线程空闲链，用 `pending_pool`、`pending_head`、`pending_tail`、`pending_count` 攒批归还，用 `return_stack` 接其他线程归还的包，入口是 `PacketPoolGetPacket` 与 `PacketPoolReturnPacket`。`Packet` 的初始化与回收分别见 `src/packet.c:74` 的 `PacketInit` 与 `src/packet.c:170` 的 `PacketRecycle`，池化机制原理见 06-01。

**队列与线程上下文**。`PacketQueue` 在 `src/packet-queue.h:49`，`top`、`bot`、`len` 加 `mutex_q`、`cond_q`；`PacketQueueNoLock` 在 `src/packet-queue.h:34`，只有 `top`、`bot`、`len`。源码注释特别要求两者「除 mutex_q 与 cond_q 外保持相同布局」，因此不能给无锁版随意增删成员。`DBG_PERF` 宏下多一个 `dbg_maxlen`。出入队入口是 `PacketEnqueue` / `PacketDequeue` 与对应 `NoLock` 版本。`DecodeThreadVars`（`src/decode.h:1014`）由 `src/decode.c:890` 的 `DecodeThreadVarsAlloc` 分配，除 `app_tctx` 外几乎全是 `counter_pkts`、`counter_bytes`、`counter_ipv4`、`counter_tcp`、`counter_vlan`、`counter_defrag_ipv4_fragments` 等 `StatsCounterId` 族计数器标识，用于把解码统计挂到 `stats` 体系，计数项名称需对照实际版本核验，基准方法见 08-01。交叉引用统一为（参数见 04-03 ｜ 原理见 06-03 ｜ 模块见 07-01）。

### 6. 版本差异

本套资料统一以「上游 main 快照（2026-11 抓取）」为版本基准，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当版本号；需要说明版本来源时写「具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验」。`Packet` 是字段最密、也最容易随版本漂移的结构：尾部存储方式、条件编译字段、状态位分配、告警与事件容量都在变化，本篇清单是这份快照的事实，不是跨版本承诺。

几处已能在本快照观察到的差异值得单列。其一是尾部包体存储：`Packet` 以柔性数组 `uint8_t pkt_data[]` 内联存放包体，`ext_pkt` 作为超长时的堆扩展，`GET_PKT_DATA` 宏在二者间选择，旧版本是否用其它字段承载需对照实际版本核验。其二是时间类型：`ts` 用 `SCTime_t`，旧资料常出现别的时间结构写法，迁移代码时要按 `src/decode.h` 实际定义核对。其三是定义文件：`PacketQueue` 与 `PacketQueueNoLock` 在 `src/packet-queue.h`，`Tmq` 在 `src/tm-queues.h`，旧资料把队列结构体笼统归到 `tm-queues.h` 的说法需对照实际版本核验。其四是状态位与枚举：`flags` 的 `BIT_U32` 位定义、`drop_reason` 的 `enum PacketDropReason`、`PacketAlerts` 里的 `firewall_discarded` 与 `PacketAlert` 的 `frame_id`、`sub_state` 等成员，都反映较新的 firewall、frame、hook 语义，这类字段的取值与启用条件需对照实际版本核验，且不得据实验性 firewall 段把引擎写成网关。其五是编译期条件：`NFQ`、`AF_PACKET`、`HAVE_DPDK`、`HAVE_AF_XDP`、`PROFILING` 等宏决定后端联合、`profile` 字段、`dbg_maxlen` 是否编入，写字段表必须注明条件。

由此得到一条通用纪律：任何「字段叫什么」「是什么类型」「在哪个文件」的问题，最终都要回 `src/decode.h`、`src/packet-queue.h`、`src/tmqh-packetpool.h` 用 Read、Grep 核实；凡 SPEC 第 0.1 节未列出或无法核实的文件一律不写进正文。字段含义与生命周期属于 05-02，解码机制见 06-03，模块归属见 07-01，运行参数见 04-03，构建变体差异见 02-02，四者不去重就会互相抄错。

### 7. 常见误用与调试

第一类是「把 `payload` 当成完整原始包、或把 `flow` 当成始终有效」。`payload` 与 `payload_len` 只指向传输层载荷，`pktlen`、`pkt_data`、`ext_pkt` 才是原始包体；`flow` 只有在 `flags` 置 `PKT_HAS_FLOW` 后才有效，未查标志直接解引用会在异常包或隧道内层包上踩空指针。判读顺序应为先看 `flags`，再看 `flowflags` 方向，最后读 `flow` 的成员（字段见 05-03）。加密会话里 `payload` 是密文或握手元数据，不得宣称读到 HTTPS 明文。

第二类是把联合体字段当单一语义。`sp` / `dp` 与 `icmp_s` / `icmp_d` 共用匿名联合，`l3.hdrs`、`l4.hdrs`、`Packet` 中段后端变量都是联合，读之前必须先判 `proto`、`ttype` 或相应编译宏，否则会把 ICMP type/code 当端口、把 IPv6 头当 IPv4 头。结构体偏移因条件编译字段而随构建变体变化，跨模块直接算偏移一律改成「需对照实际版本核验」，字段大小与 `sizeof(Packet)` 需在目标机型实测。

第三类是队列与池化误用。把 `PacketQueueNoLock` 当带锁队列用在跨线程场景会丢数据；以为改 `PacketQueue` 字段不必同步 `PacketQueueNoLock` 会破坏源码注释要求的布局对齐；以为 `pool` 一定非空、直接按池归还却遇到 malloc 分配的包会出错，正确做法是先判 `pool` 是否为 NULL 再走 `ReleasePacket` 或 `PacketPoolReturnPacket`。隧道场景下 verdict 应作用于 `root` 而非内层 `Packet`，`tunnel_rtv_cnt` 等计数受 `persistent.tunnel_lock` 保护，漏判 `tunnel_verdicted` 会重复下发 verdict，原理见 06-12。

第四类是越界与能力边界。05 册不展开解码、隧道、重组机制，遇到「怎么解码」写「原理见 06-03」，不在此列调用链；不重列抓包与线程参数全集，写「参数见 04-03」；decode 目录归属写「模块见 07-01」。同时守住全册边界：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙；规则兼容 Snort 但有自有扩展；Hyperscan 为可选加速、缺失回退 AC；`suricata-update` 独立发版；多线程不等于必然线性提速。任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」。字段级排错可配合 `suricata --build-info` 看构建特性、`--dump-config` 看运行参数，二者命令参数见 04-07，日志与返回码速查见 04-08，诊断决策树见 08-03。

## 05-03 Flow、FlowBucket 与流表结构字段

### 1. 本篇定位与覆盖范围

本篇是 05 册中「流与应用层」里流表一侧的逐字段权威源，逐项覆盖 `src/flow.h:359` 的 `Flow`、`src/flow.h:311` 的 `FlowKey`、`src/flow-hash.h:43` 的 `FlowBucket`，以及 `FlowConfig`（`src/flow.h:294`）、`FlowLookupStruct`（`src/flow.h:548`）、`FlowBypassInfo`（`src/flow.h:536`）、`FlowProtoTimeout`（`src/flow.h:525`）等配套结构。回答的是「一条流对象里有哪些成员、流表怎么组织、哪些字段无需加锁、哪些字段受锁保护」这一类问题。`Flow` 与 `Packet->flow`（字段见 05-02）是双向关联的两端：`Packet` 侧持有 `struct Flow_ *`，`Flow` 侧通过 `fb` 回指所属 `FlowBucket`、通过 `alparser` 与 `alstate`（字段见 05-04）挂接应用解析状态、通过 `sgh_toserver` 与 `sgh_toclient`（字段见 05-05、05-06）缓存检测分组。本篇把这些关联点一并点名，但不展开流超时、TCP 重组、流管理线程的机制流程，遇到「怎么算超时、怎么重组」写「原理见 06-04」；不重列 `flow.memcap`、`flow-timeouts` 等运行参数全集，写「参数见 04-02」；按目录归属写「模块见 07-02」。

`Flow` 定义在 `src/flow.h:359`，其上有一段必须读懂的注释：地址、端口、协议、递归层构成的「flow header」在初始化后保持静态、全生命周期只读，因此无锁即可访问；其余可变字段由 `flow-mutex` 保护，且注释解释选 mutex 而非 spinlock 是因为部分流操作代价较高、自旋不划算。这条「头部只读、其余加锁」的约定是本篇字段表「读写时机」列的主要依据。`FlowKey` 用 `Address` 而非 `FlowAddress` 表示地址，是查表时构造的临时键；`FlowBucket` 是流哈希表的桶，源码 `src/flow-hash.h:39` 注释说明这是一张链式哈希，同一桶内的流挂在链表上，改动链表时整桶加锁。理解这三者分工，就能把「流是什么」「怎么找到流」「流放在哪」三件事分开。

事实纪律与全册一致：唯一事实锚点 `upstream_src/suricata/suricata-main/`，版本基准「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准但不写绝对值；凡字段名、类型、条件宏无充分把握者写「需对照实际版本核验」并给出 `src/flow.h`、`src/flow-hash.h`、`src/flow-*.c` 等可定位目录，禁止编造成员与偏移。能力边界不得写反：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙；只对自身解码并重组到的流量做检测，加密载荷正文不可见；流与重组内存受 memcap 约束，任何容量数字标注「需在目标机型实测」。本篇按 B 手册字典型七节展开，引用关系收束为（参数见 04-02 ｜ 原理见 06-04 ｜ 模块见 07-02）：流的运行参数见 04-02，流管理与重组机制见 06-04，flow 目录模块见 07-02。

### 3. 逐项详解

**头部只读字段组**。`Flow` 用 `FlowAddress`（`src/flow.h:322`）而不是 `Packet` 用的 `Address` 表示 `src` / `dst`，`FlowAddress` 同样是一个 `uint32_t[4]` / `uint16_t[8]` / `uint8_t[16]` 三选一联合，但没有 `family` 字段，这是 `Flow` 与 `FlowKey` 在类型上的第一处差异：`FlowKey` 用带 `family` 的 `Address`，`Flow` 用不带 `family` 的 `FlowAddress`。`sp`、`dp` 各包在匿名联合里，除 `Port` 外还分别提供 `icmp_s` / `icmp_d` 的 `type` / `code`，`sp` 的联合里还多一个 `esp.spi`，与 `Packet` 的对应联合呼应。`proto`、`recursion_level`、`tunnel_id`、`vlan_id[VLAN_MAX_LAYERS]`、`vlan_idx` 把隧道与 VLAN 维度并入流的键，确保隧道内外层、不同 VLAN 的流不会误并。源码注释明确这一组在初始化后静态只读，因此像流哈希比对、日志取五元组这类路径不必加流锁；反过来任何要改它的代码都违背约定。字段见 05-02 的 `Packet` 头部与 05-01 的 `FlowKey.proto`。

**哈希、亲和与超时字段**。`ffr` 是一个 `uint8_t` 联合，内含 `ffr_ts:4` 与 `ffr_tc:4` 两个位域，按方向记录流超时需求；`thread_id[2]` 是 `FlowThreadId`（`src/flow.h:337` 定义为 `uint16_t`）数组，记录 stream / detect 两个方向各自的线程 id，是流亲和的依据，原理见 06-13。`flow_hash` 是取模前的哈希原值，注释说明用于计算对外暴露的 `flow_id`，与 `Packet->flow_hash`（字段见 05-02）同源。`livedev_id` 记入接口，`next` 是桶内哈希链的下一项，`RemoveFromHash`（`src/flow-hash.h:90`）在摘除流时改 `fb->head` 或前驱的 `next` 并把 `f->fb` 清 NULL。`flags` 是 `uint64_t` 通用标志，`file_flags` 记文件跟踪提取，`protodetect_dp` 在 STARTTLS、HTTP CONNECT 这类协议变更场景提供探测用目的端口。`timeout_policy` 是按策略叠加到 `lastts` 上的超时秒数，紧急模式下忽略；`lastts` 是 `SCTime_t`，注释说明在流锁或桶行锁任一下都可读；`startts` 是建流时刻；`flow_state` 取 `enum FlowState`（`src/flow.h:510`）的 `FLOW_STATE_NEW`、`ESTABLISHED`、`CLOSED`、`LOCAL_BYPASSED`，`CAPTURE_OFFLOAD` 下还有 `CAPTURE_BYPASSED`；`tenant_id` 用于多租户超时与伪包。这些状态迁移的机制见 06-04，本篇只登记字段。

**协议识别与应用解析字段**。`probing_parser_toserver_alproto_masks` 与 `probing_parser_toclient_alproto_masks` 是双向探测解析器的协议掩码；`parent_id` 记父流 id，供 FTP 一类产生子流的协议使用；`protoctx` 是 `void *`，通常指向 `TcpSession`（字段见 07-08）；`protomap` 把流映射到对应协议的超时、状态与释放函数，`FlowSetProtoFreeFunc`（`src/flow.h:574`）按协议注册释放回调；`flow_end_flags` 记流结束标志。`alproto`、`alproto_ts`、`alproto_tc` 是 `AppProto` 类型的应用协议与双向协议，`alproto_orig` 记协议变更前的值、`alproto_expect` 记期望升级到的协议，注释举例 STARTTLS。`de_ctx_version` 记首次检测本流的检测引擎上下文版本，注释说明一旦与当前在用的 `DetectEngineCtx` 不匹配，缓存的 `sgh` 指针会被复位，这是规则热重载后流上旧分组失效的字段级依据（字段见 05-05）。`min_ttl_toserver`、`max_ttl_toserver`、`min_ttl_toclient`、`max_ttl_toclient` 四个 `uint8_t` 做双向 TTL 跟踪；`applied_exception_policy` 记已应用的异常策略，取值参数见 04-02。

**应用状态、检测缓存与存储字段**。`alparser` 是 `AppLayerParserState *`，在 `src/app-layer-parser.h:34` 只有前向声明，属于不透明句柄，内部布局见 `src/app-layer-parser.c:160`，不可依赖；`alstate` 是 `void *` 的应用层状态。这两个字段是 `Flow` 与 05-04 的接口。`sgh_toclient` 与 `sgh_toserver` 是 `const struct SigGroupHead_ *`，注释说明只有在相应 `FLOW_SGH_TOCLIENT` / `FLOW_SGH_TOSERVER` 流标志置位时才可用，是检测分组在流上的缓存（字段见 05-06）。`flowvar` 是 `GenericVar *`，供 flowbits、flowvar 一类有状态关键字使用，机制见 06-09。`fb` 回指 `FlowBucket`，使 `RemoveFromHash` 无需重新算哈希就能定位桶。`todstpktcnt`、`tosrcpktcnt` 是 `uint32_t` 包计数，`todstbytecnt`、`tosrcbytecnt` 是 `uint64_t` 字节计数，四者按方向累加。`storage[]` 是尾部柔性 `Storage` 数组，各模块按注册 id 存取，接口在 `src/util-storage.h`。`Flow` 的锁字段 `r` / `m` 在 `FLOWLOCK_RWLOCK` 与 `FLOWLOCK_MUTEX` 两个宏间二选一，源码在两者都未定义时直接 `#error`，因此锁类型是构建期决定、不是恒定成员。

**`FlowKey`、`FlowBucket` 与流表配套结构**。`FlowKey`（`src/flow.h:311`）是查表用的临时键，字段顺序与 `Flow` 头部一致但地址用 `Address`、多了 `livedev_id` 且位置靠后，`FlowKeyGetHash`（`src/flow-hash.h:86`）、`FlowGetFromFlowKey`（`src/flow-hash.h:84`）以它为输入。`FlowBucket`（`src/flow-hash.h:43`）用 `head` 挂活动流、`evicted` 挂待回收的已驱逐流，锁在 `FBLOCK_MUTEX` 的 `SCMutex m` 与 `FBLOCK_SPIN` 的 `SCSpinlock s` 间二选一，`next_ts` 是 `SC_ATOMIC_DECLARE(uint32_t, ...)` 原子量，注释说明 flow-manager 把它设为本桶最早可能超时的秒数、空桶设为 `UINT_MAX`、worker 在加新流或改流状态时清零，整个结构用 `__attribute__((aligned(CLS)))` 按缓存行对齐。`FlowConfig`（`src/flow.h:294`）含 `hash_rand`、`hash_size`、`prealloc`、`timeout_new`、`timeout_est`、`emergency_recovery`、`memcap_policy` 与原子 `memcap`，由 `FlowInitConfig` 加载。`FlowLookupStruct`（`src/flow.h:548`）是每线程查表上下文，含 `spare_queue`、`work_queue` 两个 `FlowQueuePrivate`、`dtv` 与 `emerg_spare_sync_stamp`，`FlowHandlePacket`（`src/flow.h:562`）以它为参数。`FlowBypassInfo`（`src/flow.h:536`）含 `BypassUpdate`、`BypassFree` 两个函数指针与四个方向计数，`FlowProtoTimeout`（`src/flow.h:525`）含 new / est / closed / bypassed 四档超时。建流入口是 `src/flow-util.c:57` 的 `FlowAlloc`，查表主入口是 `src/flow-hash.c:903` 的 `FlowGetFlowFromHash`，准备包的是 `src/flow.h:561` 的 `FlowSetupPacket`，超时与管理分别见 `src/flow-timeout.c`、`src/flow-manager.c`。交叉引用统一为（参数见 04-02 ｜ 原理见 06-04 ｜ 模块见 07-02）。

### 6. 版本差异

本套资料统一以「上游 main 快照（2026-11 抓取）」为版本基准，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当版本号；需要说明版本来源时写「具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验」。`Flow` 与流表结构随版本变化明显：地址类型、锁实现、协议识别字段、检测缓存、异常策略字段都在演进，本篇清单是这份快照的事实，不是跨版本承诺。

几处已能在本快照观察到的差异值得单列。其一是地址类型：`Flow` 用不带 `family` 的 `FlowAddress`，`FlowKey` 用带 `family` 的 `Address`，二者在 `src/flow.h:322` 与 `src/flow.h:311` 紧邻定义，旧资料是否把二者混称需对照实际版本核验。其二是锁实现：`Flow` 在 `FLOWLOCK_RWLOCK` 与 `FLOWLOCK_MUTEX` 间二选一、`FlowBucket` 在 `FBLOCK_MUTEX` 与 `FBLOCK_SPIN` 间二选一，且源码注释说明 `Flow` 特意选 mutex 而非自旋锁，这些是编译期与注释共同决定的事实，跨版本可能调整。其三是时间类型：`lastts`、`startts` 用 `SCTime_t`，旧写法需对照实际版本核验。其四是较新语义字段：`de_ctx_version`、`applied_exception_policy`、`protodetect_dp`、`alproto_expect`、`parent_id`、`probing_parser_*_masks` 等分别对应检测版本失效、异常策略、协议探测、协议升级、期望流与探测解析器，取值与启用条件需对照实际版本核验。其五是缓存行对齐：`FlowBucket` 带 `__attribute__((aligned(CLS)))`，`Flow` 尾部有 `Storage storage[]` 柔性数组，二者都使 `sizeof` 随构建与存储注册数变化，偏移不可跨版本假定。`enum FlowState` 在 `CAPTURE_OFFLOAD` 下多一个 `CAPTURE_BYPASSED` 值，也属条件编入。

由此得到一条通用纪律：任何「字段叫什么」「是什么类型」「定义在哪个文件」的问题，最终都要回 `src/flow.h`、`src/flow-hash.h`、`src/flow-*.c` 用 Read、Grep 核实；凡 SPEC 第 0.1 节未列出或无法核实的文件一律不写进正文。字段含义与生命周期属于 05-03，流与重组机制见 06-04，模块归属见 07-02，运行参数见 04-02，四者不去重就会互相抄错。

### 7. 常见误用与调试

第一类是「把 `Flow` 头部当可写、或把 `FlowKey` 当成 `Flow`」。头部五元组按源码注释初始化后只读，日志与哈希比对走无锁路径；要改方向、状态、协议必须走受锁字段。`FlowKey` 是栈上临时键，地址类型、字段顺序、`livedev_id` 位置都与 `Flow` 不同，把 `FlowKey` 指针强转成 `Flow *` 会读错成员。查表应经 `FlowKeyGetHash`、`FlowGetFromFlowKey` 或 `FlowGetFlowFromHash`，不要自己按字节比对。

第二类是把「不透明句柄」和「双向关联」用错。`alparser` 是 `AppLayerParserState *`，头文件只有前向声明，跨模块直接访问成员会编译报不完整类型，必须通过 05-04 列出的接口；`alstate` 是 `void *`，强转前要确认 `alproto` 与协议上下文类型。`fb` 是 `Flow` 回指桶的指针，`RemoveFromHash` 摘除后会把它清 NULL，摘除后继续用 `f->fb` 定位桶会踩空；`Packet->flow`（字段见 05-02）与 `Flow.fb` 是两条不同方向的关联，不要混为一谈。

第三类是桶链与锁误用。`head` 与 `evicted` 是两条独立链，误把待回收流当活动流会重复检测；改动 `head` 链必须加桶锁，`next_ts` 是原子量，flow-manager 设值、worker 清零，用普通读写会丢更新；`sgh_toserver` / `sgh_toclient` 只有在相应流标志置位时才有效，规则热重载后 `de_ctx_version` 不匹配会触发复位，把缓存当永久有效会用到过期分组，机制见 06-06、06-08。锁类型随编译宏变化，字段表里的 `\|` 表示二选一，判断实际成员要看构建变体。

第四类是越界与能力边界。05 册不展开流超时、TCP 重组、流管理线程的机制流程，遇到「怎么算超时」写「原理见 06-04」；不重列 `flow.memcap`、`flow-timeouts` 等参数全集，写「参数见 04-02」；flow 目录归属写「模块见 07-02」。同时守住全册边界：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙；加密载荷正文不可见；规则兼容 Snort 但有自有扩展；Hyperscan 为可选加速、缺失回退 AC；多线程不等于必然线性提速。任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」。流相关计数可通过 `stats.log` 与 `suricatasc dump-counters` 观察，命令参数见 04-07，日志判读见 04-08，诊断决策树见 08-03。

以上为 05-03 全部字段与调试要点，下一篇转入应用层会话状态结构。

### 3. 逐项详解

**不透明句柄的判定与 `AppLayerParserState` 六字段**。头文件 `src/app-layer-parser.h:34` 只有 `typedef struct AppLayerParserState_ AppLayerParserState;`，没有任何成员；实现文件 `src/app-layer-parser.c:160` 才给出 `struct AppLayerParserState_` 的六个字段。`flags` 是 `uint16_t` 状态位集合，源码在结构体上方标注了 `APP_LAYER_PARSER_` 前缀的 coccinelle 规则，读写必须走 `SCAppLayerParserStateSetFlag` 与 `SCAppLayerParserStateIssetFlag`（`src/app-layer-parser.h:407`、`408`），不得自行按位操作。`inspect_id[2]` 是 `uint64_t` 数组，注释说明「按方向各存一个当前正在被检测的事务」，对应 `AppLayerParserGetTransactionInspectId` 与 `AppLayerParserSetTransactionInspectId`（`src/app-layer-parser.h:330`、`331`）；`log_id` 是 `uint64_t`，注释解释日志不需要按方向拆分，因为只有整个事务完整后才记录，对应 `Get/SetTransactionLogId`（`src/app-layer-parser.h:326`、`328`）；`min_id` 是尚未清理的最小事务 id，供 `AppLayerParserGetMinId`（`src/app-layer-parser.h:327`）查询，事务清理见 `AppLayerParserTransactionsCleanup`（`src/app-layer-parser.h:413`）。`decoder_events` 是 `AppLayerDecoderEvents *`，在 `src/decode.h:127` 也只有前向声明、同属不透明句柄，接口是 `AppLayerParserGetDecoderEvents`（`src/app-layer-parser.h:334`）与 `AppLayerParserHasDecoderEvents`（`src/app-layer-parser.h:376`）。`frames` 是 `FramesContainer *`，由 `AppLayerFramesSetupContainer`（`src/app-layer-parser.c:216`）按需 `SCCalloc` 并挂接，容器内部有 toserver 与 toclient 两组 `Frames`（`src/app-layer-frames.h:64` 定义 `struct Frames`），其布局需对照实际版本核验。这六个字段是「事务进度」的字段级表示，检测与日志各按自己的 id 推进，机制见 06-08、06-11。

**`AppLayerParserProtoCtx` 的回调表分组**。这个结构定义在 `src/app-layer-parser.c:86`，几乎是一张函数指针表，按职责可分四组。第一组是解析与状态生命周期：`Parser[2]` 是按 `STREAM_TOSERVER`、`STREAM_TOCLIENT` 两个方向索引的 `AppLayerParserFPtr`，`StateAlloc`、`StateFree`、`StateTransactionFree`、`LocalStorageAlloc`、`LocalStorageFree` 分别管应用状态、单事务释放与线程本地存储，`first_data_dir` 指明该协议首次期望看到数据的方向。第二组是事务与进度：`StateGetProgress`、`StateGetTxCnt`、`StateGetTx`、`StateGetTxIterator`、`complete_ts`、`complete_tc` 供检测引擎枚举事务并判断完成度，`GetTxFiles` 供文件检测取事务里的文件容器（原理见 06-10）。第三组是事件与配置：`StateGetEventInfoById`、`StateGetEventInfo` 做事件名与 id 互查，`GetStateData`、`GetTxData`、`ApplyTxConfig`、`SetStreamDepthFlag` 提供状态数据、事务数据、配置应用与流深度标志。第四组是 Frame 与子状态：`GetFrameIdByName`、`GetFrameNameById`、`GetStateIdByName`、`GetStateNameById`，加上 `sub_state_mappings` 与 `max_sub_state`（注释说明两者仅对 `FLOW_PROTO_DEFAULT` 设置）。数据字段 `logger`、`logger_bits`、`stream_depth`、`option_flags`、`internal_flags` 分别记日志器、日志位、每协议流深度、选项标志与内部标志，其中 `option_flags` 与 `internal_flags` 各带 `APP_LAYER_PARSER_OPT_`、`APP_LAYER_PARSER_INT_` 前缀的 coccinelle 规则，取值需对照实际版本核验。这些槽位由 `AppLayerParserRegisterParser`（`src/app-layer-parser.c:460`）在启动注册期填入，机制见 06-05。

**`AppLayerParserCtx` 与全局实例**。`AppLayerParserCtx` 定义在 `src/app-layer-parser.c:155`，只有两个字段：`ctxs` 是指向 `AppLayerParserProtoCtx` 二维数组的指针，维度按 `FLOW_PROTO_MAX` 组织，`ctxs_len` 是 `size_t` 长度。`src/app-layer-parser.c:251` 声明了 `static AppLayerParserCtx alp_ctx;` 作为全局单例，源码注释还写着「2.0 之后考虑把它挪到 app-layer.c」，这句注释本身就提示该结构的位置随版本可能变化，需对照实际版本核验。理解层次很关键：`AppLayerParserCtx` 是「全局注册表的容器」，`AppLayerParserProtoCtx` 是「某协议某 IP 层的回调表」，`AppLayerParserState` 是「某条流上的解析状态实例」，三者分别是表、表项、实例，不要把 `ctxs` 当成流状态。

**注册、解析与清理入口**。`AppLayerParserRegisterParser`（`src/app-layer-parser.c:460`）把协议解析器的实现填进 `alp_ctx.ctxs` 对应表项；`AppLayerParserStateAlloc`（`src/app-layer-parser.c:260`，头文件声明在 `src/app-layer-parser.h:410`）与 `AppLayerParserStateFree`（`src/app-layer-parser.h:411`）管状态实例的一生；`AppLayerParserParse`（实现 `src/app-layer-parser.c:1528`，声明 `src/app-layer-parser.h:373`）是每批重组数据进入解析的主入口，签名以本地头文件为准，需对照实际版本核验。清理侧有 `AppLayerParserStateProtoCleanup` 与 `AppLayerParserStateCleanup`（`src/app-layer-parser.h:401`、`403`）以及 `AppLayerParserTransactionsCleanup`（`src/app-layer-parser.h:413`），它们与 `Flow` 拆除路径配合；`AppLayerParserSetEOF`（`src/app-layer-parser.h:375`）标记流结束。协议是否启用、是否支持文件、首数据方向等查询接口集中在 `src/app-layer-parser.h:355` 至 `383` 一带，如 `AppLayerParserGetTransactionActive`、`AppLayerParserGetFirstDataDir`、`AppLayerParserSupportsFiles`、`AppLayerParserIsEnabled`。本篇只登记入口，不展开解析状态机，原理见 06-05。

**Flow 挂接与 Rust 接入**。`Flow` 侧的 `alparser`（`src/flow.h:485`）与 `alstate`（`src/flow.h:486`）是 05-03 与本层的接口：`alparser` 指向本篇的 `AppLayerParserState`，`alstate` 是 `void *` 的协议私有状态，强转前必须先用 `Flow->alproto` 判定协议。Rust 侧的大量解析器经 cbindgen 暴露 FFI：已核验存在 `rust/src/applayer.rs`、`rust/cbindgen.toml` 以及 `rust/src/dns/`、`rust/src/http2/` 等协议目录，C 侧通过生成的头文件调用 Rust 实现的解析与事务回调，注册表项最终仍落到 `AppLayerParserProtoCtx`。这印证 `rust/` 与 Cargo 是构建的一部分、Suricata 不是纯 C 项目；具体哪些协议在 Rust 侧、cbindgen 生成哪些符号需对照 `rust/cbindgen.toml` 与 `rust/src/` 实际版本核验，模块见 07-10。协议识别由 `src/app-layer-detect-proto.c` 承担，字段与机制分属 05 与 06，交叉引用统一为（参数见 04-02 ｜ 原理见 06-05 ｜ 模块见 07-03）。

### 6. 版本差异

本套资料统一以「上游 main 快照（2026-11 抓取）」为版本基准，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当版本号；需要说明版本来源时写「具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验」。应用层解析结构是 Suricata 里 Rust 化最活跃的一块，字段与接口随版本漂移尤其明显，本篇清单是这份快照的事实，不是跨版本承诺。

几处已能在本快照观察到的差异值得单列。其一是 opaque 化程度：`AppLayerParserState` 在头文件只留前向声明、六个字段全部收进 `src/app-layer-parser.c:160`，旧资料若给出头文件里的完整结构定义，需对照实际版本核验，不能照搬。其二是全局实例位置：`src/app-layer-parser.c:251` 的 `static AppLayerParserCtx alp_ctx;` 上方源码注释写着「2.0 之后考虑把它挪到 app-layer.c」，这句注释本身就是位置可能变化的提示。其三是事务与 Frame 语义：`inspect_id[2]`、`log_id`、`min_id`、`frames` 反映的是较新的按事务检测与 Frame 化模型，旧版本是否有同名成员、Frame 容器如何组织需对照实际版本核验。其四是子状态与流深度：`sub_state_mappings`、`max_sub_state`、`stream_depth`、`option_flags`、`internal_flags` 以及 `GetStateIdByName` 一类接口对应 HTTP/2 等带子状态协议与流深度控制，取值与启用条件需对照实际版本核验。其五是 Rust 边界：`rust/src/applayer.rs`、`rust/cbindgen.toml` 与 `rust/src/dns/`、`rust/src/http2/` 等目录已核验存在，但哪些协议在 Rust 侧、cbindgen 生成哪些符号随版本变化，需对照 `rust/src/` 实际版本核验；C 与 Rust 的 FFI 头由 cbindgen 在构建期生成，不得凭印象写函数名。

### 7. 常见误用与调试

第一类是「把不透明句柄当普通结构」。在只 include 了 `src/app-layer-parser.h` 的模块里写 `pstate->flags` 或对 `AppLayerParserState` 做 `sizeof`，编译器会报不完整类型；正确做法是用 `SCAppLayerParserStateSetFlag`、`SCAppLayerParserStateIssetFlag`、`AppLayerParserGetTransactionInspectId` 一类接口。这类报错的根因不是漏 include，而是该结构本就不对外暴露布局，为读一个字段去 include `.c` 会破坏封装并引入重复定义。`AppLayerDecoderEvents` 同样只有前向声明，事件读写走 `AppLayerParserGetDecoderEvents` 与 `AppLayerParserHasDecoderEvents`。

第二类是混淆三个层次的容器。把 `AppLayerParserCtx.ctxs` 当成流上的状态、把 `AppLayerParserProtoCtx` 当成某条流的实例、把 `AppLayerParserState` 当成全局注册表，是读代码时最易犯的错；三者分别是全局注册表、协议回调表项、流级状态实例。`Flow->alstate` 是 `void *`，未先判 `Flow->alproto` 就强转到具体协议状态会读错内存；`frames` 可能为 NULL，未走 `AppLayerFramesSetupContainer` 就解引用会踩空指针。事务 id 的三个字段语义也不同：`inspect_id` 按方向、`log_id` 只在事务完整后推进、`min_id` 是清理下界，混用会导致事务重复检测或提前清理。

第三类是 Rust 与 C 边界误判。把 Suricata 写成纯 C 项目、或以为 Rust parser 不参与 `src/` 编译，都与事实相反：`rust/` 与 Cargo 是构建的一部分，Rust 解析与日志实现经 `rust/cbindgen.toml` 生成 FFI 头供 C 侧注册，具体符号需对照实际版本核验。反过来，把 `rust/src/` 里某个文件当成 `src/` 下的 C 结构去 grep 字段也会扑空。协议识别由 `src/app-layer-detect-proto.c` 承担，其机制原理见 06-05，本篇不展开调用链。

第四类是越界与能力边界。05 册不展开协议识别、事务推进、Frame 产生的状态机，遇「怎么识别、怎么推进」写「原理见 06-05」；不重列 `app-layer.protocols`、`app-layer.error-policy` 等参数全集，写「参数见 04-02」；目录归属写「模块见 07-03」、Rust 生态写「模块见 07-10」。同时守住全册边界：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙；只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见，HTTP、DNS 解析器处理的是重组后的明文协议数据，不得宣称能读 HTTPS 正文；规则兼容 Snort 但有自有扩展；Hyperscan 为可选加速、缺失回退 AC；`suricata-update` 独立发版；多线程不等于必然线性提速。任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」。协议相关错误可结合 `suricata -T` 规则自检与 `suricata.log` 判读，命令参数见 04-07、日志速查见 04-08，诊断决策树见 08-03。

### 1. 本篇定位与覆盖范围

本篇是 05 册「检测层」的逐字段权威源，逐项覆盖 `src/detect.h:663` 的 `Signature`、`src/detect.h:331` 的 `SigMatch` 与 `src/detect.h:340` 的 `SigMatchData`、`src/detect.h:574` 的 `SignatureInitData`、`src/detect.h:966` 的 `DetectEngineCtx`，并点名 `src/detect.h:1730` 的 `SigGroupHead`、`src/detect.h:1657` 的 `PrefilterEngine`、`src/util-mpm.h:111` 的 `MpmCtx` 作为分组与预过滤结构的入口（逐字段展开留给 05-06）。回答的是「一条规则编译成什么对象、匹配条件怎么挂、检测引擎上下文里装了哪些表」这一类问题。按 SPEC 第 4 节去重约定，本篇只讲字段含义、内存布局、生命周期与关联函数入口，禁止展开规则解析、签名分组、MPM 构建、SigMatch 求值顺序这些机制流程，遇「怎么编译、怎么匹配」写「原理见 06-06」至「原理见 06-08」；禁止重列规则关键字全集，写「参数见 04-05」、「参数见 04-06」；按目录归属写「模块见 07-04」。

三个对象的关系可以先一句话理清：`Signature` 是一条规则编译后的容器，`SigMatch` 是解析期挂上去的链式匹配条件、`SigMatchData` 是编译后供匹配期遍历的紧凑数组表示，`SignatureInitData` 是只在初始化期存活的施工脚手架，而 `DetectEngineCtx` 是容纳全部签名与分组、MPM、预过滤、检查引擎产物的总上下文。`src/detect-parse.c:311` 的 `SigMatchAlloc` 与 `src/detect-parse.c:2314` 的 `SigAlloc` 是构造入口，`src/detect-engine.c:2874` 的 `DetectEngineCtxInit` 是上下文构造入口，`DetectEngineCtxFree` 在多个模块的单测与释放路径里出现，释放与重载机制原理见 06-06。

事实纪律与全册一致：唯一事实锚点 `upstream_src/suricata/suricata-main/`，版本基准「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准但不写绝对值；凡字段名、类型、条件宏无充分把握者写「需对照实际版本核验」并给出 `src/detect.h`、`src/detect-parse.c`、`src/detect-engine*.c` 等可定位目录，禁止编造成员与偏移。能力边界不得写反：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙；规则语法兼容 Snort 但有自有扩展，不能宣称百分之百兼容；Hyperscan 是可选 MPM 加速、缺失回退 AC 等其他实现，`mpm_matcher`、`spm_matcher` 反映的是可选实现的选择结果而非唯一依赖；`rust/` 与 Cargo 是构建的一部分；加密载荷正文不可见；性能数字一律标注「需在目标机型实测」。本篇按 B 手册字典型七节展开，引用关系收束为（参数见 04-06 ｜ 原理见 06-06 ｜ 模块见 07-04）：规则关键字参数见 04-05、04-06，规则编译与检测机制见 06-06 至 06-08，detect 目录模块见 07-04。

### 3. 逐项详解

**`Signature` 的规则身份与规则头字段**。`flags` 是 `uint32_t` 的 `SIG_FLAG_` 位集合，`type` 是 `enum SignatureType`，`alproto` 是 `AppProto`，`dsize_low`、`dsize_high`、`dsize_mode` 对应 `dsize` 关键字编译结果，`mask` 是 `SignatureMask`、`iid` 是 `SigIntId` 内部 id（注释说明用于排序），`action` 是 `uint8_t` 动作，`file_flags` 记文件标志，`proto` 是 `DetectProto *` 且源码注释说明可为空表示跳过协议检查，`action_scope` 取 `enum ActionScope`。`addr_dst_match4_cnt`、`addr_src_match4_cnt`、`addr_dst_match6_cnt`、`addr_src_match6_cnt` 四个 `uint16_t` 是编译后地址匹配数组的计数，与 `addr_dst_match4`、`addr_src_match4`、`addr_dst_match6`、`addr_src_match6` 四组指针配套。`class_id`、`class_msg`、`references`、`metadata` 来自 `classtype`、`reference`、`metadata` 等 meta 关键字（参数见 04-05），`id`、`gid`、`rev`、`prio` 分别是 `sid`、`gid`、`rev`、`priority`，`sp`、`dp` 是规则头端口，`msg` 是规则消息，`sig_str` 保留原始规则串供错误定位。`next` 把全部签名串成链表，`DetectEngineCtx.sig_list` 就指向链头。规则语法兼容 Snort 但有自有扩展，不能宣称百分之百兼容。

**`Signature` 的匹配结构与初始化数据**。`app_inspect`、`pkt_inspect`、`frame_inspect` 是三类检查引擎指针，`sm_arrays[DETECT_SM_LIST_MAX]` 是 `SigMatchData *` 数组，是编译后供匹配期遍历的紧凑表示，`filestore_ctx` 是 filestore 上下文，`init_data` 指向 `SignatureInitData *`。`SignatureInitData`（`src/detect.h:574`）是「只在初始化期存活」的施工数据：`hook` 记规则钩子，`sm_cnt` 累加匹配条件数用于分配 `SigMatch::idx`，`negated` 记选项前缀的取反，`src_contains_negation`、`dst_contains_negation`、`src_contains_range`、`dst_contains_range` 用于判断是否跳过 ip-only 引擎，`has_possible_prefilter` 记是否存在可预过滤的条件，`init_flags` 是 `SIG_FLAG_INIT_` 位，`alprotos[SIG_ALPROTO_MAX]` 是多协议掩码，`dsize_sm`、`mpm_sm`、`prefilter_sm` 分别指向 dsize、fast pattern、预过滤条件，`mpm_sm_list`、`list`、`list_set` 记录当前所在匹配链，`total_flowbits` 统计 flowbits 引用数，`transforms`、`proto`、`score`、`src`、`dst`、`buffers`、`buffer_index`、`buffers_size`、`curbuf`、`max_content_list_id`、`is_rule_state_dependant` 与 `rule_state_*` 数组管转换、规则打分、缓冲区与规则间状态依赖，`firewall_rule` 标记 firewall 规则（语义需对照实际版本核验）。理解要点是：`init_data` 在编译完成后即释放，运行期读的是 `sm_arrays` 而不是 `smlists`。

**`SigMatch` 与 `SigMatchData` 的两种表示**。`SigMatch`（`src/detect.h:331`）是解析期的双向链节点，`type` 是关键字类型号，`idx` 是该条件在签名内的位置，`ctx` 是 `SigMatchCtx *` 关键字私有数据，`next`、`prev` 串链；要注意 `src/detect.h:326` 的 `SigMatchCtx` 定义里只有一个占位成员 `int foo`，真实关键字数据由各关键字自己分配并强转，属于「约定式不透明」，具体布局需对照实际版本核验。`SigMatchData`（`src/detect.h:340`）是匹配期的紧凑数组元素，只有 `type`、`is_last`、`ctx` 三字段，去掉了链指针与 `idx`，`is_last` 供遍历终止。两者由 `src/detect-parse.c:311` 的 `SigMatchAlloc` 与编译期转换衔接，`Signature` 由 `src/detect-parse.c:2314` 的 `SigAlloc` 分配。关键字类型注册与匹配顺序机制见 06-08，本篇只登记字段。

**`DetectEngineCtx` 的签名表与分组产物**。上下文起始几项是 `failure_fatal`、`flags`（注释说只有 `DE_QUIET`）、`mpm_matcher`、`max_flowbits`、`tenant_id`、`mpm_cfg`、`spm_matcher`，其中 `mpm_matcher`、`spm_matcher` 反映 MPM 与 SPM 匹配器选择，Hyperscan 是可选加速、缺失回退 AC 等其他实现，不能写成必需依赖。`sig_list`、`sig_cnt`、`sig_array`、`sig_array_len`、`signum` 是签名集合的两种视图：链表与按 `iid` 索引的数组。`flow_gh[FLOW_STATES]` 是主流状态分组，`sgh_hash_table`、`mpm_hash_table`、`pattern_hash_table`、`dup_sig_hash_table` 是编译期各阶段用的哈希表，`io_ctx` 是 IP-only 引擎上下文，`sgh_array`、`sgh_array_cnt`、`sgh_array_size` 是注释说明「Stage4 遍历用」的全部分组数组，`decoder_event_sgh`、`eth_non_ip_sgh` 是无协议可查时的特殊分组，`pre_stream_sgh[2]`、`pre_flow_sgh` 是前置钩子分组。这些字段的具体构建顺序原理见 06-06，逐字段展开见 05-06。

**`DetectEngineCtx` 的引擎注册、配置与生命周期**。`inspection_recursion_limit`、`guess_applayer`、`guess_applayer_log_limit`、`max_fb_id`、`byte_extract_max_local_id`、`base64_decode_max_len`、`sgh_mpm_ctx_cnf`、`prefilter_setting` 是各类限制与开关；`app_inspect_engines`、`pkt_inspect_engines`、`frame_inspect_engines` 与 `app_mpms_list`、`pkt_mpms_list`、`frame_mpms_list` 及各自的 `_cnt` 是三类检查引擎与 MPM 注册链；`prefilter_id`、`prefilter_hash_table` 管预过滤引擎；`keyword_hash`、`keyword_id`、`sm_types_prefilter`、`sm_types_silent_error` 管关键字注册与线程本地上下文；`class_conf_ht`、`reference_conf_ht` 及配套的 `pcre2_code` 正则对象管分类与引用配置解析；`dport_hash_table`、`tcp_priorityports`、`udp_priorityports`、`address_table`、`metadata_table`、`buffer_type_hash_name`、`buffer_type_hash_id` 是端口、地址、元数据、缓冲类型的索引表。生命周期字段里 `version` 注释说明「重载时递增」，与 `Flow.de_ctx_version`（字段见 05-03）配合使流上缓存的 `sgh` 失效；`ref_cnt` 记有多少方在引用该上下文，`next` 把它挂在 master 的活动或空闲链，`loader_id` 记拥有它的加载线程，`last_reload` 记上次规则集重载时刻，`type` 是 `enum DetectEngineType`，`config_prefix[64]`、`tenant_path`、`ea`、`sig_stat`、`requirements`、`filestore_cnt`、`fp_support_smlist_list`、`RateFilterCallback`、`PreStreamHook`、`PreFlowHook` 等记录配置前缀、引擎分析、加载统计、速率过滤回调与钩子。构造入口是 `src/detect-engine.c:2874` 的 `DetectEngineCtxInit`，释放入口 `DetectEngineCtxFree` 在多个模块与单测中出现，重载与释放机制原理见 06-06。

**关联结构入口与交叉引用**。`SigGroupHead`（`src/detect.h:1730`）、`PrefilterEngine`（`src/detect.h:1657`）、`MpmCtx`（`src/util-mpm.h:111`）、`DetectEngineThreadCtx`（`src/detect.h:1295`）是本篇点名但不展开的四类结构，逐字段见 05-06 与 05-07；`Packet.alerts`（字段见 05-02）承载的就是 `Signature` 命中的结果；`Flow.sgh_toserver`、`sgh_toclient`（字段见 05-03）缓存的是 `SigGroupHead`。交叉引用统一为（参数见 04-05 ｜ 参数见 04-06 ｜ 原理见 06-06 ｜ 模块见 07-04）：规则关键字参数见 04-05、04-06，规则编译、MPM 与检测机制见 06-06 至 06-08，detect 目录模块见 07-04，MPM 模块见 07-05。

### 6. 版本差异

本套资料统一以「上游 main 快照（2026-11 抓取）」为版本基准，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当版本号；需要说明版本来源时写「具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验」。检测层结构随规则语言与引擎特性演进最快，本篇清单是这份快照的事实，不是跨版本承诺。

几处已能在本快照观察到的差异值得单列。其一是编译产物表示：`SigMatch` 链与 `SigMatchData` 数组并存、`SignatureInitData` 作为独立施工结构、编译后 `init_data` 释放，这套分层是较新的组织方式，旧资料是否把匹配条件直接挂在 `Signature` 上需对照实际版本核验。其二是 firewall 与 hook 语义：`action_scope`、`app_progress_hook`、`sub_state`、`detect_table`、`firewall_rule`、`fw_policies`、`PreStreamHook`、`PreFlowHook`、`pre_stream_sgh[2]`、`pre_flow_sgh` 等字段对应实验性 firewall 与前置钩子能力，`suricata.yaml.in` 里默认注释关闭的 `firewall` 段属实验性选项，其语义需对照实际版本核验，绝不能据此把引擎写成网关或路由设备。其三是匹配器可选性：`mpm_matcher`、`spm_matcher`、`prefilter_setting` 与 `mpm_ctx_factory_container` 反映 AC、AC-KS、Hyperscan 等多实现并存，Hyperscan 缺失回退 AC，`configure.ac` 的开关与雅名需对照实际版本核验。其四是条件编入字段：`profiling_id` 受 `PROFILE_RULES` 控制，`profile_ctx`、`profile_keyword_ctx`、`profile_sgh_ctx` 等受 `PROFILING` 控制，`RegisterUnittests` 一类受 `UNITTESTS` 控制，字段是否存在取决于构建变体。其五是版本与生命周期字段：`version`、`ref_cnt`、`loader_id`、`last_reload`、`next` 支撑热重载与 master 链表，`version` 与 `Flow.de_ctx_version` 的联动机制需对照实际版本核验。

由此得到一条通用纪律：任何「字段叫什么」「是什么类型」「在哪个文件」的问题，最终都要回 `src/detect.h`、`src/detect-parse.c`、`src/detect-engine*.c`、`src/util-mpm.h` 用 Read、Grep 核实；凡 SPEC 第 0.1 节未列出或无法核实的文件一律不写进正文。字段含义与生命周期属于 05-05、05-06，机制见 06-06 至 06-08，模块归属见 07-04、07-05，参数见 04-05、04-06，四者不去重就会互相抄错。

### 7. 常见误用与调试

第一类是「把初始化期结构用到运行期」。`SignatureInitData` 只在编译期存活，`smlists`、`mpm_sm`、`prefilter_sm`、`buffers` 这类字段在规则编译完成后随 `init_data` 释放；匹配期读的是 `Signature.sm_arrays` 里的 `SigMatchData` 数组，`is_last` 是遍历终止依据。反过来在解析期直接读 `sm_arrays` 也会扑空，因为它尚未构建。判读顺序应是先看当前处于 `SigAlloc` 解析期还是编译完成后的检测期，再决定读哪套字段。

第二类是把匹配条件表示与私有数据用错。`SigMatch` 与 `SigMatchData` 的 `type` 是关键字类型号，`ctx` 是 `SigMatchCtx *`，而 `src/detect.h:326` 的 `SigMatchCtx` 只有一个占位成员，真实数据由各关键字 Setup 分配并强转，把它当固定布局直接解引用会读错；关键字类型注册与求值顺序原理见 06-08。规则语法兼容 Snort 但有自有扩展，不能把 `action`、`proto`、`sp`、`dp` 的取值全集当成 Snort 的子集照抄，关键字全集参数见 04-05、04-06。

第三类是上下文生命周期与版本失效误用。`ref_cnt` 归零才走 `DetectEngineCtxFree`，`next` 把上下文挂在 master 活动或空闲链，`loader_id` 记加载线程，热重载靠 `version` 递增触发；把 `version` 当静态值、把 `Flow` 上缓存的 `sgh` 当永久有效，会在规则重载后用到过期分组（字段见 05-03、05-06）。`sig_list` 与 `sig_array` 是同一签名集合的两种视图，`sig_array` 按 `iid` 索引，混用下标与内部 id 会取错签名。`mpm_matcher` 写成必需 Hyperscan、或把 `spm_matcher` 写成唯一实现，都违反能力边界，原理见 06-07。

第四类是越界与能力边界。05 册不展开规则解析、分组构建、MPM 与 SigMatch 求值的机制流程，遇「怎么编译、怎么匹配」写「原理见 06-06」至「原理见 06-08」，分组与预过滤结构的逐字段展开留给 05-06；不重列规则关键字全集，写「参数见 04-05」、「参数见 04-06」；目录归属写「模块见 07-04」。同时守住全册边界：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙；只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见；规则兼容 Snort 但有自有扩展，不能宣称百分之百兼容；Hyperscan 为可选加速、缺失回退 AC；`rust/` 与 Cargo 是构建的一部分；`suricata-update` 独立发版；多线程不等于必然线性提速。任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」。规则加载错误可用 `suricata -T` 与 `suricata.log` 判读，命令参数见 04-07、返回码与错误速查见 04-08，诊断决策树见 08-03。
