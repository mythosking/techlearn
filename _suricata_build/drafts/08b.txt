# Suricata 技术资料 · 08 运维、性能基准与排障（分片 B）
## 08-04 故障案例库：从规则加载失败到吞吐骤降

### 1. 目标与拓扑

本篇交付的不是零散的排错技巧，而是六个可复现、可取证、可闭环的故障案例。08-01 给出可复现的基准方法，08-02 给出单变量调优的四个维度，08-03 给出六类故障的判定顺序决策树，本篇则把判定顺序落到具体现场：每个案例都写全「现象与影响面、复现步骤、证据、根因、修复动作、验证方法」六要素，让值班同学能照着复现、照着取证、照着验收。三篇是分工关系而非重复：08-03 回答「先查哪一层、凭什么排除」，本篇回答「这一层具体报什么文本、改哪个键、改完看哪一行输出才算好」。全册遵循同一条纪律——不重列任何参数全集，本场景只给最小必要配置，完整清单见 04-02 / 04-03 / 04-04 / 04-07；结构体逐字段定义见 05-xx；流水线、规则编译、EVE、IPS、runmode 的机制见 06-xx；模块归属见 07-xx。统一交叉引用写作（字段见 05-05 ｜ 参数见 04-02 ｜ 原理见 06-06 ｜ 模块见 07-04）。

动手之前先立四条不能写反的能力边界，它们直接决定案例的判读方向。其一，Suricata 是 IDS / IPS / NSM 引擎，不做 IP 转发、不做路由、不是防火墙；IDS 旁路模式只告警不丢弃，内联阻断依靠 NFQUEUE / AF_PACKET 桥接的 verdict，由内核或桥接对端决定是否放行（原理见 06-12）。把「IDS 旁路没有 drop 日志」当作「没告警」是概念混淆。其二，引擎只对自身解码并重组到的流量做检测，TLS 等加密载荷不可见，能拿到的是握手元数据、证书、SNI、JA3 一类信息（字段需对照实际版本核验），不能宣称能读到 HTTPS 明文正文；案例③里若期望在加密正文里命中关键字，那不是故障而是边界。其三，规则语法兼容 Snort 但有自有扩展（`src/detect-parse.c`、`src/detect-engine-register.c`），不能宣称 100% 兼容，移植规则时报「未知关键字」属于加载失败而非检测异常。其四，Hyperscan 是可选 MPM 加速（`src/util-mpm-hs.c`，构建开关见 `configure.ac`，选项名需对照实际版本核验），缺失时回退 AC 等其他实现（`src/util-mpm-ac*.c`），不是必需依赖。版本基准统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验；凡吞吐、pps、丢包率、内存占用结论一律标注「需在目标机型实测」，不给绝对值。

六个案例固定为：① 规则语法或加载失败；② EVE 无输出或输出错目录；③ 流式与 IPS 漏匹配或误阻断；④ 多线程与 CPU 绑核导致的丢包或性能塌方；⑤ 规则集升级后内存暴涨；⑥ 上线吞吐只有基准的十分之一。它们覆盖从启动期到运行期、从静态配置到系统侧状态的全链条。六个案例的取证来源、归因路径与验证闭环的共性结构见图 08-04-01：无论哪一例，都要先从最便宜、最确定的静态证据入手，再取运行证据，最后把根因收敛到具体源码或配置键，修复后用同一组输出验收，并把证据链归档回填案例库。

围绕图 08-04-01 还需说明证据成本的顺序：读 `--build-info`、`-T`、`--dump-config` 几乎零成本且可随时重放，读 `stats.log` / `eve.json` 不干扰进程，而 `suricatasc dump-counters` 不中断压测，`ethtool -S`、`dmesg`、core 一类系统证据最贵。案例①与②主要吃静态与启动证据，案例③与④要靠运行与实时证据，案例⑤与⑥则必须把运行证据、实时证据与系统侧状态三路交叉，才不会把「规则集变大后的正常稳态上移」误判成内存泄漏，或把「一次在线跑分」误判成容量结论。

### 2. 前置条件与环境

第一步永远是钉死二进制本身。`suricata --build-info` 打印编译期特性，对应 `src/suricata.c` 约 763 行的长选项与 `build-info.h` 的包含（约 992 行）；`suricata --dump-config` 打印解析后的运行配置（约 761 行）；`suricata -T` 解析为 `conf_test`（约 1466、1960-1961 行 `case 'T'`）并置为 `RUNMODE_CONF_TEST`（约 2210 行），成功时打印 "Configuration provided was successfully loaded. Exiting."（约 3205 行）后退出。为什么必须先做这一步：两台机器若一个编进 Hyperscan、一个没有，规则集与 yaml 都相同，跑分也不可比；带 profiling 或 Sanitizer 的调试构建有额外开销，绝不能拿来当生产基准（构建变体见 02-05，选项见 `configure.ac` 的 `--enable-profiling` 约 522 行）。这三项导出留档，是六个案例共用的静态基线。

第二步是把证据目录隔离。`-l <日志目录>` 指定日志落点，`src/suricata.c` 约 2991 行 `SCConfigGetLogDirectory()` 取目录，约 2993 行 `ConfigCheckLogDirectoryExists` 检查存在性、约 3000 行 `IsLogDirectoryWritable` 检查可写性；目录不对时这两处 `SCLogError` 会直接给出提示。这一条与案例②直接相关：`src/output-json.c` 约 63 行把默认文件名定义为 `DEFAULT_LOG_FILENAME "eve.json"`，约 1096 行用 `SCConfLogOpenGeneric(conf, json_ctx->file_ctx, DEFAULT_LOG_FILENAME, 1)` 打开输出文件，约 1072-1081 行按 `filetype` 在 `LOGFILE_TYPE_FILE` / `LOGFILE_TYPE_UNIX_DGRAM` / `LOGFILE_TYPE_UNIX_STREAM` / `LOGFILE_TYPE_REDIS` / `LOGFILE_TYPE_FILETYPE` 之间分派。也就是说「没看到 eve.json」既可能是日志目录不对、也可能是 `filetype` 根本不是普通文件、还可能是 `-l` 指向了别处，三者取证方式不同，不能一上来就改规则。日志目录与输出类型的完整键值见 04-02 / 04-04，本篇不重列。

第三步备齐样本与归档：离线 pcap 要覆盖目标链路的协议混合与平均包长，并含能触发告警的样本，否则 `detect.alert` 恒为零、检测路径等于没跑到；规则集快照、`suricata.yaml`、`etc/classification.config`、`etc/reference.config`、`threshold.config` 要打包记录校验和。观测侧提前配好 `suricata.yaml.in` 的 `stats:` 段（约 65 行，默认 `enabled: yes`、`interval: 8`，键名与默认值需对照实际版本核验），计数三路呈现为 `stats.log`（`src/log-stats.c`）、EVE 的 `event_type: stats` 事件（`src/output-json-stats.c`）与 `suricatasc dump-counters`（`src/counters.c` 的 `StatsOutputCounterSocket`）。系统侧按 `doc/userguide/performance/high-performance-config.rst` 稳定下来：关 `irqbalance`、用 `ethtool -l <iface>` 看队列数、固定 CPU governor、确认 NUMA 与网卡同侧，这些动作不在参数清单里，漏掉任何一项都会让案例④与⑥的 A/B 失去意义。基准前必须冻结的变量及其取证方式见下表，表内只写「为什么必须冻结」，不抄参数全集。

| 冻结项 | 冻结方式 | 取证命令或路径 | 不冻结的后果 |
|---|---|---|---|
| 二进制与编译期特性 | 固定同一份安装产物 | `suricata --build-info` | Hyperscan 或 profiling 差异导致不可比 |
| 规则集快照 | 记录文件清单与校验和 | `src/detect-engine-loader.c` 加载路径 | 规则数变化直接改变 detect 与内存负载 |
| 全局与模块配置 | 归档 yaml 并用 `-T` 校验 | `suricata --dump-config` | 隐式默认值随版本漂移 |
| 日志目录与 filetype | 用 `-l` 隔离并核验可写 | `src/suricata.c` 目录检查与 `output-json.c` | 输出落点漂移、误判为无告警 |
| 采样窗口与预热 | 固定 `stats.interval` 与稳定期 | `suricata.yaml.in` 的 `stats:` 段 | 未收敛计数波动大、结论不稳 |
| 系统侧状态 | 关 irqbalance、固定 governor | `ethtool -l`、`lscpu`、驱动固件版本 | 中断与频率漂移污染吞吐与丢包 |

六个案例的复现都在这套冻结基线上做，且每轮只改一个变量（方法见 08-01、调优见 08-02）。以下所有命令中的文件名取具体值便于照跑，带尖括号的路径需替换成本机真实路径，替换动作本身也是冻结基线的一部分；命令全集的完整清单见 04-07，RPC 命令见 04-07 / 07-12，本篇只给最小必要调用。

### 3. 分步操作：六个完整案例

#### 案例① 规则语法错误与规则文件加载失败

**现象与影响面。** `suricata -T` 或正常启动在加载规则阶段报错退出，或日志显示规则成功加载数为零。影响面是全局性的：一条规则都没装进检测引擎时，进程即便能继续收包，`detect.alert` 也恒为零，整个实例退化为「只抓包不检测」。这类问题最容易被误判为「无告警」或「吞吐低」而改到线程参数上，属于 08-03 判定顺序第一层就该截断的分支。

**复现步骤。** 在 `local.rules` 末尾故意写一条缺分号或使用未注册关键字的规则，再用 `-T` 加载；同时准备一个把 `rule-files` 指向不存在文件的变体，观察两类报错文本的区别。

```bash
mkdir -p case01/log
printf 'alert tcp any any -> any any (msg:"case01 test"; sid:9000001; rev:1; content:"abc"\n' > case01/local.rules
suricata -T -c suricata.yaml -S case01/local.rules -l case01/log
echo "exit_code=$?"
tail -n 40 case01/log/suricata.log
```

**证据。** 下面是该场景的典型输出（示例输出，具体格式需对照实际版本核验）。注意错误文本只按关键字定位，不要按固定字符串或错误码数值去匹配。

```text
示例输出，具体格式需对照实际版本核验
[Info] - Running suricata under test mode
[Error] - no terminating ";" found
[Error] - unknown rule keyword 'nosuchkey'.
[Info] - 1 rule files processed. 0 rules successfully loaded, 1 rules failed
[Warning] - No rules loaded, detection will be disabled
exit_code=1
```

**根因。** `src/detect-parse.c` 约 976 行 `SCLogError("no terminating \";\" found")` 对应缺分号，约 1024 行 `SCLogError("unknown rule keyword '%s'.", optname)` 对应未注册关键字，约 1097 / 1120 行给出 "invalid formatting or malformed option" 一类的选项格式错；关键字是否注册由 `src/detect-engine-register.c` 的 `sigmatch_table[]` 查表决定（约 369-406 行）。规则文件打不开时则是 `src/detect-engine-loader.c` 约 135 行 `SCLogError("opening rule file %s:"...)`，约 179-180 行把 `de_ctx->rule_file` / `rule_line` 绑到上下文以便把错误定位到具体文件与行，约 480 / 486 行汇总 " rules successfully loaded, ... rules failed"。`-T` 走到 `RUNMODE_CONF_TEST` 后若加载异常，`src/suricata.c` 会以 `exit(EXIT_FAILURE)` 退出（约 573、3183 行等），成功则 `exit(EXIT_SUCCESS)`（约 3142 行）；退出码的具体取值与错误码文本需对照实际版本核验，禁止凭印象补数值。规则头与选项的语法规则见 04-05 / 04-06，加载入口 `SigLoadSignatures`（约 384 行）的调用链见 06-06。

**修复动作。** 按报错定位到文件与行，补齐分号、把未注册关键字改为本版本支持的关键字，再用 `--dump-config` 复核 `rule-files` 与 `default-rule-path` 指向真实存在的文件；`src/suricata.c` 的 `--set name=value`（约 649 行）只用于临时覆盖单值，不能拿来长期掩盖路径错误。

```bash
# 修正规则文件后重跑自检，并确认解析后的规则清单
suricata -T -c suricata.yaml -S case01/local.rules -l case01/log
suricata --dump-config -c suricata.yaml | grep -E 'rule-files|default-rule-path'
```

**验证方法（预期输出 + 判读要点）。** 预期 `-T` 打印成功加载数稳定、`rules failed` 为零，并出现 "Configuration provided was successfully loaded. Exiting."；判读要点是「成功数」与「失败数」必须一起看，成功数为零而失败数也为零同样意味着没装规则，且成功数要与归档的规则集快照条数逐项一致。下面给出这一组证据的逐行判读，作为全篇「命令 + 输出 + 判读」的样板。

```text
示例输出，具体格式需对照实际版本核验
[Info] - Running suricata under test mode
[Config] - rule-files: suricata.rules, local.rules
[Info] - 2 rule files processed. 34128 rules successfully loaded, 0 rules failed
[Notice] - Configuration provided was successfully loaded. Exiting.
exit_code=0
```

逐行判读如下。第一行 "Running suricata under test mode" 确认进程进入 `RUNMODE_CONF_TEST` 而非普通抓包模式；若这行没出现就直接开始收包，说明 `-T` 未生效或被其它参数覆盖，应回到 `src/suricata.c` 的 `case 'T'` 分支核对命令行。第二行是配置树里的 `rule-files` 清单，判读要点是必须与归档的规则集快照逐项一致，多一条、少一条都意味着基线被改动，配置树读取见 `src/conf.c` 的 `SCConfGetNode`（约 183 行）与 `SCConfGet`（约 352 行）。第三行是本篇最关键的数值：`successfully loaded` 应为稳定的正整数且各轮一致，`failed` 必须为零；该行措辞与计数项需对照 `src/detect-engine-loader.c` 约 480 行起的实际版本核验，只要出现非零失败数就应停止后续压测、回到 `src/detect-parse.c` 排查，因为「规则没装全」会让吞吐虚高、告警虚低，数据全废。第四行 "successfully loaded. Exiting." 对应 `src/suricata.c` 约 3205 行的 `SCLogNotice`，是 `-T` 正常退出的标志。第五行 `exit_code=0` 与前面的 `exit_code=1` 形成对照，退出码具体取值需对照实际版本核验，判读时以「零与非零」区分成功与失败，不臆测数值。整段文本是示例，日志级别前缀、错误码与计数项在不同版本会变，一律以本机实际输出为准（字段见 05-05 ｜ 参数见 04-02 ｜ 原理见 06-06 ｜ 模块见 07-04）。

#### 案例② EVE 无输出或输出错目录

**现象与影响面。** 进程正常启动、`stats.log` 在涨、`capture.kernel_packets` 也在涨，但预期目录里没有 `eve.json`，或 EVE 写到了另一个目录、根本不是普通文件。影响面是下游管道（Filebeat / Logstash / SIEM）完全收不到事件，值班同学却因为「有 stats、有包」误以为系统健康；若 `outputs` 里连 `alert` 类型都没启用，还会叠加「无告警」的表象。

**复现步骤。** 用 `-l` 把日志指向一个临时目录，同时在 `suricata.yaml` 里把 `eve-log` 的 `filetype` 改成非普通文件类型，或把 `enabled` 关掉，观察落盘结果；再用 `--dump-config` 读出真正生效的 `outputs` 键值。

```bash
mkdir -p case02/log case02/other
suricata -T -c suricata.yaml -l case02/log
suricata -c suricata.yaml -r case02/sample.pcap -l case02/log
ls -l case02/log case02/other
find / -name eve.json -newermt '10 minutes ago' 2>/dev/null | head -20
suricata --dump-config -c suricata.yaml | grep -E 'outputs|eve-log|filetype|filename'
```

**证据。** 下面是目录与配置取证的输出（示例输出，具体格式需对照实际版本核验）。

```text
示例输出，具体格式需对照实际版本核验
case02/log:
total 96
-rw-r--r-- 1 root root 40960 stats.log
-rw-r--r-- 1 root root 12288 suricata.log
case02/other:
total 0
outputs.0.eve-log.enabled = no
outputs.0.eve-log.filetype = unix_stream
outputs.0.eve-log.filename = eve.json
```

**根因。** `src/output-json.c` 约 63 行 `DEFAULT_LOG_FILENAME "eve.json"` 只是默认文件名，真正落点由 `-l` 指定的日志目录决定：`src/suricata.c` 约 2991 行 `SCConfigGetLogDirectory()`、约 2993 行 `ConfigCheckLogDirectoryExists`、约 3000 行 `IsLogDirectoryWritable` 依次确认目录存在且可写。约 1072-1081 行按 `filetype` 分派，只有 `LOGFILE_TYPE_FILE` 才会经约 1096 行 `SCConfLogOpenGeneric` 打开普通文件；若配成 `LOGFILE_TYPE_UNIX_STREAM` / `LOGFILE_TYPE_UNIX_DGRAM` / `LOGFILE_TYPE_REDIS`，事件会走 socket 或 redis，本地目录自然没有 `eve.json`。此外 `outputs` 段未启用 `alert` 类型时，即便有 EVE 文件也不会有 `event_type: alert` 事件（`src/output-json-alert.c` 相关，路径需对照实际版本核验）。配置树由 `src/conf.c` 的 `SCConfGet` 系列读取，`--dump-config` 打印的正是解析后的 `SCConfNode` 树（字段见 05-09）。

**修复动作。** 把 `eve-log.enabled` 置为可用状态、`filetype` 改回普通文件、确认 `types` 里含 `alert` 与 `stats`，并统一 `-l` 与下游采集端约定的目录；随后用 `suricatasc -c "reopen-log-files"` 重开日志（命令见 04-07 / 07-12）。

```yaml
# 仅示意案例②需要核对的最小配置；完整清单见 04-02 / 04-04
outputs:
  - eve-log:
      enabled: yes
      filetype: regular
      filename: eve.json
      types:
        - alert
        - stats
```

**验证方法（预期输出 + 判读要点）。** 预期在 `-l` 指定目录下出现 `eve.json` 且体积随时间增长，`grep -c '"event_type":"alert"'` 对含告警样本返回正数；判读要点是先看文件是否生成、再看事件类型是否齐全，二者缺一都说明输出链没通。EVE 事件聚合与轮转机制见 06-11，输出模块见 07-07；`etc/suricata.logrotate.in` 的轮转模板见 08-06。

#### 案例③ 流式与 IPS 漏匹配或误阻断

**现象与影响面。** 内联部署下该丢的流没丢（漏匹配 / 漏阻断），或业务正常连接被误断开（误阻断）。前者是安全事件，后者是可用性事故，两者都可能同时伴随「有 alert 但没 drop」或「没 alert 却断了连」。影响面直接落在业务链路上，必须优先按 08-03 的判定顺序确认「到底是不是 IPS 模式、有没有 verdict 通道」，而不是先改规则内容。

**复现步骤。** 用 AF_PACKET 桥接或 NFQUEUE 起内联实例，回放含已知命中特征的 pcap，分别检查 `eve.json` 里的 `alert` / `drop` 事件与业务侧连通性；再把 `nfq.fail-open` 打开、把规则动作从 `drop` 改成 `alert`，观察差异。案例③的流式与 IPS 判定分支见图 08-04-02。

#### 案例④ 多线程与 CPU 绑核导致的丢包或性能塌方

**现象与影响面。** 加了线程、开了绑核之后吞吐不升反降，`capture.kernel_drops` 持续增长、`tcp.reassembly_gap` 抬头，甚至出现连接 intermittently 超时。影响面是「越调越慢」：本想扩容，实际把队列锁竞争、跨 NUMA 远端内存访问与同一条流的错线程分派一起引入了系统。这类现象按 08-03 判定顺序落在「吞吐低」分支，取证要三路交叉。

**复现步骤。** 固定其它变量，只把 `threading.set-cpu-affinity` 打开并把 `worker-cpu-set` 指到与抓包网卡不同 NUMA 节点的核上，同时把 `af-packet.threads` 提到超过物理核；用 `suricatasc dump-counters` 与 `ethtool -S` 取丢包证据。

```bash
mkdir -p case04/log
ethtool -l eth1
lscpu | grep -E 'NUMA|CPU\(s\)'
suricata -T -c suricata.yaml -l case04/log
suricata -c suricata.yaml --af-packet=eth1 -l case04/log &
suricatasc -c "dump-counters" case04/log/suricata.socket | grep -E 'kernel_drops|kernel_packets|wrong_thread|reassembly_gap'
ethtool -S eth1 | grep -E 'rx_missed|rx_no_buffer'
```

**证据。** 下面是一帧 `stats.log` 三列格式的节选（示例输出，具体格式需对照实际版本核验）。

```text
示例输出，具体格式需对照实际版本核验
capture.kernel_packets                | Total   | 450001754
capture.kernel_drops                  | Total   | 78093
stream.wrong_thread                   | Total   | 12004
tcp.pkt_on_wrong_thread               | Total   | 9031
tcp.reassembly_gap                    | Total   | 789
```

**根因。** `capture.kernel_packets` / `capture.kernel_drops` 由 `src/source-af-packet.c` 约 2612-2613 行 `StatsRegisterCounter` 注册，约 624-625 行把内核 TPACKET 统计 `tp_packets` / `tp_drops` 累加进来；两者比值抬头说明收包侧已经跟不上。`stream.wrong_thread` / `tcp.pkt_on_wrong_thread` 是 `doc/userguide/performance/high-performance-config.rst` 列出的负载均衡诊断项，持续升高说明同一条流的包被分到不同线程，通常与 `cluster-type`、对称哈希或 RSS 配置有关。绑核侧 `src/util-affinity.c` 约 40-59 行给出 `EXCLUSIVE_AFFINITY` / `BALANCED_AFFINITY` 与 `PRIO_MEDIUM` 初值，约 45 行 `worker-cpu-set`，约 152 / 190 行 `SCLogError("CPU affinity with name \"%s\" not found")`、约 245-253 行 "invalid cpu range" 是绑核名或范围写错时的报错；`suricata.yaml.in` 约 1950 行 `threading:`、约 1951 行 `set-cpu-affinity: no`（默认关闭）、约 2007 行 `detect-thread-ratio: 1.0`。`src/runmodes.c` 约 65-67 行 `thread_name_autofp = "RX"` / `thread_name_workers = "W"`，约 205 / 210 行按 `RunmodeGetActive()` 判定 workers / autofp，加线程不必然线性提速（原理见 06-13）。`suricata.yaml.in` 约 690 行 `cluster-type: cluster_flow`，配 `cluster_qm` 前必须先让网卡 RSS 队列与对称哈希就位。

**修复动作。** 把 worker 收回与抓包网卡同 NUMA 节点的物理核内，线程数不超过该节点可用核；无对称哈希的网卡回退 `cluster_flow`；`ethtool -S` 补齐网卡层计数后再判断是否真是收包侧瓶颈。启动期内存账（`max-pending-packets`、`ring-size`，`suricata.yaml.in` 约 1429、701-703 行注释）要一并核算，避免线程与环大小同步放大。以下为单变量复核命令。

```bash

suricatasc -c "dump-counters" case04/log/suricata.socket | grep -E 'kernel_drops|wrong_thread'
```

**验证方法（预期输出 + 判读要点）。** 预期 `capture.kernel_drops` 增量收敛到接近零、`stream.wrong_thread` 与 `tcp.pkt_on_wrong_thread` 不再持续升高、吞吐回到该机型基线；判读要点是 `tcp.reassembly_gap` 非零不能单凭断定网卡丢包（`doc/userguide/performance/statistics.rst` 说明坏校验和与流引擎内存不足也会影响它），必须先看 capture 比值、再看 `ethtool -S` 网卡层计数、最后看负载均衡诊断计数。所有速率结论标注「需在目标机型实测」（参数见 04-03 ｜ 原理见 06-13 ｜ 模块见 07-06）。

#### 案例⑤ 规则集升级后内存暴涨

**现象与影响面。** 通过 `suricata-update` 合并新规则并热加载后，`flow.memuse`、`tcp.reassembly_memuse` 稳态水位明显上移，甚至出现 `flow.emerg_mode_entered`、`tcp.ssn_memcap_drop` / `tcp.segment_memcap_drop`，启动时间也变长。影响面是容量：轻则告警延迟、重则流表进紧急回收、检测可见性下降。必须先区分「规则集变大后的正常稳态上移」与「同配置下的无界增长」，否则会把扩容需求误判成内存泄漏。

**复现步骤。** 记录升级前规则集校验和与内存曲线，执行规则合并与 `suricatasc -c "reload-rules"`，再跨多个 `stats.interval` 取同配置多轮 `flow.memuse` / `tcp.reassembly_memuse` 曲线。

```bash
suricata --dump-config -c suricata.yaml | grep -E 'flow.memcap|stream.reassembly.memcap|max-pending-packets|detect.profile'
```

**证据。** 下面是升级前后的内存计数对照（示例输出，具体格式需对照实际版本核验）。


**根因。** 规则数增长会同时推高签名分组编译时间、MPM 构建时间与检测侧负载，也会让每流状态与重组缓冲的稳态水位上移（原理见 06-06 / 06-07）。内存上限的真实依据：`src/flow.c` 约 94 行 `flow_memuse` 原子计数、约 108 / 122 行 `flow_config.memcap`、约 574 行 `FlowInitConfig`、约 589 行 `FLOW_DEFAULT_MEMCAP`、约 594-604 行 `flow.emergency-recovery`；`src/stream-tcp-reassemble.c` 约 87 行 `ra_memuse`、约 173-175 行按 `stream_config.reassembly_memcap` 判定是否还能分配；`src/app-layer-htp-mem.c` 约 40-42 行 `htp_config_memcap` / `htp_memuse` / `htp_memcap`，约 52 行读 `app-layer.protocols.http.memcap`，约 54 行解析失败时 `SCLogError("Error parsing http.memcap ")`。`suricata.yaml.in` 约 1595 行 `flow:`、约 1596 行 `flow.memcap: 128 MiB`，约 1750 行 `stream:`、约 1751 行 `stream.memcap: 64 MiB`、约 1761 行 `stream.reassembly.memcap: 256 MiB`，约 1429 行 `max-pending-packets` 注释，约 1858 行 `detect:`、约 1906 行 `detect.profiling`（以上键名与默认值需对照实际版本核验，注意 `suricata.yaml.in` 约 1574 行注释与约 1596 行取值并不一致，切勿照抄注释当默认值）。`suricata-update` 是与内核主程序分仓、独立发版的独立工具（见 07-11），不是 `src/` 的子命令或内建模块；`src/util-threshold.c` 在当前 main 快照中不存在，阈值与抑制的真实实现为 `src/detect-engine-threshold.c`、`src/detect-threshold.c`、`src/util-threshold-config.c`，`threshold.config` 语法见仓库根同名文件，均需对照实际版本核验。内存分配封装见 `src/util-mem.h` 的 `SCMalloc` / `SCCalloc` / `SCRealloc` / `SCFree`（约 35-38 行）及其 `Func` 版本（约 46-77 行）。

#### 案例⑥ 上线吞吐只有基准的十分之一

**现象与影响面。** 生产上线后实测吞吐远低于 08-01 的离线基准，收包侧 `kernel_drops` 持续增长，检测速率上不去。影响面是容量承诺落空。这里首先要破除一个方法论错误：离线回放结果偏乐观，绝不能当生产容量承诺；但差距到「十分之一」量级通常不是正常偏差，而是系统侧状态或配置组合与基准不一致。

**复现步骤。** 按 08-01 的冻结基线逐项比对：二进制特性、规则集校验和、yaml 差异、系统侧 `irqbalance` / governor / NUMA / RSS 队列、抓包后端、runmode；用 `--dump-config` 把解析后的运行配置与基准留档逐项 diff。

```bash
mkdir -p case06/log
suricata --build-info > case06/log/build-info.txt
suricata --dump-config -c suricata.yaml > case06/log/dump-config.txt
diff -u bench-log/dump-config.txt case06/log/dump-config.txt | head -60
suricata -T -c suricata.yaml -l case06/log
suricatasc -c "dump-counters" case06/log/suricata.socket | grep -E 'kernel_drops|kernel_packets|detect.alert|reassembly_gap'
ethtool -S eth1 | grep -E 'rx_missed|rx_no_buffer'
```

**证据。** 下面是 `--dump-config` 差异与一帧计数的节选（示例输出，具体格式需对照实际版本核验）。

```text

+af-packet.0.tpacket-v3 = no
-threading.set-cpu-affinity = yes
+threading.set-cpu-affinity = no
-runmode = workers
+runmode = autofp
capture.kernel_drops | Total | 981203
capture.kernel_packets | Total | 450001754
```

**根因。** 差距通常来自四类组合偏差。其一，二进制特性：`--build-info` 若显示生产机没编进 Hyperscan，而 `suricata.yaml.in` 约 1938 行 `mpm-algo: auto`、约 1928 行注释说明 auto 在有 Hyperscan 时用 `hs`，则生产机会回退 AC 等其他实现（`src/util-mpm-hs.c` / `src/util-mpm-ac*.c`），MPM 负载不同；`configure.ac` 中 Hyperscan 相关开关名需对照实际版本核验。其二，runmode 与线程：`src/runmodes.c` 约 198 行 `RunmodeGetActive`、约 205 / 210 行 workers / autofp 判定，约 366-367 行还有把不合适的 mode 收敛到 `workers` 的提示；`doc/userguide/performance/runmodes.rst` 只说 workers 通常表现最好，是经验倾向而非线性承诺。其三，抓包与负载均衡：`src/source-af-packet.c` 约 2612-2613 行的 capture 计数、`suricata.yaml.in` 约 690 行 `cluster-type: cluster_flow`、约 701-703 行 ring-size 注释，`tpacket-v3` 对 IDS / NSM 推荐、对 IPS / TAP 因引入时延不推荐（`doc/userguide/performance/tuning-considerations.rst`）。其四，系统侧：`irqbalance` 未关、governor 漂移、跨 NUMA 绑核、网卡队列数与 `af-packet.threads` 不匹配、驱动或内核升级改变性能特征（`doc/userguide/performance/high-performance-config.rst` 结尾有明确提示）。还可能叠加调试构建：带 `--enable-profiling`（`configure.ac` 约 522 行）或 Sanitizer 的二进制不能与生产变体直接比计数。

**修复动作。** 按单变量原则把生产机逐项对齐基准：先重编同一份生产变体，再对齐 runmode、`cluster-type`、`tpacket-v3`、绑核与 RSS 队列，每改一项重跑 `-T`、等计数收敛后回填对照表；`suricata --set name=value` 只用于临时覆盖单值且必须写进对照表，否则等于引入隐藏变量。完整命令见 04-07，调优动作见 08-02。

```bash
suricata --build-info | grep -iE 'hyperscan|profiling'
suricata --dump-config -c suricata.yaml | grep -E 'runmode|tpacket-v3|cluster-type|threads|mpm-algo'
```

**验证方法（预期输出 + 判读要点）。** 预期 diff 收敛到「只剩与生产链路相关的合理差异」，`capture.kernel_drops` 与 `kernel_packets` 比值回到基准量级，吞吐回到该机型基线；判读要点是任何速率结论都要带单位与边界（在哪台机型、哪个 NUMA、哪个内核上得到），并标注「需在目标机型实测」，绝不用离线跑分替代生产容量评估（参数见 04-03 ｜ 原理见 06-13 ｜ 模块见 07-06）。

### 5. 常见失败与排错

第一类是「在错误的层级上修故障」。规则没装全的实例，表现可能是告警稀少、CPU 偏低、吞吐看着不错，若按「吞吐低」去加线程调 ring-size，改一整天也不会让告警回来；反过来把真正的在线丢包当成「规则没加载」，又会白白重装规则集、重启进程。判定顺序固定为 `--build-info` / `--dump-config`（静态）→ `-T` 与 `suricata.log`（启动）→ `stats.log` / `eve.json`（运行）→ `suricatasc dump-counters`（实时）→ `ethtool -S` / `dmesg` / core（系统），逐层不跳、至少两路证据交叉印证，决策树见 08-03 图 08-03-01，条目化速查见 04-08。

第二类是取证本身的陷阱。`stats.log` 的 `Total` 行与各线程行混读会把计数翻倍；`kernel_drops` 增长不配 `ethtool -S` 会把网卡层丢包误判成收包侧瓶颈（`doc/userguide/performance/statistics.rst` 明确提醒关停时打印的内核丢包统计不完整）；`tcp.reassembly_gap` 非零既可能是丢包，也可能是坏校验和或流引擎内存吃紧，不能单凭它下结论。还有一类隐蔽错误是拿调试构建复现：`--build-info` 里带 profiling 或 Sanitizer 特征，本轮取证作废，按 02-05 重编生产变体。

第三类是忽略时间线与能力边界。规则集热加载（`suricatasc reload-rules`）、配置变更、驱动与内核升级都会改变基线，`doc/userguide/performance/high-performance-config.rst` 结尾明确提示升级会影响性能，需在 QA 环境先验证；脱离时间线谈「内存涨」或「吞吐降」等于没有基线。能力边界方面，把「加密载荷里没有关键字告警」当无告警故障、把「IDS 旁路没有 drop 日志」当没告警、把「加线程」写成必然线性提速、把 `suricata-update` 写成主程序内建模块、把 Hyperscan 写成必需依赖，都是方向性错误。规则语法兼容 Snort 但有自有扩展，移植规则报未知关键字属加载失败。所有吞吐、丢包率、内存占用结论一律标注「需在目标机型实测」。

## 08-05 安全加固：不可信规则、权限与资源耗尽

### 1. 背景与动机

加固的动机不是「把配置项调到最严」，而是认清一个事实：Suricata 是常驻的、需要高权限抓包的、并且要持续消化两类不可信输入的引擎——一类是从外部下载或由第三方提供的规则集，另一类是线上无穷无尽的报文。规则集里的一个灾难性 `pcre`、一张超大 `dataset`、或一批 `fast_pattern` 极多的规则，可以在编译期把内存与时间吃满；一条畸形流可以把流表、重组缓冲与应用层解析缓冲推到上限；一个权限过大的进程或世界可写的 unix socket，则把控制面直接暴露出去。加固要做的，是给这三类放大路径分别设上限、给进程权限划边界、给输出落点定归属，并且让这些约束在规则集增长后依然成立。这与 08-04 的排障是分工关系：08-04 讲「已经出事怎么复现与修复」，本篇讲「事前把攻击面收窄」，两者共用同一套证据来源与源码锚点。

先立四条边界，避免加固方向写反。其一，Suricata 是 IDS / IPS / NSM 引擎，不做 IP 转发、不做路由、不是防火墙；内联阻断依靠 NFQUEUE / AF_PACKET 桥接的 verdict（原理见 06-12），加固的对象是检测链路本身，不是「转发通道的访问控制」。其二，规则语法兼容 Snort 但有自有扩展（`src/detect-parse.c`、`src/detect-engine-register.c`），不能宣称 100% 兼容；所谓「不可信规则」既包括来源不可信，也包括「在本版本未验证过的关键字组合」。其三，引擎只对自身解码并重组到的流量做检测，TLS 等加密载荷不可见，加固不能建立在「能看到明文」的假设上。其四，Hyperscan 是可选 MPM 加速（`src/util-mpm-hs.c`，构建开关见 `configure.ac`，选项名需对照实际版本核验），缺失时回退 AC 等其他实现（`src/util-mpm-ac*.c`），把它写成必需依赖是错的。版本基准统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验；任何吞吐、内存、容量结论一律标注「需在目标机型实测」。本篇不重列参数全集，只给最小必要加固片段，完整清单见 04-02 / 04-03 / 04-04；结构体逐字段见 05-xx；机制见 06-xx；模块见 07-xx。统一交叉引用写作（字段见 05-05 ｜ 参数见 04-02 ｜ 原理见 06-06 ｜ 模块见 07-04）。

### 2. 核心概念

「信任边界」指输入从不可信侧进入引擎可信侧的那道分界，跨越它时必须完成校验或配额约束。在本篇语境下，边界有三段：规则文件进入检测引擎的编译期边界、报文进入流与重组子系统的运行期边界、外部命令进入控制面与输出落点的运维边界。三段边界各自的失败形态不同——编译期失败表现为启动慢、内存峰值高、`-T` 报错；运行期失败表现为 memcap drop、紧急回收、丢包；运维边界失败表现为越权命令、日志被篡改或读取。把它们分开定义，才能避免「一个 memcap 打天下」的粗糙做法。

不可信规则的风险集中在编译期放大。`pcre` 一类回溯型匹配、超大 `dataset` / `datarep` 表、以及 `fast_pattern` 选择不当导致的大量候选模式，都会在签名分组与 MPM 构建阶段推高内存与耗时（`src/detect-engine*.c`、`src/util-mpm*.c`、`src/detect-engine-register.c` 的关键字注册）。这类风险的特点是「启动期一次性爆发」：进程还没开始收包，资源就已经被规则编译吃满，因此不能靠运行期的 memcap 兜底，必须靠加载前的校验与规则来源治理。规则关键字全集见 04-05 / 04-06，分组编译与 MPM 机制见 06-06 / 06-07。

运行期资源耗尽的语义由 memcap 定义。`suricata.yaml.in` 约 1595 行 `flow:`、约 1596 行 `flow.memcap: 128 MiB`，约 1750 行 `stream:`、约 1751 行 `stream.memcap: 64 MiB`、约 1761 行 `stream.reassembly.memcap: 256 MiB`，约 1429 行 `max-pending-packets` 注释，约 1325-1328 行 dataset 的默认 memcap 注释，约 1130 行 HTTP 一类 app-layer 的 `memcap` 说明（以上键名与默认值需对照实际版本核验，注意约 1574 行注释与约 1596 行取值并不一致）。`memcap-policy` 决定超限时的处置，`suricata.yaml.in` 约 1548-1552 行与约 1592 行注释列出 `drop-packet` / `pass-packet` 一类取值，约 1681 / 1712 行还有 `drop-flow` 一类取值，具体枚举需对照实际版本核验。这里要点明概念而非抄参数：memcap 是「上限 + 超限策略」的组合，只设上限不设策略，超限行为就依赖默认值；只设策略不核算上限，等于没算容量账。

权限面分四组。抓包能力靠 `CAP_NET_RAW` / `CAP_NET_ADMIN`（AF_PACKET、DPDK 环境要求差异大，见 02-04 / 06-02）；进程身份靠 `user` / `group` 一类降权选项与 `chroot`（选项名需对照 `configure.ac`、`suricata.yaml.in` 实际版本核验，当前 main 快照中 `src/suricata.c` 约 3186 行有 `SCDropMainThreadCaps` 一类降权入口，函数名需对照实际版本核验）；控制面靠 unix socket 文件权限与 `suricatasc` 命令协议（见 07-12）；输出落点靠 EVE 目录的属主与权限，`etc/suricata.logrotate.in` 的模板对 `@e_logdir@*.log @e_logdir@*.json` 做轮转，目录若世界可写，日志就可能被替换或删除。这四组里前两组是「进程能做什么」，后两组是「谁能指挥进程、谁能改证据」，加固时缺一不可。

还有一类常被误当作「加固」、实则属于「改输入」的手段：BPF 捕获过滤与 `stream.bypass`。`doc/userguide/performance/ignoring-traffic.rst` 说明 BPF 可直接告诉内核哪些包不要送给 Suricata，`suricata.yaml.in` 约 1699 行 `inline`、约 1743 行注释一类设置会在条件满足后跳过部分工作。它们确实能降低负载，但改变的是输入或可见性，不是权限边界，绝不能与「降权、设 memcap」混为一谈；一旦启用，必须明确记录过滤表达式与业务能接受多少漏检。相关键名与取值需对照实际版本核验（原理见 06-01 ｜ 参数见 04-03 ｜ 模块见 07-06）。

### 4. 关键流程与调用链

从一次规则集投放到资源被约束，链路大致如下。`suricata-update` 把规则合并到 `rules/suricata.rules`（它是与内核主程序分仓、独立发版的独立工具，见 07-11，不是 `src/` 的子命令或内建模块）；`suricata -T` 或正常启动进入 `src/suricata.c` 的加载链，`LoadSignatures` 一类入口调用 `SigLoadSignatures`（`src/detect-engine-loader.c` 约 384 行），逐行走 `src/detect-parse.c` 的规则头与选项解析，并到 `src/detect-engine-register.c` 的 `sigmatch_table[]` 查关键字是否注册；解析成功后按 proto / 端口 / 方向分组构建 `SigGroupHead`、挂接预过滤与 MPM（`src/detect-engine-mpm.c`、`src/util-mpm*.c`，机制见 06-06 / 06-07）。这一整段就是图 08-05-02 里「编译期上限」的作用区间：`pcre` 回溯、`dataset` 大表、超多 `fast_pattern` 都在这里放大内存与时间。因此投放前的 `-T` 与引擎分析选项（需对照实际版本核验）必须作为硬门禁，而不是等问题在运行期暴露。

运行期的资源约束按另一条链落地。`src/conf.c` / `src/conf-yaml-loader.c` 把 `flow.memcap`、`stream.reassembly.memcap`、`max-pending-packets`、`memcap-policy` 读进配置树；启动时 `src/flow.c` 的 `FlowInitConfig`（约 574 行）初始化流表与 `flow_memuse`，`src/stream-tcp-reassemble.c` 约 173-175 行按 `stream_config.reassembly_memcap` 判定是否还能分配重组段，`src/app-layer-htp-mem.c` 约 52 行读 `app-layer.protocols.http.memcap` 并维护 `htp_memuse`。运行中一旦逼近上限，`memcap-policy` 决定是丢包、放行还是丢流，`flow.emerg_mode_entered`、`tcp.ssn_memcap_drop` / `tcp.segment_memcap_drop` 一类计数经 `src/counters.c` 的 `StatsRegisterCounter` 注册、`StatsOutput` 汇总，落到 `stats.log`（`src/log-stats.c`）与 EVE 的 `event_type: stats`（`src/output-json-stats.c`）。本节只描述「做什么」，模块内部实现与字段布局分别见 06-04 / 06-11 与 05-03 / 05-08，本篇不展开机制细节。

权限链同样要分清启动期与运行期。`src/suricata.c` 约 2991 行 `SCConfigGetLogDirectory()` 取日志目录，约 2993 / 3000 行检查存在性与可写性，约 3186 行一类 `SCDropMainThreadCaps` 入口在抓包能力就绪后降权（函数名需对照实际版本核验）；`etc/suricata.service.in` 的 `ExecStart=/sbin/suricata -c ... --pidfile ... $OPTIONS`、`ExecReload=/bin/kill -USR2 $MAINPID` 定义了 systemd 下的启动与重载动作。运行期控制面走 unix socket，`suricatasc` 的 `reload-rules` / `reopen-log-files` / `dump-counters` / `memcap-list` 一类命令（完整集合见 04-07 / 07-12）能改变规则数与日志句柄，socket 文件权限因此是加固对象而非附属细节。输出落点由 `src/output-json.c` 打开，`etc/suricata.logrotate.in` 以 HUP 信号配合轮转，目录属主与权限决定证据是否可信。三条链的交汇点是「谁能改配置、谁能改规则、谁能改日志」，加固就是在这三处收口。

### 5. 配置/命令/代码实例

下面给一组加固场景的最小必要片段，只示意本场景会碰到的键，刻意不展开每个键的全部取值：完整清单见 04-02（全局段）、04-03（抓包与线程）、04-04（输出）、04-05 / 04-06（规则关键字）。片段按「先编译期门禁、再运行期上限、再输出与权限」的顺序组织，对应图 08-05-02 的四路收敛；键名与默认值需对照实际版本核验。

```yaml
# 仅示意加固场景的最小必要配置；完整清单见 04-02 / 04-03 / 04-04
flow:
  memcap: 128 MiB
  memcap-policy: drop-packet

stream:
  memcap: 64 MiB
  reassembly:
    memcap: 256 MiB
    memcap-policy: drop-flow

  - eve-log:
      enabled: yes
      filetype: regular
```

配套的命令闭环如下，按「前置检查 → 投放校验 → 运行观测 → 留证」组织。`suricata --dump-config | grep` 里的竖线是 shell 管道，用于从解析后的运行配置里筛出本轮真正生效的键值；这一步能抓出「以为设了上限、其实被默认值或 `--set` 覆盖」的情况。

```bash
# 前置检查：钉死二进制特性、导出运行配置、核对日志目录权限
suricata --build-info > harden/build-info.txt
suricata --dump-config -c suricata.yaml | grep -E 'memcap|memcap-policy|max-pending-packets|filetype'
ls -ld /var/log/suricata

# 投放校验：规则集投放前后都跑 -T，记录加载数与耗时
suricata -T -c suricata.yaml -l harden/log

# 运行观测：读取内存水位与 memcap drop 计数
grep -E 'flow.memuse|tcp.reassembly_memuse|flow.emerg_mode_entered|tcp.ssn_memcap_drop|tcp.segment_memcap_drop' harden/log/stats.log
suricatasc -c "memcap-list" harden/log/suricata.socket

# 留证：归档本轮配置、加载日志与计数
tar -cf harden/round-harden.tar harden/log/suricata.log harden/log/stats.log
```

下面是 `suricata -T` 在「不可信规则被拦在门禁外」场景的典型输出（示例输出，具体格式需对照实际版本核验），随后给出逐行判读。

```text
示例输出，具体格式需对照实际版本核验
[Info] - Running suricata under test mode
[Error] - unknown rule keyword 'dataset_load'.
[Info] - 1 rule files processed. 0 rules successfully loaded, 1 rules failed
[Config] - flow.memcap = 128 MiB
[Config] - stream.reassembly.memcap = 256 MiB
[Notice] - Configuration provided was successfully loaded. Exiting.
```

逐行判读如下。第一行确认进入 `RUNMODE_CONF_TEST`；若连这行都没有就退出，问题更靠前（依赖或命令行解析），应查 `src/suricata.c` 的参数解析而非规则内容。第二行 "unknown rule keyword" 对应 `src/detect-parse.c` 约 1024 行的 `SCLogError("unknown rule keyword '%s'.", optname)`，说明该关键字未在本版本 `src/detect-engine-register.c` 的 `sigmatch_table[]` 注册；错误文本与关键字名需对照实际版本核验，不要按固定字符串匹配，而应按「unknown rule keyword + 关键字名」定位，这正是「不可信规则」在编译期被门禁拦下的典型形态——它没有机会进入分组与 MPM 构建，也就不会在运行期放大资源。第三行的 `0 rules successfully loaded` 与 `1 rules failed` 必须一起看：失败数非零即停止投放，成功数为零意味着这批规则一条都没装，绝不能把它当成「加载成功只是有警告」。第四、五行是 `--dump-config` 打印的解析后键值，`flow.memcap` 与 `stream.reassembly.memcap` 要与 `suricata.yaml.in` 约 1596、1761 行一类取值对照，判读要点是「键是否真的生效」而非「yaml 里写没写」；若这里仍是默认值，说明片段没被读到或被覆盖，加固等于没做。第六行是 `-T` 正常退出标志（`src/suricata.c` 约 3205 行）。整段是示例，日志级别前缀、错误码与计数项在不同版本会变，具体格式需对照实际版本核验（字段见 05-05 ｜ 参数见 04-02 ｜ 原理见 06-06 ｜ 模块见 07-04）。

### 6. 注意事项、陷阱与最佳实践

不可信规则治理排第一。来源上，规则集应固定来源、记录校验和、经 QA 环境 `-T` 与短基准后才投放（方法见 08-01）；内容上，对 `pcre` 回溯、`dataset` / `datarep` 大表、`fast_pattern` 极多的规则保持警惕，它们放大的是编译期内存与时间，运行期 memcap 兜不住。`threshold.config`（仓库根同名文件给出 `threshold gen_id ... type <limit|threshold|both> ...` 与 `event_filter` 语法）与 `etc/classification.config`、`etc/reference.config` 同属「被信任的输入」，应纳入归档与校验和，不要当成可随意改写的普通文本；阈值实现文件为 `src/detect-engine-threshold.c`、`src/detect-threshold.c`、`src/util-threshold-config.c`，`src/util-threshold.c` 在当前 main 快照中不存在，需对照实际版本核验。`suricata-update` 是独立工具（见 07-11），投放动作要记录时间线，热加载后 `detect.alert` 与内存计数可能跳变。

权限最小化排第二。抓包能力够用即可，容器场景下 AF_PACKET 需 `CAP_NET_RAW` / `CAP_NET_ADMIN`，`--privileged` 要按取舍慎用（见 03-06）；进程身份用 `user` / `group` 一类降权选项与 `chroot`（选项名需对照 `configure.ac`、`suricata.yaml.in` 实际版本核验），`src/suricata.c` 约 3186 行一类降权入口在能力就绪后收敛主线程权限；unix socket 文件属主与权限要限制到运维组，`suricatasc` 能热加载规则、重开日志、读计数，等于能改检测行为与证据；EVE 落盘目录不可世界可写，`etc/suricata.logrotate.in` 的 HUP 轮转与 `etc/suricata.service.in` 的 `USR2` 重载要在降权身份下验证仍可用。

资源上限排第三，且必须配超限策略。`flow.memcap`、`stream.reassembly.memcap`、`max-pending-packets`、`app-layer` 各协议的 memcap、`dataset` 默认 memcap 要按 `doc/userguide/performance/tuning-considerations.rst` 的启动期内存公式统一核算（公式中的常量与默认值需对照实际版本核验）；`memcap-policy` 的 `drop-packet` / `pass-packet` / `drop-flow` 一类取值决定超限行为，需对照 `suricata.yaml.in` 实际版本核验。观测侧用 `flow.memuse`、`tcp.memuse`、`tcp.reassembly_memuse`、`flow.emerg_mode_entered`、`tcp.ssn_memcap_drop`、`tcp.segment_memcap_drop` 与 `suricatasc memcap-list` / `dump-counters` 验收；所有容量数字标注「需在目标机型实测」。

下表按「攻击面 → 风险 → 加固手段 → 源码或配置依据」组织，属场景处置而非参数清单（完整清单见 04-xx，条目化速查见 04-08，案例见 08-04）。

| 攻击面 | 风险 | 加固手段 | 源码或配置依据 |
|---|---|---|---|
| 外部规则集 | 编译期内存与时间膨胀 | 固定来源、校验和、`-T` 门禁 | `detect-engine-loader.c` 与 `detect-parse.c` |
| 线上畸形流量 | 流表与重组 memcap 耗尽 | flow 与 stream memcap 加策略 | `flow.c` 与 `stream-tcp-reassemble.c` |
| 抓包与控制面 | 权限过大或越权命令 | 降权、capabilities、socket 权限 | `suricata.c` 与 `runmode-unix-socket.c` |
| EVE 落盘目录 | 日志被篡改或删除 | 目录属主与轮转权限 | `output-json.c` 与 `suricata.logrotate.in` |
| 启动期分配 | 起测前内存吃满 | 核算 max-pending-packets 内存账 | `util-mem.h` 与 `tuning-considerations.rst` |

常见陷阱归纳如下。其一，只设 memcap 不设 `memcap-policy`，超限行为退化为默认值，等于策略没配。其二，把 BPF 过滤或 `stream.bypass` 当成安全加固，它们改变的是输入与可见性，不是权限边界，用了就必须记录过滤表达式与可接受的漏检。其三，忽略编译期与运行期的区别：运行期 memcap 再严也救不了「规则编译阶段就把内存吃满」。其四，用调试构建验证加固效果：`--build-info` 里带 profiling 或 Sanitizer 特征，观测结论作废，按 02-05 重编生产变体。其五，忽略能力边界：把「加密载荷不可见」当成检测缺陷去「加固」，或把「加线程」写成必然线性提速，都是方向性错误。所有约束是否生效，最终要回到同一组计数与降权后的实际能力边界验收（图 08-05-02）。

### 7. 小结与延伸阅读

本篇把加固收敛成一句话：给不可信输入设三段信任边界、给引擎资源设三层上限、给进程与控制面设最小权限，并让所有约束回到同一组计数上验收。三段边界分别是规则进入检测引擎的编译期边界（图 08-05-01 的 `pcre` / `dataset` 与签名分组）、报文进入流与重组子系统的运行期边界（flow / stream / app-layer memcap）、外部命令与日志落点的运维边界（unix socket 与 EVE 目录）；三层上限分别是编译期门禁、运行期 memcap 加 `memcap-policy`、启动期内存账（图 08-05-02）。源码锚点落在 `src/detect-parse.c`、`src/detect-engine-loader.c`、`src/detect-engine-register.c`、`src/conf.c`、`src/flow.c`、`src/stream-tcp-reassemble.c`、`src/app-layer-htp-mem.c`、`src/util-mem.h`、`src/output-json.c`、`src/suricata.c`、`suricata.yaml.in`、`etc/suricata.logrotate.in`、`etc/suricata.service.in`。再强调三条不能写反的边界：Suricata 不做转发、不是防火墙，内联靠 verdict（原理见 06-12）；加密载荷不可见；Hyperscan 是可选加速、缺失回退 AC。`suricata-update` 是分仓独立工具（见 07-11）；`src/util-threshold.c` 在当前 main 快照中不存在，阈值实现需对照实际版本核验。本篇只讲场景组合与输出判读，不重列参数全集：完整清单见 04-02 / 04-03 / 04-04 / 04-07；结构体逐字段见 05-05 / 05-08 / 05-09；流水线、规则编译、MPM、流重组、EVE、IPS 的机制见 06-01 / 06-04 / 06-06 / 06-07 / 06-11 / 06-12；detect、flow、app-layer、output、util 与 conf、控制面模块见 07-02 / 07-03 / 07-04 / 07-07 / 07-09 / 07-12。统一交叉引用写作（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）。延伸阅读：08-04 给六个完整故障案例的现象、复现、证据、根因、修复与验证；08-06 把本篇的加固项与监控指标、回滚方案一起收进上线 checklist；基准方法回看 08-01，调优方法回看 08-02，判定顺序回看 08-03。

## 08-06 上线 checklist 与运维手册

### 1. 目标与拓扑

本篇把 08-01 到 08-05 的成果收进一套可执行的上线动作：上线前逐项打勾的检查清单、上线后持续观测的指标定义、以及指标越界时的回滚步骤。目标不是「把进程跑起来」，而是让「跑起来」这件事可验收、可观测、可回退——任何一项检查没有取证、任何一个指标没有健康判据、任何一次升级没有回滚快照，都不算上线完成。这与 08-04 的案例库、08-05 的加固是分工关系：08-04 讲故障发生后怎么复现与修复，08-05 讲事前把攻击面收窄，本篇讲把两者固化成上线门禁与值班手册，三者共用同一套证据来源（`suricata.log`、`stats.log`、`eve.json`、`--dump-config`、`--build-info`、`suricatasc dump-counters`）与同一组源码锚点。

先立四条贯穿全篇的边界。其一，Suricata 是 IDS / IPS / NSM 引擎，不做 IP 转发、不做路由、不是防火墙；IDS 旁路只告警不丢弃，内联阻断依靠 NFQUEUE / AF_PACKET 桥接的 verdict（原理见 06-12），上线清单里对 IPS 的检查因此是「verdict 通道与策略」而不是「转发带宽」。其二，引擎只对自身解码并重组到的流量做检测，TLS 等加密载荷不可见，能拿到的是握手元数据、证书、SNI、JA3 一类信息（字段需对照实际版本核验），不能宣称能读到 HTTPS 明文正文；监控指标里的「可见流量」口径必须据此定义。其三，多线程 runmode 分 workers / autofp / single（`src/runmodes.c`、`src/runmode-*.c`），流亲和、RSS / fanout 与队列分配共同决定扩展性，不得把「加线程」写成必然线性提速（原理见 06-13）。其四，规则语法兼容 Snort 但有自有扩展（`src/detect-parse.c`、`src/detect-engine-register.c`），不能宣称 100% 兼容；`suricata-update` 是与内核主程序分仓、独立发版的独立工具（见 07-11）；Hyperscan 是可选 MPM 加速（`src/util-mpm-hs.c`，构建开关见 `configure.ac`，选项名需对照实际版本核验），缺失时回退 AC 等其他实现（`src/util-mpm-ac*.c`）。版本基准统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验；凡吞吐、pps、丢包率、内存占用、容量数字一律标注「需在目标机型实测」，不给绝对值、不给跨机型通用数字。本篇不重列参数全集，只给最小必要调用，完整清单见 04-02 / 04-03 / 04-04 / 04-07；结构体逐字段见 05-xx；机制见 06-xx；模块见 07-xx。统一交叉引用写作（字段见 05-08 ｜ 参数见 04-02 ｜ 原理见 06-11 ｜ 模块见 07-07）。

### 2. 前置条件与环境

环境侧的冻结项与 08-01 一致，且要额外归档「回滚所需的一切」。二进制侧 `suricata --build-info` 对应 `src/suricata.c` 约 763 行长选项与 `build-info.h` 的包含（约 992 行），用它确认 AF_PACKET、DPDK、NFQUEUE、Hyperscan、profiling、unittests 等编译期特性；`suricata --dump-config` 打印解析后的运行配置（约 761 行），比直接看 yaml 更能发现「某个键其实取了默认值」；`suricata -T` 解析为 `conf_test`（约 1466、1960-1961 行 `case 'T'`）、置 `RUNMODE_CONF_TEST`（约 2210 行）、成功打印 "Configuration provided was successfully loaded. | 错线程分派 | wrong_thread 与 pkt_on_wrong_thread | `high-performance-config.rst` 诊断项 | 计数不持续升高 |
| EVE 落盘 | eve.json 体积与下游到达速率 | `src/output-json.c` 与采集端 | 体积增长 \| 采集端无积压 |

第三步，灰度与容量评估。灰度按「先单实例小流量、再按 RSS 队列或 TAP 分流扩量」推进，每档停留多个 `stats.interval`（`suricata.yaml.in` 的 `stats:` 段约 65 行，默认 `interval: 8`，键名与默认值需对照实际版本核验），等计数收敛后再读值；预热不足（刚启动就取第一帧计数）时规则分组、MPM 构建、流表备用池都还在初始化，读数不可用。容量评估必须用在线流量，离线回放偏乐观不能当承诺；`doc/userguide/performance/statistics.rst` 明确提醒关停时打印的内核丢包统计不完整，网卡层必须靠 `ethtool -S <iface>` 补齐。所有容量数字标注「需在目标机型实测」。

第四步，固化升级与回滚步骤。升级动作按 `suricata-update` 合并规则（独立工具，见 07-11）→ `suricata -T` 校验 → `suricatasc -c "reload-rules"` 热加载 → 观察多个窗口 → 记录新基线；运行中改 yaml 不会自动生效，`threading` 的 CPU 集、`af-packet` 的 `threads` / `ring-size`、`max-pending-packets`、各类 memcap、`mpm-algo` 与 `detect.profile` 都在启动时读取，必须重启进程并重跑 `-T`。回滚触发条件、动作与验证见下表，六步按序执行、每步留证。

| 步骤 | 动作 | 验收依据 |
|---|---|---|
| 1 判定 | 连续多窗口指标越界 | 指标表门槛与告警记录 |
| 2 冻结现场 | 归档当前日志与计数 | `tar` 归档与时间戳 |
| 3 停新实例 | 按 service 单元停止新版本 | `etc/suricata.service.in` |
| 4 切回快照 | 恢复上一版二进制、yaml、规则集 | 校验和逐项比对 |
| 5 自检 | 重跑 `suricata -T` 与 `--build-info` | 成功数稳定 \| 失败数为零 |
| 6 恢复观测 | 灰度恢复流量并多窗口观察 | 指标回到旧基线 |

第五步，值班命令闭环。下面给一组上线自检命令，按「前置检查 → 执行 → 验证输出 → 归档」组织；命令文件名取具体值便于照跑，带尖括号的路径需替换成本机真实路径，命令全集的完整清单见 04-07，RPC 命令见 04-07 / 07-12。

```bash
mkdir -p goline/log goline/rollback
# 前置检查：钉死二进制特性、导出运行配置、核对日志目录
suricata --build-info > goline/build-info.txt
suricata --dump-config -c suricata.yaml > goline/dump-config.txt
ls -ld /var/log/suricata

# 执行：规则自检后进入灰度，日志与计数落到独立目录
suricata -T -c suricata.yaml -l goline/log
suricata -c suricata.yaml --af-packet=eth1 -l goline/log &

# 验证输出：读取加载、告警、丢包与内存计数
grep -E 'successfully loaded|rules failed|Exiting' goline/log/suricata.log
grep -c '"event_type":"alert"' goline/log/eve.json
suricatasc -c "dump-counters" goline/log/suricata.socket | grep -E 'kernel_drops|kernel_packets|flow.memuse|reassembly_memuse'

# 归档：冻结回滚四件套（二进制、yaml、规则集、计数快照）
cp suricata.yaml goline/rollback/suricata.yaml
sha256sum rules/suricata.rules > goline/rollback/rules.sha
tar -cf goline/rollback/snapshot.tar goline/build-info.txt goline/dump-config.txt goline/log/stats.log
```

第六步，回滚命令闭环。触发条件成立后按表执行，核心是「先恢复回滚四件套、再自检、再灰度」，不要在未自检的情况下直接放量。

```bash
# 停新实例并切回上一版快照
systemctl stop suricata
cp goline/rollback/suricata.yaml /etc/suricata/suricata.yaml
tar -xf goline/rollback/snapshot.tar -C goline/rollback

# 自检：确认二进制特性与规则加载
suricata --build-info | grep -iE 'hyperscan|profiling'
suricata -T -c /etc/suricata/suricata.yaml -l goline/log

# 灰度恢复并多窗口观察
suricata -c /etc/suricata/suricata.yaml --af-packet=eth1 -l goline/log &
suricatasc -c "dump-counters" goline/log/suricata.socket | grep -E 'kernel_drops|flow.memuse'
```

### 4. 验证方法与预期结果

C 型实战篇必须给「预期输出 + 判读要点」。本节的判读对象有两类：一是上线自检的 `-T` 与 `--build-info` 输出，二是灰度期的一帧统计计数。先看自检，下面是典型输出（示例输出，具体格式需对照实际版本核验）。

```text
示例输出，具体格式需对照实际版本核验
[Info] - Running suricata under test mode
[Config] - rule-files: suricata.rules, local.rules
[Config] - default-rule-path: /etc/suricata/rules
[Info] - 2 rule files processed. 34128 rules successfully loaded, 0 rules failed
[Notice] - Configuration provided was successfully loaded. Exiting.
exit_code=0
```

逐行判读如下。第一行 "Running suricata under test mode" 确认进程进入 `RUNMODE_CONF_TEST`（`src/suricata.c` 约 2210 行）而非普通抓包模式；若这行没出现就直接开始收包，说明 `-T` 未生效或被其它参数覆盖，应回到约 1960-1961 行 `case 'T'` 分支核对命令行。第二行是配置树里的 `rule-files` 清单，判读要点是必须与归档的规则集快照逐项一致，配置树读取见 `src/conf.c` 的 `SCConfGetNode`（约 183 行）。第三行 `default-rule-path` 要与 `etc/` 下 `classification.config`、`reference.config` 的实际落位对应，路径写错时 `src/detect-engine-loader.c` 约 135 行会报 "opening rule file"。第四行是清单第 6 项的验收数值：`successfully loaded` 应为稳定的正整数且各轮一致，`failed` 必须为零；该行措辞与计数项需对照 `src/detect-engine-loader.c` 约 480 行起的实际版本核验，只要失败数非零就应停止上线，因为「规则没装全」会让吞吐虚高、告警虚低，所有容量结论作废。第五行 "successfully loaded. Exiting." 对应 `src/suricata.c` 约 3205 行的 `SCLogNotice`，是 `-T` 正常退出的标志。第六行 `exit_code=0` 以「零与非零」区分成功与失败，退出码具体取值需对照实际版本核验，禁止臆测数值。整段是示例，日志级别前缀与计数项在不同版本会变，一律以本机实际输出为准（字段见 05-05 ｜ 参数见 04-02 ｜ 原理见 06-06 ｜ 模块见 07-04）。

再看灰度期计数。下面是一帧 `stats.log` 三列格式节选（示例输出，具体格式需对照实际版本核验），其生成路径是 `src/counters.c` 的 `StatsOutput` 交给 `src/log-stats.c` 写盘、`src/output-json-stats.c` 写 `event_type: stats` 的 EVE 事件。

```text
示例输出，具体格式需对照实际版本核验
capture.kernel_packets                | Total   | 450001754
capture.kernel_drops                  | Total   | 0
detect.alert                          | Total   | 14721
tcp.reassembly_memuse                 | Total   | 67755264
flow.memuse                           | Total   | 6557568
flow.emerg_mode_entered               | Total   | 0
```

逐行判读如下。三列对应 `doc/userguide/performance/statistics.rst` 给出的 `Counter | TM Name | Value` 格式，第二列 `Total` 来自 `src/counters.c` 约 883 行的汇总行，采集脚本必须把 `Total` 行与各线程行分开，否则会把计数翻倍。`capture.kernel_packets` 与 `capture.kernel_drops` 来自 `src/source-af-packet.c` 约 2612-2613 行的 `StatsRegisterCounter`，在 AF_PACKET 模式下前者是正确送到用户态的包数、后者是被丢弃没送出来的包数；判读要点是看二者比值随时间是否抬头，稳定流量下 `kernel_drops` 增量应趋近于零，持续增长即说明收包侧跟不上，此时按 08-03 的「吞吐低」分支分层定位，而不是先加检测线程。`detect.alert` 是检测路径被触发的证据，含告警样本而它恒为零要回查可见性与 `vars` 的 `HOME_NET`（`suricata.yaml.in` 约 15、18-22 行）。`tcp.reassembly_memuse` 要与 `stream.reassembly.memcap` 一类上限对照，`flow.memuse` 与 `flow.memcap` 对照；`flow.emerg_mode_entered` 一旦非零说明流表进入紧急回收，是「内存涨」分支的重要旁证。整帧都要标注「需在目标机型实测」，此处数字仅为演示字段形态，具体格式与计数项需对照实际版本核验。实时复查用 `suricatasc dump-counters`，它走 `src/counters.c` 的 `StatsOutputCounterSocket`，适合在不中断灰度的情况确认计数是否仍在爬升；`suricatasc` 的 `memcap-list`、`iface-stat`、`reload-rules`、`reopen-log-files` 一类值班命令完整集合见 04-07 / 07-12。

### 5. 常见失败与排错

第一类失败是「门禁没过却放量」。典型表现是没跑 `-T` 就把流量切进来，结果规则一条没装、告警恒为零，或 `--build-info` 里带调试特征却拿来当生产变体。校验脚本应把「二进制特性 + `-T` 规则数 + 采样窗口」三项作为硬门禁，任一缺失就不允许进入灰度；带 profiling 或 Sanitizer 的构建按 02-05 重编。另一类常见错误是拿离线回放结果当生产容量承诺，灰度期必须用在线流量验证并标注「需在目标机型实测」。

第二类失败是输出与轮转没就位。`-l` 指定的日志目录不对、`outputs` 的 `filetype` 不是普通文件、`types` 里没开 `alert`，都会让「进程在跑、证据却没落下来」；判读顺序是先 `ls -l` 看 `eve.json` 是否生成、再 `grep -c` 看事件类型、再看采集端是否收到。`src/suricata.c` 约 2993 / 3000 行的目录检查与 `src/output-json.c` 约 1096 行的打开动作是对应源码依据。`etc/suricata.logrotate.in` 的 HUP 轮转与 `etc/suricata.service.in` 的 `USR2` 重载要在降权身份下实测可用，否则日志轮转或规则重载会在上线后静默失效。

第三类失败是灰度读数不可信。`stats.log` 的 `Total` 行与各线程行混读会翻倍计数；`kernel_drops` 增长不配 `ethtool -S` 会把网卡层丢包误判成收包侧瓶颈；`tcp.reassembly_gap` 非零既可能是丢包也可能是坏校验和或流引擎内存吃紧，不能单凭它断定网卡丢包。预热不足（刚启动就取第一帧计数）时规则分组、MPM 构建、流表备用池还在初始化，读数不可用，采样窗口至少要跨多个 `stats.interval`。系统侧 `irqbalance` 未关、governor 漂移、跨 NUMA 绑核、驱动或内核升级改变性能特征（`doc/userguide/performance/high-performance-config.rst` 结尾有明确提示），都会让灰度读数与基准不可比。

第四类失败是回滚失败。最常见的是没留「上一版四件套」（二进制、yaml、规则集、计数快照），指标越界时无回滚目标；其次是切回后没重跑 `-T` 就放量，把旧配置里的路径错误一起带回来；再次是把「启动期生效」与「运行期可变」混为一谈——`threading`、`af-packet.threads`、`max-pending-packets`、各类 memcap、`mpm-algo` 与 `detect.profile` 都要重启才生效，而规则集可 `reload-rules` 热加载、日志可 `reopen-log-files` 重开，热加载后 `detect.alert` 与内存计数可能跳变，若不记录时间线很容易把一次规则更新误判成内存涨或告警风暴。回滚六步（判定、冻结现场、停新实例、切回快照、自检、恢复观测）必须按序执行、每步留证。

下表把现象、判读证据与修复方向列成速查，属现象与处置而非参数清单（完整清单见 04-xx，条目化速查见 04-08，案例见 08-04）。

| 现象 | 判读证据 | 修复方向 |
|---|---|---|
| 门禁未过已放量 | `--build-info` 与 `-T` 输出 | 补门禁、重编生产变体 |
| 有进程无 eve.json | `ls -l` 与 `--dump-config` 的 outputs | 对齐 filetype 与 `-l` 目录 |
| 灰度读数抖动 | 对照表与 `--dump-config` 差异 | 冻结系统侧状态、延长预热 |
| 轮转或重载失效 | logrotate 与 service 单元日志 | 在降权身份下实测 HUP 与 USR2 |
| 指标越界 | 多窗口指标曲线 | 按六步回滚并留证 |
| 回滚后问题依旧 | 切回后的 `-T` 与校验和 | 核对四件套完整性、重新自检 |

### 6. 小结

本篇把上线收敛成一句话：先过门禁、再灰度、持续观测、随时可回滚。20 项清单按五组逐项打勾（图 08-06-01 的静态门禁、输出门禁、容量门禁），监控指标按收包、检测、内存、输出四层定义并汇到阈值判定（图 08-06-02），升级与回滚按六步留证执行。所有留证回到同一组证据源：`suricata --build-info`、`suricata --dump-config`、`suricata -T`、`suricata.log`、`stats.log`、`eve.json` 的 `event_type: stats`、`suricatasc dump-counters` 与 `ethtool -S`，对应源码落在 `src/suricata.c`、`src/detect-engine-loader.c`、`src/detect-parse.c`、`src/detect-engine-register.c`、`src/conf.c`、`src/output-json.c`、`src/counters.c`、`src/log-stats.c`、`src/output-json-stats.c`、`src/source-af-packet.c`、`src/flow.c`、`src/stream-tcp-reassemble.c`、`src/util-affinity.c`、`src/runmodes.c`、`suricata.yaml.in`、`etc/suricata.logrotate.in`、`etc/suricata.service.in`。反复强调四条边界：Suricata 只对自身解码并重组到的流量做检测、加密载荷不可见；不做转发、不是防火墙，IDS 旁路只告警不丢弃；加线程不必然线性提速（原理见 06-13）；`suricata-update` 是分仓独立工具（见 07-11），规则语法兼容 Snort 但非 100% 兼容，Hyperscan 是可选加速。所有容量、吞吐、丢包率、内存占用数字一律标注「需在目标机型实测」，离线回放结果不能当生产容量承诺。本篇只讲场景组合与输出判读，不重列参数全集：完整清单见 04-02 / 04-03 / 04-04 / 04-07；结构体逐字段见 05-05 / 05-08 / 05-09；流水线、规则编译、EVE、IPS、runmode 的机制见 06-01 / 06-06 / 06-11 / 06-12 / 06-13；抓包源、输出、util 与 conf、计数器与控制面模块见 07-06 / 07-07 / 07-09 / 07-12。统一交叉引用写作（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）。至此 08 册六篇齐备：基准方法见 08-01，调优见 08-02，判定顺序见 08-03，案例库见 08-04，加固见 08-05，上线与回滚见本篇。
