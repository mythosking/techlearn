# Suricata 技术资料 · 02 编译与构建

## 02-01 源码获取、仓库目录结构与依赖矩阵

### 1. 背景与动机

编译一册的起点并不是敲下第一条命令，而是先弄清「手里到底拿到了什么」。本套资料的唯一事实锚点是 `upstream_src/suricata/suricata-main/`，注意 `suricata/` 目录下还多一层 `suricata-main/` 归档目录，那才是真实仓库根。这一层差异看似琐碎，却是从业者最常踩的第一个坑：把 `configure.ac`、`Makefile.am`、`autogen.sh` 的路径写少一层，后续所有命令都会落空；把本套资料里带 `suricata-main/` 前缀的相对路径误当成仓库内惯用写法，又会在对照上游文档时找不到文件。去掉这层前缀才是 `src/decode.h`、`configure.ac`、`rust/` 这类仓库内写法，两种写法在资料里各有用途，必须分清。先把这层路径纪律立住，后面谈构建才有共同的坐标。

第二个动机来自构建系统本身的高度分散。Suricata 不是「一个 Makefile 编到底」的工程：顶层由 autotools 驱动，`configure.ac` 负责选项定义与依赖探测，`Makefile.am` 负责子目录装配与安装目标，`autogen.sh` 负责生成 configure 脚本；Rust 侧又是一整套独立的 Cargo 工程，由 `rust/Makefile.am`、`rust/Cargo.toml.in`、`rust/cbindgen.toml` 共同描述。更关键的是，仓库里大量文件是「模板」而非「成品」：`suricata.yaml.in` 要被渲染成 `suricata.yaml`，`rust/Cargo.toml.in` 要被生成成 `rust/Cargo.toml`，`rust/Cargo.lock.in` 对应生成 `rust/Cargo.lock`。若把模板误当成可直接编辑的成品，改了半天不生效；若把生成物当成源码提交，又会在清理后被覆盖。理解「哪些是输入、哪些是产物」，是读懂整个构建链的前提。

第三个动机是依赖矩阵。configure 阶段会用 `AC_CHECK_LIB`、`AC_CHECK_HEADER`、`PKG_CHECK_MODULES` 等宏逐一探测系统里的头与库，硬依赖缺失时直接报错退出，可选依赖缺失时或告警或关闭对应能力。很多「编译失败」其实在 configure 的第一屏就已经给出了答案，只是读者没把报错与探测宏对应起来。提前读懂依赖的分类，能在装依赖阶段就备齐料，而不是等 make 报到一半再回头补包。这也是本篇把「源码获取、目录结构、依赖矩阵」三者放在一起讲的原因：它们共同回答「编译前需要准备什么」。

最后要明确本册的边界。按 SPEC 第 4 节的去重约定，构建选项、构建变量与命令行参数的全集是 04 册的权威范围，本册只讲「怎么组合、怎么验证」，一律写「完整清单见 04-01」「完整变量见 04-01」；结构体逐字段写「字段见 05-xx」，机制与调用链写「原理见 06-xx」，按 `src/` 目录划分的模块能力写「模块见 07-xx」。本篇不列任何参数全集、不展开结构体字段、不重复 06 册的流水线实现。读者若只想查某个选项叫什么，请直接翻 04-01；本篇回答的是「拿到源码之后，应该先看哪些文件、按什么顺序把它们变成可编译的工程」。

### 2. 核心概念

第一个核心概念是「双层工程」。顶层 `Makefile.am` 里的 `SUBDIRS = rust src plugins qa rules doc etc python ebpf $(SURICATA_UPDATE_DIR)` 揭示了装配顺序：`rust` 排在 `src` 之前，意味着 make 期必须先产出 Rust 静态库，C 主程序才能链接它。这不是随意排列，而是由「C 侧要包含 Rust 生成的头文件、要链接 Rust 产出的 `libsuricata_rust.a`」这一依赖决定的。`configure.ac` 里 `RUST_SURICATA_LIBNAME="libsuricata_rust.a"`、`RUST_SURICATA_LIBDIR` 依据 `enable_debug` 指向 `debug` 或 `release` 目录，共同定义了这份静态库的名字与落点。把 Suricata 写成纯 C 项目，或者以为 Rust 只是可选插件，都会与这套装配顺序矛盾；`rust/` 与 Cargo 是构建的一部分，这一点贯穿全册。

第二个核心概念是「模板与生成物」。`configure.ac` 末尾用一长串 `AC_CONFIG_FILES` 声明了要生成的文件：顶层 `Makefile` 与 `src/Makefile`、`rust/Makefile`、`rust/Cargo.lock`、`rust/Cargo.toml`、`rust/.cargo/config.toml`，各 Rust 子 crate 的 `Makefile` 与 `Cargo.toml`，`qa/` 下三个 Makefile，`rules/Makefile`、`doc/Makefile`、`doc/userguide/Makefile`，`suricata.yaml`、`etc/Makefile`、`etc/suricata.logrotate`、`etc/suricata.service`，`python/suricata/config/defaults.py`、`ebpf/Makefile`、`libsuricata-config`，以及 `plugins/` 下 pfring、napatech、ndpi 三个插件目录的 Makefile。换句话说，仓库里以 `.in` 结尾或由 `AC_CONFIG_FILES` 点名的文件，都是 configure 阶段由变量替换生成的。`autogen.sh` 里还有一处配套逻辑：若 `cargo` 存在且 `rust/Cargo.lock` 已存在，就把它删掉，因为源码树里权威的是 `Cargo.lock.in` 模板，锁文件应由 configure 与 make 重新生成。理解这一点，就不会去手工维护一个迟早被覆盖的 `Cargo.toml`。

第三个核心概念是依赖的三分类。第一类是硬依赖，configure 探测不到就 `exit 1` 或在提示里给出各发行版的安装命令，代表性的有 `AC_CHECK_LIB(z,inflate)` 对应的 zlib、`AC_CHECK_LIB(pcre2-8, pcre2_compile_8)` 对应的 PCRE2、`AC_CHECK_LIB(yaml,yaml_parser_initialize)` 对应的 libyaml、`AC_CHECK_LIB(jansson, json_dump_callback)` 对应的 Jansson、`AC_CHECK_LIB(pcap, pcap_open_dead)` 对应的 libpcap，以及 `AC_CHECK_LIB(pthread, pthread_create)`。第二类是可选加速与可选能力：Hyperscan 走 `PKG_CHECK_MODULES([libhs], libhs,...)` 加 `hs.h` 与 `hs_compile` 的双重探测，缺了就 `enable_hyperscan="no"` 并回退到 AC 等其他多模式匹配实现；hwloc、GeoIP2 的 libmaxminddb、libmagic、hiredis、liblz4、libcap-ng、libunwind 也都属于「有则增强、无则告警或关闭」的一类。第三类是平台后端依赖：NFQUEUE、NFLOG、DPDK、Netmap、AF_XDP、PF_RING、DAG、Napatech、WinDivert、IPFW、eBPF 各自的头与库，往往还叠加内核版本、驱动、大页等运行期条件。把依赖分成这三类，排障时就能快速判断「这是必须补齐的、还是可以暂时绕开的」。

第四个核心概念是「获取方式影响前置条件」。从官方发布归档构建时，configure 脚本通常已随包提供，依赖相对少；从 git 源构建时则必须先跑 `autogen.sh`，因而额外需要 `libtoolize`（或 `glibtoolize`）、`autoreconf`、automake、autoconf 这一套 autotools 工具链，`configure.ac` 里 `--enable-python` 默认开启且注释明确写着 Python「is also required when building from git」。本套资料依据的是上游 main 快照（2026-11 抓取），因此按「从源码树开始」来讲述，具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验，正文不写绝对值。无论哪种获取方式，进入目录后的第一个动作都应该是核验文件是否齐全，而不是急着 configure。

### 3. 关键数据结构与源码位置

顶层构建输入集中在少数几个文件里，逐一认准能省去大量试错。`configure.ac` 开头是 `AC_INIT`、`AC_CONFIG_HEADERS([src/autoconf.h])`、`AC_CONFIG_SRCDIR([src/suricata.c])`、`AC_CONFIG_MACRO_DIR(m4)`、`AM_INIT_AUTOMAKE([tar-ustar subdir-objects])`、`LT_INIT` 与 `PKG_PROG_PKG_CONFIG`：它们分别定义工程元信息、生成的配置头、作为「源码存在性证据」的 `src/suricata.c`、宏目录、automake 行为、libtool 与 pkg-config 探测。`AC_CONFIG_SRCDIR` 尤其值得留意，configure 用它确认自己跑在正确的源码目录里，路径写错会直接报「找不到源码」。`AC_CONFIG_HEADERS` 则解释了为什么 `src/autoconf.h` 里满是 `HAVE_*`、`BUILD_*` 条件宏——它们是 configure 探测结果写进 C 代码的桥梁。

`Makefile.am` 与 `autogen.sh` 是另两个必读文件。顶层 `Makefile.am` 的 `AUTOMAKE_OPTIONS = foreign 1.4`、`ACLOCAL_AMFLAGS = -I m4` 说明这是非 GNU 规范的工程且宏来自 `m4/`；`EXTRA_DIST` 列出随发行包附带的内容，包括 `ChangeLog`、`COPYING`、`LICENSE`、`suricata.yaml.in`、`threshold.config`、`SECURITY.md`、`lua/`、`acsite.m4` 以及 `scripts/` 下几份依赖与文档脚本；`SUBDIRS` 与 `DIST_SUBDIRS` 则划定了递归构建与打包范围。`autogen.sh` 的内容极短却关键：先找 `libtoolize` 或 `glibtoolize` 并执行 `libtoolize -c`，再 `autoreconf -fv --install`，最后打印「You can now run ./configure and then make.」。把这三步记牢，就能解释「为什么发布归档可以直接 configure，而 git 源必须先 autogen」。

把归档目录按职责分层，可得到下表；完整目录清单以本地快照为准，凡 0.1 节未列出或无法核实的路径不写进正文。

| 目录或文件 | 职责 | 构建期角色 |
|---|---|---|
| suricata-main/configure.ac | 定义选项与依赖探测 | 生成 configure 脚本的输入 |
| suricata-main/Makefile.am | 顶层 SUBDIRS 与安装目标 | 生成顶层 Makefile |

### 4. 关键流程与调用链

从一份静态源码树到一个可安装的产物，调用链可以拆成四段。第一段是 `autogen.sh`：探测 `libtoolize` 或 `glibtoolize`，执行 `libtoolize -c` 生成 libtool 辅助文件，再用 `autoreconf -fv --install` 把 `configure.ac` 与各级 `Makefile.am` 展开成 `configure` 脚本与 `Makefile.in`；若检测到 `cargo` 且 `rust/Cargo.lock` 存在则删除它，为后续由模板重新生成让路。这一段讲的是「做什么」：把人类维护的 autotools 输入变成机器可执行的 configure。第二段是 `./configure`：逐条执行 `AC_CHECK_*`、`PKG_CHECK_MODULES` 完成依赖探测，按 `AC_ARG_ENABLE` / `AC_ARG_WITH` 结果写出条件宏与 `AM_CONDITIONAL`，再用 `AC_CONFIG_FILES` 批量生成 Makefile、`rust/Cargo.toml`、`suricata.yaml` 等文件，同时通过 `EXPAND_VARIABLE` 计算 `e_sysconfdir`、`e_logdir`、`e_datarulesdir` 等安装路径宏。

第三段是 `make`：顶层按 `SUBDIRS` 递归，先进入 `rust/` 由 `rust/Makefile.am` 的 `all-local` 调用 `cargo build` 产出静态库并用 cbindgen 生成 `gen/rust-bindings.h`、`gen/rust-ffi.h`、`gen/htp/htp_rs.h`，再进入 `src/` 编译 C 主程序并链接 `RUST_SURICATA_LIB`，随后处理 `plugins/`、`qa/`、`rules/`、`doc/`、`etc/`、`python/`、`ebpf/` 等子目录。第四段是安装：`install-data-am` 只打印一句提示，告诉用户可另跑 `make install-conf` 或 `make install-full`；`install-full` 是 `make install`、`make install-conf`、`make install-rules` 三者的组合；`install-conf` 把 `suricata.yaml`、`etc/classification.config`、`etc/reference.config`、`threshold.config` 以 `-m 600` 安装到 `e_sysconfdir`，并创建日志、证书、运行、数据与签名组缓存目录；`install-rules` 在 `INSTALL_SURICATA_UPDATE` 成立时调用 `suricata-update --no-test --no-reload` 拉取规则——注意这里是把 `suricata-update` 当独立可执行文件调用，正好印证它与 `src/` 主程序分仓、独立发版、不参与主程序编译的定位。此外还有 `install-library`、`install-headers` 与 `libsuricata-config`，供二次开发把 Suricata 当库使用。

configure 收尾还有一条容易被忽略的「凭据链」。`configure.ac` 末尾把 `SURICATA_BUILD_CONF` 这段配置摘要 `echo` 到终端，同时又用 `printf(` 逐行加引号写进 `src/build-info.h`；`src/suricata.c` 的 `PrintBuildInfo()` 通过 `#include "build-info.h"` 把这段内容打印出来，于是 `suricata --build-info` 能回显与 configure 结束屏几乎一致的特性清单。这条链把「构建时选了什么」与「编出来的程序里有什么」连成闭环，是 02-02 与 02-03 反复使用的验证手段。源码获取、目录分层与四段构建链的关系见图 02-01-01。

### 5. 配置/命令/代码实例

认识一份源码树，最有效的动作是「列目录 + 抽查探测宏 + 核验工具链」。下面这组命令按「前置检查 → 抽查 → 核验」闭环给出，归档名与路径以实际抓取产物为准，完整构建选项见 04-01、完整变量见 04-01。

```bash
# 进入真实仓库根（上游归档解压后多一层 suricata-main/）
cd suricata-main

# 列出顶层，确认 autotools 输入与资源目录齐全
ls -1

# 抽查 configure.ac 里的依赖探测宏，确认依赖来源
grep -nE 'AC_CHECK_LIB|PKG_CHECK_MODULES|AC_CHECK_HEADER' configure.ac | head -30

# 核验 autotools 与 Rust 工具链是否就位
command -v libtoolize || command -v glibtoolize
command -v autoreconf
command -v cargo
command -v pkg-config
```


逐行判读这段输出。前二十行是 `ls -1` 的顶层清单：`COPYING` 是 GPLv2 许可正文，合规评估以它为准；`ChangeLog` 与 `configure.ac` 是版本与构建事实的核验依据，但两者里的版本字样只作依据、不得抄进正文当本套资料的版本号；`Makefile.am`、`autogen.sh`、`configure.ac` 三者串起 autotools 链；`suricata.yaml.in` 是被渲染的配置模板。`src/` 与 `rust/` 并列出现，直接否定「纯 C 项目」的说法，也提示 `SUBDIRS` 里 Rust 先于 C；`etc/`、`rules/`、`doc/`、`qa/`、`scripts/`、`plugins/`、`python/`、`ebpf/`、`lua/`、`examples/` 分别对应配置样例、规则、文档、测试、辅助脚本、插件、控制面、eBPF、Lua 扩展与示例；`suricata-update` 是独立规则工具目录；`threshold.config` 与 `bundle.txt` 是阈值样例与打包相关文件。后面八行是 `grep` 命中的探测宏，每行前缀是 `configure.ac` 的真实行号：`AC_CHECK_HEADER(zlib.h)` 与 `AC_CHECK_LIB(z,inflate)` 是 zlib 的头与符号双探测，`pcre2-8` 与 `pcre2_compile_8` 对应 PCRE2，`PKG_CHECK_MODULES([libhs], libhs,...)` 说明 Hyperscan 优先走 pkg-config，`yaml_parser_initialize`、`json_dump_callback`、`pcap_open_dead` 分别是 libyaml、Jansson、libpcap 的链接测试符号。判读要点是：行号与确切写法会随上游演进变化，务必以本地 `configure.ac` 为准；看到某个必需库探测失败，应先按 configure 报错里给出的发行版包名补装，而不是改探测宏绕过。最后四行 `command -v` 若无输出，说明对应工具缺失，此时跑 `autogen.sh` 会在第一步就失败。

把依赖按「必需 / 可选加速 / 平台后端」归类，可得到下表；表中只列代表项，完整清单见 04-01，具体库名与版本下限需对照 `configure.ac` 实际版本核验。

| 依赖类别 | 探测宏与代表符号 | 缺失后果 |
|---|---|---|
| 压缩基础 | AC_CHECK_LIB 探测 z 的 inflate | 打印发行版安装提示后退出 |
| 正则引擎 | AC_CHECK_LIB 探测 pcre2-8 | 报错退出，PCRE2 为必需 |
| YAML 配置 | AC_CHECK_LIB 探测 yaml_parser_initialize | 报错退出，配置树无法加载 |
| JSON 输出 | AC_CHECK_LIB 探测 json_dump_callback | 提示 Jansson 必需后退出 |
| 抓包基础 | AC_CHECK_LIB 探测 pcap_open_dead | 报错退出 |
| 可选 MPM 加速 | PKG_CHECK_MODULES 探测 libhs 与 hs_compile | 回退 no，改用 AC 等其他实现 |
| 可选平台能力 | hwloc、GeoIP、libmagic、hiredis、lz4 各自探测 | 多为警告或对应能力关闭 |

补齐依赖后，进入真实仓库根还应做一次「模板齐全性」核验，避免把生成物当源码，命令如下。

```bash
# 确认 autotools 输入与 Rust 模板齐全，缺项不应直接 ./configure
for f in configure.ac Makefile.am autogen.sh suricata.yaml.in \
         rust/Cargo.toml.in rust/Cargo.lock.in rust/cbindgen.toml \
         rust/Makefile.am; do
  test -f "$f" || echo "missing: $f"
done

# 注意源码树里没有现成的 Cargo.toml，只有 Cargo.toml.in 模板
ls -1 rust/ | grep -E 'Cargo|cbindgen|Makefile'
```

### 6. 注意事项、陷阱与最佳实践

第一条陷阱是路径与文件名。归档多一层 `suricata-main/`，本套资料给的是相对 `upstream_src/suricata/` 的真实路径，去掉这层前缀才是仓库内惯用写法；混用两者会让命令与文档对不上。第二条是「Cargo.toml 不存在」：本快照的 `rust/` 下是 `Cargo.toml.in`、`Cargo.lock.in`、`cbindgen.toml`、`Makefile.am` 与 `rust/src/`，没有现成的 `Cargo.toml`，`autogen.sh` 还会主动删除可能残留的 `Cargo.lock`。手工创建 `Cargo.toml` 或提交生成物，会在下次 configure 时被覆盖，属于典型的「改了不生效」。正确姿势是改 `.in` 模板或改 `configure.ac` 的 `AC_CONFIG_FILES` 声明，改完重跑 `./autogen.sh && ./configure`。

第三条是别绕过依赖探测。configure 在 zlib、PCRE2、libyaml、Jansson、libpcap 等必需库缺失时，会打印清晰的发行版安装命令后退出；有人图省事把探测宏注释掉，结果 make 阶段冒出成片「未定义引用」，反而更难定位。若库装在非标准路径，应使用 `configure.ac` 里定义的一系列 `--with-*-includes` / `--with-*-libraries` 把头与库目录指过去，具体选项名需对照实际版本核验，完整清单见 04-01。可选依赖则相反：Hyperscan 缺头或链接测试失败时 `enable_hyperscan` 回退为 no，引擎改用 `src/util-mpm-ac*.c` 等 AC 实现，绝不能把它写成必需依赖或唯一实现；同理，hwloc、GeoIP2、libmagic、hiredis、liblz4、libcap-ng 的缺失通常只导致告警或对应能力关闭，不必为了「configure 全 yes」而硬装一堆用不到的库。

第四条是生态与能力边界。`suricata-update` 与内核主程序分仓、独立发版，负责规则集下载与合并，不参与 `src/` 主程序编译、不是内建子命令；`install-rules` 只是把已安装的独立可执行文件调用起来。PF_RING 在当前 main 快照是否仍为受支持后端、对应源文件与启用方式需对照 `configure.ac` 与 `src/source-*.c` 实际版本核验，不得编造 `src/source-pfring.c`。抓包后端能力与环境要求差异大，DPDK 需独占网卡、大页与 EAL 参数，Netmap 与 AF_XDP 有内核与驱动要求，pcap 多用于离线或低速率，详见 02-04、原理见 06-02、模块见 07-06。加密载荷明文不可见，能拿到的是握手元数据、证书、SNI、JA3 一类信息，见 `src/output-json-tls.c` 与 `rust/src/ja4.rs`；这些红线任何一篇都不得写反。

第五条是版本与性能纪律。全套资料统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准但不写绝对值；`configure.ac` 里 `AC_INIT` 的版本字样、`install.rst` 里示例归档的版本字样都只作核验依据，不得抄进正文。任何吞吐、pps、丢包率、内存占用结论一律标注「需在目标机型实测」，不给跨机型通用数字；基准方法见 08-01，调优见 08-02。把「加线程」写成必然线性提速也是错的，runmode 与流亲和、RSS、fanout 共同决定扩展性，原理见 06-13。

### 7. 小结与延伸阅读

本篇把「编译前准备」收束成三件事。其一，认清事实锚点与路径：真实仓库根是 `upstream_src/suricata/suricata-main/`，顶层 `configure.ac`、`Makefile.am`、`autogen.sh`、`suricata.yaml.in` 与 `src/`、`rust/`、`etc/`、`doc/userguide/`、`qa/` 等目录各有职责，大量文件是 `.in` 模板而非成品。其二，认清双层工程：autotools 管 C 主程序与顶层装配，Cargo 管 Rust 子工程，`SUBDIRS` 里 `rust` 先于 `src`，静态库与 FFI 头是 make 期产物。其三，认清依赖矩阵：硬依赖缺失直接中断，可选加速缺失回退或告警，平台后端依赖叠加运行环境条件，具体库名与版本下限需对照 `configure.ac` 核验，完整清单见 04-01、完整变量见 04-01。

延伸阅读按角色分流：想逐项查构建选项与变量读 04-01，查 yaml 全局段读 04-02，查命令行与 RPC 读 04-07；想理解构建链如何把选项变成条件宏与产物，读 02-02；想动手从零编译、测试并安装，读 02-03；想弄清 Rust 组件与各抓包后端的启用条件，读 02-04；调试构建、Sanitizer、单元测试与 CI 产物形态读 02-05。结构体字段查 05 册，抓包后端与应用解析的机制分别见 06-02、06-05、06-14，按目录的模块能力见 07-06、07-10、07-13，上线与排障读 08 册。全册交叉引用统一写成 `（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）`。把这条链记牢，02-02 就会接着讲清「选项到底怎样改变产物」。

## 02-02 构建系统全解：configure 选项与构建变体

### 1. 背景与动机

很多人第一次读 `configure.ac`，会把它当成一份「开关清单」，于是试图背下每个 `--enable-xxx` 的名字。这是效率最低的读法。选项在 Suricata 里从来不是孤立开关，而是一套「条件编译 + 条件装配」机制的输入：同一个选项往往同时写下一个 C 预处理宏、一个 automake 条件、一组替换变量，进而决定某份 `source-*.c` 是否被编入、某个 `Makefile.am` 条件块是否生效、某个 `*.in` 模板生成出什么内容。只记住开关名，不理解它落到哪里，遇到「选项明明传了却不生效」时就没有排查方向。本篇的动机，正是把这套传导机制讲清楚。

第二个动机是「验证」。构建选项的错误往往不会当场报错：Hyperscan 头缺失时 configure 只是把 `enable_hyperscan` 置为 no 继续往下走，DPDK 相关包不全时 `enable_dpdk` 保持 no，AF_PACKET 因内核头不满足而 `enable_af_packet="no"`。如果用户不核对 configure 收尾打印的配置摘要，就会以为自己编出了一个带某特性的程序，上线后才发现后端根本没进去。所幸 `configure.ac` 把这份摘要同时写进了 `src/build-info.h`，`suricata --build-info` 能原样回显，于是「传了什么」与「编进什么」之间有了可对照的凭据。把这条验证闭环讲透，比罗列开关更有价值。

第三个动机是「组合」。真实部署不会用默认配置一把梭：生产 IDS 追求可移植与稳定，IPS 内联必须额外启用队列后端，调试环境要打开 debug 与单测、关闭共享库以便符号排查。三种变体不是三份互斥的脚本，而是「在默认基线上叠加或关闭哪几族能力」的组合思路。理解组合，才能解释为什么同一个代码库能产出形态差异很大的可执行程序，也才能理解「构建变体」这个词在本册里的含义。

需要先声明边界。按 SPEC 第 4 节的去重约定，`configure` 选项、默认值、依赖条件与误配后果的完整清单属于 04-01，本册一律写「完整清单见 04-01」「完整变量见 04-01」，只给说明机制所需的最少量点名；`suricata.yaml` 各段参数见 04-02、04-03、04-04，命令行参数见 04-07；机制与调用链写「原理见 06-xx」，结构体字段写「字段见 05-xx」，模块能力写「模块见 07-xx」。本篇回答的是「选项怎么改变产物、怎么组合、怎么验证」，不代替 04-01 做手册。

### 2. 核心概念

第一组概念是选项的两类定义宏。`AC_ARG_ENABLE` 定义布尔型开关，形如 `AC_ARG_ENABLE(unittests, AS_HELP_STRING([--enable-unittests], [...]), [enable_unittests=$enableval], [enable_unittests=no])`，即「传了取值、没传取默认」；`AC_ARG_WITH` 定义带路径参数的配置项，例如 `--with-libhs-includes=DIR`、`--with-libpcre2-libraries=DIR`、`--with-netmap-includes=DIR` 一类，用来把非标准路径的头与库目录注入 `CPPFLAGS` 与 `LDFLAGS`。两类宏在 `configure.ac` 里成对出现，前者管「要不要」，后者管「去哪找」。具体选项名与默认值需对照实际版本核验，完整清单见 04-01。

第二组概念是选项结果的三条落点。其一是 `AC_DEFINE` 写进 `src/autoconf.h` 的预处理宏：例如 `--enable-unittests` 命中时 `AC_DEFINE([UNITTESTS],[1],...)`，`--enable-debug` 命中时 `AC_DEFINE([DEBUG],[1],...)`，`--enable-nfqueue` 命中时 `AC_DEFINE_UNQUOTED([NFQ],[1],...)`，Hyperscan 探测通过时 `AC_DEFINE([BUILD_HYPERSCAN],[1],...)`，AF_PACKET 探测通过时 `AC_DEFINE([HAVE_AF_PACKET],[1],...)`。这些宏被 C 源码里的 `#ifdef` 包围，直接决定某段实现是否编译。其二是 `AM_CONDITIONAL` 生成的 automake 条件，例如 `AM_CONDITIONAL([BUILD_UNITTESTS], ...)`、`AM_CONDITIONAL([DEBUG], ...)`、`AM_CONDITIONAL([HAVE_RUST_VENDOR], ...)`，供各级 `Makefile.am` 用 `if / endif` 包裹目标与源文件列表。其三是 `AC_SUBST` 替换变量，例如 `CFLAGS`、`LDFLAGS`、`CPPFLAGS`、`RUST_FEATURES`、`RUST_SURICATA_LIB`、`e_sysconfdir` 等，既影响编译参数，也在 `AC_CONFIG_FILES` 生成文件时被填进模板。

第三组概念是「探测决定选项，而非选项决定探测」。不少选项的默认值只是「尝试启用」，最终是否生效由探测结果改写：`--enable-af-packet` 默认 yes，但要用 `AC_CHECK_DECLS([TPACKET_V2, TPACKET_V3])` 确认内核头支持，否则 `enable_af_packet="no"`；`--disable-af-xdp` 默认启用，却要依次检查 libelf、libxdp、libbpf 的头与符号，任一不满足就 `enable_af_xdp=no`；Hyperscan 更要先走 `PKG_CHECK_MODULES([libhs], libhs,...)`，再看 `hs.h` 与 `hs_compile` 的链接测试。因此配置摘要里的 `yes / no` 是「选项意图与系统能力取交集」的结果，读摘要时要按这个逻辑理解，而不是把它当成用户输入的回声。

第四组概念是配置摘要与 `src/build-info.h` 的同源关系。`configure.ac` 末尾把 `SURICATA_BUILD_CONF` 这段多行文本先 `echo` 到终端，再用 `printf(`、逐行加引号与 `);` 写进 `src/build-info.h`；`src/suricata.c` 的 `PrintBuildInfo()` 在打印完 `Features`、`SIMD support`、`Atomic intrinsics`、字长、TLS 方式等信息后，用 `#include "build-info.h"` 把这段配置串原样输出。`--build-info` 在 `SCParseCommandLine` 的长选项表里登记为 `{"build-info", 0, &build_info, 1}`，命中后把 `suri->run_mode` 置为 `RUNMODE_PRINT_BUILDINFO`，最终由 `PrintBuildInfo()` 完成打印。这意味着「configure 结束屏」与「`suricata --build-info` 的配置段」本应是同一份内容，任何不一致都值得追查。

### 3. 关键数据结构与源码位置

选项定义与传导逻辑集中在 `configure.ac`，其 `# options` 段之后依次排列 unittests、ebpf-build、debug、debug-validation、qa-simulation、profiling 族、ipfw、coccinelle、detection 等开关族；`# libraries` 段之后则是 zlib、PCRE2、libhs、libyaml、hwloc、pthread、Jansson、unix-socket、NFQUEUE/NFLOG、WinDivert、libnet、libpcap、PF_RING、AF_PACKET、AF_XDP、DPDK、Netmap、libcap-ng、eBPF、DAG、libmagic、Napatech、GeoIP、PIE、hiredis、JA3/JA4、Rust、nDPI、warnings、fuzztargets、gccmarch-native 等探测与开关。这里不逐项展开，只借几处说明「选项 → 宏 → 下游」的传导路径，完整清单见 04-01。

传导的下游分布在各级 `Makefile.am` 与 C 源码里。`src/Makefile.am` 的 `if BUILD_UNITTESTS` 条件块重定义了 `check-am`：先 `mkdir` 日志目录，再执行 `$(top_builddir)/src/suricata -u -l $(top_builddir)/qa/log/`，最后清理目录，也就是说 `make check` 在启用单测时实际是调用编译出的程序跑单测。`src/Makefile.am` 的 `distclean-local` 则负责删掉 `src/build-info.h`，印证它是生成物。`rust/Makefile.am` 的 `if !DEBUG` 决定是否给 `cargo build` 追加 `--release`，`if DEBUG`、`if DEBUG_VALIDATION`、`if HAVE_JA3`、`if HAVE_JA4` 分别往 `RUST_FEATURES` 追加对应 feature。C 侧的 `src/source-nfq.c`、`src/source-af-packet.c`、`src/util-mpm-hs*.c` 等文件是否被编入，取决于 `src/autoconf.h` 里对应的 `NFQ`、`HAVE_AF_PACKET`、`BUILD_HYPERSCAN` 宏。

下表只点名几类代表性的条件宏，用于说明选项如何驱动编译与装配；完整清单见 04-01，具体宏名与选项名需对照实际版本核验。

| 选项族示例 | 产生的条件宏或变量 | 影响的下游 |
|---|---|---|
| unittests | UNITTESTS 与 BUILD_UNITTESTS | src/Makefile.am 的 check-am 调用 suricata -u |
| debug | DEBUG | rust/Makefile.am 决定是否追加 --release |
| nfqueue | NFQ 与 libnetfilter_queue 探测 | 编入 source-nfq.c 与 runmode-nfq.c |
| af-packet | HAVE_AF_PACKET 与 HAVE_PACKET_FANOUT | 编入 source-af-packet.c |
| libhs 相关选项 | BUILD_HYPERSCAN | 编入 util-mpm-hs.c，否则回退 AC |
| unix-socket | BUILD_UNIX_SOCKET | 编入控制面与 suricatasc 相关模块 |
| geoip | HAVE_GEOIP | 编入 GeoIP2 相关关键字 |

表中每一项都能在 `configure.ac` 里找到对应的 `AC_DEFINE` 或 `AM_CONDITIONAL`，在 `Makefile.am` 或 `src/` 里找到消费方。结构体方面，`SCInstance` 承载 `run_mode` 等运行参数，字段见 05-09；`ConfNode` 配置树字段见 05-09；`ThreadVars`、`TmModule` 字段见 05-07。本篇只借这些名字说明「选项最后落在哪些对象上」，不列任何字段表。按统一写法收束：`（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）`。

### 4. 关键流程与调用链

主链是 `./autogen.sh && ./configure && make && make install`。第一段 `autogen.sh` 用 `libtoolize -c` 与 `autoreconf -fv --install` 由 `configure.ac`、各级 `Makefile.am` 生成 `configure` 脚本与 `Makefile.in`；第二段 `./configure` 逐条执行依赖探测与选项解析，把结果写入 `src/autoconf.h`、各级 `Makefile` 与大量 `*.in` 生成物；第三段 `make` 按 `SUBDIRS` 递归，先由 `rust/Makefile.am` 调 `cargo build` 产出静态库与 FFI 头，再由 `src/Makefile.am` 编译 C 主程序并链接；第四段 `make install` 把可执行程序、库、配置样例与脚本安装到 `EXPAND_VARIABLE` 计算出的 `e_sysconfdir`、`e_logdir`、`e_datarulesdir` 等路径下。命令行参数与安装路径的完整说明见 04-07，完整变量见 04-01。

第二条链是「配置即凭据」，也是本篇最该记住的验证闭环。configure 收尾把 `SURICATA_BUILD_CONF` 打印到终端，其中包含 `Suricata Configuration:` 标题下的 `AF_PACKET support`、`DPDK support`、`PF_RING support`、`NFQueue support`、`Netmap support`、`Unix socket enabled`、`Hyperscan support`、`Rust compiler version` 等行，以及 `Development settings:` 下的 `Unit tests enabled`、`Debug output enabled`、`Fuzz targets enabled`，`Generic build parameters:` 下的 `--prefix`、`--sysconfdir`、`--localstatedir`、`CFLAGS` 等行。同一段文本被写进 `src/build-info.h`，被 `PrintBuildInfo()` 内联打印。于是验证顺序可以是：configure 结束屏看一遍、编译后 `suricata --build-info` 再比对一遍、必要时用 `--dump-config` 查运行配置、用 `-T` 做配置与规则自检。这四条命令共同回答「我这份构建里到底编进了什么」，命令全集见 04-07。

第三条链是三种典型变体的组合逻辑。生产 IDS 变体在默认基线上保留 AF_PACKET 等常规后端，并用 `--prefix`、`--sysconfdir`、`--localstatedir` 把安装布局对齐发行版目录规范，必要时用 `--disable-gccmarch-native` 换取可移植性（该选项默认开启 `-march=native`，文档明确建议二进制要跨机型或在虚拟机里运行时关闭它）。IPS 内联变体额外启用队列后端，`configure.ac` 中 `--enable-nfqueue` 会触发 `PKG_CHECK_MODULES([libnetfilter_queue], ...)`、`NFQ` 宏与 `source-nfq.c` 的编入，运行期还需内核权限与 iptables/nftables 队列规则配合，机制见 06-12。调试变体打开 `--enable-debug` 与 `--enable-unittests`、常用 `--disable-shared` 关闭共享库以便符号与 Sanitizer 排查，此时 `rust/Makefile.am` 不再追加 `--release`，`RUST_SURICATA_LIBDIR` 指向 `debug` 目录，`make check` 会真正跑起单测。构建链四阶段与配置摘要的验证闭环见图 02-02-01。

### 5. 配置/命令/代码实例

下面这组命令演示「怎么组合、怎么验证」：先抽查一个可选加速开关，再组合一套调试带单测的构建，最后用程序回显的配置摘要与 configure 结束屏比对。选项名需对照实际版本核验，完整清单见 04-01、完整变量见 04-01。

```bash
# 抽查可选加速开关是否存在，确认拼写后再决定要不要传
./configure --help | grep -i hyperscan

# 组合一套调试带单测的构建：打开 debug 与 unittests，关闭共享库
./configure --enable-debug --enable-unittests --disable-shared

# 编译后回显构建信息，验证「传了什么」是否等于「编进了什么」
make -j"$(nproc)"
./src/suricata --build-info
```

对 `./configure` 结束屏与 `--build-info` 的配置段，以下是示例输出，具体格式需对照实际版本核验；版本字符串行依版本纪律不抄录具体值。

```text
Suricata Configuration:
  AF_PACKET support:                       yes
  AF_XDP support:                          yes
  DPDK support:                            no
  PF_RING support:                         no
  NFQueue support:                         no
  Netmap support:                          no
  Unix socket enabled:                     yes
  Detection enabled:                       yes
  Hyperscan support:                       no
  Rust strict mode:                        no
  Unit tests enabled:                      yes
  Debug output enabled:                    yes
  Debug validation enabled:                no
  Fuzz targets enabled:                    no

To build and install run 'make' and 'make install'.
```

逐行判读这段输出。首行 `Suricata Configuration:` 是 configure 收尾打印的摘要标题，它与 `src/build-info.h` 里的内容同源，因此 `--build-info` 会再次出现这一段，二者不一致说明生成物被覆盖或编译的不是刚配置的那棵树。抓包后端一组要看意图与探测的交集：`AF_PACKET support: yes` 与 `AF_XDP support: yes` 表示这两族通过了内核头与库探测，`DPDK support: no`、`PF_RING support: no`、`NFQueue support: no`、`Netmap support: no` 则多为默认关闭或依赖未满足，若业务需要 IPS 内联却看到 `NFQueue support: no`，就应回查 `--enable-nfqueue` 是否传入、`libnetfilter_queue` 是否通过 `PKG_CHECK_MODULES`。`Unix socket enabled: yes` 说明控制面可用，`Detection enabled: yes` 是默认行为，`Hyperscan support: no` 表示本次未编入可选 MPM 加速，将回退 AC 等其他实现——它是可选能力而非必需依赖。`Development settings` 一组最值得与命令行对照：`Unit tests enabled: yes` 与 `Debug output enabled: yes` 正对应上面传入的 `--enable-unittests`、`--enable-debug`，`Debug validation enabled: no` 与 `Fuzz targets enabled: no` 说明这两项未开。末行 `To build and install run 'make' and 'make install'.` 是 configure 的常规收尾提示，提示还有 `make install-conf` 与 `make install-full` 可补齐配置与规则。需要留意，摘要里的对齐空格、行序与打印字段会随实际版本变化，务必以本地结果为准；它只反映编译期特性，不保证运行期后端真的能用，后者还需权限、内核与配置就位。

三种典型变体的组合思路与产物形态见下表；表中不列完整选项，具体选项名需对照实际版本核验，完整清单见 04-01。

| 构建变体 | 组合思路 | 产物形态 |
|---|---|---|
| 生产 IDS | 保留默认后端，安装布局对齐发行版 | 可执行程序加配置样例 |
| IPS 内联 | 额外启用队列后端并配好内核权限 | 具备 verdict 能力的可执行程序 |
| 调试带单测 | 打开 debug 与 unittests，关闭共享库 | 带符号与单测入口的调试程序 |

再给一组验证命令，覆盖「自检 → 单测 → 安装」的闭环；`make check` 在启用单测时由 `src/Makefile.am` 的 `check-am` 转发到 `suricata -u`，命令全集见 04-07。

```bash
# 配置与规则自检，不真正抓包
./src/suricata -T -c /etc/suricata/suricata.yaml

# 启用单测后，make check 会调用编译出的程序跑单测
make check

# 打印解析后的运行配置，核对段与键是否生效
./src/suricata --dump-config -c /etc/suricata/suricata.yaml | head -20
```

### 6. 注意事项、陷阱与最佳实践

第一条是选项之间存在互斥与前提，别一股脑全打开。`configure.ac` 明确写着 `--enable-debug-validation` 与 `--enable-unittests` 不能同时启用，命中时直接 `AC_MSG_ERROR` 退出；PF_RING、Napatech、nDPI 一族与 `--disable-shared` 也有冲突检查，注释里写明「cannot be enabled with --disable-shared」。`--enable-ebpf-build` 还要求 `clang`、对应版本的 `llc` 与 libbpf 的 `bpf/bpf_helpers.h`，缺一即报错。组合变体的正确姿势是「先确定场景，再逐族叠加」，每加一族就看一遍配置摘要，而不是把所有 `--enable-*` 堆在一行；完整清单与依赖条件见 04-01。

第二条是改选项后要清理，别信增量编译。选项会改变 `src/autoconf.h` 的宏、`Makefile` 的条件块与 `AC_CONFIG_FILES` 生成的模板内容，从 `--enable-debug` 切回默认、或改动 `--prefix` 之后，残留的目标文件与生成头文件可能让新配置「看起来生效、实际混编」。稳妥做法是 `make clean` 后重新 `./configure`，必要时重跑 `./autogen.sh`。`src/Makefile.am` 的 `distclean-local` 会删掉 `src/build-info.h`，正是为了让它随下次 configure 重生；手工编辑 `build-info.h` 毫无意义。

第三条是把「配置摘要」当凭据而非装饰。Hyperscan、DPDK、AF_XDP 这类选项的 `yes / no` 由探测结果决定，传了选项不等于生效；反过来，摘要为 `no` 也不等于程序坏了，只是该能力没编入。排障时第一步永远是 `suricata --build-info`，第二步才是查 `--dump-config` 与 `suricata.log`。还要记住 `--build-info` 是查询命令而非配置命令，它不修改任何状态；`-T` 是自检命令，只做加载与校验、不拉起抓包线程。命令语义见 04-07，返回码与告警判读见 04-08。

第四条仍是全册通用的能力边界与纪律。`suricata-update` 与内核主程序分仓、独立发版，不是内建子命令；`rust/` 与 Cargo 是构建的一部分，Suricata 不是纯 C 项目；Hyperscan 只是可选 MPM 加速，缺失时回退 `src/util-mpm-ac*.c` 等 AC 实现。抓包后端环境差异大，DPDK 需独占网卡、大页与 EAL 参数，Netmap 与 AF_XDP 有内核与驱动要求，pcap 多用于离线或低速率，详见 02-04、原理见 06-02。PF_RING 是否仍为受支持后端需对照 `configure.ac` 与 `src/source-*.c` 实际版本核验，不得编造 `src/source-pfring.c`。性能与容量结论一律标注「需在目标机型实测」，不给绝对值；版本统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验。

### 7. 小结与延伸阅读

本篇的核心判断是：configure 选项不是开关清单，而是一套「条件编译 + 条件装配」机制的输入。`AC_ARG_ENABLE` / `AC_ARG_WITH` 收集意图，`AC_CHECK_*` / `PKG_CHECK_MODULES` 校验系统能力，结果经 `AC_DEFINE` 写入 `src/autoconf.h`、经 `AM_CONDITIONAL` 驱动各级 `Makefile.am`、经 `AC_SUBST` 填进 `*.in` 模板；`SUBDIRS` 决定 Rust 静态库先于 C 主程序产出；configure 收尾把 `SURICATA_BUILD_CONF` 同时打到终端与 `src/build-info.h`，由 `PrintBuildInfo()` 让 `suricata --build-info` 回显，形成「传了什么」与「编进了什么」的可比对闭环。三种典型变体只是「在默认基线上叠加或关闭哪几族能力」的组合思路，完整清单见 04-01、完整变量见 04-01。

延伸阅读按需分流：逐项查选项、默认值、依赖条件与误配后果读 04-01，查 yaml 段读 04-02、04-03、04-04，查命令行、Unix socket 与 RPC 读 04-07，查返回码与告警判读读 04-08；结构体字段读 05 册；抓包后端、应用解析与 Rust FFI、规则编译、runmode 的机制分别见 06-02、06-05、06-06、06-13；按目录的模块能力见 07-06、07-07、07-10、07-13。想真正把这套组合落到一台 Linux 上，读 02-03 的从零构建实战；想弄清 Rust 与各后端各自的启用条件，读 02-04。全册交叉引用统一写成 `（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）`，性能数字一律标注需在目标机型实测。选项的传导机制讲清之后，02-03 就不再解释原理，只给可复现的操作序列与判读要点。

## 02-03 从零构建实战：Linux 编译、测试与安装

### 1. 目标与拓扑

本篇是一次完整的动手实战：在一台干净的 Linux 主机上，从上游源码快照编出可运行的 `suricata`，完成构建信息回显、配置与规则自检、可选单元测试，最后把可执行程序、配置样例与规则落位到约定目录，并处理动态库加载路径。全程不接入生产流量、不配置 IPS 内联、不做抓包压力测试，目标是得到一个「能被 `--build-info`、`-T` 验证通过」的干净产物，为 03 册的首次 IDS 运行准备好二进制与配置基线。凡是吞吐、内存、编译耗时一类的数字，一律标注「需在目标机型实测」，本篇不给绝对值。

拓扑可以画成三段。第一段是构建机：源码树位于 `suricata-main/`，`./autogen.sh` 与 `./configure` 在这里生成 Makefile 与各级模板产物，`make -j` 在这里产出 `src/suricata` 与 `rust/` 下的静态库及 FFI 头。第二段是安装前缀：`configure.ac` 末尾给出的示例是 `./configure --prefix=/usr/ --sysconfdir=/etc/ --localstatedir=/var/`，对应把可执行程序放进 `/usr/bin/`、配置放进 `/etc/suricata/`、日志放进 `/var/log/suricata/`；若沿用默认前缀 `/usr/local/`，则对应 `/usr/local/bin/`、`/usr/local/etc/suricata/`、`/usr/local/var/log/suricata/`，官方文档 `doc/userguide/install.rst` 也是这么描述的。第三段是落位资源：`make install-conf` 把 `suricata.yaml`、`etc/classification.config`、`etc/reference.config`、`threshold.config` 安装到配置目录，`make install-rules` 借独立工具拉取规则，`make install-full` 是三者合一。三段合起来就是「源码 → 产物 → 可运行安装」的完整闭环，操作顺序见图 02-03-01。

需要提前划清与相邻篇的分工。本篇只给「本场景最小必要命令」，构建选项与变量的完整清单见 04-01、完整变量见 04-01，`suricata.yaml` 各段参数见 04-02、04-03、04-04，命令行参数见 04-07，返回码与告警判读见 04-08；机制与调用链写「原理见 06-xx」，结构体字段写「字段见 05-xx」，模块能力写「模块见 07-xx」。本篇不解释为什么 Rust 先于 C 编译、不展开条件宏如何进入 `src/autoconf.h`，这些已在 02-01、02-02 讲过；本篇回答的是「按什么顺序敲、每条命令应该看到什么、看不到时怎么办」。

### 2. 前置条件与环境

发行版以 Debian/Ubuntu 系为例，仓库里 `scripts/docs-debian-minimal-build.sh` 给出了被 CI 验证过的最小依赖清单，注释写明「Serves for Ubuntu/Debian docs and is verified by Github Actions」，因此它比凭印象拼出来的包列表更可靠。RPM 系可对照 `scripts/docs-almalinux9-minimal-build.sh`，并需按 `doc/userguide/install.rst` 的提示先启用 epel-release 与 crb/powertools 一类额外仓库；Windows 构建另见该文档的专门章节，不在本篇范围。

工具链方面要单独确认几件事。`autogen.sh` 第一步要找 `libtoolize` 或 `glibtoolize`，第二步执行 `autoreconf -fv --install`，因此 autoconf、automake、libtool、pkg-config、make 与 C 编译器缺一不可；本套资料依据的是源码快照（等价于从 git 源构建），`configure.ac` 里 `--enable-python` 默认开启且注释写明 Python「is also required when building from git」，故也应备好 python3。Rust 侧由 `configure.ac` 通过 `AC_ARG_VAR` 与 `AC_PATH_PROG` 逐一检查 `RUSTC`、`CARGO`、`RUSTDOC`，三者任一为「no」都会报错退出；`MIN_RUSTC_VERSION` 设定了最低工具链版本，`rust/Cargo.toml.in` 的 `[workspace.package] rust-version` 与之呼应，具体数值需对照实际版本核验。绑定生成还要 `cbindgen`（`cbindgen.toml` 是它的配置）、可选 `bindgen` 与 `rustfmt`，`configure.ac` 对它们有版本下限检查，具体下限需对照实际版本核验；若源码树里已随包提供 `rust/dist/rust-bindings.h` 一类生成头，则对 cbindgen 的依赖可放宽。

依赖库的分类沿用 02-01 的结论：zlib、PCRE2、libyaml、Jansson、libpcap、pthread 属于探测失败即退出的硬依赖；Hyperscan 走 `PKG_CHECK_MODULES([libhs], libhs,...)` 加 `hs.h` 与 `hs_compile` 的双重探测，缺失只是回退为 no，不必强求；hwloc、GeoIP2、libmagic、hiredis、liblz4、libcap-ng 属于可选增强。资源方面，编译并发度、磁盘余量与内存占用都需在目标机型实测，尤其是 `make -j` 的并发数要与可用核数与内存匹配，盲目开大反而容易在链接阶段被内存耗尽打断。权限方面，源码目录与构建目录需可写，`make install` 与 `make install-conf` 写入 `/usr/`、`/etc/`、`/var/` 通常需要管理员权限，建议用受控的 sudo 执行，而不是全程 root 编译。

还有一处环境选择值得先定：是「树内构建」还是「树外构建」。autotools 支持在单独目录里执行 `configure` 与 `make`，把生成物与源码树隔离，便于同时维护多套构建变体、也便于清理；`src/Makefile.am` 的 `distclean-local` 会删除 `src/build-info.h`，`rust/Makefile.am` 的 `clean-local` 会删除 `target` 与 `gen`，都是围绕「生成物可重建」设计的。若采用树外构建，需注意 `configure.ac` 里 `AC_CONFIG_SRCDIR([src/suricata.c])` 要求能定位到源码目录，且 `rust/Makefile.am` 的 `all-local` 用 `$(abs_top_srcdir)/rust` 切回源码树执行 `cargo build`，因此源码目录必须保持完整可读。本篇为减少变量，采用在源码树内构建；若改用树外构建，命令里的相对路径需相应调整为构建目录下的路径。此外，离线环境无法执行 `make install-rules`，应提前准备规则文件并放到 `default-rule-path` 指向的目录，再用 `-T` 确认加载数量，这一点在第 4 节的判读里还会提到。

### 3. 分步操作

下面按「前置检查 → 依赖安装 → 生成 → 配置 → 编译 → 测试 → 安装 → 验证 → 清理」的闭环给出完整序列。命令中的路径与选项名需对照实际版本核验，完整清单见 04-01、完整变量见 04-01，`-c` 指向的配置文件路径按实际环境替换。

```bash
# 步骤 0：进入真实仓库根，核验 autotools 与 Rust 工具链
cd suricata-main
for t in libtoolize autoreconf pkg-config rustc cargo rustdoc; do
  command -v "$t" || echo "missing tool: $t"
done

# 步骤 1：按仓库内被 CI 验证过的清单安装最小依赖
sudo apt -y install autoconf automake build-essential cargo \
    libjansson-dev libpcap-dev libpcre2-dev libtool \
    libyaml-dev make pkg-config rustc zlib1g-dev

# 步骤 2：从源码快照生成 configure 脚本
./autogen.sh

# 步骤 3：配置安装布局；路径选项需对照实际版本核验
./configure --prefix=/usr/ --sysconfdir=/etc/ --localstatedir=/var/

# 步骤 4：并发编译，并发数按目标机型实测选择
make -j"$(nproc)"

# 步骤 5：可选单测；需 configure 时额外传入 --enable-unittests
make check

# 步骤 6：安装程序与初始配置，三者合一等价于 make install-full
sudo make install
sudo make install-conf

# 步骤 7：刷新动态库缓存，并把日志目录准备好
sudo ldconfig
ls -l /etc/suricata/suricata.yaml /etc/suricata/classification.config
```

逐条说明几个容易含糊的点。步骤 2 的 `./autogen.sh` 只在源码快照或缺 configure 脚本时需要，发布归档若已自带 configure 可跳过，但重跑不会有害，且能保证 `rust/Cargo.lock` 由 `Cargo.lock.in` 模板重新生成。步骤 3 的三选项组合直接来自 `configure.ac` 末尾的安装提示，目的是把布局对齐发行版规范；若要可移植到别的机型或在虚拟机里运行，`doc/userguide/install.rst` 建议追加 `--disable-gccmarch-native`，因为 `--enable-gccmarch-native` 默认开启 `-march=native`。步骤 5 有个前提：`src/Makefile.am` 的 `if BUILD_UNITTESTS check-am` 会调用 `$(top_builddir)/src/suricata -u -l $(top_builddir)/qa/log/`，也就是说只有 configure 时启用单测，`make check` 才会真正执行 `suricata -u`；默认配置下这一步不会跑单测，也不必因此怀疑编译失败。步骤 6 的 `make install-conf` 以 `-m 600` 安装四个配置文件，若目标文件已存在则用 `test -e ... || install` 跳过，不会覆盖已有配置；`make install-full` 额外包含 `make install-rules`，后者在 `INSTALL_SURICATA_UPDATE` 成立时调用独立工具 `suricata-update --no-test --no-reload`，离线环境可酌情只用 `install-conf` 并手工放置规则。步骤 7 的 `ldconfig` 与顶层 `Makefile.am` 打印的 `LD_LIBRARY_PATH` 提示是同一类问题的两种解法：当程序报「shared library not found」时，要么刷新系统缓存，要么临时设置 `LD_LIBRARY_PATH` 指向安装前缀的 lib 目录。

### 4. 验证方法与预期结果

验证分四路：`suricata --build-info` 查编入特性，`suricata -T -c <配置>` 做配置与规则自检，`suricata --dump-config` 查解析后的运行配置，`--list-runmodes` 查可用运行模式。本篇要求给出「预期输出 + 判读要点」，因此下面把前两路的输出逐行拆开讲。命令全集见 04-07，返回码与日志级别见 04-08。

第一路的预期输出如下，示例输出，具体格式需对照实际版本核验；版本字符串行依版本纪律不抄录具体值。

```text
This is Suricata version (build info)
Features: PCRE_JIT HAVE_PACKET_FANOUT RUST
SIMD support: SSE_4_2 SSE_4_1 SSE_3 SSE_2
Atomic intrinsics: 1 2 4 8 16 byte(s)
64-bits, Little-endian architecture
thread local storage method: _Thread_local
compiled with libhtp
Suricata Configuration:
  AF_PACKET support:                       yes
  DPDK support:                            no
  NFQueue support:                         no
  Hyperscan support:                       no
  Unix socket enabled:                     yes
  Rust strict mode:                        no
  Unit tests enabled:                      no
  Debug output enabled:                    no
```

判读要点逐行展开。第一行是版本与构建信息头，具体版本值按纪律不抄录，读者只需确认它存在且与自己抓取的快照一致。`Features` 行来自 `src/suricata.c` 的 `PrintBuildInfo()`，它把编译期宏拼成字符串：`PCRE_JIT` 对应 `PCRE2_HAVE_JIT` 探测通过，`HAVE_PACKET_FANOUT` 对应 AF_PACKET 的 fanout 头检查，`RUST` 是硬编码追加的一项，用来直观说明 Rust 组件已编入；若开启调试或 fuzz，这一行还会出现 `ASAN`、`FUZZ` 一类标记。`SIMD support` 与 `Atomic intrinsics` 两行反映编译器与目标机的指令集，属于「同一份源码在不同机器上产物不同」的证据，不能跨机型比较。`64-bits, Little-endian architecture` 与 `thread local storage method` 分别来自字长判断与 `TLS_C11` / `TLS_GNU` 宏，`compiled with libhtp` 打印的是 `htp_get_version()` 的结果，说明 Rust 侧 htp 组件已链接。从 `Suricata Configuration:` 开始是由 `src/build-info.h` 内联的配置摘要，应与 configure 结束屏逐行比对：`AF_PACKET support: yes` 说明默认后端编入，`DPDK support: no`、`NFQueue support: no` 是默认关闭或依赖未满足，`Hyperscan support: no` 表示可选 MPM 加速未编入、将回退 AC 等其他实现，`Unix socket enabled: yes` 说明控制面可用，`Unit tests enabled: no` 与 `Debug output enabled: no` 正好对应本篇未传那两个开关。任何一行与预期不符，先回查 configure 是否重跑、是否 `make clean` 干净，再查探测日志。

第二路是 `-T` 自检，预期输出如下，示例输出，具体格式需对照实际版本核验。

```text
[Info] - Running suricata under test mode
[Info] - Loading configuration /etc/suricata/suricata.yaml
[Info] - Configuration OK
[Info] - Loading rule files from default-rule-path
[Info] - 1 rule files processed, rules successfully loaded
[Info] - Initializing runmode
[Info] - Configuration provided was successfully loaded. Exiting.
```

判读要点如下。首行 `Running suricata under test mode` 来自 `src/suricata.c` 里的 `SCLogInfo("Running suricata under test mode")`，确认进入的是只加载不抓包的自检模式，可随时在预发布环境反复执行。第二行报告实际加载的配置文件路径，用来确认 `-c` 是否指向预期那份 yaml；路径写错、落回默认配置是常见故障源。第三行 `Configuration OK` 说明 yaml 语法、段结构与必要键通过解析，若此处报缩进或未知段，应回头对照 `suricata.yaml.in` 的层级。第四、五行与规则加载有关，`default-rule-path` 与 `rule-files` 决定读哪些规则文件，输出里的文件数与成功加载数应与预期规则集规模大致吻合；若明显偏少，往往是规则文件路径没配对或文件为空，本篇若只跑了 `make install-conf` 而未跑 `make install-rules`，就应先手工放置规则再自检。第六行 `Initializing runmode` 说明已进入运行模式装配前的检查，末行 `successfully loaded. Exiting.` 是正常退出标志。要牢记自检通过不等于线上一定有告警：网卡名、`vars` 里的 `HOME_NET`、`outputs` 路径与权限仍需在 03 册的部署流程里逐项验证；输出的行数、措辞与日志级别会随构建与配置变化，务必以本地结果为准。

最后补一组验证与清理命令，把闭环收尾；其中 `--dump-config` 用于核对段与键是否生效，`--list-runmodes` 用于确认可用运行模式。

```bash
# 回显构建信息与特性行
/usr/bin/suricata --build-info | grep -E 'Features|AF_PACKET|Hyperscan|Unit tests'

# 打印解析后的运行配置，核对段与键
/usr/bin/suricata --dump-config -c /etc/suricata/suricata.yaml | head -20

# 列出可用运行模式，确认后端与线程模型
/usr/bin/suricata --list-runmodes

# 清理：删除构建期临时日志目录，保留安装产物
rm -rf qa/log/
```

### 5. 常见失败与排错

失败大多集中在「依赖没备齐」「工具链版本不够」「生成物被残留污染」「安装后运行环境没配好」四类。按 SPEC 的闭环约定，每个现象都给「验证命令 → 修复方向」两段，先取证再动手，不要一上来就重装或改源码。常见失败对照见下表，完整排错速查见 04-08，诊断决策树见 08-03。

| 现象 | 可能原因 | 验证命令 | 修复方向 |
|---|---|---|---|
| autogen.sh 立即报错退出 | 缺 libtoolize 或 autoreconf | command -v libtoolize | 补装 libtool、autoconf、automake |
| configure 报 libyaml 缺失 | yaml 头或链接符号探测失败 | grep -n yaml_parser_initialize configure.ac | 按报错内的包名补 libyaml-dev |
| configure 报 Jansson 必需 | jansson.h 或 json_dump_callback 未通过 | grep -n json_dump_callback configure.ac | 补装 libjansson-dev 后重跑 |
| make 期提示 cbindgen 缺失 | cbindgen 未装或低于版本下限 | cbindgen --version | 安装并对照 configure.ac 下限核验 |
| Rust 编译中断 | rustc 低于 MSRV 或 cargo 缺失 | rustc --version | 升级 Rust 工具链并确认三件套 |
| Hyperscan 头缺失告警 | 可选加速未编入 | grep -n enable_hyperscan configure.ac | 可忽略，或用 with 选项指明路径 |
| 启动时报共享库找不到 | 安装前缀不在动态加载路径 | ldd ./src/suricata | 跑 ldconfig 或设 LD_LIBRARY_PATH |
| -T 报 YAML 缩进错误 | 配置段层级写错 | suricata --dump-config | 对照 suricata.yaml.in 修正缩进 |
| 首次运行无告警 | 规则路径或抓包权限未就位 | suricata -T -c suricata.yaml | 核对 default-rule-path 与运行权限 |

几个需要展开说明的坑。其一，configure 报错信息里通常自带 Debian/Ubuntu、Fedora、CentOS/RHEL 三种发行版的安装命令，直接照抄对应包名即可，切勿把 `AC_CHECK_LIB` 注释掉绕过探测——那样只会把失败推迟到 make 阶段，变成成片的「未定义引用」。其二，Rust 相关失败要看清是「工具缺失」还是「版本不足」：`configure.ac` 用 `AS_VERSION_COMPARE` 比对 `MIN_RUSTC_VERSION`，用 `cbindgen --version` 比对 `min_cbindgen_version`，`rust/Cargo.toml.in` 的 `[workspace.package] rust-version` 又会再卡一道；具体数值需对照实际版本核验。其三，`rust/Cargo.lock` 是生成物，`autogen.sh` 会删掉它让模板重生，遇到依赖解析异常不要手工编辑锁文件。其四，改过 `--prefix` 或开关组合后，务必 `make clean` 再 `./configure`，否则 `src/autoconf.h` 与旧目标文件混编，会出现「配置摘要说编入了、程序行为却没变」的怪象。其五，若只跑 `make install-conf` 而未跑 `make install-rules`，`default-rule-path` 下可能没有规则文件，`-T` 里规则加载数量会偏少，这不是编译失败而是资源未落位。

还有一组属于全册通用纪律但本篇尤其容易踩的红线。`suricata-update` 是与主程序分仓、独立发版的工具，`make install-rules` 只是调用它，不是主程序内建子命令；PF_RING 是否仍为受支持后端、对应源文件与启用方式需对照 `configure.ac` 与 `src/source-*.c` 实际版本核验，不得编造 `src/source-pfring.c`；Hyperscan 是可选 MPM 加速，缺失时回退 `src/util-mpm-ac*.c` 等 AC 实现，不是必需依赖；抓包后端环境差异大，DPDK 需独占网卡、大页与 EAL 参数，Netmap 与 AF_XDP 有内核与驱动要求，pcap 多用于离线或低速率，详见 02-04、原理见 06-02、模块见 07-06。调试构建带的性能代价不可用作生产基准，任何吞吐与内存结论需在目标机型实测，基准方法见 08-01。

### 6. 小结

本篇把「从零构建」收成一条可复现的闭环：备齐 `scripts/docs-debian-minimal-build.sh` 列出的最小依赖与 autotools、Rust、cbindgen 工具链，进入多一层 `suricata-main/` 的真实仓库根，依次执行 `./autogen.sh`、`./configure --prefix=/usr/ --sysconfdir=/etc/ --localstatedir=/var/`、`make -j`、可选的 `make check`、`make install` 与 `make install-conf`、`ldconfig`，最后用 `suricata --build-info` 与 `suricata -T -c` 验证，并给出每一路的预期输出与逐行判读要点。读者应能据输出判断「特性是否编入、配置是否加载、规则是否就位」，而不是只看命令有没有返回零。

与相邻篇的衔接：构建选项与变量的全集见 04-01、完整变量见 04-01，命令行与 RPC 见 04-07，返回码与告警判读见 04-08；`suricata.yaml` 主干段与抓包线程参数见 04-02、04-03、04-04；结构体字段见 05 册；规则加载、解码与 runmode 的机制分别见 06-06、06-03、06-13；按目录的模块能力见 07 册；第一次真正跑起 IDS、加载规则集、接 EVE 管道读 03-01 起各篇，基准与排障读 08 册。全册交叉引用统一写成 `（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）`。构建产物能跑通自检之后，02-04 会补上最容易在 configure 阶段「悄悄关掉」的两块：Rust 组件与抓包后端。

## 02-04 Rust 组件与抓包后端（AF_PACKET/DPDK/PF_RING/Netmap/pcap）构建

### 1. 背景与动机

把 Suricata 当成「一个用 C 写的抓包程序」来编译，是最容易在 configure 阶段翻车的认知。真实情况是：仓库里有两套并行的工程。顶层 autotools 负责 C 主程序与装配，而 `rust/` 下是一整个 Cargo workspace，`rust/Makefile.am` 的 `SUBDIRS = derive ffi htp sys suricatasc suricatactl` 列出了它的子 crate。make 期必须先由 `cargo build` 产出静态库、再由 cbindgen 生成 C 可包含的绑定头，C 侧才能编译链接。大量应用层解析器与 EVE JSON 构造都在 Rust 侧，因此「Rust 组件是构建的一部分」不是一句口号，而是决定构建顺序、工具链要求与失败模式的硬约束。本篇第一半的动机，就是把这套 Rust 构建链讲清楚。

第二半动机来自抓包后端的巨大差异。同一份源码里同时存在 `src/source-af-packet.c`、`src/source-af-xdp.c`、`src/source-dpdk.c`、`src/source-netmap.c`、`src/source-pcap.c`、`src/source-pcap-file.c`、`src/source-nfq.c`、`src/source-nflog.c`、`src/source-ipfw.c`、`src/source-windivert.c`、`src/source-erf-dag.c`、`src/source-erf-file.c` 等一整个文件族，但它们「是否被编入」由 configure 的探测结果决定，且各自对内核、驱动、大页、专用库的要求天差地别。AF_PACKET 几乎在任意 Linux 上默认可用；DPDK 要独占网卡、配置大页并传 EAL 参数；Netmap 与 AF_XDP 有内核版本、驱动与 libbpf/libxdp 依赖；pcap 多用于离线回放或低速率场景。若不看配置摘要就假定「所有后端都能用」，部署时必然碰壁。

把这两块放在一篇里讲，还有一个更实际的原因：它们共享同一套「配置摘要即凭据」的验证方法。Rust 的 `rustc`、`cargo`、`cbindgen` 三件套与各后端的 `HAVE_*` 宏，最终都会出现在 `configure.ac` 末尾的 `SURICATA_BUILD_CONF` 里，并经由 `src/build-info.h` 被 `suricata --build-info` 回显。也就是说，排查「Rust 没编进去」与「DPDK 没编进去」用的是同一条命令，区别只在看哪几行。理解这条共用链路，能把两类问题合并成一次验证。

边界仍按 SPEC 第 4 节划定：构建选项、变量与各后端 yaml 段的完整清单见 04-01、04-03，完整变量见 04-01；机制与调用链写「原理见 06-xx」，结构体字段写「字段见 05-xx」，按 `src/` 目录的模块能力写「模块见 07-xx」。本篇只讲「怎么组合启用条件、怎么验证」，不列参数全集、不展开解析器状态机、不重列字段表。抓包后端原理见 06-02，应用解析与 Rust FFI 接入见 06-05、06-14，抓包源模块见 07-06，Rust 生态见 07-10。

### 2. 核心概念

第一组概念是 Rust 工程的「模板 + workspace」结构。源码树里没有现成的 `Cargo.toml`，只有 `rust/Cargo.toml.in`、`rust/Cargo.lock.in`、`rust/.cargo/config.toml.in`，它们由 `AC_CONFIG_FILES` 在 configure 阶段生成。`rust/Cargo.toml.in` 里 `[package] name = "suricata"`、`[lib] crate-type = ["staticlib", "rlib"]`，说明产物既有供 C 链接的静态库也有 Rust 侧的 rlib；`[workspace] members` 列出 `.`、`derive`、`suricatactl`、`suricatasc`、`sys`、`ffi`、`htp`，`[workspace.package]` 里 `edition`、`license`、`rust-version` 由 `@PACKAGE_VERSION@` 一类变量与固定值填充；`[profile.release] debug = true` 说明即便 release 构建也保留调试信息；`[features]` 定义 `strict`、`debug`、`debug-validate`、`ja3`、`ja4`，由 `rust/Makefile.am` 依据 automake 条件往 `RUST_FEATURES` 里追加。依赖清单里可见 `nom`、`serde_json`、`der-parser`、`kerberos-parser`、`tls-parser`、`x509-parser`、`suricata-derive`、`suricata-sys`、`suricata-ffi`、`suricata-lua-sys` 与 `htp` 等，正是「大量解析器在 Rust 侧」的证据。

第二组概念是 FFI 边界与绑定生成。`rust/cbindgen.toml` 里 `language = "C"`、`include_guard = "__RUST_BINDINGS_GEN_H_"`、`include_version = true`、`includes = ["stdint.h", "stdbool.h"]`、`line_length = 80`，`[export.rename]` 把 `JsonBuilder` 改名为 `SCJsonBuilder`、`JsonBuilderMark` 改名为 `SCJsonBuilderMark`，`[parse.expand] features = ["cbindgen"]`。`rust/Makefile.am` 的 `all-local` 在 `cargo build` 之后依次生成 `gen/rust-bindings.h`、`gen/rust-ffi.h`、`gen/htp/htp_rs.h`，并把 `suricata.lib` 或 `libsuricata.a` 拷成 `${RUST_SURICATA_LIBNAME}`（`configure.ac` 定义为 `libsuricata_rust.a`）；`configure.ac` 又通过 `CPPFLAGS="-I${srcdir}/../rust/gen -I${srcdir}/../rust/dist ..."` 让 C 侧能包含这些头。C↔Rust 的边界就是这些生成头加上 `rust/ffi/` 与 `rust/sys/`，详见 06-05、06-14。

第三组概念是「启用条件」而非「运行开关」。后端是否可用在 configure 阶段就定了：`--enable-af-packet` 默认 yes，但要 `AC_CHECK_DECLS([TPACKET_V2, TPACKET_V3])` 通过才 `AC_DEFINE([HAVE_AF_PACKET])`，并用 `AC_CHECK_DECL([PACKET_FANOUT_QM])` 决定 `HAVE_PACKET_FANOUT`；`--disable-af-xdp` 默认启用，却要依次探测 libelf 的 `elf_begin`、`xdp/xsk.h`、libxdp 的 `xsk_umem__create`、`bpf/libbpf.h`、libbpf 的 `bpf_object__open`，任一不满足就 `enable_af_xdp=no`；`--enable-dpdk` 默认 no，要 `numa_available` 与 `PKG_CHECK_EXISTS(libdpdk ...)` 通过，具体版本下限需对照实际版本核验；`--enable-netmap` 默认 no，要 `net/netmap_user.h`、`NETMAP_API` 版本检查、`libnetmap.h` 与 `nmport_open`；`--enable-nfqueue` / `--enable-nflog` 依赖 `PKG_CHECK_MODULES([libnetfilter_queue], ...)` 与对应头库。因此 `suricata.yaml` 里配了某个后端，configure 没编进去照样用不了；这正是需要先看 `--build-info` 的原因。

第四组概念是运行期环境。`suricata.yaml.in` 的 `dpdk:` 段给出 `eal-params.proc-type`、`interfaces` 列表里以 PCIe 地址形式书写的 `interface`、`threads`、`promisc`、`multicast`、`checksum-checks`、`checksum-checks-offload`、`mtu`、`mempool-size`、`mempool-cache-size`、`rx-descriptors`、`tx-descriptors` 等键，注释明确写着「Make sure you have enough allocated hugepages.」，并提到非对齐 chunk 模式使用大页、IPS 模式有 none / tap / ips 三种。这些键名与取值需对照实际版本核验，完整清单见 04-03。换句话说，DPDK 的「构建」只是第一步，独占网卡、大页、EAL 参数属于运行期前置条件，二者缺一不可。

### 3. 关键数据结构与源码位置

Rust 侧的构建描述分散在几个文件里。`rust/Makefile.am` 是最关键的一个：`SUBDIRS = derive ffi htp sys suricatasc suricatactl` 定义子 crate 递归顺序；`if !DEBUG` 决定是否 `RELEASE = --release`；`if HAVE_JA3` / `if HAVE_JA4` / `if DEBUG` / `if DEBUG_VALIDATION` 分别往 `RUST_FEATURES` 追加 `ja3`、`ja4`、`debug`、`debug-validate`；`RUST_CROSS_COMPILE` 命中时 `RUST_TARGET = --target $(host_triplet)`；`CARGO_ENV` 组合 `RUSTC`、`RUSTDOC`、`CARGO_HOME`、`CARGO_TARGET_DIR`、`SURICATA_LUA_SYS_HEADER_DST`、`LOCALSTATEDIR` 与 `SURICATA_LUA_SYS_CFLAGS`；`all-local` 调 `cargo build $(RELEASE) --features "$(RUST_FEATURES)"`；`check` 调 `cargo test --workspace`；`install-exec-local` 安装 `suricatasc` 与 `suricatactl`；`gen/rust-bindings.h`、`gen/rust-ffi.h`、`gen/htp/htp_rs.h` 三个目标由 `cbindgen --config ... --quiet --verify --output ...` 生成。`configure.ac` 里与之呼应的是 `AC_ARG_VAR([RUSTC] ...)`、`AC_ARG_VAR([CARGO] ...)`、`AC_ARG_VAR([RUSTDOC] ...)`、`MIN_RUSTC_VERSION`、`HAVE_RUST`、`RUST_FEATURES`、`RUST_SURICATA_LIBNAME`、`RUST_SURICATA_LIBDIR`、`HAVE_CBINDGEN`、`HAVE_BINDGEN`、`HAVE_RUST_VENDOR` 与 `--enable-rust-strict`（命中时 `RUST_FEATURES="strict"`）。

后端源码按目录一一对应，`src/source-*.c` 族在本套资料的上游 main 快照中确认存在上述各文件，另有 `src/source-lib.c`、`src/source-pcap-file-helper.c`、`src/source-pcap-file-directory-helper.c` 等辅助实现，以及按后端配对的 `src/runmode-af-packet.c`、`src/runmode-dpdk.c`、`src/runmode-nfq.c` 等（文件名需对照实际版本核验）。`configure.ac` 的 `AC_CONFIG_FILES` 里还登记了 `plugins/Makefile` 与 `plugins/pfring/Makefile`、`plugins/napatech/Makefile`、`plugins/ndpi/Makefile`；`plugins/pfring/` 目录下有插件形态的实现与 `README.md`。这里要点明一个容易写错的事实：本快照 `src/source-*.c` 族里不存在独立的 PF_RING 源文件，相关实现以 `plugins/pfring/` 插件目录形态存在，PF_RING 在当前 main 快照是否仍为受支持后端、对应启用方式与插件加载路径需对照 `configure.ac`、`plugins/Makefile.am` 与实际版本核验，不得凭印象补写路径。

把后端与启用条件、运行环境对照如下，具体选项名与键名需对照实际版本核验，完整清单见 04-01、04-03。

| 后端 | 源文件 | 启用条件 | 环境要求 |
|---|---|---|---|
| AF_PACKET | source-af-packet.c | 默认开启，需 TPACKET 头探测通过 | Linux 内核与抓包权限 |

### 4. 关键流程与调用链

Rust 链可以拆成五步。第一步 configure：`AC_CONFIG_FILES` 由 `rust/Cargo.toml.in`、`rust/Cargo.lock.in`、`rust/.cargo/config.toml.in` 及六个子 crate 的 `Cargo.toml.in` 生成实际 Cargo 工程，同时用 `AC_PATH_PROG` 确认 `rustc`、`cargo`、`rustdoc`，用 `AS_VERSION_COMPARE` 卡住 `MIN_RUSTC_VERSION`，并检查 cbindgen 与绑定头是否已随包提供。第二步 `make` 进入顶层 `SUBDIRS` 里的 `rust/`。第三步 `rust/Makefile.am` 的 `all-local` 先在 `rust/gen` 建目录，再以 `CC`、`AR`、`RANLIB` 与 `CARGO_ENV` 为环境执行 `cargo build $(RELEASE) --features "$(RUST_FEATURES)" $(RUST_TARGET)`；`RELEASE` 在 `--enable-debug` 时不追加，于是 `RUST_SURICATA_LIBDIR` 指向 `debug` 目录而非 `release`。第四步把 cargo 产出的 `suricata.lib` 或 `libsuricata.a` 拷成 `libsuricata_rust.a`，再用 cbindgen 生成三个绑定头。第五步 `src/` 编译时以 `CPPFLAGS` 包含 `rust/gen` 与 `rust/dist`，链接阶段加入 `RUST_SURICATA_LIB` 与 `RUST_LDADD`，最终得到可执行程序。Rust 静态库与 FFI 头的生成链见图 02-04-01。

### 5. 配置/命令/代码实例

下面这组命令演示「怎么组合启用条件、怎么验证编入结果」。先抽查后端相关开关的拼写，再确认 Rust 工具链与绑定生成器，编译后检查静态库与生成头存在，最后用 `--build-info` 回显。选项名需对照实际版本核验，完整清单见 04-01、完整变量见 04-01。

```bash
# 抽查后端开关拼写，确认哪些需要显式开启
./configure --help | grep -E 'af-packet|af-xdp|dpdk|netmap|nfqueue|pfring'

# 确认 Rust 三件套与 cbindgen 就位
rustc --version
cargo --version
cbindgen --version

# 编译后确认静态库与 FFI 头存在；release 或 debug 取决于是否开了 debug
ls -1 rust/target/release/libsuricata_rust.a rust/gen/

# 用构建信息回显核对后端与 Rust 特性
./src/suricata --build-info | grep -E 'Features|AF_PACKET|AF_XDP|DPDK|Netmap|Hyperscan'
```

对 `suricata --build-info` 的后端段与 Rust 段，以下是示例输出，具体格式需对照实际版本核验；版本字符串行依版本纪律不抄录具体值。

```text
Features: PCRE_JIT HAVE_PACKET_FANOUT RUST
Suricata Configuration:
  AF_PACKET support:                       yes
  AF_XDP support:                          yes
  DPDK support:                            no
  eBPF support:                            no
  XDP support:                             no
  PF_RING support:                         no
  NFQueue support:                         no
  NFLOG support:                           no
  IPFW support:                            no
  Netmap support:                          no
  DAG enabled:                             no
  Napatech enabled:                        no
  WinDivert enabled:                       no
  Npcap support:                           no
  Rust strict mode:                        no
  Rust compiler path:                      rustc
  Cargo path:                              cargo
```

逐行判读这段输出。`Features` 行里出现 `RUST` 是 Rust 组件编入的直接证据，它由 `src/suricata.c` 的 `PrintBuildInfo()` 硬编码追加；`HAVE_PACKET_FANOUT` 说明 AF_PACKET 的 fanout 头探测通过，`PCRE_JIT` 说明 PCRE2 JIT 可用。后端段要按「默认值 + 探测结果」理解：`AF_PACKET support: yes` 是默认开启且 `TPACKET_V2` / `TPACKET_V3` 声明存在的结果；`AF_XDP support: yes` 表示 libelf、libxdp、libbpf 的头与符号都通过了探测；`DPDK support: no`、`Netmap support: no`、`PF_RING support: no`、`NFQueue support: no`、`NFLOG support: no`、`IPFW support: no` 多为默认关闭或依赖未满足，若业务需要其中某一族，应回查 `./configure --help` 里的确切开关拼写、`configure.ac` 里的探测条件，以及系统是否装了对应开发包。`DAG enabled`、`Napatech enabled`、`WinDivert enabled`、`Npcap support` 属于专用硬件或平台后端，没有对应设备时保持 no 属正常。`Rust strict mode: no` 对应 `--enable-rust-strict` 未传，`Rust compiler path` 与 `Cargo path` 反映 `AC_PATH_PROG` 找到的可执行程序路径，用来确认没有误用到版本不符的工具链。需要留意，字段名、对齐空格与行序会随实际版本变化，务必以本地结果为准；这份摘要只反映编译期特性，DPDK 一类后端还需大页、EAL 参数与独占网卡才能真正跑起来。

再给一组「验证 FFI 边界与静态库」的命令，把 Rust 侧的检查做实；`SCJsonBuilder` 来自 `rust/cbindgen.toml` 的 `[export.rename]`，用来确认生成头确实由 cbindgen 产出而非手工拼凑。

```bash
# 查看静态库符号表，确认 Rust 组件被编入
nm -C rust/target/release/libsuricata_rust.a | head -10

# 检查生成头里是否有 cbindgen 的重命名结果
grep -c "SCJsonBuilder" rust/gen/rust-bindings.h

# 交叉编译场景可核对 RUST_TARGET 与 CARGO_BUILD_TARGET
grep -nE 'RUST_TARGET|CARGO_BUILD_TARGET|RUST_CROSS_COMPILE' rust/Makefile.am configure.ac
```

### 6. 注意事项、陷阱与最佳实践

第一条是别把 Rust 工具链当可选件。`configure.ac` 对 `rustc`、`cargo`、`rustdoc` 用 `AC_PATH_PROG` 逐一检查，任一为「no」即报错退出；`MIN_RUSTC_VERSION` 与 `rust/Cargo.toml.in` 的 `rust-version` 还会再卡版本。cbindgen 若未安装且源码树里也没有随包提供的 `rust/dist/rust-bindings.h`，configure 会明确报「cbindgen required」。`rust/Makefile.am` 的 `check` 目标会跑 `cargo test --workspace` 并做 `check-bindgen-bindings` 一致性检查，因此改了 Rust 侧导出接口却没重新生成绑定头，`make check` 会提示绑定可能过期。具体版本下限需对照实际版本核验，完整清单见 04-01。

第二条是 debug 与 release 的连锁影响。`--enable-debug` 命中时 `rust/Makefile.am` 的 `if !DEBUG` 不成立，于是 `RELEASE` 为空、`cargo build` 不带 `--release`，`configure.ac` 里 `RUST_SURICATA_LIBDIR` 也指向 `debug` 目录；同时 `RUST_FEATURES` 会追加 `debug`。若写脚本写死了 `rust/target/release/libsuricata_rust.a`，在调试构建下就会找不到文件。同理，交叉编译时 `RUST_CROSS_COMPILE` 会让 `RUST_TARGET = --target $(host_triplet)`，静态库落点里会多一层 target 目录，`qa/ci/rust-asan.sh` 里就显式设置了 `CARGO_BUILD_TARGET` 来配合。路径要按当前构建变体推导，不要硬编码。

第三条是后端选择先看环境再谈性能。DPDK 需独占网卡、大页与 EAL 参数，`suricata.yaml.in` 的 `dpdk:` 段注释已明确提示大页数量；它与普通网卡不能即插即用，也不能和别的应用共享同一端口。Netmap 要内核模块、专用驱动与满足 `NETMAP_API` 版本检查的头文件；AF_XDP 要 libelf、libxdp、libbpf 与相应内核能力；pcap 与 `source-pcap-file*` 族多用于离线回放或低速率，不适合作为高速在线主力。PF_RING 是否仍为受支持后端、对应源文件与启用方式需对照 `configure.ac` 与 `src/source-*.c` 实际版本核验，本快照把相关实现放在 `plugins/pfring/` 插件目录，不得凭印象写成 `src/source-pfring.c`。后端差异详见 06-02、模块见 07-06，参数见 04-03。

第四条是可选加速与生态关系别写反。Hyperscan 是可选 MPM 加速，`configure.ac` 里 `enable_hyperscan` 默认 no，只有 `PKG_CHECK_MODULES([libhs], libhs,...)` 加 `hs.h` / `hs_compile` 全通过才 `AC_DEFINE([BUILD_HYPERSCAN])`，缺失时回退 `src/util-mpm-ac*.c` 等 AC 实现，绝不是必需依赖或唯一实现。`--disable-ja3` / `--disable-ja4` 默认开启，关闭它们会同时影响 `rust/Makefile.am` 里 `RUST_FEATURES` 的 `ja3` / `ja4` feature。`suricata-update` 与内核主程序分仓、独立发版，不参与 `src/` 编译。加密载荷明文不可见，能拿到的是握手元数据、证书、SNI、JA3 一类信息，见 `src/output-json-tls.c` 与 `rust/src/ja4.rs`。性能与容量结论一律标注「需在目标机型实测」，不给绝对值；版本统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验。

最后补一条与打包相关的实践。顶层 `Makefile.am` 的 `EXTRA_DIST` 与 `DIST_SUBDIRS` 决定了 `make dist` 会把哪些内容收进发行包，而 `rust/Makefile.am` 的 `EXTRA_DIST` 里明确列出 `Cargo.toml`、`Cargo.lock`、`cbindgen.toml`、`dist/rust-bindings.h`、`dist/rust-ffi.h`、`dist/htp/htp_rs.h` 与 `vendor`，说明发布归档会尽量随包携带生成好的绑定头，以降低对 cbindgen 的现场依赖；同一份 `rust/Makefile.am` 还定义了 `dist/rust-bindings.h`、`dist/htp/htp_rs.h`、`dist/rust-ffi.h` 三个目标专门生成这些随包头。这与「源码树里只有 `.in` 模板」并不矛盾：前者是发布包的形态，后者是 git 源码树的形态。读者若从发布归档构建，可能发现 cbindgen 不是硬要求，正是因为随包头已就位；若从 git 源构建，则必须按 `configure.ac` 的检查备好 cbindgen，否则会看到「cbindgen required」一类报错。两种形态的差别需在对照实际版本时留意，完整变量见 04-01，打包与 CI 产物形态见 02-05。

### 7. 小结与延伸阅读

本篇把两块「configure 阶段最容易悄悄关掉」的能力讲成一条共用链路。Rust 侧是模板生成 Cargo 工程 → `rust/Makefile.am` 的 `all-local` 调 `cargo build` → 产出 `libsuricata_rust.a` → cbindgen 生成 `gen/rust-bindings.h`、`gen/rust-ffi.h`、`gen/htp/htp_rs.h` → C 侧包含并链接；工具链版本、绑定生成器与 `RUST_FEATURES` 共同决定它能否顺利产出。后端侧是 `AC_CHECK_*` / `PKG_CHECK_MODULES` 探测 → `HAVE_*` 宏与 `AM_CONDITIONAL` → 条件编入 `source-*.c` → 运行期再过大页、内核模块、驱动与权限门槛。两者最终都汇总到 `SURICATA_BUILD_CONF`，由 `suricata --build-info` 回显，因此「怎么组合、怎么验证」的答案是同一句话：先看摘要，再查探测条件与运行环境。完整清单见 04-01、04-03，完整变量见 04-01。

延伸阅读按需分流：构建选项与各后端 yaml 段逐项见 04-01、04-03，命令与 RPC 见 04-07，返回码见 04-08；`AppLayerParserState`、`TmModule`、`Packet` 等字段见 05-04、05-07、05-02；抓包后端原理见 06-02，应用解析与协议识别见 06-05，扩展与 FFI 机制见 06-14，MPM 与 Hyperscan 见 06-07；按目录的模块能力见 07-06、07-10、07-13；实战构建顺序见 02-03，调试构建、Sanitizer 与单测见 02-05，上线与基准读 08 册。全册交叉引用统一写成 `（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）`，性能数字一律标注需在目标机型实测。产物形态讲清之后，02-05 会补上「为了排错而构建」的那一类变体。

## 02-05 调试构建、Sanitizer、单元测试与 CI 产物形态

### 1. 背景与动机

前四篇谈的都是「编出一个能上线的 Suricata」：认清源码树、理解选项如何传导、按闭环跑通编译与安装、弄清 Rust 组件与抓包后端的启用条件。但工程实践里还有一类构建，它的目标不是吞吐也不是功能齐全，而是「让问题更容易被看见」：打开调试输出、编入单元测试、给 C 与 Rust 两侧插桩以捕捉越界与释放后使用、把编译告警提到最严、为 fuzz 生成专用目标。这类产物与生产二进制在行为与性能上并不等价，把它当成生产基准会得到完全失真的结论。本篇的动机，就是把这类「为了排错而构建」的变体单独讲清楚，避免读者拿着调试构建去做容量评估或上线。

第二个动机是「测试入口分散」。Suricata 的测试资产不在一个地方：C 侧单测在 `src/tests/` 与 `src/tests/fuzz/`，单测的运行入口是编译出的 `suricata -u`，`make check` 又通过 `src/Makefile.am` 的条件目标转发到它；Rust 侧由 `rust/Makefile.am` 的 `check` 目标执行 `cargo test --workspace`；静态分析与代码模式检查在 `qa/coccinelle/`；ASan 组合脚本在 `qa/ci/rust-asan.sh`；持续集成编排在 `.github/workflows/`。若不知道这些入口彼此如何衔接，很容易出现「跑了 make check 以为测完了，其实漏了 Rust 侧」或者「改了导出接口却没重新生成绑定头」的疏漏。把测试链画成一张图，是本篇要交付的第二样东西。

第三个动机是「产物形态」这个词本身。CI 里产出的并不只有一个可执行文件：还有用作证据的配置摘要、静态库符号表、`compile_commands.json`、上传的构建 artifact、`make dist` 生成的发行包、供二次开发的 `install-library` 与 `libsuricata-config`。理解这些产物各自回答什么问题，才能在排障时快速找到该看哪份输出，而不是把所有日志混在一起翻。大纲把「CI 产物形态」放在本篇，正是因为它天然归属于「构建与验证」这条主线。

边界仍按 SPEC 第 4 节划定：构建选项、变量与返回码的完整清单见 04-01、04-08，完整变量见 04-01；命令行与 RPC 见 04-07；机制与调用链写「原理见 06-xx」，结构体字段写「字段见 05-xx」，按 `src/` 目录的模块能力写「模块见 07-xx」。本篇只讲「怎么组合调试与测试开关、怎么验证、CI 产出什么」，不列参数全集、不展开检测引擎实现、不重列字段表。工具链与测试模块见 07-13，基准方法见 08-01，诊断树见 08-03。

### 2. 核心概念

第一组概念是「调试与测试开关族」。它们并非同一层面的东西：`--enable-debug` 命中时 `AC_DEFINE([DEBUG])` 并置 `AM_CONDITIONAL([DEBUG])`，既打开调试输出，又通过 `configure.ac` 让 `RUST_SURICATA_LIBDIR` 指向 `debug` 目录，还通过 `rust/Makefile.am` 让 `cargo build` 不带 `--release`、给 `RUST_FEATURES` 追加 `debug`；`--enable-unittests` 命中时 `AC_DEFINE([UNITTESTS])` 并置 `AM_CONDITIONAL([BUILD_UNITTESTS])`，决定 `src/Makefile.am` 的 `check-am` 是否真正执行 `suricata -u`；`--enable-debug-validation` 命中时 `AC_DEFINE([DEBUG_VALIDATION])`，给 `RUST_FEATURES` 追加 `debug-validate`，但 `configure.ac` 明确禁止它与单测同时启用。此外还有 `--enable-profiling` 一族（`PROFILING`、`PROFILE_RULES`、`PROFILE_LOCKING`）、`--enable-qa-simulation`（`QA_SIMULATION`）、`--enable-warnings`、`--enable-rust-strict`（把 `RUST_FEATURES` 设为 `strict`）、`--enable-fuzztargets`（`FUZZ`、`AFLFUZZ_NO_RANDOM`、`BUILD_FUZZTARGETS`）。具体选项名与默认值需对照实际版本核验，完整清单见 04-01。

第二组概念是 Sanitizer 的注入方式。ASan / UBSan 不是 configure 开关，而是通过环境变量把编译与链接参数注入构建链。`qa/ci/rust-asan.sh` 给出了被 CI 使用的组合：C 侧 `CFLAGS` 里带 `-g`、`-fno-omit-frame-pointer`、`-fsanitize=address`，`LDFLAGS` 里带 `-fsanitize=address`；Rust 侧 `RUSTFLAGS` 里带 `-Zsanitizer=address` 与 `-Cforce-frame-pointers=yes`，因 `-Zsanitizer` 需要 nightly 工具链，脚本会固定使用某个 nightly；同时导出 `CARGO_BUILD_TARGET` 为非默认值，注释解释这是因为「不希望 proc-macro 也被地址插桩」。脚本还设置了 `ac_cv_func_realloc_0_nonnull=yes` 与 `ac_cv_func_malloc_0_nonnull=yes`，用来规避 autoconf 在插桩环境下的函数探测误判。这些组合说明一个要点：C 与 Rust 两侧都要插桩，只给 `CFLAGS` 加 `-fsanitize=address` 而不给 `RUSTFLAGS`，Rust 静态库里的内存错误依然抓不到。

第三组概念是单测的运行模型。`src/suricata.c` 的用法说明里登记了 `-u`（run the unittests and exit）、`-U=REGEX` 与 `--unittest-filter=REGEX`（按正则过滤）、`--list-unittests`（列出单测）、`--fatal-unittests`、`--unittests-coverage`；长选项表里有 `{"list-unittests", 0, &list_unittests, 1}`、`{"unittests-coverage", 0, &coverage_unittests, 1}` 等条目。命中 `-u` 后 `suri->run_mode` 置为 `RUNMODE_UNITTEST`，最终在分发处调用 `RunUnittests(0, suri->regex_arg)`；`--list-unittests` 则走 `RUNMODE_LIST_UNITTEST` 调用 `RunUnittests(1, ...)`。`src/runmode-unittests.c` 的注释写明 `list_unittests` 为 1 时列出、为 0 时运行。若构建时没有启用单测，程序会打印「unit tests not enabled. Make sure to pass --enable-unittests to configure」一类错误，函数体里 `#else` 分支则是 `FatalError("Unittests are not build-in")`。命令与返回码语义见 04-07、04-08。

第四组概念是 CI 与产物的分层。`.github/workflows/` 下有 `builds.yml`、`rust-checks.yml`、`scan-build.yml`、`codeql.yml`、`codeqlpy.yml`、`cifuzz.yml`、`formatting.yml`、`docs.yml`、`nix.yml`、`commits.yml` 等工作流；`builds.yml` 定义了 `DEFAULT_CFLAGS: "-Wall -Wextra -Werror -Wno-unused-parameter -Wno-unused-function"`，并用 `prepare-deps`、`prepare-cbindgen` 两个前置 job 准备依赖与静态 cbindgen，后者再用 `upload-artifact` 归档供后续容器 job 使用。`qa/` 下则是可被本地或 CI 复用的脚本：`qa/ci/` 的 `rust-asan.sh`、`scan-build.sh`、`freebsd.sh`、`openbsd.sh`，`qa/coccinelle/` 的一堆 `.cocci` 规则与 `run_check.sh`，以及 `qa/lsan.suppress`、`qa/valgrind.suppress` 一类抑制文件。产物形态从「构建结果」延伸到「证据与归档」，二者都要会看。

### 3. 关键数据结构与源码位置

先点名单测主链上的真实文件与函数。`src/runmode-unittests.c` 的 `RunUnittests(int list_unittests, const char *regex_arg)` 是核心入口，函数体在 `#ifdef UNITTESTS` 内依次调用 `GlobalsInitPreConfig()`、`EngineModeSetIDS()`、`MpmTableSetup()`、`SpmTableSetup()`、`SCStorageInit()`、`AppLayerSetup()`、`SigTableInit()`、`SigTableSetup()`、`TmqhSetup()`、`TagInitCtx()`，在 `regex_arg` 为空时默认用 `".*"` 并先跑 `UtRunSelftest(regex_arg)`，随后 `UtInitialize()`、`RegisterAllModules()`、`HostBitInitCtx()`、`SCStorageFinalize()`、`AppLayerHtpEnableRequestBodyCallback()`、`AppLayerHtpNeedFileInspection()`、`RegisterUnittests()`，最后按 `list_unittests` 走 `UtListTests(regex_arg)` 或 `UtRunTests(regex_arg)`；运行分支还会 `PacketPoolInit()` / `PacketPoolDestroy()`、`UtCleanup()`，并在 `BUILD_HYPERSCAN` 下 `MpmHSGlobalCleanup()`，若有失败则 `exit(EXIT_FAILURE)`。文件里另有 `UTHRegisterTests()` 的调用。`src/suricata.c` 一侧则是 `--build-info` → `RUNMODE_PRINT_BUILDINFO` → `PrintBuildInfo()`、`-u` → `RUNMODE_UNITTEST` → `RunUnittests(0, ...)`，以及 `RegisterAllModules()` 里 `TmModuleFlowManagerRegister()`、`TmModuleReceiveNFQRegister()` 等模块登记。

再点名测试资产与装配文件。`src/Makefile.am` 的 `if BUILD_UNITTESTS` 条件块重定义 `check-am`：创建 `$(top_builddir)/qa/log/`，执行 `$(top_builddir)/src/suricata -u -l $(top_builddir)/qa/log/`，再删掉该目录；`distclean-local` 删除 `$(top_builddir)/src/build-info.h`，`build-info.h` 与 `runmode-unittests.c`、`runmode-unittests.h` 都在其文件清单里。`src/tests/` 下有大量按模块命名的用例文件，例如 `detect-parse.c`、`detect.c`、`detect-http-uri.c`、`detect-tls-certs.c`、`stream-tcp.c`、`stream-tcp-reassemble.c`、`stream-tcp-inline.c`、`stream-tcp-list.c`、`source-pcap.c`、`source-netmap.c`、`app-layer-htp-file.c`、`reputation.c`、`util-plugin.c`、`output-json-stats.c` 等；`src/tests/fuzz/` 下有 `fuzz_siginit.c`、`fuzz_sigpcap.c`、`fuzz_applayerparserparse.c`、`fuzz_applayerprotodetectgetproto.c`、`fuzz_confyamlloadstring.c`、`fuzz_dataset.c`、`fuzz_decodepcapfile.c`、`fuzz_mimedecparseline.c`、`fuzz_iprep.c`、`fuzz_decodebase64.c`、`confyaml.c`、`onefile.c`、`README` 与 `oss-fuzz-configure.sh`。后者内容极短却很有代表性：`./configure --enable-warnings --disable-shared --enable-fuzztargets --disable-gccmarch-native --enable-debug-validation`，一套典型的 fuzz 构建组合。

把调试与测试开关、条件宏、入口与用途对照如下；具体宏名与选项名需对照实际版本核验，完整清单见 04-01。

| 构建开关 | 条件宏 | 主要入口 | 用途 |
|---|---|---|---|
| debug | DEBUG | rust/Makefile.am 的 RELEASE 判定 | 关闭 release 优化并追加 debug feature |
| unittests | UNITTESTS 与 BUILD_UNITTESTS | suricata -u 与 RunUnittests | 运行 C 侧单元测试 |
| debug-validation | DEBUG_VALIDATION | rust/Makefile.am 追加 debug-validate | 启用校验代码，与单测互斥 |
| profiling 族 | PROFILING 与 PROFILE_RULES | 运行期统计 | 规则与锁的性能剖析 |
| fuzztargets | FUZZ 与 BUILD_FUZZTARGETS | src/tests/fuzz 目标 | 生成 fuzz 测试二进制 |
| rust-strict | RUST_FEATURES 为 strict | rust/Makefile.am | Rust 警告视为错误 |
| warnings | 编译器告警相关 | configure 的编译探测 | 打开额外的编译告警 |

### 4. 关键流程与调用链

调试构建链从 configure 开始。`--enable-debug` 与 `--enable-unittests` 被解析后，`configure.ac` 写 `DEBUG`、`UNITTESTS` 两个宏到 `src/autoconf.h`，并置 `DEBUG`、`BUILD_UNITTESTS` 两个 automake 条件；前者经 `rust/Makefile.am` 让 `cargo build` 走 debug 目录、追加 `debug` feature，后者经 `src/Makefile.am` 让 `check-am` 转发到 `suricata -u`。`make` 完成后，`make check` 创建日志目录并调用编译出的程序，`suricata -u` 把 `run_mode` 置为 `RUNMODE_UNITTEST`，`RunUnittests(0, regex_arg)` 完成初始化、注册全部测试用例、按 `UtRunTests` 执行，失败则以非零码退出。若要只看清单，用 `--list-unittests` 走 `RunUnittests(1, ...)` 的 `UtListTests` 分支；若只要跑某一族，用 `-U` 或 `--unittest-filter` 传正则。调试构建与单测执行链见图 02-05-01。

Sanitizer 链是另一条并行线。`qa/ci/rust-asan.sh` 先导出 C 侧 `CFLAGS` / `LDFLAGS` 的 `-fsanitize=address` 与 `-fno-omit-frame-pointer`，再导出 Rust 侧 `RUSTFLAGS` 的 `-Zsanitizer=address`、`-Cforce-frame-pointers=yes` 与 `CARGO_BUILD_TARGET`，并规避 autoconf 探测误判；随后跑 `./autogen.sh`、`./configure --enable-warnings --enable-debug --enable-unittests --disable-shared`、`RUSTFLAGS=... make -j`。构建完成后脚本用 `nm -C rust/target/${CARGO_BUILD_TARGET}/debug/libsuricata_rust.a > rust-asan-symbols.txt` 再 `grep -q __asan_report_load1 rust-asan-symbols.txt`，以「静态库里是否真有 ASan 报告符号」来确认 Rust 侧插桩生效，而不是只看编译有没有报错；接着 `./src/suricata --build-info`、`./src/suricata -u -l .`，最后在 `ASAN_OPTIONS="detect_leaks=0"` 下跑 `cargo test --workspace --all-targets`，并用 `suricata-verify/run.py -q --debug-failed` 做外部验证。`src/suricata.c` 的 `PrintBuildInfo()` 在 `Features` 行里会根据 `SC_ADDRESS_SANITIZER`、`FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION` 等宏追加 `ASAN`、`FUZZ` 标记，因此 `--build-info` 也可作为插桩是否编入的旁证。

CI 与产物链则是第三条。工作流由 `.github/workflows/builds.yml` 触发，`prepare-deps` 与 `prepare-cbindgen` 两个前置 job 准备依赖与静态 cbindgen，`upload-artifact` 把中间产物归档；各发行版容器 job 用 `dnf` 或 `apt` 装齐依赖后跑 configure、make 与各类检查，`.github/workflows/` 下另有 rust-checks、scan-build、codeql、cifuzz、formatting、docs 等分工。本地可复用的证据还有：顶层 `Makefile.am` 的 `compile-commands` 目标在 clang 下生成 `compile_commands.json`，`install-library` 与 `install-headers` 配合 `libsuricata-config` 供二次开发把 Suricata 当库链接，`make dist` 结合 `bundle.txt` 生成发行包，`qa/coccinelle/run_check.sh` 做代码模式检查。CI 流水线与产物形态见图 02-05-02。

### 5. 配置/命令/代码实例

下面这组命令演示「怎么组合调试与测试开关、怎么验证」。先组合一套调试带单测的构建，再列清单、跑过滤单测、回显构建特性。选项名需对照实际版本核验，完整清单见 04-01、完整变量见 04-01，命令语义见 04-07。

```bash
# 组合一套调试带单测的构建，关闭共享库便于符号排查
./configure --enable-debug --enable-unittests --disable-shared
make -j"$(nproc)"

# 列出已注册单测，再按正则过滤后运行
./src/suricata --list-unittests | head -20
./src/suricata -u -U "Detect.*" -l .

# 回显构建信息，确认调试与测试相关开关确实编入
./src/suricata --build-info | grep -E 'Features|Unit tests|Debug output|Debug validation|Fuzz'

# make check 在启用单测时会转发到 suricata -u
make check
```

对 `--build-info` 的摘要段与 `-u` 的汇总行，以下是示例输出，具体格式需对照实际版本核验；单测汇总行的确切措辞需以本地 `src/runmode-unittests.c` 与所用版本为准，版本字符串行依版本纪律不抄录具体值。

```text
Features: RUST PCRE_JIT
Suricata Configuration:
  Unit tests enabled:                      yes
  Debug output enabled:                    yes
  Debug validation enabled:                no
  Profiling enabled:                       no
  Fuzz targets enabled:                    no
  Coccinelle / spatch:                     no
[Info] - ==== Tests: 42, Failures: 0 ====
[Info] - Unittests passed, exiting.
```

逐行判读这段输出。`Features` 行来自 `src/suricata.c` 的 `PrintBuildInfo()`，`RUST` 是硬编码追加项，`PCRE_JIT` 对应 PCRE2 JIT 探测通过；若本次构建带 ASan 或 fuzz，这一行还会出现 `ASAN`、`FUZZ` 一类标记，可据此判断插桩是否编入。配置摘要段要与命令行逐项对照：`Unit tests enabled: yes` 与 `Debug output enabled: yes` 正对应上面传入的 `--enable-unittests`、`--enable-debug`；`Debug validation enabled: no` 是必须保持的，因为 `configure.ac` 明确禁止它与单测同时启用；`Profiling enabled: no`、`Fuzz targets enabled: no`、`Coccinelle / spatch: no` 说明这几族未开。接下来两行是单测汇总示意：`Tests` 是本次按过滤正则实际执行的用例数，`Failures` 必须为零，非零时 `RunUnittests` 会走 `exit(EXIT_FAILURE)`，CI 应据此判失败；末行 `exiting.` 表示单测模式正常结束，它不会拉起抓包线程、不写告警。需要留意，摘要字段的对齐空格、单测汇总的措辞与行数会随实际版本变化，务必以本地结果为准；`-U "Detect.*"` 只跑名字匹配的那一族，若 `Tests` 为零应检查正则是否写错，而不是断定单测没编进去。命令全集见 04-07，返回码与日志级别见 04-08。

ASan 组合单独给一组命令，直接对应 `qa/ci/rust-asan.sh` 的做法；`-Zsanitizer=address` 需要 nightly 工具链，具体版本需对照实际版本核验。

```bash
# C 侧插桩
export CFLAGS="-Wall -Wextra -Werror -Wno-unused-parameter -Wno-unused-function -g -fno-omit-frame-pointer -fsanitize=address"
export LDFLAGS="-fsanitize=address"

# Rust 侧插桩，需 nightly 与非默认构建目标
export RUSTFLAGS="-Zsanitizer=address -Cforce-frame-pointers=yes"
export CARGO_BUILD_TARGET="x86_64-unknown-linux-gnu"

# 规避 autoconf 在插桩环境下的函数探测误判
export ac_cv_func_realloc_0_nonnull=yes
export ac_cv_func_malloc_0_nonnull=yes

CFLAGS="$CFLAGS" LDFLAGS="$LDFLAGS" ./configure --enable-warnings --enable-debug --enable-unittests --disable-shared
RUSTFLAGS="$RUSTFLAGS" make -j"$(nproc)"

# 以静态库符号确认 Rust 侧确实被插桩
nm -C "rust/target/${CARGO_BUILD_TARGET}/debug/libsuricata_rust.a" | grep __asan_report_load1 | head -5
```

最后给一组「CI 产物与打包」命令，把证据链收尾；`compile-commands` 目标在 clang 下生成 `compile_commands.json`，`make dist` 与 `bundle.txt` 用于发行包，`suricata-verify` 是独立测试框架（需对照实际版本核验）。

```bash
# 生成编译数据库，供静态分析与 IDE 使用
make compile-commands

# 检查 coccinelle 规则与抑制文件是否随包提供
ls -1 qa/coccinelle/ qa/lsan.suppress qa/valgrind.suppress

# 打包发行物与二次开发库入口
make dist
make install-library
command -v libsuricata-config
```

### 6. 注意事项、陷阱与最佳实践

第一条是开关互斥与前提，别把调试族一股脑全打开。`configure.ac` 里 `--enable-debug-validation` 与 `--enable-unittests` 同时启用会直接 `AC_MSG_ERROR([debug_validation can't be enabled with enabled unittests!])`；`src/tests/fuzz/oss-fuzz-configure.sh` 采用的是 `--enable-fuzztargets --disable-gccmarch-native --enable-debug-validation --disable-shared --enable-warnings`，即 fuzz 构建走 debug-validation 而不走 unittests，正体现了这条互斥。`--enable-fuzztargets` 还要求 nightly 与 `-fsanitize=fuzzer` 一类链接能力，`RUST_BUILD_STD` 条件里就检查了 nightly 与 coverage 标志。组合前先确定目的，再逐族叠加，完整清单见 04-01。

第二条是「未启用单测」与「单测失败」要分清。前者是构建问题：`src/suricata.c` 在 `--list-unittests`、`--fatal-unittests` 等分支会打印「unit tests not enabled. Make sure to pass --enable-unittests to configure」，`src/runmode-unittests.c` 的 `#else` 分支是 `FatalError("Unittests are not build-in")`，此时应回查 configure 是否传了开关、是否 `make clean` 干净、`src/autoconf.h` 里是否有 `UNITTESTS`。后者是用例或代码问题：`UtRunTests` 返回非零失败数时 `RunUnittests` 走 `exit(EXIT_FAILURE)`，应拿 `-U` 过滤到具体用例、`--list-unittests` 核对清单，再看 `qa/log/` 下的日志。两者现象相似，处理方向完全不同。命令与返回码语义见 04-07、04-08。

第三条是 Sanitizer 的坑。`-Zsanitizer=address` 需要 nightly Rust，脚本因此固定某个 nightly 工具链，具体版本需对照实际版本核验；`CARGO_BUILD_TARGET` 必须设为非默认值，否则 proc-macro 也会被插桩导致构建异常；`ac_cv_func_realloc_0_nonnull` 与 `ac_cv_func_malloc_0_nonnull` 两个变量用于绕过 autoconf 在插桩环境下的误判，缺了可能 configure 阶段就卡住。C 与 Rust 两侧都要插桩，验证方式是用 `nm -C` 检查静态库里是否有 `__asan_report_load1` 一类符号，而不是只看 make 有没有报错。Rust 侧单元测试还可能触发 leak 报告，`qa/ci/rust-asan.sh` 用 `ASAN_OPTIONS="detect_leaks=0"` 单独规避，并注明「有 leaks 待查」，这属于调试用途的取舍，不能带到生产结论里。

第四条是最重要的性能纪律。调试构建关闭了 release 优化、追加了 debug 与 debug-validate feature，ASan / UBSan 插桩又会显著改变指令与内存行为，profiling 与 coccinelle 检查同样引入额外开销，因此这类产物**不可用作生产基准**；任何吞吐、pps、丢包率、内存占用结论一律标注「需在目标机型实测」，不给绝对值，基准方法见 08-01、调优见 08-02。把「加线程」写成必然线性提速也是错的，runmode 与流亲和、RSS、fanout 共同决定扩展性，原理见 06-13。CI 产出的 artifact、发行包与静态库都是验证与分发用途，不是可直接照抄的性能样本。

第五条仍是全册通用红线。`suricata-update` 与内核主程序分仓、独立发版，不参与 `src/` 编译；`rust/` 与 Cargo 是构建的一部分，Suricata 不是纯 C 项目；Hyperscan 是可选 MPM 加速，缺失时回退 `src/util-mpm-ac*.c` 等 AC 实现，不是必需依赖或唯一实现；PF_RING 是否仍为受支持后端需对照 `configure.ac` 与 `src/source-*.c` 实际版本核验，不得编造 `src/source-pfring.c`；抓包后端环境差异大，DPDK 需独占网卡、大页与 EAL 参数，详见 02-04、原理见 06-02、模块见 07-06。加密载荷明文不可见，能拿到的是握手元数据、证书、SNI、JA3 一类信息，见 `src/output-json-tls.c` 与 `rust/src/ja4.rs`。版本统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验。

### 7. 小结与延伸阅读

本篇把「为了排错而构建」讲成三条链。调试与单测链是 configure 写出 `DEBUG`、`UNITTESTS` 宏与 `DEBUG`、`BUILD_UNITTESTS` 条件 → `rust/Makefile.am` 切到 debug 库并追加 feature → `src/Makefile.am` 的 `check-am` 转发到 `suricata -u` → `RunUnittests` 经 `UtRunTests` 执行 `src/tests/` 注册的用例 → 失败以非零码退出。Sanitizer 链是 `CFLAGS` / `LDFLAGS` 的 `-fsanitize=address` 配合 `RUSTFLAGS` 的 `-Zsanitizer=address` 与 `CARGO_BUILD_TARGET`，并以 `nm -C` 检查静态库符号确认插桩生效。CI 与产物链是 `.github/workflows/` 编排、`qa/ci/` 与 `qa/coccinelle/` 提供可复用检查、`upload-artifact` 与 `make dist`、`install-library`、`libsuricata-config`、`compile_commands.json` 构成证据与分发物。三者共同回答「怎么组合调试开关、怎么验证、CI 产出什么」，完整清单见 04-01、完整变量见 04-01。

延伸阅读按需分流：构建选项、默认值与误配后果读 04-01，命令行、Unix socket 与 RPC 读 04-07，返回码与告警判读读 04-08；`SCInstance`、`ThreadVars`、`TmModule`、`Packet` 字段分别见 05-09、05-07、05-02；规则加载与检测求值、MPM 与 Hyperscan、runmode 的机制分别见 06-06、06-07、06-08、06-13；工具链与测试模块见 07-13；源码与目录见 02-01，构建链与配置摘要闭环见 02-02，从零构建实战见 02-03，Rust 与抓包后端见 02-04；性能基准方法见 08-01，调优见 08-02，诊断树与故障案例见 08-03、08-04，上线清单见 08-06。全册交叉引用统一写成 `（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）`，性能数字一律标注需在目标机型实测。至此 02 册五篇从「拿到源码」到「编出产物」再到「为排错而构建」形成完整闭环，配置与参数的全集请始终以 04 册为唯一权威源。
