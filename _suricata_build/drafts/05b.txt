# Suricata 技术资料 · 05 关键数据结构字段详解（分片 B）

## 05-06 规则组与预过滤结构（SigGroupHead、prefilter、MPM、Hyperscan）

### 1. 本篇定位与覆盖范围

本篇是 05 册「检测层」后半段的逐字段权威源，承接 05-05 已点名但未展开的分组与预过滤结构，逐项覆盖 `src/detect.h:1730` 的 `SigGroupHead`、`src/detect.h:1701` 的 `SigGroupHeadInitData`、`src/detect.h:1594` 的 `MpmStore`、`src/detect.h:1615` 的 `PrefilterEngineList`、`src/detect.h:1657` 的 `PrefilterEngine`、`src/detect.h:762` 的 `DetectBufferMpmRegistry`，以及 `src/util-mpm.h` 中 `MpmCtx`（`:111`）、`MpmPattern`（`:70`）、`MpmThreadCtx`（`:62`）、`MpmConfig`（`:105`）、`MpmCtxFactoryItem`（`:138`）、`MpmCtxFactoryContainer`（`:148`）、`MpmTableElmt`（`:168`）这一整套多模式匹配上下文，并补上 `src/util-prefilter.h:34` 的 `PrefilterRuleStore`、`src/detect-engine-mpm.h:130` 的 `PrefilterMpmListId` 与 `:137` 的 `MpmListIdDataArgs`。回答的是「一条规则选中的 fast_pattern 落到哪个结构、编译后的签名组里挂了哪几类引擎数组、MPM 上下文靠什么字段区分 AC 与 Hyperscan、候选规则 id 存在哪里」这类问题。按 SPEC 第 4 节与总纲第 2 节的去重约定，05 册是全集团结构体逐字段的唯一权威源，其余各册遇到对象成员只点名并写「字段见 05-06」，不得另起字段表；本篇自身同时守住两条硬边界：禁止展开 fast_pattern 选择、MPM 构建、签名分组编译、预过滤引擎注册与求值这些机制的状态机与调用链，遇到「这段怎么工作」一律写「原理见 06-06」至「原理见 06-08」；禁止重列 `mpm-algo`、`configure` 选项、`content` 及其修饰符的规则关键字全集，遇到「怎么配」写「参数见 04-02」「参数见 04-06」；按 `src/` 目录归属写「模块见 07-04」「模块见 07-05」。本篇只讲字段含义、内存布局、生命周期与关联函数入口。

事实来源与全册一致：唯一事实锚点是 `upstream_src/suricata/suricata-main/`，本篇所有结构体名、成员类型、枚举取值与行号均对照该目录下 `src/detect.h`、`src/detect-engine-mpm.h`、`src/detect-engine-mpm.c`、`src/util-mpm.h`、`src/util-mpm.c`、`src/util-mpm-ac.h`、`src/util-mpm-hs.h`、`src/util-mpm-hs-core.h`、`src/util-prefilter.h`、`src/util-prefilter.c` 与顶层 `configure.ac` 核验；版本基准统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准但正文不写绝对值。凡字段名、类型宽度、条件宏、函数签名无充分把握者，一律写「需对照实际版本核验」并给出上述可定位目录，禁止凭印象补值，禁止编造内存偏移。有一类结构必须按不透明句柄处理：`MpmCtx.ctx` 是 `void *`，其真实布局并不在 `src/util-mpm.h` 里，AC 实现落在 `src/util-mpm-ac.c` 与 `src/util-mpm-ac.h` 的 `SCACCtx`，Hyperscan 实现落在 `src/util-mpm-hs.c` 与 `src/util-mpm-hs-core.h` 的 `SCHSCtx`，本篇对这类成员一律写明「不透明句柄，内部布局见 xxx」，只登记句柄本身与可见的元字段，不虚构内部成员。

能力边界贯穿全册且不得写反。Suricata 是 IDS / IPS / NSM 引擎，不做 IP 转发、不做路由、不是防火墙，内联阻断依靠 NFQUEUE 或 AF_PACKET 桥接的 verdict；只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见，能拿到的是握手元数据、证书、SNI、JA3 / JA4 一类信息；规则语法兼容 Snort 但有自有扩展，不能宣称百分之百兼容；EVE JSON 是主要输出；Hyperscan 是可选 MPM 加速，探测不到或平台校验不通过时回退 AC 等其他实现，`mpm_type`、`mpm_default_matcher` 反映的是选型结果而非唯一依赖，绝不能写成必需依赖；`rust/` 与 Cargo 是构建的一部分；`suricata-update` 是分仓独立工具；多线程不等于加线程必然线性提速。任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」，不给绝对值。本篇按 B 手册字典型七节展开，交叉引用统一收束为（参数见 04-02 ｜ 参数见 04-06 ｜ 原理见 06-07 ｜ 模块见 07-05）：匹配器与构建选项参数见 04-01、04-02，fast_pattern 与内容修饰符参数见 04-06，规则编译、MPM 与预过滤机制见 06-06 至 06-08，detect 与 util-mpm 目录模块见 07-04、07-05。

### 3. 逐项详解

**`MpmCtx` 与 `MpmPattern` 的公共外壳**。`MpmCtx`（`src/util-mpm.h:111`）是全部匹配器实现共用的外层上下文，本身不含任何自动机状态：`ctx` 是 `void *` 的不透明句柄，AC 实现把它强转为 `SCACCtx`、Hyperscan 实现把它强转为 `SCHSCtx`，因此字段表里只能登记句柄本身，内部布局见 `src/util-mpm-ac.c` 与 `src/util-mpm-hs.c`，跨模块代码不得直接解引用。`mpm_type` 是 `uint8_t` 的匹配器类型号，取值来自 `src/util-mpm.h:48` 的枚举，运行时用它索引 `mpm_table[mpm_type]` 取到对应 `MpmTableElmt` 的函数指针；`flags` 承载 `MPMCTX_FLAGS_GLOBAL`、`MPMCTX_FLAGS_NODEPTH`、`MPMCTX_FLAGS_CACHE_TO_DISK` 三个 `BIT_U8` 位，源码注释说明「single」运行模式下用全局 mpm_ctx、「full」模式下每个 sgh 一份。`maxdepth`、`minlen`、`maxlen` 是加模式过程中维护的深度与长度边界，`pattern_cnt` 记唯一模式数，`memory_cnt` 与 `memory_size` 是分配次数与字节计数，`max_pat_id` 是模式 id 上界，`init_hash` 是只在初始化期存活的 `MpmPattern *` 哈希表，编译完成后由各实现的 `Prepare` 释放。`MpmPattern`（`src/util-mpm.h:70`）是 `init_hash` 里的节点：`len`、`flags`、`offset`、`depth` 对应内容与修饰符，`original_pat`、`cs`、`ci` 是原始串与大小写两份副本，`id` 是模式 id，`sids_size` 与 `sids` 把模式映射回签名内部 id，`next` 串哈希冲突链。标志位 `MPM_PATTERN_FLAG_NOCASE`、`MPM_PATTERN_FLAG_DEPTH`、`MPM_PATTERN_FLAG_OFFSET`、`MPM_PATTERN_CTX_OWNS_ID`、`MPM_PATTERN_FLAG_ENDSWITH` 与 `MPM_FEATURE_FLAG_DEPTH`、`MPM_FEATURE_FLAG_OFFSET`、`MPM_FEATURE_FLAG_ENDSWITH` 定义在 `src/util-mpm.h:154` 之后，取值需对照实际版本核验，参数见 04-06。构造入口是 `src/util-mpm.c:208` 的 `MpmInitCtx`，登记入口是 `MpmAddPattern`、`MpmAddPatternCS`、`SCMpmAddPatternCI`，释放入口 `MpmFreePattern`，这些函数只点名，机制原理见 06-07。

**`MpmTableElmt` 与匹配器选型字段**。`MpmTableElmt`（`src/util-mpm.h:168`）是一张纯函数指针表：`name` 是匹配器名；`InitCtx`、`InitThreadCtx`、`DestroyCtx`、`DestroyThreadCtx` 管上下文与线程上下文生命周期；`ConfigInit`、`ConfigDeinit`、`ConfigCacheDirSet`、`CacheStatsInit`、`CacheStatsPrint`、`CacheStatsDeinit`、`CacheRuleset`、`CachePrune` 管配置与编译缓存；`AddPattern`、`AddPatternNocase`、`Prepare`、`Search`、`PrintCtx`、`PrintThreadCtx` 是登记、编译、扫描与打印；`RegisterUnittests` 受 `UNITTESTS` 控制；`feature_flags` 声明该实现是否支持 depth、offset、endswith。全局 `mpm_table[MPM_TABLE_SIZE]` 与 `mpm_default_matcher` 定义在 `src/util-mpm.c:46`、`src/util-mpm.c:47`，`MpmTableSetup`（`src/util-mpm.c:223`）在 `BUILD_HYPERSCAN` 下把默认匹配器设为 `MPM_HS`、否则设为 `MPM_AC`，并依次调用 `MpmACRegister`、`MpmACTileRegister`、`MpmHSRegister`；在 `HAVE_HS_VALID_PLATFORM` 下还会用 `hs_valid_platform()` 做运行时平台校验，不通过时把默认匹配器改回 `DEFAULT_MPM_AC`。这条事实直接支撑能力边界：Hyperscan 是可选 MPM 加速，缺失或平台校验失败时回退 AC 等其他实现，不得写成必需依赖或唯一实现。`configure.ac:654` 起的 `enable_hyperscan`、`--with-libhs-includes`、`--with-libhs-libraries`、`AC_CHECK_LIB(hs, hs_compile, ...)` 与 `configure.ac:692` 的 `AC_DEFINE([BUILD_HYPERSCAN], ...)` 决定该分支是否编入，选项名与默认值需对照实际版本核验，参数见 04-01、04-02。

**上下文工厂与配置字段**。`MpmCtxFactoryItem`（`src/util-mpm.h:138`）是「按缓冲区与协议复用 MPM 上下文」的登记项：`name`、`id`、`sm_list`、`alproto` 描述身份，`mpm_ctx_ts` 与 `mpm_ctx_tc` 是双向两份上下文，`next` 串链；`MpmCtxFactoryContainer`（`src/util-mpm.h:148`）只有 `items` 与 `max_id` 两个字段。相关入口是 `MpmFactoryRegisterMpmCtxProfile`、`MpmFactoryGetMpmCtxForProfile`、`MpmFactoryReClaimMpmCtx`、`MpmFactoryIsMpmCtxAvailable`、`MpmFactoryDeRegisterAllMpmCtxProfiles`，`MPM_CTX_FACTORY_UNIQUE_CONTEXT` 常量表示取唯一上下文。`MpmConfig`（`src/util-mpm.h:105`）的 `cache_dir_path`、`cache_max_age_seconds`、`cache_stats` 对应编译缓存目录、存活秒数与统计句柄，配合 `MpmTableElmt` 的缓存回调使用；`MpmThreadCtx`（`src/util-mpm.h:62`）只有 `ctx`、`memory_cnt`、`memory_size`，同样是每线程的不透明句柄外壳。这些字段的读写时机集中在注册期与配置期，运行期只读；`memory_cnt`、`memory_size` 一类计数字段的具体量级需在目标机型实测，不给绝对值。

**`SigGroupHead` 与编译产物数组**。`SigGroupHead`（`src/detect.h:1730`）是「一个签名组的匹配数据容器」，`flags` 是 `uint16_t` 的 `SIG_GROUP_HEAD_` 位集合，源码里可见 `SIG_GROUP_HEAD_HAVERAWSTREAM`、`SIG_GROUP_HEAD_HAVEFILEMAGIC`（受 `HAVE_MAGIC` 控制）、`SIG_GROUP_HEAD_HAVEFILEMD5`、`SIG_GROUP_HEAD_HAVEFILESHA1`、`SIG_GROUP_HEAD_HAVEFILESHA256`，位定义需对照实际版本核验；`filestore_cnt` 记组内带 filestore 关键字的签名数；`id` 是注释说明「用于索引 sgh_array 做统计」的唯一 id，与 `DetectEngineCtx.sgh_array`（字段见 05-05）呼应。最核心的是五类 `PrefilterEngine *` 指针：`pkt_engines`、`payload_engines`、`tx_engines`、`frame_engines`、`post_rule_match_engines`，最后一项的源码注释说明用于「规则修改状态之后」运行的引擎；`init` 指向只在初始化期存活的 `SigGroupHeadInitData`，注释明确写着只在 init 阶段使用。理解要点是运行期读的是这五个数组，编译完成后 `init` 不再有效；`Flow` 上缓存的 `sgh_toserver`、`sgh_toclient`（字段见 05-03）指向的正是本结构，热重载失效由 `DetectEngineCtx.version`（字段见 05-05）触发，机制原理见 06-06。

**`SigGroupHeadInitData` 与 `MpmStore` 的施工数据**。`SigGroupHeadInitData`（`src/detect.h:1701`）是编译期的施工脚手架：`mpm_store[MPMB_MAX]` 是按 `enum MpmBuiltinBuffers` 索引的内建缓冲区模式存储数组，`sig_array` 与 `sig_size` 是组内签名内部 id 的位图与字节数，`protos[256]` 是该组适用的协议位，`direction` 取 `SIG_FLAG_TOSERVER` 或 `SIG_FLAG_TOCLIENT` 或两者，`score` 是源码注释所说「尽量让本组唯一」的打分，`max_sig_id` 是组内最大签名 idx。`app_mpms`、`pkt_mpms`、`frame_mpms` 是三类 `MpmCtx **` 数组，`pkt_engines`、`payload_engines`、`tx_engines`、`frame_engines`、`post_rule_match_engines` 是五条 `PrefilterEngineList *` 登记链，`sig_cnt` 与 `match_array` 是组内签名数与 `Signature **` 指针数组。`MpmStore`（`src/detect.h:1594`）是 `mpm_store` 的元素：`sid_array` 与 `sid_array_size` 是签名 id 位图，`direction`、`buffer`、`sm_list`、`sgh_mpm_context`、`alproto`、`mpm_ctx` 分别记方向、内建缓冲区类型、匹配链 id、工厂上下文 id、应用协议与绑定的上下文。相关入口是 `src/detect-engine-mpm.h` 声明的 `MpmStoreInit`、`MpmStoreFree`、`MpmStoreReportStats`、`MpmStorePrepareBuffer` 与 `PatternMatchPrepareGroup`，机制原理见 06-06、06-07。

**预过滤引擎的两种表示与回调类型**。`PrefilterEngineList`（`src/detect.h:1615`）是注册期的链表节点，字段最全：身份类有 `id`、`alproto`、`tx_min_progress`、`frame_type`、`pkt_mask`、`sub_state`、`pkt_hook`、`name`、`gid`；上下文类有 `void *pectx`，源码注释说明「MPM 引擎可能是 MpmCtx，其他引擎是别的 ctx」；回调类有 `Prefilter`、`PrefilterTx`、`PrefilterFrame`、`PrefilterPostRule` 四个函数指针，类型分别来自 `src/detect.h:1607` 至 `src/detect.h:1613` 的 `PrefilterPktFn`、`PrefilterFrameFn`、`PrefilterTxFn`；链与释放类有 `next`、`Free`，`Free` 为 `NULL` 时表示不释放 `pectx`；`run_always` 表示每次事务更新都运行，源码注释特意说明它不改变真实的 `tx_min_progress` 记账。`PrefilterEngine`（`src/detect.h:1657`）是编译后的紧凑数组元素：`local_id`、`alproto` 与 `gid` 保留身份，`ctx` 是三选一联合体，包分支含 `mask` 与 `hook`、应用分支含 `tx_min_progress` 与 `sub_state`、帧分支只含 `frame_type`；`is_last` 与 `is_last_for_progress` 是两个遍历终止位，`run_always` 与登记链同名但注释说明与 `-1` 哨兵分开保存；`pectx` 是转存后的上下文句柄，`cb` 是四类回调三选一的联合体。两者关系与 05-05 里 `SigMatch` 链和 `SigMatchData` 数组的关系同构：链表便于注册期增删，数组便于匹配期顺序遍历，机制原理见 06-07、06-08。

**候选规则存储、注册表与辅助结构**。`PrefilterRuleStore`（`src/util-prefilter.h:34`）只有三个字段：`rule_id_array` 是 `SigIntId *` 候选规则 id 数组，`rule_id_array_cnt` 是当前数量，`rule_id_array_size` 是已分配槽位数；`PMQ_RESET` 宏只把 `cnt` 清零而不释放数组，`PrefilterAddSids` 在容量不足时调用 `PrefilterAddSidsResize`，分配失败时按注释「能保留多少保留多少」裁剪追加量，生命周期入口是 `PmqSetup`、`PmqReset`、`PmqCleanup`、`PmqFree`。`DetectBufferMpmRegistry`（`src/detect.h:762`）是「一次性注册」的缓冲区 MPM 登记表：`name`、`pname[DETECT_PROFILE_NAME_LEN]`、`direction`、`sm_list`、`sm_list_base`、`priority`、`id`、`type`、`sgh_mpm_context`、`PrefilterRegisterWithListId`、`transforms` 是身份与配置，尾部联合体按 `type` 在 `app_v2`（含 `GetData`、`GetDataSingle`、`GetMultiData` 三选一与 `alproto`、`tx_min_progress`、`sub_state`）、`pkt_v1`（含注册回调与 `GetData`）、`frame_v1`（含 `alproto`、`type`）之间取舍，`next` 串注册表。`src/detect-engine-mpm.h:130` 的 `PrefilterMpmListId` 含 `list_id`、`mpm_ctx`、`GetData`、`transforms`，`:137` 的 `MpmListIdDataArgs` 含 `local_id`、`txv`，`:72` 还定义了 `PrefilterRegisterFunc` 函数指针类型；注册函数族 `DetectAppLayerMpmRegister`、`DetectAppLayerMpmRegisterSubState`、`DetectAppLayerMpmRegisterSingle`、`DetectAppLayerMpmMultiRegister`、`DetectPktMpmRegister`、`DetectFrameMpmRegister` 与 `PrefilterGenericMpmFrameRegister` 只点名，机制原理见 06-07，模块见 07-05。

**AC 与 Hyperscan 内部布局的不透明边界**。`SCACCtx`（`src/util-mpm-ac.h:54`）是 AC 实现的真实布局，可见字段有 `parray`、`state_count`、`pattern_id_bitarray_size`、两份按状态数二选一的 `state_table_u16` 与 `state_table_u32`、`goto_table`、`failure_table`、`output_table`、`pid_pat_list`、`single_state_size`、`allocated_state_count`；配套 `SCACPatternList`（`:33`）含 `cs`、`patlen`、`offset`、`depth`、`endswith`、`sids_size`、`sids`，`SCACOutputTable`（`:47`）含 `pids`、`no_of_entries`。Hyperscan 侧 `src/util-mpm-hs-core.h` 在 `BUILD_HYPERSCAN` 条件内定义 `SCHSPattern`（`:37`）、`SCHSCtx`（`:59`）、`SCHSThreadCtx`（`:70`）、`PatternDatabase`（`:79`）、`PatternDatabaseCache`（`:92`），分别登记模式、上下文句柄（含 `init_hash`、`pattern_db`、`hs_db_size`）、线程 scratch、编译库（含 `hs_db`、`pattern_cnt`、`ref_cnt`、`cached`、`no_cache`）与缓存计数；`src/util-mpm-hs.h` 只暴露 `MpmHSRegister`、`MpmHSGlobalCleanup` 两个声明，属于典型的「头文件给入口、实现文件藏布局」。本篇对这些结构一律写明「内部布局见 xxx.c / xxx.h，条件编入，禁止依赖偏移」，`MpmCtx.ctx` 与 `PrefilterEngine.pectx` 这类 `void *` 同理。交叉引用统一为（参数见 04-02 ｜ 参数见 04-06 ｜ 原理见 06-07 ｜ 模块见 07-05）：匹配器与构建参数见 04-01、04-02、04-06，编译与匹配机制见 06-06 至 06-08，detect 与 util-mpm 目录模块见 07-04、07-05。

### 6. 版本差异

本套资料统一以「上游 main 快照（2026-11 抓取）」为版本基准，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当本套资料的版本号；需要说明版本来源时写「具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验」。规则组与预过滤结构恰是全项目随匹配器实现与规则语言演进最快的一类事实：函数表会新增回调、引擎种类会从包与载荷扩展到事务与帧、内部结构会在头文件与实现文件之间迁移、Hyperscan 相关结构整族受构建宏控制，因此第 2 节与第 3 节给出的行号与字段清单是「这份快照的事实」，不是跨版本永久承诺。

几处已能在本快照里观察到的差异点值得单列。其一是匹配器枚举与默认选型：`src/util-mpm.h:48` 的枚举为 `MPM_NOTSET`、`MPM_AC`、`MPM_AC_KS`、`MPM_HS`、`MPM_TABLE_SIZE`，`src/util-mpm.c:216` 起的 `DEFAULT_MPM` 在 `BUILD_HYPERSCAN` 下为 `MPM_HS`、否则为 `MPM_AC`，`DEFAULT_MPM_AC` 固定为 `MPM_AC`；`MpmTableSetup` 还会调用 `MpmACTileRegister` 并在 `HAVE_HS_VALID_PLATFORM` 下用 `hs_valid_platform()` 决定是否回退。旧资料里「只有 AC 一种实现」或「Hyperscan 必装」的说法都需对照实际版本核验。其二是注册接口的扩展：`src/detect-engine-mpm.h` 同时存在 `DetectAppLayerMpmRegister`、`DetectAppLayerMpmRegisterSubState`、`DetectAppLayerMpmRegisterSingle`、`DetectAppLayerMpmMultiRegister`、`DetectAppLayerMpmMultiRegisterSubState`、`DetectPktMpmRegister`、`DetectFrameMpmRegister` 以及 `DetectAppLayerMpmRegisterByParentId`、`DetectPktMpmRegisterByParentId`、`DetectFrameMpmRegisterByParentId` 这类带 `parent_id` 的变体，还有 `DetectEngineFrameMpmRegister`；`DetectBufferMpmRegistry` 的联合体分成 `app_v2`、`pkt_v1`、`frame_v1` 三个版本化分支，是否还有更旧的 `app_v1` 需对照实际版本核验。其三是引擎种类：`PrefilterEngine` 与 `SigGroupHead` 里出现 `frame_engines`、`post_rule_match_engines`，`PrefilterEngineList` 出现 `frame_type`、`sub_state`、`run_always`、`pkt_hook`，`PrefilterEngine` 出现 `is_last_for_progress`，这些是较新的语义字段，取值与启用条件需对照实际版本核验。其四是缓存能力：`MpmConfig` 的 `cache_dir_path`、`cache_max_age_seconds`、`cache_stats`，`MpmTableElmt` 的 `CacheRuleset`、`CachePrune`、`CacheStatsInit`、`CacheStatsPrint`、`CacheStatsDeinit`，以及 `PatternDatabaseCache` 的一串 `hs_dbs_cache_*` 计数，对应较新的编译缓存与裁剪机制，旧版本是否具备需对照实际版本核验。

其五是条件编入字段：`SCHSPattern`、`SCHSCtx`、`SCHSThreadCtx`、`PatternDatabase`、`PatternDatabaseCache` 整族位于 `src/util-mpm-hs-core.h` 的 `#ifdef BUILD_HYPERSCAN` 内，`MpmTableElmt.RegisterUnittests` 受 `UNITTESTS` 控制，`SCACCtx.state_table_u16` 与 `state_table_u32` 按状态数二选一，`SIG_GROUP_HEAD_HAVEFILEMAGIC` 受 `HAVE_MAGIC` 控制，字段是否存在取决于构建变体，写字段表时要注明条件而非当作恒定成员。其六是内部结构迁移：`MpmCtx.ctx` 的真实布局完全收进 `.c`，`src/app-layer-parser.h` 那种「头文件只留前向声明」的 opaque 化思路在 MPM 侧表现为「头文件只留 `void *`」，跨版本更不稳定，代码里绝不能依赖其偏移。由此得到一条通用版本纪律：任何「结构叫什么」「字段是什么类型」「定义在哪个文件」「是否编入」的问题，最终都要回到 `upstream_src/suricata/suricata-main/src/` 用 Read、Grep 核实；凡 SPEC 第 0.1 节未列出或无法核实的文件一律不写进正文。字段含义与生命周期属于 05-05、05-06，机制见 06-06 至 06-08，模块归属见 07-04、07-05，参数见 04-01、04-02、04-06，四者不去重就会互相抄错。

### 7. 常见误用与调试

第一类是「把初始化期结构用到运行期」。`SigGroupHeadInitData` 只在编译期存活，`mpm_store`、`app_mpms`、`pkt_mpms`、`frame_mpms`、五条 `PrefilterEngineList` 登记链、`match_array` 这些字段在编译完成后随 `SigGroupHead.init` 失效；匹配期读的是 `SigGroupHead` 里的五个 `PrefilterEngine` 数组，`is_last` 与 `is_last_for_progress` 是遍历终止依据。反过来在注册期直接读 `SigGroupHead` 的引擎数组也会扑空，因为它尚未构建。判读顺序应是先看当前处于注册编译期还是检测运行期，再决定读哪套字段；这与 05-05 里 `SignatureInitData` 与 `sm_arrays` 的分界是同一条纪律，机制原理见 06-06、06-07。

第二类是把不透明句柄当固定布局。`MpmCtx.ctx`、`PrefilterEngine.pectx`、`PrefilterEngineList.pectx`、`MpmThreadCtx.ctx` 都是 `void *`，源码注释只说明「MPM 引擎可能是 MpmCtx，其他引擎是别的 ctx」，真实布局在 `src/util-mpm-ac.c`、`src/util-mpm-hs.c`、`src/util-mpm-hs-core.h` 里，且 Hyperscan 侧整族受 `BUILD_HYPERSCAN` 控制。把它强转成 `SCACCtx` 去读 `state_count`，或在未启用 Hyperscan 的构建里引用 `PatternDatabase.hs_db`，都会读到不存在的成员；正确做法是通过 `MpmTableElmt` 的 `InitCtx`、`AddPattern`、`Prepare`、`Search`、`DestroyCtx` 回调操作，绝不直接解引用。同理 `PrefilterEngine.cb` 与 `ctx` 都是联合体，读之前必须按引擎种类确认当前有效分支，把 `pkt.mask` 当成 `app.tx_min_progress` 用会取错字节，机制原理见 06-08。

第三类是选型与能力边界误用。`mpm_type` 与 `mpm_default_matcher` 是匹配器选择结果，Hyperscan 为可选加速，缺失或 `hs_valid_platform()` 校验不通过时回退 AC 等其他实现；把 `MPM_HS` 写成必需依赖、把 `MpmTableElmt` 里某个回调写成所有实现都具备，都违反能力边界。`MpmTableElmt.feature_flags` 声明该实现是否支持 depth、offset、endswith，忽略它直接登记带 `depth` 的模式会与实现能力不符；`MpmPattern.flags` 的 `MPM_PATTERN_FLAG_NOCASE`、`DEPTH`、`OFFSET`、`ENDSWITH` 与 `MPM_PATTERN_CTX_OWNS_ID` 各有语义，取值需对照实际版本核验，关键字参数见 04-06。`PrefilterRuleStore.rule_id_array_cnt` 由 `PMQ_RESET` 清零但数组不释放，`PrefilterAddSidsResize` 分配失败时会裁剪追加量，把 `cnt` 清零误当成 `PmqFree` 会造成重复释放或漏判候选，机制原理见 06-07。

第四类是越界与全册边界。05 册不展开 fast_pattern 选择、MPM 构建、签名分组编译、预过滤引擎注册与求值的机制流程，遇「怎么编译、怎么匹配」写「原理见 06-06」至「原理见 06-08」；不重列 `mpm-algo`、`configure` 选项与 `content` 修饰符全集，写「参数见 04-01」「参数见 04-02」「参数见 04-06」；目录归属写「模块见 07-04」「模块见 07-05」。同时守住全册边界：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙，内联阻断依靠 NFQUEUE 或 AF_PACKET 桥接 verdict；只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见；规则兼容 Snort 但有自有扩展，不能宣称百分之百兼容；Hyperscan 为可选加速、缺失回退 AC；`rust/` 与 Cargo 是构建的一部分；`suricata-update` 独立发版；多线程不等于必然线性提速。任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」。规则加载与引擎分析错误可用 `suricata -T`、`suricata.log` 与 `--build-info` 判读，命令参数见 04-07、返回码与错误速查见 04-08，诊断决策树见 08-03；`MpmStoreReportStats`、`PatternMatchDefaultMatcher`、`EngineAnalysisAddAllRulePatterns` 是本篇字段最接近的诊断入口，只点名不展开流程。

## 05-07 ThreadVars、TmModule 与线程/队列结构字段

### 1. 本篇定位与覆盖范围

本篇是 05 册「抓包与线程层」的逐字段权威源，逐项覆盖 `src/threadvars.h:58` 的 `ThreadVars`、`src/tm-modules.h:47` 的 `TmModule`、`src/tm-modules.h:88` 的 `OutputCtx`、`src/tm-threads.h:53` 的 `TmSlot`、`src/tm-queues.h:30` 的 `Tmq`、`src/packet-queue.h:34` 的 `PacketQueueNoLock` 与 `:49` 的 `PacketQueue`、`src/tm-queuehandlers.h:36` 的 `Tmqh`、`src/tmqh-packetpool.h:43` 的 `PktPool` 与 `:31` 的 `PktPoolLockedStack`，并点名 `src/tm-threads-common.h:33` 的 `TmmId`、`:80` 的 `TmEcode`、`:87` 的 `TVT_` 线程类型枚举、`src/runmodes.h:27` 的 `SCRunModes` 作为取值字典。回答的是「一个工作线程由哪些字段描述、线程模块怎么注册成函数指针表、slot 链与队列怎么绑定、包池三段结构各自装什么」这类问题。按 SPEC 第 4 节去重约定，本篇只讲字段含义、内存布局、生命周期与关联函数入口，禁止展开线程创建、slot 链装配、队列出入队、包池回收、runmode 下线程与队列绑定这些机制的状态机与调用链，遇「怎么跑起来」写「原理见 06-01」「原理见 06-13」；禁止重列 `af-packet.threads`、`threading.set-cpu-affinity`、`detect-thread-ratio` 等参数全集，写「参数见 04-03」；按目录归属写「模块见 07-06」「模块见 07-09」。

三个层次可以先一句话理清：`TmModule` 是一张纯函数指针表，描述「一类模块能做什么」；`TmSlot` 把某个 `TmModule` 的一次实例化挂进线程流水线，`ThreadVars.tm_slots` 就是这条 slot 链的链头；`ThreadVars` 是每线程变量容器，把 `pthread_t`、`tm_func`、进出队列、队列处理器、标志位、统计存储与柔性数组收在一起。队列侧 `Tmq` 是注册项、`PacketQueue` 与 `PacketQueueNoLock` 是实体、`Tmqh` 是入出队处理器表、`PktPool` 是包对象的池化设施。真实仓库根为 `upstream_src/suricata/suricata-main/`，本篇所有结构体名、成员类型、枚举取值与行号均对照该目录下 `src/threadvars.h`、`src/tm-threads.h`、`src/tm-threads-common.h`、`src/tm-modules.h`、`src/tm-queues.h`、`src/tm-queuehandlers.h`、`src/packet-queue.h`、`src/tmqh-packetpool.h`、`src/tmqh-packetpool.c`、`src/tmqh-simple.c`、`src/tmqh-flow.c`、`src/tm-threads.c` 与 `src/runmodes.h` 核验；`src/tm-threads.c` 是线程创建与 slot 装配的实现文件，本篇只引用其入口函数名，不展开实现。版本基准统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准但不写绝对值；凡字段名、类型、条件宏无充分把握者写「需对照实际版本核验」并给出上述可定位目录。

能力边界不得写反：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙；多线程运行模式分 workers、autofp、single（`src/runmodes.c`），流亲和、RSS / fanout 负载均衡与队列分配共同决定扩展性，不得把「加线程」写成必然线性提速；各抓包后端能力与环境要求差异大，DPDK 需独占网卡、大页与 EAL 参数，PF_RING 在当前 main 快照是否仍为受支持后端需对照 `configure.ac` 与 `src/source-*.c` 实际版本核验；EVE JSON 是主要输出；`rust/` 与 Cargo 是构建的一部分；加密载荷正文不可见；性能数字一律标注「需在目标机型实测」。本篇按 B 手册字典型七节展开，引用关系收束为（参数见 04-03 ｜ 原理见 06-13 ｜ 模块见 07-06）：线程与抓包参数见 04-03，流水线与 runmode 机制见 06-01、06-13，source 与 util 目录模块见 07-06、07-09。

### 3. 逐项详解

**`ThreadVars` 的身份、绑核与流水线字段**。`ThreadVars`（`src/threadvars.h:58`）是每线程变量容器，源码注释明确 `tm_func` 是「直接传给 `pthread_create()` 的流水线入口函数，因此参数和返回值都是 `void *`」，这解释了为什么签名不写成 `Packet *` 之类具体类型。`t` 是 `pthread_t` 句柄，`name[16]` 与 `printable_name` 分别记内部名与可读名，上限 `TM_THREAD_NAME_MAX` 定义在 `src/tm-threads.h:49`；`thread_setup_flags` 取 `THREAD_SET_AFFINITY`、`THREAD_SET_PRIORITY`、`THREAD_SET_AFFTYPE` 三个位，`cpu_affinity` 是 `uint16_t` 绑核 cpu 号、`thread_priority` 是 `int` 实时优先级，二者由 `TmThreadSetCPUAffinity`、`TmThreadSetThreadPriority`、`TmThreadSetupOptions` 使用，参数见 04-03。`type` 取 `TVT_PPT`、`TVT_MGMT`、`TVT_CMD`，`tmm_flags` 是本线程上所有 `TmModule::flags` 的并集，`cap_flags` 是能力要求，`inq_id` 与 `outq_id` 索引 `tmqh_table`，`id` 是 `TmThreadsRegisterThread` 分配的局部 id。`tm_slots` 是构成该线程流水线的 `TmSlot` 链头，`tm_flowworker` 是注入包的起点 slot，源码注释说明「若 flowworker 不在本线程可为 `NULL`」。这些字段绝大多数在创建期与装配期写入、运行期只读，只有 `flags` 例外。

**`ThreadVars` 的原子标志、队列与柔性数组**。`flags` 用 `SC_ATOMIC_DECLARE(uint32_t, flags)` 声明为原子量，`src/threadvars.h:36` 起定义 `THV_INIT_DONE`、`THV_PAUSE`、`THV_PAUSED`、`THV_KILL`、`THV_FAILED`、`THV_CLOSED`、`THV_DEINIT`、`THV_RUNNING_DONE`、`THV_REQ_FLOW_LOOP`、`THV_FLOW_LOOP`、`THV_CAPTURE_INJECT_PKT`、`THV_DEAD`、`THV_RUNNING` 共十三个 `BIT_U32` 位，配套读写入口是 `TmThreadsCheckFlag`、`TmThreadsSetFlag`、`TmThreadsUnsetFlag`、`TmThreadWaitForFlag`，把它们当普通 `uint32_t` 直接读写会破坏线程间可见性。队列字段分三组：`inq` 与 `outq` 是 `Tmq *` 注册项，`tmqh_in` 与 `tmqh_out` 是对应的入出队处理器函数指针，`outctx` 是出队处理器私有数据；`decode_pq` 是 `PacketQueueNoLock` 类型的隧道解码临时无锁队列，源码注释说明它存放「隧道处理产生的额外包，就在当前位置之后立即处理」；`stream_pq` 与 `stream_pq_local` 是流超时注入用的 `PacketQueue *`。尾部还有 `stats`（`StatsThreadContext` 私有计数存储）、`next`（全局线程链）、`ctrl_mutex` 与 `ctrl_cond`（管理线程用互斥与条件）、`flow_queue`、`break_loop`、`iface_name`，以及 `Storage storage[]` 柔性数组——柔性数组意味着 `ThreadVars` 的 `sizeof` 不含存储项，分配时必须按注册项数追加空间，字段偏移不跨版本假定，机制原理见 06-13、模块见 07-09。

**`TmModule` 的纯函数指针表**。`TmModule`（`src/tm-modules.h:47`）不含任何数据成员，是一张按生命周期排列的函数指针表：`name` 是模块名；`ThreadInit`、`ThreadExitPrintStats`、`ThreadDeinit` 管线程级初始化、退出统计与反初始化；`Func` 是包处理回调，`PktAcqLoop` 是抓包主循环，`PktAcqBreakLoop` 是终止抓包循环，`ThreadBusy` 返回「线程是否还有任务未完成所以不能杀」；`Management` 是管理线程回调；`Init` 与 `DeInit` 是全局级初始化与反初始化；`RegisterTests` 受 `UNITTESTS` 条件编入；`cap_flags` 与 `flags` 是两个 `uint8_t` 标志。全局 `tmm_modules[TMM_SIZE]` 定义在 `src/tm-modules.h:83`，`TmmId`（`src/tm-threads-common.h:33`）从 `TMM_FLOWWORKER`、`TMM_DECODENFQ`、`TMM_RECEIVEPCAP`、`TMM_RECEIVEAFP`、`TMM_RECEIVEDPDK`、`TMM_RECEIVENETMAP` 一直到 `TMM_UNIXMANAGER`、`TMM_DETECTLOADER`、`TMM_SIZE`，注释特别提醒「此处新增项也要加到 `tm-modules.c` 的 `TmModuleTmmIdToString`」；`TmEcode` 只有 `TM_ECODE_OK`、`TM_ECODE_FAILED`、`TM_ECODE_DONE` 三值。标志 `TM_FLAG_RECEIVE_TM`、`TM_FLAG_DECODE_TM`、`TM_FLAG_FLOWWORKER_TM`、`TM_FLAG_VERDICT_TM`、`TM_FLAG_MANAGEMENT_TM`、`TM_FLAG_COMMAND_TM` 与组合 `TM_FLAG_PACKET_ALL` 定义在 `src/tm-modules.h:31` 起。查询与运行入口是 `TmModuleGetByName`、`TmModuleGetById`、`TmModuleGetIDForTM`、`TmModuleRegister`、`TmModuleRunInit`、`TmModuleRunDeInit`，只点名，原理见 06-01、06-13。

**`TmSlot` 与 `OutputCtx` 的实例化表示**。`TmSlot`（`src/tm-threads.h:53`）把某个 `TmModule` 的一次实例化挂进流水线：首部是三选一联合体 `SlotFunc`、`PktAcqLoop`、`Management`，对应普通包处理槽、抓包槽与管理槽；`slot_next` 串 slot 链；`slot_data` 用 `SC_ATOMIC_DECLARE(void *, slot_data)` 声明为原子指针，源码里通过 `SC_ATOMIC_GET(s->slot_data)` 读取，属于运行期可变数据；`tm_flags` 是 `TmModule::flags` 的副本，`tm_id` 记对应模块 id，`SlotThreadInit`、`SlotThreadExitPrintStats`、`SlotThreadDeinit` 是槽级线程生命周期回调，`slot_initdata` 是 `const void *` 初始化数据。装配入口是 `TmSlotSetFuncAppend`，运行入口是 `TmThreadsSlotVarRun` 与 `TmThreadsSlotProcessPkt`，机制原理见 06-13。`OutputCtx`（`src/tm-modules.h:88`）虽定义在线程模块头文件里，却是「输出模块维护私有数据」的结构：`data` 是私有数据指针，`DeInit` 是释放回调，`submodules` 是 `TAILQ_HEAD(, OutputModule_)` 子模块链表头，逐字段展开与输出模块注册见 05-08。

**`Tmq`、`PacketQueue` 与 `PacketQueueNoLock` 的队列三件套**。`Tmq`（`src/tm-queues.h:30`）是队列注册项：`name`、`is_packet_pool`、`id`、`reader_cnt`、`writer_cnt`、`pq`、`TAILQ_ENTRY` 类型的 `next`，配套 `TmqCreateQueue`、`TmqGetQueueByName`、`TmqDebugList`、`TmqResetQueues`、`TmValidateQueueState`。`PacketQueueNoLock`（`src/packet-queue.h:34`）只有 `top`、`bot`、`len` 加受 `DBG_PERF` 控制的 `dbg_maxlen`；`PacketQueue`（`:49`）在前三个字段与 `dbg_maxlen` 之后追加 `SCMutex mutex_q` 与 `SCCondT cond_q`。两处源码注释都要求「除 `mutex_q`、`cond_q` 外保持相同布局」，且明确「加锁或触发条件变量是调用方的责任」——这意味着 `PacketEnqueue`、`PacketDequeue` 并不隐式加锁，`TmThreadsHandleInjectedPackets` 里能看到显式 `SCMutexLock(&pq->mutex_q)` 与 `SCMutexUnlock` 成对出现。出入队入口是 `PacketEnqueueNoLock`、`PacketEnqueue`、`PacketDequeueNoLock`、`PacketDequeue`，分配释放是 `PacketQueueAlloc`、`PacketQueueFree`，机制原理见 06-01、06-13，字段见 05-02（队列里承载的 `Packet`）。

**`Tmqh` 处理器表与三种队列处理器实现**。`Tmqh`（`src/tm-queuehandlers.h:36`）是入出队处理器表：`name`、`InHandler`、`InShutdownHandler`、`OutHandler`、`OutHandlerCtxSetup`、`OutHandlerCtxFree`、`RegisterTests`，全局 `tmqh_table[TMQH_SIZE]` 由 `TmqhSetup` 填充，`TMQH_NOT_SET`、`TMQH_SIMPLE`、`TMQH_PACKETPOOL`、`TMQH_FLOW`、`TMQH_SIZE` 是索引枚举，查询入口 `TmqhNameToID`、`TmqhGetQueueHandlerByName`、`TmqhGetQueueHandlerByID`。本快照里三份实现各有典型函数：`src/tmqh-simple.c` 有 `TmqhSimpleRegister`、`TmqhInputSimple`、`TmqhInputSimpleShutdownHandler`、`TmqhOutputSimple`；`src/tmqh-packetpool.c` 有 `TmqhPacketpoolRegister`、`TmqhInputPacketpool`、`TmqhOutputPacketpool`、`TmqhReleasePacketsToPacketPool` 与 `PacketPoolGetPacket`、`PacketPoolWait`、`PacketPoolReturnPacket`、`PacketPoolInit`、`PacketPoolDestroy`、`PacketPoolPostRunmodes`；`src/tmqh-flow.c` 有 `TmqhFlowRegister`、`TmqhInputFlow`、`TmqhOutputFlowHash`、`TmqhOutputFlowIPPair`、`TmqhOutputFlowFTPHash`、`TmqhOutputFlowFreeCtx`、`StoreQueueId`、`TmqhFlowPrintAutofpHandler` 与 `TmqhFlowCtx`。这些函数只点名，autofp 下队列绑定原理见 06-13，模块见 07-06、07-09。

**`PktPool` 与 `PktPoolLockedStack` 的池化字段**。`PktPool`（`src/tmqh-packetpool.h:43`）分三段：`head` 与 `cnt` 是本线程本地空闲包链头与计数，源码注释说明「无锁，因为只有本线程访问」；`pending_pool`、`pending_head`、`pending_tail`、`pending_count` 是「等待归还到某个池」的累积区，注释说明攒到阈值后整链一次性推上归还栈，`head` 与 `tail` 是为了快速插入整条链；`initialized` 与 `destroyed` 受 `DEBUG_VALIDATION` 控制；`return_stack` 是跨线程归还栈。源码在 `return_stack` 之前有一段关键注释：「以上成员只被单一线程本地访问，应独占一条缓存行」，`PktPoolLockedStack`（`:31`）本身带 `__attribute__((aligned(CLS)))`，含 `SCMutex mutex`、`SCCondT cond`、`SC_ATOMIC_DECLARE(uint32_t, return_threshold)`、`uint32_t cnt`、`Packet *head`，其中 `return_threshold` 由池主按池满程度调整、用于触发归还同步。这种布局决定了 `PktPool` 的字节大小与成员偏移强依赖构建平台的缓存行大小，须在目标机型实测，不给绝对值。字段见 05-02（`Packet` 本体）、05-09（通用 `Pool`），机制原理见 06-13，模块见 07-09。

### 6. 版本差异

本套资料统一以「上游 main 快照（2026-11 抓取）」为版本基准，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当版本号；需要说明版本来源时写「具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验」。线程与队列结构随 runmode、抓包后端与伪包注入机制演进明显：模块 id 会新增、线程标志位会追加、队列处理器会扩展、包池会引入新的归还策略，因此第 2 节与第 3 节给出的行号与字段清单是这份快照的事实，不是跨版本永久承诺。

几处已能在本快照里观察到的差异点值得单列。其一是定义所在文件：`PacketQueue` 与 `PacketQueueNoLock` 在本快照定义于 `src/packet-queue.h`，`src/tm-queues.h` 只提供 `Tmq` 注册结构；`OutputCtx` 定义在 `src/tm-modules.h:88` 而非输出头文件；`TmSlot` 定义在 `src/tm-threads.h:53` 而非 `src/tm-modules.h`。旧资料把这些结构归到别的文件或合并成一个的说法需对照实际版本核验，按本快照 grep 到的真实行号为准。其二是模块 id 枚举：`TmmId` 里能看到 `TMM_RECEIVEAFXDP`、`TMM_RECEIVEDPDK`、`TMM_RECEIVENETMAP`、`TMM_DECODEAFP`、`TMM_DECODEAFXDP`、`TMM_DECODEDPDK`、`TMM_RECEIVEWINDIVERT` 等较新后端，以及 `TMM_BYPASSEDFLOWMANAGER`、`TMM_DETECTLOADER`、`TMM_UNIXMANAGER` 等管理类模块，注释还要求新增项同步到 `TmModuleTmmIdToString`；PF_RING 相关模块在本枚举里未出现，其支持状态需对照 `configure.ac` 与 `src/source-*.c` 实际版本核验，不得编造 `source-pfring.c`。其三是线程标志位：`THV_REQ_FLOW_LOOP`、`THV_FLOW_LOOP`、`THV_CAPTURE_INJECT_PKT`、`THV_RUNNING_DONE`、`THV_DEAD` 等对应流超时循环、伪包注入与关停阶段，是较新的控制语义，位定义需对照实际版本核验。

其四是队列处理器分工：`tmqh-simple.c`、`tmqh-packetpool.c`、`tmqh-flow.c` 三份实现并存，`Tmqh` 里出现 `InShutdownHandler`、`OutHandlerCtxSetup`、`OutHandlerCtxFree` 这类较新回调，`Tmq` 里出现 `is_packet_pool` 布尔，旧版本是否具备需对照实际版本核验。其五是条件编入字段：`PacketQueue.dbg_maxlen` 与 `PacketQueueNoLock.dbg_maxlen` 受 `DBG_PERF` 控制，`PktPool.initialized`、`PktPool.destroyed` 受 `DEBUG_VALIDATION` 控制，`TmModule.RegisterTests` 受 `UNITTESTS` 控制，`ThreadVars.user_name` 一类字段在 `SCInstance` 里受 `OS_WIN32` 控制，字段是否存在取决于构建变体与平台，写字段表时要注明条件而非当作恒定成员。其六是缓存行对齐：`PktPool` 的注释明确「以上成员只被单一线程本地访问，应独占一条缓存行」，`PktPoolLockedStack` 带 `aligned(CLS)`，这类布局随目标机型缓存行大小变化，字节大小与偏移一律需在目标机型实测。

### 7. 常见误用与调试

第一类是「把有锁队列当无锁队列用，或反之」。`PacketQueue` 带 `mutex_q` 与 `cond_q`，但 `src/packet-queue.h:44` 起的源码注释明确「加锁或触发条件变量是调用方的责任」，`PacketEnqueue`、`PacketDequeue` 并不隐式加锁；`PacketQueueNoLock` 没有锁字段，只能用在确定单线程访问的场合，例如 `ThreadVars.decode_pq` 这种隧道解码临时队列。把 `PacketQueue` 直接交给无锁路径会造成并发错乱，把 `PacketQueueNoLock` 交给多线程路径会丢包。`TmThreadsHandleInjectedPackets` 里能看到 `SCMutexLock(&pq->mutex_q)` 与 `SCMutexUnlock` 成对出现，`TmThreadsCaptureHandleTimeout` 还会检查 `flow_queue->non_empty` 原子量再决定是否注入伪包，这些是判读加锁责任的最直接依据，机制原理见 06-13。

第二类是把原子量或柔性数组当普通字段。`ThreadVars.flags` 用 `SC_ATOMIC_DECLARE(uint32_t, flags)` 声明，`TmSlot.slot_data` 用 `SC_ATOMIC_DECLARE(void *, slot_data)` 声明，跨线程读写必须走 `TmThreadsSetFlag`、`TmThreadsUnsetFlag`、`TmThreadsCheckFlag` 与 `SC_ATOMIC_GET`；直接对 `flags` 做位或会丢掉可见性保证，进而影响 `THV_KILL`、`THV_PAUSE`、`THV_FAILED` 的关停判定。`ThreadVars.storage[]` 是柔性数组，`sizeof(ThreadVars)` 不含存储项，把它按定长结构 `memcpy` 会截断存储区；`PktPool` 的 `return_stack` 带 `aligned(CLS)`，把 `PktPool` 当成紧凑结构算偏移同样会读错，字节大小需在目标机型实测。

第三类是模块与槽的联合体误读。`TmSlot` 首部是 `SlotFunc`、`PktAcqLoop`、`Management` 三选一联合体，`PrefilterEngine` 之外的另一处联合体在 `PrefilterEngine.ctx`；读 `TmSlot` 回调前必须按 `tm_flags` 与 `tm_id` 确认当前槽属于包处理、抓包还是管理槽，把 `Management` 当 `SlotFunc` 调用会因签名不同而崩。`TmModule.ThreadBusy` 返回的是「是否还有任务未完成」，把 `TM_ECODE_DONE` 与 `TM_ECODE_FAILED` 混为一谈会误判关停时机；`tmm_modules[TMM_SIZE]` 按 `TmmId` 索引，`TmSlot.tm_id` 与 `TmModuleGetById` 必须配套使用，下标与枚举值混用会取到别的模块。模块 id 与返回码取值需对照实际版本核验，原理见 06-01、06-13。

第四类是越界与能力边界。05 册不展开线程创建、slot 装配、队列出入队、包池回收与 runmode 绑定的机制流程，遇「怎么跑起来」写「原理见 06-01」「原理见 06-13」；不重列 `af-packet.threads`、`threading.set-cpu-affinity`、`detect-thread-ratio` 等参数全集，写「参数见 04-03」；目录归属写「模块见 07-06」「模块见 07-09」。同时守住全册边界：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙；多线程不等于加线程必然线性提速，流亲和与 RSS / fanout 负载均衡共同决定扩展性；各抓包后端能力与环境要求差异大，DPDK 需独占网卡、大页与 EAL 参数，PF_RING 支持状态需对照实际版本核验；只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见；EVE JSON 是主要输出；`rust/` 与 Cargo 是构建的一部分；`suricata-update` 独立发版。任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」。线程状态异常可用 `suricata.log`、`stats.log` 与 `suricatasc` 的 `dump-counters`、`iface-stat` 判读，命令参数见 04-07、返回码与错误速查见 04-08，诊断决策树见 08-03，`TmThreadsListThreads`、`TmThreadGetNbThreads`、`TmThreadCountThreadsByTmmFlags` 是本篇字段最接近的排错入口，只点名不展开流程。

按 SPEC 第 4 节去重约定，本篇只讲字段含义、内存布局、生命周期与关联函数入口，禁止展开输出模块注册、EVE 事件构造与聚合、日志轮转触发、stats 汇总这些机制的状态机与调用链，遇「怎么输出、怎么轮转」一律写「原理见 06-11」；禁止重列 `outputs` 下 `eve-log`、`fast`、`stats`、`lua`、`pcap-log` 的全部键与 `types` 子项，写「参数见 04-04」；按目录归属写「模块见 07-07」。有一类结构必须按不透明句柄处理：`SCJsonBuilder` 在 `src/output-eve.h:40` 只在 `SURICATA_BINDGEN_H` 条件下留一句 `typedef struct SCJsonBuilder SCJsonBuilder;`，真实布局在 `rust/src/jsonbuilder.rs:107` 的 `pub struct JsonBuilder`（带 `#[repr(C)]`），配套 `JsonError`（`:33`）、`JsonBuilderMark`（`:100`）与常量 `INIT_SIZE`（`:30`）；`OutputCtx.data`、`OutputModule` 里若干 `void *` 私有数据、`LogFileCtx` 的 `redis` 与 `init_data`、`thread_data` 同理，本篇一律写明「不透明句柄，内部布局见 xxx」，只登记句柄本身与可见元字段，不虚构内部成员。事实锚点仍为 `upstream_src/suricata/suricata-main/`，本篇结构体名、成员类型、枚举取值与行号均对照该目录下 `src/output.h`、`src/output.c`、`src/output-json.h`、`src/output-json.c`、`src/output-stats.h`、`src/output-eve.h`、`src/util-logopenfile.h`、`src/log-stats.c`、`src/log-pcap.c`、`src/log-tlsstore.c`、`src/log-tcp-data.c`、`src/log-maintenance.c` 与 `rust/src/jsonbuilder.rs` 核验；版本基准统一写「上游 main 快照（2026-11 抓取）」，具体版本号以 `configure.ac`、`ChangeLog` 为准但不写绝对值；凡字段名、类型宽度、条件宏无充分把握者写「需对照实际版本核验」并给出上述可定位目录。

能力边界不得写反。Suricata 是 IDS / IPS / NSM 引擎，不做 IP 转发、不做路由、不是防火墙，内联阻断依靠 NFQUEUE 或 AF_PACKET 桥接的 verdict，IDS 旁路只告警不丢弃；EVE JSON 是主要输出，fast.log、stats.log、pcap-log 等为辅助输出，不得把某一种辅助日志写成主输出；只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见，EVE 的 tls 事件拿到的是握手元数据、证书、SNI、JA3 / JA4 一类信息；规则语法兼容 Snort 但有自有扩展，不能宣称百分之百兼容；Hyperscan 是可选 MPM 加速、缺失回退 AC 等其他实现；`rust/` 与 Cargo 是构建的一部分，大量应用层解析器与 EVE 构造在 Rust 侧，不得把 Suricata 写成纯 C 项目；`suricata-update` 是分仓独立工具；多线程不等于加线程必然线性提速。任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」。本篇按 B 手册字典型七节展开，交叉引用统一收束为（参数见 04-04 ｜ 原理见 06-11 ｜ 模块见 07-07）：输出与日志配置参数见 04-04，EVE 与日志管线机制见 06-11，output 与 log 目录模块见 07-07，Rust JSON 构造见 07-10。

### 3. 逐项详解

**`OutputModule` 的身份与回调字段**。`OutputModule`（`src/output.h:56`）是输出模块注册表里的一个节点，字段可分四组。身份组是 `logger_id`（`LoggerId`）、`name`、`conf_name`、`parent_name`，其中 `conf_name` 用于按 `suricata.yaml` 的段名匹配，`parent_name` 只在子模块注册时有意义，`OutputGetModuleByConfName` 按配置名反查。初始化组是 `OutputInitFunc InitFunc` 与 `OutputInitSubFunc InitSubFunc`，返回 `OutputInitResult`；`ThreadInit` 与 `ThreadDeinit` 是线程级回调，类型来自 `src/tm-modules.h:43` 的 `ThreadInitFunc`、`ThreadDeinitFunc`、`ThreadExitPrintStatsFunc`。回调组最庞大：`PacketLogFunc`、`PacketConditionFunc`、`TxLogFunc`、`TxLogCondition`、`FileLogFunc`、`FiledataLogFunc`、`FlowLogFunc`、`StreamingLogFunc`、`StatsLogFunc` 分别对应包、事务、文件、文件数据、流、流式与统计日志，类型定义散落在 `src/output-packet.h`、`src/output-tx.h`、`src/output-file.h`、`src/output-filedata.h`、`src/output-flow.h`、`src/output-streaming.h`、`src/output-stats.h`，这些头文件由 `src/output.h:38` 至 `:44` 统一包含。限定组是 `alproto`、`sub_state`、`stream_type`（`enum SCOutputStreamingType`）、`tc_log_progress` 与 `ts_log_progress` 两个方向的事务进度，尾部 `entries` 是 `TAILQ_ENTRY` 链表节点。全局 `output_modules` 是 `OutputModuleList`（`TAILQ_HEAD`），注册入口 `OutputRegisterModule`、`OutputRegisterPacketModule`、`OutputRegisterPacketSubModule`、`OutputRegisterTxModule`、`OutputRegisterTxSubModule`、`OutputRegisterTxModuleWithCondition`、`OutputRegisterTxModuleWithProgress`、`OutputRegisterTxSubModuleWithProgressSubState`、`OutputRegisterFileSubModule`、`OutputRegisterFiledataModule`、`OutputRegisterFlowSubModule`、`OutputRegisterStreamingModule`、`OutputRegisterStatsModule`、`OutputRegisterStatsSubModule` 只点名，机制原理见 06-11、参数见 04-04、模块见 07-07。

**`OutputInitResult`、`OutputCtx` 与线程存储的衔接关系**。`OutputInitResult`（`src/output.h:46`）只有 `OutputCtx *ctx` 与 `bool ok` 两个字段，是所有 `OutputInitFunc` 的统一返回类型；`ok` 为假时注册流程短路，`ctx` 指向 05-07 已登记的 `OutputCtx`（`src/tm-modules.h:88`），其 `data` 是 `void *` 私有数据、`DeInit` 是释放回调、`submodules` 是 `TAILQ_HEAD(, OutputModule_)` 子模块链表头。这里要特别注意：`OutputCtx.data` 是不透明句柄，真实布局由各输出模块自己定义，例如 EVE 侧就是 `OutputJsonCtx`，本篇在 05-08 登记该具体类型，但跨模块代码只能用初始化时约定的强转，不得把 `void *` 当固定结构。`OutputLoggerThreadStore`（`src/output.h:33`）的 `thread_data` 与 `next` 是每线程私有数据的链表节点，`OutputPacketLoggerFunctions`（`:86`）把 `LogFunc`、`ConditionFunc`、`ThreadInitFunc`、`ThreadDeinitFunc`、`ThreadExitPrintStatsFunc` 打包成注册参数，避免注册函数参数过长。三者都是「初始化结果」「私有数据容器」「注册参数包」这类辅助结构，字段少但贯穿所有输出模块，读写时机集中在初始化期与线程初始化期。

**`LogFileCtx` 的句柄、函数指针与轮转字段**。`LogFileCtx`（`src/util-logopenfile.h:85`）是输出层的落盘总对象。首部是联合体：`FILE *fp` 与受 `HAVE_LIBHIREDIS` 控制的 `void *redis` 二选一；`threads` 指向 `LogThreadedFileCtx *`；再一个联合体装 `RedisSetup redis_setup`（同样受 `HAVE_LIBHIREDIS` 控制）。紧接着是四个函数指针 `Write`、`Close`、`Flush`、`Rotate`，源码注释说明它们构成「文件类接口」，`LogFileWrite`、`LogFileFlush`、`LogFileFlushAll`、`LogFileRotateAll` 是外部入口；`filetype` 是 `LogFileTypeCtx`，其 `filetype` 是 `SCEveFileType *`、`init_data` 与 `thread_data` 是两级私有数据。`fp_mutex` 的注释写明「当一条日志或告警记录无法一次写完时加锁」，`threaded`、`parent`、`entry` 处理线程化输出下的父子关系与每线程哈希项，`ThreadLogFileHashEntry`（`:48`）含 `ctx`、`thread_id`、`internal_thread_id`、`slot_number`、`isopen`。`type` 取 `enum LogFileType`，`filename`、`filemode`、`buffer_size`、`sensor_name` 是配置期写入的文件属性；`is_sock`、`sock_type`、`reconn_timer` 处理 unix 域套接字或 Redis 的自动重连，`LOGFILE_RECONN_MIN_TIME` 常量为 500 毫秒，`LOGFILE_EVE_BUFFER_SIZE` 默认 0。轮转组是 `rotate_time`、`rotate_interval`、`rotate_unit`、`rotate_period` 与 `prefix`、`prefix_len`，`rotate_unit` 取 `enum LogFileRotateUnit` 的五种取值，`rotation_flag` 由 `OutputNotifyFileRotation` 设置，配合 `OutputRegisterFileRotationFlag`、`OutputUnregisterFileRotationFlag` 使用；`size_limit` 与 `size_current` 的源码注释强调「必须被访问同一文件的所有线程共享」；`dropped` 与 `output_errors` 记套接字为避免阻塞而丢弃的事件数与写出错误数，`bytes_since_last_flush` 记缓冲累计。`flags`、`send_flags`、`is_regular`、`compress_ipv6`、`json_flags`、`is_pcap_offline` 是一组开关与标志。上述所有计数类字段的具体量级需在目标机型实测，不给绝对值。

**`OutputJsonCtx` 与 `OutputJsonThreadCtx` 的两级上下文**。`OutputJsonCtx`（`src/output-json.h:77`）的注释写明它是「全局配置上下文数据」：`file_ctx` 回指 `LogFileCtx`，`json_out` 是 `enum LogFileType` 输出目标，`cfg` 是 `OutputJsonCommonSettings`，`xff_cfg` 是 `HttpXFFCfg *`，`filetype` 是 `SCEveFileType *`。`OutputJsonCommonSettings`（`:62`）六个字段全是配置开关：`include_metadata`、`include_community_id`、`include_ethernet`、`compress_ipv6`、`include_suricata_version` 五个 `bool` 加 `uint16_t community_id_seed`，分别由 `EveAddMetadata`、`EveAddCommonOptions`、`JsonAddrInfoInit` 一类函数消费，参数见 04-04。`OutputJsonThreadCtx`（`:85`）是每线程上下文：`ctx` 回指全局上下文、`file_ctx` 是线程侧文件上下文、`buffer` 是 `MemBuffer *`、`too_large_warning` 用于避免超长记录重复告警，构造与释放入口 `CreateEveThreadCtx`、`FreeEveThreadCtx`，线程初始化入口 `JsonLogThreadInit`、`JsonLogThreadDeinit`。`JsonAddrInfo`（`:41`）是把包地址渲染成 JSON 的辅助结构：`src_ip[JSON_ADDR_LEN]`、`dst_ip[JSON_ADDR_LEN]`、`Port sp`、`Port dp`、`char proto[JSON_PROTO_LEN]`、`bool log_port`，源码注释说明「只有传输层提供了端口才记录端口」；全局常量 `json_addr_info_zero` 供零初始化。`OutputJSONMemBufferWrapper`（`:57`）含 `MemBuffer **buffer` 与 `uint32_t expand_by`，是 `OutputJSONMemBufferCallback` 的可扩容缓冲包装。EVE 侧函数族 `OutputJsonRegister`、`OutputJsonInitCtx`、`OutputJsonLogInitSub`、`OutputJSONBuffer`、`OutputJsonBuilderBuffer`、`CreateEveHeader`、`CreateEveHeaderWithTxId`、`CreateEveFlowId`、`EvePacket`、`EveTcpFlags`、`EveFileInfo`、`EveAddCommonOptions`、`EveAddMetadata`、`SCJsonString` 只点名，机制原理见 06-11。

**`SCJsonBuilder` 的不透明边界与 Rust 侧布局**。`src/output-eve.h:40` 在 `SURICATA_BINDGEN_H` 条件下只写 `typedef struct SCJsonBuilder SCJsonBuilder;`，同时把 `ThreadVars_`、`Flow_`、`Packet_` 也做前向声明；这意味着 C 侧拿到的 `SCJsonBuilder *` 是不透明句柄，真实布局在 `rust/src/jsonbuilder.rs`。该 Rust 文件 `:30` 定义 `INIT_SIZE: usize = 4096`，`:33` 定义 `pub enum JsonError`（`InvalidState`、`Utf8Error`、`Memory`），`:64` 定义内部 `enum Type`（`Object`、`Array`），`:100` 定义 `#[repr(C)] pub struct JsonBuilderMark`，`:107` 定义 `#[repr(C)] pub struct JsonBuilder`。`SCEveUserCallbackFn`（`:240`）与 `SCEveRegisterCallback`、`SCEveRunCallbacks`（`:261`、`:267`）说明回调在「根对象关闭前」拿到 `SCJsonBuilder *`，可以追加字段但不能修改已有对象，且源码注释明确「当前只对使用 SCJsonBuilder 的 EVE 日志器生效，stats 记录不走这条路」。本篇对该类型一律写明「不透明句柄，内部布局见 `rust/src/jsonbuilder.rs`」，禁止虚构字段；`rust/` 与 Cargo 是构建的一部分，Rust JSON 构造的模块归属见 07-10。

**stats 与 EVE filetype 结构**。`StatsRecord`（`src/output-stats.h:31`）五字段中 `value` 与 `pvalue` 都是 `int64_t`，源码注释特意说明 `pvalue` 对 memuse 类计数器可能反而更大，不能假定单调；`StatsTable`（`:39`）的 `stats` 是全局数组、`tstats` 是「数组的数组」式每线程统计，`nstats` 与 `ntstats` 分别是记录数与线程数，`start_time` 与 `ts` 供 `src/log-stats.c:67` 的 `LogStatsLogger` 计算 uptime。`LogStatsFileCtx`（`src/log-stats.c:57`）含 `LogFileCtx *file_ctx` 与 `uint32_t flags`，后者取 `LOG_STATS_TOTALS`、`LOG_STATS_THREADS`、`LOG_STATS_NULLS` 三个位；`LogStatsLogThread`（`:62`）含 `LogStatsFileCtx *statslog_ctx` 与 `MemBuffer *buffer`；常量 `DEFAULT_LOG_FILENAME` 为 `"stats.log"`、`OUTPUT_BUFFER_SIZE` 为 16384。`SCEveFileType`（`src/output-eve.h:125`）的注释把生命周期写成五个阶段：`Init`、`ThreadInit`、`Write`、`ThreadDeinit`、`Deinit`，对应五个函数指针类型 `SCEveFileTypeInitFunc`、`SCEveFileTypeThreadInitFunc`、`SCEveFileTypeWriteFunc`、`SCEveFileTypeThreadDeinitFunc`、`SCEveFileTypeDeinitFunc`（`:75` 起），加 `name` 与 `entries`；注释还说明 threaded 模式下 `ThreadInit` 会被多次调用、filetype 需自行保证线程安全，内置 syslog 与 nullsink 见 `src/output-eve-syslog.c`、`src/output-eve-null.c`。`enum SCOutputJsonLogDirection`（`:48`）四值 `LOG_DIR_PACKET`、`LOG_DIR_FLOW`、`LOG_DIR_FLOW_TOCLIENT`、`LOG_DIR_FLOW_TOSERVER` 是 `JsonAddrInfoInit`、`CreateEveHeader` 的方向参数，`ThreadId` 在 `:46` 定义为 `uint32_t`。交叉引用统一为（参数见 04-04 ｜ 原理见 06-11 ｜ 模块见 07-07）：输出与日志参数见 04-04，EVE 与日志管线机制见 06-11，output 与 log 目录模块见 07-07，Rust JSON 构造见 07-10。

### 7. 常见误用与调试

第一类是「把不透明句柄当固定结构」。`OutputCtx.data`、`OutputLoggerThreadStore.thread_data`、`LogFileTypeCtx.init_data` 与 `thread_data`、`LogFileCtx.redis`、`OutputJsonCtx.filetype` 都是私有数据或不透明句柄，真实布局由各输出模块或各 filetype 自己定义；把 `OutputCtx.data` 直接当 `OutputJsonCtx` 解引用、在未启用 `HAVE_LIBHIREDIS` 的构建里访问 `redis` 与 `redis_setup`，都会读到不存在的成员。最典型的是 `SCJsonBuilder`：C 侧只有 `src/output-eve.h:40` 的前向声明，真实布局在 `rust/src/jsonbuilder.rs:107`，跨模块代码只能用 `CreateEveHeader`、`EveAddCommonOptions`、`SCEveRunCallbacks` 一类接口操作，绝不能直接取成员；回调注释还限定「只能追加字段、不能修改已有对象」，越界修改会破坏 JSON 结构，机制原理见 06-11。

第二类是把联合体和条件字段用错。`LogFileCtx.fp` 与 `redis` 是联合体二选一，`OutputJsonCtx.json_out` 的 `enum LogFileType` 决定当前走哪条写出路径；`LogFileCtx.is_regular` 明确「只有常规文件允许轮转」，对 unix 套接字或 Redis 输出误触发 `Rotate` 会写错目标。`LogFileCtx.Write`、`Close`、`Flush`、`Rotate` 是四个函数指针而非普通函数，未初始化的 filetype 直接调用会崩；`OutputModule` 里八类日志回调并非每个模块都全部实现，按 `logger_id` 与 `conf_name` 判断当前有效回调，把 `StatsLogFunc` 当 `PacketLogFunc` 调用会因签名不同而错乱。`src/util-logopenfile.h:32` 的 `HAVE_LIBHIREDIS` 与 `src/output-eve.h` 的 `SURICATA_BINDGEN_H` 是判定条件编入的关键宏，参数见 04-04。

第三类是计数与生命周期误用。`StatsRecord.value` 与 `pvalue` 都是 `int64_t`，源码注释特意提醒 `pvalue` 对 memuse 类计数器可能反而更大，按「本轮减上轮必为正」写统计会溢出或误判；`StatsTable.nstats` 与 `ntstats` 分别是全局数组记录数与线程数，把两者混用会越界访问 `tstats`。`LogFileCtx.size_limit` 与 `size_current`、`dropped`、`output_errors`、`bytes_since_last_flush` 都是运行期累加量，源码注释强调 `size_limit`、`size_current` 必须被访问同一文件的所有线程共享，忽略 `fp_mutex` 直接读写会丢计数。`rotation_flag` 由 `OutputNotifyFileRotation` 设置，`too_large_warning` 用于抑制重复告警，把这两个标志当成持久状态会导致轮转与告警失效；所有写出量、缓冲占用与丢弃计数结论标注「需在目标机型实测」。

第四类是越界与能力边界。05 册不展开输出模块注册、EVE 事件构造与聚合、日志轮转触发、stats 汇总的机制流程，遇「怎么输出」写「原理见 06-11」；不重列 `outputs` 下各日志段与 `types` 子项，写「参数见 04-04」；目录归属写「模块见 07-07」，Rust JSON 构造见 07-10。同时守住全册边界：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙，IDS 旁路只告警不丢弃、IPS 内联阻断依靠 NFQUEUE 或 AF_PACKET 桥接 verdict；EVE JSON 是主要输出，fast.log、stats.log、pcap-log 为辅助输出；只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见，tls 事件只含握手元数据、证书、SNI、JA3 / JA4 一类信息；规则兼容 Snort 但有自有扩展，不能宣称百分之百兼容；Hyperscan 为可选加速、缺失回退 AC；`rust/` 与 Cargo 是构建的一部分；`suricata-update` 独立发版；多线程不等于必然线性提速。任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」。输出异常可用 `suricata.log`、`stats.log`、`eve.json` 与 `suricatasc` 的 `reopen-log-files`、`dump-counters` 判读，命令参数见 04-07、返回码与错误速查见 04-08，诊断决策树见 08-03；`OutputSetupActiveLoggers`、`OutputClearActiveLoggers`、`OutputDeregisterAll`、`LogFileFlushAll`、`LogFileRotateAll`、`OutputStatsLoggersRegistered` 是本篇字段最接近的排错入口，只点名不展开流程。

能力边界贯穿全册且不得写反。Suricata 是 IDS / IPS / NSM 引擎，不做 IP 转发、不做路由、不是防火墙，内联阻断依靠 NFQUEUE 或 AF_PACKET 桥接的 verdict；只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见；规则语法兼容 Snort 但有自有扩展，不能宣称百分之百兼容；EVE JSON 是主要输出；Hyperscan 是可选 MPM 加速、缺失回退 AC 等其他实现；`rust/` 与 Cargo 是构建的一部分；`suricata-update` 是分仓独立工具；多线程运行模式分 workers、autofp、single，不等于加线程必然线性提速。任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」。不透明句柄方面，`Host.iprep` 是 `void *`，`Pool.data_buffer`、`pb_buffer`、`PoolBucket.data` 与 `PoolThreadReserved` 约定都属于「消费者只按约定使用、不得探查内部」的范畴；`unix-command` 上下文在本快照由 `SCInstance.unix_socket_enabled` 等字段体现，完整实现见 `src/runmode-unix-socket.c`（路径需对照实际版本核验），本篇不虚构其成员。本篇按 B 手册字典型七节展开，引用关系收束为（参数见 04-02 ｜ 原理见 06-13 ｜ 模块见 07-09）：yaml 全局段参数见 04-02、命令行与 RPC 参数见 04-07，流水线与 runmode 机制见 06-01、06-13，util 与 conf 目录模块见 07-09，控制面见 07-12。

### 3. 逐项详解

**`SCConfNode` 的配置树节点字段**。`SCConfNode`（`src/conf.h:37`）只有七个字段，却撑起整棵配置树：`name` 与 `val` 是 `char *` 的键与值，`is_seq` 标记该节点是否为序列（yaml 里的列表），`final` 是源码注释说明「把本节点的值设为 final」的不可覆盖标志，`parent` 回指父节点，`head` 是 `TAILQ_HEAD(, SCConfNode_)` 子节点链表头，`next` 是 `TAILQ_ENTRY(SCConfNode_)` 兄弟链表节点。注意值是字符串而非 typed union，所有整型、布尔、浮点、时间都由读取函数现场转换，这正是 `SCConfGetInt`、`SCConfGetBool`、`SCConfGetDouble`、`SCConfGetFloat`、`SCConfGetTime` 存在的原因；`SCConfGetChildValue` 系列在这些之上加「从指定基节点按子键取值」，`SCConfGetChildValueWithDefault` 系列再加缺省回退，`SCConfGetChildWithDefault`、`SCConfNodeLookupChild`、`SCConfNodeLookupChildValue`、`SCConfNodeLookupKeyValue`、`SCConfNodeHasChildren`、`SCConfNodeIsSequence`、`SCConfNodeChildValueIsTrue` / `False`、`SCConfValIsTrue` / `False` 构成完整的查询族。写侧有 `SCConfSet`、`SCConfSetFromString`、`SCConfSetFinal`、`SCConfRemove`、`SCConfNodeNew`、`SCConfNodeFree`、`SCConfNodeRemove`、`SCConfNodePrune`、`SCConfNodeGetNodeOrCreate`、`SCConfSetIfaceNode`、`SCConfSetRootAndDefaultNodes`，生命周期有 `SCConfInit`、`SCConfDeInit`、`SCConfGetRootNode`、`SCConfCreateContextBackup`、`SCConfRestoreContextBackup`、`SCConfDump`、`SCConfNodeDump`。这些函数只点名，配置加载链路原理见 06-01，模块见 07-09，参数见 04-02。

**`SCInstance` 的运行模式与规则文件字段**。`SCInstance`（`src/suricata.h:134`）是进程启动姿态的集中记录。前两项 `run_mode` 与 `aux_run_mode` 都是 `enum SCRunModes`，`SCRunmodeGet`、`SCRunmodeSet` 是读写入口，`src/runmodes.h:27` 的枚举从 `RUNMODE_UNKNOWN`、`RUNMODE_PCAP_DEV`、`RUNMODE_PCAP_FILE`、`RUNMODE_NFQ`、`RUNMODE_NFLOG`、`RUNMODE_IPFW`、`RUNMODE_ERF_FILE`、`RUNMODE_DAG`、`RUNMODE_AFP_DEV`、`RUNMODE_AFXDP_DEV`、`RUNMODE_NETMAP`、`RUNMODE_DPDK`、`RUNMODE_LIB`、`RUNMODE_UNITTEST`、`RUNMODE_UNIX_SOCKET`、`RUNMODE_WINDIVERT`、`RUNMODE_PLUGIN`、`RUNMODE_USER_MAX` 一路列到 `RUNMODE_LIST_KEYWORDS`、`RUNMODE_DUMP_CONFIG`、`RUNMODE_CONF_TEST`、`RUNMODE_ENGINE_ANALYSIS`、`RUNMODE_DUMP_FEATURES`、`RUNMODE_MAX`，注释说明 `RUNMODE_USER_MAX` 是「最后一个标准运行模式」，之后的是查询与工具模式，取值需对照实际版本核验。规则相关字段是 `sig_file` 与 `sig_file_exclusive`、`regex_arg`、`keyword_info`、`strict_rule_parsing_string`，以及实验性的 `firewall_rule_file`、`firewall_rule_file_exclusive`、`is_firewall`；`SuriHasSigFile` 判定是否指定了规则文件。设备与插件字段是 `pcap_dev[128]`、`runmode_custom_mode`、`capture_plugin_name`、`capture_plugin_args`，`RunModeDispatch` 消费后两者，`RunmodeGetActive`、`RunmodeIsWorkers`、`RunmodeIsAutofp`、`RunModeGetMainMode` 提供当前模式判定，只点名不展开流程。

**`SCInstance` 的权限、开关与路径字段**。`user_name`、`group_name`、`do_setuid`、`do_setgid` 四个字段被 `#ifndef OS_WIN32` 包裹，`userid` 与 `groupid` 是 `uint32_t` 目标 id，参数见 04-07；`system`、`set_logdir`、`set_datadir`、`unix_socket_enabled`、`install_signal_handlers` 五个 `bool` 分别记系统模式、日志与数据目录是否已显式指定、是否启用 unix 控制面、是否安装默认信号处理器，`SCEnableDefaultSignalHandlers` 与 unix 控制面实现（模块见 07-12）是对应入口。`delayed_detect`、`disabled_detect`、`daemon`、`offline`、`verbose`、`checksum_validation`、`output_flush_interval` 是七个 `int` 级开关与数值，`start_time` 是 `struct timeval` 启动时刻，`PostRunDeinit` 用它算运行时长。路径与列表字段是 `log_dir`、`progname`（注释说明指向 `argv[0]`）、`conf_filename`、`additional_configs`、`additional_plugins`，`DEFAULT_CONF_FILE` 由 `CONFIG_DIR` 与 `/suricata.yaml` 拼接，`DEFAULT_PID_DIR`、`DEFAULT_PID_BASENAME`、`DEFAULT_PID_FILENAME` 定义 pid 文件默认位置。全局量 `suricata_ctl_flags`（`volatile uint8_t`）、`g_disable_randomness`、`g_vlan_mask`、`g_livedev_mask`、`g_recurlvl_mask`、`g_disable_hashing` 在 `src/suricata.h:191` 起声明，`SURICATA_STOP`（`1<<0`）与 `SURICATA_DONE`（`1<<2`）由 `EngineStop`、`EngineDone` 设置，阶段枚举 `SURICATA_INIT`、`SURICATA_RUNTIME`、`SURICATA_DEINIT` 在 `:99`。生命周期函数 `GlobalsInitPreConfig`、`SuricataPreInit`、`SuricataInit`、`SuricataPostInit`、`SuricataMainLoop`、`SuricataShutdown`、`InitGlobal`、`GlobalsDestroy`、`PostConfLoadedSetup`、`PostConfLoadedDetectSetup`、`SCParseCommandLine`、`SCStartInternalRunMode`、`SCLoadYamlConfig`、`SCFinalizeRunMode`、`PreRunInit`、`PreRunPostPrivsDropInit`、`RegisterAllModules`、`GetProgramVersion` 只点名，原理见 06-01、06-13，参数见 04-07。

**引擎模式枚举与 host-mode 的核验结论**。`enum EngineMode`（`src/suricata.h:106`）四值中源码注释写着「顺序有意义，`ENGINE_MODE_IPS` 及以上代表 IPS」，配套 `EngineModeSetFirewall`、`EngineModeSetIPS`、`EngineModeSetIDS`、`EngineModeIsUnknown`、`EngineModeIsFirewall`、`EngineModeIsIPS`、`EngineModeIsIDS`。`enum EngineHostMode`（`:115`）三值为 `ENGINE_HOST_IS_SNIFFER_ONLY`、`ENGINE_HOST_IS_ROUTER`、`ENGINE_HOST_IS_BRIDGE`，配套 `EngineHostModeIsSniffer`、`EngineHostModeIsBridge`。这里必须写清：总纲 05-09 大纲提示的「auto / sniffer-only / router」是待核验的旧写法，与本快照枚举不一致，凡引用 host-mode 取值一律以 `src/suricata.h:115` 为准并写「需对照实际版本核验」；`ENGINE_MODE_FIREWALL` 与 `SCInstance.is_firewall` 对应实验性能力，`suricata.yaml.in` 里默认注释关闭的 `firewall` 段属实验性选项，绝不能据此把引擎写成网关或路由设备——Suricata 不做 IP 转发、不做路由、不是防火墙，内联阻断依靠 NFQUEUE 或 AF_PACKET 桥接的 verdict。这条边界与 01-01、06-12、08-05 一致，本篇字段表里所有 firewall 相关成员都标注「语义需对照实际版本核验」。

**`Host`、`HostHashRow` 与 `HostConfig` 字段**。`Host`（`src/host.h:58`）以 `SCMutex m` 开头，`Address a` 是 ipv4 或 ipv6 地址（字段见 05-02），`use_cnt` 用 `SC_ATOMIC_DECLARE(unsigned int, use_cnt)` 声明为原子引用计数，`iprep` 是 `void *` 的 iprep 存储句柄属于不透明数据，`hnext` 与 `hprev` 是受哈希行锁保护的哈希链双向指针，`lnext` 与 `lprev` 是受 host-queue 锁保护的队列链双向指针，尾部 `Storage storage[]` 是柔性数组。`src/host.h:30` 起的锁宏在 `HRLOCK_SPIN` 与 `HRLOCK_MUTEX` 之间二选一，本快照里 `HRLOCK_SPIN` 被注释、`HRLOCK_MUTEX` 生效，`HRLOCK_TYPE` 因此是 `SCMutex`；这与 `Flow`、`FlowBucket` 的编译期二选一锁是同一类组织方式，字段是否存在取决于构建变体。`HostHashRow`（`:83`）含 `HRLOCK_TYPE lock`、`Host *head`、`Host *tail`，并带 `__attribute__((aligned(CLS)))` 缓存行对齐；`HostConfig`（`:95`）含 `SC_ATOMIC_DECLARE(uint64_t, memcap)` 与 `hash_rand`、`hash_size`、`prealloc` 三个 `uint32_t`。`HOST_CHECK_MEMCAP` 宏用 `host_memuse` 与 `host_config.memcap` 比较，`HostIncrUsecnt`、`HostDecrUsecnt`、`HostReference`、`HostDeReference` 管引用，函数族 `HostInitConfig`、`HostShutdown`、`HostCleanup`、`HostLookupHostFromHash`、`HostGetHostFromHash`、`HostRelease`、`HostLock`、`HostUnlock`、`HostClearMemory`、`HostMoveToSpare`、`HostPrintStats`、`HostAlloc`、`HostFree`、`HostSetMemcap`、`HostGetMemcap`、`HostGetMemuse` 只点名，原理见 06-04，模块见 07-02、07-09，参数见 04-02。

**`Pool`、`PoolBucket` 与 `PoolThread` 的池化字段**。`PoolBucket`（`src/util-pool.h:36`）含 `void *data`、`uint8_t flags`、`PoolBucket *next`，`POOL_BUCKET_PREALLOCATED`（`1<<0`）是桶标志。`Pool`（`:43`）字段可分四组：容量组 `max_buckets`、`preallocated`、`allocated`、`alloc_stack_size`、`empty_stack_size`、`elt_size`；栈组 `alloc_stack`、`empty_stack`；连续内存组 `data_buffer_size`（`int`）、`data_buffer`（`void *`）、`pb_buffer`（`PoolBucket *`）；回调组 `Alloc`、`Init`、`Cleanup` 三个函数指针；计数组 `outstanding`（注释说明是「借出未归还」，`PoolGet` 与 `PoolReturn` 之差）与受 `DEBUG` 控制的 `max_outstanding`。入口是 `PoolInit`、`PoolFree`、`PoolGet`、`PoolReturn`、`PoolRegisterTests`。`PoolThreadElement`（`src/util-pool-thread.h:45`）含 `SCMutex lock` 与 `Pool *pool`，`PoolThread`（`:53`）含 `size_t size` 与 `PoolThreadElement *array`，`PoolThreadId` 是 `uint16_t`；头文件 `:30` 起的注释是硬约束：「本 API 的消费者必须把 `PoolThreadReserved` 作为数据结构第一个成员，并且必须完全忽略它，由 API 管理，目的是让线程 X 能把数据归还到线程 Y 的池」。入口是 `PoolThreadInit`、`PoolThreadExpand`、`PoolThreadFree`、`PoolThreadGetById`、`PoolThreadReturn`、`PoolThreadLock`、`PoolThreadReturnRaw`、`PoolThreadUnlock`、`PoolThreadSize`、`PoolThreadRegisterTests`。05-07 的 `PktPool`（`src/tmqh-packetpool.h:43`）是面向 `Packet` 的专用池化设施，与本组通用 `Pool` 属同类但字段不同，两边交叉引用时用「字段见 05-07」与「字段见 05-09」区分，不混用。所有池容量、预分配与 memcap 的具体取值需在目标机型实测，不给绝对值。

**配置加载入口与交叉引用**。`src/conf-yaml-loader.c` 里 `SCConfYamlLoadFile`（`:489`）、`SCConfYamlLoadString`（`:535`）、`SCConfYamlLoadFileWithPrefix`（`:565`）是配置树构建入口，内部 `ConfYamlParse`（`:167`）、`ConfYamlSetConfDirname`（`:82`）、`Mangle`（`:68`）、`SCConfYamlHandleInclude`（`:114`）处理解析、目录、键名规整与 include；`src/conf.c` 里 `SCConfInit`（`:120`）、`SCConfGetNode`（`:183`）、`SCConfSet`（`:241`）、`SCConfGet`（`:352`）是查询与写侧代表。`src/runmodes.h:106` 起还有 `threading_set_cpu_affinity`、`threading_detect_ratio`、`threading_set_stack_size`、`debuglog_enabled` 等全局，`:69` 起是 `thread_name_autofp`、`thread_name_single`、`thread_name_workers`、`thread_name_flow_mgr`、`thread_name_detect_loader` 等线程名字符串，参数见 04-03。交叉引用统一为（参数见 04-02 ｜ 原理见 06-13 ｜ 模块见 07-09）：yaml 全局段参数见 04-02、命令行与 RPC 参数见 04-07，流水线与 runmode 机制见 06-01、06-13，util 与 conf 目录模块见 07-09，控制面见 07-12，host 相关机制见 06-04、模块见 07-02。

### 6. 版本差异

本套资料统一以「上游 main 快照（2026-11 抓取）」为版本基准，`configure.ac`、`ChangeLog` 里的版本字样只作核验依据，不抄进正文当本套资料的版本号；需要说明版本来源时写「具体版本号以 `configure.ac`、`ChangeLog` 为准，需对照实际版本核验」。配置与运行时上下文恰是最容易随命令行选项、运行模式与实验性能力漂移的一类事实：新选项会往 `SCInstance` 追加字段、新运行模式会扩展 `SCRunModes`、防火墙与钩子能力会引入新枚举值、内存池会换实现，因此第 2 节与第 3 节给出的行号与字段清单是「这份快照的事实」，不是跨版本永久承诺。

几处已能在本快照里观察到的差异点值得单列。其一是命名前缀：`src/conf.h` 的结构体叫 `SCConfNode`、`src/conf.c` 的读取接口叫 `SCConfGet`、`SCConfGetInt`、`SCConfGetBool`、`SCConfSet` 系列，`src/conf-yaml-loader.c` 的入口叫 `SCConfYamlLoadFile`、`SCConfYamlLoadString`、`SCConfYamlLoadFileWithPrefix`；不少旧资料沿用 `ConfNode`、`ConfGet`、`ConfYamlLoadFile` 的写法，迁移脚本与检索关键字要按带 `SC` 前缀的实际定义核对，需对照实际版本核验。其二是 host-mode 与 engine-mode 取值：本快照 `enum EngineHostMode` 是 `ENGINE_HOST_IS_SNIFFER_ONLY`、`ENGINE_HOST_IS_ROUTER`、`ENGINE_HOST_IS_BRIDGE`，`enum EngineMode` 是 `ENGINE_MODE_UNKNOWN`、`ENGINE_MODE_IDS`、`ENGINE_MODE_IPS`、`ENGINE_MODE_FIREWALL`；总纲 05-09 大纲提示的 auto / sniffer-only / router 与之不一致，凡涉及取值一律以 `src/suricata.h` 为准并标注「需对照实际版本核验」，且实验性 `firewall` 段默认注释关闭，绝不能据此把引擎写成网关或路由设备。其三是运行模式枚举：`SCRunModes` 里能看到 `RUNMODE_AFXDP_DEV`、`RUNMODE_DPDK`、`RUNMODE_NETMAP`、`RUNMODE_WINDIVERT`、`RUNMODE_PLUGIN`、`RUNMODE_LIB` 等较新后端，以及 `RUNMODE_DUMP_CONFIG`、`RUNMODE_CONF_TEST`、`RUNMODE_ENGINE_ANALYSIS`、`RUNMODE_DUMP_FEATURES` 等工具模式，注释说明 `RUNMODE_USER_MAX` 是最后一个标准模式，旧版本是否具备需对照实际版本核验；PF_RING 支持状态需对照 `configure.ac` 与 `src/source-*.c` 实际版本核验，不得编造 `source-pfring.c`。

其四是 `SCInstance` 的实验性字段：`firewall_rule_file`、`firewall_rule_file_exclusive`、`is_firewall`、`capture_plugin_name`、`capture_plugin_args`、`additional_plugins`、`strict_rule_parsing_string`、`regex_arg` 对应防火墙规则、抓包插件、附加插件与严格解析等较新能力，语义与启用条件需对照实际版本核验；`src/suricata.h:122` 的 `EngineModeSetFirewall` 注释写着「IPS 模式的超集」，与 05-05 里 `SignatureInitData.firewall_rule`、`DetectEngineCtx` 的钩子字段相呼应。其五是条件编入字段：`SCInstance.user_name`、`group_name`、`do_setuid`、`do_setgid` 受 `OS_WIN32` 取反条件控制，`src/conf.h:54` 的 `DEFAULT_LOG_DIR`、`DEFAULT_DATA_DIR` 在 Windows 与非 Windows 下取值不同，`HostHashRow.lock` 在 `HRLOCK_SPIN` 与 `HRLOCK_MUTEX` 之间二选一、`Pool.max_outstanding` 受 `DEBUG` 控制，字段是否存在取决于平台与构建变体。其六是柔性数组与缓存行对齐：`Host.storage[]`、`ThreadVars.storage[]` 是柔性数组，`HostHashRow` 带 `aligned(CLS)`，`PoolThreadReserved` 要求消费者把它放在数据元素首位，这类布局随注册项数与目标机型缓存行变化，字节大小与偏移一律需在目标机型实测。

由此得到一条通用版本纪律：任何「结构叫什么」「字段是什么类型」「定义在哪个文件」「是否编入」的问题，最终都要回到 `upstream_src/suricata/suricata-main/src/` 用 Read、Grep 核实；凡 SPEC 第 0.1 节未列出或无法核实的文件一律不写进正文。字段含义与生命周期属于 05-07、05-09，机制见 06-01、06-04、06-13，模块归属见 07-02、07-09、07-12，参数见 04-02、04-03、04-07，四者不去重就会互相抄错；`SCConfNode` 的 `SC` 前缀、`EngineHostMode` 的取值、`EngineMode` 的 IPS 顺序约定是本篇三处最容易跨版本抄错的锚点，核验时优先对照这三处。

### 7. 常见误用与调试

第一类是「按旧名字检索配置接口」。`src/conf.h:37` 的结构体是 `SCConfNode`，`src/conf.c` 的读取接口是 `SCConfGet`、`SCConfGetInt`、`SCConfGetBool`、`SCConfSet`，`src/conf-yaml-loader.c` 的加载入口是 `SCConfYamlLoadFile`、`SCConfYamlLoadString`、`SCConfYamlLoadFileWithPrefix`；按 `ConfGet`、`ConfNode` 去 grep 本快照会一无所获，进而误判「配置接口不存在」。`SCConfNode.val` 是字符串，必须用 `SCConfGetInt` 一类函数转换，直接 `atoi` 虽然能跑但绕过了 `SCConfGetChildValueWithDefault` 提供的缺省回退与 `final` 语义；`is_seq` 未判就读 `val` 会把序列节点当成标量。`SCConfNodeIsSequence`、`SCConfNodeHasChildren`、`SCConfNodeLookupChild`、`SCConfGetNextNode` 是判结构形状的正确入口，参数见 04-02，加载链路原理见 06-01。

第二类是 host-mode 与 engine-mode 取值误用。本快照 `enum EngineHostMode` 为 `ENGINE_HOST_IS_SNIFFER_ONLY`、`ENGINE_HOST_IS_ROUTER`、`ENGINE_HOST_IS_BRIDGE`，`enum EngineMode` 为 `ENGINE_MODE_UNKNOWN`、`ENGINE_MODE_IDS`、`ENGINE_MODE_IPS`、`ENGINE_MODE_FIREWALL`，且源码注释说明「`ENGINE_MODE_IPS` 及以上代表 IPS」；把大纲提示的 auto / sniffer-only / router 直接当枚举值写进代码或配置会取错分支，凡涉及取值一律以 `src/suricata.h` 为准并标注「需对照实际版本核验」。更要守住能力边界：`ENGINE_MODE_FIREWALL` 与 `SCInstance.is_firewall`、`firewall_rule_file` 对应实验性能力，`suricata.yaml.in` 里默认注释关闭的 `firewall` 段属实验性选项，绝不能据此把引擎写成网关、路由设备或防火墙——Suricata 不做 IP 转发、不做路由、不是防火墙，内联阻断依靠 NFQUEUE 或 AF_PACKET 桥接的 verdict，IDS 旁路只告警不丢弃。

第三类是柔性数组、原子量与池化约定误用。`Host.storage[]` 与 `ThreadVars.storage[]` 都是柔性数组，`sizeof` 不含存储项，按定长结构 `memcpy` 会截断；`Host.use_cnt` 用 `SC_ATOMIC_DECLARE` 声明，引用与释放必须走 `HostIncrUsecnt`、`HostDecrUsecnt`、`HostReference`、`HostDeReference`，直接自增会破坏并发可见性；`HostHashRow` 带 `aligned(CLS)`，`HRLOCK_MUTEX` 与 `HRLOCK_SPIN` 二选一决定锁类型，把 `lock` 当恒定 `SCMutex` 会在另一种构建下读错。`src/util-pool-thread.h:30` 起的注释是硬约束：消费者必须把 `PoolThreadReserved` 放在数据元素第一个成员并完全忽略它，否则线程 X 无法把数据归还到线程 Y 的池；`Pool.outstanding` 是「借出未归还」而非总分配数，把它与 `allocated` 混用会误判池容量，`Pool.max_outstanding` 只在 `DEBUG` 下存在。所有容量、memcap 与内存占用结论需在目标机型实测。

第四类是越界与全册边界。05 册不展开 yaml 加载链路、runmode 装配、host 哈希与超时、池化分配回收、unix 控制面协议这些机制流程，遇「怎么加载、怎么装配」写「原理见 06-01」「原理见 06-13」「原理见 06-04」；不重列 `suricata.yaml` 全部段、命令行选项与 `suricatasc` RPC 命令全集，写「参数见 04-02」「参数见 04-07」；目录归属写「模块见 07-09」「模块见 07-12」，host 模块见 07-02。同时守住全册边界：Suricata 是 IDS / IPS / NSM 引擎，不做转发、不是防火墙；只对自身解码并重组到的流量做检测，TLS 等加密载荷正文不可见；规则兼容 Snort 但有自有扩展，不能宣称百分之百兼容；EVE JSON 是主要输出；Hyperscan 为可选加速、缺失回退 AC；`rust/` 与 Cargo 是构建的一部分；`suricata-update` 独立发版；多线程不等于必然线性提速。任何吞吐、pps、丢包率、内存占用数字一律标注「需在目标机型实测」。配置问题可用 `suricata -T`、`suricata --dump-config`、`suricata --build-info` 与 `suricata.log` 判读，命令参数见 04-07、返回码与错误速查见 04-08，诊断决策树见 08-03；`SCConfDump`、`SCConfNodeDump`、`HostPrintStats`、`HostGetMemuse`、`PoolThreadSize`、`SCRunmodeGet` 是本篇字段最接近的排错入口，只点名不展开流程。至此 05 册九个篇号覆盖的结构体族全部给出逐字段权威清单，机制原理见 06 全册、模块归属见 07 全册、参数全集见 04 全册，随查时按（字段见 05-xx ｜ 参数见 04-xx ｜ 原理见 06-xx ｜ 模块见 07-xx）反查即可。
