# Redis 与缓存体系精讲

**从五种数据结构到持久化、主从、集群，再到缓存三大经典问题——把最常用的键值数据库讲透**

## DB03-00 开篇：Redis 为什么这么快

### 1. 快在哪里

Redis 是内存数据库，数据都在内存里，读写不需要磁盘输入输出，这是它快的根本原因。但只说"因为内存"太笼统，完整的答案有五点：

- **纯内存**：数据常驻内存，随机访问纳秒级。
- **单线程命令执行**：核心命令处理用单线程，避免多线程上下文切换和锁竞争。
- **高效数据结构**：底层实现经过精心设计，比如压缩列表、跳表。
- **非阻塞输入输出**：用多路复用处理大量客户端连接。
- **简单协议**：通信协议简洁，解析开销小。

### 2. 单线程的利与弊

单线程让实现简单、没有锁竞争，但也有代价：一个耗时命令会阻塞所有其他命令。比如对一个超大集合做全量遍历、一次删除海量键，都可能让服务短暂停顿。所以使用 Redis 有一条重要纪律：避免慢命令，大键要拆分、批量操作要分批。

## DB03-01 五种核心数据结构

### 1. 数据结构速查

Redis 的五种基础结构覆盖了绝大多数场景。理解每种结构适合什么，是正确使用 Redis 的第一步。

| 结构 | 特点 | 典型场景 |
|---|---|---|
| 字符串 | 最基础，可存文本数字二进制 | 缓存、计数器、分布式锁 |
| 列表 | 有序、两端操作快 | 消息队列、最新列表 |
| 哈希 | 字段值对集合 | 存对象属性 |
| 集合 | 无序去重 | 标签、共同好友 |
| 有序集合 | 带分数排序 | 排行榜、延迟队列 |

```redis
SET user:1 "张三"                      # 字符串：缓存对象
INCR article:1001:views               # 字符串：计数器
LPUSH queue:jobs "task1"              # 列表：入队
RPOP queue:jobs                       # 列表：出队
HSET user:1 name "张三" age 30        # 哈希：存对象
SADD user:1:tags "vip" "new"          # 集合：标签
ZADD leaderboard 100 "player1"        # 有序集合：排行榜
ZRANGE leaderboard 0 9 REV            # 取前十名
```

### 2. 底层实现

Redis 对外暴露的是逻辑结构，内部有更精细的物理实现。理解这个对应关系，才能明白为什么某些操作快某些慢。

| 逻辑结构 | 底层实现 |
|---|---|
| 字符串 | 简单动态字符串，长文本或数值各有编码 |
| 列表 | 压缩列表或双向链表，新版用快速列表 |
| 哈希 | 压缩列表或哈希表 |
| 集合 | 整数集合或哈希表 |
| 有序集合 | 压缩列表或跳表加哈希表 |

### 3. 编码转换

Redis 会在元素少、值小的时候用紧凑的压缩列表省内存，元素变多变大后自动转成哈希表或跳表。这种自动编码转换对使用者透明，但意味着同样的数据结构在不同数据量下性能特征会变——这也是压测要贴近真实数据量的原因。

## DB03-02 持久化：数据怎么不丢

### 1. 两种持久化方式

Redis 是内存数据库，断电数据会丢。持久化就是把内存数据存到磁盘的机制，有两种方式。

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 快照 | 某时刻把全部数据写成快照文件 | 恢复快、文件紧凑 | 两次快照间的数据会丢 |
| 只追加日志 | 把每条写命令追加到日志 | 丢失少 | 文件大、恢复慢 |

:::figure id=DB03-02-01 | name=两种持久化方式对比 | dir=LR

node n3 "只追加日志<br/>逐条记录写命令" amber
node n4 "恢复快但丢得多" green
node n5 "丢得少但恢复慢" purple
edge n1 -> n2 "方式一"
edge n1 -> n3 "方式二"
edge n2 -> n4 "特点"
edge n3 -> n5 "特点"
:::

图中节点速览：n1 内存数据有 n2 快照和 n3 只追加日志两种存盘方式，分别对应 n4 和 n5 的不同取舍。生产环境常常两者结合，用日志保证数据少丢，用快照加速恢复。

### 2. 快照的触发与问题

快照有三种触发方式：手动触发、按配置的时间与修改次数自动触发、主从全量同步时触发。快照的问题是它基于某个时间点，两次快照之间宕机的数据会丢；而且生成快照要 fork 子进程，数据量大时 fork 会阻塞主进程。

### 3. 只追加日志的刷盘策略

只追加日志的写入分两步：命令先写缓冲区，再按策略刷盘。刷盘策略决定安全与性能的取舍：

| 策略 | 何时刷盘 | 安全性 | 性能 |
|---|---|---|---|
| 每次写都刷 | 每条命令后立即刷 | 最高，最多丢一条 | 最低 |
| 每秒刷 | 每秒批量刷一次 | 较高，最多丢一秒 | 高 |
| 由系统决定 | 交给操作系统 | 最低 | 最高 |

生产常用"每秒刷",在安全和性能间取得平衡。

### 4. 日志重写

只追加日志会越来越大，因为同一个键被改多次会记多条命令。日志重写机制会读取当前数据，重新生成一份精简的命令日志，只保留每条数据的最终状态，大幅缩小文件。重写同样用子进程完成，期间的新写入会缓存在缓冲区，重写完再追加进去。

## DB03-03 主从复制与哨兵

### 1. 主从复制

和关系库类似，Redis 也支持主从复制：一个主节点负责写，多个从节点复制数据、分担读，并在主节点故障时提供提升为新的主节点的候选。

复制分两种：

- **全量复制**：从节点刚接入或差距太大时，主节点生成快照发给从节点，从节点加载后再同步期间的增量命令。
- **增量复制**：日常由一个环形缓冲区记录最近的命令，从节点断线重连后从这个缓冲区续传，不用每次都全量。

### 2. 哨兵机制

主从解决了读写分离和数据冗余，但主节点挂了谁来做切换？哨兵就是专门干这个的分布式监控系统。

### 3. 脑裂问题

如果主节点只是网络分区、实际还活着，哨兵把它切了、从节点升为新主，就会出现两个主节点同时写。老主恢复后可能覆盖新主数据。缓解手段是给主节点配置：当连接从节点数不足或失联超时，就拒绝写入，宁可不可用也不制造脏数据。

## DB03-04 Redis 集群

### 1. 为什么需要集群

单机内存有限，数据量超过单机容量就要分片到多台。Redis 集群把数据自动分散到多个节点，每个节点存一部分，并提供故障转移。

### 2. 哈希槽分片

Redis 集群用哈希槽做分片：整个键空间分成一万六千三百八十四个槽，每个键算哈希后落到一个槽，每个节点负责一部分槽。

| 特性 | 说明 |
|---|---|
| 槽数量 | 一万六千三百八十四个固定槽 |
| 键归槽 | 对键名算哈希取模 |
| 节点分槽 | 每个节点负责若干连续槽 |
| 迁移 | 增删节点时槽在节点间迁移 |

用固定数量的槽而不是直接按节点数取模，好处是增减节点时只需迁移部分槽，不用重排所有数据。

### 3. 集群的局限

- 多键操作受限：只有落在同一槽的多个键才能一起操作，跨槽不行。
- 数据库概念弱化：集群模式只支持默认的零号数据库。
- 复制是异步的，故障切换时可能丢失少量写入。

## DB03-05 缓存三大经典问题

这是 Redis 作为缓存使用时最常考、最容易出事故的三个问题。

### 1. 缓存穿透

查询一个根本不存在的数据，缓存里没有、数据库里也没有，于是每次请求都穿透缓存打到数据库。大量这种请求会压垮数据库。

**解决**：对不存在的键也缓存一个空值并设短过期时间；用布隆过滤器提前判断键是否存在，不存在直接返回。

### 2. 缓存击穿

一个热点键刚好过期，瞬间大量请求同时发现缓存没有，全部打到数据库。和穿透的区别是：击穿的键是存在的、只是过期了。

**解决**：热点键永不过期，由后台异步更新；用互斥锁保证只有一个请求去数据库加载，其他请求等待。

### 3. 缓存雪崩

大量缓存键在同一时刻集体过期，或缓存服务整体宕机，导致所有请求涌向数据库。

**解决**：给过期时间加随机抖动，避免同时过期；多级缓存；缓存服务高可用；数据库侧限流降级。

### 4. 三者对比速查

| 问题 | 键是否存在 | 范围 | 核心解法 |
|---|---|---|---|
| 穿透 | 不存在 | 单个或大量不存在的键 | 缓存空值、布隆过滤器 |
| 击穿 | 存在但过期 | 单个热点键 | 热点键永不过期、互斥锁 |
| 雪崩 | 存在但集体失效 | 大批键或服务宕机 | 过期抖动、高可用、限流 |

## DB03-06 过期策略与内存管理

### 1. 过期删除策略

给键设置过期时间后，Redis 怎么删除过期键？有两种策略配合：

- **惰性删除**：访问键时才检查是否过期，过期就删。问题是没被访问的过期键一直占内存。
- **定期删除**：定期抽样检查一批键，删掉其中过期的。抽样式避免全表扫描的开销。

两者结合，既避免全量扫描的成本，又防止过期键无限堆积。

### 2. 内存淘汰策略

当内存达到上限，Redis 要淘汰一些键来腾空间，常见策略：

| 策略 | 含义 |
|---|---|
| 不淘汰 | 直接报错，适合不能丢数据的场景 |
| 按最近最少使用淘汰 | 全局或仅设了过期时间的键里淘汰 |
| 按最近使用频率淘汰 | 淘汰使用频率最低的 |
| 随机淘汰 | 随机选键淘汰 |
| 按过期时间淘汰 | 淘汰最快过期的 |

选择哪种取决于业务：纯缓存可以随便淘汰，当作持久存储则要谨慎。

### 3. 内存优化实践

- 控制键值大小，大对象拆分或压缩。
- 利用紧凑编码，元素少时用压缩列表。
- 给键设合理过期时间，避免无限堆积。
- 监控内存碎片率，必要时触发整理。
- 大键拆解，避免删除或迁移时的阻塞。

## DB03-07 典型应用场景

### 1. 场景速查

| 场景 | 用的结构 | 关键点 |
|---|---|---|
| 对象缓存 | 字符串或哈希 | 设过期时间、防穿透击穿 |
| 分布式锁 | 字符串加强指令 | 唯一值、过期时间、安全释放 |
| 计数器 | 字符串自增 | 原子递增 |
| 排行榜 | 有序集合 | 分数排序、取TOPN |
| 消息队列 | 列表或流 | 生产者消费者 |
| 限流 | 字符串或有序集合 | 滑动窗口计数 |
| 共同好友 | 集合交集 | 集合运算 |
| 会话存储 | 字符串或哈希 | 集中式会话、过期 |

```redis
-- 分布式锁：加唯一值、设过期、安全释放
SET lock:order1 "uuid-1234" NX EX 30     # 不存在才设置，三十秒过期
-- 释放时用 Lua 脚本比对值再删，避免误删别人的锁
```

### 2. 分布式锁的坑

最简单的分布式锁看似几行命令，实则暗藏陷阱：设了锁忘设过期时间会导致死锁；过期时间太短，业务没执行完锁就没了；释放时误删别人续上的锁。正确做法是用唯一值标识自己的锁、用脚本保证"比对加删除"的原子性，关键场景还要有续期机制。

## DB03-08 本篇小结与选型

### 1. Redis 的定位

Redis 是极致性能的内存键值库，擅长缓存、计数器、排行榜、分布式锁、简单队列。它不是万能的：内存成本高，不适合存海量冷数据；持久化不如关系库完备，不能替代主存储；单线程模型怕慢命令。

### 2. 什么时候用 Redis

- 需要极高读写性能的简单数据访问 → 用。
- 需要复杂关系查询和强事务 → 用关系库，Redis 做缓存。
- 数据规模远超内存、且访问很少 → 不适合，用磁盘数据库。
- 需要丰富的数据结构和原子操作 → Redis 很合适。

### 3. 本篇小结

从五种数据结构到跳表实现，从快照日志到主从集群，从三大缓存问题到分布式锁，Redis 的设计始终围绕一个目标：用内存和精巧结构换取极致速度，同时用持久化和集群弥补内存数据库的短板。理解它的每一处设计，都能看到"取舍"二字——单线程换无锁、槽位换平滑扩容、采样换低开销。下一篇转向另一大类：NoSQL 数据库。
