# 关系型数据库精讲：MySQL 与 PostgreSQL 双雄

**基础篇讲通用原理，本篇落到两个最主流的开源关系库——它们怎么组织、怎么执行、怎么保证事务、怎么扩展**

## DB01-00 开篇：为什么是这两个

### 1. 双雄的地位

关系型数据库产品很多，但开源世界里最有代表性的就是 MySQL 和 PostgreSQL。互联网公司里，MySQL 几乎成了关系库的代名词；而在需要复杂查询、严格事务和可扩展类型的场景，PostgreSQL 越来越受欢迎。理解这两个，其他关系库（Oracle、SQL Server、达梦、人大金仓等）大多是同源思想的不同实现。

两者有个通俗的分工记忆：**MySQL 长于简单高频的在线交易，PostgreSQL 长于复杂查询和数据类型**。这不是绝对的，但抓住了设计取向的差别。

## DB01-01 整体架构

### 1. MySQL 的分层架构

MySQL 采用典型的分层加可插拔存储引擎架构。上层负责连接、解析、优化，下层存储引擎负责真正的存取。这种设计让上层与存储方式解耦，是 MySQL 能支持多种存储引擎的关键。

| 层 | 部件 | 职责 |
|---|---|---|
| 连接层 | 连接池、认证、线程管理 | 管理客户端连接 |
| 服务层 | 解析器、预处理器、优化器、执行器 | 解析与执行 SQL |
| 引擎层 | InnoDB、MyISAM 等 | 存取数据、管理索引 |
| 存储层 | 数据文件、日志文件 | 落到磁盘 |

### 2. PostgreSQL 的架构差异

PostgreSQL 的架构更"一体化"：它没有 MySQL 那种可插拔多引擎的概念，只有一个高度集成的后端。但它有独特的进程模型和扩展机制。

| 对比项 | MySQL | PostgreSQL |
|---|---|---|
| 存储引擎 | 可插拔，多种引擎 | 单一集成引擎 |
| 连接模型 | 线程模型 | 每连接一个进程 |
| 事务隔离默认 | 可重复读 | 读已提交 |
| 数据类型 | 相对基础 | 丰富，支持自定义类型 |
| 扩展能力 | 插件式存储引擎 | 强大的扩展与自定义函数 |
| 查询优化器 | 相对简洁 | 更复杂，支持更多连接策略 |

PostgreSQL 每连接一个进程的模型，在高连接数下内存开销更大，通常要配连接池；但进程隔离让稳定性更好，一个连接崩溃不会拖垮整个实例。

### 3. 查询缓存的兴衰

MySQL 早期有个查询缓存：完全相同的 SQL 直接返回缓存结果。听起来美好，实际限制极多——表有任何改动，相关缓存全部失效，高并发写入下缓存命中率很低还拖慢写入。所以较新版本已经移除了它。这个案例说明：数据库里的"缓存"设计要非常小心失效代价，看似加速的功能可能得不偿失。

## DB01-02 存储引擎与 InnoDB

### 1. 为什么默认引擎是它

InnoDB 成为 MySQL 默认引擎，靠的是三点：支持事务、支持行级锁、支持崩溃恢复。这三点正是 OLTP 在线交易最需要的。相比之下老的 MyISAM 只支持表级锁、不支持事务，一写就锁全表，高并发下性能很差，现已基本退出主流。

| 特性 | InnoDB | MyISAM |
|---|---|---|
| 事务 | 支持 | 不支持 |
| 锁粒度 | 行级锁 | 表级锁 |
| 崩溃恢复 | 支持 | 不支持 |
| 外键 | 支持 | 不支持 |
| 适合 | 高并发写入 | 只读或读多写少 |

### 2. InnoDB 的存储结构

InnoDB 把数据按页组织，页是最小读写单位，默认十六千字节。若干页组成区、段、表空间，形成一套层次结构。

| 层级 | 说明 |
|---|---|
| 表空间 | 最外层容器，可共享可独立 |
| 段 | 索引段、数据段等 |
| 区 | 六十四连续页，约一兆 |
| 页 | 十六千字节，基本单位 |
| 行 | 真正的一条记录 |

### 3. 聚簇索引与回表

InnoDB 的表是索引组织表：数据本身就按主键排成一棵 B+树，叶子节点存整行数据。这棵主键树就是聚簇索引。其他索引的叶子节点只存主键值，查到主键后还要回主键树取整行——这一步叫回表。

回表意味着走两次树，所以能少回表就少回表。由此引出两个重要优化手段：

- **覆盖索引**：查询需要的列都在索引里，不用回表。比如给"姓名、电话"建联合索引，只查这两列就不用回主键树。
- **索引下推**：把部分过滤条件下推到索引层先筛，减少回表次数。

### 4. change buffer

对于非聚簇索引的修改，如果对应的页不在内存里，InnoDB 不立刻从磁盘读上来改，而是把改动缓存在 change buffer 里，等以后读页时再合并。这把随机磁盘写变成顺序缓存写，对写多读少的场景提升明显。但如果读很频繁，改动很快就要合并，这个功能反而是负担。

## DB01-03 索引设计实战

### 1. 联合索引与最左前缀

多列组成的联合索引,查询条件必须从最左边列开始连续匹配,才能用上索引，这叫最左前缀原则。比如给"地区、年龄、姓名"建联合索引：

| 查询条件 | 能否用索引 | 原因 |
|---|---|---|
| 地区等于某值 | 能用 | 匹配最左列 |
| 地区加年龄 | 能用 | 从最左连续匹配 |
| 地区加年龄加姓名 | 能用 | 完全匹配 |
| 只给年龄 | 用不上 | 跳过最左列 |
| 地区加姓名 | 部分用上 | 跳过年龄，姓名那列用不上 |

```sql
-- 建立联合索引
CREATE INDEX idx_loc_age_name ON customer(region, age, name);

-- 能用上：从最左列开始
SELECT * FROM customer WHERE region = '华东' AND age = 30;

-- 用不上：跳过了最左列
SELECT * FROM customer WHERE age = 30;
```

### 2. 索引设计 checklist

- 区分度高的列优先：能筛掉更多数据的列放前面。
- 高频查询条件优先：经常出现在 WHERE 和 JOIN 里的列。
- 最左前缀：把最常用的列放最左。
- 尽量覆盖：把查询要返回的列也纳入索引，避免回表。
- 控制数量：写多读少的表尤其要克制。
- 避免对索引列做函数运算或隐式类型转换，会让索引失效。

## DB01-04 事务与隔离的实现

### 1. undo、redo 与多版本

基础篇讲过事务的 ACID，这里讲 InnoDB 具体靠什么实现。核心是三样东西：

| 机制 | 作用 | 对应 ACID |
|---|---|---|
| undo 日志 | 存修改前的值，用于回滚和读旧版本 | 原子性、隔离性 |
| redo 日志 | 存修改后的值，用于崩溃恢复 | 持久性 |
| 多版本并发控制 | 每行保留多个版本，读写不冲突 | 隔离性 |

一条更新语句的大致过程：把旧值写入 undo、把新值写入 redo（先日志后数据）、修改内存页、返回成功。事务提交时把 redo 刷盘，崩溃后靠 redo 重做已提交事务、靠 undo 回滚未提交事务。

node n3 "改内存页<br/>存新值" amber

图中节点速览：n1 更新语句依次经过写 undo（n2）、改内存（n3）、写 redo（n4），提交时刷 redo（n5）。这里体现了一个核心设计：日志先行——先保证日志落地，再谈数据页，这样任何时刻崩溃都能恢复。

### 2. 多版本并发控制怎么读

每行记录藏着两个隐藏列：最后修改它的事务编号、指向旧版本的回滚指针。多个版本串成一条链。读数据时，不同隔离级别看到不同版本：

- 读已提交：每次读都看最新已提交版本，所以两次读可能不同。
- 可重复读：事务开始时确定一个版本快照，整个事务都看这个快照，所以两次读一致。

这就是"快照"这个词在事务语境里的含义。

### 3. 间隙锁与幻读

InnoDB 在可重复读级别下，除了锁住已存在的行，还会锁住行与行之间的"间隙"，阻止其他事务往间隙里插入新行。这个间隙锁正是它能在可重复读级别就解决幻读的原因——比标准定义里的可重复读更强。

代价是间隙锁增加了锁冲突和死锁概率，尤其在范围更新时。这也是为什么很多人把隔离级别调成读已提交来减少锁竞争，代价是接受不可重复读。

## DB01-05 锁机制与死锁

### 1. 锁的分类

| 维度 | 类型 | 说明 |
|---|---|---|
| 粒度 | 表锁、行锁、页锁 | 粒度越细并发越高、开销越大 |
| 模式 | 共享锁、排他锁 | 读锁可共存，写锁互斥 |
| 意向 | 意向共享、意向排他 | 表级标记，快速判断能否加锁 |

InnoDB 的行锁是加在索引上的——如果一条更新语句没走索引，就可能退化成锁全表。这也是"更新一定要走索引"这条铁律的底层原因。

### 2. 死锁是怎么发生的

两个事务各持有一把锁，又想拿对方手里的锁，互相等待谁也不放手，就是死锁。

node n2 "事务乙<br/>锁住行二" teal
node n3 "甲想锁行二<br/>被乙挡住" amber
node n4 "乙想锁行一<br/>被甲挡住" green
node n5 "互相等待<br/>死锁" purple

:::

图中节点速览：n1 和 n2 各持一把锁，n3 和 n4 分别去拿对方的锁，形成等待环 n5。数据库检测到环后，会选一个代价小的事务回滚来打破僵局。

### 3. 如何减少死锁

- 让不同事务按相同顺序访问表和行，避免交叉。
- 更新尽量走索引，缩小锁定范围。
- 事务尽量短，别在事务里做耗时操作。
- 大事务拆成小事务。
- 合理使用隔离级别，必要时降低到读已提交减少间隙锁。

## DB01-06 执行计划与调优

### 1. 看懂执行计划

用 explain 加在查询前，可以看到优化器打算怎么执行。字段很多，先抓住四个关键：

| 字段 | 关注点 |
|---|---|
| 访问类型 | 系统性、范围、引用、全表等，全表通常要警惕 |
| 可能索引与实际索引 | 优化器考虑了哪些、最后用了哪个 |
| 扫描行数 | 估算要读多少行，越小越好 |
| 额外信息 | 是否用了临时表、是否文件排序 |

访问类型从好到坏大致是：系统、常量、等值引用、范围、索引扫描、全表扫描。看到全表扫描且表很大，就要想想索引是不是没建或失效了。

### 2. 索引失效的诊断

当发现查询慢，按这个顺序排查：

1. 看执行计划确认到底有没有走索引、扫了多少行。
2. 检查索引列是否被函数包裹、是否发生隐式转换。
3. 检查联合索引是否满足最左前缀。
4. 检查统计信息是否过期，必要时更新统计。
5. 检查是不是优化器判断走索引反而更慢（小表、命中率高的条件）。

### 3. 一个调优实例

有张订单表五百万行，查询某客户最近十笔订单很慢。排查发现客户编号列有索引，但查询按创建时间排序，优化器判断要回表排序代价高，干脆全表扫描。解决办法是建一个"客户编号、创建时间"的联合索引，既过滤又有序，还覆盖要查的列，查询从全表扫描变成几十行定位。

```sql
-- 优化前：客户编号有单列索引，但仍可能全表扫描加排序
SELECT * FROM orders WHERE customer_id = 1001 ORDER BY created_at DESC LIMIT 10;

-- 优化后：联合索引同时满足过滤、排序、覆盖
CREATE INDEX idx_cust_time ON orders(customer_id, created_at);
```

## DB01-07 复制与高可用

### 1. 复制的三种一致性

主从复制的核心问题是：主库写完后，什么时候算成功？这决定了数据一致性强度。

| 复制方式 | 主库何时返回成功 | 特点 |
|---|---|---|
| 异步复制 | 写入本地就返回 | 最快，可能丢数据 |
| 半同步复制 | 至少一个从库收到就返回 | 折中，丢数据风险小 |
| 全同步或组复制 | 多数节点确认才返回 | 最强一致，延迟最大 |

:::figure id=DB01-07-01 | name=三种复制的一致性强度 | dir=LR
node n1 "异步<br/>本地写完就返回" blue
node n2 "半同步<br/>一个从库确认" teal
node n3 "组复制<br/>多数节点确认" amber
edge n1 -> n2 "一致性增强"
edge n2 -> n3 "一致性再增强"
:::

图中节点速览：从 n1 到 n3，一致性越来越强、数据越来越不容易丢，但写入延迟也越来越大。这是典型的速度与安全取舍，没有绝对最优，看业务能接受丢多少数据。

### 2. 复制延迟

异步复制下从库可能落后主库几秒甚至更久，造成"刚写完立刻读读到旧值"。常见应对：

- 对一致性要求高的读走主库。
- 写后读同一用户的请求路由到同一节点。
- 监控延迟，超阈值告警或切换。
- 用半同步缩小延迟窗口。

### 3. 高可用方案

- 主从切换：主库挂了提升从库，关键是避免脑裂——两个主库同时写会造成数据分叉，所以要配仲裁或多数派机制。
- 组复制或多数派集群：写入需要多数节点同意，天然避免脑裂，自动选主。
- 读写分离中间件：应用无感知地把读写路由到不同节点。

## DB01-08 两库对比与选型

### 1. 核心差异速查

| 维度 | MySQL | PostgreSQL |
|---|---|---|
| 设计取向 | 简单、快、易用 | 功能强、标准、严谨 |
| 默认隔离 | 可重复读 | 读已提交 |
| 复杂查询 | 一般 | 强，优化器更成熟 |
| 数据类型 | 基础类型为主 | 丰富，支持数组、json、自定义 |
| 扩展 | 存储引擎插件 | 扩展与自定义函数生态强 |
| 生态 | 互联网广泛使用 | 地理信息、分析场景强 |
| 运维 | 成熟工具多 | 也成熟，略偏学院派 |

### 2. 选型建议

- 典型互联网 OLTP、团队熟悉、生态工具多、追求稳定易用 → MySQL。
- 复杂查询多、需要丰富数据类型、地理信息或分析场景、追求标准兼容 → PostgreSQL。
- 两者都能满足时，看团队熟悉度和已有运维体系，迁移成本往往比理论差异更重要。

### 3. 本篇小结

关系型数据库的核心竞争力，在于用成熟的优化器和事务机制，让开发者专注业务而不必操心存取细节。MySQL 的可插拔引擎和 PostgreSQL 的丰富功能，是两条不同的演进路线。下一篇会深入数据库内部的公共机制——B+树、预写日志、共识算法，这些是理解所有数据库的底层钥匙。

select 语句看似简单，背后是连接管理、解析、优化、引擎、缓冲、日志、锁一整套精密协作。理解这条链路，调优和排障才有的放矢。
