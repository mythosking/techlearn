# 专用数据库与全系列选型总览

**时序、图、向量、嵌入式——那些为特定场景而生的数据库，以及贯穿整个系列的选型地图**

## DB07-00 开篇：专用数据库的价值

### 1. 通用与专用的分工

关系库是通用的，能应付大多数场景。但有些数据的形状和访问模式非常特殊，用通用库能做到但事倍功半。专用数据库就是为这些场景量身打造，在特定的维度上做到极致。

| 专用库 | 数据的特殊性 | 极致的维度 |
|---|---|---|
| 时序数据库 | 数据自带时间戳、持续追加 | 高写入、按时间查询、压缩 |
| 图数据库 | 关系是一等公民 | 多跳关联查询 |
| 向量数据库 | 数据是高维向量 | 相似度检索 |
| 嵌入式数据库 | 要嵌进应用本身 | 零部署、轻量 |

## DB07-01 时序数据库

### 1. 什么是时序数据

时序数据是按时间顺序记录的一连串数值，典型如服务器每分钟的中央处理器使用率、传感器每秒的温度、股票每笔成交价。它的特点非常鲜明：

- 写入极多且几乎恒定，很少更新删除。
- 数据自带时间戳，按时间范围查询为主。
- 近期数据查得多，远期数据做汇总归档。
- 同一指标的值往往变化平缓，压缩潜力大。

### 2. 时序库的专门优化

| 优化 | 做法 |
|---|---|
| 时间分区 | 按时间分片，查询按时间范围快速裁剪 |
| 高压缩 | 对时间戳和数值用增量编码等专用压缩 |
| 降采样 | 自动把高频数据聚合成低频概要 |
| 保留策略 | 到期数据自动删除或降级存储 |
| 标签索引 | 对设备标识等标签建高效索引 |

```text
一条时序数据通常长这样：
指标名 = cpu.usage
标签 = {host: server01, region: 华东}   ← 维度，用于筛选分组
时间戳 = 2026-11-25 10:00:00
值 = 73.5
```

### 3. 代表产品

- 专门时序库：适合监控、物联网指标场景，写入吞吐和压缩极强。
- 关系库时序扩展：在关系库上加时序能力，兼容 SQL 生态，适合已有关系库体系的团队。

### 4. 什么时候用

监控告警、物联网采集、指标分析、金融行情、日志指标这类"持续产生、按时间查"的场景，时序库比通用库高效得多。但如果需要复杂事务、复杂关联，时序库并不擅长。

## DB07-02 图数据库

### 1. 关系是主角

在很多场景里，数据之间的关系和实体本身一样重要：社交网络谁认识谁、风控里设备与账户的关联、知识图谱里概念之间的语义关系。关系库能存关系，但多跳查询要反复连接，跳数一多性能急剧下降。图数据库把关系作为一等公民直接存储，多跳查询如履平地。

| 概念 | 说明 |
|---|---|
| 节点 | 实体，如人、账户、公司 |
| 边 | 实体间的关系，如认识、转账、持有 |
| 属性 | 节点和边都可以带属性 |
| 路径 | 节点和边组成的序列 |

```text
(张三)-[:认识]->(李四)-[:转账 {金额: 5000}]->(商户A)
```

这条路径在关系库里要连两张表，在图库里直接沿边遍历。

### 2. 图查询的特点

- **多跳遍历高效**：沿着边走，跳数增加代价线性增长，不像连接那样指数爆炸。
- **模式匹配**：用类结构化查询语言描述"我要找这样的关系模式"。
- **最短路径**：内建图算法，找两点间最短或最优路径。

### 3. 什么时候用

社交网络、反欺诈风控、知识图谱、推荐系统、依赖分析、权限关系这类"关系密集、多跳查询"的场景。如果数据关系简单、查询以单表为主，图库反而增加复杂度，不如关系库。

## DB07-03 向量数据库

### 1. 为什么需要向量检索

人工智能时代，文本、图片、音频都可以被模型转成一串高维数字，叫向量或嵌入。语义相近的内容，它们的向量在空间里距离也近。于是"找相似内容"就变成"在高维向量空间里找最近的向量",这类需求催生了向量数据库。

| 场景 | 说明 |
|---|---|
| 语义搜索 | 按意思而非关键词找文档 |
| 大模型知识库 | 检索增强生成，先检索相关片段再让模型回答 |
| 以图搜图 | 找视觉相似的图片 |
| 推荐 | 找兴趣相似的用户或商品 |

### 2. 近似最近邻

在高维空间里精确找最近邻代价极高，向量库通常用近似最近邻算法，用少量精度损失换取巨大速度提升。

| 算法 | 思路 |
|---|---|
| 基于哈希 | 相似向量哈希到同一桶的概率高 |
| 基于量化 | 把向量压缩成短编码快速比较 |
| 基于图 | 建近邻图，沿图搜索逐步逼近 |

### 3. 什么时候用

语义检索、大模型知识库、相似推荐、多模态搜索。很多关系库和分析库也加入了向量检索扩展，如果规模不大、已有数据库体系，可以先用扩展，规模大了再上专用向量库。

## DB07-04 嵌入式数据库

### 1. 零部署的数据库

嵌入式数据库不是一个独立运行的服务，而是一段链接进应用程序的库，直接读写本地文件。它没有服务器、不用安装配置、没有网络开销，非常适合单个应用本地存储数据。

| 特点 | 说明 |
|---|---|
| 零部署 | 作为库嵌进程序，无需单独服务 |
| 单文件 | 一个文件就是一个数据库 |
| 轻量 | 资源占用小 |
| 事务 | 支持完整事务 |

### 2. 典型代表

轻量级嵌入式数据库被广泛用在手机应用、桌面软件、浏览器、嵌入式设备、小型工具里。它可能是世界上部署量最大的数据库——因为几乎每台设备、每个应用里都藏着一个。

### 3. 什么时候用

本地应用数据存储、原型开发、小型工具、嵌入式设备、测试场景。不适合多应用共享、高并发、需要网络访问的场景——那些要专门的数据库服务。

## DB07-05 全系列选型总览

### 1. 十三类数据库一张表

把整个系列的数据库类型汇总，给出作用、解决问题、代表和场景，作为选型总索引。

| 类型 | 一句话作用 | 解决什么问题 | 代表产品 | 典型场景 |
|---|---|---|---|---|
| 关系型数据库 | 表格存结构化数据，强事务 | 一致性、复杂查询 | MySQL、PostgreSQL | 交易、账务、业务系统 |
| 键值数据库 | 按键高速取值 | 极速简单读写 | Redis | 缓存、会话、排行榜 |

| 图数据库 | 存节点与关系 | 多跳关联查询 | Neo4j | 社交、风控、图谱 |

| 嵌入式数据库 | 本地轻量存储 | 零部署单文件 | SQLite | 应用本地存储 |
| 分布式数据库 | 内建分片与事务 | 海量又要强一致 | 分布式库产品 | 金融核心、大促 |

| 数据湖与湖仓 | 存原始数据并治理 | 多格式统一平台 | 湖仓产品 | 探索与人工智能 |

### 3. 选型的四条心法

- **数据是核心**：先分析数据的形状、规模、变化频率、访问模式，再谈产品。
- **事务看强度**：需要强一致事务就往关系库和分布式库靠，能接受最终一致就有更多选择。
- **组合而非替代**：真实系统通常是多种数据库搭配，各司其职。
- **团队与生态算进成本**：产品的理论优劣之外，团队熟悉度、运维能力、生态工具往往更决定成败。

### 2. 贯穿全书的三条主线

第一条主线是**取舍**。几乎每一个设计都是取舍：行存与列存、一致性与可用性、单线程与多线程、索引的快与写的慢、强一致与高可用。理解了"没有银弹，只有取舍",就理解了数据库设计的一半。

第二条主线是**分层**。从连接、解析、优化、执行，到存储引擎、缓冲、日志、磁盘，再到分布式层，每一层解决一类问题。排障和调优时，先定位到是哪一层的问题，效率和准确度都会高很多。

第三条主线是**场景**。所有技术选择最终都要回到场景：你的数据长什么样、并发多大、能接受丢多少数据、查询模式是什么。脱离场景谈"哪个数据库更好"没有意义。

### 3. 写在最后

数据库是软件系统的基石，也是计算机科学里理论与实际结合最紧密的领域之一。从一棵 B+树到一套跨地域的分布式系统，背后是几十年工程经验的沉淀。这个系列从零基础讲起，逐层深入到机制内部，再铺开到各类数据库和选型，目标是让你既看得见森林，也看得清树木。

学无止境，愿这套资料成为你数据库之路上的一张可靠地图。
