# NoSQL 数据库精讲：文档、列族与模型选型

**关系库之外的一大片天地——为什么会出现 NoSQL，文档库和列族库各自怎么工作，如何按场景取舍**

## DB04-00 开篇：NoSQL 到底指什么

### 1. 一个被误读的名字

NoSQL 字面意思是"非 SQL"，但更准确的含义是"不仅是 SQL"。它不是某一种数据库，而是一大类不用传统表格模型、不强制 SQL 接口的数据库统称。它诞生的背景是互联网时代的关系库瓶颈：

- 海量数据单机存不下，关系库横向扩展困难。
- 高并发读写，关系库的事务和连接开销成为负担。
- 数据结构多变，固定表结构不灵活。
- 很多场景不需要强事务，更看重可用性和扩展。

### 2. 四大流派

| 流派 | 代表 | 核心特点 | 擅长 |
|---|---|---|---|
| 键值 | Redis、DynamoDB | 按键取值，结构最简单 | 缓存、简单高速读写 |
| 文档 | MongoDB、CouchDB | 存半结构化文档 | 结构灵活、快速迭代 |
| 列族 | Cassandra、HBase | 按列族存超宽表 | 海量数据、高写入 |
| 图 | Neo4j | 节点与边 | 关联关系查询 |

本篇重点讲文档和列族两大流派，键值库已在 Redis 篇详述，图数据库留到专用数据库篇。

## DB04-01 文档数据库：MongoDB

### 1. 文档模型是什么

文档数据库存的是一条条类似统一资源标记语言里的对象格式那样的"文档"——嵌套的键值对集合。它和关系表最大的区别是：每条文档可以有不同字段，字段可以嵌套，不用预先定义结构。

| 对比 | 关系表 | 文档 |
|---|---|---|
| 结构 | 先定表结构，所有行一致 | 无需预定义，每条可不同 |
| 嵌套 | 不支持，要拆表连接 | 原生支持嵌套 |
| 关联 | 用外键连接 | 用引用或内嵌 |
| 灵活 | 改结构要迁移 | 随时加字段 |
| 事务 | 强事务 | 早期弱，现已支持 |

### 2. 一个文档长什么样

```javascript
// 一条客户文档：字段可嵌套、可有数组、可与其他文档不同
{
  _id: ObjectId("..."),
  name: "张三",
  contact: { phone: "1380000", city: "上海" },  // 嵌套对象
  tags: ["vip", "new"],                          // 数组
  orders: [                                      // 内嵌子文档
    { id: 1001, amount: 299 },
    { id: 1002, amount: 158 }
  ]
}
```

在关系库里，这通常要拆成客户表、联系方式表、标签表、订单表四张，查询时连接。文档库把相关的数据放一起，一次读取就拿到全部——这叫数据聚合，是文档模型的重要优势。

### 3. 内嵌与引用

文档建模有个核心决策：关联数据是内嵌进去，还是用引用另存一份？

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 内嵌 | 把子数据放进父文档 | 一次读取、原子更新 | 重复存储、文档可能过大 |
| 引用 | 存对方编号，另存一份 | 不重复、独立更新 | 查询要多次或连接 |

经验法则：一对少、经常一起读、很少单独更新的用内嵌；一对多、数据量大、经常单独访问的用引用。

### 4. MongoDB 的关键机制

- **文档存储**：底层用类似统一资源标记语言里对象格式的二进制编码，读写高效。
- **索引**：支持单字段、复合、多键、地理、文本等多种索引。
- **副本集**：一组节点维护相同数据，自动选主、故障转移。
- **分片集群**：数据按分片键分散到多个分片，支持水平扩展。
- **聚合管道**：类似数据分析的处理流水线，做过滤、分组、转换。

## DB04-02 MongoDB 的复制与分片

### 1. 副本集

副本集是 MongoDB 的高可用基础：一个主节点接收写入，多个从节点复制数据。主节点挂了，从节点自动选举新主。

| 角色 | 职责 |
|---|---|
| 主节点 | 处理所有写请求 |
| 从节点 | 复制数据、可承担读、参与选举 |
| 仲裁节点 | 只投票不存数据，用于凑多数 |

:::figure id=DB04-02-01 | name=副本集的选主 | dir=TB
node n1 "主节点" blue
node n2 "从节点甲" teal
node n3 "从节点乙" amber
node n4 "主节点故障" green
node n5 "从节点选举新主" purple
edge n1 -> n2 "复制数据"
edge n1 -> n3 "复制数据"
edge n1 -> n4 "发生故障"
edge n4 -> n5 "触发选举"
edge n2 -> n5 "参与投票"
edge n3 -> n5 "参与投票"
:::

图中节点速览：n1 主节点向 n2、n3 复制数据；n1 故障（n4）触发 n2、n3 投票选出新主 n5。多数派机制保证不会选出两个主。

### 2. 分片集群

数据量超过单机，就要分片。MongoDB 分片集群由三部分组成：

| 组件 | 作用 |
|---|---|
| 分片 | 真正存数据的节点，每片存一部分 |
| 路由 | 客户端入口，根据分片键把请求转发到正确分片 |
| 配置服务 | 存元信息，记录数据和分片的映射 |

分片键的选择至关重要：好的分片键让数据和请求均匀分布，差的会导致热点集中。分片键一旦选定很难更改，所以设计时要慎重。

### 3. 事务能力演进

早期 MongoDB 只支持单文档原子性，跨文档事务能力弱。较新版本引入了多文档事务，支持副本集和分片集群上的事务，缩小了与关系库的差距。但事务代价高，多数场景仍推荐通过合理的文档建模把相关数据放一起，避免跨文档事务。

## DB04-03 列族数据库

### 1. 什么是列族

列族数据库介于行存和列存之间。它把相关的列归成一个"列族"，同一列族的数据物理上存在一起。它用宽表模型：一张表可以有海量列，行可以各不相同。

| 概念 | 说明 |
|---|---|
| 行键 | 唯一标识一行，数据按它排序 |
| 列族 | 若干相关列的集合，建表时定义 |
| 列限定符 | 列族内的具体列，可动态增加 |
| 单元格 | 行列交叉处的值，带时间戳版本 |

### 2. 数据模型示例

```text
行键      列族"基本信息"        列族"订单"
          name    city          order:1   order:2
user001   张三     上海           299       158
user002   李四     北京           -
user003   王五     -              -         88
```

注意每行可以只有部分列，稀疏存储。这和关系库"每行所有列都要有值（哪怕是空）"完全不同，适合列很多但每行只用其中少量的场景。

### 3. Cassandra 与 HBase

| 维度 | Cassandra | HBase |
|---|---|---|
| 架构 | 去中心化，无单点 | 主从，依赖分布式文件系统和协调服务 |
| 一致性 | 可调，最终一致为主 | 强一致（单行） |
| 扩展 | 线性扩展，加节点即扩 | 靠区域服务器分裂 |
| 模型 | 宽表列族 | 宽表列族 |
| 适合 | 高可用、多地部署 | 海量数据、与大数据生态结合 |

:::figure id=DB04-03-01 | name=Cassandra 的去中心化架构 | dir=TB

### 4. 可调一致性

列族库常提供可调一致性：一次读写要多少个副本确认才算成功。

| 级别 | 含义 | 特点 |
|---|---|---|
| 任一 | 一个副本响应即可 | 最快，可能读到旧数据 |
| 多数 | 过半副本响应 | 平衡 |
| 全部 | 所有副本响应 | 最强一致，最慢 |

这让应用能按场景权衡——用户动态可以接受最终一致（任一），账户余额则要强一致（多数或全部）。

## DB04-04 四大流派横向对比

### 1. 一张表看清区别

| 维度 | 关系型 | 键值 | 文档 | 列族 |
|---|---|---|---|---|
| 数据模型 | 表格行列 | 键到值 | 嵌套文档 | 宽表列族 |
| 查询能力 | 最强，SQL | 仅按键 | 中等，按文档 | 有限，按行键 |
| 事务 | 强 | 通常无 | 单文档到多文档 | 有限 |
| 扩展 | 较难横向 | 容易 | 容易 | 极易 |
| 灵活度 | 低 | 低 | 高 | 中 |
| 典型场景 | 业务系统 | 缓存 | 内容、画像 | 海量写入 |

### 2. CAP 视角下的取舍

用 CAP 定理看这些流派，取舍就更清楚：

| 类型 | 一致性倾向 | 可用性倾向 | 说明 |
|---|---|---|---|
| 关系型 | 强一致 | 相对弱 | 优先保证数据正确 |
| Redis 单机 | 强一致 | 高 | 单节点无分区问题 |
| MongoDB 副本集 | 强一致 | 较高 | 多数派选主保一致 |
| Cassandra | 可调 | 很高 | 默认偏可用性 |

图中节点速览：从 n2 关系型偏一致，到 n3 文档库平衡，再到 n4 列族库偏可用，是一条从"宁可不可用也要一致"到"宁可短暂不一致也要可用"的光谱。选型时先想清楚业务能接受哪一端。

## DB04-05 选型实战

### 1. 按数据特征选

- 数据结构固定、关系清晰、需要复杂查询和强事务 → 关系型。
- 简单读写、追求极致性能、做缓存 → 键值。
- 结构多变、字段不固定、对象整体存取 → 文档。
- 数据量巨大、写入极多、查询模式简单固定 → 列族。
- 关系是核心、要查多跳关联 → 图数据库。

### 2. 一个选型的反例

某团队把所有数据都塞进文档库，因为"灵活"。结果大量跨文档关联查询要靠应用层拼接，事务一致性要自己保证，反而把文档库的短板当成了主战场。教训是：灵活是有代价的，如果你的数据结构其实很固定、关系很清晰，关系库才是更省心的选择。

### 3. 混合搭配是常态

真实系统很少只用一种数据库。典型搭配：

- 关系库存核心交易数据，Redis 做缓存，文档库存用户画像，搜索引擎做全文检索。
- 不同数据放最适合的库，各司其职，这叫多模持久化。

:::figure id=DB04-05-01 | name=一个典型系统的多库搭配 | dir=TB

## DB04-06 本篇小结

NoSQL 不是要取代关系库，而是补齐关系库在某些场景的短板。文档库用灵活的 schema 和内嵌模型换来开发效率与读取性能；列族库用宽表和去中心化架构换来海量写入与高可用；键值库用最简单模型换来极致速度。每一种取舍背后，都是 CAP 与具体业务需求的权衡。

下一篇转向另一类专门场景：分析型数据库与搜索引擎——当需求从"查一条记录"变成"算一千万条数据的统计",数据库会换一套完全不同的武器。
