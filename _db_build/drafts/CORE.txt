# 数据库核心机制深潜：从索引结构到分布式共识

**第一、二篇讲现象与用法，本篇拆到引擎内部——那些决定数据库性能与正确性的底层机制**

## DB02-00 开篇：为什么要深挖机制

### 1. 会用和懂原理之间隔着一层

会用索引的人知道建索引能加速，懂原理的人知道 B+树为什么只需三四层就能定位千万行、为什么范围查询叶子链表比反复回树快、为什么写入会让索引变慢。后者能在没有现成答案时自己推导出正确做法，也能在别人优化不动的地方找到突破口。

本篇挑八个贯穿所有数据库的底层机制，讲清它们"为什么这样设计、怎么工作、代价是什么"。这些机制在 MySQL、PostgreSQL、Redis、MongoDB、分布式数据库里反复出现，是举一反三的关键。

| 机制 | 解决的核心矛盾 | 出现在哪些数据库 |
|---|---|---|
| B+树 | 快速定位与范围扫描 | 几乎所有关系库 |
| LSM 树 | 高写入吞吐与读放大 | HBase、Cassandra、部分新库 |
| 哈希索引 | 等值查询的极致速度 | Redis、内存库 |
| 多版本并发控制 | 读写互不阻塞 | MySQL、PostgreSQL 等 |
| 预写日志 | 性能与持久性 | 几乎所有数据库 |
| 缓冲管理 | 内存快但小、磁盘慢但大 | 所有数据库 |
| 查询优化 | 多种执行路径选最优 | 关系库与分析库 |
| 共识算法 | 多节点如何达成一致 | 分布式数据库 |

## DB02-01 B+树：为什么它是索引之王

### 1. 从二叉搜索树说起

查找一个值，最直观的是二叉搜索树：每个节点分左右，小的往左大的往右。但二叉树有个致命问题——数据量大时树很高，磁盘数据库里每访问一层节点就可能是一次磁盘输入输出，层数多意味着查询慢，而且节点只存一个键，一次读大量数据浪费。

B+树针对磁盘做了三点改造：

- **多叉**：一个节点存很多键，孩子数量多，树变得很矮，通常三四层就能容纳海量数据。
- **数据只在叶子**：内部节点只存键和指针，不存数据，所以一个节点能塞更多键，树更矮。
- **叶子成链**：所有叶子用双向链表串起来，范围扫描时顺着链表走，不用回到根重新查。

### 3. 为什么树这么矮

假设一个节点能存一千个键，三层树就能索引十亿条量级的数据：根节点一千个指针指向一千个内部节点，每个内部节点再指一千个叶子，一千乘一千是一百万个叶子，每个叶子存上千条记录就是十亿。而树的高度只有三——意味着查任意一条记录最多三次节点访问。这些节点常驻内存的话，查询就是纯内存操作，极快。

### 4. B+树的代价

- 写入要维护树的平衡，可能触发节点分裂、合并、旋转，有额外开销。
- 随机写入会让页在磁盘上分散，久了产生碎片，顺序性下降。
- 范围查询很好，但纯等值查询未必比哈希快。

## DB02-02 LSM 树：为写入而生

### 1. 写入密集型场景的挑战

日志、监控、消息这类场景，写入量极大、几乎不更新、很少按主键单行查。B+树的随机写入在这种场景下会产生大量磁盘碎片，吞吐上不去。LSM 树就是为这种"写多读少、顺序为主"的场景设计的。

### 2. LSM 树的核心思想

它把随机写变成顺序写：新数据先进内存的平衡树（叫内存表），内存写满了就顺序刷成磁盘上的一个有序文件（叫有序串）。磁盘上会有多个有序文件，后台不断把它们合并成更大的文件。

### 3. 读放大、写放大与空间放大

LSM 树用"放大"换取写性能，理解三个放大就理解了它的取舍：

| 放大类型 | 含义 | 原因 |
|---|---|---|
| 读放大 | 读一条要查多个文件 | 数据分散在多层文件，可能都要看 |
| 写放大 | 实际写的比逻辑写多 | 同一条数据被反复合并重写 |
| 空间放大 | 占用空间比数据大 | 旧版本未及时清理、临时文件并存 |

布隆过滤器是降低读放大的利器：它能快速判断"某个键肯定不在这个文件里",避免无谓的磁盘读。

### 4. B+树与 LSM 树对比

| 维度 | B+树 | LSM 树 |
|---|---|---|
| 写入 | 随机写，碎片多 | 顺序写，吞吐高 |
| 读取 | 单点读快且稳定 | 可能查多层，读放大 |
| 范围查询 | 叶子链表，高效 | 需多文件归并 |
| 空间 | 较紧凑 | 有三类放大 |
| 适合 | OLTP 均衡读写 | 写密集、日志、大批量 |

## DB02-03 哈希索引：等值的极致

### 1. 哈希索引怎么工作

哈希索引对键算一个哈希值，直接映射到桶的位置，一步定位。它不排序，所以只适合等值查询，不支持范围查询和排序。

node n3 "B+树<br/>逐层比较下探" amber
node n4 "等值查询<br/>哈希更快" green
node n5 "范围查询<br/>只有 B+树支持" purple
edge n1 -> n2 "路径一"
edge n1 -> n3 "路径二"
edge n2 -> n4 "擅长"
edge n3 -> n5 "擅长"
:::

图中节点速览：同样从 n1 查询键出发，n2 哈希一步定位、n3 B+树逐层下探。等值查询 n4 哈希更快，但范围查询 n5 只有 B+树能做，因为它有序。

### 2. 哈希冲突与演进

不同键可能算出相同哈希值，这就是冲突。处理方式有链地址法（一个桶挂一条链）和开放寻址法（往后找空位）。冲突多会拖慢查询，所以哈希函数质量和负载因子很关键。

| 结构 | 冲突处理 | 特点 |
|---|---|---|
| 链地址法 | 桶内挂链表 | 简单，冲突多时链变长 |
| 开放寻址法 | 线性或平方探测空位 | 缓存友好，删除复杂 |
| 可扩展哈希 | 动态分裂桶 | 扩容平滑，实现复杂 |

Redis 的字典、Java 的 HashMap 都是哈希结构的经典实现，理解了冲突处理，看这些源码就顺了。

## DB02-04 多版本并发控制

### 1. 为什么需要多版本

锁能保证正确性，但读写互相阻塞，并发差。多版本并发控制的核心洞见是：读操作看快照、写操作生成新版本，读写从不直接冲突。读不阻塞写、写不阻塞读，只有写写之间才需要协调。

### 2. 版本链与快照

每行数据背后是一条版本链，记录着历次修改。事务开始时拿到一个事务编号，读的时候只看"在它开始之前已提交"的那些版本，后面的版本对它不可见。

### 3. 不同数据库的实现差异

| 数据库 | 实现特点 |
|---|---|
| MySQL InnoDB |  undo 日志链加读视图，聚簇索引内联版本信息 |
| PostgreSQL | 元组上直接存事务编号范围，旧元组留在页里 |
| Oracle | 回滚段存旧版本，一致性读构造块 |

 PostgreSQL 的旧元组留在数据页里，靠后台清理进程（叫 vacuum）回收，这是它运维中特有的一个关注点——清理不及时会导致表膨胀和事务编号回绕问题。

## DB02-05 预写日志：不丢数据的根基

### 1. 日志先行的原则

预写日志有一条铁律：任何对数据的修改，必须先把修改记录写到日志并落盘，之后才能真正改数据。这样任何时刻崩溃，都能靠日志把已提交的改动重做、把没提交的回滚。

为什么不能先改数据？因为改数据是随机写，可能改到一半断电造成页损坏；而日志是顺序追加写，又快又安全。用小成本的顺序写，换取大成本的数据页一致性，这是核心权衡。

### 3. 检查点

如果每次恢复都要从头重放所有日志，恢复时间会很长。检查点机制定期把内存中的脏页刷到磁盘，并记录"这个点之前的事务都已经落盘"。恢复时只需重放检查点之后的日志，大大缩短恢复时间。这是恢复时间目标这个指标的关键支撑。

## DB02-06 缓冲管理：让内存替磁盘干活

### 1. 缓冲池的作用

磁盘比内存慢几个数量级，所以数据库把热点数据页放在内存的缓冲池里。读页先在缓冲池找，命中直接返回；写页先改缓冲池里的副本，后台再刷盘。命中率直接决定性能。

### 2. 页面置换算法

缓冲池满了要腾出空间，选哪个页淘汰？

| 算法 | 思路 | 评价 |
|---|---|---|
| 最近最少使用 | 淘汰最久没访问的 | 常用，有专门实现优化 |
| 先进先出 | 淘汰最早进来的 | 简单，可能误伤热点 |
| 时钟算法 | 近似最近最少使用 | 开销小，工程常用 |

数据库通常不用教科书上的朴素最近最少使用，而是做改良——比如 InnoDB 用改进的时钟算法，把脏页和干净页分开考虑，优先淘汰干净页（不用刷盘）。

### 3. 双写缓冲与页完整性

缓冲池里的脏页刷盘时，如果只写一半就断电，磁盘页会损坏——这叫部分页写入。双写缓冲的解法是：先把页写到一个临时区域，写完整了再写到真正位置。这样任何时刻崩溃，真正位置要么是完整的旧页、要么是完整的新页，不会出现半个页。

## DB02-07 查询优化器

### 1. 优化器要解决什么

一条 SQL 有多种执行方式。三张表连接有六种连接顺序，每种又能选不同连接算法和索引，组合起来是天文数字。优化器要在合理时间内估算各种方案的代价，选一个足够好的。

### 2. 代价估算

代价主要由三部分构成：

- **输入输出代价**：要读多少页，是否命中缓冲。
- **中央处理器代价**：比较、排序、哈希计算的开销。
- **内存与网络代价**：排序哈希需要的内存、分布式场景的数据传输。

估算依赖统计信息：表有多少行、列的取值分布、索引的选择性。统计信息不准，代价估算就偏，计划就可能选错——这就是为什么数据大变之后要更新统计信息。

### 3. 连接算法

| 算法 | 思路 | 适合 |
|---|---|---|
| 嵌套循环 | 外层一行内层全找 | 小外表、内表有索引 |
| 哈希连接 | 建哈希表再探测 | 大表等值连接 |
| 排序合并 | 两边排序后归并 | 已排序或范围连接 |

## DB02-08 分布式共识

### 1. 为什么需要共识

单机数据库保证事务靠本地日志和锁。一旦数据复制到多台机器，就要回答：谁是主、某条日志是否被多数节点接受、主库挂了谁接任。这些问题的答案是同一个：让多个节点对某个值达成一致，这就是共识问题。

### 2. raft 的核心机制

raft 是工程中最常用的共识算法，它把问题拆成几个子问题：选主、日志复制、安全性。

| 机制 | 做法 |
|---|---|
| 选主 | 节点有跟随者、候选者、领导者三种角色，超时发起选举，多数票当选 |
| 任期 | 每轮选举有一个任期号，旧任期消息被忽略 |
| 日志复制 | 领导者接收写请求，复制到多数节点后提交 |
| 心跳 | 领导者定期发心跳维持权威，跟随者超时未收到就重新选举 |

:::figure id=DB02-08-01 | name=raft 选主与日志复制 | dir=TB

node n2 "发起投票<br/>争取多数票" teal
node n3 "当选领导者<br/>开始发心跳" amber

node n5 "多数确认后提交<br/>保证一致" purple

图中节点速览：从 n1 跟随者超时到 n2 拉票、n3 当选、n4 复制日志、n5 多数确认后提交，是一条完整的选主加复制链路。多数派机制保证任一时刻只有一个合法领导者，也保证已提交的日志不会被覆盖。

### 3. 多数派的意义

为什么是多数而不是全部？因为节点可能宕机。只要超过半数节点活着，系统就能选出主、能提交写入；少数派节点的数据可能落后，但不能擅自做主。这就是为什么分布式系统常说"奇数个节点"——三节点能容忍一节点故障，四节点也只能容忍一节点故障，性价比不如三节点。

### 4. Paxos 与 Raft 的关系

Paxos 是更早的共识算法，理论严谨但难以理解和实现。raft 的设计目标就是可理解性，它把共识拆解成清晰的模块，工程实现更友好。现代分布式数据库多采用 raft 及其变体，少数用 Paxos 或自研改进。

## DB02-09 本篇小结：机制如何串起来

把八大机制放回一次完整的写请求里，它们是这样协作的：连接层收到 SQL（上一篇的架构），优化器选计划（DB02-07），执行引擎按 B+树或哈希索引定位（DB02-01、DB02-03），多版本机制保证读写不冲突（DB02-04），锁协调写写冲突（上一篇），修改先进缓冲池（DB02-06），预写日志先行保证持久（DB02-05），如果是分布式库还要走共识复制（DB02-08），写密集的表可能用 LSM 树（DB02-02）。
