# 分布式数据库与分库分表精讲

**当单机撑不住——从应用层的分库分表到数据库内部的分布式架构，如何在扩展的同时保住事务能力**

## DB06-00 开篇：为什么要分布式

### 1. 单机天花板

任何单机数据库都有极限：磁盘容量有限、内存有限、中央处理器核数有限、连接数有限。数据量从千万涨到十亿、并发从几百涨到几万时，换更强的机器（纵向扩展）会越来越贵，最终无机器可换。唯一的出路是加机器——横向扩展。

但把数据分散到多台机器，会引出一系列难题：

- 数据怎么分？分片键怎么选才不热点？
- 跨机器的查询怎么做？连接、排序、聚合怎么办？
- 跨机器的事务怎么保证原子性？
- 机器故障怎么办？数据不丢、服务不停？
- 全局唯一编号怎么生成？

### 2. 两条路线

| 路线 | 代表 | 思路 | 特点 |
|---|---|---|---|
| 应用层分库分表 | 中间件加关系库 | 应用改造，自己管分片 | 灵活，改造成本高 |
| 分布式数据库 | 分布式数据库产品 | 数据库内建分片与事务 | 对应用透明，能力强大 |

## DB06-01 分库分表

### 1. 垂直拆分与水平拆分

分库分表有两种基本方向：

- **垂直拆分**：按业务把表分到不同库（分库），或把宽表按列拆成几张表（分表）。比如用户库、订单库、商品库分开。
- **水平拆分**：把同一张表的数据按规则分散到多张表或多个库。比如订单表按用户编号取模分成十六张。

| 拆分 | 做法 | 解决 | 局限 |
|---|---|---|---|
| 垂直分库 | 按业务拆库 | 分担压力、隔离故障 | 单表仍可能太大 |
| 垂直分表 | 按列拆表 | 减少单行宽度 | 查询要连接 |
| 水平分表 | 按行拆表 | 突破单表容量 | 跨片查询复杂 |
| 水平分库 | 按行拆到多库 | 突破单机容量 | 事务与连接更难 |

### 2. 分片键的选择

水平拆分最关键的决定是选哪个字段做分片键。好的分片键要让数据和查询都均匀分散。

| 分片方式 | 例子 | 优点 | 缺点 |
|---|---|---|---|
| 取模 | 用户编号取模十六 | 分布均匀 | 范围查询要查所有片 |
| 按范围 | 按订单日期分月 | 范围查询高效 | 可能热点集中 |
| 按哈希 | 一致性哈希 | 扩容迁移少 | 实现复杂 |
| 按地区 | 按省份分 | 业务贴合 | 分布可能不均 |

分片键的两个大忌：一是区分度太低（如性别、状态），会导致数据倾斜；二是和主要查询条件无关，导致大多数查询要广播到所有分片。

### 3. 分库分表带来的难题

- **跨片连接与排序**：原本一条连接查询，现在数据分散在多台，要么在中间件层汇总，要么避免跨片关联。
- **全局唯一编号**：自增编号在多片会冲突，需要分布式编号方案，如雪花算法。
- **分布式事务**：一个事务跨多片，要保证原子性。
- **扩容迁移**：片数变化要迁移大量数据，取模分片尤其痛苦。
- **分页与聚合**：跨片分页要归并排序，深分页代价高。

## DB06-02 分片中间件

### 1. 中间件做什么

分库分表中间件位于应用和数据库之间，替应用屏蔽分片细节。应用照旧写结构化查询语言，中间件解析后按分片规则路由到正确的物理库表，再把结果汇总返回。

| 功能 | 说明 |
|---|---|
| SQL 解析 | 看懂查询涉及哪些分片键 |
| 路由 | 把请求发到目标分片 |
| 读写分离 | 写走主库、读走从库 |
| 结果归并 | 汇总多片结果，做排序分页聚合 |
| 分布式事务 | 协调跨片事务 |
| 全局编号 | 生成分布式唯一编号 |

### 2. 中间件的两种形态

- **代理模式**：独立部署的代理服务，应用像连普通数据库一样连它。对应用透明，但多一跳网络。
- **客户端模式**：以库的形式嵌在应用里，由客户端库做路由。少一跳、性能好，但与应用语言绑定。

### 3. 分片带来的限制

即使有中间件，有些查询仍然受限：跨片连接性能差、跨片事务复杂、某些结构化查询语言特性不支持。所以分库分表后，往往要调整数据模型和查询方式，尽量让查询落在单一分片内——这也是为什么分片键要贴合主要查询模式。

## DB06-03 分布式数据库

### 1. NewSQL 的崛起

分库分表把复杂性推给了应用和中间件，开发和运维成本高。于是出现了一类新数据库：内部实现分片、复制、事务，对外提供标准接口，让应用像用单机数据库一样用分布式能力。这类数据库常被称为分布式数据库或NewSQL。

| 特性 | 说明 |
|---|---|
| 水平扩展 | 加节点即扩容量和性能 |
| 强一致事务 | 跨分片也保证事务 |
| 对应用透明 | 无需手写分片逻辑 |
| 高可用 | 故障自动切换 |
| 兼容 SQL | 降低迁移成本 |

### 2. 整体架构

分布式数据库通常分成三层：负责接入和查询协调的计算层、负责数据和事务的存储层、负责元数据与调度的管理层。

### 3. 分布式事务

跨分片事务是分布式数据库最难的部分。常见方案：

- **两阶段提交**：协调者先问所有参与者能否提交，都同意再提交。简单但协调者故障会阻塞。
- **三阶段提交**：加询问阶段减少阻塞。
- **基于共识的事务**：用raft等算法在分片内达成一致，跨分片再协调。
- **乐观事务**：先执行，提交时检测冲突，冲突则重试。冲突少时性能好。

| 方案 | 一致性 | 性能 | 复杂度 |
|---|---|---|---|
| 两阶段提交 | 强 | 较低 | 中 |
| 三阶段提交 | 强 | 较低 | 高 |
| 乐观事务 | 强 | 冲突少时高 | 中 |

### 4. 分布式查询

一条跨分片查询的执行过程：计算层解析后生成分布式执行计划，把子任务下推到相关分片就近执行，收集中间结果再做二次聚合或排序连接返回。关键优化是尽量把计算下推到数据所在节点，减少网络传输的数据量。

```sql
-- 应用无需关心数据在哪个分片，照常写 SQL
SELECT region, SUM(amount) FROM orders
WHERE created_at >= '2026-01-01'
GROUP BY region;
-- 分布式数据库自动：定位相关分片 → 下推聚合 → 汇总二次聚合
```

## DB06-04 CAP 与一致性再深入

### 1. CAP 不是简单三选二

基础篇说过 CAP 三选二，但更准确的理解是：网络分区是客观存在、无法避免的，所以真正的取舍是在分区发生时，选一致性还是可用性。

| 选择 | 分区时的行为 | 代表 |
|---|---|---|
| 重一致性 | 无法保证一致的节点拒绝服务 | 强一致分布式数据库 |
| 重可用性 | 各节点继续服务，数据可能不一致 | 高可用 NoSQL |

### 2. BASE 与最终一致

BASE 是基本可用、软状态、最终一致的缩写。它承认中间状态的存在，只要经过一段时间所有副本收敛到一致。很多互联网系统接受这个模型，用异步复制、读修复、反熵等机制达成最终一致。

### 3. 一致性的层次

| 层次 | 含义 |
|---|---|
| 强一致 | 写完立刻读一定能读到最新 |
| 因果一致 | 有因果关系的操作保证顺序 |
| 读己之写 | 用户自己写的自己能读到 |
| 最终一致 | 无新写入时最终会一致 |

不同业务对一致性要求不同：账户余额要强一致，朋友圈点赞最终一致就够。设计时要按数据的重要性分层处理。

## DB06-05 全局唯一编号

分库分表后，数据库自增编号会冲突，需要分布式编号方案。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 数据库号段 | 每次取一段缓存本地 | 简单有序 | 依赖数据库 |
| 雪花算法 | 时间戳加机器号加序列号 | 本地生成、有序 | 依赖时钟 |
| 通用唯一识别码 | 随机生成 | 无依赖 | 无序、占空间 |

图中节点速览：n1 到 n4 拼成一个长整数编号。时间戳保证大致有序，机器标识避免不同节点冲突，序列号处理同一毫秒内的多条。主要风险是时钟回拨，实现时要处理。

## DB06-06 选型实战

### 1. 什么时候分库分表，什么时候上分布式数据库

| 情况 | 建议 |
|---|---|
| 数据量中等、查询简单 | 单机加读写分离 |
| 数据量很大、团队有中间件经验 | 分库分表 |
| 数据量大、要强一致事务、想少改造 | 分布式数据库 |
| 以分析为主 | 分析型数据库或数仓 |
| 场景简单、只要高可用 | 主从加哨兵 |

### 2. 迁移的代价

无论哪种方案，从单机迁到分布式都是大工程：数据迁移、双写校验、灰度切换、回滚预案都要齐备。分片键一旦定错，后期调整代价极高。所以最好的策略是：在设计初期就预估未来规模，留有扩展余地，不要等到撑不住了才临时拆分。

### 3. 本篇小结

分布式数据库的目标是让"扩展"这件事对应用透明。分库分表是应用层的手工方案，灵活但复杂；分布式数据库把复杂性内建到系统中，代价是架构更重。两者都在回答开篇那四个问题：怎么分片、怎么跨片查询、怎么跨片事务、怎么容错。理解这四个问题，就理解了所有分布式数据库的设计动机。
