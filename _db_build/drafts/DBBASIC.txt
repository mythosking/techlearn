# 数据库基础知识总纲：从一张表到一套系统

**本系列入口篇——先建立直觉，再讲清数据库到底在做哪些事，最后给一张全景速查表**

## DB00-00 小白导读：从一本通讯录说起

### 1. 先别背名词，从记这件事说起

假设你手上有一家公司的客户信息：姓名、电话、公司、欠款金额。最简单的办法是记在一个本子上，一行一个客户。客户多了以后，问题来了：怎么快速找到"张三"？怎么防止两个人把同一条记录改错？怎么在断电后保证账本不丢？怎么让财务和销售同时看这份数据又不互相覆盖？

数据库就是为了解决这一类问题而生的。它本质上是一个**能高速查询、能安全并发修改、能在故障后恢复的超级账本**。你看到的那些名词——表、索引、事务、主从复制——全都是在回答上面这四个问题中的一个或几个。

把四个问题记住，后面的知识就都能挂上去：

- 找得快不快 → 索引、查询优化
- 改得对不对 → 事务、并发控制、锁
- 坏了丢不丢 → 日志、备份、恢复
- 人多了撑不撑得住 → 复制、分片、分布式

### 2. 三个必须先建立的概念

**数据是表，表是行和列。** 数据库里最常见的形态就是一张二维表，和电子表格很像。一列是一种属性（比如"电话"），一行是一条记录（比如"张三"这一家）。表让人能用一个统一的结构描述一大堆相似的东西。

**结构化查询语言是提问的方式。** 你不用告诉数据库"先去第几行翻、再比对字符串"，只要说"把欠款大于一万的客户按金额排序"——这种声明式的提问语言就是 SQL。数据库自己决定怎么最快地找出答案。这是数据库和普通程序的分水岭：你说要什么，它来决定怎么做。

**事务是可靠记账的承诺。** 转账时，从 A 账户扣钱和给 B 账户加钱必须一起成功或一起失败，绝不能扣了不加。这种"要么全做、要么全不做"的保证就叫事务。它是数据库区别于普通文件最重要的能力之一。

### 3. 为什么不能直接用文件

你可能会说，用电子表格文件不也能存数据吗？小规模确实够用，但一旦多人、多量、多系统，文件就撑不住了。

| 对比维度 | 直接用文件 | 用数据库 |
|---|---|---|
| 查询速度 | 从头一行行找，数据多了很慢 | 有索引，千万条也能毫秒级定位 |
| 并发修改 | 两人同时改容易互相覆盖 | 事务隔离，各改各的互不干扰 |
| 数据安全 | 程序崩溃可能写到一半 | 日志保证要么全成要么回退 |
| 数据一致 | 约束靠人自觉，容易出错 | 主键、外键、唯一性由系统强制 |
| 权限管理 | 要么全看得见要么全看不见 | 精确到表和字段的权限控制 |
| 规模扩展 | 单文件上限明显 | 可分库分表、可集群横向扩展 |

一句话：文件只负责"存",数据库还负责"管"——管查询、管并发、管安全、管一致性。

## DB00-01 数据库到底是什么

### 1. 数据库与数据库管理系统

日常说的"数据库"其实有两种含义，严格时要分开：数据库是**按一定结构组织、集中存放的数据集合**，数据库管理系统是**创建、维护、使用这个集合的软件**。前者是仓库里的货，后者是仓库和管仓库的人。

数据库管理系统有四个核心职责：

- **定义数据**：规定有哪些表、每表有哪些列、列是什么类型、有什么约束。
- **存取数据**：插入、删除、修改、查询，并且要快。
- **保证正确**：并发访问时不乱、故障之后不丢、约束不被破坏。
- **管理运维**：用户权限、备份恢复、性能监控、扩容迁移。

### 2. 一个数据库系统的组成

从使用者到磁盘，一套数据库系统大致分成几层。理解这个分层，后面所有的专篇都能对号入座。

### 3. 数据库发展简史

知道一点来龙去脉，能理解为什么现在有这么多类型的数据库。

| 阶段 | 年代 | 代表 | 解决了什么 |
|---|---|---|---|
| 层次与网状数据库 | 1960年代 | 早期大型机系统 | 第一次把数据和程序分开，但结构僵硬 |
| 关系数据库 | 1970年代起 | 关系模型、后续商用品 | 用表格和 SQL，结构清晰、好查询 |
| 对象数据库 | 1990年代 | 面向对象数据库 | 想让对象和表直接对应，未成主流 |
| 开源关系数据库 | 2000年代 | MySQL、PostgreSQL | 免费、好用，互联网公司大规模采用 |
| NoSQL 浪潮 | 2010年代 | Redis、MongoDB、HBase | 应对海量数据和高并发，放宽一致性 |
| 分布式与新分析 | 2010年代后期 | 分布式数据库、列式分析库 | 既要扩展又要事务，或极致分析性能 |
| 云与向量时代 | 2020年代 | 云原生数据库、向量数据库 | 弹性伸缩、人工智能检索场景 |

可以看到，每一次新类型的出现，都是因为旧的数据库在某个新场景下"不够用了"。记住这条规律，后面理解每种数据库的定位就顺了。

## DB00-02 数据模型：数据库的五大流派

### 1. 什么是数据模型

数据模型决定了"数据以什么结构组织、以什么方式关联"。它是数据库的地基， SQL 方言、索引方式、扩展能力都由它派生。理解一种数据库，先看它用的是哪种模型。

### 2. 五大主流模型

| 模型 | 组织方式 | 一个直观比喻 | 代表产品 |
|---|---|---|---|
| 关系模型 | 二维表，行和列 | 一张规整的 Excel 表 | MySQL、PostgreSQL、Oracle |
| 键值模型 | 键对应值 | 一个大字典，按键取值 | Redis、Memcached |
| 文档模型 | 类似文档的嵌套结构 | 一摞可以各不相同的 JSON 文件 | MongoDB、Elasticsearch |
| 列族模型 | 按列族存放的超宽表 | 按列分块存的大表格 | Cassandra、HBase |
| 图模型 | 节点和边 | 一张关系网络图 | Neo4j |

### 3. 关系模型为什么长期占主导

关系模型有个关键优点：它用数学上的关系理论做基础，配合 SQL 这种声明式语言，让使用者不用关心数据物理上怎么存。一条查询能自动利用索引、自动选择连接方式，这在早期是革命性的。

它的三个核心概念要记牢：

- **表（关系）**：一个二维结构，整洁、无冗余地描述一类事物。
- **行（元组）**：表里的一个具体记录。
- **列（属性）**：所有行共有的一项特征，有明确的数据类型。

关系模型强调"结构化"和"少冗余",这让数据一致性容易保证，代价是面对千变万化的半结构化数据时不够灵活——这正是后来文档数据库兴起的原因。

## DB00-03 关系模型与 SQL 基础

### 1. 表、行、列与约束

一张规范的表，除了行列，还有几条约束在起作用：

| 约束 | 作用 | 生活比喻 |
|---|---|---|
| 主键 | 唯一标识一行，不能重复不能空 | 身份证号 |
| 外键 | 引用另一张表的行 | 订单上写的客户编号 |
| 唯一约束 | 这一列的值不能重复 | 手机号不能重复注册 |
| 非空约束 | 这一列必须有值 | 姓名不能留空 |
| 检查约束 | 值必须满足条件 | 年龄必须大于零 |
| 默认值 | 不填时自动填的值 | 状态默认是正常 |

这些约束不是写在程序里的检查，而是由数据库强制执行，任何入口写入都绕不过去。这是"数据一致由系统保证"的具体体现。

### 2. SQL 的四大类语句

SQL 按用途分成四类，掌握这个分类就不会觉得 SQL 杂乱。

| 类别 | 全称 | 常用关键字 | 作用 |
|---|---|---|---|
| 数据定义 | DDL | 创建、修改、删除表结构 | 定结构 |
| 数据操纵 | DML | 插入、更新、删除数据 | 改数据 |
| 数据查询 | DQL | 查询 | 查数据 |
| 数据控制 | DCL | 授权、回收权限 | 管权限 |

下面是一段最基础的建表和增删改查示例，用的是通用 SQL 写法，各家数据库大体一致。

```sql
-- 建一张客户表
CREATE TABLE customer (
  id INT PRIMARY KEY,
  name VARCHAR(64) NOT NULL,
  phone VARCHAR(20) UNIQUE,
  debt DECIMAL(10,2) DEFAULT 0
);

-- 插入一行
INSERT INTO customer (id, name, phone, debt) VALUES (1, '张三', '1380000', 12000);

-- 查询欠款过万的客户，按金额降序
SELECT name, debt FROM customer WHERE debt > 10000 ORDER BY debt DESC;

-- 更新与删除
UPDATE customer SET debt = 0 WHERE id = 1;
DELETE FROM customer WHERE id = 2;
```

关键字是英文，注释说明了每句在做什么——先看懂逻辑，不必纠结语法细节。理解"建表、插入、查询、更新、删除"这五件事，就掌握了 SQL 的骨架。

### 3. 查询的三个高级动作

实际查询很少只查一张表，常用的三个高级动作要认识：

- **连接**：把两张表按某个共同字段拼起来。比如订单表里只有客户编号，要显示客户姓名，就得和客户表连接。
- **分组聚合**：按某列分组后做统计，比如"每个客户的总欠款"。
- **子查询**：把一个查询的结果当作另一个查询的输入。

```sql
-- 连接：订单表拼上客户姓名
SELECT c.name, o.amount FROM orders o JOIN customer c ON o.customer_id = c.id;

-- 分组聚合：每个客户的总欠款
SELECT customer_id, SUM(amount) AS total FROM orders
  GROUP BY customer_id HAVING SUM(amount) > 10000;
```

这三个动作是分析类查询的基石，也是后面讲"查询优化"时最常遇到的操作。

## DB00-04 事务与 ACID

### 1. 什么是事务

事务是一组操作组成的逻辑整体，这组操作要么全部生效，要么全部不生效。最经典的例子还是转账：A 减一千和 B 加一千，必须绑在一起。如果扣完钱系统崩了、加钱没执行，那这钱就凭空消失了——事务机制要杜绝这种事。

事务的边界由两条语句划定：开始事务、提交或回滚。提交表示全部生效，回滚表示全部撤销。

```sql
BEGIN TRANSACTION;
UPDATE account SET balance = balance - 1000 WHERE id = 'A';
UPDATE account SET balance = balance + 1000 WHERE id = 'B';
COMMIT;  -- 到这里两项修改才一起生效
-- 如果中途出错则执行 ROLLBACK; 两项修改都不生效
```

### 2. ACID 四条保证

事务的可靠性用四个字母概括，这是数据库最核心的承诺。

| 特性 | 英文 | 含义 | 大白话 |
|---|---|---|---|
| 原子性 | Atomicity | 事务要么全做要么全不做 | 转账不能只扣不加 |
| 一致性 | Consistency | 事务前后数据都满足约束 | 余额不能变成负数 |
| 隔离性 | Isolation | 并发事务互相不干扰 | 两个人同时转也不会串 |
| 持久性 | Durability | 提交后即使断电也不丢 | 记到账本上就擦不掉 |

### 3. 事务的生命周期

一个事务从开始到结束，状态是单向流动的。

| 状态 | 含义 | 下一步 |
|---|---|---|
| 活动中 | 正在执行操作 | 继续或触发回滚 |
| 部分提交 | 操作都执行完，还没真正落定 | 等待提交决定 |
| 失败 | 检测到错误，无法继续 | 必须回滚 |
| 已中止 | 回滚完成，数据回到原样 | 结束 |
| 已提交 | 修改永久生效 | 结束 |

一旦进入已提交，就再也不能回滚；一旦进入已中止，所有修改作废。这条单向性保证了事务结果的确定性。

## DB00-05 并发控制与隔离级别

### 1. 并发会带来什么问题

如果所有人排队一个个执行事务，世界很安全但也很慢。数据库为了让多个事务同时进行，必须处理并发带来的三类典型问题。

| 现象 | 含义 | 一个具体场景 |
|---|---|---|
| 脏读 | 读到别人还没提交的数据 | 对方转账中途回滚，你却按那个数算了 |
| 不可重复读 | 同一事务内两次读同一行结果不同 | 你两次查余额，中间被人改了 |
| 幻读 | 同一事务内两次查一批行，行数变了 | 你统计订单数，中间有人新增订单 |

### 2. 四种隔离级别

隔离级别就是"允许并发到什么程度、容忍哪类问题"的档位。档位越高越安全，但并发性能越低。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|---|---|---|---|---|
| 读未提交 | 可能发生 | 可能发生 | 可能发生 | 最高 |
| 读已提交 | 不会发生 | 可能发生 | 可能发生 | 较高 |
| 可重复读 | 不会发生 | 不会发生 | 可能发生 | 中等 |
| 串行化 | 不会发生 | 不会发生 | 不会发生 | 最低 |

:::figure id=DB00-05-01 | name=隔离级别与并发问题的关系 | dir=TB

node n3 "可重复读<br/>再挡不可重复读" amber
node n4 "串行化<br/>全都挡住" green
edge n1 -> n2 "提升一级"
edge n2 -> n3 "提升一级"
edge n3 -> n4 "提升一级"
:::

图中节点速览：从 n1 到 n4 隔离越来越强、越来越安全，代价是并发越来越低。多数数据库默认在"读已提交"或"可重复读",就是在安全和性能之间取的折中。

### 3. 两种实现手段

数据库靠两种手段实现隔离，理解它们就能明白为什么高隔离级别慢。

- **锁**：写数据前先上锁，别人想改就得等。像会计室的保险柜，一次只让一个人进去改账。实现简单，但等待会降低并发。
- **多版本并发控制**：每次修改生成一个新版本，读的人看自己该看的那个版本，读写互不阻塞。像账本每笔改动都留一页，你看旧的那页不影响别人写新的一页。并发高，但要额外存版本、做清理。

现代数据库多为两者结合：读多写少的场景用多版本并发控制提升并发，真正冲突的写操作用锁或版本检测保证正确。

## DB00-06 索引：为什么查询能这么快

### 1. 索引就是书的目录

在一本一千页的书里找"事务"这个词，你不会从第一页翻起，而是翻到目录看它在哪一页。索引就是数据库表的目录：它把某一列的值和对应行的位置预先排好序、存起来，查询时先查目录再直接定位到行。

没有索引时，数据库只能一行行扫全表；有索引时，它像查字典一样几步就定位。这就是千万条数据也能毫秒级查出的原因。

### 2. B+树：索引的主流结构

关系数据库最常用的索引结构是 B+树。它把键值按顺序组织成一棵多层的平衡树，所有数据都在最底层叶子节点，并且叶子之间用链表连起来。

node n4 "叶子节点<br/>存键和行位置" amber
node n5 "叶子节点<br/>存键和行位置" amber

edge n1 -> n3 "走右边"
edge n2 -> n4 "继续找"
edge n3 -> n5 "继续找"

:::

图中节点速览：n1 是根，n2 和 n3 是中间层，n4 和 n5 是存真实数据的叶子，n6 表示叶子之间连成链表。查找时从根往下走三四层就能定位，树的高度很低，所以再大的表查询步数也不多。叶子连成链表让" Between 某个范围"这类查询能顺着链表一口气读完。

### 3. 索引的几种类别

| 类别 | 特点 | 适用场景 |
|---|---|---|
| 普通索引 | 只加速查找 | 经常作为查询条件的列 |
| 唯一索引 | 额外保证值不重复 | 手机号、邮箱 |
| 主键索引 | 唯一且非空，行按它聚集 | 每行标识 |
| 联合索引 | 多个列组合成一个索引 | 多条件组合查询 |
| 聚簇索引 | 索引和数据存一起，顺序一致 | 主键，范围查询快 |
| 非聚簇索引 | 索引里只存行位置 | 普通查询列 |

### 4. 索引不是越多越好

索引加速查询，但有代价，这是新手最容易踩的坑。

- **占空间**：每个索引都是一份额外的数据结构，大表上索引可能比数据还大。
- **拖慢写入**：插入、更新、删除时索引也要同步维护，索引越多写越慢。
- **优化器可能选错**：索引太多会让优化器估算困难，反而选出慢计划。

所以索引的原则是：给真正高频的查询条件建，给区分度高的列建（比如"性别"这种只有两个值的列建索引意义不大），并且定期排查从没被用过的冗余索引。

## DB00-07 存储引擎与数据落盘

### 1. 存储引擎做什么

存储引擎是数据库里真正负责"把数据存到磁盘、从磁盘读出来"的部件。它决定数据怎么组织、索引怎么实现、事务怎么落地。同一个数据库可以换不同存储引擎，就像同一辆车可以换不同轮胎。

### 2. 行存与列存

这是两种根本不同的存放方式，直接决定数据库适合做什么。

| 对比 | 行存 | 列存 |
|---|---|---|
| 存放方式 | 一行的数据挨着存 | 一列的数据挨着存 |
| 擅长 | 增删改、取整行 | 大批量统计某几列 |
| 典型场景 | 下单、转账等日常业务 | 报表、分析、聚合 |
| 代表 | MySQL 的行存引擎 | 各类分析型数据库 |

一句话记忆：**交易用行存、分析用列存**。想取一个客户的全部信息，行存一次读完；想算一百万订单的金额总和，列存只扫金额那一列，效率高得多。

### 3. 页、缓冲池与预写日志

数据最终存在磁盘上，但磁盘很慢，数据库用了三招来平衡速度与安全。

- **页**：磁盘读写以固定大小的"页"为单位，比如每页十六千字节。索引和数据都按页组织，一次读写一批，减少磁盘次数。
- **缓冲池**：把热点页留在内存里，读写先走内存，命中就直接返回，找不到再去磁盘。内存比磁盘快几个数量级，命中率是关键指标。
- **预写日志**：修改数据时，先把"我要改什么"记到日志里，再改内存和磁盘。这样即使中途断电，也能靠日志把没落盘的改动重做一遍，保证持久性。这就是前面说的原子性和持久性的实现基础。

## DB00-08 查询是怎么执行的与优化

### 1. 一条 SQL 的旅程

你写下一条查询，数据库内部要走好几步才把结果给你。理解这个流程，才知道"优化"优化的是什么。

| 步骤 | 做什么 | 类比 |
|---|---|---|
| 连接建立 | 校验身份、建立会话 | 进门前先刷卡 |
| 解析 | 检查语法、转成内部结构 | 把句子拆成词并看懂 |
| 语义分析 | 检查表、列是否存在，权限够不够 | 确认你说的东西都存在 |
| 优化 | 生成多种执行方案，挑最省的 | 规划几条路线选最快 |
| 执行 | 调用存储引擎读取、计算、返回 | 按路线实际走一趟 |

### 2. 执行计划

优化器输出的就是执行计划：先读哪张表、用哪个索引、怎么连接、怎么排序。同一条 SQL 的不同写法可能生成完全不同的计划，性能差几十倍。

数据库提供查看执行计划的工具（常见关键字是"解释"加查询语句），它会列出每一步的估算代价。学会看执行计划，是从会用数据库到会用好数据库的分水岭。重点看三件事：有没有按预期用上索引、有没有发生全表扫描、连接顺序和方式是否合理。

### 3. 优化器在优化什么

优化器本质上是在一堆等价方案里选总代价最低的那个。它主要权衡：

- **访问路径**：走索引还是全表扫描？小表全扫可能比走索引还快。
- **连接方式**：两表连接是先扫 A 再查 B，还是先扫 B 再查 A？顺序直接影响中间结果大小。
- **是否利用索引排序**：如果索引顺序正好符合要求，就能省掉一次排序。

node n2 "生成方案甲<br/>走索引" teal
node n3 "生成方案乙<br/>全表扫描" teal
node n4 "估算各自代价" amber

图中节点速览：n1 是一条查询，n2 和 n3 是两种候选方案，n4 估算代价，n5 选出最优方案。优化器并不总是对的——它依赖统计数据估算，数据分布变了却没更新统计信息，就可能选错计划，这就是为什么有时需要手动干预或更新统计。

## DB00-09 范式与表结构设计

### 1. 为什么要讲范式

同样是存订单数据，有人把所有信息塞进一张大表，有人拆成客户表、订单表、商品表几张。哪种好？范式就是一套判断"表设计得好不好"的标准，目标是减少重复数据、避免更新异常。

### 2. 三大范式

| 范式 | 要求 | 违反的后果 | 通俗记法 |
|---|---|---|---|
| 第一范式 | 每列都是不可再分的原子值 | 一个格子里塞多个值没法查 | 列要拆到最小 |
| 第二范式 | 非主键列完全依赖整个主键 | 部分依赖造成冗余 | 别只依赖主键的一半 |
| 第三范式 | 非主键列不传递依赖主键 | 改一处要改很多行 | 别间接依赖 |

:::figure id=DB00-09-01 | name=三大范式的递进关系 | dir=LR
node n1 "第一范式<br/>列不可再分" blue
node n2 "第二范式<br/>消除部分依赖" teal
node n3 "第三范式<br/>消除传递依赖" amber
edge n1 -> n2 "先满足"
edge n2 -> n3 "再满足"
:::

图中节点速览：三个范式层层递进，满足第三范式通常要先满足前两个。实际设计中一般做到第三范式就够，再高的范式理论意义大于工程价值。

### 3. 反范式：故意留冗余

范式减少冗余，但过度规范化会让查询要连接很多张表，变慢。于是有了反范式：为了查询性能，故意保留一些冗余字段。比如订单表里冗余存一份客户姓名，查订单时就不用每次都连客户表。

这是一场权衡：用一点存储空间和"改动要同步多处的麻烦",换查询速度。数据仓库和分析场景常用反范式，因为那里几乎只查不改。设计时要根据读写比例决定。

### 4. 表设计的实用建议

- 主键尽量用无业务含义的自增编号或全局唯一标识，避免用会变的业务字段。
- 字段类型选刚好够用的，能用整数不用文本，能定长不定长。
- 高频查询条件建索引，但控制索引数量。
- 大字段（长文本、二进制）考虑单独拆表，避免拖慢主表查询。
- 预留必要的审计字段，比如创建时间、更新时间。

## DB00-10 复制、分区与分片

当一台机器撑不住时，有两条路：纵向扩展（换更强的机器）和横向扩展（加更多机器）。数据库之所以能支持海量规模，靠的是后面这套横向扩展的机制。

### 1. 主从复制

把一份数据同时存到多台机器：一台主库负责写入，多台从库同步主库的数据、负责读取。

| 角色 | 职责 | 好处 |
|---|---|---|
| 主库 | 处理写操作 | 写集中，一致性好控制 |
| 从库 | 同步数据、处理读 | 分担读压力，可做备份 |

:::figure id=DB00-10-01 | name=主从复制读写分离 | dir=LR
node n1 "写请求" blue
node n2 "主库<br/>处理写" teal
node n3 "从库一<br/>处理读" amber
node n4 "从库二<br/>处理读" amber
node n5 "读请求" green
edge n1 -> n2 "写入"
edge n2 -> n3 "同步数据"
edge n2 -> n4 "同步数据"
edge n5 -> n3 "读取"
edge n5 -> n4 "读取"
:::

图中节点速览：n1 写请求只到主库 n2，n2 把数据同步给两个从库 n3 和 n4，读请求 n5 分散到从库。这样读写分离，读性能随从库数量线性提升，主库挂了还能把从库提升成新主库做容灾。代价是主从之间有时间差，刚写完立刻读可能读到旧值。

### 2. 分区与分片

这两个词容易混，其实层次不同：

- **分区**：把一张大表按规则拆成几块，但还在同一个数据库实例里。比如按月份分区，查询某个月只扫那一个分区。对应用透明。
- **分片**：把数据分散到多个数据库实例甚至多台机器上，每个实例存一部分。这样才能突破单机容量和性能上限。

| 分片方式 | 规则 | 优点 | 缺点 |
|---|---|---|---|
| 按范围 | 按编号或时间区间 | 范围查询快 | 容易热点不均 |
| 按哈希 | 对键取哈希取模 | 分布均匀 | 范围查询要扫所有片 |
| 按列表 | 按地区等枚举值 | 业务贴合 | 需要维护映射 |

### 3. 分库分表带来的新问题

拆分之后，原本简单的查询变复杂了：跨片排序、跨片连接、全局唯一编号、分布式事务都成了难题。这也是后来分布式数据库要解决的问题——把分片的复杂性从应用挪到数据库内部。

## DB00-11 一致性与分布式基础

### 1. CAP 定理

分布式系统有个著名的三选二结论，理解它就理解了为什么不同分布式数据库取舍不同。

| 字母 | 含义 | 说明 |
|---|---|---|
| C | 一致性 | 所有节点看到的数据一样 |
| A | 可用性 | 每次请求都能得到响应 |
| P | 分区容错 | 网络断成几块时仍能运作 |

CAP 说的是：分布式系统里网络分区不可避免，所以 P 是必须接受的，真正的选择是在一致性 C 和可用性 A 之间取舍——要么保证数据一致但可能拒绝服务，要么保证一直可服务但数据可能暂时不一致。

### 2. BASE 理论

BASE 是对 CAP 中"选择可用性"一方的展开，它是基本可用、软状态、最终一致的缩写。核心思想是：不追求时刻强一致，允许中间状态存在，只要最终收敛到一致即可。绝大多数互联网应用接受这个模型，因为用户能容忍短暂的不一致，但容忍不了服务不可用。

### 3. 分布式事务与共识

跨多个节点保证事务一致，比单机难得多，常见手段有：

- **两阶段提交**：先让所有节点预提交，都同意了再统一提交。简单但有阻塞风险。
- **三阶段提交**：在两阶段基础上加一个询问阶段，减少阻塞。
- **共识算法**：如raft、paxos，让多个节点对某个值达成一致，是分布式数据库选主和数据复制的理论基础。

## DB00-12 备份、恢复与高可用

### 1. 备份的两种方式

| 类型 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| 全量备份 | 每次备份全部数据 | 恢复快、简单 | 耗时占空间 |
| 增量备份 | 只备份上次之后的变化 | 快、省空间 | 恢复要先全量再逐个叠加 |

实践中通常定期全量加持续增量，配合前面讲的重做日志，就能恢复到故障前的任意时间点。

### 2. 两个关键指标

- **恢复点目标**：故障发生后最多能丢多少数据。这个数字越小，要求备份和日志越实时。
- **恢复时间目标**：故障后多久必须恢复服务。这个数字越小，要求切换流程越自动化。

金融核心系统往往要求接近零丢失、分钟级恢复，普通内部系统要求可以宽松很多。指标决定方案成本，不是越小越好。

### 3. 高可用架构

高可用不是"不出故障",而是"出了故障用户几乎无感"。常见手段：

- **主从切换**：主库故障，自动把从库提升为主库。
- **多副本**：同一份数据存多份，某份坏了用其他份。
- **异地容灾**：不同城市各放一套，抵御机房级灾难。
- **集群化**：多个节点对外提供统一入口，节点增减不影响服务。

高可用和前面讲的一致性、分区容错是联动的：切换得快可能牺牲一点一致性，要保证强一致可能切换就慢。设计时要根据业务明确取舍。

## DB00-13 数据库系统的三级模式结构

### 1. 为什么要分三层

前面从使用者角度讲了表和 SQL，但一个数据库系统要同时面对三类人：普通用户只关心"我能看到哪些数据",应用开发者关心"表怎么设计",数据库管理员关心"数据放在哪块磁盘、怎么备份"。同一份数据要给这三类人呈现不同的样子，还要在底层存储变化时尽量不影响上面的人。三级模式结构就是为解决这个矛盾而生的经典框架。

### 2. 三级模式分别是什么

| 层级 | 名称 | 面向谁 | 描述什么 |
|---|---|---|---|
| 外层 | 外模式（用户模式） | 用户与应用 | 用户能看到和使用的那部分数据 |
| 中层 | 模式（概念模式） | 数据库设计者 | 全体数据的整体逻辑结构 |
| 内层 | 内模式（存储模式） | 数据库管理员 | 数据怎么存、怎么索引、怎么压缩 |

:::figure id=DB00-13-01 | name=数据库的三级模式结构 | dir=TB
node n1 "外模式<br/>用户看到的样子" blue
node n2 "模式<br/>整体逻辑结构" teal
node n3 "内模式<br/>物理存储结构" amber
node n4 "外模式到模式映像<br/>保证逻辑独立性" green
node n5 "模式到内模式映像<br/>保证物理独立性" purple
edge n1 -> n4 "通过映像"
edge n4 -> n2 "映射"

:::

图中节点速览：n1 外模式是用户视角，n2 模式是全局逻辑结构，n3 内模式是物理存储。n4 和 n5 是两层映像，正是它们带来了数据独立性。

### 3. 两级映像与数据独立性

这是三级模式结构最核心的价值，也是教材里的高频考点。

- **逻辑独立性**：外模式到模式的映像，让"改逻辑结构不影响应用"。比如往客户表里加一列，只需要调整映像，用户原来看到的视图不用变，应用程序不用改。
- **物理独立性**：模式到内模式的映像，让"改存储结构不影响逻辑结构"。比如换了一种索引方式、把数据文件挪到别的磁盘，上层看到的表结构完全不变。

一句话记忆：**映像隔断了变化，让上层不随下层改动而改动**。这就是为什么数据库应用比直接操作文件的程序更好维护。

## DB00-14 关系代数：SQL 背后的数学基础

### 1. 关系代数是什么

SQL 之所以能声明式地"说要什么",是因为它有严格的数学基础——关系代数。关系代数是作用在关系（表）上的一套运算，每种运算输入一张或两张表、输出一张新表。理解它，就理解了 SQL 各种查询的本质，也明白为什么查询可以任意嵌套组合。

### 2. 八种基本运算

| 运算 | 符号含义 | 作用 | 对应 SQL |
|---|---|---|---|
| 选择 | 按条件挑行 | 从表里筛出符合条件的行 | WHERE |
| 投影 | 按列挑选 | 只保留指定的列 | SELECT 列名 |
| 并 | 两表合并 | 合并两表并去重 | UNION |
| 交 | 取共有 | 取两表都有的行 | INTERSECT |
| 差 | 取独有 | 取第一表有、第二表没有的行 | EXCEPT |
| 笛卡尔积 | 所有组合 | 两表行两两配对 | CROSS JOIN |
| 连接 | 按条件配对 | 按条件组合两表的行 | JOIN |
| 除 | 除法 | 处理"全部"类查询 | 需用嵌套实现 |

node n3 "集合运算<br/>并交差" amber
node n4 "二元运算<br/>笛卡尔积与连接" green

图中节点速览：n1 关系代数运算分成四类，n2 对一张表操作，n3 和 n4 对两张表操作，n5 是复合运算。SQL 的复杂查询本质上都是这些运算的组合嵌套。

### 3. 选择、投影与连接

三个最常用的运算要重点理解：

- **选择**：横向筛行。条件作用在行上，选出满足条件的整行。
- **投影**：纵向选列。只保留关心的列，还会去掉重复行。
- **连接**：把两张表按条件拼起来。它其实是笛卡尔积加选择——先两两配对，再挑出满足条件的组合。

理解"连接等于笛卡尔积加选择"很关键：它说明 JOIN 并不是什么神秘操作，而是两个基础运算的组合。优化器 reorder 连接顺序、选择连接算法，本质上都是在算怎么高效完成这个组合。

### 4. 关系运算的封闭性

关系代数有个重要性质：运算的结果还是一张关系（表）。正因为封闭，查询才能一层套一层——一个查询的结果作为下一个查询的输入。SQL 能写出任意复杂的嵌套查询，根基就在这里。

## DB00-15 键与完整性约束

### 1. 键的几种类型

基础篇提过主键和外键，实际上键有一整套概念，教材里经常考。

| 类型 | 定义 | 说明 |
|---|---|---|
| 超键 | 能唯一标识行的列或列组合 | 可能含多余列 |
| 候选键 | 不含多余列的超键 | 最小的唯一标识 |
| 主键 | 从候选键里选一个作代表 | 唯一且非空 |
| 外键 | 引用另一张表主键的列 | 建立表间联系 |
| 代理键 | 人工生成的无业务含义键 | 如自增编号 |

### 2. 三类完整性约束

关系模型定义了三类完整性，它们保证数据"合法":

| 完整性 | 要求 | 例子 |
|---|---|---|
| 实体完整性 | 主键不能为空、不能重复 | 客户编号必须有且唯一 |
| 参照完整性 | 外键的值必须在被引用表里存在 | 订单的客户编号必须是真实客户 |
| 用户定义完整性 | 满足业务自定义规则 | 年龄必须在零到一百五十之间 |

参照完整性还引出"外键指向的行被删除怎么办"的问题，常见处理有：拒绝删除、级联删除、置为空。设计表关系时要明确选择，否则容易出现孤儿数据。

## DB00-16 数据类型与 NULL

### 1. 常见数据类型

建表时每列都要指定类型，类型选得对，既省空间又保证正确。

| 类别 | 常见类型 | 用途 |
|---|---|---|
| 整数 | 小整数、整数、大整数 | 编号、计数 |
| 浮点与定点 | 单精度、双精度、定点数 | 科学计算、金额 |
| 字符 | 定长字符、变长字符 | 姓名、地址 |
| 日期时间 | 日期、时间、时间戳 | 业务时间、记录时间 |
| 布尔 | 真或假 | 开关状态 |
| 二进制与大对象 | 二进制、文本大对象 | 图片、长文本 |

金额这类需要精确计算的数，要用定点数而不是浮点数——浮点数有精度误差，一分钱都可能算错。这是新手最容易踩的坑之一。

### 2. 定长与变长

| 类型 | 特点 | 适合 |
|---|---|---|
| 定长字符 | 固定占空间，多余补空 | 手机号、邮编等长度固定的 |
| 变长字符 | 按实际长度占空间 | 姓名、地址等长度不定的 |

定长的好处是更新时行大小不变、不容易产生碎片；变长的好处是省空间。选哪个看数据长度是否稳定。

### 3. NULL 与三值逻辑

NULL 表示"未知或不存在",它和零、空字符串都不是一回事。这是数据库里最容易出错的概念之一。

| 易错点 | 说明 |
|---|---|
| NULL 不等于 NULL | 两个未知不能判为相等，要用专门的判空语法 |
| NULL 参与运算结果是 NULL | 任何数加未知还是未知 |
| 聚合函数忽略 NULL | 计数某列时不含 NULL，但计数行数含 |
| 唯一约束允许多个 NULL | 多数数据库把 NULL 视为互不相同的未知 |

## DB00-17 视图、存储过程与触发器

### 1. 数据库不只会存表

除了表和索引，数据库里还能存一些"程序化"的对象，它们把常用逻辑放到数据库内部，减少应用重复代码。

| 对象 | 是什么 | 用途 |
|---|---|---|
| 视图 | 一条查询的虚拟表 | 简化复杂查询、控制可见范围 |
| 存储过程 | 预存的一组语句 | 封装业务逻辑、减少网络往返 |
| 函数 | 可返回值的例程 | 复用计算逻辑 |
| 触发器 | 事件自动执行的动作 | 自动审计、级联维护 |

### 2. 视图

视图本身不存数据，它是一条保存起来的查询，用起来像一张表。

| 优点 | 说明 |
|---|---|
| 简化查询 | 把复杂连接封装成简单视图 |
| 安全隔离 | 只暴露部分列，隐藏敏感字段 |
| 逻辑独立 | 底层表变化时改视图即可 |

注意视图可能有更新限制：包含聚合、分组、多表连接的视图通常不能直接修改。

### 3. 存储过程与函数

存储过程是一组预编译的语句，应用调用它而不是逐条发语句。好处是减少网络往返、逻辑集中在数据库、权限控制更细。函数与之类似，但必须返回一个值，可以嵌在查询里用。

### 4. 触发器

触发器在插入、更新、删除发生时自动执行，常用于审计日志、自动维护冗余字段、复杂约束检查。

## DB00-18 连接类型全解

### 1. 连接为什么分这么多种

基础篇提过连接能拼表，但连接方式有很多种，区别在"没匹配上的行怎么办"。这是写查询时最常见的困惑之一。

| 连接类型 | 结果包含什么 |
|---|---|
| 内连接 | 只保留两边都匹配上的行 |
| 左外连接 | 左表全保留，右边没匹配填 NULL |
| 右外连接 | 右表全保留，左边没匹配填 NULL |
| 全外连接 | 两边全保留，没匹配处填 NULL |
| 交叉连接 | 两表所有行的两两组合 |
| 自连接 | 表和自己连接 |

### 2. 内外连接的区别

:::figure id=DB00-18-01 | name=内连接与外连接的区别 | dir=TB

node n2 "内连接<br/>只留共同部分" teal
node n3 "左外连接<br/>左表全留" amber
node n4 "右外连接<br/>右表全留" green
node n5 "全外连接<br/>两边全留" purple
edge n1 -> n2 "方式一"
edge n1 -> n3 "方式二"
edge n1 -> n4 "方式三"

图中节点速览：n1 是待连接的两表，n2 到 n5 是四种连接方式，区别就在"没匹配上的行保不保留、保留哪一边"。

记忆技巧：外连接保留"主表"的全部行，另一边补 NULL。左外连接保留左表、右外连接保留右表。什么时候用外连接？当你需要"即使没有对应记录也要显示主体"时——比如列出所有客户，包括没有下过单的，就该用客户表左外连接订单表。

### 3. 自连接

自连接是表和自己连接，常用于查层级或配对关系。比如员工表里每人有自己的经理编号，要查"某人的经理是谁",就把员工表当两张用，一张代表员工、一张代表经理。给表取不同别名是写自连接的关键。

## DB00-19 事务处理模型与并发问题进阶

### 1. 事务的三种处理模型

前面讲了事务的 ACID 和隔离级别，这里补几个教材常见但容易忽略的模型概念。

| 模型 | 特点 |
|---|---|
| 简单事务 | 一个事务执行到底，出错就整体回滚 |
| 嵌套事务 | 大事务里含子事务，子事务可独立回滚 |
| 分布式事务 | 跨多个节点，靠共识与两阶段提交协调 |

### 2. 调度与可串行化

多个事务交叉执行叫调度。如果调度的结果和"事务一个接一个串行执行"完全一样，就叫可串行化——这是并发正确性的黄金标准。

| 概念 | 含义 |
|---|---|
| 串行调度 | 事务一个接一个，绝对安全但没并发 |
| 并发调度 | 事务交叉执行，性能好但要保证正确 |
| 可串行化 | 并发调度的结果等价于某个串行调度 |

隔离级别里的"串行化",追求的就是可串行化这个正确性标准。

:::figure id=DB00-19-01 | name=调度的正确性标准 | dir=TB
node n1 "多个事务并发执行" blue
node n2 "串行调度<br/>安全但慢" teal
node n3 "并发调度<br/>快但要验证" amber
node n4 "可串行化<br/>并发且结果正确" green
node n5 "冲突检测与加锁<br/>保证可串行化" purple
edge n1 -> n2 "方式一"
edge n1 -> n3 "方式二"
edge n3 -> n4 "等价于串行"
edge n4 -> n5 "靠机制保证"
:::

图中节点速览：n1 多事务并发有 n2 串行和 n3 并发两种调度，n3 若结果等价于串行就是 n4 可串行化，而 n5 的冲突检测与加锁是保证手段。

### 3. 两段锁协议

为了保证可串行化，数据库常用两段锁协议：事务分两个阶段，第一阶段只加锁不释放，第二阶段只释放不加新锁。遵守这个协议就能保证调度可串行化。这也是为什么事务里"先集中加锁、后集中释放"是对的，边加边放容易出问题。

| 语义检索、人工智能向量 | 向量数据库 |

### 3. 五句话记住全文

- 数据库解决四件事：查得快、改得对、坏了能恢复、人多撑得住。
- 事务用四条保证让一组操作要么全成要么全败，靠日志、锁和多版本机制实现。
- 索引是数据的目录，用空间换时间，但不是越多越好。
- 单机不够就复制、分区、分片，代价是要处理一致性和分布式难题。
- 没有最好的数据库，只有最适合场景的——先看数据长什么样、要怎么查，再选型。

读完这篇，你已经有了数据库的完整地图。本系列后续篇目会挑主流数据库逐个深挖：关系型数据库双雄、Redis、NoSQL、分析型数据库、分布式数据库，以及时序、图、向量等专用数据库，每一篇都建立在这篇的基础概念之上。
