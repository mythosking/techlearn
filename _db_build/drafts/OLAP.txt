# 分析型数据库与搜索引擎精讲

**当需求从"查一条"变成"算一千万条"——列式存储、向量化执行、倒排索引，以及它们背后的 OLAP 思维**

## DB05-00 开篇：OLTP 与 OLAP 是两种世界

### 1. 两类负载的根本差异

前面讲的数据库多为联机事务处理，目标是快速处理大量短小的增删改查。而分析型数据库面对的是完全不同的负载：读海量数据、做复杂聚合、一次查询扫描几百万甚至几十亿行。

| 维度 | 联机事务处理 | 联机分析处理 |
|---|---|---|
| 操作 | 增删改查都有，以短事务为主 | 几乎只读，大批量扫描 |
| 数据量 | 每次查少量行 | 每次查海量行 |
| 关注 | 响应时间、并发、事务 | 吞吐、压缩比、聚合速度 |
| 存储 | 行存为主 | 列存为主 |
| 典型 | 下单、支付 | 报表、用户行为分析 |
| 代表 | MySQL、PostgreSQL | ClickHouse、数仓产品 |

### 2. 为什么分析场景要换存储

考虑一个查询："统计过去一年所有订单的总金额"。行存要读出每一行的所有字段，哪怕只关心金额一列——大量无关列被读进内存又丢掉，浪费输入输出和带宽。列存只读取金额这一列，配合压缩，同样的数据量可能少读十倍以上。这就是分析库偏爱列存的根本原因。

## DB05-01 列式存储

### 1. 列存的原理

列存把同一列的数据连续存到一起。这样有三个好处：

- **只读需要的列**：查询涉及哪几列就读哪几列。
- **压缩率高**：同一列数据类型相同、重复多，能用字典编码、行程编码等高效压缩。
- **向量化处理**：一列数据连续排列，能批量加载到中央处理器缓存，一次处理一批。

```text
行存布局：  行1[姓名 年龄 金额] 行2[姓名 年龄 金额] 行3[...]
列存布局：  姓名列[张三 李四 王五] 年龄列[30 25 41] 金额列[299 158 88]
```

### 2. 列存的代价

- 单行增删改慢：一行数据分散在多个列文件，写入要更新多处。
- 不适合点查：取一整行要访问多个列文件再拼回来。
- 事务支持弱：多数列存不擅长高并发事务。

所以列存不是要取代行存，而是各司其职。很多现代系统采用行列混合：热数据行存支撑交易，冷数据列存支撑分析。

### 3. 压缩编码技术

| 编码 | 思路 | 适合 |
|---|---|---|
| 字典编码 | 重复值映射成短整数 | 低基数列，如地区、性别 |
| 行程编码 | 连续相同值记值和次数 | 排序后重复多的列 |
| 增量编码 | 只存相邻值的差 | 有序的数值、时间戳 |
| 位图编码 | 用位表示取值 | 布尔、低基数枚举 |

## DB05-02 ClickHouse

### 1. ClickHouse 为什么快

ClickHouse 是开源的列式分析数据库，以极快的聚合查询著称。它的快来自多方面：

- 列式存储与高压缩比。
- 向量化执行：一次处理一批数据而非一行。
- 并行处理：查询在多个核心和节点上并行。
- 精心优化的聚合、连接算法。
- 数据跳过索引：跳过明显不满足条件的数据块。

### 2. MergeTree 引擎

ClickHouse 的核心是 MergeTree 系列存储引擎。它的工作方式类似 LSM 树：数据按分区写入多个片段，后台不断合并片段。

| 特性 | 说明 |
|---|---|
| 分区 | 按日期等表达式分区，查询可裁剪分区 |
| 排序键 | 数据按排序键有序存，利于范围查询和压缩 |
| 稀疏索引 | 每隔若干行记一个索引点，定位数据块 |
| 数据跳过索引 | 记录块内最值等，跳过不匹配的块 |
| 后台合并 | 小片段合并成大片段，保持查询效率 |

### 3. 分布式查询

ClickHouse 支持分片加副本的分布式架构。查询分发到各分片并行执行，中间结果汇总返回。建表时用分布式表作为统一入口，屏蔽底层分片细节。

### 4. 使用注意

- 擅长大批量导入、批量聚合，不擅长高频单行写入和点更新。
- 没有完整的事务，更新删除是通过标记旧数据实现的"突变"操作，代价高。
- 查询要尽量利用排序键和分区裁剪，否则可能全表扫描。

## DB05-03 数据仓库与湖仓

### 1. 数据仓库是什么

数据仓库是把多个业务系统的数据集中起来，经过清洗、转换后，专门为分析查询服务的数据系统。它和分析型数据库的关系是：数仓是数据与架构层，分析库是支撑它的引擎。

数据仓库的几个核心概念：

| 概念 | 含义 |
|---|---|
| 主题域 | 按业务主题组织，如销售、客户 |
| 星型模型 | 一张事实表加多张维度表 |
| 雪花模型 | 维度表再规范化拆分 |
| 数据集市 | 面向特定部门的小型数仓 |

### 2. 事实表与维度表

星型模型是数仓最经典的建模方式：中间一张事实表记录业务事件（如每笔订单），周围若干维度表描述事件的属性（时间、客户、商品）。

### 3. 数据湖与湖仓一体

数据湖存原始、未加工的各种格式数据，灵活但难管理、质量参差。湖仓一体试图兼得：以开放格式存原始数据，同时提供数仓的事务、治理和查询性能。这是当前大数据架构的重要演进方向。

| 对比 | 数据仓库 | 数据湖 | 湖仓一体 |
|---|---|---|---|
| 数据类型 | 结构化为主 | 结构化半结构化非结构化 | 全都支持 |
| 数据质量 | 高，写入前清洗 | 低，原始堆积 | 写入后治理 |
| 事务 | 支持 | 通常不支持 | 支持 |
| 灵活性 | 低 | 高 | 较高 |
| 适合 | 稳定分析 | 探索与人工智能 | 统一平台 |

## DB05-04 搜索引擎：Elasticsearch

### 1. 为什么需要搜索引擎

数据库擅长精确查询："编号等于一百零一"。但用户输入"附近的便宜酒店"这类模糊需求、或者要在海量文本里找包含某个词并且按相关度排序，传统数据库就力不从心。搜索引擎专治这类全文检索与相关性排序问题。

### 2. 倒排索引

倒排索引是搜索引擎的核心数据结构。传统索引是"文档编号到文档内容",倒排索引反过来——"词到包含它的文档列表"。

```text
文档1："数据库 索引 原理"
文档2："搜索引擎 索引 优化"
文档3："数据库 事务 机制"

倒排索引：
"数据库" → [文档1, 文档3]
"索引"   → [文档1, 文档2]
"事务"   → [文档3]
"搜索"   → [文档2]
```

查"数据库 索引"时，取两个词对应的文档列表求交集，快速得到文档一。

### 3. 分词与中文难点

分词是把文本切成词的过程。英文有空格天然分界，中文没有，需要专门的分词算法和词典。分词粒度影响很大："南京市长江大桥"切成"南京 市 长江大桥"还是"南京市 长 江大桥",结果完全不同。

| 分词方式 | 特点 |
|---|---|
| 按词典最大匹配 | 依赖词典，实现简单 |
| 基于统计与模型 | 更智能，能识别新词 |
| 按字切分 | 中文常用兜底，召回高但精度低 |

### 4. 相关性评分

搜索引擎不只返回"包含关键词"的文档，还要按相关度排序。评分考虑词频（词在文档里出现次数）、逆文档频率（词越稀有越重要）、字段权重等因素。这就是能让最相关的结果排前面的原因。

### 5. Elasticsearch 架构要点

| 概念 | 说明 |
|---|---|
| 索引 | 类似数据库的表，一类文档集合 |
| 分片 | 索引切成多片分布式存储 |
| 副本 | 分片副本，高可用与分担读 |
| 近实时 | 写入后约一秒可被搜索到 |
| 分析器 | 分词加过滤，决定索引怎么建 |

## DB05-05 选型实战

### 1. 按分析需求选

- 海量数据的实时聚合分析、列式扫描 → 分析型数据库，如 ClickHouse。
- 全文检索、模糊匹配、相关度排序 → 搜索引擎，如 Elasticsearch。
- 稳定的企业级报表、主题域建模 → 数据仓库。
- 探索性分析、非结构化数据、人工智能数据准备 → 数据湖或湖仓。
- 交易和分析都要、数据量中等 → 关系库加读写分离或列存扩展。

### 2. 一个常见误区

有人用 Elasticsearch 做所有查询，包括精确统计和事务型更新。Elasticsearch 擅长搜索，但聚合精度和实时性、事务能力都不如专门的分析库或关系库。反过来，用关系库做全文搜索，性能又远不如搜索引擎。正确做法是按查询类型分工。

## DB05-06 本篇小结

分析型数据库和搜索引擎，是为"读海量数据、做复杂计算"而生的两类专用系统。列式存储加向量化执行让聚合查询快到极致，倒排索引加分相关性评分让全文检索变得高效。它们的共性是：放弃高频单行事务，换取批量读写的极致吞吐。

数据库家族到这里已经覆盖了主流场景。下一篇讨论当单机彻底不够用时的终极方案：分布式数据库与分库分表——如何在保持事务能力的同时横向扩展。
