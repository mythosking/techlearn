# 薄篇扩写统一作业规范（提升到"纯叙述汉字 ≥3200"新标准）

## 0. 背景与目标

数据体检发现 VPP / WireGuard-Win / DPDK 三套资料里共 47 篇，按**新口径**（排除图块/代码块/表格后的纯叙述汉字）不足 3200。本轮目标：把这些篇目补到 **严格汉字 ≥3250**（留 50 字余量），与 Snort/SONiC 标准一致。

## 1. 工作范围（硬性）

- **只改** `_audit_all/gap_list.json` 里分配给你的篇目所在的合并稿文件 `drafts/NN.txt`。
- **禁止**改分片文件（如 05a.txt/05b.txt）、脚本、00.txt、SPEC.txt、其他册、交付目录。
- **禁止**运行 build_all.py / merge_parts.py（合并会覆盖你的扩写）。
- 保持 UTF-8 无 BOM、篇号/篇标题/篇数/图 id/图数量**一律不变**；已有表格、代码块、示例**只增不减、不得删除**。

## 2. 扩写口径

"字数"指**纯叙述汉字**：排除 `:::figure` 图块、` ``` ` 代码块、`|` 表格行之后的汉字。补的内容必须是**正文段落**，不要靠堆表格/代码凑数（那是旧口径，无效）。

## 3. 补什么（优先级从高到低，选 2–4 类组合补到达标）

1. **字段/命令联动关系详解**：基于该篇已有表格里的字段或命令，写它们如何互相配合（如 `dev_instance` 如何把 05-05 接口层与 dpdk 设备层缝在一起）。这是字段表篇最自然的扩写来源。
2. **生命周期与数据流叙述**：某结构/命令在"初始化→运行期→销毁"各阶段何时被读写、谁持有、何时释放。
3. **失败模式与边界条件**：什么情况下不生效、误配会怎样、如何验证、有哪些约束（字数上限、并发、版本前置条件）。
4. **典型配置 + 示例输出 + 逐行判读**：一组"命令/配置 + ```text 示例输出（注明"示例输出，具体格式需对照实际版本核验"）+ ≥150 字逐行判读"。示例须基于该篇已有命令，不得虚构新命令。
5. **版本差异与选型判据**：新旧版本行为差异、何时选 A 何时选 B（仅写有把握的方向性结论，具体字段名注明核验）。

## 4. 事实纪律（禁止编造）

- 只基于**本篇及相邻篇已出现的**字段名、命令、路径、函数做延伸；每个具体名都能在本册 drafts 里检索到。
- 确需补充的通用机制背景可以写，但凡涉及具体字段名/默认值/版本号，一律写"需对照实际版本核验"并给出可定位的 `src/...` 路径。
- **禁止**编造函数名、参数名、默认值、性能数字、CLI 关键字。
- **禁止**改表格里已有的字段名（那是此前核验过的权威内容）。

## 5. 去重铁律（不得破坏）

| 内容 | 唯一权威源 |
|---|---|
| 结构体逐字段定义 | 05 全册 |
| CLI 命令 / startup.conf 全参数 | 04 全册 |
| 机制、调度、调用链 | 06 全册 |
| 模块功能与组网 | 07 全册 |

- 07/08 篇不得重列完整字段表或 show/clear 命令清单，写"字段见 05-xx ｜ 命令见 04-xx"。
- 04 篇不展开转发原理与结构字段；05 篇不展开机制流程。
- 扩写的叙述是"解读/联动/边界"，不是把别的册的正文搬过来。
- 交叉引用统一写法：`（字段见 05-xx ｜ 命令见 04-xx ｜ 原理见 06-xx）`。

## 6. 操作方法（避免写坏文件）

1. 先 Read 目标篇全文（从 `## NN-NN` 到下一篇 `## NN-NN` 之前），确认结构与已有内容。
2. 用 **Edit 定点插入**：在某节的段落之后、下一节标题之前，插入 1–3 个新段落（必要时新增一个 `#### 3.x` 或 `### N.` 小节，但篇内小节编号要连续）。
3. **严禁 Write 整文件覆盖**——会毁掉同文件其它篇。只用 Edit。
4. 一次 Edit 处理一篇；一篇完成后再处理下一篇。

## 7. 完成前自检（必做）

对本文件所有分配篇目，用与 gap_list.py 一致的口径重新统计每篇纯叙述汉字，确认 **每篇 ≥3250**。可用：

```bash

C:/Python314/python.exe gap_list.py | grep -E "<你的项目>"
```

分配给你且出现在缺口清单里的篇目应为 0 条（或 cjk 已 ≥3200）。

完成后报告：文件名、处理的篇号列表、每篇扩写后字数、是否有未完成项。报告即收工。
